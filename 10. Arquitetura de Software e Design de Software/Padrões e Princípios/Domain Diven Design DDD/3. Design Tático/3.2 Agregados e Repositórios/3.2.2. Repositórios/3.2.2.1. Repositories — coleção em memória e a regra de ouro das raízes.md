### Repositories — coleção em memória e a regra de ouro das raízes

Um **Repository** (repositório) dá ao domínio a **ilusão de uma coleção de objetos em memória**: você adiciona, remove e busca Aggregates como se estivesse mexendo numa lista, sem saber se atrás há SQL, MongoDB ou uma API. Ele esconde a complexidade da persistência e mantém o modelo de domínio rico, e tem uma regra de ouro: **só existe repositório para Aggregate Roots**.

---

## O problema que ele resolve

A complexidade técnica do acesso a dados tende a **invadir o código do domínio**. Evans descreve o efeito: a infraestrutura de banco "afoga" o código cliente, o que leva os desenvolvedores a **empobrecer a camada de domínio**, e o modelo se torna irrelevante. Consultas sem restrição também causam estrago:

- puxam campos soltos dos objetos, **violando o encapsulamento**;
- instanciam objetos do **interior** de um Aggregate sem passar pela raiz, impedindo que ela faça valer as regras do domínio;
- empurram a lógica para consultas e camada de aplicação, e as entidades viram **meros contêineres de dados**.

**Analogia:** um arquivo de pastas num escritório. Você pede "o processo nº 123" ao arquivista e recebe o processo completo; não precisa saber em que gaveta, prédio ou sistema ele está guardado. O repositório é esse arquivista.

```
 ┌───────────── Domínio / Aplicação ─────────────┐        ┌────── Infraestrutura ──────┐
 │                                               │        │                            │
 │  CasoDeUso ──usa──► PedidoRepository          │        │  JpaPedidoRepository       │
 │                     (INTERFACE, na linguagem  │◄───────┤  (IMPLEMENTA a interface)  │
 │                      do domínio)              │        │       │                    │
 │                                               │        │       ▼                    │
 └───────────────────────────────────────────────┘        │  Banco / ORM / API         │
        o domínio não conhece a tecnologia                └────────────────────────────┘
```

---

## A definição (Evans)

Para cada tipo de Aggregate que precisa de acesso global, crie um serviço que dê a **ilusão de uma coleção em memória** de todos os objetos do tipo da raiz. Ele deve:

| Característica | Descrição |
|---|---|
| **Interface conhecida** | Acesso por uma interface global bem definida |
| **Adicionar e remover** | Métodos que encapsulam a inserção e a remoção reais no armazenamento |
| **Consultas com critérios do negócio** | Métodos que selecionam objetos por critérios que fazem sentido para os especialistas de domínio |
| **Objetos completos** | Devolve objetos totalmente instanciados (ou proxies que dão essa ilusão com carga preguiçosa) |
| **Esconde a tecnologia** | Encapsula o armazenamento e a tecnologia de consulta |
| **Só para raízes** | Repositórios apenas para Aggregate Roots que realmente precisam de acesso direto |

O objetivo final: manter a lógica da aplicação **focada no modelo**, delegando todo o armazenamento e acesso aos repositórios.

## A regra de ouro: um repositório por Aggregate Root

```
 Aggregate Pedido
 ┌──────────────────────────────────┐
 │  Pedido (RAIZ) ◄─── PedidoRepository   ✅ existe
 │    ├─ ItemPedido  (interno)       │
 │    └─ EnderecoEntrega (VO)        │     ❌ NÃO existe ItemPedidoRepository
 └──────────────────────────────────┘        (item só é acessado via Pedido)
```

| Por quê | Explicação |
|---|---|
| **Consistência** | Os objetos internos só são alterados pela raiz, que garante as invariantes |
| **Transação** | Um Aggregate é carregado e salvo **inteiro**, como unidade |
| **Encapsulamento** | Ninguém "pesca" um `ItemPedido` solto e o modifica sem passar pelas regras do `Pedido` |
| **Simplicidade** | Menos repositórios; a fronteira do Aggregate fica clara |

## Exemplo prático

```java
// 1) INTERFACE no domínio: linguagem do negócio, sem tecnologia
public interface PedidoRepository {
    void salvar(Pedido pedido);                               // "adicionar" à coleção
    Optional<Pedido> buscarPorId(PedidoId id);
    List<Pedido> buscarPendentesDoCliente(ClienteId cliente); // critério do negócio
    void remover(Pedido pedido);
}

// 2) IMPLEMENTAÇÃO na infraestrutura (adaptador): só ela conhece o JPA
@Repository
class JpaPedidoRepository implements PedidoRepository {
    private final PedidoJpaDao dao;          // Spring Data
    private final PedidoMapper mapper;       // domínio ↔ entidade JPA

    public void salvar(Pedido pedido) {
        dao.save(mapper.paraEntidade(pedido));          // grava o Aggregate inteiro
    }
    public Optional<Pedido> buscarPorId(PedidoId id) {
        return dao.findById(id.valor()).map(mapper::paraDominio);
    }
    public List<Pedido> buscarPendentesDoCliente(ClienteId cliente) {
        return dao.findByClienteIdAndStatus(cliente.valor(), "PENDENTE")
                  .stream().map(mapper::paraDominio).toList();
    }
    public void remover(Pedido pedido) { dao.deleteById(pedido.id().valor()); }
}

// 3) Fake em memória para testes (sem banco)
class PedidoRepositoryEmMemoria implements PedidoRepository {
    private final Map<PedidoId, Pedido> dados = new HashMap<>();
    public void salvar(Pedido p) { dados.put(p.id(), p); }
    public Optional<Pedido> buscarPorId(PedidoId id) { return Optional.ofNullable(dados.get(id)); }
    // ...
}
```

**Explicando o exemplo:**
- A **interface** pertence ao domínio e usa a **linguagem ubíqua** (`buscarPendentesDoCliente`), em vez de `findByStatusAndCliente...` genérico.
- A **implementação** fica na infraestrutura; trocar JPA por outro banco significa escrever outra classe.
- O **fake em memória** permite testar casos de uso sem banco e sem rede.
- Isso é exatamente **Ports & Adapters**: a interface é a *porta de saída*, e `JpaPedidoRepository` é o *adaptador* (veja o guia de Arquitetura Hexagonal).

## Repository, DAO e Spring Data: qual a diferença?

| | Repository (DDD) | DAO | Spring Data `JpaRepository` |
|---|---|---|---|
| **Visão** | Coleção de Aggregates | Acesso a uma tabela ou fonte | Interface de acesso gerada por framework |
| **Linguagem** | Do domínio | Da persistência | Da persistência |
| **Unidade** | Aggregate Root | Entidade de tabela | Entidade JPA |
| **Quem define** | O domínio | A infraestrutura | O framework |

Fowler descreve o Repository como uma camada entre o domínio e a camada de mapeamento de dados, apresentando os objetos de domínio por uma **interface semelhante a uma coleção**, com consultas descritas de forma declarativa. O ganho é concentrar a construção de consultas num lugar e manter uma dependência de mão única: do domínio para a camada de dados.

> [!note] Spring Data no domínio?
> Estender `JpaRepository<PedidoEntity, Long>` direto no domínio traz tipos do framework para dentro dele. Uma abordagem comum: manter a interface do domínio própria e **usar o Spring Data apenas dentro do adaptador** (como no exemplo, `PedidoJpaDao`). Em domínios simples ou de suporte, usar `JpaRepository` direto pode ser um compromisso aceitável.

## Quem controla a transação?

O repositório **não** abre nem fecha transações. Quem delimita a unidade de trabalho é a **camada de aplicação** (o caso de uso), que carrega o Aggregate, chama seus métodos de negócio e o salva, numa única transação:

```java
@Transactional
public void confirmarPagamento(PedidoId id) {
    Pedido pedido = repo.buscarPorId(id).orElseThrow();   // carrega o Aggregate
    pedido.confirmarPagamento();                          // regra no domínio
    repo.salvar(pedido);                                  // persiste o Aggregate inteiro
}
```

## Consultas de leitura e relatórios

O repositório serve para **carregar Aggregates e executar comandos**. Para telas, listagens e relatórios, que precisam de dados agregados ou de várias raízes, carregar Aggregates inteiros é caro e desnecessário. Soluções:

| Abordagem | Quando |
|---|---|
| **Consulta direta para DTO/projeção** (query service) | Listagens e relatórios simples |
| **Modelo de leitura separado (CQRS)** | Leitura e escrita com necessidades muito diferentes |
| **View/tabela otimizada para leitura** | Relatórios pesados |

Assim o repositório continua pequeno e focado no Aggregate, e as consultas complexas não o contaminam.

## Erros comuns

| Erro | Consequência |
|---|---|
| **Repositório por tabela** (em vez de por Aggregate Root) | Acesso a objetos internos sem passar pela raiz; invariantes violadas |
| Repositório genérico `findAll()` sem critério de negócio | Linguagem pobre; consultas espalhadas e sem controle |
| Devolver **objetos internos** do Aggregate | Quebra o encapsulamento |
| **Lógica de negócio** dentro do repositório | O domínio fica anêmico; a regra se esconde na infraestrutura |
| Deixar **tipos de persistência** (`Page`, `Specification`, entidades JPA) vazar para o domínio | Acopla o domínio ao framework |
| Carga preguiçosa vazando (`LazyInitializationException`) | O Aggregate precisa estar completo ao sair do repositório |
| Repositório controlando transações | Mistura responsabilidades; a transação é da camada de aplicação |
| Usar repositórios para relatórios complexos | Carrega Aggregates inteiros à toa; prefira consultas de leitura |

## 🧩 Quiz de Fixação

1. O que significa dizer que o repositório dá a "ilusão de uma coleção em memória"?
2. Por que só deve existir repositório para Aggregate Roots? Dê um exemplo do que não deve existir.
3. Onde ficam a interface e a implementação do repositório numa arquitetura Hexagonal, e que ganho isso traz para os testes?

**Respostas:**
1) Que o domínio usa o repositório como uma lista: adiciona, remove e busca Aggregates por critérios do negócio, sem saber como ou onde eles são armazenados (SQL, NoSQL, API). A tecnologia de armazenamento e de consulta fica encapsulada atrás da interface.
2) Porque o Aggregate é a unidade de consistência: os objetos internos só podem ser alterados pela raiz, que garante as invariantes, e o Aggregate é carregado e salvo inteiro. Um `ItemPedidoRepository` não deve existir, pois permitiria buscar e alterar um item sem passar pelo `Pedido` e suas regras. O acesso ao item é sempre via `Pedido`.
3) A **interface** (porta de saída) fica no domínio, na linguagem do negócio. A **implementação** (adaptador, por exemplo JPA) fica na infraestrutura. Nos testes, basta uma implementação **em memória** (fake) da interface, o que permite testar casos de uso e regras do domínio sem banco, de forma rápida e determinística.
