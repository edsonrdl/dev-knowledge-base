### Value Objects — sem identidade e imutáveis

Um **Value Object** (objeto de valor) é um objeto do domínio definido **apenas pelos seus atributos**, sem identidade própria. Dois Value Objects com os mesmos valores são **o mesmo valor**: `Dinheiro(100, BRL)` é intercambiável com qualquer outro `Dinheiro(100, BRL)`. Eles são imutáveis e carregam o significado e as regras do que descrevem, o que os torna o bloco mais barato e mais poderoso do design tático.

---

## O conceito central

Segundo Evans, muitos objetos **não têm identidade conceitual**: eles descrevem ou calculam uma característica de uma coisa. Rastrear identidade é essencial para entidades, mas atribuí-la a outros objetos pode prejudicar o desempenho, gerar trabalho de análise e embaralhar o modelo, fazendo tudo parecer igual.

**Analogia:** uma nota de R$ 20. Para pagar uma conta, qualquer nota de R$ 20 serve; ninguém liga para qual delas é. Já o seu **cartão de banco** é uma entidade: um cartão específico, rastreado, com número. A nota é um valor; o cartão é uma entidade.

A regra de Evans: quando você se importa apenas com os **atributos e a lógica** de um elemento do modelo, classifique-o como Value Object. Faça-o expressar o significado dos atributos, dê-lhe funcionalidade relacionada, trate-o como **imutável**, faça todas as operações serem **funções sem efeitos colaterais**, e **não lhe dê identidade**.

```
  ENTITY                                   VALUE OBJECT

  Cliente #42 ≠ Cliente #43                Dinheiro(50, BRL) == Dinheiro(50, BRL)
  (mesmo nome? ainda diferentes)           (mesmos valores = mesmo objeto)

  muda ao longo da vida                    nunca muda: "alterar" = criar outro
  Cliente#42.mudarNome(...)                preco.somar(frete)  → NOVO Dinheiro
```

---

## As quatro características

| Característica | O que significa | Por quê |
|---|---|---|
| **Igualdade por valor** | `equals` compara todos os atributos | Dois iguais são intercambiáveis |
| **Imutabilidade** | Sem setters; nenhuma operação altera o objeto | Evita bugs de *aliasing* e permite compartilhar com segurança |
| **Sem identidade** | Não tem ID nem ciclo de vida rastreado | Menos complexidade e custo |
| **Auto-validação e comportamento** | Garante a própria validade e oferece operações do conceito | A regra mora junto do dado |

### O bug de aliasing (por que imutável)

Fowler mostra o clássico: duas variáveis apontam para o **mesmo objeto de data mutável**; ao alterar a data da festa, a data da aposentadoria muda junto, sem ninguém perceber. Com Value Objects imutáveis, "alterar" cria um novo objeto, e quem tinha o antigo **não é afetado**.

```java
// ❌ Mutável: o aliasing causa o bug
Data festa = new Data(2026, 6, 10);
Data aposentadoria = festa;          // mesma referência
festa.setAno(2027);                  // a aposentadoria também mudou!

// ✅ Imutável: nada é afetado
Data festa = Data.de(2026, 6, 10);
Data aposentadoria = festa;
Data festaAdiada = festa.maisAnos(1);  // novo objeto; 'aposentadoria' intacta
```

## Exemplo prático

```java
// Value Object com validação, igualdade por valor e operações puras
public record Dinheiro(long centavos, Moeda moeda) {

    public Dinheiro {                                   // auto-validação no construtor
        Objects.requireNonNull(moeda);
        if (centavos < 0) throw new IllegalArgumentException("Valor negativo");
    }

    public static Dinheiro reais(String valor) {        // construção com significado
        return new Dinheiro(new BigDecimal(valor).movePointRight(2).longValueExact(), Moeda.BRL);
    }

    public Dinheiro somar(Dinheiro outro) {             // função sem efeito colateral
        exigirMesmaMoeda(outro);
        return new Dinheiro(centavos + outro.centavos, moeda);   // devolve NOVO objeto
    }

    public Dinheiro multiplicar(int fator) {
        return new Dinheiro(centavos * fator, moeda);
    }

    private void exigirMesmaMoeda(Dinheiro outro) {
        if (moeda != outro.moeda) throw new MoedasDiferentesException(moeda, outro.moeda);
    }
}

// Uso: expressivo e seguro
Dinheiro total = Dinheiro.reais("19.90").multiplicar(3).somar(Dinheiro.reais("12.00"));
```

**Explicando o exemplo:**
- `record` já dá **igualdade por valor** e **imutabilidade** (campos finais, sem setters).
- O construtor **valida**: é impossível existir um `Dinheiro` negativo ou sem moeda. O objeto nunca é inválido.
- `somar` e `multiplicar` **não alteram `this`**: devolvem um novo `Dinheiro`.
- A regra "não somar moedas diferentes" mora **no próprio Value Object**, e não espalhada pelo sistema.
- Usar `long` em centavos evita erros de ponto flutuante com dinheiro.

## O que é (e o que não é) um bom Value Object

| Bons candidatos | Por quê |
|---|---|
| `Dinheiro`, `Moeda` | Valor e unidade andam juntos; regras de soma |
| `Endereco`, `Cep` | Conjunto de atributos sem identidade própria |
| `Email`, `Cpf`, `Telefone` | Validação de formato num lugar só |
| `Periodo` / `IntervaloDeDatas` | Regras como "início antes do fim" |
| `Quantidade`, `Percentual`, `Peso` | Evitam operações sem sentido e unidades trocadas |
| `PedidoId`, `ClienteId` | Identificadores tipados (o *ID* é um VO, embora identifique uma Entity) |

Fowler acrescenta que objetos pequenos como pontos, valores monetários, intervalos de datas e telefones tornam o código mais explícito, dão à validação um lugar natural e impedem operações sem sentido (como somar IDs). **Estruturas maiores** também podem ser Value Objects, desde que não tenham identidade conceitual.

---

## Combatendo a "obsessão por primitivos"

O antipadrão oposto é usar `String`, `int` e `BigDecimal` para tudo (*primitive obsession*):

| Com primitivos | Com Value Objects |
|---|---|
| `void pagar(String cpf, BigDecimal valor, String moeda)` | `void pagar(Cpf cpf, Dinheiro valor)` |
| Pode passar `moeda` onde esperava `cpf` | O compilador impede a troca |
| Validação do CPF repetida em vários lugares | Validação única no construtor de `Cpf` |
| O significado vive só na cabeça de quem lê | O tipo **expressa a linguagem ubíqua** (veja 1.1.2.1) |

---

## Entity ou Value Object? Depende do contexto

O mesmo conceito pode mudar de papel. Fowler cita o endereço postal: pode ser um Value Object num sistema e uma entidade referenciada em outro.

| Contexto | Endereço é... | Por quê |
|---|---|---|
| Entrega de um pedido | **Value Object** | Só importam os campos; trocar o endereço = novo valor |
| Cadastro de imóveis, cartório | **Entity** | O imóvel é rastreado, tem matrícula, histórico |

**Teste prático:** se dois objetos com os mesmos atributos podem ser **trocados um pelo outro** sem que o negócio perceba, é Value Object. Se importa **qual** deles é, é Entity (veja 3.1.1.1).

---

## Persistência

Value Objects **não têm tabela própria** na maioria dos casos: são gravados **dentro** do dono.

| Técnica | Quando |
|---|---|
| **Colunas embutidas** (`@Embeddable` no JPA) | VO composto (`Endereco` → `rua`, `cidade`, `cep`) |
| **Conversor de atributo** (`AttributeConverter`) | VO de um valor (`Cpf`, `Email`) gravado como uma coluna |
| **Coleção de elementos** (`@ElementCollection`) | Lista de VOs dentro de uma entidade |

Como são imutáveis, atualizar significa **substituir** o VO inteiro no dono.

---

## Erros comuns

| Erro | Consequência |
|---|---|
| Value Object **mutável** (com setters) | Bugs de aliasing; perde o benefício de compartilhar com segurança |
| Dar ID a algo que é só valor | Complexidade e custo desnecessários |
| Validar **fora** do VO | Objetos inválidos circulam; validação repetida |
| Operações com efeito colateral | Quebra a imutabilidade e a previsibilidade |
| Usar `double` para dinheiro | Erros de arredondamento; use inteiros em centavos ou `BigDecimal` |
| VO gigante com dezenas de campos | Provavelmente é uma entidade ou precisa ser dividido |
| Esquecer `equals/hashCode` por valor | Comparações erradas (em Java, `record` resolve) |

## 🧩 Quiz de Fixação

1. Qual a diferença entre Entity e Value Object quanto à igualdade e à mutabilidade?
2. Por que a imutabilidade é importante num Value Object? Descreva o bug de aliasing.
3. Reescreva `void pagar(String cpf, BigDecimal valor, String moeda)` usando Value Objects e liste dois ganhos.

**Respostas:**
1) A Entity é igual a outra pela **identidade** (ID) e é mutável de forma controlada ao longo de um ciclo de vida. O Value Object é igual por **todos os valores** dos atributos, é imutável e intercambiável: "alterar" significa criar um novo objeto.
2) Se o objeto é mutável e duas variáveis apontam para ele, alterá-lo por uma referência muda o valor visto pela outra, sem aviso (aliasing). Exemplo: a data da festa e a da aposentadoria compartilham o mesmo objeto de data; ao adiar a festa, a aposentadoria também muda. Com imutabilidade, a operação devolve um novo objeto e quem tinha o antigo não é afetado.
3) `void pagar(Cpf cpf, Dinheiro valor)`. Ganhos: (a) o compilador impede trocar os argumentos e o tipo expressa o conceito do negócio; (b) a validação do CPF e a regra de moeda ficam em um só lugar (nos construtores/métodos dos VOs), em vez de repetidas em todos os pontos de uso. Também vale: operações de domínio (`somar`) ficam junto do dado.
