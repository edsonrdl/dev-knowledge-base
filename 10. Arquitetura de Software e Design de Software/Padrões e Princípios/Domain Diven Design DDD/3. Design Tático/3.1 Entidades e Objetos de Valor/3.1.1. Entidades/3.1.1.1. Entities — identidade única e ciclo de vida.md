### Entities — identidade única e ciclo de vida

Uma **Entity** (entidade) é um objeto do domínio definido pela sua **identidade**, e não pelos seus atributos. Ao longo da vida ela muda (nome, endereço, status), mas continua sendo **a mesma coisa**. Entidades são o primeiro bloco do design tático do DDD, e entender o que as torna "a mesma" é a base para modelar Aggregates, Repositories e eventos.

---

## O conceito central

Segundo Eric Evans, muitos objetos representam um **fio de continuidade e identidade** que atravessa um ciclo de vida, ainda que seus atributos mudem. Alguns objetos não são definidos principalmente pelos atributos: é preciso distingui-los de outros **mesmo que tenham os mesmos atributos**, e às vezes casá-los com outro objeto **mesmo que os atributos difiram**. Confundir identidades pode corromper dados.

**Analogia:** você. Seu nome, endereço, cabelo, emprego e até o peso mudam ao longo dos anos, mas você continua sendo você, identificado pelo CPF. E dois homônimos, com o mesmo nome e a mesma data de nascimento, são pessoas diferentes. A identidade não está nos atributos.

```
  ENTITY (identidade importa)                 NÃO é Entity (atributos importam)

  Cliente #42  "Ana Souza"  Rua A             Dinheiro(100, BRL)
        │  muda de nome e endereço                 │
        ▼                                          ▼
  Cliente #42  "Ana Lima"   Rua B             Dinheiro(100, BRL)  ==  qualquer outro
  continua sendo o mesmo Cliente              Dinheiro(100, BRL)  (intercambiáveis)
```

---

## As três marcas de uma Entity

| Marca | Descrição | Exemplo |
|---|---|---|
| **Identidade única** | Um identificador que distingue o objeto durante toda a vida | `ClienteId`, `PedidoId` |
| **Ciclo de vida** | Passa por estados ao longo do tempo (criado, ativo, cancelado...) | Pedido: `CRIADO → PAGO → ENVIADO` |
| **Mutabilidade controlada** | Os atributos mudam, mas só por operações que respeitam as regras | `pedido.cancelar()`, e não `setStatus(...)` |

A regra de modelagem de Evans: quando um objeto se distingue pela identidade, **torne isso primário na definição**; mantenha a classe simples e focada na **continuidade do ciclo de vida e na identidade**. O modelo precisa definir o que significa "ser a mesma coisa".

## Identidade na prática

A identidade deve ser **garantidamente única** e **corresponder às distinções do modelo**. Ela pode vir de fora ou ser um identificador arbitrário criado pelo sistema.

| Estratégia | Como | Prós | Contras |
|---|---|---|---|
| **UUID/ULID gerado pela aplicação** | O domínio cria o ID ao instanciar | Existe antes de persistir; funciona em sistemas distribuídos | Menos legível; escolha o formato (ULID ordena por tempo) |
| **Sequência do banco** | O banco gera ao salvar | Simples, compacto | O ID só existe depois do `INSERT`; acopla o domínio à persistência |
| **Chave natural** (CPF, ISBN) | Dado do negócio | Significativa | Pode mudar, ter erros ou restrições legais; cuidado |
| **Número de negócio** (nº do pedido) | Gerado por regra de negócio | Amigável ao usuário | Exige geração segura e sem colisão |

**Boa prática:** envolver o ID num **Value Object tipado** (`PedidoId`) em vez de `String` ou `Long` soltos. Isso evita trocar o ID de um cliente pelo de um pedido por engano, e deixa o código mais expressivo.

## Exemplo prático

```java
// O ID é um Value Object: tipado, imutável, sem confusão com outros IDs
public record ClienteId(UUID valor) {
    public static ClienteId novo() { return new ClienteId(UUID.randomUUID()); }
}

public class Cliente {
    private final ClienteId id;          // identidade: nunca muda
    private String nome;                 // atributos: mudam
    private Email email;
    private StatusCliente status;        // ciclo de vida

    public Cliente(ClienteId id, String nome, Email email) {
        this.id = Objects.requireNonNull(id);
        this.nome = validarNome(nome);
        this.email = Objects.requireNonNull(email);
        this.status = StatusCliente.ATIVO;
    }

    // Comportamento com nome do negócio e regra protegida
    public void alterarEmail(Email novoEmail) {
        if (status == StatusCliente.BLOQUEADO)
            throw new ClienteBloqueadoException(id);
        this.email = Objects.requireNonNull(novoEmail);
    }

    public void bloquear() { this.status = StatusCliente.BLOQUEADO; }

    // Igualdade pela IDENTIDADE, e não pelos atributos
    @Override public boolean equals(Object o) {
        return o instanceof Cliente outro && id.equals(outro.id);
    }
    @Override public int hashCode() { return id.hashCode(); }
}
```

**Explicando o exemplo:**
- `id` é `final`: a identidade nunca muda. Nome, e-mail e status mudam, mas só por métodos de negócio.
- `alterarEmail` **protege uma regra** (cliente bloqueado não altera dados). A regra mora na entidade, e não num serviço que a manipula por fora.
- `equals/hashCode` usam **só o ID**: dois objetos `Cliente` com o mesmo ID representam o mesmo cliente, ainda que os atributos estejam em estados diferentes.

> [!note] Sobre `equals` em entidades
> Fowler observa que, na descrição clássica, entidades normalmente não sobrescrevem a igualdade, porque em um contexto de processamento deve haver **um único objeto** por entidade conceitual. Na prática, comparar pelo ID é uma convenção comum e segura. O essencial é nunca comparar entidades pelos atributos.

## Entity vs Value Object

| Aspecto | Entity | Value Object |
|---|---|---|
| **Define-se por** | Identidade | Atributos |
| **Igualdade** | Pelo ID | Por todos os valores |
| **Mutabilidade** | Muda ao longo da vida | Imutável: alterar = criar outro |
| **Ciclo de vida** | Sim, rastreado | Não |
| **Exemplos** | `Cliente`, `Pedido`, `Conta` | `Dinheiro`, `Endereço`, `Cpf` |
| **Trocável?** | Não: cada uma é única | Sim: dois iguais são intercambiáveis |

O mesmo conceito pode ser Entity ou Value Object **conforme o contexto**: um endereço de entrega é um Value Object num pedido, mas poderia ser uma Entity num sistema de cadastro de imóveis, onde o próprio imóvel precisa ser rastreado. Veja Value Objects em 3.1.2.1.

## Entidade com comportamento (e não modelo anêmico)

Uma entidade **não é só um saco de getters e setters**. Evans diz que a entidade é responsável por rastrear seu estado e pelas regras que regem seu ciclo de vida.

| | Entidade rica (DDD) | Modelo anêmico |
|---|---|---|
| **Regras** | Dentro da entidade | Num serviço externo |
| **Estado** | Alterado por métodos de negócio | Alterado por setters públicos |
| **Invariantes** | Garantidas pelo próprio objeto | Dependem de quem chama |
| **Linguagem** | `pedido.cancelar()` | `pedido.setStatus(CANCELADO)` |

O modelo anêmico não é proibido: serve para domínios simples, de suporte ou CRUD (veja 2.1.2.1). No Core Domain, o modelo rico é onde o DDD entrega valor.

## Entity de domínio vs entity de persistência (JPA)

Em projetos com JPA, a classe `@Entity` costuma ser um **modelo de persistência**, com construtor vazio e setters exigidos pelo framework. Isso difere da **Entity de domínio**, que protege invariantes.

| Estratégia | Quando |
|---|---|
| **Mesma classe** com anotações JPA | Domínios simples; aceita algum acoplamento ao framework |
| **Classes separadas** (domínio + persistência) com um mapeador | Domínio rico e isolado, como nas arquiteturas Hexagonal e Clean |

Veja a separação nos guias de Arquitetura Hexagonal e Clean Architecture.

## Erros comuns

| Erro | Consequência |
|---|---|
| Comparar entidades pelos atributos | Duas pessoas homônimas viram "a mesma"; ou o mesmo objeto vira "diferente" ao mudar um campo |
| Identidade que muda (e-mail como ID) | Referências quebram; o "mesmo" objeto vira outro |
| Setters públicos para tudo | Invariantes violadas; regras espalhadas |
| `Long`/`String` soltos como ID | Troca de IDs entre tipos sem o compilador perceber |
| Dar identidade a tudo | Complexidade desnecessária; use Value Object quando identidade não importa |
| Depender do ID gerado pelo banco para criar o objeto | O domínio fica preso à persistência e o objeto não existe antes do `INSERT` |
| Entidade que expõe coleções internas modificáveis | Regras contornadas; encapsule e exponha cópias imutáveis |

## 🧩 Quiz de Fixação

1. O que define uma Entity e o que a diferencia de um Value Object?
2. Por que o ID deve ser imutável e, de preferência, um tipo próprio (`ClienteId`) em vez de `String`?
3. Por que `pedido.cancelar()` é melhor do que `pedido.setStatus(CANCELADO)` no Core Domain?

**Respostas:**
1) A Entity é definida pela **identidade**, que persiste ao longo do ciclo de vida mesmo que os atributos mudem; é comparada pelo ID e é mutável de forma controlada. O Value Object é definido pelos **atributos**, é imutável e intercambiável: dois com os mesmos valores são iguais. A pergunta-chave é se importa saber *qual* objeto é, ou apenas *quais valores* ele tem.
2) Se o ID mudasse, o objeto "viraria outro", e as referências a ele quebrariam. Um tipo próprio (`ClienteId`) impede trocar acidentalmente o ID de um cliente pelo de um pedido, pois o compilador diferencia os tipos, e deixa o código mais expressivo, além de concentrar a validação e a geração do ID.
3) Porque `cancelar()` tem nome do negócio (linguagem ubíqua) e **protege as regras e invariantes** (por exemplo, não cancelar um pedido já enviado), garantindo que o objeto nunca fique num estado inválido. O `setStatus` deixa qualquer chamador mudar o estado sem validação, espalhando as regras pelo sistema (modelo anêmico).
