### Linguagem Ubíqua e seu reflexo exato no código

A Linguagem Ubíqua (*Ubiquitous Language*) é o vocabulário único e preciso que desenvolvedores e especialistas de negócio constroem juntos e usam em **tudo**: conversas, documentos, testes e código. É o pilar mais barato e mais negligenciado do DDD, e é o que sustenta todo o resto da modelagem.

---

## O problema que ela resolve

Em projetos comuns, cada grupo fala um dialeto. O negócio diz "apólice", o analista escreve "contrato", o código tem `PolicyEntity` e o banco tem a tabela `TB_CTR`. Toda conversa exige uma tradução mental, e é nessas traduções que nascem os bugs e os requisitos mal entendidos.

```
 SEM linguagem ubíqua                      COM linguagem ubíqua

 Negócio:   "apólice"                      Negócio:   "apólice"
     │ tradução                                │
 Analista:  "contrato"                     Analista:  "apólice"
     │ tradução                                │
 Código:    PolicyEntity                   Código:    Apolice
     │ tradução                                │
 Banco:     TB_CTR                         Banco:     apolice
 
 4 nomes para 1 conceito                   1 nome em todos os lugares
```

**Analogia:** é como um grupo de viagem que combina um idioma comum antes de sair. Sem isso, cada um interpreta do seu jeito e ninguém percebe até algo dar errado.

---

## O conceito central

Eric Evans define a Linguagem Ubíqua como uma linguagem comum e rigorosa, construída em conjunto por desenvolvedores e usuários e baseada no **modelo de domínio**. Ela precisa ser rigorosa porque software não lida bem com ambiguidade.

Ideias-chave:

| Ideia | Significado |
|---|---|
| **Construída em conjunto** | Não é o dicionário do dev nem o do negócio, é um acordo entre os dois |
| **Rigorosa** | Cada termo tem um significado só, dentro do seu contexto |
| **Testa o modelo** | Falar o modelo em voz alta com os especialistas revela termos estranhos ou errados |
| **Evolui** | Quando o entendimento do domínio muda, a linguagem e o modelo mudam junto |
| **Reflete-se no código** | Nomes de classes, métodos e variáveis usam os mesmos termos |

> Se o código precisa de um "glossário de tradução" para ser entendido pelo negócio, a linguagem não é ubíqua.

---

## Como ela aparece no código

O termo do negócio deve aparecer **exatamente igual** nas classes, nos métodos, nos eventos e nos testes.

```java
// ❌ Linguagem técnica genérica: ninguém do negócio reconhece
public class ContractEntity {
    public void setFlag(int f) { this.status = f; }
    public void process() { ... }
}

// ✅ Linguagem do negócio: o especialista lê e valida
public class Apolice {
    public void cancelarPorInadimplencia() { ... }
    public void renovar(Vigencia novaVigencia) { ... }
}

// Eventos no passado, também na linguagem do negócio
public record ApoliceCancelada(ApoliceId id, MotivoCancelamento motivo) {}
```

**Explicando o exemplo:**
- `cancelarPorInadimplencia()` é uma operação que o especialista de seguros reconhece, enquanto `setFlag(3)` obriga a consultar uma tabela de códigos.
- A regra de negócio fica **no método com nome de negócio**, e não escondida em um `if` genérico.
- `ApoliceCancelada` segue a convenção de evento no passado e usa o mesmo termo do negócio.

| Elemento | Deve refletir a linguagem |
|---|---|
| Classes e Value Objects | `Apolice`, `Vigencia`, `Segurado` |
| Métodos (verbos de negócio) | `renovar()`, `cancelarPorInadimplencia()` |
| Eventos de domínio | `ApoliceCancelada`, `SinistroAberto` |
| Nomes de testes | `deveCancelarApoliceInadimplente()` |
| Módulos e pacotes | `sinistros`, `cobranca`, `apolices` |
| Esquema do banco e da API | Mesmos termos, quando possível |

## A linguagem vale **dentro** de um Bounded Context

A mesma palavra pode ter significados diferentes em contextos diferentes, e isso é aceitável desde que cada contexto seja consistente por dentro.

| Termo | Contexto de Vendas | Contexto de Entrega |
|---|---|---|
| **Pedido** | Intenção de compra, com preço e desconto | Carga a ser enviada, com peso e endereço |
| **Cliente** | Quem compra e tem histórico de crédito | Destinatário que recebe a entrega |

Por isso a Linguagem Ubíqua é **por contexto**, e não global para a empresa inteira. Um sinal prático de que existe uma fronteira: quando dois times usam a mesma palavra para coisas diferentes, ou palavras diferentes para a mesma coisa. Veja o conceito completo em 2.2.1.1 (Bounded Context).

```
 ┌── Contexto: Vendas ───┐      ┌── Contexto: Entrega ──┐
 │ Pedido = intenção de  │      │ Pedido = carga a      │
 │ compra (preço, desc.) │      │ enviar (peso, rota)   │
 │ linguagem própria     │      │ linguagem própria     │
 └───────────────────────┘      └───────────────────────┘
        mesma palavra, modelos distintos: tudo bem
```

## Como construir a linguagem na prática

1. **Converse com os especialistas** usando os termos deles e anote o vocabulário.
2. **Mantenha um glossário vivo** (um arquivo no repositório) com termo, definição e exemplo.
3. **Faça workshops de modelagem** (por exemplo, Event Storming), em que negócio e tecnologia desenham o fluxo juntos.
4. **Questione termos vagos** ("processar", "gerenciar", "dados") e troque por verbos e substantivos do negócio.
5. **Renomeie o código** quando a linguagem evoluir. Refatorar nomes é parte do trabalho, e não luxo.
6. **Use a linguagem nos testes** e nas revisões de código.

## Armadilhas e erros comuns

| Erro | Consequência |
|---|---|
| Nomes técnicos (`Manager`, `Helper`, `Data`) no domínio | O código deixa de comunicar o negócio |
| Uma linguagem "corporativa" única para todos os contextos | Termos forçados e ambíguos; surge o "modelo gigante" |
| Glossário escrito uma vez e esquecido | Código e conversa divergem de novo |
| Só os devs participam | A linguagem vira jargão técnico sem validação do negócio |
| Traduzir para inglês só no código, sem registrar o mapeamento | Perde-se a correspondência com o termo falado |
| Misturar idiomas sem regra | Nomes inconsistentes (`Pedido` e `OrderItem`) |

> [!tip] Sobre o idioma do código
> Pode-se escrever o código em português ou em inglês. O essencial é **decidir uma regra e registrar o mapeamento** no glossário, para que o termo falado e o termo do código se correspondam sem ambiguidade.

---

## Quando vale o esforço

| Vale muito | Vale menos |
|---|---|
| Domínio com regras ricas e vocabulário próprio (seguros, finanças, saúde, logística) | CRUD simples sem regra de negócio |
| Muitos especialistas e vários times | Sistema pequeno, de um só desenvolvedor |
| Projetos longos, em que o conhecimento precisa sobreviver à rotatividade | Protótipos descartáveis |

## 🧩 Quiz de Fixação

1. O que é a Linguagem Ubíqua e por que ela é "rigorosa"?
2. Mostre a diferença, em código, entre um nome técnico genérico e um nome na linguagem do negócio.
3. Por que a mesma palavra pode ter significados diferentes em dois sistemas da mesma empresa sem violar a Linguagem Ubíqua?

**Respostas:**
1) É o vocabulário comum, construído em conjunto por desenvolvedores e especialistas e baseado no modelo de domínio, usado em conversas, documentos e código. É rigorosa porque software não lida bem com ambiguidade: cada termo deve ter um único significado dentro do seu contexto, e usar a linguagem em voz alta com os especialistas serve para testar e corrigir o modelo.
2) Nome técnico: `setFlag(3)` ou `ContractEntity.process()`, que nada diz ao negócio. Nome ubíquo: `apolice.cancelarPorInadimplencia()` e o evento `ApoliceCancelada`, que o especialista reconhece e valida. A regra passa a ficar no método com nome de negócio.
3) Porque a Linguagem Ubíqua vale dentro de um Bounded Context, e não para a empresa toda. Em Vendas, "Pedido" é uma intenção de compra com preço; em Entrega, é uma carga com peso e rota. Cada contexto tem seu modelo e vocabulário consistentes por dentro, e a diferença entre eles é tratada na fronteira (Context Mapping).
