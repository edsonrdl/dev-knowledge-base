### Design Estratégico (o quê e onde) vs Design Tático (como)

O DDD trabalha em **dois níveis**. O **estratégico** decide como dividir o problema em partes e quem cuida de cada uma. O **tático** decide como escrever o código de **uma** dessas partes. Entender a separação evita o erro mais comum: pular direto para Entities e Repositories sem antes saber onde ficam as fronteiras.

---

## A ideia central

**Analogia:** construir uma cidade. O planejamento urbano (estratégico) define os bairros, as ruas que os ligam e o que cada bairro faz. A arquitetura de cada prédio (tático) define paredes, encanamento e a planta interna. Projetar o encanamento de um prédio sem saber em que bairro ele fica é trabalho perdido.

```
 DESIGN ESTRATÉGICO                          DESIGN TÁTICO
 "O quê e onde"                              "Como"
 (espaço do problema)                        (espaço da solução)

 ┌──────────────────────────────┐            Dentro de UM Bounded Context:
 │ Domínio                      │
 │ ┌───────┐ ┌───────┐ ┌──────┐ │            ┌───────────────────────────┐
 │ │Vendas │ │Estoque│ │Fatura│ │  ──────►   │ Aggregate (Pedido)        │
 │ │  BC   │ │  BC   │ │  BC  │ │  zoom      │  ├ Entity (ItemPedido)    │
 │ └───┬───┘ └───┬───┘ └──┬───┘ │  em um     │  └ Value Object (Dinheiro)│
 │     └─Context Map──────┘     │  contexto  │ Repository, Domain Service│
 └──────────────────────────────┘            │ Domain Event              │
 Subdomínios, contextos, times, integração   └───────────────────────────┘
```

---

## Design Estratégico: o quê e onde

Trata do sistema em **grande escala**: como particionar o domínio e organizar equipes.

| Elemento | Pergunta que responde | Onde estudar neste guia |
|---|---|---|
| **Subdomínios** (Core, Supporting, Generic) | Onde está o valor do negócio e onde investir? | 2.1 |
| **Bounded Context** | Onde o modelo e a linguagem têm validade? | 2.2 |
| **Linguagem Ubíqua** | Que vocabulário vale dentro de cada contexto? | 1.1.2 |
| **Context Map** | Como os contextos se relacionam e se integram? | 2.3 |

Decisões estratégicas afetam **times e organização**: um Bounded Context costuma ter um time dono, e as relações do Context Map (Customer-Supplier, Shared Kernel, Anticorruption Layer) descrevem a dependência entre times.

---

## Design Tático: como

Trata do código **dentro de um Bounded Context**, com blocos de construção para expressar o modelo de forma rica.

| Bloco | Papel | Onde estudar neste guia |
|---|---|---|
| **Entity** | Objeto com identidade e ciclo de vida | 3.1.1 |
| **Value Object** | Objeto sem identidade, definido pelos atributos e imutável | 3.1.2 |
| **Aggregate** | Cluster com fronteira de consistência e uma raiz | 3.2.1 |
| **Repository** | Abstração de persistência de Aggregate Roots | 3.2.2 |
| **Domain Service** | Regra que não pertence a uma entidade | 3.3.1 |
| **Domain Event** | Fato de negócio que já ocorreu | 3.3.2 |

## Lado a lado

| Aspecto | Estratégico | Tático |
|---|---|---|
| Foco | Particionar o problema | Implementar a solução |
| Escala | O sistema ou a empresa toda | Um Bounded Context |
| Quem decide | Negócio, arquitetos e líderes de time | Desenvolvedores do contexto |
| Resultado | Mapa de contextos, subdomínios, times | Classes, módulos, regras no código |
| Linguagem | Termos do negócio e relações entre equipes | Padrões de código (Entity, Aggregate...) |
| Custo de errar | **Alto**: refatora fronteiras e times | Menor: refatora dentro do contexto |
| Aplicável sem código rico? | **Sim** | Só com domínio complexo |

## Qual vem primeiro e como eles se relacionam

As fontes concordam que o ideal é começar pelo estratégico: sem fronteiras claras, o tático tende a produzir **um modelo único e gigante** para tudo. Mas a relação é **iterativa**: o que se aprende ao modelar o código (tático) revela erros de fronteira e ajusta o mapa (estratégico).

```
 1. Entender o negócio e mapear subdomínios        (estratégico)
 2. Definir Bounded Contexts e a linguagem de cada (estratégico)
 3. Desenhar o Context Map e as integrações        (estratégico)
 4. Modelar cada contexto com blocos táticos       (tático)
 5. Aprender com o código ──► revisar as fronteiras (volta ao 1-3)
```

> [!note] O que o próprio Evans destaca
> Segundo relatos de entrevistas, Evans considera que o livro de 2003 fez muitos leitores tratarem os **blocos táticos** como o coração do DDD, quando para ele o **design estratégico** é o núcleo. Martin Fowler também aponta que as ideias centrais do DDD são conceituais, e que as partes estratégicas se aplicam em vários estilos de programação.

## Exemplo prático: e-commerce

**Estratégico:**
- Subdomínios: *Catálogo* (suporte), *Pedidos* (core, é o diferencial), *Pagamentos* (genérico, usa um gateway pronto), *Logística* (suporte).
- Bounded Contexts: `Vendas`, `Estoque`, `Entrega`, cada um com seu modelo de "Produto" e de "Pedido".
- Context Map: `Vendas → Pagamentos` por Anticorruption Layer; `Vendas → Estoque` por evento.

**Tático (dentro de `Vendas`):**

```java
// Aggregate Root com Value Objects e evento de domínio
public class Pedido {
    private final PedidoId id;               // identidade (Entity)
    private final List<ItemPedido> itens;    // entidade interna
    private Dinheiro total;                  // Value Object

    public void confirmar() {
        if (itens.isEmpty()) throw new PedidoVazioException();
        // ... regra de negócio no domínio
        registrar(new PedidoConfirmado(id, total));  // Domain Event
    }
}
```

Observe a divisão: **onde** `Pedido` vive e com quem fala é decisão estratégica; **como** ele protege suas regras é decisão tática.

## Erros comuns

| Erro | Consequência |
|---|---|
| Aplicar só o tático (Entities e Repositories em tudo) | "DDD de fachada": código rebuscado, sem fronteiras, com modelo único gigante |
| Ignorar o estratégico por "ser coisa de reunião" | Bounded Contexts mal definidos; times se atropelam |
| Aplicar tático rico em subdomínio genérico ou de suporte | Esforço alto onde não há diferencial; prefira solução pronta ou CRUD |
| Tratar o Context Map como documento estático | Fronteiras desatualizadas em relação à organização e ao código |
| Esperar o mapa perfeito antes de codificar | Paralisia; refine iterativamente |

**Onde investir:** use o tático rico no **Core Domain**; nos domínios de suporte e genéricos, um modelo simples ou um produto pronto costuma bastar.

## 🧩 Quiz de Fixação

1. Qual a diferença entre o design estratégico e o tático, e a que escopo cada um se aplica?
2. Por que um time que aplica só os padrões táticos costuma acabar com um "DDD de fachada"?
3. No e-commerce do exemplo, classifique como estratégica ou tática: (a) decidir que Pagamentos usa um gateway pronto; (b) fazer `Pedido` rejeitar confirmação sem itens; (c) definir que "Produto" em Estoque é diferente de "Produto" em Vendas.

**Respostas:**
1) O estratégico trata do "o quê e onde": divide o domínio em subdomínios e Bounded Contexts, define a linguagem de cada um e o Context Map, no nível do sistema ou da empresa. O tático trata do "como": padrões de código (Entity, Value Object, Aggregate, Repository, Domain Service, Domain Event), aplicados **dentro** de um único Bounded Context.
2) Porque sem as fronteiras do estratégico, todos os conceitos caem em um único modelo grande, sem limites de linguagem nem de responsabilidade. O código parece sofisticado, com Entities e Repositories, mas mantém os problemas de acoplamento e ambiguidade que o DDD quer resolver.
3) (a) Estratégica: é decisão de subdomínio genérico e de investimento. (b) Tática: é uma regra de negócio protegida dentro do Aggregate. (c) Estratégica: é uma decisão de Bounded Context e de linguagem por contexto.
