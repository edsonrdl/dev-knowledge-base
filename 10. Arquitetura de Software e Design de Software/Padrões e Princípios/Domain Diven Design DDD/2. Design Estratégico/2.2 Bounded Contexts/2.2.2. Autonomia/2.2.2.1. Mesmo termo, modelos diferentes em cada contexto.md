### Mesmo termo, modelos diferentes em cada contexto

Num sistema grande, a mesma palavra ("Produto", "Pedido", "Cliente") significa **coisas diferentes** para áreas diferentes. O DDD aceita isso: cada Bounded Context tem seu **próprio modelo** do conceito, com os atributos e regras que importam **naquele** contexto. É essa liberdade que dá **autonomia** a cada contexto, e evita a classe gigante que tenta servir a todos.

---

## O problema do modelo único

A tentação é criar **um** modelo corporativo de "Produto" que sirva a Vendas, Estoque, Entrega e Faturamento. O resultado costuma ser uma classe enorme, com dezenas de atributos opcionais, que ninguém entende por inteiro e que **todos os times precisam alterar**.

Martin Fowler descreve a raiz do problema: conforme o domínio cresce, manter **um único modelo consistente** fica mais difícil, porque grupos diferentes usam vocabulários sutilmente diferentes. Eric Evans concluiu que unificar totalmente o modelo de um sistema grande é impraticável e pouco custo-efetivo. A saída é dividir em Bounded Contexts, cada um com um modelo **internamente consistente**.

```
 ❌ MODELO ÚNICO                          ✅ UM MODELO POR CONTEXTO

 ┌───────────────────────┐               ┌─ Vendas ──────┐  ┌─ Estoque ─────┐
 │ Produto               │               │ Produto       │  │ Produto       │
 │  preco, desconto,     │               │  preco        │  │  sku          │
 │  promocao, peso,      │               │  taxaDesconto │  │  peso         │
 │  dimensoes, corredor, │               │  promocao     │  │  dimensoes    │
 │  fornecedor, ncm,     │               └───────────────┘  │  corredor     │
 │  imagem, seo, ...     │               ┌─ Entrega ─────┐  │  quantidade   │
 │  (todos mexem aqui)   │               │ Item a enviar │  └───────────────┘
 └───────────────────────┘               │  peso, volume │
 uma classe, N times brigando            └───────────────┘
                                          cada time evolui o seu
```

**Analogia:** a palavra "banco" significa instituição financeira para um economista e assento para um carpinteiro. Ninguém tenta criar uma definição única; cada área usa o termo no seu sentido, e o contexto deixa claro qual é.

---

## O mesmo conceito, vários modelos

Um exemplo com **Pedido** em três contextos:

| Contexto | O que "Pedido" é | Atributos e regras que importam |
|---|---|---|
| **Vendas** | Solicitação de compra | Itens, preço, descontos, cupom, validade da proposta |
| **Estoque/Expedição** | Lista de separação | Localização no armazém, volumes, etiqueta de envio |
| **Faturamento** | Fatura | Condições de pagamento, impostos, vencimento |

E com **Produto**, o exemplo do glossário:

| Contexto | O que "Produto" é | Atributos |
|---|---|---|
| **Vendas** | Oferta vendável | `preco`, `taxaDesconto`, `promocaoAtiva` |
| **Estoque/Logística** | Item físico em estoque | `peso`, `dimensoes`, `localizacaoCorredor`, `quantidade` |

A diferença é **intencional**, não um defeito a corrigir.

```java
// Contexto Vendas: o que importa para vender
package vendas.dominio;
public class Produto {
    private ProdutoId id;
    private Dinheiro preco;
    private Percentual taxaDesconto;
    private boolean promocaoAtiva;
    public Dinheiro precoFinal() { /* regra de preço */ return preco; }
}

// Contexto Estoque: o que importa para guardar e movimentar
package estoque.dominio;
public class ItemEstoque {
    private ProdutoId produtoId;      // mesma identidade, outro modelo
    private Peso peso;
    private Dimensoes dimensoes;
    private Localizacao corredor;
    private int quantidade;
    public void baixar(int qtd) { /* regra de estoque */ }
}
```

As duas classes representam o **mesmo produto do mundo real**, mas cada uma só carrega o que seu contexto precisa. Quem mexe em preço não afeta o estoque, e vice-versa.

## Como os contextos se conectam sem compartilhar o modelo

Autonomia **não é isolamento total**: os contextos precisam se comunicar, mas sem acoplar os modelos.

| Mecanismo | Como funciona |
|---|---|
| **Identificadores compartilhados** | Os contextos referenciam o mesmo `ProdutoId` ou `PedidoId`, mas cada um mantém seu modelo em volta do ID |
| **Eventos de integração** | Vendas publica `PedidoRealizado` com IDs, itens e totais. É um **contrato** entre contextos, distinto dos eventos de domínio internos |
| **Anticorruption Layer** | O consumidor traduz o evento recebido para o **seu** modelo (por exemplo, `PedidoExpedicao`), acrescentando dados que só ele tem |
| **Cópias locais** | O contexto guarda uma cópia dos dados de que precisa, atualizada por eventos |
| **Chamada de API** | Quando precisa do dado atual e tolera a dependência, consulta a API do outro contexto |

```
 Vendas                          Broker                      Expedição
 ┌────────┐  PedidoRealizado    ┌────────┐   consome   ┌─────────────────────┐
 │ Pedido │──(idPedido, itens)─►│ evento │────────────►│ ACL traduz para     │
 └────────┘                     └────────┘             │ PedidoExpedicao     │
                                                       │ (+ localização no   │
                                                       │ armazém, que é só   │
                                                       │ do contexto dele)   │
                                                       └─────────────────────┘
```

**Regras de autonomia:**
- Cada contexto é **dono do seu esquema de dados**. Nunca leia a tabela de outro contexto diretamente.
- Como mensagens podem chegar repetidas, o consumidor deve ser **idempotente**: garanta unicidade pelo ID do pedido de origem no banco, e não apenas por uma verificação prévia.
- Esta é a mesma lógica de **Database per Service** dos microsserviços: veja o guia de [[10. Arquitetura de Software e Design de Software/Padrões e Princípios/Padrões Arquiteturais/Microservices/0 Microservices (Glossário )|Microservices]].

## Como descobrir onde está a fronteira

| Heurística | Sinal |
|---|---|
| **Linguagem** | A mesma palavra significa coisas diferentes para times diferentes |
| **Dados** | Dois times precisam de propriedades diferentes do mesmo conceito |
| **Regras** | A mesma operação é validada de formas diferentes em partes diferentes |
| **Organização** | Times que trabalham de forma independente indicam contextos separados |
| **Capacidade de negócio** | O contexto deve acompanhar o negócio, e não uma camada técnica |

Um aviso de equilíbrio: cada contexto tem custo de comunicação e de manutenção. As fontes recomendam **começar com poucos contextos maiores** e dividir quando a linguagem ou a estrutura dos times pedir.

## Armadilhas comuns

| Erro | Consequência |
|---|---|
| **Modelo canônico único** da empresa | Classe gigante, mudanças travadas entre times |
| Compartilhar tabelas ou entidades entre contextos | Acoplamento oculto; autonomia perdida |
| Duplicar o modelo **completo** de outro contexto | Cópia que diverge e vira fonte de bugs; guarde só o necessário |
| Dividir contextos por **camada técnica** (serviço de "banco", de "UI") | Fronteiras que não acompanham o negócio |
| Criar contextos demais, cedo demais | Sobrecarga de integração sem ganho |
| Ignorar a tradução na fronteira | O vocabulário de um contexto contamina o outro |

## 🧩 Quiz de Fixação

1. Por que o DDD aceita que "Produto" tenha modelos diferentes em Vendas e em Estoque, em vez de buscar um modelo único?
2. Como dois contextos com modelos diferentes de Pedido se comunicam sem compartilhar a mesma classe?
3. Cite duas heurísticas para identificar que um conceito precisa de contextos separados.

**Respostas:**
1) Porque um modelo único para um sistema grande é impraticável: vira uma classe enorme, que todos os times alteram, com atributos que só fazem sentido para alguns. Com um modelo por contexto, cada um carrega só o que importa (preço e promoção em Vendas; peso e corredor em Estoque), evolui de forma independente e mantém sua linguagem consistente. A diferença é intencional.
2) Por identificadores compartilhados (o mesmo `PedidoId`), eventos de integração (por exemplo, `PedidoRealizado`) e uma Anticorruption Layer no consumidor, que traduz o evento para o seu próprio modelo e acrescenta os dados que só ele possui. Cada contexto mantém seu esquema e nunca lê as tabelas do outro.
3) Linguagem (a mesma palavra significa coisas diferentes para times diferentes) e dados (dois times precisam de propriedades diferentes do mesmo conceito). Também valem: a mesma operação validada de formas diferentes, e times que trabalham de forma independente.
