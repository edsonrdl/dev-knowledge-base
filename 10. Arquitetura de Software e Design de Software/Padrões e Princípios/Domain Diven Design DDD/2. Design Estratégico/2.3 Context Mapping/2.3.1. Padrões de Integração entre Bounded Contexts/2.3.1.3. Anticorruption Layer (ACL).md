### Anticorruption Layer (ACL)

A **Anticorruption Layer** (camada anticorrupção) é uma camada de **tradução defensiva** que o contexto downstream coloca entre si e um sistema externo ou legado, para que o modelo de lá **não contamine** o seu. Ela fala com o outro sistema na interface que ele já tem e entrega ao seu domínio os dados **na linguagem do seu próprio modelo**. É o padrão que protege a integridade do domínio quando integrar é necessário, mas se adaptar ao outro lado não é desejável.

---

## O problema

Quase toda aplicação depende de outros sistemas. Sistemas legados costumam ter **esquemas confusos, APIs obsoletas e nomes crípticos**. Para integrar, o sistema novo acaba **adotando partes do modelo do legado**, e isso corrompe um design que poderia ser limpo.

Evans descreve a situação: uma interface grande com um sistema upstream pode, com o tempo, **sobrepor-se à intenção do modelo downstream**, que passa a ser modificado de forma improvisada para se parecer com o outro. Os modelos de legados costumam ser fracos (quando não são uma "bola de lama"), e mesmo os bem desenhados podem não servir ao projeto atual. Ainda assim, a integração pode ser valiosa ou obrigatória.

```
 SEM ACL                                    COM ACL

 ┌───────────────┐   campos e nomes        ┌───────────────┐        ┌───────────┐
 │ Seu domínio   │   do legado vazam       │ Seu domínio   │        │ Legado    │
 │  Pedido {     │◄── (ped_nr, cod_stt,    │  Pedido {     │        │ ped_nr    │
 │   ped_nr,     │     dt_emis_8) ─────    │   numero,     │        │ cod_stt   │
 │   cod_stt ... │                         │   status ...  │        │ dt_emis_8 │
 └───────────────┘                         └──────▲────────┘        └─────▲─────┘
  o legado dita seu modelo                        │ fala a SUA língua      │ fala a língua DELE
                                           ┌──────┴────────────────────────┴──────┐
                                           │          ANTICORRUPTION LAYER        │
                                           │      (traduz nos dois sentidos)      │
                                           └──────────────────────────────────────┘
```

**Analogia:** um intérprete numa negociação. Cada lado fala o próprio idioma e nunca precisa aprender o do outro; o intérprete traduz e, quando algo é ambíguo, resolve na fronteira.

---

## A solução (Evans)

Como cliente downstream, crie uma **camada isoladora** que oferece as funcionalidades do sistema upstream **nos termos do seu próprio modelo de domínio**. Essa camada:

- conversa com o outro sistema **pela interface existente**, exigindo pouca ou nenhuma modificação nele;
- **traduz internamente**, em um ou nos dois sentidos, entre os dois modelos.

A Microsoft resume assim: a comunicação entre o seu subsistema e a ACL **sempre usa o seu modelo**, e as chamadas da ACL ao outro sistema seguem o modelo **dele**. Toda a lógica de tradução fica dentro da camada, e ela pode ser um componente da aplicação ou um serviço independente.

### Componentes típicos

| Componente | Papel |
|---|---|
| **Facade / porta** | Interface na linguagem do seu domínio que o resto do sistema usa |
| **Adapter** | Chama o sistema externo (REST, SOAP, banco, arquivo, fila) |
| **Translator** | Converte entre o modelo externo e o seu (campos, tipos, códigos, regras de formato) |

Essa estrutura é a mesma de **Ports & Adapters** da Arquitetura Hexagonal: a porta é do seu domínio e o adaptador é o único que conhece o sistema externo.

## Exemplo prático

Um sistema novo de **Pedidos** precisa ler pedidos de um **ERP legado** com campos crípticos.

```java
// Porta: linguagem do SEU domínio (nada de ERP aqui)
public interface PedidosLegadoGateway {
    Optional<Pedido> buscarPorNumero(NumeroPedido numero);
}

// DTO do legado: exatamente como ele entrega, sem poluir o domínio
record PedidoErpDto(String ped_nr, String cod_stt, String dt_emis_8, String vlr_tot_cts) {}

// ACL: adaptador + tradutor, o único lugar que conhece o ERP
@Component
class PedidosLegadoAdapter implements PedidosLegadoGateway {
    private final ErpClient erp;

    public Optional<Pedido> buscarPorNumero(NumeroPedido numero) {
        return erp.consultar(numero.valor()).map(this::traduzir);
    }

    private Pedido traduzir(PedidoErpDto d) {
        return new Pedido(
            new NumeroPedido(d.ped_nr().trim()),
            traduzirStatus(d.cod_stt()),                           // "03" -> ENVIADO
            LocalDate.parse(d.dt_emis_8(), DateTimeFormatter.BASIC_ISO_DATE), // "20260115"
            Dinheiro.deCentavos(Long.parseLong(d.vlr_tot_cts())));
    }

    private StatusPedido traduzirStatus(String codigo) {
        return switch (codigo) {
            case "01" -> StatusPedido.CRIADO;
            case "02" -> StatusPedido.PAGO;
            case "03" -> StatusPedido.ENVIADO;
            default -> throw new CodigoLegadoDesconhecidoException(codigo);
        };
    }
}
```

**Explicando o exemplo:**
- O domínio só conhece `PedidosLegadoGateway`, `Pedido` e `StatusPedido`, e nunca `ped_nr` ou `"03"`.
- O `PedidoErpDto` e a tradução de status e de data ficam **isolados** no adaptador.
- Se o ERP mudar (ou for substituído), muda só o adaptador. Se o legado for aposentado, a ACL some e o domínio não é tocado.
- Testes do domínio usam um gateway falso, sem o ERP.

## Síncrona ou assíncrona

| Estilo | Como | Quando |
|---|---|---|
| **Síncrona** | A ACL chama o legado por requisição e resposta | Leituras e comandos que precisam de resposta imediata |
| **Assíncrona (eventos)** | A ACL consome eventos ou mensagens do legado e publica eventos no seu modelo (Service Bus, Kafka, SQS) | Alto volume ou quando o legado tem limite de vazão: desacopla o domínio moderno dessas restrições |

## Considerações de projeto

A documentação da Microsoft lista os pontos de atenção:

| Ponto | O que considerar |
|---|---|
| **Latência** | A ACL adiciona um salto às chamadas |
| **Mais uma peça** | É um componente a mais para operar e manter |
| **Escala** | Planeje como a ACL escala com a demanda |
| **Quantidade de ACLs** | Pode ser preciso mais de uma, por exemplo uma por serviço |
| **Operação** | Integre-a ao monitoramento, ao release e à configuração |
| **Consistência** | Monitore a consistência de transações e de dados |
| **Escopo** | Ela precisa tratar toda a comunicação ou só parte das funcionalidades? |
| **Temporária ou permanente?** | Em migração, decida se será **aposentada** quando o legado sair |
| **Segurança** | Valide e sanitize entradas na fronteira, pois os sistemas podem ter níveis de confiança diferentes |
| **Observabilidade** | Use IDs de correlação e logs estruturados para diagnosticar falhas de tradução |

> [!warning] Mantenha a ACL só como tradução
> Evite colocar **regras de negócio ou orquestração** na camada. Ela deve conter apenas a lógica de tradução. Regras de negócio pertencem ao domínio.

## ACL vs outros padrões de integração

| Padrão | Postura do downstream | Custo | Quando |
|---|---|---|---|
| **Anticorruption Layer** | Defensiva: traduz para o seu modelo | Camada a manter | Modelo externo fraco, legado ou que contaminaria o seu |
| **Conformist** | Adere ao modelo do upstream, sem tradução | Baixo | O upstream não atende às suas necessidades, mas o modelo dele é bom o bastante |
| **Customer-Supplier** | Negocia necessidades com o upstream | Coordenação entre times | Times cooperativos, com planejamento conjunto (veja 2.3.1.2) |
| **Shared Kernel** | Compartilha parte do modelo | Acoplamento forte | Times próximos e conceitos estáveis (veja 2.3.1.1) |

Evans observa que a tradução pode ser simples, até elegante, entre contextos bem desenhados e equipes cooperativas. Quando o controle ou a comunicação não bastam para Shared Kernel, parceria ou Customer-Supplier, a tradução se torna mais complexa e ganha um **tom defensivo**, e é aí que a ACL entra.

## Quando usar e quando não usar

| Use quando | Pode não ser adequado quando |
|---|---|
| Migração gradual: sistema novo e legado precisam conviver | Os dois sistemas não têm diferenças semânticas relevantes |
| Subsistemas com **semânticas diferentes** precisam se comunicar | O custo de manter a camada supera o benefício (integração trivial) |
| Você consome um sistema que não controla (fornecedor, parceiro, legado) | O upstream tem modelo bom e você pode simplesmente aderir (Conformist) |
| Quer trocar de fornecedor sem reescrever o domínio (veja 2.1.3.1) | |

## Erros comuns

| Erro | Consequência |
|---|---|
| Colocar regra de negócio dentro da ACL | A lógica do domínio fica escondida na borda e dispersa |
| Vazar o DTO do legado para o domínio | A contaminação que a ACL deveria evitar |
| Traduzir só alguns campos e deixar o resto "passar" | O modelo externo infiltra aos poucos |
| Não monitorar falhas de tradução | Dados incorretos entram silenciosamente |
| Esquecer de aposentar a ACL após a migração | Camada obsoleta que ninguém mantém |
| Uma ACL única e gigante para todos os sistemas | Gargalo e ponto único de falha; considere uma por integração |

## 🧩 Quiz de Fixação

1. Qual problema a Anticorruption Layer resolve e como ela o faz?
2. Em que ela se diferencia do Conformist?
3. Por que não se deve colocar regra de negócio dentro da ACL, e o que fazer quando o legado for aposentado?

**Respostas:**
1) Evita que o modelo de um sistema externo ou legado (campos crípticos, APIs obsoletas) contamine o seu domínio. A ACL é uma camada isoladora que conversa com o outro sistema pela interface existente e traduz, em um ou nos dois sentidos, entre o modelo dele e o seu, de modo que o domínio só lida com a própria linguagem.
2) O Conformist adere ao modelo do upstream, sem tradução: simplifica a integração, mas o downstream passa a depender e a se parecer com o modelo do upstream. A ACL faz o contrário: mantém o seu modelo e traduz. Escolhe-se Conformist quando o modelo do upstream é bom o bastante; ACL quando é fraco, legado ou contaminaria o seu.
3) Porque a camada deve conter apenas a lógica de tradução; regras de negócio escondidas na borda ficam dispersas e difíceis de achar e de testar, e pertencem ao domínio. Quando o legado for aposentado, a ACL pode ser removida, e como só ela conhecia o legado, o domínio não é afetado.
