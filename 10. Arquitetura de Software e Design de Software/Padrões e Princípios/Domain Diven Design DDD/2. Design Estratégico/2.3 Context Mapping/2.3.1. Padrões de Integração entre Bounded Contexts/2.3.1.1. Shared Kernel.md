### Shared Kernel

O **Shared Kernel** (núcleo compartilhado) é um padrão de relacionamento do Context Map em que **dois ou mais Bounded Contexts compartilham, de propósito, uma pequena parte do modelo** (código, esquema ou tipos). Em troca de evitar duplicação, os times aceitam um acoplamento forte e a obrigação de **coordenar toda mudança**. É um padrão legítimo, mas de uso cauteloso.

---

## O conceito central

Cada Bounded Context normalmente tem seu próprio modelo (veja 2.2.2.1). O Shared Kernel é a **exceção deliberada**: um subconjunto pequeno do modelo que ambos os contextos usam e mantêm **juntos**.

```
 ┌────────── Contexto A ──────────┐        ┌────────── Contexto B ──────────┐
 │                                │        │                                │
 │   modelo próprio de A          │        │   modelo próprio de B          │
 │                                │        │                                │
 │        ┌───────────────────────┴────────┴───────────────────────┐        │
 │        │              SHARED KERNEL                              │        │
 │        │   (pequeno, estável, mantido em comum pelos dois times) │        │
 │        └───────────────────────┬────────┬───────────────────────┘        │
 │                                │        │                                │
 └────────────────────────────────┘        └────────────────────────────────┘
        mudar o kernel = os dois times precisam concordar
```

**Analogia:** duas lojas vizinhas que dividem o mesmo estoque de uma pequena sala de depósito. Economizam espaço e compras, mas qualquer reorganização da sala precisa ser combinada entre os donos, e um erro de um afeta os dois.

---

## Shared Kernel não é "qualquer biblioteca compartilhada"

Uma biblioteca compartilhada é uma **escolha de implementação**. Ela só é um Shared Kernel, no sentido do DDD, quando os dois times **decidem conscientemente** acoplar-se a ela. O problema aparece quando o código é compartilhado **sem essa intenção**: ele cresce por conveniência e acaba acoplando todos os domínios sem que ninguém tenha escolhido isso.

| | Shared Kernel (DDD) | Biblioteca comum "acidental" |
|---|---|---|
| **Decisão** | Consciente, acordada entre os times | Cresceu por conveniência |
| **Tamanho** | Pequeno e delimitado | Tende a inchar |
| **Governança** | Dono, processo de mudança e testes definidos | Ninguém é responsável |
| **Documentação** | O acoplamento está documentado no Context Map | Não aparece no mapa |

---

## O que pertence ao kernel

O kernel deve ser **pequeno, estável e bem definido**. Candidatos típicos:

| Cabe no kernel | Não cabe |
|---|---|
| Tipos base compartilhados (`Dinheiro`, `Cpf`, `PedidoId`) | Regras específicas de um único contexto |
| Contratos de eventos realmente comuns | Modelos que um contexto altera com frequência |
| Regras de validação idênticas nos dois contextos | Utilitários genéricos de infraestrutura (use uma biblioteca normal) |
| Modelos de segurança padronizados | Tudo "que pode ser útil um dia" |

```java
// Shared Kernel: pequeno e estável, compartilhado por Vendas e Faturamento
package empresa.kernel;

public record Dinheiro(long centavos, Moeda moeda) {
    public Dinheiro somar(Dinheiro outro) {
        if (moeda != outro.moeda) throw new IllegalArgumentException("Moedas diferentes");
        return new Dinheiro(centavos + outro.centavos, moeda);
    }
}

public record Cpf(String valor) {
    public Cpf { if (!valido(valor)) throw new IllegalArgumentException("CPF inválido"); }
    // regra de validação única, idêntica para todos os contextos
}
```

`Dinheiro` e `Cpf` têm significado e regras que **não variam** entre os contextos, então compartilhá-los é seguro. Já `Pedido` varia por contexto (veja 2.2.2.1) e **não** deve ir para o kernel.

---

## Quando usar

O padrão se encaixa quando:

- os dois contextos pertencem ao **mesmo time** ou a times muito próximos;
- compartilham o mesmo **pipeline de deploy** (ou rodam juntos, como num monolito com fronteiras lógicas);
- os conceitos compartilhados são **estáveis** e raramente mudam;
- o acoplamento é **intencional e documentado**.

## Quando evitar

- Times diferentes, com **ciclos de release** diferentes.
- Contextos que precisam de autonomia de deploy (microsserviços independentes).
- Conceitos ainda instáveis, que mudam a cada sprint.
- Quando o kernel já está crescendo além do essencial.

---

## Governança: como manter o kernel saudável

| Prática | Para quê |
|---|---|
| **Dono e matriz de responsabilidade** claros | Evitar a "tragédia dos comuns", em que ninguém cuida do que é de todos |
| **Processo de mudança** coordenado (revisão pelos times consumidores) | Nenhuma alteração surpreende o outro lado |
| **Versionamento** e política de *breaking changes* | Migração previsível |
| **Testes compartilhados** e testes de compatibilidade | Pegar regressões que afetariam todos os contextos |
| **Escopo mínimo** revisado periodicamente | Impedir o crescimento por conveniência |

---

## Riscos

| Risco | Efeito |
|---|---|
| **Acoplamento forte** entre contextos | Autonomia reduzida |
| **Acoplamento de release** | Quem publica o kernel obriga os outros a atualizar, ou precisa manter compatibilidade |
| **Acoplamento de deploy** | Um bug ou mudança incompatível afeta todos os domínios de uma vez |
| **Dependências em diamante** | Contextos presos a versões diferentes do kernel entram em conflito |
| **Acoplamento conceitual** | Uma única classe precisa servir a todos os consumidores, forçando concessões |
| **Decisões lentas** | Alto custo de coordenação entre os times |

---

## Alternativas

Quando o Shared Kernel é pesado demais, existem formas de integrar com menos acoplamento:

| Alternativa | Como funciona | Quando |
|---|---|---|
| **Eventos de integração com esquema documentado** | O publicador descreve os campos; cada consumidor escreve sua própria classe | Times pequenos |
| **JSON Schema + testes de contrato** | Cada lado valida seus eventos contra o esquema no CI, sem compartilhar código | Times separados |
| **Schema registry** | Repositório central impõe regras de compatibilidade e versão | Muitos domínios |
| **Consumidor tolerante** | O consumidor declara só os campos de que precisa e ignora o resto | Evolução independente |
| **Anticorruption Layer** | O consumidor traduz o modelo externo para o seu | Contextos com modelos muito diferentes (veja 2.3.1.3) |
| **Customer-Supplier** | Relação clara de fornecedor e cliente, sem núcleo comum (veja 2.3.1.2) | Times com dependência em um sentido |

---

## Exemplo prático

Um e-commerce com os contextos **Catálogo** e **Estoque**, mantidos pelo mesmo time, que compartilham `ProdutoId`, `Sku` e `Dinheiro` num kernel mínimo. Cada contexto mantém seu modelo próprio de produto (apresentação e preço no Catálogo; quantidade e localização no Estoque), e só os **tipos base** são comuns.

Quando esses contextos passarem a ser de **times diferentes**, com deploys independentes, o kernel deve ser **revisto**: substitua-o por eventos de integração com esquemas versionados ou por uma Anticorruption Layer.

## 🧩 Quiz de Fixação

1. O que diferencia um Shared Kernel de uma simples biblioteca compartilhada?
2. Cite três riscos de um Shared Kernel e uma situação em que ele deve ser evitado.
3. O que deve (e o que não deve) entrar no kernel? Dê um exemplo de cada.

**Respostas:**
1) A **intenção**. Shared Kernel é uma decisão consciente, acordada entre os times, de compartilhar uma parte pequena e estável do modelo, com dono, processo de mudança e testes. Uma biblioteca comum "acidental" cresce por conveniência, sem governança, e acopla os domínios sem que ninguém tenha escolhido isso.
2) Riscos: acoplamento forte entre contextos, acoplamento de release e de deploy (um bug afeta todos de uma vez) e decisões lentas por coordenação. Deve ser evitado quando os times são diferentes, com ciclos de release distintos, ou quando os contextos precisam de autonomia de deploy, como microsserviços independentes.
3) Entram tipos estáveis e idênticos nos contextos, como `Dinheiro` ou `Cpf`. Não entram modelos que variam por contexto, como `Pedido`, nem regras específicas de um só contexto, nem utilitários genéricos de infraestrutura.
