### Supporting Subdomain — necessário, mas não diferencial

O **Supporting Subdomain** (subdomínio de suporte) é a parte do negócio que **precisa existir** para a empresa funcionar, mas que **não é o diferencial competitivo**. É específico do negócio, porém simples e estável. Reconhecê-lo evita dois desperdícios opostos: tratá-lo como Core (esforço demais) ou negligenciá-lo (o negócio para quando ele falha).

---

## O conceito central

Entre o Core Domain (o que diferencia) e o Generic Subdomain (o que todos fazem igual) fica o meio-termo: atividades **próprias do negócio**, necessárias para sustentar o Core, mas sem vantagem competitiva.

```
                    ┌───────────────────────────┐
                    │      CORE DOMAIN          │  ← o que nos diferencia
                    │  (precificação inteligente)│
                    └────────────▲──────────────┘
                                 │ depende de
            ┌────────────────────┴────────────────────┐
            │       SUPPORTING SUBDOMAINS              │  ← necessários, específicos
            │  catálogo · cadastro de clientes ·       │     do negócio, sem diferencial
            │  gestão de pedidos internos · cupons     │
            └────────────────────▲────────────────────┘
                                 │ usa
            ┌────────────────────┴────────────────────┐
            │       GENERIC SUBDOMAINS                 │  ← iguais em toda empresa
            │  autenticação · e-mail · faturamento     │
            └──────────────────────────────────────────┘
```

**Analogia:** num restaurante famoso por massas, a receita é o Core. O controle de reservas e a escala dos garçons são suporte: se falharem, o restaurante sofre, mas ninguém escolhe a casa por causa disso. A conta de luz e a contabilidade são genéricos.

---

## Características

| Característica | Detalhe |
|---|---|
| **Valor competitivo** | Baixo: não diferencia a empresa |
| **Específico do negócio?** | **Sim**: as regras são da empresa, então raramente há produto pronto que sirva perfeitamente |
| **Complexidade** | Baixa a média; muitas vezes é **CRUD** com validações |
| **Frequência de mudança** | Baixa e previsível |
| **Risco se falhar** | Real (o negócio depende dele), mas contornável |
| **Modelo de domínio** | Simples; dispensa Aggregates elaborados e Domain Events em quase todos os casos |

A principal diferença para o **genérico**: o suporte é **específico da empresa**, e o genérico é igual em todas elas (autenticação, pagamento).

---

## Como reconhecer

| Pergunta | Se a resposta for... |
|---|---|
| Se um concorrente tivesse algo parecido, perderíamos clientes? | **Não** → não é Core |
| O negócio precisa disso para operar? | **Sim** → é suporte ou genérico |
| As regras são específicas da nossa empresa? | **Sim** → suporte; **não** (igual em todo lugar) → genérico |
| Muda por decisão estratégica ou só por manutenção? | Só manutenção → suporte |
| Dá para resolver com um cadastro e algumas validações? | Sim → suporte simples |

---

## Como construir

A regra geral é **gastar o mínimo necessário para atender bem**.

| Decisão | Recomendação |
|---|---|
| **Construir ou comprar?** | Se é simples, construa com o mínimo de cerimônia. Se é complexo e existe produto aderente, considere comprar. As fontes admitem também a combinação "construir e comprar" |
| **Time** | Pode ser um time de menor senioridade ou terceirizado, com boa documentação |
| **Design tático** | Simples: CRUD, transaction script ou modelo anêmico bem organizado, sem camadas excessivas |
| **Arquitetura** | Pragmática (camadas simples); não precisa de Hexagonal completa |
| **Testes** | Bons, mas sem sofisticação: foco nas regras de negócio específicas |
| **Integração** | Exponha uma API estável para o Core consumir |

```java
// Supporting: simples e direto, sem Aggregates elaborados
@Service
public class CupomService {
    private final CupomRepository repository;

    public Cupom criar(String codigo, BigDecimal percentual, LocalDate validade) {
        if (percentual.compareTo(BigDecimal.valueOf(50)) > 0)
            throw new IllegalArgumentException("Desconto máximo é 50%");
        return repository.save(new Cupom(codigo, percentual, validade));
    }
}
```

Compare com o Core, em que a mesma lógica viraria parte de um Aggregate rico, com Value Objects e eventos de domínio. Aqui, o serviço enxuto basta.

## Exemplos por tipo de negócio

| Negócio | Core | Supporting | Generic |
|---|---|---|---|
| E-commerce | Precificação e recomendação | Catálogo, cupons, cadastro de clientes | Autenticação, e-mail, pagamento |
| Banco digital | Análise de crédito | Cadastro de agências, relatórios internos | Autenticação, notificações |
| Logística | Roteirização otimizada | Cadastro de veículos e motoristas | Faturamento, e-mail |
| Saúde | Triagem clínica própria | Agenda de consultórios, cadastro de convênios | Autenticação, assinatura digital |

A classificação depende da estratégia: o catálogo é suporte para um e-commerce de produtos variados, mas poderia ser Core num marketplace cujo diferencial é a curadoria.

## Armadilhas

| Erro | Consequência |
|---|---|
| Tratar suporte como Core (DDD tático completo em um cadastro) | Over-engineering; custo alto sem retorno |
| Tratar suporte como lixo e não cuidar da qualidade | A operação trava; dívida técnica afeta o Core, que depende dele |
| Acoplar o Core diretamente ao modelo interno do suporte | Mudança no suporte quebra o diferencial; use contratos estáveis (veja Anticorruption Layer em 2.3.1.3) |
| Alocar os melhores desenvolvedores no suporte | O Core fica sem os talentos de que precisa |
| Não revisar a classificação | Um suporte pode virar Core (ou o contrário) com a mudança de estratégia |

---

## Relação com os outros subdomínios

- **Core:** recebe o melhor investimento; o suporte existe para sustentá-lo.
- **Generic:** deve ser comprado ou reaproveitado. Como as fontes divergem se isso é sempre possível, a regra prática é limitar o esforço interno para que não consuma a inovação do Core.
- Cada subdomínio costuma virar **um ou mais Bounded Contexts** (veja 2.2.1.1), com sua própria linguagem.

## 🧩 Quiz de Fixação

1. O que diferencia um Supporting Subdomain de um Core e de um Generic?
2. Um módulo de cadastro de motoristas, simples e específico da empresa, deve receber design tático rico (Aggregates, eventos)? Por quê?
3. Quais riscos existem em tratar o suporte como "menos importante" e deixá-lo sem cuidado?

**Respostas:**
1) O Core é o diferencial competitivo e justifica o maior investimento. O Supporting é necessário e **específico do negócio**, mas sem vantagem competitiva e normalmente simples. O Generic é igual em todas as empresas (autenticação, pagamento) e tende a ser comprado ou reaproveitado. A fronteira entre suporte e genérico é a especificidade: se as regras são só da nossa empresa, é suporte.
2) Em geral não. Como não é diferencial e tem baixa complexidade, um serviço enxuto ou CRUD com validações atende, e o design tático rico traria custo (camadas, abstrações) sem retorno. O esforço de modelagem deve ficar no Core.
3) O negócio depende dele para operar: falhas ou dívida técnica no suporte afetam o Core, que o consome. Também há risco de acoplamento: se o Core usa diretamente o modelo interno do suporte, qualquer mudança lá o quebra. A solução é qualidade adequada e contratos estáveis, sem sofisticação desnecessária.
