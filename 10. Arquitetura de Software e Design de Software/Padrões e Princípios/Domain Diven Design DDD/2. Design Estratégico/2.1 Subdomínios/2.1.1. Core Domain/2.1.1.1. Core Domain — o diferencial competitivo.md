### Core Domain — o diferencial competitivo

O **Core Domain** é a parte do negócio que diferencia a empresa dos concorrentes e justifica a existência do software. É onde o investimento de modelagem e os melhores desenvolvedores devem estar. Identificá-lo é a primeira decisão estratégica do DDD, porque ela define **onde vale a pena ser sofisticado e onde não vale**.

---

## O conceito central

Um sistema grande nunca tem todas as partes com o mesmo valor. O DDD divide o **domínio** em **subdomínios** e classifica cada um em três tipos:

| Tipo | Valor para o negócio | Complexidade | Muda com que frequência |
|---|---|---|---|
| **Core** | Diferencial competitivo; é por isso que clientes escolhem a empresa | Alta | Muito; evolui o tempo todo |
| **Supporting** | Necessário para o negócio funcionar, mas **não** é diferencial | Média ou baixa | Pouco |
| **Generic** | Problema comum a muitas empresas, já resolvido pelo mercado | Pode ser alta | Devagar |

```
 Valor competitivo
        ▲
  alto  │   ┌─────────┐
        │   │  CORE   │  ← invista o melhor time e o melhor modelo
        │   └─────────┘
 médio  │        ┌────────────┐
        │        │ SUPPORTING │  ← faça simples, ou sob medida sem exagero
        │        └────────────┘
 baixo  │                ┌─────────┐
        │                │ GENERIC │  ← compre pronto / Open Source
        └────────────────┴─────────┴──► Especificidade do negócio
```

**Analogia:** num restaurante famoso pela sua receita de massa, a cozinha e a receita são o Core. O salão e a limpeza são suporte (precisam funcionar bem, mas ninguém escolhe o restaurante por isso). Pagar a fatura da energia ou contratar um serviço de contabilidade é genérico: usa-se o que o mercado já oferece.

---

## A classificação depende do negócio

O mesmo subdomínio pode ser Core numa empresa e genérico em outra. O que define é a **estratégia da empresa**, e não a tecnologia.

| Subdomínio | Numa empresa de identidade digital | Numa loja virtual |
|---|---|---|
| Autenticação e gestão de identidade | **Core** (é o produto) | Genérico (use um provedor pronto) |
| Recomendação de produtos | Suporte | Pode ser **Core** (se for o diferencial) |
| Faturamento | Genérico | Genérico |

> Por isso a pergunta nunca é "isso é difícil?", e sim "**isso é o que nos torna melhores que os concorrentes?**"

---

## Como identificar o Core Domain

Perguntas úteis para workshops com o negócio:

| Pergunta | O que revela |
|---|---|
| Se um concorrente copiasse esta parte, perderíamos clientes? | Alta resposta sugere Core |
| Esta parte aparece no pitch de vendas ou na proposta de valor? | Sugere Core |
| Compraríamos isto pronto se existisse? | Se sim, não é Core |
| Esta parte muda por decisão estratégica do negócio, e não por obrigação legal? | Sugere Core |
| Onde o negócio quer experimentar e inovar? | Sugere Core |
| Onde um erro custaria mais caro em receita ou reputação? | Pode apontar Core |

Evans propõe ainda a **Domain Vision Statement**: um parágrafo curto, escrito cedo, que nomeia o Core Domain e explica por que ele importa e que valor entrega. Serve de bússola para decidir prioridades e investimento. Confira a formulação original no livro dele.

## O que muda na prática

A classificação decide **como construir** cada parte:

| | Core | Supporting | Generic |
|---|---|---|---|
| **Construir ou comprar?** | Construir internamente | Construir simples, ou comprar e adaptar | **Comprar** ou usar Open Source |
| **Quem trabalha** | Os melhores desenvolvedores, em contato direto com especialistas | Time médio | Quase nenhum esforço de modelagem |
| **Design tático** | Rico: Aggregates, Domain Events, linguagem ubíqua refinada | Simples: pode ser CRUD | Integração com um produto externo |
| **Qualidade e testes** | Máxima | Boa | A do fornecedor |
| **Arquitetura** | Isolada (Hexagonal, Clean) | Pragmática | Atrás de uma Anticorruption Layer |
| **Terceirizar?** | Evite | Possível | Sim, ou já vem pronto |

```
 ┌──────────────────────── E-commerce ─────────────────────────┐
 │  Core:       motor de precificação e recomendação           │
 │              └─► time sênior, DDD tático completo           │
 │  Supporting: catálogo, cadastro de clientes                 │
 │              └─► CRUD bem feito                             │
 │  Generic:    autenticação, e-mail, faturamento, pagamento   │
 │              └─► Auth0/Cognito, SendGrid, gateway de pagto  │
 └─────────────────────────────────────────────────────────────┘
```

---

## O Core Domain muda com o tempo

- Um diferencial que **todos copiaram** deixa de ser Core e vira genérico ou de suporte, e então passa a valer a pena substituir por uma solução pronta.
- O que hoje é suporte pode virar Core se a estratégia mudar.
- Reavalie a classificação periodicamente, em geral junto com o planejamento estratégico.

---

## Erros comuns

| Erro | Consequência |
|---|---|
| Construir internamente algo **genérico** (autenticação própria, motor de e-mail) | Esforço gasto onde não há diferencial; risco de segurança |
| Colocar os melhores desenvolvedores no suporte | O Core fica com modelo raso e evolui devagar |
| Declarar tudo "Core" | Sem prioridade, o esforço se dilui; nada é de fato diferencial |
| Definir o Core só pela técnica ("é o mais complexo") | Complexidade não é diferencial; um problema genérico pode ser muito complexo |
| Nunca reavaliar | Investimento continua num diferencial que já virou commodity |
| Escolher o Core sem ouvir o negócio | Decisão técnica de algo que é estratégico |

## Relação com Bounded Contexts

Subdomínios pertencem ao **espaço do problema** (como o negócio se divide). Bounded Contexts pertencem ao **espaço da solução** (como o software se divide). O ideal é que um Bounded Context cubra **um** subdomínio, mas a correspondência nem sempre é um para um. Veja 2.2.1.1.

## 🧩 Quiz de Fixação

1. O que define um Core Domain, e por que "o mais complexo" não é um critério suficiente?
2. Autenticação é Core ou genérico? Justifique.
3. Como a classificação do subdomínio influencia a decisão de construir ou comprar e o nível de design tático aplicado?

**Respostas:**
1) O Core é a parte que dá vantagem competitiva e justifica o software: é o que os clientes valorizam e que os concorrentes teriam dificuldade de copiar. Complexidade não basta, porque problemas genéricos (como autenticação ou faturamento) podem ser muito complexos e, mesmo assim, não diferenciar a empresa; eles já foram resolvidos pelo mercado.
2) Depende do negócio. Para uma empresa cujo produto é identidade digital, é Core. Para uma loja virtual ou um SaaS comum, é genérico: usa-se um provedor pronto (Cognito, Auth0, Keycloak). A classificação nasce da estratégia da empresa, e não da tecnologia.
3) No Core: construir internamente, com os melhores desenvolvedores e design tático rico (Aggregates, Domain Events, linguagem ubíqua). No suporte: solução simples ou CRUD, construída ou adaptada. No genérico: comprar ou usar Open Source, isolando-o do modelo por uma Anticorruption Layer. Assim o investimento vai para onde gera diferencial.
