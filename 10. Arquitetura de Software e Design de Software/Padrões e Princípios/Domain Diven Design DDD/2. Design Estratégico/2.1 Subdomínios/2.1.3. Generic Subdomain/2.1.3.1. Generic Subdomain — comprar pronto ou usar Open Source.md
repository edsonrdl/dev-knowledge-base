### Generic Subdomain — comprar pronto ou usar Open Source

O **Generic Subdomain** (subdomínio genérico) é um problema que **toda empresa tem e que o mercado já resolveu**: autenticação, pagamento, envio de e-mail, faturamento. Pode ser tecnicamente difícil, mas não dá vantagem competitiva. A recomendação do DDD é **não reinventar**: comprar, usar um serviço gerenciado ou adotar uma solução Open Source, e guardar o esforço de engenharia para o Core.

---

## O conceito central

A distinção importante é entre **complexo** e **diferencial**. Um subdomínio genérico pode ser muito complexo (criptografia de senhas, conformidade de pagamentos), mas se **todos o fazem do mesmo jeito**, construí-lo internamente não torna a empresa melhor que os concorrentes.

```
                 Complexidade técnica
                        ▲
                 alta   │   ┌──────────┐        ┌──────────┐
                        │   │ GENERIC  │        │  CORE    │
                        │   │(pagamento)│        │(precific.)│
                        │   └──────────┘        └──────────┘
                 baixa  │   ┌──────────┐
                        │   │SUPPORTING│
                        │   └──────────┘
                        └────────────────────────────────────►
                          sem diferencial          diferencial
                                                   competitivo
```

**Analogia:** uma padaria famosa pelo pão não fabrica o próprio forno nem gera a própria energia: compra o equipamento e contrata a distribuidora. O esforço vai para a receita.

As fontes descrevem os genéricos como problemas já resolvidos, em que implementar por conta própria não traz vantagem competitiva. Por isso a orientação mais comum é adotar uma solução existente, e o objetivo é liberar recursos para o que de fato diferencia o negócio.

---

## Exemplos comuns

| Área | Opções prontas |
|---|---|
| **Autenticação e identidade** | Amazon Cognito, Auth0, Keycloak (Open Source), Azure AD B2C |
| **Pagamentos** | Stripe, Adyen, Mercado Pago, Pagar.me |
| **E-mail e SMS** | Amazon SES, SendGrid, Twilio |
| **Notificações push** | Firebase Cloud Messaging, Amazon SNS |
| **Faturamento e notas fiscais** | Sistemas ERP e emissores fiscais |
| **Busca textual** | Elasticsearch, OpenSearch, Algolia |
| **Armazenamento de arquivos** | Amazon S3 |
| **Observabilidade** | Prometheus, Grafana, Datadog |
| **Geração de PDF, planilhas** | Bibliotecas Open Source |

Lembre que a classificação depende do negócio: autenticação é genérica para uma loja virtual, mas é **Core** para uma empresa cujo produto é gestão de identidade (veja 2.1.1.1).

---

## Como lidar na prática

| Opção | Quando | Atenção |
|---|---|---|
| **Serviço gerenciado (SaaS)** | Quer entrega rápida e zero operação | Custo recorrente, dependência do fornecedor |
| **Open Source auto-hospedado** | Quer controle e evitar licença | Você assume a operação, atualizações e segurança |
| **Biblioteca / framework** | Problema pequeno e localizado | Manter atualizada; verifique a licença |
| **Construir internamente** | Não existe produto aderente, ou há exigência legal ou de soberania de dados | Custo contínuo de manutenção; mantenha o escopo mínimo |

## Protegendo o seu modelo: Anticorruption Layer

Ao integrar um componente genérico, **não deixe o vocabulário do fornecedor invadir o seu domínio**. Uma camada de tradução (porta + adaptador) mantém o modelo limpo e permite trocar de fornecedor.

```
 ┌──────────────── Seu Bounded Context (Vendas) ────────────────┐
 │                                                              │
 │  Pedido ──usa──► PagamentoGateway  (porta, linguagem sua)    │
 │                        ▲                                     │
 └────────────────────────┼─────────────────────────────────────┘
                          │ implementa
              ┌───────────┴───────────┐
              │  StripeAdapter (ACL)  │  traduz: Pedido ↔ PaymentIntent
              └───────────┬───────────┘
                          ▼
                    API da Stripe  (modelo e termos do fornecedor)
```

```java
// Porta: fala a linguagem do SEU domínio
public interface PagamentoGateway {
    ResultadoPagamento cobrar(PedidoId pedido, Dinheiro valor, MeioPagamento meio);
}

// Adaptador: único lugar que conhece a Stripe
public class StripeAdapter implements PagamentoGateway {
    private final StripeClient stripe;

    @Override
    public ResultadoPagamento cobrar(PedidoId pedido, Dinheiro valor, MeioPagamento meio) {
        var intent = stripe.paymentIntents().create(
            Map.of("amount", valor.centavos(), "currency", valor.moeda().codigo(),
                   "metadata", Map.of("pedido", pedido.valor())));
        return traduzir(intent);   // PaymentIntent → ResultadoPagamento
    }
}
```

**Explicando o exemplo:**
- O domínio fala em `PagamentoGateway`, `Dinheiro` e `ResultadoPagamento`, e nunca em `PaymentIntent`.
- Trocar de Stripe para Adyen significa escrever **um novo adaptador**, sem tocar no domínio.
- Testes do domínio usam um gateway falso, sem rede.

Veja o padrão em 2.3.1.3 (Anticorruption Layer) e a relação com Ports & Adapters no guia de Arquitetura Hexagonal.

## Riscos de adotar soluções prontas

| Risco | Mitigação |
|---|---|
| **Dependência do fornecedor** (*lock-in*) | Isolar atrás de uma porta; evitar espalhar o SDK pelo código |
| **Custo que cresce com o volume** | Monitorar e rever; comparar com o custo de operar internamente |
| **Dados fora do seu controle** (conformidade, LGPD) | Verificar contrato, localização dos dados e certificações |
| **Indisponibilidade do fornecedor** | Timeouts, retries, Circuit Breaker e plano de contingência |
| **Mudanças na API do fornecedor** | Adaptador único e testes de contrato |
| **Personalização limitada** | Avaliar antes de escolher; se for crítico, talvez não seja genérico |

---

## Quando faz sentido construir mesmo sendo genérico

- Não existe produto que atenda a requisitos legais, de latência ou de soberania de dados.
- O custo do produto, em escala, supera o de manter uma solução própria enxuta.
- A integração custaria mais do que a implementação simples e estável.

Mesmo assim: mantenha o escopo **mínimo**, trate como suporte e evite que consuma a energia de inovação do Core.

---

## Erros comuns

| Erro | Consequência |
|---|---|
| **Síndrome do "não foi inventado aqui"** (construir autenticação própria) | Esforço enorme, risco de segurança e nenhum diferencial |
| Espalhar o SDK do fornecedor por todo o código | Trocar de fornecedor vira reescrita |
| Deixar o modelo do fornecedor ditar o seu domínio | Vocabulário contaminado; perda de coesão |
| Classificar como genérico algo que é Core | Terceiriza o diferencial e perde vantagem |
| Escolher o fornecedor só pelo preço inicial | Custo total e lock-in aparecem depois |
| Ignorar as exigências de conformidade | Risco legal com dados de clientes |

## 🧩 Quiz de Fixação

1. Por que um subdomínio pode ser muito complexo e mesmo assim ser classificado como genérico?
2. Qual a função da Anticorruption Layer ao integrar um serviço de pagamento de terceiros?
3. Cite dois cenários em que seria razoável construir internamente um subdomínio genérico.

**Respostas:**
1) Porque complexidade técnica e diferencial competitivo são coisas diferentes. Um subdomínio genérico (como pagamentos ou autenticação) é feito de modo semelhante por todas as empresas e já foi resolvido pelo mercado; construí-lo internamente, mesmo sendo difícil, não faz a empresa melhor que a concorrência. Por isso o esforço deve ir para o Core.
2) Traduzir entre o modelo do fornecedor (por exemplo, `PaymentIntent`) e o modelo do seu domínio (`ResultadoPagamento`), isolando o vocabulário externo. Assim o domínio permanece limpo, o fornecedor pode ser trocado escrevendo um novo adaptador e os testes do domínio rodam sem depender da rede.
3) (a) Quando nenhum produto atende a requisitos legais, de latência ou de soberania de dados. (b) Quando, em escala, o custo do produto supera o de manter uma solução própria enxuta, ou quando a integração custaria mais que implementar uma versão simples e estável. Mesmo nesses casos, o escopo deve ser mínimo para não consumir a atenção do Core.
