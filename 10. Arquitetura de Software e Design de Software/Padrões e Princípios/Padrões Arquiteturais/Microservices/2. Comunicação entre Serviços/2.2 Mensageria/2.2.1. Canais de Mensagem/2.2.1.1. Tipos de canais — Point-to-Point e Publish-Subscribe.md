### Tipos de canais — Point-to-Point e Publish/Subscribe

Na comunicação assíncrona entre microsserviços, as mensagens trafegam por **canais** dentro de um broker. O tipo de canal define **quem recebe** cada mensagem: um único consumidor (Point-to-Point) ou todos os interessados (Publish/Subscribe). Escolher errado gera trabalho duplicado ou eventos perdidos.

---

## A pergunta que define o canal

> "Esta mensagem deve ser tratada por **um** consumidor ou por **todos** os que se interessam?"

```
 POINT-TO-POINT (fila)                    PUBLISH/SUBSCRIBE (tópico)

 Produtor ──► [ M1 M2 M3 ] ──┬─► Worker A   Produtor ──► [ Tópico ] ──┬─► Estoque    (cópia)
                (fila)       ├─► Worker B                             ├─► Pagamento  (cópia)
                             └─► Worker C                             └─► Notificação(cópia)
 Cada mensagem vai para               Cada assinante recebe sua própria
 UM único worker                      cópia da mesma mensagem
```

**Analogia:** Point-to-Point é a fila do caixa do mercado: cada cliente é atendido por um único caixa. Publish/Subscribe é uma rádio: o locutor fala uma vez e todos os ouvintes sintonizados recebem.

---

## Point-to-Point (fila)

O canal garante que **cada mensagem seja consumida por apenas um receptor**. Se vários receptores tentam ler a mesma mensagem, só um consegue, então os receptores não precisam se coordenar entre si.

**Competing Consumers:** vários workers podem ler a mesma fila em paralelo, e as mensagens se distribuem entre eles. Assim se escala o processamento horizontalmente: basta subir mais instâncias do consumidor.

| Característica | Detalhe |
|---|---|
| Entrega | Uma mensagem → um consumidor |
| Uso típico | **Comandos** e tarefas: "processar este pagamento", "redimensionar esta imagem" |
| Escala | Mais workers consomem em paralelo |
| Acoplamento | O produtor sabe que quer algo feito, e envia para a fila de quem faz |

---

## Publish/Subscribe (tópico)

O produtor publica um **evento** e o canal entrega **uma cópia a cada assinante**. O produtor não sabe quem são os consumidores nem quantos existem, o que dá desacoplamento forte: novos assinantes entram sem tocar no produtor.

**Detalhe importante:** a assinatura (subscription) é a unidade de consumo. Assinantes que compartilham a mesma assinatura **competem** pelas mensagens (como numa fila); assinaturas diferentes no mesmo tópico recebem **cópias separadas**.

| Característica | Detalhe |
|---|---|
| Entrega | Um evento → N assinantes (uma cópia cada) |
| Uso típico | **Eventos** de domínio: `PedidoCriado`, `PagamentoAprovado` |
| Acoplamento | O produtor anuncia um fato; quem reage é problema dos consumidores |
| Evolução | Adicionar um consumidor novo não exige mudar o produtor |

---

## Comando vs evento

| | Point-to-Point | Publish/Subscribe |
|---|---|---|
| Natureza da mensagem | **Comando** (imperativo: "faça X") | **Evento** (passado: "X aconteceu") |
| Destino | Um serviço específico | Quem tiver interesse |
| Quem decide o que fazer | O produtor | Cada consumidor |

---

## Como cada tecnologia implementa

| Tecnologia | Ponto a ponto | Pub/Sub | Observação |
|---|---|---|---|
| **RabbitMQ** | Fila ligada a um exchange | Exchange `fanout` ou `topic` com várias filas | Roteamento flexível; a mensagem é removida após o consumo |
| **Amazon SQS** | Fila | Padrão **SNS → várias filas SQS** | SQS sozinho não faz fan-out; o SNS distribui para uma fila por consumidor |
| **Apache Kafka** | Um *consumer group* com vários consumidores | Vários *consumer groups* no mesmo tópico | O log é retido e permite reprocessar; cada grupo lê o fluxo inteiro |
| **Google Pub/Sub** | Várias instâncias na mesma subscription | Várias subscriptions no tópico | Tópico dá a semântica de pub/sub; a subscription, a de consumidores concorrentes |

Diferença-chave de retenção: RabbitMQ e SQS **removem** a mensagem após o consumo, enquanto o Kafka **retém** o log e permite que novos consumidores releiam desde o início. Confira os limites e comportamentos exatos na documentação oficial de cada produto.

## Exemplo prático

```
 pedido-service ──publica "PedidoCriado"──► Tópico "pedidos"
                                              │
                    ┌─────────────────────────┼─────────────────────────┐
                    ▼                         ▼                         ▼
             Fila "estoque"           Fila "pagamento"          Fila "notificacao"
                    │                         │                         │
            ┌───────┴───────┐         (1 worker)               (2 workers competindo)
            ▼               ▼
        worker 1        worker 2      ← competing consumers dentro de cada fila
```

- O **tópico** espalha o evento para três interessados (Pub/Sub).
- Cada **fila** garante que um único worker do serviço trate cada cópia (Point-to-Point).
- Na prática, os dois tipos se **combinam**: tópico para fan-out e filas para escalar cada consumidor.

---

## Cuidados e armadilhas

- **Mensagens duplicadas:** a maioria dos brokers entrega *pelo menos uma vez*; o consumidor deve ser **idempotente**.
- **Mensagens venenosas:** uma mensagem que sempre falha pode travar o consumo. Use **Dead Letter Queue (DLQ)**: após N tentativas, a mensagem vai para uma fila separada para análise.
- **Ordenação:** com vários consumidores concorrentes, a ordem global não é garantida; se importa, particione por chave (por exemplo, por `pedidoId`).
- **Acoplamento por esquema:** o formato do evento é um contrato; versione e valide (veja 2.1.2.1).
- **Publicar de forma confiável:** gravar no banco e publicar o evento sem atomicidade é o problema de **Dual Write** (veja o domínio 3).
- **Rastreabilidade:** inclua ID de correlação nas mensagens.

---

## Quando usar cada um

| Cenário | Canal |
|---|---|
| Processar tarefas pesadas em background | Point-to-Point |
| Distribuir carga entre várias instâncias | Point-to-Point (competing consumers) |
| Notificar vários serviços sobre um fato | Publish/Subscribe |
| Adicionar consumidores sem mexer no produtor | Publish/Subscribe |
| Reprocessar histórico de eventos | Pub/Sub com log retido (Kafka) |

## 🧩 Quiz de Fixação

1. Qual a diferença de entrega entre um canal Point-to-Point e um Publish/Subscribe?
2. No SQS, como se obtém o comportamento de fan-out? E no Kafka?
3. Um consumidor recebe a mesma mensagem duas vezes e cobra o cliente em dobro. Que prática evitaria isso, e que mecanismo trata mensagens que falham sempre?

**Respostas:**
1) No Point-to-Point, cada mensagem é entregue a um único consumidor, e vários workers competem pela fila para escalar o processamento. No Publish/Subscribe, o evento é entregue a todos os assinantes, cada um com a sua própria cópia, e o produtor não sabe quem são.
2) No SQS, combina-se um tópico SNS com uma fila SQS por consumidor, porque o SQS sozinho não faz fan-out. No Kafka, cada consumer group lê o tópico inteiro de forma independente, e consumidores dentro do mesmo grupo dividem as partições (competem).
3) Tornar o consumidor **idempotente** (por exemplo, guardando o ID da mensagem/transação já processada e ignorando repetições), pois a entrega costuma ser "pelo menos uma vez". Mensagens que falham sempre vão para uma **Dead Letter Queue** após um número de tentativas, para não bloquear a fila e permitir análise.
