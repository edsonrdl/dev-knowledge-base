### API First Design — contrato antes do código

Em microsserviços, a API é a **única** fronteira entre times e serviços. API First Design significa tratar essa API como um produto: projetá-la e acordá-la **antes** de escrever a implementação, em um contrato legível por máquina. Este arquivo explica a ideia, o fluxo de trabalho, as ferramentas e como evitar quebrar consumidores.

---

## O conceito central

No modelo **code-first**, o time escreve o serviço e a documentação da API é um subproduto, geralmente gerado depois e frequentemente desatualizado. No modelo **API First** (ou contract-first), o contrato vem primeiro e é a **fonte da verdade**: cliente e servidor são construídos a partir dele.

**Analogia:** é a planta de um prédio. Eletricista, encanador e pedreiro trabalham em paralelo porque todos seguem a mesma planta. Se cada um improvisar, as paredes não se encontram.

```
 CODE-FIRST                              API FIRST
 ┌────────────┐                          ┌─────────────────┐
 │ Escreve o  │                          │ Desenha o       │
 │ serviço    │                          │ contrato (spec) │
 └─────┬──────┘                          └───────┬─────────┘
       ▼                                  revisão com consumidores
 ┌────────────┐                                   │
 │ Gera a doc │                       ┌───────────┼───────────┐
 │ (depois)   │                       ▼           ▼           ▼
 └─────┬──────┘                   Servidor     Cliente      Mock / Docs
       ▼                          (implementa) (consome)    (gerados)
 Consumidores descobrem                  tudo em paralelo
 mudanças em produção
```

---

## Por que isso importa em microsserviços

- **Times independentes:** quem consome pode começar a trabalhar contra um mock enquanto o serviço ainda não existe.
- **Menos retrabalho:** o desenho é discutido com consumidores antes de virar código.
- **Evolução segura:** o contrato permite detectar mudanças que quebram clientes.
- **Documentação sempre atual:** ela deriva do mesmo arquivo que gera o código.

---

## O contrato: OpenAPI e seus equivalentes

O **OpenAPI** é um formato neutro, mantido pela OpenAPI Initiative (Linux Foundation), para descrever APIs HTTP em um arquivo legível por máquina. Ele descreve operações, parâmetros e formatos de requisição e resposta. Como é legível por máquina, as ferramentas conseguem:

| Uso | O que acontece |
|---|---|
| **Gerar documentação** | Referência da API sempre sincronizada com o contrato |
| **Gerar código** | Esqueleto de servidor e clientes em várias linguagens |
| **Criar mocks** | Servidor falso, a partir dos exemplos, para testar antes da implementação |
| **Validar** | Checar requisições e respostas contra o formato esperado |

| Estilo de API | Formato de contrato |
|---|---|
| REST / HTTP | OpenAPI |
| gRPC | Arquivos `.proto` (Protocol Buffers) |
| Mensageria / eventos | AsyncAPI e schemas (Avro, JSON Schema, Protobuf) em um Schema Registry |

Exemplo mínimo de contrato OpenAPI:

```yaml
openapi: 3.0.3
info: { title: Pedidos, version: 1.0.0 }
paths:
  /pedidos/{id}:
    get:
      summary: Busca um pedido
      parameters:
        - { name: id, in: path, required: true, schema: { type: string } }
      responses:
        "200":
          description: Pedido encontrado
          content:
            application/json:
              schema: { $ref: "#/components/schemas/Pedido" }
        "404": { description: Pedido não existe }
components:
  schemas:
    Pedido:
      type: object
      required: [id, status]
      properties:
        id: { type: string }
        status: { type: string, enum: [CRIADO, PAGO, CANCELADO] }
```

O arquivo diz **o quê**, não **como**: caminho, parâmetro, respostas possíveis e o formato do `Pedido`.

## O fluxo de trabalho

```
 1. Levantar necessidades com os consumidores
 2. Escrever o contrato (OpenAPI / .proto / AsyncAPI)
 3. Revisar o contrato (como se revisa código) e aprovar
 4. Publicar o contrato (repositório ou catálogo de APIs)
 5. Em paralelo: servidor implementa, clientes usam mock, docs são geradas
 6. CI valida que a implementação respeita o contrato
 7. Evoluir o contrato com versionamento e checagem de compatibilidade
```

---

## Evolução e mudanças que quebram clientes

Uma mudança é **breaking** quando um consumidor que funcionava passa a falhar sem ter sido alterado.

| Mudança | Compatível? |
|---|---|
| Adicionar campo **opcional** na resposta | Sim |
| Adicionar endpoint novo | Sim |
| **Remover** um campo ou endpoint | Não |
| **Mudar o tipo** de um campo | Não |
| Adicionar campo **obrigatório** na requisição | Não |
| Renomear campo ou mudar o significado dele | Não |

**Como se proteger:**

- **Diff de OpenAPI no CI:** o pipeline compara o contrato novo com o da branch base e falha se achar mudança incompatível.
- **Contract testing orientado ao consumidor (ex.: Pact):** cada consumidor registra o que usa, e o provedor verifica que continua atendendo. Isso pega o que o contrato sozinho não mostra, como o uso real.
- **Versionamento:** mudanças incompatíveis exigem nova versão maior (ex.: `/v2/`), plano de migração e data de desativação da versão antiga.
- **Regra de Postel nas pontas:** o consumidor deve ignorar campos desconhecidos (*tolerant reader*), o que permite evoluir o provedor sem coordenação.

As duas abordagens se complementam: o diff valida o provedor contra o próprio contrato, e o contract testing valida o provedor contra o uso real dos consumidores.

## Boas práticas de design de contrato

- Modele pelo **domínio**, não pelo banco: nomes do negócio, e não colunas.
- Use **erros padronizados** (por exemplo, Problem Details, RFC 9457) com códigos estáveis.
- Torne operações de escrita **idempotentes** (chave de idempotência), pois retries acontecem.
- Planeje **paginação**, filtros e limites desde o início.
- Não exponha detalhes internos (IDs de tabela, estruturas de ORM).
- Documente com **exemplos** reais; eles viram mocks e testes.

---

## Quando usar e limitações

| Use quando | Cuidado |
|---|---|
| Vários times consomem a API | Em protótipo de um dev só, pode ser cerimônia demais |
| API pública ou de parceiros | O contrato exige disciplina de revisão e versionamento |
| Quer paralelizar front, back e QA | Contrato mal pensado engessa; revise com consumidores reais |

> [!warning] Erro comum
> Escrever o OpenAPI só como documentação e deixar o código divergir dele. Sem validação no CI, o contrato vira ficção e perde o valor.

## 🧩 Quiz de Fixação

1. Qual a diferença entre code-first e API First, e qual problema do dia a dia o API First reduz?
2. Cite três mudanças que quebram consumidores e duas que são seguras.
3. Como o diff de OpenAPI e o contract testing orientado ao consumidor se complementam?

**Respostas:**
1) Em code-first, o serviço é escrito antes e a documentação é gerada depois, muitas vezes desatualizada. Em API First, o contrato vem primeiro e é a fonte da verdade para servidor, cliente, mocks e docs. Isso reduz o retrabalho e a descoberta tardia de incompatibilidades, e permite que os times trabalhem em paralelo.
2) Quebram: remover campo ou endpoint, mudar o tipo de um campo, adicionar campo obrigatório na requisição. São seguras: adicionar campo opcional na resposta e adicionar um endpoint novo.
3) O diff compara o contrato novo com o antigo e pega alterações incompatíveis em relação ao que foi publicado. O contract testing capta o que cada consumidor realmente usa e verifica se o provedor continua atendendo. O primeiro valida o provedor contra o próprio contrato; o segundo, contra o uso real. Juntos cobrem as falhas que cada um deixaria passar.
