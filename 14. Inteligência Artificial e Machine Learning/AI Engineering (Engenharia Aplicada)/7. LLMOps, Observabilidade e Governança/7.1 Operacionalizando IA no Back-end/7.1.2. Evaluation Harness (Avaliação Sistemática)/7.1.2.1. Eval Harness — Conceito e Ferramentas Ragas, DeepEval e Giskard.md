### Eval Harness — O Que É, e as Ferramentas Ragas, DeepEval e Giskard

"Parece que melhorou" não é uma métrica. Em aplicações com LLM, qualquer mudança (um prompt, um modelo, um chunking, um reranker) pode melhorar uns casos e piorar outros **sem aviso**. A resposta de engenharia é a mesma de qualquer software: **testes automatizados**. Para sistemas com LLM, isso se chama **Eval Harness** (arcabouço de avaliação). Este arquivo apresenta o conceito e três ferramentas com focos distintos: **Ragas** (RAG), **DeepEval** (testes gerais de LLM, estilo pytest) e **Giskard** (riscos, vieses e conformidade). O tópico seguinte (7.1.2.2) completa com **inspect_ai, PromptFoo, LLM-as-a-Judge e golden dataset**.

---

## O que é um Eval Harness

> **Eval Harness** é um **framework de avaliação automatizado** que executa **casos de teste** contra o seu sistema e produz **métricas agregadas**, de forma repetível. É essencial para **CI/CD de LLMs**.

```
 ┌────────────────────── EVAL HARNESS ──────────────────────┐
 │                                                            │
 │  DATASET de casos         SISTEMA sob teste                │
 │  (entrada + referência)  ──►(chatbot, RAG, agente, prompt) ──► saídas
 │                                                            │      │
 │              MÉTRICAS / AVALIADORES ◄──────────────────────┘      │
 │   (regras determinísticas, LLM-juiz, similaridade, humano)         │
 │                        │                                           │
 │                        ▼                                           │
 │        RELATÓRIO: notas por caso, agregadas, por categoria, regressões
 └────────────────────────────────────────────────────────────┘
                        │
                        ▼  limiares → PASSA / FALHA o pipeline (CI/CD)
```

**Analogia:** é a **suíte de testes** do software, mas em vez de `assert resultado == 42`, os testes verificam **qualidades graduais** ("a resposta é fiel aos documentos?", "tom adequado?"). E, como em qualquer suíte, o valor está em rodar **a cada mudança**, e não só quando alguém se lembra.

### Por que testes tradicionais não bastam

| Teste tradicional | Teste de LLM |
|---|---|
| Saída **determinística** | Saída **variável** (não dá para comparar por igualdade exata) |
| Correto/incorreto (binário) | Qualidades **graduais** e múltiplas (fidelidade, relevância, tom, segurança) |
| Um caso, um resultado | Precisa de **conjuntos** de casos e **estatística** (média, distribuição, intervalos) |
| Falha = exceção | Falha = **resposta ruim** sem exceção |
| Dependências estáveis | O modelo/provedor muda (atualizações silenciosas de versão) |

### Os componentes de um harness

| Componente | O que é | Exemplo |
|---|---|---|
| **Dataset de casos** | Entradas + (opcional) saída de referência, contexto esperado, rótulos | 200 perguntas reais com a resposta correta e a cláusula-fonte |
| **Alvo (system under test)** | A função/serviço avaliado | `responder(pergunta) -> resposta, contextos` |
| **Avaliadores/métricas** | Como pontuar cada saída | Fidelidade, relevância, correção, toxicidade, formato JSON válido |
| **Execução** | Roda os casos (paralelo, com cache e *retries*) | Pytest, CLI, notebooks, pipeline |
| **Agregação e relatório** | Notas por caso e por métrica, comparação entre versões | Painel, JSON, tabela |
| **Critérios de aprovação** | Limiares que decidem passa/falha | "faithfulness ≥ 0,85; nenhuma queda > 5%" |
| **Integração CI/CD** | Roda a cada PR/deploy e **bloqueia** regressões | GitHub Actions, GitLab CI |
| **Rastreabilidade** | Versão do prompt/modelo/dataset de cada execução | Comparar a versão A × B |

### Tipos de avaliação

| Tipo | Quando | Características |
|---|---|---|
| **Offline** (pré-deploy) | Em desenvolvimento/CI, com dataset fixo | Repetível, rápido de iterar; pode não representar o uso real |
| **Online** (produção) | Sobre tráfego real (amostra) | Realista; sem gabarito, usa LLM-juiz e feedback (7.1.1.1) |
| **Humana** | Casos críticos, calibração de juízes | Padrão-ouro; cara e lenta |
| **A/B** | Comparar duas versões com usuários reais | Mede efeito de negócio |
| **Red teaming** | Procurar falhas de segurança e abuso | Adversarial (7.1.4.1) |

### Tipos de métricas

| Família | Exemplos | Observação |
|---|---|---|
| **Determinísticas / baseadas em regra** | JSON válido, contém a citação, tamanho, regex, execução do código gerado passa nos testes | **Baratas e confiáveis**: use sempre que possível |
| **Similaridade com referência** | Exact match, F1, BLEU/ROUGE, similaridade por embeddings (BERTScore) | Úteis em tarefas fechadas; fracas para texto livre |
| **Baseadas em LLM-juiz** | Fidelidade, relevância, completude, tom, coerência | **Flexíveis**; exigem calibração (7.1.2.2) |
| **De recuperação (retrieval)** | Hit Rate@k, MRR, nDCG, recall de contexto | Avaliam a etapa de busca isoladamente |
| **De segurança** | Taxa de injeção bem-sucedida, vazamento de PII, toxicidade, recusa indevida | Essenciais antes de produção |
| **De desempenho e custo** | Latência, tokens, custo por consulta | Entram no relatório junto da qualidade |

> **Regra de ouro:** combine **métricas determinísticas** (o que dá para checar por código) com **LLM-juiz** (o que exige julgamento) e **amostras humanas** (para validar os dois).

## Avaliar componentes e o sistema ponta a ponta

```
RAG:  pergunta ─► [RETRIEVAL] ─► contextos ─► [GERAÇÃO] ─► resposta

Avaliação de COMPONENTES (diagnóstico):                 Avaliação PONTA A PONTA (resultado):
 • Retrieval: os contextos certos vieram?                • A resposta final é correta, fiel e útil?
   (context recall/precision, Hit Rate, MRR)             • Taxa de aprovação, satisfação
 • Geração: dado o contexto, a resposta é fiel?
   (faithfulness, answer relevancy)
```

Medir **só o fim** diz *que* piorou; medir **os componentes** diz *onde*. Bons harnesses fazem os dois.

## 1. Ragas (RAG Assessment)

### O que é

Biblioteca de código aberto **especializada em avaliar sistemas RAG**. Seu diferencial é um conjunto de métricas **sem referência** (*reference-free*) baseadas em LLM, que avaliam a qualidade da **recuperação** e da **geração** mesmo sem respostas "corretas" escritas à mão, e ferramentas para **gerar conjuntos de teste sintéticos** a partir dos seus documentos.

### As métricas principais

Cada amostra de avaliação tem: `user_input` (pergunta), `retrieved_contexts` (trechos recuperados), `response` (resposta gerada) e, quando há, `reference` (resposta ideal).

| Métrica | Pergunta que responde | O que mede | Precisa de referência? |
|---|---|---|---|
| **Faithfulness** (fidelidade) | A resposta é **sustentada pelos contextos recuperados**? | Fração das afirmações da resposta que podem ser inferidas do contexto (detecta alucinação) | Não |
| **Answer/Response Relevancy** | A resposta **atende à pergunta**? | Quão pertinente e completa é a resposta em relação à pergunta | Não |
| **Context Precision** | Os trechos recuperados **relevantes estão bem posicionados** (no topo)? | Qualidade do ranking: relevantes primeiro, sem ruído | Sim/Não* |
| **Context Recall** | O contexto recuperado **contém tudo** o necessário? | Quanto da resposta de referência está coberto pelo contexto | **Sim** |
| **Context Entities Recall** | As entidades-chave estão no contexto? | Cobertura de entidades (nomes, datas, valores) | Sim |
| **Answer Correctness / Factual Correctness** | A resposta está **correta** versus a referência? | Concordância factual | **Sim** |
| **Noise Sensitivity** | O sistema é **enganado por contexto irrelevante**? | Robustez a distratores | Sim |

\* Há variantes com e sem referência.

```
Diagnóstico por métricas:

 faithfulness BAIXA  + context recall ALTO   → o contexto tinha a resposta, mas o MODELO inventou   (problema de GERAÇÃO)
 context recall BAIXO                        → a resposta nem estava no contexto                     (problema de RETRIEVAL)
 context precision BAIXA                     → muito ruído no topo: reranker/chunking                (problema de RANKING)
 answer relevancy BAIXA                      → resposta fora do assunto/vaga                         (problema de PROMPT/modelo)
```

### Exemplo

```python
from datasets import Dataset
from ragas import evaluate
from ragas.metrics import faithfulness, answer_relevancy, context_precision, context_recall

amostras = {
    "question":      ["Qual o prazo de rescisão sem multa no contrato Acme?"],
    "answer":        ["O prazo é de 30 dias, conforme a cláusula 8.2."],              # resposta do SEU sistema
    "contexts":      [["Cláusula 8.2: A rescisão sem multa exige aviso prévio de 30 dias...", "Cláusula 9: ..."]],
    "ground_truth":  ["30 dias de aviso prévio (cláusula 8.2)."],                      # referência (opcional p/ algumas métricas)
}
resultado = evaluate(Dataset.from_dict(amostras),
                     metrics=[faithfulness, answer_relevancy, context_precision, context_recall])
print(resultado)            # {'faithfulness': 1.0, 'answer_relevancy': 0.96, 'context_precision': 1.0, 'context_recall': 1.0}
df = resultado.to_pandas()  # nota por caso: encontre os piores
```

(A API do Ragas mudou bastante entre versões — nomes de colunas, classes de métrica e de amostra; consulte a documentação da versão instalada.)

### Geração de conjuntos de teste sintéticos

O Ragas pode **gerar perguntas e respostas** a partir dos seus documentos (variando tipos: simples, de raciocínio, multi-documento), criando um dataset inicial de avaliação sem anotação manual (cf. dados sintéticos, 6.1.3.1). **Sempre revise por amostragem** antes de confiar.

### Pontos fortes e cuidados

| Pontos fortes | Cuidados |
|---|---|
| **Foco em RAG**, separa recuperação e geração | Métricas dependem de **LLM-juiz**: custo e **variabilidade** entre execuções |
| Muitas métricas **sem referência** (viável em produção) | O juiz tem vieses; **calibre com avaliação humana** |
| Geração de testes sintéticos | Datasets sintéticos podem ser **fáceis demais**: complemente com perguntas reais |
| Integra-se a LangChain/LlamaIndex e a plataformas de observabilidade | API e métricas **mudam** entre versões |
| Código aberto | Notas absolutas importam menos que **comparações entre versões** com o mesmo juiz |

**Quando usar:** sistemas **RAG**, para diagnosticar retrieval vs. geração e comparar mudanças (chunking, embedding, reranker, prompt).

## 2. DeepEval

### O que é

Framework de código aberto que traz a **experiência de testes unitários (estilo pytest)** para LLMs. Você escreve **casos de teste** e **métricas** e roda `deepeval test run`, integrando facilmente ao CI/CD. Cobre **RAG, agentes, chatbots e segurança**, com métricas baseadas em LLM-juiz e determinísticas.

### Conceitos

| Conceito | Descrição |
|---|---|
| **`LLMTestCase`** | Um caso: `input`, `actual_output`, `expected_output`, `retrieval_context`, `context`, `tools_called`... |
| **Métricas prontas** | `AnswerRelevancyMetric`, `FaithfulnessMetric`, `ContextualPrecision/Recall/RelevancyMetric` (RAG); `HallucinationMetric`; `BiasMetric`, `ToxicityMetric`; `TaskCompletionMetric`, `ToolCorrectnessMetric` (agentes); e outras |
| **G-Eval** | Métrica **customizável**: você descreve **critérios em linguagem natural** e o LLM-juiz avalia (baseada no método G-Eval: critérios → passos de avaliação → nota) |
| **DAG metric** | Árvores de decisão determinísticas combinadas com julgamento do LLM |
| **Conversas multi-turno** | Casos e métricas para diálogos |
| **Dataset e *synthesizer*** | Gerenciar datasets e **gerar casos sintéticos** |
| **Integrações** | Pytest, LangChain, LlamaIndex, CI/CD, plataforma Confident AI (opcional, SaaS) |
| **Red teaming** | Módulos para testar vulnerabilidades (ex.: DeepTeam) |

### Exemplo estilo pytest

```python
# test_chatbot.py
import pytest
from deepeval import assert_test
from deepeval.test_case import LLMTestCase, LLMTestCaseParams
from deepeval.metrics import AnswerRelevancyMetric, FaithfulnessMetric, GEval

TOLERANCIA = 0.8                                           # limiar de aprovação

tom_formal = GEval(                                         # métrica customizada em linguagem natural
    name="Tom formal e objetivo",
    criteria="A resposta deve ser formal, objetiva, sem gírias e começar pela conclusão.",
    evaluation_params=[LLMTestCaseParams.INPUT, LLMTestCaseParams.ACTUAL_OUTPUT],
    threshold=0.7,
)

CASOS = carregar_golden("golden.jsonl")                    # lista de {pergunta, ...}

@pytest.mark.parametrize("c", CASOS)
def test_resposta(c):
    saida, contextos = meu_rag(c["pergunta"])               # roda o SISTEMA sob teste
    caso = LLMTestCase(input=c["pergunta"], actual_output=saida,
                       expected_output=c["resposta_ref"], retrieval_context=contextos)
    assert_test(caso, [AnswerRelevancyMetric(threshold=TOLERANCIA),
                       FaithfulnessMetric(threshold=TOLERANCIA), tom_formal])
```

```bash
deepeval test run test_chatbot.py        # executa como suíte; falha se alguma métrica < limiar
```

(Nomes de classes e parâmetros variam por versão: consulte a documentação.)

### Pontos fortes e cuidados

| Pontos fortes | Cuidados |
|---|---|
| **Fricção mínima para devs** (pytest, CI/CD) | Métricas via LLM-juiz têm **custo e variância** |
| **Muitas métricas prontas** + G-Eval customizável | Notas de juízes diferentes **não são comparáveis** entre si |
| Cobre RAG, agentes, segurança | Plataforma SaaS associada: avalie privacidade antes de enviar dados |
| Datasets e geração sintética | Limiares precisam de **calibração** com seus dados |

**Quando usar:** times de produto que querem **testes de regressão de LLM dentro do fluxo de desenvolvimento** (PR → testes → bloqueio), com métricas variadas.

## 3. Giskard

### O que é

Ferramenta de código aberto (com versão corporativa) voltada a **detectar vulnerabilidades, vieses e falhas** em modelos de IA, de ML tradicional a LLMs, e a gerar **relatórios estruturados de risco**. É ideal para **auditoria e conformidade** (LGPD, regulações financeiras, governança de IA, EU AI Act).

### Capacidades principais

| Capacidade | Descrição |
|---|---|
| **Scan automático de vulnerabilidades** | Roda baterias de **sondas adversariais** contra o seu modelo/aplicação e relata falhas |
| **Categorias de risco para LLMs** | **Alucinação e desinformação**, **prompt injection**, vazamento de informação sensível, **viés e estereótipos**, conteúdo nocivo, geração de conteúdo indevido, robustez a variações da entrada |
| **RAGET (RAG Evaluation Toolkit)** | Gera **conjunto de testes para RAG** com tipos distintos de pergunta (simples, complexa, distratora, situacional, dupla, conversacional) e **diagnostica por componente** (gerador, recuperador, reescritor, base de conhecimento) |
| **Relatórios** | Relatório navegável/exportável dos problemas encontrados, com exemplos, para stakeholders técnicos e de compliance |
| **Suítes de teste** | Transforma achados em **testes reproduzíveis** para o CI/CD |
| **Foco em ML tradicional também** | Testes para modelos tabulares/NLP clássicos (viés, desempenho por fatia) |

```python
# Esboço (API ilustrativa) — escanear uma aplicação de LLM com o Giskard
import giskard

def responder(df):                                           # envolve o seu sistema sob teste
    return [meu_assistente(p) for p in df["pergunta"]]

modelo = giskard.Model(
    model=responder, model_type="text_generation",
    name="Assistente de crédito",
    description="Responde dúvidas de clientes sobre crédito pessoal, com base nas políticas internas.",
    feature_names=["pergunta"],
)
relatorio = giskard.scan(modelo)                             # roda sondas: injeção, viés, alucinação, PII...
relatorio.to_html("relatorio_riscos.html")                   # relatório de auditoria
suite = relatorio.generate_test_suite("Suíte de segurança v1")   # vira testes reutilizáveis
suite.run()
```

(Interfaces e versões mudam — confirme na documentação.)

### Pontos fortes e cuidados

| Pontos fortes | Cuidados |
|---|---|
| **Visão de risco e conformidade**: relatórios para auditoria | Scans por LLM podem ter **falsos positivos/negativos**: revise manualmente |
| Cobre **vieses e segurança**, não só qualidade | Não substitui **red teaming humano** nem análise jurídica |
| RAGET diagnostica o RAG por componente | A **descrição do modelo** no scan influencia as sondas: escreva com cuidado |
| Código aberto + opção corporativa | Algumas capacidades avançadas são da versão paga |

**Quando usar:** antes de ir à produção e periodicamente, em domínios **regulados** (finanças, saúde, jurídico), para **mapear riscos** (alucinação, viés, injeção, vazamento) e documentar a diligência.

## Comparativo

| Critério | **Ragas** | **DeepEval** | **Giskard** |
|---|---|---|---|
| **Foco** | **Qualidade de RAG** (retrieval + geração) | **Testes de regressão de LLM** (pytest) | **Riscos, vieses e conformidade** |
| **Estilo** | Biblioteca de métricas + geração de testes | Framework de testes unitários e CI/CD | Scanner de vulnerabilidades + relatórios |
| **Métricas típicas** | Faithfulness, relevancy, context precision/recall | Relevância, fidelidade, alucinação, G-Eval, tarefas de agente, toxicidade | Injeção, vazamento, viés, alucinação, robustez |
| **Dataset sintético** | Sim (testset generation) | Sim (synthesizer) | Sim (RAGET) |
| **Integração CI/CD** | Via scripts | **Nativa** (pytest) | Suítes de testes exportáveis |
| **Saída para stakeholders de risco** | Métricas | Métricas/painel | **Relatório de auditoria** |
| **Melhor para** | Otimizar e diagnosticar RAG | Qualidade contínua no ciclo de dev | Governança, segurança e compliance |

São **complementares**: um time maduro pode usar **Ragas** (ou métricas equivalentes) para diagnosticar o RAG, **DeepEval/PromptFoo** (7.1.2.2) no CI para regressão e **Giskard** (ou red teaming) em auditorias periódicas.

### Árvore de decisão

```
O que você quer garantir?
 ├─ Qualidade do RAG e saber ONDE está o problema (retrieval × geração) ─► Ragas
 ├─ Bloquear regressões a cada PR com testes no estilo pytest ───────────► DeepEval (ou PromptFoo)
 ├─ Mapear riscos (viés, injeção, vazamento, alucinação) para compliance ─► Giskard (+ red teaming)
 ├─ Avaliar capacidades/segurança com protocolos de pesquisa e benchmarks ─► inspect_ai (7.1.2.2)
 └─ Comparar prompts/modelos lado a lado e testar em CI com configuração simples ─► PromptFoo (7.1.2.2)
```

## Implementando um eval harness do zero (e quando basta)

Nem sempre é preciso uma biblioteca. Um harness mínimo cabe em poucas linhas e é um bom começo:

```python
import json, statistics, concurrent.futures as cf

def avaliar(sistema, casos, avaliadores, workers=8):
    def um(caso):
        saida = sistema(caso["entrada"])                                  # roda o sistema
        notas = {nome: fn(caso, saida) for nome, fn in avaliadores.items()}  # cada avaliador devolve 0..1
        return {"id": caso["id"], "saida": saida, "notas": notas}
    with cf.ThreadPoolExecutor(workers) as pool:
        resultados = list(pool.map(um, casos))
    agregado = {n: statistics.mean(r["notas"][n] for r in resultados) for n in avaliadores}
    return resultados, agregado

avaliadores = {
    "formato_json": lambda c, s: float(json_valido(s)),                   # determinístico
    "cita_fonte":   lambda c, s: float("[" in s and "]" in s),            # determinístico
    "fidelidade":   lambda c, s: juiz_fidelidade(c["contextos"], s),      # LLM-juiz (0..1)
}
resultados, agregado = avaliar(meu_rag, casos, avaliadores)
assert agregado["fidelidade"] >= 0.85, f"Regressão de fidelidade: {agregado}"      # critério de aprovação
```

| Quando basta o caseiro | Quando adotar uma ferramenta |
|---|---|
| Poucas métricas, equipe pequena, protótipo | Muitas métricas, agentes, multi-turno, geração de testes |
| Lógica de avaliação muito específica do domínio | Padronização entre times; relatórios; integrações |
| Queremos controle total e zero dependência | Precisamos de colaboração, versionamento e painéis |

Recomendação: **comece simples** (métricas determinísticas + um juiz), e adote ferramentas quando a complexidade pedir.

## Boas práticas de um eval harness

| Prática | Motivo |
|---|---|
| **Dataset com casos reais** (inclusive difíceis, ruidosos e adversariais) | Representa o uso real |
| **Métricas determinísticas primeiro**, LLM-juiz para o resto | Barato, estável e confiável |
| **Avaliar componentes e ponta a ponta** | Diagnóstico + resultado |
| **Versionar** dataset, prompts, modelos, juízes e resultados | Comparar versões com rigor |
| **Fixar o juiz** (modelo e prompt) ao comparar versões | Evita variações espúrias |
| **Repetir execuções** e reportar intervalos (não só a média) | A variabilidade do LLM exige estatística |
| **Limiares de aprovação e bloqueio de CI** | Transforma avaliação em controle de qualidade |
| **Segmentar por categoria/cliente/dificuldade** | Médias escondem falhas localizadas |
| **Calibrar juízes com humanos** | Garante que a métrica significa algo |
| **Ligar produção ao harness** (traces ruins viram casos de teste, 7.1.1.1) | Dataset sempre atual |
| **Controlar custo** (cache de saídas, subamostragem em PRs, suíte completa à noite) | Avaliação sustentável |
| **Separar conjunto de desenvolvimento e de teste** | Evita overfitting às métricas |

## Exemplo prático: pipeline de qualidade de um assistente de crédito

```
Objetivo: impedir regressões e documentar riscos de um assistente RAG em instituição financeira.

1. Dataset (versionado): 300 casos reais anonimizados + 60 adversariais (injeção, pedido de dados de terceiros,
   viés) + 40 "fora de escopo" (esperado: recusar/escalar). Rotulados por analistas e jurídico.

2. Métricas:
   • Determinísticas: JSON válido; cita política [n]; não contém CPF/PII; recusa quando fora de escopo.
   • Ragas: faithfulness, context recall, context precision (diagnóstico de retrieval × geração).
   • DeepEval (G-Eval): "tom institucional e sem promessa de aprovação de crédito".

3. CI/CD (a cada PR de prompt/chunking/modelo):
   • Suíte rápida (60 casos) em ≤ 5 min; falha se faithfulness < 0,85 ou qualquer queda > 5% em relação à base.
   • Suíte completa à noite; relatório comparativo vs. versão em produção.

4. Auditoria trimestral: Giskard scan (injeção, vazamento, viés, alucinação) + red teaming humano;
   relatório arquivado para compliance (LGPD/regulatório); achados viram novos casos no dataset.

5. Produção: LLM-juiz em 5% do tráfego + feedback do usuário; traces ruins → fila de revisão → novos casos.

Resultado esperado: mudança de modelo ou prompt só entra com evidência; riscos conhecidos e documentados;
                    tempo de detecção de regressão: de semanas (reclamações) para minutos (CI).
```

## Erros comuns e armadilhas

- **Avaliar "no olho"** (alguns exemplos) e achar que é suficiente.
- **Dataset pequeno, sintético e fácil**: notas infladas e sem relação com o uso real.
- **Só métricas de LLM-juiz**, sem verificações determinísticas.
- **Trocar o juiz** (ou o prompt do juiz) entre versões e comparar as notas.
- **Confiar na média**: regressões em categorias específicas ficam escondidas.
- **Não repetir** execuções: tratar variação aleatória como melhora/piora.
- **Avaliar só o ponta a ponta**: impossível saber **onde** corrigir.
- **Medir só qualidade**, ignorando custo, latência e segurança.
- **Otimizar para a métrica** (overfitting ao conjunto de avaliação) sem conjunto de teste separado.
- **Não calibrar o juiz** com humanos.
- **Enviar dados sensíveis a SaaS de avaliação** sem avaliar privacidade.
- **Dataset estagnado**: nunca incorpora os casos de falha reais de produção.
- **Harness fora do CI**: roda quando alguém lembra, ou seja, quase nunca.

## 🧩 Quiz de Fixação

1. O que é um Eval Harness e por que testes tradicionais (`assert igual`) não bastam para LLMs?
2. Como as métricas faithfulness, context recall e context precision do Ragas ajudam a diagnosticar um RAG?
3. Quando você escolheria Ragas, DeepEval e Giskard, respectivamente?

**Respostas:**
1) É um framework que executa automaticamente casos de teste contra o sistema e produz métricas agregadas, de forma repetível, sendo essencial para CI/CD de LLMs. Testes tradicionais não bastam porque as saídas são variáveis (não comparáveis por igualdade), as qualidades são graduais (fidelidade, relevância, tom, segurança), a falha costuma ser semântica (resposta ruim sem exceção) e é preciso estatística sobre conjuntos de casos.
2) Faithfulness mede se a resposta é sustentada pelo contexto (detecta alucinação, problema de geração); context recall mede se o contexto recuperado contém o necessário (recall baixo indica problema de retrieval); context precision mede se os trechos relevantes estão bem posicionados no topo (precisão baixa indica ruído de ranking). Combinadas, indicam em qual etapa está o problema: por exemplo, recall alto com faithfulness baixa aponta falha na geração.
3) Ragas para diagnosticar e otimizar RAG (retrieval versus geração, com métricas sem referência e testes sintéticos); DeepEval para testes de regressão no estilo pytest integrados ao CI/CD, com muitas métricas e G-Eval customizável; Giskard para mapear riscos (injeção, vazamento, viés, alucinação) e gerar relatórios de auditoria e conformidade em domínios regulados.
