### Chunking Avançado — Propositional, Parent-Child e Indexação de Metadados

No tópico 2.1.1.1 vimos como **cortar** documentos. Aqui resolvemos um problema mais sutil: o chunk ideal para **buscar** não é o mesmo chunk ideal para **responder**. Buscar pede pedaços pequenos e focados; responder pede contexto amplo. As técnicas deste arquivo desacoplam as duas coisas e ainda adicionam **metadados** para filtrar, citar e ranquear melhor.

---

## O dilema: busca precisa vs. contexto suficiente

```
Chunk pequeno (1 frase):   vetor PRECISO ✔      mas o LLM recebe pouco contexto ✘
Chunk grande (1 seção):    contexto rico ✔       mas vetor DILUÍDO (vários assuntos) ✘
```

**Ideia central:** *indexe* unidades pequenas (boas para achar) e *entregue* ao LLM unidades maiores (boas para entender).

**Analogia:** é a ficha de biblioteca. A ficha (pequena, objetiva) serve para localizar; mas você não lê a ficha, vai à estante pegar o capítulo inteiro.

---

## 1. Propositional Chunking (chunking por proposições)

### O conceito

Uma **proposição** é uma afirmação atômica, **autocontida** e fatual: uma única ideia que faz sentido sozinha, sem pronomes ou referências externas. A técnica usa um LLM para **reescrever** o texto em uma lista dessas proposições e indexa cada uma como chunk.

```
Texto original:
  "A Acme foi fundada em 1998. Ela tem sede em Berlim e, desde 2015,
   também opera em São Paulo, onde emprega 300 pessoas."

Proposições:
  1. A Acme foi fundada em 1998.
  2. A Acme tem sede em Berlim.
  3. A Acme opera em São Paulo desde 2015.
  4. A Acme emprega 300 pessoas em São Paulo.
```

Note que "Ela" virou "A Acme" e "onde" virou "em São Paulo": cada linha é **compreensível isolada** (essa propriedade se chama *decontextualização*).

### Implementação

```python
PROMPT = """Decomponha o texto em proposições atômicas.
Regras: (1) cada proposição expressa um único fato; (2) é autocontida, substituindo
pronomes e referências pelos nomes completos; (3) não adicione informação nova.
Retorne uma proposição por linha.

Texto: {texto}"""

def proposicoes(trecho: str) -> list[str]:
    saida = chamar_llm(PROMPT.format(texto=trecho), temperature=0)
    return [l.strip("-• ").strip() for l in saida.splitlines() if l.strip()]

indice = []
for chunk in chunks_recursivos:                       # primeiro um chunking comum...
    for prop in proposicoes(chunk.texto):             # ...depois refinado em proposições
        indice.append({"texto": prop, "origem_id": chunk.id})   # guarda o vínculo com o chunk-pai
```

Detalhe crucial: cada proposição guarda `origem_id`, para que o sistema possa **devolver o trecho original** ao LLM (mesmo mecanismo do parent-child, abaixo).

| Vantagem | Desvantagem |
|---|---|
| Vetores muito precisos (uma ideia por vetor) | **Custo alto**: chamada de LLM para todo o corpus na indexação |
| Resolve pronomes e referências | Risco de o LLM alterar ou inventar fatos na reescrita |
| Excelente para perguntas factuais pontuais | Perde nuance, tom e argumentação encadeada |
| Reduz ruído no top-k | Índice muito maior (mais vetores) |

**Quando usar:** bases de conhecimento factuais (enciclopédias, FAQs, políticas, fichas técnicas) onde as perguntas pedem fatos específicos. **Evite** em textos argumentativos, jurídicos de interpretação fina ou narrativos.

> [!warning] Valide a fidelidade
> Amostre proposições geradas e compare com o texto-fonte. Uma reescrita que muda "pode" para "deve" corrompe o índice de forma silenciosa. Use temperature 0 e instrução explícita de não acrescentar informação.

## 2. Parent-Child Chunking (pai e filho)

### O conceito

Cada documento é dividido em **dois níveis**:

- **Filhos (child):** chunks pequenos (ex.: 200 tokens), usados na **busca vetorial**.
- **Pais (parent):** chunks grandes (ex.: 1.000 tokens ou a seção inteira), entregues ao **LLM**.

Cada filho aponta para o seu pai. Busca-se no filho; devolve-se o pai.

```
Seção 8 — Rescisão (PAI, 1.000 tokens)
  ├─ filho 8.a: "O aviso prévio é de 30 dias..."       ◄── vetor casa com a pergunta
  ├─ filho 8.b: "A multa equivale a 3 aluguéis..."
  └─ filho 8.c: "Fica dispensada a multa quando..."

Pergunta ─► busca nos FILHOS ─► acerta 8.c ─► sistema devolve o PAI inteiro (seção 8)
                                              (condição, exceção e contexto juntos)
```

Em contratos isso é decisivo: a **exceção** ("dispensada a multa quando...") raramente aparece no mesmo trecho curto que a regra; entregar a seção completa evita respostas parciais.

### Implementação com LangChain

```python
from langchain.retrievers import ParentDocumentRetriever
from langchain.storage import InMemoryStore
from langchain_text_splitters import RecursiveCharacterTextSplitter

pai_splitter   = RecursiveCharacterTextSplitter(chunk_size=1000, chunk_overlap=100)
filho_splitter = RecursiveCharacterTextSplitter(chunk_size=200,  chunk_overlap=20)

retriever = ParentDocumentRetriever(
    vectorstore=vector_store,          # guarda os FILHOS (vetores)
    docstore=InMemoryStore(),          # guarda os PAIS (texto completo), por id
    child_splitter=filho_splitter,
    parent_splitter=pai_splitter,
)
retriever.add_documents(documentos)
trechos = retriever.invoke("Qual o prazo de rescisão sem multa?")   # retorna PAIS
```

Linha a linha: o `vectorstore` indexa só os filhos; o `docstore` é um armazenamento chave-valor com os pais; no `invoke`, a busca ocorre nos filhos e o retriever substitui cada acerto pelo pai correspondente (sem duplicar pais repetidos).

Em produção, o `docstore` costuma ser Redis, PostgreSQL ou o próprio banco vetorial (guardando `parent_id` nos metadados do filho).

### Variações

| Variação | Como funciona |
|---|---|
| **Small-to-Big** (tópico 2.2.1.2) | Mesma ideia: recupera o pequeno, expande para o grande |
| **Sentence Window** | Indexa frases; ao recuperar, devolve a frase + N frases vizinhas (janela deslizante) |
| **Hierárquico (3 níveis)** | Documento → seção → parágrafo; "auto-merging": se vários filhos do mesmo pai forem recuperados, substitui-os pelo pai |
| **Document summary index** | Indexa resumos; devolve o documento completo |

### Escolhendo os tamanhos

| Parâmetro | Ponto de partida |
|---|---|
| Filho | 100 a 300 tokens |
| Pai | 800 a 2.000 tokens (ou limite natural: seção, página) |
| Razão pai:filho | 4× a 8× |

Cuidado com o **orçamento de contexto**: com top-k = 5 e pais de 1.500 tokens, você envia ~7.500 tokens ao LLM; limite o k ou deduplique pais.

## 3. Indexação de metadados

Metadados são **dados sobre o chunk** guardados ao lado do vetor. Eles permitem três coisas que o vetor sozinho não faz: **filtrar**, **citar** e **contextualizar**.

### Que metadados guardar

| Categoria | Exemplos | Uso |
|---|---|---|
| **Origem** | `documento`, `url`, `pagina`, `secao`, `titulo_caminho` | Citação ("Contrato Acme, cl. 8, p. 12") |
| **Temporal** | `data_publicacao`, `versao`, `vigente_ate` | Filtrar versões antigas, "o mais recente" |
| **Classificação** | `tipo_documento`, `departamento`, `idioma`, `confidencialidade` | Filtros e roteamento |
| **Estrutura** | `parent_id`, `posicao`, `tipo_bloco` (texto/tabela/código) | Parent-child, reconstrução da ordem |
| **Controle de acesso** | `tenant_id`, `grupos_permitidos` | **Segurança**: cada usuário só recupera o que pode ver |
| **Derivados** | `resumo`, `palavras_chave`, `perguntas_hipoteticas` | Melhorar recall |

### Filtrando na busca (pré-filtro)

```sql
-- pgvector: filtro por metadados + similaridade
SELECT conteudo, pagina,
       1 - (embedding <=> :consulta) AS similaridade
FROM trecho
WHERE tenant_id = :tenant                     -- isolamento entre clientes
  AND tipo_documento = 'contrato'
  AND vigente_ate >= CURRENT_DATE             -- só versões vigentes
ORDER BY embedding <=> :consulta
LIMIT 8;
```

```python
# Qdrant: mesmo conceito com filtro estruturado
from qdrant_client.models import Filter, FieldCondition, MatchValue
filtro = Filter(must=[
    FieldCondition(key="tenant_id", match=MatchValue(value="acme")),
    FieldCondition(key="idioma", match=MatchValue(value="pt")),
])
resultados = cliente.search("trechos", query_vector=vetor, query_filter=filtro, limit=8)
```

### Enriquecendo o texto embutido

Adicionar o **caminho de títulos** ao texto antes de gerar o embedding injeta contexto sem custo de LLM:

```python
texto_para_embedding = f"{doc} > {capitulo} > {secao}\n\n{conteudo}"
# "Manual do Motor > Capítulo 5 > Torques de aperto\n\nCabeçote: 85 Nm..."
```

### Perguntas hipotéticas (HyQE) e resumos

Para cada chunk, um LLM gera **3 perguntas que o chunk responde**; as perguntas são embutidas (e apontam para o chunk). Como a pergunta do usuário se parece mais com outra pergunta do que com um trecho de texto, o casamento melhora.

```
Chunk: "O aviso prévio para rescisão é de 30 dias."
Perguntas geradas: "Qual o prazo de aviso prévio?", "Quantos dias para rescindir?"
Índice: [vetor(pergunta1) → chunk], [vetor(pergunta2) → chunk]
```

### Esquema de metadados: boas práticas

- **Defina o esquema antes de indexar** e valide (Pydantic): metadados inconsistentes ("Pagina" vs "page") quebram filtros.
- **Indexe os campos filtráveis** no banco (índices em `tenant_id`, `data`) para manter o filtro rápido.
- **Metadados de segurança são obrigatórios** em sistemas multiusuário; filtre **no banco**, nunca no prompt.
- Guarde `versao_do_chunking` e `modelo_embedding` para saber quando reindexar.

## Comparativo das estratégias

| Estratégia | O que otimiza | Custo de indexação | Melhor para |
|---|---|---|---|
| **Propositional** | Precisão do vetor | Alto (LLM em tudo) | Bases factuais e perguntas pontuais |
| **Parent-Child** | Busca precisa + contexto amplo | Baixo | Documentos com condição/exceção (contratos, manuais) |
| **Sentence Window** | Contexto local da frase | Baixo | Textos narrativos e técnicos corridos |
| **Metadados** | Filtro, citação, segurança | Baixo a médio | **Todo** sistema de produção |

Combinação comum em produção: *chunking recursivo por estrutura → parent-child → metadados completos → (opcional) contextual retrieval*.

## Exemplo prático: base de políticas internas (RH)

```
Cenário: 800 políticas versionadas; perguntas como "quantos dias de férias tenho?".

1. Recursive por títulos → seções (PAIS, ~1.000 tokens).
2. Cada seção dividida em FILHOS de ~200 tokens.
3. Metadados: politica, versao, vigente_ate, departamento, grupos_permitidos.
4. Consulta: filtra grupos_permitidos do usuário e vigente_ate ≥ hoje (no banco),
   busca nos filhos, devolve pais deduplicados (máx. 4).
5. Citação automática: "Política de Férias v3, seção 2.1".

Ganho: respostas completas (regra + exceções), versões antigas nunca aparecem,
       cada usuário só vê o que tem permissão.
```

## Erros comuns e armadilhas

- **Indexar e devolver o mesmo chunk**: perde-se a vantagem do desacoplamento.
- **Pais grandes demais × k alto**: estoura o contexto do LLM.
- **Proposições sem validar fidelidade**: o LLM "melhora" o texto e distorce fatos.
- **Propositional em texto argumentativo**: destrói a lógica entre as ideias.
- **Esquecer o `parent_id`** (ou perder o docstore): filhos sem como voltar ao pai.
- **Metadados inconsistentes** entre documentos: filtros silenciosamente vazios.
- **Filtro de acesso no prompt** ("não mostre documentos de outros clientes"): vazamento garantido; filtre no banco.
- **Não reindexar** ao mudar o esquema de chunking ou de metadados.
- **Não registrar versões**: impossível saber qual configuração gerou qual índice.

## 🧩 Quiz de Fixação

1. Qual a ideia central do Parent-Child e por que ela é especialmente útil em contratos?
2. Qual o principal risco e o principal custo do Propositional Chunking?
3. Por que o controle de acesso deve ser feito via metadados no banco e não no prompt?

**Respostas:**
1) Indexar chunks pequenos (filhos) para uma busca precisa e devolver ao LLM o chunk maior (pai) com contexto completo. Em contratos, a regra e suas exceções ficam em frases diferentes; recuperar a seção inteira evita respostas parciais.
2) O risco é o LLM alterar ou inventar fatos ao reescrever as proposições, corrompendo o índice silenciosamente; o custo é uma chamada de LLM sobre todo o corpus na indexação, além de um índice muito maior.
3) Porque o filtro no banco impede que o conteúdo não autorizado sequer chegue ao LLM, enquanto uma instrução no prompt é frágil (pode ser contornada por prompt injection ou simples falha do modelo) e o conteúdo proibido já estaria no contexto, causando vazamento.
