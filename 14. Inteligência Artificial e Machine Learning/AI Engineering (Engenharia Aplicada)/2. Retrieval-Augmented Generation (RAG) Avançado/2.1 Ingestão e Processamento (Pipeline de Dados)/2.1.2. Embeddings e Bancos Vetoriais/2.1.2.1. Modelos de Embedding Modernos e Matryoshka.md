### Modelos de Embedding Modernos e Matryoshka

Um **embedding** transforma texto em um vetor de números de modo que textos com significado parecido fiquem **próximos** no espaço. É a base de toda busca semântica e de todo RAG. Escolher o modelo e a **dimensionalidade** certos determina qualidade, custo de armazenamento e velocidade da busca.

> [!note] Complemento
> O guia *Como LLMs Funcionam* explica como embeddings nascem dentro do modelo. Aqui o foco é **escolher e operar** modelos de embedding em produção.

---

## O que é um embedding, na prática

```
"gato"      ─► [ 0.21, -0.55,  0.08, ... ]   (ex.: 1024 números)
"felino"    ─► [ 0.19, -0.52,  0.11, ... ]   ◄─ vetor próximo
"imposto"   ─► [-0.70,  0.33,  0.61, ... ]   ◄─ vetor distante
```

A proximidade é medida por uma **métrica de similaridade**:

| Métrica | Fórmula (ideia) | Uso |
|---|---|---|
| **Cosseno** | Ângulo entre vetores (ignora o tamanho) | Padrão para texto |
| **Produto interno (dot)** | Cosseno × magnitudes | Equivalente ao cosseno se os vetores forem normalizados; mais rápido |
| **Euclidiana (L2)** | Distância em linha reta | Alguns modelos/índices |

Regra: **use a métrica recomendada pelo modelo** e normalize os vetores quando o modelo assim indicar.

**Analogia:** é um mapa em que cidades de significado parecido ficam vizinhas. A dimensionalidade é a quantidade de "eixos" do mapa: com poucos eixos, cidades diferentes se sobrepõem; com muitos, a distinção melhora, mas o mapa fica pesado.

## Como os modelos modernos evoluíram

| Geração | Característica | Exemplos |
|---|---|---|
| **Estática** | Um vetor por palavra, sem contexto | Word2Vec, GloVe |
| **Encoders contextuais** | Vetor da frase via transformers (BERT) | Sentence-BERT, MiniLM |
| **Embeddings treinados com contraste** | Aprendem "pergunta ↔ trecho relevante" em escala | E5, BGE, GTE |
| **Baseados em LLM** | Decodificadores grandes adaptados para embedding | modelos de 1B a 7B parâmetros no topo do MTEB |
| **Multivetor / multi-função** | Densos + esparsos + multivetor no mesmo modelo | **BGE-M3**, ColBERT |

## Critérios de escolha

| Critério | Pergunta a fazer |
|---|---|
| **Idioma** | O modelo foi treinado/avaliado em **português**? (modelos só em inglês degradam muito) |
| **Domínio** | Jurídico, código, médico? Há versão especializada ou será preciso fine-tuning (domínio 3.1.2)? |
| **Contexto máximo** | Quantos tokens por entrada (512? 8.192?). Entradas maiores são truncadas |
| **Dimensão** | Impacta armazenamento, memória e latência da busca |
| **Custo** | API (por milhão de tokens) vs. hospedar GPU/CPU |
| **Privacidade** | Dados sensíveis podem sair da empresa? Senão, modelo local |
| **Assimetria** | Consulta e documento usam prefixos diferentes? (E5 usa `query:` e `passage:`) |
| **Latência** | Tempo de gerar o embedding da pergunta online |

Duas regras inegociáveis:
1. **O mesmo modelo** (e versão) para indexar e consultar. Vetores de modelos diferentes vivem em espaços incompatíveis.
2. **Trocar o modelo exige reindexar tudo.**

```python
# Exemplo local com Sentence-Transformers (BGE-M3, multilíngue)
from sentence_transformers import SentenceTransformer

modelo = SentenceTransformer("BAAI/bge-m3")
docs = ["O aviso prévio é de 30 dias.", "A multa equivale a 3 aluguéis."]
vetores = modelo.encode(docs, normalize_embeddings=True)       # (2, 1024), normalizados
consulta = modelo.encode("Qual o prazo de aviso?", normalize_embeddings=True)
similaridades = vetores @ consulta                              # produto interno = cosseno (normalizado)
```

## Dimensionalidade: o trade-off

Cada dimensão é um número de ponto flutuante (4 bytes em float32). O custo escala linearmente:

| Dimensão | Tamanho de 1 vetor | 10 milhões de vetores |
|---|---|---|
| 384 | 1,5 KB | ~15 GB |
| 768 | 3 KB | ~30 GB |
| 1024 | 4 KB | ~40 GB |
| 3072 | 12 KB | ~120 GB |

(Sem contar o índice ANN, que acrescenta sobrecarga. Memória é o gargalo típico de bancos vetoriais.)

Mais dimensões = mais capacidade de representar nuances, mas também **mais memória, mais custo e busca mais lenta**; e os ganhos de qualidade têm retornos decrescentes. Antes de Matryoshka, reduzir dimensão exigia treinar outro modelo ou usar PCA (com perda).

## Matryoshka Representation Learning (MRL)

### A ideia

O nome vem das bonecas russas. Um modelo **Matryoshka** é treinado para que **os primeiros *k* números do vetor já formem um embedding útil**: o vetor de 3072 dimensões contém dentro de si um bom vetor de 1024, que contém um de 512, 256, 128...

```
Vetor completo (1024 dim):  [ ■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■ ]
                              ◄──── 256 ────►   mais fino, mais nuance
Primeiras 256 dims:           [ ■■■■■■■■ ]   ← já é um embedding bom, 4× menor
Primeiras 64 dims:            [ ■■ ]         ← grosseiro, mas utilizável
```

Isso é conseguido treinando com a função de perda aplicada em **vários comprimentos** simultaneamente (64, 128, 256...), forçando a informação mais importante a se concentrar nas primeiras dimensões.

**Analogia:** é como uma fotografia em formato progressivo: com 10% dos dados já se reconhece a imagem; mais dados acrescentam detalhe.

### Como usar (truncar e renormalizar)

```python
import numpy as np

def truncar(vetor: np.ndarray, dim: int) -> np.ndarray:
    v = vetor[:dim]                          # 1) pega só as primeiras 'dim' dimensões
    return v / np.linalg.norm(v)             # 2) RENORMALIZA (o corte altera a norma!)

v256 = truncar(v1024, 256)
```

Ou, em APIs/modelos que suportam diretamente:

```python
# OpenAI: o provedor já devolve o vetor reduzido e normalizado
resp = client.embeddings.create(model="text-embedding-3-large",
                                input="O aviso prévio é de 30 dias.",
                                dimensions=512)          # em vez de 3072
```

```python
# Sentence-Transformers: truncate_dim em modelos com suporte a Matryoshka
modelo = SentenceTransformer("nomic-ai/nomic-embed-text-v1.5", truncate_dim=256, trust_remote_code=True)
```

> [!warning] Só funciona bem em modelos treinados com Matryoshka
> Truncar um vetor de um modelo comum, não treinado para isso, destrói a qualidade. Confirme na documentação do modelo que há suporte a Matryoshka.

### O que se ganha

| Dimensão | Armazenamento | Qualidade de retrieval (ilustrativo) |
|---|---|---|
| 3072 (completo) | 100% | 100% |
| 1024 | 33% | ~98–99% |
| 512 | 17% | ~96–98% |
| 256 | 8% | ~93–96% |

(Valores ilustrativos: a perda real depende do modelo e dos dados. **Meça no seu corpus.**)

### Padrão avançado: busca em duas fases (funil)

Usar dimensões curtas para uma triagem rápida e as completas para refinar:

```
Consulta ──► vetor curto (256) ──► busca ANN em 10M vetores ──► top-200 candidatos
                                                                     │
                       vetor completo (1024) ◄───────────────────────┘ re-pontua só 200
                                  │
                                  ▼
                              top-10 final
```

Isso reduz memória e latência na etapa mais cara, preservando a precisão final. Combina muito bem com **quantização** (tópico 2.1.3.1): vetores binários ou int8 para a triagem, float completo para o rescoring.

## Outras técnicas de compactação

| Técnica | O que faz | Ganho típico | Observação |
|---|---|---|---|
| **Matryoshka** | Trunca dimensões | 2× a 12× | Requer modelo treinado para isso |
| **Quantização escalar (int8)** | Reduz de 4 bytes para 1 por dimensão | 4× | Perda pequena |
| **Quantização binária** | 1 bit por dimensão | 32× | Perda maior; use com rescoring |
| **Product Quantization (PQ)** | Comprime sub-vetores com codebooks | 8× a 64× | Detalhado em 2.1.3.1 |
| **PCA / redução linear** | Projeta em menos dimensões | variável | Perda maior que Matryoshka |

Matryoshka e quantização são **ortogonais**: podem ser combinadas (ex.: 256 dims em int8 = 64 bytes por vetor, ~64× menos que 4 KB).

## Boas práticas de operação

| Prática | Motivo |
|---|---|
| **Versionar** `modelo_embedding` e `dimensao` nos metadados | Saber o que reindexar quando mudar |
| **Usar prefixos de instrução** quando o modelo exigir (`query:`/`passage:`) | Omitir degrada o retrieval |
| **Gerar embeddings em lote** (batch) | Throughput muito maior |
| **Cachear embeddings** de textos repetidos | Economiza chamadas e custo |
| **Truncar textos ao limite do modelo conscientemente** | Evita truncamento silencioso |
| **Avaliar com o seu golden dataset** (Recall@k) | Benchmarks públicos não representam seu domínio |
| **Manter uma estratégia de migração** (índice novo em paralelo, troca atômica) | Mudança de modelo sem downtime |

## Exemplo prático: escolher o modelo e a dimensão para 5 milhões de trechos

```
Requisitos: português, dados sensíveis (sem API externa), orçamento de memória 12 GB.

1. Candidatos locais: BGE-M3 (1024), E5 multilingual (1024), GTE multilingual (768).
2. Avaliação: golden dataset de 100 perguntas → Recall@5 de cada candidato.
3. Vencedor: BGE-M3 (Recall@5 = 0,91).
4. Memória: 5M × 1024 × 4 B ≈ 20 GB > 12 GB ✘
5. Solução: quantização int8 (→ 5 GB) e/ou redução de dimensão se o modelo suportar MRL.
6. Re-medir Recall@5 após a compactação (queda aceita: ≤ 2 pontos).
```

## Erros comuns e armadilhas

- **Escolher pelo ranking do MTEB sem testar no seu idioma e domínio.**
- **Modelos diferentes** na indexação e na consulta.
- **Esquecer de renormalizar** após truncar um vetor Matryoshka.
- **Truncar vetores de um modelo que não é Matryoshka.**
- **Ignorar o limite de tokens** do modelo: textos longos são cortados sem aviso.
- **Esquecer prefixos** (`query:`/`passage:`) em modelos que os exigem.
- **Usar dimensão máxima por padrão**, pagando memória sem ganho mensurável.
- **Misturar métricas** (índice criado com L2 e consulta com cosseno).
- **Não planejar a reindexação** ao trocar de modelo.

## 🧩 Quiz de Fixação

1. Por que não se pode misturar vetores de modelos de embedding diferentes no mesmo índice?
2. O que é um embedding Matryoshka e por que é preciso renormalizar após truncá-lo?
3. Descreva a busca em duas fases usando dimensões curtas e completas.

**Respostas:**
1) Cada modelo define seu próprio espaço vetorial; as dimensões e as posições dos vetores não têm correspondência entre modelos, então distâncias entre vetores de modelos distintos não têm significado. A consulta e os documentos devem usar o mesmo modelo e versão, e trocar de modelo exige reindexar.
2) É um modelo treinado para que os primeiros k valores do vetor já formem um embedding útil (64, 128, 256...), permitindo reduzir dimensionalidade com pouca perda. Ao cortar o vetor, a norma muda, então é preciso renormalizar para que o cosseno/produto interno continuem consistentes.
3) Faz-se uma triagem rápida com vetores curtos (ex.: 256 dimensões) para obter centenas de candidatos e depois re-pontua apenas esses candidatos com os vetores completos para o ranking final, reduzindo memória e latência sem sacrificar muito a precisão.
