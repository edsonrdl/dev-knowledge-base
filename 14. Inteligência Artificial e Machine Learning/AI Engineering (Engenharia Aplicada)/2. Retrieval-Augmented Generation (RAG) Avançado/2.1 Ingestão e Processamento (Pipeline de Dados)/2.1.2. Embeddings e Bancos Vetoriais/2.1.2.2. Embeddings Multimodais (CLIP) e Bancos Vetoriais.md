### Embeddings Multimodais (CLIP) e Bancos Vetoriais

Até aqui os embeddings representavam **texto**. Mas empresas têm imagens, PDFs escaneados, diagramas, áudio e vídeo. **Embeddings multimodais** colocam conteúdos de tipos diferentes no **mesmo espaço vetorial**, permitindo buscar uma imagem por uma frase, ou achar um slide por uma foto. E, para guardar e consultar esses vetores, entram os **bancos vetoriais** (Vector Databases).

---

## 1. Embeddings multimodais

### A ideia

Um modelo multimodal tem **um codificador por modalidade** (texto, imagem...) treinados juntos para que **conteúdos que significam a mesma coisa caiam próximos**, independentemente do formato.

```
Foto de um cachorro correndo na praia ─► codificador de imagem ─┐
                                                                 ├─► mesmo espaço vetorial
Texto "um cachorro correndo na praia" ─► codificador de texto  ─┘   (vetores próximos)

Texto "contrato de aluguel"  ─► longe dos dois acima
```

**Analogia:** é um tradutor universal que converte tudo para um "idioma comum" de significado. Depois disso, comparar uma foto com uma frase é tão simples quanto comparar duas frases.

---

## 2. CLIP e a família contrastiva

**CLIP** (*Contrastive Language-Image Pre-training*, OpenAI, 2021) foi treinado com centenas de milhões de pares **imagem + legenda** da internet.

### Treinamento contrastivo

Em cada lote de N pares, o modelo aprende a **aproximar** cada imagem de **sua** legenda e **afastar** das outras N−1:

```
              legenda1  legenda2  legenda3
  imagem1   [   ALTO      baixo     baixo ]
  imagem2   [  baixo      ALTO      baixo ]    ◄ diagonal = pares corretos (maximizar)
  imagem3   [  baixo      baixo     ALTO  ]      resto = pares errados (minimizar)
```

### O que isso permite

| Capacidade | Exemplo |
|---|---|
| **Busca texto → imagem** | "planta baixa com duas suítes" retorna plantas |
| **Busca imagem → imagem** | Foto de um produto retorna itens similares |
| **Classificação zero-shot** | Compara a imagem com textos "foto de um gato", "foto de um cachorro" sem treinar classificador |
| **Busca imagem → texto** | Dada uma foto de peça, retorna o manual correspondente |

### Exemplo com CLIP (Hugging Face)

```python
from transformers import CLIPModel, CLIPProcessor
from PIL import Image
import torch

modelo = CLIPModel.from_pretrained("openai/clip-vit-base-patch32")
proc   = CLIPProcessor.from_pretrained("openai/clip-vit-base-patch32")

imagens = [Image.open(p) for p in ["sala.jpg", "cozinha.jpg", "quarto.jpg"]]
textos  = ["uma cozinha moderna", "um quarto com cama de casal"]

entrada = proc(text=textos, images=imagens, return_tensors="pt", padding=True)
with torch.no_grad():
    img_vec = modelo.get_image_features(pixel_values=entrada["pixel_values"])
    txt_vec = modelo.get_text_features(input_ids=entrada["input_ids"],
                                       attention_mask=entrada["attention_mask"])

img_vec = img_vec / img_vec.norm(dim=-1, keepdim=True)        # normaliza
txt_vec = txt_vec / txt_vec.norm(dim=-1, keepdim=True)
similaridade = txt_vec @ img_vec.T                             # (2 textos × 3 imagens), cosseno
```

Linha a linha: cada modalidade passa pelo seu codificador e produz vetores do **mesmo tamanho**; normalizados, o produto interno vira similaridade cosseno, que compara qualquer texto com qualquer imagem.

### Modelos multimodais modernos

| Modelo | Característica |
|---|---|
| **CLIP / OpenCLIP / SigLIP** | Imagem + texto; SigLIP usa uma perda mais eficiente em escala |
| **ColPali / ColQwen** | Trata a **página de documento como imagem** (multivetor), sem OCR: ótimo para PDFs com tabelas e figuras |
| **Jina CLIP, Nomic Embed Vision** | Imagem + texto com bom desempenho também em texto puro |
| **Cohere Embed (multimodal)**, **Voyage multimodal**, **Gemini embeddings** | Via API, imagem + texto no mesmo espaço |
| **ImageBind (Meta)** | Une até 6 modalidades (imagem, texto, áudio, profundidade, térmico, IMU) |
| **CLAP** | Áudio + texto |

> [!warning] Evolução rápida
> Modelos e APIs multimodais mudam com frequência. Confirme os modelos disponíveis e suas dimensões na documentação atual.

### Limitações

- **Texto dentro da imagem:** CLIP original lê pouco texto (OCR fraco); para documentos use ColPali/OCR + texto.
- **Detalhes finos e contagem** ("exatamente 3 maçãs") são difíceis.
- **Idiomas:** o CLIP original é predominantemente em inglês; existem variantes multilíngues.
- **Viés** herdado dos dados de treino.

## 3. RAG multimodal: três arquiteturas

| Abordagem | Como funciona | Quando usar |
|---|---|---|
| **A) Embedding multimodal único** | Imagens e textos no mesmo índice via CLIP/similar; a busca recupera ambos | Catálogos de produtos, busca visual, bibliotecas de imagens |
| **B) Converter tudo em texto** | Imagens → legendas/OCR por um LLM de visão; depois RAG de texto comum | Quando já existe pipeline de texto maduro; imagens com muito texto |
| **C) Página como imagem (ColPali)** | Cada página de PDF vira imagem e é indexada em multivetor | PDFs ricos visualmente (tabelas, gráficos, slides) |

```
Pergunta: "Qual o gráfico de vendas do 3º trimestre?"

A) busca vetorial ─► retorna a IMAGEM do gráfico ─► LLM de visão responde
B) busca ─► retorna a LEGENDA gerada ("Gráfico de barras: Q3 = R$ 4,2M...") ─► LLM de texto responde
C) busca ─► retorna a PÁGINA como imagem ─► LLM de visão lê o gráfico
```

Em todas, o gerador final pode ser um **LLM multimodal** (que lê imagens) ou um LLM de texto alimentado por descrições.

## 4. Bancos Vetoriais (Vector Databases)

### O papel

Um banco vetorial armazena vetores (mais seus metadados e o conteúdo) e responde rapidamente a: **"quais são os K vetores mais próximos deste vetor de consulta?"** (busca *k-NN*). Fazer isso comparando com **todos** os vetores (busca exata, "força bruta") é inviável em milhões de itens; por isso eles usam índices de **busca aproximada (ANN)**, tema do tópico 2.1.3.1.

```
                  ┌──────────────────────────────────────────┐
 Indexação        │  BANCO VETORIAL                          │
 vetor + metadados│  ├─ armazenamento (vetores, payload)     │
 ───────────────► │  ├─ índice ANN (HNSW, IVF, PQ...)        │
                  │  ├─ índice de metadados (filtros)        │
 Consulta         │  └─ (opcional) índice textual BM25       │
 vetor + filtro   │                                          │
 ───────────────► │  ─► top-K mais similares + metadados     │
                  └──────────────────────────────────────────┘
```

**Analogia:** é uma biblioteca em que os livros são organizados por **assunto no espaço** (não por ordem alfabética) e o bibliotecário sabe ir direto à prateleira certa em vez de varrer o acervo inteiro.

### Operações essenciais

| Operação | Descrição |
|---|---|
| **Upsert** | Inserir/atualizar vetor + payload por id |
| **Busca k-NN** | Retornar os K mais próximos por cosseno/dot/L2 |
| **Filtro por metadados** | Restringir candidatos (tenant, data, tipo) |
| **Busca híbrida** | Combinar vetor + palavra-chave (BM25) |
| **Delete/TTL** | Remover ou expirar dados |
| **Coleções/namespaces** | Separar domínios ou clientes |

```python
# Exemplo com Qdrant: criar coleção multimodal e buscar com filtro
from qdrant_client import QdrantClient
from qdrant_client.models import VectorParams, Distance, PointStruct, Filter, FieldCondition, MatchValue

q = QdrantClient(url="http://localhost:6333")
q.create_collection("midia", vectors_config=VectorParams(size=512, distance=Distance.COSINE))

q.upsert("midia", points=[
    PointStruct(id=1, vector=img_vec[0].tolist(),
                payload={"tipo": "imagem", "arquivo": "sala.jpg", "tenant": "acme"}),
])

achados = q.search(
    "midia",
    query_vector=txt_vec[0].tolist(),                       # texto buscando imagens
    query_filter=Filter(must=[FieldCondition(key="tenant", match=MatchValue(value="acme"))]),
    limit=5,
)
```

### Panorama de opções

| Categoria | Exemplos | Quando escolher |
|---|---|---|
| **Extensão de banco existente** | **pgvector** (PostgreSQL), Redis, MongoDB Atlas Vector Search, Elasticsearch/OpenSearch | Já se opera o banco; escala moderada; filtros SQL e transações |
| **Bancos vetoriais dedicados (open-source)** | **Qdrant, Milvus, Weaviate, Chroma** | Escala grande, recursos avançados, auto-hospedagem |
| **Serviços gerenciados** | **Pinecone**, versões cloud de Qdrant/Weaviate/Milvus | Sem operar infraestrutura |
| **Bibliotecas de índice** | **FAISS**, hnswlib, ScaNN, Annoy | Embutidas na aplicação; sem servidor, sem persistência/filtros nativos |

### Critérios de escolha

| Critério | Pergunta |
|---|---|
| **Escala** | Milhares, milhões ou bilhões de vetores? |
| **Filtros** | Os filtros por metadados são rápidos e combinam bem com ANN? |
| **Híbrido** | Há BM25/sparse vetorial nativo? |
| **Operação** | Time sabe operar? Preferência por gerenciado? |
| **Custo de memória** | Suporta quantização e armazenamento em disco? |
| **Multitenancy** | Isolamento por cliente (namespaces, partições)? |
| **Consistência/transações** | Precisa de ACID junto com dados relacionais? (pgvector) |
| **Multivetor** | Suporta vários vetores por item (ColPali/ColBERT)? |

Regra de bolso: **comece com o que já tem** (pgvector) até que a escala ou os requisitos obriguem a migrar; a complexidade de um banco novo só vale se houver um problema real.

## Exemplo prático: catálogo de peças industriais com busca visual

```
Problema: técnicos fotografam uma peça quebrada e querem achar o código no catálogo
          (12 mil peças, fotos + descrições + PDFs de manual).

Arquitetura:
 1. Cada peça: foto → embedding de imagem (SigLIP); descrição → embedding de texto
    (mesmo modelo multimodal, mesmo espaço).
 2. Qdrant: coleção "pecas" com 2 vetores nomeados por item (imagem, texto) + payload
    (codigo, linha_produto, fabricante).
 3. Consulta por foto: embedding da foto → busca em "imagem" → top-10 candidatos.
 4. Consulta por texto ("válvula de 2 polegadas"): busca no vetor de texto.
 5. Reranking com LLM de visão que compara a foto do usuário com as top-5 fotos
    e aponta a mais provável, explicando a decisão.
 6. Manuais em PDF: ColPali para localizar a página com o diagrama da peça.

Medição: golden dataset de 100 fotos reais de campo (ângulos e iluminação ruins!),
         Recall@5 e taxa de acerto no top-1.
```

## Erros comuns e armadilhas

- **Testar só com imagens limpas**; em produção, fotos desfocadas e mal iluminadas derrubam o recall.
- **Usar CLIP para ler texto em documentos** (OCR fraco): use OCR/ColPali.
- **Misturar modelos** para imagem e texto (precisam ser do **mesmo** modelo multimodal).
- **Esquecer de normalizar** os vetores antes de usar cosseno/dot.
- **Escolher banco vetorial por moda**, sem necessidade de escala; complexidade e custo desnecessários.
- **Ignorar a memória**: 10 milhões de vetores de 1024 dims ≈ 40 GB só de dados.
- **Filtros que anulam o índice ANN** (post-filtering em filtros muito seletivos), retornando poucos resultados; verifique como o banco combina filtro e ANN.
- **Não versionar o modelo** de embedding no payload.
- **Armazenar blobs de imagem no banco vetorial**; guarde o arquivo em storage de objetos e apenas a referência.

## 🧩 Quiz de Fixação

1. Como o treinamento contrastivo do CLIP permite buscar uma imagem por uma frase?
2. Compare as três arquiteturas de RAG multimodal (embedding único, converter em texto, página como imagem).
3. Por que bancos vetoriais usam índices aproximados em vez de comparar a consulta com todos os vetores?

**Respostas:**
1) O CLIP treina um codificador de imagem e um de texto com pares imagem-legenda, aproximando cada imagem da sua legenda e afastando das demais. Assim, imagens e textos de mesmo significado ficam próximos no mesmo espaço vetorial, e o vetor de uma frase pode ser comparado diretamente com vetores de imagens por similaridade cosseno.
2) Embedding único indexa imagens e textos no mesmo espaço e recupera ambos (bom para catálogos e busca visual); converter em texto usa legendas/OCR e reaproveita o RAG de texto (bom quando já existe pipeline de texto); página como imagem (ColPali) indexa cada página como imagem em multivetor, sem OCR, ótimo para PDFs com tabelas e gráficos.
3) Porque a busca exata (força bruta) cresce linearmente com o número de vetores e é inviável para milhões de itens com baixa latência. Índices ANN (HNSW, IVF, PQ) trocam uma pequena perda de precisão por ganhos enormes de velocidade e memória.
