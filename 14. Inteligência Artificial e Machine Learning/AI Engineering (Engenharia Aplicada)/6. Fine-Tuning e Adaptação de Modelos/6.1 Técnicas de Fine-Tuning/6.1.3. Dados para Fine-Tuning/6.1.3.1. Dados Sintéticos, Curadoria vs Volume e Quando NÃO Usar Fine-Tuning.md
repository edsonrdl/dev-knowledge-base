### Dados para Fine-Tuning — Dados Sintéticos, Data Curation vs. Data Volume e Quando NÃO Usar Fine-Tuning (vs. RAG)

As técnicas dos tópicos anteriores (LoRA, QLoRA, DPO...) são o **motor**; os **dados** são o **combustível**. Em fine-tuning, a qualidade do resultado depende muito mais do que você **alimenta** o modelo do que do algoritmo escolhido. Este arquivo cobre três pontos que definem o sucesso (ou o desperdício) de um projeto de fine-tuning: como **gerar dados sintéticos** com modelos de fronteira, por que **curadoria vence volume**, e, talvez o mais importante, **quando NÃO fazer fine-tuning**, preferindo RAG.

---

## Parte 1 — A regra que organiza tudo: Fine-Tuning ≠ Conhecimento

> **Fine-tuning ensina estilo, formato, tom e comportamento. RAG injeta conhecimento factual.** Usar fine-tuning para ensinar fatos novos tende a produzir **mais alucinação**, não menos.

```
                    O QUE VOCÊ QUER MUDAR NO SISTEMA?
                                  │
        ┌─────────────────────────┴──────────────────────────┐
   O QUE O MODELO SABE                                  COMO O MODELO SE COMPORTA
   (fatos, documentos, dados atuais)                    (estilo, formato, tom, tarefa, políticas)
        │                                                     │
        ▼                                                     ▼
      RAG  (domínio 2)                                  FINE-TUNING (domínio 6)
   fatos atualizáveis, citáveis,                        comportamento consistente,
   com fonte e controle de acesso                       prompts menores, modelos menores
```

**Analogia:** o fine-tuning é **treinar o profissional** (como ele fala, formata e decide); o RAG é **dar-lhe acesso à biblioteca** (o que consultar). Tentar "gravar a biblioteca na memória" do profissional (fine-tuning para fatos) é lento, caro, incompleto e o faz **inventar** quando a memória falha. Melhor treinar o jeito e deixar a biblioteca à mão.

---

## Parte 2 — Quando NÃO usar Fine-Tuning

### Por que fatos novos via fine-tuning dão errado

| Problema | Explicação |
|---|---|
| **Aprendizado fraco de fatos** | O modelo vê cada fato poucas vezes; aprende **o padrão da frase**, não um registro confiável do fato |
| **Mais alucinação** | Estudos mostram que ajustar com fatos que o modelo não conhecia **aumenta** a tendência de gerar informação inventada (o modelo aprende a "responder com confiança" mesmo sem saber) |
| **Sem citação de fonte** | Não dá para dizer **de onde** veio a informação (rastreabilidade) |
| **Desatualização** | Cada mudança de política/preço exige **retreinar**; RAG atualiza o índice em minutos |
| **Sem controle de acesso** | Conhecimento "assado" nos pesos não respeita permissões por usuário (qualquer um pode extrair) |
| **Sem remoção** | Direito de exclusão (LGPD) é inviável: não dá para "apagar" um dado dos pesos |
| **Esquecimento** | Aprender fatos novos pode degradar conhecimento prévio |
| **Custo recorrente** | Treino + avaliação + reimplantação a cada atualização |

### Árvore de decisão: RAG, prompt ou fine-tuning?

```
O problema é FALTA DE CONHECIMENTO (fatos, documentos, dados que mudam)?
 └─ SIM ──► RAG (+ busca híbrida, reranking...)              ← NÃO faça fine-tuning para isso

O problema é COMPORTAMENTO?
 │
 ├─ Um prompt melhor + poucos exemplos (few-shot, 1.2.1.1) resolvem?  ─► SIM ► fique no prompt
 ├─ Saída estruturada com schema resolve o formato? (1.2.2.1)         ─► SIM ► use structured outputs
 ├─ Um modelo MAIOR/mais novo resolve?                                ─► SIM ► teste antes de treinar
 │
 └─ Ainda não, e há razão forte para fine-tuning:
      • estilo/tom/formato CONSISTENTES em milhares de chamadas
      • prompt gigante (custo/latência) que poderia virar comportamento treinado
      • tarefa estreita onde um modelo PEQUENO ajustado supera um grande no custo
      • comportamento difícil de descrever em prompt (julgamento sutil, formato complexo)
      • privacidade/soberania: rodar localmente um modelo pequeno especializado
      ─► FINE-TUNING (e continue usando RAG para os fatos)
```

### Cenários: o que usar

| Necessidade | Solução | Por quê |
|---|---|---|
| "O assistente deve responder com base nas políticas atuais da empresa" | **RAG** | Fatos que mudam, com citação |
| "As respostas devem sempre seguir nosso formato e tom de voz" | **Fine-tuning** (ou prompt + exemplos) | Comportamento |
| "O modelo deve conhecer os 20 mil produtos do catálogo" | **RAG** (ou busca estruturada) | Conhecimento factual volumoso e mutável |
| "Classificar tickets em 40 categorias internas, com custo baixo e latência mínima" | **Fine-tuning de modelo pequeno** | Tarefa estreita, alto volume |
| "Extrair campos de documentos num formato JSON complexo" | Structured outputs; fine-tuning se a precisão faltar | Formato/tarefa |
| "Responder sobre legislação atualizada toda semana" | **RAG** | Atualização contínua |
| "Falar o jargão jurídico/médico corretamente" | **Fine-tuning leve + RAG** | Vocabulário e estilo + fatos |
| "Dados sigilosos que não podem sair: rodar modelo local especializado" | **Fine-tuning de modelo aberto + RAG local** | Soberania |
| "Queremos que o modelo 'saiba' o histórico de cada cliente" | **RAG/memória** (4.2.2.1) | Dados por usuário; acesso e exclusão |
| "Reduzir o custo: o prompt tem 3.000 tokens fixos" | **Prompt caching** primeiro (1.1.1.1); fine-tuning se necessário | Alternativa mais barata |

### Fine-tuning e RAG juntos

Não são opostos: em sistemas maduros, **combinam-se**. O fine-tuning ensina o modelo a **usar bem o contexto recuperado** (citar fontes, dizer "não encontrei", seguir o formato), e o RAG fornece os fatos.

```
Pergunta ──► RAG recupera trechos (fatos atuais) ──► MODELO AJUSTADO (estilo/formato/uso do contexto)
                                                          │
                                                          ▼
                                       resposta fundamentada, no tom da empresa, com citações
```

Exemplo clássico: **RAFT** (*Retrieval-Augmented Fine-Tuning*): treinar o modelo com exemplos que incluem **documentos relevantes e distratores**, ensinando-o a **ignorar ruído** e citar a fonte certa.

### Checklist: "realmente preciso de fine-tuning?"

```
[ ] Medi o modelo base com prompt otimizado (few-shot, instruções claras)?
[ ] Testei um modelo maior/mais recente?
[ ] RAG está bem feito (chunking, híbrida, reranking) e o problema persiste?
[ ] O problema é de COMPORTAMENTO (não de conhecimento)?
[ ] Tenho um conjunto de avaliação para provar o ganho?
[ ] Tenho dados de QUALIDADE (ou capacidade de gerá-los e validá-los)?
[ ] O ganho justifica o custo de treinar, versionar, servir e retreinar?
```

## Parte 3 — Data Curation > Data Volume

### O princípio

> **A qualidade dos dados supera a quantidade.** Poucos milhares de exemplos **excelentes** frequentemente superam centenas de milhares de exemplos medianos.

**Evidências e referências conhecidas:**
- **LIMA** (*Less Is More for Alignment*, 2023): um modelo ajustado com apenas **~1.000 exemplos cuidadosamente curados** alcançou resultados competitivos, sustentando a "hipótese da superficialidade do alinhamento": o conhecimento vem do pré-treino; o fine-tuning ensina principalmente **estilo e formato**.
- Trabalhos sobre **seleção de dados** (ex.: filtros por qualidade, diversidade e dificuldade) mostram ganhos ao usar **subconjuntos menores e melhores**.
- Na fase de **pré-treino**, a curadoria (filtros de qualidade, deduplicação) é uma das maiores alavancas de desempenho (ex.: FineWeb, Dolma).

```
Dados:       100.000 exemplos ruidosos, duplicados, inconsistentes
              ──► o modelo aprende ruído, vícios e contradições

Dados:         2.000 exemplos revisados, diversos, consistentes
              ──► o modelo aprende o comportamento desejado, com menos custo e menos overfitting
```

**Analogia:** é a diferença entre estudar com **1 livro excelente e revisado** e com **100 apostilas cheias de erros**: mais material não compensa material ruim.

### Dimensões da qualidade de um dado de fine-tuning

| Dimensão | Pergunta |
|---|---|
| **Correção** | A resposta está certa (fatos, código, cálculo)? |
| **Consistência** | Exemplos seguem o mesmo formato, tom e critérios? (contradições confundem) |
| **Diversidade** | Cobre os tipos de tarefa, tamanhos, estilos e casos de borda reais? |
| **Representatividade** | Reflete a distribuição **real** de uso (inclusive entradas "sujas")? |
| **Complexidade adequada** | Há casos fáceis e difíceis (dificuldade graduada)? |
| **Adequação ao comportamento** | A resposta modela **exatamente** o que você quer (tom, estrutura, recusas)? |
| **Limpeza** | Sem lixo, duplicatas, dados truncados, rótulos de ferramenta ("As an AI language model...") |
| **Segurança e privacidade** | Sem dados pessoais, segredos, conteúdo tóxico ou protegido |

### O pipeline de curadoria

```
DADOS BRUTOS (logs, documentos, conversas, sintéticos)
     │
     ▼ 1. COLETA e conversão ao formato (prompt → resposta; mensagens de chat)
     ▼ 2. LIMPEZA: HTML/ruído, codificação, truncamentos, idioma errado
     ▼ 3. ANONIMIZAÇÃO / remoção de PII e segredos
     ▼ 4. DEDUPLICAÇÃO (exata e aproximada — MinHash/LSH, embeddings)
     ▼ 5. FILTROS DE QUALIDADE (heurísticas + classificadores + LLM-juiz)
     ▼ 6. SELEÇÃO por diversidade e dificuldade (clusterização, amostragem balanceada)
     ▼ 7. REVISÃO HUMANA por amostragem (e das categorias críticas)
     ▼ 8. DIVISÃO treino / validação / teste (POR GRUPO — documento, cliente, conversa)
     ▼ 9. VERSIONAMENTO e documentação (data card)
DATASET FINAL (pequeno, limpo, diverso, versionado)
```

### Técnicas de cada etapa

| Etapa | Técnicas e ferramentas |
|---|---|
| **Deduplicação** | Hash exato; **MinHash + LSH** (quase-duplicatas); embeddings + similaridade (SemDeDup); **Datatrove** |
| **Filtros de qualidade** | Heurísticas (tamanho, razão de símbolos, repetição de n-gramas, idioma), **perplexidade** de um modelo de referência, **classificadores** de qualidade (ex.: educacional), **LLM-juiz** com rubrica (nota 1–5) |
| **Diversidade** | Embeddings + *clustering* (k-means) e amostragem por cluster; cobertura de intenções/tópicos |
| **Dificuldade** | Perda do modelo base por exemplo; "mantenha exemplos que o modelo base erra" (aprendizado onde há ganho) |
| **Remoção de PII** | Presidio (Microsoft), regex + NER; mascaramento de e-mails, CPFs, nomes |
| **Descontaminação** | Remover exemplos que **vazam o conjunto de teste** (n-gram overlap) |
| **Pipelines em escala** | **Datatrove** (Hugging Face), **Dolma** (Allen AI), **NeMo Curator** (NVIDIA), `datasketch`, `text-dedup` |
| **Inspeção** | Amostragem manual, **Argilla**, Label Studio, Lilac, notebooks de exploração |

```python
# Exemplo mínimo: filtro por LLM-juiz + deduplicação aproximada (esboço)
from datasketch import MinHash, MinHashLSH

def minhash(texto: str, num_perm=128) -> MinHash:
    m = MinHash(num_perm=num_perm)
    for palavra in set(texto.lower().split()):
        m.update(palavra.encode("utf8"))
    return m

lsh = MinHashLSH(threshold=0.85, num_perm=128)            # quase-duplicatas (≥ 85% de similaridade)
curados = []
for i, ex in enumerate(exemplos):
    mh = minhash(ex["prompt"] + " " + ex["resposta"])
    if lsh.query(mh):                                     # já existe algo muito parecido
        continue
    nota = juiz_llm(RUBRICA, ex)                          # 1–5 em correção, clareza, aderência ao formato
    if nota < 4:
        continue
    lsh.insert(f"ex{i}", mh)
    curados.append(ex)
```

### Quanto de dado é necessário

| Objetivo | Ordem de grandeza (ilustrativa) |
|---|---|
| **Estilo/formato/tom** com LoRA | **100 a 2.000** exemplos de alta qualidade |
| **Tarefa específica** (classificação, extração) | **500 a 10.000** |
| **Seguir instruções gerais** (SFT amplo) | 1.000 (LIMA) a centenas de milhares (conjuntos amplos) |
| **Preferências** (DPO) | **1.000 a 50.000** pares |
| **Adaptação profunda de domínio** (continued pre-training) | Bilhões de tokens |

Regra prática: **comece pequeno** (algumas centenas de exemplos excelentes), meça, e **aumente apenas se** a curva de aprendizado ainda subir e os erros apontarem lacunas de cobertura; dobrar dados ruins quase nunca ajuda.

```
Curva típica:   qualidade
                  ▲        ●─────●────●    ← platô: mais dados NÃO melhoram
                  │     ●
                  │  ●
                  │●
                  └────────────────────────► nº de exemplos
              Descubra onde está o seu platô com experimentos de 250 / 500 / 1.000 / 2.000...
```

## Parte 4 — Dados sintéticos

### A ideia

Usar **modelos de fronteira** (mais capazes e caros) para **gerar datasets** que treinam modelos **menores** (mais baratos e rápidos): uma forma de **destilação**. Em vez de anotar manualmente milhares de exemplos, você gera, filtra e revisa.

```
 Modelo de FRONTEIRA (professor)  ──gera──►  (instrução, resposta) / (prompt, chosen, rejected)
                                                    │ curadoria (filtros + revisão)
                                                    ▼
                                      fine-tuning de um modelo PEQUENO (aluno)
```

### Padrões de geração

| Padrão | Como funciona | Uso |
|---|---|---|
| **Destilação de respostas** | O professor responde prompts reais/sintéticos; o aluno aprende a imitar | Transferir capacidade a modelos menores |
| **Self-Instruct / Evol-Instruct** | O modelo **gera novas instruções** a partir de sementes e as **torna mais complexas** iterativamente | Ampliar diversidade e dificuldade |
| **Geração a partir de documentos** | O LLM lê um documento e gera perguntas/respostas sobre ele | Dados de domínio e de **RAG** (3.1.2.1) |
| **Persona/cenário** | Gera dados variando personas, tons e situações (ex.: "cliente irritado", "idoso") | Cobertura e robustez |
| **Reescrita/augmentation** | Parafraseia, traduz, altera o formato de exemplos reais | Aumentar dados escassos |
| **Raciocínio (CoT) sintético** | O professor gera **passos de raciocínio** + resposta; filtra pelos corretos (rejection sampling) | Ensinar raciocínio a modelos menores |
| **Pares de preferência sintéticos** | Gera várias respostas e as classifica (LLM-juiz ou verificador) | DPO/RLAIF (6.1.2.1) |
| **Dados "verificados"** | Código com testes, matemática com resposta conhecida: mantém só o que **passa** | Qualidade garantida objetivamente |
| **Simulação de conversas** | Dois LLMs interpretam usuário e assistente | Diálogos multi-turno |

### Exemplo: gerar e filtrar dados de suporte

```python
from pydantic import BaseModel

class Exemplo(BaseModel):
    pergunta_cliente: str
    resposta_ideal: str

PROMPT_GERADOR = """Você cria dados de treinamento para um assistente de suporte da empresa X.
Com base no trecho da política abaixo, escreva {n} interações DIFERENTES entre cliente e atendente.
Varie: tom do cliente (calmo, irritado, confuso), tamanho da pergunta e nível de detalhe.
A resposta ideal deve: começar com saudação curta, trazer a solução em passos numerados,
citar a política e terminar com uma pergunta de confirmação. NÃO invente informação que não esteja no trecho.

Trecho da política: {trecho}"""

def gerar(trechos, n=4):
    brutos = []
    for t in trechos:
        lote = llm_fronteira_estruturado(PROMPT_GERADOR.format(n=n, trecho=t.texto), list[Exemplo], temperature=0.9)
        brutos += [{"trecho_id": t.id, **e.model_dump()} for e in lote]
    return brutos

def filtrar(brutos):
    bons = []
    for ex in brutos:
        # 1) checagens determinísticas: formato exigido (passos numerados, citação, pergunta final)
        if not aderente_ao_formato(ex["resposta_ideal"]):
            continue
        # 2) fundamentação: a resposta contradiz o trecho-fonte? (juiz independente, com o trecho)
        if not fundamentado(ex["resposta_ideal"], trecho_por_id(ex["trecho_id"])):
            continue
        # 3) dedup e diversidade
        bons.append(ex)
    return dedup_semantico(bons)
```

### Riscos e cuidados dos dados sintéticos

| Risco | Descrição | Mitigação |
|---|---|---|
| **Alucinações no dado** | O gerador inventa fatos; o aluno **aprende o erro** | Gerar **a partir de fontes** (documentos), verificar fundamentação, verificadores objetivos |
| **Colapso de modelo** (*model collapse*) | Treinar repetidamente em dados gerados por modelos reduz diversidade e piora a qualidade ao longo de gerações | **Misturar dados reais**, manter dados humanos, diversificar geradores, filtrar |
| **Perda de diversidade / homogeneidade** | O gerador produz respostas parecidas (estilo "de IA") | Personas, temperaturas, múltiplos modelos, *seeds* variadas, dedup semântica |
| **Herança de vieses** | O aluno herda os vieses do professor | Auditar; misturar fontes; revisão humana |
| **Distribuição irreal** | Perguntas sintéticas "limpas" ≠ entradas reais bagunçadas | Misturar dados reais, simular ruído (erros, gírias, abreviações) |
| **Termos de uso** | Alguns provedores **proíbem usar saídas para treinar modelos concorrentes** | **Ler os termos** e a licença do modelo professor |
| **Contaminação de avaliação** | O dado sintético "vaza" o conjunto de teste | Descontaminar; avaliar em dados reais independentes |
| **Falsa sensação de qualidade** | O LLM-juiz aprova o que o próprio gerador faz | Juiz independente + amostragem humana |
| **Direitos autorais e privacidade** | Documentos-fonte com dados pessoais ou protegidos | Anonimizar; verificar direitos |
| **Custo oculto** | Muitas gerações + filtros custam tokens | Estimar (gerar 3× o necessário e filtrar) |

### Proporção real × sintético

| Cenário | Recomendação |
|---|---|
| **Existem dados reais de qualidade** | Priorize-os; use sintéticos para **cobrir lacunas** (casos raros, recusas, variações) |
| **Sem dados reais (cold start)** | Comece sintético + **validação humana** forte; substitua por dados reais conforme o produto roda |
| **Avaliação (golden dataset)** | **Sempre** dados reais (ou validados por humanos), nunca só sintéticos |

## Parte 5 — Formatos, divisão e documentação

### Formatos comuns

```json
// SFT em formato de chat (o mais usado hoje) — respeite o template do modelo base
{"messages": [
  {"role": "system",    "content": "Você é o assistente de suporte da empresa X."},
  {"role": "user",      "content": "Meu pedido chegou quebrado, o que faço?"},
  {"role": "assistant", "content": "Sinto muito pelo transtorno! Veja como resolver: 1) ... 2) ... 3) ..."}
]}

// Preferências (DPO/ORPO/SimPO)
{"prompt": "Explique inflação para uma criança.", "chosen": "...", "rejected": "..."}
```

| Cuidado | Detalhe |
|---|---|
| **Template de chat do modelo** | Usar exatamente o formato de tokens especiais do modelo base (`apply_chat_template`); erro aqui degrada silenciosamente |
| **Perda só na resposta** | Treinar apenas nos tokens do assistente (mascarar o prompt) costuma ser melhor |
| **Prompts de sistema consistentes** | O mesmo usado em produção |
| **Comprimento** | Respeitar o contexto do modelo; evitar truncar a resposta ao meio |
| **Inclusão de "não sei"/recusas** | Exemplos de quando **não** responder (calibração) |

### Divisão treino / validação / teste

| Regra | Motivo |
|---|---|
| **Dividir por grupo** (documento, cliente, conversa), não por exemplo | Evita vazamento (exemplos do mesmo documento no treino e no teste) |
| **Teste congelado e real** | Medir o ganho de verdade |
| **Validação durante o treino** | Detectar overfitting (a perda de validação sobe) |
| **Estratificar** por tipo de tarefa | Representatividade |

### Documentar o dataset (*data card*)

Registre: **origem**, método de geração/filtragem, **período**, idioma, **proporção real × sintético**, **licenças**, tratamento de PII, **viéses conhecidos**, lacunas, versão e responsável. Isso permite auditoria, reprodutibilidade e atendimento a exigências de conformidade.

## Parte 6 — Avaliar se o fine-tuning valeu a pena

```
1. LINHA DE BASE (antes de treinar)
   modelo base + melhor prompt (+ RAG) no golden dataset  →  métricas M0

2. TREINO com o dataset curado  →  modelo ajustado

3. AVALIAÇÃO COMPARATIVA
   ├─ ganho no objetivo:   M1 vs M0 (formato, tom, acerto da tarefa)
   ├─ REGRESSÃO geral:     o modelo piorou em tarefas fora do domínio? (esquecimento)
   ├─ ALUCINAÇÃO:          taxa de afirmações sem suporte nos documentos (faithfulness)
   ├─ ROBUSTEZ:            entradas ruidosas, ataques simples, casos de borda
   ├─ CUSTO/LATÊNCIA:      prompt menor? modelo menor? economia real?
   └─ MEMORIZAÇÃO:         o modelo vaza dados do treino? (teste de extração)

4. DECISÃO: o ganho justifica o custo de treinar, servir e MANTER (retreinar)?
```

Ganhos tipicamente medidos: **aderência ao formato** (determinística), **taxa de acerto** da tarefa, **win-rate** contra a linha de base, **redução de tokens de prompt**, **custo por requisição** ao trocar um modelo grande por um pequeno ajustado.

## Exemplo prático: especializar um modelo pequeno para triagem de tickets

```
Contexto: 200 mil tickets/mês; o modelo de fronteira classifica bem (94%) mas custa caro e demora;
          prompt com 40 categorias e exemplos = 2.500 tokens.

Passo 0 — Decisão: é COMPORTAMENTO (classificar nas SUAS categorias, em JSON), não conhecimento
          factual novo → fine-tuning de um modelo pequeno faz sentido. (Os fatos de resposta ao cliente
          continuam no RAG; este modelo só TRIA.)

Passo 1 — Dados:
   • 6.000 tickets reais anonimizados, rotulados por analistas (rotulagem dupla; discordâncias resolvidas).
   • +2.000 sintéticos para categorias raras (gerados por modelo de fronteira a partir de descrições e
     exemplos reais; verificados por amostragem humana; marcados como "sintético").
   • Curadoria: dedup semântica, remoção de PII, balanceamento (limite por categoria), casos ambíguos
     rotulados com a regra de desempate, exemplos de "fora de escopo".
   • Divisão por cliente (nenhum cliente aparece em treino e teste).

Passo 2 — Treino: modelo aberto de 3B com LoRA (r=16), 2 épocas, perda só na saída JSON.

Passo 3 — Avaliação (conjunto real congelado, 1.500 tickets):
   • Acurácia: 91,5% (vs 94% do modelo de fronteira; vs 78% do mesmo modelo de 3B só com prompt).
   • Custo por ticket: −93%; latência: 1.100 ms → 90 ms; prompt: 2.500 → 120 tokens.
   • Regressão geral: irrelevante (modelo especializado de uso único); formato JSON válido: 99,9%.
   • Decisão: adotar; tickets com baixa confiança escalados ao modelo de fronteira (roteamento, 7.1.3.1).

Passo 4 — Operação: monitorar deriva (novas categorias), amostragem humana semanal, retreino trimestral
          com os erros corrigidos; dataset e modelo versionados (data card).
```

## Erros comuns e armadilhas

- **Fine-tuning para injetar fatos/documentos**: gera alucinação; use RAG.
- **Treinar sem linha de base**: não se sabe se o modelo ajustado é melhor que prompt + RAG.
- **Priorizar volume**: milhares de exemplos ruidosos, duplicados e contraditórios.
- **Dados sintéticos sem verificação**: o aluno aprende alucinações do professor.
- **Colapso por reciclagem**: treinar modelos em saídas de modelos, sem dados reais.
- **Ignorar os termos de uso** do modelo que gera os dados sintéticos.
- **Sem deduplicação**: memorização e overfitting; vazamento entre treino e teste.
- **Dividir treino/teste por exemplo** (vazamento por documento/cliente).
- **PII e segredos no dataset**: o modelo pode memorizá-los e revelá-los.
- **Template de chat errado** ou perda calculada também nos tokens do prompt.
- **Conjunto de avaliação sintético ou contaminado**: ganhos ilusórios.
- **Não incluir exemplos de recusa/"não sei"**: modelo que sempre responde, inventando.
- **Não versionar nem documentar** o dataset (data card).
- **Esquecer a manutenção**: o comportamento muda e o modelo precisa de retreino.

## 🧩 Quiz de Fixação

1. Por que usar fine-tuning para ensinar fatos novos tende a aumentar a alucinação e o que usar no lugar?
2. O que significa "curadoria supera volume" e cite quatro etapas de um pipeline de curadoria.
3. Cite três riscos dos dados sintéticos e uma mitigação para cada.

**Respostas:**
1) Porque o modelo vê cada fato poucas vezes e aprende o padrão da frase em vez de um registro confiável; ao ser ajustado com fatos que não conhecia, aprende a responder com confiança mesmo sem saber, aumentando a alucinação, além de não permitir citação de fonte, atualização fácil, controle de acesso ou exclusão (LGPD). O adequado é RAG para o conhecimento factual, usando fine-tuning para estilo, formato, tom e comportamento (e, se for o caso, para usar melhor o contexto recuperado).
2) Significa que poucos milhares de exemplos corretos, consistentes, diversos e representativos costumam superar centenas de milhares de exemplos ruidosos (como no LIMA, com ~1.000 exemplos curados). Etapas: limpeza; anonimização/remoção de PII; deduplicação (exata e MinHash/embeddings); filtros de qualidade (heurísticas, classificadores, LLM-juiz); seleção por diversidade e dificuldade; revisão humana por amostragem; divisão treino/validação/teste por grupo; versionamento e documentação (data card).
3) Por exemplo: alucinações no dado, mitigadas gerando a partir de documentos-fonte e verificando a fundamentação ou usando verificadores objetivos; colapso de modelo e perda de diversidade, mitigados misturando dados reais, diversificando geradores/personas e fazendo dedup semântica; violação de termos de uso e vieses herdados do professor, mitigados lendo os termos/licenças e auditando e misturando fontes; distribuição irreal, mitigada com dados reais e simulação de ruído. Para avaliação, usar sempre dados reais independentes.
