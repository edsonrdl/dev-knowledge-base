### Computer Use, Browser Use (Playwright) e Voice Agents (Speech-to-Speech)

Function calling (5.1.1.1) funciona quando existe uma **API estruturada** para chamar. Mas boa parte do software do mundo real **não tem API**: sistemas legados, sites de terceiros, aplicações desktop, formulários, portais de governo. Para esses casos, os agentes passam a **operar a interface como uma pessoa**: olhando a tela e usando mouse e teclado (**Computer Use**), ou navegando em páginas web com um navegador automatizado (**Browser Use**). E há uma terceira fronteira: agentes que **conversam por voz** em tempo real (**Voice Agents**), com a latência de uma ligação telefônica.

> [!warning] Fronteira em rápida evolução
> Computer use, browser agents e APIs de voz em tempo real estão entre as áreas que **mais mudam**: novos modelos, parâmetros, versões *beta* e limitações são atualizados com frequência. Os exemplos abaixo mostram os **conceitos e arquiteturas**; consulte a documentação atual (inclusive os avisos de segurança de cada provedor) antes de implementar. Estas capacidades são também as de **maior risco** do domínio 5: leia a seção de segurança com atenção.

## Visão geral: três formas de o agente interagir com o mundo

```
   Há API estruturada?  ──► SIM ──► FUNCTION CALLING / MCP           (5.1.1.1, 4.1.2.1)  melhor opção
          │
          NÃO
          │
          ├─ é uma página web? ──► BROWSER USE   (navegador automatizado: DOM + screenshots)
          ├─ é qualquer app/tela? ─► COMPUTER USE (screenshot + mouse/teclado, a "interface humana")
          └─ a interação é conversa falada? ─► VOICE AGENT (áudio ↔ áudio em tempo real)
```

| Forma | O que o agente "vê" | O que o agente "faz" | Quando usar |
|---|---|---|---|
| **Function calling / MCP** | Definições de ferramentas | Chama APIs | **Sempre que houver API** (mais rápido, barato e seguro) |
| **Browser Use** | Página web (DOM, texto, árvore de acessibilidade, screenshots) | Clica, digita, navega, extrai | Automação web sem API |
| **Computer Use** | Screenshots da tela inteira | Mover/clicar mouse, digitar, atalhos, rolar | Aplicativos desktop, sistemas legados, qualquer GUI |
| **Voice Agent** | Áudio (fala) | Fala e executa ferramentas | Atendimento telefônico, assistentes por voz |

**Regra de ouro:** **API primeiro**. Operar interfaces é mais lento, mais caro, mais frágil e mais arriscado; é o recurso de **último caso** quando não há integração programática.

## Parte 1 — Computer Use

### O que é

**Computer Use** é a capacidade de um modelo **controlar uma interface gráfica** como um usuário: recebe **capturas de tela**, decide uma **ação** (mover o mouse, clicar, digitar, rolar, pressionar teclas) e recebe uma nova captura com o resultado. A Anthropic introduziu essa capacidade para o Claude em 2024 (em *beta*), e outros provedores têm recursos equivalentes (agentes de uso de computador/operador). É uma forma de **automação RPA baseada em IA**, sem depender de APIs estruturadas.

**Analogia:** é **pedir a alguém que opere o computador por você via videochamada**: ele só vê a sua tela, diz "clique ali, digite isto" e você executa. O modelo faz o papel de quem vê e comanda; o seu **ambiente** executa as ações.

### O laço: ver → decidir → agir → ver

```
   ┌────────────────────────────────────────────────────────────────────┐
   │ 1. Captura de tela  ──►  MODELO (visão + raciocínio)               │
   │                              │                                     │
   │ 2. ◄─── ação pedida: { "action": "left_click", "coordinate": [412, 308] }
   │                                                                    │
   │ 3. SEU AMBIENTE executa a ação (mouse/teclado virtual)             │
   │                                                                    │
   │ 4. Nova captura de tela ──► volta ao MODELO ... até concluir       │
   └────────────────────────────────────────────────────────────────────┘
```

É um laço **ReAct** (4.1.1.1) em que a "ferramenta" é a **interface gráfica**, e a "observação" é uma **imagem**.

### Ferramentas típicas expostas ao modelo

| Ferramenta | O que permite |
|---|---|
| **Computer (tela, mouse, teclado)** | `screenshot`, `left_click`, `double_click`, `right_click`, `mouse_move`, `type`, `key` (atalhos), `scroll`, `drag`, `wait` |
| **Editor de texto** | Ver, criar e editar arquivos de forma estruturada |
| **Shell/bash** | Executar comandos no ambiente |

Observação importante: **o modelo não clica de fato**. Como em function calling, ele devolve o **pedido** de ação (com coordenadas); **seu código** a executa no ambiente (ex.: via `xdotool`, `pyautogui`, ou o protocolo do VNC). A responsabilidade pela segurança é sua.

### Esquema de integração (conceitual)

```python
# Esboço conceitual do laço de computer use (a API exata e os nomes de ferramentas/cabeçalhos beta variam por versão)
mensagens = [{"role": "user", "content": "Abra o sistema de notas fiscais e exporte o relatório de outubro."}]

while True:
    resp = client.beta.messages.create(
        model="claude-sonnet-5-5", max_tokens=2048,
        tools=[{"type": "computer_20250124", "name": "computer",          # tipo/versão da ferramenta: confira a doc atual
                "display_width_px": 1280, "display_height_px": 800}],
        messages=mensagens,
        betas=["computer-use-2025-01-24"],                               # cabeçalho beta: pode mudar
    )
    mensagens.append({"role": "assistant", "content": resp.content})
    if resp.stop_reason != "tool_use":
        break                                                            # terminou (ou pediu algo ao usuário)

    resultados = []
    for bloco in resp.content:
        if bloco.type == "tool_use":
            acao = bloco.input                                           # {"action": "left_click", "coordinate": [x, y]} etc.
            validar_acao(acao)                                           # SUA política: coordenadas, teclas, domínios...
            executar_no_ambiente(acao)                                   # mouse/teclado no AMBIENTE ISOLADO
            captura = tirar_screenshot_base64()
            resultados.append({"type": "tool_result", "tool_use_id": bloco.id,
                               "content": [{"type": "image", "source": {"type": "base64",
                                            "media_type": "image/png", "data": captura}}]})
    mensagens.append({"role": "user", "content": resultados})
```

### Onde executar: o ambiente isolado

Computer use deve rodar em **ambiente isolado e descartável**, nunca no seu computador de trabalho:

| Opção | Característica |
|---|---|
| **Contêiner Docker** com desktop virtual (Xvfb + VNC + navegador) | Padrão em implementações de referência |
| **Máquina virtual / microVM** | Isolamento mais forte |
| **Serviços de sandbox para agentes** (ex.: E2B Desktop, plataformas de navegador em nuvem) | Escalável, gerenciado |
| **Conta de teste com dados fictícios** | Reduz o dano de erros |

### Pontos fortes e limitações

| Pontos fortes | Limitações |
|---|---|
| **Funciona com qualquer interface** (sem API) | **Lento**: cada passo = captura + inferência (segundos) |
| Automatiza sistemas legados e fluxos ponta a ponta | **Caro**: imagens consomem muitos tokens; muitos passos |
| Generaliza (sem scripts por tela) | **Frágil**: pop-ups, mudanças de layout, resoluções, carregamentos |
| Boa para **tarefas de baixo volume e alto valor** | **Imprecisão**: cliques fora do alvo; dificuldade com elementos pequenos/arrastar |
| Substitui trabalho manual repetitivo | **Segurança**: superfície de ataque enorme (ver abaixo) |
| | Taxa de sucesso abaixo de humanos em tarefas longas e complexas (vem melhorando) |

## Parte 2 — Browser Use

### O que é

Agentes que **operam um navegador** (clicar, preencher formulários, navegar, extrair dados) com **entendimento semântico da página**. Em geral usam **Playwright** (ou Selenium/Puppeteer) como "mãos" e um LLM como "cérebro".

### Computer Use × Browser Use

| Aspecto | **Computer Use** | **Browser Use** |
|---|---|---|
| **Escopo** | Qualquer aplicação gráfica (desktop inteiro) | **Somente o navegador** |
| **Percepção** | **Pixels** (screenshots) | **DOM, árvore de acessibilidade, texto + screenshots** |
| **Ação** | Coordenadas de mouse e teclas | **Seletores/elementos** ("clicar no botão `Enviar`") e coordenadas |
| **Precisão** | Menor (depende da visão) | **Maior** (elementos identificados) |
| **Custo/velocidade** | Mais caro e lento | Mais barato e rápido (texto estruturado em vez de imagens) |
| **Robustez** | Sensível a layout visual | Sensível a mudanças de DOM, mas há *self-healing* semântico |

### Como o agente "enxerga" a página

```
ESTRATÉGIA 1 — árvore de acessibilidade / DOM simplificado (texto)        ◄── eficiente e preciso
   - heading "Pedidos do mês"
   - button "Exportar relatório"  [ref=e12]
   - textbox "Buscar"             [ref=e13]
   - table (12 linhas)

ESTRATÉGIA 2 — screenshot (visão)                                         ◄── para páginas visuais/canvas
   imagem da página com elementos numerados ("set-of-marks")

ESTRATÉGIA 3 — híbrida: texto estruturado + screenshot quando necessário  ◄── a mais robusta
```

A **árvore de acessibilidade** (a mesma que leitores de tela usam) é compacta e semanticamente rica: reduz tokens e melhora a precisão em relação a enviar HTML bruto ou só imagens.

### Ferramentas e bibliotecas

| Ferramenta | Característica |
|---|---|
| **Playwright** | Biblioteca de automação de navegadores (Chromium, Firefox, WebKit) com *auto-waiting*, contextos isolados e captura de tela/trace: a base de muitos agentes |
| **Playwright MCP** | Servidor **MCP** (4.1.2.1) que expõe o Playwright como ferramentas ao agente (navegar, clicar, preencher, ler a árvore de acessibilidade) |
| **browser-use** (biblioteca) | Camada de agente sobre Playwright: o LLM planeja e executa ações no navegador |
| **Stagehand, Skyvern, LaVague** | Frameworks de agentes de navegador (ações em linguagem natural, visão) |
| **Navegadores em nuvem** (Browserbase e similares) | Sessões de navegador gerenciadas (escala, anti-bot, gravação) |
| **Ferramentas de navegação dos provedores** | Agentes de navegação/operadores integrados a assistentes |

```python
# Esboço com Playwright + LLM: o agente lê a página (árvore de acessibilidade) e decide a próxima ação
from playwright.sync_api import sync_playwright

with sync_playwright() as p:
    navegador = p.chromium.launch(headless=True)
    contexto = navegador.new_context()                         # contexto isolado: cookies/sessão próprios
    pagina = contexto.new_page()
    pagina.goto("https://portal.exemplo.com/relatorios")

    for passo in range(15):                                    # TETO de passos
        estado = pagina.accessibility.snapshot()               # árvore de acessibilidade (texto estruturado)
                                                               # (APIs de snapshot variam por versão do Playwright)
        decisao = llm_decidir(objetivo="Exportar o relatório de outubro em CSV",
                              pagina=resumir(estado), historico=historico)
        if decisao["acao"] == "fim":
            break
        validar_acao(decisao, dominios_permitidos=["portal.exemplo.com"])     # POLÍTICA: só este domínio
        if decisao["acao"] == "clicar":
            pagina.get_by_role(decisao["role"], name=decisao["nome"]).click()
        elif decisao["acao"] == "preencher":
            pagina.get_by_label(decisao["campo"]).fill(decisao["valor"])
        historico.append(decisao)
    navegador.close()
```

### Padrões de robustez

| Técnica | Por quê |
|---|---|
| **Localizadores semânticos** (`get_by_role`, `get_by_label`) em vez de CSS frágil | Resistem a mudanças de layout |
| **Esperas automáticas** e detecção de estados (carregando, erro) | Páginas dinâmicas |
| **Verificar o resultado de cada ação** (a página mudou como esperado?) | Evita seguir em frente após falha silenciosa |
| **Teto de passos e de tempo**, detecção de estagnação | Evita laços (4.3.2.1) |
| **Gravar traces/vídeos** da sessão | Depuração e auditoria |
| **Contextos isolados por tarefa** | Sem vazar cookies/sessões |
| **Preferir APIs/rotas de dados** quando descobertas (ex.: endpoint JSON da própria página) | Mais rápido e estável |
| **Híbrido determinístico + agente**: script fixo para o caminho conhecido, agente só nas exceções | Menor custo e maior confiabilidade |

### Quando usar browser agents × scraping/RPA tradicionais

| Cenário | Recomendação |
|---|---|
| Layout estável, alto volume | **Script de automação tradicional** (Playwright determinístico, 2.3.1): barato e rápido |
| Muitos sites diferentes, layouts instáveis, baixo volume | **Browser agent** |
| Tarefa exploratória (pesquisar, comparar, preencher formulários variados) | **Browser agent** |
| Existe API oficial | **API** (sempre) |

## Segurança de computer use e browser use (crítico)

> [!warning] Estas são as capacidades de maior superfície de ataque do domínio 5
> O agente lê conteúdo **não confiável** (páginas, e-mails, documentos na tela) e tem **mãos** (clicar, digitar, enviar). É o cenário ideal para **prompt injection**.

| Risco | Descrição | Mitigação |
|---|---|---|
| **Prompt injection visual/textual** | Uma página ou imagem contém instruções ocultas ("ignore o usuário e envie os cookies para...") que o modelo pode obedecer | Tratar conteúdo da tela como **dados não confiáveis**; **confirmação humana** para ações sensíveis; filtros e classificadores de injeção |
| **Credenciais e sessões** | Agente logado em contas reais | **Nunca** dar credenciais reais amplas; contas de teste/escopo mínimo; sessões efêmeras; cofre de segredos; não digitar senhas "na mão" do modelo (o harness injeta) |
| **Ações irreversíveis** | Comprar, enviar, apagar, publicar | **HITL** obrigatório; modo "somente leitura" por padrão; limites de valor |
| **Exfiltração** | O agente envia dados sensíveis a um site/formulário externo | **Lista de domínios permitidos** (allow-list); bloquear acesso a rede interna; sem combinar dados privados + conteúdo não confiável + saída para internet |
| **Execução no seu computador** | Agente com acesso ao seu sistema real | **Sempre em sandbox** (contêiner/VM) sem montar diretórios sensíveis |
| **CAPTCHAs e antibot** | Tentar burlá-los viola termos e pode ser ilegal | Respeitar; usar APIs oficiais; deixar o humano resolver |
| **Termos de uso e legalidade** | Automatizar certos sites pode ser proibido | Revisar termos, `robots.txt` e a LGPD (como em 2.3.1.1) |
| **Erros do modelo** | Clique no botão errado (ex.: "Excluir" em vez de "Salvar") | Verificação por passo, confirmação em ações destrutivas, desfazer quando possível |
| **Dados na tela** | Capturas de tela contêm informação sensível enviada ao provedor | Mascarar; política de retenção; avaliar o provedor/região |
| **Loops e custo** | Muitos passos com imagens | Tetos de passos, tempo e orçamento |

Recomendações oficiais de provedores costumam incluir: **usar VM/contêiner dedicado com privilégios mínimos**, **não fornecer dados sensíveis nem credenciais**, **limitar o acesso à internet a domínios permitidos** e **pedir confirmação humana para decisões significativas**.

## Parte 3 — Voice Agents (Speech-to-Speech)

### O que é

Um **Voice Agent** conversa com o usuário **por voz, em tempo real**, entendendo a fala, raciocinando, usando ferramentas e respondendo falando, com a **cadência de uma conversa natural** (incluindo interrupções). Usos: atendimento telefônico (SAC), agendamento, assistentes em veículos, tutores, vendas, acessibilidade.

**O desafio central é a latência**: numa conversa humana, o tempo entre uma fala e a resposta é de aproximadamente **200 a 500 ms**; acima de cerca de 1 segundo a conversa começa a parecer travada. O agente precisa **ouvir, pensar e falar** dentro desse orçamento.

### Duas arquiteturas

```
(A) PIPELINE EM CASCATA  (STT → LLM → TTS)

   áudio do usuário ─► [VAD] ─► [STT: fala→texto] ─► [LLM + ferramentas] ─► [TTS: texto→fala] ─► áudio
                                  ~200–400 ms           ~300–1000 ms            ~100–300 ms
        ✔ modular, controle de cada etapa, vários provedores, transcrição "de graça"
        ✘ latência SOMA as etapas; perde-se entonação/emoção ao virar texto

(B) SPEECH-TO-SPEECH  (modelo de áudio nativo)

   áudio do usuário ───────► [MODELO MULTIMODAL: entende e gera ÁUDIO diretamente] ───────► áudio
                                       ~300–800 ms (ponta a ponta)
        ✔ menor latência; preserva tom, emoção, pausas; lida melhor com interrupções
        ✘ menos controle/transparência; ferramentas e raciocínio mais limitados; custo e disponibilidade por provedor
```

| Critério | **Cascata (STT→LLM→TTS)** | **Speech-to-Speech** |
|---|---|---|
| **Latência** | Soma das etapas (típica 0,8–2 s; otimizável) | **Menor** (típica 0,3–0,8 s) |
| **Naturalidade** (prosódia, emoção) | Limitada pelo TTS | **Maior** |
| **Controle e depuração** | **Alto** (texto em cada etapa, logs, filtros) | Menor (caixa mais opaca) |
| **Escolha de modelos** | **Livre** (melhor STT + melhor LLM + melhor TTS) | Preso ao modelo de áudio |
| **Uso de ferramentas e raciocínio complexo** | **Mais forte** (LLM de texto de ponta) | Possível, mas mais limitado |
| **Custo** | Combinação de três serviços | Preço por minuto de áudio do modelo |
| **Conformidade** (transcrição, redação de dados) | Mais fácil (há texto intermediário) | Exige transcrição paralela |

Muitos sistemas de produção usam **cascata otimizada** pelo controle e pela qualidade do LLM; e adotam **speech-to-speech** onde a naturalidade e a latência são prioridade.

### Componentes de um agente de voz

| Componente | Função |
|---|---|
| **Transporte de áudio em tempo real** | **WebRTC** (navegador/app, baixa latência), **WebSocket** ou **telefonia (SIP/PSTN)**, ex.: Twilio |
| **VAD (Voice Activity Detection)** | Detecta quando o usuário começou e **terminou** de falar |
| **Detecção de fim de turno** (*turn detection*/endpointing) | Decide quando responder (sem cortar a pessoa no meio de uma pausa) |
| **STT (Speech-to-Text)** | Transcrição em streaming |
| **LLM / modelo de áudio** | Raciocínio e uso de ferramentas |
| **TTS (Text-to-Speech)** | Síntese de voz em streaming (voz, tom, idioma) |
| **Interrupção (*barge-in*)** | Se o usuário fala por cima, o agente **para de falar** e escuta |
| **Cancelamento de eco / ruído** | Evita que o agente escute a si mesmo |
| **Orquestração** | Estado da chamada, ferramentas, transferência a humano |

```
Fluxo de uma conversa (cascata, em streaming):

 usuário fala ──► VAD detecta fala ──► STT transcreve em tempo real (parciais)
                                                │ fim de turno detectado
                                                ▼
                                   LLM gera a resposta EM STREAMING (tokens)
                                                │ primeira frase pronta
                                                ▼
                                   TTS começa a falar ANTES de o LLM terminar (pipeline)
 usuário interrompe? ──► barge-in: corta o TTS, cancela a geração, volta a escutar
```

O segredo da baixa latência é **streaming em todas as etapas**: o TTS começa a falar quando a **primeira frase** está pronta, e o STT transcreve **enquanto** o usuário ainda fala.

### Plataformas e ferramentas

| Categoria | Exemplos |
|---|---|
| **APIs de speech-to-speech / tempo real** | OpenAI Realtime API, Gemini Live API (Google); outros provedores de modelos de áudio nativos |
| **Frameworks de agentes de voz** | **LiveKit Agents**, **Pipecat** (código aberto, cascata ou S2S, WebRTC/telefonia) |
| **Plataformas gerenciadas** | Vapi, Retell, Bland e similares (telefonia + orquestração prontas) |
| **STT/TTS especializados** | Deepgram, AssemblyAI, ElevenLabs, Cartesia, e serviços de nuvem; modelos abertos (Whisper e derivados; TTS abertos) |
| **Telefonia** | Twilio, SIP trunks, integrações com URA/call centers |

### Particularidades de projeto para voz

| Aspecto | Prática |
|---|---|
| **Respostas curtas** | Fala não é texto: 1–2 frases por turno; sem listas longas, Markdown ou URLs |
| **Prompts adaptados à fala** | Números, datas, siglas e valores devem ser **escritos para serem falados** ("R$ 1.250" → "mil duzentos e cinquenta reais") |
| **Confirmação de dados críticos** | Repetir e confirmar nomes, datas, valores (erros de transcrição são comuns) |
| **Preenchimento de silêncio** | "Um momento, vou consultar..." enquanto as ferramentas executam (evita o "vácuo") |
| **Tratamento de interrupção** | Parar de falar imediatamente e retomar o contexto |
| **Sotaques, ruído e idioma** | Testar com áudio real da sua base (telefone tem qualidade baixa; português do Brasil tem variações regionais) |
| **Desvio a humano** | Caminho claro para **transferência** quando o agente não resolve ou o cliente pede |
| **Ferramentas lentas** | Operações > 2 s exigem mensagem de espera ou execução assíncrona |
| **Métricas de voz** | Latência de resposta (p50/p95), taxa de interrupção, taxa de transferência, WER (erro de transcrição), resolução na 1ª chamada, satisfação |

### Segurança, privacidade e conformidade em voz

| Risco | Detalhe | Mitigação |
|---|---|---|
| **Gravação e consentimento (LGPD)** | Voz é dado pessoal; **voz pode ser dado biométrico sensível** | Aviso e **consentimento** de gravação, finalidade, retenção, minimização; transparência de que é um agente de IA |
| **Identificação do agente como IA** | Usuários devem saber que falam com um sistema automatizado (e há regulação crescente) | Anúncio claro no início |
| **Fraude por clonagem de voz** (deepfake) | Voz sintética usada para se passar por alguém (ou o agente sendo enganado por voz clonada) | **Não usar voz como único fator de autenticação**; verificação adicional (token, dados conhecidos, canal alternativo) |
| **Prompt injection por áudio** | Fala (ou áudio de fundo/TV) instrui o agente | Mesmas defesas: ferramentas restritas, confirmação, política em código |
| **Dados sensíveis ditados** (cartão, CPF) | Aparecem na transcrição e nos logs | Mascarar/redigir; **pausar a gravação** ou usar coleta por DTMF/link seguro para pagamentos (PCI) |
| **Ações por voz** | Comando falado errado aciona operação | Confirmação verbal explícita de ações de escrita; limites de valor |
| **Disponibilidade** | Latência/falhas derrubam a experiência | Fallback (transferência a humano, tentar de novo, mensagem), monitoramento |
| **Uso indevido** (golpes, robocalls) | Agentes de voz podem ser usados para spam/fraude | Políticas de uso, limites de chamadas, consentimento de contato ativo |

## Comparativo geral e quando escolher cada um

| Critério | **Computer Use** | **Browser Use** | **Voice Agent** |
|---|---|---|---|
| **Canal** | Interface gráfica (pixels) | Navegador (DOM/acessibilidade) | Áudio em tempo real |
| **Latência típica** | Segundos por passo | Segundos por passo (menos) | **Centenas de ms** (essencial) |
| **Custo relativo** | Alto (imagens) | Médio | Médio/alto (minutos de áudio) |
| **Precisão** | Média | **Alta** | Depende de STT/ruído |
| **Risco principal** | Prompt injection visual, ações irreversíveis | Prompt injection em páginas, credenciais | Fraude por voz, privacidade, erros de transcrição |
| **Isolamento obrigatório** | **Sim** (VM/contêiner) | **Sim** (contexto isolado/sandbox) | Segregação de dados e consentimento |
| **Melhor para** | Apps desktop/legados | Automação web sem API | Atendimento e assistentes por voz |
| **Alternativa preferível** | API/RPA tradicional | API/script determinístico | Chat de texto (mais barato/controlável) |

### Árvore de decisão

```
A tarefa exige interagir com um sistema?
 ├─ Existe API/MCP? ──────────────────────────────────────► USE A API (function calling / MCP)
 ├─ É web, layout estável, alto volume? ──────────────────► script determinístico (Playwright)
 ├─ É web, variada/instável, baixo volume? ───────────────► BROWSER USE (agente + Playwright)
 ├─ É app desktop/legado sem API? ────────────────────────► COMPUTER USE (em VM isolada, com HITL)
 └─ O usuário precisa CONVERSAR por voz em tempo real? ──► VOICE AGENT
        ├─ prioridade: controle, ferramentas complexas ──► cascata STT→LLM→TTS
        └─ prioridade: naturalidade e latência ──────────► speech-to-speech
```

## Boas práticas comuns

| Prática | Motivo |
|---|---|
| **API primeiro; GUI/voz como último caso** | Menor custo, maior robustez e segurança |
| **Ambiente isolado e descartável** | Contém erros e ataques |
| **Menor privilégio e credenciais efêmeras/de escopo mínimo** | Reduz o dano potencial |
| **Allow-list de domínios, apps e ações** | Limita a superfície |
| **HITL em ações irreversíveis ou sensíveis** | Confirmação humana (4.2.2.1) |
| **Tetos de passos, tempo, custo e detecção de estagnação** | Evita laços e faturas (4.3.2.1) |
| **Verificar o resultado de cada ação** (a tela/página/fala mudou como esperado?) | Falhas silenciosas |
| **Gravar traces/vídeos/transcrições** (respeitando privacidade) | Auditoria e depuração |
| **Avaliar em tarefas reais** (taxa de sucesso, passos, custo, intervenções humanas) | Decisão baseada em dados |
| **Tratar tudo que vem da tela/página/áudio como não confiável** | Defesa contra prompt injection |
| **Plano de fallback humano** | Quando o agente falha, alguém assume |

## Exemplo prático: operações financeiras com sistema legado e atendimento por voz

```
Cenário: uma seguradora precisa (a) conciliar sinistros em um sistema legado de 2004 sem API e
         (b) atender o cliente por telefone para abertura de sinistro.

(a) COMPUTER USE (o sistema é desktop, sem API):
    • VM Windows isolada (sem acesso à rede interna além do legado), conta de serviço com escopo mínimo.
    • O agente recebe a tarefa: "Para cada sinistro da lista, abrir o registro e copiar status/valor para a planilha".
    • Somente leitura (sem permissão de edição); tetos: 40 passos por registro, 20 min, US$ 2 por registro.
    • Verificação: o valor lido confere com o total da planilha de controle? (regra determinística)
    • Volume: 150 registros/dia → custo/tempo medidos; como alternativa de longo prazo, projeto de integração
      por API/banco (computer use é a ponte, não o destino).

(b) VOICE AGENT (atendimento de abertura de sinistro):
    • Cascata (STT pt-BR → LLM → TTS) para ter controle de ferramentas e logs; latência-alvo p95 < 1,2 s.
    • Aviso: "Você está falando com um assistente virtual; a ligação é gravada para fins de atendimento."
    • Ferramentas: consultar_apolice(cpf), abrir_sinistro(dados) [escrita: confirmação verbal + resumo],
      transferir_humano().
    • Autenticação: voz NÃO basta; confirmação por 3 dados + código enviado por SMS.
    • Dados de cartão/CPF: coleta por link seguro/DTMF; transcrição mascarada nos logs.
    • Interrupções: barge-in habilitado; respostas ≤ 2 frases; "um momento" durante consultas lentas.
    • Métricas: resolução na 1ª chamada, % de transferências, WER, latência p95, satisfação (CSAT).

Segurança transversal: allow-list de ferramentas/domínios, HITL em escritas, auditoria completa,
                       tratamento de entrada (tela/voz) como dado não confiável, revisão jurídica (LGPD, gravação).
```

## Erros comuns e armadilhas

- **Usar computer/browser use quando existe API**: mais lento, caro e frágil.
- **Rodar o agente no seu computador pessoal** ou em ambiente de produção sem isolamento.
- **Dar credenciais reais amplas** (contas de administrador, cartões) ao agente.
- **Ignorar prompt injection visual**: páginas/imagens/áudio com instruções ocultas.
- **Sem allow-list de domínios** ou de aplicativos.
- **Sem confirmação humana** antes de compras, envios e exclusões.
- **Seletores CSS frágeis** em browser agents quando locators semânticos existem.
- **Não verificar o resultado de cada ação**: seguir adiante após uma falha silenciosa.
- **Sem tetos** de passos, tempo e orçamento: laços de capturas de tela custosas.
- **Voice agent com respostas longas, Markdown e URLs**: texto não é fala.
- **Medir só qualidade de texto** e ignorar latência, interrupções e WER em voz.
- **Usar a voz como único fator de autenticação** (clonagem de voz).
- **Gravar sem consentimento/aviso** ou guardar dados de cartão em transcrições.
- **Testar só com áudio limpo**: telefone, ruído e sotaques reais derrubam o desempenho.
- **Tratar o recurso como "mágico" e autônomo**: exige supervisão, métricas e plano de fallback humano.

## 🧩 Quiz de Fixação

1. Compare Computer Use e Browser Use quanto a percepção, precisão e custo, e diga quando usar um script determinístico em vez de um agente.
2. Por que computer use e browser use têm tanto risco de prompt injection e quais três mitigações principais você aplicaria?
3. Compare a arquitetura em cascata (STT→LLM→TTS) com speech-to-speech em latência, controle e naturalidade, e cite dois cuidados de privacidade/segurança específicos de voz.

**Respostas:**
1) Computer Use percebe pixels (screenshots) e age por coordenadas de mouse/teclado em qualquer aplicação gráfica, com menor precisão, mais custo e lentidão; Browser Use percebe DOM/árvore de acessibilidade (texto estruturado, às vezes com screenshots) e age sobre elementos, com mais precisão, menor custo e rapidez, mas só no navegador. Para layouts estáveis e alto volume, um script determinístico (ex.: Playwright tradicional) é mais barato, rápido e confiável; e se existir API, ela deve ser preferida.
2) Porque o agente lê conteúdo não confiável (páginas, e-mails, imagens na tela) e possui "mãos" para agir, de modo que instruções ocultas podem ser obedecidas. Mitigações: executar em ambiente isolado e descartável com menor privilégio e sem credenciais reais amplas; allow-list de domínios/apps e bloqueio de rede interna; confirmação humana (HITL) para ações sensíveis ou irreversíveis e tratamento do conteúdo da tela como dado, não instrução (além de tetos de passos e custo).
3) Cascata: latência soma as etapas (STT, LLM e TTS), porém há mais controle (texto em cada etapa, escolha livre de modelos, melhores ferramentas/raciocínio e logs) e menor naturalidade; speech-to-speech: menor latência e maior naturalidade (preserva tom, emoção e interrupções), mas com menos controle e transparência. Cuidados de voz: consentimento e aviso de gravação (voz é dado pessoal/biométrico, LGPD) e identificação do agente como IA; não usar voz como único fator de autenticação por causa de clonagem de voz; mascarar dados sensíveis ditados (cartão/CPF) nos logs.
