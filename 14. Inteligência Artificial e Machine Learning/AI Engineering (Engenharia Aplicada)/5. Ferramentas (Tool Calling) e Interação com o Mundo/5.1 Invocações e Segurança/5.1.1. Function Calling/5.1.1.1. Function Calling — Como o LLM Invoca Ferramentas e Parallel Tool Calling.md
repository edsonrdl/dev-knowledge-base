### Function Calling — Como o LLM Invoca Ferramentas via JSON e Parallel Tool Calling

**Function calling** (ou *tool calling* / *tool use*) é o mecanismo que permite a um LLM **pedir** a execução de uma função do seu sistema (consultar um pedido, buscar no banco, enviar um e-mail) e usar o resultado na resposta. É a base de todos os agentes (4.1) e dos protocolos como o MCP (4.1.2.1). Entender o mecanismo com precisão evita o erro conceitual mais comum e mais perigoso desta área.

---

## A ideia central: o LLM não executa nada

> **O LLM não executa código. Ele gera um JSON pedindo para o seu back-end executar a API e devolver o resultado.**

```
              ┌─────────────────────────── SEU BACK-END ───────────────────────────┐
  Usuário ──► │ 1. envia: mensagens + DEFINIÇÕES das ferramentas  ───────────────► LLM │
              │                                                                     │ │
              │ 2. ◄────────── LLM responde: "quero chamar consultar_pedido         │ │
              │                 com {"numero": "9981"}"  (um JSON, NÃO a execução) ◄┘ │
              │                                                                       │
              │ 3. SEU CÓDIGO valida e EXECUTA a função (API/banco)                    │
              │                                                                       │
              │ 4. devolve o RESULTADO ao LLM  ───────────────────────────────────► LLM │
              │                                                                     │ │
              │ 5. ◄────────── LLM redige a resposta final em linguagem natural ◄───┘ │
              └─────────────────────────────────────────────────────────────────────┘
```

**Analogia:** o LLM é um **cliente num restaurante que escreve o pedido num papel**; ele nunca entra na cozinha. O **garçom (seu código)** lê o pedido, confere se é válido e se o cliente pode pedir aquilo, leva à cozinha (API), e traz o prato de volta. O cliente então descreve a refeição.

### Por que esse entendimento importa

| Consequência | Explicação |
|---|---|
| **Segurança é responsabilidade do seu código** | O JSON gerado é **entrada não confiável** (pode ser errada ou resultado de prompt injection): valide e autorize antes de executar |
| **Você controla a execução** | Pode aplicar permissões, limites, auditoria, aprovação humana |
| **O modelo só "vê" o que você devolve** | O resultado da ferramenta é texto/JSON que você injeta de volta |
| **Qualquer linguagem/serviço serve** | A ferramenta é só uma função sua; o modelo não depende de como ela é implementada |
| **Erros são recuperáveis** | Você devolve a mensagem de erro ao modelo e ele pode corrigir a chamada |

## Anatomia de uma ferramenta: o que o modelo recebe

Cada ferramenta é descrita por três coisas, normalmente em **JSON Schema**:

| Elemento | Função |
|---|---|
| **`name`** | Identificador único (ex.: `consultar_pedido`) |
| **`description`** | **Instrução para o modelo**: o que a ferramenta faz, **quando usar e quando não usar** |
| **Parâmetros (schema)** | Campos, tipos, obrigatoriedade, enums, descrições (o contrato dos argumentos) |

```json
{
  "name": "consultar_pedido",
  "description": "Consulta o status e os itens de um pedido pelo número. Use quando o cliente perguntar sobre andamento, prazo ou conteúdo de um pedido. NÃO use para criar ou cancelar pedidos.",
  "input_schema": {
    "type": "object",
    "properties": {
      "numero": { "type": "string", "description": "Número do pedido, apenas dígitos. Ex.: '9981'." },
      "incluir_itens": { "type": "boolean", "description": "Se true, inclui a lista de itens." }
    },
    "required": ["numero"],
    "additionalProperties": false
  }
}
```

> O campo do schema se chama `input_schema` na API da Anthropic e `parameters` na da OpenAI; o conceito é o mesmo. (Nomes e formatos variam por provedor e versão: confirme na documentação.)

**A descrição é "prompt engineering" de ferramenta**: o modelo escolhe e preenche a ferramenta **lendo a descrição**. Descrições vagas causam escolhas erradas.

## O ciclo completo, passo a passo (com código)

### Exemplo com a API da Anthropic

```python
import anthropic, json
client = anthropic.Anthropic()

ferramentas = [{
    "name": "consultar_pedido",
    "description": "Consulta status e itens de um pedido pelo número. Use para dúvidas sobre andamento de pedidos.",
    "input_schema": {"type": "object",
                     "properties": {"numero": {"type": "string", "description": "Número do pedido (apenas dígitos)"}},
                     "required": ["numero"]},
}]

mensagens = [{"role": "user", "content": "Onde está o meu pedido 9981?"}]

# 1) Primeira chamada: o modelo PODE pedir uma ferramenta
resp = client.messages.create(model="claude-sonnet-5-5", max_tokens=1024,
                              tools=ferramentas, messages=mensagens)

# 2) Se o modelo pediu uma ferramenta, o stop_reason é "tool_use" e há blocos tool_use no conteúdo
while resp.stop_reason == "tool_use":
    mensagens.append({"role": "assistant", "content": resp.content})          # guarda o pedido do modelo
    resultados = []
    for bloco in resp.content:
        if bloco.type == "tool_use":
            # 3) SEU CÓDIGO valida e executa (o modelo só gerou o JSON em bloco.input)
            try:
                saida = executar_ferramenta(bloco.name, bloco.input)          # com autorização e validação
                resultados.append({"type": "tool_result", "tool_use_id": bloco.id,
                                   "content": json.dumps(saida, ensure_ascii=False)})
            except Exception as e:
                resultados.append({"type": "tool_result", "tool_use_id": bloco.id,
                                   "content": f"ERRO: {e}", "is_error": True})  # o modelo pode se corrigir
    # 4) Devolve os resultados ao modelo (como mensagem de usuário com blocos tool_result)
    mensagens.append({"role": "user", "content": resultados})
    resp = client.messages.create(model="claude-sonnet-5-5", max_tokens=1024,
                                  tools=ferramentas, messages=mensagens)

# 5) Resposta final em linguagem natural
print(resp.content[0].text)
```

O formato das mensagens trocadas:

```
→ usuário:   "Onde está o meu pedido 9981?"
← assistente: [ {type: "text", text: "Vou consultar..."},
                {type: "tool_use", id: "toolu_01A", name: "consultar_pedido", input: {"numero": "9981"}} ]
→ usuário:   [ {type: "tool_result", tool_use_id: "toolu_01A", content: "{\"status\":\"em transporte\",\"previsao\":\"2026-11-08\"}"} ]
← assistente: "Seu pedido 9981 está em transporte, com previsão de entrega em 08/11."
```

### Exemplo equivalente com a API da OpenAI (Chat Completions)

```python
from openai import OpenAI
cliente = OpenAI()

ferramentas = [{"type": "function", "function": {
    "name": "consultar_pedido",
    "description": "Consulta status de um pedido pelo número.",
    "parameters": {"type": "object", "properties": {"numero": {"type": "string"}}, "required": ["numero"]},
}}]

resp = cliente.chat.completions.create(model="gpt-4o", messages=mensagens, tools=ferramentas)
msg = resp.choices[0].message

if msg.tool_calls:                                         # o modelo pediu ferramentas
    mensagens.append(msg)
    for chamada in msg.tool_calls:
        args = json.loads(chamada.function.arguments)      # os argumentos chegam como STRING JSON: faça parse e valide
        saida = executar_ferramenta(chamada.function.name, args)
        mensagens.append({"role": "tool", "tool_call_id": chamada.id, "content": json.dumps(saida)})
    resp = cliente.chat.completions.create(model="gpt-4o", messages=mensagens, tools=ferramentas)
```

(A OpenAI também oferece a Responses API, tópico 4.1.2.1, com itens `function_call` e `function_call_output`; o princípio é idêntico.)

### Resumo do vocabulário

| Conceito | Anthropic | OpenAI (Chat Completions) |
|---|---|---|
| Declarar ferramentas | `tools=[{name, description, input_schema}]` | `tools=[{type:"function", function:{name, description, parameters}}]` |
| Pedido do modelo | bloco `tool_use` (`stop_reason="tool_use"`) | `message.tool_calls` (`finish_reason="tool_calls"`) |
| Resultado devolvido | bloco `tool_result` (`tool_use_id`) | mensagem `role:"tool"` (`tool_call_id`) |
| Controlar escolha | `tool_choice` (`auto`, `any`, `tool`, `none`) | `tool_choice` (`auto`, `required`, função específica, `none`) |

---

## Controlando *se* e *qual* ferramenta é usada

| `tool_choice` | Comportamento | Uso |
|---|---|---|
| **auto** (padrão) | O modelo decide se usa e qual | Assistentes gerais |
| **required / any** | **Obriga** a chamar alguma ferramenta | Classificadores/extratores onde sempre há ação |
| **Ferramenta específica** | Obriga **aquela** ferramenta | Forçar saída estruturada (ferramenta como "schema de saída") |
| **none** | Proíbe ferramentas neste turno | Resposta final, sem mais ações |

Truque conhecido: usar uma "ferramenta" apenas como **schema de saída** (`tool_choice` forçado) para obter JSON estruturado do modelo (tópico 1.2.2.1).

### Modo estrito (*strict*)

Muitos provedores oferecem um modo em que os argumentos **seguem exatamente o schema** (decodificação restrita, tópico 1.2.2.1): tipos corretos, campos obrigatórios, sem campos extras. Reduz erros de parsing, mas **não garante que os valores estejam corretos nem que a ação seja permitida**: a validação de negócio e a autorização continuam sendo suas.

## Parallel Tool Calling (chamadas paralelas)

### A ideia

Em vez de pedir **uma** ferramenta por turno, o modelo pode pedir **várias de uma vez**, quando as chamadas são **independentes** entre si. Seu código as executa **em paralelo** e devolve **todos os resultados juntos**.

```
Pergunta: "Qual o clima em São Paulo, Rio e Curitiba, e a cotação do dólar?"

SEQUENCIAL (4 idas e voltas ao modelo):           PARALELO (1 ida e volta):
 turno 1: clima(SP)      → resultado               turno 1: o modelo pede 4 chamadas de uma vez:
 turno 2: clima(RJ)      → resultado                          clima(SP), clima(RJ), clima(CWB), cotacao(USD)
 turno 3: clima(CWB)     → resultado               seu código executa as 4 SIMULTANEAMENTE (asyncio)
 turno 4: cotacao(USD)   → resultado               devolve os 4 resultados em UMA mensagem
 turno 5: resposta final                           turno 2: resposta final
 Latência ≈ 5 × (LLM + ferramenta)                 Latência ≈ 2 × LLM + max(ferramentas)
```

**Analogia:** é a diferença entre um garçom que leva **um pedido de cada vez à cozinha** e outro que leva a **comanda inteira** e a cozinha prepara tudo em paralelo.

### Como o modelo sinaliza chamadas paralelas

Na mesma resposta do modelo vêm **vários blocos de chamada** (ex.: múltiplos `tool_use`, ou uma lista em `tool_calls`), cada um com seu **ID**. Você deve devolver **um resultado para cada ID** (a ordem não importa, mas todos os IDs precisam ser respondidos).

```python
import asyncio

async def executar_todas(blocos):
    async def uma(b):
        try:
            saida = await executar_ferramenta_async(b.name, b.input)
            return {"type": "tool_result", "tool_use_id": b.id, "content": json.dumps(saida)}
        except Exception as e:
            return {"type": "tool_result", "tool_use_id": b.id, "content": f"ERRO: {e}", "is_error": True}
    return await asyncio.gather(*(uma(b) for b in blocos if b.type == "tool_use"))   # em paralelo

resultados = asyncio.run(executar_todas(resp.content))
mensagens.append({"role": "user", "content": resultados})          # TODOS os resultados na mesma mensagem
```

### Quando paralelizar e quando não

| Situação | Paralelo? |
|---|---|
| Chamadas **independentes** (várias consultas de leitura) | **Sim**: menor latência |
| Chamadas com **dependência** (a 2ª precisa do resultado da 1ª) | **Não**: o modelo deve encadear em turnos |
| Chamadas com **efeitos colaterais que dependem de ordem** (criar pedido → cobrar) | Não (ou controle explícito de ordem) |
| Operações que **competem por um recurso** (mesma linha de banco) | Cuidado: concorrência e *rate limits* |
| Muitas chamadas simultâneas | Limite a concorrência (`asyncio.Semaphore`) |

```
Dependência de dados:    buscar_cliente(email) → id_cliente → listar_pedidos(id_cliente)
                         ▲ NÃO é paralelizável: a 2ª chamada precisa do resultado da 1ª
```

Parâmetros relacionados: alguns provedores permitem **desativar** as chamadas paralelas (ex.: um parâmetro como `parallel_tool_calls: false` na OpenAI, ou `disable_parallel_tool_use` na Anthropic), útil quando a ordem importa ou o *strict mode* não é compatível. Confirme o nome e a disponibilidade na documentação.

### Cuidados com paralelismo

| Cuidado | Detalhe |
|---|---|
| **Falha parcial** | Uma das N chamadas falha: devolva o erro **apenas daquela** (com `is_error`), e os demais resultados normalmente |
| **Idempotência** | Retentativas não devem duplicar efeitos (ex.: dois pagamentos) |
| **Timeouts individuais** | Uma chamada lenta não pode travar todas |
| **Limites de taxa** | Dezenas de chamadas simultâneas a uma API podem causar `429` |
| **Segurança** | Cada chamada passa pela **mesma validação e autorização** |
| **Custo de contexto** | Muitos resultados volumosos inflam o contexto: resuma/trunque |

## O que seu código deve fazer ao receber um pedido de ferramenta

```
Pedido do modelo (JSON)
      │
      ▼  1. VALIDAR o schema (Pydantic/JSON Schema): tipos, obrigatórios, limites, enums
      ▼  2. AUTORIZAR: este usuário/sessão pode usar esta ferramenta com estes argumentos?
      ▼  3. APLICAR POLÍTICA: limites de valor, listas permitidas, necessidade de aprovação humana (HITL)
      ▼  4. EXECUTAR com timeout e menor privilégio; registrar (auditoria)
      ▼  5. SANITIZAR a saída: truncar, remover segredos e dados desnecessários
      ▼  6. DEVOLVER ao modelo (resultado ou erro explicativo)
```

```python
from pydantic import BaseModel, Field, ValidationError

class ArgsConsultaPedido(BaseModel):
    numero: str = Field(pattern=r"^\d{1,12}$")

REGISTRO = {"consultar_pedido": (ArgsConsultaPedido, consultar_pedido_impl, "leitura")}

def executar_ferramenta(nome: str, args_brutos: dict, usuario) -> dict:
    if nome not in REGISTRO:
        raise ValueError(f"Ferramenta desconhecida: {nome}")                 # o modelo pode inventar nomes
    Modelo, impl, tipo = REGISTRO[nome]
    args = Modelo(**args_brutos)                                              # 1) VALIDAÇÃO (levanta ValidationError)
    if not usuario.pode(nome, args):                                          # 2) AUTORIZAÇÃO (por usuário, não pelo modelo)
        raise PermissionError("Sem permissão para esta operação.")
    if tipo == "escrita":                                                     # 3) POLÍTICA/HITL
        exigir_aprovacao(usuario, nome, args)
    return impl(args, timeout=10)                                             # 4) EXECUÇÃO com timeout
```

A mensagem de erro devolvida ao modelo deve ser **clara e acionável** ("`numero` deve conter apenas dígitos"), pois ele usa isso para tentar novamente.

## Segurança em function calling

| Risco | Descrição | Mitigação |
|---|---|---|
| **Argumentos maliciosos/inválidos** | O modelo (ou um atacante via prompt injection) gera argumentos perigosos | **Validar** com schema; parametrizar consultas SQL (nunca concatenar); listas de permitidos |
| **Prompt injection indireta** | Conteúdo lido (página, e-mail, resultado de ferramenta) instrui o modelo a chamar ferramentas | Tratar resultados como **dados**; confirmar ações sensíveis; separar capacidades |
| **Ferramentas com poder excessivo** | `executar_sql(consulta)` ou `shell(cmd)` livres | Ferramentas **estreitas e específicas** (`consultar_pedido(numero)`), menor privilégio, somente leitura |
| **Escalada de privilégio** | O agente age com mais poder que o usuário | **Propagar a identidade do usuário**; autorizar por usuário (não pela "sessão do agente") |
| **Ações irreversíveis** | Pagar, apagar, enviar | **HITL** (4.2.2.1), limites e confirmação |
| **Exfiltração de dados** | Modelo envia dados sensíveis por uma ferramenta (e-mail, HTTP) | Evitar a combinação dados privados + conteúdo não confiável + canal de saída; filtrar saídas |
| **Loops e custo** | Chamadas em laço infinito | Teto de iterações e de orçamento (4.3.2.1) |
| **Nomes/IDs alucinados** | O modelo inventa ferramentas ou IDs | Rejeitar ferramenta desconhecida; validar existência de IDs |
| **Vazamento em logs** | Argumentos e resultados com dados pessoais | Mascarar, controlar retenção |
| **Cadeia de suprimentos** (ferramentas de terceiros/MCP) | Descrições maliciosas ("tool poisoning") | Usar fontes confiáveis, revisar descrições, fixar versões |

## Projetando boas ferramentas

| Prática | Motivo |
|---|---|
| **Descrições como instruções** (quando usar e quando **não** usar) | É o que guia a escolha do modelo |
| **Poucas ferramentas, bem separadas** (ideal: dezenas, não centenas) | Muitas ferramentas confundem e consomem contexto; use **seleção/roteamento** de ferramentas se forem muitas |
| **Nomes e parâmetros autoexplicativos** | `data_inicio` (ISO 8601) em vez de `d1` |
| **Parâmetros com enums e formatos** | Reduz valores inventados |
| **Ferramentas estreitas** (uma função, um propósito) | Mais segurança e previsibilidade |
| **Saídas enxutas e estruturadas** | Menos tokens e melhor uso pelo modelo; inclua só o necessário |
| **Mensagens de erro acionáveis** | Permitem autocorreção |
| **Idempotência** para operações de escrita (chave de idempotência) | Retentativas seguras |
| **Ferramentas de leitura separadas das de escrita** | Permissões e aprovação diferentes |
| **Exemplos de uso** na descrição (quando útil) | Melhor preenchimento dos argumentos |
| **Versionar** as definições | Mudar uma ferramenta pode alterar o comportamento do agente |
| **Testar com um conjunto de casos** (o modelo escolhe a ferramenta certa? preenche certo?) | Avaliação de tool use |

### Muitas ferramentas: o problema da escala

Com dezenas ou centenas de ferramentas (comum com vários servidores MCP), as **definições consomem muitos tokens** e a **precisão de escolha cai**. Estratégias:

| Estratégia | Ideia |
|---|---|
| **Seleção por recuperação** | Embute descrições de ferramentas e recupera as top-k relevantes à pergunta (RAG de ferramentas) |
| **Roteamento por domínio** | Um classificador escolhe o conjunto (financeiro, logística...) antes do agente |
| **Descoberta sob demanda** | Ferramentas "buscadoras" que carregam definições só quando necessárias |
| **Subagentes especializados** | Cada um com poucas ferramentas (4.2.1.2, 4.4) |

## Function calling × outras técnicas

| Técnica | Diferença |
|---|---|
| **Saída estruturada (1.2.2.1)** | Só formata a **resposta**; function calling **aciona ações** e continua o diálogo com o resultado |
| **ReAct por texto (4.1.1.1)** | Versão "manual": o modelo escreve `Action:` em texto e o código faz *parsing*; o tool calling nativo é mais **robusto** (formato garantido pelo provedor) |
| **Code execution** (5.1.3.1) | O modelo escreve código executado em sandbox; function calling chama funções **pré-definidas** |
| **Computer/Browser use (5.1.2.1)** | O modelo opera interfaces gráficas, com ferramentas de "mouse e teclado" |
| **MCP (4.1.2.1)** | Padroniza como as ferramentas são **descobertas e expostas**; por baixo, o modelo ainda faz tool calling |

## Exemplo prático: assistente de atendimento com ferramentas de leitura e escrita

```
Ferramentas (estreitas, tipadas):
  LEITURA (automáticas):   consultar_pedido(numero)  ·  listar_pedidos_cliente()  ·  consultar_politica(tema)
  ESCRITA (com política):  solicitar_reembolso(numero, motivo)  →  valor ≤ R$ 200: automático;
                                                                  > R$ 200: aprovação humana (HITL).

Cenário: "Meu pedido 9981 chegou quebrado e quero meu dinheiro de volta; e me diga também o status do 9990."

Turno 1 — o modelo pede 3 chamadas em PARALELO (independentes):
   consultar_pedido("9981"), consultar_pedido("9990"), consultar_politica("produto avariado")
Turno 2 — seu código executa em paralelo (asyncio), valida e autoriza (usuário só vê os PRÓPRIOS pedidos):
   → dados dos pedidos + política (7 dias, foto obrigatória)
Turno 3 — o modelo pede solicitar_reembolso("9981", "avaria") (escrita, depende do resultado anterior → sequencial):
   → valor R$ 349 > R$ 200 → política exige aprovação humana → pausa (interrupt) → atendente aprova.
Turno 4 — resposta final: status do 9990, reembolso aprovado, prazo de crédito.

Salvaguardas: validação Pydantic; autorização por usuário; idempotência no reembolso;
              log de auditoria; tetos de iterações e custo; resultados sanitizados.
```

## Erros comuns e armadilhas

- **Achar que o LLM executa a função**: ele só gera o JSON; a execução (e a responsabilidade) é do seu código.
- **Executar sem validar** o JSON (confiar cegamente nos argumentos).
- **Autorizar pela "sessão do agente"** e não pelo usuário real.
- **Ferramentas amplas demais** (`executar_sql`, `shell`) sem barreiras.
- **Descrições vagas** ("faz coisas com pedidos"): o modelo escolhe mal.
- **Dezenas de ferramentas sem seleção**: contexto inflado e escolhas erradas.
- **Esquecer de devolver o resultado de algum `tool_use`/`tool_call_id`**: erro de API.
- **Paralelizar chamadas dependentes** ou com ordem/efeitos colaterais.
- **Falha parcial derrubando tudo** em chamadas paralelas.
- **Retentar escritas sem idempotência**: ações duplicadas.
- **Devolver resultados enormes** (tabelas inteiras) ao modelo.
- **Sem teto de iterações**: agente em laço infinito de chamadas.
- **Confundir "strict mode" com segurança**: garante o formato, não a permissão nem a verdade.
- **Mensagens de erro opacas** que impedem a autocorreção.

## 🧩 Quiz de Fixação

1. Descreva o ciclo do function calling e explique por que "o LLM não executa código".
2. O que é Parallel Tool Calling, quando é seguro usá-lo e que cuidados ele exige?
3. Cite quatro etapas que o seu código deve aplicar ao receber um pedido de ferramenta do modelo.

**Respostas:**
1) Você envia mensagens e as definições das ferramentas (nome, descrição, schema); o modelo responde com um pedido de ferramenta em JSON (tool_use/tool_calls); seu código valida, autoriza e executa a função; devolve o resultado ao modelo; e este redige a resposta final. O LLM só gera o JSON do pedido: quem executa é o back-end, que por isso é responsável por validação, autorização, limites e auditoria.
2) É o modelo pedir várias ferramentas independentes em um mesmo turno, que o código executa simultaneamente e devolve todos os resultados juntos, reduzindo a latência.
