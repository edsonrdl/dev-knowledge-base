### Construindo um Chatbot de Contratos — As 7 Categorias em um Único Pipeline

Nos tópicos 0.1 e 0.2 você viu as sete responsabilidades de um sistema RAG e as categorias de ferramentas que as atendem, sempre de forma separada. Aqui juntamos tudo: vamos **montar, passo a passo, um chatbot que responde perguntas sobre contratos jurídicos**, decidindo em cada etapa qual categoria de ferramenta entra em cena e por quê.

---

## O problema

Um escritório de advocacia tem 3.000 contratos em PDF (alguns digitais, outros escaneados). Os advogados querem perguntar em linguagem natural:

> "Qual o prazo de rescisão sem multa no contrato com a Acme?"
> "Quais contratos têm cláusula de reajuste pelo IGP-M?"

Requisitos: respostas **com citação da cláusula e página**, nenhum dado vazando para fora da empresa sem controle, e **medição objetiva de qualidade** antes de ir para produção.

**Analogia:** é montar uma biblioteca com bibliotecário. Alguém digitaliza os livros (extração), os cataloga por assunto (embeddings), os guarda em estantes indexadas (banco vetorial), um assistente busca os trechos certos (retrieval), um redator lê e responde (LLM), um gerente coordena (framework) e um auditor confere se as respostas estão corretas (avaliação).

---

## Passo 1 — Extração de dados (parsing)

Contratos têm cláusulas numeradas, tabelas de preço e, às vezes, páginas escaneadas. Um extrator simples de texto destruiria a estrutura. Ferramentas como **Docling** ou **LlamaParse** preservam títulos, listas e tabelas e fazem OCR quando necessário.

```python
from docling.document_converter import DocumentConverter

converter = DocumentConverter()
result = converter.convert("contratos/acme_2024.pdf")
markdown = result.document.export_to_markdown()   # estrutura preservada
```

Por que Markdown? Os títulos (`## Cláusula 8 — Rescisão`) viram âncoras naturais para o próximo passo.

## Passo 2 — Chunking por estrutura

Em contratos, a unidade semântica é a **cláusula**, não "1.000 caracteres". Dividimos pelos títulos e guardamos metadados para citação posterior.

```python
from langchain_text_splitters import MarkdownHeaderTextSplitter

splitter = MarkdownHeaderTextSplitter(headers_to_split_on=[("#", "doc"), ("##", "clausula")])
chunks = splitter.split_text(markdown)
for c in chunks:
    c.metadata.update({"contrato": "Acme 2024", "pagina": 12})   # metadados p/ citação
```

## Passo 3 — Embeddings

Cada chunk vira um vetor. Escolha pragmática: um modelo multilíngue (português!) como **bge-m3** (local) ou um modelo de API. A mesma escolha deve ser usada na consulta, ou os vetores vivem em "espaços" diferentes.

```python
from sentence_transformers import SentenceTransformer
modelo = SentenceTransformer("BAAI/bge-m3")
vetores = modelo.encode([c.page_content for c in chunks], normalize_embeddings=True)
```

## Passo 4 — Banco vetorial

Para 3.000 contratos (algumas centenas de milhares de chunks) e um time que já opera PostgreSQL, **pgvector** é a escolha de menor atrito: sem nova infraestrutura e com filtros SQL por metadados. Se a escala crescer muito, Qdrant ou Milvus entram.

```sql
CREATE TABLE trecho (
  id bigserial PRIMARY KEY, contrato text, clausula text, pagina int,
  conteudo text, embedding vector(1024)
);
CREATE INDEX ON trecho USING hnsw (embedding vector_cosine_ops);
```

## Passo 5 — Orquestração e retrieval

O framework (aqui **LangGraph**) conecta as peças em um fluxo: receber pergunta → recuperar → rerankear → gerar → validar citações. Usamos **busca híbrida** (vetorial + palavra-chave) porque números de cláusula e nomes de empresas ("Acme") são termos exatos que o vetor sozinho trata mal.

```
pergunta ─► reescrever consulta ─► busca híbrida (top 20) ─► reranker (top 5)
         ─► montar prompt com trechos ─► LLM ─► checar se cada afirmação tem citação
```

## Passo 6 — LLM

O prompt instrui o modelo a responder **somente com base nos trechos** e a citar contrato e cláusula:

```
Você é um assistente jurídico. Responda APENAS com base nos trechos abaixo.
Cite sempre [contrato, cláusula, página]. Se a resposta não estiver nos trechos,
diga "não encontrei no contrato".
<trechos> ... </trechos>
Pergunta: {pergunta}
```

Decisão de privacidade: se contratos não puderem sair da empresa, troca-se o LLM da nuvem por um modelo open-source servido localmente (vLLM ou Ollama). O restante do pipeline permanece igual — essa é a vantagem de separar as responsabilidades.

## Passo 7 — Avaliação

Antes de liberar para os advogados, cria-se um **golden dataset**: 50 a 100 perguntas reais com a resposta correta e a cláusula-fonte, validadas por um advogado. A ferramenta (por exemplo **Ragas**) mede:

| Métrica | Pergunta que responde |
|---|---|
| Context Recall | Os trechos certos foram recuperados? |
| Faithfulness | A resposta é fiel aos trechos, sem invenção? |
| Answer Relevancy | A resposta resolve o que foi perguntado? |

Qualquer mudança futura (novo chunking, novo embedding) é reavaliada contra o mesmo dataset, evitando regressões silenciosas.

## Quadro-resumo: decisão por categoria

| Categoria | Escolha no projeto | Motivo |
|---|---|---|
| Extração | Docling (+OCR) | PDFs mistos, tabelas, estrutura de cláusulas |
| Embeddings | bge-m3 | Multilíngue, roda local |
| Banco vetorial | pgvector | Time já usa PostgreSQL; filtros SQL |
| Framework | LangGraph | Fluxo com etapas condicionais e validação |
| LLM | API de nuvem ou modelo local | Depende da política de privacidade |
| Acesso a open-source | vLLM/Ollama (se local) | Dados sensíveis |
| Avaliação | Ragas + golden dataset | Medir antes de produção e a cada mudança |

---

## Erros comuns neste tipo de projeto

- **Chunking cego** (1.000 caracteres): corta cláusulas ao meio e perde o contexto jurídico.
- **Sem metadados**: impossível citar página e cláusula, e o advogado não confia na resposta.
- **Só busca vetorial**: perde consultas por número de cláusula ou nome exato.
- **Sem golden dataset**: ninguém sabe se a mudança de ontem piorou o sistema.
- **Modelo de embedding diferente na indexação e na consulta**.
- **Não tratar "não sei"**: sem instrução explícita, o LLM inventa uma cláusula plausível.

## 🧩 Quiz de Fixação

1. Por que o chunking por cláusula é melhor que por tamanho fixo em contratos?
2. Em que ponto do pipeline a escolha entre LLM de nuvem e LLM local altera o resto do sistema, e por quê?
3. Para que serve o golden dataset e quando ele deve ser reutilizado?

**Respostas:**
1) A cláusula é a unidade semântica do contrato: dividir por tamanho fixo corta cláusulas ao meio, mistura assuntos e separa condições de suas exceções, degradando o retrieval. Chunking por estrutura mantém cada cláusula íntegra e permite guardar metadados (cláusula, página) para citação.
2) Apenas na etapa do LLM (e do serviço que o expõe): como as responsabilidades são separadas, extração, chunking, embeddings, banco vetorial e avaliação permanecem iguais. Troca-se o cliente da API por um endpoint local (vLLM/Ollama), mantendo o mesmo prompt e a mesma interface.
3) É um conjunto fixo de perguntas com respostas e fontes corretas, validado por especialistas, usado para medir objetivamente a qualidade. Deve ser reutilizado a cada mudança relevante (chunking, embedding, prompt, modelo) para detectar regressões e comparar versões com a mesma régua.
