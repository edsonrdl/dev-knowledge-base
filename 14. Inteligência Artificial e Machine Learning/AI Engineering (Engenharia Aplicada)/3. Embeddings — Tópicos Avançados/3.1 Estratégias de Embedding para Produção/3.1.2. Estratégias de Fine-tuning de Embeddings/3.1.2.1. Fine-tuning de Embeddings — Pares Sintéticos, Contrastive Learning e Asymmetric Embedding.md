### Fine-tuning de Embeddings — Pares Sintéticos, Contrastive Learning e Asymmetric Embedding

Quando o modelo de embedding mais forte, somado a busca híbrida e reranking, ainda não atinge o recall exigido no seu domínio, resta **ajustar o próprio modelo**. O **fine-tuning de embeddings** reposiciona os vetores para que o *seu* conceito de "relevante" fique próximo. O maior obstáculo costuma ser a falta de dados rotulados; por isso este arquivo cobre três peças: **gerar pares de treino sintéticos** com LLM, treinar com **aprendizado contrastivo** (triplet loss e variantes) e tratar a **assimetria** entre perguntas curtas e documentos longos.

> [!note] Quando NÃO fazer fine-tuning
> Esgote antes as opções baratas (tópico 3.1.1.1): modelo genérico forte, híbrida, reranker, chunking e enriquecimento de texto. O fine-tuning adiciona custo de dados, treino, versionamento e **reindexação total** do corpus.

---

## 1. O que o fine-tuning de embeddings faz

Um embedding é um mapa em que a **distância representa similaridade**. O mapa genérico foi desenhado para a linguagem geral. No seu domínio, certas coisas que deveriam estar perto estão longe (e vice-versa).

```
ANTES (modelo genérico):                     DEPOIS (fine-tuned no domínio):

  pergunta: "prazo para recorrer de multa"    pergunta: "prazo para recorrer de multa"
        •                                            •
                    • art. 285 CTB (certo)           • art. 285 CTB (certo)   ◄ aproximou
   • texto sobre "prazo de entrega"                                  
   • texto sobre "recorrência"                                  • "prazo de entrega" ◄ afastou
        (distraidores mais perto que o certo)
```

**Analogia:** é calibrar uma bússola para o terreno local. A bússola genérica funciona no mundo todo, mas perto de uma mina de ferro (seu domínio) aponta ligeiramente errado; a calibração local corrige o desvio.

### O que ajustar: três níveis

| Nível | O que muda | Custo | Observação |
|---|---|---|---|
| **Fine-tuning completo** | Todos os pesos do modelo | Alto (GPU, risco de esquecimento) | Maior ganho potencial |
| **Eficiente em parâmetros (LoRA/PEFT)** | Pequenos adaptadores nos pesos | Médio | Bom equilíbrio; checkpoints pequenos |
| **Adaptador linear sobre os embeddings** | Matriz que transforma o vetor da pergunta (modelo congelado) | **Baixo** | Não exige reindexar documentos; ganho menor |

O **adaptador linear** (LlamaIndex: `EmbeddingAdapterFinetuneEngine`) é atraente: o modelo base permanece congelado, os vetores dos documentos **não mudam**, e só a consulta passa por uma transformação aprendida.

```
Fine-tuning completo/LoRA:      muda o modelo → TODO o corpus precisa ser reembutido.
Adaptador de consulta:          modelo igual; vetores dos docs iguais; só q' = W · q.
```

## 2. Geração de pares de treino sintéticos

### O problema dos dados

O treinamento precisa de pares **(pergunta, trecho relevante)**. Rotulá-los à mão é caro. Solução: usar um **LLM** para gerar, a partir de cada trecho, perguntas que ele responde.

```
Trecho do corpus:  "O prazo para interposição de recurso contra multa de trânsito é de 30 dias
                    contados da notificação (art. 285 do CTB)."
                              │  LLM
                              ▼
Perguntas geradas:  1. "Qual o prazo para recorrer de uma multa de trânsito?"
                    2. "Quantos dias tenho para contestar uma multa?"
                    3. "A partir de quando conta o prazo do recurso da multa?"
                              │
                              ▼
Pares de treino:   (pergunta1, trecho), (pergunta2, trecho), (pergunta3, trecho)
```

### Implementação

```python
from pydantic import BaseModel

class Perguntas(BaseModel):
    perguntas: list[str]

PROMPT = """Você cria dados de treino para um sistema de busca.
Leia o trecho e escreva {n} perguntas DIFERENTES que um usuário real faria e que este trecho
responde por completo. Varie o estilo (formal, coloquial, curta, detalhada). Não copie frases
do trecho; não mencione "o trecho". Perguntas em português.

Trecho: {trecho}"""

def gerar_pares(trechos: list[dict], n: int = 3) -> list[dict]:
    pares = []
    for t in trechos:
        resp: Perguntas = chamar_llm_estruturado(PROMPT.format(n=n, trecho=t["texto"]), Perguntas)
        for q in resp.perguntas:
            pares.append({"query": q, "positivo": t["texto"], "id_trecho": t["id"]})
    return pares
```

Linha a linha: o prompt pede perguntas **variadas e sem copiar o texto** (se a pergunta repete as palavras do trecho, o modelo aprende só a casar palavras); a saída estruturada (tópico 1.2.2.1) evita parsing frágil; guarda-se o `id_trecho` para filtrar depois.

### Garantindo a qualidade dos pares sintéticos

| Etapa | Técnica | Motivo |
|---|---|---|
| **Diversidade** | Variar estilo, comprimento, tipo de pergunta; temperatura moderada | Evita overfitting a um formato |
| **Filtragem por consistência** | Pergunta gerada deve recuperar o trecho de origem no top-k com um modelo base | Descarta perguntas vagas ou erradas |
| **Remover vazamento lexical** | Rejeitar perguntas com alta sobreposição de palavras com o trecho | Evita atalhos |
| **Amostrar trechos representativos** | Cobrir todas as áreas do corpus, inclusive as "difíceis" | Evita viés |
| **Misturar dados reais** | Incluir logs de perguntas reais de usuários, se houver | Reduz o desvio sintético ↔ real |
| **Separar treino/validação por documento** | Nenhum trecho de validação aparece no treino | Avaliação honesta |
| **Revisão humana por amostragem** | Conferir 50–100 pares | Detecta erros sistemáticos |

```python
def filtro_consistencia(pares, modelo_base, indice_trechos, k=10):
    bons = []
    for p in pares:
        topk = indice_trechos.buscar(modelo_base.encode(p["query"]), k=k)
        if p["id_trecho"] in topk:                    # o modelo base consegue achar? então é boa
            bons.append(p)
    return bons                                       # descarta pares "impossíveis" ou ruidosos
```

> Pares que o modelo base já acerta com folga ensinam pouco; os mais úteis ficam entre "o modelo acerta" e "o modelo erra por pouco". Veja *hard negatives* abaixo.

**Volume:** de **alguns milhares** (adaptador linear/LoRA) a dezenas de milhares de pares costumam produzir ganhos mensuráveis; mais dados com qualidade baixa não compensam.

Ferramentas: **LlamaIndex** (`generate_qa_embedding_pairs`, `EmbeddingAdapterFinetuneEngine`), **Sentence-Transformers** (treinadores e *loss functions*), **Ragas/DeepEval** (geração de conjuntos sintéticos de teste), bibliotecas de geração de dados como **Distilabel**.

## 3. Contrastive Learning e Triplet Loss

### A ideia

O treinamento **contrastivo** ensina o modelo por **comparação**: aproximar o que é relevante, afastar o que não é. Cada exemplo tem:

- **Âncora (A):** a pergunta;
- **Positivo (P):** o trecho relevante;
- **Negativo (N):** um trecho irrelevante.

```
        antes                              depois (treino)

   A •                                   A •───• P      (P puxado para perto)
        • N      • P                           
   (N mais perto de A que P)                        • N  (N empurrado para longe)
```

### Triplet loss

A **perda tripla** exige que a distância Âncora→Positivo seja menor que Âncora→Negativo por uma **margem** `m`:

```
L = max( 0,  d(A, P) − d(A, N) + m )

d(A,P) = distância entre âncora e positivo      m = margem (ex.: 0,2–0,5)
d(A,N) = distância entre âncora e negativo

• Se N já está mais longe que P por mais de m  → L = 0 (nada a aprender).
• Se N está perto demais (ou mais perto que P) → L > 0 → ajusta os pesos.
```

**Analogia:** é um professor mostrando três fotos: "esta é a pessoa (âncora), esta é a mesma pessoa em outro ângulo (positivo), esta é outra pessoa parecida (negativo). Aprenda a diferença." Quanto mais parecido o negativo, mais o aluno aprende.

### Negativos: o coração do treino

A qualidade dos **negativos** determina a qualidade do modelo.

| Tipo de negativo | Descrição | Efeito |
|---|---|---|
| **Aleatório** | Qualquer trecho do corpus | Fácil demais; ensina pouco |
| **In-batch** | Os positivos dos *outros* exemplos do mesmo lote servem de negativos (**gratuito**) | Base do treino eficiente (MNRL) |
| **Hard negative (difícil)** | Trecho **parecido mas incorreto** (achado pelo modelo base entre os top-k, mas que não é o certo) | **Maior ganho**: ensina distinções finas |
| **False negative** | Trecho que *parece* negativo mas é, na verdade, relevante | **Perigoso**: confunde o modelo; filtrar |

```
Mineração de hard negatives:
  1. Para cada pergunta, o modelo base busca o top-30 no corpus.
  2. Remova o positivo conhecido (e candidatos que sejam relevantes de fato).
  3. Escolha negativos das posições ~10–30 (parecidos, mas não os mais próximos,
     que podem ser falsos negativos).
```

### InfoNCE / Multiple Negatives Ranking Loss (MNRL)

Na prática, o padrão em Sentence-Transformers é a **MultipleNegativesRankingLoss**, uma perda contrastiva (InfoNCE) que usa **todos os outros exemplos do lote como negativos**. Para um lote de B pares, cada pergunta tem 1 positivo e B−1 negativos *grátis*; **lotes maiores = mais negativos = sinal melhor**.

```
Lote de 4 pares:
              P1    P2    P3    P4
   Q1       [ ✔     ✘     ✘     ✘ ]      cada linha: o positivo certo na diagonal,
   Q2       [ ✘     ✔     ✘     ✘ ]      os demais são negativos
   Q3       [ ✘     ✘     ✔     ✘ ]
   Q4       [ ✘     ✘     ✘     ✔ ]
```

### Implementação com Sentence-Transformers

```python
from sentence_transformers import SentenceTransformer, SentenceTransformerTrainer, losses
from sentence_transformers.training_args import SentenceTransformerTrainingArguments
from datasets import Dataset

modelo = SentenceTransformer("BAAI/bge-m3")                      # base a ajustar

# (anchor, positive) ou (anchor, positive, negative) com hard negatives
treino = Dataset.from_list([
    {"anchor": p["query"], "positive": p["positivo"], "negative": p["negativo_dificil"]}
    for p in pares_treino
])

perda = losses.MultipleNegativesRankingLoss(modelo)              # contrastiva com negativos in-batch

args = SentenceTransformerTrainingArguments(
    output_dir="modelos/bge-m3-juridico",
    num_train_epochs=2,                  # poucos epochs: evita esquecer o conhecimento geral
    per_device_train_batch_size=64,      # lote grande = mais negativos in-batch
    learning_rate=1e-5,                  # taxa BAIXA para não destruir o modelo base
    warmup_ratio=0.1,
    fp16=True,
)
SentenceTransformerTrainer(model=modelo, args=args, train_dataset=treino, loss=perda).train()
modelo.save("modelos/bge-m3-juridico-v1")
```

Linha a linha: a perda MNRL usa negativos do lote (e o `negative` explícito como *hard negative*); lote grande e taxa de aprendizado baixa são as duas alavancas mais importantes; poucos epochs evitam o **esquecimento catastrófico** (o modelo perder habilidades gerais).

### Outras perdas contrastivas e de ranking

| Perda | Entrada | Uso |
|---|---|---|
| **Triplet loss** | (A, P, N) | Clássica; sensível à mineração de negativos |
| **MultipleNegativesRankingLoss (InfoNCE)** | (A, P) ou (A, P, N) | **Padrão para retrieval** |
| **CosineSimilarityLoss** | (texto1, texto2, nota 0–1) | Quando há notas graduadas de similaridade |
| **ContrastiveLoss** | (t1, t2, rótulo 0/1) | Pares positivos/negativos binários |
| **MatryoshkaLoss** | Envolve outra perda | Treina vetores truncáveis (tópico 2.1.2.1) |
| **CachedMNRL / GISTEmbed** | (A, P) | Lotes gigantes com pouca memória; negativos guiados |

## 4. Asymmetric Embedding (embedding assimétrico)

### Perguntas e documentos são tipos diferentes de texto

```
Pergunta:   "prazo p/ recorrer de multa?"        ← curta, informal, uma intenção
Documento:  "Art. 285. O recurso contra a multa de trânsito será interposto no prazo de
             trinta dias, contados da notificação, devendo ser dirigido à autoridade..."
                                                  ← longo, formal, muitas informações
```

Em **busca simétrica** (ex.: achar frases parecidas, deduplicar) os dois lados têm a **mesma natureza**: um único codificador basta. Em **busca assimétrica** (pergunta → documento) o conteúdo, o comprimento e o estilo são diferentes; tratar ambos igualmente desperdiça capacidade.

### Estratégias de assimetria

| Estratégia | Como funciona | Exemplo |
|---|---|---|
| **Prefixos/instruções** (mesmo modelo) | Um prefixo diferente para consulta e documento diz ao modelo qual papel o texto tem | E5: `query: ...` × `passage: ...`; BGE: instrução "Represent this sentence for searching relevant passages:" |
| **Codificadores separados** (*two-tower* / bi-encoder assimétrico) | Um encoder para perguntas, outro para documentos, treinados juntos | DPR (*Dense Passage Retrieval*) |
| **Adaptador só de consulta** | Documentos com o modelo base (já indexados); só o vetor da pergunta passa por um adaptador treinado | `EmbeddingAdapterFinetuneEngine` |
| **Encoder leve para consulta** | Documentos com o modelo grande (offline); perguntas com um modelo pequeno (online, baixa latência), alinhados no mesmo espaço | Otimização de custo/latência |
| **Instruction-tuned embeddings** | O modelo recebe uma **instrução de tarefa** ("para recuperação jurídica...") e adapta o vetor | Modelos com `task`/`instruction` (e5-instruct, gte-Qwen, Jina, Nomic `search_query:`) |

```python
# Prefixos assimétricos (modelo E5): diferentes papéis, mesmo modelo
from sentence_transformers import SentenceTransformer
m = SentenceTransformer("intfloat/multilingual-e5-large")
docs = m.encode([f"passage: {t}" for t in trechos], normalize_embeddings=True)
q    = m.encode("query: prazo para recorrer de multa?", normalize_embeddings=True)
```

> [!warning] Esquecer o prefixo degrada o recall
> Em modelos treinados com prefixos, **omiti-los ou trocá-los** reduz a qualidade silenciosamente. Use exatamente o formato da documentação do modelo, **tanto no treino quanto na inferência**.

Ao fazer fine-tuning de um modelo assimétrico, **preserve a assimetria**: aplique os mesmos prefixos/instruções nos dados de treino que serão usados em produção.

## 5. O fluxo completo de fine-tuning

```
1. LINHA DE BASE
   Golden dataset (real, revisado) → Recall@k, MRR, nDCG do modelo atual.
        │
2. DADOS
   Pares sintéticos (LLM) + pares reais + filtros de qualidade
   + hard negatives minerados + divisão treino/validação POR DOCUMENTO.
        │
3. TREINO
   MNRL com lote grande; taxa de aprendizado baixa; 1–3 epochs; LoRA/adaptador se possível.
        │
4. AVALIAÇÃO
   Mesmo golden dataset + conjunto de validação + checagem de REGRESSÃO geral
   (o modelo continua bom em perguntas fora do domínio? teste em amostra do MTEB/BEIR).
        │
5. IMPLANTAÇÃO
   Versione o modelo (v1) → reindexe o corpus em índice novo → teste A/B → troca atômica.
        │
6. MONITORAMENTO
   Recall online (feedback, perguntas sem resposta) → novo ciclo com dados reais.
```

### Métricas e critérios de aceite

| Métrica | Pergunta | Meta |
|---|---|---|
| **Recall@k** | O trecho certo está no top-k? | Ganho relevante sobre a base (ex.: +5 a +15 pontos) |
| **MRR / nDCG@10** | Quão alto ele aparece? | Melhora |
| **Qualidade final do RAG** | Faithfulness e correção das respostas (Ragas) | Sobe, não só o retrieval |
| **Regressão geral** | Desempenho em tarefas gerais | Queda pequena aceitável |
| **Custo/latência** | Treino, reindexação, inferência | Dentro do orçamento |

---

## Riscos e boas práticas

| Risco | Mitigação |
|---|---|
| **Overfitting aos pares sintéticos** (o modelo decora o estilo do LLM gerador) | Diversificar prompts/modelos geradores; misturar dados reais; validar com perguntas humanas |
| **Esquecimento catastrófico** | Taxa de aprendizado baixa, poucos epochs, LoRA, mistura com dados gerais |
| **False negatives** nos hard negatives | Filtrar com reranker/LLM; evitar o topo mais próximo |
| **Vazamento treino→validação** | Dividir por documento, não por par |
| **Reindexação total** | Planejar custo e janela; índice paralelo; troca atômica |
| **Dados sensíveis no treino** | Treinar localmente; anonimizar; controle de acesso aos modelos (podem memorizar) |
| **Versionamento** | Registrar modelo base, dados, hiperparâmetros e métricas (MLflow/W&B) |
| **Ganho ilusório** | Medir no golden dataset **real**, não apenas em sintético |
| **Manutenção** | Reajustar quando o corpus ou o vocabulário mudarem muito |

## Exemplo prático: assistente de normas técnicas

```
Situação: base com 400 mil trechos de normas técnicas; siglas e referências cruzadas confundem
          o modelo genérico. Recall@5 = 0,71; meta = 0,85. Dados não podem sair da empresa.

1. Linha de base: BGE-M3 + híbrida + reranker → 0,78 (ainda abaixo da meta).
2. Pares: 20 mil trechos amostrados × 3 perguntas por LLM local = 60 mil pares;
   filtro de consistência (top-10 do modelo base) → 41 mil pares; 600 pares reais de
   logs de suporte adicionados; revisão humana de 100 pares (erros < 4%).
3. Hard negatives: top-30 do modelo base, posições 8–30, filtrados por reranker.
4. Treino: LoRA sobre BGE-M3, MNRL, lote 64, lr 1e-5, 2 epochs, com instrução assimétrica.
5. Avaliação (golden de 150 perguntas reais): Recall@5 0,78 → 0,88; nDCG@10 +9 pontos;
   desempenho em amostra BEIR cai 1,2 ponto (aceitável).
6. Implantação: novo índice em paralelo; A/B por 2 semanas; troca atômica; modelo v1 versionado.
7. Faithfulness do RAG sobe de 0,82 para 0,89 (efeito final confirmado).
```

## Erros comuns e armadilhas

- **Partir para fine-tuning** antes de esgotar híbrida, reranker e chunking.
- **Pares sintéticos que copiam o trecho**: o modelo aprende a casar palavras, não significado.
- **Sem filtro de qualidade** nos dados gerados por LLM.
- **Negativos aleatórios apenas**: ganho pequeno; falta de hard negatives.
- **False negatives** não tratados: o modelo aprende a afastar o que é relevante.
- **Taxa de aprendizado alta / muitos epochs**: esquecimento catastrófico.
- **Dividir treino e validação por par**, vazando o mesmo documento.
- **Avaliar só em dados sintéticos**.
- **Esquecer prefixos/instruções** do modelo assimétrico no treino ou na inferência.
- **Não reindexar** (ou misturar vetores de modelos diferentes no mesmo índice).
- **Não versionar** dados, modelo e métricas.

## 🧩 Quiz de Fixação

1. Como se geram pares de treino sintéticos e que filtros garantem sua qualidade?
2. Explique a triplet loss e por que *hard negatives* aceleram o aprendizado, citando o risco dos *false negatives*.
3. O que é embedding assimétrico e que cuidado se deve ter ao fazer fine-tuning de um modelo que usa prefixos `query:`/`passage:`?

**Respostas:**
1) Um LLM lê cada trecho do corpus e escreve perguntas diversas que ele responde, formando pares (pergunta, trecho). Filtros: checar se o modelo base recupera o trecho de origem no top-k, rejeitar perguntas com alta sobreposição lexical com o trecho, garantir diversidade, misturar perguntas reais, dividir treino e validação por documento e revisar amostras manualmente.
2) A triplet loss exige que a distância âncora–positivo seja menor que âncora–negativo por uma margem (L = max(0, d(A,P) − d(A,N) + m)). Hard negatives são trechos parecidos mas incorretos, que fazem a perda ser positiva e ensinam distinções finas, ao contrário de negativos aleatórios, fáceis demais. O risco é que alguns "negativos" sejam na verdade relevantes (false negatives), o que ensina o modelo a afastar o que deveria ficar próximo; filtra-se com reranker/LLM e evitando as posições mais próximas.
3) Embedding assimétrico trata perguntas (curtas, informais) e documentos (longos, formais) de modo diferente, via prefixos/instruções, codificadores separados ou adaptador só para a consulta. No fine-tuning, deve-se aplicar exatamente os mesmos prefixos/instruções nos dados de treino que serão usados em produção; omiti-los ou trocá-los degrada o recall silenciosamente.
