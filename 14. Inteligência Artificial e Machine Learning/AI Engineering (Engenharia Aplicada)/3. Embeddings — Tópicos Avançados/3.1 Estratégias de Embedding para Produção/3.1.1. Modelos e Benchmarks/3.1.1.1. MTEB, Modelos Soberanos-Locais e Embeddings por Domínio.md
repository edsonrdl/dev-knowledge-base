### MTEB, Modelos Soberanos/Locais e Embeddings Especializados por Domínio

Escolher um modelo de embedding parece simples: "pegar o primeiro do ranking". Na prática, é uma decisão com **três eixos** que se influenciam: **qualidade medida** (benchmarks como o MTEB), **soberania e privacidade** (onde o modelo roda e para onde vão os dados) e **adequação ao domínio** (jurídico, médico, código). Este arquivo ensina a ler benchmarks com espírito crítico, escolher entre modelos locais e de API e saber quando um embedding genérico não basta.

> [!note] Pré-requisito
> O tópico 2.1.2.1 apresentou famílias de modelos, dimensionalidade e Matryoshka. Aqui o foco é **avaliar e decidir**.

## 1. O benchmark MTEB

### O que é

O **MTEB** (*Massive Text Embedding Benchmark*) é a bateria de testes mais usada para comparar modelos de embedding. Em vez de medir uma única habilidade, avalia o modelo em **várias tarefas e muitos conjuntos de dados**, publicando um **ranking (leaderboard)** no Hugging Face.

### As tarefas avaliadas

| Tarefa | O que mede | Relevância para RAG |
|---|---|---|
| **Retrieval** | Dada uma pergunta, achar os documentos relevantes (métrica **nDCG@10**) | **A mais importante para RAG** |
| **Reranking** | Reordenar uma lista de candidatos | Alta |
| **STS** (similaridade semântica) | Quão parecidas são duas frases (correlação com notas humanas) | Média |
| **Classification** | Usar o embedding como entrada de um classificador | Baixa/média |
| **Clustering** | Agrupar textos por tema | Baixa/média |
| **Pair classification** | Dizer se dois textos são paráfrases/duplicados | Média |
| **Summarization** | Qualidade de resumos por similaridade | Baixa |
| **Bitext mining** | Achar traduções equivalentes | Baixa (relevante em multilíngue) |

```
Ranking MTEB geral = média de TODAS as tarefas
                         ▲
Seu RAG depende, sobretudo, da sub-pontuação de RETRIEVAL
(no seu idioma e no seu domínio!)
```

### Como o MTEB evoluiu

| Versão | Característica |
|---|---|
| **MTEB (original, inglês)** | ~56 tarefas em 8 categorias; referência histórica |
| **C-MTEB, MTEB-fr, MTEB-pl...** | Versões por idioma/região |
| **MMTEB (multilíngue massivo)** | Centenas de tarefas e mais de 250 idiomas; inclui código e domínios variados |
| **Subconjuntos temáticos** | Retrieval, código, jurídico, médico, longo contexto, entre outros |

Existem também benchmarks complementares: **BEIR** (retrieval zero-shot em 18 conjuntos, base do retrieval no MTEB), **MIRACL** (retrieval multilíngue, inclui português) e **LoCo/LongEmbed** (documentos longos).

### Como ler o leaderboard (e como NÃO ler)

```
✔ Filtre pelo SEU idioma e pela tarefa de RETRIEVAL.
✔ Compare dimensão, tamanho (parâmetros), contexto máximo e licença, não só a nota.
✔ Veja se o modelo é "zero-shot" no benchmark (sem ter treinado nos dados de teste).
✘ Não escolha só pela média geral.
✘ Não assuma que 1 ponto a mais no ranking vale a mudança.
```

| Cuidado | Explicação |
|---|---|
| **Contaminação de dados** | Modelos podem ter sido treinados com dados que se sobrepõem aos conjuntos de teste, inflando a nota; o leaderboard sinaliza o grau de "zero-shot" |
| **Distribuição diferente da sua** | Conjuntos públicos (Wikipedia, perguntas web) ≠ seus contratos, tickets e manuais |
| **Média esconde fraquezas** | Um modelo ótimo em classificação pode ser mediano em retrieval |
| **Custo e latência ausentes** | Um modelo de 7B parâmetros no topo pode ser inviável em produção |
| **Idioma** | Notas em inglês não preveem desempenho em português |
| **Ranking muda toda semana** | Consulte a data; modelos novos superam antigos rapidamente |

> [!warning] Consulte o leaderboard atual
> Rankings mudam muito rápido. Em vez de decorar nomes, aprenda o **processo de avaliação**: filtrar o MTEB para seu idioma/tarefa, escolher 3 a 5 candidatos e **testar no seu corpus**.

### O leaderboard é ponto de partida; seu golden dataset é o juiz

```
1. MTEB (filtro: idioma + retrieval + licença + tamanho viável) → 3 a 5 candidatos.
2. Golden dataset próprio (50–200 perguntas com trecho-fonte conhecido).
3. Para cada candidato: indexe uma amostra do corpus e meça Recall@5/10, MRR e nDCG.
4. Meça também latência (embedding da pergunta) e custo.
5. Decida; registre a versão do modelo.
```

```python
# Avaliação mínima de retrieval para comparar modelos
import numpy as np
from sentence_transformers import SentenceTransformer

def recall_at_k(modelo_nome, corpus, perguntas, gabarito, k=5):
    m = SentenceTransformer(modelo_nome)
    docs = m.encode(corpus, normalize_embeddings=True)              # (N, d)
    acertos = 0
    for pergunta, id_correto in zip(perguntas, gabarito):
        q = m.encode(pergunta, normalize_embeddings=True)
        topk = np.argsort(-(docs @ q))[:k]                          # k mais similares
        acertos += int(id_correto in topk)
    return acertos / len(perguntas)

for nome in ["BAAI/bge-m3", "intfloat/multilingual-e5-large", "Alibaba-NLP/gte-multilingual-base"]:
    print(nome, recall_at_k(nome, corpus, perguntas, gabarito))
```

(Prefixos como `query:`/`passage:` em modelos E5 devem ser aplicados conforme a documentação do modelo.)

## 2. Modelos soberanos e locais

### O que significa "soberano"

**Soberania de dados**: controle sobre **onde** os dados são processados e **quem** tem acesso a eles. Um modelo de embedding **local** (ou *self-hosted*) roda na sua infraestrutura; os textos **nunca saem** para um provedor externo.

**Analogia:** é a diferença entre mandar documentos sigilosos para um escritório de tradução externo (API) e ter um tradutor contratado **dentro** da empresa (modelo local). O segundo custa em infraestrutura e manutenção, mas o conteúdo não sai do prédio.

### Quando soberania e modelos locais são necessários

| Motivo | Exemplo |
|---|---|
| **LGPD/GDPR** | Dados pessoais de clientes e funcionários; transferência internacional restrita |
| **Sigilo profissional/regulatório** | Jurídico, saúde (prontuários), financeiro, setor público/defesa |
| **Propriedade intelectual** | Código-fonte e documentos estratégicos |
| **Disponibilidade e latência** | Ambientes *air-gapped* ou sem internet; latência baixa previsível |
| **Custo em grande volume** | Bilhões de tokens de embedding: GPU própria pode sair mais barata |
| **Estabilidade** | Versão do modelo **congelada**: APIs podem depreciar modelos e exigir reindexação forçada |
| **Contrato** | Cláusulas que proíbem processamento por terceiros |

### Modelos open-source relevantes

| Modelo/família | Parâmetros (ordem) | Dim. | Destaques |
|---|---|---|---|
| **BGE-M3** (BAAI) | ~570 M | 1024 | Multilíngue (100+ idiomas, inclui português), denso + esparso + multivetor, contexto longo (8k) |
| **multilingual-e5 (large/base/small)** (Microsoft/intfloat) | 118 M a 560 M | 384–1024 | Sólido em multilíngue; exige prefixos `query:`/`passage:` |
| **GTE multilingual** (Alibaba) | ~300 M | 768 | Contexto longo, bom custo-benefício |
| **Nomic Embed** | ~137 M | 768 | Contexto longo (8k), Matryoshka, pesos e código abertos |
| **mxbai-embed-large** (Mixedbread) | ~335 M | 1024 | Forte em retrieval em inglês; suporta Matryoshka e quantização |
| **Jina embeddings** | variados | 768–1024 | Contexto longo; suporte a late chunking |
| **e5-mistral-7b / modelos baseados em LLM** | ~7 B | 4096 | Top de ranking em qualidade; **exigem GPU** e são lentos/caros |
| **Snowflake Arctic Embed**, **Qwen3-Embedding** | variados | variados | Famílias recentes com boa relação qualidade/tamanho |

> [!warning] Verifique licenças
> Nem todo modelo "aberto" permite uso comercial: confira a licença (Apache 2.0, MIT, CC-BY-NC, licenças próprias). Isso é decisivo em projetos corporativos.

### Como rodar localmente

| Opção | Característica | Quando usar |
|---|---|---|
| **Sentence-Transformers** (Python, em processo) | Simples; controle total | Indexação em lote, pipelines Python |
| **Ollama** | Servidor local com API simples (`/api/embed`) | Desenvolvimento, estações de trabalho, pequenos servidores |
| **Hugging Face TEI** (*Text Embeddings Inference*) | Servidor otimizado (batching, GPU) | **Produção** com alto volume |
| **vLLM / Infinity** | Servidores de inferência com suporte a embeddings | Mesma infraestrutura dos LLMs |
| **ONNX Runtime / fastembed** | Execução leve em CPU (modelos quantizados) | Ambientes sem GPU, borda |

```python
# Embeddings locais via Ollama (servidor local, nenhum dado sai da máquina)
import requests

def embutir(textos: list[str]) -> list[list[float]]:
    r = requests.post("http://localhost:11434/api/embed",
                      json={"model": "nomic-embed-text", "input": textos}, timeout=60)
    r.raise_for_status()
    return r.json()["embeddings"]

vetores = embutir(["O aviso prévio é de 30 dias.", "A multa equivale a 3 aluguéis."])
```

```bash
# Servidor de produção com Hugging Face TEI (GPU)
docker run --gpus all -p 8080:80 -v $PWD/dados:/data \
  ghcr.io/huggingface/text-embeddings-inference:latest \
  --model-id BAAI/bge-m3
```

### Trade-offs: local × API

| Critério | **Local/soberano** | **API de terceiros** |
|---|---|---|
| **Privacidade e conformidade** | **Máxima** | Depende de contrato/DPA e região |
| **Custo inicial** | Infra (GPU/CPU), engenharia | Quase zero |
| **Custo em grande volume** | **Menor** (amortizado) | Cresce linearmente com tokens |
| **Qualidade de ponta** | Muito boa (modelos abertos ≈ APIs em vários benchmarks) | Frequentemente líder em modelos proprietários |
| **Operação** | Você cuida de atualização, escala, monitoramento | Gerenciada |
| **Estabilidade de versão** | **Congelada** (você decide) | Pode ser descontinuada |
| **Latência** | Baixa e previsível (rede interna) | Depende da rede e do provedor |
| **Escala elástica** | Planejar capacidade | Automática |

Regra prática: **comece pela exigência de dados**. Se os dados não podem sair, a decisão está tomada; senão, compare custo e qualidade medida.

### Soberania na prática: um desenho de referência

```
┌───────────────── Rede interna da empresa ─────────────────┐
│  Docling (parse) ─► TEI (BGE-M3 em GPU) ─► Qdrant/pgvector │
│                          ▲                      ▲          │
│  Aplicação RAG ──────────┴── embeddings ────────┘          │
│        │                                                   │
│        └─► LLM local (vLLM) ou LLM em nuvem COM dados mínimos│
└────────────────────────────────────────────────────────────┘
Nenhum documento bruto sai da rede; só (opcionalmente) os trechos mínimos
necessários ao prompt vão a um LLM externo, se a política permitir.
```

Observe: embeddings também **vazam informação** (é possível, em certas condições, reconstruir partes do texto original a partir do vetor). Trate o banco vetorial como dado sensível: **criptografia, controle de acesso e isolamento por tenant**.

## 3. Embeddings especializados por domínio

### O problema do embedding genérico

Modelos genéricos são treinados em textos amplos. Em domínios com **vocabulário técnico, abreviações e relações próprias**, o espaço vetorial não separa bem o que importa.

```
Domínio médico:
  "IAM" ≈ "infarto agudo do miocárdio"   (um modelo genérico pode confundir com "IAM" de outra área)
  "dor torácica irradiando para o braço esquerdo" ~ "isquemia miocárdica"   (relação clínica)

Domínio jurídico:
  "denunciação da lide" ≠ "denúncia" (semanticamente distintos para um jurista)

Domínio de código:
  "ordenar lista" deve se aproximar de `sorted()`/`quicksort`, não de texto sobre "listas de compras".
```

### Opções para adaptar ao domínio

| Estratégia | Descrição | Esforço | Ganho típico |
|---|---|---|---|
| **1. Modelo pré-treinado do domínio** | Usar um embedding já especializado | Baixo | Médio/alto se existir |
| **2. Modelo genérico forte + híbrida + reranker** | Compensar com BM25 e reranking | Baixo | Médio |
| **3. Fine-tuning do embedding** (tópico 3.1.2.1) | Ajustar com pares do seu domínio | Médio | **Alto** |
| **4. Enriquecer o texto** (glossário, expansão de siglas, contextual retrieval) | Preparar os dados | Baixo | Médio |
| **5. Treinar do zero** | Pré-treinar com corpus do domínio | Muito alto | Raramente justifica |

### Exemplos de modelos especializados

| Domínio | Modelos/abordagens |
|---|---|
| **Código** | Voyage-code, Jina code embeddings, CodeXEmbed, `nomic-embed-code`; (tópico 3.1.3.1) |
| **Jurídico** | Voyage-law, modelos treinados em legislação e jurisprudência; fine-tuning com pares lei↔caso |
| **Financeiro** | Voyage-finance e similares; FinMTEB como benchmark |
| **Biomédico/clínico** | PubMedBERT/BioBERT derivados, MedCPT, BioLORD; Cohere/Voyage com variantes médicas |
| **Multilíngue/idioma local** | BGE-M3, multilingual-e5; modelos treinados em português (ex.: derivados de BERTimbau) |
| **Documentos visuais** | ColPali/ColQwen (tópico 2.1.2.2) |

> [!warning] Disponibilidade muda
> Novos modelos de domínio surgem com frequência. Procure no leaderboard filtrando por domínio (MTEB tem subconjuntos como legal, médico, finanças e código) e valide com seus dados.

### Quanto se ganha com especialização?

Referências de mercado e da literatura indicam que embeddings **ajustados ao domínio** podem elevar o recall de forma notável frente a modelos genéricos (em muitos casos, da ordem de 10% a 25% em domínios técnicos), mas o ganho **varia muito** conforme o domínio, o corpus e a qualidade dos dados de ajuste. Trate esses números como ordem de grandeza e **meça no seu caso**.

### Árvore de decisão: genérico, de domínio ou fine-tuning?

```
Dados podem sair da empresa?
 ├─ Não ──► apenas modelos locais (BGE-M3, E5, GTE, Nomic...)
 └─ Sim ──► modelos locais ou API (compare custo/qualidade)

O modelo genérico forte atinge a meta de Recall@k no seu golden dataset?
 ├─ Sim ──► pare; otimize com híbrida + reranker + chunking
 └─ Não
     ├─ Existe modelo de domínio adequado? ──► teste-o
     └─ Não/insuficiente ──► fine-tuning com pares do seu domínio (3.1.2.1)
```

## Matriz de decisão resumida

| Situação | Recomendação |
|---|---|
| Português, dados públicos, prototipagem | API forte (ou BGE-M3 local) |
| Português, dados sensíveis/LGPD | **BGE-M3 / multilingual-e5 / GTE** local via TEI ou Ollama |
| Volume enorme de texto | Modelo local + quantização + Matryoshka (2.1.2.1) |
| Documentos longos | Modelos com contexto de 8k+ (BGE-M3, Nomic, Jina) + chunking adequado |
| Código-fonte | Modelo especializado em código |
| Domínio técnico com siglas e jargão | Híbrida (BM25) + reranker; fine-tuning se faltar recall |
| Sem GPU | Modelo pequeno (MiniLM, e5-small, bge-small) via ONNX/fastembed |

## Exemplo prático: escritório de advocacia que não pode usar nuvem

```
Requisitos: português jurídico, 3 milhões de trechos, sigilo profissional, 1 servidor com 1 GPU.

1. Filtro no MTEB/MIRACL: multilíngue, retrieval, licença comercial → candidatos:
   BGE-M3, multilingual-e5-large, GTE multilingual.
2. Golden dataset: 120 perguntas de advogados com o artigo/cláusula correta.
3. Resultados (Recall@5, ilustrativos): BGE-M3 0,86 · e5-large 0,83 · GTE 0,81.
4. BGE-M3 escolhido; servido por TEI; dense + sparse (esparso ajuda em números de artigos).
5. Gap em siglas jurídicas ("LINDB", "ADI"): glossário de expansão + BM25 híbrido → 0,90.
6. Ainda abaixo da meta (0,93) em jurisprudência → fine-tuning com pares sintéticos (3.1.2.1).
7. Segurança: vetores em banco com criptografia, ACL por cliente, logs de acesso.
```

## Erros comuns e armadilhas

- **Escolher pelo topo do ranking geral** sem filtrar por idioma e retrieval.
- **Não testar com o próprio corpus**: o benchmark público não é o seu domínio.
- **Ignorar a licença** de modelos "abertos".
- **Usar API para dados sensíveis** sem DPA, região e base legal.
- **Escolher modelo gigante** (7B) sem considerar GPU, latência e custo.
- **Esquecer prefixos** (`query:`/`passage:`) exigidos pelo modelo.
- **Achar que embeddings são anônimos**: vetores podem vazar informação; proteja o banco.
- **Trocar de modelo sem plano de reindexação**.
- **Pular a otimização barata** (híbrida, reranker, chunking) e ir direto ao fine-tuning.
- **Não versionar** o modelo e a versão nos metadados.

## 🧩 Quiz de Fixação

1. Qual sub-pontuação do MTEB é a mais relevante para RAG e por que a média geral pode enganar?
2. Cite três motivos para preferir um modelo de embedding local/soberano.
3. Em que ordem se esgotam as opções para adaptar embeddings a um domínio técnico antes de partir para o fine-tuning?

**Respostas:**
1) A de Retrieval (nDCG@10), pois mede achar documentos relevantes para uma pergunta, que é o uso do RAG. A média geral mistura tarefas como classificação e clustering, que podem mascarar fraqueza em retrieval, e é medida em conjuntos públicos que diferem do seu idioma e domínio.
2) Por exemplo: conformidade com LGPD/GDPR e sigilo (dados não saem da infraestrutura), custo menor em grande volume, versão congelada do modelo (sem descontinuação), latência previsível, operação em ambientes sem internet e exigências contratuais.
3) Primeiro um bom modelo genérico multilíngue; depois busca híbrida (BM25), reranker, melhorias de chunking e enriquecimento do texto (glossário, expansão de siglas, contextual retrieval); depois testar modelos especializados do domínio; só então fine-tuning com pares do próprio domínio, se o golden dataset mostrar que a meta de recall não foi atingida.
