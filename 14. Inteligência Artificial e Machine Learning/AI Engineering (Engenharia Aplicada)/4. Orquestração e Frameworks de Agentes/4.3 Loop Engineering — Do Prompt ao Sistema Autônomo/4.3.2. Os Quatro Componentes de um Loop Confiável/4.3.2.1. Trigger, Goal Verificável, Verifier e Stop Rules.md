### Os Quatro Componentes de um Loop Confiável — Trigger, Goal Verificável, Verifier e Stop Rules

O tópico 4.3.1.1 definiu Loop Engineering como o sistema que **dispara, verifica, tenta de novo e para** um agente. Este arquivo abre cada um desses quatro verbos em um **componente de projeto**: **Trigger** (o que inicia o ciclo), **Goal Verificável** (para onde se quer chegar, de forma checável), **Verifier** (quem confirma que chegou) e **Stop Rules** (quando parar, de qualquer jeito). Esquecer qualquer um deles produz uma falha previsível; juntos, formam a diferença entre um experimento e um loop confiável.

```
                 ┌──────────────────────────────────────────────────────────┐
  (1) TRIGGER ──►│  ciclo:  agente age ──► (3) VERIFIER checa o (2) GOAL     │
   inicia        │             ▲                │                            │
                 │             │ feedback       ├─ meta atingida ─► FIM ✔    │
                 │             └── (falhas) ◄───┤                            │
                 │                              └─ não ─► (4) STOP RULES?    │
                 │                                       iterações/orçamento │
                 │                                       esgotados ─► FIM ✘  │
                 └──────────────────────────────────────────────────────────┘
```

**Analogia:** um **termostato**. O gatilho é "a temperatura mudou" (ou o relógio); a meta é "22 °C" (um número, não "confortável"); o sensor é o verificador; e há um **disjuntor** (regras de parada) que corta tudo se o aquecedor ligar sem parar, evitando incêndio e conta de luz astronômica.

---

## 1. Trigger (Gatilho)

### O que é

O **evento que inicia o ciclo**, sem depender de alguém digitar um prompt. É o que torna o sistema **autônomo**: ele acorda sozinho quando há trabalho.

### Os três tipos de gatilho

| Tipo | Quando dispara | Exemplos |
|---|---|---|
| **Agendado (tempo)** | Em horários definidos (cron) | Toda madrugada de domingo: atualizar dependências; toda manhã: triagem de issues novas |
| **Orientado a eventos** | Quando algo acontece em outro sistema | PR aberto → revisar; teste falhou no CI → investigar; e-mail recebido → classificar; alerta de monitoramento → diagnosticar; nova versão de biblioteca lançada |
| **Manual pontual** | Um humano aciona, uma vez, com uma instrução | Comando `rodar-loop --tarefa "migrar para a versão 5"` |

```
Agendado:       cron "0 3 * * 0"  ──► dispara o loop de manutenção
Evento:         webhook (GitHub: pull_request.opened)  ──► dispara o loop de revisão
Manual:         linha de comando / botão no painel  ──► dispara uma execução avulsa
```

### Projetando bem o gatilho

| Preocupação | Boa prática |
|---|---|
| **Idempotência** | O mesmo evento recebido duas vezes (retentativa de webhook) não deve criar duas execuções conflitantes: use um **ID de execução** e trave por recurso (um loop por PR/branch) |
| **Descoberta de trabalho** | Gatilhos agendados podem **procurar** o que fazer (issues rotuladas, testes falhando) em vez de assumir que há trabalho |
| **Controle de rajada** | Mil eventos em um minuto não devem disparar mil loops: fila, *debounce* e limite de concorrência |
| **Contexto inicial completo** | O gatilho entrega ao agente **tudo** de que ele precisa (link do PR, log do erro, versão) para não começar às cegas |
| **Autorização** | Quem ou o que pode disparar? Webhooks assinados, tokens com escopo mínimo |
| **Rastreabilidade** | Registrar **por que** a execução começou (evento, horário, quem) |
| **Interruptor de emergência** (*kill switch*) | Poder desligar o gatilho rapidamente se algo sair do controle |

> [!warning] Gatilhos em cascata
> Um loop que, ao terminar, abre um PR que dispara **outro** loop, que abre outro PR... pode gerar uma **reação em cadeia** descontrolada. Marque as execuções originadas por agentes e **impeça que gatilhos reajam ao trabalho do próprio loop** (ou limite a profundidade).

## 2. Goal Verificável (Meta Checável)

### O que é

Um **estado-alvo que uma máquina consegue checar**. Em vez de uma aspiração ("melhorar a qualidade do código"), uma condição **mensurável e binária** ("todos os testes passam e a cobertura é ≥ 80%").

**Sem meta checável, o loop nunca sabe quando parar**, e o agente passa a decidir sozinho o que significa "pronto", normalmente de forma otimista.

### Aspiração × meta verificável

| Aspiração vaga (**evite**) | Meta verificável (**use**) |
|---|---|
| "Melhorar a qualidade do código" | `eslint` sem erros **e** `tsc --noEmit` sem erros **e** cobertura ≥ 80% |
| "Deixar o site mais rápido" | LCP ≤ 2,5 s no teste de laboratório em 3 rodadas **e** *bundle* ≤ 200 KB |
| "Corrigir os bugs" | Os 12 testes de regressão do arquivo `bugs/` passam **e** nenhum teste existente quebrou |
| "Documentar a API" | 100% dos endpoints do OpenAPI têm descrição **e** exemplos **e** os exemplos executam sem erro |
| "Migrar para a nova versão" | Build verde na versão 5 **e** nenhum *warning* de API descontinuada **e** testes passando |
| "Limpar os dados" | Validação do schema: 0 linhas inválidas; duplicatas < 0,1%; testes de qualidade passam |
| "Responder bem aos tickets" | ≥ 95% das respostas passam nos checks de política (formato, tom, sem dados pessoais) em um conjunto de 200 tickets de teste |

### Propriedades de uma boa meta

| Propriedade | Pergunta de teste |
|---|---|
| **Checável por máquina** | Um script responde "sim/não" sem opinião humana? |
| **Específica e mensurável** | Há números, nomes de arquivo, comandos? |
| **Completa** | Atingi-la realmente significa que o **objetivo real** foi cumprido? (cuidado com metas "fáceis de burlar") |
| **Alcançável** | O agente tem as ferramentas e permissões para cumpri-la? |
| **Independente do agente** | O agente não pode alterá-la (ex.: editar os testes que a definem) |
| **Com restrições explícitas** | O que **não** pode ser feito (não editar testes, não adicionar dependências, não tocar em `infra/`) |
| **Escrita antes do agente** | A meta existe como **verificação executável** antes de qualquer código do agente |

### A meta em camadas

Metas reais costumam combinar **condições obrigatórias** e **restrições**:

```
META = {
   obrigatórias:  build ok  ∧  testes ok  ∧  lint ok,
   restrições:    nenhum arquivo em tests/ modificado  ∧  nenhuma dependência nova  ∧  diff ≤ 800 linhas,
   qualidade:     cobertura não diminuiu,
}
```

As **restrições** protegem contra o atalho clássico: cumprir o letra da meta violando o espírito (por exemplo, "passar nos testes" apagando os testes).

### Quando a meta não é 100% objetiva

Há tarefas com componente subjetivo (texto, design). Opções, **da mais para a menos confiável**:

| Estratégia | Observação |
|---|---|
| **Decompor** em partes verificáveis + uma parte revisada por humano | Máximo de verificação automática; humano só no que sobra |
| **Rubricas** com critérios binários ("tem resumo de 3 linhas? cita a fonte? sem jargão?") | Torna o subjetivo parcialmente checável |
| **LLM como juiz** (um modelo **independente**, com rubrica e exemplos) | Útil, mas **não determinístico**; calibre com amostras e nunca o use como única barreira para ações críticas |
| **Revisão humana ao final** | Sempre que o resultado tiver consequência |

## 3. Verifier (Verificador)

### O que é

O mecanismo que **confirma, após cada iteração, se a meta foi atingida**, e devolve **por que não**, quando não foi.

### A regra de ouro

> **Prefira verificação determinística** (código de saída, suíte de testes, linter, compilador, validador de schema, medição numérica) **a pedir ao modelo que avalie o próprio trabalho.**
> **Nunca deixe quem escreveu a solução julgar sozinho a própria qualidade.**

**Por quê?** Modelos tendem a **concordar com o próprio trabalho** (viés de autoavaliação) e a declarar sucesso prematuramente. Um verificador determinístico não tem opinião: ou passa, ou falha.

### Hierarquia de verificadores

| Nível | Tipo | Exemplo | Confiabilidade |
|---|---|---|---|
| 1 | **Determinístico e objetivo** | `pytest`, `tsc`, `go build`, validação de JSON Schema, benchmark numérico | **Alta** |
| 2 | **Determinístico por regras** | Regex/AST para padrões proibidos, verificação de hash, política de arquivos alterados | Alta |
| 3 | **Verificador independente baseado em modelo** | Outro agente (ou outro modelo) revisa com rubrica, **sem ver o raciocínio** do autor | Média; calibrar |
| 4 | **Autoavaliação do agente** | "Você acha que terminou?" | **Baixa: use só como sinal auxiliar** |
| 5 | **Revisão humana** | Aprovação do PR | Alta, porém cara e lenta: reservar para o fim |

Padrão recomendado: **camadas** (1 + 2 sempre; 3 quando há subjetividade; 5 no fim).

### O que um bom verificador devolve

Não basta "falhou". O verificador deve produzir **feedback acionável** que alimenta a próxima iteração:

```
RESULTADO DA VERIFICAÇÃO — iteração 4
  ✔ build: ok
  ✘ testes: 2 falhas
       tests/checkout/test_desconto.py::test_cupom_expirado
         AssertionError: esperado 0.00, obtido 15.00   (linha 42)
       tests/checkout/test_frete.py::test_frete_gratis_acima_de_200
         KeyError: 'regiao'
  ✔ lint: ok
  ✔ nenhum arquivo em tests/ alterado (hash confere)
  → meta NÃO atingida (2 de 4 critérios pendentes: testes)
```

### Implementação de um verificador

```python
import subprocess, hashlib, pathlib, json

def rodar(cmd: list[str]) -> tuple[bool, str]:
    r = subprocess.run(cmd, capture_output=True, text=True, timeout=600)     # timeout: o verificador também pode travar!
    return r.returncode == 0, (r.stdout + r.stderr)[-4000:]                   # só o final: controla o tamanho do feedback

def hash_testes() -> str:
    h = hashlib.sha256()
    for p in sorted(pathlib.Path("tests").rglob("*.py")):
        h.update(p.read_bytes())
    return h.hexdigest()

HASH_ORIGINAL = hash_testes()                                                 # capturado ANTES do agente rodar

def verificar() -> dict:
    ok_build, log_build = rodar(["python", "-m", "compileall", "-q", "src"])
    ok_tests, log_tests = rodar(["pytest", "-q", "-x", "--maxfail=5"])
    ok_lint,  log_lint  = rodar(["ruff", "check", "src"])
    testes_intactos = hash_testes() == HASH_ORIGINAL                          # anti-trapaça: agente não pode editar testes
    criterios = {"build": ok_build, "testes": ok_tests, "lint": ok_lint, "testes_intactos": testes_intactos}
    return {"atingida": all(criterios.values()), "criterios": criterios,
            "feedback": "\n".join(l for ok, l in [(ok_build, log_build), (ok_tests, log_tests), (ok_lint, log_lint)] if not ok)}
```

Linha a linha: cada critério é um comando com **timeout**; o hash dos testes é guardado **antes** do agente atuar e comparado depois (impede enfraquecer o verificador); o retorno traz **os critérios** e o **feedback das falhas**, truncado para não estourar o contexto.

### Riscos do verificador

| Risco | Descrição | Mitigação |
|---|---|---|
| **Burla do verificador** (*reward hacking*) | O agente edita/apaga testes, "hardcoda" respostas, desativa checagens | Proteção de arquivos (somente leitura, hash), **testes ocultos** (de aceitação) que o agente não vê, revisão do *diff* |
| **Verificador incompleto** | Passa, mas o objetivo real não foi cumprido ("falso verde") | Cobrir comportamento real; testes de aceitação; revisão humana final |
| **Verificador instável (*flaky*)** | Falha ou passa aleatoriamente | Reexecutar, isolar fontes de não determinismo; marcar testes instáveis |
| **Verificador lento/caro** | Cada iteração leva dezenas de minutos | Verificação em níveis: rápida a cada iteração, completa só ao final |
| **Verificador que trava** | Entra em loop ou espera indefinidamente | **Timeouts** em todo comando |
| **Feedback excessivo** | Logs gigantes saturam o contexto do agente | Truncar e resumir; mostrar só falhas relevantes |
| **Verificador dependente do agente** | Usa o mesmo modelo/contexto do autor | Verificador independente (modelo/contexto diferente) |

### Verificador com LLM como juiz: como fazer direito

Quando for inevitável usar um modelo para verificar:

1. **Contexto limpo:** o juiz não recebe o raciocínio do autor, só o **resultado** e a **rubrica**.
2. **Rubrica binária e explícita**, com exemplos de aprovado/reprovado.
3. **Modelo independente** (outro modelo ou instância) e temperature baixa.
4. **Saída estruturada** (`{"criterio": "...", "passou": true, "evidencia": "..."}`), tópico 1.2.2.1.
5. **Calibração**: medir a concordância do juiz com avaliações humanas em uma amostra.
6. **Nunca como única barreira** de ações de alto risco.

## 4. Stop Rules (Regras de Parada)

### O que são

**Saídas independentes** que garantem que o loop **termina**, mesmo quando a meta nunca é atingida. Sem elas, um agente que não consegue resolver o problema **tenta para sempre**, consumindo tempo e dinheiro.

### As três regras fundamentais

| Regra | Condição | Resultado |
|---|---|---|
| **Saída de sucesso** | Verificador confirma a meta | Fim com sucesso: entrega o resultado (ex.: abre PR) |
| **Limite de iterações** (*iteration cap*) | Nº máximo de ciclos (ex.: 15) | Fim com falha controlada: escala a um humano |
| **Limite de orçamento** (*budget cap*) | Custo, tokens ou tempo máximo (ex.: US$ 15, 90 min) | Fim com falha controlada: evita gasto descontrolado |

> **Regra prática:** implemente **as três** antes de executar qualquer loop sem supervisão. Cada uma cobre falhas que as outras não cobrem (um loop pode ser barato por iteração e ainda assim infinito; ou gastar muito em poucas iterações).

### Regras adicionais recomendadas

| Regra | Para que serve |
|---|---|
| **Limite de tempo de relógio** (*wall-clock*) | Evita execuções que "penduram" |
| **Detecção de estagnação** | Para se o **mesmo erro** se repete N vezes ou se o diff não muda (o agente está andando em círculos) |
| **Detecção de regressão** | Para se o número de falhas **aumenta** ao longo das iterações (o agente está piorando o sistema) |
| **Limite de escopo da mudança** | Para se o diff passa de X linhas ou toca em áreas proibidas |
| **Disjuntor de falhas de infraestrutura** | Para após N erros de API/ferramenta consecutivos (não é problema do agente) |
| **Botão de parada (kill switch)** | Permite a um humano interromper imediatamente |
| **Cancelamento por novo evento** | Um novo commit no PR cancela a execução anterior (resultados obsoletos) |

### Implementação

```python
import time

def loop(tarefa, max_iter=15, orcamento_usd=15.0, max_segundos=5400, max_repeticoes=3):
    inicio, gasto, ultimo_erro, repeticoes = time.time(), 0.0, None, 0
    feedback = ""
    for i in range(1, max_iter + 1):                                     # STOP 1: limite de iterações
        resultado_agente = executar_agente(tarefa, feedback)             # retorna custo da chamada
        gasto += resultado_agente.custo_usd
        v = verificar()                                                  # verificador determinístico (seção 3)
        registrar(i, resultado_agente, v, gasto)                         # log para auditoria

        if v["atingida"]:                                                # SAÍDA DE SUCESSO
            return {"status": "sucesso", "iteracoes": i, "custo": gasto}

        if gasto >= orcamento_usd:                                       # STOP 2: orçamento
            return {"status": "parado_orcamento", "iteracoes": i, "custo": gasto}
        if time.time() - inicio >= max_segundos:                         # STOP 3: tempo
            return {"status": "parado_tempo", "iteracoes": i, "custo": gasto}

        erro_atual = hash(v["feedback"])                                 # STOP 4: estagnação (mesmo erro repetido)
        repeticoes = repeticoes + 1 if erro_atual == ultimo_erro else 1
        ultimo_erro = erro_atual
        if repeticoes >= max_repeticoes:
            return {"status": "parado_estagnacao", "iteracoes": i, "custo": gasto}

        feedback = v["feedback"]                                         # o erro alimenta a próxima tentativa
    return {"status": "parado_iteracoes", "iteracoes": max_iter, "custo": gasto}
```

O que acontece **depois** da parada também faz parte do projeto: um loop que parou por falha deve **entregar o estado atual** (branch, logs, hipóteses) e **escalar a um humano** (abrir issue, notificar), não simplesmente desaparecer.

### Escolhendo os limites

| Limite | Como calibrar |
|---|---|
| **Iterações** | Meça: quantas iterações as execuções bem-sucedidas costumam levar? Defina o teto em ~2–3× o P95 |
| **Orçamento** | Custo médio das execuções bem-sucedidas × margem; alerta antes do teto |
| **Tempo** | Duração do P95 + folga; considere janelas (ex.: terminar antes do expediente) |
| **Estagnação** | 2 a 3 repetições idênticas costumam bastar |

## Como os quatro componentes se combinam

| Componente | Pergunta que responde | Se faltar... |
|---|---|---|
| **Trigger** | Quando começa e com que contexto? | O loop depende de um humano (não é autônomo) ou dispara sem controle |
| **Goal verificável** | O que significa "pronto"? | O loop não sabe quando parar; o agente decide sozinho |
| **Verifier** | O objetivo foi realmente cumprido? | Resultado não verificado: "esperança"; ou burla do critério |
| **Stop Rules** | Quando desistir? | Loop infinito, gasto descontrolado |

### Diagnóstico rápido de falhas por componente ausente

```
Sintoma: "o agente fez mil mudanças e nunca disse que terminou"      → faltou GOAL verificável
Sintoma: "o agente disse que terminou, mas está quebrado"            → faltou VERIFIER (ou é autoavaliação)
Sintoma: "passou nos testes porque o agente mudou os testes"         → VERIFIER burlável (proteja o verificador)
Sintoma: "a fatura da API explodiu no fim de semana"                 → faltaram STOP RULES (orçamento/iterações)
Sintoma: "dispararam 300 execuções iguais ao mesmo tempo"            → TRIGGER sem idempotência/limite de rajada
Sintoma: "o loop abre PRs que disparam outros loops sem parar"       → TRIGGER em cascata
```

### Checklist antes de rodar um loop sem supervisão

1. [ ] **Trigger** definido (tipo, idempotência, limite de concorrência, kill switch).
2. [ ] **Meta** escrita como verificação **executável** (e testada manualmente em um ciclo).
3. [ ] **Restrições** explícitas (o que o agente não pode tocar/alterar).
4. [ ] **Verificador** determinístico, com timeouts, protegido contra burla e com feedback acionável.
5. [ ] **Regras de parada**: sucesso + iterações + orçamento (e tempo/estagnação).
6. [ ] **Isolamento**: branch/worktree/sandbox, permissões mínimas, sem segredos de produção.
7. [ ] **Ações irreversíveis** removidas ou protegidas por HITL.
8. [ ] **Logs e métricas**: custo, iterações, causa de parada, diffs.
9. [ ] **Plano de falha**: o que acontece quando o loop para sem sucesso (escalonamento).
10. [ ] **Revisão humana** do resultado final antes de qualquer efeito no mundo real.

## Exemplo prático: loop de correção de falhas de CI

```
TRIGGER:  evento "pipeline falhou na branch principal" (webhook do CI). Idempotente por commit SHA;
          1 loop por commit; ignora commits criados pelo próprio agente (evita cascata).

GOAL:     o mesmo pipeline (build + testes + lint) passa no commit corrigido;
          restrições: não alterar tests/, .github/, nem arquivos de configuração de infra; diff ≤ 300 linhas.

VERIFIER: (1) executa localmente o mesmo script do CI (determinístico);
          (2) verifica por hash que tests/ não mudou; (3) verifica o escopo do diff;
          (4) devolve ao agente as últimas 60 linhas do erro e a lista de critérios pendentes.

STOP RULES: sucesso → abre PR com o log "antes/depois";
            máx. 10 iterações; US$ 8 e 45 min; mesma falha 3× → para;
            número de testes falhando aumentando por 2 iterações → para (regressão).

AO PARAR SEM SUCESSO: comenta no commit com o diagnóstico e as hipóteses; notifica o dono do serviço.
MÉTRICAS: % de falhas de CI resolvidas sem intervenção, custo médio por correção, PRs aceitos sem alterações.
```

## Erros comuns e armadilhas

- **Gatilho sem idempotência** (mesmo evento, várias execuções) ou **sem limite de rajada**.
- **Cascata de gatilhos**: o loop reage ao trabalho do próprio loop.
- **Meta como aspiração** ("melhorar", "otimizar") sem critério checável.
- **Meta sem restrições**: o agente cumpre a letra violando o espírito.
- **Autoavaliação como único verificador**.
- **Verificador que o agente pode alterar** (testes editáveis, scripts no mesmo diretório de escrita).
- **Verificador sem timeout** ou instável (*flaky*), gerando falhas aleatórias.
- **Feedback vago** ("falhou") em vez de erros específicos e acionáveis.
- **Apenas uma regra de parada** (só iterações, sem orçamento; ou o contrário).
- **Ignorar estagnação e regressão**: o agente repete o mesmo erro ou piora o sistema até o teto.
- **Falhar em silêncio**: parar sem entregar estado e sem escalonar a um humano.
- **Não calibrar os limites** com dados de execuções reais.

## 🧩 Quiz de Fixação

1. Quais são os quatro componentes de um loop confiável e que pergunta cada um responde?
2. Por que se prefere o verificador determinístico à autoavaliação do modelo e que risco existe mesmo com verificador determinístico?
3. Por que são necessárias três regras de parada (sucesso, iterações, orçamento) e que regras adicionais ajudam a detectar um agente "andando em círculos"?

**Respostas:**
1) Trigger (quando e com que contexto o ciclo começa), Goal verificável (o que significa "pronto", de forma checável por máquina), Verifier (o objetivo realmente foi cumprido? devolvendo feedback acionável) e Stop Rules (quando desistir, garantindo que o loop termina). Sem eles o loop depende de um humano, não sabe parar, entrega resultados não verificados ou gasta sem limite.
2) Modelos tendem a concordar com o próprio trabalho e declarar sucesso prematuramente; um verificador determinístico (testes, código de saída, linter) é objetivo e independente de quem escreveu a solução. O risco que permanece é a burla do verificador (reward hacking), como editar ou apagar testes, fixar respostas ou desativar checagens; mitiga-se protegendo arquivos (somente leitura/hash), usando testes ocultos de aceitação, restringindo o escopo do diff e fazendo revisão humana final.
3) Cada regra cobre falhas que as outras não cobrem: o sucesso encerra quando a meta é atingida; o limite de iterações impede ciclos infinitos mesmo se cada um for barato; o orçamento impede gastos descontrolados mesmo em poucas iterações caras. Para detectar um agente em círculos, adicionam-se detecção de estagnação (mesmo erro repetido N vezes ou diff que não muda), detecção de regressão (falhas aumentando), limite de tempo de relógio e limite de escopo da mudança.
