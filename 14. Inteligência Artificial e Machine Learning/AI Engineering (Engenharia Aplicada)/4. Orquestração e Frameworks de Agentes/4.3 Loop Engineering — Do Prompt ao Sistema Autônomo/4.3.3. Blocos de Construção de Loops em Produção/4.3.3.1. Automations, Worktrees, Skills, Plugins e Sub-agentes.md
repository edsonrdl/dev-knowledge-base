### Blocos de Construção de Loops em Produção — Automations, Worktrees, Skills, Plugins/Connectors e Sub-agentes

O tópico 4.3.2.1 mostrou o **ciclo básico** de um loop confiável: gatilho, meta verificável, verificador e regras de parada. Esse ciclo, sozinho, serve para um experimento. Em **produção** (loops que rodam toda semana, em vários repositórios, sem ninguém olhando) surgem problemas novos: *de onde vem o trabalho? onde o agente trabalha sem estragar nada? como ele lembra das convenções do projeto? como se conecta aos sistemas reais? quem confere o trabalho de forma independente?*

Loops maduros resolvem isso com **cinco blocos de construção** acrescentados ao ciclo agir → observar → decidir:

```
                        ┌──────────────── LOOP DE PRODUÇÃO ────────────────┐
  [1] AUTOMATIONS ─────►│                                                   │
  (descobrem trabalho)  │   ciclo básico:  agir ─► observar ─► decidir      │
                        │        │                                          │
  [2] WORKTREES ───────►│   executa em espaço ISOLADO por execução          │
  (isolamento)          │        │                                          │
  [3] SKILLS ──────────►│   carrega conhecimento PERSISTENTE do projeto     │
  (memória do ofício)   │        │                                          │
  [4] PLUGINS/CONNECT. ►│   acessa sistemas reais (via MCP)                 │
  (integrações)         │        │                                          │
  [5] SUB-AGENTES ─────►│   verificação INDEPENDENTE do trabalho            │
  (revisão externa)     └───────────────────────────────────────────────────┘
```

> [!note] Rótulos de ferramentas
> Os cinco blocos descrevem **funções**. Cada ferramenta (harnesses como Claude Code e Cursor, SDKs de agentes, plataformas de CI) os implementa com nomes e recursos próprios, e eles evoluem rápido. Os exemplos abaixo são ilustrativos: confirme os recursos na documentação da ferramenta que você usa.

**Analogia:** uma equipe de manutenção predial. As **automations** são a ronda programada que descobre o que precisa de reparo; os **worktrees** são as bancadas separadas onde cada reparo é feito sem bagunçar o prédio; as **skills** são os manuais da casa; os **plugins/connectors** são as chaves e acessos aos sistemas; os **sub-agentes** são o inspetor independente que confere o serviço.

## 1. Automations (descoberta de trabalho agendada)

### O que são

Mecanismos que **encontram e iniciam trabalho por conta própria**: tarefas agendadas e reações a eventos que varrem o ambiente, identificam o que merece atenção e disparam um loop para cada item. Na prática, são a implementação operacional do **trigger** (4.3.2.1), com um passo a mais: **descobrir** o que fazer.

```
Automation (toda noite, 03:00)
   │
   ├─ varre: issues rotuladas "bom-para-agente", testes instáveis, PRs com revisão pendente,
   │         dependências desatualizadas, alertas de segurança abertos
   │
   ├─ prioriza e filtra (limite: no máximo 5 itens por noite)
   │
   └─ para cada item ─► dispara um loop isolado (worktree próprio), com meta e verificador próprios
```

### Tipos comuns

| Automation | Descoberta | Loop disparado |
|---|---|---|
| **Triagem de issues** | Issues novas sem rótulo | Classificar, pedir informação faltante, sugerir correção |
| **Manutenção de dependências** | Pacotes com versão nova ou CVE | Atualizar, rodar testes, abrir PR |
| **Saúde do CI** | Testes instáveis (*flaky*) e falhas recorrentes | Investigar, estabilizar, propor correção |
| **Revisão de PRs** | PR aberto/atualizado | Revisão automática de estilo, bugs e testes faltantes |
| **Dívida técnica** | Relatório do linter/cobertura | Correções pequenas e seguras em lote |
| **Documentação** | Código alterado sem doc atualizada | Atualizar e validar exemplos |

### Boas práticas

| Prática | Motivo |
|---|---|
| **Limitar volume** (itens por execução, concorrência) | Evita avalanche de PRs e custos |
| **Idempotência e deduplicação** | Não reabrir trabalho já feito ou em andamento (marcar itens "em processamento") |
| **Descoberta barata, execução cara** | A varredura deve usar consultas simples/regras; só gaste agente no que passou o filtro |
| **Priorização explícita** | Severidade, antiguidade e custo estimado |
| **Evitar cascata** | A automation não deve reagir ao trabalho do próprio agente |
| **Relatório de execução** | Resumo do que foi descoberto, iniciado, concluído e falho |
| **Kill switch** | Poder pausar a automation inteira |

## 2. Worktrees (espaços de trabalho isolados por execução)

### O problema que resolvem

Se vários loops editam **o mesmo diretório** ao mesmo tempo, um sobrescreve o outro; e se um agente comete um erro, ele **contamina** o trabalho de quem está usando aquele repositório. Cada execução precisa de seu **próprio espaço**.

### O que são

O termo vem do **`git worktree`**: um recurso do Git que cria **vários diretórios de trabalho independentes** a partir do **mesmo repositório**, cada um em **sua própria branch**, compartilhando o histórico (sem clonar tudo de novo).

```
repositório principal  (você trabalha aqui, intocado)
   │
   ├── git worktree add ../loop-123-deps   -b agente/atualiza-deps     ← execução 1
   ├── git worktree add ../loop-124-flaky  -b agente/corrige-flaky     ← execução 2 (em paralelo)
   └── git worktree add ../loop-125-docs   -b agente/atualiza-docs     ← execução 3 (em paralelo)

Cada agente edita só o seu diretório/branch. Falhou? Descarte o worktree, nada foi afetado.
```

```bash
# Criar um espaço isolado para uma execução
git worktree add ../exec-4821 -b agente/exec-4821 origin/main

# ... o agente trabalha em ../exec-4821, o verificador roda lá ...

# Sucesso → abre PR a partir da branch;  Falha → descarta tudo
git worktree remove ../exec-4821 --force
git branch -D agente/exec-4821
```

### Variações de isolamento (do mais leve ao mais forte)

| Nível | Mecanismo | Protege contra |
|---|---|---|
| **Branch + worktree** | `git worktree` | Conflitos entre execuções e contaminação do seu trabalho |
| **Contêiner** (Docker) | Ambiente de execução isolado por execução | Dependências conflitantes, efeitos no sistema de arquivos do host |
| **Sandbox / microVM** | Isolamento forte (rede restrita, sem segredos) | **Código malicioso ou perigoso** gerado/executado pelo agente |
| **Clone efêmero em CI/nuvem** | Máquina descartável por execução | Tudo acima + escala |

### Por que isso é essencial para loops

1. **Paralelismo seguro:** N loops simultâneos sem interferência.
2. **Reversibilidade:** ações do agente ficam confinadas; descartar é trivial (princípio central: loops devem ser **reversíveis**).
3. **Rastreabilidade:** cada execução tem sua branch, diffs e histórico, ligados ao ID da execução.
4. **Segurança:** o agente não toca no checkout do desenvolvedor nem na branch principal.
5. **Reprodutibilidade:** cada execução parte de um commit conhecido.

### Cuidados

| Cuidado | Detalhe |
|---|---|
| **Dependências e estado fora do Git** | Um worktree compartilha o repositório, mas não `node_modules`, caches, bancos de dados locais nem portas; use contêineres ou instalação por worktree |
| **Limpeza** | Remover worktrees e branches de execuções antigas (acumulam e ocupam disco) |
| **Segredos** | Não copie `.env` de produção para o espaço do agente |
| **Branches protegidas** | O agente nunca faz *push* direto na principal: apenas abre PR |
| **Conflitos entre execuções** | Dois loops mexendo nos mesmos arquivos geram conflitos de merge; reduza o escopo ou serialize |

## 3. Skills (conhecimento persistente do projeto)

### O problema

Um agente começa cada execução **sem memória**. Sem orientação, ele redescobre as convenções do projeto, repete erros já conhecidos e usa o comando errado de teste. Em loops de produção, isso significa **mais iterações, mais custo e resultados inconsistentes**.

### O que são

**Pacotes de conhecimento reutilizáveis** (instruções, procedimentos, exemplos e scripts) que o agente **carrega sob demanda** e que **persistem entre execuções**. Representam a **memória procedural** do projeto (4.2.2.1): *como fazemos as coisas aqui*.

```
.agente/skills/
   ├── rodar-testes/            "Como rodar a suíte; quais testes são lentos; como interpretar falhas"
   │     └── SKILL.md
   ├── convencoes-api/          "Padrão de endpoints, erros, versionamento; exemplos"
   │     └── SKILL.md
   ├── migracao-banco/          "Procedimento seguro de migrations; o que NUNCA fazer"
   │     ├── SKILL.md
   │     └── scripts/validar_migration.sh
   └── liberar-versao/          "Checklist de release"
         └── SKILL.md
```

Um exemplo de skill (formato ilustrativo):

```markdown
---
name: rodar-testes
description: Como executar e interpretar os testes deste repositório. Use ao verificar qualquer mudança.
---

# Rodar testes
- Comando rápido (unitários): `make test-unit` (~40 s). Comando completo: `make test` (~12 min).
- Falhas conhecidas e instáveis: `test_relatorio_mensal` (flaky, reexecute 1x antes de investigar).
- NUNCA edite arquivos em `tests/` para fazer um teste passar; corrija o código de produção.
- Saída de falha: procure a primeira linha `FAILED`; o traceback relevante está nas últimas 30 linhas.
```

### Skills × outros mecanismos de contexto

| Mecanismo | Quando é carregado | Uso |
|---|---|---|
| **Arquivo de instruções do projeto** (AGENTS.md / CLAUDE.md etc.) | **Sempre**, no início | Regras gerais curtas e essenciais |
| **Skills** | **Sob demanda**, quando a descrição casa com a tarefa | Procedimentos específicos e detalhados, sem poluir o contexto sempre |
| **Prompt da tarefa** | Em cada execução | A meta específica |
| **Memória de longo prazo** (Mem0/Zep) | Por recuperação | Fatos sobre usuários e episódios |

A vantagem do carregamento **sob demanda** (*progressive disclosure*): só o nome e a descrição entram no contexto de início; o conteúdo completo é lido apenas quando relevante, economizando tokens (1.1.1.1).

### Boas práticas

| Prática | Motivo |
|---|---|
| **Descrições claras de "quando usar"** | O agente decide pela descrição |
| **Skills pequenas e focadas** | Contexto enxuto e fácil de manter |
| **Registrar aprendizados de falhas** | "Da última vez, o loop falhou por X; evite Y": o loop **melhora** com o tempo |
| **Versionar no repositório** | Revisão por pares, histórico e consistência entre execuções |
| **Incluir scripts executáveis** | Procedimentos determinísticos > instruções em prosa |
| **Revisar como código** | Skills erradas ou maliciosas **propagam erros** a todas as execuções |
| **Tratar skills de terceiros como código não confiável** | Podem conter instruções maliciosas |

## 4. Plugins e Connectors (integrações via MCP)

### O que são

Os **braços do agente**: integrações que conectam o loop aos **sistemas reais** da organização (repositório, CI, gestão de tickets, monitoramento, bancos de dados, chat). Em ecossistemas atuais, muitos conectores são **servidores MCP** (4.1.2.1); *plugins* costumam empacotar **conectores + skills + comandos** em uma unidade instalável.

```
Loop de correção de incidentes
   ├─ connector GitHub        → ler issues, abrir PRs, comentar
   ├─ connector CI            → ler logs de pipeline, reexecutar jobs
   ├─ connector Observabilidade → consultar métricas e traces
   ├─ connector Tickets       → criar/atualizar chamados
   └─ connector Chat          → notificar o time com o resumo
```

### Por que são essenciais para loops

- **Gatilhos e descoberta** dependem de eventos desses sistemas.
- **Verificação** frequentemente usa dados reais (resultados de CI, métricas).
- **Entrega** do resultado (PR, comentário, notificação) acontece neles.

### Segurança: o ponto mais sensível dos cinco

| Princípio | Aplicação em loops |
|---|---|
| **Menor privilégio** | Credenciais de escopo mínimo **por loop**: leitura onde bastar; escrita só no necessário |
| **Separar leitura e escrita** | Conectores de leitura liberados; escrita com controles extras (HITL, branch protegida) |
| **Sem segredos de produção** no ambiente do agente | Mitiga vazamento por erro ou prompt injection |
| **Tratar saídas de conectores como dados não confiáveis** | Issues, e-mails e páginas podem conter **prompt injection** |
| **Evitar a "tríade letal"** | Dados privados + conteúdo não confiável + canal para enviar dados para fora **no mesmo loop** |
| **Lista de permitidos** (allow-list) de ferramentas por loop | Menos superfície de ataque e menos tokens de descrição de ferramentas |
| **Auditoria** de cada chamada | Quem (qual execução), o quê, quando |
| **Fixar versões** de plugins/servidores | Cadeia de suprimentos |

## 5. Sub-agentes (verificação independente do trabalho)

### O que são

**Agentes auxiliares com contexto e instruções próprios**, acionados pelo agente principal (ou pelo orquestrador) para tarefas específicas. No contexto de loops, o uso mais valioso é a **verificação independente**: um sub-agente que **revisa o trabalho do agente principal sem ter participado dele**.

### Por que a independência importa

Lembre-se da regra de ouro (4.3.2.1): **quem escreveu a solução não deve julgar sozinho a própria qualidade**. O agente autor tende a concordar com o próprio raciocínio. Um sub-agente revisor com **contexto limpo**, outro papel e, se possível, outro modelo, enxerga o resultado "de fora".

```
Agente principal:  escreve a correção ─────────────────┐
                                                        ▼ (apenas o RESULTADO: diff + meta; sem o raciocínio)
Sub-agente revisor: contexto limpo + rubrica ──► aprova / aponta problemas ──► volta ao principal
Sub-agente de testes: escreve testes adicionais/casos de borda ──► verificador roda
```

### Usos típicos de sub-agentes em loops

| Sub-agente | Função |
|---|---|
| **Revisor de código** | Procura bugs, regressões, violações de convenção, riscos de segurança no diff |
| **Verificador/auditor** | Confere se a meta realmente foi cumprida (checa evidências, não só o "passou") |
| **Escritor de testes (adversarial)** | Tenta **quebrar** a solução com casos de borda (testes que o autor não escreveu) |
| **Pesquisador/explorador** | Lê muito código/documentação em um contexto separado e devolve **só o resumo** (preserva o contexto do principal) |
| **Especialista de domínio** | Segurança, desempenho, acessibilidade, conformidade |
| **Resumidor de resultados** | Prepara a descrição do PR e o relatório da execução |

### Duas vantagens além da independência

| Vantagem | Explicação |
|---|---|
| **Isolamento de contexto** | Tarefas que lêem muito material (logs, base de código) rodam em outro contexto e devolvem **resumos curtos**, mantendo limpo o contexto do agente principal (menos custo, menos *lost in the middle*) |
| **Paralelismo** | Vários sub-agentes trabalham ao mesmo tempo em partes independentes |

### Cuidados

| Cuidado | Detalhe |
|---|---|
| **Sub-agente não é verificador determinístico** | Revisão por modelo é **camada adicional**, não substitui testes e linter |
| **Revisores concordam com demais** | Dê rubrica específica, peça evidências e **instrua a procurar problemas** (não só "confirmar") |
| **Contaminação de contexto** | Não passe o raciocínio do autor ao revisor; só resultado e meta |
| **Custo multiplicado** | Cada sub-agente é mais chamadas; limite quantidade e profundidade |
| **Recursão descontrolada** | Sub-agentes que criam sub-agentes... imponha limite de profundidade e orçamento compartilhado |
| **Permissões** | Revisor de leitura não precisa de permissão de escrita |

## Como os cinco blocos se combinam

```
 ┌─ AUTOMATION (03:00) descobre 3 itens ─────────────────────────────────────────────────┐
 │                                                                                         │
 │   item A ─► WORKTREE exec-A ─► agente carrega SKILLS (rodar-testes, convencoes-api)     │
 │                                  │                                                      │
 │                                  ├─ usa CONNECTORS (GitHub, CI) com credenciais mínimas │
 │                                  ├─ ciclo: agir ─► VERIFICADOR determinístico ─► repetir│
 │                                  │          (stop rules: sucesso / 12 iter / US$ 10)    │
 │                                  └─ SUB-AGENTE revisor (contexto limpo) avalia o diff   │
 │                                                      │                                  │
 │                                                      ▼                                  │
 │                          PR em rascunho + relatório ─► HUMANO revisa ─► merge           │
 └─────────────────────────────────────────────────────────────────────────────────────────┘
```

| Bloco | Pergunta que responde | Se faltar... |
|---|---|---|
| **Automations** | De onde vem o trabalho? | O loop depende de alguém lembrar de dispará-lo |
| **Worktrees** | Onde o agente trabalha sem causar estrago? | Conflitos, contaminação e execuções irreversíveis |
| **Skills** | Como o agente conhece nossas convenções? | Mais iterações, custo e resultados inconsistentes |
| **Plugins/Connectors** | Como o agente toca os sistemas reais? | O loop não consegue obter dados nem entregar resultados |
| **Sub-agentes** | Quem confere o trabalho de fora? | Autoavaliação enviesada; erros passam |

## Boas práticas para loops em produção

(Complementam as do 4.3.2.1.)

| Prática | Motivo |
|---|---|
| **Comece pelo loop mais simples possível** e acrescente blocos apenas quando a necessidade aparecer | Cada bloco adiciona custo e superfície de falha |
| **Escreva a meta como verificação executável antes de programar o agente** | Garante que há critério objetivo |
| **Teste um único ciclo ação → verificação** antes de adicionar retentativas | Valida o verificador |
| **Nunca rode loop sem supervisão sem as três regras de parada** (sucesso, iterações, orçamento) | Evita loops infinitos e gasto descontrolado |
| **Humano revisa o resultado final** (PR em rascunho, nunca merge automático em código crítico) | Responsabilidade continua humana |
| **Observabilidade por execução**: ID, custo, iterações, causa de parada, diffs, quem aprovou | Auditoria e melhoria contínua |
| **Métricas de saúde do loop**: taxa de sucesso, custo por PR aceito, % de PRs aceitos sem alteração | Mostra se vale a pena e onde ajustar |
| **Revise periodicamente falhas** e transforme aprendizados em skills ou verificadores melhores | O loop evolui |
| **Governança**: quem pode criar loops, com quais credenciais, com que orçamento | Evita "loops fantasmas" caros ou perigosos |
| **Plano de desligamento** (kill switch por loop e global) | Resposta a incidentes |

### Maturidade de um loop (roteiro)

| Nível | Características |
|---|---|
| **0 — Manual** | Humano conduz o agente turno a turno |
| **1 — Loop mínimo** | Script: tarefa + verificador + 3 regras de parada, em branch isolada |
| **2 — Loop confiável** | + feedback acionável, proteção do verificador, logs e métricas |
| **3 — Loop de produção** | + automations, worktrees/contêineres, skills, conectores com menor privilégio |
| **4 — Sistema de loops** | + sub-agentes revisores, paralelismo, governança e painel de custo (caminho natural para Graph Engineering, 4.4) |

## Exemplo prático: "fábrica noturna" de manutenção de um monorrepo

```
AUTOMATION (diária, 02:00):
   varre: 1) alertas de segurança abertos (Dependabot/CVE); 2) testes instáveis do CI nas últimas 24h;
          3) issues com rótulo "agent-ready". Seleciona no máximo 4 itens por noite, por prioridade.

POR ITEM — executado em paralelo, cada um em:
   WORKTREE/contêiner próprio (branch agente/<id>), sem segredos de produção, rede restrita.

   SKILLS carregadas conforme o tipo: "atualizar-dependencias", "estabilizar-teste-flaky", "convencoes-codigo".
   CONNECTORS (MCP) com menor privilégio: GitHub (leitura + abrir PR em fork/branch), CI (leitura de logs).

   LOOP: meta = build + testes + lint verdes, tests/ intactos, diff ≤ 400 linhas;
         verificador determinístico; stop rules: sucesso / 12 iterações / US$ 10 / 60 min / 3 erros idênticos.

   SUB-AGENTES:
      • revisor independente (contexto limpo, rubrica de segurança e estilo) → comentários ao agente principal;
      • escritor de testes adversariais → 5 casos de borda que o autor não considerou.

SAÍDA: PR em rascunho com descrição, evidências (logs antes/depois), custo e iterações.
       Falha → issue com diagnóstico e hipóteses; worktree descartado.

HUMANO: revisa os PRs pela manhã; nada entra na principal sem aprovação.
MÉTRICAS SEMANAIS: 14 execuções → 10 PRs abertos → 8 aceitos sem alteração; custo médio US$ 3,10/PR;
                   2 paradas por estagnação (viram skills novas: "como lidar com migrations de ORM").
```

## Erros comuns e armadilhas

- **Automation sem limite de volume**: avalanche de PRs, custo e fadiga de revisão.
- **Várias execuções no mesmo diretório**: conflitos e contaminação; sem worktree/contêiner por execução.
- **Worktree sem dependências/estado isolados**: compartilhar banco local, portas e caches entre execuções.
- **Skills desatualizadas, vagas ou maliciosas**: propagam erros a todas as execuções.
- **Skills gigantes carregadas sempre**: inflam o contexto; prefira carregamento sob demanda.
- **Credenciais amplas nos conectores** (admin, escrita em produção).
- **Não tratar saídas de conectores como dados não confiáveis**: prompt injection via issues e e-mails.
- **Revisor com o mesmo contexto do autor** ou que só "confirma".
- **Tratar sub-agente como verificador definitivo** no lugar de testes determinísticos.
- **Sub-agentes sem limite** de profundidade e orçamento.
- **Complexidade prematura**: montar os cinco blocos antes de provar um ciclo simples.
- **Merge automático** sem revisão humana em código crítico.
- **Não limpar** worktrees, branches e execuções antigas.

## 🧩 Quiz de Fixação

1. Quais são os cinco blocos que um loop de produção acrescenta ao ciclo básico e que função cada um cumpre?
2. Por que o worktree (ou outro isolamento) é considerado essencial e que cuidado adicional ele exige?
3. Por que um sub-agente revisor deve ter contexto limpo e por que ele não substitui o verificador determinístico?

**Respostas:**
1) Automations (descobrem e disparam trabalho de forma agendada ou por eventos), Worktrees (espaços isolados por execução), Skills (conhecimento persistente do projeto, carregado sob demanda), Plugins/Connectors (integrações com sistemas reais, frequentemente via MCP) e Sub-agentes (verificação independente e isolamento de contexto).
2) Permite paralelismo seguro, reversibilidade (descartar a execução sem afetar nada), rastreabilidade por branch e proteção do trabalho principal. Exige cuidado com o que o worktree não isola (dependências, caches, bancos e portas locais, segredos), com a limpeza de worktrees antigos e com não permitir push direto à branch principal.
3) Porque quem escreveu a solução tende a concordar com o próprio raciocínio; um revisor com contexto limpo (recebe só o resultado e a meta, com rubrica específica, de preferência outro modelo) enxerga o trabalho de fora. Mas ele é baseado em modelo e portanto não determinístico: é uma camada adicional de verificação, não substitui testes, build e linter, que continuam como critério objetivo de sucesso.
