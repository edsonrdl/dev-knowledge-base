### MCP (Model Context Protocol), A2A (Agent-to-Agent) e OpenAI Responses API

Cada agente precisa de três tipos de conexão: com **ferramentas e dados** (APIs, bancos, arquivos), com **outros agentes** e com a **plataforma que o executa** (estado, histórico, ferramentas embutidas). Sem padrões, cada integração é artesanal: N modelos × M ferramentas = N×M conectores. Este arquivo apresenta três peças que tentam padronizar essas conexões: **MCP** (agente ↔ ferramentas), **A2A** (agente ↔ agente) e a **Responses API da OpenAI** (agente ↔ plataforma).

> [!warning] Área em evolução rápida
> Protocolos e APIs de agentes mudam muito: versões da especificação, nomes de campos, governança dos projetos e recursos novos aparecem em ciclos de meses. Use este arquivo para entender **os conceitos e as fronteiras entre os protocolos**, e confirme a especificação e a documentação atuais antes de implementar.

---

## O problema da integração N×M

```
SEM PADRÃO:                                       COM PADRÃO (MCP):

 Claude ──┬── conector Slack                       Claude ─┐                  ┌─ servidor MCP Slack
 GPT ─────┼── conector GitHub                      GPT ────┼── protocolo ─────┼─ servidor MCP GitHub
 Gemini ──┼── conector Postgres                    Gemini ─┘   comum          └─ servidor MCP Postgres
          └── ... (N × M integrações)                          (N + M integrações)
```

**Analogia:** é o USB-C. Antes, cada aparelho tinha um carregador próprio; com uma porta padrão, qualquer dispositivo se conecta a qualquer acessório. MCP é a "porta USB-C" entre agentes e ferramentas.

### Mapa dos três protocolos

```
                    ┌──────────────────────────┐
                    │   AGENTE (LLM + lógica)   │
                    └─────┬──────────┬─────────┬┘
                          │          │         │
        MCP               │   A2A    │         │  Responses API
   (ferramentas, dados)   │ (outros  │         │  (plataforma: estado,
          │               │ agentes) │         │   ferramentas embutidas)
          ▼               ▼          ▼         ▼
   [BD] [APIs] [arquivos]   [Agente B]   [Agente C]     [OpenAI]
```

| Protocolo | Conecta | Origem | Pergunta que responde |
|---|---|---|---|
| **MCP** | Agente ↔ ferramentas e fontes de dados | Anthropic (2024), hoje padrão aberto amplamente adotado | "Como o agente descobre e usa ferramentas e dados?" |
| **A2A** | Agente ↔ agente (inclusive de fornecedores diferentes) | Google (2025), projeto aberto | "Como agentes autônomos descobrem e colaboram entre si?" |
| **Responses API** | Aplicação ↔ plataforma da OpenAI (modelos + ferramentas + estado) | OpenAI (2025) | "Como construir agentes com estado e ferramentas gerenciados pela plataforma?" |

Complementares, não concorrentes: MCP e A2A resolvem **problemas diferentes**.

## 1. MCP — Model Context Protocol

### O que é

**Protocolo aberto** que padroniza como aplicações de IA (**hosts/clientes**: Claude Desktop, Claude Code, IDEs, agentes próprios) se conectam a **servidores** que expõem **ferramentas, dados e prompts**. Usa **JSON-RPC 2.0** sobre um transporte (local ou HTTP).

### Arquitetura

```
┌────────────────────────── HOST (aplicação de IA) ──────────────────────────┐
│   LLM + lógica do agente                                                    │
│        │                                                                    │
│   ┌────▼─────┐   ┌──────────┐   ┌──────────┐                               │
│   │ CLIENTE  │   │ CLIENTE  │   │ CLIENTE  │   (1 cliente MCP por servidor) │
│   │ MCP  #1  │   │ MCP  #2  │   │ MCP  #3  │                               │
│   └────┬─────┘   └────┬─────┘   └────┬─────┘                               │
└────────┼──────────────┼──────────────┼─────────────────────────────────────┘
         │ JSON-RPC     │              │
   ┌─────▼─────┐  ┌─────▼─────┐  ┌─────▼─────┐
   │ Servidor  │  │ Servidor  │  │ Servidor  │
   │ MCP:      │  │ MCP:      │  │ MCP:      │
   │ Arquivos  │  │ Postgres  │  │ GitHub    │
   └───────────┘  └───────────┘  └───────────┘
```

| Papel | Função |
|---|---|
| **Host** | A aplicação de IA que o usuário usa; decide a política e orquestra |
| **Cliente MCP** | Componente dentro do host que mantém a conexão com **um** servidor |
| **Servidor MCP** | Programa que **expõe capacidades** (ferramentas, recursos, prompts) via protocolo |

### As primitivas que o servidor expõe

| Primitiva | Quem controla | O que é | Exemplo |
|---|---|---|---|
| **Tools (ferramentas)** | O **modelo** decide chamar | Funções executáveis, com schema de entrada | `criar_issue(titulo, corpo)`, `executar_sql(consulta)` |
| **Resources (recursos)** | A **aplicação** decide incluir | Dados de leitura identificados por URI | `file:///relatorio.pdf`, `db://clientes/42` |
| **Prompts** | O **usuário** escolhe | Modelos de prompt reutilizáveis | "/revisar-pr", "/resumo-semanal" |

E primitivas do **lado do cliente** (o servidor pode solicitar): **Sampling** (pedir uma geração ao LLM do host), **Roots** (diretórios/escopos acessíveis) e **Elicitation** (pedir informação ao usuário).

### Transportes

| Transporte | Uso |
|---|---|
| **stdio** | Servidor local como subprocesso (padrão em desktops/IDEs): simples, sem rede |
| **Streamable HTTP** | Servidor remoto via HTTP (com streaming): multiusuário e empresarial; autenticação via **OAuth 2.1** na especificação |

(Transportes e detalhes de autorização evoluíram entre versões da especificação; verifique a versão vigente.)

### Ciclo de vida de uma chamada

```
1. Inicialização:  cliente ↔ servidor negociam versão e capacidades.
2. Descoberta:     cliente chama  tools/list  → recebe nomes, descrições e JSON Schemas.
3. Decisão:        o LLM (com as descrições das ferramentas no contexto) escolhe uma ferramenta.
4. Execução:       cliente chama  tools/call {name, arguments}  → servidor executa.
5. Resultado:      servidor devolve conteúdo (texto, imagem, dados) ao cliente → vai ao LLM.
```

```json
// Requisição JSON-RPC (cliente → servidor)
{ "jsonrpc": "2.0", "id": 7, "method": "tools/call",
  "params": { "name": "executar_sql",
              "arguments": { "consulta": "SELECT count(*) FROM pedidos WHERE status = 'aberto'" } } }

// Resposta (servidor → cliente)
{ "jsonrpc": "2.0", "id": 7,
  "result": { "content": [ { "type": "text", "text": "1284" } ], "isError": false } }
```

### Criando um servidor MCP (Python, SDK oficial)

```python
from mcp.server.fastmcp import FastMCP

mcp = FastMCP("estoque")                            # nome do servidor

@mcp.tool()
def consultar_estoque(sku: str) -> str:
    """Retorna a quantidade em estoque de um SKU. Use quando o usuário perguntar sobre disponibilidade."""
    qtd = banco.consultar("SELECT qtd FROM estoque WHERE sku = %s", (sku,))   # parametrizado!
    return f"SKU {sku}: {qtd} unidades"

@mcp.resource("catalogo://{categoria}")
def catalogo(categoria: str) -> str:
    """Lista produtos de uma categoria."""
    return listar_produtos(categoria)

if __name__ == "__main__":
    mcp.run()                                       # transporte stdio por padrão
```

Linha a linha: a **docstring** vira a descrição que o LLM lê para decidir quando usar a ferramenta (escreva-a como instrução); os **tipos** viram JSON Schema automaticamente; `@mcp.resource` expõe dados somente leitura por URI.

Configuração típica no host (ex.: Claude Desktop/Claude Code) para registrar o servidor:

```json
{ "mcpServers": { "estoque": { "command": "python", "args": ["servidor_estoque.py"] } } }
```

### Ecossistema

Há **servidores prontos** (sistema de arquivos, Git/GitHub, bancos de dados, Slack, Google Drive, navegadores, busca, etc.), **SDKs** (Python, TypeScript, Java, C#, Kotlin e outros) e suporte em IDEs e frameworks de agentes (LangChain/LangGraph, OpenAI Agents SDK, etc.). Um registro de servidores ajuda a descobri-los.

### Segurança em MCP (crítico)

| Risco | Descrição | Mitigação |
|---|---|---|
| **Prompt injection via ferramentas/recursos** | Conteúdo retornado (página web, e-mail, issue) pode conter instruções maliciosas | Tratar saídas como **dados não confiáveis**; confirmação humana em ações sensíveis |
| **Tool poisoning** | Descrição de ferramenta maliciosa instrui o modelo a vazar dados | Usar servidores **confiáveis**, revisar descrições, fixar versões |
| **Permissões excessivas** | Servidor com acesso amplo (escrita, produção) | **Menor privilégio**: credenciais restritas, somente leitura quando possível |
| **Combinação perigosa** ("lethal trifecta") | Dados privados + conteúdo não confiável + capacidade de enviar dados para fora no mesmo agente | Separar capacidades; bloquear exfiltração |
| **Servidores remotos sem autenticação** | Acesso indevido | OAuth, escopos mínimos, TLS |
| **Cadeia de suprimentos** | Servidores de terceiros com código malicioso | Auditar, isolar em contêiner, lista de permitidos |
| **Execução local arbitrária** | Servidor stdio roda comandos na sua máquina | Sandbox, não executar servidores desconhecidos |

> [!warning] MCP expõe ações reais
> Conectar muitas ferramentas amplia a **superfície de ataque** e consome **contexto** (cada descrição de ferramenta ocupa tokens, tópico 1.1.1.1). Conecte apenas o necessário.

## 2. A2A — Agent-to-Agent Protocol

### O que é

Protocolo aberto (lançado pelo Google em 2025, com apoio de diversas empresas e hoje sob governança de fundação aberta) para que **agentes autônomos**, construídos por **fornecedores e frameworks diferentes**, **descubram uns aos outros, negociem e colaborem em tarefas**, sem expor seu funcionamento interno (memória, ferramentas, prompts).

**A distinção essencial com o MCP:**

```
MCP:  agente ──usa──► FERRAMENTA     (função com entrada/saída bem definida; passiva)
A2A:  agente ──delega a──► AGENTE    (entidade autônoma, com raciocínio próprio; pode levar tempo,
                                      pedir esclarecimentos, devolver resultados parciais)
```

**Analogia:** MCP é usar uma calculadora, um grampeador, um banco de dados. A2A é **delegar uma tarefa a um colega**: você descreve o objetivo, ele trabalha por conta própria, pode voltar com perguntas e entrega o resultado depois.

### Conceitos centrais

| Conceito | Descrição |
|---|---|
| **Agent Card** | Documento JSON (publicado em local conhecido, ex.: `/.well-known/agent-card.json`) que **descreve o agente**: nome, descrição, endpoint, habilidades (*skills*), formatos aceitos, requisitos de autenticação |
| **Cliente A2A** | O agente que **delega** a tarefa |
| **Servidor A2A (agente remoto)** | O agente que **recebe e executa** |
| **Task (tarefa)** | Unidade de trabalho com **ciclo de vida** (enviada, em andamento, aguardando entrada, concluída, falha, cancelada) |
| **Message / Part** | Troca de mensagens com partes tipadas (texto, arquivos, dados estruturados) |
| **Artifact** | Resultado produzido pela tarefa (relatório, arquivo, JSON) |

```json
// Agent Card (exemplo ilustrativo)
{
  "name": "Agente de Conformidade Fiscal",
  "description": "Valida notas fiscais e calcula tributos conforme a legislação vigente.",
  "url": "https://agentes.empresa.com/fiscal",
  "skills": [
    { "id": "validar_nf", "name": "Validar nota fiscal",
      "description": "Recebe uma NF-e (XML) e retorna inconsistências." }
  ],
  "authentication": { "schemes": ["oauth2"] }
}
```

### Fluxo típico

```
Agente Cliente                                         Agente Remoto (Fiscal)
     │  1. Descoberta: GET /.well-known/agent-card.json ───►│
     │◄──────────── Agent Card (skills, auth) ──────────────│
     │  2. Envia tarefa (mensagem com NF-e anexa) ─────────►│
     │◄──────── status: "working" (streaming/SSE) ──────────│
     │◄──────── status: "input-required": "qual o regime tributário?" 
     │  3. Responde ao pedido de informação ───────────────►│
     │◄──────── status: "completed" + Artifact (relatório) ─│
```

Características do protocolo (baseado em padrões web existentes): **HTTP, JSON-RPC e Server-Sent Events** para streaming; suporte a **tarefas de longa duração** e a **notificações assíncronas** (webhooks); **opacidade** (o agente remoto não revela suas entranhas).

### Quando A2A faz sentido

| Cenário | A2A? |
|---|---|
| Agentes de **times/empresas/fornecedores diferentes** precisam colaborar | **Sim** |
| **Agente especialista** exposto como serviço (fiscal, jurídico, logística) para vários clientes | Sim |
| Tarefas **longas e assíncronas**, com troca de esclarecimentos | Sim |
| Vários agentes **dentro do mesmo processo/framework** (CrewAI, LangGraph) | Normalmente **não precisa**: comunicação interna do framework basta |
| Apenas chamar uma função/API | Não: use MCP (ou chamada direta) |

> O A2A ainda é **mais novo e menos difundido** que o MCP. Avalie maturidade, suporte nos seus frameworks e a real necessidade de interoperar entre fronteiras organizacionais antes de adotá-lo.

## 3. OpenAI Responses API

### O que é

A **Responses API** (lançada pela OpenAI em 2025) é a interface recomendada pela empresa para construir aplicações e agentes com seus modelos. Ela une o que antes estava dividido entre **Chat Completions** (simples, sem estado) e **Assistants API** (com estado, mais pesada) em uma API **mais simples, com estado opcional gerenciado pela plataforma** e **ferramentas embutidas**.

> [!note] Escopo
> Este protocolo é **específico de um fornecedor** (OpenAI) — diferente do MCP e do A2A, que são abertos e multi-fornecedor. Conceitos semelhantes existem em outras plataformas (ex.: ferramentas gerenciadas e gerenciamento de estado em outras APIs); a Responses API é um exemplo representativo.

### Ideias principais

| Recurso | Descrição |
|---|---|
| **Estado gerenciado pela plataforma** | Em vez de reenviar todo o histórico, você passa `previous_response_id`; a plataforma recupera a conversa (reduz código e payload) |
| **Itens tipados de entrada/saída** | A resposta é uma lista de itens (mensagens, chamadas de ferramenta, raciocínio), não só texto |
| **Ferramentas embutidas** | Busca na web, busca em arquivos (*file search*, RAG gerenciado sobre *vector stores*), execução de código (*code interpreter*), uso de computador, geração de imagens |
| **Function calling** | Suas funções, com JSON Schema (igual ao padrão de tool calling) |
| **MCP remoto** | Conecta a servidores MCP remotos como ferramenta |
| **Modelos de raciocínio** | Suporte nativo, com controle de esforço (1.1.3.1) e preservação do raciocínio entre turnos |
| **Streaming e background mode** | Resposta em fluxo; execução longa em segundo plano |
| **Structured Outputs** | Respostas aderentes a schema (1.2.2.1) |

### Exemplo

```python
from openai import OpenAI
cliente = OpenAI()

# Turno 1: com ferramenta embutida de busca na web
r1 = cliente.responses.create(
    model="gpt-4o",
    input="Quais as novidades da LGPD este ano? Cite as fontes.",
    tools=[{"type": "web_search"}],
)
print(r1.output_text)

# Turno 2: continua a conversa SEM reenviar o histórico
r2 = cliente.responses.create(
    model="gpt-4o",
    previous_response_id=r1.id,                    # estado mantido pela plataforma
    input="Resuma em 3 tópicos para a diretoria.",
)
print(r2.output_text)
```

```python
# Function calling: o modelo devolve um item "function_call"; sua aplicação executa e devolve o resultado
r = cliente.responses.create(
    model="gpt-4o",
    input="Qual o status do pedido 9981?",
    tools=[{
        "type": "function", "name": "consultar_pedido",
        "description": "Consulta o status de um pedido pelo número.",
        "parameters": {"type": "object",
                       "properties": {"numero": {"type": "string"}}, "required": ["numero"]},
    }],
)
```

(Parâmetros, nomes de ferramentas e modelos mudam com frequência; consulte a documentação atual.)

### Trade-offs do estado gerenciado

| Vantagem | Cuidado |
|---|---|
| Menos código e menos dados trafegando | **Lock-in** na plataforma; migrar de fornecedor exige reconstruir o estado |
| Ferramentas prontas (busca, arquivos, código) | Menos **controle** e **transparência** sobre o que entra no contexto |
| Raciocínio preservado entre turnos | **Retenção de dados** na plataforma: avaliar política, região e privacidade (LGPD) |
| Rápido para protótipos | Custo e limites definidos pelo fornecedor |

Há opção de **não armazenar** a conversa no lado do fornecedor (parâmetro de retenção) e de gerenciar o estado você mesmo, quando a conformidade exigir.

### Camadas acima: SDKs de agentes

Fornecedores oferecem **SDKs de agentes** sobre suas APIs (por exemplo, o OpenAI Agents SDK, que adiciona *handoffs* entre agentes, *guardrails* e rastreamento; o Claude Agent SDK, para a família Claude). Eles empacotam o laço agente-ferramenta (ReAct, 4.1.1.1) e a integração com MCP.

## Comparativo e como combinar

| Critério | **MCP** | **A2A** | **Responses API** |
|---|---|---|---|
| **Papel** | Agente ↔ ferramentas/dados | Agente ↔ agente | Aplicação ↔ plataforma OpenAI |
| **Natureza** | Padrão aberto | Padrão aberto | API proprietária |
| **Interação típica** | Chamada de função (síncrona, bem definida) | Delegação de tarefa (assíncrona, com ciclo de vida) | Requisição/resposta com estado e ferramentas gerenciadas |
| **Descoberta** | `tools/list`, `resources/list` | **Agent Card** | Definição das ferramentas na requisição |
| **Estado** | No host/servidor | Tarefa com status | **Plataforma** (previous_response_id) |
| **Opacidade** | Ferramentas expõem schema | Agente remoto é **opaco** | Modelo é caixa-preta; ferramentas gerenciadas |
| **Maturidade/adoção** | **Ampla** | Em crescimento | Ampla no ecossistema OpenAI |
| **Principal risco** | Prompt injection, permissões excessivas | Confiança entre agentes, autenticação | Lock-in e retenção de dados |

### Arquitetura combinada

```
                        Usuário
                           │
                    ┌──────▼───────┐
                    │ AGENTE PRINCIPAL │ (modelo via Responses API, ou outro)
                    └───┬─────────┬────┘
        MCP (ferramentas)│         │ A2A (delegar tarefa)
          ┌──────────────▼─┐   ┌───▼─────────────────┐
          │ Servidores MCP │   │ Agente de Conformidade│ (outra empresa/framework)
          │ BD, arquivos,  │   │  └─ usa seus próprios │
          │ tickets...     │   │     servidores MCP    │
          └────────────────┘   └───────────────────────┘
```

O agente de conformidade, por sua vez, usa **suas próprias ferramentas via MCP**, sem expô-las ao cliente: o A2A esconde essa complexidade.

### Árvore de decisão

```
Preciso que o agente...
 ├─ chame funções/APIs/dados (com schema claro)        ──► MCP (ou tool calling direto)
 ├─ delegue trabalho a OUTRO agente autônomo
 │    ├─ dentro do mesmo framework/processo            ──► mecanismo nativo do framework
 │    └─ de outra equipe/empresa/tecnologia            ──► A2A
 └─ tenha estado e ferramentas gerenciadas pela plataforma ──► Responses API (ou equivalente do fornecedor)
```

## Exemplo prático: assistente corporativo de operações

```
Objetivo: assistente que consulta o ERP, abre chamados e pede análise fiscal a um agente externo.

1. MCP: servidores internos expõem
     • erp  → tools: consultar_pedido, listar_faturas (somente leitura);
     • itsm → tools: criar_chamado (exige confirmação humana);
     • docs → resources: políticas internas.
2. A2A: o agente fiscal de um parceiro (Agent Card publicado) recebe a NF-e, devolve
        relatório de inconsistências como Artifact; pede "regime tributário" quando falta dado.
3. Plataforma: Responses API com previous_response_id (estado) e MCP remoto; 
        a retenção de dados desativada para conversas com dados pessoais; 
        histórico próprio no banco da empresa para auditoria.
4. Segurança: menor privilégio por servidor; tratar saídas como dados não confiáveis;
        sem combinar leitura de dados privados + conteúdo externo + envio para fora no mesmo agente;
        log de todas as chamadas de ferramenta (quem, o quê, quando).
5. Observabilidade: traces por chamada (domínio 7), custo por tarefa, taxa de sucesso.
```

## Boas práticas

| Prática | Motivo |
|---|---|
| **Poucas ferramentas, bem descritas** | Menos tokens e menos escolhas erradas |
| **Descrições de ferramenta como instruções** (quando usar, quando não usar) | O LLM decide por elas |
| **Menor privilégio** em cada servidor/agente | Contém danos |
| **Confirmação humana** para ações de escrita/irreversíveis | Segurança (HITL, 4.2.2.1) |
| **Tratar toda saída externa como dado** | Defesa contra prompt injection |
| **Fixar versões** de servidores e da especificação | Evita quebras e ataques de cadeia de suprimentos |
| **Registrar e auditar** chamadas | Conformidade e depuração |
| **Abstrair o fornecedor** (camada própria) | Reduz lock-in |
| **Testar com um cliente genérico** (MCP Inspector) | Verifica o servidor isoladamente |

---

## Erros comuns e armadilhas

- **Confundir MCP com A2A**: um é para ferramentas, o outro para colaboração entre agentes.
- **Conectar dezenas de servidores MCP** "por via das dúvidas": contexto inflado e superfície de ataque maior.
- **Confiar em servidores MCP de terceiros** sem auditar.
- **Descrições de ferramenta vagas**: o modelo não sabe quando usá-las.
- **Dar a servidores credenciais de administrador**.
- **Usar A2A dentro do mesmo framework** sem necessidade real.
- **Assumir que o estado na plataforma é privado/ilimitado**: verificar retenção e conformidade.
- **Ignorar o lock-in** da API proprietária.
- **Não registrar as chamadas** de ferramenta e de agentes.
- **Usar a especificação desatualizada**: protocolos mudam; verifique a versão.

## 🧩 Quiz de Fixação

1. Qual problema o MCP resolve e quais as três primitivas que um servidor MCP expõe?
2. Qual a diferença conceitual entre MCP e A2A? Dê um exemplo em que cada um é apropriado.
3. Que vantagem e que risco traz o estado gerenciado pela plataforma na Responses API?

**Respostas:**
1) Resolve o problema de integração N×M entre modelos/aplicações e ferramentas/dados, padronizando a conexão via JSON-RPC (como uma "porta USB-C").
