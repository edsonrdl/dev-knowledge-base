### Componentes de um Grafo de Agentes — Nodes, Edges, State e Conditional Routing

O tópico 4.4.1.1 definiu Graph Engineering como o projeto explícito da topologia de um sistema multi-agente. Aqui abrimos o "kit de construção": os **quatro componentes** que formam qualquer grafo de agentes: **Nodes** (o que executa), **Edges** (como o controle flui), **State** (o que circula) e **Conditional Routing** (quem decide o caminho). Entendê-los bem permite ler, projetar e depurar qualquer sistema desse tipo, em LangGraph ou em qualquer outra ferramenta.

```
                    ┌──────────── STATE (estado compartilhado, tipado) ────────────┐
                    │ { pergunta, plano, evidencias[], rascunho, nota, revisoes }  │
                    └───────▲───────────────▲──────────────────▲────────────────────┘
                            │ lê/atualiza    │                   │
   START ──► [ NODE ] ──edge──► [ NODE ] ──edge condicional──► [ NODE ] ──► END
              agente            função                │ (routing)   humano
                                determinística        └──► [ NODE ] (outro caminho)
```

**Analogia:** um **fluxograma de processo de uma empresa**. Os **nós** são as caixas (departamentos ou tarefas); as **arestas** são as setas (quem passa o trabalho a quem); o **estado** é o **dossiê** que acompanha o processo de mão em mão; o **roteamento condicional** são os losangos de decisão ("valor > R$ 50 mil? → diretoria").

---

## 1. Nodes (Nós)

### O que são

Cada **nó** é uma **unidade de trabalho**: recebe o **estado**, faz algo e devolve **atualizações** do estado. A ideia-chave: **nem todo nó precisa ser um agente de IA.**

### Tipos de nós

| Tipo | O que faz | Exemplo | Usa LLM? |
|---|---|---|---|
| **Agente (LLM)** | Tarefa semântica: interpretar, resumir, redigir, decidir entre opções ambíguas, usar ferramentas em laço (ReAct) | `pesquisador`, `redator`, `analista` | **Sim** |
| **Função determinística** | Lógica de negócio, cálculo, validação, transformação | `validar_cnpj()`, `calcular_imposto()`, `aplicar_limite_de_credito()` | **Não** |
| **Roteador (router)** | Decide o próximo caminho (por regra ou por classificação) | `classificar_pedido` | Opcional |
| **Ferramenta (tool node)** | Executa uma chamada a API/banco/serviço | `consultar_erp`, `buscar_no_vector_db` | Não |
| **Junção (join)** | Combina resultados de ramos paralelos | `consolidar_analises` | Opcional |
| **Checkpoint humano (HITL)** | Pausa e aguarda aprovação/edição humana (4.2.2.1) | `aprovacao_gerente` | Não |
| **Avaliador (evaluator)** | Mede a qualidade de uma saída (por regras, testes ou LLM-juiz) | `avaliar_rascunho` | Opcional |
| **Subgrafo** | Um grafo inteiro dentro de um nó (modularidade) | `time_de_pesquisa` | Misto |

### O princípio de separação: semântico × determinístico

```
Pergunta de projeto para CADA nó:  "isto exige entender linguagem/ambiguidade?"

  SIM ─► nó de LLM          (ex.: "resuma o contrato e destaque riscos")
  NÃO ─► nó de código       (ex.: "o total confere com a soma dos itens?")
```

| Vantagem de manter lógica determinística em código | Explicação |
|---|---|
| **Custo** | Código é praticamente gratuito; LLM custa por token |
| **Latência** | Milissegundos × segundos |
| **Confiabilidade** | Sem alucinação nem variação |
| **Testabilidade** | Testes unitários comuns |
| **Auditabilidade** | A regra está escrita e versionada |
| **Segurança** | Não pode ser "convencido" por prompt injection |

### Anatomia de um nó

```python
def avaliador(estado: Estado) -> dict:
    """Nó: recebe o estado, devolve SÓ as atualizações."""
    nota = juiz_llm(rubrica=RUBRICA, texto=estado["rascunho"])          # trabalho do nó
    return {"nota": nota, "revisoes": estado["revisoes"]}                # atualização parcial do estado
```

Boas práticas para nós:

| Prática | Motivo |
|---|---|
| **Responsabilidade única** | Testável, substituível, governável |
| **Entradas e saídas declaradas** (campos do estado que lê e escreve) | Dependências visíveis |
| **Idempotente sempre que possível** | Retentativas e retomadas seguras |
| **Sem efeitos colaterais ocultos** | Efeitos externos (enviar e-mail) em nós próprios, atrás de aprovação |
| **Tratamento de erros próprio** | Falha local não derruba o grafo (ver arestas de erro) |
| **Identidade e permissões próprias** | Cada nó acessa só o que precisa (4.4.4.1) |
| **Timeout e limites** | Nó que trava não trava o sistema |

## 2. Edges (Arestas)

### O que são

**Caminhos de controle de fluxo entre nós.** Uma aresta expressa uma **dependência** ("B só roda depois de A") ou uma **regra de roteamento** ("depois de A, vá para B ou C, conforme..."). A aresta responde: *"o que acontece a seguir?"*

### Tipos de arestas

| Tipo | Descrição | Exemplo |
|---|---|---|
| **Direta (sequencial)** | Sempre vai de A para B | `planner → researcher` |
| **Condicional (ramificação)** | Escolhe entre vários destinos conforme uma função de roteamento | `evaluator → (writer \| humano)` |
| **Paralela (fan-out)** | Dispara vários nós ao mesmo tempo | `planner → {analise_juridica, analise_financeira}` |
| **Convergente (fan-in/join)** | Espera os ramos e consolida | `{analises} → consolidar` |
| **De retorno (loop interno)** | Volta a um nó anterior (ciclo) | `evaluator → writer` (revisar) |
| **De erro (error handler)** | Caminho alternativo quando um nó falha | `buscar_erp ──falha──► fallback_cache` |
| **Para o fim / interrupção** | Encerra a execução ou pausa para humano | `→ END`, `→ interrupt` |

```
direta:        A ─────────────► B

condicional:   A ──┬─(se x)───► B
                   └─(senão)──► C

paralela:      A ──┬──► B1 ──┐
                   ├──► B2 ──┼──► J
                   └──► B3 ──┘

retorno:       G ──► E ──(reprovado)──► G      ◄── ciclo (exige TETO)

erro:          A ──(falha)──► F  (fallback)  /  ──(esgotou retentativas)──► escalar a humano
```

### Ciclos: poder e perigo

Arestas de retorno criam **ciclos** (loops de revisão, tentar de novo, reflexão). São a base do padrão avaliador-otimizador (4.4.3.1), mas **sem limite explícito** geram loops infinitos e custo descontrolado:

```python
# O limite está na ESTRUTURA do grafo (código), não em "por favor, revise no máximo 2 vezes" no prompt
def rotear_apos_avaliacao(estado) -> str:
    if estado["nota"] >= 0.8:
        return "aprovacao_humana"
    if estado["revisoes"] >= 2:            # TETO explícito
        return "escalar_humano"
    return "revisar"                       # volta ao redator
```

### Tratamento de falhas nas arestas

| Estratégia | Quando |
|---|---|
| **Retentativa com backoff** | Falhas transitórias (timeout, limite de taxa) |
| **Fallback** | Alternativa (cache, outro modelo, resposta parcial) |
| **Circuit breaker** | Para de chamar um serviço que falha repetidamente |
| **Escalonamento humano** | Falha persistente em caso importante |
| **Compensação** | Desfazer efeitos de etapas já executadas (padrão saga) quando um passo posterior falha |

## 3. State (Estado compartilhado)

### O que é

Uma **estrutura de dados tipada** que **flui pelo grafo**: o "dossiê" que cada nó lê e atualiza. É a **memória de trabalho** da execução.

```python
from typing import TypedDict, Annotated
from operator import add

class Estado(TypedDict):
    pergunta: str                                    # entrada original
    plano: list[str]                                 # escrito pelo planner
    evidencias: Annotated[list[dict], add]           # REDUCER: cada nó ACRESCENTA, não sobrescreve
    rascunho: str                                    # escrito pelo writer
    nota: float                                      # escrito pelo evaluator
    revisoes: int                                    # contador (controla o teto do ciclo)
    aprovado_por: str | None                         # preenchido pelo humano
```

### Por que um estado tipado

| Benefício | Explicação |
|---|---|
| **Visibilidade** | Entradas e saídas de cada nó ficam explícitas (quem escreve/lê cada campo) |
| **Menos tokens** | Cada agente recebe **só os campos de que precisa**, em vez de toda a transcrição da conversa |
| **Validação** | Tipos (Pydantic/TypedDict) detectam erros cedo |
| **Depuração e reprodução** | O estado em cada passo pode ser inspecionado, salvo e **reexecutado** |
| **Persistência** | Checkpoints permitem pausar (HITL), retomar após falhas e "voltar no tempo" |
| **Contratos claros** | Define a interface entre nós: trocar um nó não quebra os outros enquanto honrar o contrato |

### Reducers: como atualizações se combinam

Quando vários nós (ou ramos paralelos) escrevem no mesmo campo, é preciso dizer **como combinar**:

| Reducer | Comportamento | Uso |
|---|---|---|
| **Sobrescrever** (padrão) | O último valor vence | Campos únicos (`rascunho`, `nota`) |
| **Acrescentar (append)** | Junta listas | `evidencias`, `mensagens`, `erros` |
| **Mesclar (merge)** | Combina dicionários | Resultados parciais por chave |
| **Soma/contador** | Acumula valores | Custo total, tentativas |
| **Personalizado** | Regra própria | Resolver conflitos entre ramos paralelos |

Sem reducer adequado, ramos paralelos **sobrescrevem uns aos outros** silenciosamente (condição de corrida lógica).

### Estado: o que colocar e o que evitar

| Colocar | Evitar |
|---|---|
| Dados que **múltiplos nós** precisam | Documentos enormes inteiros (guarde uma **referência**/ID; o conteúdo vai para armazenamento externo) |
| Resultados intermediários com **significado de negócio** | A transcrição completa para todos os nós |
| **Metadados de controle**: contadores, flags, IDs de execução e de nó | Segredos e credenciais (devem ficar no ambiente/cofre, não no estado persistido) |
| Informações para **auditoria** (quem decidiu, quando, com que base) | Dados pessoais em excesso (o estado é persistido em checkpoints) |

### Estado de entrada/saída vs. estado interno

Em grafos maiores, separa-se: **esquema de entrada** (o que o chamador envia), **esquema de saída** (o que devolve) e **estado interno** (campos de trabalho privados). Isso protege a interface pública e evita vazar detalhes internos.

## 4. Conditional Routing (Roteamento condicional)

### O que é

As **condições de guarda** que decidem **qual aresta seguir** a partir de um nó. É o "cérebro de controle" do grafo.

### Duas naturezas de roteamento

| Natureza | Como decide | Quando usar | Exemplo |
|---|---|---|---|
| **Determinístico (código)** | Regra explícita sobre o estado | Condições objetivas e restrições rígidas | `if estado["valor"] > 50_000: return "aprovacao_humana"` |
| **Semântico (LLM)** | Classificação feita por um modelo | Decisões que dependem de **interpretar linguagem** | "Esta mensagem é uma reclamação, dúvida ou pedido de cancelamento?" |

```python
# ROTEAMENTO DETERMINÍSTICO (preferível quando a condição é objetiva)
def rotear_credito(estado: Estado) -> str:
    if not estado["documentos_validos"]:
        return "pedir_documentos"
    if estado["valor"] > 50_000:
        return "aprovacao_humana"          # alçada: regra de negócio NO CÓDIGO
    return "analise_automatica"

# ROTEAMENTO SEMÂNTICO (LLM classifica; o código valida e decide)
def rotear_mensagem(estado: Estado) -> str:
    categoria = classificar_llm(estado["mensagem"], opcoes=["reclamacao", "duvida", "cancelamento"])
    return {"reclamacao": "time_retencao", "duvida": "faq_agente", "cancelamento": "fluxo_cancelamento"}.get(
        categoria, "triagem_humana")        # DEFAULT seguro para saída inesperada
```

### A regra central do roteamento

> **Restrições rígidas (*hard constraints*) não devem ficar escondidas dentro de prompts: devem ser aplicadas explicitamente no código de roteamento.**

```
✘ RUIM:   prompt do agente: "NUNCA aprove crédito acima de R$ 50 mil sem aprovação da diretoria."
          (depende da obediência do modelo; falha por esquecimento, ambiguidade ou prompt injection)

✔ BOM:    aresta condicional em código:  valor > 50_000  ─►  nó "aprovacao_diretoria" (obrigatório)
          (o agente NEM CONSEGUE chegar à execução sem passar pela aprovação)
```

| Tipo de regra | Onde implementar |
|---|---|
| **Alçadas, limites, permissões, conformidade** | **Código de roteamento / nós determinísticos** |
| **Preferências de estilo, tom, formato** | Prompt (instrução) |
| **Classificação de intenção ambígua** | LLM, **com validação e default seguro** no código |

### Boas práticas de roteamento

| Prática | Motivo |
|---|---|
| **Roteador por LLM com saída restrita** (enum/schema, tópico 1.2.2.1) | Evita destinos inventados |
| **Destino padrão seguro** (`triagem_humana`) | Para saídas inesperadas ou de baixa confiança |
| **Limiar de confiança** | Se o classificador não tem certeza, escalar |
| **Roteamento "barato primeiro"**: regras simples antes de chamar LLM | Custo e latência |
| **Registrar a decisão e o motivo** | Auditoria e depuração ("por que foi para a aprovação?") |
| **Testar o roteamento isoladamente** (tabela de casos de teste) | Funções puras de roteamento são fáceis de testar |
| **Cobrir todos os casos** (nenhum estado sem saída) | Evita grafos que travam |

## Juntando tudo: um grafo completo em código

```python
from typing import TypedDict, Annotated, Literal
from operator import add
from langgraph.graph import StateGraph, START, END
from langgraph.checkpoint.postgres import PostgresSaver

class Estado(TypedDict):
    pedido: dict
    valor: float
    analise: str
    parecer_politica: Literal["ok", "violacao", "pendente"]
    log: Annotated[list[str], add]                          # reducer: acrescenta
    aprovado: bool

# ---- NÓS ----
def validar(e):        return {"log": ["validado"], "valor": e["pedido"]["valor"]}      # determinístico
def analisar(e):       return {"analise": llm_analista(e["pedido"]), "log": ["analisado"]}   # LLM
def checar_politica(e):                                                                 # determinístico
    ok = e["valor"] <= LIMITE_POR_PERFIL[e["pedido"]["perfil"]]
    return {"parecer_politica": "ok" if ok else "violacao", "log": ["politica checada"]}
def aprovacao_humana(e): return {"aprovado": pedir_aprovacao(e), "log": ["humano decidiu"]}   # HITL (interrupt)
def efetivar(e):       return {"log": ["efetivado"]}

# ---- ROTEAMENTO (código, com restrição rígida) ----
def rota(e) -> Literal["aprovacao_humana", "efetivar", "rejeitar"]:
    if e["parecer_politica"] == "violacao":
        return "rejeitar"
    return "aprovacao_humana" if e["valor"] > 50_000 else "efetivar"

# ---- ARESTAS ----
g = StateGraph(Estado)
for nome, fn in [("validar", validar), ("analisar", analisar), ("checar_politica", checar_politica),
                 ("aprovacao_humana", aprovacao_humana), ("efetivar", efetivar), ("rejeitar", lambda e: {"log": ["rejeitado"]})]:
    g.add_node(nome, fn)
g.add_edge(START, "validar")
g.add_edge("validar", "analisar")
g.add_edge("analisar", "checar_politica")
g.add_conditional_edges("checar_politica", rota)           # aresta condicional (roteamento em código)
g.add_edge("aprovacao_humana", "efetivar")
g.add_edge("efetivar", END); g.add_edge("rejeitar", END)

app = g.compile(checkpointer=PostgresSaver.from_conn_string(DSN))      # persistência
```

(Sintaxe do LangGraph ilustrativa; consulte a documentação da versão em uso. Os conceitos valem para outras ferramentas.)

Observe os quatro componentes: **nós** de natureza mista (3 determinísticos, 1 LLM, 1 humano); **estado** tipado com reducer em `log`; **arestas** diretas e uma condicional; **roteamento** em código com a alçada de R$ 50 mil.

## Mapa de conceitos entre ferramentas

| Conceito | LangGraph | CrewAI | AutoGen | Pydantic Graph |
|---|---|---|---|---|
| **Nó** | Node (função/Runnable) | Task / Agent / Flow step | Agente / participante | Node (classe) |
| **Aresta** | Edge / conditional edge | Dependência de tarefas / `@listen`, `@router` (Flows) | Seleção de próximo orador / GraphFlow | Retorno do próximo nó |
| **Estado** | State (TypedDict/Pydantic) + reducers | Estado de Flow, contexto de tasks | Contexto/mensagens do time | Estado (dataclass) |
| **Roteamento** | `add_conditional_edges`, `Command(goto=...)` | `@router` | Selector / condições de término | Tipo de retorno do nó |
| **Persistência** | Checkpointers | Persistência de Flows | Salvar/carregar estado do time | Persistência de estado |

## Erros comuns e armadilhas

- **Todo nó é um agente de LLM**, incluindo regras que seriam código simples.
- **Restrições rígidas em prompts** em vez de em arestas condicionais.
- **Estado = transcrição completa** circulando a cada nó: custo e ruído.
- **Reducer ausente** em campos escritos por ramos paralelos: sobrescritas silenciosas.
- **Segredos no estado** (persistido em checkpoints).
- **Documentos inteiros no estado** em vez de referências.
- **Ciclos sem teto** na estrutura.
- **Roteador de LLM sem saída restrita** nem destino padrão: destinos inventados ou grafo travado.
- **Estados sem saída** (condição não coberta no roteamento).
- **Arestas de erro ausentes**: falha de um nó derruba toda a execução.
- **Nós com responsabilidades múltiplas**: difíceis de testar e governar.
- **Não registrar o motivo das decisões de roteamento**: auditoria impossível.

## 🧩 Quiz de Fixação

1. Quais são os tipos de nós de um grafo de agentes e por que "nem todo nó deve ser um agente de IA"?
2. Para que servem os reducers no estado e o que acontece sem eles em ramos paralelos?
3. Dê um exemplo de restrição rígida e explique por que ela deve ser implementada no roteamento em código e não no prompt.

**Respostas:**
1) Nós de agente (LLM), funções determinísticas, roteadores, ferramentas, junções (join), checkpoints humanos, avaliadores e subgrafos. Nem todo nó deve ser agente porque lógica de negócio determinística em código é mais barata, rápida, confiável, testável, auditável e imune a prompt injection; o LLM deve ficar onde há ambiguidade ou tarefa semântica.
2) Reducers definem como atualizações de vários nós ou ramos paralelos se combinam em um mesmo campo do estado (sobrescrever, acrescentar, mesclar, somar, personalizado). Sem um reducer adequado, ramos paralelos sobrescrevem os resultados uns dos outros silenciosamente, perdendo informação.
3) Exemplo: "créditos acima de R$ 50 mil exigem aprovação da diretoria". No roteamento em código, uma aresta condicional leva obrigatoriamente ao nó de aprovação, e o agente não consegue chegar à efetivação sem passar por ele. No prompt, a regra dependeria da obediência do modelo e poderia falhar por esquecimento, ambiguidade ou prompt injection.
