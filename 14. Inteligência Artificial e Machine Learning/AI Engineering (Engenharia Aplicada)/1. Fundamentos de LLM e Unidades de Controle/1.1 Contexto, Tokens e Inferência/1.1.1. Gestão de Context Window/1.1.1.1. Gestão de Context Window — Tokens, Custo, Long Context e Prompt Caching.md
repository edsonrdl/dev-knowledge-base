### Gestão de Context Window — Tokens, Custo, Long Context e Prompt Caching

A janela de contexto é o recurso mais caro e mais limitado de qualquer aplicação com LLM. Tudo o que o modelo "sabe" durante uma chamada precisa caber ali: instruções, histórico, documentos recuperados e a própria resposta. Gerenciar bem essa janela é a diferença entre um sistema barato e preciso e outro caro e esquecido.

> [!note] Pré-requisito
> Este arquivo é a face **prática** de um assunto que o guia [[14. Inteligência Artificial e Machine Learning/Como LLMs Funcionam/0 Como LLMs Funcionam (Glossário )|Como LLMs Funcionam]] explica por dentro (tokenização e atenção).

## Context window: o que é e do que é feita

**Context window** é o número máximo de tokens que o modelo processa em uma única chamada, **somando entrada e saída**. Se a janela é de 200 mil tokens e você envia 190 mil, só restam 10 mil para a resposta.

**Analogia:** é a mesa de trabalho do modelo. Ele só enxerga o que está sobre a mesa; o que não coube foi guardado fora de alcance. Mesas maiores comportam mais papéis, mas procurar um papel específico em uma mesa lotada também fica mais difícil.

```
┌─────────────────────── JANELA DE CONTEXTO (ex.: 200k tokens) ─────────────────────┐
│ system prompt │ histórico da conversa │ documentos (RAG) │ pergunta │ ► resposta │
│   (fixo)      │      (cresce)         │   (variável)     │          │ (reservada) │
└──────────────────────────────────────────────────────────────────────────────────┘
        tudo isto é INPUT e é cobrado a cada chamada      ▲ OUTPUT, mais caro
```

Ponto-chave: **LLMs via API não têm memória**. A "conversa" é uma ilusão: a cada turno você reenvia o histórico inteiro, e paga por ele de novo.

## Tokens e custo de API

Modelos não leem caracteres nem palavras, e sim **tokens** (pedaços de palavras). Em português, a média gira em torno de 1 token para cada 3 a 4 caracteres, e o idioma costuma gastar mais tokens que o inglês para o mesmo conteúdo, porque os vocabulários dos tokenizers foram treinados com mais texto em inglês.

O custo é cobrado por milhão de tokens, com **preços distintos para entrada e saída** (a saída costuma ser várias vezes mais cara). Uma conta simplificada:

```
custo = (tokens_entrada × preço_entrada) + (tokens_saída × preço_saída)
```

O efeito perverso nas conversas longas:

| Turno | Tokens enviados (histórico + nova msg) | Tokens acumulados pagos |
|---|---|---|
| 1 | 500 | 500 |
| 5 | 3.000 | ~9.000 |
| 20 | 12.000 | ~125.000 |

O custo cresce de forma **quadrática** com o número de turnos, porque cada turno reenvia todos os anteriores. É por isso que gestão de contexto é questão financeira, não só técnica.

Medir é o primeiro passo:

```python
import tiktoken                       # tokenizer da OpenAI (contagem aproximada p/ outros)
enc = tiktoken.get_encoding("cl100k_base")
print(len(enc.encode("Qual o prazo de rescisão do contrato?")))
```

APIs também retornam o uso real em cada resposta (`usage.input_tokens`, `usage.output_tokens`) — registre isso para acompanhar custos.

## Estratégias para conversas que crescem

### 1. Sliding window (janela deslizante)

Mantém só as últimas N mensagens, descartando as mais antigas.

```
[m1][m2][m3][m4][m5][m6]  ──►  descarta m1,m2  ──►  [m3][m4][m5][m6][m7]
```

Simples e barata, mas o modelo **esquece** o começo (nome do usuário, objetivo da conversa).

### 2. Truncation (truncamento)

Corta o que excede o limite, geralmente do meio ou do começo de documentos grandes. Risco: cortar justamente a informação relevante.

### 3. Summarization (sumarização do histórico)

Resume mensagens antigas em um parágrafo e mantém as recentes na íntegra:

```
[resumo das mensagens 1–20] + [mensagens 21–25 literais] + [nova pergunta]
```

Preserva o contexto geral com custo menor, ao preço de perder detalhes e de uma chamada extra para resumir.

### 4. Memória externa / RAG sobre o histórico

Guarda fatos importantes fora do prompt (banco vetorial, tabela de preferências) e injeta só o relevante a cada turno (tema aprofundado em *Memória de Agentes*).

| Estratégia | Custo | Retém detalhes? | Complexidade |
|---|---|---|---|
| Sliding window | Baixo | Só os recentes | Baixa |
| Truncation | Baixo | Aleatório | Baixa |
| Summarization | Médio | Parcial | Média |
| Memória externa | Médio | Sob demanda | Alta |

## Long context e o problema "Lost in the Middle"

Modelos modernos aceitam janelas enormes (centenas de milhares a milhões de tokens). Parece resolver tudo: "é só colocar todos os documentos no prompt". Não é bem assim:

1. **Custo e latência** crescem com o tamanho do prompt.
2. **Atenção diluída:** o estudo *Lost in the Middle* (Liu et al., 2023) mostrou que modelos usam melhor a informação no **início** e no **fim** do contexto, e pior a que está no **meio**.

```
Precisão de recuperação da informação, segundo a posição no contexto

 alta │██                                         ██
      │██ ██                                   ██ ██
      │██ ██ ██                             ██ ██ ██
 baixa│██ ██ ██ ░░ ░░ ░░ ░░ ░░ ░░ ░░ ░░ ██ ██ ██
      └──────────────────────────────────────────────
       início            MEIO              fim
```

Modelos mais recentes melhoraram bastante, mas o efeito não desapareceu por completo; a regra prática continua válida:

- Coloque **instruções críticas e a pergunta** no início e/ou fim.
- Em RAG, ordene os trechos por relevância e **evite enterrar o mais importante no meio**.
- Prefira **menos trechos, mais relevantes** (reranking) a despejar tudo.
- Teste com a *needle in a haystack*: esconda um fato em um texto longo e veja se o modelo o encontra.

| Abordagem | Quando faz sentido |
|---|---|
| **Long context** (tudo no prompt) | Poucos documentos, análise global (resumir um livro), prototipagem |
| **RAG** | Base grande, atualizações frequentes, custo e latência importam |
| **Híbrido** | RAG para localizar + long context para raciocinar sobre os trechos |

## Prompt Caching nativo

Se o início do prompt é idêntico entre chamadas (system prompt longo, documentos fixos, exemplos few-shot), reprocessá-lo toda vez é desperdício. O **prompt caching** reaproveita o processamento já feito desse **prefixo**.

**Analogia:** é um cache de compilação. Se o começo do arquivo não mudou, não precisa recompilar.

```
Chamada 1:  [PREFIXO FIXO (grande)][pergunta A]  → processa tudo; grava o prefixo no cache
Chamada 2:  [PREFIXO FIXO (grande)][pergunta B]  → prefixo vem do cache (barato e rápido)
                      ▲ precisa ser IDÊNTICO e vir PRIMEIRO
```

### Anthropic (explícito)

Você marca onde termina o trecho cacheável com `cache_control`:

```python
resp = client.messages.create(
    model="claude-sonnet-5-5",
    max_tokens=1024,
    system=[{
        "type": "text",
        "text": REGULAMENTO_COMPLETO,                 # texto longo e estável
        "cache_control": {"type": "ephemeral"}        # ← marca o fim do prefixo cacheável
    }],
    messages=[{"role": "user", "content": pergunta}],
)
print(resp.usage.cache_creation_input_tokens, resp.usage.cache_read_input_tokens)
```

Em linhas gerais: **escrever** no cache custa um pouco mais que a entrada normal; **ler** do cache custa uma fração (da ordem de 10%) do preço normal; o cache expira após alguns minutos sem uso (existe opção de duração maior); e há um tamanho mínimo de prefixo para ser elegível.

### OpenAI (automático)

O cache é aplicado **automaticamente** para prefixos acima de um tamanho mínimo (a partir de ~1.024 tokens), sem alteração de código, com desconto na parte reaproveitada.

> [!warning] Valores mudam
> Preços, descontos, TTL e tamanhos mínimos variam por modelo e mudam com frequência. Confira a documentação oficial de cada provedor antes de calcular custos.

### Regras de ouro do prompt caching

| Regra | Motivo |
|---|---|
| **Conteúdo estável primeiro, variável por último** | O cache casa pelo prefixo; mudar um byte no começo invalida tudo depois |
| **Não coloque timestamps ou IDs no início do prompt** | Quebram o cache a cada chamada |
| **Mantenha a ordem das ferramentas e do system prompt** | Reordenar invalida o prefixo |
| **Monitore a taxa de acerto (cache hit)** | Verifique `cache_read_input_tokens` |

## Exemplo prático: assistente de regulamento interno

Cenário: um chatbot responde dúvidas sobre um regulamento de 60 mil tokens, 5.000 consultas por dia.

```
Sem cache:   5.000 × 60.000 = 300 milhões de tokens de entrada por dia
Com cache:   ~1 escrita + ~4.999 leituras a ~10% do preço
             → redução de custo de entrada na casa de 80–90% e latência menor
```

Boas decisões combinadas: regulamento no `system` com `cache_control`; só a pergunta varia; histórico resumido após 10 turnos; saída limitada com `max_tokens`.

## Erros comuns e armadilhas

- **Reenviar tudo sem controle** e só descobrir o custo na fatura.
- **Confiar que "janela grande = resolve"**: custo, latência e *lost in the middle*.
- **Variáveis no início do prompt** (data, nome do usuário), destruindo o cache.
- **Esquecer de reservar espaço para a saída**, causando respostas cortadas.
- **Truncar sem critério**, perdendo a informação essencial.
- **Não medir tokens**: sem telemetria, não há otimização.
- **Comparar contagem de tokens entre modelos** sem notar que cada tokenizer conta diferente.

| Cenário | Recomendação |
|---|---|
| Conversa longa de suporte | Sumarização + memória de fatos |
| Prompt grande e fixo reutilizado | Prompt caching |
| Base com milhares de documentos | RAG, não long context |
| Análise única de um documento grande | Long context |

## 🧩 Quiz de Fixação

1. Por que o custo de uma conversa longa cresce de forma quadrática e como o prompt caching ajuda?
2. O que é o fenômeno *lost in the middle* e que prática ele sugere em RAG?
3. Você tem um system prompt de 30 mil tokens e um timestamp no início dele. O cache nunca acerta. Qual o problema e a correção?

**Respostas:**
1) Porque LLMs via API não têm memória: cada turno reenvia o histórico inteiro, então os tokens pagos acumulam a soma de todos os turnos. O prompt caching reaproveita o processamento do prefixo idêntico (system prompt, documentos fixos), cobrando uma fração do preço e reduzindo latência nas leituras do cache.
2) É a tendência de o modelo aproveitar melhor informações no início e no fim do contexto do que no meio. Em RAG, convém ordenar por relevância, evitar enterrar o trecho principal no meio, usar menos trechos mais relevantes (reranking) e posicionar instruções críticas e a pergunta nas extremidades.
3) O cache funciona por prefixo idêntico: o timestamp muda a cada chamada e invalida tudo que vem depois dele. A correção é mover o conteúdo variável (timestamp, ID de usuário) para o final do prompt, mantendo o bloco estável de 30 mil tokens no começo.
