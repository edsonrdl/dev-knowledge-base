### Temperature, Top-P e Semantic Caching

Dois botões controlam o comportamento de uma chamada ao LLM sem mudar o modelo: os **parâmetros de amostragem** (temperature, top-p), que decidem *quão previsível* é a resposta, e o **cache** (em especial o semântico), que decide *se vale a pena chamar o modelo*. Dominar ambos é metade da otimização de custo e qualidade em produção.

---

## Como o modelo escolhe a próxima palavra

A cada passo, o LLM calcula uma **distribuição de probabilidade** sobre todo o vocabulário e escolhe um token dessa distribuição. Os parâmetros de amostragem mexem nessa escolha.

Exemplo: após "O céu está", a distribuição pode ser:

```
azul     ████████████████████  62%
nublado  ████████               24%
claro    ███                    8%
lindo    ██                     4%
cinza    ▌                      1%
(milhares de outros tokens...) <1%
```

**Decodificação gulosa** (*greedy*) sempre pega "azul". Amostragem sorteia conforme as probabilidades. Temperature e top-p ajustam esse sorteio.

---

## Temperature

Temperature reescala a distribuição **antes** do sorteio:

- **Baixa (→ 0):** acentua o favorito; o resultado fica mais **determinístico** e repetível.
- **Alta:** achata a distribuição; tokens menos prováveis ganham chance; resultado mais **variado e criativo**, e também mais sujeito a erros e divagações.

```
Temperature = 0.2           Temperature = 1.0           Temperature = 1.8
azul     ██████████████     azul     ████████████       azul     ████████
nublado  ██                 nublado  █████              nublado  ██████
claro    ▌                  claro    ██                 claro    █████
                            lindo    █                  lindo    ████
 (quase sempre "azul")      (variação moderada)         (bem aleatório)
```

**Analogia:** é o grau de ousadia de um músico de jazz. Temperatura baixa: toca a partitura exatamente. Alta: improvisa, às vezes brilhante, às vezes desafinado.

### Valores práticos

| Tarefa | Temperature sugerida | Motivo |
|---|---|---|
| Extração de dados, classificação, SQL, JSON | 0 a 0,2 | Queremos consistência e precisão |
| Perguntas e respostas factuais (RAG) | 0 a 0,3 | Reduz invenção; fidelidade às fontes |
| Código | 0 a 0,3 | Menos ruído sintático |
| Chat conversacional | 0,5 a 0,8 | Naturalidade com variação |
| Brainstorm, copy criativo, nomes | 0,8 a 1,2 | Diversidade de ideias |

> [!warning] Temperature 0 não garante determinismo absoluto
> Mesmo com temperature 0, resultados podem variar levemente entre chamadas por detalhes de hardware, paralelismo e arredondamentos numéricos. Trate-o como "quase determinístico". Para testes, compare por critérios e não por igualdade exata de texto.

Os intervalos aceitos variam por provedor (por exemplo, 0 a 1 em uns, 0 a 2 em outros). Alguns modelos de raciocínio fixam ou ignoram esse parâmetro (veja o tópico 1.1.3).

## Top-P (nucleus sampling)

Em vez de reescalar, **corta a cauda**: considera apenas o menor conjunto de tokens cuja probabilidade acumulada atinja **p**, e sorteia dentro dele.

```
top_p = 0.9  →  soma 62% + 24% + 8% = 94% ≥ 90%
                 núcleo = {azul, nublado, claro}
                 "lindo", "cinza" e a cauda longa são descartados
```

| top_p | Efeito |
|---|---|
| 1.0 | Todos os tokens elegíveis (sem corte) |
| 0.9 a 0.95 | Valor comum; elimina a cauda de tokens improváveis |
| 0.1 a 0.3 | Muito restrito; saída quase determinística |

**Diferença conceitual:**

| Parâmetro | Atua em | Pergunta que responde |
|---|---|---|
| **Temperature** | O *formato* da distribuição | "Quão arriscado posso ser entre as opções?" |
| **Top-P** | O *conjunto* de candidatos | "Quais opções entram no sorteio?" |

**Regra prática:** ajuste **um** dos dois, não ambos. Alterar os dois ao mesmo tempo torna difícil entender o efeito (muitos provedores recomendam isso explicitamente). Outros parâmetros relacionados: `top_k` (limite fixo de candidatos, disponível em alguns provedores), `frequency_penalty`/`presence_penalty` (desencorajam repetição) e `seed` (tenta reproduzir resultados, quando suportado).

```python
resp = client.chat.completions.create(
    model="gpt-4o",
    messages=[{"role": "user", "content": "Classifique o sentimento: 'Adorei o atendimento'"}],
    temperature=0,          # classificação: queremos consistência
    max_tokens=10,
)
```

## Semantic Caching

O cache tradicional guarda resposta pela **chave exata** da pergunta. No mundo de linguagem natural isso falha: "Qual o horário de funcionamento?" e "Que horas vocês abrem?" são perguntas diferentes para o cache, mas iguais para o usuário.

O **semantic cache** compara por **significado** usando embeddings:

```
Pergunta nova ──► embedding ──► busca no cache vetorial
                                        │
              similaridade ≥ limiar? ───┴─── sim ──► devolve a resposta guardada
                                        │            (sem chamar o LLM: ~ms, custo ~0)
                                        └──── não ──► chama o LLM ──► guarda (pergunta, resposta)
```

**Analogia:** é um atendente experiente que já respondeu "como redefino a senha?" cem vezes e reconhece a pergunta mesmo escrita de outro jeito, respondendo de memória em vez de consultar o manual toda vez.

### Implementação com RedisVL

```python
from redisvl.extensions.llmcache import SemanticCache

cache = SemanticCache(
    name="faq_cache",
    redis_url="redis://localhost:6379",
    distance_threshold=0.1,        # menor = mais rígido (exige perguntas mais parecidas)
    ttl=3600,                      # expira em 1h
)

pergunta = "Que horas vocês abrem?"
if hit := cache.check(prompt=pergunta):
    resposta = hit[0]["response"]                 # acerto: sem LLM
else:
    resposta = chamar_llm(pergunta)               # falha: gasta tokens
    cache.store(prompt=pergunta, response=resposta)
```

Linha a linha: `distance_threshold` define o quão próximas as perguntas precisam ser; `check` faz a busca vetorial; `store` grava o par após uma falha; `ttl` evita respostas obsoletas.

### Estratégias de cache em múltiplas camadas

```
Pergunta
   │
   ▼
[Camada 1] Cache exato (hash)            → acerto instantâneo, 100% seguro
   │ falha
   ▼
[Camada 2] Cache semântico (embeddings)  → acerto por similaridade (RedisVL, GPTCache)
   │ falha
   ▼
[Camada 3] Prompt caching do provedor    → LLM chamado, mas com prefixo barato
   │
   ▼
 LLM (resposta nova, depois gravada nas camadas acima)
```

**GPTCache** é uma biblioteca open source que fornece esse padrão pronto, com armazenamento de embeddings, de respostas e políticas de remoção plugáveis.

| Camada | Custo do acerto | Risco de resposta errada | Melhor para |
|---|---|---|---|
| Exato | ~0 | Nenhum | Consultas repetidas idênticas |
| Semântico | Baixo (embedding + busca) | Médio (falso positivo) | FAQs, suporte, perguntas recorrentes |
| Prompt caching | Reduzido (não zero) | Nenhum | Prefixos grandes e fixos |

---

## Riscos e limitações do semantic cache

- **Falso positivo:** "Cancelar o pedido 123" e "Cancelar o pedido 124" são muito parecidos semanticamente, mas as respostas diferem. Nunca cacheie respostas que dependem de **dados específicos ou do usuário**.
- **Limiar mal calibrado:** frouxo demais devolve resposta errada; rígido demais quase nunca acerta. Calibre com exemplos reais.
- **Informação obsoleta:** defina TTL e invalide o cache quando a base de conhecimento muda.
- **Dados pessoais e privacidade:** não compartilhe cache entre usuários/tenants se a resposta contém dados privados.
- **Respostas não determinísticas:** se o caso pede variedade (criatividade), o cache devolve sempre a mesma.
- **Custo extra:** cada consulta paga embedding + busca; só compensa com taxa de acerto razoável.

| Cenário | Cachear? |
|---|---|
| FAQ público (horários, políticas) | Sim, semântico |
| "Qual o status do meu pedido?" | Não (dado dinâmico e pessoal) |
| Conteúdo criativo único por usuário | Não |
| Prompt de sistema grande e fixo | Prompt caching, não semantic cache |

## 🧩 Quiz de Fixação

1. Qual a diferença entre temperature e top-p, e por que se recomenda ajustar apenas um?
2. Que valores de temperature você usaria para (a) extrair dados de notas fiscais e (b) gerar slogans? Justifique.
3. Cite um cenário em que o semantic cache é perigoso e como mitigar.

**Respostas:**
1) Temperature reescala a distribuição de probabilidades (quão arriscada é a escolha); top-p restringe o conjunto de candidatos ao menor grupo cuja probabilidade acumulada atinge p. Os dois influenciam a aleatoriedade de forma sobreposta; alterar ambos dificulta entender qual causou o efeito, por isso costuma-se ajustar apenas um.
2) (a) Temperature baixa (0 a 0,2): extração exige precisão e consistência. (b) Temperature mais alta (0,8 a 1,2): slogans se beneficiam de diversidade e originalidade.
3) Respostas dependentes de dados específicos, como "status do pedido 123" vs "pedido 124", que são semanticamente quase iguais mas têm respostas diferentes (falso positivo). Mitigação: não cachear perguntas com dados pessoais ou dinâmicos, calibrar o limiar de similaridade, usar TTL e segregar o cache por usuário/tenant.
