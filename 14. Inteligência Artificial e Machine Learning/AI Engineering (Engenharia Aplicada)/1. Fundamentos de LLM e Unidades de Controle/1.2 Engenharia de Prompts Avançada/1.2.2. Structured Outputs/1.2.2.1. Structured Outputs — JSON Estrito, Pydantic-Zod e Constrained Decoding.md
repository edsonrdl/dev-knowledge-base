### Structured Outputs — JSON Estrito, Pydantic/Zod e Constrained Decoding

Um LLM devolve **texto livre**; o seu sistema precisa de **dados**: um objeto com campos tipados que o código possa consumir sem adivinhar. Estruturar a saída é o que transforma um LLM de "chatbot" em **componente de software confiável**: pipelines de extração, agentes que chamam funções, classificadores, roteadores.

---

## O problema: texto livre quebra sistemas

```
Prompt: "Extraia nome e idade: 'Maria tem 34 anos'"

Respostas possíveis em chamadas diferentes:
  1) {"nome": "Maria", "idade": 34}
  2) Claro! Aqui está: {"nome": "Maria", "idade": "34 anos"}
  3) ```json\n{"name": "Maria", "age": 34}\n```
  4) Nome: Maria, Idade: 34
```

Cada variação (texto extra, chave em outro idioma, tipo errado, bloco de código) faz `json.loads()` falhar ou o campo vir inválido. Em escala, isso é um incidente por dia.

**Analogia:** é a diferença entre um formulário em papel em branco (cada pessoa escreve do seu jeito) e um formulário com campos delimitados e caixas de seleção (só cabe o que é válido).

---

## Os quatro níveis de garantia

| Nível | Técnica | Garantia | Falha possível |
|---|---|---|---|
| 1 | Pedir no prompt ("responda em JSON") | Nenhuma | Texto extra, chaves erradas |
| 2 | **JSON mode** do provedor | Sintaxe JSON válida | Campos ausentes/tipos errados |
| 3 | **Structured Outputs** com JSON Schema (provedor) | Aderência ao schema | Limitações de schema suportado |
| 4 | **Constrained decoding** (Outlines, Guidance, XGrammar) | Aderência por construção | Só com acesso ao motor de inferência |

Regra prática: suba de nível conforme a criticidade, e **sempre valide no código** mesmo assim.

## Nível 2 e 3: JSON mode e Structured Outputs nas APIs

### JSON Schema: o contrato

Um **JSON Schema** descreve a forma do dado: campos, tipos, obrigatoriedade, enumerações.

```json
{
  "type": "object",
  "properties": {
    "nome": {"type": "string"},
    "idade": {"type": "integer", "minimum": 0},
    "categoria": {"type": "string", "enum": ["ACESSO", "FINANCEIRO", "BUG"]}
  },
  "required": ["nome", "idade", "categoria"],
  "additionalProperties": false
}
```

Os principais provedores oferecem modos em que a resposta **segue o schema** (nomes variam: *structured outputs*, *response_format* com `json_schema`, uso forçado de uma *tool* cujo `input_schema` é o schema, ou `response_schema` no Gemini).

> [!warning] Recursos variam por provedor
> Subconjuntos suportados do JSON Schema (limites de aninhamento, `oneOf`, formatos) e nomes de parâmetros mudam entre provedores e versões. Consulte a documentação atual antes de depender de um recurso específico.

### Com Pydantic (Python)

Escrever JSON Schema à mão é trabalhoso. **Pydantic** gera o schema a partir de classes tipadas e **valida** o resultado.

```python
from enum import Enum
from pydantic import BaseModel, Field

class Categoria(str, Enum):
    ACESSO = "ACESSO"
    FINANCEIRO = "FINANCEIRO"
    BUG = "BUG"

class Ticket(BaseModel):
    nome: str
    idade: int = Field(ge=0, le=120, description="Idade em anos completos")
    categoria: Categoria

# SDKs modernos aceitam a classe diretamente e devolvem o objeto já validado
resp = client.beta.chat.completions.parse(
    model="gpt-4o",
    messages=[{"role": "user", "content": "Extraia: 'Maria, 34 anos, não consegue logar'"}],
    response_format=Ticket,            # ← o schema vem da classe
)
ticket: Ticket = resp.choices[0].message.parsed
print(ticket.categoria)                # Categoria.ACESSO (tipado, validado)
```

Linha a linha: `Field(ge=0, le=120)` embute regras de negócio no schema; `description` vira instrução para o modelo (campos bem descritos extraem melhor); `parse` converte e valida em uma só chamada.

### Com bibliotecas de conveniência

| Biblioteca | O que faz |
|---|---|
| **Instructor** | Envolve SDKs (OpenAI, Anthropic, etc.) e retorna modelos Pydantic, com **retry automático** quando a validação falha |
| **PydanticAI** | Framework de agentes com saídas tipadas |
| **LangChain** `with_structured_output` | Interface unificada entre provedores |

```python
import instructor
cliente = instructor.from_provider("openai/gpt-4o")    # exemplo; a sintaxe varia por versão
ticket = cliente.chat.completions.create(
    response_model=Ticket,                             # Pydantic
    max_retries=3,                                     # se a validação falhar, reenvia o erro ao modelo
    messages=[{"role": "user", "content": "..."}],
)
```

O **retry com feedback** é o truque central: se o Pydantic levanta `ValidationError`, a mensagem de erro ("idade deve ser ≥ 0") volta ao modelo para ele se corrigir.

## Zod no ecossistema TypeScript

No Node/TypeScript, o equivalente do Pydantic é o **Zod**: define schema e tipo estático juntos.

```typescript
import { z } from "zod";
import { zodResponseFormat } from "openai/helpers/zod";

const Ticket = z.object({
  nome: z.string(),
  idade: z.number().int().min(0).max(120),
  categoria: z.enum(["ACESSO", "FINANCEIRO", "BUG"]),
});
type Ticket = z.infer<typeof Ticket>;                  // tipo TS derivado do schema

const resp = await client.beta.chat.completions.parse({
  model: "gpt-4o",
  messages: [{ role: "user", content: "Extraia: 'Maria, 34 anos, não consegue logar'" }],
  response_format: zodResponseFormat(Ticket, "ticket"),
});
const ticket = resp.choices[0].message.parsed;         // Ticket | null
```

Linha a linha: `z.infer` garante que o tipo usado no resto do código é o mesmo do schema (uma fonte única de verdade); `zodResponseFormat` converte para JSON Schema que a API entende.

| Pydantic | Zod |
|---|---|
| Python | TypeScript/JavaScript |
| `BaseModel`, `Field` | `z.object`, `z.string().min()...` |
| `model_validate_json` | `Ticket.parse()` / `safeParse()` |
| `model_json_schema()` | `zod-to-json-schema` |

## Nível 4: Constrained Decoding (decodificação restrita)

### Como funciona

Em cada passo, o LLM atribui probabilidade a **todos** os tokens do vocabulário. A **decodificação restrita** intercepta esse momento e **zera a probabilidade dos tokens que violariam o formato**, de modo que só os válidos possam ser escolhidos.

```
Esquema esperado: {"idade": <inteiro>}

Já gerado:  {"idade":
Próximo token, antes da máscara:      depois da máscara (só dígitos e espaço):
  "trinta"   18%                        "trinta"   0%   ✘ bloqueado
  "3"        30%          ───►          "3"        55%
  "34"       25%                        "34"       45%
  "abc"      12%                        "abc"      0%   ✘ bloqueado
```

Resultado: a saída **não pode** violar o schema, por construção, não por sorte. O formato é descrito por uma **gramática** (regex, JSON Schema ou CFG) compilada em uma *máquina de estados* que diz, a cada passo, quais tokens são permitidos.

**Analogia:** é um teclado que só habilita as teclas válidas para o campo atual. Num campo de CPF, as letras ficam desativadas; não há como digitar errado.

### Ferramentas

| Ferramenta | Característica |
|---|---|
| **Outlines** | Compila JSON Schema, regex e gramáticas em máquinas de estado; integra com Hugging Face Transformers, vLLM e outros |
| **Guidance** | Linguagem de programação de templates e restrições intercalando texto fixo e trechos gerados |
| **XGrammar / llguidance** | Motores de gramática de alto desempenho integrados a servidores de inferência |
| **vLLM / llama.cpp (GBNF) / TGI** | Servidores que suportam *guided decoding* com schema ou gramática |

### Exemplo com Outlines (modelo local)

```python
import outlines
from pydantic import BaseModel

class Ticket(BaseModel):
    nome: str
    idade: int
    categoria: str

modelo = outlines.from_transformers(modelo_hf, tokenizer)        # modelo local (a API muda entre versões)
gerador = outlines.Generator(modelo, Ticket)                      # restringe a saída ao schema
ticket_json = gerador("Extraia: 'Maria, 34 anos, não consegue logar'")
ticket = Ticket.model_validate_json(ticket_json)                  # sempre válido sintaticamente
```

### Para que serve de verdade

| Caso | Benefício |
|---|---|
| **Modelos open-source/locais** (sem JSON mode nativo) | Confiabilidade comparável a APIs comerciais |
| **Classificação com rótulos fixos** (regex/enum) | Saída garantidamente dentro do conjunto |
| **Formatos exóticos** (SQL válido, código, gramática própria) | Gramática impede sintaxe inválida |
| **Menos retries** | Menos chamadas e menos latência |

### Limitações importantes

- **Garante a forma, não a verdade.** O JSON será válido, mas os valores podem estar errados ("idade": 34 quando o texto dizia 43).
- **Pode degradar a qualidade** se a restrição for rígida demais e forçar o modelo a escolher tokens improváveis (por exemplo, quando a resposta correta não cabe no schema).
- **Precisa de acesso à distribuição de tokens**: em APIs fechadas, só o que o provedor expõe.
- **Ordem dos campos importa:** o modelo gera na ordem do schema; colocar um campo `raciocinio` **antes** de `resposta` permite pensar antes de responder.

```python
class Decisao(BaseModel):
    raciocinio: str      # ← gerado primeiro: serve de "rascunho" (CoT dentro do JSON)
    decisao: Categoria   # ← gerado depois, condicionado ao raciocínio
```

## Pipeline robusto: defesa em camadas

```
Prompt claro + exemplos
        │
        ▼
Structured Output / constrained decoding   ← forma garantida
        │
        ▼
Validação Pydantic/Zod                      ← tipos e regras de negócio
        │ falhou?
        ├────► retry com a mensagem de erro (máx. 2–3 vezes)
        │ ainda falhou?
        └────► fallback: modelo mais forte, valor padrão ou fila para revisão humana
```

```python
from pydantic import ValidationError

def extrair(texto: str, tentativas: int = 3) -> Ticket | None:
    erro = ""
    for _ in range(tentativas):
        bruto = chamar_llm(f"Extraia o ticket em JSON.\n{erro}\nTexto: {texto}")
        try:
            return Ticket.model_validate_json(bruto)          # valida tipos e regras
        except ValidationError as e:
            erro = f"Sua resposta anterior foi inválida: {e}. Corrija."   # feedback ao modelo
    return None                                                # fallback para revisão humana
```

## Boas práticas de schema

| Prática | Motivo |
|---|---|
| **Descrever cada campo** (`description`) | O modelo usa as descrições como instruções |
| **Usar enums** para valores finitos | Elimina rótulos inventados |
| **Campos opcionais explícitos** (`str | None`) | Evita que o modelo invente valores quando a informação não existe |
| **Schemas pequenos e planos** | Aninhamento profundo reduz a confiabilidade |
| **Formatos padronizados** (datas ISO 8601, moeda em centavos inteiros) | Evita ambiguidades de parsing |
| **`additionalProperties: false`** | Rejeita campos fora do contrato |
| **Versionar o schema** | Mudanças quebram consumidores |

## Exemplo prático: extração de notas fiscais

```
Entrada: texto OCR de uma nota fiscal (ruidoso).
Schema: fornecedor (str), cnpj (str, regex), data (ISO), itens [descrição, qtd, valor_centavos],
        total_centavos (int).

1. Docling/OCR extrai o texto (domínio 2.3).
2. LLM + Structured Outputs com o schema Pydantic.
3. Validação de negócio: soma(itens) == total? CNPJ com dígitos verificadores válidos?
4. Falha na validação → retry com o erro; 2ª falha → fila de revisão humana.
5. Métrica: % de notas com todos os campos corretos num golden dataset de 200 notas.
```

O ponto central: **forma garantida pelo schema, correção do conteúdo garantida pela validação de negócio.**

## Erros comuns e armadilhas

- **Confiar apenas no prompt** ("responda em JSON") em produção.
- **Achar que structured output garante valores corretos**: garante o formato, não a veracidade.
- **Não validar no código** porque "a API garante": o schema pode ter limitações, e dados vindos de fora do LLM também precisam de validação.
- **Schema gigante e profundamente aninhado**: aumenta falhas e latência.
- **Campos obrigatórios sem opção de "não sabe"**: força o modelo a inventar valores; use opcionais ou um valor `DESCONHECIDO`.
- **Retry infinito**: sempre limite tentativas e tenha um fallback.
- **Ignorar a ordem dos campos**: colocar a resposta antes do raciocínio elimina o benefício do CoT.
- **Expor parsing de texto com regex** quando a API já oferece schema nativo.

## 🧩 Quiz de Fixação

1. Qual a diferença entre JSON mode, Structured Outputs com schema e constrained decoding quanto às garantias?
2. Por que, mesmo com saída estruturada garantida, é preciso validar o conteúdo no código?
3. Por que colocar o campo `raciocinio` antes de `decisao` no schema pode melhorar a qualidade?

**Respostas:**
1) JSON mode garante apenas sintaxe JSON válida, sem garantir campos ou tipos. Structured Outputs com JSON Schema (no provedor) garante aderência ao schema declarado. Constrained decoding aplica máscara nos tokens durante a geração, tornando impossível violar a gramática por construção, e é implementada em motores de inferência que expõem a distribuição de tokens (Outlines, Guidance, vLLM).
2) Porque o schema garante a forma, não a verdade: o valor pode ser bem formatado e errado (idade trocada, total que não bate com a soma dos itens). A validação de negócio (Pydantic/Zod, regras de consistência) detecta isso, e o retry com o erro permite ao modelo se corrigir ou escalar para revisão humana.
3) Porque o modelo gera os campos na ordem do schema; escrever o raciocínio primeiro funciona como um Chain-of-Thought dentro do JSON, e a decisão seguinte fica condicionada a esse raciocínio. Se a decisão viesse primeiro, o modelo "decidiria" sem pensar e o raciocínio viraria apenas uma justificativa posterior.
