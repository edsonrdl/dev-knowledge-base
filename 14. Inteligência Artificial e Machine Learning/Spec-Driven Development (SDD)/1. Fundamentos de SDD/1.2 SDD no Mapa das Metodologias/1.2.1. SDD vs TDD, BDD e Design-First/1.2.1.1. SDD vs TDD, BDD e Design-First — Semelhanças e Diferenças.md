### SDD vs TDD, BDD e Design-First — Semelhanças e Diferenças

O SDD não nasceu do nada: herda ideias de metodologias que também colocam algo *antes* do código — testes (TDD), comportamento (BDD) e contratos de API (Design-First). Entender o que cada uma faz, e onde o SDD se encaixa, evita dois erros: achar que SDD é "só mais uma moda" ou que substitui tudo o que veio antes.

---

## As quatro abordagens em uma frase

| Abordagem | O que vem primeiro | Pergunta que responde |
|---|---|---|
| **TDD** (Test-Driven Development) | Um teste unitário que falha | "Este trecho de código faz o que eu espero?" |
| **BDD** (Behavior-Driven Development) | Cenários de comportamento em linguagem natural (Given/When/Then) | "O sistema se comporta como o negócio espera?" |
| **Design-First** (API-first) | Um contrato formal (OpenAPI, GraphQL schema, Protobuf) | "Como as partes se comunicam?" |
| **SDD** | Uma especificação completa da feature (intenção, requisitos, plano, tasks) | "O que construir, por quê, e como dividir o trabalho para um agente?" |

**Analogia:** construir uma casa. TDD é testar cada tijolo e cada junta antes de assentar; BDD é combinar com o morador como a casa deve funcionar ("quando chove, a água escoa"); Design-First é desenhar as plantas de encanamento e elétrica; SDD é o projeto arquitetônico completo que reúne intenção, plantas e cronograma — e é entregue a um construtor (o agente de IA).

---

## TDD — Test-Driven Development

Ciclo **Red → Green → Refactor**: escreve-se um teste que falha, implementa-se o mínimo para passar e refatora-se.

```
   ┌──────► RED: escreve teste que falha
   │              │
   │              ▼
   │        GREEN: código mínimo para passar
   │              │
   │              ▼
   └─── REFACTOR: melhora sem quebrar o teste
```

- **Ponto forte:** feedback rápido, design de código testável, rede de segurança.
- **Limite:** testa *unidades*; não captura a intenção de negócio nem decide *quais* features construir. Um teste só é tão bom quanto o entendimento do requisito que o originou.

## BDD — Behavior-Driven Development

Estende o TDD com cenários legíveis por pessoas de negócio, geralmente em Gherkin:

```gherkin
Cenário: Cancelar pedido não enviado
  Dado um pedido com status "PAGO"
  Quando o cliente solicita o cancelamento
  Então o pedido fica "CANCELADO"
  E o pagamento é estornado
```

- **Ponto forte:** linguagem comum entre negócio e desenvolvimento; cenários viram testes de aceitação.
- **Limite:** cobre *comportamento*, mas não as restrições técnicas, a arquitetura nem a decomposição em tarefas.

## Design-First (API-first)

Define-se o contrato antes da implementação:

```yaml
paths:
  /pedidos/{id}/cancelamento:
    post:
      responses:
        "200": { description: Pedido cancelado }
        "409": { description: Pedido já enviado }
```

- **Ponto forte:** equipes front/back trabalham em paralelo; mocks e SDKs gerados do contrato.
- **Limite:** descreve a *interface*, não o porquê, as regras de negócio internas ou os casos de borda.

## Onde o SDD se encaixa

O SDD é **mais abrangente e voltado a agentes**: reúne intenção, requisitos, critérios de aceite, plano técnico e tasks em artefatos que um agente consome. E ele **absorve** as outras três em vez de competir com elas:

```
                 SPEC (SDD)
   ┌──────────────────────────────────────────┐
   │ Intenção e requisitos                    │
   │ Critérios de aceite ──► viram cenários   │ ← BDD
   │ Plano técnico: contratos ──► OpenAPI     │ ← Design-First
   │ Tasks com verificação ──► testes         │ ← TDD
   └──────────────────────────────────────────┘
                      │
                      ▼
            Agente gera o código
```

| Aspecto | TDD | BDD | Design-First | SDD |
|---|---|---|---|---|
| **Artefato central** | Teste unitário | Cenário Gherkin | Contrato de API | Spec + plano + tasks |
| **Nível** | Função/classe | Feature/comportamento | Interface entre sistemas | Feature inteira, ponta a ponta |
| **Público principal** | Desenvolvedor | Negócio + dev + QA | Times consumidores da API | Humanos **e agentes de IA** |
| **Captura o "porquê"?** | Não | Parcialmente | Não | Sim |
| **Decompõe o trabalho?** | Não | Não | Não | Sim (tasks) |
| **Pensado para IA?** | Não | Não | Não | Sim |

## Exemplo prático: as quatro juntas

Feature "cancelar pedido" em um projeto com SDD:

1. **Spec:** requisitos e critérios de aceite em Given/When/Then (*estilo BDD*).
2. **Plano:** endpoint `POST /pedidos/{id}/cancelamento` definido em OpenAPI antes de codar (*estilo Design-First*).
3. **Tasks:** "T3: escrever testes que cobrem os 3 critérios de aceite; T4: implementar até passarem" (*estilo TDD*).
4. **Agente** executa as tasks; humano revisa o código contra a spec.

Cada técnica ocupa o lugar onde é mais forte, e a spec é o fio que as conecta.

---

## Erros comuns e quando usar cada uma

- **"SDD substitui testes"** — falso. A spec define o que testar; sem testes, ninguém verifica se o agente cumpriu.
- **Confundir SDD com Waterfall** — o SDD é iterativo e feito em fatias pequenas (uma feature por vez), com spec leve e revisão rápida; não é "especificar o sistema inteiro por meses".
- **Spec sem critérios testáveis** — vira texto bonito que nada valida.
- **Usar só TDD com agente** — o agente escreve teste *e* código a partir do mesmo prompt vago, validando a própria suposição.

| Cenário | Recomendação |
|---|---|
| Lógica algorítmica isolada | TDD basta |
| Alinhar negócio e dev sobre comportamento | BDD |
| Integração entre times/serviços | Design-First |
| Feature nova entregue a um agente de IA | SDD, usando as demais dentro dele |

## 🧩 Quiz de Fixação

1. Qual o artefato central de cada abordagem: TDD, BDD, Design-First e SDD?
2. Por que dizer que o SDD "absorve" TDD, BDD e Design-First em vez de substituí-los?
3. Um time usa apenas TDD com um agente de IA, que escreve testes e código a partir de um prompt de uma linha. Qual o risco e como o SDD o reduz?

**Respostas:**
1) TDD: teste unitário que falha. BDD: cenário de comportamento em linguagem natural (Given/When/Then). Design-First: contrato formal da interface (OpenAPI, schema). SDD: especificação completa da feature, incluindo intenção, requisitos, critérios de aceite, plano técnico e tasks.
2) Porque a spec do SDD contém elementos de cada uma: os critérios de aceite têm formato BDD, o plano técnico inclui contratos no estilo Design-First e as tasks preveem testes no estilo TDD. Cada técnica continua sendo usada no nível em que é mais forte; o SDD acrescenta o que faltava (intenção, decomposição e consumo por agentes).
3) O agente gera testes e código a partir da mesma suposição vaga, então os testes validam a interpretação dele, não o requisito real: tudo passa, mas o comportamento pode estar errado. Com SDD, os critérios de aceite são escritos e revisados por humanos antes, e os testes derivam deles, de modo que a verificação é independente da suposição do agente.
