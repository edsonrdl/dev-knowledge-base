### O que é Spec-Driven Development e Spec como Fonte da Verdade

Vimos que prompts soltos geram código frágil porque a intenção nunca é registrada. O Spec-Driven Development (SDD) responde a isso com uma inversão simples: **a especificação passa a ser o artefato principal e o código passa a ser consequência dela**. Este arquivo define o conceito, seus princípios e o que muda na prática.

---

## O que é SDD

**Spec-Driven Development** é uma metodologia de desenvolvimento assistido por IA em que se escreve primeiro uma **especificação formal, estruturada e versionada** do que o software deve fazer, e só depois agentes de código geram a implementação a partir dela. A spec é revisada por humanos *antes* de qualquer linha de código existir.

A ideia central cabe em uma frase: **a spec é a fonte da verdade; o código é a sua expressão em uma linguagem de programação.**

**Analogia:** em uma obra, a planta aprovada manda. Se a parede construída diverge da planta, o erro está na parede, não na planta. No SDD, se o código diverge da spec, corrige-se o código (ou, conscientemente, a spec — nunca "no silêncio").

```
Vibe coding                          Spec-Driven Development

  Intenção (na cabeça)                 Intenção (na cabeça)
        │                                    │
        ▼                                    ▼
  Prompt informal                      SPEC revisada e versionada  ◄── fonte da verdade
        │                                    │
        ▼                                    ▼
  Código  ◄── única verdade            Plano técnico → Tasks
  (intenção se perde)                        │
                                             ▼
                                       Código gerado e validado contra a spec
```

---

## Por que a spec é a "fonte da verdade"

Em desenvolvimento tradicional o código é a verdade e a documentação envelhece. Com agentes de IA, o cenário muda por três motivos:

1. **O custo de gerar código caiu drasticamente**, então o gargalo deixou de ser digitar e passou a ser *saber exatamente o que construir*.
2. **O agente executa fielmente o que está escrito** — e inventa onde está em branco. Quanto mais precisa a spec, menos invenção.
3. **Código é regenerável; intenção não.** Se a spec está clara, trocar de framework, linguagem ou modelo de IA vira uma nova geração, não uma reescrita de conhecimento.

| Em vez de... | O SDD propõe... |
|---|---|
| Código como único registro de decisões | Spec versionada no repositório, ao lado do código |
| Revisar apenas o diff de código | Revisar primeiro a spec, depois o código contra ela |
| Contexto no histórico do chat | Contexto em arquivos Markdown que o agente relê a cada tarefa |
| "Pronto" = parece funcionar | "Pronto" = critérios de aceite da spec satisfeitos |

## Os princípios do SDD

| Princípio | Significado |
|---|---|
| **Intenção antes de implementação** | Defina *o quê* e *por quê* antes do *como* |
| **Spec executável pelo agente** | Estruturada o bastante para o agente consumir sem adivinhar |
| **Ambiguidade é bug** | Lacunas são explicitadas e resolvidas antes do código |
| **Refinamento em etapas** | Spec → plano técnico → tasks → código; cada etapa é revisável |
| **Humano nos portões** | Pessoas aprovam cada artefato antes de avançar |
| **Verificabilidade** | Todo requisito tem critério de aceite testável |
| **Versionamento** | Specs vivem no Git, com histórico e revisão por pull request |

## O que uma spec contém (visão geral)

O detalhe vem no Domínio 2; aqui, só o mapa:

```
spec/
├── constitution.md     → princípios inegociáveis do projeto (stack, qualidade, segurança)
├── spec.md             → O QUÊ e POR QUÊ: user stories, requisitos, critérios de aceite
├── plan.md             → COMO: arquitetura, tecnologias, contratos de API, modelo de dados
└── tasks.md            → lista ordenada de tarefas pequenas e verificáveis
```

Uma regra de ouro: **a spec descreve comportamento observável, não implementação.** "O sistema estorna o pagamento integralmente" é spec; "use `stripe.refunds.create()`" é detalhe do plano técnico.

## Exemplo prático: trecho de uma spec

```markdown
# Feature: Recuperação de senha

## Contexto e objetivo
Usuários que esquecem a senha precisam recuperar o acesso sem contatar o suporte.

## Requisitos
- RF-1: O usuário informa o e-mail e recebe um link de redefinição.
- RF-2: O link expira em 30 minutos e é de uso único.
- RF-3: A resposta é a mesma para e-mails cadastrados e não cadastrados
  (evita enumeração de contas).

## Critérios de aceite
- DADO um e-mail cadastrado, QUANDO solicita recuperação, ENTÃO um e-mail
  com link válido é enviado em até 1 minuto.
- DADO um link já utilizado, QUANDO acessado, ENTÃO exibe "link inválido".

## Fora de escopo
Recuperação por SMS; autenticação multifator.
```

Observe: nenhuma menção a framework, banco ou biblioteca. Isso é intencional — a spec sobrevive a mudanças técnicas. O RF-3 é um exemplo de requisito que um prompt solto quase certamente omitiria, e que um agente sem spec implementaria revelando quais e-mails existem.

## Quando o SDD compensa e erros comuns

| Situação | SDD? |
|---|---|
| Feature com regras de negócio, segurança ou integrações | Compensa muito |
| Trabalho em equipe ou com múltiplos agentes | Compensa muito |
| Protótipo descartável de uma tarde | Excessivo |

**Erros comuns:**

- **Escrever uma spec que é código disfarçado** — com nomes de classes e funções; ela perde a função de descrever intenção.
- **Spec vaga demais** ("sistema deve ser rápido") — sem critério mensurável, não verifica nada.
- **Escrever e esquecer** — a spec desatualiza e vira ficção. A manutenção dela é parte do trabalho (tema do tópico de *spec drift*).
- **Burocracia desnecessária** — specs de dezenas de páginas para uma mudança trivial. O tamanho da spec deve ser proporcional ao risco da mudança.
- **Achar que SDD elimina a revisão de código** — a revisão continua; passa a ser feita *contra a spec*.

## 🧩 Quiz de Fixação

1. O que significa dizer que, no SDD, "a spec é a fonte da verdade"?
2. Por que o SDD ganhou relevância justamente com o surgimento de agentes de código?
3. Classifique cada frase como pertencente à spec ou ao plano técnico, justificando: (a) "O link de redefinição expira em 30 minutos"; (b) "Usar Redis para armazenar os tokens de redefinição".

**Respostas:**
1) Significa que o comportamento esperado do sistema é definido e versionado na especificação, e o código é derivado e validado contra ela. Se código e spec divergem, é uma discrepância a corrigir de forma explícita (no código ou na spec), em vez de o código "vencer" por ser o único artefato real.
2) Porque gerar código ficou barato e rápido, deslocando o gargalo para saber com precisão o que construir. Agentes preenchem lacunas com suposições, então a qualidade do resultado depende da qualidade da entrada; uma spec estruturada reduz essa invenção e permite regenerar o código com outro framework ou modelo sem perder o conhecimento do negócio.
3) (a) É spec: descreve comportamento observável e verificável, independente de tecnologia. (b) É plano técnico: escolhe uma tecnologia (Redis) para realizar o requisito; poderia ser trocada sem alterar o comportamento esperado pelo usuário.
