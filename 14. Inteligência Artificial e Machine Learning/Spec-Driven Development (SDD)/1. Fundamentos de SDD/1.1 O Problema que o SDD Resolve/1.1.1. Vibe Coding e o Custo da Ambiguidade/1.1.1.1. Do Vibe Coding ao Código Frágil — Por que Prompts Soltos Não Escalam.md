### Do Vibe Coding ao Código Frágil — Por que Prompts Soltos Não Escalam

Antes de entender o Spec-Driven Development (SDD), é preciso entender a dor que ele cura. Essa dor tem nome: **vibe coding** — pedir código a um agente de IA com prompts informais, aceitar o que vier se "parecer certo" e ir ajustando na conversa. Funciona surpreendentemente bem no começo e degrada rápido. Este arquivo explica por quê.

---

## O que é Vibe Coding

O termo foi popularizado por Andrej Karpathy (início de 2025) para descrever um estilo de programar em que você "se entrega às vibrações": descreve a intenção em linguagem natural, o modelo gera o código, você roda, vê se funciona e pede correções — muitas vezes sem ler o diff. Para protótipos descartáveis, é ótimo. Para software que precisa viver meses, é um risco.

**Analogia:** é como pedir a um pedreiro excelente "faz uma casa legal" e, a cada visita, apontar o que não gostou. Ele é rápido e habilidoso, mas sem planta você terá paredes no lugar errado, e cada correção pode derrubar algo que já estava bom.

```
Vibe coding (ciclo típico)

  Prompt vago ──► Código gerado ──► "Parece ok?" ──► Prompt de correção
       ▲                                                     │
       └─────────────────────────────────────────────────────┘
   (sem critério de pronto, sem registro do que foi decidido)
```

---

## Por que prompts soltos não escalam

O problema não é o modelo — é a **informação que falta no prompt**. O agente é forçado a preencher lacunas com suposições estatisticamente plausíveis, não necessariamente corretas para o seu contexto.

### Os cinco modos de falha

| Modo de falha | O que acontece | Exemplo |
|---|---|---|
| **Ambiguidade** | O modelo escolhe uma interpretação entre várias possíveis | "Adicione login" → ele escolhe sessão em cookie; você queria JWT + OAuth |
| **Perda de contexto** | A decisão tomada na conversa some quando a janela de contexto enche ou a sessão acaba | Regra de negócio explicada há 40 mensagens é ignorada |
| **Sem critério de pronto** | Ninguém sabe quando a feature está completa nem como testá-la | "Funciona na minha demo" vs. casos de borda não tratados |
| **Deriva de arquitetura** | Cada prompt gera código com padrões diferentes | Três formas distintas de acessar o banco no mesmo projeto |
| **Conhecimento no chat, não no repo** | A intenção vive em histórico efêmero; outro dev (ou agente) não a vê | Novo membro não sabe *por que* o código é assim |

### O custo cresce de forma não linear

```
Custo de corrigir
   ▲                                         ╱
   │                                       ╱
   │                                    ╱
   │                              ╱╱╱
   │                      ╱╱╱╱╱
   │──────────╱╱╱╱╱╱╱╱╱╱
   └──────────────────────────────────────────► Tamanho / tempo do projeto
     protótipo        features         sistema em produção
```

No início, cada prompt ajusta uma coisa isolada. Com o tempo, os trechos se acoplam, e uma mudança "simples" exige que o agente (e você) reconstrua mentalmente decisões nunca documentadas.

## Exemplo prático: o mesmo pedido, dois resultados

**Prompt de vibe coding:**

```
Cria um endpoint pra cancelar pedido.
```

O agente precisa adivinhar, entre outras coisas:

- Quem pode cancelar (cliente? admin?)
- Até quando (antes do envio? em 24h?)
- O que acontece com o pagamento (estorno total? parcial?)
- Se o estoque é devolvido
- Qual status HTTP e formato de erro em cada caso
- Se deve ser idempotente

Ele vai escolher **todas** essas respostas sozinho, silenciosamente. Algumas estarão erradas, e você só descobrirá em produção ou em revisão tardia.

**Mesmo pedido com especificação (prévia do SDD):**

```markdown
## Cancelamento de pedido

Como cliente, quero cancelar um pedido ainda não enviado.

Critérios de aceite:
- DADO um pedido com status PAGO ou PREPARANDO, QUANDO o dono solicita
  cancelamento, ENTÃO o status vira CANCELADO e o pagamento é estornado integralmente.
- DADO um pedido com status ENVIADO, QUANDO solicitado, ENTÃO retorna 409
  com código PEDIDO_JA_ENVIADO.
- DADO um pedido já CANCELADO, QUANDO solicitado de novo, ENTÃO retorna 200
  sem efeitos colaterais (idempotente).
- Itens do pedido retornam ao estoque na mesma transação.

Fora de escopo: cancelamento parcial de itens.
```

Agora o agente tem um alvo verificável, e você tem um critério objetivo para revisar e testar. A diferença não é o modelo — é a **qualidade da entrada**.

## Quando o vibe coding é aceitável

Não é um pecado; é uma ferramenta com domínio de validade.

| Cenário | Vibe coding? | Motivo |
|---|---|---|
| Protótipo descartável / prova de conceito | Sim | Velocidade importa mais que manutenção |
| Script pontual de uso único | Sim | Baixo custo de erro |
| Exploração de uma API ou biblioteca nova | Sim | Aprender rápido, jogar fora depois |
| Feature em produto com usuários reais | Não | Precisa de critérios, testes e rastreabilidade |
| Sistema com regras de negócio, segurança ou compliance | Não | Ambiguidade vira bug caro ou vulnerabilidade |
| Código que várias pessoas/agentes manterão | Não | Intenção precisa estar no repositório |

## Erros comuns

- **Culpar o modelo** por um resultado ruim quando o prompt era ambíguo — a causa raiz costuma ser a entrada.
- **Prompt gigante e desestruturado** como "solução": colocar tudo em um texto corrido não substitui estrutura (requisitos, critérios, restrições).
- **Aceitar sem revisar o diff**: o código roda, mas viola convenções ou cria dívida técnica invisível.
- **Tratar o histórico do chat como documentação**: ele é efêmero, não versionado e não pesquisável pelo time.
- **Transformar protótipo em produção** sem reescrever com critérios — o "temporário" costuma virar permanente.

> [!tip] Ponte para o SDD
> O SDD não proíbe a IA de gerar código rápido. Ele move o esforço para **antes** da geração: investe-se em uma especificação clara, versionada e revisável, e deixa-se o agente trabalhar contra ela. É o assunto do próximo conteúdo: *O que é Spec-Driven Development e Spec como Fonte da Verdade* (1.1.2.1).

## 🧩 Quiz de Fixação

1. O que caracteriza o vibe coding e por que ele funciona bem em protótipos?
2. Um colega pede "cria um endpoint pra cancelar pedido" ao agente e aceita o resultado. Cite ao menos quatro decisões que o agente tomou sem que ninguém as especificasse.
3. Compare vibe coding e desenvolvimento orientado a especificação quanto a critério de pronto, memória de decisões e manutenção por múltiplas pessoas.

**Respostas:**
1) Vibe coding é pedir código à IA com prompts informais, aceitando o resultado pela aparência de funcionar e corrigindo por conversa, sem especificação nem leitura cuidadosa. Funciona em protótipos porque o custo de erro é baixo, o código é descartável e a velocidade de iteração compensa a falta de rigor.
2) Entre outras: quem tem permissão para cancelar; até que status/prazo o cancelamento é permitido; se há estorno e se é total ou parcial; se o estoque é devolvido; quais códigos HTTP e formato de erro usar; se a operação é idempotente. O agente escolheu por probabilidade estatística, não por requisito do negócio.
3) No vibe coding, o "pronto" é subjetivo ("parece certo"), as decisões vivem em um chat efêmero e outra pessoa não consegue reconstruir a intenção. No desenvolvimento orientado a especificação, os critérios de aceite definem objetivamente o pronto, as decisões ficam versionadas no repositório e qualquer pessoa ou agente consegue ler a spec para manter ou estender o código de forma consistente.
