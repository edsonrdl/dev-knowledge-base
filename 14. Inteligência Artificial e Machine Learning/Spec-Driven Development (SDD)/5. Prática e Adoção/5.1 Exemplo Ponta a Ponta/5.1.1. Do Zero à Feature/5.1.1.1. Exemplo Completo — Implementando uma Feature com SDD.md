### Exemplo Completo — Implementando uma Feature com SDD

Teoria sem prática não fixa. Este arquivo percorre **uma feature de ponta a ponta**: da ideia solta ao código validado, passando por todos os artefatos e portões vistos no guia. A feature: **limitar tentativas de login** (proteção contra força bruta) em uma API de autenticação.

---

## Cenário

Uma API de e-commerce (Java 21, Spring Boot, PostgreSQL) já tem login por e-mail e senha. O time quer bloquear temporariamente contas com muitas tentativas falhas. A constitution do projeto já define: testes primeiro, simplicidade, nunca logar dados pessoais.

```
 Ideia ─► Specify ─► Clarify ─► Plan ─► Tasks ─► Analyze ─► Implement ─► Revisão
          [P1]       [P2]       [P3]    [P4]      [P5]        [P6]         [P7]
```

---

## Passo 1 — Specify

**Entrada humana:** "Quero bloquear contas após várias tentativas de login falhas."

O agente gera a spec (trecho):

```markdown
# Spec: Bloqueio por tentativas de login

## Contexto
Ataques de força bruta ameaçam contas. Objetivo: dificultar adivinhação de
senhas sem impedir usuários legítimos.

## Histórias
### H1 (P1) Bloquear após falhas consecutivas
Como operador de segurança, quero que contas sejam bloqueadas
temporariamente após falhas repetidas, para reduzir ataques de força bruta.

## Requisitos
- RF-1: QUANDO ocorrerem [NEEDS CLARIFICATION: quantas?] tentativas falhas
  consecutivas, o sistema DEVE bloquear o login da conta por
  [NEEDS CLARIFICATION: quanto tempo?].
- RF-2: ENQUANTO bloqueada, o sistema DEVE recusar o login, mesmo com senha correta.
- RF-3: Um login bem-sucedido DEVE zerar o contador de falhas.
- RF-4: A resposta DEVE ser idêntica para conta inexistente e para senha errada
  (evita enumeração de contas).

## Fora de escopo
CAPTCHA; autenticação multifator; desbloqueio por e-mail.
```

**▶ Portão 1:** o humano percebe duas lacunas marcadas e uma boa decisão (RF-4).

---

## Passo 2 — Clarify

```
Agente: Quantas falhas consecutivas disparam o bloqueio?
        A) 3   B) 5 (recomendado)   C) 10
Humano: B
Agente: Duração do bloqueio?
        A) 5 min   B) 15 min (recomendado)   C) até desbloqueio manual
Humano: B
Agente: O contador de falhas deve expirar sem novas tentativas?
Humano: Sim, após 15 minutos sem falhas.
```

A spec é atualizada: RF-1 = 5 falhas / bloqueio de 15 min; novo RF-5 sobre expiração do contador. Marcadores removidos.

---

## Passo 3 — Plan

```markdown
# Plano
## Contexto técnico
Java 21, Spring Boot 3, PostgreSQL 16, JUnit 5 + Testcontainers

## Constitution check
- Test-First ✔ | Simplicidade ✔ (sem Redis; usa tabela existente) |
- Sem dados pessoais em log ✔ (logar apenas id da conta)

## Modelo de dados
Tabela usuario: + falhas_login INT DEFAULT 0, + ultima_falha TIMESTAMP,
                + bloqueado_ate TIMESTAMP

## Decisões
D1. Contador no próprio banco (RF-1..RF-5); alternativa rejeitada: Redis
    — adiciona infraestrutura sem necessidade na escala atual.
D2. Resposta genérica "credenciais inválidas" para qualquer falha (RF-4).
```

**▶ Portão 2:** arquiteto aprova; pede atenção à concorrência (duas tentativas simultâneas).

---

## Passo 4 — Tasks

```markdown
## Fundação
- [ ] T001 Migração V13: colunas falhas_login, ultima_falha, bloqueado_ate

## H1 — Bloqueio (P1)  ← testes primeiro
- [ ] T002 [P] Teste: 5 falhas bloqueiam por 15 min (RF-1)
- [ ] T003 [P] Teste: conta bloqueada recusa senha correta (RF-2)
- [ ] T004 [P] Teste: login ok zera contador (RF-3)
- [ ] T005 [P] Teste: resposta idêntica p/ conta inexistente (RF-4)
- [ ] T006 [P] Teste: contador expira após 15 min sem falhas (RF-5)
- [ ] T007 Teste de concorrência: 2 falhas simultâneas incrementam 2x
- [ ] T008 Implementar LoginAttemptService (RF-1,2,3,5)
- [ ] T009 Integrar ao AuthService e padronizar resposta (RF-4)
```

---

## Passo 5 — Analyze

```
ALTA   RF-5 tem teste (T006) mas implementação só cobre RF-1,2,3 em T008 — ok após ajuste
MÉDIA  Concorrência (T007) não tem requisito → adicionar RNF-1 na spec
BAIXA  Termo "bloqueio" vs "lockout" inconsistente → padronizar
```

O humano manda corrigir: adiciona RNF-1 (incrementos atômicos), ajusta T008, padroniza o termo.

---

## Passo 6 — Implement

O agente executa **uma task por vez**, com commit para cada:

```
T001 ✔  migração criada e aplicada
T002..T007 ✔  testes escritos — TODOS FALHAM (esperado)
T008 ✔  LoginAttemptService; testes T002,T003,T004,T006 passam
        T007 falha: incremento não atômico
        → correção com UPDATE ... SET falhas_login = falhas_login + 1
T009 ✔  integração; todos os testes passam
```

O teste de concorrência (T007) pegou um bug real: sem a spec e os testes antes, ele provavelmente passaria despercebido.

---

## Passo 7 — Revisão final

| Verificação | Resultado |
|---|---|
| Diff contra a spec: algo fora de escopo? | Não |
| Critérios de aceite RF-1..RF-5 e RNF-1 com testes | Sim |
| Constitution respeitada (sem PII em logs) | Sim |
| Spec atualizada para refletir o que foi feito | Sim |

---

## Lições do exemplo

- A lacuna "quantas tentativas?" foi **resolvida por humano**, não por palpite do modelo.
- O requisito RF-4 (anti-enumeração) existia desde a spec: sem ela, um prompt solto raramente o incluiria.
- O **analyze** pegou uma lacuna de requisito não funcional (concorrência).
- Testes primeiro revelaram um bug de atomicidade ainda na implementação.
- Todo o processo gerou artefatos versionados que um novo agente ou pessoa entende em minutos.

---

## Erros comuns ao praticar

- Gerar tudo de uma vez sem revisar cada portão.
- Aceitar as recomendações do clarify sem refletir.
- Esquecer de atualizar a spec no final.
- Fazer spec grande demais para uma feature simples.
- Pular os testes de borda (concorrência, expiração).

---

## 🧩 Quiz de Fixação

1. Que decisões o clarify resolveu neste exemplo e por que não deixá-las para o agente?
2. Como o analyze e os testes primeiro contribuíram para a qualidade?
3. Reescreva RF-4 sem a restrição anti-enumeração e explique o risco que isso reintroduz.

**Respostas:**
1) Definiu o limite de falhas (5), a duração do bloqueio (15 min) e a expiração do contador. São regras de negócio e segurança; se o agente as chutasse, poderia escolher valores incompatíveis com a política da empresa e ninguém perceberia até um incidente ou reclamação.
2) O analyze apontou falta de requisito para concorrência, inconsistência de termos e cobertura de requisito; já o teste de concorrência escrito antes falhou e revelou um incremento não atômico, corrigido antes de ir para produção.
3) Algo como "o sistema DEVE informar 'senha incorreta' ou 'conta inexistente' conforme o caso". Isso permite enumeração de contas: um atacante descobre quais e-mails estão cadastrados e concentra ataques neles, o que a mensagem genérica evitava.
