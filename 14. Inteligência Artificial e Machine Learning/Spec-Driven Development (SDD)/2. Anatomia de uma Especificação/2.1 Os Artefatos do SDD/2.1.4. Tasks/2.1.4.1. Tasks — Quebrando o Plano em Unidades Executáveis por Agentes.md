### Tasks — Quebrando o Plano em Unidades Executáveis por Agentes

Spec e plano estão aprovados, mas pedir "implemente tudo" a um agente é voltar ao vibe coding em escala maior. O artefato `tasks.md` decompõe o plano em **tarefas pequenas, ordenadas e verificáveis**, que um agente executa uma de cada vez, com revisão entre elas.

---

## O que são as Tasks

Uma task é uma unidade de trabalho que cabe em uma janela de contexto, produz um resultado verificável e pode ser revisada em minutos. O conjunto delas forma o roteiro de implementação, derivado do plano e rastreável aos requisitos da spec.

**Analogia:** é o cronograma de obra. Ninguém manda a equipe "construir o prédio"; define-se fundação, estrutura, instalações e acabamento, cada etapa com critério de conclusão e dependências.

```
 plan.md ──► tasks.md
              ├─ T1  migração do banco               (base)
              ├─ T2  testes do contrato (falham)     (depende de T1)
              ├─ T3  implementar serviço             (depende de T2)
              ├─ T4  endpoint HTTP        [P]        (paralelizável)
              └─ T5  publicar evento de estorno [P]  (paralelizável)
```

---

## Características de uma boa task

| Característica | Por quê | Exemplo ruim → bom |
|---|---|---|
| **Pequena** | Cabe no contexto do agente e é revisável | "Implementar cancelamento" → "Criar `CancelamentoService.cancelar()` com regra de status" |
| **Verificável** | Tem critério objetivo de pronto | "Melhorar a API" → "Teste `cancela_pedido_pago` passa" |
| **Rastreável** | Aponta para requisitos (RF-x) | Sem ID → "Atende RF-1, RF-4" |
| **Com caminho de arquivo** | O agente sabe onde mexer | "Criar serviço" → "`src/.../CancelamentoService.java`" |
| **Ordenada por dependência** | Evita código sem base | Testes antes da implementação (Test-First) |
| **Marcada se paralelizável** | Permite trabalho simultâneo | `[P]` para tarefas independentes |

---

## Organização típica

Agrupar por **história de usuário** mantém cada fatia entregável sozinha (MVP incremental):

```
Fase 1 — Setup (infra comum)
Fase 2 — Fundação (pré-requisitos bloqueantes: migração, modelos base)
Fase 3 — História 1 (P1): testes → modelos → serviço → endpoint   ← MVP
Fase 4 — História 2 (P2): ...
Fase N — Polimento (documentação, observabilidade, hardening)
```

Cada fase termina em um **checkpoint**: o que deve estar funcionando e como validar.

---

## Exemplo prático

```markdown
# Tasks: Cancelamento de Pedido

## Fase 2 — Fundação
- [ ] T001 Criar migração V12__adiciona_cancelamento.sql (cancelado_em, motivo)

## Fase 3 — História 1: cancelar pedido (P1)
Testes primeiro (devem FALHAR antes de implementar):
- [ ] T002 [P] Teste de contrato POST /pedidos/{id}/cancelamento em
      src/test/.../CancelamentoContratoTest.java  (RF-1, RF-4)
- [ ] T003 [P] Teste de integração de idempotência em
      src/test/.../CancelamentoIdempotenteTest.java  (RF-5)

Implementação:
- [ ] T004 Implementar CancelamentoService em src/main/.../CancelamentoService.java
      (RF-1, RF-3, RF-5) — depende de T001, T002
- [ ] T005 Implementar CancelamentoController (RF-4) — depende de T004
- [ ] T006 Publicar evento PedidoCancelado em EstornoPublisher (RF-2) — depende de T004

Checkpoint: T002 e T003 passam; curl do quickstart retorna 200/409 conforme esperado.
```

O agente executa **T001**, para; humano revisa; segue para T002, e assim por diante. Cada commit corresponde a uma task, facilitando reverter.

## Erros comuns e limitações

- **Tasks gigantes** ("implementar backend"): voltam ao problema do prompt vago.
- **Tasks sem critério de pronto**: o agente declara sucesso sem prova.
- **Ordem errada**: implementar antes dos testes viola o Test-First e esconde falhas.
- **Dependências escondidas**: marcar `[P]` em tasks que editam o mesmo arquivo gera conflito.
- **Não atualizar o arquivo**: marque as tasks concluídas; senão o agente não sabe o estado.
- **Tasks demais para uma mudança trivial**: proporcione o detalhamento ao risco.

| Cenário | Granularidade |
|---|---|
| Mudança de uma linha | Dispensa tasks |
| Feature média | 5–15 tasks |
| Feature grande ou área sensível | Dividir em várias specs, cada uma com suas tasks |

## 🧩 Quiz de Fixação

1. Por que decompor o plano em tasks em vez de pedir a implementação inteira?
2. Quais características tornam uma task boa para um agente de IA?
3. Por que organizar as tasks por história de usuário e colocar testes antes da implementação?

**Respostas:**
1) Porque tarefas grandes excedem o contexto do agente, aumentam a chance de suposições erradas e dificultam a revisão. Tarefas pequenas permitem validar o resultado em cada passo, reverter facilmente e manter o humano no controle.
2) Ser pequena, verificável (critério objetivo de pronto), rastreável a requisitos, indicar os arquivos envolvidos, respeitar a ordem de dependência e sinalizar o que pode ser paralelizado.
3) Organizar por história permite entregar valor em fatias independentes (um MVP já na primeira história). Testes primeiro garantem que o critério de aceite exista antes do código, impedindo que o agente valide a própria suposição e tornando a falha visível.
