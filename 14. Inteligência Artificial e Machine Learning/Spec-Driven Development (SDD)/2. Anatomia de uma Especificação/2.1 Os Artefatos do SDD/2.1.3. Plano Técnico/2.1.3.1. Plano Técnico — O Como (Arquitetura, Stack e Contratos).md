### Plano Técnico — O Como (Arquitetura, Stack e Contratos)

Com a spec funcional aprovada, sabemos *o quê* construir. O **plano técnico** responde *como*: quais componentes, que tecnologias, quais contratos e que modelo de dados. É a ponte entre a intenção do negócio e o código, e é o último ponto barato para corrigir o rumo antes da implementação.

---

## O que é o Plano Técnico

O plano técnico (`plan.md`) traduz a spec em **decisões de engenharia**, respeitando a constitution. Enquanto a spec é estável e independente de tecnologia, o plano é onde a tecnologia entra. Uma mesma spec pode gerar planos diferentes (por exemplo, monolito Spring ou função serverless), sem mudar o comportamento esperado.

**Analogia:** a spec é o briefing do cliente; o plano é o projeto executivo do engenheiro, com o tipo de fundação, as plantas elétrica e hidráulica e a lista de materiais.

```
 constitution ─┐ (restringe)
               ▼
 spec.md ───► plan.md ───► tasks.md ───► código
 (o quê)      (como)

 Cada decisão do plano deve ser rastreável a um requisito da spec
 e compatível com a constitution.
```

---

## Conteúdo de um bom plano

| Seção | O que registra | Exemplo |
|---|---|---|
| **Resumo da abordagem** | Estratégia em poucas linhas | "Novo endpoint no serviço de pedidos; estorno via fila assíncrona" |
| **Contexto técnico** | Linguagem, frameworks, banco, testes, plataforma | Java 21, Spring Boot 3, PostgreSQL, JUnit 5 |
| **Constitution check** | Conformidade com cada princípio | "Test-First: ok; Simplicidade: ok" |
| **Arquitetura / estrutura** | Componentes e onde ficam no repositório | Diagrama + árvore de diretórios |
| **Modelo de dados** | Entidades, campos, relações, migrações | Tabela `pedido`, coluna `cancelado_em` |
| **Contratos** | APIs, eventos, mensagens (OpenAPI, schemas) | `POST /pedidos/{id}/cancelamento` |
| **Decisões e alternativas** | O que foi escolhido, o que foi descartado e por quê | "Fila vs chamada síncrona ao gateway" |
| **Riscos e pesquisa** | Incertezas técnicas e como validá-las | "Confirmar idempotência do estorno no gateway" |
| **Quickstart de validação** | Passos para verificar que funciona | Comandos/curl para o cenário principal |

## Rastreabilidade: do requisito à decisão

Cada decisão deve apontar para o requisito que a justifica. Isso evita "enfeites técnicos" e permite revisar o plano contra a spec.

```
RF-2: estornar integralmente ao cancelar
   └─► Decisão D1: publicar evento PedidoCancelado em fila
        └─► Motivo: gateway de pagamento é lento (RNF-1: resposta em 2 s)
RF-5: idempotência
   └─► Decisão D2: chave de idempotência = id do pedido + "cancelamento"
```

Também documente **alternativas rejeitadas**. É o que impede que, três meses depois, alguém (ou um agente) proponha de novo a mesma ideia já descartada.

## Exemplo prático: trecho de um plan.md

```markdown
# Plano: Cancelamento de Pedido

## Contexto técnico
Java 21 · Spring Boot 3 · PostgreSQL 16 · RabbitMQ · JUnit 5 + Testcontainers

## Constitution check
- Test-First: tasks de teste precedem as de implementação ✔
- Simplicidade: reutiliza o serviço de pedidos existente, sem novo microsserviço ✔

## Contrato
POST /pedidos/{id}/cancelamento
  200 → { "status": "CANCELADO" }
  404 → pedido inexistente ou de outro usuário
  409 → { "codigo": "PEDIDO_JA_ENVIADO" }

## Modelo de dados
Tabela pedido: + cancelado_em TIMESTAMP NULL, + motivo_cancelamento VARCHAR(255)
Migração: V12__adiciona_cancelamento.sql (reversível)

## Decisões
D1. Estorno assíncrono via fila (RF-2, RNF-1).
    Alternativa rejeitada: chamada síncrona ao gateway — viola RNF-1 em picos.
D2. Idempotência por (pedido_id, tipo_operacao) com índice único (RF-5).

## Estrutura de código
src/main/java/.../pedido/cancelamento/
  CancelamentoController.java
  CancelamentoService.java
  EstornoPublisher.java
```

O contrato responde ao RF-4 (409 informando o motivo) e a decisão D1 mostra o "porquê" ligado a um requisito não funcional.

## Erros comuns e limitações

- **Plano que contradiz a spec** — introduz comportamento que ninguém pediu. Revise sempre plano versus spec.
- **Ignorar a constitution** — o constitution check existe para isso; violações precisam de justificativa explícita.
- **Overengineering** — camadas e padrões "para o futuro". Prefira o menor design que cumpre a spec.
- **Plano sem alternativas** — decisões sem contexto são difíceis de questionar depois.
- **Deixar contratos vagos** — o agente inventa formatos de erro e campos; defina-os explicitamente.
- **Detalhar linha de código** — o plano decide estrutura e contratos, não escreve a implementação.

| Aspecto | Spec funcional | Plano técnico |
|---|---|---|
| **Foco** | O quê e por quê | Como |
| **Estabilidade** | Alta | Pode mudar com a tecnologia |
| **Quem valida** | Negócio + produto + engenharia | Engenharia (arquitetura, segurança) |
| **Menciona tecnologia?** | Não | Sim |

## 🧩 Quiz de Fixação

1. Qual a diferença entre spec funcional e plano técnico, e por que a separação é útil?
2. O que é o constitution check e em que momento do fluxo ele acontece?
3. Por que registrar alternativas rejeitadas no plano?

**Respostas:**
1) A spec define comportamento observável (o quê e por quê), sem tecnologia; o plano define a solução técnica (arquitetura, stack, contratos). A separação permite que a spec permaneça válida enquanto o plano muda (outra stack, outra arquitetura) e que cada artefato seja revisado pelo público certo.
2) É a verificação de que o plano respeita cada princípio da constitution (stack, testes, segurança, simplicidade). Acontece durante o planejamento, antes das tasks e do código; violações devem ser corrigidas ou justificadas, e a constitution só é alterada por emenda formal.
3) Porque evidenciam o raciocínio por trás da escolha e evitam reabrir discussões já resolvidas. Elas ajudam futuros mantenedores e agentes a entender restrições (como "chamada síncrona viola RNF-1") e a reavaliar a decisão apenas se o contexto mudar.
