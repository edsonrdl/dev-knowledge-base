### Constitution — Os Princípios Inegociáveis do Projeto

Uma feature tem sua própria spec, mas há regras que valem para **todas** as features: a stack, os padrões de qualidade, as políticas de segurança. Repeti-las em cada spec é cansativo e fácil de esquecer. A **constitution** é o artefato que concentra essas regras permanentes, para que todo agente as leia antes de fazer qualquer coisa.

---

## O que é a Constitution

A constitution é um documento (geralmente `constitution.md`) que registra os **princípios inegociáveis** do projeto: decisões de alto nível que não mudam de feature para feature e que o agente deve obedecer sempre. O termo é popularizado pelo GitHub Spec Kit, mas a ideia existe sob outros nomes (steering files no Kiro, regras do projeto em `CLAUDE.md`/`AGENTS.md`).

**Analogia:** é a constituição de um país. As leis ordinárias (as specs de feature) podem mudar com frequência, mas todas precisam respeitar a constituição. Se uma lei a contradiz, a lei é que está errada.

```
        ┌───────────────────────────────┐
        │        CONSTITUTION           │  ← vale para tudo, muda raramente
        │ stack, qualidade, segurança   │
        └──────────────┬────────────────┘
                       │ restringe
     ┌─────────────────┼─────────────────┐
     ▼                 ▼                 ▼
  Spec feature A   Spec feature B   Spec feature C   ← mudam com frequência
```

## O que colocar (e o que não colocar)

| Categoria | Exemplos de princípios |
|---|---|
| **Stack e tecnologia** | "Backend em Java 21 + Spring Boot; banco PostgreSQL; sem ORMs novos sem aprovação" |
| **Arquitetura** | "Arquitetura hexagonal; domínio não depende de frameworks" |
| **Qualidade e testes** | "Todo código novo exige testes; cobertura mínima de 80%; testes antes da implementação" |
| **Segurança** | "Nunca logar dados pessoais; segredos só via variáveis de ambiente; validar toda entrada" |
| **Convenções** | "Nomes de API em inglês, mensagens ao usuário em português; commits convencionais" |
| **Simplicidade** | "Preferir a solução mais simples; sem abstração sem ao menos dois usos reais" |
| **Compliance** | "Dados de usuários europeus seguem GDPR; auditoria em operações financeiras" |

**O que NÃO colocar:**
- Requisitos de uma feature específica (vão na spec daquela feature).
- Detalhes voláteis (versões que mudam toda semana, nomes de branches).
- Texto vago e aspiracional ("escreva código limpo") — não é verificável.

---

## Como funciona na prática

O agente lê a constitution **antes** de gerar spec, plano ou código. No fluxo do Spec Kit, o comando de planejamento inclui uma etapa de *constitution check*: o plano técnico é confrontado com cada princípio, e qualquer violação precisa ser justificada ou corrigida.

```
Plano técnico proposto: "usar MongoDB para os pedidos"
          │
          ▼
Constitution check:  "Banco: PostgreSQL" ──► VIOLAÇÃO
          │
          ▼
Opções: (a) ajustar o plano para PostgreSQL
        (b) emendar a constitution (decisão humana, registrada)
```

Princípios bem escritos têm três propriedades:

| Propriedade | Ruim | Bom |
|---|---|---|
| **Verificável** | "O código deve ser seguro" | "Toda entrada externa passa por validação com schema" |
| **Com justificativa** | "Não usar bibliotecas novas" | "Não usar bibliotecas novas sem ADR, para limitar a superfície de manutenção" |
| **Priorizado** | Lista de 40 regras iguais | Poucos princípios, ordenados por importância |

## Exemplo prático

```markdown
# Constitution — Projeto Loja Online

## Princípio I — Test-First (inegociável)
Nenhum código de produção é escrito antes de existirem testes que falham
e que cobrem os critérios de aceite da spec.

## Princípio II — Simplicidade
Começar com o menor design que satisfaz a spec. Sem camadas, padrões ou
bibliotecas "para o futuro". Complexidade extra exige justificativa escrita.

## Princípio III — Segurança por padrão
- Segredos nunca entram no repositório.
- Dados pessoais nunca aparecem em logs.
- Toda entrada externa é validada.

## Princípio IV — Stack
Java 21, Spring Boot 3, PostgreSQL 16. Mudanças de stack exigem emenda
desta constitution.

## Governança
Emendas são feitas por pull request, com aprovação de dois mantenedores
e nota de migração para specs existentes.
```

Observe a seção **Governança**: a constitution também define *como ela própria muda*. Sem isso, ela é alterada informalmente e perde autoridade.

## Erros comuns e limitações

- **Constitution gigante** — quanto mais longa, menos o agente (e as pessoas) a respeitam; contexto é recurso limitado.
- **Regras que ninguém verifica** — sem revisão ou teste, o princípio vira decoração.
- **Misturar com spec de feature** — duplica conteúdo e cria contradições.
- **Nunca atualizar** — uma constitution desatualizada leva o agente a seguir práticas já abandonadas.
- **Tratar como garantia absoluta** — o agente *tende* a obedecer, mas pode falhar; a revisão humana e checks automatizados continuam necessários.

| Cenário | Recomendação |
|---|---|
| Projeto novo | Comece com 5 a 8 princípios essenciais |
| Projeto existente (brownfield) | Extraia da base de código e dos ADRs as regras já praticadas |
| Vários times/repositórios | Constitution comum da organização + extensões por projeto |

## 🧩 Quiz de Fixação

1. O que é a constitution e que papel ela cumpre em relação às specs de feature?
2. Cite três características de um bom princípio de constitution e dê um exemplo ruim e um bom.
3. O plano técnico de uma feature propõe usar MongoDB, mas a constitution fixa PostgreSQL. Como o fluxo SDD deve tratar isso?

**Respostas:**
1) É o documento que reúne princípios permanentes e inegociáveis do projeto (stack, qualidade, segurança, convenções). Ela restringe todas as specs de feature: o que está nela vale sempre, e specs e planos não podem contradizê-la sem uma decisão explícita.
2) Verificável, justificado e priorizado. Exemplo ruim: "o código deve ser seguro". Exemplo bom: "toda entrada externa é validada com schema" — dá para checar objetivamente em revisão ou teste.
3) O *constitution check* deve apontar a violação. Há duas saídas legítimas: ajustar o plano para usar PostgreSQL ou, se há razão forte para MongoDB, emendar a constitution por um processo de governança registrado. Não se deve ignorar a regra em silêncio.
