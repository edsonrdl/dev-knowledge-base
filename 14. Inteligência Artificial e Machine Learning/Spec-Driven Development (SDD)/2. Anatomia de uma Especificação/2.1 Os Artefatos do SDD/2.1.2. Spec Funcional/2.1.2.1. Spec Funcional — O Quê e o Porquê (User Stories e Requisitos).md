### Spec Funcional — O Quê e o Porquê (User Stories e Requisitos)

Se a constitution diz como o projeto trabalha sempre, a **spec funcional** diz o que uma feature específica deve fazer e por que ela existe. É o artefato central do SDD: tudo que vem depois (plano, tasks, código) deriva dela. Escrevê-la bem é a habilidade mais valiosa da metodologia.

---

## O que é a Spec Funcional

A spec funcional (`spec.md`) descreve o **comportamento observável** de uma feature do ponto de vista de quem a usa, sem prescrever tecnologia. Responde duas perguntas: **o quê** o sistema deve fazer e **por quê** isso importa. A pergunta "como" fica para o plano técnico.

**Analogia:** é o briefing que um cliente entrega a um arquiteto: "quero uma casa onde a família se reúna na cozinha e que seja acessível para cadeirantes". Ele não diz qual tipo de viga usar; isso é decisão técnica posterior.

```
  spec.md  (O QUÊ + POR QUÊ)  ──►  plan.md (COMO)  ──►  tasks.md  ──►  código
     │
     └─ independente de linguagem, framework e banco
```

---

## Estrutura típica de uma spec funcional

| Seção | Conteúdo | Pergunta que responde |
|---|---|---|
| **Contexto / Objetivo** | Problema e valor para o usuário ou negócio | Por que isto existe? |
| **User stories** | Histórias priorizadas de uso | Quem precisa de quê? |
| **Requisitos funcionais** | Capacidades que o sistema deve ter | O que ele faz? |
| **Requisitos não funcionais** | Desempenho, segurança, acessibilidade | Com que qualidade? |
| **Critérios de aceite** | Condições verificáveis de "pronto" | Como sei que funciona? |
| **Casos de borda** | Situações limite e falhas | E se algo der errado? |
| **Fora de escopo** | O que não será feito agora | Onde paramos? |
| **Entidades-chave** | Conceitos de domínio (sem esquema de banco) | Sobre o que falamos? |

---

## User stories

Formato clássico: **Como** [papel], **quero** [capacidade], **para** [benefício].

O "para" é o ponto mais importante e o mais esquecido: é o *porquê*. Ele permite que o agente (e a equipe) tome boas decisões em situações não previstas.

No SDD, as histórias são **priorizadas** (P1, P2, P3) e cada uma deve ser **independentemente testável**: implementar só a P1 já deve entregar um valor demonstrável (um MVP).

```markdown
### História 1 — Cancelar pedido (P1)
Como cliente, quero cancelar um pedido que ainda não foi enviado,
para não pagar por algo que desisti de receber.

Por que P1: é a principal causa de contato com o suporte.
Teste independente: criar pedido pago, cancelar, verificar estorno.

### História 2 — Cancelamento parcial (P3)
Como cliente, quero cancelar apenas alguns itens do pedido...
```

## Requisitos funcionais bem escritos

Cada requisito deve ser **atômico, testável e sem implementação**. Use identificadores (RF-1, RF-2) para rastreabilidade: tasks e testes referenciam esses IDs.

| Ruim | Problema | Bom |
|---|---|---|
| "O sistema deve ser rápido" | Não mensurável | "A listagem de pedidos responde em até 300 ms para 95% das requisições" |
| "Usar JWT para autenticar" | Detalhe de implementação | "Somente usuários autenticados podem cancelar seus próprios pedidos" |
| "Cancelar pedidos e avisar o cliente e devolver estoque" | Vários requisitos em um | Três requisitos separados (RF-1, RF-2, RF-3) |
| "Deve ser intuitivo" | Subjetivo | "Um usuário novo conclui o cancelamento em até 3 cliques" |

Use verbos de obrigatoriedade consistentes: **DEVE** (obrigatório), **DEVERIA** (recomendado), **PODE** (opcional).

## Exemplo prático: spec funcional compacta

```markdown
# Spec: Cancelamento de Pedido

## Contexto
Cancelamentos hoje exigem contato com o suporte (35% dos chamados).
Objetivo: permitir autoatendimento seguro.

## Requisitos funcionais
- RF-1: O sistema DEVE permitir que o dono do pedido o cancele enquanto
  seu status for PAGO ou PREPARANDO.
- RF-2: O sistema DEVE estornar integralmente o valor pago ao cancelar.
- RF-3: O sistema DEVE devolver os itens ao estoque ao cancelar.
- RF-4: O sistema DEVE recusar o cancelamento de pedidos ENVIADOS,
  informando o motivo.
- RF-5: Cancelar um pedido já cancelado NÃO DEVE gerar efeitos colaterais.

## Requisitos não funcionais
- RNF-1: O cancelamento conclui em até 2 s para 95% das requisições.
- RNF-2: Toda operação é registrada em auditoria (quem, quando, motivo).

## Fora de escopo
Cancelamento parcial de itens; cancelamento por terceiros.

## Entidades-chave
Pedido (status, valor, itens), Pagamento (valor, estado do estorno).
```

Note que **nada** diz banco, framework ou formato de token. Se amanhã a stack mudar, a spec continua válida.

## Erros comuns e limitações

- **Misturar o "como" na spec** — "criar tabela `cancelamentos` com índice X" pertence ao plano.
- **Pular o "por quê"** — sem contexto, o agente otimiza o lado errado em casos ambíguos.
- **Requisitos subjetivos** — "amigável", "robusto", "escalável" não são verificáveis.
- **Spec monolítica** — uma spec para o sistema inteiro; prefira uma por feature, em fatias pequenas.
- **Detalhar demais o que não importa e de menos o que importa** — invista em regras de negócio, casos de borda e segurança.
- **Não marcar o que não se sabe** — lacunas devem ficar explícitas (veja o tópico de marcadores de clarificação), nunca preenchidas por suposição.

| Cenário | Recomendação |
|---|---|
| Mudança trivial (corrigir texto) | Spec de poucas linhas ou nenhuma |
| Feature com regras de negócio | Spec completa com critérios de aceite |
| Área sensível (pagamento, dados pessoais) | Spec detalhada com requisitos não funcionais explícitos |

## 🧩 Quiz de Fixação

1. Que perguntas a spec funcional responde e qual fica de fora dela?
2. Por que o trecho "para [benefício]" da user story é tão importante no SDD?
3. Reescreva "o sistema deve ser rápido e usar Redis para cache" separando o que é spec e o que é plano, e tornando o requisito verificável.

**Respostas:**
1) Responde *o quê* o sistema deve fazer e *por quê* (valor para usuário ou negócio). O *como* — arquitetura, tecnologia, esquemas — fica de fora e vai para o plano técnico.
2) Porque explicita a motivação, permitindo que agentes e pessoas tomem decisões coerentes em situações que a spec não previu, escolhendo a opção que serve ao benefício real em vez de adivinhar. Também ajuda a priorizar histórias por valor.
3) Spec: "A listagem de produtos DEVE responder em até 200 ms para 95% das requisições" (mensurável e sem tecnologia). Plano: "Usar Redis como cache da listagem, com TTL de 60 s, para atender ao RNF de latência". A escolha do Redis é solução técnica e poderia ser trocada sem alterar o requisito.
