### Non-Goals, Edge Cases e Marcadores de Clarificação

Mesmo uma spec bem estruturada falha se deixar lacunas. Quando há um branco, o agente preenche com a opção estatisticamente mais provável. Este arquivo apresenta três ferramentas para **tornar as lacunas visíveis antes do código**: non-goals (o que não faremos), edge cases (o que acontece nos limites) e marcadores de clarificação (o que ainda não sabemos).

---

## Princípio: ambiguidade é bug

Todo "depende" não resolvido é uma decisão que alguém tomará sem você: o agente. A meta não é prever tudo, mas garantir que **o que é desconhecido esteja marcado**, e não escondido.

```
Spec com lacuna escondida          Spec com lacuna explícita
  "Usuário pode cancelar"            "Usuário pode cancelar
        │                              [NEEDS CLARIFICATION: até quando?]"
        ▼                                      │
 Agente supõe "a qualquer momento"             ▼
 (decisão silenciosa, talvez errada)    Humano responde antes do código
```

---

## 1. Non-Goals (Fora de Escopo)

Declaram **o que a feature não fará**. Controlam o *scope creep* do agente, que tende a ser "prestativo" e acrescentar extras.

| Sem non-goals | Com non-goals |
|---|---|
| Agente adiciona cancelamento parcial "por garantia" | "Fora de escopo: cancelamento parcial" |
| Cria painel admin que ninguém pediu | "Fora de escopo: telas administrativas" |
| Mexe em módulos vizinhos | "Não alterar o módulo de faturamento" |

Escreva-os com a justificativa quando útil: *"Fora de escopo (v1): cancelamento por SMS — baixa demanda"*. Isso evita reabrir discussão.

---

## 2. Edge Cases (Casos de Borda)

São situações nos limites do comportamento normal. É onde os bugs moram, e onde o agente mais inventa.

Checklist para levantar casos de borda:

| Categoria | Perguntas |
|---|---|
| **Vazio / nulo** | E se a lista estiver vazia? E se o campo faltar? |
| **Limites** | Valor mínimo/máximo? Exatamente no limite? |
| **Duplicidade / repetição** | E se a ação for executada duas vezes? (idempotência) |
| **Concorrência** | Duas pessoas agem ao mesmo tempo no mesmo recurso? |
| **Falha externa** | E se o gateway/serviço cair no meio? |
| **Permissão** | E se outro usuário tentar? |
| **Tempo** | Fuso horário, expiração, virada de dia? |
| **Volume** | E com 100 mil itens? |

Exemplo (cancelamento):

```markdown
## Casos de borda
- Pedido já cancelado → 200 sem efeitos colaterais.
- Dois cancelamentos simultâneos → apenas um estorno é criado.
- Gateway indisponível durante o estorno → pedido fica CANCELADO e
  estorno entra em fila de nova tentativa.
- Pedido de outro usuário → 404 (não revelar existência).
```

## 3. Marcadores de Clarificação

Quando uma informação necessária **não está disponível**, não a invente: marque-a. Convenção popularizada pelo GitHub Spec Kit: `[NEEDS CLARIFICATION: pergunta]`.

```markdown
- RF-6: O sistema DEVE permitir cancelamento até
  [NEEDS CLARIFICATION: prazo máximo após a compra — 24h? 7 dias? sem limite?]
- RF-7: O estorno DEVE ser feito
  [NEEDS CLARIFICATION: no mesmo meio de pagamento ou como crédito na loja?]
```

Regras:
1. O agente **deve** criar marcadores em vez de assumir (isto pode constar na constitution ou no prompt do comando).
2. Cada marcador é uma **pergunta concreta**, de preferência com opções.
3. A spec **não avança** para o plano enquanto houver marcadores abertos (portão de qualidade).
4. Ao resolver, substitua o marcador pela decisão e registre-a (seção de *Clarificações*).

```markdown
## Clarificações
- Sessão 2026-03-10: Prazo de cancelamento → até 7 dias após a compra, se
  não enviado. Estorno → mesmo meio de pagamento.
```

## Exemplo prático: spec antes e depois

**Antes (ambígua):**
```
O usuário pode cancelar o pedido e receber o dinheiro de volta.
```

**Depois:**
```markdown
- RF-1: QUANDO o dono cancela pedido PAGO ou PREPARANDO, o sistema DEVE
  estornar integralmente no mesmo meio de pagamento.
- RF-4: ENQUANTO ENVIADO, o sistema DEVE recusar o cancelamento (409).
- Fora de escopo: cancelamento parcial; cancelamento por terceiros.
- Borda: cancelamento repetido é idempotente.
- Em aberto: [NEEDS CLARIFICATION: prazo máximo após a compra?]
```

## Erros comuns e limitações

- **Preencher lacunas "por bom senso"**: o bom senso do modelo não é o do seu negócio.
- **Non-goals ausentes**: o agente entrega extras que viram dívida e superfície de bugs.
- **Lista de bordas só com o óbvio**: revise com um colega ou use o checklist acima.
- **Marcadores esquecidos**: fazer o plano com marcadores abertos propaga a dúvida para o código.
- **Excesso de perguntas**: marque só o que impacta escopo, segurança, UX ou dados; o resto, use padrões razoáveis documentados.

| Item | Marcar como [NEEDS CLARIFICATION]? |
|---|---|
| Prazo de cancelamento, regra de negócio | Sim |
| Cor de um botão secundário | Não (padrão razoável) |
| Quem tem permissão | Sim (segurança) |

## 🧩 Quiz de Fixação

1. Qual o papel dos non-goals e que problema do agente eles previnem?
2. Cite quatro categorias para levantar casos de borda e uma pergunta de cada.
3. Por que usar `[NEEDS CLARIFICATION]` em vez de deixar o agente assumir o que falta?

**Respostas:**
1) Declaram o que a feature não fará. Previnem o scope creep: o agente tende a adicionar funcionalidades extras "por garantia", gerando código não solicitado, dívida técnica e mais superfície de bugs.
2) Exemplos: vazio/nulo (e se o campo faltar?), duplicidade (e se a ação rodar duas vezes?), concorrência (e se dois usuários agirem juntos?), falha externa (e se o gateway cair no meio?), permissão (e se outro usuário tentar?), limites e tempo também valem.
3) Porque a suposição do agente é uma decisão silenciosa baseada em probabilidade, não em regras do negócio. O marcador torna a dúvida visível e bloqueia o avanço até um humano decidir, evitando que a lacuna vire código errado.
