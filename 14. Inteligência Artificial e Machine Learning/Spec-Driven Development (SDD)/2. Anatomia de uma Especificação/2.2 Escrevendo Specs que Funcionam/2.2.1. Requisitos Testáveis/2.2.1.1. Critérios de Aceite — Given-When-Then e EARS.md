### Critérios de Aceite — Given-When-Then e EARS

Um requisito sem critério de aceite é uma opinião. Este arquivo mostra duas notações que transformam requisitos em condições **verificáveis**: Given-When-Then (herdada do BDD) e EARS (Easy Approach to Requirements Syntax). Ambas reduzem ambiguidade e servem de base direta para testes automatizados.

---

## Por que critérios de aceite

O critério de aceite define **objetivamente** quando algo está pronto. Para um agente de IA, ele é o alvo; para o revisor, é o checklist; para o teste, é a especificação executável. Sem ele, "pronto" volta a ser "parece certo".

**Analogia:** é o gabarito da prova. Sem gabarito, ninguém sabe se a resposta está certa — só se parece boa.

---

## Given-When-Then (Dado-Quando-Então)

Estrutura de cenário em três partes:

| Parte | Função | Pergunta |
|---|---|---|
| **Given (Dado)** | Estado inicial / pré-condições | Qual é o contexto? |
| **When (Quando)** | Ação ou evento | O que acontece? |
| **Then (Então)** | Resultado observável | O que deve ser verdade depois? |

```
DADO um pedido com status PAGO pertencente ao usuário A
QUANDO o usuário A solicita o cancelamento
ENTÃO o status do pedido passa a CANCELADO
  E o valor integral é estornado
  E os itens retornam ao estoque
```

Regras de ouro:
- **Um comportamento por cenário.** Cenários que testam cinco coisas escondem qual falhou.
- **Then observável**, não interno: "retorna 409", não "a variável flag é true".
- **Given completo**: inclua todo o estado necessário, senão o agente supõe.
- Cubra caminho feliz, **erros** e **bordas** (vazio, limite, duplicado, concorrência).

## EARS — Easy Approach to Requirements Syntax

Notação criada na Rolls-Royce para escrever requisitos em linguagem natural estruturada, com poucos padrões. É usada, por exemplo, pelo Kiro em seus arquivos de requisitos.

| Padrão | Template | Exemplo |
|---|---|---|
| **Ubíquo** | O sistema DEVE `<resposta>` | O sistema DEVE registrar toda operação de cancelamento em auditoria |
| **Orientado a evento** | QUANDO `<evento>`, o sistema DEVE `<resposta>` | QUANDO o cliente solicita cancelamento de pedido PAGO, o sistema DEVE estornar o valor |
| **Orientado a estado** | ENQUANTO `<estado>`, o sistema DEVE `<resposta>` | ENQUANTO o pedido estiver ENVIADO, o sistema DEVE recusar cancelamento |
| **Comportamento indesejado** | SE `<condição>`, ENTÃO o sistema DEVE `<resposta>` | SE o gateway de pagamento estiver indisponível, ENTÃO o sistema DEVE enfileirar o estorno para nova tentativa |
| **Opcional** | ONDE `<recurso presente>`, o sistema DEVE `<resposta>` | ONDE o cliente tiver cashback, o sistema DEVE estornar também o crédito |
| **Complexo** | Combinação dos anteriores | ENQUANTO PAGO, QUANDO cancelado, o sistema DEVE ... |

## Given-When-Then vs EARS

```
EARS           → requisito em UMA frase (o que o sistema deve fazer)
Given-When-Then → cenário de TESTE (como verificar)

RF-1 (EARS): QUANDO o cliente cancela pedido PAGO, o sistema DEVE estornar.
                       │
                       ▼ gera
Cenário (GWT): DADO pedido PAGO / QUANDO cancela / ENTÃO estorno integral
```

| Aspecto | Given-When-Then | EARS |
|---|---|---|
| **Foco** | Verificação do comportamento | Redação do requisito |
| **Tamanho** | Cenário com várias linhas | Uma sentença |
| **Origem** | BDD / Gherkin | Engenharia de requisitos |
| **Uso ideal** | Critérios de aceite e testes | Lista de requisitos funcionais |
| **Combinam?** | Sim: EARS descreve o requisito, GWT detalha o cenário de teste |

## Exemplo prático: do requisito ao teste

```
RF-5 (EARS): QUANDO um pedido já CANCELADO é cancelado de novo,
             o sistema NÃO DEVE gerar efeitos colaterais.

Cenário (GWT):
  DADO um pedido CANCELADO com estorno já realizado
  QUANDO o cliente solicita o cancelamento novamente
  ENTÃO a resposta é 200
    E nenhum novo estorno é criado
    E o estoque permanece inalterado
```

Teste derivado:

```java
@Test
void cancelamentoRepetido_naoGeraNovoEstorno() {
    Pedido p = pedidoCancelado();
    var resp = api.cancelar(p.id());
    assertEquals(200, resp.status());
    assertEquals(1, estornos.countByPedido(p.id()));
}
```

Cada linha do `ENTÃO` vira uma asserção — rastreável ao RF-5.

## Erros comuns e limitações

- **Critério vago**: "deve funcionar corretamente" não verifica nada.
- **Then não observável**: descrever estado interno em vez de resultado visível.
- **Cenários gigantes**: misturam vários comportamentos; use um por cenário.
- **Só caminho feliz**: os bugs moram nas bordas e nos erros.
- **Dados implícitos**: o Given omite o estado e o agente inventa.
- **Excesso de formalismo**: para mudanças triviais, uma frase basta.

| Cenário | Recomendação |
|---|---|
| Lista de requisitos de uma feature | EARS |
| Critérios de aceite e testes | Given-When-Then |
| Regra com muitas combinações | Tabela de decisão + cenários |

## 🧩 Quiz de Fixação

1. O que significa cada parte de Given-When-Then?
2. Escreva em EARS o requisito: "se o gateway estiver fora do ar, o estorno deve ser tentado depois".
3. Como EARS e Given-When-Then se complementam?

**Respostas:**
1) Given descreve o estado inicial, When a ação ou evento que ocorre e Then o resultado observável esperado. Juntos definem um comportamento verificável.
2) Padrão de comportamento indesejado: "SE o gateway de pagamento estiver indisponível, ENTÃO o sistema DEVE enfileirar o estorno para nova tentativa."
3) EARS padroniza a redação de cada requisito em uma frase clara; Given-When-Then detalha os cenários que verificam esse requisito. O requisito EARS dá a regra, o cenário gera o teste, e cada asserção do Then pode ser rastreada ao requisito.
