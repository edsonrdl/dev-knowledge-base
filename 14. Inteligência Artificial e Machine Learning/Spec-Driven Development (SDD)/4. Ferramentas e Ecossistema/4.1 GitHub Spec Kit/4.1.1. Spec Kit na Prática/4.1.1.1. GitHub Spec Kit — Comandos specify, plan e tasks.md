### GitHub Spec Kit — Comandos specify, plan e tasks

O **GitHub Spec Kit** é um toolkit open source do GitHub para praticar SDD com agentes de código. Ele fornece uma CLI (`specify`) que inicializa o projeto e um conjunto de comandos de barra que guiam o agente pelo ciclo: constitution, specify, clarify, plan, tasks, analyze e implement. É a implementação de referência de muitos conceitos vistos neste guia.

> [!warning] Ferramenta em evolução
> O Spec Kit muda com frequência (nomes de comandos, templates, agentes suportados). Os exemplos abaixo refletem o fluxo geral; confirme a sintaxe na documentação oficial do repositório `github/spec-kit` antes de usar.

---

## O que o Spec Kit entrega

```
 CLI "specify"           Comandos no agente          Templates e scripts
 (inicializa o     +     (/speckit.constitution,  +  (spec, plan, tasks,
  projeto)                /speckit.specify, ...)      checklists)
        │
        ▼
 Agentes suportados: Claude Code, GitHub Copilot, Gemini CLI, Cursor, entre outros
```

**Analogia:** é um kit de montagem com instruções: a CLI monta a bancada (estrutura de pastas), e os comandos são os passos do manual que o agente segue.

---

## Instalação e inicialização

```bash
# instalar a CLI (requer uv e Python)
uv tool install specify-cli --from git+https://github.com/github/spec-kit.git

# iniciar um projeto novo, escolhendo o agente
specify init meu-projeto --ai claude

# ou na pasta atual
specify init . --ai claude
```

O `init` cria a estrutura do projeto, aproximadamente:

```
meu-projeto/
├── .specify/
│   ├── memory/constitution.md     ← princípios do projeto
│   ├── templates/                 ← modelos de spec, plan, tasks
│   └── scripts/                   ← automações de apoio
├── .claude/commands/              ← comandos do agente (varia conforme o agente)
└── specs/
    └── 001-cancelamento-pedido/   ← criada a cada feature
        ├── spec.md
        ├── plan.md
        ├── research.md
        ├── data-model.md
        ├── contracts/
        ├── quickstart.md
        └── tasks.md
```

## Os comandos do fluxo

| Comando | Fase | O que produz |
|---|---|---|
| `/speckit.constitution` | Princípios | `.specify/memory/constitution.md` |
| `/speckit.specify` | O quê / por quê | Cria branch e `spec.md` com histórias, requisitos e marcadores |
| `/speckit.clarify` | Ambiguidade | Perguntas ao humano; atualiza a spec |
| `/speckit.plan` | Como | `plan.md`, `research.md`, `data-model.md`, `contracts/`, `quickstart.md` |
| `/speckit.tasks` | Passos | `tasks.md` ordenado, com `[P]` para paralelizáveis |
| `/speckit.analyze` | Consistência | Relatório somente leitura entre artefatos |
| `/speckit.checklist` | Qualidade da spec | Checklist de requisitos |
| `/speckit.implement` | Código | Executa as tasks em ordem |

Cada comando pode receber argumentos em linguagem natural.

---

## Exemplo prático: fluxo completo

```
/speckit.constitution  Princípios: testes primeiro, simplicidade,
                       Java 21 + Spring Boot, PostgreSQL, sem dados pessoais em logs.

/speckit.specify  Permitir que o cliente cancele pedidos ainda não enviados,
                  com estorno integral e idempotência. Fora de escopo:
                  cancelamento parcial.
   → cria branch 001-cancelamento-pedido e specs/001-.../spec.md

/speckit.clarify
   → "Qual o prazo máximo para cancelar?"  → humano responde

/speckit.plan  Usar Spring Boot, PostgreSQL e RabbitMQ para o estorno assíncrono.
   → gera plan.md, data-model.md, contracts/ (com constitution check)

/speckit.tasks
   → gera tasks.md com testes antes da implementação

/speckit.analyze
   → relatório: RF-3 sem task → corrigir

/speckit.implement
   → executa T001..Tn, marcando as concluídas
```

Em cada passo, o humano revisa o arquivo gerado antes de prosseguir (portões de revisão).

## Como ele reforça os conceitos de SDD

| Conceito | Onde aparece no Spec Kit |
|---|---|
| Constitution | `constitution.md` + *constitution check* no plano |
| Spec independente de tecnologia | Template de `spec.md` orienta a focar em o quê/por quê |
| Marcadores de ambiguidade | `[NEEDS CLARIFICATION]` limitados e tratados pelo `clarify` |
| Test-first | Tasks de teste ordenadas antes da implementação |
| Rastreabilidade | Artefatos por feature em `specs/NNN-nome/` + branch por feature |
| Validação | `analyze` e `checklist` |

---

## Limitações e erros comuns

- **Executar tudo sem ler**: o kit facilita gerar muito texto; revisar é obrigatório.
- **Specs inchadas**: os templates podem gerar documentos longos; ajuste o nível de detalhe ao risco.
- **Dependência do agente/modelo**: a qualidade varia conforme o agente e o modelo usados.
- **Overhead em mudanças pequenas**: para ajustes triviais o fluxo completo é excessivo.
- **Brownfield**: funciona melhor com features novas; em código legado exige trabalho para capturar o contexto existente.
- **Mudanças de versão**: comandos e templates evoluem, e a documentação oficial é a fonte atual.

| Cenário | Spec Kit é boa escolha? |
|---|---|
| Feature nova em projeto novo | Sim |
| Time quer um processo padronizado com vários agentes | Sim |
| Ajuste de uma linha | Não |
| Legado grande sem documentação | Com ressalvas |

## 🧩 Quiz de Fixação

1. Qual a função da CLI `specify` e dos comandos de barra no Spec Kit?
2. Em que ordem se usam os comandos principais e o que cada um produz?
3. Cite duas limitações do Spec Kit e como mitigá-las.

**Respostas:**
1) A CLI `specify` inicializa o projeto com a estrutura (`.specify/`, templates, comandos do agente). Os comandos de barra, executados dentro do agente de código, conduzem as fases do ciclo SDD e geram os artefatos de cada fase.
2) constitution (princípios) → specify (spec.md) → clarify (resolve ambiguidades) → plan (plan.md, modelo de dados, contratos) → tasks (tasks.md) → analyze (relatório de consistência) → implement (código). Checklist pode ser usado para validar a qualidade da spec.
3) Specs e documentos inchados → ajustar o nível de detalhe ao risco e fatiar features. Overhead em mudanças pequenas → não aplicar o fluxo completo em ajustes triviais. Também vale: revisar cada artefato (portões) e consultar a documentação oficial por causa das mudanças de versão.
