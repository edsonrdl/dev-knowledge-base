### CLAUDE.md, AGENTS.md e Steering Files como Ponte entre Spec e Agente

Um agente de código começa cada sessão sem memória do projeto. Se ele precisa redescobrir sempre a stack, as convenções e as regras, perde tempo e erra. Os **arquivos de contexto persistente** (`CLAUDE.md`, `AGENTS.md`, steering do Kiro) resolvem isso: são a ponte entre a spec (o que construir) e o agente (quem executa).

---

## O problema que resolvem

```
 Sessão nova do agente
        │
        ▼
 "Qual é a stack? Como rodo os testes? Que convenções seguir?"
        │
   sem contexto persistente → pergunta de novo, ou chuta
   com contexto persistente → lê o arquivo e já começa alinhado
```

**Analogia:** o manual de integração de um funcionário novo. Sem ele, cada pessoa que entra pergunta tudo; com ele, começa a trabalhar certo no primeiro dia.

---

## Os arquivos e suas convenções

| Arquivo | Usado por | Papel |
|---|---|---|
| `CLAUDE.md` | Claude Code | Instruções e contexto do projeto, carregados automaticamente no início da sessão |
| `AGENTS.md` | Convenção aberta suportada por vários agentes (Codex, Cursor, Copilot, entre outros) | Mesmo propósito, em formato independente de fornecedor |
| `.kiro/steering/*.md` | Kiro | Contexto de produto, tecnologia e estrutura |
| `.cursor/rules`, `.github/copilot-instructions.md` | Cursor, GitHub Copilot | Regras específicas de cada ferramenta |
| `constitution.md` | Spec Kit | Princípios do projeto referenciados nos comandos |

Na prática, muitos times mantêm **um arquivo principal** (por exemplo `AGENTS.md`) e fazem os demais apontarem para ele, evitando duplicação.

---

## O que colocar

| Seção | Conteúdo | Exemplo |
|---|---|---|
| **Visão do projeto** | Propósito em poucas linhas | "API de e-commerce de pedidos e pagamentos" |
| **Comandos essenciais** | Build, testes, lint | `./mvnw test`, `./mvnw spotless:apply` |
| **Stack e arquitetura** | Tecnologias e estrutura de pastas | "Java 21, hexagonal, PostgreSQL" |
| **Convenções** | Estilo, nomes, commits | "Commits convencionais; sem comentários óbvios" |
| **Regras de segurança** | O que nunca fazer | "Nunca logar dados pessoais" |
| **Onde estão as specs** | Ponteiro para o fluxo SDD | "Specs em `specs/`; leia `spec.md` e `plan.md` antes de implementar" |
| **Definição de pronto** | Quando a tarefa termina | "Testes passam e spec atualizada" |

---

## A ponte com o SDD

O arquivo de contexto **liga o agente ao fluxo SDD**: diz onde estão as specs, em que ordem lê-las e quais regras valem sempre.

```markdown
# AGENTS.md

## Fluxo de trabalho (SDD)
- Toda feature tem pasta em `specs/NNN-nome/` com spec.md, plan.md e tasks.md.
- ANTES de implementar: leia a spec.md e o plan.md da feature.
- Implemente UMA task por vez, na ordem de tasks.md, e marque-a ao concluir.
- Testes vêm primeiro; critérios de aceite da spec são a referência.
- Se algo estiver ambíguo, pare e pergunte; não assuma.
- Se o comportamento mudar, atualize a spec no mesmo commit.

## Comandos
- Testes: `./mvnw test`
- Formatar: `./mvnw spotless:apply`

## Princípios
- Ver `.specify/memory/constitution.md` (stack, segurança, simplicidade).
- Nunca logar dados pessoais. Segredos só por variáveis de ambiente.
```

Repare que o arquivo **não repete** a spec nem a constitution: aponta para elas. Contexto curto e referências, não cópias.

```
   AGENTS.md / CLAUDE.md  ──aponta──►  constitution.md   (regras permanentes)
          │                  └──────►  specs/NNN/spec.md  (o quê)
          │                  └──────►  specs/NNN/plan.md  (como)
          └─ define COMO o agente trabalha (ordem, regras, comandos)
```

## Boas práticas

| Prática | Por quê |
|---|---|
| **Curto e específico** | Contexto é recurso limitado; arquivos enormes são ignorados ou diluem o importante |
| **Instruções verificáveis** | "Rode `./mvnw test` antes de concluir" funciona melhor que "teste bem" |
| **Versionado no repositório** | Revisado por PR, compartilhado por todos |
| **Hierárquico** | Arquivos por subpasta/módulo para regras locais |
| **Atualizado** | Quando comandos ou convenções mudam, o arquivo muda |
| **Sem segredos** | É versionado; nunca coloque credenciais |
| **Evitar duplicação** | Um arquivo principal, os demais referenciam |

---

## Erros comuns e limitações

- **Arquivo gigante**: vira ruído; o agente perde o essencial.
- **Copiar a spec dentro dele**: duplica conteúdo e cria drift entre os dois.
- **Regras vagas** ("escreva código limpo"): não orientam nada concreto.
- **Desatualizado**: instrui o agente a usar comandos ou padrões que já não existem.
- **Achar que garante obediência**: o agente tende a seguir, mas pode falhar; mantenha testes, linters e revisão como verificação.
- **Segredos ou dados sensíveis no arquivo**: ele é versionado e lido por ferramentas.
- **Um arquivo por ferramenta sem sincronização**: divergem; centralize.

| Situação | Recomendação |
|---|---|
| Time com vários agentes | `AGENTS.md` como base, outros apontam para ele |
| Só Claude Code | `CLAUDE.md` |
| Monorepo com módulos distintos | Arquivos por módulo + um geral |

## 🧩 Quiz de Fixação

1. Que problema os arquivos como `CLAUDE.md` e `AGENTS.md` resolvem?
2. Por que o arquivo de contexto deve apontar para a spec e a constitution em vez de copiá-las?
3. Dê três itens que devem constar nele para integrar o agente ao fluxo SDD.

**Respostas:**
1) A falta de memória do agente entre sessões: sem eles, o agente tem que redescobrir ou adivinhar stack, comandos e convenções. Esses arquivos fornecem contexto persistente, carregado a cada sessão, para o agente começar alinhado.
2) Porque copiar duplica conteúdo e cria drift: a cópia envelhece quando a spec ou a constitution mudam. Apontar mantém uma única fonte da verdade e o arquivo de contexto curto, preservando o limitado espaço de contexto.
3) Por exemplo: onde estão as specs e em que ordem lê-las; regra de implementar uma task por vez com testes primeiro; instrução de parar e perguntar diante de ambiguidade; comandos de build e teste; regra de atualizar a spec quando o comportamento mudar.
