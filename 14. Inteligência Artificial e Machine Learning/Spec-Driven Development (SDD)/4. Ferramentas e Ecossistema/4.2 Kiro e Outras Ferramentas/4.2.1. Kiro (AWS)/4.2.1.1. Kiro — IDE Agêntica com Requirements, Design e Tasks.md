### Kiro — IDE Agêntica com Requirements, Design e Tasks

O **Kiro** é uma IDE agêntica da AWS (baseada na base de código do VS Code) construída em torno do SDD. Em vez de uma biblioteca de comandos sobre outro agente, o fluxo spec-driven é nativo da ferramenta: ele gera e mantém, para cada feature, três documentos — requisitos, design e tarefas — com revisão em cada etapa.

> [!warning] Ferramenta em evolução
> O Kiro é recente e muda rápido (planos, modelos, recursos). Os conceitos abaixo são estáveis; detalhes de interface e preços devem ser conferidos na documentação oficial.

---

## O fluxo de specs do Kiro

```
 Prompt do usuário
        │
        ▼
 ┌───────────────┐   ┌──────────────┐   ┌──────────────┐
 │ requirements  │──►│   design     │──►│    tasks     │──► implementação
 │     .md       │   │     .md      │   │     .md      │    (task a task)
 │ (EARS)        │   │ (arquitetura)│   │ (checklist)  │
 └───────────────┘   └──────────────┘   └──────────────┘
   aprovação humana    aprovação humana   aprovação humana
```

Os arquivos ficam em `.kiro/specs/<nome-da-feature>/` e são versionados no Git.

| Documento | Conteúdo | Equivale no Spec Kit a |
|---|---|---|
| `requirements.md` | User stories + critérios de aceite em **EARS** | `spec.md` |
| `design.md` | Arquitetura, componentes, interfaces, modelo de dados, tratamento de erros, estratégia de testes | `plan.md` |
| `tasks.md` | Lista de tarefas com rastreio a requisitos; execução com status por tarefa | `tasks.md` |

**Analogia:** é um escritório com as três etapas de projeto já organizadas em prateleiras; você avança de uma para a outra sempre assinando a anterior.

## Requisitos em EARS

O Kiro adota a notação EARS (vista em tópico anterior), o que dá uma estrutura previsível:

```markdown
### Requisito 1 — Cancelar pedido

**User Story:** Como cliente, quero cancelar um pedido não enviado,
para não pagar por algo que desisti de receber.

#### Critérios de aceite
1. QUANDO o cliente solicita o cancelamento de um pedido PAGO,
   ENTÃO o sistema DEVE alterar o status para CANCELADO e estornar o valor.
2. ENQUANTO o pedido estiver ENVIADO, o sistema DEVE recusar o cancelamento.
```

(Na ferramenta, os termos EARS aparecem em inglês: WHEN ... THEN the system SHALL ...)

## Steering — contexto persistente

O **steering** são arquivos Markdown em `.kiro/steering/` que dão ao agente conhecimento permanente do projeto, equivalente à constitution:

| Arquivo | Conteúdo típico |
|---|---|
| `product.md` | Propósito do produto, usuários, objetivos |
| `tech.md` | Stack, bibliotecas, restrições técnicas |
| `structure.md` | Organização de pastas e convenções de nomes |

Os arquivos de steering podem ser sempre incluídos, incluídos condicionalmente (por padrão de arquivo) ou sob demanda.

---

## Hooks — automação por eventos

**Agent hooks** disparam ações do agente quando algo acontece (salvar arquivo, criar arquivo, etc.), automatizando tarefas repetitivas:

```
Evento: salvar arquivo *.java
   └─► Ação do agente: atualizar os testes unitários correspondentes

Evento: alteração em src/
   └─► Ação: verificar se a spec/documentação precisa de atualização (ajuda contra drift)
```

## Exemplo prático de uso

```
1. Usuário (chat): "Quero cancelamento de pedidos com estorno."
2. Kiro cria requirements.md com histórias e critérios EARS → usuário revisa e aprova.
3. Kiro cria design.md (diagramas, contratos, modelo de dados) → revisão.
4. Kiro cria tasks.md, cada tarefa ligada a requisitos → revisão.
5. Usuário clica "Start task" em cada item; o agente implementa, mostra o diff
   e marca o status. O usuário revisa task a task.
```

## Kiro vs Spec Kit

| Aspecto | Kiro | GitHub Spec Kit |
|---|---|---|
| **Natureza** | IDE completa | CLI + comandos para o agente que você já usa |
| **Notação de requisitos** | EARS nativo | Livre (histórias + critérios) |
| **Contexto persistente** | Steering files | Constitution |
| **Automação** | Agent hooks | Scripts e comandos |
| **Escolha de agente** | Embutido na IDE | Vários agentes (Claude Code, Copilot, Gemini...) |
| **Curva de adoção** | Trocar de IDE | Adicionar ao fluxo atual |

## Limitações e erros comuns

- **Aprovar documentos sem ler**: a IDE gera tudo rápido; o valor está na revisão.
- **Overhead em tarefas pequenas**: ele sugere o fluxo de specs mesmo quando bastaria um ajuste direto (há o modo "vibe" para isso).
- **Lock-in de ferramenta**: o fluxo está acoplado à IDE; manter os Markdown portáteis reduz o risco.
- **Specs divergindo do código**: o Kiro não elimina o spec drift; a disciplina de atualização continua sendo sua.
- **Evolução rápida**: recursos e limites mudam; valide na documentação.

| Cenário | Kiro é boa escolha? |
|---|---|
| Time que quer SDD "pronto" dentro da IDE | Sim |
| Preferência por manter o agente/IDE atual | Talvez prefira Spec Kit ou OpenSpec |
| Prototipagem exploratória | Use o modo conversacional livre |

## 🧩 Quiz de Fixação

1. Quais são os três documentos do fluxo de specs do Kiro e o que cada um contém?
2. O que é steering e qual conceito do SDD ele equivale?
3. Compare Kiro e GitHub Spec Kit em uma dimensão que influencie a escolha.

**Respostas:**
1) `requirements.md` (user stories e critérios de aceite em EARS), `design.md` (arquitetura, componentes, interfaces, dados, erros, testes) e `tasks.md` (lista de tarefas rastreáveis aos requisitos, executáveis uma a uma).
2) São arquivos Markdown em `.kiro/steering/` (product, tech, structure) que dão contexto permanente ao agente sobre produto, stack e convenções. Equivalem à constitution do Spec Kit.
3) Exemplo: natureza da ferramenta. O Kiro é uma IDE completa com o fluxo embutido (exige trocar de ambiente), enquanto o Spec Kit é um toolkit que se acopla ao agente que o time já usa (Claude Code, Copilot, Gemini etc.), com menor custo de adoção.
