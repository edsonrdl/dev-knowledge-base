### As Fases do Ciclo SDD e os Portões de Revisão Humana

Conhecemos os artefatos; agora vemos como eles se encadeiam. O ciclo SDD é um **funil de refinamento**: cada fase transforma a anterior em algo mais concreto, e entre elas existe um **portão de revisão humana**. O agente acelera a produção; o humano garante a direção.

---

## O ciclo completo

```
 ┌────────────┐   ┌──────────┐   ┌────────┐   ┌────────┐   ┌───────────┐
 │  SPECIFY   │──►│ CLARIFY  │──►│  PLAN  │──►│ TASKS  │──►│ IMPLEMENT │
 │ (o quê/    │   │ (resolver│   │ (como) │   │(passos)│   │  (código) │
 │  por quê)  │   │ dúvidas) │   │        │   │        │   │           │
 └─────┬──────┘   └────┬─────┘   └───┬────┘   └───┬────┘   └─────┬─────┘
       ▼               ▼             ▼            ▼              ▼
   [REVISÃO]       [REVISÃO]     [REVISÃO]    [REVISÃO]     [REVISÃO + TESTES]
   humano aprova   sem pendência  arquitetura  tarefas ok    diff vs spec
```

**Analogia:** uma linha de aprovação de projeto: o briefing, o anteprojeto, o projeto executivo e a obra; em cada etapa o cliente assina antes de a próxima começar. Corrigir um erro no briefing custa uma frase; na obra, uma demolição.

---

## As fases

| Fase | Entrada | Saída | Pergunta-guia |
|---|---|---|---|
| **1. Specify** | Ideia/necessidade em linguagem natural | `spec.md` (histórias, requisitos, critérios) | O que e por quê? |
| **2. Clarify** | Spec com lacunas | Spec sem `[NEEDS CLARIFICATION]` | O que ainda é ambíguo? |
| **3. Plan** | Spec + constitution | `plan.md` (arquitetura, contratos, dados) | Como construir? |
| **4. Tasks** | Plan | `tasks.md` (tarefas ordenadas) | Em que passos? |
| **5. Implement** | Tasks | Código + testes | Cumpre a spec? |
| **(6. Analyze)** | Todos os artefatos | Relatório de inconsistências | Spec, plano e tasks concordam? |

A fase **Analyze** é opcional, mas valiosa antes de implementar (detalhada no próximo tópico).

---

## Portões de revisão humana

Um portão é um **ponto obrigatório de aprovação**. O agente não avança sem ele.

| Portão | O que o humano verifica |
|---|---|
| Após Specify/Clarify | Os requisitos refletem a necessidade real? Há critérios testáveis? Alguma suposição escondida? |
| Após Plan | Respeita a constitution? Abordagem proporcional? Segurança e dados corretos? |
| Após Tasks | Granularidade adequada? Testes antes da implementação? Cobre todos os requisitos? |
| Após cada task / Implement | O código cumpre a spec? Testes passam? Nada fora de escopo? |

**Princípio de economia:** o esforço de revisão deve ser maior nas fases iniciais, onde cada erro se multiplica, e mais automatizado nas finais (testes, lint, análise).

```
 Custo de corrigir um erro de requisito
   na spec    ████                     (minutos)
   no plano   ████████                 (horas)
   no código  ████████████████         (dias)
   em produção ██████████████████████████ (semanas + incidente)
```

## Exemplo prático: o ciclo em uma feature

```
1. Specify   Humano: "Quero permitir cancelamento de pedidos."
             Agente gera spec.md com 3 histórias e 2 [NEEDS CLARIFICATION].
   ▶ Portão  Humano revisa, vê que falta prazo e estorno.

2. Clarify   Humano responde: 7 dias; estorno no mesmo meio.
             Agente atualiza a spec e remove os marcadores.
   ▶ Portão  Humano aprova a spec.

3. Plan      Agente propõe: endpoint + fila de estorno + migração.
             Constitution check: ok.
   ▶ Portão  Arquiteto aprova; pede idempotência por índice único.

4. Tasks     Agente gera 8 tasks, testes primeiro, 2 paralelizáveis.
   ▶ Portão  Humano confirma cobertura dos RF-1..RF-5.

5. Implement Agente executa T001..T008, uma por vez, com commit por task.
   ▶ Portão  Revisão do diff contra a spec; testes e CI verdes.
```

## Erros comuns e limitações

- **Aprovar sem ler** ("o agente fez, deve estar bom"): os portões viram carimbo e o SDD perde o sentido.
- **Pular fases em features sérias**: ir direto da spec ao código recria o vibe coding.
- **Burocracia em mudanças triviais**: o ciclo completo para trocar um texto é desperdício; adapte o rigor ao risco.
- **Portões longos demais**: specs enormes ninguém revisa; fatie em features pequenas.
- **Revisar só o código final**: erros de requisito só aparecem tarde e caro.
- **Fluxo linear rígido**: o ciclo é iterativo; descobertas no plano podem exigir voltar e ajustar a spec (registrando a mudança).

| Tamanho da mudança | Ciclo recomendado |
|---|---|
| Trivial (typo, ajuste de texto) | Direto, sem spec formal |
| Pequena | Spec curta + tasks |
| Média/grande | Ciclo completo com clarify e analyze |
| Crítica (pagamento, segurança) | Ciclo completo + revisão extra e testes ampliados |

## 🧩 Quiz de Fixação

1. Liste as fases do ciclo SDD e o artefato produzido em cada uma.
2. O que é um portão de revisão humana e por que o esforço de revisão deve ser maior nas fases iniciais?
3. Um time pula Plan e Tasks e manda o agente implementar direto a partir da spec. Quais riscos?

**Respostas:**
1) Specify → spec.md; Clarify → spec sem pendências; Plan → plan.md; Tasks → tasks.md; Implement → código e testes; Analyze (opcional) → relatório de consistência entre artefatos.
2) É um ponto obrigatório de aprovação humana antes de avançar. O esforço é maior no início porque erros de requisito e de design se multiplicam ao longo das fases: corrigir na spec custa minutos, no código dias, em produção semanas.
3) O agente tomaria decisões de arquitetura e de sequência sem revisão, gerando mudanças grandes e difíceis de revisar, possível violação da constitution, ausência de rastreabilidade e testes. É praticamente voltar ao vibe coding, mas com uma spec.
