### Spec Drift — Mantendo Spec e Código Sincronizados

O maior inimigo do SDD ao longo do tempo não é a spec ruim: é a spec **boa que envelhece**. Quando o código muda e a spec não acompanha, ela vira ficção — e pior, passa a enganar quem a usa como contexto, inclusive agentes de IA. Este arquivo trata de como detectar e prevenir o *spec drift*.

---

## O que é Spec Drift

**Spec drift** é a divergência progressiva entre o que a spec diz e o que o sistema realmente faz. Acontece por correções rápidas feitas direto no código, mudanças de requisito não registradas, ou ajustes do agente que ninguém refletiu na spec.

**Analogia:** é o mapa desatualizado. Uma estrada nova foi aberta, mas o mapa continua mostrando o caminho antigo; quem confia nele se perde, e quanto mais antigo, pior.

```
 t0:  spec ═══════ código          (alinhados)
 t1:  spec ═══════ código'         hotfix no código, spec esquecida
 t2:  spec ═══╌╌╌╌ código''        mais mudanças só no código
 t3:  spec ╌╌╌╌╌╌╌ código'''       spec = ficção; agentes novos geram erro
                   ▲
              drift acumulado
```

---

## Causas comuns

| Causa | Exemplo |
|---|---|
| **Hotfix sem spec** | Bug em produção corrigido às pressas só no código |
| **Mudança de requisito informal** | Negócio pede ajuste por chat; ninguém atualiza a spec |
| **Agente "melhora" o design** | Durante a implementação, escolhe outra abordagem e ninguém registra |
| **Spec grande demais** | Custo de manter é alto, então ninguém mantém |
| **Sem dono** | Ninguém é responsável pela spec |
| **Processo não exige** | Pull requests passam sem tocar a spec |

---

## Por que é pior com agentes de IA

Um humano desconfia de documentação velha. Um agente **confia nela**: lê a spec como verdade e gera código coerente com ela, reintroduzindo comportamento já abandonado.

```
Spec diz: "link expira em 30 min"   (desatualizada)
Código real: 15 min
        │
Agente novo implementa feature relacionada lendo a spec
        ▼
Gera código com 30 min → regressão silenciosa
```

---

## Estratégias de prevenção

| Estratégia | Como funciona |
|---|---|
| **Spec e código no mesmo PR** | O PR que muda comportamento altera a spec; revisor recusa se não alterou |
| **Spec no repositório** | Versionada junto, com histórico e blame |
| **Testes derivados da spec** | Critérios de aceite viram testes; se o comportamento muda, o teste falha e força a atualização |
| **Fluxo "spec primeiro"** | Mudança começa pela spec (inclusive hotfix: spec curta depois, mas obrigatória) |
| **Specs pequenas e modulares** | Menor custo de manutenção, mais chance de ficarem em dia |
| **Dono por spec** | Responsável identificável (CODEOWNERS) |
| **Verificação de consistência** | Rodar o *analyze* ou revisão periódica comparando spec e código |
| **Rastreabilidade** | IDs (RF-x) citados em testes e commits; busca revela requisitos sem teste |

---

## Exemplo prático: PR que previne o drift

```markdown
## PR #214 — Expiração do link passa a 15 minutos

Arquivos alterados:
- specs/recuperacao-senha/spec.md   ← RF-2: "30 minutos" → "15 minutos"
- src/.../TokenService.java         ← EXPIRACAO_MIN = 15
- src/test/.../TokenExpiraTest.java ← assert 15 minutos (RF-2)

Checklist do PR:
- [x] Spec atualizada para refletir o novo comportamento
- [x] Testes ligados aos requisitos alterados
- [x] Sem divergência entre spec e implementação
```

Pode-se automatizar parte disso em CI: um job que falha se arquivos de `src/` mudam sem alteração em `specs/` (com exceção por label, como `no-spec-needed` para refatorações).

---

## Quando o drift é aceitável e limitações

- **Refatorações internas** não alteram comportamento: não exigem mudança de spec.
- **Hotfix urgente**: aceite o código primeiro, mas abra uma tarefa obrigatória de atualizar a spec em até X dias.
- **Spec-as-source** elimina drift por construção, mas traz outros desafios (visto no tópico dos níveis de adoção).
- **Nenhuma automação detecta tudo**: comparar texto livre com código é difícil; combine testes, revisão e disciplina.

| Sinal de drift | Ação |
|---|---|
| Teste de aceite falha após mudança legítima | Atualizar a spec e o teste |
| Spec cita função/campo que não existe | Corrigir a spec |
| Time "não confia mais" na spec | Reconstruir a partir do código e instituir o processo |

## 🧩 Quiz de Fixação

1. O que é spec drift e como ele surge?
2. Por que o drift é especialmente perigoso quando agentes de IA usam a spec como contexto?
3. Cite três práticas para evitar o drift e explique como uma delas o detecta automaticamente.

**Respostas:**
1) É a divergência crescente entre a spec e o comportamento real do sistema. Surge por hotfixes só no código, mudanças de requisito não registradas, decisões do agente não refletidas, specs grandes demais para manter e falta de dono ou de processo que exija atualização.
2) Porque o agente trata a spec como verdade. Se ela está desatualizada, ele gera código coerente com a versão antiga, reintroduzindo comportamentos já abandonados e causando regressões silenciosas.
3) Por exemplo: spec e código no mesmo PR, dono por spec, e testes derivados dos critérios de aceite. Os testes detectam drift automaticamente: se o comportamento do código muda e o critério de aceite continua o mesmo, o teste falha, forçando a atualização consciente da spec ou a correção do código.
