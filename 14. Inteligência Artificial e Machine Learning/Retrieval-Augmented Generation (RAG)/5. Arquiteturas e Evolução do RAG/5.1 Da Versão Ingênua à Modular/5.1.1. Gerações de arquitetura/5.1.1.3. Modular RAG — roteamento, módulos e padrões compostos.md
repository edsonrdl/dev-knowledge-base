### Modular RAG — roteamento, módulos e padrões compostos

O **Modular RAG** é a terceira geração: em vez de um pipeline fixo, o sistema é visto como um **conjunto de módulos intercambiáveis** (busca, reranking, memória, roteamento, geração, validação...) que podem ser **combinados em fluxos diferentes** conforme a pergunta. Surgem decisões dinâmicas, laços, ramificações e reutilização de componentes. Este arquivo explica a ideia, os módulos mais comuns e os padrões de composição.

> [!warning] Aviso
> "Modular RAG" é um conceito de classificação da literatura (survey de Gao et al., 2023/2024), não um produto. Frameworks de orquestração (grafos, pipelines) mudam rápido. O código **não foi executado**.

---

## Da linha reta ao Lego

```
 ADVANCED (pipeline linear fixo):
   A ─► B ─► C ─► D ─► E

 MODULAR (módulos + roteamento + laços):
                        ┌─► [Busca na doc]  ─┐
   [Entrada] ─► [Roteador] ─► [Busca SQL]   ─┼─► [Fusão] ─► [Rerank] ─► [Gerador] ─► [Verificador]
                        ├─► [Web / API]     ─┘                                           │
                        └─► [Sem busca] ─────────────────────────────► [Gerador]         │
                                       ▲                                                  │
                                       └──────────── refazer se reprovar ◄────────────────┘
```

**Analogia:** o Advanced RAG é uma linha de montagem fixa. O Modular RAG é uma cozinha profissional onde o chefe (roteador) decide, para cada pedido, quais estações acionar, em que ordem e se o prato precisa voltar para ajuste.

---

## Por que modularizar

| Motivação | Exemplo |
|---|---|
| **Heterogeneidade de fontes** | Documentos, banco SQL, API, web — cada um com seu mecanismo de busca |
| **Heterogeneidade de perguntas** | Saudação, pergunta factual, comparação, análise — exigem fluxos distintos |
| **Custo sob controle** | Perguntas simples usam fluxo curto; só as difíceis ativam etapas caras |
| **Evolução independente** | Trocar o reranker ou o banco vetorial sem reescrever tudo |
| **Teste isolado** | Avaliar cada módulo separadamente |
| **Reuso** | O mesmo módulo de retrieval serve a vários produtos |

## Catálogo de módulos

| Categoria | Módulos | Função |
|---|---|---|
| **Indexação** | Parser, chunker, enriquecedor, indexador | Preparar o conhecimento |
| **Pré-retrieval** | Condensador, expansor, decompositor, HyDE | Melhorar a consulta |
| **Roteamento** | Classificador de intenção, seletor de fonte, decisor "buscar ou não" | Escolher o caminho |
| **Retrieval** | Vetorial, lexical, híbrido, SQL, grafo, web, API | Obter evidências |
| **Pós-retrieval** | Fusão, reranker, compressor, deduplicador, ordenador | Refinar o contexto |
| **Geração** | Template, LLM(s), formatador, citador | Produzir a resposta |
| **Verificação** | Checagem de fidelidade, validação de citações, guardrails | Garantir qualidade e segurança |
| **Memória** | Histórico, resumos, preferências | Contexto da conversa |
| **Orquestração** | Controlador de fluxo, laços, limites de tentativas | Coordenar módulos |
| **Observabilidade** | Logs, tracing, métricas | Diagnóstico |

## Roteamento: o módulo-chave

O **roteador** decide, a partir da pergunta, **qual caminho seguir**. Pode usar regras, um classificador leve ou um LLM.

| Tipo de decisão | Exemplo | Efeito |
|---|---|---|
| **Buscar ou não?** | "Oi, tudo bem?" → não buscar | Economiza custo e latência |
| **Qual fonte?** | "Qual o faturamento do mês?" → SQL; "Como configuro X?" → documentação | Usa a ferramenta certa |
| **Qual estratégia?** | Pergunta composta → decomposição; pergunta com código de erro → híbrida lexical | Casa técnica e problema |
| **Qual modelo?** | Pergunta simples → modelo pequeno; complexa → modelo grande | Otimiza custo (LLM routing) |
| **Escalar para humano?** | Tema sensível/baixa confiança | Segurança |

```python
# Pseudocódigo didático — NÃO executado. 'classificar' pode ser regra, classificador ou LLM.

ROTAS = {
    "saudacao":   lambda q, c: c.llm_pequeno(q),                       # sem retrieval
    "factual_doc": lambda q, c: rag_documentos(q, c),                  # RAG sobre documentos
    "dados_sql":   lambda q, c: rag_sql(q, c),                         # text-to-SQL + resposta
    "composta":    lambda q, c: rag_decomposto(q, c),                  # sub-perguntas
    "sensivel":    lambda q, c: encaminhar_humano(q, c),               # escalonamento
}

def modular_rag(pergunta, ctx):
    intencao = classificar(ctx.llm_pequeno, pergunta, opcoes=list(ROTAS))  # roteador
    rota = ROTAS.get(intencao, ROTAS["factual_doc"])                       # padrão seguro
    return rota(pergunta, ctx)                                             # executa o fluxo escolhido
```

**Pontos a observar:** o roteador usa um modelo pequeno (barato); existe uma rota **padrão** quando a classificação falha; cada rota é um sub-pipeline reutilizável.

## Padrões de composição

### 1. Roteamento (vimos acima)
Um decisor escolhe um dentre vários caminhos.

### 2. Paralelo + fusão
Várias fontes/estratégias rodam ao mesmo tempo e os resultados são combinados.

```
 pergunta ─┬─► busca vetorial ─┐
           ├─► busca lexical ──┼─► fusão (RRF) ─► rerank
           └─► busca em SQL ───┘
```

### 3. Sequencial dependente (multi-hop)
A saída de um módulo alimenta o próximo.

```
 "Quem lidera a equipe que criou o produto X?"
   ─► buscar "criador do produto X" ─► equipe E
   ─► buscar "líder da equipe E"    ─► resposta
```

### 4. Laço de refinamento (generate–critique–retry)
Gera, verifica; se reprovar, reformula a consulta ou busca mais, com **limite de tentativas**.

```
 gerar ─► verificar fidelidade ─► aprovado? ── sim ─► entregar
                                      │ não
                                      └─► reescrever consulta / ampliar busca ─► (volta) [máx. N vezes]
```

Esse padrão é a base do Self-RAG e CRAG (5.2.1.1).

### 5. Fallback em cascata
Tenta o caminho mais barato; se falhar (sem trechos, baixa confiança), escala para um caminho mais caro ou outra fonte.

```
 busca interna ─► (sem resultado?) ─► busca web ─► (sem resultado?) ─► "não sei" / humano
```

### 6. Especialização por domínio
Roteia para pipelines distintos por área (jurídico, financeiro, RH), cada um com seus índices, prompts e guardrails.

### 7. Agente orquestrador
Um LLM decide dinamicamente quais módulos chamar e quantas vezes — o limite entre Modular RAG e **Agentic RAG** (5.2.2.2).

## Implementando: pipeline, grafo ou agente

| Abordagem | Descrição | Quando usar |
|---|---|---|
| **Pipeline estático com ramificações** | Código normal com `if/else` e funções | Poucas rotas, fluxo estável |
| **Grafo de estados** (ex.: frameworks de orquestração em grafo) | Nós = módulos, arestas = transições condicionais, estado compartilhado | Laços, paralelismo, retentativas, observabilidade |
| **Agente com ferramentas** | O LLM escolhe ferramentas em tempo de execução | Problemas abertos e imprevisíveis; aceita menos previsibilidade |

> [!tip] Regra prática
> Use a abordagem **mais simples que resolva** o problema. Fluxos determinísticos são mais fáceis de testar, depurar e controlar custos do que agentes livres. Comece com roteamento por código; evolua para grafo quando houver laços e estado; use agentes quando a flexibilidade compensar a perda de previsibilidade.

## Riscos e custos da modularidade

| Risco | Descrição | Mitigação |
|---|---|---|
| **Explosão de complexidade** | Muitos módulos e caminhos | Documentar o grafo; começar pequeno |
| **Latência imprevisível** | Laços e fallbacks alongam respostas | Limites de tentativas, timeouts, orçamento por requisição |
| **Custo imprevisível** | Chamadas encadeadas de LLM | Teto de custo por pergunta; modelos pequenos nos roteadores |
| **Erros de roteamento** | Classificação errada → caminho errado | Rota padrão segura; avaliar o roteador isoladamente |
| **Difícil depurar** | Muitos caminhos possíveis | Tracing por requisição mostrando o caminho percorrido |
| **Laços infinitos** | Verificação nunca aprova | Máximo de iterações e saída de emergência |

---

## Avaliação em sistemas modulares

- Avalie **cada módulo** isoladamente (roteador: acurácia; retrieval: recall@k; gerador: fidelidade).
- Avalie **o sistema de ponta a ponta** em perguntas que cobrem todas as rotas.
- Registre o **caminho percorrido** por pergunta para encontrar rotas problemáticas.
- Monitore custo e latência **por rota**.

---

## Erros comuns e armadilhas

- **Modularizar cedo demais.** Antes de existir uma necessidade medida, a complexidade só atrapalha.
- **Roteador caro e lento** que anula os ganhos do caminho curto.
- **Sem rota padrão** quando a classificação falha ou fica ambígua.
- **Laços sem limite** de iteração, custo ou tempo.
- **Ausência de tracing**: sem ver qual caminho a pergunta percorreu, o diagnóstico é impossível.
- **Acoplamento escondido** entre módulos (um módulo depende de formato interno de outro), perdendo o benefício da intercambialidade.
- **Usar agentes onde um `if/else` bastaria.**

## 🧩 Quiz de Fixação

1. Qual a diferença essencial entre Advanced RAG e Modular RAG?
2. Dê dois exemplos de decisões de roteamento e o benefício de cada um.
3. Quais riscos um laço de refinamento (gerar–verificar–refazer) introduz e como mitigá-los?

**Respostas:**
1) O Advanced RAG mantém um pipeline linear fixo com etapas otimizadas; o Modular RAG compõe módulos intercambiáveis em fluxos dinâmicos, com roteamento, ramificações, paralelismo e laços, escolhendo o caminho conforme a pergunta.
2) (a) Decidir "buscar ou não": saudações e perguntas triviais dispensam retrieval, economizando custo e latência; (b) escolher a fonte: perguntas numéricas vão para SQL e as conceituais para a documentação, usando a ferramenta adequada. Também: escolher modelo pequeno ou grande, escalar para humano.
3) Risco de laços infinitos, aumento imprevisível de latência e custo. Mitigações: limite máximo de iterações, timeout e teto de custo por requisição, saída de emergência (resposta "não sei" ou escalonamento) e tracing para analisar os casos que entram em laço.
