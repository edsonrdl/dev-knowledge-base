### Naive RAG e suas falhas típicas

O **Naive RAG** (RAG ingênuo ou básico) é a primeira geração do padrão: indexar → recuperar → gerar, tudo em linha reta, sem otimizações. É a implementação que qualquer tutorial ensina — e a que costuma ser feita primeiro. Funciona bem em demonstrações e **falha de formas previsíveis** em produção. Conhecer essas falhas é o que justifica cada técnica avançada vista no resto do guia: elas são, em essência, remédios para os defeitos do Naive RAG.

> [!warning] Aviso
> Os exemplos e o código são didáticos e **não foram executados**. As taxas de falha dependem de dados e modelos; use os sintomas como roteiro de diagnóstico, não como estatística.

---

## O que é o Naive RAG

```
 INDEXAÇÃO (offline)
   documentos ──► dividir em chunks de tamanho fixo ──► embeddings ──► banco vetorial

 CONSULTA (online)
   pergunta ──► embedding ──► top-k por similaridade ──► colar no prompt ──► LLM ──► resposta
```

**Características:**

| Etapa | Naive RAG |
|---|---|
| Ingestão | Extração simples de texto, sem curadoria |
| Chunking | Tamanho fixo (ex.: 500 caracteres), sem respeitar estrutura |
| Embedding | Um modelo genérico, sem teste de alternativas |
| Retrieval | Só busca vetorial, top-k fixo, sem limiar |
| Pós-retrieval | Nenhum (sem reranking, sem deduplicação) |
| Prompt | "Responda usando o contexto: ..." sem regras de grounding |
| Geração | Uma única chamada |
| Avaliação | Inexistente ou "olhômetro" |

**Analogia:** é montar uma biblioteca jogando os livros em pilhas por tamanho, e contratar um assistente que pega as 4 pilhas "mais parecidas" com a pergunta e lê tudo de uma vez — sem conferir se são as pilhas certas.

## Exemplo mínimo de Naive RAG

```python
# Pseudocódigo didático — NÃO executado. Mostra a simplicidade (e a ingenuidade) do fluxo.

def indexar(docs, embed, store):
    for doc in docs:
        texto = doc.ler_texto()                               # extração simples
        for i in range(0, len(texto), 500):                   # chunks fixos de 500 caracteres
            pedaco = texto[i:i + 500]                         # (corta no meio de frases!)
            store.add(embed(pedaco), pedaco)                  # vetor + texto

def responder(pergunta, embed, store, llm):
    achados = store.buscar(embed(pergunta), k=4)              # top-4 sempre, sem limiar
    contexto = "\n".join(a.texto for a in achados)            # cola tudo, sem ordenar/filtrar
    return llm(f"Responda usando o contexto:\n{contexto}\n\nPergunta: {pergunta}")
```

São ~10 linhas. Essa simplicidade é a virtude (prototipagem rápida) e o problema (nenhuma defesa).

## As falhas típicas, por etapa do pipeline

### Falhas de indexação

| Falha | Sintoma | Causa | Remédio (onde ver) |
|---|---|---|---|
| **Extração ruim** | Respostas sobre tabelas/PDFs erradas | Parser ingênuo, colunas embaralhadas | Parsers adequados (2.1.1.1) |
| **Chunks quebrados** | Regra e exceção separadas; trechos sem sentido | Corte fixo no meio de ideias | Chunking estrutural (2.2.1.1) |
| **Chunks sem contexto** | "Ele deve ser pago em 5 dias" — quem? | Falta título/seção | Contexto/metadados nos chunks |
| **Índice defasado** | Resposta com política antiga | Sem sincronização | Ciclo de vida do índice (2.1.1.2) |
| **Duplicatas** | Top-k com 4 cópias do mesmo texto | Sem deduplicação | Dedup / MMR (2.1.1.2, 3.1.2.1) |

### Falhas de retrieval

| Falha | Sintoma | Causa | Remédio |
|---|---|---|---|
| **Mismatch pergunta/documento** | O trecho certo existe e não é achado | Vocabulário diferente; pergunta vaga | Query transformation (3.2.1.1) |
| **Termos exatos ignorados** | Falha com códigos, siglas, nomes | Só busca vetorial | Busca híbrida (3.1.1.1) |
| **Conversa multi-turno quebra** | "E o prazo disso?" retorna lixo | Busca com a mensagem crua | Reescrita com histórico (3.2.1.1) |
| **Precisão baixa no topo** | O melhor trecho está na 8ª posição | Bi-encoder impreciso | Reranking (3.2.2.1) |
| **Top-k fixo inadequado** | Faltam evidências ou sobra ruído | k não calibrado | Parâmetros e limiar (3.1.2.1) |
| **Sem filtros** | Mistura versões, idiomas, tenants | Nenhum metadado | Filtros e ACL (2.1.1.3) |
| **Pergunta "global"** | "Quais os principais temas?" falha | Retrieval local por chunks | GraphRAG / sumarização (5.2.2.1) |
| **Multi-hop** | Resposta exige juntar 2+ fatos | Busca única | Decomposição / Agentic RAG (3.2.1.1, 5.2.2.2) |

### Falhas de geração

| Falha | Sintoma | Causa | Remédio |
|---|---|---|---|
| **Alucinação com contexto ruim** | Inventa quando o retrieval falha | Sem limiar nem "não sei" | Grounding e fallback (4.1.1.1, 4.2.1.2) |
| **Ignora o contexto** | Responde com a memória | Prompt fraco | Template robusto (4.1.1.1) |
| **Lost in the middle** | Não usa o trecho do meio | Contexto grande sem ordenação | Orçamento e ordenação (4.1.1.2) |
| **Sem citações** | Impossível verificar | Prompt sem exigência | Citações (4.2.1.1) |
| **Conflitos e dados velhos** | Mistura versões | Sem metadados no prompt | 4.2.1.2 |
| **Injeção via documento** | Segue ordens dentro do contexto | Contexto tratado como instrução | Segurança (7.1.2.1) |

### Falhas de processo

| Falha | Sintoma |
|---|---|
| **Sem avaliação** | Ninguém sabe se mudanças melhoram ou pioram |
| **Sem observabilidade** | Não se sabe quais trechos foram recuperados para cada resposta |
| **Sem iteração baseada em dados** | Ajustes "no feeling" |

## Mapa: falha → geração de arquitetura

```
 NAIVE RAG ──────► ADVANCED RAG ──────────────► MODULAR RAG
 (linha reta)      (otimiza ANTES e DEPOIS     (peças intercambiáveis,
                    do retrieval)               roteamento, laços, agentes)

 Falhas de indexação ───► melhor chunking, metadados, parsing
 Falhas de retrieval ───► query transform, híbrida, reranking, filtros
 Falhas de geração   ───► prompts, ordenação, citações, verificação
 Falhas de processo  ───► avaliação, observabilidade
```

## Quando o Naive RAG é suficiente

Nem todo caso precisa de arquitetura sofisticada.

| Cenário | Naive basta? |
|---|---|
| Prova de conceito / demonstração interna | Sim |
| Base pequena, limpa e homogênea (ex.: 1 manual) | Muitas vezes |
| Perguntas simples e factuais, sem multi-turno | Frequentemente |
| Uso crítico (jurídico, saúde, atendimento ao cliente em escala) | Não |
| Base heterogênea com PDFs complexos e tabelas | Não |
| Múltiplos tenants / permissões | Não |

> [!tip] Estratégia saudável
> Comece **simples**, mas **com avaliação desde o início**. Um conjunto de 30–50 perguntas com respostas esperadas (ver 6.1.2.1) mostra *onde* o Naive falha e orienta qual técnica adotar primeiro. Adicionar técnicas sem medir é a forma mais comum de gastar esforço sem ganho.

---

## Roteiro de diagnóstico rápido

1. **O trecho correto existe na base?** Não → problema de conteúdo/indexação.
2. **Ele foi recuperado (está no top-k)?** Não → retrieval (híbrida, query transform, chunking).
3. **Estava no top-k mas mal posicionado?** → reranking/ordenação.
4. **Estava no contexto e o modelo errou?** → prompt, modelo, grounding.

Este roteiro é expandido em 6.2.1.1.

## Erros comuns e armadilhas

- **Concluir "RAG não funciona" a partir de um Naive RAG.** Normalmente são os defeitos da implementação, não do padrão.
- **Pular direto para técnicas avançadas** (GraphRAG, agentes) sem corrigir o básico (parsing, chunking, avaliação).
- **Tunar o prompt para compensar retrieval ruim.** Se o trecho certo não chega, nenhum prompt resolve.
- **Trocar o LLM por um maior** quando o problema é o retrieval.
- **Não registrar o que foi recuperado**, impossibilitando diagnóstico.
- **Avaliar com 3–5 perguntas escolhidas à mão**, que sempre "funcionam".

## 🧩 Quiz de Fixação

1. Descreva o pipeline do Naive RAG e três de suas limitações.
2. Uma pergunta de acompanhamento ("E o prazo disso?") retorna resultados irrelevantes. Em que etapa está o defeito e qual o remédio?
3. Por que se recomenda começar simples, mas com avaliação desde o início?

**Respostas:**
1) Indexar (extração simples, chunks de tamanho fixo, embeddings, banco vetorial) e consultar (embedding da pergunta, top-k vetorial, colar o contexto no prompt, uma chamada ao LLM). Limitações: chunks quebrados sem contexto, ausência de busca híbrida/reranking, sem limiar ou "não sei", sem tratamento de multi-turno, sem avaliação, entre outras.
2) No retrieval: a busca usa a mensagem crua, sem entender o pronome "disso". O remédio é a reescrita/condensação da consulta usando o histórico antes de buscar (query transformation).
3) Porque protótipos simples validam rápido a ideia, e um conjunto de perguntas de teste mostra onde o sistema falha de fato, orientando qual técnica adotar primeiro. Sem medir, adicionar técnicas gasta esforço sem garantir melhora.
