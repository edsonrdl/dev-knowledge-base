## A intuição: um mapa de significados

Um **embedding** é uma lista de números (um vetor) que um modelo associa a um texto. O modelo é treinado para que textos com **significado parecido** recebam vetores **próximos**, e textos sem relação, vetores **distantes**.

**Analogia — o mapa:** imagine um mapa onde cada frase é um ponto. Frases sobre reembolso ficam numa região; frases sobre entrega, em outra; frases sobre senha, em outra. Para responder uma pergunta, você coloca a pergunta no mapa e olha **quais pontos estão mais perto**. Um mapa real tem 2 dimensões; um embedding tem centenas ou milhares, o que permite capturar muitas nuances ao mesmo tempo.

```
       (mapa 2D simplificado)

   devolução do produto ●  ● reembolso em 14 dias
                  ● dinheiro de volta
                         ★ "como recebo meu dinheiro de volta?"   ← pergunta cai perto

                                              ● frete grátis acima de R$200
                                              ● prazo de entrega

   ● esqueci minha senha
   ● redefinir acesso
```

Note que a pergunta **não repete as palavras** de "reembolso em 14 dias", mas cai perto dele. Essa é a vantagem sobre a busca por palavras-chave (comparação em 3.1.1.1).

## Como funciona o pipeline de embedding

```
 "Reembolso em até 14 dias"
          │
          ▼
 ┌─────────────────────────┐
 │  Modelo de embedding    │   (rede neural treinada para esta finalidade)
 └─────────────────────────┘
          │
          ▼
 [0.12, -0.38, 0.77, 0.05, ..., -0.21]     ← vetor de N dimensões (ex.: 384, 768, 1024, 1536, 3072)
```

- A **dimensão** (N) é fixa por modelo. Mais dimensões podem capturar mais nuance, mas custam mais memória e tempo de busca.
- O mesmo modelo deve embutir **chunks e perguntas** (os vetores só são comparáveis dentro do mesmo espaço).
- Alguns modelos esperam **prefixos/instruções** distintos para consulta e documento (por exemplo "query:" e "passage:"). Siga a documentação do modelo, pois é fonte comum de erro.

## Medindo proximidade: similaridade de cosseno

Para saber se dois vetores estão "próximos", usam-se métricas de similaridade/distância.

| Métrica | O que mede | Observação |
|---|---|---|
| **Similaridade de cosseno** | O **ângulo** entre os vetores (ignora o comprimento) | Mais usada em texto; valores de -1 a 1 (1 = mesma direção) |
| **Produto interno (dot product)** | Ângulo e magnitude | Equivale ao cosseno se os vetores forem normalizados |
| **Distância euclidiana (L2)** | Distância "em linha reta" | Sensível à magnitude |

**Intuição do cosseno:** pense em duas setas saindo da origem. Se apontam na mesma direção, são parecidas (cosseno ≈ 1); se formam 90°, não têm relação (≈ 0); se apontam em sentidos opostos, são contrárias (≈ -1). O comprimento da seta não importa — só a direção.

```
        ↗  A                  cosseno(A,B) ≈ 0.95  (ângulo pequeno: muito parecidos)
       ↗ B
      ┌────► C                cosseno(A,C) ≈ 0.10  (quase 90°: sem relação)
```

> [!info] Detalhe prático
> Muitos modelos já devolvem vetores **normalizados** (comprimento 1). Nesse caso, cosseno e produto interno dão o mesmo ranking. Configure no banco vetorial a **mesma métrica** para a qual o modelo foi treinado.

## Exemplo prático: cosseno "na mão"

```python
# Exemplo didático com vetores de 3 dimensões (fictícios) — NÃO executado.
import math   # funções matemáticas da biblioteca padrão

def cosseno(a, b):
    produto = sum(x * y for x, y in zip(a, b))    # soma dos produtos elemento a elemento
    norma_a = math.sqrt(sum(x * x for x in a))    # comprimento do vetor a
    norma_b = math.sqrt(sum(y * y for y in b))    # comprimento do vetor b
    return produto / (norma_a * norma_b)          # cos(ângulo) entre a e b

pergunta   = [0.9, 0.1, 0.0]   # "como recebo meu dinheiro de volta?"
reembolso  = [0.8, 0.2, 0.1]   # chunk: "reembolso em 14 dias"
entrega    = [0.1, 0.9, 0.2]   # chunk: "prazo de entrega"

print(cosseno(pergunta, reembolso))   # ≈ 0.99 -> muito parecido
print(cosseno(pergunta, entrega))     # ≈ 0.20 -> pouco parecido
# Em produção, o banco vetorial faz isso (de forma aproximada e rápida)
# contra milhões de vetores usando índices ANN (ver 2.2.3.1).
```

## O que o embedding captura (e o que não captura)

| Captura bem | Captura mal |
|---|---|
| Sinônimos e paráfrases ("reembolso" ≈ "dinheiro de volta") | **Termos exatos raros**: códigos, SKUs, siglas, nomes próprios, números |
| Tema geral do texto | **Negação** sutil ("pode" vs "não pode") — vetores próximos apesar de sentido oposto |
| Relação entre idiomas (em modelos multilíngues) | Detalhes numéricos precisos (14 dias vs 40 dias) |
| Contexto e intenção da pergunta | Conhecimento muito específico do seu domínio (se o modelo não o viu) |

Essas fraquezas motivam a **busca híbrida** (lexical + vetorial) e o **reranking** (ver 3.1.1.1 e 3.2.2.1).

## Como escolher o modelo de embedding

| Critério | Pergunta a fazer |
|---|---|
| **Idioma** | Foi treinado/avaliado em português? Há versão multilíngue? |
| **Domínio** | Jurídico, médico, código? Existe modelo especializado ou será preciso testar? |
| **Qualidade de retrieval** | Como se sai em benchmarks (ex.: MTEB) **e** nos seus próprios dados? |
| **Dimensão** | Impacta armazenamento, memória e latência; alguns modelos permitem reduzir dimensão (Matryoshka) |
| **Limite de tokens** | Cabe o tamanho dos seus chunks? |
| **Custo e latência** | API paga por token ou modelo próprio em GPU/CPU? |
| **Privacidade/soberania** | Os dados podem sair da empresa? Pode ser necessário modelo local |
| **Licença e estabilidade** | Modelos de API podem ser descontinuados; trocar exige reindexar |

### API hospedada vs modelo local

| Aspecto | API hospedada | Modelo local/open-source |
|---|---|---|
| Início | Rápido, sem infraestrutura | Requer servir o modelo |
| Custo | Por uso (tokens) | Infraestrutura fixa |
| Privacidade | Dados enviados a terceiros | Dados ficam em casa |
| Controle de versão | Sujeito a descontinuação | Você fixa a versão |
| Ajuste fino | Limitado | Possível (ver fine-tuning de embeddings no AI Engineering) |

> [!tip] Regra de ouro
> **Meça no seu próprio conjunto de perguntas.** Um modelo em primeiro lugar em benchmark geral pode perder para outro mais barato nos seus dados. Compare 2 ou 3 candidatos com recall@k (ver 6.1.1.1).

## Erros comuns e armadilhas

- **Misturar modelos** entre indexação e consulta (ou trocar de modelo sem reindexar).
- **Métrica errada no índice** (por exemplo, L2 num modelo treinado para cosseno).
- **Esquecer prefixos de instrução** exigidos por alguns modelos.
- **Truncamento silencioso:** chunks acima do limite de tokens perdem o final sem aviso.
- **Confiar que embedding entende números e códigos exatos.** Para "erro E-4021" ou "SKU 88-ABC", combine com busca lexical.
- **Escolher só pelo ranking público.** Sem teste nos seus dados, é aposta.
- **Ignorar o custo da dimensão:** 3072 dimensões em 10 milhões de chunks ocupam muito mais memória que 384.

## 🧩 Quiz de Fixação

1. O que significa dizer que dois textos têm embeddings "próximos"?
2. Por que a similaridade de cosseno ignora o comprimento do vetor, e quando cosseno e produto interno dão o mesmo ranking?
3. Um sistema precisa recuperar "erro E-4021" com exatidão, mas o retrieval vetorial falha. Por quê, e o que fazer?

**Respostas:**
1) Que o modelo os considera semanticamente parecidos: o ângulo entre os vetores é pequeno (cosseno alto), mesmo que as palavras sejam diferentes (ex.: "reembolso" e "dinheiro de volta").
2) O cosseno mede apenas o ângulo (a direção), então o comprimento das setas não influencia. Se os vetores forem normalizados (comprimento 1), o produto interno é igual ao cosseno e os rankings coincidem.
3) Embeddings capturam significado geral, mas representam mal códigos e termos exatos raros. A solução é usar busca híbrida (lexical como BM25 + vetorial), possivelmente com reranking, para casar o termo exato.
