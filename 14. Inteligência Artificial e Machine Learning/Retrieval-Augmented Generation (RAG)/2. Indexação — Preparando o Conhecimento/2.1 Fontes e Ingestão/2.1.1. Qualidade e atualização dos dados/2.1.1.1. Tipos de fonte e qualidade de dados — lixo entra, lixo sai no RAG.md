### Tipos de fonte e qualidade de dados — "lixo entra, lixo sai" no RAG

A qualidade de um sistema RAG tem um teto imposto pelos dados: **nenhum modelo, reranker ou prompt consegue extrair uma boa resposta de uma base ruim**. Este arquivo apresenta os tipos de fonte que alimentam um RAG, os problemas de qualidade mais comuns em cada um e um método para auditar e limpar os dados *antes* de indexar.

> [!warning] Aviso
> Ferramentas e APIs de extração evoluem rápido. Os exemplos de código **não foram executados**; adapte-os à sua stack.

---

## Por que a qualidade dos dados vem primeiro

**Analogia:** um garçom excelente (o LLM) servindo ingredientes estragados (dados ruins) continua entregando um prato ruim — só que, com talento, bem apresentado e dito com confiança. No RAG o "talento" do modelo torna o erro **mais convincente**, não menor.

```
  Dados ruins ──► chunks ruins ──► retrieval ruim ──► contexto ruim ──► resposta ruim
        ▲
        └── o conserto mais barato e eficaz está AQUI (início do pipeline)
```

## Tipos de fonte e seus problemas típicos

| Fonte | Exemplos | Problemas comuns | Cuidado principal |
|---|---|---|---|
| **Documentos formatados** | PDF, DOCX, PPTX | Colunas embaralhadas, cabeçalhos/rodapés repetidos, tabelas quebradas, PDFs escaneados sem texto | Parser adequado e/ou OCR; validar a extração |
| **Páginas web / wikis** | HTML, Confluence, Notion | Menus, banners e navegação misturados ao conteúdo; páginas duplicadas | Extrair só o conteúdo principal |
| **Texto estruturado leve** | Markdown, TXT, README | Estrutura útil (títulos) ignorada pelo chunking | Aproveitar títulos como metadados |
| **Dados tabulares/BD** | CSV, SQL, planilhas | Linha sem contexto vira texto sem sentido | Serializar com nome das colunas; considerar text-to-SQL |
| **Conversas e tickets** | E-mails, chats, suporte | Ruído, assinaturas, citações repetidas, informação pessoal | Remover texto citado, anonimizar PII |
| **Transcrições** | Áudio de reuniões, vídeos | Erros de reconhecimento, falta de pontuação, falantes misturados | Revisar e segmentar por falante e tópico |
| **Código** | Repositórios | Contexto espalhado entre arquivos | Chunking por função/classe |
| **Imagens e mídia** | Fotos, diagramas | Sem texto extraível | Tópico próprio: RAG Multimodal |

## As dimensões da qualidade

| Dimensão | Pergunta-chave | Falha típica |
|---|---|---|
| **Completude** | O conteúdo necessário está na base? | O usuário pergunta algo que nunca foi indexado |
| **Correção** | A informação está certa? | Documento com erro vira "verdade" para o modelo |
| **Atualidade** | É a versão vigente? | Política antiga convive com a nova |
| **Consistência** | Documentos não se contradizem? | Duas versões do mesmo procedimento |
| **Limpeza** | O texto está livre de ruído? | Rodapé "Página 3 de 40" em cada chunk |
| **Estrutura** | Títulos, listas e tabelas foram preservados? | Tabela virou sequência de números soltos |
| **Granularidade** | Cada documento trata de assunto coerente? | Arquivo "miscelânea" com 30 temas |
| **Autoridade** | A fonte é oficial/confiável? | Rascunho ou conversa informal tratada como regra |

## Problemas clássicos de extração (e como detectar)

```
 Original (PDF, 2 colunas)             Extração ingênua
 ┌──────────────┬──────────────┐       "A política de reembolso
 │ A política de│ prazo de 14  │        prazo de 14 dias O cliente
 │ reembolso... │ dias. ...    │        deve abrir o ..."
 └──────────────┴──────────────┘       (linhas das colunas intercaladas = texto sem sentido)
```

| Sintoma na extração | Como detectar | Correção |
|---|---|---|
| Colunas intercaladas | Ler amostras do texto extraído | Parser com análise de layout |
| Cabeçalho/rodapé repetido | Frases que aparecem em quase todos os chunks | Remover linhas repetidas por página |
| Tabelas destruídas | Números sem rótulos | Extrair tabela como Markdown/HTML |
| Texto vazio em PDF escaneado | Chunks com 0 caracteres ou lixo | OCR |
| Hifenização quebrada | Palavras partidas ("reem-bolso") | Normalizar no pré-processamento |
| Encoding errado | "Ã§" no lugar de "ç" | Forçar UTF-8 na leitura |

## Exemplo prático: auditoria rápida de qualidade antes de indexar

```python
# Pseudocódigo didático — NÃO executado.
from collections import Counter   # contador de ocorrências (biblioteca padrão)

def auditar(documentos):
    # 'documentos': lista de dicts {"id": ..., "paginas": [texto_pag1, texto_pag2, ...]}
    relatorio = []
    for doc in documentos:
        paginas = doc["paginas"]
        texto = "\n".join(paginas)             # texto completo do documento

        # 1) Texto praticamente vazio -> provável PDF escaneado sem OCR
        if len(texto.strip()) < 200:
            relatorio.append((doc["id"], "SEM_TEXTO: precisa de OCR?"))

        # 2) Linhas repetidas em muitas páginas -> cabeçalho/rodapé/boilerplate
        linhas = Counter(l.strip() for p in paginas for l in p.splitlines() if l.strip())
        limite = max(3, len(paginas) * 0.5)    # "muitas" páginas = metade ou pelo menos 3
        repetidas = [l for l, c in linhas.items() if c >= limite]
        if repetidas:
            relatorio.append((doc["id"], f"BOILERPLATE: {repetidas[:3]}"))

        # 3) Proporção de caracteres suspeitos -> encoding quebrado
        estranhos = sum(1 for ch in texto if ch in "Ã�")
        if estranhos / max(len(texto), 1) > 0.01:   # mais de 1% do texto
            relatorio.append((doc["id"], "ENCODING: verifique UTF-8"))
    return relatorio    # revisar manualmente antes de indexar
```

**O que o exemplo ensina:** auditorias baratas (texto vazio, linhas repetidas, encoding) pegam a maior parte dos desastres. Complemente com **leitura humana de uma amostra** (por exemplo, 20 documentos aleatórios) — nenhum script substitui olhar o texto extraído.

## Boas práticas de curadoria

| Prática | Benefício |
|---|---|
| Definir **fontes oficiais** e ignorar rascunhos | Evita respostas baseadas em material não aprovado |
| Atribuir um **dono** a cada coleção de documentos | Alguém responsável por corrigir e atualizar |
| Marcar **status** (vigente, obsoleto, rascunho) como metadado | Permite filtrar na busca |
| Limpar **na ingestão**, não na consulta | Menos latência e comportamento previsível |
| Guardar o **texto bruto original** além do limpo | Possibilita reprocessar com um parser melhor |
| Remover ou anonimizar **PII** quando não for necessária | Reduz risco de privacidade (ver 7.1.2.1) |
| Medir a qualidade da extração em amostras | Detecta regressões quando o parser muda |

## Erros comuns e armadilhas

- **"Jogar tudo na pasta e indexar".** Sem curadoria, a base reúne duplicatas, rascunhos e versões antigas que competem com o conteúdo bom.
- **Nunca olhar o texto extraído.** Muitos RAGs "ruins" simplesmente indexaram PDFs mal lidos.
- **Indexar conteúdo que o usuário não deveria ver.** Qualidade também é governança (ver 2.1.1.3).
- **Culpar o embedding/LLM** quando o problema é o dado. Diagnostique a base primeiro (ver 6.2.1.1).
- **Ignorar lacunas.** Se a pergunta frequente não tem documento correspondente, nenhuma técnica de retrieval resolve; é preciso **criar o conteúdo**.

## 🧩 Quiz de Fixação

1. Por que dizemos que o teto de qualidade de um RAG é definido pelos dados?
2. Cite três sintomas de má extração de PDFs e como cada um é detectado.
3. Por que guardar o texto bruto original, além do texto limpo, é uma boa prática?

**Respostas:**
1) Porque retrieval e geração só trabalham com o que foi indexado: dado incorreto, ausente, desatualizado ou ruidoso gera chunks e contexto ruins, e o LLM ainda os apresenta de forma convincente. Nenhuma otimização posterior compensa totalmente uma base ruim.
2) Colunas intercaladas (texto sem sentido ao ler amostras); cabeçalhos/rodapés repetidos (linhas que aparecem em quase todas as páginas/chunks); tabelas destruídas (números soltos sem rótulos); também PDFs escaneados (texto vazio) e encoding quebrado (caracteres estranhos).
3) Porque permite reprocessar os documentos com um parser ou regras de limpeza melhores sem precisar recoletar as fontes, além de facilitar auditoria e comparação entre versões da extração.
