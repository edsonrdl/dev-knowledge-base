### Sincronização, deduplicação, versionamento e deleção de documentos

Um índice RAG não é uma fotografia: é um **espelho vivo** da base de conhecimento. Documentos são criados, editados, duplicados, substituídos e apagados o tempo todo. Se o índice não acompanhar essas mudanças, o sistema passa a responder com informação velha, repetida ou — pior — de documentos que já foram removidos. Este arquivo trata do ciclo de vida dos dados no índice.

> [!warning] Aviso
> Recursos de bancos vetoriais (upsert, filtros por metadados, TTL, deleção por filtro) variam por produto e versão. O código é ilustrativo e **não foi executado**.

---

## O problema: o índice envelhece em silêncio

**Analogia:** é um catálogo de biblioteca que ninguém atualiza. Livros novos não aparecem, livros retirados continuam listados e há três fichas para o mesmo livro. O leitor confia no catálogo — e se dá mal.

```
  Fonte (verdade)                    Índice (cópia)
  ┌───────────────┐                 ┌──────────────┐
  │ doc A  v2     │ ── divergência ►│ doc A  v1    │  ← desatualizado
  │ doc B         │                 │ (ausente)    │  ← não indexado
  │ (doc C apagado)                 │ doc C        │  ← "fantasma"
  │ doc D         │                 │ doc D + D'   │  ← duplicado
  └───────────────┘                 └──────────────┘
```

Quatro tarefas mantêm o índice saudável: **sincronização, deduplicação, versionamento e deleção**.

---

## 1. Sincronização — manter o índice alinhado à fonte

| Estratégia | Como funciona | Prós | Contras |
|---|---|---|---|
| **Reindexação completa (full refresh)** | Apaga e refaz tudo periodicamente | Simples, sem estado | Caro e lento; janela de inconsistência |
| **Incremental por data** | Processa só o que mudou desde a última execução (`updated_at`) | Eficiente | Depende de a fonte expor data confiável |
| **Incremental por hash** | Calcula hash do conteúdo e compara com o anterior | Funciona sem metadados da fonte | Precisa ler o documento todo |
| **Orientada a eventos (webhook/CDC)** | A fonte avisa a cada mudança | Quase em tempo real | Requer integração e tratamento de falhas |
| **Híbrida** | Eventos + varredura periódica de reconciliação | Robusta | Mais complexa |

> [!info] Boa prática
> Mesmo com eventos, mantenha uma **varredura periódica de reconciliação**: eventos se perdem. Ela compara a lista de ids da fonte com a do índice e corrige as diferenças (faltantes e sobrantes).

```
 Para cada documento da fonte:
   hash_novo = SHA256(conteúdo)
   ┌─ não existe no índice ──────────► INDEXAR (novo)
   ├─ existe e hash igual ───────────► IGNORAR (sem mudança)
   └─ existe e hash diferente ───────► REINDEXAR (apagar chunks antigos + criar novos)
 Para cada id no índice que não está mais na fonte:
                                       ► DELETAR
```

## 2. Deduplicação — evitar o mesmo conteúdo várias vezes

Duplicatas ocupam espaço, **poluem o top-k** (os 5 resultados viram 5 cópias do mesmo texto, sobrando pouca diversidade) e **geram contradições** quando as cópias divergem.

| Tipo | Exemplo | Técnica de detecção |
|---|---|---|
| **Duplicata exata** | Mesmo arquivo em duas pastas | Hash do conteúdo (SHA-256) |
| **Quase-duplicata** | Mesmo texto com pequenas diferenças (data, assinatura) | MinHash/SimHash, similaridade de embeddings acima de um limiar |
| **Duplicata de trecho** | Mesmo parágrafo em vários documentos (avisos legais) | Hash por chunk |
| **Versões do mesmo documento** | `manual_v1.pdf`, `manual_v2.pdf` | Metadados (id lógico + versão), não hash |

Decisão importante: manter a versão canônica e descartar as outras, ou manter todas com metadado `canonical=false` para poder filtrar.

---

## 3. Versionamento — qual versão responde?

| Modelo | Descrição | Quando usar |
|---|---|---|
| **Somente a versão vigente** | Ao atualizar, substitui os chunks antigos | FAQs, manuais atuais, documentação |
| **Múltiplas versões com metadados** | Guarda `versao`, `vigente_de`, `vigente_ate`, `status` e filtra na consulta | Jurídico, compliance, histórico de preços e políticas |

Ao guardar várias versões, o retrieval deve **filtrar por padrão `status = vigente`**; versões antigas só entram quando a pergunta pede histórico. Sem esse filtro, o modelo recebe trechos de versões conflitantes.

O alicerce é o **identificador estável**:

```
 id do documento:  manual-reembolso            (nunca muda)
 id do chunk:      manual-reembolso#v3#0012    (doc + versão + posição)
 metadados:        {"doc_id":"manual-reembolso","versao":3,"status":"vigente","hash":"ab12..."}
```

Com `doc_id` constante, é possível "apagar todos os chunks do documento X" antes de reinserir a nova versão.

## 4. Deleção — esquecer de verdade

Deleção é a tarefa mais negligenciada. Documentos removidos continuam sendo recuperados ("fantasmas") se ninguém apagar seus chunks. Importa por **correção** (política revogada ainda respondendo), **segurança** (documento que perdeu acesso) e **privacidade** (pedido de exclusão de dados pessoais, previsto na LGPD).

| Cenário | Como tratar |
|---|---|
| Documento removido da fonte | Deletar todos os chunks por `doc_id` (a reconciliação garante) |
| Pedido de exclusão de dados pessoais | Deletar por filtro de titular + compactar o índice + limpar caches, logs e backups conforme a política |
| Conteúdo com expiração (promoções) | Metadado `expira_em` + filtro na consulta + job de limpeza |
| Permissão revogada | Atualizar os metadados de ACL imediatamente (ver 2.1.1.3) |

> [!warning] Atenção
> Alguns índices vetoriais fazem **deleção lógica** (marcam como removido) e só liberam o espaço depois de compactação. Verifique o comportamento do seu banco; **caches semânticos** e **logs** também podem conter o conteúdo "apagado".

## Exemplo prático: sincronização incremental com hash

```python
# Pseudocódigo didático — NÃO executado. 'store' é uma abstração de banco vetorial.
import hashlib   # funções de hash (biblioteca padrão)

def hash_conteudo(texto):
    # SHA-256 do texto: muda se qualquer caractere mudar.
    return hashlib.sha256(texto.encode("utf-8")).hexdigest()

def sincronizar(fonte_docs, store, indexar_doc):
    # fonte_docs: dict {doc_id: texto} com o estado atual da fonte de verdade.
    # store.listar_docs(): dict {doc_id: hash} do que já está indexado.
    no_indice = store.listar_docs()

    for doc_id, texto in fonte_docs.items():              # 1) novos e alterados
        h = hash_conteudo(texto)                          # hash do conteúdo atual
        if doc_id not in no_indice:                       # nunca indexado
            indexar_doc(doc_id, texto, h)                 # cria os chunks
        elif no_indice[doc_id] != h:                      # conteúdo mudou
            store.deletar_por_filtro({"doc_id": doc_id})  # apaga chunks velhos
            indexar_doc(doc_id, texto, h)                 # recria com a nova versão
        # hash igual: nada a fazer (economiza embeddings)

    for doc_id in set(no_indice) - set(fonte_docs):       # 2) no índice, mas não na fonte
        store.deletar_por_filtro({"doc_id": doc_id})      # remove "fantasmas"
```

**Pontos-chave:** (1) a comparação por hash evita recalcular embeddings do que não mudou — economia direta de custo; (2) o `deletar_por_filtro` antes de reinserir impede que sobrem chunks antigos (se o documento novo tiver menos chunks que o antigo); (3) o segundo laço implementa a reconciliação de deleções.

## Checklist operacional

| Item | Pergunta de controle |
|---|---|
| Ids estáveis | Cada documento/chunk tem identificador que sobrevive a atualizações? |
| Detecção de mudança | Usamos hash ou data confiável? |
| Reconciliação | Existe varredura periódica que corrige divergências? |
| Versionamento | O filtro padrão exclui versões obsoletas? |
| Deleção | Chunks removidos somem do índice **e** dos caches? |
| Monitoramento | Há alerta se o pipeline de sincronização parar? Qual a "idade" do índice? |
| Troca de modelo de embedding | Existe plano de reindexação completa? (ver 7.2.2.1) |

## Erros comuns e armadilhas

- **Atualizar sem apagar os chunks antigos.** O documento encolhe e sobram trechos obsoletos misturados aos novos.
- **Ids baseados no nome do arquivo ou em contadores globais.** Renomear ou reordenar quebra a rastreabilidade.
- **Deduplicar só por hash exato.** Quase-duplicatas continuam poluindo o top-k.
- **Não monitorar a "idade" do índice.** O pipeline falha, ninguém percebe e o RAG responde com dados de meses atrás.
- **Esquecer de apagar caches e logs** ao atender pedidos de exclusão.
- **Reindexar tudo a cada mudança** por falta de ids e hashes, gerando custo desnecessário de embeddings.

## 🧩 Quiz de Fixação

1. Por que a sincronização incremental por hash economiza dinheiro em comparação com a reindexação completa?
2. Qual a diferença entre duplicata exata, quase-duplicata e versões do mesmo documento, e como cada uma é tratada?
3. Um documento de política foi substituído por uma versão mais curta, mas o RAG continua citando regras que não existem mais. Qual é a causa mais provável?

**Respostas:**
1) Porque só os documentos novos ou alterados passam por parsing, chunking e embedding; os com hash igual são ignorados. Na reindexação completa, todos os embeddings são recalculados a cada execução, mesmo sem mudanças.
2) Duplicata exata tem conteúdo idêntico e se detecta por hash; quase-duplicata tem pequenas diferenças e exige MinHash/SimHash ou similaridade de embeddings; versões do mesmo documento são conteúdos relacionados tratados por metadados (id lógico, versão, status), mantendo só a vigente ou todas com filtro.
3) Os chunks da versão antiga não foram apagados antes da reinserção (a versão nova tem menos chunks e os sobrantes continuam no índice). A correção é deletar por `doc_id` antes de reindexar e ter uma reconciliação periódica.
