### Isolamento por tenant, crescimento do índice e estratégias de reindexação

Um RAG que atende uma equipe pequena e um RAG que atende centenas de clientes (**tenants**) com milhões de documentos são sistemas diferentes. Escalar traz três desafios: **isolar** os dados de cada cliente, **acompanhar o crescimento** do índice sem perder desempenho e **reindexar** com segurança quando o modelo de embedding, o chunking ou o esquema mudam. Este arquivo aborda os três.

> [!warning] Aviso
> Capacidades de isolamento, limites de escala e custos variam muito entre bancos vetoriais e provedores; os números são ordens de grandeza didáticas. Valide com testes de carga no seu produto. O código **não foi executado**.

## 1. Multi-tenancy: modelos de isolamento

**Tenant** = um cliente/organização (ou área) cujos dados não podem se misturar com os de outros. A escolha do modelo equilibra **isolamento, custo e simplicidade operacional**.

```
 (A) BASE COMPARTILHADA        (B) NAMESPACE/PARTIÇÃO         (C) ÍNDICE/COLEÇÃO POR TENANT     (D) INFRA DEDICADA
  ┌───────────────────┐         ┌───────────────────┐          ┌───┐ ┌───┐ ┌───┐                 ┌───────┐ ┌───────┐
  │ chunks de todos   │         │ ns:A │ ns:B │ ns:C│          │ A │ │ B │ │ C │                 │ ins A │ │ ins B │
  │ filtro tenant_id  │         │ (mesmo índice)    │          └───┘ └───┘ └───┘                 └───────┘ └───────┘
  └───────────────────┘         └───────────────────┘
  barato · isolamento lógico     meio-termo                     isolamento forte · mais custo     máximo isolamento · mais caro
```

| Modelo | Isolamento | Custo/operação | Quando usar |
|---|---|---|---|
| **A. Base compartilhada + filtro `tenant_id`** | Lógico (depende do filtro correto) | Mais barato e simples | Muitos tenants pequenos; risco aceitável; filtros obrigatórios e testados |
| **B. Namespaces/partições** | Lógico reforçado (separação nativa do produto) | Barato/médio | Muitos tenants; quer garantia embutida no banco |
| **C. Índice/coleção por tenant** | Forte | Médio/alto (muitos índices) | Tenants médios; requisitos de isolamento e performance previsível |
| **D. Infraestrutura dedicada por tenant** | Máximo | Alto | Clientes grandes, regulados ou com exigência contratual (dados em região específica, criptografia própria) |
| **Híbrido** | Varia por camada | Equilibrado | Tenants pequenos em base compartilhada; grandes em dedicada |

### Critérios de decisão

| Critério | Pergunta |
|---|---|
| **Risco e conformidade** | Há exigência legal/contratual de separação física, região ou chaves próprias? |
| **Número de tenants** | Dezenas? Milhares? Índice por tenant pode ser inviável com muitos |
| **Tamanho desigual** | Poucos tenants gigantes ("noisy neighbors") dominam recursos? |
| **Customização** | Cada tenant quer modelo de embedding, chunking ou retenção próprios? |
| **Exclusão/portabilidade** | É fácil apagar/exportar todos os dados de um tenant? (C e D facilitam) |
| **Custo operacional** | Quem opera dezenas de índices? |

### Garantias além do índice

Isolamento não é só o banco vetorial:

| Camada | Cuidado |
|---|---|
| **Aplicação** | Identidade do tenant derivada do token autenticado, nunca do cliente |
| **Cache** (semântico, prompt, embeddings) | Chave inclui tenant; sem compartilhamento |
| **Memória/histórico** | Escopo por tenant e usuário |
| **Logs/traces** | Separação, mascaramento e controle de acesso |
| **Armazenamento de arquivos brutos** | Prefixos/buckets por tenant, criptografia |
| **Modelos ajustados** | Não treinar/ajustar misturando dados de tenants (ver 7.1.2.1) |
| **Quotas e limites de taxa** | Evitar que um tenant degrade os demais |
| **Testes de isolamento automáticos** | Usuário do tenant A tenta acessar B; deve falhar |

```python
# Pseudocódigo didático — NÃO executado: roteamento por tenant com estratégia híbrida.
def obter_indice(tenant, ctx):
    cfg = ctx.config_tenants[tenant.id]                           # política do tenant
    if cfg["modelo"] == "dedicado":
        return ctx.cliente_dedicado(cfg["endpoint"])              # D: infra própria
    if cfg["modelo"] == "colecao":
        return ctx.store.colecao(f"tenant_{tenant.id}")           # C: coleção própria
    return ctx.store.colecao("compartilhada", namespace=tenant.id)  # B: namespace

def buscar(tenant, usuario, consulta, ctx):
    indice = obter_indice(tenant, ctx)
    filtro = {"tenant_id": tenant.id, "acl_qualquer_de": usuario.grupos}   # filtro SEMPRE aplicado
    return indice.buscar(ctx.embed_do_tenant(tenant, consulta), k=30, filtro=filtro)
```

## 2. Crescimento do índice

À medida que a base cresce — mais documentos, mais chunks, mais tenants — surgem custos e riscos.

### Como o tamanho escala

| Recurso | Cresce com | Observação |
|---|---|---|
| **Memória (RAM)** | nº de vetores × dimensões × bytes (+ overhead do índice, ex.: HNSW) | Principal limitador; quantização reduz |
| **Armazenamento** | Vetores + texto + metadados + versões | Versões históricas multiplicam |
| **Latência de busca** | Tamanho do índice, filtros, parâmetros ANN | Cresce sublinearmente, mas cresce |
| **Tempo de indexação/reindexação** | Nº de chunks × custo de embedding | Pode virar dias |
| **Custo de embedding** | Chunks novos e reindexações | Importante em reprocessamentos |
| **Complexidade operacional** | Nº de índices/tenants | Backups, upgrades, monitoração |

```python
# Estimativa ilustrativa — NÃO executada.
def estimar(n_chunks, dim=1024, bytes_por_valor=4, overhead_indice=1.5):
    vetores_gb = n_chunks * dim * bytes_por_valor / 1024**3
    return round(vetores_gb * overhead_indice, 1)      # GB aproximados em RAM (varia por índice)

print(estimar(10_000_000))            # ≈ 57 GB  (10 milhões de chunks, 1024 dims, float32)
print(estimar(10_000_000, dim=256))   # ≈ 14 GB  (dimensão reduzida, ex.: Matryoshka, se a qualidade permitir)
# Quantização (int8/binária/PQ) reduz ainda mais, com possível perda de recall — meça.
```

### Estratégias para conter o crescimento

| Estratégia | Efeito | Cuidado |
|---|---|---|
| **Deduplicação e limpeza** (ver 2.1.1.2) | Menos chunks | Fundamental e barato |
| **Política de versões** | Manter só vigentes no índice quente; arquivar o resto | Atender consultas históricas por outro caminho |
| **Expurgo/TTL** | Remover conteúdo expirado | Cuidar do cache e de logs |
| **Dimensão reduzida / quantização** | Menos memória | Medir impacto no recall |
| **Índices em disco / híbridos (memória + SSD)** | Escala a custo menor | Latência maior |
| **Sharding / particionamento** | Distribui carga | Complexidade; fusão de resultados |
| **Tiering (quente/frio)** | Conteúdo popular em índice rápido; resto em frio | Roteamento e custo de miss |
| **Hierarquia (documento → chunk)** | Busca em dois níveis: acha documentos candidatos e depois chunks | Mais etapas |
| **Pré-filtragem eficiente** | Metadados indexados para filtros comuns | Filtros restritivos podem degradar ANN |

### Monitorar a saúde do índice

Acompanhe: nº de chunks, memória/disco, latência p95 de busca, recall em amostra rotulada (para detectar degradação do ANN), idade da última sincronização e taxa de deleções pendentes de compactação.

## 3. Estratégias de reindexação

**Reindexar** = reconstruir (parcial ou totalmente) o índice. Acontece por:

| Gatilho | Exemplo |
|---|---|
| **Troca do modelo de embedding** | Novo modelo melhor ou fornecedor descontinua o antigo — vetores antigos ficam incompatíveis |
| **Mudança de chunking** | Novo tamanho/estratégia, parser melhorado |
| **Mudança de esquema de metadados** | Novos campos de ACL, versão, classificação |
| **Correção em massa** | Bug de extração descoberto |
| **Mudança de parâmetros do índice** | HNSW/IVF, quantização |
| **Migração de banco/infra** | Troca de produto ou região |

### Estratégias

| Estratégia | Como funciona | Prós | Contras |
|---|---|---|---|
| **Reindexação completa offline** | Reconstrói tudo, troca no final | Simples; consistente | Demorada; custo de embedding; janela de desatualização |
| **Blue/green de índices** | Constrói o **novo índice em paralelo** com o antigo ativo; valida; **troca o tráfego** de uma vez | Sem downtime; rollback instantâneo | Dobra o armazenamento temporariamente |
| **Canário / gradual** | Direciona uma fração do tráfego (ou tenants) ao novo índice e compara | Segurança; mede qualidade real | Mais lógica de roteamento |
| **Reindexação incremental por lotes** | Reprocessa por prioridade (mais acessados, tenants) | Menor pico de custo | Estado híbrido temporário; cuidado com mistura de embeddings |
| **Dual-write** | Novos documentos entram nos dois índices durante a migração | Evita perda de atualizações | Complexidade |
| **Reindexação sob demanda (lazy)** | Reindexa o documento quando ele é acessado/alterado | Distribui o custo | Longa convivência de versões; exige consultas multi-índice |

### Regra de ouro: nunca misturar espaços de embedding

Vetores de modelos diferentes (ou versões incompatíveis) **não são comparáveis**. Durante a migração:

- Mantenha **índices separados por versão de modelo** e consulte **o índice correspondente** (o embedding da consulta deve usar o mesmo modelo do índice consultado).
- Evite misturar vetores de dois modelos no mesmo índice.
- Registre `modelo_embedding` e `versao_chunking` como metadado do índice e dos chunks.

```
 Fase 0:  [Índice v1 (modelo A)] ◄── 100% do tráfego
 Fase 1:  construir [Índice v2 (modelo B)] em paralelo  (+ dual-write para novos docs)
 Fase 2:  validar v2 com golden set (recall, fidelidade) e comparar com v1
 Fase 3:  canário: 5% do tráfego → v2  (monitorar qualidade, latência, custo)
 Fase 4:  50% → 100% em v2  (v1 mantido como fallback por um período)
 Fase 5:  desligar v1 após janela de segurança
```

### Planejando custo e tempo

```python
# Estimativa ilustrativa — NÃO executada. Preços fictícios.
n_chunks = 10_000_000
tokens_por_chunk = 400
preco_por_1m_tokens = 0.10                 # US$ por 1M tokens de embedding (exemplo)
custo = n_chunks * tokens_por_chunk / 1_000_000 * preco_por_1m_tokens
print(custo)                               # 400.0 -> ~US$ 400 só de embeddings (sem infra, sem retrabalho)

taxa = 2_000                               # chunks/segundo sustentados (exemplo)
horas = n_chunks / taxa / 3600
print(round(horas, 1))                     # ≈ 1.4 h (limites de taxa da API podem aumentar bastante)
```

### Boas práticas de reindexação

| Prática | Motivo |
|---|---|
| **Versionar** modelo de embedding, chunking, esquema e índice | Rastreabilidade e rollback |
| **Pipeline idempotente e retomável** | Falhas no meio não exigem recomeçar |
| **Guardar o texto bruto/limpo** | Reprocessar sem rebuscar fontes |
| **Validar antes de trocar** (golden set + comparação de métricas) | Evitar regressões |
| **Manter o índice antigo** por uma janela | Rollback rápido |
| **Tratar deleções durante a migração** | Não "ressuscitar" documentos removidos |
| **Reindexar tenant a tenant** | Reduz risco e permite priorizar |
| **Respeitar limites de taxa e custo** | Evitar bloqueios e surpresas |
| **Comunicar janelas** | Quando houver degradação temporária |

## Erros comuns e armadilhas

- **Escolher multi-tenancy por filtro** sem testes de isolamento e sem fail-closed.
- **Esquecer caches, logs e memória** no desenho do isolamento.
- **Um índice por tenant** com milhares de tenants pequenos, tornando a operação inviável.
- **Ignorar tenants gigantes** ("noisy neighbors") que consomem recursos de todos.
- **Subestimar a memória** do HNSW e o crescimento por versões.
- **Trocar o modelo de embedding sem plano de reindexação** (consulta com um modelo, índice com outro).
- **Reindexar sem validação** e sem possibilidade de rollback.
- **Misturar embeddings de modelos diferentes** no mesmo índice.
- **Não considerar o limite de taxa** da API de embeddings durante reindexações em massa.

## 🧩 Quiz de Fixação

1. Compare isolamento por filtro `tenant_id` em base compartilhada e índice por tenant.
2. Por que não se devem misturar vetores de modelos de embedding diferentes no mesmo índice?
3. Descreva uma estratégia blue/green para trocar o modelo de embedding sem downtime.

**Respostas:**
1) Base compartilhada com filtro é mais barata e simples, mas o isolamento é lógico e depende de o filtro ser sempre aplicado corretamente (exige testes e fail-closed). Índice por tenant dá isolamento forte, exclusão/exportação simples e desempenho previsível, porém custa mais e se torna difícil de operar com muitos tenants.
2) Porque cada modelo gera vetores num espaço próprio; distâncias entre vetores de modelos diferentes não têm significado, e a consulta (embutida por um único modelo) não pode ser comparada corretamente com vetores de outro modelo, degradando o retrieval.
3) Constrói-se um novo índice com o novo modelo em paralelo ao ativo (com dual-write para documentos novos), valida-se com o conjunto de avaliação, direciona-se um canário do tráfego ao novo índice, monitora-se qualidade/latência/custo, amplia-se até 100%, mantém-se o antigo como fallback por uma janela e só depois o desliga; a consulta usa sempre o modelo correspondente ao índice consultado.
