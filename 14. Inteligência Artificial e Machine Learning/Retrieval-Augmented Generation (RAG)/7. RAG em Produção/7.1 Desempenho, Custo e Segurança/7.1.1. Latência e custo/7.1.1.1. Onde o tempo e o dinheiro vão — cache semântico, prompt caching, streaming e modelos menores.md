### Onde o tempo e o dinheiro vão — cache semântico, prompt caching, streaming e modelos menores

Em produção, um RAG precisa responder **rápido** e **a um custo sustentável**. Um pipeline sofisticado pode somar vários segundos e centavos por pergunta — multiplicados por milhares de usuários. Este arquivo mostra **onde o tempo e o dinheiro realmente são gastos**, como medir e quais alavancas usar: cache semântico, prompt caching, streaming, modelos menores, paralelização e outras.

> [!warning] Aviso
> Latências, preços por token e recursos de cache variam muito entre provedores, modelos e épocas; os números abaixo são ordens de grandeza didáticas para ilustrar proporções. **Meça no seu sistema.** O código **não foi executado**.

## Anatomia da latência de uma requisição RAG

```
 ┌────────────────────────────────────────────────────────────────────────────────────┐
 │ Reescrita │ Embedding │ Busca  │ Rerank │ Montagem │   LLM: tempo até 1º token    │ Geração
 │ (LLM peq.)│ da query  │ vetorial│        │ do prompt│   (processar o prompt)       │ (tokens
 │ ~200-800ms│ ~20-100ms │ ~10-100 │ ~50-500│ ~1-10ms  │   ~300-3000ms (depende do    │ de saída:
 │           │           │   ms    │   ms   │          │   tamanho do contexto)       │ ~20-100 t/s)
 └────────────────────────────────────────────────────────────────────────────────────┘
   etapas sequenciais somam; a geração costuma dominar (resposta de 300 tokens a ~50 t/s ≈ 6 s)
```

| Etapa | Peso típico | Fatores principais |
|---|---|---|
| **Reescrita/classificação (LLM)** | Médio | Tamanho do modelo; evitar quando desnecessária |
| **Embedding da consulta** | Baixo | Modelo local vs API; tamanho da consulta |
| **Busca (vetorial/híbrida)** | Baixo/médio | Índice, filtros, k, tamanho da base |
| **Reranking** | Médio | Nº de candidatos, modelo, GPU/CPU |
| **Processamento do prompt (prefill)** | Médio/alto | Nº de tokens de entrada (contexto!) |
| **Geração (decode)** | **Alto** | Nº de tokens de saída e velocidade do modelo |
| **Pós-processamento/validações** | Baixo/médio | Verificações extras de LLM |

Duas métricas importam ao usuário:

| Métrica | Significado |
|---|---|
| **TTFT** (Time To First Token) | Tempo até aparecer o primeiro pedaço da resposta — define a sensação de rapidez |
| **Latência total** | Tempo até a resposta completa |

## Anatomia do custo por requisição

```
 custo ≈ (tokens de entrada × preço_entrada) + (tokens de saída × preço_saída)
       + embeddings (consulta) + reranker + chamadas auxiliares de LLM + infraestrutura (índice, GPU)
```

| Componente | Observação |
|---|---|
| **Tokens de entrada** | Instruções + histórico + **contexto recuperado** + pergunta — costuma ser a maior parte |
| **Tokens de saída** | Geralmente mais caros por token que os de entrada |
| **Chamadas auxiliares** | Reescrita, multi-query, avaliador, verificador somam rápido |
| **Reranker** | Por candidato avaliado |
| **Infraestrutura fixa** | Banco vetorial, GPU, observabilidade — custo mesmo sem tráfego |
| **Indexação (offline)** | Embeddings e, se houver, processamento com LLM — amortizado |

```python
# Cálculo ilustrativo — NÃO executado. Preços fictícios.
PRECO_IN, PRECO_OUT = 3.00, 15.00          # US$ por 1 milhão de tokens (exemplo)
tokens_in  = 600 + 1500 + 3500 + 100       # instruções + histórico + contexto + pergunta = 5.700

# O contexto (3.500) é a maior fatia da entrada -> candidato nº 1 a otimização.
```

## Alavancas de otimização

### 1. Reduzir tokens de entrada (a mais eficaz)

| Técnica | Efeito |
|---|---|
| Reranking + k final pequeno (3–6) | Menos contexto, geralmente melhor qualidade |
| Chunks menores/focados, compressão de contexto | Remove ruído (ver 3.2.2.1) |
| Limitar/resumir histórico | Evita crescimento linear por turno |
| Instruções enxutas | Cortar redundâncias do system prompt |
| Evitar reenviar contexto antigo | Só o contexto da pergunta atual |

### 2. Prompt caching (cache de prefixo)

Provedores e servidores de inferência permitem **reaproveitar o processamento** de um **prefixo idêntico** do prompt (instruções, regras, exemplos, base estável), cobrando menos e respondendo mais rápido.

```
 [ INSTRUÇÕES FIXAS + EXEMPLOS ]  [ CONTEXTO RECUPERADO (variável) ]  [ PERGUNTA ]
   └────── prefixo estável ─────┘   └───────────── não cacheável ──────────────┘
   → cache hit no prefixo: menos custo e menor TTFT
```

| Regra | Motivo |
|---|---|
| **Fixo no início, variável no fim** | O cache só vale para prefixo idêntico |
| Manter o prefixo **byte a byte** estável | Qualquer mudança invalida |
| Observar TTL e regras do provedor | Caches expiram; podem exigir tamanho mínimo |
| Cuidado com **segurança** | Não cachear conteúdo restrito compartilhado entre usuários |

### 3. Cache semântico (de respostas)

Guarda **respostas** de perguntas anteriores e, para uma pergunta nova, verifica se há uma **suficientemente parecida** (similaridade de embeddings acima de um limiar); se sim, devolve a resposta salva — sem retrieval nem LLM.

```
 pergunta ─► embedding ─► existe resposta em cache com similaridade ≥ limiar (e mesmo escopo)?
                               │ sim ─► devolve resposta salva  (custo ≈ 0, latência mínima)
                               │ não ─► RAG completo ─► salva (pergunta, resposta, escopo, validade)
```

| Vantagem | Risco/cuidado |
|---|---|
| Custo e latência drásticos em perguntas repetidas (FAQ) | **Respostas erradas** se o limiar for frouxo (perguntas parecidas, respostas diferentes: "prazo do plano Básico" vs "Pro") |
| Escala bem em suporte | **Vazamento entre usuários/tenants:** a chave do cache deve incluir escopo e permissões |
| — | **Desatualização:** invalidar quando documentos mudam (TTL, invalidação por doc) |
| — | Perguntas com contexto de conversa não são cacheáveis diretamente |

```python
# Pseudocódigo didático — NÃO executado.
def responder_com_cache(pergunta, usuario, ctx, limiar=0.95, ttl_h=24):
    escopo = (usuario.tenant_id, usuario.nivel_acesso)            # PARTE DA CHAVE (evita vazamento)
    q = ctx.embed(pergunta)
    hit = ctx.cache.buscar(q, escopo=escopo, limiar=limiar)       # só dentro do mesmo escopo
    if hit and not hit.expirado(ttl_h) and hit.versao_base == ctx.versao_base_atual():
        return hit.resposta                                       # cache hit: sem LLM
    resposta = rag_completo(pergunta, usuario, ctx)
    ctx.cache.salvar(q, resposta, escopo=escopo, versao_base=ctx.versao_base_atual())
    return resposta
```

### 4. Streaming

Enviar a resposta **token a token** conforme é gerada. Não reduz a latência total, mas **reduz drasticamente a latência percebida** (TTFT). Combine com indicadores de progresso ("buscando documentos…"). Cuidado: validações pós-geração (citações, guardrails) são mais difíceis com streaming — considere validar por blocos ou antes do envio quando for crítico.

### 5. Modelos menores onde der

| Tarefa | Modelo |
|---|---|
| Classificação/roteamento, reescrita, avaliação simples | **Pequeno/barato** |
| Reranking | Cross-encoder dedicado (menor que LLM) |
| Geração final | Maior, se qualidade exigir; ou **cascata**: tenta o pequeno, escala ao grande se a confiança for baixa |

Roteamento/cascata de modelos é tratado também em LLM Routing (AI Engineering).

### 6. Paralelismo e redução de etapas sequenciais

| Técnica | Efeito |
|---|---|
| Rodar buscas lexical e vetorial **em paralelo** | Latência = a mais lenta, não a soma |
| Multi-query em paralelo | Idem |
| **Especulação**: iniciar embedding/busca enquanto classifica | Esconde latência |
| Pular etapas desnecessárias por roteamento | Perguntas simples usam fluxo curto |

### 7. Otimizações de infraestrutura

| Item | Ideia |
|---|---|
| Índice ANN bem ajustado, quantização | Menos memória e latência de busca |
| Embeddings com dimensão reduzida (ex.: Matryoshka) | Menos custo de armazenamento/busca |
| Cache de embeddings de consultas frequentes | Evita recomputar |
| Reuso de conexões, regiões próximas, batching | Reduz sobrecarga de rede |
| Auto-hospedar modelos pequenos (embedding, reranker) | Custo previsível em volume alto |

### 8. Controles de saída

| Técnica | Efeito |
|---|---|
| Limitar `max_tokens` e pedir respostas concisas | Menos tokens de saída (caros e lentos) |
| Formato estruturado compacto | Evita verbosidade |

## Matriz: alavanca × ganho × risco

| Alavanca | Reduz custo | Reduz latência | Risco principal |
|---|---|---|---|
| k final menor + reranking | ✅✅ | ✅ | Perder evidência se recall for baixo |
| Prompt caching | ✅✅ | ✅ | Estrutura de prompt rígida; TTL |
| Cache semântico | ✅✅✅ | ✅✅✅ | Respostas erradas/vazamento/desatualização |
| Streaming | — | ✅ (percebida) | Validação pós-geração mais difícil |
| Modelos menores | ✅✅ | ✅✅ | Queda de qualidade |
| Paralelismo | — | ✅✅ | Mais complexidade |
| Roteamento (pular etapas) | ✅✅ | ✅✅ | Erro de roteamento |
| Limitar saída | ✅ | ✅ | Respostas incompletas |

## Como medir e priorizar

1. **Instrumentar** cada etapa (tempo, tokens, custo) por requisição — tracing (ver 7.2.1.1).
2. Olhar **percentis** (p50, p95, p99), não só a média: a cauda é o que o usuário sente.
3. Definir **orçamentos** (ex.: TTFT < 1,5 s; custo médio < X por pergunta).
4. Atacar o **maior item primeiro** (geralmente contexto/entrada e geração).
5. Medir **qualidade junto** (recall, fidelidade): otimização que derruba a qualidade não é ganho.
6. Fazer **testes A/B** e acompanhar regressões.

---

## Erros comuns e armadilhas

- **Otimizar sem medir** e atacar a etapa errada.
- **Olhar só a média** de latência e ignorar p95/p99.
- **Cache semântico com limiar baixo ou sem escopo**, servindo respostas erradas ou de outro usuário.
- **Prompt com parte variável no início**, destruindo o reuso do cache de prefixo.
- **Cortar contexto para economizar** sem checar o impacto no recall e na fidelidade.
- **Encadear muitas chamadas de LLM** (reescrita + multi-query + verificação + juiz) sem orçamento.
- **Ignorar o custo de saída** (verbosidade) e do histórico crescente.
- **Streaming sem tratar validações**, enviando ao usuário conteúdo que depois seria bloqueado.

## 🧩 Quiz de Fixação

1. Por que a regra "fixo no início, variável no fim" importa para o prompt caching?
2. Quais os principais riscos do cache semântico e como mitigá-los?
3. Diferencie TTFT de latência total e diga o que o streaming melhora.

**Respostas:**
1) Porque o cache reaproveita apenas um prefixo idêntico do prompt; se a parte variável (contexto, pergunta) vier antes do conteúdo fixo, o prefixo muda a cada chamada e o cache não é aproveitado. Com o fixo no início, o prefixo estável gera cache hits, reduzindo custo e TTFT.
2) Riscos: respostas erradas por limiar frouxo (perguntas parecidas com respostas diferentes), vazamento entre usuários/tenants e respostas desatualizadas. Mitigação: limiar alto e testado, escopo/permissões na chave do cache, TTL e invalidação quando documentos mudam, e não cachear perguntas dependentes de contexto de conversa.
3) TTFT é o tempo até o primeiro token da resposta; latência total é o tempo até a resposta completa. O streaming melhora a latência percebida (TTFT/sensação de rapidez), sem reduzir a latência total.
