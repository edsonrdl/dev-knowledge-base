### Checklist de decisão — que arquitetura de RAG escolher para cada cenário

Depois de percorrer fundamentos, indexação, retrieval, geração, arquiteturas, avaliação e produção, resta a pergunta prática: **"para o meu caso, o que eu construo?"** Este arquivo é um guia de decisão: perguntas-chave, uma árvore de escolha de arquitetura, uma tabela por cenário, a sequência de evolução recomendada e checklists de lançamento. Serve como consulta rápida que remete aos arquivos do guia.

> [!warning] Aviso
> Isto é um guia de heurísticas, não uma regra. A decisão final depende de dados, requisitos e **medições** no seu contexto. Tecnologias, preços e capacidades mudam; reavalie periodicamente.

---

## Princípio orientador

> **Comece pelo mais simples que atenda aos requisitos, meça, e só adicione complexidade quando uma falha medida a justificar.**

```
 Requisitos ─► Avaliação (golden set) ─► Baseline simples ─► Medir ─► Achar o estágio da falha
      ▲                                                                       │
      └───────────── adicionar UMA técnica que ataque essa falha ◄────────────┘
```

## Passo 2 — Árvore de escolha de abordagem e arquitetura

```
 Os dados cabem na janela, são estáveis e iguais para todos?
   sim ─► Prompt longo (+ prompt caching) / CAG ........................ [simples, sem retrieval]
   não ↓
 Preciso de fatos atuais/privados/citáveis?
   não ─► Fine-tuning ou prompt engineering (estilo/tarefa) ou busca clássica
   sim ↓
 Os dados são sobretudo NÚMEROS/TABELAS em banco?
   sim ─► Text-to-SQL / camada semântica (+ RAG em texto se houver explicações) ... [5.2.2.1]
   não ↓
 Há imagens/áudio/vídeo como fonte?
   sim ─► RAG multimodal (conversão para texto e/ou embeddings multimodais) ...... [5.2.3.1]
   não ↓
 ► ADVANCED RAG sobre texto (base padrão): híbrida + filtros + reranker + grounding + citações
      │
      ├─ Perguntas variadas, várias fontes/ferramentas? ─► + roteamento (MODULAR) ........ [5.1.1.3]
      ├─ Retrieval às vezes ruim e contamina a resposta? ─► + avaliador/CRAG, Self-RAG-style [5.2.1.1]
      ├─ Perguntas globais/relacionais sobre o corpus? ───► + resumos hierárquicos / GRAPHRAG [5.2.2.1]
      └─ Multi-hop exploratório, tarefas abertas? ────────► + AGENTIC RAG (com limites) ..... [5.2.2.2]
```

## Passo 3 — Tabela por cenário

| Cenário | Arquitetura recomendada | Pontos de atenção |
|---|---|---|
| **Protótipo / prova de conceito** | Naive RAG com avaliação mínima (30–50 perguntas) | Não confundir protótipo com produção |
| **FAQ / suporte com base homogênea** | Advanced RAG: híbrida + reranker + citações + "não sei" | Cache semântico com escopo; backlog de lacunas |
| **Documentação técnica com códigos/siglas** | Híbrida (BM25 forte) + chunking por seção + reranking | Termos exatos; versões de produto como filtro |
| **Jurídico / compliance** | Advanced RAG + citações por afirmação + verificação de suporte + humano no loop | Versionamento/vigência, auditoria, grounding estrito |
| **Saúde / alto risco** | Idem + guardrails rigorosos, fontes oficiais, escalonamento | Responsabilidade; validação clínica; privacidade |
| **Multi-tenant SaaS** | Advanced RAG + isolamento por tenant (namespace/coleção) + ACL | Testes de isolamento, cache escopado, noisy neighbors |
| **Conversacional (chat longo)** | Advanced + reescrita com histórico + gestão de memória | Orçamento de contexto, follow-ups |
| **Pesquisa/análise sobre corpus grande** | Advanced + resumos hierárquicos; GraphRAG se houver relações | Custo de indexação; perguntas globais |
| **Dados estruturados (BI)** | Text-to-SQL / camada semântica; roteamento com RAG textual | SQL somente leitura, validação, definições oficiais |
| **Perguntas multi-hop / investigação** | Modular → Agentic (com limites) | Custo/latência; tracing da trajetória |
| **Base pequena e estável (um manual)** | Prompt longo + caching (ou CAG) | Reavaliar se crescer |
| **Conteúdo multimídia (reuniões, vídeos, imagens)** | RAG multimodal (transcrição/OCR/embeddings visuais) | Qualidade da conversão, privacidade |
| **Dados muito sensíveis / on-premises** | Modelos de embedding/LLM locais + RAG com isolamento forte | Custo de infraestrutura; soberania |
| **Latência ultrabaixa** | Pipeline enxuto, modelos pequenos, cache, sem multi-query | Medir o impacto na qualidade |
| **Orçamento muito limitado** | Naive/Advanced mínimo, BM25 + vetor simples, k pequeno | Avaliação enxuta, foco em conteúdo |

## Passo 4 — Sequência de evolução recomendada

| Ordem | Ação | Quando |
|---|---|---|
| 1 | **Conjunto de avaliação + métricas por estágio** | Sempre, antes de tudo |
| 2 | Curadoria de dados, parsing e chunking decentes | Sempre |
| 3 | Prompt de grounding, "não sei" e citações | Sempre |
| 4 | Busca **híbrida** + **filtros/metadados/ACL** | Quando houver termos exatos ou permissões |
| 5 | **Reranking** | Se recall alto e precision/MRR baixos |
| 6 | **Reescrita com histórico** | Se há chat |
| 7 | Sincronização/versionamento/observabilidade/feedback | Antes de produção |
| 8 | Multi-query/HyDE/decomposição | Se a avaliação mostrar vocabulary mismatch ou perguntas compostas |
| 9 | Roteamento (Modular) | Múltiplas fontes/tipos de pergunta |
| 10 | CRAG/Self-RAG-style | Se retrieval ruim contamina respostas |
| 11 | GraphRAG / resumos hierárquicos | Se há perguntas globais/relacionais frequentes |
| 12 | Agentic RAG | Se há multi-hop/exploração que o pipeline fixo não resolve |
| 13 | Otimizações de custo/latência (caching, modelos menores) | Quando o volume justificar |

## Checklist de lançamento (produção)

### Dados e indexação
- [ ] Fontes curadas, com dono e status (vigente/obsoleto)
- [ ] Parsing validado por amostra (tabelas, colunas, OCR)
- [ ] Chunking justificado e testado; metadados completos (fonte, versão, data, ACL)
- [ ] Sincronização incremental + reconciliação + deleção física
- [ ] Plano de reindexação (versionamento de modelo/chunking)

### Retrieval e geração
- [ ] Busca adequada (híbrida se houver termos exatos); filtros aplicados na busca
- [ ] Limiar calibrado; comportamento definido para "sem resultados"
- [ ] Reranking avaliado (ganho medido)
- [ ] Prompt versionado: grounding, "não sei", conflito de fontes, contexto como dado
- [ ] Citações validadas em código
- [ ] Orçamento de contexto e ordenação definidos

### Avaliação
- [ ] Golden set representativo (incluindo sem resposta, segurança, multi-turno)
- [ ] Métricas por estágio (recall@k, MRR, fidelidade, relevância, recusa correta)
- [ ] Metas definidas e atingidas; CI com gates de regressão

### Segurança e privacidade
- [ ] ACL/tenant derivados do servidor, fail-closed; testes de isolamento
- [ ] Contexto tratado como dado; privilégio mínimo; confirmação em ações com efeito
- [ ] Filtro de saída (URLs, PII); logs mascarados; retenção definida
- [ ] Provedores de LLM/embedding avaliados (retenção, treino, região); base legal e direitos do titular

### Operação
- [ ] Tracing completo (consulta, candidatos, scores, prompt, resposta, versões)
- [ ] Alertas: frescor do índice, qualidade, "não sei", latência, custo, segurança
- [ ] Coleta de feedback ligada ao trace; backlog de conteúdo
- [ ] Rollout gradual, rollback e plano de incidentes
- [ ] Limites de taxa, quotas, orçamentos de custo e latência

## Armadilhas finais (as mais comuns)

| Armadilha | Antídoto |
|---|---|
| Escolher arquitetura pela moda | Decidir por requisitos e falhas medidas |
| Pular a avaliação | Golden set desde o início |
| Subestimar dados | Priorizar curadoria, parsing e sincronização |
| Complexidade prematura (agentes, grafos) | Evoluir só com evidência |
| Ignorar segurança até o fim | Desenhar ACL e isolamento no começo |
| Otimizar o prompt para compensar retrieval ruim | Diagnosticar o estágio primeiro |
| Prometer 100% de acerto | Mostrar fontes, permitir recusa e escalonar para humanos |
| Produção sem observabilidade | Tracing, métricas e feedback antes do lançamento |

## 🧩 Quiz de Fixação

1. Por que "avaliação" é o primeiro item da sequência de evolução, antes de qualquer técnica avançada?
2. Num cenário com muitos códigos de erro e siglas, que ajuste de retrieval você priorizaria e por quê?
3. Quando faz sentido evoluir de Advanced RAG para Agentic RAG, e quais salvaguardas são indispensáveis?

**Respostas:**
1) Porque sem um conjunto de avaliação e métricas por estágio não é possível saber onde o sistema falha nem se uma técnica melhorou ou piorou algo; qualquer adição de complexidade seria aposta. A avaliação orienta qual técnica adotar e protege contra regressões.
2) Busca híbrida com BM25 forte (lexical) combinada à vetorial via fusão (RRF), porque embeddings representam mal termos exatos e raros, enquanto a busca lexical os casa precisamente; depois pode-se adicionar reranking para refinar.
3) Quando há perguntas multi-hop ou exploratórias que o pipeline fixo não resolve e a avaliação comprova o ganho. Salvaguardas: limites de passos, tokens, custo e tempo; ferramentas com privilégio mínimo e executadas com as permissões do usuário; validação de argumentos; tratamento do conteúdo recuperado como dado; confirmação humana em ações sensíveis; tracing completo e avaliação da trajetória.
