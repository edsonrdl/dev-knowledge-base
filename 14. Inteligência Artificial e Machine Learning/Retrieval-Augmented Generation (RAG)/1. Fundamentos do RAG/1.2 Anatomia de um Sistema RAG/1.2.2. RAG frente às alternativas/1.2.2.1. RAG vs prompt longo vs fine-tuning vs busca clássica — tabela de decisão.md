### RAG vs prompt longo vs fine-tuning vs busca clássica — tabela de decisão

Quando surge a necessidade de "fazer a IA conhecer nossos dados", existem quatro caminhos: **colocar tudo no prompt (contexto longo)**, **RAG**, **fine-tuning** e **busca clássica sem LLM**. Cada um resolve um problema diferente, e muitos projetos falham por escolher o caminho errado. Este arquivo compara as opções e termina com uma tabela de decisão.

> [!warning] Aviso
> Tamanhos de janela de contexto, preços e capacidades de modelos mudam rápido; os números são ordens de grandeza didáticas. Os exemplos de código **não foram executados**.

---

## As quatro opções em uma frase

| Opção | Ideia | Analogia |
|---|---|---|
| **Prompt longo (long context)** | Colocar os documentos inteiros no prompt a cada chamada | Entregar a pilha toda de papéis ao analista a cada pergunta |
| **RAG** | Buscar só os trechos relevantes e enviá-los no prompt | O analista consulta o arquivo e traz só as páginas pertinentes |
| **Fine-tuning** | Ajustar os pesos do modelo com exemplos | Treinar o analista para ter um jeito de trabalhar (estilo, formato, domínio) |
| **Busca clássica** | Mecanismo de busca (palavras-chave/filtros) que devolve documentos, sem LLM gerar resposta | O índice remissivo da biblioteca |

```
                  Conhecimento
                  ┌────────────────┐
 Prompt longo:    │ TUDO no prompt │──► LLM ──► resposta
                  └────────────────┘
 RAG:             pergunta ─► [buscar] ─► só o relevante ─► LLM ─► resposta + fonte
 Fine-tuning:     exemplos ─► [treino] ─► NOVOS PESOS ─► LLM ─► resposta (sem fonte)
 Busca clássica:  pergunta ─► [índice] ─► lista de documentos (sem síntese)
```

---

## Comparação por critério

| Critério | Prompt longo | RAG | Fine-tuning | Busca clássica |
|---|---|---|---|---|
| **Tamanho da base** | Limitado à janela | Praticamente ilimitado | Qualquer (mas virada em pesos) | Ilimitado |
| **Atualização do conhecimento** | Imediata (troca o texto) | Imediata (reindexa o item) | Lenta/cara (retreinar) | Imediata |
| **Custo por consulta** | Alto (paga todos os tokens a cada vez) | Médio (só os trechos) | Baixo no prompt, mas há custo de treino/hospedagem | Muito baixo |
| **Latência** | Alta com contextos grandes | Média (busca + geração) | Baixa | Muito baixa |
| **Citação de fontes** | Possível (documento está no prompt) | Natural (trechos têm origem) | Difícil/inexistente | Natural |
| **Controle de acesso por usuário** | Difícil | Viável (filtros por ACL) | Muito difícil | Viável |
| **Muda comportamento/estilo?** | Pouco | Pouco | **Sim, é o ponto forte** | Não se aplica |
| **"Agulha no palheiro"** | Pode degradar em contexto enorme | Depende da qualidade do retrieval | Fraca para fatos específicos | Boa para termos exatos |
| **Complexidade de operação** | Baixa | Média/alta (pipeline, índice) | Alta (dados, treino, avaliação) | Baixa/média |

## Entendendo cada alternativa

### Prompt longo
Janelas de contexto cresceram muito, e para bases pequenas (um manual de 50 páginas, um contrato) **colocar tudo no prompt é a solução mais simples**. Limites: custo e latência crescem a cada pergunta (você reenvia tudo), há degradação de atenção em contextos enormes (ver "lost in the middle" em 4.1.1.2), e não escala para milhares de documentos nem resolve permissões por usuário. Pode ser combinado com **prompt caching** para baratear partes fixas (ver 7.1.1.1).

### RAG
Brilha quando a base é **grande, mutável, privada e precisa de fonte**. Custo: manter um pipeline (ingestão, índice, avaliação). Fraqueza: se o retrieval falhar, o modelo não vê a informação certa.

### Fine-tuning
Ajusta **comportamento**: tom de voz, formato de saída, terminologia do domínio, tarefas específicas (classificação, extração), uso de ferramentas. É **ruim para injetar fatos que mudam** (difícil atualizar, sem citação, risco de o modelo misturar ou esquecer). Regra prática: *fine-tuning ensina "como responder"; RAG fornece "o que responder"*. O Glossário tem um tópico próprio sobre o tema: "Quando Usar Fine-Tuning vs RAG".

### Busca clássica
Se o usuário só precisa **achar documentos** (e lê-los sozinho), um buscador com filtros e palavras-chave pode bastar — barato, previsível e explicável. O RAG adiciona a *síntese em linguagem natural*, valiosa mas nem sempre necessária. A busca lexical (BM25) continua sendo **parte** de bons sistemas RAG via busca híbrida (ver 3.1.1.1).

## Combinações são comuns

As opções **não são excludentes**:

| Combinação | Para quê |
|---|---|
| RAG + fine-tuning | Modelo com o tom/formato da empresa **e** conhecimento atual via retrieval |
| RAG + prompt longo | Recuperar documentos inteiros relevantes (em vez de chunks pequenos) e usar janela grande |
| RAG + busca clássica | Busca híbrida: lexical para termos exatos, vetorial para semântica |
| Fine-tuning do **embedding/reranker** + RAG | Melhorar o retrieval em domínio especializado (ver [[14. Inteligência Artificial e Machine Learning/AI Engineering (Engenharia Aplicada)/3. ## Tabela de decisão

| Situação | Caminho recomendado |
|---|---|
| Base pequena (cabe na janela), poucas consultas, protótipo | **Prompt longo** (com caching, se repetido) |
| Base grande, muda com frequência, exige fonte | **RAG** |
| Dados privados com permissões diferentes por usuário | **RAG** com filtros de ACL |
| Quer padronizar tom, formato JSON, classificação | **Fine-tuning** (ou bom prompt + exemplos) |
| Domínio com jargão, mas conhecimento também muda | **RAG + fine-tuning** |
| Usuário só precisa localizar documentos | **Busca clássica** (talvez híbrida) |
| Perguntas globais sobre todo o corpus ("quais os temas principais?") | RAG simples sofre; considerar GraphRAG/sumarização (ver 5.2.2.1) |
| Necessidade de auditoria e citações | **RAG** (ou prompt longo com citações) |

### Fluxograma simplificado

```
 A base cabe na janela e muda pouco? ──sim──► Prompt longo (+ caching)
              │ não
              ▼
 Precisa de fatos atuais/privados/citáveis? ──sim──► RAG
              │ não
              ▼
 Precisa mudar estilo/formato/tarefa? ──sim──► Fine-tuning (ou prompt engineering)
              │ não
              ▼
 Só localizar documentos? ──sim──► Busca clássica
```

## Exemplo prático: estimando o custo do prompt longo vs RAG

```python
# Cálculo ilustrativo — NÃO executado. Preço fictício para mostrar a lógica.
PRECO_POR_1M_TOKENS = 3.00      # US$ por 1 milhão de tokens de entrada (exemplo)
consultas_por_dia = 2000        # volume de perguntas

tokens_base_inteira = 150_000   # prompt longo: reenvia a base toda a cada pergunta
tokens_rag = 3_000              # RAG: ~4 trechos + instruções + pergunta

custo_longo = consultas_por_dia * tokens_base_inteira / 1_000_000 * PRECO_POR_1M_TOKENS
custo_rag   = consultas_por_dia * tokens_rag          / 1_000_000 * PRECO_POR_1M_TOKENS

print(custo_longo)   # 2000 * 0.15 * 3 = 900.0  -> US$ 900/dia (só entrada)
print(custo_rag)     # 2000 * 0.003 * 3 = 18.0  -> US$ 18/dia
# Prompt caching pode reduzir bastante o custo do prompt longo, e o RAG ainda
# tem custos de embedding/infraestrutura. Compare com preços reais.
```

A diferença de 50x é o motivo clássico para preferir RAG em alto volume — mas com poucas consultas por dia, o prompt longo pode ser mais barato no total, por dispensar a infraestrutura.

## Erros comuns e armadilhas

- **Usar fine-tuning para "ensinar" documentos.** O modelo não vira um banco de dados confiável; atualizar exige retreinar e não há citação.
- **Montar RAG para uma base minúscula.** Infraestrutura desnecessária; prompt longo resolve.
- **Contar apenas o custo de tokens.** Esquecer o custo de operar pipeline, índice, monitoração e reindexação (e, no fine-tuning, de dados e avaliação).
- **Assumir que contexto longo elimina a necessidade de retrieval.** Precisão e custo pioram em contextos enormes, e permissões por usuário continuam sendo um problema.
- **Ignorar a opção "sem LLM".** Em alguns casos, uma boa busca com filtros entrega o valor com 1% do custo.

## 🧩 Quiz de Fixação

1. Qual a regra prática que diferencia fine-tuning de RAG?
2. Uma startup tem um manual de 40 páginas e 100 consultas por dia. Qual alternativa provavelmente é a mais simples e por quê?
3. Dê um exemplo de combinação entre duas dessas abordagens e o ganho que ela traz.

**Respostas:**
1) Fine-tuning ensina "como responder" (estilo, formato, tarefa), enquanto RAG fornece "o que responder" (fatos atuais, privados e citáveis). Fatos mutáveis ficam melhor no RAG.
2) Prompt longo (talvez com prompt caching): o manual cabe na janela, o volume é baixo e não é preciso montar pipeline de indexação, embeddings e banco vetorial; o custo adicional de tokens é pequeno nesse volume.
3) Por exemplo, RAG + fine-tuning: o fine-tuning padroniza tom e formato da resposta, e o RAG injeta o conhecimento atualizado e citável. Outra: busca híbrida (lexical + vetorial), que acerta tanto termos exatos quanto semântica.
