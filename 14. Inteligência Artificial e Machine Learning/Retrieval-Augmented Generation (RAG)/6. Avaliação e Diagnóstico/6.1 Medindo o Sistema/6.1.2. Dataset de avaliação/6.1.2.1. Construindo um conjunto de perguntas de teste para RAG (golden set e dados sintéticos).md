## O que é um conjunto de avaliação de RAG

Uma coleção de **casos de teste**, cada um com:

| Campo | Descrição | Usado por |
|---|---|---|
| **Pergunta** | Como um usuário real perguntaria | Todas |
| **Resposta de referência** | A resposta correta esperada (ou fatos-chave) | Correção, context recall |
| **Evidências (chunks/documentos relevantes)** | Onde a resposta está na base (ids) | Recall@k, precision@k, MRR, nDCG |
| **Tipo/categoria** | Factual, comparação, multi-hop, sem resposta... | Análise por segmento |
| **Metadados** | Dificuldade, produto, idioma, perfil de usuário | Filtros e análise |
| **Comportamento esperado** | Responder, recusar ("não sei"), pedir esclarecimento, escalar | Testes de recusa |

```
 caso_017:
   pergunta:    "Posso devolver um produto digital?"
   resposta_ref:"Produtos digitais não podem ser reembolsados após o download (exceção à regra de 14 dias)."
   evidencias:  ["politica-reembolso#v3#0004", "politica-reembolso#v3#0005"]
   tipo:        "excecao"
   esperado:    "responder"
```

## Golden set: curado por humanos

O **golden set** é a base confiável: poucos casos, bem escolhidos e **validados por especialistas**.

### De onde tirar as perguntas

| Fonte | Vantagem | Cuidado |
|---|---|---|
| **Logs reais** de usuários (anonimizados) | Reflete o uso verdadeiro | Remover PII; cuidar com perguntas ruins/ambíguas |
| **Tickets de suporte, e-mails, chats** | Linguagem real e problemas reais | Normalizar e anonimizar |
| **Especialistas de domínio** | Casos difíceis e sutis | Podem escrever perguntas "técnicas demais" |
| **FAQs existentes** | Fácil de começar | Viés para o que já está documentado |
| **Lacunas conhecidas** (reclamações, erros passados) | Cobre regressões | — |

### Cobertura: o que o conjunto precisa incluir

| Categoria | Por que incluir |
|---|---|
| **Factuais simples** | Linha de base |
| **Paráfrases e linguagem informal** | Testa vocabulário diferente do documento |
| **Termos exatos** (códigos, siglas, nomes) | Testa busca lexical/híbrida |
| **Perguntas com exceções/condições** | Testa chunking e raciocínio |
| **Multi-hop / multi-documento** | Testa decomposição e síntese |
| **Numéricas e tabulares** | Testa parsing de tabelas |
| **Multi-turno (com histórico)** | Testa reescrita de consulta |
| **Sem resposta na base** | Testa recusa correta (essencial) |
| **Fora do escopo / armadilhas** | Testa limites do assistente |
| **Conflito/versões** | Testa versionamento e vigência |
| **Perguntas ambíguas** | Testa pedido de esclarecimento |
| **Segurança** (injeção, pedidos proibidos, dados de outro usuário) | Testa guardrails e ACL |

### Tamanho

| Estágio | Tamanho típico | Uso |
|---|---|---|
| Início | 30–50 casos | Detectar falhas grosseiras e comparar configurações |
| Maturidade | 100–300+ | Métricas mais estáveis, análise por categoria |
| Produção madura | Cresce continuamente com novos casos de falha | Regressão contínua |

Mais importante que o número é a **representatividade**: 50 casos bem escolhidos valem mais que 500 repetitivos.

## Dados sintéticos: ampliando com LLM

Gerar perguntas com LLM a partir dos documentos permite **escalar** a cobertura rapidamente.

### Como funciona

```
 chunk/documento ─► LLM gera:  pergunta + resposta de referência  (a partir SÓ do trecho)
                       │
                       ▼
              filtros de qualidade (autossuficiente? respondível? não trivial?)
                       │
                       ▼
              caso sintético {pergunta, resposta_ref, evidência = o chunk de origem}
```

A **evidência é conhecida por construção** (o chunk que originou a pergunta), o que dá o gabarito de retrieval "de graça".

### Estratégias de geração

| Estratégia | Descrição |
|---|---|
| **Pergunta por chunk** | Para chunks amostrados, gerar 1–3 perguntas |
| **Multi-chunk** | Combinar chunks relacionados para gerar perguntas de síntese/comparação |
| **Evolução de perguntas** | Reescrever perguntas simples em versões mais difíceis (raciocínio, condições, informal) |
| **Personas** | Pedir perguntas "como um iniciante", "como um especialista", "com erros de digitação" |
| **Perguntas sem resposta** | Gerar perguntas plausíveis **fora** do conteúdo e rotular "sem resposta" (verificando que a base realmente não cobre) |
| **Paráfrase** | Reescrever perguntas para reduzir sobreposição lexical com o texto |

```python
# Pseudocódigo didático — NÃO executado. 'llm' é um modelo forte; 'chunks' foram amostrados da base.

PROMPT_GERAR = """Você é um usuário real do sistema. A partir SOMENTE do trecho abaixo,
escreva uma pergunta natural que um usuário faria e que este trecho responde, e a resposta correta.
Regras: não cite 'o trecho' nem 'o texto'; a pergunta deve ser autossuficiente; evite copiar frases.
Trecho:
{trecho}
Formato JSON: {{"pergunta": "...", "resposta": "..."}}"""

def gerar_casos_sinteticos(llm, chunks, n_por_chunk=1):
    casos = []
    for ch in chunks:
        for _ in range(n_por_chunk):
            bruto = llm(PROMPT_GERAR.format(trecho=ch["texto"]))
            item = json.loads(bruto)                            # (trate erros de JSON na prática)
            casos.append({
                "pergunta": item["pergunta"],
                "resposta_ref": item["resposta"],
                "evidencias": [ch["id"]],                       # gabarito de retrieval por construção
                "origem": "sintetico",
            })
    return filtrar_qualidade(llm, casos)                        # descarta perguntas ruins
```

### Filtros de qualidade (indispensáveis)

| Filtro | O que descarta |
|---|---|
| **Autossuficiência** | Perguntas como "o que o autor diz aqui?" ou que dependem do trecho |
| **Respondibilidade** | A resposta realmente está na evidência? |
| **Dificuldade** | Perguntas triviais que copiam o texto literal |
| **Duplicatas** | Perguntas repetidas ou quase iguais |
| **Ambiguidade** | Perguntas com múltiplas interpretações |
| **Ruído** | Perguntas absurdas ou fora do domínio |
| **Revisão humana por amostragem** | Mede a qualidade geral da geração |

## Golden set vs sintético: papéis diferentes

| Aspecto | Golden set (humano) | Sintético (LLM) |
|---|---|---|
| **Confiabilidade** | Alta | Média; exige filtros e amostragem humana |
| **Custo** | Alto (tempo de especialistas) | Baixo |
| **Escala** | Pequena/média | Grande |
| **Realismo** | Alto (se vier de logs reais) | Médio (tende a ser "limpo", pouco informal) |
| **Cobertura de casos estranhos** | Boa | Fraca (a menos que se dirija) |
| **Uso ideal** | **Decisões finais** e regressão | **Exploração** rápida e varredura ampla |

> [!tip] Estratégia recomendada
> Use o **sintético** para iterar rápido e cobrir muitos tópicos, e o **golden set** como árbitro para decisões importantes. Convirta casos reais de falha em produção (com feedback do usuário) em novos casos do golden set — o conjunto cresce com o aprendizado.

## Armadilhas específicas dos dados sintéticos

| Armadilha | Descrição | Mitigação |
|---|---|---|
| **Viés de vocabulário** | A pergunta copia palavras do chunk; a busca lexical "acerta" fácil demais | Pedir paráfrases e linguagem informal |
| **Circularidade** | Mesmo LLM gera e avalia, favorecendo o próprio estilo | Modelos distintos; revisão humana |
| **Favorece o que está documentado** | Gera só perguntas que a base responde | Incluir explicitamente perguntas sem resposta e fora de escopo |
| **Distribuição irreal** | Perguntas uniformes por chunk, enquanto usuários perguntam sempre as mesmas coisas | Ponderar pela frequência real (logs) |
| **Ground truth incorreto** | O LLM errou a resposta de referência | Amostragem e revisão humana |
| **Vazamento** | Reusar os mesmos chunks/perguntas para ajustar e avaliar (overfitting) | Separar conjunto de desenvolvimento e de teste |

## Ciclo de vida do conjunto de avaliação

```
 1. Definir objetivos e categorias  ─► 2. Coletar perguntas reais  ─► 3. Rotular evidências/respostas
        ▲                                                                      │
        │                                                                      ▼
 7. Incorporar novas falhas   ◄── 6. Monitorar em produção  ◄── 5. Rodar avaliações  ◄── 4. Ampliar com sintéticos + filtros
```

| Boa prática | Motivo |
|---|---|
| **Versionar** o conjunto (como código) | Comparabilidade entre execuções |
| **Separar** desenvolvimento (para ajustes) e teste (intocado) | Evitar overfitting |
| **Remapear evidências** quando mudar o chunking | O gabarito por chunk-id fica obsoleto |
| **Anonimizar** dados pessoais | Privacidade (ver 7.1.2.1) |
| **Registrar quem rotulou e quando** | Auditoria e resolução de discordâncias |
| **Medir concordância entre avaliadores** | Qualidade dos rótulos |
| **Rodar no CI** (gates de regressão) | Evitar piora silenciosa |

## Erros comuns e armadilhas

- **Não ter conjunto de avaliação** e decidir por "sentir".
- **Conjunto só com perguntas fáceis** (as que o sistema já acerta).
- **Esquecer perguntas sem resposta**, que revelam alucinação.
- **Rotular evidências por chunk-id e depois mudar o chunking** sem remapear.
- **Avaliar com os mesmos casos usados para ajustar o prompt** (overfitting).
- **Confiar cegamente no sintético**, sem filtros nem revisão humana.
- **Conjunto estático para sempre**: o produto e as perguntas evoluem.
- **Misturar PII real** no conjunto sem anonimização.

## 🧩 Quiz de Fixação

1. Por que o conjunto de avaliação deve incluir perguntas sem resposta na base?
2. Quais as vantagens e riscos de gerar perguntas sintéticas com LLM?
3. Por que separar um conjunto de desenvolvimento e um de teste?

**Respostas:**
1) Porque medem a recusa correta: sem elas não se detecta quando o sistema inventa respostas na ausência de evidência, que é um dos modos de falha mais graves do RAG; além disso, ajudam a calibrar limiar de retrieval e a instrução de "não sei".
2) Vantagens: escala, baixo custo, gabarito de retrieval por construção (o chunk de origem) e cobertura ampla. Riscos: viés de vocabulário (perguntas copiadas do texto), circularidade se o mesmo LLM gera e avalia, distribuição irreal, respostas de referência erradas e foco só no que está documentado. Mitigam-se com paráfrases, filtros de qualidade, modelos distintos e revisão humana por amostragem.
3) Para evitar overfitting: se ajustamos prompts e parâmetros olhando os mesmos casos usados para medir, as métricas ficam otimistas. O conjunto de teste, mantido intocado, dá uma estimativa honesta do desempenho em perguntas novas.
