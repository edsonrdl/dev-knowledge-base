### Métricas de retrieval — recall@k, precision@k, MRR e nDCG

Para melhorar um RAG é preciso **medir**, e a primeira regra da avaliação é **separar o retrieval da geração**: se a resposta está errada, foi porque o trecho certo não foi recuperado, ou porque o LLM usou mal o que recebeu? As métricas de retrieval respondem à primeira pergunta olhando só a lista de resultados, sem precisar de LLM. Este arquivo apresenta as métricas clássicas — **hit rate, recall@k, precision@k, MRR e nDCG** — com intuição, cálculo e orientação de uso.

## O que é preciso para medir: o "gabarito" de retrieval

Para calcular essas métricas, cada pergunta de teste precisa saber **quais chunks/documentos são relevantes** (o *ground truth*):

| Item do conjunto de teste | Exemplo |
|---|---|
| Pergunta | "Qual o prazo de reembolso no app?" |
| Documentos/chunks relevantes (rótulos) | `{politica-reembolso#v3#0004}` |
| (Opcional) Grau de relevância | 0 = irrelevante · 1 = parcial · 2 = totalmente relevante |

Esse gabarito vem de rotulagem humana, de especialistas ou, com cuidado, de geração sintética (ver 6.1.2.1).

```
 Para cada pergunta:
   o sistema devolve uma LISTA ORDENADA:  [c7, c2, c9, c4, c1, ...]   (k primeiros)
   o gabarito diz quais são relevantes:   {c2, c4}
   a métrica compara os dois
```

## As métricas

Notação: **k** = quantos resultados se consideram; **R** = conjunto de itens relevantes; **top-k** = k primeiros resultados.

### Hit rate@k (acerto)

Proporção de perguntas em que **pelo menos um** item relevante aparece no top-k.

```
 hit@k = (nº de perguntas com ao menos 1 relevante no top-k) / (nº de perguntas)
```

Útil quando basta **um** trecho certo para responder. Simples e intuitiva.

### Recall@k (cobertura)

Fração dos itens relevantes que aparecem no top-k.

```
 recall@k = |relevantes ∩ top-k| / |relevantes|
```

Exemplo: há 2 relevantes {c2, c4}; o top-5 é [c7, c2, c9, c4, c1] → contém os dois → recall@5 = 2/2 = **1,0**. Se o top-3 fosse [c7, c2, c9] → recall@3 = 1/2 = **0,5**.

**Quando importa:** quando a resposta exige **todas** as peças de evidência (multi-trecho). Também é a métrica mais usada para decidir o **k da busca inicial** (recuperar largo).

### Precision@k (pureza)

Fração do top-k que é relevante.

```
 precision@k = |relevantes ∩ top-k| / k
```

Exemplo: top-5 = [c7, c2, c9, c4, c1] com relevantes {c2, c4} → precision@5 = 2/5 = **0,4**.

**Quando importa:** quando o contexto entregue ao LLM é pequeno e o ruído prejudica (**k final**, após reranking).

> [!info] Tensão entre as duas
> Aumentar k tende a **subir o recall e baixar a precision**. Por isso se usa k grande na busca inicial (olhar recall) e k pequeno no contexto final (olhar precision).

### MRR (Mean Reciprocal Rank)

Mede **quão alto** aparece o primeiro item relevante. Para cada pergunta, calcula-se `1 / posição do primeiro relevante` (0 se não aparece); depois faz-se a média.

```
 RR = 1 / posição_do_primeiro_relevante        MRR = média de RR sobre as perguntas

 Pergunta A: primeiro relevante na posição 1 → RR = 1
 Pergunta B: na posição 2                   → RR = 0,5
 Pergunta C: na posição 4                   → RR = 0,25
 Pergunta D: não aparece                    → RR = 0
 MRR = (1 + 0,5 + 0,25 + 0) / 4 = 0,4375
```

**Quando importa:** quando o primeiro resultado correto é o que mais conta (perguntas com uma resposta; interface que mostra poucos resultados). Penaliza fortemente posições baixas.

### nDCG (Normalized Discounted Cumulative Gain)

Considera **graus de relevância** e **a posição**: itens muito relevantes devem vir primeiro. Tem três ideias:

1. **Ganho**: cada item contribui com sua relevância (ex.: 0, 1, 2).
2. **Desconto**: contribuições em posições baixas valem menos (divide por `log2(posição + 1)`).
3. **Normalização**: divide pelo valor do ranking **ideal**, resultando em 0 a 1.

```
 DCG@k  = Σ (relevância_i / log2(i + 1))           i = 1..k
 nDCG@k = DCG@k / DCG_ideal@k                      (1,0 = ordenação perfeita)

 Relevâncias reais no top-4 devolvido: [1, 0, 2, 0]
 DCG  = 1/log2(2) + 0 + 2/log2(4) + 0 = 1 + 1 = 2,0
 Ideal (ordenado): [2, 1, 0, 0]
 IDCG = 2/log2(2) + 1/log2(3) = 2 + 0,63 = 2,63
 nDCG@4 = 2,0 / 2,63 ≈ 0,76
```

**Quando importa:** quando há relevância **graduada** e a **ordem** importa (por exemplo, para avaliar o reranker).

## Quando usar cada métrica

| Métrica | Pergunta que responde | Melhor para |
|---|---|---|
| **Hit rate@k** | "Ao menos um trecho útil entrou no top-k?" | Perguntas de resposta única; checagem rápida |
| **Recall@k** | "Peguei todas as evidências necessárias?" | Escolher k da busca inicial; perguntas multi-trecho |
| **Precision@k** | "Quanto do que entreguei é útil?" | Contexto final enxuto; custo de ruído |
| **MRR** | "O primeiro acerto está no topo?" | Respostas únicas; UX com poucos resultados |
| **nDCG@k** | "A ordem reflete a relevância (graduada)?" | Avaliar reranking e ordenação |

## Exemplo prático: calculando as métricas

```python
# Pseudocódigo didático — NÃO executado.
import math

def avaliar_retrieval(casos, buscar, k=5):
    # 'casos': lista de {"pergunta": str, "relevantes": {id: grau}}  (grau 1 ou 2 etc.)
    # 'buscar(pergunta, k)': devolve lista ORDENADA de ids de chunks.
    hits = recalls = precisions = rr_total = ndcg_total = 0.0

    for caso in casos:
        rel = caso["relevantes"]                         # dict id -> grau de relevância
        topk = buscar(caso["pergunta"], k)               # ids devolvidos, em ordem
        acertos = [i for i in topk if i in rel]          # relevantes presentes no top-k

        hits      += 1.0 if acertos else 0.0                         # hit@k
        recalls   += len(acertos) / len(rel)                         # recall@k
        precisions += len(acertos) / k                               # precision@k

        # MRR: 1 / posição do primeiro relevante (0 se não houver)
        pos = next((p for p, i in enumerate(topk, start=1) if i in rel), None)
        rr_total += 1.0 / pos if pos else 0.0

        # nDCG@k com relevância graduada
        dcg  = sum(rel.get(i, 0) / math.log2(p + 1) for p, i in enumerate(topk, start=1))
        ideal = sorted(rel.values(), reverse=True)[:k]                # melhor ordenação possível
        idcg = sum(g / math.log2(p + 1) for p, g in enumerate(ideal, start=1))
        ndcg_total += dcg / idcg if idcg else 0.0

    n = len(casos)
    return {"hit@k": hits/n, "recall@k": recalls/n, "precision@k": precisions/n,
            "MRR": rr_total/n, "nDCG@k": ndcg_total/n}
```

**Leitura:** o laço percorre cada pergunta; calcula os acertos do top-k; acumula cada métrica; ao final devolve as médias. Execute com **diferentes configurações** (chunking, modelo, híbrida, reranker, k) para comparar objetivamente.

## Como interpretar e usar na prática

| Sintoma | Interpretação | Ação provável |
|---|---|---|
| Recall@50 baixo | O trecho nem entra na lista de candidatos | Melhorar chunking, embedding, híbrida, query transformation |
| Recall@50 alto, mas recall@5 baixo | Está na lista, mas mal ordenado | Reranking |
| Precision@5 baixa | Muito ruído no contexto | Reranker, limiar, MMR, k menor |
| MRR baixo | O primeiro acerto vem tarde | Reranking, melhor modelo |
| Métricas ótimas, mas respostas ruins | O problema está na geração (ver 6.1.1.2) | Prompt, modelo, grounding |

### Comparar configurações com disciplina

1. Use o **mesmo conjunto de perguntas** e o mesmo gabarito.
2. Mude **uma variável por vez** (tamanho do chunk, modelo, ...).
3. Registre as métricas por configuração (planilha/ferramenta de experimentos).
4. Verifique **casos que pioraram** (não só a média).
5. Calcule intervalos de confiança ou repita com amostras maiores quando possível.

## Limitações das métricas

| Limitação | Explicação |
|---|---|
| **Depende do gabarito** | Rótulos incompletos penalizam o sistema por achar trechos válidos não rotulados |
| **Relevância ≠ utilidade para o LLM** | Um trecho "relevante" pode ser insuficiente ou confuso para gerar a resposta |
| **Granularidade** | Rotular por documento vs. por chunk muda os resultados; mudar o chunking exige remapear o gabarito |
| **Não mede a geração** | Nada diz sobre fidelidade ou correção da resposta |
| **Perguntas sem resposta** | Precisam de tratamento à parte (o ideal é não recuperar nada relevante) |
| **Amostra pequena** | Poucas perguntas geram métricas instáveis |

---

## Erros comuns e armadilhas

- **Medir só a resposta final** e não saber se o culpado é o retrieval.
- **Gabarito rotulado pelo próprio sistema** (circularidade), inflando os números.
- **Comparar métricas entre conjuntos de teste diferentes.**
- **Otimizar para a métrica e esquecer o usuário real** (conjunto de teste não representa as perguntas reais).
- **Alterar o chunking e comparar com o gabarito antigo** sem remapear os ids.
- **Usar apenas a média**, escondendo categorias de perguntas em que o sistema falha.
- **Ignorar perguntas sem resposta** no conjunto de teste.

## 🧩 Quiz de Fixação

1. Qual a diferença entre recall@k e precision@k e por que aumentar k costuma afetá-las em sentidos opostos?
2. O MRR de um sistema é 0,25. O que isso indica de forma aproximada?
3. Um RAG tem recall@50 alto, mas recall@5 baixo. Que diagnóstico e ação?

**Respostas:**
1) Recall@k é a fração dos relevantes encontrada no top-k (cobertura); precision@k é a fração do top-k que é relevante (pureza). Aumentar k tende a trazer mais relevantes (recall sobe) e também mais itens irrelevantes (precision cai).
2) Que, em média, o primeiro resultado relevante aparece por volta da 4ª posição (1/4), ou que muitas perguntas nem recuperam o relevante; o primeiro acerto vem tarde, sinalizando necessidade de melhorar ordenação (reranking) ou recall.
3) Os trechos corretos estão entre os 50 candidatos, mas mal ordenados; o problema é de ranking. A ação é adicionar ou melhorar o reranking (e/ou ajustar a ordenação), e depois entregar ao LLM só os poucos melhores.
