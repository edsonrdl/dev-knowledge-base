### Busca lexical vs semântica vs híbrida — onde cada uma acerta e onde falha

O **retrieval** é o coração do RAG, e existem duas formas fundamentais de buscar: pelas **palavras** (lexical) ou pelo **significado** (semântica/vetorial). Cada uma acerta onde a outra falha, e a **busca híbrida** combina as duas. Este arquivo compara as abordagens de forma conceitual; implementação de BM25 + vetorial com RRF está no AI Engineering.

## Busca lexical (esparsa): casar palavras

A busca lexical procura **termos** da consulta dentro dos documentos. O algoritmo clássico é o **BM25** (evolução do TF-IDF), usado por Elasticsearch, OpenSearch, Lucene, PostgreSQL full-text e outros.

**Ideia do BM25:** um documento é mais relevante se (a) contém os termos da consulta com frequência, (b) esses termos são **raros** na coleção (palavras raras pesam mais que "de", "o") e (c) o documento não é excessivamente longo.

```
 Consulta: "erro E-4021 impressora"
 Documento A: "...código de erro E-4021 na impressora fiscal..."   → contém os 3 termos, E-4021 é raríssimo → score ALTO
 Documento B: "...problemas com impressoras em geral..."          → contém só "impressora(s)" → score baixo
```

É chamada **esparsa** porque o documento vira um vetor enorme (um campo por palavra do vocabulário) quase todo zerado.

| Pontos fortes | Pontos fracos |
|---|---|
| Excelente para **termos exatos**: códigos, SKUs, siglas, nomes, números, identificadores | Não entende **sinônimos** ("carro" ≠ "automóvel") |
| Rápida, barata, madura e **explicável** (dá para ver por que casou) | Sensível a variações: plural, conjugação, erros de digitação (mitigável com stemming/fuzzy) |
| Não requer modelo de embedding nem GPU | Não captura a **intenção** da pergunta |
| Ótima para perguntas curtas com palavras-chave | Falha quando a pergunta e o documento usam vocabulários diferentes (vocabulary mismatch) |

## Busca semântica (densa): casar significados

A busca semântica compara **embeddings** (ver 2.2.2.1): pergunta e chunks viram vetores e os mais próximos são retornados. É chamada **densa** porque os vetores têm poucas centenas ou milhares de números, todos preenchidos.

```
 Consulta: "como recebo meu dinheiro de volta?"
 Chunk A: "Reembolso em até 14 dias corridos no app."     → sem palavras em comum, MAS mesmo significado → score ALTO
 Chunk B: "Frete grátis acima de R$ 200."                  → tema diferente → score baixo
```

| Pontos fortes | Pontos fracos |
|---|---|
| Entende **sinônimos, paráfrases** e intenção | Fraca com **termos exatos raros** (códigos, SKUs, nomes próprios) |
| Funciona entre idiomas (modelos multilíngues) | Pode trazer resultados "parecidos" porém **errados** (ex.: "pode" vs "não pode") |
| Boa para perguntas em linguagem natural e longas | Menos explicável ("por que esse chunk?") |
| Reduz o problema de vocabulário diferente | Depende da qualidade do modelo e do domínio; custo de embedding e índice |

## Comparação direta: quem acerta onde

| Tipo de consulta | Lexical | Semântica |
|---|---|---|
| "erro E-4021" (código exato) | ✅ Acerta | ❌ Pode falhar |
| "SKU 88-ABC" | ✅ | ❌ |
| "como recebo meu dinheiro de volta?" (paráfrase) | ❌ Pode falhar | ✅ Acerta |
| "carro" quando o texto diz "automóvel" | ❌ | ✅ |
| Nome próprio raro ("Dra. Albuquerque") | ✅ | ⚠️ Depende |
| Pergunta longa e descritiva | ⚠️ Ruidosa | ✅ |
| Pergunta de uma palavra ("reembolso") | ✅ | ✅ (ambas) |
| Termo técnico novo, ausente do treino do modelo | ✅ | ❌ Pode não entender |
| Negação ("não pode reembolsar") | ⚠️ | ⚠️ (ambas sofrem) |

## Busca híbrida: o melhor dos dois mundos

Na busca híbrida executam-se **as duas buscas** e **combinam-se os resultados** em um único ranking.

```
                     ┌────────────► BM25 (lexical)  ──► lista A ──┐
 Pergunta ──┤                                                       ├─► FUSÃO ─► ranking final ─► (reranker) ─► top-k
                     └────────────► Vetorial (densa) ──► lista B ──┘
```

### Como fundir as duas listas

| Método | Como funciona | Observação |
|---|---|---|
| **RRF (Reciprocal Rank Fusion)** | Soma `1/(c + posição)` de cada lista para cada documento | Usa só as **posições**, não os scores; simples e robusto (c costuma ser ~60) |
| **Combinação ponderada de scores** | `α·score_denso + (1-α)·score_lexical` (após normalizar) | Exige normalizar escalas diferentes; α precisa de ajuste |
| **Reranking posterior** | Une candidatos das duas buscas e um cross-encoder reordena | Mais caro e mais preciso (ver 3.2.2.1) |

### Exemplo de RRF

```python
# Pseudocódigo didático — NÃO executado.
def rrf(listas, c=60):
    # 'listas' é uma lista de rankings; cada ranking é uma lista de ids em ordem de relevância.
    scores = {}
    for ranking in listas:                          # percorre cada busca (lexical, vetorial)
        for posicao, doc_id in enumerate(ranking, start=1):   # posição 1 = melhor
            # Cada aparição contribui 1/(c+posição): posições altas valem mais.
            scores[doc_id] = scores.get(doc_id, 0) + 1.0 / (c + posicao)
    # Ordena do maior para o menor score somado.
    return sorted(scores, key=scores.get, reverse=True)

lexical = ["d7", "d2", "d9"]    # resultado do BM25
vetorial = ["d2", "d5", "d7"]   # resultado da busca por embeddings
print(rrf([lexical, vetorial]))  # d2 e d7 aparecem nas duas -> sobem no ranking final
```

**Por que funciona:** um documento bem posicionado **nas duas** listas é fortemente promovido; um que só uma busca viu ainda pode aparecer, mas mais abaixo. Isso protege contra as falhas isoladas de cada método.

## Quando usar cada uma

| Cenário | Recomendação |
|---|---|
| Base técnica com códigos, siglas, nomes de produtos | Híbrida (lexical essencial) |
| Perguntas em linguagem natural sobre políticas/conceitos | Semântica, de preferência híbrida |
| Protótipo rápido, base pequena | Semântica simples costuma bastar |
| Base de logs, identificadores, buscas por termo exato | Lexical |
| Jurídico/legislação (números de artigos + conceitos) | Híbrida + reranking |
| Idiomas misturados | Semântica multilíngue + lexical por idioma |
| Orçamento de infraestrutura mínimo | Lexical (BM25) como linha de base |

> [!tip] Linha de base
> Antes de investir em embeddings, rode um BM25 como **baseline** e meça. Em muitos domínios ele é surpreendentemente forte, e serve de referência para saber se a busca semântica realmente agrega.

---

## Erros comuns e armadilhas

- **Achar que "semântico" é sempre melhor.** Para códigos e termos exatos, o lexical vence.
- **Ignorar o tratamento de idioma no lexical** (stopwords, stemming, acentos em português): "reembolsar", "reembolso" e "reembolsos" podem não casar sem normalização.
- **Combinar scores sem normalizar** (BM25 e cosseno têm escalas diferentes), fazendo uma busca dominar a outra.
- **Fixar o peso da fusão sem medir** com perguntas reais.
- **Tratar híbrida como bala de prata:** ela melhora a *cobertura*, mas ainda é preciso reranking e avaliação.
- **Avaliar só com perguntas parafraseadas** (favorece semântica) ou só com palavras-chave (favorece lexical): o conjunto de teste deve refletir o uso real.

## 🧩 Quiz de Fixação

1. Dê um exemplo de consulta em que a busca lexical supera a semântica e outro em que ocorre o contrário.
2. Como funciona o RRF e por que ele dispensa normalizar scores?
3. Por que rodar um BM25 como baseline antes de adotar busca vetorial é uma boa prática?

**Respostas:**
1) Lexical vence em "erro E-4021" ou "SKU 88-ABC" (termos exatos raros). Semântica vence em "como recebo meu dinheiro de volta?" quando o documento diz "reembolso" (paráfrase/sinônimo sem palavras em comum).
2) O RRF soma, para cada documento, 1/(c + posição) em cada lista de resultados; documentos bem colocados em várias listas sobem. Como usa apenas as posições (ranks) e não os scores originais, não precisa normalizar escalas diferentes como as do BM25 e do cosseno.
3) Porque o BM25 é barato e forte em muitos domínios; ele mostra o patamar mínimo de qualidade e permite verificar objetivamente se a busca semântica (mais cara e complexa) realmente melhora os resultados nos seus dados.
