### 1.1.1.1. O que é AWS Migration Hub — hub central de migração, Home Region, ferramentas integradas, fases do Cloud Adoption Framework e quando usar

> [!warning] Aviso
> Os exemplos de CLI e configuração deste material são **ilustrativos e não foram executados**. O Migration Hub e os serviços ao redor dele evoluem rápido: algumas funcionalidades (Strategy Recommendations, Refactor Spaces, Orchestrator) tiveram mudanças de disponibilidade para novos clientes e foram parcialmente absorvidas por ofertas mais novas, como o AWS Transform. Antes de planejar uma migração real, confirme na documentação oficial o que está disponível na sua conta e região.

## 1. O problema que o Migration Hub resolve

Migrar um parque de servidores para a nuvem raramente é um projeto de uma ferramenta só. Uma empresa com 800 servidores, 120 aplicações e dezenas de bancos de dados usa uma ferramenta para descobrir o inventário, outra para replicar servidores, outra para migrar bancos, planilhas para acompanhar o andamento e reuniões semanais para saber "em que pé estamos". O resultado típico é que ninguém enxerga o todo: o time de infraestrutura sabe quais servidores foram replicados, o time de aplicação sabe quais sistemas já passaram no teste, e a gerência só descobre o atraso quando o prazo estoura.

O **AWS Migration Hub** é a resposta da AWS para essa fragmentação. Ele **não migra nada sozinho**. Ele é uma camada de **visibilidade, planejamento e acompanhamento** que se conecta às ferramentas que de fato fazem o trabalho pesado e consolida, em um único painel, o estado de cada servidor e de cada aplicação ao longo da jornada. Pense nele como o "quadro de controle de uma obra": os pedreiros (ferramentas de replicação) continuam trabalhando, mas o engenheiro-chefe vê num só lugar o que está pronto, o que está atrasado e o que depende de quê.

## 2. O que o Migration Hub é — e o que ele não é

| Pergunta | Resposta |
|---|---|
| Ele replica servidores? | Não. Quem replica é o **AWS Application Migration Service (MGN)**. |
| Ele migra bancos de dados? | Não. Quem migra é o **AWS Database Migration Service (DMS)**. |
| Ele descobre o que existe no datacenter? | Ele **consome** os dados do **Application Discovery Service**; a descoberta em si é feita por agentes/coletores. |
| Ele mostra o progresso consolidado? | Sim, é a sua função central. |
| Ele agrupa servidores em aplicações? | Sim, é possível definir aplicações e associar servidores a elas. |
| Ele recomenda estratégia de migração? | Por meio de recursos associados (Strategy Recommendations e Migration Evaluator), conforme disponibilidade. |
| Ele orquestra passos de migração? | Por meio do **Migration Hub Orchestrator**, com templates de workflow. |
| Tem custo próprio? | O uso do hub em si **não tem cobrança separada**; paga-se pelos recursos e ferramentas usados (replicação, instâncias de teste, etc.). |

A frase para memorizar: **Migration Hub é o painel; as outras ferramentas são os motores.**

## 3. Arquitetura conceitual

```
   DATACENTER / OUTRA NUVEM                          CONTA AWS (Home Region)
 ┌────────────────────────────┐                ┌──────────────────────────────┐
 │ Servidores físicos/VMs     │                │      AWS Migration Hub       │
 │  ├─ Discovery Agent        │──inventário──▶│  ┌────────────────────────┐  │
 │  └─ Agentless Collector    │                │  │ Servidores descobertos │  │
 │     (vCenter VMware)       │                │  │ Aplicações (grupos)    │  │
 └────────────────────────────┘                │  │ Status de migração     │  │
                                               │  └────────────────────────┘  │
 ┌────────────────────────────┐                │            ▲   ▲   ▲         │
 │ Replicação de servidores   │──status───────▶│            │   │   │         │
 │ (Application Migration Svc)│                │   MGN ─────┘   │   └── Orchestrator
 └────────────────────────────┘                │   DMS ─────────┘                │
 ┌────────────────────────────┐                │                              │
 │ Bancos de dados            │──status───────▶│   Strategy / Evaluator       │
 │ (Database Migration Svc)   │                │                              │
 └────────────────────────────┘                └──────────────────────────────┘
```

Os dados fluem **para** o hub: as ferramentas de migração reportam o status e o hub apenas consolida e exibe. Isso explica por que o hub precisa de uma **Home Region** (próxima seção) — todos os dados de rastreamento precisam morar num lugar só.

## 4. Home Region

Ao usar o Migration Hub pela primeira vez, você escolhe uma **Home Region**. Ela é a região onde ficam armazenados os dados de descoberta, planejamento e rastreamento de migração de **todas** as regiões. Pontos importantes:

- Os dados de migração podem estar sendo gerados em várias regiões de destino, mas o painel consolidado vive na Home Region.
- A escolha é pensada para ser feita **uma vez**; mudar de Home Region depois tem restrições, então a decisão deve ser tomada com antecedência.
- Ferramentas que reportam ao hub (MGN, DMS, Application Discovery Service) precisam ser configuradas para apontar para a Home Region correta.
- Nem todas as regiões podem ser Home Region; a lista é restrita e muda com o tempo.

> [!tip] Boas práticas
> Escolha como Home Region uma região estável e próxima da equipe de migração, não necessariamente a região de destino das cargas. Documente a decisão no projeto para evitar que outra pessoa configure uma ferramenta apontando para outra região.

Exemplo ilustrativo (não executado) de consulta da Home Region atual:

```bash
# Consulta a Home Region configurada para a conta
aws migrationhub-config get-home-region

# Define a Home Region (decisão normalmente única)
aws migrationhub-config create-home-region-control \
  --home-region us-west-2 \
  --target '{"Type":"ACCOUNT"}'
```

A API de configuração usa o endpoint do serviço `migrationhub-config`, que é global para a consulta da Home Region.

## 5. Ferramentas que se integram ao Migration Hub

| Ferramenta | Papel na jornada | O que reporta ao hub |
|---|---|---|
| **AWS Application Discovery Service** | Descoberta do inventário on-premises | Servidores, configuração, utilização, conexões de rede |
| **AWS Application Migration Service (MGN)** | Rehost (lift-and-shift) de servidores | Estado da replicação, testes, cutover |
| **AWS Database Migration Service (DMS)** | Migração de bancos de dados | Estado das tarefas de migração |
| **Migration Evaluator** | Business case e dimensionamento (TCO) | Estimativas de custo na AWS |
| **Migration Hub Strategy Recommendations** | Recomenda estratégia (7 Rs) por aplicação | Estratégia sugerida e justificativas |
| **Migration Hub Orchestrator** | Automatiza fluxos de migração com templates | Progresso de passos do workflow |
| **Migration Hub Refactor Spaces** | Refatoração incremental (strangler fig) | Ambientes, aplicações, serviços e rotas |
| Ferramentas de parceiros | Migrações específicas (ex.: ferramentas de terceiros) | Status via API de rastreamento |

O ponto-chave de integração é a **API de rastreamento** (Migration Hub APIs): qualquer ferramenta, inclusive de parceiros, pode registrar tarefas de migração associadas a um recurso e reportar seu progresso (`NOT_STARTED`, `IN_PROGRESS`, `COMPLETED`, `FAILED`...).

## 6. As fases de uma migração e onde o hub entra

A AWS organiza a jornada de adoção da nuvem em fases (inspiradas no **AWS Cloud Adoption Framework** e no **Migration Acceleration Program**): **Avaliar → Mobilizar → Migrar e modernizar**. O Migration Hub se encaixa principalmente nas duas últimas, mas o *Assess* alimenta tudo:

1. **Avaliar (Assess):** inventariar o parque, estimar custos, identificar dependências e decidir a estratégia. Ferramentas: Application Discovery Service, Migration Evaluator, Strategy Recommendations.
2. **Mobilizar (Mobilize):** preparar a landing zone (contas, rede, segurança, governança), treinar equipes, montar o plano de ondas. O hub guarda o plano e as aplicações agrupadas.
3. **Migrar e modernizar (Migrate & Modernize):** executar as ondas, acompanhando cada servidor e aplicação até o cutover; depois otimizar e refatorar. Ferramentas: MGN, DMS, Orchestrator, Refactor Spaces.

Uma **onda (wave)** é um grupo de aplicações migradas juntas numa janela. As primeiras ondas costumam ser de aplicações simples e de baixo risco, para a equipe aprender; as últimas incluem os sistemas críticos e complexos.

## 7. Quando usar o Migration Hub

Use quando:

- Há **muitos servidores e aplicações** (dezenas a milhares) e é preciso uma visão consolidada.
- A migração envolve **várias ferramentas** e equipes que precisam enxergar o mesmo status.
- Há necessidade de **governança de projeto**: relatórios para a gerência, marcos de ondas, auditoria do que foi migrado.
- Você quer **agrupar servidores em aplicações** e tratar a aplicação como unidade de migração.

Evite ou reduza o esforço quando:

- A migração é **pequena** (poucos servidores): uma planilha e o MGN direto podem bastar.
- O projeto é de **replataforma pontual** de um único banco: o DMS sozinho resolve, sem camada de acompanhamento.
- A carga **já nasce na nuvem**: não há o que migrar, apenas implantar.

## 8. Comparação com alternativas de organização

| Abordagem | Vantagem | Limite |
|---|---|---|
| Planilha/Jira manual | Zero custo, flexível | Desatualiza rápido, não integra com as ferramentas |
| Migration Hub | Status automático vindo das ferramentas AWS | Foco em ferramentas AWS e parceiros integrados |
| Ferramenta de terceiros (gestão de portfólio) | Cobre cenários multi-nuvem e governança ampla | Custo e integração próprios |
| Console de cada ferramenta (MGN, DMS) | Detalhe profundo | Sem visão consolidada |

## 9. Exemplo narrativo

Uma varejista tem 300 servidores em dois datacenters. A equipe instala o **Agentless Collector** no vCenter, coleta três semanas de utilização e importa os dados para o Migration Hub. No hub, agrupa os servidores em 45 aplicações (ex.: "Checkout", "Catálogo", "ERP financeiro"). Define quatro ondas. Na onda 1 (aplicações internas simples), os servidores são replicados pelo MGN; cada servidor aparece no hub com status de replicação, teste e cutover. Os bancos Oracle da onda 2 são migrados via DMS para Aurora PostgreSQL e o hub mostra o andamento das tarefas. O diretor de TI abre o hub toda segunda-feira e vê "12 aplicações migradas, 8 em andamento, 25 pendentes", sem pedir relatório a ninguém.

## 10. Erros comuns

> [!bug] Erros comuns
> 1. **Achar que o hub migra servidores.** Ele apenas acompanha; a replicação é do MGN e a de bancos é do DMS.
> 2. **Não definir a Home Region antes de configurar as ferramentas.** Resulta em dados de rastreamento espalhados ou ferramentas sem conseguir reportar.
> 3. **Escolher a Home Region apenas pela região de destino.** Ela é um ponto de consolidação; a região de destino das cargas pode ser outra.
> 4. **Pular a descoberta e agrupar aplicações "de cabeça".** Sem dados de dependência, a onda quebra quando um servidor esquecido deixa de responder.
> 5. **Usar o hub para uma migração minúscula.** O custo de configurar e manter o painel pode superar o benefício.
> 6. **Supor que todas as funcionalidades auxiliares continuam disponíveis para novos clientes.** Verifique a disponibilidade atual de Strategy Recommendations, Orchestrator e Refactor Spaces.
> 7. **Ignorar permissões entre contas.** Em organizações com várias contas, é preciso planejar quem consegue ver e escrever dados de migração.

## 11. Troubleshooting inicial

| Sintoma | Causa provável | Ação |
|---|---|---|
| Ferramenta não aparece no hub | Ferramenta configurada para outra região | Conferir a Home Region e reconfigurar |
| Painel vazio | Descoberta não importada | Verificar o Discovery Agent/Collector ou importar CSV |
| Servidor sem status | Tarefa de migração não associada ao recurso | Verificar integração da ferramenta com a API de rastreamento |
| Erro de acesso | Falta de permissão IAM `mgh:*` / `discovery:*` | Revisar políticas do usuário/perfil |
| Dados duplicados | Mesmo servidor descoberto por agente e por coletor | Reconciliar e arquivar um dos registros |

## 12. Resumo rápido

- Migration Hub = **painel de visibilidade e planejamento** da migração; não executa replicação.
- **Home Region** consolida todos os dados e deve ser escolhida com cuidado.
- Integra **Application Discovery Service, MGN, DMS** e ferramentas de planejamento e orquestração.
- Útil em migrações **grandes e multiferramenta**; excessivo em migrações pequenas.
- A jornada segue **Avaliar → Mobilizar → Migrar e modernizar**, organizada em **ondas**.

### 🧩 Quiz de Fixação

1. Qual a função principal do Migration Hub: replicar servidores ou consolidar o acompanhamento da migração?
2. O que é a Home Region e por que ela importa?
3. Cite três ferramentas que reportam status ao Migration Hub.
4. Em quais fases da jornada o hub é mais usado?
5. Quando o Migration Hub provavelmente não vale o esforço?
6. O uso do hub em si tem cobrança separada?
7. O que é uma onda de migração?

**Respostas:**

1. Consolidar o acompanhamento; a replicação é do MGN e a de bancos é do DMS.
2. É a região onde ficam os dados de descoberta e rastreamento de todas as regiões; todas as ferramentas precisam apontar para ela.
3. Application Discovery Service, Application Migration Service (MGN) e Database Migration Service (DMS), entre outras.
4. Principalmente Mobilizar e Migrar e modernizar, com a Avaliação alimentando o planejamento.
5. Em migrações muito pequenas ou de um único banco, onde o painel consolidado traz pouco valor.
6. Não; paga-se pelos recursos e ferramentas usados, não pelo hub em si.
7. Um grupo de aplicações migradas juntas numa mesma janela de tempo, normalmente organizado por complexidade e risco.
