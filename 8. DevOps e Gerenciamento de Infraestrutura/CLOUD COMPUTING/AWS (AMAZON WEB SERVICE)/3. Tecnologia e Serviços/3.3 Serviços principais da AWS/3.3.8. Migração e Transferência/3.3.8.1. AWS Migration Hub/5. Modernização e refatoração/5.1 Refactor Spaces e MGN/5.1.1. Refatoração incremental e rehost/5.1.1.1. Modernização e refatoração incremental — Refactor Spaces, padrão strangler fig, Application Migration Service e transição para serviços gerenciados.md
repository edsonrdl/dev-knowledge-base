### 5.1.1.1. Modernização e refatoração incremental — Refactor Spaces, padrão strangler fig, Application Migration Service e transição para serviços gerenciados

> [!warning] Aviso
> Os comandos, JSONs e diagramas abaixo são **ilustrativos e não foram executados**. O Migration Hub Refactor Spaces teve mudanças de disponibilidade para novos clientes e a AWS tem direcionado modernização para ofertas mais novas (como o AWS Transform). O **padrão** (strangler fig) permanece válido e pode ser implementado com Amazon API Gateway, Application Load Balancer e Route 53 diretamente. Confirme a situação atual na documentação oficial.

## 1. Migrar não é modernizar

Um **rehost** (lift-and-shift) leva a aplicação para a nuvem rapidamente, mas ela continua sendo o mesmo monólito em uma instância EC2. Os benefícios de elasticidade, resiliência e custo por uso só aparecem de verdade com **modernização**: quebrar o monólito, adotar serviços gerenciados, containers ou serverless. O problema: reescrever tudo de uma vez ("big bang") é arriscado, demorado e frequentemente falha.

A abordagem recomendada é a **refatoração incremental**: extrair funcionalidades do monólito **uma de cada vez**, mantendo a aplicação funcionando durante todo o processo.

## 2. Application Migration Service (MGN) — o primeiro passo

O **AWS Application Migration Service (MGN)** é a ferramenta principal de **rehost**. Ele substituiu o antigo AWS Server Migration Service (SMS) e o CloudEndure Migration. Como funciona:

```
Servidor de origem                      AWS
┌──────────────────┐   replicação    ┌───────────────────────────┐
│ Agente de        │──contínua─────▶│ Staging area (VPC)        │
│ replicação       │  (nível bloco)  │  ├─ Instâncias de replicação│
└──────────────────┘                 │  └─ Volumes EBS             │
                                     └─────────────┬─────────────┘
                                          teste ou │ cutover
                                                   ▼
                                     ┌───────────────────────────┐
                                     │ Instância EC2 de destino  │
                                     │ (via launch template)     │
                                     └───────────────────────────┘
```

Pontos-chave:

- Replicação **contínua em nível de bloco**, com baixo impacto e RPO de segundos a minutos.
- **Instâncias de teste** podem ser lançadas sem interromper a replicação.
- **Launch templates** definem o tipo de instância, sub-rede, security groups e tags de destino.
- **Pós-lançamento** (post-launch actions) executam automações via Systems Manager (instalar agentes, ajustar configurações).
- Suporta servidores físicos, VMs e outras nuvens.
- O custo é por **hora de servidor replicado** (com período gratuito por servidor em condições definidas pela AWS) mais o custo da área de staging.

```bash
# Inicializa o serviço na região de destino
aws mgn initialize-service --region us-east-1

# Lista servidores de origem replicando
aws mgn describe-source-servers --region us-east-1

# Inicia instância de teste para servidores específicos
aws mgn start-test --source-server-i-ds s-0123456789abcdef0 --region us-east-1

# Marca prontos para cutover e inicia o cutover
aws mgn start-cutover --source-server-i-ds s-0123456789abcdef0 --region us-east-1
```

(Os nomes exatos dos parâmetros devem ser conferidos na referência da CLI.)

## 3. Do rehost ao replatform: serviços gerenciados

Depois do rehost, é comum fazer **replatform** gradual, trocando componentes por serviços gerenciados sem reescrever a aplicação:

| Componente no servidor | Substituir por | Ganho |
|---|---|---|
| Banco MySQL/PostgreSQL/Oracle/SQL Server | **Amazon RDS / Aurora** (via DMS) | Backups, patches, Multi-AZ gerenciados |
| Fila RabbitMQ/ActiveMQ | **Amazon MQ** ou **SQS/SNS** | Menos operação |
| Cache Redis/Memcached | **ElastiCache** | Gerenciado e escalável |
| Servidor de arquivos | **Amazon FSx / EFS** | Compartilhamento gerenciado |
| Balanceador próprio | **ALB/NLB** | Alta disponibilidade integrada |
| Servidor web estático | **S3 + CloudFront** | Escala e custo menores |

Esse caminho é de **risco menor** que refatorar: troca-se a infraestrutura, mantém-se a lógica.

## 4. O padrão Strangler Fig

O nome vem da figueira estranguladora, que cresce em volta de uma árvore até substituí-la. Em software (Martin Fowler), significa **colocar uma fachada na frente do sistema legado e ir desviando rotas, uma a uma, para novos serviços**, até o legado não ter mais tráfego e poder ser desligado.

```
Fase 1: tudo no monólito
   Cliente ──▶ [ Fachada/Proxy ] ──▶ Monólito (todas as rotas)

Fase 2: extrai /catalogo
   Cliente ──▶ [ Fachada ] ──/catalogo──▶ Novo serviço (Lambda/ECS)
                           └─demais rotas─▶ Monólito

Fase 3: extrai /pagamentos
   Cliente ──▶ [ Fachada ] ──/catalogo────▶ Serviço Catálogo
                           ──/pagamentos──▶ Serviço Pagamentos
                           └─demais rotas─▶ Monólito (cada vez menor)

Fase N: monólito sem tráfego ──▶ desligado
```

Benefícios: **entregas pequenas e reversíveis**, o negócio continua operando, risco distribuído e aprendizado contínuo. É possível reverter uma rota desviada apenas atualizando a fachada.

## 5. Migration Hub Refactor Spaces

O **Refactor Spaces** automatizava a infraestrutura de rede e roteamento do strangler fig. Ele oferece o modelo:

| Conceito | Descrição |
|---|---|
| **Environment** | Ambiente que isola a rede (usa **AWS Transit Gateway**) e pode ser compartilhado entre contas via **AWS RAM** |
| **Application** | Fachada de roteamento; cria um **API Gateway** e um **Network Load Balancer** |
| **Service** | Destino de roteamento: um endpoint **URL** (monólito, qualquer HTTP acessível) ou uma **função Lambda** |
| **Route** | Regra que mapeia caminho (`/catalogo`) a um serviço; há rota padrão (`DEFAULT`) para o monólito e rotas **URI path** para novos serviços |

Fluxo de trabalho:

```
1. Cria Environment ─▶ 2. Cria Application (proxy) ─▶ 3. Registra o monólito como Service (URL)
   ─▶ 4. Cria rota DEFAULT para o monólito ─▶ 5. Cria novo Service (Lambda/URL)
   ─▶ 6. Cria rota /catalogo para o novo serviço ─▶ 7. Valida e repete
```

Comandos ilustrativos:

```bash
# Cria o ambiente de refatoração
aws migration-hub-refactor-spaces create-environment \
  --name amb-modernizacao --network-fabric-type TRANSIT_GATEWAY

# Cria a aplicação (fachada) numa VPC
aws migration-hub-refactor-spaces create-application \
  --name loja --environment-identifier env-0123456789 \
  --proxy-type API_GATEWAY --vpc-id vpc-0abc

# Registra o monólito como serviço (URL)
aws migration-hub-refactor-spaces create-service \
  --name monolito --application-identifier app-0123 \
  --environment-identifier env-0123 --endpoint-type URL \
  --url-endpoint Url=http://monolito.interno:8080 --vpc-id vpc-0abc

# Rota padrão para o monólito
aws migration-hub-refactor-spaces create-route \
  --application-identifier app-0123 --environment-identifier env-0123 \
  --service-identifier svc-monolito --route-type DEFAULT

# Rota de extração: /catalogo vai para um novo serviço Lambda
aws migration-hub-refactor-spaces create-route \
  --application-identifier app-0123 --environment-identifier env-0123 \
  --service-identifier svc-catalogo --route-type URI_PATH \
  --uri-path-route SourcePath=/catalogo,ActivationState=ACTIVE,IncludeChildPaths=true
```

> [!tip] Dica sem Refactor Spaces
> O mesmo desenho pode ser montado com **CloudFront ou API Gateway** na frente, **ALB com regras por caminho** (`/catalogo*` → target group novo) e **Route 53 ponderado** para desvio gradual. O padrão é independente do produto.

## 6. Estratégia de extração de serviços

Como escolher **o que extrair primeiro**:

1. **Funcionalidades com alta variação de carga** (se beneficiam de escala independente).
2. **Fronteiras claras** (poucas dependências do restante do monólito).
3. **Alto ritmo de mudança** (onde o time sofre mais com o acoplamento).
4. **Baixo risco** nas primeiras extrações, para aprender o processo.

Cuidados com **dados**: o maior desafio é o banco compartilhado. Estratégias:

- **Banco por serviço**, com sincronização (CDC via DMS, eventos via EventBridge/Kinesis) durante a transição.
- **Dual write cuidadoso** ou, melhor, **eventos** como fonte da verdade.
- **Anti-corruption layer** para traduzir o modelo do legado para o novo.

Alvos comuns de destino: **AWS Lambda** (lógica pontual), **Amazon ECS/EKS com Fargate** (serviços containerizados), **Aurora Serverless** e **DynamoDB** (dados), **SQS/SNS/EventBridge** (comunicação assíncrona).

## 7. Observabilidade durante a transição

Com tráfego dividido entre legado e novo, a observabilidade é essencial:

- **Métricas comparativas** (latência, erro, throughput) entre as duas rotas.
- **Tracing distribuído** (AWS X-Ray, OpenTelemetry) atravessando a fachada.
- **Canary/ponderação**: enviar 5% do tráfego ao novo serviço, observar, aumentar.
- **Feature flags** para ligar/desligar comportamentos.
- **Rollback instantâneo** pela fachada.

## 8. Quando modernizar e quando parar no rehost

| Situação | Recomendação |
|---|---|
| Datacenter fechando em 3 meses | Rehost com MGN primeiro, modernizar depois |
| Aplicação estável e pouco alterada | Rehost/Replatform; evitar reescrita |
| Aplicação estratégica com dor de escala | Refactor incremental com strangler fig |
| Mainframe/linguagem legada sem suporte | Avaliar Refactor/Replatform assistido (ferramentas de modernização) |
| Time sem competência cloud-native | Replatform + treinamento antes de refatorar |

## 9. Erros comuns

> [!bug] Erros comuns
> 1. **Big bang rewrite** em vez de extração incremental.
> 2. **Extrair serviços sem separar os dados**, criando um "monólito distribuído" com banco compartilhado.
> 3. **Esquecer a rota padrão** para o monólito e quebrar partes da aplicação.
> 4. **Ignorar a latência** entre o novo serviço e o banco/monólito.
> 5. **Não ter rollback** por rota.
> 6. **Modernizar por moda**, sem benefício de negócio mensurável.
> 7. **Subestimar a observabilidade**, ficando sem saber qual lado causou o problema.
> 8. **Planejar em torno do Refactor Spaces sem confirmar sua disponibilidade** para a sua conta.
> 9. **Deixar o MGN replicando servidores já migrados**, pagando por replicação desnecessária.

## 10. Troubleshooting

| Sintoma | Causa provável | Ação |
|---|---|---|
| Rota nova retorna 502/504 | Serviço de destino inacessível a partir da fachada | Conferir rede (Transit Gateway/VPC), SG e health |
| Tráfego ainda vai ao monólito | Rota não ativa ou precedência incorreta | Verificar `ActivationState` e o caminho |
| Replicação do MGN travada | Falha de rede ou disco cheio na área de staging | Verificar conectividade, agente e limites |
| Lançamento de teste falha | Launch template inválido | Revisar sub-rede, tipo de instância e permissões |
| Latência alta após extração | Chamadas síncronas entre serviço e monólito | Reduzir acoplamento ou usar cache/eventos |
| Dados inconsistentes | Sincronização entre bancos incompleta | Usar CDC e reconciliação |

## 11. Resumo rápido

- **MGN** faz rehost com replicação contínua, testes e cutover; é o primeiro passo comum.
- **Replatform** troca componentes por serviços gerenciados com risco baixo.
- **Strangler fig**: fachada na frente, desvio de rotas, legado "estrangulado" aos poucos.
- **Refactor Spaces** automatiza o padrão (Environment, Application, Service, Route), mas verifique a disponibilidade; o padrão também funciona com API Gateway/ALB/CloudFront.
- Separe **dados** e invista em **observabilidade** durante a transição.
