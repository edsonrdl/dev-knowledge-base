### 1.1.1.1. O que é AWS Elastic Disaster Recovery — replicação contínua em nível de bloco, RPO de segundos e RTO de minutos, estratégias de DR e quando usar em vez de Backup e Pilot Light

> [!warning] Aviso
> Valores de RPO/RTO, limites, preços, sistemas operacionais suportados, portas e nomes de recursos abaixo são **de memória e mudam**. **Confirme na documentação do AWS Elastic Disaster Recovery (DRS) e na página de preços.** Comandos e configurações são ilustrativos e **não foram executados**. RPO/RTO reais dependem de **volume de escrita, largura de banda e testes (drills)**: nunca prometa números sem medir.

## 1. O problema que o Elastic Disaster Recovery resolve

Desastres (falha de datacenter, ransomware, erro humano, falha de região) **acontecem**. As empresas definem dois números:

| Sigla | Significado | Pergunta |
|---|---|---|
| **RPO** (Recovery Point Objective) | **Quanto dado** posso perder | “Se cair agora, voltamos ao estado de quantos minutos atrás?” |
| **RTO** (Recovery Time Objective) | **Quanto tempo** posso ficar fora | “Em quanto tempo o serviço volta?” |

Soluções tradicionais de DR para servidores (físicos, VMs, EC2) têm problemas:

| Abordagem tradicional | Problema |
|---|---|
| **Site secundário completo** (duplicar datacenter) | **Custo altíssimo** de hardware parado |
| **Backups periódicos** | **RPO alto** (horas/dias) e **RTO alto** (restauração lenta) |
| **Replicação por software de terceiros** | **Licenças caras**, complexidade, manutenção |
| **Scripts de recriação** | Frágeis; sem teste regular |
| **DR “no papel”** | Ninguém testou; falha no dia |

O **AWS Elastic Disaster Recovery (DRS)** oferece **recuperação de desastres como serviço**: **replica continuamente** seus servidores (**qualquer origem**: on-premises, outras nuvens ou AWS) para a **AWS**, mantendo uma **área de staging de baixo custo**; na hora do desastre, **lança** servidores completos em **minutos**, com **RPO de segundos**.

> [!info] Em uma frase
> **DRS = replicação contínua, em nível de bloco, de servidores inteiros para uma área de staging barata na AWS, e lançamento rápido de instâncias EC2 completas quando necessário.**

## 2. Como funciona (visão geral)

```
 ORIGEM (on-prem / outra nuvem / AWS)                      AWS (região de destino)
┌────────────────────────────────┐   replicação contínua   ┌────────────────────────────────────────────┐
│ Servidor fonte                  │  (nível de bloco,       │  ÁREA DE STAGING (subnet, baixo custo)      │
│  + AWS Replication Agent        │──── TCP 1500 ─────────▶ │   Replication Server (EC2 pequena)          │
│  (Windows/Linux)                │   TLS, compressão       │   Volumes EBS de staging (baratos)          │
└────────────────────────────────┘                          │   Snapshots de ponto no tempo (EBS)         │
        │  controle: TCP 443 ─────▶ API do DRS               └─────────────────┬──────────────────────────┘
                                                                              │ DESASTRE ou DRILL: "Launch"
                                                                              ▼
                                                            ┌────────────────────────────────────────────┐
                                                            │  RECOVERY INSTANCES (EC2 completas)         │
                                                            │  via Conversion Server + Launch Template    │
                                                            └────────────────────────────────────────────┘
```

Fluxo em 5 passos:

1. **Instalar o agente** (AWS Replication Agent) em cada servidor de origem.
2. O DRS **cria a área de staging** (replication servers + volumes EBS).
3. **Replicação inicial** (cópia completa) e **contínua** (alterações de bloco em segundos).
4. **Drills** regulares: lançar instâncias de teste, validar, **descartar**.
5. **Failover real**: lançar instâncias de recuperação; **failback** quando a origem estiver pronta.

## 3. Conceitos fundamentais

| Termo | Significado |
|---|---|
| **Source server** | Servidor protegido (com o agente) |
| **AWS Replication Agent** | Software instalado no servidor de origem que **captura mudanças de bloco** e as envia |
| **Staging area** | Recursos de **baixo custo** na conta/região de destino (subnet de staging) que **recebem** a replicação |
| **Replication server** | Instância EC2 **pequena** (ex.: `t3.small`) que **recebe dados** do agente e **grava** em volumes EBS (atende vários servidores de origem) |
| **Staging EBS volumes** | Volumes de **baixo custo** que armazenam a réplica dos discos |
| **Point-in-time (PIT) snapshots** | **Snapshots** EBS gerados **periodicamente** para permitir recuperar **estados anteriores** (proteção contra corrupção/ransomware) |
| **Conversion server** | EC2 **temporária** usada **no lançamento** para **converter** o disco replicado em um boot EC2-compatível (drivers) |
| **Recovery instance** | **Instância EC2** lançada a partir da réplica |
| **Launch settings / launch template** | Configuração de **como** lançar (tipo de instância, rede, SG, tags, IAM) |
| **Drill** | **Teste** de recuperação **sem interromper** a origem |
| **Failover** | Transferir a carga para a AWS **em desastre real** |
| **Failback** | **Retornar** à origem (ou novo ambiente) depois do desastre |
| **Recovery job** | Execução de lançamento (drill ou recovery) |
| **Data replication state** | `Initial sync`, `Continuous`, `Lagging`, `Stalled`, `Disconnected`… |
| **Lag** | Defasagem entre origem e réplica (determina o **RPO efetivo**) |

## 4. Capacidades principais

| Capacidade | Detalhe (de memória — confirmar) |
|---|---|
| **RPO de segundos** | Replicação **contínua**, em nível de bloco |
| **RTO de minutos** | Lançamento de instâncias completas a partir da réplica (tipicamente **5–20 min**, dependente de tamanho/boot) |
| **Qualquer origem** | **Físico, VMware, Hyper-V, outras nuvens (Azure, GCP), e AWS** (cross-AZ/região) |
| **Sistemas operacionais** | **Windows Server** e **Linux** (distribuições e versões suportadas listadas na documentação) |
| **Aplicações** | Agnóstico: bancos, ERPs, SAP, SharePoint, servidores de arquivos… (nível de **disco**) |
| **Custo de staging baixo** | **Servidores de replicação pequenos** + **EBS econômico**; **sem pagar computação completa** até o desastre |
| **PIT recovery** | Escolher **ponto no tempo** (ex.: antes do ransomware); retenção configurável |
| **Drills sem impacto** | Testes frequentes **sem parar replicação nem a origem** |
| **Failback automatizado** | Retorno com **replicação reversa** (cenários suportados) |
| **Pós-lançamento** | **Ações pós-lançamento** (SSM) para configurar o ambiente recuperado |
| **Segurança** | **TLS** em trânsito; **EBS criptografado** (KMS) em staging |
| **Integrações** | EC2, EBS, VPC, IAM, KMS, CloudWatch, CloudTrail, SSM, Route 53 |

## 5. Estratégias de DR na AWS (contexto para a prova e arquitetura)

A AWS descreve **quatro estratégias** (do mais barato/lento ao mais caro/rápido):

| Estratégia | Descrição | RPO / RTO típico | Custo |
|---|---|---|---|
| **Backup and Restore** | Backups (AWS Backup, S3, snapshots) e **restauração** na hora | **Horas / horas–dias** | **Mais baixo** |
| **Pilot Light** | **Núcleo mínimo** (dados replicados, ex.: banco) pronto; **liga** o resto sob demanda | **Minutos–horas / dezenas de minutos–horas** | Baixo |
| **Warm Standby** | Versão **reduzida** do ambiente **rodando** (escalável) | **Segundos–minutos / minutos** | Médio |
| **Multi-site Active/Active** | Duas+ regiões **ativas** servindo tráfego | **~Zero / ~Zero** | **Mais alto** |

### 5.1 Onde o DRS se encaixa

O DRS implementa uma forma **moderna de Pilot Light**: **dados replicados continuamente**, **computação desligada** (só staging barato) e **recuperação em minutos**. Para **servidores** (lift-and-shift) sem arquitetura “cloud-native”, é a **opção prática** para RPO/RTO de **segundos/minutos** sem pagar um **warm standby** completo.

```
Custo/Velocidade →     Backup&Restore     DRS (pilot light de servidores)      Warm Standby        Active/Active
RPO                    horas              SEGUNDOS                             segundos            ~0
RTO                    horas              MINUTOS                              minutos             ~0
Custo em paz           $                  $$ (staging)                         $$$                 $$$$
```

## 6. Quando usar o DRS (e quando não)

| Cenário | DRS? |
|---|---|
| **Servidores on-premises** (VMs/físicos) que precisam de DR na AWS com **RPO de segundos** | **Sim** |
| **Servidores em outra nuvem** (Azure/GCP) → AWS como DR | **Sim** |
| **EC2** com DR **cross-região** (ou cross-AZ) **sem reescrever** | **Sim** |
| **Aplicação cloud-native** (serverless, RDS, DynamoDB) | **Não** (use recursos nativos: **Aurora Global Database**, **DynamoDB Global Tables**, **S3 CRR**, **Multi-AZ**, **Route 53/ARC**) |
| **Somente backup/retenção** (compliance, RPO horas) | **AWS Backup** (mais barato) |
| **Migração (cutover) de servidores para a AWS** | **AWS Application Migration Service (MGN)** (mesma tecnologia de replicação; propósito diferente) |
| **Banco de dados com RPO ~0** e failover automático | **Replicação nativa do banco** (Aurora, RDS Multi-AZ/cross-region, always-on) |
| **Zero downtime** exigido | **Active/Active** |
| **Dados de arquivo** (NAS) | **DataSync/FSx/Storage Gateway/Backup** conforme o caso |

> [!tip] DRS vs MGN
> O **MGN** (**Application Migration Service**) e o **DRS** compartilham a **mesma tecnologia de replicação** (herdada do **CloudEndure**). **MGN = migrar** (cutover e desligar a origem); **DRS = proteger** (replicar indefinidamente e lançar só em caso de desastre/drill).

### 6.1 DRS vs AWS Backup vs replicação de banco

| Critério | **DRS** | **AWS Backup** | **Replicação de banco/Aurora Global** |
|---|---|---|---|
| **Granularidade** | **Servidor inteiro** (discos) | Recurso (EBS, RDS, EFS…) | **Banco de dados** |
| **RPO** | **Segundos** | Minutos–horas (agendado) | **Segundos** |
| **RTO** | **Minutos** | Horas | Minutos |
| **Origem** | **On-prem/outras nuvens/AWS** | Principalmente AWS (e alguns on-prem) | AWS |
| **Custo em repouso** | Staging (médio-baixo) | Baixo | Médio–alto (réplica ligada) |
| **Retenção histórica** | PIT (dias) | **Longa** (anos), cofres, compliance | Limitada |
| **Melhor para** | **DR de servidores/lift-and-shift** | **Backup/retenção** | **DR de dados nativo** |

Os três são **complementares**: **Backup** para retenção/ransomware de longo prazo, **replicação nativa** para bancos críticos, **DRS** para servidores e aplicações legadas.

## 7. Casos de uso típicos

1. **Datacenter on-premises** com DR na AWS (substituir o site secundário).
2. **Aplicações legadas/ERPs** em VMs sem arquitetura moderna.
3. **Proteção contra ransomware** com **recuperação a um ponto anterior** (PIT).
4. **DR cross-região de EC2** (por exemplo, `us-east-1` → `us-west-2`) sem refatorar.
5. **Multicloud**: servidores no Azure/GCP com DR na AWS.
6. **Conformidade**: demonstrar **testes de DR** periódicos (drills) com evidências.
7. **Complemento de Warm Standby**: servidores específicos no **pilot light** e o resto em arquitetura mais cara.

## 8. Primeiros passos (visão geral, ilustrativo)

```bash
# 1) Inicializar o serviço na região de destino (cria roles, templates padrão)
aws drs initialize-service --region us-west-2

# 2) Instalar o agente no servidor de origem (Linux; ilustrativo — credenciais temporárias de instalação)
wget -O ./aws-replication-installer-init https://aws-elastic-disaster-recovery-us-west-2.s3.us-west-2.amazonaws.com/latest/linux/aws-replication-installer-init
chmod +x aws-replication-installer-init
sudo ./aws-replication-installer-init --region us-west-2 --aws-access-key-id <ID> --aws-secret-access-key <SEGREDO> --no-prompt

# 3) Acompanhar os servidores de origem e o estado da replicação
aws drs describe-source-servers --region us-west-2 \
  --query 'items[].[sourceServerID,dataReplicationInfo.dataReplicationState,dataReplicationInfo.lagDuration]'

# 4) Iniciar um drill (teste)
aws drs start-recovery --is-drill --source-servers sourceServerID=s-1234567890abcdef0 --region us-west-2
```

(As credenciais de instalação devem ser **temporárias/restritas**; nunca deixe chaves de longa duração em scripts.)

## 9. Erros comuns

- **Não fazer drills**: DR não testado **não é DR**.
- **Achar que DRS substitui backup** (retenção longa/compliance continuam exigindo AWS Backup).
- **Subestimar a largura de banda**: replicação inicial e taxa de escrita precisam caber no **link**.
- **Ignorar o lag**: com lag alto, o RPO real é pior que o prometido.
- **Usar DRS para arquitetura cloud-native** (existem soluções nativas melhores/mais baratas).
- **Não planejar rede de recuperação** (IPs, DNS, SGs, VPN) → servidores sobem, mas **ninguém acessa**.
- **Não planejar o failback**.
- **Esquecer licenciamento** (Windows/SQL/aplicações) nas instâncias recuperadas.
- **Servidores de staging sem monitoramento**.
- **Confundir DRS com MGN**.

## 10. Troubleshooting inicial

| Sintoma | Causas prováveis | Ações |
|---|---|---|
| Replicação em `Stalled`/`Disconnected` | Rede/firewall (443/1500); agente parado; credenciais | Verificar conectividade, serviço do agente, proxy |
| **Lag** crescendo | Banda insuficiente; taxa de escrita alta; throttling | Aumentar banda; ajustar throttling; mais replication servers |
| Drill não inicia/instância não boota | Conversão/drivers; launch template; AMI/OS | Ver logs do job e o console da instância; ajustar launch settings |
| Servidor recuperado sem rede | Subnet/SG/rota/DNS | Revisar launch settings e a rede de recuperação |
| Staging caro | Muitos volumes/PIT longo | Revisar retenção e discos replicados |
| Agente não instala | SO não suportado; pré-requisitos; permissões | Consultar a matriz de suporte |

## 11. Resumo rápido

- **DRS** = **replicação contínua em nível de bloco** de servidores (**qualquer origem**) para **staging barato** na AWS; **RPO de segundos**, **RTO de minutos**.
- **Peças**: **AWS Replication Agent**, **replication servers** (EC2 pequenas), **volumes EBS de staging**, **snapshots PIT**, **conversion server**, **launch templates**, **recovery instances**.
- **Ciclo**: instalar agente → replicar → **drills** → **failover** → **failback**.
- **Estratégia**: DRS ≈ **pilot light moderno de servidores**; entre **Backup & Restore** e **Warm Standby**.
- **Use** para **servidores/lift-and-shift/on-prem/multicloud**; **não** para cloud-native (Aurora Global, DynamoDB Global Tables, S3 CRR); **MGN** é para **migrar**, **Backup** para retenção.
- **Boas práticas**: **drills regulares**, medir **lag**, planejar **rede, licenças, DNS e failback**.

## 🧩 Quiz de Fixação

1. O que significam RPO e RTO?
2. Quais componentes formam a staging area do DRS?
3. Qual a diferença entre DRS e MGN?
4. Em que estratégia de DR o DRS se encaixa melhor?
5. Por que fazer drills regularmente?
6. O que é recuperação por point-in-time e para que serve?
7. Quando não usar o DRS?

**Respostas:**

1. RPO é a quantidade máxima de dados que se aceita perder (em tempo); RTO é o tempo máximo aceitável para restaurar o serviço.
2. Replication servers (EC2 pequenas), volumes EBS de staging e snapshots de ponto no tempo, em uma subnet de staging na região de destino.
3. O MGN migra servidores (cutover) para a AWS; o DRS protege servidores replicando-os continuamente para recuperação em desastre e lançando instâncias apenas quando necessário.
4. Pilot light moderno de servidores: dados replicados continuamente e computação desligada, com recuperação em minutos.
5. Para validar que a recuperação funciona (boot, rede, aplicação), medir RTO real e manter evidências sem interromper a origem.
6. Recuperar a réplica em um estado anterior (por snapshots PIT), útil contra corrupção ou ransomware.
7. Em aplicações cloud-native com recursos nativos de DR, quando só é preciso backup com retenção longa, para migração ou quando se exige zero downtime (active/active).
