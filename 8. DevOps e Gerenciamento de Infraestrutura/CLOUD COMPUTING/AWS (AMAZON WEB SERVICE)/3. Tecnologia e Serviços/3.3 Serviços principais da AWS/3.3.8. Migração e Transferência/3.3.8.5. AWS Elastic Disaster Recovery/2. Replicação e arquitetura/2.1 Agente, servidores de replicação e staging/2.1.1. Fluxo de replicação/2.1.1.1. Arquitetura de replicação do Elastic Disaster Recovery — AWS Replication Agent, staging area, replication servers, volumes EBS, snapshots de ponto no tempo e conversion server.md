### 2.1.1.1. Arquitetura de replicação do Elastic Disaster Recovery — AWS Replication Agent, staging area, replication servers, volumes EBS, snapshots de ponto no tempo e conversion server

> [!warning] Aviso
> Portas, tipos de instância dos replication servers, número de discos/servidores por replication server, tipos de volume de staging, comportamento de snapshots e limites abaixo são **de memória e mudam**. **Confirme na documentação do AWS Elastic Disaster Recovery (DRS).** Comandos e configurações são ilustrativos e **não foram executados**. Nomes, IDs e CIDRs são fictícios.

## 1. Visão geral da arquitetura

```
                                 CONTA/REGIÃO DE DESTINO (AWS)
 ORIGEM                       ┌───────────────────────────────────────────────────────────┐
┌────────────────┐            │  VPC (staging subnet — dedicada)                           │
│ Servidor fonte │  TCP 1500  │   ┌───────────────────────┐   ┌────────────────────────┐  │
│ + Replication  │───────────▶│   │ Replication Server    │──▶│ EBS staging volumes     │  │
│   Agent        │  (dados,   │   │ (EC2 pequena; recebe  │   │ (réplica dos discos)    │  │
│                │   TLS)     │   │  de N servidores)     │   │ + PIT snapshots (EBS)   │  │
└──────┬─────────┘            │   └───────────────────────┘   └────────────────────────┘  │
       │ TCP 443 (controle)   │            ▲                                                │
       └─────────────────────▶│  API do DRS / EC2 / EBS / S3 (regionais)                    │
                              └───────────────────────────────────────────────────────────┘
                                   Na hora do LAUNCH: Conversion Server + EC2 de recuperação (subnet de aplicação)
```

Cada peça tem um papel claro: **o agente captura**, o **replication server recebe e grava**, **EBS guarda**, **snapshots permitem voltar no tempo** e o **conversion server prepara o boot** no lançamento.

## 2. AWS Replication Agent

### 2.1 O que faz

| Função | Detalhe (de memória — confirmar) |
|---|---|
| **Captura** | Monitora **alterações em nível de bloco** nos **discos** do servidor (driver/filtro no kernel) |
| **Replicação inicial** | **Copia todos os blocos** dos discos para a staging area |
| **Replicação contínua** | Envia **cada alteração de bloco** assim que ocorre (**segundos de lag**) |
| **Compressão e criptografia** | Dados **comprimidos** e enviados por **TLS** |
| **Throttling** | **Limite de banda** configurável |
| **Metadados** | Informa **hardware, SO, rede e discos** ao DRS (usados em launch settings) |
| **Heartbeat** | Mantém conexão de controle (443) com o serviço |

### 2.2 Compatibilidade e requisitos

| Item | Detalhe (de memória — confirmar na matriz oficial) |
|---|---|
| **SO** | **Windows Server** (versões suportadas) e **Linux** (RHEL/CentOS/Rocky/Alma, Ubuntu, Debian, SUSE, Amazon Linux, Oracle Linux…; **kernels** específicos) |
| **Hipervisores/origens** | **VMware, Hyper-V, KVM, físicos**, **AWS (EC2)**, **Azure**, **GCP** e outros |
| **Pré-requisitos Linux** | Headers/devel do **kernel**, `gcc/make`, `wget`, etc. (para compilar o módulo) |
| **Pré-requisitos Windows** | **.NET** e permissões de administrador |
| **Espaço livre** | Pequeno espaço para o agente/bitmaps |
| **Discos** | Limites de **tamanho e quantidade** por servidor |
| **Reinício** | Em geral **sem reinício** (Linux/Windows modernos; confirmar) |
| **Impacto** | **CPU/IO** adicionais **baixos** (monitorar em servidores muito sensíveis) |

### 2.3 Instalação

```bash
# Linux (ilustrativo)
sudo ./aws-replication-installer-init --region us-west-2 \
     --aws-access-key-id <ID_TEMPORARIO> --aws-secret-access-key <SEGREDO> --no-prompt
# Opção para proxy/IP privado (via VPN/DX), seleção de discos:
#   --devices /dev/sda,/dev/sdb  --no-replication  --force-volumes  --tags Ambiente=prod
```

```powershell
# Windows (ilustrativo)
.\AwsReplicationWindowsInstaller.exe --region us-west-2 --aws-access-key-id <ID> --aws-secret-access-key <SEGREDO> --no-prompt
```

> [!tip] Instalação em escala
> Use **SSM Run Command/State Manager**, **Ansible**, **GPO/SCCM** ou imagens de VM com o agente para instalar em **dezenas/centenas** de servidores. As **credenciais de instalação** devem ser **temporárias** (STS) ou de um **usuário IAM dedicado com a política gerenciada** de instalação do agente.

### 2.4 Atualização e desinstalação

- O agente **se atualiza automaticamente** (configurável) a partir do serviço.
- **Desinstalar** para de replicar; **desconectar** o servidor no console **mantém/remove** recursos de staging conforme a ação.

## 3. Staging area

### 3.1 Conceito

A **staging area** é um conjunto de recursos **econômicos** na **conta e região de destino**, **dentro de uma subnet dedicada**, que **recebe** e **guarda** a réplica **sem custos de computação completa**.

| Recurso | Função | Custo |
|---|---|---|
| **Replication server** | EC2 **pequena** que **recebe** o tráfego dos agentes e **escreve** nos volumes | **Baixo** (poucas instâncias para muitos servidores) |
| **Volumes EBS de staging** | Réplica dos discos de cada origem | **Baixo** (tipos econômicos por padrão; confirmar `gp3/st1/sc1/standard`) |
| **Snapshots EBS (PIT)** | Pontos de recuperação | **Incremental** (cobrança por GB de snapshot) |
| **Security group de replicação** | Permite **1500** do agente e **443** | Sem custo |
| **EBS metadata** | Informações de blocos | Pequeno |

### 3.2 Subnet de staging

| Prática | Detalhe |
|---|---|
| **Dedicada** | **Não** compartilhar com workloads de produção |
| **Privada** (com NAT/VPC endpoints) ou **pública com IPs** | Depende de como os agentes chegam (internet, **VPN/Direct Connect**) |
| **IPs suficientes** | Cada replication server consome IPs |
| **VPC endpoints** | Para acesso privado a **EC2/EBS/S3/DRS/KMS** |
| **DNS/rotas** | Alcançável pelos agentes (via **VPN/DX** em cenários privados) |

## 4. Replication servers

### 4.1 Funcionamento

- Um **replication server** é uma **instância EC2** (padrão `t3.small`, configurável) gerenciada pelo DRS.
- Cada um **recebe a replicação** de **vários servidores de origem** (**limite de discos por replication server**, ex.: **~15–16 discos**; confirmar) e **grava** nos **volumes EBS** correspondentes.
- O DRS **cria automaticamente** replication servers adicionais conforme o **número de discos/servidores**.
- **Escala**: mais origens → mais replication servers (custo cresce em degraus).

### 4.2 Dimensionamento

| Fator | Efeito |
|---|---|
| **Número de discos replicados** | Define a quantidade de replication servers |
| **Taxa de escrita agregada** | **CPU/rede** do replication server pode limitar; **tipo de instância maior** (`m5/c5`) ajuda |
| **Replicação inicial simultânea** | Muitos servidores iniciando juntos **saturam** banda/EBS: **escalone** |
| **Rede do replication server** | Tipos com **melhor rede** para altas taxas |
| **Tipo de volume de staging** | **Throughput/IOPS** adequados ao ritmo de escrita (volumes muito econômicos podem causar **lag**) |

### 4.3 Configurações de replicação (por servidor, com template padrão)

| Configuração | Opções |
|---|---|
| **Staging area subnet** | Subnet de destino da replicação |
| **Replication server instance type** | Padrão `t3.small` ou maior |
| **EBS volume type (staging)** | `GP3`, `GP2`, `ST1`, `SC1`, `Standard`… (**ou automático**) |
| **EBS encryption** | **Padrão** (`aws/ebs`) ou **KMS CMK** |
| **Use dedicated replication server** | Servidor **exclusivo** para fontes de alto throughput |
| **Bandwidth throttling** | Limite em **Mbps** por origem |
| **Data routing/private IP** | **IP privado** (VPN/DX) vs público |
| **Create public IP** | Para replication servers (se agentes usarem a internet) |
| **Point-in-time retention** | **Dias** de snapshots mantidos |
| **Tags** | Para alocação de custos/governança |

```bash
aws drs update-replication-configuration --source-server-id s-1234567890abcdef0 --region us-west-2 \
  --staging-area-subnet-id subnet-0stg1 --replication-server-instance-type m5.large \
  --default-large-staging-disk-type GP3 --use-dedicated-replication-server false \
  --bandwidth-throttling 0 --data-plane-routing PRIVATE_IP --create-public-ip false \
  --ebs-encryption CUSTOM --ebs-encryption-key-arn arn:aws:kms:us-west-2:123456789012:key/<id> \
  --pit-policy '[{"enabled":true,"interval":10,"retentionDuration":60,"units":"MINUTE","ruleID":1},{"enabled":true,"interval":1,"retentionDuration":7,"units":"DAY","ruleID":2}]'
```

(O formato/nomes de parâmetros devem ser confirmados na CLI atual.)

## 5. Fases da replicação

```
[Agente instalado] ─▶ Initiating ─▶ Initial sync (cópia completa) ─▶ Rescan (ocasional) ─▶ Continuous (CDP)
                                         │                                                   │
                                  Lag alto = Lagging / Stalled                         RPO ≈ lag (segundos)
```

| Estado (de memória — confirmar) | Significado |
|---|---|
| **Not started / Pending** | Aguardando início |
| **Initiating** | Preparando a replicação |
| **Initial sync** | Copiando **todos** os blocos (pode levar horas/dias conforme volume e banda) |
| **Rescan** | **Reescaneando** discos (por exemplo, após reinício/perda de rastreio de mudanças) |
| **Continuous** | **Replicação contínua saudável** (pronto para recuperar com RPO de segundos) |
| **Lagging** | Atraso crescente (banda, escrita, throttling) |
| **Stalled** | Sem progresso (rede/agente/credenciais) |
| **Disconnected** | Agente sem comunicação |
| **Paused/Stopped** | Replicação pausada por você |

### 5.1 O que “pronto para recuperar” exige

- **Estado `Continuous`** (ou próximo) e **lag baixo**;
- **Launch settings** válidos;
- **Pelo menos um ponto de recuperação** (snapshot) disponível;
- **Drill recente** com sucesso (boa prática).

## 6. Pontos de recuperação (PIT snapshots)

| Aspecto | Detalhe (de memória — confirmar) |
|---|---|
| **O que são** | **Snapshots EBS** dos volumes de staging, **coordenados** por servidor, que representam **estados consistentes** (em nível de crash/bloco) |
| **Política (PIT policy)** | Regras como: **a cada 10 minutos por 1 hora**, **a cada hora por 24 horas**, **diário por 7–35 dias**… (**retenção até ~365 dias** configurável; **padrão ~7 dias**) |
| **Uso** | **Recuperar** para um **ponto específico** (antes de corrupção/ransomware/erro) |
| **Custo** | **Snapshots incrementais** (GB-mês); retenção longa aumenta o custo |
| **Último estado** | Opção “**mais recente**” (estado atual da réplica) |
| **Consistência** | **Crash-consistent** (como após uma queda de energia); aplicações com **journal** (bancos) recuperam; para **application-consistency** use **pré/pós-scripts** do lado da origem (quando necessário) |

```bash
aws drs describe-recovery-snapshots --source-server-id s-1234567890abcdef0 --region us-west-2 \
  --query 'items[].[snapshotID,timestamp,expectedTimestamp]'
```

## 7. Conversion server

### 7.1 Por que existe

Os discos replicados vêm de **qualquer origem** (VMware, físico, Azure…), mas a **EC2** exige **drivers e configurações de boot específicos** (ENA/NVMe/AWS PV, Hyper-V). No **lançamento**, o DRS:

```
Snapshot (PIT escolhido) ──▶ volumes temporários ──▶ CONVERSION SERVER (EC2 temporária)
        └─ instala drivers, ajusta bootloader/fstab/rede ──▶ volumes convertidos ──▶ EC2 RECOVERY INSTANCE
```

| Aspecto | Detalhe |
|---|---|
| **Quando** | **A cada launch** (drill ou recovery) |
| **Duração** | **Minutos** (contribui ao RTO) |
| **Custo** | **Temporário** (alguns minutos de EC2) |
| **Falhas** | SO/kernel **não suportado**, drivers, discos grandes/complexos → job falha |

### 7.2 RTO: composição

```
RTO ≈ tempo de decisão/automação + (launch do job) + conversão (conversion server) + boot da EC2
      + pós-lançamento (SSM) + validação + DNS/roteamento
```

Em geral, **dezenas de minutos** para cargas típicas; **medir nos drills**.

## 8. Rede de replicação

### 8.1 Portas e caminhos

| Porta/Destino | Função |
|---|---|
| **TCP 443** | Agente → **API do DRS** e serviços AWS (controle, metadados) |
| **TCP 1500** | Agente → **replication server** (**dados**) |
| **TCP 443** (replication server) | Replication server → **APIs** (EC2/EBS/S3/DRS) |
| **Opcional: S3 (endpoint)** | Para baixar componentes/instalador |

### 8.2 Opções de conectividade

| Opção | Característica |
|---|---|
| **Internet pública** | Simples; dados criptografados (TLS); **sujeito à latência/variação** |
| **VPN site-to-site** | Privado, criptografado; limitações de **throughput** |
| **Direct Connect** | **Alta banda e previsibilidade**; recomendado para **muitos TB** e **RPO baixo** |
| **Replicação privada** (`data-plane-routing=PRIVATE_IP`) | O tráfego usa **IPs privados** (via VPN/DX) e VPC endpoints |
| **Proxy** | Suporte a proxy para o tráfego de controle (confirmar) |

### 8.3 Dimensionamento de banda

```
Largura de banda necessária ≳ taxa média de escrita do servidor (compressão ajuda) + folga
Replicação inicial: volume total / banda efetiva  (ex.: 5 TB em 500 Mbps ≈ 22 h)
Picos de escrita > banda ⇒ lag cresce ⇒ RPO piora
```

Medidas: **medir a taxa de escrita** (iostat/contadores) **antes**; **escalonar** a replicação inicial; **throttling** para não saturar o link de produção; **QoS**.

## 9. Fluxo de dados completo

```
Escrita no disco da origem ─▶ Agente captura o bloco alterado ─▶ Compressão + TLS ─▶ Replication Server (1500)
   ─▶ Grava no volume EBS de staging ─▶ PIT snapshot periódico ─▶ (drill/recovery) conversion + launch
```

## 10. Boas práticas de arquitetura

1. **Subnet de staging dedicada**, com **SGs** mínimos e **endpoints privados** quando possível.
2. **Direct Connect/VPN redundante** para ambientes grandes.
3. **Medir** taxa de escrita e **dimensionar banda** e replication servers.
4. **Escalonar** a replicação inicial (ondas).
5. **Política PIT** alinhada ao risco (ransomware ⇒ retenção maior) e **custo**.
6. **Tipo de volume de staging** adequado (evitar HDD muito lento em alta escrita).
7. **Replication server dedicado** para **fontes críticas** de alto throughput.
8. **Criptografia com CMK** quando exigido; **tags** em tudo.
9. **IaC** para configurações reproduzíveis (templates de replicação/launch).
10. **Monitorar lag e estados** continuamente.

## 11. Erros comuns

- **Banda subdimensionada** → `Lagging` crônico.
- **Iniciar centenas de servidores ao mesmo tempo**.
- **Portas 443/1500 bloqueadas** por firewall/proxy.
- **Staging em subnet compartilhada** (conflitos/segurança).
- **Volumes de staging lentos** (lag).
- **PIT policy curta demais** (sem ponto anterior ao incidente).
- **Agente desatualizado** com kernel novo (compatibilidade).
- **Ignorar reinícios** que disparam **rescan** longo.
- **Credenciais de instalação** de longa duração expostas.
- **Sem tags**: custos de staging sem dono.

## 12. Troubleshooting

| Sintoma | Causa provável | Ação |
|---|---|---|
| `Stalled` após instalar | 443/1500 bloqueadas; DNS; proxy | Testar conectividade ao endpoint regional e ao replication server |
| `Lagging` | Banda/escrita/volume de staging/throttling | Aumentar banda; reduzir throttling; volume mais rápido; dedicated server |
| **Rescan** frequente | Reinícios/falhas; mudanças de kernel | Estabilizar; atualizar o agente |
| Agente não instala no Linux | Faltam kernel headers/gcc | Instalar dependências do kernel |
| Replication server sobrecarregado | Muitos discos/escrita | Tipo maior; dedicated servers |
| Falta de pontos de recuperação | PIT desabilitado/curto | Ajustar a PIT policy |
| Custo de staging alto | Muitos volumes/retenção/snapshots | Revisar discos replicados e a retenção |
| Servidor “Disconnected” | Agente parado/rede/credenciais | Reiniciar o serviço; verificar a rede |

## 13. Resumo rápido

- **Arquitetura**: **Agente (origem)** → **TCP 1500 (dados, TLS)** → **Replication Server (EC2 pequena)** → **volumes EBS de staging** + **snapshots PIT**; **controle** por **TCP 443**.
- **Agente**: captura **blocos**, replicação **inicial** + **contínua**, compressão, **throttling**; suporta **Windows/Linux**, **físicos/VMs/outras nuvens/AWS**.
- **Staging**: **subnet dedicada**, replication servers (escalam por discos), **EBS econômico**; **snapshots incrementais**.
- **Estados**: `Initial sync` → **`Continuous`**; atenção a `Lagging/Stalled/Disconnected`; **lag = RPO efetivo**.
- **PIT**: políticas (ex.: 10 min → hora → dia), retenção até ~**365 dias**, **crash-consistent**.
- **Conversion server**: converte o boot para EC2 **a cada launch** (parte do **RTO**).
- **Rede**: **Direct Connect/VPN** para volume e previsibilidade; dimensionar banda pela **taxa de escrita**.

**Respostas:**

1. Capturar as alterações em nível de bloco nos discos do servidor de origem e enviá-las (comprimidas e criptografadas) à staging area, na replicação inicial e contínua.
2. Recebe os dados dos agentes e grava nos volumes EBS de staging; escala em degraus conforme o número de discos/servidores replicados, com possibilidade de servidores dedicados.
3. Snapshots EBS periódicos dos volumes de staging que permitem recuperar a um ponto anterior no tempo, útil contra corrupção ou ransomware.
4. Para converter os discos replicados (de qualquer origem) em um boot compatível com EC2, instalando drivers e ajustando o bootloader, a cada lançamento.
5. TCP 443 para controle/API (agente e replication server) e TCP 1500 para o tráfego de replicação de dados do agente ao replication server.
6. A defasagem entre a origem e a réplica, que determina o RPO efetivo naquele momento.
7. Escalonar em ondas para não saturar a banda e medir/dimensionar a banda e os replication servers (inclusive com throttling) antes de iniciar.
