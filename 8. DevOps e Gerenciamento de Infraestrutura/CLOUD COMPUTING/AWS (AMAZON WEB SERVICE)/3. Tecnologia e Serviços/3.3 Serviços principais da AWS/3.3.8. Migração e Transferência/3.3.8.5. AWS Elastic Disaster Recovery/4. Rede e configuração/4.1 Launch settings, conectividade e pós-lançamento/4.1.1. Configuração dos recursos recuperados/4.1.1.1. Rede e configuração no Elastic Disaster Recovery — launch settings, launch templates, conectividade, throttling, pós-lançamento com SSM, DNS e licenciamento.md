### 4.1.1.1. Rede e configuração no Elastic Disaster Recovery — launch settings, launch templates, conectividade, throttling, pós-lançamento com SSM, DNS e licenciamento

> [!warning] Aviso
> Campos de launch settings, comportamento de templates, ações pós-lançamento padrão, opções de licenciamento e nomes de parâmetros abaixo são **de memória e mudam**. **Confirme na documentação do AWS Elastic Disaster Recovery e do EC2 Launch Templates.** Templates, comandos e scripts são ilustrativos e **não foram executados**. IPs, CIDRs, IDs e nomes de domínio são fictícios. Erros de **rede de recuperação** são a principal razão pela qual “o servidor subiu, mas ninguém acessa”.

## 1. O que “configurar a recuperação” significa

A **replicação** guarda os discos; a **configuração de lançamento** define **como** o servidor **volta a viver** na AWS. Sem boa configuração, o **RTO** explode (instância sem rede, IP errado, DNS apontando para o lugar antigo, licença sem ativar).

```
Réplica (discos) + LAUNCH SETTINGS (instância, rede, disco, tags, IAM) + PÓS-LANÇAMENTO (SO/app/DNS) = servidor funcional
```

Três camadas de configuração:

| Camada | O que define |
|---|---|
| **Launch settings (DRS)** | Comportamento geral: **copiar** tags/IP privado, **right-sizing**, **licenciamento**, **boot mode**, **pós-lançamento** |
| **EC2 launch template** | **Tipo de instância, subnet, SGs, IAM profile, discos, tags**, placement |
| **Pós-lançamento (SSM)** | **Scripts/automação** após o boot (hostname, serviços, montagens, registro no DNS) |

## 2. Launch settings do DRS

### 2.1 Principais opções (de memória — confirmar)

| Opção | Efeito |
|---|---|
| **Instance type right-sizing** | **Dimensionar automaticamente** o tipo de instância a partir de **CPU/RAM** da origem (`NONE`, `BASIC`, `IN_AWS` — confirmar valores) |
| **Copy private IP** | Tenta **manter o IP privado** da origem na recuperação (útil se a subnet de recuperação tem o **mesmo CIDR**) |
| **Copy tags** | Copia **tags** da origem para a instância |
| **Transfer server tags** | Aplica **tags do servidor de origem** |
| **Licensing (BYOL/AWS)** | **Usar licença da AWS** (Windows incluído) ou **BYOL** (**License Manager**) |
| **Launch disposition** | **Iniciar a instância** (`STARTED`) ou deixá-la **parada** (`STOPPED`) após o lançamento |
| **Boot mode** | **Legacy BIOS** ou **UEFI** (de acordo com a origem; **detecção automática** em versões recentes) |
| **Target instance type right sizing method** | Método de escolha do tipo |
| **Post-launch actions** | Habilitar **ações padrão** (instalar **SSM Agent**, **CloudWatch Agent**, **mudar hostname**, etc.) e **personalizadas** |

```bash
aws drs update-launch-configuration --source-server-id s-1234567890abcdef0 --region us-west-2 \
  --target-instance-type-right-sizing-method BASIC \
  --copy-private-ip true --copy-tags true \
  --launch-disposition STARTED \
  --licensing osByol=false
```

### 2.2 Launch template do EC2

O DRS cria e **mantém** um **EC2 Launch Template** por servidor de origem (e um **template padrão** para novos servidores). Nele você ajusta:

| Parâmetro | Dicas |
|---|---|
| **Instance type** | Preferir **geração atual** (`m6i/m7g`…), **compatível com o SO** (cuidado: ARM vs x86) |
| **Subnet** (rede de recuperação) | Subnet **na VPC de recuperação**; **AZ** adequada |
| **Security groups** | **Mínimos** necessários; **espelhar** regras de produção |
| **IAM instance profile** | **SSM** (gerenciamento), **CloudWatch**, S3 de scripts |
| **Key pair** | Acesso de emergência (ou preferir **SSM Session Manager**) |
| **EBS (tipo/IOPS/criptografia)** | `gp3` por padrão; **KMS** da região de recuperação |
| **Placement/Tenancy** | **Dedicated Hosts** (BYOL), placement groups |
| **Tags** | `Ambiente=DR`, `Aplicacao=...`, `CentroCusto=...` |
| **Network interfaces** | **IP privado** fixo (se for copiar o IP), ENIs múltiplas |
| **User data** | Cuidado: o DRS controla o boot; use **pós-lançamento** para customizações |
| **Metadata options** | **IMDSv2 obrigatório** |

> [!tip] Versionamento do template
> Os launch templates têm **versões**. Defina a **versão padrão** e **documente mudanças** (IaC). O DRS usa a **versão “default”**: **alterar o template** altera **todos os próximos lançamentos**.

## 3. A rede de recuperação (VPC de DR)

### 3.1 Princípios

| Princípio | Detalhe |
|---|---|
| **Pré-provisionar** | **VPC, subnets, route tables, SGs, NACLs, endpoints** **antes** do desastre (**IaC**) — criar durante o incidente é lento e arriscado |
| **Espelhar produção** | Mesmos **segmentos** (web/app/db), **regras de SG**, **DNS** equivalentes |
| **CIDRs** | Planejar para **evitar sobreposição** com a rede de produção (para **drills**) e **permitir IPs idênticos** (para **failover**) |
| **Conectividade** | **VPN/Direct Connect/Transit Gateway** para usuários e sistemas que precisam alcançar o ambiente recuperado |
| **Saída para a internet** | **NAT/Network Firewall** conforme política |
| **Serviços de suporte** | **AD/DNS**, **NTP**, **monitoramento**, **bastion/SSM**, **bancos gerenciados** replicados |
| **Segmentação drill vs real** | **Duas subnets/VPCs**: **teste** (isolada) e **recuperação** (conectada à produção alternativa) |

### 3.2 IP privado: manter ou mudar?

| Estratégia | Vantagens | Desvantagens |
|---|---|---|
| **Manter o IP** (`copy private IP`) | **Menos mudanças** em aplicações/configurações/firewalls | Exige **mesmo CIDR** na subnet de recuperação; **conflitos** em drills com rota para produção |
| **Novo IP + DNS** | **Flexível**; evita conflitos | **Dependências em IP** (hardcoded, licenças por IP, ACLs) precisam ser tratadas |
| **Híbrido** | IPs críticos mantidos; resto via DNS | Mais **planejamento** |

Boa prática: **depender de DNS (nomes)**, **não de IPs**; **reduzir TTL** dos registros críticos **antes** do desastre (via pré-configuração) para acelerar o cutover.

### 3.3 Segurança de rede na recuperação

- **Mesmas políticas** de segmentação da produção; **SGs referenciando SGs**.
- **Sem IP público** salvo necessidade; acesso por **ALB/CloudFront/VPN**.
- **Network Firewall/WAF** replicados.
- **Logs** (**VPC Flow Logs**, **CloudTrail**, **CloudWatch**) ativos desde o primeiro minuto.
- **Chaves KMS** e **secrets** disponíveis **na região de recuperação**.

## 4. Conectividade de replicação (origem → AWS)

### 4.1 Opções e recomendações

| Cenário | Recomendação |
|---|---|
| **Poucos servidores, baixo volume** | Internet (TLS) com **throttling** |
| **Dezenas de servidores / TB** | **VPN** redundante ou **Direct Connect** |
| **Centenas de servidores/muitos TB/baixo RPO** | **Direct Connect** (várias conexões/LAG), **MACsec** opcional |
| **Ambientes sem saída direta** | **Proxy** para controle; **replicação privada** via VPN/DX |
| **Multi-site** | Cada site com **link próprio** e **janelas** de replicação |

### 4.2 Throttling (limite de banda)

| Aspecto | Detalhe |
|---|---|
| **Onde** | **Por servidor de origem** (configuração de replicação) |
| **Para quê** | **Proteger o link de produção** (não saturar o tráfego de negócio) |
| **Impacto** | **Throttling excessivo** ⇒ **lag** ⇒ **RPO pior** |
| **Horários** | Pode-se ajustar **por janela** (via automação: mais banda à noite) |
| **Medição** | Acompanhe **lag** e **taxa de escrita**; ajuste |

```bash
# Definir limite de 200 Mbps para um servidor (ilustrativo)
aws drs update-replication-configuration --source-server-id s-1234567890abcdef0 --region us-west-2 \
  --bandwidth-throttling 200
```

## 5. Ações pós-lançamento (post-launch actions)

### 5.1 O que são

Automação que roda **após o boot** da instância recuperada, usando o **Systems Manager** (**SSM Agent** é pré-requisito). Existem **ações padrão** do DRS e **ações customizadas** (documentos SSM).

| Ação (exemplos; confirmar) | Uso |
|---|---|
| **Instalar SSM Agent** | Gerenciamento e execução das demais ações |
| **Instalar CloudWatch Agent / Inspector Agent** | Observabilidade e segurança |
| **Mudar hostname / reconfigurar rede / DNS** | Ajustar identidade da máquina |
| **Remover drivers/agents do hipervisor antigo** (VMware Tools, etc.) | Limpeza |
| **Instalar o agente de backup/segurança/AV** | Conformidade |
| **Ingressar no domínio / registrar no DNS** | Integração com **AD/DNS** |
| **Executar scripts customizados** | Montagens, serviços, health checks, notificações |
| **Atualizar parâmetros de aplicação** | Strings de conexão, flags de ambiente |

### 5.2 Exemplo de documento SSM (ilustrativo)

```yaml
schemaVersion: '2.2'
description: Pos-lancamento DR - ajustar aplicacao e DNS
parameters:
  Ambiente: { type: String, default: DR }
mainSteps:
  - action: aws:runShellScript
    name: ajustarAplicacao
    inputs:
      runCommand:
        - sed -i 's/^AMBIENTE=.*/AMBIENTE={{ Ambiente }}/' /etc/app/app.env
        - systemctl restart app.service
        - curl -fsS http://localhost:8080/health || exit 1
  - action: aws:runShellScript
    name: registrarDNS
    inputs:
      runCommand:
        - /opt/dr/registrar-dns.sh pedidos.corp.example.com
```

### 5.3 Boas práticas de pós-lançamento

1. **Idempotente**: executar duas vezes não pode quebrar.
2. **Falhar de forma clara** (código de saída ≠ 0) e **notificar**.
3. **Ordem**: dependências antes (AD/DNS → banco → app).
4. **Sem segredos em texto**: usar **Secrets Manager/Parameter Store** (SecureString).
5. **Timeouts** e **health checks** ao final.
6. **Versionar** os documentos (Git) e **testar em drills**.
7. **Auditar** (CloudTrail/SSM logs).

## 6. DNS e redirecionamento de tráfego

| Mecanismo | Uso |
|---|---|
| **Route 53 (failover/weighted/latency)** | Direcionar tráfego público/privado **para a recuperação**; **health checks** |
| **TTL baixo** (ex.: 60 s) nos registros críticos | Cutover rápido; **definir antes** do desastre |
| **Route 53 Resolver/DNS privado** | Zonas privadas para a VPC de DR |
| **AWS Application Recovery Controller (ARC)** | **Controles de roteamento** (liga/desliga tráfego) e **readiness checks** |
| **ALB/NLB/Global Accelerator** | Front-ends estáveis para a aplicação recuperada |
| **AD DNS/split-horizon** | Resolver nomes internos para IPs de DR |
| **Atualização manual/script** | Em ambientes simples, **script** documentado/testado |

Fluxo típico:

```
Usuários ─▶ DNS (Route 53) ─▶ [normal: produção/on-prem]
                             └▶ [desastre: ALB na VPC de DR → instâncias recuperadas]
Gatilho: decisão humana ─▶ alterar registro/peso/controle ARC ─▶ propagação (TTL baixo)
```

## 7. Licenciamento

| Tema | Detalhe (de memória — confirmar) |
|---|---|
| **Windows Server** | **Licença incluída da AWS** (paga por hora) **ou BYOL** (Dedicated Hosts/License Manager) |
| **SQL Server** | Idem (incluída vs BYOL); **edição** e **core count** |
| **Ativação** | Windows precisa de **KMS** (AWS fornece) ou licença própria; instâncias recuperadas costumam **reativar** na AWS |
| **Software por IP/MAC** | Licenças **atreladas a hardware/IP** podem **invalidar**: planejar com o fornecedor |
| **Oracle/SAP/etc.** | Termos de **DR e cloud** (licença de “standby”) — **validar contratualmente** |
| **License Manager** | Controle de **conformidade** |

O custo de licenças **só aparece quando as instâncias existem** (drills e recuperação) — considere no orçamento.

## 8. Checklist de configuração

- [ ] **VPC de DR** (IaC) com subnets, SGs, rotas, NAT/endpoints, **conectividade** (VPN/DX/TGW)
- [ ] **Subnets separadas** para **drill** (isolada) e **recuperação**
- [ ] **Launch templates** revisados (tipo, subnet, SG, IAM, EBS/KMS, tags, **IMDSv2**)
- [ ] **Estratégia de IP/DNS** definida; **TTL baixo** nos registros críticos
- [ ] **Throttling** e **banda** definidos por servidor
- [ ] **Pós-lançamento** (SSM) idempotente, testado, com **segredos** no cofre
- [ ] **Licenciamento** (Windows/SQL/terceiros) tratado
- [ ] **Serviços de suporte** (AD/DNS/NTP/monitoramento/bastion) disponíveis na DR
- [ ] **Chaves KMS/secrets** na região de DR
- [ ] **Observabilidade** (CloudWatch/Flow Logs/CloudTrail) ativa
- [ ] **Documentação e IaC** versionados; **drills** validando tudo

## 9. Erros comuns

- **VPC de DR criada só no desastre**.
- **IP/DNS não planejados** (aplicações dependentes de IP fixo).
- **Template com tipo/AZ inexistente** na região de DR.
- **SGs diferentes da produção** (acesso bloqueado ou aberto demais).
- **IMDSv1/IP público** por padrão.
- **Pós-lançamento sem SSM Agent/IAM profile** → não executa.
- **Segredos hardcoded** nos scripts.
- **Licenças** não consideradas (ativação/custos).
- **Subnet de recuperação sem CIDR compatível** (copy IP falha).
- **Sem serviços de suporte** (AD/DNS/NTP) → servidores sobem mas não autenticam.
- **Throttling baixo demais** (lag/RPO) ou **zero** (satura o link).

## 10. Troubleshooting

| Sintoma | Causa provável | Ação |
|---|---|---|
| Instância lançada sem acesso | SG/subnet/rota/NACL/DNS | Revisar a VPC de DR e o template |
| Falha ao copiar IP privado | IP fora do CIDR/em uso | Ajustar a subnet ou desativar `copy private IP` |
| Pós-lançamento não roda | SSM Agent/IAM profile/rede para endpoints SSM | Instalar/ajustar; endpoints VPC |
| Windows não ativa | KMS/licenciamento/rota | Configurar a ativação; License Manager |
| Aplicação usa IP antigo | Hardcode/hosts/DNS | Corrigir a configuração; usar DNS |
| Tipo de instância indisponível | Capacidade/quota | Alternativas; Capacity Reservations; quotas |
| Falha de boot por UEFI/BIOS | `boot mode` incorreto | Ajustar o launch setting |
| Cutover DNS lento | TTL alto | Reduzir o TTL antecipadamente; ARC |
| Volumes sem KMS na região | Chave inexistente/permissão | Criar/compartilhar a chave na região de DR |

## 11. Resumo rápido

- **Launch settings (DRS)** + **EC2 launch template** + **pós-lançamento (SSM)** definem o servidor recuperado; **right-sizing**, **copy IP/tags**, **licenciamento**, **boot mode**, **launch disposition**.
- **Rede de DR pré-provisionada (IaC)**: **VPC/subnets/SGs/rotas**, **conectividade**, **serviços de suporte**; **subnets separadas** para **drill** e **recuperação**.
- **IP/DNS**: preferir **nomes**; **TTL baixo**; **Route 53/ARC** para redirecionar; **manter IP** só com **mesmo CIDR**.
- **Replicação**: **Direct Connect/VPN** conforme volume; **throttling** equilibra produção × **lag/RPO**.
- **Pós-lançamento**: **idempotente**, **ordenado**, **sem segredos em texto**, **testado em drills**.
- **Licenças** e **ativação** afetam custos/RTO; **IMDSv2**, **tags** e **observabilidade** desde o início.

## 🧩 Quiz de Fixação

1. Que três camadas de configuração definem o servidor recuperado?
2. Por que pré-provisionar a VPC de DR com IaC?
3. Quais as vantagens e desvantagens de manter o IP privado?
4. Para que serve o throttling e qual seu risco?
5. Que pré-requisitos as ações pós-lançamento têm?
6. Como acelerar o redirecionamento do tráfego no failover?
7. Por que o licenciamento importa para a recuperação?

**Respostas:**

1. Launch settings do DRS, launch template do EC2 e ações pós-lançamento (SSM).
2. Porque criar rede durante o incidente é lento e arriscado; pré-provisionar garante consistência e reduz o RTO.
3. Reduz mudanças em aplicações e firewalls, mas exige o mesmo CIDR na recuperação e pode gerar conflitos em drills.
4. Limitar a banda de replicação para proteger o link de produção; throttling excessivo aumenta o lag e piora o RPO.
5. SSM Agent funcional, IAM instance profile adequado e rede até os endpoints do Systems Manager (além de documentos SSM válidos).
6. Com TTL baixo configurado antes do desastre e uso de Route 53 (failover/weighted), ALB/Global Accelerator e Application Recovery Controller.
7. Porque licenças (Windows, SQL, terceiros) podem exigir ativação, BYOL ou custos adicionais, e licenças atreladas a IP/hardware podem invalidar na recuperação.
