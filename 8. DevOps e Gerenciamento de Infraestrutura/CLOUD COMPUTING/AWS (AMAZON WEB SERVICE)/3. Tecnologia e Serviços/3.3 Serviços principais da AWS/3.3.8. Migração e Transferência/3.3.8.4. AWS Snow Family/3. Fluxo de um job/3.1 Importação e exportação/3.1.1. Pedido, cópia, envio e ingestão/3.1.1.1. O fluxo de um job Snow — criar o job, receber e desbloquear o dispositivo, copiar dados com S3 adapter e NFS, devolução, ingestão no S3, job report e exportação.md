### 3.1.1.1. O fluxo de um job Snow — criar o job, receber e desbloquear o dispositivo, copiar dados com S3 adapter e NFS, devolução, ingestão no S3, job report e exportação

> [!warning] Aviso
> Os comandos, nomes de ferramentas, portas e sequências abaixo são **ilustrativos e não foram executados**. A interface do console, o AWS OpsHub, as versões do cliente Snowball Edge e as opções de cópia mudam; siga sempre o **guia do desenvolvedor da versão do seu dispositivo** e as instruções que acompanham o job. Confirme também quais dispositivos estão disponíveis na sua região.

## 1. Visão geral do fluxo

Um **job** Snow é um projeto de ponta a ponta. A divisão em fases ajuda a planejar:

```
 FASE 0  Planejar      Inventário, dimensionamento, rede local, janela, equipe
 FASE 1  Criar o job   Console: tipo, dispositivo, destino S3, KMS, endereço, IAM, notificações
 FASE 2  Receber       Dispositivo chega; verificação de integridade física
 FASE 3  Conectar      Energia + rede; IP; acesso ao dispositivo
 FASE 4  Desbloquear   Manifesto + código de desbloqueio
 FASE 5  Copiar        S3 adapter / NFS / OpsHub; paralelismo; verificação
 FASE 6  Devolver      Desligar; etiqueta E Ink; coleta pela transportadora
 FASE 7  Ingerir       AWS importa para o S3; job report
 FASE 8  Validar       Conferir objetos, contagens, erros; encerrar o job
```

## 2. Fase 0 — Planejamento

Antes de pedir o dispositivo:

1. **Inventariar** o volume, o número de arquivos, o tamanho médio e a taxa de mudança.
2. **Calcular** o número de dispositivos e se serão pedidos **em paralelo** ou **em ondas**.
3. Preparar o **local**: espaço, **energia** (tomada correta), **rede** (switch com porta compatível, SFP/RJ45), IP livre.
4. Definir **quem copia** e **de onde**: hosts de cópia com rede rápida e acesso ao storage de origem.
5. Escolher **buckets e prefixos** de destino e a **chave KMS**.
6. Alinhar **segurança**: quem recebe o dispositivo, quem guarda o código de desbloqueio.
7. Preparar uma **janela** e **contingência** (atraso, dispositivo com defeito).

## 3. Fase 1 — Criar o job

No console do **AWS Snow Family** (ou via API `CreateJob`), o assistente pergunta:

| Campo | Explicação |
|---|---|
| **Tipo de job** | Import into S3, Export from S3 ou Local compute and storage |
| **Dispositivo** | Snowball Edge Storage/Compute Optimized, etc. (conforme disponibilidade) |
| **Buckets S3** | Para importação, o bucket de destino; para exportação, os buckets/prefixos de origem |
| **Endereço de envio** | Local físico onde o dispositivo será entregue (e de onde será coletado) |
| **Velocidade de envio** | Opções de frete (padrão, expresso) |
| **Chave KMS** | Chave para criptografar os dados no dispositivo |
| **Role IAM** | Permissão para o Snow escrever/ler no bucket em seu nome |
| **Notificações (SNS)** | Para ser avisado de mudanças de estado do job |
| **Opções do dispositivo** | Rede, clusters, EC2/Lambda, etc. |

Exemplo ilustrativo via CLI:

```bash
aws snowball create-job \
  --job-type IMPORT \
  --resources '{"S3Resources":[{"BucketArn":"arn:aws:s3:::meu-bucket-importacao","KeyRange":{}}]}' \
  --address-id ADID1234ab12-3eec-4eb3-9be6-9374c10eb51b \
  --kms-key-arn arn:aws:kms:us-east-1:123456789012:key/abcd1234-... \
  --role-arn arn:aws:iam::123456789012:role/snow-import-role \
  --snowball-type EDGE_S \
  --shipping-option SECOND_DAY \
  --notification '{"SnsTopicARN":"arn:aws:sns:us-east-1:123456789012:snow-jobs","JobStatesToNotify":["InTransitToCustomer","WithCustomer","InTransitToAWS","Complete"]}'
```

A **role IAM** do job precisa de permissões como `s3:PutObject`, `s3:ListBucket`, `s3:GetBucketLocation` (importação) e `s3:GetObject`, `s3:ListBucket` (exportação), e a **chave KMS** precisa permitir o uso pelo serviço.

### 3.1 Estados do job

```
New ─▶ PreparingAppliance ─▶ PreparingShipment ─▶ InTransitToCustomer ─▶ WithCustomer
   ─▶ InTransitToAWS ─▶ WithAWS ─▶ InProgress (importando) ─▶ Complete
                                  └──▶ Cancelled / (Pending)
```

Você pode **cancelar** enquanto o job está em estados iniciais (`New`), sujeito às regras vigentes.

## 4. Fase 2 e 3 — Receber e conectar

Ao receber:

1. **Inspecione** o dispositivo: sinais de violação, danos de transporte. Registre fotos e, se houver dano, **não ligue** e contate a AWS.
2. **Posicione** em local estável, com ventilação.
3. Conecte a **energia** e a **rede** (cabo RJ45/SFP/QSFP) a um switch ou direto a um host.
4. **Ligue**. A tela **E Ink** exibe o estado e o **endereço IP** (DHCP por padrão); é possível configurar **IP estático** pelo painel do dispositivo.
5. Em **um** host de cópia, teste a conectividade (`ping`, `curl`).

> [!tip] Dica
> Use uma **VLAN dedicada** ou conexão direta para evitar competição com o tráfego da rede corporativa, e configure **jumbo frames** se a infraestrutura suportar e a documentação recomendar.

## 5. Fase 4 — Desbloquear

O dispositivo chega **bloqueado e criptografado**. Para usá-lo, você precisa de dois itens, obtidos **separadamente** do console (nunca vêm na caixa):

- O **manifesto** (arquivo com metadados do job e a chave criptografada).
- O **código de desbloqueio** (29 caracteres).

```bash
# Configurar o cliente com o IP, o manifesto e o código
snowballEdge configure
#  -> informa: IP do dispositivo, caminho do manifesto, código de desbloqueio

snowballEdge unlock-device
snowballEdge describe-device
# Aguarde o estado "UNLOCKED"
```

Alternativa gráfica: o **AWS OpsHub** (aplicativo de desktop) faz o desbloqueio, a configuração e o monitoramento com interface visual.

## 6. Fase 5 — Copiar dados

Há três caminhos principais para colocar dados no dispositivo.

### 6.1 Endpoint S3-compatível (S3 adapter)

O dispositivo expõe uma API **compatível com S3**; você usa a **AWS CLI** ou SDKs apontando para o endpoint local:

```bash
# Obter as credenciais locais
snowballEdge list-access-keys
snowballEdge get-secret-access-key --access-key-id AKIAIOSFODNN7EXAMPLE

# Criar um perfil para o dispositivo
aws configure --profile snowballEdge

# Listar buckets no dispositivo
aws s3 ls --endpoint-url https://192.0.2.10:8443 --profile snowballEdge --ca-bundle ./certificado.pem

# Copiar dados
aws s3 cp /dados/ s3://meu-bucket-importacao/projeto/ \
  --recursive --endpoint-url https://192.0.2.10:8443 --profile snowballEdge --ca-bundle ./certificado.pem
```

Use o **certificado do dispositivo** (`--ca-bundle`) para validar o HTTPS. HTTP (porta 8080) é possível em ambientes isolados, mas **não recomendado** com dados sensíveis.

### 6.2 NFS (interface de arquivos)

O Snowball Edge pode expor **compartilhamentos NFS** associados a buckets, para quem prefere copiar com ferramentas de arquivo:

```bash
# Habilita a interface NFS (pelo console local/OpsHub ou CLI) e monta no host
sudo mount -t nfs -o nolock,vers=3 192.0.2.10:/buckets/meu-bucket-importacao /mnt/snow
rsync -av --progress /dados/ /mnt/snow/projeto/
```

A interface NFS é conveniente, mas costuma ser **mais lenta** que a cópia paralela pela API S3 para grandes volumes.

### 6.3 AWS OpsHub e ferramentas de terceiros

O **OpsHub** oferece **arrastar e soltar** e gerenciamento visual (bom para volumes menores). Ferramentas de terceiros e utilitários de cópia paralela (por exemplo, `rclone`, `s5cmd`, scripts com `xargs -P`) aceleram cópias muito grandes.

### 6.4 Paralelismo e desempenho

Para saturar a rede (10–100 Gbps):

- **Vários hosts** de cópia, cada um lendo uma parte da origem.
- **Vários fluxos** por host (`xargs -P`, `parallel`, `s5cmd`).
- **Arquivos grandes** copiam melhor que milhões de pequenos; **empacote** os pequenos (tar) quando possível.
- Monitore o dispositivo (`snowballEdge describe-device`, OpsHub) e o storage de origem (IOPS, CPU).

Exemplo de cópia paralela (ilustrativo):

```bash
# Divide a lista de diretórios e copia 16 em paralelo
ls /dados | xargs -P 16 -I{} aws s3 cp /dados/{} s3://meu-bucket-importacao/{}/ \
  --recursive --endpoint-url https://192.0.2.10:8443 --profile snowballEdge
```

### 6.5 Verificação antes de devolver

- Compare **contagens e tamanhos** entre origem e dispositivo.
- Use **checksums** (MD5/SHA) de uma amostra ou de tudo, se o prazo permitir.
- Veja se **não restam erros** de cópia e se o espaço utilizado é coerente.
- Mantenha os dados na **origem** até a conclusão da ingestão e a validação no S3.

## 7. Fase 6 — Devolver o dispositivo

1. Conclua as cópias e **desligue** o dispositivo corretamente (botão/OpsHub/`snowballEdge`...). Aguarde o estado seguro.
2. Desconecte os cabos e guarde-os.
3. A **etiqueta E Ink** passa a exibir o **endereço de retorno** da AWS (não é preciso imprimir etiqueta).
4. Agende a **coleta** com a transportadora (ou entregue em ponto de coleta), conforme o país.
5. Acompanhe o **rastreamento** no console e por SNS.

> [!warning] Cuidado
> Não retorne o dispositivo **sem confirmar a cópia**. Depois da devolução, você não pode adicionar dados. E guarde o **manifesto** e o **código de desbloqueio** até o fim do job (não os envie junto com a caixa).

## 8. Fase 7 — Ingestão no S3

Ao receber o dispositivo, a AWS:

1. Verifica a **integridade e a cadeia de custódia**.
2. Conecta o dispositivo a uma infraestrutura segura e **importa** os objetos para o bucket configurado, usando a chave e as permissões do job.
3. Gera o **job report** (relatório de conclusão) e o **log de sucesso/falha**.
4. **Sanitiza** o dispositivo (apagamento seguro conforme NIST 800-88).
5. Atualiza o estado para **Complete**.

### 8.1 Job report e logs

Você baixa do console:

- **Job completion report** (PDF com sumário: objetos importados, falhas, bytes).
- **Success log** e **failure log** (CSV): lista de objetos importados com sucesso ou com erro.

Objetos com falha típicos: **nomes inválidos** ou muito longos, caracteres não suportados, **objetos acima do limite**, problemas de permissão (role/KMS).

### 8.2 Validação no S3

- Compare **contagem de objetos e bytes** (por exemplo, com **S3 Inventory**, `aws s3 ls --summarize`, ou **S3 Storage Lens**).
- Compare **checksums** de uma amostra.
- Trate os itens do **failure log**: corrija e reenvie por **DataSync** ou `aws s3 cp`.
- Só então **descomissione** os dados da origem.

## 9. Jobs de exportação do S3

Fluxo inverso:

1. No console, crie um job **Export** definindo **buckets e prefixos (key range)** a exportar.
2. A AWS **copia os objetos** para o dispositivo e o envia a você.
3. Você **desbloqueia** e **copia do dispositivo** para o seu storage (S3 adapter/NFS).
4. **Devolve** o dispositivo; a AWS o sanitiza.

Observações: a exportação tem **limites de tamanho** por dispositivo (se o total exceder, o job é dividido em vários dispositivos — **cada um com custo**), e é **por intervalos de chave** (ranges), então planeje os prefixos. Há **custos de saída** de dados do S3 (data transfer out) conforme preços vigentes.

## 10. Jobs de computação local

No tipo **Local compute and storage**, o dispositivo é usado como **infraestrutura de borda**:

- Importar **AMIs** e executar **instâncias EC2**.
- Executar **Lambda** local.
- Armazenar dados localmente no S3 adapter/EBS.
- Opcionalmente, **devolver** o dispositivo ao final (com ou sem importar dados).

Esses cenários são tratados na folha de computação na borda e em clusters.

## 11. Cronograma típico (importação)

| Etapa | Duração típica |
|---|---|
| Planejamento e criação do job | Dias |
| Preparação e envio da AWS | Dias a uma semana |
| Entrega e instalação | Dias |
| Cópia dos dados | Horas a dias (conforme volume e rede) |
| Devolução e transporte | Dias |
| Ingestão e relatório | Dias a uma semana |
| **Total** | **~2 a 6 semanas** |

## 12. Erros comuns

> [!bug] Erros comuns
> 1. **Não preparar a rede e a energia** antes da chegada do dispositivo.
> 2. **Guardar o código de desbloqueio junto com a caixa** ou perdê-lo.
> 3. **Copiar de uma única estação** em série.
> 4. **Usar HTTP** (8080) com dados sensíveis.
> 5. **Devolver sem verificar** contagens e checksums.
> 6. **Apagar a origem antes da validação no S3.**
> 7. **Ignorar o failure log** e deixar arquivos importantes de fora.
> 8. **Nomes de arquivos inválidos** (caracteres especiais, comprimento) que falham na ingestão.
> 9. **Role/KMS mal configurados**, causando falhas de ingestão.
> 10. **Exportar sem planejar prefixos**, multiplicando dispositivos e custos.

## 13. Troubleshooting

| Sintoma | Causa provável | Ação |
|---|---|---|
| Não alcança o dispositivo | IP/VLAN/firewall | Verificar o IP na E Ink, o switch e as portas 8080/8443 e 22 |
| `unlock-device` falha | Manifesto/código errados ou expirados | Baixar de novo no console; conferir a região |
| Erro de certificado HTTPS | Certificado não confiado | Usar `--ca-bundle` com o certificado do dispositivo |
| Cópia lenta | Poucas sessões, origem lenta, arquivos pequenos | Paralelizar, empacotar, testar a leitura da origem |
| Itens no failure log | Nomes inválidos, permissões | Corrigir e reenviar por DataSync/`aws s3 cp` |
| Job parado em estado | Logística/alfândega | Verificar o rastreamento e contatar o suporte |
| Dispositivo com defeito | Dano físico | Não ligar; contatar a AWS para substituição |

## 14. Resumo rápido

- Fluxo: **planejar → criar job → receber → conectar → desbloquear → copiar → devolver → ingerir → validar**.
- Desbloqueio exige **manifesto + código** obtidos do console, separados do dispositivo.
- Copie por **S3 adapter** (rápido, paralelo), **NFS** (conveniente) ou **OpsHub**; use **paralelismo** e empacote arquivos pequenos.
- A AWS **ingere**, gera **job report** e **sanitiza**; valide e trate o **failure log** antes de apagar a origem.
- **Exportação** é o inverso, por ranges de chave; **local compute** usa o dispositivo como edge.

### 🧩 Quiz de Fixação

1. Que dois itens são necessários para desbloquear o dispositivo?
2. Quais as formas de copiar dados para o Snowball Edge?
3. O que exibe a etiqueta E Ink ao final da cópia?
4. O que o job report traz?
5. Por que não apagar a origem logo após devolver o dispositivo?
6. Como paralelizar a cópia?
7. Qual a diferença de fluxo entre importação e exportação?

**Respostas:**

1. O manifesto e o código de desbloqueio, ambos obtidos do console.
2. Endpoint S3-compatível (AWS CLI/SDK), interface NFS e AWS OpsHub (além de ferramentas de terceiros).
3. O endereço de retorno da AWS para a transportadora.
4. Resumo da importação (objetos e bytes) com logs de sucesso e falha.
5. Porque é preciso validar a ingestão no S3 e tratar falhas antes de descomissionar a origem.
6. Com vários hosts e vários fluxos por host, usando arquivos grandes ou empacotando os pequenos.
7. Na importação você copia para o dispositivo e a AWS ingere no S3; na exportação a AWS copia do S3 para o dispositivo e você o descarrega.
