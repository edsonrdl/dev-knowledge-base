### 4.1.1.1. Computação na borda com Snow — EC2 e Lambda locais, volumes e S3 local, clusters de Snowball Edge, operação desconectada, GPU e casos de uso

> [!warning] Aviso
> Os comandos, tipos de instância, versões e capacidades abaixo são **ilustrativos e não foram executados**. Os recursos de computação em Snow (instâncias "sbe", Lambda via IoT Greengrass, clusters, assinaturas de borda) mudam com as versões de dispositivo e de software, e a oferta de modelos foi reduzida para novos clientes. Confirme na documentação oficial o que está disponível e suportado antes de projetar uma solução. Para novas cargas de borda, avalie também **AWS Outposts** e outras opções da AWS para edge.

## 1. O que é computação na borda (edge)

**Edge computing** é executar processamento **onde os dados nascem** — em vez de enviá-los a uma região AWS distante. As razões típicas:

- **Conectividade ruim ou inexistente**: navio, mina, plataforma, aeronave, campo remoto.
- **Latência**: decisões em milissegundos (controle industrial, visão computacional em linha de produção).
- **Volume de dados**: gerar terabytes por hora e só enviar o resultado resumido.
- **Soberania e regulação**: manter dados no local.
- **Resiliência**: continuar operando durante quedas de rede.

O **Snowball Edge** (e, em menor escala, o Snowcone) atende a esse perfil como um **mini-datacenter robusto**, que roda um subconjunto de serviços AWS **localmente**.

## 2. O que roda num dispositivo Snow

| Capacidade | Descrição |
|---|---|
| **Instâncias EC2 (sbe)** | VMs a partir de **AMIs** que você importa; tipos específicos de Snow (família `sbe`, `sbe-c`, `sbe-g` com GPU...) |
| **AWS Lambda (via IoT Greengrass)** | Funções locais acionadas por eventos (por exemplo, quando um objeto chega ao S3 local) |
| **Amazon S3 compatível** | Armazenamento de objetos local (S3 adapter), com buckets locais |
| **Volumes de blocos (EBS-like)** | Volumes para as instâncias EC2 |
| **NFS** | Compartilhamento de arquivos |
| **IAM e STS locais** | Autenticação e autorização locais para os serviços do dispositivo |
| **AWS IoT Greengrass** | Runtime para funções e conectores de IoT |
| **Kubernetes (EKS Anywhere em Snow)** | Em algumas versões, execução de clusters Kubernetes (verificar suporte) |
| **Armazenamento e sincronização** | Replicação posterior para a região AWS quando houver conectividade |

> [!tip] Dica
> O dispositivo oferece um **subconjunto** de funcionalidades e não é uma região AWS completa. Valide cada serviço e API de que a sua aplicação depende (por exemplo, nem todo recurso de EC2, VPC ou S3 está disponível).

## 3. Instâncias EC2 no Snow

Fluxo:

1. **Preparar a AMI**: criada a partir de uma instância EC2 na AWS (ou importada de VM local) e **exportada** como AMI compatível com o Snow; escolha um SO suportado (Amazon Linux, Ubuntu, CentOS/RHEL, Windows em algumas versões).
2. **Associar a AMI ao job** no pedido, de modo que ela já venha **no dispositivo**.
3. Após o **desbloqueio**, lançar a instância pelo cliente/OpsHub/CLI apontando para o endpoint EC2 local.

```bash
# Endpoint EC2 local do dispositivo (porta 8243)
aws ec2 describe-images --endpoint http://192.0.2.10:8008 --profile snowballEdge

aws ec2 run-instances \
  --image-id s.ami-0123456789abcdef0 \
  --instance-type sbe-c.large \
  --endpoint http://192.0.2.10:8008 --profile snowballEdge

# Cria e anexa um volume
aws ec2 create-volume --size 200 --volume-type sbg1 \
  --endpoint http://192.0.2.10:8008 --profile snowballEdge
```

### 3.1 Tipos de instância (exemplos conceituais)

| Família | Perfil | Dispositivo | Exemplo de uso |
|---|---|---|---|
| **sbe1** | Uso geral (vCPU/RAM moderados) | Storage Optimized | Serviços leves, bancos pequenos |
| **sbe-c** | Otimizada para computação | Compute Optimized | Processamento intensivo, ML CPU |
| **sbe-g** | Com **GPU** | Compute Optimized com GPU | Inferência/visão, transcodificação |
| **snc1** | Pequena | Snowcone | Pré-processamento leve |

Os **recursos máximos por instância** dependem do dispositivo; a soma das instâncias não pode ultrapassar os vCPUs, a memória e o storage do aparelho.

### 3.2 Rede virtual

O dispositivo usa **interfaces virtuais (VNIs)** associadas às **portas físicas** para dar IPs às instâncias na rede local. Você configura **IPs, máscaras, gateways e DNS** e, opcionalmente, **NAT direto** para expor um serviço na rede local.

## 4. Lambda e IoT Greengrass no dispositivo

As funções locais seguem o modelo **orientado a eventos**:

```
Dado chega ao bucket S3 local ──▶ gatilho ──▶ Função Lambda local ──▶ resultado em outro bucket
                                                │
                                   (IoT Greengrass como runtime)
```

Casos: converter imagens, extrair metadados, aplicar um modelo de ML, comprimir e filtrar antes de enviar. As funções são **empacotadas e associadas ao job** (ou implantadas posteriormente), com limitações de linguagem, memória e tempo de execução definidas pelo Greengrass.

## 5. Armazenamento local e sincronização

- **S3 compatível local**: buckets no dispositivo para alimentar aplicações.
- **Volumes EBS-like** para as instâncias.
- **NFS** para compartilhamento com clientes locais.
- **Sincronização**: quando o dispositivo (ou o cluster) tem conectividade, é possível **enviar os dados à AWS** (por exemplo, com **DataSync** a partir do Snowcone, ou devolvendo o dispositivo para ingestão física).

Padrão **store-and-forward**: coleta localmente por semanas e **devolve o dispositivo** para ingestão, ou **sincroniza** quando há janela de conectividade.

## 6. Clusters de Snowball Edge

Um **cluster** reúne **5 a 10** dispositivos Snowball Edge (valores sujeitos à versão) em um **pool de armazenamento** local:

| Característica | Detalhe |
|---|---|
| **Durabilidade** | Dados distribuídos entre os nós com redundância; tolera a perda de um ou mais nós (conforme o esquema) |
| **Escalabilidade** | Capacidade e desempenho crescem com o número de nós |
| **Disponibilidade local** | Continua operando com nós degradados |
| **Gerenciamento** | Cluster tratado como **uma unidade** no job; substituição de nó pelo suporte |
| **Uso** | Edge de longa duração com grande volume e necessidade de **resiliência** (análises, mídia, data hubs) |

Diagrama:

```
        ┌──────────┐  ┌──────────┐  ┌──────────┐  ┌──────────┐  ┌──────────┐
 Rede ──┤ Snowball ├──┤ Snowball ├──┤ Snowball ├──┤ Snowball ├──┤ Snowball │
 local  │  Edge #1 │  │  Edge #2 │  │  Edge #3 │  │  Edge #4 │  │  Edge #5 │
        └──────────┘  └──────────┘  └──────────┘  └──────────┘  └──────────┘
                    Pool de armazenamento S3 local (com redundância)
```

Cuidados: **desbloqueio** do cluster exige todos os nós (ou quorum) e o **manifesto/código** do cluster; **troca de nós** segue procedimento com a AWS; clusters não são o ideal para migração pontual (pelo custo e pela complexidade).

## 7. Operação desconectada

O ponto forte do Snow no edge é **funcionar sem a nuvem**:

- O **desbloqueio** é feito **localmente** com o manifesto e o código (sem acesso à AWS no momento do uso).
- **IAM, STS, S3, EC2 e Lambda** funcionam localmente.
- **Atualizações de software** do dispositivo podem exigir janelas com conectividade (ou ocorrem na troca do dispositivo).
- **Métricas e monitoramento** local por **SNMP/CloudWatch Agent/OpsHub**; envio ao CloudWatch quando houver conectividade.

Planeje: **tempo máximo de uso** (assinaturas ou prazos do job), **atualização de AMIs e funções**, **backup** de dados críticos e **procedimento de retorno**.

## 8. GPU e cargas de ML

O **Compute Optimized com GPU** permite **inferência e processamento de vídeo/imagem** no local:

- **Treinar** na região AWS (SageMaker) e **implantar o modelo** no dispositivo para inferência.
- **Visão computacional** em plataformas, minas e fábricas.
- **Transcodificação** de vídeo em campo.
- Uso de **frameworks** (TensorFlow, PyTorch, ONNX) em AMIs preparadas com drivers.

Considere o **consumo de energia** da GPU e a **refrigeração**, além de preparar **AMIs com drivers** compatíveis.

## 9. Casos de uso

| Setor | Cenário | Solução com Snow |
|---|---|---|
| **Petróleo e gás** | Dados sísmicos e telemetria em plataformas | Processamento local + devolução do dispositivo para ingestão |
| **Mineração** | Operação em local remoto, sem rede | Edge com EC2/Lambda; sincronização periódica |
| **Mídia e entretenimento** | Gravação em locação, vários TB por dia | Cópia local, transcodificação com GPU, envio ao S3 |
| **Saúde/campo** | Unidade móvel, hospital de campanha | Sistema local desconectado com sincronização posterior |
| **Defesa/emergência** | Ambientes austeros | Kit robusto portátil com computação |
| **Indústria** | Visão computacional em linha | Inferência local de baixa latência |
| **Pesquisa científica** | Sequenciamento, telescópios, expedições | Coleta de grandes volumes e processamento local |
| **Varejo/rede remota** | Lojas com conectividade fraca | Cache e processamento local |

## 10. Quando preferir alternativas

| Necessidade | Alternativa |
|---|---|
| Edge de longa duração, integrado a uma região, com serviços AWS completos | **AWS Outposts** |
| IoT leve com muitos dispositivos pequenos | **AWS IoT Greengrass** em hardware próprio |
| Aplicação com baixa latência em cidades | **AWS Local Zones/Wavelength** |
| Transferência de dados pura | **DataSync** (online) ou Snow (offline) |

## 11. Exemplo narrado

Uma empresa de pesquisa oceanográfica coleta 40 TB de sonar por viagem de 6 semanas, sem conexão estável. Um **Snowball Edge Compute Optimized com GPU** vai a bordo. Uma instância EC2 `sbe-g` roda um modelo de classificação que **marca anomalias** nos dados em tempo real, e uma função Lambda local organiza os arquivos por região e data no S3 local. Ao fim da viagem, o dispositivo é **devolvido** e os 40 TB são **ingeridos** no S3, onde pipelines Glue/Athena fazem análises mais pesadas. O resultado: o time vê as anomalias **durante** a viagem e ainda recebe os dados completos em poucas semanas.

## 12. Erros comuns

> [!bug] Erros comuns
> 1. **Supor que o Snow tem todos os serviços da região AWS.**
> 2. **Esquecer de associar AMIs/funções ao job**, chegando ao local sem elas.
> 3. **Subestimar energia e refrigeração** para GPU e cargas contínuas.
> 4. **Não prever o prazo de uso** e o procedimento de retorno.
> 5. **Executar um serviço crítico sem redundância** (sem cluster e sem backup).
> 6. **Usar cluster para migração pontual simples.**
> 7. **Ignorar atualizações de software e AMIs** em operação longa.
> 8. **Expor a rede do dispositivo à rede geral** sem segmentação e controles.
> 9. **Não testar a solução em um dispositivo/ambiente semelhante** antes de enviar ao campo.

## 13. Troubleshooting

| Sintoma | Causa provável | Ação |
|---|---|---|
| Instância não inicia | AMI incompatível ou recursos insuficientes | Conferir a AMI/SO, vCPU/RAM disponíveis e logs |
| Sem rede na instância | VNI/IP/NAT mal configurados | Revisar VNI, IP, rotas e NAT direto |
| Lambda não dispara | Gatilho/runtime | Verificar a configuração do Greengrass e do bucket local |
| Cluster degradado | Nó com falha | Seguir o procedimento de substituição com a AWS |
| GPU não detectada | Driver/AMI inadequados | Usar a AMI com drivers suportados |
| Armazenamento cheio | Dimensionamento | Liberar espaço, mover dados ou adicionar nós/dispositivos |

## 14. Resumo rápido

- Snow no edge = **mini-datacenter robusto** com **EC2 (sbe), Lambda (Greengrass), S3 local, volumes e NFS**, funcionando **desconectado**.
- **Clusters** (5–10 Snowball Edge) dão **durabilidade e escala** locais.
- **Compute Optimized com GPU** viabiliza **ML e vídeo** na borda.
- Padrão **store-and-forward**: processa localmente e sincroniza/devolve para ingestão.
- Dispositivos oferecem um **subconjunto** de serviços; valide dependências e considere **Outposts** para edge duradouro.
