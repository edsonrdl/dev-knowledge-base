### 5.1.1.1. Segurança do Transfer Family — IAM por usuário, criptografia, chaves de host, security policies, rede, logs estruturados, auditoria e conformidade

> [!warning] Aviso
> Nomes de security policies, opções de logging estruturado, comportamento de criptografia por protocolo, campos de logs e eventos de CloudTrail abaixo são **de memória e mudam**. **Confirme na documentação do AWS Transfer Family, do IAM, do KMS e do CloudWatch.** Políticas e comandos são ilustrativos e **não foram executados**. Um endpoint SFTP é uma **porta de entrada na internet** para dados de negócio: trate como **superfície de ataque crítica**.

## 1. Modelo de ameaças

O Transfer Family expõe um **serviço de rede** que **parceiros externos** usam para **enviar e baixar arquivos**. Ameaças típicas:

| Ameaça | Descrição | Impacto |
|---|---|---|
| **Credenciais comprometidas** | Chave SSH/senha de parceiro vazada | Acesso a **dados** do parceiro (e, com role ampla, de **todos**) |
| **Força bruta / password spraying** | Tentativas massivas de login | Contas bloqueadas, DoS, acesso indevido |
| **Isolamento fraco entre parceiros** | Role/mapeamento amplos | Um parceiro **lê/apaga** dados de outro |
| **Malware/arquivos maliciosos** | Parceiro (ou conta invadida) envia arquivos perigosos | Comprometimento de pipelines |
| **Exfiltração** | Usuário baixa dados em massa | Vazamento |
| **Algoritmos fracos** | Security policy permissiva | Interceptação/downgrade |
| **MITM** | Troca de host key sem verificação | Roubo de credenciais |
| **Exposição pública acidental** | Endpoint público sem restrições | Alvo de varreduras |
| **Má configuração do S3** | Bucket com acesso público | Vazamento total |
| **Segredos expostos** | Chaves PGP/AS2/credenciais de conectores em texto | Fraude/impersonação |
| **Falta de auditoria** | Sem logs de sessão/arquivo | Incidentes não detectados |
| **Abuso de custos** | Uploads/downloads massivos | Fatura inesperada |

Defesa em camadas: **rede** → **autenticação** → **autorização (IAM/isolamento)** → **criptografia** → **proteção de dados/arquivos** → **auditoria e detecção** → **governança**.

## 2. Rede e exposição

### 2.1 Reduzir a superfície

| Controle | Detalhe |
|---|---|
| **Endpoint VPC** | **Security Groups** limitando **CIDRs de parceiros** (**allowlist**) — preferir a **público** quando possível |
| **Público (quando necessário)** | Aceitar o risco com **security policy forte**, **chaves SSH** (sem senha), **monitoramento** e **limites** |
| **VPC internal + VPN/DX** | Para **parceiros** com conectividade **privada** |
| **Portas** | Habilitar **somente os protocolos necessários** (evitar FTP/FTPS se só SFTP) |
| **NACLs** | Camada extra de **bloqueio** |
| **WAF/NLB** | Cenários avançados (AS2/HTTPS na frente) |
| **VPC endpoint (S3/KMS/Secrets/Logs)** | **Tráfego privado** do serviço aos backends |
| **Egress (conectores)** | **Informar IPs** de saída aos parceiros; **restringir** destinos permitidos |
| **Geofencing** | Bloquear **países** não esperados (SG/NACL/WAF/NLB) |

### 2.2 DDoS e abuso

- **Shield Standard** protege a infraestrutura de rede **gerenciada**; para **VPC internet-facing**, **Shield Advanced** pode ser considerado para **EIPs**.
- **Rate limiting**: **SG não limita taxa**; use **NLB/WAF/proxy** ou **monitoramento** com **bloqueio dinâmico** (Lambda atualizando **NACL/SG** a partir de **logs**).
- **Alarmes** de **picos de conexões**/falhas de login.

## 3. Autenticação

| Prática | Detalhe |
|---|---|
| **Chaves SSH em vez de senhas** | **Resistem a força bruta**; **ed25519**/RSA forte |
| **Se senhas forem inevitáveis** | **AD/Lambda** com **políticas fortes**, **bloqueio por tentativas**, **rotação**, **IP allowlist** |
| **MFA** | Via **identidade customizada** (**chave + senha**); **VPN** como segundo fator de rede |
| **Rotação de chaves** | **Política** (ex.: anual), com **múltiplas chaves** durante a transição |
| **Revogação imediata** | Procedimento para **remover chave/usuário** em minutos |
| **Contas de serviço** | Chaves **dedicadas** por **sistema**, **não compartilhadas** |
| **Segredos** | **Nunca** em repositórios; **Secrets Manager** |

## 4. Autorização e isolamento (IAM)

### 4.1 Princípios

1. **Uma role/política por perfil** com **mínimo** de ações S3/EFS.
2. **Diretórios lógicos** e **prefixos por usuário** (isolamento).
3. **Session policy** (interseção) para **restrição adicional**.
4. **Bucket policy** como **segunda camada** (negar o que não for **role do Transfer**).
5. **Permissões distintas** para **entrada** (`PutObject`) e **saída** (`GetObject`).
6. **Sem `s3:*`**, sem `DeleteObject` se **não necessário** (**proteção contra exclusão**).
7. **Condições**: `aws:SourceVpce`, `aws:SecureTransport`, `s3:x-amz-server-side-encryption`.

### 4.2 Bucket policy de proteção (ilustrativa)

```json
{
  "Version": "2012-10-17",
  "Statement": [
    { "Sid": "ExigirTLS", "Effect": "Deny", "Principal": "*", "Action": "s3:*",
      "Resource": ["arn:aws:s3:::bucket-parceiros-123456789012", "arn:aws:s3:::bucket-parceiros-123456789012/*"],
      "Condition": { "Bool": { "aws:SecureTransport": "false" } } },
    { "Sid": "SomenteRolesAprovadas", "Effect": "Deny", "Principal": "*", "Action": "s3:*",
      "Resource": ["arn:aws:s3:::bucket-parceiros-123456789012", "arn:aws:s3:::bucket-parceiros-123456789012/*"],
      "Condition": { "ArnNotLike": { "aws:PrincipalArn": ["arn:aws:iam::123456789012:role/TransferUser*",
          "arn:aws:iam::123456789012:role/TransferWorkflowRole", "arn:aws:iam::123456789012:role/PipelinesDados*",
          "arn:aws:iam::123456789012:role/PlataformaAdmin"] } } }
  ]
}
```

(Esboço: teste para não bloquear os serviços necessários — workflows, replicação, backup etc.)

### 4.3 Separação de funções (administração)

| Papel | Pode | Não deve |
|---|---|---|
| **Plataforma (Transfer)** | Criar/alterar servidores, endpoints, security policies, logging | Acessar **dados** dos parceiros |
| **Onboarding** | Criar **usuários/chaves** (via **IaC/ticket**) | Alterar **roles** amplas |
| **Segurança** | **Auditar**, definir **políticas** | Operação diária |
| **Operações/Suporte** | **Ver** logs/estado; **reset de chave** com aprovação | Alterar **segurança** |
| **Pipelines** | Ler/escrever **áreas internas** | Alterar **usuários** |
| **Auditoria** | **Somente leitura** | Escrita |

**SCP** para proteger configurações críticas:

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Sid": "ProtegerTransferFamily",
    "Effect": "Deny",
    "Action": ["transfer:UpdateServer", "transfer:DeleteServer", "transfer:StopServer", "transfer:UpdateAccess", "transfer:DeleteAccess"],
    "Resource": "*",
    "Condition": { "ArnNotLike": { "aws:PrincipalArn": ["arn:aws:iam::*:role/TransferPlataformaAdmin", "arn:aws:iam::*:role/PipelineInfra"] } }
  }]
}
```

## 5. Criptografia

### 5.1 Em trânsito

| Protocolo | Proteção |
|---|---|
| **SFTP** | **SSH** (algoritmos da **security policy**) |
| **FTPS** | **TLS** (versão/suítes da policy); **certificado ACM** |
| **FTP** | **Sem criptografia** — **evitar**; só em **rede privada** |
| **AS2** | **Assinatura + criptografia** de **mensagens** (certificados) |
| **Servidor ↔ S3/EFS/KMS** | **TLS** (rede AWS) |

### 5.2 Security policies (resumo de segurança)

- **Usar a política mais restritiva** que os **clientes** suportem (ex.: **2024-01** ou **restricted**); **FIPS** quando necessário.
- **Desativar** algoritmos **legados** (**SHA-1, CBC, RSA 1024**…) sempre que possível; se um parceiro exigir, **isolar** em **servidor separado** com **policy dedicada** e **plano de depreciação**.
- **Revisar** quando novas policies forem publicadas.

### 5.3 Em repouso

| Camada | Prática |
|---|---|
| **S3** | **SSE-KMS (CMK)** com **bucket default encryption** e **bucket keys**; role do **Transfer** com **permissão KMS** |
| **EFS** | **Criptografia em repouso** (KMS) habilitada |
| **Logs** | **CloudWatch Logs com KMS**; S3 de logs com **KMS** |
| **Segredos** | **Secrets Manager (KMS)**; **PGP/AS2** privados **fora** de código |
| **Backups/réplicas** | **CRR** com **KMS** na região de destino |

### 5.4 Chaves de host e certificados

| Item | Prática |
|---|---|
| **Host keys (SFTP)** | **Gerenciar** (importar/rotacionar com aviso); **publicar fingerprints** |
| **Certificados FTPS** | **ACM** com **renovação automática**; **monitorar validade** |
| **Certificados AS2** | **Inventário** e **alertas de expiração** (30/14/7 dias) |
| **PGP** | Chaves privadas em **Secrets Manager**, **rotação** e **backup seguro** |

## 6. Proteção dos dados e dos arquivos

| Controle | Detalhe |
|---|---|
| **Versionamento + MFA Delete/Object Lock** | Proteção contra **exclusão/sobrescrita** (por parceiro comprometido ou erro) |
| **Lifecycle** | **Expirar** o que não é necessário (minimização) |
| **Malware scan** | **GuardDuty Malware Protection for S3**/scanners; **quarentena** |
| **Validação de formato/tamanho** | Rejeitar o que não cumpre contratos |
| **Limites** | **Tamanho máximo**, **taxa**, **tipos** permitidos (via workflow/Lambda) |
| **DLP/Macie** | Detectar **PII/segredos** em arquivos recebidos/enviados |
| **Integridade** | **Checksums/hash** (parceiro envia hash); **assinaturas** (AS2/PGP) |
| **Segregação** | **Buckets** de **parceiros** × **internos**; **sem** acesso cruzado |
| **Retenção** | **Política** (LGPD/contratos); **expurgo** automático |
| **Direitos dos titulares** | Mapear **onde** há dados pessoais em arquivos recebidos |

## 7. Logs e auditoria

### 7.1 Fontes

| Fonte | Conteúdo |
|---|---|
| **Logs estruturados do Transfer (CloudWatch Logs/S3)** | **JSON** por **evento** (conexão, autenticação, comandos, **upload/download**, erros) com **usuário**, **IP de origem**, **servidor**, **arquivo/caminho**, **bytes**, **resultado** |
| **Logs de workflow** | Execução e passos |
| **CloudTrail** | **Administração** (`CreateUser`, `ImportSshPublicKey`, `UpdateServer`, `DeleteUser`…) |
| **S3 data events/server access logs** | **Acesso a objetos** (inclusive por **outros caminhos**) |
| **VPC Flow Logs** | Tráfego dos **ENIs do endpoint** |
| **GuardDuty** | **Atividades suspeitas** (CloudTrail/VPC/S3) |
| **Config/Security Hub** | **Conformidade** (SGs, criptografia, BPA) |
| **Macie** | **Dados sensíveis** |

```bash
aws transfer update-server --server-id s-0123456789abcdef0 \
  --structured-log-destinations arn:aws:logs:us-east-1:123456789012:log-group:/aws/transfer/sftp-prod
aws logs put-subscription-filter --log-group-name /aws/transfer/sftp-prod --filter-name falhas-login \
  --filter-pattern '{ $.activity-type = "AUTH_FAILURE" }' --destination-arn arn:aws:lambda:us-east-1:123456789012:function:alerta-seguranca
```

### 7.2 Eventos a monitorar (exemplos conceituais)

| Evento/Campo | Alarme |
|---|---|
| **Falhas de autenticação** | **Picos** por origem/usuário (força bruta) |
| **Login de IP/país incomum** | **Anomalia** |
| **Downloads/uploads em massa** | **Exfiltração/abuso** |
| **Operações de exclusão** | **Volume** de `DELETE` |
| **Novo usuário/chave** | **Fora do pipeline** |
| **Mudança de security policy/endpoint** | **Alteração de configuração** |
| **Acesso fora do horário** | Se aplicável ao parceiro |
| **Falhas de workflow** | **Erros** repetidos |
| **Arquivos grandes/tipos proibidos** | **Violação** de política |

### 7.3 Consulta de auditoria (CloudWatch Logs Insights; ilustrativa)

```
fields @timestamp, user, source-ip, activity-type, path, bytes
| filter activity-type in ["AUTH_FAILURE"]
| stats count(*) as falhas by source-ip, user
| sort falhas desc
| limit 20
```

## 8. Detecção e resposta

| Cenário | Resposta |
|---|---|
| **Força bruta** | **Bloquear IP** (SG/NACL/WAF), **revisar contas**, **MFA/chaves** |
| **Chave comprometida** | **Revogar** (remover a chave/usuário), **investigar** acessos (logs), **rotacionar**, **notificar** o parceiro |
| **Exfiltração suspeita** | **Suspender usuário**, **preservar logs**, avaliar **dados acessados**, **notificar** (DPO/jurídico) |
| **Malware** | **Quarentena**, **análise**, **bloquear origem**, **comunicar** parceiro |
| **Mudança indevida de configuração** | **Reverter via IaC**, **auditar CloudTrail** |
| **Parceiro com algoritmo legado** | **Isolar** em **servidor/policy dedicada**, **cronograma de atualização** |

## 9. Governança e conformidade

| Tema | Prática |
|---|---|
| **Inventário** | **Servidores, usuários, parceiros, chaves, certificados, buckets, workflows** com **donos** |
| **Contratos/SLAs** | Protocolos, **IPs**, **janelas**, **tamanhos**, **retenção**, **segurança** exigida |
| **Conformidade** | **PCI-DSS** (dados de cartão: criptografia, acesso, logs), **HIPAA** (BAA, PHI), **SOC/ISO**, **LGPD/GDPR** |
| **Evidências** | **Configuração (IaC)**, **logs**, **revisões de acesso**, **testes** |
| **Revisões de acesso** | **Trimestral**: usuários inativos, parceiros desligados, **chaves antigas** |
| **Gestão de mudanças** | **IaC + PR**; **aprovações**; **janelas** |
| **Treinamento** | Equipe de **onboarding** e **suporte** |
| **Risco de terceiros** | **Avaliação** de parceiros, **requisitos mínimos** de segurança |
| **Plano de resposta a incidentes** | **Playbooks** para os cenários acima |
| **Retenção e descarte** | Alinhados à **lei/contrato** |

## 10. Checklist de endurecimento

- [ ] **Somente protocolos necessários** (preferir **SFTP**; **evitar FTP**)
- [ ] **Endpoint VPC** com **SG por CIDR de parceiro** (ou público com compensações)
- [ ] **Security policy** restritiva (**FIPS/atual**); **exceções isoladas**
- [ ] **Chaves SSH** (sem senha) quando possível; **rotação**; **revogação rápida**
- [ ] **Role mínima por usuário/perfil** + **diretórios lógicos** + **session policy** + **bucket policy**
- [ ] **KMS** em S3/EFS/logs/segredos; **TLS**; `aws:SecureTransport`
- [ ] **Versionamento/Object Lock**; **lifecycle**; **malware scan**; **validação de arquivos**
- [ ] **Logs estruturados** + **CloudTrail** + **alarmes** (falhas, volume, mudanças)
- [ ] **SCP/IAM** protegendo configurações; **IaC**
- [ ] **Inventário** de usuários/chaves/certificados; **revisões** trimestrais
- [ ] **Playbooks** de incidentes; **testes**
- [ ] **Conformidade** documentada (PCI/HIPAA/LGPD)

## 11. Erros comuns

- **Role ampla** compartilhada entre parceiros.
- **Endpoint público** sem alarmes/controles.
- **Senhas** em vez de chaves SSH.
- **Security policy legada** por “compatibilidade” para todos.
- **Sem logs estruturados** (ou sem alarmes).
- **Bucket policy** permissiva (acesso fora do Transfer).
- **Chaves de parceiros nunca revogadas**.
- **Sem malware scan**.
- **Host key rotacionada** sem aviso.
- **Segredos de conectores** expostos.
- **Sem retenção/expurgo** (acúmulo de dados).
- **Ignorar custos** de abuso (uploads massivos).

## 12. Troubleshooting

| Sintoma | Causa provável | Ação |
|---|---|---|
| Picos de `AUTH_FAILURE` | Força bruta/chave expirada | Bloquear IPs; verificar usuários; revisar chaves |
| Parceiro vê dados de outro | Mapeamento/role/session policy | Corrigir o isolamento imediatamente; auditar acessos |
| Cliente recusa conexão após ajuste | Security policy incompatível | Ajustar com cuidado; servidor dedicado para legado |
| Sem logs no CloudWatch | Role de logging/log group | Corrigir permissões/destino |
| Upload falha por KMS | Role sem permissão KMS | Ajustar a key policy/role |
| Alerta de MITM no cliente | Host key mudou | Restaurar/importar a chave; comunicar |
| Custos disparam | Download/upload massivo | Investigar logs; limitar; bloquear |
| Arquivo malicioso detectado | Falta de validação | Quarentena; fortalecer o scan/validação |

## 13. Resumo rápido

- **Ameaças**: credenciais, força bruta, isolamento fraco, malware, exfiltração, algoritmos fracos, MITM, exposição, segredos, falta de auditoria.
- **Rede**: **VPC + SG por CIDR** (ou público com compensações), **só protocolos necessários**, **NACL/WAF/NLB**, **VPC endpoints**.
- **Autenticação**: **chaves SSH** > senhas; **rotação/revogação**; MFA via **identidade customizada**.
- **Autorização**: **role mínima**, **diretórios lógicos**, **session policy**, **bucket policy**, **SCP** de proteção.
- **Criptografia**: **security policy** restritiva (FIPS/atual), **KMS** (S3/EFS/logs/segredos), **TLS**, **host keys/certificados** governados.
- **Dados**: **versionamento/Object Lock**, **lifecycle**, **malware scan**, **validação**, **Macie**, **buckets separados**.
- **Auditoria**: **logs estruturados**, **CloudTrail**, **S3/Flow logs**, **GuardDuty**, **alarmes**; **resposta** a incidentes.
- **Governança**: **inventário**, **contratos**, **conformidade (PCI/HIPAA/LGPD)**, **revisões**, **IaC**.

## 🧩 Quiz de Fixação

1. Por que chaves SSH são preferíveis a senhas?
2. Como a combinação de role, diretórios lógicos e bucket policy protege o isolamento?
3. Que riscos há em manter uma security policy legada para todos os parceiros?
4. Que eventos de log merecem alarme?
5. Como responder a uma chave comprometida?
6. Para que servem versionamento e Object Lock nesse cenário?
7. O que fazer com um parceiro que só suporta algoritmos legados?

**Respostas:**

1. Resistem a força bruta e password spraying, não são reutilizadas em outros sistemas e permitem rotação e revogação simples; senhas exigem políticas e controles adicionais.
2. A role limita as ações ao prefixo do usuário, os diretórios lógicos escondem e restringem o caminho e a bucket policy nega qualquer principal fora das roles aprovadas, criando camadas redundantes.
3. Permite algoritmos fracos (downgrade/interceptação) para todos; o melhor é uma policy restritiva e isolar o parceiro legado em servidor/policy dedicados.
4. Picos de falhas de autenticação, logins de origens incomuns, downloads/uploads em massa, exclusões em massa, novos usuários/chaves fora do pipeline e mudanças de configuração.
5. Revogar a chave/usuário imediatamente, investigar acessos pelos logs, rotacionar credenciais, notificar o parceiro e, se necessário, o DPO/jurídico.
6. Protegem contra exclusão ou sobrescrita (por parceiro comprometido ou erro), permitindo recuperar versões e garantir retenção imutável quando exigida.
7. Isolá-lo em um servidor com security policy dedicada, com compensações (rede restrita, monitoramento) e um cronograma para atualização.
