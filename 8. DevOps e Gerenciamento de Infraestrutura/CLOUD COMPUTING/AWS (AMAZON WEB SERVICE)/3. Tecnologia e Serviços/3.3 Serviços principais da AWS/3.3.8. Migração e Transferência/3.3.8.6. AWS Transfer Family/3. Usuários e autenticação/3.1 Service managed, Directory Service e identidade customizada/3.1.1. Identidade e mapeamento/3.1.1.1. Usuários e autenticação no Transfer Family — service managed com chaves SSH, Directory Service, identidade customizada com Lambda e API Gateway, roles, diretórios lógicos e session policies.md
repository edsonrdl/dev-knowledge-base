### 3.1.1.1. Usuários e autenticação no Transfer Family — service managed com chaves SSH, Directory Service, identidade customizada com Lambda e API Gateway, roles, diretórios lógicos e session policies

> [!warning] Aviso
> Parâmetros de API, formato de respostas do Lambda/API Gateway, limites de chaves por usuário, comportamento de session policies e opções de provedores de identidade abaixo são **de memória e mudam**. **Confirme na documentação do AWS Transfer Family.** Policies, JSONs, funções Lambda e comandos são ilustrativos e **não foram executados**. Nomes de buckets, usuários e roles são fictícios. **Nunca** guarde senhas ou chaves privadas em código ou repositórios.

## 1. O modelo de identidade do Transfer Family

No Transfer Family, **quem é o usuário** e **o que ele pode acessar** são dois conceitos separados:

```
AUTENTICAÇÃO (quem é você?)           AUTORIZAÇÃO (o que você pode?)
 Identity provider:                    Role IAM do usuário  +  Home directory (mapeamento lógico)  +  Session policy
  • Service managed (chaves SSH)        ──────────────────────────────────────────────────────────
  • AWS Directory Service (AD)           Role = permissões de S3/EFS   |   Home = "onde ele começa/o que vê"
  • Lambda (customizado)                 Session policy = restringe a role dinamicamente por sessão
  • API Gateway (customizado)
```

> [!info] Princípio
> **Cada usuário/parceiro** deve **ver apenas o seu espaço** e ter **apenas as permissões necessárias**. A combinação **role + diretórios lógicos + session policy** implementa **isolamento multi-tenant** num **único bucket**.

## 2. Provedores de identidade

| Provedor | Como autentica | Quando usar |
|---|---|---|
| **SERVICE_MANAGED** | **Chaves SSH públicas** (SFTP) cadastradas **no serviço**; **senha não** disponível (nesse modo) | **Poucos/médios** parceiros; **simplicidade**; **sem** identidade corporativa |
| **AWS_DIRECTORY_SERVICE** | **Usuários/grupos do Active Directory** (Managed Microsoft AD ou **AD Connector**) com **senha** | Empresa já usa **AD**; **SFTP/FTPS/FTP** com **credenciais corporativas** |
| **AWS_LAMBDA** | **Função Lambda** valida **credenciais** (usuário/senha ou chave) em **qualquer fonte** (**LDAP, Okta, banco, DynamoDB, Secrets Manager**) e **retorna** role/home/policy | **Integração customizada**; **muitos** usuários; **regras dinâmicas** |
| **API_GATEWAY** | **API REST** (com **Lambda/serviço**) autentica e **responde** com role/home/policy | Quando já existe **API de identidade** ou **segurança de API Gateway** (WAF/ throttling) |

### 2.1 Matriz de decisão

| Critério | Service managed | Directory Service | Lambda/API Gateway |
|---|---|---|---|
| **Autenticação por chave SSH** | **Sim** | Não (senha) | **Sim** (customizável) |
| **Autenticação por senha** | **Não** | **Sim** | **Sim** |
| **Escala de usuários** | Baixa/média (gestão **no serviço**) | **Alta** (AD) | **Muito alta** (externo) |
| **Onboarding/offboarding** | **Manual/IaC** | **AD** (processo corporativo) | **Sistema de origem** |
| **Complexidade** | **Baixa** | Média (AD) | **Maior** (código) |
| **MFA** | Via **chave SSH** (+ controles) | Limitado | **Possível** (customizado, conforme cliente) |
| **Flexibilidade** | Limitada | Média | **Máxima** |
| **Custo** | Baixo | AD (custo do diretório) | Lambda/API (baixo) |

## 3. Service managed (chaves SSH)

### 3.1 Criando usuários

```bash
aws transfer create-user --server-id s-0123456789abcdef0 --user-name parceiro-acme \
  --role arn:aws:iam::123456789012:role/TransferAcmeRole \
  --home-directory-type LOGICAL \
  --home-directory-mappings '[{"Entry":"/","Target":"/bucket-parceiros-123456789012/acme"}]' \
  --ssh-public-key-body "ssh-ed25519 AAAAC3Nz... acme-sftp" \
  --tags Key=parceiro,Value=acme Key=ambiente,Value=prod

aws transfer import-ssh-public-key --server-id s-0123456789abcdef0 --user-name parceiro-acme --ssh-public-key-body "ssh-rsa AAAA... segunda-chave"
aws transfer delete-ssh-public-key --server-id s-0123456789abcdef0 --user-name parceiro-acme --ssh-public-key-id key-abc123
aws transfer list-users --server-id s-0123456789abcdef0
```

### 3.2 Boas práticas

| Prática | Detalhe |
|---|---|
| **Chaves modernas** | **ed25519** ou **RSA ≥ 3072/4096**; evitar **DSA/RSA fraco** |
| **Múltiplas chaves** | Suporta **várias chaves** por usuário (**rotação sem downtime**) |
| **Chave do parceiro** | **Parceiro gera** o par e envia **só a pública** (você nunca recebe a privada) |
| **Rotação** | Política (ex.: anual) — **adicionar nova**, validar, **remover antiga** |
| **IaC** | Criar usuários via **Terraform/CloudFormation** (`AWS::Transfer::User`) |
| **Inventário** | **Dono**, **parceiro**, **data de criação/rotação**, tags |
| **Offboarding** | **Excluir usuário** ao fim do contrato; **auditar** acessos |
| **Sem senha** | **Chaves SSH** são **mais seguras** que senhas |

## 4. Directory Service (Active Directory)

| Aspecto | Detalhe (de memória — confirmar) |
|---|---|
| **Integração** | **AWS Managed Microsoft AD** ou **AD Connector** (proxy ao AD on-premises) |
| **Autenticação** | **Usuário/senha** do AD (SFTP/FTPS/FTP) |
| **Autorização** | **Grupos do AD** **mapeados** a **roles/policies** (por **grupo**): `CreateAccess` associando **ExternalId (SID do grupo)** → **role + home + policy** |
| **Vantagem** | **Reaproveita** identidades corporativas, **GPO/ciclo de vida** |
| **Rede** | Servidor com **endpoint VPC** que alcança o diretório (SGs) |
| **Limitação** | **Chaves SSH** não vêm do AD (para SFTP por chave, use **service managed** ou **Lambda**) |

```bash
# Conceder acesso a um GRUPO do AD (ilustrativo)
aws transfer create-access --server-id s-0123456789abcdef0 \
  --external-id S-1-2-34-567890123-456789012-345678901-1234 \
  --role arn:aws:iam::123456789012:role/TransferFinanceiroRole \
  --home-directory-type LOGICAL \
  --home-directory-mappings '[{"Entry":"/","Target":"/bucket-corp-123456789012/financeiro"}]'
```

## 5. Identidade customizada: Lambda e API Gateway

### 5.1 O fluxo

```
Cliente SFTP ──(usuário + senha/chave)──▶ Transfer Server
        └─▶ invoca LAMBDA (ou API Gateway) com {username, password?, protocol, serverId, sourceIp}
              ├─ valida em LDAP/Okta/DB/Secrets Manager/DynamoDB
              └─ retorna JSON: { Role, HomeDirectoryDetails (mapeamentos), Policy (session), PublicKeys? , Posix (EFS) }
Transfer aplica role/home/policy e libera a sessão
```

### 5.2 Exemplo de Lambda (ilustrativo, Python)

```python
import json, os, boto3, hmac, hashlib
ddb = boto3.resource("dynamodb").Table(os.environ["TABELA_USUARIOS"])

def handler(event, ctx):
    usuario = event["username"]
    senha = event.get("password")           # ausente em autenticação por chave pública
    ip = event.get("sourceIp")
    item = ddb.get_item(Key={"usuario": usuario}).get("Item")
    if not item or not item.get("ativo"):
        return {}                            # resposta vazia = FALHA de autenticação
    if senha is not None:                    # autenticação por senha
        esperado = item["hash_senha"]
        calculado = hashlib.pbkdf2_hmac("sha256", senha.encode(), bytes.fromhex(item["salt"]), 200_000).hex()
        if not hmac.compare_digest(esperado, calculado):
            return {}
    # (se chave pública: retornar PublicKeys para o serviço validar)
    parceiro = item["parceiro"]
    resp = {
        "Role": os.environ["ROLE_ARN"],
        "HomeDirectoryDetails": json.dumps([{"Entry": "/", "Target": f"/{os.environ['BUCKET']}/{parceiro}"}]),
        "Policy": json.dumps({"Version": "2012-10-17", "Statement": [{
            "Effect": "Allow", "Action": ["s3:GetObject", "s3:PutObject", "s3:ListBucket"],
            "Resource": [f"arn:aws:s3:::{os.environ['BUCKET']}", f"arn:aws:s3:::{os.environ['BUCKET']}/{parceiro}/*"]}]})
    }
    if item.get("chaves_publicas"):
        resp["PublicKeys"] = item["chaves_publicas"]
    return resp
```

(Estrutura e campos devem ser **conferidos** na documentação; **não** use hash simples sem salt/iterações adequadas; prefira **provedores de identidade** consolidados.)

### 5.3 Boas práticas de identidade customizada

| Prática | Detalhe |
|---|---|
| **Lógica mínima e rápida** | **Timeout** curto; **sem dependências externas lentas** (afeta o login) |
| **Fonte de verdade** | **IdP corporativo**/DB; **cache** com cuidado |
| **Senhas** | **Nunca em texto**; **hash forte** (bcrypt/argon2/PBKDF2), **rate limiting**, **bloqueio** |
| **Segredos** | **Secrets Manager**; **sem** credenciais no código |
| **Registro (logging)** | **Falhas de autenticação** (sem **vazar** senhas) |
| **Resposta vazia = falha** | Garantir que **erros** **não concedam** acesso |
| **Segurança do Lambda** | **Role mínima**; **VPC** se acessar recursos privados; **resource policy** permitindo **só o serviço Transfer** |
| **API Gateway** | **Autenticação por IAM** (o Transfer assina) ou **chave de API**; **WAF/throttling**; **logs** |
| **Testes** | Cenários **positivos e negativos**; **teste de carga** de login |

### 5.4 MFA

O protocolo **SFTP** padrão **não suporta MFA** interativo nativo no serviço; padrões: **chave SSH + senha** (**autenticação multifator** de **dois fatores** — chave e senha), disponível com **identidade customizada** (de memória; confirmar `SFTP` **“Password and key”**). Controle **compensatório**: **IP allowlist**, **VPN**, **monitoramento**.

## 6. Roles IAM do usuário

### 6.1 O que a role define

A **role** concede acesso ao **armazenamento** (S3/EFS). O **Transfer Family** **assume** a role **em nome do usuário** durante a sessão.

**Trust policy** (permite o serviço assumir):

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": { "Service": "transfer.amazonaws.com" },
    "Action": "sts:AssumeRole",
    "Condition": { "StringEquals": { "aws:SourceAccount": "123456789012" },
                   "ArnLike": { "aws:SourceArn": "arn:aws:transfer:us-east-1:123456789012:user/*" } }
  }]
}
```

**Permissions policy** (S3):

```json
{
  "Version": "2012-10-17",
  "Statement": [
    { "Sid": "ListarSomenteOPropriaPasta", "Effect": "Allow", "Action": "s3:ListBucket",
      "Resource": "arn:aws:s3:::bucket-parceiros-123456789012",
      "Condition": { "StringLike": { "s3:prefix": ["acme/*", "acme"] } } },
    { "Sid": "ObjetosDaPropriaPasta", "Effect": "Allow",
      "Action": ["s3:GetObject", "s3:PutObject", "s3:DeleteObject", "s3:GetObjectVersion"],
      "Resource": "arn:aws:s3:::bucket-parceiros-123456789012/acme/*" },
    { "Sid": "Localizacao", "Effect": "Allow", "Action": "s3:GetBucketLocation", "Resource": "arn:aws:s3:::bucket-parceiros-123456789012" }
  ]
}
```

### 6.2 Uma role por usuário vs role compartilhada com session policy

| Modelo | Vantagens | Desvantagens |
|---|---|---|
| **Role por usuário/parceiro** | **Isolamento explícito**, auditoria clara | **Muitas roles** (limite de roles por conta; gestão) |
| **Role compartilhada + session policy (variáveis)** | **Escala**: **uma role** para **muitos** usuários; a **session policy** restringe pela **pasta do usuário** | **Complexidade** da política; depende de **variáveis** |
| **Role por grupo/perfil** (ex.: “recebe”, “envia”) | Balanceio | Requer **mapeamentos** consistentes |

## 7. Diretórios lógicos e home directory

### 7.1 Tipos

| Tipo | Descrição |
|---|---|
| **PATH** | Home é um **caminho real** (`/bucket/prefixo`); o usuário vê a **estrutura real** (e pode **navegar para cima**, dependendo das permissões) |
| **LOGICAL** | **Mapeamentos** de **caminhos virtuais** para **caminhos reais**; o usuário vê **apenas** o que foi **mapeado** (`/` → `/bucket/acme`) |

> [!tip] Prefira LOGICAL
> **Diretórios lógicos** **escondem** a estrutura real, **impedem** a navegação fora do espaço e simplificam **mover buckets** sem afetar o usuário.

### 7.2 Exemplos de mapeamento

```json
[
  { "Entry": "/",          "Target": "/bucket-parceiros-123456789012/acme" },
  { "Entry": "/entrada",   "Target": "/bucket-parceiros-123456789012/acme/entrada" },
  { "Entry": "/saida",     "Target": "/bucket-parceiros-123456789012/acme/saida" },
  { "Entry": "/referencia","Target": "/bucket-compartilhado-123456789012/catalogos/atual" }
]
```

### 7.3 Variáveis (usuário em mapeamentos e policies)

Podem-se usar variáveis como **`${transfer:UserName}`** (e `${transfer:HomeDirectory}` etc.; confirmar) em **mapeamentos** e **session policies**, permitindo **um modelo único** para **muitos usuários**:

```json
{ "Entry": "/", "Target": "/bucket-parceiros-123456789012/${transfer:UserName}" }
```

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow", "Action": ["s3:GetObject", "s3:PutObject", "s3:DeleteObject"],
    "Resource": "arn:aws:s3:::bucket-parceiros-123456789012/${transfer:UserName}/*"
  }, {
    "Effect": "Allow", "Action": "s3:ListBucket", "Resource": "arn:aws:s3:::bucket-parceiros-123456789012",
    "Condition": { "StringLike": { "s3:prefix": ["${transfer:UserName}/*", "${transfer:UserName}"] } }
  }]
}
```

### 7.4 Isolamento multi-tenant: checklist

- [ ] **LOGICAL** com `Entry="/"` → prefixo do usuário
- [ ] **Role/session policy** limitando **ao prefixo**
- [ ] **Bucket policy** sem **permissões excessivas** a outros principais
- [ ] **Sem acesso** a `ListBucket` fora do prefixo
- [ ] **Teste** com **dois usuários**: **nenhum** vê os dados do outro

## 8. Session policies

| Aspecto | Detalhe |
|---|---|
| **O que é** | **Política passada na sessão** (do usuário ou do **provedor de identidade**) que **restringe** ainda mais a **role** |
| **Regra** | **Permissões efetivas = interseção** (role ∩ session policy) |
| **Uso** | **Reduzir** o acesso por **sessão** (por **usuário**, **grupo**, **horário**, **IP** — conforme o **IdP**) |
| **Limite** | **Tamanho máximo** da policy (confirmar) |
| **Com EFS** | **POSIX (UID/GID)** + **IAM** |

## 9. Acesso a EFS: POSIX

| Aspecto | Detalhe |
|---|---|
| **Identidade POSIX** | **UID/GID** (e grupos secundários) do usuário na sessão |
| **Permissões do sistema de arquivos** | Regras **POSIX** (rwx) do EFS aplicam-se |
| **Role** | Permissões **IAM** de **EFS** (`elasticfilesystem:ClientMount/ClientWrite`) |
| **Mapeamento** | `Posix` no **usuário** (ou na **resposta** do Lambda) |
| **Cuidado** | **UID/GID** consistentes com outras aplicações que montam o EFS |

## 10. Ciclo de vida de usuários (governança)

| Fase | Prática |
|---|---|
| **Onboarding** | **Solicitação aprovada** → **IaC** cria usuário/role/mapeamento/chave → **teste** com o parceiro |
| **Operação** | **Inventário** de usuários, **donos**, **chaves**, **último acesso** (logs) |
| **Rotação** | **Chaves** a cada X meses; **senhas** (se houver) conforme política |
| **Revisão** | **Trimestral**: usuários **inativos**, acessos **excessivos**, parceiros **desligados** |
| **Offboarding** | **Excluir usuário/chaves**; **limpar dados** conforme retenção |
| **Auditoria** | **CloudTrail** (`CreateUser`, `DeleteUser`, `ImportSshPublicKey`), **logs** de sessão |

## 11. Erros comuns

- **Role ampla compartilhada** (todos veem tudo).
- **Home PATH** sem restrições (usuário navega).
- **Sem session policy** em role compartilhada.
- **Senhas fracas/hash inseguro** no Lambda.
- **Lambda lento** ou sem tratamento de erros (login falha/instável).
- **Resposta do Lambda com sucesso por erro** (fail-open).
- **Chaves antigas** nunca removidas.
- **Usuários de parceiros desligados** ainda ativos.
- **Trust policy** sem `aws:SourceAccount/SourceArn`.
- **Esquecer** que **service managed não tem senha**.
- **Diretório lógico** apontando para bucket errado.

## 12. Troubleshooting

| Sintoma | Causa provável | Ação |
|---|---|---|
| `Permission denied` ao listar | Role/session policy/`ListBucket` prefix | Revisar a policy e o prefixo |
| Usuário vê pasta vazia | Mapeamento/Target errado; prefixo inexistente | Conferir `HomeDirectoryMappings` |
| Falha de autenticação por chave | Chave pública incorreta/formato; usuário errado | Conferir a chave (formato OpenSSH) e o usuário |
| Falha de autenticação (Lambda) | Lambda erro/timeout; resposta vazia; permissões | Logs do Lambda; permissões para o Transfer invocar |
| AD: acesso negado | Grupo sem `CreateAccess`; SID incorreto | Mapear o grupo correto |
| EFS: `Permission denied` | UID/GID/POSIX | Ajustar `Posix` e permissões do EFS |
| Assume role falhou | Trust policy | Corrigir a trust policy |
| Muitas falhas de login | Ataque/chaves antigas | Bloquear IPs (SG/WAF), investigar logs |

## 13. Resumo rápido

- **Autenticação**: **service managed** (chaves SSH), **Directory Service** (AD, senha, grupos→roles), **Lambda/API Gateway** (customizado; **resposta vazia = falha**).
- **Autorização**: **role IAM** (trust `transfer.amazonaws.com`) + **home directory** (**LOGICAL** recomendado) + **session policy** (**interseção**).
- **Isolamento multi-tenant**: **LOGICAL** + **prefixo por usuário** (variáveis **`${transfer:UserName}`**) + **role/session policy** limitadas.
- **Chaves**: **ed25519/RSA forte**, **múltiplas** (rotação), **parceiro envia só a pública**.
- **EFS**: **POSIX (UID/GID)** + IAM.
- **Ciclo de vida**: **IaC**, **inventário**, **rotação**, **revisões**, **offboarding**.
- Cuidado com **senhas/hash** em identidade customizada, **fail-open**, **roles amplas**.

## 🧩 Quiz de Fixação

1. Quais provedores de identidade o Transfer Family oferece?
2. Qual a diferença entre home directory PATH e LOGICAL?
3. Como funciona a session policy em relação à role?
4. Como isolar muitos parceiros em um único bucket?
5. Por que a resposta vazia do Lambda é importante?
6. Como o acesso a EFS é controlado?
7. Que práticas se aplicam às chaves SSH dos parceiros?

**Respostas:**

1. Service managed (chaves SSH), AWS Directory Service (AD), AWS Lambda e API Gateway (identidade customizada).
2. PATH usa um caminho real e expõe a estrutura; LOGICAL usa mapeamentos virtuais que escondem a estrutura real e limitam a navegação ao que foi mapeado.
3. A session policy restringe ainda mais a role; as permissões efetivas são a interseção entre a role e a session policy.
4. Com diretórios lógicos que mapeiam a raiz do usuário para seu prefixo, role/session policy limitadas a esse prefixo (por exemplo, com `${transfer:UserName}`), e testes de isolamento.
5. Resposta vazia significa falha de autenticação; garantir que erros não concedam acesso (evita fail-open).
6. Por identidade POSIX (UID/GID) do usuário e permissões do sistema de arquivos, além de permissões IAM da role para o EFS.
7. Usar ed25519 ou RSA forte, múltiplas chaves para rotação sem downtime, o parceiro gerar o par e enviar só a pública, remover chaves antigas e revisar periodicamente.
