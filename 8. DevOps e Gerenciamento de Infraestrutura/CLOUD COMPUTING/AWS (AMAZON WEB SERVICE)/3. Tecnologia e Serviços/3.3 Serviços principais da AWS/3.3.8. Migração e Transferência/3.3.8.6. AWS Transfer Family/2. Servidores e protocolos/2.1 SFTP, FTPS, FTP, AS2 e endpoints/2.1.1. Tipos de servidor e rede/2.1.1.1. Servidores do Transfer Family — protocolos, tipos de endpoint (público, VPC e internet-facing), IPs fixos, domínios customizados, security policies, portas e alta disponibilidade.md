### 2.1.1.1. Servidores do Transfer Family — protocolos, tipos de endpoint (público, VPC e internet-facing), IPs fixos, domínios customizados, security policies, portas e alta disponibilidade

> [!warning] Aviso
> Tipos de endpoint, regras de portas, nomes de security policies, limites e opções de domínio customizado abaixo são **de memória e mudam**. **Confirme na documentação do AWS Transfer Family.** Comandos e esquemas de rede são ilustrativos e **não foram executados**. IPs, domínios, VPCs e IDs são fictícios. Mudar o tipo de endpoint de um servidor em produção pode **interromper parceiros**: planeje DNS e janela.

## 1. Um servidor, muitas decisões

Criar um servidor no Transfer Family é simples; **acertar a configuração de rede e segurança** é o que evita **dores com parceiros**. As decisões principais:

```
Servidor Transfer Family
  ├─ PROTOCOLOS:       SFTP • FTPS • FTP • AS2
  ├─ ENDPOINT:         público  |  VPC (interno)  |  VPC internet-facing (IPs elásticos)
  ├─ DOMÍNIO/HOSTNAME: padrão (s-xxxx.server.transfer.<região>.amazonaws.com) ou customizado (Route 53 / DNS externo)
  ├─ IDENTIDADE:       service managed | Directory Service | Lambda | API Gateway
  ├─ ARMAZENAMENTO:    S3 | EFS
  ├─ SECURITY POLICY:  algoritmos SSH/TLS permitidos
  └─ LOGGING:          CloudWatch (estruturado) • CloudTrail
```

## 2. Protocolos e o que cada um exige

| Protocolo | Porta(s) | Requisitos | Observações |
|---|---|---|---|
| **SFTP** | **22** (TCP) | Chaves SSH/senha; **host key** do servidor | Mais simples; **um único canal** (bom para firewalls) |
| **FTPS** | **21** (controle) + **portas passivas** de dados (ex.: **8192–8200**; confirmar) | **Certificado TLS (ACM)**; **modo passivo**; endpoint **VPC** ou público conforme suporte | Mais complexo por **múltiplas portas** e **NAT** |
| **FTP** | **21** + **passivas** | **Somente VPC** | **Sem criptografia** |
| **AS2** | **HTTPS** (portas **5080** em uso interno do endpoint AS2; **443** via **front-end** — confirmar) | **Certificados** (assinatura/criptografia), **parceiros**, **acordos** | Para **EDI** |

> [!warning] Combinar protocolos num mesmo servidor
> Um servidor pode **habilitar vários protocolos** (ex.: SFTP+FTPS), mas **cada protocolo** é **cobrado por hora**; **FTP** só com **endpoint VPC**; **mistura** de protocolos exige **cuidado** com **política de segurança**, **identidade** e **portas**. **Separar servidores por protocolo/parceiro** simplifica **isolamento e custos** em muitos casos.

## 3. Tipos de endpoint

### 3.1 Comparação

| Tipo | Descrição | Acesso | IP | Protocolos | Quando usar |
|---|---|---|---|---|---|
| **Público** (publicly accessible) | Endpoint **gerenciado pela AWS** na internet | **Internet** | **IPs dinâmicos** (mudam) | **SFTP, (FTPS com restrições?)**, AS2 (confirmar) | **Simplicidade**; parceiros **sem allowlist de IP** |
| **VPC – internal** | Endpoint **dentro da sua VPC** (ENIs privadas) | **Somente rede privada** (VPC/peering/VPN/DX) | **IPs privados** | **SFTP, FTPS, FTP, AS2** | **Acesso interno**, parceiros via **VPN/DX** |
| **VPC – internet-facing** | Endpoint **em VPC** com **Elastic IPs** | **Internet** (via EIPs) | **IPs fixos (EIPs)** | **SFTP, FTPS, (FTP?)** | **Parceiros exigem allowlist de IP**; controle com **Security Groups** |
| **VPC endpoint (legado)** | Modelo **antigo** (PrivateLink/VPC endpoint) | — | — | — | **Descontinuado/legado** (prefira **VPC hosted**; confirmar) |

### 3.2 VPC hosted: como funciona

```
Parceiro ──Internet──▶ Elastic IP(s) (1 por AZ) ──▶ ENIs do endpoint Transfer (subnets em AZs) ──▶ servidor ──▶ S3/EFS
              ▲                                       │ Security Group do endpoint (origens permitidas)
        DNS (CNAME → s-xxxx.server.transfer…) ou A record → EIPs
```

| Aspecto | Detalhe (de memória — confirmar) |
|---|---|
| **Subnets** | Escolha **2–3 subnets** em **AZs diferentes** (HA) |
| **Elastic IPs** | **1 por AZ** (internet-facing); **IPs previsíveis** para **allowlist** |
| **Security groups** | **Controlam as origens** (CIDRs de parceiros) e **portas** |
| **Rota para o S3** | **Via VPC endpoint gateway S3** ou internet; o serviço usa **rede da AWS** |
| **DNS** | **Hostname padrão** do servidor resolve para **IPs** do endpoint |
| **Custos** | **Endpoint VPC** pode ter **custos adicionais** (ENIs/EIPs/transferência); o **servidor** é cobrado por hora de protocolo |
| **Mudança** | Trocar o **tipo** de endpoint exige **parar** o servidor e **atualizar** o endpoint (ou recriar); impacto em **parceiros** |

### 3.3 Escolha prática

| Cenário | Endpoint |
|---|---|
| **Parceiros sem restrições de IP** | **Público** |
| **Parceiros exigem IP fixo (allowlist)** | **VPC internet-facing** com **EIPs** |
| **Somente rede privada** (VPN/DX/peering) | **VPC internal** |
| **FTP** (legado) | **VPC internal** (dentro de rede privada) |
| **AS2** | Conforme documentação (**público** ou **VPC**) |
| **Controle de origem por CIDR** | **VPC** + **Security Groups** |
| **Inspeção/WAF** | **NLB/Network Firewall** na frente (cenários avançados) |

## 4. IPs fixos e allowlists

Muitos **parceiros B2B** exigem **IPs fixos** para liberar no firewall deles.

| Estratégia | Detalhe |
|---|---|
| **VPC internet-facing + Elastic IPs** | **EIPs** associados ao endpoint; **comunicar** os IPs ao parceiro; **não liberar** a EIP (mantém **estável**) |
| **Domínio estável** | **CNAME/Alias** apontando ao servidor → **mudanças internas** não afetam o parceiro |
| **Segurança em camadas** | **SG** do endpoint limitando **CIDRs** dos parceiros; **WAF/NLB** se necessário |
| **IPs de saída (conectores)** | Para **conectores** (envio), IPs de **saída** do serviço (confirmar se **estáticos**/lista publicada) — **parceiros precisam liberar** o **egress** |

## 5. Domínios e hostnames customizados

### 5.1 O que se resolve

O hostname padrão (`s-0123456789abcdef0.server.transfer.us-east-1.amazonaws.com`) é **feio e inalterável**; migrar um SFTP legado exige **manter o nome** (`sftp.suaempresa.com`) para **não reconfigurar parceiros**.

| Opção | Detalhe |
|---|---|
| **Route 53** | **Alias/CNAME** `sftp.suaempresa.com` → endpoint do servidor; o serviço **suporta** mapear o **hostname customizado** (configuração do servidor com `Route53`, para **rastreamento** no CloudWatch) |
| **DNS externo** | **CNAME** apontando ao hostname do servidor |
| **Hostname em logs/métricas** | Configure **Custom Hostname** (**tipo de provedor**: Route 53 / outro) para **registrar** o nome usado |
| **Certificado (FTPS)** | **ACM** com o **nome customizado** |
| **Host key** | **Importar chaves de host** do SFTP **legado** para os clientes **não alertarem** de mudança de chave |

```bash
aws transfer update-server --server-id s-0123456789abcdef0 \
  --protocol-details 'PassiveIp=203.0.113.10,TlsSessionResumptionMode=ENFORCED'
aws transfer tag-resource --arn arn:aws:transfer:us-east-1:123456789012:server/s-0123456789abcdef0 \
  --tags Key=aws:transfer:customHostname,Value=sftp.suaempresa.com Key=aws:transfer:route53HostedZoneId,Value=/hostedzone/Z123
```

(Mecanismo de **custom hostname** por **tags**: confirmar na documentação atual.)

### 5.2 Migração de SFTP legado sem impacto

1. **Exportar** a **host key** do servidor legado e **importar** no Transfer (`ImportHostKey`).
2. **Recriar usuários** e **chaves públicas** (migração de chaves).
3. Configurar **diretórios** e **roles** equivalentes.
4. **Testar** com **parceiros piloto** (hostname temporário).
5. **Cutover de DNS**: reduzir **TTL**, apontar `sftp.suaempresa.com` ao servidor Transfer.
6. **Monitorar** falhas de login/host key.
7. **Desligar** o servidor legado após **período de segurança**.

## 6. Security policies

### 6.1 O que definem

A **security policy** controla **algoritmos permitidos** (SSH: **KEX, ciphers, MACs, host key algorithms**; TLS: **versões e suítes**) e **recursos** (FIPS, pós-quântico).

| Aspecto | Detalhe (de memória — confirmar nomes/versões) |
|---|---|
| **Nomes** | `TransferSecurityPolicy-2024-01`, `-FIPS-2024-01`, `-PQ-SSH-Experimental-...`, `-Restricted-...` |
| **Escolha** | **Política mais recente** compatível com os **clientes dos parceiros** |
| **FIPS** | Políticas **FIPS** para **conformidade federal/regulada** (endpoint FIPS regional; confirmar) |
| **Algoritmos legados** | Parceiros **antigos** podem exigir algoritmos **fracos**: avaliar **exceção** **temporária** e **plano de migração** |
| **Atualizações** | **Revisar** periodicamente (novas políticas, depreciações) |
| **Testes** | Verificar **compatibilidade** com clientes **reais** antes de endurecer |

```bash
aws transfer update-server --server-id s-0123456789abcdef0 --security-policy-name TransferSecurityPolicy-2024-01
aws transfer describe-security-policy --security-policy-name TransferSecurityPolicy-2024-01
```

### 6.2 Host keys

| Aspecto | Detalhe |
|---|---|
| **O que é** | **Identidade** do servidor SFTP; o cliente **memoriza** (`known_hosts`) e **alerta** se mudar |
| **Padrão** | O serviço **gera** chaves de host (RSA/ECDSA/ED25519, conforme a política) |
| **Importar** | Para **migrações** (manter a mesma chave) |
| **Rotação** | Rotacionar exige **comunicar parceiros** (**alerta de MITM** no cliente) |
| **Boa prática** | **Documentar fingerprints** e **publicá-los** aos parceiros por **canal seguro** |

## 7. FTPS: certificado e modo passivo

| Ponto | Detalhe |
|---|---|
| **Certificado** | **ACM** (público ou **importado**) com o **nome do servidor/hostname** |
| **Modo passivo** | O servidor informa **IP e porta** para o canal de dados; configurar **PassiveIp** (o **EIP**/IP público/privado correto) |
| **Portas** | Faixa de **portas passivas** (ex.: **8192–8200**) abertas no **SG/NACL/firewall** |
| **NAT/Firewall do cliente** | Muitos erros vêm do **cliente** atrás de NAT; **modo passivo estendido** |
| **TLS** | **Resumption**/`TlsSessionResumptionMode` (configuração para **compatibilidade**) |
| **Teste** | `openssl s_client`, clientes **FileZilla/lftp** com **logs** |

## 9. Alta disponibilidade e resiliência

| Aspecto | Detalhe |
|---|---|
| **Multi-AZ** | O serviço **distribui** o endpoint por **AZs** (público: gerenciado; VPC: **subnets** em ≥2 AZs) |
| **Falha de AZ** | **Failover** automático (IPs dos EIPs mudam de AZ? — com **EIPs por AZ**, clientes **tentam** múltiplos IPs ou o DNS **ajuda**) |
| **Região** | Servidor **regional**; para **DR cross-region**: **segundo servidor** em outra região + **DNS failover** (Route 53) + **dados** (S3 **CRR**) |
| **S3** | **11 noves** de durabilidade; **CRR** para DR |
| **Clientes** | Implementar **retries** e **reconnects** (arquivos grandes) |
| **Monitoramento** | **Health checks** sintéticos (login + upload/download) |

### 9.1 DR cross-region (padrão)

```
Região A: Transfer server + S3 bucket (CRR →)   ──────────▶   Região B: Transfer server (standby) + S3 bucket réplica
DNS: Route 53 failover (health check do servidor A) → B em falha; usuários/chaves replicados (IaC/pipeline)
```

Cuidados: **usuários/chaves** devem estar **replicados** (IaC); **host keys** **iguais** nos dois servidores (evita alertas); **IPs diferentes** (parceiros com allowlist precisam liberar **ambos**); **testes periódicos**.

## 10. Exemplos de arquitetura

### 10.1 SFTP público simples

```
Parceiros ──SFTP──▶ Endpoint público ──▶ S3 (prefixo por parceiro) ──▶ EventBridge/Lambda ──▶ processamento
Identidade: service managed (chaves SSH)  •  Logs: CloudWatch estruturado
```

### 10.2 SFTP com IP fixo e controle de origem

```
Parceiros (allowlist) ──SFTP──▶ EIPs (VPC internet-facing, SG com CIDRs dos parceiros) ──▶ S3
Domínio: sftp.suaempresa.com (Route 53) • Security policy mais restritiva • Host key importada
```

### 10.3 Acesso privado (VPN/DX)

```
Datacenter on-prem ──VPN/DX──▶ Endpoint VPC internal ──▶ S3 (via VPC endpoint) — FTP/FTPS/SFTP internos
```

## 11. Erros comuns

- **Endpoint público** quando o parceiro exige **IP fixo**.
- **Esquecer SG/NACL** (VPC) → timeouts.
- **Troca de host key** sem avisar → alertas **MITM**.
- **Security policy** incompatível com **clientes legados** (quebra) ou **fraca demais** sem plano.
- **FTPS sem passive IP/portas** corretos.
- **Hostname padrão** distribuído a parceiros (impossível mudar depois).
- **TTL de DNS alto** no cutover.
- **Habilitar protocolos desnecessários** (custo e superfície).
- **Servidor único para todos os parceiros** (sem isolamento).
- **DR sem testar**.

## 12. Troubleshooting

| Sintoma | Causa provável | Ação |
|---|---|---|
| `Connection timed out` | SG/NACL/rota; IP/porta; allowlist do parceiro | Revisar SG, rotas e firewall do parceiro |
| `Host key verification failed` | Host key mudou | Restaurar a chave importada; comunicar parceiros |
| `No matching key exchange/cipher` | Security policy × cliente | Ajustar a política ou atualizar o cliente |
| FTPS: lista de diretórios trava | Modo passivo/portas/NAT | Configurar PassiveIp e portas; testar com clientes |
| DNS não resolve para o servidor | CNAME/Alias errado; TTL | Corrigir o DNS |
| Servidor “OFFLINE/STARTING” | Mudança de endpoint/erro de configuração | Ver o estado/eventos; revisar a config |
| Mudou o IP e o parceiro bloqueou | Endpoint público dinâmico | Migrar para VPC com EIPs |
| AS2 falha em MDN | Certificados/perfil/URL | Revisar perfis, certificados e URLs |

## 13. Resumo rápido

- **Servidor** = **protocolos** (SFTP 22; FTPS 21 + passivas; FTP só VPC; AS2) + **endpoint** + **identidade** + **security policy** + **logging** + **armazenamento (S3/EFS)**.
- **Endpoints**: **público** (simples, IP dinâmico), **VPC internal** (privado), **VPC internet-facing** (**EIPs** para allowlist, **SG** por origem).
- **Domínio customizado** (Route 53/DNS) + **host key importada** → **migração de SFTP legado sem impacto**; **TTL baixo** no cutover.
- **Security policy**: mais recente compatível; **FIPS**/pós-quântico quando exigido; testar com clientes reais.
- **FTPS**: **ACM**, **modo passivo**, **portas**; **AS2**: **perfis/certificados/acordos**/MDN.
- **HA**: **multi-AZ**; **DR cross-region** com **segundo servidor + Route 53 + CRR**.
- Dica: **um servidor por protocolo/risco** simplifica **isolamento e custos**.

## 🧩 Quiz de Fixação

1. Quais as diferenças entre endpoint público, VPC internal e VPC internet-facing?
2. Quando escolher VPC com Elastic IPs?
3. Por que importar a host key ao migrar um SFTP legado?
4. O que é modo passivo no FTPS e por que causa problemas?
5. Para que serve a security policy?
6. Como organizar um DR cross-region?
7. Por que reduzir o TTL do DNS antes do cutover?

**Respostas:**

1. Público: endpoint na internet gerenciado pela AWS com IPs dinâmicos; VPC internal: acessível só por rede privada; VPC internet-facing: em VPC com Elastic IPs fixos e controle por security groups.
2. Quando parceiros exigem IP fixo para allowlist ou quando se quer controlar origens com SGs.
3. Para que os clientes não vejam alerta de mudança de chave (possível MITM) e continuem conectando sem reconfiguração.
4. É o modo em que o servidor informa IP e porta para o canal de dados; exige faixa de portas abertas e IP passivo correto, e falha com NAT/firewall mal configurados.
5. Define os algoritmos de SSH/TLS permitidos (e opções como FIPS), equilibrando segurança e compatibilidade com os clientes.
6. Com um segundo servidor em outra região, dados replicados (S3 CRR), usuários/chaves e host keys replicados por IaC e Route 53 com health check para failover, testando periodicamente.
7. Para que a mudança do endpoint se propague rapidamente aos clientes, reduzindo o tempo de indisponibilidade ou inconsistência durante a troca.
