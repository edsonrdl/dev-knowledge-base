### 2.1.1.1. Agentes e locations no DataSync — implantação do agent, ativação, endpoints públicos e VPC, locations NFS, SMB, HDFS, S3, EFS e FSx e requisitos de rede

> [!warning] Aviso
> Os comandos, portas, requisitos de hardware e parâmetros abaixo são **ilustrativos e não foram executados**. Requisitos de CPU/RAM do agente, portas e versões suportadas de hipervisores mudam; consulte a documentação oficial do DataSync antes de implantar. Montar compartilhamentos de produção exige credenciais com o mínimo privilégio e aprovação da equipe de storage.

## 1. O papel do agent

O **DataSync agent** é uma **máquina virtual** (ou instância EC2) que atua como **ponte** entre o seu storage e o serviço DataSync na AWS. Ele:

- **Monta** (ou acessa) a origem por NFS, SMB, HDFS ou API de objeto.
- **Lê** e **organiza** os dados, aplicando o protocolo de transferência do DataSync.
- **Envia** os dados ao serviço por conexão TLS, com paralelismo e compressão.
- **Reporta** estado e progresso.

O agent é necessário quando **a origem ou o destino não é um serviço de storage AWS acessível diretamente** (NAS local, HDFS, outra nuvem). Para **S3, EFS e FSx** entre si, o próprio serviço faz a transferência, **sem agent**.

### 1.1 Onde implantar

| Plataforma | Uso típico |
|---|---|
| **VMware ESXi** | Datacenters VMware (OVA) |
| **Microsoft Hyper-V** | Ambientes Windows/Hyper-V (VHD) |
| **Linux KVM** | Ambientes KVM (imagem qcow2) |
| **Amazon EC2** | Origem em outra nuvem, ou origem em EC2/AWS acessada por rede, ou teste |
| **AWS Snowcone** | Edge e locais com conectividade limitada (agente pré-instalado) |
| **AWS Outposts** | Agent em instância no Outpost |

**Regra de posicionamento:** coloque o agent **o mais perto possível do storage de origem** (mesma rede/VLAN, com banda alta até o NAS). A latência e a banda entre o agent e o NAS afetam diretamente a velocidade; já o caminho agent → AWS costuma ser o limite externo.

### 1.2 Dimensionamento do agent

O agent é CPU/RAM-intensivo em milhões de arquivos (o **inventário e a comparação** usam memória). Pontos gerais (valores indicativos; confirmar na documentação):

- Cargas pequenas/médias: **4 vCPU e 32 GB de RAM** são um piso comum em muitas orientações.
- Cargas com **dezenas de milhões de arquivos**: mais RAM (por exemplo, 64–128 GB) para evitar lentidão e falhas de inventário.
- **Disco**: espaço pequeno para sistema e cache.
- **Rede**: interface de 10 Gbps se o objetivo é saturar links grandes.

Para throughput agregado alto, use **vários agents** em paralelo, cada um com tarefas diferentes (divisão por subárvore de diretórios).

## 2. Ativação do agent

O agent precisa ser **ativado** para se associar à sua conta e região AWS. O fluxo:

```
1. Baixa a imagem (OVA/VHD/qcow2/AMI) e implanta a VM
2. Liga a VM (obtém IP por DHCP ou configura IP fixo)
3. Obtém a chave de ativação:
     a) acessando http://<ip-do-agent>/?gatewayType=SYNC&activationRegion=<região>&endpointType=<tipo>
     b) ou pelo console local do agent
4. Chama create-agent com a chave
5. O agent passa a "ONLINE" no console
```

Exemplo ilustrativo de ativação por CLI:

```bash
aws datasync create-agent \
  --agent-name agent-nas-sp \
  --activation-key ABCDE-12345-FGHIJ-67890-KLMNO \
  --vpc-endpoint-id vpce-0abc \
  --subnet-arns arn:aws:ec2:us-east-1:123456789012:subnet/subnet-0abc \
  --security-group-arns arn:aws:ec2:us-east-1:123456789012:security-group/sg-0abc
```

> [!tip] Dica
> Em ambientes sem acesso HTTP direto ao agent a partir da estação de trabalho, a chave pode ser obtida **a partir da própria rede do agent** (por exemplo, `curl` de um host que alcance a VM). O importante é que a **região de ativação** e o **tipo de endpoint** correspondam ao que você pretende usar.

## 3. Tipos de endpoint: público, FIPS e VPC

A conexão entre o agent e o serviço DataSync pode usar:

| Endpoint | Caminho | Quando usar |
|---|---|---|
| **Público** | Pela internet, com TLS, para endpoints públicos do DataSync | Simplicidade; quando política permite saída para a internet |
| **FIPS** | Endpoints públicos compatíveis com FIPS 140-2 | Requisitos regulatórios dos EUA |
| **VPC (PrivateLink)** | Pelo **interface VPC endpoint** do DataSync, via Direct Connect ou VPN | **Sem trafegar pela internet**; segurança e previsibilidade |

Com **VPC endpoint**, o tráfego do agent chega à AWS pela rede privada (via Direct Connect/VPN até a VPC) e o endpoint é protegido por **security groups**. É a opção preferida em ambientes regulados.

### 3.1 Requisitos de rede (resumo)

| Origem → destino | Porta/protocolo | Finalidade |
|---|---|---|
| Agent → serviço DataSync (público) | **TCP 443** | Controle e dados |
| Agent → VPC endpoint | **TCP 443**, e portas de dados **1024–1064** | Controle e canais de dados via PrivateLink |
| Agent → NAS NFS | **TCP/UDP 2049** (e portmapper 111, conforme versão) | Leitura NFS |
| Agent → servidor SMB | **TCP 445** | Leitura SMB |
| Agent → HDFS (NameNode/DataNodes) | Portas do cluster (ex.: 8020, 50010...) | Leitura HDFS |
| Estação → agent (ativação) | **TCP 80** (temporário) | Obter a chave |
| Agent → NTP e DNS | **UDP 123 / 53** | Hora e resolução de nomes |

A sincronização de **hora (NTP)** é importante: diferenças grandes de relógio podem causar falhas de ativação e de TLS.

Diagrama de caminho privado:

```
NAS ── LAN ── Agent ── Direct Connect/VPN ── VPC ── VPC endpoint (DataSync) ──▶ Serviço ──▶ S3/EFS/FSx
```

## 4. Locations: tipos e configuração

Cada **location** descreve um lado da transferência. As principais:

### 4.1 NFS

```bash
aws datasync create-location-nfs \
  --server-hostname nas01.empresa.local \
  --subdirectory /export/dados \
  --on-prem-config AgentArns=arn:aws:datasync:...:agent/agent-0abc \
  --mount-options Version=NFS4_1
```

Requisitos: o **export NFS** deve permitir leitura do IP do agent (e escrita, se for destino); atenção a `root_squash` e a UID/GID para preservar permissões.

### 4.2 SMB

```bash
aws datasync create-location-smb \
  --server-hostname fs01.empresa.local \
  --subdirectory /share/financeiro \
  --user svc-datasync \
  --domain EMPRESA \
  --password '********' \
  --agent-arns arn:aws:datasync:...:agent/agent-0abc
```

O usuário precisa de **leitura** (e **backup operator/privilégios** para ler ACLs e proprietários, se for preservar metadados NTFS). Evite senhas em linha de comando em uso real (use ferramentas de segredos).

### 4.3 HDFS

Informa o **NameNode** (host e porta), o tipo de autenticação (simples ou **Kerberos**) e o agent com acesso ao cluster. Útil para migrar data lakes Hadoop para S3.

### 4.4 Object storage (genérico S3-compatível)

Para outras nuvens e storages de objeto: endpoint, bucket, chaves de acesso e agent. Serve como origem (e, em alguns casos, destino) quando há compatibilidade com a API S3.

### 4.5 Azure Blob Storage

Origem (e destino, conforme suporte) com **token SAS** e agent.

### 4.6 Amazon S3

```bash
aws datasync create-location-s3 \
  --s3-bucket-arn arn:aws:s3:::meu-bucket \
  --subdirectory /prefixo \
  --s3-storage-class INTELLIGENT_TIERING \
  --s3-config BucketAccessRoleArn=arn:aws:iam::123456789012:role/datasync-s3-role
```

- **Classe de armazenamento** do destino definida na location (STANDARD, STANDARD_IA, INTELLIGENT_TIERING, GLACIER_IR, GLACIER, DEEP_ARCHIVE...).
- A **role** precisa de `s3:GetObject`, `PutObject`, `ListBucket`, `GetBucketLocation` etc. no bucket/prefixo.
- Buckets de **outra conta** exigem política de bucket que autorize a role do DataSync.

### 4.7 Amazon EFS

```bash
aws datasync create-location-efs \
  --efs-filesystem-arn arn:aws:elasticfilesystem:us-east-1:123456789012:file-system/fs-0abc \
  --ec2-config SubnetArn=arn:aws:ec2:...:subnet/subnet-0abc,SecurityGroupArns=arn:aws:ec2:...:security-group/sg-0abc \
  --access-point-arn arn:aws:elasticfilesystem:...:access-point/fsap-0abc
```

O DataSync cria **interfaces de rede (ENIs)** na sub-rede indicada para montar o EFS; o security group precisa permitir **NFS (2049)** entre o DataSync e os mount targets.

### 4.8 FSx (Windows, Lustre, OpenZFS, ONTAP)

Cada tipo tem sua location (`create-location-fsx-windows`, `create-location-fsx-lustre`, `create-location-fsx-open-zfs`, `create-location-fsx-ontap`), com o ARN do sistema de arquivos, security groups e (no Windows) usuário/domínio com permissões administrativas para preservar ACLs.

## 5. Matriz de metadados por par origem/destino

| Origem | Destino | O que costuma ser preservado |
|---|---|---|
| NFS | S3 | Timestamps e UID/GID/permissões POSIX guardados como metadados do objeto |
| NFS | EFS/FSx OpenZFS | Permissões POSIX, UID/GID, timestamps |
| SMB | FSx Windows | ACLs NTFS, proprietário, atributos, timestamps |
| SMB | S3 | Timestamps (ACLs não existem em S3; podem ser perdidas) |
| S3 | S3 | Metadados de objeto, tags, classe de armazenamento (conforme opções) |
| HDFS | S3 | Estrutura de diretórios como prefixos; permissões como metadados |
| EFS | S3 | Metadados POSIX como metadados do objeto |

Regra: **preserve o que o destino consegue representar**. Para migrar um file server Windows mantendo ACLs, o destino natural é o **FSx for Windows File Server**, não o S3.

## 6. Alta disponibilidade e múltiplos agents

- Uma location pode referenciar **mais de um agent** (por exemplo, `AgentArns` com dois ou mais), que cooperam para aumentar o throughput e dar redundância.
- **Divida** grandes árvores em **várias tarefas** com **filtros** (por exemplo, por pasta), cada uma com seu agent.
- Em falha do agent, a execução é interrompida; **reexecutar** a tarefa retoma de forma incremental (o que já foi copiado não é recopiado).

## 7. Operação do agent

| Tarefa | Como |
|---|---|
| Ver estado | Console ou `aws datasync describe-agent` |
| Atualizar | O serviço atualiza o agent automaticamente (política de manutenção) |
| Recriar | Se necessário, criar outro agent e trocar nas locations |
| Excluir | `aws datasync delete-agent` após o fim da migração |
| Logs | Console local do agent e **CloudWatch Logs** (tarefas e agent) |
| Testar conectividade | Console local: testar rota para o endpoint, NTP e origem |

Verifique o status com:

```bash
aws datasync list-agents
aws datasync describe-agent --agent-arn arn:aws:datasync:...:agent/agent-0abc
```

## 8. Erros comuns

> [!bug] Erros comuns
> 1. **Agent longe do NAS**, limitando a velocidade por latência/banda interna.
> 2. **Agent subdimensionado** em RAM, falhando em milhões de arquivos.
> 3. **Esquecer a porta 443 (e 1024–1064 no VPC endpoint)** nos firewalls.
> 4. **Relógio do agent sem NTP**, causando falhas de ativação/TLS.
> 5. **Export NFS sem permissão para o IP do agent** ou com `root_squash` quebrando leitura.
> 6. **Usuário SMB sem privilégio** para ler ACLs, perdendo metadados.
> 7. **Role do S3 sem acesso ao bucket/prefixo**, ou bucket de outra conta sem política.
> 8. **Escolher S3 como destino quando as ACLs NTFS precisam ser preservadas.**
> 9. **Criar agent para S3 → S3**, sem necessidade.
> 10. **Deixar o agent ativo após o projeto**, mantendo uma VM com acesso amplo ao NAS.

## 9. Troubleshooting

| Sintoma | Causa provável | Ação |
|---|---|---|
| Ativação falha | Chave expirada, região/endpoint errados, relógio | Gerar nova chave e conferir região, tipo de endpoint e NTP |
| Agent "offline" | Rota/porta bloqueada | Testar 443 para o endpoint; verificar proxy/firewall |
| Não consegue montar NFS | Export/rede/versão NFS | Verificar export, `showmount`, firewall 2049/111 e a versão (NFS4_1) |
| SMB "access denied" | Credencial ou privilégio | Usar conta com leitura e privilégios de backup |
| Muito lento na origem | Agent com pouca RAM/CPU ou NAS saturado | Aumentar recursos e escalonar horário |
| EFS location falha | Security group/sub-rede incorretos | Permitir 2049 e usar sub-rede com mount target |

## 10. Resumo rápido

- O **agent** (VM ou EC2) liga o storage de origem ao serviço; fica **perto da origem** e é dispensável entre serviços AWS.
- A **ativação** associa o agent à conta/região; escolha o **endpoint** (público, FIPS ou **VPC/PrivateLink**).
- **Rede**: 443 (e 1024–1064 no VPC endpoint), 2049 NFS, 445 SMB, NTP e DNS.
- **Locations**: NFS, SMB, HDFS, object storage, Azure Blob, S3, EFS e FSx, cada uma com requisitos próprios.
- **Metadados** só se preservam onde o destino os representa; use **vários agents** e **várias tarefas** para escalar.

**Respostas:**

1. O mais perto possível, na mesma rede, com banda alta e baixa latência até o NAS.
2. Entre serviços AWS que o DataSync acessa diretamente (S3, EFS, FSx entre si).
3. Público, FIPS e VPC (PrivateLink).
4. TCP 443 e as portas de dados 1024–1064.
5. Porque o S3 não representa ACLs NTFS; o FSx for Windows as preserva.
6. Acesso ao bucket/prefixo: ListBucket, GetBucketLocation, Get/PutObject e correlatos.
7. Usando vários agents na location e dividindo a árvore em várias tarefas com filtros.
