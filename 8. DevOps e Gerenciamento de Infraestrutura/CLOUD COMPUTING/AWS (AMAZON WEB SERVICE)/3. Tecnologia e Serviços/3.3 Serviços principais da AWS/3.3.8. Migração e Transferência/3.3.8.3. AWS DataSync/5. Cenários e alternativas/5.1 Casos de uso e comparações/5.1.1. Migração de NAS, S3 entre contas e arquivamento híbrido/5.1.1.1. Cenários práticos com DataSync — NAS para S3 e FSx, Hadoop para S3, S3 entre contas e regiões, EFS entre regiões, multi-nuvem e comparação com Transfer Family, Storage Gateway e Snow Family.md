### 5.1.1.1. Cenários práticos com DataSync — NAS para S3 e FSx, Hadoop para S3, S3 entre contas e regiões, EFS entre regiões, multi-nuvem e comparação com Transfer Family, Storage Gateway e Snow Family

> [!warning] Aviso
> Os comandos, arquiteturas e números abaixo são **ilustrativos e não foram executados**. Cada cenário depende do hardware, dos volumes e das políticas da sua organização; adapte e valide em ambiente de teste. Verifique os pares de locations e modos de tarefa suportados na documentação atual antes de projetar.

## 1. Como escolher a ferramenta certa antes do cenário

O AWS tem várias formas de mover e acessar arquivos. A escolha errada custa tempo e dinheiro. As perguntas-chave:

1. É **uma migração única**, **recorrente** ou **acesso contínuo**?
2. O volume é compatível com a **banda** disponível, ou exige transporte **offline**?
3. Preciso de **protocolo de arquivo** (SFTP/NFS/SMB) para pessoas e sistemas?
4. Preciso preservar **metadados e ACLs**?
5. É dado de **banco de dados** (outra ferramenta)?

| Necessidade | Ferramenta |
|---|---|
| Copiar em massa, online, com verificação e agenda | **DataSync** |
| Volumes enormes sem rede suficiente | **Snow Family** |
| Parceiros externos enviando/baixando por SFTP/FTPS/AS2 para S3/EFS | **Transfer Family** |
| Acesso híbrido contínuo com cache local (arquivo, volume, fita) | **Storage Gateway** |
| Replicação contínua dentro do S3 | **S3 Replication** |
| Operações em massa sobre objetos S3 (copiar, tag, restaurar) | **S3 Batch Operations** |
| Migração de banco de dados | **DMS** |
| Servidores inteiros | **MGN** |

## 2. Cenário A — Migrar um file server NAS (NFS) para o Amazon S3 (arquivo e data lake)

**Objetivo:** mover 80 TB de projetos antigos de um NAS NFS para S3, com custo baixo e acesso ocasional.

```
NAS NFS ── LAN ── DataSync Agent ── Direct Connect/Internet ──▶ DataSync ──▶ S3 (STANDARD_IA / Glacier IR)
```

Passos:

1. **Implantar o agent** (VM) próximo ao NAS e ativar.
2. Criar **location NFS** (origem) e **location S3** (destino) com **classe de armazenamento** `STANDARD_IA` ou `INTELLIGENT_TIERING`.
3. Criar a **tarefa** com `TransferMode=CHANGED`, `VerifyMode=ONLY_FILES_TRANSFERRED`, **limite de banda** e **excludes** de temporários.
4. Rodar a carga inicial; depois, incrementais agendadas.
5. Aplicar **S3 Lifecycle** para mover dados frios a Glacier/Deep Archive.
6. Validar com **task reports** e conciliação (contagem/tamanho).

Pontos de atenção:

- Permissões POSIX e timestamps vão como **metadados do objeto**; o S3 não aplica permissões POSIX, então o controle de acesso deve migrar para **IAM/bucket policies/ACL de prefixo**.
- Defina **estrutura de prefixos** pensando em consultas futuras (Athena) e em throttling.
- Se os dados serão analisados, considere **Parquet/ORC** depois da migração com Glue.

## 3. Cenário B — Migrar file server Windows (SMB) para FSx for Windows File Server

**Objetivo:** manter **ACLs NTFS**, integração com **Active Directory** e compartilhamentos SMB para usuários, sem reescrever aplicações.

```
Servidor Windows (SMB) ─ Agent ─▶ DataSync ─▶ FSx for Windows (integrado ao AD)
```

Passos:

1. Criar o **FSx for Windows** (Single-AZ ou Multi-AZ) integrado ao **AWS Managed Microsoft AD** ou ao AD local.
2. Criar **location SMB** (origem) com usuário com privilégios para ler dados e ACLs; **location FSx Windows** (destino) com usuário administrador do FSx.
3. Opções: `SecurityDescriptorCopyFlags=OWNER_DACL` (ou `OWNER_DACL_SACL`), preservando dono e permissões.
4. Carga inicial + incrementais; **corte** com congelamento e última sincronização.
5. Redirecionar **DFS namespaces** ou mapeamentos de unidade para o FSx.

Pontos de atenção:

- **Contas e SIDs** devem resolver no domínio de destino; senão, ACLs aparecem como SIDs órfãos.
- Dimensione **capacidade e throughput** do FSx para a carga e **reduza** depois.
- Use **shadow copies** e **AWS Backup** no destino.

## 4. Cenário C — Data lake Hadoop (HDFS) para S3

**Objetivo:** modernizar um cluster Hadoop on-premises migrando 300 TB para S3 e usando **EMR/Athena/Glue** no lugar.

Passos:

1. Implantar o agent com acesso aos **NameNode e DataNodes** (portas do cluster; Kerberos se houver).
2. **Location HDFS** com NameNode, autenticação e agent; **location S3** de destino com prefixo por domínio de dados.
3. Dividir por **diretórios/zonas** (raw, curated) em tarefas separadas, com vários agents.
4. Executar incrementais enquanto os jobs continuam rodando no Hadoop; no corte, **repontar** jobs para `s3://`.
5. Registrar tabelas no **Glue Data Catalog** e validar consultas no Athena.

Pontos de atenção:

- HDFS usa blocos replicados; o S3 armazena objetos. **Arquivos muito pequenos** (típico em HDFS) pioram desempenho no S3 — considere **compactação** (merge de arquivos) após a migração.
- **Permissões** HDFS não existem como tal no S3; migre o modelo para **Lake Formation/IAM**.

## 5. Cenário D — S3 para S3 entre contas ou regiões

**Objetivo:** copiar o conteúdo de um bucket para outra conta (reorganização de contas, fusão de empresas) ou outra região (DR, latência).

```
Bucket origem (conta A, região 1) ──▶ DataSync (sem agent) ──▶ Bucket destino (conta B, região 2)
```

Passos:

1. Criar **location S3 de origem** e **location S3 de destino**, cada uma com sua **role** (a role precisa de acesso ao bucket correspondente).
2. Em **contas diferentes**, a **bucket policy** do bucket de outra conta deve autorizar a role do DataSync.
3. Criar a tarefa (Basic ou **Enhanced**, onde disponível), com `TransferMode=CHANGED` e `ObjectTags=PRESERVE`.
4. Se os objetos têm **criptografia SSE-KMS**, conceder à role permissões de uso das **chaves KMS** de origem (decrypt) e destino (encrypt).

Comparação com **S3 Replication** e **Batch Operations**:

| Critério | DataSync | S3 Replication | S3 Batch Operations (Copy) |
|---|---|---|---|
| Objetos **existentes** | Sim | Só com replicação sob demanda de objetos existentes (recurso adicional) | Sim |
| Replicação **contínua** de novos objetos | Por agenda (≥1 h) | **Sim, quase em tempo real** | Não (job pontual) |
| Filtros e agenda | Sim | Por regra de prefixo/tag | Via manifesto |
| Verificação | Integrada | Métricas de replicação | Relatório de conclusão |
| Melhor uso | Migração/sincronização agendada | **Replicação contínua/DR** | Cópias em massa com manifesto |

Regra: **S3 Replication** para replicação contínua de novos objetos; **DataSync** ou **Batch Operations** para migração em massa de objetos existentes.

## 6. Cenário E — EFS ou FSx entre regiões (DR e consolidação)

DataSync copia **EFS → EFS** (inclusive entre regiões), **FSx → FSx** e **EFS/FSx → S3** (arquivamento). Para EFS, existe também **EFS Replication** (replicação gerenciada contínua). Escolha:

- **EFS Replication**: RPO baixo e automático, sem agenda.
- **DataSync**: quando se precisa de **filtros**, **agenda**, **relatórios**, destino diferente (S3) ou **migração entre sistemas de tipos distintos**.

## 7. Cenário F — Multi-nuvem: Azure Blob ou Google Cloud para S3

**Objetivo:** consolidar dados de outra nuvem no S3.

- **Azure Blob Storage**: location própria com token **SAS**; agent (por exemplo, EC2 ou VM) com acesso.
- **Google Cloud Storage** e outros **S3-compatíveis**: location de **object storage** com endpoint, chaves HMAC e agent.
- **Custo de saída (egress)** da outra nuvem costuma ser relevante: calcule antes.
- Rodar o agent **perto da origem** (na outra nuvem ou em VM na mesma região do provedor) para reduzir latência e custo de rede.

## 8. Cenário G — Alimentar um data lake continuamente a partir de NAS ou EFS

Uso recorrente: um NAS de instrumentos ou sistemas gera arquivos diários e o DataSync os leva ao S3 numa agenda (por exemplo, a cada hora). Em S3, **eventos** (S3 → EventBridge/Lambda/SQS) disparam o processamento (Glue, Step Functions). Padrão:

```
NAS ──(DataSync, cron horário)──▶ S3 raw ──(evento)──▶ EventBridge ──▶ Step Functions/Glue ──▶ S3 curated ──▶ Athena
```

Atenção: arquivos grandes sendo **escritos** durante a cópia podem ser copiados incompletos; prefira que o produtor grave em área temporária e **renomeie/mova** ao concluir, ou copie de **snapshots**.

## 9. DataSync vs Transfer Family vs Storage Gateway vs Snow

| Aspecto | DataSync | Transfer Family | Storage Gateway | Snow Family |
|---|---|---|---|---|
| Finalidade | Mover dados em massa | Expor SFTP/FTPS/FTP/AS2 | Acesso híbrido contínuo | Mover dados offline e computar na borda |
| Direção | Origem → destino, agendado | Clientes enviam/baixam | Aplicações locais ↔ AWS | Dispositivo físico enviado |
| Protocolos | NFS, SMB, HDFS, objeto | SFTP, FTPS, FTP, AS2 | NFS, SMB, iSCSI, VTL | Cópia local (NFS/S3 API) |
| Latência de início | Minutos (online) | Imediata | Contínua | Dias (logística) |
| Escala típica | TB a dezenas de PB (com rede) | Por usuário/parceiro | Cache local de TB | 8 TB a PB (vários dispositivos) |
| Cobrança | Por GB | Por hora do endpoint + dados | Por GB e gateway | Por dispositivo/dia + serviço |

Combinações frequentes:

- **Snowball + DataSync** para cargas muito grandes.
- **Storage Gateway** para quem **continua** acessando arquivos localmente; **DataSync** para quem **migra de vez**.
- **Transfer Family** para ingestão de parceiros; **DataSync** para movimentos internos.

## 10. Padrões de segurança e governança por cenário

- Use **VPC endpoint** quando a política exige tráfego privado.
- **Criptografia** SSE-S3 ou **SSE-KMS** no destino; políticas de bucket restritivas e **Block Public Access**.
- **Object Lock/versionamento** para proteger contra exclusões em espelhamento.
- **Tags** nas tarefas (`projeto`, `dono`) para custo e acesso.
- **Auditoria**: task reports em S3 + CloudTrail.
- **Desativar** agents, tarefas e acessos temporários ao terminar.

## 11. Erros comuns

> [!bug] Erros comuns
> 1. **Usar DataSync como replicação contínua em tempo real** (para isso, S3 Replication/EFS Replication).
> 2. **Migrar file server Windows para S3** e perder ACLs NTFS (o destino ideal é FSx for Windows).
> 3. **Esquecer a bucket policy** do bucket de outra conta na cópia S3 → S3.
> 4. **Esquecer permissões KMS** em objetos SSE-KMS.
> 5. **Ignorar os custos de egress** ao copiar de outra nuvem.
> 6. **Copiar milhões de arquivos pequenos de HDFS** e depois sofrer no S3 sem compactação.
> 7. **Usar Storage Gateway para uma migração única**, quando o DataSync é mais adequado.
> 8. **Usar Transfer Family como ferramenta de migração em massa.**
> 9. **Copiar arquivos ainda em escrita**, gerando arquivos incompletos.
> 10. **Não reconstruir o modelo de permissões** ao sair de POSIX/HDFS para S3.

## 12. Troubleshooting por cenário

| Sintoma | Cenário | Ação |
|---|---|---|
| ACLs aparecem como SIDs desconhecidos | NAS/SMB → FSx Windows | Conferir domínio/AD e usuários resolvíveis; usar `OWNER_DACL` |
| `AccessDenied` em S3 → S3 entre contas | Entre contas | Ajustar bucket policy do bucket de destino/origem e a role |
| Erro ao ler objetos criptografados | SSE-KMS | Conceder `kms:Decrypt`/`kms:GenerateDataKey` às roles |
| Consultas lentas depois da migração Hadoop | HDFS → S3 | Compactar arquivos pequenos e usar Parquet |
| Arquivos truncados | Origem em escrita | Copiar de snapshot ou usar padrão de arquivo temporário e renomeação |
| Custos de rede altos | Multi-nuvem | Revisar egress do provedor de origem e posicionar o agent adequadamente |

## 13. Resumo rápido

- **DataSync** move dados em massa, online, com verificação e agenda; **Snow** é offline; **Transfer Family** é protocolo para parceiros; **Storage Gateway** é acesso híbrido contínuo.
- **NAS → S3** para arquivo/data lake; **SMB → FSx for Windows** para manter ACLs e AD.
- **HDFS → S3** exige atenção a arquivos pequenos e ao modelo de permissões.
- **S3 → S3 entre contas** requer bucket policy e permissões KMS; **S3 Replication** é melhor para replicação contínua.
- **Multi-nuvem** depende do custo de egress e do posicionamento do agent.

### 🧩 Quiz de Fixação

1. Para qual destino migrar um file server SMB mantendo ACLs NTFS?
2. O que é necessário para copiar S3 → S3 entre contas?
3. Quando preferir S3 Replication ao DataSync?
4. Qual problema típico ao levar HDFS para S3?
5. Qual a função do Transfer Family?
6. Como combinar Snowball e DataSync?
7. Que cuidado tomar com arquivos sendo escritos durante a cópia?

**Respostas:**

1. FSx for Windows File Server, com `SecurityDescriptorCopyFlags` adequado.
2. Roles do DataSync com acesso aos dois buckets, bucket policy autorizando a role de outra conta e permissões KMS quando há SSE-KMS.
3. Para replicação contínua quase em tempo real de novos objetos (por exemplo, DR).
4. Muitos arquivos pequenos e perda do modelo de permissões HDFS; compactar e migrar permissões para IAM/Lake Formation.
5. Expor SFTP/FTPS/FTP/AS2 com S3/EFS por trás para parceiros e usuários.
6. Snowball leva o grosso dos dados offline e o DataSync sincroniza as diferenças até o corte.
7. Copiar de snapshots ou usar arquivo temporário e renomear ao concluir; a próxima execução corrige.
