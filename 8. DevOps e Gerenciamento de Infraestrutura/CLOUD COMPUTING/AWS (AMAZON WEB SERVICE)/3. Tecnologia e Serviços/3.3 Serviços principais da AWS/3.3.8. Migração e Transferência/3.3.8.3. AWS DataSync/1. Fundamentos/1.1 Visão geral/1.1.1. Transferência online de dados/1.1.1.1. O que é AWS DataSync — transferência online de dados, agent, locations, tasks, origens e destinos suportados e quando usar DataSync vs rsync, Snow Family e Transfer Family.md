### 1.1.1.1. O que é AWS DataSync — transferência online de dados, agent, locations, tasks, origens e destinos suportados e quando usar DataSync vs rsync, Snow Family e Transfer Family

> [!warning] Aviso
> Os comandos de CLI, JSONs e valores deste material são **ilustrativos e não foram executados**. Limites de arquivos por tarefa, throughput máximo, modos de tarefa e preços do DataSync mudam com frequência; confirme na documentação oficial e na página de preços antes de planejar uma transferência real. Mover dados de produção exige backup, janela aprovada e validação de integridade.

## 1. O problema: mover muitos arquivos, de forma confiável e rápida

Depois de migrar servidores e bancos, sobra o **dado não estruturado**: servidores de arquivos NFS e SMB, NAS de 200 TB, clusters Hadoop, buckets de outras nuvens, anos de logs e mídia. Mover isso para a AWS com ferramentas improvisadas costuma doer:

- `rsync` e `robocopy` são **single-thread na prática**, lentos em milhões de arquivos pequenos e sem retomada inteligente em redes instáveis.
- Scripts caseiros não verificam integridade, não preservam metadados (permissões, timestamps, ACLs) e não deixam trilha de auditoria.
- Ninguém sabe dizer "quanto falta" nem "quais arquivos falharam".
- Saturar o link de internet de produção derruba outros serviços.

O **AWS DataSync** é um serviço **gerenciado de transferência online de dados**, projetado para automatizar e acelerar a cópia entre sistemas de armazenamento locais e a AWS, e entre serviços de armazenamento AWS. Ele usa um protocolo próprio, otimizado, com paralelismo, verificação de integridade, controle de banda e agendamento — e é cobrado **por GB transferido**.

## 2. O que o DataSync faz (e o que não faz)

| Capacidade | Descrição |
|---|---|
| **Cópia em massa** | Transfere milhões de arquivos/objetos com paralelismo e alto throughput |
| **Transferência incremental** | Detecta o que mudou e copia só o necessário nas execuções seguintes |
| **Preservação de metadados** | Timestamps, permissões POSIX, ACLs SMB (conforme origem/destino), tags de objeto |
| **Verificação de integridade** | Compara checksums durante e após a transferência |
| **Agendamento** | Execuções recorrentes (de hora em hora, diárias, semanais) |
| **Controle de banda** | Limita o uso de rede para não prejudicar a produção |
| **Relatórios** | Task reports com lista de arquivos transferidos, verificados e com erro |
| **Entre serviços AWS** | S3 ↔ EFS ↔ FSx, mesmo entre contas e regiões |

O que **não** é o DataSync:

- **Não é migração de banco de dados** (para isso, DMS).
- **Não é sincronização bidirecional**: cada tarefa copia numa direção (origem → destino). Para duas vias, crie duas tarefas, com cuidado com conflitos.
- **Não é acesso híbrido contínuo a arquivos** (para isso, Storage Gateway ou FSx File Gateway).
- **Não é backup versionado**: para proteção e retenção, use AWS Backup ou versionamento do destino.
- **Não é transferência offline** de volumes massivos sem rede (para isso, Snow Family).

## 3. Arquitetura conceitual

```
   ON-PREMISES                                         AWS
┌───────────────────┐                      ┌──────────────────────────────┐
│ NAS / servidor    │   NFS / SMB / HDFS   │      Serviço DataSync        │
│ de arquivos       │◀────────────────────▶│  (task + execuções)          │
└───────────────────┘          │           │            │                 │
                               │           │            ▼                 │
                      ┌────────┴────────┐  │   ┌─────────────────────┐    │
                      │  DataSync AGENT │──┼──▶│ Amazon S3 / EFS /    │    │
                      │ (VM ou EC2)     │ TLS  │ FSx (Windows, Lustre,│    │
                      └─────────────────┘  │   │ ONTAP, OpenZFS)      │    │
                                           │   └─────────────────────┘    │
                                           └──────────────────────────────┘
```

Os objetos principais:

1. **Agent**: máquina virtual (VMware ESXi, KVM, Hyper-V) ou instância EC2 que fica **perto do storage de origem**, lê os dados e os envia ao serviço. É necessário quando a origem é local ou em outra nuvem; **não é necessário** entre serviços AWS (por exemplo, S3 → S3, EFS → S3).
2. **Location**: descrição de **um lado** da transferência (tipo de storage, caminho, credenciais, agente a usar). Existe uma location de origem e outra de destino.
3. **Task**: liga uma location de origem a uma de destino, com **opções** (verificação, filtros, preservação de metadados, banda, agenda).
4. **Task execution**: uma **execução** da tarefa, com estados e métricas (preparando, transferindo, verificando, sucesso ou erro).

## 4. Origens e destinos suportados (visão geral)

| Categoria | Locations típicas |
|---|---|
| Armazenamento de arquivos local | **NFS**, **SMB**, **HDFS** |
| Objeto compatível | **Object storage** genérico (compatível com S3), incluindo outras nuvens via esse tipo |
| Nuvens | **Azure Blob Storage**, e Google Cloud Storage/Wasabi/outros via object storage S3-compatível (verificar a lista atual) |
| AWS | **Amazon S3** (inclusive S3 on Outposts), **Amazon EFS**, **FSx for Windows File Server**, **FSx for Lustre**, **FSx for OpenZFS**, **FSx for NetApp ONTAP** |

Regra geral: pelo menos **um dos lados** precisa ser um serviço de armazenamento AWS. A combinação on-premises → on-premises não é um caso de uso do DataSync.

Fluxos mais comuns:

- **NAS local → S3** (arquivo, backup, data lake).
- **NAS local → EFS/FSx** (lift-and-shift de servidores de arquivos).
- **Hadoop (HDFS) → S3** (modernização de data lake).
- **S3 → S3** entre contas e regiões, ou **EFS → EFS** entre regiões.
- **Outra nuvem → S3** (consolidação multi-nuvem).
- **FSx/EFS → S3** (arquivamento).

## 5. Como o DataSync transfere

O protocolo do DataSync difere de cópias simples:

1. **Descoberta (scan)**: lista origem e destino para saber o que copiar.
2. **Preparação**: decide os arquivos novos, alterados ou ausentes.
3. **Transferência paralela**: múltiplas threads/conexões, com **compressão e dados em blocos**, enviando só o necessário.
4. **Verificação**: calcula checksums e compara (conforme a opção escolhida).
5. **Relatório e métricas**: arquivos transferidos, bytes, falhas, duração.

Pontos que dão a velocidade: paralelismo, protocolo otimizado, **transferência apenas dos blocos/arquivos alterados** em execuções subsequentes e uso eficiente da rede (um agente consegue saturar links de vários Gbps, sujeito aos limites do serviço e do hardware).

## 6. Primeiro exemplo prático (ilustrativo)

NAS NFS local → bucket S3, com agente já ativado:

```bash
# 1) Location de origem (NFS)
aws datasync create-location-nfs \
  --server-hostname nas01.empresa.local \
  --subdirectory /export/projetos \
  --on-prem-config AgentArns=arn:aws:datasync:us-east-1:123456789012:agent/agent-0abc

# 2) Location de destino (S3)
aws datasync create-location-s3 \
  --s3-bucket-arn arn:aws:s3:::meu-bucket-arquivo \
  --subdirectory /projetos \
  --s3-storage-class STANDARD_IA \
  --s3-config BucketAccessRoleArn=arn:aws:iam::123456789012:role/datasync-s3-role

# 3) Tarefa com verificação e limite de banda
aws datasync create-task \
  --source-location-arn arn:aws:datasync:...:location/loc-origem \
  --destination-location-arn arn:aws:datasync:...:location/loc-destino \
  --name nas-para-s3 \
  --options VerifyMode=ONLY_FILES_TRANSFERRED,OverwriteMode=ALWAYS,PreserveDeletedFiles=PRESERVE,BytesPerSecond=-1 \
  --cloud-watch-log-group-arn arn:aws:logs:us-east-1:123456789012:log-group:/aws/datasync

# 4) Executa
aws datasync start-task-execution --task-arn arn:aws:datasync:...:task/task-0abc

# 5) Acompanha
aws datasync describe-task-execution --task-execution-arn arn:aws:datasync:...:task/task-0abc/execution/exec-0def
```

## 7. Quando usar DataSync vs alternativas

| Ferramenta | Melhor para | Limite |
|---|---|---|
| **DataSync** | Transferência **online** em massa e recorrente, com verificação e agenda | Exige rede com banda suficiente |
| **rsync / robocopy** | Cópias pequenas, pontuais, sem orçamento | Lento em escala, sem trilha, sem paralelismo gerenciado |
| **AWS CLI `s3 sync`** | Cópia simples de/para S3 em volumes modestos | Single máquina, sem verificação robusta nem agenda gerenciada |
| **Snow Family (Snowcone/Snowball)** | Volumes enormes (centenas de TB a PB) com **rede lenta/inexistente** | Logística física, latência de dias |
| **AWS Transfer Family** | Fornecer **SFTP/FTPS/FTP/AS2** a parceiros, com S3/EFS por trás | É um servidor de protocolo, não uma ferramenta de migração em massa |
| **Storage Gateway** | **Acesso híbrido contínuo** (cache local, arquivo/fita/volume) | Não é para cópia em massa única |
| **S3 Replication / Batch Operations** | Replicação e operações **dentro do S3** | Restrito ao S3 |
| **DMS** | **Bancos de dados** | Não é para arquivos |
| **AWS DataSync + Direct Connect** | Transferência com banda dedicada | Exige o circuito de rede |

Heurística de decisão por volume e rede (didática):

```
Tempo estimado = tamanho ÷ banda útil
  10 TB  em 1 Gbps (≈ 70% útil)  ≈ 1,3 dia
 100 TB  em 1 Gbps               ≈ 13 dias
   1 PB  em 1 Gbps               ≈ 130 dias  → considerar Snow Family ou aumentar banda
```

Se o tempo estimado for **inaceitável**, a decisão é Snow Family (offline) ou, quando possível, um link dedicado de maior capacidade. Muitas migrações combinam os dois: **Snowball para a carga inicial** e **DataSync para as diferenças** até o corte.

## 8. DataSync dentro da jornada de migração

- **Descoberta** (Application Discovery Service) revela os servidores de arquivos e o volume.
- **Migration Hub** pode acompanhar o projeto como um todo.
- **MGN** replica servidores; **DMS** migra bancos; **DataSync** move os **dados de arquivos** que não vão junto com os servidores (shares NAS, repositórios de mídia, datasets).
- Após o corte, o DataSync segue útil para **arquivar**, **replicar entre regiões** e **alimentar data lakes**.

## 9. Limites conceituais importantes

- **Um sentido por tarefa**; mudanças no destino não voltam para a origem.
- **Metadados dependem do par origem/destino**: nem todo atributo existe em todos os sistemas (por exemplo, ACLs SMB e S3 não se mapeiam 1:1; o DataSync guarda metadados POSIX como metadados do objeto em S3 para restauração posterior).
- A tarefa tem **limites de escala** (número de arquivos, tamanho de caminho, throughput) que variam por modo de tarefa e versão; planeje dividir grandes árvores em várias tarefas.
- **Arquivos abertos e em escrita** durante a cópia podem ser copiados de forma inconsistente; a próxima execução incremental corrige.
- O DataSync **não deduplica** nem transforma o conteúdo: copia fielmente.

## 10. Erros comuns

> [!bug] Erros comuns
> 1. **Usar DataSync para migrar bancos de dados** (o correto é DMS).
> 2. **Esperar sincronização bidirecional** de uma tarefa única.
> 3. **Subestimar o tempo** de uma carga inicial sem calcular banda e overhead.
> 4. **Rodar a carga inicial no horário comercial sem limite de banda**, saturando o link da produção.
> 5. **Escolher DataSync para volumes de petabytes com rede lenta**, quando Snow Family seria viável.
> 6. **Não verificar a integridade** ou ignorar o relatório de tarefas com erro.
> 7. **Colocar o agente longe do storage de origem** (latência alta entre agente e NAS).
> 8. **Esquecer que S3 → S3 e EFS → S3 não exigem agente**, criando infraestrutura à toa.
> 9. **Cortar a aplicação para o novo storage sem uma última sincronização incremental.**

## 11. Troubleshooting inicial

| Sintoma | Causa provável | Ação |
|---|---|---|
| Agente aparece "offline" | Sem rede para o serviço ou porta bloqueada | Liberar HTTPS 443 para os endpoints, ou configurar o VPC endpoint |
| Erro ao montar a origem NFS/SMB | Permissões/exports/credenciais | Ajustar export NFS ou usuário SMB com leitura |
| Tarefa lenta | Link, agente subdimensionado ou muitos arquivos pequenos | Aumentar recursos do agente, revisar limites de banda e dividir tarefas |
| Arquivos com erro | Permissões, caminhos longos, arquivos em uso | Consultar o log/relatório e corrigir caso a caso |
| Destino S3 negado | Role sem acesso ao bucket | Ajustar a role da location e a política do bucket |
| Metadados perdidos | Combinação origem/destino sem suporte | Revisar opções de preservação e o tipo de destino |

## 12. Resumo rápido

- DataSync = **serviço gerenciado de transferência online** de arquivos/objetos, rápido, incremental e com verificação.
- Peças: **Agent** (perto da origem), **Locations**, **Task** e **Task execution**.
- Origens: NFS, SMB, HDFS, object storage, Azure Blob, S3, EFS e FSx; um lado deve ser AWS.
- **Um sentido por tarefa**; para bancos use DMS, para volumes imensos sem rede use Snow Family.
- Calcule **tempo = tamanho ÷ banda** para decidir entre online e offline.

### 🧩 Quiz de Fixação

1. Qual a função do agent do DataSync e quando ele não é necessário?
2. Qual a diferença entre location e task?
3. Cite três origens suportadas e três destinos AWS.
4. O DataSync faz sincronização bidirecional numa única tarefa?
5. Quando a Snow Family é preferível ao DataSync?
6. Para que serve o AWS Transfer Family, em comparação ao DataSync?
7. Por que combinar Snowball e DataSync numa mesma migração?

**Respostas:**

1. Ler os dados perto do storage de origem e enviá-los ao serviço; não é necessário entre serviços AWS (ex.: S3 → S3, EFS → S3).
2. Location descreve um lado (tipo, caminho, credenciais); task liga origem e destino com opções e agenda.
3. Origens: NFS, SMB, HDFS (também object storage, Azure Blob, S3); destinos AWS: S3, EFS, FSx (Windows, Lustre, OpenZFS, ONTAP).
4. Não; é um sentido por tarefa.
5. Com volumes muito grandes (centenas de TB a PB) e rede lenta ou inexistente, quando o tempo online seria inaceitável.
6. Transfer Family oferece servidores SFTP/FTPS/FTP/AS2 para parceiros acessarem S3/EFS; DataSync move dados em massa.
7. Snowball faz a carga inicial offline e o DataSync copia as diferenças até o corte.
