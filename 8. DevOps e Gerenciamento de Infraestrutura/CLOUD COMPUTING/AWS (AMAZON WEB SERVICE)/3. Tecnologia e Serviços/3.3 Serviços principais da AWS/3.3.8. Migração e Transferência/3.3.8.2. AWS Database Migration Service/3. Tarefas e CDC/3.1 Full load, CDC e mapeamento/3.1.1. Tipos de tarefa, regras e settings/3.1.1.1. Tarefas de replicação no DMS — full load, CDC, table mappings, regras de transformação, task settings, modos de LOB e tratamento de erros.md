### 3.1.1.1. Tarefas de replicação no DMS — full load, CDC, table mappings, regras de transformação, task settings, modos de LOB e tratamento de erros

> [!warning] Aviso
> Os JSONs de table mappings e task settings abaixo são **ilustrativos e não foram executados**. Nomes de chaves e valores padrão podem variar por versão do DMS e por motor. Valide cada configuração em ambiente de teste, com `premigration assessment`, antes de rodar em produção.

## 1. A tarefa de replicação

A **replication task** descreve **o que migrar, como e quando**. Ela liga um endpoint de origem a um de destino, roda numa instância de replicação (ou em uma configuração serverless) e carrega três configurações centrais:

1. **Tipo de migração** (`migration-type`).
2. **Table mappings** (quais tabelas e que transformações).
3. **Task settings** (comportamento: LOBs, paralelismo, erros, logs, validação).

## 2. Os três tipos de migração

| Tipo | Valor na CLI | O que faz | Uso típico |
|---|---|---|---|
| Carga completa | `full-load` | Copia os dados existentes uma vez | Migração com janela de parada; carga inicial de data lake |
| Somente CDC | `cdc` | Aplica apenas mudanças a partir de um ponto | Carga inicial feita por outro meio (dump nativo, snapshot) |
| Carga completa + CDC | `full-load-and-cdc` | Copia tudo e depois replica mudanças | Migração com mínima parada (caso mais comum) |

### 2.1 Fases do full load

1. **Preparação das tabelas** (`TargetTablePrepMode`): `DO_NOTHING`, `DROP_AND_CREATE` (padrão) ou `TRUNCATE_BEFORE_LOAD`.
2. **Carga em paralelo**: o DMS carrega várias tabelas ao mesmo tempo (`MaxFullLoadSubTasks`, padrão 8). Tabelas grandes podem ser **particionadas** em segmentos paralelos (parallel load).
3. **Aplicação do cache de CDC**: mudanças ocorridas durante a carga são aplicadas ao final.
4. **Transição para CDC contínuo.**

### 2.2 Iniciar CDC a partir de um ponto

Quando a carga inicial foi feita fora do DMS, informe o ponto de partida:

```bash
aws dms create-replication-task \
  --replication-task-identifier cdc-somente \
  --migration-type cdc \
  --cdc-start-position "mysql-bin-changelog.000123:4567" \
  ...
# ou por horário
aws dms start-replication-task \
  --replication-task-arn arn:... \
  --start-replication-task-type start-replication \
  --cdc-start-time 2026-11-10T03:00:00Z
```

A posição pode ser um **LSN (SQL Server/Oracle SCN)**, **posição de binlog** ou **timestamp**, conforme o motor. Escolha um ponto **anterior** ao fim do dump para não perder transações (reaplicações são tratadas, mas lacunas, não).

## 3. Table mappings

O **table mapping** é um JSON com **regras** avaliadas em ordem (`rule-id` e `rule-name` únicos). Há dois tipos principais: **selection** (o que incluir/excluir) e **transformation** (como renomear/alterar).

### 3.1 Regras de seleção

```json
{
  "rules": [
    {
      "rule-type": "selection",
      "rule-id": "1",
      "rule-name": "inclui-schema-loja",
      "object-locator": { "schema-name": "LOJA", "table-name": "%" },
      "rule-action": "include"
    },
    {
      "rule-type": "selection",
      "rule-id": "2",
      "rule-name": "exclui-logs",
      "object-locator": { "schema-name": "LOJA", "table-name": "LOG_%" },
      "rule-action": "exclude"
    }
  ]
}
```

O caractere `%` é curinga. Ordem importa: uma exclusão específica vem depois da inclusão geral para refinar.

### 3.2 Regras de transformação

| Ação (`rule-action`) | Alvo (`rule-target`) | Efeito |
|---|---|---|
| `rename` | `schema`, `table`, `column` | Renomeia objetos |
| `remove-column` | `column` | Remove coluna do destino |
| `add-column` | `column` | Adiciona coluna calculada (com `expression`) |
| `convert-lowercase` / `convert-uppercase` | `schema`, `table`, `column` | Muda caixa (útil Oracle → PostgreSQL) |
| `add-prefix` / `add-suffix` / `remove-prefix` / `remove-suffix` | todos | Ajusta nomes |
| `change-data-type` | `column` | Altera tipo no destino |
| `define-primary-key` | `table` | Define chave primária |

Exemplo: converter nomes de Oracle (maiúsculas) para o padrão minúsculo do PostgreSQL e renomear um schema:

```json
{
  "rules": [
    { "rule-type": "selection", "rule-id": "1", "rule-name": "sel",
      "object-locator": { "schema-name": "LOJA", "table-name": "%" }, "rule-action": "include" },
    { "rule-type": "transformation", "rule-id": "2", "rule-name": "schema-minusculo",
      "rule-target": "schema", "object-locator": { "schema-name": "LOJA" },
      "rule-action": "rename", "value": "loja" },
    { "rule-type": "transformation", "rule-id": "3", "rule-name": "tabelas-minusculas",
      "rule-target": "table", "object-locator": { "schema-name": "LOJA", "table-name": "%" },
      "rule-action": "convert-lowercase" },
    { "rule-type": "transformation", "rule-id": "4", "rule-name": "colunas-minusculas",
      "rule-target": "column", "object-locator": { "schema-name": "LOJA", "table-name": "%", "column-name": "%" },
      "rule-action": "convert-lowercase" }
  ]
}
```

### 3.3 Filtros de linha

Para migrar apenas parte dos dados (por exemplo, o último ano), use `filters` na regra de seleção:

```json
{
  "rule-type": "selection", "rule-id": "5", "rule-name": "pedidos-recentes",
  "object-locator": { "schema-name": "LOJA", "table-name": "PEDIDOS" },
  "rule-action": "include",
  "filters": [
    { "filter-type": "source", "column-name": "DATA_PEDIDO",
      "filter-conditions": [ { "filter-operator": "gte", "value": "2025-01-01" } ] }
  ]
}
```

### 3.4 Carga paralela de tabelas grandes

```json
{
  "rule-type": "table-settings", "rule-id": "6", "rule-name": "pedidos-paralelo",
  "object-locator": { "schema-name": "LOJA", "table-name": "PEDIDOS" },
  "parallel-load": {
    "type": "ranges",
    "columns": ["ID_PEDIDO"],
    "boundaries": [["1000000"], ["2000000"], ["3000000"]]
  }
}
```

O DMS carrega os intervalos em paralelo, o que reduz drasticamente o tempo para tabelas de centenas de milhões de linhas.

## 4. Task settings

O **task settings** é outro JSON com blocos de comportamento. Principais:

| Bloco | O que controla |
|---|---|
| `TargetMetadata` | LOBs, paralelismo de aplicação, `BatchApplyEnabled`, nome de tabelas de controle |
| `FullLoadSettings` | Preparo de tabela, subtasks, `CommitRate`, `StopTaskCachedChangesApplied` |
| `Logging` | Habilita CloudWatch Logs e níveis por componente |
| `ControlTablesSettings` | Tabelas `awsdms_*` de controle no destino |
| `ChangeProcessingTuning` | Tamanho de lote, tempo, memória do CDC |
| `ChangeProcessingDdlHandlingPolicy` | Como tratar DDL (criar/dropar/alterar tabela) |
| `ErrorBehavior` | O que fazer em erro de dado, de tabela e de aplicação |
| `ValidationSettings` | Validação de dados |

Exemplo reduzido:

```json
{
  "TargetMetadata": {
    "SupportLobs": true,
    "FullLobMode": false,
    "LimitedSizeLobMode": true,
    "LobMaxSize": 32,
    "ParallelApplyThreads": 4,
    "BatchApplyEnabled": true
  },
  "FullLoadSettings": {
    "TargetTablePrepMode": "TRUNCATE_BEFORE_LOAD",
    "MaxFullLoadSubTasks": 8,
    "CommitRate": 50000
  },
  "Logging": { "EnableLogging": true },
  "ErrorBehavior": {
    "DataErrorPolicy": "LOG_ERROR",
    "TableErrorPolicy": "SUSPEND_TABLE",
    "ApplyErrorPolicy": "LOG_ERROR",
    "FullLoadIgnoreConflicts": true
  },
  "ValidationSettings": { "EnableValidation": true, "ThreadCount": 5 }
}
```

## 5. Modos de LOB

**LOBs** (BLOB, CLOB, TEXT, JSON grande) são os campos mais problemáticos porque seu tamanho é variável e pode ser enorme.

| Modo | Comportamento | Prós | Contras |
|---|---|---|---|
| **Limited LOB mode** | Trunca LOBs acima de `LobMaxSize` (KB) | **Mais rápido**, previsível | Dados maiores que o limite são **truncados** |
| **Full LOB mode** | Migra LOBs de qualquer tamanho, buscando por linha | Sem truncamento | **Lento**, sensível a LOBs enormes |
| **Inline LOB mode** | Pequenos LOBs vão inline; grandes são buscados | Equilíbrio | Configuração mais fina (`InlineLobMaxSize`) |

Procedimento recomendado: **medir o maior LOB** na origem (por consulta), definir `LobMaxSize` com folga e preferir **limited** ou **inline**. Truncamento silencioso é a falha clássica: a tarefa "funciona" e os dados ficam incompletos. A validação ajuda a detectar.

## 6. Aplicação das mudanças no CDC

- **Transactional apply** (padrão): aplica as mudanças na ordem e preservando transações; seguro, mais lento.
- **Batch apply** (`BatchApplyEnabled`): agrupa mudanças e aplica em lote; **mais rápido** para destinos como Redshift ou grande volume, mas pode relaxar a ordem de transações e exige cuidado com chaves e conflitos.
- **ParallelApplyThreads** (para alguns destinos como Kinesis/Kafka/S3): paraleliza a aplicação.

Tabelas **sem chave primária** não permitem localizar a linha para UPDATE/DELETE; defina `define-primary-key` ou crie a PK no destino.

## 7. Tratamento de DDL

| Política | Efeito |
|---|---|
| `HandleSourceTableDropped` | Remove/mantém/trunca a tabela no destino quando é dropada na origem |
| `HandleSourceTableTruncated` | Replica o TRUNCATE |
| `HandleSourceTableAltered` | Replica ALTER TABLE básico (ex.: adicionar coluna) |

Mudanças de schema **durante** uma migração são risco: congele DDL na origem sempre que possível ou valide que o DMS as replica para o seu motor.

## 8. Comportamento em erro

| Política | Valores | Significado |
|---|---|---|
| `DataErrorPolicy` | `LOG_ERROR`, `SUSPEND_TABLE`, `STOP_TASK`, `IGNORE_RECORD` | Erro de dado (truncamento, conversão) |
| `TableErrorPolicy` | `SUSPEND_TABLE`, `STOP_TASK` | Erro em uma tabela |
| `ApplyErrorPolicy` | `LOG_ERROR`, `IGNORE_RECORD`, `STOP_TASK`, `SUSPEND_TABLE` | Erro ao aplicar CDC (duplicidade, linha ausente) |
| `FullLoadIgnoreConflicts` | true/false | Ignora conflitos durante o full load |

Erros de aplicação ficam registrados na tabela de controle **`awsdms_apply_exceptions`** no destino. Em migração real, a política `STOP_TASK` em dados críticos evita perda silenciosa; `LOG_ERROR` em replicações tolerantes.

## 9. Operar a tarefa

```bash
aws dms start-replication-task --replication-task-arn arn:... --start-replication-task-type start-replication
aws dms stop-replication-task  --replication-task-arn arn:...
# Retomar CDC de onde parou
aws dms start-replication-task --replication-task-arn arn:... --start-replication-task-type resume-processing
# Reiniciar do zero (recarrega)
aws dms start-replication-task --replication-task-arn arn:... --start-replication-task-type reload-target
# Estatísticas por tabela
aws dms describe-table-statistics --replication-task-arn arn:...
```

`describe-table-statistics` mostra por tabela: linhas carregadas, inserts/updates/deletes do CDC, estado e validação — é o termômetro da migração.

## 10. Premigration assessment

Antes de iniciar, execute a **avaliação pré-migração**: ela checa configuração da origem/destino (ex.: logs desabilitados, tabelas sem PK, tipos não suportados, LOBs grandes) e produz um relatório para corrigir antes de gastar tempo na carga.

## 11. Erros comuns

> [!bug] Erros comuns
> 1. **Limited LOB mode com `LobMaxSize` pequeno**, truncando dados silenciosamente.
> 2. **Table mapping sem regra de inclusão**, resultando em nenhuma tabela migrada.
> 3. **Ordem errada das regras**, com exclusões sendo sobrescritas.
> 4. **`DROP_AND_CREATE` em tabelas que já têm schema curado**, perdendo índices e tipos ajustados.
> 5. **Criar FKs e índices antes do full load**, causando lentidão ou falhas de ordem.
> 6. **Ignorar tabelas sem PK**, quebrando UPDATE/DELETE no CDC.
> 7. **`LOG_ERROR` em tudo**, mascarando falhas que deveriam parar a migração.
> 8. **Iniciar CDC em posição posterior ao dump**, perdendo transações.
> 9. **Alterar o schema da origem durante a migração** sem testar o tratamento de DDL.
> 10. **Não habilitar logs** e ficar sem diagnóstico quando a tarefa falha.

## 12. Troubleshooting

| Sintoma | Causa provável | Ação |
|---|---|---|
| Nenhuma tabela carregada | Regra de seleção incorreta | Revisar `object-locator` e curingas |
| Tabela "suspended" | Erro de tabela e política `SUSPEND_TABLE` | Ver logs e `awsdms_apply_exceptions`; corrigir e recarregar a tabela |
| UPDATE/DELETE não aplicados | Tabela sem PK | Definir/criar chave primária |
| Dados LOB cortados | Limited LOB mode | Aumentar `LobMaxSize` ou usar inline/full |
| Full load muito lento | Índices/FK no destino, poucas subtasks | Remover durante a carga, aumentar paralelismo e usar parallel load |
| CDC não avança | Log da origem não retido ou slot parado | Verificar binlog/WAL e a posição inicial |

## 13. Resumo rápido

- Três tipos: **full-load**, **cdc**, **full-load-and-cdc**.
- **Table mappings**: regras de **seleção** e **transformação**, com filtros e carga paralela.
- **Task settings**: LOBs, paralelismo, batch apply, DDL, erros, logs e validação.
- **LOB limited** é rápido mas pode truncar; meça o maior LOB.
- Use **premigration assessment**, **describe-table-statistics** e a tabela **awsdms_apply_exceptions** para controlar a qualidade.

### 🧩 Quiz de Fixação

1. Qual tipo de migração combina carga inicial e replicação contínua?
2. Para que servem as regras `selection` e `transformation`?
3. Qual o risco do Limited LOB mode?
4. O que `BatchApplyEnabled` faz?
5. Onde ficam registrados os erros de aplicação do CDC?
6. Como acelerar a carga de uma tabela enorme?
7. O que a avaliação pré-migração verifica?

**Respostas:**

1. `full-load-and-cdc`.
2. Selection escolhe quais objetos incluir/excluir; transformation renomeia, remove/adiciona colunas, altera tipos, etc.
3. Truncar silenciosamente LOBs maiores que `LobMaxSize`.
4. Agrupa mudanças e as aplica em lote, acelerando o CDC, com possível relaxamento da ordem transacional.
5. Na tabela de controle `awsdms_apply_exceptions` no destino (além dos logs do CloudWatch).
6. Usando parallel load com ranges/partições e ajustando `MaxFullLoadSubTasks`.
7. Problemas de configuração e compatibilidade, como logs desabilitados, tabelas sem PK, tipos não suportados e LOBs grandes.
