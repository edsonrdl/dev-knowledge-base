### 1.1.1.1. O que é AWS Database Migration Service — migração homogênea e heterogênea, full load e CDC, arquitetura, fontes e destinos e quando usar DMS vs ferramentas nativas

> [!warning] Aviso
> Os comandos de CLI, JSONs e valores deste material são **ilustrativos e não foram executados**. Versões de motores, tipos de instância, limites e preços do DMS mudam com frequência; confirme na documentação oficial e na página de preços antes de planejar uma migração real. Migrações de banco envolvem risco de perda de dados: sempre teste em ambiente não produtivo e mantenha backups.

## 1. O problema: mover dados vivos sem parar o negócio

Migrar um banco de dados é diferente de migrar um servidor de aplicação. O banco **muda a cada segundo**: pedidos entram, estoques são atualizados, usuários se cadastram. Uma cópia simples (dump e restore) exige parar a aplicação durante todo o tempo da cópia — e, para um banco de 2 TB, isso pode significar horas ou dias de indisponibilidade. Para a maioria das empresas, isso é inaceitável.

O **AWS Database Migration Service (DMS)** resolve isso com uma ideia central: **copiar os dados existentes e, ao mesmo tempo, capturar e aplicar as mudanças que acontecem durante a cópia**, de forma que a origem e o destino fiquem sincronizados. No momento da virada (cutover), a janela de indisponibilidade cai de horas para minutos.

## 2. O que o DMS faz

| Capacidade | Descrição |
|---|---|
| **Full load** | Copia todos os dados existentes das tabelas de origem para o destino |
| **CDC (Change Data Capture)** | Captura mudanças contínuas (INSERT, UPDATE, DELETE) da origem e as aplica no destino |
| **Full load + CDC** | Copia o conteúdo e depois mantém a sincronização contínua |
| **Migração homogênea** | Mesmo motor na origem e no destino (ex.: MySQL → Aurora MySQL, Oracle → RDS Oracle) |
| **Migração heterogênea** | Motores diferentes (ex.: Oracle → Aurora PostgreSQL, SQL Server → MySQL) — exige conversão de schema |
| **Replicação contínua** | Uso além da migração: alimentar data lakes e réplicas por tempo indeterminado |
| **Consolidação** | Juntar vários bancos de origem em um destino (ex.: sharded → data warehouse) |

O que o DMS **não faz bem por conta própria**: converter automaticamente procedures, funções, triggers e tipos complexos entre motores diferentes. Para isso existe a **DMS Schema Conversion** (e a AWS Schema Conversion Tool, SCT), tratadas na folha de migração heterogênea.

## 3. Arquitetura básica

```
 ORIGEM                         AWS DMS                          DESTINO
┌──────────────┐          ┌──────────────────────┐        ┌──────────────────┐
│ Banco de     │ endpoint │  Replication Instance │endpoint│ Banco gerenciado │
│ dados fonte  │─────────▶│  (ou DMS Serverless)  │───────▶│ (RDS, Aurora,    │
│ (on-premises │  origem  │                      │ destino│  Redshift, S3 ...)│
│  ou nuvem)   │          │  ┌────────────────┐  │        └──────────────────┘
└──────────────┘          │  │ Replication    │  │
   logs de transação      │  │ Task           │  │
   (binlog, WAL, redo)    │  │ full load/CDC  │  │
                          │  └────────────────┘  │
                          └──────────────────────┘
```

Os quatro objetos fundamentais:

1. **Replication instance** (ou **DMS Serverless replication**): o servidor gerenciado que executa o trabalho. Lê da origem, transforma e escreve no destino.
2. **Source endpoint**: configuração de conexão com o banco de origem (host, porta, credenciais, SSL, atributos extras).
3. **Target endpoint**: configuração de conexão com o destino.
4. **Replication task**: a definição do trabalho — quais tabelas, que tipo de migração (full load, CDC ou ambos) e quais regras aplicar.

## 4. Como o CDC funciona (visão geral)

O DMS não "espia" a tabela comparando linhas. Ele lê o **log de transações** do banco de origem, o mesmo log que o banco usa para recuperação e replicação:

| Origem | Mecanismo de CDC | Requisito típico |
|---|---|---|
| MySQL / MariaDB | **binlog** | `log_bin` ativo, `binlog_format=ROW`, retenção adequada |
| PostgreSQL | **Replicação lógica (WAL)** | `wal_level=logical`, slot de replicação |
| Oracle | **LogMiner** ou **Binary Reader** | Modo ARCHIVELOG e *supplemental logging* |
| SQL Server | **MS-Replication** ou **MS-CDC** | CDC/replicação habilitados no banco |
| MongoDB / DocumentDB | **Change streams / oplog** | Replica set |
| Db2, SAP ASE, etc. | Mecanismos específicos | Conforme documentação |

Isso significa que, para fazer CDC, **o banco de origem precisa estar configurado para gerar e reter os logs** — e essa configuração costuma ser a etapa que mais gera surpresa e, às vezes, exige reinicialização da origem.

Fluxo temporal de uma tarefa **full load + CDC**:

```
 t0: tarefa inicia ─▶ DMS registra a posição inicial do log (ponto de partida do CDC)
 t0 → t1: FULL LOAD copia as tabelas; mudanças que ocorrem são enfileiradas/armazenadas em cache
 t1: full load termina ─▶ DMS aplica as mudanças acumuladas no destino
 t1 → ∞: CDC contínuo: destino acompanha a origem com latência de segundos
 tc: CUTOVER ─▶ para a aplicação (ou a escrita), latência chega a ~0, redireciona para o destino
```

## 5. Fontes e destinos

O DMS suporta uma lista ampla (sujeita a atualização):

| Categoria | Exemplos de **origem** | Exemplos de **destino** |
|---|---|---|
| Relacionais comerciais | Oracle, SQL Server, Db2 | Oracle, SQL Server (RDS/EC2) |
| Open source | MySQL, MariaDB, PostgreSQL | Aurora MySQL/PostgreSQL, RDS |
| NoSQL / documento | MongoDB, Amazon DocumentDB | DocumentDB, DynamoDB |
| Analytics | — | **Amazon Redshift**, **S3** (CSV/Parquet), **OpenSearch** |
| Streaming | — | **Kinesis Data Streams**, **Apache Kafka (MSK)** |
| Armazenamento | Amazon S3 (origem) | Amazon S3 |

Combinações usuais: **Oracle → Aurora PostgreSQL**, **SQL Server → RDS SQL Server**, **MySQL on-premises → Aurora MySQL**, **qualquer banco → S3 (Parquet) → Athena/Glue** para data lake, e **banco OLTP → Kinesis/MSK** para eventos de mudança.

## 6. Quando usar DMS vs ferramentas nativas

| Cenário | Recomendação |
|---|---|
| Mesmo motor, banco pequeno, janela de parada aceitável | **Ferramenta nativa** (mysqldump, pg_dump, backup/restore) — mais simples |
| Mesmo motor, banco grande, pouca parada | Ferramentas nativas de replicação (replicação MySQL, logical replication PostgreSQL) ou **DMS homogeneous data migrations** |
| Motores diferentes | **DMS + Schema Conversion** |
| Precisa filtrar/transformar tabelas e colunas | **DMS** (table mappings) |
| Precisa alimentar S3, Kinesis, Redshift | **DMS** |
| Oracle → RDS Oracle com Data Pump disponível | Data Pump para a carga inicial + DMS (CDC), ou apenas DMS |
| Migração contínua de longa duração | **DMS** (replicação contínua) |
| Origem muito sensível a carga | Avaliar **leitura de réplica** como origem do DMS |

Regra prática: **motores iguais** → considere primeiro as ferramentas nativas (mais fiéis); **motores diferentes ou necessidade de CDC com transformação** → DMS.

O DMS também oferece **homogeneous data migrations**, que usam ferramentas nativas do motor (por exemplo, `pg_dump` e replicação lógica) de forma gerenciada para migrações do mesmo tipo, com melhor fidelidade que o DMS clássico em alguns cenários.

## 7. Componentes adicionais do ecossistema

| Componente | Função |
|---|---|
| **DMS Schema Conversion** | Converte schema e código (procedures, views) entre motores, dentro do console DMS |
| **AWS SCT** | Ferramenta instalável (desktop) para conversão de schema, com relatório de avaliação |
| **Premigration assessment** | Avalia a tarefa antes de executar, apontando problemas |
| **Data validation** | Compara origem e destino após/durante a migração |
| **DMS Fleet Advisor** | Inventário de bancos (disponibilidade a verificar; recursos de descoberta foram reorganizados) |
| **Migration Hub** | Rastreia o progresso da migração |

## 8. Primeiro exemplo prático (ilustrativo)

Migração de MySQL on-premises para Aurora MySQL, **full load + CDC**:

```bash
# 1) Cria o endpoint de origem
aws dms create-endpoint \
  --endpoint-identifier mysql-origem \
  --endpoint-type source \
  --engine-name mysql \
  --server-name 10.10.2.15 --port 3306 \
  --username dms_user --password '********' \
  --ssl-mode require

# 2) Cria o endpoint de destino
aws dms create-endpoint \
  --endpoint-identifier aurora-destino \
  --endpoint-type target \
  --engine-name aurora \
  --server-name meu-cluster.cluster-abc.us-east-1.rds.amazonaws.com --port 3306 \
  --username admin --password '********'

# 3) Cria a instância de replicação
aws dms create-replication-instance \
  --replication-instance-identifier dms-inst-1 \
  --replication-instance-class dms.c5.large \
  --allocated-storage 100 \
  --multi-az

# 4) Cria a tarefa (full load + CDC)
aws dms create-replication-task \
  --replication-task-identifier mig-mysql-aurora \
  --source-endpoint-arn arn:aws:dms:...:endpoint:SRC \
  --target-endpoint-arn arn:aws:dms:...:endpoint:TGT \
  --replication-instance-arn arn:aws:dms:...:rep:INST \
  --migration-type full-load-and-cdc \
  --table-mappings file://table-mappings.json

# 5) Inicia
aws dms start-replication-task \
  --replication-task-arn arn:aws:dms:...:task:TASK \
  --start-replication-task-type start-replication
```

Senhas em linha de comando aparecem no histórico do shell; em uso real, use **AWS Secrets Manager** como fonte de credenciais do endpoint.

## 9. Limites conceituais importantes

- O DMS **não migra** objetos além de tabelas e chaves primárias por padrão: **índices secundários, triggers, procedures, views, sequences e constraints** normalmente precisam ser criados por outro meio (schema conversion, scripts) — idealmente **antes** (para índices e constraints, depois do full load para performance).
- Tabelas **sem chave primária** limitam o CDC e a validação.
- **LOBs** (colunas grandes) exigem atenção a modos (limitado, completo, inline).
- A replicação é **eventual**, com latência; não é sincronização transacional exata.

## 10. Erros comuns

> [!bug] Erros comuns
> 1. **Achar que o DMS converte o schema automaticamente** entre motores diferentes (precisa de Schema Conversion).
> 2. **Não habilitar o log de transações na origem** (binlog, supplemental logging, wal_level) e descobrir só quando o CDC falha.
> 3. **Usar DMS onde uma ferramenta nativa seria mais simples e fiel** (mesmo motor, banco pequeno).
> 4. **Subdimensionar a instância de replicação**, causando lentidão e travamentos.
> 5. **Esquecer de criar índices e constraints** no destino, ou criá-los antes do full load e degradar a carga.
> 6. **Tabelas sem chave primária** causando problemas no CDC e na validação.
> 7. **Deixar a instância de replicação rodando** depois da migração, pagando sem necessidade.
> 8. **Expor credenciais** na linha de comando em vez de usar Secrets Manager.
> 9. **Cutover sem validar dados** e sem plano de rollback.

## 11. Troubleshooting inicial

| Sintoma | Causa provável | Ação |
|---|---|---|
| Teste de conexão do endpoint falha | Rede, security group, DNS ou credenciais | Verificar rota, SG, VPN/Direct Connect e usuário |
| Tarefa falha ao iniciar CDC | Log de transações não habilitado | Configurar binlog/WAL/supplemental logging |
| Latência crescente | Instância pequena ou destino lento | Aumentar instância, ajustar paralelismo e índices |
| Tabelas ignoradas | Regras de seleção incorretas | Revisar o table mapping |
| Tarefa em "failed" sem detalhes | Logs desabilitados | Habilitar CloudWatch Logs e consultar as mensagens |
| Dados divergentes | Falta de validação ou DDL não replicado | Habilitar validação e revisar tratamento de DDL |

## 12. Resumo rápido

- DMS copia dados existentes (**full load**) e replica mudanças (**CDC**), reduzindo a janela de parada.
- Quatro peças: **instância de replicação (ou serverless), endpoint de origem, endpoint de destino e tarefa**.
- **Homogênea**: mesmo motor; **heterogênea**: motores diferentes, exige **Schema Conversion**.
- CDC lê o **log de transações**, que precisa estar habilitado e retido na origem.
- Motores iguais e bancos pequenos → ferramentas nativas costumam ser mais simples; DMS brilha em **heterogêneo, CDC e destinos como S3/Kinesis/Redshift**.
