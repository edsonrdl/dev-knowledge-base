### 4.1.1.1. Migração heterogênea com DMS — Schema Conversion e SCT, Oracle e SQL Server para Aurora PostgreSQL, mapeamento de tipos e destinos S3, Redshift, Kinesis e Kafka

> [!warning] Aviso
> Os exemplos de SQL, JSON e comandos são **ilustrativos e não foram executados**. A taxa de conversão automática de código, o suporte a versões de motores e os recursos da DMS Schema Conversion e da AWS SCT variam por versão. Trate qualquer conversão automática como **rascunho a ser revisado e testado**, nunca como resultado final.

## 1. O que torna uma migração "heterogênea"

Em uma migração **homogênea** (MySQL → Aurora MySQL), o destino fala o mesmo dialeto SQL, tem os mesmos tipos e a mesma lógica procedural: os dados e o schema "encaixam". Em uma migração **heterogênea** (Oracle → Aurora PostgreSQL, SQL Server → MySQL), os dois lados diferem em:

- **Tipos de dados** (`NUMBER` do Oracle, `DATETIME2` do SQL Server, `NVARCHAR2`, `RAW`...).
- **Dialeto SQL** (funções, `ROWNUM` vs `LIMIT`, `NVL` vs `COALESCE`, sintaxe de joins antigos).
- **Código procedural** (PL/SQL vs PL/pgSQL, T-SQL vs PL/pgSQL).
- **Objetos exclusivos** (packages, sequences vs identity, synonyms, database links, jobs, tipos de objeto).
- **Semântica** (tratamento de string vazia vs NULL no Oracle, sensibilidade de caixa, collation, isolamento de transações).

O DMS por si só migra **dados** de tabelas; o **schema e o código** exigem uma etapa de conversão. Essa etapa costuma ser **a parte mais demorada e arriscada** do projeto — frequentemente mais que a replicação dos dados.

## 2. Fluxo de trabalho recomendado

```
1. Avaliar        ─▶ Relatório de complexidade (quantos objetos convertem sozinhos)
2. Converter      ─▶ Schema + código via DMS Schema Conversion / SCT
3. Revisar/ajustar─▶ Corrigir manualmente o que não converteu (ações "manuais")
4. Aplicar schema ─▶ Criar o schema no destino (sem índices secundários/FKs pesados)
5. Migrar dados   ─▶ DMS full load + CDC
6. Pós-carga      ─▶ Criar índices, FKs, triggers; ajustar sequences
7. Validar        ─▶ Dados + funcionalidade + desempenho da aplicação
8. Cutover        ─▶ Virada; aplicação passa a usar o novo banco
```

## 3. DMS Schema Conversion e AWS SCT

| Ferramenta | Onde roda | Função |
|---|---|---|
| **DMS Schema Conversion** | No console do DMS (gerenciada) | Converte schema e código; relatório de avaliação; aplica no destino |
| **AWS SCT** | Aplicativo instalado em uma máquina (Windows/Linux/macOS) | Mesmo propósito, com mais opções locais, relatórios offline e recursos para data warehouse |

Ambas produzem um **assessment report** classificando objetos por complexidade de conversão e indicando **ações manuais**. Principais saídas:

- **Percentual de conversão automática** por tipo de objeto (tabelas, views, procedures, funções, packages...).
- **Itens de ação** (action items), classificados por esforço (simples, médio, complexo).
- **Código convertido** que você pode revisar, editar e aplicar.
- Para **Oracle**, a possibilidade de usar a **extension pack** (esquema auxiliar no destino com funções que emulam recursos do Oracle).

> [!tip] Dica
> Rode o assessment **cedo**, antes de se comprometer com prazo. Um banco Oracle com 3.000 procedures PL/SQL complexas é um projeto de meses; o mesmo banco com lógica quase toda na aplicação pode ser rápido. O relatório é o melhor preditor de esforço.

## 4. Mapeamento de tipos (exemplos)

| Origem (Oracle) | Destino (PostgreSQL) | Observação |
|---|---|---|
| `NUMBER(p,0)` | `INTEGER`/`BIGINT`/`NUMERIC(p)` | Escolha pelo intervalo real |
| `NUMBER(p,s)` | `NUMERIC(p,s)` | Preserva precisão |
| `VARCHAR2(n)` | `VARCHAR(n)` | Atenção a bytes vs caracteres |
| `DATE` (inclui hora) | `TIMESTAMP(0)` | **Oracle DATE tem hora**, não é só data |
| `TIMESTAMP WITH TIME ZONE` | `TIMESTAMPTZ` | |
| `CLOB` | `TEXT` | LOB |
| `BLOB`/`RAW` | `BYTEA` | |
| `CHAR(n)` | `CHAR(n)` | Padding semelhante |

| Origem (SQL Server) | Destino (PostgreSQL) | Observação |
|---|---|---|
| `INT`/`BIGINT` | `INTEGER`/`BIGINT` | |
| `DATETIME`/`DATETIME2` | `TIMESTAMP` | |
| `NVARCHAR(n)` | `VARCHAR(n)` | PostgreSQL usa UTF-8 |
| `BIT` | `BOOLEAN` | |
| `UNIQUEIDENTIFIER` | `UUID` | |
| `MONEY` | `NUMERIC(19,4)` | |
| `VARBINARY(MAX)` | `BYTEA` | |
| `IDENTITY` | `GENERATED ... AS IDENTITY` / `SERIAL` | Ajustar sequences após a carga |

Casos clássicos de armadilha:

- **Oracle trata string vazia como NULL**; PostgreSQL **não**. Consultas `WHERE coluna IS NULL` mudam de comportamento.
- **Sensibilidade de caixa**: SQL Server costuma ser case-insensitive por collation; PostgreSQL é case-sensitive por padrão.
- **Ordenação (collation)** altera o `ORDER BY` e índices únicos.
- **Divisão inteira** e conversões implícitas diferem.
- **Datas**: fusos e funções `SYSDATE`/`GETDATE()` vs `NOW()`/`CURRENT_TIMESTAMP`.

## 5. Código procedural

| Objeto | Dificuldade | Observações |
|---|---|---|
| Tabelas, PK, UK, índices, constraints | Baixa | Conversão quase total |
| Views simples | Baixa/média | Funções específicas precisam de troca |
| Sequences | Baixa | Ajustar valor inicial após a carga |
| Procedures e functions | Média/alta | Sintaxe e semântica de exceção diferem |
| **Packages Oracle** | Alta | PostgreSQL não tem packages; viram schemas com funções |
| Triggers | Média | Reescrever com `RETURNS TRIGGER` |
| Jobs (DBMS_SCHEDULER) | Alta | Substituir por **EventBridge Scheduler, Lambda ou pg_cron** |
| **Database links** | Alta | Reavaliar arquitetura (FDW, ETL, API) |
| Tipos de objeto / coleções | Alta | Redesenhar |

Exemplo de ajuste manual comum (Oracle → PostgreSQL):

```sql
-- Oracle
SELECT NVL(desconto, 0), TO_CHAR(data_pedido, 'DD/MM/YYYY'), ROWNUM
FROM pedidos WHERE ROWNUM <= 10;

-- PostgreSQL
SELECT COALESCE(desconto, 0), TO_CHAR(data_pedido, 'DD/MM/YYYY')
FROM pedidos LIMIT 10;
```

A **aplicação** também precisa mudar: drivers JDBC, strings de conexão, SQL embutido e uso de funções proprietárias. Parte do projeto é **adaptar a aplicação**, e a **Babelfish for Aurora PostgreSQL** pode reduzir esse trabalho para aplicações SQL Server ao aceitar o protocolo e boa parte do T-SQL no Aurora PostgreSQL (a compatibilidade deve ser avaliada com o relatório da **Babelfish Compass**).

## 6. Estratégias para Oracle e SQL Server

**Oracle → Aurora PostgreSQL**: o caminho mais comum de **fuga de licenciamento**. Usar Schema Conversion/SCT + DMS (full load + CDC). Considerar a *extension pack*, testar desempenho de consultas (otimizador diferente) e refazer **estatísticas e índices**.

**Oracle → RDS Oracle** (homogêneo): Data Pump para a carga inicial e DMS/GoldenGate para CDC, quando o objetivo é só gerenciar a infraestrutura.

**SQL Server → RDS SQL Server** (homogêneo): backup/restore nativo para S3 e log shipping ou DMS para CDC.

**SQL Server → Aurora PostgreSQL**: Schema Conversion + DMS, ou **Babelfish** para minimizar mudanças na aplicação.

## 7. Destinos analíticos e de streaming

O DMS também alimenta destinos que não são bancos transacionais — muito usados para modernização de dados.

### 7.1 Amazon S3 (data lake)

```bash
aws dms create-endpoint \
  --endpoint-identifier s3-lake \
  --endpoint-type target --engine-name s3 \
  --s3-settings '{"ServiceAccessRoleArn":"arn:aws:iam::123456789012:role/dms-s3-role","BucketName":"meu-lake","BucketFolder":"raw/loja","DataFormat":"parquet","ParquetVersion":"parquet-2-0","CdcPath":"cdc","TimestampColumnName":"dms_ts","IncludeOpForFullLoad":true}'
```

- Formato **Parquet** (colunar, compactado) para Athena/Glue/Redshift Spectrum.
- No **CDC**, o DMS grava arquivos com a coluna **`Op`** (`I`, `U`, `D`) e timestamps, permitindo reconstruir o estado (merge) em Glue/Spark ou formatos como Iceberg/Hudi/Delta.
- Use **particionamento por data** (`DatePartitionEnabled`) para consultas eficientes.

### 7.2 Amazon Redshift

Destino de **data warehouse**. O DMS usa o S3 como área intermediária para o `COPY`. Boas práticas: definir **chaves de distribuição e ordenação**, usar **batch apply**, e entender que Redshift não impõe PK/FK (são informativos), então a lógica de merge precisa ser cuidadosa.

### 7.3 Kinesis Data Streams e Apache Kafka (MSK)

Cada mudança vira um **evento JSON** com metadados (operação, timestamp, tabela). Casos de uso: **CDC para microsserviços**, atualização de caches, pipelines de eventos em tempo real e **Event Sourcing** parcial. Configure `PartitionIncludeSchemaTable` e a **chave de partição** para manter a ordem por entidade.

```json
{
  "data": { "id_pedido": 1001, "status": "PAGO" },
  "metadata": {
    "timestamp": "2026-11-10T12:00:00Z",
    "record-type": "data",
    "operation": "update",
    "schema-name": "loja",
    "table-name": "pedidos"
  }
}
```

### 7.4 Outros

**DynamoDB** (migrar relacional para NoSQL com regras de mapeamento de objetos), **OpenSearch** (indexação de buscas), **DocumentDB** (documento).

## 8. Quando NÃO converter e sim re-arquitetar

Se o banco legado concentra **muita lógica de negócio em PL/SQL** e o objetivo é modernizar, a conversão 1:1 pode apenas transferir a dívida técnica. Alternativas:

- **Replatform primeiro** (Oracle → RDS Oracle), depois modernizar com calma.
- **Extrair a lógica** do banco para serviços (ver padrão strangler fig) antes de trocar o motor.
- **Aceitar** o custo de licença nas cargas legadas e só converter as que valem a pena.

## 9. Plano de testes na migração heterogênea

1. **Testes de dados**: contagem de linhas, checksums, amostragem, validação do DMS.
2. **Testes funcionais**: casos de uso da aplicação sobre o novo banco.
3. **Testes de desempenho**: consultas críticas com volume realista; ajustar índices e estatísticas.
4. **Testes de concorrência e transações**: isolamento, bloqueios, sequences.
5. **Testes de integrações**: relatórios, ETLs e sistemas que acessavam o banco antigo.
6. **Ensaio geral do cutover** (dry run) com cronometragem.

## 10. Erros comuns

> [!bug] Erros comuns
> 1. **Subestimar a conversão de código**, orçando só a replicação de dados.
> 2. **Aceitar o código convertido sem revisão**, levando bugs sutis para produção.
> 3. **Ignorar a semântica de string vazia e NULL** do Oracle.
> 4. **Esquecer de ajustar sequences/identities** após a carga, causando violações de chave.
> 5. **Não testar desempenho**, descobrindo planos de execução ruins só em produção.
> 6. **Migrar sem adaptar a aplicação** (drivers, SQL embutido, funções proprietárias).
> 7. **Collation diferente** causando ordenação e unicidade distintas.
> 8. **Tratar o DMS como conversor de schema.**
> 9. **Gravar CDC no S3 sem estratégia de merge**, ficando com histórico bruto difícil de consultar.
> 10. **Chave de partição inadequada no Kinesis/Kafka**, perdendo a ordem de eventos da mesma entidade.

## 11. Troubleshooting

| Sintoma | Causa provável | Ação |
|---|---|---|
| Procedure convertida falha | Construção sem equivalente | Reescrever manualmente seguindo o item de ação |
| Contagem de linhas igual, dados diferentes | Conversão de tipo/precisão | Comparar colunas com checksums e rever mapeamento de tipo |
| Ordenação diferente | Collation distinta | Alinhar collation ou ajustar índices/consultas |
| Erro de chave duplicada após o cutover | Sequence não atualizada | Reajustar com `setval` ao maior valor |
| Consulta lenta no destino | Estatísticas/índices ausentes | `ANALYZE`, criar índices e revisar planos |
| Arquivos de CDC no S3 difíceis de consumir | Sem merge | Implementar upsert por PK usando a coluna `Op` |

## 12. Resumo rápido

- Heterogênea = tipos, dialeto, código e semântica diferentes; **DMS migra dados, Schema Conversion/SCT convertem schema e código**.
- Rode o **assessment** primeiro; **packages, jobs e database links** são os itens mais difíceis.
- Cuidado com **string vazia/NULL, datas, collation e sequences**.
- Destinos analíticos: **S3 (Parquet + coluna Op), Redshift, Kinesis/Kafka** para CDC e eventos.
- Considere **Babelfish** (SQL Server) e re-arquitetura quando a lógica no banco é grande.

### 🧩 Quiz de Fixação

1. O que diferencia a migração heterogênea da homogênea?
2. Qual ferramenta converte schema e código no console DMS?
3. Por que o Oracle `DATE` exige cuidado ao migrar?
4. Cite dois objetos Oracle de difícil conversão.
5. O que a coluna `Op` representa nos arquivos de CDC no S3?
6. Para que serve a Babelfish?
7. Por que ajustar sequences após o full load?

**Respostas:**

1. Motores diferentes: exige conversão de tipos, dialeto SQL e código procedural.
2. A DMS Schema Conversion (ou a AWS SCT instalada localmente).
3. Porque o `DATE` do Oracle inclui hora, então deve virar timestamp, não date.
4. Packages, jobs do scheduler, database links e tipos de objeto.
5. O tipo da operação: I (insert), U (update) ou D (delete).
6. Permitir que aplicações SQL Server falem com o Aurora PostgreSQL com menos mudanças no código.
7. Porque as sequences não acompanham os dados copiados e podem gerar chaves duplicadas.
