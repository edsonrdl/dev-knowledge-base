### 5.1.1.1. Segurança no uso dos SDKs — gestão de credenciais, menor privilégio, roles em vez de chaves, IMDSv2, segredos, auditoria e rotação

> [!warning] Aviso
> Nomes de políticas gerenciadas, ações IAM, regras do Access Analyzer/GuardDuty e comportamento de rotação abaixo são **de memória e mudam**. **Confirme na documentação do IAM, do STS e do Secrets Manager.** Políticas, comandos e scripts são ilustrativos e **não foram executados**. Chaves e tokens são **placeholders**. **Credenciais vazadas** (em repositórios públicos) costumam ser exploradas em **minutos**: trate vazamento como **incidente**.

## 1. Por que credenciais em código são o risco nº 1

Credenciais AWS de longo prazo (`AKIA…`) **commitadas** em repositórios, **embutidas** em imagens de container, **coladas** em tickets/chats ou **deixadas** em notebooks são **uma das causas mais comuns** de incidentes em nuvem: bots varrem GitHub/imagens públicas e **usam as chaves em minutos** (mineração de criptomoeda, exfiltração, criação de recursos caros).

| Vetor de vazamento | Exemplo |
|---|---|
| **Repositório Git** | `.env`, `config.py`, `terraform.tfvars`, `credentials` commitados |
| **Imagens de container** | `ENV AWS_SECRET_ACCESS_KEY=…`, `COPY ~/.aws` |
| **Logs** | Print de `os.environ`, headers `Authorization`, `--debug` com credenciais |
| **Artefatos de build** | Pacotes/zip/AMI com arquivo de credenciais |
| **Tickets/chats/wikis** | “Cole a chave aqui” |
| **Notebooks/IDEs** | Células com chaves; **telemetria** de editor |
| **Frontend** | Chaves no **JavaScript** do navegador/app mobile |
| **Máquinas de desenvolvedores** | Arquivos `~/.aws/credentials` sem proteção |
| **CI/CD** | Segredos em variáveis **sem mascaramento** |
| **Terceiros** | Ferramentas SaaS com **chaves de longo prazo** |

## 2. A hierarquia de preferência

```
MELHOR   1) Sem credencial: recursos acessados por ROLE do serviço (Lambda/ECS/EC2/EKS)
         2) Credenciais temporárias por federação: SSO (humanos), OIDC (CI/CD), Cognito (apps), Roles Anywhere (on-prem)
         3) AssumeRole entre contas, sessões curtas, MFA/ExternalId
PIOR     4) Chaves de IAM user de longo prazo (último recurso; com restrições e rotação)
```

| Cenário | Solução recomendada |
|---|---|
| **Aplicação em EC2** | **Instance profile** (role) + **IMDSv2** |
| **Containers ECS/Fargate** | **Task role** (e **task execution role** só para puxar imagem/logs) |
| **EKS** | **IRSA** ou **EKS Pod Identity** (role por **service account**) |
| **Lambda** | **Execution role** |
| **CodeBuild/CodePipeline** | **Service role** do projeto |
| **GitHub Actions/GitLab CI** | **OIDC** → `AssumeRoleWithWebIdentity` (trust restrita a **repo/branch**) |
| **Desenvolvedores** | **IAM Identity Center (SSO)**; **sem chaves locais** |
| **Servidores on-premises** | **IAM Roles Anywhere** (certificados) / **SSM hybrid** |
| **Parceiros/terceiros** | **AssumeRole** com **ExternalId** + permissões mínimas |
| **Apps web/mobile (clientes)** | **Cognito Identity Pools**; **nunca** chaves no cliente |
| **Acesso temporário a S3** | **Presigned URLs** com **expiração curta** |

## 3. Menor privilégio para aplicações

### 3.1 Princípios

1. **Uma role por aplicação/função** (não compartilhar “role mestre”).
2. **Ações específicas** (`dynamodb:GetItem`, `PutItem`), **recursos específicos** (ARNs), **condições** (`dynamodb:LeadingKeys`, `s3:prefix`, `aws:SourceVpce`).
3. **Evitar `*`** em ação e recurso.
4. **Separar** leitura/escrita/admin.
5. **Permission boundaries** e **SCPs** como **guardrails**.
6. **Revisar** com **IAM Access Analyzer** (policy generation por **CloudTrail**), **last accessed**.
7. **Testar** com **IAM Policy Simulator** e ambientes **não produtivos**.

### 3.2 Exemplo (Lambda que lê de uma tabela e grava em um bucket)

```json
{
  "Version": "2012-10-17",
  "Statement": [
    { "Sid": "LerPedidos", "Effect": "Allow",
      "Action": ["dynamodb:GetItem", "dynamodb:Query"],
      "Resource": ["arn:aws:dynamodb:us-east-1:123456789012:table/pedidos", "arn:aws:dynamodb:us-east-1:123456789012:table/pedidos/index/*"] },
    { "Sid": "GravarRelatorios", "Effect": "Allow",
      "Action": ["s3:PutObject"],
      "Resource": "arn:aws:s3:::relatorios-123456789012/saida/*" },
    { "Sid": "UsarChave", "Effect": "Allow",
      "Action": ["kms:GenerateDataKey", "kms:Decrypt"],
      "Resource": "arn:aws:kms:us-east-1:123456789012:key/<id>" }
  ]
}
```

### 3.3 Restrições adicionais por condição

| Condição | Uso |
|---|---|
| **`aws:SourceVpce` / `aws:SourceIp`** | Só aceitar chamadas **da VPC/IPs** esperados |
| **`aws:PrincipalOrgID`** | Restringir a **organização** |
| **`aws:RequestedRegion`** | Limitar **regiões** |
| **`aws:MultiFactorAuthPresent`** | Exigir **MFA** (humanos) |
| **`aws:SecureTransport`** | Exigir **TLS** |
| **`aws:PrincipalTag/ResourceTag`** | **ABAC** |
| **`aws:SourceArn`/`aws:SourceAccount`** | **Confused deputy** (serviços chamando seus recursos) |
| **`dynamodb:LeadingKeys`** | **Isolamento por tenant** |

## 4. IMDSv2 e metadados

| Aspecto | Detalhe |
|---|---|
| **Risco IMDSv1** | **SSRF** em aplicações web permite **ler credenciais da role** em `169.254.169.254` |
| **IMDSv2** | Exige **token de sessão** (PUT + header), **mitiga SSRF** |
| **Configuração** | **`HttpTokens=required`**, **`HttpPutResponseHopLimit=1`** (instâncias); **2** para **containers** que precisam acessar o IMDS |
| **Imposição** | **SCP/IAM condition** (`ec2:MetadataHttpTokens`) para **exigir IMDSv2** nas launch templates/instâncias |
| **Alternativas** | Em containers/ECS use **task role** (endpoint de credenciais do container); em EKS **IRSA/Pod Identity** (e **bloquear acesso** ao IMDS dos pods) |

## 5. Segredos: Secrets Manager e Parameter Store

| Necessidade | Solução |
|---|---|
| **Senhas de banco, API keys de terceiros, tokens** | **AWS Secrets Manager** (**rotação** automática, **KMS**, **resource policy**, **replicação** multi-região) |
| **Configuração/segredos simples** | **SSM Parameter Store** (**SecureString**, **KMS**, hierarquia, mais barato) |
| **No código** | **Buscar em runtime** (SDK) e **cachear** (Powertools Parameters, **Lambda extension**); **não** em variáveis de ambiente **em texto** quando possível (Lambda: variáveis são **visíveis** a quem tem `lambda:GetFunctionConfiguration` — **criptografar com KMS CMK** ou buscar em runtime) |
| **Conexão com RDS** | **IAM database authentication** (token temporário) ou **Secrets Manager** com **rotação**; **RDS Proxy** |
| **Rotação** | **Lambda de rotação** (Secrets Manager) com **zero downtime** (estratégia **alternating users**) |
| **Detecção de segredos em código** | **git-secrets**, **gitleaks**, **trufflehog**, **GitHub secret scanning**, **CodeGuru Security**, **Amazon Q** |

```python
import boto3, json, time
sm = boto3.client("secretsmanager")
_cache = {"valor": None, "ate": 0}

def segredo_banco():
    if time.time() > _cache["ate"]:
        v = sm.get_secret_value(SecretId="prod/pedidos/db")["SecretString"]
        _cache.update(valor=json.loads(v), ate=time.time() + 300)       # cache curto + refresh
    return _cache["valor"]
```

## 6. Chaves de longo prazo: quando inevitáveis

| Controle | Detalhe |
|---|---|
| **Justificar** | Documentar **por que** não dá para usar role/SSO/OIDC |
| **Menor privilégio** e **condições** (`aws:SourceIp`, `aws:SourceVpce`) | Limitar o dano |
| **Rotação** | **90 dias** (ou menos); **duas chaves** por usuário (rotação **sem downtime**) |
| **Inventário** | **Credential report** (`aws iam generate-credential-report`) — idade, último uso |
| **Detecção de inatividade** | **Desativar/excluir** chaves **não usadas** (**IAM last used**) |
| **Alarmes** | Uso **fora do padrão** (GuardDuty `UnauthorizedAccess:IAMUser/...`, `CredentialAccess`) |
| **Armazenamento** | **Cofre** (Secrets Manager), **nunca** em repositório |
| **Escopo humano** | Usuários IAM **só** para **break-glass**/legado; **MFA** |
| **SCP/IAM** | **Negar criação** de chaves de acesso para usuários (`iam:CreateAccessKey`) onde possível |

```bash
aws iam generate-credential-report && aws iam get-credential-report --query Content --output text | base64 -d | csvlook
aws iam list-access-keys --user-name app-legada
aws iam update-access-key --user-name app-legada --access-key-id AKIAEXEMPLO --status Inactive     # desativar antes de excluir
aws iam get-access-key-last-used --access-key-id AKIAEXEMPLO
```

## 7. Resposta a vazamento de credenciais

```
Credencial exposta?
 1) DESATIVAR a chave imediatamente (UpdateAccessKey Inactive) / revogar sessões da role (aws:TokenIssueTime deny)
 2) NÃO apagar logo: investigar com CloudTrail (o que foi feito com a chave?) — depois excluir
 3) Verificar recursos criados (EC2/Lambda/roles/usuários/chaves), exfiltração (S3/RDS snapshots), mudanças de IAM
 4) Revogar sessões temporárias derivadas (política de revogação) e rotacionar segredos acessados
 5) Corrigir a causa (remover do repositório + reescrever histórico; segredos em cofre; bloquear commit)
 6) Notificar (segurança, jurídico/DPO se dados), registrar o incidente; AWS Support se necessário
```

**Revogar sessões ativas** de uma role (emergência): anexar **política de negação** com `aws:TokenIssueTime` anterior ao agora:

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Deny", "Action": "*", "Resource": "*",
    "Condition": { "DateLessThan": { "aws:TokenIssueTime": "2026-11-12T12:00:00Z" } }
  }]
}
```

## 8. Auditoria e detecção

| Fonte | O que mostra |
|---|---|
| **CloudTrail** | **Toda chamada de API** (quem, de onde, o quê); **`userIdentity`** (tipo, `accessKeyId`, `sessionContext`, `sourceIdentity`) |
| **IAM Access Analyzer** | **Acesso externo** a recursos; **geração de políticas** a partir de CloudTrail; **findings de acesso não usado** |
| **IAM last accessed** | **Serviços/ações** **realmente usados** por role/usuário (reduzir permissões) |
| **Credential report** | Idade/uso de **senhas/chaves/MFA** |
| **GuardDuty** | **Credenciais comprometidas** (uso de **IP/região/horário** anômalos, **Tor**, **EC2 credential exfiltration**) |
| **Security Hub/Config** | Regras: `iam-user-no-policies-check`, `access-keys-rotated`, `iam-root-access-key-check`, `ec2-imdsv2-check` |
| **Macie** | Segredos/PII em **S3** |
| **CodeGuru Security/Amazon Inspector (code)** | **Segredos em código** |
| **Secret scanning (SCM)** | Push protection |

### 8.1 Alarmes recomendados

- **Uso da conta raiz**; **criação de chaves de acesso**; **chaves usadas** de **região/IP** inesperados;
- **`ConsoleLogin` sem MFA**; **mudanças em políticas IAM**;
- **`AssumeRole` anômalo** (frequência, origem, `SourceIdentity`);
- **Chaves antigas** (> 90 dias) ou **sem uso** (> 45 dias);
- **Uso de credenciais EC2 fora da instância** (GuardDuty).

## 9. Governança

| Tema | Prática |
|---|---|
| **Política de credenciais** | **Proibir** chaves de longo prazo em aplicações; exceções **aprovadas** e **rastreadas** |
| **Padrões de projeto** | **Templates** (IaC) com **roles**, **IMDSv2**, **sem chaves** |
| **Pipeline** | **Secret scanning** no PR/CI; **bloqueio** de commits com segredos |
| **Educação** | Onboarding: **SSO**, **perfis**, **não colar credenciais** |
| **SCPs** | `Deny iam:CreateAccessKey`/`iam:CreateUser` (conforme maturidade), **exigir IMDSv2**, **limitar regiões** |
| **Revisões** | **Trimestral**: roles não usadas, permissões excessivas, chaves antigas |
| **Break-glass** | Contas/roles de emergência **documentadas**, **MFA**, **alarme** de uso |
| **Inventário** | **Todas** as identidades (humanas e de máquina) com **dono** |

## 10. Checklist de segurança no uso dos SDKs

- [ ] **Nenhuma chave** em código/imagens/repositórios; **secret scanning** ativo
- [ ] **Roles** para cargas na AWS; **SSO** para humanos; **OIDC** para CI/CD
- [ ] **Menor privilégio** (ações/recursos/condições); **boundaries/SCPs**
- [ ] **IMDSv2 obrigatório**; **hop limit** adequado; pods sem acesso ao IMDS
- [ ] **Segredos** em **Secrets Manager/Parameter Store** (KMS), **rotação**, **cache** em runtime
- [ ] **Chaves de longo prazo** inventariadas, rotacionadas (≤ 90 dias), desativadas se sem uso
- [ ] **CloudTrail**, **GuardDuty**, **Access Analyzer**, **Config rules** com **alarmes**
- [ ] **Procedimento** de resposta a vazamento (desativar, investigar, revogar sessões)
- [ ] **Logs** **sem** credenciais/headers de autorização
- [ ] **Revisões** trimestrais e **educação** das equipes

## 11. Erros comuns

- **Chaves no repositório** (ou `.env` versionado).
- **Role “admin” para tudo**.
- **Credenciais no frontend**.
- **IMDSv1 habilitado**.
- **Variáveis de ambiente do Lambda** com segredos **sem KMS/rotação**.
- **Nunca rotacionar** chaves.
- **Excluir a chave vazada** sem investigar CloudTrail.
- **Usuários IAM compartilhados**.
- **Logs de debug** com credenciais.
- **Pipelines com chaves** em vez de OIDC.
- **Trust policy aberta** (`Principal: *`) em roles de OIDC/AssumeRole.

## 12. Troubleshooting

| Sintoma | Causa provável | Ação |
|---|---|---|
| Alerta de GuardDuty: credenciais usadas fora da EC2 | Exfiltração via SSRF/IMDSv1 | Isolar, revogar sessões, exigir IMDSv2 |
| `AccessDenied` após endurecer | Permissão faltando/condição | Access Analyzer/CloudTrail; ajustar com precisão |
| OIDC não assume role | Trust policy (`sub`/`aud`/repo/branch) | Corrigir condições |
| Secrets Manager `AccessDenied` | Policy/KMS/resource policy | Ajustar a role e a key policy |
| Chave “ativa” sem dono | Sem inventário | Credential report; desativar; investigar |
| Muitos segredos no código | Sem scanning | Ativar scanning; rotacionar; reescrever histórico |
| Role chaining expira em 1 h | Limite do encadeamento | Repensar arquitetura/sessões |
| Pods acessam credenciais do nó | IMDS acessível | Bloquear IMDS; usar IRSA/Pod Identity |

## 13. Resumo rápido

- **Maior risco**: **chaves de longo prazo** vazadas; **preferir** **roles** (EC2/ECS/Lambda/EKS), **SSO** (humanos), **OIDC** (CI/CD), **Cognito** (clientes), **Roles Anywhere** (on-prem), **AssumeRole+ExternalId** (terceiros).
- **Menor privilégio**: ações/recursos/condições específicos, **uma role por app**, **Access Analyzer/last accessed**, **boundaries/SCPs**.
- **IMDSv2** obrigatório (mitiga SSRF); containers: **task role/IRSA/Pod Identity**.
- **Segredos**: **Secrets Manager** (rotação) / **Parameter Store**; **buscar em runtime + cache**; **secret scanning**.
- **Chaves inevitáveis**: **rotação ≤ 90 dias**, **duas chaves**, **inventário**, **desativar inativas**.
- **Vazamento**: **desativar → investigar (CloudTrail) → revogar sessões (`aws:TokenIssueTime`) → rotacionar → corrigir causa**.
- **Auditoria**: **CloudTrail, GuardDuty, Access Analyzer, Config/Security Hub**.

## 🧩 Quiz de Fixação

1. Qual a ordem de preferência de credenciais?
2. Por que IMDSv2 é importante?
3. Como autenticar o GitHub Actions sem chaves?
4. Qual o passo imediato ao detectar uma chave vazada?
5. Como revogar sessões temporárias ativas de uma role?
6. Onde guardar senhas de banco e como evitar expor segredos no código?
7. Que fontes ajudam a reduzir permissões excessivas?

**Respostas:**

1. Sem credencial (roles de serviço), credenciais temporárias por federação (SSO/OIDC/Cognito/Roles Anywhere), AssumeRole com sessões curtas e, por último, chaves de longo prazo.
2. Porque exige token de sessão e mitiga SSRF, impedindo que uma aplicação vulnerável revele credenciais da role pelo serviço de metadados.
3. Com OIDC: o workflow assume uma role via AssumeRoleWithWebIdentity, com trust policy restrita ao repositório e branch.
4. Desativar a chave imediatamente (mantendo-a para investigação) e então investigar o uso no CloudTrail.
5. Anexando uma política de negação com condição aws:TokenIssueTime anterior ao momento atual, invalidando as sessões emitidas antes.
6. Em Secrets Manager (com rotação) ou Parameter Store SecureString, buscando em runtime com cache e usando secret scanning para impedir segredos no código.
7. IAM Access Analyzer (geração de políticas e acesso não usado), IAM last accessed e CloudTrail, validados com o Policy Simulator.
