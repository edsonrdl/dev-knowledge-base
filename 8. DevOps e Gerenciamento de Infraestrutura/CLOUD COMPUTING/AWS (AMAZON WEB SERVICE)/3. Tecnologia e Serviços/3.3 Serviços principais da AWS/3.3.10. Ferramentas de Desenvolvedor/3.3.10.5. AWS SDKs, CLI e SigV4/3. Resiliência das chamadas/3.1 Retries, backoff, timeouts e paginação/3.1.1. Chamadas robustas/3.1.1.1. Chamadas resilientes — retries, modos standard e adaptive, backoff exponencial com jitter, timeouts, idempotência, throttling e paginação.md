### 3.1.1.1. Chamadas resilientes — retries, modos standard e adaptive, backoff exponencial com jitter, timeouts, idempotência, throttling e paginação

> [!warning] Aviso
> Valores padrão de tentativas, timeouts, modos de retry e nomes de parâmetros variam por **SDK e versão** (Boto3, JS v3, Java v2, Go…) e mudam. **Confirme na documentação “Retry behavior” e “Timeouts” do seu SDK.** Código e fórmulas são ilustrativos e **não foram executados**. Parâmetros numéricos de exemplo (tentativas, tempos) são **pontos de partida** a medir, não recomendações universais.

## 1. Por que chamadas à AWS falham (e por que isso é normal)

Sistemas distribuídos **falham de formas transitórias**: **throttling** (limites de taxa), **erros 5xx** internos, **timeouts**, **quedas de conexão**, **réplicas** temporariamente indisponíveis. Uma chamada que falha agora **provavelmente funciona** se repetida **com cuidado**.

| Categoria | Exemplos | **Tentar de novo?** |
|---|---|---|
| **Transitórios** | `ThrottlingException`, `ProvisionedThroughputExceededException`, `RequestLimitExceeded`, **S3 503 SlowDown**, **HTTP 500/502/503/504**, **timeouts**, **resets de conexão**, `RequestTimeout` | **Sim** (com **backoff + jitter**) |
| **Erros do cliente** (permanentes) | `ValidationException`, `AccessDenied`, `InvalidParameter`, `ResourceNotFoundException`, `ConditionalCheckFailedException` | **Não** (repetir **não** resolve) |
| **Conflitos** | `ConflictException`, `TransactionConflict`, **concurrency** | **Talvez** (com **reavaliação** do estado) |
| **Credenciais expiradas** | `ExpiredToken` | **Renovar** e tentar (o SDK faz se o provider renova) |

> [!info] Princípio
> **Retry resolve falhas transitórias — e piora falhas de carga se feito errado.** Sem **backoff** e **jitter**, milhares de clientes **repetem juntos** e causam **“thundering herd”** (tempestade de retries) que **prolonga** a falha.

## 2. Retries nos SDKs

### 2.1 O que o SDK faz por padrão

| Aspecto | Detalhe (de memória — confirmar por SDK) |
|---|---|
| **Retries automáticos** | **Habilitados** por padrão (**3–5 tentativas** totais, conforme SDK/modo) |
| **Erros retentados** | **Throttling**, **5xx**, **timeouts**, **erros de conexão**, **expiração de relógio** (recalcula assinatura) |
| **Erros não retentados** | **4xx de cliente** (validação, permissão, não encontrado) |
| **Backoff** | **Exponencial com jitter** |
| **Configuração** | **Código** (`Config(retries=…)`), **variáveis** (`AWS_MAX_ATTEMPTS`, `AWS_RETRY_MODE`), **arquivo de config** (`max_attempts`, `retry_mode`) |
| **Serviço específico** | **DynamoDB** tem **limites e padrões próprios** (ex.: mais tentativas e **base** menor) |

### 2.2 Modos de retry

| Modo | Descrição (de memória — confirmar) |
|---|---|
| **legacy** | Comportamento **antigo** (padrão em alguns SDKs mais antigos); **menos consistente** entre SDKs |
| **standard** | **Padrão moderno**: **máximo de tentativas**, **backoff exponencial com jitter**, **lista consistente** de erros retentáveis, e **retry quota** (limite global de retries por cliente — ver abaixo) |
| **adaptive** | **Standard + limitação de taxa no cliente** (*client-side rate limiting*): reduz a **velocidade de envio** quando detecta **throttling** (ajusta com **token bucket**) — **experimental/avançado** (confirmar) |

```python
from botocore.config import Config
cfg_standard = Config(retries={"mode": "standard", "max_attempts": 5})
cfg_adaptive = Config(retries={"mode": "adaptive", "max_attempts": 10})
```

```bash
export AWS_RETRY_MODE=standard
export AWS_MAX_ATTEMPTS=5
```

```javascript
// JS v3
const client = new S3Client({ maxAttempts: 5, retryMode: "STANDARD" });
```

```java
// Java v2
S3Client s3 = S3Client.builder()
    .overrideConfiguration(o -> o.retryStrategy(RetryMode.STANDARD))
    .build();
```

### 2.3 Retry quota (token bucket de retries)

No modo **standard**, o SDK mantém um **balde de tokens** de retry: cada **retry consome** tokens (mais em **timeouts**), e **sucessos devolvem** tokens. Se o balde **esvazia**, o SDK **para de tentar de novo** (**fail fast**) — **protege o serviço** de **amplificação** durante falhas **prolongadas**.

| Efeito | Detalhe |
|---|---|
| **Durante falha geral** | O balde esvazia → **poucos retries** → **menos pressão** no serviço |
| **Durante falhas esporádicas** | Retries funcionam normalmente |
| **Relevância** | Evita **retry storms** de um mesmo cliente |

## 3. Backoff exponencial com jitter

### 3.1 O conceito

**Esperar mais** a cada tentativa (**exponencial**) e **aleatorizar** a espera (**jitter**) para **dessincronizar** clientes.

```
Tentativa 1 falha ─▶ espera ~ U(0, base × 2^0)  =  U(0, 100 ms)
Tentativa 2 falha ─▶ espera ~ U(0, base × 2^1)  =  U(0, 200 ms)
Tentativa 3 falha ─▶ espera ~ U(0, base × 2^2)  =  U(0, 400 ms)
…                     limitado por um TETO (cap), ex.: 20 s
```

### 3.2 Variantes de jitter

| Variante | Fórmula | Característica |
|---|---|---|
| **Sem jitter** | `min(cap, base × 2^n)` | **Sincroniza** clientes (**ruim**) |
| **Full jitter** | `U(0, min(cap, base × 2^n))` | **Melhor dispersão** (recomendado pela AWS) |
| **Equal jitter** | `x/2 + U(0, x/2)`, `x=min(cap, base×2^n)` | Metade fixa + aleatória |
| **Decorrelated jitter** | `min(cap, U(base, prev × 3))` | Dependente do anterior |

### 3.3 Implementação própria (quando o SDK não cobre)

```python
import random, time

def com_retry(fn, tentativas=6, base=0.1, teto=10.0, retentaveis=(TimeoutError, ConnectionError)):
    for n in range(tentativas):
        try:
            return fn()
        except retentaveis:
            if n == tentativas - 1:
                raise
            time.sleep(random.uniform(0, min(teto, base * (2 ** n))))   # full jitter
```

> [!warning] Não empilhe retries
> **Retry no SDK × retry na aplicação × retry no cliente HTTP × retry no orquestrador** se **multiplicam** (3×3×3 = **27** tentativas por falha). **Defina onde** o retry acontece (em geral, **no SDK**) e **desative/limite** os demais.

## 4. Timeouts

### 4.1 Tipos

| Timeout | Significado | Risco se ausente |
|---|---|---|
| **Connect timeout** | Tempo para **estabelecer** a conexão TCP/TLS | Fica **pendurado** com endpoint inalcançável |
| **Read/socket timeout** | Tempo **sem receber dados** da resposta | **Threads/conexões presas** |
| **Total/operação (API call timeout)** | Limite **total** da chamada (incluindo retries) | Chamada **indefinida** |
| **Per-attempt timeout** | Limite por **tentativa** | Uma tentativa **lenta** consome o orçamento |
| **Timeout do contexto** (Lambda/HTTP server) | Tempo restante da **invocação** | **Timeout do Lambda** antes de terminar |

### 4.2 Padrões típicos e orientações (de memória — confirmar)

| SDK | Padrões (aprox.) |
|---|---|
| **Boto3** | connect **60 s**, read **60 s** |
| **JS v3** | Sem timeout de requisição por padrão em alguns handlers (configurar `requestHandler`) |
| **Java v2** | Varia por HTTP client (**Apache/Netty/CRT**); **API call timeout** configurável |

Recomendações (ponto de partida):

| Cenário | Orientação |
|---|---|
| **APIs rápidas** (DynamoDB, SQS, SNS) | **connect 1–3 s**, **read 3–10 s** |
| **Chamadas pesadas** (S3 grandes, Lambda longa) | Ajustar **read**/**total** ao **p99** + folga |
| **Lambda** | **Timeout total** < **timeout da função** (reservar **margem** para erro/cleanup); usar `context.get_remaining_time_in_millis()` |
| **Orçamento de retries** | `(tentativas × timeout por tentativa) + soma de backoffs` ≤ **timeout total** |
| **Fail fast** | Melhor **falhar rápido** e **degradar** do que **bloquear** a aplicação |

```python
# Respeitando o tempo restante do Lambda
def handler(event, context):
    restante_ms = context.get_remaining_time_in_millis()
    cfg = Config(connect_timeout=2, read_timeout=min(10, max(1, restante_ms // 1000 - 2)), retries={"max_attempts": 3})
```

### 4.3 Timeouts em cascata

```
Cliente HTTP (30 s) → API Gateway (29 s máx.) → Lambda (timeout 10 s) → DynamoDB (read 3 s × 3 tentativas)
```

Cada **camada** deve ter **timeout menor** que a **camada acima**, para que **a falha seja tratada em baixo** (e **não** estoure em cima).

## 5. Throttling e limites (quotas)

### 5.1 Fontes de throttling

| Serviço | Sinal |
|---|---|
| **DynamoDB** | `ProvisionedThroughputExceededException` (capacidade/partição quente), `ThrottlingException` |
| **S3** | **503 Slow Down** (muitas requisições por prefixo) |
| **API Gateway** | **429 Too Many Requests** (limites de conta/estágio/método/uso) |
| **Lambda** | `TooManyRequestsException` (concorrência) |
| **SQS** | `OverLimit`/`RequestThrottled` (raro) |
| **KMS/STS/SSM/CloudWatch** | `ThrottlingException`/`Rate exceeded` |
| **EC2 APIs** | `RequestLimitExceeded` |

### 5.2 Estratégias

| Estratégia | Detalhe |
|---|---|
| **Backoff + jitter** | Resposta imediata |
| **Reduzir concorrência/taxa** | **Rate limiter**/semáforo/**token bucket** no cliente; modo **adaptive** |
| **Batching** | `BatchWriteItem`, `SendMessageBatch`, `PutRecords`: **menos chamadas** (tratar `UnprocessedItems`/falhas parciais!) |
| **Cache** | Evitar chamadas repetidas (parâmetros, segredos, metadados) |
| **Distribuir carga** | **Prefixos S3**, **chaves** de partição **uniformes** (DynamoDB) |
| **Aumentar limites** | **Service Quotas**; **capacidade** (on-demand/auto scaling) |
| **Filas** | **SQS** para **absorver picos** e processar na **taxa** possível |
| **Circuit breaker** | **Parar** de chamar um serviço **degradado** por um tempo |
| **Hedging cuidadoso** | Enviar **requisição duplicada** só para operações **idempotentes** (reduz latência de cauda) |

### 5.3 Falhas parciais em operações em lote

```python
resp = ddb.batch_write_item(RequestItems={"pedidos": [...]})
pendentes = resp.get("UnprocessedItems", {})
tentativa = 0
while pendentes and tentativa < 6:
    time.sleep(random.uniform(0, min(5, 0.1 * 2 ** tentativa)))
    resp = ddb.batch_write_item(RequestItems=pendentes)
    pendentes = resp.get("UnprocessedItems", {})
    tentativa += 1
# pendentes ainda não vazio → DLQ/alarme
```

> O SDK **não** repete `UnprocessedItems` por você: **200 OK** com itens **não processados** é **sucesso HTTP**, **falha parcial** de negócio.

## 6. Idempotência

### 6.1 Por que importa

Com retries, a **mesma operação pode ser executada duas vezes** (a primeira **teve sucesso**, mas a **resposta se perdeu**). Para **criar** recursos/cobranças/pedidos, isso gera **duplicatas**.

| Mecanismo | Uso |
|---|---|
| **`ClientToken` / `ClientRequestToken` / `IdempotencyToken`** | **Token único** por **intenção** (EC2 `RunInstances`, RDS, ECS, Step Functions `StartExecution` **name**, Lambda **event ID**) |
| **Chaves de idempotência próprias** | **Pedido ID** como **chave** (DynamoDB **condition expression** `attribute_not_exists`) |
| **Operações naturalmente idempotentes** | `PutObject` (sobrescreve), `DeleteObject`, `TagResource` (conjunto), `UpdateItem SET` |
| **Não idempotentes** | `UpdateItem ADD` (incremento), **append**, **envio de e-mail/pagamento** |
| **Lambda Powertools Idempotency** | Armazena **resultado** por **chave** (DynamoDB) para **evitar reexecução** |
| **SQS/SNS/EventBridge** | **At-least-once**: consumidores **precisam** ser idempotentes (**FIFO** tem **deduplicação** por 5 min) |

```python
import uuid
token = str(uuid.uuid4())                         # gerar UMA vez por intenção e reutilizar nos retries
ec2.run_instances(ImageId="ami-0abc", MinCount=1, MaxCount=1, ClientToken=token)
```

```python
# DynamoDB: inserir só se não existir (idempotente por chave)
tabela.put_item(Item={"pedido_id": pid, ...}, ConditionExpression="attribute_not_exists(pedido_id)")
```

## 7. Paginação

### 7.1 O problema

Muitas operações **limitam o tamanho da resposta** (ex.: **1 MB** no DynamoDB, **1.000** objetos no S3, **N** itens por chamada). A resposta traz um **token** para a **próxima página**. **Ignorar** a paginação leva a **resultados incompletos** (bug silencioso!).

| Serviço | Operação | Token/Parâmetro |
|---|---|---|
| **S3** | `ListObjectsV2` | `ContinuationToken` / `NextContinuationToken` (`IsTruncated`) |
| **DynamoDB** | `Query`/`Scan` | `LastEvaluatedKey` → `ExclusiveStartKey` |
| **EC2/IAM/Lambda/RDS…** | `Describe*`/`List*` | `NextToken`/`Marker`/`NextMarker` |
| **CloudWatch Logs** | `FilterLogEvents`/`GetLogEvents` | `nextToken`/`nextForwardToken` |
| **SQS** | `ReceiveMessage` | **Não pagina** (batch até 10; poll de novo) |

### 7.2 Paginators (SDK/CLI)

```python
# Boto3: paginator esconde o loop
paginator = s3.get_paginator("list_objects_v2")
for pagina in paginator.paginate(Bucket="meu-bucket", Prefix="2026/", PaginationConfig={"PageSize": 500}):
    for obj in pagina.get("Contents", []):
        processar(obj["Key"])
```

```javascript
// JS v3
import { paginateListObjectsV2, S3Client } from "@aws-sdk/client-s3";
for await (const pagina of paginateListObjectsV2({ client: new S3Client({}) }, { Bucket: "meu-bucket", Prefix: "2026/" })) {
  for (const obj of pagina.Contents ?? []) processar(obj.Key);
}
```

```python
# DynamoDB Query com paginação manual
args = {"TableName": "pedidos", "KeyConditionExpression": "cliente_id = :c", "ExpressionAttributeValues": {":c": {"S": "42"}}}
while True:
    r = ddb.query(**args)
    processar(r["Items"])
    if "LastEvaluatedKey" not in r: break
    args["ExclusiveStartKey"] = r["LastEvaluatedKey"]
```

### 7.3 CLI: paginação e `--query`

| Opção | Efeito |
|---|---|
| **(padrão)** | A CLI **pagina automaticamente** (todas as páginas) |
| `--page-size N` | Itens por **chamada** (reduz **timeouts** em listas grandes) |
| `--max-items N` | **Limita o total** retornado (e emite `NextToken`) |
| `--starting-token` | **Retomar** a partir de um token |
| `--no-paginate` | **Só a primeira página** |
| `--query` | Filtro **no cliente** (após buscar tudo) — **não reduz custo/tempo** de chamadas |
| `--filter-expression`/`--filters` | Filtro **no servidor** (DynamoDB scan filter **ainda lê tudo e cobra RCU**) |

> [!warning] Filtro ≠ economia
> No **DynamoDB**, `FilterExpression` é aplicado **depois** da leitura: você **paga a leitura** de **tudo**. Para eficiência, **modele chaves/índices** para **Query**.

### 7.4 Boas práticas de paginação

- **Sempre paginar** (ou usar **paginators**).
- **Limitar** com `PageSize`/`Limit` conforme latência/memória.
- **Streaming**: processar **página a página** (não carregar tudo).
- **Idempotência**/**checkpoint**: guardar o **último token** para **retomar**.
- **Consistência**: listas podem **mudar** durante a paginação (S3 é **fortemente consistente**; DynamoDB `Scan` **não é snapshot**).
- **Paralelismo** (DynamoDB **parallel scan** com `Segment/TotalSegments`).

## 8. Padrões de resiliência (resumo)

```
Chamada ─▶ [timeout curto] ─▶ falha transitória? ─▶ [retry com backoff+jitter, orçamento limitado]
                                         └─ persiste? ─▶ [circuit breaker] ─▶ [fallback/cache/degradação] ─▶ [DLQ/alarme]
Operações com efeitos ─▶ [idempotência (ClientToken/chave)]
Listagens ─▶ [paginação completa]   Lotes ─▶ [tratar falhas parciais]
```

| Padrão | Quando |
|---|---|
| **Retry + jitter** | Falhas **transitórias** |
| **Timeout** | **Sempre** |
| **Circuit breaker** | Dependência **degradada** prolongada |
| **Bulkhead** | **Isolar** pools/concorrência por dependência |
| **Fallback** | Cache, valor padrão, **modo degradado** |
| **DLQ** | Mensagens/eventos **não processados** |
| **Idempotência** | **Qualquer** operação retentável com efeito |
| **Rate limiting** | Respeitar **limites** |

## 9. Erros comuns

- **Ignorar paginação** (resultados incompletos).
- **Retries sem backoff/jitter** (tempestade).
- **Retries empilhados** em várias camadas.
- **Sem timeouts**.
- **Repetir erros permanentes** (validação, permissão).
- **Ignorar `UnprocessedItems`/falhas parciais**.
- **Operações não idempotentes** com retries (cobranças duplicadas).
- **Timeouts maiores que o da camada superior** (estouram acima).
- **Usar `Scan` + filtro** esperando eficiência.
- **Tentar “ser esperto”** reimplementando retries do SDK sem necessidade.
- **Não limitar a concorrência** (autothrottling).

## 10. Troubleshooting

| Sintoma | Causa provável | Ação |
|---|---|---|
| `ThrottlingException` frequente | Taxa alta/limite | Backoff, rate limit, batching, quotas |
| Latência de cauda alta | Timeouts longos/retries | Timeouts menores; hedging idempotente |
| Duplicatas após falhas | Falta de idempotência | `ClientToken`/chaves/condition |
| Lista incompleta | Sem paginação | Usar paginators/loop |
| Lambda estoura timeout | Retries/timeouts somados > timeout | Orçamento de tempo; `get_remaining_time_in_millis` |
| Retry storm | Sem jitter/camadas empilhadas | Jitter; um nível de retry |
| `ProvisionedThroughputExceeded` com pouco tráfego | **Partição quente** | Redesenhar chave; on-demand |
| Itens perdidos em batch | `UnprocessedItems` ignorados | Reprocessar com backoff |

## 11. Resumo rápido

- **Retry só em falhas transitórias** (throttling, 5xx, timeouts, conexão); **não** em **4xx permanentes**.
- **SDK**: retries automáticos; modos **legacy/standard/adaptive**; **max attempts** via config/env; **retry quota** evita amplificação.
- **Backoff exponencial com jitter** (**full jitter**): dispersa clientes; **teto**; **não empilhar** retries.
- **Timeouts**: **connect/read/total/por tentativa**; **camadas** com timeouts **decrescentes**; respeitar o **tempo restante do Lambda**.
- **Throttling**: backoff, rate limit, batching, cache, filas, quotas, circuit breaker; **tratar falhas parciais** (`UnprocessedItems`).
- **Idempotência**: `ClientToken`, chaves próprias, `ConditionExpression`; consumidores **at-least-once** idempotentes.
- **Paginação**: `NextToken/Marker/ContinuationToken/LastEvaluatedKey`; **paginators**; CLI `--page-size/--max-items/--no-paginate`; **`--query` filtra no cliente**, **FilterExpression não economiza leitura**.

## 🧩 Quiz de Fixação

1. Que tipos de erro devem ser retentados e quais não?
2. Por que usar jitter no backoff?
3. Qual a diferença entre os modos standard e adaptive?
4. Por que não empilhar retries em várias camadas?
5. Como garantir idempotência ao criar uma instância EC2?
6. O que fazer com `UnprocessedItems` em um batch do DynamoDB?
7. Por que `FilterExpression` no Scan não reduz o custo de leitura?

**Respostas:**

1. Retentam-se erros transitórios (throttling, 5xx, timeouts, falhas de conexão); não se retentam erros permanentes do cliente (validação, permissão, não encontrado).
2. Para dessincronizar clientes e evitar picos simultâneos de retentativas (thundering herd), que prolongam a falha.
3. Standard usa backoff com jitter, lista consistente de erros e retry quota; adaptive acrescenta limitação de taxa no cliente que reduz a velocidade quando detecta throttling.
4. Porque as tentativas se multiplicam entre camadas (por exemplo 3×3×3), amplificando a carga e prolongando falhas.
5. Gerando um ClientToken único por intenção e reutilizando-o em todas as tentativas, para que a repetição não crie uma segunda instância.
6. Reenviá-los com backoff e jitter em loop limitado, enviando para DLQ/alarme se persistirem, pois o SDK não os repete e a resposta é 200.
7. Porque o filtro é aplicado depois da leitura dos itens; o DynamoDB lê e cobra RCU de tudo o que foi varrido.
