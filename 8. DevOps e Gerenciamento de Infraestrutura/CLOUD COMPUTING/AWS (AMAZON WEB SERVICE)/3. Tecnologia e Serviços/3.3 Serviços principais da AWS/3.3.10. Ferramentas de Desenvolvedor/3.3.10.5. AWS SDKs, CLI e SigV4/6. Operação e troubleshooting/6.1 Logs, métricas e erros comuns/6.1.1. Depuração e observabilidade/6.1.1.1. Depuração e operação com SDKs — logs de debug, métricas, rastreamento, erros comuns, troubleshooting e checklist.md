### 6.1.1.1. Depuração e operação com SDKs — logs de debug, métricas, rastreamento, erros comuns, troubleshooting e checklist

> [!warning] Aviso
> Nomes de loggers, flags de debug, métricas dos SDKs, códigos de erro e comportamento de cada serviço abaixo são **de memória e mudam por SDK e versão**. **Confirme na documentação do SDK/CLI da sua linguagem.** Comandos e código são ilustrativos e **não foram executados**. **Logs de debug podem conter credenciais e dados sensíveis**: nunca os habilite em produção sem controles, e nunca os publique.

## 1. A mentalidade de depuração

Quando uma chamada AWS “não funciona”, quase sempre o problema cai em **um destes seis blocos**:

```
1) CREDENCIAIS/IDENTIDADE → quem sou eu?                 (NoCredentials, ExpiredToken, identidade errada)
2) AUTORIZAÇÃO            → posso fazer isso?             (AccessDenied: IAM, SCP, resource policy, boundary)
3) ASSINATURA/RELÓGIO     → a requisição é válida?        (SignatureDoesNotMatch, RequestTimeTooSkewed)
4) REDE/ENDPOINT/REGIÃO   → consigo chegar lá?            (timeouts, DNS, proxy, VPC endpoint, região errada)
5) PARÂMETROS/ESTADO      → a requisição faz sentido?     (ValidationException, ResourceNotFound, Conflict)
6) LIMITES/CARGA          → estou pedindo demais?         (Throttling, quotas, 5xx)
```

> [!tip] Método
> **1) Confirmar a identidade** (`aws sts get-caller-identity`). **2) Ler a mensagem/código de erro completos** (e o **RequestId**). **3) Reproduzir com a CLI** (`--debug`). **4) Checar CloudTrail** (a chamada chegou? qual `errorCode`?). **5) Isolar** (rede, permissão, parâmetro). **6) Só então mudar algo.**

## 2. Anatomia de um erro AWS

### 2.1 Campos importantes

| Campo | Significado | Uso |
|---|---|---|
| **Código de erro** (`Error.Code`) | Identificador **estável** (`ThrottlingException`, `AccessDenied`, `ValidationException`) | **Tratar no código** (nunca pela mensagem) |
| **Mensagem** (`Error.Message`) | Texto **humano** (pode mudar) | Diagnóstico/logs |
| **HTTP status** | 2xx/3xx/4xx/5xx | **4xx** = cliente; **5xx** = serviço |
| **RequestId** (`x-amzn-RequestId`, `x-amz-request-id`) | **Identificador** da requisição | **Suporte AWS**, correlação com logs/CloudTrail |
| **Extended RequestId** (`x-amz-id-2` no S3) | Complemento | Suporte |
| **Retry info** (`ResponseMetadata.RetryAttempts`) | Quantos retries o SDK fez | Detectar **throttling oculto** |
| **Tipo de falha** | `Sender` (cliente) vs `Receiver` (serviço) (query protocols) | Classificar |

### 2.2 Tabela de erros comuns

| Erro | Categoria | Causa típica | Ação |
|---|---|---|---|
| `NoCredentialsError` | Credenciais | Chain sem credenciais | Role/perfil/SSO/env |
| `ExpiredToken(Exception)` | Credenciais | Sessão expirou | Renovar (SSO login, provider) |
| `InvalidClientTokenId`/`UnrecognizedClientException` | Credenciais | Chave inválida/excluída/partição | Corrigir a credencial |
| `SignatureDoesNotMatch` | Assinatura | Secret/relógio/região/serviço/headers/encoding | NTP; região; sem proxy alterando headers |
| `RequestTimeTooSkewed` | Relógio | Diferença > ~5 min | NTP |
| `AccessDenied`/`AccessDeniedException`/`UnauthorizedOperation` | Autorização | IAM/SCP/boundary/resource policy/KMS | CloudTrail, Policy Simulator |
| `ValidationException`/`InvalidParameter*`/`ParamValidationError` | Parâmetros | Tipo/formato/campo faltando/limite | Conferir o **modelo** da operação |
| `ResourceNotFoundException`/`NoSuchKey`/`NoSuchBucket` | Estado | Recurso inexistente/**região errada** | Verificar nome/região/ARN |
| `ConditionalCheckFailedException` | Lógica | Condição não satisfeita | Esperado em **idempotência/locking**; tratar |
| `ConflictException`/`TransactionConflict`/`ResourceInUseException` | Concorrência | Operação simultânea/estado | Reavaliar; retry controlado |
| `ThrottlingException`/`TooManyRequestsException`/`SlowDown`/`ProvisionedThroughputExceededException` | Limites | Taxa acima do limite | Backoff, rate limit, quotas |
| `LimitExceeded`/`ServiceQuotaExceeded` | Quotas | Limite de recursos | Service Quotas |
| `InternalError`/`ServiceUnavailable`/`503` | Serviço | Falha transitória | Retry com backoff; health dashboard |
| `RequestTimeout`/`EndpointConnectionError`/`ConnectTimeout` | Rede | DNS/rota/SG/NACL/proxy/endpoint | Testar conectividade; VPC endpoint/região |
| `KMS.AccessDeniedException`/`KMSInvalidStateException` | Criptografia | Key policy/chave desabilitada | Corrigir a key policy/estado |
| `PayloadTooLarge`/`RequestEntityTooLarge` | Limites | Corpo acima do limite | Particionar/usar S3 |

## 3. Logs de debug

### 3.1 CLI

```bash
aws s3 ls --debug 2> debug.log          # requisições/respostas, credenciais usadas (provider), assinatura, retries
aws sts get-caller-identity --debug 2>&1 | grep -i -E 'credentials|provider|region|endpoint'
```

O `--debug` mostra: **de onde vieram as credenciais** (provider), **região/endpoint resolvidos**, **assinatura**, **retries** e **respostas**.

### 3.2 SDKs

```python
# Boto3: logs detalhados
import boto3, logging
boto3.set_stream_logger("botocore", logging.DEBUG)          # tudo (muito verboso; contém headers)
# ou específico:
logging.getLogger("botocore.retries").setLevel(logging.DEBUG)   # ver retries
logging.getLogger("botocore.credentials").setLevel(logging.DEBUG)
```

```javascript
// JS v3: logger no cliente
const client = new S3Client({ logger: console });   // ou um logger que filtre campos sensíveis
```

```java
// Java v2: SLF4J/Log4j2
// logger "software.amazon.awssdk" = DEBUG; "software.amazon.awssdk.request" = DEBUG (requisições)
// "org.apache.http.wire" = DEBUG (wire; MUITO verboso e sensível)
```

```bash
export AWS_SDK_JS_LOG=...        # varia por SDK
```

### 3.3 Higiene de logs

| Regra | Detalhe |
|---|---|
| **Produção**: nível **INFO/WARN**, **debug sob demanda** (feature flag, janela curta) | Logs de debug **vazam** credenciais/dados |
| **Mascarar** | `Authorization`, `X-Amz-Security-Token`, `SecretAccessKey`, PII |
| **Registrar sempre**: **serviço, operação, região, código de erro, status HTTP, RequestId, tentativas, latência** | Correlação |
| **Não registrar**: payloads completos com PII/segredos | Privacidade |
| **Estruturado (JSON)** | CloudWatch Logs Insights |
| **Retenção** | Definida; acesso restrito |

```python
import logging, json
log = logging.getLogger(__name__)
try:
    resp = client.get_item(...)
except ClientError as e:
    m = e.response["ResponseMetadata"]
    log.error(json.dumps({"servico": "dynamodb", "operacao": "GetItem", "codigo": e.response["Error"]["Code"],
                          "status": m["HTTPStatusCode"], "request_id": m.get("RequestId"), "tentativas": m.get("RetryAttempts")}))
    raise
```

## 4. Observabilidade: métricas, logs e traces

### 4.1 O que medir nas chamadas AWS

| Métrica | Por quê |
|---|---|
| **Latência por operação** (p50/p95/p99) | Saúde e **SLOs** |
| **Taxa de erro por código** | **Throttling vs permissão vs serviço** |
| **Retries** (nº, taxa) | **Throttling oculto**/instabilidade |
| **Timeouts** | Rede/serviço lento |
| **Throttles específicos** | Capacidade/limites |
| **Uso de conexões/pool** | Dimensionamento |
| **Tamanho de payload** | Limites/custos |
| **Custo por operação** (S3/DynamoDB) | FinOps |

### 4.2 Como obter

| Mecanismo | Detalhe |
|---|---|
| **Métricas do SDK** | **SDK Metrics** (Java v2 **client-side metrics**, JS/Go **middleware**) → **CloudWatch/OTel** |
| **Instrumentação** | **OpenTelemetry**/**X-Ray SDK** (subsegmentos automáticos por chamada AWS) |
| **Lambda Powertools** | **Logger/Metrics/Tracer** com **EMF** (métricas via logs) |
| **Métricas do serviço** | CloudWatch: `ThrottledRequests`, `SystemErrors`, `ConsumedReadCapacityUnits`, `5xxError` |
| **CloudTrail** | **Chamadas e erros** (`errorCode`, `errorMessage`) por **identidade** |
| **VPC Flow Logs/endpoint logs** | Rede |
| **Application Signals/ServiceLens** | Visão unificada |

### 4.3 Rastreamento (X-Ray/OTel)

```python
from aws_xray_sdk.core import patch_all, xray_recorder
patch_all()                      # instrumenta boto3 → cada chamada AWS vira subsegmento (serviço, operação, tempo, erro)
```

No trace você vê **qual chamada AWS** foi lenta/falhou, **quantos retries** e o **tempo por etapa** — **essencial** em **arquiteturas serverless**.

### 4.4 CloudTrail para depuração

```bash
aws cloudtrail lookup-events --lookup-attributes AttributeKey=EventName,AttributeValue=PutObject --max-results 20 \
  --query 'Events[].{hora:EventTime,usuario:Username,fonte:EventSource,id:EventId}'
# Ou via Athena/CloudTrail Lake: filtrar por errorCode, userIdentity.arn, sourceIPAddress
```

| Campo CloudTrail | Valor para o diagnóstico |
|---|---|
| **`errorCode` / `errorMessage`** | **Causa** da negação/falha |
| **`userIdentity`** (`type`, `arn`, `sessionContext.sessionIssuer`) | **Quem** chamou (role/sessão) |
| **`sourceIPAddress` / `userAgent`** | **De onde** e **com qual SDK/versão** (o **`user_agent_extra`** ajuda) |
| **`requestParameters` / `responseElements`** | **O que** foi pedido |
| **`additionalEventData`** | Detalhes (ex.: **autenticação SigV4**, **tipo de assinatura**) |
| **`eventTime`** | Janelas/correlação |

> CloudTrail (**eventos de gerenciamento**) tem **atraso** (minutos) e **não** inclui **eventos de dados** (S3 objetos, Lambda invoke, DynamoDB itens) **a menos** que **habilitados**.

## 5. Ferramentas de diagnóstico

| Necessidade | Ferramenta |
|---|---|
| **Quem sou eu?** | `aws sts get-caller-identity` |
| **Decodificar mensagem de autorização** | `aws sts decode-authorization-message --encoded-message <msg>` (para erros `UnauthorizedOperation` do EC2) |
| **Simular permissões** | **IAM Policy Simulator** (`aws iam simulate-principal-policy`) |
| **Analisar acesso** | **IAM Access Analyzer** |
| **Testar conectividade** | `curl -v https://<serviço>.<região>.amazonaws.com`, `nslookup`, **VPC Reachability Analyzer** |
| **Verificar tempo** | `date -u`, `chronyc tracking` |
| **Ver região/endpoint** | `aws configure list`, `env | grep AWS_` |
| **Reproduzir a chamada** | **CLI** com `--debug`, `--dry-run` (EC2) |
| **Validar JSON/parâmetros** | `aws <svc> <op> help`, **`--generate-cli-skeleton`** |
| **Status do serviço** | **AWS Health Dashboard** / `aws health` |
| **Testes locais** | **LocalStack/Moto**, **DynamoDB Local**, **SAM local** |

```bash
aws ec2 run-instances --dry-run ...                          # valida permissões sem executar
aws dynamodb put-item --generate-cli-skeleton                # modelo de parâmetros
aws sts decode-authorization-message --encoded-message "$MSG" --query DecodedMessage --output text | jq .
aws configure list                                           # de onde vêm credenciais/região
```

## 6. Troubleshooting guiado

### 6.1 Árvore: “AccessDenied”

```
AccessDenied?
├─ Identidade correta? (sts get-caller-identity)                                ── não ─▶ Corrigir credenciais/perfil/env
├─ IAM do principal permite a ação NO RECURSO (ARN) e as condições?             ── não ─▶ Ajustar a policy
├─ SCP/permission boundary/session policy negam?                                ── sim ─▶ Ajustar guardrails
├─ Resource policy (S3/KMS/SQS/Lambda/Secrets) permite o principal?             ── não ─▶ Ajustar (cross-account exige ambos os lados)
├─ KMS: key policy/grant para a role? (AccessDenied em S3 criptografado)        ── não ─▶ Ajustar a chave
├─ Condição (MFA, IP, VPCe, região, tags) não atendida?                         ── sim ─▶ Atender/ajustar
└─ CloudTrail: errorMessage indica a política negadora (em muitos serviços)     ─▶ Seguir a pista
```

### 6.2 Árvore: “timeouts / não conecta”

```
Timeout/EndpointConnectionError?
├─ Região/endpoint corretos? (aws configure list; endpoint_url)                 ── não ─▶ Corrigir
├─ DNS resolve? (nslookup)                                                      ── não ─▶ DNS/Resolver/VPC DNS
├─ Rota/SG/NACL/NAT/IGW/VPC endpoint (policy do endpoint)?                      ── não ─▶ Rede (Reachability Analyzer)
├─ Proxy/TLS inspection/CA corporativa (AWS_CA_BUNDLE)?                         ── sim ─▶ Configurar
├─ Lambda em VPC sem NAT/endpoint?                                              ── sim ─▶ Adicionar NAT/VPCe
├─ Timeouts do SDK muito baixos/pool esgotado?                                  ── sim ─▶ Ajustar timeouts/pool
└─ Serviço degradado? (Health Dashboard)                                        ─▶ Aguardar/failover
```

### 6.3 Árvore: “lento/instável”

```
Latência alta ou erros intermitentes?
├─ Retries ocultos? (RetryAttempts, logs botocore.retries)                      ── sim ─▶ Throttling → backoff/limites/capacidade
├─ Cliente recriado a cada chamada / sem pool / sem keep-alive?                 ── sim ─▶ Reusar clientes
├─ Região distante / sem VPC endpoint / NAT gargalo?                            ── sim ─▶ Aproximar; endpoints; NAT escalável
├─ Payloads grandes / falta de paginação eficiente / Scan?                      ── sim ─▶ Otimizar acesso a dados
├─ Cold start / imports pesados (Lambda)?                                       ── sim ─▶ Reduzir imports; provisioned concurrency
└─ Dependência downstream lenta (X-Ray mostra)?                                 ─▶ Timeout/circuit breaker/cache
```

## 8. Operação contínua

| Rotina | Detalhe |
|---|---|
| **Versões de SDK** | **Atualizar** regularmente (segurança, **novos recursos**, correções de retry); **fixar** versões e **testar** |
| **Depreciações** | Acompanhar **fim de suporte** (runtimes, SDK v1, APIs) |
| **User-Agent** | **Identificar** apps (`user_agent_extra`) para **suporte e auditoria** |
| **Quotas** | **Service Quotas** monitoradas |
| **Dependências** | **SBOM/SCA** para vulnerabilidades |
| **Configuração central** | **Config comum** de retries/timeouts/região (biblioteca interna) |
| **Runbooks** | Throttling, `AccessDenied`, expiração de credenciais, queda de endpoint |
| **Alarmes** | Taxa de erro/latência/retries por serviço; **expiração de credenciais**; **picos de throttling** |
| **Capacity/limits review** | Antes de lançamentos/campanhas |

## 9. Checklist

- [ ] **Identidade confirmada** (`get-caller-identity`) e **perfil/role** corretos
- [ ] **Região/endpoint** explícitos e verificados
- [ ] **Retries/timeouts/pool** configurados e **clientes reutilizados**
- [ ] **Paginação** e **falhas parciais** tratadas; **idempotência** em operações retentáveis
- [ ] **Erros tratados por código**; logs com **RequestId**, serviço, operação, tentativas
- [ ] **Debug** só sob demanda e **sem** vazar credenciais
- [ ] **Métricas/traces** (X-Ray/OTel/Powertools) e **alarmes** de erro/latência/throttling
- [ ] **CloudTrail** (e data events quando preciso) para auditoria
- [ ] **Testes** com mocks/stubs/LocalStack e **testes de falha**
- [ ] **SDKs atualizados**; **User-Agent** identificando a aplicação
- [ ] **Runbooks** publicados

## 10. Erros comuns

- **Depurar sem confirmar a identidade**.
- **Ler só a mensagem** (não o **código** nem o **RequestId**).
- **Ativar debug em produção** (vazamento de dados).
- **Tratar erros por texto**.
- **Ignorar `RetryAttempts`** (throttling oculto).
- **Não olhar o CloudTrail** (quem negou?).
- **Ajustar IAM “até funcionar”** com `*`.
- **Esquecer região/endpoint**.
- **Testar só caminho feliz** (sem simular throttling/timeouts).
- **Versões de SDK antigas**.
- **Sem `user_agent_extra`** (suporte não identifica a app).

## 11. Resumo rápido

- **Seis blocos de causa**: **credenciais, autorização, assinatura/relógio, rede/endpoint/região, parâmetros/estado, limites/carga**.
- **Anatomia do erro**: **código** (tratar por ele), mensagem, **HTTP status**, **RequestId**, **RetryAttempts**.
- **Debug**: CLI `--debug`, loggers do SDK (`botocore`, `software.amazon.awssdk`), **sob demanda e mascarando segredos**.
- **Observabilidade**: métricas (latência, erros por código, retries, timeouts), **X-Ray/OTel/Powertools**, **CloudTrail** (`errorCode`, `userIdentity`, `userAgent`).
- **Ferramentas**: `sts get-caller-identity`, `decode-authorization-message`, **Policy Simulator**, **Access Analyzer**, **Reachability Analyzer**, `--dry-run`, `--generate-cli-skeleton`.
- **Árvores**: `AccessDenied`, timeouts/conexão, lentidão/instabilidade.
- **Testes**: **Moto/Stubber/LocalStack/DynamoDB Local/SAM**; **injetar falhas**.
- **Operação**: atualizar SDKs, **User-Agent**, quotas, runbooks, alarmes.

**Respostas:**

1. Credenciais/identidade, autorização, assinatura/relógio, rede/endpoint/região, parâmetros/estado e limites/carga.
2. Porque o código é estável e a mensagem é texto humano que pode mudar; tratar pelo código evita quebras e comportamentos errados.

5. errorCode/errorMessage, userIdentity (quem/qual sessão), sourceIPAddress/userAgent e requestParameters, que indicam a causa e o contexto.
6. Com `aws sts decode-authorization-message --encoded-message <mensagem>` (com permissão sts:DecodeAuthorizationMessage).
7. Habilitar só sob demanda e por tempo limitado, mascarar credenciais/headers/PII, restringir acesso e retenção e nunca publicá-los.
