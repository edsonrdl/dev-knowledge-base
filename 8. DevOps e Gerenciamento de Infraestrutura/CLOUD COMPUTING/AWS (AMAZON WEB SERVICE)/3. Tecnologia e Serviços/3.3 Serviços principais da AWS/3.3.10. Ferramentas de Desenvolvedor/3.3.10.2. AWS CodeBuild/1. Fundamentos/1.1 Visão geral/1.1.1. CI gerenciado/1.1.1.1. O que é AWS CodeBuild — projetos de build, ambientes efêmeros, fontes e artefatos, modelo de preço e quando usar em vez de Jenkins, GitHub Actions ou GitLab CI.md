### 1.1.1.1. O que é AWS CodeBuild — projetos de build, ambientes efêmeros, fontes e artefatos, modelo de preço e quando usar em vez de Jenkins, GitHub Actions ou GitLab CI

> [!warning] Aviso
> Os comandos, YAMLs, limites, tipos de compute e preços abaixo são **ilustrativos, de memória e não foram executados**. O CodeBuild evolui rápido (novos tipos de compute, **Lambda compute**, frotas reservadas, runners de GitHub Actions). **Confirme limites, imagens e preços na documentação oficial e na página de preços.** Valores em dólar são ordens de grandeza.

## 1. O problema que o CodeBuild resolve

**Integração contínua (CI)** significa compilar, testar e empacotar o código **a cada mudança**, de forma automática e reproduzível. Na prática, alguém precisa de **servidores de build**: instalar compiladores, manter agentes atualizados, escalar para vários builds simultâneos, limpar workspaces, aplicar patches de segurança e pagar por máquinas que ficam **ociosas** a maior parte do tempo. O clássico **Jenkins** autogerenciado exige exatamente esse trabalho.

O **AWS CodeBuild** é o serviço **gerenciado de build** da AWS: você descreve **como construir** (um arquivo `buildspec.yml`), e o CodeBuild **provisiona um ambiente efêmero**, executa os comandos, **guarda os artefatos e logs** e **descarta o ambiente**. Não há servidor para manter, a capacidade **escala sob demanda** (vários builds em paralelo) e a cobrança é **por minuto de build**.

```
 Evento (push, PR, pipeline, agendamento)
        │
        ▼
 ┌─────────────────────────────────────────────┐
 │ CODEBUILD                                    │
 │  1. Baixa o código (CodeCommit/GitHub/S3...) │
 │  2. Cria ambiente efêmero (contêiner/VM)     │
 │  3. Executa o buildspec (install→build→post) │
 │  4. Sobe artefatos (S3), logs, relatórios    │
 │  5. Destrói o ambiente                       │
 └─────────────────────────────────────────────┘
        │
        ▼
 Artefatos (S3) · Imagens (ECR) · Relatórios · Estado do build → CodePipeline / EventBridge
```

## 2. Conceitos centrais

| Conceito | Significado |
|---|---|
| **Build project** | Configuração reutilizável: fonte, ambiente, buildspec, artefatos, rede, logs, role |
| **Build** | Uma **execução** do projeto (tem ID, fase, status, duração) |
| **Source** | Onde está o código (CodeCommit, S3, GitHub, GitHub Enterprise, GitLab, Bitbucket, CodePipeline) |
| **Environment** | O ambiente de execução: **imagem** (SO + ferramentas), **compute type** (vCPU/RAM), variáveis, **privileged mode** |
| **buildspec** | Arquivo YAML com as fases e comandos (`buildspec.yml`) |
| **Artifacts** | Saídas do build (S3) — binários, pacotes, relatórios |
| **Cache** | Reuso entre builds (S3 ou local) para acelerar dependências |
| **Service role** | Role IAM que o CodeBuild assume para acessar recursos |
| **Report group** | Coleção de **relatórios de teste e cobertura** |
| **Fleet** | **Capacidade reservada** de instâncias para builds mais rápidos e previsíveis |
| **Batch build** | Execução de **vários builds** coordenados (matrix, graph, list) |
| **Webhook** | Gatilho do provedor de código (push/PR) para iniciar builds |

## 3. Como um build funciona (fases)

O ciclo de vida do build tem **fases** com status e duração individuais (visíveis no console):

```
SUBMITTED → QUEUED → PROVISIONING → DOWNLOAD_SOURCE → INSTALL → PRE_BUILD → BUILD → POST_BUILD
         → UPLOAD_ARTIFACTS → FINALIZING → COMPLETED
```

| Fase | O que ocorre |
|---|---|
| **QUEUED** | Espera por capacidade (limite de concorrência) |
| **PROVISIONING** | Cria o ambiente (contêiner/VM) e baixa a imagem |
| **DOWNLOAD_SOURCE** | Clona/baixa o código |
| **INSTALL/PRE_BUILD/BUILD/POST_BUILD** | Fases do `buildspec` definidas por você |
| **UPLOAD_ARTIFACTS** | Envia artefatos ao S3 |
| **FINALIZING** | Limpeza, relatórios, logs finais |

**Ponto importante:** cada build roda em um **ambiente novo e isolado**: nada persiste entre builds (exceto o **cache** que você configurar). Isso dá **reprodutibilidade**, mas exige **cache** para não baixar dependências todas as vezes.

## 4. Fontes e saídas

| Fonte | Observações |
|---|---|
| **AWS CodeCommit** | Integração nativa, por IAM |
| **GitHub / GitHub Enterprise** | OAuth ou **GitHub App/CodeConnections**; webhooks para push e PR |
| **GitLab / GitLab self-managed / Bitbucket** | Via **CodeConnections** |
| **Amazon S3** | Zip com o código (builds de artefatos prontos) |
| **AWS CodePipeline** | O pipeline entrega a fonte como **artefato de entrada** |
| **Sem fonte** | Projetos "no source" (buildspec inline), úteis para tarefas utilitárias |

| Saída | Observações |
|---|---|
| **Artefatos no S3** | Zip ou pasta, com prefixos e *namespace* |
| **Imagens de container** | `docker push` para o **ECR** (precisa de *privileged mode*) |
| **Pacotes** | Para **CodeArtifact** (npm, Maven, PyPI, NuGet) |
| **Relatórios** | Testes (JUnit, etc.) e cobertura (Cobertura, JaCoCo) |
| **Logs** | CloudWatch Logs e/ou S3 |
| **Eventos** | EventBridge: mudanças de estado e de fase |

## 5. Modelo de preço (visão geral)

| Item | Cobrança (ordem de grandeza; confirmar) |
|---|---|
| **Minuto de build** | Por **minuto** (arredondado), conforme o **compute type** e o SO |
| **Linux small (3 GB, 2 vCPU)** | ~US$ 0,005/min |
| **Linux medium/large/2xlarge** | Múltiplos do small (2×, 4×, ~20×) |
| **ARM** | Geralmente mais barato por desempenho |
| **GPU / Windows** | Mais caros |
| **Lambda compute** | Preço por **GB-segundo** (mais barato para builds curtos) |
| **Frotas reservadas** | Cobradas por **capacidade provisionada** por hora (mesmo ociosa) |
| **Free Tier** | Franquia mensal de minutos no tipo small (conferir) |
| **Extras** | S3 (artefatos/cache), CloudWatch Logs, transferência de dados, ECR |

Exemplo: 20 desenvolvedores, 200 builds/dia de 6 min no tipo `medium` Linux (~US$ 0,01/min): `200 × 6 × 0,01 = US$ 12/dia ≈ US$ 360/mês`. Para builds curtos e frequentes, avalie **Lambda compute**; para builds pesados e constantes, **frota reservada** pode compensar.

## 6. Quando usar CodeBuild vs alternativas

| Critério | **CodeBuild** | **Jenkins** (self-managed) | **GitHub Actions** | **GitLab CI** |
|---|---|---|---|---|
| **Operação** | **Zero servidor** | Você mantém servidores/agentes | Gerenciado (runners GitHub) ou self-hosted | Gerenciado ou self-managed |
| **Escala** | Automática | Manual/plugins | Automática (runners) | Automática (runners) |
| **Integração AWS** | **Nativa** (IAM, VPC, ECR, S3) | Via plugins/credenciais | OIDC + actions da AWS | OIDC + integrações |
| **Linguagem de pipeline** | buildspec (só **build**) + CodePipeline | Jenkinsfile (muito flexível) | Workflows YAML (ricos) | `.gitlab-ci.yml` (muito rico) |
| **Marketplace/ecossistema** | Pequeno | **Enorme** (plugins) | **Enorme** (actions) | Grande |
| **Rede privada** | **Sim** (VPC) | Sim (você hospeda) | Self-hosted runners | Runners próprios |
| **Custo** | Por minuto | Infra + operação | Por minuto/plano | Por minuto/plano |
| **Melhor para** | Builds em **ambientes AWS-first/regulados**, pipelines Code* | Casos legados/customizados | Projetos no GitHub | Projetos no GitLab |

Heurística:

- **CodeBuild** é excelente como **motor de build** dentro de **CodePipeline** ou acionado por eventos AWS.
- Se o código está no **GitHub**, é comum usar **GitHub Actions** e, quando precisar de **rede privada AWS/IAM**, rodar os jobs **em runners hospedados no CodeBuild** (recurso de runners self-hosted do GitHub Actions no CodeBuild).
- Para **orquestração multi-etapa** (build → teste → aprovação → deploy), o CodeBuild **sozinho não basta**: combine com **CodePipeline/Step Functions**.

## 7. Primeiro exemplo (ilustrativo)

`buildspec.yml` mínimo para uma aplicação Node.js:

```yaml
version: 0.2
phases:
  install:
    runtime-versions:
      nodejs: 20
    commands:
      - npm ci
  build:
    commands:
      - npm test
      - npm run build
artifacts:
  files:
    - '**/*'
  base-directory: dist
```

Criação do projeto e execução:

```bash
aws codebuild create-project --name app-web-build \
  --source type=CODECOMMIT,location=https://git-codecommit.us-east-1.amazonaws.com/v1/repos/app-web \
  --artifacts type=S3,location=meu-bucket-artefatos,packaging=ZIP \
  --environment type=LINUX_CONTAINER,image=aws/codebuild/amazonlinux-x86_64-standard:5.0,computeType=BUILD_GENERAL1_SMALL \
  --service-role arn:aws:iam::123456789012:role/codebuild-app-web

aws codebuild start-build --project-name app-web-build --source-version feature/login
aws codebuild batch-get-builds --ids app-web-build:abc123-... --query 'builds[0].[buildStatus,currentPhase]'
```

## 8. Casos de uso típicos

| Caso | Como |
|---|---|
| **CI de aplicações** (compilar, testar, empacotar) | Projeto por repositório, acionado por webhook/PR |
| **Build de imagens Docker** e push para **ECR** | `privilegedMode: true` + `docker build/push` |
| **Validação de IaC** | `cfn-lint`, `terraform validate/plan`, `checkov` em PRs |
| **Testes de integração** em VPC | Build com acesso a bancos/serviços privados |
| **Publicar pacotes** | npm/Maven/PyPI no **CodeArtifact** |
| **Geração de documentação/sites** | Build e publicação no S3/CloudFront |
| **Tarefas agendadas** | EventBridge Scheduler → `StartBuild` (migrações, relatórios) |
| **Runners de GitHub Actions** | Jobs com acesso à rede AWS |

## 9. Limites a conhecer (visão geral)

| Aspecto | Observação (confirmar) |
|---|---|
| **Timeout do build** | De 5 min a **36 horas** (padrão 60 min) |
| **Concorrência** | **Quota por conta/região** (ex.: dezenas de builds simultâneos; ajustável) |
| **Fila** | Builds acima da quota **ficam em fila** (timeout de fila configurável) |
| **Tamanho de artefatos/log** | Limites; use S3 para logs grandes |
| **Docker Hub** | **Rate limits** para pulls anônimos: use ECR/mirror ou autenticação |
| **Variáveis de ambiente** | Limite de tamanho total; segredos via Secrets Manager/Parameter Store |
| **Disco** | Armazenamento limitado por tipo; builds enormes exigem compute maior |

## 10. Erros comuns

> [!bug] Erros comuns
> 1. **Achar que o ambiente persiste** entre builds (ele é descartado).
> 2. **Não usar cache** e baixar dependências a cada build (lento e caro).
> 3. **Esquecer `privilegedMode`** ao construir imagens Docker.
> 4. **Colocar segredos em variáveis de texto** do projeto.
> 5. **Service role ampla demais** (`AdministratorAccess`).
> 6. **Estourar a quota de concorrência** e acumular fila.
> 7. **Usar CodeBuild como orquestrador** de pipeline complexo (use CodePipeline).
> 8. **Puxar imagens do Docker Hub** sem tratar rate limit.
> 9. **Builds em compute maior que o necessário** (custo).
> 10. **Não guardar logs/relatórios** e perder diagnóstico.

## 11. Troubleshooting inicial

| Sintoma | Causa provável | Ação |
|---|---|---|
| `CLIENT_ERROR: no matching artifact paths` | Caminho dos artefatos incorreto | Conferir `artifacts.files` e `base-directory` |
| `Cannot connect to the Docker daemon` | Privileged mode desligado | Habilitar `privilegedMode` no projeto |
| Build travado em `QUEUED` | Limite de concorrência | Aumentar quota ou usar frota reservada |
| `AccessDenied` ao ler/escrever S3/ECR | Service role sem permissão | Ajustar a política da role |
| Falha ao baixar a fonte | Credencial/conexão do GitHub/GitLab | Reautorizar CodeConnections/OAuth |
| `toomanyrequests` do Docker Hub | Rate limit | Usar ECR/Public ECR ou autenticar |
| Build lento | Sem cache/compute pequeno | Habilitar cache e dimensionar o compute |

## 12. Resumo rápido

- **CodeBuild** = **build gerenciado**: ambiente **efêmero** por build, sem servidores, escala sob demanda, **cobrança por minuto**.
- Conceitos: **projeto, build, buildspec, ambiente (imagem + compute), cache, artefatos, relatórios, service role**.
- Integra-se a **CodeCommit/GitHub/GitLab/S3/CodePipeline**, **ECR**, **CodeArtifact**, **EventBridge**.
- Frente a **Jenkins/Actions/GitLab CI**: ganha em **integração AWS e zero operação**; perde em **ecossistema e orquestração**.
- Use **cache**, **compute adequado** e **menor privilégio**; para fluxos completos, combine com **CodePipeline**.

### 🧩 Quiz de Fixação

1. O que acontece com o ambiente depois de cada build?
2. Qual arquivo define as fases do build?
3. Como o CodeBuild é cobrado?
4. Quando é necessário o privileged mode?
5. Por que o CodeBuild não substitui um orquestrador de pipeline?
6. Cite duas formas de acelerar builds.
7. Como usar o CodeBuild com um repositório no GitHub?

**Respostas:**

1. É descartado; nada persiste, exceto o cache e os artefatos configurados.
2. O `buildspec.yml`.
3. Por minuto de build, conforme o compute type (mais extras como S3 e logs); frotas reservadas por capacidade provisionada.
4. Ao executar comandos Docker (build/push de imagens) dentro do build.
5. Ele executa builds, mas não coordena etapas com aprovação e deploys; para isso usa-se CodePipeline/Step Functions.
6. Cache (S3/local), compute maior, frota reservada, Lambda compute para builds curtos e redução de downloads.
7. Via CodeConnections/OAuth com webhooks de push/PR, ou usando runners de GitHub Actions hospedados no CodeBuild.
