### 2.1.1.1. Ambientes do CodeBuild — tipos de compute, imagens gerenciadas e customizadas, Lambda compute, frotas reservadas, VPC, privileged mode, cache e concorrência

> [!warning] Aviso
> Nomes de imagens, tipos de compute, versões de runtimes, limites e preços abaixo são **de memória e mudam com frequência** (novas imagens e tipos aparecem; imagens antigas são aposentadas). **Confirme na documentação "Build environment reference" e na página de preços.** Comandos e YAMLs são ilustrativos e não foram executados.

## 1. O que é o "ambiente" de um build

O **ambiente** do CodeBuild define **onde** os comandos do `buildspec` rodam: o **sistema operacional e as ferramentas** (a **imagem**), a **capacidade** (CPU/RAM/disco — o **compute type**), as **variáveis**, o acesso à **rede** (VPC ou não) e privilégios (como o **privileged mode** para Docker). Cada build recebe uma **instância nova e isolada** desse ambiente.

```
Ambiente = IMAGEM (SO + ferramentas) + COMPUTE (vCPU/RAM/disco) + REDE (VPC?) + PRIVILÉGIOS + VARIÁVEIS + ROLE
```

Escolher bem o ambiente é o maior fator de **tempo de build**, **custo** e **confiabilidade**.

## 2. Tipos de ambiente (environment type)

| Tipo | Descrição | Uso |
|---|---|---|
| **LINUX_CONTAINER** | Contêiner Linux x86_64 | Padrão para a maioria das aplicações |
| **ARM_CONTAINER** | Contêiner Linux ARM64 (Graviton) | Builds para ARM e **melhor custo/desempenho** em muitos casos |
| **LINUX_GPU_CONTAINER** | Linux com GPU | ML, processamento acelerado |
| **WINDOWS_SERVER_2019/2022_CONTAINER** | Windows | .NET Framework, aplicações Windows |
| **LINUX_LAMBDA_CONTAINER / ARM_LAMBDA_CONTAINER** | **Lambda compute** (builds em infraestrutura Lambda) | Builds **curtos e frequentes**, inicialização rápida |
| **MAC (macOS)** | Instâncias Mac (conforme disponibilidade) | Apps iOS/macOS |

## 3. Compute types (capacidade)

Os tipos variam por plataforma e região (confirmar valores exatos):

| Compute type | vCPU | Memória | Disco (aprox.) | Uso típico |
|---|---|---|---|---|
| **BUILD_GENERAL1_SMALL** | 2 | 3 GB (4 GB em algumas imagens) | ~64 GB | Builds leves, scripts, validações |
| **BUILD_GENERAL1_MEDIUM** | 4 | 7 GB | ~128 GB | Aplicações médias |
| **BUILD_GENERAL1_LARGE** | 8 | 15 GB | ~128–256 GB | Compilação pesada, testes paralelos |
| **BUILD_GENERAL1_XLARGE / 2XLARGE** | 36–72 | 72–145 GB | 256+ GB | Builds enormes, monorepos, C++/Android |
| **GPU (small/large)** | variável | variável | variável | ML |
| **Lambda compute (1GB–10GB)** | variável | Até 10 GB | Limitado | Builds curtos |
| **Instâncias personalizadas** (frota com tipo EC2 específico) | Conforme o tipo EC2 | Conforme | Conforme | Controle fino |

Orientação:

- Comece em **SMALL/MEDIUM** e **meça** (fase BUILD, uso de CPU/memória). Aumentar o compute **reduz o tempo**, mas o custo por minuto também cresce: o **custo total** pode **cair** se o tempo cair mais do que o preço sobe (por exemplo, MEDIUM 2× mais caro por minuto, mas 3× mais rápido).
- Builds **I/O-bound** (baixar dependências) ganham pouco com CPU: invista em **cache**.
- **ARM** costuma custar menos por minuto; valide compatibilidade das dependências nativas.

## 4. Imagens

### 4.1 Imagens gerenciadas (curated)

O CodeBuild mantém **imagens** com SO e **runtimes pré-instalados**, mantidas e atualizadas pela AWS:

| Imagem (exemplos) | Conteúdo |
|---|---|
| `aws/codebuild/amazonlinux-x86_64-standard:5.0` | Amazon Linux 2023 com Node.js, Python, Java, Go, Ruby, PHP, .NET, Docker |
| `aws/codebuild/amazonlinux-aarch64-standard:3.0` | Versão ARM |
| `aws/codebuild/standard:7.0` | Ubuntu 22.04 |
| `aws/codebuild/windows-base:2019-3.0` | Windows |
| Imagens específicas (Android, ...)** | Conforme documentação |

Os **runtimes** são selecionados no `buildspec` com **`runtime-versions`** (por exemplo `nodejs: 20`, `python: 3.12`, `java: corretto21`), e o CodeBuild **instala a versão pedida** (dentro das disponíveis na imagem).

> [!warning] Cuidado
> **Fixe a versão da imagem** (por exemplo `:5.0`), em vez de `latest`, para builds **reproduzíveis**. Imagens antigas são **descontinuadas** com o tempo: acompanhe os avisos e atualize.

### 4.2 Imagens customizadas

Use uma **imagem própria** (ECR ou Docker Hub) quando precisar de **ferramentas específicas**, **dependências pesadas pré-instaladas** ou **configuração de segurança** padronizada:

| Origem | Observação |
|---|---|
| **ECR (mesma conta/região)** | Recomendado; controle e velocidade; a **service role/ resource policy** do ECR deve permitir `ecr:GetDownloadUrlForLayer`, `BatchGetImage`, `BatchCheckLayerAvailability` |
| **Docker Hub** | Cuidado com **rate limits** e com a **proveniência** da imagem |
| **ECR Public** | Alternativa sem limites rígidos |

Boas práticas de imagem customizada: **base mínima**, **ferramentas fixadas por versão**, **escaneamento** (ECR/Inspector), **atualização periódica** (pipeline de imagens), **usuário não root** quando possível (lembrando que o CodeBuild executa como root por padrão).

Exemplo (projeto com imagem do ECR):

```bash
aws codebuild create-project --name build-java \
  --environment type=LINUX_CONTAINER,computeType=BUILD_GENERAL1_MEDIUM,image=123456789012.dkr.ecr.us-east-1.amazonaws.com/build-java:2026.11,imagePullCredentialsType=SERVICE_ROLE \
  ...
```

`imagePullCredentialsType=SERVICE_ROLE` faz o CodeBuild puxar do ECR com a **service role** (necessário para imagens privadas no ECR).

## 5. Lambda compute

O **Lambda compute** executa o build em infraestrutura **AWS Lambda**:

| Característica | Detalhe |
|---|---|
| **Início rápido** | Sem tempo de provisionamento de instância (segundos) |
| **Cobrança** | Por **GB-segundo** (muito econômico para builds curtos) |
| **Limitações** | Sem **Docker/privileged mode**, sem acesso a algumas ferramentas, tempo e disco limitados, imagens específicas |
| **Ideal para** | Testes unitários rápidos, linting, builds de funções Lambda, validações de IaC |

## 6. Frotas reservadas (reserved capacity fleets)

Uma **frota** é **capacidade provisionada** (instâncias mantidas "quentes") para os seus builds:

| Benefício | Detalhe |
|---|---|
| **Sem tempo de provisionamento** | Builds iniciam quase imediatamente |
| **Cache local persistente** | A instância reutiliza **layers Docker e dependências** entre builds |
| **Desempenho previsível** | Capacidade garantida (sem fila por quota na frota) |
| **Tipos EC2 personalizados** | Escolha precisa de CPU/memória/GPU/ARM |
| **Custo** | **Por tempo de capacidade provisionada** (mesmo ocioso) — compensa com **uso alto e contínuo** |
| **Escala** | Overflow para on-demand (opcional) |

Regra: **on-demand** para uso esporádico; **frota** para equipes com muitos builds por hora, necessidade de **cache local** ou **início instantâneo**.

## 7. Rede: VPC e conectividade

Por padrão, o build roda **fora da sua VPC** com **acesso à internet** (para baixar dependências). Para acessar **recursos privados** (bancos, APIs internas, repositórios privados), configure **VPC**:

| Configuração | Detalhe |
|---|---|
| **VPC, sub-redes, security groups** | Escolha sub-redes **privadas** com saída por **NAT Gateway** (ou endpoints) |
| **Saída à internet** | **NAT Gateway** ou **VPC endpoints** (S3, ECR, CodeArtifact, CloudWatch Logs, Secrets Manager, STS) |
| **Custos** | NAT (hora + GB) e endpoints interface (hora + GB); builds que baixam muito pelo NAT **pesam na fatura** |
| **DNS** | Resolução privada quando necessário |
| **Subnets em várias AZs** | Resiliência |

```bash
aws codebuild update-project --name build-integracao \
  --vpc-config vpcId=vpc-0abc,subnets=subnet-0a,subnet-0b,securityGroupIds=sg-0abc
```

Dicas: crie **Gateway Endpoint do S3** (gratuito) e **endpoints** para ECR/CodeArtifact para **reduzir NAT**; use **espelho/proxy de pacotes** (CodeArtifact) em vez de baixar da internet.

## 8. Privileged mode e Docker

Para **construir imagens Docker dentro do build**, o ambiente precisa do **modo privilegiado** (`privilegedMode: true`), que habilita o **daemon Docker**:

```yaml
phases:
  pre_build:
    commands:
      - aws ecr get-login-password --region $AWS_DEFAULT_REGION | docker login --username AWS --password-stdin $ACCOUNT.dkr.ecr.$AWS_DEFAULT_REGION.amazonaws.com
  build:
    commands:
      - docker build -t $REPO:$CODEBUILD_RESOLVED_SOURCE_VERSION .
      - docker push $REPO:$CODEBUILD_RESOLVED_SOURCE_VERSION
```

Considerações de segurança: privileged mode dá **mais poderes** ao contêiner do build; use em projetos **confiáveis**, com **roles mínimas**, e prefira **BuildKit/Kaniko/Buildah** quando precisar de builds **sem privilégio**. **Docker layer cache** acelera builds de imagens.

## 9. Cache

| Tipo de cache | Onde guarda | Quando usar |
|---|---|---|
| **S3 cache** | Bucket S3 (zip) | Dependências (`node_modules`, `.m2`, `.gradle`, `pip`) entre builds; funciona com ambientes efêmeros |
| **Local cache** | Na instância (apenas **frota reservada**/reuso) | **Source cache**, **Docker layer cache**, **custom cache** |
| **Sem cache** | — | Builds raros |

Exemplo no `buildspec`:

```yaml
cache:
  paths:
    - '/root/.m2/**/*'
    - 'node_modules/**/*'
```

Boas práticas: **chave de cache** coerente (hash de `package-lock.json`), **limpeza periódica**, cuidado com **cache envenenado** (artefatos corrompidos/maliciosos persistindo) — trate o cache como **dado não confiável**.

## 10. Variáveis de ambiente e metadados

| Tipo | Exemplo |
|---|---|
| **PLAINTEXT** | `STAGE=prod` (não use para segredos) |
| **PARAMETER_STORE** | `DB_URL=/app/prod/db-url` |
| **SECRETS_MANAGER** | `API_KEY=app/prod/api:key` |
| **Variáveis padrão do CodeBuild** | `CODEBUILD_BUILD_ID`, `CODEBUILD_RESOLVED_SOURCE_VERSION`, `CODEBUILD_SOURCE_VERSION`, `AWS_DEFAULT_REGION`, `AWS_ACCOUNT_ID` (via `aws sts`), `CODEBUILD_BUILD_NUMBER`, `CODEBUILD_WEBHOOK_TRIGGER` |

## 11. Concorrência e fila

| Aspecto | Observação |
|---|---|
| **Concorrência** | Limite de **builds simultâneos** por conta/região e por tipo de compute (ajustável) |
| **Fila** | Builds acima do limite entram em **QUEUED** (com timeout de fila configurável) |
| **Frotas** | Têm capacidade própria |
| **Batch builds** | Contam individualmente |
| **Boa prática** | Dimensionar quota e/ou frota para os **picos** (início do expediente, merges em massa) e **evitar builds redundantes** (cancelar builds antigos do mesmo PR) |

## 12. Escolhendo o ambiente (guia rápido)

```
Build curto (<5 min), sem Docker, lint/testes unitários?        → Lambda compute (ou SMALL)
Aplicação típica (Node/Java/Python), build de 5–15 min?          → MEDIUM + cache S3
Compilação pesada/paralela (C++, Android, monorepo)?            → LARGE/2XLARGE ou frota com instância custom
Construir imagens Docker?                                       → LINUX + privileged mode (+ cache de layers/frota)
Precisa ARM ou melhor custo?                                    → ARM_CONTAINER (validar dependências)
Acesso a banco/serviço privado?                                 → VPC + sub-rede privada + endpoints
Muito volume e cache local importante?                          → Frota reservada
```

## 13. Erros comuns

> [!bug] Erros comuns
> 1. **Usar `latest`/imagem não fixada** e quebrar builds quando a imagem muda.
> 2. **Compute grande demais** para builds I/O-bound (custo sem ganho).
> 3. **Sem cache** (ou cache sem chave) e dependências baixadas sempre.
> 4. **VPC sem NAT/endpoints**: build falha ao baixar dependências.
> 5. **Tráfego pesado pelo NAT** (custo alto) em vez de endpoints/CodeArtifact.
> 6. **Privileged mode** em projetos com código não confiável.
> 7. **Imagem customizada do ECR sem permissão** (`SERVICE_ROLE` ausente).
> 8. **Docker Hub com rate limit** em horários de pico.
> 9. **Segredos em PLAINTEXT.**
> 10. **Ignorar quotas de concorrência** e criar filas longas.

## 14. Troubleshooting

| Sintoma | Causa provável | Ação |
|---|---|---|
| `Unable to locate credentials` no pull do ECR | `imagePullCredentialsType` incorreto | Usar `SERVICE_ROLE` e permitir ECR na role |
| Build em VPC sem internet | Falta NAT/endpoints | Criar NAT ou endpoints necessários |
| Fora de memória (`OOM`) | Compute pequeno | Aumentar o compute ou limitar paralelismo (`-Xmx`, `--max-old-space-size`) |
| `no space left on device` | Disco do compute | Limpar, compute maior, remover artefatos intermediários |
| Cache não é restaurado | Caminhos/chave/região do bucket | Conferir `cache.paths` e permissões S3 |
| Runtime não encontrado | `runtime-versions` não disponível na imagem | Usar imagem mais nova ou instalar manualmente |
| Docker build falha (`permission denied`) | Privileged mode desligado | Habilitar `privilegedMode` |
| Fila longa | Quota de concorrência | Aumentar quota/frota; cancelar builds redundantes |

## 15. Resumo rápido

- Ambiente = **imagem + compute + rede + privilégios + variáveis**; cada build usa **instância nova**.
- **Compute types**: SMALL→2XLARGE, **ARM**, **GPU**, **Lambda compute** (curto/barato), **frotas** (capacidade reservada, cache local).
- **Imagens**: gerenciadas (fixe a versão) ou **customizadas no ECR** (`SERVICE_ROLE`).
- **VPC** para recursos privados; use **endpoints/CodeArtifact** para reduzir NAT.
- **Privileged mode** só para Docker; **cache** (S3/local) acelera; observe **quotas de concorrência**.

1. O que define o ambiente de um build?
2. Quando usar Lambda compute?
3. Que vantagem uma frota reservada oferece?
4. Para que serve `runtime-versions`?
5. Por que builds em VPC podem falhar ao baixar dependências?
6. O que é necessário para puxar uma imagem privada do ECR?
7. Quando o privileged mode é necessário?

**Respostas:**

1. Imagem (SO e ferramentas), compute type, rede (VPC), privilégios, variáveis e service role.
2. Para builds curtos e frequentes, sem Docker, como lint e testes unitários, aproveitando início rápido e preço por GB-segundo.
3. Início quase imediato, capacidade previsível e cache local persistente, ao custo da capacidade provisionada.
4. Selecionar as versões das linguagens (Node, Python, Java…) a instalar na imagem gerenciada.
5. Falta de NAT Gateway ou VPC endpoints para saída aos serviços e à internet.
6. `imagePullCredentialsType=SERVICE_ROLE` e permissões de ECR na service role.
7. Ao executar comandos Docker (build/push de imagens) dentro do build.
