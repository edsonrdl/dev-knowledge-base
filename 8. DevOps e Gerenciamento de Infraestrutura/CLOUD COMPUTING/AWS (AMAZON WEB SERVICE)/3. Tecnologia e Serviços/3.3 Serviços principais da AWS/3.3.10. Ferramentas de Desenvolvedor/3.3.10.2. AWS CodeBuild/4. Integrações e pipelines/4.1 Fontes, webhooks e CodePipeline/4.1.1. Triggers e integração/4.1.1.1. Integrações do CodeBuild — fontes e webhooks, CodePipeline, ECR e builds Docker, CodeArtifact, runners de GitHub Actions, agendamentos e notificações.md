### 4.1.1.1. Integrações do CodeBuild — fontes e webhooks, CodePipeline, ECR e builds Docker, CodeArtifact, runners de GitHub Actions, agendamentos e notificações

> [!warning] Aviso
> Nomes de eventos, filtros de webhook, formatos de payload e recursos (runners de GitHub Actions, CodeConnections) abaixo são **de memória e podem mudar**. **Confirme na documentação do CodeBuild, CodePipeline e CodeConnections.** Código, JSON e CLI são ilustrativos e não foram executados.

## 1. O CodeBuild como peça de um fluxo maior

O CodeBuild executa **uma tarefa de build** bem definida. O valor real aparece quando ele é **acionado por eventos** e **entrega resultados** a outras etapas:

```
Código (CodeCommit/GitHub/GitLab/Bitbucket)
      │  webhook / EventBridge / CodePipeline
      ▼
  CODEBUILD ──▶ artefatos (S3) · imagens (ECR) · pacotes (CodeArtifact) · relatórios
      │
      ▼
  CodePipeline (aprovações, deploy) · CodeDeploy · CloudFormation · ECS/EKS · Lambda
      │
      ▼
  EventBridge / SNS / Chatbot (notificações)
```

## 2. Formas de iniciar um build

| Gatilho | Como funciona | Quando usar |
|---|---|---|
| **Manual** (`start-build`, console) | Você escolhe a versão/fonte | Testes, retrabalho |
| **Webhook (GitHub/GitLab/Bitbucket)** | O provedor chama o CodeBuild em push/PR | CI direto, sem pipeline |
| **CodePipeline** | Uma ação do pipeline invoca o projeto | Fluxos de entrega com estágios |
| **EventBridge (eventos)** | Regra dispara `StartBuild` (push no CodeCommit, PR, agenda) | Automação AWS-nativa |
| **EventBridge Scheduler/cron** | Agendamento | Tarefas periódicas (migrações, backups, relatórios) |
| **API/SDK** | Aplicações ou Lambdas iniciam builds | Integrações customizadas |
| **GitHub Actions (runner no CodeBuild)** | O workflow roda **no** CodeBuild | Rede privada/IAM da AWS dentro do Actions |

```bash
aws codebuild start-build --project-name app-api \
  --source-version refs/heads/feature/login \
  --environment-variables-override name=STAGE,value=hml,type=PLAINTEXT \
  --buildspec-override buildspec-hml.yml
```

## 3. Webhooks com GitHub, GitLab e Bitbucket

### 3.1 Conexão e autenticação

| Método | Detalhe |
|---|---|
| **CodeConnections (recomendado)** | Conexão **gerenciada** entre a AWS e o provedor (GitHub App, GitLab, Bitbucket): permissões granulares e revogação centralizada |
| **OAuth/Personal Access Token** | Mais antigo; tokens de longa duração (**evite**) |
| **GitHub App no CodeBuild** | Instalado na organização com acesso aos repositórios escolhidos |

### 3.2 Filtros de webhook

O CodeBuild cria um **webhook** no provedor e permite **grupos de filtros** (condições **E** dentro do grupo, **OU** entre grupos):

| Filtro | Exemplo |
|---|---|
| **Tipo de evento** | `PUSH`, `PULL_REQUEST_CREATED`, `PULL_REQUEST_UPDATED`, `PULL_REQUEST_REOPENED`, `PULL_REQUEST_MERGED`, `RELEASED` |
| **HEAD_REF** | `^refs/heads/(main|release/.*)$`, `^refs/tags/v.*$` |
| **BASE_REF** | Branch de destino do PR (`^refs/heads/main$`) |
| **FILE_PATH** | Só dispara se arquivos específicos mudaram (`^services/pagamentos/.*`) — essencial em **monorepos** |
| **COMMIT_MESSAGE** | Excluir `[skip ci]` |
| **ACTOR_ACCOUNT_ID** | Restringir a usuários (segurança em PRs de forks) |

```bash
aws codebuild create-webhook --project-name app-api \
  --filter-groups '[[{"type":"EVENT","pattern":"PULL_REQUEST_CREATED,PULL_REQUEST_UPDATED"},
                      {"type":"BASE_REF","pattern":"^refs/heads/main$"},
                      {"type":"FILE_PATH","pattern":"^api/.*"}]]' \
  --build-type BUILD
```

> [!warning] Segurança em PRs de forks
> Em repositórios públicos ou com colaboradores externos, **não rode builds com segredos em PRs de forks** (código não confiável pode **exfiltrar** segredos). Use filtros de `ACTOR_ACCOUNT_ID`, **aprovação de comentário** ou projetos **sem credenciais** para PRs externos.

### 3.3 Monorepos

Use **`FILE_PATH`** por projeto, **múltiplos projetos** (um por serviço) e, quando preciso, um **build "orquestrador"** que decide o que construir (`git diff`). Cuidado com custo e filas.

## 4. Integração com o CodePipeline

O **CodePipeline** usa o CodeBuild como **ação de build/test** (categoria *Build* ou *Test*):

| Aspecto | Detalhe |
|---|---|
| **Artefato de entrada** | Código vindo da ação **Source** (zip no S3 gerenciado pelo pipeline) |
| **Artefato de saída** | Resultado do `artifacts` do buildspec, passado ao estágio seguinte (Deploy) |
| **Variáveis** | `exported-variables` do buildspec viram **variáveis de ação** (`#{BuildVars.IMAGE_TAG}`) |
| **Múltiplas entradas/saídas** | Até vários **artefatos de entrada** (`PrimarySource`) e **secundários** de saída |
| **Role** | O pipeline invoca o projeto; o projeto tem sua **service role** |
| **Falha** | Falha do build **para o pipeline** (ou segue conforme configuração) |
| **Reexecução** | Retry de ações |

Fluxo típico:

```
Source (CodeCommit/GitHub via CodeConnections)
   → Build (CodeBuild: compilar/testar/empacotar/docker push)
   → Test (CodeBuild: testes de integração/segurança)
   → Approval (manual)
   → Deploy (CodeDeploy / ECS / CloudFormation)
```

No buildspec do estágio Build, os arquivos de saída (por exemplo `appspec.yml`, `taskdef.json`, `imagedefinitions.json`, `template.yaml`) alimentam diretamente o **deploy**.

## 5. Integração com ECR e builds Docker

| Item | Detalhe |
|---|---|
| **Login no ECR** | `aws ecr get-login-password | docker login ...` |
| **Privileged mode** | Necessário para o daemon Docker |
| **Tags de imagem** | Use o **SHA do commit** (`CODEBUILD_RESOLVED_SOURCE_VERSION`) — evite `latest` em deploys |
| **Cache de layers** | **Docker layer cache** (local/frota) ou **BuildKit com cache em ECR** (`--cache-from/--cache-to`) |
| **Multi-arch** | `docker buildx` para amd64/arm64 |
| **Escaneamento** | **ECR image scanning** (básico/Inspector) e gate no pipeline |
| **Assinatura** | **AWS Signer/Notation/cosign** na cadeia de suprimentos |
| **Rate limit do Docker Hub** | Usar **ECR pull-through cache** ou ECR Public como espelho de imagens base |

Exemplo de **BuildKit com cache no ECR** (ilustrativo):

```bash
docker buildx build --platform linux/amd64,linux/arm64 \
  --cache-from type=registry,ref=$REGISTRY/$REPO:cache \
  --cache-to type=registry,ref=$REGISTRY/$REPO:cache,mode=max \
  -t $REGISTRY/$REPO:$TAG --push .
```

## 6. Integração com CodeArtifact (pacotes)

O **CodeArtifact** é o repositório gerenciado de **dependências** (npm, Maven, PyPI, NuGet, Cargo, Swift...), com **proxy/cache** de fontes públicas e **repositórios privados**:

```yaml
phases:
  pre_build:
    commands:
      - aws codeartifact login --tool npm --domain minha-empresa --repository libs --domain-owner $ACCOUNT
      - npm ci
  post_build:
    commands:
      - npm publish        # publica o pacote interno
```

Benefícios: **controle de supply chain** (só pacotes aprovados), **reprodutibilidade**, **menos tráfego externo** (menos NAT), **cache** de pacotes públicos e **auditoria**. A service role precisa de `codeartifact:GetAuthorizationToken`, `GetRepositoryEndpoint`, `ReadFromRepository` e `sts:GetServiceBearerToken`.

## 7. Runners de GitHub Actions no CodeBuild

Recurso que permite que **jobs do GitHub Actions** executem **em ambientes do CodeBuild** (runners efêmeros):

```yaml
# .github/workflows/ci.yml
jobs:
  build:
    runs-on: codebuild-meu-projeto-${{ github.run_id }}-${{ github.run_attempt }}
    steps:
      - uses: actions/checkout@v4
      - run: ./gradlew test
```

| Vantagem | Detalhe |
|---|---|
| **Acesso à VPC/IAM AWS** | O job alcança bancos privados e usa **service role** (sem chaves no GitHub) |
| **Compute flexível** | Todos os tipos de compute, ARM, Lambda compute, frotas |
| **Cobrança AWS** | Preço do CodeBuild (pode ser menor que minutos hospedados) |
| **Segurança** | Isolamento em sua conta |

Requisitos: **conexão (CodeConnections)** com a organização GitHub, **webhook** de `WORKFLOW_JOB_QUEUED` e o **nome do projeto** em `runs-on`.

## 8. Agendamentos e tarefas operacionais

```bash
aws events put-rule --name migracao-noturna --schedule-expression "cron(0 3 * * ? *)"
aws events put-targets --rule migracao-noturna --targets \
  "Id"="1","Arn"="arn:aws:codebuild:us-east-1:123456789012:project/db-migracoes","RoleArn"="arn:aws:iam::123456789012:role/eventbridge-codebuild"
```

Usos: **migrações de banco**, **geração de relatórios**, **limpezas**, **testes sintéticos**, **rotação de segredos** — com **logs e histórico** de execução.

## 9. Estado do build, eventos e notificações

O CodeBuild publica no **EventBridge** eventos como:

| Evento | Detalhe |
|---|---|
| **CodeBuild Build State Change** | `IN_PROGRESS`, `SUCCEEDED`, `FAILED`, `STOPPED`, `TIMED_OUT` |
| **CodeBuild Build Phase Change** | Mudança de fase (útil para métricas) |

```json
{ "source": ["aws.codebuild"],
  "detail-type": ["CodeBuild Build State Change"],
  "detail": { "build-status": ["FAILED", "TIMED_OUT"], "project-name": ["app-api"] } }
```

Alvos: **SNS/Chatbot** (Slack/Teams), **Lambda** (comentar no PR, abrir ticket), **Step Functions**. **Regras de notificação** (AWS Developer Tools) também enviam mensagens de sucesso/falha. Para **status no provedor** (check no GitHub/GitLab), o CodeBuild **reporta o status do commit** automaticamente quando a fonte é GitHub/GitLab (opção *report build status*).

## 10. Padrões de integração prontos

| Padrão | Desenho |
|---|---|
| **CI de PR** | Webhook (PR) → CodeBuild (testes) → status no PR; merge só com CI verde |
| **Build + deploy** | Source → CodeBuild → (Approval) → CodeDeploy/ECS/CloudFormation |
| **Imagens seguras** | CodeBuild → ECR (scan) → gate → deploy |
| **Biblioteca interna** | CodeBuild → testes → publicação no CodeArtifact (versionamento semântico) |
| **IaC** | PR → `cfn-lint/checkov/terraform plan` → comentário com o plano → apply por pipeline |
| **Testes noturnos** | EventBridge Scheduler → CodeBuild em VPC (testes E2E) → relatório → SNS |
| **Multi-conta** | Build na conta de ferramentas → artefatos/imagens compartilhados com contas de deploy (roles e KMS) |

## 11. Erros comuns

> [!bug] Erros comuns
> 1. **Webhook sem filtros** (dispara em tudo) e estoura custo/concorrência.
> 2. **Tokens pessoais de longa duração** em vez de **CodeConnections**.
> 3. **Rodar PRs de forks com segredos.**
> 4. **Monorepo sem `FILE_PATH`**: todos os serviços constroem sempre.
> 5. **Tag `latest` em imagens** no deploy.
> 6. **Esquecer `exported-variables`** e perder valores no pipeline.
> 7. **Artefatos em contas diferentes sem permissões de S3/KMS.**
> 8. **Docker Hub sem mitigação de rate limit.**
> 9. **Role do EventBridge sem `codebuild:StartBuild`.**
> 10. **Não reportar o status** ao provedor (PR sem feedback).

## 12. Troubleshooting

| Sintoma | Causa provável | Ação |
|---|---|---|
| Webhook não dispara | Conexão/permissão do GitHub App ou filtro | Verificar entregas do webhook no provedor e os filtros |
| Build inicia para commits errados | Filtros muito amplos | Refinar `HEAD_REF`/`BASE_REF`/`FILE_PATH` |
| Pipeline não recebe a variável | `exported-variables` ausente | Declarar e consumir como `#{namespace.VAR}` |
| `AccessDenied` ao baixar artefato do pipeline | Role/KMS do bucket do pipeline | Permitir a service role no bucket e na chave |
| Falha de login no CodeArtifact | Permissões/STS bearer token | Adicionar `sts:GetServiceBearerToken` |
| Runner de Actions não inicia | Nome do projeto/label ou webhook ausente | Conferir `runs-on` e o webhook `WORKFLOW_JOB_QUEUED` |
| Status não aparece no PR | `report build status` desligado | Habilitar no projeto de origem |

## 13. Resumo rápido

- Gatilhos: **manual, webhook, CodePipeline, EventBridge, agenda, API e runners de GitHub Actions**.
- **CodeConnections** + **filtros de webhook** (`EVENT`, `HEAD_REF`, `BASE_REF`, `FILE_PATH`); cuidado com **PRs de forks**.
- **CodePipeline**: artefatos de entrada/saída e **variáveis exportadas** ligam Build → Deploy.
- **ECR**/Docker (privileged, SHA como tag, cache, scan) e **CodeArtifact** (supply chain).
- **EventBridge/Chatbot** para notificações; **status de commit** no provedor.
