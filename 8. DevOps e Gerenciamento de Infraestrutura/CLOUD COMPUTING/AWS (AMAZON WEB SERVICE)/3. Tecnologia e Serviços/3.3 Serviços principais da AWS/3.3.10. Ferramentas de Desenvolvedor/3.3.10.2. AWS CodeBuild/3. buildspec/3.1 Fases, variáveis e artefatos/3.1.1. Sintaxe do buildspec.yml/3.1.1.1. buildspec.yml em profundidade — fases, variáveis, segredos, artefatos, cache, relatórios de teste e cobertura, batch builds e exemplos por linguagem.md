### 3.1.1.1. buildspec.yml em profundidade — fases, variáveis, segredos, artefatos, cache, relatórios de teste e cobertura, batch builds e exemplos por linguagem

> [!warning] Aviso
> Sintaxe, chaves e versões de runtime abaixo são **de memória e podem mudar**; **confirme na documentação "Build specification reference for CodeBuild"**. YAMLs e comandos são ilustrativos e **não foram executados**. Erros de indentação YAML e de caminhos de artefatos são a causa mais comum de falhas — valide com um build de teste.

## 1. O que é o buildspec

O **buildspec** é o arquivo **YAML** que diz ao CodeBuild **o que fazer** em cada etapa do build. Por padrão se chama **`buildspec.yml`** e fica na **raiz do código**; também é possível **sobrescrever** (nome/caminho diferente ou **inline** no projeto, ou via `--buildspec-override` em `start-build`).

Estrutura geral:

```yaml
version: 0.2                  # sempre 0.2 (a 0.1 é legada)
run-as: <usuário>             # opcional (Linux)
env:                          # variáveis de ambiente e segredos
  variables: { ... }
  parameter-store: { ... }
  secrets-manager: { ... }
  exported-variables: [ ... ]
  git-credential-helper: yes
proxy: { ... }                # opcional
batch: { ... }                # builds em lote
phases:                       # fases do build
  install: { ... }
  pre_build: { ... }
  build: { ... }
  post_build: { ... }
reports: { ... }              # relatórios de teste/cobertura
artifacts: { ... }            # saídas
cache: { ... }                # cache
```

## 2. Fases (`phases`)

| Fase | Para que serve | Exemplos |
|---|---|---|
| **install** | Instalar **runtimes e ferramentas** | `runtime-versions`, instalar CLIs, `npm ci` |
| **pre_build** | **Preparação** | Login no ECR, baixar dependências, lint, gerar variáveis |
| **build** | **Compilar/testar/empacotar** | `mvn package`, `npm test && npm run build`, `docker build` |
| **post_build** | **Pós-processamento** | `docker push`, publicar pacotes, notificar, gerar `imagedefinitions.json` |

Regras importantes de execução:

| Regra | Efeito |
|---|---|
| **Comandos executam em sequência** na mesma shell da fase | Falha de um comando **interrompe a fase** (por padrão) |
| **`on-failure`** | `ABORT` (padrão) ou `CONTINUE` por fase |
| **`finally`** | Bloco executado **mesmo se a fase falhar** (limpeza, upload de logs) |
| **`post_build` roda** mesmo se **`build` falhou**? | Em geral **não**, a menos que use `finally` ou `on-failure: CONTINUE`; verifique `CODEBUILD_BUILD_SUCCEEDING` |
| **Variáveis entre comandos** | Cada comando é um `sh -c` separado? **Não**: os comandos de uma **mesma fase** compartilham a shell (mas `cd` e `export` persistem apenas **dentro da fase**; use `|` multilinha para blocos) |
| **Persistência de `cd`/`export` entre fases** | **Não garantida**: reexporte o necessário ou use arquivos |

```yaml
phases:
  build:
    on-failure: ABORT
    commands:
      - echo "Início do build em $(date)"
      - |
        if [ "$CODEBUILD_WEBHOOK_TRIGGER" = "branch/main" ]; then
          echo "Build de main"
        fi
      - npm test
    finally:
      - echo "Executa sempre (sucesso ou falha)"
  post_build:
    commands:
      - if [ "$CODEBUILD_BUILD_SUCCEEDING" = "1" ]; then echo "Sucesso"; else echo "Falha"; fi
```

## 3. Variáveis e segredos (`env`)

```yaml
env:
  variables:
    STAGE: "hml"
    NODE_ENV: "production"
  parameter-store:
    DB_HOST: "/app/hml/db-host"
  secrets-manager:
    API_KEY: "app/hml/api:apiKey"            # segredo:chave-json
    DB_PASS: "app/hml/db:password:AWSCURRENT"
  exported-variables:
    - IMAGE_TAG
    - GIT_SHA
```

| Bloco | Uso | Observações |
|---|---|---|
| **variables** | Valores **não sensíveis** | Texto simples (visível) |
| **parameter-store** | **SSM Parameter Store** | A service role precisa de `ssm:GetParameters` e, para SecureString, `kms:Decrypt` |
| **secrets-manager** | **Secrets Manager** | `segredo:chave-json:estágio:versão`; role com `secretsmanager:GetSecretValue` |
| **exported-variables** | **Exporta** variáveis para **CodePipeline** (ações seguintes) | Use para passar tag/commit entre estágios |
| **git-credential-helper** | Permite `git clone` de submódulos privados com credencial do CodeBuild | Útil com submódulos |

> [!warning] Segredos
> Nunca coloque senhas/tokens em `variables`. O CodeBuild **mascara** valores de `secrets-manager`/`parameter-store` nos logs, mas **qualquer comando que imprima o segredo transformado** (base64, `echo` com prefixo) pode vazá-lo. Evite `set -x` em fases com segredos.

### 3.1 Variáveis automáticas úteis

| Variável | Significado |
|---|---|
| `CODEBUILD_BUILD_ID` / `CODEBUILD_BUILD_NUMBER` | Identificação do build |
| `CODEBUILD_SOURCE_VERSION` | Branch, tag, commit ou PR solicitado |
| `CODEBUILD_RESOLVED_SOURCE_VERSION` | **SHA do commit** efetivamente construído |
| `CODEBUILD_WEBHOOK_TRIGGER` | `branch/main`, `tag/v1.2`, `pr/42` |
| `CODEBUILD_WEBHOOK_EVENT` | `PUSH`, `PULL_REQUEST_CREATED`, etc. |
| `CODEBUILD_BUILD_SUCCEEDING` | `1` enquanto sem falhas |
| `CODEBUILD_SRC_DIR` | Diretório do código |
| `AWS_DEFAULT_REGION` | Região do build |

## 4. Artefatos (`artifacts`)

```yaml
artifacts:
  files:
    - 'target/*.jar'
    - 'appspec.yml'
    - 'scripts/**/*'
  discard-paths: no
  base-directory: 'build-output'
  name: app-$(date +%Y%m%d)-$CODEBUILD_RESOLVED_SOURCE_VERSION
  exclude-paths:
    - '**/*.map'
```

| Chave | Efeito |
|---|---|
| **files** | Arquivos/globs a incluir (obrigatório) |
| **base-directory** | Raiz relativa para os `files` |
| **discard-paths** | `yes` achata a estrutura de diretórios |
| **name** | Nome do artefato (suporta variáveis e `$(date)`) |
| **exclude-paths** | Exclusões |
| **secondary-artifacts** | **Vários artefatos** de saída (ex.: `app` e `config`) |
| **s3-prefix**, **packaging** (ZIP/NONE) | Controle no projeto |

Artefatos secundários (úteis no CodePipeline):

```yaml
artifacts:
  secondary-artifacts:
    app:
      files: ['target/app.jar']
    infra:
      base-directory: infra
      files: ['**/*']
```

## 5. Cache (`cache`)

```yaml
cache:
  paths:
    - '/root/.m2/**/*'
    - '/root/.cache/pip/**/*'
    - 'node_modules/**/*'
```

Requer **cache configurado no projeto** (S3 ou local). Boas práticas: **uma chave por tipo de projeto**, cache de **dependências** (não de saídas), e **invalidar** quando mudarem arquivos de lock.

## 6. Relatórios de teste e cobertura (`reports`)

O CodeBuild **interpreta resultados** e mostra **casos de teste** e **cobertura** no console, com **histórico por report group**.

```yaml
reports:
  testes-unitarios:
    files: ['target/surefire-reports/*.xml']
    file-format: JUNITXML
  cobertura:
    files: ['coverage/cobertura-coverage.xml']
    file-format: COBERTURAXML
```

| Formato de teste | Cobertura |
|---|---|
| JUNITXML, NUNITXML, NUNIT3XML, CUCUMBERJSON, TESTNGXML, VISUALSTUDIOTRX | **COBERTURAXML, JACOCOXML, CLOVERXML, SIMPLECOV** |

Use relatórios para **tendência** (testes flaky, queda de cobertura) e como **gate** (falhar se cobertura < limiar, via script que lê o XML).

## 7. Batch builds

Executa **vários builds** a partir de um **único** disparo:

| Tipo | Uso |
|---|---|
| **build-list** | Lista de builds independentes (diferentes ambientes) |
| **build-matrix** | **Matriz** (ex.: várias versões de runtime × SO) |
| **build-graph** | **Grafo** com dependências entre builds (build → teste → empacotar) |
| **build-fanout** | **Fan-out** de testes paralelos por *sharding* |

```yaml
batch:
  fast-fail: true
  build-matrix:
    static:
      ignore-failure: false
    dynamic:
      env:
        image: [aws/codebuild/amazonlinux-x86_64-standard:5.0]
        variables:
          NODE_VERSION: ['18', '20', '22']
```

Cuidado: batch builds **multiplicam** minutos cobrados e uso de concorrência.

## 8. Exemplos por linguagem

### 8.1 Node.js (testes, build e artefatos)

```yaml
version: 0.2
env:
  variables: { CI: "true" }
phases:
  install:
    runtime-versions: { nodejs: 20 }
    commands: [npm ci]
  pre_build:
    commands: [npm run lint]
  build:
    commands:
      - npm test -- --ci --reporters=default --reporters=jest-junit
      - npm run build
reports:
  jest:
    files: ['junit.xml']
    file-format: JUNITXML
artifacts:
  base-directory: dist
  files: ['**/*']
cache:
  paths: ['node_modules/**/*']
```

### 8.2 Java com Maven

```yaml
version: 0.2
phases:
  install:
    runtime-versions: { java: corretto21 }
  build:
    commands:
      - mvn -B -ntp clean verify
reports:
  junit:
    files: ['target/surefire-reports/*.xml']
    file-format: JUNITXML
  jacoco:
    files: ['target/site/jacoco/jacoco.xml']
    file-format: JACOCOXML
artifacts:
  files: ['target/*.jar']
  discard-paths: yes
cache:
  paths: ['/root/.m2/**/*']
```

### 8.3 Python

```yaml
version: 0.2
phases:
  install:
    runtime-versions: { python: 3.12 }
    commands:
      - pip install -r requirements.txt -r requirements-dev.txt
  build:
    commands:
      - pytest --junitxml=reports/junit.xml --cov=app --cov-report=xml:reports/coverage.xml
reports:
  pytest:
    files: ['reports/junit.xml']
    file-format: JUNITXML
  cov:
    files: ['reports/coverage.xml']
    file-format: COBERTURAXML
cache:
  paths: ['/root/.cache/pip/**/*']
```

### 8.4 Imagem Docker para o ECR e `imagedefinitions.json` (ECS + CodePipeline)

```yaml
version: 0.2
env:
  variables: { REPO_NAME: "pedidos-api" }
phases:
  pre_build:
    commands:
      - ACCOUNT=$(aws sts get-caller-identity --query Account --output text)
      - REGISTRY=$ACCOUNT.dkr.ecr.$AWS_DEFAULT_REGION.amazonaws.com
      - aws ecr get-login-password | docker login --username AWS --password-stdin $REGISTRY
      - TAG=${CODEBUILD_RESOLVED_SOURCE_VERSION:0:8}
  build:
    commands:
      - docker build -t $REGISTRY/$REPO_NAME:$TAG .
  post_build:
    commands:
      - docker push $REGISTRY/$REPO_NAME:$TAG
      - printf '[{"name":"pedidos-api","imageUri":"%s"}]' $REGISTRY/$REPO_NAME:$TAG > imagedefinitions.json
artifacts:
  files: ['imagedefinitions.json']
```

(O projeto precisa de **`privilegedMode`** e a service role de permissões de ECR.)

### 8.5 Validação de IaC (CloudFormation/Terraform)

```yaml
version: 0.2
phases:
  install:
    runtime-versions: { python: 3.12 }
    commands:
      - pip install cfn-lint checkov
  build:
    commands:
      - cfn-lint templates/*.yaml
      - checkov -d . --quiet --compact
```

## 9. Boas práticas

| Prática | Motivo |
|---|---|
| **`set -euo pipefail`** em scripts | Falhar cedo e de forma visível |
| **Scripts versionados** (`ci/*.sh`) chamados pelo buildspec | Buildspec curto e testável localmente |
| **Fixar versões** (imagem, runtimes, ferramentas) | Reprodutibilidade |
| **Paralelizar testes** (shards, batch fanout) | Reduzir tempo |
| **Fail fast** (lint e testes unitários primeiro) | Economizar minutos |
| **Relatórios e gates** de qualidade | Visibilidade |
| **Segredos só via Secrets Manager/Parameter Store** | Segurança |
| **Imprimir versões** das ferramentas | Diagnóstico |
| **Cache de dependências** | Velocidade |
| **Testar o buildspec localmente** com o **CodeBuild local agent** | Ciclo de feedback rápido |

## 10. Erros comuns

> [!bug] Erros comuns
> 1. **Indentação YAML incorreta** ou tabs.
> 2. **`version` diferente de 0.2.**
> 3. **Artefatos com caminho errado** (`base-directory`/`files`).
> 4. **Segredos em `variables`** ou impressos nos logs.
> 5. **`cd` numa fase e esperar o diretório na fase seguinte.**
> 6. **Não verificar `CODEBUILD_BUILD_SUCCEEDING`** em `post_build` (publica mesmo com falha).
> 7. **`docker push` sem login no ECR** ou sem privileged mode.
> 8. **Sem cache** ou cache mal definido.
> 9. **Buildspec gigante** em vez de scripts versionados.
> 10. **Não exportar variáveis** necessárias ao pipeline (`exported-variables`).

## 11. Troubleshooting

| Sintoma | Causa provável | Ação |
|---|---|---|
| `YAML_FILE_ERROR` | Sintaxe/indentação | Validar o YAML (linters) |
| `COMMAND_EXECUTION_ERROR` | Comando falhou | Ver o log da fase; rodar localmente |
| `no matching artifact paths found` | Glob/base-directory incorreto | Listar arquivos (`ls -R`) antes de `artifacts` |
| Segredo vazio | Nome/estágio/permissão incorretos | Ver o ARN, a chave JSON e a role |
| Relatório não aparece | Formato/caminho errado | Conferir `file-format` e `files` |
| `post_build` executou após falha | Fase roda com `finally`/`CONTINUE` | Checar `CODEBUILD_BUILD_SUCCEEDING` |
| Variável não chega ao pipeline | Sem `exported-variables` | Declarar e consumir com `#{codebuild.VAR}` |

## 12. Resumo rápido

- **buildspec 0.2**: `env`, `phases` (**install → pre_build → build → post_build**), `reports`, `artifacts`, `cache`, `batch`.
- **Segredos** com `parameter-store`/`secrets-manager`; **`exported-variables`** para o pipeline.
- **Artefatos** controlados por `files`, `base-directory`, `secondary-artifacts`; **cache** para dependências.
- **Relatórios** JUnit/Cobertura dão visibilidade; **batch builds** para matriz/paralelismo.
- Use **scripts versionados**, **fixe versões**, falhe cedo e **teste localmente**.

### 🧩 Quiz de Fixação

1. Quais são as quatro fases do buildspec?
2. Como obter um segredo do Secrets Manager no buildspec?
3. Para que serve `exported-variables`?
4. Como o CodeBuild trata os relatórios de teste?
5. O que é um batch build matrix?
6. Como evitar publicar quando o build falhou?
7. Por que usar scripts versionados chamados pelo buildspec?

**Respostas:**

1. install, pre_build, build e post_build.
2. No bloco `env.secrets-manager`, no formato `segredo:chave-json[:estágio:versão]`, com permissão na service role.
3. Exportar variáveis para as próximas ações do CodePipeline.
4. Interpreta arquivos (JUnit, cobertura etc.) e exibe casos de teste e cobertura em report groups, com histórico.
5. Uma execução que combina variações (versões de runtime, SO) em vários builds a partir de um único disparo.
6. Verificando `CODEBUILD_BUILD_SUCCEEDING` em post_build (ou estruturando com on-failure/finally).
7. Mantém o buildspec curto, testável localmente e reaproveitável.
