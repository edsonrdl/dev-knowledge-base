### 5.1.1.1. Segurança do CodeBuild — service role mínima, segredos, VPC e isolamento, imagens confiáveis, cache e artefatos, SBOM e assinatura, e hardening de pipelines de build

> [!warning] Aviso
> Políticas IAM, chaves de condição e comandos abaixo são **ilustrativos, de memória e não foram executados**. **Teste no IAM Policy Simulator e em ambiente não produtivo.** Confirme na documentação as ações atuais e as práticas recomendadas pela AWS para CI/CD seguro. O **servidor de build é um alvo valioso**: ele tem acesso ao código, a segredos e à capacidade de **implantar em produção**.

## 1. Por que o build é um alvo crítico

O ambiente de build reúne **três poderes**: ler o **código-fonte**, usar **segredos** (chaves, tokens, senhas) e **produzir artefatos que vão para produção**. Quem controla o build controla o que roda em produção. Ataques reais de **cadeia de suprimentos** (dependências maliciosas, pipelines adulterados, tokens vazados em logs, imagens base comprometidas) miram exatamente aqui.

```
 Ameaças ao pipeline de build:
 [Código malicioso em PR]  [Dependência comprometida]  [Imagem base adulterada]
 [Segredo vazado em log]   [Service role ampla]        [Cache envenenado]
 [Artefato substituído]    [Buildspec alterado]        [Exfiltração via rede]
```

Defesa em camadas: **identidade mínima**, **segredos corretos**, **isolamento de rede**, **entradas confiáveis**, **saídas verificáveis** e **auditoria**.

## 2. Service role: o ponto central

Cada projeto de build assume uma **service role**. Ela define **tudo o que o build pode fazer na AWS**.

### 2.1 Princípios

| Princípio | Aplicação |
|---|---|
| **Uma role por projeto/função** | Não compartilhar uma role "faz-tudo" |
| **Menor privilégio** | Somente S3/ECR/Logs/Secrets necessários, com **recursos específicos** |
| **Sem `AdministratorAccess`** | Nunca |
| **Separar build de deploy** | O build **não** deve ter permissão de produção; o **deploy** usa outra role (CodePipeline/CodeDeploy/CloudFormation) |
| **Permission boundary** | Limita o que a role (e quem a cria) pode conceder |
| **Condições** | `aws:SourceArn`/`aws:SourceAccount` na **trust policy** (evita *confused deputy*) |

### 2.2 Trust policy

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": { "Service": "codebuild.amazonaws.com" },
    "Action": "sts:AssumeRole",
    "Condition": {
      "StringEquals": { "aws:SourceAccount": "123456789012" },
      "ArnLike": { "aws:SourceArn": "arn:aws:codebuild:us-east-1:123456789012:project/app-api" }
    }
  }]
}
```

### 2.3 Política mínima (exemplo para build com ECR e artefatos)

```json
{
  "Version": "2012-10-17",
  "Statement": [
    { "Sid": "Logs", "Effect": "Allow",
      "Action": ["logs:CreateLogGroup","logs:CreateLogStream","logs:PutLogEvents"],
      "Resource": "arn:aws:logs:us-east-1:123456789012:log-group:/aws/codebuild/app-api*" },
    { "Sid": "Artefatos", "Effect": "Allow",
      "Action": ["s3:PutObject","s3:GetObject","s3:GetObjectVersion","s3:GetBucketAcl","s3:GetBucketLocation"],
      "Resource": ["arn:aws:s3:::meu-bucket-artefatos","arn:aws:s3:::meu-bucket-artefatos/app-api/*"] },
    { "Sid": "ECRLogin", "Effect": "Allow", "Action": "ecr:GetAuthorizationToken", "Resource": "*" },
    { "Sid": "ECRPush", "Effect": "Allow",
      "Action": ["ecr:BatchCheckLayerAvailability","ecr:InitiateLayerUpload","ecr:UploadLayerPart","ecr:CompleteLayerUpload","ecr:PutImage","ecr:BatchGetImage","ecr:GetDownloadUrlForLayer"],
      "Resource": "arn:aws:ecr:us-east-1:123456789012:repository/pedidos-api" },
    { "Sid": "Segredos", "Effect": "Allow", "Action": "secretsmanager:GetSecretValue",
      "Resource": "arn:aws:secretsmanager:us-east-1:123456789012:secret:app/build/*" },
    { "Sid": "Relatorios", "Effect": "Allow",
      "Action": ["codebuild:CreateReportGroup","codebuild:CreateReport","codebuild:UpdateReport","codebuild:BatchPutTestCases","codebuild:BatchPutCodeCoverages"],
      "Resource": "arn:aws:codebuild:us-east-1:123456789012:report-group/app-api-*" }
  ]
}
```

### 2.4 Quem pode iniciar/alterar builds

| Ação | Quem |
|---|---|
| `codebuild:StartBuild` | Pipeline, automações e perfis autorizados |
| `codebuild:UpdateProject` | **Poucos** (quem altera o projeto altera **o que roda com a role**) |
| `--buildspec-override`, `--environment-variables-override` | Restringir (permite executar **comandos arbitrários** com a service role) |
| `iam:PassRole` para a service role | Somente administradores de plataforma |

> [!warning] Escalonamento de privilégio
> Quem pode **`StartBuild` com `buildspecOverride`** ou **editar o projeto** consegue **executar comandos com a service role**. Trate essas permissões como **equivalentes às permissões da role**. Em projetos sensíveis, **bloqueie overrides** (política IAM com condição) e proteja o **buildspec** no repositório com revisão de PRs.

## 3. Segredos

| Prática | Detalhe |
|---|---|
| **Secrets Manager / Parameter Store** | Referencie no buildspec (`secrets-manager`, `parameter-store`) — valores **mascarados** nos logs |
| **Sem segredos em `PLAINTEXT`** | Nunca; nem no projeto, nem no repositório |
| **Credenciais temporárias** | Use **roles/OIDC** em vez de chaves de acesso |
| **Rotação** | Segredos de integração (tokens de registry) rotacionados automaticamente |
| **Escopo mínimo** | Cada projeto só lê os **seus** segredos (ARN específico) |
| **Evitar `set -x`** e `echo` de variáveis | Prevenir vazamento em logs |
| **Logs com retenção** e **acesso restrito** | Logs podem conter dados sensíveis |
| **Segredos para PRs não confiáveis** | **Não fornecer** (projeto separado sem credenciais) |

Atenção ao **mascaramento**: ele cobre valores **exatos**. Se o script transformar o valor (base64, partes), ele **pode aparecer** no log. Use ferramentas que não imprimem segredos e valide logs.

## 4. Isolamento de rede

| Camada | Controle |
|---|---|
| **VPC** | Rode builds em **sub-redes privadas**, com saída controlada |
| **Security groups** | **Egress restrito** (somente destinos necessários), sem ingress |
| **VPC endpoints** | S3, ECR, CloudWatch Logs, Secrets Manager, STS, CodeArtifact — reduzem exposição e NAT |
| **Proxy/firewall de saída** | Permitir apenas registries/repositórios aprovados (npm, PyPI, Maven via **CodeArtifact**) |
| **Bloquear metadados** | Contêineres de build: evitar acesso a endpoints internos indevidos |
| **Sem acesso a produção** | A sub-rede de build **não** deve alcançar bancos de produção |
| **DNS Firewall (Route 53 Resolver)** | Bloquear domínios maliciosos |

Exfiltração é um risco real: um build comprometido pode **enviar segredos** para a internet; **egress controlado** reduz o raio de dano.

## 5. Entradas confiáveis (código, dependências, imagens)

### 5.1 Código e PRs

- **Revisão obrigatória** de PRs; **proteção da branch** principal.
- **Arquivos de CI** (`buildspec`, `Dockerfile`, scripts) em **caminhos protegidos** (CODEOWNERS/regras de aprovação).
- **PRs de forks/externos**: sem segredos, sem privileged mode, **aprovação manual** antes de executar.

### 5.2 Dependências

| Controle | Como |
|---|---|
| **CodeArtifact** como único registry | Políticas de **origem de pacotes** (bloquear *dependency confusion*) |
| **Lockfiles e hashes** (`npm ci`, `pip --require-hashes`) | Reprodutibilidade e integridade |
| **SCA** (`npm audit`, `pip-audit`, `OWASP Dependency-Check`, Inspector) | Vulnerabilidades conhecidas |
| **Versões fixas** | Sem `latest`/ranges soltos em produção |
| **Dependency confusion** | Pacotes internos com **namespaces/escopos** reservados |

### 5.3 Imagens base

- Usar imagens **gerenciadas pela AWS** (fixando versão) ou **imagens próprias no ECR** com **escaneamento** (Inspector) e **atualização periódica**.
- **Espelhar** imagens públicas no **ECR (pull-through cache)** após validação; evitar `docker pull` direto do Docker Hub (rate limit e proveniência).
- **Assinar e verificar** imagens (AWS Signer/Notation/cosign) e **bloquear** o uso de imagens não assinadas em deploy (admission control).
- **Imagens mínimas** (distroless/slim) e **usuário não root** nas imagens de aplicação.

## 6. Saídas verificáveis (artefatos e imagens)

| Prática | Detalhe |
|---|---|
| **SBOM** (Software Bill of Materials) | Gerar com **Syft/CycloneDX** no build e arquivar junto ao artefato |
| **Assinatura de artefatos/imagens** | **AWS Signer**, **Notation**, **cosign**; verificação no deploy |
| **Proveniência (SLSA)** | Registrar **como e onde** foi construído (build ID, commit, imagem do builder) |
| **Escaneamento** | **ECR scan**, **Inspector**, **Trivy/Grype** como gate |
| **Imutabilidade** | **ECR tag immutability** e **S3 Object Lock/versionamento** para artefatos |
| **Artefatos criptografados** | **SSE-KMS** no bucket de artefatos; permissões de chave mínimas |
| **Bucket de artefatos protegido** | Block Public Access, política que só permite as roles do pipeline |
| **Tags por SHA**, nunca `latest` | Rastreabilidade e rollback |

## 7. Cache e privileged mode: riscos específicos

| Recurso | Risco | Mitigação |
|---|---|---|
| **Cache S3/local** | **Envenenamento**: artefato malicioso persiste entre builds | Chaves de cache por branch confiável; bucket restrito; **limpar** periodicamente; não cachear saídas executáveis sem verificação |
| **Privileged mode** | O contêiner ganha poderes de host (Docker daemon) | Só em projetos confiáveis; **roles mínimas**; considerar **BuildKit rootless/Kaniko**; nunca para código de forks |
| **Frotas reservadas** | Instâncias **reutilizadas** entre builds (estado residual) | Limpeza, isolamento por projeto, não misturar projetos de confianças diferentes |
| **`run-as`** | Executar como usuário não root quando possível | Menor impacto de comprometimento |

## 8. Auditoria e detecção

| Fonte | O que observar |
|---|---|
| **CloudTrail** | `StartBuild` (com overrides), `UpdateProject`, `CreateWebhook`, `PassRole`, acessos a segredos/KMS |
| **CloudWatch Logs** | Comandos executados, erros, vazamentos acidentais |
| **EventBridge** | Builds falhos/fora do padrão (horário, branch) |
| **Config** | Regras: projetos sem VPC, com `privilegedMode`, com `PLAINTEXT` de segredos |
| **GuardDuty** | Comportamentos anômalos de credenciais |
| **IAM Access Analyzer** | Acesso externo a buckets/ECR/KMS; geração de políticas por uso |
| **Security Hub** | Achados consolidados |

Alertas prioritários: **`UpdateProject` fora do pipeline de IaC**, **builds com override de buildspec**, **uso da service role em contexto inesperado**, **pull de segredos fora do horário**, **criação de webhooks**.

## 9. Governança multi-conta e IaC

- **Projetos definidos por IaC** (CloudFormation/CDK/Terraform), com **revisão** e **drift detection**; ninguém edita no console.
- **Conta de ferramentas (tooling)** dedicada, separada das cargas de trabalho.
- **SCPs** para limitar `iam:PassRole`, criação de projetos com `privilegedMode`, regiões e uso de imagens não aprovadas.
- **Deploy cross-account** com **roles de deploy** assumidas pelo pipeline (não pela role de build).
- **Padrão de projeto** (template) com roles, logs, VPC e criptografia já configurados.

## 10. Checklist de hardening

1. **Service role por projeto**, mínima, com **trust policy condicionada**.
2. **Bloquear `buildspec`/variáveis override** em projetos sensíveis; restringir `UpdateProject`/`PassRole`.
3. **Segredos** via Secrets Manager/Parameter Store; nunca em `PLAINTEXT`; **sem `set -x`**.
4. **VPC privada**, **egress restrito**, endpoints e **CodeArtifact** como origem de pacotes.
5. **PRs de forks** sem segredos/privilégios; aprovação antes de executar.
6. **Imagens base fixadas, escaneadas e assinadas**; espelho no ECR.
7. **Lockfiles/SCA**, proteção contra *dependency confusion*.
8. **SBOM, assinatura e proveniência**; **tags imutáveis** e por SHA.
9. **Privileged mode** só quando necessário; frotas isoladas por confiança.
10. **Logs, CloudTrail e alertas**; **IaC** e revisão para qualquer mudança.

## 11. Erros comuns

> [!bug] Erros comuns
> 1. **Service role com `AdministratorAccess`** ou compartilhada por todos os projetos.
> 2. **Permitir `StartBuild` com override** a muitos usuários (execução arbitrária).
> 3. **Segredos em variáveis PLAINTEXT** ou impressos nos logs.
> 4. **Builds sem VPC e com egress livre** para a internet.
> 5. **Rodar PRs de fork com segredos e privileged mode.**
> 6. **Puxar imagens/pacotes direto da internet** sem controle (proveniência).
> 7. **Cache sem proteção** (envenenamento).
> 8. **Mesma role para build e deploy.**
> 9. **Sem SBOM/assinatura/escaneamento**, e tags `latest`.
> 10. **Projetos editados à mão no console**, sem IaC e sem auditoria.

## 12. Troubleshooting

| Sintoma | Causa provável | Ação |
|---|---|---|
| `AccessDenied` após endurecer a role | Permissão mínima faltando (ex.: `ecr:GetAuthorizationToken`) | Ler o erro no log; usar Access Analyzer para gerar a política por uso |
| Build em VPC falha ao baixar pacotes | Egress bloqueado/sem endpoint | Liberar o destino necessário ou usar CodeArtifact |
| Segredo "vazou" no log | Comando imprimiu variável transformada | Rotacionar o segredo, corrigir o script, limpar/expirar logs |
| Imagem bloqueada no deploy | Não assinada/escaneada | Assinar/escanear no pipeline |
| Role usada fora do esperado | Override de buildspec ou `UpdateProject` | Revisar CloudTrail; restringir permissões |
| Cache suspeito | Artefato inesperado | Invalidar o cache, recriar a partir de fontes confiáveis |
| Dependência desconhecida instalada | *Dependency confusion* | Configurar origens do CodeArtifact e escopos |

## 13. Resumo rápido

- **O build é um alvo crítico**: tem código, segredos e caminho a produção.
- **Service role mínima por projeto**, trust policy condicionada, **sem admin**, **build ≠ deploy**; cuidado com **overrides** e `UpdateProject`.
- **Segredos** só por Secrets Manager/Parameter Store; **VPC privada**, **egress restrito**, **CodeArtifact**.
- **Entradas confiáveis** (PRs revisados, lockfiles, imagens fixadas/escaneadas) e **saídas verificáveis** (SBOM, assinatura, proveniência, tags imutáveis).
- **Cache e privileged mode** são riscos próprios; **audite** (CloudTrail/Config) e use **IaC**.

### 🧩 Quiz de Fixação

1. Por que a service role do build deve ser mínima e separada da de deploy?
2. Qual o risco de permitir buildspec override a muitos usuários?
3. Como evitar *dependency confusion*?
4. Por que não rodar PRs de forks com segredos?
5. Que artefatos de segurança gerar para a cadeia de suprimentos?
6. Quais riscos de cache e privileged mode?
7. Que alertas de auditoria são prioritários?

**Respostas:**

1. Porque quem controla o build controla o que a role faz; separar build de deploy limita o impacto de um comprometimento.
2. Permite executar comandos arbitrários com a service role (escalonamento de privilégio).
3. Usando o CodeArtifact como única origem de pacotes, com regras de origem, escopos/namespaces internos e lockfiles com hashes.
4. Código não confiável pode ler e exfiltrar segredos do ambiente.
5. SBOM, assinatura de artefatos/imagens, proveniência (SLSA), resultados de escaneamento e tags imutáveis.
6. Cache pode ser envenenado e persistir entre builds; privileged mode dá poderes de host ao contêiner.
7. UpdateProject fora do IaC, builds com override, uso inesperado da service role, acesso a segredos fora do padrão e criação de webhooks.
