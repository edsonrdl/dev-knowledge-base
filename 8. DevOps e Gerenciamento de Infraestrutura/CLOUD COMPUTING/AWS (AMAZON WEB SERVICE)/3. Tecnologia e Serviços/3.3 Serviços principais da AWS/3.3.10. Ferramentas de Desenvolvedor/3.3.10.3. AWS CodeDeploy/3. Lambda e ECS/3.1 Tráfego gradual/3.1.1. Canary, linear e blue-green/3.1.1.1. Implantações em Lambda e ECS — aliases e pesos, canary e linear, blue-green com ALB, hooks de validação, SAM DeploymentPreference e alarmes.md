### 3.1.1.1. Implantações em Lambda e ECS — aliases e pesos, canary e linear, blue-green com ALB, hooks de validação, SAM DeploymentPreference e alarmes

> [!warning] Aviso
> Nomes de configurações, campos do AppSync/AppSpec e a disponibilidade de alternativas (como o **blue/green nativo do ECS**) abaixo são **de memória e mudam**. **Confirme na documentação do CodeDeploy, do ECS e do SAM.** YAMLs, comandos e código são ilustrativos e **não foram executados**. Liberação gradual só protege se houver **métricas, alarmes e validações** bem definidos.

## 1. O princípio: liberar para poucos, observar e decidir

Em vez de trocar **100% do tráfego** para a nova versão de uma vez, as plataformas serverless e de contêineres permitem **mover o tráfego gradualmente** e **voltar atrás** se algo falhar. É a diferença entre **"apostar tudo"** e **"testar com 10% dos usuários"**.

```
Tráfego:  v1 ████████████ 100%
          v1 ██████████░░ 90% | v2 ██ 10%     ← canary (observa alarmes e validações)
          v1 ░░░░░░░░░░░░ 0%  | v2 ████████████ 100%   ← promove (ou volta a v1 se alarme)
```

O CodeDeploy automatiza: **desloca o tráfego**, **executa hooks de validação**, **monitora alarmes** e **reverte** automaticamente.

## 2. AWS Lambda: versões, aliases e pesos

### 2.1 Conceitos

| Conceito | Significado |
|---|---|
| **Versão** (`$LATEST`, `1`, `2`, ...) | **Foto imutável** do código e configuração da função |
| **Alias** (`prod`, `hml`) | **Ponteiro nomeado** para uma versão (ou **duas, com pesos**) |
| **Pesos do alias** | Distribuição do tráfego entre **duas versões** (ex.: 90% v1 / 10% v2) |

Clientes invocam o **alias** (ARN com `:prod`); o CodeDeploy **altera os pesos** do alias ao longo do tempo.

### 2.2 Configurações de tráfego (Lambda)

| Tipo | Exemplos de configuração | Comportamento |
|---|---|---|
| **Canary** | `Canary10Percent5Minutes`, `Canary10Percent10Minutes`, `Canary10Percent15Minutes`, `Canary10Percent30Minutes` | X% para a nova versão; depois do tempo, **100%** |
| **Linear** | `Linear10PercentEvery1Minute`, `...2Minutes`, `...3Minutes`, `...10Minutes` | +10% a cada intervalo até 100% |
| **All-at-once** | `AllAtOnce` | 100% imediatamente |

Escolha por **risco e volume**: poucos acessos exigem esperas **maiores** para obter **sinal estatístico**; funções críticas pedem **canary + janela de observação**.

### 2.3 AppSpec para Lambda

```yaml
version: 0.0
Resources:
  - MinhaFuncao:
      Type: AWS::Lambda::Function
      Properties:
        Name: processa-pedido
        Alias: prod
        CurrentVersion: 7
        TargetVersion: 8
Hooks:
  - BeforeAllowTraffic: validaAntes     # nome da FUNÇÃO Lambda de validação
  - AfterAllowTraffic: validaDepois
```

| Hook (Lambda) | Quando | Uso |
|---|---|---|
| **BeforeAllowTraffic** | Antes de enviar **qualquer** tráfego à nova versão | Testes de fumaça **invocando a versão nova** diretamente |
| **AfterAllowTraffic** | Depois que **todo** o tráfego foi deslocado | Verificações finais, limpeza |

A função de hook **reporta o resultado** ao CodeDeploy com `PutLifecycleEventHookExecutionStatus` (`Succeeded` ou `Failed`) — **sem isso**, a implantação **expira**.

```python
import boto3
cd = boto3.client("codedeploy")
lam = boto3.client("lambda")

def handler(event, context):
    deployment_id = event["DeploymentId"]
    hook_id = event["LifecycleEventHookExecutionId"]
    status = "Succeeded"
    try:
        r = lam.invoke(FunctionName="processa-pedido:8", Payload=b'{"teste": true}')
        if r["StatusCode"] != 200 or b"erro" in r["Payload"].read():
            status = "Failed"
    except Exception:
        status = "Failed"
    cd.put_lifecycle_event_hook_execution_status(
        deploymentId=deployment_id, lifecycleEventHookExecutionId=hook_id, status=status)
```

### 2.4 SAM: DeploymentPreference (o jeito mais comum)

O **AWS SAM** simplifica tudo: cria o **alias**, o **application/deployment group** do CodeDeploy e as **roles**.

```yaml
Resources:
  ProcessaPedido:
    Type: AWS::Serverless::Function
    Properties:
      Handler: app.handler
      Runtime: python3.12
      AutoPublishAlias: prod
      DeploymentPreference:
        Type: Canary10Percent5Minutes
        Alarms:
          - !Ref AlarmeErrosFuncao
          - !Ref AlarmeLatenciaApi
        Hooks:
          PreTraffic: !Ref FuncaoValidaAntes
          PostTraffic: !Ref FuncaoValidaDepois
  AlarmeErrosFuncao:
    Type: AWS::CloudWatch::Alarm
    Properties:
      Namespace: AWS/Lambda
      MetricName: Errors
      Dimensions: [{ Name: FunctionName, Value: !Ref ProcessaPedido }, { Name: Resource, Value: !Sub "${ProcessaPedido}:prod" }]
      Statistic: Sum
      Period: 60
      EvaluationPeriods: 1
      Threshold: 1
      ComparisonOperator: GreaterThanOrEqualToThreshold
```

Boas práticas Lambda:

- **Alarmes sobre o alias/versão nova** (dimensão `Resource` = `função:alias`) para isolar o efeito.
- **Métricas de negócio** (taxa de pedidos aprovados) além de `Errors`/`Duration`.
- **Provisioned concurrency** na nova versão para evitar **cold starts** distorcendo o canary.
- **Compatibilidade de dados/eventos** entre v1 e v2 (ambas ativas ao mesmo tempo).

## 3. Amazon ECS: blue/green com CodeDeploy

### 3.1 Arquitetura

```
              ┌── Listener de PRODUÇÃO (porta 443)  ──▶ Target group AZUL  ──▶ tasks v1
 ALB/NLB ─────┤
              └── Listener de TESTE   (porta 8443)  ──▶ Target group VERDE ──▶ tasks v2 (novo)
 
 CodeDeploy:  cria tasks v2 → registra no VERDE → testa via listener de teste → desloca o listener de produção
              (canary/linear/all-at-once) → mantém v1 por um tempo → encerra v1
```

| Elemento | Função |
|---|---|
| **Dois target groups** (azul/verde) | Um recebe produção, o outro o novo conjunto |
| **Listener de produção** | Roteia o tráfego real |
| **Listener de teste (opcional)** | Permite **validar a versão nova** antes de produção |
| **Task definition nova** | Define a imagem/versão a implantar |
| **Task set** | Conjunto de tasks de uma versão dentro do serviço (modelo `CODE_DEPLOY` do controlador de implantação) |

O serviço ECS precisa usar o **tipo de controlador de implantação `CODE_DEPLOY`** (criado assim; **não** se converte um serviço rolling em blue/green sem recriar).

### 3.2 Configurações de tráfego (ECS)

| Config | Comportamento |
|---|---|
| **`CodeDeployDefault.ECSAllAtOnce`** | Troca 100% de uma vez |
| **`CodeDeployDefault.ECSLinear10PercentEvery1Minutes/3Minutes`** | Gradual linear |
| **`CodeDeployDefault.ECSCanary10Percent5Minutes/15Minutes`** | Canary |
| **Personalizadas** | Canary/linear com percentuais e tempos próprios |

Parâmetros adicionais: **tempo de espera antes de terminar as tasks azuis** (de 0 a vários dias), para **rollback rápido**.

### 3.3 AppSpec para ECS

```yaml
version: 0.0
Resources:
  - TargetService:
      Type: AWS::ECS::Service
      Properties:
        TaskDefinition: "arn:aws:ecs:us-east-1:123456789012:task-definition/pedidos-api:42"
        LoadBalancerInfo:
          ContainerName: "pedidos-api"
          ContainerPort: 8080
        PlatformVersion: "LATEST"
        NetworkConfiguration:
          AwsvpcConfiguration:
            Subnets: ["subnet-0a", "subnet-0b"]
            SecurityGroups: ["sg-0abc"]
            AssignPublicIp: "DISABLED"
        CapacityProviderStrategy:
          - Base: 1
            CapacityProvider: "FARGATE"
            Weight: 1
Hooks:
  - BeforeInstall: "LambdaValidaBeforeInstall"
  - AfterInstall: "LambdaValidaAfterInstall"
  - AfterAllowTestTraffic: "LambdaTestesIntegracao"
  - BeforeAllowTraffic: "LambdaPreProducao"
  - AfterAllowTraffic: "LambdaPosProducao"
```

| Hook (ECS) | Momento |
|---|---|
| **BeforeInstall** | Antes de criar o **task set** verde |
| **AfterInstall** | Task set verde criado (ainda sem tráfego) |
| **AfterAllowTestTraffic** | Após o **listener de teste** apontar para o verde — **rode testes de integração** aqui |
| **BeforeAllowTraffic** | Antes de mover o tráfego de **produção** |
| **AfterAllowTraffic** | Após todo o tráfego estar no verde |

Os hooks são **funções Lambda** que **reportam o status** ao CodeDeploy (como no caso do Lambda).

### 3.4 Integração com CodePipeline

O pipeline usa a ação **`CodeDeployToECS`**, recebendo dois artefatos: **`taskdef.json`** e **`appspec.yaml`** (com placeholders como `<TASK_DEFINITION>` e `<IMAGE1_NAME>` substituídos com a imagem do **ECR** produzida pelo **CodeBuild**):

```
Source ─▶ CodeBuild (build/push da imagem, gera taskdef.json e appspec.yaml) ─▶ CodeDeployToECS
```

### 3.5 Alternativas no ECS

| Opção | Observação |
|---|---|
| **Rolling update** (controlador ECS) | Simples; sem listener de teste; rollback via circuit breaker |
| **ECS blue/green nativo** (recurso recente) | Gerenciado pelo ECS, **sem CodeDeploy** em alguns cenários; verifique a disponibilidade |
| **CodeDeploy blue/green** | Hooks, listener de teste, linear/canary — o mais flexível |
| **Deployment circuit breaker** | Reverte automaticamente falhas de tasks (rolling) |

## 4. Alarmes e rollback (visão geral)

Em ambas as plataformas:

- Configure **alarmes do CloudWatch** no **deployment group**; se algum **entrar em `ALARM`** durante a implantação, o CodeDeploy **interrompe e reverte** (se `DEPLOYMENT_STOP_ON_ALARM` e rollback estiverem habilitados).
- **Falha de hook** também causa rollback.
- Métricas recomendadas: **taxa de erros 5xx do ALB/API**, **latência p95/p99**, **erros da função**, **saúde do target group (UnHealthyHostCount)**, **métricas de negócio**.

Mais detalhes na folha de rollbacks e validação.

## 5. Exemplo ponta a ponta (ECS)

```
1) Commit em main → CodePipeline
2) CodeBuild: testes, docker build, push ao ECR (tag = SHA), gera taskdef.json + appspec.yaml
3) CodeDeploy (ECSCanary10Percent5Minutes):
     - Cria tasks v2 no target group VERDE
     - Hook AfterAllowTestTraffic: testes de integração contra o listener 8443
     - Desloca 10% → aguarda 5 min, monitorando alarmes (5xx, latência, saúde)
     - Sem alarmes → 100%; espera 30 min; encerra as tasks AZUL
     - Qualquer alarme/hook falho → reverte para AZUL automaticamente
```

## 6. Escolha de estratégia

| Situação | Estratégia sugerida |
|---|---|
| **API crítica**, muito tráfego | **Canary** (10% por 10–15 min) + alarmes de negócio |
| **Funcionalidade nova com risco moderado** | **Linear** (10% a cada 3–10 min) |
| **Ambiente de homologação** | **AllAtOnce** |
| **Pouco tráfego** (baixo sinal) | Esperas maiores, ou testes sintéticos em hooks |
| **Mudanças de esquema de dados** | **Expand/contract** (compatível com v1 e v2); evite blue/green sem compatibilidade |
| **Dependência de estado em memória** | Cuidado com sessões; preferir stateless |

## 7. Erros comuns

> [!bug] Erros comuns
> 1. **Hook Lambda que não reporta o status** (a implantação expira).
> 2. **Sem alarmes** no deployment group (o canary vira só "demora").
> 3. **Alarmes com métricas agregadas** que diluem o sinal da versão nova.
> 4. **Incompatibilidade de dados** entre v1 e v2 ativos simultaneamente.
> 5. **Serviço ECS com controlador errado** (não `CODE_DEPLOY`).
> 6. **Listener de teste não configurado**, sem validar antes da produção.
> 7. **Esperar 0 min para terminar o azul**, perdendo o rollback rápido.
> 8. **Canary curto demais** para o volume de tráfego.
> 9. **Cold starts** distorcendo métricas do canary em Lambda.
> 10. **AppSpec com versões/alias inconsistentes** (CurrentVersion/TargetVersion).

## 8. Troubleshooting

| Sintoma | Causa provável | Ação |
|---|---|---|
| Implantação Lambda expira no hook | Função de hook não chamou `PutLifecycleEventHookExecutionStatus` | Corrigir a função e permissões |
| Rollback imediato | Alarme já em `ALARM` ou falha de hook | Verificar o estado dos alarmes antes de iniciar |
| ECS: `The target group does not have an associated load balancer` | Configuração de LB/target groups | Revisar listeners e target groups |
| ECS: tasks verdes não saudáveis | Health check/porta/segurança | Corrigir o health check e os SGs |
| Alias não muda | `TargetVersion` igual à atual ou falta de publicação | Publicar nova versão e atualizar o AppSpec |
| Tráfego não chega ao teste | Listener de teste/SG | Abrir a porta de teste e validar regras |
| Deploy lento | Configuração linear/canary longa | Ajustar para o risco aceitável |

## 9. Resumo rápido

- **Lambda**: **alias com pesos** entre versões; **canary/linear/all-at-once**; hooks **BeforeAllowTraffic/AfterAllowTraffic** (funções que **reportam status**); **SAM DeploymentPreference** automatiza.
- **ECS**: **blue/green** com **dois target groups**, **listener de teste**, hooks (`AfterAllowTestTraffic` etc.), serviço com controlador **CODE_DEPLOY**; pipeline com **CodeDeployToECS**.
- **Alarmes + hooks** decidem promoção ou **rollback automático**.
- Considere **compatibilidade de dados**, volume de tráfego e **alternativas** (rolling, blue/green nativo do ECS).

### 🧩 Quiz de Fixação

1. O que é um alias de Lambda e como o CodeDeploy o usa?
2. Qual a diferença entre canary e linear?
3. Para que serve o listener de teste no ECS?
4. O que acontece se a função de hook não reportar o status?
5. Que tipo de controlador de implantação o serviço ECS precisa para blue/green com CodeDeploy?
6. Como o SAM simplifica a liberação gradual de Lambda?
7. Por que alarmes são essenciais?

**Respostas:**

1. Um ponteiro nomeado para versões da função; o CodeDeploy muda os pesos do alias entre a versão antiga e a nova.
2. Canary envia uma fração e depois 100%; linear aumenta o percentual em intervalos regulares.
3. Permitir validar o conjunto verde com tráfego de teste antes de mover o tráfego de produção.
4. A implantação expira/falha, pois o CodeDeploy aguarda o status do hook.
5. CODE_DEPLOY.
6. Com `AutoPublishAlias` e `DeploymentPreference` (tipo, alarmes e hooks), criando alias, application e deployment group automaticamente.
7. São o critério objetivo para interromper e reverter a implantação automaticamente quando a nova versão degrada.
