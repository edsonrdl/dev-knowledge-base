### 2.1.1.1. Implantações em EC2 e on-premises — agent, appspec.yml, hooks do ciclo de vida, in-place vs blue-green, configurações de implantação e integração com Auto Scaling e ELB

> [!warning] Aviso
> Nomes de hooks, caminhos do agent, comandos e parâmetros abaixo são **de memória e podem variar por versão do agent e do SO**; **confirme na documentação do CodeDeploy**. Scripts e YAMLs são ilustrativos e **não foram executados**. Scripts de hook rodam **como root por padrão** em servidores reais: revise-os com o mesmo cuidado de código de produção.

## 1. Arquitetura da implantação em EC2/on-premises

```
 Revisão (zip/tar com appspec.yml + código) ──▶ S3 (ou GitHub)
                                │
  CodeDeploy (serviço) ── comandos ──▶ CodeDeploy AGENT (em cada instância)
                                          │ 1) baixa a revisão (S3)
                                          │ 2) executa os hooks na ordem do ciclo de vida
                                          │ 3) copia arquivos e aplica permissões
                                          └ 4) reporta o resultado (sucesso/falha) ao serviço
```

O **agent** é o executor: faz **polling** do serviço CodeDeploy (HTTPS de saída), **baixa a revisão** com as credenciais do **instance profile**, **guarda os arquivos** em `/opt/codedeploy-agent/deployment-root/` (Linux) e **executa os scripts**.

### 1.1 Instalando e mantendo o agent

| Ponto | Detalhe |
|---|---|
| **Instalação** | Pacote do agent (via SSM Distributor, user data, AMI ou `aws s3 cp` + `install`) |
| **Serviço** | `codedeploy-agent` (systemd/init); precisa estar **em execução** |
| **Rede** | Saída HTTPS para o endpoint `codedeploy-commands` e S3 (ou **VPC endpoints**) |
| **Atualização** | **Atualize o agent** periodicamente (há configuração para auto-update) |
| **Sistemas** | Amazon Linux, Ubuntu, RHEL, Windows Server; **on-premises** exige registro da instância |
| **Logs** | `/var/log/aws/codedeploy-agent/codedeploy-agent.log` e `/opt/codedeploy-agent/deployment-root/deployment-logs/` |

```bash
# Exemplo (Amazon Linux): instalação via script oficial (ilustrativo)
sudo yum install -y ruby wget
cd /tmp && wget https://aws-codedeploy-us-east-1.s3.us-east-1.amazonaws.com/latest/install
chmod +x install && sudo ./install auto
sudo systemctl status codedeploy-agent
```

Dica: use **AWS Systems Manager** (State Manager/Distributor) para **instalar e manter** o agent em toda a frota.

### 1.2 Instance profile e permissões

A role da instância precisa **ler a revisão**:

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": ["s3:GetObject", "s3:GetObjectVersion", "s3:ListBucket"],
    "Resource": ["arn:aws:s3:::meu-bucket-revisoes", "arn:aws:s3:::meu-bucket-revisoes/*"]
  }]
}
```

(Se o bucket usa **SSE-KMS**, também `kms:Decrypt` na chave.) Sem isso, a implantação **trava** ao baixar o pacote.

### 1.3 On-premises

Servidores fora da AWS são **registrados** como **instâncias on-premises** (`aws deploy register-on-premises-instance`) com **IAM user** ou **IAM role via Systems Manager hybrid activation**, recebem o agent e passam a ser alvos por **tags**. Útil para **modelos híbridos**; há **custo por atualização** on-premises.

## 2. O arquivo `appspec.yml` (EC2/on-premises)

Fica na **raiz da revisão**. Estrutura:

```yaml
version: 0.0
os: linux                       # linux | windows
files:
  - source: /                   # origem dentro da revisão
    destination: /opt/app       # destino na instância
file_exists_behavior: OVERWRITE # DISALLOW (padrão) | OVERWRITE | RETAIN
permissions:
  - object: /opt/app
    pattern: "**"
    owner: appuser
    group: appgroup
    mode: 750
    type: [file]
hooks:
  ApplicationStop: [...]
  BeforeInstall:   [...]
  AfterInstall:    [...]
  ApplicationStart: [...]
  ValidateService: [...]
```

| Seção | Função |
|---|---|
| **version** | Sempre `0.0` |
| **os** | Sistema operacional alvo |
| **files** | Copia arquivos da revisão para a instância |
| **file_exists_behavior** | O que fazer se o arquivo já existir (**`OVERWRITE`** costuma ser necessário) |
| **permissions** | `owner`, `group`, `mode`, `acls`, `context` (SELinux) |
| **hooks** | Scripts por **evento do ciclo de vida** (com `location`, `timeout`, `runas`) |

> [!warning] Cuidado
> Com `file_exists_behavior` padrão (`DISALLOW`), a **segunda implantação falha** se os arquivos já existirem. Em in-place, defina `OVERWRITE` (ou limpe no hook).

## 3. Ciclo de vida (hooks) em implantação **in-place**

Sequência de eventos em cada instância:

```
ApplicationStop  → DownloadBundle → BeforeInstall → Install → AfterInstall → ApplicationStart → ValidateService
```

| Evento | Quem executa | Uso típico |
|---|---|---|
| **ApplicationStop** | **Seu script** (da revisão **anterior** instalada) | Parar o serviço com segurança (drenar conexões) |
| **DownloadBundle** | Agent (**não customizável**) | Baixa a revisão |
| **BeforeInstall** | Seu script | Backup, limpar diretórios, preparar usuários/pastas |
| **Install** | Agent (**não customizável**) | Copia arquivos conforme `files` |
| **AfterInstall** | Seu script | Instalar dependências, migrar config, `chmod`, compilar assets |
| **ApplicationStart** | Seu script | Iniciar/reiniciar o serviço |
| **ValidateService** | Seu script | **Smoke test**: verificar se a aplicação responde (`curl`) |

Com **load balancer**, entram eventos adicionais: **`BeforeBlockTraffic` → `BlockTraffic` → `AfterBlockTraffic`** (antes da parada: remove do balanceador e espera o **connection draining**) e **`BeforeAllowTraffic` → `AllowTraffic` → `AfterAllowTraffic`** (depois da validação: devolve ao balanceador).

> [!tip] Observação importante
> O hook **`ApplicationStop`** usa o script da **última revisão bem-sucedida** (já presente na instância). Se esse script estiver quebrado, **todas as implantações futuras falham**; trate com cuidado (e use `|| true` onde caber).

### 3.1 Scripts de hook (exemplo)

`scripts/parar.sh`:

```bash
#!/bin/bash
set -e
if systemctl is-active --quiet meu-app; then
  systemctl stop meu-app
fi
```

`scripts/validar.sh`:

```bash
#!/bin/bash
# Tenta por até 60s; falha se não responder 200
for i in $(seq 1 12); do
  code=$(curl -s -o /dev/null -w "%{http_code}" http://localhost:8080/saude || true)
  [ "$code" = "200" ] && exit 0
  sleep 5
done
echo "Aplicação não ficou saudável" >&2
exit 1
```

Regras dos scripts:

| Regra | Motivo |
|---|---|
| **Código de saída 0 = sucesso**; ≠ 0 = falha do hook (e da instância) | Contrato do CodeDeploy |
| **`timeout`** por hook (padrão 3600 s) | Evita travar a implantação |
| **Idempotência** | Podem ser reexecutados |
| **Executáveis** (`chmod +x`) e com **shebang** | Senão falham |
| **`runas`** | Executar como usuário específico (Linux) |
| **Sem entrada interativa** | Não há TTY |
| **Logs claros** em stdout/stderr | Aparecem nos `deployment-logs` |
| **Evitar dependência de rede lenta** | Reduz falhas intermitentes |

## 4. Configurações de implantação (EC2/on-premises)

| Config | Comportamento | Quando usar |
|---|---|---|
| **`CodeDeployDefault.OneAtATime`** | 1 instância por vez; falha se alguma falhar (exceto última) | Produção conservadora |
| **`CodeDeployDefault.HalfAtATime`** | Metade por vez | Equilíbrio |
| **`CodeDeployDefault.AllAtOnce`** | Todas ao mesmo tempo | Dev/teste |
| **Personalizada (MinimumHealthyHosts)** | Ex.: `type=HOST_COUNT,value=2` ou `FLEET_PERCENT,value=75` | Garantir capacidade mínima |
| **Zona de disponibilidade (zonal config)** | Implanta **uma AZ por vez**, com período de espera ("bake time") | Limitar o raio de impacto por AZ |

```bash
aws deploy create-deployment-config --deployment-config-name MinHealthy75 \
  --minimum-healthy-hosts type=FLEET_PERCENT,value=75
```

`MinimumHealthyHosts` define **quantas instâncias devem permanecer saudáveis**; o CodeDeploy **interrompe** se o limite estiver em risco.

## 5. Blue/green em EC2

Fluxo:

```
1) Provisiona o grupo VERDE (copia do ASG azul ou instâncias existentes)
2) Instala a revisão no VERDE (hooks: BeforeInstall → ... → ValidateService)
3) Registra o VERDE no load balancer (AllowTraffic)
4) Remove o AZUL do balanceador (BlockTraffic, com draining)
5) Encerra o AZUL (ou mantém por X minutos para rollback rápido)
```

| Opção | Detalhe |
|---|---|
| **Provisionamento do verde** | **Copiar o Auto Scaling group** (padrão) ou **instâncias manualmente** |
| **Roteamento de tráfego** | **Imediato** ou **após espera** (aprovação/tempo) |
| **Término do azul** | **Imediatamente** ou **após N minutos** (janela de rollback) |
| **Load balancer** | **Obrigatório** (Classic, ALB ou NLB target group) |

Vantagens: **zero downtime**, **teste do verde antes do tráfego**, **rollback rápido** (reatacha o azul). Custo: instâncias extras temporárias e **tempo** de provisionamento. Para aplicações **stateful**, planeje dados/sessões compartilhados (banco, cache externo).

## 6. Integração com Auto Scaling

O CodeDeploy se integra ao **Auto Scaling group (ASG)** por **lifecycle hook**:

| Cenário | Comportamento |
|---|---|
| **Instâncias novas** (scale-out) | O CodeDeploy implanta **a revisão mais recente bem-sucedida** automaticamente antes de a instância entrar em serviço |
| **Deployments concorrentes** | Cuidado com **race condition**: escalar durante um deploy pode instanciar versões diferentes; o CodeDeploy reimplanta a "última revisão" |
| **AMI imutável (golden)** | Alternativa: **pré-assar** a aplicação na AMI e usar **instance refresh** do ASG (sem agent) |
| **Termination hook** | Pode aguardar o término de scripts/drenagem |

Boas práticas: mantenha **AMI base** com agent e dependências estáveis, **versões fixas** e **revisão idempotente**; defina `file_exists_behavior`.

## 7. Integração com ELB

| Ponto | Detalhe |
|---|---|
| **In-place** | O CodeDeploy **desregistra** a instância do ELB (BlockTraffic), implanta e **registra** de volta (AllowTraffic) |
| **Connection draining / deregistration delay** | Respeite o tempo para concluir requisições em andamento |
| **Health checks** | A instância só volta ao serviço quando **saudável** |
| **Blue/green** | Alterna entre grupos de alvos/ASGs |

Ajuste o **deregistration delay** do target group ao tempo típico de requisição, e use **ValidateService** para confirmar que a aplicação responde **antes** do `AllowTraffic`.

## 8. Windows e outros detalhes

| Item | Observação |
|---|---|
| **`os: windows`** | Hooks em **PowerShell/bat**; permissões diferentes |
| **Pacote** | **zip/tar/tgz** com o `appspec.yml` na raiz |
| **GitHub como origem** | Possível, mas **S3** é o padrão (via CodePipeline) |
| **Tamanho** | Revisões grandes atrasam; separe dependências pesadas |
| **Variáveis de ambiente dos hooks** | `DEPLOYMENT_ID`, `APPLICATION_NAME`, `DEPLOYMENT_GROUP_NAME`, `LIFECYCLE_EVENT` |
| **Segredos** | Busque do **Secrets Manager/Parameter Store** na instância (role), **não** no pacote |

## 9. Exemplo completo (Node.js em EC2 com systemd)

```yaml
version: 0.0
os: linux
file_exists_behavior: OVERWRITE
files:
  - source: /
    destination: /opt/pedidos-api
hooks:
  ApplicationStop:
    - location: scripts/stop.sh
      timeout: 60
      runas: root
  BeforeInstall:
    - location: scripts/clean.sh
      timeout: 60
  AfterInstall:
    - location: scripts/deps.sh      # npm ci --omit=dev e permissões
      timeout: 300
  ApplicationStart:
    - location: scripts/start.sh     # systemctl restart pedidos-api
      timeout: 60
  ValidateService:
    - location: scripts/validate.sh  # curl /health
      timeout: 120
```

Pipeline: **CodeBuild** gera `pedidos-api.zip` (com `appspec.yml`, `scripts/` e a aplicação) → **S3** → **CodeDeploy** (OneAtATime, rollback automático em falha e alarme) → ALB.

## 10. Erros comuns

> [!bug] Erros comuns
> 1. **Agent parado/desatualizado** ou sem rede.
> 2. **`file_exists_behavior` padrão** causando falha na 2ª implantação.
> 3. **Scripts sem `chmod +x`/shebang** ou com CRLF (Windows).
> 4. **Hook `ApplicationStop` quebrado**, travando todos os deploys futuros.
> 5. **ValidateService fraco** (apenas "processo existe").
> 6. **`AllAtOnce` em produção** com ELB (todas fora ao mesmo tempo).
> 7. **Sem `MinimumHealthyHosts`**, derrubando a capacidade.
> 8. **Race entre Auto Scaling e deploy** (versões diferentes na frota).
> 9. **Segredos dentro do pacote.**
> 10. **Instance profile sem S3/KMS.**

## 11. Troubleshooting

| Sintoma | Causa provável | Ação |
|---|---|---|
| Hook falha com `Script at specified location: ... failed` | Script ausente/permissão/exit ≠ 0 | Ver `deployment-logs` (stdout/stderr do script) |
| `The CodeDeploy agent did not find an AppSpec file` | `appspec.yml` fora da raiz da revisão | Reempacotar com o arquivo na raiz |
| Instâncias "Skipped" | Instância saiu do LB/estado do ASG | Verificar tags, LB e estado |
| Travou em `Pending`/timeout | Agent não responde | Reiniciar o agent, checar a rede |
| `Access Denied` no S3 | Instance profile/KMS | Ajustar políticas |
| Deploy ok mas app indisponível | ValidateService não cobriu | Reforçar o health check |
| Rollback repetido | Falha persistente ou alarme sensível | Diagnosticar a causa antes de reimplantar |

## 12. Resumo rápido

- **Agent** + **instance profile** (S3/KMS) executam a implantação; mantenha o agent atualizado (SSM).
- **appspec.yml**: `files`, `permissions`, **`hooks`**; atenção a `file_exists_behavior`.
- **Ciclo (in-place)**: ApplicationStop → DownloadBundle → BeforeInstall → Install → AfterInstall → ApplicationStart → ValidateService (+ eventos de **block/allow traffic** com ELB).
- **Configurações**: OneAtATime, HalfAtATime, AllAtOnce, personalizadas (`MinimumHealthyHosts`), zonal.
- **Blue/green** dá zero downtime e rollback rápido, ao custo de infraestrutura duplicada; integre com **ASG** e **ELB**.

**Respostas:**

1. Baixar a revisão e executar os hooks/arquivos na instância, reportando o resultado ao serviço.
2. ApplicationStop.
3. Verificar (smoke test) se a aplicação está saudável antes de devolver o tráfego/concluir.
4. Permite sobrescrever arquivos existentes, evitando falha em implantações repetidas.
5. OneAtATime atualiza uma instância por vez (mais seguro e lento); AllAtOnce atualiza todas ao mesmo tempo (rápido, com risco de downtime).
6. Implanta automaticamente a última revisão bem-sucedida via lifecycle hook antes de entrarem em serviço.
7. Leitura do bucket S3 da revisão (e kms:Decrypt se houver SSE-KMS).
