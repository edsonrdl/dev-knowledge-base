### 6.1.1.1. Operação do CodeDeploy — logs do agent e dos hooks, estados e falhas comuns, métricas e eventos, quotas, custos e checklist de produção

> [!warning] Aviso
> Caminhos de log, mensagens de erro, quotas e comportamentos abaixo são **de memória e variam por SO/versão do agent**; **confirme na documentação "Troubleshooting CodeDeploy"**. Comandos são ilustrativos e **não foram executados**. Em incidentes de implantação, priorize **recuperar o serviço** (rollback) antes de diagnosticar a fundo.

## 1. O que operar

Operar o CodeDeploy significa responder, com dados:

1. **O deploy terminou?** Em que estado está, por instância/alvo?
2. **Por que falhou?** Qual hook, qual instância, qual mensagem?
3. **O serviço ficou saudável?** (métricas e alarmes)
4. **Com que frequência e rapidez entregamos?** (DORA)
5. **Quanto custa e o que pode quebrar?** (quotas, agent, versões)

```
Console/CLI (estado) ─▶ Eventos (SNS/EventBridge) ─▶ Logs do agent e dos hooks ─▶ Métricas/alarmes ─▶ Ação
```

## 2. Estados de implantação e de instância

### 2.1 Estados da implantação

| Estado | Significado |
|---|---|
| **Created / Queued** | Criada; aguardando (pode haver fila por deployment group: **um deploy por vez** por grupo) |
| **InProgress** | Em andamento |
| **Baking** | Aguardando (tempo de espera/aprovação em blue/green) |
| **Succeeded** | Concluída com sucesso |
| **Failed** | Falhou (ver `errorInformation`) |
| **Stopped** | Parada manualmente ou por alarme |
| **Ready** | Pronta para redirecionar o tráfego (blue/green com espera) |

### 2.2 Estados de instância/alvo

`Pending`, `InProgress`, `Succeeded`, `Failed`, `Skipped`, `Unknown`, `Ready`. **`Skipped`** costuma indicar que a instância **saiu do escopo** (removida do ASG/LB, ou implantação interrompida).

```bash
aws deploy get-deployment --deployment-id d-ABCDE1234 \
  --query 'deploymentInfo.[status,errorInformation.code,errorInformation.message,creator,deploymentStyle]'
aws deploy list-deployment-instances --deployment-id d-ABCDE1234 --instance-status-filter Failed
aws deploy get-deployment-instance --deployment-id d-ABCDE1234 --instance-id i-0abc123 \
  --query 'instanceSummary.lifecycleEvents[].[lifecycleEventName,status,diagnostics.errorCode,diagnostics.message]'
```

Cada instância mostra **cada evento do ciclo de vida** com status e **diagnóstico** (`ScriptFailed`, `ScriptMissing`, `ScriptNotExecutable`, `ScriptTimedOut`, `UnknownError`).

## 3. Logs

### 3.1 Linux

| Arquivo | Conteúdo |
|---|---|
| `/var/log/aws/codedeploy-agent/codedeploy-agent.log` | Log do **agent** (polling, download, erros de plataforma) |
| `/opt/codedeploy-agent/deployment-root/<deployment-group-id>/<deployment-id>/logs/scripts.log` | **Saída dos scripts de hook** (stdout/stderr) por implantação — **o mais útil** |
| `/opt/codedeploy-agent/deployment-root/deployment-logs/codedeploy-agent-deployments.log` | Resumo das implantações |
| `/opt/codedeploy-agent/deployment-root/<group>/<deployment>/deployment-archive/` | A **revisão extraída** (conteúdo exato que foi implantado) |

### 3.2 Windows

`C:\ProgramData\Amazon\CodeDeploy\log\codedeploy-agent-log.txt` e a pasta `deployment-root` equivalentes.

### 3.3 Centralizando logs

Envie os logs ao **CloudWatch Logs** com o **CloudWatch Agent** (configuração para os arquivos acima) e crie **filtros de métrica** (por exemplo, `ScriptFailed`). Vantagens: acesso sem SSH, **retenção**, **busca** (Logs Insights) e **correlação** com métricas da aplicação.

```json
{
  "logs": { "logs_collected": { "files": { "collect_list": [
    { "file_path": "/var/log/aws/codedeploy-agent/codedeploy-agent.log", "log_group_name": "/codedeploy/agent", "log_stream_name": "{instance_id}" },
    { "file_path": "/opt/codedeploy-agent/deployment-root/deployment-logs/codedeploy-agent-deployments.log", "log_group_name": "/codedeploy/deployments", "log_stream_name": "{instance_id}" }
  ]}}}
}
```

Para **Lambda/ECS**, os logs de interesse são os das **funções de hook** (CloudWatch Logs da função) e os **eventos do deployment** no console/CLI.

## 4. Falhas comuns e diagnóstico

| Código/Mensagem | Causa provável | Como resolver |
|---|---|---|
| **`ScriptFailed`** | Script retornou código ≠ 0 | Ler `scripts.log`; reproduzir manualmente; tratar erros |
| **`ScriptMissing`** | Caminho do hook errado no `appspec.yml` | Conferir `location` relativo à raiz da revisão |
| **`ScriptNotExecutable`** | Sem `chmod +x` ou shebang ausente/CRLF | Ajustar permissões e finais de linha (LF) |
| **`ScriptTimedOut`** | Excedeu `timeout` do hook | Aumentar o timeout ou otimizar |
| **`The CodeDeploy agent was not able to receive the lifecycle event`** | Agent parado/sem rede/role | Reiniciar o agent, checar rede e instance profile |
| **`HEALTH_CONSTRAINTS` / `The overall deployment failed because too many individual instances failed deployment, too few healthy instances are available, or some instances are experiencing communication problems`** | Falhas em instâncias ou **`MinimumHealthyHosts` violado** | Ver instâncias com falha; ajustar a configuração |
| **`NO_INSTANCES`** | Nenhuma instância correspondente (tags/ASG) ou todas desligadas | Revisar filtros e estado das instâncias |
| **`IAM_ROLE_MISSING / IAM_ROLE_PERMISSIONS`** | Service role ausente/insuficiente | Anexar política correta |
| **`REVISION_MISSING`/`AccessDenied` ao baixar** | S3/KMS/instance profile | Permissões de S3 e KMS |
| **`ALARM_ACTIVE`** | Alarme em ALARM antes/durante o deploy | Resolver a causa do alarme |
| **`APPLICATION_MISSING` / `DEPLOYMENT_GROUP_MISSING`** | Nome incorreto/removido | Conferir nomes |
| **`TIMEOUT`** | Implantação inteira excedeu o tempo | Aumentar timeouts, investigar lentidão |
| **`DEPLOYMENT_IN_PROGRESS`** | Já há implantação ativa no grupo | Aguardar/parar a anterior |
| **`The deployment failed because a specified file already exists at this location`** | `file_exists_behavior` padrão (DISALLOW) | Usar `OVERWRITE` ou limpar no `BeforeInstall` |
| **Lambda: `Hook ... did not report status`** | Função de hook sem `PutLifecycleEventHookExecutionStatus` | Corrigir a função |
| **ECS: `The ECS service cannot be updated due to an unexpected error`** | Task definition/LB/rede | Verificar task definition, target groups, subnets e SGs |

### 4.1 Roteiro de diagnóstico (EC2)

```
1) Console/CLI: qual hook falhou e em quais instâncias? (lifecycleEvents + diagnostics)
2) Na instância: scripts.log da implantação → saída do script (stdout/stderr)
3) agent.log → problemas de download, permissão, rede
4) deployment-archive → a revisão contém o esperado (appspec na raiz, scripts, permissões)?
5) Reproduzir o hook manualmente (mesmo usuário/ambiente) → corrigir
6) Revisar instance profile, S3/KMS, DNS/rede
7) Corrigir na revisão (novo build) e reimplantar; se produção afetada: rollback primeiro
```

## 5. Métricas, eventos e notificações

### 5.1 Eventos (EventBridge)

| Evento | Uso |
|---|---|
| **CodeDeploy Deployment State-change Notification** | Início, sucesso, falha, parada, ready |
| **CodeDeploy Instance State-change Notification** | Estado por instância |

```json
{ "source": ["aws.codedeploy"],
  "detail-type": ["CodeDeploy Deployment State-change Notification"],
  "detail": { "state": ["FAILURE", "STOP"], "application": ["app-web"] } }
```

Alvos: **SNS/Chatbot**, **Lambda** (abrir ticket, anotar no dashboard), **Step Functions**.

### 5.2 Métricas

O CodeDeploy **não publica métricas ricas próprias**; você deriva indicadores de **eventos** e de **recursos associados**:

| Indicador | Fonte |
|---|---|
| **Frequência de implantação** | Eventos `SUCCESS` por período |
| **Lead time (commit → produção)** | CodePipeline + timestamps |
| **Taxa de falha de mudança** | Falhas/rollbacks ÷ implantações |
| **MTTR** | Tempo entre falha/alarme e recuperação |
| **Saúde pós-deploy** | CloudWatch (5xx, latência, UnHealthyHostCount) |
| **Duração do deploy** | Início → fim (evento) |
| **Taxa de rollback** | Rollbacks ÷ implantações |

Mantenha um **dashboard DORA** (CloudWatch/QuickSight) alimentado por eventos.

## 6. Quotas e limites (visão geral)

| Quota (típica; confirmar) | Observação |
|---|---|
| **Aplicações por conta/região** | Centenas |
| **Deployment groups por aplicação** | Dezenas |
| **Implantações simultâneas por conta** | Limite (ajustável); **uma por deployment group** por vez |
| **Instâncias por implantação** | Milhares |
| **Tamanho do AppSpec/ da revisão** | Limites de arquivo; revisões grandes atrasam |
| **Taxa de API** | Throttling em `CreateDeployment`/`GetDeployment` |
| **Hooks por evento** | Limite de scripts/tempo |
| **Tempo máximo de uma implantação** | Há limite global (por exemplo, 24 h; confirmar) |

Planeje **filas e janelas**; para frotas muito grandes, use **configurações com porcentagem** e **zonal**.

## 7. Custos

| Item | Detalhe |
|---|---|
| **CodeDeploy (EC2/Lambda/ECS)** | **Sem cobrança** pelo serviço |
| **On-premises** | Pequeno valor por **atualização de instância** |
| **Infraestrutura extra** | **Blue/green**: instâncias/tasks duplicadas durante a janela (mais a espera antes de encerrar o azul) |
| **S3/KMS** | Armazenamento de revisões e requisições |
| **Lambda de hooks** | Custos mínimos |
| **CloudWatch** | Logs/alarmes/dashboards |
| **Tempo de engenharia** | O verdadeiro custo: manutenção de scripts, agent e pipelines |

Otimização: **encerrar o azul** após uma janela razoável; **lifecycle no S3** para revisões antigas (manter N últimas); **não manter alarmes ociosos**.

## 8. Manutenção do agent e da frota

| Tarefa | Prática |
|---|---|
| **Versão do agent** | Manter **atualizado** (SSM State Manager com associação periódica) |
| **Instalação automática** | AMI com agent, **user data**, ou **SSM Distributor** |
| **Verificação de saúde** | Alarme/inventário: instâncias com agent parado (SSM Inventory/CloudWatch) |
| **Rotação de logs** | Evitar disco cheio em `deployment-root` (o agent mantém N implantações; ajuste `:max_revisions:`) |
| **Reiniciar o agent** | `sudo systemctl restart codedeploy-agent` |
| **Imagens (AMI)** | Pipeline de AMIs com agent e dependências; reduzir o tempo de implantação |
| **Compatibilidade de SO** | Versões suportadas de Ruby/SO |

## 9. Higiene operacional

- **Uma implantação por vez** por grupo: use **janelas** e evite colisões (por exemplo, pipeline e operador).
- **Limpe revisões antigas** (S3 Lifecycle) mantendo as necessárias para rollback.
- **Remova** aplicações/grupos obsoletos (via IaC).
- **Documente** hooks e dependências (README no repositório).
- **Teste a implantação** em homologação com a **mesma topologia** da produção.
- **Runbooks**: agent parado, hook falhando, rollback falhando, S3/KMS negado, alarme preso em ALARM.
- **Revisões regulares**: tempo de deploy, taxa de falhas, instâncias com agent desatualizado.

## 10. Checklist de produção

**Confiabilidade**
1. **Rollback automático** (falha e alarme) habilitado e **testado**.
2. **ValidateService/hooks** significativos; **health checks** profundos o bastante.
3. **MinimumHealthyHosts** e configuração adequada (OneAtATime/zonal) em produção.
4. Estratégia **blue/green/canary** para serviços críticos; compatibilidade de dados (**expand/contract**).

**Operação**
5. **Agent** instalado, atualizado e monitorado (SSM).
6. **Logs** no CloudWatch com retenção; filtros de métrica para falhas.
7. **Eventos** (EventBridge/SNS/Chatbot) e **dashboard DORA**.
8. **Runbooks** e ensaios de rollback.

**Segurança e governança**
9. **Implantação só via pipeline**; `CreateDeployment` restrito; aprovação para PROD.
10. **Menor privilégio** (service role, instance profile, pipeline); **bucket e KMS** protegidos.
11. **IaC** com PR; auditoria CloudTrail/Config.

**Custo**
12. Janela de **encerramento do azul** definida; **lifecycle** de revisões.

## 11. Erros comuns

> [!bug] Erros comuns
> 1. **Diagnosticar sem olhar `scripts.log`** (a causa quase sempre está lá).
> 2. **Agent desatualizado/parado** e ninguém percebe.
> 3. **Logs só na instância** (perdidos quando ela é substituída).
> 4. **Sem notificações** de falha de implantação.
> 5. **Deploys simultâneos no mesmo grupo** gerando `DEPLOYMENT_IN_PROGRESS`.
> 6. **Disco cheio** por revisões acumuladas.
> 7. **Revisões antigas apagadas** do S3 (rollback impossível).
> 8. **Hooks não idempotentes**, falhando na reexecução.
> 9. **Não medir DORA** e não saber se está melhorando.
> 10. **Corrigir a instância "no braço"** e esquecer de corrigir a revisão (drift).

## 12. Troubleshooting operacional

| Sintoma | Causa provável | Ação |
|---|---|---|
| Implantação presa em `Pending` | Agent offline/sem rede | Verificar o serviço, endpoints, instance profile |
| Muitos `Skipped` | Instâncias saíram do LB/ASG durante o deploy | Revisar escala e estado das instâncias |
| Falha só em algumas instâncias | Diferenças entre instâncias (AMI, disco, permissão) | Comparar `scripts.log` e o estado do SO |
| Rollback também falhou | Revisão anterior inválida/ausente | Restaurar do S3 (versionamento) e reimplantar manualmente |
| Disco cheio na instância | `deployment-root` | Reduzir `max_revisions`, limpar |
| Deploy lento | Revisão grande, dependências baixadas no hook | Pré-assar na AMI, cache, reduzir o pacote |
| Eventos não chegam | Regra/SNS/Chatbot mal configurados | Revisar o padrão do evento e a política do tópico |

## 13. Resumo rápido

- **Estados** por implantação e por instância; **diagnóstico** por evento do ciclo de vida (`ScriptFailed`, `ScriptTimedOut`...).
- **Logs**: `scripts.log` (hooks), `codedeploy-agent.log`; centralize no **CloudWatch Logs**.
- **Falhas típicas**: hooks (permissão/caminho/timeout), agent/rede, S3/KMS, `MinimumHealthyHosts`, `file_exists_behavior`, hooks Lambda sem status.
- **Eventos/EventBridge + dashboard DORA**; quotas por conta e **uma implantação por grupo**.
- **Custo**: serviço gratuito (EC2/Lambda/ECS); atenção à infraestrutura **blue/green**.
- Mantenha **agent atualizado**, **rollback testado**, **IaC** e **runbooks**.

### 🧩 Quiz de Fixação

1. Onde ver a saída dos scripts de hook em Linux?
2. Que erro indica script sem permissão de execução?
3. Por que `file_exists_behavior` pode causar falha?
4. Quantas implantações simultâneas um deployment group permite?
5. Como centralizar logs das instâncias?
6. Que indicadores DORA derivar das implantações?
7. Qual o custo do CodeDeploy em EC2/Lambda/ECS?

**Respostas:**

1. Em `/opt/codedeploy-agent/deployment-root/<grupo>/<deployment>/logs/scripts.log`.
2. `ScriptNotExecutable`.
3. No padrão (DISALLOW) a implantação falha se o arquivo de destino já existe; use OVERWRITE ou limpe antes.
4. Uma por vez por deployment group.
5. Com o CloudWatch Agent enviando os logs do agent e das implantações ao CloudWatch Logs.
6. Frequência de implantação, lead time, taxa de falha de mudança e MTTR (além de taxa de rollback e duração).
7. Sem cobrança pelo serviço; pagam-se os recursos usados (e há um valor pequeno por atualização on-premises).
