### 5.1.1.1. Integração e segurança do CodeDeploy — CodePipeline, service role e instance profile, S3 e KMS, deploy multi-conta, rede privada, SAM e CloudFormation e boas práticas

> [!warning] Aviso
> Políticas IAM, nomes de ações e comandos abaixo são **ilustrativos, de memória e não foram executados**. **Teste no IAM Policy Simulator e em homologação.** O CodeDeploy tem **poder de alterar produção**: quem controla o deployment group, a revisão e os hooks controla **o que executa nos servidores**. Confirme na documentação as políticas gerenciadas atuais (por exemplo, `AWSCodeDeployRole`).

## 1. O CodeDeploy no fluxo de entrega

O CodeDeploy é a **última milha** do CI/CD: recebe uma **revisão pronta** e a coloca no ar. Ele raramente vive sozinho:

```
Código ─▶ CodeBuild (CI) ─▶ Artefato (S3) ─▶ CodePipeline ─▶ [Aprovação] ─▶ CodeDeploy ─▶ EC2 / Lambda / ECS
                                                                             │
                                          Alarmes/CloudWatch · SNS · EventBridge · Config · CloudTrail
```

## 2. Integração com o CodePipeline

O **CodePipeline** orquestra as etapas; o **CodeDeploy** executa a ação de **Deploy**.

| Plataforma | Ação do CodePipeline | Artefatos de entrada |
|---|---|---|
| **EC2/on-premises** | **`CodeDeploy`** | Pacote (zip) com **appspec.yml** + código |
| **Lambda** | **`CodeDeploy`** (via SAM/CloudFormation) ou ação de **CloudFormation** com SAM | Template SAM/CFN (o SAM cria o CodeDeploy) |
| **ECS (blue/green)** | **`CodeDeployToECS`** | **`taskdef.json`** + **`appspec.yaml`** (+ imagem no ECR) |

Aspectos práticos:

| Ponto | Detalhe |
|---|---|
| **Artefato** | Fluxo gerenciado pelo pipeline em **bucket S3 de artefatos** (com **KMS**) |
| **Variáveis** | Variáveis exportadas do CodeBuild alimentam a ação de deploy |
| **Aprovação manual** | Entre estágios (por exemplo, `Staging → Approval → Production`) |
| **Falha** | Falha do CodeDeploy marca o estágio como **Failed**; o rollback do CodeDeploy atua dentro do deploy |
| **Reexecução/Transições** | Controle de promoção e retry |
| **Multi-região** | Ações por região, com **buckets de artefatos regionais** |

Exemplo de ação (CloudFormation, ilustrativo):

```yaml
- Name: Deploy-Producao
  Actions:
    - Name: DeployEC2
      ActionTypeId: { Category: Deploy, Owner: AWS, Provider: CodeDeploy, Version: "1" }
      Configuration: { ApplicationName: app-web, DeploymentGroupName: prod }
      InputArtifacts: [{ Name: BuildOutput }]
      RoleArn: !GetAtt PipelineDeployRole.Arn
```

## 3. Roles e permissões

O CodeDeploy usa **quatro "identidades"** distintas:

| Identidade | Quem usa | Para quê |
|---|---|---|
| **Service role do CodeDeploy** | O **serviço** CodeDeploy | Descrever instâncias/ASG, mexer no ELB, ler tags, chamar Lambda/ECS, publicar em SNS, ler alarmes |
| **Instance profile (EC2)** | O **agent** nas instâncias | Baixar a revisão no S3 (e usar KMS) |
| **Role do CodePipeline** | O pipeline | `codedeploy:CreateDeployment`, `GetDeployment`, `GetApplicationRevision`, `RegisterApplicationRevision` |
| **Roles de hooks (Lambda)** | Funções de validação | `codedeploy:PutLifecycleEventHookExecutionStatus` e acesso ao necessário para testar |

### 3.1 Service role (trust e permissões)

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": { "Service": "codedeploy.amazonaws.com" },
    "Action": "sts:AssumeRole"
  }]
}
```

Permissões: use a política gerenciada **`AWSCodeDeployRole`** (EC2/on-premises), **`AWSCodeDeployRoleForLambda`** e **`AWSCodeDeployRoleForECS`** como base e **restrinja recursos** quando possível. Se usar **tags para Auto Scaling**/KMS, acrescente o necessário.

### 3.2 Instance profile mínimo

```json
{
  "Version": "2012-10-17",
  "Statement": [
    { "Effect": "Allow", "Action": ["s3:GetObject", "s3:GetObjectVersion"],
      "Resource": "arn:aws:s3:::meu-bucket-revisoes/app-web/*" },
    { "Effect": "Allow", "Action": "s3:ListBucket", "Resource": "arn:aws:s3:::meu-bucket-revisoes" },
    { "Effect": "Allow", "Action": "kms:Decrypt", "Resource": "arn:aws:kms:us-east-1:123456789012:key/abcd-..." }
  ]
}
```

Acrescente apenas o que a **aplicação** precisa (Secrets Manager/Parameter Store), **separando** a role de **execução da aplicação** das permissões de **implantação**, quando possível (usando instance profile único, mantenha o mínimo).

### 3.3 Quem pode implantar (humanos)

| Permissão | Quem |
|---|---|
| `codedeploy:CreateDeployment` | **Pipeline** e um grupo restrito de operadores |
| `codedeploy:StopDeployment` | Operadores de plantão |
| `codedeploy:UpdateDeploymentGroup`, `DeleteDeploymentGroup` | **Administração de plataforma** (via IaC) |
| `codedeploy:RegisterApplicationRevision` | Pipeline |
| `iam:PassRole` para a service role | Apenas administradores/pipeline |

> [!warning] Equivalência de poder
> Quem pode **`CreateDeployment`** com uma **revisão própria** em um deployment group **executa scripts como root nas instâncias**. Trate essa permissão como **acesso administrativo aos servidores**. Controle o **bucket de revisões** (apenas o pipeline escreve) e **aprovações** para produção.

## 4. Integridade e confidencialidade das revisões

| Controle | Detalhe |
|---|---|
| **Bucket de revisões** | **Block Public Access**, **versionamento**, **SSE-KMS**, política que permite **escrita só ao pipeline/CodeBuild** e leitura aos instance profiles |
| **Imutabilidade** | **Object Lock**/versionamento para trilha de auditoria |
| **Assinatura/verificação** | Gerar **checksum/assinatura** da revisão no CodeBuild e **verificar** no hook `BeforeInstall` |
| **Origem confiável** | Só artefatos produzidos por **builds do pipeline**; sem upload manual |
| **Segredos** | **Nunca** dentro do pacote; buscar no **Secrets Manager/Parameter Store** em runtime |
| **Revisão de hooks/scripts** | Código de hooks passa por **PR e revisão** (é código executado como root) |
| **Dependências** | Instalação a partir de **CodeArtifact**/repositórios aprovados |

## 5. Rede privada

| Cenário | Solução |
|---|---|
| **Instâncias sem internet** | **VPC endpoints**: `codedeploy`, `codedeploy-commands-secure`, `s3` (gateway), `ec2messages/ssm` (se usar SSM), `logs`, `sts` |
| **Agent → serviço** | HTTPS de saída (porta 443) para os endpoints do CodeDeploy; com endpoints privados, tráfego **não sai pela internet** |
| **Security groups** | Saída restrita ao necessário; sem entrada para o agent (ele **puxa** comandos) |
| **On-premises** | Conectividade via **Direct Connect/VPN** e endpoints, ou saída controlada por proxy |
| **Proxy** | O agent suporta **proxy** (configuração no `codedeployagent.yml`) |

O agent **não abre portas de entrada**: o modelo de **polling** reduz a superfície de ataque (diferente de ferramentas que exigem SSH/WinRM abertos).

## 6. Deploy multi-conta

Padrão comum: **conta de ferramentas (tooling)** com pipeline/CodeBuild/artefatos, e **contas de aplicação** (dev, hml, prod).

```
Conta TOOLING                            Conta PROD
 CodePipeline ──assume role──▶  Role "PipelineDeploy" (permite codedeploy:* no app de PROD)
 S3 artefatos (KMS CMK) ◀─── acesso cross-account (bucket policy + key policy)
 CodeBuild
                                         CodeDeploy (application/deployment group em PROD)
                                         Instâncias com instance profile lendo o S3 de TOOLING
```

Requisitos:

| Item | Detalhe |
|---|---|
| **Role cross-account** | Em PROD, role confiando na conta de TOOLING; pipeline a assume na ação |
| **Bucket de artefatos** | **Bucket policy** permitindo leitura às roles/contas de PROD |
| **Chave KMS (CMK)** | **Key policy** permitindo uso pelas contas de PROD (a chave **gerenciada pela AWS** não permite cross-account) |
| **Separação de ambientes** | **Contas distintas** com SCPs e acessos humanos restritos em PROD |
| **Aprovação** | Estágio manual antes de PROD |

## 7. SAM e CloudFormation

| Ferramenta | Como se relaciona |
|---|---|
| **SAM** | `DeploymentPreference` cria **application, deployment group, alias e roles** do CodeDeploy para Lambda automaticamente |
| **CloudFormation (ECS blue/green)** | Transform **`AWS::CodeDeployBlueGreen`**: o CloudFormation conduz o blue/green do ECS **usando o CodeDeploy** (por meio de hooks) |
| **CloudFormation (EC2)** | Recursos `AWS::CodeDeploy::Application`/`DeploymentGroup`/`DeploymentConfig` para **declarar** a infraestrutura de deploy |
| **Terraform/CDK** | Equivalentes (`aws_codedeploy_*`, constructs L2) |

Boas práticas: **tudo como código** (IaC) — aplicação, grupos, configurações, alarmes, roles —, com **revisão por PR** e **detecção de drift**, evitando edição manual no console.

```yaml
# CloudFormation: deployment group para EC2 com rollback e alarmes (ilustrativo)
GrupoProd:
  Type: AWS::CodeDeploy::DeploymentGroup
  Properties:
    ApplicationName: !Ref App
    ServiceRoleArn: !GetAtt CodeDeployRole.Arn
    DeploymentConfigName: CodeDeployDefault.OneAtATime
    AutoScalingGroups: [!Ref Asg]
    LoadBalancerInfo:
      TargetGroupInfoList: [{ Name: !GetAtt TargetGroup.TargetGroupName }]
    AutoRollbackConfiguration:
      Enabled: true
      Events: [DEPLOYMENT_FAILURE, DEPLOYMENT_STOP_ON_ALARM]
    AlarmConfiguration:
      Enabled: true
      Alarms: [{ Name: !Ref Alarme5xx }]
```

## 8. Notificações e auditoria

| Mecanismo | Uso |
|---|---|
| **Triggers do deployment group (SNS)** | Eventos de implantação/instância (início, sucesso, falha, rollback) |
| **Regras de notificação (Chatbot)** | Slack/Teams |
| **EventBridge** | Estados de implantação (`CodeDeploy Deployment State-change Notification`, `CodeDeploy Instance State-change Notification`) → automações |
| **CloudTrail** | `CreateDeployment`, `StopDeployment`, `UpdateDeploymentGroup`, `RegisterOnPremisesInstance`, etc. |
| **AWS Config** | Regras (deployment group com rollback habilitado? alarmes configurados?) |
| **Logs das instâncias** | `deployment-logs` enviados ao **CloudWatch Logs** (agent do CloudWatch) |

Alertas prioritários: **`UpdateDeploymentGroup` fora do IaC**, **implantações fora do pipeline**, **implantação em produção fora de janela**, **falhas/rollbacks recorrentes**, **registro de instâncias on-premises**.

## 9. Boas práticas de governança

1. **Implantação só via pipeline** em produção; **humanos sem `CreateDeployment`** direto.
2. **Contas separadas** por ambiente; **aprovação manual** antes de PROD.
3. **IaC** para tudo; **PR obrigatório** para hooks/`appspec`.
4. **Menor privilégio** em service role, instance profile e role do pipeline.
5. **Bucket de revisões** fechado e criptografado; **KMS CMK** para cross-account.
6. **Rollback automático + alarmes** habilitados e **testados**.
7. **Rede privada** (endpoints) e **agent atualizado** (SSM).
8. **Sem segredos no pacote**; buscar em runtime.
9. **Observabilidade**: notificações, EventBridge, CloudTrail e dashboards de DORA (frequência, lead time, taxa de falha, MTTR).
10. **Ensaios**: rollback e recuperação regulares.

## 10. Erros comuns

> [!bug] Erros comuns
> 1. **Dar `CreateDeployment` amplo** a desenvolvedores (execução de código como root em produção).
> 2. **Instance profile com `s3:*`/`AdministratorAccess`.**
> 3. **Bucket de revisões público ou com escrita aberta.**
> 4. **Segredos dentro do pacote da revisão.**
> 5. **KMS gerenciada pela AWS em cenário cross-account** (não funciona).
> 6. **Sem VPC endpoints** em sub-redes privadas (agent não alcança o serviço).
> 7. **Deployment groups editados no console** (drift).
> 8. **Mesma conta para dev e prod** sem isolamento.
> 9. **Falta de aprovação** antes de produção.
> 10. **Não monitorar** eventos de implantação.

## 11. Troubleshooting

| Sintoma | Causa provável | Ação |
|---|---|---|
| `AccessDenied` na ação do pipeline | Role do pipeline sem `codedeploy:*` necessário | Ajustar a role |
| Instâncias não baixam a revisão cross-account | Bucket policy/KMS sem a conta de destino | Permitir a conta/role na policy e na key policy |
| Agent sem conectividade | Sem NAT/endpoints | Criar endpoints/NAT; verificar SG/DNS |
| `The service role does not have permissions` | Service role incompleta | Anexar a política gerenciada correta |
| Pipeline não inicia o deploy | Nome do app/grupo errado ou role do pipeline | Conferir configuração e permissões |
| SAM não cria o deployment group | `AutoPublishAlias`/`DeploymentPreference` ausentes | Definir ambos |
| Hook Lambda sem permissão | Role sem `PutLifecycleEventHookExecutionStatus` | Ajustar a role |

## 12. Resumo rápido

- **CodePipeline** orquestra; ações **`CodeDeploy`** (EC2/Lambda via SAM) e **`CodeDeployToECS`** (taskdef + appspec).
- **Quatro identidades**: service role, instance profile, role do pipeline e roles dos hooks — todas com **menor privilégio**.
- **`CreateDeployment` ≈ root nos servidores**: restrinja; **bucket de revisões** fechado e criptografado (**KMS CMK** em cross-account).
- **Rede privada** por endpoints; **multi-conta** com roles cross-account; **IaC (SAM/CFN)** e PRs.
- **Notificações, EventBridge, CloudTrail e Config** para governança.

### 🧩 Quiz de Fixação

1. Quais as quatro identidades envolvidas no CodeDeploy?
2. Por que `CreateDeployment` é uma permissão sensível?
3. Que ação do CodePipeline é usada para ECS blue/green?
4. O que é necessário para deploy multi-conta com artefatos criptografados?
5. Como o agent se comunica com o serviço e o que isso implica na rede?
6. Como o SAM se relaciona com o CodeDeploy?
7. Que eventos auditar com prioridade?

**Respostas:**

1. Service role do CodeDeploy, instance profile das instâncias, role do CodePipeline e roles das funções de hook.
2. Quem cria um deployment com revisão própria executa scripts como root nas instâncias; equivale a acesso administrativo.
3. `CodeDeployToECS`, com `taskdef.json` e `appspec.yaml`.
4. Role cross-account assumida pelo pipeline, bucket policy permitindo a conta de destino e uma chave KMS gerenciada pelo cliente com key policy que permita o uso pelas outras contas.
5. Por polling HTTPS de saída (443), sem portas de entrada; em redes privadas exige VPC endpoints.
6. `DeploymentPreference` com `AutoPublishAlias` cria application, deployment group, alias e roles automaticamente para Lambda.
7. UpdateDeploymentGroup fora do IaC, implantações fora do pipeline/janela, falhas e rollbacks recorrentes e registro de instâncias on-premises.
