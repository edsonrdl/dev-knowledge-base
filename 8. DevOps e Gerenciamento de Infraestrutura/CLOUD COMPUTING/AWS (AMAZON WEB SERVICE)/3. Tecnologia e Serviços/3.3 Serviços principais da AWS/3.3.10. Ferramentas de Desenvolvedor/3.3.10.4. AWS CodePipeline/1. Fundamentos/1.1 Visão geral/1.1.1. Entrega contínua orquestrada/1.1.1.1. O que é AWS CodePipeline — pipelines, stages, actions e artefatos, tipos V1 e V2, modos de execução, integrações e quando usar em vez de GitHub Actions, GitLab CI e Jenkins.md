### 1.1.1.1. O que é AWS CodePipeline — pipelines, stages, actions e artefatos, tipos V1 e V2, modos de execução, integrações e quando usar em vez de GitHub Actions, GitLab CI e Jenkins

> [!warning] Aviso
> Os comandos, JSONs, limites, tipos de pipeline (V1/V2) e preços abaixo são **ilustrativos, de memória e não foram executados**. O CodePipeline mudou bastante com o **tipo V2** (gatilhos, variáveis, modos de execução, condições, rollback, ação Commands). **Confirme os recursos e a cobrança na documentação e na página de preços** antes de projetar ou orçar. Valores em dólar são ordens de grandeza.

## 1. O problema que o CodePipeline resolve

Entregar software envolve **várias etapas encadeadas**: obter o código, compilar, testar, escanear segurança, empacotar, implantar em homologação, validar, pedir **aprovação**, implantar em produção. Cada etapa usa uma ferramenta (CodeBuild, CodeDeploy, CloudFormation, ECS, Lambda...). Sem um **orquestrador**, o encadeamento vira scripts frágeis, sem visibilidade ("onde está a versão 42? Quem aprovou? Por que parou?").

O **AWS CodePipeline** é o serviço gerenciado de **entrega contínua (CD)** que **modela esse fluxo como um pipeline**: uma sequência de **estágios**, cada um com **ações**, passando **artefatos** de uma etapa a outra, com **visualização**, **aprovações**, **reexecução** e **integração nativa** com serviços AWS e de terceiros.

```
 [Source] ──▶ [Build] ──▶ [Test] ──▶ [Deploy HML] ──▶ [Aprovação manual] ──▶ [Deploy PROD]
  commit      CodeBuild   CodeBuild    CodeDeploy/ECS         pessoa           CodeDeploy/ECS
   ▲                                                                              │
   └────────────── artefatos (S3) passam entre as etapas ◀────────────────────────┘
```

O CodePipeline **não compila nem implanta por si só**: ele **coordena** outras ferramentas e controla **quando e em que ordem** cada ação ocorre.

## 2. Conceitos centrais

| Conceito | Significado |
|---|---|
| **Pipeline** | O fluxo completo, com nome, role e armazenamento de artefatos |
| **Stage (estágio)** | Fase lógica (Source, Build, Deploy-HML, Aprovação, Deploy-PROD); estágios executam **em sequência** |
| **Action (ação)** | Tarefa dentro de um estágio (compilar, implantar, aprovar); ações podem rodar **em sequência ou em paralelo** (`runOrder`) |
| **Action provider** | Quem executa a ação (CodeBuild, CodeDeploy, CloudFormation, Lambda, Manual approval...) |
| **Artifact (artefato)** | Arquivos que **entram e saem** das ações (zip no S3) |
| **Artifact store** | **Bucket S3** (um por região) com os artefatos do pipeline, criptografável com **KMS** |
| **Transition** | Ligação entre estágios; pode ser **desabilitada** para pausar a promoção |
| **Execution** | Uma **execução** do pipeline, com ID, gatilho e revisão de origem |
| **Revision** | O **commit/versão** de origem que a execução está processando |
| **Variables / namespaces** | Valores gerados por ações e consumidos por outras (`#{SourceVars.CommitId}`) |
| **Trigger** | O que inicia o pipeline (push, tag, PR, agenda, manual) |
| **Service role** | Role IAM que o pipeline assume para chamar serviços |
| **Pipeline type** | **V1** (clássico) ou **V2** (recursos avançados e cobrança por minuto de ação) |

## 3. Categorias de ação

| Categoria | Função | Provedores típicos |
|---|---|---|
| **Source** | Obter o código/artefato | CodeCommit, S3, ECR, GitHub/GitLab/Bitbucket (**CodeConnections**), Amazon ECR |
| **Build** | Compilar/empacotar | **CodeBuild**, Jenkins, CloudBees, TeamCity |
| **Test** | Testar | CodeBuild, Device Farm, BlazeMeter, Ghost Inspector |
| **Deploy** | Implantar | **CodeDeploy**, CloudFormation, ECS, ECS blue/green, Elastic Beanstalk, S3, AppConfig, Service Catalog, Lambda (SAM), Step Functions |
| **Approval** | **Aprovação manual** (e-mail/SNS, comentário, URL de revisão) | Manual approval |
| **Invoke** | Chamar lógica customizada | **Lambda**, Step Functions |
| **Compute (V2)** | Comandos diretos | **Commands** (executa shell sem CodeBuild, conforme disponibilidade) |

## 4. Como uma execução funciona

```
1) Gatilho (push/tag/manual/agenda) cria uma EXECUÇÃO com a revisão de origem
2) Estágio Source: obtém o código → publica o artefato "SourceOutput" no S3
3) Estágio Build: CodeBuild recebe SourceOutput → gera "BuildOutput"
4) Estágio Deploy: CodeDeploy recebe BuildOutput → implanta
5) Cada estágio só começa quando o anterior termina com sucesso (ou conforme as condições)
6) Falha → a execução para; você pode REEXECUTAR a ação/estágio com falha
```

### 4.1 Artefatos

Cada ação declara **artefatos de entrada** e **de saída**. O CodePipeline **copia** os arquivos entre ações usando o **artifact store (S3)**. Pontos importantes:

- **Nomes** únicos dentro do pipeline (`SourceOutput`, `BuildOutput`).
- Em ações em **outra região**, há **um bucket por região**.
- O artefato é um **zip** (ou pasta, conforme a ação).
- **KMS**: padrão com chave gerenciada; para **cross-account**, use **CMK** com key policy adequada.
- Ações podem ter **vários artefatos de entrada** (por exemplo, código + template de infraestrutura).

## 5. Tipos de pipeline: V1 e V2

| Característica | **V1** | **V2** |
|---|---|---|
| **Gatilhos** | Mudança de origem simples | **Filtros** por **branch**, **tag** e **caminho de arquivo**; eventos de **PR** |
| **Variáveis do pipeline** | Não | **Sim** (variáveis em nível de pipeline, passadas na execução) |
| **Modos de execução** | **Superseded** (só) | **Superseded, Queued, Parallel** |
| **Condições de estágio** | Não | **Sim** (condições de entrada, sucesso e falha; **rollback** automático do estágio) |
| **Ação Commands** | Não | **Sim** (executa comandos shell direto) |
| **Rollback** | Manual | **Rollback de estágio** para a execução anterior bem-sucedida |
| **Cobrança** | ~**US$ 1/mês por pipeline ativo** (primeiro grátis) | **Por minuto de execução de ação** (~US$ 0,002/min; franquia grátis mensal) |
| **Quando usar** | Pipelines simples e estáveis | **Padrão para novos pipelines** que precisam dos recursos |

Detalhes do V2 estão em uma folha própria.

## 6. Modos de execução (V2)

| Modo | Comportamento | Uso |
|---|---|---|
| **Superseded** | Uma nova execução **substitui** a anterior que ainda não chegou ao estágio atual | Pipelines de **entrega contínua** (só importa o mais recente) |
| **Queued** | Execuções **na fila**, processadas em ordem, **uma por vez** | Quando **cada commit** precisa ser implantado em sequência |
| **Parallel** | Execuções **simultâneas** independentes | Branches de feature / PRs em paralelo |

## 7. Quando usar CodePipeline vs alternativas

| Critério | **CodePipeline** | **GitHub Actions** | **GitLab CI/CD** | **Jenkins** |
|---|---|---|---|---|
| **Modelo** | Orquestrador visual de estágios/ações | Workflows YAML no repositório | `.gitlab-ci.yml` no repositório | Jenkinsfile; servidor próprio |
| **Operação** | **Gerenciado**, sem servidor | Gerenciado (runners) | Gerenciado ou self-managed | Você opera |
| **Integração AWS** | **Nativa** (IAM, S3, KMS, VPC, multi-conta) | OIDC + actions oficiais | OIDC + integrações | Plugins |
| **Pipeline como código** | CloudFormation/CDK/Terraform (JSON/YAML da API) | **No repositório**, junto ao código | **No repositório** | Jenkinsfile |
| **Flexibilidade** | Média (ações predefinidas) | **Alta** (marketplace) | **Alta** | **Muito alta** |
| **Aprovações** | **Nativas** | Environments/approvals | Environments/approvals | Plugins |
| **Multi-conta/região** | **Nativo** | Via roles/OIDC | Via roles/OIDC | Manual |
| **Ecossistema** | Menor | **Maior** | Grande | Enorme (legado) |
| **Custo** | Por pipeline/minuto | Por minuto/plano | Por minuto/plano | Infra + operação |

Heurística:

- **CodePipeline** é forte em **ambientes AWS-first**, **multi-conta/região**, **governança e auditoria** (IAM, CloudTrail) e **pipelines de infraestrutura**.
- **GitHub Actions/GitLab CI** vencem em **experiência de desenvolvedor**, **pipeline junto ao código** e **ecossistema** — muitas equipes usam **Actions para CI** e **CodePipeline/CodeDeploy para CD** em AWS, ou **Actions com OIDC** fazendo tudo.
- É comum a combinação: **CodeConnections** (GitHub) → **CodePipeline** → **CodeBuild** → **CodeDeploy/ECS/CloudFormation**.

## 8. Primeiro exemplo (ilustrativo)

Definição simplificada (JSON da API, V2) com Source (CodeConnections/GitHub), Build (CodeBuild) e Deploy (ECS):

```json
{
  "pipeline": {
    "name": "app-pedidos",
    "pipelineType": "V2",
    "executionMode": "QUEUED",
    "roleArn": "arn:aws:iam::123456789012:role/codepipeline-app-pedidos",
    "artifactStore": { "type": "S3", "location": "meu-bucket-artefatos",
                        "encryptionKey": { "id": "arn:aws:kms:us-east-1:123456789012:key/abcd-...", "type": "KMS" } },
    "stages": [
      { "name": "Source", "actions": [{
          "name": "GitHub", "actionTypeId": { "category": "Source", "owner": "AWS", "provider": "CodeStarSourceConnection", "version": "1" },
          "configuration": { "ConnectionArn": "arn:aws:codeconnections:us-east-1:123456789012:connection/xxx",
                              "FullRepositoryId": "empresa/app-pedidos", "BranchName": "main" },
          "outputArtifacts": [{ "name": "SourceOutput" }] }] },
      { "name": "Build", "actions": [{
          "name": "Build", "actionTypeId": { "category": "Build", "owner": "AWS", "provider": "CodeBuild", "version": "1" },
          "configuration": { "ProjectName": "app-pedidos-build" },
          "inputArtifacts": [{ "name": "SourceOutput" }], "outputArtifacts": [{ "name": "BuildOutput" }] }] },
      { "name": "Deploy", "actions": [{
          "name": "ECS", "actionTypeId": { "category": "Deploy", "owner": "AWS", "provider": "ECS", "version": "1" },
          "configuration": { "ClusterName": "prod", "ServiceName": "pedidos-api", "FileName": "imagedefinitions.json" },
          "inputArtifacts": [{ "name": "BuildOutput" }] }] }
    ]
  }
}
```

```bash
aws codepipeline create-pipeline --cli-input-json file://pipeline.json
aws codepipeline start-pipeline-execution --name app-pedidos
aws codepipeline get-pipeline-state --name app-pedidos
```

## 9. Padrões de uso típicos

| Padrão | Descrição |
|---|---|
| **Aplicação com ECS** | Source → CodeBuild (imagem ECR) → Deploy ECS/CodeDeploy blue/green |
| **Serverless (SAM)** | Source → CodeBuild (`sam build/package`) → CloudFormation deploy (com CodeDeploy gradual) |
| **Infraestrutura (IaC)** | Source → validação (cfn-lint/checkov) → change set → **aprovação** → deploy |
| **Multi-ambiente** | Dev → HML → (aprovação) → PROD, em contas distintas |
| **Multi-região** | Deploy sequencial ou paralelo em várias regiões |
| **Imagens/AMIs** | Pipeline de imagens (build → scan → publicar) |
| **Dados/ML** | Source → treino/validação (Step Functions/SageMaker) → registro e deploy do modelo |

## 10. Limites a conhecer (visão geral)

| Limite (típico; confirmar) | Observação |
|---|---|
| **Pipelines por região** | Centenas (ajustável) |
| **Estágios por pipeline** | Dezenas (até 50) |
| **Ações por estágio** | Dezenas (até 50) |
| **Tamanho de artefatos** | Limites por ação/zip; artefatos grandes retardam |
| **Duração de execução** | Limites por ação (ex.: aprovação até 7 dias) |
| **Execuções simultâneas** | Conforme o modo e as quotas |
| **Ações entre regiões** | Exigem bucket de artefatos na região da ação |

## 11. Erros comuns

> [!bug] Erros comuns
> 1. **Usar o CodePipeline como substituto do CodeBuild/CodeDeploy** (ele só orquestra).
> 2. **Pipeline V1 quando precisa de gatilhos/filtros V2.**
> 3. **Modo `superseded` em fluxos que exigem cada commit** (execuções são substituídas).
> 4. **Bucket de artefatos público ou sem KMS** adequado.
> 5. **Service role ampla** (`*`) compartilhada entre pipelines.
> 6. **Sem aprovação manual** antes de produção.
> 7. **Artefatos gigantes** passando entre ações.
> 8. **Editar o pipeline no console** sem IaC (drift).
> 9. **Fonte via polling** em vez de eventos (latência/limites).
> 10. **Ações em regiões sem bucket de artefatos** configurado.

## 12. Troubleshooting inicial

| Sintoma | Causa provável | Ação |
|---|---|---|
| Pipeline não inicia após o commit | Gatilho/conexão ou filtro de branch | Verificar CodeConnections, EventBridge/webhook e filtros |
| `AccessDenied` ao baixar artefato | Role/KMS do bucket | Permitir a role da ação no bucket e na chave |
| Execução "substituída" | Modo superseded | Usar `QUEUED` se precisar de todas as revisões |
| Ação de build falha sem logs | Erro no projeto CodeBuild | Ver o build e o log no CodeBuild |
| Estágio travado em aprovação | Ninguém aprovou/sem notificação | Configurar SNS e permissões de aprovação |
| Falha ao implantar em outra região | Sem bucket/KMS regional | Criar artifact store por região |

## 13. Resumo rápido

- **CodePipeline** = orquestrador gerenciado de **entrega contínua**: **estágios → ações → artefatos**, com **aprovações**, **reexecução** e integração nativa AWS.
- Categorias: **Source, Build, Test, Deploy, Approval, Invoke** (e **Commands** no V2).
- **V1** (por pipeline) vs **V2** (gatilhos avançados, variáveis, modos **superseded/queued/parallel**, condições, rollback; cobrança por minuto).
- Forte em **AWS-first, multi-conta/região e governança**; **Actions/GitLab** vencem em DX e ecossistema; **combinações** são comuns.
- Pipeline como código (CloudFormation/CDK), **bucket de artefatos protegido** e **menor privilégio**.

### 🧩 Quiz de Fixação

1. O que é um estágio e o que é uma ação?
2. Como os artefatos passam entre ações?
3. Quais as diferenças centrais entre V1 e V2?
4. O que muda entre os modos superseded, queued e parallel?
5. Quando preferir GitHub Actions ao CodePipeline?
6. Que categorias de ação existem?
7. O CodePipeline compila e implanta por conta própria?

**Respostas:**

1. Estágio é uma fase lógica sequencial; ação é a tarefa dentro dele, executada por um provedor (CodeBuild, CodeDeploy etc.).
2. Por um artifact store (bucket S3, um por região), com artefatos de entrada e saída declarados em cada ação.
3. V2 traz gatilhos por branch/tag/caminho, variáveis, modos de execução, condições de estágio, rollback e ação Commands, com cobrança por minuto; V1 é o modelo clássico por pipeline.
4. Superseded substitui execuções antigas; queued processa em fila uma por vez; parallel executa simultaneamente.
5. Quando o foco é pipeline junto ao código, ecossistema de ações e experiência do desenvolvedor, sem necessidade forte de integração AWS multi-conta.
6. Source, Build, Test, Deploy, Approval e Invoke (mais Commands no V2).
7. Não; ele orquestra outras ferramentas que fazem o trabalho.
