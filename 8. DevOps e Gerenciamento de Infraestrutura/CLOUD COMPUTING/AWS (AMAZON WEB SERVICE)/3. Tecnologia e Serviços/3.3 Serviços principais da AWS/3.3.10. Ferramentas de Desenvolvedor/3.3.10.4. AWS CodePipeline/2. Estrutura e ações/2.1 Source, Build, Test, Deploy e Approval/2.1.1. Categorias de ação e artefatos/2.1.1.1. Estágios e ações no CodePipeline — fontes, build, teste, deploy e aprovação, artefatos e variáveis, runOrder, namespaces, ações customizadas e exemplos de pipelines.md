### 2.1.1.1. Estágios e ações no CodePipeline — fontes, build, teste, deploy e aprovação, artefatos e variáveis, runOrder, namespaces, ações customizadas e exemplos de pipelines

> [!warning] Aviso
> Nomes de provedores, parâmetros de configuração e variáveis de ação abaixo são **de memória e variam por ação e versão**; **confirme na documentação "Action structure reference" do CodePipeline**. JSONs, YAMLs e comandos são ilustrativos e **não foram executados**. Erros de configuração de artefatos (nomes e caminhos) são a causa mais comum de falhas.

## 1. Anatomia de um pipeline

Um pipeline é uma **lista ordenada de estágios**; cada estágio é uma **lista de ações**:

```
Pipeline
 ├── Stage 1: Source
 │     └── Action: Obter código  (runOrder 1)  → saída: SourceOutput
 ├── Stage 2: Build
 │     ├── Action: Compilar+testar (runOrder 1) → entrada: SourceOutput → saída: BuildOutput
 │     └── Action: Scan de segurança (runOrder 1, PARALELO) → entrada: SourceOutput
 ├── Stage 3: Deploy-HML
 │     ├── Action: Deploy (runOrder 1)
 │     └── Action: Testes de integração (runOrder 2, DEPOIS do deploy)
 ├── Stage 4: Aprovação
 │     └── Action: Manual approval
 └── Stage 5: Deploy-PROD
       └── Action: Deploy (runOrder 1)
```

Regras de execução:

| Regra | Efeito |
|---|---|
| **Estágios** executam **em sequência** | O estágio N+1 só começa quando o N termina com sucesso |
| **Ações do mesmo `runOrder`** executam **em paralelo** | Útil para testes/scans simultâneos |
| **`runOrder` maior** executa **depois** | Sequência dentro do estágio |
| **Falha de ação** | Para o estágio (e o pipeline), salvo condições (V2) |
| **Reexecução** | Reexecutar **ações com falha** ou o estágio inteiro |
| **Transições** | Podem ser **desabilitadas** entre estágios (pausar promoção) |

## 2. Estrutura de uma ação

Campos principais:

| Campo | Descrição |
|---|---|
| **name** | Nome único no estágio |
| **actionTypeId** | `category`, `owner` (AWS/ThirdParty/Custom), `provider`, `version` |
| **runOrder** | Ordem dentro do estágio |
| **configuration** | Parâmetros específicos do provedor |
| **inputArtifacts / outputArtifacts** | Nomes dos artefatos consumidos/produzidos |
| **roleArn** | Role específica **da ação** (em vez da role do pipeline), para **menor privilégio** e **cross-account** |
| **region** | Região da ação (cross-region) |
| **namespace** | Prefixo para as **variáveis** produzidas pela ação |
| **timeoutInMinutes** | Tempo máximo da ação |

## 3. Ações de Source (origem)

| Provedor | Configuração típica | Detecção de mudanças |
|---|---|---|
| **CodeCommit** | `RepositoryName`, `BranchName`, `PollForSourceChanges: false` | **EventBridge** (recomendado) |
| **GitHub/GitLab/Bitbucket (CodeConnections)** | `ConnectionArn`, `FullRepositoryId`, `BranchName`, `OutputArtifactFormat` (`CODE_ZIP` ou `CODEBUILD_CLONE_REF`) | Webhook da conexão |
| **Amazon S3** | `S3Bucket`, `S3ObjectKey` | Evento S3/EventBridge |
| **Amazon ECR** | `RepositoryName`, `ImageTag` | Evento de push de imagem |

Detalhes importantes:

- **`CODE_ZIP`** entrega o código **sem histórico Git**; **`CODEBUILD_CLONE_REF`** entrega uma **referência** para o CodeBuild fazer **clone completo** (útil para ferramentas que precisam do histórico, como versionamento semântico e `git describe`).
- Evite **polling** (`PollForSourceChanges: true`): prefira **eventos** (EventBridge/webhook) para **menor latência** e custo.
- A ação Source **produz variáveis** (`CommitId`, `CommitMessage`, `BranchName`, `RepositoryName`, `AuthorDate`...).

## 4. Ações de Build e Test

| Provedor | Uso |
|---|---|
| **CodeBuild** | Padrão para compilar, testar, escanear, empacotar; recebe artefatos e devolve saídas; `ProjectName`, `PrimarySource`, `EnvironmentVariables`, `BatchEnabled` |
| **Jenkins/CloudBees/TeamCity** | Integração com servidores de CI existentes |
| **AWS Device Farm** | Testes em dispositivos reais (mobile) |
| **Terceiros (BlazeMeter, Ghost Inspector, ...)** | Testes de carga/UI |
| **Commands (V2)** | Executar **comandos shell** direto no pipeline (sem criar projeto CodeBuild) |

Configuração do CodeBuild no pipeline:

```json
{ "name": "Build", "actionTypeId": { "category": "Build", "owner": "AWS", "provider": "CodeBuild", "version": "1" },
  "configuration": {
    "ProjectName": "app-build",
    "PrimarySource": "SourceOutput",
    "EnvironmentVariables": "[{\"name\":\"STAGE\",\"value\":\"hml\",\"type\":\"PLAINTEXT\"},{\"name\":\"COMMIT\",\"value\":\"#{SourceVars.CommitId}\",\"type\":\"PLAINTEXT\"}]"
  },
  "inputArtifacts": [{ "name": "SourceOutput" }],
  "outputArtifacts": [{ "name": "BuildOutput" }],
  "namespace": "BuildVars" }
```

O buildspec exporta variáveis (`exported-variables`) que ficam disponíveis como **`#{BuildVars.IMAGE_TAG}`** nas ações seguintes.

## 5. Ações de Deploy

| Provedor | Entrada típica | Observações |
|---|---|---|
| **CodeDeploy** | Pacote com `appspec.yml` | EC2/on-premises, Lambda |
| **CodeDeployToECS** | `taskdef.json` + `appspec.yaml` | Blue/green no ECS |
| **Amazon ECS** | `imagedefinitions.json` | Rolling update no ECS (atualiza a imagem do container) |
| **AWS CloudFormation** | Template + parâmetros | `CREATE_UPDATE`, `CHANGE_SET_REPLACE`/`CHANGE_SET_EXECUTE`, `DELETE_ONLY`, `REPLACE_ON_FAILURE`; **StackSets** para multi-conta/região |
| **Elastic Beanstalk** | Versão da aplicação | Ambiente gerenciado |
| **Amazon S3** | Arquivos estáticos | Sites estáticos/artefatos; com `Extract` |
| **AWS AppConfig** | Configuração/flags | Implantação gradual de configuração |
| **AWS Service Catalog** | Produto | Atualiza produtos provisionados |
| **Lambda (Invoke)** | Qualquer | Lógica customizada (ex.: atualizar parâmetros, DNS, notificações) |
| **Step Functions** | Máquina de estados | Fluxos complexos de implantação |
| **Alexa Skills Kit, Snyk...** | — | Conforme integração |

### 5.1 CloudFormation: change sets e aprovação

Padrão seguro para IaC:

```
Ação 1: CloudFormation CHANGE_SET_REPLACE  (cria o change set; mostra o que mudará)
Ação 2: Manual approval                    (revisa o change set)
Ação 3: CloudFormation CHANGE_SET_EXECUTE  (aplica)
```

## 6. Ação de aprovação manual

A **Manual approval** pausa o pipeline até **alguém aprovar ou rejeitar**:

| Configuração | Detalhe |
|---|---|
| **NotificationArn (SNS)** | Notifica aprovadores por e-mail/Chatbot |
| **CustomData** | Mensagem com contexto (versão, link de relatório) |
| **ExternalEntityLink** | URL para revisão (ex.: relatório de testes, PR) |
| **Timeout** | Até **7 dias**; expira como **falha** |
| **Quem aprova** | Principals com permissão `codepipeline:PutApprovalResult` **para aquele pipeline/estágio/ação** |

Boas práticas: **limitar quem aprova** por IAM (e separar de quem desenvolve — segregação de funções), incluir **evidências** (links) na mensagem e **registrar comentários** (auditoria).

```bash
aws codepipeline put-approval-result --pipeline-name app --stage-name Aprovacao --action-name Aprovar \
  --result summary="Testes de aceite OK",status=Approved --token <token>
```

## 7. Artefatos e variáveis

### 7.1 Artefatos

| Regra | Detalhe |
|---|---|
| **Entrada → saída** | Uma ação lê artefatos de entrada e gera saídas; saídas só existem **após** a ação |
| **Nome** | Único no pipeline; referenciado por ações posteriores |
| **Formato** | Zip (ou pasta, conforme a ação) |
| **Múltiplas entradas** | Ex.: `SourceOutput` + `InfraOutput`; no CodeBuild, `PrimarySource` define o diretório principal |
| **Tamanho** | Mantenha pequeno (só o necessário) |
| **Ciclo** | O bucket guarda artefatos de **todas as execuções**: configure **S3 Lifecycle** para expirar |
| **Cross-region** | Artefatos são **replicados** para o bucket da região da ação |

### 7.2 Variáveis e namespaces

As ações **produzem variáveis** e consumem com a sintaxe **`#{namespace.variavel}`**:

| Origem | Variáveis comuns |
|---|---|
| **Source** (`SourceVariables`) | `CommitId`, `CommitMessage`, `BranchName`, `RepositoryName`, `AuthorDate`, `ConnectionArn` |
| **CodeBuild** | As declaradas em `exported-variables` + `CODEBUILD_BUILD_ID`... |
| **CloudFormation** | **Outputs** da stack (`#{DeployVars.ApiUrl}`) |
| **Execução do pipeline** | `codepipeline.PipelineExecutionId` |
| **Variáveis de pipeline (V2)** | `#{variables.AMBIENTE}` |
| **Lambda** | Via `outputVariables` retornadas |

Exemplo: passar a **tag de imagem** e a **URL** entre ações:

```
Build (namespace BuildVars): exported-variables → IMAGE_TAG
Deploy (CloudFormation):  ParameterOverrides = {"ImageTag":"#{BuildVars.IMAGE_TAG}"}
Teste (Lambda):           UserParameters = "#{DeployVars.ApiUrl}"
```

> [!warning] Cuidado
> Variáveis são **texto** e aparecem em **logs/console**: **não** passe segredos por variáveis de ação. Use Secrets Manager/Parameter Store.

## 8. Ações customizadas e Lambda

| Opção | Quando usar |
|---|---|
| **Lambda Invoke** | Lógica própria curta (validações, notificações, atualizações externas); deve chamar **`PutJobSuccessResult`/`PutJobFailureResult`** |
| **Step Functions** | Fluxos complexos com múltiplos passos e retentativas |
| **Custom action type** | Ação **própria** (worker externo faz polling por jobs: `PollForJobs`) — para integrar ferramentas internas |
| **Commands (V2)** | Pequenos comandos shell sem CodeBuild |

Exemplo de Lambda de validação pós-deploy (ilustrativo):

```python
import boto3, urllib.request
cp = boto3.client("codepipeline")
def handler(event, context):
    job = event["CodePipeline.job"]
    url = job["data"]["actionConfiguration"]["configuration"]["UserParameters"]
    try:
        r = urllib.request.urlopen(url + "/saude", timeout=10)
        if r.status == 200:
            cp.put_job_success_result(jobId=job["id"])
        else:
            cp.put_job_failure_result(jobId=job["id"], failureDetails={"type": "JobFailed", "message": f"HTTP {r.status}"})
    except Exception as e:
        cp.put_job_failure_result(jobId=job["id"], failureDetails={"type": "JobFailed", "message": str(e)})
```

Sem reportar sucesso/falha, a ação **expira**.

## 9. Exemplos de pipelines

### 9.1 Aplicação em ECS (blue/green)

```
Source (GitHub/CodeConnections)
 → Build (CodeBuild: testes, docker build/push ECR, gera taskdef.json + appspec.yaml)
 → Deploy-HML (CodeDeployToECS, canary 10%)
 → Test (CodeBuild: testes E2E contra HML)
 → Aprovação manual
 → Deploy-PROD (CodeDeployToECS em conta PROD via roleArn cross-account)
```

### 9.2 Serverless com SAM

```
Source → Build (sam build + sam package; saída: template empacotado)
 → Deploy-HML (CloudFormation CREATE_UPDATE, capabilities CAPABILITY_IAM/AUTO_EXPAND)
 → Aprovação
 → Deploy-PROD (CloudFormation; SAM + DeploymentPreference → CodeDeploy canary nas Lambdas)
```

### 9.3 Infraestrutura (IaC)

```
Source (repositório de IaC)
 → Validate (CodeBuild: cfn-lint, cfn-guard, checkov)
 → ChangeSet (CloudFormation CHANGE_SET_REPLACE) 
 → Aprovação (revisão do change set)
 → Execute (CHANGE_SET_EXECUTE)
```

## 10. Erros comuns

> [!bug] Erros comuns
> 1. **Nomes de artefatos inconsistentes** entre saída e entrada.
> 2. **`runOrder` incorreto** (tentando usar a saída antes de ser gerada).
> 3. **Source com polling** em vez de eventos.
> 4. **`CODE_ZIP` quando a ferramenta precisa do histórico Git.**
> 5. **Lambda de ação que não reporta sucesso/falha** (ação expira).
> 6. **Segredos em variáveis de ação.**
> 7. **Aprovação aberta a todos** os que têm acesso ao pipeline.
> 8. **Passar artefatos enormes** entre ações.
> 9. **Role única ampla** para todas as ações (use `roleArn` por ação).
> 10. **CloudFormation sem change set/aprovação** em produção.

## 11. Troubleshooting

| Sintoma | Causa provável | Ação |
|---|---|---|
| `InvalidActionDeclaration` | Configuração/artefatos inválidos | Validar nomes e parâmetros da ação |
| `The provided role cannot be assumed` | Role/trust incorreta | Ajustar a trust policy (`codepipeline.amazonaws.com`) |
| Ação de build falha sem artefato | Caminho em `artifacts` do buildspec | Corrigir o buildspec |
| Variável não resolve (`#{...}`) | Namespace/nome incorreto ou ação anterior não exportou | Conferir `namespace` e `exported-variables` |
| Aprovação não chega | SNS sem assinatura/permissão | Configurar o tópico e as assinaturas |
| Cross-region falha | Sem bucket/KMS na região | Criar o artifact store regional |
| Deploy CloudFormation `INSUFFICIENT_CAPABILITIES` | Faltam capabilities | Definir `CAPABILITY_IAM`/`NAMED_IAM`/`AUTO_EXPAND` |

## 12. Resumo rápido

- Pipeline = **estágios sequenciais**; ações do **mesmo `runOrder` em paralelo**.
- **Source**: CodeCommit, CodeConnections (GitHub/GitLab/Bitbucket), S3, ECR — com **eventos** (não polling); `CODE_ZIP` vs `CODEBUILD_CLONE_REF`.
- **Build/Test**: CodeBuild (e terceiros); **Deploy**: CodeDeploy, CodeDeployToECS, ECS, CloudFormation (change sets), Beanstalk, S3, AppConfig; **Approval** manual com SNS e permissão restrita.
- **Artefatos** passam por S3 (um bucket por região); **variáveis** `#{namespace.var}` (sem segredos).
- **Lambda/Step Functions/custom** para lógica própria (reporte sucesso/falha); use **`roleArn` por ação**.

### 🧩 Quiz de Fixação

1. O que significa runOrder iguais em um estágio?
2. Qual a diferença entre CODE_ZIP e CODEBUILD_CLONE_REF?
3. Como passar uma variável do CodeBuild para o deploy?
4. Como usar CloudFormation com revisão antes de aplicar?
5. Quem pode aprovar uma ação manual?
6. O que a Lambda de uma ação deve chamar ao terminar?
7. Por que evitar segredos em variáveis de ação?

**Respostas:**

1. Que as ações executam em paralelo no mesmo estágio.
2. CODE_ZIP entrega o código sem histórico Git; CODEBUILD_CLONE_REF permite que o CodeBuild faça clone completo com histórico.
3. Declarando `exported-variables` no buildspec e referenciando `#{namespace.VARIAVEL}` na ação seguinte.
4. Com CHANGE_SET_REPLACE, aprovação manual e depois CHANGE_SET_EXECUTE.
5. Quem tem `codepipeline:PutApprovalResult` para aquela ação, idealmente um grupo restrito e separado de quem desenvolve.
6. `PutJobSuccessResult` ou `PutJobFailureResult`; sem isso a ação expira.
7. Porque variáveis aparecem em logs e no console; segredos devem vir do Secrets Manager ou Parameter Store.
