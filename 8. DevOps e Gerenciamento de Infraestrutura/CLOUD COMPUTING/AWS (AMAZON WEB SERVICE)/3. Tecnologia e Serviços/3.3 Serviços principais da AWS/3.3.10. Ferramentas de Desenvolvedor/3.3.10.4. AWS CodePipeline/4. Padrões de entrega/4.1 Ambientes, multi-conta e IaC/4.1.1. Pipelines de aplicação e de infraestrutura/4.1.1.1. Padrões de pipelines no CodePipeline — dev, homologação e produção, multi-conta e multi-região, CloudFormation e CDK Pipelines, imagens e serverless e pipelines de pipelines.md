### 4.1.1.1. Padrões de pipelines no CodePipeline — dev, homologação e produção, multi-conta e multi-região, CloudFormation e CDK Pipelines, imagens e serverless e pipelines de pipelines

> [!warning] Aviso
> Os desenhos, YAMLs e comandos abaixo são **ilustrativos, de memória e não foram executados**. Detalhes de **CDK Pipelines**, **StackSets** e **roles cross-account** mudam entre versões; **confirme na documentação**. Pipelines multi-conta mexem em permissões sensíveis: valide com a equipe de segurança e ensaie em contas de teste.

## 1. Princípios de um bom desenho de entrega

| Princípio | Significado |
|---|---|
| **Build uma vez, implante muitas** | O **mesmo artefato** (imagem/zip) que passou em HML vai para PROD — **nunca recompile por ambiente** |
| **Configuração fora do artefato** | Parâmetros por ambiente (Parameter Store/AppConfig/variáveis de stack), não "builds diferentes" |
| **Ambientes parecidos** | HML o mais próximo possível de PROD (IaC, mesma topologia) |
| **Automação e repetibilidade** | Tudo como código; nada de passos manuais, exceto **aprovações** |
| **Feedback rápido** | Falhas cedo (lint, unitários), testes caros depois |
| **Promoção controlada** | Gates: testes, segurança, aprovação, janelas, alarmes |
| **Rollback ensaiado** | Voltar para a versão anterior de forma simples |
| **Menor privilégio e isolamento** | Contas separadas e roles por ação |
| **Observabilidade** | Métricas de entrega (DORA), notificações, trilha de auditoria |

```
Código ─▶ BUILD (1×) ─▶ artefato imutável ─▶ DEV ─▶ HML ─▶ [aprovação] ─▶ PROD
                           (mesmo hash)       cada ambiente: config própria, mesmo artefato
```

## 2. Pipeline multi-ambiente em uma conta (simples)

Para equipes pequenas ou projetos iniciais: **um pipeline**, **vários estágios** (DEV, HML, PROD) na **mesma conta**, com **stacks/serviços distintos** por ambiente.

```
Source → Build → Deploy-DEV → Test-DEV → Deploy-HML → Test-HML → [Aprovação] → Deploy-PROD → Verificação
```

Vantagens: **simplicidade** e custo baixo. Riscos: **blast radius** (um erro de permissão afeta tudo), **limites compartilhados** (quotas, throttling) e **isolamento fraco** entre PROD e demais. Evolua para **multi-conta** conforme a criticidade.

## 3. Pipeline multi-conta (recomendado para produção)

Padrão amplamente adotado:

```
                     CONTA "TOOLING" (ferramentas)
  Source ─▶ CodePipeline ─▶ CodeBuild ─▶ Artefatos (S3 + KMS CMK) ─▶ ECR
                │
                ├─ assume role ─▶ CONTA DEV   (implanta DEV)
                ├─ assume role ─▶ CONTA HML   (implanta HML)
                └─ assume role ─▶ CONTA PROD  (após aprovação)
```

Elementos:

| Elemento | Detalhe |
|---|---|
| **Conta tooling** | Hospeda o pipeline, o CodeBuild, repositórios de artefatos/imagens; **sem cargas de aplicação** |
| **Contas de ambiente** | DEV/HML/PROD **isoladas** (Organizations, SCPs, orçamentos) |
| **Roles cross-account** | Em cada conta de ambiente, uma **role de implantação** (CloudFormation/CodeDeploy) que **confia na conta tooling**; a ação usa `roleArn` dessa role |
| **Artefatos compartilhados** | Bucket S3 + **KMS CMK** com políticas que permitam as contas de ambiente; **ECR** com política cross-account de leitura |
| **CloudFormation execution role** | Role que o CloudFormation assume para criar recursos (limitada) |
| **Aprovação** | Antes de PROD (e/ou janela e condições de alarme) |

Boas práticas de permissão:

1. A **role do pipeline** só pode **assumir as roles de deploy**; **não** tem permissões nos recursos.
2. A **role de deploy** em PROD é a **única** com acesso para alterar PROD; ela tem **condições** (por exemplo, `aws:SourceArn` do pipeline, `aws:PrincipalOrgID`).
3. **KMS CMK** com key policy permitindo **as roles do pipeline e das contas de ambiente** (a chave gerenciada pela AWS não funciona cross-account).
4. **Bootstrapping**: crie as roles/buckets de cada ambiente por **IaC** (`cdk bootstrap` ou StackSets).
5. **Humanos** sem acesso de escrita direto em PROD; **break-glass** auditado.

## 4. Multi-região

| Cenário | Desenho |
|---|---|
| **Resiliência/DR e latência** | Ações de **deploy por região**, em **sequência** (região canário primeiro) ou **paralelo** |
| **Artefatos** | Um **artifact store por região** (replicado automaticamente pelo CodePipeline para ações cross-region) |
| **Imagens** | **ECR com replicação** entre regiões (ou build por região) |
| **Parâmetros por região** | Variáveis de pipeline (`REGIAO`) ou stacks parametrizadas |
| **Ordem** | Região piloto (menor tráfego) → demais, com **bake time** e alarmes |
| **Failover** | Route 53 e dados replicados (DynamoDB Global Tables, Aurora Global) — **fora do pipeline**, mas coordenado |

```json
{ "name": "Deploy-sa-east-1", "actions": [ { "name": "CFN-SP", "region": "sa-east-1",
   "actionTypeId": { "category": "Deploy", "owner": "AWS", "provider": "CloudFormation", "version": "1" },
   "configuration": { "ActionMode": "CREATE_UPDATE", "StackName": "app-prod", "TemplatePath": "BuildOutput::template.yaml" },
   "inputArtifacts": [{ "name": "BuildOutput" }] } ] }
```

Para **muitas contas/regiões**, use **CloudFormation StackSets** (ação de deploy com `StackSet`), com **ondas** (waves) e **tolerância a falhas**.

## 5. Pipelines de infraestrutura (IaC)

Fluxo seguro e revisável:

```
Source (IaC) → Validação (cfn-lint/cfn-guard/checkov/tfsec) → Testes (TaskCat/Terratest) 
   → Change set (CloudFormation) → [Aprovação revisando o change set] → Apply → Verificação (smoke/Config)
```

| Prática | Detalhe |
|---|---|
| **Change sets** | Mostram **o que será criado/alterado/removido** antes de aplicar |
| **Policy as code** | `cfn-guard`/OPA/Checkov bloqueiam recursos fora do padrão (S3 público, SG aberto) |
| **Drift detection** | Verificação periódica de divergências |
| **Terraform** | CodeBuild executa `terraform plan`/`apply` com **backend remoto** (S3 + DynamoDB lock) e **aprovação** do plano |
| **Segredos** | Fora do código; via Secrets Manager |
| **Ordem entre stacks** | Dependências explícitas (stacks de rede → dados → aplicação) |

## 6. AWS CDK Pipelines (pipelines que se atualizam sozinhos)

O **CDK Pipelines** é uma biblioteca do **AWS CDK** que **gera um CodePipeline** com **auto-mutação**:

```typescript
const pipeline = new pipelines.CodePipeline(this, 'Pipeline', {
  synth: new pipelines.ShellStep('Synth', {
    input: pipelines.CodePipelineSource.connection('empresa/app', 'main', { connectionArn }),
    commands: ['npm ci', 'npm test', 'npx cdk synth'],
  }),
  crossAccountKeys: true,       // cria KMS CMK para cross-account
});
pipeline.addStage(new AppStage(this, 'Hml',  { env: { account: '222222222222', region: 'us-east-1' } }));
pipeline.addStage(new AppStage(this, 'Prod', { env: { account: '333333333333', region: 'us-east-1' } }),
  { pre: [new pipelines.ManualApprovalStep('AprovarProd')] });
```

| Característica | Detalhe |
|---|---|
| **Auto-mutação (self-mutate)** | O pipeline **atualiza a si mesmo** quando seu código muda |
| **Cross-account/region** | Gera roles, buckets e chaves necessárias (`cdk bootstrap` nas contas) |
| **Stages como "aplicações"** | Cada `Stage` do CDK = um ambiente |
| **Passos** | `ShellStep` (CodeBuild), `ManualApprovalStep`, validações |
| **Benefício** | Pipeline **como código** na mesma linguagem da aplicação |
| **Cuidado** | Complexidade de bootstrapping e permissões; **versione o CDK** |

## 7. Pipelines de imagens e containers

```
Source (Dockerfile + app) → Build (CodeBuild: testes, build, SBOM) → Scan (ECR/Inspector/Trivy; gate)
   → Assinar (Signer/Notation) → Push (ECR) → Deploy (ECS/EKS) por tag/digest
```

Boas práticas: **tag por SHA**/**digest imutável**, **ECR tag immutability**, **scan com gate**, **assinatura e verificação**, **promoção** da **mesma imagem** entre ambientes (replicação/pull cross-account) e **limpeza** (ECR lifecycle policies).

## 8. Pipelines serverless (SAM/Lambda)

```
Source → Build (sam build, testes) → Package (sam package → S3) 
  → Deploy-HML (CloudFormation, SAM) → Testes (integração/E2E contra HML)
  → [Aprovação] → Deploy-PROD (CloudFormation; SAM DeploymentPreference → CodeDeploy canary/linear + alarmes)
```

Pontos de atenção: **capabilities** (`CAPABILITY_IAM`, `CAPABILITY_AUTO_EXPAND`), **parâmetros por ambiente**, **aliases** e **liberação gradual** com **alarmes**, **dependências** em camadas (layers), **versões de runtime**.

## 9. Pipelines de pipelines (plataforma)

Em organizações grandes, **dezenas/centenas** de pipelines exigem **padronização**:

| Prática | Detalhe |
|---|---|
| **Templates/módulos** | Pipelines gerados de **templates** (CloudFormation modules, CDK constructs, Terraform modules, Service Catalog) |
| **Pipeline de criação de pipelines** | Um pipeline "plataforma" que cria/atualiza pipelines de equipes a partir de um catálogo |
| **Padrões obrigatórios** | Scans de segurança, aprovação em PROD, tags, notificações, retenção de artefatos |
| **Self-service com guarda-corpos** | Equipes escolhem blueprints aprovados (Service Catalog / Proton / Backstage) |
| **Governança** | **SCPs**, **Config** e **Security Hub** verificam conformidade dos pipelines |
| **Métricas centralizadas** | DORA por equipe/serviço |

## 10. Estratégias de promoção e liberação

| Estratégia | Como |
|---|---|
| **Promoção automática até HML, manual em PROD** | Aprovação + janela + alarmes |
| **Entrega contínua total** (sem aprovação) | Para times maduros: testes fortes, canary, rollback automático, feature flags |
| **Promoção por tag/release** | Gatilho de tag (V2) |
| **Ambientes efêmeros por PR** | Pipeline paralelo cria stack temporária, testa e destrói |
| **Blue/green e canary** | CodeDeploy (ECS/Lambda/EC2) dentro da ação de deploy |
| **Feature flags (AppConfig)** | Separa deploy de release |
| **Congelamento de mudanças** | Condição de janela/desabilitar transição em datas críticas |

## 11. Testes dentro do pipeline

| Camada | Onde | Exemplos |
|---|---|---|
| **Estáticos** | Build | Lint, SAST, SCA, validação de IaC, segredos |
| **Unitários** | Build | Rápidos, cobertura |
| **Contrato/componentes** | Build/HML | Testes de contrato (Pact), testes de API |
| **Integração** | DEV/HML | Com dependências reais/ambientes efêmeros |
| **E2E/UI** | HML | Playwright/Cypress/Device Farm |
| **Carga/desempenho** | HML (pontual) | k6/Locust/Distributed Load Testing |
| **Segurança dinâmica** | HML | DAST |
| **Smoke/sintéticos** | PROD (pós-deploy) | CloudWatch Synthetics, health checks |
| **Caos/resiliência** | HML/PROD controlado | Fault Injection Service (game days) |

## 12. Erros comuns

> [!bug] Erros comuns
> 1. **Recompilar por ambiente** (artefatos diferentes entre HML e PROD).
> 2. **Tudo em uma conta**, com PROD exposto aos mesmos riscos de DEV.
> 3. **Role do pipeline com acesso direto a PROD** (em vez de assumir roles de deploy).
> 4. **KMS gerenciada pela AWS** em cenário cross-account.
> 5. **Aplicar IaC direto em PROD** sem change set/aprovação.
> 6. **Parallel em ambiente compartilhado**, gerando conflitos.
> 7. **Testes lentos antes dos rápidos** (feedback tardio).
> 8. **Sem rollback ensaiado** e sem alarmes no deploy.
> 9. **Cada equipe com um pipeline diferente** (sem padrões).
> 10. **Artefatos expirados** no S3 impedindo rollback.

## 13. Troubleshooting

| Sintoma | Causa provável | Ação |
|---|---|---|
| `AccessDenied` ao assumir role em outra conta | Trust policy/`sts:AssumeRole` | Ajustar trust (conta tooling) e permissão da role do pipeline |
| Falha ao ler artefato na conta de ambiente | Bucket/KMS cross-account | Permitir a role de deploy no bucket e na chave |
| ECS não puxa imagem cross-account | Política do ECR | Conceder pull à conta/role de execução |
| `cdk deploy` falha por bootstrap | Conta não "bootstrapped" | Executar `cdk bootstrap` com `--trust` da conta tooling |
| StackSet falha em algumas regiões | Limites/permissões regionais | Ajustar tolerância e roles em cada região |
| HML passa e PROD falha | Diferenças de configuração/permissão | Padronizar IaC e testar com roles equivalentes |
| Pipeline autogerado não atualiza | Self-mutation desabilitada | Habilitar `selfMutation` e permissões |

## 14. Resumo rápido

- **Build uma vez, implante muitas**; configuração por ambiente fora do artefato.
- **Multi-conta**: conta **tooling** + contas de ambiente; **roles cross-account**, **KMS CMK**, aprovação em PROD.
- **Multi-região**: artifact store por região, sequência com **bake time**; **StackSets** para escala.
- **IaC**: validação, **change set + aprovação**; **CDK Pipelines** para pipelines auto-atualizáveis.
- **Imagens/serverless**: tags imutáveis, scan, assinatura, **canary** com alarmes.
- **Plataforma**: templates, guarda-corpos e métricas **DORA**.

### 🧩 Quiz de Fixação

1. O que significa "build uma vez, implante muitas"?
2. Qual a função da conta tooling?
3. Por que usar KMS CMK em pipelines cross-account?
4. Como o CDK Pipelines se auto-atualiza?
5. Por que usar change sets em pipelines de IaC?
6. Como tratar multi-região?
7. O que é um pipeline de pipelines?

**Respostas:**

1. Gerar o artefato uma vez e promover o mesmo artefato por todos os ambientes, com configuração externa.
2. Hospedar pipeline, builds e artefatos, e assumir roles de deploy nas contas de ambiente, sem cargas de aplicação.
3. A chave gerenciada pela AWS não permite uso cross-account; a CMK permite via key policy às roles/contas de destino.
4. Pela etapa de self-mutation, que atualiza o pipeline quando o código do pipeline muda.
5. Para revisar o que será criado, alterado ou removido antes de aplicar, com aprovação.
6. Artifact store por região, ações de deploy por região em ordem (piloto primeiro) e StackSets para escala.
7. Um pipeline/plataforma que cria e padroniza pipelines de várias equipes a partir de templates e guarda-corpos.
