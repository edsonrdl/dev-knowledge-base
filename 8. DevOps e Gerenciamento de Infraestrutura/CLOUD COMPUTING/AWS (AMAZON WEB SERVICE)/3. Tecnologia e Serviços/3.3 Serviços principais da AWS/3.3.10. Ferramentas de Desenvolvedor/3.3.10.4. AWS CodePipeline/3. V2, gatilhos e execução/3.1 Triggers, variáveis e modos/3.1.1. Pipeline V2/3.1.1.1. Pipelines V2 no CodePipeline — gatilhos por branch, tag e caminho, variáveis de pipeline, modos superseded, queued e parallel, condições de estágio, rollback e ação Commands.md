### 3.1.1.1. Pipelines V2 no CodePipeline — gatilhos por branch, tag e caminho, variáveis de pipeline, modos superseded, queued e parallel, condições de estágio, rollback e ação Commands

> [!warning] Aviso
> Os recursos do **tipo V2** (gatilhos, variáveis, modos de execução, condições, rollback, ação Commands) **evoluem rapidamente**; nomes de campos, limites e preços abaixo são **de memória**. **Confirme na documentação do CodePipeline** e na página de preços antes de migrar ou orçar. JSONs, YAMLs e comandos são ilustrativos e **não foram executados**.

## 1. Por que o V2 existe

O pipeline **V1** dispara **sempre que a fonte muda** e executa **uma versão por vez** (cada nova execução **substitui** a anterior em andamento). Isso é limitado para times modernos que precisam:

- **Disparar só para certas branches/tags/caminhos** (monorepos, releases por tag).
- **Parametrizar** a execução (escolher ambiente, versão, flags) **sem editar o pipeline**.
- **Garantir ordem** de implantação (**fila**) ou **paralelizar** branches.
- **Controlar o fluxo** com **condições** (só entrar no estágio se...; o que fazer se falhar).
- **Reverter** automaticamente para a última versão boa.
- **Rodar comandos** simples sem manter um projeto CodeBuild.

O **tipo V2** entrega esses recursos, com **cobrança por minuto de execução de ação** (em vez de por pipeline ativo).

```
V1:  commit ─▶ pipeline (sem filtros) ─▶ 1 execução por vez, substitui anteriores
V2:  commit/tag/PR + filtros + variáveis ─▶ modo (superseded/queued/parallel) ─▶ estágios com condições e rollback
```

## 2. Gatilhos (triggers) no V2

Um **gatilho** define **quando** uma execução começa e **com quais filtros**. O pipeline pode ter **vários gatilhos**.

| Tipo de gatilho | Descrição |
|---|---|
| **Push (commit)** em uma **branch** | Filtra por **branches** (`include`/`exclude`, padrões glob) |
| **Push de tag** | Filtra por **tags** (`v*`, `release-*`) — **releases por tag** |
| **Pull request** | Eventos de PR (aberto, atualizado, fechado) com filtro de **branch de destino** |
| **Filtro por caminho (file paths)** | Dispara só se **arquivos específicos** mudaram (`services/pagamentos/**`) |
| **Manual** | Início manual (console/CLI/API), com **variáveis** |
| **Agendado (via EventBridge Scheduler)** | Execuções periódicas |
| **Outras fontes** | Eventos de S3/ECR via EventBridge |

Exemplo (declaração de gatilhos, ilustrativa):

```json
"triggers": [
  { "providerType": "CodeStarSourceConnection",
    "gitConfiguration": {
      "sourceActionName": "GitHub",
      "push": [
        { "branches": { "includes": ["main", "release/*"] },
          "filePaths": { "includes": ["services/pagamentos/**"], "excludes": ["**/*.md"] } },
        { "tags": { "includes": ["v*"] } }
      ],
      "pullRequest": [
        { "events": ["OPEN", "UPDATED"], "branches": { "includes": ["main"] } }
      ]
    } }
]
```

Valor prático:

| Caso | Como |
|---|---|
| **Monorepo** | Um pipeline por serviço, cada um com `filePaths` do seu diretório |
| **Release por tag** | Gatilho de tag `v*` implanta em produção; push na main só até HML |
| **CI de PR** | Pipeline de validação disparado por PRs (sem deploy) |
| **Ignorar docs** | `excludes: ["**/*.md", "docs/**"]` |

> [!warning] Atenção
> Os filtros por **branch/tag/caminho** dependem do tipo de **source** (principalmente **CodeConnections**); confirme o suporte da sua fonte (CodeCommit, S3...) na documentação.

## 3. Variáveis de pipeline

**Variáveis em nível de pipeline** são **parâmetros da execução**, declarados no pipeline e **informados** ao iniciar (ou com **padrão**):

```json
"variables": [
  { "name": "AMBIENTE", "defaultValue": "hml", "description": "Ambiente alvo" },
  { "name": "VERSAO", "description": "Versão a implantar" }
]
```

Uso em ações com **`#{variables.AMBIENTE}`**:

```json
"configuration": { "ProjectName": "deploy-app",
  "EnvironmentVariables": "[{\"name\":\"AMBIENTE\",\"value\":\"#{variables.AMBIENTE}\",\"type\":\"PLAINTEXT\"}]" }
```

```bash
aws codepipeline start-pipeline-execution --name app-pedidos \
  --variables name=AMBIENTE,value=prod name=VERSAO,value=1.8.0
```

Casos de uso: **pipeline único parametrizado** para vários ambientes, **reimplantar uma versão específica**, **feature flags de pipeline**, **seleção de região**. Diferem das **variáveis de ação** (`#{namespace.var}`), geradas **dentro** da execução.

> [!warning] Segredos
> Variáveis de pipeline **não são segredos**: aparecem na interface e no histórico. Use Secrets Manager/Parameter Store.

## 4. Modos de execução

| Modo | Comportamento detalhado | Quando usar |
|---|---|---|
| **SUPERSEDED** (padrão) | Se uma **nova execução** chega enquanto outra aguarda em um estágio, a **mais antiga é substituída** (só a mais recente avança) | **CD de "última versão vence"** (ex.: HML) |
| **QUEUED** | As execuções entram em **fila FIFO**; **cada uma completa** (por estágio, uma por vez) | Quando **cada revisão** deve ser implantada **em ordem** (ex.: migrações sequenciais, auditoria) |
| **PARALLEL** | Execuções **simultâneas e independentes** | Branches/PRs diferentes, builds de feature |

Considerações:

- **QUEUED** aumenta a **latência** (fila) mas garante **ordem e completude**; use com **limites de fila** e monitoramento.
- **PARALLEL** pode causar **conflitos** se várias execuções **implantam no mesmo ambiente** — restrinja a **estágios sem estado compartilhado** (testes, builds) ou use **ambientes efêmeros** por branch.
- **SUPERSEDED** é eficiente, porém **descarta** revisões intermediárias (aceitável quando só o estado final importa).

```bash
aws codepipeline update-pipeline --cli-input-json file://pipeline.json   # com "executionMode": "QUEUED"
```

## 5. Condições de estágio

O V2 permite **condições** em **três pontos** de cada estágio:

| Ponto | Uso |
|---|---|
| **Entrada (`beforeEntry`)** | **Só entra** no estágio se a condição for verdadeira (ex.: variável `AMBIENTE == "prod"`, **alarme não em ALARM**, resultado de uma regra) |
| **Sucesso (`onSuccess`)** | Executa verificações/ações **após o sucesso** do estágio (ex.: checar **alarmes** durante um período de observação) |
| **Falha (`onFailure`)** | Define o que fazer **ao falhar**: **retry** automático, **rollback**, **falhar**, **ignorar** |

Regras e verificações disponíveis (exemplos conceituais):

| Regra | Função |
|---|---|
| **CloudWatchAlarm** | Condição baseada no estado de alarmes (ex.: só promover se **nenhum alarme** ativo) |
| **VariableCheck** | Compara variáveis (ex.: `#{variables.AMBIENTE} == prod`) |
| **LambdaInvoke** | Chama uma Lambda que decide |
| **Commands** | Executa comandos e usa o resultado |
| **DeploymentWindow** | Só executa dentro de uma **janela** (ex.: horário comercial/evitar sexta à tarde) |

Exemplo (conceitual):

```json
{ "name": "Deploy-PROD",
  "beforeEntry": { "conditions": [ { "result": "FAIL", "rules": [
      { "name": "SemAlarmes", "ruleTypeId": { "category": "Rule", "owner": "AWS", "provider": "CloudWatchAlarm", "version": "1" },
        "configuration": { "AlarmNames": "app-5xx,app-latencia", "WaitTime": "5m", "AlarmStates": "OK" } } ] } ] },
  "onFailure": { "result": "ROLLBACK" },
  "onSuccess": { "conditions": [ { "result": "ROLLBACK", "rules": [
      { "name": "ObservarAlarmes", "ruleTypeId": { "category": "Rule", "owner": "AWS", "provider": "CloudWatchAlarm", "version": "1" },
        "configuration": { "AlarmNames": "app-5xx", "WaitTime": "15m", "AlarmStates": "OK" } } ] } ] },
  "actions": [ ... ] }
```

Isso implementa **"entrar só com sistema saudável", "implantar", "observar 15 minutos" e "reverter se alarmar"** — **sem scripts externos**.

## 6. Rollback de estágio

O **rollback** do V2 **reexecuta o estágio com a última execução bem-sucedida** (artefatos e revisão anteriores):

| Aspecto | Detalhe |
|---|---|
| **Gatilho** | Automático (`onFailure`/`onSuccess` com `ROLLBACK`) ou **manual** (console/CLI) |
| **O que faz** | Executa o estágio de novo com os **artefatos da execução anterior bem-sucedida** (não recompila) |
| **Escopo** | O **estágio** (não o pipeline inteiro); estágios de **Deploy** são o alvo típico |
| **Limitações** | Não desfaz **mudanças de dados**; depende de a execução anterior ter sido **bem-sucedida** e de os artefatos **existirem** (S3 lifecycle!) |
| **Combina com** | CodeDeploy (rollback de plataforma) e **CloudFormation** (reaplica o template anterior) |

```bash
aws codepipeline rollback-stage --pipeline-name app-pedidos --stage-name Deploy-PROD \
  --target-pipeline-execution-id <id-da-execucao-boa>
```

> [!warning] Cuidado
> **Rollback de pipeline ≠ rollback de dados.** Compatibilidade de schema/eventos (expand/contract) continua sendo sua responsabilidade. E o **bucket de artefatos** precisa **reter** as execuções que você pretende reaproveitar.

## 7. Ação Commands

A ação **Commands** executa **comandos shell** diretamente no pipeline (em ambiente gerenciado), **sem criar um projeto CodeBuild**:

| Característica | Detalhe |
|---|---|
| **Uso** | Passos **pequenos**: renomear artefatos, `aws s3 cp`, `curl` de verificação, gerar arquivo de parâmetros |
| **Entradas/saídas** | Pode usar **artefatos de entrada**, **gerar variáveis** de saída e **artefatos** |
| **Ambiente** | Baseado em compute do CodeBuild (cobrado por **minuto de ação**) |
| **Limitações** | Menos configurável que o CodeBuild (imagem, VPC, cache, batch) |
| **Quando preferir CodeBuild** | Builds reais, dependências, testes, VPC, cache |

```json
{ "name": "VerificaSaude", "actionTypeId": { "category": "Compute", "owner": "AWS", "provider": "Commands", "version": "1" },
  "configuration": { "Commands": "curl -sf https://hml.exemplo.com/saude || exit 1" },
  "region": "us-east-1" }
```

## 8. Cobrança V1 vs V2 (visão geral)

| Aspecto | V1 | V2 |
|---|---|---|
| **Modelo** | Taxa **mensal por pipeline ativo** (um pipeline gratuito) | **Por minuto** de execução de ações (com franquia gratuita) |
| **Pipelines ociosos** | Pagam a taxa mensal se ativos | **Sem custo** quando não executam |
| **Pipelines com muita execução** | Custo fixo | **Cresce com os minutos** |
| **Ações de aprovação/espera** | Sem custo adicional | Normalmente **não** contam minutos enquanto aguardam (confirmar) |
| **Quando compensa** | Poucos pipelines muito usados | Muitos pipelines pouco usados, ou necessidade dos recursos V2 |

Cálculo didático: 50 pipelines, cada um executando 20 vezes/mês por 6 minutos de ação = `50 × 20 × 6 = 6.000 min` → `6.000 × US$ 0,002 ≈ US$ 12/mês` (V2) vs `49 × US$ 1 ≈ US$ 49/mês` (V1). Já um pipeline com 500 execuções/mês de 20 min (10.000 min) custa ~US$ 20 no V2 vs US$ 1 no V1. **Meça** antes de decidir.

## 9. Migração de V1 para V2

| Passo | Detalhe |
|---|---|
| **1. Avaliar** | Quais recursos V2 você precisa (filtros, variáveis, queued, condições) e o custo |
| **2. Atualizar a definição** | `pipelineType: V2` (+ triggers, variables, executionMode...) via IaC |
| **3. Ajustar gatilhos** | Em V1, `PollForSourceChanges`/eventos; em V2, **triggers** explícitos |
| **4. Testar** | Em ambiente de homologação; verificar modo de execução e filtros |
| **5. Observar** | Comparar duração, execuções e custos |

Atenção: a migração **pode mudar o comportamento** de execução (principalmente gatilhos e modo). Teste.

## 10. Padrões práticos com V2

| Padrão | Configuração |
|---|---|
| **Monorepo por serviço** | Um pipeline por serviço, `filePaths` e `QUEUED` ou `SUPERSEDED` |
| **Promoção por tag** | Gatilho `tags: v*`; variável `VERSAO` = nome da tag; deploy PROD com aprovação |
| **Entrega em produção com janela** | Condição `DeploymentWindow` + `CloudWatchAlarm` na entrada |
| **Rollback seguro** | `onSuccess` observa alarmes por 15 min; se alarmar → `ROLLBACK` |
| **Pipeline parametrizado** | Variáveis `AMBIENTE`, `REGIAO`; um só pipeline para dev/hml/prod (com **aprovações** em prod) |
| **CI de PR** | Gatilho de PR + modo `PARALLEL`; sem estágio de deploy |
| **Releases ordenados** | `QUEUED` para garantir que cada versão passe por todos os estágios em ordem |

## 11. Erros comuns

> [!bug] Erros comuns
> 1. **Manter V1 por inércia** e implementar filtros com scripts frágeis.
> 2. **Modo `PARALLEL` implantando no mesmo ambiente** (corrida entre execuções).
> 3. **Esperar que `SUPERSEDED` implante todos os commits** (substitui intermediários).
> 4. **Filtros de caminho/tag** não suportados pela fonte usada.
> 5. **Segredos em variáveis de pipeline.**
> 6. **Rollback sem artefatos retidos** (S3 lifecycle expirou).
> 7. **Condições de alarme com alarmes ruidosos** (bloqueiam entregas legítimas).
> 8. **Não considerar o custo por minuto** em pipelines muito ativos.
> 9. **Usar Commands para builds pesados** (use CodeBuild).
> 10. **Esquecer janelas e aprovação** para produção.

## 12. Troubleshooting

| Sintoma | Causa provável | Ação |
|---|---|---|
| Pipeline não dispara para o push | Filtros de branch/caminho/tag | Revisar `triggers` e padrões glob |
| Execuções "Superseded" inesperadas | Modo `SUPERSEDED` | Trocar para `QUEUED` |
| Variável de pipeline vazia | Não informada e sem `defaultValue` | Passar `--variables` ou definir padrão |
| Estágio não entra | Condição `beforeEntry` falhou (alarme/variável) | Ver o resultado da regra e o motivo |
| Rollback indisponível | Sem execução bem-sucedida anterior | Garantir histórico e artefatos |
| Fila crescente (QUEUED) | Execuções mais rápidas que o pipeline | Otimizar estágios; limitar gatilhos |
| Custos subiram após migrar para V2 | Muitos minutos de ação | Reduzir ações longas, usar CodeBuild só quando necessário, revisar gatilhos |

## 13. Resumo rápido

- **V2**: **gatilhos** por branch/tag/PR/caminho, **variáveis de pipeline**, **modos** (**SUPERSEDED/QUEUED/PARALLEL**), **condições de estágio** (`beforeEntry/onSuccess/onFailure`), **rollback de estágio** e ação **Commands**.
- **Cobrança por minuto de ação** (vs taxa por pipeline no V1): compare com o uso real.
- Padrões: **monorepo por caminho**, **release por tag**, **pipeline parametrizado**, **janela + alarmes** e **rollback automático**.
- **Cuidados**: paralelismo vs ambientes compartilhados, **artefatos retidos** para rollback, **segredos fora de variáveis** e **compatibilidade de dados**.

### 🧩 Quiz de Fixação

1. Quais filtros de gatilho o V2 oferece?
2. Qual a diferença entre os modos superseded e queued?
3. Para que servem as condições de estágio?
4. O que o rollback de estágio faz?
5. Que risco tem o modo parallel?
6. Quando usar Commands e quando usar CodeBuild?
7. Como difere a cobrança do V1 e do V2?

**Respostas:**

1. Branches, tags, eventos de pull request e caminhos de arquivos (include/exclude), além do início manual.
2. Superseded substitui execuções antigas pela mais recente; queued processa todas em ordem, uma por vez.
3. Controlar entrada, sucesso e falha do estágio (por exemplo, exigir alarmes OK, observar e reverter automaticamente).
4. Reexecuta o estágio com os artefatos da última execução bem-sucedida, sem recompilar.
5. Execuções simultâneas podem colidir ao implantar no mesmo ambiente.
6. Commands para passos pequenos e rápidos; CodeBuild para builds, dependências, testes, VPC e cache.
7. V1 cobra taxa mensal por pipeline ativo; V2 cobra por minuto de execução de ação, com franquia gratuita.
