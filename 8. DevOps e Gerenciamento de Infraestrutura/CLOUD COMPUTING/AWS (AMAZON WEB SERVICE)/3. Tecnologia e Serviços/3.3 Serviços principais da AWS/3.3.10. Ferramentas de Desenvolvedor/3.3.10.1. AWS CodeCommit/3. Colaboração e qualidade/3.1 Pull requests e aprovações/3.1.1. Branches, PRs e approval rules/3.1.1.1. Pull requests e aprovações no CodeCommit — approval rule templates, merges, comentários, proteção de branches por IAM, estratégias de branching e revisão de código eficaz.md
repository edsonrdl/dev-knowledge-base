### 3.1.1.1. Pull requests e aprovações no CodeCommit — approval rule templates, merges, comentários, proteção de branches por IAM, estratégias de branching e revisão de código eficaz

> [!warning] Aviso
> Nomes de ações, estratégias de merge e recursos de aprovação abaixo são **de memória e podem mudar**; **confirme na documentação do CodeCommit**. Comandos e políticas são ilustrativos e não foram executados. O CodeCommit **não impõe** regras de branch como o GitHub (branch protection rules): a proteção é feita por **IAM + approval rules + processo**.

## 1. Por que revisão de código e proteção de branches

A **revisão de código** (code review) é a barreira que impede bugs, vulnerabilidades e segredos de chegarem à produção. Em times maduros, **nenhuma mudança entra na `main` sem pelo menos uma aprovação** e **testes passando**. O CodeCommit oferece a base para isso: **pull requests (PRs)**, **comentários**, **approval rules**, **merges controlados** e **eventos** que disparam validações automáticas.

```
feature/x ──push──▶ Pull Request ──▶ [CI roda testes] ──▶ [N aprovações] ──▶ Merge na main ──▶ Deploy
                         │
                    comentários, revisão, requisitos
```

## 2. Pull requests no CodeCommit

Um **PR** propõe mesclar a **branch de origem** (source) na **branch de destino** (destination). Ele reúne:

| Elemento | Descrição |
|---|---|
| **Título e descrição** | Contexto, motivação, como testar |
| **Diff e commits** | Alterações linha a linha |
| **Comentários** | Gerais, por arquivo ou por linha, com threads |
| **Reações** | Emojis de feedback |
| **Aprovações** | Estado de aprovação dos revisores |
| **Status de merge** | Mesclável, conflitos, regras não atendidas |
| **Eventos** | Criação, atualização, comentários, merge → EventBridge/notificações |

```bash
aws codecommit create-pull-request \
  --title "feat: pagamento via PIX" \
  --description "Implementa PIX. Testes: make test. Risco: médio (gateway externo)." \
  --targets repositoryName=pagamentos-api,sourceReference=feature/pix,destinationReference=main

aws codecommit get-pull-request --pull-request-id 12
aws codecommit post-comment-for-pull-request --pull-request-id 12 --repository-name pagamentos-api \
  --before-commit-id <sha_destino> --after-commit-id <sha_origem> \
  --content "Podemos extrair essa validação para um serviço?" \
  --location filePath=src/pix.py,filePosition=48,relativeFileVersion=AFTER
```

## 3. Approval rules (regras de aprovação)

Uma **approval rule** define **quantas aprovações** de **quais aprovadores** são necessárias antes do merge.

| Conceito | Detalhe |
|---|---|
| **Aprovadores** | Usuários/roles IAM, **ou um grupo via padrão** (ex.: `arn:aws:sts::123456789012:assumed-role/Reviewers/*`) |
| **Número de aprovações** | `NumberOfApprovalsNeeded` |
| **Pool de aprovadores** | `ApprovalPoolMembers` define quem conta |
| **Regra por PR** | Criada num PR específico |
| **Approval rule template** | **Modelo reutilizável** aplicado **automaticamente** a **todos os PRs** de repositórios associados (e filtrado por **branch de destino**) |
| **Override** | Quem tem permissão pode **ignorar** a regra (sujeito a IAM); auditável |
| **Revogação de aprovação** | Mudanças no código podem **invalidar** aprovações (conforme configuração/uso) |

Template exemplo (ilustrativo):

```bash
aws codecommit create-approval-rule-template \
  --approval-rule-template-name "duas-aprovacoes-main" \
  --approval-rule-template-description "Exige 2 aprovações de revisores em PRs para main" \
  --approval-rule-template-content '{
    "Version": "2018-11-08",
    "DestinationReferences": ["refs/heads/main"],
    "Statements": [{
      "Type": "Approvers",
      "NumberOfApprovalsNeeded": 2,
      "ApprovalPoolMembers": ["arn:aws:sts::123456789012:assumed-role/Revisores/*"]
    }]
  }'

aws codecommit associate-approval-rule-template-with-repository \
  --approval-rule-template-name duas-aprovacoes-main --repository-name pagamentos-api
```

Boas práticas:

- **Dois revisores** em código sensível (pagamentos, IAM); **um** em demais.
- **Pool de revisores** como **role/grupo** (não pessoas) para escalar e delegar.
- **Autor não aprova o próprio PR** (use `ApprovalPoolMembers` que exclua ou revise a política de merge por IAM).
- Template **por branch de destino** (`main`, `release/*`).

## 4. Merges

Opções de **merge** disponíveis no CodeCommit:

| Estratégia | Efeito | Quando usar |
|---|---|---|
| **Fast-forward** | Apenas avança a ponteiro (histórico linear, sem merge commit) | Branches curtas e sem divergência |
| **Squash** | Condensa todos os commits em **um** na destino | Histórico limpo, PRs pequenos |
| **Three-way (merge commit)** | Cria um commit de merge | Preservar o histórico completo da feature |

```bash
aws codecommit merge-pull-request-by-squash --pull-request-id 12 --repository-name pagamentos-api \
  --commit-message "feat: pagamento via PIX (#12)" --author-name "Maria" --email maria@empresa.com
```

Conflitos: o console e a CLI detectam conflitos; em geral, resolva **localmente** (rebase/merge) e envie de novo. A **branch fonte pode ser excluída** após o merge (opcional).

## 5. Proteção de branches por IAM

Como o CodeCommit não tem "branch protection rules", usa-se **IAM** para impedir **pushes diretos** e **exclusões** em branches críticas:

```json
{
  "Effect": "Deny",
  "Action": ["codecommit:GitPush", "codecommit:DeleteBranch", "codecommit:PutFile",
             "codecommit:MergeBranchesByFastForward", "codecommit:MergeBranchesBySquash",
             "codecommit:MergeBranchesByThreeWay"],
  "Resource": "arn:aws:codecommit:us-east-1:123456789012:pagamentos-*",
  "Condition": {
    "StringEqualsIfExists": { "codecommit:References": ["refs/heads/main", "refs/heads/release/*"] },
    "Null": { "codecommit:References": "false" }
  }
}
```

E uma política **Allow** para o **merge de PRs** (`MergePullRequestBy*`) apenas para a **role de maintainers/automação**:

```json
{ "Effect": "Allow",
  "Action": ["codecommit:MergePullRequestByFastForward", "codecommit:MergePullRequestBySquash", "codecommit:MergePullRequestByThreeWay"],
  "Resource": "arn:aws:codecommit:us-east-1:123456789012:pagamentos-*" }
```

Combine: **Deny** de push direto + **approval rules obrigatórias** + **merge** somente via PR por role de maintainer. Atenção: um **administrador com permissões amplas** pode burlar — use **SCP/permission boundary** em contas críticas e **audite** com CloudTrail.

## 6. Estratégias de branching

| Estratégia | Como funciona | Quando usar |
|---|---|---|
| **Trunk-based** | Branches **muito curtas**, merge frequente em `main`, feature flags | Times com CI forte, entrega contínua |
| **GitHub Flow** | `main` sempre implantável; feature branch → PR → merge → deploy | Aplicações web, SaaS |
| **Git Flow** | `main`, `develop`, `feature/*`, `release/*`, `hotfix/*` | Releases versionados, múltiplos ambientes |
| **Release branches** | `release/1.4` mantida para correções | Produtos com versões suportadas |
| **Ambiente por branch** | `dev`, `hml`, `prod` | **Desencorajado**: acopla código a ambiente (prefira artefatos e config por ambiente) |

Convenções úteis: nomes `feature/…`, `bugfix/…`, `hotfix/…`; **mensagens de commit padronizadas** (Conventional Commits) para automação de changelog/versionamento semântico.

## 7. Revisão de código eficaz

| Prática | Benefício |
|---|---|
| **PRs pequenos** (< 400 linhas) | Revisão mais rápida e profunda |
| **Descrição clara** (o quê, por quê, como testar, riscos) | Contexto |
| **CI verde antes da revisão** | Foco no design, não em lint |
| **Checklist** (segurança, testes, observabilidade, migrações) | Consistência |
| **Revisão em até 1 dia útil** (SLA do time) | Fluxo contínuo |
| **Comentários construtivos** (pergunta > ordem) | Cultura saudável |
| **Separar refatoração de funcionalidade** | Diff compreensível |
| **Automatizar o que é automatizável** (lint, formatação, SAST, testes) | Revisores humanos no que importa |

## 8. CI no ciclo do PR (padrão)

```
PR criado/atualizado ──▶ EventBridge ──▶ CodeBuild (testes, lint, SAST, cfn-lint, terraform validate)
                                   │
                                   └─▶ resultado volta ao PR como COMENTÁRIO (via Lambda/ação do CodeBuild) 
Aprovações satisfeitas + CI ok ──▶ Merge (role maintainer) ──▶ Evento em main ──▶ CodePipeline (deploy)
```

Dica: use **comentários automáticos** no PR com o **resultado do build** e links de relatório; considere um **gate** no pipeline que verifica "build do PR passou" antes do merge.

## 8.1 Exemplo de política de processo (modelo para o time)

| Regra | Valor sugerido | Como é imposto |
|---|---|---|
| **Aprovações mínimas** | 1 (código comum) · 2 (pagamentos, IAM, infraestrutura) | Approval rule template por branch de destino |
| **Quem aprova** | Role `Revisores` (nunca o autor) | `ApprovalPoolMembers` + revisão da política de merge |
| **Push direto na `main`** | Proibido | IAM `Deny` por `codecommit:References` |
| **Quem faz merge** | Role `Maintainers` ou automação após CI verde | `MergePullRequestBy*` só para essa role |
| **CI obrigatório** | Testes, lint, SAST e validação de IaC passando | Bot de CI aprova/revoga o PR via CodeBuild + Lambda |
| **Tamanho do PR** | Até ~400 linhas; acima disso, dividir | Convenção do time e comentário automático de aviso |
| **Prazo de revisão** | Primeira resposta em até 1 dia útil | Métrica acompanhada (tempo até a primeira revisão) |
| **Hotfix** | Branch `hotfix/*` com PR expresso e 1 aprovação + registro posterior | Template específico para `hotfix/*` |

Esse conjunto evita os dois extremos: **burocracia que atrasa tudo** e **liberdade que derruba a produção**. Revise os números a cada trimestre com base nas métricas do time (tempo de revisão, taxa de retrabalho e incidentes causados por mudanças).

## 9. Erros comuns

> [!bug] Erros comuns
> 1. **Confiar em "convenção" sem bloquear push direto na `main`** (alguém sempre quebra).
> 2. **Approval rule sem pool definido**, ou com o autor podendo aprovar o próprio PR.
> 3. **PRs gigantes** que ninguém revisa de verdade.
> 4. **Aprovar sem testes/CI**.
> 5. **Branch longa** que diverge meses e vira conflito.
> 6. **Merge commits sem padrão** poluindo o histórico.
> 7. **Ambientes como branches** (`prod`/`hml`) divergindo do código real.
> 8. **Permissões de merge dadas a todos.**
> 9. **Não auditar overrides** das regras de aprovação.
> 10. **Segredos em commits** passando pela revisão humana (use scanner automático).

## 10. Troubleshooting

| Sintoma | Causa provável | Ação |
|---|---|---|
| Não consigo mesclar o PR | Regras de aprovação não satisfeitas ou conflitos | Ver `get-pull-request-approval-states` e `evaluate-pull-request-approval-rules` |
| Aprovador não conta | Fora do `ApprovalPoolMembers` | Ajustar o padrão do pool |
| Template não aplica | Repositório não associado ou branch de destino diferente | Associar o template e conferir `DestinationReferences` |
| Push direto passou | Política Deny ausente/escopo errado | Revisar `codecommit:References` e policies de quem tem acesso amplo |
| Conflito no PR | Divergência com a destino | Rebase/merge localmente e reenviar |
| Merge negado por IAM | Falta de `MergePullRequestBy*` | Usar a role de maintainer |
| Sem notificações de PR | Regra de notificação/EventBridge não criada | Configurar notification rule/EventBridge |

## 11. Resumo rápido

- **PRs** + **approval rules (templates)** + **merge controlado** formam o fluxo de revisão; o CodeCommit **não tem branch protection nativa**.
- **Proteja `main`** com **IAM Deny** (`GitPush`, `DeleteBranch`, `Merge*`) por `codecommit:References` e permita **merge por PR** só a maintainers/automação.
- Escolha **branching** (trunk-based, GitHub Flow, Git Flow) conforme o ritmo de entrega; **evite ambiente-por-branch**.
- **PRs pequenos, CI verde, checklist e SLA de revisão** elevam a qualidade.
- Automatize **testes e SAST** no ciclo do PR via **EventBridge + CodeBuild**.

### 🧩 Quiz de Fixação

1. O que é uma approval rule template?
2. Como impedir push direto na main no CodeCommit?
3. Quais as estratégias de merge disponíveis?
4. Qual a diferença entre trunk-based e Git Flow?
5. Que risco tem usar branches por ambiente?
6. Como integrar testes automáticos ao PR?
7. Por que PRs pequenos?

**Respostas:**

1. Modelo reutilizável que aplica automaticamente regras de aprovação (número e pool de aprovadores) a PRs de repositórios associados, por branch de destino.
2. Com política IAM Deny em GitPush/DeleteBranch/Merge* usando a condição codecommit:References, junto a approval rules e merge via PR.
3. Fast-forward, squash e three-way (merge commit).
4. Trunk-based usa branches muito curtas e merge frequente em main; Git Flow usa main, develop, feature, release e hotfix.
5. O código diverge entre ambientes, dificultando reprodutibilidade; prefira artefatos únicos e configuração por ambiente.
6. Evento do PR no EventBridge dispara CodeBuild; o resultado volta como comentário e funciona como gate antes do merge.
7. Revisão mais rápida e profunda, menos conflitos e menor risco por mudança.
