### 5.1.1.1. Segurança do CodeCommit — IAM granular, ABAC por tags, KMS, CloudTrail, detecção de segredos, SCPs, conformidade e hardening do repositório

> [!warning] Aviso
> Políticas IAM, SCPs, chaves de condição e comandos abaixo são **ilustrativos, de memória e não foram executados**. Teste com o **IAM Policy Simulator** e em ambiente não produtivo antes de aplicar a contas reais. **Confirme na documentação** as ações e condições atuais (`codecommit:*`). Código-fonte é **ativo crítico**: um vazamento expõe lógica, segredos e superfície de ataque.

## 1. Por que o repositório é alvo

O repositório contém **lógica de negócio, configuração de infraestrutura e, às vezes, segredos esquecidos**. Um atacante com acesso de leitura mapeia vulnerabilidades; com acesso de escrita, pode **inserir backdoors** (ataque de cadeia de suprimentos). A segurança do CodeCommit cobre **quem acessa**, **o que pode fazer**, **como o dado é protegido** e **como auditar**.

```
 Camadas:  [Identidade IAM/SSO + MFA]  →  [Permissões mínimas por repo/branch]
           →  [Fluxo de PR + approval rules]  →  [Criptografia KMS + TLS]
           →  [Auditoria CloudTrail + alertas]  →  [Prevenção de segredos]
```

## 2. Identidade e autenticação

| Prática | Detalhe |
|---|---|
| **SSO (IAM Identity Center) + roles** | Desenvolvedores entram por **permission sets**; credenciais **temporárias** |
| **MFA** obrigatório | Condição `aws:MultiFactorAuthPresent` para ações sensíveis |
| **Sem usuários IAM de longo prazo** | Evite HTTPS Git credentials e chaves SSH estáticas |
| **GRC (git-remote-codecommit)** | Usa a sessão AWS atual |
| **Roles para automação** | Pipelines/CodeBuild/Lambdas com **roles de serviço**, não usuários |
| **Federação** | IdP corporativo (SAML/OIDC) com desprovisionamento automático |
| **Revisão periódica** | Remover acessos de quem mudou de função (access reviews) |

## 3. Autorização granular

### 3.1 Princípio do menor privilégio por perfil

| Perfil | Permissões típicas |
|---|---|
| **Leitor** | `GitPull`, `GetRepository`, `GetBranch`, `GetCommit`, `BatchGet*`, `ListBranches` |
| **Desenvolvedor** | Leitor + `GitPush` (branches não protegidas), `CreateBranch`, `CreatePullRequest`, comentários |
| **Revisor** | Leitor + `UpdatePullRequestApprovalState`, comentários |
| **Maintainer/Release** | Desenvolvedor + `MergePullRequestBy*` em branches protegidas |
| **Admin de repositório** | `CreateRepository`, `DeleteRepository`, triggers, approval templates, KMS |
| **Automação (CI/CD)** | Role mínima: `GitPull` e, se necessário, ações específicas (comentar, aprovar como bot) |

### 3.2 Restrições por recurso e por branch

```json
{
  "Sid": "SomenteReposDoTime",
  "Effect": "Allow",
  "Action": ["codecommit:GitPull", "codecommit:GitPush"],
  "Resource": "arn:aws:codecommit:*:123456789012:checkout-*"
}
```

E a proteção de branches (já vista) com `codecommit:References` para impedir push/merge/exclusão em `main`/`release/*`.

### 3.3 ABAC (controle por atributos/tags)

Use **tags** no repositório e no principal para escalar políticas:

```json
{
  "Effect": "Allow",
  "Action": ["codecommit:GitPull", "codecommit:GitPush", "codecommit:CreatePullRequest"],
  "Resource": "*",
  "Condition": { "StringEquals": { "aws:ResourceTag/equipe": "${aws:PrincipalTag/equipe}" } }
}
```

Assim, **uma política serve a todas as equipes**: cada pessoa só alcança repositórios com a **mesma tag `equipe`**. Exija tags na criação de repositórios (condição `aws:RequestTag`) e **proteja a edição de tags** (para que ninguém reclassifique repositórios para ganhar acesso).

### 3.4 Condições adicionais úteis

| Condição | Uso |
|---|---|
| `aws:MultiFactorAuthPresent` | Exigir MFA em ações destrutivas |
| `aws:SourceVpce` / `aws:SourceVpc` | Limitar a acesso por **rede privada** |
| `aws:SourceIp` | Restringir a redes corporativas |
| `aws:PrincipalOrgID` | Restringir a contas da organização |
| `aws:RequestedRegion` (SCP) | Impedir uso em regiões não aprovadas |
| `aws:CurrentTime` | Janelas de acesso (casos especiais) |

## 4. Criptografia

| Camada | Mecanismo |
|---|---|
| **Em trânsito** | **TLS (HTTPS)** ou **SSH** |
| **Em repouso** | **AWS KMS**: chave **gerenciada pela AWS** (`aws/codecommit`) ou **chave do cliente (CMK)** |
| **Criptografia de blob** | O CodeCommit usa **criptografia de envelope** com chaves de dados por repositório |
| **Acesso à chave** | Quem usa o repositório precisa de **permissão implícita** via CodeCommit; a **key policy** deve permitir o serviço atuar |

Boas práticas:

- Para **dados regulados**, use **CMK** com **rotação** e **key policy** restrita; monitore `kms:Decrypt` no CloudTrail.
- **Chaves separadas** por domínio (produto/classificação) para limitar o raio de impacto.
- Em **cross-account**, a chave e as roles precisam permitir o acesso da conta externa.
- Planeje a **troca de chave** (`update-repository-encryption-key`) com testes.

```bash
aws codecommit update-repository-encryption-key --repository-name pagamentos-api \
  --kms-key-id arn:aws:kms:us-east-1:123456789012:key/abcd1234-...
```

## 5. Auditoria e detecção

### 5.1 CloudTrail

O CloudTrail registra **chamadas de API** do CodeCommit (criação de repositório, PRs, merges, alterações de regras, atualização de chave, etc.). **Operações Git (clone/push) aparecem como `GitPull`/`GitPush`** com metadados do principal e do repositório. Monitore:

| Evento | Risco |
|---|---|
| `DeleteRepository`, `DeleteBranch` | Destruição de código |
| `UpdateRepositoryEncryptionKey` | Alteração criptográfica |
| `PutRepositoryTriggers` | Exfiltração via trigger/SNS/Lambda |
| `OverridePullRequestApprovalRules`, `DeleteApprovalRuleTemplate` | Burla de revisão |
| `GitPush` em branches protegidas (negados e permitidos) | Tentativa de bypass |
| `GetRepository`/`GitPull` fora do padrão (volume/horário/IP) | Exfiltração |
| `CreateApprovalRuleTemplate`, mudanças de políticas IAM | Mudança de governança |

Use **EventBridge + SNS/Chatbot** para alertas imediatos e **CloudTrail Lake/Athena** para investigação.

### 5.2 AWS Config e Security Hub

Regras do **AWS Config** (customizadas) para verificar: repositórios **sem CMK**, **sem tags obrigatórias**, **sem approval template associado**; **Security Hub** consolida achados e padrões.

## 6. Prevenção de segredos no código

Segredos em repositório (chaves de acesso, senhas, tokens) são a **causa nº 1 de incidentes**. Defesa em camadas:

| Camada | Ferramenta/prática |
|---|---|
| **Local (pré-commit)** | `git-secrets`, `gitleaks`, `detect-secrets`; hooks obrigatórios no template do projeto |
| **No PR (CI)** | CodeBuild executa scanner e **bloqueia** com falha/aprovação negativa do bot |
| **Análise do histórico** | Escanear o **histórico completo** periodicamente |
| **Amazon CodeGuru Security / Q** | Detecção de segredos e vulnerabilidades em código (confirmar disponibilidade) |
| **Resposta** | Se vazar: **revogar/rotacionar** o segredo **primeiro**, depois limpar o histórico (`git filter-repo`/BFG) — assumir que **já foi exposto** |
| **Prevenção** | Segredos no **Secrets Manager/Parameter Store**; **roles** em vez de chaves; variáveis do CI |
| **Detecção na AWS** | A AWS detecta chaves expostas em repositórios **públicos**, não em privados: não conte com isso |

> [!warning] Importante
> Um repositório **privado** não é cofre. Pessoas com acesso, clones locais, forks e backups multiplicam a exposição. **Nunca** versionar segredos.

## 7. Governança multi-conta (SCPs)

Exemplos de **SCPs** para contas de produção/ferramentas:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    { "Sid": "ProtegerRepositorios", "Effect": "Deny",
      "Action": ["codecommit:DeleteRepository", "codecommit:UpdateRepositoryEncryptionKey"],
      "Resource": "*",
      "Condition": { "StringNotLike": { "aws:PrincipalArn": "arn:aws:iam::*:role/AdminPlataforma" } } },
    { "Sid": "ExigirTLS", "Effect": "Deny", "Action": "codecommit:*", "Resource": "*",
      "Condition": { "Bool": { "aws:SecureTransport": "false" } } },
    { "Sid": "RegioesAprovadas", "Effect": "Deny", "Action": "codecommit:*", "Resource": "*",
      "Condition": { "StringNotEquals": { "aws:RequestedRegion": ["us-east-1", "sa-east-1"] } } }
  ]
}
```

Combine com **permission boundaries** para limitar o que desenvolvedores conseguem **conceder** a si mesmos.

## 8. Segurança da cadeia de suprimentos (visão ampliada)

| Risco | Controle |
|---|---|
| **Commits maliciosos** | Approval rules, revisão por código sensível (**CODEOWNERS** via convenção/bot), PRs obrigatórios |
| **Commits falsificados** | **Assinatura de commits** (GPG/SSH) verificada no CI |
| **Dependências comprometidas** | **CodeArtifact**, `npm audit`/`pip-audit`, SCA, lockfiles, SBOM |
| **Pipelines adulterados** | Arquivos de pipeline em repositório **protegido**; revisão rigorosa de `buildspec`/`pipeline` |
| **Acesso excessivo de CI** | Roles mínimas; **sem credenciais de longo prazo** |
| **Artefatos** | Assinar e verificar (AWS Signer, Sigstore); repositórios de artefatos privados |
| **Exfiltração** | Alarmes de `GitPull` anormal; **rede privada** |

## 9. Conformidade

| Requisito | Como o CodeCommit ajuda |
|---|---|
| **Controle de acesso** (ISO 27001, SOC 2, PCI) | IAM, MFA, SSO, revisões de acesso |
| **Segregação de funções** | Approval rules, merge por maintainers, branch protection por IAM |
| **Criptografia** | KMS + TLS |
| **Auditoria e trilha** | CloudTrail, histórico Git imutável (commits), retenção de logs |
| **Residência de dados** | Região escolhida |
| **Continuidade** | Replicação interna em múltiplas AZs; **espelhamento/backup** adicionais para DR |
| **Gestão de mudanças** | PRs e aprovações como evidência |

Use o **AWS Artifact** para relatórios de conformidade do serviço e guarde **evidências** (políticas, logs, revisões de acesso).

## 10. Checklist de hardening

1. **SSO + roles**, MFA, **sem credenciais estáticas**.
2. **Menor privilégio** por perfil e **ABAC por tags**.
3. **Proteção de branches** (IAM Deny + approval rules + merge por maintainer).
4. **CMK KMS** (dados sensíveis) e **TLS obrigatório** (SCP).
5. **CloudTrail** com alertas (DeleteRepository, overrides, triggers, pushes negados).
6. **Scanners de segredos** (pré-commit + PR + histórico).
7. **VPC endpoints** e restrição por `aws:SourceVpce` (ambientes sensíveis).
8. **SCPs** (exclusão, região, chave).
9. **Espelho/backup** de repositórios críticos.
10. **Revisões de acesso** trimestrais e **testes de resposta a incidentes** (vazamento de segredo).

## 11. Erros comuns

> [!bug] Erros comuns
> 1. **Segredos no código** achando que "é privado".
> 2. **Credenciais de longo prazo** (chaves/senhas Git/SSH) para pessoas e CI.
> 3. **Allow amplo (`codecommit:*`)** sem proteção de branches.
> 4. **Sem MFA** para ações sensíveis.
> 5. **Chave KMS sem controle** ou compartilhada por tudo.
> 6. **Não monitorar** `DeleteRepository`, overrides e triggers.
> 7. **Triggers/Lambda com permissões amplas** (vetor de exfiltração).
> 8. **Arquivos de pipeline editáveis sem revisão.**
> 9. **Limpar o histórico sem revogar o segredo** (já exposto).
> 10. **Não revisar acessos** de quem saiu/mudou de time.

## 12. Troubleshooting

| Sintoma | Causa provável | Ação |
|---|---|---|
| `AccessDenied` ao push | Condição `Deny`/falta de permissão/MFA | Ler a mensagem, ajustar a política/usar PR |
| `KMS` negado ao acessar | Key policy não permite o serviço/principal | Ajustar a key policy e as roles |
| ABAC não funciona | Tag ausente/diferente no repo ou principal | Padronizar tags e `PrincipalTag` (sessão SSO) |
| Alerta de pushes negados | Tentativas de bypass | Investigar CloudTrail (quem/de onde) |
| Segredo identificado no histórico | Commit antigo | Rotacionar, limpar histórico, comunicar |
| Cross-account falha | Trust/KMS entre contas | Revisar roles e permissões de chave |

## 13. Resumo rápido

- **SSO + roles + MFA**, sem credenciais estáticas; **menor privilégio** e **ABAC** por tags.
- **Proteja branches** por IAM (`codecommit:References`) + approval rules; **merge** por maintainers.
- **KMS** (CMK p/ dados sensíveis) + **TLS obrigatório**; **CloudTrail** com alertas; **SCPs** de proteção.
- **Segredos**: prevenir (pré-commit/CI/histórico) e, se vazar, **rotacionar primeiro**.
- Cadeia de suprimentos: **assinatura de commits**, **CodeArtifact/SCA**, **pipelines revisados**.
- Conformidade: evidências via IAM, PRs, CloudTrail e Artifact.

### 🧩 Quiz de Fixação

1. Como o ABAC por tags simplifica as políticas do CodeCommit?
2. Que condição restringe ações por branch?
3. Qual a primeira ação ao detectar um segredo no histórico?
4. Que eventos do CloudTrail monitorar com prioridade?
5. Como impor TLS em todas as chamadas?
6. Para que serve o `aws:SourceVpce`?
7. Por que um repositório privado não é um cofre de segredos?

**Respostas:**

1. Uma única política compara a tag do recurso com a do principal (aws:ResourceTag vs aws:PrincipalTag), servindo a todas as equipes.
2. `codecommit:References`.
3. Revogar/rotacionar o segredo (assumir que já foi exposto) e só então limpar o histórico.
4. DeleteRepository, DeleteBranch, UpdateRepositoryEncryptionKey, PutRepositoryTriggers, overrides de aprovação e pushes negados/atípicos.
5. Com SCP/política negando quando `aws:SecureTransport` é false.
6. Limitar o acesso a chamadas que passam por um VPC endpoint específico (rede privada).
7. Porque pessoas com acesso, clones, forks e backups multiplicam a exposição e o histórico guarda o segredo.
