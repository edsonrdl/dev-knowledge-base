### 4.1.1.1. Automação com CodeCommit — triggers, regras de notificação, EventBridge, integração com CodePipeline, CodeBuild e Lambda e padrões de CI a partir de commits e pull requests

> [!warning] Aviso
> Nomes de eventos, formatos de payload e limites abaixo são **de memória e podem mudar**; **confirme na documentação** (eventos do CodeCommit no EventBridge, regras de notificação). Código, JSONs e CLI são ilustrativos e não foram executados. Automação mal desenhada gera **loops** (um commit dispara pipeline que faz commit) e **custos**.

## 1. Por que automatizar a partir do repositório

Um repositório de código é o **gatilho natural** do ciclo de entrega: cada **push**, **PR** ou **comentário** é um evento que pode disparar **testes, análises, notificações e deploys**. Sem automação, a qualidade depende da disciplina humana ("lembrei de rodar os testes?"). Com ela, o **repositório vira o ponto de controle**: nada é mesclado sem validação, e cada merge em `main` segue um caminho de entrega reproduzível.

O CodeCommit expõe **três mecanismos** de automação:

| Mecanismo | O que faz | Quando usar |
|---|---|---|
| **Triggers do repositório** | Envia **SNS** ou invoca **Lambda** em eventos de Git (push, create/delete branch) | Casos simples e legados |
| **Regras de notificação** | Envia notificações (SNS/Chatbot) para eventos de commit, PR, comentário, aprovação | **Avisar pessoas/canais** |
| **Amazon EventBridge** | Publica **eventos de estado** do repositório e dos PRs; regras roteiam para qualquer alvo | **Padrão moderno** para CI/CD e automações |

## 2. Triggers do repositório

Configurados por repositório (até **10 triggers**), disparam em: **todos os eventos**, **push em branches existentes**, **criação de branch/tag**, **exclusão de branch/tag**. Destinos: **SNS** ou **Lambda**.

```bash
aws codecommit put-repository-triggers --repository-name pagamentos-api --triggers '[
  { "name": "notifica-push",
    "destinationArn": "arn:aws:sns:us-east-1:123456789012:push-pagamentos",
    "branches": ["main"],
    "events": ["updateReference"] }
]'
```

Limitações: sem filtros ricos (por caminho/arquivo), menos flexível que EventBridge, sem retentativas controladas. **Use triggers só para integrações simples** e prefira o EventBridge nos demais casos.

## 3. Regras de notificação

As **notification rules** (AWS Developer Tools Notifications) enviam mensagens a **SNS topics** ou **AWS Chatbot** (Slack/Microsoft Teams) para eventos como:

| Categoria | Exemplos de eventos |
|---|---|
| **Commits/branches** | Comentário em commit, branch criada/atualizada/excluída |
| **Pull requests** | Criada, atualizada, mesclada, fechada, comentário, aprovação, regra de aprovação alterada/excedida |

```bash
aws codestar-notifications create-notification-rule \
  --name pr-pagamentos \
  --resource arn:aws:codecommit:us-east-1:123456789012:pagamentos-api \
  --detail-type FULL \
  --event-type-ids codecommit-repository-pull-request-created codecommit-repository-pull-request-merged \
  --targets TargetType=AWSChatbotSlack,TargetAddress=arn:aws:chatbot::123456789012:chat-configuration/slack-channel/pagamentos
```

Valor: **visibilidade da revisão** ("PR aguardando você") e **alertas de merge** em canais da equipe.

## 4. Amazon EventBridge — a base da automação

O CodeCommit publica eventos no **barramento padrão** do EventBridge, com `source: aws.codecommit`:

| `detail-type` | Quando |
|---|---|
| **CodeCommit Repository State Change** | Push (referência criada/atualizada/excluída), mudança de repositório |
| **CodeCommit Pull Request State Change** | PR criado, atualizado (novos commits), mesclado, fechado |
| **CodeCommit Comment on Commit / on Pull Request** | Comentário |
| **CodeCommit Approval State Change / Approval Rule Override** | Aprovação concedida/retirada, regra sobrescrita |

Exemplo de regra: **push na `main`** dispara um pipeline:

```json
{
  "source": ["aws.codecommit"],
  "detail-type": ["CodeCommit Repository State Change"],
  "resources": ["arn:aws:codecommit:us-east-1:123456789012:pagamentos-api"],
  "detail": {
    "event": ["referenceCreated", "referenceUpdated"],
    "referenceType": ["branch"],
    "referenceName": ["main"]
  }
}
```

Alvos típicos: **CodePipeline** (`StartPipelineExecution`), **CodeBuild** (`StartBuild`), **Lambda**, **Step Functions**, **SNS/SQS**, **API destinations** (webhooks externos).

Evento de **PR criado/atualizado** para **CI de validação**:

```json
{
  "source": ["aws.codecommit"],
  "detail-type": ["CodeCommit Pull Request State Change"],
  "detail": { "event": ["pullRequestCreated", "pullRequestSourceBranchUpdated"] }
}
```

O alvo (CodeBuild) usa **input transformer** para passar `pullRequestId`, `sourceCommit`, `destinationCommit`, `repositoryNames`.

## 5. Padrão: CI de PR com CodeBuild e retorno ao PR

```
Dev abre/atualiza PR
      │  evento pullRequestCreated / pullRequestSourceBranchUpdated
      ▼
EventBridge ──▶ CodeBuild (checkout do commit de origem; testes, lint, SAST, validação de IaC)
      │                       │
      │                       └─ resultado (sucesso/falha) ──▶ EventBridge (CodeBuild State Change)
      ▼                                                          │
   Lambda "comentador" ◀─────────────────────────────────────────┘
      └─ post-comment-for-pull-request com resultado e link do relatório
         + atualiza o ESTADO DE APROVAÇÃO (update-pull-request-approval-state)  [bot revisor]
```

**Bot revisor:** uma role de automação que **aprova** o PR quando o build passa, contando para a **approval rule** (por exemplo, a regra exige "1 aprovação humana + 1 do bot"). Exemplo Lambda (esqueleto):

```python
import boto3, json
cc = boto3.client("codecommit")
def handler(event, ctx):
    d = event["detail"]            # evento do CodeBuild com variáveis do PR
    pr = d["additional-information"]["environment"]["environment-variables"]
    pr_id = next(v["value"] for v in pr if v["name"] == "PR_ID")
    repo  = next(v["value"] for v in pr if v["name"] == "REPO")
    revision = next(v["value"] for v in pr if v["name"] == "REVISION_ID")
    ok = d["build-status"] == "SUCCEEDED"
    cc.post_comment_for_pull_request(pullRequestId=pr_id, repositoryName=repo,
        beforeCommitId=next(v["value"] for v in pr if v["name"]=="DEST_COMMIT"),
        afterCommitId=next(v["value"] for v in pr if v["name"]=="SRC_COMMIT"),
        content=("✅ Build passou" if ok else "❌ Build falhou") + f" — {d['additional-information']['logs']['deep-link']}")
    cc.update_pull_request_approval_state(pullRequestId=pr_id, revisionId=revision,
        approvalState="APPROVE" if ok else "REVOKE")
```

## 6. Padrão: entrega contínua em `main`

```
Merge em main ──▶ EventBridge (referenceUpdated main) ──▶ CodePipeline
     Source (CodeCommit) → Build (CodeBuild) → Testes → Deploy HML (CodeDeploy/CloudFormation) 
     → Aprovação manual → Deploy PROD (canary/linear) → alarme CloudWatch → rollback automático
```

Notas: o **CodePipeline** com origem CodeCommit usa, por padrão, **EventBridge** para detectar mudanças (em vez de *polling*), com **menor latência** e custo. Garanta que a regra EventBridge criada exista (o console cria automaticamente; **IaC** precisa declarar).

## 7. Padrão: checagens de governança

| Automação | Evento | Ação |
|---|---|---|
| **Scanner de segredos** | `referenceUpdated` / PR | CodeBuild roda `gitleaks`; falha bloqueia |
| **Validação de IaC** | PR | `cfn-lint`, `cfn-guard`, `terraform validate/plan`, `checkov` |
| **Verificar branch name/commit message** | PR | Lambda valida convenções |
| **Notificar segurança** em mudanças de arquivos sensíveis | push | Lambda inspeciona o diff (`get-differences`) |
| **Sincronizar espelho** (GitHub/S3/outra região) | push em main | CodeBuild `git push --mirror` |
| **Atualizar tickets** (Jira) | PR | API destination com o ID do ticket no título |
| **Métricas DORA** | merge/deploy | Lambda grava lead time e frequência |

## 8. Evitando loops e armadilhas

| Risco | Mitigação |
|---|---|
| **Loop commit→pipeline→commit** (bot que comita no mesmo repo) | Filtrar o autor/branch do bot na regra, ou usar `[skip ci]` via convenção na mensagem |
| **Tempestade de eventos** em muitas branches | Filtrar por `referenceName` |
| **Execuções simultâneas** do pipeline | Configurar **modo de execução** (queued/parallel) do CodePipeline |
| **Custo de builds** em cada push de feature | Rodar CI completo só em PR/main; testes rápidos em feature |
| **Segredos no build** | Variáveis do CodeBuild do **Secrets Manager/Parameter Store** |
| **Permissões amplas** nos alvos | Roles mínimas por regra/alvo |
| **Dependência de uma região** | Regras EventBridge e recursos na **mesma região** do repositório |

## 9. IaC (esqueleto de regra EventBridge → CodePipeline)

```yaml
Resources:
  RegraMain:
    Type: AWS::Events::Rule
    Properties:
      EventPattern:
        source: [aws.codecommit]
        detail-type: [CodeCommit Repository State Change]
        resources: [!Sub "arn:aws:codecommit:${AWS::Region}:${AWS::AccountId}:pagamentos-api"]
        detail: { event: [referenceCreated, referenceUpdated], referenceName: [main] }
      Targets:
        - Arn: !Sub "arn:aws:codepipeline:${AWS::Region}:${AWS::AccountId}:${Pipeline}"
          RoleArn: !GetAtt RoleEventos.Arn
          Id: pipeline-main
```

A role do EventBridge precisa de `codepipeline:StartPipelineExecution` na pipeline alvo.

## 9.1 Comparativo: qual mecanismo escolher

| Necessidade | Triggers | Notificações | EventBridge |
|---|---|---|---|
| Avisar uma pessoa/canal sobre PR ou merge | Possível (SNS), sem formatação | **Ideal** (Chatbot Slack/Teams) | Possível, com mais montagem |
| Disparar CodePipeline/CodeBuild | Indireto | Não | **Ideal** |
| Filtrar por branch, tipo de evento, repositório | Filtro limitado | Por tipo de evento | **Filtros ricos** no padrão de evento |
| Rotear a vários alvos, com retentativa e DLQ | Não | Não | **Sim** (regras com múltiplos alvos, DLQ) |
| Integrar com sistemas externos (webhook) | Via Lambda | Não | **API destinations** |
| Observabilidade e auditoria da automação | Fraca | Média | **Boa** (métricas e logs de regra) |
| Esforço de configuração | Baixo | Baixo | Médio |

Regra prática: **EventBridge para automação**, **notificações para pessoas** e **triggers só quando já existem e funcionam**. Ao migrar de triggers para EventBridge, **remova o trigger antigo** para não executar duas vezes o mesmo fluxo.

## 10. Erros comuns

> [!bug] Erros comuns
> 1. **Usar triggers antigos** quando o EventBridge resolve melhor.
> 2. **Esquecer a regra do EventBridge** (pipeline em IaC não dispara).
> 3. **Loop de commits do bot** sem filtros.
> 4. **Regra sem filtro de branch** disparando em todas as pushes.
> 5. **Roles de EventBridge/Lambda amplas demais.**
> 6. **Comentar/aprovar PR com a role errada**, sem permissão (`codecommit:UpdatePullRequestApprovalState`).
> 7. **Não propagar IDs de PR/commits** ao CodeBuild (input transformer).
> 8. **Ignorar eventos de atualização do PR** (novos commits invalidam resultados anteriores).
> 9. **Notificações sem canal** ou ruidosas demais (todos os eventos).
> 10. **Regra em região diferente** da do repositório.

## 11. Troubleshooting

| Sintoma | Causa provável | Ação |
|---|---|---|
| Pipeline não dispara após push | Regra EventBridge ausente/padrão errado | Verificar o padrão (`referenceName`) e o alvo |
| Regra dispara mas pipeline falha ao iniciar | Role do EventBridge sem permissão | Dar `StartPipelineExecution` |
| CodeBuild sem código | Variáveis de commit/ref erradas | Usar `SourceVersion` do PR (commit de origem) |
| Comentários do bot não aparecem | Permissões ou commit IDs incorretos | Verificar IAM e `beforeCommitId/afterCommitId` |
| Notificações não chegam | SNS/Chatbot sem permissão | Ajustar política do tópico e a configuração do Chatbot |
| Execuções duplicadas | Trigger antigo + EventBridge | Remover duplicidade |
| Muitos builds | Sem filtro de branch/caminho | Refinar regras |

## 12. Resumo rápido

- Automação via **EventBridge** (padrão moderno), **regras de notificação** (pessoas/canais) e **triggers** (legado simples).
- Eventos: **Repository State Change**, **Pull Request State Change**, **Comment**, **Approval**.
- Padrões: **CI no PR com CodeBuild + comentário/aprovação do bot**, **CD em `main` com CodePipeline**, **governança** (segredos, IaC, convenções).
- Evite **loops**, filtre **branches**, use **roles mínimas** e mantenha tudo na **mesma região**.
