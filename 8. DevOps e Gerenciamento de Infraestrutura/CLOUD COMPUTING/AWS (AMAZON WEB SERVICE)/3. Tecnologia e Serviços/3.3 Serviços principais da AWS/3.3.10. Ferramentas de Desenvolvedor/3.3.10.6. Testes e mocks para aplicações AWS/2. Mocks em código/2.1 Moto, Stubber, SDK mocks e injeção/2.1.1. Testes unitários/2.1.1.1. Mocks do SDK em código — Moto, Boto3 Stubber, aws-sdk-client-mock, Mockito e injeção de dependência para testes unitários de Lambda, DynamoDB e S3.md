### 2.1.1.1. Mocks do SDK em código — Moto, Boto3 Stubber, aws-sdk-client-mock, Mockito e injeção de dependência para testes unitários de Lambda, DynamoDB e S3

> [!warning] Aviso
> APIs das bibliotecas (decorators do Moto, assinatura do `Stubber`, matchers do `aws-sdk-client-mock`, mocks do SDK Java v2) e versões mudam. **Confirme na documentação de cada biblioteca** (Moto, Boto3 “Stubber”, aws-sdk-client-mock, Mockito/JUnit). Código ilustrativo, **não executado**. Contas, ARNs e nomes são fictícios.

## 1. As quatro técnicas de mock em código

| Técnica | Idea | Quando usar |
|---|---|---|
| **Stub do cliente** (Boto3 `Stubber`) | Intercepta o cliente e devolve respostas/erros **pré-definidos**, validando **parâmetros** contra o modelo | Testar **tratamento de resposta/erro** com **precisão de contrato** |
| **Fake em memória** (**Moto**) | Reimplementa serviços (S3, DynamoDB, SQS…) **em memória** | Testar **fluxos** que leem/gravam de verdade (sem rede) |
| **Mock do SDK** (JS `aws-sdk-client-mock`, Java Mockito) | Substitui o cliente/`send` e **verifica chamadas** | Testes **unitários rápidos** com asserções de interação |
| **Injeção de dependência** | Passar um **fake próprio** (repositório/gateway) | **Lógica de negócio** desacoplada do SDK |

## 2. Boto3 Stubber

### 2.1 Conceito

`botocore.stub.Stubber` **envolve um cliente** e permite **enfileirar respostas** (`add_response`) ou **erros** (`add_client_error`) para chamadas **na ordem**. Ele **valida** que os **parâmetros esperados** e a **forma da resposta** respeitam o **modelo do serviço** — por isso é mais rigoroso do que um `MagicMock`.

### 2.2 Exemplo: resposta esperada

```python
import boto3
from botocore.stub import Stubber

def buscar_pedido(client, tabela, pedido_id):
    r = client.get_item(TableName=tabela, Key={"id": {"S": pedido_id}})
    item = r.get("Item")
    return None if item is None else {"id": item["id"]["S"], "valor": int(item["valor"]["N"])}

def test_buscar_pedido_existente():
    client = boto3.client("dynamodb", region_name="us-east-1",
                          aws_access_key_id="x", aws_secret_access_key="y")      # credenciais falsas
    with Stubber(client) as stub:
        stub.add_response(
            "get_item",
            {"Item": {"id": {"S": "1"}, "valor": {"N": "10"}}},                  # resposta
            {"TableName": "pedidos", "Key": {"id": {"S": "1"}}})                  # parâmetros ESPERADOS
        assert buscar_pedido(client, "pedidos", "1") == {"id": "1", "valor": 10}
        stub.assert_no_pending_responses()                                       # nada ficou sem consumir
```

### 2.3 Exemplo: erro do serviço

```python
from botocore.exceptions import ClientError

def test_throttling_vira_erro_de_dominio():
    client = boto3.client("dynamodb", region_name="us-east-1", aws_access_key_id="x", aws_secret_access_key="y")
    with Stubber(client) as stub:
        stub.add_client_error("get_item", service_error_code="ProvisionedThroughputExceededException",
                              service_message="limite", http_status_code=400)
        try:
            buscar_pedido(client, "pedidos", "1")
            assert False, "deveria falhar"
        except ClientError as e:
            assert e.response["Error"]["Code"] == "ProvisionedThroughputExceededException"
```

### 2.4 Pontos fortes e limites do Stubber

| Ponto | Detalhe |
|---|---|
| **Valida parâmetros** | Erra se o código passar parâmetro **diferente/ausente** (`StubAssertionError`) |
| **Valida forma da resposta** | Erra se a resposta **fabricada** não respeita o modelo (`ParamValidationError`) |
| **Ordem importa** | Respostas são consumidas **na sequência** das chamadas |
| **Sem lógica de serviço** | Não “sabe” o que o DynamoDB **faria** (condições, consistência) |
| **Retries do SDK** | Erros retentáveis podem causar **chamadas extras** → desative retries no cliente de teste ou enfileire respostas suficientes |
| **Paginadores/waiters** | Funcionam com stubs, mas exigem **todas as páginas** enfileiradas |
| **Ótimo para** | Fluxos de **erro** e **parsing** de resposta |

## 3. Moto (fake em memória para Python)

### 3.1 Conceito

**Moto** simula **dezenas de serviços** (S3, DynamoDB, SQS, SNS, Lambda, IAM, STS, Secrets Manager…) **dentro do processo**, interceptando o **Boto3**. O código **real** roda, mas “a AWS” é falsa e **efêmera** (estado em memória, zerado a cada teste). Na versão atual usa-se um **único decorator `@mock_aws`** (versões antigas tinham `@mock_s3`, `@mock_dynamodb`… — **confirmar**).

### 3.2 Exemplo: S3

```python
import boto3, pytest
from moto import mock_aws

@pytest.fixture(autouse=True)
def credenciais_falsas(monkeypatch):
    # evita QUALQUER chance de usar credenciais reais
    monkeypatch.setenv("AWS_ACCESS_KEY_ID", "testing")
    monkeypatch.setenv("AWS_SECRET_ACCESS_KEY", "testing")
    monkeypatch.setenv("AWS_SESSION_TOKEN", "testing")
    monkeypatch.setenv("AWS_DEFAULT_REGION", "us-east-1")

@mock_aws
def test_exporta_relatorio_para_s3():
    s3 = boto3.client("s3", region_name="us-east-1")
    s3.create_bucket(Bucket="relatorios")                      # cria o bucket FALSO
    exportar_relatorio(s3, "relatorios", "2026/11/rel.csv", "a,b\n1,2\n")
    obj = s3.get_object(Bucket="relatorios", Key="2026/11/rel.csv")
    assert obj["Body"].read().decode() == "a,b\n1,2\n"
```

### 3.3 Exemplo: DynamoDB (com GSI e condição)

```python
@mock_aws
def test_nao_sobrescreve_pedido_existente():
    ddb = boto3.resource("dynamodb", region_name="us-east-1")
    ddb.create_table(TableName="pedidos",
                     KeySchema=[{"AttributeName": "id", "KeyType": "HASH"}],
                     AttributeDefinitions=[{"AttributeName": "id", "AttributeType": "S"}],
                     BillingMode="PAY_PER_REQUEST")
    repo = RepositorioDynamo(ddb.Table("pedidos"))
    repo.criar({"id": "1", "valor": 10})
    with pytest.raises(PedidoJaExiste):                         # ConditionalCheckFailedException → erro de domínio
        repo.criar({"id": "1", "valor": 99})
```

### 3.4 Moto: modo decorator, context manager e servidor

| Modo | Uso |
|---|---|
| **`@mock_aws` / `with mock_aws():`** | **In-process** (padrão dos testes unitários) |
| **`moto_server`** (HTTP) | Serviço **standalone**; use `endpoint_url="http://localhost:5000"` (**qualquer linguagem**/integração) |
| **Docker** (`motoserver/moto`) | Em CI |
| **Fixtures pytest** | Criar buckets/tabelas **por teste** |

### 3.5 Limites do Moto

| Limite | Consequência |
|---|---|
| **Não aplica IAM real** (por padrão) | **Não** valida políticas (há opção experimental de **IAM enforcement** — **confirmar**) |
| **Divergências de comportamento** | Mensagens/códigos de erro e casos de borda podem **diferir** da AWS |
| **Cobertura parcial** de APIs | Operações novas/raras podem faltar |
| **Sem latência/throttling real** | Não testa **cotas** |
| **Criar o cliente antes de ativar o mock** | Pode **vazar** para a AWS real (ver erros comuns) |
| **Dados em memória** | Zeram a cada teste (bom e ruim) |

## 4. aws-sdk-client-mock (JavaScript/TypeScript, SDK v3)

```typescript
import { mockClient } from "aws-sdk-client-mock";
import "aws-sdk-client-mock-jest";
import { DynamoDBDocumentClient, GetCommand, PutCommand } from "@aws-sdk/lib-dynamodb";
import { buscarPedido } from "./pedidos";

const ddbMock = mockClient(DynamoDBDocumentClient);
beforeEach(() => ddbMock.reset());

test("retorna o pedido existente", async () => {
  ddbMock.on(GetCommand, { TableName: "pedidos", Key: { id: "1" } })
         .resolves({ Item: { id: "1", valor: 10 } });
  expect(await buscarPedido("1")).toEqual({ id: "1", valor: 10 });
  expect(ddbMock).toHaveReceivedCommandWith(GetCommand, { TableName: "pedidos" });
});

test("propaga erro de throttling", async () => {
  ddbMock.on(GetCommand).rejects(Object.assign(new Error("limite"), { name: "ProvisionedThroughputExceededException" }));
  await expect(buscarPedido("1")).rejects.toThrow("limite");
});

test("duas respostas em sequência", async () => {
  ddbMock.on(GetCommand).resolvesOnce({ Item: { id: "1" } }).resolvesOnce({});
});
```

| Recurso | Descrição |
|---|---|
| **`mockClient(Cliente)`** | Intercepta **todos** os `send()` do cliente (ou instância específica) |
| **`.on(Comando, parametros?)`** | Define **resposta** para chamadas **que casam** com o input |
| **`.resolves/.rejects/.callsFake`** | Resposta, erro ou **função customizada** |
| **`.resolvesOnce`** | Resposta **sequencial** |
| **`toHaveReceivedCommandWith`** | **Asserção de interação** (Jest/Vitest) |
| **`.reset()/.restore()`** | Limpa entre testes |
| **Streams (S3 `GetObject`)** | Use `sdkStreamMixin(Readable.from(...))` para o `Body` |
| **Limitação** | Mock **não valida** o input contra o modelo (diferente do Stubber) |

## 5. Java: Mockito e SDK v2

```java
class PedidoServiceTest {
  DynamoDbClient ddb = mock(DynamoDbClient.class);
  PedidoService service = new PedidoService(ddb, "pedidos");        // injeção por construtor

  @Test
  void retornaPedido() {
    when(ddb.getItem(any(GetItemRequest.class))).thenReturn(
        GetItemResponse.builder().item(Map.of(
            "id", AttributeValue.fromS("1"),
            "valor", AttributeValue.fromN("10"))).build());

    Pedido p = service.buscar("1");

    assertEquals(10, p.valor());
    verify(ddb).getItem(argThat((GetItemRequest r) -> r.tableName().equals("pedidos")));
  }

  @Test
  void throttlingViraExcecaoDeDominio() {
    when(ddb.getItem(any(GetItemRequest.class)))
        .thenThrow(ProvisionedThroughputExceededException.builder().message("limite").build());
    assertThrows(ServicoIndisponivel.class, () -> service.buscar("1"));
  }
}
```

| Ponto | Detalhe |
|---|---|
| **Interfaces do SDK v2** (`DynamoDbClient`, `S3Client`) | São **interfaces** → **fáceis de mockar** |
| **Builders imutáveis** | Construir respostas com `Response.builder()` |
| **`S3Client.getObject`** | Retorna `ResponseInputStream` — criar com `AbortableInputStream.create(...)` |
| **Alternativa** | **LocalStack/Testcontainers** para integração |
| **Quarkus/Spring** | Substituir **beans** com `@MockBean`/`@InjectMock` |

## 6. Injeção de dependência: o mock que não precisa de biblioteca

A técnica mais robusta é **não depender do SDK na lógica**:

```python
# porta (interface implícita)
class RepositorioPedidos:
    def obter(self, pedido_id): ...
    def salvar(self, pedido): ...

# adaptador AWS
class RepositorioDynamo(RepositorioPedidos):
    def __init__(self, tabela): self.tabela = tabela
    def obter(self, pedido_id): return self.tabela.get_item(Key={"id": pedido_id}).get("Item")
    def salvar(self, pedido): self.tabela.put_item(Item=pedido, ConditionExpression="attribute_not_exists(id)")

# fake para testes
class RepositorioMemoria(RepositorioPedidos):
    def __init__(self): self.d = {}
    def obter(self, i): return self.d.get(i)
    def salvar(self, p): self.d[p["id"]] = p
```

| Benefício | Detalhe |
|---|---|
| **Testes sem biblioteca de mock** | Rápidos e **legíveis** |
| **Lógica independente do SDK** | Trocar DynamoDB por outro **sem reescrever** regras |
| **Testar o adaptador separadamente** | Com **Moto/DynamoDB Local/serviço real** |
| **Menos acoplamento** | Handler magro |

## 7. Mocks para Lambda: o handler, o contexto e os eventos

```python
from types import SimpleNamespace

def contexto_falso(tempo_ms=30000):
    return SimpleNamespace(function_name="f", aws_request_id="req-1",
                           memory_limit_in_mb=128, get_remaining_time_in_millis=lambda: tempo_ms,
                           invoked_function_arn="arn:aws:lambda:us-east-1:123456789012:function:f")

def test_handler_api_gateway():
    evento = {"httpMethod": "POST", "path": "/pedidos", "headers": {"content-type": "application/json"},
              "body": "{\"id\":\"1\",\"valor\":10}", "isBase64Encoded": False}
    resposta = handler(evento, contexto_falso())
    assert resposta["statusCode"] == 201
```

| Dica | Detalhe |
|---|---|
| **`context` falso** | `get_remaining_time_in_millis()`, `aws_request_id`, `function_name` |
| **Eventos reais** | Capture de **CloudWatch Logs** ou gere com **`sam local generate-event`** |
| **`body` é string** | No API Gateway proxy, `body` vem **string JSON** (e pode estar **base64**) |
| **Variáveis de ambiente** | `monkeypatch.setenv("TABELA", "pedidos")` |
| **Tipos de `Decimal`** | DynamoDB resource devolve `Decimal` — cuidado em JSON |
| **Powertools for AWS Lambda** | Utilitários (validação de eventos, **fixtures de eventos** e `LambdaContext` de teste) — **confirmar** |

## 8. Escolhendo a técnica

| Cenário | Melhor escolha |
|---|---|
| Testar **erro/retry** de uma chamada específica | **Stubber** / `rejects` |
| Testar **fluxo** que lê/grava (S3/DynamoDB) em Python | **Moto** |
| Verificar **chamadas** ao SDK em Node | **aws-sdk-client-mock** |
| Verificar **chamadas** em Java | **Mockito** (+ Testcontainers/LocalStack p/ integração) |
| **Regras de negócio** | **Injeção de dependência** + fake em memória |
| Precisa de **comportamento fiel** do DynamoDB (índices, condições) | **DynamoDB Local**/Moto/**serviço real** |
| **IAM/eventos reais** | **Serviço real** |

## 9. Boas práticas

1. **Credenciais e região falsas** em todos os testes (variáveis de ambiente/fixture).
2. **Ativar o mock antes de criar o cliente** (ou criar o cliente **dentro** do contexto).
3. **Um mock por teste**; `reset()`/fixtures para **isolar**.
4. **Verificar interações importantes**, não **todos os detalhes** (testes frágeis).
5. **Cobrir erros** (`ClientError`, throttling, `ConditionalCheckFailed`, `NoSuchKey`).
6. **Fixtures de eventos** reais/anonimizados no repositório.
7. **Testes de adaptador** com fake/emulador/serviço real (não só mocks).
8. **Evitar mockar o que você não possui demais** — prefira **portas** próprias.
9. **Rodar testes sem rede** no CI para detectar chamadas acidentais.
10. **Medir cobertura**, mas valorizar **contratos**.

## 10. Erros comuns

- **Cliente criado antes do mock** (chama a AWS real).
- **Sem credenciais falsas** (SDK tenta a chain/IMDS e **demora**).
- **Mock que concorda com o código** (falso positivo).
- **Resposta fabricada com tipos errados** (`{"N": 10}` em vez de `{"N": "10"}`).
- **Ordem do Stubber** diferente das chamadas.
- **Esquecer retries** (chamadas extras consomem stubs).
- **Estado vazando** entre testes (singletons/caches do módulo).
- **Streams do S3** mal simulados (Node/Java).
- **Mockar demais** e perder valor do teste.
- **Assumir que Moto = AWS** (comportamento divergente).

## 11. Troubleshooting

| Sintoma | Causa provável | Ação |
|---|---|---|
| `NoCredentialsError`/lento | Sem credenciais falsas | Definir variáveis/fixture |
| Chamada **real** à AWS | Mock aplicado tarde/cliente global | Criar cliente **no teste**/dentro do `mock_aws` |
| `StubAssertionError` | Parâmetros diferem | Ajustar `expected_params` |
| `ParamValidationError` | Resposta/entrada fora do modelo | Corrigir tipos |
| `Missing response` no Stubber | Mais chamadas que respostas | Enfileirar mais/desativar retries |
| `aws-sdk-client-mock` não intercepta | Cliente instanciado de outra versão/pacote | Alinhar **versões** e **imports** |
| Item “some” entre testes | Estado compartilhado | `reset()`; fixtures por teste |
| Teste passa, produção falha | Mock não reflete o serviço | Teste de integração real |

## 12. Resumo rápido

- **Stubber**: respostas/erros **pré-definidos** com **validação de contrato** (ótimo para erros).
- **Moto**: **fake em memória** (`@mock_aws`) para fluxos reais sem rede; **sem IAM real**.
- **aws-sdk-client-mock** (Node) e **Mockito** (Java): **verificam interações** do SDK.
- **Injeção de dependência + fakes próprios**: lógica **desacoplada** e testes **simples**.
- **Lambda**: **handler magro**, **context falso**, **eventos reais** (body string), variáveis de ambiente.
- **Sempre**: **credenciais/região falsas**, **mock antes do cliente**, **isolamento** e **testes de integração** complementares.

## 🧩 Quiz de Fixação

1. O que o Boto3 Stubber valida que um MagicMock não valida?
2. Qual a diferença entre Moto e Stubber?
3. Por que definir credenciais falsas nos testes?
4. Como mockar o DynamoDB no SDK v3 em Node?
5. Qual o limite do Moto em relação a IAM?
6. Por que o `body` do evento API Gateway pode quebrar um teste?
7. Qual a vantagem da injeção de dependência?

**Respostas:**

1. Parâmetros esperados e a forma da resposta contra o modelo do serviço.
2. Stubber devolve respostas pré-definidas por chamada; Moto simula o serviço em memória com estado, executando o fluxo real.
3. Para evitar que o SDK use credenciais reais ou tente a chain/IMDS, causando lentidão, falhas ou chamadas reais.
4. Com aws-sdk-client-mock: `mockClient(DynamoDBDocumentClient)` e `.on(Comando).resolves/rejects`.
5. Por padrão não aplica políticas IAM reais, então permissões não são validadas.
6. Porque no proxy o body chega como string JSON (possivelmente base64), e testes que passam objeto escondem erros de parsing.
7. Desacopla a lógica do SDK, permitindo fakes em memória, testes rápidos e troca de implementação.
