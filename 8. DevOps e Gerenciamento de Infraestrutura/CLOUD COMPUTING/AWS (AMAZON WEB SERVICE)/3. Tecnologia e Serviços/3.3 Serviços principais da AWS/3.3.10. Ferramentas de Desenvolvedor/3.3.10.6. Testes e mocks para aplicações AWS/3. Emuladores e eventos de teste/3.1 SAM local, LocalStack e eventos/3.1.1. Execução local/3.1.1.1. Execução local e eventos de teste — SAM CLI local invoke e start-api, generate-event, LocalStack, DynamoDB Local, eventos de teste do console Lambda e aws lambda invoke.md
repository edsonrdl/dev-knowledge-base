### 3.1.1.1. Execução local e eventos de teste — SAM CLI local invoke e start-api, generate-event, LocalStack, DynamoDB Local, eventos de teste do console Lambda e aws lambda invoke

> [!warning] Aviso
> Subcomandos, flags, imagens Docker, variáveis e limitações de **SAM CLI**, **LocalStack** e **DynamoDB Local** mudam entre versões; recursos de LocalStack variam entre edições (Community/Pro). Formatos de eventos também evoluem. **Confirme na documentação do AWS SAM, do LocalStack e do Lambda.** Comandos e JSON são ilustrativos e **não foram executados**. Contas, ARNs e IDs são fictícios.

## 1. Visão geral: “rodar a AWS na sua máquina”

| Ferramenta | O que faz | Escopo |
|---|---|---|
| **AWS SAM CLI** (`sam local …`) | Executa **Lambda** (e emula **API Gateway**) localmente em **containers Docker** com o runtime real | **Lambda + API/Function URL** |
| **`sam local generate-event`** | **Gera eventos de exemplo** de dezenas de serviços | **Eventos de teste** |
| **LocalStack** | **Emula** dezenas de serviços (S3, DynamoDB, SQS, SNS, Lambda, API Gateway, EventBridge…) em um container | **Integração local multi-serviço** |
| **DynamoDB Local** | **DynamoDB** oficial para execução **local** (JAR/Docker) | **Só DynamoDB** |
| **Moto server** | Serviços em memória via HTTP | Python/qualquer linguagem |
| **Console Lambda — “Test events”** | Executa a função **na nuvem** com um evento salvo | **Nuvem real** |
| **`aws lambda invoke`** | Invoca a função **na nuvem** pela CLI | **Nuvem real** |
| **Debug com IDE** (AWS Toolkit) | Breakpoints em invocações locais | Desenvolvimento |

## 2. AWS SAM CLI: execução local de Lambda

### 2.1 Pré-requisitos

- **SAM CLI** instalada, **Docker** em execução (os runtimes locais usam **imagens oficiais** da AWS).
- Um **template** (`template.yaml`) descrevendo as funções.

```yaml
# template.yaml (trecho)
AWSTemplateFormatVersion: "2010-09-09"
Transform: AWS::Serverless-2016-10-31
Globals:
  Function: { Runtime: python3.12, Timeout: 10, MemorySize: 256 }
Resources:
  PedidosFunction:
    Type: AWS::Serverless::Function
    Properties:
      Handler: app.handler
      CodeUri: src/
      Environment: { Variables: { TABELA: pedidos } }
      Events:
        Criar: { Type: Api, Properties: { Path: /pedidos, Method: post } }
```

### 2.2 `sam local invoke`: uma invocação única

```bash
sam build                                                    # compila/empacota (dependências, layers)
sam local invoke PedidosFunction -e events/criar-pedido.json  # roda o handler com o evento
sam local invoke PedidosFunction -e events/criar-pedido.json --env-vars env.json
sam local invoke PedidosFunction -e events/e.json --debug-port 5858      # espera debugger (IDE)
echo '{"id":"1"}' | sam local invoke PedidosFunction                      # evento via stdin
```

```json
// env.json — sobrescreve variáveis de ambiente por função
{ "PedidosFunction": { "TABELA": "pedidos-local", "AWS_ENDPOINT_URL_DYNAMODB": "http://host.docker.internal:8000" } }
```

| Flag | Função |
|---|---|
| **`-e/--event`** | Arquivo JSON do evento |
| **`--env-vars`** | Variáveis de ambiente por função |
| **`--docker-network`** | Conectar o container a uma **rede Docker** (para DynamoDB Local/LocalStack) |
| **`--profile/--region`** | Credenciais/região usadas pelo container |
| **`--debug-port`/`--debugger-path`** | Depuração remota |
| **`--warm-containers`** | Reaproveitar containers (EAGER/LAZY) |
| **`--skip-pull-image`** | Não baixar a imagem do runtime |

> [!warning] O container não enxerga “localhost” da máquina
> Dentro do container, `localhost` é o **próprio container**. Para alcançar o DynamoDB Local/LocalStack no **host**, use **`host.docker.internal`** (Docker Desktop) ou uma **rede Docker compartilhada** (`--docker-network`).

### 2.3 `sam local start-api`: API Gateway local

```bash
sam local start-api --port 3000 --warm-containers EAGER
curl -X POST http://127.0.0.1:3000/pedidos -H "Content-Type: application/json" -d '{"id":"1","valor":10}'
```

| Aspecto | Detalhe |
|---|---|
| **Emula** | Rotas `Api`/`HttpApi`/**Function URL** do template; **recarrega** o código ao mudar (rebuild) |
| **Não emula** | **Autorizadores** (Cognito/JWT/Lambda authorizer) de forma completa, **WAF**, **throttling**, **mapeamentos VTL** completos, **mTLS**, cotas |
| **Resposta** | Converte o retorno da Lambda (proxy) em HTTP |
| **CORS** | Cabeçalhos conforme sua resposta/template (**confirmar** comportamento) |
| **Hot reload** | Com `sam sync --watch` (nuvem) ou rebuild local |

### 2.4 `sam local start-lambda`: endpoint de invocação

```bash
sam local start-lambda --port 3001
aws lambda invoke --endpoint-url http://127.0.0.1:3001 --function-name PedidosFunction \
  --cli-binary-format raw-in-base64-out --payload file://events/criar-pedido.json /dev/stdout
```

Útil para **testes de integração** que usam o **SDK** (`lambda.invoke`) apontando para o **endpoint local**.

### 2.5 `sam sync` e `sam logs` (nuvem, desenvolvimento rápido)

| Comando | Uso |
|---|---|
| **`sam sync --stack-name dev --watch`** | **Sincroniza** código com a **nuvem** em segundos (testar contra **serviços reais**) |
| **`sam logs -n PedidosFunction --stack-name dev --tail`** | **Logs** do CloudWatch |
| **`sam remote invoke PedidosFunction --stack-name dev -e events/e.json`** | Invoca a função **implantada** (**confirmar** nome do comando) |
| **`sam traces`** | **X-Ray** |

> **Local vs nuvem**: `sam local` valida **código e eventos**; `sam sync`/`remote invoke` validam **IAM, eventos reais e integrações**.

## 3. `sam local generate-event`: eventos de teste realistas

```bash
sam local generate-event --help                          # lista serviços
sam local generate-event s3 put --bucket meu-bucket --key uploads/foto.png > events/s3-put.json
sam local generate-event apigateway aws-proxy --method POST --path pedidos --body '{"id":"1"}' > events/apigw.json
sam local generate-event sqs receive-message --body '{"id":"1"}' > events/sqs.json
sam local generate-event dynamodb update > events/ddb-stream.json
sam local generate-event sns notification > events/sns.json
sam local generate-event cloudwatch scheduled-event > events/schedule.json
```

| Serviço | Estrutura essencial do evento |
|---|---|
| **S3** | `Records[].s3.bucket.name`, `Records[].s3.object.key` (**URL-encoded**), `eventName` |
| **SQS** | `Records[].body` (**string**), `messageId`, `receiptHandle`, `attributes` |
| **SNS** | `Records[].Sns.Message` (**string**) |
| **API Gateway (REST proxy)** | `httpMethod`, `path`, `headers`, `queryStringParameters`, `body` (**string**), `isBase64Encoded`, `requestContext` |
| **API Gateway HTTP API (v2)** | `requestContext.http.method`, `rawPath`, `body` |
| **DynamoDB Streams** | `Records[].dynamodb.NewImage` (**JSON tipado** `{"S": ...}`), `eventName` (INSERT/MODIFY/REMOVE) |
| **EventBridge** | `source`, `detail-type`, `detail` (objeto) |
| **Kinesis** | `Records[].kinesis.data` (**base64**) |
| **Scheduled** | `source: aws.events`, `time` |

> [!tip] Pegadinhas dos eventos
> - **SQS/SNS**: o conteúdo útil vem em **`body`/`Message` como string** → muitas vezes **JSON dentro de JSON** (`json.loads(record["body"])`).
> - **S3**: a **chave vem codificada** (`+`, `%xx`).
> - **Kinesis**: `data` em **base64**.
> - **API Gateway**: `body` pode ser **base64** (`isBase64Encoded`).
> - **DynamoDB Streams**: imagens em **JSON tipado** (`AttributeValue`).
> - **Batching**: SQS/Kinesis/DynamoDB entregam **lotes** (`Records` com vários itens) → testar **falhas parciais** (`batchItemFailures`).

## 4. Eventos de teste no console do Lambda e na CLI (nuvem)

### 4.1 Console: “Test events”

| Recurso | Detalhe |
|---|---|
| **Criar evento de teste** | Aba **Test** → escolher **template** (ex.: `apigateway-aws-proxy`, `s3-put`, `sqs`) → editar JSON |
| **Privado** | Visível **só para o criador** (por padrão) |
| **Compartilhável (shareable test events)** | Compartilhado com **outros usuários/IAM** da conta (permissões `lambda:*EventSchema`/ver docs — **confirmar**) |
| **Resultado** | Mostra **resposta**, **logs** (4 KB) e **duração/memória/billed** |
| **Uso** | Verificação rápida de **IAM/variáveis/dependências reais** |

### 4.2 `aws lambda invoke`

```bash
aws lambda invoke --function-name PedidosFunction \
  --cli-binary-format raw-in-base64-out \
  --payload file://events/criar-pedido.json \
  --log-type Tail \
  saida.json
# LogResult (base64) mostra os últimos 4 KB de logs: 
aws lambda invoke --function-name PedidosFunction --payload '{"id":"1"}' --cli-binary-format raw-in-base64-out --log-type Tail saida.json \
  --query 'LogResult' --output text | base64 --decode
```

| Opção | Efeito |
|---|---|
| **`--cli-binary-format raw-in-base64-out`** | (**CLI v2**) Envia o payload **como texto** (sem isso, a CLI v2 espera **base64** e **falha**) |
| **`--invocation-type RequestResponse`** | **Síncrona** (padrão): espera a resposta |
| **`--invocation-type Event`** | **Assíncrona**: retorna **202** imediatamente |
| **`--invocation-type DryRun`** | **Valida permissões/parâmetros** sem executar |
| **`--log-type Tail`** | Retorna os **últimos 4 KB** de log no cabeçalho (`LogResult`, base64) |
| **`--qualifier`** | **Versão/alias** (`:prod`, `:$LATEST`) |
| **`FunctionError`** | Campo da resposta quando o **handler lançou erro** (HTTP 200 com `FunctionError: Unhandled`) |

> [!warning] Erro da função ≠ erro HTTP
> Na invocação **síncrona**, se o **código** da função falhar, o **status HTTP continua 200** e a resposta traz **`FunctionError`** (`Handled`/`Unhandled`) e o payload do erro. Falhas de **permissão/serviço** (ex.: 403/429/5xx) são **diferentes**. **Verifique `FunctionError`** em testes automatizados.

## 5. DynamoDB Local

```bash
docker run -p 8000:8000 amazon/dynamodb-local -jar DynamoDBLocal.jar -inMemory -sharedDb
aws dynamodb create-table --endpoint-url http://localhost:8000 --table-name pedidos \
  --attribute-definitions AttributeName=id,AttributeType=S --key-schema AttributeName=id,KeyType=HASH \
  --billing-mode PAY_PER_REQUEST
```

```python
ddb = boto3.resource("dynamodb", endpoint_url="http://localhost:8000", region_name="us-east-1",
                     aws_access_key_id="x", aws_secret_access_key="y")
```

| Aspecto | Detalhe |
|---|---|
| **Fidelidade** | Implementação **oficial** do DynamoDB: **boa** para **consultas, índices, condições, transações** |
| **Diferenças** | **Sem** cobrança/capacidade real, **throttling** e **latência** diferentes; **Streams**/TTL/backups com **limitações** |
| **Modos** | `-inMemory` (efêmero) ou **persistente** (`-dbPath`) |
| **Nome “shared”** | `-sharedDb` usa **um banco** independente de credenciais/região |
| **Uso em CI** | **Testcontainers**/Docker Compose |

## 6. LocalStack

### 6.1 Subindo


## 7. Padrões de teste de integração local

```
docker compose up -d (LocalStack/DynamoDB Local)
 → provisionar recursos (script/IaC: tabela, fila, bucket)
 → rodar testes (pytest/jest) apontando endpoint_url para o emulador
 → asserções no ESTADO (item gravado? mensagem na fila? objeto no S3?)
 → docker compose down -v (limpeza)
```

| Prática | Detalhe |
|---|---|
| **Testcontainers** | Sobe/derruba containers **a partir do teste** (Python/Java/Node) |
| **Endpoint configurável** | `AWS_ENDPOINT_URL` ou parâmetro — **nunca** codificado |
| **Provisionamento idempotente** | Criar recursos se não existirem |
| **Isolamento** | Nomes únicos por teste; limpar |
| **Esperas** | Eventos **assíncronos** → **polling com timeout**, não `sleep` fixo |
| **Eventos reais gerados** | Disparar **S3 put** no emulador e verificar o efeito (Lambda local) |

```python
import time
def aguardar(cond, timeout=10, passo=0.2):
    fim = time.time() + timeout
    while time.time() < fim:
        if cond(): return True
        time.sleep(passo)
    raise TimeoutError("condição não atendida")
```

## 8. Local × emulador × nuvem: o que cada um prova

| Pergunta | `sam local` | LocalStack/DynamoDB Local | Nuvem (SAM sync/stack efêmero) |
|---|---|---|---|
| O **código** funciona com este evento? | Sim | Sim | Sim |
| O **mapeamento do API Gateway** (VTL) funciona? | Parcial | Parcial | **Sim** |
| As **permissões IAM** estão corretas? | **Não** | **Não/limitado** | **Sim** |
| O **evento real** (S3, DDB Streams) chega como esperado? | Não | Parcial | **Sim** |
| **Cotas/throttling/timeouts** reais? | Não | Não | **Sim** |
| Rápido e barato? | **Sim** | Sim | Não |
| **VPC/KMS/Secrets Manager** reais? | Não | Parcial | **Sim** |

## 9. Boas práticas

1. **Versionar eventos** (`events/*.json`) com **casos válidos e inválidos**.
2. **Gerar eventos** com `generate-event` e **ajustar** a partir de **eventos reais anonimizados**.
3. **Variáveis de endpoint** externas (não codificar `localhost`).
4. **Rede Docker/host.docker.internal** corretos.
5. **Testar lotes e falhas parciais** (SQS `batchItemFailures`).
6. **Combinar** local (rápido) + **nuvem** (IAM/eventos) no pipeline.
7. **Usar `--log-type Tail`/`sam logs`** para depurar.
8. **Verificar `FunctionError`** nas invocações.
9. **Esperas por polling**, não por `sleep` fixo.
10. **Limpar** recursos/containers sempre.

## 10. Erros comuns

- **`localhost` dentro do container** (falha de conexão com o emulador).
- **Docker não iniciado** (`sam local` falha).
- **Payload sem `--cli-binary-format raw-in-base64-out`** (CLI v2) → “Invalid base64”.
- **Evento de teste com formato inventado**.
- **Ignorar `FunctionError`** (considerar 200 como sucesso).
- **Esperar que `sam local start-api` aplique autorizadores/WAF/throttling**.
- **Confiar no emulador para IAM**.
- **Não decodificar** chave do S3 / `body` do SQS.
- **Sem limpar** (containers/tabelas/filas).
- **Versões do SAM/LocalStack/Docker desatualizadas**.
- **Credenciais reais** vazando para o emulador (ou vice-versa).

## 11. Troubleshooting

| Sintoma | Causa provável | Ação |
|---|---|---|
| `Cannot connect to the Docker daemon` | Docker parado | Iniciar Docker |
| `sam local` lento na 1ª vez | Download da imagem | `--skip-pull-image` depois |
| Função local não alcança DynamoDB Local | `localhost` | `host.docker.internal`/`--docker-network` |
| `Could not connect to the endpoint URL` | Emulador fora do ar/porta | Verificar container/porta |
| `Invalid base64` ao invocar | CLI v2 | `--cli-binary-format raw-in-base64-out` |
| Resposta 200 mas falhou | `FunctionError` | Ler o payload do erro |
| Handler recebe `body` como string | Comportamento correto do proxy | `json.loads` |
| Evento S3 sem chave certa | URL-encoding | Decodificar |
| Funciona local, falha na nuvem | IAM/config/rede | Teste na nuvem (`sam sync`, stack efêmero) |
| LocalStack: recurso “não implementado” | Cobertura/edição | Serviço real para esse ponto |

## 12. Resumo rápido

- **SAM CLI**: **`sam local invoke`** (uma execução), **`start-api`** (API local), **`start-lambda`**, **`generate-event`**; usam **Docker** com o **runtime real**; **não** emulam IAM/autorizadores/WAF/throttling.
- **Eventos de teste**: gerar/versionar JSON; atenção a **`body` string**, **S3 key encoded**, **Kinesis base64**, **DDB tipado**, **lotes**.
- **Nuvem**: console **Test events** (privados/compartilháveis) e **`aws lambda invoke`** (`raw-in-base64-out`, `--log-type Tail`, `FunctionError`, `DryRun`, `Event`).
- **Emuladores**: **DynamoDB Local** (oficial, só DDB), **LocalStack** (multi-serviço, fidelidade variável), **Moto server**.
- **Docker**: `host.docker.internal`/rede compartilhada; **polling** em vez de sleep.
- **Estratégia**: local para **rapidez**, **nuvem** para **IAM/eventos/integrações reais**.

## 🧩 Quiz de Fixação

1. Qual a diferença entre `sam local invoke` e `sam local start-api`?
2. Como gerar um evento S3 de exemplo?
3. Por que `aws lambda invoke` na CLI v2 pode falhar com payload JSON?
4. O que é `FunctionError` e por que importa?
5. Como a função local alcança o DynamoDB Local no host?
6. O que o `sam local` não valida?
7. Quando usar LocalStack em vez de DynamoDB Local?

**Respostas:**

1. `invoke` executa a função uma vez com um evento; `start-api` sobe um endpoint HTTP local que emula as rotas do API Gateway.
2. `sam local generate-event s3 put --bucket <b> --key <k>` redirecionando a saída para um arquivo JSON.
3. Porque a CLI v2 espera payload em base64 por padrão; é preciso `--cli-binary-format raw-in-base64-out`.
4. Campo que indica erro no código da função em invocação síncrona; o HTTP continua 200, então testes devem verificá-lo.
5. Usando `host.docker.internal` (ou rede Docker compartilhada), pois `localhost` dentro do container é o próprio container.
6. IAM, autorizadores completos, WAF, throttling/cotas, eventos reais e integrações de rede/KMS.
7. Quando o teste envolve vários serviços integrados (S3, SQS, SNS, Lambda, API Gateway), não só DynamoDB.
