### 1.1.1.1. Estratégia de testes para aplicações AWS — pirâmide de testes, stubs, mocks, fakes, emuladores e serviços reais, o que testar onde e custo versus confiança

> [!warning] Aviso
> Nomes de ferramentas, versões, flags e limites de emuladores (Moto, LocalStack, SAM CLI, DynamoDB Local) abaixo são **de memória e mudam**. **Confirme na documentação de cada ferramenta e na do AWS SAM / AWS SDKs.** Código, comandos e configurações são ilustrativos e **não foram executados**. Esta nota cobre as skills **3.2.1 a 3.2.3 do DVA-C03** (escrever testes, APIs mock, eventos de teste).

## 1. Por que testar aplicações AWS é diferente

Uma aplicação “serverless” ou “cloud-native” tem **pouca lógica isolada** e **muita cola** entre serviços: o handler Lambda lê de SQS, grava no DynamoDB, publica no SNS, chama o S3 e responde ao API Gateway. Os defeitos tendem a morar:

| Onde moram os bugs | Exemplo |
|---|---|
| **Na lógica de negócio** | Cálculo de desconto errado |
| **No contrato com o serviço** | Atributo do DynamoDB com tipo errado (`{"N": "10"}` vs `10`) |
| **Na forma do evento** | Esperar `event["body"]` já como dict quando vem **string JSON** |
| **Nas permissões (IAM)** | `AccessDenied` só em produção |
| **Na configuração** | Variável de ambiente ausente, timeout curto, memória baixa |
| **Na concorrência/resiliência** | Retentativas duplicando processamento (idempotência) |
| **Na integração** | Mapeamento do API Gateway, CORS, autorizadores |

Nenhuma técnica sozinha cobre tudo. Por isso se usa uma **estratégia em camadas**, equilibrando **velocidade**, **custo**, **fidelidade** e **confiança**.

## 2. Vocabulário: dublês de teste

| Termo | O que é | Exemplo AWS |
|---|---|---|
| **Stub** | Respostas **pré-programadas** (sem verificar chamadas) | `Stubber` do Boto3 devolvendo um `get_item` fixo |
| **Mock** | Objeto que **verifica interações** (chamado com X, N vezes) | `aws-sdk-client-mock`: `expect(ddbMock).toHaveReceivedCommandWith(...)` |
| **Fake** | Implementação **funcional simplificada** | **Moto** (S3/DynamoDB em memória), **DynamoDB Local** |
| **Spy** | Observa chamadas reais, sem substituí-las | Contar chamadas ao SDK real |
| **Emulador** | Software que **imita** a API de um serviço | **LocalStack**, Moto em modo servidor |
| **Serviço real** | A **AWS de verdade** (conta de teste) | Stack efêmero de CI com CloudFormation/SAM |
| **Contrato** | Acordo verificável sobre request/response | OpenAPI, **Pact** |

> [!info] Em uma frase
> **Stub devolve; mock verifica; fake funciona de verdade em pequeno; emulador imita a API; serviço real é a verdade — cada um troca fidelidade por velocidade e custo.**

## 3. A pirâmide (e o “troféu”) de testes para nuvem

```
                 ▲  poucos, lentos, caros, ALTA fidelidade
                ╱ ╲    E2E em conta de teste (serviços reais, stack efêmero)
               ╱───╲
              ╱     ╲  Integração: emulador (LocalStack/Moto server/SAM local)
             ╱───────╲       + testes contra serviços reais pontuais (IAM, eventos)
            ╱         ╲
           ╱ Unitários ╲ muitos, rápidos, baratos, BAIXA fidelidade
          ╱─────────────╲   lógica pura + mocks/stubs do SDK
```

| Camada | Alvo | Ferramentas típicas | Velocidade | Fidelidade |
|---|---|---|---|---|
| **Unitário** | Funções de negócio, validação, mapeamentos | pytest/unittest, Jest, JUnit, **Stubber/Moto/aws-sdk-client-mock** | **ms** | Baixa |
| **Integração local** | Handler + SDK + “serviço” emulado | **Moto server, LocalStack, DynamoDB Local, SAM CLI** | segundos | Média |
| **Integração na nuvem** | IAM, eventos reais, mapeamentos, quotas | Stack efêmero (SAM/CDK/CloudFormation) em **conta de teste** | minutos | **Alta** |
| **Contrato** | APIs entre serviços/equipes | OpenAPI, **Prism**, **Pact** | segundos | Média (do contrato) |
| **E2E / smoke** | Fluxo de usuário completo | Cypress/Playwright + API real; **smoke test** pós-deploy | minutos | **Muito alta** |
| **Não funcionais** | Carga, caos, segurança | Artillery/k6, Fault Injection Service, scanners | variável | Alta |

> Para **serverless**, muitas equipes preferem um “**troféu**”: **poucos unitários** de lógica pura, **muitos testes de integração** (porque o valor está na cola entre serviços) e **poucos E2E**. A regra prática: **teste a lógica rápida e localmente; teste a integração onde ela de fato acontece**.

## 4. O que testar em cada camada

### 4.1 Unitários (rápidos, sem rede)

| Teste | Como |
|---|---|
| **Regras de negócio** | Funções puras (sem SDK) |
| **Validação de entrada** | Eventos de exemplo (válidos/inválidos) |
| **Transformações** (evento → comando do SDK) | Verificar **parâmetros** passados ao SDK (mock) |
| **Tratamento de erro** | Stub que lança `ClientError`/`ThrottlingException` |
| **Idempotência** | Mesmo evento duas vezes → mesmo resultado |
| **Parsing de resposta** | Respostas **gravadas/estáticas** do serviço |

### 4.2 Integração local (emuladores)

| Teste | Como |
|---|---|
| **Handler + DynamoDB** | DynamoDB Local / Moto |
| **Fluxos S3 → Lambda** | Moto/LocalStack + evento S3 de exemplo |
| **API local** | `sam local start-api` |
| **Invocação com evento** | `sam local invoke -e evento.json` |
| **Filas/tópicos** | LocalStack (SQS/SNS) |

### 4.3 Integração na nuvem (serviço real)

| Teste | Por que **não** dá para emular bem |
|---|---|
| **IAM/permissões** | Emuladores **não aplicam** (ou aplicam mal) as políticas reais |
| **Eventos reais** (S3→Lambda, DynamoDB Streams, EventBridge) | Entrega, filtros, batching, retries reais |
| **Cotas/throttling/timeouts** | Comportamento real |
| **Mapeamentos do API Gateway, autorizadores, WAF** | Configuração real |
| **VPC, endpoints, KMS, Secrets Manager** | Rede e criptografia reais |
| **Custos/performance reais** | Cold start, memória |

### 4.4 E2E e smoke

- **Smoke test** pós-deploy: poucas chamadas **críticas** (healthcheck, criar/ler um item) contra o **ambiente recém-implantado**.
- **E2E**: fluxo completo, com **dados de teste** isolados e **limpeza**.
- **Rollback automático** se o smoke falhar (ex.: **CodeDeploy** com alarmes/hooks).

## 5. Custo versus confiança: como decidir

| Pergunta | Se “sim” → |
|---|---|
| É **lógica pura** que não toca AWS? | **Unitário** sem mock |
| É **chamada ao SDK** com parâmetros e tratamento de erro? | **Unitário com Stubber/mock** |
| Depende do **comportamento do serviço** (consultas, condições, transações)? | **Fake/emulador** (Moto/DynamoDB Local) ou **serviço real** |
| Depende de **IAM/KMS/VPC/eventos reais**? | **Serviço real** (stack efêmero) |
| Precisa ser **barato e rodar a cada commit**? | Unitários + emuladores |
| É **crítico** (pagamentos, dados sensíveis)? | **Mais** integração real + E2E |

| Abordagem | Custo | Velocidade | Fidelidade | Risco |
|---|---|---|---|---|
| **Mock do SDK** | Muito baixo | Muito alta | Baixa | **Falso positivo** (mock “concorda” com o código, não com a AWS) |
| **Fake (Moto)** | Baixo | Alta | Média | Divergências de comportamento/API |
| **Emulador (LocalStack)** | Baixo–médio (infra local/CI) | Média | Média–alta | Recursos/versões **parciais** |
| **Serviço real** | Médio–alto (dinheiro + tempo) | Baixa | **Alta** | Custo/vazamento de recursos; flakiness de rede |

> [!warning] O falso positivo clássico
> Um teste que **mocka o DynamoDB** e verifica “chamou `put_item` com este dict” **não prova** que o item é válido para o DynamoDB real (tipos, chaves, `ConditionExpression`). Por isso **combine**: mock para a **lógica**, **fake/emulador/serviço real** para o **contrato com o serviço**.

## 6. Princípios de testabilidade para código AWS

| Princípio | Prática |
|---|---|
| **Separar lógica do handler** | `handler(event, context)` **só adapta**; a regra fica em módulo puro |
| **Injeção de dependência** | Passar o **cliente do SDK** (ou um “repositório”) por parâmetro/construtor |
| **Criar clientes fora do handler** | Reuso (performance) — mas **permitir substituição** em testes |
| **Configuração por ambiente** | Variáveis de ambiente (nome de tabela, bucket) lidas em **um lugar** |
| **Portas e adaptadores** | Interface `RepositorioPedidos` → implementação DynamoDB + implementação em memória |
| **Funções pequenas** | Mais fáceis de testar e de reutilizar |
| **Idempotência e determinismo** | Injetar **relógio/UUID** para testes previsíveis |
| **Eventos como dados** | Guardar **eventos de exemplo** versionados no repositório |

```python
# lambda_pedidos/handler.py  — adaptador fino
import json, os, boto3
from .servico import registrar_pedido
from .repositorio import RepositorioDynamo

_repo = RepositorioDynamo(boto3.resource("dynamodb").Table(os.environ["TABELA"]))

def handler(event, context):
    corpo = json.loads(event["body"])
    pedido = registrar_pedido(corpo, repo=_repo)             # lógica pura recebe a dependência
    return {"statusCode": 201, "body": json.dumps(pedido)}
```

```python
# teste unitário: troca o repositório por um fake em memória (sem AWS)
class RepoMemoria:
    def __init__(self): self.itens = {}
    def salvar(self, p): self.itens[p["id"]] = p

def test_registra_pedido_valido():
    repo = RepoMemoria()
    pedido = registrar_pedido({"id": "1", "valor": 10}, repo=repo)
    assert repo.itens["1"]["valor"] == 10
```

## 7. Ambientes e contas de teste

| Prática | Detalhe |
|---|---|
| **Contas separadas** | `dev`/`test`/`staging`/`prod` (AWS Organizations) — **nunca** testar em produção |
| **Stack efêmero por branch/PR** | `sam deploy --stack-name app-pr-123` → testes → **destruir** |
| **Nomes únicos** | Sufixo do PR/commit para evitar colisões |
| **Teto de custo** | **AWS Budgets** + alarmes na conta de teste |
| **Limpeza obrigatória** | `sam delete`/`cdk destroy` no fim (mesmo em falha: etapa `finally`/`post_build`) |
| **Dados sintéticos** | Nunca **dados reais** (LGPD) |
| **Credenciais** | **OIDC/roles** para CI, **sem chaves de longo prazo** |

## 8. Testes não funcionais (visão geral)

| Tipo | Ferramenta/ideia |
|---|---|
| **Carga/performance** | Artillery, k6, Locust; observar **throttling**, **cold start**, **concorrência** |
| **Resiliência/caos** | **AWS Fault Injection Service** (falhas controladas) |
| **Segurança** | Scanners de IaC (cfn-lint, cfn-guard, Checkov), `iam simulate`, testes de políticas |
| **Custo** | Estimativas + alarmes; testes curtos |
| **Idempotência/duplicatas** | Reenviar o mesmo evento |

## 9. Anti-padrões

- **Só testes com mocks** (confiança ilusória).
- **Só E2E na nuvem** (lentos, caros, instáveis).
- **Testar contra produção**.
- **Handler “gordo”** (lógica + SDK misturados, difícil de testar).
- **Clientes do SDK criados dentro de funções** sem possibilidade de substituição.
- **Dados reais** em testes.
- **Recursos de teste não destruídos** (custo).
- **Testes dependentes de ordem/estado compartilhado**.
- **Ignorar IAM** nos testes (só descobre em produção).
- **Eventos de teste inventados** que **não correspondem** ao formato real.

## 10. Erros comuns

- **Confundir mock com fake** e esperar comportamento de serviço.
- **Mockar tudo** e não testar a **integração**.
- **Evento de teste com formato errado** (ex.: `body` já objeto em vez de string).
- **Não separar a lógica** do handler.
- **Emulador diferente do serviço real** em detalhes (consistência, erros, limites).
- **Esquecer credenciais falsas** nos testes unitários (o SDK tenta resolver a chain e **atrasa**/falha).
- **Testes que chamam a AWS real por acidente** (mock mal aplicado).
- **Sem teto de custo** na conta de teste.

## 11. Troubleshooting

| Sintoma | Causa provável | Ação |
|---|---|---|
| Teste unitário **tenta rede/AWS** | Mock não aplicado ao cliente certo/região | Aplicar o mock **antes** de criar o cliente; definir **credenciais/região falsas** |
| Passa local, falha na nuvem | **IAM**, evento real diferente, config | Teste de integração em conta real; comparar **evento real** |
| Teste lento | Cliente real/emulador pesado | Mock/Moto in-process; paralelizar |
| Teste **intermitente (flaky)** | Dependência de tempo/rede/ordem | Determinismo, retries controlados, isolamento |
| Divergência emulador × AWS | Recurso não suportado/versão | Teste real para esse trecho |
| Custos inesperados | Stacks esquecidos | Teardown automático + budgets |

## 12. Resumo rápido

- **Camadas**: **unitário** (rápido, mocks) → **integração local** (emuladores) → **integração na nuvem** (conta de teste) → **E2E/smoke**.
- **Dublês**: **stub** devolve, **mock** verifica, **fake** funciona simplificado, **emulador** imita a API, **serviço real** é a verdade.
- **Mocks dão velocidade, mas falso positivo**; **IAM/eventos/cotas só se validam na nuvem**.
- **Testabilidade**: separar lógica do handler, **injeção de dependência**, config por ambiente, eventos de exemplo versionados.
- **Ambientes**: **contas separadas**, **stacks efêmeros**, **dados sintéticos**, **limpeza** e **budgets**.
- **Pegadinha de prova**: escolher a **ferramenta/abordagem** certa por cenário (SAM local, mock integration, eventos de teste).

## 🧩 Quiz de Fixação

1. Qual a diferença entre stub, mock e fake?
2. Por que testes só com mocks geram falsos positivos?
3. O que deve ser validado apenas na nuvem real?
4. Como tornar um handler Lambda mais testável?
5. Por que usar contas separadas para testes?
6. Quando preferir emulador a serviço real?
7. O que é um smoke test?

**Respostas:**

1. Stub devolve respostas pré-programadas; mock verifica interações (chamadas e argumentos); fake é uma implementação funcional simplificada (ex.: Moto).
2. Porque o mock concorda com o código, não com o serviço real; tipos, condições e permissões podem estar errados e passar despercebidos.
3. IAM/permissões, eventos reais, cotas/throttling, mapeamentos do API Gateway, VPC/KMS e comportamento de produção.
4. Separando a lógica em módulo puro, injetando dependências (clientes/repositórios), lendo configuração de variáveis de ambiente e guardando eventos de exemplo.
5. Para isolar riscos e custos, evitar impacto em produção e permitir stacks efêmeros com limpeza e budgets.
6. Quando a velocidade e o custo importam e o comportamento emulado basta (lógica e fluxos), reservando o serviço real para IAM, eventos e configurações reais.
7. Um conjunto pequeno de verificações críticas executado logo após o deploy para confirmar que o ambiente funciona.
