### 6.1.1.1. Testes no pipeline de CI — CodeBuild, relatórios de teste e cobertura, estágios, testes flaky, troubleshooting de testes e checklist de qualidade

> [!warning] Aviso
> Sintaxe do `buildspec`, formatos de relatório aceitos, limites do CodeBuild e integrações do CodePipeline/CodeDeploy abaixo são **de memória e mudam**. **Confirme na documentação do AWS CodeBuild (“Test reports”, “Build specification reference”), CodePipeline e CodeDeploy.** YAML, comandos e comandos de CLI são ilustrativos e **não foram executados**. Contas, ARNs e nomes são fictícios.

## 1. Onde os testes vivem no ciclo de entrega

```
Commit/PR ─▶ [Build + testes unitários + lint + SAST] ─▶ [Deploy em ambiente efêmero/test]
          ─▶ [Testes de integração] ─▶ [Deploy em staging] ─▶ [Smoke/E2E] ─▶ [Aprovação] ─▶ [Deploy em prod + smoke + monitoração]
```

| Estágio | Testes | Velocidade desejada |
|---|---|---|
| **Pull request** | **Unitários**, lint, análise estática, **validação de templates** (cfn-lint) | **Minutos** (feedback rápido) |
| **Pós-merge (test/dev)** | **Integração** (emuladores e/ou stack efêmero) | 5–20 min |
| **Staging** | **E2E**, **contrato**, **carga leve**, **segurança** (DAST) | 10–60 min |
| **Produção** | **Smoke** + **canário** + alarmes/rollback | Segundos–minutos |

> **Princípio**: quanto **mais cedo**, **mais rápido e barato** o teste; coloque os **lentos/caros** **mais tarde** e **em menos quantidade**.

## 2. AWS CodeBuild: executando testes

### 2.1 `buildspec.yml` típico (Python/SAM)

```yaml
version: 0.2
env:
  variables:
    AWS_DEFAULT_REGION: us-east-1
    AWS_ACCESS_KEY_ID: testing            # credenciais FALSAS para unitários (nunca chaves reais)
    AWS_SECRET_ACCESS_KEY: testing
phases:
  install:
    runtime-versions: { python: 3.12 }
    commands:
      - pip install -r requirements-dev.txt
  pre_build:
    commands:
      - cfn-lint template.yaml
      - ruff check src tests
  build:
    commands:
      - pytest tests/unit --junitxml=reports/unit.xml --cov=src --cov-report=xml:reports/coverage.xml --cov-fail-under=80
  post_build:
    commands:
      - sam build
reports:
  testes-unitarios:
    files: ["unit.xml"]
    base-directory: reports
    file-format: JUNITXML
  cobertura:
    files: ["coverage.xml"]
    base-directory: reports
    file-format: COBERTURAXML
artifacts:
  files: ["**/*"]
  base-directory: .aws-sam/build
cache:
  paths: ["/root/.cache/pip/**/*"]
```

### 2.2 Fases do buildspec

| Fase | Uso | Comportamento em falha |
|---|---|---|
| **`install`** | Runtimes e dependências | Falha → build **falha** |
| **`pre_build`** | Login, lint, validações | Falha → **pula** `build` |
| **`build`** | Compilar e **rodar testes** | Falha → build **falha** (mas `post_build` **ainda roda**, **a menos que** configurado) |
| **`post_build`** | Empacotar, notificar, **publicar relatórios** | Roda **mesmo se `build` falhar** (verifique `$CODEBUILD_BUILD_SUCCEEDING`) |
| **`reports`** | Publicar **relatórios de teste/cobertura** | Independe do status dos comandos |
| **`finally`** (dentro da fase) | **Limpeza** (teardown) | Roda **mesmo com falha** na fase |

```yaml
phases:
  build:
    commands:
      - sam deploy --stack-name app-pr-$PR_ID --no-confirm-changeset
      - pytest tests/integracao
    finally:
      - sam delete --stack-name app-pr-$PR_ID --no-prompts     # limpeza garantida
```

### 2.3 Relatórios de teste do CodeBuild (Test reports)

| Formato de teste | Cobertura de código |
|---|---|
| **JUnit XML**, **NUnit/NUnit3**, **Cucumber JSON**, **TestNG XML**, **Visual Studio TRX** | **JaCoCo XML**, **Clover XML**, **Cobertura XML**, **SimpleCov JSON** |

| Recurso | Detalhe |
|---|---|
| **Grupos de relatórios** | Agregam execuções; **tendência** ao longo do tempo |
| **Métricas** | **Aprovados/falhos/ignorados**, **duração**; **cobertura** (linhas/branches) |
| **Falhas detalhadas** | Mensagens e stack traces **no console** |
| **Exportação** | Para **S3** (opcional) |
| **Permissões** | **Service role** precisa de `codebuild:CreateReportGroup/CreateReport/UpdateReport/BatchPutTestCases/BatchPutCodeCoverages` |
| **Integração com PR** | Resultado do **status check** (via CodeBuild webhook/GitHub) |

### 2.4 Variáveis de ambiente úteis do CodeBuild

| Variável | Significado |
|---|---|
| **`CODEBUILD_BUILD_ID`/`CODEBUILD_BUILD_NUMBER`** | Identificador/numeração do build |
| **`CODEBUILD_SOURCE_VERSION`** | Commit/branch/PR |
| **`CODEBUILD_BUILD_SUCCEEDING`** | `1` se **até agora** deu certo (útil em `post_build`) |
| **`CODEBUILD_WEBHOOK_TRIGGER`** | Ex.: `pr/123`, `branch/main` |
| **`CODEBUILD_RESOLVED_SOURCE_VERSION`** | SHA do commit |

### 2.5 Pontos de atenção do CodeBuild

| Ponto | Detalhe |
|---|---|
| **Docker** | Para `sam local`/LocalStack/Testcontainers, habilite **modo privilegiado** (`privilegedMode: true`) |
| **Cache** | **Local** (Docker/source/custom) ou **S3** para acelerar |
| **Rede/VPC** | Para testar contra **recursos privados** (RDS, endpoints), rode o build **na VPC** |
| **Timeouts** | Padrão 60 min (configurável) |
| **Paralelismo** | **Batch builds** (matriz) para **dividir** a suíte |
| **Segredos** | **Parameter Store/Secrets Manager** no `env` (`parameter-store:`/`secrets-manager:`) — **não** em texto no buildspec |
| **Imagens** | Imagens **gerenciadas** ou **customizadas** (ECR) com dependências pré-instaladas |
| **Custo** | Por **minuto** e tamanho da instância |

## 3. CodePipeline e CodeDeploy: testes como portões

| Componente | Papel |
|---|---|
| **CodePipeline** | Orquestra **estágios** (Source → Build/Test → Deploy test → Test → Approval → Deploy prod) |
| **Ação de teste (CodeBuild)** | Executa testes de integração/E2E como **ação** do estágio |
| **Aprovação manual** | **Portão** antes de produção |
| **CodeDeploy (Lambda/ECS)** | **Hooks `BeforeAllowTraffic`/`AfterAllowTraffic`** executam **funções de teste** durante o **deploy gradual** (canário/linear) |
| **Alarmes do CloudWatch** | **Rollback automático** se métricas piorarem |
| **SAM `DeploymentPreference`** | Configura **canário/linear** + **hooks** + **alarmes** |

```yaml
# SAM: deploy gradual com hooks de teste e alarmes (trecho)
PedidosFunction:
  Type: AWS::Serverless::Function
  Properties:
    AutoPublishAlias: live
    DeploymentPreference:
      Type: Canary10Percent5Minutes
      Alarms: [!Ref ErrosAlarm, !Ref LatenciaAlarm]
      Hooks:
        PreTraffic: !Ref SmokePreTrafficFunction      # roda ANTES de enviar tráfego à nova versão
        PostTraffic: !Ref SmokePosTrafficFunction     # roda DEPOIS
```

```python
# função de hook (PreTraffic): valida a nova versão e reporta ao CodeDeploy
import boto3
codedeploy = boto3.client("codedeploy"); lam = boto3.client("lambda")

def handler(event, context):
    status = "Succeeded"
    try:
        r = lam.invoke(FunctionName=NOVA_VERSAO, Payload=b'{"smoke": true}')       # smoke test
        if r.get("FunctionError"): status = "Failed"
    except Exception:
        status = "Failed"
    codedeploy.put_lifecycle_event_hook_execution_status(
        deploymentId=event["DeploymentId"], lifecycleEventHookExecutionId=event["LifecycleEventHookExecutionId"], status=status)
```

> [!tip] Pegadinha de prova
> “Como **validar uma nova versão do Lambda antes de receber tráfego** e **reverter automaticamente**?” → **CodeDeploy** com **`DeploymentPreference`** (canário/linear), **hook `PreTraffic`** de teste e **alarmes do CloudWatch** para **rollback**.

## 4. Organizando a suíte para CI

| Estratégia | Detalhe |
|---|---|
| **Marcadores/tags** | `@pytest.mark.unit/integration/e2e` → **estágios** executam o que cabe |
| **Pastas separadas** | `tests/unit`, `tests/integration`, `tests/e2e` |
| **Paralelização** | `pytest -n auto`, **batch builds**, **sharding** |
| **Ordem** | **Rápidos primeiro** (fail-fast) |
| **Cache** | Dependências/imagens |
| **Reexecução seletiva** | Rodar **só afetados** (monorepo) |
| **Matriz** | Várias versões de **runtime** (Python 3.11/3.12…) |
| **Deploy de teste efêmero** | **Um stack por PR** com **limpeza** |
| **Portões de qualidade** | **Cobertura mínima**, **sem vulnerabilidades críticas**, **lint limpo** |

### 4.1 Cobertura: usar com bom senso

| Boa prática | Por quê |
|---|---|
| **Meta realista** (ex.: ≥ 80% de **lógica**) | Evita **corrida** por números |
| **Branch coverage** | Mais informativa que linhas |
| **Não perseguir 100%** | Custo × valor decrescente; **handlers magros** ajudam |
| **Cobertura ≠ qualidade** | Testes sem **asserções** inflam o número |
| **Mutation testing** (opcional) | Mede se os testes **detectam mudanças** |
| **Cobertura nos PRs** | **Delta** de cobertura (não só total) |

## 5. Testes flaky (instáveis)

**Flaky** = passa e falha **sem mudança de código**. Em testes AWS, as fontes típicas:

| Causa | Exemplo | Correção |
|---|---|---|
| **Consistência eventual/assincronia** | Ler logo após evento do S3/Streams | **Polling com timeout** (não `sleep` fixo) |
| **Dependência de tempo/relógio** | Expiração, `now()` | **Injetar relógio**; congelar o tempo (`freezegun`) |
| **Estado compartilhado** | Tabela/bucket comum entre testes/execuções | **IDs únicos**, isolamento, limpeza |
| **Ordem de execução** | Um teste depende de outro | Independência; **randomizar ordem** |
| **Concorrência/limites** | **Throttling**/cotas em contas compartilhadas | Serializar; aumentar cotas; backoff |
| **Rede/Docker** | Container do emulador **ainda subindo** | **Health checks** e espera ativa |
| **Cold start/timeouts** | Primeira invocação lenta | Timeouts adequados; **warm-up** |
| **Dados aleatórios sem seed** | Faker | **Seed fixa** |
| **Recursos órfãos** de execuções anteriores | Conflito de nomes | Nomes únicos + varredura |
| **Dependência de serviços de terceiros** | API externa instável | **Mock/WireMock** |

```python
# espera ativa com timeout (em vez de sleep)
def aguardar(cond, timeout=15, passo=0.3):
    import time; fim = time.time() + timeout
    while time.time() < fim:
        if cond(): return
        time.sleep(passo)
    raise AssertionError("timeout aguardando condição")
```

| Política para flaky | Detalhe |
|---|---|
| **Detectar** | Relatórios de tendência (CodeBuild reports), reexecução em **nightly** |
| **Quarentena** | Marcar `@flaky`/**isolar** num job **não bloqueante** **com prazo** para corrigir |
| **Retry limitado** | `pytest-rerunfailures` (**1–2×**) — **não esconder** a causa |
| **Corrigir a raiz** | **Prioridade** (flaky corrói a confiança) |
| **Registrar** | Backlog de flaky com **dono** |

## 8. Boas práticas

1. **Feedback rápido** (unitários em minutos) e **fail-fast**.
2. **Pirâmide** na pipeline: **rápidos cedo**, **lentos tarde**.
3. **Relatórios e cobertura** publicados (CodeBuild reports) com **portões** razoáveis.
4. **Ambientes efêmeros** com **teardown** em `finally`.
5. **Credenciais falsas** nos unitários; **roles** nos de integração.
6. **Segredos** via **Secrets Manager/Parameter Store**.
7. **Eliminar flaky** (polling, relógio injetado, isolamento).
8. **Hooks de teste** + **alarmes** no deploy gradual (**CodeDeploy**).
9. **Smoke** pós-deploy e **canaries** contínuos.
10. **Métricas da pipeline** acompanhadas e **notificações** de falha.
11. **Reprodutibilidade**: versões **fixadas** (runtime, dependências, imagens).

## 9. Erros comuns

- **Suíte única lenta** rodando tudo em cada commit.
- **`sleep` fixo** em vez de polling.
- **Testes de integração sem teardown** (custos/órfãos).
- **Credenciais reais** no buildspec.
- **Cobertura como meta absoluta** (testes sem asserções).
- **Ignorar flaky** (“roda de novo”).
- **Não publicar relatórios** (difícil diagnosticar).
- **CodeBuild sem `privilegedMode`** ao usar Docker/LocalStack.
- **Role do CodeBuild sem permissões de relatório**.
- **Depender de `post_build` achando que só roda em sucesso**.
- **Sem alarmes/rollback** no deploy gradual.
- **Versões não fixadas** (“quebrou do nada”).

## 10. Troubleshooting

| Sintoma | Causa provável | Ação |
|---|---|---|
| Relatório **não aparece** | `reports` com caminho/formato errado; faltam permissões | Conferir `base-directory`/`files`/`file-format`; **permissões de relatório** |
| `Cannot connect to the Docker daemon` no CodeBuild | Sem **modo privilegiado** | `privilegedMode: true` |
| Testes passam local, falham no CI | Versões/ambiente diferentes, relógio, rede, credenciais | **Fixar versões**; replicar ambiente (imagem); ver logs |
| `NoCredentialsError` no CI (unitários) | Sem credenciais falsas | Variáveis de ambiente falsas |
| `AccessDenied` nos de integração | Role do build sem permissão | Ajustar **service role** (menor privilégio) |
| Build **lento** | Sem cache/paralelismo | Cache, **batch builds**, `-n auto` |
| **Flaky** intermitente | Assincronia/estado | Polling, isolamento, relógio |
| Stack de PR **não deletado** | Falha no `finally`/dependências | Teardown robusto; varredura TTL |
| Hook PreTraffic **timeout** | Smoke lento/permissão | Ajustar timeout; permitir `codedeploy:PutLifecycleEventHookExecutionStatus` |
| Cobertura **cai** sem mudança | Arquivos novos sem testes/config | Delta de cobertura; `--cov` correto |
| Pipeline **verde com bug em prod** | Mocks sem integração real | Mais **integração/E2E/smoke** |

## 11. Checklist de qualidade contínua

1. **Unitários rápidos** em todo PR (lint, tipos, SAST, cfn-lint).
2. **Relatórios JUnit + cobertura** publicados; **portão** de cobertura/qualidade.
3. **Integração** com emuladores e/ou **stack efêmero**; **teardown** garantido.
4. **E2E/contrato** em staging; **smoke** pós-deploy.
5. **Deploy gradual** com **hooks** e **alarmes** (rollback automático).
6. **Credenciais**: falsas (unit), **roles** (integração), **OIDC**; **segredos** em cofre.
7. **Flaky** monitorado e tratado.
8. **Métricas e notificações** da pipeline.
9. **Versões fixadas** e **imagens de build** controladas.
10. **Custos** do CI e dos ambientes de teste monitorados.

## 12. Resumo rápido

- **Pipeline em camadas**: **PR (unitários/lint)** → **integração (emulador/stack efêmero)** → **staging (E2E/contrato)** → **produção (smoke + canário + rollback)**.
- **CodeBuild**: `buildspec` com **fases** (`install/pre_build/build/post_build`), **`finally`** para limpeza, **`reports`** (**JUnit/Cobertura/JaCoCo…**), **modo privilegiado** para Docker, **VPC** para recursos privados, **batch builds** para paralelizar.
- **CodeDeploy + SAM `DeploymentPreference`**: **canário/linear**, **hooks `PreTraffic/PostTraffic`**, **alarmes** → **rollback automático**.
- **Cobertura**: meta realista, **branch coverage**, delta em PR; **cobertura ≠ qualidade**.
- **Flaky**: causas (assincronia, relógio, estado, rede); **polling**, **injeção de relógio**, **isolamento**, **quarentena com prazo**.
- **Observabilidade**: métricas de build, tendência de testes, alertas via **EventBridge/SNS**; **CloudWatch Synthetics** para **canaries**.

**Respostas:**

1. Testes: JUnit XML, NUnit, Cucumber JSON, TestNG, TRX; cobertura: JaCoCo, Clover, Cobertura e SimpleCov.
2. Executar comandos de limpeza (teardown) mesmo se a fase falhar.
3. CodeDeploy com SAM DeploymentPreference (canário/linear), hook PreTraffic de teste e alarmes do CloudWatch para reverter.
4. Teste que passa e falha sem mudança de código; tratar com polling, relógio injetado, isolamento, quarentena com prazo e correção da raiz.
5. Para permitir Docker dentro do build (sam local, LocalStack, Testcontainers).
6. Roda mesmo se o build falhar; é preciso verificar CODEBUILD_BUILD_SUCCEEDING antes de empacotar/publicar.
7. Porque testes sem asserções ou com mocks fracos inflam o número sem detectar defeitos.
