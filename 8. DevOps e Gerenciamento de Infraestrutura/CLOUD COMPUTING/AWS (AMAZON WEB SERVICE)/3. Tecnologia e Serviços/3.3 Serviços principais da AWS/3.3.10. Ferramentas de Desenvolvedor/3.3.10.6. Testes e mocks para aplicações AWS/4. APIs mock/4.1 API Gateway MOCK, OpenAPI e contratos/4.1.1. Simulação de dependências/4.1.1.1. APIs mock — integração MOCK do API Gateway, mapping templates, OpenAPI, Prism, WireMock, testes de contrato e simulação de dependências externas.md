### 4.1.1.1. APIs mock — integração MOCK do API Gateway, mapping templates, OpenAPI, Prism, WireMock, testes de contrato e simulação de dependências externas

> [!warning] Aviso
> Detalhes da integração MOCK (REST API vs HTTP API), sintaxe de mapping templates (VTL), extensões OpenAPI (`x-amazon-apigateway-*`) e opções de Prism/WireMock/Pact mudam entre versões. **Confirme na documentação do Amazon API Gateway, do Prism, do WireMock e do Pact.** Templates, JSON e comandos são ilustrativos e **não foram executados**. Esta nota cobre a skill **3.2.2 (APIs mock) do DVA-C03**.

## 1. Para que serve uma API mock

Uma **API mock** responde como se fosse o serviço real, **sem executar a lógica de backend**. Usos principais:

| Uso | Exemplo |
|---|---|
| **Desenvolvimento paralelo** | Front-end/mobile consome a API **antes** de o backend existir |
| **Testar clientes** | Simular **sucesso, erros (4xx/5xx), lentidão e payloads estranhos** |
| **Isolar dependências externas** | Substituir **provedor de pagamento/ERP/API de terceiros** em testes |
| **Prototipar contrato** | Validar o **desenho da API** com stakeholders |
| **Ambientes sem custo/risco** | Demos, treinamentos, **sandbox** |
| **Testes de resiliência** | Forçar **timeouts**, **429**, **500** e ver retries/circuit breaker |
| **Testes de carga do cliente** | Sem sobrecarregar um backend real |

## 2. Integração **MOCK** do Amazon API Gateway

### 2.1 O que é

No **API Gateway (REST API)**, o tipo de integração **`MOCK`** faz o **próprio gateway** gerar a resposta, **sem chamar nenhum backend** (nem Lambda, nem HTTP). Você controla **o status e o corpo** por **mapping templates**. É muito usada para:

- Retornar **respostas estáticas**;
- Responder ao **preflight CORS** (`OPTIONS`) — o uso **mais comum**;
- **Prototipar** rapidamente uma rota.

### 2.2 Como funciona o fluxo (REST API)

```
Cliente ─▶ Method Request ─▶ Integration Request ─▶ [MOCK: sem backend] ─▶ Integration Response ─▶ Method Response ─▶ Cliente
                              │ mapping template (request)                    │ mapping template (response)
                              │ define o statusCode da "chamada" mock          │ transforma em corpo/headers finais
```

1. **Integration Request** com **template** que retorna um JSON com **`statusCode`** — é isso que o gateway usa para **selecionar a resposta**:

```
{"statusCode": 200}
```

2. **Integration Response** (por **status** selecionado, via **regex de seleção**) aplica um **template de resposta** com o **corpo** desejado.
3. **Method Response** declara os **status/headers** permitidos.

### 2.3 Exemplo: mock estático com SAM/OpenAPI

```yaml
# template.yaml (trecho) — REST API com integração MOCK
Resources:
  ApiMock:
    Type: AWS::Serverless::Api
    Properties:
      StageName: dev
      DefinitionBody:
        openapi: "3.0.1"
        info: { title: "api-mock", version: "1.0" }
        paths:
          /pedidos/{id}:
            get:
              parameters: [{ name: id, in: path, required: true, schema: { type: string } }]
              responses:
                "200": { description: ok }
                "404": { description: nao encontrado }
              x-amazon-apigateway-integration:
                type: mock
                requestTemplates:
                  application/json: |
                    #if($input.params('id') == "999")
                      {"statusCode": 404}
                    #else
                      {"statusCode": 200}
                    #end
                responses:
                  "200":
                    statusCode: "200"
                    responseTemplates:
                      application/json: |
                        {"id": "$input.params('id')", "valor": 10, "status": "PAGO"}
                  "404":
                    statusCode: "404"
                    responseTemplates:
                      application/json: '{"erro": "pedido não encontrado"}'
```

### 2.4 Pontos-chave da integração MOCK

| Ponto | Detalhe |
|---|---|
| **Tipo de integração** | `MOCK` (somente **REST APIs**; **HTTP APIs** não têm integração MOCK equivalente — confirmar) |
| **`statusCode` no template de requisição** | **Obrigatório** para o gateway escolher a **Integration Response** |
| **Seleção da resposta** | Por **regex** no `selectionPattern` ou pelo **status** retornado |
| **Corpo/headers** | **Mapping templates (VTL)** e **mapeamento de headers** na Integration Response |
| **Variáveis úteis (VTL)** | `$input.params()`, `$input.json()`, `$context.*`, `$util.*`, `$stageVariables` |
| **Dinamismo** | Limitado: **lógica condicional simples** em VTL |
| **Autorizadores/CORS/API keys/WAF** | **Funcionam** normalmente (são camadas **antes** da integração) |
| **Custo** | **Sem invocação de Lambda**; paga **requisições do API Gateway** |
| **Uso em produção** | **Preflight CORS**, rotas de **teste/healthcheck**; **evite** lógica de negócio |

### 2.4.1 CORS com MOCK (padrão clássico)

O “Enable CORS” do console cria um método `OPTIONS` com **integração MOCK** que devolve os cabeçalhos:

```yaml
options:
  responses:
    "200":
      description: CORS
      headers:
        Access-Control-Allow-Origin: { schema: { type: string } }
        Access-Control-Allow-Methods: { schema: { type: string } }
        Access-Control-Allow-Headers: { schema: { type: string } }
  x-amazon-apigateway-integration:
    type: mock
    requestTemplates: { application/json: '{"statusCode": 200}' }
    responses:
      default:
        statusCode: "200"
        responseParameters:
          method.response.header.Access-Control-Allow-Origin: "'https://app.exemplo.com'"
          method.response.header.Access-Control-Allow-Methods: "'GET,POST,OPTIONS'"
          method.response.header.Access-Control-Allow-Headers: "'Content-Type,Authorization'"
```

> [!tip] Pegadinha de prova
> “Como **responder ao preflight CORS** sem Lambda?” → **integração MOCK** no método `OPTIONS` com `{"statusCode": 200}` e **cabeçalhos CORS** na **Integration Response**. “Como **prototipar** uma API **sem backend**?” → **MOCK integration**.

### 2.5 Testando a integração MOCK

| Forma | Uso |
|---|---|
| **Console → Test** (método) | Envia uma requisição simulada e mostra **logs de execução** |
| **`aws apigateway test-invoke-method`** | Via CLI (**confirmar** parâmetros) |
| **`curl` no stage implantado** | Após **deploy** (`create-deployment`) |
| **Logs de execução do API Gateway** | Mostram **template aplicado** e **status selecionado** |

```bash
aws apigateway test-invoke-method --rest-api-id abc123 --resource-id r1 --http-method GET \
  --path-with-query-string "/pedidos/1"
curl -i https://abc123.execute-api.us-east-1.amazonaws.com/dev/pedidos/1
```

### 2.6 Limites da integração MOCK

- **Sem estado** (não “lembra” de POSTs anteriores).
- **VTL** é **desconfortável** para respostas complexas/dinâmicas.
- **Mudanças exigem deploy** do stage.
- Para **comportamento rico** (estado, atrasos, falhas aleatórias), use **Lambda mock**, **WireMock/Prism** ou um **serviço de stub** em container.

## 3. Mock com Lambda (alternativa simples e dinâmica)

Quando você precisa de **lógica** (variar resposta por entrada, simular erro 1 a cada N chamadas, latência), um **Lambda “fake”** atrás de API Gateway/Function URL é mais flexível:

```python
import json, random, time

def handler(event, context):
    caminho = event.get("rawPath", "")
    # atraso simulado e falhas controladas por header de teste
    h = {k.lower(): v for k, v in (event.get("headers") or {}).items()}
    time.sleep(float(h.get("x-mock-delay", 0)))
    if h.get("x-mock-status"):
        return {"statusCode": int(h["x-mock-status"]), "body": json.dumps({"erro": "simulado"})}
    if caminho.startswith("/pagamentos"):
        return {"statusCode": 201, "headers": {"Content-Type": "application/json"},
                "body": json.dumps({"id": "pg_123", "status": "APROVADO"})}
    return {"statusCode": 404, "body": json.dumps({"erro": "rota não mockada"})}
```

| Vantagem | Limitação |
|---|---|
| **Lógica livre**, atrasos, falhas | **Custo/latência** de Lambda |
| **Versionado como código** | Precisa de **deploy** |
| **Ideal para sandbox compartilhado** | Para **uso local**, prefira WireMock/Prism |

## 4. Mocks baseados em OpenAPI: Prism, e “contrato primeiro”

### 4.1 Contrato como fonte da verdade

O **OpenAPI** descreve rotas, parâmetros, **schemas** e **exemplos**. A partir dele você pode:

| Ferramenta | O que faz |
|---|---|
| **Prism (Stoplight)** | **Servidor mock** gerado do OpenAPI (respostas dos `examples`/schemas), com **validação** de requisições |
| **API Gateway import** | Importar OpenAPI → criar a API (com `x-amazon-apigateway-integration` mock) |
| **Swagger Codegen/OpenAPI Generator** | Clientes/servers e **stubs** |
| **Dredd/Schemathesis** | Testar **o backend real contra o contrato** |

```bash
# Prism: mock local a partir do contrato
prism mock openapi.yaml -p 4010
curl -i http://127.0.0.1:4010/pedidos/1
curl -i -H "Prefer: code=404" http://127.0.0.1:4010/pedidos/1            # força uma resposta de exemplo específica
prism proxy openapi.yaml https://api.real.exemplo.com                     # valida tráfego real contra o contrato (proxy)
```

```yaml
# openapi.yaml (trecho com exemplos)
paths:
  /pedidos/{id}:
    get:
      responses:
        "200":
          description: ok
          content:
            application/json:
              schema: { $ref: "#/components/schemas/Pedido" }
              example: { id: "1", valor: 10, status: "PAGO" }
        "404":
          description: não encontrado
          content: { application/json: { example: { erro: "pedido não encontrado" } } }
```

### 4.2 Fluxo “contrato primeiro”

```
1) Equipes acordam o OpenAPI (revisão)
2) Front sobe Prism (mock) e desenvolve em paralelo
3) Back implementa; pipeline roda testes de contrato (Dredd/Schemathesis) contra o back
4) Front troca a URL do mock pela real
```

| Benefício | Detalhe |
|---|---|
| **Paralelismo** | Front e back **não se bloqueiam** |
| **Mudanças visíveis** | O contrato é **versionado** |
| **Qualidade** | Testes automáticos detectam **quebra de contrato** |

## 5. WireMock e simulação de APIs de terceiros

**WireMock** (e similares: **MockServer**, **Mountebank**, **MSW** no navegador/Node) simula **APIs HTTP** com **regras** de correspondência e respostas, inclusive **falhas e atrasos**.

```json
{
  "request":  { "method": "POST", "urlPath": "/v1/cobrancas", "headers": { "Authorization": { "matches": "Bearer .+" } } },
  "response": { "status": 201, "jsonBody": { "id": "ch_123", "status": "aprovado" },
                "headers": { "Content-Type": "application/json" }, "fixedDelayMilliseconds": 200 }
}
```

| Cenário simulado | Como |
|---|---|
| **Erro 500/503** | `response.status` |
| **Latência/timeout** | `fixedDelayMilliseconds`/`fault: "CONNECTION_RESET_BY_PEER"` |
| **Falha intermitente** | **Cenários** (estados: 1ª chamada falha, 2ª ok) |
| **Rate limit (429)** | Respostas com `Retry-After` |
| **Respostas dinâmicas** | **Templating** (Handlebars) |
| **Verificar chamadas** | `verify(postRequestedFor(...))` |
| **Gravação/replay** | **Record/playback** de API real (cuidado com **dados sensíveis**) |

```bash
docker run -p 8080:8080 -v $PWD/mappings:/home/wiremock/mappings wiremock/wiremock
# aplicação sob teste usa BASE_URL=http://localhost:8080 em vez da API real
```

> [!tip] Em ambientes AWS
> Sirva WireMock em **ECS/Fargate** (ou container no CI) e configure a **URL do provedor externo** por **variável de ambiente/SSM Parameter** para apontar ao **mock** em **dev/test** e à **API real** em **produção**.

## 6. Testes de contrato (consumer-driven) com Pact

| Conceito | Detalhe |
|---|---|
| **Problema** | Mocks **divergem** da API real com o tempo (“mock mentiroso”) |
| **Pact** | O **consumidor** escreve **expectativas** (requisição → resposta) → gera um **contrato (pact file)** |
| **Verificação do provedor** | O **provedor** executa o pact contra **seu serviço real** (ou stub) e **falha** se quebrar |
| **Broker** | **Pact Broker** compartilha contratos e controla **can-i-deploy** |
| **Benefício** | **Mocks confiáveis** e **deploys independentes** |
| **Quando usar** | **Microsserviços** de equipes diferentes |

```
Consumidor: testes com mock Pact → publica pact → Broker
Provedor:   CI baixa pact → verifica contra serviço real → publica resultado
Deploy:     can-i-deploy? (compatível?) → libera
```

## 7. Mocks de serviços AWS “do lado de fora” (resumo)

| Necessidade | Ferramenta |
|---|---|
| Simular **S3/DynamoDB/SQS** no código | **Moto** / **Stubber** (nota anterior) |
| Simular **Lambda/API Gateway/filas** localmente | **SAM local / LocalStack** |
| Simular **API de terceiros** | **WireMock/Prism/MSW** |
| Simular **API Gateway** sem backend | **Integração MOCK** |
| Simular **eventos** | **`sam local generate-event`**, eventos de teste |
| Simular **falhas de infraestrutura** | **AWS Fault Injection Service** (na nuvem) |

## 8. Padrões para simular falhas e variações

| Simulação | Como no mock |
|---|---|
| **Sucesso** | 200/201 com corpo válido |
| **Validação** | 400 com lista de erros |
| **Não autorizado** | 401/403 |
| **Não encontrado** | 404 |
| **Conflito/idempotência** | 409 / reenvio da mesma chave |
| **Throttling** | **429** + `Retry-After` |
| **Erro do servidor** | 500/502/503/504 |
| **Lentidão/timeout** | Atraso > timeout do cliente |
| **Payload inesperado** | Campos extras/ausentes, tipos diferentes |
| **Resposta enorme** | Testar limites/streaming |
| **Falha intermitente** | Cenário: erro nas 2 primeiras chamadas, ok na 3ª (testa **retries**) |

> Esses cenários validam **retries com backoff**, **timeouts**, **circuit breaker**, **idempotência** e **mensagens de erro** do **cliente** — sem tocar a API real.

## 9. Boas práticas

1. **Contrato primeiro** (OpenAPI) e **mock gerado do contrato**.
2. **Testes de contrato** para evitar “mock mentiroso”.
3. **URLs de dependências externas configuráveis** (env/SSM) — apontar ao mock em teste.
4. **Cobrir erros e lentidão**, não só o caminho feliz.
5. **MOCK integration** para **CORS preflight** e protótipos; **não** para lógica de negócio.
6. **Marcar claramente** ambientes mock (headers `X-Mock: true`) para **não confundir** com produção.
7. **Versionar** mappings/respostas junto do código.
8. **Dados fictícios** nos mocks (nunca dados reais).
9. **Isolar** mocks por teste (estado limpo).
10. **Substituir** mocks por **serviço real** em testes de integração críticos.

## 10. Erros comuns

- **Template MOCK sem `{"statusCode": ...}`** → resposta 500/erro de mapeamento.
- **Esquecer o deploy do stage** após alterar a integração.
- **Method Response sem declarar o status/headers** → integração não aplica.
- **Esperar lógica rica/estado** em MOCK integration.
- **Mock desatualizado** em relação ao contrato real.
- **Mock em produção** acidentalmente (rota mock exposta).
- **Cobrir só o sucesso** (sem erros/timeouts).
- **Dados reais** gravados por record/playback.
- **CORS** com `Access-Control-Allow-Origin: *` indevido em ambientes reais.
- **Confundir HTTP API com REST API** (MOCK é do REST API).
- **Respostas mock sem `Content-Type`** adequado.

## 11. Troubleshooting

| Sintoma | Causa provável | Ação |
|---|---|---|
| 500 “Internal server error” na rota MOCK | Template de requisição sem `statusCode` válido; mapeamento ausente | Corrigir template; ver **logs de execução** |
| Corpo vazio | Integration Response sem `responseTemplates` | Adicionar template |
| Preflight falha no navegador | Cabeçalhos CORS ausentes na **Integration Response**/**Method Response** | Configurar `OPTIONS` com MOCK + headers |
| Mudança não aparece | Sem **deployment** | `create-deployment` |
| Status errado | `selectionPattern`/lógica VTL | Revisar regex/condição |
| Prism rejeita requisição | Violou o contrato (schema) | Ajustar a requisição ou o contrato |
| WireMock “no match” | Regra não casa (método/URL/headers) | Ver **/__admin/requests/unmatched** |
| Teste passa com mock, falha com real | Mock divergente | **Teste de contrato/integração** |

## 12. Resumo rápido

- **API mock** responde **sem backend real**: protótipos, desenvolvimento paralelo, testes de **cliente**, **falhas/latência**.
- **API Gateway MOCK integration** (REST API): o gateway responde sozinho; template de requisição retorna **`{"statusCode": N}`**; **Integration Response** monta o corpo; uso clássico: **preflight CORS**.
- **Lambda mock** para **lógica/atraso/falha**; **Prism** (de **OpenAPI**) e **WireMock** (regras, falhas, cenários) para **local/CI**.
- **Contrato primeiro** + **Pact/Dredd/Schemathesis** evitam **mock mentiroso**.
- **URLs configuráveis** (env/SSM) para alternar **mock × real**.
- **Simule falhas**: 4xx/5xx/429/timeouts/intermitência para validar **retries e resiliência**.
