### 5.1.1.1. Segurança e governança em testes AWS — dados de teste, contas separadas, credenciais e OIDC no CI, IAM de teste, isolamento, custos, limpeza e conformidade

> [!warning] Aviso
> Recursos e nomes de produtos (OIDC do GitHub Actions/CodeBuild, AWS Organizations, SCPs, Budgets, Config) e detalhes de políticas abaixo são **de memória e mudam**. **Confirme na documentação da AWS e do seu provedor de CI.** Políticas JSON, YAML e comandos são ilustrativos e **não foram executados**. Contas, ARNs, repositórios e domínios são fictícios.

## 1. Por que governar os testes

Testes **tocam recursos reais** (quando saem do mock) e costumam rodar em **automação** com **credenciais poderosas**. Os riscos típicos:

| Risco | Exemplo |
|---|---|
| **Testar em produção** | Um teste E2E apaga/duplica dados reais |
| **Vazar dados reais** | Cópia de produção em ambiente de teste (LGPD) |
| **Credenciais de longo prazo no CI** | Chaves em variáveis do pipeline, vazadas em logs/forks |
| **IAM excessivo no pipeline** | Pipeline com `AdministratorAccess` na conta de produção |
| **Custos descontrolados** | Stacks e recursos esquecidos; testes de carga |
| **Recursos órfãos** | Buckets/tabelas/filas acumulando |
| **Colisão entre testes/equipes** | Nomes iguais, dados compartilhados |
| **Testes que enviam e-mail/SMS reais** | Spam para clientes |
| **Chamadas a terceiros reais** | Cobranças/ações reais em APIs externas |
| **Segredos em fixtures/mocks** | Tokens reais em arquivos de teste |

## 2. Contas e ambientes separados

| Prática | Detalhe |
|---|---|
| **Uma conta por ambiente** | `dev`, `test/qa`, `staging`, `prod` (e **sandbox** por desenvolvedor) via **AWS Organizations** |
| **Unidades organizacionais (OUs)** | `Workloads/NonProd` e `Workloads/Prod` com **SCPs** diferentes |
| **Sem caminho de teste → prod** | Role de CI de teste **não** assume roles em prod |
| **Deploy em prod por pipeline dedicado** | Com **aprovações** e **menor privilégio** |
| **Rede isolada** | VPCs separadas, **sem peering** entre test e prod |
| **Observabilidade separada** | Logs/alarmes por conta (e agregação central) |
| **Tags obrigatórias** | `Environment`, `Owner`, `CostCenter`, `TTL` |

```
Organização
├─ OU Segurança   (log archive, audit)
├─ OU NonProd     (SCP: regiões limitadas, bloqueia serviços caros/sensíveis)
│   ├─ conta dev-sandbox-ana
│   ├─ conta test
│   └─ conta staging
└─ OU Prod        (SCP mais restritivas, mudanças só via pipeline)
```

### 2.1 SCPs úteis para contas de teste

| Controle | Ideia |
|---|---|
| **Restringir regiões** | Negar tudo fora de `us-east-1`/`sa-east-1` (`aws:RequestedRegion`) |
| **Bloquear serviços caros** | Negar tipos de instância/serviços não necessários |
| **Impedir desligar auditoria** | Negar `cloudtrail:StopLogging`, `config:Delete*` |
| **Exigir tags** | Negar criação sem `Owner`/`TTL` (via **tag policies**/condições) |
| **Impedir público** | Negar `s3:PutBucketPublicAccessBlock` removendo proteção |
| **Limitar tamanho** | Negar `ec2:RunInstances` acima de determinado tamanho |

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Sid": "NegarForaDeRegioesPermitidas",
    "Effect": "Deny",
    "NotAction": ["iam:*", "organizations:*", "sts:*", "support:*", "cloudfront:*", "route53:*"],
    "Resource": "*",
    "Condition": { "StringNotEquals": { "aws:RequestedRegion": ["us-east-1", "sa-east-1"] } }
  }]
}
```

## 3. Credenciais no CI: sem chaves de longo prazo

### 3.1 Princípios

| Princípio | Prática |
|---|---|
| **Roles em vez de usuários** | O pipeline **assume uma role** (credenciais **temporárias**) |
| **Federação OIDC** | GitHub Actions/GitLab/Bitbucket → **IAM OIDC provider** → `AssumeRoleWithWebIdentity` |
| **CodeBuild/CodePipeline** | Usam **service roles** (sem chaves) |
| **Condições na confiança** | Restringir **repositório, branch, ambiente** (`sub` do token) |
| **Menor privilégio** | Role de teste **só** cria/destrói recursos do stack de teste |
| **Sem segredos em código/fixtures** | Segredos no **Secrets Manager/SSM**/cofre do CI |
| **Rotação/expiração** | Sessões curtas (≤ 1 h) |
| **Auditoria** | **CloudTrail** mostra **quem** (sessão `repo:org/app:ref:refs/heads/main`) |

### 3.2 Trust policy para GitHub Actions (OIDC)

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": { "Federated": "arn:aws:iam::111111111111:oidc-provider/token.actions.githubusercontent.com" },
    "Action": "sts:AssumeRoleWithWebIdentity",
    "Condition": {
      "StringEquals": { "token.actions.githubusercontent.com:aud": "sts.amazonaws.com" },
      "StringLike":   { "token.actions.githubusercontent.com:sub": "repo:minha-org/meu-app:pull_request" }
    }
  }]
}
```

```yaml
# .github/workflows/test.yml (trecho)
permissions: { id-token: write, contents: read }
jobs:
  integracao:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::111111111111:role/ci-teste
          aws-region: us-east-1
          role-session-name: gh-${{ github.run_id }}
      - run: sam build && sam deploy --stack-name app-pr-${{ github.event.number }} --no-confirm-changeset
      - run: pytest tests/integracao
      - if: always()
        run: sam delete --stack-name app-pr-${{ github.event.number }} --no-prompts
```

> [!warning] PRs de forks
> Workflows disparados por **forks** **não devem** receber permissões de assumir roles (ou use **`pull_request`** sem segredos / **ambientes protegidos**). Restrinja o `sub` do token a **branches/ambientes** confiáveis para impedir que código **não revisado** use a role.

### 3.3 Role de CI de teste (menor privilégio)

| Permissão | Escopo |
|---|---|
| **CloudFormation** (`CreateStack/DeleteStack`…) | Somente **stacks com prefixo** `app-pr-*` |
| **Criação de recursos do stack** | Via **CloudFormation service role** (a role do CI **não** precisa de todas as permissões diretas) |
| **`iam:PassRole`** | Somente para **roles específicas do stack** |
| **S3 de artefatos** | **Bucket** do SAM/pipeline |
| **Permission boundary** | **Teto** para roles criadas pelo teste |
| **Sem** `iam:*` irrestrito | Evita **escalada de privilégios** |

```json
{
  "Sid": "SomenteStacksDePR",
  "Effect": "Allow",
  "Action": ["cloudformation:CreateStack", "cloudformation:UpdateStack", "cloudformation:DeleteStack", "cloudformation:Describe*"],
  "Resource": "arn:aws:cloudformation:us-east-1:111111111111:stack/app-pr-*/*"
}
```

## 4. Credenciais e segredos nos **testes**

| Prática | Detalhe |
|---|---|
| **Credenciais falsas em testes unitários** | `AWS_ACCESS_KEY_ID=testing` etc., para **nunca** usar chaves reais por acidente |
| **Bloquear rede nos unitários** (opcional) | Detecta chamadas reais (ex.: `pytest-socket`) |
| **Perfis nomeados** | `AWS_PROFILE=test` explícito; **não** depender do perfil default |
| **Sem segredos no repositório** | Scanners (**git-secrets**, **gitleaks**, **GitHub secret scanning**) |
| **Segredos de teste ≠ de produção** | **Chaves de API sandbox** do provedor |
| **Secrets Manager por ambiente** | `/test/app/chave-api` vs `/prod/app/chave-api` |
| **Rotação** | Para tokens de longa duração em ambientes compartilhados |
| **`.env` fora do Git** | `.gitignore`; **exemplo** sem valores (`.env.example`) |

## 5. Dados de teste

| Regra | Detalhe |
|---|---|
| **Dados sintéticos** | Gerados por **factories**/**Faker**; **nunca** CPF/e-mail/telefone reais |
| **Determinismo** | **Seeds** fixas para reprodutibilidade |
| **Sem cópia de produção** | Se for **inevitável**: **anonimizar/mascarar**/tokenizar, minimizar, **controle de acesso**, **retenção curta** |
| **Isolamento por teste** | Prefixos/IDs únicos (`test-{uuid}`) |
| **Mínimo necessário** | Dados **só do cenário** |
| **Fixtures versionadas** | Eventos/respostas **anonimizados** no repositório |
| **Validação de PII** | Scanner (**Macie** em buckets de teste, scanners de repositório) |
| **Domínios seguros** | E-mails em `@example.com`/`.invalid`; telefones de teste; **`+test`** |
| **Serviços de envio** | **SES sandbox**, **simulador de caixa postal** (`success@simulator.amazonses.com`), SNS **sandbox** de SMS |

```python
from faker import Faker
fake = Faker("pt_BR"); Faker.seed(1234)
pedido = {"id": f"test-{uuid4()}", "cliente": fake.name(), "email": "cliente@example.com", "cpf": fake.cpf()}   # CPF sintético válido, não real
```

> [!tip] E-mail e SMS
> Testes **nunca** devem enviar mensagens a **clientes reais**. Use **SES sandbox** (só envia a endereços **verificados**), o **simulador** do SES (`success@simulator.amazonses.com`, `bounce@…`, `complaint@…`) e números de **teste**.

## 6. Isolamento de testes

| Dimensão | Técnica |
|---|---|
| **Entre execuções** | **Stack por PR/branch**, nomes com **sufixo** único |
| **Entre testes** | Dados com **ID único**; limpeza **por teste** |
| **Entre equipes** | Contas **sandbox** individuais |
| **Concorrência** | Cuidado com **limites de serviço** (cotas) em contas de teste compartilhadas |
| **Estado compartilhado** | Evitar tabelas/buckets **globais** reutilizados; se necessário, **prefixos** por execução |
| **Ordem** | Testes **independentes** (sem depender de ordem) |
| **Tempo** | Evitar `sleep` fixo; **polling** com timeout |

## 7. Custos: evitar surpresas

| Mecanismo | Uso |
|---|---|
| **AWS Budgets** | **Orçamento** + alertas (e/ou **ações**, como aplicar **SCP/IAM deny** ao estourar) |
| **Cost Anomaly Detection** | Alerta de **picos** |
| **Tags de custo** (`Owner`, `PR`, `TTL`) | **Rateio** e identificação de órfãos |
| **TTL/limpeza automática** | Rotina remove stacks com `TTL` vencido |
| **Preferir serverless/PAY_PER_REQUEST** | Baixo custo ocioso |
| **Tamanhos mínimos** | Instâncias pequenas, **Single-AZ** em teste (quando adequado) |
| **Testes de carga controlados** | Janelas, limites, **aviso prévio** (política de testes de segurança/carga da AWS — **confirmar**) |
| **Gravar menos logs** | Retenção curta (`RetentionInDays`) |
| **Emuladores** | Reduzem chamadas à AWS real |

## 8. Limpeza (teardown) confiável

| Prática | Detalhe |
|---|---|
| **`finally`/`if: always()`** | Destruir recursos **mesmo se o teste falhar** |
| **IaC para tudo** | `sam delete`/`cdk destroy`/`terraform destroy` — **sem recursos manuais** |
| **Deletion/Retention policies** | Em stacks de teste: `DeletionPolicy: Delete`; **buckets** precisam ser **esvaziados** antes (`autoDeleteObjects` no CDK) |
| **Recursos “presos”** | ENIs, buckets não vazios, log groups **sem** retenção, **KMS** (agendamento de exclusão) |
| **Varredura de órfãos** | Job que lista recursos por tag e remove vencidos |
| **Ferramentas** | **aws-nuke** (**com extremo cuidado**, só em contas de **sandbox** com **allowlist**) |
| **Evidência** | Registrar **o que foi criado/destruído** |

> [!warning] Ferramentas de “limpar tudo”
> Utilitários como **aws-nuke** **apagam recursos da conta inteira**. Use **somente** em contas **descartáveis**, com **lista de contas permitidas** e **confirmação**. Um engano de **conta/perfil** pode destruir **produção**.

## 9. Segurança dos mocks e emuladores

| Ponto | Cuidado |
|---|---|
| **Imagens Docker de emuladores** | Usar **fontes confiáveis**; fixar **versões/digest** |
| **Portas expostas** | Emuladores **não** devem ficar acessíveis na rede (bind em `127.0.0.1`) |
| **Credenciais “test”** | **Não** reutilizar valores reais; **nunca** apontar **para o endpoint real** por engano |
| **Mock em produção** | Rotas/headers de mock **desabilitados** em prod; **verificação** no pipeline |
| **Gravações (record/playback)** | **Mascarar** tokens/PII antes de versionar |
| **Dependências de teste** | Atualizar e **escanear** (Dependabot/Snyk) |
| **Fixtures com segredos** | Detectar por scanners |

## 10. Conformidade e evidências

| Requisito | Prática |
|---|---|
| **LGPD/GDPR** | **Sem PII real** em teste; base legal/minimização quando inevitável |
| **PCI-DSS** | **Nunca** PAN real em teste; usar **cartões de teste** do provedor |
| **SOC2/ISO** | Evidenciar **segregação de ambientes**, **controle de acesso** e **mudanças via pipeline** |
| **Rastreabilidade** | **CloudTrail**, **logs do CI**, **relatórios de teste** retidos |
| **Revisão de acesso** | Revisões periódicas das **roles de CI** |
| **Segregação de funções** | Quem escreve código **não** aprova sozinho o deploy em prod |
| **Política de dados de teste** | Documentada e **auditável** |

## 11. Checklist

1. **Contas separadas** (dev/test/staging/prod) com **SCPs**.
2. **CI com OIDC** (sem chaves de longo prazo) e **trust policy** restrita (repo/branch/ambiente).
3. **Role de CI com menor privilégio** e **permission boundary**.
4. **Credenciais falsas** nos testes unitários; **sem rede** acidental.
5. **Dados sintéticos**; **sem PII real**; **sandbox** de e-mail/SMS/pagamentos.
6. **Segredos** no cofre; **scanners** no repositório.
7. **Stacks efêmeros** com **TTL**, **tags** e **limpeza** garantida.
8. **Budgets/anomaly detection** na conta de teste.
9. **Emuladores** presos ao localhost; **imagens** confiáveis.
10. **Mocks desativados em produção**.
11. **Auditoria** (CloudTrail/logs do CI) e **revisões periódicas**.

## 12. Erros comuns

- **Testes de integração apontando para produção** (conta/perfil errados).
- **Chaves de acesso fixas** no CI.
- **Role de CI com administrador**.
- **Cópia de base de produção** para teste sem anonimizar.
- **Sem teardown** (custos e superfície de ataque).
- **Trust policy OIDC com `sub` aberto** (qualquer repo/branch assume).
- **Fork de PR** com acesso à role.
- **E-mail/SMS reais** em testes.
- **Segredos em fixtures/gravações** de mocks.
- **Emulador exposto na rede**.
- **Sem tags/TTL** (órfãos sem dono).
- **Usar aws-nuke** sem allowlist.

## 13. Troubleshooting

| Sintoma | Causa provável | Ação |
|---|---|---|
| `Not authorized to perform sts:AssumeRoleWithWebIdentity` | `sub`/`aud` da trust policy não casam | Ver claims do token; ajustar condição |
| Pipeline cria recursos na conta errada | Perfil/role errada | Role por ambiente; **`aws sts get-caller-identity`** no início |
| Stack de teste não deleta | Bucket não vazio/dependências | Esvaziar bucket; remover dependências; retenção |
| Conta de teste com custo alto | Órfãos/carga | Budgets, varredura por tag, TTL |
| Teste unitário chama a AWS real | Mock mal aplicado/sem credenciais falsas | Credenciais falsas; `pytest-socket` |
| Vazamento de segredo | Fixture/log | **Rotacionar**, remover do histórico, scanners |
| E-mails reais enviados | Fora do sandbox | SES sandbox/simulador; revisar configuração |
| Falha por cota em teste paralelo | Limites da conta | Serializar/ajustar cotas/contas por equipe |

## 14. Resumo rápido

- **Contas separadas + SCPs**; **nenhum caminho** de teste para produção.
- **CI sem chaves**: **OIDC → roles temporárias**, trust policy **restrita**, **menor privilégio** e **permission boundary**.
- **Testes unitários com credenciais falsas**; **dados sintéticos**; **sandbox** para e-mail/SMS/pagamento.
- **Isolamento**: stacks por PR, IDs únicos, testes independentes.
- **Custos**: **Budgets/Anomaly Detection**, **tags/TTL**, **limpeza** garantida (`always()`/`finally`).
- **Mocks/emuladores seguros**: localhost, imagens confiáveis, **desativados em produção**, gravações **mascaradas**.
- **Conformidade**: **sem PII real**, **auditoria**, **segregação de funções**.

## 🧩 Quiz de Fixação

1. Por que separar contas por ambiente?
2. Como evitar chaves de longo prazo no CI?
3. O que restringir na trust policy OIDC?
4. Por que usar credenciais falsas nos testes unitários?
5. Como enviar e-mails de teste sem atingir clientes?
6. Por que o teardown deve rodar mesmo com falha?
7. Qual o risco do aws-nuke?

**Respostas:**

1. Para isolar riscos, custos e permissões, impedir que testes afetem produção e aplicar SCPs específicas.
2. Usando federação OIDC com roles temporárias (AssumeRoleWithWebIdentity) ou service roles de CodeBuild/CodePipeline.
3. As claims aud e sub (repositório, branch, ambiente), para que apenas código confiável assuma a role.
4. Para garantir que nenhuma credencial real seja usada por acidente e evitar chamadas reais e lentidão na credential chain.
5. Com SES sandbox e os endereços do simulador (success@simulator.amazonses.com etc.), além de domínios de teste.
6. Para não deixar recursos órfãos que geram custo e ampliam a superfície de ataque.
7. Apaga recursos da conta inteira; um engano de conta ou perfil pode destruir produção, então só em contas descartáveis com allowlist.
