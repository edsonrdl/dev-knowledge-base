### 4.1.1.1. Eventos, API e deploy gradual no SAM — fontes de evento, autorizadores, CORS, layers, AutoPublishAlias, DeploymentPreference, hooks do CodeDeploy e alarmes de rollback

> [!warning] Aviso
> Propriedades, nomes de estratégias de deploy, limites e comportamentos abaixo são **de memória e mudam**. **Confirme na especificação do AWS SAM, na documentação do Lambda, do API Gateway e do CodeDeploy.** Templates e código são ilustrativos e **não foram executados**. Esta nota cobre as skills de **integrar fontes de evento, expor APIs e implantar Lambda com segurança** do DVA-C03.

## 1. Visão geral

Depois de ter o template e o fluxo de CLI, as perguntas práticas são: **o que dispara a função**, **como a API é protegida e configurada** e **como lançar uma nova versão sem derrubar produção**. O SAM resolve essas três com `Events`, `Auth/Cors` e `AutoPublishAlias` + `DeploymentPreference`.

| Tema | Mecanismo SAM |
|---|---|
| Gatilhos | `Events` na função |
| Segurança da API | `Auth` (autorizadores, chaves, IAM) |
| Navegador | `Cors` / `CorsConfiguration` |
| Dependências compartilhadas | `Layers` |
| Release seguro | `AutoPublishAlias` + `DeploymentPreference` (CodeDeploy) |
| Permissões entre recursos | `Policies` ou `AWS::Serverless::Connector` |

## 2. Fontes de evento: síncronas, assíncronas e polling

Entender **como** o Lambda é invocado é essencial, pois muda o tratamento de erro:

| Modelo | Exemplos | Quem invoca | Em caso de erro |
|---|---|---|---|
| **Síncrono** | API Gateway, Function URL, ALB | O serviço chamador espera a resposta | O erro volta ao cliente |
| **Assíncrono** | S3, SNS, EventBridge, Schedule | O serviço enfileira o evento no Lambda | **Retentativas** (padrão 2) e depois DLQ/destino |
| **Polling (event source mapping)** | SQS, Kinesis, DynamoDB Streams, MSK | O próprio Lambda consulta a fonte | Depende da fonte: o lote volta à fila, ou o shard trava até resolver |

### 2.1 SQS

```yaml
Processador:
  Type: AWS::Serverless::Function
  Properties:
    Handler: app.handler
    CodeUri: src/processador/
    Timeout: 30
    Events:
      Fila:
        Type: SQS
        Properties:
          Queue: !GetAtt FilaPedidos.Arn
          BatchSize: 10
          MaximumBatchingWindowInSeconds: 5
          FunctionResponseTypes: [ReportBatchItemFailures]
          ScalingConfig:
            MaximumConcurrency: 10

FilaPedidos:
  Type: AWS::SQS::Queue
  Properties:
    VisibilityTimeout: 180
    RedrivePolicy:
      deadLetterTargetArn: !GetAtt FilaDLQ.Arn
      maxReceiveCount: 3
```

Pontos exigidos em prova e na prática:

- O **VisibilityTimeout** da fila deve ser **pelo menos 6 vezes o Timeout** da função (regra recomendada), para evitar reprocessamento durante a execução.
- A **DLQ** mora na **fila de origem** (`RedrivePolicy`), não na função, para eventos SQS.
- `ReportBatchItemFailures` permite devolver **só os itens que falharam** do lote, evitando reprocessar os bem-sucedidos.
- `MaximumConcurrency` limita quantas invocações simultâneas a fila gera (protege bancos e APIs downstream).
- O SAM adiciona automaticamente a permissão `sqs:ReceiveMessage`, `sqs:DeleteMessage` e `sqs:GetQueueAttributes` à role da função.

### 2.2 S3, SNS, EventBridge e agendamento

```yaml
Events:
  NovoArquivo:
    Type: S3
    Properties:
      Bucket: !Ref BucketEntrada      # precisa estar no mesmo template
      Events: s3:ObjectCreated:*
  Aviso:
    Type: SNS
    Properties:
      Topic: !Ref TopicoAvisos
      FilterPolicy:
        tipo: [pedido]
  PorRegra:
    Type: EventBridgeRule
    Properties:
      EventBusName: default
      Pattern:
        source: ["app.pedidos"]
        detail-type: ["PedidoCriado"]
  Noturno:
    Type: ScheduleV2
    Properties:
      ScheduleExpression: "rate(1 day)"
```

Armadilhas dos eventos assíncronos:

| Armadilha | Explicação |
|---|---|
| **Bucket fora do template** | O evento `S3` do SAM exige que o bucket esteja declarado no **mesmo** template; para bucket existente, configure a notificação por outro meio (EventBridge, custom resource) |
| **Eventos duplicados** | Entrega **at-least-once**: a função deve ser **idempotente** |
| **Laço infinito** | A função grava no mesmo bucket/prefixo que a dispara; use **prefixos distintos** |
| **Throttling** | Concorrência insuficiente leva a retentativas e, enfim, perda; configure **destinos** (`EventInvokeConfig`) |

### 2.3 Kinesis e DynamoDB Streams

```yaml
Events:
  Mudancas:
    Type: DynamoDB
    Properties:
      Stream: !GetAtt Tabela.StreamArn
      StartingPosition: TRIM_HORIZON
      BatchSize: 100
      BisectBatchOnFunctionError: true
      MaximumRetryAttempts: 3
      DestinationConfig:
        OnFailure:
          Type: SQS
          Destination: !GetAtt FilaDLQ.Arn
```

Nas fontes de **stream**, um lote com erro **bloqueia o shard** até ser processado ou expirar. Por isso: `BisectBatchOnFunctionError` (divide o lote para isolar o registro defeituoso), `MaximumRetryAttempts` e `DestinationConfig.OnFailure` são as ferramentas para não travar o fluxo. Lembre: a tabela precisa ser `AWS::DynamoDB::Table` com `StreamSpecification`, pois `SimpleTable` não expõe stream.

## 3. APIs: autorização, CORS e validação

### 3.1 Tipos de autorização

| Mecanismo | Em `Api` (REST) | Em `HttpApi` | Quando usar |
|---|---|---|---|
| **IAM** (`AWS_IAM`) | Sim | Sim | Chamadores internos com SigV4 |
| **Cognito User Pool** | Sim | JWT authorizer | Usuários finais autenticados |
| **Lambda authorizer** | `TOKEN` ou `REQUEST` | `REQUEST` | Lógica própria (OAuth custom, tokens legados) |
| **Chave de API + usage plan** | Sim | Não | Medição e limites por cliente (não é autenticação forte) |
| **JWT (OIDC/OAuth2)** | Via Lambda/Cognito | **Nativo** | Provedores como Cognito, Auth0 |

Exemplo REST com autorizador Lambda do tipo `TOKEN` e cache:

```yaml
Api:
  Type: AWS::Serverless::Api
  Properties:
    StageName: !Ref Stage
    Auth:
      DefaultAuthorizer: MeuAuth
      Authorizers:
        MeuAuth:
          FunctionArn: !GetAtt FuncaoAuth.Arn
          Identity:
            Header: Authorization
            ReauthorizeEvery: 300
      ApiKeyRequired: false
      UsagePlan:
        CreateUsagePlan: PER_API
        Throttle:
          BurstLimit: 100
          RateLimit: 50
```

Exemplo HTTP API com JWT:

```yaml
HttpApi:
  Type: AWS::Serverless::HttpApi
  Properties:
    Auth:
      DefaultAuthorizer: JwtAuth
      Authorizers:
        JwtAuth:
          JwtConfiguration:
            issuer: !Sub "https://cognito-idp.${AWS::Region}.amazonaws.com/${UserPool}"
            audience: [!Ref UserPoolClient]
          IdentitySource: "$request.header.Authorization"
```

Um evento específico pode **sobrescrever** o autorizador padrão (`Auth: Authorizer: NONE` torna aquela rota pública; útil para `/health`).

### 3.2 CORS

CORS é imposto pelo **navegador**; você precisa que a **resposta** traga os cabeçalhos corretos, inclusive no **preflight** (`OPTIONS`).

| Onde configurar | Resultado |
|---|---|
| `Cors` na `Api` / `Globals.Api` | O SAM cria o método `OPTIONS` mock e adiciona cabeçalhos nas respostas de **gateway** |
| `CorsConfiguration` na `HttpApi` | O HTTP API responde ao preflight sozinho |
| **No código da função** | Em integração **proxy**, a função **também** deve devolver `Access-Control-Allow-Origin` na resposta real |

Erro clássico: configurar `Cors` no SAM, mas a função responde **sem** o cabeçalho em um erro 500, e o navegador mostra “CORS error” em vez do erro real. Depure olhando a resposta no Network, não a mensagem do navegador.

### 3.3 Validação, throttling e cache

Na API REST: `RequestValidator`/modelos (via `DefinitionBody` com OpenAPI), `MethodSettings` (throttling por método, cache, logs de acesso), `AccessLogSetting`, `CacheClusterEnabled`, `TracingEnabled`, `Domain` (domínio personalizado com certificado e base path). Na HTTP API: throttling por rota e `AccessLogSettings`.

## 4. Layers

```yaml
DepsLayer:
  Type: AWS::Serverless::LayerVersion
  Properties:
    ContentUri: layers/deps/
    CompatibleRuntimes: [python3.12]
    CompatibleArchitectures: [arm64]
  Metadata:
    BuildMethod: python3.12
    BuildArchitecture: arm64
```

| Fato sobre layers | Detalhe |
|---|---|
| Quantidade | **Até 5** layers por função |
| Tamanho | O total (função + layers) descompactado deve respeitar o limite de **250 MB** |
| Local no runtime | Extraídas em `/opt` (ex.: Python em `/opt/python`, Node em `/opt/nodejs/node_modules`) |
| Versionamento | Cada alteração cria **nova versão**; as funções precisam apontar para a nova |
| Compatibilidade | Respeitar **runtime** e **arquitetura** |
| `RetentionPolicy: Retain` | Mantém versões antigas (evita quebrar funções que ainda usam) |

Layers não substituem boas práticas de empacotamento: para dependências críticas e fixas, **imagens de container** ou empacotamento junto à função podem ser mais previsíveis.

## 5. Deploy gradual: AutoPublishAlias e DeploymentPreference

### 5.1 O que cada peça faz

Por padrão, atualizar uma função Lambda substitui `$LATEST` de imediato (**all at once**). Para lançar de forma controlada você usa **versões**, **aliases** e o **CodeDeploy**:

| Conceito | Função |
|---|---|
| **Versão** | Snapshot imutável do código e configuração |
| **Alias** | Ponteiro nomeado (ex.: `live`) para uma versão; permite **peso** entre duas versões |
| **`AutoPublishAlias`** | O SAM publica uma **nova versão** a cada mudança e **move o alias** |
| **`DeploymentPreference`** | Define **como** o alias migra da versão antiga para a nova, via **CodeDeploy** |

```yaml
Pedidos:
  Type: AWS::Serverless::Function
  Properties:
    Handler: app.handler
    CodeUri: src/pedidos/
    AutoPublishAlias: live
    DeploymentPreference:
      Type: Canary10Percent5Minutes
      Alarms:
        - !Ref AlarmeErros
        - !Ref AlarmeLatencia
      Hooks:
        PreTraffic: !Ref TestePre
        PostTraffic: !Ref TestePos
    Events:
      Criar:
        Type: Api
        Properties:
          Path: /pedidos
          Method: POST
```

O SAM cria: o **alias** `live`, a **versão** nova, um **CodeDeploy Application** e **Deployment Group**, e a **role do CodeDeploy** (a menos que você informe outra). As **fontes de evento apontam para o alias**, não para `$LATEST`, então o tráfego passa a seguir o peso do alias.

### 5.2 Estratégias disponíveis

| Tipo | Comportamento |
|---|---|
| `Canary10Percent5Minutes` (e `…10Minutes`, `…15Minutes`, `…30Minutes`) | **10%** do tráfego vai à nova versão; se tudo bem após o intervalo, os **90% restantes** migram de uma vez |
| `Linear10PercentEvery1Minute` (e `…2Minutes`, `…3Minutes`, `…10Minutes`) | **+10%** a cada intervalo até 100% |
| `AllAtOnce` | 100% imediato (ainda com hooks e alarmes) |

Há também a opção `Type` personalizada via `CodeDeployDefault.LambdaCanary10Percent5Minutes` etc. (nomes de configurações do CodeDeploy).

### 5.3 Hooks de validação

| Hook | Quando roda | Uso típico |
|---|---|---|
| **PreTraffic** | **Antes** de qualquer tráfego ir à nova versão | Teste de fumaça: invocar a nova versão, validar resposta, conexões e esquema |
| **PostTraffic** | **Depois** de 100% do tráfego migrar | Verificações finais, limpeza, notificações |

Os hooks são **funções Lambda** que devem reportar o resultado ao CodeDeploy chamando `PutLifecycleEventHookExecutionStatus` com `Succeeded` ou `Failed` (e o `DeploymentId` + `LifecycleEventHookExecutionId` do evento). Se **não reportarem** dentro do tempo, o hook falha e o deploy reverte. O nome da função de hook costuma exigir o prefixo `CodeDeployHook_` na política padrão do CodeDeploy (mantenha a política da role do hook compatível).

```python
import boto3
cd = boto3.client("codedeploy")

def handler(event, context):
    status = "Succeeded"
    try:
        # invocar a nova versão e validar
        pass
    except Exception:
        status = "Failed"
    cd.put_lifecycle_event_hook_execution_status(
        deploymentId=event["DeploymentId"],
        lifecycleEventHookExecutionId=event["LifecycleEventHookExecutionId"],
        status=status,
    )
```

### 5.4 Alarmes e rollback automático

Os **alarmes do CloudWatch** listados em `Alarms` são monitorados **durante o deploy**. Se algum entrar em `ALARM`, o CodeDeploy **reverte** o tráfego para a versão anterior automaticamente. Boas escolhas de alarmes:

| Alarme | Métrica |
|---|---|
| Erros | `AWS/Lambda Errors` da **versão nova** (usar dimensão `Resource` com alias/versão, ou `ExecutedVersion`) |
| Latência | `Duration` p99 |
| Throttles | `Throttles` |
| Negócio | Taxa de pedidos concluídos, 5XX no API Gateway |

> [!tip] Rollback sem hooks ou alarmes
> Se você não definir alarmes nem hooks, o CodeDeploy só reverte quando a **própria implantação falha** (por exemplo, um hook falha). Alarmes bem calibrados são o que dá **proteção contra regressões em tempo de execução**.

### 5.5 Habilitar por ambiente

Para evitar lentidão em dev, use `Enabled` condicional:

```yaml
DeploymentPreference:
  Type: !If [EhProd, Canary10Percent10Minutes, AllAtOnce]
  Enabled: !If [EhProd, true, false]
```

`DeploymentPreference` também pode ir em `Globals.Function` para aplicar a todas as funções.

## 6. Permissões entre recursos: Connectors

Alternativa moderna a policy templates para ligar dois recursos:

```yaml
ConectorFuncaoTabela:
  Type: AWS::Serverless::Connector
  Properties:
    Source:
      Id: Pedidos
    Destination:
      Id: Tabela
    Permissions:
      - Read
      - Write
```

O Connector gera **a política IAM mínima** (e permissões de recurso, quando necessário) para a combinação origem/destino suportada (função→tabela, função→fila, SNS→fila, API→função etc.). Também pode usar `Fn::GetAtt` na sintaxe curta `Connectors:` dentro do recurso de origem.

## 7. Pegadinhas de prova (DVA-C03)

- **Para canário em Lambda usando SAM?** → `AutoPublishAlias` + `DeploymentPreference` (CodeDeploy). Sem alias, não há deploy gradual.
- **Quem faz o rollback automático?** → **CodeDeploy**, disparado por **alarmes do CloudWatch** ou falha de hook.
- **Hook que roda antes do tráfego?** → `PreTraffic`; depois → `PostTraffic`.
- **Como o hook sinaliza sucesso?** → Chamando `PutLifecycleEventHookExecutionStatus`.
- **Fonte de evento de SQS com falhas?** → DLQ na **fila**; `ReportBatchItemFailures` para falhas parciais.
- **Stream (Kinesis/DynamoDB) travado por registro ruim?** → `BisectBatchOnFunctionError`, retentativas máximas e destino on-failure.
- **Quantas layers por função?** → **5**.
- **Onde ficam as layers no runtime?** → **`/opt`**.
- **Qual API é mais barata e tem JWT nativo?** → **HTTP API**.
- **Evento S3 do SAM em bucket existente?** → Não suportado diretamente; o bucket deve estar **no mesmo template**.

## 8. Resumo rápido

- `Events` define gatilhos; o modelo (síncrono, assíncrono, polling) determina o tratamento de erro.
- SQS: **VisibilityTimeout ≥ 6× Timeout**, DLQ na fila, `ReportBatchItemFailures`.
- Streams: **bisect**, retentativas e destino on-failure para não travar o shard.
- API: IAM, Cognito, Lambda, JWT; CORS no gateway **e** na resposta da função.
- Layers: até 5, em `/opt`, versionadas, com cuidado de compatibilidade.
- **Deploy gradual** = `AutoPublishAlias` + `DeploymentPreference` + alarmes + hooks.
- **Connectors** geram permissões mínimas entre recursos.
