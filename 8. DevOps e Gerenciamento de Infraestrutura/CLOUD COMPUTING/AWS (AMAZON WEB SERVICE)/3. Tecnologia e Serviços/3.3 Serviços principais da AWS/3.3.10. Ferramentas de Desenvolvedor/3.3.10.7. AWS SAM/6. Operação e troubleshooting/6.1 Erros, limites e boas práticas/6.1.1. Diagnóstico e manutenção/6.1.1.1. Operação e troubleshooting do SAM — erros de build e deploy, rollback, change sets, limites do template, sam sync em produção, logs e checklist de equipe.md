### 6.1.1.1. Operação e troubleshooting do SAM — erros de build e deploy, rollback, change sets, limites do template, sam sync em produção, logs e checklist de equipe

> [!warning] Aviso
> Mensagens de erro, limites, estados de stack e comportamentos abaixo são **de memória e mudam**. **Confirme na documentação do CloudFormation, do AWS SAM e do Lambda.** Comandos e saídas são ilustrativos e **não foram executados**. Esta nota cobre as skills de **depurar e operar aplicações serverless implantadas via IaC** do DVA-C03.

## 1. Uma regra para depurar: em que fase falhou?

Falhas em um projeto SAM acontecem em **fases distintas**, e identificar a fase corta o diagnóstico pela metade:

| Fase | Sintoma típico | Onde olhar |
|---|---|---|
| **Template / validação** | Erro antes de qualquer coisa ser criada | `sam validate --lint`, mensagem do CLI |
| **Build** | “Build Failed” | Saída do `sam build`, runtime, dependências |
| **Empacotamento/upload** | Erro de S3/ECR | Bucket de artefatos, credenciais, permissões |
| **Change set** | “Failed to create ChangeSet” | Eventos do CloudFormation, template processado |
| **Execução da stack** | `CREATE_FAILED`/`UPDATE_FAILED` e rollback | **Eventos da stack** (aba Events) |
| **Execução da função** | 5XX, timeout, `AccessDenied` | CloudWatch Logs, X-Ray, `sam logs` |
| **Pós-deploy gradual** | Rollback automático do CodeDeploy | Console do CodeDeploy, alarmes, hooks |

> [!tip] Onde está a causa raiz no CloudFormation
> Na lista de eventos da stack, procure o **primeiro** `*_FAILED` em ordem cronológica. Os demais recursos costumam falhar com “Resource creation cancelled” por consequência. A causa raiz está na **razão (status reason)** do primeiro recurso que falhou.

## 2. Erros de build

| Mensagem / sintoma | Causa | Correção |
|---|---|---|
| `Build Failed ... Runtime python3.12 not supported / not found` | A versão do runtime não está instalada localmente | Instalar a versão ou usar `sam build --use-container` |
| Falha ao compilar dependência nativa (`gcc`, `wheel`) | Falta de toolchain; plataforma diferente do Lambda | `--use-container` (ou `--build-image`) |
| Artefato com dependências erradas para `arm64` | Compilou em x86_64 | Declarar `Architectures: [arm64]` e construir com a mesma arquitetura |
| `Template file not found` / `CodeUri` inexistente | Caminho relativo errado | Rodar na pasta do template; checar `CodeUri` |
| `Manifest file is not found` | Falta `requirements.txt`/`package.json` | Criar o arquivo (mesmo vazio) ou ajustar `--manifest` |
| `esbuild` não encontrado | Ferramenta não instalada | Instalar `esbuild` ou usar container |
| Build lento a cada vez | Sem cache | `sam build --cached --parallel` |
| Funções gigantes | `node_modules`/dependências de desenvolvimento no pacote | Separar dependências de dev, minificar, usar layers/containers |

## 3. Erros de deploy e de stack

| Mensagem / sintoma | Causa | Correção |
|---|---|---|
| `Unable to upload artifact ... S3 bucket` | Sem bucket de artefatos ou sem permissão | `--resolve-s3` ou `--s3-bucket`; checar `s3:PutObject` |
| `Requires capabilities : [CAPABILITY_IAM]` | O template cria roles IAM | Adicionar a capability |
| `... [CAPABILITY_NAMED_IAM]` | Role com `RoleName` explícito | Usar a capability, ou remover o nome fixo |
| `... [CAPABILITY_AUTO_EXPAND]` | Aplicação aninhada/macro | Adicionar a capability |
| `Unrecognized resource types: [AWS::Serverless::Function]` | Faltou `Transform` | Incluir `Transform: AWS::Serverless-2016-10-31` |
| `Template format error: Unresolved resource dependencies` | `!Ref` para recurso inexistente | Corrigir o nome lógico |
| `Circular dependency between resources` | A função referencia o bucket que referencia a função (ex.: evento S3 + política) | Quebrar o ciclo com nome construído por `!Sub` e `DependsOn` |
| `X already exists` (recurso nomeado) | Nome físico fixo já em uso | Remover o nome fixo ou usar `!Sub ${AWS::StackName}-...` |
| `No changes to deploy. Stack is up to date` com exit 1 | Sem diferenças | `--no-fail-on-empty-changeset` |
| `Stack is in ROLLBACK_COMPLETE state and can not be updated` | A **criação** falhou | **Apagar a stack** e criar de novo |
| `UPDATE_ROLLBACK_FAILED` | O rollback também falhou | Corrigir a causa e **continuar o rollback** (opção “Continue update rollback”, pulando recursos se necessário) |
| `Resource handler returned message: "... is not authorized"` | Permissão ausente do **deployer/role de serviço** | Conceder a ação indicada |
| `The security token included in the request is invalid/expired` | Credenciais expiradas | Renovar SSO/credenciais |
| Falha ao apagar a stack | Bucket não vazio, recurso com dependência | Esvaziar o bucket; remover dependências |
| `Export ... cannot be deleted as it is in use by ...` | Outra stack importa o valor | Remover a importação antes |

### 3.1 Estados de stack que você precisa reconhecer

| Estado | Significado | Ação |
|---|---|---|
| `CREATE_IN_PROGRESS` / `UPDATE_IN_PROGRESS` | Em andamento | Aguardar |
| `CREATE_COMPLETE` / `UPDATE_COMPLETE` | Sucesso | — |
| `ROLLBACK_COMPLETE` | Criação falhou e foi desfeita | **Excluir** e recriar |
| `UPDATE_ROLLBACK_COMPLETE` | Atualização falhou e voltou ao estado anterior | Corrigir e tentar de novo |
| `UPDATE_ROLLBACK_FAILED` | Não conseguiu voltar | Corrigir e **continuar o rollback** |
| `DELETE_FAILED` | Exclusão incompleta | Resolver o recurso preso, tentar de novo (ou reter o recurso) |
| `REVIEW_IN_PROGRESS` | Existe change set criado, ainda não executado (stack nova) | Executar ou excluir |

Para investigar sem perder evidências, use `--disable-rollback` (**apenas em desenvolvimento**) ou `--on-failure DO_NOTHING` na **criação**. Isso deixa os recursos criados no ar para inspeção, mas a stack em estado de falha precisará ser tratada depois.

## 4. Change sets: ler antes de aplicar

O deploy do SAM cria um **change set**. Ler esse resultado evita desastres:

| Coluna | O que olhar |
|---|---|
| **Action** | `Add`, `Modify`, `Remove` |
| **Replacement** | `True` significa que o recurso **será substituído** (novo recurso criado, antigo apagado) |
| **Logical/Physical ID** | Quais recursos |
| **Details** | Propriedades que mudaram e se são “condicionais” |

Propriedades que costumam causar **substituição** (varia por recurso): nome físico, chaves de tabelas DynamoDB, nomes de filas, certos parâmetros imutáveis. Para tabelas e buckets com dados, **substituição = perda de dados** a não ser que haja `UpdateReplacePolicy: Retain/Snapshot`.

Em pipelines, o deploy sem confirmação (`--no-confirm-changeset`) deve ser precedido de **revisão automatizada** (cfn-guard, aprovação manual em produção).

## 5. Limites que quebram templates SAM

| Limite | Valor (verifique) | Observação |
|---|---|---|
| Tamanho do **template** enviado direto | **51.200 bytes** | Acima disso, use S3 (o SAM CLI já envia ao S3) |
| Tamanho do template via S3 | **1 MB** | |
| **Recursos por stack** | **500** | O SAM gera vários recursos por função/API |
| Parâmetros por template | 200 | |
| Outputs por template | 200 | |
| Funções Lambda: pacote zip (upload direto) | 50 MB zipado | Acima, via S3 |
| Descompactado (função + layers) | **250 MB** | Imagem de container: até **10 GB** |
| Layers por função | 5 | |
| Timeout máximo | **900 s** (15 min) | |
| Memória | 128 MB a **10.240 MB** | CPU proporcional |
| Variáveis de ambiente (total) | **4 KB** | |
| Concorrência da conta (padrão) | 1.000 por região (ajustável) | Pode haver throttling |
| Stacks aninhadas | Profundidade limitada | Dividir por domínio |

**Soluções para chegar ao limite de 500 recursos:** dividir em **stacks aninhadas** (`AWS::Serverless::Application` ou `AWS::CloudFormation::Stack`), separar por **domínio** (stack de dados, stack de API, stack de workers) e trocar recursos implícitos por explícitos compartilhados (uma API compartilhada em vez de uma por função).

## 6. Diagnóstico em tempo de execução

### 6.1 Logs, métricas e traces

```bash
sam logs --stack-name app-prod --name Pedidos --tail
sam logs --stack-name app-prod --filter "Task timed out"
sam traces --stack-name app-prod
```

| Sintoma na função | Causa provável | Verificação |
|---|---|---|
| `Task timed out after N seconds` | Timeout curto, chamada bloqueada, cold start em VPC | Aumentar timeout; checar latência de dependências; X-Ray |
| `Runtime.ImportModuleError` / `Cannot find module` | Dependência faltando ou `Handler` errado | Conferir `Handler`, `CodeUri`, conteúdo do pacote |
| `AccessDeniedException` / `AccessDenied` | Falta permissão na role | Ler a mensagem (ação e recurso) e ajustar `Policies` |
| `Runtime exited with error: signal: killed` / OOM | Memória insuficiente | Aumentar `MemorySize` |
| 502 do API Gateway | Resposta fora do formato proxy (`statusCode`, `body` string) | Corrigir formato de retorno |
| 504/timeout da API | Integração > 29 s (padrão REST) | Tornar assíncrono; reduzir trabalho |
| 403 `Missing Authentication Token` | Rota/método inexistente ou stage ausente na URL | Checar caminho e o stage |
| 429 / `Rate exceeded` | Throttling da conta/função | Concorrência reservada, backoff |
| Mensagens SQS reprocessadas | Visibility timeout menor que o processamento | **VisibilityTimeout ≥ 6× Timeout** |
| Eventos duplicados | Entrega at-least-once | Idempotência |
| Alias/versão inesperada em execução | Evento aponta para `$LATEST` ou alias errado | Checar `AutoPublishAlias` e a origem do evento |

### 6.2 Diferenças entre local e nuvem

| Item | `sam local` | Nuvem |
|---|---|---|
| IAM | **Não valida** a role da função (usa suas credenciais locais) | Aplica a role real |
| Rede/VPC | Rede local | VPC, subnets, security groups |
| Limites e cotas | Em geral não aplicados | Aplicados |
| Fontes de evento | Você gera o evento | Eventos reais, formatos e latências |
| Recursos dependentes | Emulados ou reais conforme configurar | Reais |

Por isso: **funciona local, falha na AWS com `AccessDenied`** é o caso mais comum. Valide em uma stack real de teste.

## 7. sam sync e produção

| Questão | Resposta |
|---|---|
| Posso usar `sam sync` em produção? | **Não é recomendado.** Ele atualiza serviços diretamente, **sem change set** e com **drift** em relação ao CloudFormation |
| Como voltar a um estado consistente? | Executar um **`sam deploy`** normal, que reconcilia a stack com o template |
| O que usar em produção? | **Pipeline** com `sam build` + `sam deploy` + deploy gradual |
| E em desenvolvimento? | `sam sync --watch` em **stack pessoal** é ótimo |

## 8. Rollback, versões e recuperação

| Cenário | Estratégia |
|---|---|
| Deploy ruim detectado **durante** o canário | Rollback **automático** pelo CodeDeploy (alarme ou hook) |
| Problema descoberto **depois** do deploy | Reverter o código no Git e **reimplantar** (preferível), ou mover o **alias** para a versão anterior |
| Substituição indesejada de recurso | Restaurar de **backup/snapshot** (`UpdateReplacePolicy`) |
| Stack em `UPDATE_ROLLBACK_FAILED` | Corrigir a causa e **continuar o rollback** |
| Perda de acesso por mudança de IAM | Reverter a política; auditar com CloudTrail |

Mover o alias manualmente é uma **mitigação rápida** (`aws lambda update-alias --function-name X --name live --function-version N`), mas gera divergência com o CloudFormation: registre a ação e corrija no template em seguida.

## 9. Otimização operacional

| Prática | Ganho |
|---|---|
| `Architectures: [arm64]` | Custo/desempenho frequentemente melhores |
| Ajustar `MemorySize` com **Lambda Power Tuning** | Menor custo por execução |
| **Provisioned Concurrency** (com alias) | Reduz cold start em endpoints críticos |
| **SnapStart** (runtimes suportados) | Inicialização rápida |
| Retenção de logs (`RetentionInDays`) | Menor custo e conformidade |
| Alarmes por função (Errors, Throttles, Duration, IteratorAge) | Detecção precoce |
| Tags de custo (`Tags` em `Globals`) | Alocação de custos |
| Painéis do CloudWatch/Application Insights | Visão única |
| Remover stacks de teste (`sam delete`) | Evita custos residuais |

## 10. Boas práticas de equipe

1. **Um template por domínio**, com stacks pequenas; evitar o monólito de 500 recursos.
2. **Nada de nomes fixos** em recursos de aplicação.
3. **Parâmetros e SSM** para variação por ambiente; **uma stack por ambiente**, uma conta por ambiente quando possível.
4. **Pipeline única** para todos os ambientes; **build uma vez, promover o artefato**.
5. **Deploy gradual com alarmes** em produção; hooks PreTraffic para smoke tests.
6. **Testes**: unitários, integração local e em stack efêmera, e **smoke test** pós-deploy.
7. **cfn-lint e cfn-guard** como portões do CI.
8. **Revisão do change set** em produção (aprovação manual).
9. **Drift** monitorado; sem alterações manuais.
10. **Runbook** de incidentes com os erros desta nota e os comandos `sam logs`/`sam traces`.
11. **Fixar a versão da SAM CLI** na pipeline (evitar mudanças inesperadas de comportamento).
12. **Documentar** convenções (nomes, tags, estrutura de pastas, `samconfig.toml`).

## 11. Pegadinhas de prova (DVA-C03)

- **Stack em `ROLLBACK_COMPLETE`?** → Só pode ser **excluída**; depois, recriada.
- **Função funciona local e dá AccessDenied na nuvem?** → A role gerada não tem a permissão; o `sam local` não valida IAM.
- **Dependência nativa quebra no Lambda?** → Compilar com `sam build --use-container`.
- **Limite de recursos por stack?** → **500**; dividir em stacks aninhadas.
- **Mensagens SQS processadas duas vezes?** → Visibility timeout inferior ao tempo de processamento.
- **Onde ver a causa raiz de uma falha de deploy?** → Eventos da stack, **primeiro** `*_FAILED`.
- **Como reverter rápido um deploy gradual ruim?** → Alarmes/hook disparam rollback do CodeDeploy; ou mover o alias para a versão anterior.
- **API retorna 502 com Lambda proxy?** → Formato de resposta inválido.
- **`sam sync` em produção?** → Evitar; contorna o change set e gera drift.

## 12. Resumo rápido

- Diagnostique por **fase**: template, build, upload, change set, stack, função, deploy gradual.
- Causa raiz de falha de stack: **primeiro `*_FAILED`** nos eventos.
- `ROLLBACK_COMPLETE` exige **excluir** a stack; `UPDATE_ROLLBACK_FAILED` exige **continuar o rollback**.
- **Capabilities**, bucket de artefatos, nomes fixos e dependências circulares são os erros de deploy mais comuns.
- Limites: **51.200 bytes**, **500 recursos**, **250 MB**, **900 s**, **5 layers**.
- **Local ≠ nuvem** (IAM, VPC, cotas): valide em stack real.
- `sam sync` é para dev; produção usa pipeline e deploy gradual.
- Boas práticas: stacks pequenas, artefato único, alarmes, lint/guard, drift, runbook.
