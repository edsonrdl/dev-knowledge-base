### 1.1.1.1. AWS SAM — o que é, Transform serverless sobre CloudFormation, SAM CLI, recursos principais e quando usar SAM versus CDK e CloudFormation puro

> [!warning] Aviso
> Nomes de propriedades, versões de runtime, flags da SAM CLI e comportamentos abaixo são **de memória e mudam com frequência**. **Confirme na documentação do AWS SAM e do CloudFormation.** Templates, comandos e saídas são ilustrativos e **não foram executados**. Esta nota cobre as skills de **infraestrutura como código e deploy do DVA-C03** (empacotar, implantar e testar aplicações serverless).

## 1. O problema que o SAM resolve

Uma aplicação serverless típica tem uma função Lambda, uma API no API Gateway, uma tabela DynamoDB, uma fila SQS, permissões IAM, logs e alarmes. Escrever isso em **CloudFormation puro** funciona, mas é verboso: só para expor uma função Lambda atrás de uma rota HTTP você precisa declarar a função, a role de execução, a REST API, o recurso, o método, a integração, a permissão `AWS::Lambda::Permission`, o deployment e o stage. São **dezenas de linhas** para algo que, conceitualmente, é “quando chegar `GET /items`, execute esta função”.

O **AWS Serverless Application Model (SAM)** é uma **extensão do CloudFormation** que oferece uma **sintaxe abreviada** para recursos serverless. Em vez de declarar cada peça, você declara um `AWS::Serverless::Function` com um evento `Api`, e o SAM **expande** isso em todos os recursos CloudFormation necessários durante o deploy.

Duas partes formam o SAM:

| Parte | O que é | Onde atua |
|---|---|---|
| **SAM template specification** | Superconjunto do CloudFormation com tipos `AWS::Serverless::*` | No arquivo `template.yaml` |
| **SAM CLI** | Ferramenta de linha de comando para criar, compilar, testar localmente, implantar e depurar | Na sua máquina e no CI |

> [!info] Em uma frase
> **SAM = template curto que o CloudFormation expande (via Transform) + CLI que compila, testa localmente e implanta.** Por baixo, tudo vira uma **stack do CloudFormation**.

## 2. O Transform: como o template curto vira CloudFormation

A linha que identifica um template SAM é:

```yaml
AWSTemplateFormatVersion: '2010-09-09'
Transform: AWS::Serverless-2016-10-31
```

`Transform` instrui o CloudFormation a chamar uma **macro hospedada pela AWS** que reescreve o template. O processo é:

1. Você envia o template com tipos `AWS::Serverless::*`.
2. O CloudFormation executa o Transform e gera um **template processado** com apenas tipos nativos (`AWS::Lambda::Function`, `AWS::IAM::Role`, `AWS::ApiGateway::RestApi` etc.).
3. O CloudFormation cria um **change set** e implanta esse template processado.

Você pode ver o template processado no console do CloudFormation (aba **Template**, opção **View processed template**) ou com a API `GetTemplate` pedindo o estágio `Processed`. Esse é o melhor jeito de **entender o que o SAM criou** e de depurar erros.

### 2.1 O que o SAM gera sozinho

Para uma função simples com evento `Api`, o SAM cria, entre outros:

| Recurso gerado | Nome lógico típico |
|---|---|
| Função Lambda | `MinhaFuncao` |
| Role de execução com `AWSLambdaBasicExecutionRole` | `MinhaFuncaoRole` |
| REST API implícita | `ServerlessRestApi` |
| Deployment e Stage | `ServerlessRestApiDeployment<hash>`, `ServerlessRestApiProdStage` |
| Permissão para o API Gateway invocar a função | `MinhaFuncaoApiPermissionProd` |
| (com `AutoPublishAlias`) versão e alias | `MinhaFuncaoVersion<hash>`, `MinhaFuncaoAliasLive` |

Isso explica por que um template de 20 linhas pode gerar uma stack com 8 ou 10 recursos — e por que o **limite de 500 recursos por stack** do CloudFormation pode ser atingido mais cedo do que parece (veja a nota de operação).

## 3. Os recursos serverless do SAM

O SAM define um conjunto pequeno e focado de tipos:

| Tipo | Para que serve | Gera (resumo) |
|---|---|---|
| `AWS::Serverless::Function` | Função Lambda + eventos + permissões | Function, Role, Permissions, Event Source Mappings, Version/Alias |
| `AWS::Serverless::Api` | API REST (API Gateway v1) | RestApi, Deployment, Stage, Authorizers, UsagePlan |
| `AWS::Serverless::HttpApi` | API HTTP (API Gateway v2), mais barata e simples | Api v2, Stage, Authorizers JWT/Lambda |
| `AWS::Serverless::SimpleTable` | Tabela DynamoDB com chave primária simples | `AWS::DynamoDB::Table` |
| `AWS::Serverless::LayerVersion` | Camada Lambda (dependências compartilhadas) | `AWS::Lambda::LayerVersion` |
| `AWS::Serverless::StateMachine` | Step Functions com eventos e políticas | StateMachine, Role, EventBridge/API events |
| `AWS::Serverless::Application` | Aplicação aninhada (Serverless Application Repository ou S3) | Stack aninhada |
| `AWS::Serverless::Connector` | Permissões entre dois recursos sem escrever IAM à mão | Policies IAM mínimas |
| `AWS::Serverless::GraphQLApi` | API AppSync (recurso mais novo) | AppSync + resolvers |

Você pode **misturar** esses tipos com **qualquer recurso CloudFormation comum** no mesmo template: uma fila SQS (`AWS::SQS::Queue`), um bucket S3, uma Secret, um alarme. O SAM **não substitui** o CloudFormation; ele o complementa.

### 3.1 Exemplo mínimo comentado

```yaml
AWSTemplateFormatVersion: '2010-09-09'
Transform: AWS::Serverless-2016-10-31
Description: API de itens

Globals:
  Function:
    Runtime: python3.12
    Timeout: 10
    MemorySize: 256
    Tracing: Active

Resources:
  TabelaItens:
    Type: AWS::Serverless::SimpleTable
    Properties:
      PrimaryKey:
        Name: id
        Type: String

  ListarItens:
    Type: AWS::Serverless::Function
    Properties:
      Handler: app.handler
      CodeUri: src/listar/
      Environment:
        Variables:
          TABELA: !Ref TabelaItens
      Policies:
        - DynamoDBReadPolicy:
            TableName: !Ref TabelaItens
      Events:
        Listar:
          Type: HttpApi
          Properties:
            Path: /items
            Method: GET

Outputs:
  ApiUrl:
    Value: !Sub "https://${ServerlessHttpApi}.execute-api.${AWS::Region}.amazonaws.com/"
```

Observe o que **você não escreveu**: a role IAM, a permissão de invocação, a API HTTP, o stage e a integração. Observe também que `Policies` usa um **policy template** do SAM (`DynamoDBReadPolicy`), que concede apenas leitura àquela tabela.

## 4. A SAM CLI em visão geral

A SAM CLI cobre o ciclo completo. Os comandos principais (detalhados na nota de CLI) são:

| Comando | Função |
|---|---|
| `sam init` | Cria um projeto a partir de template (runtime, tipo de app) |
| `sam validate` | Valida o template (opção `--lint` usa cfn-lint) |
| `sam build` | Instala dependências e prepara artefatos em `.aws-sam/build` |
| `sam local invoke` / `start-api` / `start-lambda` | Executa funções e APIs **localmente** em containers Docker |
| `sam local generate-event` | Gera eventos de exemplo (S3, SQS, API Gateway…) |
| `sam deploy` | Empacota, envia artefatos ao S3 e cria/atualiza a stack |
| `sam sync` | Sincroniza mudanças rápido em um ambiente de desenvolvimento |
| `sam logs` / `sam traces` | Lê CloudWatch Logs e X-Ray |
| `sam delete` | Remove a stack e artefatos |
| `sam pipeline` | Gera pipelines de CI/CD |

O fluxo clássico é **build → deploy**. Antes de `deploy` existia o par `sam package` + `sam deploy`; hoje `sam deploy` faz o empacotamento sozinho, mas o conceito aparece em questões de prova: `sam package` equivale a `aws cloudformation package`, e `sam deploy` equivale a `aws cloudformation deploy`.

## 5. SAM, CloudFormation, CDK e Terraform: quando usar cada um

| Critério | **SAM** | **CloudFormation puro** | **AWS CDK** | **Terraform** |
|---|---|---|---|---|
| Linguagem | YAML/JSON | YAML/JSON | TypeScript, Python, Java, C#, Go | HCL |
| Foco | **Serverless** | Todos os serviços AWS | Todos os serviços, com abstrações | Multicloud |
| Abstração | Média (recursos serverless) | Baixa | Alta (constructs L2/L3) | Média |
| Teste local de Lambda/API | **Sim (`sam local`)** | Não | Via SAM CLI (`sam local` lê o template sintetizado) | Não nativo |
| Estado | Gerenciado pela AWS (stack) | Gerenciado pela AWS | Gerenciado pela AWS (gera CloudFormation) | Arquivo de estado próprio |
| Curva | Baixa para quem conhece CFN | Média | Média, exige programação | Média |

**Regra prática:**

- **Aplicação serverless focada em Lambda, API, filas e tabelas**, equipe confortável com YAML, desejo de testar localmente → **SAM**.
- **Infraestrutura ampla e heterogênea** (VPC, EKS, RDS, redes complexas), com lógica de composição (loops, condicionais complexas), equipe de desenvolvedores → **CDK**.
- **Controle total e templates declarativos puros**, sem abstrações → **CloudFormation**.
- **Multicloud ou padronização com times que já usam** → **Terraform**.

> [!tip] CDK e SAM convivem
> O CDK sintetiza um template CloudFormation que pode usar recursos `AWS::Serverless::*`, e a SAM CLI consegue **invocar localmente** funções definidas em projetos CDK apontando para o template sintetizado (`cdk.out`). Muitas equipes escrevem a infra no CDK e usam a SAM CLI só para teste e depuração local.

## 6. Como o SAM se encaixa no ciclo de entrega

```
 código + template.yaml
        │  sam build
        ▼
 .aws-sam/build (artefatos prontos)
        │  sam deploy
        ▼
 S3 (artefatos) ──► CloudFormation (Transform + change set) ──► recursos
        │
        └── (opcional) CodeDeploy: deploy gradual de Lambda com alias
```

Pontos relevantes:

- Os **artefatos** (zip das funções, imagens de container, templates aninhados) vão para um **bucket S3** (ou ECR para imagens). A SAM CLI cria e gerencia um bucket com `--resolve-s3`.
- O **deploy** é uma operação de **stack do CloudFormation**: cria um **change set**, mostra o que muda (se `confirm_changeset` estiver ativo) e executa.
- O **deploy gradual** (canário/linear) de funções Lambda usa **CodeDeploy** por baixo, configurado com `AutoPublishAlias` e `DeploymentPreference` (detalhado em outra nota).

## 7. Vantagens e limitações

| Vantagens | Limitações |
|---|---|
| Templates **muito mais curtos** para serverless | Focado em serverless; o resto cai no CloudFormation comum |
| **Policy templates** reduzem erros de IAM | Abstrações às vezes **escondem** detalhes (precisa ver o template processado) |
| **Teste local** com Docker | Emulação local **não é idêntica** à nuvem (IAM, limites, rede) |
| Integra com **CodeDeploy** (canário/linear/rollback) | Limites do CloudFormation continuam valendo (500 recursos, tamanho do template) |
| Toda a **API do CloudFormation** continua disponível (outputs, parâmetros, condições) | Erros de deploy vêm como erros de CloudFormation, às vezes crípticos |
| Pipelines prontos (`sam pipeline`) | Atualizações de propriedades podem **substituir** recursos (atenção a nomes fixos) |

## 8. Armadilhas comuns de iniciantes

| Armadilha | Consequência | Como evitar |
|---|---|---|
| Esquecer a linha `Transform` | O CloudFormation rejeita `AWS::Serverless::*` (“Unrecognized resource types”) | Sempre incluir `Transform: AWS::Serverless-2016-10-31` |
| Achar que `sam local` equivale à nuvem | Funciona local, falha com `AccessDenied` na AWS | Testar também em stack real de teste |
| Dar nome fixo a recursos (`TableName`, `FunctionName`) | Impede **substituição** sem conflito e dificulta múltiplas stacks | Deixar o CloudFormation gerar nomes, ou parametrizar com `!Sub ${AWS::StackName}-…` |
| Editar recursos manualmente no console | **Drift**: a stack diverge do template | Alterar sempre pelo template; detectar drift |
| Usar `sam sync` em produção | Contorna o change set do CloudFormation | Reservar `sync` para ambientes de desenvolvimento |
| Ignorar o template processado | Não entende por que um recurso existe | Consultar o **template processado** |

## 9. Pegadinhas de prova (DVA-C03)

- **“Qual declaração torna um template CloudFormation um template SAM?”** → `Transform: AWS::Serverless-2016-10-31`.
- **“Quais tipos de recurso o SAM adiciona?”** → `AWS::Serverless::Function`, `Api`, `HttpApi`, `SimpleTable`, `LayerVersion`, `StateMachine`, `Application` (e `Connector`).
- **“O que `sam deploy` usa por baixo?”** → **CloudFormation** (change set e stack).
- **“Qual comando equivale a `aws cloudformation package`?”** → `sam package` (ou o empacotamento embutido em `sam deploy`).
- **“Como testar a Lambda localmente antes do deploy?”** → `sam local invoke` / `sam local start-api` (requer **Docker**).
- **“Preciso de deploy gradual com rollback automático.”** → `AutoPublishAlias` + `DeploymentPreference` (CodeDeploy).
- **“Qual a diferença entre `AWS::Serverless::Api` e `HttpApi`?”** → `Api` é API REST (mais recursos: chaves de API, usage plans, validação de request, cache); `HttpApi` é HTTP API (mais barata, menor latência, autorizadores JWT).
- **“O template SAM pode conter recursos que não são serverless?”** → **Sim**, qualquer recurso CloudFormation.

## 10. Resumo rápido

- **SAM** = extensão do CloudFormation para serverless (Transform `AWS::Serverless-2016-10-31`) + **SAM CLI**.
- O template curto é **expandido** em recursos nativos; a implantação é uma **stack do CloudFormation**.
- Tipos principais: **Function, Api, HttpApi, SimpleTable, LayerVersion, StateMachine, Application, Connector**.
- **Policy templates** e **Connectors** simplificam permissões com privilégio mínimo.
- A CLI cobre **init, build, validate, local, deploy, sync, logs, delete, pipeline**.
- **Teste local** é útil, mas **não substitui** teste em stack real.
- Use SAM para **serverless**; CDK para infraestrutura ampla com código; CloudFormation para controle declarativo total.
- Consulte sempre o **template processado** para entender o que foi criado.
