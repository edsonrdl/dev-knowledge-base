### 3.1.1.1. SAM CLI no dia a dia — init, build, validate, deploy, samconfig.toml, sync e accelerate, logs, traces, delete e pipelines

> [!warning] Aviso
> Nomes de comandos, flags, valores padrão e mensagens de saída da SAM CLI abaixo são **de memória e mudam entre versões**. **Confirme com `sam <comando> --help` e na documentação oficial.** Comandos e saídas são ilustrativos e **não foram executados**. Esta nota cobre as skills de **empacotar, implantar e depurar aplicações serverless** do DVA-C03.

## 1. Pré-requisitos e instalação

A SAM CLI é um programa independente (não é parte da AWS CLI). Para usá-la você precisa de:

| Requisito | Para quê |
|---|---|
| **AWS CLI** configurada com credenciais | Autenticar no deploy (`aws configure`, perfis, SSO) |
| **SAM CLI** | Os comandos `sam ...` |
| **Docker** | `sam local ...` e `sam build --use-container` |
| Runtime da linguagem (Python, Node, Java, .NET…) | `sam build` sem container |

A SAM CLI usa a mesma cadeia de credenciais do AWS SDK (variáveis de ambiente, perfis, SSO, roles). Para escolher perfil e região: `--profile` e `--region`.

## 2. sam init: começar um projeto

```bash
sam init
sam init --runtime python3.12 --app-template hello-world --name meu-app
```

O assistente pergunta a origem (templates de início rápido da AWS ou um repositório personalizado), o runtime, o tipo de pacote (**Zip** ou **Image**), se habilita X-Ray e CloudWatch Insights, e gera uma estrutura como:

```
meu-app/
├── template.yaml
├── samconfig.toml        (após o primeiro deploy guiado)
├── events/event.json
├── hello_world/
│   ├── app.py
│   └── requirements.txt
└── tests/
```

## 3. sam validate: checar o template

```bash
sam validate
sam validate --lint
```

`sam validate` verifica se o template SAM é válido (consulta a API do CloudFormation e a especificação). Com `--lint`, também roda o **cfn-lint** e aponta problemas de propriedades, tipos e boas práticas. É um bom **primeiro passo do CI**, antes do build.

## 4. sam build: preparar os artefatos

```bash
sam build
sam build --use-container
sam build --cached --parallel
sam build --template-file outro-template.yaml
```

O `sam build` lê o `template.yaml`, instala dependências de cada função e grava o resultado em `.aws-sam/build/`, além de um template ajustado (`.aws-sam/build/template.yaml`) que aponta para os artefatos. Como cada linguagem é tratada:

| Runtime | Dependências lidas de | Observação |
|---|---|---|
| Python | `requirements.txt` | Instala com pip dentro de `.aws-sam/build/<Função>/` |
| Node.js | `package.json` | `npm install`; com `Metadata: BuildMethod: esbuild` compila TypeScript |
| Java | `pom.xml` ou `build.gradle` | Maven/Gradle |
| .NET | `.csproj` | `dotnet publish` |
| Go, Rust | `go.mod`, `Cargo.toml` | Rust usa `cargo-lambda` |
| Qualquer | **Makefile** | `Metadata: BuildMethod: makefile` com alvo `build-<NomeLógico>` |

Flags importantes:

| Flag | Efeito |
|---|---|
| `--use-container` | Compila dentro de um container Docker com o ambiente do Lambda. Evita problemas de **dependências nativas** (ex.: `numpy`, `cryptography`) compiladas na plataforma errada |
| `--cached` | Reutiliza artefatos se o código não mudou |
| `--parallel` | Compila funções em paralelo |
| `--build-image` | Imagem de build personalizada |
| `--manifest` | Caminho alternativo do arquivo de dependências |
| `--mount-with WRITE` | Permite escrita no diretório montado em build com container |

> [!tip] Por que `--use-container` importa
> Compilar em Windows ou macOS e rodar no Lambda Linux pode gerar binários incompatíveis. Com `--use-container`, a compilação ocorre em uma imagem que imita o ambiente de execução do Lambda, reproduzindo o que vai rodar na nuvem. Para funções **arm64**, garanta que a imagem de build use a mesma arquitetura declarada em `Architectures`.

## 5. sam local: executar e testar localmente

Resumo (a estratégia completa de testes está em outra nota):

```bash
sam local invoke ListarItens --event events/get.json
sam local start-api --warm-containers EAGER
sam local start-lambda
sam local generate-event s3 put > events/s3.json
```

| Comando | Uso |
|---|---|
| `invoke` | Executa **uma** função com um evento JSON |
| `start-api` | Sobe um endpoint HTTP local (`http://127.0.0.1:3000`) para funções com eventos `Api`/`HttpApi` |
| `start-lambda` | Emula o endpoint do serviço Lambda local (para SDK/CLI apontando a `--endpoint-url`) |
| `generate-event` | Gera payloads de exemplo de S3, SQS, SNS, API Gateway, DynamoDB etc. |

Em `start-api`, o código é recarregado a cada requisição por padrão (container novo). `--warm-containers EAGER|LAZY` mantém containers quentes para acelerar. Variáveis de ambiente locais podem vir de `--env-vars env.json`, e parâmetros do template, de `--parameter-overrides`.

## 6. sam deploy: implantar

### 6.1 Primeiro deploy guiado

```bash
sam deploy --guided
```

O assistente pergunta: nome da stack, região, se deseja confirmar o change set, se permite criação de roles IAM (`CAPABILITY_IAM`), se desabilita rollback, se salva os argumentos em `samconfig.toml`, e, para funções com recursos sem autenticação (ex.: API aberta), confirma explicitamente. Depois do primeiro deploy, basta:

```bash
sam deploy
```

### 6.2 O que acontece no deploy

1. A CLI localiza ou cria um **bucket S3 gerenciado** para artefatos (`--resolve-s3` ou `s3_bucket`).
2. Faz **upload** dos artefatos (zips, templates aninhados) e, para imagens, o **push ao ECR**.
3. Gera o template empacotado com referências S3.
4. Cria um **change set** do CloudFormation.
5. Mostra as mudanças (se `confirm_changeset = true`) e pede confirmação.
6. Executa o change set e acompanha os **eventos da stack** até concluir.

### 6.3 Flags frequentes de deploy

| Flag | Efeito |
|---|---|
| `--stack-name` | Nome da stack |
| `--resolve-s3` | Usa/cria bucket gerenciado de artefatos |
| `--s3-bucket` / `--s3-prefix` | Bucket e prefixo explícitos |
| `--capabilities CAPABILITY_IAM CAPABILITY_NAMED_IAM CAPABILITY_AUTO_EXPAND` | Autorizações para criar IAM (nomeada) e expandir transforms/aplicações aninhadas |
| `--parameter-overrides Stage=prod` | Valores de parâmetros |
| `--no-confirm-changeset` | Não pergunta antes de executar (CI) |
| `--no-fail-on-empty-changeset` | Não falha (exit code 0) quando não há mudanças |
| `--on-failure ROLLBACK \| DELETE \| DO_NOTHING` | Comportamento em falha de **criação** de stack |
| `--disable-rollback` | Mantém recursos criados para investigação |
| `--config-env prod` | Usa o ambiente `prod` do `samconfig.toml` |
| `--tags` | Tags da stack |
| `--role-arn` | Role de serviço que o CloudFormation assume |
| `--notification-arns` | Tópicos SNS para eventos da stack |
| `--image-repository` / `--resolve-image-repos` | Repositório ECR para imagens |
| `--use-json` | Saída em JSON |

> [!warning] Capacidades
> Se o template cria roles IAM sem a capability adequada, o deploy falha com “Requires capabilities: [CAPABILITY_IAM]”. Se as roles têm **nome explícito**, é preciso `CAPABILITY_NAMED_IAM`. Aplicações aninhadas (`AWS::Serverless::Application`) pedem `CAPABILITY_AUTO_EXPAND`.

## 7. samconfig.toml: configuração versionada

O arquivo guarda argumentos por **ambiente**, evitando longas linhas de comando:

```toml
version = 0.1

[default.global.parameters]
stack_name = "meu-app-dev"

[default.build.parameters]
cached = true
parallel = true

[default.deploy.parameters]
resolve_s3 = true
capabilities = "CAPABILITY_IAM"
confirm_changeset = true
parameter_overrides = "Stage=dev"
region = "sa-east-1"

[prod.deploy.parameters]
stack_name = "meu-app-prod"
confirm_changeset = false
parameter_overrides = "Stage=prod"
capabilities = "CAPABILITY_IAM"
resolve_s3 = true
```

Uso: `sam deploy --config-env prod`. Pontos de atenção:

- O arquivo também aceita formato **YAML** (`samconfig.yaml`) e variáveis de ambiente `SAMCONFIG_*` em algumas versões.
- **Não coloque segredos** em `parameter_overrides`; ele costuma ser versionado no Git.
- Separe **uma stack por ambiente** (nome distinto) e preferencialmente **uma conta por ambiente**.

## 8. sam sync e accelerate: iteração rápida

```bash
sam sync --stack-name meu-app-dev --watch
sam sync --stack-name meu-app-dev --code
```

O `sam sync` (parte do conjunto “SAM Accelerate”) detecta o que mudou:

| Tipo de mudança | O que o sync faz |
|---|---|
| **Só código** de funções/layers/estados | Atualiza **direto pelas APIs do serviço** (ex.: `UpdateFunctionCode`), em segundos, **sem CloudFormation** |
| **Infraestrutura** (template) | Executa um deploy normal via CloudFormation |
| **`--watch`** | Observa o diretório e sincroniza continuamente |

O `sync` é excelente para **desenvolvimento**, mas há contrapartidas:

| Ponto | Detalhe |
|---|---|
| Contorna o **change set** | Produz **drift** entre a stack e o estado real até o próximo deploy completo |
| Não substitui o deploy da pipeline | Use só em stacks de **desenvolvimento individual** |
| Pode atualizar recursos na hora | Cuidado com ambientes compartilhados |

## 9. sam logs, sam traces e sam remote invoke

```bash
sam logs --stack-name meu-app-dev --name ListarItens --tail
sam logs --stack-name meu-app-dev --filter "ERROR" --start-time "10min ago"
sam traces --stack-name meu-app-dev
sam remote invoke ListarItens --stack-name meu-app-dev --event-file events/get.json
sam remote test-event put ListarItens --stack-name meu-app-dev --name caso1
```

| Comando | Uso |
|---|---|
| `sam logs` | Lê **CloudWatch Logs** das funções (e do API Gateway) da stack, com `--tail`, `--filter`, `--start-time`, `--end-time` |
| `sam traces` | Lê **X-Ray traces** da stack |
| `sam remote invoke` | Invoca recursos **na nuvem** (Lambda, Step Functions, SQS, Kinesis) e mostra a resposta |
| `sam remote test-event` | Gerencia eventos de teste compartilháveis (Lambda test events) |
| `sam list endpoints` / `resources` / `stack-outputs` | Lista endpoints, recursos físicos e outputs da stack |

`sam logs --tail` evita você procurar manualmente o log group (`/aws/lambda/<nome-físico>`), pois resolve o nome físico a partir da stack.

## 10. sam delete, sam package e sam publish

| Comando | Função |
|---|---|
| `sam delete --stack-name X` | Apaga a stack **e** os artefatos do S3/ECR gerenciados |
| `sam package` | Gera o template empacotado (equivale a `aws cloudformation package`) |
| `sam publish` | Publica no **Serverless Application Repository** (SAR) |

Em `sam delete`, recursos com `DeletionPolicy: Retain` (por exemplo, um bucket de dados) **permanecem**. Buckets S3 **não vazios** impedem a exclusão da stack: é preciso esvaziar antes.

## 11. sam pipeline: CI/CD guiado

```bash
sam pipeline bootstrap      # cria roles, bucket e (opcional) ECR por estágio
sam pipeline init --bootstrap
```

O `sam pipeline`:

- Cria a **infraestrutura da pipeline** por estágio (dev, hml, prod): role de execução do CloudFormation, role da pipeline, bucket de artefatos e repositório ECR.
- Gera um **arquivo de pipeline** para o sistema escolhido: **AWS CodePipeline**, **GitHub Actions**, **GitLab CI/CD**, **Jenkins** ou **Bitbucket Pipelines**.
- Orienta uma abordagem de **uma conta por estágio** e uso de **OIDC** para provedores externos.

Um fluxo de CI simplificado, usando comandos diretos:

```bash
sam validate --lint
sam build --cached --parallel
sam deploy --no-confirm-changeset --no-fail-on-empty-changeset \
  --config-env prod --resolve-s3
```

Boas práticas em pipeline:

1. **Build uma vez**, implante o **mesmo artefato** em todos os estágios (promoção).
2. Executar **testes** antes do deploy e **smoke tests** depois.
3. Usar uma **role de serviço do CloudFormation** (`--role-arn`) com permissões limitadas.
4. Requerer **aprovação manual** antes de produção.
5. Ativar **deploy gradual** com alarmes para rollback automático.

## 13. Erros frequentes e diagnóstico rápido

| Sintoma | Causa provável | Solução |
|---|---|---|
| `Error: Running AWS SAM projects locally requires Docker` | Docker não instalado ou parado | Iniciar o Docker Desktop/daemon |
| `Build Failed: Runtime python3.12 not found` | Versão do runtime não instalada | Instalar a versão, ou `sam build --use-container` |
| `Unable to upload artifact ... S3 Bucket does not exist` | Sem bucket de artefatos | `--resolve-s3` ou `--s3-bucket` |
| `Requires capabilities : [CAPABILITY_IAM]` | Template cria roles IAM | `--capabilities CAPABILITY_IAM` |
| `No changes to deploy. Stack is up to date` com exit code 1 | Sem diferenças | `--no-fail-on-empty-changeset` |
| Stack em `ROLLBACK_COMPLETE` | Criação falhou e foi desfeita | **Apagar a stack** e implantar de novo |
| Função nativa quebra no Lambda | Dependências nativas compiladas no SO errado | `sam build --use-container` |
| `sam local` ignora alteração | Código em cache de container quente | Reiniciar ou usar modo sem warm containers |

## 14. Pegadinhas de prova (DVA-C03)

- **Comando que cria artefatos de build localmente?** → `sam build` (saída em `.aws-sam/build`).
- **Comando que faz upload do código para o S3 e cria a stack?** → `sam deploy` (por baixo, `package` + `deploy`).
- **Qual arquivo guarda a configuração do deploy?** → `samconfig.toml`.
- **Como evitar falha de deploy sem mudanças?** → `--no-fail-on-empty-changeset`.
- **O que exige Docker?** → `sam local ...` e `sam build --use-container`.
- **Como ver os logs de uma função da stack em tempo real?** → `sam logs --tail`.
- **Qual comando atualiza só o código rapidamente em desenvolvimento?** → `sam sync` (usa APIs diretas; gera drift).
- **Como o deploy trata IAM?** → Exige **capabilities** (`CAPABILITY_IAM`, `CAPABILITY_NAMED_IAM`, `CAPABILITY_AUTO_EXPAND`).

## 15. Resumo rápido

- Ciclo: **init → validate → build → local → deploy → logs/traces → delete**.
- `sam build` prepara `.aws-sam/build`; use `--use-container` para compatibilidade nativa.
- `sam deploy` empacota, envia ao S3/ECR e executa um **change set**; `--guided` gera o `samconfig.toml`.
- Ambientes com `--config-env`; sem segredos no arquivo.
- `sam sync` acelera o desenvolvimento, mas **gera drift** e não é para produção.
- `sam logs`, `sam traces`, `sam remote invoke` e `sam list` ajudam a operar.
- `sam pipeline` gera CI/CD por estágio com roles e OIDC.
- Erros comuns: Docker ausente, capabilities, bucket de artefatos, `ROLLBACK_COMPLETE`.
