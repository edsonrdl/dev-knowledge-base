### O que é Amazon SQS — filas gerenciadas, desacoplamento, produtores e consumidores, Standard vs FIFO e quando usar em vez de SNS, Kinesis ou EventBridge

> [!warning] Aviso
> Limites (tamanho de mensagem, retenção, throughput, tamanho de lote), preços e recursos do SQS mudam. Os números aqui são referências de estudo; confirme na documentação oficial. Os comandos e códigos são exemplos e **não foram executados**.

O **Amazon Simple Queue Service (SQS)** é o **serviço de filas de mensagens totalmente gerenciado** da AWS. Ele permite que **partes de um sistema se comuniquem de forma assíncrona**: um **produtor** coloca **mensagens** em uma **fila**, e um ou mais **consumidores** as **retiram e processam** quando puderem. A fila funciona como um **amortecedor**: absorve picos, isola falhas e permite que produtor e consumidor **evoluam, escalem e falhem de forma independente**.

O SQS foi um dos **primeiros serviços da AWS** (2004) e continua sendo uma das **peças fundamentais de arquiteturas desacopladas**. É **serverless** (sem servidores para operar), **altamente disponível e durável** (mensagens replicadas em várias zonas de disponibilidade), e **escala automaticamente** de poucas a milhões de mensagens por segundo.

**Analogia:** a fila do SQS é uma **caixa de correio de uma fábrica**. Quem **envia pedidos** (produtor) os deposita na caixa sem esperar; os **funcionários** (consumidores) **retiram um pedido por vez** quando estão livres, trabalham nele e só então **o riscam da lista** (deletam). Se um funcionário **desaparece no meio do trabalho**, o pedido **volta à caixa** depois de um tempo para outro assumir. Se chegarem 10 mil pedidos de uma vez, **a caixa guarda todos**; ninguém é derrubado pela avalanche.

## O problema que o SQS resolve

| Problema (acoplamento síncrono) | Efeito |
|---|---|
| A API chama o serviço de e-mail **na hora** | Se o e-mail estiver lento ou fora, **a API também falha** |
| **Pico de tráfego** (Black Friday) | O backend é derrubado pela carga |
| Um consumidor lento **bloqueia** o produtor | Latência e timeouts em cascata |
| Escalar produtor e consumidor **juntos** | Desperdício de capacidade |
| Falha no processamento **perde** o trabalho | Dados e pedidos perdidos |
| Mudanças no consumidor **quebram** o produtor | Deploys arriscados |

**Com SQS:** o produtor **grava na fila e segue**; o consumidor **processa no seu ritmo**; picos viram **backlog** (fila crescendo), não **falhas**; falhas viram **retentativas** (a mensagem volta à fila); cada lado **escala independentemente**.

```
 SÍNCRONO (acoplado):       Cliente ─► API ─► Serviço de pedidos ─► Serviço de e-mail ─► ...
                                       (se algo falha ou demora, tudo falha ou demora)

 ASSÍNCRONO com SQS:        Cliente ─► API ─► [FILA SQS] ─► Consumidores (escalam conforme o backlog)
                                       │ responde rápido        │ falhou? a mensagem volta e é reprocessada
                                       ▼                        ▼
                                  (picos absorvidos)       DLQ para mensagens "venenosas"
```

## Conceitos fundamentais

| Conceito | Descrição |
|---|---|
| **Fila (queue)** | Contêiner de mensagens, com nome, URL e configurações |
| **Mensagem** | Dados (texto/JSON, até ~256 KiB por padrão; limites maiores podem existir) + **atributos** |
| **Produtor** | Quem **envia** mensagens (`SendMessage`) |
| **Consumidor** | Quem **recebe** (`ReceiveMessage`) e **deleta** (`DeleteMessage`) mensagens |
| **Message ID** | Identificador atribuído pelo SQS ao enviar |
| **Receipt handle** | **Token** devolvido **a cada recebimento**, necessário para **deletar** ou alterar a visibilidade da mensagem |
| **Visibility timeout** | Tempo em que a mensagem **fica invisível** para outros consumidores após ser recebida |
| **Retenção** | Tempo que a mensagem permanece na fila (60 s a **14 dias**; padrão 4 dias) |
| **Long polling** | Receber esperando até N segundos por mensagens (reduz chamadas vazias e custo) |
| **Dead-letter queue (DLQ)** | Fila para onde vão mensagens que **falham repetidamente** |
| **Message attributes** | Metadados estruturados (tipo, correlação, versão) |
| **Delay queue / delay por mensagem** | Atrasar a **disponibilidade** da mensagem (0 a 15 min) |
| **Standard vs FIFO** | Os **dois tipos de fila**, com garantias diferentes |

## O ciclo de vida de uma mensagem (visão geral)

```
 1. Produtor: SendMessage ───────────────► mensagem fica DISPONÍVEL na fila
 2. Consumidor: ReceiveMessage ──────────► mensagem fica INVISÍVEL (visibility timeout começa)
 3a. Processou com sucesso: DeleteMessage ► mensagem REMOVIDA definitivamente
 3b. Falhou ou demorou demais ──────────► timeout expira ─► mensagem VOLTA a ficar disponível (retentativa)
 4. Falhas repetidas (maxReceiveCount) ─► mensagem vai para a DLQ
```

> [!tip] O consumidor é quem apaga
> No SQS, **receber não remove a mensagem**. Quem **confirma o sucesso** é o consumidor, chamando **`DeleteMessage`**. Se ele **não deletar** (por falha ou esquecimento), a mensagem **reaparece** após o *visibility timeout* e será **processada de novo**. É o que garante **entrega "pelo menos uma vez"**, mas exige **idempotência**.

## Standard vs FIFO: os dois tipos de fila

| Característica | **Standard** | **FIFO** |
|---|---|---|
| **Throughput** | **Praticamente ilimitado** | **Até 300 msg/s por API** (3.000 com lotes); modo **high throughput** chega a **dezenas de milhares/s** por fila |
| **Entrega** | **Pelo menos uma vez** (*at-least-once*); duplicatas possíveis | **Exatamente uma vez** (processamento) com **deduplicação** em janela de 5 min |
| **Ordem** | **Melhor esforço** (pode chegar fora de ordem) | **Ordem estrita** **por grupo de mensagens** (`MessageGroupId`) |
| **Nome da fila** | Qualquer | **Termina em `.fifo`** |
| **Custo** | Menor | Um pouco maior por requisição |
| **Paralelismo** | Total entre consumidores | Paralelismo **entre grupos** (um grupo é processado em ordem por vez) |
| **Quando usar** | **Maioria dos casos**: tarefas independentes, alto volume | **Ordem e duplicatas importam**: transações, comandos sequenciais |

```
 STANDARD:  enviadas A,B,C,D  → podem ser recebidas B,A,C,A (A duplicada)   ← escala enorme
 FIFO:      enviadas A,B,C,D  → recebidas A,B,C,D (por grupo), sem duplicatas
```

Os detalhes de FIFO (grupos, deduplicação) têm uma folha própria.

## Modelo de preço (referência)

| Item | Cobrança |
|---|---|
| **Requisições** | **Por milhão de requisições** (`Send`, `Receive`, `Delete`, `ChangeVisibility`…); **1 milhão/mês gratuito** (confirme) |
| **Lotes (`SendMessageBatch`, etc.)** | **Uma requisição** cobre até **10 mensagens** |
| **Chunks de 64 KB** | **Cada 64 KB** de payload conta como **uma requisição** (mensagem de 256 KB = 4 requisições) |
| **FIFO** | Preço por requisição **maior** que Standard |
| **Transferência de dados** | Saída para a Internet/entre regiões |
| **SSE-KMS** | Custos do **KMS** por requisição |
| **Não cobra** | Armazenamento de mensagens, existência da fila, long polling "vazio" (cobra como requisição, mas **menos requisições**) |

> [!tip] Long polling e lotes reduzem custo
> **Short polling** (resposta imediata, muitas vezes vazia) gera **milhões de requisições inúteis**. **Long polling** (espera até 20 s) e **operações em lote** (até 10 mensagens) **reduzem muito** o número de requisições e, portanto, o custo.

## Limites de referência

| Limite | Valor de referência |
|---|---|
| **Tamanho da mensagem** | **256 KiB** (padrão histórico; a AWS ampliou o limite para **1 MiB** em evolução recente: confirme) |
| **Retenção** | 60 s a **14 dias** (padrão 4 dias) |
| **Visibility timeout** | 0 s a **12 horas** (padrão 30 s) |
| **Atraso (delay)** | 0 a **15 minutos** |
| **Long polling** | até **20 s** |
| **Mensagens por lote** | **10** |
| **Mensagens em voo** (recebidas e não deletadas) | **120.000** (Standard) / **20.000** (FIFO) por fila |
| **Atributos de mensagem** | Até **10** por mensagem |
| **Número de filas** | Praticamente ilimitado |
| **Nome da fila** | Até 80 caracteres (alfanuméricos, `-`, `_`) |

> [!warning] "Mensagens em voo" é um limite que pega desprevenido
> Se os consumidores **recebem mensagens e não as deletam**, elas ficam **em voo** até o *visibility timeout*. Ao atingir **120.000 em voo** (Standard), o SQS passa a devolver erros em `ReceiveMessage`. Corrija **o consumidor** (deletar ao terminar) e **reduza o visibility timeout** se for o caso.

## SQS vs SNS vs Kinesis vs EventBridge vs Amazon MQ

| Critério | **SQS** | **SNS** | **Kinesis Data Streams** | **EventBridge** | **Amazon MQ** |
|---|---|---|---|---|---|
| **Modelo** | **Fila** (ponto a ponto, consumo e remoção) | **Pub/Sub** (fan-out, push) | **Stream** ordenado e retido | **Barramento de eventos** com regras | **Brokers** (ActiveMQ/RabbitMQ) |
| **Consumo** | **Pull** (consumidor busca) | **Push** (SNS entrega) | Pull (shard iterators/EFO push) | **Push** para alvos | Protocolos padrão (AMQP, MQTT, JMS…) |
| **Retenção/releitura** | **Até 14 dias**, sem releitura após deletar | Não retém | **Até 365 dias**, com releitura | Arquivo/replay limitado | Conforme broker |
| **Múltiplos consumidores da mesma mensagem** | **Não** (cada mensagem vai para **um** consumidor) | **Sim** (todos os assinantes) | **Sim** (cada consumidor lê todo o stream) | **Sim** (vários alvos) | Tópicos/filas |
| **Ordem** | Standard: não; **FIFO**: por grupo | FIFO opcional | **Por shard** | Não garantida | Conforme broker |
| **Operação** | **Nenhuma** | Nenhuma | Gerenciar shards (ou on-demand) | Nenhuma | **Gerenciar brokers** |
| **Throughput** | Altíssimo (Standard) | Altíssimo | Alto por shard | Moderado/alto | Limitado pelo broker |
| **Ideal para** | **Desacoplar e amortecer trabalho** | **Notificar muitos** assinantes | **Streaming** em tempo real, vários leitores | **Integração baseada em regras** entre serviços/SaaS | **Migração** de apps que usam JMS/AMQP |

```
 Preciso que UM trabalhador processe cada tarefa, com buffer e retentativa?     ─► SQS
 Preciso avisar VÁRIOS sistemas do mesmo evento?                                 ─► SNS (e SQS por assinante: fan-out)
 Preciso de um fluxo ordenado, retido, com reprocessamento e vários leitores?    ─► Kinesis Data Streams
 Preciso rotear eventos por regras entre serviços AWS e SaaS?                    ─► EventBridge
 Tenho uma aplicação legada que usa JMS/AMQP e quero migrar sem reescrever?      ─► Amazon MQ
```

### Padrão clássico: SNS + SQS (fan-out)

```
 Produtor ──► SNS (tópico "pedido.criado")
                 ├─► Fila SQS "faturamento"  ──► consumidores de faturamento
                 ├─► Fila SQS "estoque"      ──► consumidores de estoque
                 └─► Fila SQS "notificacoes" ──► consumidores de e-mail
```

Cada serviço **tem sua própria fila** (com **seu ritmo, DLQ e escala**) e recebe **uma cópia** do evento: o **melhor dos dois mundos** (fan-out + buffer).

## Casos de uso

| Caso | Como o SQS ajuda |
|---|---|
| **Processamento assíncrono de tarefas** | Upload de imagem → fila → workers geram miniaturas |
| **Amortecer picos** | Pedidos de uma promoção entram na fila e são processados no ritmo do backend |
| **Desacoplar microsserviços** | Serviços se comunicam por filas, não por chamadas diretas |
| **Filas de trabalho (work queues)** | Distribuir tarefas entre vários workers (EC2, ECS, Lambda) |
| **Retentativas e tolerância a falhas** | Mensagens não processadas voltam à fila; DLQ isola as problemáticas |
| **Orquestração leve** | Passos de um fluxo em filas distintas |
| **Integração com Lambda** | Lambda consome a fila automaticamente |
| **Ordenação de comandos** | FIFO para transações por entidade (conta, pedido) |
| **Comunicação cross-account** | Filas compartilhadas por política |
| **Ingestão de eventos para batch** | Mensagens acumuladas e processadas em lotes |

## Primeiros comandos

```bash
# Cria uma fila Standard com long polling padrão e retenção de 4 dias
aws sqs create-queue --queue-name pedidos \
  --attributes ReceiveMessageWaitTimeSeconds=20,MessageRetentionPeriod=345600,VisibilityTimeout=60

URL=$(aws sqs get-queue-url --queue-name pedidos --query QueueUrl --output text)

# Envia uma mensagem
aws sqs send-message --queue-url "$URL" \
  --message-body '{"pedido_id":999,"valor":42.5}' \
  --message-attributes 'tipo={DataType=String,StringValue=pedido.criado}'

# Recebe (long polling de 20 s), processa e deleta
aws sqs receive-message --queue-url "$URL" --max-number-of-messages 5 --wait-time-seconds 20 \
  --attribute-names All --message-attribute-names All
aws sqs delete-message --queue-url "$URL" --receipt-handle "<ReceiptHandle>"

# Quantas mensagens há na fila?
aws sqs get-queue-attributes --queue-url "$URL" \
  --attribute-names ApproximateNumberOfMessages ApproximateNumberOfMessagesNotVisible
```

```python
import boto3, json
sqs = boto3.client("sqs")
url = sqs.get_queue_url(QueueName="pedidos")["QueueUrl"]

# Produtor
sqs.send_message(QueueUrl=url, MessageBody=json.dumps({"pedido_id": 999}))

# Consumidor (loop com long polling)
while True:
    resp = sqs.receive_message(QueueUrl=url, MaxNumberOfMessages=10, WaitTimeSeconds=20)
    for m in resp.get("Messages", []):
        try:
            processar(json.loads(m["Body"]))                       # idempotente!
            sqs.delete_message(QueueUrl=url, ReceiptHandle=m["ReceiptHandle"])
        except Exception:
            pass          # não deleta: volta à fila após o visibility timeout
```

## Exemplo prático: processamento de imagens

1. O usuário envia uma foto; a **API** a grava no **S3** e coloca uma mensagem `{bucket, chave}` na fila `imagens` (**responde em milissegundos**).
2. Um **Auto Scaling Group** (ou **Lambda**) consome a fila, gera **miniaturas** e grava no S3.
3. Em uma promoção, entram **50 mil fotos** em 10 minutos: a fila **cresce** (backlog) e os workers **escalam** conforme o tamanho da fila.
4. Imagens corrompidas **falham 3 vezes** e vão para a **DLQ**; um alarme avisa o time.
5. Os workers são **idempotentes**: reprocessar a mesma foto gera o mesmo resultado.
6. Um alarme em **`ApproximateAgeOfOldestMessage`** > 10 min indica que o processamento está atrasado.

## Erros comuns e armadilhas

- **Esquecer de deletar** a mensagem e processá-la repetidamente.
- **Visibility timeout menor que o tempo de processamento**, gerando processamento duplicado.
- **Sem DLQ**: mensagens "venenosas" ficam em loop até expirar.
- **Esperar ordem e exatamente-uma-vez em fila Standard.**
- **Short polling** com milhões de requisições vazias.
- **Consumidores não idempotentes** numa entrega *at-least-once*.
- **Usar SQS onde vários sistemas precisam da mesma mensagem** (use SNS + SQS).
- **Colocar payloads enormes na fila** (guarde no S3 e envie a referência).

## 🧩 Quiz de Fixação

1. Quem remove a mensagem da fila SQS?
2. O que é o visibility timeout?
3. Qual a diferença de garantias entre Standard e FIFO?
4. Para que serve uma DLQ?
5. Qual padrão permite que vários sistemas recebam a mesma mensagem com buffer próprio?
6. Como reduzir o custo de requisições do SQS?

**Respostas:**
1) O consumidor, chamando DeleteMessage após processar com sucesso; receber a mensagem não a remove.
2) O tempo em que a mensagem fica invisível para outros consumidores depois de recebida; se não for deletada nesse prazo, volta à fila.
3) Standard: entrega pelo menos uma vez, ordem de melhor esforço e throughput quase ilimitado; FIFO: ordem estrita por grupo e processamento exatamente uma vez com deduplicação, com throughput menor.
4) Receber mensagens que falharam repetidamente (acima de maxReceiveCount), isolando-as para análise sem bloquear a fila principal.
5) O fan-out SNS + SQS: um tópico SNS entrega uma cópia a cada fila SQS assinante.
6) Usando long polling (até 20 s) e operações em lote (até 10 mensagens por requisição).
