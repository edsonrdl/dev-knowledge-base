### Regras e padrões de evento no EventBridge — estrutura do evento, operadores de correspondência, regras por padrão e por agendamento, input transformers e testes

> [!warning] Aviso
> Operadores de correspondência, limites de tamanho de padrão, sintaxe de input transformers e comportamento de regras mudam. Os exemplos aqui são referências de estudo; confirme na documentação. Os padrões e comandos **não foram executados**.

As **regras** são o **cérebro de roteamento** do EventBridge: cada regra **descreve**, por meio de um **padrão de evento** (*event pattern*), **quais eventos lhe interessam** e **para onde enviá-los**. Dominar a **sintaxe dos padrões** (campos aninhados, listas, operadores de prefixo, numéricos, existência, exceções, curingas, OR) é o que permite **roteamento preciso sem código**. Esta folha cobre a **estrutura do evento**, a **lógica de correspondência**, **todos os operadores**, **regras por agendamento**, **input transformers** (reformatar o evento para o alvo), **eventos de exemplo e testes**, além dos **erros mais comuns** (padrões que "não casam").

**Analogia:** uma regra é um **filtro de e-mail**: "**se** o remetente é X **e** o assunto contém Y **e** o valor é maior que Z, **então** encaminhe para a pasta A e avise o time B". O EventBridge aplica **milhares de filtros** a cada evento que chega, **em paralelo**, e **entrega uma cópia** a cada alvo das regras que casaram.

---

## Estrutura de uma regra

| Elemento | Descrição |
|---|---|
| **Nome e barramento** | A regra **pertence a um barramento** (padrão, customizado ou de parceiro) |
| **Tipo** | **Padrão de evento** (*event pattern*) **ou** **agendamento** (cron/rate) |
| **Padrão de evento** | **JSON** que descreve o que casar |
| **Alvos (targets)** | Até **5** por regra, cada um com **ID**, **ARN**, **papel/IAM**, **input transformer**, **retry policy** e **DLQ** |
| **Estado** | `ENABLED` / `DISABLED` |
| **Descrição e tags** | Governança |

```bash
aws events put-rule --name pedidos-grandes --event-bus-name pedidos-bus \
  --event-pattern file://padrao.json --state ENABLED \
  --description "Pedidos acima de 10 mil"

aws events put-targets --rule pedidos-grandes --event-bus-name pedidos-bus --targets file://alvos.json
```

## Como funciona a correspondência (matching)

O EventBridge compara o **padrão** com o **evento**, **campo a campo**:

| Regra de lógica | Descrição |
|---|---|
| **Todos os campos listados** no padrão **devem casar** | **AND** entre campos (chaves) |
| **Vários valores no mesmo campo** | **OR** entre os valores (lista) |
| **Campos não mencionados no padrão** | **Ignorados** (o evento pode ter outros campos) |
| **Estrutura** | O padrão **espelha a estrutura** do evento (objetos aninhados) |
| **Valores são sempre listas** | Mesmo para um único valor: `"source": ["aws.ec2"]` |
| **Sensibilidade** | Correspondência **exata** e **sensível a maiúsculas** (exceto `equals-ignore-case`) |
| **Arrays no evento** | Casa se **qualquer elemento** do array casa |

```json
// Evento
{ "source": "com.minhaempresa.pedidos", "detail-type": "Pedido Criado",
  "detail": {"pedido_id": 999, "valor": 4299.9, "cliente": {"tipo": "premium", "pais": "BR"},
             "tags": ["urgente", "fragil"]} }

// Padrão que casa
{
  "source": ["com.minhaempresa.pedidos"],
  "detail-type": ["Pedido Criado", "Pedido Atualizado"],
  "detail": {
    "cliente": {"tipo": ["premium"]},
    "tags": ["urgente"]
  }
}
```
`detail-type` casa por ser **um dos** valores; `cliente.tipo` casa; `tags` casa porque **o array contém** `"urgente"`.

> [!tip] O padrão é uma "máscara" do evento
> Pense no padrão como **uma versão reduzida do próprio evento**, onde cada folha é **uma lista de valores aceitos**. Se você **copia um evento de exemplo** e **substitui os valores por listas**, já tem **um padrão válido**.

## Operadores de correspondência

| Operador | Sintaxe | Exemplo | Casa quando |
|---|---|---|---|
| **Igualdade (string)** | `["valor"]` | `"state": ["running"]` | Valor igual |
| **Igualdade (número)** | `[123]` | `"codigo": [404]` | Número igual |
| **Prefixo** | `[{"prefix": "..."}]` | `"key": [{"prefix": "uploads/"}]` | Começa com |
| **Sufixo** | `[{"suffix": "..."}]` | `"key": [{"suffix": ".csv"}]` | Termina com |
| **Prefixo ignorando caixa** | `[{"prefix": {"equals-ignore-case": "ab"}}]` | | Começa com (sem caixa) |
| **Igual ignorando caixa** | `[{"equals-ignore-case": "..."}]` | `"pais": [{"equals-ignore-case": "br"}]` | Igual sem distinguir caixa |
| **Curinga (wildcard)** | `[{"wildcard": "..."}]` | `"key": [{"wildcard": "dados/*/2026-*.csv"}]` | Casa com `*` em qualquer posição |
| **Qualquer exceto** | `[{"anything-but": [...]}]` | `"state": [{"anything-but": ["pending"]}]` | **Diferente** de todos os listados |
| **Anything-but prefixo/sufixo/curinga** | `[{"anything-but": {"prefix": "tmp"}}]` | | Não começa com |
| **Numérico** | `[{"numeric": ["op", n]}]` | `"valor": [{"numeric": [">", 1000]}]` | Comparações `=`, `<`, `<=`, `>`, `>=` |
| **Faixa numérica** | `[{"numeric": [">", 0, "<=", 100]}]` | | Entre valores |
| **Existência** | `[{"exists": true/false}]` | `"cupom": [{"exists": false}]` | Campo **presente/ausente** |
| **IP (CIDR)** | `[{"cidr": "10.0.0.0/8"}]` | `"sourceIp": [{"cidr": "10.0.0.0/8"}]` | IP dentro do bloco |
| **Nulo / vazio** | `[null]`, `[""]` | | Valor nulo / string vazia |
| **OR entre campos** | `"$or": [{...}, {...}]` | `{"$or": [{"a": ["x"]}, {"b": ["y"]}]}` | **Qualquer** das cláusulas |

```json
{
  "source": ["aws.s3"],
  "detail-type": ["Object Created"],
  "detail": {
    "bucket": {"name": ["meu-bucket-uploads"]},
    "object": {
      "key": [{"prefix": "entrada/"}, {"suffix": ".parquet"}],
      "size": [{"numeric": [">", 0, "<", 5368709120]}]
    },
    "reason": [{"anything-but": ["CopyObject"]}]
  }
}
```
Casa com: **objetos criados** no bucket `meu-bucket-uploads` cuja **chave começa com `entrada/` OU termina com `.parquet`**, **tamanho entre 0 e 5 GB**, e **motivo diferente de `CopyObject`**.

### Cuidados com operadores

| Cuidado | Explicação |
|---|---|
| **Lista de operadores = OR** | `"key": [{"prefix": "a"}, {"suffix": ".b"}]` é **prefixo `a` OU sufixo `.b`** |
| **Combinar condições no mesmo campo (AND)** | Não existe AND dentro do **mesmo campo** com operadores diferentes (exceto **faixas numéricas**); use **`$or`/estrutura** ou **filtre no alvo** |
| **Números vs strings** | `"valor": ["100"]` **não** casa `100` (número). **Tipos importam** |
| **`exists: false`** | Casa quando o campo **não existe**; **não** casa com `null` |
| **Anything-but numérico/string** | Aplica-se ao **tipo** informado |
| **Campos com ponto/hífen** | Use a **estrutura aninhada** correta; chaves com caracteres especiais exigem **atenção** |
| **Tamanho do padrão** | Há **limite** de tamanho/complexidade |
| **`$or` em profundidade** | Possível em níveis aninhados (conforme a documentação atual) |

> [!warning] O erro mais comum: padrão que "quase" casa
> Os causadores típicos: **valor do campo em tipo diferente** (string × número), **caminho errado** (`detail.pedido.valor` vs `detail.valor`), **esquecer que valores são listas**, **caixa diferente** (`Running` × `running`) e **evento com `detail` como string** em vez de objeto JSON. **Teste com o evento real** (veja "Testes" adiante).

## Padrões úteis (receitas)

### Eventos de serviços AWS

```json
// EC2 parou ou foi encerrada
{"source": ["aws.ec2"], "detail-type": ["EC2 Instance State-change Notification"],
 "detail": {"state": ["stopped", "terminated"]}}

// Falha em um estágio do CodePipeline
{"source": ["aws.codepipeline"], "detail-type": ["CodePipeline Stage Execution State Change"],
 "detail": {"state": ["FAILED"]}}

// Achado de alta severidade do GuardDuty
{"source": ["aws.guardduty"], "detail-type": ["GuardDuty Finding"],
 "detail": {"severity": [{"numeric": [">=", 7]}]}}

// Qualquer chamada de API que altera um security group (via CloudTrail)
{"source": ["aws.ec2"], "detail-type": ["AWS API Call via CloudTrail"],
 "detail": {"eventSource": ["ec2.amazonaws.com"],
            "eventName": ["AuthorizeSecurityGroupIngress", "RevokeSecurityGroupIngress"]}}

// Uso do usuário root
{"detail-type": ["AWS Console Sign In via CloudTrail"],
 "detail": {"userIdentity": {"type": ["Root"]}}}

// Eventos de saúde que afetam a conta
{"source": ["aws.health"], "detail-type": ["AWS Health Event"]}
```

### Eventos de negócio

```json
// Pedidos de clientes premium acima de R$ 1.000
{"source": ["com.minhaempresa.pedidos"], "detail-type": ["Pedido Criado"],
 "detail": {"cliente": {"tipo": ["premium"]}, "valor": [{"numeric": [">", 1000]}]}}

// Qualquer evento do domínio de pagamentos, exceto os de teste
{"source": [{"prefix": "com.minhaempresa.pagamentos"}],
 "detail": {"ambiente": [{"anything-but": ["teste"]}]}}

// Eventos cuja versão do esquema é 2 ou superior
{"detail": {"versao_esquema": [{"numeric": [">=", 2]}]}}
```

> [!tip] Sempre inclua `source` no padrão
> Um padrão **sem `source`** casa com **eventos de qualquer origem**, o que costuma **causar disparos inesperados** (e custos). Delimite **sempre** por `source` (e idealmente `detail-type`).

## Regras por agendamento (schedule)

Regras podem **disparar por tempo** em vez de por evento (no **barramento padrão**):

| Tipo | Sintaxe | Exemplo |
|---|---|---|
| **Rate** | `rate(valor unidade)` | `rate(5 minutes)`, `rate(1 hour)`, `rate(1 day)` |
| **Cron** | `cron(min hora dia-do-mês mês dia-da-semana ano)` | `cron(0 12 * * ? *)` (todo dia às 12:00 UTC) |
| **Fuso** | **UTC** nas regras (use **Scheduler** para fusos) | — |

```bash
aws events put-rule --name limpeza-noturna --schedule-expression "cron(0 3 * * ? *)"
```

> [!warning] Regras agendadas (CloudWatch Events) vs EventBridge Scheduler
> As **regras agendadas** são **legado**: **UTC apenas**, **precisão de ~1 minuto**, **sem janelas flexíveis**, **sem execução única**, **limitadas em escala**. Para **novos agendamentos**, prefira o **EventBridge Scheduler** (próxima folha): **fusos**, **janelas flexíveis**, **escala massiva**, **execução única**, **retries e DLQ**.

### Cron: atenção à sintaxe

```
 cron(Minutos Horas Dia-do-mês Mês Dia-da-semana Ano)
   0 12 * * ? *         → todo dia 12:00 UTC
   0/15 * * * ? *       → a cada 15 minutos
   0 8 ? * MON-FRI *    → dias úteis às 08:00 UTC
   0 0 1 * ? *          → primeiro dia de cada mês, meia-noite UTC
 Observação: "Dia-do-mês" e "Dia-da-semana" não podem ser ambos "*": um deles deve ser "?"
```

## Input transformer: reformatando o evento para o alvo

Por padrão, o alvo recebe o **evento completo**. Com **input** você pode **personalizar o que é enviado**:

| Opção de entrada do alvo | Descrição |
|---|---|
| **Evento correspondente (padrão)** | O **evento inteiro** |
| **Parte do evento (`InputPath`)** | Apenas **um trecho** (JSONPath), ex.: `$.detail` |
| **Constante (`Input`)** | **Texto/JSON fixo** (ignora o evento) |
| **Transformador de entrada (`InputTransformer`)** | **Extrai variáveis** do evento e **monta um novo texto/JSON** |

```json
{
  "InputTransformer": {
    "InputPathsMap": {
      "pedido": "$.detail.pedido_id",
      "valor": "$.detail.valor",
      "tipo": "$.detail.cliente.tipo",
      "quando": "$.time"
    },
    "InputTemplate": "{\"mensagem\": \"Pedido <pedido> (<tipo>) no valor de R$ <valor> criado em <quando>\", \"pedido_id\": <pedido>}"
  }
}
```

| Aspecto | Detalhe |
|---|---|
| **`InputPathsMap`** | **Variáveis** extraídas do evento por **JSONPath** |
| **`InputTemplate`** | **Modelo** em que `<variável>` é substituída |
| **Variáveis predefinidas** | `<aws.events.event.json>` (evento inteiro), `<aws.events.rule-arn>`, `<aws.events.rule-name>`, `<aws.events.event.ingestion-time>` |
| **Aspas** | **Strings** em JSON precisam de aspas **no template**; **números** não |
| **Limite** | Máximo de **100 variáveis**; erros de template **não entregam** o evento |
| **Usos** | Adaptar o evento a **APIs com formato próprio**, **mensagens legíveis** para SNS/Slack, **reduzir payload** |

```json
// Exemplo para SNS (mensagem de texto legível)
{
  "InputPathsMap": {"instancia": "$.detail.instance-id", "estado": "$.detail.state", "regiao": "$.region"},
  "InputTemplate": "\"A instância <instancia> mudou para <estado> na região <regiao>.\""
}
```

> [!tip] Transforme na regra, não no consumidor
> Usar **input transformers** **tira lógica de formatação** do código dos consumidores e **desacopla** o **formato do evento** do **formato esperado pelo alvo** (por exemplo, uma API de terceiros ou um webhook do Slack).

## Testar padrões e regras

| Método | Como |
|---|---|
| **Console: "Test event pattern"** | Cole **um evento** e **um padrão**; o console diz **se casa** |
| **API `test-event-pattern`** | `aws events test-event-pattern --event-pattern ... --event ...` |
| **Eventos de exemplo (sample events)** | Console oferece **eventos de exemplo** de serviços AWS |
| **`put-events` em um barramento de teste** | Publicar e observar a entrega a um alvo de teste (SQS/Lambda de log) |
| **Archive + Replay** | Reproduzir eventos reais em um barramento de teste |
| **CloudWatch Logs como alvo** | Enviar eventos a um **log group** para **inspecionar** |
| **Testes automatizados (CI)** | `test-event-pattern` com **casos positivos e negativos** |

```bash
aws events test-event-pattern \
  --event-pattern '{"source":["com.minhaempresa.pedidos"],"detail":{"valor":[{"numeric":[">",1000]}]}}' \
  --event '{"id":"1","account":"123456789012","time":"2026-11-09T14:00:00Z","region":"us-east-1",
            "source":"com.minhaempresa.pedidos","detail-type":"Pedido Criado","detail":{"valor":4299.9}}'
# {"Result": true}
```

> [!tip] Um log group como alvo de depuração
> Crie uma regra com o **mesmo padrão** e **alvo CloudWatch Logs**: você **vê exatamente o que casa**. É a forma mais rápida de **entender por que** uma regra dispara (ou **não dispara**).

## Boas práticas de regras e padrões

| Prática | Motivo |
|---|---|
| **Delimitar por `source` e `detail-type`** | Evita disparos amplos |
| **Padrões simples e legíveis** | Manutenção e menos erros |
| **Uma regra por intenção** | Clareza (em vez de padrões gigantes com `$or`) |
| **Regras como código** (CloudFormation/Terraform/CDK) | Versionamento e revisão |
| **Convenções de nomes** (`dominio-evento-acao`) | Governança |
| **Alvos com DLQ e retry** | Não perder eventos |
| **Testes de padrões no CI** | Evitar regressões |
| **Evitar regras "catch-all"** em barramentos de alto volume | Custos e ruído |
| **Documentar o contrato do evento** (schema) | Produtores e consumidores alinhados |
| **Versionar eventos** (`versao_esquema` em `detail`) | Evolução compatível |

## Armadilhas de modelagem de eventos

| Armadilha | Consequência | Solução |
|---|---|---|
| **Eventos "anêmicos"** (só um ID) | Consumidores precisam **consultar a fonte** (acoplamento) | Incluir os **campos essenciais** (event-carried state) ou aceitar a consulta conscientemente |
| **Eventos "gordos" demais** | Payload grande, dados sensíveis expostos | Equilíbrio: dados necessários + **referências** |
| **Nomes de eventos instáveis** | Regras quebram | **Contratos** e versionamento |
| **Misturar comando e fato** | Confusão ("CriarPedido" vs "PedidoCriado") | Eventos são **fatos no passado** |
| **Dados sensíveis no `detail`** | Vazamento a todos os alvos | Minimizar; criptografia; permissões |
| **Dependência de ordem** | Bugs sutis | Eventos **autossuficientes** e idempotência |

## Exemplo prático: roteamento de segurança e operação

1. **Regra 1** (barramento padrão): GuardDuty `severity >= 7` → **SNS** (equipe de segurança) com **input transformer** gerando uma mensagem legível.
2. **Regra 2**: CloudTrail `AuthorizeSecurityGroupIngress` com `cidrIp = 0.0.0.0/0` → **Lambda** que **remove a regra** e abre ticket.
3. **Regra 3**: `DeleteTrail`/`StopLogging` → **Step Functions** (restaura a trilha e alerta).
4. **Regra 4**: CodePipeline `FAILED` → **SNS/Slack** (via API destination) com o link da execução.
5. **Regra 5**: EC2 `terminated` com tag `env=prod` (filtro em `detail`) → **auditoria** em Firehose/S3.
6. Cada alvo tem **DLQ (SQS)** e **retry policy**; um **log group** captura **todos os eventos casados** por 7 dias para depuração.
7. **Testes** no CI validam cada padrão com **eventos positivos e negativos**.

## Troubleshooting

| Sintoma | Causa provável | Como resolver |
|---|---|---|
| **A regra não dispara** | Padrão não casa (tipo/caminho/caixa) | `test-event-pattern`; alvo de log; conferir o evento real |
| **A regra dispara demais** | Padrão amplo; sem `source`/`detail-type` | Delimitar; usar `anything-but`/prefixos |
| **`InvalidEventPatternException`** | JSON inválido ou operador incorreto | Validar sintaxe |
| **Evento casa mas o alvo não recebe** | Permissão do alvo ausente; alvo desabilitado | Role/política do alvo; verificar `FailedInvocations` |
| **Input transformer falha** | Caminho inexistente; template inválido (aspas) | Ajustar `InputPathsMap`/template; testar |
| **Número não casa** | Valor como string no evento | Padronizar tipos no produtor |
| **Campo opcional causa falhas** | Ausência do campo | `exists`; templates tolerantes |
| **Regra agendada no horário errado** | UTC | Converter fuso; usar Scheduler |
| **Duplicatas no alvo** | At-least-once | Idempotência |
| **Evento de serviço AWS não chega** | Serviço não emite para EventBridge; recurso não configurado (ex.: S3 sem EventBridge ligado) | Habilitar a integração (ex.: notificações do S3 ao EventBridge) |
| **Excede 5 alvos** | Limite por regra | Criar outra regra ou usar SNS/SQS para fan-out |
| **Padrão muito grande** | Limite de tamanho | Simplificar; dividir regras |

## Erros comuns e armadilhas

- **Valores sem lista** no padrão (`"source": "aws.ec2"` em vez de `["aws.ec2"]`).
- **Tipos trocados** (string × número) nos campos.
- **Padrões sem `source`**, disparando para eventos indesejados.
- **Regras agendadas legadas** para cenários que exigem fuso/escala.
- **Esquecer que `exists: false` não casa com `null`.**
- **Alvos sem DLQ**, perdendo eventos.
- **Templates de input** com aspas incorretas.
- **Não testar padrões** antes de produção.

## 🧩 Quiz de Fixação

1. Como o EventBridge combina vários campos e vários valores em um padrão?
2. Qual operador casa um campo que não existe no evento?
3. Para que serve um input transformer?
4. Por que sempre incluir `source` no padrão?
5. Qual a limitação das regras agendadas em relação ao Scheduler?
6. Como testar rapidamente se um padrão casa com um evento?

**Respostas:**
1) Campos diferentes combinam com AND (todos devem casar); múltiplos valores do mesmo campo combinam com OR.
2) `{"exists": false}`.
3) Reformatar o evento antes de entregá-lo ao alvo, extraindo variáveis por JSONPath e montando um novo texto ou JSON.
4) Para delimitar a origem; sem ele, o padrão pode casar eventos de qualquer fonte, causando disparos inesperados e custos.
5) As regras agendadas usam apenas UTC, não têm janelas flexíveis, execução única nem escala massiva; o Scheduler oferece fusos, janelas flexíveis, agendamentos únicos e grande escala.
6) Com `aws events test-event-pattern` (ou o teste de padrão no console), informando o padrão e um evento de exemplo.
