### Pipes, Scheduler, Archive e Schema Registry — fontes e enriquecimento, agendamentos em escala, replay de eventos, descoberta de schemas e geração de código

> [!warning] Aviso
> Fontes e alvos suportados por Pipes, limites do Scheduler, opções de archive, formatos de schema e preços mudam. Os exemplos aqui são referências de estudo; confirme na documentação. Os comandos e configurações **não foram executados**.

O barramento de eventos com regras resolve o **roteamento um-para-muitos por conteúdo**. Mas há **outros problemas de integração** que o EventBridge também resolve com **recursos especializados**: **conectar uma fonte a um destino de forma direta, com filtro e enriquecimento** (**Pipes**), **disparar ações em horários e prazos** (**Scheduler**), **guardar eventos e reprocessá-los** (**Archive e Replay**) e **documentar e descobrir o formato dos eventos** (**Schema Registry e Discovery**). Esta folha cobre esses **quatro recursos**, **quando usar cada um** e **como combiná-los** com o barramento.

**Analogia:** se o **barramento** é a **central de despacho**, os **Pipes** são **tubulações diretas** entre duas instalações (com **filtro** e **tratamento** no meio); o **Scheduler** é o **relógio de alarmes** da cidade; o **Archive** é a **gravação das chamadas** para **ouvir de novo**; e o **Schema Registry** é o **manual do formato das chamadas**, mantido automaticamente.

## EventBridge Pipes

O **Pipes** conecta **uma fonte** a **um destino** (**ponto a ponto**), com **etapas opcionais** de **filtro**, **enriquecimento** e **transformação**, **sem código de cola**.

```
 FONTE ─────► [Filtro] ─────► [Enriquecimento] ─────► [Transformação de entrada] ─────► ALVO
 (poll/stream)  (opcional)       (opcional)               (opcional)                      
 SQS, Kinesis, DynamoDB Streams, MSK/Kafka (gerenciado ou autogerenciado), Amazon MQ    Lambda, SFN, SQS, SNS, Kinesis, Event Bus, API destination, ECS, ...
                                Lambda / Step Functions (Express) / API Gateway / API destination
```

| Componente | Descrição |
|---|---|
| **Fonte (source)** | **SQS**, **Kinesis Data Streams**, **DynamoDB Streams**, **Amazon MQ**, **MSK / Kafka**: o Pipes **faz o polling** e **gerencia lotes, retries e escala** |
| **Filtro (filtering)** | **Padrão de evento** (a mesma sintaxe das regras) para **processar só o que interessa** (**reduz custo**) |
| **Enriquecimento (enrichment)** | **Lambda, Step Functions Express, API Gateway ou API destination** que **adiciona/transforma dados** (consultas a bancos, APIs) |
| **Alvo (target)** | Mais de **15 destinos** (Lambda, Step Functions, SQS, SNS, Kinesis, Firehose, **Event Bus**, API destinations, ECS, Batch, Redshift, SageMaker…) |
| **Transformação de entrada** | **Input transformer** antes do enriquecimento e antes do alvo |
| **Papel IAM** | Uma **role** única que acessa **fonte, enriquecimento e alvo** |
| **Configuração de lote** | Tamanho do **lote** e **janela de batching** |
| **DLQ** | Para **fontes** que suportam (SQS, Kinesis, DynamoDB Streams): **mensagens com falha** |

```bash
aws pipes create-pipe --name pedidos-dynamodb-para-eventbridge \
  --role-arn arn:aws:iam::123456789012:role/PipesRole \
  --source arn:aws:dynamodb:us-east-1:123456789012:table/pedidos/stream/2026-11-09T00:00:00.000 \
  --source-parameters '{
     "DynamoDBStreamParameters":{"StartingPosition":"LATEST","BatchSize":10,"MaximumRetryAttempts":3},
     "FilterCriteria":{"Filters":[{"Pattern":"{\"eventName\":[\"INSERT\"]}"}]}}' \
  --enrichment arn:aws:lambda:us-east-1:123456789012:function:enriquece-cliente \
  --target arn:aws:events:us-east-1:123456789012:event-bus/pedidos-bus \
  --target-parameters '{"EventBridgeEventBusParameters":{"DetailType":"Pedido Criado","Source":"com.minhaempresa.pedidos"}}'
```

### Pipes vs regras do barramento vs Lambda de cola

| Critério | **Pipes** | **Regras no barramento** | **Lambda "de cola"** |
|---|---|---|---|
| **Fontes** | **SQS, Kinesis, DynamoDB Streams, Kafka, MQ** (com polling gerenciado) | **Eventos publicados** (push) | Qualquer, **com código** |
| **Modelo** | **Ponto a ponto** (1 fonte → 1 alvo) | **Um para muitos** (pub-sub) | Lógica livre |
| **Código** | **Nenhum** (config) | Nenhum | **Você escreve e opera** |
| **Filtro/enriquecimento** | **Nativos** | Padrão de evento; sem enriquecimento nativo | Código |
| **Escala/retries/lotes** | **Gerenciados** | Gerenciados | Você configura |
| **Ordem** | Preserva a **ordem da fonte** (Kinesis/DynamoDB/FIFO) | Sem garantia | Depende |
| **Custo** | Por **requisição** pós-filtro | Por evento | Compute + eventos |
| **Ideal para** | **Conectar streams/filas a alvos** com filtro/enriquecimento | **Roteamento de eventos** para vários | Lógica complexa não coberta |

> [!tip] Filtre antes: o Pipes só cobra o que passa
> Com **filtro**, **eventos descartados não geram cobrança de requisição do Pipes** (e **evitam invocar** enriquecimento/alvo). Em **DynamoDB Streams**, filtrar por `eventName = INSERT` ou por campos de `NewImage` **reduz drasticamente** custos e ruído.

### Casos de uso do Pipes

| Caso | Pipe |
|---|---|
| **DynamoDB Streams → EventBridge** | Publicar **eventos de domínio** a partir de mudanças de dados, com **enriquecimento** |
| **SQS → Step Functions** | **Iniciar fluxos** para cada mensagem, **sem Lambda** |
| **Kinesis → API destination** | **Enviar eventos filtrados** a SaaS |
| **SQS → Lambda com enriquecimento** | Buscar dados e **injetar** antes de processar |
| **Kafka (MSK) → EventBridge** | **Integrar** o ecossistema Kafka a eventos AWS |
| **Fila → ECS task** | **Disparar tarefas** por mensagem |

### Boas práticas e limites do Pipes

| Prática | Motivo |
|---|---|
| **Filtrar na origem do Pipe** | Custo e ruído |
| **Enriquecimento rápido e idempotente** | Falhas de enriquecimento repetem o lote |
| **Configurar DLQ** da fonte (SQS/Kinesis/DynamoDB) | Não perder registros "venenosos" |
| **Lotes adequados** | Equilíbrio entre latência e custo |
| **Role com menor privilégio** | Segurança |
| **Observabilidade** (métricas e logs do Pipe) | Diagnóstico |
| **Ordem preservada** por fonte, **dentro dos limites** | Cuidado com **paralelismo** do alvo |
| **Limites**: **tamanho de payload**, **tipos de enriquecimento síncronos** | Confirmar na documentação |

## EventBridge Scheduler

O **Scheduler** é o serviço de **agendamento serverless** do EventBridge: dispara **ações** (**uma vez** ou **de forma recorrente**) em **mais de 270 serviços e 6.000+ APIs** da AWS, **em escala massiva** (**milhões de agendamentos**).

| Característica | Detalhe |
|---|---|
| **Tipos de agendamento** | **`at(...)`** (**uma vez**), **`rate(...)`** (**intervalo fixo**), **`cron(...)`** (**calendário**) |
| **Fuso horário** | **Qualquer fuso** (ex.: `America/Sao_Paulo`), com **horário de verão** tratado |
| **Janela flexível (flexible time window)** | Distribui as execuções em uma **janela** (ex.: **até 15 min**) para **evitar picos** |
| **Alvos** | **Lambda, SQS, SNS, Step Functions, ECS RunTask, Kinesis, EventBridge bus**, e **APIs universais** (`aws-sdk`) como `ec2:StartInstances`, `s3:PutObject`… |
| **Retentativas** | **Política** (`MaximumEventAgeInSeconds`, `MaximumRetryAttempts`) |
| **DLQ** | **Fila SQS** para falhas |
| **Datas** | **Início e fim** (`StartDate`, `EndDate`) |
| **Estado** | `ENABLED`/`DISABLED` |
| **Grupos de agendamentos (schedule groups)** | Organização, **tags** e **permissões** |
| **Excluir após executar** | `ActionAfterCompletion: DELETE` (para agendamentos únicos) |
| **Escala** | **Milhões** de agendamentos por conta |
| **Preço** | **14 milhões de invocações grátis/mês** (confirme); depois por milhão |

```bash
# Agendamento ÚNICO: lembrar o cliente em uma data/hora específica (fuso de São Paulo)
aws scheduler create-schedule --name lembrete-pedido-999 \
  --schedule-expression "at(2026-12-24T09:00:00)" --schedule-expression-timezone "America/Sao_Paulo" \
  --flexible-time-window Mode=OFF \
  --action-after-completion DELETE \
  --target '{
    "Arn":"arn:aws:lambda:us-east-1:123456789012:function:envia-lembrete",
    "RoleArn":"arn:aws:iam::123456789012:role/SchedulerRole",
    "Input":"{\"pedido_id\":999}",
    "RetryPolicy":{"MaximumEventAgeInSeconds":3600,"MaximumRetryAttempts":5},
    "DeadLetterConfig":{"Arn":"arn:aws:sqs:us-east-1:123456789012:scheduler-dlq"}}'

# RECORRENTE: relatório diário às 06:00 em São Paulo, com janela flexível de 15 min
aws scheduler create-schedule --name relatorio-diario \
  --schedule-expression "cron(0 6 * * ? *)" --schedule-expression-timezone "America/Sao_Paulo" \
  --flexible-time-window Mode=FLEXIBLE,MaximumWindowInMinutes=15 \
  --target '{"Arn":"arn:aws:states:us-east-1:123456789012:stateMachine:GeraRelatorio",
             "RoleArn":"arn:aws:iam::123456789012:role/SchedulerRole"}'
```

### Alvos "universais" (APIs do SDK)

O Scheduler pode **chamar diretamente APIs da AWS** sem Lambda, usando **alvos universais** (`arn:aws:scheduler:::aws-sdk:<serviço>:<ação>`):

```json
{
  "Arn": "arn:aws:scheduler:::aws-sdk:ec2:stopInstances",
  "RoleArn": "arn:aws:iam::123456789012:role/SchedulerRole",
  "Input": "{\"InstanceIds\":[\"i-0123456789abcdef0\"]}"
}
```

| Exemplo | Efeito |
|---|---|
| **`ec2:startInstances` / `stopInstances`** | Ligar/desligar ambientes por horário |
| **`rds:stopDBInstance`** | Economia fora do expediente |
| **`ecs:runTask`** | Jobs agendados |
| **`s3:putObject`** | Gravar marcas/arquivos |
| **`states:startExecution`** | Iniciar fluxos |
| **`sns:publish`** | Avisos programados |

### Scheduler vs regras agendadas vs cron em servidores

| Critério | **Scheduler** | **Regras agendadas (barramento padrão)** | **Cron em EC2/Lambda auto-agendada** |
|---|---|---|---|
| **Escala** | **Milhões** | Centenas (limites por regra) | Limitado |
| **Fuso horário** | **Qualquer** | **UTC apenas** | Do servidor |
| **Janela flexível** | **Sim** | Não | Não |
| **Execução única (`at`)** | **Sim** (e auto-exclusão) | Não | Não nativo |
| **Retries e DLQ** | **Sim** | Parcial | Manual |
| **Alvos universais** | **Sim** (6.000+ APIs) | Lista de alvos de regras | Código |
| **Operação** | **Nenhuma** | Nenhuma | Servidores/patches |
| **Preço** | Pequeno, com franquia | Gratuito (regras) | Computação |
| **Recomendação** | **Padrão para novos agendamentos** | Legado | Evitar |

> [!tip] Janela flexível evita o "efeito manada"
> Se **milhares de agendamentos** disparam **às 00:00:00**, o alvo recebe **um pico enorme**. Com **janela flexível (ex.: 15 min)**, o Scheduler **espalha** as execuções, **protegendo** o alvo e **reduzindo throttling**.

### Padrões de uso do Scheduler

| Padrão | Exemplo |
|---|---|
| **Lembretes e prazos por usuário** | Um agendamento `at` por pedido/assinatura (**auto-exclusão**) |
| **Ligar/desligar ambientes** | Seg–sex 07:00 liga; 20:00 desliga (economia) |
| **Relatórios e ETL periódicos** | `cron` com Step Functions/Glue |
| **Expiração e limpeza** | Agendar a remoção/arquivamento no futuro |
| **Retentativas com atraso longo** | `at` em +N horas para **reprocessar** |
| **Timers de negócio** | "Cancelar reserva se não paga em 30 min" |

> [!warning] "Executar uma vez" não substitui um workflow de longa duração
> Para **processos com estado** e **espera** (aprovações, timeouts compostos), use **Step Functions** (com `Wait`). O Scheduler é ótimo para **disparar** a ação no momento certo, **não para manter estado**.

## Archive e Replay

O **Archive** **guarda** os eventos de um barramento (**todos** ou **filtrados** por padrão) e o **Replay** **reenvia** eventos arquivados **a um barramento**, **por intervalo de tempo**.

```
 Barramento ─► Archive (padrão opcional, retenção N dias ou indefinida)
                  │
                  └─► Replay (de t1 a t2) ─► reenvia para o MESMO barramento (ou regras específicas) ─► alvos reprocessam
```

| Recurso | Detalhe |
|---|---|
| **Criação** | `create-archive` em um **barramento**, com **padrão** (opcional) e **retenção** (dias ou indefinida) |
| **Escopo do archive** | **Eventos do barramento** (custom, default, partner) |
| **Replay** | `start-replay`: **fonte** (archive), **destino** (barramento e, opcionalmente, **regras específicas**), **janela de tempo** |
| **Marcação** | Eventos reenviados têm `replay-name` no envelope; **o `time` original é preservado** |
| **Regras no replay** | Pode **limitar a regras** específicas (evita reenviar a todos os alvos) |
| **Custos** | **Armazenamento**, **processamento** do archive e **replay** |
| **Usos** | **Recuperar** de falhas de consumidor, **testes de regressão**, **popular novo serviço** com histórico, **reproduzir incidentes** |

```bash
aws events create-archive --archive-name pedidos-30d \
  --event-source-arn arn:aws:events:us-east-1:123456789012:event-bus/pedidos-bus \
  --retention-days 30 \
  --event-pattern '{"source":["com.minhaempresa.pedidos"]}'

aws events start-replay --replay-name reproc-bug-1109 \
  --event-source-arn arn:aws:events:us-east-1:123456789012:event-bus/pedidos-bus \
  --destination '{"Arn":"arn:aws:events:us-east-1:123456789012:event-bus/pedidos-bus",
                  "FilterArns":["arn:aws:events:us-east-1:123456789012:rule/pedidos-bus/faturamento"]}' \
  --event-start-time 2026-11-09T10:00:00Z --event-end-time 2026-11-09T14:00:00Z
```

| Boa prática de replay | Motivo |
|---|---|
| **Limitar a regras específicas** (`FilterArns`) | Evitar efeitos em outros consumidores |
| **Idempotência** nos consumidores | Reentrega de eventos já processados |
| **Replay em barramento de teste** primeiro | Validar |
| **Taxa de replay controlada** | Não sobrecarregar alvos |
| **Detectar eventos replayed** (`replay-name`) | Lógica especial (ex.: não enviar e-mails de novo) |
| **Retenção adequada** | Custo × necessidade |
| **Não confundir com event sourcing** | O archive **não é um store transacional**; use bancos/streams para isso |

> [!warning] Replay reenvia "efeitos colaterais" também
> Reproduzir eventos faz **todos os consumidores selecionados** agirem **de novo**: **e-mails duplicados**, **cobranças**, **chamadas a APIs**. **Restrinja** a replay às **regras certas** e **garanta idempotência** (ou **detecte** `replay-name` para **suprimir** efeitos externos).

## Schema Registry e Schema Discovery

O **Schema Registry** é um **catálogo de esquemas de eventos**; o **Schema Discovery** **infere esquemas automaticamente** dos eventos que passam por um barramento.

| Recurso | Descrição |
|---|---|
| **Schema Registry** | Armazena **esquemas** (OpenAPI 3 / JSON Schema Draft 4) **versionados** |
| **Registros** | `aws.events` (**esquemas de eventos de serviços AWS**, **públicos**), `discovered-schemas` (**descobertos**) e **seus** registros |
| **Schema Discovery** | Habilitado **por barramento**: **detecta** a **estrutura** dos eventos e **cria/atualiza** esquemas **automaticamente** (por **tipo** `source` + `detail-type`) |
| **Versões** | Mudanças compatíveis geram **novas versões** |
| **Code bindings** | **Gera código** (Java, Python, TypeScript) para **construir e ler** eventos tipados, via **console/IDE (AWS Toolkit)/CLI** |
| **Uso** | **Contratos** entre equipes, **IDE com autocompletar**, **documentação viva** |
| **Custo** | Discovery cobra por **milhão de eventos** ingeridos |

```bash
aws schemas create-discoverer --source-arn arn:aws:events:us-east-1:123456789012:event-bus/pedidos-bus \
  --description "Descoberta de esquemas de pedidos"

aws schemas list-schemas --registry-name discovered-schemas
aws schemas describe-schema --registry-name discovered-schemas --schema-name com.minhaempresa.pedidos@PedidoCriado

# Gerar bindings de código (ex.: Python)
aws schemas put-code-binding --registry-name discovered-schemas \
  --schema-name com.minhaempresa.pedidos@PedidoCriado --language Python36
aws schemas get-code-binding-source --registry-name discovered-schemas \
  --schema-name com.minhaempresa.pedidos@PedidoCriado --language Python36 binding.zip
```

```json
// Esquema (OpenAPI 3) descoberto, resumido
{
  "openapi": "3.0.0",
  "info": {"version": "1.0.0", "title": "PedidoCriado"},
  "paths": {},
  "components": {"schemas": {
    "AWSEvent": {"type": "object", "required": ["detail-type","resources","detail","id","source","time","region","version","account"],
      "x-amazon-events-detail-type": "Pedido Criado", "x-amazon-events-source": "com.minhaempresa.pedidos",
      "properties": {"detail": {"$ref": "#/components/schemas/PedidoCriado"}}},
    "PedidoCriado": {"type": "object", "properties": {
      "pedido_id": {"type": "integer"}, "valor": {"type": "number"},
      "cliente": {"type": "object", "properties": {"tipo": {"type": "string"}}}}}
  }}
}
```

### Esquemas como contratos

| Prática | Motivo |
|---|---|
| **Descobrir em desenvolvimento**, **fixar contratos** em produção | Discovery em produção **gera custo** e pode registrar formatos acidentais |
| **Registrar esquemas "oficiais"** (versionados em Git) no Registry | Fonte da verdade |
| **Evolução compatível** (adicionar campos opcionais) | Não quebra consumidores |
| **Versionar** mudanças incompatíveis (novo `detail-type`/campo `versao`) | Migração gradual |
| **Gerar bindings** para produtores e consumidores | Menos erros de tipagem |
| **Testes de contrato** no CI | Detectar quebras |
| **Governança** (donos, revisão) | Qualidade |

## Como combinar os recursos

```
 DynamoDB Streams ──Pipe (filtro INSERT + enriquecimento Lambda)──► Event Bus "pedidos-bus"
                                                                       │ (Schema Discovery documenta o formato)
                                                                       ├─ Archive 30 dias (para replay)
                                                                       ├─ Regras ─► SQS / SFN / SNS / API destination
                                                                       └─ Regra ─► Pipe? (não: Pipes têm FONTE própria; regras entregam a alvos)
 Scheduler ─► (at/cron) ─► Step Functions / Lambda / APIs SDK     (disparos por tempo)
```

| Necessidade | Recurso |
|---|---|
| **Converter mudanças de banco/fila em eventos** | **Pipes** → barramento |
| **Distribuir eventos por conteúdo** | **Regras** |
| **Disparar no futuro/recorrente** | **Scheduler** |
| **Reprocessar o passado** | **Archive + Replay** |
| **Documentar/gerar código** | **Schema Registry** |

## Exemplo prático: do banco ao evento, com agendamento e replay

1. **DynamoDB Streams** da tabela `pedidos` alimenta um **Pipe** com **filtro** `INSERT`, **enriquecimento** (Lambda que busca o **perfil do cliente**) e **alvo** `pedidos-bus` com `detail-type = "Pedido Criado"`.
2. O barramento tem **Schema Discovery** (em homologação) e um **Archive de 30 dias**.
3. **Regras** distribuem o evento a **faturamento** (SQS), **antifraude** (Step Functions) e **analytics** (Firehose).
4. Quando o pedido é criado, um **agendamento único** (`at(+30min)`, **auto-exclusão**) executa a **checagem de pagamento** (`states:startExecution`) e **cancela** se não pago.
5. **Relatório diário** às 06:00 (fuso de São Paulo) com **janela flexível de 15 min**.
6. Após um **bug** no faturamento, a equipe corrige o código e faz **replay** das 10:00–14:00 **apenas para a regra `faturamento`**, com **consumidores idempotentes**.
7. As **equipes consumidoras** geram **bindings** de código a partir dos **esquemas** registrados.

## Troubleshooting

| Sintoma | Causa provável | Como resolver |
|---|---|---|
| **Pipe não processa** | Role sem permissão na fonte/alvo; filtro excessivo; estado `STOPPED` | Revisar a role, o filtro e o estado |
| **Pipe duplica eventos** | Retentativas/lotes; enriquecimento falhando | Idempotência; corrigir o enriquecimento |
| **Enriquecimento lento** | Lambda/API demorada | Otimizar; aumentar capacidade; lotes menores |
| **Registros "venenosos" travam o Pipe** | Falhas persistentes | DLQ da fonte; `MaximumRetryAttempts` |
| **Scheduler dispara no horário errado** | Fuso/horário de verão; `cron` UTC | Definir `schedule-expression-timezone` |
| **Scheduler não executa** | Role sem permissão no alvo; expressão inválida; `EndDate` | Verificar role, expressão e datas |
| **Picos no alvo no mesmo horário** | Sem janela flexível | `Mode=FLEXIBLE` |
| **Agendamentos únicos "acumulam"** | Sem `ActionAfterCompletion` | `DELETE` |
| **Replay não reenvia** | Intervalo fora da retenção; sem eventos; regras filtradas | Conferir archive e janela |
| **Replay causa efeitos duplicados** | Sem idempotência/`FilterArns` | Restringir e proteger efeitos |
| **Schema Discovery sem esquemas** | Não habilitado; eventos não casam | Criar o discoverer; verificar tráfego |
| **Esquemas "poluídos"** | Descoberta em produção com eventos de teste | Descobrir só em dev; curar manualmente |
| **Custos de Pipes/Discovery** | Volume alto sem filtros | Filtrar; desligar discovery em produção |

## Erros comuns e armadilhas

- **Escrever Lambdas de cola** onde um **Pipe** basta.
- **Pipes sem filtro**, processando e pagando por tudo.
- **Usar regras agendadas legadas** para cenários com fuso, escala ou execução única.
- **Agendamentos em massa no mesmo segundo**, sem janela flexível.
- **Replay sem idempotência** e sem restringir regras.
- **Schema Discovery ligado indefinidamente** em produção.
- **Confundir Scheduler com orquestrador** de processos de longa duração.
- **Tratar Archive como event store transacional.**

## 🧩 Quiz de Fixação

1. O que é um Pipe do EventBridge e quais etapas ele pode ter?
2. Quais as vantagens do Scheduler sobre as regras agendadas?
3. Para que serve a janela flexível do Scheduler?
4. Como restringir um replay para não afetar todos os consumidores?
5. O que faz o Schema Discovery?
6. Por que filtrar no Pipe antes do enriquecimento?

**Respostas:**
1) Uma conexão ponto a ponto entre uma fonte (SQS, Kinesis, DynamoDB Streams, Kafka, MQ) e um alvo, com etapas opcionais de filtro, enriquecimento e transformação, sem código de cola.
2) Fusos horários, janelas flexíveis, execução única (at), escala de milhões de agendamentos, retries e DLQ, e alvos universais para milhares de APIs da AWS.
3) Distribuir as execuções dentro de uma janela de tempo, evitando picos simultâneos no alvo e throttling.
