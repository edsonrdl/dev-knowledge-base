### Alvos e entrega no EventBridge — tipos de alvo, permissões, retentativas e DLQ, API destinations, barramentos entre contas e regiões e políticas de recurso

> [!warning] Aviso
> Tipos de alvo suportados, parâmetros específicos por alvo, política de retentativa padrão, limites de API destinations e regras de acesso entre contas mudam. Os exemplos aqui são referências de estudo; confirme na documentação. Os comandos e políticas **não foram executados**.

Casar o evento com a regra é **metade do trabalho**; a outra metade é **entregá-lo ao alvo com segurança e confiabilidade**. É na **entrega** que aparecem os **problemas reais**: **permissões ausentes** (a regra dispara, **o alvo nunca executa**), **alvos lentos ou fora do ar**, **eventos perdidos** após as retentativas, **APIs externas** que **limitam a taxa**, **barramentos de outras contas** sem autorização. Esta folha cobre **os tipos de alvo**, **como cada um é autorizado** (**roles IAM** vs **políticas de recurso**), a **política de retentativa e a DLQ**, as **API destinations** (chamar HTTPS externos com autenticação e limite de taxa), os **barramentos entre contas e regiões** e **como monitorar e depurar** falhas de entrega.

**Analogia:** o EventBridge é uma **transportadora**. A regra define **o destino do pacote**; a **entrega** exige **autorização para entrar no prédio** (permissões), **tentativas repetidas** se **ninguém atende** (retry), **um depósito para pacotes não entregues** (DLQ) e, para destinos externos, **o protocolo de portaria** do cliente (autenticação das API destinations).

## Tipos de alvo

| Categoria | Alvos | Observações |
|---|---|---|
| **Computação** | **AWS Lambda**, **ECS task** (RunTask), **Batch job**, **EC2** (via SSM Run Command/Automation), **EKS** (via outros meios) | Lambda é o mais comum |
| **Orquestração** | **Step Functions state machine** | Inicia **execuções** |
| **Mensageria** | **SQS**, **SNS**, **Kinesis Data Streams**, **Kinesis Data Firehose** | **Padrão de buffering** |
| **Integração** | **API Gateway** (REST), **API destinations** (HTTPS externo), **EventBridge Event Bus** (outro barramento/conta/região) | Conexões a sistemas externos |
| **Operações e segurança** | **Systems Manager** (Run Command, Automation, OpsItem), **CodePipeline**, **CodeBuild**, **CloudWatch Logs** (log group), **Inspector**, **Security Hub** | Automação e depuração |
| **Dados** | **Redshift Data API**, **SageMaker Pipeline**, **Glue Workflow** | Pipelines |
| **Outros** | **EC2 actions** (StopInstances, RebootInstances…), **Amazon Pinpoint**, **Amazon MQ**, **App Runner** etc. | Ver a lista atual |

```bash
# Alvo Lambda
aws events put-targets --rule pedidos-grandes --event-bus-name pedidos-bus --targets '[
  {"Id":"analise","Arn":"arn:aws:lambda:us-east-1:123456789012:function:analisa-pedido"}]'

# Alvo SQS FIFO (exige MessageGroupId)
aws events put-targets --rule pedidos-todos --event-bus-name pedidos-bus --targets '[
  {"Id":"fila-fifo","Arn":"arn:aws:sqs:us-east-1:123456789012:pedidos.fifo",
   "SqsParameters":{"MessageGroupId":"pedidos"}}]'

# Alvo Step Functions
aws events put-targets --rule falha-pipeline --targets '[
  {"Id":"sfn","Arn":"arn:aws:states:us-east-1:123456789012:stateMachine:Remedia",
   "RoleArn":"arn:aws:iam::123456789012:role/EventBridgeInvokeSfn"}]'
```

### Parâmetros específicos por alvo

| Alvo | Parâmetros importantes |
|---|---|
| **SQS FIFO** | `MessageGroupId` (obrigatório), dedup |
| **Kinesis** | `PartitionKeyPath` (campo do evento usado como chave) |
| **ECS** | Cluster, definição de tarefa, rede (`NetworkConfiguration`), `LaunchType`, contagem |
| **Batch** | Job definition, job name, array size |
| **API Gateway / HTTP** | Método, **parâmetros de cabeçalho/query/caminho** (`HttpParameters`) |
| **Step Functions** | Input (evento ou transformado) |
| **Redshift Data API** | Banco, SQL(s), nome da declaração |
| **Run Command (SSM)** | Alvos por tag/ID |
| **Log group** | Nada extra |
| **Outro barramento** | `EventBusName` (ARN do destino) |

> [!tip] Até 5 alvos por regra
> Cada regra suporta **no máximo 5 alvos** (limite padrão de referência). Para **mais destinos**, **crie regras adicionais** com o mesmo padrão, ou **encaminhe a um SNS** (fan-out massivo) ou a um **barramento intermediário**.

## Permissões de entrega

O EventBridge precisa de **autorização** para **invocar cada alvo**. Há **dois mecanismos**:

| Mecanismo | Alvos | Como funciona |
|---|---|---|
| **Política de recurso (resource-based)** | **Lambda, SQS, SNS, CloudWatch Logs, API Gateway (em alguns casos)** | A **política do alvo** permite **`events.amazonaws.com`** com **condição** na **regra** (`aws:SourceArn`) |
| **Role IAM (execution role) da regra/alvo** | **Step Functions, ECS, Kinesis, Firehose, Batch, SSM, CodePipeline, outro barramento…** | O alvo é configurado com um **`RoleArn`** que o EventBridge **assume** (a trust policy confia em **`events.amazonaws.com`**) |

```bash
# Lambda: a política da função permite o EventBridge (adicionada automaticamente pelo console; manual pela CLI)
aws lambda add-permission --function-name analisa-pedido \
  --statement-id eventbridge-pedidos-grandes \
  --action lambda:InvokeFunction --principal events.amazonaws.com \
  --source-arn arn:aws:events:us-east-1:123456789012:rule/pedidos-bus/pedidos-grandes
```

```json
// Política da fila SQS: permite que a regra envie mensagens
{
  "Effect": "Allow",
  "Principal": {"Service": "events.amazonaws.com"},
  "Action": "sqs:SendMessage",
  "Resource": "arn:aws:sqs:us-east-1:123456789012:faturamento",
  "Condition": {"ArnEquals": {"aws:SourceArn": "arn:aws:events:us-east-1:123456789012:rule/pedidos-bus/pedidos-todos"}}
}
```

```json
// Role para Step Functions (trust policy + permissão)
{ "Trust": {"Effect":"Allow","Principal":{"Service":"events.amazonaws.com"},"Action":"sts:AssumeRole"},
  "Permissão": {"Effect":"Allow","Action":"states:StartExecution","Resource":"arn:aws:states:us-east-1:123456789012:stateMachine:Remedia"} }
```

> [!warning] "A regra dispara, mas o alvo não executa": quase sempre é permissão
> Se as métricas mostram **`MatchedEvents`/`TriggeredRules`** subindo mas o alvo **não roda** (e **`FailedInvocations`** > 0), a causa é **permissão**: **política da Lambda/SQS/SNS** sem `events.amazonaws.com`, ou **role** sem permissão/trust corretos. Ao **criar alvos pelo console**, as permissões costumam ser **adicionadas automaticamente**; **na IaC/CLI, você precisa declará-las**.

### Criptografia e KMS

| Situação | Cuidado |
|---|---|
| **SQS/SNS criptografados com CMK** | A **política da chave** deve permitir **`events.amazonaws.com`** (`kms:GenerateDataKey*`, `kms:Decrypt`) |
| **Barramento com KMS** | O barramento pode usar **CMK** para criptografar eventos em repouso |
| **Chave gerenciada pela AWS** | **Sem controle** da política: pode impedir entrega de alguns serviços |

## Retentativas e DLQ

Se a **entrega falha** (alvo **indisponível**, **throttling**, **erro 5xx**), o EventBridge **tenta de novo**.

| Parâmetro | Padrão (referência) | Faixa |
|---|---|---|
| **`MaximumEventAgeInSeconds`** | **24 horas** | 60 s a 24 h |
| **`MaximumRetryAttempts`** | **185** | 0 a 185 |
| **Backoff** | **Exponencial com jitter** | — |
| **Ao esgotar** | O evento é **descartado** ou enviado à **DLQ** do alvo | — |

```json
{
  "Id": "analise",
  "Arn": "arn:aws:lambda:us-east-1:123456789012:function:analisa-pedido",
  "RetryPolicy": {"MaximumEventAgeInSeconds": 3600, "MaximumRetryAttempts": 20},
  "DeadLetterConfig": {"Arn": "arn:aws:sqs:us-east-1:123456789012:eventbridge-dlq"}
}
```

| Aspecto da DLQ | Detalhe |
|---|---|
| **Tipo** | **Fila SQS** (Standard) |
| **Configuração** | **Por alvo** (`DeadLetterConfig`) |
| **Permissão** | A **fila** deve permitir **`events.amazonaws.com`** com `aws:SourceArn` da **regra** |
| **Conteúdo** | O **evento original** + **atributos** com **erro** (`ERROR_CODE`, `ERROR_MESSAGE`, `RULE_ARN`, `TARGET_ARN`, tentativas) |
| **Retenção** | Defina **longa** (ex.: 14 dias) |
| **Monitoramento** | Alarme em **mensagens na DLQ** e na métrica **`InvocationsSentToDlq`**/**`InvocationsFailedToBeSentToDlq`** |

> [!tip] A retentativa padrão é muito generosa
> **185 tentativas em 24 horas** é ótimo para **resiliência**, mas **mascara problemas** por horas e pode **acumular eventos** no alvo quando ele volta. Para **eventos que perdem valor** com o tempo, **reduza** `MaximumEventAgeInSeconds`. Para **eventos críticos**, mantenha **longo** e **configure DLQ**.

### O que conta como falha

| Tipo | Comportamento |
|---|---|
| **Erros transitórios** (5xx, throttling, timeouts) | **Retentativa** com backoff |
| **Erros permanentes** (alvo inexistente, permissão negada, parâmetros inválidos) | **Sem retentativa útil**: vai à **DLQ** (se houver) ou é descartado |
| **Lambda: erro dentro da função** | A invocação foi **aceita**: a falha **do código** é tratada pela **política assíncrona da Lambda** (retries, DLQ/destino da função), **não** pela DLQ do EventBridge |
| **API destination: 429/5xx** | Retentativas conforme a política e o **limite de taxa** |

> [!warning] Lambda: duas camadas de retry
> O EventBridge invoca a Lambda **de forma assíncrona**. **Falha de entrega** (permissão, função inexistente) → **retry/DLQ do EventBridge**. **Falha do código** → **retry assíncrono da Lambda** (até 2 por padrão) e **DLQ/destino da função**. Configure **ambos** e **idempotência**.

## API destinations

As **API destinations** permitem que uma regra **chame diretamente um endpoint HTTPS** (de **SaaS**, **sistemas on-premises expostos** ou **suas APIs**), **sem escrever Lambda**.

```
 Evento ─► Regra ─► Alvo: API Destination ─► Connection (autenticação) ─► HTTPS endpoint (ex.: Slack, PagerDuty, ServiceNow, sua API)
```

| Componente | Descrição |
|---|---|
| **Connection** | Define a **autenticação**: **Basic**, **API Key** (cabeçalho/parâmetro) ou **OAuth client credentials**; guarda segredos no **Secrets Manager** (gerenciado) |
| **API destination** | **URL**, **método HTTP**, **limite de invocações por segundo** |
| **Parâmetros do alvo** | Cabeçalhos, query strings e corpo (via **input transformer**) |
| **Timeout** | Limite curto por requisição (ex.: ~5 s) |

```bash
aws events create-connection --name slack-conn --authorization-type API_KEY \
  --auth-parameters '{"ApiKeyAuthParameters":{"ApiKeyName":"Authorization","ApiKeyValue":"Bearer xoxb-..."}}'

aws events create-api-destination --name slack-alertas \
  --connection-arn arn:aws:events:us-east-1:123456789012:connection/slack-conn/abc123 \
  --invocation-endpoint https://slack.com/api/chat.postMessage \
  --http-method POST --invocation-rate-limit-per-second 5
```

| Boa prática | Motivo |
|---|---|
| **Definir `invocation-rate-limit-per-second`** | **Respeitar limites** do SaaS e evitar **429** |
| **Usar input transformer** para montar o **corpo** exigido pela API | Sem código |
| **DLQ no alvo** | Falhas após retentativas |
| **Segredos gerenciados pela Connection** | Sem credenciais no código |
| **Endpoints públicos HTTPS com TLS válido** | Requisito |
| **Cuidado com dados sensíveis** | O evento vai a um terceiro |
| **Para APIs privadas** | Use **API Gateway privado/Lambda em VPC** ou **PrivateLink** conforme o caso |
| **Monitorar `Invocations`/`FailedInvocations`** | Saúde da integração |

> [!tip] API destinations substituem muitas "Lambdas de cola"
> Se a única função da Lambda é **repassar o evento a uma API HTTP**, uma **API destination + input transformer** **elimina o código**, **reduz custo e manutenção** e ganha **rate limiting e retry** nativos.

## Barramentos entre contas e entre regiões

### Encaminhar eventos para outro barramento

Um **alvo** pode ser **outro barramento** (mesma conta, **outra conta** ou **outra região**), formando **topologias** como **hub-and-spoke**.

```
 Conta A (workload)                   Conta Hub (observabilidade/segurança)
 bus default ──regra: GuardDuty──► bus central ──► regras ──► SNS/Lambda/Security Hub
 bus pedidos ──regra: todos──────► bus de dados ──► Firehose ──► S3 (data lake)
```

| Elemento | Detalhe |
|---|---|
| **Alvo do tipo "Event bus"** | `Arn` do barramento destino + **`RoleArn`** (para a origem enviar) |
| **Política do barramento de destino** | **Resource policy** permitindo **`events:PutEvents`** da **conta/organização de origem** |
| **Entre regiões** | Suportado (alvo = barramento em outra região); **latência e custo** adicionais |
| **Custo** | Eventos **entregues ao outro barramento são cobrados** (por milhão) |
| **Evitar loops** | Cuidado com **regras circulares** entre barramentos |

```json
// Política do barramento central: aceita eventos de toda a organização
{
  "Version": "2012-10-17",
  "Statement": [{
    "Sid": "AceitarEventosDaOrganizacao",
    "Effect": "Allow",
    "Principal": "*",
    "Action": "events:PutEvents",
    "Resource": "arn:aws:events:us-east-1:111111111111:event-bus/central",
    "Condition": {"StringEquals": {"aws:PrincipalOrgID": "o-abc123xyz"}}
  }]
}
```

```bash
aws events put-permission --event-bus-name central \
  --policy file://politica-bus.json
```

| Padrão | Uso |
|---|---|
| **Hub de segurança** | Todas as contas encaminham **GuardDuty/Config/CloudTrail** a uma conta central |
| **Hub de operações** | Eventos de saúde e de pipelines em um painel |
| **Barramento por domínio** | Cada time publica no **seu barramento**; assinantes **criam regras** |
| **Multi-região (DR)** | Replicar eventos críticos para outra região |
| **Aceitar de "qualquer conta"** | **Evite**: use **`aws:PrincipalOrgID`** ou **lista explícita** |

> [!warning] Aceitar `PutEvents` de qualquer lugar é arriscado
> Uma política com `Principal: "*"` **sem condição** permite que **qualquer conta AWS** publique no seu barramento (**injetando eventos falsos**, gerando **custos** e **disparando ações**). **Sempre** restrinja com **`aws:PrincipalOrgID`** ou **contas específicas**.

### Global Endpoints (failover de ingestão)

| Aspecto | Detalhe |
|---|---|
| **O que são** | Endpoint **global** que roteia `PutEvents` para um **barramento primário** e **faz failover** para um **secundário** em outra região |
| **Gatilho de failover** | **Alarme do Route 53 Health Check** (por exemplo, falhas de ingestão) |
| **Replicação** | **Replicação de eventos** do primário ao secundário (opcional) |
| **Uso** | **Alta disponibilidade** de ingestão e **DR** |
| **Cuidados** | **Idempotência** (eventos podem ser entregues em ambas as regiões); regras equivalentes nas duas regiões |

## Observabilidade da entrega

| Métrica (`AWS/Events`) | Significado |
|---|---|
| **`Invocations`** | Tentativas de invocação de alvos |
| **`SuccessfulInvocationAttempts`** | Invocações **bem-sucedidas** |
| **`FailedInvocations`** | **Falhas** (após retentativas) |
| **`TriggeredRules`** | Regras que **casaram** |
| **`MatchedEvents`** | Eventos que **casaram** |
| **`ThrottledRules`** | Regras **limitadas** (throttling) |
| **`InvocationsSentToDlq`** | Enviadas à **DLQ** |
| **`InvocationsFailedToBeSentToDlq`** | **Falha ao enviar à DLQ** (crítico) |
| **`DeadLetterInvocations`** | Entregas à DLQ |
| **`RetryInvocationAttempts`** | Retentativas |
| **`IngestionToInvocationStartLatency`** | **Latência** entre ingestão e início da invocação |
| **`PutEventsApproximateThrottledCount`** etc. | Throttling de ingestão |

```bash
aws cloudwatch put-metric-alarm --alarm-name eb-pedidos-falhas \
  --namespace AWS/Events --metric-name FailedInvocations \
  --dimensions Name=RuleName,Value=pedidos-grandes Name=EventBusName,Value=pedidos-bus \
  --statistic Sum --period 300 --evaluation-periods 1 --threshold 0 \
  --comparison-operator GreaterThanThreshold --alarm-actions arn:aws:sns:us-east-1:123456789012:oncall
```

| Alarme recomendado | Por quê |
|---|---|
| **`FailedInvocations` > 0** | Entregas falhando |
| **`InvocationsFailedToBeSentToDlq` > 0** | Eventos **perdidos** |
| **DLQ não vazia** | Falhas a tratar |
| **`ThrottledRules` > 0** | Capacidade/limite |
| **Latência de entrega alta** | Degradação |
| **Queda de `MatchedEvents`** | Produtor parou ou padrão quebrou |

## Exemplo prático: entrega robusta a Slack, filas e a outra conta

1. A regra `pedidos-todos` entrega a **SQS** (`faturamento`, com **DLQ**), a **Firehose** (arquivo) e ao **barramento central** da conta de dados (via role).
2. A regra `pedidos-grandes` (> 10 mil) usa uma **API destination** para o **Slack** (rate limit de **5/s**), com **input transformer** que monta a mensagem e **DLQ**.
3. A regra de **segurança** (GuardDuty alto) entrega a **Step Functions** com **role** de mínimo privilégio.
4. A **fila `faturamento`** permite **`events.amazonaws.com`** com `aws:SourceArn` da regra; a **CMK** permite o serviço.
5. **Retry policy**: 6 horas e 50 tentativas para faturamento (crítico); **1 hora** para o Slack (perde valor rapidamente).
6. O **barramento central** aceita eventos **só da organização** (`aws:PrincipalOrgID`).
7. **Alarmes**: `FailedInvocations`, DLQs, `InvocationsFailedToBeSentToDlq`, latência; **runbook** de redrive da DLQ.

## Troubleshooting

| Sintoma | Causa provável | Como resolver |
|---|---|---|
| **Regra casa, alvo não executa** | Permissão (política do alvo ou role/trust) | Adicionar `events.amazonaws.com`/`SourceArn` ou role correta |
| **`FailedInvocations` alto** | Alvo indisponível/throttling/erro de parâmetros | Ver erro; capacidade do alvo; corrigir parâmetros |
| **Nada na DLQ** | Sem `DeadLetterConfig` ou sem permissão da fila | Configurar; queue policy |
| **`InvocationsFailedToBeSentToDlq`** | Fila inexistente/sem permissão/KMS | Corrigir |
| **SQS FIFO recusa** | Falta `MessageGroupId` | `SqsParameters` |
| **Kinesis sem chave** | `PartitionKeyPath` incorreto | Ajustar |
| **API destination 429/5xx** | Taxa acima do limite do SaaS | Reduzir `invocation-rate-limit`; retry; DLQ |
| **API destination 401/403** | Credenciais da connection | Atualizar a connection |
| **Evento não chega a outra conta** | Política do barramento destino; role de envio | `put-permission`; role/trust |
| **Eventos duplicados** | At-least-once; retries; Global Endpoint | Idempotência |
| **Eventos perdidos após horas** | Retentativas esgotadas sem DLQ | DLQ; ajustar retry |
| **Lambda recebe, mas falha** | Erro no código | Retry assíncrono da Lambda; DLQ/destino da função |
| **Latência alta** | Alvo lento; backlog de retentativas | Escalar alvo; reduzir idade máxima |
| **Custos inesperados** | Cross-account/region; muitos eventos; replays | Revisar topologia e volumes |

## Erros comuns e armadilhas

- **Esquecer as permissões do alvo** ao criar regras por IaC/CLI.
- **Alvos sem DLQ** e sem alarmes.
- **Aceitar `PutEvents` de qualquer conta.**
- **Confundir falha de entrega com falha do código** em Lambda.
- **Chamar APIs externas sem rate limit** e esgotar cotas do parceiro.
- **Dados sensíveis no evento** enviados a API destinations de terceiros.
- **Loops** de regras entre barramentos.
- **Não tratar duplicatas** (entrega at-least-once).

## 🧩 Quiz de Fixação

1. Quais são os dois mecanismos de autorização para o EventBridge invocar alvos?
2. Qual a política de retentativa padrão do EventBridge?
3. Para que servem as API destinations?
4. Como permitir que outra conta publique no seu barramento com segurança?
5. Por que a falha do código de uma Lambda não vai para a DLQ do EventBridge?
6. Que métrica indica que eventos falharam até ao ir para a DLQ?

**Respostas:**
1) Política de recurso no alvo (para Lambda, SQS, SNS, Logs) com `events.amazonaws.com` e `aws:SourceArn`, e role IAM assumida pelo EventBridge (para Step Functions, ECS, Kinesis, outro barramento etc.).
2) Até 24 horas e 185 tentativas, com backoff exponencial e jitter, configuráveis por alvo, com DLQ opcional.
3) Chamar endpoints HTTPS externos diretamente de uma regra, com autenticação (Basic, API Key, OAuth) e limite de taxa, sem escrever código.
4) Com a resource policy do barramento permitindo `events:PutEvents` restrito por `aws:PrincipalOrgID` ou por contas específicas.
5) Porque a invocação é assíncrona e foi aceita; falhas do código seguem a política assíncrona da própria Lambda (retries e DLQ ou destino da função).
6) `InvocationsFailedToBeSentToDlq`.
