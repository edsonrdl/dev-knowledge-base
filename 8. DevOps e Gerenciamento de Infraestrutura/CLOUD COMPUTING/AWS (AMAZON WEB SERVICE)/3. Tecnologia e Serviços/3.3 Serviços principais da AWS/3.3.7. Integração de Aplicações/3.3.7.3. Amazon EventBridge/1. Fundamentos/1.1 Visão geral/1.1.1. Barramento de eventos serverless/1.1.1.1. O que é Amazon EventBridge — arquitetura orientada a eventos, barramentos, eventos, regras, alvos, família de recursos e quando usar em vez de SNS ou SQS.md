### O que é Amazon EventBridge — arquitetura orientada a eventos, barramentos, eventos, regras, alvos, família de recursos e quando usar em vez de SNS ou SQS

> [!warning] Aviso
> Limites (regras por barramento, alvos por regra, tamanho de evento, taxa de PutEvents), preços e recursos do EventBridge mudam com frequência. Os números aqui são referências de estudo; confirme na documentação oficial. Os comandos e códigos são exemplos e **não foram executados**.

O **Amazon EventBridge** é o **barramento de eventos serverless** da AWS. Ele **recebe eventos** (de **serviços AWS**, de **suas aplicações** e de **parceiros SaaS**), **avalia regras** que descrevem **quais eventos interessam** e **entrega cada evento aos alvos** certos (Lambda, SQS, SNS, Step Functions, Kinesis, APIs HTTP, outros barramentos e mais de **20 tipos de destinos**). É a **espinha dorsal de arquiteturas orientadas a eventos (EDA)** na AWS: **produtores** e **consumidores** **não se conhecem**, comunicam-se por **eventos** e **evoluem de forma independente**.

O EventBridge evoluiu do **Amazon CloudWatch Events** (e usa a **mesma API** para regras de serviços AWS), e hoje reúne uma **família de recursos**: **Event Bus** (barramentos), **Rules** (regras), **Pipes** (ponto a ponto com filtro e enriquecimento), **Scheduler** (agendamentos), **Schema Registry** (esquemas), **Archive & Replay** (arquivo e reprodução), **API Destinations** (chamar APIs externas) e **Global Endpoints** (failover entre regiões).

**Analogia:** o EventBridge é a **central de despacho de uma cidade**. Eventos chegam de todo lado (um acidente, um alarme, um pedido). A central tem **regras claras** ("se for incêndio na zona sul, acione os bombeiros e a defesa civil"). **Quem gera o evento não sabe quem vai atender**, e **novos órgãos podem ser incluídos** (novas regras) **sem alterar quem reporta**.

## Por que arquitetura orientada a eventos

| Problema (integração ponto a ponto) | Efeito |
|---|---|
| Serviço A **chama diretamente** B, C e D | Cada novo interessado exige **mudar A** |
| **Dependência temporal**: B fora do ar derruba A | Falhas em cascata |
| **Regras de negócio espalhadas** em código de integração | Difícil de entender/auditar |
| **Eventos de infraestrutura** (EC2 parou, build falhou) precisam acionar automações | Scripts e polling |
| **Integração com SaaS** exige conectores caso a caso | Custo e manutenção |
| **Falta de visibilidade** do fluxo de eventos | Depuração difícil |

**Com EventBridge:** produtores **publicam fatos** ("pedido criado"); **regras** decidem **quem reage**; **alvos** executam; **novos consumidores** entram **por configuração**; **eventos são descobertos, versionados (schemas) e reprocessáveis (replay)**.

```
 Produtores                         EVENT BUS                     Regras                     Alvos
 ──────────                   ┌──────────────────┐        ┌─────────────────┐        ──────────────
 Serviços AWS (S3, EC2...) ──►│                  │──────► │ Regra A (padrão)│───────► Lambda
 Suas aplicações (PutEvents)──►│   default /      │──────► │ Regra B (padrão)│───────► Step Functions
 Parceiros SaaS             ──►│   custom /       │──────► │ Regra C (padrão)│───────► SQS / SNS / API
 Outros barramentos/contas  ──►│   partner        │        └─────────────────┘         (até 5 alvos por regra)
                              └──────────────────┘
```

## Conceitos fundamentais

| Conceito | Descrição |
|---|---|
| **Evento (event)** | **Fato imutável** em **JSON** (algo que **aconteceu**): `source`, `detail-type`, `detail`, etc. |
| **Event bus (barramento)** | **Canal** que recebe eventos e os **entrega às regras** |
| **Default event bus** | Barramento **padrão** de cada conta/região, que **recebe eventos de serviços AWS** |
| **Custom event bus** | Barramento **seu**, para **eventos de aplicações** (e isolamento por domínio) |
| **Partner event bus** | Barramento que recebe eventos de **parceiros SaaS** (Zendesk, Datadog, Auth0, Shopify…) |
| **Regra (rule)** | **Padrão de evento** (ou **agendamento**) + **alvos** |
| **Event pattern** | **Filtro JSON** que define **quais eventos casam** |
| **Alvo (target)** | **Destino** do evento (Lambda, SQS, etc.) |
| **Input transformer** | **Reformata** o evento antes de entregar ao alvo |
| **Schema Registry** | **Catálogo de esquemas** de eventos (descoberta automática e geração de código) |
| **Archive / Replay** | **Armazena** eventos e **reenvia** a um barramento |
| **Pipes** | Conexão **ponto a ponto**: fonte → (filtro) → (enriquecimento) → alvo |
| **Scheduler** | **Agendamentos** (cron, rate, único) com alvos, escala e fusos |
| **API destination** | Alvo que chama um **endpoint HTTPS** externo, com **autenticação** e **limite de taxa** |
| **Global endpoint** | **Failover** de ingestão de eventos entre **duas regiões** |

## Anatomia de um evento

```json
{
  "version": "0",
  "id": "6a7e8feb-b491-4cf7-a9f1-bf3703467718",
  "detail-type": "Pedido Criado",
  "source": "com.minhaempresa.pedidos",
  "account": "123456789012",
  "time": "2026-11-09T14:03:21Z",
  "region": "us-east-1",
  "resources": ["arn:aws:dynamodb:us-east-1:123456789012:table/pedidos"],
  "detail": {
    "pedido_id": 999,
    "cliente": {"id": 42, "tipo": "premium"},
    "valor": 4299.9,
    "itens": 3,
    "versao_esquema": 2
  }
}
```

| Campo | Função |
|---|---|
| **`version`** | Versão do envelope (sempre `"0"`) |
| **`id`** | **ID único** do evento (gerado pelo EventBridge) |
| **`detail-type`** | **Tipo** legível do evento ("EC2 Instance State-change Notification") |
| **`source`** | **Origem**: `aws.*` (serviços AWS) ou **seu namespace** (`com.empresa.pedidos`); **não pode começar com `aws.`** em eventos customizados |
| **`account` / `region` / `time`** | Contexto |
| **`resources`** | ARNs de **recursos relacionados** |
| **`detail`** | **Conteúdo livre** (JSON) com os dados do evento |

> [!tip] `source` e `detail-type` são as chaves de roteamento
> A maioria das regras filtra por **`source`** e **`detail-type`** (e depois por campos de **`detail`**). Padronize **nomes** (`com.empresa.dominio`) e **tipos** ("Pedido Criado") para que os **padrões fiquem previsíveis** e **evolutivos**.

## Os três tipos de barramento

| Barramento | O que recebe | Quando usar |
|---|---|---|
| **Default** | Eventos de **serviços AWS** da conta/região (EC2, S3, CodePipeline, GuardDuty, Health, CloudTrail API calls…) | **Reagir a mudanças na infraestrutura** AWS |
| **Custom** | Eventos que **você publica** (`PutEvents`) ou **encaminha** de outros barramentos | **Eventos de negócio**; **isolamento por domínio/ambiente**; **barramento central** multi-conta |
| **Partner** | Eventos de **parceiros SaaS** integrados | Reagir a **eventos de SaaS** (ex.: ticket criado no Zendesk) |

```bash
# Cria um barramento customizado
aws events create-event-bus --name pedidos-bus

# Publica um evento customizado
aws events put-events --entries '[{
  "EventBusName": "pedidos-bus",
  "Source": "com.minhaempresa.pedidos",
  "DetailType": "Pedido Criado",
  "Detail": "{\"pedido_id\":999,\"valor\":4299.9,\"cliente\":{\"tipo\":\"premium\"}}"
}]'

# Cria uma regra que casa com esses eventos e envia a uma fila SQS
aws events put-rule --name pedidos-premium --event-bus-name pedidos-bus \
  --event-pattern '{"source":["com.minhaempresa.pedidos"],"detail-type":["Pedido Criado"],
                    "detail":{"cliente":{"tipo":["premium"]},"valor":[{"numeric":[">",1000]}]}}'
aws events put-targets --rule pedidos-premium --event-bus-name pedidos-bus \
  --targets 'Id=fila-premium,Arn=arn:aws:sqs:us-east-1:123456789012:pedidos-premium'
```

## O fluxo de ponta a ponta

```
 1. Produtor publica o evento (PutEvents) ou um serviço AWS o emite
 2. O barramento recebe e valida (tamanho, formato)
 3. Cada REGRA do barramento avalia o evento contra seu EVENT PATTERN
 4. Para cada regra que CASA: o evento é entregue a TODOS os alvos da regra (em paralelo)
 5. Entrega com política de RETRY (padrão: até 24 h / 185 tentativas) e DLQ opcional por alvo
 6. (Opcional) Archive grava o evento; Replay pode reenviá-lo depois
 7. Métricas (CloudWatch) e logs (CloudTrail) registram o fluxo
```

## Os recursos da família

| Recurso | O que faz | Quando usar |
|---|---|---|
| **Event Bus + Rules** | **Roteamento pub-sub com filtros** | Distribuição de eventos para **vários consumidores** |
| **EventBridge Pipes** | **Fonte → filtro → enriquecimento → alvo** (ponto a ponto, **com buffer**) | Conectar **SQS/Kinesis/DynamoDB Streams/Kafka** a um destino com **transformação**, **sem código de cola** |
| **EventBridge Scheduler** | **Agendamentos** em escala (milhões), **fusos**, **janelas flexíveis**, **uma vez ou recorrente** | **Cron jobs serverless**, lembretes, ações futuras |
| **Schema Registry & Discovery** | **Descobre e registra** esquemas dos eventos; **gera bindings** de código | **Contratos de eventos** e **produtividade** |
| **Archive & Replay** | **Guarda** eventos e **reenvia** | **Recuperação**, **reprocessamento**, **testes** |
| **API Destinations** | **Chama APIs HTTPS** com **auth** (API Key, Basic, OAuth) e **limite de taxa** | **Integrar SaaS/legados** sem Lambda |
| **Global Endpoints** | **Failover** automático entre **duas regiões** | **Alta disponibilidade** de ingestão de eventos |
| **Cross-account / cross-region** | **Encaminhar eventos** entre barramentos | **Hub de eventos** organizacional |

## EventBridge vs SNS vs SQS vs Kinesis vs Step Functions

| Critério | **EventBridge** | **SNS** | **SQS** | **Kinesis Data Streams** | **Step Functions** |
|---|---|---|---|---|---|
| **Papel** | **Roteamento** de eventos por **regras ricas** | **Pub-sub** simples e de alto volume | **Fila** (buffer, ponto a ponto) | **Streaming** ordenado e retido | **Orquestração** de fluxos |
| **Filtro** | **Muito rico** (padrões sobre todo o evento, campos aninhados, wildcards, numéricos…) | Filter policies (atributos/corpo) | Não | — | Choice states |
| **Fontes nativas** | **Serviços AWS (centenas de eventos)**, **SaaS parceiros**, apps | Apps e alguns serviços (alarmes, S3…) | Apps/serviços | Apps/serviços | Eventos/APIs |
| **Alvos** | **20+ tipos** (Lambda, SQS, SNS, SFN, Kinesis, ECS, API HTTP, outros buses…) | SQS, Lambda, HTTP, e-mail, SMS, push, Firehose | Consumidores | Consumidores | Serviços AWS |
| **Throughput** | **Alto** (milhares/s, ajustável); menor que SNS | **Muito alto** (milhões/s) | Muito alto | Alto por shard | — |
| **Latência típica** | Dezenas a centenas de ms | **Menor** (dezenas de ms) | — | ms | — |
| **Retenção/replay** | **Archive & Replay** | Replay (FIFO) | Até 14 dias | Até 365 dias | Histórico de execuções |
| **Schemas/descoberta** | **Sim** | Não | Não | Glue Schema Registry | — |
| **Pessoas (SMS/e-mail/push)** | **Não** (use SNS como alvo) | **Sim** | Não | Não | Via SNS |
| **Ideal para** | **Integração orientada a eventos** entre serviços/SaaS, **reagir a eventos AWS**, **agendamentos** | **Fan-out massivo** e **notificações a pessoas** | **Desacoplar e amortecer** trabalho | **Streams** com vários leitores | **Fluxos com estado** |

```
 Reagir a um evento de serviço AWS (EC2 parou, S3 criou objeto, build falhou) com regras flexíveis?    ─► EventBridge
 Roteamento de eventos de NEGÓCIO por conteúdo, com vários consumidores e evolução independente?      ─► EventBridge (bus customizado)
 Fan-out de altíssimo volume e baixa latência, ou notificar PESSOAS (SMS/e-mail/push)?                  ─► SNS
 Preciso de buffer, retentativas e um trabalhador por tarefa?                                           ─► SQS (EventBridge/SNS → SQS)
 Streaming ordenado, retido, com reprocessamento por vários leitores?                                   ─► Kinesis Data Streams
 Um fluxo com passos, estado, retries e compensações?                                                   ─► Step Functions
 Integrar um SaaS que já emite eventos (Zendesk, Auth0, Datadog)?                                       ─► EventBridge (partner bus)
```

> [!tip] Eles se combinam
> Um padrão comum: **EventBridge** (roteamento) → **SQS** (buffer e escala do consumidor) e **EventBridge** → **SNS** (para **notificar pessoas**). **Não é "um ou outro"**: cada serviço faz o que faz melhor.

## Eventos de serviços AWS

O **barramento padrão** recebe **eventos automáticos** de centenas de serviços:

| Serviço | Exemplos de evento (`detail-type`) |
|---|---|
| **EC2** | "EC2 Instance State-change Notification" (running, stopped, terminated) |
| **S3** | "Object Created", "Object Deleted" (com EventBridge habilitado no bucket) |
| **CodePipeline / CodeBuild** | "CodePipeline Pipeline Execution State Change", "CodeBuild Build State Change" |
| **GuardDuty / Security Hub / Inspector** | "GuardDuty Finding", "Security Hub Findings - Imported" |
| **AWS Health** | "AWS Health Event" (manutenções, incidentes) |
| **CloudTrail** | "AWS API Call via CloudTrail" (**qualquer chamada de API** de gerenciamento) |
| **ECS / EKS / Batch / Glue** | Mudanças de estado de tarefas/jobs |
| **Auto Scaling / RDS / Backup / Config** | Lançamentos, snapshots, mudanças de conformidade |
| **Step Functions** | "Step Functions Execution Status Change" |

```json
{
  "source": ["aws.ec2"],
  "detail-type": ["EC2 Instance State-change Notification"],
  "detail": {"state": ["stopped", "terminated"]}
}
```

> [!tip] CloudTrail + EventBridge = "gatilho para qualquer ação"
> Como o **CloudTrail** publica **chamadas de API** como eventos, é possível reagir a **quase qualquer ação** na conta (criar bucket, alterar security group, `DeleteTrail`…) com **regras** que acionam **alertas e remediações**.

## Modelo de preço (referência)

| Item | Cobrança |
|---|---|
| **Eventos de serviços AWS (barramento padrão)** | **Gratuitos** |
| **Eventos customizados (`PutEvents`)** | **Por milhão** de eventos publicados (cada **64 KB** conta como um evento) |
| **Eventos de parceiros SaaS** | Por milhão |
| **Eventos entre barramentos/contas** | Por milhão de eventos entregues ao outro barramento |
| **Archive** | Por GB processado e armazenado |
| **Replay** | Por evento reenviado |
| **Schema discovery** | Por milhão de eventos ingeridos pela descoberta |
| **API Destinations** | Por milhão de invocações |
| **Pipes** | Por milhão de requisições (após filtro/enriquecimento) |
| **Scheduler** | **Primeiros 14 milhões de invocações/mês grátis** (confirme); depois por milhão |
| **Entrega a alvos** | **Sem custo adicional** do EventBridge (paga-se o alvo: Lambda, SQS…) |

> [!warning] Eventos de serviços AWS são grátis; os seus, não
> Reagir a **eventos AWS** (EC2, S3, GuardDuty) **não custa** pelo EventBridge. Mas **eventos customizados**, **cross-account**, **archive** e **replay** têm custo: **planeje o volume** (e **64 KB por unidade**).

## Limites de referência

| Limite | Valor de referência |
|---|---|
| **Tamanho do evento** | **256 KB** |
| **Eventos por `PutEvents`** | Até **10 entradas** (e 256 KB no total) |
| **Taxa de `PutEvents`** | Milhares/s por região (ajustável) |
| **Regras por barramento** | **300** (ajustável) |
| **Alvos por regra** | **5** |
| **Barramentos por conta/região** | 100 |
| **Tamanho do padrão de evento** | Limite de caracteres (ex.: 2.048) |
| **Retentativa de entrega** | Até **24 horas** e **185 tentativas** (configurável) |
| **Arquivo (retention)** | Indefinida ou por dias |
| **API destinations** | Limite de taxa configurável por destino |
| **Scheduler** | Milhões de agendamentos por conta |

## Casos de uso

| Caso | Como o EventBridge ajuda |
|---|---|
| **Automação de operações** | "Instância parou" → Lambda/SSM reinicia; "Security Group alterado" → alerta/remedia |
| **Integração de microsserviços (coreografia)** | Eventos de domínio roteados a serviços interessados |
| **Segurança e conformidade** | GuardDuty/Config/CloudTrail → Step Functions/SNS/ticket |
| **Pipelines de CI/CD** | Eventos do CodePipeline/CodeBuild → notificações |
| **Integração com SaaS** | Eventos de parceiros → fluxos internos; API Destinations para chamar SaaS |
| **Agendamentos serverless** | Scheduler substitui cron em servidores |
| **Fan-out multi-conta** | Hub central coleta eventos de todas as contas |
| **Replay e testes** | Reprocessar eventos de um período |
| **Event sourcing leve** | Archive como registro de fatos (com limites) |
| **Streams → ações** | Pipes ligam DynamoDB Streams/Kinesis/SQS a alvos |

## Exemplo prático: reagir a eventos e coordenar serviços

1. O serviço de pedidos publica **"Pedido Criado"** no **barramento `pedidos-bus`** (`PutEvents`), com `detail` contendo `valor`, `cliente.tipo` e `versao_esquema`.
2. **Regra 1** (padrão: `cliente.tipo = premium` e `valor > 1000`) → **Step Functions** (análise de risco).
3. **Regra 2** (todos os pedidos) → **SQS `faturamento`** (buffer) com **DLQ**.
4. **Regra 3** (todos) → **Firehose** (arquivo em S3) para analytics.
5. **Regra 4** (`valor > 10000`) → **SNS** (alerta ao gerente por SMS/e-mail).
6. **Regra 5** (Archive) guarda 30 dias de eventos para **replay** em caso de bug.
7. O **barramento padrão** reage a eventos AWS: "GuardDuty Finding (high)" → **SNS + ticket**; "EC2 terminated" → **auditoria**.
8. **Alarmes** em `FailedInvocations` e nas **DLQs** dos alvos.

## Erros comuns e armadilhas

- **Tratar EventBridge como SNS** (esperando throughput e latência idênticos).
- **Esquecer a permissão do alvo** (política de recurso/role) e achar que "o evento não chegou".
- **Padrões de evento que não casam** (caminho do campo errado, tipo de dado errado).
- **Sem DLQ nos alvos** críticos, perdendo eventos após as retentativas.
- **Eventos gigantes** (acima de 256 KB) em vez de referências.
- **Misturar tudo no barramento padrão** (sem barramentos customizados por domínio).
- **Dependência de ordem**: o EventBridge **não garante ordem** nem **exatamente uma vez**.
- **Esquecer que cada alvo recebe uma cópia** (idempotência nos consumidores).

## 🧩 Quiz de Fixação

1. Quais são os três tipos de barramento do EventBridge?
2. O que define quais eventos uma regra captura?
3. Quantos alvos pode ter uma regra?
4. Qual a diferença essencial entre EventBridge e SNS?
5. O que é o EventBridge Scheduler?
6. Eventos de serviços AWS no barramento padrão são cobrados?

**Respostas:**
1) Default (eventos de serviços AWS), custom (eventos de suas aplicações) e partner (eventos de parceiros SaaS).
2) O event pattern, um filtro JSON sobre campos do evento (source, detail-type, detail, etc.).
3) Até 5 alvos por regra (limite padrão de referência).
4) O EventBridge é um barramento de roteamento por regras ricas, com fontes nativas de serviços AWS e SaaS, schemas e replay; o SNS é pub-sub simples de altíssimo volume e baixa latência, que também alcança pessoas (SMS, e-mail, push).
5) O serviço de agendamentos serverless do EventBridge (cron, rate, execução única), com fusos, janelas flexíveis e escala de milhões de agendamentos.
6) Não; os eventos de serviços AWS no barramento padrão são gratuitos, enquanto eventos customizados, entre barramentos, archive e replay têm custo.
