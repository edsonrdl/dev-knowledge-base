### Tópicos e mensagens no SNS — criação, assinaturas e confirmação, atributos, raw message delivery, estrutura por protocolo, publicação em lote e mensagens grandes

> [!warning] Aviso
> Formatos de mensagem, limites de tamanho e de lote, comportamento de confirmação e propriedades de tópico mudam. Os exemplos aqui são referências de estudo; confirme na documentação. Os comandos e códigos **não foram executados**.

Entender o **tópico** e a **mensagem** do SNS em detalhe é o que separa **integrações que funcionam** de **integrações que "quase funcionam"**: consumidores que **não conseguem ler o corpo** porque estava **dentro de um envelope**, assinaturas **pendentes de confirmação**, atributos que **não chegam**, mensagens **maiores que o limite** e **formatos diferentes por protocolo** que ninguém previu. Esta folha cobre o **ciclo de vida do tópico e da assinatura**, a **anatomia da mensagem**, os **atributos**, o **raw message delivery**, a **estrutura por protocolo (`MessageStructure: json`)**, a **publicação em lote** e a **estratégia para payloads grandes**.

**Analogia:** o tópico é uma **lista de distribuição**. Para **entrar na lista** (assinatura), o destinatário às vezes precisa **confirmar** ("clique para confirmar"). Cada **carta** (mensagem) pode ir **com um envelope** (formato padrão do SNS) ou **sem envelope** (raw), e pode ter **etiquetas** (atributos) que ajudam a **filtrar** quem recebe o quê. Cartas **muito grandes** vão **por malote separado** (S3), e a lista só leva **o recibo**.

## Tópicos

### Criação e propriedades

```bash
aws sns create-topic --name pedido-criado \
  --attributes '{
    "DisplayName":"Pedidos",
    "KmsMasterKeyId":"alias/sns-pedidos",
    "Policy":"{...}",
    "DeliveryPolicy":"{...}"
  }' \
  --tags Key=projeto,Value=loja Key=ambiente,Value=prod

aws sns get-topic-attributes --topic-arn arn:aws:sns:us-east-1:123456789012:pedido-criado
aws sns list-topics
aws sns delete-topic --topic-arn arn:aws:sns:us-east-1:123456789012:pedido-criado
```

| Atributo do tópico | Função |
|---|---|
| **`TopicArn`** | Identificador (`arn:aws:sns:região:conta:nome`) |
| **`DisplayName`** | Nome exibido (prefixo em SMS/e-mail) |
| **`Policy`** | **Política de acesso** do tópico (quem publica/assina) |
| **`DeliveryPolicy`** | **Retentativas** padrão para HTTP/S |
| **`KmsMasterKeyId`** | **Criptografia SSE-KMS** |
| **`FifoTopic`** / **`ContentBasedDeduplication`** | Tópico FIFO e dedup por conteúdo |
| **`SubscriptionsConfirmed/Pending/Deleted`** | Contagens |
| **`EffectiveDeliveryPolicy`** | Política efetiva após combinação |
| **`TracingConfig`** | **X-Ray** (`Active`) |
| **`SignatureVersion`** | Versão da assinatura das mensagens (1 SHA1 / 2 SHA256) |
| **`ArchivePolicy`** | (FIFO) **Arquivamento** de mensagens para replay |

| Boa prática | Motivo |
|---|---|
| **Um tópico por tipo de evento/domínio** (`pedido-criado`, `pagamento-aprovado`) | Clareza e filtros simples |
| **Evitar "tópico para tudo"** | Filtros complexos, acoplamento |
| **Evitar milhares de tópicos "por usuário"** | Use **filter policies** ou **push por endpoint** |
| **Nomes padronizados** e **tags** | Governança |
| **Criar via IaC** | Reprodutibilidade |
| **Mudar o nome recria o tópico** | Cuidado com deploys |

## Assinaturas

### Ciclo de vida

```
 Subscribe ──► [PendingConfirmation] ──(confirmação)──► [Confirmed]  ──► recebe mensagens
                    │ (e-mail, HTTP/S, SMS opt-in)                         │
                    └─ não confirmada em 3 dias → expira                  └─ Unsubscribe → [Deleted]
 (SQS, Lambda, Firehose na MESMA conta: confirmação automática quando as permissões estão corretas)
```

| Protocolo | Confirmação |
|---|---|
| **SQS** (mesma conta) | **Automática** (com permissão adequada na fila) |
| **SQS** (outra conta) | **Manual** (aceitar com a assinatura/política) |
| **Lambda** | **Automática** (a assinatura exige permissão de invocação) |
| **E-mail / e-mail-JSON** | **Manual**: o destinatário **clica** no link do e-mail |
| **HTTP / HTTPS** | **Manual**: o endpoint recebe `SubscriptionConfirmation` com `SubscribeURL`/`Token` e **deve confirmar** |
| **SMS** | Opt-in conforme regras do país; **resposta STOP/opt-out** |
| **Push (application)** | Via **registro de endpoint** de dispositivo |
| **Firehose** | **Automática** (com role de assinatura) |

```bash
# Assina e acompanha o estado
aws sns subscribe --topic-arn $TOPIC --protocol https \
  --notification-endpoint https://api.parceiro.com/webhooks/sns \
  --return-subscription-arn

aws sns list-subscriptions-by-topic --topic-arn $TOPIC \
  --query 'Subscriptions[].[Protocol,Endpoint,SubscriptionArn]' --output table

# Confirmar manualmente (HTTP/S): usar o token recebido
aws sns confirm-subscription --topic-arn $TOPIC --token <token>
```

> [!warning] "PendingConfirmation" significa que NADA é entregue
> Assinaturas por **e-mail** e **HTTP/S** só recebem mensagens **depois de confirmadas**. Se o destinatário **ignora o e-mail** ou o **endpoint não processa a requisição de confirmação**, o status fica **`PendingConfirmation`** (e expira). É a causa mais comum de "**o SNS não está entregando**".

### Atributos da assinatura

| Atributo | Função |
|---|---|
| **`RawMessageDelivery`** | Entrega **só o corpo original** (sem envelope SNS) para SQS/HTTP/S/Firehose |
| **`FilterPolicy`** + **`FilterPolicyScope`** | **Filtro** por atributos ou corpo (`MessageAttributes`/`MessageBody`) |
| **`RedrivePolicy`** | **DLQ da assinatura** (fila SQS para falhas de entrega) |
| **`DeliveryPolicy`** | **Retentativas** específicas da assinatura (HTTP/S) |
| **`SubscriptionRoleArn`** | Role para entrega ao **Firehose** |
| **`ConfirmationWasAuthenticated`** | Se a confirmação foi autenticada |
| **`PendingConfirmation`** | `true`/`false` |
| **`ReplayPolicy`** | (FIFO) **Replay** de mensagens arquivadas |

```bash
aws sns set-subscription-attributes --subscription-arn <arn> \
  --attribute-name RawMessageDelivery --attribute-value true

aws sns set-subscription-attributes --subscription-arn <arn> \
  --attribute-name RedrivePolicy \
  --attribute-value '{"deadLetterTargetArn":"arn:aws:sqs:us-east-1:123456789012:estoque-sns-dlq"}'
```

## A mensagem

| Elemento | Detalhe |
|---|---|
| **`Message`** | Corpo (texto/JSON/XML, **UTF-8**); **até 256 KB** (incluindo atributos) |
| **`Subject`** | Assunto (e-mail e alguns protocolos); até 100 caracteres |
| **`MessageAttributes`** | Até **10** atributos tipados (`String`, `String.Array`, `Number`, `Binary`) |
| **`MessageStructure`** | `json` para **mensagens diferentes por protocolo** |
| **`MessageGroupId` / `MessageDeduplicationId`** | (FIFO) |
| **`PhoneNumber` / `TargetArn`** | Publicação **direta** para um número SMS ou endpoint de push |
| **Tamanho para cobrança** | **64 KB por unidade** |

### Atributos de mensagem

| Tipo (`DataType`) | Exemplo | Uso em filtros |
|---|---|---|
| **`String`** | `pedido.criado` | Igualdade, prefixo, sufixo, `anything-but` |
| **`String.Array`** | `["eletronicos","promocao"]` | **Qualquer valor** do array casa |
| **`Number`** | `199.90` | Operadores **numéricos** (`>`, `<`, `between`) |
| **`Binary`** | bytes | Pouco usado em filtros |

```python
import boto3, json
sns = boto3.client("sns")

sns.publish(
    TopicArn="arn:aws:sns:us-east-1:123456789012:pedido-criado",
    Message=json.dumps({"pedido_id": 999, "valor": 4299.9, "itens": 3}),
    Subject="Pedido criado",
    MessageAttributes={
        "tipo":     {"DataType": "String", "StringValue": "pedido.criado"},
        "valor":    {"DataType": "Number", "StringValue": "4299.9"},
        "categorias": {"DataType": "String.Array", "StringValue": json.dumps(["eletronicos", "premium"])},
        "regiao":   {"DataType": "String", "StringValue": "sul"},
    },
)
```

> [!tip] Atributos para filtrar, corpo para dados
> Coloque no **atributo** apenas o que **ajuda a decidir quem recebe** (tipo, região, faixa, versão). O **resto** vai no **corpo**. Atributos demais **encarecem** (contam no tamanho) e **confundem** o contrato. Com **filtro por corpo** (`MessageBody`), é possível filtrar por campos do JSON **sem duplicá-los** em atributos.

## Formato da entrega e raw message delivery

### Envelope padrão do SNS (para SQS, HTTP/S, e-mail-JSON)

```json
{
  "Type": "Notification",
  "MessageId": "...",
  "TopicArn": "arn:aws:sns:us-east-1:123456789012:pedido-criado",
  "Subject": "Pedido criado",
  "Message": "{\"pedido_id\":999,\"valor\":4299.9}",     // <-- STRING JSON dentro do JSON
  "Timestamp": "2026-11-09T14:03:21.000Z",
  "Signature": "...", "SigningCertURL": "...", "UnsubscribeURL": "...",
  "MessageAttributes": {"tipo": {"Type": "String", "Value": "pedido.criado"}}
}
```

O consumidor precisa **desserializar duas vezes**: o **envelope**, e depois o campo **`Message`** (que é **uma string** contendo o JSON).

### `RawMessageDelivery`

| Aspecto | **Envelope (padrão)** | **Raw message delivery** |
|---|---|---|
| **Corpo recebido** | JSON **com envelope** e metadados | **Somente a mensagem original** |
| **Atributos** | Dentro do envelope (`MessageAttributes`) | Mapeados para **atributos de mensagem do SQS** (ou cabeçalhos HTTP) |
| **Assinatura/validação** | **Sim** (`Signature`) | **Não** (HTTP/S perde a assinatura no corpo; use cabeçalhos/segurança de transporte) |
| **Simplicidade do consumidor** | Menor | **Maior** (mesmo formato que o publicador enviou) |
| **Metadados SNS (TopicArn, MessageId)** | Presentes | **Ausentes** (em SQS há `MessageId` próprio) |
| **Quando usar** | Precisa de **TopicArn/Subject/assinatura**, ou **múltiplos tópicos** na mesma fila | **Um tópico por fila**, e o consumidor **só quer o corpo** |

> [!warning] Raw e assinaturas de HTTP/S
> Em **HTTP/S**, o **envelope** inclui a **assinatura** que você **valida** para garantir a **autenticidade**. Com **raw delivery**, essa validação **no corpo** deixa de existir: use **segredos no cabeçalho/URL**, **mTLS** ou **IP allow-list** (e avalie se a perda é aceitável).

> [!tip] SQS + raw = consumidor mais simples
> Para **SNS → SQS** com **um tópico por fila**, **habilite raw delivery**: o consumidor lê **exatamente o JSON** que o publicador mandou, e os **atributos** aparecem como **message attributes do SQS**.

## Mensagens diferentes por protocolo (`MessageStructure: json`)

Você pode enviar **conteúdos diferentes** para **cada protocolo** em **uma única publicação**: por exemplo, **texto curto para SMS**, **HTML para e-mail** e **JSON estruturado para filas**.

```python
sns.publish(
    TopicArn=TOPIC,
    MessageStructure="json",
    Message=json.dumps({
        "default": "Pedido 999 criado",                                   # obrigatório
        "sms":     "Seu pedido 999 foi recebido. Obrigado!",
        "email":   "Olá! Seu pedido 999 foi recebido e será enviado em breve.\n\nEquipe Loja",
        "sqs":     json.dumps({"pedido_id": 999, "valor": 4299.9}),
        "lambda":  json.dumps({"pedido_id": 999, "origem": "checkout"}),
        "GCM":     json.dumps({"fcmV1Message": {"message": {"notification": {"title": "Pedido recebido", "body": "#999"}}}}),
        "APNS":    json.dumps({"aps": {"alert": "Pedido recebido", "sound": "default"}}),
    }),
)
```

| Chave | Protocolo |
|---|---|
| **`default`** | **Obrigatória**: usada quando não há chave específica |
| **`sqs`, `lambda`, `http`, `https`, `email`, `email-json`, `sms`, `firehose`** | Conteúdo por protocolo |
| **`APNS`, `APNS_SANDBOX`, `GCM`, `ADM`, `BAIDU`, `WNS`, …** | **Push móvel** por plataforma |

## Publicação em lote e direta

### `PublishBatch`

```python
resp = sns.publish_batch(
    TopicArn=TOPIC,
    PublishBatchRequestEntries=[
        {"Id": str(i), "Message": json.dumps({"pedido_id": i}),
         "MessageAttributes": {"tipo": {"DataType": "String", "StringValue": "pedido.criado"}}}
        for i in range(10)                      # até 10 mensagens por lote
    ],
)
for falha in resp.get("Failed", []):
    print("falhou:", falha["Id"], falha["Code"], falha["Message"])
```

| Aspecto | Detalhe |
|---|---|
| **Tamanho do lote** | Até **10 mensagens**; **payload total ≤ 256 KB** |
| **Cobrança** | Cada **64 KB** do lote conta como requisição; **economiza** em relação a publicações individuais |
| **Falhas parciais** | Verifique **`Failed`** e **reenvie** |
| **FIFO** | Exige `MessageGroupId` (e dedup) por entrada |

### Publicação direta (sem tópico)

| Alvo | Uso |
|---|---|
| **`PhoneNumber`** | Envia **SMS** a um número (sem assinatura) |
| **`TargetArn`** | Envia **push** para **um endpoint de dispositivo** específico |
| **Observação** | Não é fan-out; útil para **mensagens individualizadas** (OTP, notificação pessoal) |

## Mensagens grandes

| Estratégia | Detalhe |
|---|---|
| **Limite** | **256 KB** (corpo + atributos) |
| **Claim check** | Guardar o payload no **S3** e publicar a **referência** (`bucket`, `chave`, `versão`) |
| **SNS Extended Client Library** (Java) | Faz upload ao S3 e publica o **ponteiro** automaticamente (e o assinante busca) |
| **Compactação** | **Gzip** + Base64 (cuidado: aumenta ~33% em Base64) |
| **Reduzir o conteúdo** | Enviar **IDs/deltas** em vez do objeto completo |
| **Consumidores** | Precisam de **acesso ao S3** (IAM/KMS) |

```json
{
  "tipo": "relatorio.gerado",
  "arquivo": {"bucket": "meu-bucket-relatorios", "chave": "2026/11/09/relatorio-999.parquet",
              "versao": "3Lg9...", "tamanho": 52428800},
  "gerado_em": "2026-11-09T14:03:21Z"
}
```

> [!tip] Mensagens pequenas e autossuficientes
> Prefira mensagens **curtas** com **identificadores** e os **campos necessários para decidir** (tipo, versão, tenant). Quem precisar do **objeto completo** o busca na **fonte da verdade**: evita **dados desatualizados** e **excesso de payload**.

## Versionamento de contratos de mensagem

| Prática | Motivo |
|---|---|
| **Campo `versao`** no atributo e no corpo | Consumidores tratam versões |
| **Evolução compatível** (adicionar campos opcionais; não remover/renomear) | Evita quebrar assinantes |
| **Novo tópico/tipo para mudanças incompatíveis** | Migração gradual |
| **Esquemas documentados** (JSON Schema/Glue Schema Registry/EventBridge Schema Registry) | Contrato explícito |
| **Testes de contrato** (publicador × assinantes) | Detecta quebras no CI |
| **Atributo `tipo` padronizado** (`dominio.entidade.evento`) | Filtros e roteamento |

## Exemplo prático: tópico de pedidos bem estruturado

1. Tópico **`pedido-criado`** (Standard, SSE-KMS), tags `projeto=loja`, `ambiente=prod`.
2. O produtor publica com **atributos**: `tipo=pedido.criado`, `versao=2`, `valor` (Number), `regiao`, e **corpo JSON** com o pedido essencial (IDs e campos de decisão).
3. Assinaturas **SQS** (estoque, faturamento) com **`RawMessageDelivery=true`**, **DLQ** e **`RedrivePolicy`**.
4. Uma assinatura **HTTPS** (parceiro) mantém o **envelope** (para validar a **assinatura** do SNS) e usa **filter policy** por `valor > 1000`.
5. Uma assinatura **Firehose** arquiva tudo em S3.
6. **E-mails** de gerentes ficam em **outro tópico** de alertas, com `MessageStructure: json` para formatar o texto.
7. Um **teste de contrato** no CI valida o formato publicado contra os esquemas dos assinantes.

## Troubleshooting

| Sintoma | Causa provável | Como resolver |
|---|---|---|
| **Assinatura em `PendingConfirmation`** | E-mail/HTTP não confirmado | Confirmar; verificar o handler do endpoint |
| **Nada chega à fila SQS** | **Queue policy** não permite o SNS (ou KMS) | Adicionar `Principal: sns.amazonaws.com` + `aws:SourceArn` |
| **Consumidor não consegue ler o corpo** | Envelope SNS (string dentro do JSON) | Desserializar o envelope ou usar **raw delivery** |
| **Atributos não aparecem** | Raw delivery mapeia para atributos SQS; ou não foram enviados | Conferir `message-attribute-names` no `ReceiveMessage` |
| **`InvalidParameter: Message too long`** | > 256 KB | Claim check no S3 |
| **`InvalidParameter: MessageStructure`** | Falta `default` ou JSON inválido | Incluir `default`; validar JSON |
| **HTTP/S não recebe** | Endpoint inacessível/sem confirmar; TLS inválido | Verificar certificado, firewall, resposta 2xx |
| **Lambda não é invocada** | Falta permissão (`lambda:InvokeFunction` do SNS) | `add-permission` na função |
| **SMS não entregue** | Opt-out, país, limites, sandbox | Ver status de entrega; regras do país |
| **Duplicatas** | At-least-once | Idempotência nos assinantes |
| **Falhas parciais em `PublishBatch`** | Entradas inválidas | Reenviar as falhas |
| **Tópico FIFO recusa publicação** | Sem `MessageGroupId`/dedup | Informar os parâmetros |

## Erros comuns e armadilhas

- **Não confirmar assinaturas** de e-mail/HTTP e achar que "o SNS falha".
- **Consumidor que não trata o envelope** (ou não usa raw).
- **Tópico único para todos os eventos** sem padrão de atributos.
- **Enviar objetos grandes** em vez de referências.
- **Esquecer a queue policy** e a política de KMS ao ligar SNS a SQS.
- **Usar raw delivery em HTTP/S** e perder a validação de assinatura sem compensar.
- **Mudar contratos** de mensagem sem versão e quebrar assinantes.
- **Ignorar `Failed`** em `PublishBatch`.

5. Quais tipos de dados de atributo o SNS suporta?

**Respostas:**
1) Entrega apenas o corpo original da mensagem (sem o envelope JSON do SNS), mapeando atributos para atributos do SQS ou cabeçalhos HTTP.
2) Porque o destinatário ainda não clicou no link de confirmação enviado por e-mail; enquanto pendente, nada é entregue.
3) Enviar conteúdos diferentes para cada protocolo (SMS, e-mail, SQS, push) em uma única publicação, com a chave default obrigatória.
4) 256 KB (incluindo atributos); contorna-se guardando o payload no S3 e publicando uma referência (claim check), manualmente ou com a Extended Client Library.
5) String, String.Array, Number e Binary.
6) Para que o consumidor receba exatamente o JSON enviado pelo publicador, sem desserializar o envelope, com atributos como message attributes do SQS.
