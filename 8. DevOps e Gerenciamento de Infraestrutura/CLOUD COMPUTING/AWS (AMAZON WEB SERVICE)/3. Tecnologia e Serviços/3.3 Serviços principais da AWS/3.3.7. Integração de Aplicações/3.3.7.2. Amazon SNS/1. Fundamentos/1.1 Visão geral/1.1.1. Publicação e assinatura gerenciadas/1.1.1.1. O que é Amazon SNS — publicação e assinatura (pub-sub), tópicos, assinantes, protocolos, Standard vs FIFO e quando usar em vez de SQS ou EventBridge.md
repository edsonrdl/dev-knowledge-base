### O que é Amazon SNS — publicação e assinatura (pub-sub), tópicos, assinantes, protocolos, Standard vs FIFO e quando usar em vez de SQS ou EventBridge

> [!warning] Aviso
> Protocolos suportados, limites (tamanho de mensagem, assinaturas por tópico, taxas de publicação), preços e recursos do SNS mudam. Os números aqui são referências de estudo; confirme na documentação oficial. Os comandos e códigos são exemplos e **não foram executados**.

O **Amazon Simple Notification Service (SNS)** é o serviço **gerenciado de publicação e assinatura (pub-sub)** da AWS. Um **publicador** envia **uma mensagem a um tópico**, e o SNS **entrega uma cópia a cada assinante** do tópico, **imediatamente** e **em paralelo**, por **vários protocolos**: filas **SQS**, funções **Lambda**, endpoints **HTTP/HTTPS**, **e-mail**, **SMS** e **notificações push** para celulares, além do **Firehose**. É o mecanismo de **fan-out** (um para muitos) e de **notificação** da AWS, **sem servidores para operar**, com **alta disponibilidade** e **escala praticamente ilimitada**.

Existem **duas faces** do SNS: **A2A (application-to-application)**, que conecta **sistemas** (SQS, Lambda, HTTP, Firehose), e **A2P (application-to-person)**, que alcança **pessoas** (SMS, e-mail, push móvel).

**Analogia:** o SNS é uma **rádio com várias frequências**. A emissora (**publicador**) transmite **uma vez** em um canal (**tópico**); **todos os receptores sintonizados** (**assinantes**) recebem **na mesma hora**: o sistema de estoque, o de faturamento, o app no celular do cliente, o e-mail do gerente. A emissora **não precisa saber quem está ouvindo** nem **quantos são**.

## O problema que o SNS resolve

| Problema (acoplamento ponto a ponto) | Efeito |
|---|---|
| O serviço de pedidos **chama diretamente** estoque, faturamento, e-mail e analytics | Cada novo interessado exige **mudar o publicador** |
| Um destinatário **lento ou fora** | **Atrasa ou derruba** quem publica |
| Notificar pessoas por **SMS/e-mail/push** exige integrar vários provedores | Complexidade e manutenção |
| Alarmes e eventos precisam chegar a **vários lugares** | Código repetido |
| Difícil **adicionar/remover** consumidores | Deploys arriscados |

**Com SNS:** o publicador **conhece só o tópico**; **assinantes entram e saem** **sem tocar no publicador**; cada assinante recebe **sua cópia** com **retentativas e DLQ próprias**; o mesmo evento pode **acionar sistemas e avisar pessoas**.

```
 SEM SNS:   Pedidos ─► Estoque
                    ─► Faturamento       (Pedidos conhece e chama cada um)
                    ─► E-mail
                    ─► Analytics

 COM SNS:   Pedidos ─► [TÓPICO pedido.criado] ─┬─► SQS "estoque"
                                                ├─► Lambda "faturamento"
                                                ├─► Firehose ─► S3 (analytics)
                                                ├─► HTTPS (parceiro externo)
                                                └─► E-mail / SMS / push (pessoas)
```

## Conceitos fundamentais

| Conceito | Descrição |
|---|---|
| **Tópico (topic)** | **Canal lógico** de comunicação; tem **ARN** e **política de acesso** |
| **Publicador (publisher)** | Quem **envia** mensagens ao tópico (`Publish`) |
| **Assinante (subscriber/endpoint)** | Destino que **recebe** as mensagens |
| **Assinatura (subscription)** | **Vínculo** entre tópico e endpoint, com **protocolo**, **filter policy** e configurações |
| **Protocolo** | Como entregar: `sqs`, `lambda`, `http`, `https`, `email`, `email-json`, `sms`, `application` (push), `firehose` |
| **Mensagem** | Corpo (texto/JSON, até **256 KB**) + **atributos de mensagem** |
| **Message ID** | Identificador único da publicação |
| **Filter policy** | Regra que define **quais mensagens** cada assinante recebe |
| **Delivery policy / retry** | Política de **retentativas** por protocolo |
| **DLQ da assinatura** | **Fila SQS** para mensagens que **não foram entregues** |
| **Tópico Standard vs FIFO** | Tipos de tópico com **garantias diferentes** |
| **Platform application** | Configuração de **push móvel** (APNs, FCM…) |

### Publicar e assinar em um comando

```bash
# Cria o tópico
aws sns create-topic --name pedido-criado
TOPIC=arn:aws:sns:us-east-1:123456789012:pedido-criado

# Assina uma fila SQS, um e-mail e uma função Lambda
aws sns subscribe --topic-arn $TOPIC --protocol sqs \
  --notification-endpoint arn:aws:sqs:us-east-1:123456789012:estoque
aws sns subscribe --topic-arn $TOPIC --protocol email --notification-endpoint gerente@empresa.com
aws sns subscribe --topic-arn $TOPIC --protocol lambda \
  --notification-endpoint arn:aws:lambda:us-east-1:123456789012:function:faturamento

# Publica uma mensagem com atributos
aws sns publish --topic-arn $TOPIC \
  --message '{"pedido_id":999,"valor":42.5}' \
  --message-attributes '{"tipo":{"DataType":"String","StringValue":"pedido.criado"}}'
```

## Protocolos de entrega

| Protocolo | Tipo | Como funciona | Observações |
|---|---|---|---|
| **Amazon SQS** | A2A | Entrega **na fila** (padrão **SNS + SQS**) | **Mais usado**; buffer, retentativa, escala |
| **AWS Lambda** | A2A | **Invoca** a função com o evento SNS | Execução **assíncrona** |
| **HTTP / HTTPS** | A2A | **POST** no endpoint (webhook) | Exige **confirmação de assinatura** e validação de **assinatura** |
| **Amazon Data Firehose** | A2A | Entrega a **S3, Redshift, OpenSearch…** | Arquivar **todos** os eventos |
| **E-mail / E-mail-JSON** | A2P | Envia e-mail (texto ou JSON) | Exige **confirmação** do destinatário; volume baixo |
| **SMS** | A2P | Mensagem de texto a celulares | **Custo por mensagem**; regras por país |
| **Push móvel (Application)** | A2P | Notificações para apps (APNs, FCM, ADM, Baidu, WNS…) | Requer **platform application** e **tokens** de dispositivo |

> [!tip] Padrão de ouro: SNS + SQS
> Para integrar **sistemas**, prefira **assinar filas SQS** em vez de chamar **HTTP/Lambda direto**: a **fila** dá **buffer**, **retentativas controláveis** e **isolamento** de cada consumidor. O SNS faz o **fan-out**; o SQS dá a **resiliência**.

## Tópicos Standard vs FIFO

| Característica | **Standard** | **FIFO** |
|---|---|---|
| **Throughput** | **Praticamente ilimitado** (milhões/s por tópico em escala) | Limitado (por tópico, com grupos de mensagem; confirme) |
| **Ordem** | **Melhor esforço** | **Estrita por `MessageGroupId`** |
| **Duplicatas** | **Possíveis** (*at-least-once*) | **Deduplicação** (janela de 5 min) |
| **Protocolos de assinatura** | **Todos** (SQS, Lambda, HTTP/S, e-mail, SMS, push, Firehose) | **SQS (FIFO e Standard)** e outros limitados (Lambda/HTTP/Firehose em alguns casos, confirme) |
| **Nome** | Qualquer | **Termina em `.fifo`** |
| **Recursos extras** | Filtros, DLQ, SSE | Filtros, DLQ, SSE, **arquivamento e replay** de mensagens |
| **Quando usar** | **Maioria**: notificações, fan-out | **Ordem e dedup** por entidade (com SQS FIFO) |

```
 Tópico FIFO "contas.fifo" + filas SQS FIFO assinantes:
   Produtor (MessageGroupId = conta-123) ─► SNS FIFO ─► SQS FIFO A, SQS FIFO B  (ordem por conta preservada em ambos)
```

## Modelo de preço (referência)

| Item | Cobrança |
|---|---|
| **Publicações (requisições)** | **Por milhão** de publicações (primeiro milhão grátis/mês, confirme); cada **64 KB** de payload conta como **uma requisição** |
| **Entregas a SQS/Lambda/Firehose** | **Sem custo adicional** de entrega (cobra-se a publicação) |
| **Entregas HTTP/S** | Por milhão de entregas |
| **E-mail** | Por 100 mil mensagens (primeiros 1.000 grátis, confirme) |
| **SMS** | **Por mensagem**, variável por **país/operadora** |
| **Push móvel** | Por milhão de notificações (primeiro milhão grátis, confirme) |
| **Tópicos FIFO** | Preço por requisição **maior** que Standard; custos de **arquivamento** |
| **Transferência de dados** | Saída para Internet/entre regiões |
| **SSE-KMS** | Requisições ao KMS |

> [!warning] SMS é o item que mais surpreende na fatura
> Cada SMS tem **custo por país** (centavos a dezenas de centavos). Um **loop de notificações** ou **fraude de pumping de SMS** pode gerar **contas enormes** rapidamente. Configure **limite mensal de gasto**, **validações** e **alarmes**.

## Limites de referência

| Limite | Valor de referência |
|---|---|
| **Tamanho da mensagem** | **256 KB** (acima: **claim check** com S3; Extended Client) |
| **Tópicos por conta/região** | Até **100.000** (Standard) / **1.000** (FIFO) (ajustável) |
| **Assinaturas por tópico** | Até **12,5 milhões** (Standard) / **100** (FIFO)* |
| **Assinaturas por conta** | Até **~ 25 milhões** |
| **Filter policy** | Limites de tamanho, nº de atributos e valores |
| **Atributos de mensagem** | Até **10** por mensagem |
| **Publicação em lote (`PublishBatch`)** | Até **10 mensagens** por requisição |
| **Taxa de publicação** | Por tópico/região, com cotas (Standard muito alta) |
| **Retenção para entrega** | Conforme política de retentativa (horas a dias, por protocolo) |

\* Valores ilustrativos; os limites variam com a evolução do serviço e a região. Confirme em Service Quotas.

## SNS vs SQS vs EventBridge vs Kinesis vs Amazon MQ

| Critério | **SNS** | **SQS** | **EventBridge** | **Kinesis Data Streams** | **Amazon MQ** |
|---|---|---|---|---|---|
| **Modelo** | **Pub-sub (push)**, fan-out | **Fila (pull)**, ponto a ponto | **Barramento de eventos** com regras | **Stream** retido | **Brokers** (AMQP, MQTT…) |
| **Entrega** | **Push** a todos os assinantes | **Pull** pelo consumidor | **Push** para alvos | Pull/push (EFO) | Protocolos padrão |
| **Retenção** | **Não retém** (reentrega por política limitada) | **Até 14 dias** | Arquivo/replay | **Até 365 dias** | Conforme broker |
| **Múltiplos consumidores** | **Sim** (todos recebem) | **Não** (um consumidor por mensagem) | **Sim** | **Sim** | Tópicos/filas |
| **Filtragem** | **Filter policies** (atributos/corpo) | Não nativa | **Padrões de evento** ricos | — | Seletores |
| **Alcança pessoas (SMS/e-mail/push)** | **Sim** | Não | Não (via SNS) | Não | Não |
| **Alvos** | SQS, Lambda, HTTP, Firehose, SMS, e-mail, push | Consumidores | **Mais de 20 serviços AWS**, SaaS, API destinations | Consumidores | Aplicações |
| **Esquema/registro, replay** | Replay (FIFO) | — | **Schema registry**, **archive/replay** | Releitura | — |
| **Ideal para** | **Notificar muitos** e **fan-out** simples | **Desacoplar e amortecer** trabalho | **Integração orientada a eventos** entre serviços/SaaS | **Streaming** | **Migração** JMS/AMQP |

```
 Preciso que VÁRIOS sistemas recebam o mesmo evento (e/ou pessoas por SMS/e-mail/push)?   ─► SNS
 Preciso de buffer, retentativa e UM trabalhador por tarefa?                              ─► SQS (e SNS + SQS para ambos)
 Preciso rotear eventos por regras ricas entre serviços AWS e SaaS, com schemas?           ─► EventBridge
 Preciso de fluxo ordenado, retido, com reprocessamento e vários leitores?                 ─► Kinesis Data Streams
```

### SNS ou EventBridge?

| Situação | Escolha | Motivo |
|---|---|---|
| **Fan-out simples e de altíssimo volume** (milhões/s) | **SNS** | Throughput e latência |
| **Notificar pessoas** (SMS/e-mail/push) | **SNS** | Canais A2P |
| **Regras de roteamento complexas**, **eventos de serviços AWS** (EC2, S3, CodePipeline…) | **EventBridge** | Fontes nativas e padrões ricos |
| **Integrar SaaS** (Zendesk, Datadog…) | **EventBridge** | Parceiros e API destinations |
| **Agendamentos** | **EventBridge Scheduler** | Cron/rate |
| **Replay/archive de eventos** | **EventBridge** (ou FIFO SNS) | Recursos nativos |
| **Latência mínima e fan-out massivo** | **SNS** | Mais leve |

> [!tip] Eles se combinam
> É comum **EventBridge → SNS** (para **notificar pessoas**) e **SNS → SQS** (para **fan-out com buffer**). Não é "um ou outro": cada serviço tem **seu papel**.

```json

  "Type": "Notification",
  "MessageId": "22b80b92-fdea-4c2c-8f9d-bdfb0c7bf324",
  "TopicArn": "arn:aws:sns:us-east-1:123456789012:pedido-criado",
  "Subject": "Pedido criado",
  "Message": "{\"pedido_id\":999,\"valor\":42.5}",
  "Timestamp": "2026-11-09T14:03:21.000Z",
  "SignatureVersion": "1",
  "Signature": "EXAMPLEpH+...",
  "SigningCertURL": "https://sns.us-east-1.amazonaws.com/SimpleNotificationService-....pem",

  "MessageAttributes": {"tipo": {"Type": "String", "Value": "pedido.criado"}}
```

> [!tip] Raw message delivery
> Por padrão, SQS e HTTP recebem o **envelope JSON** acima (com `Message` como **string**). Habilite **`RawMessageDelivery`** para entregar **apenas o corpo original** (e os atributos como atributos SQS), **simplificando** o consumidor. Detalhes na próxima folha.

## Fluxo de ponta a ponta (A2A)

```
 1. Publicador chama Publish (tópico, mensagem, atributos)
 2. SNS autentica/autoriza (IAM + política do tópico) e valida
 3. SNS aplica a FILTER POLICY de cada assinatura
 4. Para cada assinatura elegível: entrega em PARALELO ao endpoint
 5. Falha de entrega? aplica a política de RETRY do protocolo
 6. Esgotou as tentativas? envia à DLQ da assinatura (se configurada) ou descarta
 7. Métricas e logs de entrega (CloudWatch)
```

## Exemplo prático: evento de pedido com fan-out e notificação

1. O **checkout** publica `pedido.criado` no tópico **`pedidos`** com atributos `tipo`, `valor_faixa` e `canal`.
2. **Assinaturas SQS** (estoque, faturamento) recebem **todos** os eventos; cada uma tem **DLQ** e **consumidores** próprios.
3. Uma assinatura **Lambda** com **filter policy** (`valor_faixa = alto`) dispara **análise antifraude**.
4. Uma assinatura **Firehose** arquiva **tudo** em S3 (Parquet) para analytics.
5. Uma assinatura **SMS/push** (via outro tópico ou filtro) avisa o **cliente** que o pedido foi recebido.
6. Alarmes monitoram **`NumberOfNotificationsFailed`** e a **DLQ** das assinaturas.
7. Novos interessados (ex.: um serviço de fidelidade) **assinam o tópico** **sem alterar o checkout**.

## Erros comuns e armadilhas

- **Assinar Lambda/HTTP direto** e perder **buffer** e **controle de retentativas** (prefira SQS).
- **Esquecer a política da fila SQS** permitindo o SNS publicar.
- **Não usar filter policies**, fazendo cada assinante **descartar** o que não quer (custo e ruído).
- **Esperar ordem/dedup em tópicos Standard.**
- **Usar SNS como armazenamento**: **não retém** mensagens para releitura.
- **SMS sem limite de gasto** nem proteção contra abuso.
- **Confundir SNS (push)** com SQS (pull) e esperar que o assinante "busque".
- **Mensagens enormes** (use claim check no S3).

## 🧩 Quiz de Fixação

1. Qual a diferença essencial entre SNS e SQS?
2. O que significa A2A e A2P?
3. Quais protocolos de assinatura o SNS suporta?
4. Por que o padrão SNS + SQS é tão usado?
5. O SNS retém mensagens para releitura?
6. Quando preferir EventBridge ao SNS?

**Respostas:**
1) O SNS é publicação e assinatura (push) com fan-out a todos os assinantes; o SQS é uma fila (pull) em que cada mensagem vai a um consumidor.
2) A2A (application-to-application) conecta sistemas (SQS, Lambda, HTTP, Firehose); A2P (application-to-person) alcança pessoas (SMS, e-mail, push móvel).
3) SQS, Lambda, HTTP/HTTPS, e-mail, e-mail-JSON, SMS, push móvel (application) e Amazon Data Firehose.
4) Porque une o fan-out do SNS ao buffer, às retentativas e ao isolamento de cada consumidor proporcionados pelas filas SQS.
5) Não; ele entrega e, com falha, aplica retentativas e DLQ da assinatura, mas não é armazenamento para releitura (FIFO oferece arquivamento e replay como recurso específico).
6) Para roteamento por regras ricas entre serviços AWS e SaaS, eventos nativos de serviços AWS, schema registry, archive e replay.
