### 1.1.1.1. O que é Amazon API Gateway — REST, HTTP e WebSocket APIs, tipos de endpoint, integrações e quando usar em vez de ALB, Function URLs ou AppSync

> [!warning] Aviso
> Os comandos de CLI, JSONs, limites e preços deste material são **ilustrativos, de memória e não foram executados**. O API Gateway evolui rápido (novos recursos de HTTP API, limites de timeout, streaming de respostas, portais de desenvolvedor). **Confirme limites, quotas e preços na documentação oficial e na página de preços** antes de projetar ou orçar. Valores em dólar são ordens de grandeza.

## 1. O problema que o API Gateway resolve

Uma API pública ou interna que entrega funcionalidade de negócio precisa de muito mais do que "receber uma requisição e devolver JSON". Em produção, alguém precisa cuidar de: **autenticação e autorização**, **limitação de taxa** (para um cliente não derrubar o sistema), **validação de requisições**, **cache**, **versionamento e estágios** (dev, homologação, produção), **domínio próprio com TLS**, **logs, métricas e rastreamento**, **proteção contra ataques** e **roteamento** para vários backends. Implementar isso em cada serviço é repetitivo e propenso a erro.

O **Amazon API Gateway** é o serviço **gerenciado** da AWS para **criar, publicar, proteger, monitorar e escalar APIs** em qualquer volume. Ele fica **na frente dos seus backends** (Lambda, EC2/ECS/EKS via HTTP, outros serviços AWS, sistemas on-premises) e centraliza essas responsabilidades. Não há servidor para provisionar: a AWS escala sob demanda e você paga **por requisição** (mais cache e outros extras).

```
 Clientes (web, mobile, parceiros, IoT)
        │  HTTPS (ou WebSocket)
        ▼
┌─────────────────────────────────────────────┐
│               AMAZON API GATEWAY            │
│  domínio · TLS · autorização · throttling   │
│  validação · cache · transformação · logs   │
└───────┬───────────┬──────────────┬──────────┘
        ▼           ▼              ▼
     Lambda     HTTP/ALB/NLB   Serviços AWS (SQS, SNS, DynamoDB,
   (serverless)  (containers,   Step Functions, S3, Kinesis...)
                  on-premises)
```

## 2. Os três tipos de API

| Tipo | Protocolo | Melhor para | Pontos-chave |
|---|---|---|---|
| **REST API** | HTTP/HTTPS, request-response | APIs corporativas completas, com todos os recursos de gestão | Mais **recursos** (API keys, usage plans, cache, WAF, validação, mapping templates, private endpoints, canary); **mais cara** |
| **HTTP API** | HTTP/HTTPS, request-response | APIs simples, proxies para Lambda/HTTP, custo e latência baixos | **~70% mais barata** e **mais rápida**; JWT authorizer nativo, CORS simplificado; **menos recursos** |
| **WebSocket API** | WebSocket (bidirecional, persistente) | Chat, painéis em tempo real, notificações, jogos, colaboração | Rotas por mensagem (`$connect`, `$disconnect`, `$default`, rotas custom); servidor "empurra" mensagens aos clientes |

Existe ainda a noção de **"REST API privada"** (endpoint privado), tratada abaixo como tipo de endpoint, não como outro produto.

> [!tip] Nomenclatura confusa
> "REST API" no API Gateway é o **nome do produto** (versão 1 do serviço, "API Gateway v1"), não significa que HTTP APIs não sejam "RESTful". **HTTP API** é a versão 2 do serviço, mais enxuta.

## 3. Tipos de endpoint (REST API)

| Endpoint | Como funciona | Quando usar |
|---|---|---|
| **Edge-optimized** | Requisições entram pelo **CloudFront** (pontos de presença) e seguem até a região da API | Clientes **globalmente distribuídos** (padrão histórico) |
| **Regional** | Endpoint na região escolhida, sem CloudFront embutido | Clientes **na mesma região** ou quando você usa **seu próprio CloudFront** |
| **Private** | Acessível **somente de dentro de uma VPC**, via **VPC endpoint** (`execute-api`) | APIs **internas**, sem exposição à internet |

HTTP APIs e WebSocket APIs são **regionais**. Para APIs globais com mais controle, é comum usar um endpoint **regional + CloudFront próprio** (cache, WAF, políticas de cabeçalho).

## 4. Tipos de integração (o que fica atrás da API)

| Integração | Descrição | Exemplo |
|---|---|---|
| **Lambda (proxy)** | A requisição inteira vai à função; ela devolve a resposta formatada | Backend serverless clássico |
| **Lambda (custom/não proxy)** | O Gateway **transforma** entrada/saída com mapping templates | Isolar o formato da função do contrato da API |
| **HTTP / HTTP proxy** | Encaminha a um endpoint HTTP(S) | API legada, microserviço em ECS/EKS atrás de ALB |
| **AWS service** | Chama diretamente a API de outro serviço AWS | `PutItem` no DynamoDB, `SendMessage` no SQS, iniciar Step Functions — **sem Lambda** |
| **Mock** | Responde sem backend | Prototipar, testar contrato, CORS preflight |
| **VPC link** | Conecta o Gateway a recursos **privados** (NLB/ALB/Cloud Map) | Backend em sub-rede privada |

A integração **AWS service** é um dos recursos mais valiosos: permite arquiteturas **sem Lambda** (por exemplo, `API Gateway → SQS`), reduzindo custo e latência quando não há lógica de negócio.

## 5. Quando usar API Gateway vs alternativas

| Necessidade | Opção | Observação |
|---|---|---|
| API gerenciada com auth, throttling, estágios, cache | **API Gateway (REST)** | Pacote completo |
| API simples e barata para Lambda/HTTP | **API Gateway (HTTP API)** | Menos recursos, preço menor |
| Tempo real bidirecional | **API Gateway (WebSocket)** ou **AppSync** | AppSync usa GraphQL e assinaturas |
| API GraphQL com resolvers e tempo real | **AWS AppSync** | Outro produto |
| Rotear tráfego HTTP para instâncias/containers com **muito volume e baixo custo** | **ALB** | Sem recursos de gestão de API; preço por LCU, não por requisição |
| Expor **uma função Lambda** direto, sem recursos extras | **Lambda Function URL** | Gratuita, simples, auth IAM ou pública |
| Camada de borda global com cache e proteção | **CloudFront** (na frente de qualquer API) | Combina bem com API Gateway regional |
| Portal para publicar APIs a desenvolvedores externos | **API Gateway + developer portal** | Chaves e planos de uso |

Heurística: **precisa gerir a API como produto** (chaves, planos, quotas, validação, versões) → **REST API**. **Só precisa expor Lambda barato** → **HTTP API** ou **Function URL**. **Alto volume sem recursos de gestão** → **ALB**.

## 6. Preços (visão geral)

O modelo é **por uso**, sem mensalidade:

| Item | Cobrança aproximada |
|---|---|
| **REST API** | ~US$ 3,50 por **milhão de requisições** (com faixas decrescentes por volume) |
| **HTTP API** | ~US$ 1,00 por milhão de requisições (faixas decrescentes) |
| **WebSocket API** | Por milhão de **mensagens** (~US$ 1,00) + por **minutos de conexão** (~US$ 0,25 por milhão de minutos) |
| **Cache (REST)** | Por **hora**, conforme o tamanho (0,5 GB a 237 GB) |
| **Transferência de dados** | Saída para a internet como outros serviços |
| **Free Tier** | Em contas no modelo clássico, **1 milhão de chamadas/mês por 12 meses** (REST e HTTP) |

Exemplo: 50 milhões de requisições/mês → REST ≈ US$ 175; HTTP ≈ US$ 50. Em **altíssimo volume**, o custo por requisição pode superar o de um **ALB**; nesses casos avalie se os recursos de gestão compensam.

## 7. Primeiro exemplo: HTTP API com Lambda (ilustrativo)

```bash
# 1) Cria uma HTTP API com integração "quick create" a uma função existente
aws apigatewayv2 create-api \
  --name api-pedidos \
  --protocol-type HTTP \
  --target arn:aws:lambda:us-east-1:123456789012:function:processa-pedido

# 2) Descobre a URL padrão (invoke URL)
aws apigatewayv2 get-apis --query 'Items[?Name==`api-pedidos`].ApiEndpoint'
# https://abc123.execute-api.us-east-1.amazonaws.com

# 3) Dá permissão ao API Gateway para invocar a função
aws lambda add-permission \
  --function-name processa-pedido \
  --statement-id apigw-invoke \
  --action lambda:InvokeFunction \
  --principal apigateway.amazonaws.com \
  --source-arn "arn:aws:execute-api:us-east-1:123456789012:abc123/*/*"

# 4) Testa
curl -s https://abc123.execute-api.us-east-1.amazonaws.com/pedidos -d '{"id":1}'
```

## 8. Conceitos centrais (vocabulário)

| Termo | Significado |
|---|---|
| **API** | O conjunto de recursos e métodos publicados |
| **Resource / Route** | Caminho (`/pedidos/{id}`) — "resource" em REST, "route" em HTTP/WebSocket |
| **Method** | Verbo HTTP em um recurso (GET, POST...) |
| **Integration** | Como a requisição chega ao backend |
| **Stage** | Versão implantada da API (`dev`, `prod`), com URL própria |
| **Deployment** | "Foto" da API publicada em um stage |
| **Authorizer** | Mecanismo de autenticação/autorização |
| **Usage plan / API key** | Quotas e throttling por cliente (REST) |
| **Mapping template** | Transformação de requisição/resposta (VTL) |
| **Model / Validator** | Esquema JSON e validação de payloads |
| **Gateway response** | Resposta padrão de erros do próprio Gateway |
| **Invoke URL** | URL pública da API/stage |
| **Custom domain** | Nome de domínio próprio (com ACM) |

## 9. Limites que você precisa conhecer

| Limite | Valor típico (confirmar) |
|---|---|
| **Timeout de integração** | **29 s** (REST, padrão; pode ser aumentado para APIs regionais conforme documentação atual) e **30 s** (HTTP API) |
| **Tamanho de payload** | **10 MB** (requisição/resposta) |
| **Throttling por conta/região** | Algo como **10.000 req/s** com **burst** de **5.000** (ajustável) |
| **Tamanho de cache** | 0,5 GB a 237 GB (REST) |
| **WebSocket** | Mensagens de até 128 KB (frames de 32 KB), conexão por até **2 horas**, ociosa por **10 minutos** |
| **Rotas/recursos por API** | Centenas (ajustável) |
| **Stages por API** | Dezenas |

Implicação: **processamentos longos** não devem ficar dentro do timeout de 29–30 s; use **padrão assíncrono** (API → SQS/Step Functions → resposta por polling ou webhook).

## 10. Padrões de arquitetura comuns

```
1) Serverless clássico        : API Gateway → Lambda → DynamoDB
2) Direto ao serviço (sem λ)  : API Gateway → SQS / SNS / Step Functions / DynamoDB
3) Containers                 : API Gateway → VPC Link → ALB/NLB → ECS/EKS
4) Assíncrono com 202         : API Gateway → SQS → worker → status em DynamoDB; GET /status/{id}
5) BFF/Fachada de legado      : API Gateway (HTTP proxy) → sistema on-premises via VPN/Direct Connect
6) Tempo real                 : WebSocket API → Lambda → DynamoDB (conexões) → @connections para empurrar
7) API privada interna        : Private REST API + VPC endpoint + resource policy
```

## 11. Erros comuns

> [!bug] Erros comuns
> 1. **Escolher REST API quando HTTP API bastava** (e pagar ~3,5× mais).
> 2. **Escolher HTTP API** e depois precisar de **API keys, usage plans, WAF ou cache** (só existem em REST).
> 3. **Processar tarefa longa na integração** e estourar o timeout de 29/30 s.
> 4. **Esquecer a permissão** do API Gateway para invocar a Lambda (erro 500 ou 403 na integração).
> 5. **Lambda proxy devolvendo formato inválido** (causa clássica de **502 Bad Gateway**).
> 6. **Expor o endpoint padrão** (`execute-api`) sem controle e sem domínio próprio.
> 7. **Usar edge-optimized** quando você já tem CloudFront próprio (duplica a camada).
> 8. **Não configurar CORS** corretamente para navegadores.
> 9. **Não ligar logs e métricas** e ficar às cegas em incidentes.
> 10. **Confundir throttling por API com limite da conta** e não pedir aumento de quota.

## 12. Troubleshooting inicial

| Sintoma | Causa provável | Ação |
|---|---|---|
| **502 Bad Gateway** | Resposta da Lambda fora do formato proxy | Devolver `statusCode`, `headers`, `body` (string) |
| **504 Gateway Timeout** | Integração excedeu o timeout | Otimizar, tornar assíncrono ou aumentar o limite quando permitido |
| **403 Forbidden / Missing Authentication Token** | Rota/método inexistente, falta de auth, resource policy ou WAF | Conferir URL/stage, autorizador e políticas |
| **429 Too Many Requests** | Throttling (conta, stage, plano de uso) | Ajustar limites, backoff no cliente, pedir aumento |
| **CORS no navegador** | Cabeçalhos/OPTIONS ausentes | Habilitar CORS no Gateway e na resposta do backend |
| **500 Internal Server Error** | Erro de integração/mapeamento/permissão | Ver logs de execução e CloudWatch Logs da Lambda |
| **Endpoint privado não responde** | VPC endpoint/DNS/políticas | Conferir VPC endpoint `execute-api`, DNS privado e resource policy |

## 13. Resumo rápido

- **API Gateway** = serviço gerenciado para **publicar e gerir APIs**: auth, throttling, cache, validação, estágios, domínios, logs e integrações.
- Três tipos: **REST** (mais recursos), **HTTP** (mais barata e simples) e **WebSocket** (tempo real).
- Endpoints: **edge-optimized, regional e privado**; integrações: **Lambda, HTTP, serviços AWS, mock, VPC link**.
- Limites-chave: **timeout 29–30 s**, **payload 10 MB**, **throttling por conta/região**.
- Alternativas: **ALB** (volume e custo), **Function URL** (simples), **AppSync** (GraphQL), **CloudFront** (borda).
