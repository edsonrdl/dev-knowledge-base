### 6.1.1.1. Operação do API Gateway — logs de acesso e execução, métricas e alarmes, X-Ray, custos, quotas, erros 4xx e 5xx, IaC e checklist de produção

> [!warning] Aviso
> Nomes de métricas, formatos de log, preços e quotas abaixo são **de memória, aproximados e variam entre REST e HTTP API**. **Confirme na documentação e na página de preços.** Comandos, JSONs e YAMLs são ilustrativos e não foram executados. Logs de execução com dados completos podem conter **dados sensíveis**: trate com cuidado.

## 1. Observabilidade em três pilares

Operar uma API é responder, a qualquer momento, a três perguntas: **está funcionando?** (métricas e alarmes), **o que aconteceu naquela requisição?** (logs) e **onde está o gargalo?** (tracing). O API Gateway integra-se a **CloudWatch** (métricas e logs) e **X-Ray** (traces).

```
Requisição ──▶ API Gateway ──┬─▶ MÉTRICAS (CloudWatch Metrics) ──▶ alarmes, painéis
                             ├─▶ ACCESS LOGS (CloudWatch Logs/Firehose) ──▶ "quem chamou o quê"
                             ├─▶ EXECUTION LOGS (CloudWatch Logs) ──▶ "como o Gateway processou" (REST)
                             └─▶ TRACES (X-Ray) ──▶ "onde gastou tempo"
```

## 2. Métricas do CloudWatch (namespace `AWS/ApiGateway`)

| Métrica | O que mede | Uso |
|---|---|---|
| **Count** | Total de requisições | Volume e custo |
| **4XXError** | Erros do **cliente** (400–499) | Contratos, auth, throttling |
| **5XXError** | Erros do **servidor** (500–599) | Saúde do backend/Gateway |
| **Latency** | Tempo **total** (Gateway + integração) | SLA ao cliente |
| **IntegrationLatency** | Tempo **só do backend** | Gargalo no backend |
| **CacheHitCount / CacheMissCount** | Acertos/erros de cache (REST) | Eficácia do cache |
| **(HTTP API)** `DataProcessed`, `4xx`, `5xx`, `Latency`, `IntegrationLatency` | Equivalentes com nomes ligeiramente diferentes | |
| **(WebSocket)** `ConnectCount`, `MessageCount`, `IntegrationError`, `ClientError`, `ExecutionError` | Conexões e mensagens | |

Regra para diagnosticar latência:

```
Latency alta  e  IntegrationLatency alta   →  problema no BACKEND
Latency alta  e  IntegrationLatency baixa  →  overhead no Gateway (auth, validação, mapeamento, cache miss, rede)
```

Dimensões: **ApiName**, **Stage**, **Resource**, **Method** (granularidade por rota exige habilitar **métricas detalhadas**, que podem custar).

### 2.1 Alarmes essenciais

| Alarme | Limiar sugerido | Ação |
|---|---|---|
| **5XXError** (taxa) | > 1–2% por 5 min | Acionar plantão |
| **4XXError** súbito | Pico anormal | Investigar auth/contratos/ataque |
| **Latency p95/p99** | > SLO | Investigar backend |
| **Count** (queda brusca) | Queda > X% | Possível indisponibilidade a montante |
| **Throttled (429)** | > 0 sustentado | Ajustar limites/escala |
| **IntegrationLatency** | > SLO do backend | Investigar a integração |

```bash
aws cloudwatch put-metric-alarm --alarm-name api-5xx-prod \
  --namespace AWS/ApiGateway --metric-name 5XXError \
  --dimensions Name=ApiName,Value=api-pedidos Name=Stage,Value=prod \
  --statistic Sum --period 60 --evaluation-periods 5 --threshold 5 \
  --comparison-operator GreaterThanOrEqualToThreshold \
  --alarm-actions arn:aws:sns:us-east-1:123456789012:alertas-api
```

Use **percentis (p95/p99)** para latência, não só a média.

## 3. Logs

### 3.1 Access logs (acesso)

Um registro por requisição, com **formato configurável**. Ideal para **auditoria, análise de uso e segurança** (quem, de onde, qual rota, status, tamanho, latência).

Exemplo de formato JSON (REST/HTTP; variáveis `$context.*`):

```json
{
  "requestId": "$context.requestId",
  "ip": "$context.identity.sourceIp",
  "usuario": "$context.authorizer.principalId",
  "metodo": "$context.httpMethod",
  "rota": "$context.resourcePath",
  "status": "$context.status",
  "latenciaTotal": "$context.responseLatency",
  "latenciaIntegracao": "$context.integrationLatency",
  "bytes": "$context.responseLength",
  "erroIntegracao": "$context.integrationErrorMessage",
  "userAgent": "$context.identity.userAgent"
}
```

Destinos: **CloudWatch Logs** ou **Kinesis Data Firehose** (para S3/OpenSearch/Athena). Consulte com **CloudWatch Logs Insights**:

```sql
fields @timestamp, rota, status, latenciaTotal
| filter status >= 500
| stats count() as erros, avg(latenciaTotal) as media by rota
| sort erros desc
```

### 3.2 Execution logs (execução) — REST

Mostram **o que o Gateway fez** (autorização, mapeamento, chamada ao backend, resposta). Níveis: **OFF, ERROR, INFO**; opção **"Log full requests/responses data"** (**não use em produção sem necessidade** — vaza **dados sensíveis** e **gera custo**). Úteis para **depurar mapeamentos e integrações**.

### 3.3 Pré-requisito: role de log da conta

O API Gateway precisa de uma **role IAM no nível da conta/região** com permissão para escrever em CloudWatch Logs (`AmazonAPIGatewayPushToCloudWatchLogs`). **Sem ela**, habilitar logs falha com erro de ARN do CloudWatch Logs.

```bash
aws apigateway update-account --patch-operations \
  op=replace,path=/cloudwatchRoleArn,value=arn:aws:iam::123456789012:role/apigw-cloudwatch-logs
```

### 3.4 Boas práticas de logs

| Prática | Motivo |
|---|---|
| **Access logs em JSON estruturado** | Consulta e análise fáceis |
| **Correlation ID** (`$context.requestId` ou `X-Amzn-Trace-Id`) propagado ao backend | Ligar logs entre Gateway, Lambda e serviços |
| **Execution logs em ERROR** em produção | Custo e privacidade |
| **Retenção** definida no log group | Evitar custo infinito |
| **Mascarar dados sensíveis** | LGPD/GDPR |
| **Enviar a S3 (Firehose) para longo prazo** | Auditoria barata |

## 4. X-Ray (tracing)

Habilitado por **stage**, o X-Ray registra o **tempo em cada segmento**: Gateway → Lambda → DynamoDB/HTTP externo. Mostra **mapa de serviços**, **latência por etapa**, **erros e falhas**.

```
API Gateway (12 ms) → Lambda (180 ms) → DynamoDB (8 ms) / API externa (95 ms)
```

Uso: encontrar **qual dependência** causa a lentidão; correlacionar com **request IDs**. Habilite **amostragem** adequada para controlar custo.

## 5. CloudTrail e auditoria

- **CloudTrail** registra **chamadas de gerenciamento** (criar/alterar APIs, stages, authorizers, domínios) — não registra as requisições de dados (isso é nos **access logs**).
- Monitore ações sensíveis: **alteração de authorizers, resource policies, desabilitação de logs, mudança de domínio, exclusão de APIs**.
- Combine com **AWS Config** (regras de conformidade, por exemplo "API sem WAF"/"stage sem logging").

## 6. Custos

| Componente | Cobrança |
|---|---|
| **REST** | ~US$ 3,50/milhão (faixas) |
| **HTTP** | ~US$ 1,00/milhão (faixas) |
| **WebSocket** | mensagens + minutos de conexão |
| **Cache** | por hora |
| **Transferência de dados** | saída para a internet |
| **CloudWatch Logs** | ingestão e armazenamento (pode superar o custo das requisições se logar demais) |
| **X-Ray** | traces gravados/lidos |
| **WAF** | web ACL + regras + requisições |
| **Backend** | Lambda/containers/bancos |

Como controlar: **HTTP API**, **cache com bom hit ratio**, **log em ERROR**, **retenção curta**, **amostragem de X-Ray**, **compressão**, **Budgets e tags** por API/stage, **Cost Explorer** filtrando por `AmazonApiGateway`.

## 7. Quotas

| Quota (típica) | Observação |
|---|---|
| Requisições/s por conta e região | Ajustável |
| Nº de APIs por conta | Ajustável |
| Recursos/rotas por API | Ajustável |
| Stages por API | Dezenas |
| Authorizers por API | Dezenas |
| Tamanho de payload, timeout | **Fixos** (10 MB, ~29–30 s) ou conforme a documentação |
| Conexões WebSocket/mensagens | Há limites |
| Usage plans/API keys | Ajustável |

Confirme em **Service Quotas** e planeje aumentos **antes** de picos (lançamentos, campanhas).

## 8. Erros: 4xx e 5xx (guia de diagnóstico)

| Código | Significado no Gateway | Causas frequentes | Onde olhar |
|---|---|---|---|
| **400** | Requisição inválida | Validação de corpo/parâmetros, JSON malformado | Execution logs, modelos |
| **401** | Não autorizado | Token ausente/inválido (Cognito/JWT/authorizer) | Authorizer, claims |
| **403** | Proibido | Policy IAM, resource policy, WAF, API key inválida, `Missing Authentication Token` | Políticas, WAF logs |
| **404** | Rota/recurso não encontrado | Caminho/método/stage errados | Definição da API/stage |
| **413** | Payload grande demais | > 10 MB | Presigned URL |
| **429** | Throttling | Limite de conta/stage/plan | Métricas de throttling |
| **500** | Erro interno/integração | Permissão de integração, mapeamento, backend falhou | Execution logs e logs do backend |
| **502** | Bad Gateway | **Resposta do backend inválida** (Lambda proxy malformada) ou backend caiu | Formato da resposta |
| **503** | Indisponível | Serviço/backend indisponível | Health do backend, Health Dashboard |
| **504** | Gateway Timeout | **Integração excedeu o timeout** | IntegrationLatency, timeout do backend |

Método rápido de diagnóstico:

```
1) Veja o STATUS e o Request ID.
2) Access log: qual rota, qual latência, qual erro de integração?
3) Execution log (se habilitado): onde falhou (auth, mapping, integração)?
4) Logs/traces do backend com o mesmo request ID.
5) Métricas: foi um pico (429/5xx) ou erro pontual?
6) Mudanças recentes (deploy, config, certificado, WAF)?
```

## 9. Segurança operacional

- **Menor privilégio** nas roles de integração (somente as ações necessárias nos recursos específicos).
- **WAF** (REST) e **Shield**; **rate-based rules**.
- **Desabilitar o endpoint padrão** quando houver domínio custom.
- **TLS 1.2+** e **mTLS** quando aplicável.
- **Revisão periódica** de authorizers, resource policies, API keys e planos de uso.
- **Rotação de segredos** do backend e **segredos fora de stage variables**.
- **Dados sensíveis** fora de logs; **retenção** definida.

## 10. IaC e governança

```yaml
# SAM: HTTP API com access logs e throttling (ilustrativo)
Resources:
  LogGroup:
    Type: AWS::Logs::LogGroup
    Properties: { RetentionInDays: 30 }
  Api:
    Type: AWS::Serverless::HttpApi
    Properties:
      AccessLogSettings:
        DestinationArn: !GetAtt LogGroup.Arn
        Format: '{"requestId":"$context.requestId","ip":"$context.identity.sourceIp","rota":"$context.routeKey","status":"$context.status","latencia":"$context.responseLatency"}'
      DefaultRouteSettings:
        ThrottlingBurstLimit: 200
        ThrottlingRateLimit: 100
```

Governança: **tags obrigatórias**, **Config rules**, **SCPs** (impedir APIs sem autenticação em contas de produção, quando viável), **revisão em PR** do OpenAPI/IaC e **testes de contrato**.

## 11. Checklist de produção

**Segurança**
1. Autenticação/autorização definida (Cognito/JWT/IAM/authorizer/mTLS); API key só para medição.
2. **WAF** e **throttling** configurados; **endpoint padrão desabilitado**; **TLS 1.2+**.
3. Validação de entrada (REST) e no backend; CORS restrito.

**Confiabilidade**
4. Timeouts coerentes (backend < Gateway); tarefas longas assíncronas.
5. Idempotência e retentativas com backoff; filas/DLQ para escrita.
6. Multi-AZ no backend; plano de **failover** (Route 53) se necessário.

**Observabilidade**
7. **Access logs JSON**, execution logs em ERROR, **retenção** definida.
8. **Métricas e alarmes** (5xx, 4xx, latência p95/p99, 429, IntegrationLatency).
9. **X-Ray** com amostragem e **correlation ID** propagado.

**Operação e custo**
10. **IaC**, **CI/CD**, **canary** e rollback por alarme; contratos OpenAPI versionados.
11. **Tags**, **Budgets**, revisão de custos (cache, logs, WAF).
12. **Quotas** revisadas antes de picos; runbook de incidentes.

## 12. Erros comuns

> [!bug] Erros comuns
> 1. **Habilitar logs sem a role de CloudWatch da conta** (erro ao salvar).
> 2. **Logar corpo completo em produção** (custo e vazamento).
> 3. **Alarme só na média de latência**, escondendo p99.
> 4. **Não propagar correlation ID** ao backend.
> 5. **Retenção infinita de logs.**
> 6. **Não monitorar 429/5xx** e descobrir pelo cliente.
> 7. **Confundir CloudTrail (gestão) com access logs (dados).**
> 8. **Autorizers/policies sem revisão** após mudanças.
> 9. **Deploy direto em prod sem canary/rollback.**
> 10. **Esquecer de pedir aumento de quota** antes de um pico.

## 13. Troubleshooting operacional

| Sintoma | Causa provável | Ação |
|---|---|---|
| Não consigo habilitar logs | Role de logs da conta ausente | Configurar `cloudwatchRoleArn` |
| Logs vazios | Stage sem logging/nível OFF | Habilitar no stage e redeployar (REST) |
| Custo de logs alto | Full data logging/retenção longa | Reduzir nível e definir retenção |
| 5xx sem causa clara | Backend e Gateway separados | Cruzar request ID: access log → backend |
| Latência alta | Backend ou cache miss | Comparar `Latency` vs `IntegrationLatency`; X-Ray |
| Alarmes ruidosos | Limiar inadequado | Usar taxas/percentis e janelas maiores |
| Mudanças sem rastro | Sem CloudTrail/Config | Habilitar trail e regras de conformidade |

## 14. Resumo rápido

- **Métricas** (Count, 4XX/5XX, Latency, IntegrationLatency) + **alarmes** (5xx, 429, p95/p99) são a primeira linha.
- **Access logs** (quem/o quê, JSON) e **execution logs** (REST, ERROR em prod); **role de logs da conta** é pré-requisito.
- **X-Ray** mostra onde está o tempo; **CloudTrail** audita mudanças; propague **correlation ID**.
- **Custos**: requisições (REST > HTTP), cache, logs, WAF, X-Ray; **quotas** devem ser revisadas antes de picos.
- **Erros**: 400/401/403/404/413/429 (cliente), 500/502/503/504 (servidor/integração); siga o **fluxo de diagnóstico**.
- Use **IaC, canary e checklist** para operar com segurança.

### 🧩 Quiz de Fixação

1. Como distinguir problema de backend de problema de Gateway pela latência?
2. O que são access logs e execution logs?
3. Que pré-requisito é necessário para habilitar logs?
4. Qual a causa clássica de 502 e de 504?
5. O que o CloudTrail registra no API Gateway?
6. Cite três cuidados de custo.
7. Quais alarmes essenciais configurar?

**Respostas:**

1. Latency alta com IntegrationLatency alta indica backend; Latency alta com IntegrationLatency baixa indica overhead no Gateway.
2. Access logs registram cada requisição (quem, rota, status, latência); execution logs (REST) mostram como o Gateway processou (auth, mapeamento, integração).
3. Uma role IAM no nível da conta/região permitindo ao Gateway escrever no CloudWatch Logs.
4. 502: resposta do backend inválida (Lambda proxy malformada); 504: integração excedeu o timeout.
5. Chamadas de gerenciamento (criar/alterar APIs, stages, authorizers, domínios), não as requisições de dados.
6. Usar HTTP API quando possível, cache com bom hit ratio, logs em ERROR com retenção curta, amostragem de X-Ray, tags e Budgets.
7. 5XXError, 4XXError, Latency p95/p99, 429/Throttled, IntegrationLatency e queda anormal de Count.
