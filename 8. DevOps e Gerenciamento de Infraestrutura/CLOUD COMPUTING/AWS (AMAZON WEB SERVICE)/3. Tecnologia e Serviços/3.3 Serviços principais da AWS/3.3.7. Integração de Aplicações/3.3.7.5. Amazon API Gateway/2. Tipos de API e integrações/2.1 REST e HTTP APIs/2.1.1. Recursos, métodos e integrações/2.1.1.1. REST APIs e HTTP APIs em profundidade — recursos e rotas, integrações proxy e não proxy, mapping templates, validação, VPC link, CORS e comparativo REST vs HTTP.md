### 2.1.1.1. REST APIs e HTTP APIs em profundidade — recursos e rotas, integrações proxy e não proxy, mapping templates, validação, VPC link, CORS e comparativo REST vs HTTP

> [!warning] Aviso
> Os JSONs, templates VTL e comandos abaixo são **ilustrativos e não foram executados**. Recursos específicos de REST vs HTTP API mudam ao longo do tempo (a HTTP API vem ganhando funcionalidades). **Confirme a matriz de recursos atual na documentação oficial** antes de escolher o tipo de API para um projeto novo.

## 1. Modelos de roteamento: recursos (REST) vs rotas (HTTP)

A forma de declarar a API é diferente entre os dois produtos:

| Aspecto | REST API | HTTP API |
|---|---|---|
| **Estrutura** | Árvore de **recursos** (`/pedidos`, `/pedidos/{id}`) com **métodos** (GET, POST...) | Lista de **rotas** (`GET /pedidos/{id}`, `ANY /{proxy+}`, `$default`) |
| **Proxy catch-all** | Recurso `{proxy+}` + método `ANY` | Rota `ANY /{proxy+}` ou `$default` |
| **Parâmetros de caminho** | `{id}` | `{id}` |
| **Estágios** | Obrigatórios (deploy explícito de uma "versão" da API) | Opcionais; `$default` com **auto-deploy** |
| **Definição** | Console, CLI, OpenAPI 3/Swagger 2, CloudFormation/SAM | Console, CLI, OpenAPI 3, CloudFormation/SAM |

Exemplo de rota catch-all (HTTP API, ilustrativo) que envia **tudo** a uma Lambda e deixa o roteamento ao framework (Express, FastAPI, Flask):

```bash
aws apigatewayv2 create-route --api-id abc123 --route-key 'ANY /{proxy+}' --target integrations/xyz789
```

## 2. Integrações: proxy vs não proxy

### 2.1 Lambda proxy (AWS_PROXY)

Mais comum e simples. O Gateway **empacota a requisição inteira** em um evento e entrega à função; a função devolve a resposta no **formato esperado**. Não há mapeamento a manter.

Evento (REST, payload 1.0, simplificado):

```json
{
  "resource": "/pedidos/{id}",
  "path": "/pedidos/42",
  "httpMethod": "GET",
  "headers": { "Authorization": "Bearer ...", "Accept": "application/json" },
  "queryStringParameters": { "detalhado": "true" },
  "pathParameters": { "id": "42" },
  "requestContext": { "stage": "prod", "identity": { "sourceIp": "203.0.113.5" } },
  "body": null,
  "isBase64Encoded": false
}
```

Resposta obrigatória da função:

```json
{
  "statusCode": 200,
  "headers": { "Content-Type": "application/json" },
  "body": "{\"id\":42,\"status\":\"PAGO\"}",
  "isBase64Encoded": false
}
```

> [!warning] Cuidado
> `body` deve ser **string** (não objeto). Esquecer isso gera **502 Bad Gateway: Malformed Lambda proxy response**.

**HTTP API** usa por padrão o **payload format 2.0**, mais enxuto (por exemplo, `rawPath`, `requestContext.http.method`, `cookies`) e permite respostas **simplificadas** (a função pode devolver só um objeto/string e o Gateway completa os campos).

### 2.2 Lambda custom (AWS) — não proxy (REST)

O Gateway **transforma** a requisição com um **mapping template** (VTL) antes de chamar a função e transforma a resposta antes de devolver ao cliente. Útil para **isolar contratos** (o formato da API difere do formato da função) ou **versionar** sem alterar o backend.

Exemplo de template de requisição (ilustrativo):

```velocity
{
  "pedidoId": "$input.params('id')",
  "cliente": "$context.identity.cognitoIdentityId",
  "origemIp": "$context.identity.sourceIp",
  "dados": $input.json('$')
}
```

Desvantagens: **mais configuração** (resposta de integração, mapeamento de status, modelos). Na prática, a maioria dos times prefere **proxy** e faz a transformação no código.

### 2.3 HTTP e HTTP proxy

Encaminha a requisição a um **endpoint HTTP(S)** (ALB, serviço no ECS/EKS, API de terceiros). No **HTTP proxy**, a requisição e a resposta **passam sem transformação**. Pode-se **sobrescrever** parâmetros (cabeçalhos, caminho) em ambos os produtos (HTTP API tem *parameter mapping*).

### 2.4 Integração com serviços AWS (service integration)

O Gateway **assume uma role IAM** e chama a API do serviço. Exemplo clássico, **API → SQS** (REST, não proxy):

```
Método POST /fila  ──▶ Integração AWS (SQS: SendMessage)
   Request template (application/json → x-www-form-urlencoded):
      Action=SendMessage&MessageBody=$util.urlEncode($input.body)
   Credenciais: role com sqs:SendMessage
   Resposta: 202 com {"mensagem":"recebida"}
```

Casos populares: **DynamoDB** (PutItem/GetItem), **SQS/SNS** (publicar), **Step Functions** (StartExecution, **StartSyncExecution** para Express), **Kinesis**, **EventBridge** (PutEvents), **S3** (upload/download de objetos). **HTTP API** oferece **integrações de serviço de primeira classe** para um conjunto reduzido (SQS, EventBridge, Kinesis, Step Functions, AppConfig) com mapeamento por parâmetros, sem VTL.

### 2.5 Mock

Responde com um corpo fixo, sem backend; útil para **prototipar**, **testar contratos** e responder a `OPTIONS` (CORS) em REST.

### 2.6 VPC link

Para recursos **privados** (sub-redes sem IP público):

| Produto | VPC link para |
|---|---|
| **REST API** | **NLB** (Network Load Balancer) |
| **HTTP API** | **ALB, NLB ou Cloud Map** (service discovery) |

```
API Gateway ──VPC link──▶ ALB/NLB (sub-rede privada) ──▶ ECS/EKS/EC2
```

Segurança: o tráfego do VPC link não passa pela internet; combine com **security groups** (HTTP API) e **TLS** onde necessário.

## 3. Validação e modelos (REST)

O REST API Gateway pode **validar requisições antes de chamar o backend**, economizando invocações e protegendo contra payloads inválidos:

| Validação | Exemplo |
|---|---|
| **Parâmetros de query/caminho/cabeçalho obrigatórios** | Rejeita sem `X-Tenant-Id` |
| **Corpo contra um modelo JSON Schema** | Rejeita se faltar `pedidoId` ou se `valor` não for número |

```json
{
  "$schema": "http://json-schema.org/draft-04/schema#",
  "title": "NovoPedido",
  "type": "object",
  "required": ["clienteId", "itens"],
  "properties": {
    "clienteId": { "type": "string" },
    "itens": { "type": "array", "minItems": 1,
               "items": { "type": "object", "required": ["sku","qtd"],
                          "properties": { "sku": {"type":"string"}, "qtd": {"type":"integer","minimum":1} } } }
  }
}
```

Requisições inválidas recebem **400** do próprio Gateway, **sem custo de invocação** do backend (mas com custo de requisição do Gateway). **HTTP API não tem validação nativa de corpo**: faça no backend ou use um authorizer/camada intermediária.

## 4. CORS

O **CORS** (Cross-Origin Resource Sharing) é exigido por navegadores quando o front-end e a API têm origens diferentes.

| Produto | Como configurar |
|---|---|
| **HTTP API** | Configuração **nativa** de CORS (origens, métodos, cabeçalhos, `max-age`); o Gateway responde ao `OPTIONS` |
| **REST API** | **Habilitar CORS** no recurso (cria método `OPTIONS` com integração **mock**) **e** devolver os cabeçalhos `Access-Control-Allow-*` nas **respostas** do backend (em proxy, a função precisa incluí-los) |

```json
{ "headers": { "Access-Control-Allow-Origin": "https://app.exemplo.com",
               "Access-Control-Allow-Headers": "Content-Type,Authorization",
               "Access-Control-Allow-Methods": "GET,POST,OPTIONS" } }
```

Erro comum: configurar `OPTIONS` mas esquecer o cabeçalho na resposta do método real, o que ainda quebra no navegador.

## 5. Binários e compressão

- **Conteúdo binário** (imagens, PDFs): em REST, configure **binary media types** e `isBase64Encoded`; em HTTP API, o tratamento é automático por `Content-Type`.
- **Compressão**: REST permite habilitar **compressão** de payload (gzip) com limite mínimo de bytes.
- Tamanho máximo de payload: **10 MB**; para arquivos grandes, use **presigned URLs do S3** em vez de passar pelo Gateway.

## 6. Comparativo REST vs HTTP (matriz de decisão)

| Recurso | REST API | HTTP API |
|---|---|---|
| **Preço** | ~US$ 3,50/milhão | **~US$ 1,00/milhão** |
| **Latência** | Maior | **Menor** |
| **Lambda proxy** | Sim (payload 1.0) | Sim (payload **1.0 ou 2.0**) |
| **Integração HTTP / VPC link** | Sim (NLB) | Sim (**ALB, NLB, Cloud Map**) |
| **Integrações de serviço AWS** | **Amplas** (qualquer ação, VTL) | **Algumas** (SQS, EventBridge, Kinesis, Step Functions, AppConfig) |
| **Mapping templates (VTL)** | **Sim** | Não (parameter mapping simples) |
| **Validação de requisição** | **Sim** | Não |
| **API keys e usage plans** | **Sim** | Não |
| **Cache** | **Sim** | Não |
| **AWS WAF** | **Sim** | Não (use CloudFront+WAF na frente) |
| **Resource policies** | **Sim** | Não |
| **Private endpoint (VPC endpoint)** | **Sim** | Não |
| **Canary releases** | **Sim** | Não |
| **Authorizers** | IAM, Cognito, **Lambda** | IAM, **JWT**, **Lambda** |
| **Certificados de cliente (backend)** | Sim | Não |
| **mTLS (domínio custom)** | Sim | Sim |
| **CORS** | Manual | **Nativo** |
| **Auto-deploy** | Não | **Sim** |
| **Streaming/respostas de longa duração** | Conforme recursos recentes | Conforme recursos recentes |
| **Uso ideal** | API como **produto** (parceiros, monetização, governança) | API **interna/simples** de baixo custo e alta velocidade |

Regra: **comece pela HTTP API**; migre para REST apenas se precisar de **cache, WAF, usage plans, validação, private endpoint, canary ou transformações**.

## 7. Exemplo completo: REST API com integração direta ao DynamoDB (ilustrativo)

```
POST /itens  ──▶ Integração AWS (DynamoDB: PutItem), role com dynamodb:PutItem

Request template:
{
  "TableName": "Itens",
  "Item": {
    "id":   { "S": "$context.requestId" },
    "nome": { "S": "$input.path('$.nome')" },
    "preco":{ "N": "$input.path('$.preco')" }
  }
}
Resposta de integração (200): {"id":"$context.requestId"}
```

Vantagem: **sem Lambda** (custo e latência menores). Limite: regras de negócio complexas ficam difíceis de testar no VTL; use com moderação.

## 8. Infraestrutura como código (SAM, ilustrativo)

```yaml
Resources:
  Api:
    Type: AWS::Serverless::HttpApi
    Properties:
      CorsConfiguration:
        AllowOrigins: ["https://app.exemplo.com"]
        AllowMethods: ["GET","POST"]
  Funcao:
    Type: AWS::Serverless::Function
    Properties:
      Runtime: python3.12
      Handler: app.handler
      Events:
        Get:
          Type: HttpApi
          Properties: { Path: /pedidos/{id}, Method: GET, ApiId: !Ref Api }
```

O SAM cria a API, a integração, a **permissão de invocação** e o stage `$default` automaticamente.

## 9. Erros comuns

> [!bug] Erros comuns
> 1. **`body` como objeto** na resposta da Lambda proxy (502).
> 2. **Usar HTTP API e esperar validação, cache ou WAF.**
> 3. **Mapping templates complexos** que ninguém consegue manter.
> 4. **CORS só no `OPTIONS`**, sem cabeçalhos na resposta do método.
> 5. **VPC link para REST apontando para ALB** (REST exige NLB).
> 6. **Esquecer a role da integração com serviço AWS**, gerando 500.
> 7. **Payload format 2.0 vs 1.0 confundido** no código da função.
> 8. **Passar arquivos grandes pelo Gateway** (limite de 10 MB; use presigned URL).
> 9. **Rotas sobrepostas** sem entender a precedência (rota mais específica vence).
> 10. **Não versionar o contrato** (OpenAPI), quebrando clientes em mudanças.

## 10. Troubleshooting

| Sintoma | Causa provável | Ação |
|---|---|---|
| 502 em REST com Lambda | Formato de resposta inválido | Corrigir `statusCode/headers/body(string)` |
| 500 em integração AWS service | Role/permissão ou template incorreto | Revisar a role e o VTL; usar logs de execução |
| 400 Bad Request do Gateway | Validação de requisição falhou | Conferir o modelo/parâmetros obrigatórios |
| Rota não encontrada (`Not Found`) | Caminho/método/stage errados | Conferir a rota exata e o stage (REST exige deploy) |
| Mudança não aparece (REST) | **Falta de novo deployment** | Fazer deploy no stage |
| VPC link `UNAVAILABLE`/timeout | NLB/ALB/SG/rota | Verificar target health e security groups |
| Binário corrompido | Media type não configurado | Configurar binary media types/`isBase64Encoded` |

## 11. Resumo rápido

- **REST** usa **recursos+métodos** e exige **deploy em stage**; **HTTP** usa **rotas** e tem **auto-deploy**.
- Integrações: **Lambda proxy** (padrão), **não proxy com VTL**, **HTTP/proxy**, **serviços AWS**, **mock**, **VPC link** (NLB em REST; ALB/NLB/Cloud Map em HTTP).
- Só o **REST** tem **validação, mapping templates VTL, cache, WAF, usage plans/keys, resource policies, private endpoint e canary**.
- **CORS**: nativo em HTTP; manual em REST (OPTIONS + cabeçalhos na resposta).
- **Escolha**: comece por HTTP API; use REST quando precisar dos recursos de gestão.

**Respostas:**

1. `statusCode`, `headers` e `body` como string; erro 502 (Malformed Lambda proxy response).
2. Transformação da requisição/resposta em VTL; existe na REST API.
3. REST usa NLB; HTTP API usa ALB, NLB ou Cloud Map.
4. Cache, WAF direto, API keys/usage plans, validação de requisição, mapping templates, resource policies, private endpoint e canary (entre outros).
5. Em HTTP é configuração nativa; em REST habilita-se o método OPTIONS (mock) e devolvem-se os cabeçalhos nas respostas do backend.
6. Formato de evento mais enxuto da HTTP API para Lambda, com respostas simplificadas.
7. O limite de payload é 10 MB; o ideal é usar presigned URLs do S3.
