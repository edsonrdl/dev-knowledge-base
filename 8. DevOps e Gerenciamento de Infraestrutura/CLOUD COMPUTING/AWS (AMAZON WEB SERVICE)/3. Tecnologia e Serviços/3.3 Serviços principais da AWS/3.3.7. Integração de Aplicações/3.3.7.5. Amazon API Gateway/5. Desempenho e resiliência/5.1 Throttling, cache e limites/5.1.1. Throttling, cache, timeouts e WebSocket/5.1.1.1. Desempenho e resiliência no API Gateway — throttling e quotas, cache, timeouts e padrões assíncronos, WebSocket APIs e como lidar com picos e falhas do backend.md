### 5.1.1.1. Desempenho e resiliência no API Gateway — throttling e quotas, cache, timeouts e padrões assíncronos, WebSocket APIs e como lidar com picos e falhas do backend

> [!warning] Aviso
> Os limites, valores de throttling, tamanhos de cache e prazos abaixo são **de memória, aproximados e variam por região, tipo de API e versão do serviço**; vários são **ajustáveis por solicitação**. **Confirme as quotas atuais em Service Quotas e na documentação.** Comandos e JSONs são ilustrativos e não foram executados.

## 1. O que decide o desempenho de uma API

O desempenho percebido pelo cliente é a soma de **quatro tempos**:

```
Tempo total = [rede cliente→borda] + [processamento do API Gateway] + [integração com o backend] + [volta]
```

O API Gateway adiciona **poucos milissegundos** (REST em torno de dezenas de ms; HTTP API menos). O que realmente pesa é o **backend** (Lambda cold start, banco, serviços externos). Por isso, as ferramentas de desempenho do Gateway são, em essência: **cache** (evitar o backend), **throttling** (proteger o backend), **timeouts** (não esperar para sempre) e **padrões assíncronos** (não bloquear o cliente).

## 2. Throttling: limites de taxa

O API Gateway usa um algoritmo de **token bucket** com dois parâmetros:

| Parâmetro | Significado |
|---|---|
| **Rate (taxa)** | Requisições por segundo **sustentadas** |
| **Burst (rajada)** | Capacidade do "balde": quantas requisições podem chegar **de uma vez** acima da taxa |

Há **vários níveis** de limite, aplicados do mais amplo ao mais específico:

```
1) Limite da CONTA por região (ex.: ~10.000 req/s, burst ~5.000 — ajustável)
2) Limite por STAGE (padrão para todos os métodos)
3) Limite por MÉTODO (sobrescreve o stage em rotas específicas)
4) Limite por USAGE PLAN / API KEY (por cliente) — REST
```

O limite **mais restritivo vence**. Ao exceder, o Gateway responde **429 Too Many Requests**.

| Exemplo | Efeito |
|---|---|
| Conta: 10.000 rps; stage: 2.000 rps/burst 1.000 | Esse stage nunca passa de 2.000 rps |
| Método `POST /pagamentos`: 50 rps | Protege um backend frágil |
| Usage plan Bronze: 10 rps, quota 100k/mês | Limita clientes gratuitos |

> [!warning] Importante
> O limite de **conta** é **compartilhado entre todas as APIs** da conta/região: uma API "barulhenta" pode **consumir a taxa de outras**. Use **limites por stage/método** e, quando necessário, **contas separadas** para isolar cargas.

### 2.1 Quotas (usage plan) vs throttling

| Conceito | Janela | Exemplo |
|---|---|---|
| **Throttling** | **Segundos** (taxa/burst) | 100 req/s |
| **Quota** | **Dia/semana/mês** | 1 milhão de requisições/mês por cliente |

### 2.2 Resposta do cliente ao 429

Clientes devem implementar **retry com backoff exponencial e jitter** e respeitar `Retry-After` quando existir. Evite **tempestades de retentativas** (todos tentam ao mesmo tempo): jitter distribui as tentativas.

```
espera = min(teto, base × 2^tentativa) × aleatório(0.5–1.0)
```

## 3. Cache (REST API)

O cache do stage armazena **respostas do backend** e atende requisições repetidas **sem invocar a integração**: reduz **latência**, **custo do backend** e **carga**.

| Parâmetro | Detalhe |
|---|---|
| **Tamanho** | 0,5 GB a 237 GB (cobrado por **hora**) |
| **TTL** | Padrão **300 s** (0 a 3.600 s) por stage ou por método |
| **Chave de cache** | Caminho + parâmetros escolhidos (query, cabeçalhos, caminho) |
| **Escopo** | Por **stage** |
| **Criptografia** | Opcional |
| **Invalidação** | Cliente com `Cache-Control: max-age=0` (se a política permitir), console/API (`flush-stage-cache`) |
| **Métodos** | Em geral **GET** (cache de POST não é padrão) |

```bash
aws apigateway update-stage --rest-api-id abc123 --stage-name prod --patch-operations \
  op=replace,path=/cacheClusterEnabled,value=true \
  op=replace,path=/cacheClusterSize,value=0.5 \
  op=replace,path=/*/*/caching/ttlInSeconds,value=120

aws apigateway flush-stage-cache --rest-api-id abc123 --stage-name prod
```

Boas práticas:

- **Cache em GET idempotentes** e de baixa volatilidade (catálogos, configurações).
- **Inclua no cache key** os parâmetros que alteram a resposta (por exemplo, `idioma`) — e só eles.
- **Dados por usuário**: inclua o identificador do usuário na chave ou **não cacheie** (risco de **vazar dados** entre usuários).
- Combine com **CloudFront** para cache de borda (edge) e com **headers** `Cache-Control` do backend.
- O cache **tem custo fixo por hora**: só compensa se a taxa de acerto for boa.

**HTTP API não tem cache nativo**: use **CloudFront** na frente.

## 4. Timeouts e limites de execução

| Limite | Valor típico | Observação |
|---|---|---|
| **Timeout de integração (REST)** | **29 s** padrão (pode ser ajustado para APIs regionais conforme a documentação atual) | Backend mais lento → **504** |
| **Timeout (HTTP API)** | **30 s** | Idem |
| **Payload** | **10 MB** | Para arquivos grandes, **presigned URL do S3** |
| **Timeout da Lambda** | Até 15 min | **Deve ser menor** que o do Gateway, senão o cliente verá 504 antes |
| **WebSocket**: ociosidade | **10 min**; duração máxima **2 h** | Cliente deve enviar *ping*/reconectar |

Regra: **configure o timeout do backend < timeout do Gateway** e deixe **margem** para o retorno. Quando uma operação pode passar de ~20 s, **mude o padrão**.

## 5. Padrões assíncronos (para tarefas longas ou picos)

### 5.1 202 Accepted + fila

```
POST /pedidos ──▶ API Gateway ──▶ SQS (integração direta, sem Lambda) ──▶ worker (Lambda/ECS)
                  responde 202 + ID                                         │
GET /pedidos/{id}/status ◀── API Gateway ◀── DynamoDB (estado) ◀────────────┘
```

Vantagens: **amortece picos** (a fila absorve), **resiliência** (retentativas e DLQ), **resposta imediata** ao cliente.

### 5.2 Step Functions

- **Express (StartSyncExecution)**: executa **fluxos curtos** e **devolve o resultado** na mesma chamada (até 5 min no serviço, mas limitado ao timeout do Gateway).
- **Standard (StartExecution)**: devolve o **ARN da execução**; o cliente consulta o status ou recebe **callback/webhook**.

### 5.3 Webhook/callback e WebSocket

O cliente informa uma **URL de callback**, ou mantém um **WebSocket** para receber o resultado quando pronto.

## 6. WebSocket APIs

O WebSocket API mantém uma **conexão persistente e bidirecional** (cliente ↔ servidor) — o servidor **empurra** dados sem o cliente perguntar.

| Conceito | Detalhe |
|---|---|
| **Rotas** | Determinadas pela **route selection expression** (por exemplo, `$request.body.action`) |
| **Rotas especiais** | **`$connect`** (abertura; local para autorizar), **`$disconnect`**, **`$default`** (sem correspondência) |
| **Integrações** | Lambda, HTTP, serviços AWS, mock |
| **Connection ID** | Identificador de cada cliente conectado |
| **Enviar ao cliente** | API **`@connections`** (`POST https://{api-id}.execute-api.../@connections/{connectionId}`) |
| **Estado** | O Gateway **não guarda** quem está conectado: **você persiste** os `connectionId` (por exemplo, no **DynamoDB**) |
| **Cobrança** | Por **mensagem** e por **minutos de conexão** |

Padrão de chat/painel em tempo real:

```
Cliente ──WS──▶ $connect ──▶ Lambda grava connectionId no DynamoDB
Cliente envia {"action":"enviar","texto":"oi"} ──▶ rota "enviar" ──▶ Lambda
Lambda consulta conexões no DynamoDB ──▶ @connections POST para cada connectionId
Cliente ──▶ $disconnect ──▶ Lambda remove connectionId
```

```python
import boto3, json
def enviar(event, ctx):
    api = boto3.client("apigatewaymanagementapi",
        endpoint_url=f"https://{event['requestContext']['domainName']}/{event['requestContext']['stage']}")
    for conexao in listar_conexoes():          # lê do DynamoDB
        try:
            api.post_to_connection(ConnectionId=conexao, Data=json.dumps({"msg": "olá"}).encode())
        except api.exceptions.GoneException:
            remover_conexao(conexao)           # cliente desconectado
```

Cuidados: lidar com **GoneException** (cliente saiu), **reconexão** com backoff, **autorização no `$connect`**, **limite de conexões** por conta e **custo** de conexões longas. Para necessidades maiores de tempo real com GraphQL e assinaturas, avalie **AWS AppSync**.

## 7. Resiliência: protegendo o backend

| Técnica | Como |
|---|---|
| **Throttling por método** | Evitar que rotas caras derrubem o sistema |
| **Cache** | Absorver picos de leituras |
| **Fila (SQS)** | Desacoplar escrita; DLQ para falhas |
| **Retentativas no cliente** | Backoff + jitter + idempotência |
| **Idempotência** | Chave de idempotência (`Idempotency-Key`) para POSTs repetidos |
| **Timeouts coerentes** | Backend < Gateway; cliente com seu timeout |
| **Circuit breaker** | No backend/cliente (evita cascata) |
| **Multi-AZ/multi-região** | Backend resiliente; **Route 53 failover** + APIs regionais por região |
| **Gateway responses customizadas** | Mensagens claras para 429/5xx |
| **Alarmes** | 5XXError, Latency, 429 (Throttled) |

### 7.1 Multi-região (visão geral)

Para **alta disponibilidade global**: implante a **mesma API em duas regiões** (por IaC), use **domínio custom regional** em cada uma e **Route 53** com **latência ou failover** (health checks). Dados com **DynamoDB Global Tables** e filas por região. O estado (por exemplo, sessões) deve ser replicado ou **stateless**.

## 8. Dimensionamento e custo

| Fator | Observação |
|---|---|
| **Nº de requisições** | Preço por milhão; HTTP API ~3,5× mais barata |
| **Cache** | Custo por hora (compensa com alto *hit ratio*) |
| **Dados** | Saída de dados para a internet |
| **Lambda/backend** | Geralmente o maior custo; otimize memória e duração |
| **Logs** | CloudWatch Logs de execução completa pode custar mais que as requisições |
| **WebSocket** | Mensagens + minutos de conexão |

Otimizações: **HTTP API** quando possível, **cache** em leituras, **integração direta com serviços** (sem Lambda), **respostas compactas**, **logs em nível adequado**.

## 9. Erros comuns

> [!bug] Erros comuns
> 1. **Timeout da Lambda maior que o do Gateway**, produzindo 504 mesmo com função bem-sucedida.
> 2. **Processar tarefa longa de forma síncrona.**
> 3. **Cache sem chave adequada**, servindo dados de um usuário a outro.
> 4. **Não definir throttling por método** e deixar uma rota derrubar o backend.
> 5. **Todos os clientes com retry imediato (sem jitter)**, causando tempestade.
> 6. **Não persistir `connectionId` no WebSocket** e não conseguir enviar mensagens.
> 7. **Ignorar `GoneException`**, acumulando conexões mortas.
> 8. **Cache habilitado com baixa taxa de acerto**, pagando sem benefício.
> 9. **Um único limite de conta compartilhado** entre produção e laboratório.
> 10. **Sem alarmes** de 5xx, 429 e latência.

## 10. Troubleshooting

| Sintoma | Causa provável | Ação |
|---|---|---|
| **429** frequentes | Throttling por conta/stage/usage plan | Ajustar limites, pedir aumento, backoff no cliente |
| **504** | Backend lento ou timeout em desacordo | Otimizar, aumentar o limite se permitido, tornar assíncrono |
| Cache sem efeito | Chave inclui parâmetros voláteis ou método não GET | Revisar chave/TTL/método |
| Dados trocados entre usuários | Cache sem identificador do usuário | Incluir o usuário na chave ou desabilitar |
| WebSocket cai | Ociosidade de 10 min / limite de 2 h | Ping periódico e reconexão |
| `410 Gone` no `@connections` | Cliente desconectado | Remover o `connectionId` |
| Latência alta | Cold start/backend/região | Provisioned concurrency, cache, aproximar região |

## 11. Resumo rápido

- **Throttling** (token bucket): limites por **conta, stage, método e usage plan**; excesso → **429**; clientes usam **backoff + jitter**.
- **Cache (REST)**: 0,5–237 GB, TTL padrão 300 s, custo por hora; atenção à **chave** e a **dados por usuário**; HTTP API usa CloudFront.
- **Timeouts**: ~29–30 s no Gateway; **backend < Gateway**; tarefas longas → **202 + fila/Step Functions/WebSocket/webhook**.
- **WebSocket**: `$connect`/`$disconnect`/`$default`, **você guarda os `connectionId`**, envia via `@connections`.
- **Resiliência**: fila, DLQ, idempotência, alarmes e (se necessário) multi-região com Route 53.

**Respostas:**

1. Rate (taxa) e burst (rajada); o código é 429.
2. Conta/região, stage, método e usage plan; vale o mais restritivo.
3. Servir a resposta de um usuário a outro (vazamento de dados).
4. Padrão assíncrono: 202 + fila/Step Functions, com status por consulta, webhook ou WebSocket.
5. Para o backend responder (ou falhar) antes de o Gateway expirar e devolver 504 ao cliente.
6. A aplicação (por exemplo, DynamoDB); o Gateway não guarda o estado das conexões.
7. Uma fila (SQS) como buffer, com integração direta e DLQ, além de throttling.
