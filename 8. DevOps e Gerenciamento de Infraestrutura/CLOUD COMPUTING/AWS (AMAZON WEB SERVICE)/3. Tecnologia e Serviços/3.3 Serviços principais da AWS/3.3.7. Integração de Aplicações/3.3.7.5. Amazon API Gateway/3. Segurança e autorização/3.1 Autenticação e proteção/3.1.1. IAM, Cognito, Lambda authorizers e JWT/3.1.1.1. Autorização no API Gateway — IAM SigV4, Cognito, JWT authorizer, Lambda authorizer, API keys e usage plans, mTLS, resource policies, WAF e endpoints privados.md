### 3.1.1.1. Autorização no API Gateway — IAM SigV4, Cognito, JWT authorizer, Lambda authorizer, API keys e usage plans, mTLS, resource policies, WAF e endpoints privados

> [!warning] Aviso
> Políticas, JSONs e comandos abaixo são **ilustrativos e não foram executados**. A disponibilidade de cada mecanismo varia entre **REST API** e **HTTP API**; **confirme a matriz atual na documentação**. Segurança de API é crítica: valide sempre em ambiente de teste e revise com a equipe de segurança antes de expor em produção.

## 1. O modelo de segurança em camadas

Uma API exposta à internet sofre ataques de todo tipo: força bruta, injeção, abuso de taxa, scraping, DDoS, vazamento de chaves. A segurança do API Gateway é pensada em **camadas**, e cada camada responde a uma pergunta:

```
 Cliente ──▶ [1 Rede/Borda]     CloudFront, WAF, Shield, endpoint privado
         ──▶ [2 Transporte]     TLS, mTLS, domínio custom com ACM
         ──▶ [3 Identidade]     QUEM é? (IAM, Cognito, JWT, Lambda authorizer, API key)
         ──▶ [4 Autorização]    PODE fazer isto? (policies, escopos, claims, resource policy)
         ──▶ [5 Controle de taxa] QUANTO pode usar? (throttling, usage plans)
         ──▶ [6 Backend]        validação de entrada, permissões mínimas, segredos
```

Princípio-chave: **API Gateway autentica e autoriza; o backend ainda valida e aplica regras de negócio**. Nunca confie apenas no Gateway.

## 2. Mecanismos de autenticação e autorização

| Mecanismo | REST API | HTTP API | Quando usar |
|---|---|---|---|
| **IAM (SigV4)** | Sim | Sim | Chamadas **entre serviços AWS** ou clientes com credenciais AWS (contas, roles, Cognito Identity Pools) |
| **Amazon Cognito user pool authorizer** | Sim (nativo) | Via **JWT authorizer** | **Usuários finais** de apps web/mobile (login/senha, MFA, social) |
| **JWT authorizer (OIDC/OAuth 2.0)** | Não (use Lambda ou Cognito) | **Sim** | Qualquer IdP que emita **JWT** (Cognito, Auth0, Okta, Entra ID) |
| **Lambda authorizer (custom)** | Sim (TOKEN e REQUEST) | Sim (**simple responses**) | **Lógica própria**: tokens opacos, API keys custom, multi-tenant, consulta a banco |
| **API keys + usage plans** | Sim | Não | **Identificar clientes** e aplicar **quotas/throttling** (não é autenticação forte) |
| **Resource policy** | Sim | Não | **Restringir por IP, VPC, conta** |
| **mTLS** | Sim (domínio custom) | Sim (domínio custom) | **Autenticar o cliente por certificado** (B2B, IoT) |
| **WAF** | Sim | Não direto | Proteger contra **OWASP Top 10, bots, rate-based** |

> [!tip] Regra prática
> **Usuários finais** → **Cognito/JWT**. **Serviços AWS ou máquinas com role** → **IAM**. **Regra de negócio própria** → **Lambda authorizer**. **Parceiros B2B com certificado** → **mTLS**. **API key sozinha nunca é segurança**: serve para **medir e limitar**, não para autenticar.

## 3. IAM authorization (SigV4)

O cliente **assina** a requisição com **AWS Signature Version 4** usando credenciais (de usuário, role ou temporárias do STS). O Gateway valida a assinatura e **a política IAM** do principal.

Política que permite invocar uma rota (ilustrativa):

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": "execute-api:Invoke",
    "Resource": "arn:aws:execute-api:us-east-1:123456789012:abc123/prod/GET/pedidos/*"
  }]
}
```

Formato do ARN: `arn:aws:execute-api:<região>:<conta>:<api-id>/<stage>/<método>/<caminho>`. Boas práticas:

- **Menor privilégio**: um principal por consumidor, limitado a rotas específicas.
- Use **credenciais temporárias** (roles) — nunca chaves de longa duração em clientes.
- Em **Cognito Identity Pools**, mapeie usuários autenticados a uma role com `execute-api:Invoke` restrito.
- Ideal para **microsserviços internos** (service-to-service).

## 4. Amazon Cognito e JWT

### 4.1 Cognito user pool authorizer (REST)

O Gateway valida o **ID token ou access token** emitido por um **user pool** do Cognito: assinatura, expiração e emissor. Você pode exigir **escopos OAuth** (`scope`) por método.

Fluxo:

```
1) Cliente autentica no Cognito  ──▶ recebe JWT (ID/access token)
2) Cliente chama a API com  Authorization: Bearer <JWT>
3) API Gateway valida o JWT no Cognito (sem Lambda) ──▶ repassa claims ao backend
4) Backend lê as claims em requestContext.authorizer.claims
```

### 4.2 JWT authorizer (HTTP API)

Valida JWT de **qualquer provedor OIDC/OAuth 2.0**. Configuração: **issuer** (URL do IdP), **audience** (client IDs) e opcionalmente **escopos** exigidos por rota. É **nativo, barato e rápido** (sem Lambda).

```bash
aws apigatewayv2 create-authorizer \
  --api-id abc123 --name jwt-cognito --authorizer-type JWT \
  --identity-source '$request.header.Authorization' \
  --jwt-configuration Audience=1h57kf5cpq17m0eml12EXAMPLE,Issuer=https://cognito-idp.us-east-1.amazonaws.com/us-east-1_EXAMPLE
```

Claims chegam ao backend em `requestContext.authorizer.jwt.claims`. Use **escopos/claims** para autorização fina (por exemplo, `scope: pedidos:read`) e valide **regras de negócio** (o usuário é dono do recurso?) **no backend**.

## 5. Lambda authorizer (custom)

Uma **função Lambda** que você escreve decide se a requisição é permitida e devolve (REST) uma **política IAM** ou (HTTP) uma **resposta simples**.

| Tipo (REST) | Entrada | Uso |
|---|---|---|
| **TOKEN** | Um único token (cabeçalho) | Bearer tokens, tokens opacos |
| **REQUEST** | Cabeçalhos, query, stage variables, contexto | Decisões com **vários** parâmetros, API keys custom, IP |

Resposta típica (REST):

```json
{
  "principalId": "usuario-123",
  "policyDocument": {
    "Version": "2012-10-17",
    "Statement": [{ "Action": "execute-api:Invoke", "Effect": "Allow",
                    "Resource": "arn:aws:execute-api:us-east-1:123456789012:abc123/prod/*/*" }]
  },
  "context": { "tenantId": "acme", "plano": "gold" }
}
```

Na HTTP API, a resposta simples é `{"isAuthorized": true, "context": {...}}`.

Pontos de atenção:

- **Cache de autorização**: o resultado é **cacheado por TTL** (padrão 300 s) pela chave de identidade; reduz invocações. **Cuidado:** a política cacheada vale para **todas as rotas** autorizadas por ela — use `Resource` amplo (`*/*`) ou chave de cache coerente, ou desabilite o cache se a decisão depende da rota.
- **Latência e custo**: cada cache miss invoca a Lambda.
- **Segurança do próprio authorizer**: valide assinatura/expiração do token; não confie em claims sem validar; trate erros como **negar**.
- `context` repassa **strings** ao backend (não objetos aninhados).

## 6. API keys e usage plans (REST)

| Conceito | Função |
|---|---|
| **API key** | Identificador (string) enviado no cabeçalho `x-api-key` |
| **Usage plan** | Define **throttling** (taxa e burst) e **quota** (por dia/semana/mês) para um conjunto de keys e estágios |
| **Associação** | Vincula keys a planos e a stages |

Caso de uso: **API pública monetizada** com planos Bronze/Prata/Ouro (limites diferentes) e **medição de consumo** por cliente.

> [!warning] Cuidado
> **API key não é um mecanismo de autenticação confiável**: pode vazar, não expira por padrão e não prova identidade. Combine com **Cognito/IAM/Lambda authorizer** e use a key para **medição e limites**.

## 7. mTLS (autenticação mútua por certificado)

No **domínio custom**, o Gateway pode **exigir certificado de cliente**, validado contra um **truststore** (arquivo PEM de CAs) armazenado no **S3**.

```
Cliente (certificado X.509) ◀── TLS mútuo ──▶ API Gateway (domínio custom + truststore S3)
```

Usos: **B2B**, **IoT**, **ambientes regulados** (bancos, saúde). Exige **domínio custom** (não funciona no endpoint padrão `execute-api`) e **desabilitar o endpoint padrão** para impedir contornar o mTLS. Combine com autorizadores para autorização.

## 8. Resource policies (REST)

Políticas **baseadas em recurso** anexadas à API controlam **quem pode invocar**:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    { "Effect": "Allow", "Principal": "*", "Action": "execute-api:Invoke",
      "Resource": "arn:aws:execute-api:us-east-1:123456789012:abc123/*" },
    { "Effect": "Deny", "Principal": "*", "Action": "execute-api:Invoke",
      "Resource": "arn:aws:execute-api:us-east-1:123456789012:abc123/*",
      "Condition": { "NotIpAddress": { "aws:SourceIp": ["203.0.113.0/24"] } } }
  ]
}
```

Usos: **restringir por IP/CIDR**, **por VPC/VPC endpoint** (`aws:SourceVpce`), **por conta AWS** (acesso cross-account). Em **APIs privadas**, a resource policy é **obrigatória** para permitir o acesso via VPC endpoint.

## 9. AWS WAF (REST) e Shield

- **WAF** associa-se a **stages de REST API**: regras gerenciadas (OWASP Top 10, IP reputation, bot control), **rate-based rules**, listas de IP, geoblocking, regras customizadas.
- Para **HTTP API**, a proteção WAF vem de colocar **CloudFront + WAF** na frente (com origem regional e restrição para só aceitar tráfego do CloudFront).
- **Shield Standard** protege contra DDoS L3/L4 automaticamente; **Shield Advanced** adiciona proteção estendida e suporte da equipe de resposta.

## 10. Endpoints privados e domínios

- **Private REST API**: acessível só de **VPCs** via **VPC endpoint (`execute-api`)**; combine com **resource policy** e **security groups** do endpoint.
- **Custom domain + ACM**: use **TLS 1.2+**, **security policy** mínima, **mTLS** se necessário e **desabilite o endpoint padrão** (`DisableExecuteApiEndpoint`) para forçar o domínio custom.
- **Certificado**: ACM na **mesma região** (regional) ou em **us-east-1** (edge-optimized).

## 11. Throttling como proteção

Além da autorização, o **controle de taxa** é uma defesa: limites por **conta**, por **stage/método** e por **usage plan/key**. Respostas **429** sinalizam excesso; clientes devem usar **backoff exponencial com jitter**.

## 12. Padrões recomendados por cenário

| Cenário | Desenho |
|---|---|
| App web/mobile com login | Cognito + JWT authorizer (HTTP API) ou Cognito authorizer (REST) + WAF/CloudFront |
| Microsserviços internos | IAM (SigV4) + endpoint privado/VPC link |
| API pública com planos | REST + API keys/usage plans + Cognito/Lambda authorizer + WAF |
| B2B com certificado | mTLS + Lambda authorizer (mapear certificado → cliente) |
| Webhooks de terceiros | Lambda authorizer validando **assinatura HMAC** do remetente |
| API interna entre contas | IAM com resource policy cross-account |
| Tempo real (WebSocket) | Authorizer no `$connect` (Lambda/IAM) |

## 13. Erros comuns

> [!bug] Erros comuns
> 1. **Tratar API key como autenticação.**
> 2. **Cache do Lambda authorizer retornando política para uma rota e permitindo outra** (política restrita demais ou ampla demais).
> 3. **Não validar claims no backend** (autorização por recurso).
> 4. **Deixar o endpoint padrão ativo** com mTLS/domínio custom.
> 5. **Chaves IAM de longa duração em clientes** em vez de credenciais temporárias.
> 6. **CORS aberto (`*`) com cookies/credenciais.**
> 7. **WAF esperado em HTTP API** (não há associação direta).
> 8. **Não limitar taxa** e sofrer abuso/custos.
> 9. **Resource policy errada em API privada**, bloqueando o próprio acesso.
> 10. **Segredos em variáveis do Gateway** (stage variables não são seguras para segredos).

## 14. Troubleshooting

| Sintoma | Causa provável | Ação |
|---|---|---|
| **401 Unauthorized** | Token ausente/inválido/expirado | Conferir cabeçalho, issuer/audience e expiração |
| **403 Forbidden** | Authorizer negou, política IAM, resource policy ou WAF | Ver logs do authorizer, política e WAF |
| **403 `Missing Authentication Token`** | Rota/método inexistente ou sem assinatura SigV4 | Conferir URL, método e assinatura |
| **500 no authorizer** | Erro na Lambda authorizer ou resposta inválida | Logs da função; validar o formato |
| **Política cacheada errada** | TTL de cache e chave de identidade | Ajustar o TTL, `Resource` e a identity source |
| **429** | Throttling/usage plan | Ajustar limites e backoff |
| **API privada inacessível** | VPC endpoint, DNS, resource policy | Verificar `execute-api` endpoint, DNS privado e política |

## 15. Resumo rápido

- Mecanismos: **IAM (SigV4)**, **Cognito/JWT**, **Lambda authorizer**, **API keys + usage plans**, **mTLS**, **resource policies**, **WAF**.
- **Usuários finais → Cognito/JWT**; **serviços AWS → IAM**; **regras próprias → Lambda authorizer**; **B2B → mTLS**.
- **API key mede e limita; não autentica.**
- **Cuide do cache do authorizer**, **valide claims no backend**, **desabilite o endpoint padrão** com domínio custom e proteja com **WAF/Shield/throttling**.
- **REST** tem o conjunto completo; **HTTP API** oferece JWT, IAM, Lambda e mTLS.

**Respostas:**

3. Pode vazar, não expira por padrão e não prova identidade; serve para medir e limitar.
