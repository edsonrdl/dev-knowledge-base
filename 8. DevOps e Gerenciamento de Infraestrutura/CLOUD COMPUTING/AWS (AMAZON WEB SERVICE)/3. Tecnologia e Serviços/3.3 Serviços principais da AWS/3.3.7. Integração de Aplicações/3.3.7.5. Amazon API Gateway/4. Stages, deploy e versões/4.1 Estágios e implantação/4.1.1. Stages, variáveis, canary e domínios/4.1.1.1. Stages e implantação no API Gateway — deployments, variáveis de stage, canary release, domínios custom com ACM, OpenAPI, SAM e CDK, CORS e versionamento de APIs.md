### 4.1.1.1. Stages e implantação no API Gateway — deployments, variáveis de stage, canary release, domínios custom com ACM, OpenAPI, SAM e CDK, CORS e versionamento de APIs

> [!warning] Aviso
> Comandos, JSONs e YAMLs abaixo são **ilustrativos e não foram executados**. O comportamento de deploy difere entre **REST API** (deploy explícito) e **HTTP API** (auto-deploy opcional); **confirme na documentação** os recursos atuais (canary, variáveis, mapeamento de domínio) antes de montar um pipeline de produção.

## 1. O modelo: API, deployment e stage

Uma API do API Gateway não é "ao vivo" assim que você a cria ou edita. O modelo de implantação (principalmente em **REST API**) tem **três conceitos**:

| Conceito | O que é | Analogia |
|---|---|---|
| **API (definição)** | Recursos, métodos, integrações, modelos — o "rascunho" editável | Código-fonte |
| **Deployment** | Uma **foto imutável** da definição da API em um instante | Um build/release |
| **Stage** | Um **ponto de acesso nomeado** (`dev`, `hml`, `prod`) que **aponta para um deployment** e tem **configurações próprias** | Ambiente (URL, cache, logs, variáveis) |

```
 Definição da API (rascunho) ──[Deploy]──▶ Deployment #14 ──▶ Stage "prod"  → https://abc123.execute-api.../prod
                                          Deployment #13 ◀── Stage "hml"   → https://abc123.execute-api.../hml
```

Pontos cruciais (REST):

- **Editar a API não muda os stages** até você fazer **um novo deployment**. Esquecer o deploy é uma das causas mais comuns de "mudei e não funcionou".
- Cada stage tem **URL própria**: `https://{api-id}.execute-api.{região}.amazonaws.com/{stage}`.
- Você pode **reapontar** um stage para um deployment anterior (**rollback**).

**HTTP API:** o stage especial **`$default`** serve na raiz (sem `/stage` na URL) e pode ter **auto-deploy**: qualquer alteração é publicada automaticamente (conveniente em dev; avalie em produção).

## 2. O que se configura por stage (REST)

| Configuração | Detalhe |
|---|---|
| **Cache** | Habilitar, tamanho (0,5–237 GB), TTL (padrão 300 s), chaves, criptografia |
| **Throttling** | Limites de taxa e burst por stage ou por método |
| **Logs de execução** | Nível (ERROR/INFO) e dados completos (cuidado com dados sensíveis) |
| **Access logs** | Formato customizado, enviado ao CloudWatch Logs/Firehose |
| **X-Ray tracing** | Rastreamento distribuído |
| **WAF** | Web ACL associada ao stage |
| **Certificado de cliente** | Para o backend validar que a chamada veio do Gateway |
| **Variáveis de stage** | Parâmetros do ambiente |
| **Canary** | Percentual de tráfego para uma nova versão |
| **Tags** | Alocação de custos |

## 3. Variáveis de stage (stage variables)

Parâmetros **por ambiente** usados em integrações, mapeamentos e autorizadores, para **reutilizar a mesma definição** com backends diferentes.

```
Stage "hml":   urlBackend = hml.api.interno   · aliasLambda = hml
Stage "prod":  urlBackend = api.interno       · aliasLambda = prod

Integração HTTP:   https://${stageVariables.urlBackend}/pedidos
Integração Lambda: arn:aws:lambda:...:function:processa-pedido:${stageVariables.aliasLambda}
```

Referência em templates: `$stageVariables.nome` (VTL) ou `${stageVariables.nome}` em URIs. Boas práticas:

- Use para **URLs, aliases de Lambda, nomes de tabelas, feature flags**.
- **Nunca para segredos** (visíveis a quem lê a configuração): use **Secrets Manager/Parameter Store** no backend.
- Com **aliases de Lambda**, o API Gateway pode apontar `hml` e `prod` para aliases distintos e **promover versões** sem mudar a API.
- Conceda à Lambda a permissão de invocação **para cada alias** usado via stage variable (a permissão não é automática quando o alias vem de variável).

## 4. Canary release (REST)

O **canary** direciona uma **fração do tráfego** do stage para uma **nova versão** (deployment candidato) enquanto o restante continua na estável.

```
Stage prod (deployment atual)  ◀── 90% do tráfego
Canary    (deployment novo)    ◀── 10% do tráfego   (métricas e logs separados)
```

Fluxo:

1. **Criar o deployment** em modo canary com `percentTraffic` (por exemplo, 10).
2. **Monitorar** métricas/logs do canary (erros 5xx, latência) — o Gateway separa as métricas.
3. **Promover** (o canary vira o deployment do stage) ou **reverter** (remover o canary).
4. Opcionalmente, substituir variáveis de stage **só para o canary** (apontar para outro backend).

```bash
aws apigateway create-deployment --rest-api-id abc123 --stage-name prod \
  --canary-settings percentTraffic=10,useStageCache=false
# Após validar:
aws apigateway update-stage --rest-api-id abc123 --stage-name prod \
  --patch-operations op=remove,path=/canarySettings
```

**HTTP API não tem canary nativo**: use **pesos entre aliases de Lambda** (`routing-config`) ou **CodeDeploy**/**weighted target groups do ALB** para liberação gradual.

## 5. Estratégias de ambientes e versionamento

| Abordagem | Como | Prós/Contras |
|---|---|---|
| **Um stage por ambiente** | `dev`, `hml`, `prod` na mesma API | Simples; **risco**: mesma conta/definição compartilhada |
| **Uma API por ambiente/conta** | APIs separadas, de preferência **contas distintas** | **Isolamento** e permissões separadas; mais IaC |
| **Versão na URL** | `/v1/pedidos`, `/v2/pedidos` (recursos/rotas) | Fácil de entender; convive com clientes antigos |
| **Versão em cabeçalho/mapeamento de domínio** | `api.exemplo.com/v1` → API A, `/v2` → API B (base path mapping) | Evolução independente |
| **Aliases de Lambda** | `prod` aponta para a versão N; promover alterando o alias | Rollback instantâneo |

Recomendação: **contas separadas por ambiente** (Organizations) e **IaC** para criar tudo; **stages** para variações pequenas; **versionar contrato** (OpenAPI) e **deprecar com aviso**.

## 6. Domínios customizados

O endereço padrão (`abc123.execute-api...`) não é amigável nem estável. Use um **domínio custom**:

| Passo | Detalhe |
|---|---|
| **1. Certificado** | **ACM** na mesma região (regional) ou **us-east-1** (edge-optimized) |
| **2. Domain name** | Criar o nome (`api.exemplo.com`) no API Gateway, tipo regional/edge |
| **3. API mapping / base path mapping** | Mapear `domínio/caminho` → `API + stage` (ex.: `/v1` → API v1 prod) |
| **4. DNS** | Route 53: registro **A/AAAA alias** para o endpoint do domínio |
| **5. Política TLS** | TLS 1.2 mínimo |
| **6. mTLS (opcional)** | Truststore no S3 |
| **7. Desabilitar endpoint padrão** | Forçar uso do domínio custom |

```bash
aws apigatewayv2 create-domain-name --domain-name api.exemplo.com \
  --domain-name-configurations CertificateArn=arn:aws:acm:us-east-1:123456789012:certificate/abc-123,EndpointType=REGIONAL,SecurityPolicy=TLS_1_2

aws apigatewayv2 create-api-mapping --domain-name api.exemplo.com \
  --api-id abc123 --stage prod --api-mapping-key v1
# https://api.exemplo.com/v1/...
```

Vantagens: URL estável (você pode **trocar de API** sem mudar clientes), **certificado gerenciado e renovado**, **vários domínios** e **multi-API** num só nome.

## 7. OpenAPI e IaC

### 7.1 OpenAPI (Swagger)

Você pode **importar** e **exportar** a definição da API em **OpenAPI 3** (com extensões `x-amazon-apigateway-*` para integrações, autorizadores, validadores). Benefícios: **contrato como código**, geração de **SDKs** e **documentação**, revisão por pull request.

```yaml
openapi: 3.0.1
info: { title: api-pedidos, version: "1.0" }
paths:
  /pedidos/{id}:
    get:
      parameters: [{ name: id, in: path, required: true, schema: { type: string } }]
      x-amazon-apigateway-integration:
        type: aws_proxy
        httpMethod: POST
        uri: arn:aws:apigateway:us-east-1:lambda:path/2015-03-31/functions/arn:aws:lambda:us-east-1:123456789012:function:busca-pedido/invocations
      security: [{ cognito: [] }]
components:
  securitySchemes:
    cognito:
      type: apiKey
      name: Authorization
      in: header
      x-amazon-apigateway-authtype: cognito_user_pools
      x-amazon-apigateway-authorizer:
        type: cognito_user_pools
        providerARNs: [arn:aws:cognito-idp:us-east-1:123456789012:userpool/us-east-1_EXAMPLE]
```

### 7.2 SAM e CDK

- **AWS SAM** (`AWS::Serverless::Api` e `AWS::Serverless::HttpApi`): declara API, funções, permissões e eventos de forma compacta; `sam deploy` faz o deployment.
- **AWS CDK** (`RestApi`, `HttpApi`): código (TypeScript/Python) com construtos de alto nível (domínios, authorizers, stages).
- **CloudFormation**: atenção a **`AWS::ApiGateway::Deployment`** — uma mudança na API **não redeploya** automaticamente; é preciso um novo recurso Deployment (o SAM/CDK cuidam disso com *hash* da definição).

```yaml
# SAM com REST API, stage e canary (ilustrativo)
Resources:
  Api:
    Type: AWS::Serverless::Api
    Properties:
      StageName: prod
      CanarySetting: { PercentTraffic: 10 }
      TracingEnabled: true
      MethodSettings: [{ HttpMethod: "*", ResourcePath: "/*", ThrottlingRateLimit: 200, ThrottlingBurstLimit: 400 }]
```

## 8. CI/CD

Fluxo típico:

```
Commit → Pipeline (CodePipeline/GitHub Actions)
      → Testes (unitários, contrato OpenAPI)
      → sam build / cdk synth → deploy em hml (stack/ stage)
      → Testes de integração (smoke tests com a invoke URL)
      → Aprovação → deploy em prod (canary 10% → monitoramento → promover)
      → Rollback automático por alarmes CloudWatch (5xx, latência)
```

Boas práticas: **IaC para tudo**, **mesma definição** em todos os ambientes, **parâmetros por ambiente**, **testes de contrato**, **alarmes** ligados ao canary, e **aliases de Lambda** para trocas rápidas.

## 9. CORS e cabeçalhos

(Detalhado na folha de recursos e integrações.) Lembre-se de que CORS é configuração **do Gateway e do backend**, que varia por tipo de API e **precisa de redeploy em REST**.

## 10. Erros comuns

> [!bug] Erros comuns
> 1. **Esquecer de fazer deployment** em REST após alterar a API.
> 2. **Usar stage variables para segredos.**
> 3. **Aliases de Lambda via variável sem `add-permission`** para cada alias (erro 500).
> 4. **Compartilhar stages dev/prod na mesma conta** sem isolamento.
> 5. **Auto-deploy em produção** sem revisão (HTTP API).
> 6. **Canary sem monitoramento** separado e sem critério de promoção.
> 7. **Certificado ACM na região errada** (edge exige us-east-1).
> 8. **Deixar o endpoint padrão ativo** e contornar WAF/mTLS/domínio.
> 9. **Mudar a API sem versionar** e quebrar clientes.
> 10. **CloudFormation sem forçar novo Deployment**, e o stage ficar desatualizado.

## 11. Troubleshooting

| Sintoma | Causa provável | Ação |
|---|---|---|
| Alteração não aparece | Falta deploy (REST) | Criar novo deployment no stage |
| Variável de stage vazia | Nome/stage errados | Conferir a variável no stage correto |
| 500 ao usar alias via variável | Permissão de invocação ausente | `lambda add-permission` para o alias |
| Domínio custom 403/404 | API mapping/stage incorreto | Revisar base path mapping e o stage |
| Certificado não aparece | Região do ACM errada | Emitir na região certa (us-east-1 para edge) |
| Canary com erro alto | Versão nova com bug | Remover o canary (rollback) e investigar logs |
| Stack CloudFormation não atualiza o stage | Deployment não recriado | Usar SAM/CDK ou forçar novo recurso Deployment |

## 12. Resumo rápido

- **REST**: **API (rascunho) → Deployment (foto) → Stage (ambiente)**; sem novo deployment, nada muda. **HTTP**: stage `$default` com **auto-deploy**.
- **Variáveis de stage** parametrizam ambientes (não são para segredos); combine com **aliases de Lambda**.
- **Canary** (REST) libera uma fração do tráfego; em HTTP use **pesos de alias**/ALB/CodeDeploy.
- **Domínio custom + ACM + mapping** dá URL estável; **desabilite o endpoint padrão**.
- **OpenAPI/SAM/CDK** + **CI/CD** com testes, canary e rollback por alarme.

**Respostas:**

1. Deployment é uma foto imutável da definição; stage é um ambiente nomeado que aponta para um deployment e tem configurações próprias.
2. Porque é preciso criar um novo deployment e associá-lo ao stage.
3. Parametrizar ambientes (URLs, aliases, tabelas); não usar para segredos.
4. Direciona uma porcentagem do tráfego do stage para um deployment candidato, com métricas separadas, até promover ou reverter.
5. Em us-east-1.
6. Com pesos entre aliases de Lambda, weighted target groups do ALB ou CodeDeploy.
7. O recurso Deployment não é recriado automaticamente quando a API muda; usar SAM/CDK ou forçar novo Deployment.
