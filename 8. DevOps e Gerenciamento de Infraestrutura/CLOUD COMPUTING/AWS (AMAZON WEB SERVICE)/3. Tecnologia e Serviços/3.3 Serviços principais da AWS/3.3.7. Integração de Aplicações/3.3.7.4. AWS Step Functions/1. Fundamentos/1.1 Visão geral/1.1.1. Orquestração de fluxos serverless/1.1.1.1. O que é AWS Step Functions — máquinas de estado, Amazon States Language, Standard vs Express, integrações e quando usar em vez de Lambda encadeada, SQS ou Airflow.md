### O que é AWS Step Functions — máquinas de estado, Amazon States Language, Standard vs Express, integrações e quando usar em vez de Lambda encadeada, SQS ou Airflow

> [!warning] Aviso
> Limites (tamanho de payload, histórico de execução, duração), preços por transição e por duração, tipos de estado (inclusive JSONata) e integrações mudam com frequência. Os números aqui são referências de estudo; confirme na documentação oficial. Os comandos e definições são exemplos e **não foram executados**.

O **AWS Step Functions** é o serviço de **orquestração de fluxos de trabalho (workflows) serverless** da AWS. Você descreve o fluxo como uma **máquina de estados** (*state machine*): **uma sequência (ou grafo) de passos**, com **decisões**, **paralelismo**, **esperas**, **repetições** e **tratamento de erros**, e o Step Functions **executa, acompanha e registra** cada passo, **chamando serviços AWS** (Lambda, Batch, ECS, Glue, DynamoDB, SNS, SQS, SageMaker e **mais de 200 serviços** pela **integração com o AWS SDK**) **sem você escrever o código de cola**. O resultado é um **fluxo visual**, **durável**, **auditável** e **resiliente**.

A ideia central: **tirar a lógica de coordenação do código das funções** e **colocá-la em uma definição declarativa**. Cada **função** (ou serviço) faz **uma coisa bem**; o **fluxo** decide **a ordem, os desvios, as tentativas e as compensações**.

**Analogia:** o Step Functions é um **maestro de orquestra**. Cada músico (Lambda, Batch, DynamoDB…) **toca seu instrumento**; o maestro **segue a partitura** (a definição da máquina de estados): **quem entra agora, quem espera, quem toca junto, o que fazer se alguém erra**. Sem maestro, cada músico precisaria **combinar sozinho** com todos os outros (código de cola, difícil de manter e de depurar).

## O problema que o Step Functions resolve

| Problema (coordenação "à mão") | Efeito |
|---|---|
| **Lambda chamando Lambda** em cadeia | Acoplamento, **timeouts compostos**, custo de espera, difícil depurar |
| **Lógica de retry/backoff** espalhada em cada função | Inconsistência e bugs |
| **Processos longos** (horas/dias) com **esperas** | Exigem polling, filas e tabelas de estado |
| **Paralelismo e agregação** (fan-out/fan-in) | Código complexo e frágil |
| **Compensações** (saga) em falhas parciais | Difíceis de implementar e testar |
| **Aprovações humanas** no meio do fluxo | Infraestrutura extra de callbacks |
| **Visibilidade**: "onde está o pedido 999?" | Sem histórico claro |
| **Auditoria** e **conformidade** | Logs dispersos |

**Com Step Functions:** o fluxo é **declarado**; **estado e histórico** são **geridos pelo serviço**; **retries, timeouts e erros** são **configuração**; **paralelismo** e **iteração** são **estados nativos**; **callbacks e esperas** são **suportados**; **cada execução** tem **histórico visual** de ponta a ponta.

## Conceitos fundamentais

| Conceito | Descrição |
|---|---|
| **State machine (máquina de estados)** | A **definição do fluxo** (JSON em **Amazon States Language**, ASL) |
| **Execution (execução)** | **Uma instância** da máquina em andamento ou concluída, com **entrada** e **saída** |
| **State (estado)** | **Um passo** do fluxo (tarefa, decisão, espera, paralelo, mapa…) |
| **Amazon States Language (ASL)** | **Linguagem declarativa JSON** que descreve estados e transições |
| **Task** | Estado que **faz trabalho**: chama Lambda, um serviço AWS, uma API ou uma *activity* |
| **Transição (state transition)** | Passagem de um estado ao próximo (**unidade de cobrança** em Standard) |
| **Input / Output** | **JSON** que **flui** entre estados |
| **Workflow Studio** | **Editor visual** (arrastar e soltar) que gera ASL |
| **Tipos de workflow** | **Standard** e **Express** |
| **Versions e aliases** | **Versionamento** de definições e **implantação gradual** |
| **Activity** | Trabalho executado por **um worker externo** que faz *polling* do Step Functions |
| **Task token** | **Token** para **pausar** e **retomar** por **callback** |

### Uma máquina de estados mínima

```json
{
  "Comment": "Processa um pedido",
  "StartAt": "ValidaPedido",
  "States": {
    "ValidaPedido": {
      "Type": "Task",
      "Resource": "arn:aws:states:::lambda:invoke",
      "Parameters": {"FunctionName": "valida-pedido", "Payload.$": "$"},
      "ResultSelector": {"valido.$": "$.Payload.valido"},
      "ResultPath": "$.validacao",
      "Next": "PedidoValido?"
    },
    "PedidoValido?": {
      "Type": "Choice",
      "Choices": [{"Variable": "$.validacao.valido", "BooleanEquals": true, "Next": "Cobra"}],
      "Default": "Rejeita"
    },
    "Cobra": {
      "Type": "Task",
      "Resource": "arn:aws:states:::lambda:invoke",
      "Parameters": {"FunctionName": "cobra-pedido", "Payload.$": "$"},
      "Retry": [{"ErrorEquals": ["States.TaskFailed"], "IntervalSeconds": 5, "MaxAttempts": 3, "BackoffRate": 2}],
      "Catch": [{"ErrorEquals": ["States.ALL"], "Next": "Rejeita"}],
      "End": true
    },
    "Rejeita": {"Type": "Fail", "Error": "PedidoRejeitado", "Cause": "Validação ou cobrança falhou"}
  }
}
```

```
        ┌──────────────┐     válido?      ┌────────┐
 início │ ValidaPedido │ ───────────────► │ Cobra  │──► fim (sucesso)
        └──────────────┘        sim       └───┬────┘
                │ não                          │ erro
                ▼                              ▼
            ┌─────────┐◄───────────────────────┘
            │ Rejeita │ (Fail)
            └─────────┘
```

## Standard vs Express

O Step Functions tem **dois tipos de workflow**, com **garantias e custos diferentes**:

| Característica | **Standard** | **Express** |
|---|---|---|
| **Duração máxima** | **Até 1 ano** | **Até 5 minutos** |
| **Modelo de execução** | **Exactly-once** (cada passo executado **uma vez**, salvo retries configurados) | **At-least-once** (assíncrono) ou **at-most-once** (síncrono) |
| **Taxa de início** | Milhares/s (ajustável) | **Centenas de milhares/s** |
| **Histórico** | **Completo e persistente** (consultável **90 dias**, console/API) | **Sem histórico no serviço**: **logs no CloudWatch Logs** |
| **Cobrança** | **Por transição de estado** | **Por número de execuções + duração e memória** |
| **Chamadas** | Assíncrono (`StartExecution`) | **Assíncrono** ou **síncrono** (`StartSyncExecution`, resposta imediata) |
| **Integração `.sync` e `.waitForTaskToken`** | **Sim** | **Não** (apenas Request Response) |
| **Activities** | Sim | Não |
| **Ideal para** | **Processos longos, críticos, auditáveis** (pedidos, ETL, aprovações) | **Alto volume e curta duração** (processamento de eventos/streams, APIs síncronas, IoT) |

```
 Fluxo de negócio longo, com esperas, aprovações, auditoria e semântica exactly-once?    ─► STANDARD
 Alto volume (milhares/s), curta duração, idempotente, custo por execução baixo?         ─► EXPRESS
 Resposta síncrona a um chamador (ex.: API Gateway → workflow → resposta)?               ─► EXPRESS (Sync)
 Pipeline de dados que roda por horas (Glue/EMR/Batch)?                                  ─► STANDARD
```

> [!tip] Padrão híbrido: Standard por fora, Express por dentro
> Um workflow **Standard** (longo, auditável) **chama workflows Express** (alto volume e baixo custo) para **trechos rápidos e numerosos** (ex.: processar milhares de itens em um **Distributed Map**, cada item por um **Express**). Combina **durabilidade** com **economia**.

## Tipos de estado (visão geral)

| Estado | Função | Exemplo de uso |
|---|---|---|
| **Task** | Executa **trabalho** (Lambda, serviço AWS, API, activity) | Chamar Lambda, iniciar job do Glue |
| **Choice** | **Decisão** condicional (if/else) | Roteamento por valor/estado |
| **Parallel** | **Ramos em paralelo**, com **agregação** | Verificar estoque e fraude ao mesmo tempo |
| **Map** | **Itera** sobre uma **lista** (inline ou **distribuído**) | Processar cada item de um pedido; milhões de objetos no S3 |
| **Wait** | **Espera** por tempo ou até uma data/hora | Aguardar 24 h antes de lembrar o cliente |
| **Pass** | Passa a entrada à saída (com **injeção/transformação** de dados) | Montar estruturas; depuração |
| **Succeed** | Termina **com sucesso** | Fim de ramo |
| **Fail** | Termina **com falha** (com `Error` e `Cause`) | Erros de negócio |

Detalhes e **processamento de entrada/saída** na próxima folha.

## Integrações com serviços

O Step Functions integra-se a serviços de **três maneiras**:

| Tipo de integração | Descrição | Exemplos |
|---|---|---|
| **Integrações otimizadas** | **Recursos dedicados** com **parâmetros específicos** e suporte aos **padrões** `.sync` e `.waitForTaskToken` | **Lambda, Batch, ECS/Fargate, Glue, SageMaker, EMR, Athena, DynamoDB, SNS, SQS, EventBridge, API Gateway, CodeBuild, Step Functions (aninhado), Bedrock** |
| **Integrações com o AWS SDK** | Chama **qualquer API** de **200+ serviços** (**9.000+ ações**) diretamente, sem Lambda | `arn:aws:states:::aws-sdk:s3:putObject`, `aws-sdk:ec2:startInstances`, `aws-sdk:rekognition:detectLabels` |
| **HTTP Task** | Chama **APIs HTTP/HTTPS** externas (via **EventBridge Connection**) | SaaS, APIs de parceiros |

### Padrões de integração (sufixos do `Resource`)

| Padrão | Sufixo | Comportamento |
|---|---|---|
| **Request Response** | (nenhum) | **Chama e segue** imediatamente (não espera conclusão do trabalho) |
| **Run a Job** | **`.sync`** | **Espera o job terminar** (Batch, Glue, ECS, EMR, execução aninhada…) |
| **Wait for Callback** | **`.waitForTaskToken`** | **Pausa** até que alguém chame **`SendTaskSuccess/Failure`** com o **token** (aprovação humana, sistema externo) |

> [!tip] Menos Lambda, mais integração direta
> Antes de escrever uma Lambda **só para chamar outro serviço** (gravar no DynamoDB, publicar no SNS, iniciar um job do Glue), use a **integração otimizada ou do SDK**: **menos código**, **menos custo**, **menos manutenção** e **retries/erros nativos**.

## Modelo de preço (referência)

| Item | Cobrança |
|---|---|
| **Standard** | **Por transição de estado** (centenas de milhares de transições gratuitas por mês; depois cobra por mil transições) |
| **Express** | **Por execução (requisição)** + **duração** (GB-segundo, conforme memória) |
| **Distributed Map** | Execuções-filhas cobradas conforme o **tipo** (Standard ou Express) |
| **Integrações** | Sem cobrança extra do Step Functions; paga-se o **serviço chamado** |
| **CloudWatch Logs / X-Ray** | Por uso |
| **Workflow Studio, versions/aliases** | Sem custo adicional |

```
 Standard: custo ≈ nº de transições × preço (cada estado executado = 1+ transições; retries também contam)
 Express:  custo ≈ nº de execuções × preço + duração (GB-s)
```

> [!warning] Em Standard, loops e retries aumentam a conta
> Cada **passagem por estado** é uma **transição cobrada**. **Polling em loop** (Wait + Choice + Task repetidos) ou **Map com milhões de itens** (em Standard inline) pode **custar muito**. Prefira **`.sync`/callback** (sem polling), **Distributed Map com filhos Express** e **Express** para **alto volume**.

## Limites de referência

| Limite | Valor de referência |
|---|---|
| **Duração Standard** | **1 ano** |
| **Duração Express** | **5 minutos** |
| **Tamanho de entrada/saída** (payload) | **256 KB** por estado/execução |
| **Eventos no histórico Standard** | **25.000** por execução (use workflows aninhados/Distributed Map para fluxos longos) |
| **Execuções simultâneas (Distributed Map)** | Até **10.000** execuções-filhas paralelas |
| **Tamanho da definição** | Até ~1 MB |
| **Máquinas de estado por conta/região** | **Dezenas de milhares** (ajustável) |
| **Taxa de `StartExecution` (Standard)** | Milhares/s com *burst*, ajustável |
| **Retenção do histórico (Standard)** | **90 dias** |
| **Task token / callback** | Até a duração máxima da execução |

## Step Functions vs alternativas

| Critério | **Step Functions** | **Lambda encadeada** | **SQS (filas)** | **EventBridge** | **Apache Airflow (MWAA)** |
|---|---|---|---|---|---|
| **Modelo** | **Orquestração** declarativa de estados | **Código** chamando código | **Mensageria** ponto a ponto | **Coreografia** por eventos | **DAGs** em Python (agendamento e dependências) |
| **Estado e histórico** | **Gerenciados** | Você implementa | Não | Não | Banco do Airflow |
| **Retries/erros** | **Nativos** (Retry/Catch) | Código | DLQ/visibility | Retry/DLQ por alvo | Por tarefa |
| **Esperas longas e callbacks** | **Sim** (até 1 ano) | Difícil | Limitado | Scheduler | Sim |
| **Paralelismo/iteração** | **Parallel/Map/Distributed Map** | Código | Consumidores | Várias regras | Dynamic task mapping |
| **Visualização** | **Nativa** | Não | Não | Limitada | UI do Airflow |
| **Serverless** | **Sim** | Sim | Sim | Sim | **Gerenciado, mas com ambiente/hora** |
| **Foco** | **Fluxos de aplicação e dados** em AWS | Casos simples | Desacoplamento/buffer | Roteamento de eventos | **Pipelines de dados** (ecossistema Python/operadores) |
| **Melhor para** | **Orquestração de microsserviços e ETL**, **sagas**, **aprovações** | Duas funções simples | Tarefas independentes | Reações paralelas | Equipes com Airflow e **muitos pipelines de dados** |

```
 Preciso de passos com ordem, decisões, paralelismo, retries, esperas e visibilidade?    ─► Step Functions
 Apenas desacoplar produtor e consumidor e amortecer picos?                              ─► SQS
 Reações independentes de vários serviços a um fato?                                     ─► EventBridge (coreografia)
 Pipelines de dados com centenas de DAGs, operadores Python e ecossistema Airflow?      ─► MWAA (ou Step Functions para o núcleo AWS)
 Duas ou três Lambdas simples em sequência, sem erros complexos?                         ─► Lambda encadeada ou Step Functions Express
```

### Orquestração vs coreografia

| Orquestração (Step Functions) | Coreografia (EventBridge/SNS) |
|---|---|
| **Um maestro** conduz | Cada serviço **reage** a eventos |
| Fluxo **visível** e **centralizado** | Fluxo **emergente** e difuso |
| **Compensações** centralizadas | Compensações distribuídas |
| Mais **acoplamento** ao orquestrador | **Menos acoplamento** |
| Ótimo **dentro de um domínio** | Ótimo **entre domínios** |

> [!tip] Combine: eventos entre domínios, orquestração dentro do domínio
> Um evento do **EventBridge** **dispara** um **Step Functions** que **conduz o fluxo interno** do domínio e, ao terminar, **publica novos eventos**. Cada ferramenta no seu papel.

## Casos de uso

| Caso | Como o Step Functions ajuda |
|---|---|
| **Processamento de pedidos** | Validar, cobrar, reservar estoque, emitir nota, com **compensações** |
| **ETL e pipelines de dados** | Orquestrar Glue, EMR, Athena, Batch (`.sync`) |
| **Machine learning (MLOps)** | Pré-processar, treinar, avaliar, **aprovar**, implantar (SageMaker) |
| **Aprovações humanas** | **Callback** com **task token** (e-mail/Slack/aplicativo) |
| **Sagas (consistência distribuída)** | **Compensar** passos já executados em caso de falha |
| **Processamento em massa** | **Distributed Map** sobre **milhões de objetos no S3** |
| **Automação de operações** | Runbooks (remediação, patching, DR) com SDK integrations |
| **Onboarding e KYC** | Etapas, esperas, verificações manuais e automáticas |
| **APIs síncronas compostas** | **Express Sync** atrás do API Gateway |
| **Processamento de eventos em alto volume** | **Express** a partir de EventBridge/SQS/Kinesis |
| **Agentes de IA generativa** | Orquestrar chamadas ao **Bedrock**, ferramentas e validações |

## Primeiros comandos

```bash
# Cria a máquina de estados (Standard)
aws stepfunctions create-state-machine --name processa-pedido \
  --definition file://definicao.asl.json \
  --role-arn arn:aws:iam::123456789012:role/StepFunctionsPedidosRole \
  --type STANDARD \
  --logging-configuration '{"level":"ERROR","includeExecutionData":false,
        "destinations":[{"cloudWatchLogsLogGroup":{"logGroupArn":"arn:aws:logs:us-east-1:123456789012:log-group:/sfn/processa-pedido:*"}}]}' \
  --tracing-configuration enabled=true

# Inicia uma execução
aws stepfunctions start-execution \
  --state-machine-arn arn:aws:states:us-east-1:123456789012:stateMachine:processa-pedido \
  --name pedido-999 --input '{"pedido_id":999,"valor":4299.9}'

# Acompanha e vê o histórico
aws stepfunctions describe-execution --execution-arn <arn> --query '[status,startDate,stopDate,output]'
aws stepfunctions get-execution-history --execution-arn <arn> --query 'events[].[id,type]'

# Execução síncrona (Express)
aws stepfunctions start-sync-execution --state-machine-arn <arn-express> --input '{"x":1}'
```

## Exemplo prático: fluxo de pedido com compensação

1. **Evento** `PedidoCriado` (EventBridge) **inicia** a máquina **Standard** com o pedido.
2. **Valida** (Lambda) → **Choice** decide se segue ou rejeita.
3. **Parallel**: **reserva estoque** (DynamoDB via SDK) e **verifica fraude** (Lambda/Bedrock) **ao mesmo tempo**.
4. **Cobra** (Lambda/API de pagamento) com **Retry** exponencial; se falhar definitivamente, **Catch** aciona a **compensação** (**libera estoque**).
5. Pedidos **acima de R$ 10 mil** exigem **aprovação humana**: **`.waitForTaskToken`** envia um e-mail/Slack e **pausa** até que o gerente aprove ou recuse.
6. **Emite nota fiscal** (SQS → sistema legado) e **notifica o cliente** (SNS).
7. Ao terminar, **publica `PedidoConcluído`** no EventBridge.
8. **Logs, X-Ray e histórico** mostram **cada passo** de **cada pedido**; alarmes avisam sobre `ExecutionsFailed`.

## Erros comuns e armadilhas

- **Usar Lambda como "cola"** onde uma **integração direta** bastaria.
- **Colocar lógica de negócio pesada nos estados** (use as funções para isso; o fluxo apenas coordena).
- **Payload grande** (> 256 KB) circulando entre estados: guarde no **S3** e passe a **referência**.
- **Polling em loop** (Wait+Choice+Task) em vez de `.sync`/callback.
- **Esquecer Retry/Catch/Timeout**, deixando falhas silenciosas ou execuções penduradas.
- **Escolher Standard para alto volume** (custo por transição) ou **Express para processos longos/aprovações**.
- **Execuções que estouram 25.000 eventos** de histórico.
- **Achar que Express tem exactly-once** (é *at-least-once*/*at-most-once*; use idempotência).

## 🧩 Quiz de Fixação

1. O que é uma máquina de estados e em que linguagem é definida?
2. Qual a diferença entre workflows Standard e Express?
3. Para que servem os padrões `.sync` e `.waitForTaskToken`?
4. O que são as integrações com o AWS SDK?
5. Por que evitar polling em loop em workflows Standard?
6. Quando preferir EventBridge a Step Functions?

**Respostas:**
1) A definição declarativa do fluxo (estados e transições), escrita em Amazon States Language (JSON).
2) Standard: até 1 ano, exactly-once, histórico persistente, cobrança por transição, com `.sync` e callback; Express: até 5 minutos, alto volume, at-least-once (ou at-most-once síncrono), logs no CloudWatch, cobrança por execução e duração.
3) `.sync` espera o término de um job (Batch, Glue, ECS, execução aninhada); `.waitForTaskToken` pausa até um callback externo com o token (aprovação humana, sistemas externos).
4) Permitem chamar diretamente APIs de mais de 200 serviços AWS a partir de estados Task, sem escrever Lambda.
5) Porque cada passagem por estado é uma transição cobrada; loops de polling geram muitas transições e custo, quando `.sync` ou callback evitam isso.
6) Para coreografia entre domínios, com reações independentes e baixo acoplamento a eventos; Step Functions é preferível quando o fluxo exige ordem, estado, retries, esperas e visibilidade centralizada.
