### Padrões de workflow e escala no Step Functions — Distributed Map, paralelismo, aninhamento, Express síncrono, versões e aliases, implantação gradual, testes e ferramentas de autoria

> [!warning] Aviso
> Limites do Distributed Map, formatos de `ItemReader`, recursos de versões/aliases, `TestState` e ferramentas de autoria mudam com frequência. Os exemplos aqui são referências de estudo; confirme na documentação. As definições e comandos **não foram executados**.

Conhecer os estados, as integrações e o tratamento de erros dá a **base**; **padrões** dão **soluções prontas** para **problemas recorrentes**: **processar milhões de itens do S3**, **paralelizar com controle**, **dividir fluxos grandes** em máquinas aninhadas, **expor workflows como APIs síncronas**, **implantar mudanças com segurança** (**versões, aliases e implantação gradual**), **testar** definições antes de produção e **usar as ferramentas de autoria** (Workflow Studio, CDK, SAM, CloudFormation). Esta folha reúne **os padrões mais úteis**, **como escalar**, **como evoluir** a definição com segurança e **como testar**.

**Analogia:** depois de aprender as **notas e os instrumentos**, aprende-se a **tocar peças inteiras**: **um coro de milhares de vozes** (Distributed Map), **seções que tocam juntas** (Parallel), **movimentos separados em partituras próprias** (aninhamento), **mudar a partitura sem interromper o concerto** (versões/aliases) e **ensaiar antes** (testes).

## Padrões de controle de fluxo

### 1. Sequência com decisão e fusão

```
 [Valida] → [Choice: tipo?] ─► [Fluxo A] ─┐
                          ├─► [Fluxo B] ─┼─► [Consolida] → fim
                          └─► [Default]  ─┘
```
Uso: **roteamento por regra**, com um ponto **comum** de continuação (os ramos convergem para o mesmo estado `Next`).

### 2. Fan-out/fan-in com Parallel

```
 [Prepara] → ┌ Parallel ┐ → [Agrega]
             │ ramo A   │
             │ ramo B   │
             │ ramo C   │
             └──────────┘
```
Uso: **tarefas independentes** (verificar estoque, fraude, crédito) **em paralelo**; a saída é um **array** consolidável.

### 3. Iteração com Map (inline)

```
 [Lista de itens] → Map(MaxConcurrency=N) → [Para cada item: sub-fluxo] → [Agrega resultados]
```
Uso: **dezenas a centenas** de itens (linhas de um pedido, arquivos pequenos) com **controle de concorrência**.

### 4. Laço com condição (loop)

```
 [Inicia] → [Verifica] → Choice: concluído? ─ não ─► [Wait] ─► [Verifica] (volta)
                                    └ sim ─► [Segue]
```
Uso: **quando não existe `.sync`** (APIs de terceiros sem callback). **Limite o nº de iterações** (contador no payload) para **evitar loops infinitos** e **custos**.

```json
"IncrementaTentativa": {"Type": "Pass", "Parameters": {"tentativas.$": "States.MathAdd($.tentativas, 1)", "id.$": "$.id"}, "Next": "LimiteAtingido?"},
"LimiteAtingido?": {"Type": "Choice", "Choices": [{"Variable": "$.tentativas", "NumericGreaterThan": 60, "Next": "FalhaPorExcessoDeTentativas"}], "Default": "EsperaEVerifica"}
```

### 5. Timeout de negócio com Wait + Parallel (corrida)

```
 Parallel ┌ ramo 1: aguarda callback (aprovação) ──────┐
          └ ramo 2: Wait 24h → marca "expirado"        ┘  → quem terminar primeiro? (cuidado: Parallel espera AMBOS)
```
Para **"o que ocorrer primeiro"**, prefira **`TimeoutSeconds` + `Catch States.Timeout`** na própria Task de callback (mais simples e correto).

### 6. Callback com humano (aprovação)

Já vista na folha de integrações: **`.waitForTaskToken`** + **API autenticada** + **timeout/escalonamento**.

### 7. Orquestração de jobs de dados (`.sync`)

```
 [Glue .sync] → [Athena .sync (qualidade)] → Choice → [SageMaker .sync] → [Publica]
```

### 8. Saga com compensação

Já vista na folha de erros: **Catch** em cada passo desviando para **compensações em ordem inversa**.

### 9. Orquestrador "pai" e executores "filhos"

```
 [Pai Standard] ─ startExecution.sync:2 ─► [Filho 1] (sub-domínio A)
                ─ startExecution.sync:2 ─► [Filho 2] (sub-domínio B)
```
Uso: **modularizar**, **reutilizar** e **contornar limites de histórico**.

## Distributed Map: processamento em escala massiva

O **Distributed Map** processa **grandes volumes** (**milhões de itens**) **em paralelo**, **iniciando uma execução-filha por lote** de itens, com **até 10.000 execuções filhas simultâneas**.

| Aspecto | **Map inline** | **Distributed Map** |
|---|---|---|
| **Concorrência máxima** | ~40 iterações | **Até 10.000** execuções-filhas |
| **Origem dos itens** | **JSON do payload** | **JSON, JSONL, CSV, Parquet (conforme suporte), inventário do S3, lista de objetos do S3, saída de outro estado** |
| **Histórico** | Itens **no histórico da execução pai** (limite de 25.000 eventos) | Cada filho tem **histórico próprio** (Standard) ou **logs** (Express) |
| **Resultados** | Retornados no **payload** (256 KB) | **Gravados no S3** (`ResultWriter`) |
| **Lotes** | Item a item | **Batches** (`ItemBatcher`): vários itens **por execução-filha** |
| **Tolerância a falhas** | Falha do item falha o Map (salvo `Catch`) | **`ToleratedFailurePercentage`/`Count`** |
| **Tipo da filha** | Inline | **Standard** ou **Express** |
| **Uso** | Listas pequenas | **ETL em massa**, **processar milhões de arquivos/linhas**, **migrações** |

```json
"ProcessaArquivos": {
  "Type": "Map",
  "ItemReader": {
    "Resource": "arn:aws:states:::s3:listObjectsV2",
    "Parameters": {"Bucket": "meu-datalake", "Prefix": "bruto/2026/11/"},
    "ReaderConfig": {"MaxItems": 1000000}
  },
  "ItemBatcher": {"MaxItemsPerBatch": 100, "MaxInputBytesPerBatch": 262144},
  "MaxConcurrency": 1000,
  "ToleratedFailurePercentage": 1,
  "ItemProcessor": {
    "ProcessorConfig": {"Mode": "DISTRIBUTED", "ExecutionType": "EXPRESS"},
    "StartAt": "TransformaLote",
    "States": {"TransformaLote": {"Type": "Task", "Resource": "arn:aws:states:::lambda:invoke",
        "Parameters": {"FunctionName": "transforma-lote", "Payload.$": "$"}, "End": true}}
  },
  "ResultWriter": {"Resource": "arn:aws:states:::s3:putObject", "Parameters": {"Bucket": "meu-resultados", "Prefix": "map-run/"}},
  "Next": "Consolida"
}
```

| Campo | Função |
|---|---|
| **`ItemReader`** | **De onde ler** (S3 objeto/CSV/JSON/lista de objetos/inventário), com **`ReaderConfig`** (formato, cabeçalhos, `MaxItems`) |
| **`ItemBatcher`** | **Agrupa** itens por execução-filha (**reduz custo e overhead**) |
| **`MaxConcurrency`** | Concorrência máxima de filhas |
| **`ToleratedFailurePercentage` / `ToleratedFailureCount`** | Aceita **parte de falhas** |
| **`ItemProcessor`** | **Sub-fluxo** + `ProcessorConfig` (`DISTRIBUTED`, `ExecutionType`: `STANDARD`/`EXPRESS`) |
| **`ResultWriter`** | **Grava resultados** (sucessos/falhas/pendentes) no S3 como **manifesto** |
| **`ItemSelector`** | Monta a **entrada de cada item/lote** |

### Padrões do Distributed Map

| Cenário | Configuração |
|---|---|
| **Processar milhões de objetos S3** | `ItemReader: listObjectsV2` + **batches** + filhas **Express** (baratas) |
| **Processar um CSV gigante** | `ItemReader: getObject` (CSV com cabeçalho) + batches por N linhas |
| **Migração de dados** | Falha tolerada baixa; **manifesto** de resultados; **redrive** das filhas falhas |
| **Backfill** | Janelas de datas como itens, `MaxConcurrency` limitada para **proteger** o banco |
| **Fan-out para ML** | Cada lote **chama** SageMaker/Bedrock com **limite de taxa** |

> [!tip] Batches e filhas Express reduzem muito o custo
> Processar **1 milhão de itens** como **1 milhão de execuções-filhas** seria **caro**. Com **`ItemBatcher` (ex.: 100 itens por lote)** e **filhas Express**, você tem **10.000 execuções curtas**: **muito mais barato** e **mais eficiente**.

> [!warning] Proteja as dependências com `MaxConcurrency`
> 10.000 execuções paralelas podem **derrubar um banco ou uma API**. **Dimensione `MaxConcurrency`** com base na **capacidade da dependência** (conexões do RDS, limites de API) e **monitore throttling**.

### Relatórios e redrive

| Item | Detalhe |
|---|---|
| **Resultados** | Arquivos no S3: **`SUCCEEDED_*.json`**, **`FAILED_*.json`**, **`PENDING_*.json`**, **`manifest.json`** |
| **Redrive** | Reexecuta **somente as filhas que falharam** |
| **Consolidação** | Um passo posterior **lê o manifesto** e **agrega** |
| **Auditoria** | Cada filha tem **histórico** (Standard) |

## Express síncrono: workflows como APIs

O **Express** suporta **`StartSyncExecution`**: o chamador **espera a saída** (até 5 min), ideal para **endpoints** que **compõem vários passos**.

```
 Cliente ──HTTP──► API Gateway ──(integração direta com StartSyncExecution)──► Express (valida → consulta → calcula) ──► resposta JSON
```

```bash
aws stepfunctions start-sync-execution --state-machine-arn <arn-express> --input '{"cep":"01001000","peso":2}'
```

| Prática | Motivo |
|---|---|
| **API Gateway → Step Functions direto** (integração de serviço) | Sem Lambda intermediária |
| **Idempotência** | Retries do cliente e semântica at-most-once do Sync |
| **Timeout do cliente** | Menor que 5 min |
| **Mapeamento de erros HTTP** | Converter `status`/erros em respostas adequadas |
| **Logs ligados** | O histórico só existe em CloudWatch Logs |
| **Cabeçalhos/autenticação** | No API Gateway (Cognito/IAM) |

## Aninhamento e modularização

| Estratégia | Benefício |
|---|---|
| **Máquinas pequenas e focadas** (por subdomínio) | Testáveis, reutilizáveis |
| **`startExecution.sync:2`** para chamar filhas | Orquestração hierárquica |
| **Express dentro de Standard** | Economia em trechos de alto volume |
| **Fluxos longos divididos** | Fugir dos **25.000 eventos** de histórico |
| **Contratos de entrada/saída** entre máquinas | Evolução independente |
| **Bibliotecas de sub-fluxos** (ex.: "notifica", "aprova") | Padronização |
| **Cuidado com recursão** | Máquina que inicia a si mesma **sem limite** gera **loop de custo** |

## Versões e aliases

O Step Functions suporta **versionamento** de máquinas de estado e **aliases** que **apontam para versões**.

| Conceito | Descrição |
|---|---|
| **Versão** | **Foto imutável** da definição (`PublishVersion`); numerada (1, 2, 3…) |
| **Alias** | **Ponteiro nomeado** (`PROD`, `STAGING`) para **uma ou duas versões** (com **pesos**) |
| **Implantação gradual** | **Alias com roteamento ponderado** (ex.: **10% na v5, 90% na v4**) para **canary/linear** |
| **Execução** | Inicie por **ARN do alias** (`...:stateMachine:processa:PROD`) |
| **Rollback** | **Reapontar o alias** à versão anterior |
| **Execuções em andamento** | **Continuam na versão** com que **iniciaram** (estável) |

```bash
# Publica uma nova versão a partir da definição atual
aws stepfunctions publish-state-machine-version --state-machine-arn <arn> --description "v5: JSONata e novo passo de fraude"

# Cria alias PROD apontando 100% para a v4
aws stepfunctions create-state-machine-alias --name PROD \
  --routing-configuration '[{"stateMachineVersionArn":"<arn>:4","weight":100}]'

# Canary: 10% para v5 e 90% para v4
aws stepfunctions update-state-machine-alias --state-machine-alias-arn <arn>:PROD \
  --routing-configuration '[{"stateMachineVersionArn":"<arn>:5","weight":10},{"stateMachineVersionArn":"<arn>:4","weight":90}]'

# Inicia pela rota do alias
aws stepfunctions start-execution --state-machine-arn <arn>:PROD --input '{...}'
```

| Prática de implantação | Motivo |
|---|---|
| **Sempre iniciar execuções por alias** | Controle de implantação e rollback |
| **Canary → linear → 100%** | Detectar problemas cedo |
| **Monitorar `ExecutionsFailed` por versão** | Decisão de promover/reverter |
| **Definições compatíveis** (entrada/saída estáveis) | Evitar quebrar chamadores |
| **Versões imutáveis em Git/IaC** | Rastreabilidade |
| **Limpar versões antigas** | Organização |
| **CodeDeploy-like (via CloudFormation `DeploymentPreference` no SAM)** | Implantação gradual automatizada com alarmes |

## Testes

| Nível | Ferramenta | O que valida |
|---|---|---|
| **Estado isolado** | **API `TestState`** (console/CLI) | Executa **um estado** com entrada fornecida; mostra **saída, erros e processamento de entrada/saída**; permite **mock** de serviço |
| **Máquina inteira com mocks** | **Step Functions Local / Test with mocked service integrations** | Testes **offline** de lógica de fluxo |
| **Integração** | Execução em **conta de testes** | Interações reais |
| **Unitário das Lambdas** | Frameworks da linguagem | Lógica de negócio |
| **Contrato** | Esquemas de entrada/saída | Compatibilidade entre máquinas |
| **Carga** | Execuções em massa (Express/Distributed Map) | Limites e custo |
| **Caos** | Injetar falhas (erros, timeouts) | Retry/Catch/saga |
| **Pipeline CI** | Validar a ASL, `TestState`, deploy em staging | Qualidade contínua |

```bash
# TestState: roda um estado isolado com entrada e (opcionalmente) mock da resposta do serviço
aws stepfunctions test-state \
  --definition '{"Type":"Pass","Parameters":{"total.$":"States.MathAdd($.a,$.b)"},"End":true}' \
  --role-arn arn:aws:iam::123456789012:role/StepFunctionsTestRole \
  --input '{"a":2,"b":3}' --inspection-level DEBUG
```

| `inspection-level` | Mostra |
|---|---|
| **`INFO`** | Saída e status |
| **`DEBUG`** | **Cada etapa** do processamento de entrada/saída (`InputPath`, `Parameters`, `ResultSelector`, `ResultPath`, `OutputPath`) |
| **`TRACE`** | Detalhes de **HTTP Task** |

> [!tip] Depure transformações com `TestState` em DEBUG
> Grande parte dos erros está na **manipulação de JSON**. O **`TestState`** em modo **DEBUG** mostra **o resultado de cada etapa** do pipeline de dados, **muito mais rápido** do que **executar a máquina inteira** repetidamente.

## Ferramentas de autoria

| Ferramenta | Uso |
|---|---|
| **Workflow Studio** | **Editor visual** (arrastar e soltar) no console e no **VS Code (AWS Toolkit)**; gera/edita a ASL; **boa para aprender e prototipar** |
| **Definição em ASL (JSON/YAML)** | Fonte da verdade em **Git** |
| **AWS SAM** | `AWS::Serverless::StateMachine` com **`DefinitionUri`**, **eventos** (EventBridge, API), **políticas**, **implantação gradual** e **substituições** (`DefinitionSubstitutions`) |
| **AWS CDK** | **Código** (TypeScript/Python…) com **construtos** (`sfn.StateMachine`, `tasks.LambdaInvoke`, `sfn.Map`…), **tipagem e reuso** |
| **CloudFormation / Terraform** | `AWS::StepFunctions::StateMachine` com `DefinitionString`/`DefinitionS3Location` |
| **Step Functions Local / mocks** | Testes offline |
| **Observabilidade** | Console de execução (grafo), X-Ray, CloudWatch |

```yaml
# AWS SAM: máquina Standard com definição externa, substituições e política de implantação gradual
Resources:
  ProcessaPedido:
    Type: AWS::Serverless::StateMachine
    Properties:
      DefinitionUri: statemachines/processa-pedido.asl.json
      DefinitionSubstitutions:
        FuncaoCobraArn: !GetAtt FuncaoCobra.Arn
        TabelaPedidos: !Ref TabelaPedidos
      Policies:
        - LambdaInvokePolicy: {FunctionName: !Ref FuncaoCobra}
        - DynamoDBWritePolicy: {TableName: !Ref TabelaPedidos}
      AutoPublishAlias: PROD
      DeploymentPreference: {Type: Canary10Percent5Minutes, Alarms: [!Ref AlarmeFalhas]}
      Events:
        PedidoCriado:
          Type: EventBridgeRule
          Properties:
            Pattern: {source: [com.minhaempresa.pedidos], detail-type: [Pedido Criado]}
```

```typescript
// AWS CDK (TypeScript): Map + Task Lambda com Retry/Catch
const cobra = new tasks.LambdaInvoke(this, 'Cobra', {lambdaFunction: fnCobra, resultPath: '$.cobranca'})
  .addRetry({errors: ['Lambda.TooManyRequestsException'], interval: Duration.seconds(2), maxAttempts: 5, backoffRate: 2})
  .addCatch(new sfn.Fail(this, 'Falhou'), {resultPath: '$.erro'});
new sfn.StateMachine(this, 'Pedido', {definitionBody: sfn.DefinitionBody.fromChainable(cobra), tracingEnabled: true});
```

| **Equipes de desenvolvimento** que preferem código e testes | **CDK** |

## Exemplo prático: processamento massivo de arquivos com implantação segura

1. **Scheduler** dispara toda noite uma máquina **Standard** `processa-lote`, iniciada por **alias `PROD`**.
2. **Distributed Map** com **`ItemReader: listObjectsV2`** (3 milhões de arquivos), **`ItemBatcher` de 200 itens** e **filhas Express** (`transforma-lote` via Lambda), `MaxConcurrency = 800` (calibrado para o banco destino), **`ToleratedFailurePercentage = 0,5`**.
3. **`ResultWriter`** grava manifestos no S3; um passo posterior **lê o manifesto** e **publica métricas**.
4. Falhas acima do limite ⇒ **`Fail`** + alerta; abaixo ⇒ **sucesso com lista de falhas**, tratada por **redrive** na manhã seguinte.
5. Uma nova versão da máquina (v6) entra por **canary 10% / 30 min** com **alarme em `ExecutionsFailed`**; sem alarmes, **100%**; se falhar, **rollback do alias**.
6. O time testa as transformações com **`TestState` DEBUG** e o fluxo com **mocks** no CI.
7. O **custo** é monitorado: transições Standard (pequenas) + execuções Express (batches) + Lambda.

## Troubleshooting

| Sintoma | Causa provável | Como resolver |
|---|---|---|
| **Distributed Map lento** | `MaxConcurrency` baixa; batches pequenos; throttling da Lambda | Ajustar concorrência/batches; limites da Lambda |
| **Dependência sobrecarregada** | `MaxConcurrency` alta | Reduzir; fila/rate limit |
| **Custo alto no Map** | Filhas Standard por item; batches pequenos | Express + `ItemBatcher` |
| **`ItemReader` falha** | Permissão no S3/formato incorreto | Role; `ReaderConfig`; cabeçalhos |
| **Histórico estoura (25.000 eventos)** | Map inline grande; loops | Distributed Map; aninhar |
| **Loop infinito/custo** | Laço sem contador; recursão | Limite de iterações; revisão |
| **Canary não roteia** | Execuções iniciadas pelo ARN da máquina, não pelo alias | Iniciar por alias |
| **Rollback não efetivo** | Execuções em andamento na versão antiga (comportamento esperado) | Aguardar/abortar; novas execuções seguem o alias |
| **`TestState` ≠ produção** | Mocks/ambiente diferentes | Testes de integração em staging |
| **Express síncrono expira** | > 5 min ou dependência lenta | Standard assíncrono; otimizar |
| **SAM não substitui ARNs** | `DefinitionSubstitutions` ausente | Declarar; usar `${Nome}` na ASL |
| **Execuções duplicadas por eventos** | Início at-least-once | Nome determinístico da execução |

## Erros comuns e armadilhas

- **Map inline para listas enormes** (histórico e custo).
- **`MaxConcurrency` ilimitada** sobre dependências frágeis.
- **Filhas Standard por item** sem lotes.
- **Loops sem limite** de iterações.
- **Iniciar execuções pelo ARN da máquina** em vez do **alias**.
- **Alterar a definição diretamente em produção**, sem versões.
- **Não testar transformações** isoladamente.
- **Usar Parallel para "o que ocorrer primeiro"** (espera todos os ramos).

## 🧩 Quiz de Fixação

1. Quando usar Distributed Map em vez do Map inline?
2. Para que serve o `ItemBatcher`?
3. Como funciona a implantação gradual de uma máquina de estados?
4. O que faz o `TestState` com `inspection-level DEBUG`?
5. Como contornar o limite de 25.000 eventos no histórico?
6. Qual a vantagem de iniciar execuções por alias?

**Respostas:**
1) Quando há muitos itens (milhares a milhões), origem no S3 ou necessidade de alta concorrência (até 10.000 filhas), com histórico próprio por filha e resultados gravados no S3.
2) Agrupar vários itens por execução-filha, reduzindo o número de execuções, o custo e o overhead.
3) Publicando versões imutáveis e usando um alias com roteamento ponderado (por exemplo, 10% na nova versão e 90% na anterior), monitorando alarmes e promovendo ou revertendo reapontando o alias.
4) Executa um único estado com uma entrada e mostra o resultado de cada etapa do processamento de entrada e saída, facilitando a depuração de transformações JSON.
5) Dividindo o fluxo em máquinas aninhadas (startExecution.sync:2) ou usando Distributed Map, em que cada filha tem histórico próprio.
6) Permite controlar versões (canary, rollback) sem mudar o chamador, já que o alias aponta para versões imutáveis e as execuções em andamento permanecem na versão em que iniciaram.
