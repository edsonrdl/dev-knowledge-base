### Erros e confiabilidade no Step Functions — Retry e Catch, nomes de erro, timeouts, heartbeats, sagas com compensação, redrive de execuções e semântica Standard vs Express

> [!warning] Aviso
> Nomes de erro predefinidos, limites de retentativa, comportamento de redrive e semânticas de execução mudam. Os exemplos aqui são referências de estudo; confirme na documentação. As definições e comandos **não foram executados**.

Em sistemas distribuídos, **falhas são normais**: uma API devolve 503, uma Lambda estoura o tempo, um banco recusa conexões, um parceiro responde 429, um job de ETL aborta. O valor real de um orquestrador está em **como lida com a falha**. O Step Functions oferece **tratamento de erros declarativo**: **`Retry`** (tentar de novo, com *backoff*), **`Catch`** (desviar para um caminho alternativo), **`TimeoutSeconds`/`HeartbeatSeconds`** (limites de tempo), **compensações** (padrão **saga**), **redrive** (retomar execuções falhas do ponto onde pararam) e **garantias de execução** diferentes entre **Standard** e **Express**. Esta folha cobre **cada mecanismo**, **os nomes de erro**, **estratégias de idempotência** e **padrões de confiabilidade**.

**Analogia:** o maestro precisa saber **o que fazer quando um músico erra**: **pedir para repetir o trecho** (Retry), **chamar o substituto** (Catch), **parar a orquestra se o erro é grave** (Fail), **avisar a plateia** (notificação) e, se o concerto já foi parcialmente tocado, **desfazer o que for preciso** (compensação). E precisa de **um registro** do que aconteceu para **retomar do compasso certo** (redrive).

## Como os erros surgem

Um estado pode **falhar** por vários motivos:

| Origem | Exemplo | Nome do erro |
|---|---|---|
| **Falha do serviço/função** | Lambda lança exceção; DynamoDB devolve `ProvisionedThroughputExceededException` | **Nome da exceção** (ex.: `States.TaskFailed` ou o **tipo do erro** da Lambda) |
| **Tempo excedido** | Tarefa passa do `TimeoutSeconds` | `States.Timeout` |
| **Batimento perdido** | Worker não envia heartbeat | `States.HeartbeatTimeout` |
| **Permissão negada** | Role sem acesso | `States.Permissions` |
| **Erro de execução da ASL** | Caminho JSON inexistente, tipo errado | `States.Runtime`, `States.ResultPathMatchFailure`, `States.ParameterPathFailure` |
| **Falha do Branch/Map** | Algum ramo falhou | `States.BranchFailed`, `States.ItemReaderFailed` |
| **Nenhuma escolha casou** | `Choice` sem `Default` | `States.NoChoiceMatched` |
| **Dados grandes demais** | Payload > 256 KB | `States.DataLimitExceeded` |
| **Interceptado como "qualquer"** | — | `States.ALL` |
| **Erro de intrínseca/consulta** | Função intrínseca inválida; JSONata falhou | `States.IntrinsicFailure`, `States.QueryEvaluationError` |
| **Falha de HTTP Task** | Resposta 4xx/5xx | `States.Http.StatusCode.<código>` |
| **Erro de negócio** | Estado `Fail` com `Error` próprio | Nome **definido por você** (`PedidoReprovado`) |

### Erros predefinidos mais usados

| Nome | Significado | Retentável? |
|---|---|---|
| **`States.ALL`** | **Qualquer** erro (curinga) | Depende |
| **`States.TaskFailed`** | **Qualquer falha de tarefa** (exceto `States.Timeout`) | Muitas vezes |
| **`States.Timeout`** | Excedeu `TimeoutSeconds` ou `HeartbeatSeconds` | Sim (com cuidado) |
| **`States.HeartbeatTimeout`** | Sem batimento | Sim |
| **`States.Permissions`** | Permissão insuficiente | **Não** (corrigir IAM) |
| **`States.Runtime`** | Erro de runtime da ASL | **Não** (corrigir a definição) |
| **`States.DataLimitExceeded`** | Payload grande | **Não** (redesenhar) |
| **`States.NoChoiceMatched`** | `Choice` sem caminho | **Não** (adicionar `Default`) |
| **`Lambda.ServiceException`, `Lambda.AWSLambdaException`, `Lambda.SdkClientException`, `Lambda.TooManyRequestsException`** | **Erros de infraestrutura da Lambda** | **Sim** (transitórios) |

> [!tip] Distinga erros transitórios de permanentes
> **Transitórios** (throttling, 5xx, timeouts de rede) **merecem retry**. **Permanentes** (permissão, validação, erro de lógica, dados inválidos) **não melhoram com repetição**: vá direto a **Catch/Fail**. Repetir erros permanentes **gasta transições (custo)** e **atrasa a falha** visível.

## Retry: tentar de novo

```json
"Cobra": {
  "Type": "Task",
  "Resource": "arn:aws:states:::lambda:invoke",
  "Parameters": {"FunctionName": "cobra-pedido", "Payload.$": "$"},
  "Retry": [
    {
      "ErrorEquals": ["Lambda.ServiceException","Lambda.AWSLambdaException","Lambda.SdkClientException","Lambda.TooManyRequestsException"],
      "IntervalSeconds": 2, "MaxAttempts": 6, "BackoffRate": 2.0, "MaxDelaySeconds": 60, "JitterStrategy": "FULL"
    },
    {
      "ErrorEquals": ["PagamentoIndisponivel"],
      "IntervalSeconds": 30, "MaxAttempts": 3, "BackoffRate": 2.0
    }
  ],
  "Catch": [{"ErrorEquals": ["States.ALL"], "ResultPath": "$.erro", "Next": "CompensaPedido"}],
  "Next": "Emite"
}
```

| Campo | Função | Padrão |
|---|---|---|
| **`ErrorEquals`** | **Lista de erros** que ativam este *retrier* | (obrigatório) |
| **`IntervalSeconds`** | **Espera** antes da primeira retentativa | 1 s |
| **`MaxAttempts`** | **Número máximo** de retentativas (**0 = não retentar**) | 3 |
| **`BackoffRate`** | **Multiplicador** do intervalo a cada tentativa | 2.0 |
| **`MaxDelaySeconds`** | **Teto** do intervalo | — |
| **`JitterStrategy`** | `FULL` (aleatoriza o intervalo) ou `NONE` | `NONE` |

```
 Backoff: IntervalSeconds=2, BackoffRate=2, MaxAttempts=5
   tentativa 1 falha → espera 2 s → tentativa 2 falha → 4 s → 3 → 8 s → 4 → 16 s → 5 → 32 s → falha definitiva
```

| Regra | Detalhe |
|---|---|
| **Ordem** | Os *retriers* são avaliados **em ordem**; **o primeiro que casa** é usado |
| **Contadores independentes** | **Cada retrier** tem **seu próprio** contador de tentativas |
| **`States.ALL` deve ser o último** | Capturaria tudo antes dos específicos |
| **`States.ALL` não captura `States.DataLimitExceeded`** em *Catch*/*Retry* (conforme a documentação) | Trate explicitamente |
| **Retry antes de Catch** | O Retry se esgota; só então o Catch é avaliado |
| **Custo** | Cada tentativa gera **transições** em Standard |
| **Jitter** | **`FULL`** evita **"manada" de retentativas** simultâneas |

> [!warning] Retry sem idempotência duplica efeitos
> Se a **Task** **já executou o efeito** (cobrou o cartão) e **falhou ao responder** (timeout), o **retry cobrará de novo**. **Torne as operações idempotentes** (**chave de idempotência**, escrita condicional) ou **verifique o estado antes** de repetir.

## Catch: desviar em caso de falha

```json
"Catch": [
  {"ErrorEquals": ["PagamentoRecusado"], "ResultPath": "$.erro", "Next": "CancelaPedido"},
  {"ErrorEquals": ["States.Timeout"],    "ResultPath": "$.erro", "Next": "EscalaParaHumano"},
  {"ErrorEquals": ["States.ALL"],        "ResultPath": "$.erro", "Next": "NotificaFalhaGeral"}
]
```

| Campo | Função |
|---|---|
| **`ErrorEquals`** | Erros capturados |
| **`Next`** | **Estado** para onde desviar |
| **`ResultPath`** | **Onde anexar** as informações do erro (`Error`, `Cause`) na entrada |
| **Saída do erro** | `{"Error": "NomeDoErro", "Cause": "mensagem ou JSON"}` |
| **JSONata** | `$states.errorOutput` |

> [!tip] Sempre use `ResultPath` no Catch
> **Sem `ResultPath`**, a **saída de erro substitui a entrada** e **o próximo estado perde o contexto** (inclusive o ID do pedido que precisa ser compensado). **Anexe** o erro em um campo (`$.erro`) para **preservar a entrada**.

### Padrão: um Catch "guarda-chuva" no fim

```json
"Catch": [
  {"ErrorEquals": ["ErroDeNegocioConhecido"], "Next": "TrataNegocio", "ResultPath": "$.erro"},
  {"ErrorEquals": ["States.ALL"], "Next": "FalhaInesperada", "ResultPath": "$.erro"}
]
```
Trate **erros esperados** de forma **específica** e use `States.ALL` apenas como **rede de segurança** (que **notifica, registra e falha**).

## Timeouts e heartbeats

| Mecanismo | Escopo | Efeito |
|---|---|---|
| **`TimeoutSeconds` (Task)** | Uma tarefa | Excedeu ⇒ **`States.Timeout`** (retentável/capturável) |
| **`HeartbeatSeconds` (Task)** | Tarefas longas com **callback/activity** | Sem **`SendTaskHeartbeat`** no intervalo ⇒ **`States.HeartbeatTimeout`** |
| **`TimeoutSeconds` (máquina)** | A **execução inteira** | Excedeu ⇒ **falha** (`States.Timeout`) |
| **Limite de duração do tipo** | Standard: 1 ano; Express: 5 min | Duro |
| **`TimeoutSecondsPath`** | Timeout **dinâmico** vindo da entrada | Flexibilidade |

```json
"ProcessaVideo": {
  "Type": "Task",
  "Resource": "arn:aws:states:::sqs:sendMessage.waitForTaskToken",
  "Parameters": {"QueueUrl": "...", "MessageBody": {"video.$": "$.video", "token.$": "$$.Task.Token"}},
  "TimeoutSeconds": 7200,
  "HeartbeatSeconds": 300,
  "Catch": [{"ErrorEquals": ["States.Timeout","States.HeartbeatTimeout"], "ResultPath": "$.erro", "Next": "ReenfileiraOuEscala"}],
  "End": true
}
```

> [!warning] Sem `TimeoutSeconds`, uma Task de callback pode esperar até 1 ano
> **Callbacks e activities** **sem timeout** deixam execuções **penduradas por meses** (com **estado reservado** e **possíveis cobranças** de **quotas de execuções abertas**). **Defina sempre** `TimeoutSeconds` (e `HeartbeatSeconds` em tarefas longas).

## Fail e Succeed: finais explícitos

```json
"PedidoReprovado": {"Type": "Fail", "Error": "PedidoReprovado", "Cause": "Fraude detectada"},
"FalhaDinamica":  {"Type": "Fail", "ErrorPath": "$.erro.Error", "CausePath": "$.erro.Cause"}
```

| Uso | Detalhe |
|---|---|
| **`Error` e `Cause` customizados** | Nome **semântico** da falha de negócio; aparece no histórico e em **métricas/alarmes** |
| **`ErrorPath`/`CausePath`** | Repassa o erro **capturado** |
| **Quando falhar de propósito** | Quando **o fluxo não pode continuar** e é preciso **sinalizar** a quem **iniciou a execução** |

## Sagas e compensações

Em **fluxos distribuídos** sem **transação global**, a consistência é obtida por **sagas**: **cada passo** tem uma **ação compensatória** que **desfaz** seu efeito; se **um passo falha**, **executam-se as compensações dos passos anteriores**, **em ordem inversa**.

```
 Passos:         Reserva estoque → Cobra cartão → Emite nota → Agenda envio
 Compensações:   Libera estoque  ← Estorna       ← Cancela nota ← Cancela envio

 Se "Emite nota" falha:  executa  Estorna  →  Libera estoque   (inverso do que já foi feito)
```

```json
{
  "StartAt": "ReservaEstoque",
  "States": {
    "ReservaEstoque": {
      "Type": "Task", "Resource": "arn:aws:states:::lambda:invoke",
      "Parameters": {"FunctionName": "reserva-estoque", "Payload.$": "$"},
      "ResultPath": "$.reserva",
      "Catch": [{"ErrorEquals": ["States.ALL"], "ResultPath": "$.erro", "Next": "Falhou"}],
      "Next": "Cobra"
    },
    "Cobra": {
      "Type": "Task", "Resource": "arn:aws:states:::lambda:invoke",
      "Parameters": {"FunctionName": "cobra", "Payload.$": "$"},
      "ResultPath": "$.cobranca",
      "Catch": [{"ErrorEquals": ["States.ALL"], "ResultPath": "$.erro", "Next": "LiberaEstoque"}],
      "Next": "EmiteNota"
    },
    "EmiteNota": {
      "Type": "Task", "Resource": "arn:aws:states:::lambda:invoke",
      "Parameters": {"FunctionName": "emite-nota", "Payload.$": "$"},
      "ResultPath": "$.nota",
      "Catch": [{"ErrorEquals": ["States.ALL"], "ResultPath": "$.erro", "Next": "Estorna"}],
      "End": true
    },
    "Estorna":       {"Type": "Task", "Resource": "arn:aws:states:::lambda:invoke", "Parameters": {"FunctionName": "estorna", "Payload.$": "$"},
                      "ResultPath": "$.estorno", "Next": "LiberaEstoque"},
    "LiberaEstoque": {"Type": "Task", "Resource": "arn:aws:states:::lambda:invoke", "Parameters": {"FunctionName": "libera-estoque", "Payload.$": "$"},
                      "ResultPath": "$.liberacao", "Next": "Falhou"},
    "Falhou": {"Type": "Fail", "Error": "PedidoNaoConcluido", "Cause": "Fluxo compensado"}
  }
}
```

| Princípio da saga | Prática |
|---|---|
| **Compensações idempotentes** | Podem rodar mais de uma vez |
| **Compensações podem falhar** | `Retry` robusto + **DLQ/alerta humano** se esgotar |
| **Guardar o necessário para compensar** | IDs de reserva/cobrança no payload (`ResultPath`) |
| **Ordem inversa** | Desfazer do mais recente ao mais antigo |
| **Nem tudo é compensável** | E-mails enviados, ações físicas: **projete ordem** (deixe o **irreversível por último**) |
| **Semântica de negócio** | "Cancelar" ≠ "apagar"; compensação **registra** |
| **Auditoria** | Histórico da execução prova o que ocorreu |

> [!tip] Deixe o passo irreversível para o final
> Ordene os passos de modo que **os mais difíceis de desfazer** (enviar e-mail ao cliente, despachar mercadoria) ocorram **por último**, depois que **todos os reversíveis** tiveram sucesso. Menos compensações, menos surpresas.

## Redrive: retomar execuções falhas

O **redrive** permite **retomar uma execução Standard falha, abortada ou com timeout** **a partir do estado que falhou**, **sem refazer os passos já concluídos**.

| Aspecto | Detalhe |
|---|---|
| **Disponível em** | **Standard** |
| **Quando** | Execuções em **`FAILED`**, **`TIMED_OUT`**, **`ABORTED`** |
| **Como** | Console ou **`RedriveExecution`** (CLI/API) |
| **O que acontece** | Retoma **do ponto de falha**, usando **o estado e entrada já registrados**; **mantém os resultados dos passos anteriores** |
| **Em Map/Parallel** | Reexecuta **apenas os itens/ramos que falharam** (em Distributed Map, **só as execuções-filhas falhas**) |
| **Janela** | Até **14 dias** após o encerramento |
| **Limite** | Número máximo de redrives por execução; **histórico acumula** (25.000 eventos) |
| **Cuidado** | **Corrija a causa raiz** antes (permissão, bug, dependência) e **use versão da máquina compatível** |
| **Alteração de definição** | O redrive usa **a mesma versão** da máquina da execução original |

```bash
aws stepfunctions redrive-execution --execution-arn arn:aws:states:us-east-1:123456789012:execution:processa-pedido:pedido-999
```

> [!warning] Redrive repete o passo que falhou
> O passo que falhou é **executado de novo** (**efeitos colaterais parciais** podem existir). A **idempotência** continua **indispensável**. Para **falhas "no meio" de um efeito**, valide **o estado** antes de redirigir.

### Redrive em Distributed Map

| Cenário | Benefício |
|---|---|
| **10 milhões de itens, 500 falharam** | Redrive reexecuta **só as 500 execuções-filhas** falhas |
| **Tolerância a falhas** (`ToleratedFailurePercentage`) | Permite **concluir** com falhas aceitáveis e **tratar depois** |
| **Relatórios de resultado** (`ResultWriter` no S3) | **Manifesto** de sucessos/falhas para **reprocessamento direcionado** |

## Standard vs Express: semântica de execução

| Propriedade | **Standard** | **Express Assíncrono** | **Express Síncrono** |
|---|---|---|---|
| **Garantia** | **Exactly-once** por estado (sujeito a retries configurados) | **At-least-once** | **At-most-once** |
| **Duplicatas** | Não (por padrão) | **Possíveis** (o serviço pode reexecutar) | Não, mas **pode não executar** em falha |
| **Duração** | Até 1 ano | Até 5 min | Até 5 min |
| **Resposta ao chamador** | Assíncrona (ARN da execução) | Assíncrona | **Resposta imediata** com a saída |
| **Histórico** | **Persistente (90 dias)** | **Só em CloudWatch Logs** | **Só em CloudWatch Logs** |
| **Idempotência exigida** | Moderada (retries/redrive) | **Obrigatória** | **Obrigatória** (retries do chamador) |
| **Ideal para** | **Críticos/longos** | Alto volume, idempotente | **APIs síncronas** |

> [!warning] Express: projete para idempotência
> No **Express assíncrono**, **um passo pode ser executado mais de uma vez**. Com **efeitos externos** (gravações, cobranças), **use chaves de idempotência** e **escritas condicionais**. Para **garantia exactly-once**, **use Standard**.

## Idempotência: estratégias

| Estratégia | Como |
|---|---|
| **Nome de execução determinístico** | `StartExecution` com **`name`** = **ID de negócio** (`pedido-999`): **chamadas repetidas com a mesma entrada retornam a execução existente** (Standard; **idempotência por nome** por 90 dias) |
| **Chave de idempotência nos serviços** | Passar `$$.Execution.Name` ou o ID do pedido como **chave** em chamadas externas |
| **Escritas condicionais** | `ConditionExpression: attribute_not_exists(...)` |
| **Checar antes de agir** | Verificar se o efeito já ocorreu |
| **Operações naturalmente idempotentes** | "Definir estado" em vez de "incrementar" |
| **Compensações idempotentes** | Rodar duas vezes não causa mal |
| **Deduplicação na entrada** | Evitar execuções duplicadas (SQS FIFO, EventBridge + nome) |

```bash
# Idempotência por nome (Standard): repetir com o mesmo nome e entrada não cria uma nova execução
aws stepfunctions start-execution --state-machine-arn <arn> --name pedido-999 --input '{"pedido_id":999}'
```

> [!tip] O nome da execução como chave de idempotência
> Em **Standard**, iniciar duas execuções com **o mesmo `name` e a mesma entrada** **não** cria duplicata (devolve a **existente**). Use **IDs de negócio** como nome para **proteger** contra **disparos duplicados** (eventos at-least-once do EventBridge/SQS).

## Padrões de confiabilidade

| Padrão | Descrição |
|---|---|
| **Retry com backoff e jitter** | Tolerar falhas transitórias |
| **Circuit breaker** (leve) | Contador de falhas em DynamoDB; **Choice** que **desvia** quando o serviço está degradado |
| **Dead-letter para execuções** | Falhas finais → **SQS/ticket** com `execution_id` e erro |
| **Timeout em tudo** | Nada fica pendurado |
| **Compensação (saga)** | Consistência sem transação global |
| **Redrive** | Retomada sem refazer |
| **Idempotência por nome** | Evita duplicatas |
| **Máquinas aninhadas** | Isolar falhas e reaproveitar |
| **Heartbeats** | Detectar workers mortos |
| **Observabilidade** | Alarmes em falhas/timeouts; logs; X-Ray |
| **Execuções "caixa de entrada"** | SQS na frente com **controle de concorrência** |
| **Back-pressure** | Limitar `MaxConcurrency` em Map para proteger dependências |

## Exemplo prático: pipeline robusto com compensação e redrive

1. **Início idempotente**: o evento `PedidoCriado` inicia a máquina com **nome = `pedido-<id>`**.
2. **Cobrança** com **Retry** (3 tentativas, backoff 2, jitter) **apenas para erros transitórios** e **Catch** específico (`PagamentoRecusado` → cancela; `States.ALL` → compensa e notifica).
3. **Reserva de estoque** e **cobrança** têm **compensações idempotentes** (`libera-estoque`, `estorna`), ordenadas **inversamente**.
4. **Emissão de nota** (efeito **difícil de desfazer**) ocorre **por último**.
5. **Timeouts**: 30 s nas Lambdas; 48 h na aprovação humana (com `Catch` de escalonamento).
6. **Falha final** → **Fail** com erro semântico + **SQS "execuções com falha"** (ID, causa) + alarme.
7. Após **corrigir um bug** de integração, o time executa **redrive** das execuções **FAILED** das últimas 24 h; **só o passo que falhou** (e seguintes) rodam.
8. **Painel**: `ExecutionsFailed`, `ExecutionsTimedOut`, duração, **falhas por estado**.

## Troubleshooting

| Sintoma | Causa provável | Como resolver |
|---|---|---|
| **Retry não acontece** | `ErrorEquals` não casa com o erro real | Ver o nome do erro no histórico; ajustar |
| **Retry demora demais/custa** | `MaxAttempts`/backoff altos; erros permanentes retentados | Limitar; separar permanentes |
| **Catch perde o contexto** | Sem `ResultPath` | `ResultPath: "$.erro"` |
| **Execução pendurada por dias** | Callback sem timeout; token perdido | `TimeoutSeconds`; reemissão; `Catch Timeout` |
| **`States.DataLimitExceeded` no Catch** | Payload grande | Reduzir; guardar no S3 |
| **Compensação falhou** | Efeito parcial; permissões | Retry; alerta; correção manual |
| **Cobrança duplicada** | Retry sem idempotência | Chave de idempotência; checagem |
| **Redrive indisponível** | Execução > 14 dias; tipo Express; sem falha elegível | Reexecutar manualmente |
| **Redrive falha de novo** | Causa raiz não corrigida | Corrigir; validar estado |
| **Execuções duplicadas** | Início at-least-once sem nome determinístico | Nome = ID de negócio |
| **Express com efeitos duplicados** | At-least-once | Idempotência; ou Standard |
| **`States.Permissions`** | Role sem permissão | Corrigir IAM (não retentar) |
| **Fluxo trava em Choice** | Sem `Default` | Adicionar `Default` |

## Erros comuns e armadilhas

- **Retentar erros permanentes** (permissão, validação).
- **Retry/Catch sem `ResultPath`**, perdendo contexto.
- **Sem `TimeoutSeconds`** (especialmente em callbacks).
- **Operações não idempotentes** com retries/redrive.
- **Compensações não idempotentes** ou sem tratamento de falha.
- **Passo irreversível no meio do fluxo.**
- **`States.ALL` antes dos erros específicos.**
- **Esperar exactly-once em Express.**

## 🧩 Quiz de Fixação

1. Qual a diferença entre Retry e Catch?
2. Por que usar `ResultPath` no Catch?
3. O que é uma saga e como se implementa no Step Functions?
4. O que o redrive faz e em que tipo de workflow está disponível?
5. Qual a semântica de execução do Express assíncrono?
6. Como o nome da execução ajuda na idempotência?

**Respostas:**
1) Retry tenta de novo o mesmo estado com backoff para erros transitórios; Catch desvia para outro estado quando o erro persiste (ou é de um tipo capturado), permitindo compensação ou tratamento.
2) Para anexar as informações do erro à entrada em vez de substituí-la, preservando o contexto (como IDs) necessário nos estados seguintes.
3) Uma sequência de passos com ações compensatórias que desfazem os anteriores em ordem inversa em caso de falha; implementa-se com Catch desviando para estados de compensação idempotentes.
4) Retoma uma execução Standard falha, com timeout ou abortada a partir do estado que falhou, sem refazer os passos concluídos (e, em Map distribuído, só os itens falhos), dentro de uma janela de 14 dias.
5) At-least-once: um passo pode ser executado mais de uma vez, exigindo idempotência.
6) Em Standard, iniciar execuções com o mesmo nome e entrada devolve a execução existente em vez de criar duplicatas, protegendo contra disparos repetidos.
