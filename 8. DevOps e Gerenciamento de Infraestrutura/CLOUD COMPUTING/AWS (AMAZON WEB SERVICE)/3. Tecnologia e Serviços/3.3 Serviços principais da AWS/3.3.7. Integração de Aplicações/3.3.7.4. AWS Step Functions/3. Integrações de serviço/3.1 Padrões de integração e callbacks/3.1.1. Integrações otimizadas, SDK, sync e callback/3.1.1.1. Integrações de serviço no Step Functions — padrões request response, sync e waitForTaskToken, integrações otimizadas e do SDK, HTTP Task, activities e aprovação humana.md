### Integrações de serviço no Step Functions — padrões request response, sync e waitForTaskToken, integrações otimizadas e do SDK, HTTP Task, activities e aprovação humana

> [!warning] Aviso
> Serviços com integração otimizada, parâmetros por serviço, suporte a padrões (`.sync`, `.waitForTaskToken`) e limites mudam. Os exemplos aqui são referências de estudo; confirme na documentação. As definições e comandos **não foram executados**.

O grande ganho do Step Functions é **chamar serviços diretamente do fluxo**, **sem escrever funções de cola**. Cada estado **Task** aponta para um **recurso** (`Resource`) que define **qual serviço** e **qual padrão de interação** usar: **disparar e seguir** (*request response*), **disparar e esperar o término** (`.sync`) ou **disparar e pausar até um callback** (`.waitForTaskToken`). Esta folha cobre **os três padrões**, as **integrações otimizadas** (Lambda, Batch, ECS, Glue, SageMaker, DynamoDB, SNS, SQS, EventBridge e outras), as **integrações com o AWS SDK** (200+ serviços), a **HTTP Task** (APIs externas), as **activities** (workers externos), o **padrão de aprovação humana**, as **permissões** necessárias e os **erros típicos**.

**Analogia:** o maestro pode **dar um sinal e seguir** (o músico toca em paralelo, "request response"), **dar o sinal e esperar o músico terminar** (`.sync`) ou **entregar uma senha e só continuar quando o músico a devolver** (`.waitForTaskToken`: por exemplo, quando alguém **de fora da orquestra** precisa dar o "ok").

---

## O formato do `Resource`

```
 arn:aws:states:::<serviço>:<ação>[.sync | .waitForTaskToken]       ← integração OTIMIZADA
 arn:aws:states:::aws-sdk:<serviço>:<ação>[.waitForTaskToken]       ← integração com o AWS SDK
 arn:aws:states:::http:invoke                                       ← HTTP Task
 arn:aws:states:::states:startExecution[.sync[:2]]                  ← máquina aninhada
 arn:aws:states:<região>:<conta>:activity:<nome>                    ← activity (worker externo)
```

| Parte | Significado |
|---|---|
| **`arn:aws:states:::`** | Prefixo de **integração de serviço** |
| **`lambda:invoke`**, **`dynamodb:putItem`**, **`sns:publish`**, **`glue:startJobRun`**, **`batch:submitJob`** | **Serviço e ação** |
| **`.sync`** | **Run a Job**: espera a conclusão |
| **`.waitForTaskToken`** | **Callback**: pausa até `SendTaskSuccess/Failure` |
| **`aws-sdk:`** | **Qualquer API** de qualquer serviço suportado pelo SDK |

## Os três padrões de integração

### 1. Request Response (padrão)

**Chama o serviço e segue** assim que a API **responde** (a resposta HTTP), **sem esperar** o trabalho assíncrono terminar.

```json
"PublicaAviso": {
  "Type": "Task",
  "Resource": "arn:aws:states:::sns:publish",
  "Parameters": {"TopicArn": "arn:aws:sns:us-east-1:123456789012:avisos", "Message.$": "$.mensagem"},
  "ResultPath": null,
  "Next": "Proximo"
}
```

| Característica | Detalhe |
|---|---|
| **Comportamento** | Executa a **chamada de API** e **continua** com a resposta |
| **Quando usar** | **Operações rápidas e síncronas** (gravar no DynamoDB, publicar no SNS/SQS, `Invoke` de Lambda **síncrona**) |
| **Disponível em** | **Standard e Express** |

### 2. Run a Job (`.sync`)

**Inicia um job** e **aguarda a conclusão**; o Step Functions **monitora** (por eventos/polling interno) e só avança quando o job **termina** (sucesso ou falha).

```json
"RodaGlue": {
  "Type": "Task",
  "Resource": "arn:aws:states:::glue:startJobRun.sync",
  "Parameters": {"JobName": "etl-pedidos", "Arguments": {"--dia.$": "$.dia"}},
  "TimeoutSeconds": 7200,
  "ResultPath": "$.glue",
  "Next": "ValidaQualidade"
}
```

| Serviços com `.sync` (exemplos) | Observação |
|---|---|
| **AWS Batch** (`batch:submitJob.sync`) | Espera o job |
| **Amazon ECS/Fargate** (`ecs:runTask.sync`) | Espera a tarefa |
| **AWS Glue** (`glue:startJobRun.sync`) | Espera o job de ETL |
| **Amazon SageMaker** (`sagemaker:createTrainingJob.sync`, `createProcessingJob.sync`, `createTransformJob.sync`) | Treino/processamento |
| **Amazon EMR / EMR on EKS / EMR Serverless** | Clusters/jobs |
| **AWS CodeBuild** (`codebuild:startBuild.sync`) | Builds |
| **Athena** (`athena:startQueryExecution.sync`) | Consultas |
| **Step Functions** (`states:startExecution.sync:2`) | **Máquina aninhada** |
| **Amazon EKS** (`eks:runJob.sync`) | Jobs no Kubernetes |
| **Redshift Data API**, **Bedrock** (jobs), **Lambda?** (use `invoke`, que já é síncrono) | Conforme suporte |

| Característica | Detalhe |
|---|---|
| **Disponível em** | **Somente Standard** |
| **Custo da espera** | Apenas **transições** (sem cobrança de tempo de espera) |
| **Falhas** | Falha do job ⇒ erro no estado (`States.TaskFailed`) tratável por `Retry`/`Catch` |
| **Permissões extras** | A **role** precisa de permissão para **gerenciar regras gerenciadas do EventBridge** (`events:PutTargets/PutRule/DescribeRule`) que o serviço usa para monitorar |
| **Vantagem** | **Sem polling manual**, **sem Lambda de verificação** |

> [!tip] `.sync` elimina o clássico "Wait + Choice + Task de polling"
> Antes, era comum: **iniciar job → Wait 30 s → consultar status → Choice → voltar ao Wait**. Com `.sync`, **uma única Task** faz tudo: **menos estados**, **menos transições (custo)** e **menos código**.

### 3. Wait for Callback (`.waitForTaskToken`)

O Step Functions **gera um token**, **entrega-o ao serviço/sistema externo** e **pausa** o estado **até** alguém chamar **`SendTaskSuccess`**, **`SendTaskFailure`** ou **`SendTaskHeartbeat`** com **esse token**.

```json
"AguardaAprovacao": {
  "Type": "Task",
  "Resource": "arn:aws:states:::sqs:sendMessage.waitForTaskToken",
  "Parameters": {
    "QueueUrl": "https://sqs.us-east-1.amazonaws.com/123456789012/aprovacoes",
    "MessageBody": {"pedido_id.$": "$.pedido_id", "valor.$": "$.valor", "token.$": "$$.Task.Token"}
  },
  "TimeoutSeconds": 172800,
  "Next": "Segue",
  "Catch": [{"ErrorEquals": ["States.Timeout"], "Next": "EscalaParaDiretor"}]
}
```

```bash
# O sistema externo (ou humano via app/Lambda) responde com o token recebido
aws stepfunctions send-task-success --task-token "<token>" \
  --task-output '{"aprovado":true,"aprovador":"ana"}'
aws stepfunctions send-task-failure --task-token "<token>" --error "Recusado" --cause "Valor acima da alçada"
aws stepfunctions send-task-heartbeat --task-token "<token>"
```

| Característica | Detalhe |
|---|---|
| **Disponível em** | **Somente Standard** |
| **O token** | `$$.Task.Token` (**guarde-o** onde o respondente possa acessá-lo) |
| **Duração** | Até **1 ano** (ou o `TimeoutSeconds`) |
| **Serviços que aceitam o token no parâmetro** | **Lambda, SQS, SNS, EventBridge `PutEvents`, DynamoDB, ECS, Batch, SageMaker, Glue, API Gateway, Step Functions** e **qualquer API via SDK** (você **injeta o token** em algum campo/mensagem) |
| **Cobrança** | **Transições** apenas (a espera é grátis) |
| **Heartbeat** | `HeartbeatSeconds` exige **batimentos** periódicos para tarefas longas (detecta workers mortos) |
| **Segurança do token** | O token é um **segredo de capacidade**: **quem o tem pode concluir a tarefa** |

> [!warning] Trate o task token como credencial
> **Qualquer pessoa/sistema com o token** pode **aprovar ou falhar** a tarefa. **Não o exponha** em URLs públicas ou logs; entregue-o por **canais autenticados** e, em aprovações por link (e-mail), **use um intermediário** (API Gateway + Lambda com **autorização**) que **valide quem aprova** antes de chamar `SendTaskSuccess`.

## Integrações com o AWS SDK

As integrações com o **SDK** permitem **chamar praticamente qualquer API** de **mais de 200 serviços** (milhares de ações), **sem Lambda**.

```json
"CriaThumbnailRekognition": {
  "Type": "Task",
  "Resource": "arn:aws:states:::aws-sdk:rekognition:detectLabels",
  "Parameters": {"Image": {"S3Object": {"Bucket.$": "$.bucket", "Name.$": "$.chave"}}, "MaxLabels": 10},
  "ResultSelector": {"rotulos.$": "$.Labels[*].Name"},
  "ResultPath": "$.analise",
  "Next": "Segue"
},
"LigaInstancia": {
  "Type": "Task",
  "Resource": "arn:aws:states:::aws-sdk:ec2:startInstances",
  "Parameters": {"InstanceIds.$": "$.instancias"},
  "Next": "Aguarda"
}
```

| Aspecto | Detalhe |
|---|---|
| **Nome do recurso** | `aws-sdk:<serviço em minúsculas>:<ação em camelCase>` |
| **Parâmetros** | Os da **API do serviço** (nomes em **PascalCase** como na API) |
| **Resposta** | **Chaves em PascalCase** (ex.: `$.Labels`) |
| **Padrões** | **Request Response** (e `.waitForTaskToken`); **sem `.sync`** nativo (use **polling** via `Wait`/`Choice` ou integrações otimizadas) |
| **Permissões** | A **role** da máquina precisa das **ações IAM** correspondentes (ex.: `rekognition:DetectLabels`) |
| **Vantagem** | **Cobertura quase total** de serviços; **menos Lambdas** |

> [!tip] O SDK é a "faca suíça" para automação
> **Runbooks operacionais** (ligar/desligar instâncias, criar snapshots, alterar parâmetros, aplicar tags) viram **fluxos sem uma linha de código**, com **retries, erros e histórico** inclusos.

### Optimizado vs SDK: qual escolher

| Critério | **Otimizada** | **SDK** |
|---|---|---|
| **`.sync` / callback** | **Sim** (em serviços aplicáveis) | Limitado (callback sim; `.sync` não) |
| **Parâmetros** | Específicos e **documentados no Step Functions** | **Da API do serviço** |
| **Cobertura** | Dezenas de serviços | **200+ serviços** |
| **Quando preferir** | **Orquestrar jobs longos** e serviços centrais | **Qualquer API** sem integração otimizada |

## HTTP Task: chamar APIs externas

A **HTTP Task** chama **endpoints HTTPS públicos** (SaaS, APIs de parceiros) **diretamente do fluxo**, com **autenticação** gerenciada por uma **EventBridge Connection** (API Key, Basic, OAuth).

```json
"ConsultaCEP": {
  "Type": "Task",
  "Resource": "arn:aws:states:::http:invoke",
  "Parameters": {
    "ApiEndpoint": "https://api.parceiro.com/v1/enderecos",
    "Method": "GET",
    "Authentication": {"ConnectionArn": "arn:aws:events:us-east-1:123456789012:connection/parceiro/abc123"},
    "Headers": {"Accept": "application/json"},
    "QueryParameters": {"cep.$": "$.cep"}
  },
  "Retry": [{"ErrorEquals": ["States.Http.StatusCode.429","States.Http.StatusCode.503"], "IntervalSeconds": 3, "MaxAttempts": 5, "BackoffRate": 2}],
  "ResultSelector": {"endereco.$": "$.ResponseBody"},
  "Next": "Segue"
}
```

| Aspecto | Detalhe |
|---|---|
| **Autenticação** | **Connection** do EventBridge (segredos no **Secrets Manager**) |
| **Erros** | `States.Http.StatusCode.<código>` (ex.: `404`, `429`) para **Retry/Catch** |
| **Limites** | Timeout e tamanho de resposta limitados; endpoints **públicos** |
| **Quando usar** | Chamadas **simples** a APIs REST; para lógica complexa, **Lambda** |

## Máquinas aninhadas (`states:startExecution`)

| Padrão | Sufixo | Uso |
|---|---|---|
| **Fire-and-forget** | (nenhum) | Inicia **outra máquina** e **segue** |
| **Aguardar o término** | **`.sync:2`** | **Espera** a execução filha e recebe a **saída como JSON** |
| **Callback** | `.waitForTaskToken` | A filha chama `SendTaskSuccess` |

| Uso | Benefício |
|---|---|
| **Modularizar** fluxos | Reuso de **sub-fluxos** |
| **Contornar o limite de 25.000 eventos** de histórico | Cada filha tem **seu histórico** |
| **Standard por fora, Express por dentro** | Economia em trechos de alto volume (**Express** não suporta `.sync`; use **`StartSyncExecution`** via SDK para Express síncrono) |
| **Isolamento de falhas** | Equipes donas de sub-fluxos |

```json
"ProcessaLote": {
  "Type": "Task",
  "Resource": "arn:aws:states:::states:startExecution.sync:2",
  "Parameters": {"StateMachineArn": "arn:aws:states:us-east-1:123456789012:stateMachine:processa-lote",
                 "Input": {"lote.$": "$.lote", "AWS_STEP_FUNCTIONS_STARTED_BY_EXECUTION_ID.$": "$$.Execution.Id"}},
  "OutputPath": "$.Output",
  "Next": "Consolida"
}
```

## Activities (workers externos)

Uma **activity** representa **trabalho executado fora da AWS gerenciada** (por exemplo, **um servidor on-premises**, **um worker próprio**): o worker **faz polling** do Step Functions (`GetActivityTask`), **executa** e **responde** (`SendTaskSuccess/Failure`).

| Aspecto | Detalhe |
|---|---|
| **Modelo** | **Pull**: o worker busca tarefas |
| **Uso** | **Sistemas legados**, **workers em redes privadas**, **máquinas especializadas** |
| **Segurança** | Credenciais **IAM** do worker; sem abrir portas de entrada |
| **Heartbeat** | `HeartbeatSeconds` detecta worker morto |
| **Disponível em** | **Standard** |
| **Alternativa moderna** | **Callback (`.waitForTaskToken`)** com SQS (o worker consome a fila e responde com o token) |

> [!tip] SQS + `.waitForTaskToken` costuma ser melhor que activities
> A fila **dá buffer, escala e DLQ**; os workers **não precisam de polling especial do Step Functions**, e o token vai **na mensagem**. Activities continuam úteis para **workers legados** que já usam esse modelo.

## Aprovação humana: padrão completo

```
 Step Functions ─(1)─► SNS/SQS/SES: envia pedido de aprovação (com task token) ─► Aprovador recebe
        ▲                                                                         │
        │                                                               (2) clica em "Aprovar"
        │                                                                         ▼
        └──(4) SendTaskSuccess(token) ◄── Lambda ◄── API Gateway (autenticado) ◄──┘
                                       (3) valida o aprovador e chama a API do Step Functions
```

| Elemento | Prática |
|---|---|
| **Envio do pedido** | **SNS/SES/Slack** com **link** para uma **página/endpoint** que **recebe o token** |
| **Endpoint de resposta** | **API Gateway + Lambda** **autenticados** (Cognito/SSO), que **valida a identidade e a alçada** |
| **Token** | **Guardado** (DynamoDB) e **referenciado por ID**, **não exposto** em URL pública |
| **Timeout** | `TimeoutSeconds` + `Catch States.Timeout` → **escalonar** ou **cancelar** |
| **Recusa** | `SendTaskFailure` com `Error`/`Cause` → `Catch` → fluxo alternativo |
| **Auditoria** | Histórico da execução + logs do endpoint |
| **Lembretes** | `Parallel` com ramo de **Wait** que envia **lembretes** |

```json
{
  "StartAt": "PedeAprovacao",
  "States": {
    "PedeAprovacao": {
      "Type": "Parallel",
      "Branches": [
        {"StartAt": "AguardaDecisao", "States": {"AguardaDecisao": {
            "Type": "Task", "Resource": "arn:aws:states:::lambda:invoke.waitForTaskToken",
            "Parameters": {"FunctionName": "envia-pedido-aprovacao", "Payload": {"pedido.$": "$", "token.$": "$$.Task.Token"}},
            "End": true}}},
        {"StartAt": "AguardaLembrete", "States": {"AguardaLembrete": {"Type": "Wait", "Seconds": 86400, "Next": "EnviaLembrete"},
                                                  "EnviaLembrete": {"Type": "Task", "Resource": "arn:aws:states:::sns:publish",
                                                                    "Parameters": {"TopicArn": "arn:aws:sns:us-east-1:123456789012:lembretes", "Message": "Aprovação pendente"},
                                                                    "End": true}}}
      ],
      "Next": "Segue"
    },
    "Segue": {"Type": "Succeed"}
  }
}
```

> [!warning] Em `Parallel`, o ramo mais lento define o fim
> No exemplo acima, o ramo de **lembrete termina em 24 h** enquanto a aprovação **pode levar dias**; o `Parallel` **só conclui quando todos os ramos terminam**. Para **"lembrar enquanto espera"**, use **um laço** (Wait + Task + Choice) **ou** **EventBridge Scheduler** para os lembretes, e mantenha o estado de callback **no fluxo principal**.

## Permissões e segurança das integrações

| Elemento | Detalhe |
|---|---|
| **Role de execução da máquina** | O Step Functions **assume** esta role para **chamar serviços**; **permissões mínimas por ação e recurso** |
| **`.sync`** | Exige permissões do **EventBridge** (`events:PutTargets`, `PutRule`, `DescribeRule`) para **regras gerenciadas** |
| **Lambda** | `lambda:InvokeFunction` no ARN específico |
| **SDK integrations** | Ações IAM do serviço (`s3:PutObject`, `ec2:StartInstances`…) |
| **Callback** | O **respondente** precisa de `states:SendTaskSuccess/Failure/Heartbeat` |
| **`iam:PassRole`** | Se a Task **passa uma role** a outro serviço (Batch, SageMaker, ECS) |
| **Entre contas** | **Roles** com *trust* e chamadas a recursos de outra conta (`Credentials: {RoleArn}` na Task) |
| **Criptografia** | KMS nos serviços de destino; payloads no S3 com SSE-KMS |

```json
"Credentials": {"RoleArn": "arn:aws:iam::999999999999:role/AcessoFluxoEntreContas"}
```

> [!tip] Credenciais por Task para entre contas
> O campo **`Credentials.RoleArn`** na Task permite que **uma máquina** chame **serviços em outra conta**, assumindo **uma role específica** apenas **naquele passo**: **menor privilégio** e **sem Lambda intermediária**.

## Boas práticas de integração

| Prática | Motivo |
|---|---|
| **Preferir integração direta a Lambda** | Menos código/custo |
| **`.sync` em vez de polling** | Menos transições |
| **`.waitForTaskToken` para humanos e sistemas externos** | Esperas longas e baratas |
| **`TimeoutSeconds` e `HeartbeatSeconds`** | Evitar execuções penduradas |
| **Tratamento de erros por serviço** (`Retry` para throttling/5xx) | Resiliência |
| **Idempotência nas ações com efeito** | Retries seguros |
| **Tokens protegidos** | Segurança |
| **Roles de mínimo privilégio** | Segurança |
| **Payload enxuto** (`ResultSelector`/`ResultPath: null`) | Limite de 256 KB |
| **Máquinas aninhadas para modularizar** | Histórico e reuso |
| **Testar com `TestState`** | Ciclo rápido |

## Exemplo prático: ETL com aprovação e integrações diretas

1. **Início** por EventBridge (arquivo no S3) → máquina **Standard**.
2. **`aws-sdk:s3:headObject`** verifica o **tamanho/formato** do arquivo (sem Lambda).
3. **`glue:startJobRun.sync`** executa o **ETL** e **espera** (sem polling).
4. **`athena:startQueryExecution.sync`** roda **verificações de qualidade** em SQL.
5. **Choice**: se **anomalias** ⇒ **aprovação humana** via **`sqs:sendMessage.waitForTaskToken`** (equipe de dados aprova em até 48 h; `Catch Timeout` ⇒ escala).
6. **`states:startExecution.sync:2`** chama a máquina de **publicação** (aninhada), que **atualiza tabelas** e **invalida caches**.
7. **`sns:publish`** avisa o resultado; **`ResultPath: null`** mantém o payload enxuto.
8. **`Catch States.ALL`** → **notificação de falha** + **abertura de ticket** (HTTP Task).
9. **Tudo** visível no **histórico da execução**, com **logs** e **alarmes**.

## Troubleshooting

| Sintoma | Causa provável | Como resolver |
|---|---|---|
| **`AccessDeniedException` na Task** | Role de execução sem a ação IAM | Adicionar a permissão no ARN específico |
| **`.sync` nunca conclui** | Faltam permissões do EventBridge; job travado | `events:*` necessários; `TimeoutSeconds`; investigar o job |
| **Callback não retoma** | Token errado/expirado; respondente sem permissão; já respondido | Verificar token; `states:SendTask*`; timeouts |
| **`States.Timeout`** | Tarefa mais longa que `TimeoutSeconds` | Ajustar; heartbeat; otimizar |
| **`States.HeartbeatTimeout`** | Worker parou de enviar batimentos | Worker vivo; `HeartbeatSeconds` |
| **`States.TaskFailed` em `.sync`** | Job falhou | Ver detalhes do job; `Catch` |
| **SDK: parâmetros inválidos** | Nome/caixa dos campos fora do padrão da API | Seguir a documentação da API (PascalCase) |
| **Resposta SDK com chaves inesperadas** | PascalCase | Ajustar caminhos (`$.Item`, `$.Labels`) |
| **HTTP Task retorna 401/403** | Connection/credenciais | Atualizar a connection |
| **HTTP Task falha por tamanho/timeout** | Limites da HTTP Task | Usar Lambda/endpoint mais rápido |
| **Express recusa `.sync`/callback** | Express só suporta Request Response | Usar Standard ou `StartSyncExecution` |
| **Activity sem workers** | Worker offline/sem credenciais | Subir workers; heartbeat; alarmes |
| **Entre contas falha** | Role/trust da outra conta | `Credentials.RoleArn`; trust policy |
| **Payload cresce a cada Task** | `ResultPath` anexando tudo | `ResultSelector` e `ResultPath: null` |

## Erros comuns e armadilhas

- **Lambdas "de cola"** onde existe integração direta.
- **Polling manual** em vez de `.sync`.
- **Expor o task token** em canais públicos.
- **Esquecer `TimeoutSeconds`/`HeartbeatSeconds`** em callbacks e activities.
- **Usar `.sync` ou callback em workflows Express** (não suportado).
- **Role de execução muito ampla** (`*:*`).
- **Não tratar `429/5xx`** em HTTP Task e chamadas SDK.
- **Parallel esperando o ramo mais lento** quando o objetivo era "lembrar".

1. Qual a diferença entre Request Response, `.sync` e `.waitForTaskToken`?
2. Por que `.sync` é melhor que polling manual?
3. Para que serve o task token e como protegê-lo?
4. Quais as vantagens das integrações com o AWS SDK?
5. Em quais tipos de workflow `.sync` e callback estão disponíveis?
6. Como uma máquina pode chamar serviços em outra conta?

**Respostas:**
1) Request Response chama e segue; `.sync` inicia um job e espera a conclusão; `.waitForTaskToken` pausa até um callback externo com o token.
2) Porque uma única Task espera o término do job, eliminando estados de Wait, consulta e Choice, com menos transições (custo) e menos código.
3) Identifica a tarefa pausada para ser concluída por SendTaskSuccess/Failure; deve ser tratado como segredo, entregue por canais autenticados e validado por um intermediário que confirme quem responde.
4) Chamar qualquer API de mais de 200 serviços diretamente do fluxo, sem Lambda, com retries, erros e histórico nativos.
5) Somente em workflows Standard; o Express suporta apenas Request Response.
6) Usando o campo Credentials.RoleArn na Task, assumindo uma role com trust adequada na outra conta.
