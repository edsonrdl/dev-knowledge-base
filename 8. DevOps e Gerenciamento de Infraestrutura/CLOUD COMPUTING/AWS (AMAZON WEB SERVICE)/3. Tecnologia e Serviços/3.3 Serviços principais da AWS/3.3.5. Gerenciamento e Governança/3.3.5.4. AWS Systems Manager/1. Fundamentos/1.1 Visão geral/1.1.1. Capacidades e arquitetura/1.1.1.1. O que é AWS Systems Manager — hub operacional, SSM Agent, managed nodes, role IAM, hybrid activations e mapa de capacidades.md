### O que é AWS Systems Manager — hub operacional, SSM Agent, managed nodes, role IAM, hybrid activations e mapa de capacidades

> [!warning] Aviso
> Nomes de capacidades, limites, preços, camadas (tiers) e requisitos do agente mudam, e a AWS reorganiza o Systems Manager com frequência. Os números aqui são referências de estudo; confirme na documentação oficial. Os comandos de CLI são exemplos e **não foram executados**.

O **AWS Systems Manager (SSM)** é o **centro de operações** da AWS para **ver e controlar** sua frota de servidores e recursos. Com ele você **acessa instâncias sem abrir porta SSH**, **executa comandos em centenas de máquinas ao mesmo tempo**, **aplica patches**, **guarda configurações e segredos**, **automatiza rotinas operacionais** e **inventaria** software instalado, tudo de forma **centralizada, auditada e sem precisar de chaves SSH nem bastion hosts**.

Ele funciona para **instâncias EC2**, para **servidores locais (on-premises)**, para **máquinas de outras nuvens** e até para **dispositivos de borda**: todos viram **managed nodes** (nós gerenciados).

**Analogia:** o Systems Manager é a **central de manutenção de um grande condomínio de prédios**. Em vez de o zelador andar de apartamento em apartamento com um molho de chaves (SSH), a central tem **um canal seguro e auditado** com um funcionário de plantão em cada prédio (o **SSM Agent**), por onde envia ordens ("troque a lâmpada em todos os prédios"), consulta o que há em cada um (inventário), agenda manutenções (maintenance windows) e guarda o livro de configurações do condomínio (Parameter Store).

---

## Por que usar o Systems Manager

| Problema clássico | Solução com o SSM |
|---|---|
| Abrir a porta 22/3389 para administrar servidores | **Session Manager**: acesso por navegador/CLI sem porta aberta |
| Distribuir e rotacionar chaves SSH | Acesso por **IAM**, sem chaves |
| Rodar um comando em 500 servidores | **Run Command** com alvo por tag |
| Servidores sem patch | **Patch Manager** com baselines e janelas |
| Configurações e segredos espalhados em arquivos | **Parameter Store** hierárquico |
| Rotinas manuais repetitivas | **Automation** com runbooks |
| Não saber o que está instalado onde | **Inventory** |
| Auditar quem fez o quê no servidor | Logs de sessão em **S3/CloudWatch Logs** e eventos no CloudTrail |
| Gerenciar servidores fora da AWS | **Hybrid activations** |

## Arquitetura básica

```
 Você (console / CLI / API / CI)
          │  IAM + MFA + CloudTrail
          ▼
 ┌──────────────────────────┐
 │   AWS SYSTEMS MANAGER    │  (serviço regional)
 └─────────────┬────────────┘
               │ canal HTTPS de saída (porta 443)
               ▼
 ┌─────────────────────────────────────────────────┐
 │  Managed node (EC2 / on-premises / outra nuvem)  │
 │   ┌───────────────┐                             │
 │   │  SSM Agent    │ ◄── role/perfil IAM         │
 │   └───────────────┘     (AmazonSSMManagedInstanceCore)
 └─────────────────────────────────────────────────┘
```

O ponto-chave: a comunicação é **iniciada pelo agente para fora** (HTTPS 443 até os endpoints do SSM). **Nenhuma porta de entrada** precisa ser aberta no servidor, o que reduz muito a superfície de ataque.

## Requisitos para uma instância virar managed node

| Requisito | Detalhe |
|---|---|
| **SSM Agent** instalado e rodando | Vem **pré-instalado** em muitas AMIs da AWS (Amazon Linux, Windows Server, Ubuntu recentes) |
| **Role/Instance profile IAM** | Normalmente a política gerenciada **`AmazonSSMManagedInstanceCore`** |
| **Conectividade** | Saída HTTPS para os endpoints do SSM: via Internet/NAT **ou** **VPC endpoints** |
| **Sistema operacional suportado** | Linux, Windows e macOS (conforme a versão) |
| **Região** | O SSM é **regional**: o nó aparece na região onde está registrado |

### VPC endpoints para sub-redes privadas

Em sub-redes **sem acesso à Internet**, crie **endpoints de interface** para que o agente alcance o serviço:

| Endpoint | Para quê |
|---|---|
| `com.amazonaws.<região>.ssm` | API principal do Systems Manager |
| `com.amazonaws.<região>.ssmmessages` | Canal do Session Manager |
| `com.amazonaws.<região>.ec2messages` | Entrega de comandos ao agente |
| `com.amazonaws.<região>.s3` (gateway) | Download de componentes e logs, quando aplicável |
| `com.amazonaws.<região>.logs` | Envio de logs ao CloudWatch, se usado |
| `com.amazonaws.<região>.kms` | Se houver criptografia com chave própria |

> [!warning] "A instância não aparece no Fleet Manager"
> É o problema mais comum. Causas típicas: **perfil IAM ausente**, **agente parado**, **sem rota/endpoint** para o SSM, ou **horário do servidor muito desajustado**. A folha de operação traz o roteiro de diagnóstico.

```bash
# A instância está registrada como managed node?
aws ssm describe-instance-information \
  --query 'InstanceInformationList[].[InstanceId,PingStatus,PlatformName,AgentVersion]' \
  --output table

# Anexa o perfil com a política do SSM a uma instância existente
aws ec2 associate-iam-instance-profile \
  --instance-id i-0123456789abcdef0 \
  --iam-instance-profile Name=PerfilSSM
```

## O mapa de capacidades

O Systems Manager é uma **família de ferramentas**. Os grupos principais:

| Grupo | Capacidades | Para que servem |
|---|---|---|
| **Gerenciamento de nós** | Fleet Manager, Session Manager, Run Command, Patch Manager, State Manager, Inventory, Distributor, Compliance, Hybrid Activations | Controlar e manter a frota |
| **Configuração de aplicação** | **Parameter Store**, AppConfig | Configurações, flags e segredos |
| **Mudança e automação** | **Automation**, Change Manager, Maintenance Windows, Change Calendar | Rotinas e mudanças controladas |
| **Operações e incidentes** | OpsCenter, Explorer, Incident Manager | Itens operacionais, painéis e resposta a incidentes |
| **Aplicações e recursos** | Application Manager, Resource Groups | Visão por aplicação |
| **Acesso just-in-time** | Just-in-time node access | Acesso temporário aprovado |

```
              ┌──────────────────── SYSTEMS MANAGER ───────────────────┐
   Nós        │ Session Mgr │ Run Command │ Patch Mgr │ State Mgr │ Inv │
   Config     │ Parameter Store │ AppConfig                              │
   Mudança    │ Automation │ Change Manager │ Maintenance Windows        │
   Operações  │ OpsCenter │ Explorer │ Incident Manager                  │
              └─────────────────────────────────────────────────────────┘
```

Cada capacidade ganha uma folha própria ou uma seção neste guia. Aqui o objetivo é o **panorama**.

## Documentos SSM (SSM Documents)

Quase tudo no Systems Manager é feito por **documentos**: arquivos **JSON ou YAML** que descrevem **o que executar**.

| Tipo de documento | Uso | Exemplos |
|---|---|---|
| **Command** | Run Command e State Manager | `AWS-RunShellScript`, `AWS-RunPowerShellScript`, `AWS-ConfigureAWSPackage` |
| **Automation** (runbook) | Automation | `AWS-RestartEC2Instance`, `AWS-CreateImage` |
| **Session** | Session Manager | `SSM-SessionManagerRunShell` |
| **Policy** | State Manager/Inventory | Coleta de inventário |
| **Package** | Distributor | Instalação de pacotes |
| **ChangeCalendar** | Change Calendar | Janelas abertas e fechadas |

```yaml
# Exemplo de documento Command (YAML)
schemaVersion: '2.2'
description: Atualiza o pacote nginx e reinicia o serviço
parameters:
  versao:
    type: String
    default: latest
mainSteps:
  - action: aws:runShellScript
    name: atualizaNginx
    inputs:
      runCommand:
        - sudo yum update -y nginx
        - sudo systemctl restart nginx
```

> [!tip] Documentos da AWS e os seus
> A AWS fornece centenas de documentos prontos (prefixo `AWS-`). Crie os seus para padronizar rotinas, **versionando-os** em IaC e compartilhando entre contas quando necessário.

## Alvos: como escolher onde executar

Quase toda ação do SSM aceita **alvos** (targets):

| Forma de alvo | Exemplo | Quando usar |
|---|---|---|
| **IDs de instância** | `i-0abc...`, `mi-0123...` | Poucas máquinas conhecidas |
| **Tags** | `Ambiente=producao`, `Funcao=web` | **Padrão recomendado**: frotas dinâmicas |
| **Resource groups** | Grupo de recursos por tag/pilha | Por aplicação |
| **Todos os nós** | `*` | Inventário e configurações globais |
| **Parâmetros de rate control** | `max-concurrency`, `max-errors` | Controlar o ritmo e interromper em falhas |

```bash
# Roda um comando em todas as instâncias com a tag Funcao=web, 10% por vez
aws ssm send-command \
  --document-name AWS-RunShellScript \
  --targets Key=tag:Funcao,Values=web \
  --parameters 'commands=["uptime"]' \
  --max-concurrency 10% --max-errors 5%
```

> [!tip] Tags como contrato operacional
> Padronize tags (`Ambiente`, `Funcao`, `Dono`, `PatchGroup`). Elas viram o **mecanismo de endereçamento** da frota: sem tags consistentes, o SSM não sabe "quem são os servidores web de produção".

## Servidores fora da AWS: hybrid activations

Para gerenciar máquinas **on-premises ou de outra nuvem**, você cria uma **ativação híbrida**:

1. Cria uma **hybrid activation** (código e ID) e uma **service role** para o SSM.
2. Instala o **SSM Agent** na máquina e a **registra** com o código.
3. A máquina aparece como **managed node** com prefixo **`mi-`** (managed instance).

```bash
aws ssm create-activation \
  --default-instance-name servidor-filial-01 \
  --iam-role AmazonEC2RunCommandRoleForManagedInstances \
  --registration-limit 20 --expiration-date 2026-12-31T00:00:00Z
```

| Aspecto | Observação |
|---|---|
| Cobrança | Nós híbridos usam a **camada avançada** (advanced tier), com custo por nó/hora (confirme os preços) |
| Segurança | O código de ativação é um **segredo**; limite o número de registros e a validade |
| Benefício | Mesmo plano de gestão para toda a frota, dentro e fora da AWS |

---

## Camadas: padrão e avançada

| Recurso | Camada padrão (standard) | Camada avançada (advanced) |
|---|---|---|
| Nós EC2 | Incluídos sem custo | Incluídos sem custo |
| Nós híbridos | Limitados (até uma quantidade) | **Cobrados** por nó |
| Parâmetros Parameter Store | Até um número grande, sem custo | Permite mais parâmetros, valores maiores e **políticas** (expiração) |
| Throughput de parâmetros | Padrão | Mais alto (cobrado) |

Confirme os limites e preços vigentes antes de dimensionar. Em geral, **EC2 e Session/Run Command básicos não têm custo adicional**; o que cobra é a **camada avançada**, alguns recursos (por exemplo, certos itens de Change Manager/OpsCenter) e serviços consumidos (S3, CloudWatch Logs).

---

## Segurança: o modelo de acesso

| Camada | Controle |
|---|---|
| **Quem pode usar** | Políticas IAM (por ação, por documento, por tag do alvo) |
| **Onde pode agir** | Condições por **tag** (`ssm:resourceTag/Ambiente`) e por **ARN** |
| **O que pode executar** | Controle por **documento** (ex.: só `AWS-RunShellScript` em dev) |
| **Rastreabilidade** | **CloudTrail** registra as chamadas; logs de sessão em S3/CloudWatch Logs |
| **Dados em trânsito** | TLS; opção de criptografar sessões com **KMS** |
| **Menor privilégio no nó** | A role da instância concede só o necessário |

```json
{
  "Effect": "Allow",
  "Action": ["ssm:StartSession"],
  "Resource": "arn:aws:ec2:*:123456789012:instance/*",
  "Condition": {"StringEquals": {"ssm:resourceTag/Ambiente": "desenvolvimento"}}
}
```

Essa política permite abrir sessões **somente** em instâncias de desenvolvimento, bloqueando produção para esse perfil.

## Exemplo prático: do zero à frota gerenciada

1. Crie uma **role** com `AmazonSSMManagedInstanceCore` e um **instance profile**.
2. Lance as instâncias com o perfil e **tags padronizadas** (`Ambiente`, `Funcao`, `PatchGroup`).
3. Em sub-redes privadas, crie os **VPC endpoints** `ssm`, `ssmmessages`, `ec2messages`.
4. Confirme no **Fleet Manager** ou com `describe-instance-information` que as máquinas estão **Online**.
5. Acesse uma instância com **Session Manager** (sem SSH) e verifique o log da sessão.
6. Execute `uptime` em todas as máquinas `Funcao=web` com **Run Command** e rate control.
7. Habilite **Inventory** e **Patch Manager** para o restante do ciclo de vida.

## Erros comuns e armadilhas

- **Esquecer o perfil IAM** e o nó nunca aparecer.
- **Sub-rede privada sem VPC endpoints** nem NAT.
- **Tags inconsistentes**, impossibilitando alvos dinâmicos.
- **Manter a porta 22 aberta "por garantia"** mesmo com Session Manager.
- **Dar `ssm:*` amplo** a todos, sem restringir por tag ou ambiente.
- **Rodar comandos em toda a frota sem rate control**, causando falhas em massa.
- **Não registrar sessões** (sem log em S3/CloudWatch) e perder auditoria.
- **Esquecer que o SSM é regional**: a frota de cada região é separada.

## 🧩 Quiz de Fixação

1. O que é um managed node?
2. Qual política IAM é normalmente anexada à instância para o SSM?
3. Por que o Session Manager dispensa a porta 22?
4. Para que servem as hybrid activations?
5. Qual a vantagem de alvejar por tags?
6. O que são os SSM Documents?

**Respostas:**
1) Qualquer máquina (EC2, on-premises ou de outra nuvem) com o SSM Agent registrado e gerenciável pelo Systems Manager.
2) `AmazonSSMManagedInstanceCore` (via instance profile).
3) Porque o agente inicia uma conexão HTTPS de saída para o serviço; não há porta de entrada aberta no servidor.
4) Registrar servidores fora da AWS como managed nodes (prefixo mi-), gerenciando-os com as mesmas ferramentas.
5) Permite endereçar frotas dinâmicas (novas instâncias com a tag entram automaticamente) sem listar IDs.
6) Arquivos JSON/YAML que descrevem o que o SSM deve executar (comandos, automações, sessões, políticas, pacotes).
