### Automation e operações — runbooks, aprovação, execução multi-conta, Change Manager, OpsCenter, Explorer e Incident Manager

> [!warning] Aviso
> Ações disponíveis em runbooks, limites de execução, nomes de recursos, integrações e preços mudam. Os números e exemplos aqui são referências de estudo; confirme na documentação. Os comandos **não foram executados**.

O **Systems Manager Automation** transforma **procedimentos operacionais** (reiniciar um serviço, criar uma AMI, corrigir uma configuração, restaurar um backup) em **fluxos repetíveis, auditáveis e seguros**, descritos em **runbooks**. Ao redor dele, o SSM oferece ferramentas de **gestão de mudança** (Change Manager), de **itens operacionais** (OpsCenter), de **visão consolidada** (Explorer) e de **resposta a incidentes** (Incident Manager). É a camada que leva a operação do "faz na mão" para o **"está no código e passa por aprovação"**.

**Analogia:** um runbook é uma **receita de cozinha padronizada** de restaurante: cada passo está escrito, qualquer cozinheiro autorizado a executa do mesmo jeito, e o resultado é registrado. O **Change Manager** é o **gerente que aprova pedidos especiais**; o **OpsCenter** é o **quadro de ocorrências** do dia; o **Incident Manager** é o **plano de emergência** (quem chamar, em que ordem).

## Automation: conceitos

| Conceito | Descrição |
|---|---|
| **Runbook** | Documento (YAML/JSON) do tipo *Automation* com **passos** (steps) |
| **Passo (step)** | Uma ação: chamar API AWS, executar comando, esperar, aprovar, ramificar |
| **Execução** | Uma instância de runbook com parâmetros; tem estado e histórico |
| **Assume role** | Role IAM que a automação assume para agir (menor privilégio) |
| **Alvos** | Recursos afetados (instâncias, buckets, etc.), em paralelo ou em taxa controlada |
| **Gatilhos** | Console, CLI, EventBridge, Maintenance Windows, Config remediation, Lambda |

### Ações (actions) mais usadas

| Ação | Função |
|---|---|
| `aws:executeAwsApi` | Chama qualquer API AWS |
| `aws:runCommand` | Executa um documento de comando em nós |
| `aws:executeScript` | Executa **Python ou PowerShell** inline |
| `aws:createImage` | Cria uma AMI |
| `aws:changeInstanceState` | Para/inicia instâncias |
| `aws:waitForAwsResourceProperty` | Espera uma propriedade atingir um valor |
| `aws:approve` | **Pausa e exige aprovação** humana |
| `aws:branch` | Ramificação condicional |
| `aws:invokeLambdaFunction` | Chama uma função Lambda |
| `aws:sleep` | Espera um tempo |
| `aws:executeStateMachine` | Aciona Step Functions |

### Exemplo de runbook

```yaml
schemaVersion: '0.3'
description: Cria AMI de uma instância, aguarda e reinicia o serviço
assumeRole: '{{ AutomationAssumeRole }}'
parameters:
  InstanceId: {type: String}
  AutomationAssumeRole: {type: String}
mainSteps:
  - name: criaImagem
    action: aws:createImage
    inputs:
      InstanceId: '{{ InstanceId }}'
      ImageName: 'backup-{{ InstanceId }}-{{ global:DATE_TIME }}'
      NoReboot: true
  - name: aprovaReinicio
    action: aws:approve
    inputs:
      NotificationArn: arn:aws:sns:us-east-1:123456789012:aprovacoes
      Message: 'Reiniciar {{ InstanceId }}?'
      MinRequiredApprovals: 1
      Approvers: ['arn:aws:iam::123456789012:role/Operadores']
  - name: reinicia
    action: aws:changeInstanceState
    inputs:
      InstanceIds: ['{{ InstanceId }}']
      DesiredState: running
```

```bash
aws ssm start-automation-execution \
  --document-name MeuRunbookBackupReinicio \
  --parameters InstanceId=i-0123456789abcdef0,AutomationAssumeRole=arn:aws:iam::123456789012:role/AutomacaoRole
aws ssm get-automation-execution --automation-execution-id <id>
```

> [!tip] Automação com menor privilégio
> A **AutomationAssumeRole** deve conter só as permissões dos passos do runbook. Quem **executa** o runbook precisa de `ssm:StartAutomationExecution` e `iam:PassRole` para essa role; assim, **usuários sem permissão direta** sobre as instâncias ainda podem executar **ações aprovadas e limitadas**.

### Controle de execução

| Parâmetro | Efeito |
|---|---|
| **Alvos e `TargetParameterName`** | Executa o runbook em muitos recursos |
| **`MaxConcurrency` / `MaxErrors`** | Rate control como no Run Command |
| **Modos: Rate control, Multi-conta e multi-região** | Executa em várias contas e regiões a partir de um ponto central |
| **Execução simples vs interativa** | Interativa permite acompanhar e aprovar passo a passo |
| **Tratamento de falhas** | `onFailure` (`Abort`, `Continue`, `step:nome`), `isCritical`, `maxAttempts` |

## Casos de uso do Automation

| Caso | Exemplo de runbook |
|---|---|
| **Remediação do Config** | Fechar security group aberto; ativar *Block Public Access* |
| **Resposta a alarmes** | Alarme dispara runbook que reinicia o serviço ou aumenta capacidade |
| **Ciclo de AMIs** | Criar, testar e compartilhar AMIs (Golden AMI) |
| **Backup e restauração** | Snapshots, cópias, restauração controlada |
| **Gestão de recursos** | Limpar volumes órfãos, encerrar recursos de teste |
| **Patching orquestrado** | Retirar do balanceador, patch, validar, devolver |
| **Rotação de chaves** | Rotação orquestrada de credenciais |
| **Autoatendimento** | Operadores executam tarefas pré-aprovadas sem acesso amplo |

```
 Alarme CloudWatch ─► EventBridge ─► Automation "reinicia-servico"
                                          ├─ confere saúde
                                          ├─ reinicia
                                          └─ valida e notifica
```

## Change Manager

O **Change Manager** adiciona **processo de gestão de mudança** à automação.

| Elemento | Função |
|---|---|
| **Template de mudança** | Define o runbook, aprovadores, revisores e notificações |
| **Solicitação de mudança** | Pedido de execução com **justificativa** e janela |
| **Aprovação** | Um ou mais aprovadores autorizam |
| **Change Calendar** | Bloqueia mudanças em períodos críticos |
| **Auditoria** | Histórico completo de quem pediu, aprovou e executou |
| **Mudança emergencial** | Fluxo acelerado com registro |

```
 Solicitação ──► Revisão/Aprovação ──► Janela (Change Calendar aberto?) ──► Execução (Automation) ──► Registro
```

Ideal para organizações com **requisitos de conformidade** (ITIL, SOX) que exigem **trilha formal** de quem aprovou cada mudança em produção.

## OpsCenter

O **OpsCenter** é a **central de itens operacionais (OpsItems)**: problemas e eventos que exigem atenção, com **contexto**, **recursos relacionados** e **ações sugeridas**.

| Fonte de OpsItem | Exemplo |
|---|---|
| **EventBridge** | Alarmes, falhas de Config, eventos do Health |
| **CloudWatch Alarms** | Alarme cria OpsItem automaticamente |
| **Manual** | Operador registra um problema |
| **Compliance** | Nós não conformes de patch |
| **Outros serviços** | Integrações (Security Hub, Config, Incident Manager) |

| Recurso do OpsItem | Uso |
|---|---|
| **Recursos relacionados** | Instâncias, buckets, alarmes ligados ao problema |
| **Runbooks sugeridos** | Executar a correção direto do OpsItem |
| **Status e prioridade** | Aberto, em andamento, resolvido |
| **Deduplicação** | Evita itens repetidos para o mesmo problema |
| **Operational data** | Campos e anexos para a investigação |

> [!tip] Do alarme ao runbook
> Configure o alarme para criar um **OpsItem** com um **runbook sugerido**. O operador abre o item, vê os recursos afetados e executa a correção com um clique, tudo registrado.

## Explorer

O **Explorer** é um **painel operacional consolidado** (multi-conta e multi-região) com:

| Painel | Informação |
|---|---|
| **OpsItems** | Abertos por gravidade e fonte |
| **Compliance** | Patches e associações |
| **Nós gerenciados** | Estado do SSM Agent |
| **Alarmes e Trusted Advisor** | Alertas relevantes |
| **AWS Health** | Eventos que afetam a conta |

É o **ponto de partida do dia** para a equipe de operações: o que está aberto, o que está fora de conformidade, onde agir.

## Incident Manager

O **Incident Manager** apoia a **resposta a incidentes**:

| Elemento | Função |
|---|---|
| **Response plan** | Plano com **contatos**, escalonamento, runbooks e canais de chat |
| **Contatos e escalas** | Quem é chamado, em que ordem, por qual canal (SMS, voz, e-mail) |
| **Engajamento** | Escalonamento automático se ninguém responder |
| **Chat channel** | Sala de incidente (via Chatbot) |
| **Runbooks de resposta** | Diagnóstico e mitigação automatizados |
| **Linha do tempo e post-incident analysis** | Registro e **análise pós-incidente** (lições aprendidas) |

```
 Alarme crítico ─► Incident Manager ─► chama on-call (escala) ─► abre canal de chat
                                         └─► executa runbook de diagnóstico ─► registra linha do tempo
```

## Exemplo prático: de alarme a correção governada

1. O **Config** detecta um security group com SSH aberto ao mundo e cria um **OpsItem**.
2. O OpsItem sugere o runbook **`FechaSshAberto`** (com **aprovação**).
3. O operador executa o runbook; o passo `aws:approve` pede confirmação de um segundo responsável.
4. A automação remove a regra, valida e notifica.
5. Tudo fica registrado: quem aprovou, quando e o que mudou (CloudTrail + histórico da execução).
6. O padrão é promovido a **remediação automática** com exceções documentadas.

## Troubleshooting

| Sintoma | Causa provável | Como resolver |
|---|---|---|
| Execução falha por permissão | AutomationAssumeRole sem permissões | Ajustar a role e `iam:PassRole` |
| Passo `approve` nunca conclui | Aprovadores ou SNS incorretos | Revisar aprovadores e notificação |
| Runbook não encontra recursos | Parâmetro/alvos incorretos | Conferir parâmetros e tags |
| Execução multi-conta falha | Role de execução ausente nas contas-alvo | Implantar a role (StackSet) |
| OpsItem duplicado | Sem deduplicação | Configurar chave de deduplicação |
| Incident Manager não chama | Contato sem canal de engajamento | Ajustar contatos e escalas |
| `executeScript` com erro | Dependência/runtime | Testar o script; ver logs da execução |
| Change bloqueada | Change Calendar fechado | Aguardar ou usar fluxo emergencial |

---

## Erros comuns e armadilhas

- **AutomationAssumeRole amplo demais** (`*:*`).
- **Runbooks não idempotentes** ou sem tratamento de falhas.
- **Sem aprovação** em passos destrutivos.
- **Executar em toda a frota** sem rate control.
- **Não versionar runbooks** em IaC.
- **OpsItems sem dono** nem prazo.
- **Incident Manager sem escalas testadas.**
- **Automatizar correções arriscadas** sem janela e sem exceções.

## 🧩 Quiz de Fixação

1. O que é um runbook do Automation?
2. Qual ação do Automation exige aprovação humana?
3. Qual a função do Change Manager?
4. Para que serve o OpsCenter?
5. O que o Incident Manager adiciona?
6. Por que usar uma AutomationAssumeRole com menor privilégio?

**Respostas:**
1) Um documento YAML/JSON com passos (steps) que automatiza um procedimento operacional de forma repetível e auditável.
2) `aws:approve`, que pausa a execução até que aprovadores autorizem.
3) Adicionar processo formal de mudança: templates, solicitações, aprovações, Change Calendar e auditoria.
4) Centralizar itens operacionais (OpsItems), com recursos relacionados, runbooks sugeridos, status e deduplicação.
5) Resposta a incidentes: planos, contatos e escalas, canal de chat, runbooks de resposta, linha do tempo e análise pós-incidente.
6) Porque a automação age com essa identidade; limitá-la reduz o impacto de erros e permite que usuários executem apenas ações aprovadas.
