### Manutenção da frota — Patch Manager, patch baselines, maintenance windows, State Manager, Inventory e Compliance

> [!warning] Aviso
> Sistemas operacionais suportados, nomes de documentos, classificações de patch, limites de janelas e preços mudam. Os números aqui são referências de estudo; confirme na documentação. Os comandos **não foram executados**.

Manter uma frota **atualizada, consistente e visível** é o trabalho menos glamoroso e mais importante da operação: servidores sem patch são a porta de entrada de grande parte dos incidentes de segurança, e configurações que **divergem** sem ninguém perceber causam falhas misteriosas. O Systems Manager cobre esse ciclo com quatro ferramentas que trabalham juntas: **Patch Manager** (aplicar correções), **Maintenance Windows** (quando agir), **State Manager** (manter o estado desejado) e **Inventory + Compliance** (saber o que existe e se está conforme).

**Analogia:** é a **rotina de manutenção de um prédio**. O **Patch Manager** é a equipe que troca peças defeituosas conforme a lista do fabricante; as **Maintenance Windows** são os horários combinados com os moradores; o **State Manager** é o zelador que, todo dia, confere se as portas estão trancadas e o gerador ligado, corrigindo o que saiu do padrão; o **Inventory** é o livro com tudo o que há em cada apartamento; a **Compliance** é o relatório que diz quais estão em dia.

---

## Visão do ciclo

```
 Inventory ──► "o que tenho e o que falta?"
      │
      ▼
 Patch Manager (baseline define o que é necessário)
      │  executado dentro de
      ▼
 Maintenance Window (quando, em que ordem, com que ritmo)
      │
      ▼
 State Manager (reaplica configurações; corrige desvios continuamente)
      │
      ▼
 Compliance (relatório: Compliant / Non-compliant)  ──► OpsCenter / EventBridge
```

## Patch Manager

O **Patch Manager** automatiza a **verificação e a instalação de patches** de **sistema operacional** (e, conforme o SO, de aplicações da Microsoft) nos managed nodes, com **politica de aprovação**, **agendamento** e **relatório de conformidade**.

### Patch baselines

Um **patch baseline** define **quais patches estão aprovados** para instalação.

| Elemento | Função |
|---|---|
| **Regras de aprovação** | Classificações (Security, Critical, Bugfix...), severidades e **atraso de aprovação** (ex.: aprovar 7 dias após a publicação) |
| **Patches aprovados/rejeitados** | Listas explícitas de exceções |
| **Fonte** (Linux) | Repositórios alternativos |
| **Baseline padrão** | A AWS fornece um por sistema operacional; você pode criar o seu e defini-lo como padrão |
| **Aprovar patches não relacionados à segurança** | Opcional |

```bash
aws ssm create-patch-baseline \
  --name "AL2023-Seguranca-7dias" \
  --operating-system AMAZON_LINUX_2023 \
  --approval-rules '{
    "PatchRules":[{
      "PatchFilterGroup":{"PatchFilters":[
        {"Key":"CLASSIFICATION","Values":["Security","Bugfix"]},
        {"Key":"SEVERITY","Values":["Critical","Important"]}]},
      "ApproveAfterDays":7,
      "ComplianceLevel":"CRITICAL"
    }]
  }'
```

> [!tip] Atraso de aprovação como proteção
> Aprovar patches **alguns dias após a publicação** dá tempo para que problemas apareçam na comunidade antes de chegarem à produção. Teste em **dev/homologação** primeiro, com baselines e grupos distintos.

### Patch groups (grupos de patch)

Os nós recebem um **baseline** de acordo com a **tag `Patch Group`** (ou `PatchGroup`).

| Tag | Baseline associado | Uso |
|---|---|---|
| `Patch Group = dev` | Aprova imediatamente | Teste primeiro |
| `Patch Group = prod-a` | Aprova após 7 dias | Produção, onda A |
| `Patch Group = prod-b` | Aprova após 10 dias | Produção, onda B |

```bash
aws ssm register-patch-baseline-for-patch-group \
  --baseline-id pb-0123456789abcdef0 --patch-group prod-a
```

### Operações: Scan e Install

| Operação | Efeito |
|---|---|
| **Scan** | Apenas **verifica** quais patches faltam; não instala |
| **Scan and install** | Instala os patches aprovados |
| **Reboot option** | `RebootIfNeeded` ou `NoReboot` |

O documento usado é o **`AWS-RunPatchBaseline`**:

```bash
aws ssm send-command --document-name AWS-RunPatchBaseline \
  --targets Key=tag:Patch\ Group,Values=prod-a \
  --parameters Operation=Install,RebootOption=RebootIfNeeded \
  --max-concurrency 20% --max-errors 1
```

### Patch policies (configuração em nível de organização)

As **patch policies** (via **Quick Setup**) permitem definir **baselines, agendas e escopo** para **múltiplas contas e regiões** da organização de forma centralizada, em vez de configurar conta a conta.

> [!warning] Patch em Auto Scaling
> Instâncias efêmeras de Auto Scaling devem ser **substituídas** por AMIs novas e já corrigidas (imutabilidade), e não "remendadas" em execução. Use o Patch Manager principalmente para **frotas de longa duração** e para **verificação de conformidade**; para o resto, **atualize a AMI** (por exemplo, com EC2 Image Builder).

## Maintenance Windows

Uma **maintenance window** define **quando** ações podem ser executadas, **em quais alvos** e **com que ritmo**.

| Elemento | Descrição |
|---|---|
| **Agenda** | Cron/rate (ex.: domingos às 02:00) |
| **Duração e cutoff** | Duração total e quando parar de iniciar novas tarefas |
| **Alvos** | Por tag, ID ou resource group |
| **Tarefas** | `Run Command`, `Automation`, `Lambda`, `Step Functions` |
| **Prioridade** | Ordem das tarefas |
| **Rate control** | `max-concurrency` e `max-errors` por tarefa |
| **Fuso horário** | Define quando a agenda é interpretada |

```bash
aws ssm create-maintenance-window --name janela-prod-a \
  --schedule "cron(0 2 ? * SUN *)" --schedule-timezone "America/Sao_Paulo" \
  --duration 3 --cutoff 1 --no-allow-unassociated-targets

aws ssm register-target-with-maintenance-window --window-id mw-0123 \
  --resource-type INSTANCE \
  --targets Key=tag:Patch\ Group,Values=prod-a

aws ssm register-task-with-maintenance-window --window-id mw-0123 \
  --task-type RUN_COMMAND --task-arn AWS-RunPatchBaseline \
  --targets Key=WindowTargetIds,Values=<id-do-alvo> \
  --max-concurrency 20% --max-errors 1 \
  --task-invocation-parameters '{"RunCommand":{"Parameters":{"Operation":["Install"]}}}'
```

### Change Calendar

O **Change Calendar** marca períodos **abertos** ou **fechados** para mudanças (por exemplo, **fechado** em Black Friday). Automações e janelas podem **respeitar** o calendário e não executar quando está fechado.

## State Manager

O **State Manager** mantém os nós no **estado desejado**: você cria uma **associação** que liga um **documento** a **alvos** com uma **agenda**, e o SSM **reaplica** o documento periodicamente, **corrigindo desvios**.

```
 Associação = documento + alvos + agenda (+ parâmetros)

 Exemplo:  "AWS-ConfigureAWSPackage (agente de monitoramento)" ► alvos Funcao=web ► a cada 30 min
```

| Uso típico | Documento |
|---|---|
| Garantir que o **agente de monitoramento** esteja instalado | `AWS-ConfigureAWSPackage` |
| Manter o **SSM Agent atualizado** | `AWS-UpdateSSMAgent` |
| Aplicar configurações de segurança (hardening) | Documento próprio |
| Coletar **inventário** periodicamente | `AWS-GatherSoftwareInventory` |
| Executar **playbooks Ansible** | `AWS-ApplyAnsiblePlaybooks` |
| Garantir um serviço em execução | Documento customizado |

```bash
aws ssm create-association \
  --name AWS-UpdateSSMAgent \
  --targets Key=InstanceIds,Values=* \
  --schedule-expression "rate(14 days)" \
  --association-name atualiza-agente
```

| Característica | Detalhe |
|---|---|
| **Idempotência** | Documentos devem poder rodar várias vezes sem efeito colateral |
| **Compliance** | Cada associação reporta `Compliant/Non-compliant` por nó |
| **Aplicar no registro** | `--apply-only-at-cron-interval` controla o comportamento ao criar/atualizar |
| **Rate control** | `max-concurrency`, `max-errors` também valem |

> [!tip] State Manager substitui scripts de "boot"
> Em vez de confiar em *user data* executado uma vez, use associações para que **novas instâncias** recebam a configuração e **desvios** sejam corrigidos continuamente.

## Inventory

O **Inventory** coleta **metadados** dos nós: **aplicações instaladas**, **atualizações**, **serviços**, **arquivos**, **chaves de registro** (Windows), **informações de rede**, **configurações de instância** e **tags customizadas**.

| Categoria | Exemplos |
|---|---|
| Aplicações | Nome, versão, editor |
| Rede | Interfaces, IPs, MACs |
| Serviços (Windows) | Estado dos serviços |
| Atualizações | Patches instalados |
| Informações da instância | SO, versão, arquitetura |
| Customizado | Inventário próprio (JSON) |

```bash
aws ssm create-association --name AWS-GatherSoftwareInventory \
  --targets Key=InstanceIds,Values=* \
  --schedule-expression "rate(12 hours)" \
  --parameters applications=Enabled,networkConfig=Enabled
```

### Resource Data Sync e consulta

| Recurso | Função |
|---|---|
| **Resource Data Sync** | Envia o inventário para um **bucket S3** (inclusive **multi-conta**) |
| **Athena / QuickSight** | Consultas e painéis sobre o inventário |
| **Console (Inventory/Explorer)** | Visões prontas |

```sql
-- Exemplo no Athena: quais servidores têm uma versão vulnerável do OpenSSL?
SELECT resourceid, name, version
FROM aws_application
WHERE name = 'openssl' AND version LIKE '1.0.%'
```

## Compliance

A **Compliance** consolida o **estado de conformidade** de **patches**, **associações** e **itens personalizados**.

| Fonte | Significado |
|---|---|
| **Patch** | Nós com patches aprovados **ausentes** (`Non-compliant`) |
| **Association** | Associações que **falharam** ou estão atrasadas |
| **Custom** | Itens que você reporta (`put-compliance-items`) |

```bash
aws ssm list-compliance-summaries
aws ssm list-resource-compliance-summaries \
  --filters Key=ComplianceType,Values=Patch Key=Status,Values=NON_COMPLIANT
```

Os resultados alimentam **Explorer**, **OpsCenter** (itens operacionais) e **EventBridge** (alertas), além do **Security Hub** e do **Config** conforme integrações.

## Exemplo prático: ciclo mensal de patches

1. Três grupos: `dev`, `prod-a`, `prod-b`, com baselines de aprovação 0, 7 e 10 dias.
2. **Janela de dev** (terça): `Scan and install`; validação automática por testes.
3. **Janela prod-a** (domingo): `Install` com `max-concurrency 20%` e `max-errors 1`, `RebootIfNeeded`.
4. **Janela prod-b** (domingo seguinte): mesmo processo, após validar a onda A.
5. O **State Manager** garante que o agente de monitoramento volte após reboot.
6. O relatório de **Compliance** mostra nós `Non-compliant`; o **OpsCenter** abre itens para os que falharam; o **Inventory** apoia a análise de vulnerabilidades.

## Troubleshooting

| Sintoma | Causa provável | Como resolver |
|---|---|---|
| Nó não recebe patches | Sem `Patch Group` ou baseline não associado | Verificar tag e associação |
| Patches "ausentes" persistem | Falha ao instalar, reboot pendente | Ver saída do `RunPatchBaseline`; reboot |
| Janela não executa | Fuso, `cutoff` ou alvos não registrados | Revisar agenda, alvos e role |
| Associação `Failed` | Documento com erro ou sem permissão | Ver histórico de execução |
| Inventário vazio | Associação de inventário ausente | Criar `AWS-GatherSoftwareInventory` |
| Compliance divergente | Dados antigos | Reexecutar scan/associação |
| Reboot inesperado | `RebootIfNeeded` em produção sem janela | Ajustar opção e agenda |
| Patch derruba a aplicação | Sem teste em ondas | Estratégia dev → prod-a → prod-b |

## Erros comuns e armadilhas

- **Aplicar patches em toda a frota de uma vez**, sem ondas e sem `max-errors`.
- **Não testar em dev** antes de produção.
- **Esquecer o reboot** e achar que o patch já está efetivo.
- **Patch Manager em instâncias efêmeras** em vez de atualizar a AMI.
- **Associações não idempotentes**, que quebram ao reexecutar.
- **Sem Inventory**, sem saber qual versão roda onde.
- **Tags inconsistentes** (`PatchGroup` vs `Patch Group`).
- **Ignorar o relatório de Compliance**, deixando passivos acumularem.

## 🧩 Quiz de Fixação

1. O que define um patch baseline?
2. Para que servem os patch groups?
3. Qual a diferença entre Scan e Install?
4. O que o State Manager faz?
5. Como o Inventory pode ser consultado em escala?
6. Por que aplicar patches em ondas?

**Respostas:**
1) Quais patches estão aprovados (classificações, severidades, atraso de aprovação, exceções) para instalação em um sistema operacional.
2) Associar nós a baselines diferentes por tag (Patch Group), permitindo ondas como dev e produção com atrasos distintos.
3) Scan apenas verifica os patches ausentes; Install instala os aprovados (com opção de reboot).
4) Mantém os nós no estado desejado reaplicando documentos por agenda e corrigindo desvios, reportando compliance.
5) Com Resource Data Sync para S3 e consultas no Athena/QuickSight, inclusive multi-conta.
6) Para limitar o impacto de um patch problemático, validando primeiro em dev e em pequenas parcelas da produção.
