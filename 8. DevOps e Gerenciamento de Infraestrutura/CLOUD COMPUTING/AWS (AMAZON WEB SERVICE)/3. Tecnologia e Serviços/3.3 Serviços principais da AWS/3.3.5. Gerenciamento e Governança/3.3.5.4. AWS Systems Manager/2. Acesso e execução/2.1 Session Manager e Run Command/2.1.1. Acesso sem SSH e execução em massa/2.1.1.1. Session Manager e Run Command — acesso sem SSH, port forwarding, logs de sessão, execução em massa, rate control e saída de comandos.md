### Session Manager e Run Command — acesso sem SSH, port forwarding, logs de sessão, execução em massa, rate control e saída de comandos

> [!warning] Aviso
> Limites de sessão, requisitos de versão do agente, nomes de documentos, preços e opções do plugin da CLI mudam. Os números aqui são referências de estudo; confirme na documentação. Os comandos **não foram executados**.

Duas das capacidades mais usadas do Systems Manager resolvem o dia a dia de quem opera servidores: o **Session Manager**, para **abrir um terminal (shell) seguro** em uma máquina **sem SSH, sem bastion e sem porta aberta**, e o **Run Command**, para **executar comandos em muitas máquinas de uma vez**, com **controle de ritmo, de erros e de saída**. Juntos eliminam a maior parte dos motivos para ter chaves SSH espalhadas pela organização.

**Analogia:** o Session Manager é um **interfone seguro** instalado dentro de cada apartamento: o zelador fala com o morador pela central, sem precisar de uma chave física, e a conversa é **gravada**. O Run Command é um **alto-falante coordenado**: a central manda o mesmo aviso a todos os apartamentos de um bloco, de dez em dez, e para se muitos não responderem.

## Session Manager

### Como funciona

```
 Usuário (console / CLI / SSH via proxy)
        │  IAM + MFA  (ssm:StartSession)
        ▼
 ┌──────────────────────┐      WebSocket TLS      ┌──────────────────┐
 │  Systems Manager     │ ◄──────────────────────►│  SSM Agent       │
 │  (Session Manager)   │   (iniciado pelo agente)│  no managed node │
 └──────────┬───────────┘                         └──────────────────┘
            │ registra
            ▼
   CloudTrail (StartSession) + logs de sessão (S3 / CloudWatch Logs)
```

| Aspecto | Detalhe |
|---|---|
| **Porta de entrada** | Nenhuma: o agente liga **para fora** |
| **Autenticação** | IAM (identidade, MFA, SSO); **sem chaves SSH** |
| **Autorização** | Políticas IAM por instância, tag e documento |
| **Auditoria** | CloudTrail + **log completo da sessão** (comandos e saída) |
| **Plataformas** | Linux, Windows (PowerShell) e macOS |
| **Acesso por** | Console, **AWS CLI + plugin Session Manager**, ou SSH/SCP via proxy |

```bash
# Abre um shell na instância (requer o plugin do Session Manager)
aws ssm start-session --target i-0123456789abcdef0

# Executa dentro da sessão: o prompt é do servidor
sh-5.2$ whoami
ssm-user
```

O usuário do SO é, por padrão, **`ssm-user`** (Linux) com privilégios de `sudo` conforme a configuração; é possível **executar como outro usuário** por preferências.

### Preferências de sessão

| Preferência | Efeito |
|---|---|
| **Log em S3** | Grava a transcrição da sessão em um bucket (criptografável) |
| **Log em CloudWatch Logs** | Streaming da sessão para análise e alarmes |
| **Criptografia KMS** | Criptografia adicional do canal |
| **Timeout de ociosidade** | Encerra sessões paradas (por padrão, alguns minutos) |
| **Duração máxima** | Limita o tempo total de uma sessão |
| **Executar como** | Usuário do SO usado nas sessões |
| **Shell profile** | Comandos iniciais por plataforma |
| **Auditoria de comandos** | Registro dos comandos digitados |

> [!tip] Sessão sempre gravada
> Configure **S3 + CloudWatch Logs** nas preferências e crie alarmes para comandos sensíveis (`sudo su`, `rm -rf`, `cat /etc/shadow`). A transcrição transforma o acesso interativo em algo **auditável**, o que o SSH com chave compartilhada nunca foi.

### Port forwarding e acesso a recursos privados

O Session Manager também **encaminha portas**, permitindo acessar serviços em **redes privadas** sem VPN ou bastion.

```bash
# Acessa um banco RDS privado pela porta local 5432, usando uma instância como ponte
aws ssm start-session --target i-0123456789abcdef0 \
  --document-name AWS-StartPortForwardingSessionToRemoteHost \
  --parameters '{"host":["meu-banco.xyz.us-east-1.rds.amazonaws.com"],
                 "portNumber":["5432"],"localPortNumber":["15432"]}'

# Em outro terminal
psql -h 127.0.0.1 -p 15432 -U app meubanco

# RDP para uma instância Windows pela porta local 33389
aws ssm start-session --target i-0abcdef0123456789 \
  --document-name AWS-StartPortForwardingSession \
  --parameters '{"portNumber":["3389"],"localPortNumber":["33389"]}'
```

| Documento | Uso |
|---|---|
| `AWS-StartPortForwardingSession` | Porta da própria instância |
| `AWS-StartPortForwardingSessionToRemoteHost` | Porta de um host remoto alcançável pela instância |
| `AWS-StartSSHSession` | SSH tradicional tunelado (para SCP e ferramentas) |
| `SSM-SessionManagerRunShell` | Shell interativo padrão |

### SSH sobre Session Manager

Quem precisa de **SCP, rsync ou IDEs remotas** pode manter o SSH, mas **sem expor a porta 22**:

```
# ~/.ssh/config
Host i-* mi-*
    ProxyCommand sh -c "aws ssm start-session --target %h \
      --document-name AWS-StartSSHSession --parameters 'portNumber=%p'"
```

> [!warning] Isso ainda usa chaves SSH
> O tunelamento resolve a **exposição de rede**, mas as chaves continuam existindo. Para o ganho completo (auditoria e ausência de chaves), prefira o **shell nativo** do Session Manager.

### Controles de acesso com IAM

| Objetivo | Condição/técnica |
|---|---|
| Só instâncias de dev | `ssm:resourceTag/Ambiente = desenvolvimento` |
| Só o próprio dono | Tag `Dono` igual a `${aws:username}` |
| Proibir port forwarding | Negar documentos `AWS-StartPortForwarding*` |
| Obrigar MFA | `aws:MultiFactorAuthPresent = true` |
| Restringir tempo | Duração máxima da sessão nas preferências |
| Ver apenas as próprias sessões | `ssm:TerminateSession` restrito a `ssm:resourceTag/aws:ssmmessages:session-id` |

### Just-in-time node access

Para ambientes mais controlados, o SSM oferece **acesso just-in-time**: o usuário **solicita** acesso temporário a um nó, a solicitação é **aprovada** (por pessoas ou política automática) e o acesso **expira**. Isso evita permissões permanentes de acesso interativo.

## Run Command

### Visão geral

O **Run Command** executa um **documento** (um script ou comando) em **muitos managed nodes** simultaneamente, **sem SSH**, com **alvos por tag**, **controle de ritmo** e **registro da saída**.

```
 send-command (documento + alvos + parâmetros + rate control)
        │
        ▼
 Systems Manager ──► Nó A (Success) ── saída ──► S3 / CloudWatch Logs
                 ├─► Nó B (Success)
                 ├─► Nó C (Failed)   ─► conta para max-errors
                 └─► ...             └─► interrompe se exceder max-errors
```

```bash
aws ssm send-command \
  --document-name AWS-RunShellScript \
  --targets Key=tag:Funcao,Values=web Key=tag:Ambiente,Values=producao \
  --parameters 'commands=["sudo systemctl restart nginx","systemctl is-active nginx"]' \
  --max-concurrency 20% \
  --max-errors 10% \
  --timeout-seconds 120 \
  --comment "Reinicia nginx em producao" \
  --output-s3-bucket-name meu-bucket-ssm-saida \
  --cloud-watch-output-config CloudWatchOutputEnabled=true,CloudWatchLogGroupName=/ssm/run-command
```

### Rate control

| Parâmetro | Função | Exemplo |
|---|---|---|
| `max-concurrency` | Quantos nós em paralelo (número ou %) | `10%`, `5` |
| `max-errors` | Quantos erros toleram antes de **parar** | `1`, `5%` |
| `timeout-seconds` | Tempo para o nó **começar** a executar | `60` |
| `execution-timeout` (parâmetro do documento) | Tempo máximo de execução | `3600` |

> [!tip] Faça rollouts em ondas
> Use `max-concurrency` baixo e `max-errors = 1` ou `2` em mudanças arriscadas. Se o primeiro nó falhar, o comando **para** em vez de quebrar a frota inteira. É o equivalente a um *canary* operacional.

### Status do comando

| Status | Significado |
|---|---|
| **Pending / InProgress** | Aguardando ou executando |
| **Success** | Todos os alvos concluíram com sucesso |
| **Failed** | Falhou (limite de erros excedido ou falha de nó) |
| **TimedOut** | Nó não iniciou a tempo |
| **Cancelled** | Cancelado pelo usuário |
| **DeliveryTimedOut / ExecutionTimedOut** | Problemas de entrega ou execução lenta |

```bash
# Consulta o resultado de cada nó
aws ssm list-command-invocations --command-id <id> --details \
  --query 'CommandInvocations[].[InstanceId,Status,CommandPlugins[0].Output]'

# Detalhe de um nó
aws ssm get-command-invocation --command-id <id> --instance-id i-0abc...
```

A saída exibida diretamente é **truncada** (primeiros caracteres); para saída completa, envie para **S3** e/ou **CloudWatch Logs**.

### Documentos úteis do Run Command

| Documento | Uso |
|---|---|
| `AWS-RunShellScript` | Executa comandos shell (Linux/macOS) |
| `AWS-RunPowerShellScript` | Executa PowerShell (Windows) |
| `AWS-UpdateSSMAgent` | Atualiza o agente |
| `AWS-ConfigureAWSPackage` | Instala/desinstala pacotes do Distributor |
| `AWS-RunPatchBaseline` | Aplica patches (usado pelo Patch Manager) |
| `AWS-GatherSoftwareInventory` | Coleta inventário |
| `AWS-ApplyAnsiblePlaybooks` | Executa playbooks Ansible |
| `AWS-RunRemoteScript` | Baixa e executa um script do S3/GitHub |

### Segurança do Run Command

| Risco | Controle |
|---|---|
| Quem executa o quê | IAM por documento e por tag do alvo |
| Segredos em `commands` | Use **Parameter Store** (`{{ssm-secure:...}}`) e nunca em texto |
| Comandos livres em produção | Restrinja a **documentos aprovados** |
| Auditoria | CloudTrail (`SendCommand`) + saída em S3/CloudWatch |
| Scripts maliciosos | Exija revisão e use `AWS-RunRemoteScript` só de fontes confiáveis |

## Session Manager vs Run Command vs SSH

| Critério | Session Manager | Run Command | SSH tradicional |
|---|---|---|---|
| Interativo | **Sim** | Não (execução remota) | Sim |
| Escala (muitos nós) | Não | **Sim** | Difícil |
| Porta aberta | Nenhuma | Nenhuma | 22/3389 |
| Chaves | Não | Não | Sim |
| Auditoria | **Alta** (transcrição) | **Alta** (saída + CloudTrail) | Baixa |
| Ideal para | Depuração pontual | Rotinas e mudanças em frota | Legado |

```
 Preciso investigar UM servidor agora?       ─► Session Manager
 Preciso aplicar algo em MUITOS servidores?  ─► Run Command (ou Automation)
 Preciso de fluxo com aprovação/passos?      ─► Automation / Change Manager
 Preciso manter estado desejado contínuo?    ─► State Manager
```

## Exemplo prático: reiniciar um serviço com segurança

1. Um alarme do CloudWatch aponta degradação em servidores web de produção.
2. O operador usa o **Session Manager** em **um** servidor, lê os logs e confirma que o `nginx` precisa reiniciar.
3. Dispara o **Run Command** com `Funcao=web`, `max-concurrency 10%` e `max-errors 1`.
4. A saída vai para **CloudWatch Logs**; o painel confirma `Success` em todos.
5. A transcrição da sessão e o comando ficam registrados no **CloudTrail** e no **S3**.
6. A causa raiz vira um item no **OpsCenter** e uma correção na imagem (AMI) do servidor.

## Troubleshooting

| Sintoma | Causa provável | Como resolver |
|---|---|---|
| `TargetNotConnected` ao iniciar sessão | Nó offline, sem agente/perfil/endpoint | Verificar `describe-instance-information` |
| Plugin ausente na CLI | Session Manager plugin não instalado | Instalar o plugin |
| Sessão sem permissão | IAM sem `ssm:StartSession` ou condição de tag | Ajustar a política |
| Sessão cai por ociosidade | Timeout curto | Ajustar preferência de idle |
| Comando `TimedOut` | Nó não recebeu a tempo | Verificar conectividade/agente |
| `Failed` por limite de erros | `max-errors` baixo ou erro real | Ver a saída por nó |
| Saída truncada | Limite de exibição | Enviar saída para S3/CloudWatch |
| Windows sem `ssm-user` com permissões | Política do SO | Ajustar grupos/perfil |
| Comando não encontra variáveis | Shell não-login | Usar caminhos absolutos |

## Erros comuns e armadilhas

- **Manter a porta 22 aberta** "só por garantia" depois de adotar o Session Manager.
- **Não ativar log de sessão**, perdendo a auditoria.
- **Rodar Run Command em toda a frota** sem `max-concurrency` e `max-errors`.
- **Colocar senhas em `commands`** em vez de usar Parameter Store.
- **Permitir `ssm:SendCommand` irrestrito**, o que equivale a um shell remoto em tudo.
- **Esquecer endpoints** em sub-redes privadas.
- **Esperar saída completa no console**, que é truncada.
- **Usar SSH tunelado como solução final**, mantendo as chaves e o risco.

## 🧩 Quiz de Fixação

1. Por que o Session Manager não exige porta de entrada?
2. Como o Session Manager acessa um banco privado?
3. O que fazem `max-concurrency` e `max-errors`?
4. Onde guardar a saída completa de um Run Command?
5. Qual a diferença entre Session Manager e Run Command?
6. Como impedir que um usuário abra sessões em produção?

**Respostas:**
1) Porque o SSM Agent inicia uma conexão de saída para o serviço; o usuário acessa pelo SSM, sem tráfego de entrada no servidor.
2) Com port forwarding (AWS-StartPortForwardingSessionToRemoteHost), usando uma instância como ponte e uma porta local.
3) `max-concurrency` limita quantos nós executam em paralelo; `max-errors` define quantos erros são tolerados antes de interromper o comando.
4) Em S3 e/ou CloudWatch Logs, configurados no `send-command`.
5) O Session Manager dá um shell interativo em um nó; o Run Command executa um documento em muitos nós, de forma não interativa.
6) Com política IAM que condicione `ssm:StartSession` à tag do recurso (por exemplo, permitir só Ambiente=desenvolvimento) ou negue produção.
