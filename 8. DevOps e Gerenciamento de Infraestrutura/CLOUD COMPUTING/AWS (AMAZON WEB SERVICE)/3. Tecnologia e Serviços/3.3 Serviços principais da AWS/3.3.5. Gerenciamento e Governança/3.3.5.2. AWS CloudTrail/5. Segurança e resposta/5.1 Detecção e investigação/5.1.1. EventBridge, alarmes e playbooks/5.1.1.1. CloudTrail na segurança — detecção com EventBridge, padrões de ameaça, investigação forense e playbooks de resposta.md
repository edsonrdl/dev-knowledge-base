### CloudTrail na segurança — detecção com EventBridge, padrões de ameaça, investigação forense e playbooks de resposta

> [!warning] Aviso
> Nomes de eventos, formatos de payload, serviços de segurança e limites mudam. Os exemplos aqui são referências de estudo; confirme na documentação e adapte à sua organização. Os comandos e padrões **não foram executados**.

O CloudTrail é a **fonte de verdade** de quase toda investigação de segurança na AWS, porque registra **toda mudança** e **toda tentativa de acesso**. Mas só produz valor se alguém (ou algo) **olha os registros a tempo**. Esta folha mostra como transformar o CloudTrail em **detecção ativa** (EventBridge e CloudWatch), reconhecer **padrões típicos de ataque**, conduzir uma **investigação forense** e preparar **playbooks de resposta**.

**Analogia:** as câmeras de um banco gravam tudo (CloudTrail), mas segurança de verdade exige **alguém assistindo aos monitores e um protocolo** para quando algo suspeito aparece: trancar a porta, chamar a polícia, preservar a gravação. Detecção sem resposta, e resposta sem evidência preservada, falham.

---

## Visão do ciclo: detectar, investigar, responder

```
  CloudTrail ──► EventBridge / CloudWatch Logs ──► alerta (SNS, chat, ticket)
       │                                                 │
       │                                                 ▼
       │                                         playbook / Lambda de contenção
       ▼
  Evidência (S3 + Object Lock, digest) ──► investigação (Athena / Lake / Detective)
```

| Fase | Ferramentas |
|---|---|
| **Detectar** | EventBridge, metric filters, GuardDuty, Insights, Security Hub |
| **Investigar** | Lake, Athena, Detective, Config |
| **Conter** | Lambda/SSM, IAM (revogar sessão), SCP, security groups |
| **Erradicar e recuperar** | Rotação de credenciais, restauração de backups |
| **Aprender** | Pós-incidente, novos alarmes e controles |

## Detecção em tempo quase real com EventBridge

Os eventos de **gerenciamento** do CloudTrail chegam ao **EventBridge** como eventos do tipo **"AWS API Call via CloudTrail"**, permitindo reagir **sem esperar** a entrega ao S3.

```json
{
  "source": ["aws.iam"],
  "detail-type": ["AWS API Call via CloudTrail"],
  "detail": {
    "eventSource": ["iam.amazonaws.com"],
    "eventName": ["CreateAccessKey", "AttachUserPolicy", "PutUserPolicy", "CreateUser"]
  }
}
```

| Padrão de regra | O que detecta |
|---|---|
| Uso do **usuário raiz** (`userIdentity.type = Root`) | Qualquer ação do raiz |
| `StopLogging`, `DeleteTrail`, `UpdateTrail` | Tentativa de cegar a auditoria |
| `PutBucketPolicy`, `PutBucketAcl`, `DeletePublicAccessBlock` | Exposição de dados |
| `AuthorizeSecurityGroupIngress` com `0.0.0.0/0` | Abertura de rede |
| `CreateAccessKey` para outro usuário | Persistência/escalada |
| `ConsoleLogin` sem MFA | Acesso fraco |
| `DisableKey`, `ScheduleKeyDeletion` | Sabotagem de criptografia |

Os destinos típicos: **SNS** (alerta), **Lambda** (contenção automática), **SSM Automation** (remediação), **Step Functions** (fluxo de resposta) e **ferramentas de chat/tickets**.

```bash
aws events put-rule --name alerta-uso-root \
  --event-pattern '{"detail-type":["AWS API Call via CloudTrail"],
                    "detail":{"userIdentity":{"type":["Root"]}}}'
aws events put-targets --rule alerta-uso-root \
  --targets "Id"="sns","Arn"="arn:aws:sns:us-east-1:123456789012:seguranca"
```

> [!tip] Regras em todas as regiões
> Eventos de gerenciamento são regionais. Para cobrir ameaças em regiões não usadas (comum em ataques), replique as regras ou use uma **trilha multirregião** com **CloudWatch Logs** central.

## Padrões de ataque que o CloudTrail revela

| Fase do ataque | Assinatura no CloudTrail |
|---|---|
| **Reconhecimento** | Muitos `List*`/`Describe*`/`Get*` seguidos de `AccessDenied` |
| **Credencial vazada em uso** | Chamadas de **IP/país/ASN incomuns** com uma chave de acesso estável |
| **Escalada de privilégios** | `AttachUserPolicy`, `CreatePolicyVersion`, `PassRole` + criação de recursos |
| **Persistência** | `CreateAccessKey`, `CreateUser`, `CreateLoginProfile`, novos `AssumeRole` trust |
| **Evasão** | `StopLogging`, `DeleteTrail`, `PutEventSelectors`, desligar GuardDuty |
| **Impacto** | `RunInstances` em massa (mineração), `DeleteBucket`, `ScheduleKeyDeletion` |
| **Exfiltração** | Muitos `GetObject`, `CreateSnapshot` + `ModifySnapshotAttribute` (compartilhar) |
| **Movimento lateral** | `AssumeRole` encadeado entre contas |

### Indicadores de comprometimento

| Sinal | Interpretação |
|---|---|
| `sourceIPAddress` de provedor desconhecido (Tor, VPS) | Uso externo da credencial |
| `userAgent` incomum (`python-requests`, `Boto3` em conta que só usa console) | Automação inesperada |
| Região nunca usada | Atacante evitando monitoramento |
| `eventTime` fora do horário | Atividade suspeita |
| Muitas chamadas negadas seguidas de sucesso | Descoberta de permissões |

> [!warning] "Funcionou" não significa "legítimo"
> Um atacante com credenciais válidas gera eventos **bem-sucedidos**. A detecção deve combinar **contexto** (IP, horário, região, agente) e não apenas erros.

## Investigação forense com CloudTrail

Passos recomendados diante de uma suspeita de comprometimento:

1. **Preservar evidência:** garantir que os logs do período estejam copiados e protegidos (Object Lock, cópia em conta de forense). Validar com `validate-logs`.
2. **Identificar a identidade afetada:** `userIdentity.arn`, `accessKeyId`, sessão de role.
3. **Linha do tempo:** listar **todos** os eventos da identidade desde a **primeira atividade anômala**.
4. **Delimitar o impacto:** quais serviços, recursos e regiões foram tocados.
5. **Rastrear a origem:** de onde veio a credencial (vazamento, phishing, instância comprometida).
6. **Verificar persistência:** novas chaves, usuários, roles, políticas, regras de EventBridge/Lambda criadas.
7. **Conter:** revogar sessões, desativar chaves, aplicar política de negação, isolar recursos.
8. **Erradicar e recuperar:** rotação de segredos, limpeza de recursos criados, restauração.

```sql
-- Linha do tempo de uma chave de acesso suspeita
SELECT eventTime, eventSource, eventName, awsRegion, sourceIpAddress, errorCode
FROM cloudtrail_logs
WHERE userIdentity.accessKeyId = 'AKIAEXEMPLO1234567'
  AND year = '2026' AND month = '11'
ORDER BY eventTime;

-- O que essa identidade criou?
SELECT eventName, count(*) AS vezes
FROM cloudtrail_logs
WHERE userIdentity.accessKeyId = 'AKIAEXEMPLO1234567'
  AND readOnly = 'false'
GROUP BY eventName ORDER BY vezes DESC;
```

> [!tip] Revogar sessões de roles
> Para sessões de role já emitidas, desativar a chave do usuário não basta: aplique a política **"revogar sessões anteriores"** (negar com `aws:TokenIssueTime`) à role afetada.

## Playbooks de resposta (exemplos)

### Playbook 1: uso do usuário raiz

```
 Alerta: ação do Root
 1. Confirmar com o dono da conta se foi legítimo
 2. Se não: trocar senha, revisar MFA, revogar chaves do root
 3. Revisar CloudTrail das últimas 24 h
 4. Abrir incidente e documentar
```

### Playbook 2: chave de acesso exposta

```
 Alerta: GuardDuty/CloudTrail aponta uso anômalo da chave AKIA...
 1. Desativar a chave (update-access-key --status Inactive)
 2. Anexar política de negação à identidade
 3. Levantar linha do tempo; listar recursos criados
 4. Excluir recursos maliciosos; verificar persistência
 5. Rotacionar segredos relacionados; emitir nova credencial segura
```

### Playbook 3: tentativa de desligar a auditoria

```
 Alerta: StopLogging / DeleteTrail
 1. Reativar a trilha imediatamente (start-logging)
 2. Identificar quem executou; tratar como possível comprometimento
 3. Aplicar SCP que impeça alterar a trilha em contas-membro
 4. Validar integridade dos logs do intervalo
```

### Contenção automática (exemplo conceitual)

| Gatilho | Ação automática | Cuidado |
|---|---|---|
| Security group aberto a `0.0.0.0/0` em porta de banco | Lambda remove a regra e notifica | Pode afetar serviço legítimo |
| Bucket tornado público | Reativar Block Public Access | Alertar o dono |
| `StopLogging` | Religar a trilha | Investigar o autor |

> [!warning] Automatize com critério
> Contenção automática reduz o tempo de exposição, mas pode **derrubar produção** por falso positivo. Comece com **alerta + aprovação humana** e automatize apenas ações de baixo risco e alta confiança.

## Prevenção complementar

| Controle | Efeito |
|---|---|
| **SCPs** (Organizations) | Impedir `cloudtrail:StopLogging`, `DeleteTrail`, desligar GuardDuty |
| **MFA obrigatório** | Reduz ataque por credencial roubada |
| **Credenciais temporárias** (SSO/roles) | Menos chaves de longa duração |
| **Permissões mínimas + IAM Access Analyzer** | Menos superfície |
| **Alarmes sobre uso do raiz** | Detecção do pior caso |
| **GuardDuty, Security Hub, Detective** | Detecção, consolidação e investigação |

## Exemplo prático: do alerta ao relatório

1. EventBridge dispara alerta de `CreateAccessKey` feito por um usuário que nunca criou chaves.
2. O analista consulta o Lake: o usuário fez `AssumeRole` de um IP desconhecido, sem MFA.
3. Em 40 minutos, a identidade criou 3 usuários e subiu instâncias em uma região não usada.
4. Contenção: chaves desativadas, política de negação aplicada, instâncias encerradas.
5. Verificação de persistência: duas regras de EventBridge maliciosas removidas.
6. Relatório com linha do tempo (consultas do CloudTrail como evidência) e ações preventivas: SCP e MFA.

## Troubleshooting

| Sintoma | Causa provável | Como resolver |
|---|---|---|
| Regra do EventBridge não dispara | Padrão incorreto ou região errada | Testar o padrão; criar a regra na região do evento |
| Eventos de IAM não aparecem | Evento global só em `us-east-1` | Criar regra em `us-east-1` |
| Alerta chega com atraso | Fonte S3 em vez de EventBridge/Logs | Usar EventBridge/CloudWatch Logs para urgência |
| Muitos falsos positivos | Regras genéricas | Filtrar por identidade, IP, horário |
| Sem evidência do período | Retenção curta ou sem trilha | Criar trilha e ajustar retenção |
| Contenção automática derrubou serviço | Ação agressiva sem exceções | Lista de exceções; aprovação humana |

## Erros comuns e armadilhas

- **Ter CloudTrail e ninguém olhando** (sem alarmes).
- **Detecção apenas por erro**, ignorando credenciais válidas usadas indevidamente.
- **Não proteger a trilha** com SCP e alarmes.
- **Ignorar regiões não usadas.**
- **Preservar evidência tarde**, após o invasor apagar logs.
- **Automatizar contenção sem testes.**
- **Esquecer persistência** (chaves, usuários, regras) ao encerrar o incidente.
- **Não ensaiar playbooks** antes de precisar deles.

## 🧩 Quiz de Fixação

1. Como detectar eventos do CloudTrail em quase tempo real?
2. Cite três assinaturas de ataque no CloudTrail.
3. Por que alarmar `StopLogging` e `DeleteTrail`?
4. Primeiro passo de uma investigação forense?
5. Por que desativar a chave pode não bastar em sessões de role?
6. Quando automatizar a contenção?

**Respostas:**
1) Com regras do EventBridge sobre eventos "AWS API Call via CloudTrail" ou com metric filters no CloudWatch Logs.
2) Por exemplo: muitos List/Describe seguidos de AccessDenied (reconhecimento); CreateAccessKey/AttachUserPolicy (persistência/escalada); StopLogging/DeleteTrail (evasão); RunInstances em massa (impacto).
3) Porque quem quer agir sem deixar rastros tenta primeiro desligar a auditoria; é um forte indicador de comprometimento.
4) Preservar a evidência: proteger e validar os logs do período antes que sejam alterados.
5) Porque sessões já emitidas continuam válidas; é preciso revogar sessões da role (negar por aws:TokenIssueTime).
6) Para ações de baixo risco e alta confiança, após testes; começar com alerta e aprovação humana evita derrubar produção por falso positivo.
