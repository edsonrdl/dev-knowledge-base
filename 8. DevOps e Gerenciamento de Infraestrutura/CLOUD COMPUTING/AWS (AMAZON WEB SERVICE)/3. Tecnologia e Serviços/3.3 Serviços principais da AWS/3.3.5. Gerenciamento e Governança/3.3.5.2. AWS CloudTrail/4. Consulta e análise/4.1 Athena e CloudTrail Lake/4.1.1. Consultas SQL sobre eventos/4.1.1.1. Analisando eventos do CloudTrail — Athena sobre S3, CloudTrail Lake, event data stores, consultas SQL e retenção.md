### Analisando eventos do CloudTrail — Athena sobre S3, CloudTrail Lake, event data stores, consultas SQL e retenção

> [!warning] Aviso
> Preços, limites de consulta, períodos de retenção, nomes de recursos e sintaxe de tabelas mudam. Os números aqui são referências de estudo; confirme na documentação. Os comandos e consultas **não foram executados**.

Guardar eventos é só metade do trabalho; a outra metade é **consultá-los rápido** quando um incidente ou uma auditoria exige respostas. O CloudTrail oferece três caminhos: a **busca do Event history** (poucos dias, limitada), o **Amazon Athena** sobre os arquivos no S3 e o **CloudTrail Lake**, um armazenamento gerenciado consultável por **SQL**.

**Analogia:** os arquivos `.json.gz` no S3 são **milhares de caixas de documentos arquivadas** em um depósito. O **Athena** é um **leitor que você manda ao depósito** para vasculhar as caixas conforme sua pergunta (você paga pelo que ele lê). O **CloudTrail Lake** é um **arquivo já indexado e catalogado**, onde você faz perguntas direto ao fichário e obtém respostas em segundos, mas paga pela guarda organizada.

---

## Comparação das formas de consulta

| Critério | Event history | Athena sobre S3 | CloudTrail Lake |
|---|---|---|---|
| Configuração | Nenhuma | Tabela no Glue/Athena | Criar **event data store** |
| Retenção | ~90 dias | Quanto durar o S3 | De dias a anos (configurável) |
| Linguagem | Filtros simples | SQL (Presto/Trino) | SQL |
| Tipos de evento | Só management | O que a trilha gravou | Management, data, Insights, de configuração e **eventos de fora da AWS** |
| Custo de consulta | Sem custo | Por dado escaneado | Por dado escaneado/ingerido e retido |
| Agregação multi-conta | Não | Sim (S3 central) | Sim (organização) |
| Esforço | Zero | Médio (particionar) | Baixo |
| Ideal para | Pesquisa rápida recente | Auditoria barata em grande volume | Investigação ágil e conformidade |

## Athena sobre os logs do S3

O Athena consulta diretamente os arquivos do bucket da trilha, usando uma **tabela** definida no catálogo (Glue). O console do CloudTrail pode **criar a tabela automaticamente**, ou você escreve o DDL.

### Tabela com projeção de partições (resumo)

```sql
CREATE EXTERNAL TABLE cloudtrail_logs (
  eventVersion STRING,
  userIdentity STRUCT<type:STRING, arn:STRING, accountId:STRING, userName:STRING,
                      sessionContext:STRUCT<sessionIssuer:STRUCT<userName:STRING>>>,
  eventTime STRING,
  eventSource STRING,
  eventName STRING,
  awsRegion STRING,
  sourceIpAddress STRING,
  userAgent STRING,
  errorCode STRING,
  errorMessage STRING,
  requestParameters STRING,
  responseElements STRING,
  readOnly STRING,
  recipientAccountId STRING
)
PARTITIONED BY (region STRING, year STRING, month STRING, day STRING)
ROW FORMAT SERDE 'org.apache.hive.hcatalog.data.JsonSerDe'
STORED AS INPUTFORMAT 'com.amazon.emr.cloudtrail.CloudTrailInputFormat'
OUTPUTFORMAT 'org.apache.hadoop.hive.ql.io.HiveIgnoreKeyTextOutputFormat'
LOCATION 's3://meu-bucket-cloudtrail/AWSLogs/123456789012/CloudTrail/';
```

> [!tip] Use projeção de partições
> Com **partition projection** (propriedades da tabela), o Athena calcula as partições por data **sem** `MSCK REPAIR TABLE` e sem catalogar dia a dia. Em tabelas grandes, isso é essencial.

### Consultas de investigação

```sql
-- Quem excluiu recursos nas últimas 24 horas?
SELECT eventTime, userIdentity.arn, eventSource, eventName, sourceIpAddress
FROM cloudtrail_logs
WHERE year = '2026' AND month = '11' AND day = '09'
  AND eventName LIKE 'Delete%'
ORDER BY eventTime DESC
LIMIT 100;

-- Tentativas negadas por identidade
SELECT userIdentity.arn, count(*) AS negadas
FROM cloudtrail_logs
WHERE errorCode IN ('AccessDenied','UnauthorizedOperation','Client.UnauthorizedOperation')
  AND year = '2026' AND month = '11'
GROUP BY userIdentity.arn
ORDER BY negadas DESC;

-- Logins no console sem MFA
SELECT eventTime, userIdentity.userName, sourceIpAddress
FROM cloudtrail_logs
WHERE eventName = 'ConsoleLogin'
  AND json_extract_scalar(additionalEventData, '$.MFAUsed') = 'No';

-- Uso do usuário raiz
SELECT eventTime, eventName, sourceIpAddress
FROM cloudtrail_logs
WHERE userIdentity.type = 'Root';
```

| Boa prática de custo no Athena | Efeito |
|---|---|
| **Sempre filtrar por partição** (`year/month/day`) | Escaneia só o necessário |
| Converter para **Parquet** (tabela derivada, `CTAS`) | Consultas muito mais baratas |
| Selecionar só colunas necessárias | Menos dado lido |
| Definir **workgroup** com limite de dado escaneado | Evita consultas descontroladas |

## CloudTrail Lake

O **CloudTrail Lake** armazena eventos em um **event data store** gerenciado, **imutável** e consultável por **SQL** diretamente no console ou por API, **sem montar tabelas ou pipelines**.

```
 Eventos ──► Event data store (retenção definida) ──► SQL ──► resultados/dashboards
  (AWS, Config, Insights, e eventos de parceiros/aplicações próprias)
```

| Característica | Detalhe |
|---|---|
| **Event data store** | Coleção de eventos com tipo, retenção e escopo definidos |
| **Retenção** | Padrão de 7 anos configuráveis em alguns modos (ou prazos menores, conforme opção); confirme os modos de preço |
| **Multi-conta** | Pode agregar eventos de toda a organização |
| **Eventos externos (integrações)** | Receber eventos de aplicações próprias e de parceiros |
| **Consultas salvas e dashboards** | Padrões reutilizáveis para equipes de segurança |
| **Federação** | Consultar o Lake pelo Athena (federação com Glue) |
| **Imutabilidade** | Eventos não podem ser alterados após a ingestão |

```bash
# Cria um event data store com retenção em dias
aws cloudtrail create-event-data-store --name auditoria-org \
  --multi-region-enabled --organization-enabled \
  --retention-period 365 --termination-protection-enabled

# Executa uma consulta SQL
aws cloudtrail start-query --query-statement "
  SELECT eventTime, userIdentity.arn, eventName
  FROM <id-do-event-data-store>
  WHERE eventName = 'DeleteBucket'
    AND eventTime > '2026-11-01 00:00:00'
  ORDER BY eventTime DESC" 

aws cloudtrail get-query-results --query-id <id>
```

> [!warning] Lake tem modelo de preço próprio
> Cobra-se por **ingestão**, **retenção** e **consulta (dados escaneados)**. Para grandes volumes e retenção longa, compare com **S3 + Athena**, que costuma ser mais barato, porém exige mais trabalho. Confira os modos de preço atuais.

### Consultas típicas no Lake

```sql
-- Mudanças de IAM em todas as contas na última semana
SELECT eventTime, recipientAccountId, userIdentity.arn, eventName
FROM <event-data-store-id>
WHERE eventSource = 'iam.amazonaws.com'
  AND readOnly = false
  AND eventTime > '2026-11-02 00:00:00'
ORDER BY eventTime DESC

-- Volume de GetObject por identidade (exfiltração?)
SELECT userIdentity.arn, count(*) AS leituras
FROM <event-data-store-id>
WHERE eventName = 'GetObject' AND eventTime > '2026-11-09 00:00:00'
GROUP BY userIdentity.arn
ORDER BY leituras DESC
LIMIT 20
```

## Quando usar cada abordagem

```
 Preciso saber algo dos últimos dias, rápido?
 ├─ Sim ─► Event history (lookup-events / console)
 └─ Não
     ├─ Retenção longa e volume enorme, custo mínimo? ─► S3 + Athena (Parquet, partições)
     ├─ Time de segurança precisa de SQL ágil, multi-conta, sem montar infra? ─► CloudTrail Lake
     └─ Alarmes em quase tempo real? ─► CloudWatch Logs / EventBridge
```

| Cenário | Escolha |
|---|---|
| Startup, auditoria básica | Event history + trilha em S3 |
| Empresa regulada, dados por anos | Trilha em S3 com Object Lock + Athena |
| SOC com investigações frequentes | CloudTrail Lake |
| Detecção contínua | EventBridge + CloudWatch Logs |

## Convertendo os logs para Parquet

Para reduzir custo em grandes volumes, crie uma tabela derivada em **Parquet**, particionada por data:

```sql
CREATE TABLE cloudtrail_parquet
WITH (format = 'PARQUET', external_location = 's3://meu-bucket-analise/cloudtrail/',
      partitioned_by = ARRAY['dia'])
AS SELECT eventTime, userIdentity.arn AS arn, eventSource, eventName,
          sourceIpAddress, errorCode, substr(eventTime, 1, 10) AS dia
FROM cloudtrail_logs
WHERE year = '2026' AND month = '11';
```

Consultas sobre essa tabela leem **menos colunas e menos bytes**, o que reduz custo e tempo. Agende a conversão diária (por exemplo, com Glue ou Step Functions) para manter a tabela atualizada.

## Exemplo prático: investigação de exfiltração

1. Um alerta do GuardDuty sinaliza downloads incomuns do bucket `dados-clientes`.
2. No **Lake**, o analista consulta `GetObject` por identidade nas últimas 48 h.
3. Uma role `app-legado` aparece com **milhares** de leituras de um IP externo.
4. Outra consulta mostra `AssumeRole` dessa role vindo de um usuário federado **sem MFA**.
5. A equipe revoga a sessão, rotaciona credenciais e fecha o acesso.
6. O relatório usa as consultas salvas como **evidência** e um novo alarme é criado.

## Troubleshooting

| Sintoma | Causa provável | Como resolver |
|---|---|---|
| Athena retorna zero linhas | Partição/região/caminho incorretos | Conferir `LOCATION` e a projeção |
| Consulta Athena cara | Sem filtro de partição | Filtrar por data; converter para Parquet |
| Erro de acesso ao bucket | Falta permissão S3/KMS ao analista | Ajustar IAM e política da chave |
| Lake sem eventos recentes | Event data store não ingeriu o tipo | Verificar seletores do data store |
| Consulta Lake lenta/cara | Intervalo de tempo muito amplo | Restringir `eventTime` |
| Campos aninhados vazios | Estrutura JSON diferente | Usar `json_extract_scalar` |
| Dados antigos ausentes | Retenção expirou | Revisar retenção e arquivar em S3 |

## Erros comuns e armadilhas

- **Consultar sem filtro de data/partição** no Athena e pagar por tudo.
- **Só ter Event history** quando o incidente é de meses atrás.
- **Usar Lake para volumes enormes** sem comparar o custo com S3+Athena.
- **Não treinar o time** em consultas antes do incidente.
- **Esquecer a permissão da chave KMS** para quem analisa.
- **Mistura de regiões/contas sem padrão** nas tabelas.
- **Não salvar consultas úteis** como runbooks.
- **Achar que o Lake substitui o arquivo S3 com Object Lock** para guarda legal.
