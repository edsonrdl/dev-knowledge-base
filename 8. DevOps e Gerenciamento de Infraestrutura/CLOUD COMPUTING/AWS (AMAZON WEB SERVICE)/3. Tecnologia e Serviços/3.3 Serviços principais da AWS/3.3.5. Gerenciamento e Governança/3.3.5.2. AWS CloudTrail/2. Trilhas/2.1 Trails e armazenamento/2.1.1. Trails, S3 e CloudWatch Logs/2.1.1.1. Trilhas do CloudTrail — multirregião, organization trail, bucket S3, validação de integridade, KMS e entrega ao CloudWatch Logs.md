### Trilhas do CloudTrail — multirregião, organization trail, bucket S3, validação de integridade, KMS e entrega ao CloudWatch Logs

> [!warning] Aviso
> Prazos de entrega, limites de trilhas, preços, políticas de bucket e opções de criptografia mudam. Os números aqui são referências de estudo; confirme na documentação. Os comandos **não foram executados**.

Uma **trilha (trail)** é a configuração que faz o CloudTrail **entregar continuamente os registros** de eventos a um **bucket do S3** (e, opcionalmente, ao **CloudWatch Logs** e ao **EventBridge**), por **tempo indeterminado** e com **controle de escopo**. É a base de uma auditoria séria: o Event history guarda poucos dias; a trilha guarda o que você decidir, no lugar que você controlar.

**Analogia:** o Event history é o **caderno de rascunho** da portaria, que é jogado fora a cada três meses. A trilha é o **arquivo oficial**: cópias numeradas, lacradas (validação de integridade), guardadas num cofre (S3 com KMS) e enviadas também à central de segurança (CloudWatch Logs).

---

## Anatomia de uma trilha

```
 CloudTrail ──► Trilha "trilha-principal" (multirregião, organização)
                    │
        ┌───────────┼─────────────────────────┐
        ▼           ▼                         ▼
   S3 bucket    CloudWatch Logs           EventBridge
   (arquivo     (alarmes e consultas       (reações a
   .json.gz)     quase em tempo real)      eventos)
        │
        └─► Digest files (validação de integridade, a cada hora)
```

| Elemento | Função |
|---|---|
| **Bucket S3** | Armazenamento durável dos arquivos `.json.gz` |
| **Prefixo** | Organização lógica dentro do bucket |
| **KMS** | Criptografia dos arquivos com chave gerenciada pelo cliente |
| **SNS** (opcional) | Notificação de entrega de novos arquivos |
| **CloudWatch Logs** (opcional) | Análise e alarmes quase em tempo real |
| **Digest files** | Hashes para provar que os logs não foram alterados |

### Estrutura de caminhos no S3

```
s3://meu-bucket-cloudtrail/AWSLogs/<id-da-conta>/CloudTrail/<região>/<ano>/<mês>/<dia>/
    123456789012_CloudTrail_us-east-1_20261109T1230Z_AbCdEf.json.gz
```

Esse padrão previsível facilita consultas por conta, região e data com **Athena** e regras de **ciclo de vida**.

## Escopo: o que a trilha cobre

| Opção | Efeito | Recomendação |
|---|---|---|
| **Trilha de uma região** | Só eventos daquela região | Evite como única trilha |
| **Trilha multirregião** | Uma configuração, **todas as regiões** (incluindo novas) | **Padrão recomendado** |
| **Eventos de serviços globais** | IAM, STS, CloudFront, Route 53 etc. | Incluir (em geral vêm via `us-east-1` na multirregião) |
| **Organization trail** | Trilha criada na conta de gerenciamento que cobre **todas as contas** da AWS Organizations | Ideal para empresas |
| **Várias trilhas** | Podem coexistir (ex.: segurança e auditoria) | Controle custo: cópias adicionais de eventos de gerenciamento são cobradas |

> [!tip] Uma trilha multirregião cobre regiões futuras
> Se a AWS lançar uma nova região e você usa uma trilha multirregião, ela **já a cobre**; trilhas por região exigiriam ação manual e podem deixar buracos sem que ninguém perceba.

### Organization trail

```bash
# Na conta de gerenciamento (com acesso confiável habilitado para o CloudTrail)
aws cloudtrail create-trail --name trilha-organizacao \
  --s3-bucket-name bucket-auditoria-central \
  --is-multi-region-trail --is-organization-trail \
  --enable-log-file-validation
```

| Vantagem | Observação |
|---|---|
| Cobertura automática de contas novas | Contas-membro não conseguem desligar nem alterar |
| Logs centralizados em um bucket | Normalmente em uma **conta de arquivo de logs** dedicada |
| Governança | Combina com SCPs para proteger o serviço |

## O bucket de destino

O bucket precisa de uma **política** que permita ao serviço `cloudtrail.amazonaws.com` verificar a ACL e gravar objetos.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AWSCloudTrailAclCheck",
      "Effect": "Allow",
      "Principal": {"Service": "cloudtrail.amazonaws.com"},
      "Action": "s3:GetBucketAcl",
      "Resource": "arn:aws:s3:::meu-bucket-cloudtrail"
    },
    {
      "Sid": "AWSCloudTrailWrite",
      "Effect": "Allow",
      "Principal": {"Service": "cloudtrail.amazonaws.com"},
      "Action": "s3:PutObject",
      "Resource": "arn:aws:s3:::meu-bucket-cloudtrail/AWSLogs/123456789012/*",
      "Condition": {"StringEquals": {"s3:x-amz-acl": "bucket-owner-full-control"}}
    }
  ]
}
```

### Proteção do bucket de auditoria

| Controle | Por quê |
|---|---|
| **Conta separada** de arquivo de logs | O invasor da conta de workload não alcança as evidências |
| **Bloqueio de acesso público** | Logs contêm identidades e IPs |
| **Versionamento** | Recuperação de sobrescritas |
| **MFA Delete / Object Lock** (modo compliance) | Impede apagar ou alterar logs por um período |
| **Ciclo de vida** | Move a classes mais baratas (IA, Glacier) e expira após a retenção |
| **Replicação entre regiões/contas** | Cópia de segurança independente |
| **Criptografia SSE-KMS** | Controle de quem lê |

> [!warning] Quem pode apagar o bucket pode apagar a prova
> Um bucket de auditoria na **mesma conta** do workload, sem Object Lock, permite a um atacante com privilégios **apagar os próprios rastros**. Isolar a conta e travar a exclusão é o ponto central do desenho.

## Validação de integridade dos logs

Com a opção **log file validation**, o CloudTrail grava **arquivos de digest** (uma vez por hora) com os **hashes SHA-256** dos arquivos de log entregues, **assinados** digitalmente. Isso permite provar que um log **não foi modificado, apagado ou forjado** depois da entrega.

```bash
aws cloudtrail validate-logs \
  --trail-arn arn:aws:cloudtrail:us-east-1:123456789012:trail/trilha-principal \
  --start-time 2026-11-01T00:00:00Z --end-time 2026-11-09T00:00:00Z
```

A saída informa quantos arquivos foram **validados**, quais estão **ausentes** ou **alterados**. Em auditorias e investigações forenses, isso transforma os logs em **evidência confiável**.

## Criptografia com KMS

| Opção | Comportamento |
|---|---|
| **SSE-S3** (padrão do S3) | Criptografia gerenciada pelo S3 |
| **SSE-KMS com chave do cliente** | Controle fino: só quem tem permissão na chave lê os logs |

```bash
aws cloudtrail update-trail --name trilha-principal \
  --kms-key-id arn:aws:kms:us-east-1:123456789012:key/<id-da-chave>
```

A política da chave deve permitir ao CloudTrail **gerar chaves de dados** (`kms:GenerateDataKey*`) e aos analistas **descriptografar** (`kms:Decrypt`). Sem isso, a trilha **falha ao entregar** ou ninguém consegue ler.

## Entrega ao CloudWatch Logs

Enviar os eventos também para o **CloudWatch Logs** permite **detecção quase em tempo real** com *metric filters* e **alarmes**.

```
 CloudTrail ──► log group "CloudTrail/auditoria" ──► metric filter ──► alarme ──► SNS
```

```bash
aws cloudtrail update-trail --name trilha-principal \
  --cloud-watch-logs-log-group-arn arn:aws:logs:us-east-1:123456789012:log-group:CloudTrail/auditoria:* \
  --cloud-watch-logs-role-arn arn:aws:iam::123456789012:role/CloudTrail_CWLogs_Role
```

### Alarmes clássicos de segurança sobre CloudTrail

| Evento observado | Por que alarmar |
|---|---|
| Uso do **usuário raiz** | Deve ser excepcional |
| `ConsoleLogin` sem MFA | Acesso fraco |
| Chamadas **não autorizadas** em excesso | Reconhecimento ou erro de permissões |
| Mudanças em **políticas IAM** | Escalada de privilégios |
| `StopLogging` / `DeleteTrail` / `UpdateTrail` | Tentativa de **desligar a auditoria** |
| Mudanças em **security groups** e **NACLs** | Exposição de rede |
| Desativação ou remoção de chaves **KMS** | Perda de acesso aos dados |
| Mudanças em **buckets S3** (política/ACL) | Exposição de dados |

> [!tip] Alarme sobre a própria trilha
> Crie um alarme para `StopLogging`, `DeleteTrail`, `UpdateTrail` e `PutEventSelectors`. Quem quer agir sem deixar rastros tenta **desligar o CloudTrail primeiro**.

## Entrega e latência

| Aspecto | Referência |
|---|---|
| Entrega ao S3 | Tipicamente alguns minutos (por volta de 5; pode chegar a ~15) |
| Entrega ao CloudWatch Logs | Normalmente mais rápida que o S3 |
| Entrega ao EventBridge | Quase em tempo real para eventos de gerenciamento |
| Arquivos | Um conjunto por região, por conta, em janelas curtas |

Os registros **não são em tempo real absoluto**: para resposta imediata, use **EventBridge** ou **CloudWatch Logs**; para arquivo e análise, S3/Lake.

## Exemplo prático: desenho de auditoria de uma empresa

1. **Conta de arquivo de logs** (`log-archive`) cria o bucket com **Object Lock** (compliance, 1 ano), versionamento, SSE-KMS e política para o CloudTrail.
2. **Organization trail** multirregião na conta de gerenciamento, com validação, entregando ao bucket central.
3. **CloudWatch Logs** habilitado na trilha, com alarmes de raiz, `StopLogging` e mudanças de IAM.
4. **Ciclo de vida:** 90 dias em S3 Standard → Glacier por 7 anos.
5. **Athena** com tabela particionada por data para investigações.
6. Revisão trimestral: `validate-logs` e checagem de que nenhuma conta ficou sem cobertura.

## Troubleshooting

| Sintoma | Causa provável | Como resolver |
|---|---|---|
| Trilha não entrega ao S3 | Política do bucket incorreta | Ajustar `GetBucketAcl`/`PutObject` para o CloudTrail |
| Erro de KMS na entrega | Política da chave sem permissão | Permitir `GenerateDataKey*` ao serviço |
| Sem eventos de uma região | Trilha não é multirregião | Converter para multirregião |
| Eventos de IAM ausentes | Eventos globais não incluídos | Habilitar `--include-global-service-events` |
| CloudWatch Logs vazio | Role da trilha sem permissão | Revisar a role e o log group |
| Logs de contas-membro ausentes | Sem organization trail | Criar trilha da organização |
| `validate-logs` aponta ausentes | Logs apagados ou ainda não entregues | Investigar; verificar Object Lock e intervalo |

## Erros comuns e armadilhas

- **Trilha de uma só região** sem cobertura das demais.
- **Bucket na mesma conta**, sem Object Lock, sujeito a apagamento por invasor.
- **Sem validação de integridade**, enfraquecendo o valor probatório.
- **Esquecer a política da chave KMS** e quebrar a entrega.
- **Sem alarme sobre `StopLogging`/`DeleteTrail`.**
- **Retenção sem ciclo de vida**, acumulando custo de armazenamento.
- **Múltiplas trilhas redundantes** pagando cópias duplicadas de eventos.
- **Não testar a leitura** dos logs (Athena) antes de precisar deles em um incidente.

## 🧩 Quiz de Fixação

1. Qual a vantagem de uma trilha multirregião?
2. O que é uma organization trail?
3. Para que serve a validação de integridade dos logs?
4. Por que manter o bucket de auditoria em uma conta separada?
5. Qual evento sinaliza uma tentativa de desligar a auditoria?
6. Qual a vantagem de enviar a trilha ao CloudWatch Logs?

**Respostas:**
1) Uma única configuração cobre todas as regiões, inclusive futuras, evitando buracos de cobertura.
2) Uma trilha criada na conta de gerenciamento da Organizations que registra os eventos de todas as contas-membro, sem que elas possam alterá-la.
3) Provar, com digest files assinados e hashes SHA-256, que os logs não foram modificados, apagados ou forjados após a entrega.
4) Para que um invasor da conta de workload não consiga apagar nem alterar as evidências.
5) `StopLogging` (e também `DeleteTrail`, `UpdateTrail`, `PutEventSelectors`).
6) Detecção e alarmes quase em tempo real com metric filters, além de consultas com Logs Insights.
