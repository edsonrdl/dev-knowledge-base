### O que é AWS CloudTrail — registro de chamadas de API, anatomia de um evento, Event history e quando usar em vez de CloudWatch ou Config

> [!warning] Aviso
> Prazos de entrega, períodos de retenção, preços, tipos de evento e campos de registros mudam. Os números aqui são referências de estudo; confirme na documentação oficial. Os comandos de CLI são exemplos e **não foram executados**.

O **AWS CloudTrail** é o serviço de **auditoria e governança** da AWS: ele **registra as chamadas de API e as ações** feitas na sua conta, seja pelo console, pela CLI, por SDKs ou por outros serviços AWS. Cada registro responde às perguntas centrais de qualquer investigação: **quem** fez, **o quê**, **quando**, **de onde** e **com que resultado**.

**Analogia:** é o **livro de ocorrências da portaria** de um prédio. Toda vez que alguém entra, abre uma porta ou muda uma fechadura, o porteiro anota nome, horário, origem e o que foi feito. O livro não diz se o prédio está funcionando bem (isso é o CloudWatch), mas diz **quem mexeu em quê** quando algo dá errado.

---

## Para que serve

| Objetivo | Exemplo |
|---|---|
| **Auditoria e conformidade** | Provar quem acessou dados regulados (PCI, SOC, LGPD) |
| **Investigação de incidentes** | Descobrir quem abriu um security group ou apagou um bucket |
| **Análise de segurança** | Detectar uso anômalo de credenciais, chamadas negadas |
| **Resolução de problemas operacionais** | Qual mudança precedeu a falha? |
| **Rastreabilidade de mudanças** | Quem alterou uma política IAM |
| **Automação** | Reagir a eventos de API via EventBridge |

O CloudTrail está **habilitado por padrão** em toda conta AWS, com o **Event history** (histórico de eventos recentes). Para guardar por mais tempo e entregar os registros a um bucket, cria-se uma **trilha (trail)**.

---

## Como funciona

```
 Ação (console, CLI, SDK, serviço AWS)
        │
        ▼
 ┌────────────────────┐
 │  API da AWS        │ ──► registra o evento
 └────────────────────┘          │
                                 ▼
                        ┌─────────────────┐
                        │   CLOUDTRAIL    │
                        └───┬───────┬─────┘
          Event history ◄───┘       │ trail / event data store
          (90 dias, mgmt)           ▼
                       ┌────────────┬──────────────┬─────────────┐
                       │ S3 (logs)  │ CloudWatch   │ CloudTrail  │
                       │ + Athena   │ Logs + alarmes│ Lake (SQL) │
                       └────────────┴──────────────┴─────────────┘
```

| Etapa | O que acontece |
|---|---|
| 1. Ação | Um usuário, role ou serviço chama uma API |
| 2. Registro | O CloudTrail captura o evento, normalmente em poucos minutos |
| 3. Destino | Event history (padrão), trail (S3/CloudWatch Logs) ou Lake |
| 4. Consumo | Consulta, alarmes, investigação, EventBridge |

## Anatomia de um evento

Cada evento é um registro em **JSON**. Os campos mais importantes:

```json
{
  "eventVersion": "1.09",
  "userIdentity": {
    "type": "IAMUser",
    "arn": "arn:aws:iam::123456789012:user/maria",
    "accessKeyId": "AKIA...",
    "sessionContext": {"mfaAuthenticated": "true"}
  },
  "eventTime": "2026-11-09T12:34:56Z",
  "eventSource": "s3.amazonaws.com",
  "eventName": "DeleteBucket",
  "awsRegion": "us-east-1",
  "sourceIPAddress": "203.0.113.10",
  "userAgent": "aws-cli/2.x",
  "requestParameters": {"bucketName": "dados-producao"},
  "responseElements": null,
  "errorCode": "AccessDenied",
  "readOnly": false,
  "eventType": "AwsApiCall",
  "recipientAccountId": "123456789012"
}
```

| Campo | Responde a... | Uso típico |
|---|---|---|
| `userIdentity` | **Quem** | Usuário, role assumida, serviço, conta federada |
| `eventTime` | **Quando** | Linha do tempo do incidente |
| `eventSource` + `eventName` | **O quê** | `ec2.amazonaws.com` + `TerminateInstances` |
| `sourceIPAddress` / `userAgent` | **De onde / com quê** | IP suspeito, ferramenta usada |
| `awsRegion` | **Onde** | Atividade em região inesperada |
| `requestParameters` | **Com quais parâmetros** | Qual recurso foi afetado |
| `responseElements` | **Resultado** | Recurso criado, IDs retornados |
| `errorCode` / `errorMessage` | **Falhou?** | `AccessDenied`, `UnauthorizedOperation` |
| `readOnly` | Leitura ou escrita | Filtrar só mudanças |

> [!tip] Chamadas negadas também são registradas
> Um `errorCode` de `AccessDenied` mostra **tentativas bloqueadas**. Muitas negações vindas de uma mesma identidade em pouco tempo costumam indicar **reconhecimento** (alguém explorando permissões).

### Tipos de identidade (`userIdentity.type`)

| Tipo | Significado |
|---|---|
| `Root` | Usuário raiz da conta (uso deve ser raríssimo e alertado) |
| `IAMUser` | Usuário IAM com credenciais próprias |
| `AssumedRole` | Role assumida (instância, Lambda, federação, SSO) |
| `AWSService` | Um serviço AWS agindo em seu nome |
| `FederatedUser` / `WebIdentityUser` | Identidade federada |

## Event history: o que vem de graça

O **Event history** mostra, **sem nenhuma configuração**, os eventos de **gerenciamento** (management events) dos **últimos 90 dias**, por região, com busca por atributos (nome do evento, usuário, tipo de recurso, fonte, ID de acesso).

```bash
# Quem terminou instâncias EC2 recentemente?
aws cloudtrail lookup-events \
  --lookup-attributes AttributeKey=EventName,AttributeValue=TerminateInstances \
  --max-results 20

# Atividade de um usuário específico
aws cloudtrail lookup-events \
  --lookup-attributes AttributeKey=Username,AttributeValue=maria
```

| Característica | Event history | Trail / Lake |
|---|---|---|
| Configuração | Nenhuma | Você cria |
| Retenção | ~90 dias | Prazo que você definir (S3 / Lake) |
| Tipos de evento | Apenas **management** (escrita e leitura) | Management, data, Insights |
| Entrega a S3/CloudWatch | Não | Sim |
| Consulta | `lookup-events` limitado | Athena, Lake, Logs Insights |
| Multirregião | Visão por região | Pode ser uma trilha única multirregião |

> [!warning] 90 dias não basta para conformidade
> Se você precisa de **retenção longa** (anos) ou de eventos de **dados** (S3 objetos, funções Lambda), é necessário criar uma **trilha** ou um **event data store**. Sem isso, os registros de incidentes antigos simplesmente **não existem** mais.

## CloudTrail vs CloudWatch vs Config

| Serviço | Pergunta | Natureza do dado |
|---|---|---|
| **CloudTrail** | **Quem fez o quê, quando e de onde?** | Registro de chamadas de API (auditoria) |
| **CloudWatch** | **Como está o desempenho e a saúde agora?** | Métricas, logs, alarmes |
| **AWS Config** | **Como é/era a configuração e está em conformidade?** | Histórico e avaliação de configuração |

```
 "O bucket foi apagado"                 → CloudTrail  (quem apagou? quando?)
 "O site ficou lento às 14h"            → CloudWatch  (latência, erros)
 "O security group estava aberto ontem?" → Config      (estado da configuração)
```

Eles se **complementam**: o Config detecta que um security group ficou aberto; o CloudTrail mostra **quem** o abriu; o CloudWatch dispara o **alarme** em tempo hábil.

## Conceitos-chave para guardar

| Conceito | Resumo |
|---|---|
| **Event** | Um registro de atividade (API ou outra) |
| **Management events** | Operações no plano de controle (criar/alterar/excluir recursos, IAM, login no console) |
| **Data events** | Operações de alto volume nos dados (S3 objetos, Lambda invoke, DynamoDB itens) |
| **Insights events** | Detecção de atividade **incomum** em chamadas de escrita |
| **Trail** | Configuração que entrega eventos a S3 (e opcionalmente CloudWatch Logs) |
| **Event data store** | Armazenamento gerenciado do **CloudTrail Lake**, consultável por SQL |
| **Organization trail** | Trilha única que cobre todas as contas de uma organização |
| **Log file validation** | Prova de integridade dos arquivos de log entregues |

Cada um deles ganha detalhe nas outras folhas do guia.

## Exemplo prático: "quem apagou o bucket?"

1. Alguém percebe que o bucket `dados-producao` sumiu.
2. No **Event history**, filtra por `EventName = DeleteBucket` e `ResourceName = dados-producao`.
3. O evento mostra `userIdentity` (a role `dev-temp`), `sourceIPAddress` e `eventTime`.
4. Cruzando com eventos de `AssumeRole`, descobre que a role foi assumida por um usuário federado do SSO.
5. A equipe revoga a sessão, restaura os dados do backup e cria um **alarme** para `DeleteBucket` fora do horário comercial.
6. Para o futuro, habilita uma **trilha multirregião** com validação e retenção de 1 ano.

## Limites do que o CloudTrail enxerga

| Registra | Não registra (por si só) |
|---|---|
| Chamadas de API e ações no console | Comandos executados **dentro** do sistema operacional de uma instância |
| Quem assumiu qual role e quando | O conteúdo dos arquivos acessados |
| Mudanças de configuração e IAM | Tráfego de rede entre instâncias (use VPC Flow Logs) |
| Tentativas negadas | Desempenho e métricas (use CloudWatch) |

Para completar o quadro, combine o CloudTrail com **VPC Flow Logs** (rede), **CloudWatch Logs** (aplicação), **Config** (estado da configuração) e **GuardDuty** (detecção de ameaças).

## Primeiros passos recomendados

```bash
# Cria uma trilha multirregião que também cobre eventos globais (ex.: IAM)
aws cloudtrail create-trail --name trilha-principal \
  --s3-bucket-name meu-bucket-cloudtrail \
  --is-multi-region-trail --include-global-service-events \
  --enable-log-file-validation

# Liga o registro
aws cloudtrail start-logging --name trilha-principal

# Confere o status
aws cloudtrail get-trail-status --name trilha-principal
```

O bucket de destino precisa de uma **política** que permita ao serviço CloudTrail gravar; veja detalhes na folha sobre trilhas.

## Erros comuns e armadilhas

- **Confiar apenas no Event history** e perder registros após 90 dias.
- **Não habilitar uma trilha multirregião**, deixando regiões sem cobertura de longo prazo.
- **Esquecer que data events não vêm por padrão** (acesso a objetos do S3 não aparece).
- **Confundir CloudTrail com monitoramento de desempenho.**
- **Guardar os logs no mesmo bucket e conta sem proteção**, permitindo que um invasor apague a evidência.
- **Ignorar eventos do usuário raiz** (`Root`), que devem ser alarmados.
- **Não ativar a validação de integridade** dos arquivos.
- **Acreditar que o CloudTrail registra tudo**: nem toda atividade (por exemplo, ações dentro do sistema operacional) é uma chamada de API.

## 🧩 Quiz de Fixação

1. O que o CloudTrail registra?
2. Quais campos de um evento respondem a "quem", "o quê" e "de onde"?
3. Por quanto tempo o Event history guarda eventos e de que tipo?
4. Qual a diferença entre CloudTrail, CloudWatch e Config?
5. Por que chamadas com `AccessDenied` também importam?
6. Quando é necessário criar uma trilha?

**Respostas:**
1) As chamadas de API e ações feitas na conta, por console, CLI, SDK ou serviços AWS, indicando quem, o quê, quando, de onde e com que resultado.
2) `userIdentity` (quem), `eventSource` + `eventName` (o quê) e `sourceIPAddress`/`userAgent` (de onde e com quê).
3) Cerca de 90 dias, apenas eventos de gerenciamento, por região.
4) CloudTrail audita chamadas de API; CloudWatch mede desempenho e saúde; Config registra e avalia o estado das configurações.
5) Mostram tentativas bloqueadas, que podem indicar reconhecimento ou uso indevido de credenciais.
6) Quando se precisa de retenção longa, eventos de dados ou Insights, entrega em S3/CloudWatch Logs e cobertura multirregião ou da organização.
