### Tipos de eventos do CloudTrail — management, data, Insights, network activity, seletores avançados e custo

> [!warning] Aviso
> Tipos de evento, preços, limites de seletores e recursos suportados mudam com frequência. Os números aqui são referências de estudo; confirme na documentação. Os comandos **não foram executados**.

O CloudTrail não registra tudo da mesma forma. Os eventos são divididos em **tipos**, com **volume, custo e finalidade diferentes**: os **management events** (plano de controle), os **data events** (plano de dados, alto volume), os **Insights events** (atividade incomum) e os **network activity events** (atividade de rede em endpoints de VPC). Escolher bem o que registrar equilibra **visibilidade** e **custo**.

**Analogia:** num prédio, os **management events** são o registro de **quem mudou fechaduras, chaves e regras de acesso**; os **data events** são o registro de **cada vez que alguém abriu cada gaveta de cada armário** (volume enorme); os **Insights** são o **alerta do porteiro** dizendo "hoje estão mexendo nas fechaduras muito mais do que o normal".

---

## Visão geral dos tipos

| Tipo | O que registra | Volume | Habilitado por padrão em trilha? |
|---|---|---|---|
| **Management events** | Operações de **controle** (criar, alterar, excluir recursos; IAM; login no console) | Moderado | **Sim** (leitura e escrita) |
| **Data events** | Operações **nos dados** de recursos (S3 objetos, Lambda invoke, DynamoDB itens...) | **Muito alto** | **Não** |
| **Insights events** | **Anomalias** na taxa de chamadas de escrita ou nas taxas de erro | Baixo | **Não** |
| **Network activity events** | Chamadas feitas por **endpoints de VPC** (permitidas e negadas) | Variável | **Não** |

```
 Quantidade de eventos (aproximada)

 management ▏██                      mudanças de configuração
 data       ▏████████████████████    cada GetObject/PutObject/Invoke
 insights   ▏▌                       só quando há anomalia
```

## Management events (plano de controle)

São operações que **gerenciam recursos AWS**.

| Exemplos | Serviço |
|---|---|
| `RunInstances`, `TerminateInstances`, `AuthorizeSecurityGroupIngress` | EC2 |
| `CreateUser`, `AttachRolePolicy`, `AssumeRole` | IAM/STS |
| `CreateBucket`, `PutBucketPolicy`, `DeleteBucket` | S3 (no nível do bucket) |
| `CreateTrail`, `StopLogging` | CloudTrail |
| `ConsoleLogin` | Login |
| `CreateDBInstance`, `ModifyDBInstance` | RDS |

Eles se dividem em **leitura** (`Describe*`, `List*`, `Get*` de configuração) e **escrita** (`Create*`, `Delete*`, `Modify*`). Uma trilha pode capturar **ambos**, só **escrita** ou só **leitura**.

> [!tip] Escrita é o essencial; leitura ajuda a detectar reconhecimento
> Registrar só **escrita** reduz volume, mas perde sinais de **reconhecimento** (muitos `List*`/`Describe*` de um invasor). Para segurança, vale registrar **leitura e escrita**.

### Custo dos management events

| Item | Referência |
|---|---|
| Event history (90 dias) | Sem custo |
| **Primeira cópia** de management events por região em uma trilha | Sem custo adicional (além do S3) |
| **Cópias adicionais** (segunda trilha etc.) | Cobradas por volume |

## Data events (plano de dados)

Registram o que acontece **dentro dos recursos**, normalmente em alto volume. **Não são habilitados por padrão**.

| Recurso | Evento de dados |
|---|---|
| **S3** | `GetObject`, `PutObject`, `DeleteObject` (objetos) |
| **Lambda** | `Invoke` de funções |
| **DynamoDB** | Operações em itens (`GetItem`, `PutItem`) |
| **EBS direct APIs, SNS, SQS, Kinesis, Glue, outros** | Conforme o serviço suportado |
| **S3 Object Lambda, Access Points** | Acessos por esses pontos |

```bash
# Habilita data events de S3 apenas para um bucket sensível (seletores avançados)
aws cloudtrail put-event-selectors --trail-name trilha-principal \
  --advanced-event-selectors '[
    {"Name":"S3 do bucket sensivel",
     "FieldSelectors":[
       {"Field":"eventCategory","Equals":["Data"]},
       {"Field":"resources.type","Equals":["AWS::S3::Object"]},
       {"Field":"resources.ARN","StartsWith":["arn:aws:s3:::dados-sensiveis/"]}
     ]}
  ]'
```

> [!warning] Data events podem custar mais que tudo
> Registrar **todos os objetos de todos os buckets** pode gerar **bilhões de eventos** e uma conta alta. Habilite **seletivamente**: buckets com dados sensíveis, regulados ou críticos.

### O que o evento de dados responde

| Pergunta | Evento |
|---|---|
| Quem baixou o arquivo confidencial? | `GetObject` |
| Quem apagou os objetos? | `DeleteObject` |
| Qual função foi invocada, por quem? | `Invoke` |
| Houve exfiltração em massa? | Volume atípico de `GetObject` |

## Seletores de eventos: básico vs avançado

| Tipo | Capacidade |
|---|---|
| **Event selectors (básicos)** | Escolher read/write e recursos por ARN (S3, Lambda, DynamoDB) |
| **Advanced event selectors** | Filtros por **campo**: `eventName`, `resources.ARN`, `readOnly`, `userIdentity.arn`, `eventCategory`... com `Equals`, `StartsWith`, `NotEquals` |

Os **seletores avançados** permitem, por exemplo:

| Objetivo | Filtro |
|---|---|
| Só **escritas** em S3 sensível | `readOnly = false` + ARN do bucket |
| Excluir um bucket de logs barulhento | `resources.ARN NotStartsWith` |
| Só eventos de uma identidade | `userIdentity.arn` |
| Excluir `kms:Decrypt` muito frequente | `eventName NotEquals` |

> [!tip] Comece restritivo e amplie
> Registre dados apenas dos **recursos críticos**, observe o volume e o custo por uma semana e só então amplie. É mais fácil adicionar do que explicar uma fatura.

## Insights events

O **CloudTrail Insights** analisa continuamente os **management events de escrita** (e, conforme configuração, a **taxa de erros**) para detectar **atividade incomum** em relação à linha de base da conta.

| Tipo de insight | O que detecta |
|---|---|
| **ApiCallRateInsight** | Pico anormal na **taxa de chamadas** de uma API de escrita |
| **ApiErrorRateInsight** | Pico anormal de **erros** em chamadas de API |

```
 chamadas/min de RunInstances
  │            ╭─╮   ← Insights event: taxa muito acima do normal
  │ ──────────╯  ╰─────────
  └──────────────────────────► tempo
```

Casos típicos: **credenciais vazadas** subindo centenas de instâncias para mineração, **loop de automação** que cria recursos sem parar, **limites de serviço** sendo estourados (aumento de erros `Throttling`).

```bash
aws cloudtrail put-insight-selectors --trail-name trilha-principal \
  --insight-selectors '[{"InsightType":"ApiCallRateInsight"},{"InsightType":"ApiErrorRateInsight"}]'
```

> [!warning] Insights é cobrado separadamente
> Cobra-se pela quantidade de eventos de gerenciamento **analisados**. Habilite onde a detecção compensa (contas de produção), e não indiscriminadamente.

## Network activity events

Registram chamadas de API feitas **através de endpoints de VPC**, incluindo **tentativas negadas** por política do endpoint. Úteis para detectar **exfiltração por rede privada** e validar que as políticas de endpoint bloqueiam o que deveriam.

| Caso | Valor |
|---|---|
| Endpoint de VPC para S3/outros serviços | Ver quais chamadas passam e quais são negadas |
| Perímetro de dados | Provar que só identidades da organização usam o endpoint |
| Investigação | Origem de chamadas de dentro da VPC |

## Escolhendo o que registrar

| Necessidade | Configuração sugerida |
|---|---|
| Auditoria básica de toda a conta | Trilha multirregião, **management read+write** |
| Dados regulados/sensíveis | **Data events** seletivos nos buckets e tabelas críticos |
| Detecção de abuso de credenciais | **Insights** nas contas de produção |
| Perímetro de rede privada | **Network activity** em endpoints relevantes |
| Retenção e consulta SQL ágil | **CloudTrail Lake** (event data store) |

```
 Dados críticos?
 ├─ Sim ─► data events seletivos (ARN do recurso) + Object Lock no bucket de logs
 └─ Não ─► management events bastam
 Preciso de alerta de comportamento incomum?
 ├─ Sim ─► Insights (produção)
 └─ Não ─► alarmes por metric filter no CloudWatch Logs
```

## Estimando o volume antes de habilitar

| Pergunta | Como estimar |
|---|---|
| Quantos objetos o bucket recebe por dia? | Métricas de requisição do S3 (`GetRequests`, `PutRequests`) |
| Quantas invocações Lambda por dia? | Métrica `Invocations` do CloudWatch |
| Quanto custaria registrar tudo? | Volume diário × preço por 100 mil eventos × 30 dias |

Uma regra prática: se o recurso recebe **milhões de requisições por dia**, avalie registrar só **escritas** ou só um **prefixo** crítico, em vez de leituras de tudo.

---

## Exemplo prático: auditoria dirigida de um bucket de dados

1. O bucket `dados-clientes` guarda informações pessoais.
2. Uma trilha com **advanced event selectors** registra `GetObject`, `PutObject` e `DeleteObject` **só desse bucket**.
3. O restante da conta registra apenas **management events**.
4. **Insights** está ativo na conta de produção.
5. Uma consulta no Athena mostra, por identidade e IP, quem leu objetos nas últimas 24 h.
6. Um alarme avisa se `DeleteObject` ocorrer fora do horário comercial.

## Troubleshooting

| Sintoma | Causa provável | Como resolver |
|---|---|---|
| Não vejo `GetObject` | Data events não habilitados | Configurar seletores de dados |
| Fatura do CloudTrail alta | Data events em tudo ou várias trilhas | Restringir seletores; unificar trilhas |
| Insights não aparece | Não habilitado ou sem linha de base | Habilitar e aguardar aprendizado |
| Falta leitura de IAM | Trilha só com escrita | Incluir read events |
| Seletor não aplica | Sintaxe/campo incorreto | Validar com `get-event-selectors` |
| Eventos de rede ausentes | Network activity não habilitado | Configurar para o endpoint |

---

## Erros comuns e armadilhas

- **Achar que o CloudTrail já registra acessos a objetos do S3** por padrão.
- **Habilitar data events em tudo** sem estimar custo.
- **Registrar só escrita** e perder sinais de reconhecimento.
- **Duas ou mais trilhas idênticas** cobrando cópias extras.
- **Esquecer eventos globais** (IAM) na trilha multirregião.
- **Ligar Insights sem alguém para tratar os alertas.**
- **Não filtrar eventos muito frequentes** (como `kms:Decrypt` de serviços) quando irrelevantes.
- **Ignorar o limite de seletores** ao desenhar filtros complexos.

## 🧩 Quiz de Fixação

1. Qual a diferença entre management events e data events?
2. Data events vêm habilitados por padrão?
3. O que o CloudTrail Insights detecta?
4. Para que servem os advanced event selectors?
5. Por que registrar também eventos de leitura de gerenciamento?
6. Como evitar custo excessivo com data events?

**Respostas:**
1) Management events registram operações de controle sobre recursos; data events registram operações nos dados dentro dos recursos (objetos S3, invocações Lambda), em alto volume.
2) Não; é preciso habilitá-los na trilha.
3) Atividade incomum: picos anormais na taxa de chamadas de escrita ou nas taxas de erro de API em relação à linha de base da conta.
4) Para filtrar por campos (nome do evento, ARN, readOnly, identidade etc.) e registrar apenas o necessário.
5) Porque rajadas de chamadas de leitura (List/Describe) podem indicar reconhecimento por um invasor.
6) Habilitando seletivamente apenas para recursos críticos, filtrando eventos irrelevantes e evitando trilhas duplicadas.
