### O que é AWS Service Catalog — catálogo de produtos aprovados, portfolios, products, autoatendimento governado e quando usar

> [!warning] Aviso
> Tipos de produto suportados, limites, preços, nomes de constraints e integrações mudam. Os números aqui são referências de estudo; confirme na documentação oficial. Os comandos de CLI são exemplos e **não foram executados**.

O **AWS Service Catalog** permite que uma organização crie um **catálogo de produtos de TI aprovados** (ambientes, servidores, bancos, aplicações, redes) e os **ofereça em autoatendimento** a equipes e usuários, **com governança embutida**. Em vez de cada desenvolvedor montar sua própria VPC, banco ou instância do jeito que achar melhor (e fora dos padrões de segurança), a equipe de plataforma publica **produtos pré-validados** e os usuários **lançam o que precisam com poucos cliques**, dentro das regras da empresa.

A ideia central: **velocidade para quem consome, controle para quem governa**. O desenvolvedor não precisa de permissões amplas na conta, e a organização não perde padronização, conformidade nem rastreabilidade de custo.

**Analogia:** é a **vitrine de um catálogo corporativo de compras**. O departamento de compras (equipe de plataforma) negocia e aprova os itens (produtos) e os organiza em seções (portfolios). Os funcionários (usuários finais) **escolhem da vitrine** sem negociar nada, e o pedido é atendido **com as regras da empresa já aplicadas** (orçamento, fornecedor aprovado, etiqueta de centro de custo). Ninguém precisa ser comprador para pedir uma cadeira aprovada.

---

## O problema que o Service Catalog resolve

| Problema sem catálogo | Efeito |
|---|---|
| Cada time cria infraestrutura **do seu jeito** | Inconsistência, falhas de segurança, difícil de operar |
| Desenvolvedores precisam de **permissões amplas** para provisionar | Risco de escalada de privilégios e incidentes |
| **Fila no time de plataforma** para cada pedido | Lentidão, gargalo, frustração |
| Conformidade verificada **depois** | Retrabalho e exposição |
| Custos **sem rastreio** por projeto | Contas surpresa |
| Templates **copiados e adulterados** | Versões divergentes em produção |

**Solução:** produtos **versionados**, com **permissões controladas** (launch constraints), **parâmetros restritos** (template constraints), **tags automáticas** e **ciclo de vida gerenciado**.

## Conceitos centrais

```
 ┌─────────────────────────── PORTFOLIO "Dados e Analytics" ───────────────────────────┐
 │                                                                                    │
 │   PRODUCT "Banco PostgreSQL padrão"   PRODUCT "Data lake básico"   PRODUCT ...     │
 │    ├─ versão v1.0                      ├─ versão v1.0                                │
 │    ├─ versão v1.1 (ativa)              └─ versão v2.0                                │
 │    └─ versão v2.0                                                                  │
 │                                                                                    │
 │   CONSTRAINTS: launch role • template rules • notificações • tags (TagOptions)     │
 │   ACESSO: grupos/roles IAM autorizados a ver e lançar                              │
 └────────────────────────────────────────────────────────────────────────────────────┘
                                   │ usuário lança
                                   ▼
                       PROVISIONED PRODUCT  (instância do produto: stack de CloudFormation,
                                              workspace Terraform...) na conta do usuário
```

| Conceito | O que é |
|---|---|
| **Product (produto)** | Um item oferecido: normalmente um **template** (CloudFormation) que cria recursos; também pode ser Terraform (via engines) ou produto do Marketplace |
| **Provisioning artifact (versão)** | Uma **versão** do produto (v1.0, v1.1...), cada uma com seu template |
| **Portfolio** | **Coleção de produtos** com acesso e regras comuns |
| **Constraint (restrição)** | Regra aplicada a um produto num portfolio: **launch**, **notification**, **template**, **StackSet**, **resource update** |
| **Launch role** | Role que o Service Catalog **assume** para criar os recursos (o usuário não precisa de permissão direta) |
| **TagOptions** | Pares chave/valor de tags **permitidos ou obrigatórios** |
| **Provisioned product** | **Instância** de um produto lançado por um usuário |
| **Service action** | Ação operacional (documento do SSM) disponível sobre um produto provisionado (ex.: reiniciar, fazer backup) |
| **Administrador do catálogo** | Quem cria/gerencia portfolios e produtos (equipe de plataforma) |
| **Usuário final** | Quem navega e lança produtos |

---

## Os dois papéis

| Papel | O que faz | Permissões típicas |
|---|---|---|
| **Administrador do catálogo** | Cria portfolios, produtos, versões, constraints, compartilha | `servicecatalog:*` de administração; `AWSServiceCatalogAdminFullAccess` (gerenciada) |
| **Usuário final** | Lista produtos disponíveis e lança/atualiza/encerra os seus | `servicecatalog:ListPortfolios`, `ProvisionProduct`, etc.; `AWSServiceCatalogEndUserFullAccess` (gerenciada) |

> [!tip] Separação de poderes é o valor central
> O **usuário final não precisa de permissão para criar EC2, RDS ou VPC**. Ele só precisa poder **pedir o produto**; quem **cria** os recursos é a **launch role**, e o que pode ser criado é definido **pelo template aprovado**.

## Como funciona o fluxo de ponta a ponta

```
 1. ADMIN publica      → template (CloudFormation) validado, em S3 ou Git
 2. ADMIN cria produto → com versão v1.0, dentro de um portfolio
 3. ADMIN configura    → launch constraint (role), template constraint, TagOptions
 4. ADMIN concede      → acesso a grupos/roles IAM (ex.: "Desenvolvedores")
 5. USUÁRIO navega     → vê só os produtos autorizados para ele
 6. USUÁRIO lança      → informa os parâmetros permitidos (nome, tamanho, ambiente)
 7. SERVICE CATALOG    → assume a launch role, cria a stack, aplica as tags
 8. USUÁRIO gerencia   → atualiza para nova versão, executa service actions, encerra
```

```bash
# Usuário final: lista produtos disponíveis
aws servicecatalog search-products --query 'ProductViewSummaries[].[Name,ProductId]'

# Lança um produto
aws servicecatalog provision-product \
  --product-id prod-abc123 \
  --provisioning-artifact-id pa-xyz789 \
  --provisioned-product-name banco-pedidos-dev \
  --provisioning-parameters Key=Ambiente,Value=dev Key=Tamanho,Value=pequeno

# Acompanha
aws servicecatalog describe-provisioned-product --name banco-pedidos-dev
```

## Tipos de produto

| Tipo | Descrição | Observações |
|---|---|---|
| **CloudFormation** | Template YAML/JSON que cria uma stack por lançamento | O mais comum |
| **Terraform (Open Source / Cloud / Enterprise)** | Via **engines** de provisionamento (Terraform Reference Engine) | Permite reaproveitar módulos Terraform no catálogo |
| **Marketplace** | Produtos de terceiros assinados no AWS Marketplace | Aparecem no catálogo interno |
| **Externos (engines customizados)** | Integração via engine com outras ferramentas | Casos avançados |

## Service Catalog vs outras opções

| Critério | Console direto | CloudFormation direto | **Service Catalog** | AWS Proton |
|---|---|---|---|---|
| Quem executa | Quem tem permissão ampla | Quem tem permissão para a stack | **Usuário com permissão mínima** (launch role) | Equipes de plataforma/desenvolvimento |
| Governança | Nenhuma | Pipeline/PR | **Catálogo, constraints, tags, versões** | Templates de ambiente/serviço |
| Autoatendimento | Parcial | Não | **Sim** | Sim (foco em apps containerizadas/serverless) |
| Versões e atualização | Manual | Por stack | **Versões do produto + atualização do provisionado** | Versões de templates |
| Multi-conta | Manual | StackSets | **Compartilhamento de portfolios** | Contas de ambiente |
| Ideal para | Exploração | IaC por times técnicos | **Autoatendimento governado** | Plataformas de aplicação |

```
 O time de plataforma quer entregar "blocos aprovados" a muitos times, com permissões mínimas? ─► Service Catalog
 Quer modelar ambientes e serviços de aplicações com pipelines integrados?                    ─► AWS Proton
 Só precisa versionar infraestrutura para um time técnico?                                    ─► CloudFormation + pipeline
```

## Casos de uso

| Caso | Exemplo de produto |
|---|---|
| **Ambientes de desenvolvimento** | "Sandbox de desenvolvedor" com VPC, instância e limite de custo |
| **Bancos de dados padrão** | RDS com backup, criptografia e Multi-AZ já configurados |
| **Redes e conectividade** | VPC padrão com subnets, endpoints e logs |
| **Workstations / bastions** | Instância com ferramentas aprovadas e SSM |
| **Ambientes de ciência de dados** | Notebook + bucket + permissões |
| **Contas novas (landing zone)** | Baseline via portfolio compartilhado |
| **Conformidade** | Só produtos que atendem às políticas (criptografia, tags, logging) |

## Benefícios e limitações

| Benefício | Limitação |
|---|---|
| Autoatendimento com **menor privilégio** | Exige **trabalho de curadoria** da equipe de plataforma |
| **Padronização e conformidade** por construção | Produtos precisam ser **mantidos e versionados** |
| **Rastreio de custo** via tags | Flexibilidade limitada ao que o template expõe |
| **Atualização controlada** das instâncias | Atualizar um produto em massa exige processo |
| **Compartilhamento multi-conta** | Gerenciar acesso e imports em muitas contas dá trabalho |
| Integra com **Organizations, SSM, Budgets** | Curva de aprendizado de constraints |

## Exemplo prático: "banco de dados padrão" em autoatendimento

1. A equipe de plataforma escreve um template de **RDS PostgreSQL** com criptografia, backups, Multi-AZ opcional e parâmetros limitados (`Ambiente`, `Tamanho`).
2. Cria o produto **"PostgreSQL padrão"** (versão v1.0) no portfolio **"Dados"**.
3. Define uma **launch role** com permissões só para criar RDS e recursos associados.
4. Adiciona **TagOptions** (`CentroDeCusto` obrigatória) e uma **template constraint** limitando `Tamanho` a `pequeno/medio` em dev.
5. Concede acesso ao grupo **Desenvolvedores**.
6. Um desenvolvedor lança o produto em 2 minutos, sem permissão de RDS na conta.
7. Meses depois, a v1.1 corrige uma configuração; os produtos provisionados podem ser **atualizados** para a nova versão.

## Erros comuns e armadilhas

- **Criar produtos sem launch role** e dar ao usuário permissões amplas ("para funcionar").
- **Launch role administradora** que anula o ganho de menor privilégio.
- **Templates sem parâmetros restritos**, permitindo qualquer configuração.
- **Sem versionamento disciplinado**: alterar o template "no lugar" em vez de criar nova versão.
- **Catálogo grande demais e desorganizado**, que ninguém entende.
- **Esquecer tags de custo** e perder rastreio.
- **Não manter o catálogo**: produtos obsoletos com versões antigas e vulneráveis.
- **Tratar o Service Catalog como substituto de pipeline de IaC**: ele **complementa** o pipeline, não o substitui.

## 🧩 Quiz de Fixação

1. O que é um portfolio e o que é um product?
2. Qual a função da launch role?
3. O que é um provisioned product?
4. Qual a diferença entre administrador do catálogo e usuário final?
5. Que tipos de produto o Service Catalog suporta?
6. Qual o principal benefício de segurança do Service Catalog?

**Respostas:**
1) O portfolio é uma coleção de produtos com acesso e regras comuns; o product é um item oferecido, normalmente um template que cria recursos, com versões.
2) É a role que o Service Catalog assume para criar os recursos, permitindo que o usuário final lance o produto sem ter permissões diretas sobre os recursos.
3) A instância de um produto lançada por um usuário (por exemplo, uma stack CloudFormation criada a partir do template).
4) O administrador cria e governa portfolios, produtos, versões, constraints e compartilhamentos; o usuário final navega e lança os produtos autorizados.
5) CloudFormation, Terraform (por engines), produtos do AWS Marketplace e engines externos customizados.
6) Autoatendimento com menor privilégio: o usuário só pede o produto aprovado, e quem cria os recursos é uma role controlada, limitada pelo template.
