### Governança no Service Catalog — constraints de launch, template, notification e StackSet, launch roles, TagOptions, acesso e budgets

> [!warning] Aviso
> Tipos de constraint, sintaxe de regras, limites e comportamento de TagOptions e budgets mudam. Os detalhes aqui são referências de estudo; confirme na documentação. Os comandos e documentos **não foram executados**.

O que diferencia o Service Catalog de "um bucket com templates" é a **governança embutida**. Sem ela, o catálogo é só uma lista; com ela, cada lançamento acontece **com permissões mínimas, parâmetros restritos, tags obrigatórias, notificações e controle de custo**. As ferramentas são as **constraints** (restrições), as **launch roles**, as **TagOptions**, o **controle de acesso** a portfolios e a **associação com budgets**. Esta folha mostra como combinar tudo para entregar **autoatendimento seguro**.

**Analogia:** o catálogo é um **balcão de empréstimo de ferramentas** de uma empresa. As **constraints** são as regras do balcão ("só empresta furadeira com crachá de técnico", "devolver em 3 dias"); a **launch role** é o **almoxarife**, que busca a ferramenta com a chave do estoque (o funcionário nunca entra no estoque); as **TagOptions** são a **etiqueta obrigatória** de centro de custo; os **budgets** são o **limite mensal** de empréstimos do setor.

---

## Visão geral dos controles

| Controle | O que governa | Onde se aplica |
|---|---|---|
| **Launch constraint** | **Quem executa** a criação dos recursos (role) | Produto em um portfolio |
| **Template constraint** | **Quais valores de parâmetros** são permitidos | Produto em um portfolio |
| **Notification constraint** | **Avisos** (SNS) sobre eventos do produto | Produto em um portfolio |
| **StackSet constraint** | Implantar o produto em **várias contas/regiões** | Produto em um portfolio |
| **Resource update constraint** | Se **tags** de recursos podem ser alteradas em atualizações | Produto em um portfolio |
| **TagOptions** | **Tags** permitidas/obrigatórias | Portfolio ou produto |
| **Acesso ao portfolio** | **Quem vê e lança** | Portfolio |
| **Budgets** | **Limite de gasto** associado | Portfolio ou produto |

> [!tip] Constraints valem por portfolio
> A mesma **versão de produto** pode ter regras **diferentes** em portfolios diferentes (ex.: `Tamanho` livre no portfolio de "Plataforma" e restrito no de "Desenvolvedores"). Isso permite **reutilizar o produto** com governança distinta por público.

## Launch constraint (a mais importante)

A **launch constraint** define **uma role IAM** que o Service Catalog **assume** para criar, atualizar e excluir os recursos do produto. O usuário **não precisa** de permissão sobre esses recursos.

```
 Usuário (poucas permissões)
   │  servicecatalog:ProvisionProduct
   ▼
 Service Catalog ──assume──► LaunchRole (permissões para criar RDS, SG, KMS...)
                                   │
                                   ▼
                              CloudFormation / recursos
```

| Forma | Descrição | Quando usar |
|---|---|---|
| **Role específica (ARN)** | Uma role fixa na conta administradora | Uma única conta |
| **Local role name** | Nome de role que **existe em cada conta** com o produto compartilhado | **Multi-conta**: cada conta tem sua role com o mesmo nome |
| **Sem launch constraint** | Usa as **permissões do usuário** | Evitar; exige permissões amplas |

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {"Effect": "Allow",
     "Action": ["rds:*","ec2:Describe*","kms:CreateGrant","kms:Decrypt","kms:GenerateDataKey",
                "cloudformation:*","s3:GetObject","iam:PassRole"],
     "Resource": "*"}
  ]
}
```

(Exemplo ilustrativo: restrinja `Resource` e `Action` ao **mínimo** que o produto exige.)

A **trust policy** da role deve permitir ao serviço `servicecatalog.amazonaws.com` assumi-la.

```bash
aws servicecatalog associate-principal-with-portfolio ...      # quem acessa
aws servicecatalog create-constraint --portfolio-id port-xyz --product-id prod-abc \
  --type LAUNCH \
  --parameters '{"RoleArn":"arn:aws:iam::123456789012:role/SCLaunchRolePostgres"}'
```

> [!warning] Launch role ampla demais = escalada de privilégios
> Se a launch role for `AdministratorAccess` e o template permitir recursos arbitrários, o usuário consegue **fazer qualquer coisa** através do produto. Aplique **menor privilégio** e **mantenha o template restrito**.

## Template constraints

As **template constraints** usam **regras** (semelhantes às `Rules` do CloudFormation) para **limitar combinações de parâmetros** com base em condições.

```json
{
  "Rules": {
    "TamanhoEmDev": {
      "RuleCondition": {"Fn::Equals": [{"Ref": "Ambiente"}, "dev"]},
      "Assertions": [
        {
          "Assert": {"Fn::Contains": [["pequeno", "medio"], {"Ref": "Tamanho"}]},
          "AssertDescription": "Em dev só é permitido tamanho pequeno ou medio"
        }
      ]
    },
    "ProdExigeMultiAz": {
      "RuleCondition": {"Fn::Equals": [{"Ref": "Ambiente"}, "prod"]},
      "Assertions": [
        {"Assert": {"Fn::Equals": [{"Ref": "MultiAz"}, "true"]},
         "AssertDescription": "Produção exige Multi-AZ"}
      ]
    }
  }
}
```

| Exemplo de regra | Efeito |
|---|---|
| Tamanho máximo por ambiente | Evita custo descontrolado |
| Região permitida | Só `sa-east-1` e `us-east-1` |
| Criptografia obrigatória | Impede desabilitar |
| Janela de backup | Valores válidos apenas |
| Campos dependentes | "Se Ambiente=prod, MultiAz=true" |

> [!tip] Regras no portfolio, não no template
> Colocar as regras como **template constraints** permite **ajustar a governança** sem criar nova versão do produto. O template fica genérico; as regras variam por portfolio/público.

## Notification constraint

Associa um **tópico SNS** que recebe **eventos da stack** do produto provisionado (criação, falha, exclusão).

| Uso | Exemplo |
|---|---|
| **Aviso à equipe de plataforma** | Falha de provisionamento |
| **Auditoria** | Registro de eventos |
| **Integração** | Dispara automação (Lambda) para abrir ticket |

```bash
aws servicecatalog create-constraint --portfolio-id port-xyz --product-id prod-abc \
  --type NOTIFICATION --parameters '{"NotificationArns":["arn:aws:sns:us-east-1:123456789012:catalogo-eventos"]}'
```

---

## StackSet constraint

Permite que um produto seja **implantado em várias contas e regiões** por **StackSets** (em vez de uma stack única).

| Elemento | Descrição |
|---|---|
| **Contas e regiões** | Lista de destinos |
| **Role de administração/execução** | Permissões do StackSet |
| **Ordem de implantação** | Controle de regiões/ contas |

Útil para **baselines de contas** (CloudTrail, Config, roles de auditoria) oferecidos como produto.

## TagOptions e tags

**TagOptions** definem **tags e seus valores permitidos**, impondo **padronização** e **rastreio de custo**.

```bash
aws servicecatalog create-tag-option --key CentroDeCusto --value CC-1001
aws servicecatalog create-tag-option --key CentroDeCusto --value CC-2002
aws servicecatalog associate-tag-option-with-resource --resource-id port-xyz --tag-option-id tag-abc
```

| Mecanismo | Efeito |
|---|---|
| **TagOption associada ao portfolio/produto** | O usuário **escolhe** entre os valores permitidos ao lançar |
| **Tags do produto** | Tags aplicadas **automaticamente** a todos os recursos criados |
| **Tags de sistema** (`aws:servicecatalog:*`) | Identificam portfolio, produto e provisionado |
| **Tags de alocação de custo** | Habilitadas no Billing para relatórios por tag |
| **Resource update constraint** | Define se tags podem ser alteradas em atualizações |

> [!tip] Tags automáticas = custo rastreável
> Ative as **tags de alocação de custo** (as do Service Catalog e as suas, como `CentroDeCusto`) no Billing. Assim, o Cost Explorer mostra **quanto cada produto, portfolio e time gasta**.

## Controle de acesso

O acesso é concedido **por portfolio**, a **principais IAM** (grupo, usuário ou role).

| Forma | Observação |
|---|---|
| **Grupos/roles IAM** | Associados ao portfolio (`associate-principal-with-portfolio`) |
| **Por nome de role/grupo (IAM Identity Center)** | Padrão com `IAM_PATTERN` (ex.: `arn:aws:iam:::role/DevRole*`) para funcionar **em várias contas** |
| **Política IAM do usuário** | Precisa das permissões de **usuário final** do Service Catalog |

```
 Portfolio "Dados"      ← acesso: grupo "Analistas" e role "DataEngineer"
 Portfolio "Sandbox"    ← acesso: grupo "Desenvolvedores"
 Portfolio "Rede"       ← acesso: somente "Plataforma"
```

| Boa prática | Motivo |
|---|---|
| **Portfolios por público** | Cada grupo vê só o que precisa |
| **Roles do SSO** como principais | Acesso por identidade corporativa |
| **Revisão periódica de acessos** | Remover quem saiu/mudou de função |
| **Administradores distintos** dos usuários finais | Separação de funções |

## Budgets

O Service Catalog pode **associar um AWS Budget** a um **portfolio** ou **produto**.

| Elemento | Função |
|---|---|
| **Budget (por tag)** | Acompanha o gasto dos recursos com as tags do produto |
| **Alertas** | Notificam ao atingir 80% / 100% |
| **Ação do budget** (opcional) | Pode acionar políticas de restrição (ex.: bloquear novos lançamentos) |

```bash
aws servicecatalog associate-budget-with-resource --budget-name orcamento-sandbox --resource-id port-xyz
```

Combine com **TTL** de ambientes efêmeros para controlar custo ativamente.

## Modelo completo de governança (exemplo)

```
 Portfolio "Sandbox do desenvolvedor"
 ├─ Acesso: grupo Desenvolvedores
 ├─ TagOptions: CentroDeCusto (valores permitidos), Responsavel
 ├─ Budget: US$ X/mês com alertas
 └─ Produto "Sandbox padrão" v1.0
     ├─ Launch constraint: SCLaunchRoleSandbox (menor privilégio)
     ├─ Template constraint: instância ≤ t3.large, regiões permitidas
     ├─ Notification constraint: SNS catalogo-eventos
     └─ Service actions: Parar ambiente, Iniciar ambiente
```

| Pergunta | Controle que responde |
|---|---|
| Quem pode lançar? | Acesso ao portfolio |
| Com quais permissões os recursos são criados? | Launch constraint |
| O que o usuário pode escolher? | Template constraint, parâmetros do template |
| Como rastrear o custo? | TagOptions + tags de alocação + budgets |
| Como ser avisado de problemas? | Notification constraint |
| Como operar sem acesso direto? | Service actions |

| Camada | Ferramenta |
|---|---|
| **Pré-catálogo** | Revisão de templates (PR), cfn-lint, Guard |
| **No catálogo** | Constraints, launch roles, TagOptions |
| **Em runtime** | CloudFormation Hooks, SCPs |
| **Pós-lançamento** | AWS Config, Security Hub |
| **Custo** | Budgets, Cost Anomaly Detection |

## Exemplo prático: portfolio "Dados" com governança

1. A plataforma cria o produto **"Data lake básico"** (S3 + Glue + Athena).
2. **Launch role** com permissões só para esses serviços, com `iam:PassRole` restrito.
3. **Template constraint:** região fixa, criptografia obrigatória, nome do bucket com padrão da empresa.
4. **TagOptions:** `CentroDeCusto` (lista aprovada) e `Dono`.
5. **Notification:** falhas vão ao canal da plataforma.
6. **Budget** por tag `Projeto` alerta a 80% do orçamento.
7. Somente o grupo **Analistas** vê o portfolio; as ações de operação são **service actions**.

## Troubleshooting

| Sintoma | Causa provável | Como resolver |
|---|---|---|
| `AccessDenied` ao lançar | Launch role sem permissão ou trust incorreta | Ajustar role e trust para `servicecatalog.amazonaws.com` |
| Launch role "não encontrada" em outra conta | Usou ARN em vez de **local role name** | Usar local role name e criar a role em cada conta |
| Regra de template não dispara | Sintaxe/RuleCondition incorreta | Testar a regra; ver mensagens de assertiva |
| Usuário não vê produto | Sem acesso ao portfolio | Associar principal (grupo/role) |
| Tags não aparecem no billing | Tags de alocação não ativadas | Ativar no Billing |
| Notificação não chega | Política do tópico SNS | Permitir publicação do serviço |
| Budget não alerta | Filtro de tag incorreto | Revisar escopo e tags |
| Constraint conflitante | Duas launch constraints no mesmo produto/portfolio | Manter apenas uma por produto/portfolio |

## Erros comuns e armadilhas

- **Sem launch constraint**, exigindo permissões amplas dos usuários.
- **Launch role com `*:*`**.
- **Template sem restrições** de parâmetros e sem template constraints.
- **ARN fixo de role** em portfolios compartilhados (use local role name).
- **TagOptions ausentes**, perdendo rastreio de custo.
- **Sem revisão de acessos** dos portfolios.
- **Budgets apenas informativos** em ambientes sem TTL.
- **Confiar só no catálogo** e esquecer SCPs/Config para o que for criado fora dele.

## 🧩 Quiz de Fixação

1. Qual a função da launch constraint?
2. Para que serve uma template constraint?
3. Qual a vantagem do "local role name" em produtos compartilhados?
4. O que fazem as TagOptions?
5. Como o Service Catalog ajuda no controle de custo?
6. Por que aplicar constraints no portfolio e não só no template?

**Respostas:**
1) Define a role que o Service Catalog assume para criar os recursos, permitindo que o usuário lance o produto sem permissões diretas.
2) Limitar valores e combinações de parâmetros por regras (por exemplo, tamanho máximo em dev), validando a escolha do usuário.
3) Cada conta usa a role de mesmo nome que existe nela, permitindo reaproveitar o produto compartilhado em várias contas sem ARN fixo.
4) Definem tags e valores permitidos ou obrigatórios, padronizando etiquetas e permitindo rastrear custo.
5) Com tags automáticas e de alocação, TagOptions, budgets associados a portfolios/produtos e TTL de ambientes efêmeros.
6) Porque assim a mesma versão do produto pode ter governança diferente por público, sem criar novas versões do template.
