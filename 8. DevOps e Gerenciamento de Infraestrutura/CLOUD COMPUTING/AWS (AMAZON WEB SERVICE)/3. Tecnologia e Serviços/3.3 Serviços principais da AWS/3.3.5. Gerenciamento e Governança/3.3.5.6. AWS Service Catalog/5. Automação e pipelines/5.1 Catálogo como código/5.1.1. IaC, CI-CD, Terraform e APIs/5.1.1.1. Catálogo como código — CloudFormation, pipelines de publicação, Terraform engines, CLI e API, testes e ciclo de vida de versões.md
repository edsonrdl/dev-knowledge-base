### Catálogo como código — CloudFormation, pipelines de publicação, Terraform engines, CLI/API, testes e ciclo de vida de versões

> [!warning] Aviso
> Recursos do CloudFormation/Terraform para o Service Catalog, engines de provisionamento, limites de API e nomes de integrações mudam. Os exemplos aqui são referências de estudo; confirme na documentação. Os comandos **não foram executados**.

Um catálogo mantido **clicando no console** vira rapidamente uma bagunça: versões sem histórico, constraints esquecidas, portfolios diferentes entre contas. A prática profissional é tratar o **catálogo como código**: **portfolios, produtos, constraints, TagOptions e compartilhamentos** definidos em **templates versionados**, **revisados por pull request**, **testados** e **publicados por pipeline**. Assim o catálogo se torna **reprodutível**, **auditável** e **seguro de evoluir**, com o mesmo rigor aplicado aos produtos que ele entrega.

**Analogia:** é a diferença entre um **restaurante que anota o cardápio à mão** em cada mesa e uma **rede com central de receitas**: a receita (template do produto) e o cardápio (portfolio) ficam em **documentos controlados**, passam por **degustação** (testes), são **aprovados** (pull request) e **distribuídos** a todas as filiais (pipeline).

## O que "catálogo como código" abrange

| Camada | O que é definido em código |
|---|---|
| **Produtos** | Templates dos produtos (CloudFormation/Terraform) |
| **Versões** | Tags/commits do Git → versões do produto |
| **Portfolios** | Nome, descrição, provedor |
| **Associações** | Quais produtos pertencem a quais portfolios |
| **Constraints** | Launch, template, notification, StackSet |
| **TagOptions** | Tags e valores permitidos |
| **Acesso** | Principais (grupos/roles) por portfolio |
| **Compartilhamento** | Org/OU/contas |
| **Launch roles locais** | StackSet para todas as contas |
| **Budgets** | Associações de orçamento |

```
 Repositório Git
 ├─ products/
 │   ├─ postgres/        template.yaml  (+ testes)
 │   └─ sandbox/         template.yaml
 ├─ catalog/             portfolios.yaml, constraints, tagoptions, shares
 ├─ roles/               launch-roles.yaml  (StackSet)
 └─ pipeline/            buildspec, workflows
```

## Definindo o catálogo em CloudFormation

O próprio Service Catalog tem **recursos do CloudFormation** (`AWS::ServiceCatalog::*`).

```yaml
AWSTemplateFormatVersion: '2010-09-09'
Description: Portfolio Dados e produto PostgreSQL padrão

Parameters:
  TemplateUrlV10:
    Type: String
    Description: URL S3 do template do produto v1.0

Resources:
  PortfolioDados:
    Type: AWS::ServiceCatalog::Portfolio
    Properties:
      DisplayName: Dados
      ProviderName: Plataforma
      Description: Produtos de dados aprovados

  ProdutoPostgres:
    Type: AWS::ServiceCatalog::CloudFormationProduct
    Properties:
      Name: PostgreSQL padrao
      Owner: Plataforma
      ProvisioningArtifactParameters:
        - Name: v1.0
          Description: Versao inicial
          Info:
            LoadTemplateFromURL: !Ref TemplateUrlV10

  Associacao:
    Type: AWS::ServiceCatalog::PortfolioProductAssociation
    Properties:
      PortfolioId: !Ref PortfolioDados
      ProductId: !Ref ProdutoPostgres

  LaunchRole:
    Type: AWS::ServiceCatalog::LaunchRoleConstraint
    Properties:
      PortfolioId: !Ref PortfolioDados
      ProductId: !Ref ProdutoPostgres
      LocalRoleName: SCLaunchRolePostgres      # role local em cada conta
      Description: Launch role de menor privilegio

  AcessoDevs:
    Type: AWS::ServiceCatalog::PortfolioPrincipalAssociation
    Properties:
      PortfolioId: !Ref PortfolioDados
      PrincipalARN: !Sub 'arn:${AWS::Partition}:iam::${AWS::AccountId}:role/Desenvolvedores'
      PrincipalType: IAM

  TagCusto:
    Type: AWS::ServiceCatalog::TagOption
    Properties: {Key: CentroDeCusto, Value: CC-1001, Active: true}

  TagCustoAssoc:
    Type: AWS::ServiceCatalog::TagOptionAssociation
    Properties: {ResourceId: !Ref PortfolioDados, TagOptionId: !Ref TagCusto}

  CompartilhaComOU:
    Type: AWS::ServiceCatalog::PortfolioShare
    Properties:
      PortfolioId: !Ref PortfolioDados
      AccountId: '111122223333'          # ou use CLI/automação para Organizations
      ShareTagOptions: true
```

| Recurso CloudFormation | Função |
|---|---|
| `AWS::ServiceCatalog::Portfolio` | Cria o portfolio |
| `AWS::ServiceCatalog::CloudFormationProduct` | Produto + versões |
| `AWS::ServiceCatalog::CloudFormationProvisionedProduct` | **Lança** um produto (provisionamento como código) |
| `...PortfolioProductAssociation` | Liga produto ↔ portfolio |
| `...LaunchRoleConstraint`, `...LaunchTemplateConstraint`, `...LaunchNotificationConstraint`, `...StackSetConstraint` | Constraints |
| `...PortfolioPrincipalAssociation` | Acesso |
| `...TagOption`, `...TagOptionAssociation` | Tags |
| `...PortfolioShare` | Compartilhamento |
| `...ServiceAction` | Service actions |

> [!tip] Provisionar produtos também por código
> `AWS::ServiceCatalog::CloudFormationProvisionedProduct` permite que **outro template** (ou o CDK) **lance produtos do catálogo**, mantendo o princípio de "usar o padrão aprovado" também na automação.

## Pipeline de publicação de produtos

```
 PR no Git ──► CI: cfn-lint + Guard + testes do template
          │
          ▼
 merge/tag v1.2 ──► publica template no S3 (versionado)
          │
          ▼
 Cria nova versão do produto (create-provisioning-artifact)
          │
          ▼
 Testa em conta sandbox: provision-product ──► validações ──► terminate
          │
          ▼
 Marca como versão padrão e deprecia a anterior (com aviso)
```

```yaml
# GitHub Actions (resumo)
jobs:
  publica-produto:
    runs-on: ubuntu-latest
    permissions: {id-token: write, contents: read}
    steps:
      - uses: actions/checkout@v4
      - uses: aws-actions/configure-aws-credentials@v4
        with: {role-to-assume: arn:aws:iam::111111111111:role/CatalogoPublisher, aws-region: us-east-1}
      - run: pip install cfn-lint && cfn-lint products/postgres/template.yaml
      - run: aws s3 cp products/postgres/template.yaml s3://meu-bucket-catalogo/postgres/${{ github.ref_name }}.yaml
      - run: |
          aws servicecatalog create-provisioning-artifact --product-id $PRODUCT_ID \
            --parameters "Name=${{ github.ref_name }},Info={LoadTemplateFromURL=https://meu-bucket-catalogo.s3.amazonaws.com/postgres/${{ github.ref_name }}.yaml},Type=CLOUD_FORMATION_TEMPLATE"
```

| Boa prática | Motivo |
|---|---|
| **OIDC** no pipeline | Sem chaves de longa duração |
| **Bucket de templates versionado** com acesso restrito | Integridade e rastreabilidade |
| **Tag do Git = nome da versão** | Rastreabilidade |
| **Testes de provisionamento** | Garante que o produto realmente funciona |
| **Revisão obrigatória** | Nenhum template vai ao catálogo sem PR |
| **Aprovação manual** antes de promover para "padrão" | Controle de mudança |

### Sincronização Git nativa

O Service Catalog pode **sincronizar produtos com um repositório Git** (via conexão com o provedor): ao receber um **commit/tag**, cria **versões** automaticamente.

| Vantagem | Cuidado |
|---|---|
| Menos código de pipeline | Menos controle sobre testes intermediários |
| Versão ligada ao commit | Exige convenção de ramos/tags |
| Reduz erros manuais | Complementar com validação no CI |

## Terraform no Service Catalog

O Service Catalog permite **produtos Terraform** por meio de **engines de provisionamento**.

| Opção | Descrição |
|---|---|
| **Terraform Reference Engine (open source)** | Engine implantado na sua conta (CodeBuild + S3) que executa `terraform apply` para produtos Terraform |
| **Terraform Cloud/Enterprise** | Integração por engine com workspaces gerenciados |
| **Empacotamento** | Módulos Terraform em **tar.gz** com os arquivos `.tf` |

```
 Usuário ──► Service Catalog ──► Engine (CodeBuild) ──► terraform init/plan/apply ──► recursos
                                      │
                                      └── estado (state) em S3/DynamoDB gerenciado pelo engine
```

| Ponto | Observação |
|---|---|
| **Quando usar** | Equipes já padronizadas em Terraform que querem **governança do catálogo** |
| **Estado** | Gerenciado pelo engine; atenção a locks e backups |
| **Launch role** | Também usada para o provisionamento |
| **Parâmetros** | Variáveis do módulo viram campos do formulário |
| **Limitações** | Menos integração nativa que CloudFormation (por exemplo, nem todos os recursos de atualização/plan) |

> [!warning] Escolha uma linguagem por catálogo quando possível
> Misturar produtos CloudFormation e Terraform **funciona**, mas multiplica **modelos de teste, de erro e de operação**. Se a organização é Terraform-first, avalie os engines; se é AWS-first, mantenha CloudFormation/CDK.

## CLI e API: automações úteis

| Tarefa | Operação |
|---|---|
| Listar produtos disponíveis | `search-products`, `list-portfolios` |
| Lançar | `provision-product` |
| Atualizar em massa | `scan-provisioned-products` + `update-provisioned-product` |
| Descobrir versões em uso | `search-provisioned-products` (filtro por produto/versão) |
| Aplicar TTL | Tag `Expira` + `terminate-provisioned-product` |
| Auditar acessos | `list-principals-for-portfolio` |
| Exportar o catálogo | `list-*` e `describe-*` para documentar |

```bash
# Quais provisionados usam versões obsoletas?
aws servicecatalog search-provisioned-products \
  --filters 'SearchQuery=["productId:prod-abc123"]' \
  --query 'ProvisionedProducts[].[Name,ProvisioningArtifactId,Status]'

# Atualiza um provisionado para a versão recomendada
aws servicecatalog update-provisioned-product --provisioned-product-name banco-pedidos-dev \
  --product-id prod-abc123 --provisioning-artifact-id pa-v12
```

## Testando produtos antes de publicar

| Nível | O que valida | Ferramenta |
|---|---|---|
| **Estático** | Sintaxe, boas práticas, políticas | cfn-lint, cfn-guard |
| **Provisionamento** | O produto sobe e desce sem erro | `provision-product`/`terminate` em conta de teste |
| **Funcional** | O recurso funciona (conexão ao banco, endpoint responde) | Scripts pós-deploy, pytest/boto3 |
| **Segurança** | Criptografia, acesso público, IAM | Config rules, Prowler, checkov |
| **Atualização** | v1.0 → v1.1 sem perda de dados | Teste de upgrade com dados |
| **Custo** | Estimativa do produto | Calculadora, tags e budgets de teste |

```
 Pipeline de testes do produto:
   lint ─► guard ─► provisiona em sandbox ─► valida ─► atualiza (upgrade test) ─► encerra
```

## Ciclo de vida de versões

```
 v1.0 (ativa, padrão) ──► v1.1 (nova) ──► v1.1 vira padrão ──► v1.0 DEPRECATED (aviso) ──► v1.0 desativada
```

| Etapa | Ação |
|---|---|
| **Publicar** | Nova versão via pipeline, testada |
| **Promover** | Marcar como padrão (guidance `DEFAULT`) |
| **Depreciar** | Marcar a anterior `DEPRECATED` e **notificar** donos |
| **Migrar** | Orientar/automatizar a atualização dos provisionados |
| **Desativar** | Bloquear novos lançamentos da versão antiga |
| **Remover** | Apenas quando **nenhum** provisionado a usa |

> [!tip] Métrica de saúde do catálogo
> Acompanhe **quantos provisionados usam cada versão**. Se uma versão obsoleta ainda tem muitos usuários, o catálogo está acumulando **dívida de versões**.

## Governança do próprio pipeline

| Controle | Motivo |
|---|---|
| **Roles do pipeline com menor privilégio** | Só publicar no catálogo e no bucket |
| **Proteção da branch `main`** | Revisão obrigatória |
| **Assinatura/versão dos artefatos** | Integridade |
| **Auditoria (CloudTrail)** | Quem publicou o quê |
| **Separar quem publica de quem usa** | Segregação de funções |

## Exemplo prático: do pull request ao usuário final

1. Um engenheiro abre um PR alterando `products/postgres/template.yaml` (ativa Performance Insights).
2. O CI roda **cfn-lint**, **Guard** e um **teste de provisionamento** em conta sandbox, seguido de um **teste de upgrade** v1.1 → v1.2.
3. Após revisão e merge, a tag `v1.2` dispara a **publicação**: template no S3 e **nova versão** no produto.
4. A versão v1.1 é marcada **DEPRECATED**; um **EventBridge** notifica os donos dos provisionados em v1.1.
5. Um painel mostra a **adesão** à v1.2; após 30 dias, a v1.1 é **desativada**.
6. Tudo isso — produto, versão e constraints — está **no Git**, com histórico e revisões.

## Troubleshooting

| Sintoma | Causa provável | Como resolver |
|---|---|---|
| Nova versão sem efeito | Criada, mas não é a padrão/ativa | Ajustar guidance e estado |
| Stack do catálogo falha ao criar associação | Ordem/dependência de recursos | Revisar `DependsOn` e IDs |
| Terraform engine falha | Permissões do CodeBuild/estado | Ver logs do build; revisar role |
| Pipeline sem permissão | Role OIDC insuficiente | Ajustar trust e permissões |
| Teste de provisionamento instável | Dependências externas/quota | Isolar; reservar quotas na conta de teste |
| Versão antiga não pode ser removida | Ainda há provisionados | Migrar e só então remover |
| Divergência entre console e código | Alterações manuais | Bloquear edição manual; reaplicar IaC |
| Portfolio duplicado | Criado manualmente e por IaC | Importar o existente para a stack |

## Erros comuns e armadilhas

- **Manter o catálogo só no console**, sem histórico nem revisão.
- **Publicar sem testes** (o primeiro usuário vira o teste).
- **Alterar versões já publicadas** em vez de criar novas.
- **Pipeline com chaves de longa duração.**
- **Sem teste de upgrade**, perdendo dados em atualização.
- **Desativar versão sem avisar** os donos.
- **Misturar muitas tecnologias** (CloudFormation, Terraform, scripts) sem padrão.
- **Esquecer de versionar constraints e TagOptions**, que também fazem parte da governança.

## 🧩 Quiz de Fixação

1. O que significa "catálogo como código"?
2. Qual recurso do CloudFormation lança um produto do catálogo?
3. Por que testar o upgrade de uma versão?
4. Qual a função de um Terraform engine no Service Catalog?
5. Qual métrica indica dívida de versões?
6. Como a versão do produto se relaciona com o Git?

**Respostas:**
1) Definir portfolios, produtos, versões, constraints, tags e compartilhamentos em código versionado, revisado e publicado por pipeline.
2) `AWS::ServiceCatalog::CloudFormationProvisionedProduct`.
3) Para garantir que a atualização de uma versão para outra não cause perda de dados nem falhas em produtos já provisionados.
4) Executar o provisionamento de produtos Terraform (terraform apply) quando o usuário lança o produto, gerenciando o estado e as variáveis.
5) A quantidade de produtos provisionados que ainda usam versões obsoletas.
6) Cada tag ou commit do Git pode corresponder a uma versão do produto, publicada pelo pipeline ou pela sincronização nativa com o repositório.
