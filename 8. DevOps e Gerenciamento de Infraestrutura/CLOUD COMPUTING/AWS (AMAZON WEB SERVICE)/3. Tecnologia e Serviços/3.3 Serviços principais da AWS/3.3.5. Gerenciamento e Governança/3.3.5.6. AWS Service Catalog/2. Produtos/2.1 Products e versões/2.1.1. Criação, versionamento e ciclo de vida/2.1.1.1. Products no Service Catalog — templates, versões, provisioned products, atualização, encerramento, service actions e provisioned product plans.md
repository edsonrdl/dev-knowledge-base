### Products no Service Catalog — templates, versões, provisioned products, atualização, encerramento, service actions e provisioned product plans

> [!warning] Aviso
> Estados de produto provisionado, opções de atualização, limites de versões e nomes de campos mudam. Os detalhes aqui são referências de estudo; confirme na documentação. Os comandos **não foram executados**.

O coração do Service Catalog é o **produto**: um **template aprovado**, **versionado**, que o usuário lança por conta própria. Esta folha cobre o **ciclo de vida completo**: como **criar produtos e versões**, o que acontece quando um usuário **lança** (provisiona), **atualiza**, **encerra** (termina) e **executa ações** sobre um produto provisionado. Também mostra como lidar com **mudanças de versão**, **planos de provisionamento** e **estados de erro**.

**Analogia:** um produto é um **modelo de eletrodoméstico** com **versões de fabricação** (v1, v2). Quando um cliente "compra" (provisiona), recebe **uma unidade** (provisioned product). Se a fábrica corrigir um defeito (v1.1), o cliente pode **trocar a unidade** (atualizar). Também pode usar **o manual de serviços** do produto (service actions) e **devolver** a unidade (terminar).

## Criando um produto

Um produto nasce de um **template** (e metadados).

| Origem do template | Uso |
|---|---|
| **Upload de arquivo / URL do S3** | Template CloudFormation em um bucket |
| **Repositório Git** (via sync) | A versão do produto acompanha um repositório (CodeStar Connections) |
| **Template existente (stack)** | Gera o produto a partir de uma stack |
| **Terraform** | Pacote (tar.gz) para engines Terraform |

```bash
aws servicecatalog create-product \
  --name "PostgreSQL padrao" \
  --owner "Plataforma" \
  --description "RDS PostgreSQL com criptografia e backup" \
  --product-type CLOUD_FORMATION_TEMPLATE \
  --provisioning-artifact-parameters '{
    "Name": "v1.0",
    "Description": "Versao inicial",
    "Info": {"LoadTemplateFromURL": "https://meu-bucket.s3.amazonaws.com/produtos/postgres-v1.0.yaml"},
    "Type": "CLOUD_FORMATION_TEMPLATE"
  }'

# Associa o produto a um portfolio
aws servicecatalog associate-product-with-portfolio \
  --product-id prod-abc123 --portfolio-id port-xyz789
```

| Metadado do produto | Função |
|---|---|
| **Nome, descrição, proprietário** | Aparecem na vitrine |
| **Suporte** (e-mail, URL, descrição) | Contato para dúvidas |
| **Distribuidor** | Origem do produto |
| **Tags** | Rastreabilidade |
| **Descrição das versões** | Explica mudanças |

## Versões (provisioning artifacts)

Cada alteração significativa gera uma **nova versão**; as antigas podem ser mantidas, **desativadas** ou **removidas**.

```bash
# Nova versão
aws servicecatalog create-provisioning-artifact --product-id prod-abc123 \
  --parameters '{
    "Name": "v1.1",
    "Description": "Ativa Performance Insights",
    "Info": {"LoadTemplateFromURL": "https://meu-bucket.s3.amazonaws.com/produtos/postgres-v1.1.yaml"},
    "Type": "CLOUD_FORMATION_TEMPLATE"
  }'

# Desativa uma versão antiga (usuários não conseguem mais lançá-la)
aws servicecatalog update-provisioning-artifact --product-id prod-abc123 \
  --provisioning-artifact-id pa-old --active=false
```

| Estado da versão | Efeito |
|---|---|
| **Ativa** | Pode ser lançada e usada em atualizações |
| **Inativa** | Não pode ser lançada; os provisionados continuam existindo |
| **Guidance** (`DEFAULT`, `DEPRECATED`) | Sinaliza a versão recomendada ou obsoleta |
| **Removida** | Só se nenhum produto provisionado usar |

> [!tip] Nunca altere uma versão publicada
> Mudou o template? Crie uma **nova versão** (v1.2). Alterar uma versão já usada gera **inconsistência**: provisionados antigos ficam divergentes do que a versão "diz" ser. Versionamento semântico (v1.0 → v1.1 correção, v2.0 mudança incompatível) ajuda.

### Sincronização com Git

Com a **integração com repositório**, o Service Catalog pode **criar versões automaticamente** quando há um *commit/tag* no repositório conectado.

| Vantagem | Observação |
|---|---|
| **Revisão por pull request** | O catálogo reflete código revisado |
| **Rastreabilidade** | Versão ligada a um commit |
| **Menos trabalho manual** | Pipeline publica novas versões |

## Parâmetros do produto

Os **parâmetros do template** (`Parameters`) viram os **campos do formulário** do usuário.

```yaml
Parameters:
  Ambiente:
    Type: String
    AllowedValues: [dev, homolog, prod]
  Tamanho:
    Type: String
    AllowedValues: [pequeno, medio, grande]
    Default: pequeno
  NomeDoBanco:
    Type: String
    AllowedPattern: '^[a-z][a-z0-9_]{2,30}$'
```

| Boa prática | Motivo |
|---|---|
| **Poucos parâmetros** | Simplicidade para o usuário |
| **`AllowedValues` e `AllowedPattern`** | Limitam o que pode ser escolhido |
| **Defaults seguros** | Quem não sabe usa o padrão correto |
| **Descrições claras** | Reduz chamados de suporte |
| **Nada de segredos em parâmetros** | Prefira Secrets Manager e referências dinâmicas |

## Provisionando (lançando) um produto

Quando o usuário lança, o Service Catalog:

1. **Verifica** acesso do usuário ao portfolio/produto.
2. **Assume a launch role** (se houver constraint de launch).
3. **Valida** parâmetros (template constraints).
4. **Cria a stack** (ou executa o engine Terraform) com as tags configuradas.
5. **Registra** o produto provisionado com saídas (`Outputs`).

```
 Estados principais de um provisioned product:
   UNDER_CHANGE ──► AVAILABLE      (lançado/atualizado com sucesso)
        │
        ├─► ERROR                   (falhou; recursos podem ter sido criados)
        └─► TAINTED                 (atualização falhou; estado inconsistente)
   PLAN_IN_PROGRESS                 (plano de mudança em análise)
```

| Estado | Significado | Ação |
|---|---|---|
| **AVAILABLE** | Operacional | Nenhuma |
| **UNDER_CHANGE** | Em criação, atualização ou encerramento | Aguardar |
| **TAINTED** | Atualização falhou; recursos divergentes | Corrigir e tentar de novo, ou encerrar |
| **ERROR** | Criação falhou | Ver eventos da stack; encerrar e relançar |
| **PLAN_IN_PROGRESS** | Plano criado, não executado | Revisar e executar/excluir |

### Saídas e rastreabilidade

```bash
aws servicecatalog describe-record --id rec-abc123          # resultado da operação
aws servicecatalog scan-provisioned-products --query 'ProvisionedProducts[].[Name,Status]'
aws servicecatalog get-provisioned-product-outputs --provisioned-product-name banco-pedidos-dev
```

Cada operação (provisionar, atualizar, terminar) gera um **record** com status, saídas, erros e o usuário que a solicitou.

## Atualizando um produto provisionado

Para aplicar uma **nova versão** (ou novos parâmetros) a um produto já lançado:

```bash
aws servicecatalog update-provisioned-product \
  --provisioned-product-name banco-pedidos-dev \
  --product-id prod-abc123 \
  --provisioning-artifact-id pa-v11 \
  --provisioning-parameters Key=Tamanho,Value=medio
```

| Aspecto | Observação |
|---|---|
| **Impacto** | Segue as regras do CloudFormation: pode haver *replacement* |
| **Quem atualiza** | O próprio usuário (ou um administrador) |
| **Versões inativas** | Não podem ser alvo da atualização |
| **Atualização em massa** | Não é automática: a plataforma precisa orientar, notificar ou automatizar por API |
| **Constraints** | Podem restringir atualizações (resource update constraint) |

### Provisioned product plans

Os **planos** são o equivalente a **change sets**: permitem **pré-visualizar** o impacto de uma atualização antes de executá-la.

```bash
aws servicecatalog create-provisioned-product-plan \
  --plan-name atualiza-v11 --plan-type CLOUDFORMATION \
  --product-id prod-abc123 --provisioned-product-name banco-pedidos-dev \
  --provisioning-artifact-id pa-v11

aws servicecatalog describe-provisioned-product-plan --plan-id plan-xyz        # ver as mudanças
aws servicecatalog execute-provisioned-product-plan --plan-id plan-xyz         # aplicar
```

> [!warning] Cuidado com *replacement* em dados
> Um produto de banco de dados atualizado com mudança que substitui o recurso pode **apagar dados**. Garanta `DeletionPolicy/UpdateReplacePolicy` nos templates e use **planos** para revisar.

## Encerrando (terminando) um produto provisionado

```bash
aws servicecatalog terminate-provisioned-product \
  --provisioned-product-name banco-pedidos-dev
```

| Comportamento | Detalhe |
|---|---|
| **Exclusão da stack** | Todos os recursos criados são removidos (respeitando `DeletionPolicy`) |
| **Dados críticos** | Use `Retain`/`Snapshot` para bancos e buckets |
| **`--ignore-errors`** | Remove o registro mesmo se a exclusão falhar (recursos podem ficar órfãos) |
| **Quem pode encerrar** | Quem lançou ou um administrador |
| **Custo** | Parar de pagar só depois que os recursos forem de fato removidos |

> [!tip] Políticas de expiração
> Para ambientes **efêmeros** (sandbox), automatize **TTL**: um agendamento verifica a tag `Expira` e executa `terminate-provisioned-product`, evitando contas esquecidas.

## Service actions

As **service actions** permitem **operações administrativas autorizadas** sobre produtos provisionados, **sem dar acesso direto** aos recursos. Elas executam **documentos do Systems Manager (SSM Automation)**.

| Exemplo de ação | Efeito |
|---|---|
| **Reiniciar instância** | Documento `AWS-RestartEC2Instance` |
| **Criar snapshot do banco** | Runbook personalizado |
| **Parar/iniciar ambiente** | Economia fora do expediente |
| **Rodar verificação** | Diagnóstico padrão |

```bash
aws servicecatalog create-service-action --name ReiniciarInstancia \
  --definition-type SSM_AUTOMATION \
  --definition 'Name=AWS-RestartEC2Instance,Version=1,AssumeRole=arn:aws:iam::123456789012:role/SvcActionRole,Parameters={"InstanceId":"[{\"Name\":\"InstanceId\",\"Type\":\"TARGET\"}]"}'

aws servicecatalog associate-service-action-with-provisioning-artifact \
  --product-id prod-abc123 --provisioning-artifact-id pa-v11 --service-action-id act-123

aws servicecatalog execute-provisioned-product-service-action \
  --provisioned-product-id pp-abc --service-action-id act-123
```

| Vantagem | Observação |
|---|---|
| **Menor privilégio** | Usuário executa só ações aprovadas |
| **Auditoria** | Cada execução gera registro |
| **Padronização** | Procedimentos operacionais iguais para todos |

## Exemplo prático: ciclo de vida de um ambiente sandbox

1. Produto **"Sandbox de desenvolvedor"** v1.0 com VPC, instância pequena e budget.
2. O desenvolvedor lança com parâmetros `Ambiente=dev` e `Responsavel=ana`; as **tags** são aplicadas automaticamente.
3. Uma **service action** "Parar ambiente" permite desligar fora do expediente.
4. Uma automação verifica a tag `Expira` e **encerra** ambientes após 14 dias.
5. A plataforma lança a v1.1 (endpoint SSM); os usuários **atualizam** quando conveniente.
6. A v1.0 é marcada como **DEPRECATED** e depois desativada.

## Troubleshooting

| Sintoma | Causa provável | Como resolver |
|---|---|---|
| Lançamento falha com `AccessDenied` | Launch role sem permissão | Ajustar a role (ver evento da stack) |
| Produto **TAINTED** | Atualização falhou | Ver stack; corrigir e atualizar de novo ou encerrar |
| Não consigo encerrar | Recurso com dependência externa | Remover o bloqueio; `--ignore-errors` com cautela |
| Usuário não vê o produto | Sem acesso ao portfolio | Conceder acesso (grupo/role) |
| Parâmetro inválido | Template constraint/AllowedValues | Ajustar o valor |
| Versão não aparece | Inativa ou sem associação | Ativar e associar |
| Atualização causa perda de dados | *Replacement* sem proteção | Usar plano e `Retain/Snapshot` |
| Service action falha | Role do SSM sem permissão | Revisar a role de execução |

## Erros comuns e armadilhas

- **Editar uma versão publicada** em vez de criar uma nova.
- **Produtos com dezenas de parâmetros** que confundem o usuário.
- **Sem proteção de dados** em produtos de banco.
- **Não planejar atualizações**: dezenas de versões antigas em uso.
- **Ambientes efêmeros sem TTL.**
- **Service actions com roles amplas.**
- **Catálogo sem curadoria**, repleto de produtos obsoletos.
- **Esquecer tags e budgets** nos produtos.

## 🧩 Quiz de Fixação

1. Por que criar uma nova versão em vez de editar a existente?
2. O que é um provisioned product plan?
3. O que significa o estado TAINTED?
4. Para que servem as service actions?
5. Como evitar a perda de dados ao encerrar um produto de banco?
6. Como automatizar a expiração de ambientes efêmeros?

**Respostas:**
1) Para manter consistência: produtos já lançados dependem da versão, e alterá-la gera divergência; versões novas permitem atualização controlada e rollback.
2) Uma pré-visualização das mudanças de uma atualização (como um change set), que pode ser revisada antes de executar.
3) A atualização falhou e o produto ficou em estado inconsistente, exigindo correção ou encerramento.
4) Permitir operações administrativas aprovadas (via documentos do SSM) sobre produtos provisionados, sem dar acesso direto aos recursos.
5) Usando DeletionPolicy/UpdateReplacePolicy com Retain ou Snapshot no template do produto.
6) Com uma automação que lê uma tag (como Expira) e executa terminate-provisioned-product quando o prazo vence.
