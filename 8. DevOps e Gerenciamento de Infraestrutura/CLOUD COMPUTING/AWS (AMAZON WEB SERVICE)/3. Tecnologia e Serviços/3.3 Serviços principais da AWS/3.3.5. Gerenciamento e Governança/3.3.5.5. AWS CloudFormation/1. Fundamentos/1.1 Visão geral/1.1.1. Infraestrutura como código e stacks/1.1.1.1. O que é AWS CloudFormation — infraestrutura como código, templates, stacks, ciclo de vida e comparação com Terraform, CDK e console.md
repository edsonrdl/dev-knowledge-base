### O que é AWS CloudFormation — infraestrutura como código, templates, stacks, ciclo de vida e comparação com Terraform, CDK e console

> [!warning] Aviso
> Tipos de recurso suportados, limites (tamanho de template, número de recursos por stack), estados de stack, preços e funcionalidades mudam. Os números aqui são referências de estudo; confirme na documentação oficial. Os comandos de CLI são exemplos e **não foram executados**.

O **AWS CloudFormation** é o serviço de **infraestrutura como código (IaC)** nativo da AWS. Em vez de criar recursos clicando no console ou rodando comandos soltos, você **descreve em um arquivo (template)** tudo o que quer: VPCs, buckets, bancos, funções, balanceadores. O CloudFormation **lê o template, descobre a ordem correta**, **cria, atualiza e remove** os recursos por você e **agrupa tudo em uma unidade gerenciável chamada stack**.

A ideia central é o **modelo declarativo**: você diz **o estado desejado** ("quero um bucket com versionamento e um banco Multi-AZ"), e o serviço calcula **como chegar lá**. Isso torna a infraestrutura **reprodutível, versionável, revisável e auditável**.

**Analogia:** o template é a **planta de uma casa** e a stack é **a casa construída a partir dela**. Se você muda a planta (adiciona uma janela) e pede uma atualização, o construtor (CloudFormation) compara a planta nova com a casa existente e faz **só as reformas necessárias**. Se você manda demolir a casa (excluir a stack), ele remove tudo na ordem certa. Construir 10 casas iguais é só aplicar a mesma planta 10 vezes.

## Por que usar IaC

| Problema do "clicar no console" | Como o CloudFormation resolve |
|---|---|
| **Ambientes diferentes entre si** (dev ≠ prod) | O **mesmo template** cria os dois, com parâmetros distintos |
| **Ninguém lembra quem mudou o quê** | Template em **Git**: histórico, revisão e *pull request* |
| **Recriar do zero após um desastre leva dias** | `create-stack` recria a infraestrutura em minutos |
| **Erros manuais** | Processo repetível e testável |
| **Limpeza esquecida** (recursos órfãos) | Excluir a stack remove tudo que ela criou |
| **Conformidade** | Templates são **a documentação viva** da infraestrutura |
| **Escala** (50 contas, várias regiões) | **StackSets** aplicam o template em massa |

> [!tip] O custo do CloudFormation
> O **CloudFormation em si não tem custo** para recursos AWS nativos; você paga **apenas pelos recursos que ele cria**. Há cobrança para certos usos específicos (por exemplo, operações de handler em tipos de recursos de terceiros além de uma franquia). Confirme os detalhes na página de preços.

## Conceitos centrais

```
 ┌─────────────┐   create / update    ┌──────────────────┐
 │  TEMPLATE   │ ───────────────────► │      STACK       │
 │ (YAML/JSON) │                      │  ┌────────────┐  │
 │  versionado │                      │  │ Recurso A  │  │  ← VPC, bucket,
 │  no Git     │                      │  │ Recurso B  │  │    instância,
 └─────────────┘                      │  │ Recurso C  │  │    função Lambda...
        ▲                             │  └────────────┘  │
        │ parâmetros                  └──────────────────┘
        │ (ambiente, tamanho...)
```

| Conceito | O que é |
|---|---|
| **Template** | Arquivo **YAML ou JSON** que declara os recursos e suas propriedades |
| **Stack** | Conjunto de recursos criados e gerenciados **como uma unidade** a partir de um template |
| **Resource** | Cada objeto AWS declarado (`AWS::S3::Bucket`, `AWS::EC2::Instance`) |
| **Parameters** | Entradas que mudam por implantação (ambiente, tipo de instância) |
| **Outputs** | Saídas exportáveis (ID da VPC, URL do site) |
| **Change set** | **Pré-visualização** das mudanças antes de aplicar |
| **Stack policy** | Protege recursos críticos contra atualizações acidentais |
| **StackSet** | Implanta o mesmo template em **várias contas e regiões** |
| **Drift** | Diferença entre o que o template diz e o que existe de fato |
| **Macro / Module / Custom resource** | Extensões para lógica e reutilização |

### Um template mínimo

```yaml
AWSTemplateFormatVersion: '2010-09-09'
Description: Bucket de logs com versionamento e criptografia

Parameters:
  Ambiente:
    Type: String
    AllowedValues: [dev, prod]
    Default: dev

Resources:
  BucketLogs:
    Type: AWS::S3::Bucket
    Properties:
      BucketName: !Sub 'logs-${Ambiente}-${AWS::AccountId}'
      VersioningConfiguration:
        Status: Enabled
      BucketEncryption:
        ServerSideEncryptionConfiguration:
          - ServerSideEncryptionByDefault:
              SSEAlgorithm: AES256

Outputs:
  NomeDoBucket:
    Description: Nome do bucket criado
    Value: !Ref BucketLogs
```

```bash
# Cria a stack
aws cloudformation create-stack --stack-name logs-dev \
  --template-body file://bucket.yaml \
  --parameters ParameterKey=Ambiente,ParameterValue=dev

# Acompanha
aws cloudformation describe-stacks --stack-name logs-dev \
  --query 'Stacks[0].[StackStatus,Outputs]'

# Atualiza com uma nova versão do template
aws cloudformation update-stack --stack-name logs-dev \
  --template-body file://bucket.yaml --parameters ParameterKey=Ambiente,ParameterValue=dev

# Remove a stack e tudo que ela criou
aws cloudformation delete-stack --stack-name logs-dev
```

Para quem prefere um único comando idempotente (cria ou atualiza): `aws cloudformation deploy --template-file bucket.yaml --stack-name logs-dev`.

## Como o CloudFormation executa

| Etapa | O que acontece |
|---|---|
| 1. **Validação** | Sintaxe e estrutura do template |
| 2. **Resolução** | Parâmetros, condições e referências (`!Ref`, `!GetAtt`) |
| 3. **Grafo de dependências** | Monta a ordem: o que depende de quê |
| 4. **Execução** | Cria/atualiza recursos **em paralelo** quando possível, respeitando dependências |
| 5. **Resultado** | Todos OK → `CREATE_COMPLETE`; algum falha → **rollback** |

```
 VPC ──► Subnet ──► Instância ──► (saída: IP)
   └──► Security Group ─────────┘
 
 O CloudFormation cria VPC e SG em paralelo, depois Subnet, depois a instância.
```

### Estados de stack mais comuns

| Estado | Significado |
|---|---|
| `CREATE_IN_PROGRESS` / `CREATE_COMPLETE` | Criando / criada com sucesso |
| `CREATE_FAILED` → `ROLLBACK_COMPLETE` | Falhou e **reverteu** (a stack precisa ser **excluída**; não dá para atualizar) |
| `UPDATE_IN_PROGRESS` / `UPDATE_COMPLETE` | Atualizando / atualizada |
| `UPDATE_ROLLBACK_COMPLETE` | Atualização falhou e voltou ao estado anterior |
| `UPDATE_ROLLBACK_FAILED` | Nem o rollback conseguiu; exige intervenção |
| `DELETE_FAILED` | Algum recurso impediu a exclusão |
| `REVIEW_IN_PROGRESS` | Change set criado, aguardando execução |

> [!warning] Rollback automático é um comportamento de segurança
> Se **qualquer** recurso falha na criação, por padrão o CloudFormation **desfaz tudo**. Isso evita stacks pela metade, mas pode esconder a causa: **leia os eventos** da stack antes de excluí-la.

## Atualizações: como o CloudFormation altera recursos

Ao atualizar um template, cada propriedade modificada tem um **tipo de atualização**:

| Tipo | Efeito | Exemplo |
|---|---|---|
| **No interruption** | Altera sem parar o recurso | Mudar tags |
| **Some interruptions** | Pode causar breve parada | Tipo de instância (EBS-backed) |
| **Replacement** | **Cria um novo recurso e apaga o antigo** | Mudar o nome de uma tabela DynamoDB |

> [!warning] "Replacement" pode destruir dados
> Substituir um banco de dados ou um bucket com dados **apaga o antigo**. Por isso existem **change sets**, `UpdateReplacePolicy` e `DeletionPolicy: Retain/Snapshot`, abordados na folha de mudanças.

## CloudFormation vs outras formas de criar infraestrutura

| Critério | Console | CLI/SDK (scripts) | **CloudFormation** | **Terraform** | **AWS CDK** |
|---|---|---|---|---|---|
| Modelo | Manual | Imperativo | **Declarativo** | Declarativo | **Código (TS/Python/Java...)** que gera CloudFormation |
| Reprodutível | Não | Parcial | **Sim** | Sim | Sim |
| Estado | — | Você controla | **Gerenciado pela AWS** (sem arquivo de state) | Arquivo de **state** (precisa de backend) | Gerenciado pelo CloudFormation |
| Multi-nuvem | — | — | **Só AWS** | **Sim** | Só AWS (CDK for Terraform existe à parte) |
| Rollback automático | — | Não | **Sim** | Não nativo | Sim (usa CloudFormation) |
| Suporte a novos serviços | — | Imediato | Normalmente rápido | Depende do provider | Depende do CloudFormation |
| Curva | Baixa | Média | Média | Média | Média (exige programar) |

```
 Só AWS e quero algo nativo, sem gerenciar state?          ─► CloudFormation
 Prefiro escrever em TypeScript/Python com loops e classes? ─► AWS CDK (gera templates)
 Preciso de multi-nuvem ou ecossistema de providers?        ─► Terraform
 Funções serverless com atalhos?                            ─► AWS SAM (extensão do CloudFormation)
```

> [!tip] CDK e SAM são "camadas" sobre o CloudFormation
> O **CDK** **sintetiza** templates CloudFormation e o **SAM** é uma **transformação** (`AWS::Serverless-2016-10-31`) que expande para recursos CloudFormation. Entender CloudFormation ajuda a depurar ambos, pois os erros aparecem como eventos de stack.

## Onde o template fica e como é implantado

| Origem do template | Uso |
|---|---|
| **Arquivo local** (`--template-body`) | Pequenos e testes |
| **Amazon S3** (`--template-url`) | Templates grandes, nested stacks, StackSets |
| **Repositório Git + pipeline** | **Prática recomendada**: CodePipeline/GitHub Actions |
| **Service Catalog** | Produtos aprovados para autoatendimento |

Limites de referência: **tamanho** do template (algumas dezenas de KB direto; centenas de KB via S3) e **número de recursos** por stack (em torno de 500). Para além disso, divida em **nested stacks** ou várias stacks.

| Caso | Como o CloudFormation ajuda |
|---|---|
| **Ambientes efêmeros** (feature branches) | Cria e destrói uma stack por branch |

## Exemplo prático: do console para o código

1. A equipe tem uma VPC criada à mão. Usa o **IaC generator** (ou *resource import*) para gerar um template a partir dos recursos existentes.
2. O template vai para o **Git**; o time revisa e corrige.
3. Cria-se a stack **importando** os recursos existentes (sem recriá-los).
4. Mudanças futuras são feitas por **pull request**, com **change set** revisado.
5. O pipeline aplica em **dev**, valida e promove para **prod**.
6. Um alarme de **drift** avisa se alguém alterar o recurso fora do código.

## Erros comuns e armadilhas

- **Editar recursos da stack manualmente** no console, gerando **drift**.
- **Aplicar `update-stack` sem olhar um change set** e causar *replacement* inesperado.
- **Um template gigante e monolítico** com todos os recursos de todas as camadas.
- **Colocar segredos no template** em texto claro (use Secrets Manager/Parameter Store).
- **Não definir `DeletionPolicy`** em bancos e buckets críticos.
- **Nomes fixos de recursos** (`BucketName`) que impedem criar duas stacks iguais.
- **Excluir uma stack em `ROLLBACK_COMPLETE` sem ler os eventos** e perder a causa do erro.
- **Achar que o CloudFormation é multi-nuvem.**

## 🧩 Quiz de Fixação

1. Qual a diferença entre template e stack?
2. O que significa dizer que o CloudFormation é declarativo?
3. O que acontece, por padrão, se um recurso falha na criação da stack?
4. Qual o risco de uma atualização do tipo *replacement*?
5. Qual a relação entre CDK e CloudFormation?
6. O CloudFormation cobra pelo serviço em si?

**Respostas:**
1) O template é o arquivo que descreve a infraestrutura; a stack é o conjunto de recursos criados e gerenciados a partir dele.
2) Você descreve o estado desejado, e o serviço calcula a ordem e as ações necessárias para chegar a ele.
3) A stack faz rollback, desfazendo o que foi criado (ficando em ROLLBACK_COMPLETE, que precisa ser excluída).
4) O recurso antigo é criado de novo e apagado, o que pode destruir dados (banco, bucket) se não houver proteções.
5) O CDK sintetiza templates CloudFormation a partir de código; a implantação e os erros são do CloudFormation.
6) Não para recursos AWS nativos; paga-se pelos recursos criados (há cobranças em usos específicos, como certos handlers de terceiros).
