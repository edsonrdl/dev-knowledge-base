### CloudFormation em escala — nested stacks, cross-stack references, StackSets, modules, macros e custom resources

> [!warning] Aviso
> Limites (recursos por stack, profundidade de nested stacks, quantidade de instâncias de StackSet), modelos de permissão e nomes de recursos mudam. Os números aqui são referências de estudo; confirme na documentação. Os comandos **não foram executados**.

Um template único com tudo funciona para um projeto pequeno; em **organizações reais**, o CloudFormation precisa ser **modular** (reutilizar blocos), **dividido** (stacks por camada e por equipe), **replicado** (dezenas de contas e regiões) e **extensível** (lógica que o serviço não tem nativamente). Esta folha cobre os mecanismos de escala: **nested stacks**, **referências entre stacks**, **StackSets**, **modules**, **macros**, **custom resources** e o **CloudFormation Registry**.

**Analogia:** uma construtora que faz um único prédio desenha **uma planta grande**. Uma construtora que faz **centenas de prédios** em **cidades diferentes** precisa de **módulos padronizados** (banheiro pré-fabricado = module), **plantas divididas por especialidade** (hidráulica, elétrica = stacks por camada), **um escritório central que dispara a obra em todas as cidades de uma vez** (StackSets) e **ferramentas especiais** para o que não existe em catálogo (custom resources).

---

## Por que dividir stacks

| Problema do template monolítico | Efeito |
|---|---|
| Limite de **tamanho** e de **~500 recursos** | Template não cabe |
| Atualização lenta e arriscada | Mudar uma regra de segurança "toca" a stack inteira |
| **Raio de explosão** grande | Erro derruba tudo |
| Equipes diferentes no mesmo arquivo | Conflitos e gargalos |
| Ciclos de vida distintos | Rede muda raramente; aplicação, todo dia |

**Regra prática:** separe por **ciclo de vida** e por **dono**.

```
 Camada de fundação (muda raramente)   → stack "rede"        (VPC, subnets, rotas)
 Camada de plataforma                  → stack "dados"       (RDS, S3, KMS)
 Camada de aplicação (muda sempre)     → stack "app-api"     (ECS, ALB, funções)
 Camada de observabilidade             → stack "monitoramento"
```

## Nested stacks

Uma **nested stack** é uma stack **criada como recurso dentro de outra** (a **stack raiz**). Permite **componentizar** e **reutilizar** templates.

```yaml
# template raiz
Resources:
  Rede:
    Type: AWS::CloudFormation::Stack
    Properties:
      TemplateURL: https://meu-bucket.s3.amazonaws.com/templates/rede.yaml
      Parameters:
        Ambiente: !Ref Ambiente
        CidrVpc: 10.0.0.0/16

  App:
    Type: AWS::CloudFormation::Stack
    Properties:
      TemplateURL: https://meu-bucket.s3.amazonaws.com/templates/app.yaml
      Parameters:
        VpcId: !GetAtt Rede.Outputs.VpcId           # usa a saída da stack filha
        SubnetIds: !GetAtt Rede.Outputs.SubnetsPrivadas
```

| Característica | Detalhe |
|---|---|
| **Templates no S3** | `TemplateURL` aponta para um objeto S3 |
| **Atualização** | Atualizar a raiz atualiza as filhas cujo template/parâmetros mudaram |
| **Exclusão** | Excluir a raiz exclui as filhas |
| **Ciclo de vida unificado** | Uma mudança, uma operação |
| **`aws cloudformation package`** | Empacota e envia templates filhos ao S3, ajustando as URLs |

```bash
aws cloudformation package --template-file raiz.yaml --s3-bucket meu-bucket-cfn \
  --output-template-file raiz-empacotado.yaml
aws cloudformation deploy --template-file raiz-empacotado.yaml --stack-name plataforma \
  --capabilities CAPABILITY_IAM
```

> [!warning] Não altere nested stacks diretamente
> Sempre atualize pela **stack raiz**. Mexer na filha isoladamente cria **inconsistência** e pode quebrar atualizações futuras.

## Referências entre stacks independentes

Quando as stacks têm **ciclos de vida separados** (e não aninhadas), há duas formas de compartilhar valores:

| Método | Como funciona | Prós | Contras |
|---|---|---|---|
| **Export / ImportValue** | A stack A **exporta** (`Export.Name`); a B usa `!ImportValue` | Simples; verificado pelo serviço | **Acoplamento rígido**: A não pode ser alterada/excluída enquanto B importar; só na mesma região/conta |
| **Parameter Store (SSM)** | A grava um parâmetro; B lê com parâmetro `AWS::SSM::Parameter::Value<...>` | **Desacoplado**; entre regiões e contas (com permissão) | Sem verificação automática de dependência |
| **Parâmetros por pipeline** | O pipeline lê saídas e as passa como parâmetros | Controle total | Mais código de orquestração |

```yaml
# Stack de rede: publica no Parameter Store (desacoplado)
Resources:
  ParamVpc:
    Type: AWS::SSM::Parameter
    Properties:
      Name: !Sub '/${Ambiente}/rede/vpc-id'
      Type: String
      Value: !Ref Vpc

# Stack de aplicação: consome
Parameters:
  VpcId:
    Type: AWS::SSM::Parameter::Value<AWS::EC2::VPC::Id>
    Default: /prod/rede/vpc-id
```

> [!tip] Prefira SSM a Export em organizações grandes
> Exports bloqueiam mudanças (não dá para remover ou alterar o valor enquanto houver importadores). O Parameter Store dá flexibilidade; combine com convenções de nomes e permissões por caminho.

## StackSets

Um **StackSet** implanta **o mesmo template** em **várias contas e regiões** com **uma única operação**.

```
                      ┌─► Conta A / us-east-1  (stack instance)
 Conta administradora ├─► Conta A / sa-east-1
 (admin delegado)     ├─► Conta B / us-east-1
   StackSet           └─► Conta C / us-east-1  ...
```

| Conceito | Descrição |
|---|---|
| **StackSet** | Definição (template + parâmetros + configuração) na conta administradora |
| **Stack instance** | A stack criada em **uma conta/região** de destino |
| **Modelo de permissões** | **Self-managed** (roles que você cria) ou **service-managed** (integrado ao AWS Organizations) |
| **Implantação automática** | Em **service-managed**, novas contas da OU recebem o StackSet automaticamente |
| **Operação** | Create/update/delete de instâncias com controle de **concorrência** e **tolerância a falhas** |
| **Administrador delegado** | Conta de operações que gerencia StackSets, em vez da conta de gerenciamento |

```bash
aws cloudformation create-stack-set --stack-set-name baseline-seguranca \
  --template-body file://baseline.yaml \
  --permission-model SERVICE_MANAGED \
  --auto-deployment Enabled=true,RetainStacksOnAccountRemoval=false \
  --capabilities CAPABILITY_NAMED_IAM

aws cloudformation create-stack-instances --stack-set-name baseline-seguranca \
  --deployment-targets OrganizationalUnitIds=ou-abcd-12345678 \
  --regions us-east-1 sa-east-1 \
  --operation-preferences FailureToleranceCount=1,MaxConcurrentCount=5,RegionConcurrencyType=PARALLEL
```

| Preferência de operação | Função |
|---|---|
| `MaxConcurrentCount/Percentage` | Quantas contas em paralelo |
| `FailureToleranceCount/Percentage` | Quantas falhas toleradas antes de parar |
| `RegionOrder` e `RegionConcurrencyType` | Ordem e paralelismo entre regiões |

### Casos de uso de StackSets

| Caso | Exemplo |
|---|---|
| **Baseline de segurança** | Habilitar CloudTrail, Config, GuardDuty em todas as contas |
| **Roles de acesso** | Role de auditoria/leitura em cada conta |
| **Rede padrão** | Subnets e endpoints em contas novas |
| **Regras de governança** | Config rules, alarmes padrão |
| **Habilitar o SSM (Quick Setup)** | Perfil e agente em toda a organização |

> [!warning] Drift e StackSets
> Alterações manuais em uma **stack instance** causam drift. Use **detecção de drift do StackSet** e trate as instâncias divergentes; contas novas só entram automaticamente no modelo **service-managed**.

## Modules

Um **module** é um **bloco reutilizável de recursos** (por exemplo, "bucket seguro com logs e criptografia") **registrado** no **CloudFormation Registry** e **usado como se fosse um recurso**.

```yaml
Resources:
  MeuBucket:
    Type: MinhaOrg::S3::BucketSeguro::MODULE
    Properties:
      NomeBase: dados-clientes
      Ambiente: !Ref Ambiente
```

| Vantagem | Observação |
|---|---|
| **Padronização** | Equipe de plataforma publica o "jeito certo" |
| **Governança embutida** | Criptografia, tags, logging nos padrões |
| **Menos repetição** | Sem copiar/colar blocos |
| **Versionamento** | Versões do módulo no Registry |

Alternativas para reuso: **nested stacks** (por template), **Service Catalog** (produtos aprovados) e **CDK constructs** (código).

## Macros e Transform

Uma **macro** é uma **função Lambda** que **processa o template** (ou um fragmento) **antes** da implantação, permitindo **lógica que o YAML não tem**.

| Tipo | Uso |
|---|---|
| **`Transform` (nível de template)** | Reescreve o template inteiro (ex.: `AWS::Serverless`, a macro do SAM) |
| **`Fn::Transform` (fragmento)** | Reescreve um trecho (ex.: `AWS::Include`) |
| **Macros próprias** | Ex.: "adicione as tags padrão a todos os recursos", "gere N subnets" |

```yaml
Transform: [MinhaMacroDeTags]
Resources: ...
```

| Cuidado | Por quê |
|---|---|
| **Capability `CAPABILITY_AUTO_EXPAND`** | Obrigatória em stacks que usam macros |
| **Segurança** | A macro **altera** o que será criado; controle quem a publica |
| **Depuração** | Use `get-template --template-stage Processed` para ver o resultado |

## Custom resources

Um **custom resource** executa **sua própria lógica** durante a criação/atualização/exclusão da stack, para o que o CloudFormation **não suporta nativamente**.

```
 Stack ──(Create/Update/Delete)──► Lambda (ou SNS) ──► faz o trabalho
                                         │
                                         └── responde (SUCCESS/FAILED + dados) à URL pré-assinada
```

```yaml
Resources:
  LimpaBucketAoExcluir:
    Type: Custom::EsvaziaBucket
    Properties:
      ServiceToken: !GetAtt FuncaoEsvazia.Arn
      Bucket: !Ref BucketDados
```

```python
import cfnresponse, boto3

def handler(event, context):
    try:
        if event["RequestType"] == "Delete":
            s3 = boto3.resource("s3")
            s3.Bucket(event["ResourceProperties"]["Bucket"]).objects.all().delete()
        cfnresponse.send(event, context, cfnresponse.SUCCESS, {})
    except Exception as e:
        cfnresponse.send(event, context, cfnresponse.FAILED, {"erro": str(e)})
```

| Usos comuns | Exemplo |
|---|---|
| **Esvaziar bucket** antes da exclusão | Evita `DELETE_FAILED` |
| **Buscar a AMI mais recente** | Consulta e retorna o ID |
| **Integrar sistemas externos** | Registrar a instância em um sistema de CMDB |
| **Configuração inicial de um serviço** | Popular dados iniciais |

> [!warning] Sempre responda ao CloudFormation
> Se a função **não envia a resposta** (por erro ou timeout), a stack **fica pendurada por até uma hora** antes de falhar. Use `try/except`, trate **Delete** (sempre responda SUCCESS para não travar exclusões) e defina timeouts curtos.

Hoje, muitas necessidades de custom resources são cobertas por **hooks, módulos, `AWS::CloudFormation::CustomResource`** com o **CDK Provider Framework**, ou **tipos de recurso do Registry**.

## CloudFormation Registry

O **Registry** é o catálogo de **tipos** (resources, modules, hooks):

| Tipo | Quem publica | Uso |
|---|---|---|
| **AWS types** | AWS | Recursos nativos |
| **Third-party** | Parceiros (Datadog, MongoDB Atlas...) | Gerenciar recursos de terceiros como IaC |
| **Private** | Sua organização | Recursos, módulos e hooks privados |

**Hooks** executam **verificações proativas** antes de criar/atualizar recursos (por exemplo, "buckets devem ser criptografados"), **falhando a operação** ou **avisando**.

## Exemplo prático: plataforma de uma empresa com 40 contas

1. A equipe de plataforma publica **modules** para bucket seguro, role padrão e VPC.
2. A **rede** e a **segurança** ficam em stacks de fundação, com ciclo de vida lento, expostas via **Parameter Store**.
3. Cada squad mantém a **stack de aplicação** com **nested stacks** para API, fila e banco.
4. Um **StackSet service-managed** implanta o **baseline** (CloudTrail, Config, roles de auditoria) em toda a OU, inclusive em contas novas.
5. **Hooks** bloqueiam recursos sem criptografia.
6. Uma **macro** adiciona tags de custo automaticamente.
7. O pipeline aplica **change sets** revisados; **drift** é verificado semanalmente.

## Troubleshooting

| Sintoma | Causa provável | Como resolver |
|---|---|---|
| Template filho não encontrado | `TemplateURL` incorreta/sem permissão | Usar `package`; checar bucket e política |
| Stack "pendurada" em custom resource | Função não respondeu | Enviar resposta sempre; reduzir timeout; cancelar |
| Não consigo excluir/alterar stack | Outra stack importa seus exports | Remover as importações primeiro |
| StackSet falha em algumas contas | Roles ausentes ou limites | Ver motivo por instância; corrigir e reaplicar |
| Conta nova sem baseline | StackSet self-managed | Usar service-managed com auto-deployment |
| `InsufficientCapabilities` com macro | Falta `CAPABILITY_AUTO_EXPAND` | Informar a capability |
| Macro gera resultado inesperado | Lógica da função | Ver template processado |
| Limite de recursos por stack | Template grande demais | Dividir em nested stacks |

## Erros comuns e armadilhas

- **Um template monolítico** com tudo.
- **Alterar nested stacks diretamente** em vez da raiz.
- **Abusar de Export/ImportValue**, travando mudanças.
- **StackSets self-managed** sem automação de roles.
- **Custom resources sem resposta** e sem tratamento de Delete.
- **Macros com permissões excessivas** ou sem controle de versão.
- **Não testar StackSets em uma OU de teste** antes da organização inteira.
- **Reuso por copiar/colar** em vez de modules ou nested stacks.

## 🧩 Quiz de Fixação

1. Quando preferir nested stacks a stacks independentes?
2. Qual a desvantagem de Export/ImportValue?
3. O que faz um StackSet?
4. Qual a diferença entre modelo self-managed e service-managed?
5. Por que um custom resource precisa responder ao CloudFormation?
6. Para que servem os modules?

**Respostas:**
1) Quando os componentes compartilham o mesmo ciclo de vida e são implantados juntos, reutilizando templates; stacks independentes servem a ciclos de vida distintos.
2) Cria acoplamento rígido: a stack exportadora não pode ser alterada ou excluída enquanto houver importadores, e funciona só na mesma região e conta.
3) Implanta o mesmo template em várias contas e regiões com uma única operação, criando stack instances em cada destino.
4) No self-managed você cria as roles de administração e execução; no service-managed a integração com o Organizations as cria e permite implantação automática em novas contas.
5) Porque o CloudFormation aguarda a resposta para continuar; sem ela a stack fica pendurada até o timeout (até cerca de uma hora).
6) Para empacotar blocos reutilizáveis de recursos, registrados no Registry, padronizando configurações e governança.
