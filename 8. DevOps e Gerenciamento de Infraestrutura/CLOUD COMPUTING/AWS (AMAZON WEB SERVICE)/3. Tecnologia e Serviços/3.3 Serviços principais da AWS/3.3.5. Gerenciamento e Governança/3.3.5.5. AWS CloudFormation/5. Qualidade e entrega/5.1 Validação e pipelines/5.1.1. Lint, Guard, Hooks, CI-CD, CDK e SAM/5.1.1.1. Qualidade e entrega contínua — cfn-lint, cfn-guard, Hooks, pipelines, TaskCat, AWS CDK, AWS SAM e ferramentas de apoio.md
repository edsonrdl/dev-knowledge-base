### Qualidade e entrega contínua — cfn-lint, cfn-guard, Hooks, pipelines, TaskCat, AWS CDK, AWS SAM e ferramentas de apoio

> [!warning] Aviso
> Versões de ferramentas, nomes de serviços de pipeline, sintaxe de regras Guard e recursos do CDK/SAM mudam com frequência. Os exemplos aqui são referências de estudo; confirme na documentação. Os comandos **não foram executados**.

Infraestrutura como código só entrega o seu valor completo quando é tratada **como software**: **validada automaticamente**, **testada**, **revisada** e **implantada por pipelines**. Um template que "funciona na minha máquina" mas falha na produção, ou que cria um bucket sem criptografia porque ninguém revisou, é o equivalente a **subir código sem testes**. Esta folha reúne as ferramentas para **garantir qualidade antes do deploy** (lint, policy as code, hooks), **entregar com segurança** (pipelines, ambientes, promoção) e **escrever menos YAML** (CDK, SAM).

**Analogia:** uma fábrica não despacha produtos sem **inspeção de qualidade** (lint e Guard), **teste em protótipo** (ambiente de homologação, TaskCat), **aprovação do responsável técnico** (revisão do change set) e **linha de montagem padronizada** (pipeline). O CDK e o SAM são **máquinas que geram as plantas** a partir de um projeto de nível mais alto.

## O pipeline de qualidade de IaC

```
 Commit ─► Lint ─► Policy as code ─► Testes ─► Change set ─► Aprovação ─► Deploy dev ─► Deploy prod
           cfn-lint  cfn-guard         TaskCat  (preview)     (humana)       │               │
                     Hooks (runtime)                                         └── Drift detection periódica
```

| Estágio | Ferramenta | Pergunta |
|---|---|---|
| **Sintaxe e boas práticas** | `cfn-lint` | O template é válido e segue boas práticas? |
| **Políticas organizacionais** | `cfn-guard` | Atende às regras (criptografia, tags, acesso público)? |
| **Verificação em runtime** | **CloudFormation Hooks** | Bloqueia criação/atualização fora da política? |
| **Teste de implantação** | TaskCat, stacks de teste | O template realmente cria o ambiente? |
| **Pré-visualização** | Change set | O que vai mudar? Há *replacement*? |
| **Entrega** | CodePipeline, GitHub Actions, GitLab CI | Implantação automatizada e promovida |
| **Pós-deploy** | Drift detection, Config | O ambiente continua igual ao código? |

## cfn-lint

O **cfn-lint** valida templates contra a **especificação do CloudFormation** e **boas práticas**, **sem implantar nada**.

```bash
pip install cfn-lint
cfn-lint template.yaml
cfn-lint templates/**/*.yaml --format parseable
```

| Detecta | Exemplo |
|---|---|
| Propriedades inexistentes ou com tipo errado | `InstanceType` com número |
| Referências inválidas | `!Ref RecursoQueNaoExiste` |
| Valores inválidos para a região | Tipo de instância inexistente |
| Boas práticas | Uso de `DependsOn` desnecessário, runtimes obsoletos |
| Segurança básica | Regras de security group abertas, IAM `*` (conforme regras habilitadas) |

```yaml
# .pre-commit-config.yaml
repos:
  - repo: https://github.com/aws-cloudformation/cfn-lint
    rev: v1.x
    hooks:
      - id: cfn-lint
```

> [!tip] Lint no pre-commit **e** no CI
> No pre-commit, o desenvolvedor corrige em segundos; no CI, ninguém pula a verificação. Os dois juntos fecham o ciclo.

O comando nativo `aws cloudformation validate-template` só checa **sintaxe básica**; o cfn-lint é muito mais rigoroso.

## cfn-guard (policy as code)

O **CloudFormation Guard** é uma ferramenta de **política como código** com uma DSL declarativa. Ele avalia templates (e outros JSON/YAML) contra **regras** da organização.

```
# regras.guard
let buckets = Resources.*[ Type == 'AWS::S3::Bucket' ]

rule buckets_criptografados when %buckets !empty {
    %buckets.Properties.BucketEncryption exists
    <<Todo bucket deve ter criptografia>>
}

rule buckets_sem_acesso_publico when %buckets !empty {
    %buckets.Properties.PublicAccessBlockConfiguration.BlockPublicAcls == true
    %buckets.Properties.PublicAccessBlockConfiguration.RestrictPublicBuckets == true
}

rule tags_obrigatorias {
    Resources.*.Properties.Tags exists
}
```

```bash
cfn-guard validate --data template.yaml --rules regras.guard
cfn-guard test --rules-file regras.guard --test-data testes.yaml   # testes das próprias regras
```

| Uso | Observação |
|---|---|
| **Shift-left** | Barra o template **antes** do deploy |
| **Mesmas regras no AWS Config** | Regras custom Guard no Config avaliam o **estado real** |
| **Rule packs** | Coleções de regras prontas (CIS, boas práticas) |
| **Testes unitários de regras** | Garante que a regra aceita/rejeita o que deve |

## CloudFormation Hooks

**Hooks** executam **verificações proativas em tempo de implantação**: o CloudFormation os invoca **antes** de provisionar um recurso, e, se a regra falhar, **bloqueia a operação** (modo `FAIL`) ou apenas **avisa** (`WARN`).

| Característica | Detalhe |
|---|---|
| **Escopo** | Tipos de recurso, stacks ou change sets |
| **Modos de falha** | `FAIL` (bloqueia) ou `WARN` (avisa) |
| **Hook com Guard** | Escreva a regra em Guard, sem programar |
| **Hook com Lambda** | Lógica customizada |
| **Hooks da AWS** | Alguns prontos (ex.: verificar criptografia de buckets) |
| **Vantagem sobre lint** | Vale para **qualquer** implantação, inclusive as feitas à mão |

```
 create-stack ──► Hook "S3-criptografado" ──┬─ OK    ──► cria o bucket
                                            └─ FALHA ──► bloqueia: "bucket sem criptografia"
```

> [!tip] Defesa em profundidade
> **Lint + Guard no pipeline** pegam cedo; **Hooks** pegam o que escapar; **Config rules** pegam o que foi criado fora do CloudFormation. Cada camada cobre a falha da outra.

## Testes de templates

| Tipo de teste | Ferramenta | O que valida |
|---|---|---|
| **Estático** | cfn-lint, cfn-guard | Estrutura e políticas |
| **Implantação em conta de teste** | `deploy` + `delete` em pipeline | O template cria e exclui sem erro |
| **Multi-região** | **TaskCat** | Cria o template em várias regiões/parametrizações e gera relatório |
| **Integração** | Scripts pós-deploy (curl, smoke tests) | O ambiente responde |
| **Testes de infraestrutura** | InSpec, Terratest (Go), pytest + boto3 | Propriedades reais dos recursos |
| **Rollback** | Provocar falha em dev | O plano de volta funciona |

```yaml
# .taskcat.yml
project:
  name: minha-plataforma
  regions: [us-east-1, sa-east-1]
tests:
  basico:
    template: templates/rede.yaml
    parameters:
      Ambiente: dev
```

## Pipelines de implantação

### Padrão recomendado

```
 Git (main) ─► CI: lint + guard + testes
              ─► Change set (dev)  ─► deploy dev ─► smoke tests
              ─► Change set (prod) ─► APROVAÇÃO MANUAL ─► deploy prod ─► drift/Config
```

| Ferramenta | Uso |
|---|---|
| **AWS CodePipeline + CodeBuild + CloudFormation actions** | Pipeline nativo; ações `CREATE_UPDATE`, `CHANGE_SET_REPLACE`, `CHANGE_SET_EXECUTE` |
| **GitHub Actions** | `aws-actions/aws-cloudformation-github-deploy` |
| **GitLab CI / Jenkins** | `aws cloudformation deploy` em jobs |
| **Git sync (CloudFormation Git sync)** | A stack se **sincroniza** com um repositório; commits disparam atualizações |

```yaml
# GitHub Actions (resumo)
jobs:
  deploy-dev:
    runs-on: ubuntu-latest
    permissions: {id-token: write, contents: read}   # OIDC: sem chaves de longa duração
    steps:
      - uses: actions/checkout@v4
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::123456789012:role/GitHubDeploy
          aws-region: us-east-1
      - run: pip install cfn-lint && cfn-lint templates/*.yaml
      - run: aws cloudformation deploy --template-file templates/app.yaml
              --stack-name app-dev --parameter-overrides Ambiente=dev
              --capabilities CAPABILITY_NAMED_IAM --no-fail-on-empty-changeset
```

| Boa prática | Motivo |
|---|---|
| **OIDC** em vez de chaves de acesso | Credenciais temporárias, sem segredos no CI |
| **Contas separadas** (dev/homolog/prod) | Isolamento |
| **Mesmo template**, parâmetros por ambiente | Paridade |
| **Role de serviço** da stack com **menor privilégio** | Limita o dano |
| **Aprovação humana** para prod | Controle de mudança |
| **Artefatos versionados** | Rastreabilidade |

## AWS CDK

O **AWS Cloud Development Kit (CDK)** permite **definir infraestrutura em linguagens de programação** (TypeScript, Python, Java, C#, Go). O CDK **sintetiza** templates CloudFormation e os implanta por ele.

```typescript
import * as cdk from 'aws-cdk-lib';
import * as s3 from 'aws-cdk-lib/aws-s3';

export class DadosStack extends cdk.Stack {
  constructor(scope: cdk.App, id: string, props?: cdk.StackProps) {
    super(scope, id, props);
    new s3.Bucket(this, 'BucketDados', {
      versioned: true,
      encryption: s3.BucketEncryption.S3_MANAGED,
      blockPublicAccess: s3.BlockPublicAccess.BLOCK_ALL,
      removalPolicy: cdk.RemovalPolicy.RETAIN,
    });
  }
}
```

```bash
cdk synth      # gera o template CloudFormation
cdk diff       # compara com a stack implantada (equivale a um change set)
cdk deploy     # implanta
```

| Conceito CDK | Descrição |
|---|---|
| **App / Stack** | Unidade de implantação (uma stack CloudFormation) |
| **Construct L1** | Mapeamento 1:1 de um recurso (`CfnBucket`) |
| **Construct L2** | Abstração com padrões sensatos (`s3.Bucket`) |
| **Construct L3 (patterns)** | Arquiteturas prontas (`ApplicationLoadBalancedFargateService`) |
| **Aspects** | Aplicam regras a todos os recursos (ex.: tags, verificações) |
| **cdk-nag** | Verificações de segurança/boas práticas no synth |

| CDK vs YAML puro | Vantagem do CDK | Cuidado |
|---|---|---|
| Reuso | Classes, funções, loops | Mais abstração para depurar |
| Padrões | Defaults seguros | Pode esconder o que será criado (use `cdk diff`) |
| Testes | Testes unitários da infra | Requer conhecimento de programação |
| Saída | Gera CloudFormation | Os erros aparecem como eventos de stack |

## AWS SAM

O **AWS Serverless Application Model (SAM)** é uma **extensão do CloudFormation** para aplicações **serverless**: com poucas linhas declara funções, APIs, tabelas e filas, e a **transformação** `AWS::Serverless-2016-10-31` as expande em recursos CloudFormation.

```yaml
Transform: AWS::Serverless-2016-10-31
Resources:
  Funcao:
    Type: AWS::Serverless::Function
    Properties:
      Runtime: python3.12
      Handler: app.handler
      CodeUri: src/
      Events:
        Api:
          Type: Api
          Properties: {Path: /itens, Method: get}
  Tabela:
    Type: AWS::Serverless::SimpleTable
```

```bash
sam build && sam validate
sam local invoke Funcao --event evento.json      # teste local
sam deploy --guided                               # implanta (usa CloudFormation)
```

| Ferramenta | Melhor para |
|---|---|
| **YAML puro** | Aprender o modelo; infraestrutura estável e direta |
| **SAM** | Aplicações serverless (Lambda, API Gateway, DynamoDB) |
| **CDK** | Plataformas e padrões reutilizáveis, equipes que programam |
| **Terraform** | Multi-nuvem ou ecossistema já adotado |

## Governança contínua

| Mecanismo | Função |
|---|---|
| **Config rules** | Avalia o estado real, inclusive o criado fora do código |
| **Drift detection** | Aponta alterações manuais |
| **Service Catalog** | Entrega templates aprovados como produtos de autoatendimento |
| **SCPs** | Impedem criar recursos fora do padrão (ex.: sem criptografia) |
| **Tags de custo** | Rastreabilidade por stack e time |
| **Notificações da stack** | Eventos via SNS/EventBridge |

```json
{
  "source": ["aws.cloudformation"],
  "detail-type": ["CloudFormation Stack Status Change"],
  "detail": {"status-details": {"status": ["UPDATE_ROLLBACK_COMPLETE", "ROLLBACK_COMPLETE", "UPDATE_ROLLBACK_FAILED"]}}
}
```

Alertar **falhas de stack** no canal da equipe encurta o tempo até a correção.

## Exemplo prático: pipeline completo para uma plataforma

1. Repositório com `templates/` (rede, dados, app), `rules/` (Guard) e `tests/`.
2. **Pre-commit**: `cfn-lint`. **CI**: lint + Guard + testes das regras.
3. **Deploy em dev** automático por OIDC; **smoke tests** validam a aplicação.
4. **Change set de prod** gerado e **anexado ao pull request**; aprovação humana.
5. **Hooks** bloqueiam recursos sem criptografia mesmo em deploys fora do pipeline.
6. Após o deploy, **drift detection** semanal e **Config rules** confirmam a conformidade.
7. Falhas de stack geram eventos para o canal de operações.

## Troubleshooting

| Sintoma | Causa provável | Como resolver |
|---|---|---|
| `cfn-lint` acusa regra que não se aplica | Falso positivo | Ignorar a regra pontualmente com justificativa (`Metadata: cfn-lint`) |
| Guard falha em template válido | Regra muito rígida ou escopo incorreto | Ajustar a regra e testar com `cfn-guard test` |
| Hook bloqueia deploy legítimo | Política restritiva | Ajustar o hook ou usar `WARN` durante a adoção |
| Pipeline sem permissão | Role OIDC/serviço insuficiente | Revisar trust policy e permissões |
| `deploy` falha "No changes" | Sem mudanças | Usar `--no-fail-on-empty-changeset` |
| CDK cria algo inesperado | Abstração L2/L3 com defaults | `cdk diff` e `cdk synth` para inspecionar |
| SAM local diferente da nuvem | Emulação limitada | Testar também em conta de desenvolvimento |
| Template processado difere | Macro/Transform | `get-template --template-stage Processed` |

## Erros comuns e armadilhas

- **Implantar direto do notebook** sem pipeline.
- **Só `validate-template`** achando que basta.
- **Chaves de acesso de longa duração** no CI em vez de OIDC.
- **Aplicar em prod sem change set e sem aprovação.**
- **Policy as code só no CI**, sem Hooks/Config para o que escapar.
- **Usar CDK sem `cdk diff`** e perder a noção do que será alterado.
- **Ambientes com templates diferentes** em vez de parâmetros.
- **Não monitorar falhas de stack.**

## 🧩 Quiz de Fixação

1. Qual a diferença entre cfn-lint e cfn-guard?
2. O que fazem os CloudFormation Hooks?
3. Por que usar OIDC no pipeline?
4. Qual a relação entre CDK e CloudFormation?
5. Para que serve o SAM?
6. Por que combinar lint, Guard, Hooks e Config?

**Respostas:**
1) O cfn-lint valida sintaxe e boas práticas do template; o cfn-guard avalia regras organizacionais (policy as code), como criptografia e tags obrigatórias.
2) Verificam proativamente, durante a implantação, se os recursos atendem a políticas, bloqueando (FAIL) ou avisando (WARN).
3) Para usar credenciais temporárias, sem guardar chaves de acesso de longa duração no CI.
4) O CDK sintetiza templates CloudFormation a partir de código e os implanta por ele; os erros aparecem como eventos da stack.
5) Simplificar aplicações serverless, expandindo declarações curtas em recursos CloudFormation por meio de uma transformação.
6) Defesa em profundidade: cada camada pega falhas que as outras podem deixar passar (cedo no pipeline, na implantação e no estado real).
