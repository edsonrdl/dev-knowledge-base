### Mudanças seguras no CloudFormation — change sets, rollback, drift detection, stack policy, termination protection, import e retain

> [!warning] Aviso
> Estados de stack, opções de rollback, tipos de recurso com suporte a drift e import, e limites mudam. Os detalhes aqui são referências de estudo; confirme na documentação. Os comandos **não foram executados**.

Criar uma stack é fácil; **alterá-la sem destruir nada** é onde está o risco. Uma pequena edição de propriedade pode virar uma **substituição (replacement)** que apaga um banco de dados; uma alteração manual no console cria **drift** que surpreende na próxima atualização; um rollback quebrado deixa a stack **travada**. Esta folha reúne os mecanismos do CloudFormation para **prever, controlar, proteger e recuperar** mudanças: **change sets**, **rollback**, **drift detection**, **stack policy**, **termination protection**, **retain/snapshot** e **import**.

**Analogia:** reformar uma casa habitada exige **projeto aprovado** antes da obra (change set), **registro do que já foi alterado fora do projeto** (drift), **tapumes protegendo as paredes estruturais** (stack policy), **cadeado na porta da demolição** (termination protection) e **cópia dos documentos importantes guardada fora da casa** (retain/snapshot). Se a obra falha, o **plano de volta** (rollback) deve funcionar.

## Change sets: ver antes de aplicar

Um **change set** é uma **pré-visualização** das mudanças que uma atualização causaria, **sem executá-las**.

```
 Template novo ──► create-change-set ──► Lista de mudanças ──► (revisão humana) ──► execute-change-set
                                         ├─ Add:    BucketLogs
                                         ├─ Modify: Servidor (Replacement = True!)
                                         └─ Remove: SecurityGroupAntigo
```

```bash
aws cloudformation create-change-set \
  --stack-name app-prod --change-set-name mudanca-123 \
  --template-body file://app.yaml \
  --parameters ParameterKey=Ambiente,ParameterValue=prod \
  --capabilities CAPABILITY_NAMED_IAM

aws cloudformation describe-change-set --stack-name app-prod --change-set-name mudanca-123 \
  --query 'Changes[].ResourceChange.[Action,LogicalResourceId,Replacement,Scope]' --output table

aws cloudformation execute-change-set --stack-name app-prod --change-set-name mudanca-123
```

| Campo da pré-visualização | O que revela |
|---|---|
| **Action** | `Add`, `Modify`, `Remove`, `Import`, `Dynamic` |
| **Replacement** | `True` (**substitui** o recurso), `False`, `Conditional` |
| **Scope** | Propriedades, tags, atributos afetados |
| **Details** | Qual propriedade causa a mudança e por quê |

> [!warning] `Replacement: True` em recurso com dados é sinal vermelho
> Banco de dados, tabela, volume ou bucket com `Replacement: True` significa **criar um novo e apagar o antigo**. Pare, revise e use `Retain/Snapshot` ou outra estratégia (por exemplo, migração controlada).

### Tipos de change set

| Tipo | Uso |
|---|---|
| **UPDATE** | Atualizar stack existente |
| **CREATE** | Pré-visualizar a **criação** de uma stack nova |
| **IMPORT** | **Importar** recursos existentes para a stack |
| **Deploy com `--no-execute-changeset`** | `aws cloudformation deploy --no-execute-changeset` cria sem executar |

> [!tip] Change set no pipeline
> Em CI/CD, gere o change set, **publique o resumo** na revisão (pull request ou aprovação manual) e só então execute. Isso transforma a infraestrutura em algo **revisável como código**.

## Rollback e estados de falha

| Situação | Comportamento |
|---|---|
| **Falha na criação** | Rollback automático → `ROLLBACK_COMPLETE`; a stack só pode ser **excluída** |
| **Falha na atualização** | Rollback → `UPDATE_ROLLBACK_COMPLETE` (volta ao estado anterior) |
| **Falha no rollback** | `UPDATE_ROLLBACK_FAILED`; exige correção e **`continue-update-rollback`** |
| **Desligar rollback na criação** | `--disable-rollback` (mantém os recursos criados para depuração) |
| **Gatilhos de rollback** | Alarmes do CloudWatch que, se disparam durante a atualização, causam rollback |

```bash
# Mantém os recursos criados para investigar a falha
aws cloudformation create-stack --stack-name teste --template-body file://t.yaml --disable-rollback

# Estado travado em UPDATE_ROLLBACK_FAILED: continuar, ignorando recursos problemáticos
aws cloudformation continue-update-rollback --stack-name app-prod \
  --resources-to-skip RecursoQueNaoVoltaAoEstadoAnterior
```

### Rollback triggers

```bash
aws cloudformation update-stack --stack-name app-prod --template-body file://app.yaml \
  --rollback-configuration 'RollbackTriggers=[{Arn=arn:aws:cloudwatch:us-east-1:123456789012:alarm:erros5xx,Type=AWS::CloudWatch::Alarm}],MonitoringTimeInMinutes=10'
```

Se o alarme disparar durante ou até 10 minutos depois da atualização, o CloudFormation **reverte automaticamente**, útil para **deploys seguros** de aplicações.

### Causas comuns de `UPDATE_ROLLBACK_FAILED`

| Causa | Solução |
|---|---|
| Recurso alterado/excluído manualmente | Corrigir o recurso ou usar `--resources-to-skip` |
| Permissão IAM insuficiente | Ajustar a role de serviço da stack |
| Limite de serviço | Resolver a quota |
| Dependência de recurso excluído | Recriar ou pular |

## Drift detection

**Drift** é a diferença entre o **template** e o **estado real**. Surge quando alguém altera um recurso no console, pela CLI ou por outra automação.

```bash
aws cloudformation detect-stack-drift --stack-name app-prod
aws cloudformation describe-stack-drift-detection-status --stack-drift-detection-id <id>
aws cloudformation describe-stack-resource-drifts --stack-name app-prod \
  --stack-resource-drift-status-filters MODIFIED DELETED
```

| Status do recurso | Significado |
|---|---|
| **IN_SYNC** | Igual ao template |
| **MODIFIED** | Propriedades alteradas fora do CloudFormation |
| **DELETED** | Recurso removido manualmente |
| **NOT_CHECKED** | Tipo sem suporte a drift |

O resultado mostra **propriedade a propriedade**: valor esperado vs valor atual.

| Como tratar o drift | Quando |
|---|---|
| **Reverter a mudança manual** | A alteração era indevida |
| **Atualizar o template** para refletir o novo estado | A mudança era legítima |
| **Reaplicar a stack** | Corrige propriedades divergentes (nem sempre; depende do que o CloudFormation compara) |

> [!tip] Drift automático
> Combine **drift detection agendada** (EventBridge + Lambda/Automation) com **alarme** para avisar quando uma stack crítica divergir. O **AWS Config** também tem regra `cloudformation-stack-drift-detection-check`.

> [!warning] Drift só vê o que o template declara
> O CloudFormation compara **propriedades declaradas** no template. Se alguém adicionar **um recurso extra** (por exemplo, uma regra em um security group gerido por outro recurso) que o template não descreve, pode não ser detectado. Governança complementar (Config) é recomendada.

## Proteções de recurso e de stack

### DeletionPolicy e UpdateReplacePolicy

| Política | Valores | Efeito |
|---|---|---|
| **`DeletionPolicy`** | `Delete` (padrão), `Retain`, `Snapshot`, `RetainExceptOnCreate` | O que fazer ao **excluir** a stack ou remover o recurso |
| **`UpdateReplacePolicy`** | `Delete`, `Retain`, `Snapshot` | O que fazer com o recurso **antigo** em uma **substituição** |

`Snapshot` vale para volumes EBS, RDS, Redshift, Neptune, DocumentDB e outros que suportam snapshots.

### Stack policy

Uma **stack policy** é um documento JSON que **impede atualizações** em recursos protegidos.

```json
{
  "Statement": [
    {"Effect": "Allow", "Action": "Update:*", "Principal": "*", "Resource": "*"},
    {"Effect": "Deny",  "Action": ["Update:Replace", "Update:Delete"],
     "Principal": "*", "Resource": "LogicalResourceId/BancoPrincipal"}
  ]
}
```

| Efeito | Detalhe |
|---|---|
| Protege o `BancoPrincipal` | Nenhuma atualização pode **substituir ou excluir** |
| **Sobrescrita temporária** | Em casos justificados, `--stack-policy-during-update-body` permite uma exceção |
| Limite | Só vale para **atualizações da stack**, não para ações diretas no recurso |

### Termination protection

```bash
aws cloudformation update-termination-protection --enable-termination-protection \
  --stack-name app-prod
```

Impede que a stack seja **excluída** por engano (a exclusão exige desabilitar a proteção antes). Ative em **toda stack de produção**.

### Role de serviço e IAM

| Recurso | Função |
|---|---|
| **Service role** da stack | O CloudFormation assume uma role específica para criar/alterar recursos |
| **Permissões separadas** | Quem **aciona** a stack pode ter menos poder do que a role que **executa** |
| **`iam:PassRole`** | Necessário para usar a service role |
| **Capabilities** | `CAPABILITY_IAM`, `CAPABILITY_NAMED_IAM`, `CAPABILITY_AUTO_EXPAND` reconhecem que o template cria IAM ou usa macros |

## Importar recursos existentes

O **resource import** traz **recursos criados fora do CloudFormation** para uma stack, **sem recriá-los**.

```bash
# 1. Descrever o que importar
cat > recursos.json <<'EOF'
[{"ResourceType":"AWS::S3::Bucket","LogicalResourceId":"BucketDados",
  "ResourceIdentifier":{"BucketName":"meu-bucket-existente"}}]
EOF

# 2. Change set do tipo IMPORT
aws cloudformation create-change-set --stack-name importada --change-set-name imp \
  --change-set-type IMPORT --resources-to-import file://recursos.json \
  --template-body file://template-com-o-bucket.yaml

aws cloudformation execute-change-set --stack-name importada --change-set-name imp
```

| Regra | Observação |
|---|---|
| O template precisa **declarar** o recurso com `DeletionPolicy` | `Retain` é exigido na importação |
| O template deve **refletir** a configuração real | Divergências geram drift/erros |
| Nem todos os tipos suportam importação | Confira a lista de tipos |
| Importação **não altera** o recurso | Só passa a ser gerenciado |

O **IaC generator** pode **escanear** a conta e **gerar** templates a partir de recursos existentes, acelerando a adoção.

### Mover recursos entre stacks (refactoring)

Para reorganizar, existe o **stack refactoring**/**import + Retain**: exclua o recurso da stack antiga com `Retain` e importe para a nova, evitando recriação.

## Atualizações em Auto Scaling e Lambda

| Recurso | Política | Efeito |
|---|---|---|
| **Auto Scaling Group** | `UpdatePolicy: AutoScalingRollingUpdate` | Atualiza instâncias em lotes (`MinInstancesInService`, `MaxBatchSize`, `PauseTime`) |
| **ASG com `CreationPolicy`** | `ResourceSignal` | Espera `cfn-signal` das instâncias antes de considerar OK |
| **Lambda Alias** | `UpdatePolicy: CodeDeployLambdaAliasUpdate` | Deploy gradual (canary/linear) |
| **ECS Service** | `DeploymentConfiguration` e `DeploymentCircuitBreaker` | Rollback automático de deploy |

## Fluxo recomendado de mudança

```
 1. Alterar o template no Git (branch)
 2. Validar: cfn-lint / cfn-guard / validate-template
 3. Pull request + change set anexado
 4. Revisão: há Replacement? Mudança em IAM? Em dados?
 5. Aplicar em dev → homolog → prod (mesmo template, parâmetros distintos)
 6. Rollback triggers com alarmes de saúde
 7. Drift detection periódica
```

| Camada de segurança | Mecanismo |
|---|---|
| Pré-deploy | Lint, Guard, Hooks, change set |
| Durante | Rollback triggers, circuit breakers |
| Pós-deploy | Drift detection, Config |
| Proteção permanente | `Retain/Snapshot`, stack policy, termination protection |

## Exemplo prático: evitando a substituição de um banco

1. Um desenvolvedor muda o nome lógico do recurso `BancoPrincipal` para `Banco`.
2. O **change set** mostra `Remove: BancoPrincipal` e `Add: Banco` (ou `Replacement: True`).
3. O revisor percebe o risco; o PR é reprovado.
4. Para renomear com segurança: adiciona `DeletionPolicy: Retain`, remove da stack antiga, **importa** o banco na stack nova com o novo nome lógico.
5. A **stack policy** passa a negar `Update:Replace` e `Update:Delete` no banco.
6. Uma regra do Config acusa qualquer stack de produção sem `TerminationProtection`.

## Troubleshooting

| Sintoma | Causa provável | Como resolver |
|---|---|---|
| `ROLLBACK_COMPLETE` na criação | Erro em algum recurso | Ler eventos; excluir a stack; corrigir e recriar |
| `UPDATE_ROLLBACK_FAILED` | Recurso alterado manualmente ou sem permissão | `continue-update-rollback` com skip |
| `DELETE_FAILED` | Bucket não vazio, ENI em uso, dependência externa | Esvaziar/remover o bloqueio e excluir de novo (retain) |
| Change set vazio | Sem mudanças no template | Verificar parâmetros e versão |
| Import falha | Template diverge do recurso real | Alinhar propriedades; `DeletionPolicy: Retain` |
| Drift inesperado | Alteração manual | Reverter ou atualizar o template |
| `InsufficientCapabilitiesException` | Falta `CAPABILITY_IAM` | Informar a capability |
| Stack bloqueada por exports | Outra stack importa o valor | Remover a dependência primeiro |

## Erros comuns e armadilhas

- **Aplicar `update-stack` sem change set** em produção.
- **Ignorar `Replacement: True`** em recursos com dados.
- **Editar recursos no console** e deixar drift acumular.
- **Sem `TerminationProtection`** em stacks críticas.
- **Rollback desligado** e deixar recursos pela metade.
- **Importar sem `DeletionPolicy: Retain`.**
- **Roles de serviço amplas demais** (`AdministratorAccess`).
- **Não testar o plano de volta** (rollback) em ambientes não produtivos.

## 🧩 Quiz de Fixação

1. O que é um change set?
2. Qual valor do change set indica que o recurso será substituído?
3. O que é drift e como detectá-lo?
4. Para que serve a stack policy?
5. Qual o papel da termination protection?
6. Qual comando continua um rollback travado?

**Respostas:**
1) Uma pré-visualização das mudanças que uma atualização causaria, que pode ser revisada antes de ser executada.
2) `Replacement: True`.
3) É a diferença entre o template e o estado real dos recursos (por alterações manuais); detecta-se com detect-stack-drift e descreve-se com describe-stack-resource-drifts.
4) Impedir atualizações (por exemplo, replace ou delete) em recursos protegidos da stack.
5) Impedir a exclusão acidental da stack, exigindo desabilitar a proteção antes.
6) `continue-update-rollback`, opcionalmente com `--resources-to-skip`.
