### Operando o CloudFormation — IAM e service roles, limites, custos, troubleshooting de falhas de stack e checklist de produção

> [!warning] Aviso
> Limites de serviço, mensagens de erro, preços e comportamentos de estados mudam. Os números aqui são referências de estudo; confirme na documentação e em Service Quotas. Os comandos **não foram executados**.

O CloudFormation tem **poder de criar, alterar e destruir** praticamente qualquer recurso da conta. Por isso operá-lo em produção é, antes de tudo, uma questão de **permissões**, de **limites conhecidos** e de **diagnóstico rápido** quando uma stack falha. Esta folha reúne o que sustenta o CloudFormation em escala: o **modelo de IAM** (quem pode implantar e com que identidade), os **limites** que travam projetos grandes, **custos**, um **roteiro de troubleshooting** dos erros mais comuns e um **checklist de produção**.

**Analogia:** o CloudFormation é um **empreiteiro com procuração**: ele assina e executa obras em seu nome. Você precisa decidir **quem pode contratá-lo**, **até onde vai a procuração** (service role), **quais obras são proibidas** (SCPs, hooks, stack policy) e **como investigar** quando uma obra emperra.

## Modelo de permissões

```
 Quem aciona (pessoa/pipeline)      ──► cloudformation:CreateStack / UpdateStack ...
        │ iam:PassRole
        ▼
 Service role da stack  ──► o CloudFormation ASSUME esta role para criar os recursos
        │
        ▼
 Recursos criados (S3, EC2, IAM, ...)
```

| Identidade | Papel | Prática |
|---|---|---|
| **Usuário/pipeline** | Chama a API do CloudFormation | Permissões **só** para as stacks de seu escopo (por ARN/nome/tags) |
| **Service role da stack** | **Executa** a criação dos recursos | Menor privilégio **por stack ou camada** |
| **Role do pipeline** | Assumida por OIDC/CodePipeline | Pode apenas `PassRole` da service role específica |
| **Sem service role** | O CloudFormation usa as **credenciais de quem chamou** | Dá ao chamador poder direto sobre todos os recursos |

> [!tip] Separação de poderes
> Com uma **service role**, o desenvolvedor pode **implantar** uma stack **sem ter permissão** para criar os recursos diretamente. Ele só consegue o que o **template** (revisado) e a role permitem: é um excelente controle para **autoatendimento seguro**.

### Políticas típicas

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "OperarStacksDoTime",
      "Effect": "Allow",
      "Action": ["cloudformation:CreateStack","cloudformation:UpdateStack","cloudformation:DeleteStack",
                 "cloudformation:CreateChangeSet","cloudformation:ExecuteChangeSet",
                 "cloudformation:DescribeStacks","cloudformation:DescribeStackEvents"],
      "Resource": "arn:aws:cloudformation:*:123456789012:stack/timeA-*/*"
    },
    {
      "Sid": "UsarSomenteAServiceRoleDoTime",
      "Effect": "Allow",
      "Action": "iam:PassRole",
      "Resource": "arn:aws:iam::123456789012:role/CfnServiceRole-timeA",
      "Condition": {"StringEquals": {"iam:PassedToService": "cloudformation.amazonaws.com"}}
    }
  ]
}
```

| Condição útil | Efeito |
|---|---|
| `cloudformation:RoleArn` | Exige que a stack use uma service role aprovada |
| `cloudformation:TemplateUrl` | Só permite templates de um bucket confiável |
| `cloudformation:ResourceTypes` | Restringe **quais tipos de recurso** podem ser criados (ex.: proibir `AWS::IAM::User`) |
| `aws:RequestTag` / `aws:ResourceTag` | Controle por tags |

### Capabilities

| Capability | Quando é exigida |
|---|---|
| `CAPABILITY_IAM` | Template cria recursos IAM com nomes gerados |
| `CAPABILITY_NAMED_IAM` | Template cria IAM com **nomes personalizados** |
| `CAPABILITY_AUTO_EXPAND` | Template usa **macros** ou nested stacks com transforms |

São um **reconhecimento explícito** de que o template pode **alterar permissões**; **revise sempre** os recursos IAM de um template antes de aceitar.

### Riscos de escalada de privilégio

| Risco | Como acontece | Mitigação |
|---|---|---|
| Template cria uma role **administradora** | Usuário com permissão de stack escala privilégios | Condição `cloudformation:ResourceTypes`; **permissions boundary** nas roles criadas; revisão de PR |
| Service role **AdministratorAccess** | Qualquer template faz qualquer coisa | Roles por camada com permissões mínimas |
| `iam:PassRole` irrestrito | Passar roles poderosas | Restringir por ARN e serviço |
| Templates de URLs não confiáveis | Código malicioso | Restringir `TemplateUrl` |

## Limites de referência

| Limite | Valor de referência | Como lidar |
|---|---|---|
| **Recursos por stack** | ~500 | Nested stacks / dividir por camada |
| **Parâmetros por template** | ~200 | Agrupar em tipos de lista/JSON |
| **Outputs por template** | ~200 | Reduzir exports |
| **Mappings** | ~200 | Mapas menores |
| **Tamanho do template** | Algumas dezenas de KB (corpo) a algumas centenas de KB (S3) | Usar S3; modularizar |
| **Stacks por conta/região** | Alguns milhares | Limpar stacks obsoletas |
| **Profundidade de nested stacks** | Limitada | Manter estrutura rasa |
| **Instâncias de StackSet** | Muitas milhares | Planejar lotes |
| **Tempo de custom resource** | Até ~1 hora de espera | Responder sempre |

Confirme os valores atuais em **Service Quotas**. Os limites de **cada serviço** (VPCs por região, IPs elásticos, instâncias) também podem bloquear a criação de recursos pelo CloudFormation.

## Custos

| Item | Observação |
|---|---|
| **CloudFormation (recursos AWS)** | **Sem custo** pelo serviço |
| **Recursos criados** | Cobrados normalmente (EC2, RDS, NAT...) |
| **Tipos de terceiros / handlers** | Cobrança por operação além de uma franquia (consulte a política) |
| **S3 dos templates** | Centavos |
| **Hooks, macros e custom resources** | Custo de Lambda associado |
| **StackSets** | Sem custo adicional pelo serviço; recursos nas contas-alvo são cobrados |
| **Ambientes efêmeros esquecidos** | O maior risco: stacks de teste ligadas |

| Controle de custo | Efeito |
|---|---|
| **Tags de custo** em todos os recursos (via stack tags) | Rateio por projeto/time |
| **Stack tags** propagadas | `--tags Key=Projeto,Value=X` aplica a todos os recursos suportados |
| **Remoção automática de ambientes de teste** | Excluir stacks por agenda/TTL |
| **Budgets e alertas** | Aviso de gasto anormal |
| **Revisão de stacks órfãs** | Listar e remover |

```bash
# Stacks de teste antigas (exemplo de auditoria)
aws cloudformation list-stacks --stack-status-filter CREATE_COMPLETE UPDATE_COMPLETE \
  --query "StackSummaries[?starts_with(StackName,'teste-')].[StackName,CreationTime]"
```

## Troubleshooting de falhas de stack

**Passo zero:** leia os **eventos** da stack, do mais recente para o mais antigo; a **primeira falha** (não a última) costuma ser a causa.

```bash
aws cloudformation describe-stack-events --stack-name app-prod \
  --query "StackEvents[?contains(ResourceStatus,'FAILED')].[Timestamp,LogicalResourceId,ResourceStatusReason]" \
  --output table
```

| Erro/sintoma | Causa provável | Como resolver |
|---|---|---|
| `ROLLBACK_COMPLETE` | Falha na criação | Ler o motivo no evento; corrigir; **excluir** e recriar |
| `UPDATE_ROLLBACK_FAILED` | Recurso alterado manualmente, sem permissão | Corrigir o recurso ou `continue-update-rollback --resources-to-skip` |
| `DELETE_FAILED` | Bucket não vazio, ENI em uso, dependência externa | Remover o impedimento e excluir novamente (ou `--retain-resources`) |
| `AlreadyExists` | Nome físico fixo já em uso | Remover o `Name` fixo (deixar o CloudFormation gerar) |
| `Circular dependency between resources` | `!Ref` mútuo (ex.: SG A referencia B e B referencia A) | Quebrar o ciclo: regras de SG como recursos separados |
| `Template format error` | YAML inválido, indentação, tipo errado | `cfn-lint`; revisar sintaxe |
| `Parameters: [x] must have values` | Parâmetro sem valor/padrão | Informar o parâmetro |
| `No export named X found` | `ImportValue` sem export correspondente | Criar a stack exportadora antes |
| `Resource handler returned message: "... limit exceeded"` | Quota do serviço | Pedir aumento de quota |
| `AccessDenied` / `is not authorized to perform` | Service role/usuário sem permissão | Ajustar a role (observe **qual** ação e **qual** identidade) |
| Stack pendurada em `CREATE_IN_PROGRESS` | `WaitCondition`/custom resource sem resposta | Verificar `cfn-signal`/Lambda; aguardar timeout |
| `Resource is not in the state ...` | Recurso em transição (ex.: RDS modificando) | Aguardar e reexecutar |
| Update sem efeito | Propriedade não suporta atualização in-place ou sem mudança real | Ver o change set |
| `InsufficientCapabilitiesException` | Falta capability | Informar `CAPABILITY_*` |

### Roteiro de diagnóstico

```
 A stack falhou?
 ├─ 1. Ler eventos: qual recurso e qual razão (primeira FAILED)
 ├─ 2. Erro de permissão? ─► ver service role / PassRole / SCP / condição
 ├─ 3. Erro de limite?    ─► Service Quotas
 ├─ 4. Erro de conteúdo?  ─► cfn-lint, template processado (macros)
 ├─ 5. Erro de dependência/ordem? ─► DependsOn, ciclo, export inexistente
 ├─ 6. Erro de estado?    ─► recurso alterado manualmente (drift)
 └─ 7. Ainda sem causa?   ─► CloudTrail (chamada de API com errorCode) e logs do recurso
```

> [!tip] O CloudTrail resolve o "porquê" profundo
> O evento da stack mostra **que** falhou; o **CloudTrail** mostra a **chamada de API real** feita pelo CloudFormation e o **errorCode/errorMessage** completos. Procure pela **service role** ou pelo usuário como `userIdentity`.

## Boas práticas e checklist de produção

1. **Templates no Git**, revisados por PR; **cfn-lint** e **Guard** no CI; **Hooks** ativos.
2. **Change set revisado** antes de qualquer atualização em produção; atenção a `Replacement`.
3. **`DeletionPolicy`/`UpdateReplacePolicy`** em dados; **stack policy** e **termination protection** em stacks críticas.
4. **Service roles com menor privilégio**, por camada; pipeline com **OIDC**, sem chaves de longa duração.
5. Restrições IAM: `cloudformation:ResourceTypes`, `TemplateUrl`, **permissions boundary**.
6. **Stacks por ciclo de vida** (rede, dados, app); nested stacks para reuso; **SSM** em vez de excesso de exports.
7. **Segredos** por referências dinâmicas (Secrets Manager/SSM), nunca em Parameters.
8. **Tags** padronizadas nas stacks; **Budgets** e limpeza de ambientes efêmeros.
9. **Drift detection** periódica e **Config rules**; alerta de **falhas de stack** (EventBridge).
10. **Runbook de troubleshooting** e **teste de rollback** em ambientes não produtivos.

## Exemplo prático: estruturando acesso seguro para 10 squads

1. A equipe de plataforma publica **service roles** por squad, cada uma limitada a recursos do domínio do time.
2. Os pipelines dos squads usam **OIDC** e só têm `iam:PassRole` para a role do próprio squad.
3. Uma **SCP** proíbe criar usuários IAM de longa duração e desabilitar logs.
4. A condição `cloudformation:ResourceTypes` impede templates de criarem `AWS::IAM::User` ou policies administrativas.
5. **Hooks** exigem criptografia; **Config** acusa recursos sem tags de custo.
6. Alertas de `ROLLBACK`/`FAILED` vão para o canal do squad; a plataforma recebe um resumo semanal.
7. Um **painel de custo por tag `Squad`** acompanha o gasto.

## Erros comuns e armadilhas

- **Service role administrativa** para todas as stacks.
- **Pipeline com chaves de acesso de longa duração.**
- **Ler só o último evento** de erro, em vez do primeiro `FAILED`.
- **Nomes físicos fixos**, causando `AlreadyExists` em reimplantações.
- **Ciclos de dependência** com security groups mal modelados.
- **Stacks de teste esquecidas** gerando custo.
- **Não pedir aumento de quota** antes de um lançamento grande.
- **Sem alerta de falha de stack**, descobrindo problemas só quando o usuário reclama.

## 🧩 Quiz de Fixação

1. Qual a vantagem de usar uma service role em uma stack?
2. O que exige `CAPABILITY_NAMED_IAM`?
3. Qual evento examinar primeiro ao diagnosticar uma falha?
4. Como resolver `Circular dependency between resources`?
5. Que condição IAM limita os tipos de recurso criados por uma stack?
6. Como o CloudTrail ajuda a depurar uma falha de stack?

**Respostas:**
1) Separa quem aciona a stack de quem cria os recursos: o usuário precisa só de permissão de stack e PassRole, enquanto a role de serviço (menor privilégio) executa a criação.
2) Templates que criam recursos IAM com nomes personalizados; é um reconhecimento de que o template altera permissões.
3) O primeiro evento com status FAILED (o mais antigo), que costuma ser a causa raiz.
4) Quebrando a referência mútua, por exemplo definindo regras de security group como recursos separados em vez de referências cruzadas.
5) `cloudformation:ResourceTypes`.
6) Mostrando a chamada de API real feita pelo CloudFormation, com errorCode e errorMessage completos e a identidade usada.
