### 1.1.1.1. O que é AWS Compute Optimizer — right-sizing com machine learning sobre métricas do CloudWatch, recursos suportados, findings, ativação e quando usar em vez de Trusted Advisor e Cost Explorer

> [!warning] Aviso
> Lista de recursos suportados, janelas de análise, nomes de findings, preços de métricas aprimoradas e integrações abaixo são **de memória e mudam com frequência** (o serviço ganha recursos novos). **Confirme na documentação do AWS Compute Optimizer.** Comandos e JSONs são ilustrativos e **não foram executados**. Recomendações são **sugestões estatísticas**: valide sempre com testes antes de alterar produção.

## 1. O problema que o Compute Optimizer resolve

Na nuvem, **dimensionar errado custa caro** — de duas formas opostas:

| Erro | Sintoma | Custo |
|---|---|---|
| **Superdimensionamento** (over-provisioning) | Instâncias com 5% de CPU, 90% de memória livre, EBS de IOPS que ninguém usa, Lambda com 3 GB que roda com 300 MB | **Pagamento desnecessário** (muitas vezes 30–50% da conta de compute) |
| **Subdimensionamento** (under-provisioning) | CPU a 95%, throttling, latência alta, timeouts | **Perda de desempenho**, incidentes, clientes insatisfeitos |

Descobrir o tamanho certo manualmente exige **analisar métricas de semanas** para **cada recurso**, entender **famílias de instâncias**, **preços**, **compatibilidade** (x86 vs Graviton)… Em centenas de recursos, é inviável.

O **AWS Compute Optimizer** é o serviço que **analisa as métricas de utilização** (principalmente do **Amazon CloudWatch**) dos seus recursos e usa **machine learning** para **recomendar configurações ótimas** — apontando **o que está superdimensionado, subdimensionado ou otimizado**, a **economia estimada** e o **risco de desempenho** de cada opção.

> [!info] Em uma frase
> **Compute Optimizer = “right-sizing automático e baseado em dados”: olha como você realmente usa seus recursos e diz qual seria a configuração melhor e mais barata.”**

## 2. Como funciona (visão geral)

```
 Seus recursos (EC2, ASG, EBS, Lambda, ECS/Fargate, RDS…)
        │  métricas de utilização (CloudWatch; memória via CloudWatch Agent; opcional: métricas externas)
        ▼
 AWS COMPUTE OPTIMIZER  (análise estatística + ML sobre os últimos 14 dias+ de uso)
        │  compara o perfil de uso com as especificações e preços de todas as opções disponíveis
        ▼
 RECOMENDAÇÕES: finding (sub/super/otimizado) + até 3 opções + risco de desempenho + economia estimada + esforço de migração
        ▼
 Console / API / exportação S3 / Cost Optimization Hub / Trusted Advisor
```

1. Você **ativa (opt-in)** o serviço (conta ou organização).
2. O Compute Optimizer **coleta e analisa** as métricas **automaticamente**.
3. Para cada recurso, gera **findings** e **recomendações** (**atualizadas diariamente**, conforme dados novos).
4. Você **avalia, testa e implementa** (manual ou via automação).

## 3. Recursos suportados (de memória — confirmar a lista atual)

| Recurso | O que é otimizado |
|---|---|
| **Instâncias EC2** | **Tipo/tamanho** da instância (inclui **Graviton/ARM**), estimativas de **utilização projetada** |
| **EC2 Auto Scaling groups** | Tipo de instância **dos grupos** (grupos com tipo único de instância) |
| **Volumes EBS** | **Tipo de volume** (ex.: **gp2 → gp3**), **tamanho**, **IOPS** e **throughput** |
| **Funções AWS Lambda** | **Memória** configurada (que também define a CPU) |
| **Serviços Amazon ECS no AWS Fargate** | **CPU e memória** da task |
| **Licenças de software comercial** (ex.: **SQL Server** em EC2) | **Edição/licenciamento** adequados ao uso |
| **Amazon RDS** (instâncias e **armazenamento**) / Aurora | **Classe da instância** e **armazenamento** (confirmar engines suportadas) |
| **Recursos ociosos (idle)** | Identificação de recursos **sem uso** (candidatos a **desligar/excluir**) |
| **Contas de orquestração** | **Organizations**: visão **multi-conta** |

> Os recursos suportados aumentam com o tempo; cada tipo tem **requisitos mínimos de dados** (por exemplo, **horas de métricas**, **invocações mínimas** no Lambda).

## 4. Conceitos fundamentais

| Termo | Significado |
|---|---|
| **Opt-in** | **Ativação** do serviço (por **conta/região** ou para toda a **organização**) |
| **Finding (classificação)** | **Estado** do recurso: sub/super/otimizado (varia por tipo) |
| **Recommendation options** | **Até 3 configurações alternativas** (ranqueadas) |
| **Performance risk** | **Risco** (escala **0–5**, de “muito baixo” a “muito alto”) de a opção **não atender** à carga |
| **Projected utilization** | **Utilização projetada** (CPU/memória) **se** você trocasse para a opção |
| **Savings opportunity** | **Economia estimada** (R$/US$ e %) |
| **Migration effort** | Esforço para migrar (**muito baixo, baixo, médio, alto**) — ex.: mudar de x86 para **ARM** exige **testes** |
| **Lookback period** | Janela de dados analisada (padrão **14 dias**; até **32/93 dias** com **métricas aprimoradas**) |
| **Recommendation preferences** | **Ajustes** (headroom de CPU, famílias preferidas, janela, estimativa de economia) |
| **Enhanced infrastructure metrics** | **Métricas aprimoradas** (histórico de **até ~3 meses**; **recurso pago**) |
| **External metrics** | **Métricas de ferramentas externas** (Datadog, Dynatrace, New Relic, Instana) para melhorar as recomendações |
| **Inferred workload types** | Tipos de carga **detectados** (ex.: Redis, PostgreSQL, Kafka, Nginx) que influenciam a recomendação |
| **Idle** | Recurso **sem utilização relevante** |

## 5. Os “findings” (resultados da análise)

### 5.1 EC2 e Auto Scaling (de memória — confirmar)

| Finding | Significado | Ação típica |
|---|---|---|
| **Under-provisioned** (subdimensionada) | **Falta de capacidade**: ao menos uma **especificação** (CPU, memória, rede, disco) **não atende** ao perfil | **Aumentar** (melhora desempenho; custo pode subir) |
| **Over-provisioned** (superdimensionada) | **Sobra** de capacidade; **economia** possível **sem perder desempenho** | **Reduzir** para um tipo **menor/mais barato** |
| **Optimized** (otimizada) | Configuração **adequada** ao uso | Manter (revisar periodicamente) |
| **None/Unavailable** | **Dados insuficientes** (recurso novo, sem métricas) | Aguardar |

### 5.2 Outros recursos

| Recurso | Findings (exemplos) |
|---|---|
| **EBS** | **Optimized / NotOptimized** (com recomendações de tipo, tamanho e IOPS/throughput) |
| **Lambda** | **Optimized / NotOptimized / Unavailable** (ex.: **memória** acima/abaixo do ideal; precisa de **invocações mínimas**) |
| **ECS no Fargate** | **Optimized / Under-provisioned / Over-provisioned** |
| **RDS** | **Optimized / Under / Over** (instância/armazenamento) |
| **Idle** | Lista de **recursos ociosos** com **economia por desativação** |

## 6. Como ler uma recomendação

Exemplo conceitual (EC2):

| Item | Valor |
|---|---|
| **Instância atual** | `m5.2xlarge` (8 vCPU, 32 GiB) — **Over-provisioned** |
| **Uso observado (14 dias)** | CPU máx. 22%, memória máx. 35% |
| **Opção 1** | `m6g.xlarge` (Graviton, 4 vCPU, 16 GiB) — **risco 1** (muito baixo), **economia ~48%**, **esforço: médio** (ARM) |
| **Opção 2** | `m6i.xlarge` (x86, 4 vCPU, 16 GiB) — risco 1, **economia ~29%**, **esforço: muito baixo** |
| **Opção 3** | `m5.xlarge` — risco 2, economia ~25%, esforço: muito baixo |
| **Utilização projetada** | CPU ~44%, memória ~70% na opção 1 |

Interpretação: a opção 2 é a **mais segura e simples**; a opção 1 oferece **mais economia**, mas exige **validar a compatibilidade ARM**.

```bash
# Recomendações de EC2 (ilustrativo)
aws compute-optimizer get-ec2-instance-recommendations --region us-east-1 \
  --query 'instanceRecommendations[].[instanceArn,finding,currentInstanceType,recommendationOptions[0].instanceType,recommendationOptions[0].performanceRisk]' --output table

# Resumo geral (contagem por finding)
aws compute-optimizer get-recommendation-summaries --region us-east-1
```

## 7. Ativação (opt-in)

| Aspecto | Detalhe |
|---|---|
| **Custo** | O serviço **em si é gratuito** (as recomendações **padrão**); **métricas aprimoradas** têm **cobrança** (por vCPU/hora do recurso, ordem de centavos; confirmar) |
| **Conta individual** | `update-enrollment-status --status Active` (por **região**/conta) |
| **Organização** | A **conta de gestão** ativa para **todas as contas** (e pode **delegar** administração; confirmar) |
| **Dados necessários** | **Métricas do CloudWatch** de pelo menos **30 horas** (EC2) para as primeiras recomendações; **mais tempo** melhora a qualidade |
| **Regiões** | **Regional**: as recomendações vêm **por região** (visão agregada no console) |
| **Permissões** | IAM com **`compute-optimizer:*`** e acesso de leitura ao **CloudWatch** (service-linked role `AWSServiceRoleForComputeOptimizer`) |

```bash
aws compute-optimizer update-enrollment-status --status Active --include-member-accounts   # na conta de gestão (ilustrativo)
aws compute-optimizer get-enrollment-status
```

## 8. Quando usar o Compute Optimizer (e quando usar outra ferramenta)

| Necessidade | Ferramenta |
|---|---|
| **Right-sizing** de EC2/ASG/EBS/Lambda/Fargate/RDS com **base em uso real** | **Compute Optimizer** |
| **Visão consolidada de oportunidades de custo** (rightsizing, Savings Plans, ociosos) | **Cost Optimization Hub** (que **consome** o Compute Optimizer) |
| **Recomendações de rightsizing no console de custos** | **Cost Explorer (rightsizing recommendations)** — escopo mais simples (**EC2**, baseado em CPU) |
| **Checklist de boas práticas** (custo, segurança, limites) | **Trusted Advisor** (inclui verificações de **baixa utilização**) |
| **Comprar compromissos** (Savings Plans/RIs) | **Cost Explorer/Savings Plans recommendations** |
| **Otimizar o código/performance de aplicação** | **CodeGuru Profiler**, **X-Ray**, **CloudWatch Application Signals** |
| **Dimensionar Lambda por teste de carga** (custo × tempo) | **AWS Lambda Power Tuning** (complementar) |
| **Escala automática** conforme a demanda | **Auto Scaling** (o Compute Optimizer **não escala**, só recomenda o **tamanho**) |
| **Avaliar migração para Graviton** | Compute Optimizer **sugere** opções ARM; valide com testes |

### 8.1 Compute Optimizer vs Trusted Advisor vs Cost Explorer

| Critério | **Compute Optimizer** | **Trusted Advisor** | **Cost Explorer (rightsizing)** |
|---|---|---|---|
| **Foco** | **Right-sizing profundo** (ML, múltiplas métricas) | **Boas práticas** gerais (custo, segurança, performance, limites, resiliência) | **Custos e uso**; rightsizing **simples** |
| **Recursos** | EC2, ASG, EBS, Lambda, ECS/Fargate, RDS, licenças, idle | Muitos tipos (verificações **por categoria**) | **EC2** |
| **Métricas** | **CPU, memória (com agente), rede, disco/IOPS**, projeção | Principalmente **CPU/rede** (regras simples) | CPU |
| **Opções** | **Até 3 alternativas** com **risco** e **economia** | “Baixa utilização” (alerta) | Recomendação de tamanho **menor/terminar** |
| **Planos de suporte** | **Gratuito** (todos) | **Completo** em Business/Enterprise (verificações básicas nos demais) | Gratuito |

Resumo para prova: “**recomendações de dimensionamento baseadas em métricas de utilização**” → **Compute Optimizer**.

## 9. Casos de uso típicos

1. **Reduzir custos** de EC2 com **tipo/tamanho** adequados (e **Graviton**).
2. **Migrar volumes gp2 → gp3** (mais barato e com IOPS/throughput configuráveis).
3. **Ajustar a memória do Lambda** (menos custo ou menos latência).
4. **Dimensionar tasks do Fargate** (CPU/memória realistas).
5. **Identificar recursos ociosos** (desligar).
6. **Preparar compra de Savings Plans**: **primeiro right-size**, **depois comprometer** (evita comprar compromisso para capacidade inflada).
7. **Governança FinOps**: revisão mensal de recomendações por equipe/conta.
8. **Projetos de migração**: ajustar o tamanho **após** lift-and-shift.

> [!tip] Ordem correta no FinOps
> **1) Eliminar ociosos → 2) Right-size → 3) Comprar Savings Plans/RIs → 4) Automatizar/otimizar continuamente.** Comprar compromisso antes do right-sizing **cristaliza o desperdício**.

## 10. Limitações e cuidados (visão geral)

| Limitação | Detalhe |
|---|---|
| **Memória** | **Não é coletada por padrão** em EC2: instale o **CloudWatch Agent** para métricas de memória (sem isso, a recomendação ignora memória e pode ser **perigosa** para cargas **memory-bound**) |
| **Janela curta** | **14 dias** padrão pode **perder sazonalidade** (fim de mês, picos mensais); use **métricas aprimoradas** (até **93 dias**) quando a carga é sazonal |
| **Picos raros** | Estatística baseada em **percentis**; eventos **raríssimos** podem não aparecer |
| **Contexto de negócio** | Não conhece **SLAs**, **janelas de manutenção**, **licenças**, **compliance** ou **dependências** |
| **Requisitos de aplicação** | ARM/arquitetura, **drivers**, **bibliotecas nativas**, **AMI** — o esforço de migração é **sua** responsabilidade |
| **Auto Scaling** | Recomendações de **tipo**; **não** ajustam **políticas** de escala |
| **Estimativa de economia** | Baseia-se em **preços públicos** (ajustável) — descontos **EDP/Savings Plans** alteram o resultado |
| **Recursos novos** | Sem dados suficientes → **sem recomendação** |

## 11. Erros comuns

- **Aplicar recomendações “às cegas”** em produção sem teste.
- **Ignorar métricas de memória** (sem CloudWatch Agent).
- **Janela de 14 dias** em cargas **sazonais**.
- **Comprar Savings Plans antes do right-sizing**.
- **Reduzir demais** (headroom insuficiente → incidentes em picos).
- **Esquecer ARM/compatibilidade** ao aceitar Graviton.
- **Tratar Optimized como definitivo** (a carga muda).
- **Não revisar periodicamente** (recomendações envelhecem).
- **Não considerar custos de transição** (janela de mudança, risco).
- **Ativar sem Organizations**: visão fragmentada por conta.

## 12. Troubleshooting inicial

| Sintoma | Causas prováveis | Ações |
|---|---|---|
| Sem recomendações para um recurso | Dados insuficientes; tipo/engine não suportado; sem métricas; opt-in recente | Aguardar (30+ h/14 dias); verificar suporte e CloudWatch |
| Finding “Unavailable” (Lambda) | Menos de **50 invocações** em 14 dias (de memória) | Mais uso/tempo |
| Recomendação sem considerar memória | Sem **CloudWatch Agent** | Instalar o agente e aguardar |
| Economia menor que o esperado | Estimativa em preços públicos; descontos aplicados | Ajustar a **preferência de estimativa** (após descontos) |
| Opção ARM inviável | Dependências x86 | Preferir opção x86 ou ajustar **famílias preferidas** |
| Conta não aparece | Não incluída na organização/opt-in | Ativar para a organização |

## 13. Resumo rápido

- **Compute Optimizer** = **right-sizing** com **ML** sobre **métricas** (CloudWatch; memória via **CloudWatch Agent**), **gratuito** (métricas aprimoradas pagas).
- **Recursos**: **EC2, Auto Scaling, EBS, Lambda, ECS/Fargate, RDS, licenças, idle**.
- **Findings**: **Under-provisioned / Over-provisioned / Optimized** (EC2/Fargate/RDS); **Optimized/NotOptimized** (EBS/Lambda).
- **Saída**: **até 3 opções** com **risco de performance**, **economia estimada**, **esforço de migração** e **utilização projetada**.
- **Ativação**: **opt-in** por conta/região ou **Organizations**; dados mínimos (**~30 h**); janela **14 dias** (até **93** com métricas aprimoradas).
- **Ordem FinOps**: **ociosos → right-size → Savings Plans**.
- **Cuidados**: **memória**, **sazonalidade**, **ARM**, **testes** e **revisão periódica**.

## 🧩 Quiz de Fixação

1. Que problema o Compute Optimizer resolve e como?
2. Quais os possíveis findings de uma instância EC2?
3. O que são performance risk e migration effort?
4. Por que instalar o CloudWatch Agent?
5. Por que fazer right-sizing antes de comprar Savings Plans?
6. Que limitação a janela de 14 dias impõe e como contorná-la?
7. Qual a diferença entre Compute Optimizer e Trusted Advisor?

**Respostas:**

1. Dimensionamento inadequado (sub ou superdimensionamento); ele analisa métricas de uso com ML e recomenda configurações melhores com economia e risco estimados.
2. Under-provisioned, Over-provisioned, Optimized (e sem dados suficientes quando faltam métricas).
3. Performance risk é a chance de a opção não atender à carga (0–5); migration effort é o esforço para migrar para a opção (muito baixo a alto).
4. Para coletar métricas de memória, que não vêm por padrão em EC2; sem elas a recomendação pode ignorar cargas limitadas por memória.
5. Para não comprometer capacidade superdimensionada por 1–3 anos, cristalizando o desperdício; primeiro reduz-se o tamanho e depois se compra o compromisso.
6. Pode perder sazonalidade e picos mensais; contorna-se com métricas aprimoradas (até 93 dias) e preferências de janela.
7. O Compute Optimizer faz right-sizing profundo com ML e múltiplas opções; o Trusted Advisor faz verificações de boas práticas de forma mais ampla e simples (incluindo baixa utilização).
