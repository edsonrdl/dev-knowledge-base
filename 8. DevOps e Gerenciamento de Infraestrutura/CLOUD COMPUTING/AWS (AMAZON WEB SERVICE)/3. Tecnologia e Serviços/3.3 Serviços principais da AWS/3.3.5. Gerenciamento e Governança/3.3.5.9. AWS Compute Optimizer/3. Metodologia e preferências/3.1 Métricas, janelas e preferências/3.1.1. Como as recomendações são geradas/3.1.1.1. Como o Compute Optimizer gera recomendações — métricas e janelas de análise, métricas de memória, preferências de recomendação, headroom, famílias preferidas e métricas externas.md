### 3.1.1.1. Como o Compute Optimizer gera recomendações — métricas e janelas de análise, métricas de memória, preferências de recomendação, headroom, famílias preferidas e métricas externas

> [!warning] Aviso
> Janelas de análise, percentis usados, valores de headroom, opções de preferência, preços de métricas aprimoradas e integrações de métricas externas abaixo são **de memória e mudam**. **Confirme na documentação (“Metrics analyzed”, “Recommendation preferences”).** Comandos e JSONs são ilustrativos e **não foram executados**. A explicação do “motor” é **conceitual**: a AWS não publica o algoritmo exato.

## 1. A ideia por trás das recomendações

O Compute Optimizer responde, para cada recurso: **“se eu trocasse a configuração atual por X, **como** a **mesma carga** se comportaria?”** Isso exige três coisas:

```
(1) Perfil de uso real  +  (2) Catálogo de alternativas  +  (3) Regras de segurança (folga, risco)
      métricas no tempo          tipos, preços, specs           headroom, percentis, preferências
                         └──────────────── projeção ──────────────┘
                                  → ranking de até 3 opções
```

### 1.1 Visão simplificada do pipeline

1. **Coleta** das métricas (CloudWatch + agente + externas) em **janelas** de tempo.
2. **Normalização** (por **vCPU, memória, rede, disco**) e remoção de ruído.
3. **Perfil estatístico**: **máximo**, **percentis**, **padrões** diários/semanais.
4. **Projeção**: **estimar a utilização** **na especificação de cada candidato** (ex.: a mesma carga em **4 vCPU** em vez de **8**).
5. **Filtragem**: descarta candidatos que **violariam limites** (CPU > limite de segurança, memória insuficiente, rede/EBS/IOPS acima do suportado).
6. **Pontuação**: **risco de performance** e **economia** (usando **preços**).
7. **Ranqueamento**: até **3 opções** com **utilização projetada**.

## 2. Métricas analisadas

### 2.1 EC2 e Auto Scaling

| Métrica | Fonte | Observação |
|---|---|---|
| **`CPUUtilization`** | CloudWatch (padrão) | Base da análise |
| **`NetworkIn/Out`**, `NetworkPacketsIn/Out` | CloudWatch | Rede |
| **`DiskReadOps/WriteOps`** (instance store) | CloudWatch | Disco local |
| **`EBSReadOps/WriteOps/Bytes`** | CloudWatch | I/O dos volumes |
| **Memória usada (%)** | **CloudWatch Agent** (`mem_used_percent`) ou **métricas externas** | **Não** é padrão |
| **Disco usado/tamanho do volume** | **CloudWatch Agent** | Para EBS/dados |
| **GPU** | Agente/NVIDIA (confirmar) | Instâncias aceleradas |
| **Créditos de CPU** (T-series) | CloudWatch | **Burst** |

### 2.2 EBS

| Métrica | Uso |
|---|---|
| **`VolumeReadOps/WriteOps`**, **`VolumeReadBytes/WriteBytes`** | IOPS e throughput |
| **`VolumeQueueLength`**, `VolumeTotalReadTime/WriteTime` | Saturação |
| **Tipo/tamanho/IOPS/throughput provisionados** | Comparação com uso |

### 2.3 Lambda, Fargate e RDS

| **RDS/Aurora** | `CPUUtilization`, `FreeableMemory`, `DatabaseConnections`, `ReadIOPS/WriteIOPS`, `ReadLatency`, **Performance Insights** (opcional) |

## 3. Janelas de análise (lookback)

| Janela | Característica |
|---|---|
| **14 dias** (padrão) | **Gratuita**; cobre **2 ciclos semanais**; **pode perder** picos mensais/sazonais |
| **32 dias** | Com **métricas aprimoradas** (pagas) — cobre **um ciclo mensal** |
| **93 dias** (~3 meses) | Com **métricas aprimoradas** — cobre **trimestres/sazonalidade** |

```
Carga com pico de fim de mês:
 14 dias (meio do mês): CPU máx. 25%  ──▶ "over-provisioned"  ✘ perigoso
 32/93 dias:            CPU máx. 85%  ──▶ "optimized"           ✔ correto
```

> [!tip] Escolha da janela
> **Cargas estáveis** (web simples, microsserviços) → **14 dias** bastam. **Cargas sazonais** (folha de pagamento, fechamento contábil, Black Friday, relatórios mensais) → **32/93 dias** (métricas aprimoradas) **ou** análise manual do período crítico.

## 4. Métricas aprimoradas (enhanced infrastructure metrics)

| Aspecto | Detalhe (de memória — confirmar) |
|---|---|
| **O que é** | Recurso **pago** que **estende o histórico** analisado (até **93 dias**) e melhora a precisão para **cargas sazonais** |
| **Ativação** | Por **conta/organização** e **por recurso** (ex.: EC2, ASG, RDS) — **preferência de recomendação** |
| **Cobrança** | **Por recurso por hora** (valor pequeno por **vCPU/hora** ou por recurso; confirmar), **somente** para recursos com a preferência **ativa** |
| **Retorno** | Evita **erros caros** (subdimensionar por falta de visão sazonal) |
| **Estratégia** | Ativar **só** para recursos **grandes/críticos/sazonais** |

```bash
aws compute-optimizer put-recommendation-preferences --resource-type Ec2Instance \
  --scope name=Organization,value=o-exemplo12345 --enhanced-infrastructure-metrics Active
aws compute-optimizer get-recommendation-preferences --resource-type Ec2Instance
```

## 5. Métricas de memória

### 5.1 Por que importam

CPU **e** memória definem se uma instância **serve**. Cargas **memory-bound** (Java, bancos em instância, caches) podem ter **CPU baixa** e **memória alta**. Sem a métrica de memória, o Compute Optimizer **vê CPU baixa** e pode sugerir **instância com menos memória** → **OOM**.

### 5.2 Como habilitar (CloudWatch Agent)

```json
{
  "metrics": {
    "append_dimensions": { "InstanceId": "${aws:InstanceId}" },
    "metrics_collected": {
      "mem": { "measurement": ["mem_used_percent"], "metrics_collection_interval": 60 },
      "disk": { "measurement": ["used_percent"], "resources": ["*"] }
    }
  }
}
```

| Prática | Detalhe |
|---|---|
| **Instalar** | Via **SSM Distributor/State Manager** em toda a frota |
| **Configurar** | **`mem_used_percent`** (namespace `CWAgent`) |
| **IAM** | **CloudWatchAgentServerPolicy** no instance profile |
| **Custo** | Métricas **customizadas** do CloudWatch (por métrica/mês) |
| **Tempo** | Após ativar, aguardar **dias** para dados suficientes |
| **Alternativa** | **Métricas externas** (Datadog/Dynatrace/New Relic/Instana) |

### 5.3 Métricas externas

O Compute Optimizer pode **ingerir métricas de memória e CPU** de **ferramentas de observabilidade** (**Datadog, Dynatrace, New Relic, Instana**; confirmar a lista) para melhorar as recomendações **sem** o CloudWatch Agent.

```bash
aws compute-optimizer put-recommendation-preferences --resource-type Ec2Instance \
  --scope name=Organization,value=o-exemplo12345 --external-metrics-preference source=Datadog
```

## 6. Preferências de recomendação

As **preferências** ajustam **como** as recomendações são geradas — por **organização, conta ou recurso**.

| Preferência | Efeito |
|---|---|
| **Headroom de CPU** | **Folga** de CPU que a recomendação mantém: **10%**, **20%** ou **30%** (**padrão 20%**) — maior headroom = **recomendações mais conservadoras** (menos economia, mais segurança) |
| **Headroom de memória** (se aplicável) | Idem para memória |
| **Janela de análise (lookback)** | **14 / 32 / 93 dias** (com métricas aprimoradas) |
| **Métricas aprimoradas** | Ativa/desativa |
| **Famílias de instância preferidas** (preferred resources) | **Restringir** as opções a famílias específicas (ex.: **apenas `m6i`, `r6i`**, ou excluir **burstable**) |
| **Arquitetura (CPU vendor)** | Incluir/excluir **Graviton (ARM)** — `cpuVendorArchitectures=AWS_ARM64` ou `CURRENT` |
| **Modo de estimativa de economia** | **Preços públicos on-demand** (padrão) ou **após descontos** (**Savings Plans/RIs**/EDP) — **mais realista** |
| **Métricas externas** | Fonte de métricas de terceiros |
| **Utilização de memória/inferência de carga** | Ativa/desativa a **inferência de workload** |
| **Escopo** | **Organização**, **conta** ou **recurso** (**mais específico vence**) |

### 6.1 Headroom (folga) — exemplo

```
Uso máximo observado = 60% de CPU na instância atual (8 vCPU)  →  4,8 vCPU "efetivos"
Headroom 20%: a recomendação garante ≥ 20% livre no pico ⇒ alvo de uso ≤ 80% na nova instância
   Opção 6 vCPU → pico projetado 80% (no limite); Opção 4 vCPU → pico projetado 120% ✘ descartada
Headroom 30%: alvo ≤ 70% ⇒ Opção 6 vCPU → 80% ✘; precisa de 8 vCPU (sem economia)
```

| Escolha | Quando |
|---|---|
| **10%** | **Dev/Test**, cargas **previsíveis**, com **Auto Scaling** absorvendo picos |
| **20%** (padrão) | **Equilíbrio** geral |
| **30%** | **Produção crítica**, cargas **imprevisíveis**, **SLA** rigoroso |

### 6.2 Famílias preferidas e arquiteturas

| Cenário | Preferência |
|---|---|
| **Padronização** de frota (suporte, AMIs, licenças) | Listar **famílias aprovadas** |
| **Reservas/Savings Plans** vinculados a famílias | Restringir às **famílias cobertas** |
| **Sem ARM ainda** | Manter **x86** (`CURRENT`) |
| **Adoção de Graviton** | Incluir **ARM** para ver economia |
| **Evitar burstable (T)** em produção | Excluir `t3/t4g` |
| **Regras corporativas** (geração mínima) | Limitar a **gerações atuais** |

```bash
aws compute-optimizer put-recommendation-preferences --resource-type Ec2Instance \
  --scope name=Account,value=123456789012 \
  --preferred-resources name=EC2InstanceTypes,includeList=m6i.*,m7i.*,r6i.* \
  --utilization-preferences metricName=CpuUtilization,metricParameters='{threshold=P90,headroom=PERCENT_20}' \
  --look-back-period DAYS_32 --enhanced-infrastructure-metrics Active
```

(Parâmetros ilustrativos — confirme os nomes na CLI atual.)

## 7. Estatísticas e percentis

| Conceito | Detalhe (de memória — confirmar) |
|---|---|
| **Máximo (peak)** | Base conservadora (pior caso observado) |
| **Percentis** (ex.: P90, P99.5) | Ignoram **picos raríssimos** (outliers) |
| **Limiar configurável** | Em preferências (ex.: usar **P90** vs **máximo**) |
| **Padrão** | Mais próximo de **picos** (conservador) para evitar subdimensionamento |

Consequência: **escolher percentis menores** ⇒ **mais economia**, **mais risco** em picos; **máximo** ⇒ **mais seguro**. Combine com **Auto Scaling** para absorver picos sem manter capacidade permanente.

## 8. O que o motor “não sabe”

| Não considera | Consequência |
|---|---|
| **SLAs/SLOs** | Pode sugerir configuração **no limite** |
| **Eventos futuros** (campanhas, lançamentos) | Baseia-se no **passado** |
| **Dependências** entre serviços | Mudar um pode **deslocar gargalo** |
| **Compatibilidade de software** (ARM, drivers, licenças) | **Esforço de migração** é estimativa genérica |
| **Compromissos financeiros** (RIs/SPs) | Só reflete se **estimativa após descontos** estiver ativa |
| **Custos de transição** (janela, risco, tempo da equipe) | Fora do cálculo |
| **Cargas intermitentes** | Podem ser mal classificadas |
| **Instance store/estado local** | Não avalia perda de dados na troca |

## 9. Melhorando a qualidade das recomendações

| Ação | Efeito |
|---|---|
| **CloudWatch Agent (memória)** em toda a frota | Evita **recomendações perigosas** |
| **Métricas aprimoradas** para cargas sazonais | Cobre ciclos longos |
| **Preferências por ambiente** (headroom 30% em prod; 10% em dev) | Alinha o risco |
| **Famílias preferidas** | Respeita padrões |
| **Estimativa após descontos** | Economia realista |
| **Tags** de dono/ambiente | Priorização e filtros |
| **Métricas externas** | Melhor cobertura quando já há APM |
| **Revisão periódica** | Acompanha a evolução da carga |
| **Teste de carga** nas opções | Valida o que a estatística sugere |

## 10. Exemplo de configuração por ambiente

```
Organização (padrão):          headroom 20% • janela 14d • estimativa "após descontos" • x86 + ARM
OU Produção-Crítica:           headroom 30% • janela 93d (métricas aprimoradas) • famílias m6i/r6i • sem burstable
OU Desenvolvimento:            headroom 10% • janela 14d • inclui t3/t4g • inclui ARM
Contas de folha/fechamento:    janela 93d • métricas aprimoradas (sazonalidade)
```

## 11. Erros comuns

- **Janela de 14 dias** em carga **sazonal**.
- **Sem CloudWatch Agent**.
- **Headroom padrão** em produção crítica (risco) ou **muito alto** em dev (desperdício).
- **Não restringir famílias** e receber recomendações **fora do padrão** da empresa.
- **Estimativa em preço público** com **grandes descontos** (**exagera** a economia).
- **Métricas aprimoradas em todos** os recursos (custo desnecessário).
- **Interpretar projeção como garantia**.
- **Não revisar preferências** após mudanças de arquitetura.
- **Ignorar outliers** (picos reais legítimos) ao usar percentis baixos.

## 12. Troubleshooting

| Sintoma | Causa provável | Ação |
|---|---|---|
| Recomendação agressiva demais | Headroom baixo; percentil baixo; janela curta | Aumentar headroom/janela; usar máximo |
| Recomendação conservadora demais | Headroom alto; picos antigos | Ajustar; revisar a janela |
| Sem dados de memória | Agente ausente/permissões | Instalar/configurar; `CloudWatchAgentServerPolicy` |
| Métricas aprimoradas “ativas”, mas janela não muda | Propagação/escopo/recurso | Verificar o escopo e esperar a atualização |
| Opção ARM aparece e não é desejada | Preferência de arquitetura | Definir `CURRENT` (x86) |
| Famílias fora do padrão | Sem preferred resources | Definir lista de inclusão |
| Economia diverge da fatura | Estimativa em preços públicos | Mudar para “após descontos” |
| Preferência não surtiu efeito | Escopo mais específico sobrescreve | Conferir hierarquia org → conta → recurso |

## 13. Resumo rápido

- **Pipeline**: coleta de métricas → perfil estatístico → **projeção em cada candidato** → filtro por **headroom/limites** → **risco + economia** → **até 3 opções**.
- **Métricas**: CPU, rede, EBS/disco (padrão); **memória** via **CloudWatch Agent** ou **métricas externas**; Lambda (duração/memória), RDS (Performance Insights).
- **Janelas**: **14 dias** (gratuita) vs **32/93 dias** (**métricas aprimoradas pagas**) para **sazonalidade**.
- **Preferências**: **headroom (10/20/30%)**, **lookback**, **famílias**, **arquitetura (ARM)**, **estimativa de economia**, **métricas externas**; **escopo** org/conta/recurso.
- **Limites do motor**: não conhece **SLA**, **futuro**, **dependências**, **licenças** e **custos de transição**.
- **Boas práticas**: **agente de memória**, **preferências por ambiente**, **estimativa após descontos**, **teste de carga** e **revisão periódica**.

## 🧩 Quiz de Fixação

1. Quais são as etapas conceituais do cálculo de uma recomendação?
2. Por que a janela de 14 dias pode ser perigosa em cargas sazonais?
3. O que é headroom e como escolhê-lo?
4. Como obter métricas de memória?
5. Para que servem as famílias preferidas?
6. Por que ativar a estimativa de economia “após descontos”?
7. O que o motor não considera?

**Respostas:**

1. Coleta de métricas, perfil estatístico, projeção da mesma carga em cada candidato, filtragem por limites e headroom, pontuação de risco e economia e ranqueamento de até 3 opções.
2. Porque pode não capturar picos mensais ou sazonais, levando a classificar como superdimensionado um recurso que precisa dessa capacidade; mitiga-se com 32/93 dias (métricas aprimoradas).
3. A folga de CPU mantida no pico projetado (10, 20 ou 30%); maior em produção crítica, menor em dev/test ou com Auto Scaling.
4. Instalando o CloudWatch Agent (`mem_used_percent`) ou ingerindo métricas externas (Datadog, Dynatrace, New Relic, Instana).
5. Restringir as opções a famílias aprovadas, cobertas por reservas/Savings Plans ou padronizadas pela empresa (e excluir burstable ou ARM, se necessário).
6. Porque considera Savings Plans, RIs e descontos contratados, dando uma economia mais realista que o preço público on-demand.
7. SLAs/SLOs, eventos futuros, dependências entre serviços, compatibilidade de software e licenças, compromissos financeiros e custos de transição.
