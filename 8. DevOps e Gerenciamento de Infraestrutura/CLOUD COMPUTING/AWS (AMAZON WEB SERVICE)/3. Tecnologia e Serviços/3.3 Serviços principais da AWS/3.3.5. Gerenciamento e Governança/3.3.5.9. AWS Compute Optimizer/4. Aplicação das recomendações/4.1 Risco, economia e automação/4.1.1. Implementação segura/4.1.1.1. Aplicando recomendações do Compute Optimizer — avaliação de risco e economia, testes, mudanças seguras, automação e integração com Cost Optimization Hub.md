### 4.1.1.1. Aplicando recomendações do Compute Optimizer — avaliação de risco e economia, testes, mudanças seguras, automação e integração com Cost Optimization Hub

> [!warning] Aviso
> Valores de economia, riscos, comandos e comportamento de integrações (Cost Optimization Hub, Trusted Advisor, automações) abaixo são **de memória e mudam**. **Confirme na documentação.** Comandos, scripts e fluxos são ilustrativos e **não foram executados**. **Nunca automatize mudanças de tamanho em produção sem testes, janelas, monitoramento e rollback**: recomendações são estatísticas, não garantias.

## 1. Da recomendação à economia real

Receber uma recomendação **não economiza nada**: a economia só existe quando a mudança é **aplicada com segurança** e **mantida**. Muitos programas falham porque ficam em **planilhas de recomendações** que ninguém executa — ou, no extremo oposto, aplicam tudo **às cegas** e geram **incidentes**.

```
Recomendação ─▶ Triagem (valor/risco/esforço) ─▶ Validação (dono, dependências) ─▶ Teste ─▶ Mudança controlada
      ─▶ Monitoramento pós-mudança ─▶ Medição da economia ─▶ Rollback (se preciso) ─▶ Reavaliação periódica
```

## 2. Triagem: priorizar o que vale a pena

### 2.1 Critérios

| Critério | Como avaliar |
|---|---|
| **Economia absoluta** | Valor mensal (um recurso grande > cem pequenos) |
| **Performance risk** | **0–2** (aplicar com testes leves); **3–5** (testes pesados/evitar) |
| **Migration effort** | **Muito baixo/baixo** primeiro |
| **Criticidade/ambiente** | **Dev/Test → Homolog → Prod** |
| **Dependências** | **RIs/Savings Plans**, licenças, DR, ASG, **compliance** |
| **Janela/Downtime** | Exige **parar/reiniciar**? |
| **Dono identificável** | Tags de **owner/team/app** |
| **Idade da recomendação** | Recomendações **antigas** (> 30 dias) merecem **reavaliação** |

### 2.2 Matriz de ação

| | **Baixo esforço** | **Alto esforço** |
|---|---|---|
| **Baixo risco** | ✅ **Quick wins**: gp2→gp3, tamanho dentro da mesma família, Lambda memória (com power tuning) | 🗓️ **Projetos planejados**: Graviton, mudança de família/licenças |
| **Alto risco** | 🔍 **Revisar/testar** com carga | ⛔ **Evitar** ou reavaliar com mais dados |

### 2.3 Ordem sugerida (FinOps)

1. **Eliminar ociosos** (com validação).
2. **Quick wins de baixo risco** (EBS, Lambda, dev/test).
3. **Right-size de produção** com testes e janelas.
4. **Graviton/modernização** (projetos).
5. **Comprar Savings Plans/RIs** **depois** (sobre a base já otimizada).
6. **Automatizar a revisão contínua.**

## 3. Validação antes de mudar

### 3.1 Checklist de validação (por recurso)

| Pergunta | Fonte |
|---|---|
| **Quem é o dono?** | Tags/CMDB |
| **É DR/standby/sazonal?** | Dono, documentação |
| **A janela de análise cobre o ciclo da carga?** | 14 vs 93 dias; calendário de negócio |
| **Há métricas de memória?** | CloudWatch Agent |
| **Há RIs/SPs atrelados** (família/região)? | Cost Explorer/Billing |
| **Licenças dependem de vCPU/edição?** | Licenciamento |
| **Há instance store/estado local?** | Arquitetura |
| **É parte de ASG/ECS/EKS?** | Mudar via **template/IaC** |
| **Compatibilidade (ARM, drivers, AMI)?** | Testes |
| **SLAs/SLOs e picos futuros** (campanhas)? | Negócio |
| **Dependências** (outros serviços saturam?) | Observabilidade |

### 3.2 Tags para governar

| Tag | Uso |
|---|---|
| `owner`/`team` | Quem decide |
| `environment` | prod/hml/dev |
| `rightsizing=skip` (ou `compute-optimizer-exempt`) | **Exceções** (ex.: DR/standby) |
| `dr=true`/`standby=true` | Evitar desligar |
| `cost-center`/`app` | Alocação de economia |

## 4. Testes

### 4.1 Níveis

| Nível | Quando |
|---|---|
| **Revisão de métricas** (projeção do Compute Optimizer) | Sempre |
| **Teste em staging** (mesmo tipo candidato) | Mudança de família/ARM/memória |
| **Teste de carga** (k6/Locust/JMeter) | Produção crítica |
| **Canary** (uma parte da frota em prod) | ASG/ECS/Lambda |
| **Shadow/blue-green** | Mudanças de maior risco |

### 4.2 Critérios de sucesso (definir **antes**)

| Métrica | Limite exemplo |
|---|---|
| **Latência p95/p99** | ≤ baseline + X% |
| **Taxa de erro** | ≤ baseline |
| **CPU de pico** | ≤ 70–80% |
| **Memória de pico** | ≤ 80% |
| **Throttling/ filas** | Sem aumento |
| **Custo** | Economia ≥ meta |

### 4.3 Graviton (ARM): checklist de migração

1. **Inventário** de dependências: **imagens, binários nativos, bibliotecas** (Java/Node/Python geralmente ok; **binários x86** não).
2. **Build multi-arch** (containers) e **AMIs ARM**.
3. **Testes funcionais e de desempenho** (**benchmarks** reais).
4. **Canary** em produção (ASG/ECS) com **fallback** para x86.
5. **Observabilidade** comparando **latência/custo**.
6. **Migrar por camadas** (stateless primeiro).
7. **Atualizar compromissos** (Compute Savings Plans cobrem Graviton).

## 5. Mudanças seguras por tipo de recurso

### 5.1 EC2 (instância única)

```
1. Snapshot/AMI (backup)  →  2. Janela e comunicação  →  3. Parar instância  →  4. Mudar tipo (modify-instance-attribute)
→  5. Iniciar  →  6. Validar (health checks, métricas, logs)  →  7. Monitorar 24–72 h  →  8. Rollback = voltar ao tipo anterior
```

```bash
aws ec2 stop-instances --instance-ids i-0abc123
aws ec2 wait instance-stopped --instance-ids i-0abc123
aws ec2 modify-instance-attribute --instance-id i-0abc123 --instance-type "{\"Value\": \"m6i.xlarge\"}"
aws ec2 start-instances --instance-ids i-0abc123
```

Cuidados: **IP público** muda (sem EIP); **instance store** perde dados; **drivers**/AMI compatíveis; **placement groups**/**capacity**; **licenças**.

### 5.2 Auto Scaling groups

1. Criar **nova versão do launch template** com o tipo recomendado.
2. **Instance refresh** gradual (`MinHealthyPercentage` 90%, **warmup** adequado) ou **troca por ondas**.
3. **Monitorar** métricas e **política de escala** (CPU alvo pode mudar com instâncias menores).
4. **Rollback**: voltar à versão anterior do template e **refresh**.

### 5.3 EBS

```bash
aws ec2 modify-volume --volume-id vol-0abc123 --volume-type gp3 --iops 3000 --throughput 250
aws ec2 describe-volumes-modifications --volume-ids vol-0abc123
```

- **Online**, mas **uma modificação a cada 6 horas** por volume (limite) e **fase de “optimizing”** (desempenho levemente afetado).
- **Reduzir tamanho**: **novo volume + cópia** (planejar janela).

### 5.4 Lambda

1. **Validar com Power Tuning** (ou testes de carga).
2. **Alias + deployment** gradual (CodeDeploy canary/linear) **se** a mudança for com **versão**; memória é parâmetro de **versão**.
3. **Monitorar** duração, erros, throttles, custo.
4. **Rollback**: reapontar alias/versão anterior.

### 5.5 ECS/Fargate

- Nova **revisão da task definition** (CPU/memória) + **deploy rolling/blue-green** com **circuit breaker** e **rollback automático**.
- Validar **limites por container** (soft/hard) e **picos de memória**.

### 5.6 RDS/Aurora

- **Janela de manutenção**; **Multi-AZ** (failover rápido); **snapshot manual** antes.
- Mudar **classe**: reinício/failover (~1–3 min em Multi-AZ).
- **Monitorar** CPU, conexões, latência, **replica lag**.
- Storage: **gp2→gp3** e ajuste de IOPS (verificar limites e janelas de otimização).

## 6. Automação e integração

### 6.1 Cost Optimization Hub

| Aspecto | Detalhe (de memória — confirmar) |
|---|---|
| **O que é** | Console/API **central** que **consolida** oportunidades de economia de **vários serviços** (Compute Optimizer, Savings Plans, RIs, **recursos ociosos**…) |
| **Valor** | **Ranking por economia**, **deduplicação** (evita **dupla contagem** de sobreposições), **estimativa após descontos**, **filtros** por conta/região/tag |
| **Uso** | **Fila de trabalho FinOps**: priorizar, atribuir e acompanhar |
| **Ativação** | **Opt-in** (conta de gestão/organização) |
| **Fonte** | Usa **Compute Optimizer** (precisa estar ativo) |

### 6.2 Outras integrações

| Integração | Uso |
|---|---|
| **AWS Trusted Advisor** | Mostra verificações de **baixa utilização** e (em planos elegíveis) **recomendações do Compute Optimizer** |
| **Cost Explorer** | **Rightsizing recommendations** (EC2) e análise de impacto |
| **AWS Organizations** | **Visão agregada** de todas as contas |
| **AWS Config/Systems Manager** | **Inventário** e execução de mudanças em escala |
| **EventBridge** | (quando disponível) Eventos para automação |
| **QuickSight/Athena** | Relatórios sobre **exportações S3** |
| **Ticketing (Jira/ServiceNow)** | Criar **tarefas** a partir de recomendações (via Lambda/API) |

### 6.3 Fluxo automatizado “seguro” (exemplo)

```
EventBridge Scheduler (semanal)
   └▶ Lambda: get-*-recommendations (org) → filtra: risco ≤ 2, esforço ≤ baixo, ambiente != prod, sem tag exempt
        └▶ Cria ticket (Jira) com contexto: recurso, dono, economia, opções, link da projeção
              └▶ Dono aprova ──▶ Pipeline (SSM Automation/CodePipeline/Terraform PR) aplica em Dev/Test
                                     └▶ Monitora X horas ──▶ Se OK, abre PR para Prod (com aprovação humana)
```

| Princípio | Detalhe |
|---|---|
| **Automatizar a descoberta e o ticket**, **não a mudança em prod** | Mudanças em prod com **aprovação** |
| **Auto-aplicar só quick wins seguros** | gp2→gp3, tamanho em **dev/test** |
| **IaC como fonte da verdade** | **Alterar o Terraform/CloudFormation** (PR), não o recurso manualmente (evita **drift**) |
| **Guardrails** | Limites (ex.: no máximo **N mudanças/dia**), **janelas**, **exceções por tag** |
| **Observabilidade** | Alarmes de **latência/erros** pós-mudança; **rollback automático** quando possível |
| **Auditoria** | CloudTrail e registro de **quem aprovou** |

### 6.4 Exemplo: Lambda que lista recomendações EC2 de baixo risco (ilustrativo)

```python
import boto3
co = boto3.client("compute-optimizer")

def handler(event, ctx):
    resp = co.get_ec2_instance_recommendations(filters=[{"name": "Finding", "values": ["Overprovisioned"]}])
    candidatos = []
    for r in resp["instanceRecommendations"]:
        opt = r["recommendationOptions"][0]
        if opt.get("performanceRisk", 5) <= 2 and r.get("recommendationOptions")[0].get("migrationEffort") in ("VeryLow", "Low"):
            tags = {t["key"]: t["value"] for t in r.get("tags", [])}
            if tags.get("rightsizing") != "skip":
                candidatos.append({"arn": r["instanceArn"], "atual": r["currentInstanceType"], "novo": opt["instanceType"]})
    # ... publicar em SNS/criar ticket (não aplicar em produção automaticamente)
    return candidatos
```

(Estrutura da resposta e nomes de campos ilustrativos — confirme na API.)

## 7. Medir a economia (realizada vs estimada)

| Passo | Detalhe |
|---|---|
| **Baseline** | Custo **antes** (por recurso/app/tag) |
| **Registrar** | Data da mudança, **de → para**, economia estimada |
| **Medir depois** | **Cost Explorer/CUR** por **tag/recurso** (≥ 1 ciclo de faturamento) |
| **Ajustar** | Considerar **RIs/SPs** (a economia pode ser **diferente** da estimativa de preço público) |
| **Reportar** | **Economia realizada** vs **estimada**, **por equipe**; **incidentes** causados |
| **Cultura** | **Showback/chargeback** incentiva os donos a agir |

### 7.1 KPIs do programa

| KPI | Meta |
|---|---|
| **% de recursos “Optimized”** | Tendência crescente |
| **Economia realizada/mês** | Acima da meta |
| **Idade média das recomendações abertas** | < 30 dias |
| **Taxa de recomendações aceitas** | > 50% (nas de baixo risco) |
| **Incidentes por right-sizing** | ~0 |
| **Cobertura de memória** (CW Agent) | ~100% da frota |
| **Sobreposição com SPs** | Compromissos alinhados à base otimizada |

## 8. Governança do processo

| Elemento | Prática |
|---|---|
| **Cadência** | Revisão **mensal** (FinOps) com donos de contas/apps |
| **Responsabilidade** | **Dono do recurso decide**; **FinOps facilita**; **Plataforma automatiza** |
| **Política de exceções** | Tag + **justificativa** + **validade** |
| **Gestão de mudanças** | Aprovações e janelas conforme criticidade |
| **Compartilhar sucessos** | Casos de economia sem incidentes |
| **Treinamento** | Como ler recomendações, testar e reverter |
| **Revisão de preferências** | Trimestral (headroom, famílias, janela) |

## 9. Erros comuns

- **Relatórios sem donos** (ninguém executa).
- **Auto-aplicar** em produção sem teste/rollback.
- **Ignorar o feedback**: recomendações **aceitas e revertidas** por incidente sem lição aprendida.
- **Alterar manualmente** recursos geridos por **IaC** (drift e reversão).
- **Mudar tipo do ASG** sem revisar **política de escala**.
- **Reduzir demais** e **perder o headroom** de picos.
- **Medir economia só pela estimativa** (sem validar na fatura).
- **Comprar Savings Plans** **antes** de aplicar as recomendações.
- **Não registrar exceções** (DR/standby reaparecem como “ociosos” sempre).
- **Esquecer de monitorar** após a mudança (problema descoberto por clientes).

## 10. Troubleshooting

| Sintoma | Causa provável | Ação |
|---|---|---|
| Latência subiu após a mudança | Subdimensionado em picos; memória/IO | Rollback; aumentar headroom; reavaliar |
| Instância não inicia no novo tipo | Compatibilidade (ENA/NVMe/ARM/AMI) | Voltar ao tipo anterior; ajustar AMI/drivers |
| ASG não troca o tipo | Template não atualizado/refresh | Nova versão do template + refresh |
| Economia não aparece na fatura | RIs/SPs absorveram; estimativa em preço público; ocorrência de outras mudanças | Medir por tag/CUR; usar estimativa após descontos |
| Recomendação reaparece após aplicar | Carga mudou; opção diferente | Revisar a nova recomendação |
| Volume EBS “optimizing” longo | Modificação em andamento | Aguardar; evitar nova mudança por 6 h |
| Terraform reverte a mudança | Drift (mudança manual) | Aplicar via IaC |
| Cost Optimization Hub sem dados | Não habilitado/Compute Optimizer inativo | Ativar ambos |

## 11. Resumo rápido

- **Aplicar bem** vale mais que **ter muitas recomendações**: **triagem** (economia × **risco** × **esforço**), **validação** (dono, DR, sazonalidade, RIs/SPs, licenças, memória), **teste**, **mudança controlada**, **monitoramento**, **rollback**, **medição**.
- **Quick wins**: **gp2→gp3**, Lambda (com **Power Tuning**), tamanhos em **dev/test**; **Graviton** como **projeto** com testes e **canary**.
- **Mudanças por recurso**: EC2 (**snapshot → parar → mudar → iniciar**), ASG (**launch template + instance refresh**), EBS (**modify-volume**, 6 h entre mudanças), Lambda (**alias/canary**), Fargate (**task definition + rolling**), RDS (**janela, Multi-AZ**).
- **Automação**: descobrir e abrir **tickets** automaticamente; **aprovar humanamente** produção; **IaC** como fonte; **guardrails**.
- **Cost Optimization Hub** consolida oportunidades (**deduplicadas**, após descontos); **Trusted Advisor/Cost Explorer** complementam.
- **Medir** economia **realizada** (CUR/tags), **KPIs** e **governança** (cadência, exceções, responsabilidades).

## 🧩 Quiz de Fixação

1. Que critérios usar para priorizar recomendações?
2. Por que alterar via IaC em vez de manualmente?
3. Como aplicar com segurança uma recomendação em um Auto Scaling group?
4. Que cuidados tem a migração para Graviton?
5. O que é o Cost Optimization Hub e qual seu valor?
6. Como medir a economia realizada?
7. Por que não auto-aplicar mudanças em produção?

**Respostas:**

1. Economia absoluta, performance risk, migration effort, criticidade/ambiente, dependências (RIs/SPs, licenças, DR), janela necessária, dono identificável e idade da recomendação.
2. Para evitar drift: mudanças manuais em recursos geridos por IaC são revertidas na próxima aplicação e perdem rastreabilidade.
3. Criando uma nova versão do launch template com o tipo recomendado e fazendo instance refresh gradual, monitorando métricas e a política de escala, com rollback voltando à versão anterior.
4. Inventariar dependências x86, construir imagens/AMIs multi-arch ou ARM, testar função e desempenho, fazer canary com fallback e migrar por camadas, atualizando compromissos (Compute Savings Plans cobrem Graviton).
5. É um console/API que consolida oportunidades de economia de vários serviços, deduplica sobreposições, estima após descontos e permite priorizar e acompanhar.
6. Registrando baseline e mudança, e comparando custos por tag/recurso no Cost Explorer ou CUR em pelo menos um ciclo de faturamento, considerando RIs/SPs.
7. Porque recomendações são estatísticas e podem ignorar picos raros, compatibilidade e dependências; mudanças em produção exigem testes, janela, monitoramento, rollback e aprovação humana.
