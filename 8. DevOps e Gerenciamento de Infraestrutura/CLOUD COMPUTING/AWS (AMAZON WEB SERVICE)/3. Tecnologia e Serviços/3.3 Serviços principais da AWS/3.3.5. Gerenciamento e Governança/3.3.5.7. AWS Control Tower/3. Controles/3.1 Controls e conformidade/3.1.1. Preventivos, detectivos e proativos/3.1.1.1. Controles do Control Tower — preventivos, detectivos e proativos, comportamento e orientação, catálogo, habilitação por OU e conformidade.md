### Controles do Control Tower — preventivos, detectivos e proativos, comportamento e orientação, catálogo, habilitação por OU e conformidade

> [!warning] Aviso
> Identificadores de controles, catálogo, quantidade, mecanismos e limites (por exemplo, número de SCPs por OU) mudam com frequência. Os exemplos aqui são referências de estudo; confirme na documentação. Os comandos **não foram executados**.

Os **controles** (*controls*, antes chamados **guardrails**) são **o coração da governança** do Control Tower: **regras de alto nível** que você **habilita em OUs** para garantir que **todas as contas** respeitem a política da organização. Eles se dividem em **preventivos** (impedem), **detectivos** (alertam) e **proativos** (verificam antes de criar), e se **herdam** pela hierarquia de OUs. Esta folha explica **como funcionam, que mecanismo está por trás de cada um, como habilitá-los e como acompanhar a conformidade**.

**Analogia:** são as **regras de um condomínio**. Algumas são **proibições com cadeado** (ninguém corta o fio das câmeras = preventivo), outras são **inspeções periódicas** que acusam o morador que deixou algo fora do padrão (detectivo), e outras são **uma checagem na portaria antes de deixar a obra começar** (proativo).

---

## Os três tipos de controle

```
 AÇÃO DO USUÁRIO / TEMPLATE
        │
        ├─► PROATIVO   ──► CloudFormation Hooks verificam o template ANTES de criar o recurso
        │                  (falha o deploy se violar)
        │
        ├─► PREVENTIVO ──► SCP/RCP BLOQUEIA a chamada de API que viola a regra
        │
        └─► (recurso criado) ──► DETECTIVO ──► Config rule AVALIA e marca "Non-compliant"
```

| Tipo | Quando age | Mecanismo | Resultado |
|---|---|---|---|
| **Preventivo** | No momento da **chamada de API** | **SCPs** (e RCPs - resource control policies) no Organizations | A ação é **negada** |
| **Detectivo** | **Depois** que o recurso existe | **AWS Config rules** | Marca `Compliant` / `Non-compliant`; notifica |
| **Proativo** | **Antes** do provisionamento | **AWS CloudFormation Hooks** | O deploy **falha** se o template violar |

### Exemplos

| Controle | Tipo | O que faz |
|---|---|---|
| Proibir desabilitar o CloudTrail | Preventivo | Nega `StopLogging`/`DeleteTrail` |
| Negar acesso a regiões não governadas | Preventivo | Bloqueia chamadas em outras regiões |
| Proibir alterar as roles do Control Tower | Preventivo | Protege a infraestrutura de governança |
| Detectar buckets S3 com leitura pública | Detectivo | Config rule `s3-bucket-public-read-prohibited` |
| Detectar volumes EBS sem criptografia | Detectivo | Config rule `encrypted-volumes` |
| Detectar usuários root com chaves de acesso | Detectivo | Config rule |
| Exigir criptografia em volumes EBS no template | Proativo | Hook falha se `Encrypted` ausente/false |
| Exigir bucket com versionamento no template | Proativo | Hook verifica o recurso antes da criação |

> [!tip] A combinação é o ponto
> **Preventivos** protegem a base de governança e ações críticas; **proativos** barram erros no **pipeline de IaC**; **detectivos** pegam o que foi criado fora do padrão (console, outras ferramentas). Cada tipo cobre a lacuna do outro.

## Comportamento e orientação (guidance)

| Orientação | Significado | Pode desabilitar? |
|---|---|---|
| **Obrigatório (mandatory)** | Sempre aplicado; **protege o landing zone** | Não |
| **Fortemente recomendado** | Boas práticas da AWS; recomendado habilitar em todas as OUs | Sim |
| **Eletivo (elective)** | Opcional; para casos específicos (como bloquear certos serviços) | Sim |

| Mudança de comportamento | Efeito |
|---|---|
| **Habilitar** um controle numa OU | Aplica a **todas as contas** da OU (e OUs filhas) |
| **Desabilitar** | Remove a regra (cuidado: remove proteção) |
| **Herança** | Controles de uma OU pai valem para as OUs filhas |
| **Contas inscritas** | Recebem os controles da OU em que estão |

## Catálogo de controles

O **Control Catalog** lista os controles disponíveis, com **identificador**, **objetivo de controle** (por exemplo, "Criptografar dados em repouso"), **serviço**, **tipo**, **severidade** e **frameworks mapeados** (CIS, NIST, PCI DSS etc.).

| Campo | Utilidade |
|---|---|
| **ID** | Ex.: `CT.S3.PR.1` (padrão atual de nomenclatura) |
| **Objetivo de controle** | Agrupa controles por intenção |
| **Serviço** | S3, EC2, IAM, RDS, KMS... |
| **Severidade** | Baixa, média, alta, crítica |
| **Implementação** | SCP, Config rule ou Hook |
| **Frameworks** | Mapeamento para padrões de conformidade |

```bash
# Catálogo e controles habilitados (exemplos)
aws controlcatalog list-controls --query 'Controls[].[Arn,Name]' --output table
aws controltower list-enabled-controls \
  --target-identifier arn:aws:organizations::111111111111:ou/o-abc/ou-xyz-12345678

# Habilita um controle em uma OU
aws controltower enable-control \
  --control-identifier arn:aws:controltower:sa-east-1::control/<ID-DO-CONTROLE> \
  --target-identifier arn:aws:organizations::111111111111:ou/o-abc/ou-xyz-12345678
```

> [!tip] Comece pelos "fortemente recomendados"
> Habilite o conjunto **recomendado** em todas as OUs de workload (criptografia, logging, bloqueio de acesso público) e acrescente os **eletivos** conforme a política: restrição de serviços, bloqueio de tipos de instância, entre outros.

## Estratégia de adoção de controles

| Etapa | Prática |
|---|---|
| **1. Inventariar requisitos** | Políticas internas e normas (LGPD, PCI, ISO) |
| **2. Mapear a controles** | Usar o catálogo e seus frameworks |
| **3. Começar em Sandbox/NonProd** | Medir impacto antes de produção |
| **4. Detectivo antes do preventivo** | Entender o que seria bloqueado |
| **5. Habilitar em produção** | Com comunicação e janela |
| **6. Monitorar o dashboard** | Tratar `Non-compliant` |
| **7. Revisar periodicamente** | Novos controles e requisitos |

```
 Novo controle preventivo?
 ├─ 1. Habilita em PolicyStaging/Sandbox
 ├─ 2. Observa 1 a 2 semanas (logs de negação no CloudTrail)
 ├─ 3. Comunica as equipes
 └─ 4. Habilita em NonProd e depois em Prod
```

## Conformidade e dashboard

O **dashboard do Control Tower** mostra:

| Visão | Informação |
|---|---|
| **Contas e OUs** | Quantidade e estado de inscrição |
| **Controles habilitados** | Por OU, tipo e comportamento |
| **Conformidade** | Contas/recursos `Compliant` e `Non-compliant` por controle |
| **Recursos não conformes** | Lista com detalhes (via Config) |
| **Drift** | Contas/OUs fora do padrão |

| Status de um controle detectivo | Significado |
|---|---|
| **Compliant** | Todos os recursos avaliados atendem |
| **Non-compliant** | Há recursos que violam a regra |
| **Not applicable** | Sem recursos do tipo |
| **Unknown / Error** | Falha de avaliação (Config desabilitado, permissão) |

**Integração com outros serviços:** os resultados dos controles detectivos (Config) alimentam o **AWS Security Hub** (CSPM) e o **Audit Manager**; eventos de não conformidade podem acionar **EventBridge** e **SNS** (a conta Audit centraliza as notificações).

## SCPs gerenciados e os seus

| Quem | Papel |
|---|---|
| **SCPs do Control Tower** | Preventivos gerenciados; **não os edite** manualmente |
| **Suas SCPs** | Adicionais, aplicadas via Organizations ou **CfCT**, respeitando o limite de SCPs por alvo e o tamanho do documento |
| **Interação** | O efeito final é a **interseção** (Deny prevalece); as permissões efetivas ficam limitadas pelo conjunto |

> [!warning] Limites de SCP
> Existe **limite** de SCPs anexadas por OU/conta e de **tamanho** por política. Muitos controles preventivos **consomem esse espaço**. Planeje a estrutura (e use **StatementIds** curtos e SCPs consolidadas) para não bater no limite.

### Padrões úteis de SCPs adicionais

| Objetivo | Exemplo |
|---|---|
| **Proteger o Control Tower e logs** | Negar alterações em recursos `aws-controltower-*` |
| **Negar regiões não usadas** | `aws:RequestedRegion` não permitido (exceto serviços globais) |
| **Impedir saída da organização** | Negar `organizations:LeaveOrganization` |
| **Proibir usuário root** | Negar ações do root nas contas-membro |
| **Obrigar criptografia** | Negar criação sem `Encrypted=true` (quando possível) |
| **Restringir serviços** | Permitir só uma lista aprovada em Sandbox |

## Exceções e escopo

Nem todo controle serve para toda conta. Estratégias:

| Necessidade | Estratégia |
|---|---|
| **Exceção temporária** | Mover a conta para uma OU `Exceptions` com controles diferentes, **com prazo** |
| **Controle com escopo parcial** | Alguns controles aceitam **exceções por principal** (por exemplo, roles administrativas autorizadas) |
| **Teste de impacto** | OU `PolicyStaging` |
| **Documentação** | Registrar **quem aprovou**, **motivo** e **data de revisão** |

## Exemplo prático: estratégia de controles por OU

| OU | Controles |
|---|---|
| **Security** | Obrigatórios + proteção reforçada de logs e KMS |
| **Workloads-Prod** | Obrigatórios + fortemente recomendados + proativos de criptografia + região negada |
| **Workloads-NonProd** | Obrigatórios + recomendados; alguns eletivos relaxados |
| **Sandbox** | Obrigatórios + restrição de serviços e tipos de instância + orçamento |
| **Suspended** | SCP **deny all** |

1. Habilitam-se primeiro os **detectivos** em Prod para medir o estado.
2. Após correções, os **preventivos** e **proativos** são ativados.
3. O dashboard acompanha a conformidade; falhas viram tarefas com dono.
4. Eventos `Non-compliant` críticos chegam ao canal de segurança via EventBridge.

## Troubleshooting

| Sintoma | Causa provável | Como resolver |
|---|---|---|
| Ação legítima negada | SCP/controle preventivo | Identificar o controle no CloudTrail (`errorMessage`); ajustar escopo ou usar OU de exceção |
| Controle detectivo em `Error` | Config desabilitado ou sem permissão | Verificar o Config e as roles |
| Controle não aparece aplicado | Conta não atualizada após mover de OU | **Update account** / re-register OU |
| Deploy de CloudFormation falha por Hook | Template violou controle proativo | Corrigir o template (ver mensagem do Hook) |
| SCP excede o limite | Muitos controles preventivos | Consolidar; reduzir controles eletivos; rever a estrutura |
| Controle não habilita | Drift ou OU não registrada | Registrar a OU; resolver o drift |
| Conformidade não atualiza | Atraso na avaliação do Config | Aguardar/reavaliar; checar o recorder |
| Falsos positivos | Regra genérica demais | Excluir recursos justificados ou ajustar o escopo |

## Erros comuns e armadilhas

- **Habilitar preventivos em produção sem testar** e quebrar pipelines.
- **Editar SCPs gerenciadas** pelo Control Tower.
- **Ignorar o dashboard** de conformidade.
- **Confundir tipos**: esperar que um controle detectivo impeça a criação.
- **Mover contas de OU** sem atualizá-las, ficando com controles antigos.
- **Esquecer serviços globais** ao negar regiões.
- **Exceções permanentes** sem revisão.
- **Estourar o limite de SCPs** por excesso de controles.

## 🧩 Quiz de Fixação

1. Qual mecanismo implementa os controles preventivos?
2. O que faz um controle proativo?
3. O que significa orientação "obrigatório"?
4. Como testar um novo controle preventivo com segurança?
5. Por que atualizar uma conta após movê-la de OU?
6. Para onde vão os resultados dos controles detectivos?

**Respostas:**
1) SCPs (e, em alguns casos, RCPs) do AWS Organizations.
2) Verifica o template antes do provisionamento, por CloudFormation Hooks, e faz o deploy falhar se violar a regra.
3) Controle sempre aplicado, que protege a landing zone e não pode ser desabilitado.
4) Habilitando primeiro em uma OU de teste (PolicyStaging/Sandbox), observando o impacto e comunicando as equipes antes de produção.
5) Para que a conta receba os controles e o baseline da nova OU.
6) Para o dashboard do Control Tower e, por integração, para Security Hub, Audit Manager e EventBridge/SNS.
