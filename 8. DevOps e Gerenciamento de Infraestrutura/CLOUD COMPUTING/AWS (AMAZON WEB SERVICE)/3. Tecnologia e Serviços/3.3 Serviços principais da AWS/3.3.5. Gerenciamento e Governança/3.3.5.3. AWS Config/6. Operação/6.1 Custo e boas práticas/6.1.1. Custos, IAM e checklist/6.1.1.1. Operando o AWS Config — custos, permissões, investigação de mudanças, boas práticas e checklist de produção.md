### Operando o AWS Config — custos, permissões, investigação de mudanças, boas práticas e checklist de produção

> [!warning] Aviso
> Preços, camadas, limites, nomes de políticas gerenciadas e recursos suportados mudam. Os números aqui são referências de estudo; confirme na documentação e no console de custos. Os comandos **não foram executados**.

O AWS Config entrega muito valor, mas **só se for operado com disciplina**: sem controle, ele vira **uma fatura grande** (milhões de configuration items e avaliações) e **uma lista infinita de não conformidades** que ninguém trata. Esta folha reúne o que sustenta o Config em produção: **entender e controlar custo**, **dar as permissões certas**, **usar o histórico para investigar mudanças**, **medir a saúde da governança** e seguir um **checklist**.

**Analogia:** é a **manutenção de um sistema de inspeção predial**. Inspecionar todos os cômodos a cada minuto é caro e gera relatórios que ninguém lê. A operação eficiente decide **o que inspecionar, com que frequência, quem recebe o relatório e o que é corrigido na hora**.

## Onde o custo se origina

| Fonte | Como é cobrada (referência) | Alavanca |
|---|---|---|
| **Configuration items** | Por CI gravado | Escopo e modo (contínuo/diário) |
| **Avaliações de regras** | Por avaliação (recurso × regra) | Escopo, quantidade e frequência das regras |
| **Conformance packs** | Por avaliação das regras do pack | Pacotes enxutos |
| **Execuções de Automation** | Conforme o SSM | Remediar só o que vale |
| **S3** | Armazenamento do histórico e snapshots | Ciclo de vida |
| **SNS/EventBridge/Lambda** | Pelo uso | Filtros |
| **Advanced queries** | Consulte a política atual | — |

```
 custo mensal ≈ (CIs gravados × preço/CI) + (avaliações × preço/avaliação) + S3 + extras
```

> [!tip] Onde a conta costuma crescer
> Em contas com **muitos recursos efêmeros** (Auto Scaling, tarefas, ENIs, snapshots) e **muitas regras periódicas**. Cada mudança vira um CI e cada reavaliação vira uma cobrança.

### Descobrindo os maiores custos

| Passo | Como |
|---|---|
| Ver CIs por tipo de recurso | Cost Explorer filtrado por serviço Config e tipo de uso; consultas de inventário com `COUNT(*)` por tipo |
| Ver quais regras avaliam mais | Métricas de avaliações por regra/conta |
| Identificar recursos que mudam demais | Histórico: recursos com milhares de CIs |

```sql
-- Quais tipos têm mais recursos (proxy de volume de CIs)
SELECT resourceType, COUNT(*)
GROUP BY resourceType
ORDER BY COUNT(*) DESC
LIMIT 20
```

## Plano de otimização de custo

| Passo | Ação | Efeito |
|---|---|---|
| 1 | Gravar **tipos relevantes** em vez de tudo (ou excluir ruidosos) | Menos CIs |
| 2 | **Modo diário** para tipos de alta rotatividade | Menos CIs |
| 3 | Recursos globais em **uma única região** | Sem duplicidade |
| 4 | Restringir regras por **tipo e tag** (ex.: só produção) | Menos avaliações |
| 5 | Evitar **regras duplicadas** em packs e regras avulsas | Menos avaliações |
| 6 | Ajustar frequência de regras **periódicas** | Menos avaliações |
| 7 | Ciclo de vida no **S3** (IA, Glacier, expiração) | Menos armazenamento |
| 8 | **Bloquear regiões** não usadas com SCP | Menos superfície e custo |
| 9 | Remediar só o que traz valor | Menos execuções |

> [!warning] Cortar custo cortando visibilidade
> Desligar o recorder "para economizar" derruba também **auditoria, regras e controles do Security Hub**. Prefira **reduzir escopo e frequência** com critério, mantendo os tipos de risco (IAM, rede, dados, criptografia) sempre gravados.

## Permissões (IAM)

| Necessidade | Como atender |
|---|---|
| O próprio Config gravar | **Service-linked role** `AWSServiceRoleForConfig` |
| Entrega ao S3/SNS | Política do bucket e do tópico para `config.amazonaws.com` |
| Analistas consultam | Políticas de leitura (`config:Get*`, `config:Describe*`, `config:SelectResourceConfig`) |
| Remediação | Role do SSM Automation com **menor privilégio** |
| Regras Lambda | `config:PutEvaluations` para a função |
| Impedir desligar o Config | **SCP** negando `config:StopConfigurationRecorder`, `config:DeleteConfigurationRecorder`, `config:DeleteDeliveryChannel`, `config:DeleteConfigRule` |

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Sid": "ProtegerConfig",
    "Effect": "Deny",
    "Action": [
      "config:StopConfigurationRecorder",
      "config:DeleteConfigurationRecorder",
      "config:DeleteDeliveryChannel",
      "config:PutConfigurationRecorder",
      "config:DeleteConfigRule"
    ],
    "Resource": "*",
    "Condition": {"ArnNotLike": {"aws:PrincipalArn": "arn:aws:iam::*:role/RoleAdminGovernanca"}}
  }]
}
```

> [!tip] Quem gera atividade não desliga a inspeção
> Equipes de workload não devem poder **parar o recorder** nem **apagar regras**. Isso preserva a integridade da governança, como no caso do CloudTrail.

## Investigando mudanças com o histórico

O histórico de configuração permite reconstruir **o que mudou, quando e como estava antes**.

```bash
# Linha do tempo de um security group
aws configservice get-resource-config-history \
  --resource-type AWS::EC2::SecurityGroup --resource-id sg-0123456789abcdef0 \
  --earlier-time 2026-11-01T00:00:00Z --later-time 2026-11-09T23:59:59Z

# Lista os recursos de um tipo que existiram/existem
aws configservice list-discovered-resources --resource-type AWS::S3::Bucket
```

### Roteiro de investigação

1. **Config:** qual recurso mudou, em que horário, e o que diferiu da versão anterior.
2. **CloudTrail:** quem executou a chamada de API (identidade, IP, ferramenta) naquele horário.
3. **CloudWatch:** houve efeito observável (erros, latência) depois da mudança?
4. **Decisão:** reverter, corrigir o template de IaC ou abrir exceção.

```
 SG aberto ao mundo às 10:03
   Config     → diff: 10.0.0.0/8 → 0.0.0.0/0
   CloudTrail → usuário maria, console, IP externo
   CloudWatch → pico de conexões recusadas às 10:20
```

> [!warning] Config sem CloudTrail deixa a pergunta "quem" sem resposta
> Habilite os dois. O Config mostra o estado antes e depois; o CloudTrail identifica o autor. Juntos formam a investigação completa.

## Medindo a saúde da governança

| Indicador | Meta |
|---|---|
| Cobertura do recorder (contas × regiões) | 100% das contas e regiões permitidas |
| Entrega ao S3 sem falhas | Sem erros no status do delivery channel |
| Recursos críticos não conformes além do prazo | Zero |
| Tempo médio de remediação (críticos) | Em horas |
| Exceções vencidas | Zero |
| Regras sem dono | Zero |
| Custo do Config por conta (tendência) | Estável |

```bash
aws configservice describe-configuration-recorder-status
aws configservice describe-delivery-channel-status
aws configservice describe-compliance-by-config-rule \
  --compliance-types NON_COMPLIANT
```

## Boas práticas e checklist de produção

1. **Recorder ligado** em todas as contas e regiões permitidas; recursos globais em **uma** região.
2. **Tipos de risco sempre gravados** (IAM, rede, S3, KMS, bancos); **diário/exclusão** para tipos efêmeros.
3. **Bucket central** em conta de log archive, com **Object Lock**, versionamento, KMS e **ciclo de vida**.
4. **Aggregator** na conta de segurança (administrador delegado).
5. **Organization conformance packs** como piso obrigatório, versionados em Git.
6. **Escopo por tag/ambiente** nas regras para reduzir ruído e custo.
7. **Remediação automática só para baixo risco**; exceções documentadas com prazo.
8. **EventBridge** com filtro; alertas com **dono** (tag) e ticket.
9. **SCP** protegendo recorder, canal e regras.
10. **Revisão trimestral** de regras, custo, exceções e cobertura; integração com **Security Hub**.

## Relatório mensal de governança (modelo)

| Seção | Conteúdo |
|---|---|
| Cobertura | Contas e regiões com recorder ativo vs esperado |
| Conformidade | Percentual por regra e por conta; críticos em destaque |
| Tendência | Evolução de não conformes críticos nos últimos meses |
| Remediação | Tempo médio, falhas, ações manuais pendentes |
| Exceções | Ativas, vencidas e justificativas |
| Custo | Gasto do Config por conta e por componente |
| Ações | Prioridades do próximo mês e responsáveis |

Esse relatório transforma o Config de uma ferramenta técnica em um **instrumento de gestão**, com donos e metas claras.

## Exemplo prático: reduzindo ruído e custo em 40 contas

1. A auditoria mostra 60% dos CIs vindos de ENIs e snapshots (alta rotatividade).
2. Esses tipos passam para **modo diário**; IAM fica em **uma região**.
3. As regras de criptografia agora valem só para **Ambiente=producao**.
4. Dois packs com regras duplicadas são consolidados em um só.
5. O ciclo de vida do bucket move histórico antigo para Glacier e expira em 7 anos.
6. Resultado: menos CIs e avaliações, sem perder cobertura dos tipos de risco; painel de custo acompanha a tendência.

## Troubleshooting

| Sintoma | Causa provável | Como resolver |
|---|---|---|
| Conta do Config disparou | Tipos efêmeros contínuos, regras periódicas demais | Modo diário; escopo; ajustar frequência |
| Recorder parado | Alguém o desligou | SCP; religar; investigar no CloudTrail |
| Delivery channel falhando | Política do bucket/KMS | Corrigir permissões |
| Lista enorme de não conformes | Regras sem priorização | Priorizar por severidade; donos e prazos |
| Regra "avalia tudo" | Sem escopo | Restringir por tipo/tag |
| Histórico incompleto | Gravação parada no período | Verificar status; checar lacunas |
| Remediação em loop | IaC recria o recurso fora da regra | Corrigir a fonte |

## Erros comuns e armadilhas

- **Desligar o recorder para economizar** e perder auditoria e controles.
- **Gravar tudo continuamente** sem avaliar o volume de CIs.
- **Regras sem escopo**, avaliando recursos irrelevantes.
- **Lista de não conformes sem dono** nem prazo.
- **Deixar equipes de workload** parar o recorder ou apagar regras.
- **Não usar Config e CloudTrail juntos** nas investigações.
- **Sem ciclo de vida no S3** do histórico.
- **Tratar conformidade como percentual**, ignorando a severidade.

## 🧩 Quiz de Fixação

1. Quais são as duas principais fontes de custo do Config?
2. Como reduzir CIs de tipos de alta rotatividade?
3. Qual SCP protege a governança do Config?
4. Como combinar Config e CloudTrail em uma investigação?
5. Por que restringir o escopo das regras por tag?
6. Por que não desligar o recorder para economizar?

**Respostas:**
1) Configuration items gravados e avaliações de regras (mais S3 e extras).
2) Usando modo de gravação diário ou excluindo esses tipos do recorder.
3) Uma SCP que negue ações como StopConfigurationRecorder, DeleteConfigurationRecorder, DeleteDeliveryChannel e DeleteConfigRule a quem não seja a role de governança.
4) O Config mostra o que mudou e quando (antes e depois); o CloudTrail identifica quem fez a chamada; o CloudWatch mostra o efeito observável.
5) Para avaliar apenas recursos relevantes (como produção), reduzindo custo e ruído.
6) Porque isso elimina auditoria, regras e a base de controles do Security Hub, criando pontos cegos.
