### Config rules — regras gerenciadas, custom com Lambda e Guard, gatilhos, escopo, avaliação de conformidade e conformance packs

> [!warning] Aviso
> Identificadores de regras gerenciadas, runtimes suportados, linguagem Guard, preços e limites mudam. Os nomes e valores aqui são referências de estudo; confirme na documentação. Os comandos **não foram executados**.

As **Config rules** são o que transforma o inventário do AWS Config em **governança**: cada regra define **um critério de conformidade** e o Config **avalia continuamente** os recursos contra ele, marcando-os como **conformes** ou **não conformes**. É o mecanismo que responde "meus recursos obedecem à política?" sem inspeção manual.

**Analogia:** é o **checklist de um fiscal de obras**. Cada item ("extintor presente", "saída de emergência desobstruída") é uma regra. O fiscal passa em todas as salas (recursos), marca ✅ ou ❌ e registra. Alguns itens são checados **sempre que a sala é reformada** (por mudança) e outros **toda semana** (periodicamente).

---

## Tipos de regras

| Tipo | Origem | Quando usar |
|---|---|---|
| **AWS managed rules** | Mantidas pela AWS; centenas de regras prontas | **Primeira escolha**: cobrem os controles comuns |
| **Custom rules com Lambda** | Você escreve uma função que avalia o recurso | Lógica complexa ou integração com sistemas |
| **Custom rules com Guard (policy as code)** | Você escreve a regra em **CloudFormation Guard** (DSL declarativa), sem servidor | Regras declarativas simples e legíveis |
| **Service-linked rules** | Criadas por outros serviços (ex.: Security Hub, Control Tower) | Gerenciadas pelo serviço de origem |

> [!tip] Managed rule primeiro
> Antes de escrever código, procure uma **managed rule**. Ela já foi testada, é mantida pela AWS e reduz esforço de manutenção.

### Exemplos de managed rules

| Regra | Verifica |
|---|---|
| `s3-bucket-public-read-prohibited` | Buckets sem leitura pública |
| `restricted-ssh` | Security groups sem SSH aberto a `0.0.0.0/0` |
| `encrypted-volumes` | Volumes EBS criptografados |
| `rds-storage-encrypted` | RDS com criptografia |
| `iam-user-mfa-enabled` | Usuários IAM com MFA |
| `root-account-mfa-enabled` | Usuário raiz com MFA |
| `cloudtrail-enabled` | CloudTrail habilitado |
| `required-tags` | Presença de tags obrigatórias |
| `ec2-instance-no-public-ip` | Instâncias sem IP público |
| `vpc-flow-logs-enabled` | VPC Flow Logs ligados |
| `access-keys-rotated` | Chaves de acesso rotacionadas dentro do prazo |

## Gatilhos: quando a regra roda

| Gatilho | Comportamento | Exemplo |
|---|---|---|
| **Mudança de configuração** (`ConfigurationItemChangeNotification`) | Avalia o recurso **sempre que ele muda** | Security group alterado |
| **Periódico** (`ScheduledNotification`) | Avalia em intervalos (1, 3, 6, 12, 24 h) | Verificar chaves antigas, avaliação do conjunto |
| **Híbrido** | Ambos, conforme o tipo | Regras que olham tempo decorrido |

```
 Regra por mudança:   recurso muda ──► CI ──► avaliação imediata
 Regra periódica:     relógio (24 h) ───────► avaliação de todos os recursos do escopo
```

### Escopo da regra

| Opção | Efeito |
|---|---|
| **Tipos de recurso** | Só avalia certos tipos (ex.: `AWS::S3::Bucket`) |
| **Recurso específico** | Avalia um ID |
| **Tag** | Avalia só recursos com determinada tag (ex.: `Ambiente=producao`) |

Restringir o escopo **reduz custo e ruído**: uma regra de criptografia pode valer só para produção.

---

## Resultados da avaliação

| Status | Significado |
|---|---|
| **COMPLIANT** | O recurso atende à regra |
| **NON_COMPLIANT** | O recurso viola a regra |
| **NOT_APPLICABLE** | A regra não se aplica ao recurso |
| **INSUFFICIENT_DATA** | Ainda sem dados para avaliar |

```bash
# Habilita uma managed rule
aws configservice put-config-rule --config-rule '{
  "ConfigRuleName": "restricted-ssh",
  "Source": {"Owner": "AWS", "SourceIdentifier": "INCOMING_SSH_DISABLED"},
  "Scope": {"ComplianceResourceTypes": ["AWS::EC2::SecurityGroup"]}
}'

# Resumo de conformidade
aws configservice describe-compliance-by-config-rule

# Recursos não conformes
aws configservice get-compliance-details-by-config-rule \
  --config-rule-name restricted-ssh --compliance-types NON_COMPLIANT
```

> [!warning] A conformidade "geral" pode enganar
> Uma conta com 98% de conformidade ainda tem recursos críticos fora da política. Priorize por **severidade** (dados públicos, falta de MFA no raiz) e não apenas pelo percentual.

## Regras custom com Guard (sem servidor)

O **CloudFormation Guard** permite escrever regras declarativas (*policy as code*), sem Lambda:

```
# Regra: volumes EBS devem ser criptografados
rule volumes_criptografados when resourceType == "AWS::EC2::Volume" {
    configuration.encrypted == true
}

# Regra: buckets devem ter versionamento habilitado
rule buckets_versionados when resourceType == "AWS::S3::Bucket" {
    supplementaryConfiguration.BucketVersioningConfiguration.status == "Enabled"
}
```

| Vantagem | Observação |
|---|---|
| Sem código para hospedar | Sem Lambda, sem permissões extras |
| Legível por auditores | Linguagem declarativa |
| Reutilizável | Também serve em pipelines de CI (validar templates antes do deploy) |

## Regras custom com Lambda

Para lógica que Guard não expressa (consultar sistemas externos, cálculos complexos):

```python
import json, boto3

config = boto3.client("config")

def lambda_handler(event, context):
    invoking = json.loads(event["invokingEvent"])
    item = invoking["configurationItem"]
    # Exemplo: exige a tag "Dono"
    tags = item.get("tags", {})
    compliance = "COMPLIANT" if "Dono" in tags else "NON_COMPLIANT"

    config.put_evaluations(
        Evaluations=[{
            "ComplianceResourceType": item["resourceType"],
            "ComplianceResourceId": item["resourceId"],
            "ComplianceType": compliance,
            "OrderingTimestamp": item["configurationItemCaptureTime"],
        }],
        ResultToken=event["resultToken"],
    )
```

| Cuidado | Por quê |
|---|---|
| **Idempotência** | A função pode ser chamada várias vezes |
| **Permissões** | A role precisa de `config:PutEvaluations` |
| **Tempo e erros** | Falhas deixam o recurso sem avaliação |
| **Manutenção** | É código seu: versões, testes, runtime |

## Conformance packs

Um **conformance pack** é um **conjunto de regras (e ações de remediação)** implantado como uma unidade, descrito em **template YAML**. Existem **pacotes de exemplo** alinhados a normas e boas práticas (por exemplo, CIS, PCI DSS, NIST, boas práticas operacionais).

```
 Conformance pack "boas-praticas-seguranca"
 ├─ regra: s3-bucket-public-read-prohibited
 ├─ regra: encrypted-volumes
 ├─ regra: iam-user-mfa-enabled
 ├─ regra: restricted-ssh
 └─ remediação: reativar Block Public Access
```

```bash
aws configservice put-conformance-pack \
  --conformance-pack-name seguranca-base \
  --template-s3-uri s3://meu-bucket-packs/seguranca-base.yaml
```

| Benefício | Efeito |
|---|---|
| Implantação em massa | Um comando cria dezenas de regras |
| Relatório por pacote | Pontuação de conformidade do conjunto |
| **Organization conformance packs** | Implantados em **todas as contas** da organização |
| Versionamento | Template em Git; mudanças revisadas |

## Desenho de um conjunto de regras

| Camada | Regras típicas |
|---|---|
| **Identidade** | MFA no raiz e em usuários, rotação de chaves, sem políticas `*:*` |
| **Dados** | Criptografia (EBS, RDS, S3), sem buckets públicos, versionamento |
| **Rede** | Sem SSH/RDP abertos, flow logs, sem IP público indevido |
| **Auditoria** | CloudTrail ativo, validação de logs, Config ligado |
| **Governança** | Tags obrigatórias, regiões permitidas |
| **Resiliência** | Backups, multi-AZ em produção |

> [!tip] Comece com poucas regras de alto valor
> Dez regras bem escolhidas e tratadas valem mais do que duzentas ignoradas. Defina **dono**, **prazo** e **prioridade** para cada tipo de não conformidade.

## Validando regras antes de aplicar

| Prática | Como fazer |
|---|---|
| Testar a regra Guard localmente | Rodar a CLI do Guard contra amostras de CIs em JSON |
| Validar templates de IaC no pipeline | Usar as mesmas regras Guard antes do deploy (**shift-left**) |
| Começar só com notificação | Habilitar a regra sem remediação e observar os resultados |
| Reavaliar sob demanda | `start-config-rules-evaluation` para ver o efeito imediato |

```bash
aws configservice start-config-rules-evaluation --config-rule-names restricted-ssh
aws configservice describe-config-rule-evaluation-status --config-rule-names restricted-ssh
```

> [!tip] Detectar cedo é mais barato
> Rodar as mesmas regras **antes do deploy** (no pipeline) evita que recursos não conformes sequer existam; o Config fica como **rede de segurança** para o que escapar.

## Exemplo prático: política de tags e criptografia

1. Ativa `required-tags` (Dono, Ambiente, CentroDeCusto) para EC2, RDS e S3.
2. Ativa `encrypted-volumes` e `rds-storage-encrypted` com escopo **Ambiente=producao**.
3. Cria uma regra Guard para exigir versionamento em buckets de dados.
4. Agrupa tudo em um **conformance pack** versionado no Git.
5. Implanta como **organization conformance pack** em todas as contas.
6. Cria um painel de não conformidade por conta e por severidade.

## Troubleshooting

| Sintoma | Causa provável | Como resolver |
|---|---|---|
| Regra com `INSUFFICIENT_DATA` | Recorder não grava o tipo | Incluir o tipo no `recordingGroup` |
| Regra não dispara | Gatilho/escopo incorreto | Revisar tipo de recurso e gatilho |
| Custom Lambda sem resultado | Falha ou falta de `PutEvaluations` | Ver logs da função e permissões |
| Muitos `NOT_APPLICABLE` | Escopo amplo demais | Restringir por tipo ou tag |
| Custo de avaliações alto | Regras duplicadas/periódicas frequentes | Consolidar; ajustar frequência |
| Conformance pack falha | Template ou permissão inválida | Ver eventos de implantação |
| Regra gerenciada indisponível | Tipo não suportado na região | Verificar disponibilidade por região |

## Erros comuns e armadilhas

- **Escrever regra custom** quando já existe uma managed.
- **Regras sem dono**, gerando uma lista de não conformes que ninguém trata.
- **Escopo amplo** em regras que só valem para produção.
- **Esquecer que a regra depende do recorder** gravar o tipo.
- **Medir só o percentual de conformidade** e ignorar a severidade.
- **Lambda custom sem idempotência** ou sem permissão de `PutEvaluations`.
- **Não versionar** conformance packs e regras.
- **Esperar que a regra impeça** o recurso de existir.

## 🧩 Quiz de Fixação

1. Quais são os principais tipos de Config rules?
2. Qual a diferença entre gatilho por mudança e periódico?
3. O que é uma regra Guard?
4. O que é um conformance pack?
5. Qual o papel do `PutEvaluations` em uma regra Lambda?
6. Por que restringir o escopo de uma regra?

**Respostas:**
1) Managed rules da AWS, custom com Lambda, custom com Guard e regras service-linked.
2) A por mudança avalia o recurso sempre que ele muda; a periódica avalia em intervalos configurados (de 1 a 24 horas).
3) Uma regra declarativa escrita em CloudFormation Guard (policy as code), avaliada pelo Config sem servidor.
4) Um conjunto de regras e remediações implantado como unidade por template YAML, inclusive em toda a organização.
5) Enviar ao Config o resultado da avaliação (COMPLIANT/NON_COMPLIANT) de cada recurso.
6) Para reduzir custo e ruído, avaliando somente os recursos relevantes (por tipo ou tag, como produção).
