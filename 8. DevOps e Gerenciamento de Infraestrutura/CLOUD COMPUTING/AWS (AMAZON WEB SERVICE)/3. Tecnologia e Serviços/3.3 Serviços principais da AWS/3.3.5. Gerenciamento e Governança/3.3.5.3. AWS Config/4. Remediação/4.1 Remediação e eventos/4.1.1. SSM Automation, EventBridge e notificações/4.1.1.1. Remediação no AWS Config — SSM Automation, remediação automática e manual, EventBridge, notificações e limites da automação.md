### Remediação no AWS Config — SSM Automation, remediação automática e manual, EventBridge, notificações e limites da automação

> [!warning] Aviso
> Nomes de documentos de automação, parâmetros, limites de tentativas e comportamentos de eventos mudam. Os exemplos aqui são referências de estudo; confirme na documentação. Os comandos **não foram executados**.

Detectar que um recurso está **NON_COMPLIANT** é só o primeiro passo; o valor real vem de **corrigir** (remediar) e **avisar** as pessoas certas. O AWS Config integra-se ao **AWS Systems Manager Automation** para **remediar** (manual ou automaticamente) e ao **Amazon EventBridge** e ao **SNS** para **notificar** e disparar fluxos de trabalho.

**Analogia:** o fiscal de obras que encontra uma saída de emergência bloqueada pode apenas **anotar a infração** (detecção), **chamar a equipe de manutenção para desbloquear** (remediação) e **avisar o síndico** (notificação). Remediar automaticamente é como ter uma equipe de manutenção de plantão que age assim que a infração é registrada, mas só deve agir sozinha onde o risco de erro é baixo.

---

## Visão do fluxo

```
 Recurso muda ──► Config rule avalia ──► NON_COMPLIANT
                                              │
              ┌───────────────────────────────┼─────────────────────────────┐
              ▼                               ▼                             ▼
     Remediação automática           EventBridge (evento)              Console/CLI
     (SSM Automation)                       │                          Remediação manual
              │                  ┌──────────┼───────────┐
              ▼                  ▼          ▼           ▼
        Recurso corrigido      SNS       Lambda     Ticket/Chat
              │
              └─► nova avaliação ──► COMPLIANT
```

| Mecanismo | Função |
|---|---|
| **Remediation action** | Associada a uma regra; executa um **documento SSM Automation** |
| **Automática** | Dispara sozinha para recursos não conformes |
| **Manual** | Um operador aprova e executa pelo console/CLI |
| **EventBridge** | Reage a mudanças de conformidade para qualquer fluxo |
| **SNS** | Notificações de mudança de configuração e conformidade |

## Remediação com SSM Automation

A remediação usa **documentos de Automation** (runbooks) do **Systems Manager**. A AWS fornece muitos prontos (prefixo `AWS-`, `AWSConfigRemediation-`), e você pode criar os seus.

| Regra | Documento de remediação (exemplo) | Efeito |
|---|---|---|
| `s3-bucket-public-read-prohibited` | `AWS-DisableS3BucketPublicReadWrite` | Desativa acesso público |
| `restricted-ssh` | Remover regra de entrada aberta | Fecha porta 22 |
| `encrypted-volumes` | Criar cópia criptografada (ação mais intrusiva) | Muitas vezes só notifica |
| `cloudtrail-enabled` | Habilitar CloudTrail | Restaura auditoria |
| `s3-bucket-versioning-enabled` | Habilitar versionamento | Corrige configuração |

```bash
aws configservice put-remediation-configurations --remediation-configurations '[{
  "ConfigRuleName": "s3-bucket-public-read-prohibited",
  "TargetType": "SSM_DOCUMENT",
  "TargetId": "AWS-DisableS3BucketPublicReadWrite",
  "Automatic": true,
  "MaximumAutomaticAttempts": 3,
  "RetryAttemptSeconds": 60,
  "Parameters": {
    "AutomationAssumeRole": {"StaticValue": {"Values": ["arn:aws:iam::123456789012:role/ConfigRemediacaoRole"]}},
    "S3BucketName": {"ResourceValue": {"Value": "RESOURCE_ID"}}
  }
}]'
```

| Parâmetro | Significado |
|---|---|
| `Automatic` | `true` = remedia sozinho; `false` = exige execução manual |
| `MaximumAutomaticAttempts` | Quantas tentativas automáticas |
| `RetryAttemptSeconds` | Intervalo entre tentativas |
| `AutomationAssumeRole` | Role que o SSM assume para corrigir |
| `ResourceValue: RESOURCE_ID` | Passa o ID do recurso não conforme ao documento |

> [!tip] Role de remediação com menor privilégio
> A role usada pela automação deve ter **só** as permissões da correção (por exemplo, alterar o *Block Public Access* de buckets), e **nada além**. Ela é o seu "robô com chave-mestra": trate com cuidado.

## Remediação automática vs manual

| Aspecto | Automática | Manual |
|---|---|---|
| Velocidade | Imediata | Depende de uma pessoa |
| Risco | Pode afetar serviço legítimo | Humano avalia o contexto |
| Escala | Muitos recursos de uma vez | Trabalhoso |
| Quando usar | Ações **de baixo risco e alta confiança** | Ações intrusivas, dados, produção crítica |

| Ação | Recomendação |
|---|---|
| Fechar acesso público de bucket | Automática (baixo risco, alto ganho) |
| Remover SSH aberto ao mundo | Automática, com exceções documentadas |
| Habilitar versionamento / flow logs | Automática |
| Criptografar volume existente | Manual (exige recriar o volume) |
| Encerrar instâncias fora do padrão | **Nunca** automática sem processo claro |
| Alterar políticas IAM | Manual, com aprovação |

> [!warning] Remediar sem exceções derruba serviços
> Uma regra que fecha **qualquer** SSH aberto pode isolar uma instância de manutenção legítima. Mantenha **lista de exceções** (por tag ou ID) e comece em modo **manual** ou apenas notificação antes de automatizar.

## EventBridge: reagir à conformidade

Mudanças de conformidade e de configuração geram eventos que o **EventBridge** pode rotear.

```json
{
  "source": ["aws.config"],
  "detail-type": ["Config Rules Compliance Change"],
  "detail": {
    "messageType": ["ComplianceChangeNotification"],
    "newEvaluationResult": {"complianceType": ["NON_COMPLIANT"]},
    "configRuleName": ["restricted-ssh", "s3-bucket-public-read-prohibited"]
  }
}
```

| Detail-type | Quando ocorre |
|---|---|
| `Config Rules Compliance Change` | Um recurso muda de `COMPLIANT` para `NON_COMPLIANT` (ou vice-versa) |
| `Config Configuration Item Change` | Um recurso muda de configuração |
| `Config Rules Re-evaluation Status` | Reavaliação concluída |
| `Config Configuration Snapshot Delivery Status` | Entrega de snapshot |

Destinos úteis: **SNS** (aviso), **Lambda** (lógica customizada), **Step Functions** (fluxo de aprovação), **SQS** (fila de tratamento), integração com **chat/ticket** para abrir tarefas com dono.

```
 NON_COMPLIANT ──► EventBridge ──► Lambda ──► abre ticket com dono (tag "Dono")
                               └──► SNS ──► canal de segurança
```

---

## Notificações SNS do delivery channel

O **delivery channel** pode publicar no **SNS** todas as notificações do Config (mudanças de configuração, conformidade, entrega de snapshots). É mais **verboso** que o EventBridge; prefira o **EventBridge com filtro** para alertas acionáveis.

---

## Fluxo completo de tratamento

```
 1. Regra detecta NON_COMPLIANT
 2. EventBridge notifica (canal + ticket para o dono)
 3. Se houver remediação segura → automática (SSM)
 4. Config reavalia → COMPLIANT (ou continua NON_COMPLIANT)
 5. Se persistir: escalonar; exceção documentada com prazo
 6. Métrica: tempo médio de remediação (MTTR) e backlog de não conformes
```

| Indicador | Meta sugerida |
|---|---|
| Tempo médio até corrigir (críticos) | Horas |
| Não conformes críticos abertos > prazo | Zero |
| Remediações automáticas com falha | Investigar cada uma |
| Exceções vencidas | Zero |

## Limites e cuidados da automação

| Limite | Detalhe |
|---|---|
| **Nem tudo é remediável por Automation** | Algumas correções exigem recriar o recurso |
| **Tentativas finitas** | Após o máximo, o recurso permanece não conforme |
| **Loops** | Remediação que desfaz uma mudança legítima gera "briga" com automação |
| **Permissões** | Falta de permissão faz a automação falhar silenciosamente (ver execuções) |
| **Eventual consistência** | A reavaliação pode levar minutos |
| **Custo** | Execuções de Automation e reavaliações têm custo |

> [!tip] Evite a guerra entre automações
> Se uma pipeline de IaC recria um recurso fora da regra e a remediação o corrige, você pode ter um **ciclo** de mudanças. Corrija a **fonte** (o template) e use a remediação como rede de segurança, não como processo normal.

## Runbook próprio de remediação

Quando nenhum documento pronto serve, crie um **runbook de Automation** que implemente a correção da sua política.

```yaml
schemaVersion: '0.3'
description: Fecha acesso SSH aberto ao mundo em um security group
assumeRole: '{{ AutomationAssumeRole }}'
parameters:
  GroupId: {type: String}
  AutomationAssumeRole: {type: String}
mainSteps:
  - name: revogarSshAberto
    action: aws:executeAwsApi
    inputs:
      Service: ec2
      Api: RevokeSecurityGroupIngress
      GroupId: '{{ GroupId }}'
      IpProtocol: tcp
      FromPort: 22
      ToPort: 22
      CidrIp: 0.0.0.0/0
```

| Boa prática | Motivo |
|---|---|
| Runbooks **idempotentes** | Podem rodar várias vezes sem efeito colateral |
| Registrar o que foi alterado | Rastreabilidade e reversão |
| Testar em conta de desenvolvimento | Evita surpresas em produção |
| Versionar em Git/IaC | Revisão e auditoria |

## Exemplo prático: bucket público, do alerta à correção

1. Um desenvolvedor remove o *Block Public Access* de `relatorios` para um teste.
2. Em minutos, `s3-bucket-public-read-prohibited` marca o bucket **NON_COMPLIANT**.
3. O EventBridge envia alerta ao canal de segurança e cria um ticket com o dono (tag `Dono`).
4. A **remediação automática** executa `AWS-DisableS3BucketPublicReadWrite`.
5. O Config reavalia: o bucket volta a **COMPLIANT**.
6. O CloudTrail mostra quem alterou; o time conversa com o desenvolvedor e oferece um caminho seguro (URL pré-assinada ou CloudFront).

## Troubleshooting

| Sintoma | Causa provável | Como resolver |
|---|---|---|
| Remediação não executa | `Automatic: false` ou role sem permissão | Revisar configuração e `AutomationAssumeRole` |
| Execução falha no SSM | Parâmetros incorretos / recurso inexistente | Ver detalhes da execução do Automation |
| Recurso continua não conforme | Remediação não corrige a causa | Revisar o documento; intervenção manual |
| Muitas tentativas e falhas | Erro permanente | Reduzir tentativas; tratar manualmente |
| Alertas excessivos | Evento sem filtro | Filtrar por regra, severidade, conta |
| Corrige e volta a quebrar | IaC recria o recurso fora da regra | Corrigir o template/pipeline |
| Eventos não chegam | Regra do EventBridge em outra região | Criar na região do evento |

## Erros comuns e armadilhas

- **Automatizar remediação sem lista de exceções.**
- **Role de remediação muito poderosa.**
- **Não filtrar eventos** e inundar o canal de segurança.
- **Ignorar o dono do recurso**: alerta sem responsável não é tratado.
- **Corrigir sintomas** e não a origem (templates de IaC).
- **Esperar remediação automática para tudo**, inclusive ações destrutivas.
- **Não monitorar falhas** das próprias remediações.
- **Ações intrusivas sem janela de mudança.**

## 🧩 Quiz de Fixação

1. Que serviço executa a remediação do Config?
2. Quando preferir remediação manual?
3. Para que serve `MaximumAutomaticAttempts`?
4. Qual evento do EventBridge indica mudança de conformidade?
5. Por que manter uma lista de exceções?
6. Por que a role de remediação deve ter menor privilégio?

**Respostas:**
1) O AWS Systems Manager Automation, por documentos (runbooks) associados à regra.
2) Para ações intrusivas ou de risco (recriar volumes, alterar IAM, produção crítica), em que um humano deve avaliar o contexto.
3) Define quantas vezes o Config tenta remediar automaticamente antes de desistir.
4) "Config Rules Compliance Change".
5) Para evitar que a automação afete recursos legítimos, como uma instância de manutenção com SSH autorizado.
6) Porque é uma identidade com poder de alterar recursos automaticamente; limitar suas permissões reduz o impacto de erro ou abuso.
