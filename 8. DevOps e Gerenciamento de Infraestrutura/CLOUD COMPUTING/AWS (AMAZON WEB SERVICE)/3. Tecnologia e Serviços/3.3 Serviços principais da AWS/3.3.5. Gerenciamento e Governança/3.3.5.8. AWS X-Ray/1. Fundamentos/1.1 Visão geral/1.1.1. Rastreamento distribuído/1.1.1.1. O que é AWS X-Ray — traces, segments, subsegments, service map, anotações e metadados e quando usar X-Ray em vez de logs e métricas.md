### 1.1.1.1. O que é AWS X-Ray — traces, segments, subsegments, service map, anotações e metadados e quando usar X-Ray em vez de logs e métricas

> [!warning] Aviso
> Nomes de campos, limites, preços e o estado das ferramentas de instrumentação (SDKs do X-Ray, ADOT, OpenTelemetry) abaixo são **de memória e mudam com frequência**. A AWS vem **recomendando OpenTelemetry** como caminho de instrumentação e colocando os SDKs próprios do X-Ray em modo de manutenção; **confirme o estado atual na documentação oficial**. Comandos e JSONs são ilustrativos e **não foram executados**.

## 1. O problema que o X-Ray resolve

Numa aplicação monolítica, quando uma requisição fica lenta, você abre o log e a pilha de chamadas conta a história. Em uma arquitetura distribuída — API Gateway → Lambda → DynamoDB → SQS → outro Lambda → serviço externo — **uma única requisição do usuário atravessa dez componentes**, cada um com seu próprio log, seu próprio relógio e sua própria equipe. Perguntas simples ficam difíceis:

- **Onde** a requisição ficou lenta? No API Gateway, no cold start do Lambda, na query do DynamoDB, na chamada HTTP externa?
- **Qual** componente está gerando os erros 5xx que o usuário vê?
- **Quais** serviços dependem de quais (o mapa real, não o do diagrama de arquitetura desatualizado)?
- A lentidão afeta **todos** os usuários ou só um tipo de requisição (um cliente, uma região, uma versão)?

O **AWS X-Ray** é o serviço de **rastreamento distribuído** (distributed tracing) da AWS: ele coleta dados sobre as requisições que a sua aplicação atende, **costura os pedaços de cada requisição em um único trace** e oferece um **mapa de serviços** (service map) e ferramentas de análise para encontrar gargalos e erros.

> [!info] Em uma frase
> **Logs** dizem *o que* aconteceu em um componente; **métricas** dizem *quanto/quantas vezes* no agregado; **traces** dizem *por onde* uma requisição específica passou e *quanto tempo* gastou em cada parada.

## 2. Conceitos fundamentais

### 2.1 Trace, segment e subsegment

| Conceito | O que é | Exemplo |
|---|---|---|
| **Trace** | Todo o caminho de **uma requisição**, identificado por um **trace ID**, reunindo os dados de todos os serviços que ela tocou | A requisição `POST /pedidos` do usuário João |
| **Segment** | A parte do trace gerada por **um serviço/recurso** (um “recurso” = a aplicação, a função Lambda, o serviço gerenciado) | O trabalho do Lambda `criar-pedido` |
| **Subsegment** | Detalhamento **dentro** de um segment: uma chamada a outro serviço, uma query, uma chamada HTTP, um trecho de código | A chamada `PutItem` ao DynamoDB dentro do Lambda |
| **Trace ID** | Identificador único propagado entre serviços (formato `1-<epoch hex>-<96 bits>`) | `1-67a1b2c3-1234567890abcdef12345678` |
| **Segment ID / Parent ID** | Identificam cada segmento e seu pai, formando a árvore | — |

```
Trace 1-67a1b2c3-...           (uma requisição)
│
├─ Segment: API Gateway        120 ms
│   └─ Subsegment: integração Lambda
│
└─ Segment: Lambda criar-pedido  95 ms
    ├─ Subsegment: Initialization (cold start)   40 ms
    ├─ Subsegment: DynamoDB PutItem              18 ms
    ├─ Subsegment: SQS SendMessage                9 ms
    └─ Subsegment: HTTPS api.pagamentos.com      22 ms
```

### 2.2 Documento de segment (formato)

O X-Ray recebe **segment documents** em JSON. Um exemplo simplificado e ilustrativo:

```json
{
  "name": "criar-pedido",
  "id": "70de5b6f19ff9a0a",
  "trace_id": "1-581cf771-a006649127e371903a2de979",
  "start_time": 1478293361.271,
  "end_time": 1478293361.449,
  "annotations": { "tenant": "acme", "tipo_pedido": "premium" },
  "metadata": { "carrinho": { "itens": 3, "total": 199.9 } },
  "subsegments": [
    { "name": "DynamoDB", "namespace": "aws", "start_time": 1478293361.3, "end_time": 1478293361.32 }
  ]
}
```

Campos relevantes: **`name`** (nome do serviço no mapa), **`start_time`/`end_time`**, flags **`error`** (erro do cliente, 4xx), **`fault`** (erro do servidor, 5xx) e **`throttle`** (429), além de **`http`**, **`aws`**, **`cause`** (exceções) e **`annotations`/`metadata`**.

### 2.3 Anotações vs metadados

| | **Annotations** | **Metadata** |
|---|---|---|
| Indexadas para busca? | **Sim** — usadas em filter expressions e grupos | **Não** |
| Tipos | string, número, booleano | qualquer objeto/JSON |
| Uso típico | `tenant`, `versao`, `tipo_pedido`, `canal` | payloads, listas, objetos de depuração |
| Limite | Quantidade limitada por segment (confirmar o limite atual) | Dentro do limite de tamanho do documento |

Regra prática: **se você vai querer filtrar por isso, é annotation; se só quer olhar quando abrir o trace, é metadata.** Nunca coloque dados sensíveis (CPF, token, senha) em nenhum dos dois (ver a nota de segurança).

## 3. Como os dados chegam ao X-Ray

```
Aplicação instrumentada ──UDP/gRPC──▶ X-Ray daemon / ADOT Collector ──HTTPS──▶ API do X-Ray (PutTraceSegments)
        │                                                                              │
        └── serviços AWS (API Gateway, Lambda, ...) enviam segmentos diretamente ──────┘
                                                                                        ▼
                                                    Console: Service map • Traces • Analytics • Insights
```

- A **aplicação** (via SDK ou OpenTelemetry) gera segmentos e os envia a um **intermediário local** — o **X-Ray daemon** (processo que escuta em UDP 2000 e agrupa em lotes) ou o **AWS Distro for OpenTelemetry (ADOT) Collector**.
- O intermediário chama a API **`PutTraceSegments`** (e `PutTelemetryRecords`) do X-Ray.
- Alguns **serviços da AWS** geram segmentos próprios automaticamente quando o tracing é habilitado (API Gateway, Lambda, App Mesh, entre outros) — isso é o que desenha o início e o meio do trace sem você escrever código.

### 3.1 Propagação do trace header

Para o trace não “quebrar” entre serviços, o **trace ID viaja** junto com a requisição, no header HTTP **`X-Amzn-Trace-Id`**:

```
X-Amzn-Trace-Id: Root=1-5759e988-bd862e3fe1be46a994272793;Parent=53995c3f42cd8ad8;Sampled=1
```

- **Root**: o trace ID.
- **Parent**: o segmento que está chamando.
- **Sampled**: se aquela requisição foi **amostrada** (1) ou não (0) — decisão de *sampling* tomada na borda e propagada.

Em fluxos assíncronos (SQS, SNS, EventBridge, Step Functions), a propagação depende de **atributos do sistema** (por exemplo, `AWSTraceHeader` em mensagens SQS) ou de instrumentação específica; um trace pode se “partir” em vários se a propagação não for suportada — veja a seção de troubleshooting.

## 4. O service map

O **service map** é um grafo **gerado automaticamente** a partir dos traces: cada **nó** é um serviço/recurso e cada **aresta** é uma chamada entre eles. Em cada nó você enxerga:

- **Latência média/percentis** e distribuição.
- **Taxa de requisições** e de **erros (4xx), falhas (5xx) e throttling (429)**, geralmente coloridos (verde/amarelo/vermelho/roxo).
- Clique no nó → **traces** relacionados.

É a resposta à pergunta “quem chama quem, de verdade?”. Em arquiteturas de microsserviços, é frequentemente a **primeira tela de investigação**: o nó vermelho indica onde começar.

## 5. Quando usar X-Ray (e quando não)

| Pergunta | Melhor ferramenta |
|---|---|
| “A CPU do servidor está alta?” | **Métrica** (CloudWatch) |
| “Qual a mensagem de erro dessa exceção?” | **Log** (CloudWatch Logs) |
| “**Em qual dos 8 serviços** esta requisição específica perdeu 2 s?” | **X-Ray / trace** |
| “Quais dependências meu serviço realmente tem?” | **X-Ray (service map)** |
| “Quem executou `DeleteBucket`?” | **CloudTrail** |
| “O recurso mudou de configuração?” | **AWS Config** |
| “Uma requisição de um cliente específico falhou — mostre o caminho” | **X-Ray + annotations** |

**Os três pilares se complementam:** o trace aponta o serviço e o trecho; o **log** dá o detalhe do erro (idealmente com o **trace ID no log** para correlação); a **métrica** dispara o alarme que leva você até lá.

### 5.1 X-Ray e o ecossistema de observabilidade da AWS

- **CloudWatch** integra X-Ray em **ServiceLens/Application Signals** (visão unificada de traces, métricas e logs; confirmar nomenclatura atual).
- **OpenTelemetry** é o padrão aberto de instrumentação; o X-Ray funciona como **backend** de traces OTel via ADOT/OTLP (confirmar o suporte OTLP direto atual).
- Alternativas fora da AWS: Jaeger, Zipkin, Datadog, New Relic, Grafana Tempo. O X-Ray vence em **integração nativa com serviços AWS** e simplicidade; perde em recursos avançados de análise e retenção longa frente a plataformas dedicadas.

## 6. Limites e características a conhecer

| Característica | Valor/nota (de memória — confirmar) |
|---|---|
| **Retenção dos traces** | Aproximadamente **30 dias** |
| **Dados enviados** | Segmentos em lotes; o daemon agrupa e reenvia |
| **Sampling** | Por padrão, uma **amostra** (ex.: 1 requisição por segundo + 5% do restante); configurável por regras |
| **Tamanho do segment document** | Limitado (ordem de dezenas de KB) |
| **Anotações indexadas** | Limite por trace/segmento |
| **Granularidade temporal** | Segmentos têm marcadores de início/fim; necessária **sincronia de relógio** razoável entre hosts |

## 7. Exemplo guiado: investigando uma lentidão

Cenário: usuários reclamam que “criar pedido” demora 4 segundos às vezes.

1. **Service map**: o nó `criar-pedido` está amarelo; a aresta para `api.pagamentos.com` mostra latência alta.
2. **Filter expression** (próxima seção do curso): `service("criar-pedido") { duration > 3 }` lista só os traces lentos.
3. **Abrir um trace**: o subsegment `HTTPS api.pagamentos.com` consome 3,4 s; DynamoDB e SQS ficam em milissegundos.
4. **Annotation** `tenant=acme` aparece em todos os traces lentos → o problema é a integração de **um cliente específico**.
5. **Conclusão**: não é capacidade da sua infraestrutura; é o parceiro de pagamento para esse tenant. Ação: *timeout* + *retry* com *backoff*, e abrir chamado com o parceiro, anexando trace IDs como evidência.

Sem tracing, os mesmos achados exigiriam correlacionar manualmente logs de 4 serviços por timestamp — e provavelmente não chegariam à anotação do tenant.

## 8. Comandos úteis (ilustrativos, não executados)

```bash
# Resumos de traces nas últimas horas, com filtro de lentidão
aws xray get-trace-summaries \
  --start-time $(date -u -d '-1 hour' +%s) --end-time $(date -u +%s) \
  --filter-expression 'duration > 3'

# Detalhar traces específicos
aws xray batch-get-traces --trace-ids 1-67a1b2c3-1234567890abcdef12345678

# Grafo do service map no período
aws xray get-service-graph --start-time <epoch> --end-time <epoch>
```

## 9. Erros comuns

- **Achar que o X-Ray rastreia tudo automaticamente**: serviços AWS geram parte do trace, mas **o código da sua aplicação precisa ser instrumentado** (SDK/OTel) para aparecerem subsegmentos de chamadas externas e do seu código.
- **Esquecer a propagação do trace header** em chamadas HTTP próprias → trace quebrado em vários.
- **Colocar dados sensíveis em annotations/metadata** → exposição no console e em exportações.
- **Confiar em 100% de cobertura**: com **sampling**, nem toda requisição é gravada; para investigar um erro raro, ajuste regras de amostragem.
- **Usar como substituto de logs**: o trace tem pouco texto; sem logs você sabe *onde*, mas nem sempre *por quê*.
- **Relógios dessincronizados** entre hosts distorcem durações e a ordem dos subsegmentos.

## 10. Troubleshooting inicial

| Sintoma | Causas prováveis | Ações |
|---|---|---|
| Nenhum trace aparece | Tracing não habilitado; sem permissão IAM; daemon/collector ausente; região errada | Habilitar active tracing; checar role com `xray:PutTraceSegments`; ver logs do daemon |
| Trace “cortado” no meio | Serviço intermediário não propaga `X-Amzn-Trace-Id`; chamada assíncrona sem suporte | Instrumentar o salto; usar `AWSTraceHeader` no SQS; revisar o middleware |
| Apenas parte das requisições aparece | **Sampling** por padrão | Criar regra de amostragem para a rota/serviço de interesse |
| Mapa mostra serviço desconhecido (“cliente”) | Nó de origem sem instrumentação | Instrumentar o cliente ou aceitar o nó como “Client” |
| Durações negativas/estranhas | Clock skew entre hosts | Sincronizar NTP/Chrony |

## 11. Resumo rápido

- X-Ray = **rastreamento distribuído**: **trace** (uma requisição) → **segments** (por serviço) → **subsegments** (detalhes).
- **Service map** gerado automaticamente; mostra latência, erros, falhas e throttling.
- **Annotations** (indexadas, filtráveis) vs **metadata** (não indexados).
- Dados chegam via **SDK/OTel → daemon/ADOT → API do X-Ray**; propagação por **`X-Amzn-Trace-Id`**.
- **Sampling** limita o volume; retenção de ~30 dias.
- Complementa **logs** (detalhe) e **métricas** (agregado); recomendação atual: instrumentar com **OpenTelemetry/ADOT**.

## 🧩 Quiz de Fixação

1. Qual a diferença entre trace, segment e subsegment?
2. Quando usar annotation em vez de metadata?
3. Por que o trace pode ficar “quebrado” em chamadas assíncronas?
4. O que o header `X-Amzn-Trace-Id` carrega?
5. Por que nem toda requisição aparece no X-Ray por padrão?
6. Que perguntas o service map responde que logs e métricas respondem mal?
7. Por que não colocar dados pessoais em annotations?

**Respostas:**

1. Trace é a requisição inteira (um trace ID); segment é a parte gerada por um serviço/recurso; subsegment detalha chamadas ou trechos dentro de um segment.
2. Quando for filtrar/buscar por esse valor (annotation é indexada); metadata serve só para contexto visível ao abrir o trace.
3. Porque o trace ID precisa ser propagado (atributos de sistema, como `AWSTraceHeader` no SQS, ou instrumentação específica); sem isso o fluxo vira traces separados.
4. O trace ID (`Root`), o segmento pai (`Parent`) e a decisão de amostragem (`Sampled`).
5. Porque o X-Ray usa amostragem (sampling) para controlar volume e custo; regras podem aumentar a cobertura.
6. Quem chama quem na prática, em que serviço/trecho uma requisição específica perdeu tempo e quais dependências realmente existem.
7. Porque annotations são indexadas e visíveis no console/exportações, expondo dados sensíveis a quem tem acesso ao X-Ray.
