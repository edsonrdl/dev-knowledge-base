### 4.1.1.1. Sampling e integrações do X-Ray — regras de amostragem, API Gateway, Lambda, SNS e SQS, ALB, Step Functions e CloudWatch

> [!warning] Aviso
> Valores padrão de amostragem, campos das regras, quotas e o suporte de cada integração (SNS, EventBridge, Step Functions, ALB) são **de memória e mudam**. **Confirme na documentação do X-Ray e de cada serviço integrado.** JSONs e comandos são ilustrativos e **não foram executados**.

## 1. Por que amostrar

Gravar **cada** requisição de uma API com 5.000 req/s geraria um volume e um **custo** desproporcionais ao valor analítico: a 100ª requisição idêntica raramente ensina algo novo. O **sampling** (amostragem) grava uma **fração representativa** dos traces, mantendo o custo previsível e ainda permitindo enxergar padrões.

```
100% das requisições ──▶ [decisão de amostragem na borda] ──▶ N% rastreadas ──▶ X-Ray
                                   │
                       decisão propagada no header (Sampled=1/0)
```

Pontos centrais:

- A **decisão é tomada uma vez**, no **início da requisição** (primeiro serviço instrumentado), e **propagada** (`Sampled=1`/`0` no `X-Amzn-Trace-Id`). Assim o trace é **inteiro ou nada** — nunca pela metade por causa do sampling.
- Requisições **não amostradas** não geram segmentos gravados (mas ainda podem gerar métricas em outros serviços, como CloudWatch).

## 2. Regras de amostragem (sampling rules)

### 2.1 Comportamento padrão

Por padrão (de memória — confirmar), o X-Ray usa a regra **default**: **1 requisição por segundo (reservoir)** + **5% das requisições adicionais (fixed rate)** por host/serviço. Isso garante **pelo menos um trace por segundo** mesmo com pouco tráfego e limita o volume em picos.

### 2.2 Anatomia de uma regra

| Campo | Função |
|---|---|
| **RuleName** | Nome da regra |
| **Priority** | Número menor = avaliada primeiro; a **primeira regra que casa vence** |
| **ReservoirSize** | Nº de requisições **por segundo** garantidamente amostradas (compartilhado entre todos os hosts da regra) |
| **FixedRate** | Fração (0 a 1) das requisições **restantes** que também são amostradas |
| **ServiceName / ServiceType** | Casa com o nome/tipo do serviço |
| **Host / HTTPMethod / URLPath** | Casam com atributos HTTP (aceitam curingas `*`, `?`) |
| **ResourceARN** | Casa com o ARN do recurso (ex.: função Lambda) |
| **Attributes** | Casa com **annotations**/atributos do segmento |

```json
{
  "SamplingRule": {
    "RuleName": "checkout-alta-fidelidade",
    "Priority": 10,
    "FixedRate": 0.5,
    "ReservoirSize": 5,
    "ServiceName": "checkout",
    "ServiceType": "*",
    "Host": "*",
    "HTTPMethod": "POST",
    "URLPath": "/checkout/*",
    "ResourceARN": "*",
    "Version": 1
  }
}
```

```bash
aws xray create-sampling-rule --cli-input-json file://regra-checkout.json
aws xray get-sampling-rules
aws xray update-sampling-rule --sampling-rule-update '{"RuleName":"checkout-alta-fidelidade","FixedRate":0.1}'
aws xray delete-sampling-rule --rule-name checkout-alta-fidelidade
```

### 2.3 Como a taxa é calculada (modelo mental)

```
Para cada requisição que casa com a regra:
  1) Há "cota do reservoir" disponível neste segundo?  ──sim──▶ AMOSTRA
  2) Senão: sorteia com probabilidade = FixedRate     ──────▶ AMOSTRA ou NÃO
```

Exemplo: reservoir=5, fixed rate=10%; 100 requisições no segundo → as 5 primeiras são amostradas; das 95 restantes, ~9,5 → **~14,5 traces/s**.

> [!info] Cota distribuída
> O X-Ray **reparte o reservoir** entre os hosts que reportam à regra; a aplicação/daemon busca periodicamente as regras e **cotas** (`GetSamplingRules`/`GetSamplingTargets`), por isso mudanças em regras levam alguns segundos/minutos para valer e **não exigem redeploy**.

### 2.4 Estratégias recomendadas

| Cenário | Regra sugerida |
|---|---|
| **Health checks** barulhentos (`/health`) | `FixedRate=0`, `ReservoirSize=0` — não gastar traces |
| **Fluxos críticos** (checkout, login) | Reservoir e fixed rate **mais altos** |
| **Rotas de baixo tráfego e alto valor** | Reservoir ≥ 1 para garantir visibilidade |
| **Depuração temporária** de um tenant | Regra com `Attributes` (`tenant=acme`) a 100% por um período, depois removida |
| **Ambiente de homologação** | Taxas altas (volume pequeno) |
| **Pico de tráfego/custos** | Reduzir fixed rate global; manter reservoir |

Ordem de prioridade importa: regras **mais específicas com prioridade menor** (número menor) antes da regra **geral**.

### 2.5 Sampling no Lambda e em outros ambientes

- **Lambda (Active tracing)**: o Lambda segue a decisão que vem no header; se **ele** inicia o trace, aplica uma taxa própria (de memória, **1 req/s + 5%**, não ajustável como as regras do daemon — confirmar). Para controle fino, use **API Gateway/ALB** na frente ou **OTel com sampler**.
- **OpenTelemetry**: o **sampler** pode ser configurado no SDK (*parent-based*, *trace ID ratio*) ou — com o **ADOT** — buscar as **regras remotas do X-Ray** (*X-Ray remote sampler*; confirmar suporte por linguagem).
- **Amostragem no collector (tail sampling)**: o ADOT/OTel Collector permite decidir **depois** de ver o trace inteiro (ex.: manter todos os traces com erro) — mais poderoso, porém exige mais memória e um ponto central de coleta.

## 3. Head sampling vs tail sampling

| | **Head sampling** (X-Ray padrão) | **Tail sampling** (collector) |
|---|---|---|
| Decisão | No **início** da requisição | **Após** o trace completo |
| Custo/complexidade | Baixo | Mais alto (buffer, roteamento por trace ID) |
| Captura erros raros? | Só por sorte/regra | **Sim** (mantém 100% dos traces com erro/lentos) |
| Previsibilidade | Alta | Depende das políticas |

Observação importante: **X-Ray nativo usa head sampling**. Se o requisito é “guardar todos os traces com erro”, as saídas são **tail sampling no collector** (e/ou enviar métricas de erro por outro caminho) — confirmar as capacidades atuais.

## 4. Integrações com serviços AWS

### 4.1 Tabela geral (de memória — confirmar cada uma)

| Serviço | Como integra | Observações |
|---|---|---|
| **API Gateway (REST)** | Habilitar **tracing no estágio** | Gera segmento do gateway; injeta/propaga header; suporta regras de amostragem |
| **API Gateway (HTTP API)** | Suporte a X-Ray **limitado/diferente** do REST | Confirmar; alternativa: logs de acesso + propagação pelo backend |
| **AWS Lambda** | **Active tracing** (por função) | Segmentos de *Invocation* e *Initialization*; precisa de role com escrita |
| **Application Load Balancer** | Adiciona/propaga `X-Amzn-Trace-Id` | O ALB **não** emite segmento próprio como o API Gateway; é usado para correlação (de memória — confirmar) |
| **Amazon SQS** | Atributo de sistema `AWSTraceHeader` | Lambda consumidor continua o trace |
| **Amazon SNS** | Propagação do trace para alvos suportados (ex.: SQS, Lambda) | Habilitar tracing no tópico (**Active**) — confirmar |
| **Amazon EventBridge** | Propagação do header do evento para alvos suportados | Confirmar por alvo |
| **AWS Step Functions** | Habilitar tracing na máquina de estados | Mostra estados como nós/subsegmentos e liga aos Lambdas |
| **Amazon ECS/EKS/EC2** | Daemon/collector + SDK/OTel | Ver folha de instrumentação |
| **AWS App Mesh** | Envoy gera segmentos | Serviço em **descontinuação** anunciada — confirmar status antes de adotar |
| **Elastic Beanstalk** | Opção da plataforma para o daemon | Simples para apps tradicionais |
| **AWS AppSync** | Tracing habilitável na API | Confirmar |
| **Amazon DynamoDB/S3 etc.** | **Subsegmentos criados pelo cliente instrumentado** | O serviço em si não emite segmento; o trace mostra a chamada vista pelo cliente |

### 4.2 Padrão típico: API Gateway → Lambda → SQS → Lambda

1. Habilite o tracing no **estágio** do API Gateway.
2. `Tracing: Active` nos dois Lambdas.
3. Produtor com SDK/OTel envia a mensagem; o **`AWSTraceHeader`** acompanha.
4. Resultado: um único trace da chamada HTTP até o processamento assíncrono (se todos os saltos suportarem).

```yaml
# SAM (ilustrativo)
Resources:
  Api:
    Type: AWS::Serverless::Api
    Properties:
      StageName: prod
      TracingEnabled: true
  Produtor:
    Type: AWS::Serverless::Function
    Properties:
      Tracing: Active
      Events: { Post: { Type: Api, Properties: { RestApiId: !Ref Api, Path: /pedidos, Method: post } } }
  Consumidor:
    Type: AWS::Serverless::Function
    Properties:
      Tracing: Active
      Events: { Fila: { Type: SQS, Properties: { Queue: !GetAtt Fila.Arn } } }
```

### 4.3 CloudWatch: ServiceLens, Application Signals e correlação

- **Correlação traces ↔ logs ↔ métricas**: no console do CloudWatch (ServiceLens/Application Signals; confirmar nomes atuais) você parte de um nó/trace e pula para logs e métricas da mesma janela.
- **Logs com trace ID**: use o **formato JSON** com campo `trace_id` (Lambda e bibliotecas de logging estruturado podem injetá-lo) para a pesquisa no CloudWatch Logs Insights:

```
fields @timestamp, @message
| filter trace_id = "1-67a1b2c3-1234567890abcdef12345678"
| sort @timestamp asc
```

- **Métricas de grupo** do X-Ray (por grupo) alimentam **alarmes** do CloudWatch (ver a folha de operação).

### 4.4 EventBridge e eventos de aplicação

Mesmo sem propagação nativa para um alvo, você pode **carregar o trace ID no payload** (campo `trace_id`/`traceHeader`) e, no consumidor, **retomar o contexto manualmente** — padrão para brokers sem suporte (Kafka, filas de terceiros).

## 7. Erros comuns

- **Deixar a regra default** em tudo e ficar sem traces de rotas raras ou com custo alto em rotas barulhentas.
- **Prioridade invertida**: regra geral com número menor que a específica → a específica **nunca é avaliada**.
- **Health checks consumindo reservoir**: sem regra para `/health`, o ALB “gasta” seus traces.
- **Assumir tail sampling no X-Ray nativo**: ele não está disponível sem collector.
- **Habilitar tracing só no Lambda** e esquecer o API Gateway (ou o contrário) → trace sem começo ou sem meio.
- **Assumir que SNS/EventBridge/Kafka propagam** sem testar → traces quebrados.
- **Depuração com 100% e esquecer de remover** → custo inesperado.
- **Confiar nas contagens do X-Ray como volume real** (são amostras).

## 8. Troubleshooting

| Sintoma | Causa provável | Ação |
|---|---|---|
| Rota rara nunca aparece | Fixed rate baixo e reservoir consumido por rotas barulhentas | Regra dedicada com reservoir ≥ 1 e prioridade baixa (número menor) |
| Regra nova “não pega” | Prioridade, curingas ou nome do serviço divergentes | Conferir `ServiceName` exato, `URLPath` e prioridade |
| Custo subiu | Fixed rate alto, depuração esquecida, muitos hosts com reservoir | Reduzir taxas, revisar `get-sampling-statistic-summaries` |
| Trace termina no SQS | Consumidor sem tracing ou sem `AWSTraceHeader` | Habilitar Active no consumidor; instrumentar produtor |
| Gateway sem segmento | Tracing não habilitado no estágio (ou HTTP API) | Habilitar no estágio; para HTTP API, usar alternativa |
| Traces de erro raros ausentes | Head sampling | Tail sampling no collector ou regras por atributo |

## 9. Resumo rápido

- **Sampling** controla custo/volume; decisão **na borda** e **propagada** → trace inteiro ou nada.
- **Regra padrão**: ~**1 req/s + 5%**; regras personalizadas: **Priority, ReservoirSize, FixedRate** e critérios de correspondência.
- **Primeira regra que casa vence** (prioridade menor primeiro); mudanças valem sem redeploy.
- **Head sampling** nativo; **tail sampling** só com **collector**.
- Integrações: **API Gateway (estágio)**, **Lambda (Active)**, **SQS (`AWSTraceHeader`)**, SNS/EventBridge/Step Functions (confirmar), **ALB (header)**.
- **Trace ID nos logs** + grupos → métricas e alarmes no CloudWatch.

## 🧩 Quiz de Fixação

1. O que significam `ReservoirSize` e `FixedRate` em uma regra?
2. Por que a decisão de amostragem é propagada no header?
3. Que regra você criaria para `/health`?
4. Qual a diferença entre head e tail sampling?
5. Por que a prioridade das regras importa?
6. Como ligar o trace do API Gateway ao processamento assíncrono via SQS?
7. Por que as contagens do X-Ray não equivalem ao total de requisições?

**Respostas:**

1. Reservoir é o número de requisições por segundo sempre amostradas; fixed rate é a fração das requisições restantes que também são amostradas.
2. Para que todos os serviços sigam a mesma decisão e o trace seja gravado inteiro ou não gravado, nunca pela metade.
3. Uma regra de prioridade alta (número baixo) com reservoir 0 e fixed rate 0 para a URL de health check, evitando gastar traces.
4. Head decide no início da requisição; tail decide depois de ver o trace completo (permite guardar todos os traces com erro), mas exige um collector.
5. Porque a primeira regra que casa vence; uma regra geral com prioridade menor que a específica impede a específica de ser avaliada.
6. Habilitando tracing no estágio e nos Lambdas e garantindo a propagação do `AWSTraceHeader` na mensagem SQS.
7. Porque apenas uma amostra das requisições é gravada; volumes reais vêm de métricas do CloudWatch.
