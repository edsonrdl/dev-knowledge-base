### 2.1.1.1. Instrumentação com X-Ray — X-Ray SDK, daemon, ADOT e OpenTelemetry, Lambda, ECS, EKS e EC2, propagação do trace header e anotações

> [!warning] Aviso
> Nomes de pacotes, versões, variáveis de ambiente, portas e o estado de suporte dos SDKs do X-Ray (manutenção) vs **OpenTelemetry/ADOT** são **de memória e mudam**. **Confirme na documentação oficial do X-Ray e do AWS Distro for OpenTelemetry antes de adotar.** Comandos, YAMLs e trechos de código são ilustrativos e **não foram executados**.

## 1. As três camadas da instrumentação

Para um trace existir, três coisas precisam acontecer:

```
[1] GERAR  ──▶  [2] COLETAR/ENCAMINHAR  ──▶  [3] ENVIAR AO X-RAY
 (SDK/OTel)       (daemon ou ADOT Collector)     (API PutTraceSegments / OTLP)
```

1. **Gerar** segmentos no código: bibliotecas (SDK do X-Ray ou **OpenTelemetry**) interceptam requisições HTTP, clientes AWS, drivers de banco e criam segmentos/subsegmentos.
2. **Coletar e encaminhar**: um processo **local** (daemon do X-Ray ou **ADOT Collector**) recebe os dados da aplicação e os envia em lote — a aplicação não precisa de credenciais nem lidar com retentativas de rede.
3. **Enviar** à API do X-Ray com credenciais IAM (do host/tarefa/pod/função).

Serviços gerenciados (API Gateway, Lambda, App Mesh etc.) pulam as camadas 2 e 3 para os segmentos **deles**: enviam diretamente quando o tracing está habilitado.

## 2. Duas famílias de instrumentação

| | **SDKs do X-Ray** | **OpenTelemetry (ADOT)** |
|---|---|---|
| Origem | Próprios da AWS (Java, Node.js, Python, .NET, Go, Ruby) | Padrão aberto (CNCF); a AWS distribui o **ADOT** |
| Portabilidade | Presa ao X-Ray | **Neutra de fornecedor** — mesmo código serve a X-Ray, Jaeger, Datadog etc. |
| Auto-instrumentação | Limitada, por biblioteca | Ampla (agentes e bibliotecas para muitas stacks) |
| Direção da AWS | **Modo de manutenção** (de memória — confirmar data e política) | **Caminho recomendado** |
| Quando usar | Código legado já instrumentado | **Projetos novos** |

> [!tip] Decisão prática
> **Projeto novo → OpenTelemetry/ADOT.** Código antigo com SDK do X-Ray continua funcionando; planeje migração ao ritmo das refatorações, mantendo o **mesmo formato de trace ID** (o ADOT gera IDs compatíveis com X-Ray quando configurado com o *ID generator* apropriado).

## 3. O X-Ray daemon

O **daemon** é um processo (código aberto) que:

- **Escuta** em **UDP porta 2000** (por padrão) os segmentos enviados pelo SDK;
- **Agrupa** em lotes e **envia por HTTPS** à API do X-Ray;
- Usa as credenciais **da instância/tarefa/pod** (role IAM) — a aplicação em si pode não ter credencial nenhuma;
- Em Lambda, o daemon é **embutido no ambiente de execução** (você não o instala).

Onde roda:

| Ambiente | Como o daemon/collector entra |
|---|---|
| **EC2** | Instalar como serviço (systemd) ou rodar em container; role da instância com permissão de escrita |
| **Elastic Beanstalk** | Opção de configuração que habilita o daemon na plataforma |
| **ECS** | **Container sidecar** na task definition (`amazon/aws-xray-daemon` ou ADOT collector) |
| **EKS** | **DaemonSet** (um por nó) ou **sidecar**; permissões via **IRSA/Pod Identity** |
| **Lambda** | Embutido; habilitar *active tracing* |
| **On-premises** | Daemon/collector com credenciais configuradas (perfil/roles anywhere) |

## 4. Instrumentando no código (SDK do X-Ray — exemplos)

### 4.1 Python (ilustrativo)

```python
from aws_xray_sdk.core import xray_recorder, patch_all
from aws_xray_sdk.core import xray_recorder as rec

patch_all()   # instrumenta boto3, requests, drivers SQL comuns, etc.

@xray_recorder.capture('calcular-frete')
def calcular_frete(pedido):
    seg = xray_recorder.current_subsegment()
    seg.put_annotation('tenant', pedido['tenant'])     # indexado
    seg.put_metadata('carrinho', pedido['itens'])      # contexto
    ...
```

### 4.2 Node.js (ilustrativo)

```javascript
const AWSXRay = require('aws-xray-sdk');
const AWS = AWSXRay.captureAWS(require('aws-sdk'));   // clientes AWS ganham subsegmentos
AWSXRay.captureHTTPsGlobal(require('https'));          // chamadas HTTPS ganham subsegmentos

app.use(AWSXRay.express.openSegment('app-pedidos'));
// ... rotas ...
app.use(AWSXRay.express.closeSegment());
```

### 4.3 O que a “captura” faz

Ao *patchar* um cliente (por exemplo, `boto3`/AWS SDK), cada chamada vira um **subsegmento** com nome do serviço, operação, tempo, `request_id`, status HTTP e exceções — sem você escrever código para cada chamada.

## 5. Instrumentando com OpenTelemetry/ADOT

Fluxo típico:

```
App (OTel SDK/agent) ──OTLP (gRPC 4317 / HTTP 4318)──▶ ADOT Collector ──▶ X-Ray (exporter awsxray)
```

Exemplo de **configuração do collector** (ilustrativo):

```yaml
receivers:
  otlp:
    protocols:
      grpc: { endpoint: 0.0.0.0:4317 }
      http: { endpoint: 0.0.0.0:4318 }
processors:
  batch: {}
exporters:
  awsxray:
    region: us-east-1
service:
  pipelines:
    traces:
      receivers: [otlp]
      processors: [batch]
      exporters: [awsxray]
```

Pontos de atenção:

- **ID generator compatível com X-Ray**: o trace ID do X-Ray embute o **timestamp** nos primeiros bytes; o OTel precisa gerar IDs nesse formato (extensão `AWSXRayIdGenerator`) para o X-Ray aceitar os traces.
- **Propagador**: habilitar o *propagator* do X-Ray (`xray`) para ler/escrever `X-Amzn-Trace-Id`, além do `W3C tracecontext` — convivência entre os dois facilita integração com serviços AWS e fora dela.
- **Auto-instrumentação por agente**: em Java, um *javaagent*; em Python/Node, pacotes `opentelemetry-instrument`/`@opentelemetry/auto-instrumentations-node`. Reduz código, mas confirme compatibilidade com frameworks.
- **ADOT em Lambda**: **Lambda Layer** gerenciada com collector embutido (`ADOT Lambda layer`); alternativa à *active tracing* nativa quando se quer OTel completo.

## 6. Lambda

### 6.1 Active tracing

```bash
# Habilitar tracing ativo (ilustrativo)
aws lambda update-function-configuration \
  --function-name criar-pedido --tracing-config Mode=Active
```

Em SAM/CloudFormation:

```yaml
Resources:
  CriarPedido:
    Type: AWS::Serverless::Function
    Properties:
      Tracing: Active          # Lambda gera segmentos e o segmento de Initialization
      Policies:
        - AWSXRayDaemonWriteAccess   # ou permissão equivalente (a role de execução precisa de escrita)
```

- Com **Active**, o Lambda cria o **segmento da função** (Invocation) e, quando aplicável, o de **Initialization** (cold start). Com **PassThrough**, só propaga se a requisição já vier amostrada.
- **Subsegmentos do seu código** (chamadas AWS, HTTP) exigem **SDK/OTel dentro da função**.
- A role de execução precisa de **`xray:PutTraceSegments`** e **`xray:PutTelemetryRecords`**.

### 6.2 API Gateway → Lambda

Habilite o tracing no **estágio** do API Gateway; o gateway inicia o trace e injeta o header, que o Lambda continua. Resultado: um trace único mostrando **latência do gateway**, **integração** e **função**.

## 7. ECS, EKS e EC2

### 7.1 ECS (sidecar)

```json
{
  "containerDefinitions": [
    { "name": "app", "image": "123456789012.dkr.ecr.us-east-1.amazonaws.com/pedidos:1.4.2",
      "environment": [ { "name": "AWS_XRAY_DAEMON_ADDRESS", "value": "xray-daemon:2000" } ],
      "links": ["xray-daemon"] },
    { "name": "xray-daemon", "image": "public.ecr.aws/xray/aws-xray-daemon:latest",
      "portMappings": [ { "containerPort": 2000, "protocol": "udp" } ] }
  ]
}
```

A **task role** (não a execution role) precisa da permissão de escrita no X-Ray. Em Fargate (modo `awsvpc`), o sidecar fica em `localhost:2000`.

### 7.2 EKS

- **DaemonSet** do collector/daemon por nó **ou** sidecar por pod.
- Permissão via **IRSA** (IAM Roles for Service Accounts) ou **EKS Pod Identity**.
- Alternativa: o **CloudWatch agent / add-on ADOT** gerenciado do EKS (confirmar disponibilidade e nome atual).

### 7.3 EC2

- Instalar o daemon (pacote/script) e rodá-lo como serviço; a **instance profile** deve permitir a escrita.
- Para auto-scaling, empacote o daemon na AMI/launch template.

## 8. Propagação do trace header

Regra de ouro: **todo salto precisa levar o `X-Amzn-Trace-Id` adiante.**

| Salto | Como propaga |
|---|---|
| HTTP síncrono entre serviços | SDK/OTel injeta o header nas chamadas de saída e o lê nas de entrada |
| ALB → aplicação | O ALB **adiciona** `X-Amzn-Trace-Id` (e pode gerar segmentos de roteamento conforme integração); a app deve **continuar** o trace |
| SQS | Atributo de sistema **`AWSTraceHeader`** (o Lambda consumidor continua o trace se estiver habilitado) |
| SNS / EventBridge | Suporte à propagação para alguns alvos — **confirmar por integração** |
| Step Functions | Suporta X-Ray por máquina de estados |
| Kafka/outros brokers | Normalmente **instrumentação manual**: colocar o contexto em headers da mensagem |

Se um salto não propaga, o trace **se parte**: você verá dois traces independentes em vez de um.

## 9. Boas práticas de anotações e nomes

- **Nome do segmento = nome do serviço** (estável, sem versão/ID). Nomes variáveis poluem o service map.
- **Annotations de negócio de baixa cardinalidade** (tenant, plano, região, canal, versão do deploy): úteis para filtrar e para criar **grupos**.
- **Evite alta cardinalidade** (ID de usuário único, ID de pedido) como annotation indexada; use **metadata** ou logue o ID e correlacione pelo trace ID.
- **Inclua o trace ID nos logs** (campo `trace_id`) para pular de um trace ao log exato e vice-versa.
- **Não coloque PII/segredos** em annotations/metadata.

## 10. Exemplo de ponta a ponta

```
Cliente ─▶ API Gateway (tracing no estágio) ─▶ Lambda criar-pedido (Active + ADOT layer ou SDK)
                                                  ├─▶ DynamoDB       (subsegmento via instrumentação do cliente AWS)
                                                  ├─▶ SQS            (propaga AWSTraceHeader)
                                                  └─▶ HTTPS parceiro (subsegmento HTTP)
                                  SQS ─▶ Lambda processar-pedido (continua o mesmo trace)
```

Resultado: um **service map** com API Gateway → Lambda → (DynamoDB, SQS, parceiro) → Lambda, com latência e erros por aresta.

## 11. Comandos de apoio (ilustrativos, não executados)

```bash
# Conferir se o daemon está recebendo (logs)
journalctl -u xray -n 50

# Testar permissão de escrita (simulação IAM)
aws iam simulate-principal-policy --policy-source-arn <role-arn> \
  --action-names xray:PutTraceSegments xray:PutTelemetryRecords

# Ver a configuração de tracing do Lambda
aws lambda get-function-configuration --function-name criar-pedido --query TracingConfig
```

## 12. Erros comuns

- **Instrumentar só o serviço de entrada**: o mapa mostra um único nó; cada serviço precisa de instrumentação.
- **Daemon sem rede/porta**: UDP 2000 bloqueado entre containers (security group/NetworkPolicy) → traces somem em silêncio.
- **Role errada no ECS** (execution role em vez de **task role**): sem permissão de escrita.
- **ID generator incompatível** no OTel: o X-Ray rejeita segmentos com IDs fora do formato.
- **Misturar SDK do X-Ray e OTel** no mesmo processo sem planejar: segmentos duplicados ou contexto conflitante.
- **Esquecer de habilitar tracing no estágio do API Gateway**: o trace começa no Lambda, sem a visão do gateway.
- **Annotations de alta cardinalidade** em excesso: estouram limites e dificultam análise.

## 13. Troubleshooting

| Sintoma | Verificar | Ação |
|---|---|---|
| Sem traces do container | Daemon/collector rodando? Endereço (`AWS_XRAY_DAEMON_ADDRESS`)? UDP liberado? | Corrigir sidecar, rede e variável |
| Lambda sem subsegmentos de DynamoDB | Código instrumentado? | Adicionar SDK/OTel e *patch* do cliente |
| `AccessDenied` nos logs do daemon | Role tem `PutTraceSegments`/`PutTelemetryRecords`? | Anexar permissão à role correta |
| Traces duplicados | Dois SDKs/agents ativos | Escolher um caminho de instrumentação |
| Trace não continua após SQS | `AWSTraceHeader` ausente; consumidor sem tracing | Habilitar tracing no consumidor; instrumentar produtor |
| IDs recusados | Formato do trace ID | Configurar `AWSXRayIdGenerator` no OTel |

## 14. Resumo rápido

- Instrumentação = **gerar** (SDK/OTel) → **coletar** (daemon/ADOT) → **enviar** (API do X-Ray).
- **Projetos novos: OpenTelemetry/ADOT**; SDKs do X-Ray em **manutenção** (confirmar).
- Daemon: **UDP 2000**, role IAM no host/tarefa/pod; em **Lambda** é embutido (**Active tracing**).
- ECS: **sidecar** + **task role**; EKS: **DaemonSet/sidecar** + IRSA/Pod Identity.
- **Propague `X-Amzn-Trace-Id`** em todo salto; SQS usa `AWSTraceHeader`.
- Annotations de **baixa cardinalidade**; trace ID nos **logs**.

## 🧩 Quiz de Fixação

1. Quais as três camadas necessárias para um trace chegar ao X-Ray?
2. Por que o ADOT precisa de um ID generator compatível com X-Ray?
3. Em ECS, qual role precisa da permissão de escrita no X-Ray?
4. O que muda entre `Active` e `PassThrough` no tracing do Lambda?
5. Como o trace continua através do SQS?
6. Por que evitar annotations de alta cardinalidade?
7. Qual a recomendação atual entre SDK do X-Ray e OpenTelemetry para projetos novos?

**Respostas:**

1. Gerar (SDK/OTel), coletar/encaminhar (daemon ou ADOT Collector) e enviar à API do X-Ray.
2. Porque o trace ID do X-Ray embute o timestamp e o serviço rejeita IDs fora do formato esperado.
3. A task role (não a execution role).
4. Em Active o Lambda cria os segmentos e inicia/amostra o trace; em PassThrough só propaga se a requisição já vier amostrada.
5. Pelo atributo de sistema `AWSTraceHeader` na mensagem, desde que produtor e consumidor suportem/habilitem o tracing.
6. Porque as annotations são indexadas e limitadas; muitos valores únicos poluem o índice e dificultam filtros e grupos.
7. Usar OpenTelemetry/ADOT; os SDKs do X-Ray estão em modo de manutenção (confirmar a política atual).
