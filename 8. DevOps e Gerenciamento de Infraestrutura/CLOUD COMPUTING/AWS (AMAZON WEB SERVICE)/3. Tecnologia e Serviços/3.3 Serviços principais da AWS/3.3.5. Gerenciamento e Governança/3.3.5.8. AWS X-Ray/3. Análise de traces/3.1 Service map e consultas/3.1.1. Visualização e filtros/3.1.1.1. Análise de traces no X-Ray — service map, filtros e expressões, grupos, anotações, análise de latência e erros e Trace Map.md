### 3.1.1.1. Análise de traces no X-Ray — service map, filtros e expressões, grupos, anotações, análise de latência e erros e Trace Map

> [!warning] Aviso
> Nomes de telas, sintaxe de *filter expressions*, limites de grupos e recursos de análise (Analytics, Trace Map, integração com CloudWatch) são **de memória e a console muda com frequência**. **Confirme na documentação do X-Ray.** Comandos e expressões são ilustrativos e **não foram executados**.

## 1. Do dado bruto à resposta

Ter traces não resolve nada se você não souber **fazer perguntas** a eles. O X-Ray oferece um funil de investigação:

```
Service map (quem está doente?) ─▶ Traces (quais requisições?) ─▶ Trace detail (onde exatamente?) ─▶ Logs/Métricas (por quê?)
        │                                  │
        └── Grupos (recortes salvos) ──────┘      Analytics/Insights (padrões e anomalias)
```

## 2. Service map em profundidade

### 2.1 Como ler o mapa

| Elemento | Significado |
|---|---|
| **Nó** | Serviço/recurso (Lambda, API Gateway, tabela DynamoDB, serviço HTTP externo, “Client”) |
| **Aresta** | Chamada de um nó para outro |
| **Cor do nó/anel** | Proporção de respostas **OK (2xx)**, **erros do cliente (4xx)**, **falhas (5xx)** e **throttling** |
| **Tempo médio / p50–p99** | Latência do nó e da aresta |
| **Taxa de requisições** | Requisições por minuto/segundo no intervalo escolhido |

Convenções de cor comuns (confirmar na console): **verde** = ok, **vermelho** = falhas 5xx, **amarelo** = erros 4xx, **roxo** = throttling.

### 2.2 Perguntas típicas respondidas pelo mapa

1. **Onde está o gargalo?** O nó com maior latência relativa.
2. **Quem está causando as falhas?** Siga as arestas vermelhas até o nó **mais profundo** que falha — a causa-raiz costuma estar na ponta, e os nós acima só **propagam**.
3. **Há dependência inesperada?** Uma aresta que não está no diagrama de arquitetura.
4. **Um deploy mudou o perfil?** Compare intervalos de tempo antes/depois.

### 2.3 Janela de tempo e filtros no mapa

O mapa depende do **intervalo** selecionado (últimos 5 minutos, 1 hora, personalizado). Para uma regressão recente, use janelas curtas; para tendência, janelas longas. Também é possível **filtrar por grupo** ou expressão para ver só parte do tráfego (por exemplo, só o tenant `acme`).

## 3. Filter expressions

Uma **filter expression** é a linguagem de consulta para selecionar traces. Pode ser usada no console, na CLI (`--filter-expression`) e em **grupos**.

### 3.1 Palavras-chave comuns

| Palavra-chave | Exemplo | Seleciona |
|---|---|---|
| **`responsetime` / `duration`** | `duration >= 5` | Traces com duração ≥ 5 s |
| **`http.status`** | `http.status = 500` | Requisições com status 500 |
| **`http.url`** | `http.url CONTAINS "/pedidos"` | URL que contém o trecho |
| **`http.method`** | `http.method = "POST"` | Método HTTP |
| **`error` / `fault` / `throttle`** | `fault = true` | Falhas 5xx; erros 4xx; throttling |
| **`ok`** | `ok = true` | Respostas sem erro |
| **`service()`** | `service("criar-pedido")` | Traces que passam por esse serviço |
| **`edge()`** | `edge("api-gateway","criar-pedido")` | Traces que atravessam essa aresta |
| **`annotation.<chave>`** | `annotation.tenant = "acme"` | Filtra por annotation indexada |
| **`user`** | `user = "joao"` | Se o `user` foi registrado no segment |
| **`id(...)`** | `id(trace_id)` | Trace específico |

### 3.2 Combinando

```
service("criar-pedido") AND annotation.tenant = "acme" AND duration > 3
service("criar-pedido") { fault = true AND http.status = 502 }     # bloco: condições no mesmo serviço
(http.status = 500 OR http.status = 503) AND annotation.versao = "v42"
responsetime > 2 AND http.url CONTAINS "/checkout" AND NOT annotation.canary = "true"
```

> [!tip] Dica
> Use o **bloco `service("x") { ... }`** quando a condição precisa valer **dentro do mesmo serviço**; sem o bloco, as condições podem ser satisfeitas por serviços diferentes no mesmo trace.

### 3.3 Pela CLI

```bash
aws xray get-trace-summaries \
  --start-time 2026-11-10T10:00:00Z --end-time 2026-11-10T11:00:00Z \
  --filter-expression 'annotation.tenant = "acme" AND duration > 3' \
  --sampling   # opcional: considera a amostragem para estatísticas
```

O `get-trace-summaries` devolve **metadados** (ID, duração, status, annotations, erros); `batch-get-traces` traz os **documentos completos**.

## 4. Grupos

Um **grupo** é um **filtro nomeado e persistente** (filter expression + nome) aplicado de forma contínua:

- O console permite **ver o mapa e os traces só do grupo**.
- O X-Ray **publica métricas no CloudWatch por grupo** (taxas de sucesso, erro, falha, throttling, latência) — base para **alarmes** (ver a folha de operação).
- O número de grupos tem **limite** (de memória, da ordem de dezenas; confirmar na documentação de quotas).

```bash
aws xray create-group --group-name tenant-acme \
  --filter-expression 'annotation.tenant = "acme"'
aws xray create-group --group-name checkout-falhas \
  --filter-expression 'service("checkout") { fault = true }'
aws xray get-groups
```

Casos de uso:

| Grupo | Expressão | Para quê |
|---|---|---|
| `canary` | `annotation.deploy = "canary"` | Comparar a versão nova com a estável |
| `tenant-premium` | `annotation.plano = "premium"` | SLO diferenciado para clientes premium |
| `erros-pagamento` | `service("pagamentos") { error = true OR fault = true }` | Alarme dedicado |
| `lentos` | `duration >= 3` | Acompanhar a cauda de latência |

## 5. Anotações como eixo de análise

Anotações são o que transforma o X-Ray de “mapa bonito” em **ferramenta de diagnóstico de negócio**:

| Annotation | Pergunta respondida |
|---|---|
| `versao` / `deploy_id` | O erro começou com qual release? |
| `tenant` / `plano` | O problema afeta quem? |
| `regiao` / `az` | É local a uma região ou AZ? |
| `feature_flag` | A funcionalidade nova degrada a latência? |
| `canal` (app, web, parceiro) | O canal influencia o desempenho? |

Procedimento clássico de **comparação**: crie dois grupos (`versao = "v41"` e `versao = "v42"`) e compare latência e taxa de falha lado a lado.

## 6. Analisando latência

### 6.1 Distribuição de tempo de resposta

O X-Ray mostra um **histograma de latência**: onde a maioria das requisições está e como é a **cauda** (p95/p99). Médias escondem problemas — uma média de 200 ms com p99 de 6 s significa que **1% dos usuários tem uma experiência péssima**.

### 6.2 Anatomia de um trace lento

Ao abrir o trace (linha do tempo em cascata):

- **Barras longas e sequenciais** → trabalho serial que poderia ser **paralelizado**.
- **Barra de Initialization** grande no Lambda → **cold start**.
- **Subsegmento de um serviço AWS com muita latência e `throttle`** → limite de capacidade (DynamoDB, por exemplo).
- **Lacunas sem subsegmento** → tempo gasto no **seu código** ou espera por um recurso não instrumentado; instrumente mais trechos.
- **Muitos subsegmentos idênticos** → padrão **N+1** (muitas chamadas pequenas em loop).

### 6.3 Exemplo de leitura

```
criar-pedido  ████████████████████████████████████████ 3,9 s
  ├ Initialization  ████ 0,5 s                         (cold start)
  ├ DynamoDB GetItem █ 20 ms
  ├ DynamoDB GetItem █ 22 ms     × 40 vezes seguidas   (N+1!)
  └ HTTPS parceiro   ████████████████ 2,6 s            (dependência lenta)
```

Duas descobertas: um N+1 contra o DynamoDB (pode virar `BatchGetItem`) e um parceiro lento (timeout/retry/circuit breaker).

## 7. Analisando erros e falhas

| Flag no segmento | Significado | Onde costuma estar a causa |
|---|---|---|
| `error` | Erro **do cliente** (4xx) | Entrada inválida, autenticação, regra de negócio |
| `fault` | Erro **do servidor** (5xx/exceção) | Bug, dependência indisponível, timeout |
| `throttle` | **429/limite** | Cota/capacidade (Lambda concurrency, DynamoDB, API Gateway) |

No trace, a seção **Exceptions** mostra **pilha de exceção** (quando capturada pelo SDK/OTel), mensagem e o subsegmento em que ocorreu. Combine com o **log** da mesma execução (via trace ID) para o contexto completo.

> [!info] Propagação de falhas
> Uma falha profunda “pinta” o caminho acima dela: o gateway devolve 502 porque o Lambda falhou porque o parceiro deu timeout. Siga **para o nó mais interno** com `fault`.

## 8. Analytics e Trace Map

- **X-Ray Analytics** (console): exploração **interativa** sobre os traces filtrados — distribuições por **annotation, URL, status, usuário**, comparação entre dois conjuntos (*compare*), identificação de **qual atributo explica a diferença de latência**.
- **Trace Map / ServiceLens (via CloudWatch)**: a visão unificada que liga **mapa**, **traces**, **métricas** e **logs** no console do CloudWatch (confirmar nomenclatura: ServiceLens/Application Signals/Trace Map).
- **Insights**: detecção automática de anomalias (próxima folha).

Uso sugerido do **compare**: selecione “traces lentos” (A) vs “todos” (B) e veja que `annotation.tenant = acme` é super-representado em A.

## 9. Fluxo de investigação (runbook)

1. **Alarme** (CloudWatch) dispara: p95 do grupo `checkout` acima do limite.
2. Abra o **service map** filtrado pelo grupo `checkout`; identifique o nó/aresta vermelha ou amarela.
3. Liste traces com `service("checkout") { duration > 3 }`.
4. **Compare** com o intervalo anterior (antes do deploy) e por annotations (`versao`, `tenant`, `az`).
5. Abra **2–3 traces** representativos; identifique o subsegmento dominante.
6. Pegue o **trace ID** → procure nos **logs** da aplicação/dependência.
7. Registre o achado (trace IDs como evidência), aplique mitigação (rollback, timeout, capacidade) e **valide no mapa**.

## 11. Erros comuns

- **Olhar só a média** de latência e ignorar p95/p99.
- **Culpar o nó de cima**: tratar o gateway como causa quando a falha nasce dois saltos abaixo.
- **Filter expression sem bloco `service(){}`** e concluir algo errado por condições espalhadas entre serviços.
- **Annotations ausentes**: sem `tenant`/`versao`, cada investigação vira adivinhação.
- **Janela de tempo inadequada**: mapa de 5 minutos para uma regressão de dias (ou o contrário).
- **Ignorar o sampling**: contagens do X-Ray refletem a amostra, **não** o total real de requisições (use métricas do CloudWatch para volumes exatos).
- **Excesso de grupos** ou grupos com expressões caras sem necessidade.

## 12. Troubleshooting

| Sintoma | Causa provável | Ação |
|---|---|---|
| Filtro não retorna nada | Annotation não indexada (era metadata) ou nome errado | Conferir `put_annotation` e a grafia da chave |
| Mapa vazio no período | Fora da retenção, sampling baixo, tracing desligado | Ampliar janela; revisar sampling e habilitação |
| Latência do nó difere do que o usuário sente | Tempo de rede/cliente não está no trace | Instrumentar o cliente (RUM) ou comparar com métricas do ALB |
| Grupo não gera métricas | Sem tráfego amostrado ou notificações desabilitadas | Verificar a configuração de insights/métricas do grupo |
| Exceção sem pilha | SDK/OTel não capturou a exceção | Habilitar captura; registrar `record_exception` |

## 13. Resumo rápido

- Funil: **mapa → traces → detalhe → logs**.
- Mapa: **nós/arestas** com latência e proporção ok/erro/falha/throttle; siga a falha até o **nó mais interno**.
- **Filter expressions** (`service()`, `edge()`, `annotation.*`, `duration`, `fault`) e blocos `{}` para condições no mesmo serviço.
- **Grupos** = filtros salvos que viram **métricas e alarmes** no CloudWatch.
- **Annotations** (`versao`, `tenant`) permitem comparar releases e clientes; **Analytics/compare** isola atributos que explicam a lentidão.
- Contagens refletem a **amostra**; use p95/p99, não só a média.

## 🧩 Quiz de Fixação

1. Que diferença há entre `error`, `fault` e `throttle`?
2. Por que usar o bloco `service("x") { ... }` numa expressão?
3. Para que servem os grupos além de filtrar o console?
4. Como o X-Ray ajuda a identificar um padrão N+1?
5. Por que a média de latência pode enganar?
6. Qual a ordem recomendada de investigação ao receber um alarme de latência?
7. Por que contagens do X-Ray não representam o total real de requisições?

**Respostas:**

1. `error` = erros do cliente (4xx); `fault` = falhas do servidor (5xx/exceções); `throttle` = limitação (429).
2. Para exigir que todas as condições valham dentro do mesmo serviço, evitando que sejam satisfeitas por serviços diferentes do mesmo trace.
3. Publicam métricas no CloudWatch por grupo, permitindo alarmes e acompanhamento contínuo de taxa de sucesso, erro, falha e latência.
4. O trace mostra muitos subsegmentos idênticos e sequenciais (por exemplo, dezenas de `GetItem` seguidos).
5. Porque esconde a cauda (p95/p99): poucos usuários podem ter tempos péssimos mesmo com média baixa.
6. Mapa filtrado pelo grupo, listagem de traces lentos, comparação por annotations/janelas, abertura de traces representativos, busca nos logs pelo trace ID e validação da mitigação.
7. Porque há amostragem (sampling): apenas parte das requisições é gravada; volumes exatos vêm de métricas do CloudWatch.
