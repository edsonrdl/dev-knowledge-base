### Métricas do CloudWatch — namespaces, dimensões, resolução, métricas customizadas, EMF, Metric Math e retenção

> [!warning] Aviso
> Limites de dimensões, resolução, retenção, preços e formato do EMF mudam. Os números aqui são referências de estudo; confirme na documentação. Os comandos **não foram executados**.

As **métricas** são a base do CloudWatch: **séries temporais** de valores numéricos que descrevem o comportamento de um recurso ao longo do tempo. Entender como elas são **nomeadas, dimensionadas, agregadas e cobradas** evita os erros mais comuns: consultas vazias, custos inesperados e gráficos enganosos.

**Analogia:** uma métrica é como o **diário de um termômetro**. Cada linha registra *quando* foi medido e *quanto* marcou. O **namespace** é a "estação meteorológica", o **nome** é "temperatura" e as **dimensões** dizem "qual termômetro" (sala, cozinha, jardim). Sem dizer qual termômetro, você não sabe qual diário abrir.

---

## Anatomia de uma métrica

```
 Namespace:  AWS/EC2
 Nome:       CPUUtilization
 Dimensões:  InstanceId = i-0123456789abcdef0
 Unidade:    Percent
 Pontos:     (12:00, 41.2) (12:05, 44.8) (12:10, 87.3) ...
```

| Elemento | Regras e dicas |
|---|---|
| **Namespace** | Obrigatório; serviços AWS usam `AWS/<Serviço>`; os seus **não podem** começar com `AWS/` |
| **Nome** | Descreve a medida; mantenha padrão (`PedidosProcessados`) |
| **Dimensões** | Até um número limitado por métrica; cada **combinação** única cria uma série |
| **Unidade** | Opcional mas recomendada; facilita gráficos e alarmes |
| **Timestamp** | Aceita dados de até algumas semanas no passado e poucas horas no futuro (referência) |
| **Valor** | Número; também aceita **conjuntos estatísticos** (min, max, soma, contagem) |

> [!tip] Cuidado com a cardinalidade
> Cada combinação distinta de dimensões é **uma métrica separada e cobrada**. Usar `UserId` ou `RequestId` como dimensão cria milhões de séries e uma conta enorme. Dimensões devem ter **poucos valores possíveis** (ambiente, serviço, região, endpoint).

## Estatísticas e períodos

O CloudWatch **agrega** os pontos brutos em janelas (**períodos**) usando uma **estatística**.

| Estatística | Quando usar |
|---|---|
| **Average** | Tendência geral (CPU média) |
| **Sum** | Totais (requisições, erros) |
| **Minimum / Maximum** | Extremos, detecção de picos |
| **SampleCount** | Quantas amostras entraram no período |
| **Percentis (p50, p90, p99)** | Latência e experiência real do usuário |

```
 Latências no período (ms):  50 52 49 51 48 50 900 53
 Average = 156   ← esconde o problema
 p50     = 51    ← experiência típica
 p99     = ~900  ← revela a cauda ruim
```

> [!warning] Média engana
> Para latência, prefira **p90/p99** e alarme sobre eles. A média de um sistema com algumas requisições muito lentas parece saudável.

O **período** deve ser múltiplo de 60 s (ou 1, 5, 10, 30 s para alta resolução). Um período menor que a frequência de publicação gera pontos "buracos" (sem dados).

## Métricas padrão e frequência

| Serviço | Frequência típica | Observação |
|---|---|---|
| EC2 | 5 min (1 min com monitoramento detalhado) | Sem memória/disco por padrão |
| Lambda, ALB, API Gateway, DynamoDB | ~1 min | Publicadas automaticamente |
| S3 | Diária (storage) / 1 min (request metrics opcionais) | Request metrics exigem habilitar |
| RDS | 1 min (Enhanced Monitoring para SO) | Enhanced Monitoring é opcional |

## Métricas customizadas

Qualquer aplicação pode publicar **suas próprias métricas** (negócio ou técnicas):

```bash
# Publica uma métrica de negócio
aws cloudwatch put-metric-data \
  --namespace MeuApp/Pedidos \
  --metric-name PedidosProcessados \
  --dimensions Ambiente=producao,Servico=checkout \
  --unit Count --value 42

# Publica com resolução de 1 segundo (alta resolução)
aws cloudwatch put-metric-data \
  --namespace MeuApp/Latencia --metric-name Tempo --unit Milliseconds \
  --value 120 --storage-resolution 1
```

| Tipo | Resolução | Custo | Quando usar |
|---|---|---|---|
| **Padrão** | 60 s | Menor | Maioria dos casos |
| **Alta resolução** | 1 s | Maior; alarmes de alta resolução têm preço próprio | Picos curtos e reação rápida |

> [!tip] Agregue antes de enviar
> Publicar um ponto por requisição gera chamadas e custo demais. Agregue na aplicação (contagem, soma, min, max por minuto) e envie **conjuntos estatísticos**, ou use o **EMF**.

## Embedded Metric Format (EMF)

O **EMF** permite publicar métricas **escrevendo um log JSON em formato especial**; o CloudWatch extrai as métricas automaticamente dos logs, sem chamar `PutMetricData`. É ideal para **Lambda** e containers, onde fazer chamadas síncronas de API é caro.

```json
{
  "_aws": {
    "Timestamp": 1731153600000,
    "CloudWatchMetrics": [{
      "Namespace": "MeuApp/Checkout",
      "Dimensions": [["Servico", "Ambiente"]],
      "Metrics": [{"Name": "TempoPagamento", "Unit": "Milliseconds"}]
    }]
  },
  "Servico": "checkout",
  "Ambiente": "producao",
  "TempoPagamento": 183,
  "RequestId": "abc-123"
}
```

| Vantagem | Observação |
|---|---|
| Log **e** métrica no mesmo evento | Alta cardinalidade fica no log (RequestId), não na dimensão |
| Sem latência extra de API | Escrita no stdout/log basta |
| Consulta detalhada com Logs Insights | Métrica para alarme, log para investigar |

## Metric Math

**Metric Math** permite calcular **novas séries** a partir de outras, em gráficos e alarmes.

| Expressão | Resultado |
|---|---|
| `m1 / m2 * 100` | Taxa percentual (erros ÷ requisições) |
| `SUM(METRICS())` | Soma de várias métricas selecionadas |
| `RATE(m1)` | Taxa de variação por segundo |
| `FILL(m1, 0)` | Preenche buracos com zero |
| `ANOMALY_DETECTION_BAND(m1, 2)` | Banda de comportamento esperado |
| `IF(m1 > 80, 1, 0)` | Lógica condicional |

```bash
# Alarme de taxa de erro: 5xx / total
aws cloudwatch put-metric-alarm --alarm-name taxa-erro-alta \
  --evaluation-periods 3 --threshold 1 \
  --comparison-operator GreaterThanThreshold \
  --metrics '[
    {"Id":"erros","MetricStat":{"Metric":{"Namespace":"AWS/ApplicationELB",
      "MetricName":"HTTPCode_Target_5XX_Count",
      "Dimensions":[{"Name":"LoadBalancer","Value":"app/meu-alb/abc"}]},
      "Period":60,"Stat":"Sum"},"ReturnData":false},
    {"Id":"total","MetricStat":{"Metric":{"Namespace":"AWS/ApplicationELB",
      "MetricName":"RequestCount",
      "Dimensions":[{"Name":"LoadBalancer","Value":"app/meu-alb/abc"}]},
      "Period":60,"Stat":"Sum"},"ReturnData":false},
    {"Id":"taxa","Expression":"100 * erros / total","Label":"% de erro"}
  ]'
```

> [!tip] Taxas são melhores que contagens
> Alarmar em "5% de erros" continua válido quando o tráfego dobra; "100 erros" não.

## Métricas do CloudWatch Agent

Para ver **memória, disco, swap e processos** em EC2 ou servidores locais, instale o **CloudWatch Agent** e configure o arquivo JSON:

```json
{
  "metrics": {
    "namespace": "CWAgent",
    "append_dimensions": {"InstanceId": "${aws:InstanceId}"},
    "metrics_collected": {
      "mem":  {"measurement": ["mem_used_percent"]},
      "disk": {"measurement": ["used_percent"], "resources": ["/"]}
    }
  }
}
```

As métricas aparecem no namespace **`CWAgent`** (ou o que você definir). A instância precisa de um **perfil IAM** com permissão de publicação (política gerenciada de servidor do agente).

## Retenção e agregação ao longo do tempo

| Resolução do ponto | Retenção (referência) |
|---|---|
| < 60 s | ~3 horas |
| 60 s | ~15 dias |
| 5 min | ~63 dias |
| 1 hora | ~455 dias (15 meses) |

Os dados são **consolidados automaticamente**: após 15 dias você só tem pontos de 5 minutos. Para guardar dados brutos por mais tempo, exporte por **Metric Streams** (para S3/Firehose) ou armazene em outro sistema.

## Exemplo prático: métrica de negócio com alarme

1. A API emite EMF a cada pedido concluído, com dimensões `Servico` e `Ambiente`.
2. A métrica `PedidosProcessados` (Sum por minuto) alimenta um dashboard.
3. Um alarme usa **anomaly detection** para avisar se os pedidos caírem fora do padrão da semana.
4. Outro alarme usa Metric Math (`erros/total`) para taxa de falha de pagamentos acima de 2%.
5. O `RequestId` fica só no log, para investigação com Logs Insights.

## Consultando métricas com GetMetricData

Para dashboards e automações, `get-metric-data` é preferível a `get-metric-statistics`: permite **várias métricas e expressões numa chamada**.

```bash
aws cloudwatch get-metric-data \
  --start-time 2026-11-09T10:00:00Z --end-time 2026-11-09T12:00:00Z \
  --metric-data-queries '[
    {"Id":"cpu","MetricStat":{"Metric":{"Namespace":"AWS/EC2",
       "MetricName":"CPUUtilization",
       "Dimensions":[{"Name":"InstanceId","Value":"i-0123456789abcdef0"}]},
       "Period":300,"Stat":"Maximum"}}
  ]'
```

| Recurso | Benefício |
|---|---|
| `SEARCH('{AWS/EC2,InstanceId} CPUUtilization', 'Average', 300)` | Descobre métricas dinamicamente, sem listar IDs |
| Várias consultas por chamada | Menos chamadas e menos throttling |
| Paginação (`NextToken`) | Lida com grandes volumes de pontos |

### Métricas de serviços AWS que vale conhecer

| Serviço | Métrica | O que indica |
|---|---|---|
| **Lambda** | `Errors`, `Throttles`, `Duration` | Falhas, limite de concorrência, lentidão |
| **SQS** | `ApproximateAgeOfOldestMessage` | Fila atrasada, consumidores lentos |
| **RDS** | `DatabaseConnections`, `FreeStorageSpace` | Saturação de conexões e disco |
| **DynamoDB** | `ThrottledRequests` | Capacidade insuficiente |
| **ALB** | `UnHealthyHostCount` | Alvos reprovados no health check |

Conhecer essas métricas evita criar métricas customizadas para algo que a AWS já publica de graça.

### Checklist antes de publicar uma métrica nova

1. O nome é claro e consistente com as demais?
2. A unidade está definida?
3. As dimensões têm poucos valores possíveis?
4. Alguém vai alarmar ou visualizar? (se ninguém usar, não publique)
5. A resolução (1 s vs 60 s) é realmente necessária?

## Erros comuns e armadilhas

- **Dimensão de alta cardinalidade** (`UserId`) que explode o custo.
- **Consultar a região, namespace ou dimensão erradas** e ver "sem dados".
- **Usar Average para latência** em vez de percentis.
- **Publicar um ponto por requisição** em vez de agregar ou usar EMF.
- **Esperar memória/disco de EC2** sem instalar o agente.
- **Esquecer que dados antigos perdem resolução** ao fazer análises históricas.
- **Alarmar contagens absolutas** que não acompanham o crescimento do tráfego.
- **Namespace iniciando com `AWS/`** para métricas próprias (não permitido).

## 🧩 Quiz de Fixação

1. O que forma a identidade de uma métrica?
2. Por que evitar `UserId` como dimensão?
3. Qual estatística melhor revela a cauda de latência?
4. O que é o EMF e quando é útil?
5. Para que serve Metric Math em alarmes?
6. Que ferramenta traz memória e disco do EC2 para o CloudWatch?

**Respostas:**
1) Namespace, nome da métrica e conjunto de dimensões (a unidade acompanha a medida).
2) Cada combinação de dimensões é uma série separada e cobrada; alta cardinalidade gera milhões de séries e custo alto.
3) Percentis como p99 (ou p95), pois a média esconde valores extremos.
4) Embedded Metric Format: escrever logs JSON especiais dos quais o CloudWatch extrai métricas automaticamente, sem chamar PutMetricData; ótimo para Lambda e containers.
5) Para criar séries calculadas, como taxa de erro (erros ÷ total), e alarmar sobre elas.
6) O CloudWatch Agent.
