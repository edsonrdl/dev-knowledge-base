### CloudWatch Logs — log groups e streams, retenção, metric filters, subscription filters, Logs Insights e agente

> [!warning] Aviso
> Preços de ingestão e armazenamento, classes de log, limites de tamanho de evento, sintaxe de consulta e recursos mudam. Os números aqui são referências de estudo; confirme na documentação. Os comandos **não foram executados**.

O **CloudWatch Logs** centraliza **logs de aplicações, sistemas e serviços AWS** em um lugar só, com armazenamento durável, busca, análise e integração com alarmes e outros serviços. Em vez de entrar por SSH em cada servidor para ler arquivos, você **envia os logs** para o CloudWatch e os consulta de forma central.

**Analogia:** é o **arquivo central de uma redação**. Cada repórter (aplicação) entrega suas anotações (eventos) em pastas organizadas (log groups e streams); o arquivo define por quanto tempo guardar (retenção), permite buscar rapidamente (Insights), marcar certas palavras para contagem (metric filters) e copiar o fluxo para outros departamentos (subscription filters).

---

## Hierarquia: group, stream e evento

```
 Log group: /producao/api                 ← retenção, KMS, permissões, classe
   ├─ Log stream: i-0abc/2026-11-09       ← uma origem (instância, container, invocação)
   │     ├─ evento {timestamp, mensagem}
   │     └─ evento ...
   └─ Log stream: i-0def/2026-11-09
```

| Conceito | Descrição | Dica |
|---|---|---|
| **Log event** | Um registro com timestamp e mensagem | Limite de tamanho por evento (referência: ~256 KB) |
| **Log stream** | Sequência de eventos de uma **mesma origem** | Um por instância/container |
| **Log group** | Conjunto de streams com **mesmas configurações** | Um por aplicação/ambiente |

As **configurações** (retenção, criptografia, filtros, permissões) são do **log group**, não do stream.

## Retenção e classes de armazenamento

| Aspecto | Detalhe |
|---|---|
| **Retenção** | Por log group: de 1 dia a vários anos, ou **nunca expirar** (padrão) |
| **Classe Standard** | Todos os recursos (Insights, filtros, assinaturas) |
| **Classe Infrequent Access** | Ingestão mais barata, com menos recursos; para logs consultados raramente |
| **Exportação para S3** | Arquivar logs antigos a custo menor (`create-export-task`) |
| **Criptografia** | Padrão do serviço ou chave **KMS** do cliente |

```bash
# Define retenção de 30 dias
aws logs put-retention-policy --log-group-name /producao/api --retention-in-days 30

# Cria o log group com classe e KMS (exemplo)
aws logs create-log-group --log-group-name /producao/api \
  --log-group-class STANDARD
```

> [!warning] O padrão "nunca expira" é a maior fonte de custo oculto
> Defina retenção em **todos** os log groups (incluindo os criados automaticamente por Lambda). Revise periodicamente com um script que liste grupos sem retenção.

## Como os logs chegam

| Origem | Mecanismo |
|---|---|
| **Lambda** | Automático: `/aws/lambda/<função>` |
| **ECS/Fargate/Batch** | Driver `awslogs` na definição do container |
| **EKS** | Fluent Bit / CloudWatch Agent (Container Insights) |
| **EC2 / on-premises** | **CloudWatch Agent** lendo arquivos de log |
| **API Gateway, CloudTrail, Route 53, VPC Flow Logs, RDS** | Opção de publicar no CloudWatch Logs |
| **Aplicação via SDK** | `PutLogEvents` |

### Configuração do agente para arquivos

```json
{
  "logs": {
    "logs_collected": {
      "files": {
        "collect_list": [
          {
            "file_path": "/var/log/app/*.log",
            "log_group_name": "/producao/api",
            "log_stream_name": "{instance_id}",
            "retention_in_days": 30
          }
        ]
      }
    }
  }
}
```

A instância precisa de um **perfil IAM** que permita `logs:CreateLogStream` e `logs:PutLogEvents`.

## Logs estruturados (JSON)

Logs em **JSON** são muito mais fáceis de consultar que texto livre.

```json
{"ts":"2026-11-09T12:00:01Z","nivel":"ERROR","servico":"checkout",
 "requestId":"abc-123","duracao_ms":812,"mensagem":"falha ao cobrar"}
```

| Benefício | Efeito |
|---|---|
| Campos descobertos automaticamente | Filtros e consultas por campo no Logs Insights |
| Correlação | `requestId` liga logs de serviços diferentes |
| Métricas via EMF | Extrai métricas do próprio log |
| Menos regex frágil | Consultas estáveis |

## Metric filters

Um **metric filter** observa os eventos que chegam e **incrementa uma métrica** quando encontra um padrão — transformando logs em números que podem ter alarmes.

```bash
aws logs put-metric-filter \
  --log-group-name /producao/api \
  --filter-name erros-aplicacao \
  --filter-pattern '{ $.nivel = "ERROR" }' \
  --metric-transformations \
    metricName=ErrosAplicacao,metricNamespace=MeuApp,metricValue=1,defaultValue=0
```

| Padrão | Exemplo |
|---|---|
| Termo simples | `ERROR` |
| JSON | `{ $.nivel = "ERROR" && $.duracao_ms > 500 }` |
| Texto delimitado (espaços) | `[ip, user, ts, req, status=5*, size]` |

> [!tip] Defina `defaultValue = 0`
> Sem valor padrão, a métrica só existe quando há erro; combine com `TreatMissingData` adequado no alarme.

## Subscription filters: enviando logs para outros destinos

Um **subscription filter** entrega, **quase em tempo real**, os eventos de um log group para outro destino.

| Destino | Uso |
|---|---|
| **Kinesis Data Streams / Firehose** | Análise em fluxo, entrega em S3, OpenSearch, Splunk |
| **Lambda** | Processar e reagir a eventos |
| **Outro log group/conta** (via destino) | Centralização entre contas |

```
 /producao/api ──► subscription filter (padrão "ERROR") ──► Firehose ──► S3 (data lake)
                                                      └───► Lambda ──► abre ticket
```

Cada log group tem um **número pequeno de subscription filters** permitido; planeje a arquitetura de fan-out com Kinesis/Firehose se precisar de vários consumidores.

## CloudWatch Logs Insights

Linguagem de consulta interativa, executada sobre os log groups escolhidos e o intervalo de tempo.

```
fields @timestamp, requestId, duracao_ms, mensagem
| filter nivel = "ERROR" and duracao_ms > 500
| stats count() as erros, avg(duracao_ms) as media by bin(5m)
| sort @timestamp desc
| limit 50
```

| Comando | Função |
|---|---|
| `fields` | Escolhe campos a exibir |
| `filter` | Filtra eventos |
| `stats` | Agrega (count, avg, sum, pct) |
| `sort`, `limit` | Ordena e limita |
| `parse` | Extrai campos de texto com regex/padrão |
| `dedup` | Remove duplicados |
| `pattern`/`diff` | Detecta padrões e compara períodos |

```bash
aws logs start-query \
  --log-group-names /producao/api \
  --start-time 1731150000 --end-time 1731153600 \
  --query-string 'fields @timestamp,@message | filter @message like /ERROR/ | limit 20'
aws logs get-query-results --query-id <id>
```

> [!warning] Insights cobra por dado escaneado
> Restrinja o **intervalo de tempo** e os **log groups** e use `filter` cedo na consulta. Varrer 90 dias de logs de dezenas de grupos pode custar caro.

## Live Tail e acompanhamento em tempo real

```bash
aws logs tail /producao/api --since 10m --follow --filter-pattern ERROR
```

O **Live Tail** (console/CLI) mostra eventos **conforme chegam**, útil em deploys e depuração. Não substitui consultas analíticas.

## Proteção de dados sensíveis

| Recurso | Função |
|---|---|
| **Data protection policies** | Detectam e **mascaram** dados sensíveis (cartões, CPFs, chaves) nos logs |
| **KMS** | Criptografia do log group com chave própria |
| **Políticas de recurso** | Controle de quem escreve/lê |
| **Não logar segredos** | A melhor proteção: nunca imprimir senhas e tokens |

## Exemplo prático: do log ao alarme e ao arquivo

1. A API escreve logs JSON em `/producao/api` (retenção 30 dias).
2. Um **metric filter** gera `ErrosAplicacao`; um **alarme** avisa se passar de 20/min.
3. Um **subscription filter** envia tudo via **Firehose** para um bucket S3 (arquivo de longo prazo e Athena).
4. No incidente, o time usa **Logs Insights** agrupando erros por `servico` e `requestId`.
5. Logs com mais de 30 dias saem do CloudWatch, mas continuam no S3 por custo menor.

## Troubleshooting

| Sintoma | Causa provável | Como resolver |
|---|---|---|
| Logs não aparecem | Perfil IAM sem `PutLogEvents` ou agente parado | Revisar role e status do agente |
| Lambda sem logs | Role de execução sem permissão de logs | Anexar política básica de execução |
| Consulta lenta/cara | Intervalo grande, filtros tardios | Reduzir tempo e grupos; filtrar primeiro |
| Metric filter sem dados | Padrão não casa com o formato | Testar padrão no console |
| Subscription falha | Permissão do destino/limite | Verificar role e quotas |
| Custo crescente | Sem retenção, logs verbosos | Definir retenção; reduzir nível de log |

## Consultas Insights prontas para o dia a dia

```
# Top 10 erros mais frequentes
fields @message
| filter @message like /ERROR/
| stats count() as ocorrencias by @message
| sort ocorrencias desc
| limit 10

# Latência p50/p90/p99 por serviço
stats pct(duracao_ms, 50) as p50, pct(duracao_ms, 90) as p90,
      pct(duracao_ms, 99) as p99 by servico

# Invocações Lambda mais lentas e memória usada
filter @type = "REPORT"
| fields @requestId, @duration, @maxMemoryUsed/1000000 as memMB
| sort @duration desc
| limit 20
```

| Situação | Consulta |
|---|---|
| Pico de erros | `stats count() by bin(1m)` com `filter` de nível |
| Correlacionar requisição | `filter requestId = "abc-123"` em vários grupos |
| Custo de Lambda | Comparar `@maxMemoryUsed` com a memória configurada |

> [!tip] Salve consultas
> Consultas usadas em incidentes devem ser **salvas** (ou versionadas como IaC) e linkadas nos runbooks, para não serem reescritas sob pressão.

## Erros comuns e armadilhas

- **Deixar retenção em "nunca expirar".**
- **Logar em DEBUG em produção** e pagar ingestão enorme.
- **Texto livre** sem estrutura, dificultando consulta.
- **Registrar dados sensíveis** (senhas, cartões).
- **Insights em períodos e grupos amplos** sem filtro.
- **Metric filter sem `defaultValue`** e alarmes mudos.
- **Esquecer a região** do log group.
- **Usar logs como banco de dados** de eventos de negócio em vez de armazenamento apropriado.

## 🧩 Quiz de Fixação

1. Qual a relação entre log group, log stream e log event?
2. Onde ficam configurações como retenção e KMS?
3. O que faz um metric filter?
4. Para que serve um subscription filter?
5. Por que o Logs Insights pode ficar caro?
6. Qual a ferramenta para enviar arquivos de log do EC2?

**Respostas:**
1) O log group agrupa streams com as mesmas configurações; cada stream é a sequência de eventos de uma origem; o evento é um registro com timestamp e mensagem.
2) No log group.
3) Observa os eventos que chegam e incrementa uma métrica quando encontra um padrão, permitindo criar alarmes sobre logs.
4) Entregar, quase em tempo real, os eventos de um log group a destinos como Kinesis, Firehose ou Lambda, inclusive entre contas.
5) Porque é cobrado por dado escaneado; períodos longos e muitos grupos sem filtro aumentam o volume.
6) O CloudWatch Agent.
