### Observabilidade avançada — dashboards, Container Insights, Lambda Insights, Synthetics, RUM, Application Signals e X-Ray

> [!warning] Aviso
> Nomes de produtos, recursos, preços e integrações da família de observabilidade do CloudWatch evoluem rápido. Os números e capacidades aqui são referências de estudo; confirme na documentação. Os comandos **não foram executados**.

Além de métricas, logs e alarmes, o CloudWatch oferece uma **camada de observabilidade** que **junta os sinais** em visões prontas: **dashboards** para painéis, **Insights** para containers e funções, **Synthetics** e **RUM** para a perspectiva do usuário e **Application Signals** com **X-Ray** para acompanhar requisições entre serviços. O objetivo é sair de "o que está vermelho?" para "**onde** e **por que** está lento?".

**Analogia:** se métricas e logs são os **exames** de um paciente, esta camada é o **prontuário integrado**: gráficos consolidados (dashboards), monitor cardíaco por sistema (Insights), um **paciente-teste** que visita a clínica a cada minuto para ver se o atendimento funciona (Synthetics) e o **mapa do caminho** que o paciente percorre entre setores (traces).

---

## Visão geral da camada

```
        Experiência do usuário
   RUM (usuários reais)    Synthetics (canários)
             │                     │
             ▼                     ▼
     Application Signals  ──►  Traces (X-Ray / OpenTelemetry)
             │                     │
             ▼                     ▼
   Container Insights   Lambda Insights   Database Insights ...
             │
             ▼
   Métricas + Logs + Alarmes  ──►  DASHBOARDS
```

| Recurso | Pergunta que responde |
|---|---|
| **Dashboards** | Qual o estado geral em uma tela? |
| **Container Insights** | Como estão meus clusters, serviços e pods? |
| **Lambda Insights** | Por que minha função está lenta ou cara? |
| **Synthetics** | O fluxo crítico funciona agora, visto de fora? |
| **RUM** | Como é a experiência dos usuários reais no navegador? |
| **Application Signals / X-Ray** | Qual serviço/dependência causa a lentidão? |

## Dashboards

Um **dashboard** é uma página personalizável com **widgets** (gráficos, números, textos, tabelas de logs, alarmes).

| Widget | Uso |
|---|---|
| **Linha / área** | Tendências (tráfego, latência) |
| **Número** | KPIs em destaque (erros nas últimas 24 h) |
| **Gauge** | Valor atual vs limite |
| **Texto (Markdown)** | Links para runbooks e contatos |
| **Alarmes** | Estado de vários alarmes |
| **Logs Insights** | Tabela/consulta de logs no painel |
| **Explorador de métricas** | Dashboards dinâmicos por tag |

```bash
aws cloudwatch put-dashboard --dashboard-name producao-api \
  --dashboard-body file://dashboard.json
```

```json
{
  "widgets": [
    {"type":"metric","x":0,"y":0,"width":12,"height":6,
     "properties":{"title":"Latência p99","region":"us-east-1","stat":"p99","period":60,
       "metrics":[["AWS/ApplicationELB","TargetResponseTime","LoadBalancer","app/meu-alb/abc"]]}},
    {"type":"text","x":12,"y":0,"width":12,"height":6,
     "properties":{"markdown":"## Runbook\n[Guia de incidentes](https://wiki/incidentes)"}}
  ]
}
```

> [!tip] Dashboards como código
> Versione o JSON em Git e aplique com IaC (CloudFormation/Terraform). Dashboards editados só no console acabam inconsistentes entre ambientes.

### Boas práticas de dashboard

1. **Os quatro sinais dourados** no topo: latência, tráfego, erros, saturação.
2. Um dashboard de **visão geral** e outros por **serviço**.
3. Linha de **alarmes** no topo; runbooks em widget de texto.
4. Dashboards **entre contas e regiões** quando a arquitetura é distribuída.
5. Evite dezenas de gráficos: quem olha precisa decidir em segundos.

## Container Insights

Coleta e agrega **métricas e logs de containers** em **ECS, EKS e Kubernetes** (CPU, memória, rede, disco, reinicializações, contagem de pods/tarefas) e fornece **visões prontas** por cluster, serviço, namespace e pod.

| Plataforma | Como habilitar |
|---|---|
| **ECS** | Configuração do cluster (`containerInsights` habilitado) |
| **EKS** | Add-on de observabilidade (agente/Fluent Bit) |
| **Kubernetes próprio** | Agente do CloudWatch e Fluent Bit |

```bash
aws ecs update-cluster-settings --cluster producao \
  --settings name=containerInsights,value=enabled
```

> [!warning] Custo de métricas customizadas
> O Container Insights gera **muitas métricas** (por tarefa, pod, container). Habilite onde há valor e acompanhe o custo; a versão "enhanced" detalha mais e custa mais.

---

## Lambda Insights

Extensão (layer) que coleta **métricas de sistema** por função: uso de memória, CPU, duração de *cold start*, rede e falhas de inicialização, além de visões comparativas entre funções.

| Problema | O que o Lambda Insights mostra |
|---|---|
| Função lenta | Parcela de cold start vs execução |
| Custo alto | Memória configurada vs usada |
| Timeouts | Duração próxima ao limite |
| Erros de memória | Picos de uso |

## Synthetics: canários

O **CloudWatch Synthetics** executa **scripts agendados (canários)** que **simulam o usuário**: chamam APIs, abrem páginas em um navegador sem interface e validam o resultado. Funciona mesmo **sem tráfego real** (madrugada).

| Tipo de canário | Uso |
|---|---|
| **Heartbeat** | A página carrega? Captura screenshot |
| **API canary** | Endpoints respondem corretamente? |
| **Broken link checker** | Links quebrados no site |
| **Fluxo/visual** | Login, carrinho, checkout (script customizado) |

```
 Canário (a cada 1 min) ─► GET /login ─► valida 200 + texto ─► publica métrica SuccessPercent
                                                          └──► alarme se < 100% por 2 períodos
```

Canários geram métricas (`SuccessPercent`, `Duration`) que viram **alarmes**, e guardam artefatos (screenshots, HAR, logs) em S3 para investigação.

## RUM: usuários reais

O **CloudWatch RUM (Real User Monitoring)** injeta um **script no navegador** para coletar a experiência de **usuários reais**: tempo de carregamento, **Core Web Vitals**, erros de JavaScript, sessões por navegador, país e dispositivo.

| Synthetics | RUM |
|---|---|
| Tráfego **simulado** e previsível | Tráfego **real** e variado |
| Detecta queda mesmo sem usuários | Revela problemas de certos navegadores/regiões |
| Ótimo para disponibilidade | Ótimo para desempenho percebido |

Use os dois: Synthetics responde "está no ar?" e RUM responde "está bom para quem usa?".

## Application Signals e X-Ray

O **Application Signals** descobre **serviços e dependências** automaticamente (com instrumentação OpenTelemetry/ADOT), calcula **SLIs/SLOs** (latência, erros, disponibilidade) e mostra um **mapa de serviços**. O **AWS X-Ray** fornece **traces distribuídos**: o caminho de uma requisição entre serviços, com tempo em cada trecho.

```
 Cliente ─► ALB ─► API ─────► Serviço de pagamento ─► Banco
             12ms   35ms           420ms  ◄── gargalo       30ms
                 └──────────── trace de uma requisição ───────────┘
```

| Recurso | Entrega |
|---|---|
| **Mapa de serviços** | Visão das dependências e saúde |
| **Traces** | Detalhe de uma requisição lenta |
| **SLOs** | Metas e *burn rate* de orçamento de erro |
| **Correlação** | Do alarme ao trace e ao log |

> [!tip] Instrumente cedo
> Traces só existem para requisições **instrumentadas**. Adote OpenTelemetry/ADOT desde o início para não depender de reescrever depois.

## Cross-account e cross-region

Em organizações com várias contas, a **observabilidade entre contas** permite que uma **conta de monitoramento** veja métricas, logs e traces das **contas de origem** em um painel único, sem copiar dados.

| Item | Observação |
|---|---|
| Configuração | Sink na conta de monitoramento; link nas contas de origem |
| Permissões | Compartilhamento por tipo de dado (métricas, logs, traces) |
| Benefício | Um dashboard/alarme para toda a organização |

---

## Exemplo prático: investigando "o checkout está lento"

1. O **dashboard** mostra latência p99 subindo e alarme de SLO em ALARM.
2. **Application Signals** aponta o serviço de pagamento como origem.
3. Um **trace** do X-Ray revela 400 ms numa chamada ao banco.
4. **Logs Insights** filtra por `requestId` e mostra consulta sem índice.
5. O **canário** confirma que o fluxo de checkout falha de fora; o **RUM** mostra o impacto nos usuários.
6. Corrigido o índice, o dashboard volta ao normal e o SLO se recupera.

## Troubleshooting

| Sintoma | Causa provável | Como resolver |
|---|---|---|
| Container Insights sem dados | Agente/Fluent Bit ausente ou sem permissão | Verificar add-on e role |
| Mapa de serviços vazio | Aplicação sem instrumentação | Instrumentar com ADOT/OpenTelemetry |
| Canário falha só no CloudWatch | Rede/firewall bloqueando o canário | Liberar acesso ou rodar em VPC |
| RUM sem eventos | Snippet não instalado/CORS | Revisar o script e o monitor |
| Dashboard vazio | Região/dimensão incorretas | Conferir região e identificadores |
| Custo de Insights alto | Muitas métricas por pod | Escopo seletivo; revisar versão enhanced |

## SLIs, SLOs e orçamento de erro

O Application Signals formaliza a ideia de **meta de confiabilidade**:

| Termo | Significado | Exemplo |
|---|---|---|
| **SLI** | Indicador medido | % de requisições com latência < 500 ms |
| **SLO** | Meta para o SLI | 99,5% em 30 dias |
| **Orçamento de erro** | Falha tolerada (100% − SLO) | 0,5% das requisições |
| **Burn rate** | Velocidade de consumo do orçamento | Alarme se consumir 10× o ritmo normal |

> [!tip] Alarme por burn rate
> Alarmar quando o **orçamento de erro está sendo consumido rápido demais** reduz falsos positivos: um pico curto que não ameaça o SLO não acorda ninguém, mas uma degradação lenta e persistente sim.

### Escolhendo o que usar primeiro

```
 Começando?                                 Ordem sugerida
 1. Dashboard + alarmes dos 4 sinais        (métricas padrão)
 2. Logs estruturados + Logs Insights       (diagnóstico)
 3. Synthetics no fluxo crítico             (visão externa)
 4. Traces / Application Signals            (microsserviços)
 5. RUM                                     (front-end com muitos usuários)
```

## Erros comuns e armadilhas

- **Dashboard gigante** que ninguém consegue ler.
- **Dashboards manuais** não versionados.
- **Habilitar Container Insights em tudo** sem olhar o custo.
- **Depender só de Synthetics** e ignorar usuários reais (ou o contrário).
- **Sem instrumentação** e esperar traces.
- **Canários sem alarme:** geram métricas que ninguém observa.
- **Esquecer que o escopo é regional** ao montar painéis.
- **Não ligar alarmes a runbooks** nos dashboards.

## 🧩 Quiz de Fixação

1. Qual a diferença entre Synthetics e RUM?
2. Para que serve o Container Insights?
3. O que o Application Signals adiciona às métricas?
4. O que mostra um trace do X-Ray?
5. Por que versionar dashboards como código?
6. Qual risco de habilitar Container Insights em todo o ambiente?

**Respostas:**
1) Synthetics simula usuários com canários agendados (disponibilidade mesmo sem tráfego); RUM mede a experiência de usuários reais no navegador.
2) Coletar e visualizar métricas e logs de containers em ECS, EKS e Kubernetes, por cluster, serviço e pod.
3) Descoberta de serviços e dependências, mapa de serviços e SLIs/SLOs com correlação a traces e logs.
4) O caminho de uma requisição entre serviços, com o tempo gasto em cada trecho.
5) Para manter consistência entre ambientes, permitir revisão e restaurar painéis facilmente.
6) Aumento de custo, pois gera muitas métricas por tarefa/pod/container.
