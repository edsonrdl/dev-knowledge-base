### O que é Amazon CloudWatch — observabilidade na AWS, métricas, logs, alarmes, dashboards e quando usar cada recurso

> [!warning] Aviso
> Preços, limites, resoluções, períodos de retenção e nomes de recursos mudam. Os números aqui são referências de estudo; confirme na documentação oficial. Os comandos de CLI são exemplos e **não foram executados**.

O **Amazon CloudWatch** é o serviço de **observabilidade** da AWS: ele **coleta, armazena e permite analisar métricas, logs e eventos** de recursos AWS, aplicações e servidores locais, e **reage** a eles com alarmes e automações. Quase todo serviço da AWS publica métricas no CloudWatch automaticamente, sem você instalar nada.

Observabilidade responde a três perguntas: **está funcionando?** (métricas e alarmes), **por que parou?** (logs e traces) e **como está o conjunto?** (dashboards e insights).

**Analogia:** pense no **painel de um carro**. Os ponteiros e luzes (métricas) mostram velocidade e temperatura; a luz de alerta (alarme) acende quando algo passa do limite; o **registro da caixa-preta** (logs) guarda o que aconteceu em detalhe; e o painel inteiro (dashboard) junta tudo numa tela. O CloudWatch é o painel e a caixa-preta de toda a sua infraestrutura.

## Os pilares do CloudWatch

```
                        ┌────────────────────────────────────────┐
  EC2, RDS, Lambda,     │             AMAZON CLOUDWATCH          │
  S3, ELB, ECS...  ───► │                                        │
  (métricas auto)       │  MÉTRICAS ──► ALARMES ──► Ações        │
                        │     │            │       (SNS, ASG,    │
  Aplicações/agente ──► │     ▼            ▼        EC2, SSM)    │
  (métricas custom)     │  DASHBOARDS   Anomaly                  │
                        │                Detection               │
  Logs de apps e    ──► │  LOGS ──► Logs Insights / Filtros      │
  serviços              │                                        │
                        │  Insights, Synthetics, RUM, X-Ray...   │
                        └────────────────────────────────────────┘
```

| Pilar | O que faz | Exemplo |
|---|---|---|
| **Metrics** | Séries temporais numéricas | CPU de uma instância, latência de um ALB |
| **Alarms** | Observam uma métrica e agem | Notificar quando CPU > 80% por 5 min |
| **Logs** | Armazenam e consultam texto/JSON | Logs da aplicação, de Lambda, de VPC Flow |
| **Dashboards** | Painéis visuais | Saúde da produção em uma tela |
| **Events/EventBridge** | Reagem a mudanças de estado | Disparar Lambda quando a instância para |
| **Insights** | Análise de containers, Lambda, aplicações | Container Insights, Lambda Insights |
| **Synthetics / RUM** | Monitoramento sintético e de usuário real | Canário que testa o login a cada minuto |

## Métricas: o conceito central

Uma **métrica** é uma **série temporal** de pontos de dados (timestamp, valor). É identificada por:

| Elemento | Significado | Exemplo |
|---|---|---|
| **Namespace** | Contêiner lógico (geralmente por serviço) | `AWS/EC2`, `AWS/Lambda`, `MeuApp` |
| **Nome da métrica** | O que é medido | `CPUUtilization`, `Invocations` |
| **Dimensões** | Pares nome/valor que identificam o recurso | `InstanceId=i-0abc`, `FunctionName=minha-func` |
| **Unidade** | Tipo de medida | Percent, Count, Bytes, Seconds |
| **Estatística** | Como agregar no período | Average, Sum, Min, Max, p99 |

> [!tip] Dimensões fazem parte da identidade
> A métrica `CPUUtilization` da instância A e da instância B são **séries diferentes**, pois a dimensão `InstanceId` difere. Consultar sem a dimensão correta devolve "sem dados" — erro frequente.

### Métricas padrão vs detalhadas

| Tipo | Frequência típica | Custo | Observação |
|---|---|---|---|
| **Padrão (basic)** | 5 minutos (EC2) | Incluído | Muitos serviços publicam a cada 1 min |
| **Detalhada** | 1 minuto (EC2) | Cobrada à parte | Útil para Auto Scaling mais reativo |
| **Alta resolução (custom)** | Até 1 segundo | Maior custo | Para eventos rápidos |

> [!warning] O que o CloudWatch NÃO coleta sozinho
> Para EC2, **memória e uso de disco não são métricas padrão**: o hipervisor não enxerga o interior do SO. É preciso instalar o **CloudWatch Agent**.

## Logs: o outro pilar

O **CloudWatch Logs** organiza os registros em:

```
 Log group   (ex.: /aplicacao/api)         ← política de retenção, permissões
   ├─ Log stream (ex.: instancia-1)        ← sequência de eventos de uma origem
   │    ├─ evento: {timestamp, mensagem}
   │    └─ evento: ...
   └─ Log stream (ex.: instancia-2)
```

| Origem comum de logs | Como chega |
|---|---|
| **Lambda** | Automático (grupo `/aws/lambda/<nome>`) |
| **ECS/Fargate, Batch** | Driver `awslogs` |
| **EC2 / servidores locais** | CloudWatch Agent |
| **VPC Flow Logs, Route 53, API Gateway, CloudTrail** | Configuração do serviço |
| **Aplicação própria** | SDK / agente |

Com **Logs Insights** você consulta esses logs com uma linguagem própria; com **metric filters** transforma padrões de texto em **métricas** (por exemplo, contar linhas com `ERROR`).

## Alarmes: transformando dados em ação

Um **alarme** observa **uma métrica** (ou expressão) e muda entre **três estados**:

| Estado | Significado |
|---|---|
| **OK** | Métrica dentro do limite |
| **ALARM** | Limite violado pelo número de períodos configurado |
| **INSUFFICIENT_DATA** | Ainda sem dados suficientes para decidir |

Ao mudar de estado, o alarme executa **ações**: notificar por **SNS**, acionar **Auto Scaling**, parar/reiniciar/recuperar uma instância EC2 ou criar um item no **Systems Manager**. ## CloudWatch vs CloudTrail vs Config

Três serviços que se confundem facilmente:

| Serviço | Pergunta que responde | Exemplo |
|---|---|---|
| **CloudWatch** | **Como está o desempenho/saúde agora?** | CPU alta, erros 5xx, latência |
| **CloudTrail** | **Quem fez qual chamada de API?** | Quem excluiu o bucket |
| **AWS Config** | **Como estava a configuração e mudou?** | Security group aberto, histórico de config |

```
 "O site está lento"                    → CloudWatch (métricas, logs, dashboards)
 "Quem apagou a instância?"             → CloudTrail
 "O bucket estava público ontem?"       → Config
```

## Primeiros comandos

```bash
# Lista métricas de um namespace
aws cloudwatch list-metrics --namespace AWS/EC2 \
  --dimensions Name=InstanceId,Value=i-0123456789abcdef0

# Obtém estatísticas de CPU das últimas horas
aws cloudwatch get-metric-statistics \
  --namespace AWS/EC2 --metric-name CPUUtilization \
  --dimensions Name=InstanceId,Value=i-0123456789abcdef0 \
  --start-time 2026-11-09T10:00:00Z --end-time 2026-11-09T12:00:00Z \
  --period 300 --statistics Average Maximum

# Cria um alarme simples de CPU
aws cloudwatch put-metric-alarm \
  --alarm-name cpu-alta-web --namespace AWS/EC2 --metric-name CPUUtilization \
  --dimensions Name=InstanceId,Value=i-0123456789abcdef0 \
  --statistic Average --period 300 --evaluation-periods 2 \
  --threshold 80 --comparison-operator GreaterThanThreshold \
  --alarm-actions arn:aws:sns:us-east-1:123456789012:alertas

# Consulta logs recentes de um grupo
aws logs tail /aws/lambda/minha-funcao --since 30m --follow
```

## Modelo de dados e retenção (referência)

| Item | Referência de estudo |
|---|---|
| Pontos de 1 s a 1 min | Retidos por algumas horas |
| Pontos de 1 min | Cerca de 15 dias |
| Pontos de 5 min | Cerca de 63 dias |
| Pontos de 1 h | Cerca de 15 meses |
| Logs | Retenção **configurável** por log group (de dias a anos, ou "nunca expirar") |

Os dados de métricas são **agregados automaticamente** em resoluções menores à medida que envelhecem. Logs **não expiram por padrão**: sem política de retenção, o custo cresce sem limite.

## Escopo regional

CloudWatch é **regional**: métricas, alarmes e logs de `us-east-1` não aparecem em `sa-east-1`. Para ver várias regiões/contas no mesmo painel use **dashboards entre regiões** e **observabilidade entre contas** (cross-account observability), configuradas com contas de monitoramento e de origem.

## Exemplo prático: monitorando uma API

1. A API roda em **ECS Fargate** atrás de um **ALB**.
2. As métricas padrão do ALB (`HTTPCode_Target_5XX_Count`, `TargetResponseTime`) e do ECS (CPU/memória) já aparecem no CloudWatch.
3. Os logs vão para `/producao/api` com **retenção de 30 dias**.
4. Um **metric filter** conta linhas com `"level":"ERROR"` e gera a métrica `ErrosAplicacao`.
5. **Alarmes** avisam por SNS quando 5xx > 1% por 5 minutos ou quando `ErrosAplicacao` sobe.
6. Um **dashboard** mostra tráfego, latência p99, erros e CPU numa tela.

## Os quatro sinais dourados

Ao decidir o que monitorar em qualquer serviço, comece pelos **quatro sinais dourados** (*golden signals*):

| Sinal | Pergunta | Exemplo no CloudWatch |
|---|---|---|
| **Latência** | Quanto tempo leva responder? | `TargetResponseTime` p99 do ALB |
| **Tráfego** | Quanta demanda existe? | `RequestCount`, `Invocations` |
| **Erros** | Quanto está falhando? | `HTTPCode_Target_5XX_Count`, `Errors` do Lambda |
| **Saturação** | Quão cheio está o recurso? | CPU, memória, conexões, profundidade de fila |

> [!tip] Comece pequeno
> Para um serviço novo, quatro alarmes (um por sinal) e um dashboard com esses quatro gráficos já entregam a maior parte do valor. Refine depois com base em incidentes reais.

### Mapa rápido: qual recurso usar

```
 Preciso de...                         Use
 Um número ao longo do tempo           Métrica
 Ser avisado quando passar do limite   Alarme
 Ler o que a aplicação escreveu        Logs / Logs Insights
 Contar ocorrências de um texto        Metric filter
 Ver tudo numa tela                    Dashboard
 Testar o fluxo de fora                Synthetics
 Reagir a um evento da AWS             EventBridge
```

## Erros comuns e armadilhas

- **Esperar métrica de memória do EC2 sem instalar o agente.**
- **Não definir retenção dos logs** e pagar armazenamento indefinido.
- **Consultar métrica sem a dimensão correta** e concluir que não há dados.
- **Confundir CloudWatch, CloudTrail e Config.**
- **Alarmes sem ação** (ninguém é avisado).
- **Olhar a região errada** ao procurar métricas e logs.
- **Criar alarmes demais** sem critério, causando fadiga de alertas.
- **Usar apenas média** e esconder picos de latência (use percentis).

## 🧩 Quiz de Fixação

1. Quais são os principais pilares do CloudWatch?
2. O que identifica uma métrica além do nome?
3. Quais são os três estados de um alarme?
4. A memória de uma instância EC2 é coletada por padrão? Por quê?
5. Qual a diferença entre CloudWatch e CloudTrail?
6. Por que definir retenção em um log group?

**Respostas:**
1) Métricas, alarmes, logs, dashboards, eventos e recursos de insights/monitoramento (Synthetics, RUM, Container Insights).
2) O namespace, as dimensões e a unidade; as dimensões fazem parte da identidade da série.
3) OK, ALARM e INSUFFICIENT_DATA.
4) Não. O hipervisor não enxerga o interior do SO; é preciso instalar o CloudWatch Agent para memória e disco.
5) CloudWatch mede desempenho e saúde (métricas, logs, alarmes); CloudTrail registra quem fez cada chamada de API.
6) Porque os logs não expiram por padrão e o armazenamento cresce indefinidamente, aumentando o custo.
