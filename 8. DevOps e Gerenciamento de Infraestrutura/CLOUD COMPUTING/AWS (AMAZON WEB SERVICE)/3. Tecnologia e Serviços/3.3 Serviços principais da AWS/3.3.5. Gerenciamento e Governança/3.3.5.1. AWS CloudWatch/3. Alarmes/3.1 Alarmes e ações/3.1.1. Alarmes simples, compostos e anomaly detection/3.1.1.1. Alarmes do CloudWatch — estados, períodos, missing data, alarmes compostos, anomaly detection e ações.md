### Alarmes do CloudWatch — estados, períodos, missing data, alarmes compostos, anomaly detection e ações

> [!warning] Aviso
> Limites de alarmes por conta, preços, ações disponíveis e comportamentos de avaliação mudam. Os números aqui são referências de estudo; confirme na documentação. Os comandos **não foram executados**.

Um **alarme do CloudWatch** observa **uma métrica** (ou uma expressão de Metric Math) ao longo do tempo e **executa ações** quando ela viola um limite. É o mecanismo que transforma dados em **resposta**: avisar uma pessoa, escalar uma frota, recuperar uma instância ou abrir um incidente.

**Analogia:** é o **detector de fumaça** da casa. Ele fica medindo o ar (métrica); só dispara se a fumaça passar de um nível por tempo suficiente (limite e períodos); toca a sirene e liga para os bombeiros (ações); e, se o sensor quebra e para de enviar leitura, você decide se isso deve soar como alarme ou ser ignorado (missing data).

---

## Os três estados

```
              dados dentro do limite
       ┌──────────────────────────────┐
       ▼                              │
  ┌─────────┐   violou N de M    ┌────┴─────┐
  │   OK    │ ─────────────────► │  ALARM   │
  └─────────┘ ◄───────────────── └──────────┘
       ▲        voltou ao normal       
       │
  ┌────┴──────────────────┐
  │  INSUFFICIENT_DATA    │  (alarme novo ou sem dados suficientes)
  └───────────────────────┘
```

| Estado | Significado | Ações |
|---|---|---|
| **OK** | Métrica dentro do limite | Pode acionar ações de OK (ex.: "recuperado") |
| **ALARM** | Limite violado | Aciona as ações de ALARM |
| **INSUFFICIENT_DATA** | Sem dados para avaliar | Pode acionar ações específicas |

---

## Parâmetros de um alarme

| Parâmetro | Função |
|---|---|
| **Métrica/expressão** | O que observar (namespace, nome, dimensões) |
| **Estatística** | Average, Sum, Maximum, p99... |
| **Period** | Janela de agregação (ex.: 60 s, 300 s) |
| **Threshold** | Valor limite |
| **ComparisonOperator** | `GreaterThanThreshold`, `LessThanThreshold` etc. |
| **EvaluationPeriods (N)** | Quantos períodos são avaliados |
| **DatapointsToAlarm (M)** | Quantos dos N precisam violar ("M de N") |
| **TreatMissingData** | O que fazer quando faltam pontos |
| **Actions** | O que executar em ALARM / OK / INSUFFICIENT_DATA |

### "M de N": reduzindo falsos positivos

```
 Threshold = 80%      EvaluationPeriods = 5     DatapointsToAlarm = 3

 períodos:   82  75  91  60  88          →  3 dos 5 violam  →  ALARM
 períodos:   82  75  70  60  88          →  2 dos 5 violam  →  OK
```

Exigir **M de N** em vez de "um ponto" evita alarmes por picos isolados, sem atrasar demais a detecção de problemas reais.

## Missing data: o ponto mais traiçoeiro

Quando a métrica **para de chegar**, o alarme precisa saber o que fazer:

| Opção `TreatMissingData` | Efeito | Quando usar |
|---|---|---|
| `missing` (padrão) | Mantém o estado; pode ir a INSUFFICIENT_DATA | Métricas contínuas |
| `notBreaching` | Dado ausente conta como **dentro** do limite | Eventos esparsos (erros) |
| `breaching` | Dado ausente conta como **violação** | Heartbeats: ausência = problema |
| `ignore` | Ignora o período | Mantém o estado atual |

> [!tip] Escolha pela semântica
> - **Contador de erros** (só existe quando há erro): `notBreaching`.
> - **Heartbeat/batimento** (deveria sempre chegar): `breaching`.
> - **CPU de instância** (sempre existe): padrão.

## Ações de um alarme

| Ação | Uso |
|---|---|
| **Notificação SNS** | E-mail, SMS, HTTP, Lambda, fila SQS, chat |
| **Auto Scaling** | Política de escala para dentro/fora |
| **Ações EC2** | Parar, encerrar, **reiniciar** ou **recuperar** a instância |
| **Systems Manager** | Criar OpsItem ou incidente |
| **Lambda** (via SNS/EventBridge) | Remediação customizada |

```bash
aws cloudwatch put-metric-alarm \
  --alarm-name ec2-recuperar \
  --namespace AWS/EC2 --metric-name StatusCheckFailed_System \
  --dimensions Name=InstanceId,Value=i-0123456789abcdef0 \
  --statistic Maximum --period 60 --evaluation-periods 2 \
  --threshold 1 --comparison-operator GreaterThanOrEqualToThreshold \
  --alarm-actions arn:aws:automate:us-east-1:ec2:recover \
                  arn:aws:sns:us-east-1:123456789012:alertas
```

> [!warning] SNS precisa de assinatura confirmada
> Alarme que aponta para um tópico **sem assinante confirmado** "funciona" e ninguém é avisado. Teste a entrega.

## Alarmes compostos (composite alarms)

Um **alarme composto** combina o estado de **outros alarmes** com lógica booleana, reduzindo ruído.

```
 ALARM(cpu-alta) AND ALARM(latencia-alta)  AND NOT ALARM(manutencao)
                         │
                         ▼
             Alarme composto "servico-degradado"  ──► SNS (1 notificação)
```

| Vantagem | Exemplo |
|---|---|
| Menos alertas | Notifica só quando CPU **e** latência estão ruins |
| Contexto | "Banco lento E fila crescendo" |
| Supressão | Silenciar durante janela de manutenção |
| Hierarquia | Alarme "serviço" agrega alarmes de componentes |

```bash
aws cloudwatch put-composite-alarm --alarm-name servico-degradado \
  --alarm-rule 'ALARM("cpu-alta") AND ALARM("latencia-alta")' \
  --alarm-actions arn:aws:sns:us-east-1:123456789012:oncall
```

## Anomaly detection

Em vez de um limite fixo, o **anomaly detection** usa **machine learning** para aprender o padrão normal da métrica (incluindo sazonalidade diária e semanal) e cria uma **banda esperada**. O alarme dispara quando o valor **sai da banda**.

```
 valor
  │          ╭─── banda superior ───╮
  │   ~~~~~~~│~~~~~~~~~~~~~~~~~~~~~~│~~~~~
  │   ▲ normal      ▲ x violação    │
  │   ~~~~~~~│~~~~~~~~~~~~~~~~~~~~~~│~~~~~
  │          ╰─── banda inferior ───╯
  └────────────────────────────────────────► tempo
```

| Use anomaly detection quando | Prefira limite estático quando |
|---|---|
| Tráfego varia por hora/dia | Existe um limite técnico claro (disco 90%) |
| Não sabe qual valor é "normal" | O limite vem de um SLA |
| Quer detectar quedas anormais | Métrica sem padrão (ruído) |

> [!tip] Treino leva tempo
> O modelo precisa de dados históricos e se ajusta ao longo de dias; alarmes recém-criados podem ser imprecisos no início.

## Estratégia de alarmes: o que vale alarmar

| Camada | Sinal | Exemplo de alarme |
|---|---|---|
| **Usuário** | Disponibilidade/latência | 5xx > 1% por 5 min; p99 > 2 s |
| **Aplicação** | Erros e filas | Erros de aplicação; mensagens antigas no SQS |
| **Infraestrutura** | Saturação | CPU sustentada alta, disco quase cheio |
| **Negócio** | Volume | Pedidos fora da banda esperada |
| **Plataforma** | Saúde | StatusCheckFailed, falha de replicação |

> [!warning] Alarme sem ação clara é ruído
> Cada alarme deve responder: **quem age, o que faz e com que urgência**. Alarmes sem dono nem runbook são ignorados e fazem as pessoas desligarem o sistema inteiro.

## Alarmes e Auto Scaling

O padrão clássico: um alarme observa a carga e aciona uma política de escala.

```
 CPU média do ASG > 70% por 3 períodos ──► alarme ──► política "scale out +2"
 CPU média do ASG < 30% por 15 períodos ─► alarme ──► política "scale in -1"
```

Para a maioria dos casos, **target tracking** do Auto Scaling cria e gerencia esses alarmes automaticamente.

---

## Exemplo prático: pacote mínimo de alarmes de uma API

1. `5xx-alto`: taxa de erros (Metric Math) > 1% em 3 de 5 períodos de 1 min, `notBreaching`.
2. `latencia-p99`: p99 do `TargetResponseTime` > 2 s em 3 de 5 períodos.
3. `fila-parada` (heartbeat): mensagens processadas = 0 por 10 min, `breaching`.
4. `ec2-status-check`: `StatusCheckFailed_System` → ação **recover**.
5. Alarme **composto** `api-degradada` = 5xx-alto **E** latencia-p99, notificando o on-call.
6. Cada alarme aponta para um **runbook** na descrição.

## Troubleshooting

| Sintoma | Causa provável | Como resolver |
|---|---|---|
| Alarme em INSUFFICIENT_DATA | Dimensão errada ou métrica sem dados | Conferir namespace/dimensões/período |
| Não notifica | Assinatura SNS não confirmada ou política do tópico | Confirmar assinatura; revisar permissões |
| Dispara demais | Limite apertado, sem M de N | Aumentar períodos; usar anomaly detection |
| Nunca dispara | Estatística errada (Average em vez de Max) | Ajustar estatística e período |
| Alarme "preso" em ALARM | `TreatMissingData` mantendo estado | Rever a opção de missing data |
| Ação EC2 falha | Permissão/serviço não habilitado | Verificar a role de ação e a região |

## Testando e operando alarmes

```bash
# Força um estado para testar as ações (não altera a métrica real)
aws cloudwatch set-alarm-state --alarm-name cpu-alta-web \
  --state-value ALARM --state-reason "teste de notificação"

# Histórico de mudanças de estado
aws cloudwatch describe-alarm-history --alarm-name cpu-alta-web \
  --history-item-type StateUpdate

# Alarmes atualmente em ALARM
aws cloudwatch describe-alarms --state-value ALARM \
  --query 'MetricAlarms[].[AlarmName,StateReason]'
```

| Prática | Motivo |
|---|---|
| Testar com `set-alarm-state` ao criar | Confirma que SNS e ações funcionam |
| Revisar o histórico após incidentes | Ajusta limites e períodos |
| Padronizar nomes (`servico-sintoma-severidade`) | Facilita filtros e ownership |
| Alarmes via IaC | Evita divergência entre ambientes |
| Ação de OK além da de ALARM | Avisa a recuperação e fecha o incidente |

### Severidade e roteamento

| Severidade | Critério | Destino |
|---|---|---|
| **Crítica** | Impacto ao usuário agora | Pager do on-call |
| **Aviso** | Tendência ruim, sem impacto ainda | Canal de equipe |
| **Informativa** | Mudança relevante | Dashboard/e-mail |

## Erros comuns e armadilhas

- **Alarmar sobre média** quando o problema aparece no máximo ou em percentis.
- **Ignorar `TreatMissingData`** e ter alarmes mudos quando o serviço cai.
- **Um ponto isolado** como gatilho (sem M de N).
- **Tópico SNS sem assinante** confirmado.
- **Dezenas de alarmes sobre o mesmo sintoma** em vez de um composto.
- **Limite fixo para métricas sazonais.**
- **Alarmes sem dono ou runbook.**
- **Esquecer a região:** alarmes são regionais.

## 🧩 Quiz de Fixação

1. Quais são os estados de um alarme?
2. O que significa "M de N" (DatapointsToAlarm)?
3. Qual `TreatMissingData` usar em um heartbeat?
4. Para que servem alarmes compostos?
5. Quando usar anomaly detection em vez de limite estático?
6. Por que testar a assinatura do tópico SNS?

**Respostas:**
1) OK, ALARM e INSUFFICIENT_DATA.
2) Que M dos últimos N períodos precisam violar o limite para o alarme disparar, reduzindo falsos positivos de picos isolados.
3) `breaching`, pois a ausência de dados indica falha.
4) Combinar o estado de vários alarmes com lógica booleana (AND/OR/NOT) para reduzir ruído e dar contexto, inclusive suprimindo durante manutenção.
5) Quando a métrica tem padrão sazonal e não há um valor fixo de referência; o modelo aprende a banda esperada.
6) Porque, sem assinante confirmado, o alarme dispara mas ninguém é notificado.
