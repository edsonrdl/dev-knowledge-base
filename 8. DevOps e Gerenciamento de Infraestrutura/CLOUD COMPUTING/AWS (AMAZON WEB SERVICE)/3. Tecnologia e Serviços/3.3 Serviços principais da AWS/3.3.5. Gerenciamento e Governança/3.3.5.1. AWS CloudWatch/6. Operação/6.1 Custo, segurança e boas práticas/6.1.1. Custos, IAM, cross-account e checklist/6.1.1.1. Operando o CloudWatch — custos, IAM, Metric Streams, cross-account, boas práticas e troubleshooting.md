### Operando o CloudWatch — custos, IAM, Metric Streams, cross-account, boas práticas e troubleshooting

> [!warning] Aviso
> Preços, camadas gratuitas, limites de API e políticas gerenciadas mudam. Os números aqui são referências de estudo; confirme na documentação e no console de custos. Os comandos **não foram executados**.

O CloudWatch é fácil de começar e **fácil de deixar caro e desorganizado**. Esta folha reúne o que sustenta o uso em produção: **de onde vem o custo**, **quem pode fazer o quê**, **como exportar e centralizar dados** e um **checklist** de boas práticas. A ideia é ter observabilidade **suficiente** sem ruído nem conta inesperada.

**Analogia:** é a **manutenção de um sistema de câmeras de segurança**. Câmeras demais gravando em alta resolução 24 h enchem o disco e a fatura; poucas deixam pontos cegos. É preciso decidir *o que gravar, por quanto tempo, quem pode assistir* e *quando apagar*.

## De onde vem o custo

| Fonte | Como é cobrada (referência) | Alavanca principal |
|---|---|---|
| **Métricas customizadas** | Por métrica (série) por mês | Reduzir cardinalidade de dimensões |
| **Métricas detalhadas** | Por métrica habilitada | Habilitar só onde necessário |
| **Alarmes** | Por alarme (padrão, alta resolução, composto) | Remover alarmes sem uso |
| **Logs — ingestão** | Por GB ingerido | Reduzir verbosidade; classe Infrequent Access |
| **Logs — armazenamento** | Por GB/mês | **Retenção** e arquivamento em S3 |
| **Logs Insights** | Por GB escaneado | Filtrar cedo; limitar intervalo |
| **Dashboards** | Por dashboard (com camada gratuita) | Consolidar painéis |
| **Chamadas de API** | `GetMetricData`, `PutMetricData` | Agregar, usar EMF |
| **Synthetics / RUM / Insights** | Por execução/evento/métrica | Ajustar frequência e escopo |
| **Metric Streams** | Por métrica atualizada | Filtrar namespaces |

> [!tip] Onde o dinheiro costuma estar
> Na prática, os **maiores ofensores** são quase sempre **ingestão de logs** (aplicações verbosas) e **métricas de alta cardinalidade**. Comece por aí.

### Descobrindo os maiores custos

```bash
# Tamanho armazenado e retenção por log group
aws logs describe-log-groups \
  --query 'logGroups[].[logGroupName,storedBytes,retentionInDays]' --output table

# Log groups sem retenção definida
aws logs describe-log-groups \
  --query 'logGroups[?retentionInDays==`null`].logGroupName'
```

No **Cost Explorer**, filtre por serviço **CloudWatch** e agrupe por **tipo de uso** (`DataProcessing-Bytes`, `TimedStorage-ByteHrs`, `MetricMonitorUsage`...) para ver qual componente domina.

## Plano de redução de custo

| Passo | Ação | Efeito típico |
|---|---|---|
| 1 | Definir **retenção** em todos os log groups | Corta armazenamento acumulado |
| 2 | Baixar nível de log (DEBUG → INFO/WARN) em produção | Reduz ingestão |
| 3 | Classe **Infrequent Access** para logs pouco consultados | Ingestão mais barata |
| 4 | Exportar/assinar logs para **S3** para arquivo longo | Armazenamento barato |
| 5 | Remover dimensões de alta cardinalidade | Menos métricas cobradas |
| 6 | Apagar alarmes e dashboards órfãos | Custo fixo menor |
| 7 | Revisar Container Insights/Synthetics | Menos métricas e execuções |
| 8 | Amostragem de logs/traces | Mantém sinal, corta volume |

## Segurança e IAM

| Necessidade | Como atender |
|---|---|
| Aplicação publica logs/métricas | Role com `logs:CreateLogStream`, `logs:PutLogEvents`, `cloudwatch:PutMetricData` |
| Pessoas consultam | Políticas de leitura (`cloudwatch:GetMetricData`, `logs:StartQuery`, `logs:GetQueryResults`) |
| Limitar por recurso | ARNs de **log groups** específicos |
| Proteger dados | **KMS** nos log groups; **data protection policies** |
| Isolar produção | Contas separadas; acesso somente leitura a desenvolvedores |
| Auditar | **CloudTrail** registra chamadas de API do CloudWatch |

```json
{
  "Effect": "Allow",
  "Action": ["logs:StartQuery","logs:GetQueryResults","logs:DescribeLogGroups"],
  "Resource": "arn:aws:logs:us-east-1:123456789012:log-group:/producao/*"
}
```

> [!warning] Logs são dados sensíveis
> Logs frequentemente carregam e-mails, IDs, tokens e trechos de payloads. Trate o acesso a log groups como acesso a dados de produção; **mascare** o que for sensível e restrinja permissões.

## Metric Streams: exportando métricas em tempo real

O **CloudWatch Metric Streams** entrega métricas **quase em tempo real** a um destino, via **Kinesis Data Firehose**, para S3, ferramentas de terceiros (APM) ou data lake.

```
 CloudWatch Metrics ──► Metric Stream (filtro de namespaces) ──► Firehose ──► S3 / OpenSearch / terceiros
```

| Uso | Exemplo |
|---|---|
| Retenção além de 15 meses | Arquivar em S3 e consultar com Athena |
| Plataforma de observabilidade externa | Enviar métricas ao Datadog, Splunk etc. |
| Análises de custo/capacidade | Cruzar com outros dados no data lake |

Filtre **por namespace** para não pagar por métricas que não serão usadas.

## Observabilidade entre contas e regiões

| Recurso | Função |
|---|---|
| **Cross-account observability** | Conta de monitoramento vê métricas, logs e traces das contas de origem |
| **Dashboards multi-região** | Um painel com widgets de várias regiões |
| **Subscription filters com destino cross-account** | Centraliza logs numa conta de segurança |
| **AWS Organizations** | Permite habilitar o compartilhamento para toda a organização |

Um desenho comum: **uma conta de observabilidade** recebe sinais de todas as contas de workload, onde ficam dashboards, alarmes e acesso do time de operações.

## Boas práticas e checklist

1. **Retenção definida** em todos os log groups (automatize com IaC ou Config).
2. **Logs estruturados (JSON)** com `requestId`/trace id.
3. **EMF** para métricas de negócio, sem alta cardinalidade nas dimensões.
4. **Alarmes com dono e runbook**; M de N; `TreatMissingData` adequado.
5. **Composite alarms** para reduzir ruído; anomaly detection para métricas sazonais.
6. **Percentis** (p99) para latência.
7. **Dashboards como código** e hierarquia (geral → serviço).
8. **Alarme de custo** (Budgets) para CloudWatch.
9. Acesso por **menor privilégio**; KMS e mascaramento de dados sensíveis.
10. **Centralizar** observabilidade em conta dedicada em ambientes multi-conta.

## Troubleshooting

| Sintoma | Causa provável | Como resolver |
|---|---|---|
| Conta do CloudWatch disparou | Ingestão de logs ou métricas custom | Cost Explorer por tipo de uso; reduzir volume |
| Alarme "sem dados" | Dimensões/região/período incorretos | Verificar métrica no console |
| Throttling em `PutMetricData`/`GetMetricData` | Muitas chamadas | Agregar, usar EMF, cache e batching |
| Dashboard lento | Muitos widgets/consultas pesadas | Simplificar; reduzir períodos |
| Dados antigos sem detalhe | Consolidação de retenção | Usar Metric Streams para arquivo |
| Sem permissão no console | Políticas restritas demais | Conceder leitura específica |
| Logs de outra conta ausentes | Compartilhamento não configurado | Configurar sink/link ou destino cross-account |

## Exemplo prático: auditoria mensal de CloudWatch

1. Listar log groups **sem retenção** e aplicar 30 ou 90 dias conforme criticidade.
2. Ver no Cost Explorer os três maiores tipos de uso do CloudWatch.
3. Identificar o log group que mais ingere e rever o nível de log.
4. Procurar métricas com dimensões de alta cardinalidade e ajustar.
5. Remover alarmes em `INSUFFICIENT_DATA` há meses e dashboards sem acesso.
6. Verificar se logs críticos de segurança estão sendo arquivados no S3.
7. Registrar a economia e as exceções aprovadas.

## Automação com IaC: o mínimo para cada serviço

Padronize um **módulo** que, ao criar um serviço, já entregue observabilidade básica:

```
 módulo "observabilidade" (por serviço)
 ├─ Log group com retenção e KMS
 ├─ Metric filter de erros
 ├─ Alarmes: 5xx/erros, latência p99, saturação
 ├─ Alarme composto "servico-degradado"
 ├─ Dashboard dos quatro sinais
 └─ Tags: servico, ambiente, time, custo
```

| Benefício | Efeito |
|---|---|
| Consistência | Todo serviço nasce monitorado |
| Governança | Retenção e criptografia nunca esquecidas |
| Custo | Tags permitem rateio por time |
| Revisão | Mudanças em alarmes passam por pull request |

### Limites e quotas a acompanhar

| Item | Por que importa |
|---|---|
| Taxa de `PutMetricData` e `GetMetricData` | Throttling quebra painéis e automações |
| Número de alarmes por conta/região | Pode exigir pedido de aumento de quota |
| Subscription filters por log group | Limita o fan-out; planeje com Kinesis/Firehose |
| Tamanho máximo de evento de log | Eventos grandes são truncados ou rejeitados |

Verifique as quotas em **Service Quotas** antes de lançar um ambiente grande e configure alertas de uso próximo do limite.

### Indicadores de saúde da própria observabilidade

1. Percentual de log groups com retenção definida (meta: 100%).
2. Alarmes sem ação ou sem dono (meta: zero).
3. Custo mensal do CloudWatch por serviço (acompanhar tendência).
4. Tempo médio entre o início de um incidente e o alarme (quanto menor, melhor).

## Erros comuns e armadilhas

- **Nunca revisar o custo** até a fatura chegar.
- **Retenção infinita** por omissão.
- **Alta cardinalidade** em dimensões de métricas.
- **DEBUG em produção** por tempo indeterminado.
- **Acesso amplo a logs** sem mascarar dados sensíveis.
- **Alarmes órfãos** que só geram custo e ruído.
- **Centralização improvisada** sem permissões e destinos planejados.
- **Tratar CloudWatch como armazenamento de longo prazo** de logs e métricas em vez de arquivar em S3.

## 🧩 Quiz de Fixação

1. Quais são os dois maiores ofensores usuais de custo no CloudWatch?
2. Como descobrir log groups sem retenção?
3. Para que serve o Metric Streams?
4. Como proteger dados sensíveis em logs?
5. O que a observabilidade entre contas permite?
6. Por que agregar ou usar EMF em vez de `PutMetricData` por evento?

**Respostas:**
1) Ingestão/armazenamento de logs e métricas customizadas de alta cardinalidade.
2) Listando os log groups e filtrando os com retentionInDays nulo (por CLI ou console).
3) Exportar métricas quase em tempo real, via Firehose, para S3, data lake ou ferramentas externas, permitindo retenção maior e análises cruzadas.
4) Não logar segredos, usar data protection policies para mascarar, KMS e permissões restritas aos log groups.
5) Que uma conta de monitoramento veja métricas, logs e traces de várias contas de origem em um painel único.
6) Para reduzir chamadas de API, latência, throttling e custo.
