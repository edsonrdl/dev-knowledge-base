### 3.1.1.1. Ciclo de vida e pull through cache no ECR — lifecycle policies, tag immutability, limpeza de imagens, espelhos de registries públicos e custos de armazenamento

> [!warning] Aviso
> Sintaxe das regras, limites, registries upstream suportados pelo pull through cache e preços abaixo são **de memória e mudam**. **Confirme na documentação do ECR e na página de preços.** Políticas e comandos são ilustrativos e **não foram executados**. **Teste lifecycle policies com o recurso de preview antes de ativar** — a exclusão de imagens é irreversível.

## 1. O problema do acúmulo

Cada commit de CI gera uma imagem. Em um time ativo:

```
20 commits/dia × 22 dias × 15 serviços = 6.600 imagens/mês
× 300 MB (camadas únicas médias) → terabytes em poucos meses
```

Sem controle, o repositório vira um **cemitério de imagens** que: custa **armazenamento**, polui listagens, atrasa varreduras e dificulta achar o que realmente está em produção. O ECR resolve isso com **lifecycle policies** (limpeza automática) e **tag immutability** (proteção contra sobrescrita), e resolve a dependência de registries externos com **pull through cache**.

## 2. Lifecycle policies

### 2.1 Como funcionam

Uma **lifecycle policy** é um conjunto de **regras** (em JSON) **por repositório** que **expiram** (excluem) imagens segundo critérios de **status de tag**, **prefixo de tag** ou **idade/quantidade**.

| Elemento | Descrição |
|---|---|
| **`rulePriority`** | Ordem de avaliação (número menor primeiro); **único** por regra |
| **`selection.tagStatus`** | `tagged`, `untagged` ou `any` |
| **`selection.tagPrefixList` / `tagPatternList`** | Prefixos/padrões de tag (para `tagged`) — confirmar suporte a padrões com curinga |
| **`selection.countType`** | `imageCountMoreThan` (manter as N mais recentes) ou `sinceImagePushed` (idade em dias) |
| **`selection.countNumber`** | N imagens ou N dias |
| **`action.type`** | `expire` |

### 2.2 Exemplo realista

```json
{
  "rules": [
    {
      "rulePriority": 1,
      "description": "Expirar imagens sem tag após 7 dias",
      "selection": { "tagStatus": "untagged", "countType": "sinceImagePushed", "countUnit": "days", "countNumber": 7 },
      "action": { "type": "expire" }
    },
    {
      "rulePriority": 10,
      "description": "Manter só as 30 imagens de feature branches mais recentes",
      "selection": { "tagStatus": "tagged", "tagPrefixList": ["feat-", "pr-"], "countType": "imageCountMoreThan", "countNumber": 30 },
      "action": { "type": "expire" }
    },
    {
      "rulePriority": 20,
      "description": "Manter as 50 imagens de release mais recentes",
      "selection": { "tagStatus": "tagged", "tagPrefixList": ["rel-", "v"], "countType": "imageCountMoreThan", "countNumber": 50 },
      "action": { "type": "expire" }
    }
  ]
}
```

```bash
aws ecr put-lifecycle-policy --repository-name pedidos/api \
  --lifecycle-policy-text file://lifecycle.json
aws ecr get-lifecycle-policy --repository-name pedidos/api

# Pré-visualizar o que seria expirado, SEM apagar (ilustrativo)
aws ecr start-lifecycle-policy-preview --repository-name pedidos/api \
  --lifecycle-policy-text file://lifecycle.json
aws ecr get-lifecycle-policy-preview --repository-name pedidos/api
```

### 2.3 Regras de avaliação (armadilhas clássicas)

1. **Avaliação por prioridade**: uma imagem é “capturada” pela **primeira regra** (menor número) que a seleciona; regras posteriores não a reavaliam.
2. **`tagStatus: any` deve ser a de maior número** (menor prioridade): ela casa com tudo e “engole” as demais.
3. **`imageCountMoreThan` conta imagens**, não camadas; uma imagem multi-tag conta **uma vez**, mas casar um prefixo pode envolver todas as tags dela.
4. **A imagem em uso não é protegida**: o ECR **não sabe** que uma task ECS/pod EKS usa aquela imagem. Se a regra expirar a tag que a produção referencia e um nó novo precisar fazer pull → **falha** (`ImagePullBackOff`/`CannotPullContainerError`).
5. **Execução assíncrona**: a limpeza ocorre em segundo plano (pode levar até horas; confirmar), não instantaneamente.
6. **Tags imutáveis + lifecycle**: a expiração de uma tag libera o nome? (Confirmar o comportamento atual antes de depender disso.)

> [!tip] Estratégia segura
> Mantenha uma **tag de ambiente protegida por prefixo** (ex.: `prod-`) e **mais antiga/maior retenção** que as demais, ou, melhor, **mantenha por contagem** (últimas N releases) em vez de por idade, para nunca expirar a versão que está implantada por estar “velha”.

### 2.4 Padrão por tipo de imagem

| Tipo | Regra sugerida |
|---|---|
| **Untagged** (resíduos de re-push, camadas órfãs) | Expirar em **1–7 dias** |
| **Branches/PRs** | Manter **poucas** (10–30) ou por **7–14 dias** |
| **Release/prod** | Manter **mais** (50–100) ou por **180 dias+**, conforme conformidade e rollback |
| **Cache de build** (`buildcache`) | Manter **1–3** |
| **Repositórios de espelho (cache)** | Política própria (ver seção 5) |

### 2.5 Aplicação em escala

- **Templates de repositório** (*repository creation templates*): definem política de ciclo de vida, tags imutáveis, criptografia e permissões **por prefixo de nome** para repositórios criados automaticamente (pull through cache/replicação/*create on push*; confirmar disponibilidade atual).
- **IaC**: `AWS::ECR::Repository` com `LifecyclePolicy` (CloudFormation/CDK/Terraform), versionada e revisada.
- **Revisão periódica**: relatório mensal de `describe-images` por repositório (tamanho total, nº de imagens, imagem mais antiga).

## 3. Tag immutability

### 3.1 O que faz

Com **imutabilidade de tags** ligada no repositório, **uma tag existente não pode ser sobrescrita**: um `push` para `1.4.2` quando já existe falha (`ImageTagAlreadyExistsException`).

| | **MUTABLE** (padrão) | **IMMUTABLE** |
|---|---|---|
| Re-push da mesma tag | Sobrescreve (tag passa a apontar para a nova imagem; a antiga fica *untagged*) | **Recusa** |
| Rastreabilidade | Fraca | **Forte** |
| Tags “deslizantes” (`latest`, `prod`) | Possíveis | **Impossíveis** no mesmo repositório |
| Segurança | Risco de substituição maliciosa/acidental | Mitiga adulteração de releases |

```bash
aws ecr put-image-tag-mutability --repository-name pedidos/api --image-tag-mutability IMMUTABLE
```

### 3.2 Como conviver com `latest`/`prod` (tags deslizantes)

- **Não use tags deslizantes em produção**: use **tags únicas** (`1.4.2-a1b2c3d`) e **digest** no manifest.
- Se precisar de ponteiros de ambiente, mantenha-os **em outro repositório** mutável (`pedidos/api-canais`) ou **no manifest/GitOps**, não na imagem.
- Em versões recentes, há **exceções por padrão de tag** na imutabilidade (confirmar disponibilidade): permite deixar `latest` mutável e o restante imutável.

## 4. Limpeza manual e exclusão

```bash
# Excluir uma imagem específica por tag ou digest
aws ecr batch-delete-image --repository-name pedidos/api \
  --image-ids imageTag=feat-login-1 imageDigest=sha256:aaa...

# Listar imagens sem tag (candidatas a limpeza)
aws ecr list-images --repository-name pedidos/api --filter tagStatus=UNTAGGED

# Excluir um repositório inteiro (cuidado!)
aws ecr delete-repository --repository-name pedidos/api-antigo --force
```

Cuidados: **`--force` apaga todas as imagens**; proteja com **IAM** (negar `ecr:DeleteRepository`/`BatchDeleteImage` a quem não deve) e **SCP** em contas de produção.

## 5. Pull through cache (espelhamento de registries públicos)

### 5.1 O problema

Builds e clusters dependem de **imagens base de terceiros** (Docker Hub, Quay, GitHub Container Registry, registries públicos da AWS/Kubernetes, etc.). Isso traz:

- **Rate limits** de pull que quebram CI/deploys;
- **Dependência da internet** e de disponibilidade externa;
- **Risco de supply chain** (imagem alterada upstream sem aviso);
- **Latência** e custo de NAT.

### 5.2 A solução

O **pull through cache** cria **regras** que mapeiam um **prefixo no seu ECR** a um **registry upstream**. No primeiro pull, o ECR **busca, guarda e serve** a imagem; nos pulls seguintes, entrega da **cópia local** (e verifica atualizações periodicamente).

```
Seu cluster ── pull ──▶ ECR (prefixo "dockerhub/")
                          ├── hit: entrega do cache
                          └── miss: busca no upstream (Docker Hub), cria o repositório, guarda e entrega
```

| Aspecto | Detalhe (de memória — confirmar) |
|---|---|
| **Upstreams** | Registries públicos populares (ex.: ECR Public, Quay, Kubernetes registry, GitHub Container Registry) e, com **credenciais no Secrets Manager**, também **Docker Hub**, GitHub CR, GitLab etc. |
| **Autenticação upstream** | Alguns exigem **credenciais** guardadas no **AWS Secrets Manager** |
| **Atualização** | O ECR verifica o upstream **no máximo a cada ~24 horas** para novas versões da mesma tag (confirmar) |
| **Repositórios criados** | Automaticamente, sob o prefixo escolhido; use **templates de criação** para aplicar lifecycle/permissões |
| **Scan** | Pode combinar com scanning para as imagens espelhadas |

```bash
# Regra para Docker Hub (exige segredo com credenciais; ilustrativo)
aws ecr create-pull-through-cache-rule \
  --ecr-repository-prefix dockerhub \
  --upstream-registry-url registry-1.docker.io \
  --credential-arn arn:aws:secretsmanager:us-east-1:123456789012:secret:ecr-pullthroughcache/dockerhub

# Usar: em vez de "nginx:1.27", referenciar
docker pull 123456789012.dkr.ecr.us-east-1.amazonaws.com/dockerhub/library/nginx:1.27
```

Permissões necessárias: `ecr:CreatePullThroughCacheRule`, e para o primeiro pull criar repositório/importar camadas (`ecr:CreateRepository`, `ecr:BatchImportUpstreamImage`; confirmar nomes).

### 5.3 Boas práticas com pull through cache

1. **Referencie o ECR no Dockerfile/manifest** (`FROM <conta>.dkr.ecr...dockerhub/library/node:20-slim`) — assim, builds e clusters **não falam com o Docker Hub**.
2. **Fixe versões e digests** das imagens base; o cache preserva o que foi puxado.
3. **Aplique lifecycle** aos repositórios de cache (senão acumulam versões antigas).
4. **Escaneie** as imagens espelhadas e reprove bases com vulnerabilidades críticas.
5. **Controle quais registries** são permitidos (política interna + SCP) para evitar “portas dos fundos”.
6. Considere **curadoria**: para bases críticas, **copie e aprove** explicitamente em vez de cache automático (modelo de “golden images”).

## 6. Custos de armazenamento

### 6.1 Modelo (de memória — confirmar)

| Item | Cobrança |
|---|---|
| **Armazenamento** | **Por GB-mês** de dados de imagens armazenados (camadas únicas) |
| **Transferência de dados (saída)** | Pulls **na mesma região** para serviços AWS são **gratuitos** (confirmar); **entre regiões/internet** têm custo |
| **Scanning avançado (Inspector)** | Cobrado por **imagem escaneada** (separado) |
| **Replicação** | Armazenamento na região de destino + transferência entre regiões |
| **ECR Public** | Franquia gratuita; excedente cobrado (confirmar) |

### 6.2 Estimativa (raciocínio, **não cotação**)

```
Antes da limpeza:  40.000 imagens × média 250 MB únicos ≈ 10 TB
Preço ilustrativo: ≈ US$ 0,10/GB-mês  ⇒  ≈ US$ 1.000/mês

Depois (lifecycle):  4.000 imagens × 250 MB ≈ 1 TB  ⇒  ≈ US$ 100/mês
Economia ilustrativa: ~90% do custo de armazenamento
```

### 6.3 Alavancas de economia

- **Lifecycle policies** em **todos** os repositórios (incluindo os de cache e build).
- **Imagens menores** (multi-stage, slim/distroless): cada MB menor multiplica por todas as versões.
- **Evitar duplicação** de repositórios idênticos entre regiões sem necessidade (replicação só para o que realmente precisa).
- **Pull dentro da região** (evitar transferência inter-região).
- **Vigiar `untagged`**: re-pushes e builds multi-arch geram resíduos.
- **Custo por repositório** com **tags de alocação** (via AWS Cost Explorer; atente para o suporte a tags em repositórios).

## 7. Boas práticas (checklist)

- [ ] **Lifecycle policy** em todo repositório, validada com **preview**
- [ ] Regra para **untagged** e para **branches/PRs** com retenção curta
- [ ] Retenção **por contagem** nas releases (nunca expirar o que está implantado)
- [ ] **Tag immutability** nos repositórios de produção
- [ ] **Pull through cache** para bases públicas + lifecycle nos espelhos
- [ ] **Templates de criação** de repositórios para padronizar
- [ ] **IAM/SCP** impedindo exclusões indevidas
- [ ] **Relatório mensal** de tamanho/quantidade por repositório

## 8. Erros comuns

- **Ativar lifecycle sem preview** e expirar a imagem de produção.
- **Regra `any` com prioridade menor** que as específicas → engole tudo.
- **Retenção por idade** em releases estáveis: a imagem em uso “envelhece” e é apagada.
- **Tags imutáveis + `latest`/`prod`** no mesmo repositório → falha de pipeline.
- **Confiar que o ECR protege imagens em uso**: ele não sabe o que o cluster referencia.
- **Pull through cache sem lifecycle**: espelhos crescem indefinidamente.
- **Credenciais upstream expostas** em vez de **Secrets Manager**.
- **Esquecer repositórios de teste/legados** acumulando custo.

## 9. Troubleshooting

| Sintoma | Causa provável | Ação |
|---|---|---|
| Deploy falha com `ImagePullBackOff` após limpeza | Lifecycle expirou a imagem referenciada | Reconstruir/restaurar a imagem (rebuild do commit); revisar regras |
| Lifecycle “não está apagando” | Prioridade/seleção erradas, execução assíncrona, imagens recentes demais | Usar **preview**; revisar `rulePriority`, `tagPrefixList`, `countNumber` |
| Pull through cache falha | Sem credencial/segredo, permissão de criação de repositório, prefixo errado | Verificar regra, segredo no Secrets Manager e IAM |
| Imagem do cache desatualizada | Janela de atualização do upstream | Aguardar o próximo ciclo ou forçar novo pull conforme documentação |
| `ImageTagAlreadyExistsException` | Tags imutáveis | Tag única (versão + SHA) |
| Custo de ECR inesperado | Sem lifecycle; imagens grandes; replicação desnecessária | Auditar com `describe-images`; limpar e replicar só o necessário |

## 10. Resumo rápido

- **Lifecycle policies** expiram imagens por **status de tag, prefixo, contagem ou idade**; regras por **prioridade**, `any` por último; **sempre use o preview**.
- O ECR **não protege imagens em uso**: retenha **por contagem** as releases e mantenha o que a produção referencia.
- **Tag immutability** impede sobrescrita e melhora rastreabilidade; evite tags deslizantes (`latest`, `prod`) no mesmo repositório.
- **Pull through cache** espelha registries públicos no ECR: evita **rate limits**, reduz dependência externa e risco de supply chain; aplique **lifecycle** e **scan**.
- **Custos**: armazenamento por GB-mês (principal alavanca = lifecycle + imagens menores); pulls na mesma região são baratos.

2. Por que `tagStatus: any` deve ter a maior prioridade numérica?
3. O que acontece se uma regra expirar a imagem que o ECS referencia?
4. Para que serve o preview de lifecycle?
5. Que efeito tem a imutabilidade de tags num push repetido da mesma tag?
6. Que problemas o pull through cache ajuda a resolver?
7. Qual a principal alavanca de redução de custo de armazenamento?

**Respostas:**

1. Pela `rulePriority`: a primeira regra (menor número) que seleciona a imagem a captura, e as demais não a reavaliam.
2. Porque `any` casa com todas as imagens e engoliria as imagens que as regras mais específicas deveriam tratar.
3. Novos pulls (por exemplo, em um nó novo) falham, pois o ECR não sabe que a imagem está em uso; é preciso reconstruir/restaurar a imagem.
4. Mostrar o que seria expirado sem apagar nada, validando as regras antes de ativá-las.
5. O push é recusado (`ImageTagAlreadyExistsException`), preservando a imagem original da tag.
6. Rate limits de registries públicos, dependência da internet e risco de supply chain, além de latência e custo de NAT.
7. Lifecycle policies (junto com imagens menores): reduzem o volume de dados armazenados.
