### 5.1.1.1. Segurança do ECR — repository policies e IAM, KMS, scanning básico e avançado com Inspector, assinatura de imagens, VPC endpoints e hardening

> [!warning] Aviso
> Recursos de scanning (básico vs avançado/Inspector), assinatura de imagens (AWS Signer, Notation, Cosign), VPC endpoints e nomes de políticas gerenciadas são **de memória e mudam**. **Confirme na documentação do ECR, do Inspector e do AWS Signer.** Políticas e comandos são ilustrativos e **não foram executados**. Trate qualquer política como ponto de partida, não como configuração pronta.

## 1. Por que o registry é um alvo

O ECR é um ponto único por onde **todo o seu código em execução passa**. Quem controla o registry controla **o que roda em produção**:

| Ameaça | Exemplo | Impacto |
|---|---|---|
| **Substituição de imagem** | Alguém re-envia `1.4.2` com código malicioso | Backdoor em produção sem novo deploy visível |
| **Imagem vulnerável** | Base desatualizada com CVE crítica | Exploração remota |
| **Credenciais em camadas** | `.env` ou chave embutida na imagem | Vazamento a quem puder baixar a imagem |
| **Acesso excessivo** | `ecr:*` para o CI inteiro | Exclusão/adulteração em massa |
| **Imagem pública acidental** | Repositório no ECR Public | Código proprietário exposto |
| **Supply chain upstream** | Imagem base alterada no Docker Hub | Código de terceiros comprometido entra no build |
| **Exfiltração** | Pull por identidade indevida | Cópia do software da empresa |

Defesa em camadas: **identidade (IAM/policies)** → **integridade (tags imutáveis, digest, assinatura)** → **conteúdo (scanning)** → **dados (KMS)** → **rede (VPC endpoints)** → **auditoria (CloudTrail)**.

## 2. Controle de acesso: IAM e repository policy

### 2.1 Dois mecanismos que se somam

| Mecanismo | Onde fica | Para quê |
|---|---|---|
| **Política de identidade (IAM)** | Anexada a roles/usuários | O que **aquela identidade** pode fazer |
| **Repository policy** | No repositório (recurso) | **Quem** (inclusive outras contas) pode agir **nesse repositório** |
| **Registry policy** | No registry (conta × região) | Permissões de **replicação** e **pull through cache** entre contas |

Na **mesma conta**, basta **uma** das duas permitir (a menos que haja `Deny`). **Entre contas**, **as duas** precisam permitir.

### 2.2 Separação de papéis (princípio do menor privilégio)

| Identidade | Pode | Não pode |
|---|---|---|
| **CI/Build** | `GetAuthorizationToken`; **push** no repositório do projeto | Excluir imagens/repositórios; alterar policies; push em repositórios de outros times |
| **Runtime** (task execution role, role do nó) | **Pull** | Push, excluir |
| **Plataforma/Admin** | Criar repositórios, definir lifecycle, policies | Operações diárias de CI |
| **Segurança/Auditoria** | **Leitura** de configurações e findings | Alterar |
| **Humanos (desenvolvedores)** | **Pull** (para depuração) em DEV; **nada** em PROD por padrão | Push manual em PROD |

Exemplo de política do **CI** (push em um repositório):

```json
{
  "Version": "2012-10-17",
  "Statement": [
    { "Sid": "Login", "Effect": "Allow", "Action": "ecr:GetAuthorizationToken", "Resource": "*" },
    { "Sid": "PushNoRepo", "Effect": "Allow",
      "Action": ["ecr:BatchCheckLayerAvailability","ecr:InitiateLayerUpload","ecr:UploadLayerPart",
                 "ecr:CompleteLayerUpload","ecr:PutImage","ecr:BatchGetImage","ecr:GetDownloadUrlForLayer"],
      "Resource": "arn:aws:ecr:us-east-1:123456789012:repository/pedidos/api" }
  ]
}
```

### 2.3 Repository policy: restringindo pulls

Exemplo de **negar** acesso fora da organização (ilustrativo):

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Sid": "SomenteOrganizacao",
    "Effect": "Deny",
    "Principal": "*",
    "Action": ["ecr:BatchGetImage","ecr:GetDownloadUrlForLayer"],
    "Condition": { "StringNotEquals": { "aws:PrincipalOrgID": "o-exemplo12345" } }
  }]
}
```

Condições úteis: **`aws:PrincipalOrgID`** (limitar à organização), **`aws:SourceVpce`/`aws:SourceVpc`** (exigir caminho privado), **`aws:PrincipalArn`**, tags de recurso (ABAC).

### 2.4 Guardrails de organização

- **SCP** negando `ecr:DeleteRepository`, `ecr:PutImageTagMutability` (para MUTABLE) e `ecr:SetRepositoryPolicy` fora de roles de plataforma;
- **Permission boundaries** para roles de CI;
- **IAM Access Analyzer** para detectar **repositórios acessíveis externamente**;
- **AWS Config** (regras gerenciadas para ECR: scan on push, tag immutability, lifecycle, política pública; confirmar nomes) para **conformidade contínua**.

## 3. Integridade: imutabilidade, digest e assinatura

### 3.1 Camada 1 — Tags imutáveis e digest

- **Tag immutability** impede a sobrescrita de uma tag (ver a folha de ciclo de vida).
- **Implante por digest** (`image@sha256:...`): o conteúdo é **verificável** por hash; mesmo uma tag adulterada não afeta um deploy por digest.

### 3.2 Camada 2 — Assinatura de imagens

A assinatura prova **quem** publicou a imagem e que ela **não foi alterada** desde então.

| Abordagem | Descrição (de memória — confirmar) |
|---|---|
| **AWS Signer + Notation** | Assinatura com perfil de assinatura gerenciado e o padrão **Notary Project/Notation**; integração com ECR |
| **Cosign (Sigstore)** | Assinatura *keyless* (OIDC) ou com chaves KMS; muito usada com Kubernetes |
| **Armazenamento** | A assinatura é guardada **como artefato OCI** no mesmo repositório, referenciando o digest da imagem |

Fluxo recomendado:

```
CI: build → push → scan limpo → ASSINAR o digest ─▶ ECR (imagem + assinatura)
                                              │
Admissão (EKS): Kyverno/Gatekeeper/Ratify verifica a assinatura ─▶ só então permite o pod
```

Pontos de atenção:

- **Verificar na entrada** (admission controller) — assinar sem verificar não protege nada.
- **Chaves/perfis** sob controle restrito (KMS/Signer), com **rotação** e **auditoria**.
- **Provenance/SBOM**: anexe **SBOM** (SPDX/CycloneDX) e **atestados de build** (SLSA) como artefatos associados.

### 3.3 Camada 3 — Origem confiável do build

- Builds em **ambiente efêmero e controlado** (CodeBuild/Actions com OIDC), não em máquinas pessoais.
- **Bases pinadas por digest** (`FROM ...@sha256:...`) e **espelhadas** via pull through cache/curadoria.
- Proibir `docker push` manual em produção (SCP/IAM + auditoria).

## 4. Scanning de vulnerabilidades

### 4.1 Básico vs avançado (de memória — confirmar)

| | **Scanning básico** | **Scanning avançado (Amazon Inspector)** |
|---|---|---|
| Mecanismo | Scanner de código aberto (CVEs de **pacotes de SO**) | **Inspector**: SO + **dependências de linguagem** (pip, npm, Maven etc.) |
| Quando roda | **On push** ou **manual** | **On push** e **contínuo** (reavalia quando surgem novas CVEs) |
| Resultado | Findings por severidade no ECR | Findings no ECR **e no Inspector** (priorização por **score**/exploitabilidade, SBOM) |
| Integração | Evento no EventBridge | EventBridge/Security Hub/consolidação multi-conta |
| Custo | Sem custo adicional (confirmar) | **Cobrado por imagem** escaneada |
| Uso | Higiene mínima | **Produção/conformidade** |

```bash
# Habilitar scan on push em um repositório (básico)
aws ecr put-image-scanning-configuration --repository-name pedidos/api \
  --image-scanning-configuration scanOnPush=true

# Escaneamento no nível do registry (básico/avançado; confirmar sintaxe atual)
aws ecr put-registry-scanning-configuration --scan-type ENHANCED \
  --rules '[{"scanFrequency":"CONTINUOUS_SCAN","repositoryFilters":[{"filter":"pedidos","filterType":"WILDCARD"}]}]'

# Ver resultados
aws ecr describe-image-scan-findings --repository-name pedidos/api --image-id imageTag=1.4.2-a1b2c3d
```

### 4.2 Como usar os resultados

1. **Gate no pipeline**: reprovar o build com **CRITICAL/HIGH** (com exceções justificadas e prazo).
2. **Priorizar** por **explorabilidade** e **exposição** (imagem em serviço público vs batch interno).
3. **Corrigir na base**: atualizar a imagem base e reconstruir; ver se há **versão corrigida** disponível (campo *fixed in*).
4. **Contínuo**: imagens antigas em produção podem ganhar **novos achados** — alarme via **EventBridge/Security Hub** e **rebuild** periódico.
5. **Exceções (VEX/waiver)**: documentar CVEs não aplicáveis, com data de revisão.

> [!info] Limites do scanning
> Scanners detectam **CVEs conhecidas** em pacotes; **não** detectam código malicioso, segredos embutidos nem má configuração. Complemente com **detecção de segredos** (no CI), revisão de Dockerfile (hadolint), análise de IaC e **runtime security** (GuardDuty Runtime Monitoring, Falco).

## 5. Criptografia (KMS)

| Camada | Padrão | Opção reforçada |
|---|---|---|
| **Em trânsito** | **TLS** em todos os acessos | — |
| **Em repouso** | Criptografia gerenciada (AES-256) no armazenamento | **KMS gerenciada pelo cliente (CMK)** por repositório |

```bash
aws ecr create-repository --repository-name pedidos/api \
  --encryption-configuration encryptionType=KMS,kmsKey=arn:aws:kms:us-east-1:123456789012:key/<id>
```

Cuidados:

- A **criptografia é definida na criação** do repositório (não se troca depois — confirmar; migre criando outro e copiando).
- A **key policy** deve permitir o uso aos principais que fazem push/pull (via ECR); **chaves desativadas/apagadas** tornam imagens inacessíveis → controle e alarme (CloudTrail/EventBridge) para `DisableKey`/`ScheduleKeyDeletion`.
- Em **cross-account**, o consumidor precisa de permissão também na **key policy** da CMK.
- CMK aumenta **custo e complexidade**; adote onde a **política de segurança/regulação** exigir.

## 6. Rede: VPC endpoints

Para puxar/enviar imagens **sem internet**:

| Endpoint | Tipo | Função |
|---|---|---|
| **`com.amazonaws.<região>.ecr.api`** | Interface | API do ECR (`GetAuthorizationToken`, `DescribeImages`...) |
| **`com.amazonaws.<região>.ecr.dkr`** | Interface | Protocolo Docker (**manifests**) |
| **`com.amazonaws.<região>.s3`** | **Gateway** | Download das **camadas** (armazenadas no S3 gerenciado) |
| **`com.amazonaws.<região>.logs`** | Interface | Para logs de tasks (Fargate/awslogs) |

Controles:

- **Endpoint policies** limitando ações e repositórios (e, no S3 gateway, o acesso aos **buckets de camadas do ECR** exigidos pela documentação).
- **Security group** dos endpoints de interface permitindo **443** só das subnets de workload.
- Condição **`aws:SourceVpce`** nas repository policies para **obrigar** o caminho privado.

## 7. Auditoria e detecção

| Necessidade | Ferramenta |
|---|---|
| Quem fez **push/pull/delete**? | **CloudTrail** (eventos de dados do ECR: pull/push — confirmar tipos de evento e opções de logging) |
| Alterações de **policies/configuração** | CloudTrail (gerência) + EventBridge → alarmes |
| **Conformidade** contínua | **AWS Config** (regras de ECR), **Security Hub** |
| **Findings de vulnerabilidades** | Inspector → Security Hub → ticket/pager |
| **Comportamento anômalo** (pull massivo, push fora de horário) | **GuardDuty** (confirmar cobertura de ECR), alarmes customizados |
| **Imagens implantadas** vs **imagens aprovadas** | Admission controller + inventário (SBOM) |

## 8. Checklist de endurecimento

- [ ] **Repositórios privados**; nenhum dado proprietário no ECR Public
- [ ] **Roles separadas**: CI (push), runtime (pull), plataforma (admin), segurança (read)
- [ ] **Repository policies** com `aws:PrincipalOrgID`; cross-account com **ambos os lados**
- [ ] **Tag immutability** + deploy por **digest**
- [ ] **Assinatura** de imagens (Signer/Notation ou Cosign) e **verificação** na admissão
- [ ] **Scan on push** (e **avançado/contínuo** em produção) com **gate** no pipeline
- [ ] **Bases pinadas por digest** e espelhadas (pull through cache/curadoria)
- [ ] **KMS CMK** onde exigido; alarmes de desativação/exclusão de chave
- [ ] **VPC endpoints** (`ecr.api`, `ecr.dkr`, S3) e policies de endpoint
- [ ] **SCP/boundaries** contra exclusões e mudanças indevidas
- [ ] **CloudTrail + Config + Security Hub** ativos; revisão periódica de acessos
- [ ] **Sem segredos** em imagens (scan de segredos no CI; usar Secrets Manager/Parameter Store em runtime)
- [ ] **Imagens mínimas** (distroless/slim), **usuário não-root**, sem ferramentas desnecessárias

## 9. Erros comuns

- **`ecr:*` no CI**, incluindo exclusão e alteração de policies.
- **Esquecer o lado IAM** (ou o da repository policy) em cross-account.
- **Assinar sem verificar**: ninguém barra imagens não assinadas.
- **Scan on push apenas**: imagens antigas ficam sem reavaliação; novas CVEs passam despercebidas.
- **Gate rígido sem exceções**: o time contorna a política (ex.: tag `latest` em outro repositório).
- **Segredos na imagem** (`.env`, chaves SSH, tokens de pacote em `ARG`).
- **Confiar na tag**: política de aprovação baseada em tag mutável.
- **Repository policy com `Principal: "*"` sem condições**.
- **CMK apagada/desativada** sem plano de recuperação.

## 10. Troubleshooting

| Sintoma | Causa provável | Ação |
|---|---|---|
| `denied: not authorized` | IAM ou repository policy ausente/negada | Verificar ambas, `Deny` explícito e condições (`aws:SourceVpce`, `PrincipalOrgID`) |
| Pull falha só em subnet privada | Falta de endpoints ou policy de endpoint restritiva | Criar/ajustar `ecr.api`, `ecr.dkr`, S3 |
| Erro de KMS no pull/push | Key policy sem o principal; chave desativada | Ajustar a key policy; reabilitar a chave |
| Scan não roda | Scan on push desabilitado; tipo de scan do registry diferente | Revisar a configuração do repositório/registry |
| Findings “desapareceram” | Re-scan contínuo reavaliou (CVE corrigida ou fora do escopo) | Consultar o histórico no Inspector |
| Pod bloqueado pelo admission controller | Imagem sem assinatura válida / fora do registry permitido | Assinar o digest correto; revisar a política |
| Assinatura não encontrada | Assinatura aponta para outro digest (retag/rebuild) | Assinar o digest exato implantado |

## 11. Resumo rápido

- Segurança do ECR = **identidade + integridade + conteúdo + dados + rede + auditoria**.
- **IAM** (CI = push; runtime = pull) + **repository/registry policy**; cross-account exige **ambos**.
- **Integridade**: **tags imutáveis**, deploy por **digest**, **assinatura** (Signer/Notation, Cosign) **verificada na admissão**.
- **Scanning**: básico (pacotes de SO) vs **avançado/Inspector** (SO + linguagens, **contínuo**); use como **gate** e acompanhe achados novos; scanners **não** pegam segredos nem malware.
- **KMS CMK** opcional (definida na criação); cuidado com key policy e exclusão.
- **VPC endpoints** (`ecr.api`, `ecr.dkr`, S3 gateway) + condições `aws:SourceVpce`.
- **CloudTrail/Config/Security Hub/GuardDuty** e **SCPs** completam a governança.

## 🧩 Quiz de Fixação

1. Em cross-account, por que são necessárias duas permissões?
2. Qual a diferença entre scanning básico e avançado?
3. Por que implantar por digest aumenta a segurança?
4. Para que serve verificar assinaturas no admission controller?
5. Que endpoints permitem pull do ECR em subnet privada sem NAT?
6. O que o scanning de imagens não detecta?
7. Quais permissões o CI deve ter e quais deve **não** ter?

**Respostas:**

1. Porque a repository policy (recurso) e o IAM da identidade (conta consumidora) precisam permitir a ação; na mesma conta basta uma delas.
2. O básico verifica CVEs de pacotes de SO no push; o avançado (Inspector) cobre também dependências de linguagem e é contínuo, reavaliando quando surgem novas CVEs.
3. Porque o digest identifica o conteúdo por hash: mesmo que uma tag seja adulterada ou reapontada, o deploy por digest continua usando a imagem verificada.
4. Para garantir que só imagens assinadas por quem é confiável (e não alteradas) entrem no cluster; assinar sem verificar não protege.
5. `ecr.api` e `ecr.dkr` (interface) e o gateway endpoint do S3 (mais `logs`, se usar awslogs).
6. Segredos embutidos, código malicioso e más configurações; ele só encontra CVEs conhecidas em pacotes.
7. Deve ter `GetAuthorizationToken` e push no repositório do projeto; não deve ter exclusão de imagens/repositórios, alteração de policies nem acesso a outros repositórios.
