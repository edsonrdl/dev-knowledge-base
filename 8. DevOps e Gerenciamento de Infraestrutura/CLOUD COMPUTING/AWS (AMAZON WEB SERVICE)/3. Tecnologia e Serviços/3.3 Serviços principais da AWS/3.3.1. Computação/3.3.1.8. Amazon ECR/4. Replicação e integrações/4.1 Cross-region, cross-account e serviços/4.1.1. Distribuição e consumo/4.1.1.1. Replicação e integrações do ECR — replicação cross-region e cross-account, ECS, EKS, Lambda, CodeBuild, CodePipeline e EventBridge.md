### 4.1.1.1. Replicação e integrações do ECR — replicação cross-region e cross-account, ECS, EKS, Lambda, CodeBuild, CodePipeline e EventBridge

> [!warning] Aviso
> Detalhes de replicação (filtros, latência, regiões), requisitos de cada serviço consumidor (Lambda, EKS, ECS) e nomes de eventos abaixo são **de memória e mudam**. **Confirme na documentação do ECR e de cada serviço.** Políticas, JSONs e comandos são ilustrativos e **não foram executados**. IDs de conta (`111111111111` build, `222222222222` produção) e regiões são fictícios.

## 1. Por que distribuir imagens

Uma imagem enviada ao ECR existe **só na conta e região** onde foi publicada. Mas a vida real pede:

- **Produção em outra região** (latência, DR, multi-região): a task em `sa-east-1` precisa da imagem **perto**, não de `us-east-1`;
- **Contas separadas** (build, homologação, produção): a conta de produção precisa **puxar** imagens construídas em outra conta;
- **Vários consumidores** (ECS, EKS, Lambda, CodeBuild, SageMaker) com **mecanismos de autenticação diferentes**;
- **Automação**: reagir a “imagem publicada” ou “scan terminou” para disparar deploys e alertas.

```
                 ┌─────────── Conta BUILD (111111111111) ───────────┐
   CI ──push───▶ │  ECR us-east-1  pedidos/api:1.4.2-a1b2c3d        │
                 └──────────┬───────────────────────┬───────────────┘
              replicação    │ cross-region          │ cross-account (repository policy ou replicação)
                            ▼                       ▼
                 ECR sa-east-1 (mesma conta)   Conta PROD (222222222222): ECR us-east-1 / sa-east-1
                            │                       │
                       ECS/EKS/Lambda          ECS/EKS/Lambda (pull local, rápido)
```

## 2. Replicação do ECR

### 2.1 O que é

A **replicação** copia automaticamente imagens **após o push** para **outras regiões** e/ou **outras contas**, conforme **regras** configuradas **no registry** (nível de registry, não de repositório).

| Característica | Detalhe (de memória — confirmar) |
|---|---|
| **Gatilho** | Push de imagem (nova ou re-tag) no repositório de origem |
| **Destino** | Região e/ou conta; **cria o repositório** no destino se não existir |
| **Filtros** | Por **prefixo de nome de repositório** (replica só `pedidos/*`) |
| **Assíncrona** | Pode levar de segundos a minutos; **não** é sincronização bidirecional |
| **O que replica** | Imagens e tags enviadas **depois** da regra; imagens antigas **não** são copiadas retroativamente (confirmar) |
| **Exclusões** | **Deletes não se propagam** — apagar na origem não apaga no destino |
| **Configurações** | Lifecycle e policies do repositório **não** são copiadas; cada destino tem as suas |
| **Custo** | Armazenamento no destino + **transferência inter-região** |

### 2.2 Configuração (registry-level)

```json
{
  "rules": [
    {
      "destinations": [
        { "region": "sa-east-1", "registryId": "111111111111" },
        { "region": "us-east-1", "registryId": "222222222222" }
      ],
      "repositoryFilters": [
        { "filter": "pedidos", "filterType": "PREFIX_MATCH" }
      ]
    }
  ]
}
```

```bash
aws ecr put-replication-configuration --replication-configuration file://replicacao.json
aws ecr describe-registry          # mostra a replicação configurada
```

### 2.3 Replicação cross-account — requisitos

Para replicar para **outra conta**, a conta **destino** precisa **autorizar** a origem via **registry permissions policy** (política no nível do registry do destino):

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Sid": "PermitirReplicacaoDaContaBuild",
    "Effect": "Allow",
    "Principal": { "AWS": "arn:aws:iam::111111111111:root" },
    "Action": ["ecr:CreateRepository", "ecr:ReplicateImage"],
    "Resource": "arn:aws:ecr:us-east-1:222222222222:repository/*"
  }]
}
```

```bash
# Na conta de DESTINO (222222222222) — ilustrativo
aws ecr put-registry-policy --policy-text file://registry-policy.json
```

### 2.4 Quando replicar (e quando não)

| Situação | Replicar? |
|---|---|
| Workloads em **várias regiões** | **Sim**: pull local, menor latência e independência de região |
| **DR** em outra região | **Sim**, com validação periódica de que as imagens existem lá |
| **Contas** de produção isoladas | **Sim**, ou use cross-account pull com repository policy (ver 3) |
| Região única, conta única | **Não** — custo sem benefício |
| Imagens grandes e raramente usadas na região secundária | Avalie: replicar **só** o necessário (prefixos) |
| Fluxo precisa da imagem **imediatamente** no destino | Cuidado: replicação é **assíncrona** — o deploy pode correr antes da cópia |

> [!tip] Sincronização no pipeline
> Antes de implantar na região secundária, **verifique que o digest existe** lá (`describe-images`) ou publique **explicitamente** nas duas regiões no CI, em vez de assumir a replicação concluída.

## 3. Acesso cross-account sem replicar

Em vez de copiar, a conta de produção pode **puxar direto** da conta de build:

**Repository policy** no repositório de origem (conta 111111111111):

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Sid": "PullDaContaProd",
    "Effect": "Allow",
    "Principal": { "AWS": "arn:aws:iam::222222222222:root" },
    "Action": [
      "ecr:BatchGetImage",
      "ecr:GetDownloadUrlForLayer",
      "ecr:BatchCheckLayerAvailability"
    ]
  }]
}
```

E, na conta 222222222222, a **role de execução** (task execution role / role do nó) precisa de permissão IAM equivalente ao ARN do repositório de origem. **Ambos os lados** (policy do recurso + IAM da identidade) devem permitir.

| Modelo | Vantagens | Desvantagens |
|---|---|---|
| **Pull cross-account** | Sem cópia; uma única fonte da verdade | Pull cruza contas (e regiões, se diferentes → custo/latência); dependência da conta de build |
| **Replicação para a conta de prod** | Prod **autossuficiente**; falhas na conta de build não afetam deploys | Duplicação de armazenamento; lag assíncrono |
| **Hub dedicado** (conta de artefatos) | Governança centralizada | Mais um ponto crítico a proteger |

## 4. Integração com serviços consumidores

### 4.1 Amazon ECS (EC2 e Fargate)

- A **task execution role** precisa de `ecr:GetAuthorizationToken` + ações de pull (a política gerenciada `AmazonECSTaskExecutionRolePolicy` cobre o caso na mesma conta).
- A task definition usa o URI completo (preferencialmente **digest**).
- **Fargate** em subnet privada exige **VPC endpoints** (`ecr.api`, `ecr.dkr` e gateway **S3**) ou NAT, pois as camadas vêm do S3.

```json
{ "name": "app", "image": "123456789012.dkr.ecr.us-east-1.amazonaws.com/pedidos/api@sha256:9f86d0..." }
```

### 4.2 Amazon EKS

- **Nós EC2**: a **role do nó** (instance profile) precisa de pull (`AmazonEC2ContainerRegistryReadOnly`, ou equivalente mais restrito).
- **Fargate no EKS**: **pod execution role**.
- **Cross-account**: a role do nó em prod + repository policy na origem.
- **`imagePullPolicy`**: com digest, `IfNotPresent` é suficiente e eficiente.
- Boas práticas: **admission controllers** (Kyverno/OPA Gatekeeper) para **permitir apenas imagens do seu registry** e **verificar assinaturas** (ver a folha de segurança).

### 4.3 AWS Lambda (imagens de container)

| Ponto | Detalhe (de memória — confirmar) |
|---|---|
| **Tamanho** | Imagem até **10 GB** |
| **Origem** | **ECR na mesma região** da função (pode ser de outra conta com policy adequada) |
| **Base** | Imagens base da AWS para Lambda ou imagens próprias que implementem a **Runtime API** |
| **Permissões** | A função precisa que o **serviço Lambda** consiga fazer pull: repository policy permitindo `ecr:BatchGetImage`/`GetDownloadUrlForLayer` ao principal `lambda.amazonaws.com` (com condição de ARN da função) em cenários cross-account/ restritos |
| **Atualizações** | Alterar a imagem **não** atualiza a função sozinha: faça `update-function-code --image-uri` (por digest) |
| **Cold start** | Imagens grandes aumentam o tempo de cold start; mantenha-as enxutas |

```bash
aws lambda update-function-code --function-name criar-pedido \
  --image-uri 123456789012.dkr.ecr.us-east-1.amazonaws.com/pedidos/api@sha256:9f86d0...
```

### 4.4 AWS CodeBuild e CodePipeline

- **CodeBuild como origem do push**: role do projeto com permissões de push; **modo privilegiado** para `docker build` (ver a folha de CodeBuild).
- **CodeBuild usando imagem do ECR** como ambiente de build: a role precisa de pull; boa prática para **imagens de build padronizadas** da empresa.
- **CodePipeline**: ação **ECR (source)** dispara o pipeline quando uma **nova imagem/tag** é publicada; as ações de deploy (ECS, CloudFormation) consomem a imagem.
- **Artefato com digest**: gere `imagedefinitions.json`/`imageDetail.json` com o **digest** para deploy imutável.

### 4.5 Outros consumidores

| Serviço | Observação |
|---|---|
| **AWS App Runner** | Fonte de imagem do ECR (privado ou público) com **role de acesso** |
| **AWS Batch** | Job definitions referenciam imagens do ECR |
| **Amazon SageMaker** | Imagens de treinamento/inferência no ECR |
| **AWS Proton / Copilot / Elastic Beanstalk (Docker)** | Referenciam ECR nas definições |
| **Máquinas on-premises / Anywhere** | Pull com **IAM Roles Anywhere**/credenciais temporárias + `get-login-password` |

## 5. EventBridge: reagindo a eventos do ECR

O ECR emite eventos ao **Amazon EventBridge**:

| Evento (detail-type, de memória) | Quando |
|---|---|
| **ECR Image Action** | Push (`PUSH`), delete (`DELETE`) e ações de **replicação** de imagem |
| **ECR Image Scan** | Conclusão do **scan básico** (com contagem de findings) |
| **ECR Pull Through Cache Action** | Ações do pull through cache |
| **ECR Inspector Scan** (scanning avançado, via Inspector) | Resultados do scan contínuo/avançado |

Exemplo de **regra** (ilustrativa) para disparar uma Lambda quando uma imagem de `pedidos/api` for enviada com sucesso:

```json
{
  "source": ["aws.ecr"],
  "detail-type": ["ECR Image Action"],
  "detail": {
    "action-type": ["PUSH"],
    "result": ["SUCCESS"],
    "repository-name": [{ "prefix": "pedidos/" }]
  }
}
```

Casos de uso:

1. **Deploy automático** em DEV quando uma tag `dev-*` chega.
2. **Notificação** (SNS/Slack) de novas versões de produção.
3. **Bloqueio**: Lambda que **verifica o resultado do scan** e **marca/retira** imagens com vulnerabilidades críticas (ou abre ticket).
4. **Auditoria**: enviar eventos `DELETE` a um canal de segurança.
5. **Orquestração de promoção**: após scan limpo, copiar/retag para o repositório de produção.

```json
{
  "source": ["aws.ecr"],
  "detail-type": ["ECR Image Scan"],
  "detail": { "scan-status": ["COMPLETE"], "finding-severity-counts": { "CRITICAL": [{ "numeric": [">", 0] }] } }
}
```

## 6. Padrão recomendado: pipeline multi-conta com promoção por digest

```
1. CI (conta BUILD):   build → push (tag única) → scan → guarda DIGEST
2. Replicação/pull:    conta HML e PROD enxergam o mesmo digest (replicação ou repository policy)
3. Deploy HML:         task/pod/função com image@digest  → testes
4. Aprovação manual:   (CodePipeline) e checagem do scan limpo
5. Deploy PROD:        o MESMO digest, via role da conta PROD
```

Controles:

- **Contas separadas** com **roles mínimas**: CI só **push** na conta BUILD; PROD só **pull**.
- **Assinatura de imagem** (ver a folha de segurança) verificada na admissão (EKS) ou no pipeline.
- **Tag immutability** nos repositórios de release.
- **SCP** impedindo `ecr:DeleteRepository` e mudança de policies em PROD.

```bash
aws ecr describe-images --region sa-east-1 --repository-name pedidos/api \
  --image-ids imageDigest=sha256:9f86d0... --query 'imageDetails[0].imageDigest'

# Ver a policy de um repositório (cross-account)

# Verificar o resultado do scan de uma imagem

```

## 8. Erros comuns

- **Assumir replicação instantânea** e implantar na região secundária antes de a imagem chegar.
- **Esperar que deletes e lifecycle sejam replicados**: cada destino precisa do seu.
- **Esquecer a registry policy** no destino cross-account.
- **Permitir só o IAM da identidade** **ou** só a repository policy: em cross-account, **ambos** precisam permitir.
- **Lambda em região diferente da imagem**: a imagem tem de estar na **mesma região** da função.
- **Atualizar a imagem e esperar que o Lambda “pegue sozinho”**: é preciso atualizar o código da função.
- **Fargate em subnet privada sem endpoints**: pull falha por timeout.
- **Regra de EventBridge ampla demais** disparando para todos os repositórios (loops de automação, custo).

## 9. Troubleshooting

| Sintoma | Causa provável | Ação |
|---|---|---|
| Imagem não aparece no destino | Replicação não configurada para o prefixo; push anterior à regra; falta de registry policy | Conferir `describe-registry`, filtros e a policy no destino |
| `CannotPullContainerError` em prod (cross-account) | Falta de repository policy na origem ou IAM na role de execução | Corrigir ambos os lados |
| Lambda “não consegue acessar a imagem” | ECR em outra região; policy sem principal `lambda.amazonaws.com` (cenários restritos) | Replicar para a região da função; ajustar a policy |
| Deploy na região secundária falha por imagem ausente | Replicação assíncrona não terminou | Esperar/validar digest; publicar em ambas as regiões |
| EventBridge não dispara | Padrão de evento incorreto; região diferente da do evento | Testar o padrão; criar a regra na região do registry |
| Custos de transferência altos | Pulls cross-region frequentes | Replicar para a região de uso; usar VPC endpoints |

## 10. Resumo rápido

- **Replicação** (nível de **registry**): copia **após o push** para outras **regiões/contas**, com filtro por **prefixo**; **assíncrona**; **não propaga deletes nem lifecycle**; cross-account exige **registry policy** no destino.
- **Alternativa**: **pull cross-account** com **repository policy + IAM** (ambos os lados).
- **Consumidores**: ECS (**execution role**), EKS (**role do nó**/Fargate), **Lambda** (imagem na **mesma região**, até 10 GB, atualizar por `update-function-code`), CodeBuild/CodePipeline.
- **EventBridge**: eventos de **push**, **scan**, **replicação** e **cache** para automação.
- Padrão: **build uma vez**, **promover o digest**, **contas separadas**, **assinatura** e **tags imutáveis**.

## 🧩 Quiz de Fixação

1. Em que nível a replicação do ECR é configurada e o que ela não replica?
2. O que a conta de destino precisa configurar para receber replicação cross-account?
3. Por que, em acesso cross-account sem replicação, são necessárias duas permissões?
4. Qual restrição de região vale para imagens de container no Lambda?
5. Que evento do EventBridge indica o push de uma imagem?
6. Por que verificar o digest no destino antes de implantar na região secundária?
7. Que endpoints a Fargate em subnet privada precisa para puxar imagens do ECR?

**Respostas:**

1. No nível de registry, com filtros por prefixo; não replica deletes, lifecycle policies nem permissões de repositório, e só copia imagens enviadas após a regra.
2. Uma registry permissions policy permitindo `ecr:CreateRepository` e `ecr:ReplicateImage` à conta de origem.
3. Porque a repository policy (do recurso) e o IAM da identidade (na conta consumidora) precisam permitir a mesma ação.
4. A imagem deve estar no ECR da mesma região da função Lambda.
5. `ECR Image Action` com `action-type` `PUSH` e `result` `SUCCESS`.
6. Porque a replicação é assíncrona; a imagem pode ainda não ter chegado quando o deploy começa.
7. Os endpoints de interface `ecr.api` e `ecr.dkr` e o gateway endpoint do S3 (ou uma rota via NAT).
