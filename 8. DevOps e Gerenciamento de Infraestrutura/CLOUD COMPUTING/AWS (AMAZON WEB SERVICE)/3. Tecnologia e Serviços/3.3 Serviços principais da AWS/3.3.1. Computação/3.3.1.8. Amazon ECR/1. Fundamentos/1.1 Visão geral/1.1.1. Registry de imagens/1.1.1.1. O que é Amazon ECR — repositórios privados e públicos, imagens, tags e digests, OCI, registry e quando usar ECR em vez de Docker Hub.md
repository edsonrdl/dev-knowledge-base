### 1.1.1.1. O que é Amazon ECR — repositórios privados e públicos, imagens, tags e digests, OCI, registry e quando usar ECR em vez de Docker Hub

> [!warning] Aviso
> Limites, preços, nomes de recursos e novidades (pull through cache, ECR Public, scanning, assinatura) abaixo são **de memória e mudam**. **Confirme na documentação do Amazon ECR e na página de preços.** Comandos, JSONs e Dockerfiles são ilustrativos e **não foram executados**. Registre IDs de conta e regiões reais só em ambiente seu — os exemplos usam `123456789012`.

## 1. O problema que o ECR resolve

Containers são empacotados como **imagens** (camadas de sistema de arquivos + metadados). Para rodar a mesma imagem em ECS, EKS, Lambda, Fargate ou na sua máquina, você precisa de um lugar **central, versionado, seguro e rápido** para guardá-las. Esse lugar é um **registry de containers**.

Perguntas que todo time acaba fazendo:

- **Onde** ficam as imagens de produção? Quem pode **enviar** (push) e quem pode **baixar** (pull)?
- Como garantir que o que roda em produção é **exatamente** a imagem que passou no pipeline?
- Como evitar o limite de **pull rate** de registries públicos no meio de um deploy?
- Como **escanear vulnerabilidades**, **replicar** para outra região e **limpar** imagens velhas?
- Como fazer isso **sem manter infraestrutura** (servidor de registry, armazenamento, certificados)?

O **Amazon Elastic Container Registry (ECR)** é o registry **gerenciado, compatível com OCI/Docker**, da AWS: armazena, gerencia e distribui imagens (e outros artefatos OCI), integrado ao **IAM**, ao **KMS**, ao **ECS/EKS/Lambda/CodeBuild** e à **rede da AWS**.

> [!info] Em uma frase
> **ECR é o “Docker Hub privado da AWS”** — com permissões do IAM, criptografia, scanning, replicação e integração nativa com os serviços de computação.

## 2. Vocabulário essencial

| Termo | Significado | Exemplo |
|---|---|---|
| **Registry** | A “conta” de registry, uma **por conta AWS e região** | `123456789012.dkr.ecr.us-east-1.amazonaws.com` |
| **Repository** | Coleção de versões de uma mesma imagem/aplicação | `pedidos/api` |
| **Image** | Conjunto de **camadas + manifest + config** | A imagem `pedidos/api:1.4.2` |
| **Tag** | Rótulo **mutável** (por padrão) que aponta para uma imagem | `1.4.2`, `latest`, `prod` |
| **Digest** | Hash **imutável** (`sha256:...`) do manifest; identifica o conteúdo | `pedidos/api@sha256:9f86d0...` |
| **Layer** | Camada de arquivos reaproveitada entre imagens | A camada do `FROM node:20-slim` |
| **Manifest / manifest list** | Descreve camadas; a lista agrupa variantes por arquitetura | `linux/amd64` + `linux/arm64` |
| **OCI** | Open Container Initiative: formato aberto de imagem e distribuição | Compatível com Docker, containerd, Podman |
| **Artifact OCI** | Outros conteúdos além de imagens (Helm charts, assinaturas, SBOMs) | Chart Helm em OCI |

### 2.1 Anatomia do endereço

```
123456789012 . dkr . ecr . us-east-1 . amazonaws.com / pedidos/api : 1.4.2
└── conta ──┘         └── região ──┘                  └─ repo ──┘  └ tag ┘

Por digest (imutável):  .../pedidos/api@sha256:9f86d081884c7d659a2feaa0c55ad015a3bf4f1b2b0b822cd15d6c15b0f00a08
```

Cada **conta × região** tem seu próprio registry; imagens **não** aparecem automaticamente em outras regiões (a menos que você ative a **replicação** — ver a folha de integrações).

## 3. Tags vs digests — o conceito mais importante

```
Repositório pedidos/api
 ├── tag latest ──┐
 ├── tag 1.4.2  ──┼──▶ digest sha256:aaa111... (imagem A)
 ├── tag prod   ──┘
 └── tag 1.4.3  ─────▶ digest sha256:bbb222... (imagem B)
```

- Uma **tag é um ponteiro**; o **digest é o conteúdo**. Duas imagens diferentes nunca compartilham digest; a **mesma tag pode ser reapontada** para outro digest (se o repositório permitir).
- **Problema clássico**: `latest` hoje é uma imagem; amanhã, outra. Um deploy “idêntico” traz código diferente.
- **Boa prática**: em produção, referencie **digest** (ou tags **imutáveis** com versão + commit, como `1.4.2-a1b2c3d`) e guarde o **digest implantado** no registro de release.

```bash
# Descobrir o digest de uma tag (ilustrativo)
aws ecr describe-images --repository-name pedidos/api --image-ids imageTag=1.4.2 \
  --query 'imageDetails[0].imageDigest' --output text
```

## 4. Repositórios privados e públicos

| | **ECR privado** | **ECR Public** |
|---|---|---|
| Visibilidade | Só quem tem permissão IAM/policy | **Qualquer pessoa** pode baixar (sem autenticação) |
| Endereço | `<conta>.dkr.ecr.<região>.amazonaws.com/<repo>` | `public.ecr.aws/<alias>/<repo>` |
| Autenticação do pull | **Obrigatória** | Opcional (autenticar eleva limites; confirmar) |
| Região | Por região | Console/serviço em **us-east-1**; distribuição global (confirmar) |
| Caso de uso | Aplicações da empresa | Imagens **open source** ou distribuição pública |
| Custo | Armazenamento + transferência | Armazenamento (com franquia); transferência de saída gratuita para pulls anônimos/autenticados dentro de limites (confirmar) |

Para imagens **da sua aplicação**: **privado, sempre**. ECR Public serve a quem **publica** imagens para a comunidade (ou espelha imagens base para evitar limites de outros registries).

## 5. Como o ECR guarda os dados

```
docker push ──▶ camadas (blobs) ──▶ Amazon S3 (gerenciado, com redundância multi-AZ)
                manifest/tags ───▶ metadados do repositório (ECR)
```

- As **camadas** são **deduplicadas**: se dez imagens usam a mesma camada base, ela é armazenada **uma vez** por repositório (a cobrança é pelo armazenamento total de dados únicos; confirmar granularidade por repositório vs registry).
- Dados **criptografados em repouso** (padrão: chave gerenciada; opção de **KMS**).
- Acesso por **HTTPS**; a comunicação interna é gerenciada pela AWS.
- **Alta disponibilidade** e durabilidade herdadas da infraestrutura gerenciada (sem você operar nada).

## 6. Primeiros passos (visão geral)

```bash
# 1) Criar um repositório privado (ilustrativo)
aws ecr create-repository --repository-name pedidos/api \
  --image-tag-mutability IMMUTABLE \
  --image-scanning-configuration scanOnPush=true \
  --encryption-configuration encryptionType=KMS

# 2) Autenticar o Docker no registry
aws ecr get-login-password --region us-east-1 | \
  docker login --username AWS --password-stdin 123456789012.dkr.ecr.us-east-1.amazonaws.com

# 3) Construir, marcar e enviar
docker build -t pedidos/api:1.4.2 .
docker tag pedidos/api:1.4.2 123456789012.dkr.ecr.us-east-1.amazonaws.com/pedidos/api:1.4.2
docker push 123456789012.dkr.ecr.us-east-1.amazonaws.com/pedidos/api:1.4.2

# 4) Listar e inspecionar
aws ecr list-images --repository-name pedidos/api
aws ecr describe-images --repository-name pedidos/api
```

O detalhamento de cada passo (autenticação, multi-arch, CI) está na folha de **Push e pull**.

## 7. ECR e o ecossistema de containers da AWS

```
Dev/CI ──push──▶ ECR ──pull──▶ ECS (EC2/Fargate)
                  │      ├────▶ EKS (nós EC2/Fargate)
                  │      ├────▶ Lambda (imagens de container até 10 GB)
                  │      ├────▶ App Runner, Batch, SageMaker
                  │      └────▶ CodeBuild (imagens de build/ambiente)
                  ├── Inspector (scanning)         ├── EventBridge (eventos de push/scan)
                  └── Replicação (região/conta)    └── KMS, IAM, CloudTrail
```

Por que a integração é um diferencial: o pull usa **credenciais do IAM** (task execution role, node role, role da função), **sem segredo de registry** para guardar, e trafega pela **rede da AWS** (com VPC endpoints, sem sair para a internet).

## 8. Quando usar ECR em vez de alternativas

| Cenário | Recomendação |
|---|---|
| Workloads em **ECS/EKS/Lambda/Fargate** | **ECR** (integração IAM + rede + velocidade) |
| Imagem de função **Lambda** | **ECR obrigatório** (Lambda só aceita imagens do ECR na mesma região da função; confirmar) |
| Evitar **rate limit de pull** do Docker Hub | **ECR + pull through cache** (espelha o upstream) |
| Distribuir imagens **open source** para todos | **ECR Public** (ou Docker Hub/GitHub Container Registry, conforme audiência) |
| Time usa **GitHub/GitLab** e já tem registry no repositório de código | Pode manter, mas **cuide da latência e da autenticação** na AWS; ECR costuma vencer em integração |
| Registry **on-premises** por conformidade | Harbor/Artifactory; ou ECR com **replicação/espelhos** conforme a política |
| Artefatos **não-container** (npm, Maven, pip) | **CodeArtifact** (não ECR) |
| Multicloud com um único registry | Registry neutro (Artifactory, Harbor) ou replicação |

### 8.1 ECR vs Docker Hub

| Critério | ECR | Docker Hub |
|---|---|---|
| Autenticação | **IAM** | Contas/tokens próprios |
| Limite de pull | Sem rate limit equivalente para recursos internos (há **quotas de API**) | **Rate limits** para pulls anônimos/gratuitos (confirmar valores atuais) |
| Rede | Dentro da AWS, com **VPC endpoints** | Internet pública |
| Segurança/Scan | Inspector integrado, KMS, policies | Recursos próprios (planos pagos) |
| Latência até ECS/EKS | **Baixa** (mesma região) | Depende da internet/NAT |
| Ecossistema de imagens públicas | Via ECR Public/pull through cache | **Enorme** (origem de quase tudo) |

## 9. Boas práticas iniciais

1. **Um repositório por aplicação/serviço**, com nomes hierárquicos (`equipe/servico`).
2. **Tag immutability ligada** em repositórios de produção.
3. **Scan on push** habilitado (e scanning avançado para o que for crítico).
4. **Lifecycle policies** desde o início (imagens de CI se acumulam rápido).
5. **Digest** (ou tag com commit SHA) nos manifests de deploy — nunca `latest`.
6. **Pull through cache** para imagens base de terceiros.
7. **Permissões mínimas**: CI só **push** no repositório do projeto; runtime só **pull**.
8. **Contas separadas** (build/prod) com **replicação** ou policy cross-account — nunca credenciais compartilhadas.

## 10. Erros comuns

- **Usar `latest` em produção** e perder a rastreabilidade.
- **Repositório com tags mutáveis** em produção: alguém sobrescreve `1.4.2`.
- **Esquecer a autenticação** (`get-login-password`) e achar que o ECR está “fora do ar” (`no basic auth credentials`).
- **Confundir a região**: a imagem está em `us-east-1` e a task roda em `sa-east-1`.
- **Nunca limpar**: milhares de imagens de CI acumulando custo.
- **Imagem pública por acidente**: publicar no ECR Public algo que deveria ser privado.
- **Imagens enormes**: build sem *multi-stage*, com ferramentas de compilação no runtime.
- **Tratar ECR como cofre de segredos**: nunca embuta credenciais na imagem.

## 11. Troubleshooting inicial

| Sintoma | Causas prováveis | Ações |
|---|---|---|
| `no basic auth credentials` no push/pull | Token expirado (~12 h) ou ausente | Refazer `get-login-password` |
| `denied: User is not authorized` | Falta permissão IAM/policy do repositório | Conferir `ecr:BatchCheckLayerAvailability`, `PutImage`... (ver folha de segurança) |
| `repository does not exist` | Nome/região/conta errados | Conferir o URI completo e a região |
| Tag não pode ser sobrescrita | Repositório com tags **imutáveis** | Usar nova tag (ou outro repositório) |
| Pull lento/falha em subnet privada | Sem NAT e sem VPC endpoints | Criar endpoints (`ecr.api`, `ecr.dkr`, S3 gateway) |
| Imagem “sumiu” | **Lifecycle policy** a expirou | Revisar regras e a prioridade |

## 12. Resumo rápido

- **ECR = registry de containers gerenciado**, compatível com **OCI/Docker**, integrado a **IAM, KMS, ECS, EKS, Lambda, CodeBuild**.
- **Registry por conta × região**; **repositório** por aplicação; **tag** é ponteiro mutável, **digest** é o conteúdo imutável.
- **Privado** (aplicações) vs **Public** (distribuição aberta).
- Camadas **deduplicadas** no armazenamento (S3 gerenciado); criptografia em repouso.
- Boas práticas: **tag immutability**, **scan on push**, **lifecycle**, **digest em produção**, **pull through cache**, permissões mínimas.
- Lambda com imagem de container exige **ECR**; artefatos de pacotes (npm/Maven) → **CodeArtifact**.
