### 2.1.1.1. Push e pull no ECR — autenticação com get-login-password, build e push, tags e digests, multi-arch, manifest lists, Buildx e fluxo de CI

> [!warning] Aviso
> Versões de ferramentas (Docker, Buildx, AWS CLI), duração do token, quotas e flags abaixo são **de memória e mudam**. **Confirme na documentação do ECR e das ferramentas.** Comandos e arquivos são ilustrativos e **não foram executados**. Os IDs de conta (`123456789012`) e regiões são fictícios.

## 1. Visão do fluxo

```
Desenvolvedor / CI
   │  1) autentica  (aws ecr get-login-password)
   │  2) build      (docker build / buildx)
   │  3) tag        (URI do registry + tag)
   │  4) push       (envia camadas + manifest)
   ▼
 Amazon ECR  ◀── 5) pull ── ECS / EKS / Lambda / CodeBuild / sua máquina
```

Em todos os passos a autenticação é feita com **credenciais do IAM** que o ECR converte em um **token temporário** para o cliente Docker/containerd.

## 2. Autenticação

### 2.1 Como funciona

- O **ECR não usa usuário/senha próprios**; o comando `aws ecr get-login-password` chama a API `GetAuthorizationToken` e devolve um **token** (senha) válido por **cerca de 12 horas** (de memória — confirmar).
- O **usuário** é sempre a string **`AWS`**.
- O token é **por registry (conta × região)**; é preciso autenticar em cada região/conta usada.
- As **permissões efetivas** vêm do **IAM** da identidade que pediu o token (e da *repository policy*).

```bash
aws ecr get-login-password --region us-east-1 \
  | docker login --username AWS --password-stdin 123456789012.dkr.ecr.us-east-1.amazonaws.com
```

### 2.2 Alternativas ao `docker login` manual

| Opção | Descrição |
|---|---|
| **Amazon ECR Docker Credential Helper** | Faz a autenticação automaticamente a cada operação (`docker-credential-ecr-login`); evita expirar no meio do dia |
| **CodeBuild/CodePipeline** | Autenticação no `buildspec` (`pre_build`) via `get-login-password` |
| **GitHub Actions** | Ação oficial de login no ECR; credenciais via **OIDC** (sem chaves de longa duração) |
| **EKS/ECS/Lambda** | **Sem login manual**: o pull usa a role do nó/task/função |
| **Máquina local** | `aws sso login` + `get-login-password` |

Configuração do credential helper (ilustrativa):

```json
{
  "credHelpers": {
    "123456789012.dkr.ecr.us-east-1.amazonaws.com": "ecr-login"
  }
}
```

(arquivo `~/.docker/config.json`)

### 2.3 Permissões IAM mínimas

| Operação | Ações IAM típicas |
|---|---|
| **Login** | `ecr:GetAuthorizationToken` (recurso `*`) |
| **Push** | `ecr:BatchCheckLayerAvailability`, `ecr:InitiateLayerUpload`, `ecr:UploadLayerPart`, `ecr:CompleteLayerUpload`, `ecr:PutImage` |
| **Pull** | `ecr:BatchGetImage`, `ecr:GetDownloadUrlForLayer`, `ecr:BatchCheckLayerAvailability` |
| **Listar/descrever** | `ecr:DescribeRepositories`, `ecr:ListImages`, `ecr:DescribeImages` |
| **Criar repositório** | `ecr:CreateRepository` (restrinja a CI/Plataforma) |

Pipeline de CI → **push** no repositório do projeto (ARN do repo no `Resource`); runtime → **pull**.

## 3. Build, tag e push

### 3.1 Convenção de tags

Combine **estabilidade** e **rastreabilidade**:

| Tag | Exemplo | Uso |
|---|---|---|
| **SemVer** | `1.4.2` | Versão de release legível |
| **Commit SHA** | `a1b2c3d` | Rastreabilidade ao código |
| **Combinada** | `1.4.2-a1b2c3d` | Imutável, única |
| **Canal** (mutável) | `staging`, `prod` | Ponteiros de ambiente (use só se a política permitir; preferir **digest** no manifest de deploy) |
| **`latest`** | — | Evitar em produção |

### 3.2 Passo a passo

```bash
REG=123456789012.dkr.ecr.us-east-1.amazonaws.com
REPO=pedidos/api
VERSAO=1.4.2
SHA=$(git rev-parse --short HEAD)

docker build -t $REPO:$VERSAO-$SHA .
docker tag  $REPO:$VERSAO-$SHA $REG/$REPO:$VERSAO-$SHA
docker push $REG/$REPO:$VERSAO-$SHA
```

A saída do push mostra o **digest** (`digest: sha256:... size: ...`); **guarde-o** (artefato do pipeline) para implantar por digest.

### 3.3 Dockerfile enxuto (ilustrativo, multi-stage)

```dockerfile
FROM node:20 AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

FROM node:20-slim
WORKDIR /app
ENV NODE_ENV=production
COPY --from=build /app/dist ./dist
COPY --from=build /app/package*.json ./
RUN npm ci --omit=dev
USER node
CMD ["node", "dist/server.js"]
```

Boas práticas: **multi-stage**, imagem base **slim/distroless**, **usuário não-root**, `.dockerignore`, **camadas ordenadas** do que menos muda ao que mais muda (melhora o cache).

### 3.4 Como o push funciona por dentro

1. O cliente pergunta ao ECR **quais camadas já existem** (`BatchCheckLayerAvailability`).
2. Envia **só as camadas novas** (`InitiateLayerUpload` → `UploadLayerPart` → `CompleteLayerUpload`).
3. Envia o **manifest** (`PutImage`) associando a **tag**.

Consequência: pushes sucessivos de imagens parecidas são **rápidos**; camadas compartilhadas não são reenviadas.

## 4. Pull

```bash
docker pull 123456789012.dkr.ecr.us-east-1.amazonaws.com/pedidos/api:1.4.2-a1b2c3d
docker pull 123456789012.dkr.ecr.us-east-1.amazonaws.com/pedidos/api@sha256:9f86d081...   # por digest
```

Nos serviços da AWS não há `docker pull` manual:

| Serviço | Quem autentica o pull |
|---|---|
| **ECS (EC2/Fargate)** | **Task execution role** (`AmazonECSTaskExecutionRolePolicy` inclui as ações de pull) |
| **EKS** | **Role do nó** (ou Fargate pod execution role); **IRSA** não é usado para pull de imagem (de memória — confirmar) |
| **Lambda** | A função usa permissões do **serviço Lambda**/repository policy (ver folha de segurança) |
| **CodeBuild** | **Role do projeto** (para imagens de build/ambiente em ECR) |

## 5. Multi-arquitetura

Para rodar em **x86_64 (amd64)** e **ARM (arm64/Graviton)** com um único nome:

```
pedidos/api:1.4.2   ──▶ manifest list (índice)
                          ├── linux/amd64  → digest sha256:aaa...
                          └── linux/arm64  → digest sha256:bbb...
```

O cliente (containerd/Docker) baixa **automaticamente a variante da arquitetura** do host.

```bash
# Buildx (ilustrativo)
docker buildx create --use
docker buildx build --platform linux/amd64,linux/arm64 \
  -t $REG/$REPO:$VERSAO-$SHA --push .
```

Pontos de atenção:

- O build **ARM em máquina x86** usa emulação (QEMU) — **lento**; prefira **runners ARM** ou *builders* remotos nativos.
- Graviton oferece **melhor preço/desempenho** em muitos workloads; ter a imagem multi-arch facilita migrar ECS/EKS/Lambda para ARM.
- Confirme que **dependências nativas** (bibliotecas compiladas) existem para ARM.
- Atenção a **attestations/provenance** do Buildx: podem adicionar manifests extras ao índice; confirme compatibilidade com seu fluxo de scanning/replicação.

## 6. Fluxo de CI/CD (exemplos)

### 6.1 CodeBuild (`buildspec.yml`, ilustrativo)

```yaml
version: 0.2
env:
  variables:
    REPO: pedidos/api
phases:
  pre_build:
    commands:
      - REG=$AWS_ACCOUNT_ID.dkr.ecr.$AWS_DEFAULT_REGION.amazonaws.com
      - aws ecr get-login-password | docker login --username AWS --password-stdin $REG
      - TAG=${CODEBUILD_RESOLVED_SOURCE_VERSION:0:7}
  build:
    commands:
      - docker build -t $REG/$REPO:$TAG .
  post_build:
    commands:
      - docker push $REG/$REPO:$TAG
      - DIGEST=$(aws ecr describe-images --repository-name $REPO --image-ids imageTag=$TAG --query 'imageDetails[0].imageDigest' --output text)
      - printf '{"image":"%s/%s@%s"}' "$REG" "$REPO" "$DIGEST" > imagedefinitions-digest.json
artifacts:
  files: [imagedefinitions-digest.json]
```

(O projeto CodeBuild precisa de **modo privilegiado** para `docker build`; ver a nota sobre CodeBuild nas folhas da família Code*.)

### 6.2 GitHub Actions com OIDC (ilustrativo)

```yaml
permissions: { id-token: write, contents: read }
steps:
  - uses: actions/checkout@v4
  - uses: aws-actions/configure-aws-credentials@v4
    with:
      role-to-assume: arn:aws:iam::123456789012:role/gha-ecr-push
      aws-region: us-east-1
  - id: ecr
    uses: aws-actions/amazon-ecr-login@v2
  - run: |
      docker build -t ${{ steps.ecr.outputs.registry }}/pedidos/api:${{ github.sha }} .
      docker push  ${{ steps.ecr.outputs.registry }}/pedidos/api:${{ github.sha }}
```

A role assumida via **OIDC** deve ter **confiança restrita** ao repositório/branch (condição `sub`) e permissões **somente de push** no repositório do projeto.

### 6.3 Princípio: “build once, promote the digest”

```
CI: build + push (tag SHA)  ──▶ guarda DIGEST ──▶ deploy DEV (digest)
                                                  ──▶ deploy HML (mesmo digest)
                                                  ──▶ deploy PROD (mesmo digest)
```

**Não reconstrua** a imagem a cada ambiente: promova o **mesmo digest**; assim, o que foi testado é o que roda em produção.

## 7. Inspeção e utilitários

```bash
aws ecr describe-repositories
aws ecr list-images --repository-name pedidos/api --filter tagStatus=TAGGED
aws ecr describe-images --repository-name pedidos/api \
  --query 'sort_by(imageDetails,&imagePushedAt)[-5:].[imageTags,imageDigest,imageSizeInBytes,imagePushedAt]'
aws ecr batch-delete-image --repository-name pedidos/api --image-ids imageTag=1.0.0-obsoleta
aws ecr put-image --repository-name pedidos/api --image-tag prod \
  --image-manifest "$(aws ecr batch-get-image --repository-name pedidos/api \
      --image-ids imageTag=1.4.2-a1b2c3d --query 'images[0].imageManifest' --output text)"
```

O último comando **re-etiqueta** (retag) uma imagem existente **sem rebuild/pull** — útil para promover `1.4.2-a1b2c3d` a `prod` (em repositórios com tags mutáveis, ou usando um repositório de “release”).

## 8. Otimizações práticas

| Objetivo | Técnica |
|---|---|
| **Push/pull mais rápido** | Imagens pequenas; camadas estáveis primeiro; reaproveitar cache (`--cache-from`, cache do BuildKit no registry) |
| **Menos custo** | Imagens enxutas + **lifecycle** + sem duplicações |
| **Menos latência em produção** | Replicar para a **região de uso**; usar **VPC endpoints** |
| **Builds reproduzíveis** | Fixar versões e **digest das imagens base** (`FROM node:20-slim@sha256:...`) |
| **Menos superfície de ataque** | `distroless`/`slim`, sem shell/ferramentas no runtime |

## 9. Erros comuns

- **Token expirado** durante um job longo (reautenticar ou usar o credential helper).
- **Esquecer a região** em `get-login-password --region` → `no basic auth credentials`.
- **`docker push` sem o URI completo** (tentando enviar para o Docker Hub).
- **Rebuild por ambiente** em vez de **promover o digest**.
- **Tag `latest` no manifest de ECS/Kubernetes** → deploys não reproduzíveis.
- **Imagem multi-arch “de mentira”**: build em amd64 e rodar em ARM → `exec format error`.
- **CI com permissões amplas** (`ecr:*`) e **criação automática de repositórios** sem controle.
- **Segredos dentro da imagem** (visíveis em qualquer camada).

## 10. Troubleshooting

| Sintoma | Causa provável | Ação |
|---|---|---|
| `denied: not authorized to perform: ecr:InitiateLayerUpload` | Role de CI sem permissão de push no repositório | Conceder as ações de push ao ARN do repo |
| `repository ... not found` no push | Repositório não existe (ECR **não cria automaticamente**, salvo recurso de *create on push* configurado — confirmar) | Criar o repositório ou habilitar a criação sob template |
| `exec format error` no container | Imagem com arquitetura errada | Build multi-arch ou imagem da arquitetura do nó |
| Push muito lento | Imagem grande, banda do runner, sem camadas reaproveitáveis | Reduzir imagem; runner na mesma região |
| `toomanyrequests` no pull do upstream | Rate limit do Docker Hub no build | Usar **pull through cache** ou espelhar a base no ECR |
| `ImageTagAlreadyExistsException` | Tags imutáveis e tag repetida | Nova tag única (versão + SHA) |
| Pull falha em subnet privada | Sem endpoints ECR/S3 ou NAT | Criar VPC endpoints (`ecr.api`, `ecr.dkr`, gateway S3) |

## 11. Resumo rápido

- **Login**: `aws ecr get-login-password | docker login --username AWS ...`; token ~**12 h**, por **registry**; credential helper evita expiração.
- **Push**: só **camadas novas** são enviadas; resposta traz o **digest**.
- **Pull** nos serviços AWS usa a **role** (execution role/role do nó) — sem login manual.
- **Tags**: SemVer + SHA; evite `latest`; **promova o digest**, não reconstrua.
- **Multi-arch**: `buildx --platform linux/amd64,linux/arm64` gera **manifest list**.
- **CI**: CodeBuild ou GitHub Actions + **OIDC**, com permissão **apenas de push**.

## 🧩 Quiz de Fixação

1. Qual o usuário usado no `docker login` do ECR e de onde vem a senha?
2. Por que o push de uma imagem parecida com a anterior é rápido?
3. Quais ações IAM compõem um pull?
4. O que é uma manifest list e para que serve?
5. O que significa “build once, promote the digest”?
6. Por que usar OIDC no GitHub Actions em vez de chaves de acesso?
7. O que causa `exec format error` ao iniciar um container?

**Respostas:**

1. O usuário é `AWS`; a senha é o token de `aws ecr get-login-password` (válido por cerca de 12 horas, por registry).
2. Porque o cliente envia só as camadas que o ECR ainda não possui (as demais são reaproveitadas).
3. `ecr:BatchGetImage`, `ecr:GetDownloadUrlForLayer` e `ecr:BatchCheckLayerAvailability` (mais `GetAuthorizationToken` para o login).
4. Um índice que agrupa variantes de uma imagem por arquitetura/SO sob uma mesma tag; o cliente baixa a variante do seu host.
5. Construir a imagem uma vez e implantar o mesmo digest em todos os ambientes, garantindo que o testado é o que vai para produção.
6. Porque emite credenciais temporárias por execução e permite restringir a confiança a repositório/branch, sem chaves de longa duração armazenadas.
7. A imagem foi construída para uma arquitetura (por exemplo, amd64) diferente da do host (por exemplo, arm64).
