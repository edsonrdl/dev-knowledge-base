### Job definitions e jobs — container properties, parâmetros, retries, timeout, dependências, array jobs e multi-node parallel

> [!warning] Aviso
> Limites (tamanho de array, número de dependências, tamanho de parâmetros), nomes de campos e comportamento de retries mudam. Os números aqui são referências de estudo; confirme na documentação. Os comandos **não foram executados**.

A **job definition** é a **receita** de um job: qual imagem de container rodar, com quanta CPU/memória/GPU, que comando, que variáveis de ambiente, que *roles* IAM, quantas tentativas e qual timeout. O **job** é uma **execução** dessa receita, submetida a uma fila. Separar os dois permite **versionar** a receita e **reutilizá-la** em milhares de submissões.

**Analogia:** a job definition é uma **receita de bolo** (ingredientes, forno, tempo) e cada job é **um bolo assado** seguindo-a. Você pode ter várias versões da receita (revisões) e assar quantos bolos quiser; ao assar, pode trocar detalhes pontuais (parâmetros) sem reescrever a receita.

---

## Anatomia de uma job definition

```
 job definition: processa-arquivo (revisão 3)
 ├─ type:               container | multinode
 ├─ platformCapabilities: EC2 | FARGATE
 ├─ containerProperties
 │    ├─ image, command, environment, secrets
 │    ├─ resourceRequirements (VCPU, MEMORY, GPU)
 │    ├─ jobRoleArn         (permissões do código)
 │    ├─ executionRoleArn   (pull de imagem, logs, segredos)
 │    ├─ logConfiguration   (awslogs, etc.)
 │    ├─ volumes / mountPoints
 │    └─ linuxParameters, ulimits, user, privileged
 ├─ retryStrategy:      attempts + evaluateOnExit
 ├─ timeout:            attemptDurationSeconds
 ├─ parameters:         valores padrão para Ref::
 └─ tags / propagateTags
```

| Campo | Função |
|---|---|
| `image` | Imagem Docker (ECR, Docker Hub etc.) |
| `command` | Comando e argumentos (aceita `Ref::nome`) |
| `resourceRequirements` | vCPU, memória (MiB) e GPU do job |
| `jobRoleArn` | **Role que o código do job assume** (acesso a S3, DynamoDB etc.) |
| `executionRoleArn` | Role para o agente puxar imagem, enviar logs, ler segredos (obrigatória em Fargate) |
| `environment` | Variáveis de ambiente em texto |
| `secrets` | Valores vindos de Secrets Manager / SSM Parameter Store |
| `retryStrategy` | Tentativas e condições de retry |
| `timeout` | Tempo máximo por tentativa |

> [!tip] Duas roles, dois papéis
> **jobRole** = o que o **seu código** pode fazer na AWS. **executionRole** = o que a **plataforma** precisa para iniciar o container (pull da imagem, logs, segredos). Confundir as duas é causa clássica de `AccessDenied`.

## Parâmetros e substituição

Parâmetros permitem **reaproveitar** a definição:

```bash
# Na definição: command com Ref::
"command": ["python","etl.py","--entrada","Ref::entrada","--data","Ref::data"]

# Valores padrão na definição
"parameters": {"data": "hoje"}

# Na submissão, sobrescreve o que quiser
aws batch submit-job ... --parameters entrada=s3://b/x.csv,data=2026-11-09
```

A substituição ocorre **apenas no `command`**; para variáveis de ambiente use `containerOverrides` na submissão.

```bash
aws batch submit-job \
  --job-name etl-0001 --job-queue fila-principal --job-definition etl:3 \
  --container-overrides '{
    "environment":[{"name":"MODO","value":"completo"}],
    "resourceRequirements":[{"type":"MEMORY","value":"8192"}]
  }'
```

O sufixo `:3` fixa a **revisão**. Sem ele, o Batch usa a **última ativa**.

## Retries e `evaluateOnExit`

`retryStrategy` define quantas vezes (1 a 10) o Batch tenta de novo um job que falha, e **quais falhas valem nova tentativa**.

```json
"retryStrategy": {
  "attempts": 4,
  "evaluateOnExit": [
    {"onStatusReason": "Host EC2*", "action": "RETRY"},
    {"onReason": "CannotPullContainerError*", "action": "RETRY"},
    {"onExitCode": "137", "action": "RETRY"},
    {"onExitCode": "1", "action": "EXIT"}
  ]
}
```

| Cenário | Estratégia |
|---|---|
| Interrupção de Spot / falha do host | **RETRY** (a falha não é culpa do código) |
| Erro de aplicação determinístico (bug) | **EXIT** (repetir só gasta dinheiro) |
| Falha transitória de rede/pull | RETRY |
| Falta de memória (exit 137) | Normalmente corrigir `MEMORY`, não repetir |

> [!warning] Retry não é solução para bug
> Repetir um job que falha sempre pelo mesmo motivo apenas multiplica o custo. Use `evaluateOnExit` para repetir **só falhas de infraestrutura**.

## Timeout

```json
"timeout": {"attemptDurationSeconds": 3600}
```

O timeout vale **por tentativa**. Quando estoura, o job é terminado e marcado como **FAILED** (e pode ser repetido, conforme o retry). Defina sempre um timeout para **evitar jobs "zumbis"** consumindo vCPU indefinidamente.

## Dependências entre jobs

```bash
# Job B só roda depois que A terminar com sucesso
aws batch submit-job --job-name B --job-queue fila --job-definition def \
  --depends-on jobId=<id-do-A>

# Dependência do tipo "sequencial" em array jobs
aws batch submit-job ... --depends-on jobId=<id>,type=SEQUENTIAL
```

```
  A ──► B ──┬──► D
            └──► C ──► E          D e E esperam em PENDING até as dependências terminarem
```

| Tipo | Comportamento |
|---|---|
| Dependência simples (`jobId`) | Espera o job terminar com sucesso |
| `N_TO_N` (arrays) | Cada índice espera o índice correspondente do outro array |
| `SEQUENTIAL` | Os índices de um array rodam em ordem |

Se uma dependência **falha**, o job dependente **também falha** (não executa). Para fluxos com ramificações e tratamento de erro elaborado, prefira **Step Functions**.

## Array jobs

Um **array job** submete **N cópias** do mesmo job com **índices** de 0 a N-1, ideal para processamento paralelo "embaraçosamente paralelo".

```bash
aws batch submit-job \
  --job-name processa-lote --job-queue fila-spot --job-definition processa:2 \
  --array-properties size=10000
```

Dentro do container, a variável **`AWS_BATCH_JOB_ARRAY_INDEX`** informa o índice do filho:

```bash
#!/bin/bash
# cada filho pega uma linha de uma lista no S3
ARQ=$(sed -n "$((AWS_BATCH_JOB_ARRAY_INDEX + 1))p" lista.txt)
processa "$ARQ"
```

| Vantagem | Observação |
|---|---|
| Uma submissão = milhares de jobs | Reduz chamadas de API e overhead |
| Cada filho tem retry próprio | Falhas isoladas |
| Monitoramento agregado | Estado do pai resume os filhos |

> [!tip] Particione os dados
> O truque do array job é cada índice saber **qual pedaço processar** (índice → arquivo, intervalo, partição). Planeje a distribuição para que os filhos tenham duração parecida.

## Multi-node parallel (MNP)

Para **HPC fortemente acoplado** (por exemplo, simulações com **MPI**), o Batch oferece jobs **multi-node parallel**: **um job que roda em várias instâncias EC2 ao mesmo tempo**, com um **nó principal** e **nós filhos**.

| Característica | Detalhe |
|---|---|
| Plataforma | **Somente EC2** (não Fargate) |
| Sincronização | Nós se comunicam entre si (ex.: MPI) |
| Variáveis úteis | `AWS_BATCH_JOB_NODE_INDEX`, `AWS_BATCH_JOB_MAIN_NODE_INDEX`, `AWS_BATCH_JOB_NUM_NODES` |
| Rede | Recomenda-se *cluster placement group* e instâncias com rede rápida |
| Quando usar | Simulações acopladas; **não** para tarefas independentes (use array) |

## Armazenamento do job

| Opção | Uso |
|---|---|
| **Disco efêmero** do container | Arquivos temporários; some ao fim do job |
| **Volumes do host / EFS** | Dados compartilhados entre jobs e nós |
| **S3** | Entrada e saída dos dados (padrão mais comum) |
| **Fargate ephemeral storage** | Configurável em tarefas Fargate (tamanho limitado) |

O padrão recomendado é **entrada e saída no S3**, usando o disco local apenas como área de trabalho.

## Exemplo prático: ETL em array com retry inteligente

1. Registre a definição `etl:1` com `VCPU=2`, `MEMORY=4096`, `timeout=1800`.
2. Configure `retryStrategy` com 3 tentativas apenas para falhas de host/pull.
3. Submeta um **array job** com `size` igual ao número de partições.
4. Cada filho lê `AWS_BATCH_JOB_ARRAY_INDEX`, baixa a partição do S3 e grava o resultado.
5. Submeta o job de **consolidação** com `--depends-on` do array (para rodar só após todos terminarem).
6. Monitore falhas por índice e reprocesse apenas os que falharam.

## Troubleshooting

| Sintoma | Causa provável | Como resolver |
|---|---|---|
| `CannotPullContainerError` | Rede, imagem inexistente ou role sem permissão | Verificar ECR, endpoints, `executionRole` |
| Exit code 137 | Falta de memória (OOM) ou kill | Aumentar `MEMORY`; revisar uso |
| `AccessDenied` no código | `jobRole` sem a permissão | Ajustar a role do job |
| Job em PENDING | Dependência não concluída ou falhou | Verificar o job do qual depende |
| Array parcial falhou | Falhas em alguns índices | Reexecutar só os índices ruins |
| Job nunca termina | Sem timeout | Definir `attemptDurationSeconds` |

## Ciclo de vida de revisões e boas práticas de imagem

Cada `register-job-definition` com o mesmo nome cria uma **nova revisão**; revisões antigas continuam existindo até serem **desregistradas**.

```bash
# Lista as revisões ativas
aws batch describe-job-definitions --job-definition-name etl --status ACTIVE \
  --query 'jobDefinitions[].[revision,status]'

# Desativa uma revisão antiga (jobs já submetidos não são afetados)
aws batch deregister-job-definition --job-definition etl:2
```

| Prática | Motivo |
|---|---|
| Fixar `nome:revisão` no pipeline de produção | Evita mudança inesperada de comportamento |
| Tag de imagem **imutável** (versão ou digest) | Reprodutibilidade e rollback |
| Definição versionada em **IaC** (CloudFormation/Terraform) | Revisão por pull request e auditoria |
| Imagens enxutas (multi-stage build) | Pull mais rápido, menos custo de transferência |
| Entrypoint que **propaga o código de saída** | O Batch só enxerga SUCCEEDED/FAILED pelo exit code |
| Tratar `SIGTERM` | Permite salvar estado antes de uma interrupção Spot |

> [!tip] Idempotência
> Em Spot e com retries, o mesmo trabalho pode rodar mais de uma vez. Projete o job para ser **idempotente**: gravar saída em caminho determinístico (por índice ou data) e sobrescrever, em vez de acumular duplicatas.

### Checklist de uma boa definição

1. Imagem com tag imutável e usuário não root.
2. `VCPU` e `MEMORY` medidos, com folga pequena.
3. `timeout` e `retryStrategy` com `evaluateOnExit`.
4. `jobRole` com menor privilégio e `executionRole` separada.
5. `logConfiguration` com grupo de logs por projeto.
6. `propagateTags` e tags de custo.

## Erros comuns e armadilhas

- **Embutir segredos em `environment`:** use `secrets` (Secrets Manager/SSM).
- **Esquecer a `executionRole` em Fargate.**
- **Não fixar a revisão da definição** em produção e receber mudanças inesperadas.
- **Retry cego em erro de código.**
- **Sem timeout:** um job travado consome recursos por dias.
- **Array com partições desiguais:** poucos filhos longos atrasam o conjunto.
- **Usar multi-node para tarefas independentes** (desperdício e complexidade).
- **Gravar resultados só no disco local:** somem ao fim do job.

## 🧩 Quiz de Fixação

1. Qual a diferença entre job definition e job?
2. Qual a diferença entre `jobRoleArn` e `executionRoleArn`?
3. Para que serve `evaluateOnExit`?
4. Que variável identifica o índice de um filho em um array job?
5. Quando usar multi-node parallel em vez de array job?
6. O que acontece com um job dependente se a dependência falhar?

**Respostas:**
1) A definição é a receita versionada e reutilizável; o job é uma execução dessa receita submetida a uma fila.
2) A jobRole é assumida pelo código do job (acessar S3, DynamoDB etc.); a executionRole é usada pela plataforma para puxar a imagem, enviar logs e ler segredos.
3) Para repetir apenas certas falhas (por exemplo, falha de host ou pull) e encerrar imediatamente nas demais, evitando retry inútil.
4) AWS_BATCH_JOB_ARRAY_INDEX.
5) Quando as tarefas são fortemente acopladas e precisam rodar simultaneamente em vários nós se comunicando (como MPI); para tarefas independentes use array.
6) Ele não executa e também termina em falha.
