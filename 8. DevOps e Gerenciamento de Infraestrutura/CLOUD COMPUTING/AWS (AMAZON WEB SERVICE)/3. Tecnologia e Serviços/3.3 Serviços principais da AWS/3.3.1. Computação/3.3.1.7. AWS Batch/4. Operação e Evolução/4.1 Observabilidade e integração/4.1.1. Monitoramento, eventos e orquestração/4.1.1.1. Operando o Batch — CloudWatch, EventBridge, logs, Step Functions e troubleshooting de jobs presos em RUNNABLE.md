### Operando o Batch — CloudWatch, EventBridge, logs, Step Functions e troubleshooting de jobs presos em RUNNABLE

> [!warning] Aviso
> Nomes de métricas, eventos, campos de payload e integrações mudam. Os números e exemplos aqui são referências de estudo; confirme na documentação. Os comandos **não foram executados**.

Operar o AWS Batch é **observar a fila**, **reagir a mudanças de estado dos jobs**, **ler os logs** e **encadear o Batch com outros serviços**. Como os jobs são assíncronos, ninguém "vê" o resultado na hora: sem observabilidade, falhas e filas paradas passam despercebidas por horas.

**Analogia:** é o **painel de controle de uma fábrica**. As esteiras (jobs) rodam sozinhas, mas você precisa de luzes de alerta (alarmes), um registro de ocorrências (logs), um sistema que avise o setor seguinte quando uma etapa termina (EventBridge) e um supervisor de linha de produção (Step Functions).

## Logs dos jobs

Por padrão, a saída padrão (stdout/stderr) do container vai para o grupo de logs **`/aws/batch/job`** quando se usa o driver `awslogs`.

```json
"logConfiguration": {
  "logDriver": "awslogs",
  "options": {
    "awslogs-group": "/meu-projeto/batch/processa",
    "awslogs-stream-prefix": "job"
  }
}
```

```bash
# Descobre o stream do job e lê os eventos
aws batch describe-jobs --jobs <jobId> \
  --query 'jobs[0].container.logStreamName'

aws logs get-log-events \
  --log-group-name /aws/batch/job \
  --log-stream-name <logStreamName> --limit 50
```

| Boa prática | Motivo |
|---|---|
| Grupo de logs por projeto | Retenção e permissão separadas |
| **Retenção definida** (ex.: 30 dias) | Evita custo crescente de logs |
| Logs estruturados (JSON) | Facilita consultas no Logs Insights |
| Imprimir `jobId` e índice do array | Correlação de falhas |
| Em Fargate, a `executionRole` precisa de permissão de logs | Senão nada é gravado |

## EventBridge: reagir a mudanças de estado

O Batch emite eventos **"Batch Job State Change"** quando o job muda de estado. Uma regra do EventBridge pode filtrar e acionar destinos.

```json
{
  "source": ["aws.batch"],
  "detail-type": ["Batch Job State Change"],
  "detail": {
    "status": ["FAILED"],
    "jobQueue": ["arn:aws:batch:us-east-1:123456789012:job-queue/fila-principal"]
  }
}
```

| Destino | Uso |
|---|---|
| **SNS** | Notificar a equipe sobre falhas |
| **Lambda** | Reenviar, limpar, registrar em banco |
| **SQS** | Fila de reprocessamento |
| **Step Functions** | Disparar a próxima etapa do pipeline |

> [!tip] Notifique falhas, não sucessos
> Regras para `FAILED` geram sinal útil; regras para todo `SUCCEEDED` de um array de 10 mil jobs geram ruído e custo.

## Métricas e alarmes

O Batch não publica um conjunto único de "métricas de fila" como um serviço de mensageria; você combina:

| Sinal | Origem | Alarme sugerido |
|---|---|---|
| Quantidade de jobs por estado | `list-jobs` (consulta periódica) ou eventos | Jobs RUNNABLE acima de N por mais de X min |
| Tempo em RUNNABLE | Diferença entre `createdAt` e `startedAt` | Acima do SLA |
| Uso de CPU/memória do CE | CloudWatch (EC2/ECS) | Subutilização crônica |
| Falhas por job definition | Eventos + Logs Insights | Taxa de FAILED acima do normal |
| Custo | Cost Explorer / Budgets | Orçamento mensal por tag |

```bash
# Conta jobs presos em RUNNABLE
aws batch list-jobs --job-queue fila-principal --job-status RUNNABLE \
  --query 'length(jobSummaryList)'
```

## Orquestração com Step Functions

O **Step Functions** tem integração otimizada com o Batch (`arn:aws:states:::batch:submitJob.sync`): o fluxo **submete o job e espera** o término antes de seguir.

```json
{
  "StartAt": "Extrai",
  "States": {
    "Extrai": {
      "Type": "Task",
      "Resource": "arn:aws:states:::batch:submitJob.sync",
      "Parameters": {
        "JobName": "extrai",
        "JobQueue": "fila-principal",
        "JobDefinition": "extrai:1"
      },
      "Catch": [{"ErrorEquals": ["States.ALL"], "Next": "Falha"}],
      "Next": "Transforma"
    },
    "Transforma": {"Type": "Task", "Resource": "arn:aws:states:::batch:submitJob.sync",
      "Parameters": {"JobName":"transforma","JobQueue":"fila-principal","JobDefinition":"transforma:1"},
      "End": true},
    "Falha": {"Type": "Fail"}
  }
}
```

| Prefira Step Functions quando... | Prefira `depends-on` do Batch quando... |
|---|---|
| Há ramificações, `Choice`, `Parallel` | O fluxo é linear e simples |
| Precisa de tratamento de erro elaborado | Basta "só rode se o anterior passar" |
| Mistura Batch com Lambda, Glue, SNS | Só Batch |
| Quer histórico visual de execução | Aceita acompanhar por job |

Outros gatilhos comuns: **EventBridge Scheduler/regras agendadas** (jobs recorrentes), **S3 + EventBridge** (novo arquivo → submitJob) e **Lambda** chamando `SubmitJob`.

## Troubleshooting: job preso em RUNNABLE

O sintoma mais frequente. Siga a árvore:

```
Job em RUNNABLE por muito tempo
├─ CE está VALID e ENABLED?
│    └─ Não ─► corrigir CE (statusReason), habilitar
├─ Fila está ENABLED e ligada ao CE?
│    └─ Não ─► associar o CE na ordem da fila
├─ vCPU/memória/GPU pedidos cabem em ALGUMA instância do CE?
│    └─ Não ─► reduzir pedido ou incluir tipos maiores
├─ Já atingiu maxvCpus ou limite de vCPU da conta?
│    └─ Sim ─► aumentar maxvCpus / pedir quota
├─ É Spot? Há capacidade nos tipos/AZs listados?
│    └─ Não ─► ampliar tipos e AZs; CE On-Demand de reserva
├─ Sub-redes têm IPs livres e rota?
│    └─ Não ─► liberar IPs / corrigir rede
└─ Job depende de outro que falhou?
     └─ Sim ─► (seria PENDING/FAILED) revisar dependências
```

```bash
# Diagnóstico rápido
aws batch describe-jobs --jobs <jobId> --query 'jobs[0].[status,statusReason]'
aws batch describe-compute-environments --compute-environments ce-spot \
  --query 'computeEnvironments[0].[state,status,statusReason]'
aws batch describe-job-queues --job-queues fila-principal
```

## Troubleshooting geral

| Sintoma | Causa provável | Como resolver |
|---|---|---|
| FAILED com `CannotPullContainerError` | Rede/ECR/permissão | Endpoints, NAT, `executionRole` |
| FAILED exit 137 | OOM | Aumentar memória |
| FAILED "Host EC2 terminated" | Interrupção Spot | `retryStrategy` com RETRY para host |
| Sem logs | `executionRole` sem permissão ou driver ausente | Corrigir role e `logConfiguration` |
| Evento não dispara | Padrão da regra incorreto | Testar o padrão no EventBridge |
| Step Functions não termina | Job travado sem timeout | Definir timeout no job e no estado |
| Custo alto | `minvCpus` > 0, sem tags | Zerar mínimo; marcar recursos |

## Auditoria e mudanças de configuração

| Pergunta | Onde responder |
|---|---|
| Quem submeteu ou cancelou este job? | **CloudTrail** (eventos `SubmitJob`, `TerminateJob`, `CancelJob`) |
| Quem alterou o compute environment ou a fila? | CloudTrail (`UpdateComputeEnvironment`, `UpdateJobQueue`) |
| A configuração mudou desde ontem? | **AWS Config** (histórico de configuração, quando habilitado) |
| Quanto cada time gastou? | Cost Explorer filtrado por tags |

Habilite o CloudTrail com retenção adequada: em incidentes de custo, saber **quem enviou 50 mil jobs** é a primeira pergunta.

## Exemplo prático: pipeline diário observável

1. EventBridge Scheduler dispara a state machine às 02:00.
2. Step Functions executa `extrai.sync` → `transforma.sync` → `carrega.sync`.
3. Cada job grava logs em `/projeto/batch/<etapa>` com retenção de 30 dias.
4. Regra do EventBridge notifica o SNS **apenas em FAILED**.
5. Alarme avisa se houver jobs RUNNABLE por mais de 20 minutos.
6. Relatório mensal por tag `projeto` no Cost Explorer.

## Consultando logs com CloudWatch Logs Insights

Logs estruturados em JSON permitem consultas agregadas sobre milhares de jobs.

```
fields @timestamp, jobId, indice, nivel, mensagem
| filter nivel = "ERROR"
| stats count() as erros by bin(15m)
| sort @timestamp desc
```

| Consulta útil | Para quê |
|---|---|
| Contagem de `ERROR` por janela | Detectar pico de falhas |
| Tempo por etapa (`duracao_ms`) | Achar gargalos |
| Erros agrupados por `indice` do array | Saber quais partições reprocessar |
| Mensagens de `OutOfMemory` | Justificar aumento de memória |

### Reprocessando apenas o que falhou

```bash
# Lista os filhos de um array que falharam
aws batch list-jobs --array-job-id <idDoPai> --job-status FAILED \
  --query 'jobSummaryList[].[jobId,arrayProperties.index]'
```

A partir dessa lista, submeta um novo job apenas com os **índices que falharam** (por exemplo, passando a lista de partições por parâmetro), em vez de reexecutar o lote inteiro.

> [!tip] Painel único
> Monte um **dashboard do CloudWatch** com: jobs RUNNABLE, jobs FAILED por hora, uso de vCPU do CE e custo diário. Em poucos minutos o time vê se a fila está saudável ou saturada.

### Rotina de operação diária

1. Conferir falhas das últimas 24 h (eventos `FAILED` e Logs Insights).
2. Verificar se há jobs RUNNABLE acima do esperado.
3. Revisar o CE: estado `VALID`, uso e `maxvCpus`.
4. Olhar o gasto do dia por tag de projeto.
5. Registrar causas recorrentes e corrigir na definição, não só reexecutar.

## Erros comuns e armadilhas

- **Não definir retenção dos logs** e pagar armazenamento indefinido.
- **Alertar em todo SUCCEEDED** de arrays gigantes.
- **Sem timeout no job nem no estado** do Step Functions.
- **Ignorar `statusReason`**, que quase sempre aponta a causa.
- **Esperar que o Batch publique métricas de fila prontas:** monte alarmes com `list-jobs`/eventos.
- **Misturar logs de todos os projetos** em um grupo só.
- **Orquestrar fluxos complexos apenas com `depends-on`.**
- **Esquecer tags** e perder rastreio de custo.

## 🧩 Quiz de Fixação

1. Para onde vai a saída padrão do container por padrão?
2. Qual evento o Batch emite a cada mudança de estado do job?
3. Qual a vantagem do `submitJob.sync` no Step Functions?
4. Cite duas causas comuns de job preso em RUNNABLE.
5. Por que definir retenção nos grupos de logs?
6. Quando usar Step Functions em vez de `depends-on`?

**Respostas:**
1) Para o CloudWatch Logs (grupo /aws/batch/job), quando se usa o driver awslogs.
2) "Batch Job State Change", publicado no EventBridge.
3) O fluxo submete o job e aguarda o término antes de avançar, simplificando orquestração e tratamento de erro.
4) Requisito maior que as instâncias do CE; limite de vCPU/maxvCpus; Spot sem capacidade; CE inválido/desabilitado; rede sem IP ou rota.
5) Para limitar o custo crescente de armazenamento de logs.
6) Quando o fluxo tem ramificações, paralelismo, tratamento de erro elaborado ou mistura Batch com outros serviços.
