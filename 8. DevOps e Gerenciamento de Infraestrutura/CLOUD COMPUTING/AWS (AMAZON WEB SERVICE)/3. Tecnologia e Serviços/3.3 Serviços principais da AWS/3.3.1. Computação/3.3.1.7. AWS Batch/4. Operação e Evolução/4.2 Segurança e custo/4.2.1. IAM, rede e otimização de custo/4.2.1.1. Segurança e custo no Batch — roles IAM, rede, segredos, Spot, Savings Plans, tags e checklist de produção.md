### Segurança e custo no Batch — roles IAM, rede, segredos, Spot, Savings Plans, tags e checklist de produção

> [!warning] Aviso
> Nomes de políticas gerenciadas, descontos, preços, regras de Spot e Savings Plans mudam. Os números aqui são referências de estudo; confirme na documentação e no console de custos. Os comandos **não foram executados**.

Como o AWS Batch **cria e destrói computação sozinho**, segurança e custo exigem **limites bem desenhados**: quem pode submeter jobs, que permissões o código tem, por onde o tráfego sai e **qual o teto de gasto**. Um erro de configuração aqui costuma aparecer como **conta alta** ou **dados expostos**.

**Analogia:** é como **dar as chaves de uma fábrica automatizada**. Você precisa definir **quem pode apertar o botão** (IAM de submissão), **o que cada máquina pode tocar** (role do job), **por quais portas o material entra e sai** (rede) e **um disjuntor** (`maxvCpus` e orçamentos) para que um defeito não queime a conta.

---

## O mapa das identidades IAM

```
 Quem submete (usuário/CI/Lambda)  ──►  batch:SubmitJob (+ iam:PassRole)
 Batch service role                ──►  AWSServiceRoleForBatch (gerencia EC2/ECS/Fargate)
 Instance profile (EC2)            ──►  agente ECS nas instâncias
 Execution role (Fargate/ECS)      ──►  pull de imagem, logs, segredos
 Job role                          ──►  permissões do CÓDIGO (S3, DynamoDB...)
 Spot Fleet role (Spot clássico)   ──►  gerenciar solicitações Spot
```

| Role | Quem assume | Exemplo de permissão |
|---|---|---|
| **Quem submete** | Pessoa/pipeline | `batch:SubmitJob`, `batch:DescribeJobs`, `iam:PassRole` (para as roles da definição) |
| **Service-linked role do Batch** | O serviço Batch | Criar e gerenciar instâncias e recursos |
| **Instance role** | Instâncias EC2 do CE | Política gerenciada do agente de container |
| **Execution role** | Plataforma (Fargate) | ECR, CloudWatch Logs, Secrets Manager |
| **Job role** | **Seu código** | Ler `s3://entrada/*`, gravar `s3://saida/*` |

> [!tip] Menor privilégio na job role
> A **job role** deve conceder **apenas** o que o código precisa: prefixos específicos de S3, tabelas específicas. Uma role ampla (`s3:*` em `*`) transforma um bug ou imagem comprometida em acesso a tudo.

### Restringindo quem submete

```json
{
  "Effect": "Allow",
  "Action": ["batch:SubmitJob"],
  "Resource": [
    "arn:aws:batch:us-east-1:123456789012:job-definition/processa:*",
    "arn:aws:batch:us-east-1:123456789012:job-queue/fila-principal"
  ]
}
```

Limitar por **job definition** e **fila** impede que um usuário envie jobs arbitrários para filas caras. O `iam:PassRole` deve ser restrito às roles esperadas.

## Rede e isolamento

| Controle | Prática |
|---|---|
| **Sub-redes privadas** | Rode CEs em sub-redes sem IP público |
| **VPC endpoints** | ECR (api e dkr), S3 (gateway), CloudWatch Logs, Secrets Manager — evitam NAT e reduzem exposição |
| **Security groups** | Saída restrita ao necessário; sem entrada (jobs não são servidores) |
| **Sem `privileged`** | Evite containers privilegiados |
| **Imagens de fontes confiáveis** | ECR privado com varredura de vulnerabilidades |
| **Criptografia** | Volumes EBS e S3 com KMS; TLS em trânsito |

```
 Sub-rede privada ──► VPC endpoints (ECR, S3, Logs, Secrets)   [sem passar pela Internet]
        └── NAT Gateway (somente se precisar de saída externa)
```

> [!warning] NAT Gateway cobra por dado processado
> Baixar terabytes do S3 **via NAT** gera custo alto. Use o **gateway endpoint do S3** (sem custo por dado) para entrada e saída de dados.

## Segredos e configuração

| Dado | Onde guardar | Como entregar ao job |
|---|---|---|
| Senhas, chaves de API | **Secrets Manager** | `secrets` na definição (valueFrom) |
| Parâmetros não sensíveis | **SSM Parameter Store** | `secrets` ou `environment` |
| Configuração simples | `environment` | Variável em texto (nada sensível) |

```json
"secrets": [
  {"name": "DB_PASSWORD",
   "valueFrom": "arn:aws:secretsmanager:us-east-1:123456789012:secret:db-prod-AbCdEf"}
]
```

A **execution role** precisa permitir `secretsmanager:GetSecretValue` para esse segredo. **Nunca** coloque segredos em `command`, `environment` ou na imagem.

## Onde o custo se origina

| Fonte | Observação |
|---|---|
| **Computação** (EC2/Spot/Fargate) | Maior parcela; paga enquanto existe |
| Armazenamento (EBS, S3, EFS) | Volumes das instâncias e dados |
| Transferência (NAT, inter-AZ, Internet) | Frequentemente subestimada |
| CloudWatch Logs | Ingestão e retenção |
| ECR | Armazenamento das imagens |
| **AWS Batch em si** | Sem custo adicional |

## Alavancas de otimização

| Alavanca | Economia / efeito | Cuidado |
|---|---|---|
| **Spot** | Pode chegar a dezenas de % de desconto | Exige tolerância a interrupção e retries |
| **Savings Plans / RIs** | Desconto por compromisso para carga base estável | Só para o que roda de forma previsível |
| **`minvCpus = 0`** | Sem ociosidade | Pequeno atraso de partida |
| **Tipos flexíveis / `optimal`** | Melhor encaixe e capacidade | Teste de desempenho |
| **Graviton (ARM)** | Melhor preço/desempenho em muitos casos | Imagem multi-arquitetura |
| **Right-sizing de jobs** | Menos instâncias ociosas | Medir uso real |
| **Fargate Spot** | Serverless mais barato | Sem GPU; interrupções |
| **Imagens pequenas** | Início rápido, menos transferência | Build otimizado |

```
 Decisão de compra
 ├─ Carga base previsível 24/7?  ─► Savings Plans (cobre o piso)
 ├─ Carga elástica tolerante?    ─► Spot (com retry)
 └─ Carga crítica com prazo?     ─► On-Demand de reserva atrás do Spot
```

## Governança de custo

```bash
# Marca jobs/definições para alocação de custo
aws batch register-job-definition ... \
  --tags projeto=etl,time=dados --propagate-tags

# Orçamento mensal com alerta
aws budgets create-budget --account-id 123456789012 \
  --budget file://orcamento.json \
  --notifications-with-subscribers file://alertas.json
```

| Controle | Função |
|---|---|
| **Tags** + tags de alocação de custo | Atribuir gasto por time/projeto |
| **AWS Budgets** | Alerta ao aproximar do limite |
| **Cost Anomaly Detection** | Detectar picos incomuns |
| **`maxvCpus`** | Disjuntor técnico por CE |
| **Quotas de serviço** | Teto por região/conta |
| **Tag em CE e em job** | Rastreio por pipeline |

## Checklist de produção

1. Job role com **menor privilégio**; execution role separada.
2. CEs em **sub-redes privadas** com **VPC endpoints**.
3. Imagens em **ECR** com varredura e **tags de versão** (não `latest`).
4. `retryStrategy` apenas para falhas de infraestrutura; **timeout** em todos os jobs.
5. **Spot** com muitos tipos/AZs e **CE On-Demand de reserva**.
6. `maxvCpus` realista e `minvCpus = 0` quando possível.
7. Logs com **retenção** e alarme de **RUNNABLE**.
8. **Tags** em tudo; **Budgets** e detecção de anomalia ativos.
9. Segredos no **Secrets Manager**, nunca em texto.
10. Permissão de submissão restrita por fila e definição.

## Exemplo prático: reduzindo uma conta de 100 para menos

1. Auditoria: o CE On-Demand mantinha `minvCpus = 64` fora do horário → zerado.
2. Troca para **Spot** com 8 famílias de instância e 3 AZs.
3. Acesso ao S3 via **gateway endpoint** em vez de NAT.
4. Right-sizing: jobs pediam 8 GB, usavam 3 GB → ajustado.
5. Logs com retenção de 14 dias.
6. Resultado: menos horas de instância, menos transferência e menos armazenamento, **sem mudar o código**, com orçamento e alertas por tag.

## Troubleshooting

| Sintoma | Causa provável | Como resolver |
|---|---|---|
| `AccessDenied` ao submeter | Falta `iam:PassRole` ou restrição de recurso | Ajustar política do submissor |
| `AccessDenied` no S3 dentro do job | Job role sem permissão | Corrigir a job role |
| Segredo não injetado | Execution role sem `GetSecretValue` | Conceder permissão ao segredo |
| Conta alta de NAT | Dados via NAT | Gateway endpoint do S3 |
| Gasto sem dono | Sem tags | Padronizar tags e ativar alocação |
| Spot interrompe demais | Poucos tipos/AZs | Ampliar pools; usar capacity-optimized |

## Estimando o custo de um lote

Uma conta simples ajuda a comparar alternativas antes de executar.

```
 custo ≈ (vCPU-horas × preço por vCPU-hora) + (GB-horas × preço por GB-hora) + transferência + logs

 Exemplo de raciocínio (valores ilustrativos, não reais):
   10.000 jobs × 10 min × 2 vCPU  =  ≈ 3.333 vCPU-horas
   Se Spot custa, por exemplo, 60% menos que On-Demand,
   o mesmo lote custa ≈ 40% do valor On-Demand.
```

| Pergunta | Como responder |
|---|---|
| Quanto custa um job? | Duração × recursos × preço, medido no Cost Explorer por tag |
| Spot compensa? | Compare o custo incluindo retries por interrupção |
| Fargate ou EC2? | Fargate cobra por vCPU/GB-hora do job; EC2 cobra a instância inteira, ocupada ou não |
| Empacotamento é bom? | Veja a utilização média das instâncias; baixa utilização indica jobs mal dimensionados |

> [!warning] Fargate x EC2 depende da ocupação
> Em EC2, instâncias bem empacotadas (vários jobs por máquina) costumam sair mais baratas para cargas contínuas; Fargate brilha em cargas esparsas, onde você não quer pagar por máquina ociosa.

### Metas de FinOps para o Batch

1. Custo por job e por projeto visível em dashboard.
2. Taxa de retries por interrupção abaixo de um limite acordado.
3. Utilização média das instâncias acima de uma meta (por exemplo, 60%).
4. Revisão mensal de `maxvCpus`, tipos de instância e retenção de logs.

## Erros comuns e armadilhas

- **Usar uma role única e poderosa** para submissão, execução e código.
- **Dar `iam:PassRole` irrestrito.**
- **Segredos em `environment` ou na imagem.**
- **Tráfego pesado de dados pelo NAT Gateway.**
- **Comprar Savings Plan para carga que é pico ocasional.**
- **`minvCpus` fixo "por segurança"** gerando custo contínuo.
- **Sem orçamento nem tags**, descobrindo o gasto só na fatura.
- **Imagens com `latest` e sem varredura** de vulnerabilidades.

## 🧩 Quiz de Fixação

1. Qual a diferença entre job role e execution role?
2. Como restringir quais filas e definições um usuário pode usar?
3. Por que preferir VPC endpoints (S3 gateway) ao NAT para grandes volumes?
4. Quando faz sentido comprar Savings Plans no Batch?
5. Onde guardar uma senha de banco usada por um job?
6. Quais controles funcionam como "disjuntor" de custo?

**Respostas:**
1) A job role dá permissões ao código do job; a execution role é usada pela plataforma para puxar imagem, gravar logs e ler segredos.
2) Com políticas IAM que limitam batch:SubmitJob a ARNs específicos de job-definition e job-queue, e restringindo iam:PassRole às roles esperadas.
3) O NAT cobra por dado processado; o gateway endpoint do S3 evita esse custo e mantém o tráfego dentro da rede AWS.
4) Para a parcela de carga base previsível e contínua; picos e cargas ocasionais ficam em Spot/On-Demand.
5) No Secrets Manager, injetada via campo secrets, com a execution role autorizada a ler o segredo.
6) maxvCpus, minvCpus baixo, quotas de serviço, AWS Budgets e Cost Anomaly Detection.
