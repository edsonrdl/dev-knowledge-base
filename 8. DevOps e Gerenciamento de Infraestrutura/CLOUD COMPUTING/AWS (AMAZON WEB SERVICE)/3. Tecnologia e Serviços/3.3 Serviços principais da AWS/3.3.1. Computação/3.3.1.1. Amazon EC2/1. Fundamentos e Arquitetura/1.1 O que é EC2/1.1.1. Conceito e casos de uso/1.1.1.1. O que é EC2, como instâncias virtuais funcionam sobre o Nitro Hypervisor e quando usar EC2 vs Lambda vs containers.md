### O que é EC2, como funciona internamente e quando escolhê-lo

Amazon EC2 (Elastic Compute Cloud) é o serviço de computação virtual da AWS: ele fornece servidores virtuais — chamados de instâncias — que você pode iniciar, configurar, usar e terminar sob demanda. Cada instância é um ambiente computacional completo com vCPU, memória RAM, armazenamento e rede dedicados, executando sobre o hardware físico dos data centers da AWS. Entender como o EC2 funciona por baixo do capô é o que diferencia quem só usa o serviço de quem projeta sistemas eficientes e resilientes sobre ele.

---

## O que acontece quando você inicia uma instância EC2

```
Você chama: aws ec2 run-instances --image-id ami-xxx --instance-type t3.medium

Nos bastidores:

1. Scheduler AWS:
   → Encontra um servidor físico com capacidade disponível
   → Considera: tipo de instância, AZ solicitada, placement group

2. AWS Nitro Hypervisor:
   → Cria uma VM isolada no servidor físico
   → Aloca: 2 vCPUs (threads do processador físico) + 4GB RAM
   → Estabelece: Elastic Network Interface (ENI) na VPC
   → Configura: Nitro Card para I/O de rede e storage

3. Boot:
   → AMI (Amazon Machine Image) copiada para volume EBS
   → VM inicia: BIOS → Bootloader → Kernel → Init system
   → User data executado (se configurado)
   → Instância fica "running" em ~60 segundos

4. Você recebe:
   → ID da instância (i-0abc123...)
   → IP privado (10.0.x.x) — permanente enquanto a instância existir
   → IP público (54.x.x.x) — muda a cada stop/start (sem Elastic IP)
```

## O AWS Nitro System — o coração do EC2 moderno

```
Nitro é a plataforma de hypervisor proprietária da AWS,
substituindo o Xen (tecnologia anterior) desde 2017:

Arquitetura do Nitro:

┌─────────────────────────────────────────────────────────────┐
│  Instância EC2 (sua VM)                                     │
│  ├── vCPUs (threads do processador físico)                  │
│  ├── RAM (páginas de memória física)                        │
│  └── Dispositivos virtuais (disco, rede)                   │
├─────────────────────────────────────────────────────────────┤
│  Nitro Hypervisor (kernel mínimo ~5.000 linhas de código)   │
│  → Isola memória entre VMs                                 │
│  → Gerencia CPU scheduling                                  │
├─────────────────────────────────────────────────────────────┤
│  Nitro Cards (hardware dedicado — ASICs)                    │
│  ├── Nitro Card for VPC: processa rede (sem overhead CPU)   │
│  ├── Nitro Card for EBS: processa I/O de storage            │
│  └── Nitro Security Chip: root of trust, medição segura     │
├─────────────────────────────────────────────────────────────┤
│  Servidor Físico (CPU + RAM física)                         │
└─────────────────────────────────────────────────────────────┘
```

### Por que o Nitro é uma vantagem real

**1. Overhead praticamente zero:**
```
Hypervisor tradicional (Xen/VMware):
  → Hypervisor consume 10-30% dos recursos do servidor
  → Sua VM tem apenas 70-90% da capacidade real

Nitro Hypervisor:
  → Quase zero overhead (hypervisor mínimo em hardware dedicado)
  → Instâncias "metal" (bare-metal): zero overhead, acesso direto ao HW
  → Você paga pelo que usa — não paga pelo overhead do hypervisor
```

**2. I/O offloaded para hardware:**
```
Rede e storage processados pelas Nitro Cards:
→ CPU da instância não gasta ciclos em I/O
→ Sua aplicação tem CPU disponível para o trabalho real
→ Throughput de rede: até 100 Gbps em instâncias grandes
→ Throughput de EBS: até 256.000 IOPS em instâncias io2
```

**3. Isolamento de segurança forte:**
```
Nitro Security Chip:
→ Estabelece root of trust verificável em hardware
→ VM escape é extremamente difícil (ataque que sai da VM para o hypervisor)
→ Memória de uma instância nunca acessível por outra (mesmo no mesmo host)
→ Base para multi-tenancy seguro de clientes diferentes no mesmo hardware
```

## AMI — o template de uma instância

```
AMI (Amazon Machine Image) é a "receita" da instância:
  ├── SO e kernel (Amazon Linux, Ubuntu, Windows, etc.)
  ├── Software pré-instalado (Docker, Apache, etc.)
  ├── Configurações do sistema
  └── Volumes de EBS mapeados (root + adicionais)

Tipos de AMI:
  AWS managed: Amazon Linux 2023, Windows Server 2022, Ubuntu 22.04...
  AWS Marketplace: AMIs de terceiros com software comercial
  Community AMIs: AMIs públicas criadas pela comunidade
  Custom AMIs: você cria a partir de instância existente

Ciclo de uso da AMI:
  1. Lança instância a partir da AMI base
  2. Instala e configura software
  3. Para a instância
  4. Cria AMI customizada (snapshot do estado atual)
  5. Usa a AMI customizada para lançar novas instâncias idênticas

Golden AMI (prática recomendada):
  → AMI com tudo pré-instalado e pré-configurado
  → Nova instância do ASG: inicia em 30-60s (sem instalar nada durante boot)
  → User data mínimo: apenas configuração dinâmica (IP, secrets, etc.)
  → Alternativa: container Docker para mesma finalidade

Regiões e AMIs:
  → AMI é regional — não está disponível em outra Região automaticamente
  → Para usar em outra Região: aws ec2 copy-image
  → AMIs são imutáveis após criação (versionamento via nomenclatura)
```

## EC2 vs Lambda vs Containers — quando usar cada um

```
A escolha entre EC2, Lambda e containers (ECS/EKS/Fargate) depende
de cinco dimensões: controle, latência, duração, custo e complexidade.
```

### Quando escolher EC2

```
✓ EC2 é a escolha certa quando:

1. Controle total do ambiente é necessário:
   → Software que requer configuração específica do kernel
   → Aplicações que precisam de módulos kernel customizados
   → Workloads que requerem acesso a hardware (GPU, FPGA, NVMe local)

2. Workloads de longa duração (> 15 minutos):
   → Lambda tem timeout de 15 minutos — jobs longos exigem EC2
   → Processamento de vídeo, treinamento de ML, jobs batch longos

3. Aplicações stateful com estado em memória:
   → Servidores de jogo que mantêm sessão em RAM
   → In-memory databases (Redis auto-gerenciado com muita RAM)
   → Aplicações legadas que não foram projetadas para escala horizontal

4. Workloads previsíveis e de alto uso contínuo:
   → 24/7 com alta utilização de CPU → Reserved Instances = mais barato
   → Custo EC2 linear com tempo; Lambda = custo por invocação

5. Necessidade de GPU para workloads pesados:
   → Lambda não tem GPU; ECS/EKS com Fargate tem suporte limitado
   → P/G instances com GPU NVidia: único caminho para HPC/ML pesado
```

### Quando escolher Lambda

```
✓ Lambda é a escolha certa quando:

1. Workloads event-driven e intermitentes:
   → Tráfego de 0 a N invocações — paga zero quando sem tráfego
   → Processamento de imagem ao ser enviada ao S3
   → Resposta a eventos (IOT, webhooks, notificações)

2. APIs de baixo a médio volume:
   → < 1-5 milhões de requisições/dia: Lambda geralmente mais barato
   → Sem previsão de tráfego: Lambda escala automaticamente

3. Glue code entre serviços:
   → "Quando evento X chegar, transforma e manda para Y"
   → Transformação de dados em pipelines ETL

4. Execuções curtas (< 5 minutos idealmente):
   → Evita cold starts frequentes que penalizam execuções longas

5. Zero operação desejada:
   → Sem patch de SO, sem ASG para configurar, sem capacity planning
```

### Quando escolher Containers (ECS/EKS/Fargate)

```
✓ Containers são a escolha certa quando:

1. Portabilidade e reproducibilidade são críticas:
   → Mesmo container roda igual em dev, staging e prod
   → Migrar entre clouds sem reescrever (Kubernetes = cloud-agnóstico)

2. Microserviços com múltiplos componentes:
   → Cada serviço como container separado
   → Orquestração (health check, rolling deploy, service discovery)

3. Latência de inicialização melhor que Lambda com menor custo que EC2:
   → Container inicia em segundos (não minutos como EC2)
   → Mais barato que EC2 para workloads de densidade média
   → Melhor cold start que Lambda Java/JVM

4. Times que já usam Docker no desenvolvimento:
   → "O que roda localmente roda igual na AWS"
   → Pipeline CI/CD já constrói imagens Docker

5. Quando Lambda é muito restritivo:
   → Timeout > 15 min, GPU, estado complexo, portabilidade
   → Containers oferecem ambiente customizável sem gerenciar EC2
```

### Árvore de decisão rápida

```
Meu workload precisa de GPU?
  Sim → EC2 (P/G family)
  Não → continua...

É event-driven e pode escalar a zero?
  Sim + execução < 15min → Lambda
  Não → continua...

Preciso de controle total do SO ou longa duração?
  Sim → EC2
  Não → continua...

Já uso Docker ou preciso de portabilidade?
  Sim → Containers (ECS/EKS/Fargate)
  Não → continua...

Carga previsível e constante 24/7?
  Sim → EC2 (Reserved Instances)
  Não + intermitente → Lambda ou Fargate

```

## Primeira instância: decisões que importam

| Decisão | Opções | Recomendação inicial |
|---|---|---|
| AMI | Amazon Linux, Ubuntu, Windows, customizada | AMI atual e mínima; golden AMI em produção |
| Tipo | t (burst), m (geral), c, r... | Comece em m ou t3/t4g e meça |
| Rede | Subnet pública/privada, SG | Privada + SSM Session Manager |
| Acesso | Chave SSH, SSM | SSM (sem porta 22 aberta) |
| Armazenamento | EBS gp3, instance store | gp3 para dados que devem persistir |
| Identidade | Instance profile (IAM role) | Sempre; nunca chaves no disco |
| Metadata | IMDSv2 | Exigir IMDSv2 |

```
 Estados de uma instância:
 pending ─► running ─► stopping ─► stopped ─► (start) ─► pending
                │                      │
                └─► shutting-down ─► terminated   (terminate é irreversível)
 stop: preserva EBS, perde IP público dinâmico e instance store
```

### Árvore de decisão: onde rodar a carga

```
Preciso de SO completo, software legado, GPU, controle total? ─► EC2
Código curto orientado a eventos? ─────────────────────────────► Lambda
Aplicação já em containers? ───────────────────────────────────► ECS/EKS (Fargate ou EC2)
Aplicação web simples, quer só enviar o código? ───────────────► Beanstalk
```

## Segurança desde o primeiro dia

1. IMDSv2 obrigatório (mitiga SSRF roubando credenciais).
2. SG com o mínimo necessário; sem `0.0.0.0/0` na porta 22.
3. EBS criptografado por padrão (habilite no nível da conta/região).
4. Patches automatizados com Systems Manager Patch Manager.
5. Tags obrigatórias (`env`, `owner`, `custo`).

## CLI comentado

```bash
# Lança instância privada, com IMDSv2 e role, sem chave SSH
aws ec2 run-instances --image-id ami-0abc --instance-type t3.small \
  --subnet-id subnet-0123 --security-group-ids sg-0123 \
  --iam-instance-profile Name=ssm-profile \
  --metadata-options HttpTokens=required,HttpEndpoint=enabled \
  --block-device-mappings 'DeviceName=/dev/xvda,Ebs={VolumeSize=20,VolumeType=gp3,Encrypted=true}' \
  --tag-specifications 'ResourceType=instance,Tags=[{Key=env,Value=dev}]'

# Acessa sem SSH
aws ssm start-session --target i-0123456789abcdef0

# Estado e IP
aws ec2 describe-instances --instance-ids i-0123456789abcdef0 \
  --query 'Reservations[0].Instances[0].[State.Name,PrivateIpAddress]'
```

## Troubleshooting

| Sintoma | Causa provável | Ação |
|---|---|---|
| Não conecta por SSH | SG, rota, IP público, chave | Usar SSM ou revisar SG/rota |
| `Status check failed` | Falha de SO/rede/hardware | Reiniciar; ver console output; recriar a partir da AMI |
| SSM não aparece | Falta role ou conectividade ao SSM | Role + endpoints/NAT |
| Instância encerrou ao parar | Instance store ou política | Usar EBS para dados persistentes |

## 🧩 Quiz de Fixação

1. Uma instância EC2 m6i.xlarge usa 4 vCPUs. Esses 4 vCPUs são "reais" no sentido físico? Como o Nitro Hypervisor mapeia vCPUs para hardware físico e qual é o impacto disso na performance?
2. Um time está debatendo entre EC2 e Lambda para um serviço de API REST que recebe 500 requisições/hora (tráfego muito baixo e irregular). Qual é o argumento técnico E financeiro para Lambda nesse cenário específico?
3. Por que o Nitro System permitiu à AWS lançar instâncias "bare-metal" (como i3.metal ou m6i.metal), e qual é o caso de uso que justifica pagar por uma instância bare-metal em vez de uma instância EC2 regular?

**Respostas:**
1) Os vCPUs do EC2 são mapeados para threads físicas do processador (hyperthreading/SMT). Um core físico moderno com SMT expõe 2 threads — cada uma é um vCPU do ponto de vista do SO guest. Em um servidor com 2 sockets × 32 cores × 2 threads = 128 vCPUs disponíveis para distribuir entre VMs. O Nitro Hypervisor aloca 4 dessas threads para a m6i.xlarge. O impacto é que o isolamento de CPU não é perfeito — duas VMs no mesmo core físico podem sofrer interferência (CPU cache contention, shared execution units). Para workloads de alta performance sensíveis a jitter, instâncias "metal" (bare-metal) eliminam esse problema dando acesso direto ao hardware sem VM intermediária.
2) Argumento técnico: com 500 requisições/hora = ~8 requisições/minuto, a instância EC2 ficaria ociosa 99%+ do tempo. Lambda só executa quando há requisição — ambiente iniciado sob demanda, executa e termina. Sem servidor idle consumindo recursos. Argumento financeiro: Lambda com 500 req/hora × 200ms × 512MB = 0.05 req/s × 0.2s × 0.5GB × $0.0000166667 = $0.0000008333/segundo = $0.072/dia = $2.16/mês. EC2 t3.micro (menor opção) 24/7 = $0.0104/hora × 720h = $7.49/mês. Lambda é 3.5× mais barato para esse volume e cobra zero quando não há tráfego (madrugada, fins de semana). Para 500 req/hora, Lambda ganha em custo E operação.
3) O Nitro System permitiu bare-metal porque o hypervisor foi movido para hardware dedicado (Nitro Chips), liberando os recursos do servidor inteiro para a VM. Anteriormente com Xen, remover o hypervisor seria impossível pois estava no caminho de I/O. Com Nitro, a instância bare-metal não tem VM — é acesso direto ao servidor físico, com as Nitro Cards ainda gerenciando rede e storage da AWS. Casos de uso que justificam: (1) licenças de software por socket/core físico (Oracle, VMware) — o bare-metal expõe sockets físicos reais, não vCPUs; (2) executar seu próprio hypervisor dentro da AWS (VMware on AWS, Nutanix Cloud Clusters) — para migrar VMs on-premises sem recompilação; (3) workloads extremamente sensíveis a jitter onde qualquer overhead de hypervisor é inaceitável (HFT, simulações físicas em tempo real).

**Questões complementares:**

4. Por que exigir IMDSv2 nas instâncias?
5. O que se perde ao parar (stop) uma instância EC2?
6. Qual a forma recomendada de acessar uma instância privada sem abrir a porta 22?

**Respostas das questões complementares:**
4) Porque IMDSv2 usa token de sessão e mitiga ataques de SSRF que roubariam credenciais da role pelo serviço de metadata.
5) O IP público dinâmico e os dados do instance store; volumes EBS são preservados.
6) AWS Systems Manager Session Manager, com a role adequada e conectividade ao SSM (endpoints ou NAT).
