### Família C — Compute Optimized: alta CPU para cargas intensivas de processamento

A família C (Compute Optimized) é a escolha da AWS para workloads onde a CPU é o recurso crítico — não memória, não armazenamento, não GPU. Ela entrega a melhor relação vCPU/custo da linha EC2, sendo a referência para qualquer aplicação que precise de ciclos de processamento puros e previsíveis.

---

## O que define a família C

A família C é otimizada para **alta densidade de vCPU por dólar**. Enquanto as famílias T e M equilibram CPU e memória, as instâncias C entregam proporcionalmente mais vCPU com menos memória — a relação típica é de **2 GiB de RAM por vCPU**, metade do que a família M oferece.

```
Comparativo de proporção vCPU : Memória
────────────────────────────────────────────────────
Família T (burstable)  │ ~2 GiB/vCPU (com créditos)
Família M (balanced)   │ ~4 GiB/vCPU
Família C (compute)    │ ~2 GiB/vCPU (sem throttling)
Família R (memory)     │ ~8 GiB/vCPU
────────────────────────────────────────────────────
```

A diferença essencial entre C e T não é só a proporção — é a **garantia de performance**: instâncias C entregam 100% dos vCPUs o tempo todo, sem o mecanismo de créditos e throttling das T. Ideal para cargas sustentadas.

---

## Gerações e processadores disponíveis

A AWS oferece a família C em múltiplas gerações, cada uma com um processador subjacente diferente. A geração atual é a **C7**:

| Instância | Processador | Destaque |
|---|---|---|
| **C7g** | AWS Graviton3 (ARM) | Melhor desempenho/$ da família; ideal para workloads Linux nativos |
| **C7gn** | Graviton3E (ARM) | Otimizado para rede — até 200 Gbps; casos de uso de telecomunicações |
| **C7i** | Intel Xeon Scalable (Sapphire Rapids) | Melhor compatibilidade com software legado x86 |
| **C7a** | AMD EPYC Genoa | Boa relação custo/desempenho para cargas x86 |
| **C6g / C6i / C6a** | Graviton2 / Intel Ice Lake / AMD Milan | Geração anterior — ainda amplamente usada |

**Graviton3 (C7g) é a recomendação padrão** para novos projetos em Linux: ~25% mais rápido que C6g e até 40% melhor eficiência energética, com custo menor que os equivalentes Intel.

## Casos de uso principais

### Transcoding e processamento de mídia

Encoding de vídeo (H.264, H.265/HEVC, AV1) é intenso em CPU e paralelizável. A família C escala horizontalmente — várias instâncias menores (ex: `c7g.2xlarge`) processando segmentos em paralelo costuma ser mais eficiente que uma instância grande única.

```
Exemplo de pipeline de transcoding:
┌─────────────┐    ┌──────────────────────────────────┐
│  S3 (input) │───▶│  Auto Scaling Group de c7g.2xl   │
│  vídeo raw  │    │  FFmpeg / MediaConvert workers    │
└─────────────┘    └──────────────┬───────────────────┘
                                  │
                        ┌─────────▼────────┐
                        │  S3 (output)     │
                        │  vídeo encodado  │
                        └──────────────────┘
```

### Game servers

Servidores de jogos multiplayer (física, lógica de jogo, sincronização de estado) precisam de CPU consistente e baixa latência de rede. A família C, combinada com **Enhanced Networking (ENA)** e colocação em **Placement Groups**, atende esse perfil.

- Tick rate alto (ex: 128 tick em FPS competitivos) exige processamento de centenas de eventos por segundo por sala
- Instâncias como `c7i.4xlarge` ou `c7g.4xlarge` são referências comuns para game server hosting

### ML Inference (sem GPU)

Modelos de ML em produção frequentemente não precisam de GPU na fase de inferência — especialmente modelos menores ou quando a latência GPU não compensa o custo. A família C suporta **AVX-512** (Intel/AMD) e as instruções vetoriais do Graviton3, acelerando operações de álgebra linear usadas em inferência.

```
Quando usar C para inferência vs instâncias de GPU:
────────────────────────────────────────────────────────────────
Use C quando:          │ Use G/P/Inf quando:
• Modelo pequeno/médio │ • Modelo grande (LLM, difusão)
• Latência tolerável   │ • Throughput alto exigido
• Custo é prioridade   │ • Batch inference em escala
• Modelo já otimizado  │ • Treinamento contínuo
  (ONNX, TensorRT CPU) │
────────────────────────────────────────────────────────────────
```

### HPC (High Performance Computing)

Simulações científicas, cálculos de risco financeiro, análises de elementos finitos e CFD (Computational Fluid Dynamics) se beneficiam da alta densidade de vCPU. Para HPC em larga escala, o `c7gn` com 200 Gbps de rede permite clusters de computação com baixíssima latência de comunicação entre nós (essencial para MPI).

### Outros casos de uso relevantes

- **Web servers de alta concorrência** (Nginx, HAProxy) com muitos workers
- **Compilação distribuída** (builds de C++, Rust, Go em larga escala)
- **DNS servers e proxies reversos** com alta taxa de requisições
- **Batch processing** com workloads CPU-bound (ETL, compressão, criptografia)

## Comparativo: quando usar C vs outras famílias

| Critério | Família T | Família M | Família C | Família R |
|---|---|---|---|---|
| CPU sustentada | Não (créditos) | Sim | Sim | Sim |
| Proporção RAM/vCPU | ~2 GiB | ~4 GiB | ~2 GiB | ~8 GiB |
| Melhor para | Dev, cargas irregulares | Web apps, bancos gerais | CPU-bound, transcoding, HPC | In-memory DBs, caches |
| Custo relativo | Mais barato | Médio | Médio | Mais caro |
| CPU burst | Sim (prejudica sob carga) | Não | Não | Não |

**Regra prática:** se sua aplicação passa mais de 20-30% do tempo com CPU acima de 80%, migre de T para C ou M. Se a CPU é o único gargalo e memória sobra, C é mais econômico que M.

## Árvore de decisão

```
O gargalo é CPU (não memória)?
├─ Sim ─► C
│    ├─ Binário recompilável para ARM? ─► c*g (Graviton)
│    ├─ Precisa AVX-512/ecossistema x86? ─► c*i
│    └─ Só quer preço/desempenho x86 ─► c*a
└─ Não ─► M ou R
```

## Como validar a escolha

1. Rodar benchmark representativo (não sintético) em 2-3 candidatas.
2. Medir custo por unidade de trabalho (por req/s, por vídeo transcodificado).
3. Observar CPU, memória e rede no CloudWatch; se a memória sobra, a família C é a certa.
4. Usar Compute Optimizer para recomendações baseadas em uso real.

## CLI comentado

```bash
# Lista tipos da família c7 com vCPU e memória
aws ec2 describe-instance-types --filters "Name=instance-type,Values=c7*" \
  --query 'InstanceTypes[].[InstanceType,VCpuInfo.DefaultVCpus,MemoryInfo.SizeInMiB]' \
  --output table

# Pede recomendações de rightsizing
aws compute-optimizer get-ec2-instance-recommendations \
  --instance-arns <ARN_INSTANCIA>
```

## Troubleshooting

| Sintoma | Causa provável | Ação |
|---|---|---|
| Out of memory em C | Razão vCPU:memória baixa | Migrar para M/R |
| Desempenho abaixo do esperado | Throttling de rede/EBS | Checar limites da instância e `n`/EBS-optimized |
| Binário não roda em c*g | Arquitetura ARM | Recompilar/usar imagem multi-arch |
| CPU em 100% constante | Subdimensionada | Escalar horizontal ou subir tamanho |

## Custo

Família C custa menos por vCPU que M/R, mas só gera economia se a memória sobrante não for desperdiçada. Graviton costuma entregar melhor preço/desempenho; Savings Plans cobrem famílias flexíveis, e Spot é boa opção para transcoding e batch tolerantes a interrupção.

## Erros comuns e armadilhas

**Usar C quando a aplicação é memory-bound:** se a aplicação troca frequentemente dados com disco (swap) ou tem cache miss alto por falta de RAM, adicionar vCPU não resolve. Verifique métricas de memória antes de escolher C.

**Ignorar o Graviton3 por hábito:** muitas equipes escolhem C7i por familiaridade com x86, deixando até 30% de economia na mesa. A maioria dos workloads Linux modernos (containers, microserviços, linguagens gerenciadas) roda sem alterações no Graviton.

**Superdimensionar para "segurança":** uma `c7g.4xlarge` ociosa custa o dobro de uma `c7g.2xlarge`. Use CloudWatch + Compute Optimizer para dimensionar corretamente.

**Não considerar Spot para cargas stateless:** transcoding, renderização e HPC são candidatos perfeitos para Spot Instances com família C — até 70% de desconto para cargas que toleram interrupção.

## 🧩 Quiz de Fixação

1. Qual é a principal diferença entre usar uma instância `t3.xlarge` e uma `c7g.xlarge` para um servidor de processamento de vídeo que roda 24/7?

2. Você está fazendo inferência com um modelo BERT (110M parâmetros) em produção, recebendo 500 requisições/segundo. Por que uma instância `c7i.4xlarge` pode ser mais vantajosa que uma `g4dn.xlarge` nesse cenário?

3. Um cliente precisa rodar simulações de dinâmica de fluidos em um cluster de 50 nós que trocam muitos dados entre si via MPI. Qual variante da família C você recomendaria e por quê?

**Respostas:**

1) A `t3.xlarge` usa o mecanismo de CPU Credits — quando os créditos se esgotam (o que ocorre rapidamente em carga sustentada de 24/7), a CPU é reduzida a um baseline de 40% da capacidade. A `c7g.xlarge` entrega 100% dos vCPUs continuamente, sem throttling. Para processamento de vídeo contínuo, a C é a escolha correta; a T geraria gargalos e latência imprevisível.

2) GPUs têm latência de inicialização alta para batches pequenos e o custo fixo da `g4dn.xlarge` (~$0,526/h) supera o da `c7i.4xlarge` para modelos de tamanho médio. BERT otimizado com ONNX Runtime ou OpenVINO roda eficientemente em CPU com AVX-512 (suportado pelo Xeon Sapphire Rapids da C7i). O custo por requisição tende a ser menor na família C para esse perfil, e não há dependência de drivers CUDA.

3) `c7gn.xlarge` ou superior. A variante **C7gn** é construída sobre o Graviton3E e oferece até **200 Gbps de largura de banda de rede**, essencial para clusters MPI que trocam grandes volumes de dados entre nós (halo exchanges, AllReduce). Combinada com um **Cluster Placement Group** para minimizar latência de rede, é a configuração ideal para HPC na família C.

**Questões complementares:**

4. Que sinal nas métricas confirma que a família C é adequada?
5. Quando escolher c*g (Graviton)?
6. Qual o uso do sufixo `d`?

**Respostas das questões complementares:**
4) CPU alta com memória sobrando: a carga é limitada por computação, não por memória.
5) Quando o software pode rodar em ARM (recompilável ou imagens multi-arch) e se busca melhor preço/desempenho.
6) Indica NVMe local na instância, útil para cache e dados temporários rápidos (não persistem).
