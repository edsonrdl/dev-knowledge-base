### Discos, buckets e bancos gerenciados no Lightsail — block storage, object storage e relational databases

> [!warning] Aviso
> Tamanhos máximos, planos de bucket, versões de engine, janelas de backup e preços mudam. Os valores aqui são referências de estudo; confirme na documentação. Os comandos **não foram executados**.

O Lightsail oferece três formas de guardar dados, cada uma com um papel bem diferente: **discos** (bloco, anexados a uma instância), **buckets** (objetos, acessados por HTTP) e **bancos de dados gerenciados** (MySQL e PostgreSQL com backup e manutenção automáticos). Escolher a forma errada é uma das causas mais comuns de custo extra e de perda de dados em projetos pequenos.

**Analogia:** o **disco** é o **HD externo plugado no seu notebook** (rápido, mas ligado a uma máquina por vez); o **bucket** é um **armário de arquivos na nuvem** que muita gente acessa por endereço; o **banco gerenciado** é um **arquivista profissional** que organiza, indexa e faz cópia de segurança para você.

## Visão geral e escolha

```
                    ┌────────────────────────────────────┐
 Dados do app ────► │ Precisam de consultas/transações?  │
                    └───────┬─────────────────┬──────────┘
                         sim│                 │não
                            ▼                 ▼
                    Banco gerenciado   Arquivos/objetos?
                    (MySQL/Postgres)     ├─ acessados por HTTP/CDN, muitos clientes ─► Bucket
                                         └─ lidos como pasta local de UMA instância ─► Disco
```

| Característica | Disco (block) | Bucket (object) | Banco gerenciado |
|---|---|---|---|
| Acesso | Montado como volume na instância | API/HTTP (S3-compatível) | Conexão SQL |
| Compartilhável | Uma instância por vez | Sim, muitos clientes | Sim, via rede |
| Latência | Baixa | Média | Baixa a média |
| Escala | Até um teto por disco | Por plano (armazenamento/transferência) | Por plano (vCPU/RAM/SSD) |
| Backup | Snapshot de disco | Versionamento | Automático + snapshots |
| Uso típico | Dados do app, uploads locais | Mídia, estáticos, backups | Dados transacionais |

## Discos (block storage)

Um **disco** do Lightsail é um volume SSD extra que você **anexa a uma instância** para ampliar o espaço (além do SSD do plano) ou separar dados do sistema operacional.

### Regras essenciais

1. O disco precisa estar na **mesma AZ** da instância.
2. Um disco anexa a **uma instância por vez**.
3. Depois de anexar, é preciso **formatar e montar** o volume dentro do SO.
4. Dá para **aumentar** o tamanho, não reduzir.
5. Snapshots de disco permitem backup e criar discos em outras instâncias.

```
 Instância web-1 (AZ-a)                     Disco dados-1 (AZ-a)
 ┌──────────────────────┐   attach-disk     ┌─────────────────┐
 │ SSD do plano  /dev/xvda │◄────────────────│ 200 GB SSD      │
 │ montagem: /dados  ◄─── /dev/xvdf ────────┘                 │
 └──────────────────────┘                    └─────────────────┘
```

```bash
# Cria um disco de 200 GB na AZ da instância
aws lightsail create-disk --disk-name dados-1 \
  --availability-zone sa-east-1a --size-in-gb 200

# Anexa à instância (aparece como /dev/xvdf, por exemplo)
aws lightsail attach-disk --disk-name dados-1 \
  --instance-name web-1 --disk-path /dev/xvdf

# Dentro da instância: formata, monta e persiste no fstab
sudo mkfs.ext4 /dev/xvdf
sudo mkdir -p /dados && sudo mount /dev/xvdf /dados
echo '/dev/xvdf /dados ext4 defaults,nofail 0 2' | sudo tee -a /etc/fstab

# Snapshot do disco
aws lightsail create-disk-snapshot --disk-name dados-1 --disk-snapshot-name dados-1-snap
```

| Sintoma | Causa | Ação |
|---|---|---|
| Disco não aparece no SO | Não formatado/montado | `lsblk`, `mkfs`, `mount` |
| Perdeu a montagem após reboot | Sem entrada no `fstab` | Adicionar com `nofail` |
| Erro ao anexar | AZ diferente | Recriar na AZ correta |
| Espaço acabou | Disco pequeno | Aumentar e expandir o FS (`resize2fs`) |

## Buckets (object storage)

O **bucket** do Lightsail é um armazenamento de objetos **compatível com a API do S3**, vendido por **plano** que inclui armazenamento e transferência mensais. É uma versão simplificada do S3 para quem não quer lidar com todas as opções do serviço grande (veja [[8. DevOps e Gerenciamento de Infraestrutura/CLOUD COMPUTING/AWS (AMAZON WEB SERVICE)/3. Tecnologia e Serviços/3.3 Serviços principais da AWS/3.3.2. Armazenamento/3.3.2.1. Amazon S3/0 Amazon S3 (Tópicos )|Amazon S3]]).

| Recurso | Descrição |
|---|---|
| Planos | Tamanhos fixos (ex.: 250 GB, 1 TB, 5 TB) com transferência incluída |
| Acesso | Privado por padrão; opção de tornar objetos públicos ou de liberar acesso a instâncias |
| Versionamento | Protege contra sobrescrita/exclusão acidental |
| Chaves de acesso | Para aplicações externas (access keys do bucket) |
| Acesso a recursos | Anexar instâncias ao bucket para dar permissão sem chaves |

```bash
# Cria o bucket com plano pequeno
aws lightsail create-bucket --bucket-name midia-do-site-2026 \
  --bundle-id small_1_0

# Mantém o histórico de versões
aws lightsail update-bucket --bucket-name midia-do-site-2026 \
  --versioning Enabled

# Libera leitura pública apenas de objetos (cuidado!)
aws lightsail update-bucket --bucket-name midia-do-site-2026 \
  --access-rules getObject=public,allowPublicOverrides=false

# Permite que a instância acesse o bucket sem chaves fixas
aws lightsail set-resource-access-for-bucket \
  --resource-name web-1 --bucket-name midia-do-site-2026 --access allow

# Usa a API S3 (endpoint regional do Lightsail) com a CLI s3
aws s3 cp foto.jpg s3://midia-do-site-2026/foto.jpg --profile lightsail-bucket
```

> [!warning] Público só quando necessário
> Buckets públicos expõem dados na internet. Para entregar conteúdo ao mundo, prefira **buckets privados atrás de uma distribuição CDN** do Lightsail.

### Árvore de decisão: bucket ou disco?

```
O conteúdo é lido por vários clientes/usuários via URL?
├─ Sim ─► Bucket (+ CDN)
└─ Não
    └─ A aplicação precisa de acesso como sistema de arquivos local, baixa latência? ─► Disco
Preciso guardar backups/arquivos grandes baratos? ─► Bucket
```

## Bancos de dados gerenciados

O **banco gerenciado do Lightsail** entrega **MySQL ou PostgreSQL** em planos fixos, com **backups automáticos, manutenção, snapshots e métricas**. É um "RDS simplificado" (veja [[8. DevOps e Gerenciamento de Infraestrutura/CLOUD COMPUTING/AWS (AMAZON WEB SERVICE)/3. Tecnologia e Serviços/3.3 Serviços principais da AWS/3.3.3. Banco de Dados/3.3.3.1. Amazon RDS/0 Amazon RDS (Tópicos )|Amazon RDS]]).

| Plano | Característica | Quando |
|---|---|---|
| **Standard** | Uma instância em uma AZ | Dev/teste e sites pequenos |
| **High availability** | Standby em outra AZ com failover automático | Produção que não pode parar |

Funcionalidades: **backup automático diário** com retenção de poucos dias (referência), **restauração para ponto no tempo (PITR)**, **snapshots manuais**, janelas de backup e manutenção configuráveis, **acesso público opcional** (padrão: privado), criptografia em repouso, parâmetros do banco ajustáveis.

```
 Plano Standard                   Plano High availability
 ┌──────────┐                     ┌──────────┐  replicação  ┌──────────┐
 │ Primário │                     │ Primário │ ───────────► │ Standby  │
 │  AZ-a    │                     │  AZ-a    │  síncrona    │  AZ-b    │
 └──────────┘                     └──────────┘              └──────────┘
 falha da AZ = indisponível       falha da AZ = failover automático
```

```bash
# Cria um MySQL de plano pequeno
aws lightsail create-relational-database \
  --relational-database-name bd-site --availability-zone sa-east-1a \
  --relational-database-blueprint-id mysql_8_0 \
  --relational-database-bundle-id micro_2_0 \
  --master-database-name app --master-username admin \
  --master-user-password '<defina-uma-senha-forte>' \
  --no-publicly-accessible

# Endpoint e estado
aws lightsail get-relational-database --relational-database-name bd-site \
  --query 'relationalDatabase.[state,masterEndpoint.address]'

# Restaura para um ponto no tempo (gera NOVO banco)
aws lightsail create-relational-database-from-snapshot \
  --relational-database-name bd-site-restaurado \
  --source-relational-database-name bd-site \
  --restore-time 2026-11-09T10:00:00Z

# Snapshot manual
aws lightsail create-relational-database-snapshot \
  --relational-database-name bd-site \
  --relational-database-snapshot-name bd-site-antes-migracao
```

### Acesso e segurança

| Prática | Detalhe |
|---|---|
| Não público | Mantenha `publiclyAccessible=false` e acesse a partir da instância do Lightsail na mesma região |
| Senha forte | Guarde em gerenciador de segredos; troque periodicamente |
| Usuário por aplicação | Não use o usuário master na aplicação |
| TLS | Exija conexão criptografada quando suportado |
| Peering | Para acessar de fora do Lightsail (VPC), use VPC peering e não o acesso público |

## Qual armazenamento para cada dado

| Dado | Melhor lugar | Motivo |
|---|---|---|
| Usuários, pedidos, transações | Banco gerenciado | Consistência e consultas |
| Imagens e vídeos do site | Bucket + CDN | Escala e custo |
| Uploads temporários da app | Disco local ou bucket | Depende do compartilhamento |
| Logs antigos e backups | Bucket | Barato e durável |
| Cache/sessão volátil | Memória da instância/serviço de cache | Latência |
| Banco rodando na própria instância | Evitar em produção | Sem HA e backup frágil |

## Troubleshooting

| Sintoma | Causa provável | Como resolver |
|---|---|---|
| App não conecta ao banco | Banco privado e cliente fora da rede, senha/endpoint errados | Conectar de instância na mesma região ou usar peering; revisar credenciais |
| Timeout no banco | Firewall/rota ausentes | Conferir acesso público/peering |
| Custo de bucket maior | Transferência acima do plano | CDN, compressão, plano maior |
| Objetos públicos inesperados | Regra pública ativa | Revisar `access-rules` e permissões por objeto |
| Restauração "perdeu" dados recentes | PITR volta a um instante anterior | Escolher horário mais próximo do erro |
| Disco cheio | Dados acumulados | Aumentar disco, expandir FS, limpar |

## Custo

| Recurso | Cobrança |
|---|---|
| Disco | GB-mês provisionado |
| Snapshot de disco | GB-mês armazenado |
| Bucket | Plano fixo mensal (armazenamento + transferência) |
| Banco | Plano fixo; HA é mais caro |
| Snapshots de banco | GB-mês acima do incluído |

**Estratégias:** mover mídia para bucket + CDN reduz a carga da instância; snapshot antigo de disco/banco acumula custo — defina rotina de limpeza; não pague plano HA para ambiente de teste.

## Exemplo prático: WordPress mais robusto

1. Instância WordPress (sem banco interno) em `sa-east-1a`.
2. Banco gerenciado MySQL **privado**, plano Standard (ou HA em produção).
3. Plugin de mídia enviando uploads para um **bucket** privado.
4. **Distribuição CDN** na frente do bucket e do site.
5. Snapshot automático da instância e do banco; snapshot manual antes de atualizações.

## Erros comuns e armadilhas

- **Rodar o banco na mesma instância do site** sem backup separado.
- **Deixar o banco com acesso público** para facilitar testes e esquecer.
- **Esquecer de montar/formatar o disco** e achar que "não funcionou".
- **Não persistir a montagem no `fstab`.**
- **Bucket público por padrão em cada objeto.**
- **Usar o usuário master na aplicação.**
- **Confiar só no backup automático**, de retenção curta.
- **Achar que PITR altera o banco atual:** ele cria um **novo** banco.

## 🧩 Quiz de Fixação

1. Que restrição de AZ existe para anexar um disco?
2. Qual a diferença de uso entre disco e bucket?
3. Por que manter o banco gerenciado como não público?
4. O que muda entre os planos Standard e High availability?
5. Restaurar por ponto no tempo (PITR) sobrescreve o banco atual?
6. Como entregar mídia ao público sem expor o bucket diretamente?

**Respostas:**
1) O disco e a instância precisam estar na **mesma AZ**.
2) O disco é um volume de bloco montado em **uma** instância (baixa latência, uso local); o bucket é armazenamento de objetos acessado por HTTP/S3 por **muitos clientes**, ideal para mídia e backups.
3) Para reduzir a superfície de ataque; o acesso deve vir de instâncias do Lightsail na mesma região ou por VPC peering, não pela internet.
4) O HA mantém um standby em outra AZ com failover automático; o Standard roda em uma só AZ e fica indisponível se ela falhar.
5) Não. O PITR cria um **novo banco** no instante escolhido; é preciso apontar a aplicação para ele.
6) Mantendo o bucket privado e usando uma **distribuição CDN** do Lightsail à frente dele.
