### O que é Amazon Lightsail — VPS simplificado, planos de preço fixo, blueprints, regiões e quando usar em vez de EC2

> [!warning] Aviso
> Planos, preços, franquias de transferência, limites e blueprints do Lightsail mudam com frequência. Os valores deste material são **ordens de grandeza** para fins de estudo; confirme na documentação e na página de preços. Os comandos de CLI e os exemplos **não foram executados**.

O **Amazon Lightsail** é a porta de entrada da AWS para quem quer **subir um servidor, um site ou uma pequena aplicação sem aprender dezenas de serviços**. Em vez de montar à mão VPC, subnets, route tables, security groups, EBS, Elastic IP e Route 53, você escolhe uma **imagem pronta** (um *blueprint*, como WordPress ou Node.js), um **plano com preço mensal fixo** (CPU, memória, SSD e franquia de transferência já incluídos) e clica em criar. O restante é abstraído.

**Analogia:** se o EC2 é **alugar um galpão vazio e montar a infraestrutura você mesmo** (energia, água, divisórias, segurança), o Lightsail é **alugar uma sala comercial mobiliada**: preço fechado por mês, chave na mão, com menos liberdade de reforma, mas pronta para trabalhar no primeiro dia.

Por baixo, o Lightsail roda na mesma infraestrutura global da AWS (mesmas Regiões e AZs), mas expõe **uma API, um console e uma CLI próprios** (`aws lightsail ...`). Isso tem uma consequência importante: **os recursos do Lightsail não aparecem no console do EC2** e vivem em uma rede (VPC) separada e gerenciada pelo próprio Lightsail, que pode ser conectada à sua VPC padrão por *VPC peering* (veja a folha de integração).

## Para quem o Lightsail foi pensado

| Perfil | Por que o Lightsail ajuda |
|---|---|
| Desenvolvedor solo / freelancer | Sobe site ou API em minutos com preço previsível |
| Pequenas empresas e agências | WordPress, lojas e sites institucionais sem equipe de infra |
| Estudantes e laboratórios | Custo baixo e fixo para aprender Linux, Docker e redes |
| Provas de conceito (POC) | Ambientes descartáveis e baratos |
| Times que querem migrar depois | Começam simples e exportam para EC2 quando crescem |

Não é o serviço certo para cargas que exigem **Auto Scaling horizontal sofisticado, múltiplas camadas de rede, endpoints privados para dezenas de serviços, instâncias muito grandes ou conformidade complexa**. Para isso, EC2/ECS/EKS (veja [[8. DevOps e Gerenciamento de Infraestrutura/CLOUD COMPUTING/AWS (AMAZON WEB SERVICE)/3. Tecnologia e Serviços/3.3 Serviços principais da AWS/3.3.1. Computação/3.3.1.1. Amazon EC2/0 Amazon EC2 (Tópicos )|Amazon EC2]]) são os caminhos naturais.

## O que vem "no pacote"

O Lightsail agrupa, em um único serviço, peças que no resto da AWS são independentes:

```
 ┌───────────────────────────── Lightsail ─────────────────────────────┐
 │                                                                     │
 │  Instâncias (VPS)      Container services       Bancos gerenciados  │
 │  Discos (bloco)        Buckets (objeto)         IPs estáticos       │
 │  Load balancers        Distribuições CDN        Zonas DNS           │
 │  Certificados TLS      Snapshots / backups      Firewall por recurso│
 │                                                                     │
 └──────────────┬──────────────────────────────────────┬───────────────┘
                │ roda sobre a infraestrutura AWS      │ VPC peering (opcional)
                ▼                                      ▼
        Regiões e AZs da AWS                   VPC padrão da sua conta
        (EC2, RDS, S3 podem coexistir)         (acesso a RDS, ElastiCache...)
```

| Peça do Lightsail | Equivalente "grande" na AWS | Diferença prática |
|---|---|---|
| Instância | EC2 | Planos fixos; sem escolher família/tipo livremente |
| Disco | EBS | Anexa a instâncias da mesma AZ; até 16 TB por disco (referência) |
| Bucket | S3 | Planos de armazenamento + transferência incluídos |
| Banco gerenciado | RDS | MySQL/PostgreSQL com planos padrão ou de alta disponibilidade |
| Container service | ECS/Fargate (simplificado) | Define "power" e "scale"; sem cluster visível |
| Load balancer | ALB | Camada 7 com TLS e health check, preço fixo |
| Distribuição | CloudFront | CDN com pacote de transferência incluído |
| Zona DNS | Route 53 | Gerenciamento de registros do domínio |
| Firewall | Security Group | Regras por instância/serviço, simplificadas |

## Blueprints: a imagem pronta

Um **blueprint** é um *template* de instância. Há dois grandes grupos:

| Tipo | Exemplos | Quando escolher |
|---|---|---|
| **Somente SO** | Amazon Linux, Ubuntu, Debian, FreeBSD, openSUSE, Windows Server | Você instalará tudo; controle máximo |
| **Aplicações** | WordPress, LAMP, Node.js, MEAN, Django, Joomla, Drupal, Magento, Plesk, Ghost, GitLab | Quer o app funcionando assim que a instância subir |

Os blueprints de aplicação já trazem o stack configurado (por exemplo, Apache + PHP + MariaDB + WordPress), com credenciais iniciais geradas e acessíveis via SSH. Você obtém a lista atual com a CLI:

```bash
# Lista os blueprints disponíveis (id, nome, plataforma, tipo)
aws lightsail get-blueprints \
  --query 'blueprints[].[blueprintId,name,platform,type]' --output table

# Lista os bundles (planos): id, preço, vCPU, RAM, disco, transferência
aws lightsail get-bundles \
  --query 'bundles[].[bundleId,price,cpuCount,ramSizeInGb,diskSizeInGb,transferPerMonthInGb]' \
  --output table
```

## Planos (bundles): o preço fixo

Cada plano combina **vCPU, memória, SSD e franquia mensal de transferência** por um valor mensal fixo (cobrado proporcionalmente por hora, com teto mensal). Instâncias menores têm baixíssimo custo; planos maiores aumentam todos os recursos juntos.

| Dimensão | Como funciona (referência) |
|---|---|
| Preço | Mensal fixo, com cobrança por hora até o teto do mês |
| CPU | Instâncias de uso geral com **burst** (créditos de CPU) nos planos pequenos |
| Transferência | Franquia mensal incluída; excedente cobrado por GB |
| Armazenamento | SSD do plano; discos extras cobrados à parte |
| IP estático | Gratuito **enquanto anexado** a uma instância |
| Snapshots | Cobrados por GB-mês armazenado |

> [!tip] Vantagem de previsibilidade
> Em EC2 você soma instância + EBS + IP + transferência e a conta varia. No Lightsail a fatura base é **o preço do plano**, o que facilita orçamentos pequenos.

### Árvore de decisão: Lightsail ou EC2?

```
Preciso de um servidor/aplicação pequeno com custo previsível?
├─ Sim
│   ├─ Quero poucos conceitos, console simples, app pronta (WordPress...)? ─► LIGHTSAIL
│   ├─ Posso precisar de Auto Scaling, tipos de instância específicos, ALB avançado? ─► EC2
│   └─ Vou integrar com muitos serviços AWS (RDS, ElastiCache, VPC endpoints)? ─► EC2
│        (ou Lightsail + VPC peering, com limitações)
└─ Não (carga grande, crítica, regulada) ─► EC2 / ECS / EKS
```

| Critério | Lightsail | EC2 |
|---|---|---|
| Curva de aprendizado | Baixa | Média a alta |
| Modelo de preço | Plano fixo mensal | Por segundo + componentes |
| Escolha de hardware | Lista curta de planos | Centenas de tipos |
| Auto Scaling | Não nativo (escala via container service ou manual) | Sim |
| Redes avançadas | Simples (firewall + peering) | VPC completa |
| Integração com o ecossistema | Parcial | Total |
| Saída para crescer | Exportar snapshot para EC2 | — |

## Regiões e Zonas de Disponibilidade

O Lightsail está disponível em um subconjunto das Regiões AWS. Cada recurso é criado em uma **Região** e, no caso de instâncias, bancos e discos, em uma **AZ** específica. Isso importa para:

1. **Latência:** escolha a região mais próxima dos usuários.
2. **Discos:** só anexam a instâncias da **mesma AZ**.
3. **Resiliência:** um único servidor em uma AZ cai com a AZ; distribua em AZs e use load balancer e banco de alta disponibilidade quando precisar.
4. **Preços:** podem variar por região.

```
 Região (ex.: sa-east-1)
 ├─ AZ-a: Instância web-1 ── Disco dados-1
 ├─ AZ-b: Instância web-2 ── Disco dados-2
 └─ Load balancer (distribui entre web-1 e web-2)
     └─ Banco gerenciado de alta disponibilidade (standby em outra AZ)
```

## Primeira instância em quatro passos (visão do console)

1. **Escolher a localização** (Região e AZ).
2. **Escolher a imagem** (blueprint de SO ou de aplicação).
3. **Escolher o plano** (bundle) e, opcionalmente, ativar *snapshots automáticos*.
4. **Nomear e criar**; em instantes você recebe um IP público e pode conectar pelo **terminal no navegador** (SSH/RDP embutido) ou pelo seu cliente.

```bash
# Equivalente via CLI (valores ilustrativos)
aws lightsail create-instances \
  --instance-names web-1 \
  --availability-zone sa-east-1a \
  --blueprint-id wordpress \
  --bundle-id small_3_0 \
  --user-data "echo ola > /tmp/boot.txt"

# Consulta o estado e o IP
aws lightsail get-instance --instance-name web-1 \
  --query 'instance.[state.name,publicIpAddress]'
```

## Troubleshooting inicial

| Sintoma | Causa provável | Como resolver |
|---|---|---|
| Não consigo acessar o site na porta 80/443 | Firewall da instância sem regra | Abrir as portas no firewall do Lightsail |
| SSH recusa a chave | Chave padrão da região diferente da usada | Baixar a chave padrão ou usar o terminal no navegador |
| Instância "não aparece" no EC2 | Recursos do Lightsail ficam fora do console do EC2 | Procurar no console do Lightsail |
| Disco não anexa | AZ diferente da instância | Criar o disco na mesma AZ |
| Site lento sob carga | Plano pequeno com créditos de CPU esgotados | Subir de plano (via snapshot) ou usar CDN/cache |
| Conta maior que o esperado | Snapshots, IPs sem uso, transferência excedente | Revisar recursos, apagar sobras |

## Custo: como pensar

1. **Plano da instância** (fixo) — a maior parte da conta.
2. **Extras:** discos adicionais, snapshots, bancos, load balancers, CDN, buckets.
3. **Transferência excedente:** além da franquia, cobrada por GB.
4. **IPs estáticos não anexados:** podem gerar cobrança.

Exemplo de raciocínio: um site WordPress simples pode caber em um plano pequeno com IP estático e snapshot diário. Se o tráfego cresce, antes de trocar de plano considere uma **distribuição CDN** para aliviar a instância. Se a aplicação passa a exigir Auto Scaling e rede complexa, é hora de **migrar para EC2**.

## Exemplo prático: site institucional com baixo custo

```
 Usuários ──► Distribuição CDN (cache de imagens/CSS)
                   │
                   ▼
            Instância WordPress (plano pequeno)
                   │
          ┌────────┴─────────┐
          ▼                  ▼
   Snapshot diário     Bucket de mídia (opcional)
```

Passos: criar a instância com o blueprint WordPress, alocar e anexar um **IP estático**, apontar o domínio via **zona DNS** do Lightsail, ativar **snapshots automáticos**, restringir SSH ao seu IP no firewall e emitir um certificado TLS pelo balanceador ou pela distribuição.

## Erros comuns e armadilhas

- **Achar que Lightsail é EC2 "com outro nome":** não aparece no console do EC2 e tem API própria.
- **Deixar IPs estáticos sem anexar:** podem ser cobrados.
- **Esquecer firewall:** por padrão só algumas portas ficam abertas; abrir `0.0.0.0/0` para SSH é arriscado.
- **Ignorar snapshots:** sem backup, perder a instância é perder o site.
- **Usar um único servidor para algo crítico:** ele vive em uma AZ.
- **Dimensionar pelo menor plano e esquecer créditos de CPU:** carga constante esgota os créditos e a performance cai.
- **Esperar Auto Scaling nativo:** o Lightsail não escala instâncias sozinho.
- **Não planejar a saída:** saiba que dá para exportar snapshots para EC2 quando crescer.

## 🧩 Quiz de Fixação

1. Qual a principal diferença de modelo de preço entre Lightsail e EC2?
2. O que é um *blueprint* e quais os dois grandes tipos?
3. Por que um disco do Lightsail não anexa a uma instância?
4. Os recursos do Lightsail aparecem no console do EC2? O que isso implica?
5. Em que situação você deve migrar do Lightsail para o EC2?
6. Por que o IP estático merece atenção na conta?

**Respostas:**
1) O Lightsail cobra um **plano fixo mensal** que já inclui vCPU, memória, SSD e franquia de transferência; no EC2 a conta soma instância (por segundo), EBS, IP e transferência, e varia.
2) É a imagem pronta da instância: **somente SO** (Amazon Linux, Ubuntu, Windows etc.) ou **aplicação** (WordPress, LAMP, Node.js, Django etc.), já configurada.
3) Porque o disco só anexa a instâncias da **mesma AZ**; é preciso criar o disco na AZ da instância.
4) Não aparecem; o Lightsail tem console, API e CLI próprios e roda em uma rede separada. Para integrar com recursos do EC2/RDS é preciso **VPC peering**.
5) Quando surgirem necessidades de Auto Scaling, tipos de instância específicos, rede complexa, integração ampla com outros serviços ou conformidade que o Lightsail não cobre; a migração se faz exportando snapshots para EC2.
6) Ele é gratuito **enquanto anexado** a uma instância; um IP estático alocado e não usado pode gerar cobrança.
