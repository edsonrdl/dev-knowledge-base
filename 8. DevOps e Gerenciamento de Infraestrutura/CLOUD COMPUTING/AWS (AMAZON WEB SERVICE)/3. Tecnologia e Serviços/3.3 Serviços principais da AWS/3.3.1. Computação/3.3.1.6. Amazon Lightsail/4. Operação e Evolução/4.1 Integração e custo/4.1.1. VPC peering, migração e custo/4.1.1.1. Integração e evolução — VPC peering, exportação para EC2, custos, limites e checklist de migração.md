### Integração e evolução — VPC peering, exportação para EC2, custos, limites e checklist de migração

> [!warning] Aviso
> Regras de peering, formatos de exportação, limites e preços do Lightsail mudam. Os valores são referências de estudo; confirme na documentação. Os comandos **não foram executados**.

O Lightsail é ótimo para **começar**, mas projetos crescem. Esta folha trata das **três questões de maturidade**: (1) como o Lightsail **conversa com o resto da AWS** (VPC peering), (2) como **sair dele** quando o projeto exigir mais (exportar para EC2 e recriar serviços), e (3) como **controlar custos e limites** enquanto ele é a sua plataforma.

**Analogia:** o Lightsail é a **casa de aluguel mobiliada**; o VPC peering é a **passagem coberta** que liga essa casa ao condomínio vizinho (sua VPC com RDS, ElastiCache etc.); exportar para EC2 é **mudar para a casa própria**, levando os móveis (snapshots) para uma estrutura que você pode reformar à vontade.

## VPC peering: ligando o Lightsail à sua VPC

Os recursos do Lightsail vivem em uma **VPC gerenciada pelo Lightsail**, separada da VPC padrão da sua conta. O **VPC peering** cria uma conexão privada entre as duas, **por Região**, permitindo que instâncias do Lightsail acessem recursos privados da VPC (RDS, ElastiCache, instâncias EC2) usando **IPs privados**.

```
 VPC do Lightsail (região sa-east-1)          VPC padrão da sua conta (sa-east-1)
 ┌──────────────────────────┐   peering     ┌─────────────────────────────┐
 │ web-1  172.26.x.x        │◄─────────────►│ RDS / ElastiCache / EC2      │
 │ web-2                    │  rota privada │ 172.31.x.x (CIDR distinto)   │
 └──────────────────────────┘               └─────────────────────────────┘
```

| Aspecto | Detalhe |
|---|---|
| Escopo | Por Região; habilite em cada região usada |
| Alvo | Normalmente a VPC **padrão** da conta |
| CIDRs | Não podem se sobrepor |
| Roteamento | O peering adiciona o caminho entre as VPCs |
| Segurança | Regras de **Security Group** do lado AWS precisam permitir a origem do Lightsail |
| Transitividade | O peering **não é transitivo** |

```bash
# Habilita o peering com a VPC padrão na região do Lightsail
aws lightsail peer-vpc --region sa-east-1

# Confere o estado
aws lightsail is-vpc-peered --region sa-east-1

# Desfaz (se necessário)
aws lightsail unpeer-vpc --region sa-east-1
```

Depois do peering, é preciso: (1) **liberar no Security Group** do RDS a origem (CIDR da VPC do Lightsail) e a porta; (2) usar o **endpoint privado** do recurso; (3) validar com `nc`/`telnet` a partir da instância.

### Quando usar peering

```
Preciso de um recurso AWS que não existe no Lightsail (ElastiCache, Redshift, EFS...)?
├─ Sim ─► peering com a VPC padrão e crio o recurso lá
└─ Não ─► mantenha tudo dentro do Lightsail

Preciso de várias VPCs, Transit Gateway, endpoints PrivateLink?
└─ Provavelmente já é hora de migrar para EC2/VPC própria
```

## Exportar para o EC2

O Lightsail permite **exportar snapshots de instâncias e de discos para o Amazon EC2**, gerando **AMIs** e **snapshots do EBS** na sua conta. A partir daí você roda a mesma máquina como **instância EC2**, com acesso a tipos de instância, Auto Scaling, ALB, múltiplas redes e todo o ecossistema.

```
 Instância Lightsail
     │ 1. create-instance-snapshot
     ▼
 Snapshot Lightsail
     │ 2. export-snapshot  (gera AMI + snapshots EBS no EC2)
     ▼
 AMI no EC2 ──3. launch── Instância EC2 (tipo à sua escolha)
     │
     └─ 4. (opcional) CloudFormation stack gerada pelo Lightsail para lançar a instância
```

| Etapa | Cuidados |
|---|---|
| Snapshot | Faça com a aplicação em estado consistente |
| Exportação | Pode levar algum tempo; acompanhe o status |
| Lançamento | Escolha tipo, subnet, SG, IAM role no EC2 |
| DNS | Aponte para o novo IP/ALB e reduza TTL antes |
| Descomissionamento | Mantenha a origem por um período de segurança |

```bash
# 1. Snapshot da instância
aws lightsail create-instance-snapshot \
  --instance-name web-1 --instance-snapshot-name web-1-export

# 2. Exporta o snapshot para o EC2
aws lightsail export-snapshot --source-snapshot-name web-1-export

# 3. Acompanha
aws lightsail get-export-snapshot-records \
  --query 'exportSnapshotRecords[].[state,destinationInfo.id]'

# 4. Lança no EC2 a partir da AMI exportada (já no EC2)
aws ec2 run-instances --image-id <AMI_EXPORTADA> --instance-type t3.small \
  --subnet-id subnet-0123 --security-group-ids sg-0123
```

### O que não migra automaticamente

| Recurso | Como recriar no mundo "grande" |
|---|---|
| Load balancer do Lightsail | ALB/NLB |
| Distribuição CDN | CloudFront |
| Zona DNS | Route 53 |
| Banco gerenciado | RDS/Aurora (restaurar dump/snapshot lógico) |
| Bucket | S3 (copiar objetos) |
| Container service | ECS/Fargate ou EKS |
| Certificados | ACM |

Ou seja: a **exportação cobre instâncias e discos**; os demais serviços exigem **recriação e migração de dados**.

## Estratégia de migração em fases

```
Fase 0  Inventário         ─► listar instâncias, discos, bancos, buckets, DNS, certificados
Fase 1  Preparação         ─► VPC alvo, SGs, roles, ACM, Route 53 (zona), observabilidade
Fase 2  Dados              ─► banco: dump/restore ou DMS; bucket: sync para S3
Fase 3  Computação         ─► exportar snapshots → AMIs → EC2 (ou containers → ECS)
Fase 4  Teste paralelo     ─► validar com tráfego controlado (DNS ponderado)
Fase 5  Corte              ─► reduzir TTL, trocar DNS, monitorar
Fase 6  Descomissionar     ─► após período de segurança, remover recursos do Lightsail
```

| Tipo de recurso | Ferramenta de migração sugerida |
|---|---|
| Instâncias/discos | Exportar snapshot para EC2 |
| Banco MySQL/PostgreSQL | `mysqldump`/`pg_dump` + restore, ou AWS DMS |
| Objetos | `aws s3 sync` entre buckets |
| Containers | Reimplantar imagem em ECS/Fargate |
| DNS | Recriar registros no Route 53; troca de NS |

## Governança de custos no Lightsail

O custo base é previsível, mas **vazamentos** são comuns. Faça uma revisão mensal destes pontos:

| Fonte de custo | Como detectar | Ação |
|---|---|---|
| Instâncias paradas | Estado `stopped` | Excluir (após snapshot) se não usa |
| IPs estáticos soltos | `isAttached=false` | Liberar |
| Snapshots antigos | Lista de snapshots | Apagar obsoletos |
| Discos sem anexo | Disco `isAttached=false` | Snapshot e excluir |
| Transferência excedente | Métricas de rede e fatura | CDN, compressão, plano maior |
| Bancos de teste com HA | Plano HA em dev | Reduzir para Standard |
| Load balancers sem alvos | Sem instâncias anexadas | Excluir |

```bash
# IPs estáticos não anexados
aws lightsail get-static-ips \
  --query 'staticIps[?isAttached==`false`].[name,ipAddress]'

# Discos sem anexo
aws lightsail get-disks \
  --query 'disks[?isAttached==`false`].[name,sizeInGb]'

# Snapshots de instância (revisar antigos)
aws lightsail get-instance-snapshots \
  --query 'instanceSnapshots[].[name,createdAt,sizeInGb]'

# Instâncias paradas (continuam cobrando o plano)
aws lightsail get-instances \
  --query 'instances[?state.name==`stopped`].[name,bundleId]'
```

Use **AWS Budgets** e **Cost Explorer** para acompanhar o gasto total da conta, incluindo o Lightsail, e **tags** nos recursos para alocar custos por projeto.

## Limites e quotas

| Categoria | Ordem de grandeza | Observação |
|---|---|---|
| Instâncias | Dezenas por região | Aumento sob pedido |
| IPs estáticos | Dezenas | Libere os soltos |
| Discos, buckets | Dezenas | Verifique por região |
| Zonas DNS | Poucas | Route 53 para escalar |
| Load balancers/distribuições | Poucos | Aumento sob pedido |
| Peering | Uma VPC padrão por região | Não é transitivo |

## Checklist: Lightsail está sendo suficiente?

| Sinal | Se "sim", considere |
|---|---|
| Precisa de Auto Scaling horizontal | EC2/ECS com ASG |
| Precisa de instâncias com GPU, muita RAM ou rede avançada | EC2 |
| Precisa de muitos serviços AWS integrados por rede privada | EC2/VPC própria |
| Exige conformidade e logging detalhado por serviço | Arquitetura em VPC com CloudTrail/Config/Flow Logs |
| Equipe e tráfego cresceram, falta observabilidade | CloudWatch e stack própria |
| Precisa de políticas avançadas de DNS | Route 53 |
| Mais de ~dezenas de instâncias para gerenciar | Infraestrutura como código (CloudFormation/Terraform) |

Se **poucos** sinais se aplicam, mantenha-se no Lightsail: simplicidade e preço fixo são vantagens reais.

## Troubleshooting

| Sintoma | Causa provável | Como resolver |
|---|---|---|
| Instância do Lightsail não alcança o RDS | Peering ausente ou SG sem origem do Lightsail | `peer-vpc` e liberar o CIDR no Security Group |
| `peer-vpc` falha | CIDR sobreposto ou sem VPC padrão | Recriar VPC padrão/ajustar CIDRs |
| Exportação "travada" | Snapshot grande ou fila | Aguardar e acompanhar `get-export-snapshot-records` |
| AMI exportada não inicia | Drivers/configuração incompatíveis | Revisar console output; ajustar tipo e rede |
| Fatura subindo sem motivo | Recursos soltos (IPs, snapshots) | Rodar a revisão mensal |
| Mudança de DNS não propaga | TTL alto | Reduzir TTL antes do corte |

## Exemplo prático: do Lightsail ao EC2 com banco no RDS

1. Peering habilitado e SG do RDS aceitando o CIDR do Lightsail.
2. Crie o RDS e migre os dados com `mysqldump` (ou DMS) a partir do banco do Lightsail.
3. Exporte o snapshot da instância web e lance a AMI no EC2 em subnet privada atrás de um ALB.
4. Teste com DNS ponderado (10% → 50% → 100%).
5. Reduza TTL, corte o tráfego, monitore erros e latência.
6. Após uma semana estável, apague instância, IP estático, snapshots e o banco antigos.

---

## Erros comuns e armadilhas

- **Esperar que o peering seja transitivo.**
- **Esquecer o Security Group** do lado AWS ao habilitar peering.
- **CIDRs sobrepostos** entre as VPCs.
- **Achar que a exportação leva o load balancer, o banco e o DNS.**
- **Migrar sem reduzir o TTL** do DNS e sofrer com cache.
- **Apagar o ambiente antigo cedo demais.**
- **Deixar IPs, discos e snapshots órfãos** após a migração.
- **Migrar por impulso** quando o Lightsail ainda atendia bem.

## 🧩 Quiz de Fixação

1. Para que serve o VPC peering do Lightsail e qual seu escopo?
2. O que é necessário no lado da AWS, além do peering, para o RDS aceitar a instância do Lightsail?
3. O que a exportação de snapshot para o EC2 gera?
4. Que serviços não são migrados automaticamente pela exportação?
5. Como detectar custos "vazando" no Lightsail?
6. Cite dois sinais de que é hora de sair do Lightsail.

**Respostas:**
1) Liga a VPC gerenciada do Lightsail à VPC padrão da sua conta, por Região, para acessar recursos privados (RDS, ElastiCache, EC2) por IPs privados; não é transitivo.
2) Liberar no Security Group do RDS a origem (CIDR da VPC do Lightsail) e a porta do banco, além de usar o endpoint privado.
3) Gera uma AMI e snapshots do EBS no EC2, a partir dos quais se lança uma instância EC2.
4) Load balancer, CDN, DNS, banco gerenciado, buckets, container services e certificados; todos precisam ser recriados e os dados migrados.
5) Revisando IPs estáticos não anexados, discos sem anexo, snapshots antigos, instâncias paradas, bancos de teste com HA e load balancers sem alvos; apoiado por Budgets e Cost Explorer.
6) Por exemplo: necessidade de Auto Scaling, de tipos de instância específicos/GPU, de integração ampla com serviços AWS por rede privada, de DNS avançado ou de conformidade detalhada.
