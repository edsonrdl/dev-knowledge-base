### Container services do Lightsail — power e scale, deployments, imagens, endpoint público e quando usar

> [!warning] Aviso
> Tamanhos de *power*, número máximo de nós (*scale*), preços, limites de containers por deployment e regras de domínio personalizado mudam. Os números aqui são referências de estudo; confirme na documentação. Os comandos **não foram executados**.

Os **Container services** do Lightsail permitem **rodar containers Docker sem administrar servidores, clusters ou orquestradores**. Você descreve *quais imagens rodar*, *qual tamanho de máquina* e *quantas cópias*, e o Lightsail cuida de provisionar, distribuir, reiniciar e expor o serviço com um **endpoint HTTPS público**.

**Analogia:** é como contratar um **food truck pronto**: você escolhe o tamanho do caminhão (power), quantos caminhões estarão na rua (scale) e o cardápio (as imagens de container). Não precisa montar a cozinha (cluster), comprar o terreno (VPC) nem contratar a segurança (load balancer); o pacote já vem com tudo.

Comparado ao ECS/Fargate (veja [[8. DevOps e Gerenciamento de Infraestrutura/CLOUD COMPUTING/AWS (AMAZON WEB SERVICE)/3. Tecnologia e Serviços/3.3 Serviços principais da AWS/3.3.1. Computação/3.3.1.3. Amazon ECS/0 Amazon ECS (Tópicos )|Amazon ECS]]), é **muito mais simples e de preço fixo**, mas oferece menos controle e menos integrações.

## Os dois botões: power e scale

O dimensionamento é feito com **dois parâmetros**:

| Parâmetro | O que define | Efeito |
|---|---|---|
| **Power** | Tamanho de **cada nó** (vCPU e memória) | Capacidade de cada cópia do container |
| **Scale** | **Quantidade de nós** (cópias) | Capacidade total e disponibilidade |

A **capacidade total** é aproximadamente `power × scale`. O preço mensal é o preço do power multiplicado pelo scale.

```
 power = small   scale = 3
 ┌───────────┐ ┌───────────┐ ┌───────────┐
 │  nó 1     │ │  nó 2     │ │  nó 3     │   ← cada nó roda TODOS os
 │ (small)   │ │ (small)   │ │ (small)   │     containers do deployment
 └─────┬─────┘ └─────┬─────┘ └─────┬─────┘
       └─────────────┼─────────────┘
                     ▼
         Endpoint público HTTPS (balanceamento embutido)
```

| Situação | Ajuste |
|---|---|
| CPU/memória insuficiente em cada nó | Subir o **power** |
| Muitas requisições simultâneas | Subir o **scale** |
| Quer tolerância a falha | **scale ≥ 2** (nós em locais distintos) |
| Dev/teste | power e scale mínimos (nano, scale 1) |

> [!tip] Escala é manual
> O Lightsail **não faz Auto Scaling** automático de container service. Você muda o *scale* por console/CLI/API (e pode automatizar por script com base em alarmes).

## Deployment: o que roda

Um **deployment** é a descrição declarativa do que executa no serviço. Cada deployment contém:

1. **Containers** (um ou mais): imagem, comandos, variáveis de ambiente, portas.
2. **Public endpoint:** qual container e qual porta recebem o tráfego público e qual **health check** usar.

Um serviço guarda um **histórico de versões de deployment**, o que permite reverter para uma versão anterior.

```
 Deployment v7
 ├─ container "web"  imagem: meu-app:1.4   porta 80   env: APP_ENV=prod
 ├─ container "cache" imagem: redis:7       porta 6379 (acesso pelo localhost)
 └─ public endpoint → container "web", porta 80, health check "/health"
```

**Comunicação entre containers do mesmo deployment:** rodam no mesmo nó e conversam por `localhost`. Containers de **serviços diferentes** se comunicam por endpoint (público ou por rede privada, conforme suporte).

## De onde vêm as imagens

| Origem | Como usar | Observação |
|---|---|---|
| **Registro público** (Docker Hub, ECR Public) | Informar `nginx:latest` etc. | Simples; atenção a limites de pull |
| **Imagem enviada ao Lightsail** | `push-container-image` da imagem local | Armazenada no registro do serviço |
| **Amazon ECR privado** | Autorizando o serviço a puxar | Útil se já usa ECR |

```bash
# Envia uma imagem local para o container service "api" (rótulo "app")
aws lightsail push-container-image \
  --service-name api --label app --image meu-app:1.4

# A saída informa o nome referenciável, por exemplo:  :api.app.1
# Use esse nome no deployment.
```

> [!warning] Evite `latest`
> Tags mutáveis dificultam reprodutibilidade e rollback. Prefira **tags de versão** ou o nome imutável gerado no *push* (`:serviço.rótulo.N`).

## Criando serviço e deployment pela CLI

```bash
# 1. Cria o serviço: power micro, 2 nós
aws lightsail create-container-service \
  --service-name api --power micro --scale 2

# 2. Cria o deployment com 1 container e endpoint público
aws lightsail create-container-service-deployment --service-name api \
  --containers '{
    "web": {
      "image": ":api.app.1",
      "ports": {"80": "HTTP"},
      "environment": {"APP_ENV": "prod"}
    }
  }' \
  --public-endpoint '{
    "containerName": "web",
    "containerPort": 80,
    "healthCheck": {"path": "/health", "intervalSeconds": 10, "timeoutSeconds": 5,
                    "healthyThreshold": 2, "unhealthyThreshold": 2, "successCodes": "200-299"}
  }'

# 3. Acompanha o estado (PENDING, DEPLOYING, RUNNING, DISABLED...)
aws lightsail get-container-services --service-name api \
  --query 'containerServices[0].[state,url,power,scale]'

# 4. Vê logs de um container
aws lightsail get-container-log --service-name api --container-name web
```

O serviço recebe uma **URL pública com HTTPS** (domínio `*.amazonlightsail.com`). Para usar **domínio próprio**, associe um **certificado TLS** do Lightsail e crie o registro DNS apontando para o endpoint.

## Estratégia de deploy e rollback

| Situação | Comportamento |
|---|---|
| Novo deployment criado | O Lightsail sobe os novos containers e só direciona tráfego quando passam no health check |
| Health check falha | O deployment novo não assume o tráfego; o anterior continua ativo (conforme estado) |
| Rollback necessário | Criar novo deployment com a configuração/imagem da versão anterior |
| Mudança de imagem | Novo `push` gera novo identificador; atualize o deployment |

```
 v6 (RUNNING) ───────────────────────► recebe tráfego
 v7 criado ──► sobe ──► health check ──ok──► passa a receber tráfego, v6 sai
                           └─falha──► v7 FAILED, v6 continua
```

> [!tip] Sempre teste o `/health`
> Um health check que retorna 200 mesmo com dependência quebrada esconde falhas; um que depende de recurso instável derruba deploys. Equilibre.

## Container service vs instância vs ECS/Fargate

| Critério | Container service (Lightsail) | Instância (Lightsail) | ECS/Fargate |
|---|---|---|---|
| Gestão de SO | Nenhuma | Você (patches) | Nenhuma |
| Preço | Fixo (power × scale) | Fixo (plano) | Por vCPU/GB-hora |
| Auto Scaling | Manual | Não | Sim |
| Endpoint HTTPS | Embutido | Você configura | ALB |
| Orquestração | Simples | Docker manual | Completa |
| Integração AWS | Limitada | Peering | Total |
| Ideal para | Apps web pequenas em container | Monólitos/VPS | Microsserviços em escala |

### Árvore de decisão

```
Minha aplicação já é um container?
├─ Não, é app tradicional (WordPress, PHP) ─► Instância Lightsail
└─ Sim
    ├─ Poucos serviços, tráfego previsível, quero preço fixo? ─► Container service
    ├─ Preciso de Auto Scaling, service discovery, muitos serviços? ─► ECS/EKS
    └─ Preciso de GPU, rede privada complexa, conformidade? ─► ECS/EKS em EC2/Fargate
```

## Troubleshooting

| Sintoma | Causa provável | Como resolver |
|---|---|---|
| Estado `DEPLOYING` que não termina | Health check falhando | Conferir `path`, porta e logs do container |
| `503` no endpoint | Nenhum nó saudável | Ajustar health check; ver logs |
| Container reinicia em loop | Erro da aplicação ou falta de memória | Ver logs; subir o power |
| Imagem não encontrada | Nome do *push* ou da tag incorreto | Usar o nome retornado pelo `push-container-image` |
| Pull falha de registro público | Limite de pulls anônimos | Enviar a imagem ao Lightsail ou usar ECR |
| Domínio próprio sem HTTPS válido | Certificado não associado/validado | Validar o certificado e associar ao serviço |

## Custo

| Componente | Observação |
|---|---|
| Power × scale | Base da conta, fixa por mês |
| Transferência | Franquia incluída; excedente cobrado |
| Registro de imagens | Armazenamento limitado incluído |
| Certificado TLS | Sem custo no Lightsail |

**Exemplo de raciocínio:** dois nós `micro` têm o dobro do custo de um nó `micro`, mas oferecem tolerância a falha e deploy sem indisponibilidade. Se a carga cresce e você precisa de Auto Scaling, a migração para ECS/Fargate é o próximo degrau.

## Exemplo prático: API em container com deploy seguro

1. Construa a imagem: `docker build -t meu-app:1.4 .`
2. Crie o serviço `api` (power `micro`, scale 2).
3. Envie a imagem com `push-container-image` e anote o nome retornado.
4. Crie o deployment com endpoint público e health check em `/health`.
5. Valide a URL pública e os logs.
6. Para a versão 1.5: novo `push`, novo deployment, observe o health check; se falhar, recrie com a imagem 1.4.

## Erros comuns e armadilhas

- **Usar `latest`** e não conseguir reproduzir ou reverter.
- **scale = 1 em produção:** qualquer reinício causa indisponibilidade.
- **Health check inexistente ou frouxo.**
- **Guardar dados no filesystem do container:** é efêmero; use banco/bucket.
- **Segredos em variáveis em texto puro no repositório.**
- **Esperar Auto Scaling.**
- **Esquecer que cada nó roda todos os containers do deployment**, multiplicando o consumo.
- **Subir o power quando o gargalo é concorrência** (e vice-versa).

## 🧩 Quiz de Fixação

1. Qual a diferença entre *power* e *scale*?
2. O container service escala sozinho?
3. Como containers de um mesmo deployment se comunicam?
4. Por que evitar a tag `latest`?
5. O que acontece se o health check do novo deployment falhar?
6. Quando preferir ECS/Fargate ao container service?

**Respostas:**
1) *Power* define o tamanho (vCPU/memória) de cada nó; *scale* define quantos nós existem. Capacidade total ≈ power × scale.
2) Não. A escala é manual (console/CLI/API); é possível automatizar por script, mas não há Auto Scaling nativo.
3) Por `localhost`, pois rodam no mesmo nó.
4) Porque é mutável: dificulta reprodutibilidade e rollback; prefira tags de versão ou o identificador imutável gerado no push.
5) O novo deployment não assume o tráfego e o anterior continua ativo; é preciso corrigir e criar outro deployment.
6) Quando precisar de Auto Scaling, muitos serviços, service discovery, GPU, rede privada complexa ou integrações amplas com a AWS.
