### Instâncias do Lightsail — criação, bundles, IP estático, firewall, acesso SSH, snapshots e backups automáticos

> [!warning] Aviso
> Planos, preços, limites de regras de firewall, retenção de snapshots automáticos e comportamento de créditos de CPU mudam. Valores aqui são referências de estudo; confirme na documentação. Os comandos **não foram executados**.

A **instância do Lightsail** é o recurso central do serviço: um servidor virtual (VPS) com SO ou aplicação pré-instalada, IP público, firewall próprio e SSD incluído no plano. Esta folha cobre o ciclo de vida completo: **criar, acessar, proteger, fazer backup, escalar e descartar**.

**Analogia:** a instância é um **apartamento mobiliado**: você escolhe o tamanho (plano), recebe a chave (par de chaves SSH), a campainha tem endereço fixo se você contratar (IP estático), a portaria só deixa entrar quem estiver autorizado (firewall) e existe a opção de **fotografar o apartamento inteiro** (snapshot) para reconstruí-lo igual em outro lugar.

---

## Ciclo de vida de uma instância

```
 criar ──► pending ──► running ──► stopping ──► stopped ──► start ──► running
                          │                                              │
                          └──────────── reboot ◄─────────────────────────┘
                          │
                          └──► delete (irreversível; snapshots permanecem)
```

| Estado | O que acontece | Cobrança |
|---|---|---|
| `running` | Serviço ativo | Plano é cobrado |
| `stopped` | Desligada; disco preservado | **Plano continua sendo cobrado** (reserva de recursos) |
| `deleted` | Instância removida | Para de cobrar a instância; snapshots e IPs separados continuam |

> [!tip] Parar não é pausar a conta
> No Lightsail, **parar a instância não zera o custo** do plano. Para parar de pagar, é preciso **excluir** (depois de tirar um snapshot, se quiser recriar).

## Escolhendo o plano (bundle)

Os planos variam em vCPU, RAM, SSD e franquia de transferência. Há planos para Linux/Unix e para Windows (mais caros por causa da licença) e, em geral, também a opção de **IPv6 apenas** com preço menor.

| Sinal de que o plano é pequeno | Ação |
|---|---|
| `BurstCapacityPercentage` caindo a zero | Créditos de CPU esgotando: subir de plano |
| Memória em swap constante | Mais RAM |
| Disco acima de 80% | Subir de plano ou anexar disco extra |
| Transferência perto da franquia | CDN/cache ou plano maior |

**Como mudar de plano:** o Lightsail não redimensiona no lugar. O fluxo é **snapshot ➜ criar nova instância a partir do snapshot escolhendo um plano maior ➜ mover o IP estático ➜ remover a antiga**.

```
 Instância A (plano pequeno)
     │ 1. create-instance-snapshot
     ▼
 Snapshot ──2. create-instances-from-snapshot (bundle maior)──► Instância B
     │                                                              │
     └───── 3. detach IP estático de A e attach em B ───────────────┘
            4. testar e excluir A
```

## Acesso: SSH, terminal no navegador e Windows

| Método | Uso | Observação |
|---|---|---|
| Terminal no navegador | Acesso rápido pelo console | Não precisa baixar chave |
| SSH com chave padrão | Cliente local (OpenSSH, PuTTY) | Chave padrão por região; pode criar chaves próprias |
| RDP | Instâncias Windows | Senha obtida pelo console/CLI |
| Chave própria | Em produção | Importe sua chave pública |

```bash
# Obtém detalhes de acesso (IP, usuário) da instância
aws lightsail get-instance-access-details \
  --instance-name web-1 --protocol ssh

# Conecta (usuário depende do blueprint: ubuntu, ec2-user, bitnami...)
ssh -i ~/.ssh/LightsailDefaultKey-sa-east-1.pem ubuntu@<IP_PUBLICO>

# Baixa a chave padrão da região (guarde com permissão 600)
aws lightsail download-default-key-pair
```

**Boa prática:** use **chaves por pessoa**, restrinja a porta 22 ao seu IP e evite compartilhar a chave padrão.

## IP estático

O IP público dinâmico **muda** quando a instância é parada/iniciada. Para ter um endereço estável (necessário para DNS e certificados), aloque um **IP estático** e anexe à instância.

```bash
# Aloca e anexa um IP estático
aws lightsail allocate-static-ip --static-ip-name ip-web-1
aws lightsail attach-static-ip --static-ip-name ip-web-1 --instance-name web-1

# Confere
aws lightsail get-static-ip --static-ip-name ip-web-1 \
  --query 'staticIp.[ipAddress,isAttached,attachedTo]'
```

| Situação | Consequência |
|---|---|
| IP estático anexado | Sem custo adicional |
| IP estático alocado e não anexado | Pode gerar cobrança |
| Trocar de instância (resize) | Desanexar da antiga e anexar na nova |
| IP dinâmico com DNS apontando | Quebra ao reiniciar; evite |

## Firewall da instância

Cada instância tem seu **firewall** com regras de entrada por protocolo, porta/intervalo e origem (IPv4/IPv6). O padrão libera apenas o que o blueprint precisa (por exemplo, SSH e HTTP/HTTPS). **Regras são de entrada**; a saída é livre. É conceitualmente um Security Group simplificado.

| Regra | Origem recomendada | Observação |
|---|---|---|
| SSH (22) | Seu IP/32 | Nunca `0.0.0.0/0` em produção |
| HTTP (80) / HTTPS (443) | Qualquer | Se usar CDN/balanceador, restrinja à origem |
| Banco (3306/5432) | Somente IPs necessários | Preferir banco gerenciado privado |
| RDP (3389) | Seu IP/32 | Windows |
| Portas customizadas | Específicas | Documente |

```bash
# Define as portas abertas (substitui o conjunto atual)
aws lightsail put-instance-public-ports --instance-name web-1 \
  --port-infos \
    fromPort=22,toPort=22,protocol=tcp,cidrs=203.0.113.10/32 \
    fromPort=80,toPort=80,protocol=tcp \
    fromPort=443,toPort=443,protocol=tcp

# Lista o estado atual do firewall
aws lightsail get-instance-port-states --instance-name web-1
```

> [!warning] `put-instance-public-ports` substitui tudo
> Esse comando **troca o conjunto inteiro de regras**. Se omitir uma porta que estava aberta, ela será fechada. Use `open-instance-public-ports` para **adicionar** uma regra sem remover as demais.

## Snapshots e backups automáticos

Um **snapshot** é uma cópia pontual do disco do sistema (e, se for snapshot de disco, dos discos adicionais). Serve para **backup, clonagem, redimensionamento e migração para EC2**.

| Tipo | Como funciona | Quando usar |
|---|---|---|
| Snapshot manual | Você cria quando quiser; guarda até apagar | Antes de mudanças de risco |
| Snapshot automático (add-on) | Diário, em horário configurável; retém os últimos N (referência: 7) | Proteção contínua padrão |
| Snapshot de disco | Cópia de um disco de bloco | Dados em disco extra |
| Cópia entre regiões | Copia o snapshot para outra região | DR e migração |

```
  Instância ──snapshot manual──► Snapshot ──► criar nova instância (clone/resize)
      │                              │
      │ add-on autoSnapshot          ├─► copiar para outra região (DR)
      ▼ (diário)                     └─► exportar para EC2 (AMI)
  Snapshots automáticos (retenção limitada)
```

```bash
# Snapshot manual
aws lightsail create-instance-snapshot \
  --instance-name web-1 --instance-snapshot-name web-1-pre-upgrade

# Ativa snapshots automáticos diários às 03:00 UTC
aws lightsail enable-add-on --resource-name web-1 \
  --add-on-request addOnType=AutoSnapshot,autoSnapshotAddOnRequest={snapshotTimeOfDay=03:00}

# Cria nova instância (plano maior) a partir do snapshot
aws lightsail create-instances-from-snapshot \
  --instance-snapshot-name web-1-pre-upgrade \
  --instance-names web-1-v2 --availability-zone sa-east-1a --bundle-id medium_3_0
```

> [!tip] Snapshot automático não é arquivo de longo prazo
> A retenção dos automáticos é curta. Para guardar por semanas ou meses, **copie** para um snapshot manual e apague quando não precisar mais.

## Alertas e métricas

O Lightsail expõe métricas como `CPUUtilization`, `NetworkIn/Out`, `StatusCheckFailed` e `BurstCapacityPercentage`/`BurstCapacityTime`, e permite **alarmes** com notificação por e-mail/SMS.

```bash
# Alarme de CPU alta (> 80% por 3 períodos de 5 min)
aws lightsail put-alarm --alarm-name cpu-alta-web-1 \
  --metric-name CPUUtilization --monitored-resource-name web-1 \
  --comparison-operator GreaterThanThreshold --threshold 80 \
  --evaluation-periods 3 --datapoints-to-alarm 3 \
  --contact-protocols Email --notification-triggers ALARM

# Consulta uma métrica
aws lightsail get-instance-metric-data --instance-name web-1 \
  --metric-name CPUUtilization --period 300 --unit Percent --statistics Average \
  --start-time 2026-11-09T00:00:00Z --end-time 2026-11-09T06:00:00Z
```

## Árvore de decisão: o que fazer quando o servidor está lento

```
Instância lenta?
├─ CPU alta e BurstCapacity zerada ─► plano maior, ou cache/CDN
├─ CPU baixa, memória cheia ──────► plano com mais RAM; ajustar processos
├─ Disco cheio ───────────────────► limpar logs; anexar disco; plano maior
├─ Rede saturada / franquia estourada ─► CDN, compressão, plano maior
└─ Tudo ok, mas lento sob carga ──► 2+ instâncias atrás de load balancer
```

## Troubleshooting

| Sintoma | Causa provável | Como resolver |
|---|---|---|
| `Permission denied (publickey)` | Usuário ou chave erradas | Verificar usuário do blueprint e a chave da região |
| Site fora do ar após reboot | IP dinâmico mudou | Usar IP estático |
| Porta aberta no app, mas inacessível | Firewall do Lightsail fechado | Abrir a porta ou usar `open-instance-public-ports` |
| Todas as regras sumiram | Usou `put-instance-public-ports` incompleto | Reaplicar o conjunto completo |
| Snapshot não restaura no plano menor | Disco do snapshot maior que o do plano | Escolher plano com disco ≥ snapshot |
| `StatusCheckFailed` | Falha de SO/kernel/rede | Reiniciar; se persistir, recriar de snapshot |

## Custo

| Componente | Observação |
|---|---|
| Plano da instância | Fixo; cobrado mesmo parada |
| Snapshots | Por GB-mês; apague os antigos |
| IP estático solto | Pode ser cobrado |
| Transferência excedente | Por GB além da franquia |
| Discos extras | Por GB-mês |

**Estratégia:** use snapshot automático, mas apague snapshots manuais obsoletos; mantenha IPs estáticos apenas anexados; monitore a franquia de transferência com alarmes.

## Exemplo prático: servidor Node.js com SSH restrito e backup

1. Crie a instância `api-1` com blueprint **Node.js**, plano pequeno, em `sa-east-1a`.
2. Aloque e anexe o IP estático `ip-api-1`.
3. No firewall: SSH apenas do seu IP, HTTPS aberto; remova HTTP se usar só TLS.
4. Ative o **snapshot automático** às 03:00.
5. Crie um **alarme** de CPU e outro de `StatusCheckFailed`.
6. Antes de cada deploy relevante, gere um snapshot manual `api-1-pre-deploy`.

## Erros comuns e armadilhas

- **Achar que parar a instância zera o custo.**
- **Apontar o DNS para o IP dinâmico** e perder o site no próximo reboot.
- **Usar `put-instance-public-ports` para "adicionar"** e fechar portas sem querer.
- **Deixar o SSH aberto para o mundo.**
- **Confiar só nos snapshots automáticos** como arquivo de longo prazo.
- **Esquecer snapshots antigos**, que acumulam custo.
- **Redimensionar sem testar o snapshot** antes de apagar a original.
- **Compartilhar a chave padrão** entre pessoas, sem rastreabilidade.

## 🧩 Quiz de Fixação

1. Parar uma instância do Lightsail interrompe a cobrança do plano?
2. Como "aumentar o plano" de uma instância existente?
3. Qual a diferença entre `open-instance-public-ports` e `put-instance-public-ports`?
4. Por que usar IP estático em vez do IP dinâmico?
5. Para que serve o snapshot automático e qual sua limitação?
6. Que métrica indica esgotamento de créditos de CPU?

**Respostas:**
1) Não. A instância parada continua cobrando o plano; para parar a cobrança é preciso excluí-la (após snapshot, se quiser recriar).
2) Criando um snapshot, gerando uma nova instância a partir dele com um plano maior, movendo o IP estático e removendo a antiga.
3) `open-instance-public-ports` **adiciona** uma regra; `put-instance-public-ports` **substitui todo o conjunto**, fechando portas que não forem informadas.
4) O IP dinâmico muda ao parar/iniciar; o estático permanece e permite DNS e certificados estáveis (sem custo extra quando anexado).
5) Faz snapshots diários em horário definido, protegendo contra perda; a retenção é curta (poucos snapshots), então não serve como arquivo de longo prazo.
6) `BurstCapacityPercentage`/`BurstCapacityTime` caindo a zero indicam créditos de CPU esgotados.
