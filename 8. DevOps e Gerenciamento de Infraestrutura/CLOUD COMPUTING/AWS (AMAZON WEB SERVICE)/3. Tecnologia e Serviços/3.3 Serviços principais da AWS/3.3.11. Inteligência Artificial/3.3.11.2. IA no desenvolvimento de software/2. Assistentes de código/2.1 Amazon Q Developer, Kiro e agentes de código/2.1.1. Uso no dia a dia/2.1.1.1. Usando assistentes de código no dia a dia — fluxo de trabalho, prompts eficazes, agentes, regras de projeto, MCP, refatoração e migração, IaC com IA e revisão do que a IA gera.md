### 2.1.1.1. Usando assistentes de código no dia a dia — fluxo de trabalho, prompts eficazes, agentes, regras de projeto, MCP, refatoração e migração, IaC com IA e revisão do que a IA gera

> [!warning] Aviso
> Comandos, atalhos, nomes de recursos (por exemplo `/dev`, `/test`, steering, hooks), limites e comportamento de **Amazon Q Developer**, **Kiro** e outros assistentes mudam com frequência. Tudo abaixo é **de memória e não foi executado**. **Confirme na documentação da ferramenta que você usa.** Prompts e exemplos são ilustrativos; nomes de recursos e contas são fictícios.

## 1. Fluxo de trabalho recomendado

```
1. Entender o problema (você)           ← IA pode ajudar a explorar o código/serviço
2. Pedir um PLANO ao assistente          ← revisar/ajustar (escopo, arquivos, riscos)
3. Implementar em PASSOS PEQUENOS        ← diffs revisáveis, commits frequentes
4. Rodar TESTES/lint/tipos               ← evidência real (cole falhas de volta)
5. Revisar o diff com olhar crítico      ← segurança, edge cases, dependências
6. Documentar e abrir o PR               ← descrição gerada, validada por você
```

| Princípio | Prática |
|---|---|
| **Você dirige** | Defina **objetivo, restrições e critérios de aceite** |
| **Plano antes do código** | Peça um plano e **corrija antes** de gerar |
| **Pequenos incrementos** | Um comportamento por vez; **commit** a cada passo verde |
| **Testes como contrato** | Escreva/gere testes **antes** (ou junto) e **execute** |
| **Feedback com evidência** | Cole **erro real** (stack trace, saída do teste), não descrições vagas |
| **Reverter é barato** | Branch dedicado; **git** como rede de segurança |

## 2. Prompts eficazes: anatomia

| Parte | Exemplo |
|---|---|
| **Contexto** | “Lambda em Python 3.12, boto3, DynamoDB single-table, sem novas dependências.” |
| **Tarefa** | “Implementar `cancelar_pedido(pedido_id, usuario)`.” |
| **Regras** | “Só o dono pode cancelar; pedidos **ENVIADO** não podem; operação **idempotente**.” |
| **Formato** | “Retorne apenas o diff dos arquivos alterados.” |
| **Critérios** | “Testes cobrindo: sucesso, não encontrado, não autorizado, já cancelado.” |
| **Restrições** | “Não altere `utils/`; siga o padrão de `criar_pedido`.” |

Exemplos de prompts úteis:

```text
# Plano
Antes de escrever código, liste os arquivos que mudariam, o plano em passos e os riscos. Não implemente ainda.

# Explicar
Explique o fluxo de autenticação neste módulo, citando arquivos e funções. Aponte pontos frágeis.

# Teste primeiro
Escreva testes (pytest + moto) que falham para o bug descrito: <descrição>. Depois proponha a correção mínima.

# Revisão adversarial
Revise este diff como um revisor sênior de segurança. Liste problemas por severidade e sugira correções.

# Diagnóstico
Estes são o stack trace e o handler. Liste as 3 causas mais prováveis, como confirmar cada uma e a correção.
```

> [!tip] Peça justificativas e fontes
> “Qual a **documentação** que confirma esse parâmetro?” reduz alucinações; **valide no site oficial**.

## 3. Usando agentes (modo agêntico)

| Aspecto | Boa prática |
|---|---|
| **Escopo** | Tarefas **delimitadas** (uma funcionalidade/bug) |
| **Branch dedicado** | Isolar mudanças |
| **Aprovações** | Exigir **confirmação** para comandos/edições sensíveis; **negar** operações destrutivas |
| **Permissões** | **Mínimas** (diretório do projeto; sem credenciais de produção) |
| **Ambiente** | Rodar em **sandbox/conta de desenvolvimento** |
| **Critério de parada** | “Pare quando os testes X passarem” |
| **Observar** | Acompanhar comandos executados; interromper em loops |
| **Revisar o diff completo** | Inclusive arquivos “colaterais” |
| **Limitar iterações/custo** | Evitar loops caros |
| **Registrar** | Mensagens de commit descrevendo **o que e por quê** |

Sinais de que o agente se perdeu: **edita testes para passar** em vez de corrigir o código, **muda arquivos não relacionados**, **repete a mesma tentativa**, **instala dependências inesperadas**, **desativa verificações**. Interrompa, **reduza o escopo** e dê **critérios mais claros**.

## 4. Regras e contexto do projeto

Arquivos de instruções persistentes aumentam a consistência. Nomes variam por ferramenta (**steering** no Kiro; **regras/instruções do projeto** em outros — **confirmar**):

```markdown
# Contexto do projeto (exemplo de steering/regras)
## Stack
- Python 3.12, AWS SAM, DynamoDB (single-table), pytest + moto
## Convenções
- Handlers magros em `src/handlers/`; lógica em `src/servicos/`
- Logging estruturado (JSON) com `aws-lambda-powertools`
- Tipos obrigatórios (mypy), formatação ruff
## Comandos
- Testes: `pytest -q`    Lint: `ruff check .`    Build: `sam build`
## Segurança
- Nunca registrar PII; segredos só via Secrets Manager; IAM de menor privilégio
## Proibições
- Não adicionar dependências sem aprovação; não alterar `template.yaml` sem pedir
```

| Benefício | Detalhe |
|---|---|
| **Consistência** | Mesmos padrões em todas as sessões |
| **Menos repetição** | Não reexplicar a stack |
| **Segurança** | Regras sempre presentes |
| **Onboarding** | Serve também como documentação |

## 5. MCP e ferramentas externas

**MCP (Model Context Protocol)** permite que o assistente use **ferramentas e fontes de dados** (documentação da AWS, banco de dados, issue tracker, repositórios).

| Uso | Exemplo |
|---|---|
| **Documentação** | Servidor MCP com **docs AWS** atualizadas (reduz alucinação de APIs) |
| **IaC** | Servidor para **CDK/CloudFormation/Terraform** (validações, melhores práticas) |
| **Dados** | Consultas **somente leitura** a um banco de dev |
| **Operação** | Logs/métricas (CloudWatch) para diagnóstico |

| Cuidado | Motivo |
|---|---|
| **Servidores confiáveis** | Ferramentas maliciosas/descrições com **prompt injection** |
| **Menor privilégio** | Credenciais **somente leitura** e **conta de desenvolvimento** |
| **Aprovação por chamada** | Para ações com **efeito** |
| **Auditar o que o agente chamou** | Rastreabilidade |
| **Fixar versões** | Evitar mudança silenciosa |

## 6. Tarefas do dia a dia e como a IA ajuda

| Tarefa | Como usar | Verificação |
|---|---|---|
| **Entender código legado** | Pedir mapa de módulos, fluxo, dependências | Conferir lendo o código/rodando |
| **Escrever função** | Descrição + assinatura + exemplos | Testes |
| **Integração com SDK** | “Exemplo com `boto3` para listar objetos paginando” | **Doc oficial**, versão do SDK |
| **Regex/SQL/JQ** | Descrever entrada/saída | Casos de teste |
| **Converter** (JS → TS, callback → async) | Arquivo por arquivo | Testes + tipos |
| **Documentar** | Docstrings/README/ADR | Conferir precisão |
| **Mensagem de commit/PR** | A partir do diff | Ajustar ao que **realmente** mudou |
| **Depurar** | Stack trace + trecho | Reproduzir e confirmar |
| **Explicar custo/serviço AWS** | Pergunta no console/chat | **Calculadora de preços/doc** |
| **Comandos de CLI** | Linguagem natural → comando | **Ler antes de executar** (especialmente `delete`/`--force`) |

## 7. Refatoração e migração

| Cenário | Estratégia |
|---|---|
| **Refatoração mecânica** (renomear, extrair função) | Com **testes** verdes antes e depois; commits pequenos |
| **Migração de versão** (Python 3.9 → 3.12, SDK v2 → v3) | Pedir **plano**, depois **módulo a módulo**; rodar suíte; ler **changelogs** |
| **Transformação em larga escala** (Java 8/11 → 17/21) | Ferramentas especializadas (**Q Developer transformation**): revisar o **relatório** e os **diffs**; validar build/testes; **atenção a dependências** |
| **Modernização** (monólito → serverless) | **Arquitetura primeiro** (humano); IA para **trechos** |
| **Remoção de código morto** | Confirmar com **cobertura/uso real** |
| **Mudança de banco/ORM** | Alto risco: testes de **contrato/dados** |

Regra: **nunca refatore sem testes**; se não há, **gere testes de caracterização** (capturam o comportamento atual) **antes**.

## 8. IaC com IA (CloudFormation, SAM, CDK, Terraform)

| Boa prática | Detalhe |
|---|---|
| **Rascunho, não verdade** | IA gera **base**; você valida |
| **Menor privilégio** | **Rejeitar** `Action: "*"`/`Resource: "*"` sugeridos; refinar |
| **Validar** | `cfn-lint`, `cfn-guard`, `cdk synth`, `terraform validate/plan`, **Checkov/tfsec** |
| **Conferir propriedades** | Nomes/atributos **inventados** são comuns |
| **Segurança padrão** | Criptografia, **Block Public Access**, logs, TLS |
| **Parametrizar** | Sem **IDs/contas/segredos** fixos |
| **Revisar o `plan`/change set** | **Antes** de aplicar |
| **Ambiente de teste** | Aplicar em **conta de desenvolvimento** |
| **Drift e imports** | Cuidado com recursos existentes |

```text
Prompt: "Gere um template SAM com Lambda (Python 3.12) acionada por SQS, DLQ após 3 tentativas, 
role com permissões mínimas (sqs:ReceiveMessage/DeleteMessage/GetQueueAttributes só nessa fila),
log group com retenção de 14 dias e alarme para mensagens na DLQ. Não use curingas em IAM."
```

## 9. Revisando o que a IA gera (checklist)

| Item | Pergunta |
|---|---|
| **Corretude** | Faz o que foi pedido? Cobre **casos de borda** e erros? |
| **APIs reais** | Métodos/parâmetros **existem** na **versão** usada? |
| **Segurança** | Entrada validada? Sem **injeção**, **segredos**, **permissões amplas**? |
| **Dependências** | Existem, são **mantidas**, licença OK, **versão fixada**? |
| **Desempenho** | Complexidade, consultas **N+1**, **loops** em chamadas à AWS? |
| **Resiliência** | **Timeouts**, **retries**, **idempotência**, tratamento de falhas? |
| **Custos** | Chamadas desnecessárias, **logs verbosos**? |
| **Observabilidade** | Logs/métricas/traces adequados (sem PII)? |
| **Estilo/padrões** | Consistente com o projeto? |
| **Testes** | Verificam **comportamento** (não só espelham a implementação)? |
| **Licença** | Trecho **semelhante a código aberto**? |
| **Entendimento** | **Eu consigo explicar** este código? Se não, **não aceitar** |

## 10. Erros comuns

- **Pedir tudo de uma vez** (megadiffs impossíveis de revisar).
- **Não pedir plano**.
- **Aceitar testes gerados** sem executar/mutar.
- **Deixar o agente rodar comandos destrutivos** sem aprovação.
- **Credenciais reais/produção** acessíveis ao agente.
- **Não commitar em passos** (difícil reverter).
- **Corrigir testes em vez do código**.
- **Aceitar dependências novas** sem verificar.
- **IaC com permissões amplas** aceita por conveniência.
- **Executar comandos de CLI gerados sem ler**.
- **Conversas gigantes** (contexto confuso).
- **Sem regras de projeto** (resultados inconsistentes).

## 11. Troubleshooting

| Sintoma | Causa provável | Ação |
|---|---|---|
| Código não compila após a sugestão | Versões/APIs diferentes | Informar versões; colar erro completo |
| O assistente “esquece” regras | Contexto longo/sem steering | Regras persistentes; sessão nova com resumo |
| Agente altera arquivos demais | Escopo aberto | Limitar arquivos; pedir plano e aprovar |
| Testes quebram em cascata | Refatoração sem rede de segurança | Reverter; testes de caracterização; passos menores |
| Sugestões lentas/ausentes | Rede/autenticação/limite do plano | Reautenticar; ver status/limites |
| IaC não valida | Propriedades inventadas | `cfn-lint`/`validate` e corrigir pela doc |
| Resultado diferente a cada tentativa | Não determinismo | Especificar critérios/exemplos; testes |
| Comando de CLI perigoso sugerido | Falta de contexto | **Revisar** e usar `--dry-run` |

## 12. Resumo rápido

- **Fluxo**: entender → **plano** → **passos pequenos** → **testes** → **revisão** → PR; **você dirige**.
- **Prompts**: contexto + tarefa + regras + formato + critérios + restrições; **colar evidências reais**.
- **Agentes**: escopo curto, branch dedicado, **aprovações**, **permissões mínimas**, **sandbox**, atenção a sinais de loop.
- **Regras do projeto (steering)**: stack, convenções, comandos, segurança e proibições.
- **MCP**: documentação/ferramentas externas, com **servidores confiáveis** e **menor privilégio**.
- **Refatoração/migração**: **testes antes**, passos pequenos, ferramentas de transformação com **revisão**.
- **IaC com IA**: validar (`cfn-lint`, `cfn-guard`, `plan`), **sem curingas IAM**, testar em dev.
- **Revisar sempre**: corretude, APIs reais, segurança, dependências, resiliência, licenças e **entendimento**.

## 🧩 Quiz de Fixação

1. Por que pedir um plano antes da implementação?
2. Quais sinais indicam que um agente se perdeu?
3. O que são regras/steering de projeto?
4. Por que o MCP exige cuidado?
5. Como migrar código com segurança usando IA?
6. Que verificações aplicar em IaC gerado por IA?
7. Qual o teste final de aceitação de um trecho gerado?

**Respostas:**

1. Para revisar escopo, arquivos e riscos antes de gerar código, evitando mudanças grandes e erradas.
2. Alterar testes para passar, editar arquivos não relacionados, repetir tentativas, instalar dependências inesperadas ou desativar verificações.
3. Arquivos de contexto persistente com stack, convenções, comandos e restrições que orientam o assistente em todas as sessões.
4. Porque ferramentas externas podem ser maliciosas ou conter prompt injection e ter permissões excessivas; use servidores confiáveis, menor privilégio e aprovações.
5. Com testes verdes antes, plano, passos pequenos módulo a módulo, leitura de changelogs e revisão dos diffs e relatórios.
6. Validar com cfn-lint/cfn-guard/plan, rejeitar curingas IAM, checar propriedades inventadas, segurança padrão e testar em conta de desenvolvimento.
7. Se você consegue explicar o código, ele passa nos testes de comportamento e foi revisado quanto a segurança, dependências e licenças.
