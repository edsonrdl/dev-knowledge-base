### 3.1.1.1. IA em testes e CI-CD — geração de testes unitários, mutation testing, revisão automatizada de PR, análise de falhas de build, pipelines assistidos e limites de automação

> [!warning] Aviso
> Recursos de IA em ferramentas de CI/CD (Amazon Q Developer em PRs, CodeGuru Reviewer, GitHub Actions com agentes, CodeBuild) e a **disponibilidade desses produtos** mudam rápido. Tudo abaixo é **de memória e não foi executado**. **Confirme na documentação de cada ferramenta.** YAML, comandos e prompts são ilustrativos; contas, repositórios e ARNs são fictícios. Esta nota apoia as skills **3.2.5 (IA para testes)** e **3.3.9 (IA em CI/CD)** do DVA-C03.

## 1. Onde a IA ajuda no ciclo de qualidade

```
Código ─▶ Testes (geração/ampliação) ─▶ Revisão de PR (assistida) ─▶ CI (análise de falhas) ─▶ Deploy (portões) ─▶ Pós-deploy (smoke/alertas)
          IA gera casos                  IA aponta riscos             IA explica logs             regras DETERMINÍSTICAS     IA resume incidentes
```

| Etapa | O que a IA faz | O que **não** delegar |
|---|---|---|
| **Testes** | Rascunha casos, mocks, dados sintéticos | **Decidir** o comportamento correto |
| **Revisão** | Primeira passada: bugs, segurança, estilo | **Aprovação final** |
| **CI** | Explica falhas, sugere correção | **Alterar silenciosamente** o pipeline/testes |
| **Deploy** | Resumo de mudanças, notas de release | **Portões de qualidade/segurança** (determinísticos) |
| **Operação** | Triagem inicial de alertas | **Ações de produção** sem aprovação |

> [!tip] Princípio
> **IA sugere; a pipeline decide com regras determinísticas; humanos aprovam o que é crítico.**

## 2. Geração de testes com IA

### 2.1 Fluxo recomendado

```
1. Escolher a unidade (função/classe) e seu CONTRATO (entradas, saídas, erros)
2. Pedir à IA: casos felizes + bordas + erros + propriedades (com fixtures claras)
3. EXECUTAR os testes → corrigir falhas
4. Validar QUALIDADE: as asserções verificam comportamento? (mutation testing / revisão)
5. Remover testes redundantes/frágeis; versionar
```

```text
Prompt: "Para a função `calcular_frete(peso_kg, cep, expresso)`, escreva testes pytest parametrizados cobrindo:
limites de peso (0, 0.1, 30, 30.01), CEP inválido (levanta ValueError), expresso x padrão, e arredondamento
em 2 casas. Use apenas o comportamento documentado na docstring; não invente regras. Sem mocks de rede."
```

### 2.2 O que a IA gera bem e mal em testes

| Bem | Mal |
|---|---|
| **Boilerplate** de testes, parametrização | **Descobrir regras de negócio** que não estão no código/doc |
| **Casos de borda comuns** (vazio, nulo, limites) | **Casos de domínio** sutis |
| **Mocks/fixtures** para SDK (Moto/Stubber) | **Mocks que concordam com o código** (falso positivo) |
| **Dados sintéticos** | **Dados realistas** sem vazar PII |
| **Testes de caracterização** (legado) | **Testes de integração** corretos (IAM/eventos reais) |
| **Variações de entradas** | **Asserções significativas** (muitas vezes fracas) |

### 2.3 Armadilhas comuns de testes gerados

| Armadilha | Como detectar |
|---|---|
| **Teste espelho** (repete a implementação) | Mutation testing; revisão: “isto falharia se o código estivesse errado?” |
| **Asserção fraca** (`assert resultado is not None`) | Revisão; **mutation** |
| **Dependência de ordem/estado** | Rodar em **ordem aleatória**/isolado |
| **Flaky** (tempo, rede) | Rodar várias vezes; injetar relógio |
| **Mock excessivo** | Verificar se há **teste de integração** |
| **Cobertura inflada** | Cobertura **sem** asserções úteis |
| **Corrigir o teste para passar** | Revisar **diffs** de arquivos de teste |

### 2.4 Mutation testing: medindo a qualidade dos testes

**Mutation testing** altera o código (muta operadores/condições) e verifica se os **testes falham**. Mutantes que **sobrevivem** indicam **testes fracos**.

| Ferramenta (exemplos) | Linguagem |
|---|---|
| **mutmut / cosmic-ray** | Python |
| **Stryker** | JS/TS/.NET |
| **PIT (pitest)** | Java |

```bash
mutmut run --paths-to-mutate src/frete.py && mutmut results      # exemplo ilustrativo
```

| Uso | Detalhe |
|---|---|
| **Pós-geração** | Medir se testes de IA **detectam** defeitos |
| **Meta realista** | Mutation score **alto em lógica crítica** |
| **Custo** | Lento → rodar **noturno** ou em **módulos críticos** |

### 2.5 Dados de teste e privacidade

- Peça **dados sintéticos**, nunca cole **dados reais** no prompt.
- Gere **fixtures** com seeds fixas (Faker) e **anonimizadas**.
- **Não** inclua segredos/tokens em exemplos.

## 3. Revisão automatizada de código e PRs

| Recurso | Descrição |
|---|---|
| **Revisão com IA** (Amazon Q Developer `/review`, integrações com GitHub/GitLab, Copilot review etc.) | Comenta **bugs, vulnerabilidades, smells, desempenho** |
| **CodeGuru Reviewer** (ML) | Revisão automática de **Java/Python** com foco em defeitos de **uso de AWS SDK**, **concorrência** e **segurança** — **verificar disponibilidade/descontinuação atual** |
| **SAST** (CodeQL, Semgrep, SonarQube, Bandit) | Análise **estática determinística** |
| **SCA** (Dependabot, Snyk, `npm audit`, `pip-audit`) | **Dependências vulneráveis** |
| **Secret scanning** (git-secrets, gitleaks, GitHub) | **Segredos** em commits |
| **IaC scanning** (cfn-guard, Checkov, cfn-nag) | **Configurações inseguras** |

### 3.1 Como combinar IA e análise determinística

| Camada | Natureza | Papel |
|---|---|---|
| **SAST/SCA/secrets/IaC** | **Determinística** (regras) | **Portão** obrigatório (bloqueia merge) |
| **Revisão por IA** | **Probabilística** | **Consultiva**: ajuda o revisor humano; **não** bloqueia sozinha |
| **Revisão humana** | Julgamento | **Aprovação** |

| Boa prática | Detalhe |
|---|---|
| **Revisão de IA como “primeira passada”** | Humano revisa **o que importa** |
| **Tratar falsos positivos** | Marcar/ignorar com **justificativa** |
| **Não confiar na ausência de comentários** | “Sem achados” ≠ “sem defeitos” |
| **Prompt com contexto** | Padrões do projeto, ameaças relevantes |
| **PRs pequenos** | Melhor qualidade de revisão (humana e IA) |
| **Registrar decisões** | Por que aceitar/rejeitar sugestões |

## 4. IA na análise de falhas de CI

| Situação | Como a IA ajuda | Cuidado |
|---|---|---|
| **Build quebrou** | Resume o **log** (causa provável, trecho relevante) | Confirmar com o log completo |
| **Teste falhou** | Relaciona **diff × falha**, sugere correção | **Não** alterar o teste só para passar |
| **Dependência quebrou** | Aponta versão/changelog | Verificar **fonte** |
| **Pipeline lenta** | Sugere **cache/paralelização** | Medir antes/depois |
| **Flaky** | Sugere padrões (tempo, ordem, rede) | Reproduzir |
| **Erros de permissão (AccessDenied)** | Sugere a **ação IAM** faltante | **Menor privilégio** (não `*`) |

```yaml
# Exemplo (GitHub Actions): resumo de falha por IA como comentário CONSULTIVO (esboço de ideia)
- name: Coletar últimas 200 linhas do log
  if: failure()
  run: tail -n 200 build.log > falha.txt
- name: Pedir análise (ferramenta interna/Bedrock) e comentar no PR
  if: failure()
  run: python scripts/analisar_falha.py falha.txt   # chama Bedrock; NÃO envia segredos; saída apenas informativa
```

> [!warning] Cuidado com segredos em logs
> Logs de CI podem conter **tokens/URLs assinadas/PII**. **Mascare** antes de enviar a qualquer modelo (e **nunca** envie a serviços não aprovados).

## 5. Pipelines assistidos por IA

| Uso | Exemplo | Cuidado |
|---|---|---|
| **Gerar rascunho de pipeline** | `buildspec.yml`, workflow do GitHub Actions, `appspec` | **Revisar permissões**, versões de ações, segredos |
| **Gerar IaC do pipeline** | CDK Pipelines/CloudFormation | `cfn-lint/guard`, menor privilégio |
| **Notas de release/changelog** | A partir de commits/PRs | **Validar** precisão |
| **Descrição de PR** | A partir do diff | Ajustar ao que mudou |
| **Triagem de issues/alertas** | Classificar e roteirizar | Humanos decidem prioridade |
| **Geração de runbooks** | Passos de rollback/diagnóstico | **Testar** em simulação |
| **Agentes que corrigem falhas** (auto-fix) | Abrem **PR** com correção | **Nunca** fazer merge/deploy automático sem portões |

### 5.1 Arquitetura segura para “IA no pipeline”

```
Evento (PR/falha) ─▶ Job de análise (permissão SOMENTE LEITURA)
                       ├─ coleta contexto mascarado (diff, logs)
                       ├─ chama modelo (Bedrock/Q) com guardrails
                       └─ publica COMENTÁRIO ou abre PR de sugestão
Portões determinísticos (testes, SAST, SCA, IaC, aprovação) ─▶ merge ─▶ deploy
```

| Controle | Detalhe |
|---|---|
| **Permissão mínima** | O job de IA **lê** e **comenta**; **não** faz deploy |
| **Isolamento** | Executar em **runner/conta** sem acesso a produção |
| **PRs de forks** | **Não** expor segredos/roles |
| **Saída não confiável** | **Não executar** comandos/scripts vindos do modelo sem revisão |
| **Prompt injection** | Conteúdo de PR/issue/log pode conter **instruções maliciosas** → **isolar**, usar guardrails, **sem ferramentas poderosas** |
| **Auditoria** | Registrar **o que foi enviado e o que foi sugerido** |
| **Custos** | Limitar **tokens**/frequência |
| **Dados** | **Mascarar** PII/segredos antes de enviar |

## 6. Portões de qualidade (continuam determinísticos)

| Portão | Exemplo |
|---|---|
| **Testes** | Unitários/integração verdes |
| **Cobertura/mutation** | Mínimos em **código crítico** |
| **SAST/SCA/segredos/IaC** | **Sem** achados críticos |
| **Revisão humana obrigatória** | Proteção de branch (**CODEOWNERS**) |
| **Smoke pós-deploy + alarmes** | **Rollback automático** (CodeDeploy) |
| **Aprovação manual** | Para produção |

> A IA **melhora a produtividade ao redor** dos portões, mas **não os substitui**.

## 7. Medindo o valor (e os riscos)

| Métrica | Observação |
|---|---|
| **Tempo de PR até merge** | Pode cair com revisão assistida |
| **Taxa de defeitos escapados** | **Não** deve aumentar |
| **Mutation score / cobertura efetiva** | Qualidade dos testes gerados |
| **Taxa de aceitação de sugestões** | Indicador de utilidade (não de qualidade) |
| **Retrabalho/reversões** | Sinal de problemas |
| **Vulnerabilidades introduzidas** | SAST/SCA antes/depois |
| **Custo** por PR (tokens/licenças) | Controle |
| **Satisfação dos devs** | Adoção sustentável |

## 8. Erros comuns

- **Aceitar testes gerados sem executar/mutar**.
- **Tratar revisão de IA como aprovação**.
- **Auto-merge/deploy** disparado por IA.
- **Enviar logs com segredos/PII** a modelos.
- **Dar ao job de IA credenciais de deploy**.
- **PRs de forks** com acesso a segredos.
- **Prompt injection via PR/issue** ignorada.
- **Alterar testes para “passar”**.
- **Pipeline gerado com permissões amplas**.
- **Sem métricas** (adoção “por fé”).
- **Substituir SAST/SCA por IA**.

## 9. Troubleshooting

| Sintoma | Causa provável | Ação |
|---|---|---|
| Testes gerados passam mesmo com bug | Asserções fracas/espelho | Mutation testing; reforçar asserções |
| Muitos comentários irrelevantes de IA | Falta de contexto/PRs grandes | Regras do projeto; PRs menores; filtrar severidade |
| Falsos positivos de segurança | Heurísticas | Triagem; supressão justificada; SAST determinístico |
| Pipeline “consertada” por IA quebra segurança | Permissões/ações novas | Revisar diff do pipeline; **CODEOWNERS** em `.github/`/`buildspec` |
| Segredo vazou em prompt | Log não mascarado | **Rotacionar**; mascarar; revisar integrações |
| Custo de tokens alto | Logs enormes/muitas execuções | Truncar/filtrar; limitar frequência |
| IA sugere ação IAM ampla | Falta de menor privilégio | Restringir; Access Analyzer |
| Flaky após testes gerados | Dependência de tempo/ordem | Isolar; relógio injetado |

## 10. Resumo rápido

- **Geração de testes**: ótima para **boilerplate/bordas**; valide com **execução** e **mutation testing**; evite **testes espelho** e **mocks que concordam com o código**.
- **Revisão com IA**: **consultiva** (primeira passada); **SAST/SCA/segredos/IaC** permanecem **portões determinísticos**; **humano aprova**.
- **Falhas de CI**: IA resume logs e sugere correções — **mascarar segredos**, **não alterar testes para passar**, **menor privilégio IAM**.
- **Pipelines assistidos**: rascunhos e notas úteis; **jobs de IA somente leitura**, sem acesso a produção, **sem auto-merge/deploy**.
- **Riscos**: prompt injection em PR/logs, vazamento de dados, permissões amplas, falsa sensação de segurança.
- **Medir**: tempo de PR, defeitos escapados, mutation score, custo, retrabalho.

## 🧩 Quiz de Fixação

1. Por que mutation testing é útil com testes gerados por IA?
2. A revisão por IA deve bloquear o merge sozinha?
3. O que são portões determinísticos?
4. Que cuidados ter ao enviar logs de CI a um modelo?
5. Por que o job de IA deve ter permissão somente leitura?
6. O que é teste espelho?
7. Que risco existe em PRs de forks com agentes de IA?

**Respostas:**

1. Mede se os testes detectam alterações no código, revelando testes fracos ou espelho.
2. Não; é consultiva. Os bloqueios devem vir de regras determinísticas (testes, SAST, SCA, IaC) e de aprovação humana.
3. Verificações baseadas em regras (testes, análise estática, scanners, aprovação) que bloqueiam deploy de forma previsível.
4. Mascarar segredos/PII/URLs assinadas, usar serviços aprovados e limitar o volume de dados.
5. Para limitar o dano em caso de prompt injection ou erro, impedindo alterações e deploys indevidos.
6. Teste que repete a implementação e passa mesmo se o código estiver errado.
7. Código não confiável pode acessar segredos/roles ou injetar prompts; deve-se isolar e não expor credenciais.
