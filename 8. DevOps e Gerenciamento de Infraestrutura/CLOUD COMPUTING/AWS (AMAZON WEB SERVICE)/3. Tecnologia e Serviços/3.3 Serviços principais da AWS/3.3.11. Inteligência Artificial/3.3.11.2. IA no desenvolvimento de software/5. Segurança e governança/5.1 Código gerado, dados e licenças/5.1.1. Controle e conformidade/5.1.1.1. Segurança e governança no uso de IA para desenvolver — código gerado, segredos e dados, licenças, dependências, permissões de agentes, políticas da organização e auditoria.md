### 5.1.1.1. Segurança e governança no uso de IA para desenvolver — código gerado, segredos e dados, licenças, dependências, permissões de agentes, políticas da organização e auditoria

> [!warning] Aviso
> Termos de serviço, políticas de retenção/treinamento de dados, recursos de administração (Q Developer Pro, Kiro, Copilot etc.), requisitos legais (LGPD, direitos autorais, regulações de IA) e riscos emergentes mudam **rápido**. Tudo abaixo é **de memória, não é aconselhamento jurídico e não foi executado**. **Confirme nos termos oficiais da ferramenta e com o jurídico/segurança da sua organização.** JSON e exemplos são ilustrativos; contas e ARNs são fictícios. Esta nota apoia as skills **2.3.1 a 2.3.4 do DVA-C03** no contexto de **ferramentas de IA para desenvolvedores**.

## 1. Mapa de riscos

| Risco | Descrição | Exemplo |
|---|---|---|
| **Código inseguro gerado** | Padrões vulneráveis (injeção, validação fraca, criptografia inadequada) | `eval` de entrada do usuário; SQL concatenado |
| **Segredos e dados sensíveis** | Colados em prompts/contexto ou **gerados no código** | Chave AWS no snippet enviado ao assistente |
| **Vazamento de código proprietário** | Código vai para **serviço externo** | Ferramenta não aprovada |
| **Licenças e direitos autorais** | Trechos **semelhantes a código sob licença** | Copyleft em produto proprietário |
| **Dependências inexistentes/maliciosas** | IA sugere pacotes **inventados** ou typosquatting | `pip install` de pacote falso |
| **Permissões excessivas (agentes)** | Agente executa comandos/edita arquivos com poder demais | `rm -rf`, `aws s3 rm --recursive` |
| **Prompt injection** | Instruções ocultas em arquivos/issues/páginas | README malicioso instrui o agente |
| **IaC permissiva** | Políticas IAM amplas, buckets públicos | `Principal: "*"` |
| **Alucinações com impacto** | API/flag inexistente, **comando destrutivo** | CLI com `--force` |
| **Dependência excessiva** | Perda de **compreensão** e habilidades | Código que ninguém explica |
| **Conformidade** | Dados regulados em ferramentas inadequadas | PII/PHI/PCI em prompts |
| **Cadeia de suprimentos (MCP/extensões)** | Servidores/extensões **maliciosos** | Ferramenta que exfiltra dados |

## 2. Código gerado: segurança como em qualquer código

> **Código gerado por IA = código de terceiros não revisado.** Aplique **os mesmos controles** (ou mais).

| Controle | Detalhe |
|---|---|
| **Revisão humana obrigatória** | PR com **CODEOWNERS**; sem **auto-merge** de código gerado |
| **SAST** | CodeQL, Semgrep, SonarQube, Bandit, **Amazon Q security scan**, CodeGuru Security (**confirmar**) |
| **SCA** | **Dependabot**, `npm audit`, `pip-audit`, Snyk, OWASP Dependency-Check |
| **Secret scanning** | git-secrets, gitleaks, **GitHub push protection**, hooks `pre-commit` |
| **IaC scanning** | cfn-guard, cfn-nag, Checkov, tfsec |
| **DAST/testes de segurança** | Em staging |
| **Testes de segurança dirigidos** | Entradas maliciosas, autorização, limites |
| **Políticas de CI** | **Bloquear** merge com achados críticos (determinístico) |
| **Padrões seguros no contexto** | **Regras/steering** com requisitos (validação, criptografia, logs sem PII) |
| **Bibliotecas auditadas** | Para **criptografia/autenticação** — **não** reinventar |

### 2.1 Vulnerabilidades típicas em código gerado (e correção)

| Padrão inseguro | Correção |
|---|---|
| **SQL por concatenação** | Consultas **parametrizadas** |
| **`eval/exec`/`shell=True`** com entrada | Evitar; **allowlist**/APIs seguras |
| **Desserialização insegura** (`pickle`, YAML `load`) | Formatos seguros (JSON, `safe_load`) |
| **Validação ausente** | Schemas (pydantic/JSON Schema), limites |
| **CORS `*`/autenticação ausente** | Origens específicas; **authorizers** |
| **Segredos no código** | **Secrets Manager/SSM**, variáveis de ambiente |
| **Hash fraco** (MD5/SHA1 para senhas) | **Argon2/bcrypt/scrypt** |
| **TLS desabilitado** (`verify=False`) | Manter verificação |
| **Logs com PII/tokens** | Mascarar |
| **IAM `*`** | Menor privilégio |
| **SSRF/path traversal** | Validar URLs/caminhos |
| **Uploads sem validação** | Tipo/tamanho/quarentena |

## 3. Segredos e dados nos prompts

| Regra | Prática |
|---|---|
| **Nunca colar segredos** (chaves, tokens, senhas, strings de conexão) | **Rotacionar** se vazar |
| **Mascarar PII/PHI/PCI** | Dados **sintéticos** em exemplos |
| **Arquivos de ambiente** | `.env`, credenciais (`~/.aws/credentials`) **fora do contexto** do assistente; **ignore files** (`.gitignore`/arquivo de exclusão da ferramenta) |
| **Logs e dumps** | Mascarar antes de enviar |
| **Ferramentas aprovadas** | Só **ferramentas e planos aprovados** pela organização (termos de dados) |
| **Contas corporativas** | Evitar **contas pessoais** para código da empresa |
| **Contexto automático** | Saber **o que** o assistente envia (arquivos abertos, repositório) |
| **Treinamento** | Entender se **seus dados treinam modelos** (planos gratuitos × pagos variam — **confirmar**) |
| **Retenção** | Prazo de armazenamento de prompts/respostas |
| **Região/residência** | Onde os dados são processados |
| **Detecção de vazamento** | Scanners no repositório e **DLP** |

```gitignore
# Exemplo: manter segredos fora do repositório (e do contexto do assistente)
.env
*.pem
.aws/
terraform.tfstate*
secrets/
```

> [!warning] Se um segredo foi enviado a um modelo
> Trate como **vazado**: **revogue e rotacione**, **verifique logs de uso** (CloudTrail/Access Advisor) e **remova** do histórico/commits.

## 4. Licenças e propriedade intelectual

| Tema | Orientação (não é aconselhamento jurídico) |
|---|---|
| **Sugestões semelhantes a código aberto** | Use **filtros/referência de licença** da ferramenta quando houver (ex.: sinalização do Q Developer — **confirmar**) |
| **Licenças copyleft** (GPL/AGPL) | Podem **impor obrigações** ao seu produto |
| **Dependências sugeridas** | Verificar **licença** (SCA/licenças) |
| **Propriedade do código gerado** | Depende de **termos** e **legislação**; consultar **jurídico** |
| **Código de terceiros colado no prompt** | Pode violar **licença/NDA** |
| **Política interna** | Definir **o que pode** ser enviado e **como** registrar origem |
| **Auditoria de licenças** | Ferramentas (FOSSA, Snyk, `license-checker`) no CI |
| **Proveniência** | Registrar **uso de IA** em commits/PRs quando exigido |

## 5. Dependências: slopsquatting e cadeia de suprimentos

| Risco | Mitigação |
|---|---|
| **Pacote inexistente sugerido** (“alucinado”) e depois **registrado por atacante** | **Verificar** se existe, **reputação**, downloads, mantenedores, **repositório** |
| **Typosquatting** | Conferir **nome exato**; usar **lockfiles** e **registries privados** |
| **Versões vulneráveis** | SCA; **fixar versões**; atualizar com testes |
| **Scripts de instalação maliciosos** | `--ignore-scripts` quando aplicável; revisão; sandbox |
| **Dependências demais** | Preferir **biblioteca padrão** |
| **Proveniência/SBOM** | Gerar **SBOM** (CycloneDX/SPDX); **assinaturas** (sigstore) |
| **Registry interno (CodeArtifact)** | **Upstream** controlado; bloquear pacotes **não aprovados** |
| **Aprovação** | Política: **novas dependências** exigem revisão |

## 6. Permissões de agentes e ambientes de execução

| Controle | Detalhe |
|---|---|
| **Menor privilégio** | Diretório do projeto apenas; **sem** acesso a `~`, credenciais, produção |
| **Credenciais** | **Contas de desenvolvimento**; **roles temporárias** com **permission boundary**; **sem chaves de longo prazo** |
| **Aprovação de comandos** | **Exigir** para comandos **destrutivos/de rede/instalação**; **negar** `rm -rf`, `aws … delete/--force`, `git push --force`, `terraform apply` em prod |
| **Allowlist de comandos** | Permitir `pytest`, `ruff`, `sam build`; **bloquear** o resto |
| **Sandbox/container/devcontainer** | Isolar o agente; **rede restrita** |
| **Branch protegido** | Agente **não** faz push em `main`; **PR** obrigatório |
| **Limites** | **Passos, tempo, tokens/custo** |
| **Auditoria** | **Logs** de comandos e edições; **diffs** revisáveis |
| **Prompt injection** | **Não confiar** em instruções vindas de **arquivos/issues/páginas** lidos pelo agente; **isolar** |
| **MCP/extensões** | **Somente servidores confiáveis**, **versões fixas**, **menor privilégio** |
| **Produção** | **Nunca** conceder ao agente acesso direto a **produção** |

```json
{
  "Sid": "RoleDoAgenteSoDev",
  "Effect": "Allow",
  "Action": ["s3:GetObject", "s3:PutObject", "dynamodb:GetItem", "dynamodb:PutItem", "dynamodb:Query", "logs:GetLogEvents"],
  "Resource": ["arn:aws:s3:::meu-app-dev/*", "arn:aws:dynamodb:us-east-1:111111111111:table/pedidos-dev", "arn:aws:logs:us-east-1:111111111111:log-group:/aws/lambda/pedidos-dev:*"]
}
```

## 7. Governança organizacional

| Elemento | Conteúdo |
|---|---|
| **Política de uso de IA** | Ferramentas **aprovadas**, casos permitidos/proibidos, **classificação de dados** |
| **Gestão de contas/planos** | **SSO** (IAM Identity Center), **licenças corporativas**, **configuração central** |
| **Controles administrativos** | **Desativar** compartilhamento/telemetria quando necessário; **filtros de licença**; **personalização** com repositórios internos (**confirmar recursos**) |
| **Treinamento** | Boas práticas de **prompts, revisão e segurança** |
| **Revisão de código** | **Obrigatória**, **sem exceção** para código gerado |
| **Rastreabilidade** | Convenção para **marcar** PRs com **assistência de IA** (quando exigido) |
| **Gestão de risco** | **Avaliação** por projeto (criticidade, dados, regulação) |
| **Aprovação de novas ferramentas** | **Processo** de segurança/jurídico/privacidade |
| **Monitoramento de uso** | Adoção, **custos**, incidentes |
| **Resposta a incidentes** | Vazamento por prompt, dependência maliciosa, **comando destrutivo** |
| **Frameworks** | **OWASP LLM Top 10**, **NIST AI RMF/SSDF**, **ISO/IEC 42001**, **SLSA** — **confirmar** requisitos aplicáveis |

### 7.1 Classificação de dados × ferramenta

| Dado | Pode usar assistente externo? |
|---|---|
| **Código aberto/público** | Geralmente **sim** |
| **Código proprietário interno** | **Apenas ferramentas aprovadas** (termos de dados) |
| **Segredos/credenciais** | **Nunca** |
| **PII/PHI/PCI** | **Nunca** (usar sintéticos) |
| **Dados regulados/contratuais (NDA)** | **Conforme contrato/política** |

## 8. Auditoria e evidências

| Fonte | Uso |
|---|---|
| **Logs da ferramenta** (admin do Q Developer/Copilot) | Quem usa, quanto, quais recursos (**confirmar**) |
| **Histórico de Git/PRs** | Mudanças, revisores, marcadores de IA |
| **CI (SAST/SCA/segredos/IaC)** | Achados e bloqueios |
| **CloudTrail** | Ações de **roles de agentes** e do desenvolvedor |
| **Registros de aprovações de comandos** | Do agente |
| **SBOM/licenças** | Conformidade |
| **Exceções de política** | Aprovações documentadas |
| **Revisões periódicas** | Acessos, MCPs/extensões, políticas |

## 9. Checklist

1. **Ferramentas aprovadas**, contas corporativas/SSO, termos de dados revisados.
2. **Sem segredos/PII** em prompts; arquivos sensíveis **excluídos** do contexto.
3. **Revisão humana** + **SAST/SCA/segredos/IaC** como **portões** determinísticos.
4. **Dependências verificadas** (existência, reputação, licença), **lockfiles**, **SBOM**.
5. **Licenças** auditadas; **filtros/referência** de licença ativados.
6. **Agentes**: menor privilégio, **sandbox**, aprovação de comandos, **sem produção**, branch protegido, limites.
7. **IaC gerada validada** (sem curingas).
8. **MCP/extensões** confiáveis e com versão fixa.
9. **Prompt injection** considerada (não confiar em conteúdo lido).
10. **Política, treinamento e auditoria** definidos; **plano de incidentes**.
11. **Capacidade humana** preservada (entender o que entra no código).

## 10. Erros comuns

- **Aceitar código gerado sem revisão/scan**.
- **Colar segredos/logs com tokens** em prompts.
- **Usar contas pessoais/ferramentas não aprovadas** com código da empresa.
- **Instalar pacote sugerido** sem verificar.
- **Ignorar licenças**.
- **Agente com credenciais de produção/administrador**.
- **Auto-aprovar todos os comandos do agente**.
- **IaC com `*`** aceita por conveniência.
- **Ferramentas MCP de origem duvidosa**.
- **Sem política/treinamento**.
- **Sem registro** de uso de IA quando exigido.
- **Esquecer prompt injection** em arquivos/issues lidos pelo agente.

## 11. Troubleshooting

| Sintoma | Causa provável | Ação |
|---|---|---|
| Segredo em commit gerado | Código de exemplo com chave | **Rotacionar**, remover do histórico, ativar **push protection** |
| Pacote desconhecido no `requirements` | Sugestão alucinada | Verificar; remover; política de dependências |
| Alerta de licença | Trecho semelhante a OSS | Reescrever/substituir; consultar jurídico |
| Agente executou comando destrutivo | Aprovação automática/permissões amplas | Restringir; sandbox; backups; revisão de incidente |
| Vazamento de código em ferramenta externa | Ferramenta não aprovada | Cessar; avaliar impacto; migrar para ferramenta aprovada |
| SAST acusa muitas falhas em código gerado | Padrões inseguros | Regras de projeto + revisão; treinar equipe |
| IaC aplicada com permissões amplas | Sem validação | `cfn-guard`/`plan`; **permission boundary**; revisar |
| Agente seguiu instruções de um README malicioso | Prompt injection | Isolar; revisar; limitar ferramentas; confiar apenas em fontes confiáveis |

## 12. Resumo rápido

- **Código gerado = código não confiável até revisado**: **revisão + SAST/SCA/segredos/IaC** como **portões determinísticos**.
- **Segredos e dados**: **nunca** em prompts; excluir arquivos sensíveis; **ferramentas e contas aprovadas**; entender **retenção/treinamento**.
- **Licenças**: filtros/referência, SCA de licenças, política e **jurídico**.
- **Dependências**: verificar existência/reputação (**slopsquatting**), lockfiles, **SBOM**, **CodeArtifact**.
- **Agentes**: **menor privilégio**, **sandbox**, **aprovação de comandos**, **sem produção**, branch protegido, limites e **auditoria**; atenção a **prompt injection** e **MCP** não confiável.
- **Governança**: política de IA, SSO, treinamento, classificação de dados, frameworks (**OWASP LLM, NIST, ISO 42001**), resposta a incidentes.

## 🧩 Quiz de Fixação

1. Por que tratar código gerado como código de terceiros?
2. O que fazer se um segredo foi colado em um prompt?
3. O que é slopsquatting?
4. Que permissões dar a um agente de código?
5. Como mitigar riscos de licença?
6. Por que IaC gerada exige validação extra?
7. Que tipo de dado nunca deve ir a um assistente de IA?

**Respostas:**

1. Porque não foi escrito nem entendido por você e pode ter vulnerabilidades, dependências ou licenças problemáticas; exige revisão e scans.
2. Tratar como vazado: revogar e rotacionar, checar logs de uso e remover do histórico.
3. Registro malicioso de nomes de pacotes que a IA costuma inventar; mitigue verificando existência/reputação e usando lockfiles e registries controlados.
4. Menor privilégio: escopo do projeto, conta/roles de desenvolvimento, aprovação de comandos destrutivos, sandbox, sem produção.
5. Ativando filtros/referência de licença, usando SCA de licenças, políticas internas e consultando o jurídico.
6. Porque costuma gerar permissões amplas, propriedades inventadas e configurações inseguras; usar cfn-guard/plan e menor privilégio.
7. Segredos, credenciais e dados pessoais/regulados (PII/PHI/PCI); use dados sintéticos.
