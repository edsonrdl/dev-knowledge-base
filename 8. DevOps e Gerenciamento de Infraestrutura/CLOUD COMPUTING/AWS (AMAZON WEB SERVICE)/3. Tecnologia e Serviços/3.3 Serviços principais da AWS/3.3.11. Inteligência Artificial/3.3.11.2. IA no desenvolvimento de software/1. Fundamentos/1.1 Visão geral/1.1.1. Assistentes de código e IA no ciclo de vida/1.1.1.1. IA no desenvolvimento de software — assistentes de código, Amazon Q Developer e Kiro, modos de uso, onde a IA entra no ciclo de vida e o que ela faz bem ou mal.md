### 1.1.1.1. IA no desenvolvimento de software — assistentes de código, Amazon Q Developer e Kiro, modos de uso, onde a IA entra no ciclo de vida e o que ela faz bem ou mal

> [!warning] Aviso
> Ferramentas de IA para desenvolvedores mudam **muito rápido**: nomes, planos, recursos, modelos, limites e até a existência de produtos (por exemplo, **CodeWhisperer** foi incorporado ao **Amazon Q Developer**; **Kiro** é um IDE/agente mais recente; **CodeGuru** teve mudanças de disponibilidade). Tudo abaixo é **de memória e não foi executado**. **Confirme na documentação oficial de cada ferramenta.** Esta nota apoia as skills **1.1.9 (ferramentas de desenvolvimento assistido por IA)** e **3.2.5, 3.3.9, 4.1.5, 4.3.6** do DVA-C03.

## 1. O que é desenvolvimento assistido por IA

É o uso de **modelos de linguagem** (LLMs) **dentro do fluxo do desenvolvedor** para **gerar, explicar, transformar, revisar e depurar código** e artefatos (testes, documentação, IaC, consultas). A IA **não substitui** o julgamento do desenvolvedor: ela **propõe**; **você valida**.

| Modo | Descrição | Exemplo |
|---|---|---|
| **Autocomplete inline** | Sugere o **próximo trecho** enquanto você digita | Completar função a partir do comentário |
| **Chat no IDE** | Perguntas sobre código/projeto, explicações, refatorações | “Explique esta classe”, “Converta para async” |
| **Geração por prompt** | Cria funções/arquivos/testes a partir de uma descrição | “Escreva testes unitários para esta função” |
| **Modo agente (agentic)** | Planeja e executa **várias etapas**: lê arquivos, edita, roda comandos/testes e itera | Implementar uma funcionalidade e rodar a suíte |
| **Transformação de código** | Migrações **em larga escala** (versão de Java, frameworks) | Atualizar Java 8 → 17 |
| **Revisão automatizada** | Analisa **diffs/PRs**: bugs, segurança, estilo | Comentários em pull request |
| **Operação/diagnóstico** | Analisa **logs, erros e recursos AWS** | “Por que esta Lambda falha?” |
| **CLI com IA** | Assistente no terminal | Traduzir linguagem natural em comandos |

## 2. Ferramentas relevantes (visão geral)

| Ferramenta | Foco | Observação |
|---|---|---|
| **Amazon Q Developer** | Assistente de **desenvolvimento e operação na AWS**: chat, geração, **agentes** (`/dev`, `/test`, `/review`, `/doc`), **transformação** (Java, .NET), varredura de **segurança**, conhecimento de serviços AWS, **console/CLI** | Planos **gratuito e Pro**; integra **IDE (VS Code, JetBrains, Visual Studio)**, console, CLI, GitHub/GitLab (**confirmar**) |
| **Kiro (AWS)** | IDE/agente com fluxo **orientado a especificações (spec-driven)**: requisitos → design → tarefas; **steering** (contexto/regras do projeto), **hooks** (automação por eventos) e **MCP** (**confirmar**) | Para **estruturar** o trabalho agêntico |
| **GitHub Copilot** | Autocomplete, chat e agente no GitHub/IDE | Terceiros |
| **Cursor, Windsurf, Claude Code, Codex CLI** etc. | IDEs/CLIs com agentes | Terceiros |
| **Bedrock (API)** | **Construir seus próprios** assistentes/agentes | Quando precisa de **customização** |
| **CodeGuru** (Reviewer/Profiler) | Revisão e **profiling** assistidos por ML | **Verificar status/disponibilidade atuais** |
| **DevOps Guru** | **Detecção de anomalias** operacionais com ML | Operação |
| **Compute Optimizer** | **Recomendações de dimensionamento** com ML | Ver nota do vault |

> [!tip] Para a prova
> Pergunta típica: “Qual serviço **auxilia o desenvolvedor com sugestões de código, chat e explicações dentro do IDE**, com conhecimento de **serviços AWS**?” → **Amazon Q Developer**. “Construir um **assistente próprio** com modelos fundacionais” → **Bedrock**.

## 3. Onde a IA entra no ciclo de vida (SDLC)

```
Requisitos ─▶ Design ─▶ Implementação ─▶ Testes ─▶ Revisão ─▶ CI/CD ─▶ Operação ─▶ Manutenção
   │            │            │             │          │          │          │           │
 rascunho     alternativas  autocomplete  geração   revisão    análise   diagnóstico  refatoração
 de specs     e diagramas   chat/agente   de testes de PR      de falhas de logs     migração
```

| Fase | Uso útil da IA | Cuidado |
|---|---|---|
| **Requisitos/Design** | Rascunhar **user stories**, critérios de aceite, alternativas de arquitetura, diagramas | **Validar** com o negócio; IA **assume** o que não sabe |
| **Implementação** | Boilerplate, CRUD, integrações com SDK, regex, conversões | **Revisar** APIs/versões (alucinação de métodos) |
| **IaC** | Rascunhar **CloudFormation/CDK/Terraform/SAM** | **Segurança** (permissões amplas) e **boas práticas** |
| **Testes** | Gerar **casos de teste**, mocks, dados sintéticos | **Qualidade** das asserções (evitar testes triviais) |
| **Revisão de código** | Detectar bugs, smells, vulnerabilidades | **Falsos positivos/negativos** |
| **CI/CD** | Explicar **falhas de build**, sugerir correções, gerar pipelines | **Não** conceder permissões irrestritas |
| **Operação** | Triagem de **erros/logs/métricas**, runbooks | **Confirmar** a hipótese com dados |
| **Manutenção** | **Refatoração**, **migração de versões**, **documentação** | **Testes** como rede de segurança |
| **Aprendizado** | Explicar código legado/serviços | Cruzar com a **documentação oficial** |

## 4. O que a IA faz bem — e mal

| Faz bem | Faz mal / riscos |
|---|---|
| **Boilerplate**, código repetitivo, padrões conhecidos | **Lógica de negócio específica** sem contexto |
| **Traduzir** entre linguagens/formatos, regex, SQL simples | **Alucinar APIs/parâmetros/versões** inexistentes |
| **Explicar** código e erros comuns | Explicações **plausíveis porém erradas** |
| **Gerar testes** de casos óbvios | Testes que **só espelham** a implementação |
| **Rascunhar** documentação, mensagens de commit, PRs | **Detalhes técnicos** imprecisos |
| **Refatorações** mecânicas com testes | **Mudanças silenciosas** de comportamento |
| **Acelerar** exploração de bibliotecas | **Dependências inexistentes/maliciosas** sugeridas (**slopsquatting**) |
| **Resumir** logs/diffs | **Perder** contexto crítico |
| **Segurança**: apontar padrões inseguros comuns | **Introduzir** vulnerabilidades/segredos/licenças problemáticas |
| **Iterar rápido** com feedback de testes | **Ficar preso em loops** ou “consertar” testes em vez do código |

> [!warning] Princípio de ouro
> **A IA é responsabilidade sua depois que o código entra no repositório.** Trate sugestões como **código de um colega júnior muito rápido**: **revise, teste e entenda** antes de aceitar.

## 5. Como esses assistentes funcionam (visão conceitual)

| Conceito | Explicação |
|---|---|
| **Contexto** | O assistente monta um **prompt** com o **trecho atual**, **arquivos abertos**, símbolos e (em modo agente) **partes do repositório** |
| **Janela de contexto** | Limite do que o modelo “vê”; projetos grandes exigem **seleção/recuperação** (RAG sobre o código) |
| **Instruções do projeto** | Arquivos de **regras/steering** (padrões de código, comandos de build/teste) orientam o modelo |
| **Ferramentas** | No modo agente: **ler/editar arquivos, executar comandos, buscar na web/docs, MCP** |
| **Aprovações** | O agente **pede confirmação** para ações sensíveis (conforme configuração) |
| **Memória de sessão** | Histórico da conversa — **cresce e custa**; resumir/limpar |
| **Determinismo** | Respostas **variam**; resultados devem ser **verificados por testes** |

## 6. Amazon Q Developer — recursos típicos (de memória)

| Recurso | O que faz |
|---|---|
| **Sugestões inline** | Completar código; suporta várias linguagens |
| **Chat** | Perguntas sobre código, AWS, erros; explicações; **comandos de CLI** |
| **`/dev` (agente de implementação)** | Planeja e implementa funcionalidades a partir de uma descrição, gerando **diffs** para você revisar |
| **`/test`** | Gera testes unitários |
| **`/review`** | Revisão de código (qualidade e segurança) |
| **`/doc`** | Gera/atualiza documentação (README, diagramas) |
| **Transformação** | **Atualização de Java (ex.: 8/11 → 17/21)**, migração de frameworks/.NET (**confirmar escopo**) |
| **Varredura de segurança** | Identifica vulnerabilidades e sugere **correções** |
| **Console AWS** | Chat sobre **recursos e custos**, **diagnóstico de erros** de serviços |
| **CLI** | Assistente no terminal (autocompletar e linguagem natural) |
| **Referência de licença** | Sinaliza sugestões **semelhantes a código de código aberto** com licença (**confirmar**) |
| **Personalização** | Ajustar sugestões ao **código da organização** (planos Pro) |
| **Administração** | Controle de **usuários/políticas** via IAM Identity Center (**confirmar**) |

## 7. Kiro e o desenvolvimento orientado a especificações (visão geral)

| Conceito | Descrição |
|---|---|
| **Specs** | Documentos estruturados: **requisitos (EARS)**, **design**, **tarefas** — o agente **implementa por tarefas** |
| **Steering** | Arquivos que dão **contexto persistente** (convenções, stack, regras) |
| **Hooks** | Automações disparadas por **eventos** (ex.: salvar arquivo → gerar teste/doc) |
| **MCP** | Conexão a **ferramentas/dados** externos |
| **Vantagem** | **Rastreabilidade** entre requisito, design e código; menos “vibe coding” |
| **Quando usar** | Funcionalidades **maiores**, equipes que exigem **documentação viva** |

> “**Vibe coding**” (pedir e aceitar sem entender) é **ótimo para protótipos descartáveis** e **perigoso para produção**.

## 8. Prompt e contexto: o que melhora os resultados

| Prática | Exemplo |
|---|---|
| **Contexto claro** | Linguagem, framework, versão, restrições (“Python 3.12, boto3, sem novas dependências”) |
| **Objetivo + critérios de aceite** | “Retorne 404 se não existir; log estruturado” |
| **Exemplos** | Entrada/saída esperadas |
| **Padrões do projeto** | “Siga o estilo de `src/handlers/`” |
| **Passos pequenos** | Quebrar a tarefa em **etapas verificáveis** |
| **Pedir o plano antes** | Revisar o plano e **depois** gerar |
| **Fornecer erros completos** | Stack trace, versão, comando |
| **Pedir testes junto** | “E escreva testes que falhariam sem esta mudança” |
| **Limitar escopo** | “Altere apenas `pedidos.py`” |
| **Iterar com evidências** | Rodar testes e colar o **resultado real** |

## 9. Quando **não** usar (ou usar com muito cuidado)

| Situação | Motivo |
|---|---|
| **Código crítico de segurança/criptografia** | Erros sutis; use **bibliotecas auditadas** |
| **Dados sensíveis/segredos** no prompt | **Vazamento** (veja nota de segurança) |
| **Domínios regulados** sem revisão | Conformidade |
| **Algoritmos sem testes** | Sem rede de segurança |
| **Código que você não consegue revisar** | Dívida técnica e risco |
| **Licenças incertas** | Risco jurídico |
| **Aprender fundamentos** (como único método) | Perde a compreensão |

## 10. Erros comuns

- **Aceitar sugestões sem ler**.
- **Confiar em APIs/parâmetros inventados**.
- **Colar segredos/PII/código proprietário** em ferramentas não aprovadas.
- **Pedir tarefas enormes de uma vez**.
- **Deixar o agente com permissões excessivas** (apagar, executar qualquer comando).
- **Aceitar testes gerados que não testam nada** (asserções fracas).
- **Não versionar/commitar em passos pequenos** (difícil reverter).
- **Instalar dependências sugeridas sem verificar** (existência/reputação).
- **Não fornecer contexto** (resultados genéricos).
- **Usar IA como única fonte** (sem consultar a documentação oficial).
- **Ignorar licenças**.

## 11. Troubleshooting do uso

| Sintoma | Causa provável | Ação |
|---|---|---|
| Sugestões genéricas/erradas | Pouco contexto | Abrir arquivos relevantes; descrever stack/versões; regras do projeto |
| Método/API inexistente | Alucinação/versão antiga | Conferir **documentação**; fixar versão; pedir o link/fonte |
| Agente em loop | Tarefa ambígua/teste quebrado | Reduzir escopo; dar critérios; interromper e corrigir manualmente |
| Mudanças demais num PR | Escopo aberto | Limitar arquivos; **commits pequenos** |
| Testes passam mas bug persiste | Testes espelham a implementação | Escrever **testes de comportamento** e casos de borda |
| Código inseguro | Padrão comum, mas inseguro | Varredura de segurança; revisão; guardrails de CI |
| Contexto “estourado” | Conversa longa | Nova sessão com **resumo**; steering |
| Sugestão copiou licença | Trecho similar a OSS | Ver **referência de licença**; reescrever |

## 12. Resumo rápido

- **IA para desenvolvedores**: autocomplete, chat, geração, **agentes**, transformação de código, revisão e diagnóstico — **propõe**, **você valida**.
- **Amazon Q Developer** (IDE/console/CLI; `/dev`, `/test`, `/review`, `/doc`, transformação, varredura de segurança) e **Kiro** (spec-driven, steering, hooks, MCP); **Bedrock** para **construir os seus**.
- **SDLC**: requisitos → design → código → testes → revisão → CI/CD → operação → manutenção — a IA ajuda em **todas**, com **cuidados** distintos.
- Faz bem **boilerplate/explicações/testes óbvios**; faz mal **lógica específica, APIs inventadas, segurança**.
- **Boas práticas**: contexto claro, passos pequenos, pedir plano, **testes como rede de segurança**, **revisar tudo**.
- **Responsabilidade é sua**: segurança, licenças, qualidade e privacidade.

3. O que é desenvolvimento orientado a especificações?
4. Cite dois riscos de aceitar código gerado sem revisão.
5. Por que dividir tarefas em passos pequenos?

7. Quando evitar usar IA?

**Respostas:**

1. Autocomplete inline, chat, geração por prompt, modo agente, transformação de código, revisão automatizada, diagnóstico e CLI.
2. Amazon Q Developer.
3. Fluxo em que requisitos, design e tarefas são documentados em specs e o agente implementa por tarefas, mantendo rastreabilidade (como no Kiro).
4. Alucinação de APIs/dependências e introdução de vulnerabilidades, segredos ou problemas de licença.
5. Para facilitar revisão, testes, reversão e reduzir erros e loops do agente.
6. Registrar pacotes com nomes que a IA costuma inventar para distribuir código malicioso; por isso é preciso verificar a existência e a reputação das dependências sugeridas.
7. Em código crítico de segurança sem revisão, com dados sensíveis/segredos, domínios regulados sem controles ou quando não se consegue revisar o resultado.
