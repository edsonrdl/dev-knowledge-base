### 4.1.1.1. IA para analisar erros e otimizar — diagnóstico de logs e stack traces, Amazon Q no console, CloudWatch e DevOps Guru, Compute Optimizer, profiling e como validar hipóteses

> [!warning] Aviso
> Recursos de IA em observabilidade (Amazon Q Developer no console, **CloudWatch investigations**, **DevOps Guru**, **CodeGuru Profiler**, **Compute Optimizer**) mudam rápido, e alguns produtos têm **disponibilidade alterada**. Tudo abaixo é **de memória e não foi executado**. **Confirme na documentação de cada serviço.** Comandos e consultas são ilustrativos; nomes, contas e ARNs são fictícios. Esta nota apoia as skills **4.1.5 (IA para analisar erros)** e **4.3.6 (IA para otimização)** do DVA-C03; veja também a nota do **AWS Compute Optimizer** no vault.

## 1. Diagnóstico assistido por IA: o que é e o que não é

**Diagnóstico assistido** usa modelos para **ler logs, métricas, traces e configuração**, **resumir** o que acontece e **propor hipóteses e correções**. É um **acelerador de triagem**; **não** é oráculo.

| A IA ajuda a… | Mas você precisa… |
|---|---|
| **Resumir** milhares de linhas de log | **Confirmar** com dados originais |
| **Correlacionar** erro × deploy × métrica | **Validar causalidade** (correlação ≠ causa) |
| **Sugerir causas prováveis** de uma exceção | **Reproduzir/testar** a hipótese |
| **Explicar** mensagens de erro de serviços AWS | **Cruzar com a documentação** |
| **Propor correção** (código/IAM/config) | **Revisar** (menor privilégio, efeitos colaterais) |
| **Gerar consultas** (Logs Insights, SQL, JQ) | **Executar e conferir** resultados |
| **Redigir** pós-mortem/runbook | **Validar** fatos e linha do tempo |

## 2. Método de diagnóstico (com IA no processo)

```
1. DEFINIR o sintoma (o que, onde, desde quando, quem é afetado, o que mudou)
2. COLETAR evidências (logs, métricas, traces, deploys, alarmes, configuração)
3. PEDIR hipóteses à IA COM contexto + dados (mascarados)
4. TESTAR cada hipótese (query, reprodução, feature flag, rollback)
5. CORRIGIR (mínimo, reversível) e VERIFICAR (métricas/testes)
6. REGISTRAR (causa raiz, correção, prevenção)
```

| Boa prática | Detalhe |
|---|---|
| **Dar contexto completo** | Serviço, runtime/versão, **stack trace inteiro**, configuração relevante, **o que mudou** |
| **Pedir hipóteses ranqueadas** | “Liste 3 causas prováveis e **como confirmar** cada uma” |
| **Pedir o teste, não só a resposta** | Qual consulta/comando **confirma** |
| **Mascarar dados** | Remover **PII/segredos/tokens** |
| **Não confiar em uma única hipótese** | Evitar **viés de confirmação** |
| **Registrar o que foi descartado** | Evita repetir |
| **Preferir correção mínima** | E **reversível** |

## 3. Analisando erros de aplicação

### 3.1 Exemplo de prompt (stack trace de Lambda)

```text
Contexto: Lambda Python 3.12 (256 MB, timeout 10 s), lê do DynamoDB e chama o Bedrock. 
Sintoma: 5% das invocações terminam em "Task timed out after 10.01 seconds" desde o deploy de ontem 14:00.
Logs (mascarados): <trecho com REPORT: Duration, Max Memory Used, Init Duration>
Mudou: incluímos retries adaptive e aumentamos o contexto do prompt.
Pergunta: liste 3 hipóteses ranqueadas, como confirmar cada uma (consultas do Logs Insights/métricas) e correções de menor risco.
```

### 3.2 Erros típicos e padrões que a IA costuma acertar

| Sintoma | Hipóteses comuns | Como confirmar |
|---|---|---|
| **`AccessDeniedException`** | IAM faltando, **SCP/boundary**, **KMS**, endpoint policy, recurso de outra conta | CloudTrail (`errorCode`), **IAM Policy Simulator**, `sts get-caller-identity` |
| **`ThrottlingException`/429** | Cotas, picos, sem backoff | Métricas de throttle, **Service Quotas**, concorrência |
| **Timeout** | Timeout curto, **cold start**, chamada lenta, retries, VPC sem NAT/endpoint | `REPORT`, X-Ray, `Init Duration`, métricas de dependências |
| **`OutOfMemory`/`Runtime exited`** | Memória baixa, vazamento, payload grande | `Max Memory Used` vs configurado |
| **5xx do API Gateway** | Integração/timeout/permissão do Lambda | Logs de acesso/execução do API Gateway |
| **DLQ crescendo** | Exceções no consumidor, mensagens “venenosas” | Logs do consumidor; amostra da DLQ |
| **`ConditionalCheckFailed`** | Concorrência/idempotência | Lógica de condição; chaves |
| **`SignatureDoesNotMatch`/`ExpiredToken`** | Relógio, credenciais, headers | Hora do host; sessão |
| **Conexões esgotadas (RDS)** | Lambda sem **RDS Proxy**, picos | Métricas de conexões |

> Peça sempre à IA que **cite a evidência** que sustenta cada hipótese (linha do log, métrica) — se não houver, é **suposição**.

### 3.3 Consultas úteis (a IA ajuda a escrever; **você valida**)

```sql
-- CloudWatch Logs Insights: erros por tipo nas últimas horas
fields @timestamp, @message
| filter @message like /ERROR|Exception|Task timed out/
| stats count() as n by bin(15m)
| sort @timestamp desc
```

```sql
-- Lambda: latência e memória (a partir das linhas REPORT)
filter @type = "REPORT"
| stats avg(@duration) as media_ms, pct(@duration, 99) as p99_ms, max(@maxMemoryUsed/1024/1024) as mb_max, count(*) as n by bin(5m)
```

```sql
-- Cold starts
filter @type = "REPORT" and ispresent(@initDuration)
| stats count() as cold, avg(@initDuration) as init_ms by bin(1h)
```

## 4. IA na AWS para operação e diagnóstico (visão geral)

| Recurso | O que faz | Observação |
|---|---|---|
| **Amazon Q Developer no console** | Chat sobre **recursos da conta**, explicação de erros, **diagnóstico** (ex.: “por que esta Lambda falha?”), dicas de **IAM/rede** | Usa o **seu contexto/permissões**; **verificar** respostas |
| **CloudWatch — investigations (IA generativa)** | **Investigação assistida** de incidentes: correlaciona sinais e sugere **hipóteses** (**confirmar disponibilidade**) | Complementa alarmes |
| **CloudWatch Logs — geração de consultas em linguagem natural** | Cria consultas **Logs Insights/PromQL** | **Revisar** a consulta |
| **CloudWatch Anomaly Detection** | **ML** para bandas de **normalidade** em métricas; alarmes de anomalia | Reduz limiares fixos |
| **Amazon DevOps Guru** | **ML** detecta **anomalias operacionais** em recursos (Lambda, DynamoDB, RDS…) e **recomenda** ações | **Verificar status/disponibilidade atuais** |
| **AWS X-Ray / ServiceLens** | **Traces** e mapa de serviços — **evidência** para a IA | Ver nota do X-Ray |
| **CodeGuru Profiler** | Profiling contínuo com recomendações de **otimização de CPU/memória** | **Verificar disponibilidade atual** |
| **AWS Compute Optimizer** | **ML** recomenda **tamanho** de EC2/EBS/Lambda/ECS/ASG etc. | Ver nota do vault |
| **Trusted Advisor / Cost Explorer (recomendações)** | Verificações de **custo, segurança, limites** | |
| **Health Dashboard** | Eventos do **serviço AWS** | Descartar causa externa |

> [!tip] Pegadinha de prova
> “**Recomendações de dimensionamento** com base em métricas históricas (ML)” → **Compute Optimizer**. “**Detectar anomalias operacionais** e recomendar ações” → **DevOps Guru**. “Assistente de IA para **entender erros no console/IDE**” → **Amazon Q Developer**. “**Rastrear** requisições entre serviços” → **X-Ray**.

## 5. IA para otimização de desempenho e custo

### 5.1 Onde a IA ajuda

| Área | Uso | Verificação |
|---|---|---|
| **Código** | Apontar **gargalos** (N+1, loops com chamadas ao SDK, I/O síncrono, estruturas ineficientes) | **Profiling/benchmark** antes e depois |
| **Consultas** | Sugerir **índices**/reescritas (SQL/DynamoDB Query vs Scan) | **EXPLAIN**, métricas reais |
| **Lambda** | Ajustar **memória** (CPU proporcional), reduzir **cold start**, reusar conexões | **AWS Lambda Power Tuning**, Compute Optimizer |
| **Contêineres/EC2** | **Right-sizing**, Spot/Savings Plans | Compute Optimizer + carga real |
| **Custos** | Achar **recursos ociosos**, logs verbosos, **transferência** | Cost Explorer, Trusted Advisor |
| **Arquitetura** | Cache, filas, assíncrono, **batching** | Teste de carga |
| **IaC** | Remover **superdimensionamento** | Revisão do plan |

### 5.2 Método seguro de otimização

```
1. MEDIR (baseline): latência p50/p99, custo, uso de CPU/memória
2. HIPÓTESE (IA propõe): onde está o gargalo?
3. EXPERIMENTO: mudar UMA coisa, em ambiente de teste/canário
4. MEDIR de novo e comparar
5. DECIDIR (manter/reverter) e DOCUMENTAR
```

| Regra | Motivo |
|---|---|
| **Nunca otimizar sem medir** | A intuição (e a IA) erram frequentemente |
| **Uma mudança por vez** | Isolar o efeito |
| **Preservar o comportamento** | Testes de regressão |
| **Cuidado com “micro-otimizações”** | Custo de manutenção > ganho |
| **Considerar custo × latência × confiabilidade** | Trade-offs reais |

### 5.3 Exemplo: memória do Lambda

```
Observação: função de 256 MB com Duration média 900 ms, Max Memory Used 120 MB.
Hipótese da IA: aumentar para 1024 MB pode reduzir a duração (mais CPU) e, às vezes, o custo total.
Teste: AWS Lambda Power Tuning (Step Functions) em 128/256/512/1024/2048 MB, com payload representativo.
Decisão: escolher o ponto com melhor custo-benefício (curva custo × duração), não o "mais rápido".
```

## 6. Armadilhas ao usar IA para diagnóstico e otimização

| Armadilha | Consequência | Mitigação |
|---|---|---|
| **Aceitar a primeira hipótese** | Correção errada, causa raiz persiste | Testar **várias** hipóteses |
| **Correlação tomada como causa** | “Culpar” o último deploy sem prova | Linha do tempo, **teste de reversão** |
| **Contexto incompleto** | Resposta genérica | Fornecer **dados e o que mudou** |
| **Alucinação de recursos/flags** | Comandos inexistentes | Conferir na **documentação** |
| **Correção de IAM ampla** (“adicione `*`”) | Falha de segurança | **Menor privilégio**, Access Analyzer |
| **Executar comandos sugeridos sem ler** | Dano em produção | `--dry-run`, ambiente de teste |
| **Enviar dados sensíveis** | Vazamento | **Mascarar**; ferramentas aprovadas |
| **Otimizar sem medir** | Regressões | Baseline e experimentos |
| **Confiar em recomendações sem carga real** | Subdimensionamento | Validar com picos/sazonalidade |
| **Ignorar causas externas** | Perde tempo | **Health Dashboard** e status do serviço |

## 7. Pós-incidente: IA como redatora, humano como autor

| Entregável | Papel da IA | Papel humano |
|---|---|---|
| **Linha do tempo** | Montar a partir de logs/alarmes | **Validar** horários e fatos |
| **Causa raiz** | Sugerir “5 porquês” | **Confirmar** com evidências |
| **Ações corretivas** | Rascunhar lista | **Priorizar** e atribuir |
| **Runbook** | Gerar passos | **Testar** em simulação |
| **Comunicação** | Rascunhar mensagens | **Revisar tom/precisão** |

## 8. Erros comuns

- **“A IA disse que é X”** sem verificar.
- **Aplicar correção direto em produção**.
- **Não mascarar dados** ao pedir ajuda.
- **Ignorar o que mudou** (deploys/configuração).
- **Otimizar sem baseline**.
- **Aceitar IAM `*`**.
- **Confiar cegamente em Compute Optimizer** sem verificar picos/sazonalidade.
- **Usar ferramenta de IA não aprovada** com dados da empresa.
- **Não registrar** a causa raiz e a prevenção.
- **Esquecer causa externa** (incidente do provedor).

## 9. Troubleshooting do próprio processo

| Sintoma | Causa provável | Ação |
|---|---|---|
| Respostas genéricas | Falta de dados | Anexar logs/métricas/trace (mascarados) |
| Hipóteses contraditórias | Pouca evidência | Coletar mais sinais; testar a mais barata |
| Consulta de Logs Insights não retorna | Campos/filtros errados | Conferir campos (`@message`, `@type`); intervalo |
| Recomendação de otimização piora | Sem medir/validar | Reverter; baseline; canário |
| Correção funciona só às vezes | Causa raiz diferente/intermitente | Mais evidências (traces), reproduzir |
| Q/console sem acesso aos recursos | Permissões do usuário/contexto | Ajustar **IAM** do usuário (menor privilégio) |
| Alarmes de anomalia ruidosos | Banda mal treinada | Ajustar sensibilidade/período |

## 10. Resumo rápido

- **IA acelera triagem** (resumir logs, correlacionar, propor hipóteses e consultas), **mas você valida** com dados e testes.
- **Método**: sintoma → evidências → **hipóteses ranqueadas + como confirmar** → teste → correção mínima → verificação → registro.
- **Ferramentas AWS**: **Amazon Q Developer** (console/IDE), **CloudWatch** (Logs Insights, anomaly detection, investigações), **X-Ray**, **DevOps Guru**, **CodeGuru Profiler**, **Compute Optimizer**, **Trusted Advisor**.
- **Otimizar** = **medir → hipótese → experimento → medir** (Lambda Power Tuning, profiling, Compute Optimizer).
- **Riscos**: correlação ≠ causa, **alucinação**, **IAM amplo**, comandos sem revisão, **vazamento de dados**, otimizar sem medir.
- **Pós-incidente**: IA redige; **humanos confirmam** e decidem.
