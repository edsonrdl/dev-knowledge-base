### 4.1.1.1. Arquiteturas com Bedrock — Lambda e API Gateway, streaming, filas e batch, Step Functions, VPC endpoints, cross-region, caching, controle de custos e padrões de produção

> [!warning] Aviso
> Limites (timeouts do API Gateway/Lambda, cotas do Bedrock), preços, recursos de streaming e de caching mudam. Tudo abaixo é **de memória e não foi executado**. **Confirme na documentação do Bedrock, Lambda, API Gateway e Step Functions e nas páginas de preços.** Diagramas, YAML e código são ilustrativos; contas, ARNs e IDs são fictícios.

## 1. Princípios de arquitetura para IA generativa

| Princípio | Aplicação |
|---|---|
| **Chamadas lentas e caras** | Tratar o modelo como **dependência lenta**: timeouts, retries, **assíncrono** quando possível |
| **Cotas por região/modelo** | **Controlar concorrência**, usar **filas** e **backoff**, planejar **cross-region/Provisioned** |
| **Não determinismo** | Validar saídas; **testes de avaliação**; **fallback** |
| **Custo por token** | Limitar entrada/saída; **cache**; modelo adequado |
| **Dados sensíveis** | **Rede privada**, KMS, minimização, **Guardrails** |
| **Observabilidade** | Registrar **tokens, latência, motivos de parada, erros** |
| **Defesa em profundidade** | Autenticação na API, **rate limit**, **WAF**, validação de entrada |

## 2. Padrão 1: API síncrona (Lambda + API Gateway)

```
Cliente ─▶ API Gateway (auth, throttling, WAF) ─▶ Lambda ─▶ Bedrock (Converse)
                                                      └▶ DynamoDB (histórico/uso)
```

| Ponto | Detalhe |
|---|---|
| **Quando usar** | Respostas **curtas** (segundos), baixa/média carga |
| **Timeouts** | **API Gateway REST: 29 s por padrão** (pode ser estendido em alguns cenários — **confirmar**); **HTTP API: 30 s**; **Lambda: até 15 min** → o **menor** vale |
| **Memória/CPU do Lambda** | Pouca CPU necessária (aguarda I/O); **memória média** basta |
| **Timeout do cliente SDK** | `read_timeout` maior que o padrão; menor que o do Lambda |
| **Limites de payload** | API Gateway **10 MB**; Lambda **6 MB** (síncrono) |
| **Autenticação** | **Cognito/JWT/IAM**; **chaves de API** só para planos de uso |
| **Throttling** | **Usage plans**/limites por cliente → **protege custo e cota** |

> [!warning] Resposta > 29 s
> Perguntas longas (documentos grandes, agentes) **estouram** o limite do API Gateway. Use **streaming**, **assíncrono** ou **WebSocket**.

## 3. Padrão 2: streaming ao cliente

| Opção | Como | Observação |
|---|---|---|
| **Lambda Function URL + response streaming** | Handler transmite tokens (`InvokeModelWithResponseStream`/`ConverseStream`) | Suporte nativo em **Node.js**; outras linguagens via **runtime customizado/Lambda Web Adapter** (**confirmar**) |
| **API Gateway REST com streaming de resposta** | Recurso mais recente (**confirmar** disponibilidade/limites) | Evita o limite de 29 s |
| **WebSocket API (API Gateway)** | Lambda envia tokens por `PostToConnection` | Bidirecional; **gestão de conexões** |
| **AppSync (GraphQL subscriptions)** | Publica deltas em tempo real | Bom p/ front GraphQL |
| **ALB/ECS (SSE)** | Servidor mantém conexão | **Controle total**; custo de infra |
| **CloudFront** | Pode **encaminhar** streaming; **desabilitar buffering** (confirmar) | Cuidado com **cache** |

```javascript
// Node.js: Lambda com response streaming (esboço)
import { BedrockRuntimeClient, ConverseStreamCommand } from "@aws-sdk/client-bedrock-runtime";
const client = new BedrockRuntimeClient({});
export const handler = awslambda.streamifyResponse(async (event, responseStream) => {
  const out = await client.send(new ConverseStreamCommand({ modelId: process.env.MODEL_ID,
      messages: [{ role: "user", content: [{ text: JSON.parse(event.body).pergunta }] }] }));
  responseStream.setContentType("text/event-stream");
  for await (const ev of out.stream) {
    const t = ev.contentBlockDelta?.delta?.text; if (t) responseStream.write(`data: ${JSON.stringify({t})}\n\n`);
  }
  responseStream.end();
});
```

## 4. Padrão 3: processamento assíncrono (fila → worker)

```
Cliente ─▶ API ─▶ SQS (fila) ─▶ Lambda (concurrency limitada) ─▶ Bedrock ─▶ DynamoDB/S3
   ▲                                   │ falhas ─▶ DLQ
   └─── polling/WebSocket/SNS/EventBridge ◀── notificação de conclusão
```

| Ponto | Benefício |
|---|---|
| **Absorve picos** | A fila **amortece**; evita throttling |
| **Concorrência controlada** | `ReservedConcurrentExecutions`/`MaximumConcurrency` do **event source** = **limitar chamadas simultâneas** ao Bedrock |
| **Retries e DLQ** | Tratamento de falhas; **redrive** |
| **Visibility timeout** | **> tempo de processamento** (≥ 6× timeout do Lambda recomendado para SQS) |
| **Idempotência** | Mensagens podem repetir → chave de idempotência (job ID) |
| **Status do job** | Tabela DynamoDB (`PENDENTE/PROCESSANDO/CONCLUIDO/ERRO`) |
| **Quando usar** | Documentos grandes, resumos em lote, **tarefas > 29 s**, **cargas irregulares** |

## 5. Padrão 4: lote (batch inference e Step Functions Map)

| Opção | Quando | Observação |
|---|---|---|
| **Bedrock Batch Inference** | **Milhares/milhões** de prompts sem urgência | **JSONL no S3 → S3**, tipicamente com **desconto** (**confirmar**) e **latência de horas** |
| **Step Functions Distributed Map** | Paralelizar por item de um lote em S3 | Controla **concorrência**, **retries**, **tolerância a falhas** |
| **SQS + Lambda** | Fluxo contínuo | Simples |
| **AWS Batch/ECS** | Pré/pós-processamento pesado | |

## 6. Padrão 5: orquestração com Step Functions

```
Início ─▶ Extrair texto (Textract) ─▶ Classificar (Bedrock) ─▶ Choice
                                                   ├─ "fatura" ─▶ Extrair campos (Bedrock, JSON) ─▶ Validar ─▶ Gravar
                                                   └─ "outro"  ─▶ Revisão humana (callback .waitForTaskToken)
                                  (Retry/Catch em cada passo; fallback para modelo alternativo)
```

| Vantagem | Detalhe |
|---|---|
| **Integração otimizada com Bedrock** | Tarefa **`bedrock:invokeModel`** direto (sem Lambda) (**confirmar**) |
| **Retries/backoff** declarativos | `Retry` com `ThrottlingException` |
| **Aprovação humana** | `.waitForTaskToken` |
| **Paralelismo** | `Map`/`Parallel` |
| **Auditoria** | Histórico de execuções |
| **Determinismo** | Menos “agente”, **mais previsível** |



| Ponto | Detalhe |

## 8. Rede, privacidade e conformidade

| Recurso | Uso |
|---|---|
| **VPC endpoint (PrivateLink)** para `bedrock-runtime` (e `bedrock-agent-runtime`) | **Tráfego privado** da VPC ao Bedrock, **sem Internet/NAT** |
| **Endpoint policy** | Restringir **quais modelos/ações** podem ser chamados via endpoint |
| **Lambda em VPC** | Para acessar **RDS/OpenSearch privados** junto ao Bedrock (exige endpoint ou NAT) |
| **KMS (CMK)** | Criptografia de **jobs de batch, customização, KBs**, logs |
| **Logging de invocações** | Opcional para **S3/CloudWatch** (contém **prompts/respostas** → **dados sensíveis**: proteger e definir retenção) |
| **CloudTrail** | **Eventos de gestão** e (para alguns) de dados do Bedrock |
| **Residência de dados** | Escolher **região**; atenção a **cross-region inference** (dados podem **transitar entre regiões** da geografia — **confirmar** política) |
| **Compartilhamento com provedores** | Pela documentação, **não** (**confirmar**) |

```json
    "Action": ["bedrock:InvokeModel", "bedrock:InvokeModelWithResponseStream"],
    "Resource": "arn:aws:bedrock:us-east-1::foundation-model/anthropic.claude-3-haiku-*"
  }]
}
```

## 9. Resiliência: cotas, cross-region, fallback

| Técnica | Detalhe |
|---|---|
| **Backoff + jitter** | SDK `adaptive`; limitar concorrência |
| **Cross-region inference profiles** | Distribui requisições entre regiões → **mais cota/disponibilidade** |
| **Provisioned Throughput** | Capacidade **dedicada** (custo fixo) |
| **Fallback de modelo** | Se o principal falhar/throttling → **modelo alternativo** (qualidade/custo diferentes) |
| **Circuit breaker** | Parar de chamar quando muitas falhas; resposta degradada |
| **Timeouts em cascata** | Cliente < gateway < Lambda < modelo |
| **Degradação elegante** | Resposta em cache/“tente mais tarde” |
| **Multi-região ativo/passivo** | Para **DR** (dados/KBs replicados) |
| **Aumento de cotas** | **Service Quotas** (planejar com antecedência) |

## 10. Controle de custos

| Alavanca | Detalhe |
|---|---|
| **Modelo certo** | Pequeno para extração/classificação; grande só quando necessário |
| **`maxTokens` e limites de entrada** | Evita explosões |
| **Prompt caching** | Prefixos longos reutilizados (sistema, documentos) → **menos tokens cobrados** (**confirmar** regras) |
| **Cache de respostas** | Perguntas repetidas (DynamoDB/ElastiCache) |
| **Resumir histórico** | Conversas longas |
| **RAG enxuto** | `top-k` pequeno + rerank |
| **Batch** | Desconto para cargas não urgentes |
| **Provisioned** | Só com **uso alto e estável** |
| **Cotas por usuário/tenant** | **Tokens/dia**, rate limit |
| **Orçamentos e alarmes** | **AWS Budgets**, **Cost Anomaly Detection**, tags/`application inference profiles` para **rateio por aplicação** |
| **Monitorar `usage`** | Métricas por requisição → **custo por funcionalidade/cliente** |

```python
# Cotas simples por usuário (esboço)
def checar_cota(usuario, tokens_estimados):
    r = tabela.update_item(Key={"u": usuario}, UpdateExpression="ADD usados :t",
        ConditionExpression="attribute_not_exists(usados) OR usados < :lim",
        ExpressionAttributeValues={":t": tokens_estimados, ":lim": LIMITE_DIARIO}, ReturnValues="UPDATED_NEW")
```

## 12. Erros comuns

- **API Gateway síncrono para respostas longas** (estouro de 29 s).
- **Concorrência ilimitada** de Lambdas → **throttling**.
- **Sem DLQ/idempotência** em filas.
- **Sem limite de custo** por usuário/tenant.
- **Logar prompts completos** sem proteção (PII).
- **Cross-region** sem checar **residência de dados**.
- **Sem fallback** (indisponibilidade derruba o produto).
- **Provisioned Throughput** sem uso estável.
- **Caching de respostas personalizadas** compartilhado entre usuários.
- **Confundir timeouts** (cliente/gateway/Lambda/SDK).
- **Não medir qualidade** após trocar modelo/prompt.

## 13. Troubleshooting

| Sintoma | Causa provável | Ação |
|---|---|---|
| 504/timeout no cliente | Resposta > limite do gateway | Streaming/assíncrono/WebSocket |
| Muitos `ThrottlingException` | Pico/cota | Fila + `MaxConcurrency`, backoff, cross-region, aumento de cota |
| Lambda sem acesso ao Bedrock em VPC | Sem endpoint/NAT | **VPC endpoint** `bedrock-runtime` |
| Custo explode | Contexto longo/sem limites/loops de agente | Limites, caching, monitorar `usage` |
| Mensagens SQS reprocessadas | Visibility timeout curto | Aumentar; idempotência |
| Streaming “em bloco” no cliente | Buffering (proxy/CloudFront/API) | Desabilitar buffering/usar opção suportada |
| Respostas diferentes entre ambientes | Modelo/região/versão/temperatura | Fixar **modelId/versão** e parâmetros |
| `AccessDenied` só na VPC | **Endpoint policy** restritiva | Ajustar a policy |

## 14. Resumo rápido

- **Síncrono (Lambda+API Gateway)** para respostas curtas; **streaming/WebSocket/Function URL** para longas; **fila → worker** e **batch** para volume; **Step Functions** para fluxos determinísticos com aprovação humana.
- **Controle de concorrência** + **backoff** + **cross-region/Provisioned** para lidar com **cotas**.
- **Rede privada**: **VPC endpoint (PrivateLink)**, endpoint policy, **KMS**; cuidado com **logs de invocação** e **residência de dados**.
- **Custos**: modelo certo, **limites de tokens**, **prompt caching**, cache de respostas, batch, **cotas por usuário**, **Budgets/Anomaly Detection**.
- **Observabilidade**: tokens, latência (TTFT), `stopReason`, erros, métricas `AWS/Bedrock`, traces.
- **Fallback e circuit breaker** para resiliência.

## 🧩 Quiz de Fixação

1. Por que o API Gateway síncrono é problemático para respostas longas?
2. Como limitar chamadas simultâneas ao Bedrock em um worker SQS?
3. Quando usar Batch Inference?
4. Para que serve o VPC endpoint do Bedrock?
5. Como reduzir custo com prompts longos repetidos?
6. Qual risco de habilitar logs de invocação?
7. Por que usar Step Functions em vez de agente?

**Respostas:**

1. Porque tem timeout de cerca de 29 s (REST) e 30 s (HTTP API), menor que o tempo de muitas respostas; use streaming, assíncrono ou WebSocket.
2. Com MaximumConcurrency no event source mapping ou reserved concurrency do Lambda.
3. Para grandes volumes sem urgência, com entrada/saída no S3 e custo geralmente menor.
4. Manter o tráfego privado da VPC ao Bedrock sem Internet/NAT e permitir endpoint policy.
5. Com prompt caching do prefixo, cache de respostas, resumir histórico e limitar contexto.
6. Os logs contêm prompts e respostas, possivelmente com dados sensíveis; exigem proteção, retenção e acesso controlado.
7. Para processos conhecidos, pela previsibilidade, custo, testabilidade, retries declarativos e aprovação humana.
