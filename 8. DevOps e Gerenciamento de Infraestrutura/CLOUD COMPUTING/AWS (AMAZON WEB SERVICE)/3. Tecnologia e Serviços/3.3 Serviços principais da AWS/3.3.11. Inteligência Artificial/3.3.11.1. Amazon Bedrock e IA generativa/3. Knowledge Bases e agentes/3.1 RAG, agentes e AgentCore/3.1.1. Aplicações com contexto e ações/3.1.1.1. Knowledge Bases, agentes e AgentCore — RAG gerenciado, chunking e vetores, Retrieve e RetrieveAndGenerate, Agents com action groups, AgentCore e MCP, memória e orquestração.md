## 1. Por que RAG e agentes

Um LLM sozinho **não conhece seus dados** e **não age no mundo**. Duas soluções:

| Necessidade | Solução | Resultado |
|---|---|---|
| Responder com base em **documentos da empresa** (políticas, manuais, tickets) | **RAG** (Retrieval-Augmented Generation) | Respostas **fundamentadas e atualizáveis**, com **citações** |
| **Executar ações** (consultar pedido, abrir chamado, enviar e-mail) | **Agentes** (tool use + orquestração) | O modelo **planeja e chama APIs** |
| Ambos | Agente com **Knowledge Base** + ferramentas | Assistente corporativo |

## 2. RAG: como funciona

```
INGESTÃO (offline)                                   CONSULTA (online)
Documentos (S3, web, Confluence, SharePoint…)        Pergunta do usuário
   │ parse + chunking                                   │ embedding da pergunta
   ▼                                                    ▼
Embeddings (modelo) ──▶ Índice vetorial ◀── busca por similaridade (top-k) [+ filtros/híbrida]
                         (OpenSearch Serverless,           │ trechos relevantes
                          Aurora pgvector, S3 Vectors…)    ▼
                                                  Prompt = instruções + trechos + pergunta
                                                           │
                                                           ▼
                                                  LLM → resposta + citações
```

## 3. Knowledge Bases for Amazon Bedrock (RAG gerenciado)

### 3.1 O que oferece

| Recurso | Detalhe |
|---|---|
| **Conectores de dados** | **S3**, web crawler, Confluence, SharePoint, Salesforce (**confirmar lista**) |
| **Parsing** | Texto, PDF, HTML, planilhas; parsing **avançado** com FM para tabelas/imagens (**confirmar**) |
| **Chunking** | **Fixo** (tamanho + sobreposição), **semântico**, **hierárquico** (pai/filho), **sem chunking**, **customizado (Lambda)** |
| **Embeddings** | Modelos do Bedrock (Titan Embeddings, Cohere Embed…) |
| **Vector store** | **OpenSearch Serverless** (padrão criado pelo console), **Aurora PostgreSQL (pgvector)**, **S3 Vectors**, Pinecone, Redis Enterprise, MongoDB Atlas (**confirmar**) |
| **Sincronização** | **Ingestion jobs** (`StartIngestionJob`) — **incremental** |
| **APIs de consulta** | **`Retrieve`** e **`RetrieveAndGenerate`** |
| **Filtros de metadados** | Restringir a busca (ex.: `departamento = "RH"`) |
| **Busca híbrida** | **Semântica + palavra-chave** |
| **Reranking** | Reordenar resultados com modelo de rerank |
| **Citações** | Fontes retornadas com a resposta |
| **Guardrails** | Aplicáveis à geração |
| **Dados estruturados** | Consulta a **data warehouses** via **NL→SQL** (**confirmar**) |

### 3.2 `Retrieve` × `RetrieveAndGenerate`

| API | O que faz | Quando usar |
|---|---|---|
| **`Retrieve`** | Retorna **trechos** relevantes (+ scores, metadados) | Você **controla o prompt** e o modelo (RAG customizado) |
| **`RetrieveAndGenerate`** | Busca **e** gera a resposta com **citações**; suporta **sessão** (`sessionId`) | **Rapidez**; menos código |

```python
bar = boto3.client("bedrock-agent-runtime", region_name="us-east-1")

# 1) Só recuperar (você monta o prompt)
r = bar.retrieve(knowledgeBaseId="KB12345678",
                 retrievalQuery={"text": "Qual a política de reembolso?"},
                 retrievalConfiguration={"vectorSearchConfiguration": {
                     "numberOfResults": 5, "overrideSearchType": "HYBRID",
                     "filter": {"equals": {"key": "departamento", "value": "financeiro"}}}})
trechos = [x["content"]["text"] for x in r["retrievalResults"]]

# 2) Recuperar e gerar
g = bar.retrieve_and_generate(
    input={"text": "Qual a política de reembolso?"},
    retrieveAndGenerateConfiguration={
        "type": "KNOWLEDGE_BASE",
        "knowledgeBaseConfiguration": {
            "knowledgeBaseId": "KB12345678",
            "modelArn": "arn:aws:bedrock:us-east-1::foundation-model/anthropic.claude-3-haiku-20240307-v1:0"}})
print(g["output"]["text"]); print([c for c in g["citations"]])
```

### 3.3 Chunking: decisões que definem a qualidade

| Estratégia | Quando | Observação |
|---|---|---|
| **Fixo (ex.: 300 tokens, 20% de overlap)** | Padrão | Simples; pode **cortar** ideias |
| **Hierárquico** | Documentos longos/estruturados | Busca em **filhos** pequenos, devolve **pai** (contexto maior) |
| **Semântico** | Texto corrido | Quebra por **mudança de assunto**; custo extra |
| **Customizado (Lambda)** | Regras específicas (seções, tabelas) | Controle total |
| **Sem chunking** | Documentos já pequenos | |

> [!tip] Regra prática
> **Chunks pequenos** = busca precisa, **pouco contexto**; **grandes** = muito contexto, **ruído**. Teste com **perguntas reais** e meça (**recall, relevância, fidelidade**).

### 3.4 Qualidade do RAG: causas de respostas ruins

| Problema | Causa | Correção |
|---|---|---|
| Não acha a informação | Chunking/embedding ruins, pergunta ambígua | Ajustar chunk, **busca híbrida**, **reformular a query**, mais `numberOfResults` |
| Resposta com trechos irrelevantes | Poucos filtros | **Metadados + filtros**, **rerank** |
| **Alucinação** | Prompt permissivo | “Responda **somente** com o contexto; se faltar, diga que não sabe” |
| Informação desatualizada | Ingestão não rodou | **Sincronizar** (agendar/evento S3) |
| Vazamento entre usuários | Sem controle de acesso por documento | **Filtros por metadados** (ACL), KB por tenant, **verificação pós-recuperação** |
| Lento/caro | Muitos trechos/contexto grande | Reduzir top-k, caching |

## 4. Agents for Amazon Bedrock (agentes gerenciados)

### 4.1 Componentes

| Componente | Função |
|---|---|
| **Modelo** (FM) | Raciocina/planeja |
| **Instruções** | Papel e regras do agente |
| **Action groups** | **Ferramentas**: definidas por **OpenAPI** ou **function schema**, executadas por uma **Lambda** (ou “return of control” para a sua aplicação) |
| **Knowledge Bases** | Fonte de conhecimento (RAG) |
| **Prompt templates** | Pré-processamento, orquestração, pós-processamento, KB |
| **Aliases/versões** | Implantação controlada |
| **Memória** | Resumo entre sessões (**confirmar**) |
| **Guardrails** | Segurança |
| **Code interpretation** | Executar código em sandbox (**confirmar**) |
| **Multi-agent collaboration** | Supervisor + agentes especializados (**confirmar**) |

### 4.2 Ciclo de orquestração (ReAct)

```
Usuário ─▶ Agente: raciocina ("preciso do status do pedido")
              ├─ escolhe ação/ferramenta (action group → Lambda) com parâmetros
              ├─ recebe a observação (resultado)
              ├─ (repete até ter o suficiente) ─ pode consultar Knowledge Base
              └─ responde ao usuário
```

```python
bar = boto3.client("bedrock-agent-runtime")
resp = bar.invoke_agent(agentId="AGENT123", agentAliasId="ALIAS456",
                        sessionId="sessao-usuario-42", inputText="Cancele o pedido 123",
                        enableTrace=True)
for ev in resp["completion"]:                       # stream de eventos
    if "chunk" in ev: print(ev["chunk"]["bytes"].decode(), end="")
    if "trace" in ev: pass                           # raciocínio/ações (depuração)
```

### 4.3 Lambda de action group (esqueleto)

```python
def handler(event, context):
    acao = event["function"]; params = {p["name"]: p["value"] for p in event.get("parameters", [])}
    if acao == "buscar_pedido":
        dado = {"id": params["pedido_id"], "status": "PAGO"}
    else:
        dado = {"erro": "função desconhecida"}
    return {"messageVersion": "1.0",
            "response": {"actionGroup": event["actionGroup"], "function": acao,
                         "functionResponse": {"responseBody": {"TEXT": {"body": json.dumps(dado)}}}}}
```

| Ponto | Detalhe |
|---|---|
| **Permissões** | O **Bedrock** precisa de permissão para **invocar a Lambda** (resource policy) |
| **Idempotência** | Ações podem ser **repetidas** → projetar **idempotentes** |
| **Validação** | **Nunca confiar** nos parâmetros: validar tipos/limites/autorização |
| **Autorização do usuário** | A Lambda deve verificar **quem** pede (propagar identidade em `sessionAttributes`) |
| **Return of control** | Em vez de Lambda, devolve a **intenção** ao seu app (que executa) — útil para **confirmação humana** |
| **Ações destrutivas** | **Confirmação do usuário** antes de executar |

## 5. Amazon Bedrock AgentCore (infraestrutura para agentes)

O **AgentCore** é um conjunto de serviços para **implantar e operar agentes em produção**, **independente de framework** (Strands Agents, LangGraph, CrewAI, LlamaIndex, código próprio) e **de modelo** (Bedrock ou outros). Componentes (**de memória — confirmar nomes e disponibilidade**):

| Componente | Função |
|---|---|
| **Runtime** | Hospeda o agente/ferramentas **serverless**, com **isolamento por sessão** (microVM), execuções longas, suporte a **MCP/A2A** |
| **Gateway** | Converte **APIs/Lambdas/OpenAPI** em **ferramentas MCP** para agentes; **descoberta** de ferramentas |
| **Identity** | Gestão de **identidade e credenciais** do agente (OAuth, tokens, integração com IdPs); acesso a recursos **em nome do usuário** |
| **Memory** | **Memória de curto e longo prazo** gerenciada |
| **Observability** | Traces/métricas (**OpenTelemetry**/CloudWatch) do raciocínio e das ferramentas |
| **Code Interpreter** | **Sandbox** para executar código gerado |
| **Browser** | **Navegador gerenciado** para o agente operar páginas |
| **Policy/Evaluations** | Controles e avaliação de agentes (**confirmar**) |

| Opção | Quando |
|---|---|
| **Agents for Bedrock (gerenciado)** | Agente **declarativo**, rápido de montar, ecossistema Bedrock |
| **AgentCore + framework (Strands etc.)** | **Controle de código**, multi-modelo, produção com **isolamento e identidade** |
| **Seu próprio loop (Converse + tool use)** | Casos simples; **máximo controle** |

### 5.1 MCP (Model Context Protocol) em uma linha

**MCP** é um **protocolo aberto** que padroniza como **agentes descobrem e chamam ferramentas/dados** (servidor MCP expõe *tools*, *resources*, *prompts*). Benefício: **ferramentas reutilizáveis** entre agentes/IDEs. Riscos: **ferramentas não confiáveis**, **injeção via descrições/resultados**, **excesso de permissão**.

## 6. Orquestração e fluxos

| Ferramenta | Uso |
|---|---|
| **Bedrock Flows** | **Fluxos visuais** encadeando prompts, KBs, Lambdas, condições |
| **Step Functions** | **Orquestração determinística** com **chamadas ao Bedrock** (integração otimizada), **retries**, **aprovação humana** (callbacks), **Map** para lotes |
| **Lambda/Fargate + framework** | Lógica customizada |
| **EventBridge/SQS** | **Assíncrono/desacoplado** |

> **Regra de design**: use **fluxo determinístico** (Step Functions/Flows) para **processos conhecidos** e **agentes** só quando o **caminho não é previsível**. Agentes são **menos previsíveis, mais caros e mais difíceis de testar**.

## 7. Memória e estado

| Tipo | Como |
|---|---|
| **Janela de contexto** | Histórico enviado a cada chamada (limitado/custoso) |
| **Resumo** | Compactar conversas antigas |
| **Sessão (Agents/RAG)** | `sessionId` mantém contexto por tempo limitado (**TTL**) |
| **Memória de longo prazo** | **AgentCore Memory** ou **DynamoDB/vetores** (preferências, fatos) |
| **Privacidade** | **Minimizar** dados lembrados; **expiração**; direito de **apagar** |

## 8. Avaliação e testes

| Prática | Detalhe |
|---|---|
| **Conjunto dourado** | Perguntas + respostas/fontes esperadas |
| **Métricas RAG** | **Relevância do contexto**, **fidelidade (groundedness)**, **correção**, cobertura |
| **Model/RAG Evaluation (Bedrock)** | Avaliação automática (LLM-as-judge) e humana (**confirmar**) |
| **Testes de agente** | Trajetórias (ferramentas chamadas), **resultado final**, **casos adversariais** (prompt injection) |
| **Regressão** | Reexecutar a suíte a cada **mudança de prompt/modelo/chunking** |
| **Traces** | `enableTrace`, AgentCore Observability |

## 9. Custos e desempenho

| Fator | Dica |
|---|---|
| **OpenSearch Serverless** (OCUs mínimas) | Pode ter **custo fixo relevante**; avaliar **S3 Vectors/pgvector** (**confirmar custos**) |
| **Ingestão** | Embeddings por token processado |
| **Consultas** | Tokens do contexto recuperado |
| **Agentes** | Várias chamadas ao modelo por pergunta |
| **Latência** | Menos chamadas, **modelos menores**, **caching**, **streaming** |
| **Reranking** | Custo extra por consulta |

## 10. Erros comuns

- **RAG sem avaliar** (confiar no “parece bom”).
- **Chunking padrão** sem testes.
- **Sem controle de acesso por documento** (vazamento entre usuários).
- **Não sincronizar** a ingestão (conteúdo velho).
- **Agente para tudo** (onde um fluxo determinístico bastava).
- **Lambda de ação sem validação/autorização**.
- **Ações destrutivas sem confirmação**.
- **Sem limite de iterações/custo** do agente.
- **Memória guardando dados sensíveis** sem expiração.
- **Ferramentas MCP não confiáveis** com permissões amplas.
- **Misturar modelos de embedding** entre ingestão e consulta.

## 11. Troubleshooting

| Sintoma | Causa provável | Ação |
|---|---|---|
| `retrieve` devolve vazio | Ingestão não executada/falhou; filtro restritivo | Ver **ingestion job** e **status**; revisar filtro |
| Ingestão falha | Permissão S3/KMS/vector store; formato; limite | Ver `failureReasons`, IAM da **service role** |
| Respostas inventadas | Prompt permissivo/contexto fraco | Restringir ao contexto, aumentar qualidade da busca |
| Agente não chama a ferramenta | Descrição/schema ruim; instruções vagas | Melhorar **descrições** e exemplos; ver `trace` |
| Agente em loop/custo alto | Sem limite | Limitar passos; validar observações |
| Lambda de ação **não é invocada** | Falta **resource policy** | Permitir `bedrock.amazonaws.com` invocar |
| `AccessDenied` na KB | Role da KB sem acesso ao S3/modelo de embedding | Ajustar IAM/KMS |
| Resposta de outro tenant | Sem filtro por metadados/ACL | Filtros obrigatórios no servidor |

## 12. Resumo rápido

- **RAG** fundamenta respostas em **seus documentos**: **ingestão** (chunking → embeddings → vetores) + **consulta** (busca → prompt → resposta com **citações**).
- **Knowledge Bases**: conectores, chunking (**fixo/hierárquico/semântico/custom**), vector stores (**OpenSearch Serverless, pgvector, S3 Vectors…**), **`Retrieve`** × **`RetrieveAndGenerate`**, **filtros**, **híbrida**, **rerank**.
- **Agents**: instruções + **action groups (OpenAPI/function + Lambda)** + KB; **return of control** para confirmação.
- **AgentCore**: **Runtime, Gateway (MCP), Identity, Memory, Observability, Code Interpreter, Browser** para **agentes em produção**.
- **Determinístico (Step Functions/Flows) quando possível; agentes quando necessário**.
- **Segurança**: validar parâmetros, autorização por usuário, confirmação de ações, limites, ACL por documento.
- **Avaliar** sempre (golden set, groundedness, regressão).

**Respostas:**

1. Recuperar trechos de documentos relevantes e incluí-los no prompt para fundamentar a resposta, reduzindo alucinações e usando dados atualizados da empresa.
2. Retrieve devolve só os trechos; RetrieveAndGenerate também gera a resposta com citações usando um modelo.
3. Conjunto de ferramentas do agente, definidas por OpenAPI ou function schema e executadas por Lambda (ou devolvidas ao app).
4. Expor APIs, Lambdas e OpenAPI como ferramentas MCP para agentes, com descoberta e controle.
5. Quando o processo é conhecido e previsível; é mais barato, testável e determinístico.
6. Com filtros por metadados/ACL impostos no servidor, bases por tenant e verificação após a recuperação.
7. Porque o modelo pode gerar argumentos errados ou manipulados por prompt injection; sem validação e autorização, ações indevidas podem ocorrer.
