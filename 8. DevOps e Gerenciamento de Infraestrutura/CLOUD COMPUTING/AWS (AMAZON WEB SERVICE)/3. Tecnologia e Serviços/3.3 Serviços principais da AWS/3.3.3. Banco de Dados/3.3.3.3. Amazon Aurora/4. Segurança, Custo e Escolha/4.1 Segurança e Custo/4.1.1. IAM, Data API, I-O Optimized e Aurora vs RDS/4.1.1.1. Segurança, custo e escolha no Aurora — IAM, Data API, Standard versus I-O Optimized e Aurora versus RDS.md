### Segurança, custo e escolha no Aurora — IAM, Data API, Standard versus I/O-Optimized e Aurora versus RDS

> [!warning] Aviso
> Modelos de cobrança (Standard e I/O-Optimized), preços, Data API e opções de segurança evoluem. Nenhum valor numérico aqui é oficial. Confirme na documentação e na calculadora. Os comandos **não foram executados**.

Fechando o Aurora: **como proteger** o cluster (rede, criptografia, IAM, segredos), **como pagar** (instâncias, armazenamento, I/O e as duas configurações de cobrança) e **como decidir** entre Aurora, RDS e outras opções.

**Analogia:** é a decisão de **alugar um escritório**: a segurança é a portaria e os cofres; o custo é aluguel (instâncias) + condomínio (armazenamento) + taxa de uso de elevador (I/O, no modelo Standard) ou condomínio "tudo incluso" (I/O-Optimized); a escolha é saber se um escritório compartilhado básico (RDS) basta ou se precisa de um prédio corporativo (Aurora).

## Segurança no Aurora

| Camada | Prática |
|---|---|
| **Rede** | Subnets privadas, `PubliclyAccessible=false`, Security Group aceitando apenas o SG da aplicação |
| **Criptografia em repouso** | Definida **na criação do cluster** (KMS); cobre volume, backups, snapshots, réplicas e logs; clusters não criptografados exigem snapshot → cópia criptografada → restauração |
| **Criptografia em trânsito** | TLS; exija por parâmetro (`rds.force_ssl` no PostgreSQL; `require_secure_transport` no MySQL) |
| **IAM database authentication** | Token de 15 minutos em lugar de senha (MySQL e PostgreSQL) |
| **Senha master** | `--manage-master-user-password`: o Secrets Manager guarda e rotaciona |
| **RDS Proxy** | Pool + autenticação por IAM/Secrets Manager |
| **Auditoria** | Advanced Auditing (Aurora MySQL), pgAudit (PostgreSQL), **Database Activity Streams** (fluxo quase em tempo real via Kinesis, independente do DBA), logs no CloudWatch |
| **Proteção** | Deletion protection, backups, SCPs e AWS Config |
| **Rede entre regiões** | Global Database replica por backbone AWS criptografado |

### RDS Data API (HTTP)

Permite executar SQL por uma **API HTTPS** (sem driver nem conexões persistentes), autenticada por **IAM + Secrets Manager**. Útil para **Lambda** e aplicações serverless que não querem gerenciar conexões e VPC.

```bash
aws rds-data execute-statement \
  --resource-arn arn:aws:rds:sa-east-1:111122223333:cluster:app-sv2 \
  --secret-arn arn:aws:secretsmanager:sa-east-1:111122223333:secret:app-db \
  --database loja --sql "SELECT id, total FROM pedidos WHERE cliente_id = :c" \
  --parameters '[{"name":"c","value":{"stringValue":"C1001"}}]'
```

Limites: tamanho de resposta, latência maior que conexão direta e disponibilidade por engine/versão. Para alto volume, prefira RDS Proxy.

### Políticas e governança

```json
{
  "Effect": "Deny",
  "Action": ["rds:CreateDBCluster", "rds:RestoreDBClusterFromSnapshot"],
  "Resource": "*",
  "Condition": { "Bool": { "rds:StorageEncrypted": "false" } }
}
```

Combine com tags, Config rules e Security Hub (padrões de segurança para Aurora).

## Custo — o que compõe a conta

| Componente | Observação |
|---|---|
| **Instâncias** | Por hora: provisionadas (classe) ou **ACU-hora** (Serverless v2) |
| **Armazenamento** | Por GB-mês do volume do cluster (cresce sozinho) |
| **I/O** | **Standard:** por milhão de requisições de I/O. **I/O-Optimized:** sem cobrança de I/O, com preço maior de instância e armazenamento |
| **Backup** | Acima do tamanho do volume, por GB-mês |
| **Backtrack** | Por change records |
| **Global Database** | Replicação de I/O entre regiões e instâncias da secundária |
| **Transferência de dados** | Entre regiões e para a internet |
| **Outros** | Performance Insights acima do gratuito, Data API, Proxy (por vCPU), Database Activity Streams |

### Standard × I/O-Optimized

| Critério | **Aurora Standard** | **Aurora I/O-Optimized** |
|---|---|---|
| Cobrança de I/O | Sim (por requisição) | **Não** |
| Preço de instância/armazenamento | Menor | Maior (acréscimo percentual) |
| Melhor para | Cargas de I/O baixo a moderado | Cargas **intensivas em I/O** (quando I/O > ~25% da conta) |
| Troca | Pode alternar entre as configurações (com limite de frequência) | Idem |
| Previsibilidade | Custo varia com o I/O | **Previsível** |

Regra prática: se a fatura de I/O representa uma fração grande (a AWS cita algo em torno de um quarto) do custo do Aurora, avalie o I/O-Optimized. Use o Cost Explorer (`StorageIOUsage`) para decidir.

### Redução de custo

1. **Serverless v2** para cargas variáveis e dev/test (escala para baixo).
2. **Reserved Instances** para instâncias provisionadas estáveis (mesmo cluster, não Serverless).
3. Escolher **Graviton** (`g`) quando o engine suporta.
4. Retenção de backup e snapshots de acordo com o requisito real.
5. Desligar/excluir **clones** e ambientes não produtivos fora do expediente (Aurora permite *stop* do cluster por até 7 dias).
6. Otimizar consultas e índices (reduz I/O e CPU).

## Aurora × RDS × DynamoDB × Redshift: como escolher

| Necessidade | Escolha |
|---|---|
| OLTP relacional crítico, alta disponibilidade, muitas leituras | **Aurora** |
| OLTP relacional com cargas pequenas/estáveis e custo mínimo | **RDS** (MySQL/PostgreSQL/MariaDB) |
| Oracle ou SQL Server (licenciados) | **RDS** (ou RDS Custom) |
| Acesso por chave, escala massiva, latência de ms, serverless | **DynamoDB** |
| Análise de grandes volumes, BI, data warehouse | **Redshift** |
| Cache/estruturas em memória | **ElastiCache** |
| Escala variável com SQL | **Aurora Serverless v2** |
| DR multi-região com RPO de segundos | **Aurora Global Database** |

```
 Precisa de SQL relacional?
   ├─ Não → DynamoDB / DocumentDB / outros
   └─ Sim → Oracle/SQL Server? ─ Sim → RDS
                │ Não
                ├─ Carga pequena, estável, orçamento apertado → RDS MySQL/PostgreSQL
                └─ Alta disponibilidade, muitas réplicas, escala, Global → AURORA
```

## Checklist de migração para Aurora

1. Validar **compatibilidade** (versão, extensões, recursos) em ambiente de teste.
2. Migrar de RDS MySQL/PostgreSQL: **réplica Aurora** do RDS (promoção) ou **snapshot** restaurado como Aurora; de outros bancos: **DMS/SCT**.
3. Ajustar **parâmetros** e **drivers** (failover-aware).
4. Dimensionar writer/readers, definir **prioridades de failover**.
5. Configurar **backup, monitoramento** e alarmes.
6. Planejar corte com **mínimo downtime** e rollback.

## Exemplo prático

Decisão para uma API de pedidos: 2.000 transações/s no pico, 5 TB e crescimento de 20%/mês, clientes em três continentes.

- **Aurora PostgreSQL** com writer provisionado `r6g.2xlarge` e 3 readers (2 serverless v2), cluster **I/O-Optimized** após constatar que o I/O era ~35% do custo.
- **RDS Proxy** + **Data API** para funções Lambda de baixo volume.
- **Global Database** com secundárias em `us-east-1` e `eu-west-1`.
- **IAM auth** + Secrets Manager, KMS CMK, TLS obrigatório, Database Activity Streams para auditoria.
- **Reserved Instances** de 1 ano no writer; Savings Plans onde cabível.
- Orçamento e alarme de custo por tag `servico=pedidos`.

## Erros comuns e armadilhas

- **Criar o cluster sem criptografia** (não há como ligar depois).
- **Escolher Aurora por "ser melhor"** sem avaliar custo para cargas pequenas.
- **Manter Standard com I/O dominando a fatura** sem avaliar I/O-Optimized.
- **Comprar reservas para instâncias serverless** (não se aplicam da mesma forma).
- **Usar Data API para alto volume** em vez de RDS Proxy/conexões.
- **Esquecer de parar clusters de teste** (custo de instâncias e armazenamento).
- **Migrar sem validar extensões e comportamento** do PostgreSQL/MySQL.
- **Backups sem teste** e sem cópia entre contas.
- **Permissões IAM amplas** para `rds:*`.
- **Mistura de endpoints** (instância no lugar do cluster) na aplicação.

## 🧩 Quiz de Fixação

1. Qual a diferença entre Aurora Standard e I/O-Optimized e quando migrar para o segundo?
2. Para que serve a Data API do Aurora?
3. Cite dois cenários em que RDS é melhor escolha que Aurora.

**Respostas:**
1) No Standard paga-se por requisição de I/O, com instância e armazenamento mais baratos; no I/O-Optimized não há cobrança de I/O, mas o preço base é maior. Vale migrar quando o I/O representa uma parcela significativa da fatura (da ordem de um quarto) ou quando se quer custo previsível.
2) Executar SQL por uma API HTTPS autenticada por IAM e Secrets Manager, sem driver nem conexões persistentes, útil para Lambda e aplicações serverless de volume moderado.
3) Oracle ou SQL Server (engines licenciados), e cargas pequenas e estáveis em MySQL/PostgreSQL em que o custo menor do RDS compensa a ausência dos recursos avançados do Aurora.
