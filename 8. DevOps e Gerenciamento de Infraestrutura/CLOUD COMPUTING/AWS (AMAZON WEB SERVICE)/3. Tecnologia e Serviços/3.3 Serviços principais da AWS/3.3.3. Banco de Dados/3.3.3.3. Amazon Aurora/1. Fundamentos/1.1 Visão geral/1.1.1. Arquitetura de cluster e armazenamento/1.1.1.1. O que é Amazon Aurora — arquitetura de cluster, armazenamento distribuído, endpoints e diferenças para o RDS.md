### O que é Amazon Aurora — arquitetura de cluster, armazenamento distribuído, endpoints e diferenças para o RDS

> [!warning] Aviso
> Versões compatíveis, limites (tamanho máximo, número de réplicas), preços e recursos do Aurora mudam. Os números abaixo são ordens de grandeza. Confirme na documentação. Os comandos **não foram executados**.

O **Amazon Aurora** é um banco relacional **compatível com MySQL e PostgreSQL**, projetado pela AWS para a nuvem. Faz parte da família do RDS (mesmo console, mesma API `rds`, mesmo modelo gerenciado), mas tem **arquitetura própria**: a camada de **computação** (instâncias) é separada de uma camada de **armazenamento distribuído** compartilhada. Isso entrega mais desempenho, failover rápido e réplicas baratas.

**Analogia:** no RDS tradicional, cada instância tem seu **próprio disco** (e as réplicas copiam dados). No Aurora, todas as instâncias de um cluster **leem do mesmo grande armazém compartilhado**, replicado em seis cópias. A instância é só o "balcão de atendimento"; trocar de atendente é rápido porque o estoque não muda de lugar.

## Arquitetura de cluster

```
                         CLUSTER Aurora (um "banco" lógico)
   ┌─────────────────────────────────────────────────────────────────────┐
   │ Camada de computação                                                  │
   │   [ WRITER ]      [ READER 1 ]     [ READER 2 ] ... (até ~15)         │
   │       │                │                │                             │
   │ ─────────────── Camada de armazenamento compartilhada ───────────── │
   │   volume do cluster: blocos de 10 GB, 6 cópias em 3 AZs              │
   │   AZ-a: ██ ██     AZ-b: ██ ██     AZ-c: ██ ██                        │
   └─────────────────────────────────────────────────────────────────────┘
```

| Elemento | Descrição |
|---|---|
| **Cluster** | Conjunto de instâncias + um volume compartilhado |
| **Writer (primária)** | Única instância que aceita escritas |
| **Readers (réplicas Aurora)** | Instâncias de leitura que acessam o **mesmo volume** (atraso de réplica tipicamente de dezenas de ms) |
| **Volume do cluster** | Armazenamento distribuído, **cresce automaticamente** de 10 GiB até dezenas de TiB (até ~128 TiB; confirme), cobrado pelo que usa |
| **Cópias** | **6 cópias** dos dados em **3 AZs** (2 por AZ) |

### Quórum de armazenamento

- Escritas exigem confirmação de **4 de 6** cópias; leituras, **3 de 6**.
- Tolera a perda de **uma AZ inteira** sem perder disponibilidade de escrita/leitura e de **uma AZ + 1 nó** sem perder dados.
- O armazenamento se **autocura**: blocos danificados são reparados a partir das cópias saudáveis, em segundo plano.

### Logs como base ("o log é o banco")

A instância writer envia ao armazenamento apenas **registros de redo log**, e o armazenamento aplica as mudanças aos blocos. Resultado: menos tráfego de rede e I/O, **commit rápido** e recuperação de falha quase instantânea (sem reprocessar logs inteiros).

## Endpoints do cluster

| Endpoint | Aponta para | Uso |
|---|---|---|
| **Cluster (writer) endpoint** | Sempre o writer atual | Escritas e leituras que exigem o dado mais recente; segue o failover |
| **Reader endpoint** | Balanceia entre os readers (DNS round robin) | Leituras escaláveis |
| **Instance endpoints** | Uma instância específica | Diagnóstico, cargas dedicadas |
| **Custom endpoints** | Subconjunto de instâncias que você define | Separar relatórios (instâncias maiores) de leituras comuns |

```
 App (escrita) ──► meucluster.cluster-xxxx.sa-east-1.rds.amazonaws.com        → WRITER
 App (leitura) ──► meucluster.cluster-ro-xxxx.sa-east-1.rds.amazonaws.com     → READERS
```

Use **sempre** os endpoints do cluster; o failover muda quem é o writer.

## Aurora × RDS tradicional

| Critério | **Aurora** | **RDS (MySQL/PostgreSQL)** |
|---|---|---|
| Armazenamento | Distribuído, 6 cópias em 3 AZs, **autoexpansível** | EBS por instância, tamanho definido (autoscaling com limite) |
| Réplicas | Até ~15, compartilham o volume (lag baixo) | Até 5, replicação assíncrona com cópia dos dados |
| Failover | Tipicamente **dezenas de segundos** | 1-2 min (Multi-AZ instância) |
| Desempenho | Declarado até ~5× MySQL e ~3× PostgreSQL (benchmarks AWS; varia com a carga) | Padrão do engine |
| Backup | Contínuo, sem impacto, PITR | Snapshot diário + logs |
| Clonagem | Rápida (copy-on-write) | Restauração completa |
| Recursos próprios | Serverless v2, Global Database, Backtrack (MySQL), Parallel Query | — |
| Custo | Maior por instância; cobrança de I/O (Standard) ou I/O-Optimized | Mais barato em cargas pequenas |
| Licença/engines | Apenas MySQL e PostgreSQL compatíveis | MySQL, PostgreSQL, MariaDB, Oracle, SQL Server, Db2 |

Compatibilidade: aplicações MySQL/PostgreSQL funcionam com mudanças mínimas, mas nem toda extensão ou recurso existe; teste antes de migrar.

## Quando usar Aurora

- Cargas **OLTP críticas** com alta disponibilidade e muitas leituras.
- Necessidade de **muitas réplicas** com baixo lag.
- **Escala imprevisível** (Serverless v2).
- **DR multi-região** com RPO de segundos (Global Database).
- Migrar bancos comerciais (Oracle/SQL Server) para engine aberto com ferramentas de conversão (SCT/DMS).

Quando preferir RDS: engines Oracle/SQL Server/MariaDB, cargas pequenas e estáveis onde o custo importa, ou necessidade de compatibilidade fiel com versões específicas.

## Exemplo prático

```bash
# Criar o cluster Aurora PostgreSQL (somente o "banco"; as instâncias vêm depois)
aws rds create-db-cluster --db-cluster-identifier loja-aurora \
  --engine aurora-postgresql --engine-version 16.4 \
  --master-username adminloja --manage-master-user-password \
  --db-subnet-group-name sg-bd-prod --vpc-security-group-ids sg-0bd123 \
  --storage-encrypted --backup-retention-period 14 --deletion-protection

# Adicionar a instância writer e um reader em outra AZ
aws rds create-db-instance --db-instance-identifier loja-aurora-w1 \
  --db-cluster-identifier loja-aurora --engine aurora-postgresql --db-instance-class db.r6g.large
aws rds create-db-instance --db-instance-identifier loja-aurora-r1 \
  --db-cluster-identifier loja-aurora --engine aurora-postgresql --db-instance-class db.r6g.large \
  --availability-zone sa-east-1b

# Consultar endpoints e funções (writer/reader)
aws rds describe-db-clusters --db-cluster-identifier loja-aurora \
  --query 'DBClusters[0].{Writer:Endpoint,Reader:ReaderEndpoint,Membros:DBClusterMembers[].{Id:DBInstanceIdentifier,Writer:IsClusterWriter}}'
```

Explicação: diferente do RDS, primeiro cria-se o **cluster** e depois as **instâncias** que o compõem. Versões são ilustrativas.

## Dimensionando um cluster Aurora

```
              Aplicação
        ┌─────────┴──────────┐
   escrita│                 │leitura
        ▼                   ▼
 Cluster endpoint     Reader endpoint (balanceia)
        │                   │
   ┌────▼────┐   ┌─────────┴─────────┐
   │ Writer  │   │ Reader 1 │ Reader 2│  (até 15 réplicas)
   └────┬────┘   └────┬─────┴────┬────┘
        └─────────────┼──────────┘
        ┌─────────────▼────────────────────────┐
        │ Volume compartilhado (até 128 TiB)   │
        │ 6 cópias em 3 AZs · cresce de 10 GiB │
        └──────────────────────────────────────┘
```

A separação entre computação e armazenamento é a chave: adicionar um reader **não copia dados**, pois todos leem o mesmo volume. Por isso o failover costuma ser bem mais rápido que no RDS Multi-AZ clássico e o lag de réplica é tipicamente de milissegundos.

## Escolha da forma de capacidade

| Opção | Indicado para | Observação |
|---|---|---|
| Instâncias provisionadas (db.r*, db.t*) | Carga estável e previsível | Reserved Instances reduzem custo |
| Aurora Serverless v2 | Carga variável, dev/test, multi-tenant | Escala em ACUs, com mínimo e máximo configuráveis |
| Aurora I/O-Optimized | I/O muito alto (≈ >25% da conta) | Sem cobrança por I/O, preço maior de instância/armazenamento |
| Aurora Standard | I/O moderado | Cobra por milhão de requisições de I/O |
| Global Database | DR entre regiões, leitura global | Replicação por camada de storage, RPO tipicamente em segundos |

> [!warning] Valores, limites e preços mudam; os exemplos deste material não foram executados. Verifique limites de réplicas, tamanhos e preços vigentes na documentação.

### Árvore de decisão rápida

```
Precisa de banco relacional MySQL/PostgreSQL gerenciado?
├─ Carga pequena, sem exigência de réplicas rápidas ─► RDS comum
└─ Precisa de >5 réplicas, failover rápido, storage elástico?
      ├─ Carga imprevisível ─► Aurora Serverless v2
      ├─ Carga estável ─────► Aurora provisionado (+ RIs)
      └─ DR multi-região ───► Aurora Global Database
```

## CLI comentado

```bash
# Cria o cluster (storage compartilhado), ainda sem instâncias
aws rds create-db-cluster --db-cluster-identifier meu-aurora \
  --engine aurora-postgresql --master-username admin \
  --manage-master-user-password        # senha gerenciada no Secrets Manager

# Adiciona a instância writer (a primeira vira writer)
aws rds create-db-instance --db-instance-identifier meu-aurora-1 \
  --db-cluster-identifier meu-aurora --engine aurora-postgresql \
  --db-instance-class db.r6g.large

# Adiciona um reader em outra AZ
aws rds create-db-instance --db-instance-identifier meu-aurora-2 \
  --db-cluster-identifier meu-aurora --engine aurora-postgresql \
  --db-instance-class db.r6g.large

# Testa o failover (promove um reader)
aws rds failover-db-cluster --db-cluster-identifier meu-aurora
```

## Troubleshooting

| Sintoma | Causa provável | Ação |
|---|---|---|
| Leituras não balanceiam | App usa cluster endpoint ou conexões longas fixas | Usar reader endpoint e pool com reconexão/DNS curto |
| Failover lento percebido | Cache DNS da aplicação | Reduzir TTL, usar RDS Proxy |
| Conta de I/O alta | Consultas sem índice, scans | Analisar Performance Insights; avaliar I/O-Optimized |
| Replica lag alto | Writer sobrecarregado ou consultas longas no reader | Escalar writer/readers, otimizar consultas |

## Custo

Quatro parcelas: **instâncias** (hora ou ACU), **armazenamento** (GB-mês realmente usado), **I/O** (no modo Standard) e **backup acima do tamanho do cluster** e transferências. Readers extras custam como instâncias completas, mas não duplicam armazenamento, o que torna o escalonamento de leitura barato em relação a manter vários bancos independentes.

## Erros comuns e armadilhas

- **Usar o endpoint de instância** na aplicação: o failover quebra a conexão.
- **Esperar escrita nos readers:** só o writer escreve (exceto *write forwarding* em Global/cluster, recurso específico).
- **Achar que 6 cópias dispensam backup:** erro lógico e exclusão são replicados.
- **Ignorar o custo de I/O** no modo Standard (cargas intensas).
- **Assumir 100% de compatibilidade** com MySQL/PostgreSQL de comunidade.
- **Dimensionar só o writer:** os readers precisam ter capacidade para assumir em failover (prioridade de promoção).
- **Misturar classes muito diferentes** sem definir a *failover priority*.
- **Esquecer que o armazenamento só cresce** de forma automática, mas **libera espaço apenas em certas condições** (verifique o comportamento da versão).

## 🧩 Quiz de Fixação

1. O que diferencia a camada de armazenamento do Aurora da do RDS tradicional?
2. Qual endpoint usar para leituras escaláveis e qual para escritas?
3. Quantas cópias dos dados existem e em quantas AZs?

**Respostas:**
1) Um volume de cluster distribuído e compartilhado por todas as instâncias, que cresce automaticamente e guarda 6 cópias em 3 AZs, enquanto no RDS cada instância tem seu próprio volume EBS.
2) Reader endpoint para leituras (balanceia entre os readers) e cluster (writer) endpoint para escritas e leituras que exigem o dado mais recente.
3) Seis cópias, em três Availability Zones (duas por AZ).

**Questões complementares:**

4. Por que adicionar um reader no Aurora é rápido e não duplica armazenamento?
5. Quando considerar Aurora I/O-Optimized?
6. Como reduzir o impacto do failover percebido pela aplicação?

**Respostas das questões complementares:**
4) Porque computação e armazenamento são separados: todos os nós leem o mesmo volume compartilhado, então o novo reader só precisa subir a instância, sem copiar dados.
5) Quando o custo de I/O no modo Standard é alto (aproximadamente mais de 25% da conta), pois o I/O-Optimized elimina a cobrança por requisição em troca de preço maior de instância e armazenamento.
6) Reduzindo o TTL de DNS, usando reconexão automática e RDS Proxy, e mantendo pelo menos um reader em outra AZ para promoção rápida.
