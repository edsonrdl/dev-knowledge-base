### Aurora Global Database a fundo — replicação por armazenamento, switchover, failover, write forwarding, RPO e RTO

> [!warning] Aviso
> Limites de regiões secundárias, métricas, parâmetros de RPO, comportamento de failover gerenciado, write forwarding e preços do Global Database mudam. **Confirme na documentação e teste o failover no seu ambiente.** Os comandos **não foram executados**.

O **Aurora Global Database** estende um cluster Aurora para **várias regiões da AWS**: uma região **primária** que aceita escritas e até **cinco regiões secundárias** que servem **leituras locais** e podem assumir como primária em um desastre. A diferença para uma réplica entre regiões "comum" é a **replicação em nível de armazenamento**: dedicada, sem consumir o motor do banco, com lag tipicamente **menor que 1 segundo**. Esta nota detalha como funciona, as operações de **switchover** e **failover**, o **write forwarding**, os conceitos de **RPO/RTO**, o custo e as arquiteturas.

**Analogia:** é uma **rede de arquivos espelhados**: a matriz (primária) registra tudo e um malote automático (replicação do armazenamento) copia cada alteração para as filiais (secundárias) em menos de um segundo. Cada filial consulta o seu arquivo local rapidamente. Se a matriz cair, uma filial é promovida a nova matriz.

## Arquitetura

```
 Região primária (sa-east-1)                        Região secundária (us-east-1)
 ┌──────────────────────────────┐   replicação de   ┌──────────────────────────────┐
 │ Cluster primário             │   armazenamento   │ Cluster secundário (somente  │
 │  WRITER + até 15 readers     │ ═══ (< 1 s) ═══►  │ leitura): até 16 readers     │
 │  Volume do cluster           │   dedicada        │  Volume do cluster (réplica) │
 └──────────────────────────────┘                   └──────────────────────────────┘
        escrita + leitura                                  leitura local (baixa latência)
```

| Componente | Descrição |
|---|---|
| **Global cluster** | Recurso lógico que agrupa um cluster **primário** e os **secundários** |
| **Cluster primário** | Aceita escritas; tem writer e readers |
| **Clusters secundários** | Somente leitura; em até 5 regiões; cada um com até 16 readers (confirme) |
| **Replicação** | Feita pela camada de **armazenamento**, não pela replicação do engine (binlog/WAL); **não usa CPU do writer** de forma significativa |
| **Cluster secundário "headless"** | Sem instâncias (somente volume): custo mínimo de DR; para ativar, adicione instâncias ou promova |
| **Criptografia** | Cada região usa sua própria chave KMS |

## Replicação e lag

| Aspecto | Detalhe |
|---|---|
| **Lag típico** | Menos de **1 segundo** entre regiões (varia com a distância, a taxa de escrita e a rede) |
| **Direção** | Primária → secundárias (unidirecional) |
| **Consistência** | Leituras na secundária são **eventualmente consistentes** em relação à primária |
| **Métricas** | `AuroraGlobalDBReplicationLag` (ms), `AuroraGlobalDBProgressLag`, `AuroraGlobalDBRPOLag`, `AuroraGlobalDBDataTransferBytes`, `AuroraGlobalDBReplicatedWriteIO` |
| **Controle de RPO** (Aurora PostgreSQL) | Parâmetro `rds.global_db_rpo` limita o atraso máximo tolerado; se o lag excede, o writer **suspende commits** até a secundária alcançar (protege o RPO ao custo de disponibilidade de escrita) |

Alarme essencial: `AuroraGlobalDBReplicationLag` acima do seu RPO (por exemplo > 5 s por 5 min).

## Operações: switchover e failover

| Operação | Quando | Perda de dados | Resultado |
|---|---|---|---|
| **Switchover** (planejado) | Manutenção, teste de DR, mover o primário para perto dos usuários | **Nenhuma** (aguarda a sincronização) | A secundária vira primária e a antiga primária vira secundária (a topologia é preservada) |
| **Failover** (não planejado) | Falha ou indisponibilidade da região primária | **Possível** (transações ainda não replicadas, até o RPO) | A secundária é **promovida**; o cluster antigo é desanexado e precisa ser recriado/ressincronizado quando a região volta |
| **Detach / remove** | Separar uma secundária e torná-la cluster independente | — | Vira um cluster regional autônomo |

```
 SWITCHOVER (planejado):  aguarda lag zero → troca de papéis → antigo primário vira secundário (sem perda)
 FAILOVER (desastre):     promove a secundária → antigo primário fica órfão (recria depois)
```

```bash
# Criar o global database a partir de um cluster existente e adicionar a secundária
aws rds create-global-cluster --global-cluster-identifier loja-global \
  --source-db-cluster-identifier arn:aws:rds:sa-east-1:111122223333:cluster:loja-aurora
aws rds create-db-cluster --region us-east-1 --db-cluster-identifier loja-aurora-us \
  --global-cluster-identifier loja-global --engine aurora-postgresql --engine-version 16.4 \
  --db-subnet-group-name sg-bd-us --vpc-security-group-ids sg-0us123 --storage-encrypted --kms-key-id alias/aurora-us
aws rds create-db-instance --region us-east-1 --db-instance-identifier loja-aurora-us-r1 \
  --db-cluster-identifier loja-aurora-us --engine aurora-postgresql --db-instance-class db.r6g.large

# Switchover planejado (sem perda): leva o primário para us-east-1
aws rds switchover-global-cluster --global-cluster-identifier loja-global \
  --target-db-cluster-identifier arn:aws:rds:us-east-1:111122223333:cluster:loja-aurora-us

# Failover não planejado (pode haver perda): promove a secundária
aws rds failover-global-cluster --global-cluster-identifier loja-global \
  --target-db-cluster-identifier arn:aws:rds:us-east-1:111122223333:cluster:loja-aurora-us --allow-data-loss
```

(Os nomes dos parâmetros podem variar conforme a versão da CLI/API — confirme.)

## RPO e RTO

| Conceito | No Global Database |
|---|---|
| **RPO** (quanto de dado se pode perder) | Normalmente **< 1 s** (lag de replicação); pode ser **limitado** por `rds.global_db_rpo` no PostgreSQL |
| **RTO** (tempo para voltar) | Failover entre regiões em **cerca de 1 minuto ou pouco mais** para o banco; o RTO total inclui **detectar, decidir, promover e redirecionar a aplicação** |
| **Switchover** | RPO = 0; RTO de poucos minutos (conforme o cluster e a rede) |

Atenção: o RTO real depende da **aplicação** (DNS, caches, pools de conexões, configuração de endpoints por região). O banco é só uma parte; ensaie o fluxo completo.

## Write forwarding

Permite que clientes conectados a uma **secundária** executem **escritas**; o Aurora **encaminha** a operação ao cluster primário e devolve o resultado.

```
 App na região secundária ──escrita──► reader endpoint (secundária) ──forward──► WRITER (primária)
                                    ◄── resultado ◄──
```

| Característica | Detalhe |
|---|---|
| **Disponibilidade** | Aurora MySQL e Aurora PostgreSQL (confirme versões) |
| **Consistência** | Controlada por nível: `EVENTUAL`, `SESSION`, `GLOBAL` (o nível global espera a replicação para ler o que se escreveu; maior latência) |
| **Latência** | Escrita paga o **round trip entre regiões**; leitura continua local |
| **Uso** | Aplicações já ativas em várias regiões que precisam escrever sem mudar a lógica; não substitui multi-primário |
| **Limitações** | Nem todas as operações são encaminhadas (DDL, transações com certos recursos); sujeito a latência e a throughput |
| **Ativação** | No cluster secundário (`--enable-global-write-forwarding`) e por sessão/parâmetro |

Não é um banco **multi-primário**: há um único writer global. Para escrita ativa-ativa real em várias regiões, considere DynamoDB Global Tables ou modelos por região.

## Endpoints e roteamento da aplicação

| Elemento | Uso |
|---|---|
| **Cluster endpoint de cada região** | Escrita (primária) e leitura local (secundária) |
| **Reader endpoint local** | Leituras locais de baixa latência |
| **Endpoint global do cluster** (recurso mais recente; confirme) | Um nome que segue o primário atual, simplificando o failover |
| **Route 53** | Registro com failover/latência para o endpoint certo; health checks da aplicação |
| **Secrets e parâmetros por região** | Credenciais (Secrets Manager replicado), parameter groups |

Boa prática: a aplicação em cada região lê do **reader local** e escreve no **endpoint do primário** (ou usa write forwarding); em failover, atualiza-se o apontamento de escrita (DNS/Parameter Store) e, se necessário, escala-se a secundária.

## Custos

| Componente | Observação |
|---|---|
| **Instâncias da secundária** | Cobradas como qualquer instância (use *headless* ou Serverless v2 para reduzir) |
| **Armazenamento** | Pago em cada região |
| **Replicação de I/O** (*replicated write I/Os*) | Escritas replicadas cobradas à parte (Standard) |
| **Transferência entre regiões** | Cobrada por GB |
| **Write forwarding, Proxy, backups** | Itens adicionais |

Dicas: manter a secundária **dimensionada para o necessário** (leitura local) com capacidade de crescer no failover (Serverless v2 ou Auto Scaling de readers); avaliar I/O-Optimized quando a replicação de I/O dominar.

## Quando usar Global Database × alternativas

| Necessidade | Opção |
|---|---|
| Leitura de baixa latência em várias regiões + DR com RPO de segundos | **Aurora Global Database** |
| DR regional mais barato, RPO de minutos | Réplica de leitura entre regiões (RDS/Aurora) ou snapshots copiados |
| Escrita local em várias regiões | **DynamoDB Global Tables** |
| Backup e recuperação | AWS Backup (RPO maior) |
| Cache global | ElastiCache Global Datastore |

## Arquiteturas

1. **Primário + leitura global:** escrita na região principal; usuários globais leem do reader local; relatórios na secundária.
2. **DR ativo-passivo:** secundária *headless* ou pequena; failover por runbook testado trimestralmente.
3. **Follow-the-sun:** switchover planejado para a região do horário comercial, reduzindo a latência de escrita.
4. **Migração entre regiões:** criar a secundária na região-alvo e fazer o switchover.
5. **Ativo-ativo aparente:** write forwarding nas regiões secundárias (com latência de escrita).

## Exemplo prático

E-commerce com operação no Brasil e vendas na Europa:

1. Primário em `sa-east-1` (Aurora PostgreSQL, writer `r6g.2xlarge` + 2 readers).
2. Secundária em `eu-west-1` com 2 readers **serverless v2** (min 2 / max 32 ACU) para leituras de catálogo e carrinho.
3. `rds.global_db_rpo = 10` para garantir RPO máximo de 10 s (aceitando suspender commits se a replicação atrasar).
4. Write forwarding habilitado na Europa para pedidos de baixa frequência (`SESSION`), e filas locais para picos.
5. Route 53 por latência para o front-end; health checks e runbook de failover.
6. Teste semestral de **switchover** (sem perda) e anual de **failover** (com perda aceitável), medindo o RTO fim a fim (banco + DNS + caches).
7. Alarmes: `AuroraGlobalDBReplicationLag` > 5 s, custo de `ReplicatedWriteIO`, `ACUUtilization`.

## Erros comuns e armadilhas

- **Confundir Global Database com multi-primário:** há um único writer.
- **Achar que substitui backup:** exclusões e corrupções replicam.
- **Não testar failover/switchover** e descobrir que a aplicação não troca de endpoint.
- **Secundária subdimensionada** que não aguenta a carga após o failover.
- **Ignorar o custo de `ReplicatedWriteIO` e da transferência entre regiões.**
- **Usar failover quando o switchover bastava** (perda de dados desnecessária).
- **Esquecer chaves KMS, Secrets e parameter groups por região.**
- **Não monitorar o lag** nem definir um RPO máximo (`rds.global_db_rpo`).
- **Write forwarding em cargas intensas de escrita:** latência de ida e volta entre regiões.
- **Não ter plano para reconstruir o antigo primário** após um failover.

## 🧩 Quiz de Fixação

1. Qual a diferença entre switchover e failover no Global Database?
2. Como a replicação do Global Database difere de uma réplica de leitura entre regiões comum?
3. O que o write forwarding faz e quais seus limites?
4. O que o parâmetro `rds.global_db_rpo` controla no Aurora PostgreSQL?

**Respostas:**
1) O switchover é planejado, aguarda a sincronização, não perde dados e troca os papéis preservando a topologia; o failover é uma promoção de emergência da secundária que pode perder transações ainda não replicadas e deixa o antigo primário desanexado.
2) A do Global Database é feita pela camada de armazenamento, de forma dedicada e sem usar o engine, com lag normalmente menor que 1 s; a réplica comum usa a replicação do engine (binlog/WAL), com mais lag e maior carga na primária.
3) Encaminha as escritas feitas em uma secundária para o writer da primária, devolvendo o resultado; tem latência de ida e volta entre regiões, níveis de consistência (eventual, sessão, global) e restrições de operações. Não é multi-primário.
4) Limita o atraso máximo tolerado de replicação (RPO); se o lag ultrapassar o valor, o writer suspende commits até a secundária alcançar, preservando o RPO ao custo de disponibilidade de escrita.
