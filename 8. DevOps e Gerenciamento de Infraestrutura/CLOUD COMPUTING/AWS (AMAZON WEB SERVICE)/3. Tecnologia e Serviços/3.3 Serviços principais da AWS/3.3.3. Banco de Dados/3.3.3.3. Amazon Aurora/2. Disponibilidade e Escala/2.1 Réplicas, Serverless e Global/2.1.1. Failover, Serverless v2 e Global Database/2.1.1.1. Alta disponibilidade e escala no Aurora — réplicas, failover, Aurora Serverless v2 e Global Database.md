### Alta disponibilidade e escala no Aurora — réplicas, failover, Aurora Serverless v2 e Global Database

> [!warning] Aviso
> Tempos de failover, limites de ACU, comportamento de pausa do Serverless v2, limites do Global Database e preços mudam. Os números são ordens de grandeza. Confirme na documentação. Os comandos **não foram executados**.

O Aurora entrega disponibilidade e escala em **três níveis**: dentro do cluster (**réplicas e failover**), na **capacidade de computação** (**Serverless v2**) e entre **regiões** (**Global Database**). Entender quando cada um se aplica é o núcleo do desenho de arquiteturas com Aurora.

**Analogia:** o cluster é uma **equipe de atendimento** com um caixa (writer) e vários atendentes de consulta (readers) que usam o mesmo arquivo. O Serverless v2 é a **equipe elástica** que chama mais atendentes nos picos e os dispensa depois. O Global Database é uma **filial em outro país** com uma cópia quase em tempo real do arquivo.

## Réplicas Aurora e failover

| Característica | Detalhe |
|---|---|
| **Quantidade** | Até ~15 réplicas Aurora por cluster |
| **Replicação** | Compartilham o volume; o lag normalmente é de dezenas de ms |
| **Distribuição** | Em até 3 AZs (e várias subnets do DB subnet group) |
| **Failover** | Se o writer falha, o Aurora **promove uma réplica** (por prioridade) e atualiza o cluster endpoint; tipicamente **dezenas de segundos** |
| **Sem réplicas** | Se não há reader, o Aurora cria uma nova instância writer (demora mais) |
| **Prioridade de promoção** | Valor 0 a 15 por instância (0 = preferida) |

```
 ANTES:  WRITER (AZ-a)   READER 1 (AZ-b) prio 0   READER 2 (AZ-c) prio 1
 FALHA:  writer cai ───► Aurora promove READER 1 ───► cluster endpoint passa a apontar para ele
```

Boas práticas:

- Pelo menos **uma réplica em outra AZ**, com classe igual ou maior que o writer.
- Aplicação com **retry** e **driver com reconhecimento do cluster** (AWS JDBC/Python wrapper, que detecta o writer rapidamente).
- Teste de resiliência com **failover manual**.

```bash
# Testar failover (promove outra instância)
aws rds failover-db-cluster --db-cluster-identifier loja-aurora \
  --target-db-instance-identifier loja-aurora-r1

# Auto Scaling de réplicas pela métrica de CPU (Application Auto Scaling)
aws application-autoscaling register-scalable-target --service-namespace rds \
  --resource-id cluster:loja-aurora --scalable-dimension rds:cluster:ReadReplicaCount \
  --min-capacity 1 --max-capacity 8
aws application-autoscaling put-scaling-policy --service-namespace rds \
  --resource-id cluster:loja-aurora --scalable-dimension rds:cluster:ReadReplicaCount \
  --policy-name cpu-readers --policy-type TargetTrackingScaling \
  --target-tracking-scaling-policy-configuration \
  '{"TargetValue":60.0,"PredefinedMetricSpecification":{"PredefinedMetricType":"RDSReaderAverageCPUUtilization"}}'
```

## Aurora Serverless v2

Aurora com **capacidade de computação que escala automaticamente** em frações finas, medida em **ACUs** (Aurora Capacity Units; 1 ACU ≈ 2 GiB de memória com CPU e rede proporcionais).

```
 Carga baixa:  [writer 0,5–2 ACU]                       ← paga pouco
 Pico:         [writer 32 ACU] (escala em segundos)      ← sem reiniciar nem trocar de instância
```

| Característica | Detalhe |
|---|---|
| **Escala** | Contínua, em incrementos pequenos, em segundos, **sem interromper conexões** |
| **Configuração** | `MinCapacity` e `MaxCapacity` (ACUs) por cluster |
| **Mistura** | Instâncias **provisionadas e serverless v2** no mesmo cluster (ex.: writer provisionado e readers serverless) |
| **Recursos** | Multi-AZ, réplicas, Global Database e a maioria dos recursos do Aurora provisionado |
| **Pausa em zero** | Versões recentes permitem **escalar a 0 ACU** com pausa automática após inatividade (retomada leva alguns segundos); confirme disponibilidade e versões |
| **Cobrança** | Por ACU-hora, por segundo |
| **Quando usar** | Cargas variáveis/imprevisíveis, multi-tenant, dev/test, novos produtos |

Comparação com v1: o **Serverless v1** (legado, com pausas e escala em passos maiores) está sendo descontinuado em favor do v2; para projetos novos use v2.

```bash
# Cluster com capacidade serverless v2 (0,5 a 16 ACUs)
aws rds create-db-cluster --db-cluster-identifier app-sv2 --engine aurora-postgresql \
  --serverless-v2-scaling-configuration MinCapacity=0.5,MaxCapacity=16 \
  --master-username admin --manage-master-user-password \
  --db-subnet-group-name sg-bd-prod --vpc-security-group-ids sg-0bd123 --storage-encrypted
aws rds create-db-instance --db-instance-identifier app-sv2-w1 --db-cluster-identifier app-sv2 \
  --engine aurora-postgresql --db-instance-class db.serverless
# db.serverless é a "classe" das instâncias serverless v2
```

Regra de dimensionamento: o `MinCapacity` deve ser suficiente para o **cache de memória** (buffer pool) e para evitar partidas a frio; capacidade mínima muito baixa pode causar latência ao subir.

## Aurora Global Database

Um cluster **primário** em uma região e até **cinco regiões secundárias** (somente leitura), com replicação em nível de **armazenamento** (não pelo log do engine).

```
 Região primária (sa-east-1)                       Região secundária (us-east-1)
  WRITER + readers ──► volume ══ replicação de armazenamento (lag < 1 s típico) ══► readers (leitura)
                                            ▲ failover/switchover: promove a secundária
```

| Característica | Detalhe |
|---|---|
| **RPO** | Em geral **< 1 segundo** de lag |
| **RTO** | Failover entre regiões em **cerca de um minuto** (managed failover/switchover; confirme) |
| **Leituras locais** | Usuários distantes leem da região mais próxima, com baixa latência |
| **Escrita** | Apenas na primária; **write forwarding** permite que secundárias recebam escritas e as encaminhem à primária |
| **Switchover planejado** | Troca de região sem perda de dados (manutenção, DR test) |
| **Failover não planejado** | Promove a secundária (pode perder transações de últimos instantes) |
| **Custo** | Instâncias na secundária + replicação de I/O + transferência entre regiões |

Boas práticas: monitorar `AuroraGlobalDBReplicationLag`, testar switchover regularmente, manter capacidade na secundária para assumir toda a carga e preparar a aplicação (DNS/Route 53, secrets e parâmetros por região). Veja o roteamento em [[8. DevOps e Gerenciamento de Infraestrutura/CLOUD COMPUTING/AWS (AMAZON WEB SERVICE)/3. Tecnologia e Serviços/3.3 Serviços principais da AWS/3.3.4. Rede/3.3.4.5. Amazon Route 53/0 Amazon Route 53 (Tópicos )|Amazon Route 53]].

```bash
aws rds create-global-cluster --global-cluster-identifier loja-global \
  --source-db-cluster-identifier arn:aws:rds:sa-east-1:111122223333:cluster:loja-aurora

# Planejado: trocar a região primária sem perda de dados
aws rds switchover-global-cluster --global-cluster-identifier loja-global \
  --target-db-cluster-identifier arn:aws:rds:us-east-1:111122223333:cluster:loja-aurora-dr
```

## Escolha de estratégia

| Necessidade | Estratégia |
|---|---|
| Alta disponibilidade na região | Reader(s) em outra AZ + failover |
| Escalar leituras | Mais readers + Auto Scaling + reader endpoint |
| Carga muito variável | Serverless v2 |
| DR entre regiões, RPO de segundos | Global Database |
| Relatórios pesados | Custom endpoint com readers maiores / Parallel Query |
| Muitas conexões (Lambda) | RDS Proxy |

## Exemplo prático

SaaS multi-tenant com picos imprevisíveis e clientes na Europa e no Brasil:

1. Cluster **Aurora PostgreSQL**: writer provisionado `db.r6g.xlarge` e 2 readers **serverless v2** (2–32 ACU) em AZs distintas.
2. **Auto Scaling** de readers e **RDS Proxy** para as funções Lambda.
3. **Global Database** com secundária em `eu-west-1` para leituras locais e DR (RPO < 1 s).
4. Drivers com failover rápido, retry e endpoints do cluster.
5. Exercício trimestral de **switchover** e medição do RTO real; alarmes em lag de réplica e ACU.
6. Custom endpoint `relatorios` para as instâncias maiores de BI.

## Escolhendo a estratégia de escala e resiliência

| Necessidade | Recurso | Detalhe |
|---|---|---|
| Failover rápido em uma região | Réplica Aurora em outra AZ com prioridade (tier 0-15) | Promoção da réplica de maior prioridade |
| Escalar leitura | Até 15 réplicas + reader endpoint | Auto Scaling de réplicas via Application Auto Scaling |
| Carga variável | Serverless v2 (ACUs min/max) | Escala em incrementos finos, sem reiniciar |
| DR/leitura em outra região | Global Database | Replicação na camada de storage, RPO em segundos |
| Reduzir custo de I/O | I/O-Optimized | Sem cobrança por I/O |

> [!warning] Valores, limites e preços mudam; os exemplos deste material não foram executados. Limites de ACU, de réplicas e de regiões secundárias mudam; consulte a documentação.

```
 Região primária                    Região secundária
 ┌─────────────────────┐  storage   ┌─────────────────────┐
 │ Writer + N readers  │ ─────────► │ Somente readers      │
 │ volume compartilhado│ replicação │ (promovível ao DR)   │
 └─────────────────────┘  (~s)      └─────────────────────┘
   failover regional: "switchover" planejado (sem perda) ou "failover" (RPO>0)
```

### Árvore de decisão

```
O que quero proteger/escalar?
├─ Queda de AZ ─► réplica em outra AZ + prioridade de failover
├─ Leitura pesada ─► mais readers + Auto Scaling
├─ Carga com picos e vales ─► Serverless v2
├─ Queda regional / usuários globais ─► Global Database
└─ Mix: writer provisionado + readers Serverless v2 (custo/escala)
```

## Dimensionando o Serverless v2

1. Defina **ACU mínima** pelo working set de memória (o buffer cache é perdido se escalar demais para baixo).
2. Defina a **máxima** pelo teto aceitável de custo.
3. Monitore `ServerlessDatabaseCapacity` e `ACUUtilization`.
4. Combine com readers provisionados se a carga base for estável.

## CLI comentado

```bash
# Configura limites do Serverless v2
aws rds modify-db-cluster --db-cluster-identifier meu-aurora \
  --serverless-v2-scaling-configuration MinCapacity=2,MaxCapacity=32

# Instância Serverless v2 (classe db.serverless)
aws rds create-db-instance --db-instance-identifier meu-aurora-sv2 \
  --db-cluster-identifier meu-aurora --engine aurora-postgresql \
  --db-instance-class db.serverless

# Auto Scaling de réplicas por CPU
aws application-autoscaling register-scalable-target --service-namespace rds \
  --resource-id cluster:meu-aurora --scalable-dimension rds:cluster:ReadReplicaCount \
  --min-capacity 1 --max-capacity 5

# Switchover planejado da Global Database
aws rds switchover-global-cluster --global-cluster-identifier meu-global \
  --target-db-cluster-identifier <ARN_CLUSTER_SECUNDARIO>
```

## Troubleshooting

| Sintoma | Causa provável | Ação |
|---|---|---|
| Latência após escalar para baixo | Cache frio com ACU mínima baixa | Subir ACU mínima |
| Failover escolheu réplica menor | Prioridade igual/errada | Ajustar `PromotionTier` |
| Lag na região secundária | Pico de escrita / rede | Monitorar `AuroraGlobalDBReplicationLag` |
| Conta alta no Serverless | ACU máxima alta, consultas ineficientes | Limitar e otimizar |

## Custo

Serverless v2 cobra por ACU-hora (escala contínua); Global Database cobra instâncias na secundária, replicação de I/O e transferência entre regiões. Mantenha somente as réplicas que a carga exige.

## Erros comuns e armadilhas

- **Nenhuma réplica em outra AZ:** o failover demora e há indisponibilidade maior.
- **Aplicação cacheando DNS ou usando endpoints de instância.**
- **MinCapacity do Serverless v2 muito baixo** para o working set: latência e cache frio.
- **MaxCapacity baixo demais:** throttling em picos.
- **Tratar o Global Database como backup:** exclusões e corrupção replicam.
- **Escrever em duas regiões** sem usar write forwarding/estratégia: não é multi-master.
- **Não testar failover/switchover.**
- **Classes de réplica menores que o writer:** no failover a promovida não aguenta a carga.
- **Ignorar o custo da secundária** (instâncias e I/O).

## 🧩 Quiz de Fixação

1. O que acontece quando o writer de um cluster Aurora falha e há réplicas?
2. O que é uma ACU e para que serve o Serverless v2?
3. Quais as diferenças entre failover e switchover no Global Database?

**Respostas:**
1) O Aurora promove uma réplica (conforme a prioridade) a writer e atualiza o cluster endpoint, normalmente em dezenas de segundos; a aplicação precisa reconectar.
2) ACU (Aurora Capacity Unit) é a unidade de capacidade (cerca de 2 GiB de memória com CPU/rede proporcionais); o Serverless v2 escala a computação automaticamente entre um mínimo e um máximo de ACUs, cobrando por uso.
3) Switchover é uma troca planejada de região primária sem perda de dados; failover é a promoção não planejada da secundária após uma falha, que pode perder transações dos últimos instantes.

**Questões complementares:**

4. Para que serve a prioridade (tier) de uma réplica Aurora?
5. Por que não configurar ACU mínima baixa demais no Serverless v2?
6. Qual a diferença entre switchover e failover em Global Database?

**Respostas das questões complementares:**
4) Define qual réplica será promovida a writer em um failover (menor número = maior prioridade).
5) Escalar para baixo demais descarta o buffer cache; quando a carga volta, há latência por cache frio.
6) Switchover é planejado, sem perda de dados; failover é emergencial e pode ter RPO maior que zero.
