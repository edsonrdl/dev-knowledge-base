### Backup, clones e Backtrack no Aurora — backup contínuo, PITR, clonagem rápida, snapshots e exportação

> [!warning] Aviso
> Janelas de retenção, disponibilidade do Backtrack (somente Aurora MySQL), limites de clonagem e formatos de exportação mudam. Confirme na documentação. Os comandos **não foram executados**.

A arquitetura de armazenamento distribuído do Aurora permite recursos de dados que bancos tradicionais não têm: **backup contínuo sem impacto**, **clonagem em minutos sem copiar dados**, **Backtrack** para "rebobinar" o banco e **exportação** de snapshots para o S3. Esta nota mostra como usar cada um e quando.

**Analogia:** o volume do Aurora é um **livro-razão com histórico completo**. Backup contínuo é o **registro de cada lançamento**; clonar é **tirar uma cópia que só gasta papel quando alguém reescreve uma página**; Backtrack é **voltar o livro ao estado de determinado momento** sem reconstruir tudo.

## Backup contínuo e PITR

| Característica | Detalhe |
|---|---|
| **Funcionamento** | O Aurora faz backup **contínuo e incremental** do volume para o S3, **sem impacto** de desempenho e sem janela de backup |
| **Retenção** | 1 a 35 dias (padrão 1) |
| **PITR** | Restaura para qualquer segundo da retenção (últimos ~5 min atrás) |
| **Custo** | Armazenamento de backup acima do tamanho do volume é cobrado; até esse tamanho, sem cobrança adicional |
| **Restauração** | Cria um **novo cluster** (novo endpoint); depois adicione instâncias |
| **Backups automáticos** | Removidos quando o cluster é excluído (retenha snapshot final) |

```bash
# Ajustar retenção
aws rds modify-db-cluster --db-cluster-identifier loja-aurora --backup-retention-period 14 --apply-immediately

# PITR: cria um novo cluster no instante desejado
aws rds restore-db-cluster-to-point-in-time --db-cluster-identifier loja-aurora-pitr \
  --source-db-cluster-identifier loja-aurora --restore-to-time 2026-11-06T14:30:00Z
# O cluster restaurado vem sem instâncias: crie ao menos uma
aws rds create-db-instance --db-instance-identifier loja-aurora-pitr-w1 \
  --db-cluster-identifier loja-aurora-pitr --engine aurora-postgresql --db-instance-class db.r6g.large
```

### Snapshots de cluster

- **Automáticos** (parte do backup contínuo) e **manuais** (sem expiração).
- Podem ser **copiados entre regiões**, **compartilhados** com outras contas (criptografados com CMK) e usados para restaurar.
- Use antes de mudanças de risco e com **AWS Backup** para governança ([[8. DevOps e Gerenciamento de Infraestrutura/CLOUD COMPUTING/AWS (AMAZON WEB SERVICE)/3. Tecnologia e Serviços/3.3 Serviços principais da AWS/3.3.2. Armazenamento/3.3.2.6. AWS Backup/0 AWS Backup (Tópicos )|AWS Backup]]).

## Clonagem rápida (Aurora cloning)

Cria um novo cluster que **compartilha as páginas de dados** com o original usando **copy-on-write**: só os blocos alterados depois da clonagem ocupam novo espaço.

```
 Cluster ORIGEM ─────┐
                      ├── mesmas páginas de dados (compartilhadas)
 Cluster CLONE  ─────┘   → quando um lado altera uma página, ela é copiada (copy-on-write)
```

| Característica | Detalhe |
|---|---|
| **Velocidade** | Minutos, independentemente do tamanho do banco |
| **Custo inicial** | Praticamente só o das instâncias do clone; armazenamento extra apenas do que mudar |
| **Isolamento** | Alterações no clone **não afetam** a origem e vice-versa |
| **Escopo** | Mesma região, mesma conta ou entre contas (via RAM) |
| **Limites** | Número máximo de clones por origem, e clones de clones, conforme a documentação |

Casos de uso: **ambientes de teste/homologação** com dados reais, **testes de migração de esquema** e de upgrade, **análises pesadas** sem tocar a produção, reproduzir bugs.

```bash
aws rds restore-db-cluster-to-point-in-time --db-cluster-identifier loja-clone-teste \
  --source-db-cluster-identifier loja-aurora --restore-type copy-on-write --use-latest-restorable-time
aws rds create-db-instance --db-instance-identifier loja-clone-w1 \
  --db-cluster-identifier loja-clone-teste --engine aurora-postgresql --db-instance-class db.r6g.large
```

Atenção: o clone pode conter **dados sensíveis**; mascare ou controle o acesso. Um clone mantém dependência dos blocos compartilhados; evite excluir a origem sem planejar.

## Backtrack (Aurora MySQL)

Permite **"rebobinar" o cluster para um momento anterior sem restaurar de backup**, desfazendo um erro (ex.: `DELETE` sem `WHERE`).

| Característica | Detalhe |
|---|---|
| **Disponibilidade** | **Aurora MySQL** (não existe em Aurora PostgreSQL) |
| **Funcionamento** | Mantém um histórico de mudanças (change records) durante a janela configurada (até 72 h) |
| **Execução** | Cluster fica **indisponível por instantes**; volta ao estado escolhido no mesmo cluster/endpoint |
| **Custo** | Cobrança por change records armazenados |
| **Limitações** | Não substitui backup (janela curta); incompatível com alguns recursos (ex.: Global Database em certas condições); a operação afeta todo o cluster |

```bash
# Habilitar na criação: --backtrack-window 86400 (24 h)
aws rds backtrack-db-cluster --db-cluster-identifier loja-aurora-mysql \
  --backtrack-to 2026-11-06T14:00:00Z
# Volta o banco inteiro a esse instante (operação "para tudo": avalie o impacto antes)
```

Alternativa em PostgreSQL: **PITR** para um novo cluster (e copiar os dados necessários) ou **clone** + extração seletiva.

## Exportação para o S3

- **Export de snapshot para S3** em formato **Parquet**, sem afetar o banco: alimenta data lakes e consultas com **Athena**.
- **Aurora zero-ETL** com Redshift (e outras integrações): replicação quase em tempo real para análises sem pipelines manuais (confirme disponibilidade e engines).
- **`SELECT ... INTO OUTFILE S3`** (MySQL) e `aws_s3` extension (PostgreSQL) para exportar/importar dados por consulta.

```bash
aws rds start-export-task --export-task-identifier exp-loja-2026-11 \
  --source-arn arn:aws:rds:sa-east-1:111122223333:cluster-snapshot:loja-snap \
  --s3-bucket-name datalake-export --iam-role-arn arn:aws:iam::111122223333:role/rds-export \
  --kms-key-id alias/datalake
```

## Qual recurso usar

| Situação | Recurso |
|---|---|
| Apagamos dados por engano há poucos minutos/horas (MySQL) | **Backtrack** (rápido) ou **PITR** |
| Apagamos dados por engano (PostgreSQL) | **PITR** para novo cluster + extração |
| Ambiente de teste com dados de produção | **Clone** |
| Backup antes de uma migração | **Snapshot manual** (+ clone) |
| Proteção de longo prazo/conformidade | **AWS Backup** com cópia entre contas e Vault Lock |
| Análise de dados históricos | **Export para S3** / zero-ETL |
| DR entre regiões | **Global Database** (+ snapshots copiados) |

## Exemplo prático

Plano de dados de um Aurora MySQL de produção:

1. Retenção de backup de **14 dias** e **Backtrack de 24 h**.
2. **Snapshots manuais** antes de cada release, copiados para outra região via AWS Backup.
3. Toda semana, um **clone** é criado para homologação e descartado ao final.
4. Exportação mensal de um snapshot para S3 (Parquet) para o data lake.
5. Runbook de incidente: erro humano <24 h → Backtrack; entre 1 e 14 dias → PITR para novo cluster; perda do cluster → snapshot cross-region.
6. Teste trimestral de restauração (PITR e snapshot) com RTO medido.

## Erros comuns e armadilhas

- **Achar que Backtrack substitui backup** (janela curta e escopo global).
- **Tentar Backtrack em Aurora PostgreSQL:** não existe.
- **Restaurar e esquecer de criar instâncias** no cluster restaurado.
- **Esquecer SG/parameter group/endpoints** no cluster restaurado ou clonado.
- **Clone com dados sensíveis acessível a todos.**
- **Excluir cluster sem snapshot final.**
- **Retenção de 1 dia** em produção.
- **Backtrack durante a carga:** derruba todas as conexões do cluster.
- **Compartilhar snapshot criptografado sem compartilhar a CMK.**

## 🧩 Quiz de Fixação

1. Como o Aurora faz backup sem impacto no desempenho?
2. O que é copy-on-write na clonagem e qual a vantagem?
3. Qual a diferença entre Backtrack e PITR?

**Respostas:**
1) O armazenamento distribuído faz backup contínuo e incremental do volume para o S3, de forma independente da instância, sem janela de backup nem impacto de I/O.
2) O clone compartilha as páginas de dados com a origem; só os blocos alterados em cada lado são copiados. Assim a clonagem leva minutos e quase não consome armazenamento extra de início.
3) O Backtrack (somente Aurora MySQL) volta o cluster existente a um instante anterior, rapidamente, dentro de uma janela de até 72 h; o PITR cria um novo cluster restaurado de um ponto no tempo dentro da retenção de até 35 dias.
