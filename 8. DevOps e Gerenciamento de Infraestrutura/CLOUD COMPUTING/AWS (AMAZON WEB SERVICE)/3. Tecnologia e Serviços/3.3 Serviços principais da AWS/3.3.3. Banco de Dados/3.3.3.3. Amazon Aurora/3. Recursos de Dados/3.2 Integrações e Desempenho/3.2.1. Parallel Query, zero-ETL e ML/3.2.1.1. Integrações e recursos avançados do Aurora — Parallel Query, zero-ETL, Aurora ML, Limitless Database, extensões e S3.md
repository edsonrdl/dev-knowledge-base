### Integrações e recursos avançados do Aurora — Parallel Query, zero-ETL, Aurora ML, Limitless Database, extensões e S3

> [!warning] Aviso
> Esta é a área do Aurora que **mais muda**: novos recursos, engines e versões suportadas surgem com frequência, e alguns estão em preview ou com restrições. Os recursos abaixo foram descritos como conhecidos na época da escrita. **Confirme disponibilidade, versão e região na documentação antes de usar.** Os comandos **não foram executados**.

Além de ser um banco relacional rápido e disponível, o Aurora se **integra ao ecossistema da AWS**: carrega e exporta dados do **S3**, chama **Lambda**, usa **machine learning** (SageMaker, Comprehend, Bedrock) direto em SQL, replica para o **Redshift** sem pipeline (**zero-ETL**), acelera consultas analíticas com **Parallel Query** e, em PostgreSQL, escala escrita horizontalmente com o **Limitless Database**. Esta nota organiza esses recursos, quando usar cada um e as ressalvas.

**Analogia:** o Aurora é uma **cozinha profissional** que, além de preparar pratos (consultas), tem **portas de serviço** para o estoque (S3), para a equipe externa (Lambda), para a nutricionista (ML) e para o restaurante vizinho (Redshift), sem precisar sair da cozinha.

## Integração com Amazon S3

Permite **importar dados do S3** para tabelas e **exportar resultados** para o S3, usando uma **role IAM** associada ao cluster.

| Engine | Importar | Exportar |
|---|---|---|
| **Aurora MySQL** | `LOAD DATA FROM S3 's3://bucket/arquivo.csv' INTO TABLE ...` | `SELECT ... INTO OUTFILE S3 's3://bucket/saida'` |
| **Aurora PostgreSQL** | `aws_s3.table_import_from_s3(...)` | `aws_s3.query_export_to_s3(...)` |
| **Snapshots** | Export de snapshot do cluster para S3 em Parquet (sem afetar o banco) | — |

```sql
-- PostgreSQL: pré-requisitos: CREATE EXTENSION aws_s3 CASCADE; role IAM associada ao cluster (feature s3Import / s3Export)
SELECT aws_s3.table_import_from_s3(
  'pedidos', '', '(format csv, header true)',
  aws_commons.create_s3_uri('meu-bucket', 'carga/pedidos.csv', 'sa-east-1'));

SELECT * FROM aws_s3.query_export_to_s3(
  'SELECT * FROM pedidos WHERE criado >= now() - interval ''30 days''',
  aws_commons.create_s3_uri('meu-bucket', 'export/pedidos-30d.csv', 'sa-east-1'),
  options := 'format csv, header true');
```

```bash
# Associar a role ao cluster
aws rds add-role-to-db-cluster --db-cluster-identifier loja-aurora \
  --role-arn arn:aws:iam::111122223333:role/aurora-s3-access --feature-name s3Import
```

Boas práticas: bucket na **mesma região** (ou configurar acesso entre regiões), role de **menor privilégio** restrita ao prefixo, criptografia (SSE-KMS) e arquivos em lotes de tamanho razoável.

## Invocar Lambda a partir do banco

Funções do banco chamam **AWS Lambda** (síncrona ou assíncrona), útil para **notificações, integração de eventos e enriquecimento**.

| Engine | Mecanismo |
|---|---|
| **MySQL** | `lambda_sync(...)` e `lambda_async(...)` (funções nativas), role associada com `Lambda` |
| **PostgreSQL** | Extensão `aws_lambda` (`aws_lambda.invoke(...)`) |

Cuidados: chamadas **dentro de transações** aumentam a latência e podem repetir se a transação reexecuta; prefira o padrão **outbox** (gravar o evento na tabela e processar por fora) quando precisa de confiabilidade e desacoplamento.

## Parallel Query (Aurora MySQL)

Empurra parte do processamento de **consultas analíticas** (filtros, agregações parciais) para a **camada de armazenamento distribuída**, em paralelo, reduzindo transferência e CPU da instância.

```
 Consulta analítica ──► Instância ──► (empurra filtro/agregação) ──► centenas de nós de armazenamento processam em paralelo
```

| Característica | Detalhe |
|---|---|
| **Ideal para** | Scans grandes em tabelas de dezenas/centenas de GB, filtros seletivos, agregações |
| **Benefício** | Consultas até muitas vezes mais rápidas e menos pressão no buffer pool; **HTAP leve** sem ETL |
| **Não indicado** | Consultas pontuais curtas OLTP; tabelas pequenas |
| **Restrições** | Suporte limitado a certos tipos de consulta/tabela/versão; ativado por parâmetro; coexistência com buffer cache (dados quentes podem preferir o cache) |
| **Verificação** | `EXPLAIN` indica *Using parallel query*; status `Aurora_pq_*` |

Alternativas analíticas: **réplica dedicada** com instâncias maiores (custom endpoint), **zero-ETL para Redshift**, **export para S3 + Athena**.

## Aurora Machine Learning

Chame modelos de ML **diretamente em SQL**, sem mover dados para fora do banco:

| Serviço | Uso |
|---|---|
| **Amazon SageMaker** | Inferência com seus modelos (fraude, recomendação, churn) |
| **Amazon Comprehend** | Sentimento, entidades em texto |
| **Amazon Bedrock** | Modelos de fundação (embeddings, geração de texto) |

```sql
-- PostgreSQL (extensão aws_ml): exemplo ilustrativo de análise de sentimento
SELECT comentario, aws_comprehend.detect_sentiment(comentario, 'pt') AS sentimento
FROM avaliacoes WHERE criado >= current_date - 1;
```

Requisitos: role IAM associada ao cluster, extensão (`aws_ml`) ou funções MySQL, rede (VPC endpoints). Cuidados: **latência e custo por chamada**; não use em consultas de alta frequência; prefira processar em lote ou materializar o resultado.

## Busca vetorial e extensões (Aurora PostgreSQL)

| Extensão | Uso |
|---|---|
| **pgvector** | Armazenar embeddings e fazer busca por similaridade (`<->`, `<=>`), índices HNSW/IVFFlat — base para **RAG** e busca semântica |
| **PostGIS** | Dados geoespaciais |
| **pg_cron** | Agendamento de jobs SQL |
| **pg_stat_statements / pg_hint_plan** | Diagnóstico e controle de planos |
| **pg_partman / pg_repack** | Particionamento e reorganização |
| **aws_s3 / aws_lambda / aws_ml** | Integrações AWS |

```sql
CREATE EXTENSION IF NOT EXISTS vector;
CREATE TABLE documentos (id bigserial PRIMARY KEY, conteudo text, embedding vector(1024));
CREATE INDEX ON documentos USING hnsw (embedding vector_cosine_ops);
SELECT id, conteudo FROM documentos ORDER BY embedding <=> $1 LIMIT 5;   -- 5 documentos mais similares
```

**Optimized Reads** (NVMe local) pode acelerar buscas vetoriais com conjunto maior que a memória (ver nota de arquitetura). A lista de extensões é por versão: consulte a documentação.

## Zero-ETL

Integração **gerenciada e quase em tempo real** de dados transacionais do Aurora para um **destino analítico** (Amazon Redshift e, conforme a oferta, SageMaker Lakehouse/outros), **sem construir pipelines ETL**.

```
 Aurora (OLTP) ──replicação contínua gerenciada (segundos)──► Redshift (OLAP) ──► BI, SQL analítico, ML
```

| Característica | Detalhe |
|---|---|
| **Latência** | Segundos a poucos minutos |
| **Impacto no OLTP** | Baixo (usa o log/armazenamento) |
| **Configuração** | Integração entre cluster de origem e destino, com filtros de bancos/tabelas (conforme versão) |
| **Benefício** | Elimina Glue/DMS/ETL manual para casos de analytics quase em tempo real |
| **Limites** | Versões, DDL suportados e tipos de dados; custo do destino |

Alternativas: exportar snapshots para S3 + Athena (lote), DMS CDC (mais controle), Streams/Kafka (arquiteturas de eventos).

## Limitless Database (Aurora PostgreSQL)

Recurso para **escala horizontal** de escrita e armazenamento (**sharding gerenciado**) sem dividir manualmente a aplicação.

```
 Aplicação ─► Roteadores (distributed transaction routers) ─► Shards (data access shards) ─► volume distribuído
```

| Conceito | Descrição |
|---|---|
| **DB shard group** | Conjunto de roteadores e shards com capacidade em ACUs (mín/máx) |
| **Sharded tables** | Tabelas distribuídas por **shard key** |
| **Reference tables** | Tabelas pequenas replicadas em todos os shards |
| **Standard tables** | Tabelas em um único shard (não distribuídas) |
| **Transações distribuídas** | Suportadas, com custo de coordenação |

Quando considerar: escrita ou volume que ultrapassa o limite do writer único (centenas de milhares de transações/s, dezenas de TiB) e o esquema tem uma boa **shard key** (por exemplo `tenant_id`). Restrições: recursos e extensões suportados, versões, consultas entre shards; modelagem exige cuidado. Em geral: **esgote antes** as otimizações do cluster regular (índices, read replicas, Serverless v2, particionamento).

## Como escolher

| Necessidade | Recurso |
|---|---|
| Carga/exportação em massa | Integração com S3 |
| Reagir a eventos do banco | Lambda (preferir outbox/CDC) |
| Consultas analíticas pesadas no próprio Aurora MySQL | Parallel Query ou réplica dedicada |
| Analytics quase em tempo real sem ETL | Zero-ETL para Redshift |
| IA generativa / busca semântica | pgvector (+ Bedrock) |
| Escala de escrita além de um writer | Limitless Database (após esgotar outras opções) |
| Migrar aplicações SQL Server com poucas mudanças | Babelfish |
| Auditoria independente | Database Activity Streams |

## Exemplo prático

Plataforma de suporte ao cliente com Aurora PostgreSQL:

1. **Busca semântica** de artigos: coluna `embedding vector(1024)` com índice HNSW; embeddings gerados por Bedrock em lote noturno e na gravação (via fila, não dentro da transação).
2. **Zero-ETL** para Redshift: painéis de BI quase em tempo real sem tocar o OLTP.
3. **Importação** diária de tickets do parceiro via `aws_s3.table_import_from_s3`, de um bucket com SSE-KMS.
4. **Exportação** mensal de dados de auditoria para S3 (Parquet via export de snapshot) para o data lake.
5. **Notificação**: gatilho no banco grava em `outbox`; um consumidor dispara Lambda/SNS (não chamar Lambda dentro da transação).
6. **Roadmap**: avaliar Limitless se o `tenant_id` crescer além da capacidade de um writer; antes, otimizar índices e usar Serverless v2 para picos.

## Erros comuns e armadilhas

- **Assumir que o recurso existe na sua versão/região** sem checar a documentação.
- **Chamar Lambda/ML dentro de transações frequentes:** latência alta e efeitos repetidos em retries.
- **Role IAM ampla demais** para S3/Lambda/Bedrock.
- **Usar Parallel Query para OLTP ou tabelas pequenas.**
- **Confiar em zero-ETL sem monitorar atraso e esquemas** (DDL incompatível pode pausar a integração).
- **pgvector sem índice ou com parâmetros inadequados:** consultas lentas ou resultados ruins.
- **Adotar Limitless sem shard key adequada.**
- **Importar arquivos gigantes sem lotes** e estourar I/O/tempo.
- **Ignorar custos** (ML por chamada, destino do zero-ETL, I/O).
- **Depender de preview/novos recursos em produção crítica sem plano de contingência.**

## 🧩 Quiz de Fixação

1. Para que serve o Parallel Query e quando não usá-lo?
2. O que é zero-ETL e que problema resolve?
3. Por que evitar chamar Lambda dentro de transações e qual padrão usar?
4. Quando considerar o Limitless Database?

**Respostas:**
1) Empurra filtros e agregações de consultas analíticas para a camada de armazenamento em paralelo, acelerando scans grandes no Aurora MySQL; não serve para consultas OLTP curtas nem para tabelas pequenas.
2) É a replicação gerenciada e quase em tempo real de dados do Aurora para um destino analítico (como o Redshift), eliminando a construção e manutenção de pipelines ETL e reduzindo o impacto no OLTP.
3) Porque aumenta a latência da transação e pode repetir a chamada se a transação for reexecutada; use o padrão outbox (gravar o evento na tabela e processá-lo fora da transação, via fila/CDC).
4) Quando a escrita ou o volume ultrapassa o que um único writer suporta e existe uma boa shard key (como tenant_id), depois de esgotar as otimizações do cluster regular.
