## Caminhos de migração para o Aurora

| Origem | Técnica recomendada | Downtime |
|---|---|---|
| **RDS MySQL / PostgreSQL** | **Réplica Aurora** da instância RDS → promover no corte | Mínimo (minutos) |
| **RDS MySQL / PostgreSQL** | **Restaurar snapshot** como cluster Aurora | Janela maior (tempo do restore + quedas de escrita) |
| **MySQL on-premises/EC2** | **Percona XtraBackup → S3 → restore** como Aurora MySQL, + replicação binlog até o corte | Mínimo |
| **PostgreSQL on-premises/EC2** | `pg_dump/pg_restore` (janela), **replicação lógica** (pglogical/assinatura) ou **DMS** | Mínimo com CDC |
| **Oracle / SQL Server** | **SCT/DMS Schema Conversion** + **DMS** (full load + CDC); para SQL Server, avaliar **Babelfish** | Mínimo (dados) + esforço de conversão |
| **MariaDB** | Dump/binlog para Aurora MySQL | Depende |
| **Aurora → Aurora (outra região/conta)** | Snapshot compartilhado/copiado, clone, **Global Database** | Baixo |

### RDS → Aurora via réplica

```
 RDS (primário) ═ replicação nativa ═► Réplica Aurora (cluster) → sincroniza → promove → Aurora independente
```

```bash
# 1) Criar um cluster Aurora que é réplica de leitura da instância RDS de origem
aws rds create-db-cluster --db-cluster-identifier loja-aurora --engine aurora-postgresql \
  --replication-source-identifier arn:aws:rds:sa-east-1:111122223333:db:loja-prod \
  --db-subnet-group-name sg-bd-prod --vpc-security-group-ids sg-0bd123 --storage-encrypted --kms-key-id alias/aurora
aws rds create-db-instance --db-instance-identifier loja-aurora-w1 --db-cluster-identifier loja-aurora \
  --engine aurora-postgresql --db-instance-class db.r6g.large

# 2) Aguardar a sincronização (lag perto de zero) e pausar escritas na origem
# 3) Promover o cluster Aurora a independente
aws rds promote-read-replica-db-cluster --db-cluster-identifier loja-aurora
# 4) Apontar a aplicação para o cluster endpoint do Aurora; manter o RDS como fallback por um período
```

(A disponibilidade da réplica Aurora varia por engine e versão; confirme.)

## Roteiro de migração (resumo)

1. **Avaliação:** compatibilidade de versão, extensões (PostgreSQL), parâmetros, collation, tamanho, picos, SLAs.
2. **Desenho:** writer/readers, Serverless v2 ou provisionado, I/O-Optimized ou Standard, rede, KMS, Proxy, parâmetros (cluster e instância).
3. **Ambiente de teste:** restaurar um snapshot/clone como Aurora e rodar testes funcionais e de carga (planos de consulta podem diferir).
4. **Sincronização:** réplica Aurora/DMS/binlog até lag zero.
5. **Ensaio de corte:** cronometrar; validar sequências, usuários, grants, jobs, extensões.
6. **Corte:** pausar escritas, aguardar lag zero, promover, trocar endpoints, smoke tests.
7. **Pós-corte:** monitorar desempenho (comparar baseline), ajustar parâmetros, manter a origem em leitura por um período; plano de retorno.

Validação: contagem de linhas, checksums, consultas de negócio, comparação de planos, testes de desempenho.

## Versões e upgrades

| Conceito | Detalhe |
|---|---|
| **Versões menores** | Patches e melhorias; aplicadas na janela de manutenção (pode ser automático — *auto minor version upgrade*) |
| **Zero-Downtime Patching (ZDP)** | Em Aurora MySQL (e em condições específicas), aplica patches preservando conexões; depende de não haver transações longas, tabelas temporárias abertas, etc. |
| **Versões maiores** | Upgrade **manual** (in-place com `pg_upgrade`/equivalente, via Blue/Green ou por snapshot/restore) |
| **LTS (Long Term Support)** | Versões com suporte estendido de patches; recomendadas para produção estável |
| **Fim de suporte / Extended Support** | Versões antigas passam para Extended Support pago; planeje upgrade antes |
| **Compatibilidade** | Verificar mudanças de comportamento, parâmetros removidos, extensões incompatíveis |

### Opções para upgrade major

| Opção | Downtime | Reversão | Observações |
|---|---|---|---|
| **In-place** | Reinício/minutos a horas | Difícil (restaurar snapshot) | Simples; fazer snapshot antes |
| **Blue/Green deployments** | **Switchover em ~1 min** | O ambiente azul permanece | Replica lógica; suporta Aurora MySQL e PostgreSQL (confirme) |
| **Clone + upgrade + corte** | Médio | Mantém o original | Para testes e cargas pequenas |
| **Snapshot → restaurar com nova versão** | Janela | Mantém o original | Para cargas com janela |

```bash
# Blue/Green: criar o ambiente verde com a nova versão major e depois trocar
aws rds create-blue-green-deployment --blue-green-deployment-name up-pg17 \
  --source arn:aws:rds:sa-east-1:111122223333:cluster:loja-aurora \
  --target-engine-version 17.4 --target-db-cluster-parameter-group-name aurora-pg17-prod
# ... testar o verde (carga, regressão) ...
aws rds switchover-blue-green-deployment --blue-green-deployment-identifier bgd-abc123 --switchover-timeout 300
```

(Versões ilustrativas. Verifique as versões e o suporte a Blue/Green para a sua combinação.)

## Operação e manutenção

| Tema | Orientação |
|---|---|
| **Janela de manutenção** | Defina em horário de baixo tráfego; patches obrigatórios podem reiniciar instâncias |
| **Ordem de manutenção** | Readers primeiro, depois failover e writer (o Aurora faz com cuidado, mas observe) |
| **Parâmetros** | Cluster parameter group + DB parameter group; muitos parâmetros estáticos exigem reinício de **todas** as instâncias |
| **Backups** | Contínuos; retenção 1-35 dias; snapshots manuais antes de mudanças |
| **Testes de failover** | Periódicos (`failover-db-cluster`) e medição de RTO real da aplicação |
| **Capacidade** | Revisar classes, número de readers, Serverless v2 min/max, I/O |
| **Segurança** | Rotação de segredos, certificados CA do RDS, revisão de IAM/SG |
| **Custos** | Revisão mensal (I/O, backups, instâncias, readers ociosos) |

## Monitoramento específico do Aurora

| Métrica (CloudWatch `AWS/RDS`) | O que diz |
|---|---|
| `AuroraReplicaLag` / `AuroraReplicaLagMaximum` | Atraso das réplicas (ms); alto → writer saturado, réplica pequena ou consultas longas |
| `BufferCacheHitRatio` | % de leituras atendidas pela memória; queda → mais I/O |
| `VolumeReadIOPs` / `VolumeWriteIOPs` | I/O faturado do volume |
| `VolumeBytesUsed` / `AuroraVolumeBytesLeftTotal` | Tamanho do volume e margem |
| `CommitLatency`, `DMLLatency`, `SelectLatency` | Latência por tipo de operação |
| `DatabaseConnections` | Conexões |
| `Deadlocks`, `BlockedTransactions` (MySQL) | Concorrência |
| `ServerlessDatabaseCapacity`, `ACUUtilization` | Serverless v2 |
| `AuroraGlobalDB*` | Global Database |
| `EngineUptime` | Reinícios inesperados |

Ferramentas: Performance Insights (wait events), Enhanced Monitoring, logs no CloudWatch, `pg_stat_statements`, DevOps Guru for RDS, eventos do RDS (failover, manutenção).

## Troubleshooting típico

| Sintoma | Causas prováveis | Ações |
|---|---|---|
| **Lag de réplica alto** | Writer com escrita intensa, réplica subdimensionada, consultas longas na réplica, conflitos | Aumentar classe do reader, otimizar queries, dividir cargas, checar `AuroraReplicaLag` por réplica |
| **Falhas durante o failover** | Aplicação com DNS em cache, pool que não reconecta, endpoints de instância | Usar cluster/reader endpoint, driver com reconhecimento de failover, retry com backoff |
| **Cache frio após failover/reinício** | PostgreSQL sem CCM, reader pequeno | Habilitar cluster cache management, tier 0 com mesma classe |
| **Conexões esgotadas** | Pico, vazamento de conexões, `max_connections` dependente da memória | RDS Proxy, pool, timeouts, aumentar classe/ACU |
| **I/O alto e custo de I/O** | Scans grandes, cache hit baixo, falta de índices | Índices, mais memória, Optimized Reads, I/O-Optimized |
| **Espera `IO:XactSync` / commit lento (PG)** | Muitos commits pequenos | Agrupar commits |
| **Espera `IO:DataFileRead`** | Misses de cache | Memória, índices, consultas seletivas |
| **`Lock:transactionid`/deadlocks** | Transações longas, ordem inconsistente | Encurtar transações, revisar índices |
| **Volume crescendo** | Tabelas inchadas, objetos temporários, binlogs/WAL retidos, snapshots | `VACUUM`, remover slots lógicos inativos, reduzir retenção de binlog, particionar |
| **Upgrade falha na pré-checagem** | Extensões/objetos incompatíveis, prepared transactions, replication slots | Corrigir pendências, testar em clone/Blue-Green |
| **Reinícios inesperados** | Falta de memória, bug, manutenção | `EngineUptime`, logs de erro, eventos, suporte |

Procedimentos úteis:

```sql
-- PostgreSQL: ver réplicas e lag
SELECT * FROM aurora_replica_status();
-- Transações longas e bloqueios
SELECT pid, now()-xact_start AS dur, state, query FROM pg_stat_activity WHERE xact_start IS NOT NULL ORDER BY dur DESC LIMIT 10;
-- Slots de replicação lógica inativos (podem reter WAL e encher o volume)
SELECT slot_name, active, pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) AS retido FROM pg_replication_slots;
```

```sql
-- MySQL: estado de réplicas e transações longas
SELECT server_id, session_id, replica_lag_in_msec FROM mysql.ro_replica_status;
SELECT * FROM information_schema.innodb_trx ORDER BY trx_started LIMIT 10;
```

## Runbook de incidente (modelo)

```
1. Confirmar impacto: quais serviços/regiões? início? mudanças recentes (deploy, parâmetro, upgrade)?
2. Eventos do RDS e AWS Health: failover, manutenção, indisponibilidade?
3. CloudWatch: CPU, memória, conexões, latência, lag, I/O, ACU
4. Performance Insights: espera dominante e top SQL
5. Mitigar: reiniciar conexões ruins, matar sessões bloqueantes, escalar (classe/ACU/readers), fazer failover se o writer está degradado
6. Comunicar e registrar linha do tempo
7. Pós-incidente: causa raiz, ação corretiva, alarmes novos, atualização do runbook
```

## Exemplo prático

Migração e upgrade de um RDS PostgreSQL 14 (2 TB) para Aurora PostgreSQL 16 com no máximo 5 minutos de indisponibilidade:

1. **Teste:** restaurar snapshot como Aurora PostgreSQL 14, rodar a suíte de testes e a carga de produção gravada; ajustar extensões (`pg_stat_statements`, `pgcrypto`) e parâmetros.
2. **Réplica Aurora** do RDS (14) sincronizando (lag < 1 s) por 3 dias.
3. **Corte 1 (RDS → Aurora 14):** pausa de escritas, promoção, troca de endpoints (Parameter Store), smoke tests. Janela total: 4 min.
4. **Estabilização:** 2 semanas observando métricas (lag, cache hit, I/O, latência) e ajustando parâmetros; backups e testes de failover.
5. **Upgrade 14 → 16 via Blue/Green:** ambiente verde com parameter group novo, testes e switchover (~1 min).
6. **Operação:** I/O-Optimized avaliado após 30 dias de métricas; Proxy para Lambda; alarmes de `AuroraReplicaLag`, `ACUUtilization`, `BufferCacheHitRatio`; runbook atualizado.

## Erros comuns e armadilhas

- **Migrar sem testar planos de consulta** (otimizador/estatísticas diferem; rodar `ANALYZE` pós-migração).
- **Esquecer extensões** não suportadas ou de versão diferente.
- **Upgrade major direto em produção** sem Blue/Green ou ensaio.
- **Não ter plano de retorno** (replicação reversa/origem em leitura).
- **Ignorar sequências/identidades** no corte.
- **Usar endpoint de instância** na aplicação.
- **Parâmetros copiados cegamente** do RDS (parâmetros de cluster vs instância mudam).
- **Não testar failover** e descobrir problemas no incidente real.
- **Slots de replicação lógica inativos** enchendo o volume.
- **Janela de manutenção em horário de pico.**
- **Manter versão em Extended Support sem planejar o upgrade.**
- **Ignorar `AuroraReplicaLag`** ao ler da réplica dados que acabaram de ser gravados.

## 🧩 Quiz de Fixação

1. Como migrar um RDS PostgreSQL para Aurora com baixo downtime?
2. Quais as vantagens do Blue/Green para um upgrade major?
3. Que métricas indicam problemas de réplicas e de cache no Aurora?
4. Por que o failover pode causar lentidão mesmo quando o banco volta rápido?

**Respostas:**
1) Criar um cluster Aurora como réplica da instância RDS, deixar sincronizar até lag próximo de zero, pausar as escritas na origem, promover o cluster e trocar o endpoint da aplicação, mantendo a origem como fallback.
2) Cria um ambiente verde sincronizado em que a nova versão é aplicada e testada sem afetar a produção, e o switchover leva cerca de um minuto, mantendo o ambiente azul para reversão.
3) `AuroraReplicaLag` (atraso das réplicas) e `BufferCacheHitRatio` (queda indica mais leituras do volume), além de `VolumeReadIOPs`, `CommitLatency` e `DatabaseConnections`.
4) Porque a nova writer pode ter o cache frio (sem as páginas quentes) e as conexões da aplicação precisam se restabelecer; no PostgreSQL o cluster cache management e um reader em tier 0 reduzem o efeito, e drivers com reconhecimento de failover aceleram a reconexão.
