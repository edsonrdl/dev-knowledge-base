> [!warning] Aviso

## Snapshots e restauração

| Tipo | Característica |
|---|---|
| **Automáticos** | Tirados periodicamente (aproximadamente a cada 8 horas ou a cada ~5 GB de alteração por nó); retenção padrão de **1 dia**, configurável até **35 dias**; apagados com o cluster |
| **Manuais** | Sob demanda; **sem expiração** (ou com retenção definida); persistem após excluir o cluster |
| **Incrementais** | Cada snapshot guarda apenas as mudanças desde o anterior |
| **Armazenamento** | S3 gerenciado; gratuito até o tamanho do armazenamento provisionado (RA3: conforme regras), depois cobrado por GB-mês |
| **Cópia entre regiões** | Replicação automática para outra região (DR), com chave KMS própria no destino |
| **Compartilhamento** | Para outras contas (criptografados exigem compartilhar a chave) |
| **Backups contínuos** | No Serverless, **recovery points** automáticos (24 h) e snapshots manuais |

### Restauração

```
 Snapshot ──restore-from-cluster-snapshot──► NOVO cluster (mesmo ou outro tamanho/tipo)
 Snapshot ──table-level restore──► restaura UMA tabela em um cluster existente (com outro nome)
```

| Operação | Detalhe |
|---|---|
| **Restaurar cluster** | Cria um novo cluster; **o antigo permanece**. Troque o endpoint (DNS/alias) depois |
| **Restauração em nível de tabela** | Recupera uma tabela de um snapshot sem restaurar o cluster inteiro |
| **Serverless** | Restaurar um snapshot/recovery point para um namespace |
| **Tempo** | Proporcional ao tamanho; RA3 restaura rápido (storage gerenciado, hidratação sob demanda) |

```bash
aws redshift create-cluster-snapshot --cluster-identifier dw-prod --snapshot-identifier dw-pre-migracao
aws redshift modify-cluster --cluster-identifier dw-prod --automated-snapshot-retention-period 14
aws redshift restore-from-cluster-snapshot --cluster-identifier dw-restaurado --snapshot-identifier dw-pre-migracao
aws redshift restore-table-from-cluster-snapshot --cluster-identifier dw-prod --snapshot-identifier dw-pre-migracao \
  --source-database-name analytics --source-table-name fato_vendas --new-table-name fato_vendas_restaurada --target-database-name analytics

# Cópia automática de snapshots para outra região (DR)
aws redshift enable-snapshot-copy --cluster-identifier dw-prod --destination-region us-east-1 --retention-period 14
```

Para política central, cofres imutáveis e cópias entre contas, veja o [[8. DevOps e Gerenciamento de Infraestrutura/CLOUD COMPUTING/AWS (AMAZON WEB SERVICE)/3. Tecnologia e Serviços/3.3 Serviços principais da AWS/3.3.2. Armazenamento/3.3.2.6. AWS Backup/0 AWS Backup (Tópicos )|AWS Backup]].

## Resize e escala do cluster provisionado

| Operação | O que faz | Impacto |
|---|---|---|
| **Elastic resize** | Altera o nº de nós (e, com limites, o tipo) redistribuindo slices | Minutos; breve indisponibilidade (consultas em andamento podem ser interrompidas); sem copiar todos os dados |
| **Classic resize** | Cria um cluster novo e copia os dados | Horas; cluster fica **somente leitura** durante a cópia |
| **Snapshot, restore e resize** | Restaurar com outro tamanho | Mantém o original; útil para teste |
| **Concurrency scaling** | Capacidade temporária para consultas | Automático |
| **Cluster relocation** | Mudar de AZ | Para recuperação/capacidade |
| **Mudar o tipo de nó** | DC2 → RA3 (migração) | Planeje com snapshot e restore |

```bash
aws redshift resize-cluster --cluster-identifier dw-prod --number-of-nodes 4 --classic false   # elastic resize
aws redshift describe-resize --cluster-identifier dw-prod
```

Quando redimensionar: filas crescendo, CPU alta, disco > 75-80%, consultas lentas por falta de capacidade. Antes, otimize: distribuição, sort keys, consultas, WLM, materializações.

## Pausa e retomada

| Característica | Detalhe |
|---|---|
| **Pause** | Interrompe a computação; **continua pagando armazenamento**; os dados permanecem |
| **Resume** | Restabelece o cluster em minutos |
| **Agendamento** | Pause/resume agendados (EventBridge/Scheduler) para ambientes não produtivos ou cargas fora do horário |
| **Limites** | Não é possível durante algumas operações; planeje conexões ao retomar |

```bash
aws redshift pause-cluster --cluster-identifier dw-dev
aws redshift resume-cluster --cluster-identifier dw-dev
```

Em cargas com horários bem definidos (ex.: 9h-19h), pausar à noite e aos fins de semana reduz cerca de 60% do custo de computação; compare com **Serverless**.

## Monitoramento e manutenção

| Item | Orientação |
|---|---|
| **Métricas CloudWatch** | `CPUUtilization`, `PercentageDiskSpaceUsed`, `DatabaseConnections`, `HealthStatus`, `WLMQueueLength`, `QueryDuration`, `ConcurrencyScalingSeconds`, `ReadIOPS/WriteIOPS`, `MaintenanceMode` |
| **Alarmes** | Disco > 80%, CPU > 90% sustentado, fila WLM crescente, falhas de COPY, saúde do cluster |
| **Janela de manutenção** | Semanal; patches/versão; escolha horário de menor uso; **track** (current/trailing) |
| **Redshift Advisor** | Recomendações de distribuição, sort, compressão, rightsizing |
| **Eventos (SNS/EventBridge)** | Falhas, manutenção, snapshots |
| **Auditoria** | Logs e CloudTrail (ver nota de segurança) |
| **Tabelas de sistema** | `SVV_TABLE_INFO`, `SYS_QUERY_HISTORY`, `SVV_DISKUSAGE` |

## Custo: onde o dinheiro vai

| Componente | Observação |
|---|---|
| **Computação** (nós provisionados) | Por hora de nó; RA3 cobra computação e armazenamento separadamente |
| **Armazenamento gerenciado (RA3)** | Por GB-mês |
| **Serverless** | RPU-hora + armazenamento |
| **Snapshots acima da cota** | Por GB-mês |
| **Spectrum** | Por TB escaneado |
| **Concurrency scaling** | Segundos de uso acima dos créditos gratuitos |
| **Transferência de dados** | Entre regiões/saída para a internet; dentro da AZ gratuita |
| **Data sharing cross-region, ML (SageMaker), Glue** | Conforme uso |

### Alavancas de economia

| Alavanca | Efeito |
|---|---|
| **Reserved Nodes** (1 ou 3 anos) | Descontos de dezenas de % em nós estáveis (RA3) |
| **Pause/resume** | Zero computação nos períodos desligados |
| **Serverless para cargas variáveis** | Paga só o que usa |
| **Rightsizing** | Reduzir nós/tipo conforme CPU, fila e disco |
| **RA3 managed storage** | Evita pagar nós por armazenamento |
| **Compressão e tipos enxutos** | Menos disco |
| **Dados frios no S3 + Spectrum** | Move o histórico barato para o lake |
| **Arquivar/excluir tabelas antigas** | Menos armazenamento |
| **Snapshot retention** | Reter só o necessário |
| **Controle de consultas** (QMR) | Evita consultas descontroladas e concurrency scaling excessivo |
| **Otimização de consultas** | Menos CPU e I/O |
| **Tags + Budgets + Anomaly Detection** | Visibilidade |

### Reserved Nodes: como decidir

1. Dimensione e **estabilize** o cluster (pelo menos 2-3 meses).
2. Reserve a **base 24×7** (60-80% dos nós).
3. Escolha prazo e pagamento (Partial/All Upfront) conforme o fluxo de caixa.
4. Mantenha o excedente em On-Demand ou Serverless.
5. Reavalie se pretende migrar para Serverless ou mudar o tipo de nó (RA3).

## Rightsizing: sinais

| Sinal | Ação |
|---|---|
| CPU média < 20-30%, sem fila, disco < 50% | Reduzir nós (elastic resize) |
| Fila WLM e CPU > 85% frequentemente | Aumentar nós ou ativar/ajustar concurrency scaling, otimizar |
| Disco > 80% | Mais nós/RA3, arquivar para S3, compressão |
| Pico concentrado em poucas horas | Concurrency scaling ou Serverless |
| Uso apenas em horário comercial | Pause/resume agendado |

## Recuperação de desastres (DR)

| Estratégia | RPO | RTO | Custo |
|---|---|---|---|
| **Snapshots cross-region** | Até o último snapshot (horas) | Restauração do cluster (minutos a horas) | Baixo |
| **Cluster secundário restaurado sob demanda** | Idem | Maior (criar cluster) | Baixíssimo |
| **Data sharing / zero-ETL para outra região** | Segundos a minutos (com carga contínua) | Baixo, se o cluster já existe | Médio/alto |
| **Multi-AZ para RA3** (recurso de alta disponibilidade em AZs, conforme oferta) | Perto de zero | Failover automático | Maior |
| **Replay de ETL** | Depende da fonte | Maior | Baixo |

Teste a restauração periodicamente e documente o RTO.

## Exemplo prático

Plano operacional de um DW RA3 com 4 nós:

1. **Backups:** retenção automática de 14 dias; snapshots manuais antes de cada release; **cópia cross-region** para `us-east-1` (retenção 14 dias) com CMK local; AWS Backup para cópia mensal em conta de arquivamento.
2. **Capacidade:** `PercentageDiskSpaceUsed` alvo ≤ 70%; alarme em 80%; concurrency scaling na fila de BI; revisão trimestral de rightsizing (CPU média 38%, pico 82% → manter 4 nós).
3. **Custo:** 3 nós em **Reserved Nodes (1 ano, Partial Upfront)** e 1 em On-Demand; ambiente de desenvolvimento em cluster `ra3.xlplus` com **pause agendado** às 20h e **resume** às 7h.
4. **Frio:** dados de mais de 18 meses descarregados (`UNLOAD`) para S3/Parquet e consultados via Spectrum; economia de 30% de armazenamento.
5. **Manutenção:** janela dominical 03:00-03:30; avisos por SNS; teste de restauração trimestral de tabela e de cluster.
6. **Governança:** orçamento mensal e alerta de anomalia; tags `centro_de_custo`; revisão das 10 consultas mais caras.
7. **DR:** runbook testado: restaurar snapshot cross-region em 55 minutos, validar contagens e apontar o BI.

## Erros comuns e armadilhas

- **Retenção de snapshot de 1 dia** em produção.
- **Não copiar snapshots para outra região** (DR inexistente).
- **Nunca testar restauração.**
- **Classic resize em horário de pico** (cluster somente leitura).
- **Disco acima de 80-90%** sem ação: degradação e falhas de operações.
- **Cluster 24×7 em ambiente de desenvolvimento** sem pause.
- **Comprar Reserved Nodes antes de dimensionar** ou antes de avaliar Serverless.
- **Esquecer que o pause não elimina o custo de armazenamento.**
- **Concurrency scaling sem limites** gerando conta alta.
- **Manter dados frios no cluster** quando poderiam estar no S3.
- **Ignorar o Advisor e as métricas** de fila/disco.
- **Janela de manutenção em horário crítico.**

## 🧩 Quiz de Fixação

1. Qual a diferença entre elastic resize e classic resize?
2. O que acontece com a cobrança quando se pausa um cluster?
3. Como recuperar uma única tabela apagada por engano?
4. Como combinar Reserved Nodes e pausa agendada de forma eficiente?

**Respostas:**
1) O elastic resize altera o número de nós redistribuindo slices em minutos, sem copiar todos os dados; o classic resize cria um cluster novo e copia tudo, levando horas e deixando o cluster somente leitura durante a cópia.
2) A computação deixa de ser cobrada, mas o armazenamento (e snapshots) continua cobrado; ao retomar, a cobrança de computação volta.
3) Com a restauração em nível de tabela a partir de um snapshot (`restore-table-from-cluster-snapshot`), criando a tabela com outro nome no cluster existente, sem restaurar o cluster inteiro.
4) Reservar apenas a base que roda 24×7 (que não pode ser pausada) e usar pausa agendada ou Serverless para as cargas de horário limitado, evitando pagar reservas por capacidade que ficaria desligada.
