### Segurança e governança no Redshift — VPC, criptografia, IAM, RBAC, segurança em nível de linha e coluna, mascaramento e auditoria

> [!warning] Aviso
> Recursos de segurança (RLS, mascaramento dinâmico, integração com IAM Identity Center, políticas de criptografia) são **recentes ou evoluem** e variam por versão e tipo de implantação. Confirme na documentação. Os comandos e SQL **não foram executados**.

Um data warehouse concentra os **dados mais sensíveis da empresa** em um só lugar, o que o torna alvo prioritário e exige governança forte. A segurança do Redshift se organiza em camadas: **rede** (VPC, Security Groups, enhanced VPC routing), **criptografia** (repouso, trânsito, chaves), **identidade e acesso** (IAM, IAM Identity Center/federação, roles, RBAC), **controle fino de dados** (permissões em nível de coluna, **segurança em nível de linha**, **mascaramento dinâmico de dados**) e **auditoria** (logs de conexão, de usuário e de atividade).

**Analogia:** o data warehouse é a **sala de arquivos confidenciais** de um banco. A rede é o **prédio com portaria**; a criptografia é o **cofre das caixas**; o IAM/RBAC é o **crachá com níveis de acesso**; o RLS e o mascaramento são **viseiras** que mostram a cada funcionário só as linhas permitidas e com campos sensíveis borrados; a auditoria são as **câmeras e o livro de registro**.

## Camada 1 — Rede

| Prática | Detalhe |
|---|---|
| **VPC e subnets privadas** | O cluster/workgroup vive em um **subnet group** de subnets privadas em ≥ 2 AZs (3 no Serverless) |
| **`PubliclyAccessible = false`** | Sem IP público; acesso por VPN, Direct Connect, Client VPN, bastion/SSM, ou peering/Transit Gateway |
| **Security Group** | Libera a porta (5439) **somente** de SGs/CIDRs confiáveis (BI, ETL, VPN) |
| **Enhanced VPC routing** | **Força** o tráfego `COPY`/`UNLOAD` e do Spectrum a passar pela **VPC** (permitindo VPC endpoints para S3, NAT, endpoint policies e flow logs), em vez da rede pública da AWS |
| **VPC endpoints** | S3 (gateway endpoint), Glue, KMS, STS, Secrets Manager, Redshift API |
| **Cross-account** | Compartilhamento de rede por RAM/peering; endpoints gerenciados do Redshift (*Redshift-managed VPC endpoints*) para acesso de outra VPC/conta |

```
 BI/ETL (SG-bi) ──5439/TLS──► Redshift (SG-rs: entrada somente de SG-bi/VPN)  — subnets privadas
 COPY/UNLOAD ──(enhanced VPC routing)──► VPC endpoint S3 ──► S3 (política restringe o bucket)
```

## Camada 2 — Criptografia

| Tipo | Como |
|---|---|
| **Em repouso** | AES-256 com **KMS** (chave gerenciada pela AWS ou **CMK**) ou **HSM**; cobre dados, backups/snapshots e logs; habilite na criação (`--encrypted`) ou migre via snapshot (e alteração de criptografia no cluster) |
| **Em trânsito** | **TLS/SSL**; exija com o parâmetro `require_ssl=true` (e use `sslmode=verify-full` nos clientes) |
| **Hierarquia de chaves** | Chave raiz (KMS/HSM) → chave de cluster → chave de banco → chaves de dados; **rotação** de chaves suportada |
| **Cross-region copy** | Snapshots criptografados exigem uma chave KMS na região de destino |
| **Spectrum/S3** | SSE-S3 ou SSE-KMS nos objetos; a IAM role precisa de permissão na chave |
| **Redshift ML/SageMaker** | Artefatos no S3 com SSE-KMS |

Veja [[8. DevOps e Gerenciamento de Infraestrutura/CLOUD COMPUTING/AWS (AMAZON WEB SERVICE)/2. Segurança e Conformidade/2.3 Capacidades de gerenciamento de acesso da AWS/2.3.2. Serviços de segurança/2.3.2.7. AWS Key Management Service (KMS)|AWS KMS]].

## Camada 3 — Identidade e acesso

| Mecanismo | Descrição |
|---|---|
| **Usuários e grupos do banco** | `CREATE USER` com senha; evite usar o usuário admin no dia a dia; senha master gerenciada pelo Secrets Manager (`--manage-master-password`) |
| **IAM** | Controla a **API do Redshift** (criar/modificar/excluir clusters, snapshots) e `redshift:GetClusterCredentials`/`GetCredentials` (credenciais temporárias para conexão sem senha fixa) |
| **Federação SAML/SSO** | Okta, Azure AD, etc. via IAM; **IAM Identity Center** (SSO centralizado e *trusted identity propagation* com QuickSight/Query Editor v2) |
| **IAM roles associadas ao cluster** | Permitem `COPY`/`UNLOAD`/Spectrum/ML acessarem S3, Glue, SageMaker, Lambda com **menor privilégio** |
| **Secrets Manager** | Credenciais de ferramentas e Data API |
| **Políticas de recurso/Service Control Policies** | Limitam clusters públicos, sem criptografia, regiões etc. |

```bash
# Credenciais temporárias (sem senha fixa) para um usuário do banco
aws redshift get-cluster-credentials --cluster-identifier dw-prod --db-user analista01 --db-name analytics --duration-seconds 900
```

### RBAC (controle de acesso baseado em papéis)

Em vez de conceder privilégios usuário a usuário, crie **roles** com permissões e atribua aos usuários (as roles podem ser hierárquicas).

```sql
CREATE ROLE analista_vendas;
GRANT USAGE ON SCHEMA vendas TO ROLE analista_vendas;
GRANT SELECT ON ALL TABLES IN SCHEMA vendas TO ROLE analista_vendas;
GRANT ROLE analista_vendas TO analista01;

CREATE ROLE engenheiro_dados;
GRANT ALL ON SCHEMA staging TO ROLE engenheiro_dados;
GRANT ROLE analista_vendas TO ROLE engenheiro_dados;     -- hierarquia: herda as permissões do analista
```

Vantagens: governança simples, auditoria clara, menos erros; atribua roles a grupos do IdP.

## Camada 4 — Controle fino de dados

### Permissões em nível de coluna

```sql
GRANT SELECT (cliente_id, cidade, plano) ON clientes TO ROLE analista_vendas;   -- sem CPF, e-mail, telefone
```

### Segurança em nível de linha (RLS — Row-Level Security)

Políticas que **filtram linhas** conforme quem consulta.

```sql
CREATE RLS POLICY politica_regiao
WITH (regiao VARCHAR(20))
USING (regiao = current_setting('app.regiao', true));       -- ou uma tabela de mapeamento usuário→região

ATTACH RLS POLICY politica_regiao ON vendas TO ROLE analista_regional;
ALTER TABLE vendas ROW LEVEL SECURITY ON;
```

Padrão comum: tabela de mapeamento `usuario_regiao` e política `USING (regiao IN (SELECT regiao FROM usuario_regiao WHERE usuario = current_user))`. Cada analista vê só as linhas da sua região, no mesmo dashboard.

### Mascaramento dinâmico de dados (DDM)

Mostra **valores ofuscados** em tempo de consulta a quem não pode ver o dado real, sem alterar o armazenado.

```sql
CREATE MASKING POLICY mascara_cpf
WITH (cpf VARCHAR(14))
USING (CASE WHEN has_role('privacidade') THEN cpf ELSE 'XXX.XXX.XXX-' || RIGHT(cpf, 2) END);

ATTACH MASKING POLICY mascara_cpf ON clientes(cpf) TO PUBLIC PRIORITY 10;
```

| Técnica | Quando |
|---|---|
| **Permissão de coluna** | Esconder a coluna inteira |
| **Mascaramento dinâmico** | Mostrar parcialmente (últimos dígitos, hash, nulo) |
| **RLS** | Restringir linhas |
| **Views seguras** | Compatibilidade e abstração |
| **Tokenização/criptografia no ETL** | Dados altamente sensíveis (PAN, saúde) |

### Lake Formation

Para dados no lake e no Spectrum, o **Lake Formation** centraliza permissões (tabela/coluna/linha) e governa Glue Catalog, Athena, EMR e Redshift.

## Camada 5 — Auditoria e monitoramento

| Registro | O que contém | Destino |
|---|---|---|
| **Connection log** | Autenticações, conexões, desconexões | S3 ou CloudWatch Logs |
| **User log** | Mudanças em usuários/roles | S3/CloudWatch |
| **User activity log** | **Cada consulta** executada (requer `enable_user_activity_logging=true`) | S3/CloudWatch |
| **Tabelas de sistema** | `STL_CONNECTION_LOG`, `SYS_QUERY_HISTORY`, `SVL_STATEMENTTEXT` | No cluster (retenção curta) |
| **CloudTrail** | Chamadas à API (criar/excluir/modificar clusters, snapshots, credenciais) | S3/CloudWatch |
| **Config / Security Hub** | Regras: criptografia, acesso público, SSL obrigatório, log de auditoria, versões | Conformidade |
| **GuardDuty / Macie (nos dados no S3)** | Anomalias e dados sensíveis | Alertas |

```bash
aws redshift enable-logging --cluster-identifier dw-prod --log-destination-type cloudwatch --log-exports connectionlog userlog useractivitylog
# Ative também no parameter group: enable_user_activity_logging = true (requer reinício)
```

Alertas úteis: muitos `authentication failed`, consultas em tabelas sensíveis por usuários fora do padrão, `GRANT` a `PUBLIC`, snapshots compartilhados publicamente, exclusão de cluster, mudança de parâmetro `require_ssl`.

## Governança e conformidade

| Prática | Detalhe |
|---|---|
| **Classificação de dados** | Marcar colunas sensíveis (PII, financeiros) e aplicar políticas |
| **Menor privilégio** | Roles por função; revisar periodicamente |
| **Separação de funções** | Quem administra ≠ quem acessa os dados; ETL com role própria |
| **Retenção e exclusão** | Políticas LGPD/GDPR: `DELETE`/`VACUUM`, retenção de snapshots |
| **Snapshots e cópias** | Criptografados; compartilhamento controlado |
| **Ambientes** | Dev/test sem dados reais (ou mascarados) |
| **Revisões e evidências** | Relatórios de auditoria, trilhas |
| **Resposta a incidentes** | Runbook: desabilitar usuário, rotacionar credenciais, snapshot forense |

## Checklist de segurança

- [ ] Cluster/workgroup em subnets privadas, **sem acesso público**; SG restrito.
- [ ] **Enhanced VPC routing** e VPC endpoints para S3.
- [ ] Criptografia em repouso (CMK) e `require_ssl = true`.
- [ ] Senha master gerenciada; **sem uso diário do admin**; SSO/IAM Identity Center ou credenciais temporárias.
- [ ] **RBAC** com roles por função; sem `GRANT` direto a `PUBLIC`.
- [ ] Colunas sensíveis protegidas (coluna, RLS, mascaramento).
- [ ] IAM roles do cluster com **menor privilégio** (buckets e prefixos específicos).
- [ ] Logs de conexão, usuário e atividade habilitados e retidos.
- [ ] CloudTrail, Config, Security Hub e alarmes.
- [ ] Snapshots criptografados; cópia cross-region com chave própria; sem compartilhamento público.
- [ ] Revisão trimestral de acessos e testes de restauração.

## Exemplo prático

DW de uma operadora de saúde com dados pessoais e clínicos:

1. **Rede:** workgroup Serverless em subnets privadas, sem IP público, SG aceitando 5439 só da VPN e dos SGs do BI; **enhanced VPC routing**; endpoint S3 com política restrita ao bucket do data lake.
2. **Criptografia:** CMK `alias/dw-saude` (rotação anual), `require_ssl`; snapshots copiados à região DR com CMK local.
3. **Identidade:** IAM Identity Center com grupos `analistas`, `cientistas`, `auditores`, `engenharia`; Query Editor v2 via SSO; admin só em break-glass.
4. **RBAC:** roles `analista_assistencial`, `analista_financeiro`, `engenheiro_dados`, `auditoria` (somente leitura em logs).
5. **Dados sensíveis:** CPF e diagnóstico protegidos com **mascaramento dinâmico** (visíveis só ao papel `privacidade`); **RLS** por unidade/hospital com tabela de mapeamento; colunas clínicas fora do alcance do financeiro.
6. **Auditoria:** user activity log no CloudWatch Logs → Athena; alarme para consultas na tabela `prontuarios` fora do horário; relatório mensal para o comitê de privacidade (LGPD).
7. **Ambientes:** dev/test com dados mascarados por job de ETL; pipelines CI/CD aplicam DDL e permissões como código.
8. **Governança:** Config rules (`redshift-cluster-public-access-check`, criptografia), revisão trimestral de roles e testes de restauração.

## Erros comuns e armadilhas

- **Cluster público com SG aberto** e senha fraca.
- **Usar o usuário admin** para tudo (BI, ETL).
- **`GRANT` a `PUBLIC`** ou permissões amplas por conveniência.
- **Esquecer `require_ssl`** e clientes sem validação de certificado.
- **Não habilitar o user activity log** antes do incidente (sem trilha).
- **IAM role do cluster com `s3:*` em `*`.**
- **Achar que mascaramento substitui criptografia/controle de acesso:** é uma camada de apresentação.
- **RLS mal testado:** políticas que vazam linhas ou degradam o desempenho.
- **Ambientes de desenvolvimento com dados reais.**
- **Snapshots compartilhados publicamente ou sem criptografia.**
- **Sem rotação de credenciais/chaves** e sem revisão de acessos.
- **Deixar o Spectrum acessar buckets inteiros** em vez de prefixos específicos.

## 🧩 Quiz de Fixação

1. Qual a função do enhanced VPC routing?
2. Qual a diferença entre permissão de coluna, RLS e mascaramento dinâmico?
3. Por que usar RBAC em vez de conceder privilégios a cada usuário?
4. O que é preciso habilitar para registrar cada consulta executada?

**Respostas:**
1) Forçar o tráfego de COPY, UNLOAD e Spectrum a passar pela VPC do cliente, permitindo VPC endpoints, políticas, NAT e flow logs, em vez de usar a rede pública da AWS.
2) A permissão de coluna oculta colunas inteiras; a RLS filtra as linhas visíveis conforme o usuário; o mascaramento dinâmico mostra valores ofuscados de uma coluna (por exemplo últimos dígitos) a quem não pode ver o dado real, sem alterar o armazenado.
3) Porque as roles agrupam permissões por função (e podem ser hierárquicas), simplificando a governança, a auditoria e a revogação, reduzindo erros e privilégios acumulados.
4) O user activity log: habilitar `enable_user_activity_logging=true` no parameter group (com reinício) e habilitar o registro de logs de auditoria no cluster para S3 ou CloudWatch Logs.
