### Redshift Serverless — RPUs, namespaces e workgroups, capacidade base, limites de uso e custo

> [!warning] Aviso
> Faixas de RPU, preços, recursos suportados (nem todos os recursos do provisionado existem no Serverless), regiões e limites de escala mudam. **Confirme na documentação e na calculadora.** Os comandos **não foram executados**.

O **Amazon Redshift Serverless** executa o mesmo mecanismo do Redshift **sem que você provisione ou gerencie nós**: a capacidade de computação é medida em **RPUs** (*Redshift Processing Units*), **escala automaticamente** conforme a carga e **você paga apenas pelo que usa**, por segundo. Serve para cargas **variáveis ou esporádicas**, ambientes de desenvolvimento e teste, equipes que querem evitar administração de cluster e **novos data warehouses** sem histórico de uso. Esta nota explica os conceitos (**namespace** e **workgroup**), como a escala funciona, como configurar **capacidade base** e **limites de uso**, o custo e as diferenças para o provisionado.

**Analogia:** o cluster provisionado é **alugar um andar de escritório** (você paga o aluguel mesmo vazio). O Serverless é um **espaço de coworking cobrado por hora de uso**: quando há muita gente, o sistema abre mais mesas; quando ninguém usa, não cobra pelas mesas.

## Conceitos

| Conceito | Descrição |
|---|---|
| **Namespace** | Conjunto de **objetos de dados**: bancos, esquemas, tabelas, usuários, snapshots, chave KMS e roles IAM. É onde os dados "moram" |
| **Workgroup** | Conjunto de **recursos de computação**: capacidade em RPUs, VPC/subnets/Security Groups, endpoint e configurações de acesso |
| **RPU** | Unidade de computação (CPU, memória e rede); **1 RPU ≈ 16 GB de memória** (confirme) |
| **Capacidade base** | RPUs mínimas com que o workgroup começa a processar consultas |
| **Capacidade máxima** | Teto de escala automática (opcional) |
| **Limites de uso** | Limites de RPU-horas por período e ações (alertar, registrar, desligar) |
| **Endpoint** | Nome DNS do workgroup para JDBC/ODBC/Data API |

```
 Namespace "dw-prod"  (dados, usuários, KMS, snapshots)
        ▲
        │ associado a
 Workgroup "wg-bi" (RPU base 64, máx 256, VPC, SG)   ← endpoint: wg-bi.123456789012.sa-east-1.redshift-serverless.amazonaws.com
 Workgroup "wg-etl" (RPU base 128) … podem compartilhar dados via data sharing entre namespaces
```

Um namespace é associado a **um workgroup** (e um workgroup a um namespace). Para isolar cargas (ETL × BI), use **namespaces separados** com **data sharing**.

## Como a escala funciona

| Aspecto | Comportamento |
|---|---|
| **Início** | Ao chegar uma consulta, o Redshift Serverless liga os recursos (sem esperar minutos; "partida a frio" curta) |
| **Escala automática** | Ajusta as RPUs para a carga (consultas simultâneas e complexidade), buscando bom desempenho |
| **AI-driven scaling and optimization** | Meta de **custo × desempenho** (de "otimizar custo" a "otimizar desempenho") em vez de apenas fixar RPUs; o serviço aprende com as consultas |
| **Ociosidade** | Sem consultas, a computação **não é cobrada** (apenas o armazenamento) |
| **Concurrency** | Concurrency scaling embutido (a capacidade se ajusta); consultas curtas são priorizadas |
| **Limites** | Máximo de RPUs por workgroup (centenas); consultas muito grandes podem exigir mais capacidade base |

### Definindo capacidade base

| Capacidade base (RPU) | Perfil |
|---|---|
| 4 a 32 | Desenvolvimento, dashboards leves, dados pequenos (mínimo configurável por região/versão) |
| 64 a 128 | Cargas moderadas de BI e ETL (128 é o padrão histórico) |
| 256 ou mais | DW grande, concorrência alta, janelas de ETL curtas |

Regra prática: **comece menor** que o padrão para economizar e **aumente** se o tempo de consulta ou a fila aumentarem; use a meta de preço-desempenho se disponível. Monitore `ComputeCapacity` e o tempo de execução.

```bash
# Criar namespace e workgroup (resumo)
aws redshift-serverless create-namespace --namespace-name dw-prod --db-name analytics \
  --admin-username admin --manage-admin-password \
  --kms-key-id alias/redshift --iam-roles arn:aws:iam::111122223333:role/redshift-s3-access

aws redshift-serverless create-workgroup --workgroup-name wg-bi --namespace-name dw-prod \
  --base-capacity 64 --max-capacity 256 \
  --subnet-ids subnet-0aaa111 subnet-0bbb222 subnet-0ccc333 --security-group-ids sg-0rs123 \
  --enhanced-vpc-routing --no-publicly-accessible

# Ajustar capacidade
aws redshift-serverless update-workgroup --workgroup-name wg-bi --base-capacity 96
```

## Limites de uso e controle de custo

Para evitar contas inesperadas, defina **usage limits**:

| Tipo | Função |
|---|---|
| **Limite de RPU-horas** por dia/semana/mês | Teto de consumo de computação |
| **Ação ao atingir** | `log` (registrar), `emit-metric` (alarme CloudWatch) ou `turn-off-user-queries` (bloquear consultas) |
| **Limites de data sharing/cross-region** | Controlam transferência |
| **Capacidade máxima** (`max-capacity`) | Limita a escala automática |
| **Query monitoring rules** | Abortam consultas que excedem tempo/linhas/escaneamento |

```bash
aws redshift-serverless create-usage-limit --resource-arn $WORKGROUP_ARN --usage-type serverless-compute \
  --amount 2000 --period monthly --breach-action emit-metric
# 2000 RPU-horas por mês; ao exceder, emite métrica para alarme (alternativa: turn-off-user-queries)
```

## Modelo de custo

| Componente | Cobrança |
|---|---|
| **Computação** | **RPU-hora**, medida por segundo, com **mínimo de 60 segundos** por consulta/período ativo; apenas quando há processamento |
| **Armazenamento** | Managed storage por GB-mês (mesmo modelo do RA3) |
| **Snapshots** | Armazenamento de snapshots/recovery points acima da cota |
| **Spectrum/consultas externas** | Por TB escaneado no S3 |
| **Data sharing entre regiões, transferência** | Conforme o caso |
| **Reservas** | Há opções de compromisso (Serverless Reservations) para uso previsível (confirme a oferta atual) |

Exemplo de cálculo (ilustrativo, preço hipotético de US$ 0,375 por RPU-hora):

```
 Carga: 60 RPUs ativos durante 3 horas por dia, 22 dias úteis
 Consumo = 60 × 3 × 22 = 3.960 RPU-horas/mês
 Custo de computação ≈ 3.960 × 0,375 ≈ US$ 1.485 / mês   (+ armazenamento)
 Provisionado equivalente 24×7: 2 nós ra3.4xlarge ≈ US$ 5.000+/mês  → o Serverless vence se o uso é baixo
```

Quando o uso é **contínuo e alto** (24×7), o provisionado com **Reserved Nodes** costuma ser mais barato. Faça a conta com a calculadora.

## Serverless × Provisionado

| Critério | **Serverless** | **Provisionado (RA3)** |
|---|---|---|
| Administração | Mínima | Nós, resize, WLM |
| Custo em uso esporádico | **Menor** (paga o que usa) | Maior (nós ligados) ou exige pausa manual |
| Custo em uso contínuo | Maior por unidade | **Menor** com reservas |
| Escala | Automática | Manual/elastic + concurrency scaling |
| Controles | Menos parâmetros; limites de uso | Total (WLM manual, parâmetros) |
| Recursos | Quase todos; verifique diferenças (algumas features só no provisionado) | Todos |
| Latência de partida | Pequena (frio) | Nenhuma |
| Pausa | Automática (sem custo de computação ociosa) | Manual (`pause-cluster`) |

## Segurança, acesso e integração

| Item | Detalhe |
|---|---|
| **VPC e rede** | Workgroup em subnets e Security Groups; acesso público opcional (evite); **enhanced VPC routing** |
| **Criptografia** | Sempre em repouso (KMS) e em trânsito (TLS) |
| **IAM** | Permissões `redshift-serverless:*`, GetCredentials temporárias; RBAC no banco |
| **Data API** | SQL via HTTPS sem gerenciar conexões — ótimo para Lambda/serverless |
| **Query Editor v2** | Console web para consultas |
| **Ferramentas de BI** | JDBC/ODBC com endpoint do workgroup |
| **Data sharing e zero-ETL** | Compatíveis (confirme versões) |
| **Backups** | Recovery points automáticos e snapshots manuais; restauração para namespace/provisionado |

## Quando usar

| Situação | Serverless? |
|---|---|
| Novo DW sem histórico de carga | **Sim** (descubra o padrão antes de comprar capacidade) |
| BI com uso intermitente (horário comercial) | **Sim** |
| Dev/test/homologação | **Sim** |
| ETL esporádico/ad hoc | **Sim** |
| Workloads multi-tenant isolados por equipe | **Sim** (namespaces + data sharing) |
| DW 24×7 de alta carga constante | Avaliar provisionado + reservas |
| Necessidade de recursos exclusivos do provisionado | Provisionado |

## Exemplo prático

Startup de análise de dados com picos às 9h e 15h e quase nenhum uso à noite:

1. Namespace `dw` com KMS e roles; workgroup `wg-prod` com **capacidade base 32 RPU** e máxima 192.
2. **Meta de preço-desempenho** equilibrada; limites de uso: alarme em 1.200 RPU-horas/mês e `turn-off-user-queries` em 2.000 (somente workgroup de exploração).
3. Segundo workgroup `wg-etl` (outro namespace `dw-etl`) para cargas pesadas noturnas, com **data sharing** para o namespace de BI (sem copiar dados).
4. Dashboards via QuickSight; funções Lambda usando **Data API**.
5. Após 3 meses: consumo médio de 1.050 RPU-horas/mês; comparação com um cluster provisionado de 2 nós → Serverless ~70% mais barato. Revisão semestral para decidir reservas.
6. Governança: tags de custo por workgroup, Budgets, revisão de consultas mais caras (`SYS_QUERY_HISTORY` e `SYS_SERVERLESS_USAGE`).

```sql
-- Consumo de RPU por período
SELECT start_time, end_time, compute_seconds, compute_capacity FROM sys_serverless_usage ORDER BY start_time DESC LIMIT 24;
```

## Erros comuns e armadilhas

- **Capacidade base alta demais** (ex.: 512) para cargas leves: gasta sem necessidade.
- **Sem limites de uso**: uma consulta ruim ou um loop gera conta alta.
- **Achar que Serverless é sempre mais barato:** não é para cargas contínuas e grandes.
- **Um único workgroup para ETL, BI e exploração:** interferência entre cargas.
- **Ignorar consultas mal otimizadas:** escala não conserta SQL ruim (apenas custa mais).
- **Usar Serverless e esperar todos os recursos do provisionado.**
- **Workgroup público com SG aberto.**
- **Não monitorar `ComputeCapacity`/RPU-horas.**
- **Esquecer o armazenamento e os snapshots** (continuam cobrados).
- **Não usar Data API/pool de conexões** em funções Lambda.

## 🧩 Quiz de Fixação

1. Qual a diferença entre namespace e workgroup?
2. Como o Redshift Serverless cobra a computação?
3. Como proteger-se contra custos inesperados?
4. Quando o provisionado tende a ser melhor que o Serverless?

**Respostas:**
1) O namespace guarda os objetos de dados (bancos, esquemas, tabelas, usuários, KMS, snapshots); o workgroup reúne os recursos de computação (capacidade em RPUs, VPC, Security Groups, endpoint).
2) Por RPU-hora, medida por segundo (com mínimo de 60 s) apenas enquanto há processamento; sem consultas não há cobrança de computação, mas o armazenamento continua cobrado.
3) Definindo limites de uso (RPU-horas por período com ação de alertar ou bloquear), capacidade máxima, regras de monitoramento de consultas, orçamentos e alarmes.
4) Em cargas contínuas e altas (24×7), em que nós reservados por 1 a 3 anos saem mais baratos, ou quando se precisa de recursos e controles exclusivos do provisionado.
