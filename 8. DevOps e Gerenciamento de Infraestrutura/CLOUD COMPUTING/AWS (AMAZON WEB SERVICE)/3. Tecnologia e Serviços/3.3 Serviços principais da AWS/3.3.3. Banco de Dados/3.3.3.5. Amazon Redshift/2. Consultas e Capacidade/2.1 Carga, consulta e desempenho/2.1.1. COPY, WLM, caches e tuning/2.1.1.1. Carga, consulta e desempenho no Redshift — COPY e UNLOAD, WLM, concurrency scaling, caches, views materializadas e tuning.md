### Carga, consulta e desempenho no Redshift — COPY e UNLOAD, WLM, concurrency scaling, caches, views materializadas e tuning

> [!warning] Aviso
> Parâmetros de WLM, limites de concorrência, recursos automáticos (auto WLM, SQA, AQUA/materialized views automáticas) e tabelas de sistema mudam por versão. **Confirme na documentação** e meça no seu ambiente. Os comandos SQL e CLI **não foram executados**.

Um data warehouse vive de duas operações: **carregar dados rápido** e **consultá-los com desempenho previsível sob concorrência**. No Redshift isso envolve o **`COPY`** (carga paralela a partir do S3), o **`UNLOAD`** (exportação), o **WLM** (gerenciamento de carga de trabalho), o **concurrency scaling**, os **caches** (resultado, SQA), as **views materializadas** e o **tuning de consultas** com `EXPLAIN` e tabelas de sistema.

**Analogia:** é uma **linha de produção de relatórios**. O `COPY` é o **caminhão de descarga paralela** com várias docas. O WLM é o **gerente de filas** que decide quem entra primeiro (consultas curtas na frente), o concurrency scaling abre **balcões extras** em horário de pico, e o cache guarda **cópias dos relatórios já prontos**.

## Carga de dados: `COPY`

O `COPY` carrega dados **em paralelo** de S3, DynamoDB, EMR ou hosts remotos. É **muito** mais rápido que `INSERT` linha a linha.

```
 Arquivos no S3:  parte-0001.parquet  parte-0002.parquet  ...  parte-0032.parquet
                        │                    │                         │
                  slice 1               slice 2     ...          slice 32   (cada slice lê arquivos diferentes)
```

Boas práticas:

| Prática | Por quê |
|---|---|
| **Vários arquivos** em número **múltiplo do nº de slices**, de tamanho semelhante (100 MB-1 GB comprimido) | Aproveita o paralelismo; um arquivo grande só usa um slice |
| **Formatos colunares** (Parquet/ORC) ou CSV comprimido (gzip/zstd) | Menos transferência e I/O |
| **Manifest** | Lista exata de arquivos (evita carregar arquivos parciais ou duplicados) |
| **IAM role** associada ao cluster | Sem chaves de acesso no comando |
| **Ordenar na carga** por sort key | Menos `VACUUM SORT` |
| **`COMPUPDATE`/`STATUPDATE`** | Compressão/estatísticas automáticas em tabela vazia |
| **Staging + transação** | Carrega em tabela temporária e faz `MERGE`/`INSERT` atômico |
| **Tratamento de erros** | `MAXERROR`, tabela `STL_LOAD_ERRORS` / `SYS_LOAD_ERROR_DETAIL` |

```sql
COPY stg_vendas
FROM 's3://dw-landing/vendas/2026/11/06/'
IAM_ROLE 'arn:aws:iam::111122223333:role/redshift-s3-access'
FORMAT AS PARQUET;

-- CSV comprimido com manifest
COPY stg_clientes
FROM 's3://dw-landing/clientes/manifest-2026-11-06.json'
IAM_ROLE default
CSV GZIP IGNOREHEADER 1 MANIFEST
TIMEFORMAT 'auto' MAXERROR 10;

-- Conferir erros de carga
SELECT * FROM sys_load_error_detail ORDER BY start_time DESC LIMIT 10;
```

Alternativas de ingestão: **auto-copy** (`COPY JOB` monitora um prefixo S3 e carrega novos arquivos), **streaming ingestion** (Kinesis/MSK por view materializada), **zero-ETL** (veja a nota de integrações), **Glue/DMS**, **Data API** para operações pequenas.

## Exportação: `UNLOAD`

```sql
UNLOAD ('SELECT * FROM fato_vendas WHERE data_id >= 20260101')
TO 's3://dw-export/vendas/2026/'
IAM_ROLE default
FORMAT AS PARQUET PARTITION BY (data_id) ALLOWOVERWRITE;
```

Use para alimentar o data lake, arquivar partições antigas ou compartilhar dados. Saída paralela em vários arquivos; formatos Parquet/CSV; suporta criptografia (SSE-KMS).

## Gerenciamento de carga de trabalho (WLM)

O WLM controla **filas, memória e concorrência** das consultas.

| Modo | Descrição |
|---|---|
| **Automático (auto WLM)** | O Redshift gerencia concorrência e memória dinamicamente; você define **prioridades** por fila/usuário/grupo (`LOWEST` a `HIGHEST`, `CRITICAL`) | **Recomendado** |
| **Manual** | Você define filas, nº de slots e % de memória | Controle fino; requer ajustes constantes |
| **Short Query Acceleration (SQA)** | Consultas curtas vão a uma área reservada, sem esperar atrás de consultas longas |
| **Query monitoring rules (QMR)** | Regras que **registram, redirecionam ou abortam** consultas por critérios (tempo, linhas, uso de memória, escaneamento) |
| **Query priority** | Prioriza ETL crítico vs relatórios exploratórios |

```
 Fila "ETL" (prioridade alta, noturna)     Fila "BI" (prioridade normal)     Fila "Adhoc" (baixa; QMR aborta > 10 min)
```

Configurar (JSON no parameter group `wlm_json_configuration`) ou pelo console. Boas práticas: filas por **tipo de carga** (ETL, dashboards, exploração), QMR para evitar consultas descontroladas, SQA habilitada.

### Concurrency scaling

Adiciona **capacidade temporária** (clusters de apoio) para atender picos de consultas **de leitura** (e algumas de escrita), sem intervenção.

| Característica | Detalhe |
|---|---|
| **Ativação** | Por fila do WLM (`concurrency_scaling = auto`) |
| **Custo** | Créditos gratuitos acumulados (cerca de 1 hora por dia de cluster ativo); depois, cobrança por segundo |
| **Benefício** | Desempenho consistente sob alta concorrência (muitos usuários de BI) |
| **Limite** | Máximo de clusters de escala (`max_concurrency_scaling_clusters`) |

### Caches

| Cache | Função |
|---|---|
| **Result cache** | Se a mesma consulta é executada e os dados não mudaram, devolve o resultado em milissegundos (no leader) |
| **Cache de código compilado** | Reuso de segmentos compilados |
| **RA3 SSD cache** | Dados quentes do managed storage nos SSDs locais |
| **AQUA** (em nós RA3 anteriores) | Cache distribuído acelerado (recurso evoluído; confirme) |

Dica: para dashboards, o result cache é um ganho enorme; evite funções não determinísticas (`GETDATE()`, `RANDOM()`) nas consultas repetidas.

## Views materializadas

Armazenam o **resultado pré-computado** de uma consulta, com **refresh incremental** quando possível.

```sql
CREATE MATERIALIZED VIEW mv_receita_diaria AUTO REFRESH YES AS
SELECT data_id, produto_id, SUM(valor) AS receita, COUNT(*) AS itens
FROM fato_vendas GROUP BY data_id, produto_id;

REFRESH MATERIALIZED VIEW mv_receita_diaria;   -- manual
```

| Característica | Detalhe |
|---|---|
| **Auto refresh** | Atualização automática em segundo plano quando há capacidade |
| **Reescrita automática** | O otimizador pode usar a MV em consultas que casam com ela (*automatic query rewriting*) |
| **Streaming ingestion** | MV sobre Kinesis/MSK ingere eventos quase em tempo real |
| **Sobre dados externos** | MVs sobre tabelas do Spectrum/lake |
| **Limitações** | Nem toda consulta suporta refresh incremental (joins complexos, funções não suportadas) |

Use para agregados caros e repetidos (dashboards); avalie o custo de manter atualizado.

## Tuning de consultas

### Roteiro

1. **Identifique** consultas lentas: `SYS_QUERY_HISTORY`, `SVL_QLOG`, console (Query monitoring).
2. **Veja o plano**: `EXPLAIN` — procure `DS_BCAST_INNER`/`DS_DIST_BOTH`, scans de tabelas enormes, `Nested Loop`.
3. **Confira estatísticas** (`SVV_TABLE_INFO`: `stats_off`) e rode `ANALYZE`.
4. **Reduza dados cedo**: filtros na sort key, `WHERE` seletivo, projete só colunas necessárias (nada de `SELECT *`).
5. **Revise distribuição e sort keys** (nota de modelagem).
6. **Reescreva**: evite subconsultas correlacionadas, `DISTINCT` desnecessário, `UNION` em vez de `UNION ALL`, funções em colunas filtradas (`WHERE funcao(coluna)`) que impedem poda.
7. **Materialize** agregados repetidos.
8. **Verifique concorrência/filas**: tempo de fila (`queue_time`) vs execução.

```sql
-- Top consultas por tempo
SELECT query_id, user_id, elapsed_time/1000000 AS seg, queue_time/1000000 AS fila_seg, LEFT(query_text, 100) AS sql
FROM sys_query_history WHERE start_time > dateadd(hour, -24, getdate())
ORDER BY elapsed_time DESC LIMIT 10;

-- Tabelas com estatísticas desatualizadas ou muito desordenadas
SELECT "table", stats_off, unsorted, tbl_rows FROM svv_table_info WHERE stats_off > 10 OR unsorted > 20;

-- Plano
EXPLAIN SELECT p.categoria, SUM(f.valor) FROM fato_vendas f JOIN dim_produto p USING (produto_id) GROUP BY 1;
```

### Anti-padrões frequentes

| Anti-padrão | Efeito | Correção |
|---|---|---|
| `SELECT *` em fato larga | Lê todas as colunas | Listar colunas |
| `WHERE CAST(data AS date) = ...` | Impede poda por sort key | Comparar na forma nativa da coluna |
| Junções por colunas de tipos diferentes | Conversões e sem otimização | Alinhar tipos |
| Muitos `INSERT` de uma linha | Lento, gera fragmentação | `COPY` / `INSERT ... SELECT` em lote |
| Transações longas bloqueando `VACUUM` | Espaço e desempenho | Encurtar, agendar |
| `ORDER BY` sem `LIMIT` em tabelas grandes | Ordenação global cara | Aplicar `LIMIT`/ordenar só o necessário |
| Tabelas temporárias grandes sem `DISTKEY` | Redistribuição | Definir `DISTKEY/SORTKEY` ou `CREATE TEMP TABLE AS` com chaves |

## Monitoramento de desempenho

| Fonte | O que mostra |
|---|---|
| **Console → Query monitoring / Performance** | Consultas em execução, tempo de fila, uso de recursos |
| **CloudWatch** | `CPUUtilization`, `PercentageDiskSpaceUsed`, `DatabaseConnections`, `QueriesCompletedPerSecond`, `QueryDuration`, `WLMQueueLength`, `ConcurrencyScalingSeconds` |
| **Tabelas/visões de sistema** | `SYS_QUERY_HISTORY`, `SYS_QUERY_DETAIL`, `SVL_QUERY_SUMMARY`, `STL_ALERT_EVENT_LOG` (avisos do otimizador), `SVV_TRANSACTIONS`, `STV_LOCKS` |
| **Advisor** | Recomendações de distribuição/sort/compressão (Redshift Advisor) |

Alarmes: espaço em disco > 80%, fila WLM crescente, CPU > 90% sustentado, falhas de `COPY`.

## Exemplo prático

Pipeline noturno + dashboards diurnos:

1. **ETL (02:00):** Glue converte arquivos para Parquet em `s3://dw-landing/vendas/aaaa/mm/dd/` (64 arquivos de ~200 MB, múltiplo dos 32 slices).
2. `COPY` na tabela `stg_vendas` → validação → `MERGE` em `fato_vendas` dentro de uma transação → `ANALYZE` na tabela.
3. **WLM automático:** fila `etl` com prioridade `HIGH` (usuário `etl_user`), fila `bi` com `NORMAL`, fila `adhoc` com `LOW` e QMR abortando consultas > 15 min ou > 1 TB de escaneamento. SQA habilitada.
4. **Concurrency scaling** na fila `bi` (até 4 clusters) para o pico das 9h-11h.
5. **Dashboards:** views materializadas `mv_receita_diaria` com auto refresh; o result cache atende repetições.
6. **Monitoramento:** alarme em `WLMQueueLength` e `PercentageDiskSpaceUsed`; revisão semanal das 10 consultas mais lentas.
7. **Resultado:** ETL cai de 55 para 14 minutos; dashboards respondem em 1-3 s mesmo com 120 usuários.

## Erros comuns e armadilhas

- **Carregar com `INSERT` linha a linha.**
- **Um único arquivão no `COPY`:** só um slice trabalha.
- **Sem manifest:** reprocessa arquivos parciais ou duplicados.
- **Ignorar `ANALYZE`** após cargas grandes.
- **Filas manuais mal dimensionadas** (muita memória para poucas consultas).
- **Não habilitar SQA/QMR:** consultas curtas presas atrás de longas; consultas descontroladas.
- **Esperar que concurrency scaling resolva consulta mal escrita.**
- **Funções não determinísticas** quebrando o result cache.
- **Views materializadas sem monitorar o custo de refresh.**
- **Transações longas** impedindo `VACUUM` e inflando o disco.
- **Disco acima de 80-90%:** degrada desempenho e dificulta operações.
- **Não revisar o `EXPLAIN`** de consultas críticas.

## 🧩 Quiz de Fixação

1. Por que o `COPY` deve usar vários arquivos?
2. Qual a diferença entre WLM automático e manual, e para que servem SQA e QMR?
3. Quando usar uma view materializada?
4. Que sinais no `EXPLAIN` indicam movimentação cara de dados?

**Respostas:**
1) Porque cada slice lê arquivos diferentes em paralelo; com um único arquivo grande, só um slice trabalha. O ideal é um número de arquivos múltiplo do número de slices, de tamanho semelhante.
2) No automático o Redshift gerencia concorrência e memória dinamicamente com prioridades; no manual você define filas, slots e memória. SQA acelera consultas curtas em uma área reservada e QMR registra, redireciona ou aborta consultas que violam regras (tempo, linhas, escaneamento).
3) Para agregados ou junções caras e repetidos (dashboards), pré-computando o resultado com refresh incremental/automático e, se possível, reescrita automática de consultas.
4) `DS_BCAST_INNER` (broadcast de uma tabela a todos os nós) e `DS_DIST_BOTH` (redistribuição das duas tabelas), indicando falta de colocalização.
