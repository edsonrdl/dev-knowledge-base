### O que é Amazon Redshift — data warehouse colunar MPP, leader e compute nodes, RA3, provisionado e serverless, e quando usar

> [!warning] Aviso
> Tipos de nó, limites, modelos de implantação (provisionado e Serverless), recursos de IA/ML e preços do Redshift mudam com frequência. Os números são **ordens de grandeza**. **Confirme na documentação.** Os comandos **não foram executados**.

O **Amazon Redshift** é o **data warehouse** gerenciado da AWS: um banco de dados **analítico (OLAP)**, **colunar** e de **processamento massivamente paralelo (MPP)**, projetado para executar **consultas SQL complexas sobre grandes volumes** (de gigabytes a petabytes) com bom desempenho e custo. Ele é compatível com o **protocolo e a sintaxe do PostgreSQL** (com diferenças), integra-se ao S3, ao Glue e ao ecossistema de BI, e pode ser usado em **clusters provisionados** ou em **Redshift Serverless**.

**Analogia:** um banco OLTP (RDS) é um **balcão de atendimento** que registra milhares de pequenas transações. O Redshift é um **departamento de análises** com uma equipe de analistas lendo planilhas gigantes **coluna por coluna**, cada um responsável por uma parte dos dados, trabalhando ao mesmo tempo, e um coordenador que consolida as respostas.

## OLTP × OLAP

| Critério | **OLTP** (RDS/Aurora/DynamoDB) | **OLAP** (Redshift) |
|---|---|---|
| Carga | Muitas transações pequenas (inserir, atualizar, consultar poucos registros) | Consultas grandes que leem **milhões a bilhões de linhas** |
| Acesso | Por linha | Por **coluna** (agregações, filtros) |
| Armazenamento | Orientado a **linhas** | Orientado a **colunas** |
| Consistência | ACID, transações curtas | ACID, mas otimizado para leitura analítica em lote |
| Usuários | Aplicações, milhares de conexões | Analistas, BI, cientistas de dados (dezenas a centenas de conexões simultâneas) |
| Modelagem | Normalizada (3FN) | Dimensional (estrela/floco de neve), desnormalizada |

Usar o banco OLTP para análises pesadas compromete a aplicação; o Redshift existe para separar essa carga.

## Armazenamento colunar e MPP

```
 Linha (OLTP):   [id|nome|cidade|valor|data]  [id|nome|cidade|valor|data] ...
 Coluna (OLAP):  [id id id ...] [nome nome ...] [cidade cidade ...] [valor valor valor ...] [data data ...]

 SELECT SUM(valor) FROM vendas WHERE data >= '2026-01-01'
   → lê só as colunas "valor" e "data" (menos I/O), com compressão por coluna
```

| Característica | Benefício |
|---|---|
| **Colunar** | Lê apenas as colunas necessárias; mais I/O eficiente |
| **Compressão** | Valores da mesma coluna são parecidos → alta compressão (menos disco e I/O) |
| **Zone maps** | Metadados por bloco (mín/máx) permitem **pular blocos** que não atendem ao filtro |
| **MPP** | Os dados e o processamento são **distribuídos** entre vários nós/slices que trabalham em paralelo |
| **Compilação de consultas** | Código gerado e armazenado em cache para execuções repetidas |
| **Result cache** | Resultados idênticos servidos do cache |

## Arquitetura de um cluster provisionado

```
                    Aplicações / BI / SQL clients (JDBC/ODBC/Data API)
                                    │
                         ┌──────────▼──────────┐
                         │     LEADER NODE      │  analisa SQL, planeja, compila, coordena, agrega resultados
                         └───┬────────┬─────┬──┘
                             │        │     │
                   ┌─────────▼┐ ┌─────▼────┐ ┌▼─────────┐
                   │ COMPUTE 1│ │COMPUTE 2 │ │COMPUTE n │   cada nó tem CPU, memória e slices
                   │ slice slice│ │slice slice│ │ slice ...│   (slice = unidade de paralelismo)
                   └──────────┘ └──────────┘ └──────────┘
                         armazenamento gerenciado (RA3: managed storage no S3 + cache SSD local)
```

| Componente | Função |
|---|---|
| **Leader node** | Recebe conexões e consultas, gera o plano, distribui trabalho e consolida resultados (sem custo adicional em clusters com mais de um nó) |
| **Compute nodes** | Armazenam dados (ou cache) e executam as etapas do plano |
| **Slices** | Partições de CPU/memória/disco em cada nó; o paralelismo máximo = nº de slices |
| **Managed storage (RA3)** | Armazenamento durável no S3 (gerenciado), com cache SSD local; **computação e armazenamento escalam separadamente** |
| **Cluster subnet group / SG** | Rede na VPC |
| **Parameter group** | Configurações do cluster (WLM, `require_ssl`, etc.) |

### Famílias de nós

| Família | Perfil | Observação |
|---|---|---|
| **RA3** (`ra3.xlplus`, `ra3.4xlarge`, `ra3.16xlarge`) | Armazenamento gerenciado separado da computação | **Recomendada**; paga-se computação por hora e armazenamento por GB-mês |
| **DC2** (SSD local) | Computação+armazenamento acoplados | Legado, para datasets pequenos; evite em projetos novos |
| **DS2** | HDD (descontinuada) | Migrar |

## Provisionado × Serverless

| Critério | **Cluster provisionado** | **Redshift Serverless** |
|---|---|---|
| Administração | Escolhe tipo e número de nós, resize, WLM | **Sem nós**: capacidade em **RPUs**, escala automática |
| Escala | Manual/elastic resize; concurrency scaling | **Automática** (memória/CPU) conforme a carga |
| Pagamento | Nós por hora (reservas possíveis) + armazenamento | **RPU-hora** (por segundo, com mínimo) + armazenamento |
| Carga | Previsível e constante | Esporádica/variável, ambientes de teste |
| Controle | Alto (parâmetros, WLM manual) | Menor, com limites de uso |
| Pausa | Pause/resume manual | Ociosidade não custa computação |

Notas dedicadas ao Serverless e à operação aprofundam cada um.

## Casos de uso

| Caso | Detalhe |
|---|---|
| **BI e dashboards** | QuickSight, Tableau, Power BI sobre fatos e dimensões |
| **Data warehouse corporativo** | Consolida ERP, CRM, e-commerce |
| **Analytics sobre o data lake** | Spectrum consulta S3 sem carregar |
| **Análises quase em tempo real** | Zero-ETL de Aurora/DynamoDB, ingestão por streaming |
| **Machine learning em SQL** | Redshift ML |
| **Compartilhamento de dados** | Data sharing entre equipes e contas |
| **Relatórios regulatórios e históricos** | Grandes volumes com SQL padrão |

### Quando **não** usar

| Situação | Alternativa |
|---|---|
| Transações de alta frequência (OLTP) | RDS/Aurora/DynamoDB |
| Consultas ad hoc ocasionais direto no S3, sem cluster | **Athena** |
| Pesquisa de texto/logs | OpenSearch |
| Processamento Spark/ETL pesado | EMR/Glue |
| Séries temporais de IoT em tempo real | Timestream |

## Redshift × Athena × EMR (visão rápida)

| Critério | **Redshift** | **Athena** | **EMR** |
|---|---|---|---|
| Modelo | Warehouse gerenciado com armazenamento próprio | Consulta serverless direto no S3 | Cluster Hadoop/Spark |
| Desempenho recorrente | **Alto** (dados otimizados, caches) | Bom para ad hoc | Depende do job |
| Concorrência | Alta com WLM/concurrency scaling | Alta (serverless) | Depende |
| Custo | Por nó/RPU | Por TB escaneado | Por instância |
| Uso típico | BI e relatórios recorrentes | Exploração ad hoc, logs | ETL, ML, Spark |

## Exemplo prático

```bash
# Cluster provisionado RA3 com 2 nós, criptografado, na VPC
aws redshift create-cluster --cluster-identifier dw-prod \
  --node-type ra3.xlplus --number-of-nodes 2 \
  --master-username admin --manage-master-password \
  --db-name analytics \
  --cluster-subnet-group-name sg-redshift --vpc-security-group-ids sg-0rs123 \
  --encrypted --kms-key-id alias/redshift \
  --no-publicly-accessible --enhanced-vpc-routing \
  --iam-roles arn:aws:iam::111122223333:role/redshift-s3-access

aws redshift describe-clusters --cluster-identifier dw-prod \
  --query 'Clusters[0].{Estado:ClusterStatus,Endpoint:Endpoint.Address,Nos:NumberOfNodes,Tipo:NodeType}'
```

```sql
-- Exemplo de consulta analítica típica
SELECT d.ano, d.mes, p.categoria, SUM(f.valor) AS receita, COUNT(DISTINCT f.cliente_id) AS clientes
FROM fato_vendas f
JOIN dim_data d ON d.data_id = f.data_id
JOIN dim_produto p ON p.produto_id = f.produto_id
WHERE d.ano = 2026
GROUP BY d.ano, d.mes, p.categoria
ORDER BY d.mes, receita DESC;
```

## Erros comuns e armadilhas

- **Usar o Redshift como banco transacional:** muitos INSERT/UPDATE pequenos e conexões demais.
- **Não modelar para análise** (copiar tabelas normalizadas do OLTP sem pensar em distribuição e ordenação).
- **Escolher DC2/DS2 em projetos novos.**
- **Cluster público** (`PubliclyAccessible=true`) com SG aberto.
- **Superdimensionar** sem medir (ou subdimensionar e gerar filas de consultas).
- **Ignorar o custo de cluster ligado 24×7** para cargas esporádicas (Serverless/pausa).
- **Carregar com `INSERT` linha a linha** em vez de `COPY`.
- **Achar que o Redshift cria índices:** não há índices tradicionais; o desempenho vem de sort keys, distribuição e zone maps.
- **Esperar baixa latência por consulta de milissegundos** em consultas ad hoc grandes.

## 🧩 Quiz de Fixação

1. Por que o armazenamento colunar acelera consultas analíticas?
2. Qual o papel do leader node e dos compute nodes?
3. O que são os nós RA3 e qual sua vantagem?
4. Quando preferir Athena ao Redshift?

**Respostas:**
1) Porque a consulta lê apenas as colunas necessárias, os dados de uma coluna comprimem melhor (menos I/O) e os zone maps permitem pular blocos que não atendem ao filtro.
2) O leader node recebe o SQL, planeja, compila, distribui o trabalho e consolida os resultados; os compute nodes armazenam e processam dados em paralelo, divididos em slices.
3) São nós com armazenamento gerenciado (durável no S3, com cache SSD local), permitindo escalar computação e armazenamento de forma independente e pagar pelo armazenamento por GB.
4) Para exploração ad hoc e esporádica direto no S3, sem manter um cluster, pagando por TB escaneado; o Redshift compensa em consultas recorrentes, BI e alta concorrência.
