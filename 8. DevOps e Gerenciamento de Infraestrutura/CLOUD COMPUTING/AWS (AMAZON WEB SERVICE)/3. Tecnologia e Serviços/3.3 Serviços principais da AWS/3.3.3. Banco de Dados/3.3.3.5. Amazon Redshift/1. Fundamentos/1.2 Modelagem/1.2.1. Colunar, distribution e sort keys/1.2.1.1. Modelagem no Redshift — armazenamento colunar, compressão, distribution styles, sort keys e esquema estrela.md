### Modelagem no Redshift — armazenamento colunar, compressão, distribution styles, sort keys e esquema estrela

> [!warning] Aviso
> Recursos de otimização automática (AUTO distribution, AUTO sort keys, Automatic Table Optimization), encodings e restrições mudam. As recomendações abaixo são práticas consolidadas, mas **meça com os seus dados**. Confirme na documentação. Os comandos SQL **não foram executados**.

No Redshift, o desempenho depende muito de **como as tabelas são desenhadas**: como os dados são **distribuídos** entre os nós, em que **ordem** são armazenados e como são **comprimidos**. Uma boa modelagem faz as junções acontecerem **localmente** em cada nó, os filtros **pularem blocos** inteiros e o I/O cair drasticamente. Esta nota cobre o **esquema dimensional (estrela)**, os **distribution styles**, as **sort keys**, a **compressão** e as **restrições** (que são apenas informativas).

**Analogia:** é a **organização de um arquivo morto entre vários armazéns**. Se os documentos que serão cruzados com frequência ficam no mesmo armazém (distribuição por chave), ninguém precisa transportar caixas entre eles. Se dentro de cada armazém as caixas estão **ordenadas por data**, quem procura um período só abre as prateleiras certas (sort key).

## Esquema dimensional (estrela)

```
                 dim_data            dim_cliente
                    \                 /
                     \               /
                      fato_vendas  (grão: 1 linha por item vendido)
                     /               \
                    /                 \
               dim_produto          dim_loja
```

| Tabela | Conteúdo | Tamanho típico |
|---|---|---|
| **Fato** | Eventos/medidas (valor, quantidade) + chaves das dimensões | **Muito grande** (milhões a bilhões de linhas) |
| **Dimensão** | Descrições (cliente, produto, data, loja), atributos para filtrar/agrupar | **Pequena a média** (milhares a milhões) |

Boas práticas de modelagem dimensional:

1. Defina o **grão** da fato (o que representa uma linha).
2. Use **chaves substitutas** (inteiros) nas dimensões.
3. **Desnormalize** as dimensões (floco de neve só quando necessário).
4. Mantenha tipos de dados **enxutos** (`SMALLINT`/`INT` em vez de `BIGINT` quando possível, `VARCHAR` com tamanho realista).
5. Evite colunas `VARCHAR(65535)` "por segurança": consomem memória em consultas.
6. Mantenha dimensão de **data** própria com atributos (ano, mês, trimestre, feriado).

## Distribution styles (estilo de distribuição)

Define **em qual nó/slice** cada linha é armazenada.

| Estilo | Como distribui | Quando usar | Cuidado |
|---|---|---|---|
| **AUTO** (padrão) | O Redshift escolhe: `ALL` para tabelas pequenas e `EVEN`/`KEY` conforme o uso | **Ponto de partida recomendado** | Pode mudar com o tempo (otimização automática) |
| **EVEN** | Round-robin entre slices | Tabelas sem junções frequentes ou sem chave clara | Junções exigem redistribuição |
| **KEY** | Linhas com o **mesmo valor da chave** vão ao mesmo slice | Junção frequente entre **duas grandes tabelas** (colocalização) | Chave com **distorção** (skew) sobrecarrega um slice |
| **ALL** | **Cópia completa** em cada nó | **Dimensões pequenas** e relativamente estáticas | Multiplica armazenamento e custo de carga; não para tabelas grandes |

```
 Junção fato (KEY=cliente_id) ⨝ dimensão cliente (KEY=cliente_id): cada slice junta localmente (sem movimentar dados)
 Junção fato ⨝ dimensão pequena (ALL): a dimensão já existe em todos os nós → junção local
 Junção sem colocalização: o plano contém DS_DIST_* (redistribui dados pela rede, caro)
```

### Plano de execução e movimentação de dados

No `EXPLAIN`, procure:

| Operação | Significado | Custo |
|---|---|---|
| `DS_DIST_NONE` | Junção local, sem movimentação | **Ótimo** |
| `DS_DIST_ALL_NONE` | Uma tabela é ALL: sem movimentação | Ótimo |
| `DS_DIST_INNER` / `DS_DIST_OUTER` | Redistribui uma das tabelas | Médio |
| `DS_BCAST_INNER` | **Broadcast** da tabela interna a todos os nós | Caro se a tabela é grande |
| `DS_DIST_BOTH` | Redistribui as duas | **Mais caro** |

### Como escolher a chave de distribuição

1. Identifique as **maiores tabelas** e as **junções mais frequentes/pesadas**.
2. Use como `DISTKEY` a coluna usada na junção entre as duas maiores tabelas.
3. Verifique a **cardinalidade e a distorção** (`SVV_TABLE_INFO`: `skew_rows`); evite chaves com muito valor nulo ou dominado por poucos valores.
4. Dimensões pequenas: `ALL` (ou deixe `AUTO`).
5. Reavalie quando os padrões de consulta mudarem.

```sql
CREATE TABLE fato_vendas (
  venda_id     BIGINT,
  data_id      INT,
  cliente_id   INT,
  produto_id   INT,
  quantidade   SMALLINT,
  valor        DECIMAL(12,2)
)
DISTSTYLE KEY DISTKEY (cliente_id)
SORTKEY (data_id);

CREATE TABLE dim_produto (produto_id INT, nome VARCHAR(200), categoria VARCHAR(80))
DISTSTYLE ALL;

-- Verificar distribuição e distorção
SELECT "table", diststyle, tbl_rows, skew_rows, unsorted, pct_used
FROM svv_table_info ORDER BY size DESC LIMIT 20;
```

## Sort keys (chaves de ordenação)

Definem a **ordem física** das linhas em cada slice. Combinadas com os **zone maps** (mín/máx por bloco de 1 MB), permitem **pular blocos** inteiros em filtros e junções.

| Tipo | Como funciona | Quando usar |
|---|---|---|
| **AUTO** (padrão) | O Redshift define e ajusta | Ponto de partida recomendado |
| **Compound** | Ordena por colunas na ordem declarada (como um índice composto) | Filtros pela **primeira coluna** (ou prefixo): `data`, `evento` |
| **Interleaved** | Dá peso igual a cada coluna da chave | Consultas com filtros variados em colunas diferentes (uso restrito; custo maior de manutenção) |

Regras práticas:

- A **coluna de data/hora** costuma ser a melhor primeira coluna da sort key em fatos (filtros por período).
- Evite sort keys com colunas de alta cardinalidade que raramente são filtradas.
- Colunas usadas em `JOIN` merge podem se beneficiar de sort key igual à distribuição.
- **Dados inseridos fora de ordem** aumentam a região "não ordenada" (`unsorted`): `VACUUM SORT` (automático em segundo plano) reorganiza.
- Use `SORTKEY` em dimensões grandes usadas em filtros.

```sql
-- Consulta que se beneficia da sort key por data (poda de blocos)
SELECT SUM(valor) FROM fato_vendas WHERE data_id BETWEEN 20260101 AND 20260131;
-- EXPLAIN mostra "Seq Scan ... Filter"; o ganho está na leitura de poucos blocos (ver SVL_QUERY_SUMMARY: blocos lidos)
```

## Compressão (column encodings)

Cada coluna é comprimida com um **encoding** adequado ao tipo e à distribuição dos valores.

| Encoding | Uso típico |
|---|---|
| **AZ64** | Tipos numéricos, data/hora (padrão moderno, bom equilíbrio) |
| **ZSTD** | Texto e geral (ótima compressão) |
| **LZO**, **BYTEDICT**, **RUNLENGTH**, **DELTA**, **MOSTLY8/16/32**, **TEXT255/32K** | Casos específicos (legado/otimização) |
| **RAW** (sem compressão) | Colunas de sort key de baixa cardinalidade ou colunas boolean, conforme recomendação |

- Com `COPY` em tabela vazia, o Redshift pode **aplicar compressão automática** (`COMPUPDATE`).
- Com **ATO (Automatic Table Optimization)**, o serviço ajusta distribuição, sort key e encodings automaticamente conforme o uso (verifique `ALTER TABLE ... ALTER DISTSTYLE AUTO`/`ALTER SORTKEY AUTO`).
- Verifique: `ANALYZE COMPRESSION tabela;` e `SVV_TABLE_INFO`.

## Restrições (constraints) e identidade

| Restrição | Comportamento no Redshift |
|---|---|
| `PRIMARY KEY`, `FOREIGN KEY`, `UNIQUE` | **Informativas**: **não são impostas**; o otimizador as usa para planejar. A aplicação/ETL precisa garantir unicidade |
| `NOT NULL` | **Imposta** |
| `DEFAULT` / `IDENTITY` | Geração de valores (identity não é estritamente sequencial entre slices) |

Implicações: duplicatas podem entrar se o ETL não deduplicar; use **staging + MERGE** (o Redshift suporta `MERGE`) ou delete+insert em transação.

```sql
-- Upsert padrão com staging
BEGIN;
MERGE INTO dim_cliente USING stg_cliente s ON dim_cliente.cliente_id = s.cliente_id
WHEN MATCHED THEN UPDATE SET nome = s.nome, cidade = s.cidade
WHEN NOT MATCHED THEN INSERT VALUES (s.cliente_id, s.nome, s.cidade);
COMMIT;
```

## Manutenção das tabelas

| Tarefa | O que faz | Automação |
|---|---|---|
| **VACUUM** | Recupera espaço de linhas excluídas e reordena | Automático em segundo plano (`VACUUM DELETE`/`SORT`); manual em grandes cargas |
| **ANALYZE** | Atualiza estatísticas para o otimizador | Automático (`ANALYZE` automático); manual após cargas grandes |
| **Table maintenance (ATO)** | Ajusta DIST/SORT automaticamente | Habilitado com `AUTO` |

Após carregar bastante dado: `ANALYZE` evita planos ruins; muitas exclusões/atualizações deixam "linhas fantasmas" que `VACUUM` limpa.

## Exemplo prático

Modelagem do DW de vendas de uma rede de varejo (5 bilhões de linhas de fato, 800 mil clientes, 40 mil produtos):

| Tabela | DIST | SORT | Observação |
|---|---|---|---|
| `fato_vendas` | KEY (`cliente_id`) | `data_id` | Junção principal com clientes; filtros por período |
| `dim_cliente` | KEY (`cliente_id`) | `cliente_id` | Colocalizada com a fato |
| `dim_produto` | ALL | `produto_id` | 40 mil linhas: cópia em cada nó |
| `dim_data` | ALL | `data_id` | Pequena |
| `dim_loja` | ALL | `loja_id` | Pequena |

1. Verificar distorção: `skew_rows` de `fato_vendas` ≈ 1,05 (aceitável).
2. Teste: relatório "receita por categoria e mês" cai de 48 s para 6 s após colocalizar `fato_vendas` e `dim_cliente` e ordenar por data.
3. `EXPLAIN` mostra `DS_DIST_NONE` nas junções cliente e `DS_DIST_ALL_NONE` nas demais.
4. Carga diária via `COPY` de arquivos Parquet no S3 (por data), `ANALYZE` automático e verificação semanal de `unsorted`.
5. Manter `AUTO` nas tabelas pequenas e delegar ao ATO o ajuste fino.

## Erros comuns e armadilhas

- **Chave de distribuição com distorção** (muitos nulos ou um valor dominante): um slice trabalha mais que os outros.
- **ALL em tabelas grandes:** duplica armazenamento e lentifica cargas.
- **Sort key em colunas que ninguém filtra.**
- **Ignorar `DS_BCAST_INNER`/`DS_DIST_BOTH`** no plano e a movimentação de dados.
- **Não deduplicar** esperando `PRIMARY KEY` impor unicidade.
- **`VARCHAR(65535)` em todas as colunas.**
- **Interleaved sort keys** por padrão (manutenção cara).
- **Estatísticas desatualizadas** após cargas (planos ruins).
- **Cargas fora de ordem** sem `VACUUM SORT`.
- **Normalizar demais** (3FN) e esperar desempenho de DW.

## 🧩 Quiz de Fixação

1. Quando usar `DISTSTYLE KEY` e quando `ALL`?
2. Qual a função da sort key e dos zone maps?
3. As chaves primária e estrangeira são impostas no Redshift?
4. O que indica `DS_BCAST_INNER` no plano de execução?

**Respostas:**
1) KEY para colocalizar as linhas de duas grandes tabelas que se juntam com frequência pela mesma coluna; ALL para dimensões pequenas e estáticas copiadas em todos os nós, evitando redistribuição nas junções.
2) A sort key define a ordem física dos dados e, com os zone maps (mín/máx por bloco), permite pular blocos que não atendem ao filtro, reduzindo o I/O.
3) Não: são informativas, usadas apenas pelo otimizador; a unicidade e a integridade referencial devem ser garantidas pelo ETL/aplicação. Apenas NOT NULL é imposta.
4) Que uma tabela (a interna) está sendo transmitida (broadcast) para todos os nós para a junção, o que é caro se a tabela for grande e sugere revisar a distribuição.
