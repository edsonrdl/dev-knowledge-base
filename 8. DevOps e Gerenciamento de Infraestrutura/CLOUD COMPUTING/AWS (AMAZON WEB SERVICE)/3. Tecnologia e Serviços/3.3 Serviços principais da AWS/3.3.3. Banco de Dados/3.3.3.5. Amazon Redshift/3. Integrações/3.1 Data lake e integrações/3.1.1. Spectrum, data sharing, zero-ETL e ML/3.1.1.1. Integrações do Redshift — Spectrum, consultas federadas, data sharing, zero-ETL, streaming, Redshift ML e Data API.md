### Integrações do Redshift — Spectrum, consultas federadas, data sharing, zero-ETL, streaming, Redshift ML e Data API

> [!warning] Aviso
> Esta é uma área de **muita evolução**: fontes suportadas pelo zero-ETL, formatos do Spectrum, regras de data sharing, integrações de ML e limites mudam. Alguns recursos exigem versões, regiões ou tipos de cluster específicos. **Confirme a disponibilidade na documentação.** Os comandos **não foram executados**.

Um data warehouse moderno raramente vive isolado: precisa **consultar o data lake no S3**, **ler bancos operacionais**, **compartilhar dados** entre equipes, **ingerir eventos em tempo quase real**, **treinar e aplicar modelos de ML** e **ser acessado por aplicações**. O Redshift tem recursos nativos para cada um: **Spectrum**, **consultas federadas**, **data sharing**, **zero-ETL**, **ingestão por streaming**, **Redshift ML** e a **Data API**. Esta nota mostra o que cada um faz, quando usar e os cuidados.

**Analogia:** o Redshift é o **departamento de análises** de uma empresa; as integrações são as **portas e pontes** para o **depósito de arquivos** (S3/Spectrum), os **sistemas das lojas** (federação), **departamentos parceiros** (data sharing), a **correia transportadora** de dados novos (zero-ETL/streaming) e a **consultoria de IA** (ML).

## Redshift Spectrum (consultar o data lake)

O **Spectrum** executa consultas SQL **diretamente sobre arquivos no S3** (Parquet, ORC, CSV, JSON, Avro etc.), sem carregá-los, por meio de **tabelas externas** registradas no **Glue Data Catalog** (ou Lake Formation / metastore Hive).

```
 Redshift (cluster/Serverless) ──consulta──► Camada Spectrum (fleet gerenciada, milhares de nós) ──lê──► S3 (data lake)
        │ junção local (dim_cliente) ◄── resultados parciais agregados ──┘
```

| Característica | Detalhe |
|---|---|
| **Schema externo** | `CREATE EXTERNAL SCHEMA` aponta para um database do Glue Data Catalog e uma IAM role |
| **Tabelas externas** | Metadados no catálogo; dados no S3 |
| **Junções** | Pode juntar tabelas externas com tabelas locais |
| **Custo** | Por **TB escaneado** no S3 (além do cluster) |
| **Otimização** | **Particionar** por colunas de filtro (data), usar **Parquet/ORC** (colunar + compressão), arquivos de 128 MB-1 GB, `pushdown` de filtros |
| **Casos** | Dados frios/históricos no lake, join do DW com o lake, ELT |

```sql
CREATE EXTERNAL SCHEMA lake FROM DATA CATALOG DATABASE 'datalake'
IAM_ROLE 'arn:aws:iam::111122223333:role/redshift-spectrum'
CREATE EXTERNAL DATABASE IF NOT EXISTS;

-- Tabela externa particionada em Parquet
CREATE EXTERNAL TABLE lake.eventos (id BIGINT, usuario INT, tipo VARCHAR(30), valor DECIMAL(12,2))
PARTITIONED BY (dt DATE) STORED AS PARQUET LOCATION 's3://datalake/eventos/';
ALTER TABLE lake.eventos ADD PARTITION (dt='2026-11-06') LOCATION 's3://datalake/eventos/dt=2026-11-06/';

SELECT d.regiao, SUM(e.valor) FROM lake.eventos e JOIN dim_usuario d ON d.usuario_id = e.usuario
WHERE e.dt BETWEEN '2026-11-01' AND '2026-11-06' GROUP BY 1;     -- poda de partições reduz o escaneamento
```

Padrão **lakehouse**: dados quentes no Redshift (rápidos), dados frios no S3 consultados via Spectrum; **Athena** é a alternativa sem cluster.

## Consultas federadas

Consultam diretamente **bancos operacionais** (RDS/Aurora PostgreSQL e MySQL, e outras fontes) sem ETL, a partir do Redshift.

| Característica | Detalhe |
|---|---|
| **Fontes** | Aurora/RDS PostgreSQL e MySQL (e outras conforme a oferta) |
| **Credenciais** | Secrets Manager |
| **Uso** | Dados muito recentes, tabelas de referência, validações |
| **Cuidado** | Latência e carga na fonte; **não substitui** carregar os dados para consultas pesadas; evite junções grandes |

```sql
CREATE EXTERNAL SCHEMA pedidos_oltp FROM POSTGRES DATABASE 'loja' SCHEMA 'public'
URI 'loja-aurora.cluster-xxxx.sa-east-1.rds.amazonaws.com' PORT 5432
IAM_ROLE 'arn:aws:iam::111122223333:role/redshift-federated' SECRET_ARN 'arn:aws:secretsmanager:...:secret:loja-ro';
SELECT COUNT(*) FROM pedidos_oltp.pedidos WHERE criado > current_date - 1;
```

## Data sharing (compartilhamento sem cópia)

Permite que um cluster/workgroup **produtor** compartilhe dados **ao vivo** com **consumidores**, sem copiar ou mover dados, com isolamento de computação.

```
 Produtor (ETL, namespace A)  ──datashare──►  Consumidor 1 (BI, namespace B)
 gravações e atualizações                    Consumidor 2 (ciência de dados, outra conta/região)
 leituras sempre veem o dado atual (transacionalmente consistente)
```

| Característica | Detalhe |
|---|---|
| **Escopo** | Mesma conta, **entre contas** e **entre regiões** (cross-region com custo de transferência) |
| **Conteúdo** | Esquemas, tabelas, views, UDFs |
| **Consumidores** | Provisionado ou Serverless |
| **Acesso** | Somente leitura (e escrita em compartilhamentos com *write* em recursos mais recentes) |
| **Governança** | Controle por `GRANT USAGE ON DATASHARE`, integração com **Lake Formation** e **AWS Data Exchange** (monetização) |
| **Benefício** | Isolamento de cargas (ETL × BI), uma única fonte de verdade, sem duplicação |

```sql
-- Produtor
CREATE DATASHARE vendas_share;
ALTER DATASHARE vendas_share ADD SCHEMA publico;
ALTER DATASHARE vendas_share ADD ALL TABLES IN SCHEMA publico;
GRANT USAGE ON DATASHARE vendas_share TO NAMESPACE 'ns-consumidor-guid';

-- Consumidor
CREATE DATABASE vendas_compartilhado FROM DATASHARE vendas_share OF NAMESPACE 'ns-produtor-guid';
SELECT COUNT(*) FROM vendas_compartilhado.publico.fato_vendas;
```

## Zero-ETL

Integração **gerenciada** que replica dados de fontes operacionais para o Redshift em **quase tempo real**, **sem construir pipelines**.

| Fonte | Detalhe |
|---|---|
| **Aurora MySQL / PostgreSQL** | Replicação contínua |
| **RDS MySQL** | Idem (conforme versão) |
| **DynamoDB** | Dados NoSQL para análise SQL |
| **Aplicações SaaS** (Salesforce, SAP, ServiceNow etc., via AWS Glue zero-ETL) | Conforme a oferta |

```
 Aurora/DynamoDB (OLTP) ──replicação gerenciada (segundos)──► Redshift (OLAP) ──► BI/ML
```

| Característica | Detalhe |
|---|---|
| **Latência** | Segundos a poucos minutos |
| **Impacto na fonte** | Baixo |
| **Esquema** | Reflete tabelas escolhidas, com filtros de bancos/tabelas |
| **Limitações** | DDLs e tipos suportados, regiões, versões, custo do destino |
| **Alternativas** | DMS CDC, Glue, Kinesis, exportação periódica |

Boa prática: use o zero-ETL para análises recentes e **modele camadas** (silver/gold) por cima com views materializadas.

## Ingestão por streaming

O Redshift ingere **diretamente** de **Kinesis Data Streams** e **Amazon MSK/Kafka** usando **views materializadas**, em latência de segundos, sem Firehose/S3 intermediário.

```sql
CREATE EXTERNAL SCHEMA kds FROM KINESIS IAM_ROLE default;
CREATE MATERIALIZED VIEW mv_eventos AUTO REFRESH YES AS
SELECT approximate_arrival_timestamp, JSON_PARSE(kinesis_data) AS dado
FROM kds."stream-eventos";
```

Use para painéis operacionais em tempo quase real; mantenha o processamento pesado para etapas posteriores.

## Redshift ML

Cria, treina e usa **modelos de machine learning** com **SQL**, delegando o treinamento ao **SageMaker** (inclusive AutoML) e executando a **inferência dentro do Redshift**.

```sql
CREATE MODEL churn_modelo
FROM (SELECT idade, plano, meses_de_casa, chamados_suporte, churn FROM clientes_historico)
TARGET churn
FUNCTION prever_churn
IAM_ROLE default
SETTINGS (S3_BUCKET 'ml-redshift-artefatos', MAX_RUNTIME 3600);

SELECT cliente_id, prever_churn(idade, plano, meses_de_casa, chamados_suporte) AS prob_churn
FROM clientes_atuais ORDER BY prob_churn DESC LIMIT 100;
```

| Aspecto | Detalhe |
|---|---|
| **Quem usa** | Analistas de SQL (sem escrever código de ML) |
| **Modelos** | AutoML, XGBoost, modelos próprios no SageMaker, modelos de linguagem (integração com Bedrock em recursos recentes) |
| **Custo** | Treinamento no SageMaker + armazenamento no S3; inferência local |
| **Cuidados** | Qualidade/viés dos dados, governança de modelos, reprodutibilidade |

## Data API e acesso programático

| Mecanismo | Uso |
|---|---|
| **Data API** (HTTP) | Executa SQL por API (`ExecuteStatement`, `BatchExecuteStatement`), assíncrona, autenticada por **IAM + Secrets Manager**; ideal para **Lambda**, Step Functions e aplicações sem conexão persistente |
| **JDBC/ODBC/Python** (driver `redshift_connector`) | BI e aplicações tradicionais |
| **Query Editor v2** | Console web para SQL |
| **Scheduled queries** | Consultas agendadas (EventBridge) |
| **Python/Notebooks** | SageMaker/Jupyter |

```bash
aws redshift-data execute-statement --workgroup-name wg-bi --database analytics --secret-arn $SECRET \
  --sql "SELECT COUNT(*) FROM fato_vendas WHERE data_id = 20260106"
aws redshift-data describe-statement --id $STATEMENT_ID
aws redshift-data get-statement-result --id $STATEMENT_ID
```

## Como escolher a integração

| Necessidade | Recurso |
|---|---|
| Consultar dados históricos/frios no S3 sem carregar | **Spectrum** |
| Ler o banco operacional ocasionalmente, sem ETL | **Consulta federada** |
| Compartilhar dados entre equipes/contas sem copiar | **Data sharing** |
| Dados do Aurora/DynamoDB quase em tempo real | **Zero-ETL** |
| Eventos de Kinesis/Kafka em segundos | **Streaming ingestion** |
| Previsões por SQL | **Redshift ML** |
| Aplicações serverless executando SQL | **Data API** |

## Exemplo prático

Plataforma de varejo com DW no Redshift, data lake no S3 e Aurora operacional:

1. **Zero-ETL** do Aurora (pedidos, clientes) para o Redshift: relatórios quase em tempo real de vendas do dia.
2. **Histórico de navegação** (10 TB em Parquet particionado por dia) no S3, consultado via **Spectrum**; só os 90 dias mais recentes são carregados no Redshift.
3. **Streaming ingestion** de eventos de carrinho do Kinesis em uma view materializada para o painel "ao vivo".
4. **Data sharing:** namespace de ETL (produtor) compartilha com o de BI (consumidor) e com a conta de Ciência de Dados em outra região; sem duplicação.
5. **Redshift ML:** modelo de propensão a compra treinado semanalmente; pontuação em lote por SQL.
6. **Data API** chamada por funções Lambda de relatórios agendados que exportam CSVs para o S3.
7. **Governança:** Lake Formation para permissões comuns; custo de Spectrum monitorado por TB escaneado.

## Erros comuns e armadilhas

- **Spectrum sem partições e em CSV:** escaneia tudo e custa muito.
- **Usar consulta federada como substituta de carga** para análises pesadas.
- **Data sharing sem governança** (consumidores com acesso a dados sensíveis).
- **Esperar que zero-ETL cubra todos os tipos de dados/DDL.**
- **Ignorar custo de transferência** em data sharing entre regiões.
- **Redshift ML sem validação** da qualidade e do viés do modelo.
- **Permissões amplas na IAM role** (S3 total, Lambda, SageMaker).
- **Streaming ingestion sem controle de volume** (view materializada enorme).
- **Data API sem tratamento assíncrono** e de erros.
- **Misturar muitas fontes sem catálogo/governança** (Glue/Lake Formation).

## 🧩 Quiz de Fixação

1. Como o Spectrum acessa dados do S3 e como reduzir seu custo?
2. Qual a diferença entre data sharing e simplesmente copiar tabelas?
3. Quando usar zero-ETL em vez de consulta federada?
4. Para que serve a Data API?

**Respostas:**
1) Por tabelas externas registradas no Glue Data Catalog, lendo arquivos do S3 com uma frota gerenciada; o custo é por TB escaneado, reduzido com particionamento, formatos colunares (Parquet/ORC) e arquivos de tamanho adequado.
2) O data sharing dá acesso ao vivo e transacionalmente consistente aos dados do produtor, sem duplicar armazenamento nem pipelines e isolando as computações; a cópia gera custo, atraso e inconsistência.
3) Quando se precisa de dados operacionais replicados para análises recorrentes e pesadas, quase em tempo real, sem carga na fonte; a consulta federada serve para leituras ocasionais e pontuais.
4) Executar SQL por API HTTP assíncrona, autenticada por IAM e Secrets Manager, sem driver nem conexões persistentes, ideal para Lambda e aplicações serverless.
