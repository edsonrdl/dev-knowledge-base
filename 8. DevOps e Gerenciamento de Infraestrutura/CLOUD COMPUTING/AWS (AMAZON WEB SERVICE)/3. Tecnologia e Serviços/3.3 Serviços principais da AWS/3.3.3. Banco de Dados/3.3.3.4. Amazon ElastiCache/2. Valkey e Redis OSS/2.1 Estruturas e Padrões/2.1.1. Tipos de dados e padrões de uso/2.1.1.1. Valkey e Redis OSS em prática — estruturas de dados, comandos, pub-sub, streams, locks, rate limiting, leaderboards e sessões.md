### Valkey e Redis OSS em prática — estruturas de dados, comandos, pub/sub, streams, locks, rate limiting, leaderboards e sessões

> [!warning] Aviso
> Comandos, módulos, versões e limites variam entre Valkey, Redis OSS e versões do ElastiCache (por exemplo, suporte a módulos de busca vetorial, JSON ou a funções). Os exemplos são **ilustrativos e não foram executados**. **Confirme a compatibilidade na documentação.**

O diferencial do Valkey/Redis OSS sobre um cache simples é o conjunto de **estruturas de dados nativas** e de **comandos atômicos** que as manipulam no servidor. Em vez de ler um blob, alterar na aplicação e gravar de volta, você pede ao servidor que **some**, **adicione**, **ordene** ou **publique**, com uma só operação atômica e em microssegundos. Esta nota ensina as estruturas, os padrões mais usados (**sessões, rate limiting, locks, leaderboards, filas, Pub/Sub, Streams**) e as boas práticas de comandos.

**Analogia:** um cache simples é uma **gaveta** onde se guarda e se retira papéis inteiros. O Valkey/Redis é uma **bancada de ferramentas**: contador, fila, ranking e quadro de avisos prontos, com instruções que o próprio servidor executa sem que ninguém mais interfira no meio da operação.

## Modelo de execução (por que é atômico e rápido)

| Característica | Detalhe |
|---|---|
| **Servidor de comandos single-thread** | Cada comando executa **inteiro** antes do próximo: operações são **atômicas** sem locks |
| **Em memória** | Latência de microssegundos; o gargalo costuma ser rede e CPU de um núcleo |
| **I/O multithread** (versões recentes) | Leitura/escrita de rede em threads, comandos continuam serializados |
| **Consequência** | Um comando **lento (O(N))** bloqueia todos: evite `KEYS *`, `SMEMBERS` em conjuntos enormes, `FLUSHALL` etc. |
| **Pipeline** | Enviar vários comandos sem esperar cada resposta reduz o custo de rede |
| **Transações** | `MULTI`/`EXEC` agrupam comandos; `WATCH` dá locking otimista |
| **Scripts** | Lua (`EVAL`) e *Functions* executam lógica composta atomicamente no servidor |

## Estruturas de dados

| Estrutura | Comandos-chave | Uso típico |
|---|---|---|
| **String** | `SET`/`GET`, `INCR`/`DECR`, `SETEX`, `SET NX` | Cache de objetos serializados, contadores, flags, locks |
| **Hash** | `HSET`/`HGET`/`HGETALL`/`HINCRBY` | Objetos com campos (perfil, sessão): altera um campo sem reescrever o resto |
| **List** | `LPUSH`/`RPUSH`/`LPOP`/`BRPOP`/`LRANGE` | Filas simples, últimos N itens |
| **Set** | `SADD`/`SMEMBERS`/`SISMEMBER`/`SINTER`/`SUNION` | Tags, relacionamentos, únicos, interseção de conjuntos |
| **Sorted Set** | `ZADD`/`ZRANGE`/`ZREVRANK`/`ZINCRBY`/`ZRANGEBYSCORE` | **Rankings**, filas por prioridade/tempo, janelas deslizantes |
| **Bitmap / Bitfield** | `SETBIT`/`GETBIT`/`BITCOUNT` | Presença diária de usuários, flags compactas |
| **HyperLogLog** | `PFADD`/`PFCOUNT` | Contagem **aproximada** de únicos (~0,81% erro) com 12 KB |
| **Geo** | `GEOADD`/`GEOSEARCH` | Pontos de interesse, "perto de mim" |
| **Stream** | `XADD`/`XREADGROUP`/`XACK` | Log de eventos com consumer groups |
| **Pub/Sub** | `PUBLISH`/`SUBSCRIBE` | Notificações em tempo real (sem persistência) |
| **JSON / busca / vetor** (módulos, se suportados) | `JSON.*`, `FT.*` | Documentos, busca, similaridade (confirme disponibilidade) |

### Exemplos de comandos

```text
SET sessao:abc123 "{...}" EX 1800                 # sessão com expiração em 30 min
HSET usuario:42 nome "Ana" plano "pro" visitas 0  # objeto em hash
HINCRBY usuario:42 visitas 1                      # incremento atômico de um campo
ZADD ranking:semana 1500 "ana" 1320 "bruno"       # pontuações
ZREVRANGE ranking:semana 0 9 WITHSCORES           # top 10
SADD seguidores:42 7 9 11                          # conjunto
SINTER seguidores:42 seguidores:7                  # amigos em comum
PFADD visitantes:2026-11-06 "u1" "u2" "u1"         # únicos aproximados
PFCOUNT visitantes:2026-11-06                      # ≈ 2
GEOADD lojas -46.63 -23.55 "loja-sp" -43.17 -22.90 "loja-rj"
GEOSEARCH lojas FROMLONLAT -46.6 -23.5 BYRADIUS 20 km WITHDIST
```

## Padrões de uso

### 1. Sessões web

```text
HSET sessao:abc123 usuario 42 papel "admin" criado 1730900000
EXPIRE sessao:abc123 1800
# A cada requisição: EXPIRE sessao:abc123 1800 (sliding expiration)
```

Vantagens: sessão compartilhada entre N instâncias; logout invalidando `DEL`. Segurança: ID de sessão aleatório e longo; TLS; dados sensíveis mínimos.

### 2. Rate limiting

**Janela fixa (simples):**

```text
INCR limite:ip:203.0.113.5:202611061405      # chave por janela de 1 min
EXPIRE limite:ip:203.0.113.5:202611061405 60 # só na primeira vez
# se o valor > limite → rejeitar (HTTP 429)
```

**Janela deslizante com sorted set:** `ZADD limite:u1 <timestamp> <id>`, `ZREMRANGEBYSCORE limite:u1 0 <agora-janela>`, `ZCARD` → conta eventos na janela (use Lua para atomicidade). **Token bucket** com script Lua guarda `tokens` e `ultimo`.

### 3. Locks distribuídos

```text
SET lock:pedido:123 <token-unico> NX PX 30000     # adquire (só se não existir) com expiração
# liberar: só se o token for o seu (script Lua atômico)
if redis.call("GET", KEYS[1]) == ARGV[1] then return redis.call("DEL", KEYS[1]) else return 0 end
```

Notas: tempo de expiração maior que a seção crítica; renovação (*watchdog*); o padrão de lock com **uma única instância** não é totalmente seguro em falhas (failover pode perder o lock); para garantias fortes use um sistema de consenso ou **fencing tokens**. Para locks leves e eficiência (não correção estrita), é aceitável.

### 4. Leaderboards (rankings)

```text
ZINCRBY ranking:jogo 50 "ana"          # soma pontos
ZREVRANK ranking:jogo "ana"            # posição de ana (0 = 1º)
ZREVRANGE ranking:jogo 0 99 WITHSCORES # top 100
ZRANGEBYSCORE ranking:jogo 1000 2000   # faixa de pontuação
```

Complexidade O(log N): suporta milhões de jogadores em tempo real.

### 5. Filas e mensageria

| Mecanismo | Característica |
|---|---|
| **List** (`LPUSH`/`BRPOP`) | Fila simples; sem confirmação — itens se perdem se o consumidor cair após o `POP` (use `LMOVE`/`BLMOVE` para uma lista de "em processamento") |
| **Streams** (`XADD`/`XREADGROUP`/`XACK`) | Log persistente, **consumer groups**, confirmação (`XACK`), reentrega de pendentes (`XPENDING`/`XCLAIM`) |
| **Pub/Sub** | Difusão em tempo real; **sem persistência**: assinante offline perde mensagens |

Para filas confiáveis em larga escala, **SQS/Kinesis/EventBridge** costumam ser a escolha; Streams do Valkey/Redis servem para pipelines leves de baixa latência.

```text
XADD pedidos * id 123 valor 59.90                       # produz evento
XGROUP CREATE pedidos workers $ MKSTREAM                 # grupo de consumidores
XREADGROUP GROUP workers w1 COUNT 10 BLOCK 5000 STREAMS pedidos >   # consome
XACK pedidos workers 1730900000000-0                     # confirma processamento
```

### 6. Contagem de únicos e presença

HyperLogLog para visitantes únicos; Bitmap (`SETBIT presenca:2026-11-06 <idUsuario> 1`, `BITCOUNT`) para presença diária com 1 bit por usuário.

### 7. Cache de objetos e invalidação por versão

`SET produto:42:v7 <json> EX 3600` com mudança de versão na atualização (ver nota de estratégias).

### 8. Busca vetorial (quando suportada)

Armazenar embeddings e buscar por similaridade para RAG e recomendações; confirme módulos e versões disponíveis no ElastiCache antes de projetar (alternativas: Aurora/RDS pgvector, OpenSearch).

## Boas práticas de comandos e dados

| Boas práticas | Por quê |
|---|---|
| **`SCAN` em vez de `KEYS`** | `KEYS` bloqueia o servidor |
| **Pipelines e `MGET`/`MSET`** | Menos idas e voltas de rede |
| **Chaves curtas e padronizadas** (`dominio:entidade:id`) | Memória e legibilidade |
| **TTL em quase tudo** | Evita acúmulo; memória previsível |
| **Evitar valores grandes** (> alguns KB a MB) e coleções gigantes (milhões de membros) | Big keys bloqueiam e consomem rede; divida em shards (`lista:1`, `lista:2`) |
| **Hash para objetos pequenos** | Mais eficiente em memória que várias chaves string |
| **Lua/Functions** para operações compostas | Atomicidade e menos latência |
| **Pool de conexões** e reuso | Abrir conexão é caro; limite de conexões |
| **`UNLINK` em vez de `DEL`** para chaves grandes | Exclusão assíncrona |
| **Evitar `FLUSHALL`/`FLUSHDB`** em produção | Cold start e risco |
| **Medir com `SLOWLOG` e `LATENCY`** | Achar comandos lentos |
| **Uso de `MULTI/EXEC` e `WATCH` com cuidado** | No cluster mode, as chaves devem estar no mesmo slot (hash tags `{}`) |

### Hash tags no cluster mode

Para operações multi-chave no cluster, as chaves devem estar no **mesmo slot**: use `{usuario:42}:perfil` e `{usuario:42}:carrinho` — a parte entre chaves define o slot.

## Persistência e durabilidade

| Mecanismo | No ElastiCache |
|---|---|
| **Snapshots (RDB)** | Sim, manuais e automáticos (veja a nota de operação) |
| **AOF** | Não disponível nas versões atuais do ElastiCache |
| **Réplicas Multi-AZ** | Replicação **assíncrona**: no failover pode haver perda das últimas gravações |
| **Durabilidade forte** | Use **Amazon MemoryDB** (log transacional multi-AZ) |

Regra: trate o ElastiCache como **volátil**; tudo que não pode ser perdido tem uma fonte durável.

## Exemplo prático

Jogo online com ranking global, sessões, limitação de ações e eventos de partida:

1. **Sessões:** `HSET sessao:{id}` + `EXPIRE 1800`, renovado a cada requisição.
2. **Ranking:** `ZINCRBY ranking:global <pontos> <jogador>`; top 100 via `ZREVRANGE`; posição do jogador via `ZREVRANK`; ranking semanal em outra chave com `EXPIRE` de 8 dias.
3. **Rate limit de ações:** script Lua de token bucket por jogador (atômico).
4. **Eventos de partida:** `XADD partida:{id}` + consumer group para o serviço de estatísticas; consumo com `XACK` e reprocessamento de pendentes.
5. **Matchmaking:** sorted set por nível (`ZRANGEBYSCORE` para achar parceiros) e lock `SET NX PX` por sala.
6. **Observabilidade:** `EngineCPUUtilization`, `SLOWLOG`, hit ratio, `Evictions`; alarme se `CurrConnections` se aproxima do limite.
7. **Persistência:** o ranking é reconstruível a partir das partidas no banco (Aurora/DynamoDB) caso o cache seja perdido; resultados finais vão ao banco durável.

## Erros comuns e armadilhas

- **Usar `KEYS *`** em produção.
- **Coleções gigantes numa chave só** (um sorted set com bilhões de membros) e hot keys.
- **Pub/Sub para mensagens que não podem ser perdidas.**
- **Lock sem token/expiração ou liberado por quem não é dono.**
- **Rate limit sem atomicidade** (`GET` + `SET` separados): condições de corrida.
- **Esquecer TTL** em sessões e chaves temporárias.
- **Depender de persistência do ElastiCache** como banco de dados.
- **Operações multi-chave no cluster mode sem hash tags:** erro `CROSSSLOT`.
- **Conexões sem pool** (tempestade de conexões).
- **Valores enormes** saturando rede e bloqueando o servidor.
- **Sem monitorar `SLOWLOG`:** comandos lentos passam despercebidos.

## 🧩 Quiz de Fixação

1. Por que as operações do Valkey/Redis são atômicas e qual o risco dessa característica?
2. Que estrutura usar para um ranking em tempo real e quais comandos?
3. Como implementar um lock distribuído básico e qual seu limite?
4. Por que usar `SCAN` e não `KEYS`?

**Respostas:**
1) Porque os comandos são executados um por vez por um único thread, sem interferência no meio de uma operação. O risco é que um comando lento (O(N)) bloqueia todos os outros clientes.
2) Sorted set: `ZADD`/`ZINCRBY` para pontuar, `ZREVRANGE` para o top N e `ZREVRANK` para a posição de um jogador, todos O(log N).
3) `SET chave token NX PX tempo` para adquirir e um script Lua que apaga a chave somente se o token coincidir, para liberar. O limite: com uma única instância e replicação assíncrona, um failover pode perder o lock; para garantias fortes são necessários fencing tokens ou consenso.
4) Porque `KEYS` percorre todas as chaves de uma vez e bloqueia o servidor; `SCAN` itera em lotes pequenos sem bloquear por muito tempo.
