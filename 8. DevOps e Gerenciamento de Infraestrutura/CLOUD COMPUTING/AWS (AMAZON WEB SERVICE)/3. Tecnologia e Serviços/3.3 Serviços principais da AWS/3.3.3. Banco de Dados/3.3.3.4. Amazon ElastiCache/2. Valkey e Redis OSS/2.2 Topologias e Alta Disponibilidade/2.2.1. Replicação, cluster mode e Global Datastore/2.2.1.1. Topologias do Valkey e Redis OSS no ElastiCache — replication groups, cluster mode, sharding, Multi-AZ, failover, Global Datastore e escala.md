### Topologias do Valkey e Redis OSS no ElastiCache — replication groups, cluster mode, sharding, Multi-AZ, failover, Global Datastore e escala

> [!warning] Aviso
> Limites de nós/shards/réplicas, tempos de failover, regras de escala online e do Global Datastore mudam por versão do engine. Os números são **ordens de grandeza**. **Confirme na documentação.** Os comandos **não foram executados**.

A topologia define **quanto o cache aguenta** (memória, vazão), **como sobrevive a falhas** (réplicas, Multi-AZ, failover) e **como escala** (vertical e horizontal). No ElastiCache para Valkey/Redis OSS, as peças são: **replication group**, **shards**, **cluster mode desabilitado/habilitado**, **réplicas de leitura**, **Multi-AZ com failover automático** e **Global Datastore** para múltiplas regiões. Esta nota explica cada uma, como escolher e como escalar.

**Analogia:** um balcão de atendimento. Um **único balcão com gerente e assistentes de leitura** (cluster mode desabilitado) funciona até certo volume. Quando o movimento cresce além do que um balcão comporta, você **abre vários balcões, cada um responsável por um intervalo de clientes** (cluster mode habilitado, com shards). Para ter atendimento mesmo se um balcão pegar fogo, cada um tem **um substituto pronto em outro andar** (Multi-AZ).

## Peças da topologia

| Termo | Significado |
|---|---|
| **Nó** | Instância com um processo Valkey/Redis; é a unidade de cobrança |
| **Shard (node group)** | Um nó **primário** (leitura e escrita) + 0 a 5 **réplicas** (somente leitura) |
| **Replication group** | O conjunto de shards (1 em cluster mode desabilitado, 1 a centenas em habilitado) |
| **Primário** | Recebe as escritas e replica de forma **assíncrona** para as réplicas |
| **Réplica** | Cópia para **escala de leitura** e **alta disponibilidade** |
| **Hash slots** | O espaço de chaves é dividido em **16.384 slots** distribuídos entre os shards (cluster mode habilitado) |

## Cluster mode desabilitado × habilitado

```
 DESABILITADO                              HABILITADO
  1 shard                                   N shards (cada um com primário + réplicas)
  ┌──────────────────────┐                 ┌──────────┐ ┌──────────┐ ┌──────────┐
  │ Primário + réplicas  │                 │ Shard 1  │ │ Shard 2  │ │ Shard 3  │
  │ (todo o dataset)     │                 │ slots    │ │ slots    │ │ slots    │
  └──────────────────────┘                 │ 0-5460   │ │ 5461-10922│ │ 10923-16383│
  limite: memória de 1 nó                  └──────────┘ └──────────┘ └──────────┘
  escala: vertical + réplicas de leitura    escala: horizontal (mais shards) + vertical
```

| Critério | **Cluster mode desabilitado** | **Cluster mode habilitado** |
|---|---|---|
| Shards | 1 | 1 a centenas (limite total de nós por cluster, da ordem de 500) |
| Capacidade de memória | Limitada pelo maior nó | **Soma** dos shards (terabytes) |
| Escala de escrita | Vertical apenas | **Horizontal** (cada shard recebe escritas) |
| Escala de leitura | Réplicas (até 5) | Réplicas por shard |
| Operações multi-chave | Livres | Só no mesmo slot (**hash tags**) |
| Endpoints | Primary e reader | **Configuration endpoint** (o cliente "cluster-aware" descobre os shards) |
| Cliente | Qualquer cliente Redis | Cliente com **suporte a cluster** (MOVED/ASK, redirecionamento) |
| Complexidade | Menor | Maior |
| Quando | Dataset cabe em um nó; simplicidade | Dataset ou escrita além de um nó; crescimento previsto |

Dica: **projetos novos que podem crescer** devem começar em cluster mode habilitado (mesmo com 1 shard), pois **migrar de desabilitado para habilitado** exige procedimento específico (e clientes compatíveis).

## Alta disponibilidade: Multi-AZ e failover automático

```
 AZ-a: [Primário shard 1]  ── replicação assíncrona ──► AZ-b: [Réplica 1]   AZ-c: [Réplica 2]
 Falha do primário ─► ElastiCache promove a réplica com menor atraso ─► atualiza o endpoint primário
```

| Característica | Detalhe |
|---|---|
| **Multi-AZ** | Distribui primário e réplicas em AZs diferentes |
| **Failover automático** | Detecta a falha e promove uma réplica; tipicamente **dezenas de segundos** (menos de 1 a 2 min) |
| **Perda de dados** | A replicação é **assíncrona**: as gravações mais recentes ainda não replicadas podem ser perdidas |
| **Novo nó** | Após o failover, o ElastiCache cria uma nova réplica para restaurar a redundância |
| **Aplicação** | Deve **reconectar** automaticamente (cliente com retry/backoff) e usar o **endpoint primário** (DNS) |
| **Sem réplicas** | Falha do primário = perda do shard até recriar (cache frio) |

Regras práticas:

1. **Produção:** pelo menos **1 réplica por shard**, em outra AZ, com Multi-AZ e failover automático habilitados.
2. Pelo menos 2 réplicas para cargas muito críticas (a falha de uma réplica não reduz a HA a zero).
3. Use sempre o **endpoint** (primary/reader/configuration), nunca IPs.
4. Testar failover: `aws elasticache test-failover --replication-group-id ... --node-group-id ...`.

```bash
aws elasticache test-failover --replication-group-id sessoes-prod --node-group-id 0001
# Simula a falha do primário; observe o tempo de recuperação da aplicação
```

## Escala

### Vertical (trocar o tipo de nó)

| Característica | Detalhe |
|---|---|
| **Como** | `modify-replication-group --cache-node-type` |
| **Impacto** | Em Multi-AZ, é feita de forma rolling com failover; há reconexão |
| **Limite** | Tamanho do maior nó; custo |

### Horizontal (cluster mode habilitado)

| Operação | Descrição |
|---|---|
| **Online resharding** | Adicionar/remover **shards** movendo slots entre eles, **com o cluster em operação** (impacto de desempenho durante a migração) |
| **Rebalanceamento** | Redistribui slots entre shards |
| **Adicionar/remover réplicas** | Escala de leitura e HA |
| **Auto Scaling** | Políticas do Application Auto Scaling para **shards** e **réplicas** baseadas em métricas (CPU do engine, memória, conexões) |

```bash
# Aumentar de 3 para 5 shards (resharding online)
aws elasticache modify-replication-group-shard-configuration --replication-group-id catalogo-cluster \
  --node-group-count 5 --apply-immediately

# Adicionar uma réplica por shard
aws elasticache increase-replica-count --replication-group-id catalogo-cluster --new-replica-count 2 --apply-immediately
```

Cuidados: o resharding consome CPU e rede; faça em horários de menor carga; clientes devem tratar redirecionamentos `MOVED/ASK`.

### Escala de leitura

- **Reader endpoint** balanceia entre réplicas.
- Em cluster mode, o cliente pode ler das réplicas (`READONLY`).
- Atenção à **consistência eventual**: a réplica pode estar poucos ms atrás.

### Quando escalar o quê

| Sintoma | Ação |
|---|---|
| `DatabaseMemoryUsagePercentage` alto / evictions | Mais memória: tipo de nó maior ou mais shards |
| `EngineCPUUtilization` alto (thread principal) | Mais shards (distribui comandos) ou otimizar comandos; apenas nó maior tem ganho limitado |
| Leituras saturando o primário | Mais réplicas / ler das réplicas |
| `NetworkBandwidth...AllowanceExceeded` | Nó com mais rede, mais shards |
| `CurrConnections` perto do limite | Pool de conexões, mais nós |

## Global Datastore (multirregião)

Replica um cluster Valkey/Redis **entre regiões** com um **primário** em uma região e até **duas regiões secundárias** (somente leitura), com lag tipicamente **menor que 1 segundo**.

```
 us-east-1 (primário: leitura/escrita)  ══ replicação entre regiões ══►  sa-east-1 (secundário: leitura)
                                         └═════════════════════════════►  eu-west-1 (secundário: leitura)
```

| Característica | Detalhe |
|---|---|
| **Uso** | Leitura local de baixa latência e **recuperação de desastres** regional |
| **Promoção** | Promover uma secundária a primária (failover entre regiões) |
| **Consistência** | Eventual entre regiões; escrita apenas na primária |
| **Requisitos** | Mesmo engine e versão compatíveis; criptografia; tipos de nó suportados |
| **Custo** | Nós em cada região + transferência entre regiões |
| **Limite** | Não é multi-primário |

Alternativas: cache independente por região com invalidação por eventos; **MemoryDB** com multi-região (conforme a oferta); Global Tables do DynamoDB com DAX por região.

## Endpoints e clientes

| Endpoint | Para quê |
|---|---|
| **Primary endpoint** (cluster mode desabilitado) | Escritas |
| **Reader endpoint** | Leituras balanceadas entre réplicas |
| **Configuration endpoint** (cluster mode habilitado) | Descoberta da topologia; o cliente cluster-aware roteia por slot |
| **Node endpoints** | Diagnóstico; evite usar na aplicação |

Cliente: use bibliotecas com suporte a cluster, **reconexão automática**, timeouts curtos, retry com backoff e *connection pooling*. Cuidado com cache de DNS em runtimes (JVM) que impede seguir o failover.

## Escolha da topologia (guia)

| Cenário | Topologia sugerida |
|---|---|
| Dev/test | 1 nó (ou sem réplica), `cache.t4g` |
| Cache pequeno (< ~10 GB), leitura moderada | Cluster mode desabilitado, 1 primário + 1-2 réplicas Multi-AZ |
| Dataset grande ou escrita intensa | **Cluster mode habilitado**, N shards × (1 + 1-2 réplicas), Multi-AZ |
| Cargas muito variáveis | **Serverless** ou Auto Scaling de shards/réplicas |
| Leitura global / DR | **Global Datastore** |
| Durabilidade obrigatória | **MemoryDB** (em vez de ElastiCache) |

## Exemplo prático

Aplicação de e-commerce com sessões e catálogo (60 GB de dados, 100 mil leituras/s, 5 mil escritas/s):

1. **Cluster mode habilitado** com 3 shards `cache.r7g.2xlarge`, 2 réplicas por shard, em 3 AZs.
2. **Hash tags** para chaves relacionadas (`{carrinho:42}:itens` e `{carrinho:42}:total`).
3. Cliente cluster-aware com leitura nas réplicas para catálogo e escrita no primário para sessões.
4. **Auto Scaling** de réplicas por `EngineCPUUtilization` > 60% (de 2 a 5) e alarme para adicionar shards se `DatabaseMemoryUsagePercentage` > 75%.
5. **Teste de failover** mensal (`test-failover`): tempo de recuperação da aplicação < 30 s.
6. **Global Datastore** para a região de DR (`sa-east-1`) com runbook de promoção.
7. Resharding planejado antes da Black Friday: 3 → 5 shards na semana anterior, com monitoramento da latência durante a migração.

## Erros comuns e armadilhas

- **Produção sem réplica ou sem Multi-AZ:** falha = cache frio e indisponibilidade.
- **Cluster mode desabilitado quando o dataset vai crescer:** migração dolorosa.
- **Cliente sem suporte a cluster** (erros `MOVED`, `CROSSSLOT`).
- **Operações multi-chave sem hash tags.**
- **Resharding no horário de pico.**
- **Conectar pelo IP ou fixar o IP de um nó:** quebra no failover.
- **Cache de DNS no cliente** impedindo seguir o failover.
- **Escalar só vertical um problema de CPU da thread única.**
- **Esperar consistência forte nas réplicas** (assíncronas).
- **Esquecer o custo** de réplicas, Multi-AZ e Global Datastore.
- **Não testar o failover** nem o comportamento da aplicação.

## 🧩 Quiz de Fixação

1. Qual a diferença entre cluster mode desabilitado e habilitado?
2. Como funciona o failover automático e o que pode ser perdido?
3. Quando adicionar shards em vez de réplicas?
4. Para que serve o Global Datastore?

**Respostas:**
1) Desabilitado tem um único shard (dataset limitado ao maior nó, escala de escrita só vertical); habilitado particiona o espaço em 16.384 slots entre vários shards, escalando memória e escrita horizontalmente, mas exige cliente cluster-aware e hash tags para operações multi-chave.
2) O ElastiCache detecta a falha do primário e promove a réplica com menor atraso, atualizando o endpoint, em dezenas de segundos. Como a replicação é assíncrona, as gravações mais recentes ainda não replicadas podem ser perdidas.
3) Quando o gargalo é memória total, vazão de escrita ou CPU da thread principal do primário; réplicas ajudam apenas a escalar leituras e a disponibilidade.
4) Replicar um cluster Valkey/Redis entre regiões, com um primário e até duas secundárias somente leitura, oferecendo leitura local de baixa latência e recuperação de desastres regional.
