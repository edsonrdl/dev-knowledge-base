### Segurança, backup e operação do ElastiCache — VPC, TLS, AUTH, RBAC e IAM, snapshots, parameter groups, métricas e troubleshooting

> [!warning] Aviso
> Opções de autenticação (AUTH, RBAC, IAM), criptografia, métricas, limites e comportamentos de manutenção/backup variam por engine e versão e mudam. **Confirme na documentação.** Os comandos **não foram executados**.

Colocar o ElastiCache em produção exige mais que criar o cluster: é preciso **isolá-lo na rede**, **criptografar** dados e conexões, **autenticar** quem acessa, **fazer backup** quando o engine permite, **ajustar parâmetros**, **monitorar** as métricas certas e saber **diagnosticar** os problemas típicos (memória cheia, CPU da thread única, conexões, latência, evictions, failover). Esta nota reúne esse conjunto operacional.

**Analogia:** é a **rotina de um datacenter pequeno**: portaria (VPC e Security Group), cofre (criptografia), crachás (AUTH/RBAC/IAM), fitas de backup (snapshots), painel de controle (parâmetros) e câmeras (métricas e alarmes).

## Segurança em camadas

### 1. Rede

| Prática | Detalhe |
|---|---|
| **VPC e subnets privadas** | O ElastiCache **não tem endpoint público**; vive em um **subnet group** de subnets privadas em várias AZs |
| **Security Group** | Libera 6379 (Valkey/Redis) ou 11211 (Memcached) **apenas** do SG da aplicação (SG-a-SG) |
| **Acesso externo** | Via VPN, Direct Connect, peering ou Transit Gateway; **nunca** exponha o cache à internet |
| **Cross-account** | Compartilhamento de rede (RAM) ou PrivateLink/peering com políticas de SG |
| **Isolamento por ambiente** | Um cluster por ambiente/aplicação sensível; evite cache compartilhado entre domínios com dados distintos |

```
 App (SG-app) ──6379/TLS──► ElastiCache (SG-cache: entrada somente do SG-app) — subnets privadas
```

Base de rede: [[8. DevOps e Gerenciamento de Infraestrutura/CLOUD COMPUTING/AWS (AMAZON WEB SERVICE)/3. Tecnologia e Serviços/3.3 Serviços principais da AWS/3.3.4. Rede/3.3.4.1. Amazon VPC/0 Amazon VPC (Tópicos )|Amazon VPC]].

### 2. Criptografia

| Tipo | Como |
|---|---|
| **Em repouso** | Chave **KMS** (padrão ou CMK) para snapshots e dados em disco (dados em memória não persistem em disco, exceto snapshots e data tiering); habilite na criação (`--at-rest-encryption-enabled`) |
| **Em trânsito** | **TLS** (`--transit-encryption-enabled`); clientes devem usar TLS (`rediss://`, `--tls`) |
| **Migração** | Habilitar a criptografia depois pode exigir recriar o cluster ou um modo de migração (`preferred`) em versões recentes; planeje antes |

### 3. Autenticação e autorização (Valkey/Redis OSS)

| Mecanismo | Descrição |
|---|---|
| **AUTH token** | Senha única do grupo (legado); exige TLS; rotacionável (`ROTATE`/`SET`) |
| **RBAC (usuários e grupos de usuários)** | **Usuários** com senha(s) e **access strings** (`on ~app:* +@read +@write -@dangerous`), agrupados em **user groups** associados ao replication group; princípio do menor privilégio |
| **IAM authentication** | Token IAM de curta duração (cerca de 15 minutos) como senha, via role; exige TLS; elimina senhas estáticas (confirme versões) |
| **Comandos perigosos** | Restrinja `FLUSHALL`, `KEYS`, `CONFIG`, `DEBUG` por RBAC ou renomeie via parameter group |

```bash
# RBAC: usuário somente com acesso a chaves "app:*"
aws elasticache create-user --user-id app-reader --user-name app-reader \
  --engine valkey --passwords "SenhaLongaEAleatoria-123" \
  --access-string "on ~app:* -@all +@read"
aws elasticache create-user-group --user-group-id grupo-app --engine valkey --user-ids default app-reader
aws elasticache modify-replication-group --replication-group-id sessoes-prod --user-group-ids-to-add grupo-app
```

(Mantenha segredos no Secrets Manager; não em código.)

### 4. Governança

| Controle | Função |
|---|---|
| **IAM** | Quem administra (criar/modificar/excluir clusters e snapshots) |
| **SCP / Config** | Exigir criptografia, bloquear clusters sem TLS ou com SG aberto |
| **CloudTrail** | Auditoria da API |
| **Tags** | Alocação de custos e inventário |
| **Logs do engine** (slow log, engine log) | Exportar para CloudWatch Logs/Firehose |

## Backup e restauração (Valkey/Redis OSS)

O Memcached **não tem backup**. Para Valkey/Redis OSS:

| Característica | Detalhe |
|---|---|
| **Snapshots (RDB)** | Cópia do dataset em um ponto no tempo, guardada no S3 gerenciado |
| **Automáticos** | Diários, em janela configurável, retenção de **0 a 35 dias** |
| **Manuais** | A qualquer momento; sem expiração |
| **Origem do snapshot** | De preferência de uma **réplica** (menos impacto no primário) |
| **Impacto** | O processo faz *fork*: usa memória adicional (copy-on-write) → precisa de **memória reservada** |
| **Memória reservada** | Parâmetro `reserved-memory-percent` (por padrão cerca de 25%) para backup/replicação; sem isso, risco de swap, latência e falha |
| **Restauração** | Cria um **novo** cluster a partir do snapshot (ou do arquivo RDB no S3) |
| **Cópia entre regiões/contas** | Possível via cópia/exportação para S3; integração com AWS Backup (conforme a oferta) |
| **Data tiering** | Backups incluem os dados em SSD |

```bash
# Snapshot manual e restauração em novo cluster
aws elasticache create-snapshot --replication-group-id sessoes-prod --snapshot-name sessoes-pre-release
aws elasticache create-replication-group --replication-group-id sessoes-restaurado \
  --replication-group-description "Restaurado" --snapshot-name sessoes-pre-release \
  --cache-node-type cache.r7g.large --engine valkey
# Backup automático
aws elasticache modify-replication-group --replication-group-id sessoes-prod \
  --snapshot-retention-limit 7 --snapshot-window 03:00-04:00 --apply-immediately
```

Lembrete: o cache é **volátil**. O backup é útil para **aquecer rapidamente** um cache grande ou preservar um conjunto de dados caro de recalcular, não substitui uma fonte durável. Para durabilidade real, use o MemoryDB.

## Parameter groups e parâmetros-chave

| Parâmetro | Função | Orientação |
|---|---|---|
| `maxmemory-policy` | Política de eviction (ver nota de custo) | `volatile-lru` (padrão) ou `allkeys-lru`/`allkeys-lfu` para cache puro |
| `reserved-memory-percent` | Memória reservada para operações internas (backup) | Mantenha ≥ 25% se usar snapshots |
| `timeout` | Fecha conexões ociosas (segundos) | 300-600 evita vazamento de conexões |
| `tcp-keepalive` | Mantém e detecta conexões mortas | 300 |
| `maxclients` | Máximo de conexões | Depende do nó (≈65 mil) |
| `slowlog-log-slower-than` / `slowlog-max-len` | Registro de comandos lentos | 10.000 µs e 128 itens como ponto de partida |
| `notify-keyspace-events` | Notificações de eventos de chaves | Habilite só se precisar (custo) |
| `activedefrag` | Desfragmentação ativa | Considere em cargas com fragmentação |
| `lazyfree-lazy-eviction` | Liberação assíncrona | Reduz bloqueios em evictions |
| `cluster-enabled` | Modo cluster | Definido na criação |
| `client-output-buffer-limit-*` | Limite de buffer de saída (Pub/Sub, réplicas) | Evita desconexões/ estouro de memória |

Alguns parâmetros são **estáticos** (reinício/recriação); crie um **parameter group customizado** (o padrão é somente leitura) e versione em IaC.

## Monitoramento: métricas essenciais

| Métrica | Interpretação | Alerta típico |
|---|---|---|
| `EngineCPUUtilization` | CPU da **thread do engine** (a que importa em Valkey/Redis) | > 65-70% sustentado |
| `CPUUtilization` | CPU total do host (inclui outras threads) | > 80-90% |
| `DatabaseMemoryUsagePercentage` | % de `maxmemory` em uso | > 75-80% |
| `FreeableMemory` / `SwapUsage` | Memória do host; swap > 0 é sinal ruim | Swap crescendo |
| `Evictions` | Chaves despejadas por falta de memória | > 0 sustentado (se não é esperado) |
| `CacheHits` / `CacheMisses` | Hit ratio = hits/(hits+misses) | < 80-90% (depende do caso) |
| `CurrConnections` / `NewConnections` | Conexões; picos de novas conexões | Perto do limite; picos |
| `ReplicationLag` | Atraso das réplicas | > poucos segundos |
| `BytesUsedForCache`, `CurrItems` | Volume de dados | Tendência de crescimento |
| `NetworkBandwidthInAllowanceExceeded` / `OutAllowanceExceeded` | O nó atingiu o limite de rede | > 0 |
| `Latência de comando` (`SuccessfulReadRequestLatency`/`WriteRequestLatency` em Serverless; `...Latency` por tipo) | Tempo por tipo de comando | Subida vs baseline |
| `ReplicationBytes`, `SaveInProgress` | Backups/replicação em andamento | Correlacione com picos de latência |

Logs: **slow log** (`SLOWLOG GET`) e **engine log** no CloudWatch Logs.

## Troubleshooting

| Sintoma | Causas prováveis | Ações |
|---|---|---|
| **Latência alta / timeouts** | Comando lento (O(N)), big key, `EngineCPUUtilization` alto, rede saturada, swap, backup em andamento | `SLOWLOG`, `--bigkeys`/`MEMORY USAGE`, evitar `KEYS`, pipeline, escalar shards/nó, mover o backup para a réplica |
| **Memória cheia / evictions** | Dataset cresceu, sem TTL, política de eviction inadequada, big keys | Mais memória/shards, TTL, `allkeys-lru`, revisar o que se cacheia |
| **Hit ratio baixo** | TTL curto, chaves únicas, evictions, invalidação excessiva | Ajustar TTL, chaves, tamanho; medir por prefixo |
| **Muitas conexões / `max number of clients`** | Sem pool, vazamento de conexões, funções Lambda sem reuso | Pool, `timeout`, reutilizar conexões entre invocações, RDS Proxy não se aplica: considere menos clientes por função |
| **CPU do engine alta** | Comandos pesados, script Lua longo, muitas operações pequenas | Distribuir em shards, pipelines, otimizar comandos |
| **Failover recente / erros de conexão** | Falha do nó, manutenção | Cliente com retry/backoff, DNS sem cache longo, Multi-AZ |
| **Réplica atrasada** | Escrita intensa, rede, réplica pequena | Nó maior, mais shards, aliviar leituras |
| **`CROSSSLOT` / `MOVED`** | Cluster mode sem hash tags ou cliente sem suporte | Hash tags, cliente cluster-aware |
| **`OOM command not allowed`** | `maxmemory` atingido com `noeviction` | Mudar a política ou aumentar a memória |
| **Falha de backup / latência durante snapshot** | Pouca memória reservada | Aumentar `reserved-memory-percent`, backup da réplica |

Comandos úteis (via `redis-cli`/`valkey-cli`):

```text
INFO memory                 # uso de memória, fragmentação (mem_fragmentation_ratio)
INFO stats                  # hits, misses, evictions, conexões
INFO commandstats           # custo por comando
SLOWLOG GET 10              # comandos lentos
MEMORY USAGE chave          # tamanho de uma chave
CLIENT LIST                 # conexões (origem, idade, ociosidade)
LATENCY DOCTOR              # análise de latência
redis-cli --bigkeys         # procura chaves grandes (cuidado em produção; use em réplica)
```

## Manutenção e ciclo de vida

- **Janela de manutenção** semanal: patches podem reiniciar nós (com Multi-AZ, o impacto é um failover).
- **Upgrades de versão**: menores e maiores; teste em staging; versões antigas saem de suporte.
- **Eventos do ElastiCache** (SNS): failover, substituição de nó, backup concluído, falha.
- **Runbook**: failover testado, procedimento de restauração, escala emergencial, comunicação.

## Exemplo prático

Hardening e operação do cache de sessões de uma aplicação financeira:

1. **Rede:** subnets privadas, SG-cache aceitando 6379 só do SG-app; sem rota para a internet.
2. **Criptografia:** KMS CMK em repouso, TLS obrigatório; clientes com `rediss://`.
3. **Acesso:** usuário RBAC `app-sessoes` com `~sessao:* +@read +@write +@keyspace -@dangerous`; senha no Secrets Manager (rotação); IAM auth avaliado para as tasks ECS.
4. **Backup:** snapshots diários (retenção 7 dias) a partir da réplica; `reserved-memory-percent=30`.
5. **Parâmetros:** `timeout=300`, `maxmemory-policy=volatile-lru`, `slowlog-log-slower-than=10000`, grupo versionado em Terraform.
6. **Observabilidade:** alarmes em `EngineCPUUtilization` > 65%, `DatabaseMemoryUsagePercentage` > 75%, `Evictions` > 0, `ReplicationLag` > 5 s, `CurrConnections` > 80% do limite; slow log exportado ao CloudWatch Logs.
7. **Resiliência:** Multi-AZ, teste de failover trimestral; o app reconecta com backoff; sessões perdidas forçam novo login (aceito).
8. **Governança:** AWS Config exige TLS e criptografia; CloudTrail e alerta para exclusão de clusters.

## Erros comuns e armadilhas

- **Cluster sem criptografia/TLS e sem autenticação** (acessível por qualquer cliente da VPC).
- **Security Group aberto à VPC inteira ou 0.0.0.0/0.**
- **Habilitar TLS tarde:** mudança exige planejamento e clientes compatíveis.
- **AUTH único compartilhado por todas as aplicações** em vez de RBAC por aplicação.
- **Backup sem memória reservada:** swap, latência e falha de snapshot.
- **Usar `redis-cli --bigkeys` ou `KEYS` no primário em horário de pico.**
- **Monitorar só `CPUUtilization`** e ignorar `EngineCPUUtilization`.
- **Não ter alarme de `Evictions`.**
- **Conexão sem pool** (Lambda abrindo uma por invocação).
- **Tratar o snapshot como backup de banco de dados.**
- **Parâmetros alterados no console sem IaC**, causando drift.

## 🧩 Quiz de Fixação

1. Que camadas de segurança se aplicam a um cluster ElastiCache?
2. Por que a memória reservada é importante para snapshots?
3. Qual a diferença entre `CPUUtilization` e `EngineCPUUtilization`?
4. Cite três causas de latência alta em Valkey/Redis e uma ação para cada.

**Respostas:**
1) Rede (VPC, subnets privadas, Security Group), criptografia em repouso (KMS) e em trânsito (TLS), autenticação e autorização (AUTH, RBAC, IAM), governança (IAM, SCP/Config, CloudTrail) e logs.
2) Porque o snapshot usa *fork* e copy-on-write, exigindo memória adicional; sem reserva, o nó pode usar swap, ter latência alta ou falhar o backup. O parâmetro `reserved-memory-percent` evita isso.
3) `CPUUtilization` mede o host inteiro; `EngineCPUUtilization` mede a thread principal do engine, que é a que limita comandos no Valkey/Redis; esta é a que deve ter alarme.
4) Comandos lentos (O(N), como `KEYS`): usar `SCAN`/pipelines; big keys: dividir a chave; backup/replicação em andamento ou pouca memória: backup na réplica e memória reservada; CPU do engine alta: adicionar shards ou otimizar; rede saturada: nó maior ou mais shards.
