### O que é Amazon ElastiCache — caching em memória, engines Valkey, Redis OSS e Memcached, nós, clusters, serverless e casos de uso

> [!warning] Aviso
> Engines e versões suportadas (Valkey, Redis OSS, Memcached), modelos de implantação, limites e preços do ElastiCache mudam com frequência, e houve mudanças recentes de licenciamento do Redis que levaram à adoção do **Valkey**. Os números são **ordens de grandeza**. **Confirme na documentação.** Os comandos **não foram executados**.

O **Amazon ElastiCache** é o serviço gerenciado de **armazenamento de dados em memória** da AWS. Ele entrega latência de **microssegundos a poucos milissegundos** e alta vazão, sendo usado principalmente como **cache** na frente de bancos de dados e APIs, mas também como armazenamento rápido para **sessões, filas leves, rankings, contadores e mensageria**. A AWS cuida de provisionamento, patches, monitoramento, failover e backups; você escolhe o **engine** e o modelo de implantação.

**Analogia:** o banco de dados é o **arquivo central do prédio** (confiável, mas leva tempo para buscar). O ElastiCache é a **mesa do atendente**, onde ficam à mão as pastas mais consultadas. Se a pasta não está na mesa (cache miss), o atendente vai ao arquivo, traz a pasta e deixa uma cópia na mesa para a próxima vez.

## Por que usar cache em memória

```
 Sem cache:   App ──► Banco (disco, SQL, ~5-50 ms por consulta) ──► sobrecarga com o crescimento do tráfego
 Com cache:   App ──► ElastiCache (memória, ~0,2-1 ms)  ──hit──► resposta
                              └─miss─► Banco ──► grava no cache ──► resposta
```

| Benefício | Detalhe |
|---|---|
| **Latência** | Respostas em sub-milissegundo, contra dezenas de ms do banco |
| **Alívio do banco** | Menos leituras repetidas; permite adiar o upgrade da instância |
| **Escala de leitura** | Milhões de operações por segundo por cluster |
| **Custo** | Uma camada de cache costuma custar menos que escalar o banco para a mesma vazão |
| **Resiliência** | O cache absorve picos e pode servir dados temporariamente se o banco degradar (conforme a estratégia) |

Quando **não** vale: dados que **mudam quase a cada leitura**, consultas únicas que nunca se repetem, ou quando a consistência exigida é incompatível com dados defasados.

## Engines suportados

| Engine | Perfil | Quando |
|---|---|---|
| **Valkey** | Fork de código aberto do Redis OSS, mantido pela Linux Foundation; compatível com o protocolo Redis; **preço menor** que Redis OSS no ElastiCache (confirme) | **Recomendado para projetos novos** |
| **Redis OSS** | Estruturas de dados ricas, replicação, persistência por snapshots, cluster mode | Aplicações existentes em Redis; versões até as abertas suportadas |
| **Memcached** | Chave-valor simples, multithread, sem replicação nem persistência | Cache simples e barato, escala horizontal sem recursos avançados |

Observação: o **Amazon MemoryDB** (serviço separado) é compatível com Redis/Valkey e oferece **durabilidade** (log transacional multi-AZ), servindo como banco primário em memória. O ElastiCache é voltado a **cache** e a dados que toleram perda.

### Comparação rápida

| Critério | Valkey / Redis OSS | Memcached |
|---|---|---|
| Tipos de dados | Strings, hashes, listas, conjuntos, sorted sets, streams, bitmaps, HyperLogLog, geoespacial | Strings (blobs) |
| Replicação / Multi-AZ | **Sim** | Não |
| Persistência (snapshots) | **Sim** | Não |
| Cluster / sharding | Cluster mode nativo | Sharding no **cliente** |
| Multithread | Principalmente single-thread para comandos (I/O multithread nas versões recentes) | **Multithread** |
| Pub/Sub, transações, Lua | **Sim** | Não |
| Global Datastore | **Sim** | Não |
| Uso típico | Cache, sessões, filas, rankings, rate limiting | Cache puro de objetos |

## Modelos de implantação

| Modelo | Descrição | Quando |
|---|---|---|
| **ElastiCache Serverless** | Sem escolher nós: escala automática de memória e computação; cobrança por dados armazenados (GB-hora) e por **ECPUs** consumidas | Cargas variáveis, simplicidade operacional, início rápido |
| **Clusters baseados em nós (*node-based*)** | Você escolhe o **tipo e a quantidade de nós**, shards e réplicas | Cargas previsíveis, controle de custo e topologia, reservas |

```
 Node-based (Valkey/Redis):
   Replication group
    ├─ Shard 1: [primário] + [réplica] + [réplica]
    ├─ Shard 2: [primário] + [réplica] + [réplica]       (cluster mode habilitado: dados divididos em 16.384 slots)
    └─ ...
 Memcached: N nós independentes; o cliente distribui as chaves (hash consistente)
```

### Componentes

| Termo | Significado |
|---|---|
| **Nó** | Instância de cache (ex.: `cache.r7g.large`); unidade de cobrança |
| **Shard (grupo de nós)** | Um primário + 0 a 5 réplicas |
| **Replication group** | Conjunto de shards que formam o cluster Valkey/Redis |
| **Cluster mode** | Habilitado: dados particionados em vários shards; desabilitado: um único shard |
| **Endpoints** | Primary, reader e configuration endpoint (cluster mode) |
| **Subnet group** | Subnets da VPC onde os nós vivem (várias AZs) |
| **Parameter group** | Parâmetros do engine (política de eviction, timeouts etc.) |
| **Snapshot** | Backup em RDB (Valkey/Redis) |

## Famílias de nós

| Família | Perfil | Uso |
|---|---|---|
| **cache.m** (m6g/m7g) | Uso geral | Caches mistos |
| **cache.r** (r6g/r7g) | Memory optimized | Datasets grandes em memória |
| **cache.r6gd** | Memória + **SSD local** (**data tiering**) | Dataset maior que a RAM com custo menor |
| **cache.t** (t3/t4g) | Burstable | Desenvolvimento e cargas leves |

Sufixo `g` = **Graviton** (ARM), normalmente com melhor custo-benefício.

## Casos de uso típicos

| Caso | Como o ElastiCache ajuda |
|---|---|
| **Cache de consultas e objetos** | Reduz leituras em RDS/Aurora/DynamoDB |
| **Cache de sessões web** | Sessão compartilhada entre instâncias da aplicação |
| **Rankings / leaderboards** | Sorted sets em tempo real |
| **Rate limiting e contadores** | `INCR` + `EXPIRE` atômicos |
| **Filas leves e mensageria** | Listas, Pub/Sub, Streams |
| **Locks distribuídos** | `SET NX PX` com token |
| **Geoespacial** | `GEOSEARCH` para "perto de mim" |
| **Cache de resultados de APIs/ML** | Respostas caras recalculadas raramente |
| **Busca vetorial** (Valkey/Redis com módulos suportados) | Embeddings para IA (confirme a disponibilidade) |

## Exemplo prático

```bash
# Cluster Valkey (node-based) com 1 shard, 1 réplica, Multi-AZ, criptografado
aws elasticache create-replication-group --replication-group-id sessoes-prod \
  --replication-group-description "Sessoes web" \
  --engine valkey --engine-version 8.0 \
  --cache-node-type cache.r7g.large --num-node-groups 1 --replicas-per-node-group 1 \
  --automatic-failover-enabled --multi-az-enabled \
  --cache-subnet-group-name sg-cache-prod --security-group-ids sg-0cache123 \
  --at-rest-encryption-enabled --transit-encryption-enabled

# Cache Serverless (sem escolher nós)
aws elasticache create-serverless-cache --serverless-cache-name catalogo-cache \
  --engine valkey --subnet-ids subnet-0aaa111 subnet-0bbb222 --security-group-ids sg-0cache123

# Listar endpoints
aws elasticache describe-replication-groups --replication-group-id sessoes-prod \
  --query 'ReplicationGroups[0].NodeGroups[0].{Primario:PrimaryEndpoint.Address,Leitura:ReaderEndpoint.Address}'
```

Teste de conexão (de uma instância na mesma VPC, com TLS):

```bash
redis-cli -h sessoes-prod.xxxxx.use1.cache.amazonaws.com -p 6379 --tls PING
# PONG
```

(Versões e nomes de engine são ilustrativos; confirme os valores aceitos.)

## Padrões de cache e política de invalidação

```
 Cache-aside (mais comum)
 App ─1─► Cache: GET chave ──hit──► resposta
      └─2─ miss ─► Banco ─3─► App ─4─► Cache: SET chave TTL
 Write-through: App grava no cache E no banco (consistência maior, escrita mais lenta)
```

| Padrão | Consistência | Complexidade | Quando |
|---|---|---|---|
| Cache-aside + TTL | Eventual | Baixa | Leituras repetidas, tolera dados levemente velhos |
| Write-through | Alta | Média | Dados lidos logo após escritos |
| Write-behind | Eventual (risco de perda) | Alta | Escrita em lote, tolera risco |
| Invalidate-on-write | Alta | Média | Dados críticos com poucos escritores |

> [!warning] Valores, limites e preços mudam; os exemplos deste material não foram executados. Engines, versões e recursos (como Valkey e serverless) mudam; consulte a documentação.

### Árvore de decisão: engine

```
Precisa de estruturas ricas (listas, sets, sorted sets), persistência, réplicas, pub/sub?
├─ Sim ─► Valkey / Redis OSS
│     └─ Quer durabilidade de banco primário? ─► MemoryDB
└─ Não, só chave-valor simples multi-thread? ─► Memcached
Carga imprevisível, sem gerenciar nós? ─► ElastiCache Serverless
```

## Dimensionamento e proteção

1. Dimensione a memória pelo **conjunto de trabalho** + folga (~25-30%) e observe `Evictions`.
2. Defina **TTL** em todas as chaves de cache e evite chaves sem expiração.
3. Evite *cache stampede*: jitter no TTL, lock/`single-flight` na repopulação.
4. Criptografia em trânsito (TLS) e repouso; AUTH/IAM; nunca exponha publicamente.
5. Réplicas em outra AZ e failover automático para produção.

## Troubleshooting

| Sintoma | Causa provável | Ação |
|---|---|---|
| Evictions altas | Memória insuficiente | Subir nó/shards, revisar TTL |
| Latência alta | Chaves enormes, comandos O(N) | Evitar `KEYS`, dividir valores |
| Muitos misses | TTL curto/chaves mal formadas | Revisar estratégia e chave |
| Falha após failover | Cliente sem reconexão | Usar endpoint primário e retry |

## Custo

Cobra por nó-hora (ou ECPU/GB no Serverless), por backups e transferência. Reserved Nodes baixam o custo de nós estáveis; um cache bem dimensionado costuma reduzir o custo do banco por tirar leituras dele.

## Erros comuns e armadilhas

- **Tratar o cache como fonte de verdade:** nós podem falhar; a aplicação precisa reconstruir do banco.
- **Achar que cache sempre ajuda:** dados pouco reutilizados só adicionam complexidade.
- **Escolher Memcached e depois precisar de replicação/estruturas:** reavalie cedo.
- **Expor o cache à internet:** o ElastiCache vive em VPC; nunca abra a porta publicamente.
- **Sem TTL:** o cache enche e os dados envelhecem.
- **Dimensionar só pela memória do dataset:** esquecer overhead, réplicas e **reserva para snapshots**.
- **Usar `KEYS *` ou comandos O(N) em produção:** bloqueiam o servidor single-thread.
- **Ignorar a latência de rede entre AZs** (cliente e nó em AZs diferentes).
- **Usar nó `t` em produção sob carga contínua:** créditos de CPU acabam.
- **Não planejar o cold start do cache** (após reinício/failover, a taxa de acerto cai).

## 🧩 Quiz de Fixação

1. Qual o papel do ElastiCache na arquitetura de uma aplicação e que benefícios traz?
2. Quais as diferenças principais entre Valkey/Redis OSS e Memcached?
3. O que é o ElastiCache Serverless e quando preferi-lo aos clusters baseados em nós?
4. Por que o cache não deve ser tratado como fonte de verdade?

**Respostas:**
1) É uma camada em memória na frente de bancos e APIs, que reduz a latência (sub-milissegundo), alivia leituras no banco, absorve picos e aumenta a vazão, além de servir sessões, rankings e contadores.
2) Valkey/Redis OSS oferecem estruturas de dados ricas, replicação, Multi-AZ, persistência por snapshots, cluster mode, Pub/Sub e Lua; Memcached é um chave-valor simples, multithread, sem replicação nem persistência e com sharding no cliente.
3) É um modo em que não se escolhem nós: a capacidade escala automaticamente e se paga por dados armazenados e ECPUs. É indicado para cargas variáveis e para simplificar a operação; os clusters baseados em nós são melhores com carga previsível e quando se quer controlar topologia e custo (com reservas).
4) Porque nós podem falhar, ser reiniciados ou despejar chaves por pouca memória; a aplicação precisa conseguir reconstruir os dados a partir da fonte durável (ou usar MemoryDB quando é preciso durabilidade).

**Questões complementares:**

4. O que é cache stampede e como mitigar?
5. Qual métrica indica memória insuficiente no cache?
6. Quando escolher MemoryDB em vez de ElastiCache?

**Respostas das questões complementares:**
4) Muitos clientes repopulando a mesma chave expirada ao mesmo tempo, sobrecarregando o banco; mitigue com jitter no TTL e lock/single-flight na repopulação.
5) `Evictions` alto (chaves removidas por falta de memória).
6) Quando se precisa de durabilidade (log multi-AZ) para usar o serviço como banco primário compatível com Redis, e não apenas como cache.
