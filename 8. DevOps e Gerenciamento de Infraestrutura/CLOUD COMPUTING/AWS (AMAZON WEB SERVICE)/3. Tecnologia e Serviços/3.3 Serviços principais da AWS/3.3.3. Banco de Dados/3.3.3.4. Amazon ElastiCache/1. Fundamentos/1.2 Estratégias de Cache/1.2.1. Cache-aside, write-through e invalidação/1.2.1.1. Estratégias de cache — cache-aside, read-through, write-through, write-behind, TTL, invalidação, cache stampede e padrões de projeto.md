### Estratégias de cache — cache-aside, read-through, write-through, write-behind, TTL, invalidação, cache stampede e padrões de projeto

> [!warning] Aviso
> Os padrões desta nota são práticas de engenharia consolidadas, mas o comportamento exato depende da biblioteca/cliente, do engine e da carga. Os códigos são **ilustrativos e não foram executados**. Valide em ambiente de teste com tráfego realista.

Ter o ElastiCache não basta: o ganho (ou o problema) está em **como a aplicação usa o cache**. Esta nota cobre as **estratégias de leitura e escrita** (cache-aside, read-through, write-through, write-behind, refresh-ahead), a **política de expiração** (TTL), a **invalidação** — "um dos dois problemas difíceis da computação" —, os riscos clássicos (**cache stampede, penetração, avalanche, hot keys**) e como medir o sucesso (**hit ratio**).

**Analogia:** o cache é a **estante de livros mais usados da biblioteca**. Estratégias diferentes decidem quem repõe os livros na estante (o próprio leitor, o bibliotecário), quando retirá-los (prazo de devolução) e o que fazer quando 1.000 pessoas pedem o mesmo livro que acabou de sair.

## Estratégias de leitura

### 1. Cache-aside (lazy loading) — a mais comum

A **aplicação** controla o cache: consulta o cache; se não encontrar, busca no banco e **popula** o cache.

```
 leitura(chave):
   v = cache.get(chave)
   se v existe  → retorna v                    (HIT)
   senão        → v = banco.consulta(chave)    (MISS)
                  cache.set(chave, v, TTL)
                  retorna v
```

| Vantagem | Desvantagem |
|---|---|
| Só guarda o que é pedido (eficiente em memória) | A 1ª leitura é lenta (miss) |
| Tolera falha do cache (cai para o banco) | Dados podem ficar **defasados** até o TTL/invalidação |
| Simples e independente do banco | Lógica de cache espalhada pela aplicação |

### 2. Read-through

O **cache** (ou uma camada/biblioteca) busca no banco quando há miss; a aplicação conversa só com o cache. Menos código na aplicação, mas exige uma camada que saiba carregar os dados (no ElastiCache puro, você implementa essa camada; para DynamoDB, o **DAX** é read-through).

### 3. Refresh-ahead

Renova entradas **antes de expirar**, para as chaves quentes, evitando misses em horários de pico. Exige prever quais chaves renovar.

## Estratégias de escrita

### 4. Write-through

Cada escrita grava **no banco e no cache** juntos (de forma síncrona).

```
 escrita(chave, valor):
   banco.grava(chave, valor)
   cache.set(chave, valor, TTL)
```

| Vantagem | Desvantagem |
|---|---|
| Cache sempre fresco | Latência de escrita maior (duas gravações) |
| Menos misses de leitura | Guarda dados que podem nunca ser lidos (desperdício) |
| Combina bem com cache-aside | Falha parcial (banco ok, cache falhou) exige tratamento |

### 5. Write-behind (write-back)

A aplicação grava **no cache**, e este grava no banco **depois** (assíncrono, em lote).

| Vantagem | Desvantagem |
|---|---|
| Escrita muito rápida e agrupa gravações | **Risco de perda de dados** se o cache falhar antes de persistir |
| Reduz carga no banco | Complexidade e ordenação; consistência eventual |

Use com cautela; se precisa de durabilidade, considere **MemoryDB** ou uma fila (SQS/Kinesis) para persistir.

### 6. Write-around

Escreve **só no banco** e deixa a leitura popular o cache. Evita encher o cache com dados escritos e pouco lidos.

### Resumo

| Estratégia | Leitura | Escrita | Quando |
|---|---|---|---|
| **Cache-aside** | Aplicação | Banco + invalida/atualiza cache | **Padrão geral** |
| **Read-through** | Cache carrega | — | Camada de acesso padronizada |
| **Write-through** | — | Banco + cache | Leituras logo após escritas |
| **Write-behind** | — | Cache → banco (assíncrono) | Escritas muito frequentes e tolerantes a risco |
| **Refresh-ahead** | Renova antes de expirar | — | Chaves quentes críticas |

## TTL (Time To Live)

| Prática | Detalhe |
|---|---|
| **Sempre defina TTL** | Evita crescimento infinito e dados eternamente defasados |
| **TTL por tipo de dado** | Catálogo (horas), sessão (minutos-horas), contadores (curto), configurações (muito curto/invalidação) |
| **Jitter** | Adicione variação aleatória (±10-20%) para evitar que muitas chaves expirem juntas (**avalanche**) |
| **TTL curto não é consistência** | Reduz defasagem, mas não elimina; combine com invalidação para dados críticos |
| **Sliding vs absoluto** | Renovar o TTL a cada acesso (sessão) ou fixo (dado derivado) |

```
 # TTL com jitter (pseudocódigo)
 ttl = 3600 + random(0, 600)
 cache.set(chave, valor, ex=ttl)
```

## Invalidação

| Técnica | Como | Observações |
|---|---|---|
| **Expiração (TTL)** | Aguardar | Simples; defasagem tolerável |
| **Delete na escrita** | Após atualizar o banco, `DEL chave` | Padrão com cache-aside; o próximo read repovoa |
| **Atualização na escrita** | Escrever o valor novo no cache | Risco de gravar valor antigo em concorrência |
| **Versionamento de chave** | `produto:42:v7` — mudar a versão | Evita apagar muitas chaves; a antiga expira |
| **Eventos (CDC / Streams)** | DynamoDB Streams, binlog/Debezium → Lambda invalida chaves | Desacopla; cobre escritas por qualquer origem |
| **Tags / conjuntos** | Guardar um `SET` de chaves por entidade e apagar o conjunto | Invalida grupos relacionados |
| **Flush** | `FLUSHALL` | Evite em produção (cold start) |

### Cuidado com a ordem e concorrência

```
 Corrida clássica (cache-aside com delete):
   T1: lê banco (valor antigo)            T2: atualiza banco; apaga cache
   T1: grava no cache o valor ANTIGO  ← cache fica sujo até o TTL
```

Mitigações: **TTL curto** como rede de segurança, **versionamento**, **invalidação por eventos após o commit**, e "delete duplo atrasado" (apagar de novo após alguns segundos) em casos críticos.

## Problemas clássicos e mitigações

| Problema | O que é | Mitigação |
|---|---|---|
| **Cache stampede (thundering herd)** | Uma chave quente expira e **milhares de requisições** vão ao banco ao mesmo tempo | **Lock/single-flight** (só uma requisição repovoa), TTL com jitter, **expiração probabilística antecipada**, refresh-ahead, servir dado antigo enquanto atualiza (*stale-while-revalidate*) |
| **Cache avalanche** | Muitas chaves expiram juntas (ou o cache cai) e o banco é soterrado | Jitter no TTL, Multi-AZ, aquecimento, limitação de taxa ao banco, circuit breaker |
| **Cache penetration** | Consultas por chaves **inexistentes** sempre dão miss e vão ao banco (ou ataque) | **Cache negativo** (guardar "não existe" com TTL curto), filtro de Bloom, validação de entrada |
| **Hot key** | Uma chave concentra muito tráfego e satura um nó/shard | Réplicas de leitura, cache local (L1) em memória da aplicação, replicar a chave com sufixos |
| **Big key** | Valor muito grande (MBs) bloqueia o servidor e a rede | Dividir, comprimir, evitar |
| **Cold start** | Cache vazio após reinício/failover | Aquecimento (pré-carga), failover Multi-AZ, throttling |
| **Inconsistência** | Cache diferente do banco | TTL, invalidação por eventos, tolerância explícita |

### Single-flight com lock (exemplo)

```python
# Python ilustrativo com redis-py (compatível com Valkey): evita stampede ao repovoar uma chave
import time, json, random

def obter_produto(r, db, produto_id, ttl=600):
    chave = f"produto:{produto_id}"
    dado = r.get(chave)
    if dado:                                     # HIT
        return json.loads(dado)

    lock = f"lock:{chave}"
    if r.set(lock, "1", nx=True, ex=10):         # só UM processo repovoa (lock com expiração)
        try:
            valor = db.consulta_produto(produto_id)          # MISS: vai ao banco
            r.set(chave, json.dumps(valor), ex=ttl + random.randint(0, 60))   # TTL com jitter
            return valor
        finally:
            r.delete(lock)
    else:                                        # outro processo está repovoando: espera um pouco e relê
        time.sleep(0.05)
        dado = r.get(chave)
        return json.loads(dado) if dado else db.consulta_produto(produto_id)
```

(Em produção, use bibliotecas de *single-flight*/cache com *request coalescing* e trate tempo limite e falhas do cache.)

## Hit ratio e como medir

```
 hit ratio = CacheHits / (CacheHits + CacheMisses)
```

| Faixa | Interpretação |
|---|---|
| > 90% | Saudável para leitura intensiva |
| 70-90% | Avaliar TTL, tamanho, chaves e padrões de acesso |
| < 50% | O cache pode não estar agregando valor, ou está subdimensionado/evictando |

Métricas CloudWatch do ElastiCache: `CacheHits`, `CacheMisses`, `Evictions`, `CurrItems`, `DatabaseMemoryUsagePercentage`. **Evictions altas** indicam falta de memória; **muitos misses com poucas evictions** indicam TTL curto ou padrões de acesso sem repetição.

## Padrões de projeto na prática

1. **Camada de acesso a dados única** (repositório com cache): evita lógica de cache duplicada.
2. **Chaves bem desenhadas**: `entidade:id:versão`, prefixos por domínio, tamanho curto; evite dados pessoais em chaves.
3. **Serialização compacta** (MessagePack, Protobuf) e compressão para valores grandes.
4. **Cache em duas camadas**: cache local por instância (L1, milissegundos de TTL) + ElastiCache (L2) para aliviar hot keys.
5. **Degradação graciosa**: se o cache cair, a aplicação vai ao banco com limitador de taxa e circuit breaker.
6. **Observabilidade**: logar hit/miss por tipo de dado; alarmes em hit ratio, evictions e latência.
7. **Invalidação por eventos**: DynamoDB Streams/CDC/EventBridge para refletir mudanças vindas de qualquer origem.
8. **Teste de carga com cache frio** para dimensionar o banco.

## Exemplo prático

API de catálogo (RDS) com 5.000 req/s de leitura e 20 req/s de escrita:

1. **Cache-aside** com Valkey: chave `produto:{id}:v{versao}`; TTL de 30 min com jitter de ±5 min.
2. **Atualização de produto:** a escrita incrementa `versao` no banco (na mesma transação), emite evento; consumidor atualiza a chave `produto:{id}:vN+1` (warm) e deixa a antiga expirar.
3. **Lock single-flight** para as 200 chaves mais quentes (campanhas) com `SET NX EX 10`.
4. **Cache negativo**: produtos inexistentes guardados por 60 s (evita penetração por IDs aleatórios).
5. **L1**: cache local de 5 s para a home page (1 chave com 100 mil leituras/min).
6. **Métricas**: hit ratio alvo ≥ 95%; alarmes em `Evictions > 0`, `EngineCPUUtilization > 70%` e na taxa de leituras no banco.
7. **Resultado esperado:** o banco recebe ~5% das leituras (250 req/s), com picos controlados pelo lock; teste de "cache frio" confirma que o banco aguenta o cold start com limitador de taxa.

## Erros comuns e armadilhas

- **Cache sem TTL** nem política de eviction pensada.
- **Todas as chaves com o mesmo TTL** (avalanche de expiração).
- **Ignorar stampede** em chaves quentes.
- **Gravar no cache antes de confirmar a transação do banco** (dado que depois é revertido).
- **Cache-aside com atualização de valor** em vez de delete, causando corridas.
- **Cachear dados de usuário com chave compartilhada** (vazamento entre usuários).
- **Cache de dados sensíveis sem TLS/criptografia** ou sem TTL curto.
- **Confiar que `FLUSHALL` é seguro** em produção.
- **Não tratar falha do cache** (a aplicação para junto).
- **Valores gigantes** e hot keys sem mitigação.
- **Medir só a latência média**, ignorando hit ratio e p99.

## 🧩 Quiz de Fixação

1. Descreva o fluxo do cache-aside e uma desvantagem.
2. O que é cache stampede e como mitigar?
3. Por que adicionar jitter ao TTL?
4. Quando write-behind é arriscado?

**Respostas:**
1) A aplicação consulta o cache; em miss, busca no banco e grava no cache com TTL. Desvantagem: a primeira leitura é lenta e os dados podem ficar defasados até o TTL ou a invalidação.
2) É quando uma chave quente expira e muitas requisições simultâneas vão ao banco para repovoá-la. Mitiga-se com lock/single-flight, TTL com jitter, refresh-ahead, expiração probabilística antecipada ou servir o dado antigo enquanto se atualiza.
3) Para evitar que muitas chaves expirem ao mesmo tempo (avalanche), espalhando as expirações e a carga no banco.
4) Porque a escrita só é persistida depois, de forma assíncrona; se o cache falhar antes, os dados confirmados ao cliente são perdidos. Exige tolerância a perda ou uma camada durável (fila, MemoryDB).
