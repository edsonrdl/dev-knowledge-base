### Memcached no ElastiCache — modelo multithread, sharding no cliente, auto discovery, escala horizontal e quando escolher

> [!warning] Aviso
> Versões do Memcached suportadas, limites de nós por cluster, tamanho máximo de item e recursos de segurança (TLS, IAM) variam por versão do ElastiCache e mudam. Os números são **ordens de grandeza**. **Confirme na documentação.** Os comandos e códigos **não foram executados**.

O **Memcached** é o engine de cache mais simples do ElastiCache: um **armazenamento chave-valor em memória**, **multithread**, sem replicação, sem persistência e sem estruturas de dados complexas. Em compensação, é **muito leve**, escala **horizontalmente** com facilidade e é uma boa escolha quando o objetivo é **só cache**, com dados descartáveis e acesso por chave. Esta nota explica o modelo, como o **sharding é feito no cliente**, o **auto discovery**, como escalar, as **limitações** e **quando escolher Memcached em vez de Valkey/Redis OSS**.

**Analogia:** o Memcached é um **conjunto de armários independentes**. Cada armário guarda o que o cliente colocar, sem copiar para outro e sem anotar em lugar nenhum. Quem decide **em qual armário** guardar cada pasta é o **cliente** (a aplicação), com uma regra fixa (hash). Se um armário pegar fogo, as pastas dele somem — e o cliente vai buscar tudo de novo no arquivo central.

## O modelo do Memcached

| Característica | Detalhe |
|---|---|
| **Dados** | Pares chave-valor; valor é um blob (bytes/string); chave até 250 bytes; valor até ~1 MB por padrão |
| **Operações** | `get`/`set`/`add`/`replace`/`delete`/`incr`/`decr`/`cas`/`touch` e multi-get |
| **Multithread** | Usa vários núcleos de CPU por nó (diferente do Redis, de thread principal única) |
| **Sem replicação** | Cada nó guarda apenas o que lhe cabe; não há réplicas |
| **Sem persistência** | Reiniciou o nó, perdeu os dados |
| **Sem Multi-AZ de dados** | Pode-se espalhar nós por AZs, mas cada chave vive em um só nó |
| **Eviction** | **LRU** por classe de slab quando a memória enche (política interna; não configurável como no Redis) |
| **TTL** | Por item (em segundos, ou timestamp Unix) |
| **Sem comandos compostos** | Sem listas, conjuntos, Pub/Sub, scripts ou transações |
| **CAS** | `cas` (check-and-set) para atualização otimista |

### Gerenciamento de memória (slabs)

O Memcached aloca memória em **páginas de 1 MB divididas em slabs (chunks) de tamanhos crescentes**. Cada item vai para o slab de tamanho adequado. Consequências:

- Pode haver **fragmentação interna** (item de 600 bytes em chunk de 700).
- Distribuição desigual de tamanhos pode causar **evictions precoces** em uma classe enquanto outra sobra memória.
- Ajustes (`-f` fator de crescimento, `-n` tamanho mínimo) são feitos por parameter group (conforme permitido).

## Sharding no cliente e hash consistente

Diferente do Redis cluster mode (o servidor conhece os slots), no Memcached **o cliente decide o nó**:

```
 chave "produto:42" ──hash──► nó 3 de 5      (a mesma chave sempre vai ao mesmo nó)
 Aplicação (biblioteca cliente) conhece a lista de nós e aplica a regra de distribuição
```

| Estratégia | Comportamento | Problema |
|---|---|---|
| **Módulo simples** (`hash % N`) | Trivial | Ao mudar N (adicionar/remover nós), **quase todas as chaves mudam de nó** → cache esvazia (miss em massa) |
| **Hash consistente** (ex.: ketama) | Cada nó cobre faixas de um anel; ao mudar N, só ~1/N das chaves se move | **Recomendado**: reduz o impacto de escalar |

Pontos de atenção:

- Todos os clientes precisam usar **o mesmo algoritmo e a mesma lista de nós**; do contrário, a mesma chave vai a nós diferentes.
- Falha de um nó: com hash consistente, as chaves dele passam a outros nós (cache frio para elas); com módulo simples, o impacto é maior.

## Auto Discovery

Para o cliente saber dos nós sem lista fixa, o ElastiCache oferece o **configuration endpoint** do cluster Memcached.

```
 Cliente ──config endpoint──► recebe a lista atual de nós (host:porta) ──► abre conexões e aplica hash consistente
 (consulta periodicamente → percebe nós adicionados/removidos automaticamente)
```

| Elemento | Descrição |
|---|---|
| **Configuration endpoint** | Nome DNS único para descobrir os nós (`meucache.xxxx.cfg.use1.cache.amazonaws.com:11211`) |
| **Node endpoints** | Endpoints individuais de cada nó |
| **Clientes compatíveis** | Bibliotecas com suporte a Auto Discovery (ex.: ElastiCache Cluster Client para Java/.NET/PHP; em outras linguagens, lógica de polling) |
| **Benefício** | Escalar adicionando/removendo nós **sem redeploy** da aplicação |

## Escala

### Horizontal (adicionar ou remover nós)

| Aspecto | Detalhe |
|---|---|
| **Adicionar nós** | Aumenta a memória total e a vazão; com hash consistente, parte das chaves migra (misses temporários) |
| **Remover nós** | As chaves do nó removido são perdidas |
| **Limite** | Dezenas de nós por cluster (padrão; ajustável por solicitação) |
| **Distribuição por AZ** | Escolha o modo *cross-AZ* para espalhar nós e reduzir o impacto da perda de uma AZ |
| **Cuidado** | Escalar durante picos agrava a taxa de miss; planeje aquecimento |

### Vertical (tipo de nó maior)

Trocar o tipo de nó exige **substituir o cluster/nós** (os dados em memória são perdidos): planeje como cache frio.

```bash
# Criar um cluster Memcached de 4 nós distribuídos entre AZs
aws elasticache create-cache-cluster --cache-cluster-id catalogo-mc \
  --engine memcached --engine-version 1.6.22 \
  --cache-node-type cache.r7g.large --num-cache-nodes 4 --az-mode cross-az \
  --cache-subnet-group-name sg-cache-prod --security-group-ids sg-0cache123

# Adicionar nós (escala horizontal)
aws elasticache modify-cache-cluster --cache-cluster-id catalogo-mc --num-cache-nodes 6 --apply-immediately

# Descobrir os endpoints
aws elasticache describe-cache-clusters --cache-cluster-id catalogo-mc --show-cache-node-info \
  --query 'CacheClusters[0].{Config:ConfigurationEndpoint.Address,Nos:CacheNodes[].Endpoint.Address}'
```

(Versões e parâmetros são ilustrativos; confirme os valores aceitos.)

## Exemplo de cliente (Python com hash consistente)

```python
# Ilustrativo: usa pymemcache com hash consistente entre os nós descobertos
from pymemcache.client.hash import HashClient

servidores = [("n1.catalogo-mc.xxxx.cache.amazonaws.com", 11211),
              ("n2.catalogo-mc.xxxx.cache.amazonaws.com", 11211),
              ("n3.catalogo-mc.xxxx.cache.amazonaws.com", 11211)]
cache = HashClient(servidores, use_pooling=True, hasher=None)   # hasher padrão: hash consistente

def obter_produto(produto_id, db):
    chave = f"produto:{produto_id}"
    valor = cache.get(chave)
    if valor is not None:
        return valor                                     # HIT
    valor = db.consulta_produto(produto_id)              # MISS
    cache.set(chave, valor, expire=600)                  # TTL
    return valor
```

## Segurança e operação

| Tema | Detalhe |
|---|---|
| **Rede** | Dentro da VPC; Security Group na porta 11211 |
| **Criptografia em trânsito** | TLS suportado em versões recentes do Memcached no ElastiCache (confirme) |
| **Criptografia em repouso** | Não aplicável de forma persistente (dados só em memória); consulte as opções disponíveis |
| **Autenticação** | Mais limitada que no Redis (sem ACL/RBAC); proteção principal por rede e TLS |
| **Backups** | **Não há** snapshots |
| **Métricas** | `CPUUtilization`, `SwapUsage`, `Evictions`, `CurrConnections`, `GetHits`/`GetMisses`, `BytesUsedForCacheItems`, `CurrItems`, `NetworkBytesIn/Out` |
| **Manutenção** | Janela de manutenção; patches podem reiniciar nós (cache perdido) |
| **Parameter groups** | `max_item_size`, `chunk_size_growth_factor`, `maxconns`, etc. |

## Memcached × Valkey/Redis OSS: quando escolher

| Critério | **Memcached** | **Valkey / Redis OSS** |
|---|---|---|
| Simplicidade | **Alta** | Média |
| Estruturas de dados | Não | **Sim** |
| Alta disponibilidade (réplicas, failover) | **Não** | **Sim** |
| Persistência / snapshots | Não | **Sim** |
| Multithread por nó | **Sim** (uso eficiente de muitas vCPUs) | Principalmente single-thread (I/O multithread) |
| Escala horizontal | Sim, no cliente | Cluster mode nativo |
| Pub/Sub, Lua, transações | Não | **Sim** |
| Global Datastore | Não | **Sim** |
| Casos | Cache puro de objetos/fragmentos HTML/resultados de consulta, com alta vazão e perda tolerável | Sessões, rankings, filas, rate limiting, cache com HA |
| Custo | Geralmente menor para o mesmo tamanho | Maior (réplicas, recursos) |

Escolha o Memcached quando: **só precisa de cache simples**, o dataset é facilmente reconstruível, deseja usar **muitos núcleos** por nó e quer **escala horizontal simples**. Escolha Valkey/Redis quando precisa de **HA**, **estruturas de dados**, **persistência por snapshot**, **Pub/Sub** ou **cluster mode**.

## Exemplo prático

Portal de notícias com cache de fragmentos HTML e resultados de consulta (500 mil leituras/s no pico), em que perder o cache apenas aumenta temporariamente a carga do banco:

1. Cluster Memcached com **8 nós** `cache.r7g.xlarge` em 3 AZs (cross-AZ), com **Auto Discovery**.
2. Cliente com **hash consistente** (ketama) e pool de conexões; TTLs de 60 s a 10 min com jitter.
3. Chaves: `frag:home:v12`, `frag:materia:{id}:v7` (versionamento para invalidar sem varrer).
4. Alarmes: `Evictions` > 0 sustentado, hit ratio < 90%, `CPUUtilization` > 70%.
5. Plano para falha de nó: o hash consistente redistribui as chaves (cache frio parcial); o banco tem limitador de taxa e cache de segunda camada (CloudFront) para absorver.
6. Escala em picos: adicionar 4 nós **antes** do evento (para aquecer), e não durante.
7. Se surgir necessidade de ranking ou sessão com HA, usar Valkey para esses casos, mantendo o Memcached para fragmentos.

## Erros comuns e armadilhas

- **Esperar replicação/persistência no Memcached:** nó perdido = dados perdidos.
- **Hash `% N`** (sem consistente) e escalar em produção: esvazia o cache.
- **Clientes com listas de nós ou algoritmos diferentes:** mesma chave em nós distintos.
- **Itens maiores que o limite** (1 MB padrão): falha silenciosa ou erro; comprimir/dividir.
- **Não monitorar evictions** e alocação de slabs.
- **Escalar durante o pico** em vez de antecipar.
- **Usar Memcached para sessões que não podem ser perdidas.**
- **Ignorar TLS** quando a política de segurança exige criptografia em trânsito.
- **Cache stampede** sem lock ou jitter.
- **Todos os nós em uma AZ.**

## 🧩 Quiz de Fixação

1. Quem decide em qual nó uma chave vai no Memcached e por que usar hash consistente?
2. O que é Auto Discovery?
3. Cite três limitações do Memcached em relação ao Valkey/Redis OSS.
4. Em que cenário o Memcached é uma boa escolha?

**Respostas:**
1) O cliente (a biblioteca) decide, aplicando um algoritmo de hash sobre a chave e a lista de nós. O hash consistente reduz a movimentação de chaves quando nós são adicionados ou removidos (cerca de 1/N), evitando esvaziar quase todo o cache como ocorre com o módulo simples.
2) Recurso do ElastiCache em que o cliente consulta o configuration endpoint para obter a lista atual de nós, percebendo adições e remoções automaticamente, sem alterar a configuração da aplicação.
3) Sem replicação/failover, sem persistência/snapshots e sem estruturas de dados avançadas, Pub/Sub, scripts ou Global Datastore.
4) Cache simples de objetos, fragmentos ou resultados de consulta, com alta vazão e escala horizontal simples, quando os dados são facilmente reconstruíveis e perder o cache de um nó é tolerável.
