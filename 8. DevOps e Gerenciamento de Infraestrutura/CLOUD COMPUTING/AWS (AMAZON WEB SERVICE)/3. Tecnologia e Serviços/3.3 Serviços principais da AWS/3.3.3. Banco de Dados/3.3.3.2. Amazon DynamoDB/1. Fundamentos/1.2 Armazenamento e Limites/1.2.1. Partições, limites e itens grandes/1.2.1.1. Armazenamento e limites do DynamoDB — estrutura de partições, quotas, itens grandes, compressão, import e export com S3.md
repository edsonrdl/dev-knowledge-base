### Armazenamento e limites do DynamoDB — estrutura de partições, quotas, itens grandes, compressão, import e export com S3

> [!warning] Aviso
> Quotas, limites por item/partição, formatos de import/export e preços do DynamoDB mudam, e várias quotas são ajustáveis por solicitação. Os números abaixo refletem a documentação conhecida na época da escrita. **Confirme em "Service, account, and table quotas" antes de projetar.** Os comandos **não foram executados**.

Conhecer **como o DynamoDB guarda os dados** e **onde estão os limites** evita três classes de problema: itens que não cabem, custos de armazenamento inesperados e migrações lentas. Esta nota abre o "capô" do armazenamento, lista os limites mais importantes, mostra padrões para **itens grandes** e cobre **import e export** com o S3.

**Analogia:** o DynamoDB é um **grande arquivo de gavetas**. Cada gaveta (partição) tem tamanho e velocidade de atendimento limitados; o arquivo cria gavetas novas conforme o volume cresce. Cada ficha (item) tem tamanho máximo — fichas maiores vão para o depósito ao lado (S3), deixando na gaveta só o endereço.

## Como os dados são armazenados

```
 Item ──hash(PK)──► partição física (SSD, replicada em 3 AZs)
                    ┌──────────────────────────────────────────┐
                    │ dentro da partição: itens ordenados por SK │
                    │   PK=C#1  SK=P#001                         │
                    │   PK=C#1  SK=P#002   ← mesma "coleção de itens" (mesma PK) fica junta │
                    └──────────────────────────────────────────┘
```

| Aspecto | Detalhe |
|---|---|
| **Particionamento** | O DynamoDB aplica uma função de hash sobre a **partition key** para escolher a partição |
| **Ordenação** | Dentro de uma PK, os itens ficam **ordenados pela sort key** (por isso `Query` por faixa é eficiente) |
| **Replicação** | Cada partição é replicada em **três AZs**; uma réplica é a líder de escrita |
| **Tamanho da partição** | Da ordem de **10 GB** por partição e **3.000 RCU / 1.000 WCU** por partição; ao exceder, a partição **se divide** automaticamente |
| **Divisão** | Por tamanho ou por throughput (carga); invisível para a aplicação |
| **Índices** | Cada GSI é uma tabela derivada, com suas próprias partições; o LSI vive junto da partição da tabela |
| **Armazenamento** | SSD; cobra-se por GB efetivamente armazenado, incluindo índices |

Você **não gerencia** partições, mas o **desenho da chave** determina como elas se formam. Uma PK de baixa cardinalidade concentra dados e tráfego; uma PK de alta cardinalidade espalha. Detalhes de escala na nota de **escala em profundidade**.

## Tamanho do item e como é calculado

O limite é **400 KB por item**, contando **nomes de atributos + valores**:

| Parte | Como conta |
|---|---|
| **Nomes de atributos** | UTF-8, **entram no tamanho** de cada item (atributos longos repetidos em milhões de itens custam armazenamento) |
| **Strings / binário** | Bytes UTF-8 / bytes |
| **Números** | Tamanho variável (até 21 bytes, aproximadamente 1 byte a cada 2 dígitos + 1) |
| **Boolean / Null** | 1 byte |
| **List / Map** | 3 bytes de overhead + soma dos elementos + 1 byte por elemento |
| **Índices** | Para cada item e cada índice, o DynamoDB acrescenta cerca de **100 bytes de overhead** no armazenamento do índice |

Exemplo de cálculo (aproximado):

```
Item: { "ClienteId": "C#1001", "PedidoId": "P#2026-0001", "total": 150.5, "status": "PAGO" }
 nomes:   9 + 8 + 5 + 6   = 28 bytes
 valores: 6 + 11 + ~4 + 4 = 25 bytes
 total ≈ 53 bytes  (muito abaixo de 400 KB)
```

Implicações práticas:

- Para tabelas com **bilhões de itens**, trocar `data_de_criacao_do_pedido` por `criado` economiza gigabytes (e RCU/WCU, que dependem do tamanho lido/escrito).
- Leitura/escrita consomem capacidade conforme o **tamanho do item** (blocos de 4 KB / 1 KB), então itens menores são mais baratos.
- Medir: a resposta do SDK pode devolver `ConsumedCapacity` (`--return-consumed-capacity TOTAL`), e `describe-table` traz `TableSizeBytes` e `ItemCount` (atualizados a cada ~6 horas).

## Quotas e limites principais

| Recurso | Limite típico (confirme) |
|---|---|
| Tamanho do item | 400 KB |
| Tamanho da partition key (valor) | 2.048 bytes |
| Tamanho da sort key (valor) | 1.024 bytes |
| Profundidade de aninhamento (Map/List) | 32 níveis |
| Itens por `BatchGetItem` / `BatchWriteItem` | 100 / 25 (16 MB de payload) |
| Itens por transação | Até 100 (4 MB) |
| Resultado de `Query`/`Scan` por página | 1 MB (use paginação com `LastEvaluatedKey`) |
| GSIs por tabela | 20 (ajustável) |
| LSIs por tabela | 5 (somente na criação) |
| Tamanho de uma coleção de itens com LSI | 10 GB por valor de PK |
| Tabelas por conta/região | 2.500 (ajustável) |
| Capacidade provisionada por tabela / conta | Altas, ajustáveis por solicitação |
| Duração do stream | 24 horas |
| Janela do PITR | 1 a 35 dias |
| Operações de controle (criar/excluir/alterar tabela) | Limitadas por taxa; muitas simultâneas dão erro |

**Limites são para planejar, não para decorar**: ao desenhar a tabela, cheque *item máximo*, *itens por transação*, *GSIs por tabela* e *tamanho de coleção de itens com LSI*. A página de quotas da AWS é a fonte de verdade.

## Itens grandes: padrões

Quando um atributo pode ultrapassar o limite (documento, HTML, imagem, histórico):

### 1. Ponteiro para o S3 (o mais comum)

```
 DynamoDB: { PK: "DOC#42", titulo: "...", s3_uri: "s3://docs/42/v3.json", tamanho: 2_400_000, etag: "..." }
 S3:       objeto com o conteúdo grande
```

| Vantagem | Cuidado |
|---|---|
| Sem limite de 400 KB, barato para armazenar | Duas operações (consistência entre elas é da aplicação) |
| Download direto pelo cliente (pre-signed URL) | Remover o objeto quando apagar o item (lifecycle ou evento de Stream) |
| Pode usar versionamento do S3 | Gravar **primeiro no S3**, depois o item (evita ponteiro quebrado) |

### 2. Compressão

Comprima valores textuais grandes (JSON/HTML) com gzip/zstd e grave como **Binary**. Reduz armazenamento e RCU/WCU; perde a capacidade de filtrar dentro do atributo (não dá para fazer `contains` em campo comprimido).

### 3. Particionamento vertical (dividir o item)

```
 PK=DOC#42  SK=META       → { titulo, autor, versao }          (pequeno, lido sempre)
 PK=DOC#42  SK=CORPO#001  → { chunk 1 do conteúdo }            (lido só quando necessário)
 PK=DOC#42  SK=CORPO#002  → { chunk 2 do conteúdo }
```

Vantagem: lê-se só a parte que interessa (RCU menor); `Query` com `begins_with(SK, 'CORPO#')` recompõe. Cuidado com consistência entre partes (use transação para atualizar vários).

### 4. Atributos "frios" em outra tabela

Separe dados quentes (acesso frequente) e frios (histórico) em tabelas diferentes, com **table class** apropriada.

## Table classes e custo de armazenamento

| Classe | Armazenamento | Leitura/escrita | Uso |
|---|---|---|---|
| **Standard** | Mais caro por GB | Mais barato por operação | Dados acessados com frequência |
| **Standard-IA** | ~60% mais barato por GB | Mais caro por operação | Tabelas grandes e pouco acessadas (logs, auditoria, histórico) |

Regra de bolso: se o **armazenamento** for mais de ~50% do custo da tabela, avalie Standard-IA; se o **throughput** dominar, mantenha Standard. A mudança de classe é online e reversível (com limite de frequência).

```bash
aws dynamodb update-table --table-name Historico --table-class STANDARD_INFREQUENT_ACCESS
aws dynamodb describe-table --table-name Historico \
  --query 'Table.{Classe:TableClassSummary.TableClass,Bytes:TableSizeBytes,Itens:ItemCount}'
```

Outras alavancas de custo de armazenamento: **TTL** (expurgo gratuito), **nomes curtos de atributos**, **projeção enxuta** nos GSIs (`KEYS_ONLY`/`INCLUDE`), **compressão** e **arquivar para S3** (export) o que não precisa estar quente.

## Export para o S3

Exporta os dados da tabela para o S3 **sem consumir RCU** e sem afetar o desempenho da tabela.

| Característica | Detalhe |
|---|---|
| **Pré-requisito** | **PITR habilitado** |
| **Tipos** | **Export completo** (snapshot em um ponto do tempo) e **export incremental** (mudanças em uma janela) |
| **Formatos** | DynamoDB JSON ou Amazon Ion |
| **Destino** | Bucket S3 na mesma ou em outra conta/região, com SSE-S3 ou SSE-KMS |
| **Uso** | Análises com Athena/Glue/EMR, arquivamento, migração, auditoria, treino de ML |
| **Custo** | Por GB exportado; sem RCU |

```bash
# Export completo para o S3 em um instante dentro da janela do PITR
aws dynamodb export-table-to-point-in-time \
  --table-arn arn:aws:dynamodb:sa-east-1:111122223333:table/Pedidos \
  --s3-bucket datalake-dynamo --s3-prefix pedidos/2026-11-06/ \
  --export-format DYNAMODB_JSON --export-type FULL_EXPORT

# Acompanhar
aws dynamodb list-exports --table-arn arn:aws:dynamodb:sa-east-1:111122223333:table/Pedidos
aws dynamodb describe-export --export-arn $EXPORT_ARN
```

Os arquivos saem em partes (`data/*.json.gz`) com `manifest-summary.json`; crie uma tabela no Glue/Athena apontando para o prefixo para consultar em SQL.

## Import do S3

Cria uma **nova tabela** a partir de arquivos no S3, sem consumir WCU.

| Característica | Detalhe |
|---|---|
| **Formatos** | CSV, DynamoDB JSON, Amazon Ion; compactados em GZIP ou ZSTD |
| **Destino** | **Sempre uma nova tabela** (não atualiza tabela existente) |
| **Chaves e índices** | Definidos na importação |
| **Erros** | Registros inválidos vão para o CloudWatch Logs; a importação pode continuar |
| **Custo** | Por GB importado |

```bash
aws dynamodb import-table \
  --s3-bucket-source S3Bucket=datalake-dynamo,S3KeyPrefix=carga-inicial/ \
  --input-format CSV --input-compression-type GZIP \
  --table-creation-parameters '{
     "TableName":"Produtos",
     "KeySchema":[{"AttributeName":"Sku","KeyType":"HASH"}],
     "AttributeDefinitions":[{"AttributeName":"Sku","AttributeType":"S"}],
     "BillingMode":"PAY_PER_REQUEST"}'
```

Para **carga em tabela existente**, use `BatchWriteItem` (paralelizado e com backoff), AWS Glue, DMS ou Step Functions Distributed Map.

## Exemplo prático

Cenário: tabela `Eventos` (logs de auditoria) com 3 TB, consultada raramente, e documentos de contrato que às vezes passam de 400 KB.

1. Mover `Eventos` para **Standard-IA** e ativar **TTL** (expurgo após 400 dias, após exportar o que for necessário).
2. Habilitar **PITR** e agendar **exports mensais** para S3 (Parquet via Glue) para o data lake e Athena.
3. Contratos: manter só metadados no DynamoDB (`PK=CONTRATO#id`, `s3_uri`, `versao`) e o PDF no S3 com versionamento; gravar no S3 antes de gravar o item.
4. Encurtar nomes de atributos nos novos itens (`ts`, `usr`, `ac`), economizando ~15% do armazenamento.
5. Alarmes: `TableSizeBytes` e custo por tag da tabela.
6. Nova versão do modelo? Importar um export no formato novo com `import-table` em uma tabela paralela e trocar a aplicação.

## Erros comuns e armadilhas

- **Guardar blobs grandes no item** e bater em 400 KB (ou pagar RCU enormes).
- **Nomes de atributos longos** multiplicados por bilhões de itens.
- **Gravar o item antes do objeto S3:** ponteiro quebrado se o upload falhar.
- **Esquecer de apagar o objeto S3** ao excluir o item (custo acumulado).
- **Projetar `ALL` em todo GSI:** duplica o armazenamento do item em cada índice.
- **Esperar que `ItemCount`/`TableSizeBytes` sejam em tempo real:** atualizam a cada ~6 h.
- **Tentar exportar sem PITR.**
- **Achar que o import atualiza uma tabela existente:** ele sempre cria uma nova.
- **Usar Scan para exportar tabelas grandes**, consumindo RCU, em vez de export para S3.
- **Ignorar quotas ajustáveis** até o dia em que a aplicação falha por limite.

## 🧩 Quiz de Fixação

1. O que conta para o limite de 400 KB de um item e por que isso importa para os nomes de atributos?
2. Qual o padrão recomendado para armazenar conteúdo maior que 400 KB e qual a ordem correta de escrita?
3. Quais as diferenças entre export e import do S3 quanto a pré-requisitos e destino?
4. Quando vale usar Standard-IA em uma tabela?

**Respostas:**
1) Contam os nomes dos atributos e seus valores (mais overhead de listas/mapas). Como o nome é repetido em cada item, nomes longos multiplicados por milhões de itens aumentam armazenamento e consumo de RCU/WCU.
2) Guardar o conteúdo no S3 e apenas um ponteiro (URI, versão, tamanho) no DynamoDB. Grava-se primeiro no S3 e depois o item, para nunca existir um ponteiro apontando para um objeto inexistente; na exclusão, remove-se também o objeto.
3) O export exige PITR habilitado, não consome RCU e grava no S3 (completo ou incremental, em DynamoDB JSON ou Ion). O import lê arquivos do S3 (CSV, DynamoDB JSON, Ion) e sempre cria uma nova tabela, sem consumir WCU.
4) Quando o armazenamento domina o custo da tabela (tabelas grandes) e o acesso é pouco frequente, como logs, auditoria e históricos; o custo por operação é maior, então não serve para tabelas muito acessadas.
