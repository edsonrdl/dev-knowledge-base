### O que é Amazon DynamoDB — banco NoSQL serverless, tabelas, itens, partition key e sort key

> [!warning] Aviso
> Limites (tamanho de item, quotas por tabela e partição), preços e recursos do DynamoDB mudam. Confirme na documentação. Os comandos **não foram executados**.

O **Amazon DynamoDB** é um banco de dados **NoSQL chave-valor e de documentos**, **totalmente gerenciado e serverless**, com latência de **milissegundos de um dígito** em qualquer escala. Não há servidores para provisionar, versões para atualizar nem partições para gerenciar manualmente: você cria uma **tabela**, define a **chave primária** e grava/lê itens.

**Analogia:** o DynamoDB é um **armário gigante com gavetas numeradas**. Para achar algo, você precisa saber **o número da gaveta** (partition key) e, se houver divisórias dentro dela, **a posição** (sort key). Não dá para perguntar "me traga tudo que é azul" sem varrer o armário inteiro: o acesso é rápido **porque** é por chave.

```
 Tabela "Pedidos"
 ┌──────────────┬───────────────┬───────────────────────────────────────┐
 │ PK (cliente) │ SK (pedido)   │ atributos livres por item             │
 ├──────────────┼───────────────┼───────────────────────────────────────┤
 │ C#1001       │ P#2026-0001   │ { total: 150.0, status: "PAGO" }      │
 │ C#1001       │ P#2026-0007   │ { total: 80.0,  itens: [...] }        │
 │ C#1002       │ P#2026-0003   │ { total: 300.0, cupom: "NATAL" }      │
 └──────────────┴───────────────┴───────────────────────────────────────┘
```

## Conceitos básicos

| Conceito | Descrição |
|---|---|
| **Tabela** | Coleção de itens; não há esquema fixo além da chave primária |
| **Item** | Registro (equivale a uma linha), até **400 KB** |
| **Atributo** | Campo do item; cada item pode ter atributos diferentes |
| **Chave primária** | Identifica o item de forma única; definida na criação e **imutável** |
| **Partition key (PK / hash)** | Define em qual partição física o item é armazenado |
| **Sort key (SK / range)** | Opcional; ordena itens com a mesma PK e permite consultas por faixa |
| **Índices secundários** | GSI e LSI, para consultar por outras chaves (próxima nota) |

### Tipos de chave primária

| Tipo | Composição | Exemplo |
|---|---|---|
| **Simples** | Só partition key | `UsuarioId` |
| **Composta** | Partition key + sort key | `ClienteId` + `PedidoId` |

Com chave composta, vários itens compartilham a mesma PK (uma "coleção de itens") e são consultados por faixa de SK (`begins_with`, `between`, `>`, `<`).

### Tipos de dados

| Categoria | Tipos |
|---|---|
| **Escalares** | String (S), Number (N), Binary (B), Boolean (BOOL), Null |
| **Conjuntos** | String Set (SS), Number Set (NS), Binary Set (BS) |
| **Documento** | List (L), Map (M), com aninhamento (JSON) |

Para chaves, só String, Number ou Binary.

---

## Como o DynamoDB distribui os dados

```
 PK → função hash → partição física (SSD, replicada em 3 AZs)
```

- O DynamoDB divide os dados em **partições**, escolhidas pelo **hash da partition key**.
- Cada partição é **replicada em três AZs** da região, com consistência forte opcional.
- Quando a tabela cresce ou recebe mais tráfego, as partições se **dividem automaticamente**.
- Por isso a escolha da **partition key** é a decisão de modelagem mais importante: precisa de **alta cardinalidade** e **distribuição uniforme** de acessos. Veja a nota de capacidade para as *hot partitions*.

---

## Consistência de leitura

| Tipo | Característica | Custo |
|---|---|---|
| **Eventualmente consistente** (padrão) | Pode devolver dados ligeiramente antigos (milissegundos) | 1 RCU = 2 leituras de até 4 KB |
| **Fortemente consistente** | Sempre devolve a escrita mais recente | 1 RCU = 1 leitura de até 4 KB |
| **Transacional** | ACID entre vários itens/tabelas | 2× o custo |

Índices secundários globais (GSI) só oferecem consistência eventual.

---

## Modos de capacidade (visão geral)

| Modo | Como funciona | Quando |
|---|---|---|
| **On-demand** | Paga por requisição, sem planejar capacidade | Tráfego imprevisível, novas aplicações |
| **Provisioned** | Você define RCU/WCU (com auto scaling opcional) | Tráfego previsível; custo menor com reservas |

Detalhes na nota de capacidade e desempenho.

## Quando usar DynamoDB (e quando não)

| Bom para | Evitar quando |
|---|---|
| Acesso por chave com latência previsível em qualquer escala | Você precisa de **consultas ad hoc**, junções complexas e agregações livres (use RDS/Aurora/Redshift/Athena) |
| Sessões, carrinhos, perfis, catálogos, jogos, IoT, filas de estado | Modelo relacional altamente normalizado com muitos relacionamentos |
| Cargas com picos enormes (escala automática) | Relatórios analíticos pesados diretamente na tabela |
| Aplicações serverless (Lambda, API Gateway) | Itens maiores que 400 KB (guarde no S3 e referencie) |
| Multi-região ativa-ativa (Global Tables) | Equipe sem disposição para modelar por padrões de acesso |

## Exemplo prático

```bash
# Criar a tabela Pedidos com chave composta e capacidade sob demanda
aws dynamodb create-table --table-name Pedidos \
  --attribute-definitions AttributeName=ClienteId,AttributeType=S AttributeName=PedidoId,AttributeType=S \
  --key-schema AttributeName=ClienteId,KeyType=HASH AttributeName=PedidoId,KeyType=RANGE \
  --billing-mode PAY_PER_REQUEST
# HASH = partition key ; RANGE = sort key ; PAY_PER_REQUEST = on-demand

# Inserir (ou substituir) um item
aws dynamodb put-item --table-name Pedidos --item '{
  "ClienteId": {"S": "C#1001"},
  "PedidoId":  {"S": "P#2026-0001"},
  "total":     {"N": "150.0"},
  "status":    {"S": "PAGO"}
}'

# Ler um item pela chave completa (GetItem: O(1), a operação mais barata)
aws dynamodb get-item --table-name Pedidos \
  --key '{"ClienteId": {"S": "C#1001"}, "PedidoId": {"S": "P#2026-0001"}}' \
  --consistent-read

# Listar todos os pedidos de um cliente (Query por PK + faixa de SK)
aws dynamodb query --table-name Pedidos \
  --key-condition-expression "ClienteId = :c AND begins_with(PedidoId, :p)" \
  --expression-attribute-values '{":c":{"S":"C#1001"},":p":{"S":"P#2026"}}'
```

Explicação: `get-item` e `query` usam a chave e são rápidos e baratos; `scan` leria a tabela inteira (evite em tabelas grandes).

## Como acessar

| Forma | Observação |
|---|---|
| **SDKs** (Python/boto3, JS, Java...) | `DynamoDBClient` / `DocumentClient`; recomenda-se a API de alto nível |
| **PartiQL** | Linguagem SQL-like (`SELECT * FROM Pedidos WHERE ClienteId='C#1001'`); continua respeitando o modelo de chave |
| **Console / CLI** | Administração e consultas pontuais |
| **Endpoint** | HTTPS público regional; use **VPC gateway endpoint** para tráfego privado |
| **DynamoDB local** | Versão local para desenvolvimento e testes |

## Erros comuns e armadilhas

- **Modelar como relacional** (tabelas normalizadas, joins): o DynamoDB não faz joins.
- **Partition key de baixa cardinalidade** (ex.: `status`, `data` do dia): partições quentes.
- **Usar Scan** em produção para consultas frequentes.
- **Não pensar nos access patterns antes de criar a tabela.**
- **Tentar mudar a chave primária:** é preciso criar nova tabela e migrar.
- **Itens muito grandes** (limite de 400 KB): armazene blobs no S3.
- **Esperar consistência forte nos GSIs.**
- **Valores numéricos como string** sem planejar ordenação (strings ordenam lexicograficamente).
- **Ignorar throttling** (`ProvisionedThroughputExceededException`) sem retry com backoff.

## 🧩 Quiz de Fixação

1. O que a partition key determina e por que sua escolha é crítica?
2. Qual a diferença entre `GetItem`, `Query` e `Scan`?
3. Quando o DynamoDB não é a melhor escolha?

**Respostas:**
1) Determina em qual partição física o item é armazenado (via hash). Se a chave tem baixa cardinalidade ou o acesso é desigual, surgem partições quentes e throttling; a escolha impacta desempenho e custo.
2) `GetItem` busca um item pela chave completa; `Query` busca itens de uma mesma partition key, opcionalmente filtrando por faixa de sort key; `Scan` lê a tabela inteira (lento e caro em tabelas grandes).
3) Quando é necessário consultar de forma ad hoc, fazer junções e agregações complexas, ou o modelo é altamente relacional; nesses casos, RDS/Aurora ou serviços analíticos são mais adequados.
