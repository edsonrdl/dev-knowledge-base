### Modelagem no DynamoDB — access patterns, GSI e LSI, Query versus Scan, expressões e transações

> [!warning] Aviso
> Limites de índices por tabela, tamanho de transação, regras de projeção e sintaxe de expressões podem mudar. Confirme na documentação. Os comandos **não foram executados**.

No DynamoDB você **modela a partir das perguntas** que a aplicação fará (os **access patterns**), e não a partir das entidades. Primeiro listam-se os padrões de acesso; depois desenha-se a chave da tabela e os índices para que cada padrão seja resolvido por **Query** (barato e rápido), nunca por **Scan**.

**Analogia:** em um banco relacional você organiza uma biblioteca por assunto e depois descobre como achar os livros. No DynamoDB você **organiza as estantes de acordo com as perguntas que os leitores vão fazer**, mesmo que isso signifique ter o mesmo livro em duas estantes.

## Passo a passo da modelagem

1. **Listar os access patterns** (leituras e escritas) com frequência e latência esperadas.
2. **Escolher a chave primária** (PK/SK) para atender os padrões mais importantes.
3. **Adicionar índices secundários** (GSI/LSI) para os padrões restantes.
4. **Validar** com o volume real e a distribuição de acessos (evitar partições quentes).
5. **Iterar**: novas perguntas podem exigir novos índices (mas a chave primária não muda).

Exemplo de lista de padrões (e-commerce):

| # | Padrão | Solução |
|---|---|---|
| 1 | Buscar um pedido pelo ID | `GetItem` (PK=Pedido) ou chave composta |
| 2 | Listar pedidos de um cliente, mais recentes primeiro | `Query` PK=Cliente, SK por data (`ScanIndexForward=false`) |
| 3 | Listar pedidos por status (para o time de logística) | GSI com PK=`status` (cuidado com cardinalidade) |
| 4 | Itens de um pedido | Itens na mesma coleção (PK=Pedido, SK=`ITEM#...`) |
| 5 | Pedidos de hoje por loja | GSI com PK=`loja#data` |

## Single-table design (tabela única)

Prática comum: **várias entidades na mesma tabela**, diferenciadas por prefixos nas chaves, de modo que uma única `Query` traga dados relacionados (substituindo o join).

```
 PK            │ SK                   │ tipo     │ atributos
 ──────────────┼──────────────────────┼──────────┼──────────────────────────
 CLIENTE#1001  │ PERFIL               │ cliente  │ nome, email
 CLIENTE#1001  │ PEDIDO#2026-0001     │ pedido   │ total, status
 CLIENTE#1001  │ PEDIDO#2026-0007     │ pedido   │ total, status
 PEDIDO#2026-0001 │ ITEM#1            │ item     │ sku, qtd, preco
 PEDIDO#2026-0001 │ ITEM#2            │ item     │ sku, qtd, preco

 Query PK=CLIENTE#1001            → perfil + todos os pedidos do cliente (uma chamada)
 Query PK=CLIENTE#1001, SK begins_with PEDIDO#  → só os pedidos
```

| Vantagens | Cuidados |
|---|---|
| Menos chamadas (sem join), menos latência | Mais difícil de ler e evoluir |
| Uma tabela, uma configuração de capacidade/backup | Exige disciplina de prefixos e documentação |
| Transações entre entidades da mesma tabela | Nem sempre é o melhor: múltiplas tabelas são válidas para domínios simples |

Não é dogma: use tabela única quando os padrões de acesso agregarem entidades relacionadas; use tabelas separadas quando fizer sentido operacional (TTL, backup, permissões).

## Índices secundários

### GSI (Global Secondary Index)

| Característica | Detalhe |
|---|---|
| **Chave** | PK e SK **diferentes** da tabela |
| **Escopo** | Cobre a tabela inteira (todas as partições) |
| **Criação** | A qualquer momento |
| **Capacidade** | **Própria** (provisionada/on-demand separada da tabela) |
| **Consistência** | **Eventual** apenas |
| **Projeção** | `KEYS_ONLY`, `INCLUDE` (alguns atributos) ou `ALL` |
| **Limite** | Tipicamente 20 por tabela (confirme) |

### LSI (Local Secondary Index)

| Característica | Detalhe |
|---|---|
| **Chave** | **Mesma PK** da tabela, SK diferente |
| **Criação** | **Somente na criação da tabela** |
| **Consistência** | Permite leitura fortemente consistente |
| **Limite** | Até 5 por tabela; coleção de itens limitada a 10 GB por PK |
| **Capacidade** | Compartilha com a tabela |

### GSI × LSI

| Critério | GSI | LSI |
|---|---|---|
| Chave de partição | Qualquer atributo | A mesma da tabela |
| Criar depois | **Sim** | Não |
| Consistência forte | Não | Sim |
| Capacidade própria | Sim | Não |
| Uso comum | **Maioria dos casos** | Ordenações alternativas dentro da mesma PK |

Padrões úteis de GSI:

- **Inversão de chaves** (GSI com PK=SK da tabela, SK=PK): consultar "relações inversas".
- **Sparse index:** só itens que possuem o atributo da chave do índice aparecem no índice (ex.: `pendente_envio`), formando uma fila barata.
- **Sharding de chave** (`status#0..9`) para espalhar escrita quente.

## Query × Scan

| Aspecto | **Query** | **Scan** |
|---|---|---|
| Entrada | PK (obrigatória) + condição opcional de SK | Nenhuma |
| O que lê | Só os itens da partição (ou faixa) | **Tabela inteira** |
| Custo | Proporcional aos itens lidos | Proporcional à tabela inteira |
| Filtro (`FilterExpression`) | Aplicado **depois** de ler (não reduz o consumo de RCU) | Idem |
| Uso | Padrão de acesso | Exportação, análises raras, tabelas pequenas |

Alternativas ao Scan: **export para S3** (sem consumir capacidade), **Athena** sobre o export, **parallel scan** com cuidado, ou índice dedicado.

## Expressões

| Tipo | Para quê | Exemplo |
|---|---|---|
| **KeyConditionExpression** | Selecionar itens na Query | `ClienteId = :c AND begins_with(PedidoId, :p)` |
| **FilterExpression** | Filtrar o resultado (após a leitura) | `status = :s` |
| **ProjectionExpression** | Escolher atributos retornados | `PedidoId, total` |
| **ConditionExpression** | Escrita condicional (concorrência otimista) | `attribute_not_exists(PedidoId)` |
| **UpdateExpression** | Atualizar atributos de forma atômica | `SET total = total + :v ADD qtd :um` |

```bash
# Inserção condicional: impede sobrescrever um pedido existente
aws dynamodb put-item --table-name Pedidos \
  --item '{"ClienteId":{"S":"C#1001"},"PedidoId":{"S":"P#2026-0010"},"status":{"S":"NOVO"}}' \
  --condition-expression "attribute_not_exists(PedidoId)"

# Atualização atômica de contador e mudança de status
aws dynamodb update-item --table-name Pedidos \
  --key '{"ClienteId":{"S":"C#1001"},"PedidoId":{"S":"P#2026-0010"}}' \
  --update-expression "SET #s = :novo ADD tentativas :um" \
  --condition-expression "#s = :atual" \
  --expression-attribute-names '{"#s":"status"}' \
  --expression-attribute-values '{":novo":{"S":"PAGO"},":atual":{"S":"NOVO"},":um":{"N":"1"}}'
# #s: alias porque "status" é palavra reservada
# A condição garante que só atualiza se o status ainda for NOVO (evita corrida)
```

## Transações e escrita em lote

| Operação | Característica |
|---|---|
| **TransactWriteItems** | Até ~100 itens/ações **ACID** (all-or-nothing) entre tabelas da mesma região; custo 2× |
| **TransactGetItems** | Leituras consistentes de vários itens |
| **BatchWriteItem / BatchGetItem** | Até 25 escritas / 100 leituras por chamada; **não** são transacionais; tratar itens não processados |
| **Escritas condicionais** | Concorrência otimista com versão (`version = :v`) |
| **Idempotência** | Token de cliente em transações (`ClientRequestToken`) |

Use transações quando precisar de consistência entre itens (ex.: debitar saldo e registrar a movimentação). Caso contrário, prefira operações simples e idempotentes.

## Exemplo prático

Pedido com itens e atualização de estoque de forma atômica:

```bash
aws dynamodb transact-write-items --transact-items '[
  {"Put":{"TableName":"Pedidos","Item":{"ClienteId":{"S":"C#1001"},"PedidoId":{"S":"P#2026-0011"},"status":{"S":"NOVO"}},
          "ConditionExpression":"attribute_not_exists(PedidoId)"}},
  {"Update":{"TableName":"Estoque","Key":{"Sku":{"S":"SKU-9"}},
             "UpdateExpression":"SET qtd = qtd - :n",
             "ConditionExpression":"qtd >= :n",
             "ExpressionAttributeValues":{":n":{"N":"2"}}}}
]'
# Ou o pedido é criado E o estoque baixa, ou nada acontece (estoque insuficiente cancela tudo)
```

## Modelagem na prática: do requisito à tabela

```
 Requisitos            Entidades+acessos          Chaves
 "pedido por ID"   ──►  AP1: GetItem             ──► PK=ORDER#id
 "pedidos do cliente    AP2: Query por cliente      GSI1: PK=CUSTOMER#id SK=data
  por data"             AP3: Query por status       GSI2: PK=STATUS#x SK=data
 "pedidos abertos"
```

| Índice | Chaves | Consistência | Capacidade | Quando usar |
|---|---|---|---|---|
| Tabela base | PK + SK | Forte ou eventual | Própria | Acesso principal |
| **GSI** | PK/SK diferentes | Só eventual | Própria (cobra escrita) | Novos padrões de acesso, a qualquer momento |
| **LSI** | Mesma PK, outra SK | Forte ou eventual | Compartilha a da tabela | Só na criação da tabela; limita partição |

> [!warning] Valores, limites e preços mudam; os exemplos deste material não foram executados. Cotas de GSIs/LSIs e limite de tamanho de coleção de itens mudam; consulte a documentação.

### Árvore de decisão: Query, Scan ou GSI

```
Sei a partition key?
├─ Sim ─► Query (com condição na SK)
└─ Não
    ├─ Consulta frequente? ─► criar GSI para ela
    └─ Rara / exportação / manutenção? ─► Scan paginado (ou export p/ S3)
```

## Anti-padrões

| Anti-padrão | Efeito | Correção |
|---|---|---|
| Scan em produção | Custo e lentidão | GSI ou remodelagem |
| Partition key de baixa cardinalidade | Hot partition | Chave composta/sharding |
| GSI para tudo | Escritas amplificadas e caras | Projetar só os atributos necessários |
| Itens enormes | Custo de leitura | Dividir ou mover para S3 |
| Transação onde basta escrita simples | Custo 2× | Usar `PutItem`/`UpdateItem` condicionais |

## CLI comentado

```bash
# Escrita condicional: evita sobrescrever um item existente
aws dynamodb put-item --table-name Pedidos \
  --item '{"PK":{"S":"ORDER#1"},"SK":{"S":"META"},"status":{"S":"NEW"}}' \
  --condition-expression "attribute_not_exists(PK)"

# Consulta no GSI, paginando de 25 em 25
aws dynamodb query --table-name Pedidos --index-name GSI1 \
  --key-condition-expression "GSI1PK = :c" \
  --expression-attribute-values '{":c":{"S":"CUSTOMER#9"}}' --limit 25

# Transação atômica entre dois itens
aws dynamodb transact-write-items --transact-items file://transacao.json
```

## Troubleshooting

| Sintoma | Causa provável | Ação |
|---|---|---|
| `ConditionalCheckFailed` | Condição não atendida (esperado em concorrência) | Tratar como controle de concorrência/retry |
| GSI atrasado | Replicação eventual | Aceitar ou ler da tabela base |
| Throttling no GSI | GSI com capacidade menor que a escrita | Ajustar capacidade/on-demand |
| `ValidationException` em expressão | Nome reservado de atributo | Usar `ExpressionAttributeNames` |

## Custo

Cada GSI replica escritas (custo de gravação adicional) e armazena atributos projetados. Transações consomem o dobro de unidades de capacidade. Projete índices só para padrões de acesso reais.

## Erros comuns e armadilhas

- **Começar pelas entidades em vez dos access patterns.**
- **Usar FilterExpression achando que reduz o custo:** o consumo de RCU é pelo que foi lido.
- **GSI com chave de baixa cardinalidade:** partição quente no índice.
- **GSI com projeção `ALL` por padrão:** custo de armazenamento e escrita.
- **Esperar consistência forte em GSI.**
- **Criar LSI depois:** só na criação da tabela.
- **Esquecer palavras reservadas** (`status`, `name`, `date`): use `ExpressionAttributeNames`.
- **Batch sem tratar `UnprocessedItems`.**
- **Transações em excesso:** custo 2× e limites de contenção.
- **Scan em produção** para listagens frequentes.

## 🧩 Quiz de Fixação

1. Por que se diz que no DynamoDB se modela a partir dos access patterns?
2. Qual a diferença entre GSI e LSI?
3. O `FilterExpression` reduz o consumo de capacidade de uma Query?

**Respostas:**
1) Porque o DynamoDB só é eficiente para acessos pela chave; as chaves e índices precisam ser desenhados para atender as perguntas conhecidas, sem joins nem consultas ad hoc.
2) GSI tem PK/SK diferentes, cobre a tabela, pode ser criado depois, tem capacidade própria e só consistência eventual; LSI usa a mesma PK com outra SK, só pode ser criado na criação da tabela, compartilha capacidade e permite consistência forte.
3) Não: o filtro é aplicado depois da leitura, e o consumo é calculado pelos itens lidos, não pelos retornados.

4. Qual a principal limitação de um GSI quanto à consistência?
5. Por que um GSI amplifica custo de escrita?

**Respostas das questões complementares:**
4) Só oferece leitura eventualmente consistente.
5) Cada escrita na tabela base que afeta atributos do índice também é replicada no GSI, consumindo capacidade de gravação e armazenamento adicionais.
6) É esperado quando a condição não é atendida (por exemplo, concorrência); trate como controle de concorrência, relendo o item e tentando novamente se fizer sentido.
