### Consistência, concorrência e padrões avançados de modelagem no DynamoDB — locking otimista, idempotência, adjacency list, GSI overloading, versionamento e séries temporais

> [!warning] Aviso
> Limites de transações, regras de consistência e recursos de expressões evoluem. Os padrões aqui são práticas consolidadas, mas devem ser validados com o volume e a distribuição reais da sua carga. Confirme limites na documentação. Os comandos e códigos **não foram executados**.

Depois de entender chaves, índices e capacidade, o desafio seguinte é fazer o DynamoDB se comportar **corretamente sob concorrência** (duas requisições alterando o mesmo item) e **modelar relacionamentos e histórico** sem joins. Esta nota cobre: modelos de **consistência** e **isolamento**, **locking otimista**, **idempotência**, **transações**, e padrões como **adjacency list**, **GSI overloading**, **versionamento de itens**, **séries temporais** e **locks distribuídos**.

**Analogia:** várias pessoas editando a mesma ficha de papel. Sem regra, a última a escrever apaga o trabalho da anterior. **Locking otimista** é conferir o "número da versão" da ficha antes de gravar; **idempotência** é carimbar a operação com um número único para que repeti-la não duplique o efeito; **transações** são fechar duas fichas ao mesmo tempo, ou as duas, ou nenhuma.

## Consistência e isolamento

| Operação | Garantia |
|---|---|
| `GetItem`/`Query`/`Scan` padrão | **Eventualmente consistente** (pode ler um valor ligeiramente antigo) |
| Leitura com `ConsistentRead=true` | **Fortemente consistente** na tabela (lê o resultado das escritas confirmadas); **não** disponível em GSIs |
| Escrita de um único item | **Atômica**; sempre fortemente consistente na gravação |
| `TransactGetItems` / `TransactWriteItems` | **ACID**, com isolamento **serializável** entre transações e *read-committed* para leituras comuns concorrentes |
| `BatchGetItem` / `BatchWriteItem` | **Não** são atômicos: itens podem ter sucesso ou falha individualmente |
| GSI | Sempre eventualmente consistente (atraso em geral de ms) |
| Entre regiões (Global Tables MREC) | Eventual; conflito resolvido por last-writer-wins |

Regra prática: **leia com consistência forte quando o resultado alimenta uma decisão** (ex.: ler saldo antes de debitar) e use escrita condicional para tornar a decisão segura mesmo se a leitura estiver defasada.

## Locking otimista (escrita condicional com versão)

Evita o clássico *lost update*: dois clientes leem o mesmo item e o segundo sobrescreve a alteração do primeiro.

```
 Cliente A lê  (versao=5, saldo=100)       Cliente B lê (versao=5, saldo=100)
 A grava SET saldo=70, versao=6  IF versao=5  → OK
 B grava SET saldo=60, versao=6  IF versao=5  → FALHA (ConditionalCheckFailedException) → B relê e tenta de novo
```

```bash
aws dynamodb update-item --table-name Contas \
  --key '{"ContaId":{"S":"C#1001"}}' \
  --update-expression "SET saldo = :novo, versao = :v1" \
  --condition-expression "versao = :v0" \
  --expression-attribute-values '{":novo":{"N":"70"},":v1":{"N":"6"},":v0":{"N":"5"}}'
# Se versao != 5, a operação falha com ConditionalCheckFailedException e nada é gravado
```

Boas práticas:

- Atributo `versao` (ou `updatedAt`) em todo item sujeito a edição concorrente.
- Em caso de falha: **reler, reaplicar a lógica e tentar de novo** (com limite e backoff).
- Para valores numéricos incrementais, prefira **`ADD`/`SET x = x + :n`** (atômico, sem leitura prévia).
- Evite *read-modify-write* sem condição.
- `ReturnValuesOnConditionCheckFailure=ALL_OLD` devolve o item atual na falha, evitando uma nova leitura.

### Condições úteis

| Padrão | Expressão |
|---|---|
| Criar apenas se não existir | `attribute_not_exists(PK)` |
| Atualizar apenas se existir | `attribute_exists(PK)` |
| Máquina de estados | `#status = :esperado` (só transita de NOVO para PAGO) |
| Limite/estoque | `estoque >= :qtd` |
| Versão | `versao = :v` |

## Idempotência

Em sistemas distribuídos, repetições são normais (retry de SDK, reentrega de fila, reprocessamento de Stream). Uma operação é **idempotente** se executá-la 1 ou N vezes produz o mesmo efeito.

| Técnica | Como |
|---|---|
| **Chave natural determinística** | Use um ID derivado da requisição (`PedidoId` gerado pelo cliente, ULID) em vez de gerar aleatório no servidor a cada tentativa |
| **Put condicional** | `attribute_not_exists(PK)`: a segunda tentativa falha sem efeito |
| **Tabela de idempotência** | Item `IDEMP#<chave>` com resultado e TTL; verificar antes de executar |
| **Client request token em transação** | `TransactWriteItems` aceita `ClientRequestToken` (idempotente por ~10 minutos) |
| **Atualizações monotônicas** | `SET status = :novo` com condição de transição válida |
| **Operações comutativas** | `ADD` não é idempotente — para contagem exata, registre o evento (`EVENTO#id`) em vez de apenas incrementar |

Padrão "registrar-e-processar" em uma transação:

```bash
aws dynamodb transact-write-items --transact-items '[
 {"Put":{"TableName":"App","Item":{"PK":{"S":"IDEMP#req-8f2"},"SK":{"S":"RES"},"ttl":{"N":"1731000000"}},
         "ConditionExpression":"attribute_not_exists(PK)"}},
 {"Update":{"TableName":"App","Key":{"PK":{"S":"CONTA#1001"},"SK":{"S":"SALDO"}},
            "UpdateExpression":"SET saldo = saldo - :v","ConditionExpression":"saldo >= :v",
            "ExpressionAttributeValues":{":v":{"N":"30"}}}}
]'
# Se req-8f2 já foi processada, a transação é cancelada (item de idempotência já existe) e o saldo não é debitado de novo
```

## Transações em detalhe

| Aspecto | Detalhe |
|---|---|
| **Itens por transação** | Até 100 (limite de 4 MB no total) |
| **Escopo** | Mesma conta e região; pode envolver várias tabelas |
| **Operações** | `Put`, `Update`, `Delete`, `ConditionCheck` (checa sem alterar) |
| **Custo** | 2× unidades de leitura/escrita (fase de preparação e confirmação) |
| **Conflitos** | Duas transações no mesmo item: uma é cancelada (`TransactionCanceledException` com motivos por item, ex.: `TransactionConflict`, `ConditionalCheckFailed`) |
| **Uso em GSI** | Não incluem leitura de GSI |
| **Retry** | Trate cancelamentos por conflito com backoff |
| **Global Tables** | ACID somente dentro da região |

Quando usar: movimentação entre contas, criar pedido + baixar estoque, outbox (dado + evento), manter um índice invertido manual. Evite transações para tudo: elas custam o dobro e aumentam contenção.

## Padrões avançados de modelagem

### 1. Adjacency list (listas de adjacência)

Modela **relações muitos-para-muitos** e grafos simples em uma tabela, com itens representando as **arestas**, e um GSI invertido.

```
 PK        │ SK          │ atributos
 ──────────┼─────────────┼─────────────────
 ALUNO#10  │ ALUNO#10    │ nome, email                (metadados do nó)
 ALUNO#10  │ CURSO#7     │ matriculadoEm, nota        (aresta aluno→curso)
 ALUNO#10  │ CURSO#9     │ ...
 CURSO#7   │ CURSO#7     │ titulo, professor
 GSI1: PK=SK, SK=PK  (invertido)
   Query PK=ALUNO#10          → o aluno e todos os cursos dele
   GSI1 Query PK=CURSO#7      → o curso e todos os alunos
```

### 2. GSI overloading (sobrecarga de índice)

Usar **nomes genéricos** (`GSI1PK`, `GSI1SK`) preenchidos de forma diferente conforme o tipo de entidade, aproveitando **um único GSI** para vários padrões de acesso (limite de 20 GSIs).

| Entidade | `GSI1PK` | `GSI1SK` | Padrão atendido |
|---|---|---|---|
| Pedido | `STATUS#PAGO` | `2026-11-06T10:00#ped123` | Pedidos pagos por data |
| Usuário | `EMAIL#ana@x.com` | `USER` | Buscar usuário por e-mail |
| Produto | `CAT#livros` | `PRECO#0049.90` | Produtos de uma categoria por preço |

Cuidado: PKs de GSI como `STATUS#PAGO` têm baixa cardinalidade — combine com sharding (`STATUS#PAGO#03`) se houver alto volume.

### 3. Sort key hierárquica

`SK = PAIS#BR#ESTADO#SP#CIDADE#Campinas` permite `begins_with` em qualquer nível (`PAIS#BR#ESTADO#SP`) com um único `Query`.

### 4. Versionamento de itens

Guarda o **histórico** de alterações mantendo uma versão "corrente" fácil de ler:

```
 PK=DOC#42  SK=v0000          → cópia da versão corrente (atualizada a cada mudança)   ← lido sempre
 PK=DOC#42  SK=v0001          → versão 1 (imutável)
 PK=DOC#42  SK=v0002          → versão 2 (imutável)
```

Gravação em transação: `Put v000N` (imutável, `attribute_not_exists`) + `Update v0000` com `versao = :n-1` (locking otimista). Consulta de histórico: `Query PK=DOC#42 begins_with(SK,'v') ScanIndexForward=false Limit=N`.

### 5. Séries temporais

| Técnica | Como |
|---|---|
| **PK por entidade, SK por timestamp** | `PK=SENSOR#12`, `SK=2026-11-06T10:00:00Z` — consulta por intervalo (`between`) |
| **Bucket temporal na PK** | `PK=SENSOR#12#2026-11`, evita partições gigantes e permite arquivamento por mês |
| **Sharding no bucket** | `PK=SENSOR#12#2026-11-06#07` (shard 0-9) para alta frequência |
| **TTL** | Expirar dados antigos sem custo de escrita |
| **Tabelas por período** | Tabela por mês/semana: descarte barato (delete table), `table class` IA para meses antigos |
| **Agregados pré-calculados** | Streams → Lambda atualiza resumos por hora/dia |

### 6. Sparse index (índice esparso)

Só os itens com o atributo da chave do índice aparecem. Ex.: atributo `pendente_envio` presente apenas em itens a enviar → um GSI funciona como **fila barata** de pendentes; ao enviar, remova o atributo e o item sai do índice.

### 7. Soft delete e arquivamento

`SET excluido_em = :agora, ttl = :agora+30d` em vez de `DeleteItem`: recuperável, e o TTL limpa depois (arquive o `REMOVE` via Streams).

### 8. Item grande dividido

Separar metadados (leitura frequente) do corpo/anexos em itens ou no S3 (nota de armazenamento).

## Lock distribuído com DynamoDB (lease)

Pode-se implementar um **lock com expiração** usando escrita condicional:

```
 Adquirir:  PutItem  PK=LOCK#job-x  {dono, expira_em=agora+30s}
            Condition: attribute_not_exists(PK) OR expira_em < :agora
 Renovar:   UpdateItem SET expira_em = :novo  Condition: dono = :eu
 Liberar:   DeleteItem  Condition: dono = :eu
```

Pontos de atenção: **sincronia de relógios** (use o relógio do cliente com folga ou o valor de `:agora` calculado de forma consistente), tempo de vida curto com renovação (heartbeat), e **não confie no TTL do DynamoDB** para liberar o lock (a remoção pode demorar): sempre compare `expira_em` na condição. Existe uma biblioteca (`dynamodb-lock-client`) que implementa o padrão.

## Quando o modelo deixa de servir

| Sintoma | Provável causa | Ação |
|---|---|---|
| Muitos padrões de acesso novos exigindo GSIs | Modelo muito rígido | Revisar access patterns, GSI overloading, ou usar outro banco para consultas ad hoc |
| Scan frequente | Falta de índice adequado | Criar GSI/esparso, export para Athena |
| Conflitos frequentes em um item | Item "quente" de escrita | Sharding, eventos em vez de contador |
| Relações profundas e traversais | Domínio de grafo | Considere Neptune |
| Relatórios complexos | OLAP | Export/zero-ETL para Redshift/Athena |

## Exemplo prático

Sistema de **carteira digital**:

1. `Contas` com `versao`; débito/crédito via `TransactWriteItems`: `Update` do saldo origem (`saldo >= :v`), `Update` do destino e `Put` do lançamento `LANC#<id>` (`attribute_not_exists`), tudo com `ClientRequestToken` derivado do ID da operação enviado pelo cliente.
2. Histórico de lançamentos: `PK=CONTA#1001`, `SK=LANC#<timestamp>#<id>`; consulta paginada por período; **bucket mensal** para contas muito ativas.
3. Extrato mensal: Stream → Lambda agrega por conta e grava `PK=CONTA#1001, SK=EXTRATO#2026-11`.
4. Estorno: cria `LANC` de estorno referenciando o original (nunca altera lançamentos).
5. Idempotência: o app móvel gera o `idOperacao` uma vez; reenvios caem na condição `attribute_not_exists`.
6. Busca por e-mail e por CPF: **GSI overloading** (`GSI1PK=EMAIL#...` / `CPF#...`).
7. Auditoria: Streams (`NEW_AND_OLD_IMAGES`) → Firehose → S3 imutável.

## Erros comuns e armadilhas

- **Read-modify-write sem condição:** perda de atualização.
- **Esquecer `ConsistentRead`** quando a decisão depende do dado mais recente.
- **Esperar atomicidade de `BatchWriteItem`.**
- **Usar contadores `ADD` onde repetição causa erro** (não é idempotente).
- **Gerar IDs no servidor a cada tentativa**, duplicando registros em retries.
- **Transações demais:** custo 2× e contenção.
- **Cancelamento de transação por conflito sem retry/backoff.**
- **GSI overloading sem documentação:** ninguém entende depois.
- **GSI com chave de baixa cardinalidade** (`STATUS#PAGO`) em alto volume.
- **Lock distribuído dependente do TTL do DynamoDB.**
- **Versionamento sem transação**, deixando o "corrente" desalinhado do histórico.
- **Modelar relacionamentos profundos** que pedem um banco de grafos.

## 🧩 Quiz de Fixação

1. Como o locking otimista evita *lost update* e o que o cliente faz ao falhar?
2. Quais técnicas tornam uma escrita idempotente?
3. Qual a diferença entre `BatchWriteItem` e `TransactWriteItems`?
4. Para que serve o GSI overloading e qual o risco?

**Respostas:**
1) A escrita inclui `ConditionExpression versao = :v_lido`; se outro cliente já alterou, falha com `ConditionalCheckFailedException` e nada é gravado. O cliente relê o item, reaplica a lógica e tenta de novo, com limite e backoff.
2) IDs determinísticos gerados pelo cliente, put condicional `attribute_not_exists`, item de idempotência com TTL, `ClientRequestToken` em transações e condições de transição de estado.
3) `BatchWriteItem` agrupa até 25 operações para eficiência, sem atomicidade (itens podem falhar individualmente); `TransactWriteItems` executa até 100 operações de forma ACID (todas ou nenhuma), com custo 2× e risco de conflito.
4) Usar atributos genéricos (`GSI1PK/GSI1SK`) preenchidos de formas diferentes por entidade para atender vários padrões de acesso com um único GSI, economizando índices. O risco é a complexidade/obscuridade do modelo e chaves de baixa cardinalidade gerando partições quentes.
