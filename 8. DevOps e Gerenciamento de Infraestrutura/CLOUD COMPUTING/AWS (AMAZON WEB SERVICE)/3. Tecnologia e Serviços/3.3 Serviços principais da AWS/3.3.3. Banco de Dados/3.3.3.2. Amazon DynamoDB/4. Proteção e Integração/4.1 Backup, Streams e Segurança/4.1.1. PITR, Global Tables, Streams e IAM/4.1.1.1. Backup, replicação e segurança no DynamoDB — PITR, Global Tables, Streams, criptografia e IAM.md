### Backup, replicação e segurança no DynamoDB — PITR, Global Tables, Streams, criptografia e IAM

> [!warning] Aviso
> Janelas de PITR, comportamento de Global Tables (versões), limites de Streams e opções de criptografia mudam. Confirme na documentação. Os comandos e JSONs **não foram executados**.

Fechando o DynamoDB: como **proteger os dados** (backups e PITR), **replicá-los entre regiões** (Global Tables), **reagir a mudanças** (Streams) e **controlar o acesso** (criptografia, IAM, VPC endpoints).

**Analogia:** a tabela é um **cofre com câmera e réplicas**: backups são fotografias do cofre, o PITR é a gravação contínua que permite rebobinar, Global Tables são filiais com o mesmo cofre sincronizado, Streams são o alarme que avisa a cada mudança, e o IAM é o controle de quem entra e em qual gaveta.

## Backup e recuperação

### Backups sob demanda

- Cópia **completa** da tabela em um instante, **sem impacto de desempenho** e sem consumir capacidade.
- Retidos até você excluir; podem ser **restaurados** para uma **nova** tabela (mesma ou outra região/conta, conforme configuração).
- Inclui dados, índices, configurações de capacidade e criptografia; **não** inclui automaticamente: auto scaling, TTL, tags, alarmes (reconfigure após restaurar).

### Point-in-time recovery (PITR)

| Característica | Detalhe |
|---|---|
| **Janela** | Restaura para qualquer segundo dos últimos **1 a 35 dias** (configurável) |
| **Ativação** | Por tabela (desabilitado por padrão) |
| **Restauração** | Cria uma **nova tabela**; leva tempo proporcional ao tamanho |
| **Custo** | Cobrado por GB da tabela |
| **Proteção** | Contra exclusão/alteração acidental de dados ou tabela |

```bash
# Habilitar PITR com retenção de 35 dias
aws dynamodb update-continuous-backups --table-name Pedidos \
  --point-in-time-recovery-specification PointInTimeRecoveryEnabled=true,RecoveryPeriodInDays=35

# Restaurar para um instante específico em uma tabela nova
aws dynamodb restore-table-to-point-in-time --source-table-name Pedidos \
  --target-table-name Pedidos-restaurada --restore-date-time 2026-11-06T14:30:00Z

# Backup sob demanda
aws dynamodb create-backup --table-name Pedidos --backup-name pre-migracao
```

Para política centralizada, cópia entre contas e regiões, cofres imutáveis e relatórios, use o **AWS Backup** ([[8. DevOps e Gerenciamento de Infraestrutura/CLOUD COMPUTING/AWS (AMAZON WEB SERVICE)/3. Tecnologia e Serviços/3.3 Serviços principais da AWS/3.3.2. Armazenamento/3.3.2.6. AWS Backup/0 AWS Backup (Tópicos )|AWS Backup]]).

Outros recursos de dados: **export para S3** (a partir do PITR, sem consumir capacidade; formatos DynamoDB JSON/Ion) e **import do S3**.

## Global Tables (multi-região ativa-ativa)

Replica uma tabela em **várias regiões**, com **escrita em qualquer réplica** e replicação assíncrona (tipicamente em **menos de ~1 s**).

```
 us-east-1 (réplica)  ◄══ replicação multiativa ══►  sa-east-1 (réplica)
        ▲                                                    ▲
   usuários EUA                                       usuários Brasil
```

| Característica | Detalhe |
|---|---|
| **Escrita** | Em qualquer região (multi-active) |
| **Resolução de conflitos** | **Last writer wins** (última escrita por timestamp) |
| **Consistência** | Forte apenas dentro da região; entre regiões é eventual (versão MREC) ou, na versão mais recente, opção de forte multi-região (MRSC, confirme disponibilidade) |
| **Requisitos** | Streams habilitados (gerenciado), mesmas chaves e índices, capacidade configurada em cada região |
| **Uso** | Baixa latência global, **DR com RPO próximo de zero**, alta disponibilidade regional |
| **Custo** | Escritas replicadas cobradas (rWCU) em cada região + transferência entre regiões |

Boas práticas: evitar escrever o **mesmo item** em duas regiões simultaneamente (conflitos); roteie cada usuário à sua região "casa" (Route 53 latência/failover). Veja o roteamento em [[8. DevOps e Gerenciamento de Infraestrutura/CLOUD COMPUTING/AWS (AMAZON WEB SERVICE)/3. Tecnologia e Serviços/3.3 Serviços principais da AWS/3.3.4. Rede/3.3.4.5. Amazon Route 53/0 Amazon Route 53 (Tópicos )|Amazon Route 53]].

```bash
# Adicionar uma réplica em outra região (tabela com streams e criptografia compatíveis)
aws dynamodb update-table --table-name Pedidos \
  --replica-updates '[{"Create":{"RegionName":"us-east-1"}}]'
```

## DynamoDB Streams

Registro **ordenado e temporário (24 h)** das alterações de itens (inserção, atualização, exclusão), por partição.

| Visão do stream (`StreamViewType`) | Conteúdo |
|---|---|
| `KEYS_ONLY` | Apenas as chaves |
| `NEW_IMAGE` | Item após a mudança |
| `OLD_IMAGE` | Item antes da mudança |
| `NEW_AND_OLD_IMAGES` | Ambos |

```
 Tabela ──escrita──► Stream (24 h) ──► Lambda (event source mapping)
                                   ├─► índice em OpenSearch
                                   ├─► agregações/contadores
                                   └─► replicação, auditoria, notificações
```

Casos de uso: **event-driven** (disparar Lambda), manter **view materializada**, **replicação** para outros stores, **auditoria**, integração com EventBridge Pipes. Alternativa: **Kinesis Data Streams for DynamoDB** (retenção maior, múltiplos consumidores).

```bash
aws dynamodb update-table --table-name Pedidos \
  --stream-specification StreamEnabled=true,StreamViewType=NEW_AND_OLD_IMAGES
aws lambda create-event-source-mapping --function-name processa-pedidos \
  --event-source-arn $STREAM_ARN --starting-position LATEST --batch-size 100
```

Atenção: garanta **idempotência** no consumidor (entrega pelo menos uma vez) e trate erros com DLQ/bisect.

## Segurança

### Criptografia

- **Em repouso:** sempre ativa (não pode ser desligada). Opções de chave: **AWS owned key** (padrão, sem custo), **AWS managed key** (`aws/dynamodb`) ou **CMK** do cliente no KMS. Veja [[8. DevOps e Gerenciamento de Infraestrutura/CLOUD COMPUTING/AWS (AMAZON WEB SERVICE)/2. Segurança e Conformidade/2.3 Capacidades de gerenciamento de acesso da AWS/2.3.2. Serviços de segurança/2.3.2.7. AWS Key Management Service (KMS)|AWS KMS]].
- **Em trânsito:** HTTPS/TLS (endpoints exigem).
- Criptografia **no cliente** (DynamoDB Encryption Client / AWS Database Encryption SDK) para campos sensíveis.

### IAM e controle de acesso

| Recurso | Uso |
|---|---|
| **Políticas de identidade** | Permissões por ação (`dynamodb:GetItem`, `Query`, `PutItem`...) e por recurso (tabela/índice) |
| **Fine-grained access control** | Condições `dynamodb:LeadingKeys` (restringir às chaves do usuário), `dynamodb:Attributes` |
| **Políticas de recurso** | Política anexada à tabela/stream (acesso entre contas) |
| **Roles** | Lambda, ECS, EC2 usando roles; evite chaves de acesso fixas |

```json
{
  "Effect": "Allow",
  "Action": ["dynamodb:GetItem", "dynamodb:Query", "dynamodb:PutItem"],
  "Resource": "arn:aws:dynamodb:sa-east-1:111122223333:table/Pedidos",
  "Condition": {
    "ForAllValues:StringEquals": {
      "dynamodb:LeadingKeys": ["${cognito-identity.amazonaws.com:sub}"]
    }
  }
}
```

Esse exemplo restringe cada usuário autenticado (Cognito) aos itens cuja partition key é o próprio ID.

### Rede

- **VPC gateway endpoint** para DynamoDB: tráfego privado, sem NAT nem internet; política do endpoint pode limitar tabelas/ações. Veja [[8. Amazon VPC/0 Amazon VPC (Tópicos )|Amazon VPC]].
- Interface endpoint (PrivateLink) para acesso a partir de on-premises (recurso mais recente; confirme).

### Proteção e auditoria

| Mecanismo | Função |
|---|---|
| **Deletion protection** | Impede exclusão acidental da tabela |
| **CloudTrail** | Chamadas de API de controle e (opcionalmente) de dados |
| **CloudWatch / Contributor Insights** | Métricas e chaves quentes |
| **AWS Config / Security Hub** | Regras como PITR habilitado, criptografia, deletion protection |
| **Tags + SCP/IAM** | Governança |

## Exemplo prático

Aplicação global de pedidos:

1. Tabela `Pedidos` on-demand, **PITR 35 dias**, **deletion protection**, criptografia com CMK.
2. **Global Table** em `sa-east-1` e `us-east-1`; cada usuário roteado à região mais próxima; failover por Route 53.
3. **Streams** (`NEW_AND_OLD_IMAGES`) → Lambda atualiza índice de busca (OpenSearch) e publica evento no EventBridge.
4. **Export diário para S3** + Athena para análises (sem consumir RCU).
5. Acesso via **VPC gateway endpoint**; roles de serviço com `LeadingKeys` por tenant.
6. **AWS Backup** para cópia mensal em conta de arquivamento, com retenção de 7 anos.
7. Teste trimestral: restauração PITR para tabela temporária e comparação de contagens.

## Erros comuns e armadilhas

- **Não habilitar PITR:** só descobre ao precisar voltar no tempo.
- **Achar que Global Tables é backup:** exclusões também são replicadas.
- **Escrever o mesmo item em várias regiões:** conflitos resolvidos por last-writer-wins (perda silenciosa).
- **Consumidor de Streams não idempotente.**
- **Esquecer que o stream retém apenas 24 horas.**
- **Restaurar e esquecer auto scaling, TTL, alarmes e tags** (não restaurados automaticamente).
- **Chave KMS desabilitada:** a tabela fica inacessível.
- **Políticas IAM `dynamodb:*` em `*`.**
- **Acesso via NAT/internet** quando um gateway endpoint resolveria.
- **Sem deletion protection** em tabelas críticas.

## 🧩 Quiz de Fixação

1. Qual a diferença entre backup sob demanda e PITR?
2. Global Tables substitui backup? Por quê?
3. Para que servem os DynamoDB Streams e qual a retenção?

**Respostas:**
1) O backup sob demanda é uma cópia completa de um instante, mantida até ser excluída; o PITR permite restaurar para qualquer segundo dentro da janela configurada (1 a 35 dias), criando uma nova tabela.
2) Não: a replicação propaga também exclusões e corrupções para as outras regiões; Global Tables dá disponibilidade e baixa latência, enquanto backup/PITR dá recuperação.
3) Registram as alterações dos itens em ordem para acionar Lambda, manter views, replicar e auditar; retêm os dados por 24 horas.
