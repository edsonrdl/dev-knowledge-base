### DynamoDB Streams a fundo — view types, Lambda event source mapping, filtros, tratamento de erros, Kinesis Data Streams for DynamoDB e EventBridge Pipes

> [!warning] Aviso
> Parâmetros do event source mapping (batch, janela, paralelismo), limites de shards, retenção e preços dos Streams, do Kinesis e do EventBridge Pipes mudam. Confirme na documentação. Os comandos, JSONs e códigos **não foram executados**.

Os **DynamoDB Streams** transformam a tabela em uma **fonte de eventos**: cada inserção, atualização ou exclusão gera um registro ordenado que outros serviços podem consumir. Isso viabiliza arquiteturas **orientadas a eventos**, **CDC (change data capture)**, **views materializadas**, **replicação**, **auditoria** e **integração com buscas e analytics**. Esta nota detalha como o stream funciona e como consumi-lo **com segurança e idempotência**.

**Analogia:** o stream é a **câmera de segurança do cofre** que registra cada alteração em ordem e guarda a gravação por 24 horas. Quem consome (Lambda, Kinesis, Pipes) é o **vigilante** que assiste e age; se ele piscar, pode rever o trecho — por isso, as ações do vigilante precisam ser **idempotentes**.

## O que o stream contém

| Propriedade | Detalhe |
|---|---|
| **Eventos** | `INSERT`, `MODIFY`, `REMOVE` |
| **Ordem** | **Garantida por item** (para uma mesma PK+SK, na ordem em que ocorreram); **não** há ordem global entre itens |
| **Retenção** | **24 horas** |
| **Entrega** | **Pelo menos uma vez** na leitura (o consumidor deve tolerar duplicatas) |
| **Sharding** | O stream é dividido em **shards** (gerenciados pelo DynamoDB), acompanhando as partições da tabela |
| **Latência** | Tipicamente menos de 1 segundo |
| **Custo** | Sem custo de habilitar; cobra-se pelas **unidades de leitura de stream** (as leituras feitas por Lambda a partir do DynamoDB Streams não são cobradas) |
| **Escritas de TTL** | Exclusões por TTL aparecem como `REMOVE` com `userIdentity.principalId = dynamodb.amazonaws.com` |

### StreamViewType

| Valor | Conteúdo do registro | Quando usar |
|---|---|---|
| `KEYS_ONLY` | Só as chaves do item | Consumidor relê o item (mais barato) |
| `NEW_IMAGE` | Item **depois** da mudança | Indexação, cópia, notificação |
| `OLD_IMAGE` | Item **antes** da mudança | Auditoria de exclusões |
| `NEW_AND_OLD_IMAGES` | Ambos | **Diff**, auditoria completa, detecção de mudanças |

O view type é escolhido ao habilitar e só pode ser mudado desabilitando e habilitando de novo (o que cria um stream novo).

Exemplo de registro (simplificado):

```json
{
  "eventID": "1b2c3d...",
  "eventName": "MODIFY",
  "eventSource": "aws:dynamodb",
  "dynamodb": {
    "ApproximateCreationDateTime": 1730900000,
    "Keys": { "ClienteId": {"S": "C#1001"}, "PedidoId": {"S": "P#2026-0001"} },
    "OldImage": { "status": {"S": "NOVO"}, "total": {"N": "150"} },
    "NewImage": { "status": {"S": "PAGO"}, "total": {"N": "150"} },
    "SequenceNumber": "1234567890",
    "SizeBytes": 160,
    "StreamViewType": "NEW_AND_OLD_IMAGES"
  }
}
```

## Consumindo com AWS Lambda (event source mapping)

O **event source mapping** (ESM) faz o *polling* dos shards e invoca a função com lotes de registros, em ordem, **um lote por shard por vez** (ou em paralelo se configurado).

```
 Stream: shard A ──► ESM ──► Lambda (lote de até N registros, na ordem do shard)
         shard B ──► ESM ──► Lambda
```

Parâmetros importantes:

| Parâmetro | Função | Dica |
|---|---|---|
| `BatchSize` | Máximo de registros por invocação (até 10.000) | Maior = menos invocações, mais tempo por execução |
| `MaximumBatchingWindowInSeconds` | Espera para completar o lote (0 a 300 s) | Aumenta eficiência; adiciona latência |
| `ParallelizationFactor` | Invocações simultâneas por shard (1 a 10) | Preserva ordem **por chave**, não global |
| `StartingPosition` | `LATEST` ou `TRIM_HORIZON` | `TRIM_HORIZON` reprocessa o histórico retido |
| `MaximumRetryAttempts` | Tentativas após erro (-1 = ilimitado até expirar) | Defina um limite para não travar o shard |
| `MaximumRecordAgeInSeconds` | Descarta registros mais velhos | Evita processar eventos obsoletos |
| `BisectBatchOnFunctionError` | Divide o lote em dois ao falhar, isolando o registro "veneno" | **Recomendado** |
| `FunctionResponseTypes = ReportBatchItemFailures` | A função informa **quais itens** falharam | Evita reprocessar o lote inteiro |
| `DestinationConfig.OnFailure` | Envia metadados do lote falho para **SQS/SNS/S3/Kafka** (DLQ) | Para análise e reprocessamento |
| `TumblingWindowInSeconds` | Agregação em janelas fixas | Cálculos por janela |
| `FilterCriteria` | Filtra eventos antes de invocar | Reduz custo e ruído |

> **Atenção:** se a função falha, o shard **fica bloqueado** no mesmo lote até sucesso, expiração do registro (24 h) ou descarte por `MaximumRetryAttempts`/`MaximumRecordAgeInSeconds`. Um "poison pill" sem tratamento pode atrasar toda a fila daquele shard.

### Filtros de evento

Em vez de invocar a Lambda para todos os registros, filtre por padrão (até alguns filtros por mapping):

```bash
aws lambda create-event-source-mapping \
  --function-name processa-pedidos \
  --event-source-arn $STREAM_ARN \
  --starting-position LATEST --batch-size 100 --maximum-batching-window-in-seconds 5 \
  --bisect-batch-on-function-error --maximum-retry-attempts 3 --maximum-record-age-in-seconds 3600 \
  --function-response-types ReportBatchItemFailures \
  --destination-config '{"OnFailure":{"Destination":"arn:aws:sqs:sa-east-1:111122223333:dlq-pedidos"}}' \
  --filter-criteria '{"Filters":[{"Pattern":"{\"eventName\":[\"INSERT\",\"MODIFY\"],\"dynamodb\":{\"NewImage\":{\"status\":{\"S\":[\"PAGO\"]}}}}"}]}'
```

Esse filtro só dispara a função para inserções/alterações cujo novo `status` seja `PAGO`. Registros filtrados **não são cobrados** como invocações (mas contam como lidos do shard).

### Exemplo de handler idempotente com falha parcial

```python
# Python (ilustrativo): processa lote e reporta somente os itens com falha
import json

def handler(event, context):
    falhas = []
    for r in event["Records"]:
        try:
            if r["eventName"] == "MODIFY":
                antes = r["dynamodb"].get("OldImage", {})
                depois = r["dynamodb"].get("NewImage", {})
                if antes.get("status") != depois.get("status"):
                    processar_mudanca_status(depois, chave_idempotencia=r["eventID"])
        except Exception:
            falhas.append({"itemIdentifier": r["dynamodb"]["SequenceNumber"]})
    return {"batchItemFailures": falhas}
```

`chave_idempotencia` deve ser registrada (por exemplo numa tabela de "processados" com `ConditionExpression attribute_not_exists`) para que o reprocessamento não duplique efeitos (e-mail enviado duas vezes, cobrança dupla).

## Kinesis Data Streams for DynamoDB

Alternativa que envia as mudanças para um **Kinesis Data Stream** que você controla.

| Critério | DynamoDB Streams | Kinesis Data Streams for DynamoDB |
|---|---|---|
| Retenção | 24 h | **24 h a 365 dias** |
| Consumidores | Poucos (limite por shard; recomendado ≤ 2 simultâneos) | **Muitos**, com **enhanced fan-out** |
| Ordem | Por item | Por chave de partição do Kinesis (ordem aproximada; podem ocorrer duplicatas e reordenações) |
| Integrações | Lambda, KCL adapter | Lambda, KCL, **Firehose** (S3/OpenSearch/Redshift), Flink/Managed Service for Apache Flink |
| Custo | Leituras de stream | Capacidade Kinesis + escritas replicadas |
| Controle | Gerenciado pelo DynamoDB | Você gerencia shards (provisionado ou on-demand) |
| Pode coexistir com DynamoDB Streams | Sim | Sim |

Quando escolher o Kinesis: **vários consumidores independentes**, **retenção longa**, **analytics em streaming** (Flink), **entrega para o S3 via Firehose** para um data lake.

```bash
aws dynamodb enable-kinesis-streaming-destination --table-name Pedidos \
  --stream-arn arn:aws:kinesis:sa-east-1:111122223333:stream/pedidos-cdc \
  --enable-kinesis-streaming-configuration ApproximateCreationDateTimePrecision=MICROSECOND
```

Cuidado: registros do Kinesis for DynamoDB podem chegar **duplicados e fora de ordem**; use `ApproximateCreationDateTime` e o conteúdo (versão do item) para resolver.

## EventBridge Pipes

O **EventBridge Pipes** conecta uma fonte (aqui, um DynamoDB Stream) a um destino com **filtro, enriquecimento e transformação**, sem escrever código de integração.

```
 DynamoDB Stream ──► [Filtro] ──► [Enriquecimento: Lambda/API/Step Functions] ──► [Transformação] ──► Destino
                                                                                  (EventBridge bus, SQS, SNS, Step Functions, Kinesis, API...)
```

| Benefício | Detalhe |
|---|---|
| **Menos código** | Filtro e mapeamento declarativos |
| **Fan-out** | Envia o evento ao **bus** do EventBridge, onde regras distribuem a vários consumidores |
| **Enriquecimento** | Consulta outra fonte antes de entregar |
| **Resiliência** | Retries, DLQ, controle de batch |

Use quando o destino é **EventBridge/SQS/SNS/Step Functions** e não há lógica complexa na função.

## Padrões de uso

| Padrão | Como funciona |
|---|---|
| **Outbox transacional** | A aplicação grava o dado de negócio **e** um item `OUTBOX#...` na **mesma transação**; o stream dispara a publicação (evita "gravei no banco mas não publiquei o evento") |
| **CDC para busca** | Stream → Lambda → indexa/atualiza no OpenSearch |
| **View materializada / agregados** | Stream → Lambda atualiza tabelas de resumo (ex.: total por cliente) com updates condicionais idempotentes |
| **Auditoria** | `NEW_AND_OLD_IMAGES` → Firehose → S3 (imutável) |
| **Replicação customizada** | Stream → Lambda → outra tabela/região/serviço |
| **Arquivar TTL** | Filtrar `REMOVE` com `principalId = dynamodb.amazonaws.com` e enviar o item removido ao S3 |
| **Notificações** | `MODIFY` com mudança de status → SNS/SES |
| **Invalidação de cache** | Stream → Lambda invalida chaves no ElastiCache |

Filtro para capturar apenas exclusões por TTL:

```json
{ "Filters": [ { "Pattern": "{\"userIdentity\":{\"type\":[\"Service\"],\"principalId\":[\"dynamodb.amazonaws.com\"]}}" } ] }
```

## Operação e monitoramento

| Métrica / sinal | Significado |
|---|---|
| `IteratorAge` (Lambda) | Atraso entre o registro e seu processamento; **alarme essencial** (cresce quando o consumidor não acompanha) |
| `Errors` / `Throttles` (Lambda) | Falhas e limitação do consumidor |
| `ReturnedRecordsCount`, `ReturnedBytes` (stream) | Volume lido |
| `UserErrors`, `SystemErrors` (DynamoDB) | Erros de API |
| DLQ (SQS) | Mensagens com metadados dos lotes que falharam |
| `ConcurrentExecutions` | Controle de concorrência; use `reserved concurrency` para proteger o downstream |

Boas práticas:

1. Funções **idempotentes** e rápidas; trabalho pesado vai para fila.
2. `BisectBatchOnFunctionError` + `ReportBatchItemFailures` + DLQ **sempre**.
3. Alarme em `IteratorAge`.
4. Não use Streams para enviar o **mesmo** evento a muitos consumidores: use EventBridge/SNS/Kinesis como distribuição.
5. Cuidado com **loops**: uma Lambda que escreve na mesma tabela dispara o stream de novo — use atributos de controle e filtros.
6. Dimensione o `ParallelizationFactor` conforme a ordem exigida.

## Exemplo prático

Fluxo "pedido pago → nota fiscal + e-mail + índice de busca":

1. A aplicação grava o pedido e, na **mesma transação**, o item `OUTBOX#pedido-123` com o evento.
2. Stream (`NEW_IMAGE`) → **EventBridge Pipe** com filtro `INSERT` de itens `OUTBOX#`, que publica no **bus** do EventBridge.
3. Regras do bus: (a) Lambda de nota fiscal; (b) SES para e-mail; (c) Lambda que indexa no OpenSearch.
4. Cada consumidor registra `eventID` processado (idempotência) e usa DLQ própria.
5. Em paralelo, **Kinesis for DynamoDB** → Firehose → S3 (Parquet) para o data lake, com retenção de 7 dias no stream.
6. Alarme: `IteratorAge` > 60 s e mensagens na DLQ > 0.

## Erros comuns e armadilhas

- **Lambda sem tratamento de poison pill:** o shard fica bloqueado até 24 h.
- **Consumidor não idempotente:** duplicatas geram efeitos repetidos.
- **Esperar ordem global:** só há ordem por item.
- **Ignorar o limite de 24 h de retenção:** consumidor parado por mais tempo perde eventos.
- **Muitos consumidores lendo o mesmo stream:** throttling de leitura (use Kinesis ou fan-out via EventBridge).
- **Loop infinito:** a Lambda atualiza o mesmo item e o stream a dispara de novo.
- **Habilitar `NEW_AND_OLD_IMAGES` por padrão** quando só as chaves bastam (maior volume de dados).
- **Filtro mal escrito** que descarta eventos necessários (teste com `test-event-pattern`).
- **Não monitorar `IteratorAge`.**
- **Confundir TTL deletes com deletes de usuário** ao arquivar.

## 🧩 Quiz de Fixação

1. Qual a garantia de ordem dos DynamoDB Streams e a de entrega?
2. Por que usar `BisectBatchOnFunctionError` e `ReportBatchItemFailures`?
3. Quando escolher Kinesis Data Streams for DynamoDB em vez do DynamoDB Streams?
4. Como o padrão outbox garante que um evento não se perde?

**Respostas:**
1) Ordem garantida por item (mesma chave), sem ordem global entre itens; a entrega é pelo menos uma vez, então o consumidor deve ser idempotente.
2) Para isolar registros que causam falha: o bisect divide o lote para achar o registro problemático e o relato de falhas por item evita reprocessar o lote inteiro, impedindo que um registro "veneno" bloqueie o shard.
3) Quando se precisa de retenção maior que 24 h (até 365 dias), muitos consumidores com enhanced fan-out ou integração com Firehose/Flink para analytics e data lake.
4) O dado de negócio e o item de outbox são gravados na mesma transação ACID; o stream então publica o evento a partir do outbox, de modo que ou ambos existem ou nenhum, sem a janela "gravei mas não publiquei".
