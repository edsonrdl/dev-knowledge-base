### Proteção e recuperação no DynamoDB — backups on-demand, PITR, AWS Backup, deletion protection, restauração e checklist de DR

> [!warning] Aviso
> Janelas de PITR, o que é (ou não) restaurado junto com a tabela, restauração entre regiões/contas, recursos do AWS Backup para DynamoDB e preços mudam. Confirme na documentação. Os comandos **não foram executados**.

Uma tabela do DynamoDB é replicada em três AZs, o que a protege contra **falhas de infraestrutura**. Isso **não** protege contra os dois riscos mais comuns em produção: **erro humano ou de aplicação** (um `DeleteItem` em massa, um `UpdateItem` errado, um `DeleteTable`) e **ataques ou corrupção lógica**. Para esses você precisa de **backups, PITR, cópias isoladas e um processo de restauração testado**. Esta nota organiza os mecanismos, o que é restaurado, os custos e um checklist de DR.

**Analogia:** a replicação em três AZs é o **extintor de incêndio do prédio**. Backups e PITR são o **seguro e o cofre fora do prédio**: servem quando alguém, por engano, joga fora o documento ou o arquivo inteiro. E de nada adianta o seguro se ninguém nunca testou como acioná-lo.

## Os mecanismos de proteção

| Mecanismo | Protege contra | Granularidade | RPO típico |
|---|---|---|---|
| Replicação em 3 AZs | Falha de hardware/AZ | — (automática) | 0 |
| **Backup on-demand** | Erro humano/lógico | Ponto fixo, quando você pede | Idade do backup |
| **PITR** | Erro humano/lógico | **Qualquer segundo** dos últimos 1-35 dias | ~segundos (até ~5 min atrás) |
| **AWS Backup** | Erro, ransomware, conformidade | Planos agendados, cópias entre regiões/contas, cofres imutáveis | Frequência do plano |
| **Global Tables** | Falha regional | Réplica ativa | < 1 s (não protege de erros) |
| **Export para S3** | Arquivo/analytics/arquivamento | Ponto no tempo (requer PITR) | Conforme agendamento |
| **Deletion protection** | `DeleteTable` acidental | Tabela inteira | — |
| **IAM / SCP** | Exclusões por quem não deve | Permissões | — |

## Backups on-demand

```
 Tabela (qualquer tamanho) ──create-backup──► backup completo, em segundos, sem impacto de desempenho
```

| Característica | Detalhe |
|---|---|
| **Impacto** | Nenhum: não consome capacidade nem afeta latência |
| **Tempo** | Conclui em minutos, independentemente do tamanho |
| **Retenção** | Até você excluir (sem expiração automática) |
| **Conteúdo** | Dados e índices, configuração de capacidade e criptografia |
| **Restauração** | Sempre para uma **nova** tabela |
| **Cópia** | Pode ser restaurado em **outra região** e (via AWS Backup) copiado para outra conta |
| **Custo** | Por GB-mês armazenado e por GB restaurado |

```bash
# Criar o backup
aws dynamodb create-backup --table-name Pedidos --backup-name pedidos-pre-release-2026-11-06
# Listar
aws dynamodb list-backups --table-name Pedidos \
  --query 'BackupSummaries[].{Nome:BackupName,Arn:BackupArn,Estado:BackupStatus,Tipo:BackupType,Bytes:BackupSizeBytes}'
# Restaurar para uma tabela nova (pode mudar modo de cobrança, GSIs, chave KMS)
aws dynamodb restore-table-from-backup --target-table-name Pedidos-restaurada --backup-arn $BACKUP_ARN \
  --billing-mode-override PAY_PER_REQUEST
```

Use para: antes de **releases** e migrações de esquema, antes de operações em massa e como pontos de retenção longa (junto ao AWS Backup).

## PITR (point-in-time recovery)

| Característica | Detalhe |
|---|---|
| **Janela** | Configurável de **1 a 35 dias** (`RecoveryPeriodInDays`) |
| **Resolução** | Restaura para qualquer **segundo** dentro da janela, até cerca de **5 minutos antes de agora** (`LatestRestorableDateTime`) |
| **Ativação** | **Desabilitado por padrão**; habilite por tabela |
| **Restauração** | Cria uma **nova tabela**; pode ser na mesma região ou em outra |
| **Custo** | Por GB da tabela e índices |
| **Impacto** | Nenhum no desempenho |
| **Requisito de export** | O export para S3 usa o PITR |

```bash
aws dynamodb update-continuous-backups --table-name Pedidos \
  --point-in-time-recovery-specification PointInTimeRecoveryEnabled=true,RecoveryPeriodInDays=35

aws dynamodb describe-continuous-backups --table-name Pedidos \
  --query 'ContinuousBackupsDescription.PointInTimeRecoveryDescription'
# Mostra EarliestRestorableDateTime e LatestRestorableDateTime

aws dynamodb restore-table-to-point-in-time \
  --source-table-name Pedidos --target-table-name Pedidos-pitr \
  --restore-date-time 2026-11-06T14:29:00Z
# ou --use-latest-restorable-time
```

**Se você apagar a tabela**, o PITR e os backups ligados a ela têm tratamento específico: ao excluir uma tabela com PITR habilitado, o DynamoDB pode criar um backup do sistema de segurança (verifique o comportamento atual e use `deletion protection` para não depender disso).

## O que é e o que não é restaurado

A restauração recria **dados e estrutura**, mas **não tudo**. Após restaurar, reconfigure:

| Restaurado | **Não** restaurado automaticamente (reconfigure) |
|---|---|
| Itens e atributos | **Auto scaling** policies |
| Chave primária, GSIs e LSIs (opcional ao restaurar) | Políticas **IAM** / resource policies |
| Modo de capacidade e valores provisionados | Alarmes e métricas do **CloudWatch** |
| Configurações de criptografia (pode trocar a chave) | **Tags** |
| | Configuração de **Streams** |
| | **TTL** |
| | Configuração de **PITR** (reabilite na tabela nova) |
| | Réplicas de **Global Tables** |
| | **Deletion protection** |

Isso deve estar no runbook: **IaC (CloudFormation/CDK/Terraform)** descreve esses itens e reduz o risco de esquecê-los.

## Recuperando um item ou conjunto de itens

Não há "restauração in-place". Para recuperar dados específicos:

```
 1. Restaurar o PITR para uma tabela temporária (instante anterior ao erro)
 2. Ler os itens corretos da tabela temporária
 3. Gravar os itens de volta na tabela de produção (script, Glue, Step Functions, Lambda)
 4. Validar, excluir a tabela temporária
```

Para desastre completo (tabela inteira corrompida), o plano é: restaurar para a tabela nova, **trocar a aplicação** (nome de tabela por parâmetro, Parameter Store/AppConfig) e, só depois, desativar a antiga. Nomes de tabela configuráveis tornam a troca rápida.

Tempo de restauração: **proporcional ao tamanho e ao número de partições**, tipicamente de minutos a horas para tabelas grandes — **meça no seu ambiente**.

## AWS Backup para DynamoDB

O AWS Backup centraliza políticas para DynamoDB e outros serviços. Com o recurso de "advanced DynamoDB backup" habilitado, ganha-se:

| Recurso | Benefício |
|---|---|
| **Cópia entre regiões e contas** | DR e proteção contra comprometimento da conta |
| **Cold storage e lifecycle** | Retenção longa a menor custo |
| **Cofres imutáveis (Vault Lock) e logicamente isolados** | Proteção contra ransomware e conformidade |
| **Planos por tags e políticas do Organizations** | Governança em escala |
| **Auditoria** | Backup Audit Manager |
| **Restore testing** | Prova periódica de restauração |

AWS Backup/0 AWS Backup (Tópicos )|AWS Backup]]. Tenha em mente: backups feitos pelo AWS Backup têm seu próprio ciclo e cobrança, e o PITR continua sendo configurado no DynamoDB.

## Proteção preventiva

| Medida | Como |
|---|---|
| **Deletion protection** | `aws dynamodb update-table --deletion-protection-enabled`; impede `DeleteTable` até desabilitar |
| **IAM de menor privilégio** | Aplicações **sem** `dynamodb:DeleteTable`, `DeleteBackup`, `UpdateContinuousBackups` |
| **SCP/permissions boundary** | Negar exclusão de tabelas/backups de produção a todos, exceto uma role de *break-glass* |
| **Condition keys** | Exigir MFA ou tag para ações destrutivas |
| **Condições nas escritas** | `attribute_exists`/`attribute_not_exists`/versão para evitar sobrescritas acidentais |
| **Soft delete** | Atributo `excluido_em` em vez de `DeleteItem`; TTL limpa depois |
| **Versionamento de itens** | Mantém histórico (nota de padrões avançados) |
| **Streams para trilha de auditoria** | Registro das mudanças em S3 imutável |
| **CloudTrail** | Auditoria de chamadas de controle (e opcionalmente de dados) |
| **Alarmes** | `DeleteTable`, `UpdateTable` e picos de `DeleteItem` no EventBridge |

```json
{
  "Effect": "Deny",
  "Action": ["dynamodb:DeleteTable", "dynamodb:DeleteBackup", "dynamodb:UpdateContinuousBackups"],
  "Resource": "arn:aws:dynamodb:*:111122223333:table/Pedidos*",
  "Condition": { "StringNotEquals": { "aws:PrincipalArn": "arn:aws:iam::111122223333:role/BreakGlassDBA" } }
}
```

## Custos

| Item | Observação |
|---|---|
| **PITR** | Por GB-mês da tabela (e índices) |
| **Backups on-demand** | Por GB-mês |
| **Restauração** | Por GB restaurado, mais a tabela nova |
| **Cópia entre regiões** | Transferência + armazenamento no destino |
| **Export para S3** | Por GB exportado |
| **AWS Backup** | Armazenamento warm/cold, cópias |
| **Tabela temporária de restauração** | Capacidade e armazenamento enquanto existir (apague depois) |

Dimensione a janela do PITR pela necessidade: 35 dias para dados críticos; 7 dias costuma bastar para dados menos sensíveis.

## Checklist de DR

- [ ] PITR habilitado nas tabelas críticas (janela definida) e **deletion protection** ligada.
- [ ] Backups on-demand antes de releases e plano do AWS Backup com **cópia em outra conta e região**.
- [ ] Cofre com Vault Lock para dados regulados.
- [ ] IAM/SCP impedindo exclusões fora do *break-glass*; CloudTrail e alarmes de ações destrutivas.
- [ ] **IaC** que recria auto scaling, IAM, alarmes, tags, Streams, TTL e réplicas após restaurar.
- [ ] Nome da tabela **parametrizado** na aplicação (troca rápida).
- [ ] Runbook com: como escolher o ponto no tempo, como restaurar, como validar, como trocar a aplicação, como limpar.
- [ ] **Teste de restauração trimestral** com o tempo medido (RTO real) e a contagem de itens validada.
- [ ] Definição de RPO/RTO por tabela e coerente com a estratégia (PITR, backup, Global Tables).
- [ ] Global Tables **não** consideradas como backup.

## Exemplo prático

Incidente: um deploy com bug executou `UpdateItem` zerando o campo `saldo` de 12 mil clientes às 14:32 UTC.

1. Descobrir o horário exato do erro (logs da aplicação, CloudTrail e Streams).
2. `restore-table-to-point-in-time` para `Contas-pitr` no instante `14:31:00Z`.
3. Script (Lambda/Glue) lê os saldos corretos de `Contas-pitr` apenas dos 12 mil `UsuarioId` afetados (lista vinda do stream/log) e regrava na tabela de produção com `ConditionExpression` de segurança.
4. Validação por amostragem e por soma de controle; liberar o tráfego novamente.
5. Excluir `Contas-pitr` e registrar o aprendizado; corrigir o deploy e adicionar teste.
6. Tempo total medido: 47 minutos — vira o RTO de referência para este tipo de incidente.

## Erros comuns e armadilhas

- **Considerar a replicação em 3 AZs e Global Tables como backup.**
- **Não habilitar PITR** (é desabilitado por padrão).
- **Esperar restauração in-place** ou que a tabela restaurada "volte" com o mesmo nome automaticamente.
- **Esquecer de reconfigurar** auto scaling, IAM, alarmes, TTL, Streams, tags e PITR na tabela restaurada.
- **Nunca testar a restauração** nem medir o tempo.
- **Restaurar sem decidir como trocar a aplicação** (nome de tabela fixo no código).
- **Apps com permissão de `DeleteTable`.**
- **Sem deletion protection em tabelas críticas.**
- **Deixar tabelas temporárias de restauração** ligadas (custo).
- **Cópia só na mesma conta e região**: um comprometimento da conta apaga tudo.

## 🧩 Quiz de Fixação

1. Por que a replicação em três AZs não substitui backup?
2. O que não é restaurado automaticamente junto com a tabela e como reduzir o risco de esquecer?
3. Como recuperar apenas alguns itens apagados por engano às 14:32?
4. Que controles preventivos reduzem o risco de exclusão acidental?

**Respostas:**
1) Porque protege contra falhas de hardware/AZ, mas replica também erros lógicos: um `DeleteItem` em massa ou um `DeleteTable` acontece em todas as réplicas; só backups e PITR permitem voltar no tempo.
2) Auto scaling, IAM, alarmes, tags, Streams, TTL, PITR, réplicas de Global Tables e deletion protection. Reduz-se o risco com infraestrutura como código e um runbook que reaplique essas configurações.
3) Restaurar o PITR para uma tabela temporária em um instante anterior ao erro (por exemplo 14:31), ler os itens corretos dela e regravá-los na tabela de produção, validar e apagar a tabela temporária.
4) Deletion protection, IAM/SCP sem `DeleteTable` e `DeleteBackup` para as aplicações (com role de break-glass), soft delete, escritas condicionais, CloudTrail com alarmes e backups com cópias isoladas.
