### Parameter groups, option groups e tuning de engines no RDS — parâmetros dinâmicos e estáticos, conexões, memória, logs e boas práticas

> [!warning] Aviso
> Nomes, valores padrão, fórmulas e parâmetros modificáveis variam por engine e versão e mudam com o tempo. Os valores abaixo são **pontos de partida**, não receitas. **Valide na documentação do engine e teste com a sua carga.** Os comandos **não foram executados**.

Como não há acesso aos arquivos de configuração (`my.cnf`, `postgresql.conf`, `init.ora`, `sp_configure`), **toda a configuração do engine no RDS é feita por parameter groups** (e, para recursos opcionais, **option groups**). Dominar os dois, mais o tuning básico de **conexões, memória, logs e autovacuum**, evita boa parte dos incidentes de desempenho.

**Analogia:** o parameter group é o **painel de controle do motor**: você ajusta botões (parâmetros) que a oficina (RDS) aplica ao carro. Alguns botões mudam na hora (dinâmicos); outros só valem depois de desligar e ligar o motor (estáticos). O option group é o **catálogo de acessórios opcionais** que você instala (auditoria, APEX, backup nativo).

## Parameter groups

### Conceitos

| Conceito | Descrição |
|---|---|
| **DB parameter group** | Conjunto de parâmetros do engine aplicados a uma **instância** |
| **DB cluster parameter group** | Parâmetros de nível de **cluster** (Aurora e Multi-AZ DB cluster); parte dos parâmetros fica no cluster, parte na instância |
| **Família (family)** | Tipo de engine/versão (`mysql8.0`, `postgres16`, `sqlserver-se-15.0`); o grupo só vale para sua família |
| **Grupo padrão (default.*)** | **Somente leitura**; crie um customizado para alterar |
| **Valores dinâmicos de fórmula** | Muitos padrões são fórmulas como `{DBInstanceClassMemory/12582880}`, que se ajustam à classe da instância |

### Tipos de aplicação

| Tipo | Efeito | Status na instância |
|---|---|---|
| **Dinâmico** | Aplica-se **imediatamente** (`ApplyMethod=immediate`) ou no próximo reinício | `in-sync` |
| **Estático** | Só vale após **reinício** (`pending-reboot`) | `pending-reboot` |

```
 modificar parâmetro estático → status "pending-reboot" → reinicia a instância → "in-sync"
```

Fluxo seguro de mudança:

1. Criar uma **cópia** do grupo atual (`copy-db-parameter-group`).
2. Alterar a cópia e **testar** em staging com carga.
3. Associar à instância de produção (`modify-db-instance --db-parameter-group-name`).
4. Planejar o **reinício** na janela de manutenção (se houver parâmetros estáticos).
5. Registrar a mudança (IaC) e manter o histórico.

```bash
aws rds create-db-parameter-group --db-parameter-group-name pg16-prod \
  --db-parameter-group-family postgres16 --description "Producao"

aws rds modify-db-parameter-group --db-parameter-group-name pg16-prod --parameters \
  "ParameterName=log_min_duration_statement,ParameterValue=500,ApplyMethod=immediate" \
  "ParameterName=shared_preload_libraries,ParameterValue='pg_stat_statements,pg_cron',ApplyMethod=pending-reboot"

aws rds describe-db-parameters --db-parameter-group-name pg16-prod \
  --query "Parameters[?Source=='user'].{Nome:ParameterName,Valor:ParameterValue,Aplicacao:ApplyType}"
# Source=='user' lista só o que você alterou em relação ao padrão

aws rds describe-db-instances --db-instance-identifier loja-prod \
  --query 'DBInstances[0].DBParameterGroups'     # mostra ParameterApplyStatus (in-sync / pending-reboot)
```

## Option groups

Habilitam **recursos opcionais** de alguns engines.

| Engine | Opções comuns |
|---|---|
| **MySQL / MariaDB** | `MARIADB_AUDIT_PLUGIN` (auditoria) |
| **Oracle** | `APEX`, `OEM`, `S3_INTEGRATION`, `SSL`, `NATIVE_NETWORK_ENCRYPTION`, `TDE`, `STATSPACK`, `XMLDB`, `JVM` |
| **SQL Server** | `SQLSERVER_BACKUP_RESTORE`, `SSRS`, `TDE`, `SQLSERVER_AUDIT` |
| **PostgreSQL** | Não usa option groups (extensões via `CREATE EXTENSION`) |

Cada opção pode ter **configurações** e **grupos de segurança** próprios (por exemplo, porta do OEM). O option group também é criado por família e associado à instância; algumas opções exigem reinício.

## Tuning de conexões

`max_connections` dimensiona memória por conexão. O padrão é fórmula da memória da classe.

| Engine | Fórmula padrão (referência) |
|---|---|
| MySQL | `max_connections = {DBInstanceClassMemory/12582880}` |
| PostgreSQL | `max_connections = LEAST({DBInstanceClassMemory/9531392}, 5000)` |
| SQL Server | Dinâmico (limite alto; controle por `user connections`) |
| Oracle | Parâmetro `processes` ligado à classe |

Boas práticas:

- Não "aumente por aumentar": cada conexão consome memória (PostgreSQL ~10 MB+ por backend) e gera troca de contexto.
- Use **pool de conexões** na aplicação e **RDS Proxy**/pgBouncer.
- Monitore `DatabaseConnections` vs o limite.
- Defina timeouts: `wait_timeout`/`interactive_timeout` (MySQL), `idle_in_transaction_session_timeout` e `statement_timeout` (PostgreSQL).

## Tuning de memória

| Engine | Parâmetros-chave | Orientação inicial |
|---|---|---|
| **MySQL (InnoDB)** | `innodb_buffer_pool_size` | Padrão do RDS ≈ **75% da memória**; é o maior ganho de desempenho |
| | `innodb_log_file_size`, `innodb_flush_log_at_trx_commit` | Durabilidade × desempenho: `1` é o mais seguro |
| **PostgreSQL** | `shared_buffers` | Padrão ≈ **25%** da memória; o SO usa o restante como cache |
| | `work_mem` | Por operação de ordenação/hash (multiplicado por consultas × nós); **aumente com cuidado** |
| | `maintenance_work_mem` | Vacuum, criação de índices |
| | `effective_cache_size` | Informa o planejador (≈ 50-75% da memória) |
| **SQL Server** | `max server memory` | Deixe margem para o SO |
| **Oracle** | `sga_target`/`pga_aggregate_target` | Ajuste conforme workload (RDS define padrões pela classe) |

Sinais de pouca memória: `FreeableMemory` baixo, uso de swap (`SwapUsage`), leituras de disco altas, `BufferCacheHitRatio`/cache hit abaixo de ~99% em OLTP.

## Logs e observabilidade via parâmetros

| Engine | Parâmetros úteis |
|---|---|
| **MySQL** | `slow_query_log=1`, `long_query_time=1`, `log_output=FILE`, `general_log` (cuidado: volume), `performance_schema=1` |
| **PostgreSQL** | `log_min_duration_statement=500` (ms), `log_connections`, `log_disconnections`, `log_lock_waits=1`, `log_temp_files`, `track_activity_query_size`, `pg_stat_statements` |
| **SQL Server** | Traces/Extended Events, SQL Server Error Log, Agent logs |
| **Oracle** | Alert log, listener log, trace files, AWR/ASH (licença Diagnostics Pack) |

Publique os logs no **CloudWatch Logs** (`--cloudwatch-logs-export-configuration`) para pesquisa e alarmes. Controle o volume (logar tudo custa armazenamento e I/O).

## PostgreSQL: autovacuum e manutenção

| Parâmetro | Função |
|---|---|
| `autovacuum` | Mantenha ligado |
| `autovacuum_vacuum_scale_factor` / `threshold` | Quando vacuum dispara (reduza em tabelas grandes e com muito UPDATE/DELETE) |
| `autovacuum_max_workers`, `autovacuum_naptime` | Capacidade do vacuum |
| `autovacuum_vacuum_cost_limit` | Ritmo do vacuum |
| `idle_in_transaction_session_timeout` | Evita transações abertas que bloqueiam o vacuum |

Monitorar *bloat*, `n_dead_tup`, `age(datfrozenxid)` e transações longas (`pg_stat_activity`). O alerta clássico: **wraparound de XID**.

## Parâmetros de segurança e conformidade

| Parâmetro | Efeito |
|---|---|
| `rds.force_ssl` (PostgreSQL/SQL Server) | Exige TLS |
| `require_secure_transport` (MySQL) | Exige TLS |
| `log_statement`, auditoria (pgAudit, MariaDB Audit, SQL Server Audit) | Trilha de auditoria |
| `password_encryption=scram-sha-256` (PostgreSQL) | Hash mais forte de senhas |
| `rds.accepted_password_auth_method` | Aceitar só SCRAM/IAM |

## Boas práticas de gestão de configuração

1. **Nunca** usar o grupo `default.*`; crie um customizado por engine/ambiente.
2. Versionar em **IaC** (CloudFormation/Terraform/CDK) e revisar em pull request.
3. **Uma mudança por vez**, com métrica antes/depois.
4. Documentar o motivo de cada parâmetro.
5. Em Multi-AZ/réplicas, lembrar que algumas réplicas têm parâmetros próprios (por exemplo `max_connections` da réplica deve ser ≥ ao da primária no PostgreSQL).
6. Comparar grupos entre ambientes (`describe-db-parameters` + diff).
7. Reavaliar parâmetros ao **mudar de classe de instância** (as fórmulas se ajustam, os valores fixos não).
8. Testar upgrade de versão: parâmetros podem ser renomeados, removidos ou ter novos padrões.

## Exemplo prático

PostgreSQL 16 em `db.r6g.xlarge` (32 GiB) com consultas lentas e picos de conexões:

1. Criar `pg16-prod` e aplicar:
   - `log_min_duration_statement = 500`, `log_lock_waits = 1`, `log_temp_files = 10240`.
   - `shared_preload_libraries = 'pg_stat_statements'` (reinício).
   - `idle_in_transaction_session_timeout = 60000`, `statement_timeout = 30000`.
   - `work_mem` de 4 MB para 16 MB, depois de checar `log_temp_files` e o número de conexões (evitar estouro de memória).
   - `autovacuum_vacuum_scale_factor = 0.05` para as tabelas grandes de pedidos (via `ALTER TABLE ... SET (...)`).
2. Habilitar exportação do log `postgresql` ao CloudWatch Logs.
3. Introduzir **RDS Proxy** para estabilizar as conexões.
4. Medir antes/depois: latência p95, `CPUUtilization`, `ReadIOPS`, `DatabaseConnections`, `FreeableMemory`.
5. Documentar a mudança no repositório de IaC.

## Erros comuns e armadilhas

- **Tentar editar o `default.*`** (somente leitura).
- **Alterar parâmetro estático** e esquecer de reiniciar (`pending-reboot` por semanas).
- **Aumentar `max_connections` ou `work_mem`** sem calcular a memória total.
- **Trocar a classe de instância** e manter valores fixos inadequados.
- **Habilitar `general_log` no MySQL** em produção (I/O e custo).
- **Misturar grupos de famílias diferentes** na atualização de versão.
- **Mudar vários parâmetros ao mesmo tempo** e não saber qual causou o efeito.
- **Não versionar a configuração** (drift entre ambientes).
- **Desligar autovacuum** para "ganhar desempenho".
- **Ignorar `idle in transaction`**: bloqueia vacuum e causa bloat.

## 🧩 Quiz de Fixação

1. Qual a diferença entre parâmetro dinâmico e estático?
2. Por que não se edita o `default.*` e qual o fluxo seguro para mudar configuração?
3. Para que servem os option groups e quais engines os usam?
4. Por que não basta aumentar `max_connections` para resolver falta de conexões?

**Respostas:**
1) Dinâmico aplica-se imediatamente (ou no próximo reinício, conforme a opção); estático só vale após reinício da instância, ficando em `pending-reboot` até lá.
2) O grupo padrão é somente leitura. O fluxo seguro: copiar o grupo, alterar a cópia, testar em staging, associar à instância, reiniciar na janela se houver estáticos e versionar a mudança em IaC.
3) Habilitam recursos opcionais do engine (auditoria no MySQL/MariaDB; APEX, TDE, S3 integration no Oracle; backup nativo, SSRS no SQL Server). PostgreSQL não usa option groups; usa extensões.
4) Cada conexão consome memória e CPU; aumentar o limite pode estourar a memória e piorar o desempenho. A solução é pool de conexões (aplicação, RDS Proxy ou pgBouncer) e timeouts adequados.
