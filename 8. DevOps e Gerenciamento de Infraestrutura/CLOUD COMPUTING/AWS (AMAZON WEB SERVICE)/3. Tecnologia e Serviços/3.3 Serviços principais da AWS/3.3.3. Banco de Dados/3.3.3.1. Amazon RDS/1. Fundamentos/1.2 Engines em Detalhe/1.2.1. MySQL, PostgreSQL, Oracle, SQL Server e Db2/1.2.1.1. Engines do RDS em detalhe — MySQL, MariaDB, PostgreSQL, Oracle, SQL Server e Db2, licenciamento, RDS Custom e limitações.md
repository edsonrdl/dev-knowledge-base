### Engines do RDS em detalhe — MySQL, MariaDB, PostgreSQL, Oracle, SQL Server e Db2, licenciamento, RDS Custom e limitações

> [!warning] Aviso
> Versões suportadas, edições, modelos de licença, recursos por engine, política de Extended Support e preços mudam com frequência. Os detalhes abaixo refletem a documentação conhecida na época da escrita. **Confirme na documentação de cada engine antes de decidir.** Os comandos **não foram executados**.

Na nota de fundamentos vimos que o RDS gerencia vários engines. Na prática, **cada engine tem particularidades** — o que o RDS permite ou proíbe, como funciona o licenciamento, quais recursos de comunidade estão disponíveis e onde estão as armadilhas de migração. Esta nota detalha os seis engines (MySQL, MariaDB, PostgreSQL, Oracle, SQL Server e Db2), a diferença entre **License Included** e **BYOL**, o **RDS Custom** e as **limitações comuns** de um serviço gerenciado.

**Analogia:** o RDS é uma **rede de apartamentos mobiliados** com seis plantas diferentes. Todos têm zeladoria, mas cada planta tem regras próprias: em alguns você pode trocar a fiação, em outros nem tocar no quadro de luz; em uns o aluguel já inclui a licença do móvel, em outros você traz o seu.

## Visão comparativa

| Engine | Origem / licença | Recursos de destaque no RDS | Limites típicos do serviço |
|---|---|---|---|
| **MySQL** | Open source (Oracle) | Réplicas de leitura, Multi-AZ (instância e cluster), parâmetros ampliados, plugins de auditoria | Sem `SUPER`; sem acesso ao SO; algumas engines de armazenamento restritas |
| **MariaDB** | Open source | Compatível com MySQL; recursos próprios (Audit plugin, Galera não) | Menos versões e recursos que MySQL/PostgreSQL no RDS |
| **PostgreSQL** | Open source | Extensões ricas (PostGIS, pg_stat_statements, pg_cron, pgvector, pglogical, etc.), replicação lógica | Sem `superuser` real (existe `rds_superuser`); extensões restritas à lista aprovada |
| **Oracle** | Comercial | Edições SE2/EE, Multi-AZ, réplicas (Active Data Guard), APEX, TDE, integração com S3 | Sem `SYSDBA`; sem acesso ao SO; recursos que dependem do SO limitados |
| **SQL Server** | Comercial (Microsoft) | Edições Express/Web/Standard/Enterprise, Multi-AZ (Always On/espelhamento), backup nativo via S3, SSRS/SSIS (opções) | Sem `sysadmin` real (existe `rdsadmin`); CLR/linked servers com restrições |
| **Db2** | Comercial (IBM) | Db2 LUW gerenciado, BYOL/licenciamento via Marketplace | Conjunto de recursos mais recente e menor |

Aurora (MySQL/PostgreSQL compatível) é um produto à parte com arquitetura própria; veja o tópico do Aurora.

## MySQL e MariaDB

| Tema | Detalhe |
|---|---|
| **Versões** | Séries principais mantidas (por exemplo 8.0 e 8.4 no MySQL; várias do MariaDB); versões antigas saem do suporte padrão e passam para **Extended Support** pago |
| **Storage engine** | **InnoDB** é o suportado e recomendado; MyISAM não oferece durabilidade/recuperação |
| **Replicação** | Binlog; réplicas de leitura (também entre regiões) e replicação de/para fora do RDS |
| **Multi-AZ** | Instância (standby) ou **cluster com 2 standbys legíveis** (MySQL e PostgreSQL) |
| **Plugins** | `MARIADB_AUDIT_PLUGIN` (auditoria) por option group; validação de senha |
| **Privilégios** | O usuário master tem a maioria dos privilégios, **sem `SUPER`/`FILE`** (use procedimentos `mysql.rds_*` para tarefas administrativas) |
| **Parâmetros** | `innodb_buffer_pool_size`, `max_connections`, `slow_query_log`, `binlog_format`, `performance_schema` |
| **Dicas** | Use `utf8mb4` e collations modernas; defina `time_zone`; cuidado com `sql_mode` ao migrar |

Procedimentos administrativos típicos:

```sql
CALL mysql.rds_kill(12345);                       -- encerra uma sessão
CALL mysql.rds_set_configuration('binlog retention hours', 24);  -- retém binlogs (para replicação/CDC)
CALL mysql.rds_show_configuration;
```

Diferenças do MariaDB: licença GPL pura, recursos próprios (por exemplo, motores adicionais e alguns otimizadores), mas ecossistema de réplicas/recursos menor no RDS.

## PostgreSQL

| Tema | Detalhe |
|---|---|
| **Extensões** | Lista oficial por versão: `postgis`, `pg_stat_statements`, `pg_trgm`, `pg_cron`, `pgcrypto`, `pgvector` (busca vetorial), `pglogical`, `aws_s3`, `aws_lambda`, entre outras. **Extensões fora da lista não podem ser instaladas** |
| **Papéis** | `rds_superuser` (privilégios altos, não é superuser real), `rds_iam` (autenticação IAM), `rds_replication` |
| **Replicação lógica** | `rds.logical_replication = 1` (estático) habilita publicações/assinaturas e CDC (DMS, Debezium) |
| **Autovacuum** | Habilitado e crítico; ajuste por tabela em cargas pesadas; monitorar *bloat* e `age(datfrozenxid)` |
| **Parâmetros** | `shared_buffers` (≈25% da memória por padrão), `work_mem`, `max_connections`, `log_min_duration_statement`, `shared_preload_libraries` (reinício) |
| **Integração com AWS** | `aws_s3` (importar/exportar para S3), `aws_lambda` (invocar funções) |
| **Upgrades** | Major version upgrade manual (`pg_upgrade` gerenciado), ou **Blue/Green** |
| **Babelfish** | Camada de compatibilidade com T-SQL no **Aurora** PostgreSQL (não no RDS PostgreSQL) |

Cuidados clássicos: **transações longas** impedem vacuum; excesso de conexões (use RDS Proxy ou pgBouncer); *wraparound* de XID.

```sql
CREATE EXTENSION IF NOT EXISTS pg_stat_statements;   -- precisa constar em shared_preload_libraries
SELECT query, calls, mean_exec_time FROM pg_stat_statements ORDER BY total_exec_time DESC LIMIT 10;
```

## Oracle Database

| Tema | Detalhe |
|---|---|
| **Edições** | **Standard Edition Two (SE2)** e **Enterprise Edition (EE)** |
| **Licenciamento** | **License Included** (SE2) ou **BYOL** (SE2 e EE, com licença própria); a escolha altera preço e disponibilidade |
| **Multi-AZ** | Replicação de armazenamento síncrona; réplicas de leitura (mounted/read-only, **Active Data Guard** exige licença) |
| **Option groups** | `APEX`, `OEM`, `S3_INTEGRATION`, `SSL`, `NATIVE_NETWORK_ENCRYPTION`, `TDE` (licença Advanced Security), `STATSPACK`, `JVM`, `XMLDB` |
| **Privilégios** | Sem `SYSDBA`; pacote `rdsadmin` para tarefas administrativas (por exemplo `rdsadmin.rdsadmin_util.*`) |
| **Importação** | **Data Pump** com `DBMS_FILE_TRANSFER` ou integração com S3; export/import por link de banco |
| **Arquitetura** | Single-tenant CDB (multitenant com um PDB) nas versões atuais |
| **Limitações** | Sem acesso ao SO; sem RAC; sem Data Guard gerenciado diretamente (use réplicas); customizações profundas pedem **RDS Custom** |

```sql
-- Exemplo de tarefa administrativa (ilustrativa)
EXEC rdsadmin.rdsadmin_util.grant_sys_object('DBA_USERS','APP_USER','SELECT');
SELECT * FROM TABLE(rdsadmin.rds_file_util.listdir('DATA_PUMP_DIR'));
```

Licenças Oracle são complexas e variam por vCPU/edição: **valide com o time de licenciamento**. Para muitas cargas, migrar de Oracle para PostgreSQL (Aurora/RDS) reduz custo, usando SCT/DMS.

## Microsoft SQL Server

| Tema | Detalhe |
|---|---|
| **Edições** | Express, Web, Standard e Enterprise (por região/versão) |
| **Licenciamento** | **License Included** no preço da instância (também BYOL via License Mobility ou Dedicated Hosts, em cenários específicos) |
| **Multi-AZ** | **Always On Availability Groups** (Enterprise) ou **espelhamento de banco** (Standard) |
| **Backup/restore nativo** | Option group `SQLSERVER_BACKUP_RESTORE` + S3: restaurar arquivos `.bak` via procedimentos `rdsadmin.dbo.rds_restore_database` |
| **SQL Server Agent** | Disponível para jobs |
| **Recursos adicionais** | SSRS, SSIS e SSAS via option groups (conforme versão), TDE, integração com Active Directory (Kerberos), Always On leitura |
| **Limitações** | Sem `sysadmin`; filestream/CLR/linked servers com restrições; limites no número de bancos por instância (dezenas, conforme classe/versão); **sem acesso ao SO** |
| **Collation e timezone** | Definidos na criação da instância; difíceis de mudar |

```sql
-- Restaurar um backup nativo guardado no S3 (ilustrativo)
EXEC msdb.dbo.rds_restore_database
  @restore_db_name='MinhaBase',
  @s3_arn_to_restore_from='arn:aws:s3:::meu-bucket/backups/MinhaBase.bak';
EXEC msdb.dbo.rds_task_status @db_name='MinhaBase';
```

Cuidados: custo de licença em edições Enterprise; *collation* errada na criação; *tempdb* dimensionado conforme a classe.

## Db2

Disponibiliza o **Db2 for LUW** gerenciado. Licenciamento via **BYOL** ou **AWS Marketplace**, com Standard/Advanced Edition. Recursos incluem Multi-AZ, réplicas de leitura, backups, criptografia e integração com IAM/Secrets Manager. Por ser o engine mais recente no RDS, o conjunto de recursos e a maturidade da documentação são menores; confirme suporte a funções específicas antes de migrar.

## Licenciamento: License Included × BYOL

| Modelo | O que significa | Quando considerar |
|---|---|---|
| **License Included** | A licença do software está **embutida** no preço por hora da instância | Sem licença própria; cargas variáveis; simplicidade |
| **BYOL** (Bring Your Own License) | Você usa licença que já possui (Oracle, Db2; SQL Server em cenários específicos) | Já tem licenças com direito de mobilidade; custo menor por hora |
| **Marketplace** | Licença paga via AWS Marketplace (Db2) | Sem licença própria no engine |

Regras práticas: **engines open source (MySQL, MariaDB, PostgreSQL)** não têm licença a pagar; **Oracle e SQL Server** podem representar a maior parte do custo; avalie **substituir** por engine aberto quando o legado permitir.

## RDS Custom e opções especiais

| Opção | Para quê |
|---|---|
| **RDS Custom for Oracle / SQL Server** | Precisa de **acesso ao SO e ao banco** (instalar agentes, patches específicos, customizações de terceiros) mantendo automação de backup, monitoramento e Multi-AZ do RDS. Você assume mais responsabilidade (perímetro de suporte) |
| **RDS on Outposts** | Banco rodando em **Outposts** nas instalações do cliente |
| **Multi-AZ DB cluster** (MySQL/PostgreSQL) | Primária + 2 standbys legíveis, failover mais rápido |
| **Blue/Green deployments** | Upgrades e mudanças com baixo downtime |

RDS Custom exige cuidado: se você alterar algo fora do "perímetro de suporte", a automação pode ficar **pausada** até o ambiente voltar ao estado suportado.

## Extended Support e ciclo de vida de versões

Cada versão de engine tem um fim de **suporte padrão**. Depois dele:

- A AWS pode **atualizar à força** (manutenção) ou cobrar **Extended Support** (por vCPU-hora) para MySQL e PostgreSQL antigos, por tempo limitado.
- Planeje upgrades: ler as notas de versão, testar em clone, usar Blue/Green.
- Monitorar o calendário de fim de suporte no console/e-mails/AWS Health.

## Limitações comuns do serviço gerenciado

| Limitação | Consequência |
|---|---|
| **Sem acesso ao SO** (exceto RDS Custom) | Sem agentes de terceiros, sem scripts locais |
| **Sem superusuário completo** | Algumas extensões/comandos exigem procedimentos `rds_*` |
| **Extensões/plugins restritos** | Somente os homologados |
| **Parâmetros restritos** | Alguns não são modificáveis |
| **Manutenção** | Janelas e reinícios gerenciados |
| **Upgrades** | Limitados às versões suportadas |
| **Armazenamento** | Só aumenta; limite máximo por engine |
| **Rede** | Dentro da VPC; sem IP fixo estável (use DNS) |

## Como escolher o engine

```
Aplicação nova, sem restrição?                         → PostgreSQL (ecossistema) ou MySQL
Precisa de extensões geoespaciais/vetor/JSON avançado? → PostgreSQL
Aplicação legada Oracle com PL/SQL pesado?             → Oracle (BYOL) ou migrar para PostgreSQL (SCT/DMS)
Aplicação .NET / SQL Server com T-SQL e SSRS?          → SQL Server
Já usa MariaDB ou recursos específicos?                → MariaDB
Alta escala/disponibilidade em MySQL/PG?               → considerar Aurora
Precisa de acesso ao SO em Oracle/SQL Server?          → RDS Custom
```

## Exemplo prático

Decisão de engine para um ERP legado em Oracle 19c (SE2) com 800 GB:

1. Levantamento: uso de PL/SQL, DB links, jobs, APEX, recursos EE? Se só SE2, o RDS Oracle **SE2 BYOL** resolve rápido.
2. Cenário A (manter): RDS Oracle SE2 Multi-AZ BYOL, `db.r6i.2xlarge`, option groups APEX e S3_INTEGRATION; migração por Data Pump.
3. Cenário B (modernizar): converter para PostgreSQL com **DMS Schema Conversion/SCT**, medindo a porcentagem de código convertido automaticamente; piloto com um módulo.
4. Comparar TCO de 3 anos incluindo licenças, DBA e esforço de migração.
5. Decisão por módulo: financeiro mantém Oracle; módulos novos nascem em PostgreSQL.

## Erros comuns e armadilhas

- **Assumir acesso total** (SYSDBA, SUPER, sysadmin, SO) e descobrir a restrição na migração.
- **Extensão PostgreSQL ou plugin indisponível** só descoberto no cutover.
- **Collation/time zone/character set errados** na criação (difíceis de alterar).
- **Ignorar o custo de licença** (Oracle EE, SQL Server Enterprise).
- **Confundir License Included com BYOL** e contratar o modelo errado.
- **Manter versão antiga** até cair em Extended Support (custo extra) ou upgrade forçado.
- **Usar MyISAM** no MySQL.
- **Esperar paridade de recursos** entre RDS e o on-premises.
- **Usar RDS Custom sem entender o perímetro de suporte.**
- **Não validar `max_connections` e parâmetros** do engine escolhido.

## 🧩 Quiz de Fixação

1. Qual a principal limitação de privilégios do RDS e como se executam tarefas administrativas?
2. Qual a diferença entre License Included e BYOL?
3. Quando considerar o RDS Custom?
4. Por que verificar a lista de extensões antes de migrar para o RDS PostgreSQL?

**Respostas:**
1) Não há acesso ao SO nem a superusuários completos (SUPER, superuser, SYSDBA, sysadmin); as tarefas são feitas por procedimentos e papéis do RDS (`mysql.rds_*`, `rds_superuser`, `rdsadmin`).
2) License Included embute a licença no preço por hora da instância; BYOL usa licença que o cliente já possui (Oracle, Db2, SQL Server em cenários específicos), com custo horário menor.
3) Quando se precisa de acesso ao SO e ao banco (agentes de terceiros, customizações) em Oracle ou SQL Server, mantendo parte da automação do RDS, aceitando mais responsabilidade operacional.
4) Porque só as extensões homologadas por versão podem ser instaladas; se a aplicação depende de uma extensão fora da lista, a migração para o RDS fica bloqueada ou exige alternativa (Aurora, EC2).
