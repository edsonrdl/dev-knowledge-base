### O que é Amazon RDS — engines, classes de instância, armazenamento, subnet groups e parameter groups

> [!warning] Aviso
> Versões de engines, classes de instância, tipos de armazenamento, limites e preços do RDS mudam constantemente. Confirme na documentação. Os comandos **não foram executados**.

O **Amazon Relational Database Service (RDS)** é um serviço de **banco de dados relacional gerenciado**: a AWS cuida de provisionamento, instalação, patches, backups, failover e monitoramento básico, e você cuida do **esquema, dos dados, das consultas e do desempenho da aplicação**. Você não tem acesso ao sistema operacional da instância (exceto no RDS Custom).

**Analogia:** é **alugar um apartamento mobiliado e com zeladoria**: a estrutura, a manutenção predial e a segurança de portaria são da administradora (AWS); você decide a decoração (esquemas, índices) e o que guardar dentro, mas não pode derrubar paredes (sem acesso ao SO nem ao `superuser` completo).

```
   Aplicação ──(endpoint DNS)──► INSTÂNCIA RDS (engine + classe + storage EBS)
                                      │  em subnets de um DB subnet group, protegida por Security Group
                                      └─ backups automáticos, patches, Multi-AZ opcional
```

---

## O que o RDS gerencia × o que é seu

| A AWS gerencia | Você gerencia |
|---|---|
| Hardware, SO, instalação e patches do engine | Modelagem, índices, consultas, esquemas |
| Backups automáticos, snapshots, PITR | Política de retenção, testes de restauração |
| Failover Multi-AZ | Escolha de Multi-AZ, tolerância a reconexão |
| Monitoramento básico, métricas | Alarmes, tuning de consultas |
| Replicação (read replicas) | Uso de réplicas e arquitetura da aplicação |
| Criptografia, integração IAM/KMS | Quem acessa, rotação de credenciais |

## Engines suportados

| Engine | Licenciamento | Observações |
|---|---|---|
| **MySQL** | Open source | Muito comum; compatível com MySQL Community |
| **PostgreSQL** | Open source | Extensões populares (PostGIS, pgvector etc., conforme versão) |
| **MariaDB** | Open source | Fork do MySQL |
| **Oracle Database** | License Included ou BYOL | Edições Standard/Enterprise; recursos específicos |
| **Microsoft SQL Server** | License Included (BYOL em alguns casos) | Edições Express/Web/Standard/Enterprise |
| **Db2** | BYOL/License Included | Suporte mais recente |
| **Amazon Aurora** | Gerenciado pela AWS | Engine próprio compatível com MySQL/PostgreSQL; tem nota própria |

Versões e edições suportadas mudam; veja a lista oficial. Aurora é um produto à parte (arquitetura distribuída), tratado em outro tópico desta trilha.

| Variante | Quando |

## Classes de instância

| Família | Perfil | Exemplos |
|---|---|---|
| **Standard (db.m)** | Uso geral (CPU/memória equilibrados) | `db.m6g.large` |
| **Memory Optimized (db.r, db.x, db.z)** | Muita memória por vCPU: caches de banco, OLTP grande | `db.r6g.xlarge` |
| **Burstable (db.t)** | CPU "creditada", barato: dev/test, cargas leves | `db.t4g.medium` |

Sufixo `g` indica processadores **Graviton** (ARM), costumam ter melhor custo-benefício quando o engine suporta. A classe define vCPU, memória, banda de rede e o limite de EBS.

Dica: bancos são normalmente limitados por **memória e I/O**; comece por Memory Optimized em produção e use `t` apenas em ambientes não críticos (créditos esgotam).

## Armazenamento

O RDS usa volumes baseados em **EBS** (gerenciados para você):

| Tipo | Característica | Uso |
|---|---|---|
| **General Purpose SSD (gp3 / gp2)** | IOPS base com possibilidade de provisionar mais (gp3) | Maioria das cargas |
| **Provisioned IOPS SSD (io1/io2)** | IOPS provisionados e consistentes | OLTP crítico, latência estável |
| **Magnético (legado)** | Baixo custo/desempenho | Evitar |

Recursos:

- **Storage autoscaling:** o RDS aumenta o armazenamento automaticamente até um limite máximo definido por você.
- Aumentar armazenamento é possível; **reduzir não**. Há um período mínimo entre modificações.
- **Tamanho máximo** depende do engine (dezenas de TiB).
- Para o conceito de IOPS/throughput, veja a nota de tipos de volume do [[8. DevOps e Gerenciamento de Infraestrutura/CLOUD COMPUTING/AWS (AMAZON WEB SERVICE)/3. Tecnologia e Serviços/3.3 Serviços principais da AWS/3.3.2. Armazenamento/3.3.2.2. Amazon EBS/0 Amazon EBS (Tópicos )|Amazon EBS]].

## Estrutura de rede e configuração

### DB subnet group

Conjunto de **subnets em pelo menos duas AZs** da VPC onde o RDS pode criar instâncias (e o standby do Multi-AZ). Em geral, subnets **privadas**, sem acesso direto da internet. Veja [[8. DevOps e Gerenciamento de Infraestrutura/CLOUD COMPUTING/AWS (AMAZON WEB SERVICE)/3. Tecnologia e Serviços/3.3 Serviços principais da AWS/3.3.4. Rede/3.3.4.1. Amazon VPC/0 Amazon VPC (Tópicos )|Amazon VPC]].

### Endpoint

Cada instância tem um **endpoint DNS** (`meubanco.abc123.sa-east-1.rds.amazonaws.com:5432`). Use **sempre o nome DNS**, nunca o IP, pois o failover muda o destino.

### Parameter group

Conjunto de **parâmetros do engine** (equivalente ao `my.cnf`/`postgresql.conf`): `max_connections`, `innodb_buffer_pool_size`, `shared_buffers`, timeouts etc.

- O grupo **padrão** não é editável; crie um **customizado** e associe à instância.
- Parâmetros **dinâmicos** aplicam-se imediatamente; **estáticos** exigem **reinício**.

### Option group

Recursos opcionais de alguns engines (MySQL: auditoria; Oracle: APEX, TDE; SQL Server: backup/restore nativo).

### Security group

Libera a porta do banco (3306, 5432, 1433...) **apenas a partir** do Security Group da aplicação.

## Exemplo prático

```bash
# 1) DB subnet group com subnets privadas de duas AZs
aws rds create-db-subnet-group --db-subnet-group-name sg-bd-prod \
  --db-subnet-group-description "Subnets privadas do banco" \
  --subnet-ids subnet-0aaa111 subnet-0bbb222

# 2) Parameter group customizado para PostgreSQL 16 (ajuste conforme sua versão)
aws rds create-db-parameter-group --db-parameter-group-name pg16-prod \
  --db-parameter-group-family postgres16 --description "Parametros de producao"
aws rds modify-db-parameter-group --db-parameter-group-name pg16-prod \
  --parameters "ParameterName=log_min_duration_statement,ParameterValue=500,ApplyMethod=immediate"

# 3) Criar a instância (Multi-AZ, gp3, criptografada, sem acesso público)
aws rds create-db-instance \
  --db-instance-identifier loja-prod \
  --engine postgres --engine-version 16.4 \
  --db-instance-class db.r6g.large \
  --allocated-storage 200 --storage-type gp3 --max-allocated-storage 1000 \
  --master-username adminloja --manage-master-user-password \
  --db-subnet-group-name sg-bd-prod --vpc-security-group-ids sg-0bd123 \
  --db-parameter-group-name pg16-prod \
  --multi-az --storage-encrypted --no-publicly-accessible \
  --backup-retention-period 14 --deletion-protection
# --manage-master-user-password: a senha é gerada e guardada no Secrets Manager
# --max-allocated-storage: teto do autoscaling de armazenamento

# 4) Consultar o endpoint e o estado
aws rds describe-db-instances --db-instance-identifier loja-prod \
  --query 'DBInstances[0].{Estado:DBInstanceStatus,Endpoint:Endpoint.Address,Porta:Endpoint.Port,Classe:DBInstanceClass}'
```

Explicação: o exemplo reúne boas práticas — subnets privadas, criptografia, senha gerenciada, retenção de backup, proteção contra exclusão, Multi-AZ. A versão `16.4` é ilustrativa; consulte as suportadas.

## Quando RDS e quando não

| Situação | Recomendação |
|---|---|
| Aplicação relacional padrão, sem necessidade de acesso ao SO | **RDS** |
| Alta escala/disponibilidade e desempenho superior em MySQL/PostgreSQL | **Aurora** |
| Chave-valor com escala massiva e latência de milissegundos | **DynamoDB** |
| Customização profunda do SO/banco | **EC2** com banco próprio ou **RDS Custom** |
| Análise de grandes volumes (OLAP) | **Redshift** |
| Documentos JSON compatíveis com MongoDB | **DocumentDB** |

## Erros comuns e armadilhas

- **Banco com `PubliclyAccessible=true` e SG aberto:** exposição na internet.
- **Conectar pelo IP em vez do endpoint DNS:** quebra no failover.
- **Usar `db.t` em produção:** créditos de CPU acabam e o desempenho cai.
- **Parameter group padrão:** impossível ajustar; crie um customizado desde o início.
- **Esquecer o reinício** para parâmetros estáticos.
- **Subnet group com subnets de uma única AZ:** não permite Multi-AZ.
- **Sem proteção contra exclusão** e sem snapshot final.
- **Subdimensionar IOPS** e culpar o engine.
- **Achar que RDS dispensa tuning:** índices e consultas continuam sendo seus.

## 🧩 Quiz de Fixação

1. O que a AWS gerencia no RDS e o que continua sendo responsabilidade sua?
2. Por que usar sempre o endpoint DNS e não o IP?
3. Qual a função do parameter group e por que não editar o padrão?

**Respostas:**
1) A AWS gerencia hardware, SO, instalação/patches do engine, backups, failover e monitoramento básico; você gerencia esquema, índices, consultas, acesso, retenção e testes de restauração.
2) Porque, em um failover ou troca de instância, o IP muda; o DNS aponta para o novo primário.
3) Ele define os parâmetros do engine (como `max_connections` ou `shared_buffers`). O grupo padrão é somente leitura; é necessário criar um customizado para ajustar valores.
