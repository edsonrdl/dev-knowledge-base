### Migração para o RDS — DMS e SCT, dump e restore, replicação nativa, backup nativo do SQL Server e estratégias de cutover

> [!warning] Aviso
> Ferramentas (DMS, Schema Conversion, SCT), versões suportadas, limites e procedimentos mudam. Os passos abaixo são **roteiros ilustrativos**, não testados. **Valide na documentação de cada engine e faça um ensaio completo antes da virada.** Os comandos **não foram executados**.

Migrar um banco para o RDS é um projeto de **dados + esquema + aplicação + rede + corte**. A escolha da técnica depende de dois eixos: **o quanto de indisponibilidade o negócio tolera** e **se origem e destino são o mesmo engine** (migração homogênea) ou engines diferentes (heterogênea). Esta nota apresenta as técnicas, quando usar cada uma e um roteiro de cutover com validação e plano de retorno.

**Analogia:** é uma **mudança de casa**. Dá para encaixotar tudo num fim de semana (dump e restore, com a casa parada), ou ir levando as caixas aos poucos enquanto se mora na casa antiga e só trocar as chaves no final (replicação contínua com virada curta).

## Mapa de decisão

```
 Quanto downtime é aceitável?
   ├─ Horas (janela longa)  → dump/restore ou backup nativo (simples, previsível)
   └─ Minutos               → replicação contínua (CDC): DMS, replicação nativa, logical replication
 Os engines são iguais?
   ├─ Sim → ferramentas nativas costumam ser as melhores (pg_dump, mysqldump, backup nativo)
   └─ Não → SCT / DMS Schema Conversion (esquema) + DMS (dados)
 Origem é RDS/Aurora?
   └─ Sim → read replica + promoção, snapshot, Blue/Green
```

| Técnica | Downtime | Heterogênea? | Complexidade |
|---|---|---|---|
| **Dump e restore lógico** | Alto (proporcional ao volume) | Não | Baixa |
| **Backup físico/nativo** (SQL Server `.bak`, Percona XtraBackup para MySQL, Oracle Data Pump/RMAN conforme caso) | Médio | Não | Baixa a média |
| **Replicação nativa** (binlog MySQL, logical replication PostgreSQL) | **Mínimo** | Não | Média |
| **AWS DMS (full load + CDC)** | **Mínimo** | **Sim** | Média |
| **SCT / DMS Schema Conversion + DMS** | Mínimo (dados) | **Sim** | Alta (conversão de código) |
| **Réplica do RDS → Aurora / snapshot** | Mínimo | Mesmo engine | Baixa |

## AWS DMS (Database Migration Service)

Serviço gerenciado para **migrar dados** entre bancos, com **carga completa** e **captura contínua de mudanças (CDC)**.

```
 Origem (on-prem / EC2 / RDS) ──► [ Instância de replicação DMS ] ──► Destino (RDS / Aurora / S3 ...)
        1. full load (tabelas)                  2. CDC (aplica mudanças do log) até o cutover
```

| Componente | Função |
|---|---|
| **Replication instance** | Servidor gerenciado que executa a tarefa (dimensione CPU/memória/rede) |
| **Source / target endpoints** | Conexões com origem e destino |
| **Task** | Define o tipo (`full-load`, `cdc`, `full-load-and-cdc`), mapeamentos e transformações |
| **Table mappings** | Seleção e regras de transformação de esquemas/tabelas/colunas |
| **Validation** | Compara linhas entre origem e destino (data validation) |
| **DMS Serverless** | Capacidade escalada automaticamente (recurso mais recente) |

Pré-requisitos da origem para CDC:

| Origem | Requisito |
|---|---|
| MySQL/MariaDB | `binlog_format=ROW`, binlog habilitado e retido |
| PostgreSQL | `wal_level=logical` (`rds.logical_replication=1` no RDS), slots |
| Oracle | Supplemental logging, LogMiner/Binary Reader |
| SQL Server | CDC ou replicação transacional habilitados |

```bash
# Criar uma tarefa full-load + CDC (resumo; os mapeamentos ficam em JSON)
aws dms create-replication-task --replication-task-identifier ped-migra \
  --source-endpoint-arn $SRC --target-endpoint-arn $TGT --replication-instance-arn $RI \
  --migration-type full-load-and-cdc \
  --table-mappings file://mapeamento.json --replication-task-settings file://settings.json
aws dms start-replication-task --replication-task-arn $TASK --start-replication-task-type start-replication
aws dms describe-replication-tasks --query 'ReplicationTasks[].{Tarefa:ReplicationTaskIdentifier,Estado:Status,Progresso:ReplicationTaskStats}'
```

Limites do DMS: **não migra esquema completo** (índices secundários, procedures, triggers, funções) — use o SCT/Schema Conversion ou ferramentas nativas para o esquema; LOBs exigem configuração; sequências e valores `auto_increment` precisam ser ajustados no cutover; DDL durante CDC tem suporte limitado.

## Conversão de esquema (heterogênea)

| Ferramenta | Função |
|---|---|
| **AWS SCT** (desktop) | Avalia e converte esquema e código (Oracle/SQL Server → PostgreSQL/MySQL/Aurora), gera relatório de **complexidade** e itens manuais |
| **DMS Schema Conversion** | Versão gerenciada no console, com avaliação e conversão |
| **Babelfish for Aurora PostgreSQL** | Aceita conexões e T-SQL do SQL Server em Aurora PostgreSQL, reduzindo mudanças na aplicação |

Fluxo: **avaliar** (relatório de aderência) → **converter** esquema → **tratar manualmente** o que não converteu (procedures complexas, tipos, funções) → **carregar dados** com DMS → **testar a aplicação**. O custo real está em **código de banco e queries** da aplicação.

## Migração homogênea: ferramentas nativas

### MySQL / MariaDB

| Opção | Como |
|---|---|
| `mysqldump` / `mydumper` | Dump lógico → restore no RDS; use `--single-transaction`, `--routines`, `--triggers` |
| **Percona XtraBackup para S3** | Backup físico enviado ao S3 e restaurado como nova instância RDS MySQL (mais rápido para bases grandes) |
| **Replicação binlog** | Configurar o RDS como réplica de uma origem externa (`mysql.rds_set_external_master` / procedimento equivalente) e promover no cutover |

### PostgreSQL

| Opção | Como |
|---|---|
| `pg_dump`/`pg_restore` | Dump lógico em formato custom/directory; `-j` para paralelismo |
| **Logical replication** (publicações/assinaturas) ou `pglogical` | Replica tabelas continuamente da origem para o RDS; requer `wal_level=logical` na origem; sequências precisam ser sincronizadas manualmente |
| **Snapshot/PITR de outro RDS** | Restaurar diretamente |
| `aws_s3` | Importar CSV do S3 com `aws_s3.table_import_from_s3` |

### SQL Server

| Opção | Como |
|---|---|
| **Backup/restore nativo** | `.bak` no S3 + option group `SQLSERVER_BACKUP_RESTORE` + procedimentos `rds_restore_database` (full + diferenciais + logs com `NORECOVERY` para reduzir o downtime) |
| **Replicação transacional / log shipping** | Mantém o destino atualizado até o cutover |
| **DMS** | Para casos heterogêneos ou tabelas específicas |

### Oracle

| Opção | Como |
|---|---|
| **Data Pump** (`expdp`/`impdp`) | Exportar, transferir para o `DATA_PUMP_DIR` do RDS (S3 integration ou `DBMS_FILE_TRANSFER`) e importar |
| **Oracle GoldenGate / DMS** | Replicação contínua |
| **Materialized views / DB links** | Cenários pequenos |

## RDS ou Aurora como origem

| Cenário | Técnica |
|---|---|
| RDS MySQL/PostgreSQL → **Aurora** | **Réplica Aurora** da instância RDS, promover no cutover; ou restaurar snapshot como Aurora |
| RDS → outra região/conta | Snapshot copiado/compartilhado; read replica entre regiões |
| Upgrade de versão major | **Blue/Green deployment** |
| Migração de classe/armazenamento | `modify-db-instance` (com impacto de reinício/otimização) |

## Roteiro de migração (fases)

1. **Descoberta e avaliação:** inventário (tamanho, versão, extensões, jobs, linked servers, DB links, charset/collation, usuários), dependências, RPO/RTO, janela, compliance.
2. **Desenho do destino:** engine/versão, classe, storage, Multi-AZ, rede (VPC, subnet group, SG), parâmetros, criptografia, backup, monitoramento.
3. **Conectividade:** VPN/Direct Connect, largura de banda e latência para a carga inicial e o CDC; ou **Snowball** para volumes muito grandes.
4. **Preparar a origem:** ativar log para CDC, usuário de replicação, retenção de logs, espaço.
5. **Migrar o esquema** (nativo ou SCT) e criar objetos.
6. **Carga completa** (full load) e **CDC** até o atraso próximo de zero.
7. **Validação:** contagem de linhas, somas de controle (`checksum`), amostras, DMS validation, testes funcionais e de desempenho (carga realista).
8. **Ensaios gerais:** pelo menos um ensaio completo do cutover, cronometrado.
9. **Cutover:** congelar escritas, drenar a replicação, validar, ajustar sequências, apontar a aplicação.
10. **Pós-cutover:** monitorar, manter origem em modo leitura por um período, plano de rollback.

## Cutover e rollback

```
 T-0   : aplicação em modo manutenção / escrita pausada
 T+1   : replicação com atraso 0 → confirmar contagens e checksums
 T+2   : ajustar sequências/identidades; reabilitar triggers/constraints (se desabilitadas)
 T+3   : trocar a string de conexão (DNS/Parameter Store) para o endpoint RDS
 T+4   : smoke tests; liberar tráfego gradualmente
 T+N   : manter origem somente leitura; para rollback, replicação reversa ou restaurar escritas
```

| Risco | Mitigação |
|---|---|
| Esquecer sequências/`auto_increment` | Script para igualar ao máximo + margem |
| Atraso de replicação no momento da virada | Pausar escritas e esperar atraso zero |
| Diferenças de collation/timezone | Testes de ordenação e datas |
| Rollback impossível | Replicação reversa (destino → origem) ou janela de congelamento |
| Aplicação com timeouts diferentes | Testes de carga e ajuste de pool |
| Permissões e usuários | Migrar roles/grants, validar privilégios |
| Jobs e agendamentos | Reimplementar (pg_cron, EventBridge, SQL Agent) |

## Validação de dados

| Técnica | Quando |
|---|---|
| **Contagem de linhas** por tabela | Sempre, rápido |
| **Checksums / hashes** por faixa | Tabelas críticas |
| **DMS data validation** | Durante o CDC |
| **Consultas de negócio** (somatórios, saldos) | Valida o que importa |
| **Amostragem aleatória** | Rápido e eficaz |
| **Testes de regressão da aplicação** | Antes do corte |

## Exemplo prático

Migração de um PostgreSQL 13 em EC2 (1,2 TB) para RDS PostgreSQL 16 com no máximo 15 minutos de indisponibilidade:

1. **Preparar o destino:** RDS PostgreSQL 16 Multi-AZ, parâmetros equivalentes, extensões conferidas, criptografia e SG.
2. **Preparar a origem:** `wal_level=logical`, usuário de replicação, `max_replication_slots`.
3. **Esquema:** `pg_dump --schema-only` aplicado no destino; ajustes de extensões incompatíveis.
4. **Dados:** DMS `full-load-and-cdc` com 2 instâncias de replicação e validação ativada; Direct Connect de 1 Gbps; carga em 9 horas, CDC com atraso < 5 s.
5. **Ensaio:** cutover simulado em staging, cronometrado em 11 minutos.
6. **Virada:** pausar a aplicação, aguardar atraso 0, ajustar sequências (`setval`), validar contagens, trocar o endpoint (Parameter Store), liberar tráfego.
7. **Rollback preparado:** replicação lógica reversa (destino → origem) por 7 dias.
8. **Pós:** upgrade de estatísticas (`ANALYZE`), monitoramento via Performance Insights, desligar a origem após 14 dias.

## Erros comuns e armadilhas

- **Migrar sem avaliar compatibilidade** (extensões, versões, collation).
- **Achar que o DMS migra todo o esquema** (índices secundários, procedures, triggers).
- **Subdimensionar a instância de replicação** do DMS.
- **Esquecer sequências/identidades** no cutover (colisões de chave primária).
- **Não ensaiar o cutover** nem cronometrar.
- **Retenção de binlog/WAL insuficiente** durante a carga completa (CDC perde o ponto).
- **Rede subdimensionada** (carga inicial leva dias).
- **Validar só contagem de linhas.**
- **Sem plano de rollback.**
- **Desligar a origem cedo demais.**
- **Não testar desempenho** da aplicação no novo ambiente (planos de execução diferentes, estatísticas ausentes).

## 🧩 Quiz de Fixação

1. Quando preferir replicação contínua (CDC) a dump e restore?
2. O que o DMS migra bem e o que normalmente exige o SCT/ferramentas nativas?
3. Que cuidados tomar no momento do cutover?
4. Como migrar um RDS MySQL para Aurora com mínimo de downtime?

**Respostas:**
1) Quando a janela de indisponibilidade é curta (minutos): a carga completa acontece antes e o CDC mantém o destino sincronizado até a virada, enquanto o dump e restore exige parar as escritas durante todo o processo.
2) O DMS migra bem dados (full load e CDC); esquema completo, procedures, triggers e conversões entre engines exigem SCT/Schema Conversion ou ferramentas nativas.
3) Pausar escritas, esperar atraso de replicação zero, validar contagens e checksums, ajustar sequências, trocar o endpoint, testar e manter plano de rollback (replicação reversa ou origem em leitura).
4) Criando uma réplica Aurora da instância RDS, deixando sincronizar e promovendo no cutover (ou restaurando um snapshot como cluster Aurora para janelas maiores).
