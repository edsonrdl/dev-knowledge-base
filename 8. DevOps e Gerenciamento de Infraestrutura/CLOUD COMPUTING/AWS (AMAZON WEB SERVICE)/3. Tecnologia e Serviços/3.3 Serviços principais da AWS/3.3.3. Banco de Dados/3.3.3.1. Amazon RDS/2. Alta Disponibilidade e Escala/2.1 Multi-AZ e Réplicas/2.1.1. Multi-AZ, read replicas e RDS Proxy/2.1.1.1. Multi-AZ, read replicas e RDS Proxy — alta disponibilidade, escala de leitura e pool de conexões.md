### Multi-AZ, read replicas e RDS Proxy — alta disponibilidade, escala de leitura e pool de conexões

> [!warning] Aviso
> Tipos de Multi-AZ, regras de réplicas, tempos de failover e limites do RDS Proxy mudam por engine e versão. Confirme na documentação. Os comandos **não foram executados**.

Três recursos do RDS resolvem problemas diferentes que costumam ser confundidos:

| Recurso | Problema que resolve |
|---|---|
| **Multi-AZ** | **Disponibilidade** e durabilidade: sobreviver à falha de instância ou AZ |
| **Read replicas** | **Escala de leitura** (e DR entre regiões) |
| **RDS Proxy** | **Conexões**: reduzir picos, reaproveitar conexões, acelerar failover |

**Analogia:** Multi-AZ é ter um **gerador de reserva** ligado em sincronia, que assume sozinho se a energia cair. Read replicas são **filiais que atendem consultas** (só leitura). O RDS Proxy é a **recepção** que organiza a fila e reaproveita atendimentos, protegendo o banco de uma multidão de conexões.

## Multi-AZ

### Multi-AZ com standby (instância)

```
        AZ-a                                 AZ-b
 ┌────────────────────┐   replicação     ┌────────────────────┐
 │  PRIMÁRIA (ativa)  │ ══ síncrona ══►  │  STANDBY (passiva) │  ← não atende consultas
 └────────────────────┘                  └────────────────────┘
        ▲ endpoint DNS aponta para a primária; no failover o DNS passa para o standby
```

| Característica | Detalhe |
|---|---|
| **Replicação** | Síncrona (a escrita só confirma quando está no standby) |
| **Failover** | Automático em falha da primária, da AZ, de rede ou durante manutenção; costuma levar de **1 a 2 minutos** (varia) |
| **Standby** | **Não** é legível; serve só para HA |
| **Endpoint** | Permanece o mesmo; é preciso a aplicação **reconectar** |
| **Backups** | Feitos a partir do standby, reduzindo impacto no primário |
| **Custo** | Aproximadamente **dobra** o custo da instância |
| **Escopo** | Mesma região |

### Multi-AZ com dois standbys legíveis (cluster)

Disponível para MySQL e PostgreSQL: **uma primária e dois standbys legíveis** em três AZs, com replicação semi-síncrona, **failover mais rápido (tipicamente abaixo de ~35 s)** e uso dos standbys para **leituras**.

| Critério | Multi-AZ instância | Multi-AZ cluster (2 standbys) |
|---|---|---|
| Standbys | 1, não legível | 2, **legíveis** |
| Failover | ~1-2 min | Mais rápido (dezenas de segundos) |
| Escrita | Latência com replicação síncrona | Geralmente menor latência de commit (semi-síncrona) |
| Endpoints | 1 (escrita) | Writer, reader (balanceado) e instância |
| Engines | Todos | MySQL e PostgreSQL |

### Quando ocorre failover

Falha da primária (hardware/SO), perda da AZ, falha de rede, **reinício com failover**, mudança de classe, aplicação de patch. A aplicação deve ter **retry com backoff** e respeitar o TTL de DNS curto do endpoint.

```bash
# Forçar um failover (teste de resiliência)
aws rds reboot-db-instance --db-instance-identifier loja-prod --force-failover

# Converter uma instância Single-AZ em Multi-AZ (pode causar breve impacto de I/O)
aws rds modify-db-instance --db-instance-identifier loja-prod --multi-az --apply-immediately
```

Multi-AZ **não** é backup nem escala de leitura: protege contra falha de infraestrutura, não contra um `DROP TABLE` (que é replicado).

## Read replicas

Cópias **assíncronas e legíveis** da instância de origem, com **endpoint próprio**.

```
 Aplicação (escrita) ──► PRIMÁRIA ══ replicação assíncrona ══► RÉPLICA 1 ◄── relatórios
                                                         ╚════► RÉPLICA 2 ◄── leituras da API
```

| Característica | Detalhe |
|---|---|
| **Replicação** | Assíncrona: há **replica lag** (atraso); leituras podem ver dados ligeiramente antigos |
| **Quantidade** | Até 5 (MySQL/MariaDB/PostgreSQL/Oracle) por origem; mais no Aurora (confirme) |
| **Escopo** | Mesma região ou **entre regiões** (cross-region) |
| **Promoção** | Pode ser **promovida** a instância independente (DR, migração, quebrar a replicação) |
| **Réplica de réplica** | Suportada em alguns engines (aumenta o lag) |
| **Multi-AZ na réplica** | Possível |
| **Backups** | Precisam estar habilitados na origem (retenção > 0) |
| **Gravações** | Somente leitura por padrão |

### Casos de uso

- **Escalar leituras**: relatórios, dashboards, APIs de consulta.
- **Isolar cargas analíticas** do OLTP.
- **DR entre regiões**: réplica na outra região para promoção em desastre (RPO = lag).
- **Migrar** para outra região ou conta (replica + promoção).

### Multi-AZ × Read replica

| Critério | Multi-AZ (instância) | Read replica |
|---|---|---|
| Objetivo | Alta disponibilidade | Escala de leitura / DR |
| Replicação | **Síncrona** | **Assíncrona** |
| Legível | Não (instância) | **Sim** |
| Failover | Automático | Manual (promoção) |
| Mesma região | Sim | Sim ou outra região |
| Endpoint | Único | Próprio |

Pode-se (e deve-se, em produção) combinar: **primária Multi-AZ + réplicas de leitura**.

```bash
# Criar uma réplica na mesma região
aws rds create-db-instance-read-replica --db-instance-identifier loja-prod-rr1 \
  --source-db-instance-identifier loja-prod --db-instance-class db.r6g.large

# Réplica em outra região (DR); informe o ARN da origem e a região de destino
aws rds create-db-instance-read-replica --region us-east-1 \
  --db-instance-identifier loja-prod-dr \
  --source-db-instance-identifier arn:aws:rds:sa-east-1:111122223333:db:loja-prod \
  --kms-key-id alias/rds-dr    # se a origem for criptografada

# Promover a réplica (rompe a replicação; operação irreversível)
aws rds promote-read-replica --db-instance-identifier loja-prod-dr

# Monitorar o atraso (CloudWatch: ReplicaLag, em segundos)
```

## RDS Proxy

Serviço **gerenciado de proxy e pool de conexões** entre a aplicação e o RDS/Aurora.

```
 Lambda × 1000 ─┐                      ┌─► Primária
 ECS tasks      ├──► RDS PROXY (pool) ─┤
 Aplicações     ┘   reaproveita conexões└─► (failover transparente mais rápido)
```

| Benefício | Detalhe |
|---|---|
| **Pool de conexões** | Multiplexa muitas conexões de aplicação em poucas ao banco, evitando exaustão de `max_connections` |
| **Ideal para Lambda** | Funções efêmeras abrem muitas conexões; o proxy absorve |
| **Failover mais rápido** | Mantém conexões da aplicação e redireciona (reduz tempo de indisponibilidade percebido em até ~66%, segundo a AWS) |
| **Segurança** | Autenticação via **Secrets Manager** e/ou **IAM**, TLS |
| **Menor carga de CPU** | Menos handshakes e threads no banco |
| **Endpoint próprio** | Pode haver endpoint somente leitura para réplicas |

Limitações: nem todos os engines/versões; comportamento de *pinning* (conexões que usam recursos de sessão ficam "fixadas" e reduzem a multiplexação); custo por vCPU da instância.

```bash
aws rds create-db-proxy --db-proxy-name loja-proxy --engine-family POSTGRESQL \
  --auth '[{"AuthScheme":"SECRETS","SecretArn":"arn:aws:secretsmanager:sa-east-1:111122223333:secret:loja-db","IAMAuth":"REQUIRED"}]' \
  --role-arn arn:aws:iam::111122223333:role/rds-proxy-role \
  --vpc-subnet-ids subnet-0aaa111 subnet-0bbb222 --vpc-security-group-ids sg-0proxy1 \
  --require-tls
aws rds register-db-proxy-targets --db-proxy-name loja-proxy --db-instance-identifiers loja-prod
```

A aplicação passa a conectar no **endpoint do proxy**, em vez do endpoint da instância.

## Arquitetura recomendada (produção)

```
 App (escrita/leitura) ──► RDS Proxy ──► PRIMÁRIA Multi-AZ (AZ-a / standby AZ-b)
 App (somente leitura) ──► endpoint de réplica ──► Read replicas (AZ-a, AZ-b)
 DR: réplica cross-region (promoção manual) + snapshots copiados
```

## Exemplo prático

Aplicação com picos de leitura por relatórios e funções Lambda abrindo muitas conexões:

1. Primária **Multi-AZ** para HA.
2. Duas **read replicas**: uma para a API de consulta e outra para BI/relatórios.
3. **RDS Proxy** na frente da primária (escritas das Lambdas) com IAM auth.
4. Aplicação com **retry/backoff** e testes de `--force-failover` trimestrais.
5. Alarme em `ReplicaLag` > 30 s e em `DatabaseConnections`.
6. Réplica em outra região para DR com runbook de promoção.

## Matriz de decisão: qual recurso resolve qual problema

| Problema | Recurso | Não resolve |
|---|---|---|
| Falha de instância/AZ | Multi-AZ | Lentidão por leitura |
| Muitas leituras | Read replicas | Falha da primária (promoção é manual, salvo Aurora) |
| Estouro de conexões (Lambda, microsserviços) | RDS Proxy | Consultas lentas |
| DR entre regiões | Replica cross-region | Failover automático |
| Erro humano (DROP) | Backup/PITR | Multi-AZ (replica o erro) |

> [!warning] Valores, limites e preços mudam; os exemplos deste material não foram executados. Comportamento de failover e limites de réplicas variam por engine; consulte a documentação.

```
            Aplicação
         ┌──────┴────────┐
    escrita│            │leitura
        ▼                ▼
   RDS Proxy (pool) ──► Replica 1 / Replica 2
        │
   ┌────▼────┐  replicação síncrona  ┌─────────┐
   │Primária │ ────────────────────► │ Standby │  (outra AZ, sem leitura)
   └─────────┘                       └─────────┘
```

Multi-AZ clássico é **alta disponibilidade**, não escalabilidade: o standby não atende leituras. Read replicas são **assíncronas**, então podem ter lag; a aplicação deve tolerar leituras levemente desatualizadas.

### Árvore de decisão

```
Banco crítico?  ── sim ─► Multi-AZ
Leitura pesada? ── sim ─► Read replicas (+ Proxy ou endpoint de leitura)
Muitas conexões curtas (serverless)? ── sim ─► RDS Proxy
Precisa DR regional? ── sim ─► replica cross-region / backups copiados
```

## CLI comentado

```bash
# Converte para Multi-AZ (causa breve impacto na modificação)
aws rds modify-db-instance --db-instance-identifier prod-db \
  --multi-az --apply-immediately

# Cria uma read replica
aws rds create-db-instance-read-replica \
  --db-instance-identifier prod-db-r1 --source-db-instance-identifier prod-db

# Testa failover do Multi-AZ
aws rds reboot-db-instance --db-instance-identifier prod-db --force-failover

# Promove replica (por exemplo, em DR)
aws rds promote-read-replica --db-instance-identifier prod-db-r1
```

## Troubleshooting

| Sintoma | Causa provável | Ação |
|---|---|---|
| Replica lag crescente | Escrita pesada ou réplica pequena | Escalar réplica, reduzir escritas longas |
| Erros de conexão após failover | DNS em cache na aplicação | TTL curto, reconexão, RDS Proxy |
| `Too many connections` | Pool inexistente | RDS Proxy ou pool no app |
| Proxy sem acesso | SG/Secrets Manager mal configurados | Revisar SGs e permissões da role |

## Custo

Multi-AZ aproximadamente **dobra** o custo da instância; cada réplica custa como instância adicional, mais transferência entre regiões nas cross-region. O RDS Proxy cobra por vCPU do banco por hora. Compense com rightsizing e instâncias reservadas para a primária.

## Erros comuns e armadilhas

- **Achar que Multi-AZ escala leituras:** o standby de instância não é legível.
- **Achar que a réplica é HA automática:** a promoção é manual (exceto Aurora com failover).
- **Ler da réplica dados que acabaram de ser gravados** (lag) e quebrar a consistência esperada.
- **Aplicação sem retry/reconexão:** o failover derruba requisições.
- **Cache de DNS longo** na aplicação (JVM etc.): continua apontando para o antigo primário.
- **Não habilitar backups** (retenção 0) e tentar criar réplica.
- **Esquecer o custo** de cada réplica e do Multi-AZ.
- **Usar o proxy sem tratar o pinning** e perder o benefício.
- **Promover réplica por engano** (irreversível).

## 🧩 Quiz de Fixação

1. Multi-AZ e read replica resolvem o mesmo problema? Explique.
2. Por que o RDS Proxy é útil com Lambda?
3. O que é o replica lag e como ele afeta a aplicação?

**Respostas:**
1) Não. Multi-AZ (replicação síncrona, standby não legível) dá alta disponibilidade com failover automático; read replica (assíncrona, legível) escala leituras e serve DR, com promoção manual.
2) Porque muitas execuções simultâneas abrem muitas conexões e esgotam o banco; o proxy faz pool e multiplexação, reaproveitando conexões e aliviando o banco.
3) É o atraso da réplica em relação à primária; leituras na réplica podem retornar dados defasados, exigindo que a aplicação tolere consistência eventual ou leia da primária quando precisa do dado mais recente.

**Questões complementares:**

4. Por que Multi-AZ não protege contra um `DROP TABLE` acidental?
5. Qual a diferença de replicação entre Multi-AZ clássico e read replica?
6. Em que situação o RDS Proxy ajuda mais?

**Respostas das questões complementares:**
4) Porque a replicação para o standby é síncrona e replica também o erro; é preciso backup/PITR para recuperar.
5) Multi-AZ replica de forma síncrona para um standby que não atende leituras; a read replica é assíncrona, atende leituras e pode ter lag.
6) Com muitas conexões curtas ou simultâneas (Lambda, microsserviços), pois o proxy faz pool e protege o banco de estourar conexões, além de acelerar o failover.
