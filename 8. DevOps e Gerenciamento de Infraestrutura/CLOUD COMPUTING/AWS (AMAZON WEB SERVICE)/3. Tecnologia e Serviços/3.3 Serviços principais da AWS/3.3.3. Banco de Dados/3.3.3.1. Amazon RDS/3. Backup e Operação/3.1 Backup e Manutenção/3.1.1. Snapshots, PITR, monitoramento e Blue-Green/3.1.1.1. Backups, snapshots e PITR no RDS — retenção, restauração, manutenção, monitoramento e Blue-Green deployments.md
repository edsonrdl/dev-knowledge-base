### Backups, snapshots e PITR no RDS — retenção, restauração, manutenção, monitoramento e Blue/Green deployments

> [!warning] Aviso
> Retenção máxima, comportamento de restauração, janelas, métricas e preços do RDS mudam por engine e versão. Confirme na documentação. Os comandos **não foram executados**.

Operar um banco é garantir que ele possa ser **recuperado** (backups), **mantido** (patches e upgrades sem surpresas) e **observado** (desempenho e saúde). O RDS entrega ferramentas para as três coisas; esta nota as organiza.

**Analogia:** é a **rotina de uma frota de carros**: fotos periódicas do estado (snapshots), um diário minuto a minuto para voltar a qualquer instante (PITR), revisões programadas (manutenção), painel do carro (monitoramento) e um **carro reserva idêntico** para testar uma troca de motor antes de usar de verdade (Blue/Green).

## Backups automáticos e PITR

| Característica | Detalhe |
|---|---|
| **Backup automatizado** | Snapshot diário do volume de armazenamento na **janela de backup** + **logs de transação** continuamente |
| **Retenção** | 0 a 35 dias (0 desabilita backups; padrão 1 ou 7 conforme o modo de criação) |
| **PITR (point-in-time recovery)** | Restaura para **qualquer segundo** dentro da retenção (até ~5 minutos atrás) |
| **Armazenamento** | Gratuito até o tamanho do armazenamento provisionado, na região; acima disso cobrado |
| **Impacto** | Em Single-AZ pode haver breve suspensão de I/O; em Multi-AZ o backup é feito no standby |
| **Exclusão** | Backups automáticos são **apagados com a instância** (a menos que você mantenha backups automáticos retidos ou tire snapshot final) |

### Snapshots manuais

- Iniciados por você, **sem expiração automática**, persistem após excluir a instância.
- Podem ser **copiados entre regiões e contas**, criptografados com KMS e compartilhados.
- Use antes de mudanças de risco (migração de esquema, upgrade de versão).

```bash
# Snapshot manual
aws rds create-db-snapshot --db-instance-identifier loja-prod --db-snapshot-identifier loja-pre-upgrade

# Copiar para outra região (DR); --kms-key-id da região de destino se criptografado
aws rds copy-db-snapshot --source-region sa-east-1 --region us-east-1 \
  --source-db-snapshot-identifier arn:aws:rds:sa-east-1:111122223333:snapshot:loja-pre-upgrade \
  --target-db-snapshot-identifier loja-pre-upgrade-dr --kms-key-id alias/rds-dr

# Ajustar retenção e janela de backup
aws rds modify-db-instance --db-instance-identifier loja-prod \
  --backup-retention-period 14 --preferred-backup-window 03:00-04:00 --apply-immediately
```

### Restauração

A restauração **sempre cria uma nova instância** (novo endpoint); a original permanece.

```bash
# Restaurar de um snapshot
aws rds restore-db-instance-from-db-snapshot --db-instance-identifier loja-restaurada \
  --db-snapshot-identifier loja-pre-upgrade --db-instance-class db.r6g.large

# PITR: restaurar para um instante específico (UTC) ou para o último horário restaurável
aws rds restore-db-instance-to-point-in-time \
  --source-db-instance-identifier loja-prod --target-db-instance-identifier loja-pitr \
  --restore-time 2026-11-06T14:30:00Z
# Depois: validar os dados, ajustar SG/parameter group (não herdados em alguns casos) e apontar a aplicação
```

Cuidados: parameter groups, option groups e Security Groups podem precisar ser reassociados; o tempo de restauração cresce com o volume de dados e **o desempenho inicial pode ser menor** (carregamento lazy do volume).

Para integrar com política centralizada, cópias entre contas e cofres imutáveis, use o **AWS Backup** (nota própria desta trilha).

## Manutenção e upgrades

| Item | Como funciona |
|---|---|
| **Janela de manutenção** | Período semanal de 30 min+ em que o RDS pode aplicar patches/upgrades obrigatórios; escolha horário de baixo tráfego |
| **Patches de SO e engine** | Aplicados automaticamente na janela (pode haver reinício; em Multi-AZ o impacto é reduzido pelo failover) |
| **Auto minor version upgrade** | Atualiza versões menores automaticamente; desabilite se quiser controle total (e teste antes) |
| **Major version upgrade** | **Manual**; exige teste; pode precisar de ajuste de parâmetros, extensões e compatibilidade de código |
| **Fim de suporte de versão** | A AWS anuncia o fim; versões sem suporte são atualizadas à força (ou cobradas como Extended Support) |

Boas práticas de upgrade:

1. Ler as notas de versão e avisos de depreciação.
2. Testar em **clone** (restaurado de snapshot) e rodar a suíte da aplicação.
3. Tirar **snapshot** antes.
4. Executar na janela com plano de rollback.
5. Preferir **Blue/Green deployments** para reduzir indisponibilidade.

## Blue/Green deployments

Cria um ambiente **verde** (cópia sincronizada do azul/produção) onde você aplica mudanças (upgrade major, alteração de parâmetros, mudança de esquema compatível) e testa, e depois faz o **switchover** controlado.

```
 AZUL (produção atual) ══ replicação lógica ══► VERDE (staging com a mudança aplicada)
        ▲                                                   │ testes
        └────────── SWITCHOVER (minutos) ◄──────────────────┘   endpoints são trocados
```

| Característica | Detalhe |
|---|---|
| **Engines** | MySQL, MariaDB, PostgreSQL (e Aurora), conforme versão |
| **Sincronização** | Replicação contínua azul → verde |
| **Switchover** | Tipicamente **menos de ~1 minuto** de indisponibilidade; nomes/endpoints são trocados |
| **Rollback** | Ambiente azul antigo é mantido até você excluí-lo |
| **Casos** | Upgrade de versão major, mudanças de parameter group, ajustes de storage |

```bash
aws rds create-blue-green-deployment --blue-green-deployment-name upgrade-pg17 \
  --source arn:aws:rds:sa-east-1:111122223333:db:loja-prod \
  --target-engine-version 17.1
# ... testar o ambiente verde ...
aws rds switchover-blue-green-deployment --blue-green-deployment-identifier bgd-abc123 --switchover-timeout 300
```

(Valores de versão são ilustrativos.)

## Monitoramento

| Ferramenta | O que oferece |
|---|---|
| **CloudWatch (métricas padrão)** | `CPUUtilization`, `FreeableMemory`, `FreeStorageSpace`, `DatabaseConnections`, `ReadIOPS/WriteIOPS`, `ReadLatency/WriteLatency`, `ReplicaLag`, `DiskQueueDepth` |
| **Enhanced Monitoring** | Métricas do **SO** em granularidade de 1-60 s (por processo) |
| **Performance Insights** | Painel de **carga do banco (DB load)** por *wait events*, SQL, host e usuário; encontra a consulta que causa o gargalo |
| **Database Insights / CloudWatch Database Insights** | Visão consolidada da frota (recurso mais recente; confirme) |
| **Logs** | Logs do engine (erro, lento, geral, auditoria) publicados no CloudWatch Logs |
| **Eventos (RDS Events / EventBridge)** | Failover, backup, manutenção, mudança de configuração |
| **CloudTrail** | Chamadas de API |

Alarmes essenciais: `FreeStorageSpace` baixo, `FreeableMemory` baixo, `CPUUtilization` > 80%, `DatabaseConnections` perto de `max_connections`, `ReplicaLag`, `DiskQueueDepth` alto, eventos de failover.

```bash
# Habilitar Performance Insights (retenção padrão gratuita de 7 dias)
aws rds modify-db-instance --db-instance-identifier loja-prod \
  --enable-performance-insights --performance-insights-retention-period 7 --apply-immediately

# Publicar log de consultas lentas no CloudWatch Logs
aws rds modify-db-instance --db-instance-identifier loja-prod \
  --cloudwatch-logs-export-configuration '{"EnableLogTypes":["postgresql","upgrade"]}'
```

| Item | Observação |
|---|---|
| Instância (hora) | Principal componente; Multi-AZ ~2×; réplicas cobram como instância |
| Armazenamento e IOPS | Por GB-mês e IOPS provisionados |
| Backups acima do armazenamento provisionado e snapshots manuais | Por GB-mês |

| Reserved Instances / Savings Plans | Descontos para uso previsível |
| Instâncias paradas | Podem ser paradas por até 7 dias; o armazenamento continua cobrado |

## Exemplo prático

Plano operacional de um banco de produção:

1. Backup automático com retenção de **14 dias**, janela 03:00–04:00; snapshots manuais antes de cada release.
2. Cópia diária de snapshots para outra região (via AWS Backup).
3. **Teste mensal de restauração** com PITR em um clone, medindo o tempo.
4. Janela de manutenção domingo 05:00–06:00; `auto minor version upgrade` ligado em staging, desligado em produção até validação.
5. Upgrade major via **Blue/Green** com testes automatizados no verde.
6. Performance Insights + alarmes + exportação de logs lentos; revisão semanal das 5 piores consultas.

## Erros comuns e armadilhas

- **Retenção de backup 0** por engano (sem PITR, sem réplicas).
- **Nunca testar a restauração**, sem conhecer o RTO real.
- **Achar que a restauração sobrescreve o banco:** cria nova instância com novo endpoint.
- **Esquecer SGs e parameter groups** na instância restaurada.
- **Excluir a instância sem snapshot final:** backups automáticos somem com ela.
- **Upgrade major direto em produção**, sem testes e sem snapshot.
- **Janela de manutenção em horário de pico.**
- **Monitorar só CPU**, ignorando memória, conexões, latência de disco e espaço livre.
- **Não habilitar Performance Insights/logs** antes do incidente.
- **Deixar o storage encher:** a instância entra em `storage-full` e fica indisponível; use autoscaling e alarme.

## 🧩 Quiz de Fixação

1. Qual a diferença entre backup automático com PITR e snapshot manual?
2. O que acontece com o banco original ao restaurar um snapshot?
3. Para que servem os Blue/Green deployments?

**Respostas:**
1) O backup automático (snapshot diário + logs de transação) permite restaurar para qualquer segundo da retenção (até 35 dias) e é apagado com a instância; o snapshot manual é um ponto fixo, sem expiração automática, que persiste após excluir a instância.
2) Nada: a restauração cria uma nova instância com novo endpoint; o original continua. É preciso reapontar a aplicação e reassociar SG/parameter group.
3) Criar um ambiente verde sincronizado para aplicar e testar mudanças (como upgrades major) e fazer o switchover em cerca de um minuto, mantendo o azul como rollback.
