### Diagnóstico de desempenho no RDS — Performance Insights, Enhanced Monitoring, slow logs, wait events e troubleshooting

> [!warning] Aviso
> Nomes de métricas, retenção do Performance Insights, produtos de monitoramento (Database Insights), wait events e preços mudam com frequência. Os limiares citados são **pontos de partida**. Confirme na documentação. Os comandos **não foram executados**.

Quando o banco "está lento", a pergunta certa não é "qual métrica subiu?", e sim **"onde o banco está gastando tempo?"**. O RDS oferece camadas de observabilidade — **CloudWatch**, **Enhanced Monitoring**, **Performance Insights**, **logs do engine** — que, usadas em sequência, levam da **sintoma** à **consulta ou recurso** causador. Esta nota ensina o método e os atalhos.

**Analogia:** é um **atendimento de emergência**. Os sinais vitais (CloudWatch) dizem que há febre; o exame de sangue (Enhanced Monitoring) mostra o estado do corpo (SO); a tomografia (Performance Insights) mostra qual órgão (consulta/espera) está comprometido; o prontuário (logs) conta a história.

## As camadas de observabilidade

| Camada | O que mostra | Granularidade | Custo |
|---|---|---|---|
| **CloudWatch (métricas padrão)** | CPU, memória livre, IOPS, latência de disco, conexões, espaço livre, réplica | 1 minuto | Incluído |
| **Enhanced Monitoring** | Métricas do **SO** (CPU por processo, memória, swap, disco, rede) via agente | 1 a 60 s | Cobrado por CloudWatch Logs |
| **Performance Insights** | **Carga do banco (DB load)** por consulta, espera, usuário, host e banco | 1 s | Retenção curta gratuita; longa paga |
| **Logs do engine** | Erros, consultas lentas, deadlocks, auditoria | Evento | CloudWatch Logs |
| **Eventos do RDS** | Failover, reinício, manutenção, backup | Evento | Gratuito |
| **DevOps Guru for RDS** | Detecção de anomalias e recomendações (ML) | Contínuo | Pago |
| **Database Insights** | Visão consolidada de frota (recurso mais recente) | — | Pago (confirme) |

## CloudWatch: o primeiro olhar

| Métrica | O que indica | Alerta típico |
|---|---|---|
| `CPUUtilization` | Uso de CPU do host | > 80% sustentado |
| `FreeableMemory` | Memória disponível | Queda contínua; < 10-15% |
| `SwapUsage` | Uso de swap | > 0 e crescendo |
| `ReadIOPS` / `WriteIOPS` | I/O | Perto do limite do volume/instância |
| `ReadLatency` / `WriteLatency` | Latência do disco | > 10-20 ms em SSD |
| `DiskQueueDepth` | Fila de I/O | Alta e sustentada |
| `FreeStorageSpace` | Espaço livre | < 10-20% |
| `DatabaseConnections` | Conexões | Perto de `max_connections` |
| `ReplicaLag` | Atraso das réplicas | > 30 s (ajuste ao seu RPO) |
| `BurstBalance` / `EBSIOBalance%` | Créditos de I/O (gp2 / instâncias burst) | Perto de 0 |
| `CPUCreditBalance` | Créditos de CPU (`db.t`) | Perto de 0 |
| `NetworkReceive/TransmitThroughput` | Rede | Perto do limite da classe |

Cuidado com **limites de EBS da instância** (IOPS/throughput máximos da classe) e **créditos de burst**, que causam quedas súbitas de desempenho.

## Enhanced Monitoring

Instala um agente no host que reporta métricas do **sistema operacional** em intervalos de até 1 s:

```bash
aws rds modify-db-instance --db-instance-identifier loja-prod \
  --monitoring-interval 15 \
  --monitoring-role-arn arn:aws:iam::111122223333:role/rds-monitoring-role \
  --apply-immediately
# Os dados vão para o CloudWatch Logs, grupo RDSOSMetrics
```

Mostra: CPU por processo (`topN`), memória (livre, cache, buffers), swap, I/O por dispositivo, rede. Útil para distinguir **CPU do banco** de **CPU do sistema/outros processos** e ver **picos curtos** que a granularidade de 1 minuto esconde.

## Performance Insights

Mede a **carga do banco** em **AAS** (*Average Active Sessions*): quantas sessões, em média, estão ativas (executando ou esperando).

```
 AAS
  12 ┤            ▓▓▓▓▓
   8 ┤        ▓▓▓▓▓▓▓▓▓▓▓       ← linha do nº de vCPUs (ex.: 8)
   4 ┤  ▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓
   0 ┼──────────────────────► tempo
       cores: CPU (verde) · I/O (azul) · Lock (vermelho) · Outras esperas
```

Regra de leitura: **AAS acima do número de vCPUs** indica saturação; **a cor predominante** (tipo de espera) mostra o gargalo.

| Dimensão (*slice by*) | Pergunta que responde |
|---|---|
| **Waits** (eventos de espera) | O que o banco está esperando? CPU, I/O, lock, rede? |
| **SQL** | Quais consultas geram mais carga? |
| **Hosts** | Quais clientes/servidores de aplicação? |
| **Users** | Qual usuário do banco? |
| **Databases** | Qual banco/esquema? |
| **Application (PostgreSQL)** | Qual aplicação? |

```bash
aws rds modify-db-instance --db-instance-identifier loja-prod \
  --enable-performance-insights --performance-insights-retention-period 7 --apply-immediately
# 7 dias é o período gratuito; períodos maiores (até 24 meses) são cobrados

# Consulta via API (top SQL por carga, ilustrativa)
aws pi get-resource-metrics --service-type RDS --identifier db-ABCDEFGHIJKL \
  --metric-queries '[{"Metric":"db.load.avg","GroupBy":{"Group":"db.sql_tokenized","Limit":5}}]' \
  --start-time 2026-11-06T13:00:00Z --end-time 2026-11-06T14:00:00Z --period-in-seconds 60
```

## Wait events: como interpretar (exemplos)

### PostgreSQL

| Evento | Significado | Ação comum |
|---|---|---|
| `CPU` | Consultas consumindo CPU | Otimizar SQL, índices, aumentar classe |
| `IO:DataFileRead` | Leitura de páginas do disco (cache miss) | Índices, mais memória, consultas seletivas |
| `IO:WALWrite` / `LWLock:WALWriteLock` | Escrita do WAL | Reduzir commits pequenos (lotes), I/O mais rápido |
| `Lock:transactionid` / `Lock:tuple` | Bloqueios por transações concorrentes | Encurtar transações, ordem consistente de acesso |
| `LWLock:BufferMapping` | Contenção de buffer | Reduzir concorrência, revisar índice quente |
| `Client:ClientRead` | Aguardando a aplicação ler/enviar | Rede, aplicação lenta, transação aberta |
| `Timeout:PgSleep` | `pg_sleep` | Intencional |

### MySQL/MariaDB

| Evento | Significado | Ação |
|---|---|---|
| `cpu` | CPU | Otimizar consultas |
| `io/table/sql/handler` | Acesso a tabelas (I/O) | Índices, plano de execução |
| `io/file/innodb/innodb_data_file` | Leitura/gravação de dados | Aumentar buffer pool, I/O |
| `synch/mutex/innodb/...`, `synch/sxlock` | Contenção interna | Revisar concorrência e índices |
| `lock/table/sql/handler` / row locks | Bloqueios | Transações curtas |

### SQL Server / Oracle

SQL Server: `PAGEIOLATCH_*` (I/O de dados), `WRITELOG`, `LCK_M_*` (bloqueios), `CXPACKET`/`CXCONSUMER` (paralelismo), `SOS_SCHEDULER_YIELD` (CPU). Oracle: `db file sequential read`, `log file sync`, `enq: TX - row lock contention`, `latch:*`.

## Logs do engine

| Log | Como habilitar | Uso |
|---|---|---|
| **Slow query log** | MySQL: `slow_query_log=1`, `long_query_time`; PostgreSQL: `log_min_duration_statement` | Achar consultas lentas |
| **Erro** | Padrão | Falhas, reinícios, deadlocks (conforme engine) |
| **Auditoria** | pgAudit / MariaDB Audit / SQL Server Audit | Quem fez o quê |
| **Deadlock** | MySQL: `innodb_print_all_deadlocks`; PostgreSQL: `log_lock_waits` | Diagnóstico |
| **Upgrade/Postgres** | `upgrade` | Acompanhar upgrades |

Exporte para o CloudWatch Logs e crie **filtros de métrica** (`ERROR`, `deadlock`, `FATAL`) com alarmes. Para PostgreSQL, a extensão `pg_stat_statements` oferece estatísticas agregadas por consulta, e `auto_explain` registra planos de consultas lentas.

## Método de troubleshooting

```
1. Sintoma: usuários reclamam / latência alta / erros?          → quando começou? mudou algo (deploy, parâmetro, volume)?
2. CloudWatch: CPU? memória? I/O? conexões? réplica? espaço?     → qual recurso está saturado?
3. Performance Insights: AAS > vCPU? qual espera domina?         → CPU, I/O, lock, rede?
4. Top SQL: qual consulta responde pela carga?                    → plano de execução (EXPLAIN / EXPLAIN ANALYZE)
5. Enhanced Monitoring: algo no SO fora do banco?                → processo, swap, I/O
6. Logs: erros, deadlocks, consultas lentas, vacuum                → causa contextual
7. Hipótese → mudança pequena → medir → documentar
```

### Receitas por sintoma

| Sintoma | Causas prováveis | Ações |
|---|---|---|
| **CPU alta** | Consultas sem índice, muitas execuções, funções caras | Top SQL, índices, cache na aplicação, escalar classe, réplicas de leitura |
| **I/O alto / latência de disco** | Cache miss, scans, checkpoints, limite de IOPS | Índices, mais memória, gp3/io2 com mais IOPS, verificar limite da instância |
| **Memória baixa / swap** | `work_mem` alto × conexões, buffer mal dimensionado, vazamento | Pool de conexões, reduzir `work_mem`, classe maior |
| **Conexões esgotadas** | Pool sem limite, conexões ociosas, picos Lambda | RDS Proxy, timeouts, ajustar pool |
| **Lock/deadlock** | Transações longas, ordem inconsistente | Encurtar transações, índices, retry |
| **Réplica atrasada** | Escrita intensa, réplica pequena, consultas longas na réplica | Classe maior, ajustar queries, reduzir carga |
| **Espaço acabando** | Logs, tabelas inchadas, backups temporários, WAL retido por slot lógico | Limpeza, `VACUUM`, remover slots de replicação inativos, autoscaling |
| **Latência intermitente** | Créditos de burst, backups/snapshots, manutenção | `BurstBalance`, `CPUCreditBalance`, janelas |
| **Lentidão após restauração** | Carregamento lazy do volume | Aquecer lendo dados, aguardar |

## Boas práticas

1. Habilitar **Performance Insights** e **Enhanced Monitoring** em produção (antes do incidente).
2. Exportar **slow logs** e **logs de erro** ao CloudWatch.
3. Alarmes de CPU, memória, conexões, espaço, latência, réplica e eventos de failover.
4. Habilitar `pg_stat_statements` e revisar semanalmente o top 10 de consultas.
5. Registrar **baseline** (valores normais) para comparar.
6. Usar **EXPLAIN (ANALYZE, BUFFERS)** em ambiente de teste com volume realista.
7. Versionar índices e mudanças de esquema.
8. Dimensionar pelo **p95/p99**, não pela média.

## Exemplo prático

Alerta: latência da API passou de 120 ms para 900 ms às 14:05 em um PostgreSQL `db.r6g.xlarge` (4 vCPUs).

1. CloudWatch: CPU em 98%, `ReadIOPS` normal, `DatabaseConnections` subiu de 200 para 650.
2. Performance Insights: AAS = 14 (vCPU = 4), faixa dominada por `CPU`; **top SQL** é um `SELECT ... FROM pedidos WHERE cliente_id = $1 ORDER BY criado DESC` executando milhares de vezes por minuto.
3. `EXPLAIN (ANALYZE, BUFFERS)` mostra *Seq Scan* em `pedidos` (3 milhões de linhas): o índice `(cliente_id, criado)` foi removido no deploy das 14:00.
4. Correção: `CREATE INDEX CONCURRENTLY idx_pedidos_cliente_criado ON pedidos (cliente_id, criado DESC);`.
5. Medir: AAS cai para 2, CPU 25%, latência 110 ms. Adicionar teste no pipeline que valida a existência do índice e alarme em AAS > vCPU.
6. Pós-incidente: documentar, incluir `pg_stat_statements` no dashboard e alarme em `DatabaseConnections`.

## Erros comuns e armadilhas

- **Olhar só `CPUUtilization`** sem Performance Insights: não se sabe qual consulta nem qual espera.
- **Habilitar o monitoramento depois do incidente.**
- **Ignorar limites de EBS da instância** e créditos de burst.
- **Aumentar a classe sem analisar a consulta:** custo maior, problema igual.
- **Medir só médias** em vez de p95/p99.
- **Logar tudo** (`general_log`, `log_statement=all`) em produção.
- **Criar índice bloqueante** (`CREATE INDEX` sem `CONCURRENTLY`) em horário de pico.
- **Analisar `EXPLAIN` com pouco dado** no teste.
- **Não limpar slots de replicação inativos** (PostgreSQL), enchendo o disco com WAL.
- **Concluir sem baseline**, sem saber o que é "normal".

## 🧩 Quiz de Fixação

1. O que é AAS no Performance Insights e como interpretá-lo?
2. Quando usar Enhanced Monitoring além do CloudWatch?
3. Quais passos seguir ao diagnosticar um banco lento?
4. Cite duas causas de espaço em disco acabando em um PostgreSQL no RDS.

**Respostas:**
1) *Average Active Sessions*: média de sessões ativas (executando ou esperando). Se for maior que o número de vCPUs, há saturação; a categoria de espera predominante indica o gargalo (CPU, I/O, locks).
2) Para ver métricas do sistema operacional em granularidade fina (processos, memória, swap, I/O por dispositivo), separar CPU do banco de outros processos e enxergar picos curtos que o CloudWatch de 1 minuto esconde.
3) Identificar o sintoma e a hora, olhar CloudWatch para o recurso saturado, usar Performance Insights para a espera e o top SQL, analisar o plano de execução, conferir Enhanced Monitoring e logs, e então testar uma mudança pequena medindo antes e depois.
4) Tabelas inchadas (bloat) por vacuum bloqueado, logs grandes, WAL retido por slot de replicação lógica inativo, arquivos temporários de consultas grandes.
