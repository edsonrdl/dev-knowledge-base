### Segurança do RDS — rede, criptografia KMS, SSL/TLS, IAM database authentication e Secrets Manager

> [!warning] Aviso
> Opções de criptografia, autenticação IAM por engine, certificados CA e políticas gerenciadas mudam. Confirme na documentação. Os comandos e JSONs **não foram executados**.

O banco guarda os dados mais valiosos da aplicação; a segurança do RDS se organiza em **camadas**: **rede** (quem alcança a porta), **identidade** (quem se autentica e como), **criptografia** (em repouso e em trânsito), **segredos** (credenciais) e **auditoria** (o que foi feito).

**Analogia:** o banco é uma **sala-cofre**. A rede é o corredor com portas trancadas (subnets privadas e Security Groups); a identidade é o crachá (IAM/credenciais); a criptografia é o cofre embutido nas paredes; o Secrets Manager é o cofre das chaves com troca periódica; a auditoria são as câmeras.

## Camada 1 — Rede

| Prática | Detalhe |
|---|---|
| **Subnets privadas** | DB subnet group sem rota para o Internet Gateway; o banco não tem IP público |
| **`PubliclyAccessible=false`** | Padrão recomendado; evita IP público e resolução para IP público |
| **Security Group** | Libera a porta do banco **somente** do SG da aplicação (referência SG-a-SG), nunca `0.0.0.0/0` |
| **NACLs** | Camada adicional, stateless; opcional |
| **Acesso administrativo** | Via bastion/SSM Session Manager, VPN, Direct Connect, Client VPN; evite expor o banco |
| **VPC endpoints / PrivateLink** | RDS Data API (Aurora) e RDS API sem internet |

```
 Internet ✗──── (sem rota)         Subnets privadas
 App (SG-app) ──porta 5432──► RDS (SG-bd: entrada somente de SG-app)
 Admin ──SSM/VPN──► bastion/ferramenta ──► RDS
```

## Camada 2 — Criptografia

### Em repouso (KMS)

- Opção **`--storage-encrypted`** na criação: criptografa volume, snapshots, backups automáticos, logs e réplicas.
- Usa chave KMS (`aws/rds` gerenciada ou **CMK** sua).
- **Não pode ser habilitada depois** em uma instância existente. Para criptografar uma não criptografada: **snapshot → cópia criptografada → restaurar**.
- Réplicas e snapshots de instância criptografada são criptografados; **cópia entre regiões** exige chave KMS na região de destino.
- Compartilhar snapshot criptografado entre contas exige **CMK** e compartilhar a chave.
- Alguns engines oferecem **TDE** (Transparent Data Encryption: Oracle, SQL Server) no nível do engine, além do KMS. Veja [[8. DevOps e Gerenciamento de Infraestrutura/CLOUD COMPUTING/AWS (AMAZON WEB SERVICE)/2. Segurança e Conformidade/2.3 Capacidades de gerenciamento de acesso da AWS/2.3.2. Serviços de segurança/2.3.2.7. AWS Key Management Service (KMS)|AWS KMS]].

```bash
# Criptografar uma instância existente: snapshot → cópia criptografada → restaurar
aws rds create-db-snapshot --db-instance-identifier legado --db-snapshot-identifier legado-snap
aws rds copy-db-snapshot --source-db-snapshot-identifier legado-snap \
  --target-db-snapshot-identifier legado-snap-enc --kms-key-id alias/rds-prod
aws rds restore-db-instance-from-db-snapshot --db-instance-identifier legado-enc \
  --db-snapshot-identifier legado-snap-enc
```

### Em trânsito (SSL/TLS)

- Todos os engines suportam TLS; cada instância tem um certificado emitido por uma **CA do RDS** (observe as datas de expiração e a rotação de CA).
- **Exija TLS**:
  - PostgreSQL: parâmetro `rds.force_ssl = 1`.
  - MySQL/MariaDB: `require_secure_transport = ON` (ou `REQUIRE SSL` por usuário).
  - SQL Server: `rds.force_ssl`.
  - Oracle: opções SSL.
- No cliente, valide o certificado (`sslmode=verify-full` no PostgreSQL) com o bundle de CA do RDS.

```bash
# Exemplo de conexão PostgreSQL exigindo TLS e validando o certificado
psql "host=loja-prod.abc123.sa-east-1.rds.amazonaws.com port=5432 dbname=loja user=app \
      sslmode=verify-full sslrootcert=global-bundle.pem"
```

## Camada 3 — Autenticação e autorização

### Autenticação nativa (usuário/senha)

Usuários e permissões criados dentro do banco (`CREATE USER`, `GRANT`). O **master user** do RDS tem privilégios altos, mas não `superuser` completo; use-o só para administração e crie usuários de aplicação com privilégios mínimos.

### IAM database authentication

Em vez de senha fixa, a aplicação usa um **token de autenticação temporário (15 minutos)** gerado com credenciais IAM (role).

| Aspecto | Detalhe |
|---|---|
| **Engines** | MySQL, MariaDB, PostgreSQL (e Aurora); verifique a lista |
| **Token** | Gerado com `aws rds generate-db-auth-token`, usado como senha, **exige TLS** |
| **Vantagens** | Sem senhas no código; controle por IAM; auditoria por CloudTrail |
| **Limites** | Quantidade de novas conexões por segundo limitada; combine com RDS Proxy para alto volume |

```bash
TOKEN=$(aws rds generate-db-auth-token --hostname loja-prod.abc123.sa-east-1.rds.amazonaws.com \
        --port 5432 --region sa-east-1 --username app_iam)
psql "host=loja-prod.abc123.sa-east-1.rds.amazonaws.com port=5432 dbname=loja user=app_iam \
      password=$TOKEN sslmode=verify-full sslrootcert=global-bundle.pem"
```

```json
{
  "Effect": "Allow",
  "Action": "rds-db:connect",
  "Resource": "arn:aws:rds-db:sa-east-1:111122223333:dbuser:db-ABCDEFGHIJKL/app_iam"
}
```

No PostgreSQL, o usuário recebe `GRANT rds_iam TO app_iam;`; no MySQL, `CREATE USER ... IDENTIFIED WITH AWSAuthenticationPlugin AS 'RDS'`.

### Outras opções

- **Kerberos / Active Directory** (SQL Server, Oracle, PostgreSQL, MySQL) via AWS Managed Microsoft AD.
- **Controle da API do RDS** por IAM (`rds:CreateDBInstance`, `rds:DeleteDBInstance`...): restrinja quem pode excluir/modificar, exigir tags, bloquear `PubliclyAccessible`.

## Camada 4 — Segredos (AWS Secrets Manager)

| Recurso | Uso |
|---|---|
| **Senha do master gerenciada pelo RDS** (`--manage-master-user-password`) | O RDS cria e guarda a senha no Secrets Manager e a **rotaciona automaticamente** |
| **Segredos de aplicação** | Credenciais do usuário da aplicação, com **rotação automática** por Lambda |
| **Integração** | Aplicação recupera o segredo no startup (ou via RDS Proxy) |

Evite senhas em variáveis de ambiente fixas, repositórios e imagens de contêiner.

```bash
# Rotacionar a senha master gerenciada pelo RDS sob demanda
aws rds modify-db-instance --db-instance-identifier loja-prod --manage-master-user-password --rotate-master-user-password --apply-immediately
```

## Camada 5 — Auditoria e proteção

| Mecanismo | Função |
|---|---|
| **CloudTrail** | Registra chamadas à API do RDS |
| **Logs do engine** (audit, error, slow query, general) exportados ao CloudWatch Logs | Detecção e investigação |
| **Database Activity Streams** (Aurora e alguns engines) | Fluxo de atividade de banco quase em tempo real, via Kinesis, para auditoria independente |
| **pgAudit / MariaDB Audit Plugin / SQL Server Audit** | Auditoria no nível do SQL |
| **Deletion protection** | Impede exclusão acidental da instância |
| **AWS Config** | Regras como `rds-instance-public-access-check`, `rds-storage-encrypted`, `rds-multi-az-support` |
| **Security Hub / GuardDuty RDS Protection** | Postura e detecção de anomalias de login |
| **Tags + SCP** | Governança em escala (negar banco sem criptografia ou público) |

```json
{
  "Effect": "Deny",
  "Action": ["rds:CreateDBInstance", "rds:RestoreDBInstanceFromDBSnapshot"],
  "Resource": "*",
  "Condition": { "Bool": { "rds:StorageEncrypted": "false" } }
}
```

## Checklist de segurança

- [ ] Subnets privadas; `PubliclyAccessible=false`.
- [ ] SG permitindo somente os SGs da aplicação.
- [ ] Criptografia em repouso (CMK) e **TLS obrigatório**.
- [ ] Usuários de aplicação com privilégio mínimo; master user só para administração.
- [ ] Senha master gerenciada pelo Secrets Manager com rotação; IAM auth quando viável.
- [ ] Logs de auditoria e de erros no CloudWatch; alarmes de falha de login.
- [ ] Deletion protection, backups e testes de restauração.
- [ ] AWS Config/SCP impedindo configurações inseguras.
- [ ] CA do RDS e certificados dentro da validade.

## Exemplo prático

Cenário: aplicação em ECS acessando PostgreSQL no RDS.

1. RDS em subnets privadas, SG-bd aceitando 5432 apenas de SG-app.
2. Criptografia com CMK `alias/rds-prod`; `rds.force_ssl=1`.
3. Senha master gerenciada no Secrets Manager (rotação automática).
4. A task role ECS tem `rds-db:connect` para o usuário `app_iam`; a aplicação gera o token e conecta com `sslmode=verify-full`.
5. Logs `postgresql` + `pgaudit` exportados; alarme para `FATAL: password authentication failed` repetido.
6. SCP negando instâncias sem criptografia ou com acesso público.

## Mapa de controles e prioridade de implementação

| Prioridade | Controle | Mitiga | Esforço |
|---|---|---|---|
| 1 | Não público + SG restrito | Acesso indevido pela internet | Baixo |
| 2 | Criptografia em repouso (KMS) | Vazamento de snapshot/disco | Baixo (na criação) |
| 3 | TLS obrigatório | Interceptação | Baixo |
| 4 | Secrets Manager com rotação | Senhas fixas e vazadas | Médio |
| 5 | IAM database authentication | Gestão de senhas | Médio |
| 6 | Logs de auditoria + alertas | Detecção | Médio |
| 7 | Backups com acesso restrito e cópia isolada | Ransomware | Médio |

> [!warning] Valores, limites e preços mudam; os exemplos deste material não foram executados. Parâmetros de SSL e recursos de auditoria variam por engine; consulte a documentação.

```
 Aplicação ──► (SG: 5432 só do SG do app) ──► RDS (subnet privada)
     │                                           │
     └─ segredo via Secrets Manager (rotação) ───┤ KMS em repouso
        ou token IAM (15 min)                    │ TLS em trânsito
                                                 └─ logs ─► CloudWatch ─► alarmes
```

### Árvore de decisão: autenticação

```
Quantas conexões novas por segundo?
├─ Muitas (centenas+) ─► senha via Secrets Manager (token IAM tem limite de taxa)
└─ Moderadas ─► IAM auth é viável
     └─ Precisa rotação automática sem mudar código? ─► Secrets Manager + rotation
```

## Pontos que surpreendem

- **Criptografia não pode ser ligada em instância já criada**: é preciso copiar um snapshot criptografado e restaurar.
- Snapshots de bancos criptografados só são compartilhados entre contas com chave KMS **gerenciada pelo cliente** compartilhada.
- Security Group ≠ authN: mesmo na rede correta, o usuário/papel precisa de permissão.

## CLI comentado

```bash
# Impede acesso público e confirma criptografia
aws rds describe-db-instances --db-instance-identifier prod-db \
  --query 'DBInstances[0].[PubliclyAccessible,StorageEncrypted,KmsKeyId]'

# Cria segredo com rotação gerenciada
aws secretsmanager rotate-secret --secret-id prod/db/app \
  --rotation-rules AutomaticallyAfterDays=30

# Gera token IAM de conexão (válido por ~15 minutos)
aws rds generate-db-auth-token --hostname prod-db.xxxx.sa-east-1.rds.amazonaws.com \
  --port 5432 --username app_iam
```

## Troubleshooting

| Sintoma | Causa provável | Ação |
|---|---|---|
| Timeout de conexão | SG/subnet/rota errados | Revisar SG, NACL e rota |
| `SSL required` | Parâmetro exige TLS | Conectar com TLS e CA bundle da AWS |
| Falha de IAM auth | Usuário DB sem plugin/grant ou policy ausente | Conceder `rds_iam` e `rds-db:connect` |
| Senha rotacionada quebrou app | App cacheia a senha antiga | Ler o segredo dinamicamente |

## Custo

Segredos têm custo mensal por segredo e por chamada de API; chaves KMS próprias cobram por chave e requisição. É pequeno frente ao custo de um incidente; centralize chaves e segredos por ambiente para não multiplicar custos.

## Erros comuns e armadilhas

- **Banco público com SG aberto à internet.**
- **Esquecer de criar a instância criptografada** (não dá para ligar depois).
- **TLS opcional** e clientes sem validação de certificado.
- **Senha master em código/variáveis** e sem rotação.
- **Usar o master user na aplicação.**
- **IAM auth sem TLS ou com taxa de conexões acima do limite** (use RDS Proxy).
- **Chave KMS apagada/desabilitada:** instância e backups inacessíveis.
- **Snapshot compartilhado publicamente por engano.**
- **Ignorar a expiração/rotação da CA do RDS:** conexões TLS passam a falhar.
- **Sem deletion protection** em produção.

## 🧩 Quiz de Fixação

1. É possível ativar a criptografia em repouso em uma instância RDS já criada?
2. Como funciona a IAM database authentication e quais seus benefícios?
3. Como evitar que a senha do master user fique em código?

**Respostas:**
1) Não. É preciso criar um snapshot, copiá-lo com criptografia (chave KMS) e restaurar uma nova instância a partir da cópia.
2) A aplicação gera um token temporário (15 min) com credenciais IAM e o usa como senha, sobre TLS. Evita senhas fixas, centraliza o controle no IAM e gera auditoria no CloudTrail.
3) Usando `--manage-master-user-password` (RDS gerencia e rotaciona a senha no Secrets Manager) e recuperando o segredo em tempo de execução, em vez de gravá-lo em código ou variáveis.

**Questões complementares:**

4. Como criptografar uma instância RDS que foi criada sem criptografia?
5. Quando preferir Secrets Manager a IAM authentication?
6. Qual o primeiro controle a implementar e por quê?

**Respostas das questões complementares:**
4) Criar um snapshot, copiá-lo com criptografia KMS e restaurar a partir da cópia em uma nova instância.
5) Quando há muitas conexões novas por segundo, pois a autenticação IAM tem limites de taxa; o Secrets Manager também oferece rotação automática.
6) Bloquear acesso público e restringir o Security Group ao app: elimina a maior superfície de ataque com baixo esforço.
