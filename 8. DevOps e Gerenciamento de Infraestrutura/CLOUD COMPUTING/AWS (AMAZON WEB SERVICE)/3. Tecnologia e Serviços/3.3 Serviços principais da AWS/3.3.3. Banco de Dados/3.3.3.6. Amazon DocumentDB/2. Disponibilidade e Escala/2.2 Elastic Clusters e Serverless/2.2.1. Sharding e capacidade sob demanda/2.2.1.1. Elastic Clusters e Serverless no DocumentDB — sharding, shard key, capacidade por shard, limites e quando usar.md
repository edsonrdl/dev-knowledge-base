### Elastic Clusters e Serverless no DocumentDB — sharding, shard key, capacidade por shard, limites e quando usar

> [!warning] Aviso
> Elastic Clusters e DocumentDB Serverless são **recursos mais recentes**, com limites, versões da API, recursos suportados e preços que mudam e que diferem dos clusters baseados em instâncias. Os números são **ordens de grandeza**. **Confirme disponibilidade, limites e restrições na documentação antes de adotar.** Os comandos **não foram executados**.

Um cluster DocumentDB baseado em instâncias tem **uma única primária** para escritas: o teto de escrita é o de uma instância. Quando a carga de escrita ou o volume de dados excede esse teto, a solução é **sharding** — dividir os dados em várias partições, cada uma com sua própria computação. O **DocumentDB Elastic Clusters** entrega isso de forma **gerenciada**, escalando escrita e armazenamento de forma quase linear. Já o **DocumentDB Serverless** ajusta automaticamente a capacidade de **computação** de clusters baseados em instâncias. Esta nota explica ambos, como **escolher a shard key**, a **capacidade** e as **limitações**.

**Analogia:** o cluster baseado em instâncias é **uma única caixa registradora com muitos auxiliares de leitura**. O Elastic Cluster é **um supermercado com várias caixas** (shards): cada cliente (documento) é encaminhado à caixa certa pela sua **chave**, e novas caixas podem ser abertas conforme a fila cresce. O Serverless é **uma caixa que muda de tamanho sozinha** conforme o movimento.

## Quando o cluster tradicional não basta

| Sintoma | Causa | Solução |
|---|---|---|
| CPU da **primária** saturada por escritas | Teto de escrita de uma instância | **Elastic Clusters** (sharding) |
| Volume de dados na casa de dezenas/centenas de TiB com working set grande | Limite de memória/armazenamento por cluster | Elastic Clusters |
| Escritas em picos extremos | Primária única | Elastic Clusters / fila na frente |
| Carga muito variável (dia vs noite) | Capacidade fixa | **Serverless** |
| Leituras demais | — | Réplicas (cluster tradicional) |

Antes de adotar sharding, esgote: índices adequados, modelagem, instância maior, réplicas, cache e filas. Sharding adiciona **complexidade** (shard key, restrições de consulta).

## Elastic Clusters: como funcionam

```
 Aplicação ──► endpoint do Elastic Cluster ──► roteadores gerenciados ──► Shard 1 (computação + armazenamento)
                                                                       ├─► Shard 2
                                                                       ├─► Shard 3
                                                                       └─► ... Shard N
```

| Elemento | Descrição |
|---|---|
| **Shard** | Partição com computação própria (vCPUs) e seu volume distribuído de 6 cópias |
| **Número de shards** | Configurável (por exemplo de 1 a dezenas) |
| **Capacidade por shard** | Em **vCPUs** (por exemplo 2, 4, 8, 16, 32, 64 vCPUs) |
| **Réplicas por shard** | Configuráveis para alta disponibilidade e leitura |
| **Armazenamento** | Distribuído, automático, até petabytes no total |
| **Roteamento** | O serviço roteia cada operação ao(s) shard(s) conforme a **shard key** |
| **Escala** | Altere o nº de shards e a capacidade **sem recriar** o cluster (com redistribuição de dados) |
| **Endpoint único** | A aplicação conecta a um endpoint, sem conhecer os shards |

### Shard key

Cada **coleção shardada** precisa de uma **shard key**: o campo (ou campos) cujo valor determina **em qual shard** o documento fica.

| Critério de uma boa shard key | Por quê |
|---|---|
| **Alta cardinalidade** | Muitos valores distintos → distribuição uniforme |
| **Distribuição uniforme de acessos** | Evita "hot shard" |
| **Presente nas consultas frequentes** | Consultas com a shard key vão a **um** shard; sem ela, vão a **todos** (*scatter-gather*) |
| **Imutável (ou raramente muda)** | Alterar a chave exige mover o documento |
| **Não monotônica** | Chaves crescentes (timestamp, ObjectId) concentram escrita no último shard |

Exemplos:

| Caso | Shard key sugerida | Observação |
|---|---|---|
| Pedidos multi-tenant | `tenantId` (ou `tenantId` + `pedidoId`) | Isola o tenant; cuidado com tenants gigantes |
| Eventos de dispositivos | `dispositivoId` (ou hash) | Evite só `timestamp` |
| Perfis de usuário | `usuarioId` | Cardinalidade alta |
| Séries temporais | `sensorId` + bucket de tempo | Evita hot shard |

```javascript
// Criar uma coleção shardada (comandos específicos do Elastic Clusters / mongosh)
sh.shardCollection("loja.pedidos", { tenantId: "hashed" })     // hash distribui uniformemente (se suportado)
// ou: sh.shardCollection("loja.eventos", { dispositivoId: 1 })
```

(A sintaxe exata e as opções suportadas dependem da versão; confirme.)

## Consultas em um cluster shardado

| Tipo | Comportamento | Custo |
|---|---|---|
| **Com a shard key** (`{tenantId: "T1", ...}`) | Roteada a **um shard** | Baixo, escala linearmente |
| **Sem a shard key** | **Scatter-gather**: consulta todos os shards e consolida | Alto; evita em caminhos quentes |
| **Escritas com shard key** | Um shard | Escala |
| **Agregações** | Parte executa em cada shard, consolidada no roteador | Cuidado com estágios que forçam o merge (por exemplo `$lookup`) |
| **Índices** | Cada shard mantém seus índices; incluir a shard key em índices compostos | — |
| **Transações** | Suporte e restrições específicos (verifique) | — |

Regra: **projete as consultas principais para incluir a shard key.**

## Limitações e diferenças

| Aspecto | Observação |
|---|---|
| **API/recursos** | Subconjunto dos recursos do cluster baseado em instâncias (versões da API, change streams, transações, alguns operadores, `$lookup` entre coleções shardadas etc., conforme a versão) |
| **Replicação global** | Global Clusters podem **não** estar disponíveis para Elastic Clusters (confirme) |
| **Shard key** | Escolha cuidadosa; mudar exige migração (recriar coleção) |
| **Tamanho/limite de shards** | Limites máximos de shards e de vCPU por shard |
| **Custos** | Pago por vCPU de shard-hora, armazenamento, I/O e backup |
| **Migração** | De cluster tradicional para elastic: exportar/importar (DMS, `mongodump/mongorestore`) com a shard key definida |
| **Backups** | Snapshots e restauração para novo Elastic Cluster; PITR conforme suporte |

## DocumentDB Serverless

Computação **sob demanda** para clusters baseados em instâncias: as instâncias "serverless" escalam em **DCUs** (*DocumentDB Capacity Units*; 1 DCU ≈ 2 GiB de memória com CPU e rede proporcionais) entre um mínimo e um máximo configurados.

| Característica | Detalhe |
|---|---|
| **Escala** | Em segundos, em passos pequenos (por exemplo 0,5 DCU), sem interromper conexões |
| **Config** | `MinCapacity` e `MaxCapacity` (por cluster) |
| **Misto** | Pode combinar instâncias provisionadas e serverless no cluster |
| **Armazenamento** | Igual ao cluster tradicional (volume compartilhado) |
| **Cobrança** | **DCU-hora** (por segundo) + armazenamento + I/O (ou I/O-Optimized) |
| **Bom para** | Cargas variáveis, multi-tenant, dev/test, picos imprevisíveis |
| **Cuidado** | Capacidade mínima muito baixa deixa o cache frio; a capacidade máxima limita memória e conexões; compare custo com instâncias reservadas |
| **Escala de escrita** | Continua limitada a **uma primária** (vertical): para além disso, Elastic Clusters |

```bash
aws docdb create-db-cluster --db-cluster-identifier app-docdb-sv --engine docdb \
  --serverless-v2-scaling-configuration MinCapacity=1,MaxCapacity=32 ...
aws docdb create-db-instance --db-instance-identifier app-docdb-sv-1 --db-cluster-identifier app-docdb-sv \
  --engine docdb --db-instance-class db.serverless
```

(Confirme nomes de parâmetros e disponibilidade na documentação atual.)

## Como escolher

```
Carga cabe em uma primária (com réplicas para leitura)?
   ├─ Sim, e a carga é estável → cluster baseado em instâncias (reservas)
   ├─ Sim, mas variável         → cluster com instâncias Serverless
   └─ Não (escrita/volume além de uma primária) → Elastic Clusters (defina bem a shard key)
Precisa de DR multirregião? → Global Cluster (instâncias) ou outra estratégia para Elastic (confirme suporte)
```

| Critério | **Instâncias** | **Serverless** | **Elastic Clusters** |
|---|---|---|---|
| Escala de escrita | Vertical | Vertical (automática) | **Horizontal (shards)** |
| Escala de leitura | Réplicas (até 15) | Réplicas | Réplicas por shard |
| Armazenamento | Dezenas de TiB | Idem | **Petabytes** |
| Administração | Média | Baixa | Baixa/média (shard key) |
| Compatibilidade | **Mais ampla** | Ampla | Subconjunto |
| Custo | Reservas | Variável, paga o uso | vCPU de shard |

## Exemplo prático

SaaS multi-tenant de eventos de dispositivos IoT com 150 mil escritas/s e 80 TiB, crescendo 10% ao mês:

1. O cluster tradicional chega a 85% de CPU na primária mesmo na maior classe: **migrar para Elastic Cluster**.
2. **Shard key:** `dispositivoId` (hash) — alta cardinalidade e distribuição uniforme; consultas principais sempre incluem `dispositivoId` e intervalo de tempo.
3. Configuração: 12 shards de 32 vCPUs, 1 réplica por shard em outra AZ; escala planejada para 18 shards em 6 meses.
4. **Padrão bucket:** um documento por dispositivo e por hora com array de medições (reduz o número de documentos e escritas).
5. **TTL** de 90 dias para dados brutos; agregados diários em coleção de resumo; histórico exportado para S3 (Parquet).
6. Migração com **DMS** (full load + CDC) para o cluster elástico, validação de contagens e janela de corte curta.
7. Monitoramento: distribuição por shard, CPU por shard, latência p99 por tipo de consulta; alarme de "hot shard".
8. Reavaliação de custo trimestral e teste de restauração.

## Erros comuns e armadilhas

- **Adotar sharding cedo demais**, sem esgotar índices, modelagem e instâncias maiores.
- **Shard key monotônica** (timestamp, ObjectId): hot shard.
- **Shard key de baixa cardinalidade** (status, país).
- **Consultas sem a shard key** em caminhos quentes (scatter-gather).
- **Presumir paridade total de recursos** com o cluster tradicional.
- **Não planejar a migração** (shard key definida na carga).
- **Serverless com `MinCapacity` muito baixo** e cache frio constante.
- **Esperar que Serverless escale a escrita horizontalmente.**
- **Ignorar limites** (shards, vCPU por shard, conexões).
- **Não testar o balanceamento** com dados reais (skew).

## 🧩 Quiz de Fixação

1. Que problema os Elastic Clusters resolvem e como?
2. O que caracteriza uma boa shard key?
3. O que acontece com uma consulta que não inclui a shard key?
4. O Serverless escala a escrita horizontalmente?

**Respostas:**
1) O teto de escrita e de armazenamento de uma única primária: dividem os dados em shards, cada um com computação e armazenamento próprios, roteando as operações pela shard key e permitindo escalar escrita e volume horizontalmente.
2) Alta cardinalidade, distribuição uniforme de acessos, presença nas consultas frequentes, imutabilidade e não ser monotônica (evita hot shard).
3) Ela é enviada a todos os shards (scatter-gather) e o resultado é consolidado, o que custa mais e escala pior.
4) Não: o Serverless ajusta automaticamente a computação (DCUs) de instâncias, mas a escrita continua limitada a uma primária; para escala horizontal de escrita usam-se Elastic Clusters.
