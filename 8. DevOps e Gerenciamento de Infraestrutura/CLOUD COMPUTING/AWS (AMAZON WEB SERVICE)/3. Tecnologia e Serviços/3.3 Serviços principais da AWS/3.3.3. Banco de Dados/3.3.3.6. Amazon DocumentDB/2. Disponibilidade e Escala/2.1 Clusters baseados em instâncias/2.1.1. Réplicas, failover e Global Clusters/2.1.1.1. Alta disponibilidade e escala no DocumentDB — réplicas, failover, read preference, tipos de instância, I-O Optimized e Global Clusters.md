### Alta disponibilidade e escala no DocumentDB — réplicas, failover, read preference, tipos de instância, I/O-Optimized e Global Clusters

> [!warning] Aviso
> Tempos de failover, número máximo de réplicas, regiões suportadas em Global Clusters, tipos de instância e modelos de cobrança (Standard e I/O-Optimized) mudam. Os números são **ordens de grandeza**. **Confirme na documentação.** Os comandos **não foram executados**.

Em um cluster DocumentDB baseado em instâncias, a **alta disponibilidade** e a **escala de leitura** vêm de réplicas que compartilham o volume do cluster; a **escala de escrita** é vertical (instância maior) ou, para além disso, vem dos **Elastic Clusters**; a **resiliência regional** vem dos **Global Clusters**. Esta nota cobre cada mecanismo: **réplicas e failover**, **read preference** na aplicação, **tipos de instância**, **modelos de cobrança** (**Standard** vs **I/O-Optimized**), **Global Clusters** e boas práticas de resiliência.

**Analogia:** o cluster é um **balcão com um caixa (primária) e atendentes de consulta (réplicas)** lendo o mesmo livro-razão. Se o caixa adoecer, um atendente assume em segundos. Um Global Cluster é uma **filial em outro país** com cópia quase instantânea do mesmo livro-razão.

## Réplicas e failover

```
 ANTES:   PRIMÁRIA (AZ-a)     RÉPLICA 1 (AZ-b) prioridade 0     RÉPLICA 2 (AZ-c) prioridade 1
 FALHA:   primária cai ─► DocumentDB promove a réplica de maior prioridade ─► endpoint do cluster passa a apontar para ela
```

| Característica | Detalhe |
|---|---|
| **Réplicas** | Até **15** por cluster; compartilham o volume; lag de ms |
| **Distribuição** | Em pelo menos 2 AZs (idealmente 3) |
| **Failover automático** | Ao detectar falha da primária, promove uma réplica (por **prioridade de promoção** 0-15) em geralmente **menos de 30 s a poucos minutos** |
| **Sem réplicas** | Se não existe réplica, uma nova instância é criada (tempo maior, indisponibilidade) |
| **Failover manual** | `failover-db-cluster` para testes |
| **Endpoints** | **Cluster endpoint** (aponta para a primária atual) e **reader endpoint** (balanceia entre réplicas) |
| **Aplicação** | Usa drivers com **reconexão automática** e a string de conexão com `replicaSet=rs0` |

```bash
# Testar failover
aws docdb failover-db-cluster --db-cluster-identifier catalogo-docdb --target-db-instance-identifier catalogo-docdb-2
# Ajustar a prioridade de promoção
aws docdb modify-db-instance --db-instance-identifier catalogo-docdb-2 --promotion-tier 0 --apply-immediately
```

Boas práticas: **pelo menos uma réplica em outra AZ** com classe igual à primária; testes periódicos de failover; monitorar `ReplicaLag`.

## Read preference (escala de leitura)

O driver escolhe de onde ler conforme a **read preference**:

| Valor | Comportamento | Uso |
|---|---|---|
| `primary` (padrão) | Lê da primária | Consistência máxima |
| `primaryPreferred` | Primária, ou réplica se indisponível | Tolerância a falha |
| `secondary` | Só réplicas | Relatórios, leituras pesadas |
| `secondaryPreferred` | Réplicas, ou primária se não houver | **Escalar leituras** (padrão recomendado para leituras) |
| `nearest` | Menor latência | Multi-região |

```
mongodb://usuario:senha@cluster.docdb.amazonaws.com:27017/?tls=true&replicaSet=rs0&readPreference=secondaryPreferred&retryWrites=false
```

Atenção: leituras em réplicas são **eventualmente consistentes** (lag de ms): após gravar, ler da réplica pode não mostrar a escrita; use `primary` quando for necessário o dado mais recente (read-your-writes).

## Escala: vertical e horizontal

| Dimensão | Como |
|---|---|
| **Vertical (escrita e memória)** | Trocar a classe das instâncias (a mudança exige failover/reinício) |
| **Leitura** | Adicionar réplicas (até 15) e usar `secondaryPreferred`; Auto Scaling de réplicas (Application Auto Scaling) |
| **Armazenamento** | Automático (cresce com o volume) |
| **Escrita além de uma primária** | **Elastic Clusters** (sharding; nota própria) |
| **Capacidade variável** | **DocumentDB Serverless** (recurso mais recente) |
| **Cache** | ElastiCache para resultados repetidos |

### Classes de instância

| Família | Perfil | Observação |
|---|---|---|
| **db.t3 / db.t4g** | Burstable | Dev/test; créditos de CPU |
| **db.r5 / db.r6g / db.r7g / db.r8g** | Memory optimized | Produção; Graviton (`g`) com melhor custo-benefício |
| **db.r6gd / db.r7gd (NVMe)** | Memória + armazenamento local | Cache de leitura (*Optimized Reads*), temp |
| **db.x2g** | Memória extra | Working sets grandes |

O **working set** (dados e índices acessados com frequência) deve caber na memória (buffer cache); acompanhe `BufferCacheHitRatio`.

## Modelos de cobrança: Standard × I/O-Optimized

| Critério | **Standard** | **I/O-Optimized** |
|---|---|---|
| Armazenamento | Menor preço por GB | Maior |
| Instâncias | Menor | Maior |
| I/O | Pago por **milhão de requisições** | **Sem cobrança de I/O** |
| Melhor para | I/O baixo a moderado | Cargas intensas em I/O (quando I/O > ~25% da conta) |
| Previsibilidade | Custo varia com I/O | **Previsível** |

Pode-se alternar entre os modos (com limite de frequência). Use o Cost Explorer (`StorageIOUsage`) para decidir.

## Global Clusters (multirregião)

Um Global Cluster tem uma **região primária** (leitura/escrita) e até **cinco regiões secundárias** (somente leitura), com replicação em nível de **armazenamento** (lag tipicamente < 1 s).

```
 Primária (sa-east-1) ══ replicação de armazenamento ══► Secundária (us-east-1)  ═►  Secundária (eu-west-1)
   leitura/escrita                                         leitura local            leitura local
```

| Característica | Detalhe |
|---|---|
| **Uso** | Leitura local de baixa latência e **DR** com RPO de segundos |
| **Failover** | **Switchover** gerenciado (planejado, sem perda) e **failover** (não planejado, pode perder dados mínimos) |
| **RTO** | Cerca de 1 minuto para o banco (mais o redirecionamento da aplicação) |
| **Custo** | Instâncias na secundária + replicação de I/O + transferência entre regiões |
| **Limitações** | Verifique versões, recursos (change streams, elastic clusters) e regiões |
| **Aplicação** | Endpoint por região; Route 53 para apontar ao primário atual |

```bash
aws docdb create-global-cluster --global-cluster-identifier catalogo-global --source-db-cluster-identifier arn:aws:rds:sa-east-1:111122223333:cluster:catalogo-docdb
aws docdb create-db-cluster --region us-east-1 --db-cluster-identifier catalogo-docdb-us --global-cluster-identifier catalogo-global --engine docdb ...
aws docdb switchover-global-cluster --global-cluster-identifier catalogo-global --target-db-cluster-identifier arn:aws:rds:us-east-1:111122223333:cluster:catalogo-docdb-us
```

## Resiliência na aplicação

| Prática | Detalhe |
|---|---|
| **Drivers com retry** | Reconectar e repetir operações idempotentes após failover |
| **`retryWrites`** | O DocumentDB não suporta *retryable writes* em algumas versões: defina `retryWrites=false` conforme a documentação e implemente retry na aplicação |
| **Timeouts** | `serverSelectionTimeoutMS`, `connectTimeoutMS`, `socketTimeoutMS` ajustados |
| **Pool de conexões** | Limite de `maxPoolSize` coerente com o limite de conexões por instância |
| **Idempotência** | Operações repetidas não duplicam efeitos (chaves naturais, upserts) |
| **Degradação** | Cache e fila na frente em caso de indisponibilidade |
| **Teste de failover** | Trimestral, medindo o RTO da aplicação |

## Monitoramento de disponibilidade e escala

| Métrica | Uso |
|---|---|
| `ReplicaLag` / `DBInstanceReplicaLag` | Atraso das réplicas |
| `CPUUtilization`, `FreeableMemory`, `BufferCacheHitRatio` | Saúde e working set |
| `DatabaseConnections` | Conexões (limite por classe) |
| `VolumeBytesUsed` | Crescimento do volume |
| `DiskQueueDepth`, `ReadIOPS/WriteIOPS` | I/O |
| `OpcountersQuery/Insert/Update/Delete` | Carga por tipo |
| `GlobalClusterReplicationLag` | Lag entre regiões |
| Eventos RDS/DocDB | Failover, manutenção |

Alarmes: CPU > 80%, `FreeableMemory` baixa, `ReplicaLag` > 1 s sustentado, conexões > 80% do limite.

## Exemplo prático

Cluster de catálogo para um marketplace com picos em campanhas:

1. Primária `db.r6g.2xlarge` (AZ-a) + 2 réplicas `db.r6g.xlarge` (AZ-b e AZ-c); réplica de AZ-b com **promotion tier 0**.
2. Aplicação: leituras com `secondaryPreferred`; escritas na primária; reads críticos pós-escrita com `primary`.
3. **Auto Scaling** de réplicas de 2 a 6 por `CPUUtilization` média > 60% durante campanhas.
4. **I/O-Optimized** após constatar I/O de 35% da fatura.
5. **Global Cluster** com secundária em `us-east-1` para clientes nos EUA (leitura local) e DR (RPO < 1 s).
6. Failover testado mensalmente em staging e trimestralmente em produção; drivers com timeouts e retry.
7. Alarmes e runbook: `ReplicaLag`, `BufferCacheHitRatio` < 95%, `DatabaseConnections`.

## Erros comuns e armadilhas

- **Sem réplica em outra AZ:** failover demorado e indisponível.
- **Usar o endpoint de instância na aplicação.**
- **Ler sempre da primária** e sobrecarregá-la, ou **ler da réplica** esperando consistência imediata.
- **Aplicação sem reconexão** e sem retry após failover.
- **Classe da réplica menor que a primária:** ao assumir, não aguenta.
- **Working set maior que a memória** (cache hit baixo, I/O alto).
- **Achar que Global Cluster é backup.**
- **Ignorar o custo de I/O** no modo Standard.
- **Conexões excessivas** (limite por classe) sem pool.
- **Escalar leitura quando o gargalo é escrita** (ou vice-versa).

## 🧩 Quiz de Fixação

1. Como funciona o failover no DocumentDB e o que a aplicação deve fazer?
2. Para que serve `readPreference=secondaryPreferred` e qual seu risco?
3. Quando migrar de Standard para I/O-Optimized?
4. Qual a função de um Global Cluster?

**Respostas:**
1) Uma réplica (de acordo com a prioridade de promoção) é promovida a primária em dezenas de segundos e o endpoint do cluster passa a apontar para ela; a aplicação deve usar o cluster/reader endpoint, ter reconexão automática, timeouts e retry com operações idempotentes.
2) Lê das réplicas quando disponíveis (e da primária se não houver), escalando as leituras; o risco é a consistência eventual (lag de ms), em que uma leitura logo após a escrita pode não ver o dado novo.
3) Quando o custo de I/O representa uma parte significativa da fatura (da ordem de um quarto) ou se quer custo previsível, pois no I/O-Optimized não há cobrança por requisição de I/O.
4) Replicar o cluster para até cinco regiões secundárias somente leitura, com lag de menos de 1 s, oferecendo leitura local de baixa latência e recuperação de desastres regional.
