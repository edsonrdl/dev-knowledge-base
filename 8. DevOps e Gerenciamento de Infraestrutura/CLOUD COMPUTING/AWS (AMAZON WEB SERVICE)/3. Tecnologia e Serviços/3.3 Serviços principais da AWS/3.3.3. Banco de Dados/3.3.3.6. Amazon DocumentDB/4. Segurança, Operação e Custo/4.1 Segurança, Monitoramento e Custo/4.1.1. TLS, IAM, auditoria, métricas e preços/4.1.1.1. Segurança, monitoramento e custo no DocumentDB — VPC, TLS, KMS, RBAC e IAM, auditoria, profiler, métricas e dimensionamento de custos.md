### Segurança, monitoramento e custo no DocumentDB — VPC, TLS, KMS, RBAC e IAM, auditoria, profiler, métricas e dimensionamento de custos

> [!warning] Aviso
> Opções de autenticação (usuário/senha, IAM), parâmetros de auditoria e profiler, métricas, tipos de instância e preços do DocumentDB mudam por versão e modo. **Nenhum valor numérico é oficial.** Confirme na documentação e na calculadora da AWS. Os comandos **não foram executados**.

Fechamos o DocumentDB com o que sustenta a operação em produção: **segurança em camadas** (rede, criptografia, autenticação, autorização, auditoria), **monitoramento** (métricas, profiler, logs, alarmes) e **custo** (instâncias, armazenamento, I/O, backups, reservas e dimensionamento). Muito do que vale para o RDS e o Aurora se aplica aqui, com as particularidades do DocumentDB e do protocolo MongoDB.

**Analogia:** é a **gestão de um cofre bancário**: a rede é o prédio com portaria, a criptografia é o cofre, a autenticação e as roles são os crachás por departamento, a auditoria e o profiler são as câmeras, e o painel de custos é o balanço mensal.

## Segurança em camadas

### 1. Rede

| Prática | Detalhe |
|---|---|
| **VPC e subnets privadas** | O DocumentDB **não tem endpoint público**; o cluster vive em um **subnet group** de subnets privadas em várias AZs |
| **Security Group** | Libera a porta **27017** somente a partir dos SGs da aplicação (SG-a-SG) |
| **Acesso administrativo** | Via bastion/SSM Session Manager, VPN, Direct Connect ou peering; evite túneis permanentes abertos |
| **Cross-account/região** | Peering/Transit Gateway/PrivateLink; endpoints gerenciados |
| **Isolamento** | Clusters separados por ambiente/domínio sensível |

```
 App (SG-app) ──27017/TLS──► DocumentDB (SG-docdb: entrada somente de SG-app) — subnets privadas
```

Base de rede: [[8. DevOps e Gerenciamento de Infraestrutura/CLOUD COMPUTING/AWS (AMAZON WEB SERVICE)/3. Tecnologia e Serviços/3.3 Serviços principais da AWS/3.3.4. Rede/3.3.4.1. Amazon VPC/0 Amazon VPC (Tópicos )|Amazon VPC]].

### 2. Criptografia

| Tipo | Como |
|---|---|
| **Em repouso** | AES-256 com **KMS** (`--storage-encrypted --kms-key-id`); cobre volume, backups, snapshots e logs; **definir na criação** (não dá para ativar depois; migre via snapshot → cópia criptografada → restore) |
| **Em trânsito** | **TLS** habilitado por padrão (parâmetro `tls`); clientes usam o **bundle de CA** (`global-bundle.pem`) e `tls=true` |
| **Campo a campo** | **Client-Side Field Level Encryption (CSFLE)** do driver MongoDB (quando suportado) ou criptografia na aplicação para dados muito sensíveis |
| **Chaves** | CMK com política restrita, rotação; cuidado com exclusão (dados inacessíveis) — veja [[8. DevOps e Gerenciamento de Infraestrutura/CLOUD COMPUTING/AWS (AMAZON WEB SERVICE)/2. Segurança e Conformidade/2.3 Capacidades de gerenciamento de acesso da AWS/2.3.2. Serviços de segurança/2.3.2.7. AWS Key Management Service (KMS)|AWS KMS]] |

### 3. Autenticação e autorização

| Mecanismo | Descrição |
|---|---|
| **Usuário e senha (SCRAM)** | Padrão; o usuário master é criado na criação; senha master gerenciada pelo **Secrets Manager** (`--manage-master-user-password`) com rotação |
| **IAM authentication** (`MONGODB-AWS`) | Credenciais temporárias via roles IAM, sem senha fixa (em versões/modos suportados; confirme) |
| **RBAC (roles do banco)** | Roles integradas (`read`, `readWrite`, `dbAdmin`, `userAdmin`, `readAnyDatabase`, etc.) por banco; princípio do menor privilégio |
| **IAM (API)** | Controla quem administra clusters, snapshots, parameter groups (`rds:*`/`docdb:*` e condições) |
| **SCP/Config** | Exigir criptografia, TLS, proteção contra exclusão, bloquear clusters sem backup |

```javascript
// Criar um usuário de aplicação com permissão de leitura/escrita apenas no banco "loja"
use admin
db.createUser({ user: "app_loja", pwd: passwordPrompt(), roles: [ { role: "readWrite", db: "loja" } ] })
// Usuário somente leitura para relatórios
db.createUser({ user: "relatorios", pwd: passwordPrompt(), roles: [ { role: "read", db: "loja" } ] })
```

Boas práticas: **nunca** usar o master na aplicação; um usuário por aplicação/serviço; rotação de segredos; revisão de acessos.

### 4. Auditoria

| Registro | Como habilitar | Conteúdo |
|---|---|---|
| **Audit logs** | Parâmetro `audit_logs = enabled` (e `audit_logs` com eventos: `ddl`, `dml_read`, `dml_write`, `authenticate`, `authCheck`...) + exportar para CloudWatch Logs | Autenticações, DDL, operações de dados (volume grande: filtre eventos) |
| **Profiler** | `profiler = enabled`, `profiler_threshold_ms`, `profiler_sampling_rate` | Operações **lentas** (acima do limiar) com plano e tempos |
| **CloudTrail** | Padrão | Chamadas de API (criar/excluir clusters, snapshots, mudanças de parâmetros) |
| **Config / Security Hub** | Regras: criptografia, backups, proteção contra exclusão, acesso público | Conformidade |

```bash
aws docdb modify-db-cluster-parameter-group --db-cluster-parameter-group-name docdb50-prod --parameters \
  "ParameterName=audit_logs,ParameterValue=enabled,ApplyMethod=immediate" \
  "ParameterName=profiler,ParameterValue=enabled,ApplyMethod=immediate" \
  "ParameterName=profiler_threshold_ms,ParameterValue=100,ApplyMethod=immediate"
aws docdb modify-db-cluster --db-cluster-identifier catalogo-docdb \
  --cloudwatch-logs-export-configuration '{"EnableLogTypes":["audit","profiler"]}'
```

## Monitoramento

### Métricas CloudWatch (`AWS/DocDB`)

| Métrica | Interpretação | Alerta típico |
|---|---|---|
| `CPUUtilization` | CPU da instância | > 80% sustentado |
| `FreeableMemory` | Memória livre | Queda contínua; < 10-15% |
| `BufferCacheHitRatio` | % de leituras atendidas pela memória | < 95% (working set não cabe) |
| `DatabaseConnections` | Conexões abertas | Perto do limite da classe |
| `ReplicaLag` / `DBInstanceReplicaLag` | Atraso das réplicas | > 1 s sustentado |
| `VolumeBytesUsed` | Tamanho do volume | Tendência de crescimento |
| `ReadIOPS` / `WriteIOPS`, `VolumeReadIOPs` / `VolumeWriteIOPs` | I/O (inclusive faturado) | Picos; custo de I/O |
| `ReadLatency` / `WriteLatency` | Latência de armazenamento | Subida vs baseline |
| `DiskQueueDepth` | Fila de I/O | Alta e sustentada |
| `OpcountersQuery/Insert/Update/Delete/Command` | Operações por tipo | Mudança de padrão |
| `DocumentsReturned/Inserted/Updated/Deleted` | Volume de documentos | — |
| `CursorsOpen`, `CursorsTimedOut` | Cursores | Vazamento |
| `LowMemThrottleQueueDepth`/`LowMemNumOperationsThrottled` | Operações limitadas por pouca memória | > 0 |

### Diagnóstico de consultas lentas

1. Ligue o **profiler** com limiar (por exemplo 100 ms) e exporte para CloudWatch Logs.
2. Analise o plano: `db.colecao.find(...).explain("executionStats")` → `COLLSCAN`, `docsExamined` ≫ `nReturned`.
3. Verifique **índices** (`$indexStats`), crie/ajuste.
4. Evite agregações pesadas na primária (use réplicas ou materialize).
5. Cheque `BufferCacheHitRatio`, memória e conexões.
6. `db.currentOp()` para operações em andamento (e `killOp` quando necessário).

```javascript
db.currentOp({ secs_running: { $gt: 5 } })       // operações com mais de 5 s
db.pedidos.aggregate([{ $indexStats: {} }])      // uso de cada índice
```

## Custo

| Componente | Observação |
|---|---|
| **Instâncias** | Por hora, por classe; primária **e** réplicas; Graviton (`g`) costuma ser mais econômico |
| **Armazenamento** | GB-mês do volume (cresce automaticamente) |
| **I/O** | **Standard:** por milhão de requisições; **I/O-Optimized:** sem cobrança de I/O (preço de instância e armazenamento maiores) |
| **Backup** | Acima do tamanho do volume, GB-mês; snapshots manuais |
| **Transferência** | Entre AZs/regiões/internet |
| **Elastic Clusters** | vCPU de shard-hora + armazenamento + I/O |
| **Serverless** | DCU-hora |
| **Reservas** | **Reserved Instances** de 1 ou 3 anos para instâncias provisionadas |
| **Global Cluster** | Instâncias na secundária + replicação de I/O + transferência |

### Dimensionamento (sizing)

1. **Working set** (dados e índices acessados com frequência) deve caber na memória: classe com RAM adequada; meta de `BufferCacheHitRatio` > 95-99%.
2. **Conexões:** limite por classe (cada conexão consome memória); use pool.
3. **Réplicas:** pelo menos uma em outra AZ; mais conforme leitura.
4. **Crescimento:** volume cresce sozinho; monitore `VolumeBytesUsed`.
5. **Teste de carga** com consultas e padrões reais.

### Redução de custo

| Alavanca | Efeito |
|---|---|
| **Rightsizing** (reduzir classe/réplicas ociosas) | ~50% por degrau |
| **Graviton** | Melhor custo-benefício |
| **I/O-Optimized** quando I/O > ~25% da fatura | Custo previsível e menor |
| **Reserved Instances** na base estável | Descontos de dezenas de % |
| **Serverless** em cargas variáveis | Paga o que usa |
| **Dev/test** | Instâncias menores, Single-AZ, **parar** o cluster quando possível (o DocumentDB permite parar por até 7 dias) |
| **Índices e consultas eficientes** | Menos I/O e CPU |
| **TTL e limpeza de dados** | Menos armazenamento |
| **Snapshots e retenção** | Reter o necessário; apagar órfãos |
| **Tags, Budgets e Anomaly Detection** | Visibilidade |

```bash
aws docdb stop-db-cluster --db-cluster-identifier catalogo-dev      # para o cluster de desenvolvimento (reinicia sozinho após 7 dias)
aws docdb start-db-cluster --db-cluster-identifier catalogo-dev
```

## Checklist de produção

- [ ] Cluster em subnets privadas; SG restrito à aplicação; **TLS obrigatório** com bundle de CA.
- [ ] Criptografia em repouso (CMK); deletion protection; snapshot final.
- [ ] Senha master gerenciada; **usuários por aplicação** com roles mínimas; IAM auth quando viável.
- [ ] Audit logs e profiler exportados ao CloudWatch Logs (com filtros e retenção).
- [ ] Backup 14-35 dias, cópia cross-region, teste de restauração.
- [ ] Pelo menos 1 réplica em outra AZ (mesma classe); failover testado.
- [ ] Alarmes: CPU, memória, `BufferCacheHitRatio`, conexões, `ReplicaLag`, espaço/tendência, I/O.
- [ ] Índices revisados (`explain`, `$indexStats`).
- [ ] Parameter group versionado em IaC.
- [ ] Orçamentos, tags e revisão mensal de custo/rightsizing.

## Exemplo prático

Hardening e operação do cluster de catálogo:

1. **Rede/criptografia:** subnets privadas; SG-docdb aceitando 27017 só do SG-app; CMK `alias/docdb-prod`; `tls=enabled` e conexões com o CA bundle.
2. **Acesso:** usuários `app_catalogo` (readWrite em `loja`) e `bi_leitura` (read); master apenas em break-glass (senha no Secrets Manager).
3. **Observabilidade:** audit logs de `ddl`, `authenticate` e `dml_write` filtrados; profiler com limiar de 100 ms exportado ao CloudWatch Logs; dashboards de latência p95.
4. **Alarmes:** `BufferCacheHitRatio` < 95% por 15 min, `ReplicaLag` > 1 s, `DatabaseConnections` > 80% do limite, `FreeableMemory` < 15%.
5. **Ajuste:** o profiler mostra `COLLSCAN` em `produtos.find({categoria, preco})`; criar o índice composto `{categoria:1, preco:1}` reduz a latência de 380 ms para 12 ms.
6. **Custo:** I/O era 38% da fatura → migrar para **I/O-Optimized** (economia estimada de 22%); **Reserved Instances** de 1 ano para a primária e uma réplica; ambiente de dev parado à noite e fins de semana.
7. **Governança:** AWS Config exige criptografia, backup ≥ 14 dias e proteção contra exclusão; revisão trimestral de usuários, índices e custo.

## Erros comuns e armadilhas

- **Desabilitar o TLS** ou conectar sem validar o certificado.
- **Usar o usuário master na aplicação.**
- **Cluster sem criptografia em repouso** (não dá para ligar depois).
- **Audit logs de `dml_read` em tudo:** volume e custo enormes.
- **Profiler desligado** até o incidente.
- **Working set maior que a memória** (cache hit baixo, I/O e custo altos).
- **Conexões sem pool** estourando o limite.
- **Ignorar o custo de I/O** no modo Standard.
- **Comprar Reserved Instances antes de dimensionar.**
- **Cluster de dev ligado 24×7.**
- **Sem teste de failover e de restauração.**

## 🧩 Quiz de Fixação

1. Quais camadas de segurança se aplicam a um cluster DocumentDB?
2. Para que servem o profiler e o audit log?
3. Que métrica indica que o working set não cabe na memória?
4. Quando migrar para I/O-Optimized?

**Respostas:**
1) Rede (VPC, subnets privadas, Security Group), criptografia em repouso (KMS) e em trânsito (TLS), autenticação (usuário/senha, IAM) e autorização (RBAC), auditoria (audit logs, CloudTrail) e governança (Config/SCP).
2) O profiler registra operações lentas acima de um limiar (com plano e tempo) para diagnosticar desempenho; o audit log registra autenticações, DDL e operações de dados para conformidade e investigação.
3) `BufferCacheHitRatio` baixo (por exemplo, abaixo de 95%), junto com alto I/O de leitura e memória livre baixa.
4) Quando o custo de I/O representa uma parte relevante da fatura (da ordem de um quarto) ou se quer custo previsível, pois nesse modo não há cobrança por requisição de I/O.
