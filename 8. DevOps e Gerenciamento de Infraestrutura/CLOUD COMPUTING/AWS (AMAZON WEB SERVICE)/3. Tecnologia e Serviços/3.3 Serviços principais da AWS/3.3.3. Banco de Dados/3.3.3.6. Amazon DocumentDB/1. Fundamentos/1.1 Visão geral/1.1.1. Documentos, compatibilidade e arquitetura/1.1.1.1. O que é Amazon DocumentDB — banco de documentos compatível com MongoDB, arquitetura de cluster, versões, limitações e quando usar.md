### O que é Amazon DocumentDB — banco de documentos compatível com MongoDB, arquitetura de cluster, versões, limitações e quando usar

> [!warning] Aviso
> Versões da API do MongoDB suportadas, limites de armazenamento, tipos de instância, modos (instância, elastic clusters, serverless) e preços do DocumentDB mudam. **A compatibilidade com o MongoDB é parcial e varia por versão.** Confirme na documentação. Os comandos **não foram executados**.

O **Amazon DocumentDB** (com compatibilidade com o MongoDB) é um banco de dados de **documentos JSON/BSON**, gerenciado pela AWS, que **implementa a API do MongoDB** (versões 3.6, 4.0, 5.0 e posteriores) sobre uma **arquitetura própria**, semelhante à do Aurora: computação separada de um **armazenamento distribuído** com seis cópias em três AZs. As aplicações e drivers do MongoDB conectam-se com poucas mudanças, enquanto a AWS cuida de provisionamento, patches, backups, failover e escala.

**Analogia:** é uma **fichário de pastas flexíveis**: cada documento (pasta) tem a estrutura que precisar, sem esquema rígido, e é buscado pelo conteúdo. O DocumentDB mantém as **mesmas gavetas e etiquetas do MongoDB** (API), mas o armário por trás é o **cofre distribuído da AWS**.

## O modelo de documentos

```
 Banco relacional                     Banco de documentos (DocumentDB / MongoDB)
 ┌─ tabela pedidos ──────────┐        pedidos: {
 │ id │ cliente │ total      │          _id: ObjectId("..."),
 └────┴─────────┴────────────┘          cliente: { id: 1001, nome: "Ana" },
 ┌─ tabela itens ────────────┐          itens: [ { sku: "A1", qtd: 2 }, { sku: "B7", qtd: 1 } ],
 │ pedido_id │ sku │ qtd     │          total: 150.0, status: "PAGO"
 └───────────┴─────┴─────────┘        }   ← um documento carrega os dados relacionados (aninhados)
```

| Conceito | MongoDB / DocumentDB | Equivalente relacional |
|---|---|---|
| **Banco** | database | database |
| **Coleção** | collection | tabela |
| **Documento** | document (BSON, até 16 MB) | linha |
| **Campo** | field | coluna |
| **Índice** | index | índice |
| **Agregação** | aggregation pipeline | `GROUP BY`/joins |
| **`_id`** | chave primária obrigatória e única | PK |

Vantagens: **esquema flexível** (cada documento pode ter campos diferentes), dados aninhados e arrays, evolução sem migrações pesadas, desenvolvimento ágil. Cuidados: modelagem exige disciplina (embutir vs referenciar), e consultas entre coleções são menos naturais que SQL.

## Arquitetura

```
   Aplicações (driver MongoDB) ──► cluster endpoint / reader endpoint (TLS)
                                        │
         ┌──────────────────────────────┼──────────────────────────────┐
         ▼                              ▼                              ▼
   INSTÂNCIA PRIMÁRIA            RÉPLICA 1 (leitura)           RÉPLICA n (até 15)
         └────────── volume do cluster compartilhado (6 cópias, 3 AZs, cresce em 10 GiB) ──────────┘
```

| Elemento | Descrição |
|---|---|
| **Cluster** | Conjunto de instâncias + um volume compartilhado |
| **Instância primária** | Aceita leituras e escritas |
| **Réplicas** | Até **15** instâncias de leitura, que compartilham o volume (lag em ms) |
| **Volume de armazenamento** | Distribuído, **6 cópias em 3 AZs**, **autoexpansível** até dezenas de TiB, backup contínuo |
| **Endpoints** | Cluster (escrita), reader (leitura balanceada) e de instância |
| **Failover** | Automático: uma réplica é promovida em dezenas de segundos |
| **Compatibilidade** | API do MongoDB, **não** o código do MongoDB: o engine é diferente |

## Modos de implantação

| Modo | Descrição | Quando |
|---|---|---|
| **Cluster baseado em instâncias** | Escolhe a classe da instância e o nº de réplicas; um único shard (escrita em uma primária) | Maioria das cargas; escala vertical e leitura horizontal |
| **Elastic Clusters** | **Sharding** gerenciado: várias partições para escalar escrita e armazenamento (milhões de operações/s, petabytes) | Escrita e volume além de uma primária |
| **Serverless** (recurso mais recente; confirme) | Capacidade em **DCUs** que escala automaticamente | Cargas variáveis, dev/test |
| **Global Cluster** | Réplicas em outras regiões (DR e leitura local) | Resiliência regional e baixa latência global |

## Versões e compatibilidade

| Aspecto | Detalhe |
|---|---|
| **Versões da API** | 3.6, 4.0, 5.0 e mais recentes (confirme a lista e a política de fim de suporte) |
| **Drivers** | Drivers oficiais do MongoDB compatíveis com a versão da API |
| **Recursos suportados** | CRUD, índices (inclusive TTL, parcial, esparso, composto, texto, geoespacial, vetorial em versões recentes), aggregation pipeline, change streams, transações multi-documento (4.0+), `$lookup` (limitado) |
| **Lacunas e diferenças** | Alguns operadores/estágios de agregação, comandos administrativos, `mapReduce` e outros recursos não são suportados ou se comportam de forma diferente; `retryWrites` e outras opções de string de conexão têm particularidades |
| **Ferramentas de avaliação** | O **Amazon DocumentDB compatibility tool** analisa logs/queries para apontar incompatibilidades |
| **Não é MongoDB** | Não executa o código do MongoDB; recursos de produto proprietários do MongoDB Atlas (Atlas Search, Charts etc.) não existem |

Regra: **teste a aplicação** contra o DocumentDB antes de migrar; "compatível" não significa "idêntico".

## Quando usar

| Situação | DocumentDB? |
|---|---|
| Aplicação MongoDB existente que quer um serviço gerenciado na AWS | **Sim**, após teste de compatibilidade |
| Dados naturalmente em documentos (catálogos, perfis, conteúdo, configurações) | **Sim** |
| Necessidade de escala massiva chave-valor com latência de ms e custo por requisição | **DynamoDB** |
| Joins e transações relacionais complexas | **Aurora/RDS** |
| Recursos exclusivos do MongoDB (Atlas Search, motor completo) | MongoDB Atlas na AWS |
| Busca de texto/logs | OpenSearch |
| Grafos | Neptune |

### DocumentDB × DynamoDB × MongoDB Atlas

| Critério | **DocumentDB** | **DynamoDB** | **MongoDB Atlas** |
|---|---|---|---|
| API | MongoDB | Própria (PutItem/Query) e PartiQL | MongoDB (completa) |
| Modelo | Documentos, consultas ricas | Chave-valor/documento por chave | Documentos |
| Escala | Instâncias + elastic clusters | Praticamente ilimitada, serverless | Clusters/sharding |
| Gerenciamento | Cluster na VPC | Serverless total | SaaS (múltiplas nuvens) |
| Consultas ad hoc | **Ricas** (índices, agregações) | Limitadas a chaves/índices | Ricas |
| Custo | Instâncias + armazenamento + I/O | Por requisição ou capacidade | Por cluster |

## Exemplo prático

```bash
# Cluster DocumentDB com 1 primária e 2 réplicas em AZs distintas
aws docdb create-db-cluster --db-cluster-identifier catalogo-docdb --engine docdb --engine-version 5.0.0 \
  --master-username adminmongo --manage-master-user-password \
  --db-subnet-group-name sg-docdb --vpc-security-group-ids sg-0docdb123 \
  --storage-encrypted --kms-key-id alias/docdb --backup-retention-period 14 --deletion-protection
for i in 1 2 3; do
  aws docdb create-db-instance --db-instance-identifier catalogo-docdb-$i --db-cluster-identifier catalogo-docdb \
    --engine docdb --db-instance-class db.r6g.large
done
aws docdb describe-db-clusters --db-cluster-identifier catalogo-docdb \
  --query 'DBClusters[0].{Endpoint:Endpoint,Leitura:ReaderEndpoint,Membros:DBClusterMembers[].{Id:DBInstanceIdentifier,Primaria:IsClusterWriter}}'
```

Conexão (cliente `mongosh`, TLS e leitura nas réplicas):

```bash
mongosh "mongodb://adminmongo:<senha>@catalogo-docdb.cluster-xxxx.sa-east-1.docdb.amazonaws.com:27017/?tls=true&tlsCAFile=global-bundle.pem&replicaSet=rs0&readPreference=secondaryPreferred&retryWrites=false"
```

```javascript
// Dentro do shell: operações típicas
use loja
db.pedidos.insertOne({ cliente: { id: 1001, nome: "Ana" }, itens: [{ sku: "A1", qtd: 2 }], total: 150.0, status: "PAGO" })
db.pedidos.find({ "cliente.id": 1001, status: "PAGO" }).sort({ _id: -1 }).limit(10)
```

## Erros comuns e armadilhas

- **Assumir compatibilidade total com o MongoDB** sem testar (operadores, comandos, opções de driver).
- **Migrar sem avaliar com a compatibility tool.**
- **Conectar sem TLS** ou sem o bundle de CA; o TLS vem habilitado por padrão.
- **Usar o endpoint de instância na aplicação** em vez do cluster/reader endpoint.
- **Esquecer `readPreference=secondaryPreferred`** e deixar a primária sobrecarregada.
- **Modelar como relacional** (referências para tudo) ou embutir arrays que crescem sem limite (documentos até 16 MB).
- **Falta de índices:** `COLLSCAN` em coleções grandes.
- **Cluster público:** o DocumentDB vive na VPC; nunca exponha.
- **Esperar sharding no cluster baseado em instâncias:** é preciso Elastic Clusters.
- **Ignorar o custo de I/O** (modelo Standard) em cargas intensas.

## 🧩 Quiz de Fixação

1. O que significa o DocumentDB ser "compatível com MongoDB"?
2. Como é a arquitetura de armazenamento do DocumentDB?
3. Quando escolher DocumentDB em vez de DynamoDB?
4. O que fazer antes de migrar uma aplicação MongoDB para o DocumentDB?

**Respostas:**
1) Implementa a API e o protocolo do MongoDB (versões específicas), de modo que drivers e ferramentas funcionam com poucas mudanças, mas o engine é diferente e nem todos os operadores e recursos são suportados.
2) Um volume de cluster distribuído e compartilhado, com seis cópias em três AZs, que cresce automaticamente, com uma primária e até 15 réplicas de leitura, além de backup contínuo e failover rápido (semelhante ao Aurora).
3) Quando a aplicação já usa a API do MongoDB, depende de consultas ricas, índices e agregações sobre documentos, e se quer um serviço gerenciado com poucas mudanças de código; o DynamoDB é melhor para acesso por chave em escala massiva e custo por requisição.
4) Avaliar a compatibilidade (compatibility tool e testes de integração e de carga), revisar operadores e opções do driver, desenhar índices e topologia, testar a migração (DMS ou dump/restore) e planejar o corte e o retorno.
