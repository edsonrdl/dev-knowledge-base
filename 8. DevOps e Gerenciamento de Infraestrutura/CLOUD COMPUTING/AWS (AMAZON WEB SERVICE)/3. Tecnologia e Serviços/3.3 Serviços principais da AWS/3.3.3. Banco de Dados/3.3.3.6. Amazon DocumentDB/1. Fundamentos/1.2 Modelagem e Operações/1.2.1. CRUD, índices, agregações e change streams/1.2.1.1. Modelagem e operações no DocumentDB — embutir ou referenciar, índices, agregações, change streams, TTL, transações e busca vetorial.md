### Modelagem e operações no DocumentDB — embutir ou referenciar, índices, agregações, change streams, TTL, transações e busca vetorial

> [!warning] Aviso
> Operadores e estágios de agregação suportados, tipos de índice (texto, geoespacial, vetorial), change streams e transações variam **por versão da API** (3.6, 4.0, 5.0 e posteriores) e diferem do MongoDB. Os exemplos são **ilustrativos e não foram executados**. **Valide cada recurso na sua versão.**

Em um banco de documentos, a modelagem e os índices determinam o desempenho tanto quanto o hardware. Esta nota cobre **como modelar** (embutir vs referenciar e padrões), **operações CRUD**, **tipos de índice** e como evitar varreduras completas, o **pipeline de agregação**, **TTL**, **change streams**, **transações** e **busca vetorial**, destacando as particularidades do DocumentDB em relação ao MongoDB.

**Analogia:** modelar documentos é decidir **o que vai dentro da mesma pasta** (embutir) e o que fica em **outra pasta com um bilhete de referência**. Os índices são o **catálogo de etiquetas** que evita abrir todas as pastas para achar uma.

## Modelagem: embutir ou referenciar

| Critério | **Embutir** (documento aninhado) | **Referenciar** (ids entre coleções) |
|---|---|---|
| Relação | Um-para-poucos; dados lidos juntos | Um-para-muitos grandes ou muitos-para-muitos |
| Leitura | Uma consulta traz tudo | Várias consultas ou `$lookup` |
| Escrita | Atualiza um documento (atômico) | Atualiza vários documentos |
| Crescimento | Documento cresce (limite de **16 MB**) | Sem limite por documento |
| Duplicação | Pode duplicar dados | Normalizado |
| Exemplo | Pedido com itens | Cliente e seus milhões de pedidos |

Regras práticas:

1. **Modele pelas consultas** (como no DynamoDB): os padrões de acesso mandam.
2. **Embuta** o que é lido junto e tem cardinalidade limitada (endereços, itens de pedido).
3. **Referencie** quando o lado "muitos" é ilimitado (comentários de um post popular) ou muda independentemente.
4. Evite **arrays que crescem sem limite** (anti-padrão "unbounded array").
5. Use **padrões**: *bucket* (agrupar séries temporais em documentos por hora), *subset* (embutir só os N últimos itens), *computed* (guardar totais pré-calculados), *polymorphic* (coleção com documentos de tipos diferentes e campo `tipo`), *schema versioning* (`schemaVersion`).
6. Mantenha documentos **pequenos e previsíveis**; documentos grandes consomem memória e I/O.

```javascript
// Pedido com itens embutidos e snapshot do cliente (dados lidos juntos)
{
  _id: ObjectId("..."),
  numero: "P-2026-0001",
  cliente: { id: 1001, nome: "Ana", cidade: "São Paulo" },        // snapshot (desnormalizado)
  itens: [ { sku: "A1", nome: "Camiseta", qtd: 2, preco: 49.9 } ],
  total: 99.8, status: "PAGO", criadoEm: ISODate("2026-11-06T14:30:00Z"), schemaVersion: 3
}
```

## Operações CRUD básicas

```javascript
db.pedidos.insertOne({ ... });  db.pedidos.insertMany([ ... ]);
db.pedidos.find({ "cliente.id": 1001, status: "PAGO" }, { numero: 1, total: 1 });      // filtro e projeção
db.pedidos.updateOne({ numero: "P-2026-0001" }, { $set: { status: "ENVIADO" }, $inc: { versao: 1 } });
db.pedidos.updateMany({ status: "NOVO", criadoEm: { $lt: ISODate("2026-10-01") } }, { $set: { status: "EXPIRADO" } });
db.pedidos.deleteOne({ numero: "P-2026-0001" });
db.pedidos.countDocuments({ status: "PAGO" });
```

Operadores atômicos de atualização (`$set`, `$inc`, `$push`, `$pull`, `$addToSet`, `$unset`) modificam parte do documento sem reescrevê-lo. **Atualizações em um único documento são atômicas.** `findOneAndUpdate` permite *read-modify-write* atômico (filas, contadores).

## Índices

Sem índice, uma consulta faz `COLLSCAN` (varre a coleção inteira). Índices aceleram consultas, ordenações e restrições de unicidade, ao custo de espaço e de escritas mais lentas.

| Tipo de índice | Uso | Observação no DocumentDB |
|---|---|---|
| **Simples** (um campo) | Filtros e ordenação por um campo | Suportado |
| **Composto** | Filtros em vários campos; ordem dos campos importa (ESR: Equality, Sort, Range) | Suportado |
| **Único** (`unique: true`) | Impõe unicidade | Suportado |
| **Esparso** (`sparse`) e **parcial** (`partialFilterExpression`) | Indexa só documentos com o campo/que atendem à condição | Suportado (versões recentes) |
| **TTL** | Remove documentos expirados automaticamente | Suportado; remoção por processo em segundo plano (pode levar até ~1 min ou mais) |
| **Texto** | Busca textual básica | Suportado em versões recentes, com limitações; para busca avançada use OpenSearch |
| **Geoespacial** (`2dsphere`) | Consultas por proximidade/área | Suportado |
| **Vetorial** (HNSW/IVFFlat) | Busca por similaridade de embeddings | Suportado em versões recentes (5.0+; confirme) |
| **Multikey** (arrays) | Indexa elementos de arrays | Suportado |
| **Hashed**, **wildcard** | Particulares do MongoDB | Podem **não** ser suportados: confira |

```javascript
db.pedidos.createIndex({ "cliente.id": 1, criadoEm: -1 });                 // composto: filtra cliente, ordena por data
db.pedidos.createIndex({ numero: 1 }, { unique: true });
db.sessoes.createIndex({ expiraEm: 1 }, { expireAfterSeconds: 0 });         // TTL: expira quando expiraEm passa
db.pedidos.createIndex({ status: 1 }, { partialFilterExpression: { status: "PENDENTE" } });  // índice só dos pendentes

db.pedidos.find({ "cliente.id": 1001 }).sort({ criadoEm: -1 }).explain("executionStats")
// Verifique: stage IXSCAN (usa índice) em vez de COLLSCAN; docsExamined próximo de nReturned
```

Boas práticas: crie índices **antes** de cargas massivas apenas quando necessário (ou depois, para acelerar a carga, e meça), evite índices excessivos, **monitore** o uso (`$indexStats`), remova os não usados, e atenção ao tamanho dos índices em memória (working set).

## Aggregation pipeline

Sequência de **estágios** que transformam documentos: filtrar, agrupar, projetar, juntar, ordenar.

```javascript
db.pedidos.aggregate([
  { $match: { status: "PAGO", criadoEm: { $gte: ISODate("2026-11-01") } } },        // filtra primeiro (usa índice)
  { $unwind: "$itens" },
  { $group: { _id: "$itens.sku", qtd: { $sum: "$itens.qtd" }, receita: { $sum: { $multiply: ["$itens.qtd", "$itens.preco"] } } } },
  { $sort: { receita: -1 } },
  { $limit: 10 }
])
```

| Estágio | Função |
|---|---|
| `$match` | Filtra (coloque no início para usar índices) |
| `$project` / `$addFields` | Seleciona/cria campos |
| `$group` | Agrega (`$sum`, `$avg`, `$min`, `$max`, `$push`) |
| `$sort` / `$limit` / `$skip` | Ordenar e paginar |
| `$unwind` | "Explode" arrays em documentos |
| `$lookup` | "Join" com outra coleção (suporte e desempenho **limitados**; evite em grandes volumes) |
| `$facet`, `$bucket` | Várias agregações em uma, faixas |
| `$out` / `$merge` | Gravar resultados em coleção |

Particularidades do DocumentDB: **nem todos os estágios/operadores existem** (confira a lista suportada); agregações pesadas podem exigir réplicas dedicadas (`readPreference=secondary`) ou serem materializadas em coleções de resumo; para analytics, prefira exportar para S3/Redshift/Athena.

## Transações e atomicidade

| Escopo | Garantia |
|---|---|
| **Um documento** | Atômico (inclusive campos aninhados e arrays) |
| **Vários documentos** | **Transações multi-documento** disponíveis na API 4.0+, em uma única instância/cluster (com limites de tamanho/tempo) |
| **Entre clusters/elastic clusters** | Verifique suporte e restrições |

```javascript
const sessao = db.getMongo().startSession();
sessao.startTransaction();
try {
  sessao.getDatabase("loja").estoque.updateOne({ sku: "A1", qtd: { $gte: 2 } }, { $inc: { qtd: -2 } });
  sessao.getDatabase("loja").pedidos.insertOne({ sku: "A1", qtd: 2 });
  sessao.commitTransaction();
} catch (e) { sessao.abortTransaction(); throw e; }
```

Use transações quando necessário; modelagem com documentos embutidos reduz a necessidade (e o custo). Mantenha transações **curtas**.

## Change streams

Fluxo de **eventos de mudança** (insert/update/replace/delete) de uma coleção, base para **CDC**, atualização de caches/índices e integrações orientadas a eventos.

| Característica | Detalhe |
|---|---|
| **Ativação** | Habilite por coleção/banco (`modifyChangeStreams`) e defina a **retenção** do log (`change_stream_log_retention_duration`, de minutos a dias) no parameter group |
| **Uso** | `db.pedidos.watch([{ $match: { operationType: "insert" } }])` |
| **Retomada** | `resumeAfter` / token para continuar após falha |
| **Consumidores** | Lambda (event source mapping para DocumentDB), Kafka Connect, DMS (CDC), aplicações próprias |
| **Cuidados** | Custo de armazenamento do log, volume de eventos, idempotência do consumidor, retenção suficiente |

```javascript
db.runCommand({ modifyChangeStreams: 1, database: "loja", collection: "pedidos", enable: true });
const cursor = db.pedidos.watch([{ $match: { operationType: { $in: ["insert", "update"] } } }], { fullDocument: "updateLookup" });
```

## TTL (expiração de documentos)

Índice TTL em campo de data remove documentos automaticamente após o tempo definido: sessões, tokens, logs temporários, carrinhos abandonados. A remoção ocorre por processo periódico e **não é instantânea**; filtre por data nas consultas quando a precisão importar.

---

## Busca vetorial

O DocumentDB suporta, em versões recentes, **índices vetoriais** (HNSW, IVFFlat) para busca por similaridade em embeddings — base para **RAG**, recomendação e busca semântica.

```javascript
db.artigos.createIndex({ embedding: "vector" }, { name: "idx_vec", vectorOptions: { type: "hnsw", dimensions: 1024, similarity: "cosine", m: 16, efConstruction: 64 } });
db.artigos.aggregate([{ $search: { vectorSearch: { vector: [/* embedding da pergunta */], path: "embedding", similarity: "cosine", k: 5 } } }]);
```

(A sintaxe exata depende da versão; confirme na documentação. Alternativas: Aurora PostgreSQL com pgvector, OpenSearch, Bedrock Knowledge Bases.)

## Exemplo prático

Catálogo de produtos de um marketplace:

1. **Modelo:** `produtos` com atributos variáveis por categoria (polimórfico), `preco`, `estoque`, `avaliacoes` (subset: últimas 10 embutidas; o restante em `avaliacoes` referenciadas por `produtoId`).
2. **Índices:** composto `{categoria:1, preco:1}`, único `{sku:1}`, texto/campo de busca simples, parcial `{estoque:1}` para `estoque < 5` (reposição), TTL em `carrinhos.expiraEm`.
3. **Consultas:** listagem por categoria e faixa de preço (IXSCAN), página de produto por `sku` (uma leitura, com avaliações embutidas).
4. **Agregações:** receita por categoria no mês materializada por job noturno em `resumos_vendas` (evita agregações pesadas no horário comercial).
5. **Change streams:** alterações de preço/estoque → Lambda → invalida cache e atualiza o índice de busca (OpenSearch).
6. **Operação:** `explain("executionStats")` nas 10 consultas mais frequentes; `$indexStats` trimestral para remover índices ociosos.
7. **Evolução:** campo `schemaVersion` e migração gradual de documentos antigos em lotes.

## Erros comuns e armadilhas

- **Embutir arrays ilimitados** (documento passa de 16 MB ou fica lento).
- **Referenciar tudo** e depender de `$lookup` em grandes volumes.
- **Consulta sem índice** (`COLLSCAN`) em coleções grandes.
- **Índice composto com ordem errada** dos campos.
- **Índices demais** (escrita lenta, memória).
- **Usar operadores/estágios não suportados** e descobrir só em produção.
- **Esperar TTL instantâneo.**
- **Change streams sem retenção suficiente** (consumidor parado perde eventos) ou sem idempotência.
- **Transações longas** e muitas operações em uma transação.
- **Agregações pesadas na primária** durante o pico.
- **Esquecer `schemaVersion`** e quebrar compatibilidade.

## 🧩 Quiz de Fixação

1. Quando embutir e quando referenciar dados em documentos?
2. Por que um índice composto depende da ordem dos campos?
3. O que é um índice TTL e qual sua principal limitação?
4. Para que servem os change streams e que cuidado tomar no consumidor?

**Respostas:**
1) Embute-se o que é lido junto e tem cardinalidade limitada (itens de pedido, endereços); referencia-se quando o lado "muitos" é ilimitado ou muda de forma independente, evitando documentos gigantes.
2) Porque o índice é ordenado pelos campos na ordem declarada: ele atende melhor filtros pelo prefixo (primeiros campos) e ordenações compatíveis (regra ESR: igualdade, ordenação, intervalo).
3) Remove documentos automaticamente depois de um tempo, definido em um campo de data. A limitação é que a remoção é feita por um processo periódico e não é instantânea.
4) Fornecem o fluxo de mudanças (insert, update, delete) para CDC e integrações orientadas a eventos; o consumidor deve ser idempotente, usar tokens de retomada e garantir retenção do log suficiente.
