### Backup, restauração e migração para o DocumentDB — PITR, snapshots, clonagem, DMS, mongodump e mongorestore, e estratégia de cutover

> [!warning] Aviso
> Janelas de retenção, suporte a PITR/clonagem em cada modo (instâncias, Elastic Clusters), limites do DMS e procedimentos de migração variam por versão. Os roteiros são **ilustrativos e não testados**. **Valide na documentação e ensaie antes do corte.** Os comandos **não foram executados**.

Duas perguntas operacionais: **como recupero meus dados?** (backup e restauração) e **como chego ao DocumentDB a partir do MongoDB (ou de outro banco)?** (migração). A arquitetura de armazenamento do DocumentDB entrega **backup contínuo sem impacto** e **restauração para qualquer segundo**; a migração pode ser **offline** (dump e restore) ou **online** (DMS com CDC), com uma **etapa de avaliação de compatibilidade** que determina o esforço real.

**Analogia:** o backup contínuo é um **gravador de câmera que filma o cofre o tempo todo** — você rebobina até o segundo desejado. A migração é uma **mudança de casa**: ou se leva tudo em um fim de semana (dump e restore) ou se transportam as caixas aos poucos enquanto se mora na casa velha, trocando as chaves no fim (DMS com CDC).

## Backup e restauração

### Backup contínuo

| Característica | Detalhe |
|---|---|
| **Funcionamento** | O volume distribuído faz backup **contínuo e incremental** para o S3, **sem impacto** de desempenho e sem janela de backup |
| **Retenção** | **1 a 35 dias** (padrão 1) |
| **PITR** | Restaura para qualquer segundo da retenção (até ~5 minutos atrás) |
| **Restauração** | Cria um **novo cluster** (novo endpoint); depois adicione as instâncias |
| **Custo** | Armazenamento de backup acima do volume é cobrado |
| **Cluster excluído** | Backups automáticos são apagados com o cluster: tire um **snapshot final** |

### Snapshots

| Tipo | Característica |
|---|---|
| **Automáticos** | Parte do backup contínuo; expiram conforme a retenção |
| **Manuais** | Sem expiração; podem ser **copiados entre regiões** e **compartilhados** entre contas (criptografados com CMK) |
| **Restauração** | De um snapshot cria um novo cluster |

### Clonagem rápida

Cria um novo cluster que **compartilha as páginas** do original com *copy-on-write* — minutos, sem copiar dados, pouco custo inicial. Útil para homologação, testes de migração de esquema/índices e análises (veja a disponibilidade para a sua versão e modo).

```bash
# Retenção e janela
aws docdb modify-db-cluster --db-cluster-identifier catalogo-docdb --backup-retention-period 14 --apply-immediately

# Snapshot manual antes de uma mudança
aws docdb create-db-cluster-snapshot --db-cluster-identifier catalogo-docdb --db-cluster-snapshot-identifier catalogo-pre-release

# PITR: novo cluster no instante desejado
aws docdb restore-db-cluster-to-point-in-time --db-cluster-identifier catalogo-docdb-pitr \
  --source-db-cluster-identifier catalogo-docdb --restore-to-time 2026-11-06T14:30:00Z \
  --vpc-security-group-ids sg-0docdb123 --db-subnet-group-name sg-docdb
aws docdb create-db-instance --db-instance-identifier catalogo-docdb-pitr-1 --db-cluster-identifier catalogo-docdb-pitr \
  --engine docdb --db-instance-class db.r6g.large

# Restaurar de snapshot
aws docdb restore-db-cluster-from-snapshot --db-cluster-identifier catalogo-restaurado --snapshot-identifier catalogo-pre-release --engine docdb
```

### Backups lógicos e AWS Backup

- **`mongodump`/`mongoexport`**: exportam dados (lógico), úteis para migração entre ambientes e cópias seletivas, mas **não substituem** o backup do cluster (mais lentos, com impacto de leitura).
- **AWS Backup**: planos centrais, cópias entre contas/regiões e cofres imutáveis ([[8. DevOps e Gerenciamento de Infraestrutura/CLOUD COMPUTING/AWS (AMAZON WEB SERVICE)/3. Tecnologia e Serviços/3.3 Serviços principais da AWS/3.3.2. Armazenamento/3.3.2.6. AWS Backup/0 AWS Backup (Tópicos )|AWS Backup]]).
- **Exportações para S3** (via jobs/DMS) para o data lake.

### Boas práticas

1. Retenção de 14 a 35 dias em produção; snapshots manuais antes de mudanças.
2. **Cópia de snapshots para outra região/conta** (DR).
3. **Teste de restauração** periódico, medindo o RTO; validar contagens.
4. Lembrar de **reassociar** parameter group, SG e criar **instâncias** no cluster restaurado.
5. Proteção contra exclusão (`--deletion-protection`) e snapshot final.

## Migração para o DocumentDB

### Passo 0: avaliação de compatibilidade

| Etapa | Ferramenta/ação |
|---|---|
| **Inventário** | Versão do MongoDB, coleções, tamanhos, índices, uso de recursos (agregações, `$lookup`, text search, geo, change streams, transações, time series, mapReduce) |
| **Compatibility tool** | Analisa logs/queries para apontar **operadores e comandos não suportados** |
| **Testes** | Rodar a suíte de testes da aplicação e carga contra um cluster DocumentDB de teste |
| **Decisão** | Se há muitas incompatibilidades, considere MongoDB Atlas na AWS, refatoração ou DynamoDB/Aurora |

### Estratégias

| Estratégia | Downtime | Quando |
|---|---|---|
| **Offline: `mongodump`/`mongorestore`** (ou export/import) | Alto (proporcional ao volume) | Bases pequenas/médias, janela longa aceitável |
| **Online: AWS DMS (full load + CDC)** | **Mínimo** | Bases grandes, pouca janela |
| **Híbrida: dump inicial + DMS/CDC** | Mínimo | Volumes muito grandes |
| **Dual-write na aplicação** | Zero (complexo) | Cenários especiais, com idempotência |
| **Elastic Clusters** | Mesma lógica, definindo a shard key antes | Cargas muito grandes |

### Migração offline (dump e restore)

```bash
# Origem (MongoDB)
mongodump --uri="mongodb://origem:27017/loja" --gzip --archive=loja.archive.gz
# Destino (DocumentDB, TLS)
mongorestore --host catalogo-docdb.cluster-xxxx.sa-east-1.docdb.amazonaws.com:27017 --ssl --sslCAFile global-bundle.pem \
  --username adminmongo --password '...' --gzip --archive=loja.archive.gz --numInsertionWorkersPerCollection 4
```

Boas práticas: **criar os índices** (crie antes ou depois da carga, medindo); restaurar coleções grandes em paralelo; verificar `_id` e tipos BSON; desativar índices pesados durante a carga e criá-los depois pode acelerar.

### Migração online com DMS

```
 MongoDB (origem) ──► [ AWS DMS: full load + CDC (change streams/oplog) ] ──► DocumentDB (destino)
```

| Etapa | Detalhe |
|---|---|
| **Endpoint de origem** | MongoDB (replica set com oplog) ou DocumentDB; modo *document* ou *table*; autenticação |
| **Endpoint de destino** | DocumentDB (TLS) |
| **Tarefa** | `full-load-and-cdc`; mapeamento de coleções; validação opcional |
| **Pré-requisito** | Índices: DMS **não migra índices** — crie-os no destino (script separado) |
| **Acompanhamento** | Latência de CDC; erros; contagem de documentos |

```bash
aws dms create-replication-task --replication-task-identifier mongo-para-docdb --migration-type full-load-and-cdc \
  --source-endpoint-arn $SRC --target-endpoint-arn $TGT --replication-instance-arn $RI \
  --table-mappings file://mapeamento.json --replication-task-settings file://settings.json
```

### Migração de outros bancos

| Origem | Caminho |
|---|---|
| **Relacional (SQL)** | Redesenhar o modelo em documentos; ETL com Glue/DMS (por coleção) |
| **DynamoDB** | Exportação para S3 + Glue/Lambda para o DocumentDB (ou DMS) |
| **JSON em S3** | `mongoimport` / Glue |
| **Entre clusters DocumentDB** | Snapshot / clone / Global Cluster |

## Cutover (virada) e validação

```
 1. Ambiente de destino pronto: cluster, índices, parâmetros, SG, monitoramento
 2. Full load + CDC até a latência próxima de zero
 3. Ensaio de corte (tempo, scripts, rollback)
 4. Congelar escritas na origem (ou modo manutenção)
 5. Esperar CDC zerar → validar contagens e amostras
 6. Trocar a string de conexão da aplicação (DNS/Parameter Store)
 7. Smoke tests e liberação gradual
 8. Manter a origem somente leitura por um período (rollback via replicação reversa ou reexportação)
```

| Validação | Como |
|---|---|
| **Contagem** | `countDocuments` por coleção |
| **Amostragem e hash** | Comparar documentos aleatórios; checksums por faixa de `_id` |
| **Índices** | Comparar definições |
| **Consultas críticas** | Planos (`explain`) e tempos |
| **Comportamento da aplicação** | Testes de regressão e carga |
| **Dados sensíveis** | Criptografia, acessos |

## Exemplo prático

Migração de um MongoDB 4.4 (replica set em EC2, 900 GB, 40 coleções) para o DocumentDB 5.0 com janela de 10 minutos:

1. **Avaliação:** a compatibility tool aponta 3 usos de `$facet` e 1 de `mapReduce`; os dois primeiros funcionam no 5.0, `mapReduce` é reescrito como agregação.
2. **Destino:** cluster DocumentDB (1 primária + 2 réplicas `r6g.2xlarge`), parameter group com TLS, `change_stream_log_retention_duration`, I/O-Optimized.
3. **Índices:** script exportado do MongoDB e aplicado no destino antes do CDC (DMS não migra índices).
4. **DMS:** `full-load-and-cdc` com 2 instâncias de replicação; carga completa em 11 h; CDC com latência < 3 s.
5. **Ensaio:** corte simulado em staging em 7 minutos; validação de contagem e de 5.000 documentos por amostragem.
6. **Virada:** modo manutenção, esperar CDC zerar, validar, trocar a string de conexão; smoke tests; liberação gradual.
7. **Rollback:** replicação reversa (DMS) do DocumentDB para o MongoDB por 7 dias.
8. **Pós:** backups de 14 dias, snapshots cross-region, teste de restauração, ajustes de índices com `$indexStats` e monitoramento de `BufferCacheHitRatio`.

## Erros comuns e armadilhas

- **Não avaliar a compatibilidade** e descobrir operadores não suportados no corte.
- **Esquecer os índices** (DMS e `mongorestore` com opções que os omitem) e ver consultas lentas.
- **Retenção de 1 dia** em produção e **sem cópia cross-region**.
- **Nunca testar a restauração** e o tempo.
- **Excluir o cluster sem snapshot final.**
- **Restaurar e esquecer de criar instâncias**, SG, parameter group.
- **Origem MongoDB sem oplog/change streams** para CDC.
- **Rede subdimensionada** (Direct Connect/VPN) na carga inicial.
- **Corte sem ensaio e sem plano de retorno.**
- **Ignorar diferenças de tipos BSON** (decimais, datas, `_id` não ObjectId) e opções de driver (`retryWrites`).
- **Backup lógico como único backup.**

## 🧩 Quiz de Fixação

1. Como funciona o backup do DocumentDB e como restaurar para um momento específico?
2. O que a restauração cria e o que costuma ser esquecido?
3. Por que avaliar a compatibilidade antes de migrar?
4. O DMS migra índices? Como lidar com isso?

**Respostas:**
1) O volume distribuído faz backup contínuo e incremental para o S3, sem impacto, com retenção de 1 a 35 dias; para um instante específico usa-se o PITR, que cria um novo cluster restaurado a esse momento.
2) Cria um novo cluster (novo endpoint), sem instâncias; costuma-se esquecer de criar as instâncias, reassociar SG e parameter group e apontar a aplicação.
3) Porque a compatibilidade com o MongoDB é parcial e varia por versão; operadores, comandos ou opções de driver não suportados só aparecem em produção se não forem testados. A compatibility tool e os testes de integração e de carga mostram o esforço real.
4) Não. É preciso criar os índices no destino por script (exportados da origem) antes ou durante a migração, validando-os depois.
