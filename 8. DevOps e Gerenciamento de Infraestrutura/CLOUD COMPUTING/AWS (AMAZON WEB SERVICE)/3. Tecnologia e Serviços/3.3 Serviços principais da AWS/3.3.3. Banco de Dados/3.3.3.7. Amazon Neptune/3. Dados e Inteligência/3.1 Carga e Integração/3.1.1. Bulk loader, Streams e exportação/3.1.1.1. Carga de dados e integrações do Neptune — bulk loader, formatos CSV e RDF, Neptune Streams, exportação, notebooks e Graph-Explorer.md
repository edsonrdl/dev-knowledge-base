### Carga de dados e integrações do Neptune — bulk loader, formatos CSV e RDF, Neptune Streams, exportação, notebooks e Graph-Explorer

> [!warning] Aviso
> Formatos de arquivo suportados, parâmetros do bulk loader, retenção do Neptune Streams, ferramentas (Graph-Explorer, notebooks) e integrações mudam. Os exemplos são **ilustrativos e não foram executados**. **Confirme na documentação.**

Um grafo só tem valor quando está **populado e conectado ao restante da arquitetura**. Esta nota mostra como **carregar dados em massa** (bulk loader a partir do S3), os **formatos** (CSV para property graph, formatos RDF), **atualizações incrementais** (via consultas e *upserts*), como **reagir a mudanças** (**Neptune Streams**), como **exportar** dados e como **explorar e visualizar** o grafo (notebooks, **Graph-Explorer**), além de integrações com **Lambda, Glue, DMS e Kinesis**.

**Analogia:** carregar um grafo linha a linha é como **montar uma cidade colocando um tijolo por vez**. O bulk loader é o **caminhão-betoneira**: despeja arquivos inteiros do S3 em paralelo. Os Streams são o **registro de obras** que avisa a cada mudança, e o Graph-Explorer é o **drone** que mostra a cidade de cima.

## Estratégias de carga

| Estratégia | Quando |
|---|---|
| **Bulk loader (S3)** | Carga inicial e cargas em lote: **rápida**, paralela, em escala de bilhões de elementos |
| **Consultas de escrita** (`addV`, `CREATE`/`MERGE`, `INSERT DATA`) | Atualizações pequenas e transacionais |
| **Lotes via aplicação/Lambda** | Fluxos contínuos moderados (agrupar em transações) |
| **AWS Glue / Spark** | Transformar dados de origem e escrever CSVs no formato do Neptune |
| **AWS DMS** | Migrar de relacionais/NoSQL para o S3 (formato intermediário) e depois carregar |
| **Streaming (Kinesis/MSK → Lambda)** | Eventos em tempo quase real; cuidado com conflitos e idempotência |
| **Neptune ML/Analytics import** | Para o serviço de análise (nota própria) |

## Bulk loader

O **bulk loader** lê arquivos do **S3** e grava no cluster, usando paralelismo. Pré-requisitos:

1. **Cluster na VPC** com **VPC endpoint (gateway) para o S3** (o tráfego do loader sai pela VPC).
2. **IAM role** associada ao cluster com permissão `s3:GetObject`/`ListBucket` no bucket/prefixo (menor privilégio) e, se o bucket é criptografado com SSE-KMS, permissão na chave.
3. Arquivos no **formato correto**, em **UTF-8**, preferencialmente **comprimidos (gzip)** e **divididos em partes** (vários arquivos de ~100 MB-1 GB para paralelismo).

```
 S3 (arquivos CSV/RDF) ──► [VPC endpoint S3] ──► Neptune bulk loader (POST /loader) ──► grafo
```

### Formatos

| Modelo | Formatos | Observação |
|---|---|---|
| **Property graph — Gremlin** | **CSV Gremlin**: arquivos de **vértices** (`~id`, `~label`, propriedades tipadas) e de **arestas** (`~id`, `~from`, `~to`, `~label`, propriedades) | Cabeçalhos com tipos (`nome:String`, `idade:Int`) |
| **Property graph — openCypher** | **CSV openCypher**: `:ID`, `:LABEL`, `:START_ID`, `:END_ID`, `:TYPE` | Formato próprio do openCypher |
| **RDF** | **N-Triples**, **N-Quads**, **RDF/XML**, **Turtle** | Triplas/quádruplas |

Exemplo de CSV Gremlin:

```csv
~id,~label,nome:String,idade:Int
p1,Pessoa,Ana,31
p2,Pessoa,Bruno,28
```
```csv
~id,~from,~to,~label,desde:Int
e1,p1,p2,CONHECE,2020
```

### Executar o loader

```bash
# POST /loader (de uma instância na mesma VPC; use awscurl/SigV4 se IAM estiver habilitado)
curl -X POST https://grafo-prod.cluster-xxxx.sa-east-1.neptune.amazonaws.com:8182/loader -H 'Content-Type: application/json' -d '{
  "source": "s3://dados-grafo/carga-2026-11/",
  "format": "csv",
  "iamRoleArn": "arn:aws:iam::111122223333:role/neptune-s3-load",
  "region": "sa-east-1",
  "failOnError": "FALSE",
  "parallelism": "HIGH",
  "updateSingleCardinalityProperties": "TRUE",
  "queueRequest": "TRUE"
}'
# Retorna um loadId; acompanhe:
curl https://grafo-prod...:8182/loader/<loadId>?details=true&errors=true
```

| Parâmetro | Função |
|---|---|
| `parallelism` | `LOW` a `OVERSUBSCRIBE` (usa mais threads; `HIGH`/`OVERSUBSCRIBE` pode saturar CPU) |
| `failOnError` | Se `TRUE`, aborta no primeiro erro |
| `queueRequest` | Enfileira o carregamento |
| `updateSingleCardinalityProperties` | Permite atualizar propriedades de cardinalidade única |
| `dependencies` | Ordena cargas (vértices antes de arestas) |
| `mode` | `RESUME` / `NEW` / `AUTO` |

Boas práticas:

1. **Carregue vértices antes das arestas** (arestas referenciam vértices existentes) ou use `dependencies`.
2. **Divida** os arquivos e comprima em gzip.
3. **Use uma instância maior** temporariamente na carga inicial (a carga é intensiva em CPU e I/O) e reduza depois.
4. **Evite consultas concorrentes pesadas** durante a carga.
5. **Verifique erros** (`errors=true`) e reprocesse os registros rejeitados.
6. **Idempotência:** o loader faz *upsert* por `~id`; reexecutar atualiza em vez de duplicar.
7. **Valide** contagens após a carga (`g.V().count()`, `MATCH (n) RETURN count(n)`).

## Atualizações incrementais

| Técnica | Exemplo |
|---|---|
| **Upsert** | `MERGE (c:Conta {id:$id}) SET c.status=$s` ou `g.V(id).fold().coalesce(unfold(), addV(...))` |
| **Lotes** | Agrupe dezenas a centenas de operações em uma transação/consulta |
| **Parâmetros** | Use consultas parametrizadas (openCypher) para reaproveitar planos e evitar injeção |
| **Tratamento de conflitos** | Retry com backoff em `ConcurrentModificationException` |
| **Eventos de origem** | Lambda consome Kinesis/SQS/DynamoDB Streams e escreve no grafo de forma idempotente |

## Neptune Streams (CDC do grafo)

O **Neptune Streams** registra um **log ordenado de alterações** (adições, atualizações, remoções de vértices, arestas, propriedades, triplas) que pode ser lido por uma API HTTP.

| Característica | Detalhe |
|---|---|
| **Habilitar** | Parâmetro do cluster `neptune_streams = 1` (reinício) |
| **Retenção** | Configurável (`neptune_streams_expiry_days`; de 1 a vários dias) |
| **API** | `GET /gremlin/stream` ou `/sparql/stream` (ou `/propertygraph/stream`), com `commitNum`/`opNum` para paginação |
| **Consumidores** | Lambda (polling), aplicações próprias; modelos de replicação para OpenSearch, Kinesis, outro Neptune |
| **Usos** | Busca em texto completo (sincronizar para OpenSearch), invalidação de caches, auditoria, replicação, pipelines de eventos |
| **Cuidados** | Aumenta o uso de armazenamento/I/O; consumo idempotente; mantenha a retenção maior que o pior atraso |

```bash
curl "https://grafo-prod...:8182/propertygraph/stream?limit=100&iteratorType=TRIM_HORIZON"
# Cada registro traz: eventId (commitNum, opNum), op (ADD/REMOVE), data (vértice/aresta/propriedade)
```

Padrão comum — **busca em texto completo**: Neptune Streams → Lambda → OpenSearch (atualiza o índice a cada mudança) e, na consulta, o Neptune chama o OpenSearch (integração de full-text search) para achar vértices por texto e depois percorre o grafo.

## Exportação e backup lógico

| Opção | Uso |
|---|---|
| **Neptune-Export** (utilitário) | Exporta o grafo para CSV/JSON/RDF em S3 (migração, análise, cópia entre clusters) |
| **Export de snapshot** | Em recursos recentes, snapshots para S3 (confirme) |
| **Consultas exportadoras** | Subgrafos específicos por Gremlin/openCypher |
| **Neptune Analytics import** | Carregar do cluster/S3 para análises |
| **Backups do cluster** | Contínuos e snapshots (nota de operação) — **não** substituídos por exportação lógica |

## Exemplo prático

Carga e sincronização do grafo de fraude:

1. **Origem:** Aurora (clientes, contas, transações) → AWS Glue gera CSVs Gremlin particionados em `s3://dados-grafo/aaaa/mm/dd/{vertices,arestas}/*.csv.gz`.
2. **Carga inicial:** instância primária elevada para `db.r6g.4xlarge` durante a carga; bulk loader com `parallelism=HIGH`, vértices antes de arestas via `dependencies`; validação de contagem; voltar a `db.r6g.xlarge`.
3. **Atualização diária:** Glue gera deltas; o loader executa *upserts* por `~id`.
4. **Eventos quase em tempo real:** transações novas vêm do Kinesis → Lambda → `MERGE` em lotes de 100 (idempotentes, retry em conflito).
5. **Streams:** habilitado (retenção 7 dias) → Lambda → OpenSearch para busca por nome/endereço (full-text) e → EventBridge para alertar quando um novo vínculo conecta uma conta a uma conta fraudulenta.
6. **Exploração:** analistas usam o **Graph-Explorer** (atrás de SSO e SG restrito) e notebooks.
7. **Exportação mensal** via Neptune-Export para S3 (Parquet via Glue) para o data lake e Neptune Analytics.
8. **Governança:** a role do loader só acessa o prefixo `dados-grafo/`; o endpoint S3 tem política; logs e alarmes para falhas de carga.

## Erros comuns e armadilhas

- **Carregar arestas antes dos vértices** (erros de referência).
- **Arquivo único gigante** (sem paralelismo) ou sem gzip.
- **Sem VPC endpoint do S3** ou role incorreta: o loader falha com acesso negado.
- **`parallelism=OVERSUBSCRIBE` em produção** sob carga de consultas.
- **Ignorar erros do loader** (`errors=true`) e perder registros.
- **Não usar `~id` estável** e duplicar dados em recargas.
- **Streams habilitado e retenção menor que o atraso do consumidor.**
- **Consumidor de Streams não idempotente.**
- **Expor o Graph-Explorer publicamente.**
- **Usar a exportação lógica como único backup.**
- **Carga com consultas pesadas simultâneas** causando timeouts.

## 🧩 Quiz de Fixação

1. Quais os pré-requisitos para usar o bulk loader?
2. Por que carregar vértices antes das arestas?
3. Para que serve o Neptune Streams e que cuidado tomar no consumidor?
4. Qual a vantagem do Graph-Explorer?

**Respostas:**
1) Cluster na VPC com VPC endpoint do S3, uma IAM role associada ao cluster com acesso ao bucket (e à chave KMS, se houver), arquivos no formato correto (CSV Gremlin/openCypher ou RDF), em UTF-8, divididos e idealmente comprimidos.
2) Porque as arestas referenciam os vértices pelos ids; se os vértices ainda não existem, a carga das arestas falha ou é rejeitada.
3) Registra o log ordenado de mudanças do grafo (CDC) para sincronizar com OpenSearch, invalidar caches, auditar e replicar; o consumidor deve ser idempotente e a retenção deve cobrir o pior atraso.
4) Explorar o grafo visualmente (buscar, expandir vizinhos, filtrar) sem escrever consultas, facilitando a análise por pessoas que não dominam as linguagens.
