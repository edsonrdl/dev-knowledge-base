### Alta disponibilidade e escala no Neptune — réplicas, failover, endpoints, Neptune Serverless e Global Database

> [!warning] Aviso
> Tempos de failover, número de réplicas, faixas de NCU, regiões e limites do Global Database, classes de instância e preços do Neptune mudam. Os números são **ordens de grandeza**. **Confirme na documentação.** Os comandos **não foram executados**.

O Neptune, como o Aurora e o DocumentDB, separa **computação** de um **volume de armazenamento compartilhado** de seis cópias em três AZs. Isso permite **failover rápido**, **até 15 réplicas de leitura** baratas, **crescimento automático do armazenamento** e recursos como **Serverless** (computação elástica) e **Global Database** (multirregião). Esta nota cobre cada mecanismo, como **dimensionar instâncias** (a memória do grafo é crucial), **escalar leitura e escrita** e **desenhar a resiliência**.

**Analogia:** o cluster é uma **central de informações turísticas** com um balcão de cadastro (primária) e vários balcões de consulta (réplicas) lendo o mesmo guia. Se o cadastro fechar, um balcão de consulta assume em segundos. O Serverless é o **efetivo que sobe e desce com o fluxo de turistas**; o Global Database é uma **filial em outro país com cópia do guia**.

## Réplicas e failover

```
 ANTES:  PRIMÁRIA (AZ-a)   RÉPLICA 1 (AZ-b) prioridade 0   RÉPLICA 2 (AZ-c) prioridade 1
 FALHA:  a primária cai ─► o Neptune promove a réplica de maior prioridade ─► o cluster endpoint passa a apontá-la
```

| Característica | Detalhe |
|---|---|
| **Réplicas** | Até **15**, compartilham o volume; lag de dezenas de ms |
| **Failover** | Automático em dezenas de segundos (menos de ~30 s a 2 min conforme o caso); depende de ter ao menos uma réplica |
| **Sem réplicas** | O Neptune cria nova instância (indisponibilidade maior) |
| **Prioridade de promoção** | Tier 0-15 por instância |
| **Failover manual** | `failover-db-cluster` para testes |
| **Aplicação** | Reconexão automática, retry com backoff, uso dos endpoints do cluster |

### Endpoints

| Endpoint | Uso |
|---|---|
| **Cluster endpoint** | Sempre a primária atual (escrita e leituras que exigem o dado mais recente) |
| **Reader endpoint** | Balanceia leituras entre réplicas (DNS round robin); pode estar na primária se não houver réplicas |
| **Instance endpoints** | Instância específica (diagnóstico, cargas dedicadas) |
| **Custom endpoints** | Subconjunto de instâncias (por exemplo, réplicas maiores para análise) |

```bash
aws neptune failover-db-cluster --db-cluster-identifier grafo-prod --target-db-instance-identifier grafo-prod-2
aws neptune create-db-cluster-endpoint --db-cluster-identifier grafo-prod --db-cluster-endpoint-identifier analise \
  --endpoint-type READER --static-members grafo-prod-3 grafo-prod-4       # réplicas maiores para consultas pesadas
```

Clientes Gremlin/WebSocket devem **recriar conexões** e respeitar o DNS curto do endpoint; evite *connection pools* que mantenham conexões velhas após o failover.

## Dimensionamento de instância

O desempenho do grafo depende da **memória**: o **buffer cache** guarda as páginas do grafo acessadas; se o working set cabe na memória, as travessias são rápidas.

| Família | Perfil | Uso |
|---|---|---|
| **db.t3 / db.t4g (medium)** | Burstable | Desenvolvimento, testes |
| **db.r5 / r6g / r7g / r8g** | Memória otimizada | **Produção** (Graviton `g` com melhor custo) |
| **db.x2g** | Memória extra | Working sets muito grandes |
| **db.r6gd / r7gd** | Memória + NVMe | Cache de leitura em grafos grandes (Optimized Reads; confirme) |
| **db.serverless** | NCUs | Cargas variáveis |

Orientações:

1. Observe `BufferCacheHitRatio` (alvo > 99% em OLTP de grafo) e `FreeableMemory`.
2. O número de **threads de consulta** é proporcional aos vCPUs (≈ 2 por vCPU); a fila de requisições (`MainRequestQueuePendingRequests`) sinaliza saturação.
3. Escalar **verticalmente** a primária para escritas pesadas; **horizontalmente** com réplicas para leituras.
4. Evite misturar classes muito diferentes sem definir prioridades de failover.

## Neptune Serverless

Computação **elástica** em **NCUs** (*Neptune Capacity Units*; 1 NCU ≈ 2 GiB de memória com CPU e rede proporcionais), que escala **em segundos** e **sem interromper conexões**.

| Característica | Detalhe |
|---|---|
| **Config** | `MinCapacity` e `MaxCapacity` (em NCUs, em passos de 0,5) por cluster |
| **Instâncias** | `db.serverless`; podem coexistir com instâncias provisionadas no mesmo cluster |
| **Escala** | Acompanha CPU, memória e rede; reduz mais lentamente do que sobe |
| **Cobrança** | **NCU-hora** (por segundo) + armazenamento + I/O |
| **Bom para** | Cargas variáveis/imprevisíveis, dev/test, picos esporádicos, aplicações novas |
| **Cuidado** | `MinCapacity` baixo → cache frio e latência a cada pico; `MaxCapacity` limita memória e conexões; compare custo com instâncias reservadas |
| **Tiers de promoção** | Réplicas em tiers 0 e 1 acompanham a capacidade do writer (prontas para failover) |

```bash
aws neptune create-db-cluster --db-cluster-identifier grafo-sv --engine neptune \
  --serverless-v2-scaling-configuration MinCapacity=2.5,MaxCapacity=64 ...
aws neptune create-db-instance --db-instance-identifier grafo-sv-1 --db-cluster-identifier grafo-sv --engine neptune --db-instance-class db.serverless
```

(Confirme nomes de parâmetros e faixas na documentação atual.)

## Global Database

Replica o cluster para **até cinco regiões secundárias** (somente leitura) por replicação em nível de **armazenamento**, com lag tipicamente **menor que 1 s**.

```
 Primária (sa-east-1) ══ replicação de armazenamento ══► Secundária (us-east-1) ═► Secundária (eu-west-1)
   leitura/escrita                                          leitura local            leitura local
```

| Característica | Detalhe |
|---|---|
| **Uso** | Leitura global de baixa latência e **DR** com RPO de segundos |
| **Switchover** | Planejado, sem perda |
| **Failover** | Não planejado; promove a secundária (pode perder transações recentes) |
| **RTO** | Cerca de 1 minuto no banco (mais o redirecionamento da aplicação) |
| **Limitações** | Verifique versões/engines suportados e recursos (Streams, ML) |
| **Custo** | Instâncias da secundária + replicação de I/O + transferência entre regiões |

## Modelo de cobrança de I/O

| Modo | Característica |
|---|---|
| **Standard** | Armazenamento e instâncias mais baratos; **I/O cobrado** por milhão de requisições |
| **I/O-Optimized** | Sem cobrança de I/O; preço maior de instância e armazenamento; vale quando o I/O é uma parcela relevante da fatura (cerca de um quarto ou mais) |

## Escala de leitura e escrita: o que fazer

| Sintoma | Ação |
|---|---|
| **Leituras saturando a primária** | Rotear leituras ao **reader endpoint**; adicionar réplicas; Auto Scaling de réplicas |
| **CPU alta nas consultas** | Otimizar consultas (`profile`), limitar profundidade/resultados, mais vCPUs |
| **Cache hit baixo** | Mais memória (classe maior), reduzir o working set, evitar varreduras |
| **Fila de requisições** | Mais vCPUs ou réplicas; controlar concorrência no cliente |
| **Escrita saturando a primária** | Instância maior; lotes (bulk loader / transações em lote); reduzir índices extras |
| **Cargas analíticas pesadas** | Réplicas dedicadas (custom endpoint) ou **Neptune Analytics** |
| **Picos imprevisíveis** | Serverless |
| **Latência para usuários globais** | Global Database com leitura local |

### Auto Scaling de réplicas

```bash
aws application-autoscaling register-scalable-target --service-namespace neptune \
  --resource-id cluster:grafo-prod --scalable-dimension neptune:cluster:ReadReplicaCount --min-capacity 1 --max-capacity 8
aws application-autoscaling put-scaling-policy --service-namespace neptune \
  --resource-id cluster:grafo-prod --scalable-dimension neptune:cluster:ReadReplicaCount \
  --policy-name cpu-leitura --policy-type TargetTrackingScaling \
  --target-tracking-scaling-policy-configuration '{"TargetValue":60.0,"PredefinedMetricSpecification":{"PredefinedMetricType":"NeptuneReaderAverageCPUUtilization"}}'
```

## Resiliência na aplicação

| Prática | Detalhe |
|---|---|
| **Retry com backoff** | Para erros transitórios, `ConcurrentModificationException`, `ReadOnlyViolationException` (escrita em réplica) e failover |
| **Idempotência** | `~id` definido pela aplicação e `MERGE` |
| **Timeouts** | Defina `neptune_query_timeout` e timeouts do cliente |
| **Gestão de conexões** | Reconectar após failover; evitar pools com conexões velhas; limitar conexões WebSocket |
| **Testes de failover** | Periódicos, medindo o RTO da aplicação |
| **Degradação** | Cache (ElastiCache) de resultados de travessias caras; fila para escritas |
| **Observabilidade** | Alarmes em `ClusterReplicaLag`, `CPUUtilization`, `BufferCacheHitRatio`, `MainRequestQueuePendingRequests` |

## Exemplo prático

Grafo de recomendação para um e-commerce com picos nas campanhas:

1. Cluster com primária `db.r6g.2xlarge` + 2 réplicas `db.r6g.xlarge` (AZs distintas); réplica em tier 0.
2. **Leituras de recomendação** no reader endpoint; **escritas** (compras, cliques) em lotes pela primária.
3. **Auto Scaling** de réplicas (2 a 8) por CPU > 60% nos eventos.
4. **Custom endpoint** `analise` com duas réplicas maiores para consultas de segmentação.
5. **Cache** (ElastiCache) para as recomendações dos 100 mil produtos mais vistos (TTL de 10 min).
6. **Global Database** com secundária em `us-east-1` para clientes nos EUA e DR.
7. **Failover** testado mensalmente; clientes com reconexão e timeouts; alarmes de `ClusterReplicaLag` e fila.
8. Após 3 meses, avaliar **Serverless** para as réplicas de pico e **I/O-Optimized** se o I/O ultrapassar ~25% do custo.

## Erros comuns e armadilhas

- **Sem réplica em outra AZ:** failover lento e indisponível.
- **Memória insuficiente** (cache hit baixo): latência alta e I/O faturado.
- **Aplicação usando endpoint de instância** ou conexões antigas após failover.
- **Ler sempre da primária** e sobrecarregá-la.
- **Réplicas menores que a primária** assumindo a carga.
- **Serverless com `MinCapacity` baixo** e cache frio constante.
- **Tratar Global Database como backup.**
- **Ignorar o limite de concorrência** (fila longa) e disparar mais requisições.
- **Escritas gigantes em uma transação** (conflitos e timeouts).
- **Não monitorar o lag das réplicas.**

## 🧩 Quiz de Fixação

1. Como funciona o failover do Neptune e o que a aplicação deve fazer?
2. Por que a memória é crítica para o desempenho de um grafo?
3. O que é uma NCU e quando usar o Neptune Serverless?
4. Para que serve o Global Database?

**Respostas:**
1) Uma réplica é promovida (por prioridade) em dezenas de segundos e o cluster endpoint passa a apontá-la; a aplicação deve usar os endpoints do cluster, reconectar, ter timeouts e retry com backoff e operações idempotentes.
2) Porque as travessias acessam muitas páginas do grafo; se o working set cabe no buffer cache a latência é baixa, caso contrário há leituras do volume (I/O faturado e mais lento).
3) *Neptune Capacity Unit*, cerca de 2 GiB de memória com CPU e rede proporcionais; o Serverless escala a computação automaticamente entre um mínimo e um máximo e é indicado para cargas variáveis, picos e ambientes de teste.
4) Replicar o cluster para até cinco regiões secundárias somente leitura, com lag inferior a 1 s, oferecendo leitura local de baixa latência e recuperação de desastres regional.
