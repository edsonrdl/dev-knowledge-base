### O que é Amazon Neptune — banco de dados de grafos, property graph e RDF, arquitetura de cluster, casos de uso e quando usar

> [!warning] Aviso
> Versões de engine, limites de armazenamento, linguagens suportadas, classes de instância, modos (cluster, Serverless, Analytics) e preços do Neptune mudam. Os números são **ordens de grandeza**. **Confirme na documentação.** Os comandos **não foram executados**.

O **Amazon Neptune** é o banco de dados de **grafos** gerenciado da AWS: projetado para armazenar e consultar **bilhões de relacionamentos** com latência de milissegundos. Em vez de tabelas, linhas e junções, os dados são **nós (vértices)** e **conexões (arestas)**, e as consultas **percorrem** esses relacionamentos. Isso torna natural — e rápido — responder perguntas como "quem são os amigos dos amigos de Ana?", "quais contas compartilham o mesmo dispositivo?" ou "qual o caminho entre dois componentes de uma rede?", que em SQL exigiriam junções profundas e caras.

**Analogia:** um banco relacional é uma **planilha**: para achar amigos de amigos você cruza tabelas inteiras. Um banco de grafos é um **mapa de metrô**: você parte de uma estação e **segue as linhas**, sem olhar o resto do mapa. O custo de uma viagem depende do trecho percorrido, não do tamanho da cidade.

## O problema que os grafos resolvem

```
 SQL: amigos de amigos de Ana (3 níveis)
   SELECT ... FROM pessoa p1 JOIN amizade a1 ON ... JOIN pessoa p2 ON ... JOIN amizade a2 ON ... JOIN pessoa p3 ...
   → cada nível adiciona uma junção; o custo cresce com o tamanho das TABELAS

 Grafo: Ana ──CONHECE──► Bruno ──CONHECE──► Carla ──CONHECE──► Diego
   → "adjacência sem índice": cada nó guarda ponteiros para seus vizinhos; o custo depende do TRECHO percorrido
```

| Característica | Relacional | Grafo |
|---|---|---|
| Foco | Entidades e atributos | **Relacionamentos** |
| Consulta de relacionamentos profundos | Junções caras | **Travessias rápidas** |
| Esquema | Rígido | Flexível |
| Evolução | Migrações | Adicionar novos tipos de nós/arestas |
| Ideal para | Transações e relatórios tabulares | Redes, recomendações, fraude, conhecimento |

## Modelos de grafo suportados

O Neptune suporta **dois modelos**, cada um com sua(s) linguagem(ns), no mesmo serviço (os dados de um modelo **não** são consultáveis pelo outro).

### 1. Property graph (grafo de propriedades)

| Elemento | Descrição | Exemplo |
|---|---|---|
| **Vértice (nó)** | Entidade com **rótulo** e propriedades | `(:Pessoa {nome: "Ana", idade: 31})` |
| **Aresta** | Relacionamento **direcionado** entre dois vértices, com rótulo e propriedades | `(Ana)-[:CONHECE {desde: 2020}]->(Bruno)` |
| **Propriedades** | Pares chave-valor em vértices e arestas | `nome`, `desde` |

Linguagens: **Apache TinkerPop Gremlin** (traversal imperativa) e **openCypher** (declarativa, similar a SQL para grafos).

### 2. RDF (Resource Description Framework)

Dados como **triplas** `sujeito – predicado – objeto` (e opcionalmente grafo nomeado: quádruplas), base da **web semântica**, ontologias e **knowledge graphs** padronizados (W3C). Linguagem: **SPARQL 1.1**.

```
 <Ana> <conhece> <Bruno> .
 <Ana> <nome> "Ana Silva" .
 <Bruno> <trabalhaEm> <ACME> .
```

| Critério | Property graph | RDF |
|---|---|---|
| Foco | Aplicações, travessias, análises de rede | Dados interoperáveis, ontologias, dados abertos/vinculados |
| Linguagens | Gremlin, openCypher | SPARQL |
| Propriedades em arestas | **Sim** (nativo) | Via reificação ou grafos nomeados |
| Raciocínio/inferência | Limitado | Orientado a semântica (RDFS/OWL em ferramentas) |
| Quando | Fraude, recomendação, redes sociais | Catálogos de conhecimento, saúde/ciências, integração semântica |

## Arquitetura do Neptune

```
   Aplicações / notebooks / Lambda ──HTTPS ou WebSocket :8182──► cluster endpoint (escrita) / reader endpoint (leitura)
                                                         │
          ┌───────────────────────────┬──────────────────┴─────────────────┐
          ▼                           ▼                                    ▼
   INSTÂNCIA PRIMÁRIA          RÉPLICA 1 (leitura)               RÉPLICA n (até 15)
          └───────────── volume do cluster compartilhado (6 cópias em 3 AZs, cresce em 10 GiB) ─────────────┘
```

| Elemento | Descrição |
|---|---|
| **Cluster** | Instância primária + até **15 réplicas** de leitura |
| **Volume de armazenamento** | Distribuído, **6 cópias em 3 AZs**, **autoexpansível** (dezenas de TiB), backup contínuo para o S3 |
| **Endpoints** | **Cluster** (escrita), **reader** (leitura balanceada) e de instância; porta **8182** |
| **Protocolos** | HTTPS (REST/SPARQL/openCypher) e **WebSocket** (Gremlin) |
| **Failover** | Automático (réplica promovida em dezenas de segundos) |
| **Índices** | O Neptune mantém **índices automáticos** para as travessias (não há `CREATE INDEX` tradicional; opcionalmente um índice extra em RDF/propriedades via configuração) |
| **Rede** | Dentro da **VPC**, sem endpoint público |
| **Variantes** | Instâncias **provisionadas**, **Serverless** (NCUs), **Global Database** e **Neptune Analytics** (serviço de análise em memória) |

Arquitetura análoga ao Aurora e ao DocumentDB (computação separada de armazenamento compartilhado): veja [[8. DevOps e Gerenciamento de Infraestrutura/CLOUD COMPUTING/AWS (AMAZON WEB SERVICE)/3. ## Casos de uso

| Caso | Como o grafo ajuda |
|---|---|
| **Detecção de fraude** | Encontrar anéis de contas que compartilham dispositivos, endereços, cartões ou IPs; padrões de rede suspeitos em milissegundos |
| **Recomendações** | "Quem comprou isto também comprou..." via travessias sobre usuários, produtos e interesses |
| **Redes sociais** | Amigos de amigos, comunidades, influência, feeds |
| **Knowledge graphs** | Entidades e relações de domínio (produtos, pessoas, regulação, saúde) para busca semântica e **GraphRAG** com IA generativa |
| **Identity graph** | Unificar identidades de clientes em múltiplos canais |
| **Segurança e TI** | Caminhos de ataque, dependências entre ativos, impacto de mudanças (CMDB), IAM |
| **Cadeia de suprimentos** | Rastreabilidade e dependências multinível |
| **Ciências da vida** | Interações proteína-fármaco, ontologias (RDF) |
| **Roteamento e redes** | Caminhos mais curtos, topologias |

### Quando **não** usar

| Situação | Alternativa |
|---|---|
| Transações tabulares, relatórios SQL | Aurora/RDS |
| Chave-valor com latência de ms e escala massiva | DynamoDB |
| Documentos sem relacionamentos profundos | DocumentDB |
| Busca de texto | OpenSearch |
| Análise de colunas em larga escala | Redshift |
| Poucos relacionamentos simples | Um relacional com chaves estrangeiras basta |

## Exemplo prático

```bash
# Cluster Neptune com 1 primária e 1 réplica, criptografado, na VPC
aws neptune create-db-cluster --db-cluster-identifier grafo-prod --engine neptune \
  --db-subnet-group-name sg-neptune --vpc-security-group-ids sg-0nep123 \
  --storage-encrypted --kms-key-id alias/neptune \
  --iam-database-authentication-enabled --backup-retention-period 14 --deletion-protection
aws neptune create-db-instance --db-instance-identifier grafo-prod-1 --db-cluster-identifier grafo-prod \
  --engine neptune --db-instance-class db.r6g.xlarge
aws neptune create-db-instance --db-instance-identifier grafo-prod-2 --db-cluster-identifier grafo-prod \
  --engine neptune --db-instance-class db.r6g.xlarge

aws neptune describe-db-clusters --db-cluster-identifier grafo-prod \
  --query 'DBClusters[0].{Escrita:Endpoint,Leitura:ReaderEndpoint,Porta:Port}'
```

Primeira consulta (openCypher via HTTPS, de uma instância na VPC):

```bash
curl -s https://grafo-prod.cluster-xxxx.sa-east-1.neptune.amazonaws.com:8182/openCypher \
  -d "query=MATCH (n) RETURN count(n) AS total"
# Com IAM habilitado, as requisições precisam ser assinadas com SigV4 (use awscurl ou os SDKs)
```

## Erros comuns e armadilhas

- **Usar grafo quando um relacional resolve:** poucos relacionamentos simples não justificam a complexidade.
- **Misturar modelos:** dados em property graph não são consultáveis por SPARQL e vice-versa.
- **Esperar SQL:** é preciso aprender Gremlin, openCypher ou SPARQL.
- **Travessias sem limite** (`LIMIT`, profundidade): explosão combinatória em grafos densos ("supernós").
- **Ignorar supernós** (vértices com milhões de arestas): gargalos.
- **Expor o endpoint publicamente:** Neptune vive na VPC; acesso por IAM/SigV4 e SG.
- **Carregar dados linha a linha** em vez de usar o **bulk loader**.
- **Subdimensionar a memória:** o working set do grafo deve caber no cache de buffer para boa latência.
- **Não planejar o modelo** (rótulos, direção, propriedades) em função das consultas.

## 🧩 Quiz de Fixação

1. Por que consultas de relacionamentos profundos são mais eficientes em um grafo que em SQL?
2. Quais os dois modelos de grafo do Neptune e suas linguagens?
3. Cite três casos de uso típicos do Neptune.
4. Como é a arquitetura de armazenamento do Neptune?

**Respostas:**
1) Porque os nós guardam referências diretas aos vizinhos (adjacência), então a consulta percorre apenas o trecho necessário, sem cruzar tabelas inteiras com junções cujo custo cresce com o tamanho dos dados.
2) Property graph (Gremlin e openCypher) e RDF (SPARQL); os dados de um modelo não são consultáveis pelo outro.
3) Detecção de fraude, recomendações, redes sociais/identity graph, knowledge graphs (inclusive GraphRAG), segurança e dependências de TI.
4) Um volume de cluster distribuído e compartilhado, com seis cópias em três AZs, que cresce automaticamente, com uma primária e até 15 réplicas de leitura, backup contínuo e failover rápido.
