### Modelagem de grafos e consultas no Neptune — Gremlin, openCypher e SPARQL, padrões de travessia, supernós e otimização

> [!warning] Aviso
> Recursos das linguagens (steps do Gremlin, cláusulas do openCypher, extensões do SPARQL), configurações de índices e limites de consulta variam por versão do engine. Os exemplos são **ilustrativos e não foram executados**. **Valide na sua versão do Neptune.**

Em um grafo, a **modelagem** decide quais conceitos viram **vértices**, quais viram **arestas**, quais viram **propriedades** — e isso determina a facilidade e a velocidade das consultas. Como no DynamoDB e no DocumentDB, **modele a partir das perguntas** que o negócio fará. Esta nota cobre os princípios de modelagem, as três linguagens (**Gremlin**, **openCypher**, **SPARQL**) com exemplos equivalentes, **padrões comuns** (amigos de amigos, caminho mais curto, detecção de anéis de fraude), **supernós** e **boas práticas de desempenho**.

**Analogia:** modelar um grafo é desenhar o **mapa de uma cidade**: o que é uma estação (vértice), o que é uma linha ligando estações (aresta), e que informações ficam nas placas (propriedades). Um mapa bem desenhado deixa as rotas óbvias; um mal desenhado obriga a andar por toda a cidade.

## Princípios de modelagem (property graph)

| Pergunta | Decisão |
|---|---|
| **Substantivo importante com identidade própria?** | Vértice (`Pessoa`, `Conta`, `Dispositivo`, `Produto`) |
| **Relação entre dois substantivos?** | Aresta (`CONHECE`, `COMPROU`, `USA`, `PERTENCE_A`) |
| **Atributo de um substantivo?** | Propriedade do vértice (`nome`, `data_nascimento`) |
| **Atributo da relação?** | Propriedade da aresta (`desde`, `valor`, `peso`) |
| **Um valor compartilhado por muitos vértices e usado para ligar?** | Vértice próprio (o `Dispositivo`, `Endereço`, `Telefone` compartilhado vira nó, não propriedade) |
| **Evento no tempo?** | Vértice de evento (`Transação`) ou aresta com timestamp |

Regras práticas:

1. **Promova a nó** o que você quer **percorrer**: se precisa achar "contas que usam o mesmo dispositivo", `dispositivo` deve ser vértice, não propriedade.
2. **Direção da aresta**: escolha a mais natural (`Pessoa -[COMPROU]-> Produto`); consultas podem percorrer em ambos os sentidos, mas a direção dá semântica.
3. **Rótulos específicos** e verbos claros.
4. **Evite supernós** (vértices com milhões de arestas) ou mitigue (veja abaixo).
5. **Propriedades enxutas**: não guarde blobs grandes; use S3 e guarde o ponteiro.
6. **IDs estáveis** (`~id` definido pela aplicação) permitem *upserts* idempotentes.
7. **Pense em índices**: as travessias dependem da adjacência; filtros por propriedade em grandes volumes devem começar de um vértice âncora indexado por `~id` ou rótulo.

```
 (Conta A)──USA──►(Dispositivo X)◄──USA──(Conta B)      ← "contas ligadas por dispositivo" vira uma travessia curta
 (Conta A)──TRANSFERIU {valor, data}──►(Conta C)
```

## As três linguagens: exemplos equivalentes

Pergunta: **quem são os "amigos de amigos" de Ana (e não são amigos diretos)?**

### Gremlin (traversal, `g`)

```groovy
// Inserir
g.addV('Pessoa').property(id, 'p1').property('nome', 'Ana')
g.addV('Pessoa').property(id, 'p2').property('nome', 'Bruno')
g.V('p1').addE('CONHECE').to(V('p2')).property('desde', 2020)

// Amigos de amigos (excluindo amigos diretos e a própria Ana)
g.V('p1').as('ana')
 .out('CONHECE').aggregate('diretos')
 .out('CONHECE').where(neq('ana')).where(without('diretos'))
 .dedup().values('nome').limit(20)
```

### openCypher (declarativo)

```cypher
MATCH (ana:Pessoa {nome: 'Ana'})-[:CONHECE]->(:Pessoa)-[:CONHECE]->(fof:Pessoa)
WHERE NOT (ana)-[:CONHECE]->(fof) AND fof <> ana
RETURN DISTINCT fof.nome LIMIT 20
```

### SPARQL (RDF)

```sparql
PREFIX ex: <http://exemplo.com/>
SELECT DISTINCT ?nome WHERE {
  ex:Ana ex:conhece ?amigo .
  ?amigo ex:conhece ?fof .
  FILTER NOT EXISTS { ex:Ana ex:conhece ?fof }
  FILTER (?fof != ex:Ana)
  ?fof ex:nome ?nome
} LIMIT 20
```

### Qual linguagem escolher

| Critério | **Gremlin** | **openCypher** | **SPARQL** |
|---|---|---|---|
| Estilo | Imperativo (passos encadeados) | Declarativo (padrões ASCII-art) | Declarativo (triplas) |
| Modelo | Property graph | Property graph | RDF |
| Curva | Média/alta | **Baixa** (parecido com SQL) | Média |
| Poder | Alto (controle fino, loops, side effects) | Alto para padrões | Alto para semântica |
| Quando | Travessias complexas, aplicações Java/Python, TinkerPop | Equipes SQL, ferramentas de BI/ML | Dados vinculados, ontologias |

**Gremlin e openCypher compartilham o mesmo grafo** (property graph): podem conviver e ser usados nas mesmas consultas via endpoints distintos.

## Padrões de consulta frequentes

### 1. Vizinhança e caminhos de comprimento variável

```cypher
MATCH (a:Pessoa {id:'p1'})-[:CONHECE*1..3]->(b:Pessoa) RETURN DISTINCT b.nome LIMIT 50   // até 3 saltos
```

```groovy
g.V('p1').repeat(out('CONHECE').simplePath()).times(3).emit().dedup().values('nome').limit(50)
```

### 2. Caminho mais curto

```cypher
MATCH p = shortestPath((a:Pessoa {id:'p1'})-[:CONHECE*..6]-(b:Pessoa {id:'p99'})) RETURN length(p), [n IN nodes(p) | n.nome]
```

```groovy
g.V('p1').repeat(both('CONHECE').simplePath()).until(hasId('p99')).limit(1).path().by('nome')
```

### 3. Detecção de fraude: contas ligadas por atributos compartilhados

```cypher
// Contas que compartilham dispositivo ou telefone com uma conta marcada como fraude
MATCH (f:Conta {fraude:true})-[:USA|TEM_TELEFONE]->(x)<-[:USA|TEM_TELEFONE]-(suspeita:Conta)
WHERE suspeita <> f AND coalesce(suspeita.fraude,false) = false
RETURN suspeita.id, collect(DISTINCT labels(x)[0]) AS ligacoes, count(DISTINCT x) AS qtd ORDER BY qtd DESC LIMIT 50
```

### 4. Recomendação (colaborativa)

```cypher
MATCH (u:Usuario {id:'u1'})-[:COMPROU]->(p:Produto)<-[:COMPROU]-(outro:Usuario)-[:COMPROU]->(rec:Produto)
WHERE NOT (u)-[:COMPROU]->(rec)
RETURN rec.nome, count(*) AS score ORDER BY score DESC LIMIT 10
```

### 5. Centralidade simples e comunidades

Grau (número de conexões) com `size((n)--())`; algoritmos como PageRank, componentes conexos e detecção de comunidades são mais indicados no **Neptune Analytics** (nota própria).

## Supernós e explosão combinatória

Um **supernó** é um vértice com um número muito grande de arestas (ex.: um país, um hashtag famoso, um IP corporativo). Percorrer através dele explode o conjunto de resultados.

| Mitigação | Como |
|---|---|
| **Limitar** a travessia (`LIMIT`, profundidade máxima, `simplePath`) | Evita explosão |
| **Filtrar cedo** por rótulo, propriedade ou direção | Reduz o fan-out |
| **Dividir o nó**: criar nós intermediários (`País → Região → Cidade`) ou bucket por período | Distribui as arestas |
| **Excluir supernós** das travessias de similaridade (lista de exceções) | Evita falsos vínculos (o "mesmo IP do escritório") |
| **Usar propriedades de aresta** (pesos, datas) para priorizar | Travessia guiada |
| **Materializar** conexões derivadas | Pré-cálculo |

## Otimização de consultas

| Prática | Efeito |
|---|---|
| **Comece de um vértice âncora** por `~id` ou rótulo + propriedade selecionada | Evita varredura do grafo inteiro |
| **Filtre o mais cedo possível** (`has`, `hasLabel`, `WHERE` junto ao `MATCH`) | Menos caminhos explorados |
| **Use `limit`** e paginação | Controle de resultados |
| **`dedup()` / `DISTINCT`** cedo quando adequado | Reduz duplicatas |
| **Evite `V()` sem filtro** e `g.V().has('propriedade', valor)` em grafos grandes sem âncora | Varredura completa |
| **Use `explain`/`profile`** | Mostra o plano e o custo por passo |
| **Execute leituras nas réplicas** | Escala de leitura |
| **Mantenha o working set em memória** | Escolha a classe com RAM suficiente; `BufferCacheHitRatio` alto |
| **Timeouts** (`neptune_query_timeout`) | Interrompe consultas descontroladas |
| **Concorrência** | O número de threads de consulta é proporcional aos vCPUs; filas longas indicam subdimensionamento |

```groovy
g.V().has('Conta','id','c1').out('USA').in('USA').dedup().limit(100).profile()    // veja o custo por passo
```

```bash
# Endpoint de explain (openCypher)
curl -s https://grafo-prod...:8182/openCypher -d "query=MATCH (n:Conta) RETURN n LIMIT 1" -d "explain=details"
```

## Consistência e transações

| Aspecto | Detalhe |
|---|---|
| **Escrita** | Na instância primária |
| **Isolamento** | Leituras em **READ COMMITTED** (writer) e **snapshot** nas réplicas; transações com isolamento serializável de escrita onde aplicável |
| **Réplicas** | Eventualmente consistentes (lag de ms) |
| **Transações** | ACID por requisição/transação; evite transações muito longas e grandes |
| **Concorrência de escrita** | Conflitos geram `ConcurrentModificationException` — a aplicação deve **tentar de novo** com backoff |
| **Idempotência** | `~id` definido pela aplicação e `mergeV`/`MERGE` para upserts |

```cypher
MERGE (c:Conta {id:'c1'}) ON CREATE SET c.criada = timestamp() SET c.status = 'ATIVA'      // upsert idempotente
```

## Exemplo prático

Grafo de fraude de um banco:

1. **Modelo:** vértices `Conta`, `Cliente`, `Dispositivo`, `Telefone`, `Endereço`, `Transação`; arestas `TITULAR_DE`, `USA` (com `ultimoAcesso`), `TEM_TELEFONE`, `RESIDE_EM`, `ENVIOU` (conta→transação) e `RECEBEU` (transação→conta).
2. **Supernós:** endereço corporativo e IPs de NAT tratados com **lista de exceções** e *buckets* (`Endereço` só entra nas travessias quando grau < 50).
3. **Consulta de risco** (openCypher): contas a até 2 saltos de uma conta fraudulenta confirmada via `Dispositivo` ou `Telefone`, com score por tipo de ligação.
4. **Padrões de anel:** `MATCH (a)-[:ENVIOU*2..4]->(a)` para circulação de dinheiro, limitada por janela de tempo.
5. **Operação:** consultas de produção em réplicas; `profile` nas 10 consultas mais caras; `neptune_query_timeout=30000`; carga por **bulk loader** (nota de carga).
6. **Resultado esperado:** o score de risco no momento da transação sai em ~30-80 ms em travessias de 2-3 saltos.

## Erros comuns e armadilhas

- **Modelar atributos compartilhados como propriedades** (impede percorrer por eles).
- **Travessias sem `LIMIT`/profundidade** em grafos densos.
- **Supernós** ignorados (explosão de resultados e latência).
- **Começar a consulta sem âncora** (`g.V()` + filtro por propriedade sem índice).
- **Esquecer `dedup()`** e retornar duplicatas gigantes.
- **Misturar rótulos genéricos** (`Node`, `Rel`) e perder semântica.
- **Escrever sem tratar conflitos** (`ConcurrentModificationException`) nem idempotência.
- **Usar SPARQL em dados de property graph** (ou vice-versa).
- **Guardar blobs** em propriedades.
- **Não usar `profile`/`explain`** para entender o custo.

## 🧩 Quiz de Fixação

1. Por que um atributo compartilhado (como um dispositivo) deve virar vértice?
2. Quais as diferenças entre Gremlin, openCypher e SPARQL?
3. O que é um supernó e como mitigá-lo?
4. Como tornar uma escrita idempotente no Neptune?

**Respostas:**
1) Porque só o que é vértice pode ser percorrido: com o dispositivo como nó, contas que o usam ficam a uma travessia curta de distância; como propriedade, seria preciso varrer e comparar valores.
2) Gremlin é imperativo (passos encadeados) para property graph; openCypher é declarativo, com padrões, para property graph e fácil para quem conhece SQL; SPARQL é declarativo para RDF (triplas) e semântica.
3) Um vértice com um número enorme de arestas que causa explosão de resultados; mitiga-se limitando profundidade e resultados, filtrando cedo, dividindo o nó em intermediários, excluindo-o de travessias de similaridade e materializando conexões derivadas.
4) Definindo o `~id` pela aplicação e usando `mergeV`/`MERGE` (upsert), com tratamento de conflitos e retry com backoff.
