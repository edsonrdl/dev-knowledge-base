### Segurança, backup, monitoramento e custo no Neptune — VPC, IAM SigV4, KMS, snapshots, métricas, logs de consultas lentas e dimensionamento

> [!warning] Aviso
> Parâmetros, métricas, políticas IAM de dados (`neptune-db:*`), limites e preços do Neptune mudam por versão. **Nenhum valor numérico é oficial.** Confirme na documentação e na calculadora da AWS. Os comandos **não foram executados**.

Fechando o Neptune: **proteger** o grafo (rede, criptografia, autenticação IAM com SigV4, autorização fina), **garantir recuperação** (backups, snapshots, PITR, clones), **observar** (métricas, logs de consultas lentas e de auditoria) e **controlar custos** (instâncias, armazenamento, I/O, Serverless, reservas, cargas). Muitos conceitos são os mesmos do Aurora e do DocumentDB; aqui destacam-se as particularidades do Neptune (porta 8182, IAM por SigV4, `neptune-db:*`, bulk loader e Streams).

**Analogia:** é a **administração de um arquivo secreto de investigações**: portaria e cofre (rede e criptografia), crachá com permissão por tipo de consulta (IAM), fotografias periódicas do arquivo (snapshots), câmeras (logs e métricas) e orçamento anual.

## Segurança em camadas

### 1. Rede

| Prática | Detalhe |
|---|---|
| **VPC e subnets privadas** | O cluster vive em um **subnet group** privado (≥ 2 AZs); **sem endpoint público** |
| **Security Group** | Libera a porta **8182** somente dos SGs de aplicações/bastion |
| **Acesso externo** | VPN, Direct Connect, peering, Transit Gateway; para ferramentas (notebooks, Graph-Explorer) em SG controlado atrás de SSO |
| **Endpoints VPC** | S3 (bulk loader), KMS, CloudWatch Logs |
| **Load balancer** | Se necessário, NLB/ALB interno na frente dos endpoints (atenção ao SigV4 e ao certificado) |

### 2. Criptografia

| Tipo | Como |
|---|---|
| **Em repouso** | **KMS** (`--storage-encrypted --kms-key-id`) para volume, backups, snapshots e logs; **definir na criação** (para criptografar um cluster existente: snapshot → cópia criptografada → restauração) |
| **Em trânsito** | **TLS 1.2+** obrigatório nos endpoints (HTTPS/WSS) |
| **Chaves** | CMK com política restrita e rotação; cuidado com exclusão/desativação — veja [[8. DevOps e Gerenciamento de Infraestrutura/CLOUD COMPUTING/AWS (AMAZON WEB SERVICE)/2. Segurança e Conformidade/2.3 Capacidades de gerenciamento de acesso da AWS/2.3.2. Serviços de segurança/2.3.2.7. AWS Key Management Service (KMS)|AWS KMS]] |
| **Bulk loader/S3** | SSE-S3/SSE-KMS no bucket; a role precisa de permissão na chave |

### 3. Autenticação e autorização (IAM)

O Neptune usa **IAM database authentication** com **assinatura SigV4** nas requisições HTTP/WebSocket (não há usuário/senha de banco).

| Elemento | Detalhe |
|---|---|
| **Habilitar** | `--iam-database-authentication-enabled` (ou `EnableIAMDatabaseAuthentication`) |
| **Clientes** | SDKs, `awscurl`, bibliotecas Gremlin/openCypher com assinatura SigV4; as credenciais vêm de **roles** (EC2, ECS, Lambda) |
| **Ações de dados** | `neptune-db:ReadDataViaQuery`, `neptune-db:WriteDataViaQuery`, `neptune-db:DeleteDataViaQuery`, `neptune-db:GetQueryStatus`, `neptune-db:CancelQuery`, `neptune-db:StartLoaderJob`, `neptune-db:ResetDatabase`, `neptune-db:GetStreamRecords`, `neptune-db:*` |
| **Recurso** | `arn:aws:neptune-db:região:conta:cluster-resource-id/*` |
| **Menor privilégio** | Aplicações de leitura só com `ReadDataViaQuery`; ETL com `WriteDataViaQuery` e loader; `ResetDatabase` restrito (apaga tudo) |
| **Condições** | `neptune-db:QueryLanguage` (Gremlin, OpenCypher, Sparql) para restringir linguagens |
| **Admin** | Ações de controle (`rds:*`/`neptune:*`) separadas: criar/excluir clusters, snapshots |

```json
{
  "Effect": "Allow",
  "Action": ["neptune-db:ReadDataViaQuery", "neptune-db:GetQueryStatus"],
  "Resource": "arn:aws:neptune-db:sa-east-1:111122223333:cluster-ABCDEFGHIJKL/*",
  "Condition": { "StringEquals": { "neptune-db:QueryLanguage": "OpenCypher" } }
}
```

```bash
# Chamada assinada com SigV4 (awscurl)
awscurl --service neptune-db --region sa-east-1 -X POST \
  https://grafo-prod.cluster-xxxx.sa-east-1.neptune.amazonaws.com:8182/openCypher -d "query=MATCH (n) RETURN count(n)"
```

Observação: o controle é por **tipo de operação** (ler/escrever/apagar) e linguagem, **não** por vértice ou propriedade; para isolamento por tenant/entidade, aplique a regra na aplicação (filtros em todas as consultas) ou use clusters/grafos separados.

### 4. Auditoria e governança

| Mecanismo | Detalhe |
|---|---|
| **Audit log** | Parâmetro `neptune_enable_audit_log = 1`; registra conexões, consultas e falhas de autenticação; exportar para **CloudWatch Logs** (`audit`) |
| **Slow query log** | `neptune_enable_slow_query_log = info\|debug`, `neptune_slow_query_log_threshold` (ms) |
| **CloudTrail** | Chamadas de API de controle |
| **Config/Security Hub** | Regras de criptografia, IAM auth, proteção contra exclusão, backups |
| **GuardDuty** | Atividade anômala |
| **Tags e SCP** | Governança em escala |
| **Deletion protection** | Impede exclusão acidental do cluster |

## Backup e recuperação

| Mecanismo | Característica |
|---|---|
| **Backup contínuo** | Incremental no volume, sem impacto; retenção **1 a 35 dias** |
| **PITR** | Restaura para qualquer segundo da retenção, criando **novo cluster** |
| **Snapshots manuais** | Sem expiração; copiáveis entre regiões e compartilháveis entre contas (criptografados com CMK) |
| **Clonagem** | Cluster novo por *copy-on-write*, em minutos (homologação, testes, ML) |
| **Exportação lógica** | Neptune-Export para S3 (migração/análise); **não substitui** os backups |
| **Global Database** | Resiliência regional; **não** substitui backup |
| **AWS Backup** | Políticas centralizadas, cópia entre contas/regiões |

```bash
aws neptune modify-db-cluster --db-cluster-identifier grafo-prod --backup-retention-period 14 --apply-immediately
aws neptune create-db-cluster-snapshot --db-cluster-identifier grafo-prod --db-cluster-snapshot-identifier grafo-pre-carga
aws neptune restore-db-cluster-to-point-in-time --db-cluster-identifier grafo-pitr --source-db-cluster-identifier grafo-prod \
  --restore-to-time 2026-11-06T14:30:00Z --db-subnet-group-name sg-neptune --vpc-security-group-ids sg-0nep123
aws neptune create-db-instance --db-instance-identifier grafo-pitr-1 --db-cluster-identifier grafo-pitr --engine neptune --db-instance-class db.r6g.xlarge
```

Lembretes: a restauração cria um **novo cluster** (reassocie parameter groups, SG, roles e crie instâncias); backups automáticos somem com o cluster (snapshot final); teste a restauração e meça o RTO; veja também o [[8. DevOps e Gerenciamento de Infraestrutura/CLOUD COMPUTING/AWS (AMAZON WEB SERVICE)/3. Tecnologia e Serviços/3.3 Serviços principais da AWS/3.3.2. Armazenamento/3.3.2.6. AWS Backup/0 AWS Backup (Tópicos )|AWS Backup]].

## Monitoramento

### Métricas CloudWatch (`AWS/Neptune`)

| Métrica | Interpretação | Alerta típico |
|---|---|---|
| `CPUUtilization` | CPU da instância | > 80% sustentado |
| `FreeableMemory` | Memória livre | Queda contínua |
| `BufferCacheHitRatio` | % de leituras atendidas pelo cache | < 99% em OLTP |
| `MainRequestQueuePendingRequests` | Requisições na fila (threads ocupadas) | > 0 sustentado |
| `GremlinRequestsPerSec`, `OpenCypherRequestsPerSec`, `SparqlRequestsPerSec`, `TotalRequestsPerSec` | Vazão por linguagem | Mudança de padrão |
| `GremlinWebSocketOpenConnections` | Conexões WebSocket | Perto do limite |
| `ClusterReplicaLag` / `ClusterReplicaLagMaximum` | Atraso das réplicas | > 1 s sustentado |
| `VolumeBytesUsed` | Tamanho do volume | Tendência de crescimento |
| `VolumeReadIOPs` / `VolumeWriteIOPs` | I/O faturado | Picos; custo |
| `LoaderRequestsFailed`, `BulkLoad...` | Falhas do loader | > 0 |
| `StatsNumStatementsScanned` | Instruções varridas | Consultas ineficientes |
| `NCUUtilization`, `ServerlessDatabaseCapacity` | Serverless | Perto do máximo |

### Ferramentas de diagnóstico

| Ferramenta | Uso |
|---|---|
| **Status API** (`/status`) | Saúde, versão, features |
| **Query status API** (`/gremlin/status`, `/openCypher/status`, `/sparql/status`) | Consultas em execução, tempo, ids; **cancelar** consultas (`cancelQuery`) |
| **`explain` / `profile`** | Plano e custo por passo |
| **Slow query log** | Consultas acima do limiar |
| **Performance Insights** | Carga do banco e top queries (se suportado) |
| **Neptune workbench / Graph-Explorer** | Exploração e depuração |

```bash
curl -s https://grafo-prod...:8182/openCypher/status                      # consultas em execução
curl -s -X POST https://grafo-prod...:8182/openCypher/status -d "cancelQuery&queryId=<id>"    # cancelar
```

Parâmetros úteis do cluster: `neptune_query_timeout` (ms; padrão 120000), `neptune_lab_mode` (recursos experimentais; evite em produção), `neptune_enable_audit_log`, `neptune_streams`.

## Custo

| Componente | Observação |
|---|---|
| **Instâncias** | Por hora, por classe; primária e réplicas; Graviton melhor custo-benefício |
| **Serverless** | NCU-hora |
| **Armazenamento** | GB-mês do volume (cresce sozinho) |
| **I/O** | Standard: por milhão de requisições; **I/O-Optimized**: sem cobrança de I/O |
| **Backup** | Acima do tamanho do volume; snapshots |
| **Transferência** | Entre AZs/regiões/internet |
| **Global Database** | Instâncias da secundária + replicação de I/O + transferência |
| **Neptune Analytics** | m-NCU-hora + armazenamento |
| **Neptune ML** | SageMaker (treinamento/endpoint) + S3 |
| **Reservas** | Reserved Instances (1 e 3 anos) para a base provisionada estável |

### Alavancas de economia

1. **Rightsizing** conforme `CPUUtilization`, `FreeableMemory` e cache hit.
2. **Graviton** e classes adequadas ao working set.
3. **Serverless** para cargas variáveis/dev.
4. **I/O-Optimized** quando I/O > ~25% da fatura.
5. **Reservas** na base estável.
6. **Cargas em lote** com instância temporariamente maior e depois reduzir.
7. **Dev/test** com `db.t4g.medium`, Single-AZ, **parar** o cluster quando possível (até 7 dias).
8. **Consultas eficientes** (menos I/O e CPU).
9. **Snapshots** com retenção adequada; apagar órfãos.
10. **Tags e orçamentos**.

## Checklist de produção

- [ ] Cluster em subnets privadas; SG restrito na 8182; sem acesso público.
- [ ] Criptografia em repouso (CMK) e TLS; **IAM database authentication** habilitada.
- [ ] Policies `neptune-db:*` por função (leitura, escrita, loader, admin) e `ResetDatabase` restrito.
- [ ] Audit log e slow query log exportados ao CloudWatch Logs.
- [ ] Backup 14-35 dias; snapshot final; deletion protection; teste de restauração.
- [ ] Réplica em outra AZ; failover testado; reader endpoint nas leituras.
- [ ] Alarmes: CPU, memória, cache hit, fila, `ClusterReplicaLag`, conexões, volume, falhas do loader.
- [ ] `neptune_query_timeout` ajustado; consultas com `LIMIT` e profundidade controlada.
- [ ] Parameter groups versionados em IaC.
- [ ] Orçamentos, tags, revisão mensal de custo e de rightsizing.

## Exemplo prático

Operação do grafo de fraude de um banco:

1. **Rede/acesso:** SG-neptune aceita 8182 só do SG da API de risco e do SG do job de carga; sem acesso público; Graph-Explorer atrás de SSO em subnet privada.
2. **IAM:** role `risco-api` com `ReadDataViaQuery` (OpenCypher); role `carga-etl` com `WriteDataViaQuery`, `StartLoaderJob` e `GetLoaderJobStatus`; ninguém (exceto break-glass) com `ResetDatabase`.
3. **Logs:** audit log e slow query log (limiar 500 ms) no CloudWatch Logs; alerta em falhas de autenticação repetidas e consultas > 5 s.
4. **Backup:** retenção de 21 dias; snapshots antes de cada carga grande; cópia semanal para outra região/conta via AWS Backup; PITR testado trimestralmente (RTO 40 min).
5. **Capacidade:** primária `r6g.2xlarge` + 2 réplicas; alarme em `BufferCacheHitRatio` < 99%; `MainRequestQueuePendingRequests` > 0 por 5 min dispara Auto Scaling de réplicas.
6. **Custo:** I/O era 31% da fatura → I/O-Optimized; Reserved Instances de 1 ano para a primária e uma réplica; ambiente de homologação parado à noite.
7. **Governança:** AWS Config exige criptografia, IAM auth e backup ≥ 14 dias; revisão trimestral de policies e consultas lentas.

## Erros comuns e armadilhas

- **IAM authentication desabilitada** (endpoint acessível a qualquer cliente da VPC).
- **Assinatura SigV4 mal configurada** e credenciais expiradas em clientes de longa duração.
- **Policy `neptune-db:*` para todos**, inclusive `ResetDatabase`.
- **Cluster sem criptografia** (não dá para ligar depois).
- **Audit logs desabilitados** até o incidente.
- **`neptune_query_timeout` altíssimo ou ilimitado:** consultas descontroladas.
- **`neptune_lab_mode` em produção.**
- **Sem teste de restauração** e sem snapshot antes de cargas grandes.
- **Memória insuficiente** (cache hit baixo) e custo de I/O alto.
- **Achar que IAM isola vértices/propriedades:** o controle é por operação e linguagem.
- **Streams/Loader sem monitoramento e alarmes.**

## 🧩 Quiz de Fixação

1. Como funciona a autenticação do Neptune e que ações IAM controlam os dados?
2. O que o IAM do Neptune **não** consegue controlar?
3. Como diagnosticar e cancelar uma consulta que consome recursos demais?
4. Quando migrar para I/O-Optimized?

**Respostas:**
1) Por IAM database authentication com requisições assinadas por SigV4 (sem usuário/senha de banco); as ações de dados são `neptune-db:ReadDataViaQuery`, `WriteDataViaQuery`, `DeleteDataViaQuery`, `StartLoaderJob`, `GetQueryStatus`, `CancelQuery`, `ResetDatabase`, entre outras, sobre o recurso do cluster.
2) Não controla acesso por vértice, aresta ou propriedade; o controle é por tipo de operação e linguagem. Isolamento por tenant deve ser feito na aplicação ou com clusters/grafos separados.
3) Com as APIs de status de consulta (`/openCypher/status`, `/gremlin/status`, `/sparql/status`), `explain`/`profile` e o slow query log para achar o problema, e com `cancelQuery` (permissão `CancelQuery`) para interromper; além de ajustar `neptune_query_timeout`.
4) Quando o custo de I/O representa uma parcela relevante da fatura (da ordem de um quarto) ou se quer custo previsível, pois nesse modo não há cobrança de I/O.
