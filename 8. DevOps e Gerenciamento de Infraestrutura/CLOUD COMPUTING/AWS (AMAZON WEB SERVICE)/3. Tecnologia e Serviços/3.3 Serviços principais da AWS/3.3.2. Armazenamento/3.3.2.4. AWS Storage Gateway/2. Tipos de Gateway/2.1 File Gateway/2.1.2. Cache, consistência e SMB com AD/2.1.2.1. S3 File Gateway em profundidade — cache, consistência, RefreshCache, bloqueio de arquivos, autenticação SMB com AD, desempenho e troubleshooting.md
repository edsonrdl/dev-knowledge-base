### S3 File Gateway em profundidade — cache, consistência, RefreshCache, bloqueio de arquivos, autenticação SMB com AD, desempenho e troubleshooting

> [!warning] Aviso
> Parâmetros do file share (políticas de notificação de upload, tempo de validade do cache, modos de autenticação), limites por gateway, métricas e comportamentos do Storage Gateway mudam. Os números são **ordens de grandeza**. **Confirme na documentação.** Os comandos **não foram executados**; operações como renomear diretórios grandes ou limpar o cache **podem gerar muitos objetos no S3 e custo**.

O S3 File Gateway parece simples — "uma pasta de rede que grava no S3" —, mas na prática há decisões que definem se ele será **estável e rápido** ou uma **fonte constante de chamados**: como o **cache** funciona e deve ser dimensionado, **quando as mudanças aparecem** (consistência entre cliente, gateway e S3), como o **bloqueio de arquivos** se comporta, como funciona a **autenticação SMB com Active Directory**, o que **degrada o desempenho** (arquivos pequenos, renomeações, listagens) e como **diagnosticar**. Esta nota aprofunda esses pontos.

**Analogia:** o gateway é um **balcão de atendimento local com uma prateleira (cache) e um malote para o depósito central (S3)**. Entregar um arquivo no balcão é rápido; o malote só sai depois que você "fecha a pasta"; e se alguém colocar algo diretamente no depósito, o balcão só fica sabendo quando **alguém lhe conta (refresh)**.

## Fluxo de dados e o cache

```
 Cliente (NFS/SMB) ──escrita──► CACHE LOCAL (disco do gateway) ──[após fechar o arquivo / período ocioso]──► upload assíncrono ──► S3
 Cliente ◄──leitura (hit)── CACHE LOCAL       ◄──leitura (miss)── S3 (GET) ──► copia para o cache
```

| Aspecto | Detalhe |
|---|---|
| **Cache de escrita** | Dados escritos ficam no disco de cache até serem enviados ao S3; o cliente recebe a confirmação **antes do upload** |
| **Cache de leitura** | Dados lidos/recentemente escritos permanecem no cache (política LRU); *hit* tem latência de disco local |
| **Upload** | Assíncrono, em paralelo; iniciado após o arquivo ser **fechado** e um período de inatividade configurado |
| **Disco de cache** | Dedicado, **SSD/NVMe** de preferência; não compartilhar com o SO; tamanho ≥ conjunto de trabalho de leitura + folga para escrita pendente |
| **Métricas** | `CachePercentUsed`, `CachePercentDirty` (dados ainda não enviados), `CacheHitPercent`, `CloudBytesUploaded/Downloaded`, `UploadBufferPercentUsed` (n/a File) |
| **Risco** | Se o gateway falhar com dados **sujos** (não enviados), eles podem ser perdidos; mantenha `CachePercentDirty` baixo e a rede suficiente |

### Dimensionamento

| Fator | Regra prática |
|---|---|
| **Cache** | ~ o conjunto de arquivos acessados no período típico (dias); mínimo recomendado de centenas de GB para uso real |
| **Throughput de upload** | Média diária de escrita + pico: a rede precisa drenar o `dirty` antes do próximo ciclo |
| **CPU/RAM** | Seguir requisitos por tipo de implantação; mais RAM melhora o cache de metadados |
| **Disco** | IOPS do disco de cache importa tanto quanto a banda do link |
| **Número de gateways** | Escala horizontal: vários gateways para vários shares/equipes, em vez de um enorme |

## Mapeamento e consistência

### Arquivo ↔ objeto

| Conceito | Comportamento |
|---|---|
| **Arquivo** | Objeto S3 cuja chave é o caminho (`/projetos/a.docx` → `projetos/a.docx`) |
| **Diretório** | Objeto de **zero bytes** com sufixo `/` (marcador) |
| **Metadados POSIX/NTFS** | Guardados como metadados do objeto (permissões, UID/GID, timestamps) |
| **Tamanho máximo** | Arquivos até ~5 TiB (limite do S3 por objeto) |
| **Renomear** | **Cópia + exclusão** no S3 (não existe rename); renomear diretórios com milhares de arquivos gera **milhares de operações** (lento, caro) |
| **Alterações parciais** | Reescrita do **objeto inteiro** a cada alteração (não é uma API de blocos); arquivos grandes editados com frequência geram tráfego e versões |
| **Versionamento do S3** | Cada gravação cria uma versão; combine com lifecycle de versões |

### Quando as mudanças aparecem

| Origem da mudança | Visível para... |
|---|---|
| **Via o mesmo gateway** | Imediatamente para os clientes desse gateway (cache) |
| **Via outro gateway** (mesmo bucket) | Somente após o **upload** do primeiro e a **atualização do cache** do segundo |
| **Direto no S3** (aplicação, outro serviço) | Somente após **RefreshCache** (manual ou automático) |
| **Para o S3** | Após o upload assíncrono (segundos a minutos; depende do volume e da banda) |

**Políticas relevantes do file share:**

| Política | Função |
|---|---|
| **Notificação de upload concluído** (`NotificationPolicy`) | Quanto esperar após a **última gravação** para considerar o arquivo "concluído" e notificar (EventBridge); impacta o disparo de pipelines |
| **Cache stale timeout / refresh automático** (`CacheAttributes` com `CacheStaleTimeoutInSeconds`) | Intervalo em que o gateway revalida diretórios com o S3 sem refresh manual |
| **Classe de armazenamento padrão** | Onde os novos objetos caem (Standard, Intelligent-Tiering, IA…) |
| **Object ACL, KMS, Requester pays** | Propriedades de gravação |
| **Squash / Read-only / lista de clientes** | Controle de acesso NFS |

```bash
# Atualizar manualmente o conteúdo de um diretório (após escritas diretas no S3)
aws storagegateway refresh-cache --file-share-arn $SHARE_ARN --folder-list "/projetos/2026" --recursive
# Revalidar automaticamente a cada 5 minutos
aws storagegateway update-nfs-file-share --file-share-arn $SHARE_ARN --cache-attributes CacheStaleTimeoutInSeconds=300
# Automatizar: EventBridge (s3:ObjectCreated) -> Lambda -> RefreshCache da pasta do prefixo
```

Padrão arquitetural: **evite escrita direta no mesmo prefixo por gateway e aplicação ao mesmo tempo**; designe um "dono" por prefixo, ou use **share dedicado** para escrita on-premises e outro caminho para ingestão em nuvem.

## Bloqueio de arquivos e concorrência

| Cenário | Comportamento |
|---|---|
| **Vários clientes no mesmo gateway** | Locks SMB/NFS são respeitados localmente pelo gateway (oplocks/byte-range) |
| **Vários gateways no mesmo bucket** | **Não há bloqueio distribuído** entre gateways; dois usuários editando o mesmo arquivo em gateways diferentes → **última escrita vence** (conflito) |
| **Gravação direta no S3** | Ignora locks do gateway |
| **Aplicações que exigem locks fortes** (bancos de dados, Office com autosave concorrente, VMDK) | **Não** usar S3 File Gateway; usar FSx/EFS/NAS |
| **Boas práticas** | Particionar por equipe/escritório (um gateway por área), definir donos, usar o gateway apenas para padrões de acesso "um escritor por vez" |

## Autenticação e permissões

### NFS

| Item | Detalhe |
|---|---|
| **Lista de clientes** | CIDRs permitidos a montar (`ClientList`) |
| **Squash** | `RootSquash`, `NoSquash`, `AllSquash` |
| **UID/GID** | Gravados como metadados; padronizar entre clientes |

### SMB com Active Directory

| Item | Detalhe |
|---|---|
| **Modos** | **Active Directory** (recomendado) ou **Guest access** (evite em produção) |
| **Ingresso no domínio** | O gateway **entra no domínio** com uma conta com permissão de criar objetos de computador; precisa de DNS e hora sincronizados |
| **Admin/ACLs** | ACLs de compartilhamento via `ValidUserList`, `InvalidUserList`, `AdminUserList`; ACLs NTFS detalhadas aplicadas por clientes Windows (armazenadas nos metadados) |
| **Enumeração baseada em acesso** (`AccessBasedEnumeration`) | Esconde itens sem permissão |
| **Criptografia SMB** (`SMBSecurityStrategy`): `ClientSpecified`, `MandatorySigning`, `MandatoryEncryption` | Exige assinatura/criptografia |
| **Auditoria** | Logs de auditoria do file share para CloudWatch Logs |
| **Kerberos** | Suportado com ingresso no AD; atenção ao SPN/nomes |
| **AWS Managed AD / AD on-premises** | Conectividade (DNS, portas de AD) entre o gateway e os DCs |

```bash
aws storagegateway join-domain --gateway-arn $GW_ARN --domain-name empresa.local \
  --user-name svc-gw --password '***' --organizational-unit "OU=Gateways,DC=empresa,DC=local" --domain-controllers dc1.empresa.local
aws storagegateway create-smb-file-share --client-token tok-2 --gateway-arn $GW_ARN \
  --role arn:aws:iam::111122223333:role/sgw-acesso-s3 --location-arn arn:aws:s3:::arquivos-escritorio \
  --authentication ActiveDirectory --smb-acl-enabled --access-based-enumeration \
  --admin-user-list "empresa\\admins-ti" --default-storage-class S3_INTELLIGENT_TIERING --smb-security-strategy MandatoryEncryption
```

Dicas: o gateway **precisa resolver o domínio** (DNS apontando para os DCs); o relógio (NTP) deve estar sincronizado (Kerberos); reingressar ao domínio após mudança de senha da conta de serviço; permissões do bucket concedidas **à role do gateway** (não aos usuários).

## Desempenho

| Fator | Orientação |
|---|---|
| **Cache hit** | Leituras repetidas do conjunto de trabalho: dimensione o cache; `CacheHitPercent` alto |
| **Latência de cache miss** | Primeiro acesso baixa do S3 (round trip + transferência); arquivos grandes demoram |
| **Arquivos pequenos** | Cada arquivo = 1 objeto: muitas requisições, custo e latência; **agrupe** (tar/zip) quando possível |
| **Diretórios gigantes** | Listagens custosas; use hierarquia |
| **Operações de metadados** | `ls -l`, antivírus no cliente varrendo tudo, indexadores (Windows Search) → tráfego e requisições; excluir o share dos indexadores |
| **Renomeação em massa** | Evitar (copiar/excluir objetos) |
| **Upload** | Link com banda suficiente, ajuste de limite de banda para não saturar o escritório |
| **Disco de cache** | SSD; separar do disco raiz |
| **Gateway em EC2 vs on-premises** | Latência para o S3 menor em EC2; on-premises depende do link |
| **Endpoint** | VPC endpoint (PrivateLink) ou Direct Connect para tráfego estável |
| **Paralelismo no cliente** | Várias transferências simultâneas (robocopy `/MT`, rsync paralelo) |

## Monitoramento e troubleshooting

### Métricas e alarmes (`AWS/StorageGateway`)

| Métrica | Alerta |
|---|---|
| `CachePercentDirty` | Alto e crescente (upload não acompanha) |
| `CachePercentUsed` | > 90% (risco de despejo/espera) |
| `CacheHitPercent` | Baixo (cache pequeno) |
| `CloudBytesUploaded` / `CloudBytesDownloaded` | Tendência e picos |
| `ReadBytes` / `WriteBytes`, `IoWaitPercent` | Carga e latência de disco |
| `HealthNotification`, `AvailabilityNotifications` (eventos) | Gateway fora do ar |
| `FileShareHealth` | Estado do share |

### Problemas comuns

| Sintoma | Causas | Ação |
|---|---|---|
| **Arquivos criados no S3 não aparecem** | Cache desatualizado | `RefreshCache` / `CacheStaleTimeoutInSeconds` / automação com EventBridge |
| **Alterações do usuário não chegam ao S3** | Arquivo ainda aberto, upload pendente, rede/permissões | Fechar o arquivo; ver `CachePercentDirty`; permissões da role/KMS |
| **Erro de acesso (Access Denied) ao gravar** | Role sem `s3:PutObject`, política do bucket, SSE-KMS sem permissão, Block Public Access/objeto ACL | Revisar role, bucket policy, chave KMS |
| **Conflito de edição** | Dois gateways/escritores | Redesenhar: um escritor por prefixo |
| **Lentidão geral** | Cache miss, link saturado, disco lento, antivírus/indexador | Cache/SSD, limites de banda, excluir da indexação |
| **SMB: falha de ingresso no domínio / acesso negado** | DNS, hora, conta sem permissão, SPN, nomes | `join-domain`, DNS, NTP, logs de auditoria |
| **Diretório renomeado ficou lento/caro** | Cópia + exclusão de milhares de objetos | Evitar; planejar estrutura |
| **Objeto em Glacier não abre** | Classe de armazenamento arquivada | Restaurar o objeto no S3 antes (ou não arquivar o prefixo) |
| **Cache cheio de dados sujos** | Upload lento/interrompido | Aumentar link/cache; reduzir carga; investigar erros |
| **Share "unhealthy"** | Gateway sem acesso ao bucket/KMS, nome do bucket | Reconfigurar permissões/endpoint |

## Exemplo prático

Escritório regional (250 usuários, 12 TB, link de 500 Mbps) migrando o NAS para o S3 com S3 File Gateway:

1. **Implantação:** VM VMware com 16 vCPUs, 32 GB RAM, **cache de 4 TB em SSD** (conjunto de trabalho de ~3 TB) e disco raiz separado; gateway ativado em `sa-east-1`, conectividade por VPC endpoint via Direct Connect.
2. **Share SMB** com AD: `ActiveDirectory`, `SMBSecurityStrategy=MandatoryEncryption`, `AccessBasedEnumeration`, grupo `admins-ti` como administrador; classe padrão **S3 Intelligent-Tiering**; versionamento do bucket com lifecycle (versões antigas → IA após 30 dias, expiração em 180).
3. **Regras:** pastas por departamento, cada uma escrita por **um único** gateway; ingestão de relatórios pelo pipeline em nuvem em um prefixo próprio, com **EventBridge → Lambda → RefreshCache** daquele prefixo.
4. **Operação:** limite de banda de upload 300 Mbps em horário comercial; alarmes em `CachePercentDirty` > 40%, `CachePercentUsed` > 85%, `CacheHitPercent` < 70%; indexador do Windows e antivírus configurados para ignorar o share.
5. **Validação:** teste de queda do gateway (reiniciar a VM com dados sujos baixos), de restauração de arquivo via versionamento do S3 e de reingresso no domínio.
6. **Resultado:** o NAS foi aposentado, o custo de armazenamento caiu ~40% com Intelligent-Tiering e a TI recuperou versões antigas sem backup separado.

## Erros comuns e armadilhas

- **Cache subdimensionado** (ou no mesmo disco do SO).
- **Esperar que a escrita direta no S3 apareça sem refresh.**
- **Dois gateways/escritores no mesmo prefixo** (conflitos silenciosos).
- **Usar para bancos de dados, VMs ou edição concorrente** com locks fortes.
- **Renomear pastas grandes** e gerar milhares de operações.
- **Milhões de arquivos minúsculos** sem agrupamento.
- **Guest access** no SMB em produção.
- **DNS/hora errados** na integração com AD.
- **Role sem permissão em KMS/bucket** (falhas de upload).
- **Antivírus/indexador varrendo o share** e gerando custo de requisições.
- **Perder dados sujos** em falha do gateway sem monitorar `CachePercentDirty`.
- **Lifecycle para Glacier em dados que os usuários ainda leem.**

## 🧩 Quiz de Fixação

1. Quando um arquivo gravado no File Gateway chega ao S3 e que risco há nesse intervalo?
2. Como fazer o gateway enxergar um objeto criado diretamente no S3?
3. Por que dois gateways no mesmo prefixo são problemáticos?
4. Que requisitos há para o gateway SMB autenticar com Active Directory?

**Respostas:**
1) Depois que o arquivo é fechado e passa um período de inatividade, o upload é assíncrono; até lá os dados estão apenas no cache ("sujos") e podem se perder se o gateway falhar antes do envio.
2) Executando o RefreshCache (manual ou automatizado via EventBridge e Lambda) ou configurando o tempo de revalidação automática do cache (`CacheStaleTimeoutInSeconds`).
3) Não existe bloqueio distribuído entre gateways: edições simultâneas do mesmo arquivo resultam em conflito e a última escrita vence; além disso, um só enxerga o que o outro enviou depois do upload e do refresh.
4) Ingressar o gateway no domínio com uma conta com permissão de criar objetos de computador, DNS apontando para os controladores de domínio, hora sincronizada, conectividade nas portas de AD e uma role com acesso ao bucket e à chave KMS.
