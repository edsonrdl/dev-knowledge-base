### Tape Gateway e Volume Gateway na prática — integração com software de backup, ciclo de vida de fitas, DR em EC2, dimensionamento de cache e troubleshooting

> [!warning] Aviso
> Limites de fitas e volumes, tamanhos máximos, classes de arquivamento, compatibilidade de software de backup, recursos de retenção e preços mudam. Os números são **ordens de grandeza**. **Confirme a matriz de compatibilidade e os limites na documentação.** Os comandos **não foram executados**; ejetar, arquivar ou excluir fitas/volumes **pode ser irreversível**.

A nota anterior apresentou os modos do **Volume Gateway** (cached/stored) e do **Tape Gateway** (VTL). Aqui vamos à **prática**: como **dimensionar o cache e o buffer**, como **integrar com softwares de backup** (Veeam, NetBackup, Commvault, etc.), como funciona o **ciclo de vida das fitas** (ativas, ejetadas, arquivadas, recuperadas, retenção bloqueada), como montar o **DR em EC2** e como **diagnosticar** os problemas mais comuns (fila de upload, lentidão, falha de job de backup).

**Analogia:** o Tape Gateway é uma **biblioteca de fitas virtual com um cofre no subsolo (Glacier)**: o software de backup carrega e descarrega "fitas" como sempre, mas elas são arquivos no S3, e as fitas antigas são enviadas ao cofre. O Volume Gateway é um **armário de discos que mantém cópias de segurança automáticas na nuvem**.

## Tape Gateway: componentes e ciclo de vida

```
 Software de backup ──iSCSI──► Tape Gateway (changer + drives virtuais)
   ┌─ fitas ATIVAS (na VTL) ─ armazenadas no S3 (Standard), cache local
   └─ fita EJETADA ─► ARQUIVADA (Glacier Flexible Retrieval / Deep Archive) ─► RECUPERADA (volta à VTL) ─► uso para restauração
```

| Elemento | Detalhe |
|---|---|
| **Media changer + drives** | Dispositivos iSCSI que o software de backup enxerga (modelos compatíveis) |
| **Fitas virtuais** | Tamanho de ~100 GiB a ~15 TiB cada; criadas automaticamente (`auto-create`) ou manualmente; **código de barras** com prefixo |
| **VTL** | Fitas disponíveis para uso (no S3) |
| **Pool de arquivamento** | **Glacier Flexible Retrieval** ou **S3 Glacier Deep Archive** (a escolha define o custo e o tempo de recuperação) |
| **Ejeção** | O software ejeta a fita → o gateway a **arquiva** no pool escolhido |
| **Recuperação** | `retrieve-tape` traz a fita arquivada de volta à VTL (horas) |
| **Retenção bloqueada** (*tape retention lock*) | Impede a exclusão/recuperação prematura da fita arquivada por um período (governance/compliance) |
| **Exclusão** | Fita arquivada apagada manualmente (sujeita a custos de exclusão antecipada nas classes Glacier) |
| **Cache + upload buffer** | Disco local para dados recentes e para dados em trânsito |

### Pools e tempo de recuperação (indicativo)

| Pool | Recuperação | Custo |
|---|---|---|
| **Glacier Flexible Retrieval** | Algumas horas | Menor que S3, maior que Deep Archive |
| **Deep Archive** | ~12 horas ou mais | **Menor custo** (retenção longa, conformidade) |

## Integração com softwares de backup

| Tema | Orientação |
|---|---|
| **Compatibilidade** | Verifique a **matriz suportada** (Veeam, Veritas NetBackup, Commvault, Dell EMC NetWorker, IBM Spectrum Protect, Microsoft DPM/System Center, Bacula etc.) e versões |
| **Detecção** | Initiators iSCSI no servidor de backup (Windows iSCSI Initiator, `iscsiadm`) conectam ao changer e aos drives; rodar inventário no software |
| **Mídia** | Defina pools de mídia por política (diária, semanal, mensal, anual) com **retenção** coerente com o pool de arquivamento |
| **Tamanho das fitas** | Mais fitas menores → recuperação mais granular; menos fitas grandes → menos objetos; ajuste ao job |
| **Paralelismo** | Número de drives virtuais (até dezenas) × jobs simultâneos; evite saturar o link |
| **Janela de backup** | O fluxo é **limitado pela rede de upload** para a nuvem; planeje o tamanho do backup diário vs banda |
| **Reutilização de fitas** | Fitas expiradas pelo software podem ser reutilizadas; **fitas arquivadas** não (exclua/recupere conforme política) |
| **Catálogo do software** | Mantenha o **catálogo/banco** do software de backup protegido (ele sabe em qual fita está cada arquivo) — um servidor de backup perdido sem catálogo exige reinventariar fitas |

### Fluxo de restauração

```
 1. Restauração pede a fita X (arquivada)
 2. retrieve-tape (Glacier: horas)  → fita volta à VTL
 3. Software de backup inventaria e lê a fita
 4. Dados restaurados ao destino
```

Dica: para **restaurações frequentes ou rápidas**, mantenha as últimas semanas em fitas **ativas** (na VTL/S3) e arquive só as antigas; para **DR**, consulte a seção de EC2.

```bash
aws storagegateway create-tapes --gateway-arn $GW_ARN --tape-size-in-bytes 2199023255552 --client-token tok-3 \
  --num-tapes-to-create 10 --tape-barcode-prefix BKP --pool-id DEEP_ARCHIVE
aws storagegateway list-tapes --query 'TapeInfos[].{Barcode:TapeBarcode,Status:TapeStatus,Tamanho:TapeSizeInBytes,Pool:PoolId}'
aws storagegateway retrieve-tape --tape-arn $TAPE_ARN --gateway-arn $GW_RESTORE_ARN
# Bloqueio de retenção: define a fita arquivada como protegida por 7 anos
aws storagegateway update-tape-pool ... # (ou política de retenção por pool; consulte a API atual)
```

## Dimensionamento do cache e do upload buffer

| Disco | Função | Regra |
|---|---|---|
| **Cache** | Dados recentes para leitura (restaurações rápidas) | Pelo menos o volume de backup de **1-2 dias** que pode precisar restaurar; SSD de preferência |
| **Upload buffer** | Dados aguardando envio à AWS | Suficiente para a **maior janela de backup**: `taxa de ingestão − taxa de upload` × tempo; típico 150 GiB+ por TB/dia (ajuste) |
| **Link de upload** | Taxa efetiva para a AWS | `dados_do_dia ÷ janela_de_tempo`: 4 TB em 10 h exige ~1 Gbps efetivo |
| **CPU/RAM** | Requisitos mínimos por tipo de implantação | Mais RAM melhora o desempenho |

Cálculo de exemplo:

```
 Backup diário: 3 TB a gravar em 8 h; link de upload efetivo: 400 Mbps (≈ 180 GB/h → 1,44 TB em 8 h)
 Excedente a bufferizar: 3 TB − 1,44 TB = 1,56 TB → upload buffer ≥ 2 TB (com folga) e janela total real ≈ 17 h
 Soluções: link maior (Direct Connect), reduzir o volume (incremental/deduplicação), ou ampliar a janela
```

Se o buffer enche, o gateway **rejeita novas gravações** e os jobs falham: alarmes de `UploadBufferPercentUsed` e `CachePercentDirty`.

## Volume Gateway na prática

| Tema | Cached | Stored |
|---|---|---|
| **Dados primários** | Na AWS (S3), cache local | No gateway (local) |
| **Capacidade por volume** | Muito alta (dezenas de TiB) | Menor (até ~16 TiB) |
| **Quando** | Expandir capacidade sem hardware; leituras quentes locais | Latência baixa a **todo** o dataset, backup na nuvem |
| **Snapshots** | EBS snapshots (agendados/manuais), incrementais | Idem |
| **Restauração/DR** | Criar volume EBS do snapshot e anexar a EC2; ou **clonar** um volume do gateway | Idem |
| **Bandwidth** | Leituras fora do cache vão à AWS | Apenas o upload do backup |

### Snapshots e recuperação

- Snapshots do Volume Gateway aparecem como **EBS snapshots**: você pode criar **volumes EBS** e anexar a instâncias EC2 (**DR na nuvem**) ou **restaurar** um volume do gateway a partir do snapshot.
- **Política de snapshots**: agendamento por volume; integração com AWS Backup.
- **Consistência de aplicação**: quiesce (VSS no Windows, flush em bancos) antes do snapshot; ou snapshots crash-consistent.

```bash
aws storagegateway create-snapshot-schedule ... # (ver update-snapshot-schedule)
aws storagegateway update-snapshot-schedule --volume-arn $VOL_ARN --start-at 2 --recurrence-in-hours 6 --description "snap 6h"
aws storagegateway create-cached-iscsi-volume --gateway-arn $GW_ARN --volume-size-in-bytes 2199023255552 \
  --snapshot-id snap-0abc123 --target-name vol-clonado --network-interface-id 10.0.1.20 --client-token tok-4
```

## DR com Storage Gateway em EC2

Cenário: o datacenter fica indisponível; é preciso restaurar dados e serviços na AWS.

| Estratégia | Como |
|---|---|
| **Volume Gateway → EBS/EC2** | Criar volumes EBS dos snapshots (`create-volume`), anexar a instâncias EC2 preparadas (AMI) e subir os serviços; IaC para a infraestrutura |
| **Tape Gateway em EC2** | Subir um **Tape Gateway em EC2** (ativado em outra conta/região), **recuperar as fitas** necessárias e ler com o software de backup (também em EC2) para restaurar servidores/dados na AWS |
| **File Gateway em EC2** | Os dados estão no S3; outro gateway em EC2 ou acesso direto |
| **Runbook** | Passos, responsáveis, tempos; **teste anual** de DR (restaurar um servidor real) com cronometragem |
| **Rede** | VPC de DR pronta (SG, rotas, DNS), AMIs/IaC, chaves KMS e permissões nas regiões |
| **Catálogo do backup** | Replicar o **catálogo** do software de backup (ou reinventariar fitas, que leva horas) |

RPO: frequência dos snapshots (Volume) ou do último backup arquivado (Tape). RTO: tempo de recuperação das fitas (horas, Glacier) + restauração (depende do volume e da banda) — com **Deep Archive** o RTO é maior.

## Segurança

| Tema | Detalhe |
|---|---|
| **Criptografia** | Em trânsito (TLS) para a AWS; em repouso (S3/Glacier com SSE-S3 ou SSE-KMS; EBS snapshots com KMS) |
| **iSCSI** | CHAP bidirecional entre iniciadores e alvos; restrição por rede/SG; evitar exposição à internet |
| **Retenção bloqueada** | Imutabilidade das fitas arquivadas (proteção contra ransomware e exclusão) |
| **IAM** | Permissões mínimas para administradores e roles do gateway |
| **Isolamento** | Conta de backup separada; MFA para exclusão |
| **Auditoria** | CloudTrail e eventos EventBridge de fitas (arquivada/recuperada) |

## Monitoramento e troubleshooting

| Sintoma | Causas | Ação |
|---|---|---|
| **Job de backup falha com "buffer cheio"** | Upload buffer insuficiente / link saturado | Aumentar buffer/link, reduzir paralelismo, escalonar janelas |
| **Backup muito lento** | Link, CPU, disco de cache, iSCSI mal configurado | Medir `CloudBytesUploaded`, `IoWaitPercent`; MPIO; ajustar jobs |
| **Software não vê o changer/drives** | iSCSI não conectado, drivers do changer, firewall | Reconectar iniciador (3260), instalar driver correto, reinventariar |
| **Fita "não encontrada" ao restaurar** | Fita arquivada ainda não recuperada | `retrieve-tape` e aguardar |
| **Recuperação demorando** | Deep Archive (≥ 12 h) | Planejar; usar Flexible Retrieval para as fitas recentes |
| **Fita não pode ser excluída** | Retenção bloqueada | Esperar o fim da retenção (por design) |
| **Gateway offline** | VM parada, rede, relógio/DNS, sem acesso ao endpoint | Verificar VM, conectividade, NTP; reativar |
| **Volume não aparece no cliente** | CHAP, igroup/target, iSCSI | Revisar autenticação, conectar e reescanear discos |
| **Snapshot falha** | Volume sem espaço/ocupado, buffer cheio | Ajustar janelas e capacidade |
| **Custos inesperados** | Fitas não arquivadas, recuperações frequentes, exclusão antecipada em Glacier | Revisar política e pools |

Métricas (`AWS/StorageGateway`): `CloudBytesUploaded`, `CloudBytesDownloaded`, `CachePercentUsed`, `CachePercentDirty`, `CacheHitPercent`, `UploadBufferPercentUsed`, `QueuedWrites`, `IoWaitPercent`, `ReadBytes/WriteBytes`, `TimeSinceLastRecoveryPoint` (Volume), `TapeUsed`.

## Exemplo prático

Empresa com 120 TB de backups em fita física (LTO) migrando para Tape Gateway com Veeam:

1. **Implantação:** gateway em VM (16 vCPUs, 64 GB RAM) com cache de 4 TB (NVMe) e upload buffer de 4 TB; conexão por Direct Connect de 2 Gbps ao endpoint VPC.
2. **Mídia:** fitas de 2 TiB (prefixo `PRD`), pool de arquivamento **Deep Archive** para mensais/anuais e **Flexible Retrieval** para semanais (restauração mais rápida).
3. **Software:** Veeam enxerga o changer e 8 drives virtuais; políticas: diária (14 dias na VTL/ativas), semanal (arquivar após 14 dias), mensal (Deep Archive, 7 anos), anual (Deep Archive, 10 anos com **retention lock** compliance).
4. **Capacidade:** backup diário de 3 TB em janela de 10 h com link efetivo de 1 Gbps (≈ 4,5 TB/10 h) e buffer folgado; alarmes em `UploadBufferPercentUsed` > 60% e `CachePercentDirty` > 50%.
5. **DR:** runbook testado — subir **Tape Gateway em EC2** em outra região, recuperar as fitas do último mensal, restaurar um servidor de arquivos (RTO medido de 22 h, aceito para o tier 2) e catálogo do Veeam replicado diariamente.
6. **Governança:** CloudTrail e EventBridge para fitas arquivadas/recuperadas; relatório mensal de capacidade; custo por GB-mês de Deep Archive muito inferior ao de manter o robô de fitas e o transporte.

## Erros comuns e armadilhas

- **Upload buffer e link subdimensionados** para a janela de backup.
- **Software de backup ou versão fora da matriz de compatibilidade.**
- **Perder o catálogo** do software de backup (sem saber em qual fita está cada dado).
- **Arquivar tudo em Deep Archive** e precisar de restaurações rápidas.
- **Ignorar o tempo de recuperação** (RTO) no plano de DR.
- **Excluir fitas Glacier antes do prazo mínimo** (cobrança de exclusão antecipada).
- **Retention lock em modo compliance sem teste.**
- **iSCSI sem MPIO/CHAP** e sem isolamento de rede.
- **Tratar snapshots de Volume Gateway como backup lógico de banco** sem quiesce.
- **DR nunca testado.**
- **Gateway único sem monitoramento** (offline sem alarmes).

## 🧩 Quiz de Fixação

1. Como funciona o ciclo de vida de uma fita virtual, da gravação à recuperação?
2. Como dimensionar o upload buffer de um Tape Gateway?
3. Como montar o DR de um Volume Gateway e de um Tape Gateway?
4. Que cuidados tomar com o catálogo do software de backup?

**Respostas:**
1) O software grava na fita ativa (na VTL, armazenada no S3); ao ejetar, o gateway a arquiva no pool escolhido (Glacier Flexible Retrieval ou Deep Archive); para restaurar, usa-se `retrieve-tape` para trazê-la de volta à VTL (horas) e o software a lê; a retenção bloqueada pode impedir exclusão prematura.
2) Calculando o excedente entre a taxa de ingestão do backup e a taxa efetiva de upload durante a janela (dados do dia menos o que o link envia no período), com folga; ajusta-se também o link e o volume (incrementais) e monitora-se `UploadBufferPercentUsed`.
3) Volume Gateway: criar volumes EBS dos snapshots e anexar a instâncias EC2 preparadas (IaC/AMIs); Tape Gateway: subir outro Tape Gateway em EC2, recuperar as fitas necessárias e restaurar com o software de backup (também na AWS), com runbook testado e catálogo disponível.
4) Protegê-lo e replicá-lo, pois é ele que sabe em qual fita está cada arquivo; sem o catálogo é preciso reinventariar as fitas, o que leva horas e atrasa a restauração.
