### Volume Gateway e Tape Gateway — iSCSI, modos cached e stored, snapshots e fitas virtuais

> [!warning] Aviso
> Modos, limites de volumes/fitas, integrações de software de backup e preços mudam; alguns modos podem ser descontinuados. Confirme na documentação. Os comandos **não foram executados**.

Os gateways de **blocos** e de **fita** atendem a cenários em que a aplicação enxerga **discos iSCSI** (Volume Gateway) ou uma **biblioteca de fitas** (Tape Gateway), com dados e backups protegidos na AWS.

**Analogia:** o Volume Gateway é um **HD externo com cópia automática na nuvem**. O Tape Gateway é uma **fitoteca virtual**: o software de backup acha que está carregando fitas físicas, mas elas são gravadas no S3 e arquivadas no Glacier.

## Volume Gateway

Apresenta **volumes iSCSI** aos servidores locais. Os dados são enviados à AWS e protegidos por **snapshots** incrementais armazenados como **snapshots do EBS**.

```
 Servidor ──iSCSI──► Volume Gateway ──(HTTPS)──► S3 (dados) ──► snapshots EBS ──► restaurar como volume EBS/EC2
```

### Dois modos

| Modo | Onde ficam os dados "primários" | Cache local | Uso |
|---|---|---|---|
| **Cached volumes** | **Na AWS (S3)**; só o conjunto quente fica localmente | Cache de leitura/escrita + buffer de upload | Reduzir uso de disco local, expandir capacidade (volumes de dezenas de TB) |
| **Stored volumes** | **No local** (disco inteiro no gateway) | Dados completos locais; backup assíncrono à AWS | Baixa latência a **todo** o conjunto de dados, com backup na nuvem |

```
 Cached:  [ cache local (quente) ]  ◄──►  [ dados completos no S3 ]
 Stored:  [ dados completos locais ] ──►  [ snapshots/backup no S3 ]
```

### Snapshots e recuperação

- Snapshots **incrementais** (agendados ou sob demanda), armazenados como snapshots do EBS.
- Podem ser **restaurados como volumes EBS** e anexados a instâncias EC2 (DR em nuvem) ou usados para **clonar** volumes.
- Integra-se ao **AWS Backup** para políticas centralizadas.

```bash
# Snapshot sob demanda de um volume do gateway
aws storagegateway create-snapshot --volume-arn $VOL_ARN \
  --snapshot-description "antes da atualizacao"

# Listar volumes do gateway
aws storagegateway list-volumes --gateway-arn $GW_ARN

# Restaurar: criar um volume EBS a partir do snapshot (por exemplo, para DR na AWS)
aws ec2 create-volume --snapshot-id snap-0abc123 --availability-zone sa-east-1a
```

### Conexão iSCSI no cliente (Linux)

```bash
# Descobrir e conectar o alvo iSCSI exposto pelo gateway
sudo iscsiadm -m discovery -t sendtargets -p $GATEWAY_IP:3260
sudo iscsiadm -m node --targetname iqn.1997-05.com.amazon:meu-volume -p $GATEWAY_IP:3260 --login
lsblk    # o novo disco aparece; formate e monte como qualquer disco
```

### Quando usar

- Aplicações que **exigem blocos** (iSCSI) e querem backup/DR em nuvem.
- Expandir capacidade sem comprar SAN (cached).
- Cenários de **DR**: restaurar o volume na AWS e subir a aplicação em EC2.

## Tape Gateway

Substitui fitas físicas e robôs de fita por uma **Virtual Tape Library (VTL)**, compatível com os principais softwares de backup (Veeam, Veritas/NetBackup, Commvault, IBM, Dell EMC etc.; confirme a lista).

```
 Software de backup ──iSCSI VTL──► Tape Gateway
        │ escreve em "fitas" virtuais
        ▼
   S3 (fitas ativas)  ──ejetar/arquivar──►  S3 Glacier Flexible / Deep Archive (fitas arquivadas)
```

| Conceito | Detalhe |
|---|---|
| **Virtual tape library (VTL)** | Mostra drives e changer ao software de backup |
| **Fitas virtuais** | Criadas sob demanda (tamanho de centenas de GB até alguns TB) |
| **Fitas ativas** | Armazenadas no S3, disponíveis para o software de backup |
| **Arquivamento** | Fitas ejetadas pelo software vão para Glacier/Deep Archive (baixo custo) |
| **Recuperação** | Pedir a recuperação da fita arquivada (horas) e montá-la na VTL |
| **Cache local** | Mantém dados recentes/dados prestes a ser enviados |
| **Retenção (tape retention lock)** | Bloqueio de exclusão/ejeção por período, para conformidade |

### Fluxo de backup

1. O software de backup grava na fita virtual (iSCSI).
2. O gateway envia os dados ao S3.
3. Ao concluir, o software **ejeta** a fita → o gateway a **arquiva** no Glacier/Deep Archive.
4. Para restaurar, **recupere** a fita (`retrieve-tape`) → ela volta à VTL em horas → o software de backup lê.

```bash
# Criar fitas virtuais
aws storagegateway create-tapes --gateway-arn $GW_ARN \
  --tape-size-in-bytes 107374182400 --client-token tok-1 \
  --num-tapes-to-create 5 --tape-barcode-prefix BKP

# Recuperar uma fita arquivada
aws storagegateway retrieve-tape --tape-arn $TAPE_ARN --gateway-arn $GW_ARN

aws storagegateway list-tapes
```

### Benefícios

- Elimina fitas físicas, transporte e robôs.
- Mantém o **processo e as ferramentas de backup** existentes.
- Custo baixo para retenção de longo prazo (Deep Archive).
- Durabilidade da AWS e opção de bloqueio de retenção.

## Comparação

| Critério | Volume Gateway | Tape Gateway |
|---|---|---|
| Protocolo | iSCSI (blocos) | iSCSI VTL (fita) |
| Uso | Discos para aplicações, DR | Backup/arquivo com software de backup |
| Proteção | Snapshots EBS | Fitas em S3/Glacier |
| Restauração | Volume EBS/EC2 | Recuperação de fita |
| Acesso aleatório | Sim | Não (sequencial, como fita) |

## Exemplo prático

Empresa com software de backup e biblioteca de fitas LTO reduzindo o parque:

1. Tape Gateway como VM com 1 TB de cache e 1 TB de upload buffer.
2. Software de backup configurado com a nova biblioteca virtual; políticas existentes preservadas.
3. Fitas de backups semanais ejetadas e arquivadas em Deep Archive; retenção de 7 anos com *retention lock*.
4. Teste anual: recuperar uma fita, montar na VTL, restaurar um servidor de teste e **medir o tempo** (RTO).

## Dimensionamento e armadilhas dos modos

```
 CACHED:  dados primários no S3, cache local só do que é quente  → capacidade "ilimitada", latência varia
 STORED:  dados primários no disco local, cópia assíncrona ao S3 → latência de disco local, limite = disco
```

| Critério | Cached | Stored |
|---|---|---|
| Local do dado primário | S3 | Disco local |
| Limite de volume | Muito maior | Limitado pelo hardware local |
| Latência | Alta no miss | Baixa sempre |
| DR | Excelente (tudo no S3) | Boa (snapshots) |
| Uso | Expandir capacidade | Apps sensíveis que precisam de tudo local |

> [!warning] Limites de volume, quantidade de fitas e disponibilidade do modo stored mudam; confirme na documentação atual.

## Fluxo de recuperação de desastre com Volume Gateway

```
 Datacenter cai
   └─► Snapshot do volume (EBS) mais recente ──► criar volume EBS na região
        └─► anexar à EC2 (ou gateway EC2 + iSCSI) ──► app volta em horas, não dias
```

## Tape Gateway: ciclo de vida da fita

| Estado | Local | Observação |
|---|---|---|
| Virtual Tape Library (VTL) | S3 (Standard) | Disponível ao software de backup |
| Ejetada/arquivada | Glacier Flexible / Deep Archive | Custo mínimo; recuperar leva horas |
| Recuperação | Retornar à VTL | Leva de 3-5 h (Flexible) até 12 h+ (Deep Archive) |

### Exemplo de CLI (comentado, não executado)

```bash
# Criar fita virtual
aws storagegateway create-tapes --gateway-arn <ARN> --tape-size-in-bytes 107374182400 \
  --client-token $(uuidgen) --num-tapes-to-create 5 --tape-barcode-prefix BKP
# Listar fitas arquivadas e recuperar uma
aws storagegateway list-tapes
aws storagegateway retrieve-tape-archive --tape-arn <ARN-fita> --gateway-arn <ARN>
```

## Troubleshooting

| Sintoma | Causa provável | Ação |
|---|---|---|
| iSCSI não descobre alvo | SG/firewall, initiator errado | Liberar 3260 e conferir o IQN |
| Upload buffer cheio | Banda saída insuficiente | Aumentar banda/buffer |
| Fita não aparece no software | VTL não atualizada | Re-inventariar a biblioteca |
| Restauração lenta | Fita em Deep Archive | Planejar RTO conforme a classe |

## Custo

Gateway por mês, armazenamento (S3/EBS snapshots/Glacier), recuperação de fitas arquivadas e saída de dados.

---

## Erros comuns e armadilhas

- **Cached volumes com link WAN lento:** leituras fora do cache ficam lentas.
- **Stored volumes sem espaço local suficiente** para todo o dataset.
- **Upload buffer subdimensionado:** o gateway rejeita escritas quando enche.
- **Esquecer que fitas arquivadas levam horas** para recuperar: o RTO precisa refletir isso.
- **Software de backup não suportado/certificado** com a VTL.
- **Tratar snapshots de volume como backup lógico de banco de dados** sem quiescência.
- **Não testar a restauração (volume ou fita).**
- **Excluir ou ejetar fitas** sem política de retenção.

## 🧩 Quiz de Fixação

1. Qual a diferença entre cached e stored volumes?
2. Como o Tape Gateway se integra ao software de backup e onde as fitas ficam armazenadas?
3. Por que o RTO de restauração via Tape Gateway deve considerar a recuperação da fita?

**Respostas:**
1) Em *cached*, os dados completos ficam na AWS e só o conjunto quente fica no cache local; em *stored*, o conjunto completo fica local e há backup assíncrono (snapshots) na AWS.
2) O gateway apresenta uma biblioteca de fitas virtual (iSCSI VTL) que o software de backup usa como fitas físicas; as fitas ativas ficam no S3 e, ao serem ejetadas, são arquivadas no S3 Glacier/Deep Archive.
3) Porque fitas arquivadas precisam ser recuperadas (leva horas) antes de o software de backup lê-las, adicionando tempo à restauração.

### Questões de aprofundamento

4. Qual modo do Volume Gateway permite mais capacidade que o disco local?
5. Quanto tempo esperar para recuperar uma fita em Deep Archive?
6. Como usar snapshots do Volume Gateway para DR?

**Respostas:**
4) O modo Cached, pois o dado primário fica no S3.
5) Várias horas (da ordem de 12 horas ou mais); planeje o RTO de acordo.
6) Criar um volume EBS a partir do snapshot na região de destino e anexá-lo a uma EC2.
