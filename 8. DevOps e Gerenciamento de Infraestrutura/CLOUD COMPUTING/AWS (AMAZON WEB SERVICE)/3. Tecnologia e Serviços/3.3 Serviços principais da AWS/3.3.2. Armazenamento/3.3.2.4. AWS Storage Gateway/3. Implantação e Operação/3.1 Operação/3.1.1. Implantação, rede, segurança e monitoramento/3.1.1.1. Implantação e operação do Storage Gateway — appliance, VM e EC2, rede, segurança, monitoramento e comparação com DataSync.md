> Requisitos de hardware, plataformas suportadas, portas, métricas e preços mudam. Confirme na documentação (guia de requisitos do gateway). Os comandos **não foram executados**.

Depois de escolher o tipo de gateway, falta **implantá-lo**, **conectá-lo com segurança à AWS**, **dimensioná-lo** e **operá-lo**. Essa nota cobre as formas de implantação, os requisitos de rede e discos, segurança, monitoramento e a comparação com **DataSync** e **Transfer Family**.

## Formas de implantação

| Opção | Descrição | Quando |
|---|---|---|
| **VM** (VMware ESXi, Hyper-V, Linux KVM) | Imagem baixada e importada no hipervisor | Datacenter com virtualização |
| **Hardware Appliance** | Servidor físico pré-configurado adquirido via AWS | Sem infraestrutura de virtualização |
| **Instância EC2** | AMI do Storage Gateway na própria AWS | DR em nuvem, VMware Cloud on AWS, acesso a partir de VPC |

Passos gerais:

```
 1. Escolher tipo de gateway e plataforma
 2. Implantar a VM/appliance/EC2 com discos (SO + CACHE + UPLOAD BUFFER)
 3. Ativar (chave de ativação via IP local ou VPC endpoint) na região desejada
 4. Configurar discos de cache/buffer
 5. Criar shares (File) / volumes (Volume) / fitas (Tape)
 6. Conectar clientes (NFS/SMB/iSCSI) e testar
```

### Dimensionamento (regras práticas)

| Item | Orientação |
|---|---|
| **Cache** | Pelo menos o tamanho do conjunto de dados "quente"; SSD/NVMe quando a latência importa |
| **Upload buffer** (Volume/Tape) | Dimensionar pela taxa de ingestão × tempo de upload; cada gateway tem mínimos documentados |
| **CPU/RAM** | Seguir os requisitos mínimos por tipo; mais RAM melhora a performance do cache |
| **Disco** | Discos dedicados e rápidos; não compartilhar com cargas pesadas |
| **Rede** | Link com banda compatível com o volume de upload diário |

## Rede e conectividade

| Ponto | Detalhe |
|---|---|
| **Saída HTTPS (443)** | O gateway se conecta aos endpoints do Storage Gateway, S3 e outros por HTTPS |
| **Internet pública** | Funciona com os endpoints públicos (firewall precisa liberar as saídas) |
| **Direct Connect** | Recomendado para volume alto/latência estável (interface virtual pública ou privada) |
| **VPC endpoint (PrivateLink)** | Conectividade privada ao serviço, sem tráfego pela internet pública |
| **Portas locais para clientes** | NFS (2049, 111...), SMB (445), iSCSI (3260); dependem do tipo |
| **DNS e NTP** | Resolução de nomes e **relógio sincronizado** são obrigatórios (autenticação falha com relógio errado) |
| **Limite de banda** | Configurável para evitar saturar o link WAN |

```bash
# Limitar a taxa de upload/download do gateway (bytes por segundo), útil em horário comercial
aws storagegateway update-bandwidth-rate-limit --gateway-arn $GW_ARN \
  --average-upload-rate-limit-in-bits-per-sec 104857600 \
  --average-download-rate-limit-in-bits-per-sec 209715200
# Também existe agendamento por dia/hora (update-bandwidth-rate-limit-schedule)
```

## Segurança

| Camada | Prática |
|---|---|
| **IAM** | Role do gateway com acesso mínimo ao bucket/KMS; usuários administrativos com permissões restritas ao serviço |
| **Criptografia em trânsito** | HTTPS/TLS entre gateway e AWS |
| **Criptografia em repouso** | SSE-S3 ou SSE-KMS no S3; EBS/FSx com KMS; volume/tape criptografados com KMS (veja a nota de AWS KMS). |
| **Autenticação de clientes** | SMB com **Active Directory**; NFS com lista de clientes permitidos (CIDR); iSCSI com **CHAP** |
| **Rede** | Segmentar o gateway; liberar portas apenas para clientes autorizados |
| **Proteção dos dados** | Versionamento, replicação, Object Lock (File Gateway), retention lock (Tape) |
| **Auditoria** | CloudTrail (APIs), logs de auditoria de arquivo SMB para CloudWatch Logs |

## Monitoramento e manutenção

| Item | Como |
|---|---|
| **Métricas CloudWatch** (`AWS/StorageGateway`) | `CacheHitPercent`, `CachePercentUsed`, `CachePercentDirty`, `UploadBufferPercentUsed`, `CloudBytesUploaded/Downloaded`, `ReadBytes/WriteBytes`, `IoWaitPercent` |
| **Alarmes úteis** | `CachePercentDirty` alto (muito dado a enviar), `UploadBufferPercentUsed` > 80%, gateway offline |
| **Saúde** | `ListGateways`, estado `RUNNING`; eventos no EventBridge |
| **Atualizações** | Janela de manutenção semanal configurável; aplique atualizações do gateway |
| **Backup da configuração** | Registre a configuração (shares, volumes) em IaC; os dados são protegidos na AWS, mas o gateway precisa ser recriado/ativado |
| **Recuperação do gateway** | Em falha, ativar novo gateway e anexar volumes/fitas existentes (conforme o tipo) |

```bash
aws cloudwatch get-metric-statistics --namespace AWS/StorageGateway \
  --metric-name CachePercentDirty \
  --dimensions Name=GatewayId,Value=sgw-12A3456B Name=GatewayName,Value=gw-escritorio \
  --start-time 2026-11-05T00:00:00Z --end-time 2026-11-06T00:00:00Z \
  --period 300 --statistics Average
# Valores altos e persistentes indicam que o link não acompanha a ingestão
```

## Storage Gateway × DataSync × Transfer Family × Snow

| Critério | **Storage Gateway** | **DataSync** | **Transfer Family** | **Snow Family** |
|---|---|---|---|---|
| Modelo | Acesso híbrido contínuo | Cópia/sincronização agendada | Servidor SFTP/FTPS/FTP gerenciado | Transporte físico offline |
| Protocolos | NFS, SMB, iSCSI, fita | Agente + NFS/SMB/HDFS/S3 etc. | SFTP, FTPS, FTP, AS2 | Dispositivo físico |
| Cache local | **Sim** | Não | Não | Não |
| Uso típico | Estender NAS, backup em fita, DR | Migração, replicação periódica | Troca de arquivos com parceiros | Petabytes sem rede suficiente |
| Destino | S3, FSx, EBS snapshots | S3, EFS, FSx etc. | S3, EFS | S3 |

Regra: **acesso contínuo com cache local → Storage Gateway; mover dados de uma vez ou em janelas → DataSync; parceiros com SFTP → Transfer Family; volumes enormes sem rede → Snow.**

## Exemplo prático

Checklist de implantação de um S3 File Gateway em VMware:

1. Validar requisitos: 4 vCPUs, 16 GB RAM, disco raiz e **disco de cache de 500 GB SSD**; NTP e DNS funcionando.
2. Criar o VPC endpoint de Storage Gateway (se for usar PrivateLink) e liberar saída 443.
3. Baixar a OVA, implantar e ativar na região `sa-east-1`.
4. Criar role com acesso mínimo ao bucket e à chave KMS; criar o share SMB com AD.
5. Configurar limite de banda diurno de 100 Mbps e livre à noite.
6. Criar alarmes em `CachePercentDirty` e `CachePercentUsed`; testar falha (desligar o gateway, reativar, remontar).
7. Documentar o runbook de recuperação.

## Erros comuns e armadilhas

- **Relógio e DNS errados:** ativação ou autenticação falham.
- **Firewall bloqueando saída 443** para os endpoints necessários.
- **Disco de cache em armazenamento lento ou compartilhado.**
- **Link saturado em horário comercial:** sem limite de banda, o gateway impacta o escritório.
- **Não monitorar `CachePercentDirty`:** dados presos no gateway em caso de falha antes do envio.
- **Role com permissão ampla demais** (`s3:*` em todos os buckets).
- **Atualizações automáticas em horário crítico:** configure a janela.
- **Usar o gateway quando DataSync resolveria** (migração única).
- **Ausência de plano de recuperação do próprio gateway.**

## 🧩 Quiz de Fixação

1. Quais são as três formas de implantar um Storage Gateway?
2. Que métrica indica que o link não acompanha a ingestão e há muitos dados aguardando envio?
3. Quando escolher DataSync em vez de Storage Gateway?

**Respostas:**
1) Como VM (VMware ESXi, Hyper-V, KVM), como Hardware Appliance físico fornecido pela AWS ou como instância EC2.
2) `CachePercentDirty` (e `UploadBufferPercentUsed` nos gateways que usam buffer) alto de forma persistente.
3) Para migração ou sincronização de grandes volumes, única ou em janelas agendadas; o Storage Gateway é para acesso híbrido contínuo com cache local.
