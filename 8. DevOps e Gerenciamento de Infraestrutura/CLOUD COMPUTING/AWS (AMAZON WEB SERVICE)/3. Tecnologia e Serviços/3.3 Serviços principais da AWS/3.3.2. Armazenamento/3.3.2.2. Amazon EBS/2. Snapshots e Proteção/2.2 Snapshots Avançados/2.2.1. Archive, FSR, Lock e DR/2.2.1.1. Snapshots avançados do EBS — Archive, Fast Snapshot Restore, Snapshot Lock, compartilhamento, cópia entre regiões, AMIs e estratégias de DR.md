### Snapshots avançados do EBS — Archive, Fast Snapshot Restore, Snapshot Lock, compartilhamento, cópia entre regiões, AMIs e estratégias de DR

> [!warning] Aviso
> Camadas de snapshot (Standard/Archive), prazos mínimos, tempos de restauração, preços, limites de FSR e modos do Snapshot Lock mudam. **Nenhum valor numérico aqui é oficial.** Confirme na documentação. Os comandos **não foram executados**.

A nota anterior de snapshots cobriu o básico (incremental, restauração, DLM, Recycle Bin). Aqui vão os recursos que decidem **custo, velocidade de restauração, imutabilidade e recuperação de desastres**: a **camada Archive**, o **Fast Snapshot Restore (FSR)**, o **Snapshot Lock**, o **compartilhamento e cópia** entre contas e regiões, o **bloqueio de acesso público**, a relação com **AMIs**, as **EBS direct APIs** e as **estratégias de DR** (pilot light, warm standby).

**Analogia:** os snapshots são **fotografias do HD**. A camada Archive é o **depósito de fotos antigas** (barato, mas pedir uma foto leva dias). O FSR é ter **fotos já reveladas e prontas para impressão imediata**. O Snapshot Lock é **colocar a foto num cofre de tempo**, que ninguém abre antes da data. A cópia entre regiões é **guardar uma cópia em outra cidade**.

## Camadas de armazenamento de snapshot

| Camada | Característica | Custo | Restauração |
|---|---|---|---|
| **Standard** | Incremental, restauração rápida | Mais caro por GB | Imediata (com lazy loading) |
| **Archive** | **Cópia completa** (não incremental) em armazenamento frio; retenção mínima de **90 dias** | Cerca de **75% mais barato** por GB do que o incremental Standard (varia) | **Restauração** (volta para Standard) leva **de horas a 1-3 dias**; cobrança de recuperação |

```
 Standard (incremental):   S1 ◄─ S2 ◄─ S3 ◄─ S4   (cada um guarda só os blocos alterados)
 Archive:                   S1 completo | S2 completo | S3 completo   (cada archive é uma cópia completa dos blocos usados)
```

Quando usar Archive: **retenção de longo prazo** (conformidade, fim de projeto, marcos mensais/anuais) com baixa probabilidade de restauração. Quando **não**: snapshots que se restauram com frequência; cadeias com **poucas diferenças entre snapshots** (o incremental Standard pode ser mais barato); retenção < 90 dias (cobra-se o mínimo).

```bash
aws ec2 modify-snapshot-tier --snapshot-id snap-0abc123 --storage-tier archive
aws ec2 restore-snapshot-tier --snapshot-id snap-0abc123 --temporary-restore-days 7      # restaura temporariamente
aws ec2 restore-snapshot-tier --snapshot-id snap-0abc123 --permanent-restore              # volta de vez para Standard
aws ec2 describe-snapshot-tier-status
```

O **DLM** pode arquivar automaticamente snapshots antigos por política (camada Archive após N dias).

## Fast Snapshot Restore (FSR)

Volumes restaurados de snapshot têm **lazy loading**: a primeira leitura de cada bloco é mais lenta. O **FSR** pré-inicializa o snapshot **em AZs escolhidas**, e os volumes criados dele entregam **desempenho total desde o início**.

| Característica | Detalhe |
|---|---|
| **Escopo** | Por snapshot **e por AZ** |
| **Limite** | Número limitado de snapshots com FSR por região (cerca de 50) |
| **Créditos** | A criação de volumes usa "créditos de FSR" (balde por snapshot/AZ); excedido, a criação cai ao comportamento normal |
| **Custo** | **Por hora de FSR habilitado**, por snapshot e AZ — pode ser **caro**; habilite só onde o RTO exige |
| **Uso típico** | AMIs/Auto Scaling que lançam muitas instâncias rápido; restaurações de DR com RTO curto; ambientes de teste |
| **Estados** | `enabling` → `optimizing` → `enabled` |

```bash
aws ec2 enable-fast-snapshot-restores --availability-zones sa-east-1a sa-east-1b --source-snapshot-ids snap-0abc123
aws ec2 describe-fast-snapshot-restores --filters Name=state,Values=enabled
aws ec2 disable-fast-snapshot-restores --availability-zones sa-east-1a --source-snapshot-ids snap-0abc123
```

Alternativas mais baratas: **inicialização manual** (ler todos os blocos com `fio`/`dd`), aceitar a lentidão inicial, ou **volume initialization rate** (taxa de inicialização provisionada, recurso mais recente).

## Snapshot Lock (imutabilidade)

Impede a **exclusão** de snapshots por um período, protegendo contra erro humano, ransomware e insiders.

| Modo | Característica |
|---|---|
| **Governance** | Usuários com permissão específica podem remover o bloqueio ou alterá-lo; bom para começar e testar |
| **Compliance** | Após um **período de carência (cooling-off)**, o bloqueio é **imutável**: nem a conta raiz remove nem encurta; só espera expirar |

| Parâmetro | Significado |
|---|---|
| `LockDuration` ou `ExpirationDate` | Duração do bloqueio |
| `CoolOffPeriod` | Janela (horas) para desfazer um bloqueio em modo compliance |
| Efeito | Bloqueia `DeleteSnapshot`, `modify-snapshot-tier` para remoção etc. |

```bash
aws ec2 lock-snapshot --snapshot-id snap-0abc123 --lock-mode governance --lock-duration 30
aws ec2 lock-snapshot --snapshot-id snap-0abc123 --lock-mode compliance --cool-off-period 24 --lock-duration 365
aws ec2 describe-locked-snapshots
```

⚠️ **Compliance é irreversível após o cooling-off**: teste antes em governance. Combine com **Recycle Bin com regras de bloqueio**, **AWS Backup Vault Lock** e **SCPs**.

## Compartilhamento e cópia

| Operação | Como | Observações |
|---|---|---|
| **Compartilhar com contas específicas** | `modify-snapshot-attribute --attribute createVolumePermission --operation-type add --user-ids <conta>` | Snapshots **criptografados** só com **CMK** (compartilhe a chave) |
| **Compartilhar publicamente** | `--group-names all` | **Evite**; use o bloqueio |
| **Block public access for snapshots** | Configuração de conta/região que impede compartilhamento público | Habilite por padrão |
| **Copiar para outra região** | `copy-snapshot --source-region ... --region ...` (pode criptografar na cópia, trocando a chave) | Base do DR; cobrança de transferência |
| **Copiar para outra conta** | Compartilhar → a conta destino copia (recriptografando com a própria CMK) | Proteção contra comprometimento da conta |
| **Cópia temporalmente restrita** | DLM com cross-account/cross-region copy | Automatizada |
| **Compartilhar via Organizations** | Compartilhar com a organização ou OU | Governança |

```bash
aws ec2 enable-snapshot-block-public-access --state block-all-sharing
aws ec2 copy-snapshot --source-region sa-east-1 --source-snapshot-id snap-0abc123 --region us-east-1 \
  --encrypted --kms-key-id alias/ebs-dr --description "DR dados-app"
```

## AMIs e snapshots

- Uma **AMI** é um conjunto de **snapshots** dos volumes (raiz e dados) + metadados.
- **Desregistrar a AMI não apaga** os snapshots (limpe-os: custo oculto); **apagar o snapshot** de uma AMI registrada a quebra.
- Cópia de AMI entre regiões copia os snapshots; AMIs criptografadas exigem chaves compartilhadas.
- **AMIs com Fast Launch** (Windows) e **FSR** aceleram o lançamento de muitas instâncias.
- **Recycle Bin** pode reter AMIs e snapshots excluídos.
- **EC2 Image Builder** automatiza criação, teste e distribuição de AMIs.

```bash
aws ec2 describe-snapshots --owner-ids self --query 'Snapshots[?!contains(Description, `Created by CreateImage`)].[SnapshotId,StartTime,VolumeSize]'
# Ache snapshots órfãos (sem volume/AMI): cuidado antes de apagar
```

## EBS direct APIs

Permitem **ler e escrever snapshots em nível de bloco**, sem criar volumes:

| API | Uso |
|---|---|
| `ListSnapshotBlocks`, `GetSnapshotBlock` | Ler blocos de um snapshot (backup externo, análise forense, replicação) |
| `ListChangedBlocks` | Descobrir blocos alterados entre dois snapshots (backups incrementais para outro sistema) |
| `StartSnapshot`, `PutSnapshotBlock`, `CompleteSnapshot` | Criar um snapshot a partir de dados externos (importar de on-premises) |

Úteis para **soluções de backup de terceiros** e para importar discos sem VM Import.

## Estratégias de DR com snapshots

| Estratégia | RPO | RTO | Custo | Como |
|---|---|---|---|---|
| **Backup e restauração** | Frequência do snapshot (horas) | Horas | Baixo | Snapshots copiados à região de DR; restaurar volumes, lançar instâncias via IaC |
| **Pilot light** | Minutos-horas | Dezenas de minutos | Médio | Infra mínima (rede, banco replicado) + snapshots/AMIs prontos; escalar no desastre |
| **Warm standby** | Minutos | Minutos | Maior | Ambiente reduzido rodando; volumes sincronizados por replicação em nível de aplicação |
| **Multi-site** | ~0 | ~0 | Alto | Ativo-ativo (outro assunto) |

Pontos práticos de DR com EBS:

1. **Snapshots consistentes** (`create-snapshots` multi-volume, ou `fsfreeze`/quiesce de banco) para aplicação com vários discos.
2. **Cópia automática** (DLM/AWS Backup) para outra região e conta, com **chave KMS** da região de destino.
3. **FSR** só nos snapshots críticos da região de DR (se o RTO exige).
4. **IaC** para recriar a infraestrutura (VPC, SG, instâncias, ASG).
5. **Runbook testado**: restaurar, validar, medir RTO.
6. **Retenção em camadas**: diária (Standard), mensal (Archive), anual (Archive + Lock).

## Exemplo prático

Política de retenção de um sistema financeiro:

| Camada | Frequência | Retenção | Armazenamento | Proteção |
|---|---|---|---|---|
| Operacional | A cada 4 h | 7 dias | Standard | DLM + Recycle Bin (7 dias) |
| Diária | 1×/dia | 35 dias | Standard | Cópia para `us-east-1` (35 dias) |
| Mensal | 1×/mês | 24 meses | **Archive** | Lock **governance** 24 meses; cópia em conta `bunker` |
| Anual | 1×/ano | 7 anos | **Archive** | Lock **compliance** (após teste) + Vault Lock no AWS Backup |

1. **DLM** (ou AWS Backup) cria as camadas; tags `Backup=financeiro`.
2. **Bloqueio de acesso público** a snapshots em todas as contas (SCP + configuração).
3. **FSR** habilitado apenas nos snapshots diários da região de DR (2 AZs), medido e revisto mensalmente.
4. **Teste semestral de DR**: restaurar volumes na região de DR a partir da cópia, subir instâncias por IaC, validar e registrar o RTO (meta 90 min).
5. **Auditoria**: Config (`ebs-snapshot-public-restorable-check`), CloudTrail para `DeleteSnapshot`/`ModifySnapshotAttribute`, alarme para tentativas de exclusão de snapshots travados.

## Erros comuns e armadilhas

- **Mover tudo para Archive** sem considerar retenção mínima de 90 dias e tempo de restauração.
- **Habilitar FSR em todos os snapshots e AZs** (custo alto).
- **Usar compliance lock sem testar** (irreversível).
- **Snapshot criptografado com chave `aws/ebs`** e tentar compartilhar (precisa de CMK).
- **Compartilhar snapshots publicamente** por engano.
- **Apagar snapshot de AMI registrada** (AMI quebra) ou **deixar snapshots órfãos** após desregistrar.
- **Cópia entre regiões sem chave KMS no destino.**
- **Snapshots não consistentes** em aplicações com múltiplos discos.
- **DR nunca testado** nem cronometrado.
- **Confundir Recycle Bin com imutabilidade:** ele apenas retém excluídos por um prazo.

## 🧩 Quiz de Fixação

1. Qual a diferença entre a camada Standard e a Archive de snapshots e quando usar a Archive?
2. O que o Fast Snapshot Restore resolve e qual seu custo/risco?
3. Qual a diferença entre Snapshot Lock governance e compliance?
4. Como proteger snapshots contra compartilhamento público e exclusão?

**Respostas:**
1) Standard é incremental e restaura rápido; Archive guarda cópias completas em armazenamento frio, bem mais barato por GB, com retenção mínima de 90 dias e restauração em horas a dias; indicada para retenção longa com baixa chance de restauração.
2) Elimina a lentidão inicial (lazy loading) de volumes restaurados, pré-inicializando o snapshot nas AZs escolhidas; cobra por hora, por snapshot e AZ, e tem limite de snapshots por região, então deve ser usado só onde o RTO exige.
3) Governance permite que usuários com permissão especial removam ou alterem o bloqueio; compliance, após o período de carência, é imutável (nem a conta raiz remove antes do prazo).
4) Habilitando o bloqueio de acesso público a snapshots na conta, restringindo o compartilhamento com IAM/SCP, usando CMK para criptografar, aplicando Snapshot Lock, Recycle Bin e cópias em conta/região separadas, com CloudTrail e Config para auditar.
