### Snapshots do EBS — incrementais, restauração, Fast Snapshot Restore, Data Lifecycle Manager e Recycle Bin

> [!warning] Aviso
> Preços de snapshot, camadas (Standard/Archive), tempos de restauração e quotas mudam. Confirme na documentação. Os comandos **não foram executados**.

Um **snapshot** é uma cópia pontual de um volume EBS, guardada de forma durável (armazenada pela AWS em infraestrutura baseada no S3, não visível como objetos no seu bucket). É o mecanismo de **backup, migração entre AZs/regiões, criação de AMIs e recuperação de desastres** do EBS.

**Analogia:** é tirar **fotografias do HD**. A primeira foto registra tudo; as seguintes registram **só o que mudou** desde a anterior. Para restaurar um dia específico, o sistema combina as fotos necessárias, e você não precisa guardar cópias inteiras.

## Como funcionam

```
 Volume (100 GiB)
   Snap 1 (dia 1): copia todos os blocos usados          → 40 GiB armazenados
   Snap 2 (dia 2): só blocos alterados (5 GiB)           → +5 GiB
   Snap 3 (dia 3): só blocos alterados (3 GiB)           → +3 GiB

 Apagar Snap 2: os blocos ainda necessários ao Snap 3 são preservados automaticamente
```

| Característica | Detalhe |
|---|---|
| **Incremental** | Cada snapshot guarda só os blocos alterados desde o último; você paga pelos blocos únicos |
| **Independência lógica** | Excluir um snapshot intermediário não quebra os demais |
| **Consistência** | Snapshot é *crash-consistent* (como queda de energia); para banco de dados, **pause escritas / flush** ou use backup com consciência de aplicação (VSS no Windows, scripts, AWS Backup) |
| **Escopo** | Regional; pode ser **copiado para outra região** e **compartilhado** com outras contas |
| **Criação** | Em volume em uso (sem desanexar), com leve impacto no desempenho na primeira vez |
| **Armazenamento** | Camada **Standard** ou **Archive** (mais barata, restauração mais lenta, retenção mínima) |

## Operações principais

```bash
# Criar um snapshot de um volume
aws ec2 create-snapshot --volume-id vol-0abc123 \
  --description "dados-app 2026-11-06" \
  --tag-specifications 'ResourceType=snapshot,Tags=[{Key=Name,Value=dados-app}]'

# Snapshots multi-volume consistentes de uma instância (vários volumes ao mesmo tempo)
aws ec2 create-snapshots --instance-specification InstanceId=i-0def456,ExcludeBootVolume=false

# Copiar para outra região (DR); --encrypted para criptografar na cópia
aws ec2 copy-snapshot --source-region sa-east-1 --source-snapshot-id snap-0aaa111 \
  --region us-east-1 --description "DR dados-app" --encrypted

# Restaurar: criar um volume NOVO a partir do snapshot, na AZ desejada
aws ec2 create-volume --snapshot-id snap-0aaa111 \
  --availability-zone sa-east-1b --volume-type gp3

# Criar uma AMI a partir de uma instância (gera snapshots dos volumes)
aws ec2 create-image --instance-id i-0def456 --name "app-v42" --no-reboot
# --no-reboot evita reinício, mas reduz a consistência do sistema de arquivos
```

Restaurar **não sobrescreve** o volume original: sempre cria um novo volume (que pode substituir o antigo depois de trocar o anexo).

## Restauração e "lazy loading"

O volume criado de um snapshot fica **disponível imediatamente**, mas os blocos são **carregados do armazenamento sob demanda** na primeira leitura, o que causa **latência maior no primeiro acesso**. Opções:

| Técnica | Efeito |
|---|---|
| **Inicialização manual** (ler todos os blocos, ex.: `fio`/`dd`) | "Aquece" o volume antes do uso |
| **Fast Snapshot Restore (FSR)** | O snapshot é pré-aquecido em AZs escolhidas: volumes criados dele entregam desempenho total desde o início. **Cobrança por hora e por AZ**; use para snapshots críticos de restauração rápida |
| **Provisioned Rate for Volume Initialization** | Taxa de carregamento definida para previsibilidade (recurso mais recente; confirme) |

## Automação: Data Lifecycle Manager (DLM)

O **DLM** cria, retém e exclui snapshots (e AMIs) automaticamente por **políticas** baseadas em tags.

```
 Política "diaria":  alvo = volumes com tag Backup=diario
                      agenda: todo dia 03:00 UTC
                      retenção: 14 snapshots
                      copiar para us-east-1: sim (retenção 7)
```

```bash
# Política simplificada (resumo; confira o formato completo na documentação)
aws dlm create-lifecycle-policy \
  --description "Snapshots diarios" --state ENABLED \
  --execution-role-arn arn:aws:iam::111122223333:role/AWSDataLifecycleManagerDefaultRole \
  --policy-details file://politica-dlm.json
```

Para um **plano de backup centralizado e entre serviços** (EBS, RDS, EFS, DynamoDB), com cofres e regras de conformidade, prefira o **AWS Backup** (nota própria desta trilha). O DLM é focado em EBS/AMI.

## Recycle Bin e proteção contra exclusão

- **Recycle Bin (Lixeira)**: regras de retenção mantêm snapshots e AMIs excluídos por um período (de 1 dia a 1 ano), permitindo **restaurar exclusões acidentais**.
- **Snapshot lock** (recurso de bloqueio) impede exclusão durante um período; útil para ransomware/conformidade (confirme os modos disponíveis).
- Controle com **IAM** (permissão `ec2:DeleteSnapshot` restrita) e **SCP** em Organizations.

```bash
# Regra de lixeira: reter snapshots excluídos por 7 dias
aws rbin create-rule --resource-type EBS_SNAPSHOT \
  --retention-period RetentionPeriodValue=7,RetentionPeriodUnit=DAYS \
  --description "Reter snapshots excluídos"
```

## Compartilhamento e DR

| Cenário | Como |
|---|---|
| Entregar dados a outra conta | Compartilhar snapshot (modify-snapshot-attribute) ou usar cópia; snapshots **criptografados** exigem compartilhar a **chave KMS** |
| DR em outra região | `copy-snapshot` agendado (DLM ou AWS Backup) |
| Migrar volume para outra AZ | snapshot → novo volume na AZ de destino |
| Clonar ambiente | snapshot → volumes → instâncias (ou AMI) |

## Exemplo prático

Estratégia para o volume de dados de um banco em EC2:

1. Política DLM diária com retenção de 14 dias e cópia semanal para outra região.
2. Antes do snapshot, `FLUSH TABLES WITH READ LOCK`/`pg_start_backup` (ou use backup do próprio banco) para consistência; ou aceite crash-consistency se o banco tolera recuperação por log.
3. Recycle Bin com 7 dias de retenção.
4. Teste mensal de restauração: criar volume do snapshot, anexar a instância de teste, validar dados e **medir o RTO** (tempo real).
5. FSR habilitado somente no snapshot mais recente da AZ de DR, se o RTO exigir.

## Como o incremental realmente funciona

```
 Snap1 (completo)   blocos: A B C D
 Snap2 (incremental) mudou: B' → armazena só B' (e referencia A C D do Snap1)
 Snap3 (incremental) mudou: D' → armazena só D'
 Apagar Snap2: B' é preservado se Snap3 precisar; a AWS reorganiza as referências
 → qualquer snapshot restaura o volume COMPLETO daquele ponto no tempo
```

| Aspecto | Regra |
|---|---|
| Consistência | Crash-consistent por padrão; para consistência de aplicação, quiesce (VSS no Windows, `fsfreeze` no Linux) ou use `multi-volume snapshots` |
| Armazenamento | S3 gerenciado pela AWS (não aparece no seu bucket) |
| Custo | Por GB-mês dos blocos únicos, com opção Archive (mais barata, restauração lenta) |
| Cópia | Entre regiões e contas (criptografia exige chave compartilhada) |
| Tags | Herdáveis do volume; úteis para DLM e custos |

> [!warning] Camadas (Standard/Archive), tempos de restauração e preços mudam; confirme na documentação atual.

## Fast Snapshot Restore (FSR) e lazy loading

| Situação | Sem FSR | Com FSR |
|---|---|---|
| Primeira leitura de blocos | Baixa performance (blocos buscados do S3) | Volume com desempenho total desde o início |
| Custo | Nenhum extra | Cobrança por AZ habilitada por hora |
| Uso | Dev/test | Boot em escala (ASG com muitas instâncias), bancos de produção |
| Alternativa | Pré-aquecer lendo todos os blocos (`fio`/`dd`) | — |

## Estratégia de proteção em camadas

```
 DLM / AWS Backup (agendado) ──► Snapshots ──► Recycle Bin (retenção de exclusão acidental)
                                      └─► Copy cross-region (DR) ──► Vault Lock (imutável, via AWS Backup)
```

## Troubleshooting

| Sintoma | Causa provável | Ação |
|---|---|---|
| Volume restaurado lento | Lazy loading | FSR ou pré-aquecimento |
| Cópia cross-region falha | Chave KMS sem permissão na região de destino | Re-encriptar com chave do destino |
| Snapshot enorme | Muitos blocos alterados | Revisar churn (logs, temporários) |
| Apagou sem querer | Sem Recycle Bin | Criar regra de retenção do Recycle Bin |

## Erros comuns e armadilhas

- **Nunca testar a restauração:** backup não testado não é backup.
- **Achar que snapshot é consistente para banco de dados** sem coordenação.
- **Esquecer que snapshots acumulam custo:** defina retenção (DLM) e apague órfãos.
- **Apagar o snapshot usado por uma AMI:** a AMI quebra (desregistre a AMI primeiro).
- **Copiar snapshot criptografado sem acesso à chave KMS no destino.**
- **FSR habilitado em todos os snapshots e AZs:** custo alto; use seletivamente.
- **Não ter cópia fora da região:** um desastre regional afeta volumes e snapshots da mesma região.
- **Esperar desempenho total logo após restaurar:** lazy loading.

## 🧩 Quiz de Fixação

1. Snapshots são incrementais: o que acontece ao excluir um snapshot do meio da cadeia?
2. Qual o problema de desempenho ao restaurar um volume de snapshot e como mitigá-lo?
3. Como evitar a perda de snapshots por exclusão acidental?

**Respostas:**
1) Nada de ruim: a AWS preserva os blocos ainda referenciados pelos snapshots seguintes; cada snapshot continua restaurável de forma independente.
2) Os blocos são carregados sob demanda, então o primeiro acesso é mais lento (lazy loading). Mitigue com inicialização prévia (ler todos os blocos) ou **Fast Snapshot Restore**.
3) Com **Recycle Bin** (retenção após exclusão), snapshot lock, permissões IAM/SCP restritas e políticas DLM/AWS Backup com cópias em outra conta ou região.

### Questões de aprofundamento

4. Apagar o snapshot do meio de uma cadeia quebra os demais?
5. Por que um volume restaurado de snapshot pode ser lento nas primeiras leituras?
6. Como obter snapshot consistente de um banco de dados?

**Respostas:**
4) Não; a AWS preserva os blocos que snapshots posteriores ainda referenciam.
5) Pelo lazy loading dos blocos do S3; mitigue com Fast Snapshot Restore ou pré-aquecimento.
6) Quiesce da aplicação (VSS/`fsfreeze`) ou snapshot multi-volume coordenado.
