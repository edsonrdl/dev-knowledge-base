### Criptografia do EBS — KMS, criptografia por padrão e compartilhamento de snapshots criptografados

> [!warning] Aviso
> Detalhes de chaves KMS, limites, preços e comportamentos de criptografia mudam. Confirme na documentação do EBS e do KMS. Os comandos **não foram executados**.

A criptografia do EBS protege **dados em repouso**, dados em trânsito entre a instância e o volume, **snapshots** e volumes criados deles. É transparente: a aplicação e o sistema operacional não mudam, e o impacto de desempenho é desprezível na maioria dos casos (a criptografia ocorre no hardware do host, em instâncias modernas).

**Analogia:** é um **cofre embutido no HD**. A chave não fica no disco: vive no serviço de chaves (KMS). Sem permissão na chave, o disco é só bytes ilegíveis, mesmo que alguém copie o snapshot.

## O que é criptografado

Quando um volume é criptografado, **tudo** abaixo é protegido com a mesma chave de dados:

- Dados em repouso no volume.
- Dados em **trânsito** entre a instância e o volume.
- **Snapshots** do volume.
- Volumes criados a partir desses snapshots.

```
 Instância ──(cifrado em trânsito)──► Volume EBS (cifrado) ──► Snapshot (cifrado) ──► Volume novo (cifrado)
                  chave de dados do volume (envelope) protegida por uma chave KMS
```

---

## Como funciona (envelope encryption)

1. O EBS pede ao KMS uma **chave de dados** exclusiva para o volume, protegida (cifrada) pela sua **chave KMS** (a *KMS key*).
2. A chave de dados cifrada fica guardada junto aos metadados do volume.
3. Ao anexar o volume, o EBS pede ao KMS para decifrar a chave de dados (se o principal tiver permissão) e a mantém na memória do host para cifrar/decifrar I/O.
4. Se a permissão na chave KMS é revogada, o volume deixa de poder ser anexado/lido.

---

## Que chave usar

| Opção | Gestão | Quando usar |
|---|---|---|
| **Chave gerenciada pela AWS** (`aws/ebs`) | A AWS gerencia; sem custo de chave; política não editável | Padrão simples; **não compartilhável** entre contas |
| **Chave gerenciada pelo cliente (CMK)** | Você controla política, rotação, desabilitação, auditoria | Requisito de conformidade, **compartilhamento entre contas**, separação de funções |

Regra: se for **compartilhar snapshots** com outra conta, use CMK (a chave `aws/ebs` não pode ser compartilhada).

## Criptografia por padrão (por região)

Você pode habilitar, **por conta e por região**, que **todo novo volume e snapshot copiado seja criptografado**.

```bash
# Habilitar a criptografia padrão EBS na região atual
aws ec2 enable-ebs-encryption-by-default --region sa-east-1
# Definir a chave padrão (CMK) usada quando não se especifica uma
aws ec2 modify-ebs-default-kms-key-id --kms-key-id alias/ebs-prod --region sa-east-1
# Conferir
aws ec2 get-ebs-encryption-by-default --region sa-east-1
```

Efeitos:

- Novos volumes e novas instâncias passam a ter volumes criptografados automaticamente.
- **Não** criptografa volumes existentes.
- Algumas famílias de instância antigas podem não suportar; verifique a compatibilidade.
- Combine com **SCP** ou IAM condition `ec2:Encrypted` para **negar** a criação de volumes não criptografados.

```json
{
  "Effect": "Deny",
  "Action": ["ec2:CreateVolume", "ec2:RunInstances"],
  "Resource": "*",
  "Condition": { "Bool": { "ec2:Encrypted": "false" } }
}
```

## Criptografar um volume existente (não criptografado)

Não existe "ligar a criptografia" em um volume existente. O caminho é **snapshot → cópia criptografada → novo volume**:

```bash
# 1) Snapshot do volume não criptografado
aws ec2 create-snapshot --volume-id vol-0aberto

# 2) Copiar o snapshot habilitando criptografia com a chave desejada
aws ec2 copy-snapshot --source-region sa-east-1 --source-snapshot-id snap-0aaa111 \
  --encrypted --kms-key-id alias/ebs-prod --region sa-east-1

# 3) Criar um volume do snapshot criptografado e substituir o anexo
aws ec2 create-volume --snapshot-id snap-0bbb222 --availability-zone sa-east-1a --volume-type gp3
# 4) Parar a instância, desanexar o volume antigo, anexar o novo (mesmo device), iniciar
```

Para o volume raiz, o procedimento equivalente usa uma **AMI copiada com criptografia** e novas instâncias, ou a opção de criptografar durante a cópia da AMI.

## Compartilhar snapshots criptografados

Cenário: enviar um snapshot à conta `444455556666`.

1. O snapshot deve estar criptografado com uma **CMK** (não `aws/ebs`).
2. **Compartilhe o snapshot** com a conta destino.
3. **Compartilhe a chave KMS** (policy permitindo `kms:Decrypt`, `kms:DescribeKey`, `kms:CreateGrant`, `kms:ReEncrypt*`, `kms:GenerateDataKey*` à conta/role destino).
4. A conta destino **copia o snapshot** recriptografando com **a própria chave** (recomendado), assumindo a posse independente dos dados.

```bash
aws ec2 modify-snapshot-attribute --snapshot-id snap-0aaa111 \
  --attribute createVolumePermission --operation-type add --user-ids 444455556666
# Na conta destino, após a chave ser compartilhada:
aws ec2 copy-snapshot --source-region sa-east-1 --source-snapshot-id snap-0aaa111 \
  --encrypted --kms-key-id alias/chave-destino --region sa-east-1
```

Snapshots **não criptografados** compartilhados publicamente expõem dados: evite; verifique com o AWS Config / Trusted Advisor.

## Auditoria e boas práticas

- Habilite a **criptografia por padrão** em todas as regiões usadas.
- Use **CMK** com rotação automática anual e alias claro por ambiente.
- Restrinja a policy da chave (princípio do menor privilégio) e separe quem administra a chave de quem a usa.
- **CloudTrail** registra o uso da chave (`Decrypt`, `GenerateDataKey`, `CreateGrant`).
- Regra do **AWS Config** `encrypted-volumes` detecta volumes sem criptografia.
- Cuidado com **desabilitar/agendar exclusão da chave**: os volumes ficam inacessíveis.
- Inclua a chave nos planos de **DR multi-região** (cópias de snapshot recriptografadas com a chave da região de destino).

---

## Exemplo prático

Política corporativa: "nenhum volume sem criptografia, com chave por ambiente".

1. Em cada conta e região, `enable-ebs-encryption-by-default` com CMK `alias/ebs-<ambiente>`.
2. SCP em Organizations negando `ec2:CreateVolume`/`RunInstances` com `ec2:Encrypted=false`.
3. Regra do AWS Config `encrypted-volumes` para detectar legado, com plano para migrar via snapshot → cópia criptografada.
4. DR: cópia diária do snapshot para outra região recriptografada com a CMK local de lá.

## Matriz de decisão de chaves

| Chave | Quando usar | Prós | Contras |
|---|---|---|---|
| **aws/ebs** (gerenciada) | Padrão, sem requisitos especiais | Simples, sem custo de chave | Não permite compartilhar snapshots com outra conta |
| **CMK do cliente (KMS)** | Compliance, rotação, compartilhamento, auditoria | Controle de política, grants, cross-account | Custo da chave e requisições |
| **CMK multi-região** | DR com mesma chave lógica em duas regiões | Re-encriptação simplificada | Gestão mais complexa |

> [!warning] Preços, cotas de requisições e recursos do KMS mudam; confirme na documentação atual.

## Fluxo de compartilhamento cross-account

```
 Conta A: snapshot criptografado com CMK-A
   1. Política da CMK-A permite Conta B (Decrypt, CreateGrant, DescribeKey, ReEncrypt*, GenerateDataKey*)
   2. Compartilhar o snapshot com Conta B (modify-snapshot-attribute)
 Conta B: copy-snapshot --kms-key-id CMK-B  → cópia re-encriptada com chave própria → create-volume
```

## Receita para criptografar o que já existe

```
 Volume não criptografado ──snapshot──► copy-snapshot --encrypted --kms-key-id X ──► create-volume ──► trocar na instância
 (parar a instância, desanexar o antigo, anexar o novo com o mesmo device, validar e só então excluir o antigo)
```

## Efeitos operacionais

| Tema | Detalhe |
|---|---|
| Desempenho | Impacto desprezível; criptografia no host |
| Instâncias | Maioria dos tipos suporta; verificar tipos antigos |
| Chave desabilitada/excluída | Volumes inacessíveis; instância não inicia |
| AMI criptografada | Herda a chave; cópia para outra região exige chave no destino |
| Auditoria | CloudTrail registra `Decrypt`/`CreateGrant`; Config `encrypted-volumes` |

## Troubleshooting

| Sintoma | Causa provável | Ação |
|---|---|---|
| `Client.InvalidKMSKey.InvalidState` | Chave desabilitada/pendente de exclusão | Reabilitar ou restaurar a chave |
| Instância não inicia após restaurar | Role sem `kms:CreateGrant` | Ajustar a política |
| Não dá para compartilhar snapshot | Usa chave `aws/ebs` | Copiar com CMK |
| Volume criado não criptografado | Política sem default encryption na região | Habilitar por região |

## Erros comuns e armadilhas

- **Achar que a criptografia por padrão criptografa volumes existentes.**
- **Usar a chave `aws/ebs` e depois precisar compartilhar o snapshot:** é preciso recriar com CMK.
- **Esquecer de compartilhar a chave KMS** junto com o snapshot.
- **Apagar ou desabilitar a chave:** perda de acesso aos dados.
- **Falta de permissão do Auto Scaling/ECS** (role de serviço) na chave: instâncias não sobem com volumes criptografados.
- **Misturar regiões:** a chave é regional; DR precisa de chave na região de destino.
- **Tratar criptografia como substituta de backup ou controle de acesso.**
- **Esquecer o volume raiz** em instâncias legadas.

## 🧩 Quiz de Fixação

1. O que a criptografia do EBS protege?
2. Como criptografar um volume que foi criado sem criptografia?
3. Para compartilhar um snapshot criptografado com outra conta, o que é necessário?

**Respostas:**
1) Dados em repouso no volume, em trânsito entre instância e volume, os snapshots e os volumes criados deles.
2) Criar um snapshot, copiá-lo com criptografia habilitada (chave KMS escolhida), criar um volume do snapshot criptografado e substituir o volume na instância.
3) O snapshot precisa estar criptografado com uma **CMK** (não a chave `aws/ebs`), compartilhar o snapshot e a **chave KMS** com a conta destino, que deve copiar o snapshot recriptografando com a própria chave.

### Questões de aprofundamento

4. Por que não dá para compartilhar com outra conta um snapshot criptografado com a chave `aws/ebs`?
5. O que acontece se a CMK de um volume em uso for desabilitada?
6. Como forçar criptografia em toda a região?

**Respostas:**
4) A chave gerenciada não permite política de acesso entre contas; é preciso usar uma CMK do cliente.
5) O volume fica inacessível e a instância pode falhar ao iniciar até reabilitar a chave.
6) Ativar a criptografia por padrão na região e opcionalmente definir a CMK padrão.
