### Operações com volumes EBS — Elastic Volumes, expansão do sistema de arquivos, Multi-Attach, mudança de AZ e automação

> [!warning] Aviso
> Regras de modificação (intervalo mínimo entre alterações, tipos suportados), limites do Multi-Attach e comportamentos de dispositivos NVMe variam por tipo de volume e instância. **Confirme na documentação.** Os comandos **não foram executados** — muitos deles **alteram dados**: ensaie em ambiente de teste e **tire snapshot antes**.

O ciclo de vida de um volume EBS envolve operações recorrentes: **aumentar tamanho**, **mudar tipo ou IOPS** sem parar a aplicação (**Elastic Volumes**), **expandir a partição e o sistema de arquivos**, **anexar a mais de uma instância** (**Multi-Attach**), **mover para outra AZ** e **automatizar** tudo isso com IaC e user data. Esta nota dá o passo a passo seguro, os limites e os erros que derrubam servidores.

**Analogia:** é a **manutenção de um armário em uso**: dá para trocar as prateleiras e aumentar o armário sem tirar os documentos (Elastic Volumes), mas depois é preciso **reorganizar o espaço interno** (estender sistema de arquivos). Compartilhar o mesmo armário entre dois funcionários (Multi-Attach) exige um **sistema de reservas** para ninguém sobrescrever a pasta do outro.

## Elastic Volumes: alterar sem desanexar

Permite alterar **tamanho**, **tipo**, **IOPS** e **throughput** de um volume **em uso**.

| Característica | Detalhe |
|---|---|
| **Operações** | Aumentar tamanho; trocar tipo (gp2→gp3, gp3→io2, etc.); ajustar IOPS/throughput |
| **Online** | Sem desanexar e, na maioria dos casos, sem reiniciar a instância |
| **Redução de tamanho** | **Não suportada** |
| **Intervalo entre modificações** | É preciso aguardar (cerca de 6 horas ou até concluir a otimização) para modificar o mesmo volume de novo |
| **Estados** | `modifying` → `optimizing` (x%) → `completed`; o volume é utilizável durante o processo (desempenho pode oscilar) |
| **Tipos que exigem atenção** | Mudar de/para st1/sc1 tem restrições (consulte a matriz); volumes magnéticos legados |
| **Instâncias antigas** | Algumas gerações exigem parar/iniciar a instância para reconhecer o novo tamanho |
| **Custo** | Passa a cobrar o novo tipo/tamanho/IOPS imediatamente |

```bash
# Aumentar tamanho para 500 GiB e subir IOPS/throughput de um gp3
aws ec2 modify-volume --volume-id vol-0abc123 --size 500 --iops 8000 --throughput 400

# Acompanhar a modificação
aws ec2 describe-volumes-modifications --volume-ids vol-0abc123 \
  --query 'VolumesModifications[0].{Estado:ModificationState,Progresso:Progress,Tamanho:TargetSize,IOPS:TargetIops}'

# Migrar gp2 -> gp3 (online) — normalmente economiza e mantém/ganha desempenho
aws ec2 modify-volume --volume-id vol-0abc123 --volume-type gp3
```

Boas práticas: **snapshot antes**; modifique em horário de menor carga; evite "otimizar" em pico; monitore latência durante `optimizing`.

## Expandir partição e sistema de arquivos (Linux)

Aumentar o volume **não** aumenta automaticamente a partição nem o sistema de arquivos.

```bash
lsblk                                   # veja o tamanho do disco x partição
# Volume raiz com partição (nvme0n1p1):
sudo growpart /dev/nvme0n1 1            # estende a partição 1 para ocupar o disco todo
# Sistema de arquivos XFS (montado) — use o PONTO DE MONTAGEM:
sudo xfs_growfs -d /
# ext4 — use o DISPOSITIVO:
sudo resize2fs /dev/nvme0n1p1
df -h /                                 # confirme o novo tamanho
```

| Cenário | Comandos |
|---|---|
| **Disco sem partição** (ex.: `/dev/nvme1n1` formatado direto) | `sudo xfs_growfs -d /dados` ou `sudo resize2fs /dev/nvme1n1` |
| **LVM** | `pvresize /dev/nvme1n1` → `lvextend -r -l +100%FREE /dev/vg/lv` |
| **Windows** | Gerenciamento de Disco → *Estender Volume* (ou `Resize-Partition` em PowerShell) |
| **Instâncias antigas (Xen)** | Pode exigir `stop/start` |

Com **SSM Run Command** ou **EC2 Image Builder**, automatize a expansão em frotas.

## Multi-Attach

Permite anexar **um mesmo volume io1/io2** a **várias instâncias** na **mesma AZ** (até 16 instâncias Nitro).

```
        AZ-a
 ┌── EC2 nó 1 ──┐
 ├── EC2 nó 2 ──┼──► MESMO volume io2 (blocos compartilhados)   ← exige sistema de arquivos/aplicação "cluster-aware"
 └── EC2 nó 3 ──┘
```

| Característica | Detalhe |
|---|---|
| **Tipos** | io1 e io2 (inclusive Block Express); **não** gp3/st1/sc1 |
| **Instâncias** | Nitro, na mesma AZ; até 16 |
| **Acesso** | Cada instância lê e escreve nos mesmos blocos — **sem coordenação automática** |
| **Requisito** | Sistema de arquivos cluster-aware (GFS2, OCFS2, Windows Server Failover Cluster com CSV) ou aplicação que gerencia a concorrência (Oracle RAC, SAP) |
| **Reservas** | io2 Block Express suporta **NVMe reservations** para coordenar acesso |
| **Casos** | Alta disponibilidade de aplicações em cluster com disco compartilhado, failover rápido sem reanexar |
| **Não use para** | Compartilhar arquivos entre instâncias com ext4/xfs comuns (**corrupção**) — use **EFS/FSx** |
| **Limites** | Sem criptografia diferente por instância; snapshots são do volume |

```bash
aws ec2 create-volume --availability-zone sa-east-1a --volume-type io2 --size 200 --iops 10000 --multi-attach-enabled
aws ec2 attach-volume --volume-id vol-0multi --instance-id i-0nodo1 --device /dev/sdf
aws ec2 attach-volume --volume-id vol-0multi --instance-id i-0nodo2 --device /dev/sdf
```

Alternativas modernas: **EFS** (NFS), **FSx** (Windows/ONTAP/Lustre) e **replicação em nível de aplicação** (Always On, DRBD, Pacemaker).

## Mover dados entre AZs e instâncias

| Necessidade | Procedimento |
|---|---|
| **Outra instância, mesma AZ** | `detach-volume` → `attach-volume` (desmontar antes; para raiz, parar a instância) |
| **Outra AZ** | **Snapshot** → `create-volume --snapshot-id --availability-zone` na AZ de destino → anexar |
| **Outra região** | Snapshot → `copy-snapshot` (região de destino) → `create-volume` |
| **Outra conta** | Compartilhar o snapshot (e a CMK se criptografado) → copiar na conta de destino |
| **Trocar o volume raiz** | Criar do snapshot, parar a instância, desanexar o raiz atual, anexar o novo como `/dev/xvda`, iniciar (ou *replace root volume*, recurso mais recente) |

```bash
aws ec2 detach-volume --volume-id vol-0abc123                 # desmonte (umount) ANTES no SO
aws ec2 create-snapshot --volume-id vol-0abc123 --description "mover para AZ b"
aws ec2 create-volume --snapshot-id snap-0aaa --availability-zone sa-east-1b --volume-type gp3
```

## Automação e IaC

### User data para formatar e montar na primeira inicialização

```bash
#!/bin/bash
# Idempotente: formata só se o dispositivo ainda não tem sistema de arquivos
DEV=/dev/nvme1n1
if ! blkid $DEV; then mkfs -t xfs $DEV; fi
mkdir -p /dados
UUID=$(blkid -s UUID -o value $DEV)
grep -q "$UUID" /etc/fstab || echo "UUID=$UUID /dados xfs defaults,nofail,noatime 0 2" >> /etc/fstab
mount -a
```

### CloudFormation / Terraform (volume de dados)

```yaml
VolumeDados:
  Type: AWS::EC2::Volume
  Properties: { AvailabilityZone: !GetAtt Instancia.AvailabilityZone, Size: 200, VolumeType: gp3, Iops: 6000, Throughput: 250, Encrypted: true, KmsKeyId: !Ref ChaveEBS, Tags: [{Key: Name, Value: dados-app}] }
Anexo:
  Type: AWS::EC2::VolumeAttachment
  Properties: { InstanceId: !Ref Instancia, VolumeId: !Ref VolumeDados, Device: /dev/sdf }
```

Em **Launch Templates**/ASG: use `BlockDeviceMappings` com `DeleteOnTermination`, `Encrypted`, tipo, IOPS e tags; para volumes de dados persistentes ligados a instâncias com estado, planeje a reanexação (script de boot que anexa o volume por tag) ou prefira armazenamento externo (EFS, RDS).

### Tags e políticas

- **Tags** obrigatórias (`Name`, `Dono`, `Ambiente`, `Backup=diario`) para custos, backup (DLM/AWS Backup) e limpeza.
- **SCP/IAM** exigindo `ec2:Encrypted=true` e tipos permitidos.
- **AWS Config** (`ec2-volume-inuse-check`, `encrypted-volumes`).

## Exemplo prático

Disco de dados de um banco precisa dobrar de 500 GiB para 1 TiB e ganhar IOPS, sem parar:

1. **Snapshot** de segurança do volume (`create-snapshot`) e confirmação de `completed`.
2. `modify-volume --size 1024 --iops 10000 --throughput 500` (gp3); acompanhar `optimizing` até concluir.
3. Na instância: `lsblk` mostra 1 TiB; `growpart` (se particionado) e `xfs_growfs -d /dados`.
4. Validar: `df -h`, `fio` curto de leitura, latência da aplicação, métricas do volume.
5. Registrar a mudança em IaC (CloudFormation `Size/Iops/Throughput` atualizados) para evitar *drift*.
6. Alarme de espaço (`disk_used_percent` via CloudWatch Agent) em 80% para o próximo ciclo.
7. Próxima modificação só após o período de espera.

## Procedimentos seguros e árvore de decisão

| Mudança desejada | Ferramenta | Sem downtime? | Limites |
|---|---|---|---|
| Aumentar tamanho | Elastic Volumes | Sim | Depois expandir FS; espera de ~6 h antes de nova modificação |
| Trocar tipo (gp2→gp3) | Elastic Volumes | Sim | Idem |
| Aumentar IOPS/throughput | Elastic Volumes | Sim | Dentro dos limites do tipo |
| Diminuir tamanho | Não suportado | — | Criar volume menor e copiar dados |
| Mover para outra AZ | Snapshot → novo volume | Não | Cria cópia na AZ destino |
| Compartilhar entre instâncias | Multi-Attach (io1/io2) | Sim | Mesma AZ, FS cluster-aware |

> [!warning] Valores, limites e preços mudam; os exemplos deste material não foram executados. Tempo mínimo entre modificações e instâncias compatíveis com Multi-Attach mudam; consulte a documentação.

```
 Aumentar disco (Linux):
 1. modify-volume (nuvem)         ──► estado "optimizing" (usável)
 2. growpart /dev/xvda 1          ──► expande a partição
 3. resize2fs  (ext4) / xfs_growfs (XFS) ──► expande o sistema de arquivos
 4. df -h                         ──► confere
```

### Árvore de decisão

```
Preciso de mais espaço/desempenho?
├─ Sim ─► Elastic Volumes + expandir FS (sem parar a instância)
Preciso REDUZIR o volume?
├─ Sim ─► novo volume menor + rsync/dd; trocar anexo
Dois nós escrevendo no mesmo volume?
├─ Sim ─► só com FS cluster-aware + io2 Multi-Attach; senão EFS/FSx
```

## Boas práticas

1. **Snapshot antes** de modificar qualquer volume crítico.
2. Monitore `VolumeQueueLength` e `BurstBalance` (gp2) para decidir sobre IOPS.
3. Prefira gp3 a gp2: custo menor e IOPS desacoplados do tamanho.
4. Automatize com IaC (CloudFormation/Terraform); evite mudanças manuais não registradas.

## CLI comentado

```bash
# Aumenta para 500 GiB e migra para gp3 com 6000 IOPS
aws ec2 modify-volume --volume-id vol-0123 --size 500 --volume-type gp3 --iops 6000

# Acompanha o progresso da modificação
aws ec2 describe-volumes-modifications --volume-ids vol-0123

# Expande partição e sistema de arquivos (dentro da instância)
sudo growpart /dev/nvme0n1 1
sudo xfs_growfs -d /          # para ext4: sudo resize2fs /dev/nvme0n1p1

# Snapshot de segurança
aws ec2 create-snapshot --volume-id vol-0123 --description "pre-resize"
```

## Troubleshooting

| Sintoma | Causa provável | Ação |
|---|---|---|
| `df` mostra tamanho antigo | FS não expandido | `growpart` + `resize2fs/xfs_growfs` |
| Erro ao modificar de novo | Janela mínima entre modificações | Aguardar |
| Corrupção com Multi-Attach | FS não cluster-aware | Usar GFS2/OCFS2 ou EFS |
| Lentidão após restore de snapshot | Inicialização preguiçosa dos blocos | Pré-aquecer (leitura) ou Fast Snapshot Restore |

## Custo

Cobra-se por GB provisionado, IOPS/throughput acima do incluído e snapshots (incrementais). Migrar gp2→gp3 costuma reduzir custo. Fast Snapshot Restore tem custo por AZ/hora.

## Erros comuns e armadilhas

- **Esquecer de estender partição e sistema de arquivos** após aumentar o volume.
- **Tentar reduzir** o volume (não existe): é preciso criar um menor e copiar.
- **Modificar duas vezes seguidas** e ficar bloqueado pelo intervalo mínimo.
- **Usar `xfs_growfs` com o dispositivo** (usa o ponto de montagem) ou `resize2fs` com o ponto de montagem.
- **Multi-Attach com ext4/xfs comuns** (corrupção silenciosa).
- **Detach de volume montado** sem `umount` (risco de corrupção).
- **Volume em AZ diferente da instância:** não anexa; use snapshot.
- **Nomes de dispositivo no `fstab`** em vez de UUID.
- **Deixar `DeleteOnTermination=true` em disco de dados** importante (ou volumes órfãos acumulando custo).
- **Não versionar em IaC** e criar *drift*.
- **Sem snapshot antes** de operações de risco.

## 🧩 Quiz de Fixação

1. O que o Elastic Volumes permite e quais suas restrições?
2. Que passos são necessários dentro do SO depois de aumentar um volume?
3. Quando usar Multi-Attach e por que não para compartilhar arquivos comuns?
4. Como mover um volume para outra AZ?

**Respostas:**
1) Alterar tamanho, tipo, IOPS e throughput de um volume em uso, sem desanexar; não permite reduzir tamanho e há um intervalo mínimo entre modificações do mesmo volume.
2) Estender a partição (`growpart`) quando houver e depois o sistema de arquivos (`xfs_growfs` pelo ponto de montagem ou `resize2fs` pelo dispositivo), confirmando com `df -h`.
3) Em io1/io2 para aplicações ou sistemas de arquivos cluster-aware que coordenam o acesso concorrente (Oracle RAC, GFS2, WSFC); sistemas de arquivos comuns não coordenam e corrompem dados; para compartilhar arquivos use EFS ou FSx.
4) Criar um snapshot do volume e, a partir dele, criar um novo volume na AZ de destino e anexá-lo à instância dessa AZ.

**Questões complementares:**

4. Quais os passos para o Linux enxergar o novo tamanho depois de um `modify-volume`?
5. É possível reduzir um volume EBS?
6. Por que lentidão após restaurar um snapshot?

**Respostas das questões complementares:**
4) Expandir a partição (`growpart`) e depois o sistema de arquivos (`resize2fs` para ext4 ou `xfs_growfs` para XFS), conferindo com `df -h`.
5) Não; é preciso criar um volume menor, copiar os dados e trocar o anexo.
6) Porque os blocos são carregados do S3 sob demanda no primeiro acesso; pré-aquecer lendo o volume ou usar Fast Snapshot Restore.
