### 3.1.1.1. Validade e cenários de presigned URLs — expiração por tipo de credencial, roles e sessões, upload direto do navegador, downloads, CORS e padrões de aplicação

> [!warning] Aviso
> Limites exatos de expiração por tipo de credencial, comportamento em cada serviço de computação e recursos recentes (Access Points, S3 Access Grants) abaixo são **de memória e mudam**. **Confirme na documentação “Limiting presigned URL capabilities” e “Sharing objects with presigned URLs”.** Código, JSON e configurações são ilustrativos e **não foram executados**. Esta é uma das **pegadinhas clássicas do DVA-C03**: a validade real é **o menor** entre o prazo informado e a vida da **credencial**.

## 1. Quanto tempo uma presigned URL realmente vale?

A URL carrega `X-Amz-Expires` (segundos), mas **a validade efetiva** depende de **dois relógios**:

```
Validade efetiva = MENOR entre:
   (A) X-Amz-Expires pedido na geração (a partir de X-Amz-Date)
   (B) tempo de vida da CREDENCIAL que assinou (sessão STS/role/SSO) — e a permissão do assinante AINDA valer no uso
```

| Credencial do assinante | Máximo prático (de memória — confirmar) | Observação |
|---|---|---|
| **IAM user (chaves de longo prazo)**, SigV4 | **Até 7 dias** (604.800 s) | Limite do **SigV4**; **chave excluída/desativada → URL deixa de valer** |
| **IAM user (SigV2 legado)** | Até **uma data** distante (legado) | **Evitar** (SigV2 obsoleto) |
| **Role em EC2 (instance profile)** | **Até a expiração do token da instância** (**~6 h**, renovado automaticamente) | A URL **pode ser invalidada antes** do prazo pedido, se o token expirar |
| **Lambda (execution role)** | **Até a expiração da sessão da função** (em geral **horas**; **não** garanta mais que o tempo da **invocação/sessão**) | **Não** prometer > **~minutos–poucas horas**; **gerar sob demanda** |
| **ECS/Fargate task role / EKS (IRSA/Pod Identity)** | Até a **expiração das credenciais do container** (~**6 h** ou conforme configuração) | Idem |
| **AssumeRole/STS (AssumeRole, SSO)** | **Duração da sessão** (**15 min–12 h**; **role chaining ≤ 1 h**) | URL ≤ sessão |
| **Console AWS (CloudShell/console)** | **Até 12 h** | Limitado pela **sessão** |
| **Cognito Identity Pools** | Duração das **credenciais temporárias** (≈ **1 h**) | |
| **IAM Identity Center (SSO)** | **Sessão** do permission set | |

> [!warning] Armadilha
> Se você gera, **em Lambda**, uma URL com `ExpiresIn=7 dias`, ela **NÃO** vale 7 dias: **morre** quando o **token da execution role** expira. Para URLs **longas** (dias), assine com **IAM user** (de **longo prazo**, **com cautela**) **ou** — melhor — **gere URLs novas sob demanda**, ou use **CloudFront signed URLs** (com **par de chaves** próprias, sem depender de sessão).

### 1.1 Valor mínimo/máximo de `X-Amz-Expires`

| Limite | Valor |
|---|---|
| **Mínimo** | **1 segundo** |
| **Máximo (SigV4)** | **604.800 s (7 dias)** |
| **Padrão** (SDKs) | **3.600 s (1 h)** (Boto3) / **900 s (15 min)** (alguns SDKs) — **definir explicitamente** |

### 1.2 O que invalida uma URL antes do prazo

| Evento | Efeito |
|---|---|
| **Expiração da credencial do assinante** (token/sessão) | URL **inválida** (`ExpiredToken`) |
| **Exclusão/desativação da access key** | URL **inválida** |
| **Remoção/alteração da permissão** do assinante | **403** |
| **Revogação de sessões da role** (`aws:TokenIssueTime`) | URL **inválida** |
| **Bucket policy/ACL** passando a negar | **403** |
| **Exclusão do objeto** (GET) | 404/403 |
| **Relógio** (cliente/servidor) | Diferença > tolerância → **“Request has expired”** prematuramente |
| **Troca de chave KMS/permissão** | Falhas de decriptação |

## 2. Estratégias de expiração

| Estratégia | Quando |
|---|---|
| **Curta (30 s–5 min) para downloads iniciados pelo usuário** | **Padrão seguro**: o front **solicita a URL no clique** |
| **Média (5–15 min) para uploads simples** | Tempo de **upload** + folga |
| **Longa para uploads multipart/grandes** | **Horas**, **limitada** pela credencial (use **role** com **sessão** longa **ou** renove URLs por parte) |
| **Sob demanda** | **Não** armazenar URLs; **gerar** a cada acesso (e **cachear** curtíssimo, se preciso) |
| **Links compartilhados por e-mail/mensagem** | **Evitar**; usar **link do app** que **autentica** e **gera a URL** na hora |
| **Acesso por dias** | **CloudFront signed URL** (par de chaves) ou **página da aplicação** com autenticação |

## 3. Cenário A: download seguro de arquivos privados

```
Usuário logado ─▶ clica "Baixar" ─▶ API (Lambda) autoriza (o usuário pode acessar este arquivo?)
                                         └─▶ gera presigned GET (ExpiresIn=60–300) com ResponseContentDisposition
                                         └─▶ responde 200 {url} (ou 302 Location: url)
Navegador ─▶ GET direto no S3 (sem passar pelo backend)
```

Cuidados:

- **Autorização no backend** (a URL **não** sabe quem é o usuário).
- **Auditar** a **emissão** (log: usuário, chave, hora, IP).
- **Cabeçalhos**: `Content-Disposition`, `Cache-Control: private, no-store` (via `ResponseCacheControl`).
- **Evitar** URLs em **logs** (query string contém assinatura): **mascarar** `X-Amz-Signature`.

## 4. Cenário B: upload direto do navegador/app

```
1) Front pede ao backend: "quero enviar arquivo X (tipo, tamanho)"
2) Backend: autentica → valida (tipo/tamanho permitidos) → gera CHAVE própria → presigned PUT/POST (curto) → retorna {url, chave}
3) Front: PUT/POST direto ao S3 (progresso, retry, cancelamento)
4) S3 → evento (ObjectCreated) → Lambda valida/processa (antivírus, imagem, metadados) → atualiza o registro (DynamoDB)
5) Front consulta o status (polling/WebSocket/EventBridge → push)
```

### 4.1 CORS (obrigatório para navegadores)

O **navegador** faz requisições **cross-origin** ao S3: o **bucket** precisa de **regras CORS**.

```json
[
  {
    "AllowedOrigins": ["https://app.suaempresa.com"],
    "AllowedMethods": ["PUT", "POST", "GET", "HEAD"],
    "AllowedHeaders": ["*"],
    "ExposeHeaders": ["ETag", "x-amz-request-id", "x-amz-version-id"],
    "MaxAgeSeconds": 3000
  }
]
```

```bash
aws s3api put-bucket-cors --bucket uploads-prod --cors-configuration file://cors.json
```

| Ponto CORS | Detalhe |
|---|---|
| **`AllowedOrigins`** | **Origens específicas** (evitar `*` em produção) |
| **`AllowedHeaders`** | **Content-Type**, **x-amz-*** etc. (ou `*`) |
| **`ExposeHeaders: ETag`** | **Obrigatório** em **multipart** (o front lê o **ETag** de cada parte) |
| **Preflight (OPTIONS)** | O S3 responde conforme a configuração |
| **Erro típico** | **“CORS policy: No 'Access-Control-Allow-Origin'”** no console do navegador (parece falha da URL, mas é CORS) |

### 4.2 Upload com progresso e retry

- **XHR/`fetch`+streams** com **eventos de progresso**;
- **Retentativa** de **partes** (multipart);
- **Cancelamento** (`AbortController`) e **abort** no backend.

## 5. Cenário C: apps mobile

| Ponto | Detalhe |
|---|---|
| **Fluxo** | Igual ao navegador; usar **bibliotecas** (URLSession/OkHttp/Amplify Storage) |
| **Conectividade instável** | **Multipart** + **retries** + **URLs renováveis** |
| **Segurança** | **Sem chaves** no app; URLs **curtas**; **TLS** |
| **Alternativa** | **Amplify Storage** (usa **Cognito** + S3) com **permissões por usuário/prefixo** |

## 6. Cenário D: integração B2B (parceiros)

| Aspecto | Prática |
|---|---|
| **Envio** | Parceiro recebe **PUT presigned** por **arquivo** (ou **URL do portal**) |
| **Recebimento** | Parceiro baixa via **GET presigned** (curto) |
| **Escala** | Muitos arquivos → **API** de emissão de URLs ou **Transfer Family/SFTP** (se o parceiro exige protocolo) |
| **Contrato** | **Expiração**, **tamanho**, **formatos**, **retentativas**, **IPs** |
| **Rastreabilidade** | **Chave** com **ID do parceiro/lote**; **eventos**; **logs** |

## 7. Cenário E: Presigned URL com Access Points e VPC endpoints

| Recurso | Comportamento (de memória — confirmar) |
|---|---|
| **S3 Access Points** | É possível gerar presigned URLs para **ARNs de Access Point** (políticas **por access point**) |
| **VPC endpoints** | URLs **funcionam por dentro da VPC** se a **rota** existir; **bucket policy** com `aws:SourceVpce` **exige** que o **cliente** use o **endpoint** (URLs usadas **fora** da VPC falham) |
| **Multi-Region Access Points** | Requer **SigV4A** (suporte do SDK) |
| **Transfer Acceleration** | `use_accelerate_endpoint` na geração (endpoint `s3-accelerate`) |
| **Dual-stack** | `use_dualstack_endpoint` |

## 8. Alternativas para validade longa ou controle fino

| Necessidade | Alternativa |
|---|---|
| **Dias/semanas de validade** | **CloudFront signed URL** (par de chaves, `DateLessThan` arbitrário) ou **página autenticada** |
| **Restringir por IP** | **CloudFront signed URL com IP** ou **condição de bucket policy** `aws:SourceIp` (afeta **todas** as requisições) |
| **Várias arquivos** | **CloudFront signed cookies** |
| **Controle por usuário/grupo com auditoria** | **S3 Access Grants** (IAM Identity Center/IdP) ou **proxy** |
| **Download com revogação instantânea** | **Proxy** autenticado (com revogação) ou **URL curtíssima** |
| **Compartilhamento “público por link”** com expiração | **Link da aplicação** (token próprio) → gera presigned na hora |

## 9. Boas práticas de validade

1. **Menor expiração possível** que atenda ao caso (**segundos–minutos**).
2. **Gerar sob demanda**; **não persistir** URLs.
3. **Não prometer validade > sessão** do assinante.
4. **Assinar com role de privilégio mínimo** e **chave não excluída**.
5. **Monitorar** relógio (**NTP**) em backends e clientes.
6. **Renovar** URLs de **multipart** por parte.
7. **Usar HTTPS** (a URL é um **portador**).
8. **Registrar** emissões (auditoria).
9. **Testar** expiração/renovação em **homologação**.
10. **Educar** times sobre a **pegadinha da validade** com **roles**.

## 10. Erros comuns

- **`ExpiresIn` de dias em Lambda/EC2** (expira com o token).
- **Armazenar URLs em banco/e-mail** (vencem/vazam).
- **CORS ausente** (confundido com URL inválida).
- **Relógio do dispositivo** desajustado (URL “expirada”).
- **URL com VPC endpoint** usada **fora da VPC**.
- **Exclusão de usuário/chave** invalidando URLs em uso.
- **Reutilizar a mesma URL de upload** para vários arquivos.
- **Expiração curta demais para uploads grandes** (cai no meio).
- **Ignorar o ETag exposto** (multipart).
- **Sem reconciliação** do upload (arquivos órfãos).

## 11. Troubleshooting

| Sintoma | Causa provável | Ação |
|---|---|---|
| URL “expira” antes do prazo | Credencial do assinante expirou | Renovar sessão; gerar sob demanda; usar CloudFront para longos |
| `ExpiredToken` na URL | Token de sessão vencido | Gerar nova URL |
| Funciona no curl, falha no navegador | **CORS** | Configurar CORS |
| Upload grande falha no meio | Expiração/credencial | Multipart + renovar URLs; sessão maior |
| `Request has expired` imediato | Relógio do cliente/servidor | Sincronizar NTP |
| 403 só fora da VPC | `aws:SourceVpce` na bucket policy | Usar dentro da VPC ou ajustar a policy |
| Parceiros reclamam de links vencidos | Expiração curta/links por e-mail | Link da aplicação que gera a URL na hora |

## 12. Resumo rápido

- **Validade efetiva = menor entre `X-Amz-Expires` e a vida da credencial do assinante**; **IAM user** até **7 dias**; **roles/STS** limitados pela **sessão** (EC2 ~6 h; Lambda/ECS conforme sessão; **role chaining 1 h**).
- **Gerar sob demanda**, **expiração curta**; para **dias**, usar **CloudFront signed URLs** ou **página autenticada**.
- **Download**: **autorizar no backend**, **URL curta**, `ResponseContentDisposition`/`CacheControl`, **auditar**.
- **Upload do navegador**: backend **gera a chave**, **PUT/POST curto**, **CORS** (`ExposeHeaders: ETag`), **evento S3** para validar/processar.
- **Mobile**: multipart + retries; **Amplify/Cognito** como alternativa.
- **VPC endpoint/Access Points/Acceleration/SigV4A** têm requisitos próprios.
- **Invalidam antes**: expiração da credencial, chave excluída, permissão removida, revogação de sessões, policies, relógio.

## 🧩 Quiz de Fixação

1. Qual a validade efetiva de uma URL assinada por uma execution role do Lambda com ExpiresIn de 7 dias?
2. Qual o máximo de expiração com SigV4 e chaves de IAM user?
3. Por que configurar CORS é necessário em uploads do navegador?
4. Por que expor o ETag no CORS?
5. O que invalida uma presigned URL antes do prazo?
6. Como oferecer links válidos por vários dias com segurança?
7. Qual o impacto de `aws:SourceVpce` na bucket policy sobre presigned URLs?

**Respostas:**

1. A menor entre 7 dias e a vida do token da execution role; na prática expira quando a sessão da função expira (horas), bem antes de 7 dias.
2. 7 dias (604.800 segundos).
3. Porque o navegador faz requisições cross-origin ao S3; sem regras CORS ele bloqueia PUT/POST/GET mesmo com URL válida.
4. Porque no multipart o front precisa ler o ETag de cada parte para o backend completar o upload.
5. Expiração do token/sessão do assinante, exclusão/desativação da chave, remoção de permissões, revogação de sessões, policies que negam, exclusão do objeto ou relógio desajustado.
6. Com CloudFront signed URLs (par de chaves) ou links da aplicação autenticados que geram a presigned URL na hora.
7. Faz a URL funcionar só quando usada a partir do VPC endpoint indicado; usada de fora da VPC, é negada.
