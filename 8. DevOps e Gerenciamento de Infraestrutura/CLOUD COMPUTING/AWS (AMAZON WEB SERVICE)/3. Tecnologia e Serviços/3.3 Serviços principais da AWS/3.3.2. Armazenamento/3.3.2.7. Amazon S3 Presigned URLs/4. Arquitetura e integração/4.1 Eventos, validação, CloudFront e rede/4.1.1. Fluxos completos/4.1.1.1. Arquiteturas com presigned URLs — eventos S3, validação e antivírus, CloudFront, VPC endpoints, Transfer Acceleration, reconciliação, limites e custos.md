### 4.1.1.1. Arquiteturas com presigned URLs — eventos S3, validação e antivírus, CloudFront, VPC endpoints, Transfer Acceleration, reconciliação, limites e custos

> [!warning] Aviso
> Limites (tamanhos, partes, cotas de eventos), preços e comportamento de integrações (EventBridge, CloudFront, Access Points, Object Lambda) abaixo são **de memória e mudam**. **Confirme na documentação do S3, do CloudFront e na página de preços.** Diagramas, JSON e código são ilustrativos e **não foram executados**. Nomes de buckets, tabelas e funções são fictícios.

## 1. A ideia central: tirar o seu backend do caminho dos bytes

A grande vantagem das presigned URLs é **separar o plano de controle do plano de dados**:

| Plano | Quem faz | O que passa |
|---|---|---|
| **Controle** (autenticar, autorizar, decidir a chave, registrar a intenção) | **Seu backend** (API Gateway + Lambda, ECS, etc.) | **Poucos bytes** (JSON com a URL) |
| **Dados** (o arquivo em si) | **Cliente ↔ S3 direto** | **Todos os bytes** (MB–GB) |

Isso elimina **gargalos** (limite de **payload** do API Gateway e do Lambda, **timeouts**, **memória**), reduz **custo** (você não paga computação para “empurrar” bytes) e escala **quase sem limite** (o S3 absorve).

```
          (1) pede URL                (2) valida + gera chave + assina
 Cliente ─────────────▶ API (Lambda) ─────────────────────────────▶ DynamoDB (upload pendente)
    ▲                       │ (3) {url, chave}
    └───────────────────────┘
    │ (4) PUT/POST direto
    ▼
   S3 ──(5) ObjectCreated──▶ EventBridge/SQS/Lambda ──(6) valida/processa──▶ DynamoDB (status) ──▶ (7) notifica o cliente
```

## 2. Padrão completo de upload (ponta a ponta)

### 2.1 Etapas e responsabilidades

| # | Etapa | Responsável | Detalhe |
|---|---|---|---|
| 1 | **Solicitar upload** | Cliente → API | Envia **nome**, **tipo** e **tamanho** declarados |
| 2 | **Autenticar/autorizar** | API (Cognito/authorizer) | Usuário pode enviar **este tipo** nesta **cota**? |
| 3 | **Gerar a chave** | API | `usuarios/{id}/{uuid}.{ext}` — **nunca** aceitar a chave do cliente |
| 4 | **Registrar intenção** | API → DynamoDB | `PENDENTE`, **TTL** (ex.: 1 h), tamanho/tipo esperados, `uploadId` |
| 5 | **Assinar** | API | PUT/POST **curto** com **headers fixos** |
| 6 | **Upload direto** | Cliente → S3 | Progresso/retry/cancelamento |
| 7 | **Evento de criação** | S3 → fila/Lambda | `ObjectCreated:Put`/`CompleteMultipartUpload`/`Post` |
| 8 | **Validação pós-upload** | Lambda | Tamanho real, **magic bytes**, **antivírus**, dimensões etc. |
| 9 | **Promoção** | Lambda | Move de `quarentena/` para `aprovado/` (ou marca tag) |
| 10 | **Notificar** | EventBridge/WebSocket | Cliente sabe que o arquivo foi **aceito/rejeitado** |
| 11 | **Reconciliação** | Job agendado | Remove **órfãos** e marca **expirados** |

### 2.2 Por que validar **depois** do upload

O cliente **controla o corpo** enviado. Mesmo com `Content-Type` assinado e policy de POST, o conteúdo pode **mentir** (um `.exe` com `Content-Type: image/png`). Por isso:

| Controle **antes** (na assinatura) | Controle **depois** (no evento) |
|---|---|
| Tipo **declarado**, prefixo da chave, faixa de tamanho (POST), SSE obrigatória | **Magic bytes**, **antivírus**, **extensão real**, **dimensões**, **escaneamento de conteúdo** |
| **Barato** e **imediato** | **Definitivo** (olha o conteúdo real) |
| Reduz abuso **óbvio** | Elimina abuso **sofisticado** |

> [!tip] Padrão “quarentena → aprovado”
> Envie para um **prefixo/bucket de quarentena** (`quarentena/…`) **sem acesso de leitura** para os usuários. Só **depois** da validação o objeto é **copiado/movido** para o local final. Assim, **nenhum arquivo não validado** é servido.

## 3. Eventos do S3: como “ouvir” o upload

| Destino | Quando usar | Observações (de memória — confirmar) |
|---|---|---|
| **Lambda (direto)** | Processamento **simples** e **rápido** | Invocação **assíncrona** com **retries**; use **DLQ/destinos** |
| **SQS** | **Desacoplar**, controlar **concorrência**, **picos** | Padrão **robusto** para **cargas altas**; **DLQ** na fila |
| **SNS** | **Fan-out** para vários consumidores | Combine com SQS por consumidor |
| **EventBridge** | **Roteamento** por regras, filtros **ricos**, **vários alvos**, **arquivo/replay** | Ative “Send notifications to Amazon EventBridge” no bucket |

```json
{
  "source": ["aws.s3"],
  "detail-type": ["Object Created"],
  "detail": {
    "bucket": {"name": ["uploads-prod"]},
    "object": {"key": [{"prefix": "quarentena/"}]}
  }
}
```

### 3.1 Cuidados com eventos

| Ponto | Detalhe |
|---|---|
| **Entrega “pelo menos uma vez”** | Eventos **podem duplicar** → processamento **idempotente** (chave de idempotência = `bucket+key+versionId/etag`) |
| **Ordem não garantida** | Não dependa de **sequência** |
| **Chaves em URL-encoding** | Chave no evento vem **codificada** (`+` para espaço, `%xx`) → **decodificar** |
| **Loop de eventos** | Se o Lambda **escreve no mesmo bucket/prefixo** que dispara o evento → **recursão infinita** (use **prefixos distintos** ou **filtros**) |
| **Multipart** | O evento sai **uma vez**, no **complete** (não por parte) |
| **Atraso** | Normalmente **segundos**, sem **SLA rígido** |
| **Falhas** | **DLQ**/destinos de falha + **alarmes** |

### 3.2 Lambda de validação (esqueleto)

```python
import boto3, urllib.parse, json
s3 = boto3.client("s3"); ddb = boto3.resource("dynamodb").Table("uploads")

def handler(event, context):
    for rec in event["Records"]:                                  # (via SQS, o corpo contém o evento S3)
        body = json.loads(rec["body"])
        for r in body.get("Records", []):
            bucket = r["s3"]["bucket"]["name"]
            key = urllib.parse.unquote_plus(r["s3"]["object"]["key"])
            head = s3.head_object(Bucket=bucket, Key=key)
            esperado = ddb.get_item(Key={"chave": key}).get("Item")
            if not esperado or head["ContentLength"] > esperado["tamanho_max"]:
                s3.delete_object(Bucket=bucket, Key=key); atualizar(key, "REJEITADO"); continue
            cabecalho = s3.get_object(Bucket=bucket, Key=key, Range="bytes=0-15")["Body"].read()
            if not assinatura_valida(cabecalho, esperado["tipo"]):      # magic bytes
                s3.delete_object(Bucket=bucket, Key=key); atualizar(key, "REJEITADO"); continue
            # antivírus (ex.: container/serviço de scan) → tag "scan=clean" → copia para aprovado/
            s3.copy_object(Bucket=bucket, Key=key.replace("quarentena/", "aprovado/"),
                           CopySource={"Bucket": bucket, "Key": key}); atualizar(key, "APROVADO")
```

## 4. Antivírus e proteção de conteúdo

| Abordagem | Detalhe |
|---|---|
| **Scanner em container/Lambda** (ex.: ClamAV) | Baixa o objeto, escaneia, **tag/move** |
| **Soluções gerenciadas/parceiros** | Escaneamento **nativo ao S3** (ex.: serviços de proteção contra malware para S3) — **confirmar disponibilidade** |
| **Amazon Macie** | Descobre **dados sensíveis** (PII) — **não** substitui antivírus |
| **Tags de estado** | `scan-status=pending/clean/infected`; **bucket policy** nega **GET** quando `!= clean` |
| **Limites de tamanho** | Lambda tem **/tmp** e **tempo** limitados → **arquivos grandes**: **Fargate/ECS/Batch** |

```json
{
  "Sid": "SoLerObjetosLimpos",
  "Effect": "Deny",
  "Principal": "*",
  "Action": "s3:GetObject",
  "Resource": "arn:aws:s3:::uploads-prod/aprovado/*",
  "Condition": { "StringNotEquals": { "s3:ExistingObjectTag/scan-status": "clean" } }
}
```

## 5. Reconciliação e limpeza de órfãos

Falhas acontecem: o usuário **fecha a aba**, o upload **não termina**, a **validação rejeita**, o **registro** fica `PENDENTE` para sempre.

| Problema | Solução |
|---|---|
| **Registro `PENDENTE` sem objeto** | **TTL** no DynamoDB + job que marca **EXPIRADO** |
| **Objeto sem registro** (chave forjada/erro) | Job (**S3 Inventory** + comparação) → **remove** |
| **Multipart incompleto** | Lifecycle **`AbortIncompleteMultipartUpload`** (ex.: 1–7 dias) |
| **Quarentena acumulada** | Lifecycle **expira** `quarentena/` em N dias |
| **Versões não correntes** | Lifecycle de **versões antigas** |
| **Cotas por usuário** | Contabilizar **no evento** (tamanho real), **não** só na solicitação |

```json
{
  "Rules": [
    {"ID": "AbortarMultipart", "Status": "Enabled", "Filter": {"Prefix": ""},
     "AbortIncompleteMultipartUpload": {"DaysAfterInitiation": 3}},
    {"ID": "LimparQuarentena", "Status": "Enabled", "Filter": {"Prefix": "quarentena/"},
     "Expiration": {"Days": 2}}
  ]
}
```

## 6. Presigned URLs e CloudFront

### 6.1 Download: S3 direto vs CloudFront

| Critério | **Presigned URL (S3)** | **CloudFront (OAC) + signed URL/cookie** |
|---|---|---|
| **Cache** | Não | **Sim** (borda) |
| **Latência global** | Variável | **Baixa** |
| **Custo de saída** | Transferência do S3 para internet | Geralmente **menor** com CloudFront (e **sem** taxa de requisição do S3 nos hits) |
| **Controle** | Por **objeto** (assinante) | **Key groups**, políticas customizadas, **IP**, **janela** |
| **Origem protegida** | Bucket **privado** com permissões do assinante | Bucket privado **só acessível pelo CloudFront (OAC)** |
| **Quando usar** | **Poucos downloads**, **dados dinâmicos**, **simplicidade** | **Mídia/estáticos**, **muitos downloads**, **audiência global** |

### 6.2 Upload via CloudFront

Para **uploads**, CloudFront pode atuar como **“aceleração de borda”** (PUT/POST via distribuição), mas o padrão mais comum e simples continua sendo **presigned direto ao S3** ou **S3 Transfer Acceleration**. Se usar CloudFront para uploads, exija **OAC** com **assinatura SigV4 pela origem** e **cabeçalhos/políticas** adequados (**de memória — confirmar**).

### 6.3 Combinações comuns

| Necessidade | Arquitetura |
|---|---|
| **Upload privado + entrega global** | Upload **presigned** → bucket privado → **CloudFront (OAC)** com **signed URLs/cookies** para leitura |
| **Mídia com autorização por usuário** | **Signed cookies** após login + origem S3 **via OAC** |
| **Documentos sensíveis, poucos acessos** | **Presigned GET curtíssimo** gerado **na hora** |
| **Pré-processamento (miniaturas)** | Evento → Lambda → `thumbnails/` → CloudFront |

## 7. Rede: VPC endpoints, Access Points e aceleração

| Recurso | Papel com presigned URLs |
|---|---|
| **Gateway VPC endpoint (S3)** | **Tráfego privado** da VPC ao S3 (sem NAT/Internet). Presigned URLs usadas **de dentro da VPC** passam pelo endpoint |
| **Endpoint policy** | Pode **restringir** buckets/ações permitidos **pelo endpoint** (afeta **também** as URLs usadas **a partir da VPC**) |
| **Bucket policy `aws:SourceVpce`/`aws:SourceVpc`** | Restringe o acesso a **requisições vindas do endpoint/VPC** — presigned URLs **fora da VPC** são negadas |
| **Interface endpoints (PrivateLink)** | Acesso privado **de redes on-premises** (DX/VPN) |
| **S3 Access Points** | **Política por ponto de acesso**; presigned URLs podem usar o **ARN do access point** |
| **Multi-Region Access Point** | **SigV4A**; failover entre regiões |
| **Transfer Acceleration** | Endpoint **`bucket.s3-accelerate.amazonaws.com`**; **gere a URL já com o endpoint acelerado**; **custo extra** por GB |
| **Dual-stack** | IPv4/IPv6 |

```python
from botocore.config import Config
s3 = boto3.client("s3", region_name="us-east-1",
                  config=Config(signature_version="s3v4", s3={"use_accelerate_endpoint": True}))
url = s3.generate_presigned_url("put_object", Params={"Bucket": "uploads-prod", "Key": "usuarios/42/v.mp4"}, ExpiresIn=3600)
```

> [!warning] Host assinado
> O **`host`** faz parte da assinatura. Se você assinou para `uploads-prod.s3.us-east-1.amazonaws.com` e o cliente usa o **endpoint acelerado** (ou um **CNAME/proxy** que muda o `Host`), a assinatura **falha**. A URL deve ser **usada exatamente no host para o qual foi gerada**.

### 7.1 Proxy reverso/domínio próprio

Colocar um **domínio próprio** na frente do S3 (CNAME, ALB, Nginx) **altera o `Host`** → `SignatureDoesNotMatch`. Soluções: **CloudFront** com **cabeçalho Host preservado/origem S3** (não via presigned) ou **assinar para o host efetivo** (cenários avançados e frágeis — **evite**).

## 8. Limites e custos

| Item | Valor/ideia (de memória — confirmar) |
|---|---|
| **Tamanho máximo de objeto** | **5 TiB** |
| **PUT único** | **até 5 GiB** (recomenda-se **multipart > 100 MiB**) |
| **Partes (multipart)** | **5 MiB–5 GiB** cada, **até 10.000 partes** |
| **Expiração da URL** | **≤ 7 dias** (limitado pela credencial) |
| **Requisições** | Alta escala por prefixo (**milhares/s**) — **sem** limite prático para a maioria |
| **Custos S3** | **Armazenamento**, **requisições** (PUT/GET/LIST), **transferência de saída**, **Acceleration**, **eventos/Lambda**, **scan** |
| **Entrada (upload)** | **Sem cobrança** de transferência **de entrada** da Internet para o S3 |
| **Saída (download)** | **Cobrada** (exceto faixa gratuita); **CloudFront** costuma **reduzir** |
| **Multipart órfão** | **Cobra armazenamento** das partes → **lifecycle** de aborto |
| **Validação em Lambda** | Paga **invocações + duração** (arquivos grandes → **Fargate/Batch**) |

### 8.1 Evitando abuso e “custo surpresa”

| Risco | Mitigação |
|---|---|
| **Usuário gera milhares de URLs** | **Rate limit** na API (usage plans/WAF) |
| **Uploads enormes** | **POST policy** com `content-length-range`; **cotas por usuário** |
| **Downloads massivos** (URL vazada) | **Expiração curta**, **CloudFront** com WAF/rate limit, **alarmes de custo/tráfego** |
| **Armazenamento crescente** | Lifecycle (**Intelligent-Tiering/Glacier**), **limpeza** de quarentena |
| **Bots** | **WAF** + **CAPTCHA** na API de emissão |

## 10. Erros comuns

- **Processar no mesmo prefixo que dispara o evento** (loop).
- **Eventos sem idempotência** (duplicados).
- **Esquecer de decodificar a chave** do evento.
- **Servir arquivos antes da validação** (sem quarentena).
- **Confiar só no Content-Type** declarado.
- **Sem lifecycle** para multipart/quarentena.
- **Domínio/proxy** que altera o `Host`.
- **Usar a URL de Transfer Acceleration** sem gerar para o host acelerado.
- **Lambda tentando escanear arquivos gigantes** (tempo/memória).
- **Sem rate limit** na API que emite URLs.
- **Sem reconciliação** (registros e objetos órfãos).

## 11. Troubleshooting

| Sintoma | Causa provável | Ação |
|---|---|---|
| Evento **não dispara** | Notificação não configurada/filtro de prefixo errado | Conferir configuração e **permissão** do S3 para invocar Lambda/SQS |
| Lambda **dispara em loop** | Escreve no prefixo observado | Prefixos separados/filtros |
| Duplicatas no processamento | Entrega ao-menos-uma-vez | **Idempotência** |
| Chave com caracteres estranhos | URL-encoding | `unquote_plus` |
| `SignatureDoesNotMatch` via domínio próprio | `Host` diferente | Usar o host assinado |
| Upload **lento** para clientes distantes | Região distante | **Transfer Acceleration** / bucket regional |
| Custo de saída alto | Downloads diretos massivos | **CloudFront** + expiração curta |
| Objetos órfãos | Sem reconciliação/lifecycle | Jobs + lifecycle |

## 12. Resumo rápido

- **Presigned URLs separam controle e dados**: backend **só decide e assina**; **bytes vão direto ao S3**.
- Fluxo: **solicitar → autorizar → gerar chave → registrar intenção → URL curta → upload → evento → validar → promover → notificar → reconciliar**.
- **Validar depois** (magic bytes, antivírus) com **quarentena → aprovado**; **tag + bucket policy** para só servir objetos **limpos**.
- **Eventos**: Lambda/SQS/SNS/EventBridge; **idempotência**, **decodificar chave**, **evitar loops**, **DLQ**.
- **CloudFront** para **entrega global** (OAC + signed URLs/cookies); **presigned** para **upload** e **downloads simples**.
- **Rede**: VPC endpoints/`aws:SourceVpce`, Access Points, **Acceleration** (host assinado!), **não** alterar o `Host`.
- **Custos/limites**: multipart **5 MiB–5 GiB × 10.000**, objeto **5 TiB**, **lifecycle** de aborto, **rate limit** e **WAF** na emissão.

## 🧩 Quiz de Fixação

1. Que vantagem arquitetural as presigned URLs trazem?
2. Por que validar o conteúdo depois do upload?
3. O que é o padrão quarentena → aprovado?
4. Como evitar loops de eventos do S3?
5. Por que um domínio próprio na frente do S3 quebra a assinatura?
6. Como limpar uploads multipart incompletos?
7. Quando preferir CloudFront a presigned URLs para download?

**Respostas:**

1. Separam controle e dados: o backend só autoriza e assina; os bytes vão direto cliente↔S3, eliminando gargalos e custos de proxy.
2. Porque o cliente controla o corpo; Content-Type e policy não garantem o conteúdo real (magic bytes, vírus).
3. Enviar para um prefixo de quarentena sem leitura pública e só mover para aprovado após validação.
4. Usando prefixos distintos para entrada e saída e filtros de prefixo/sufixo nas notificações.
5. Porque o header host é assinado; alterá-lo invalida a assinatura (SignatureDoesNotMatch).
6. Com regra de lifecycle AbortIncompleteMultipartUpload.
7. Para entrega global com cache, muitos downloads e controles flexíveis (signed cookies, IP, janela), reduzindo latência e custo.
