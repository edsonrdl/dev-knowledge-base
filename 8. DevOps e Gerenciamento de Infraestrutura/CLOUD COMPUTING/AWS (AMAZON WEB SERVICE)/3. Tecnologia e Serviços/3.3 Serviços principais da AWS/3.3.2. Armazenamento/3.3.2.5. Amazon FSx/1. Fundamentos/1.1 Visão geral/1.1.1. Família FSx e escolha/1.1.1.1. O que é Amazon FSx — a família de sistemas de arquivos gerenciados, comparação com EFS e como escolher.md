### O que é Amazon FSx — a família de sistemas de arquivos gerenciados, comparação com EFS e como escolher

> [!warning] Aviso
> Os sabores do FSx, seus limites, tipos de implantação e preços mudam com frequência. Confirme na documentação. Os comandos **não foram executados**.

O **Amazon FSx** é uma **família de serviços** que entrega sistemas de arquivos de terceiros ou de código aberto **totalmente gerenciados** (provisionamento, patches, backups, alta disponibilidade). Em vez de instalar e operar um servidor de arquivos Windows, um cluster Lustre ou um NetApp em EC2, você pede o sistema pronto e a AWS cuida da infraestrutura.

**Analogia:** se o EFS é a "pasta compartilhada genérica da AWS", o FSx é uma **loja de marcas especializadas**: uma prateleira para quem precisa do Windows de sempre, outra para supercomputação, outra para o NetApp que a empresa já usa, outra para o ZFS.

## Os quatro sabores

| Sabor | Base | Protocolos | Para quê |
|---|---|---|---|
| **FSx for Windows File Server** | Windows Server (NTFS) | SMB, integração com Active Directory | Compartilhamentos Windows, home directories, aplicações .NET, SQL Server |
| **FSx for Lustre** | Lustre (código aberto) | Cliente Lustre POSIX | HPC, machine learning, processamento de mídia, análise financeira (alta vazão e baixa latência) |
| **FSx for NetApp ONTAP** | NetApp ONTAP | NFS, SMB, iSCSI (multiprotocolo) | Migrar cargas NetApp, ambientes multiprotocolo, clones e replicação avançados |
| **FSx for OpenZFS** | OpenZFS | NFS (v3/v4.x) e SMB | Migrar servidores ZFS/Linux, baixa latência, snapshots e clones baratos |

```
 Preciso de...
   SMB/NTFS/Active Directory (Windows)?          ─► FSx for Windows File Server
   Throughput gigantesco para HPC/ML + S3?       ─► FSx for Lustre
   NetApp ONTAP, multiprotocolo, SnapMirror?     ─► FSx for NetApp ONTAP
   ZFS/NFS de baixa latência, clones, snapshots? ─► FSx for OpenZFS
   NFS Linux simples, elástico, multi-AZ?        ─► EFS (não é FSx)
```

## Características comuns

| Característica | Detalhe |
|---|---|
| **Gerenciado** | A AWS provisiona, atualiza e monitora a infraestrutura |
| **Dimensionamento** | Você escolhe **capacidade de armazenamento** e **throughput** (aumentáveis; reduzir depende do sabor) |
| **Rede** | Dentro da VPC, com ENIs e Security Groups; acessível por VPN/Direct Connect |
| **Criptografia** | Em repouso (KMS) e em trânsito |
| **Backups** | Automáticos e manuais (incrementais), integração com AWS Backup |
| **Alta disponibilidade** | Depende do sabor: Multi-AZ (Windows, ONTAP, OpenZFS) ou AZ única (Lustre) |
| **Integração** | EC2, ECS, EKS, Lambda (alguns), WorkSpaces, AppStream, on-premises |
| **Custo** | Capacidade, throughput, IOPS (alguns), backups, transferência; sem taxa por requisição como no S3 |

## FSx × EFS × EBS × S3

| Critério | **FSx** | **EFS** | **EBS** | **S3** |
|---|---|---|---|---|
| Tipo | Arquivos (vários sabores) | Arquivos NFS | Bloco | Objetos |
| Protocolo | SMB, NFS, iSCSI, Lustre | NFS | Bloco (anexado) | HTTP/API |
| Windows | **Sim** (Windows, ONTAP) | Não | Sim (como disco) | Via gateway |
| Elasticidade | Dimensiona manualmente (alguns suportam automático) | **Totalmente elástico** | Manual | Ilimitado |
| Performance extrema (HPC) | **Lustre** | Boa | Alta por volume | Alta, mas outro modelo |
| Recursos de enterprise (snapshots, clones, dedup, replicação) | **ONTAP/OpenZFS/Windows** | Limitado | Snapshots | Versionamento, replicação |

Regra: **Linux simples e elástico → EFS; Windows ou enterprise → FSx; blocos → EBS; objetos → S3.**

---

## Tipos de implantação (conceito)

- **Single-AZ**: menor custo, resiliência de hardware dentro da AZ, sem proteção contra perda de AZ.
- **Multi-AZ**: standby em outra AZ com failover automático (Windows, ONTAP, OpenZFS).
- **Lustre**: *scratch* (temporário, sem replicação, máximo desempenho/custo menor) e *persistent* (replicado na AZ, dados duradouros).

## Exemplo prático

```bash
# Listar os sistemas de arquivos FSx da conta e o sabor de cada um
aws fsx describe-file-systems \
  --query 'FileSystems[].{Id:FileSystemId,Tipo:FileSystemType,Estado:Lifecycle,GiB:StorageCapacity,DNS:DNSName}'

# Listar backups
aws fsx describe-backups --query 'Backups[].{Id:BackupId,Tipo:Type,Estado:Lifecycle}'

# Criar um backup manual
aws fsx create-backup --file-system-id fs-0abc123 --tags Key=Name,Value=antes-da-migracao
```

Decisão de exemplo: uma empresa migra seus servidores de arquivos Windows e uma aplicação de análise de dados com milhares de núcleos.

- Servidores de arquivos Windows → **FSx for Windows File Server** Multi-AZ com AD.
- Análise HPC com dados no S3 → **FSx for Lustre** vinculado ao bucket.
- Linux simples para web → **EFS**.

## Comparação detalhada dos quatro sabores

| Critério | **Windows File Server** | **Lustre** | **NetApp ONTAP** | **OpenZFS** |
|---|---|---|---|---|
| Base | Windows Server + NTFS | Lustre (HPC) | ONTAP (NetApp) | OpenZFS |
| Acesso | SMB | Cliente Lustre (POSIX, Linux) | NFS, SMB, iSCSI, NVMe/TCP | NFS (SMB em versões novas) |
| Identidade | Active Directory | POSIX (UID/GID) | AD (SMB) e POSIX/Kerberos (NFS) | POSIX (NFS) |
| Alta disponibilidade | Single-AZ ou **Multi-AZ** | **Uma AZ** (scratch sem replicação) | Single-AZ ou **Multi-AZ** | Single-AZ ou **Multi-AZ** |
| Escala típica | Dezenas de TiB | Centenas de GB/s agregados | Centenas de TiB + capacity pool | Centenas de TiB, IOPS altos |
| Integração com S3 | Não nativa (DataSync) | **Nativa** (Data Repository Associations) | Tiering interno (capacity pool) | Não nativa (DataSync) |
| Cópias instantâneas | Shadow copies | Backups (persistent) | Snapshots, **FlexClone** | Snapshots, **clones** |
| Replicação/DR | Backups cross-region, DFS | Backups; S3 como fonte | **SnapMirror**, backups | Cópia incremental de snapshots |
| Quando é a escolha | Compartilhamentos Windows, .NET/SQL Server | HPC, ML, mídia, genômica | NetApp existente, multiprotocolo, híbrido | Migrar ZFS/NAS Linux, baixa latência, dev/test |

## Árvore de decisão

```
Workload Windows/SMB com Active Directory?
   └─ Sim ──► FSx for Windows File Server (ou ONTAP, se também precisar de NFS/iSCSI)
Throughput massivo paralelo para HPC/ML com dados no S3?
   └─ Sim ──► FSx for Lustre (scratch p/ jobs temporários, persistent p/ longa duração)
Já usa NetApp, precisa de NFS+SMB+iSCSI, SnapMirror ou tiering de custo?
   └─ Sim ──► FSx for NetApp ONTAP
Vem de servidor ZFS/NAS Linux, quer latência sub-ms e clones baratos?
   └─ Sim ──► FSx for OpenZFS
NFS Linux simples, elástico, sem planejar capacidade?
   └─ Sim ──► Amazon EFS (não é FSx)
Objetos, escala ilimitada, menor custo por GB?
   └─ Sim ──► Amazon S3
```

## Padrões de arquitetura

### 1. Lift-and-shift de servidor de arquivos Windows

```
 On-premises: servidor Windows ──DataSync/Robocopy──► FSx for Windows (Multi-AZ) ◄── usuários via VPN/Direct Connect
              AD local ◄──relação de confiança──► AWS Managed Microsoft AD   (DFS Namespace preserva os caminhos)
```

### 2. HPC com "burst" e dados no S3

```
 S3 (dataset durável) ◄─DRA─► FSx for Lustre (scratch) ◄── cluster Batch/ParallelCluster (centenas de nós, Spot)
 Ao fim do job: exportar resultados ao S3 e excluir o FSx (paga só enquanto usa)
```

### 3. Armazenamento híbrido com ONTAP

```
 Datacenter (NetApp) ══ SnapMirror ══► FSx for ONTAP (Multi-AZ) ──► aplicações na AWS (NFS/SMB/iSCSI)
                                          └─ capacity pool (frio) reduz custo; backup e DR na nuvem
```

### 4. Dev/test e CI com clones instantâneos

```
 FSx for OpenZFS: volume "golden" ──snapshot──► clone por pipeline (segundos) ──► descartado ao fim
```

## Migração para o FSx: ferramentas

| Origem | Ferramenta | Observações |
|---|---|---|
| Servidor Windows/NAS SMB | **DataSync**, **Robocopy** | Preservar ACLs NTFS (`/COPYALL`) |
| NFS (Linux/NAS) | **DataSync**, `rsync` paralelo | Preservar `uid/gid` e permissões |
| NetApp on-premises | **SnapMirror** (para ONTAP) | Baseline + incrementais + corte |
| Dados em S3 | **DRA** (Lustre) ou **DataSync** | Lustre lê do S3 sob demanda |
| FSx → FSx | Backups/restauração, DataSync | Mudar de sabor exige cópia |
| Volumes enormes offline | **Snow Family** | Depois DataSync para o destino final |

## Considerações transversais

1. **Capacidade e throughput são provisionados** (diferente de EFS/S3): dimensione e monitore; todos permitem aumentar a capacidade online.
2. **Rede**: sistemas vivem na VPC com Security Groups por sabor; acesso on-premises via VPN/Direct Connect.
3. **Criptografia**: sempre em repouso (KMS); em trânsito conforme o sabor.
4. **Backups**: automáticos e manuais (exceto Lustre scratch); **AWS Backup** para política central.
5. **Custo**: capacidade (SSD/HDD), throughput, IOPS, backups e (ONTAP) capacity pool; Multi-AZ aproximadamente dobra a infraestrutura.
6. **Gestão**: console/API da AWS para o sistema de arquivos; ferramentas nativas de cada sabor para o conteúdo.

## Erros comuns e armadilhas

- **Usar FSx onde o EFS bastaria:** custo e gestão maiores.
- **Escolher Single-AZ em produção crítica** sem plano de recuperação.
- **Subdimensionar a capacidade e o throughput:** o FSx não é "ilimitado" como o EFS/S3.
- **Esquecer que Lustre scratch é efêmero:** dados somem se o hardware falhar.
- **Não integrar com o AD** (Windows/ONTAP SMB) antes de criar o sistema de arquivos.
- **Security Group sem as portas do protocolo** (SMB 445, NFS 2049, Lustre 988/1018-1023).
- **Não planejar backups e retenção.**
- **Assumir que todos os recursos existem em todos os sabores.**

## 🧩 Quiz de Fixação

1. Que sabor do FSx escolher para compartilhamentos SMB integrados ao Active Directory?
2. Qual a diferença de uso entre FSx for Lustre e EFS?
3. Por que dizer que o FSx é "gerenciado" não elimina o planejamento de capacidade?

**Respostas:**
1) **FSx for Windows File Server** (ou FSx for NetApp ONTAP, quando se quer multiprotocolo e recursos NetApp).
2) Lustre é para HPC/ML com vazão e IOPS muito altos e integração com S3; o EFS é um NFS elástico e simples para uso geral em Linux.
3) Porque a AWS cuida da infraestrutura, mas você define capacidade, throughput e tipo de implantação, e precisa aumentá-los conforme a necessidade.

### Questões de aprofundamento

4. Uma aplicação .NET em EC2 precisa de um compartilhamento SMB com permissões do Active Directory e alta disponibilidade entre AZs. Qual sabor e que implantação escolher?
5. Uma equipe de ML treina modelos com 40 TB de imagens no S3 durante 3 dias por mês. Que sabor, tipo de implantação e ciclo de vida de custo faz sentido?
6. Quando preferir EFS ou S3 ao FSx?

**Respostas:**
4) FSx for Windows File Server em implantação **Multi-AZ** (standby em outra AZ com failover automático), integrado ao AWS Managed Microsoft AD ou ao AD próprio; ONTAP seria a alternativa se também fosse preciso NFS ou iSCSI.
5) FSx for Lustre **scratch** com Data Repository Association ao bucket do S3; cria-se sob demanda, treina-se, exportam-se os resultados e exclui-se o sistema, pagando só pelo período de uso; persistent só se o sistema precisasse viver por meses.
6) EFS quando o requisito é NFS Linux simples, totalmente elástico e sem planejar capacidade; S3 quando os dados são objetos acessados por API, sem semântica de sistema de arquivos, com escala ilimitada e menor custo por GB.
