### FSx for Lustre na prática — Data Repository Associations, striping, tuning do cliente, integração com Batch, ParallelCluster e SageMaker, e custo

> [!warning] Aviso
> Tipos de implantação, camadas de throughput por TiB, tamanhos mínimos, versões do cliente Lustre, integrações e preços do FSx for Lustre mudam. Os números são **ordens de grandeza**. **Confirme na documentação.** Os comandos **não foram executados**; operações de `release`/exclusão podem **apagar dados do sistema de arquivos**: confira a exportação ao S3 antes.

A nota anterior apresentou o FSx for Lustre (scratch vs persistent, integração com S3). Aqui vem a **prática**: configurar **Data Repository Associations (DRA)** com política de importação e exportação, **ajustar striping** de arquivos, **instalar e afinar o cliente**, **integrar com AWS Batch, ParallelCluster, EKS e SageMaker**, e **controlar custo** (o recurso certo para o job certo, e desligar quando termina).

**Analogia:** o Lustre é uma **oficina de produção paralela** que recebe matéria-prima do **armazém (S3)**, trabalha em altíssima velocidade com centenas de máquinas e devolve o produto ao armazém. A oficina só deve existir enquanto há produção — e o segredo é **distribuir bem as peças entre as esteiras (striping)**.

## Escolha do tipo de implantação (resumo prático)

| Tipo | Quando | Observações |
|---|---|---|
| **Scratch** | Jobs temporários (horas/dias); dados reconstruíveis a partir do S3 | Menor custo/maior burst; sem replicação: falha de hardware pode perder dados |
| **Persistent (SSD)** | Cargas contínuas/longas com dados que não podem ser perdidos | Replicado na AZ; **throughput por TiB configurável** (diversos níveis); suporta backups e criptografia em trânsito |
| **Persistent (HDD + cache SSD)** | Grandes volumes de throughput sequencial, custo menor | Cache SSD de leitura opcional |

Tamanhos: o armazenamento é provisionado em **incrementos** (por exemplo 1,2 TiB mínimo e múltiplos de 2,4 TiB em SSD; confira); o throughput total escala com a capacidade e o nível de MB/s por TiB.

## Data Repository Associations (DRA)

Uma **DRA** liga um **diretório** do sistema de arquivos a um **bucket/prefixo do S3** (até dezenas de associações por sistema), com políticas independentes.

```
 /fsx/treino  ◄───import (lazy)────  s3://dataset/treino/
 /fsx/saida   ────export (auto)───►  s3://dataset/saida/
```

| Elemento | Detalhe |
|---|---|
| **Caminho no sistema de arquivos** | Diretório mapeado (`/treino`) |
| **Caminho no repositório** | `s3://bucket/prefixo` |
| **Política de importação automática** | Eventos do S3: `NEW`, `CHANGED`, `DELETED` refletidos como metadados no Lustre |
| **Política de exportação automática** | Eventos do Lustre: `NEW`, `CHANGED`, `DELETED` enviados ao S3 |
| **Carregamento de dados** | Metadados primeiro; **conteúdo sob demanda** na primeira leitura (lazy load) |
| **Tarefas sob demanda** | `create-data-repository-task` de tipo `IMPORT_METADATA_FROM_REPOSITORY`, `EXPORT_TO_REPOSITORY`, `RELEASE_DATA_FROM_FILESYSTEM`, `AUTO_RELEASE_DATA` |
| **Release** | Libera o conteúdo do disco (mantém metadados), recuperável do S3: libera espaço no SSD |

```bash
aws fsx create-data-repository-association --file-system-id fs-0lus123 \
  --file-system-path /treino --data-repository-path s3://meu-dataset/treino \
  --s3 "AutoImportPolicy={Events=[NEW,CHANGED,DELETED]},AutoExportPolicy={Events=[NEW,CHANGED,DELETED]}" \
  --batch-import-meta-data-on-create
# Exportar tudo de um diretório (antes de excluir o sistema de arquivos)
aws fsx create-data-repository-task --file-system-id fs-0lus123 --type EXPORT_TO_REPOSITORY \
  --paths /saida --report Enabled=true,Path=s3://meu-dataset/relatorios/,Format=REPORT_CSV_20191124,Scope=FAILED_FILES_ONLY
# Liberar do disco arquivos não acessados há 30 dias (mantidos no S3)
aws fsx create-data-repository-task --file-system-id fs-0lus123 --type RELEASE_DATA_FROM_FILESYSTEM --paths /treino \
  --release-configuration DurationSinceLastAccess={Unit=DAYS,Value=30} --report Enabled=false
```

### Boas práticas das DRAs

1. **Dividir por caminho**: entrada somente-importação (`/treino`), saída somente-exportação (`/saida`).
2. **Exportar antes de excluir** o sistema de arquivos (confirmar relatório sem falhas).
3. **Evitar dois escritores** (S3 e Lustre) no mesmo objeto: o último vence.
4. **Release automático** para manter o SSD com os dados quentes.
5. **Permissões**: a IAM do serviço precisa de `s3:GetObject/PutObject/ListBucket`; com SSE-KMS, permissão na chave.
6. Alterações no S3 podem levar segundos a minutos para aparecer; validar contagens.

## Striping (distribuição de arquivos)

O Lustre divide o conteúdo de cada arquivo em **stripes** distribuídos pelos **OSTs** (alvos de armazenamento). O **stripe count** define em quantos OSTs o arquivo é espalhado; o **stripe size** é o tamanho de cada pedaço.

```
 arquivo grande, stripe_count=4:   [bloco1][bloco2][bloco3][bloco4][bloco5]...
                                      OST0    OST1    OST2    OST3    OST0 ...   → leituras/escritas paralelas em 4 alvos
```

| Cenário | Stripe recomendado |
|---|---|
| **Muitos arquivos pequenos** (< alguns MB) | `stripe_count=1` (menos metadados e overhead) |
| **Arquivos grandes** (centenas de MB a TB), acessados por muitos clientes em paralelo | `stripe_count=-1` (todos os OSTs) ou 4-16 |
| **Arquivo único gravado por muitos processos** (checkpoint, MPI-IO) | Stripe alto para espalhar I/O |
| **Padrão (default)** | O FSx já define um *progressive file layout* (PFL) adaptativo: pequenos com 1 stripe, crescendo com mais stripes |

```bash
lfs getstripe /fsx/saida                         # ver o layout atual
lfs setstripe -c -1 -S 4M /fsx/checkpoints       # novos arquivos neste diretório: todos os OSTs, stripe de 4 MiB
lfs setstripe -c 1 /fsx/miniaturas               # arquivos pequenos: 1 stripe
lfs df -h /fsx                                    # uso por OST (detecta desbalanceamento)
lfs migrate -c 8 /fsx/saida/arquivao.dat         # reestriparar um arquivo existente
```

## Cliente e montagem

### Instalação (exemplos)

```bash
# Amazon Linux 2
sudo amazon-linux-extras install -y lustre
# Amazon Linux 2023 / RHEL / Ubuntu: pacotes/kmods do cliente Lustre compatíveis com o kernel (consulte a documentação)
sudo mkdir -p /fsx
sudo mount -t lustre -o noatime,flock fs-0lus123.fsx.sa-east-1.amazonaws.com@tcp:/abcdefgh /fsx
echo 'fs-0lus123.fsx.sa-east-1.amazonaws.com@tcp:/abcdefgh /fsx lustre defaults,noatime,flock,_netdev 0 0' | sudo tee -a /etc/fstab
```

| Opção | Efeito |
|---|---|
| `noatime` | Evita atualizar tempo de acesso (menos metadados) |
| `flock` | Habilita bloqueio de arquivos POSIX (necessário para algumas aplicações) |
| `_netdev` | Aguarda a rede |

### Afinação do cliente

| Aspecto | Orientação |
|---|---|
| **Kernel/versão do cliente** | Use as versões **suportadas**; versões novas trazem desempenho (PFL, EFA, compressão) |
| **Rede** | Instâncias com **EFA** e alta banda de rede (para Persistent_2 com *EFA enhanced*); jumbo frames (MTU 9001) na VPC |
| **Paralelismo** | Muitos processos/threads com I/O grande (≥ 1 MiB); evite I/O de 4 KiB sequencial de um thread |
| **Metadados** | Muitos `stat` pequenos limitam; use `lfs find`, evite `ls -l` em milhões de arquivos |
| **Parâmetros** | `lctl set_param osc.*.max_rpcs_in_flight`, `llite.*.max_read_ahead_mb` etc. (use valores recomendados pela AWS; teste) |
| **Segurança de rede** | SG com portas 988 e 1018-1023 (TCP) entre clientes e servidores |
| **Compressão** | LZ4 de dados (habilitada por padrão em tipos recentes): reduz armazenamento e I/O |
| **Metadados provisionados** | Em Persistent_2, configure **IOPS de metadados** para cargas com muitos arquivos |

## Integrações

### AWS Batch e ParallelCluster (HPC)

| Plataforma | Uso do Lustre |
|---|---|
| **AWS ParallelCluster** | Cria/atrela FSx for Lustre como `SharedStorage` (`FsxLustre`), montado em todos os nós, com DRA para o S3; o cluster e o FSx podem ser efêmeros |
| **AWS Batch** | Jobs montam o FSx via launch template (user data) ou imagem; filas EC2/Spot |
| **Slurm** | Diretório de trabalho compartilhado |

```yaml
# Trecho do ParallelCluster
SharedStorage:
  - MountDir: /fsx
    Name: scratch
    StorageType: FsxLustre
    FsxLustreSettings:
      StorageCapacity: 1200
      DeploymentType: SCRATCH_2
      ImportPath: s3://meu-dataset/treino
      ExportPath: s3://meu-dataset/saida
```

### SageMaker e EKS

| Plataforma | Uso |
|---|---|
| **SageMaker Training** | FSx for Lustre como **canal de entrada** (mais rápido que o S3 para epochs repetidas): instâncias na mesma VPC e AZ do FSx |
| **EKS** | **FSx for Lustre CSI Driver**; PV estático/dinâmico, `ReadWriteMany` |
| **EC2 GPU (p4/p5)** | Alimenta GPUs com datasets grandes |

### Outros padrões

- **Burst para HPC**: cluster on-premises + FSx na nuvem via DX/VPN; DRA sincroniza com o S3.
- **Processamento de mídia**: render farms com centenas de nós; resultados exportados ao S3.
- **Genômica e CFD**: pipelines Nextflow/Snakemake com `/fsx` compartilhado.

## Custo e ciclo de vida

| Componente | Observação |
|---|---|
| **Armazenamento** | Por GB-mês (SSD > HDD); scratch mais barato que persistent |
| **Throughput (persistent)** | Preço por MB/s por TiB provisionado (níveis) |
| **Metadados provisionados** | IOPS de metadados (Persistent_2) |
| **Backups** | Persistent (armazenamento incremental) |
| **Transferência** | Entre AZs; do/para o S3 na mesma região sem custo de transferência (requests do S3 cobradas) |
| **Compressão** | Reduz GB armazenados e cobrados |

Estratégias:

1. **Criar sob demanda e excluir ao fim do job** (scratch + DRA): paga-se só enquanto há processamento.
2. **Dimensionar pela necessidade de throughput**, não só pelo dataset.
3. **Release automático** de arquivos frios para reduzir o SSD necessário.
4. **Persistent apenas quando o sistema vive meses**; do contrário scratch.
5. **Mesma AZ** dos clientes (sem tráfego entre AZs).
6. **Spot/Batch** para os nós de computação.
7. **Automatizar** a criação/destruição (Step Functions, CloudFormation, ParallelCluster).

## Troubleshooting

| Sintoma | Causas | Ação |
|---|---|---|
| **Mount falha / trava** | SG sem 988 e 1018-1023; DNS; cliente Lustre incompatível | Portas, `nslookup`, versão do cliente, logs (`dmesg`, `lctl`) |
| **Arquivos do S3 não aparecem** | DRA sem importação de metadados, permissões, prefixo errado | Tarefa `IMPORT_METADATA`, IAM/KMS, políticas de eventos |
| **Primeira leitura lenta** | Lazy load do S3 | Pré-carregar (`lfs hsm_restore` / `lfs_migrate` ou tarefa de importação/cópia ou `find | xargs -P cat`) |
| **Throughput abaixo do esperado** | Pouco paralelismo, stripe=1 em arquivos grandes, rede da instância, capacidade pequena | `lfs setstripe`, mais processos, instâncias com EFA, mais TiB/nível |
| **Muitos arquivos pequenos lentos** | Metadados | Persistent_2 com IOPS de metadados maiores, empacotar arquivos, stripe 1 |
| **Disco cheio** | Dados não liberados, falta de release/exportação | Release, mais capacidade |
| **Dados perdidos em scratch** | Falha de hardware | Reimportar do S3; usar persistent para dados sem cópia |
| **Exportação com falhas** | Permissões S3/KMS, caracteres/nomes inválidos, tamanho | Relatório da tarefa, ajustar |
| **Desbalanceamento de OSTs** | Arquivos mal distribuídos | `lfs df`, `lfs migrate`, rebalancear |

Métricas CloudWatch (`AWS/FSx`): `DataReadBytes`, `DataWriteBytes`, `DataReadOperations`, `DataWriteOperations`, `MetadataOperations`, `FreeDataStorageCapacity`, `FreeDataStorageCapacity` por OST; use alarmes de capacidade livre e de metadados.

## Exemplo prático

Treinamento distribuído de um modelo de visão com 8 TB de imagens no S3 e 64 GPUs:

1. **FSx for Lustre Persistent_2 SSD**, 12 TiB (~1.000 MB/s por TiB), na mesma AZ do cluster de treino; DRA `/treino` ↔ `s3://imagens/treino` (importação automática, exportação desligada) e `/checkpoints` ↔ `s3://imagens/checkpoints` (exportação automática).
2. **Cliente:** instâncias `p4d` com EFA; montagem `noatime,flock`; `lfs setstripe -c -1 -S 4M /fsx/checkpoints` (checkpoints grandes) e `-c 1` para imagens pequenas.
3. **Pré-carga:** job de aquecimento lê o dataset uma vez (`find /fsx/treino -type f | xargs -P 64 cat > /dev/null`) antes do treino.
4. **Treinamento:** SageMaker/EKS com `ReadWriteMany`; a primeira época já usa ~80% da GPU (contra 45% lendo do S3 sob demanda).
5. **Release automático** de arquivos não acessados há 7 dias para manter a SSD enxuta.
6. **Ciclo de vida:** após o experimento, exportar `/checkpoints`, validar o relatório e **excluir** o sistema de arquivos; custo proporcional ao tempo de uso.
7. **Monitoramento:** `DataReadBytes`, `MetadataOperations`, utilização da GPU; alarme de `FreeDataStorageCapacity` < 15%.

## Erros comuns e armadilhas

- **Excluir o sistema de arquivos sem exportar** (ou sem verificar o relatório).
- **Usar scratch para dados que não existem no S3.**
- **Portas 988/1018-1023 bloqueadas** no SG.
- **Dois escritores** (S3 e Lustre) no mesmo caminho.
- **Stripe=1 para arquivos enormes** (um OST vira gargalo) ou **stripe=-1 para milhões de arquivos pequenos** (overhead).
- **Esperar desempenho com um único thread.**
- **Sistema de arquivos em AZ diferente dos clientes** (tráfego e latência).
- **Deixar persistent ligado depois do projeto.**
- **Ignorar permissões do S3/KMS** da DRA.
- **Cliente Lustre desatualizado** para o kernel.

## 🧩 Quiz de Fixação

1. O que é uma Data Repository Association e quais políticas ela define?
2. Como o striping influencia o desempenho e quando usar `stripe_count=1` ou `-1`?
3. Por que exportar para o S3 antes de excluir um sistema de arquivos scratch?
4. Como reduzir o custo de um FSx for Lustre de uso temporário?

**Respostas:**
1) É a ligação entre um diretório do sistema de arquivos e um prefixo do S3, com políticas de importação automática (NEW, CHANGED, DELETED do S3) e de exportação automática (do Lustre para o S3), além de tarefas sob demanda e release de dados.
2) O striping distribui o conteúdo do arquivo entre os OSTs, paralelizando I/O; `stripe_count=1` para muitos arquivos pequenos (menos overhead) e `-1` (ou alto) para arquivos grandes acessados em paralelo ou checkpoints.
3) Porque o scratch não replica dados e a exclusão apaga tudo; resultados ainda não exportados seriam perdidos.
4) Criando sob demanda e excluindo ao fim do job (scratch + DRA), dimensionando pelo throughput necessário, usando release automático, mantendo na mesma AZ dos clientes e usando Spot/Batch para a computação.
