## Dimensionamento

Cada sistema de arquivos tem três dimensões independentes:

| Dimensão | Opções | Como decidir |
|---|---|---|
| **Capacidade de armazenamento** | De dezenas de GiB a dezenas de TiB por sistema (confirme o máximo); **só aumenta** | Dados atuais + crescimento de 12-18 meses + margem de 20-30% (deduplicação reduz) |
| **Tipo de armazenamento** | **SSD** (latência baixa, IOPS maiores) ou **HDD** (custo menor, throughput menor) | HDD para arquivos de usuários/arquivamento; SSD para cargas intensivas (perfis, bancos de dados em SMB, aplicações) |
| **Throughput capacity** | De dezenas a milhares de MB/s | Pelo pico de uso simultâneo; define também CPU, memória e **cache em memória** do servidor; pode ser **alterado** depois |
| **IOPS** (SSD) | Proporcional à capacidade (relação por GiB) com opção de **IOPS provisionados** | Cargas aleatórias intensas |

Regra prática de partida: contar **usuários simultâneos × demanda por usuário** (uso típico de escritório: poucos MB/s por centenas de usuários), validar com o **perfil real** de um servidor de arquivos atual (contadores do Windows Performance Monitor: *Bytes/sec*, *IOPS*, *Queue Length*) e ajustar com as métricas do FSx.

```
Servidor atual:  pico de leitura 120 MB/s, escrita 40 MB/s, 4.500 IOPS, 6 TB usados (crescendo 25% ao ano)
Dimensionamento: capacidade 10 TiB SSD (6 TB × 1,25^2 ≈ 9,4 + margem), throughput 256 MB/s (folga 1,5x sobre o pico agregado),
                 IOPS: padrão SSD de 10 TiB ≈ 30.000 (3 IOPS/GiB) > 4.500 → suficiente
```

## Implantação

### Pré-requisitos

| Item | Detalhe |
|---|---|
| **Active Directory** | AWS Managed Microsoft AD, ou AD próprio (on-premises/EC2) com conta de serviço **delegada** para criar objetos de computador |
| **Rede** | Subnets em 1 ou 2 AZs (Single-AZ ou Multi-AZ), SG liberando portas SMB e de AD |
| **DNS** | Os clientes e o FSx resolvem o domínio (DNS apontando para os controladores de domínio) |
| **KMS** | Chave para criptografia em repouso |
| **Backup** | Retenção automática (0-90 dias) e janela |
| **Auditoria** | Destino de logs (CloudWatch Logs ou Firehose) se for usar auditoria de acesso a arquivos |

### Portas principais (Security Group)

| Protocolo | Porta | Uso |
|---|---|---|
| SMB | TCP 445 | Acesso aos arquivos |
| PowerShell remoto (WinRM) | TCP 5985 | Administração remota |
| DNS | TCP/UDP 53 | Resolução |
| Kerberos | TCP/UDP 88 | Autenticação |
| LDAP / LDAPS | TCP 389 / 636 | Diretório |
| RPC | TCP 135 e portas dinâmicas | Integração com AD |
| NTP | UDP 123 | Hora |

```bash
aws fsx create-file-system --file-system-type WINDOWS --storage-type SSD --storage-capacity 10240 \
  --subnet-ids subnet-0aaa111 subnet-0bbb222 --security-group-ids sg-0fsx123 \
  --windows-configuration "ActiveDirectoryId=d-1234567890,DeploymentType=MULTI_AZ_1,PreferredSubnetId=subnet-0aaa111,ThroughputCapacity=256,AutomaticBackupRetentionDays=30,DailyAutomaticBackupStartTime=03:00,WeeklyMaintenanceStartTime=7:04:00,Aliases=arquivos.empresa.local" \
  --kms-key-id alias/fsx --tags Key=Name,Value=fs-corporativo
```

### Alias DNS e SPN (nome amigável)

Para continuar usando `\\arquivos\setor` (nome do servidor antigo) com Kerberos, é preciso:

1. Registrar o **alias** (`Aliases=` ao criar, ou `associate-file-system-aliases`).
2. Criar o **CNAME** no DNS do domínio apontando para o DNS do FSx (`amznfsxxxx.empresa.local`).
3. Configurar o **SPN** do alias na conta de computador do FSx com o script `Set-FsxSpn` (ou equivalente).
4. Aplicar à **resolução** dos clientes (limpar caches) e testar `\\arquivos\setor`.

Isso permite migrar sem reconfigurar scripts, GPOs e mapeamentos de unidade.

## Migração de servidores de arquivos

### Escolha da ferramenta

| Ferramenta | Quando | Vantagens | Cuidados |
|---|---|---|---|
| **AWS DataSync** | Origem SMB/NFS on-premises ou outro FSx; grandes volumes | Gerenciado, incremental, verificação, preserva **ACLs NTFS**, agendamento, paralelismo | Agente na origem; custo por GB |
| **Robocopy** | Windows → FSx por SMB; controle fino | Familiar, `/MIR` incremental, `/COPYALL` preserva ACL/ownership/auditoria | `/MIR` **apaga** no destino o que não existe na origem; execute com conta de backup (`/B`) |
| **FSx File Gateway / Storage Gateway** | Acesso local com cache | Migração gradual | Complexidade adicional |
| **AWS Backup / restauração de backup do FSx** | FSx → FSx | Cópia exata | Cria novo sistema de arquivos |
| **Snowball / Transfer Family** | Volumes enormes offline / SFTP | — | Etapas extras |

### Robocopy (exemplo)

```cmd
:: Cópia inicial (preservando tudo), multithread, com log. Execute como conta com privilégios de backup.
robocopy \\SERVIDOR_ANTIGO\dados \\arquivos.empresa.local\dados /MIR /COPYALL /DCOPY:DAT /B /R:3 /W:5 /MT:32 /XD "System Volume Information" "$RECYCLE.BIN" /LOG+:C:\logs\migracao.log /TEE /NP
:: Sincronizações incrementais repetidas até a janela de corte; na janela, última cópia com os usuários desconectados
```

### Estratégia de corte

```
 1. Cópia inicial (semanas antes, em horário de baixo uso)
 2. Sincronizações incrementais diárias (diff pequeno)
 3. Janela de corte: bloquear escrita na origem (somente leitura), última sincronização, validar contagem e ACLs
 4. Alterar DNS/alias e DFS Namespace para apontar ao FSx
 5. Smoke test com usuários-piloto; liberar
 6. Manter a origem somente leitura por alguns dias (rollback), depois desativar
```

Validação: comparação de **contagem de arquivos e tamanho** (`robocopy /L`, PowerShell), amostras de **ACL** (`icacls`), **permissões de compartilhamento**, DFS-N, scripts de logon, impressoras/aplicações que usam o caminho.

## Administração por PowerShell remoto

O FSx for Windows é **gerenciado**, mas oferece um **endpoint de PowerShell remoto** para tarefas de administração que o console não cobre:

```powershell
# De uma instância Windows no domínio, com credenciais de administrador do FSx:
$Endpoint = "amznfsxxxx.empresa.local"           # "Windows Remote PowerShell Endpoint" do sistema de arquivos
Invoke-Command -ComputerName $Endpoint -ConfigurationName FSxRemoteAdmin -ScriptBlock { Get-FSxSmbShare }

# Criar um compartilhamento
Invoke-Command -ComputerName $Endpoint -ConfigurationName FSxRemoteAdmin -ScriptBlock {
  New-FSxSmbShare -Name "financeiro" -Path "D:\share\financeiro" -Description "Financeiro" -FolderEnumerationMode AccessBased
}
# Habilitar criptografia SMB obrigatória no compartilhamento
Invoke-Command -ComputerName $Endpoint -ConfigurationName FSxRemoteAdmin -ScriptBlock { Set-FSxSmbShare -Name "financeiro" -EncryptData $true -Force }
```

| Tarefa | Cmdlets típicos |
|---|---|
| **Compartilhamentos** | `New-FSxSmbShare`, `Get-FSxSmbShare`, `Set-FSxSmbShare`, `Grant-FSxSmbShareAccess` |
| **Cotas de usuário** | `Enable-FSxUserQuotas`, `Set-FSxUserQuotas`, `Get-FSxUserQuotas` |
| **Shadow copies** | `Set-FsxShadowStorage`, `New-FsxShadowCopy`, `Set-FsxShadowCopySchedule` |
| **Deduplicação** | `Enable-FsxDedup`, `Set-FsxDedupConfiguration`, `Get-FsxDedupStatus` |
| **Sessões e arquivos abertos** | `Get-FSxSmbSession`, `Close-FSxSmbSession`, `Get-FSxSmbOpenFile` |
| **Armazenamento** | `Get-FsxStorage`, `Optimize-FsxVolume` |

(Os nomes dos cmdlets seguem a convenção `*-FSx*`; consulte a referência atual.)

### Cotas, shadow copies e deduplicação

| Recurso | Configuração recomendada |
|---|---|
| **Cotas de usuário** | Aviso (soft) e limite (hard) por usuário/grupo; evita que um usuário consuma tudo |
| **Shadow copies (versões anteriores)** | Reservar até ~10-15% do armazenamento; 2 agendamentos por dia (ex.: 07h e 12h); recuperação self-service pelo botão direito |
| **Deduplicação** | Ativar em pastas de documentos e perfis; economia típica de 30-50% em arquivos de usuário; monitorar CPU/ganho |
| **Auditoria de acesso** | Registrar leituras/gravações/exclusões em CloudWatch Logs ou Firehose (volume alto: filtre) |

## Desempenho

| Aspecto | Orientação |
|---|---|
| **Throughput** | Ajuste a *throughput capacity* conforme `DataReadBytes`/`DataWriteBytes` e `NetworkThroughputUtilization` |
| **Disco** | `DiskThroughputUtilization`, `DiskIopsUtilization`; HDD limita IOPS (aumente a capacidade ou use SSD) |
| **Cache em memória** | O servidor de arquivos usa memória para cache de leitura; mais throughput capacity = mais memória |
| **SMB Multichannel** | Aumenta throughput por cliente com várias conexões (versões e instâncias suportadas) |
| **Clientes** | Windows recente (SMB 3.x); em Linux, `mount -t cifs` com `vers=3.0`/`3.1.1`, `seal` (criptografia) |
| **Latência de rede** | Clientes na mesma região/AZ (prefira a AZ do servidor ativo); WAN com Direct Connect |
| **Operações de metadados** | Listagem de milhões de arquivos, antivírus agressivo no cliente |
| **Backups e deduplicação** | Rodam em segundo plano; considere janelas |

```
Mudar throughput: aws fsx update-file-system --file-system-id fs-xxxx --windows-configuration ThroughputCapacity=512
Aumentar capacidade: aws fsx update-file-system --file-system-id fs-xxxx --storage-capacity 14336     # só aumenta; pode haver espera entre alterações
```

## Troubleshooting

| Sintoma | Causas | Ação |
|---|---|---|
| **Não monta `\\fs\share` / "network path not found"** | SG sem 445, DNS não resolve, firewall do cliente, alias sem CNAME/SPN | `Test-NetConnection fs -Port 445`, `nslookup`, conferir CNAME e SPN |
| **"Access denied"** | Permissão de compartilhamento **e** NTFS (as duas precisam permitir), usuário fora do grupo, token do Kerberos antigo | `icacls`, `Get-FSxSmbShare`, `klist purge`, reentrar no grupo |
| **Falha de ingresso no AD / FSx indisponível** | Conta de serviço sem delegação, DNS, sincronização de hora | Verificar delegação, DNS do AD, NTP |
| **Lentidão geral** | Throughput capacity baixo, HDD, cliente em outra região | Métricas, aumentar throughput, SSD, proximidade |
| **Lentidão só em pastas gigantes** | Metadados/listagem | Reorganizar a estrutura, enumeração baseada em acesso, evitar indexação no cliente |
| **Disco cheio** | Shadow copies, dedup desligada, lixeira | `Get-FsxStorage`, ajustar sombras, ativar dedup, aumentar capacidade |
| **Failover Multi-AZ** | Falha/manutenção | Esperado (1-2 min); clientes reconectam; sessões abertas podem cair |
| **Backup falha** | Janela sobreposta, retenção | Verificar eventos e métricas |
| **Perda de ACLs na migração** | Ferramenta sem `/COPYALL`/`/B` ou DataSync sem preservar ACL | Reexecutar com opções corretas, comparar com `icacls` |

## Exemplo prático

Migração de dois servidores de arquivos (9 TB) para um FSx Multi-AZ:

1. **Dimensionamento:** SSD 12 TiB, throughput 256 MB/s, deduplicação e cotas (soft 20 GB / hard 25 GB por usuário nas pastas pessoais); alias `arquivos.empresa.local`.
2. **Pré-requisitos:** Managed AD confiável com o AD local; SG com 445/5985/AD; backup de 30 dias, cópia para outra região.
3. **Migração:** Robocopy `/MIR /COPYALL /B /MT:32` do servidor A e DataSync para o servidor B; sincronizações noturnas por 3 semanas.
4. **Corte de fim de semana:** origem somente leitura, última sincronização, validação de contagem (`robocopy /L`) e de ACL (amostra de 500 pastas com `icacls`), CNAME/SPN do alias, DFS-N atualizado.
5. **Pós-corte:** shadow copies 07h/12h com 10% de reserva; dedup ativada em `\\...\documentos`; alarmes de `FreeStorageCapacity` < 15% e `NetworkThroughputUtilization` > 80%.
6. **Resultado:** usuários mantêm os mesmos caminhos; recuperação de versões anteriores sem chamado; custo de armazenamento reduzido em ~35% com a deduplicação.

## Erros comuns e armadilhas

- **Robocopy `/MIR` na direção errada** (apaga a origem).
- **Migrar sem `/COPYALL`/`/B`** ou sem preservar ACLs no DataSync.
- **Alias sem CNAME/SPN:** autenticação cai para NTLM ou falha.
- **Subdimensionar throughput/IOPS** e culpar o "serviço lento".
- **HDD** para cargas de metadados/IOPS aleatório.
- **Shadow copies com reserva grande demais** (disco cheio) ou desligadas.
- **SG sem 5985** (sem PowerShell remoto).
- **Esquecer de corrigir permissões do compartilhamento** e só do NTFS.
- **Single-AZ em produção crítica.**
- **Sem teste de restauração** e sem backup de configuração (compartilhamentos, cotas).
- **Não monitorar** capacidade livre e throughput.

## 🧩 Quiz de Fixação

1. Quais as três dimensões de dimensionamento do FSx for Windows e quais podem ser alteradas depois?
2. Que passos permitem usar o nome do servidor antigo (alias) com Kerberos?
3. Qual o risco do `robocopy /MIR` e como minimizá-lo?
4. Como administrar cotas e shadow copies de um FSx gerenciado?

**Respostas:**
1) Capacidade de armazenamento (só aumenta), tipo de armazenamento (SSD/HDD, definido na criação) e throughput capacity (pode ser alterada), além de IOPS no SSD; o tamanho do cache e da CPU acompanham o throughput.
2) Registrar o alias no sistema de arquivos, criar um CNAME no DNS do domínio apontando para o nome do FSx e configurar o SPN do alias na conta de computador do FSx, depois testar `\\alias\share`.
3) O `/MIR` espelha e apaga no destino o que não existe na origem; minimiza-se conferindo a direção origem/destino, testando com `/L` (simulação), usando logs e backup antes de executar.
4) Pelo endpoint de PowerShell remoto (`Invoke-Command -ConfigurationName FSxRemoteAdmin`) com cmdlets `*-FSx*` para cotas, shadow copies, deduplicação e compartilhamentos, a partir de uma instância Windows no domínio.
