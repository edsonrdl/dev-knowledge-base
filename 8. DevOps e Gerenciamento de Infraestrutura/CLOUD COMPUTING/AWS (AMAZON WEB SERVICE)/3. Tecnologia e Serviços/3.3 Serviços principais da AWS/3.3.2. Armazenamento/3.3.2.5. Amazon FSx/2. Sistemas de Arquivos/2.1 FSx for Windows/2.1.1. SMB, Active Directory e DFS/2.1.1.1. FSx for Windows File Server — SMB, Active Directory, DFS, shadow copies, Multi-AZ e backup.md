### FSx for Windows File Server — SMB, Active Directory, DFS, shadow copies, Multi-AZ e backup

> [!warning] Aviso
> Limites de capacidade/throughput, tipos de implantação, preços e recursos (deduplicação, cotas, auditoria) mudam. Confirme na documentação. Os comandos **não foram executados**.

O **FSx for Windows File Server** é um servidor de arquivos **Windows Server nativo e gerenciado**, com protocolo **SMB**, permissões **NTFS** e integração com o **Active Directory**. É a opção para migrar (*lift-and-shift*) compartilhamentos de arquivos Windows para a AWS sem reescrever aplicações.

**Analogia:** é o **servidor de arquivos do departamento de TI**, mas alugado: você mantém as mesmas pastas, permissões do AD e unidades mapeadas (`\\fs\setor`), e a AWS cuida do hardware, patches e backup.

## Características

| Característica | Detalhe |
|---|---|
| **Protocolo** | SMB 2.0 a 3.1.1 (inclusive criptografia SMB em trânsito) |
| **Sistema de arquivos** | NTFS, ACLs, cotas por usuário |
| **Autenticação** | **Microsoft Active Directory**: AWS Managed Microsoft AD ou AD próprio (on-premises/EC2) |
| **Armazenamento** | SSD ou HDD; capacidade de GiB a dezenas de TiB por sistema (confirme limites) |
| **Throughput** | Configurável (MB/s) |
| **Acesso** | Windows, Linux (cliente CIFS/SMB), macOS; EC2, WorkSpaces, AppStream, on-premises |
| **Recursos Windows** | **DFS Namespaces** (nome único para vários servidores), **shadow copies** (versões anteriores), **deduplicação de dados**, **cotas de usuário**, **auditoria de acesso a arquivos** |

## Alta disponibilidade: Single-AZ × Multi-AZ

```
 Multi-AZ:
   AZ-a: servidor de arquivos ATIVO ──replicação síncrona──► AZ-b: STANDBY
        ▲ clientes usam o DNS único; em falha, o failover automático leva ~minutos
   Single-AZ: um servidor em uma AZ (backups protegem; falha de AZ = indisponibilidade)
```

| Tipo | Disponibilidade | Uso |
|---|---|---|
| **Single-AZ** | Falhas de componente são tratadas na AZ; sem proteção contra perda da AZ | Dev/test, cargas tolerantes |
| **Multi-AZ** | Standby em outra AZ, failover automático, replicação síncrona | Produção |

O endereço (nome DNS) do sistema de arquivos permanece o mesmo após o failover.

## Active Directory

O FSx precisa estar **ingressado em um domínio** para autenticação e ACLs NTFS:

| Opção | Descrição |
|---|---|
| **AWS Managed Microsoft AD** | AD gerenciado pela AWS; mais simples |
| **AD self-managed** | Seu AD (on-premises ou em EC2); exige conectividade de rede (VPN/Direct Connect), conta de serviço com delegação para ingressar computadores, DNS resolvendo o domínio |

Requisitos: rede entre FSx e controladores de domínio (portas de AD: DNS 53, Kerberos 88, LDAP 389/636, SMB 445, RPC etc.), DNS apontando para o AD e usuário/delegação para criar objetos de computador.

---

## DFS (Distributed File System)

- **DFS Namespaces** agrupam vários compartilhamentos em um **caminho único** (`\\empresa.local\dados`).
- **DFS Replication** (replicação entre servidores) não é um recurso gerenciado direto: use **Multi-AZ** para HA, ou Namespaces com vários sistemas de arquivos para escala horizontal.
- FSx pode ser alvo de namespaces DFS existentes, facilitando a migração gradual.

## Shadow copies, cotas e deduplicação

| Recurso | O que faz | Observação |
|---|---|---|
| **Shadow copies (VSS)** | Versões anteriores de arquivos; o usuário restaura pelo botão direito *Versões anteriores* | Agende e defina o espaço máximo; recupera exclusões acidentais |
| **Cotas de usuário** | Limite de espaço por usuário/grupo | Via PowerShell remoto |
| **Deduplicação** | Reduz espaço de arquivos duplicados | Economia dependente do tipo de dado |
| **Auditoria** | Registra acessos a arquivos | Envia para CloudWatch Logs/Firehose |
| **Criptografia SMB** | Dados em trânsito | Pode ser exigida |

Gerenciamento: por **PowerShell remoto** (`Invoke-Command -ConfigurationName FSxRemoteAdmin`) ou **Gerenciador de Pastas Compartilhadas/Console MMC** a partir de uma instância Windows no domínio.

## Backup e recuperação

| Mecanismo | Característica |
|---|---|
| **Backups automáticos diários** | Retenção configurável (0 a 90 dias), incrementais |
| **Backups manuais** | Sem expiração automática |
| **AWS Backup** | Planos centralizados, cópia entre regiões/contas |
| **Shadow copies** | Recuperação rápida de arquivos individuais |
| **Restauração** | Cria um **novo** sistema de arquivos a partir do backup |

```bash
# Criar um sistema de arquivos FSx for Windows Multi-AZ (resumo; verifique todos os parâmetros)
aws fsx create-file-system --file-system-type WINDOWS \
  --storage-capacity 1024 --storage-type SSD \
  --subnet-ids subnet-0aaa111 subnet-0bbb222 \
  --security-group-ids sg-0fsx123 \
  --windows-configuration \
    "ActiveDirectoryId=d-1234567890,DeploymentType=MULTI_AZ_1,PreferredSubnetId=subnet-0aaa111,ThroughputCapacity=64,AutomaticBackupRetentionDays=14,DailyAutomaticBackupStartTime=03:00"
# ThroughputCapacity em MB/s; AD já criado (AWS Managed Microsoft AD)

# Mapear a unidade em um cliente Windows
# net use Z: \\fs-0abc123.empresa.local\share /persistent:yes

# Aumentar a capacidade (online)
aws fsx update-file-system --file-system-id fs-0abc123 --storage-capacity 2048
```

## Segurança

- **Security Group** do FSx: SMB 445 (e portas de AD) apenas de clientes autorizados.
- **Criptografia em repouso** com KMS (padrão) e em trânsito (SMB encryption).
- **ACLs NTFS** e grupos do AD como no ambiente tradicional.
- **Auditoria** e CloudTrail para chamadas de API.
- Para acesso on-premises: VPN/Direct Connect e DNS do domínio.

## Exemplo prático

Migração de um servidor de arquivos de 5 TB para a AWS:

1. Criar **AWS Managed Microsoft AD** com relação de confiança com o AD local (ou usar AD self-managed).
2. Criar FSx for Windows **Multi-AZ**, SSD, 6 TiB, throughput 128 MB/s, backups de 14 dias.
3. Migrar os dados com **AWS DataSync** (preserva ACLs NTFS) ou Robocopy.
4. Atualizar o **DFS Namespace** para apontar ao FSx; usuários seguem usando `\\empresa\dados`.
5. Habilitar shadow copies e cotas; auditoria em CloudWatch Logs.
6. Testar failover Multi-AZ e restauração de backup.

## Dimensionamento e desempenho

```
 Throughput capacity (MB/s) ──define──► banda de rede + disco + cache em memória do servidor de arquivos
 Capacidade de armazenamento (GiB) ──define──► IOPS de disco (SSD: 3 IOPS/GiB; HDD: mais baixo)
 Gargalo comum: capacidade pequena + throughput alto → disco limita antes do servidor
```

| Decisão | SSD | HDD |
|---|---|---|
| Perfil | Latência baixa, bancos, home dirs ativos | Compartilhamentos de arquivo gerais, mais barato por GB |
| Custo | Maior | Menor |
| Quando | Workloads sensíveis (SQL Server em SMB, VDI) | Arquivos de usuário e arquivamento ativo |

> [!warning] Mínimos de capacidade, faixas de throughput e preços mudam; confirme na documentação atual.

## Integração de rede e identidade

| Tema | Detalhe |
|---|---|
| Acesso | SMB (porta 445) a partir da VPC, peering, Transit Gateway, VPN e Direct Connect |
| Nome DNS | Usar o DNS do sistema (`fs-xxx.dominio.local`) ou CNAME/DFS-N para nome amigável |
| Security Group | Liberar 445, 135, 5985 (remote PowerShell), 53/88/389 conforme o AD |
| Conta de serviço | Delegação mínima para o FSx ingressar no domínio (não usar Domain Admin) |
| Failover Multi-AZ | O DNS do arquivo aponta para o servidor ativo; standby assume em ~minutos ao falhar |

## Operação com PowerShell remoto

```powershell
# Conectar ao endpoint de administração do FSx (comentado, não executado)
Enter-PSSession -ComputerName amznfsxxxxx.dominio.local -ConfigurationName FsxRemoteAdmin
# Cotas e compartilhamentos
New-FSxSmbShare -Name "Financeiro" -Path "D:\share\financeiro" -Description "Setor financeiro"
Set-FsxQuota ...   # cotas por usuário (cmdlets FSx / FSRM)
Get-FSxVssShadowCopy
```

## Migração e boas práticas

1. Use **DataSync** ou `robocopy /COPYALL /MIR /R:1 /W:1` para preservar ACLs e timestamps.
2. Planeje o corte com **DFS Namespace** para manter os caminhos UNC dos usuários.
3. Ative shadow copies e backups automáticos antes de liberar aos usuários.
4. Habilite **auditoria de acesso a arquivos** para o CloudWatch Logs ou Kinesis Firehose.
5. Monitore `FreeStorageCapacity`, `DataReadBytes`, `DataWriteBytes` e `ClientConnections`.

## Troubleshooting

| Sintoma | Causa provável | Ação |
|---|---|---|
| Falha ao criar (ingresso no domínio) | DNS da VPC não resolve o AD, SG ou conta sem permissão | Ajustar DHCP options e delegação |
| Acesso negado a pasta | ACL NTFS ou share permission | Revisar ACL (`icacls`) e permissões do share |
| Lento em arquivos pequenos | Throughput baixo ou disco HDD | Aumentar throughput capacity / mudar para SSD |
| Disco cheio | Capacidade não aumentada | Aumentar capacidade online (somente aumenta) |
| Failover demorado | Cliente cacheando DNS | Reduzir TTL e reconectar o mapeamento |

## Erros comuns e armadilhas

- **Escolher Single-AZ para produção crítica.**
- **DNS/rede inadequados para o AD:** o ingresso no domínio falha.
- **Conta de serviço sem delegação** para criar objetos de computador.
- **Capacidade/throughput subdimensionados:** latência alta nos picos; ajustar depois exige operação.
- **Esquecer shadow copies:** usuários não têm "versões anteriores".
- **Sem plano para reduzir capacidade:** só aumenta online; reduzir exige criar novo e migrar.
- **Usar HDD para carga de metadados intensa.**
- **Não testar a restauração** (cria novo sistema de arquivos).
- **Acesso SMB aberto na internet:** nunca exponha a porta 445.

## 🧩 Quiz de Fixação

1. Que dois requisitos de rede/identidade o FSx for Windows precisa para autenticar usuários?
2. Qual a diferença de proteção entre Single-AZ e Multi-AZ?
3. Como o usuário recupera uma versão anterior de um arquivo apagado por engano?

**Respostas:**
1) Estar ingressado em um domínio do Active Directory (AWS Managed Microsoft AD ou AD próprio) e ter conectividade/DNS com os controladores de domínio nas portas necessárias.
2) Single-AZ protege contra falhas de componente dentro da AZ, mas não contra a perda da AZ; Multi-AZ mantém um standby síncrono em outra AZ com failover automático.
3) Pelas **shadow copies**: botão direito na pasta/arquivo → *Versões anteriores*, se estiverem habilitadas; ou restaurando de um backup.

### Questões de aprofundamento

4. Por que SSD de 300 GiB com throughput alto pode ainda ser lento?
5. Qual o papel do DFS Namespace numa migração?
6. Como proteger a conta de serviço do ingresso no domínio?

**Respostas:**
4) O IOPS de disco é proporcional à capacidade; com pouca capacidade o disco limita antes do servidor de arquivos.
5) Preserva os caminhos UNC dos usuários, permitindo trocar o servidor de origem por FSx sem reconfigurar clientes.
6) Delegar apenas as permissões necessárias a uma OU específica, nunca usar Domain Admin.
