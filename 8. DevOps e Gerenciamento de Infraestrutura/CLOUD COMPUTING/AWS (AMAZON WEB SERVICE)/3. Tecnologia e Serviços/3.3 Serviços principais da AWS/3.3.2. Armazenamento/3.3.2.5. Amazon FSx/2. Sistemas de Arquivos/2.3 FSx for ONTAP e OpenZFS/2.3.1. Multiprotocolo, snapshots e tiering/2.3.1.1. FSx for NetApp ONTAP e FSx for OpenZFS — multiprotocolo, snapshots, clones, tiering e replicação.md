### FSx for NetApp ONTAP e FSx for OpenZFS — multiprotocolo, snapshots, clones, tiering e replicação

> [!warning] Aviso
> Os recursos, limites e preços do FSx for ONTAP e do FSx for OpenZFS evoluem rapidamente (tiering, SnapMirror, tipos de implantação). Confirme na documentação. Os comandos **não foram executados**.

Os dois sabores restantes do FSx levam à AWS sistemas de arquivos **enterprise** já conhecidos: o **NetApp ONTAP** (com o ecossistema de dados da NetApp) e o **OpenZFS** (com snapshots e clones instantâneos). Ambos são indicados para **migrar cargas existentes** sem refatorar e para quem precisa de recursos além do NFS/SMB simples.

**Analogia:** o ONTAP é o **servidor corporativo multifuncional** (fala NFS, SMB e iSCSI, tem cofre de backup e espelhamento embutidos). O OpenZFS é o **arquivo com "máquina do tempo"**: tira fotos instantâneas e cria cópias de trabalho (clones) sem gastar espaço.

## FSx for NetApp ONTAP

Sistema de arquivos **NetApp ONTAP** totalmente gerenciado, com acesso **multiprotocolo** e as funções de gestão de dados da NetApp.

### Conceitos

| Conceito | Descrição |
|---|---|
| **File system** | O cluster ONTAP gerenciado pela AWS (par de nós HA em Multi-AZ ou Single-AZ) |
| **SVM** (Storage Virtual Machine) | Servidor virtual isolado com seus protocolos, endpoint e identidade (AD); permite multi-tenancy |
| **Volume** | Unidade de dados dentro da SVM, com tamanho, política de tiering, snapshots; **FlexVol** e **FlexGroup** |
| **Tier de capacidade** | Armazenamento elástico e barato (baseado em objetos) para dados frios |
| **Tier primário (SSD)** | Dados quentes |
| **Endpoints** | NFS, SMB, iSCSI (blocos) e acesso de gerenciamento (CLI/REST do ONTAP) |

```
 Clientes ──NFS/SMB/iSCSI──► SVM ──► Volumes ──► Tier SSD (quente)
                                            └──► Tier de capacidade (frio, automático)
```

### Recursos principais

| Recurso | O que oferece |
|---|---|
| **Multiprotocolo** | Mesmos dados via NFS e SMB (nomes e permissões mapeados) e iSCSI |
| **Tiering automático** | Dados sem acesso migram para o tier de capacidade (políticas *auto*, *snapshot-only*, *all*, *none*) |
| **Snapshots** | Instantâneos eficientes e *Snapshot copies* acessíveis aos usuários |
| **FlexClone** | Clones de volume instantâneos e econômicos (dev/test) |
| **Deduplicação, compressão, compactação** | Eficiência de armazenamento |
| **SnapMirror** | Replicação entre sistemas ONTAP (inclusive on-premises ↔ AWS) para DR e migração |
| **Multi-AZ** | Failover automático entre AZs |
| **Ferramentas NetApp** | BlueXP, ONTAP CLI/REST, SnapCenter, integrações já conhecidas |
| **Quotas, QoS, SnapLock** | Governança, desempenho por volume, retenção WORM |

### Casos de uso

- Migrar **NetApp on-premises** para a AWS mantendo ferramentas e processos (SnapMirror).
- Ambientes **Windows + Linux** compartilhando os mesmos dados.
- **Bancos de dados** (Oracle, SQL Server) via iSCSI ou NFS/SMB.
- **Dev/test** com FlexClone.
- Armazenamento **híbrido** com cache e replicação.

## FSx for OpenZFS

Sistema de arquivos **OpenZFS** gerenciado, com **latência muito baixa** e as funções do ZFS.

### Conceitos

| Conceito | Descrição |
|---|---|
| **File system** | Servidor(es) OpenZFS gerenciado(s), com SSD, em Single-AZ ou Multi-AZ |
| **Volume** | Subárvore (dataset ZFS) com propriedades próprias (quota, compressão, snapshots) |
| **Protocolos** | NFS v3, v4.0/4.1/4.2 e SMB (conforme versão) |
| **Snapshots** | Instantâneos praticamente imediatos e baratos; usuários recuperam via diretório `.zfs/snapshot` |
| **Clones** | Volumes graváveis derivados de um snapshot, sem copiar dados |
| **Compressão** | LZ4/ZSTD transparente, economizando espaço |
| **Replicação** | Cópia de volumes/snapshots (backup e DR) |
| **Throughput e IOPS** | Configuráveis, com cache em memória (ARC) |

### Casos de uso

- Migrar **servidores Linux/ZFS** on-premises.
- **Latência baixa** (sub-ms) para NFS em cargas como compilações, análises, aplicações legadas.
- **Clones instantâneos** de datasets para desenvolvimento, CI e data science.
- **Home directories** e repositórios com alto reuso de dados.

## ONTAP × OpenZFS × Windows × EFS

| Critério | **ONTAP** | **OpenZFS** | **Windows** | **EFS** |
|---|---|---|---|---|
| Protocolos | NFS, SMB, iSCSI | NFS, SMB | SMB | NFS |
| Multi-AZ | Sim | Sim (conforme geração) | Sim | Regional |
| Tiering para capacidade barata | **Sim** | Não (SSD) | Não | Lifecycle (IA) |
| Clones/Snapshots avançados | **FlexClone/SnapMirror** | **Clones/snapshots rápidos** | Shadow copies | Backup |
| Foco | Enterprise, multiprotocolo, híbrido | Latência baixa, ZFS | Windows/AD | Linux elástico simples |
| Gestão | ONTAP (CLI/REST/BlueXP) | Console/API AWS | Console/PowerShell | Console/API |

## Escolha

```
Já usa NetApp / precisa NFS + SMB + iSCSI e replicação para on-premises? ─► FSx for NetApp ONTAP
Servidor ZFS/NFS de baixa latência com clones baratos?                  ─► FSx for OpenZFS
Só SMB com Active Directory?                                            ─► FSx for Windows
HPC/ML com S3?                                                          ─► FSx for Lustre
NFS Linux simples e elástico?                                           ─► EFS
```

## Exemplo prático

```bash
# Listar sistemas de arquivos ONTAP e suas SVMs/volumes
aws fsx describe-file-systems --query 'FileSystems[?FileSystemType==`ONTAP`].{Id:FileSystemId,Estado:Lifecycle,GiB:StorageCapacity}'
aws fsx describe-storage-virtual-machines
aws fsx describe-volumes --query 'Volumes[].{Id:VolumeId,Nome:Name,Tipo:VolumeType}'

# Criar um volume ONTAP com tiering automático (resumo)
aws fsx create-volume --volume-type ONTAP --name vol_dados \
  --ontap-configuration "StorageVirtualMachineId=svm-0abc,JunctionPath=/dados,SizeInMegabytes=1048576,StorageEfficiencyEnabled=true,TieringPolicy={Name=AUTO,CoolingPeriod=31}"

# OpenZFS: criar um snapshot e depois um volume clone a partir dele
aws fsx create-snapshot --volume-id fsvol-0zfs123 --name antes-do-teste
aws fsx create-volume --volume-type OPENZFS --name clone-teste \
  --open-zfs-configuration "ParentVolumeId=fsvol-0root,OriginSnapshot={SnapshotARN=arn:aws:fsx:sa-east-1:111122223333:snapshot/fsvolsnap-0abc,CopyStrategy=CLONE}"
```

Cenário: migração de um NetApp on-premises de 80 TB para a AWS.

1. Criar FSx for ONTAP **Multi-AZ** com SVM integrada ao AD.
2. Configurar **SnapMirror** do cluster local para o FSx (baseline + incrementais).
3. Usar tiering **auto** para que dados frios fiquem no tier de capacidade.
4. No dia da virada: último sync, quebrar o espelho e apontar clientes para a SVM do FSx.
5. Manter SnapMirror inverso para fallback ou DR.

## Segurança e operação

- Security Groups para NFS (2049), SMB (445), iSCSI (3260) e gerenciamento ONTAP (443/22).
- Criptografia em repouso (KMS) e em trânsito (conforme protocolo).
- **IAM** controla a API da AWS; o **ONTAP** tem seus próprios usuários/roles (`fsxadmin`, `vsadmin`) para dados.
- Backups automáticos e manuais; AWS Backup.
- CloudWatch para métricas de capacidade, IOPS, throughput.

## Erros comuns e armadilhas

- **Escolher ONTAP sem necessidade** (custo e complexidade): se NFS simples basta, use EFS.
- **Esquecer a capacidade do tier SSD:** volumes cheios mesmo com tiering configurado.
- **Políticas de tiering erradas:** acesso frequente a dados "frios" gera latência.
- **Não planejar a rede de replicação** (SnapMirror) entre on-premises e AWS (VPN/Direct Connect, peering de clusters).
- **Single-AZ em produção.**
- **Clones/snapshots sem política de retenção:** acumulam espaço.
- **Misturar permissões NFS e SMB** sem estilo de segurança definido (unix/ntfs/mixed).
- **Confundir o administrador AWS com o administrador ONTAP.**
- **Presumir paridade entre ONTAP e OpenZFS** (ex.: tiering existe no ONTAP, não no OpenZFS).

## 🧩 Quiz de Fixação

1. O que é uma SVM no FSx for ONTAP e por que usá-la?
2. Qual a diferença entre um snapshot e um clone no OpenZFS?
3. Para que serve o SnapMirror na migração para o FSx for ONTAP?

**Respostas:**
1) *Storage Virtual Machine* é um servidor virtual isolado dentro do sistema de arquivos, com seus protocolos, endpoints e identidade (AD), permitindo multi-tenancy e separação de dados.
2) O snapshot é uma imagem somente leitura de um momento; o clone é um volume gravável derivado de um snapshot, sem copiar dados no início.
3) Replica continuamente os volumes do ONTAP local para o FSx, permitindo uma migração com pouca interrupção (último sync e virada) e também DR.
