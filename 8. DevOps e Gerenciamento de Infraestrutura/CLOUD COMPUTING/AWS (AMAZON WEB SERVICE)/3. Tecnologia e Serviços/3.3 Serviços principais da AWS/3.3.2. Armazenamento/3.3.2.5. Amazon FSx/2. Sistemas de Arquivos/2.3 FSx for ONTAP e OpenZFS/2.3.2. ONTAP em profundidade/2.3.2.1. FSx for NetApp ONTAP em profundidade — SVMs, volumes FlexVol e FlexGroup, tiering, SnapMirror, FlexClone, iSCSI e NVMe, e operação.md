### FSx for NetApp ONTAP em profundidade — SVMs, volumes FlexVol e FlexGroup, tiering, SnapMirror, FlexClone, iSCSI e NVMe, e operação

> [!warning] Aviso
> O FSx for NetApp ONTAP evolui rápido (gerações de sistema de arquivos, escala horizontal, protocolos, limites de capacidade e throughput, recursos como SnapLock e NVMe/TCP). Os números são **ordens de grandeza**. **Confirme na documentação do FSx e da NetApp.** Os comandos **não foram executados**; operações de volume, snapshot e SnapMirror **podem causar perda de dados** se mal usadas.

O FSx for NetApp ONTAP entrega o **sistema operacional de dados ONTAP** da NetApp como serviço gerenciado: **multiprotocolo** (NFS, SMB, iSCSI e NVMe/TCP), **eficiência de armazenamento**, **snapshots e clones instantâneos**, **replicação SnapMirror** e **camada de capacidade elástica**. Na nota de visão geral vimos o essencial. Aqui aprofundamos a **arquitetura**, os **volumes**, o **tiering**, a **proteção de dados**, o **acesso por blocos** (iSCSI/NVMe) e a **operação** com a CLI/REST do ONTAP.

**Analogia:** é uma **central de armazenamento corporativa multifuncional** — um mesmo prédio que oferece pastas de rede, discos para servidores, fotos instantâneas, cópias para filiais e um depósito barato nos fundos para o que raramente é usado. A AWS cuida do prédio; você organiza as salas (SVMs e volumes).

## Arquitetura em camadas

```
 AWS (API/console)          ONTAP (CLI/REST/System Manager)
 ───────────────────        ───────────────────────────────
  File system  ───────────►  Cluster ONTAP (pares HA de nós)
                                │
                                ├─ SVM (Storage Virtual Machine)  ← "servidor virtual": endpoints NFS/SMB/iSCSI, identidade (AD), políticas
                                │    ├─ Volume FlexVol / FlexGroup  ← unidade de dados, snapshots, tiering, quotas
                                │    └─ LUNs / namespaces NVMe (blocos) dentro de volumes
                                └─ Aggregate: SSD (primário) + Capacity pool (S3 gerenciado)
```

| Camada | Conceito |
|---|---|
| **File system** | Recurso AWS: implantação (Single-AZ / Multi-AZ), capacidade SSD, throughput, IOPS, subnets, KMS |
| **Pares HA** | Cada par de nós = um *HA pair* com failover automático; sistemas maiores têm vários pares (escala horizontal) |
| **SVM** | Contêiner lógico de dados e acesso: tem **seu próprio** conjunto de endpoints, protocolos habilitados, domínio AD, usuários, políticas de exportação |
| **Volume** | Unidade de gestão (tamanho, tiering, snapshots, eficiência) |
| **Namespace/Junction path** | Montagem dos volumes em uma árvore única da SVM (`/vol1`, `/vol1/sub`) |
| **Capacity pool** | Tier barato elástico para dados frios |

### Implantações

| Tipo | Disponibilidade | Uso |
|---|---|---|
| **Multi-AZ** | Nó ativo e standby em AZs distintas; failover automático (~minutos ou menos); endpoints flutuantes (IPs de um *route table* /faixa) | Produção |
| **Single-AZ** | Pares HA na mesma AZ | Dev/test, custo menor, DR secundário |
| **Escala horizontal (scale-out)** | Vários pares HA em um só cluster (Single-AZ em gerações novas) | Throughput e IOPS agregados maiores |

Endpoints de Multi-AZ usam **IPs de uma faixa fora dos CIDRs das subnets** (`EndpointIpAddressRange`), roteados via **route tables**: planeje isso na rede (e para acesso on-premises).

## Volumes

| Tipo | Características | Quando |
|---|---|---|
| **FlexVol** | Volume em um agregado de um nó; até dezenas de TiB (limite por geração) | Padrão; cargas gerais |
| **FlexGroup** | Volume distribuído em **vários constituintes** (e nós); capacidade e throughput escaláveis; ótimo para muitos arquivos/ grandes volumes (EDA, mídia, data lakes) | Datasets grandes/muitos arquivos |
| **Volume de proteção de dados (DP)** | Destino de SnapMirror (somente leitura) | DR/replicação |

Propriedades:

| Propriedade | Função |
|---|---|
| **Junction path** | Ponto de montagem na SVM |
| **Tamanho / Autosize** | Crescimento automático até um máximo |
| **Security style** | `unix`, `ntfs` ou `mixed` (define como permissões são avaliadas para acesso NFS vs SMB) |
| **Tiering policy** | Onde os dados ficam (abaixo) |
| **Snapshot policy** | Agendamento e retenção |
| **Storage efficiency** | Deduplicação, compressão, compactação (inline e em segundo plano) |
| **Quotas** | Por usuário/grupo/árvore |
| **Snapshot reserve** | Espaço reservado para snapshots |
| **SnapLock** | WORM para conformidade (volumes SnapLock Enterprise/Compliance) |
| **QoS (adaptativo)** | Limites/pisos de IOPS e throughput por volume |

```bash
aws fsx create-volume --volume-type ONTAP --name vol_dados \
  --ontap-configuration "StorageVirtualMachineId=svm-0abc,JunctionPath=/dados,SizeInMegabytes=2097152,StorageEfficiencyEnabled=true,SecurityStyle=UNIX,TieringPolicy={Name=AUTO,CoolingPeriod=31},OntapVolumeType=RW,SnapshotPolicy=default"
aws fsx describe-volumes --filters Name=file-system-id,Values=fs-0ontap1 --query 'Volumes[].{Nome:Name,Tipo:OntapConfiguration.OntapVolumeType,Junction:OntapConfiguration.JunctionPath}'
```

## Tiering (capacity pool)

Dados **frios** migram do SSD (tier primário) para o **capacity pool** automaticamente, de forma transparente para as aplicações (os mesmos arquivos, latência maior no tier frio).

| Política | Comportamento |
|---|---|
| **Auto** | Blocos de dados **frios** (não acessados por um período — *cooling period*, padrão 31 dias; configurável 2-183) vão para o capacity pool; voltam ao SSD quando lidos aleatoriamente |
| **Snapshot-only** | Só os blocos de **snapshots** frios |
| **All** | Todos os dados (exceto metadados) vão para o capacity pool; ideal para destinos de backup/DR/arquivo |
| **None** | Tudo no SSD |

| Aspecto | Detalhe |
|---|---|
| **Granularidade** | Blocos de 4 KiB |
| **Metadados** | Ficam no SSD |
| **Leitura sequencial de dados frios** | Pode permanecer no tier frio (política *cloud retrieval*) |
| **Custo** | O capacity pool custa uma fração do SSD, com cobrança por requisições de acesso/tiering |
| **Dimensionamento do SSD** | Deve comportar metadados + dados quentes + operações (snapshots); monitore `StorageUsed` |
| **Métricas** | Uso do SSD e do capacity pool; taxa de tiering |

```
 SSD (quente)  ──[cooling period]──►  Capacity pool (frio)  ◄── leitura de dado frio traz de volta (aleatória) ou lê direto
```

## Proteção de dados

### Snapshots e FlexClone

| Recurso | Descrição |
|---|---|
| **Snapshots** | Cópias **somente leitura** instantâneas (ponteiros), com espaço apenas das mudanças; visíveis ao cliente (`.snapshot` em NFS, "Versões anteriores" em SMB) |
| **Políticas** | Horária/diária/semanal com retenção (ex.: 6 horárias, 2 diárias, 2 semanais) |
| **Restauração** | Por arquivo (cliente), por volume (`volume snapshot restore`) ou por clone |
| **FlexClone** | Volume gravável derivado de um snapshot em segundos, sem copiar dados (dev/test, CI, analytics) |

### SnapMirror (replicação)

```
 Origem (ONTAP on-premises ou FSx)  ══ SnapMirror (assíncrono, incremental, por snapshots) ══►  Destino (volume DP no FSx)
```

| Característica | Detalhe |
|---|---|
| **Direção** | Entre sistemas ONTAP (on-premises ↔ FSx, FSx ↔ FSx, entre regiões) |
| **Modo** | Assíncrono por snapshots; opção de sincronização contínua em alguns cenários |
| **Requisitos** | **Cluster peering** (rede entre clusters; portas 11104/11105 e ICMP/ICMP), **SVM peering** |
| **Usos** | **Migração** (baseline + incrementais + corte), **DR**, **backup**, replicação multirregião |
| **Failover** | Quebrar o espelho (`snapmirror break`), tornar o destino gravável, montar nos clientes; failback com `snapmirror resync` |
| **Eficiência** | Preserva eficiência de armazenamento na transferência (dedup/compressão) |

### Backups

Backups **automáticos diários** (volume) com retenção configurável e **backups manuais**, armazenados de forma incremental fora do sistema de arquivos; restauração para um volume novo. **AWS Backup** centraliza políticas. Cópia entre regiões/contas conforme disponível.

## Protocolos e acesso

### NFS e SMB

| Aspecto | Detalhe |
|---|---|
| **NFS** | v3, v4.0, v4.1, v4.2; **export policies** por volume (CIDR, super user, read-only) |
| **SMB** | v2/3, ingresso da SVM no **AD** (AWS Managed AD ou próprio), ACLs NTFS, **shares** com ACL de compartilhamento, SMB encryption, **continuous availability (CA)** em Multi-AZ para SQL Server/Hyper-V |
| **Multiprotocolo** | O mesmo volume por NFS e SMB com *name mapping* usuários UNIX ↔ Windows e `security style` apropriado |
| **Kerberos** | NFS e SMB com Kerberos (krb5/krb5p) |

### iSCSI e NVMe/TCP (blocos)

| Aspecto | Detalhe |
|---|---|
| **LUNs iSCSI** | Criadas em volumes; **igroup** controla quem acessa (IQN do iniciador); mapeamento LUN→igroup |
| **MPIO** | Múltiplos caminhos (Linux `multipath`, Windows MPIO) entre iniciador e endpoints iSCSI da SVM para resiliência |
| **NVMe/TCP** | Namespaces NVMe com menor latência/overhead (recurso mais recente; confirme) |
| **Casos** | Bancos de dados (Oracle, SQL Server, SAP), VMware (Datastores), clusters Windows |
| **Planejamento** | Volume com espaço para snapshots; tiering **None** para LUNs sensíveis à latência |

```bash
# Via CLI do ONTAP (SSH no endpoint de gerenciamento da SVM, usuário vsadmin/fsxadmin)
ssh fsxadmin@management.fs-0ontap1.fsx.sa-east-1.amazonaws.com
::> lun create -vserver svm1 -volume vol_bd -lun lun1 -size 500GB -ostype linux
::> igroup create -vserver svm1 -igroup ig_servidores -protocol iscsi -ostype linux -initiator iqn.1994-05.com.redhat:servidor01
::> lun mapping create -vserver svm1 -volume vol_bd -lun lun1 -igroup ig_servidores
```

## Segurança

- **Rede:** SG por porta (NFS 111/2049/635/4045/4046, SMB 445, iSCSI 3260, gerenciamento 443/22, SnapMirror 11104/11105); sem acesso público.
- **Criptografia:** em repouso (KMS) e em trânsito (SMB encryption, Kerberos, NFS krb5p, IPsec opcional).
- **IAM:** controla a API AWS; o ONTAP tem papéis próprios (RBAC).
- **Auditoria:** do ONTAP (acesso a arquivos, NAS audit) e CloudTrail.
- **Antivírus:** integração com *Vscan* de parceiros.
- **Proteção ransomware:** snapshots imutáveis, SnapLock, políticas de bloqueio de extensões (FPolicy), detecção autônoma (ARP) conforme versão.

## Exemplo prático

Migração de um cluster NetApp on-premises (80 TB) com bancos Oracle (iSCSI) e arquivos (SMB) para a AWS:

1. **Destino:** FSx for ONTAP Multi-AZ com 2 SVMs (`svm-arquivos` no domínio AD; `svm-bd` para blocos), SSD 40 TiB, capacity pool habilitado.
2. **Volumes:** `vol_arquivos` (FlexGroup, tiering Auto/31 dias) e `vol_bd` (FlexVol, tiering None, LUNs iSCSI com MPIO).
3. **Migração:** cluster peering + SVM peering; **SnapMirror** com baseline (via Direct Connect) e atualizações horárias.
4. **Corte:** na janela, última atualização, `snapmirror break`, montar clientes SMB/NFS e iniciadores iSCSI no FSx; atualizar DNS/alias; validar com os DBAs.
5. **Proteção:** snapshots a cada hora e diários (retenção 30), backup diário do FSx, cópia SnapMirror para outra região (volume DP com tiering All).
6. **Dev/test:** FlexClone semanal do volume de BD para homologação, em segundos e sem custo inicial.
7. **Operação:** métricas de `StorageUsed`, capacity pool, throughput; QoS para isolar o ambiente de homologação; alarmes de capacidade SSD livre < 15%.

## Erros comuns e armadilhas

- **SSD subdimensionado:** o tiering não resolve se os dados quentes + metadados não cabem; o SSD enche e o desempenho cai.
- **Tiering em LUNs sensíveis à latência.**
- **Security style incorreto** em ambientes multiprotocolo (permissões negadas inesperadas).
- **Endpoints de Multi-AZ fora da rota** (route tables não propagadas / faixa de IP conflitante).
- **Peering de cluster sem portas liberadas** (SnapMirror não inicia).
- **Quebrar o SnapMirror sem planejar o failback.**
- **Snapshots em excesso** consumindo espaço (reserva).
- **Esquecer MPIO** em iSCSI (queda de caminho derruba o disco).
- **Usar `fsxadmin` no dia a dia** sem governança.
- **Comparar apenas preço/GB** com EFS/FSx Windows sem contar os recursos (clones, SnapMirror, eficiência).
- **Ignorar o limite de snapshots e volumes por sistema de arquivos.**

## 🧩 Quiz de Fixação

1. O que é uma SVM no FSx for ONTAP e por que usar mais de uma?
2. Quais as quatro políticas de tiering e quando usar a "All"?
3. Como o SnapMirror apoia migração e DR?
4. Qual a diferença entre FlexVol e FlexGroup?

**Respostas:**
1) A Storage Virtual Machine é um servidor virtual com seus próprios endpoints, protocolos, domínio AD e políticas; várias SVMs isolam locatários, ambientes ou protocolos no mesmo sistema de arquivos.
2) Auto (blocos frios após o período), Snapshot-only (só blocos de snapshots), All (tudo no capacity pool) e None (tudo no SSD); "All" serve para destinos de backup, DR ou arquivo, com acesso pouco frequente.
3) Replica volumes de forma assíncrona e incremental por snapshots entre sistemas ONTAP (on-premises ou FSx, inclusive entre regiões); para migração faz-se baseline, atualizações e corte (break), e para DR mantém-se o destino pronto para ser promovido.
4) FlexVol reside em um agregado de um nó (limite de tamanho); FlexGroup distribui o volume em vários constituintes e nós, escalando capacidade e throughput para muitos arquivos e grandes volumes.
