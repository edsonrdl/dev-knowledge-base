### FSx for Lustre — computação de alto desempenho, integração com S3, scratch e persistent

> [!warning] Aviso
> Tipos de implantação, throughput por TiB, classes de armazenamento, limites e preços do FSx for Lustre mudam. Confirme na documentação. Os comandos **não foram executados**.

O **FSx for Lustre** é um sistema de arquivos **paralelo e de altíssimo desempenho**, baseado no **Lustre** (padrão em supercomputadores). Entrega **centenas de GB/s** de vazão agregada, **milhões de IOPS** e latência sub-milissegundo, para cargas de **HPC, machine learning, processamento de mídia, genômica e análise financeira**. Integra-se nativamente ao **Amazon S3**.

**Analogia:** o Lustre é uma **linha de montagem com centenas de esteiras em paralelo**: cada arquivo é dividido em pedaços (stripes) espalhados por muitos servidores, e centenas de máquinas leem e escrevem ao mesmo tempo, sem fila.

## Como funciona

```
 Clientes (centenas de EC2/GPU) ──cliente Lustre──► ┌ servidor de metadados (MDS) ┐
                                                     └ servidores de objetos (OSS/OST) ┘
                                                       dados distribuídos em stripes
                                                              ▲
                                       Data Repository Association ──► Amazon S3 (bucket)
```

- **Metadados** separados dos **dados**, escalando de forma independente.
- Os arquivos são **distribuídos (striped)** entre muitos discos/servidores, permitindo leitura e escrita paralelas.
- Os clientes precisam do **cliente Lustre** (kernel module) instalado — não é SMB/NFS padrão. Funciona em Linux (EC2, ECS, EKS via CSI), inclusive instâncias de GPU e AWS ParallelCluster.

## Tipos de implantação

| Tipo | Dados | Durabilidade | Uso |
|---|---|---|---|
| **Scratch** (SCRATCH_1/SCRATCH_2) | Armazenados em servidor único, **sem replicação** | Se um servidor falha, os dados naquele servidor se perdem | Processamento **temporário** de curta duração, melhor custo/desempenho |
| **Persistent** (PERSISTENT_1/PERSISTENT_2) | **Replicados** dentro da AZ, com substituição automática de servidor | Dados duradouros dentro da AZ | Cargas de longa duração, dados sensíveis, necessidade de backup |

Outras diferenças: *persistent* oferece **backups**, **criptografia em trânsito**, **throughput configurável por TiB** e classes de armazenamento (SSD, HDD, com cache SSD de leitura); *scratch* oferece o maior throughput de burst por custo.

Armazenamento: **SSD** (IOPS e latência) ou **HDD** (throughput, custo menor), com opção de **cache SSD** para HDD.

Escopo: **uma AZ** (não é Multi-AZ). Para resiliência regional use backups e o S3.

## Integração com Amazon S3

A integração é o grande diferencial: o FSx for Lustre apresenta objetos do S3 como **arquivos** e pode exportar resultados de volta.

| Recurso | Função |
|---|---|
| **Data Repository Association (DRA)** | Vincula um **diretório do sistema de arquivos** a um **bucket/prefixo S3** |
| **Importação lazy** | Metadados dos objetos aparecem automaticamente; o **conteúdo é carregado do S3 na primeira leitura** |
| **Importação automática** | Reflete novos objetos/alterações do S3 no sistema de arquivos |
| **Exportação** | Grava arquivos novos/alterados de volta ao S3 (automática ou por tarefa sob demanda) |
| **Release de dados** | Libera arquivos exportados do disco, mantendo-os no S3, para economizar espaço |

```
 S3: s3://dataset/treino/  ──DRA──►  /fsx/treino/   (arquivos "aparecem" sob demanda)
 Treinamento escreve  /fsx/saida/  ──export──►  s3://dataset/saida/
```

Fluxo típico de ML/HPC:

1. Dados brutos no S3 (barato, durável).
2. Criar FSx for Lustre (scratch) com DRA para o bucket.
3. Cluster lê em altíssima velocidade via Lustre.
4. Resultados exportados ao S3.
5. **Excluir** o sistema de arquivos (paga só pelo tempo de uso).

## Casos de uso

| Caso | Por quê |
|---|---|
| **Treinamento de ML/DL** com datasets grandes | Alimenta GPUs sem gargalo de I/O |
| **HPC** (simulações, CFD, genômica, reservoir) | Vazão paralela |
| **Renderização e transcodificação** de mídia | Muitos nós lendo/escrevendo |
| **Análise financeira/risco** | Janelas curtas e picos |
| **Big data temporário** | Camada de cache sobre S3 |

Quando não usar: compartilhamento geral de arquivos (EFS/FSx Windows), Windows, banco de dados, acesso esporádico.

## Exemplo prático

```bash
# Criar um FSx for Lustre scratch de 1,2 TiB (resumo; ver parâmetros atuais)
aws fsx create-file-system --file-system-type LUSTRE \
  --storage-capacity 1200 --subnet-ids subnet-0aaa111 \
  --security-group-ids sg-0lustre123 \
  --lustre-configuration DeploymentType=SCRATCH_2

# Associar um diretório a um prefixo do S3 (Data Repository Association)
aws fsx create-data-repository-association --file-system-id fs-0lus123 \
  --file-system-path /treino --data-repository-path s3://meu-dataset/treino \
  --s3 "AutoImportPolicy={Events=[NEW,CHANGED,DELETED]},AutoExportPolicy={Events=[NEW,CHANGED,DELETED]}"

# Montar no cliente Linux (cliente Lustre instalado)
sudo mkdir -p /fsx
sudo mount -t lustre -o noatime,flock fs-0lus123.fsx.sa-east-1.amazonaws.com@tcp:/abcdefgh /fsx
# O ponto de montagem e o "mount name" aparecem no describe-file-systems

# Exportar manualmente e liberar espaço
aws fsx create-data-repository-task --file-system-id fs-0lus123 --type EXPORT_TO_REPOSITORY \
  --paths /saida --report Enabled=false
```

Explicação: o scratch entrega o máximo de desempenho por custo para o job; ao final, os resultados são exportados ao S3 e o sistema de arquivos é excluído.

## Desempenho e dimensionamento

| Fator | Observação |
|---|---|
| **Throughput** | Proporcional à capacidade (MB/s por TiB conforme o tipo) — mais capacidade = mais vazão |
| **Striping** | Arquivos grandes se beneficiam de mais stripes; ajustar com `lfs setstripe` |
| **Tamanho de I/O** | Operações grandes e sequenciais rendem mais |
| **Rede do cliente** | Instâncias com **EFA** e rede de alta largura de banda aproveitam melhor |
| **Muitos arquivos pequenos** | Sobrecarga de metadados; o Lustre é bom, mas dimensione IOPS de metadados |

## Segurança

- Dentro da VPC com Security Group (portas Lustre 988 e 1018-1023 entre clientes e servidores).
- Criptografia em repouso com KMS; em trânsito (em tipos *persistent*/geração recente).
- Permissões POSIX; acesso ao bucket S3 via IAM do serviço (DRA usa a identidade do serviço).
- Backups (persistent) e AWS Backup.

## Anatomia do Lustre e como o desempenho escala

```
 Clientes (centenas) ──rede──► MDS/MDT (metadados) + vários OSS/OST (dados em stripes)
 Um arquivo grande é dividido em stripes distribuídos entre servidores → leituras/escritas em paralelo
 Throughput agregado ≈ capacidade provisionada × MB/s por TiB do tipo escolhido
```

| Opção | Scratch | Persistent (1/2) |
|---|---|---|
| Durabilidade | Sem replicação; falha de servidor perde dados | Replicação na AZ; arquivos de servidor com falha são restaurados |
| Uso | Processamento temporário, burst | Longa duração, dados que não se quer reprocessar |
| Custo | Menor | Maior |
| Backup | Não | Sim |
| Throughput por TiB | Alto (varia por geração) | Faixas por MB/s/TiB escolhidas |

> [!warning] Faixas de MB/s por TiB, tamanhos mínimos e novas gerações mudam; confirme na documentação atual.

## Data Repository Association (DRA) com o S3

```
 S3 prefixo s3://dataset/train/  ◄──DRA──►  /fsx/train/
   Import: lê metadados na criação (lazy load de dados quando acessados)
   Export: grava alterações de volta ao S3 (automático ou por tarefa)
```

| Modo | Efeito |
|---|---|
| Lazy loading | Arquivo só é trazido do S3 no primeiro acesso, o que pode causar latência |
| Preload | `lfs hsm_restore` ou tarefa para aquecer o cache antes do job |
| Export automático | Mudanças fluem ao S3 (políticas de import/export configuráveis) |
| Release | `lfs hsm_release` libera espaço em disco mantendo os metadados |

### Comandos úteis (comentados, não executados)

```bash
sudo amazon-linux-extras install -y lustre
sudo mount -t lustre -o noatime,flock fs-0abc.fsx.sa-east-1.amazonaws.com@tcp:/abcdefgh /fsx
lfs getstripe /fsx/train/dados.bin          # ver striping
lfs setstripe -c 8 -S 4M /fsx/saida         # 8 stripes de 4 MB para arquivos grandes

  --file-system-path /train --data-repository-path s3://dataset/train \
  --s3 "AutoImportPolicy={Events=[NEW,CHANGED,DELETED]},AutoExportPolicy={Events=[NEW,CHANGED,DELETED]}"
```

## Quando usar e quando não

| Cenário | Decisão |
|---|---|
| Treino de ML com datasets grandes no S3 | Lustre scratch + DRA |
| Simulações HPC (CFD, genômica) com checkpoints | Lustre persistent |
| Cargas pequenas, poucos clientes | EFS/FSx OpenZFS bastam |
| Compartilhamento Windows | FSx for Windows |

## Troubleshooting

| Sintoma | Causa provável | Ação |
|---|---|---|
| Primeira leitura lenta | Lazy loading do S3 | Preload antes do job |
| Montagem falha | SG sem portas 988 e 1018-1023 / módulo cliente ausente | Liberar portas, instalar cliente Lustre |
| Muitos arquivos pequenos lentos | Metadados no MDS | Agrupar em arquivos maiores, ajustar striping |
| Disco cheio | Dados não liberados | `lfs hsm_release`, aumentar capacidade |

## Erros comuns e armadilhas

- **Usar scratch para dados que não podem ser perdidos.**
- **Esquecer que é uma AZ só:** clientes em outra AZ geram tráfego cruzado e custo.
- **Security Group sem as portas do Lustre.**
- **Cliente Lustre incompatível com o kernel** do SO.
- **Deixar o sistema de arquivos ligado depois do job:** custo por hora.
- **Não configurar exportação ao S3** e perder resultados ao excluir o sistema.
- **Subdimensionar capacidade** esperando alto throughput: a vazão depende da capacidade.
- **Esperar que alterações no S3 apareçam sem importação automática/tarefa.**
- **Usar o Lustre como servidor de arquivos geral.**

## 🧩 Quiz de Fixação

1. Qual a diferença entre scratch e persistent?
2. Como o FSx for Lustre se integra ao S3?
3. Por que o throughput do Lustre depende da capacidade provisionada?

**Respostas:**
1) *Scratch* não replica os dados (menor custo e maior burst, para processamento temporário); *persistent* replica dentro da AZ, substitui servidores com falha e oferece backups, para dados duradouros.
2) Por Data Repository Associations: objetos do S3 aparecem como arquivos (carregados na primeira leitura) e os resultados podem ser exportados de volta ao bucket, automática ou manualmente.
3) Porque os dados são distribuídos em servidores de armazenamento; mais capacidade significa mais servidores/discos e, portanto, mais vazão agregada (MB/s por TiB).

### Questões de aprofundamento

4. Por que o primeiro epoch de treino é mais lento com DRA?
5. Por que milhões de arquivos pequenos prejudicam o Lustre?
6. Quando preferir persistent a scratch?

**Respostas:**
4) O lazy loading busca os dados no S3 no primeiro acesso; faça preload para aquecer o cache.
5) A carga recai sobre o servidor de metadados, e o striping paralelo não ajuda arquivos minúsculos.
6) Quando o sistema deve viver por muito tempo ou os dados não podem ser perdidos por falha de servidor.
