### FSx for OpenZFS em profundidade — volumes, snapshots, clones, compressão, cotas, replicação e comparação com ONTAP

> [!warning] Aviso
> Tipos de implantação (Single-AZ, Multi-AZ), limites de capacidade, throughput e IOPS, protocolos (NFS e SMB) e recursos do FSx for OpenZFS mudam com frequência. Os números são **ordens de grandeza**. **Confirme na documentação.** Os comandos **não foram executados**; operações de snapshot, rollback e exclusão **podem causar perda de dados**.

O **FSx for OpenZFS** oferece o sistema de arquivos **OpenZFS** como serviço gerenciado: **latência muito baixa** (SSD com cache em memória), **snapshots e clones praticamente instantâneos e baratos**, **compressão transparente**, **cotas por usuário/grupo/projeto**, **NFS** (e SMB nas gerações mais novas) e **replicação** por snapshots. É a migração natural de **servidores ZFS/Linux e NAS baseados em ZFS** e uma ótima base para **ambientes de desenvolvimento e CI** com clones por branch. Esta nota aprofunda a arquitetura, os volumes e as propriedades ZFS, a proteção de dados, o acesso, a operação e a comparação com o ONTAP e o EFS.

**Analogia:** o OpenZFS é um **cofre com máquina do tempo e fotocopiadora mágica**: tira fotos do estado a qualquer instante (snapshots), faz cópias de trabalho que só ocupam espaço quando alteradas (clones) e comprime tudo para caber mais.

## Arquitetura

```
 Clientes Linux (NFS) / Windows (SMB, geração recente)
              │  endpoint do sistema de arquivos (Multi-AZ: IP flutuante)
   ┌──────────▼───────────┐          ┌───────────────────────┐
   │ Servidor de arquivos │◄─ HA ───►│ Servidor standby (AZ-b)│   (Single-AZ HA / Multi-AZ)
   │  ZFS + cache (ARC)   │          └───────────────────────┘
   └──────────┬───────────┘
        pool ZFS em SSD (volumes EBS de alta durabilidade gerenciados)
        ├─ raiz (/fsx) ├─ volume: /fsx/dev   ├─ volume: /fsx/dados  └─ snapshots / clones
```

| Elemento | Detalhe |
|---|---|
| **File system** | Pool de armazenamento SSD; capacidade e throughput provisionados (e IOPS) |
| **Volume** | Dataset ZFS filho do sistema de arquivos; **hierárquico** (volumes dentro de volumes); cada um com propriedades próprias |
| **Cache** | **ARC** em memória e cache de leitura em NVMe (L2ARC), o que dá latência sub-ms em leituras quentes |
| **Implantações** | **Single-AZ** (HA em um par ou não) e **Multi-AZ** (standby em outra AZ com failover automático); verifique as gerações atuais |
| **Armazenamento** | SSD apenas; capacidade de dezenas de GiB até centenas de TiB (confirme); só aumenta |
| **Throughput / IOPS** | Configuráveis (do sistema de arquivos) até alto desempenho (centenas de milhares de IOPS e dezenas de GB/s em configurações maiores; confirme) |
| **Protocolos** | NFS v3, v4.0, v4.1, v4.2; SMB em versões recentes (confirme região e geração) |

## Volumes e propriedades ZFS

Cada volume pode ter propriedades independentes:

| Propriedade | Função | Valores/observações |
|---|---|---|
| **Compressão** (`DataCompressionType`) | Comprime transparentemente | `LZ4` (rápido, bom padrão) ou `ZSTD` (maior compressão, mais CPU); `NONE` |
| **Cotas e reservas** (`StorageCapacityQuotaGiB`, `StorageCapacityReservationGiB`) | Limitar ou garantir capacidade por volume | Evita que um volume ocupe tudo |
| **Cotas de usuário/grupo** (`UserAndGroupQuotas`) | Limite por UID/GID | Para home directories |
| **`RecordSizeKiB`** | Tamanho do bloco do ZFS (4 KiB-1 MiB) | **128 KiB** (padrão) para arquivos gerais; 1 MiB para arquivos grandes sequenciais; 8-16 KiB para bancos de dados com blocos pequenos |
| **Opções de exportação NFS** (`NfsExports`) | Quem pode montar e como | Por CIDR: `rw`/`ro`, `crossmnt`, `sync`/`async`, `no_root_squash`/`root_squash`, `all_squash` |
| **Cópia de tags para snapshots** | Governança | — |
| **Leitura somente** (`ReadOnly`) | Proteger dados | — |
| **Volume raiz** | Herança de propriedades para filhos | Filhos herdam compressão e recordsize, sobrescrevíveis |

```bash
aws fsx create-volume --volume-type OPENZFS --name dados \
  --open-zfs-configuration "ParentVolumeId=fsvol-0root,DataCompressionType=ZSTD,RecordSizeKiB=128,StorageCapacityQuotaGiB=2048,\
NfsExports=[{ClientConfigurations=[{Clients=10.0.0.0/16,Options=[rw,crossmnt,no_root_squash]}]}],\
UserAndGroupQuotas=[{Type=USER,Id=1001,StorageCapacityQuotaGiB=50}]"
aws fsx describe-volumes --filters Name=file-system-id,Values=fs-0zfs1 \
  --query 'Volumes[].{Nome:Name,Id:VolumeId,Tipo:VolumeType,Raiz:OpenZFSConfiguration.ParentVolumeId}'
```

### Montagem (NFS)

```bash
sudo mkdir -p /fsx/dados
sudo mount -t nfs -o nfsvers=4.1,rsize=1048576,wsize=1048576,noresvport fs-0zfs1.fsx.sa-east-1.amazonaws.com:/fsx/dados /fsx/dados
```

## Snapshots, clones e rollback

| Recurso | Descrição |
|---|---|
| **Snapshots** | Cópias **somente leitura**, instantâneas, de um volume; ocupam espaço apenas das mudanças; visíveis ao usuário em `.zfs/snapshot` (restauração self-service) |
| **Snapshots automáticos** | Via AWS Backup/políticas ou agendamento próprio (cron + API) |
| **Clones** | Volumes **graváveis** derivados de um snapshot, instantâneos, usando espaço só das alterações — ideais para dev/test, CI, análises e testes de migração |
| **Rollback** | Reverte um volume a um snapshot (`RestoreToSnapshot`), descartando mudanças posteriores (e snapshots posteriores, conforme opção) |
| **Dependência de clones** | O snapshot de origem de um clone não pode ser removido enquanto o clone existe (ou é promovido/copiado) |

```bash
aws fsx create-snapshot --volume-id fsvol-0dados --name pre-release-2026-11
aws fsx create-volume --volume-type OPENZFS --name dados-hml \
  --open-zfs-configuration "ParentVolumeId=fsvol-0root,OriginSnapshot={SnapshotARN=arn:aws:fsx:sa-east-1:111122223333:snapshot/fsvolsnap-0abc,CopyStrategy=CLONE}"
aws fsx restore-volume-from-snapshot --volume-id fsvol-0dados --snapshot-id fsvolsnap-0abc --options DELETE_INTERMEDIATE_SNAPSHOTS
# Atenção: o rollback descarta alterações feitas depois do snapshot
```

Padrões:

1. **CI/CD com clones por branch**: clone do dataset de produção (mascarado) para cada pipeline, descartado ao fim.
2. **Antes de upgrades**: snapshot → atualizar → rollback se falhar.
3. **Dados científicos**: snapshots imutáveis por versão do dataset; clones para experimentos.
4. **Recuperação rápida**: usuário restaura arquivo via `.zfs/snapshot/<nome>/arquivo`.

## Replicação, backup e DR

| Mecanismo | Detalhe |
|---|---|
| **Backups automáticos e manuais** | Diários, incrementais, retenção configurável; restauração em novo sistema de arquivos ou volume |
| **AWS Backup** | Planos, cópias entre regiões/contas, cofres |
| **Cópia de snapshot para outro sistema de arquivos** (`CopySnapshotAndUpdateVolume`) | **Replicação incremental** de um volume para outro sistema OpenZFS (na mesma ou outra região/conta) baseada em snapshots — equivalente ao `zfs send/receive` gerenciado |
| **Copy-on-write** | Os dados replicados preservam eficiência (compressão) |
| **Failover entre sistemas** | Promover/gravar no destino e redirecionar clientes (DNS) |
| **RPO** | Intervalo entre replicações (minutos a horas) |
| **Multi-AZ** | HA dentro da região; não substitui backup |

```bash
# Replicar incrementalmente um volume para um segundo sistema OpenZFS (destino em outra região)
aws fsx copy-snapshot-and-update-volume --volume-id fsvol-0destino --source-snapshot-arn arn:aws:fsx:sa-east-1:111122223333:snapshot/fsvolsnap-0abc \
  --copy-strategy INCREMENTAL_COPY --options DELETE_INTERMEDIATE_SNAPSHOTS
```

Combine com **agendamento** (EventBridge + Lambda) para criar snapshots e replicar a cada N minutos.

## Acesso, segurança e rede

| Tema | Detalhe |
|---|---|
| **Rede** | Subnets/ENIs na VPC; SG com NFS (111, 2049, 20001-20003) e SMB (445) conforme protocolo |
| **Exportações NFS** | Por CIDR e opções; princípio do menor privilégio; `root_squash` por padrão em dados de usuários |
| **Criptografia** | Em repouso (KMS) sempre; em trânsito (NFS com Kerberos/TLS conforme suporte; use rede privada) |
| **Autenticação** | NFS por host/UID (sem AD nativo no NFS); SMB com AD nas gerações novas |
| **Auditoria** | CloudTrail para API; logs do servidor conforme disponível |
| **IAM** | Controla a API (criar, snapshots, backups); não há controle IAM por arquivo |
| **Acesso on-premises** | VPN/Direct Connect |

Observação: no NFS, a identidade é por **UID/GID**; alinhe usuários entre clientes (LDAP/SSSD) ou use cotas/mapeamento.

## Desempenho e dimensionamento

| Fator | Orientação |
|---|---|
| **Throughput e IOPS do file system** | Dimensione pelo pico agregado; podem ser **alterados** depois |
| **Capacidade SSD** | Inclui dados + snapshots + clones divergentes; reserve margem (ZFS degrada perto de 100%; mantenha < 80-85%) |
| **Cache** | Working set de leitura que caiba em memória/NVMe tem latência sub-ms |
| **Recordsize** | Alinhar ao padrão de I/O (grandes sequenciais: 1 MiB; bancos: 8-16 KiB) |
| **Compressão** | LZ4 quase sem custo de CPU e economia de espaço/I/O; ZSTD para dados muito compressíveis |
| **Cliente** | `nfsvers=4.1`, `rsize/wsize=1048576`, `nconnect=` (kernels recentes) para throughput, conexões em paralelo |
| **Paralelismo** | Vários processos/clientes |
| **Rede** | Banda da instância |

Métricas CloudWatch (`AWS/FSx`): `DataReadBytes`, `DataWriteBytes`, `DataReadOperations`, `DataWriteOperations`, `MetadataOperations`, `FreeStorageCapacity`, `NetworkThroughputUtilization`, `CPUUtilization`, `FileServerCacheHitRatio`, `DiskThroughputUtilization`/`DiskIopsUtilization`, `UsedStorageCapacity` por tipo (dados/snapshots).

## OpenZFS × ONTAP × EFS

| Critério | **FSx for OpenZFS** | **FSx for ONTAP** | **EFS** |
|---|---|---|---|
| Protocolos | NFS (e SMB em versões novas) | NFS, SMB, iSCSI, NVMe/TCP | NFS |
| Latência | **Sub-ms** (SSD+cache) | Sub-ms (SSD), maior no capacity pool | ~ms |
| Snapshots/clones | **Excelentes e baratos** | Excelentes (FlexClone) | Backup (sem clones) |
| Tiering para camada barata | Não | **Sim** (capacity pool) | Sim (IA/Archive) |
| Replicação | Snapshot incremental entre sistemas OpenZFS | **SnapMirror** (on-premises ↔ AWS) | Replicação entre regiões |
| Blocos (iSCSI) | Não | **Sim** | Não |
| Escala | Até centenas de TiB; throughput configurável | Muito grande (scale-out) | Elástico e ilimitado |
| Ecossistema | ZFS/Linux; simples | NetApp (ferramentas, Trident, BlueXP) | AWS nativo |
| Custo | SSD (previsível) | SSD + capacity pool | Por GB usado |
| Quando | Migrar ZFS/NAS Linux; baixa latência; dev/test com clones | Ambientes NetApp/multiprotocolo/blocos | Linux elástico simples |

## Exemplo prático

Plataforma de CI/CD com 40 desenvolvedores e um dataset de testes de 3 TB (monorepo + bancos de teste):

1. **FSx for OpenZFS** Multi-AZ, SSD 8 TiB, throughput 1.280 MB/s; volume `golden` (compressão ZSTD, recordsize 128 KiB) com o dataset mascarado de produção; export NFS para o CIDR dos runners.
2. **Snapshot** `golden@2026-11-06` semanal.
3. **Clones por pipeline:** cada execução cria `ci-<id>` a partir do snapshot (segundos, sem custo inicial), monta no runner, executa os testes e **exclui** o clone; testes que antes esperavam 40 minutos de cópia agora começam em < 1 minuto.
4. **Proteção:** backup diário + AWS Backup (cópia em outra região); `CopySnapshotAndUpdateVolume` a cada 15 min para um segundo sistema OpenZFS no DR.
5. **Cotas:** home dirs de desenvolvedores com cotas de usuário (50 GiB); volumes de equipe com cotas e reservas.
6. **Observabilidade:** `FileServerCacheHitRatio` > 90%, `FreeStorageCapacity` > 20%, alarmes; limpeza automática de clones órfãos por tag/TTL.
7. **Resultado:** tempo de preparação de ambiente de teste de 40 min para < 1 min; custo de armazenamento do dataset único + deltas.

## Erros comuns e armadilhas

- **Encher o pool acima de ~85%:** desempenho cai e operações demoram.
- **Esquecer que clones prendem o snapshot de origem** (não dá para apagar).
- **Rollback sem perceber que descarta tudo depois do snapshot.**
- **Exportações NFS abertas (`0.0.0.0/0`, `no_root_squash`)** em dados sensíveis.
- **UIDs divergentes entre clientes** (permissões quebradas).
- **Esperar iSCSI/blocos no OpenZFS** (use ONTAP).
- **Recordsize inadequado** (grande para banco; pequeno para streaming).
- **Snapshots e clones sem política de retenção** (capacidade consumida).
- **Single-AZ em produção crítica.**
- **Confundir Multi-AZ com backup/DR.**
- **Não testar a replicação/restauração.**

## 🧩 Quiz de Fixação

1. O que diferencia um snapshot de um clone no OpenZFS e para que usar clones?
2. Qual o papel do `recordsize` e como escolhê-lo?
3. Como replicar um volume OpenZFS para outro sistema de arquivos?
4. Quando escolher OpenZFS em vez de ONTAP ou EFS?

**Respostas:**
1) O snapshot é uma imagem somente leitura de um instante; o clone é um volume gravável derivado de um snapshot, que só ocupa espaço do que for alterado; clones servem para dev/test, CI, análises e testes de migração, criando ambientes em segundos.
2) Define o tamanho do bloco do ZFS: 128 KiB (padrão) para uso geral, 1 MiB para arquivos grandes sequenciais e 8-16 KiB para bancos de dados com blocos pequenos, alinhando com o padrão de I/O.
3) Com a cópia incremental de snapshot (`CopySnapshotAndUpdateVolume`, estilo `zfs send/receive` gerenciado) para um volume em outro sistema OpenZFS, possivelmente em outra região ou conta, ou com backups do FSx/AWS Backup.
4) Quando se migra de servidores ZFS/NAS Linux, quer-se latência muito baixa, snapshots e clones baratos para dev/test, e não se precisa de iSCSI nem de SnapMirror; ONTAP serve para ambientes NetApp, blocos e replicação on-premises, e EFS para um NFS elástico simples.
