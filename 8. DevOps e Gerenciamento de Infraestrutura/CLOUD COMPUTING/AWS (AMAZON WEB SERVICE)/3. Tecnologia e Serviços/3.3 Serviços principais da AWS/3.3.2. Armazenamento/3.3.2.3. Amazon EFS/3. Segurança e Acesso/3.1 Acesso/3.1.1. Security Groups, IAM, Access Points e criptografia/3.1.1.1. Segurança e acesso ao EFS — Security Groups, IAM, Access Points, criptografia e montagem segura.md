### Segurança e acesso ao EFS — Security Groups, IAM, Access Points, criptografia e montagem segura

> [!warning] Aviso
> Condições de política, opções de montagem e recursos do EFS evoluem. Confirme na documentação. Os comandos e JSONs **não foram executados**.

A segurança do EFS tem **várias camadas** que se somam: **rede** (Security Groups), **identidade** (IAM e política do sistema de arquivos), **permissões de arquivo** (POSIX), **pontos de acesso** (Access Points) e **criptografia** em repouso e em trânsito. Entender qual camada resolve cada problema evita tanto brechas quanto erros de "Permission denied".

**Analogia:** acessar um arquivo no EFS é entrar numa **sala-cofre dentro de um prédio**: o *Security Group* é a portaria do prédio; o *IAM/policy* é o crachá que autoriza entrar na sala; os *Access Points* são portas específicas que levam a uma estante e impõem um uniforme; as *permissões POSIX* são as chaves de cada gaveta; a *criptografia* é o cofre que protege o conteúdo.

## Camada 1 — Rede: Security Groups e NACLs

- O acesso NFS é feito por **TCP 2049** ao **mount target**.
- O **Security Group do mount target** deve permitir entrada na 2049 **apenas do SG dos clientes** (referência SG-a-SG), não de `0.0.0.0/0`.
- O SG do cliente precisa permitir saída 2049 para o mount target.
- NACLs: lembrar de portas efêmeras de retorno.
- O EFS **não tem endereço público**: só é alcançável na VPC (ou via VPN/Direct Connect/peering/Transit Gateway). Veja [[8. DevOps e Gerenciamento de Infraestrutura/CLOUD COMPUTING/AWS (AMAZON WEB SERVICE)/3. Tecnologia e Serviços/3.3 Serviços principais da AWS/3.3.4. Rede/3.3.4.1. Amazon VPC/0 Amazon VPC (Tópicos )|Amazon VPC]].

```
 SG-app (clientes) ──TCP 2049──► SG-efs (mount target): regra de entrada "origem = SG-app"
```

## Camada 2 — Identidade: IAM e file system policy

Há dois tipos de política:

| Política | Onde fica | Para quê |
|---|---|---|
| **IAM identity-based** | Anexada ao usuário/role (instância, task) | O que o principal pode fazer (`elasticfilesystem:ClientMount`, `ClientWrite`, `ClientRootAccess`) |
| **File system (resource) policy** | No próprio EFS | Quem pode acessar o sistema de arquivos, exigir TLS, exigir IAM, restringir a Access Points |

Ações de cliente:

| Ação | Permite |
|---|---|
| `elasticfilesystem:ClientMount` | Montar o sistema de arquivos (leitura) |
| `elasticfilesystem:ClientWrite` | Escrever |
| `elasticfilesystem:ClientRootAccess` | Acessar como root |

Exemplo de **file system policy** exigindo TLS e negando acesso sem criptografia em trânsito:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "NegarSemTLS",
      "Effect": "Deny",
      "Principal": { "AWS": "*" },
      "Action": "*",
      "Resource": "arn:aws:elasticfilesystem:sa-east-1:111122223333:file-system/fs-0123abcd",
      "Condition": { "Bool": { "aws:SecureTransport": "false" } }
    },
    {
      "Sid": "PermitirRoleDaApp",
      "Effect": "Allow",
      "Principal": { "AWS": "arn:aws:iam::111122223333:role/app-ec2" },
      "Action": ["elasticfilesystem:ClientMount", "elasticfilesystem:ClientWrite"],
      "Resource": "arn:aws:elasticfilesystem:sa-east-1:111122223333:file-system/fs-0123abcd"
    }
  ]
}
```

```bash
aws efs put-file-system-policy --file-system-id fs-0123abcd --policy file://politica-efs.json
# Montar usando autorização IAM (requer o helper amazon-efs-utils e a opção iam)
sudo mount -t efs -o tls,iam fs-0123abcd:/ /mnt/efs
```

Sem política de recurso, o EFS permite acesso a qualquer cliente que alcance a rede (controlado só por SG e POSIX); **com** política, o IAM passa a valer.

## Camada 3 — Permissões POSIX

Dentro do sistema de arquivos valem **UID/GID e modos** (`rwx`) normais. Armadilha: **UIDs diferentes entre instâncias** causam "Permission denied" mesmo com o usuário "certo" em cada servidor. Por isso existem os Access Points.

---

## Access Points

Um **Access Point** é um ponto de entrada **específico por aplicação** que:

- **Impõe um diretório raiz** (a aplicação "enxerga" só `/app1`, como se fosse a raiz).
- **Impõe uma identidade POSIX** (UID/GID) a todas as operações, independente do usuário do cliente.
- **Cria o diretório** com dono e permissões na primeira vez (`CreationInfo`).
- Pode ser restringido por **IAM** (apenas certas roles usam determinado Access Point).

```
 Aplicação A ──► Access Point A  (raiz /apps/a, UID 1001) ──┐
 Aplicação B ──► Access Point B  (raiz /apps/b, UID 1002) ──┼──► mesmo EFS, isolamento lógico
 Lambda      ──► Access Point C  (raiz /lambda, UID 1003) ──┘
```

```bash
aws efs create-access-point --file-system-id fs-0123abcd \
  --posix-user Uid=1001,Gid=1001 \
  --root-directory 'Path=/apps/a,CreationInfo={OwnerUid=1001,OwnerGid=1001,Permissions=750}' \
  --tags Key=Name,Value=app-a

# Montar via Access Point
sudo mount -t efs -o tls,accesspoint=fsap-0abc123 fs-0123abcd:/ /mnt/app-a
```

Uso típico: **multi-tenant**, **Lambda** (exige Access Point), **ECS/EKS** com isolamento por serviço, e política de IAM que obriga `elasticfilesystem:AccessPointArn`.

## Criptografia

| Tipo | Como |
|---|---|
| **Em repouso** | Opção `--encrypted` **na criação** (não pode ser ativada depois); usa chave KMS (padrão `aws/elasticfilesystem` ou CMK). Para migrar um sistema não criptografado, crie um novo criptografado e copie (DataSync/AWS Backup/rsync). Veja a nota de AWS KMS. |
| **Em trânsito** | **TLS** via helper `amazon-efs-utils` (`-o tls`), que cria um túnel `stunnel` local; ou exigido por política (`aws:SecureTransport`) |

Observações:

- Criptografia em repouso tem impacto mínimo no desempenho.
- A chave KMS precisa permitir o uso pelo EFS e pelos clientes (grants).
- Sem `tls`, o tráfego NFS ao mount target dentro da VPC vai em claro; muitas políticas de conformidade exigem TLS.

## Acesso on-premises e multi-VPC

| Cenário | Como |
|---|---|
| Datacenter | VPN/Direct Connect + montar o IP do mount target (ou DNS via Route 53 Resolver) |
| Outra VPC | VPC peering ou Transit Gateway; resolver o DNS do EFS ou usar o IP do mount target |
| Outra conta | Compartilhar rede + file system policy permitindo a conta |

## Exemplo prático

Cenário: duas aplicações (ECS) compartilham o mesmo EFS com isolamento e criptografia.

1. EFS **criptografado** com CMK `alias/efs-prod`.
2. SG-efs aceita 2049 somente de SG-app-a e SG-app-b.
3. Dois Access Points (`/apps/a` UID 1001 e `/apps/b` UID 1002).
4. File system policy: nega `SecureTransport=false`; permite a role de A somente via AP-A, e a role de B somente via AP-B.
5. Task definitions com `transitEncryption=ENABLED`, `authorizationConfig` com `iam=ENABLED` e `accessPointId`.

```json
// efsVolumeConfiguration no ECS (ilustrativo)
{
  "fileSystemId": "fs-0123abcd",
  "transitEncryption": "ENABLED",
  "authorizationConfig": { "accessPointId": "fsap-0aaa111", "iam": "ENABLED" }
}
```

Resultado: A não consegue ler os dados de B, tudo trafega cifrado e as chaves/roles são auditáveis via CloudTrail.

## Modelo de decisão: quem controla o quê

| Camada | Controla | Ferramenta | Falha típica |
|---|---|---|---|
| Rede | Quem alcança a porta 2049 | Security Group do mount target, NACL | SG aberto demais ou fechado demais |
| Identidade | Quem pode montar/escrever/root | IAM (`elasticfilesystem:Client*`) + file system policy | Policy sem `ClientMount` |
| Arquivo | Quem lê/grava cada arquivo | Permissões POSIX (UID/GID) | UIDs diferentes entre instâncias |
| Entrada | Diretório raiz e identidade forçada | Access Points | Aplicação enxergando diretórios de outras |
| Dados | Confidencialidade | KMS (repouso) e TLS (trânsito) | Montar sem `tls` |

> [!warning] Valores, limites e preços mudam; os exemplos deste material não foram executados. Revise ações IAM e opções de montagem na documentação oficial.

```
 Cliente ──► (1) SG/NACL ──► (2) IAM + file system policy ──► (3) Access Point
                                                                   │ força UID/GID e raiz
                                                                   ▼
                                                    (4) POSIX no diretório ──► dados
                                      (5) TLS em trânsito  ·  (6) KMS em repouso
```

Cada camada nega por padrão: para um acesso ter sucesso, **todas** precisam permitir. Em troubleshooting, percorra-as na ordem acima.

## Padrão recomendado: um Access Point por aplicação

```
 /  (raiz do EFS)
 ├── /app-a   ◄── Access Point A (UID 1001, raiz /app-a)
 ├── /app-b   ◄── Access Point B (UID 1002, raiz /app-b)
 └── /shared  ◄── Access Point C (somente leitura via policy)
```

Com isso, mesmo que a aplicação A seja comprometida, ela enxerga `/app-a` como raiz e não consegue navegar para `/app-b`. Combine com uma file system policy que **negue** acesso sem TLS (`aws:SecureTransport = false`) e restrinja `ClientRootAccess`.

## CLI comentado

```bash
# Cria um access point com identidade POSIX forçada e diretório raiz próprio
aws efs create-access-point --file-system-id fs-0123456789abcdef0 \
  --posix-user Uid=1001,Gid=1001 \
  --root-directory 'Path=/app-a,CreationInfo={OwnerUid=1001,OwnerGid=1001,Permissions=750}'

# Aplica uma file system policy exigindo TLS
aws efs put-file-system-policy --file-system-id fs-0123456789abcdef0 \
  --policy file://policy-tls.json

# Monta via access point com IAM e TLS
sudo mount -t efs -o tls,iam,accesspoint=fsap-0abc123 fs-0123456789abcdef0:/ /mnt/app-a
```

## Troubleshooting

| Sintoma | Camada | Ação |
|---|---|---|
| Timeout no mount | Rede | SG com TCP 2049, NACL, mount target na AZ |
| `access denied by server` | IAM/policy | Conferir `ClientMount`/`ClientWrite` e a policy do recurso |
| Montou mas não grava | POSIX/Access Point | Revisar UID/GID e permissões do diretório |
| Falha com `-o iam` | Role | Instância sem role, ou sem credenciais disponíveis |
| Erro de TLS | Helper | Instalar `amazon-efs-utils`, stunnel/porta local livre |

## Custo

Segurança no EFS não tem tarifa própria, exceto a **chave KMS** gerenciada pelo cliente (custo mensal por chave e por requisição) e o tráfego entre AZs ou VPCs. Criptografar em repouso é obrigatório para novos sistemas pelo console e não adiciona custo de armazenamento. O custo real de segurança fraca aparece como incidente, não como fatura.

## Erros comuns e armadilhas

- **Security Group do mount target aberto à internet** (`0.0.0.0/0`): exposição desnecessária.
- **Esquecer a porta 2049** na regra de entrada.
- **Não criar o EFS criptografado:** não há como ligar depois.
- **Política de recurso com `Principal: *` sem condições.**
- **UID/GID divergentes** entre servidores: arquivos inacessíveis; use Access Points.
- **Access Point sem permissão IAM equivalente:** o mount falha com acesso negado.
- **Lambda sem Access Point** ou sem rede na VPC.
- **Montar sem `tls`** quando a política exige.
- **Chave KMS sem permissão** para a role: erro ao montar.
- **Confundir IAM com POSIX:** IAM autoriza montar/escrever; as permissões do arquivo ainda valem.

## 🧩 Quiz de Fixação

1. Quais camadas controlam o acesso a um arquivo no EFS?
2. Para que servem os Access Points?
3. É possível ativar a criptografia em repouso em um EFS existente?

**Respostas:**
1) Rede (Security Group na 2049), identidade (IAM e file system policy), permissões POSIX do arquivo, e opcionalmente Access Points; mais criptografia em repouso e em trânsito.
2) Impor diretório raiz e identidade POSIX por aplicação, isolando usuários/serviços no mesmo EFS, resolvendo divergência de UID/GID e sendo obrigatórios para Lambda.
3) Não. A criptografia em repouso só é definida na criação; para um sistema existente, crie um novo criptografado e copie os dados.

**Questões complementares:**

4. Por que usar um Access Point por aplicação?
5. Como exigir criptografia em trânsito de forma obrigatória?
6. Em que ordem diagnosticar um `access denied`?

**Respostas das questões complementares:**
4) Porque cada Access Point força uma identidade POSIX e um diretório raiz próprio, isolando aplicações: uma comprometida não navega para os dados das outras.
5) Com uma file system policy que nega acesso quando `aws:SecureTransport` é falso, junto com a montagem via helper usando a opção `tls`.
6) Da rede para o dado: Security Group/NACL, depois IAM e file system policy, depois Access Point, depois permissões POSIX, conferindo ainda TLS e KMS.
