### Classes de armazenamento, lifecycle, custo, backup e replicação do EFS

> [!warning] Aviso
> Nomes de classes, preços, períodos mínimos e recursos de proteção do EFS mudam. Nenhum valor numérico aqui é oficial. Confirme na documentação e na calculadora de preços. Os comandos **não foram executados**.

Como o EFS cobra pelo **volume armazenado** e por acesso, gerenciar **quais dados ficam em qual classe** é a principal alavanca de custo. Esta nota cobre as **classes de armazenamento**, as **políticas de lifecycle**, o **backup** e a **replicação** para resiliência e recuperação de desastres.

**Analogia:** é um **arquivo-morto de escritório**. Documentos usados todo dia ficam na mesa (Standard); os pouco consultados vão para o armário (Infrequent Access); os quase nunca consultados vão para o depósito (Archive). Um funcionário (lifecycle) faz a mudança automaticamente com base na última consulta.

## Classes de armazenamento

| Classe | Para quê | Custo de armazenamento | Cobrança de acesso |
|---|---|---|---|
| **Standard** | Dados acessados com frequência (multi-AZ) | Mais alto | Sem taxa por leitura além do throughput |
| **Infrequent Access (IA)** | Dados acessados ocasionalmente | Bem menor | **Taxa por GB lido/gravado** |
| **Archive** | Dados acessados poucas vezes ao ano | Ainda menor | Taxa de acesso maior; período mínimo de armazenamento |
| **One Zone Standard / One Zone-IA** | Versões de uma única AZ | Menor que Regional (~metade) | Igual às equivalentes |

Os dados em IA/Archive continuam **no mesmo sistema de arquivos e caminho**; a aplicação não percebe a mudança, apenas a latência do primeiro acesso é ligeiramente maior.

```
 Standard ──(30 dias sem acesso)──► IA ──(90 dias sem acesso)──► Archive
     ▲                               │                              │
     └────── acesso (opcional: volta para Standard) ◄───────────────┘
```

## Lifecycle management

Política por sistema de arquivos que move automaticamente arquivos **não acessados** entre classes:

| Transição | Parâmetros |
|---|---|
| **Para IA** | Após 1, 7, 14, 30, 60, 90... dias sem acesso (valores selecionáveis) |
| **Para Archive** | Após período configurável sem acesso (por exemplo 90+ dias) |
| **De volta para Standard** | `AFTER_1_ACCESS` (volta ao primeiro acesso) ou `None` (permanece em IA) |

```bash
# Mover arquivos para IA após 30 dias sem acesso, Archive após 90 e voltar ao Standard no primeiro acesso
aws efs put-lifecycle-configuration --file-system-id fs-0123abcd \
  --lifecycle-policies \
    TransitionToIA=AFTER_30_DAYS \
    TransitionToArchive=AFTER_90_DAYS \
    TransitionToPrimaryStorageClass=AFTER_1_ACCESS
# Os valores aceitos (AFTER_N_DAYS) são fixos; consulte a documentação para a lista atual

aws efs describe-lifecycle-configuration --file-system-id fs-0123abcd
```

Observações:

- Arquivos **menores que 128 KiB** não entram em IA (permanecem em Standard).
- Se o padrão de acesso for imprevisível, a volta para Standard ao primeiro acesso evita taxas repetidas de leitura em IA.
- A métrica `StorageBytes` (por classe) mostra a distribuição.

### Intelligent-Tiering (conceito)

Combinação das políticas de lifecycle e retorno ao primeiro acesso funciona como camadas inteligentes: dados quentes ficam em Standard; frios migram sozinhos.

## Custo — o que compõe a conta

| Item | Observação |
|---|---|
| **Armazenamento (GB-mês)** por classe | Principal componente |
| **Throughput** | Elastic: por GB transferido; Provisioned: MiB/s reservados; Bursting: incluído |
| **Acesso a IA/Archive** | Por GB lido/gravado |
| **Transferência entre AZs/regiões** | Replicação e acesso cross-AZ podem gerar custo |
| **Backup** | Armazenamento de backups (AWS Backup) |
| **Replicação** | Dados replicados e transferência |

Estratégias de redução:

1. **Lifecycle** agressivo para dados frios.
2. **One Zone** para dados recriáveis ou secundários.
3. **Elastic** (ou Bursting) para evitar throughput ocioso.
4. Limpar dados temporários e logs antigos.
5. Montar pelo mount target da **mesma AZ** do cliente.

## Backup

O EFS integra-se ao **AWS Backup** (backup automático habilitado por padrão em sistemas de arquivos criados pelo console, com política diária; confirme):

| Característica | Detalhe |
|---|---|
| **Incremental** | Backups incrementais após o primeiro completo |
| **Agendamento e retenção** | Planos do AWS Backup (diário, semanal, retenção em dias/anos) |
| **Restauração** | Para um **novo** sistema de arquivos, ou parcial (arquivos/diretórios específicos) |
| **Cópia entre regiões/contas** | Suportada pelo AWS Backup (inclusive cofres com Vault Lock) |
| **Consistência** | Ponto no tempo consistente |

```bash
# Habilitar o backup automático do EFS
aws efs put-backup-policy --file-system-id fs-0123abcd --backup-policy Status=ENABLED
aws efs describe-backup-policy --file-system-id fs-0123abcd
```

Detalhes de planos e cofres: nota do AWS Backup desta trilha (3.3.2.6).

## Replicação (EFS Replication)

Replica de forma **contínua e assíncrona** o sistema de arquivos para outra **região** (ou outra AZ via One Zone), mantendo uma cópia **somente leitura** no destino. Serve para **DR** com RPO tipicamente de minutos.

```
 Região A (origem)  ══ replicação assíncrona ══►  Região B (réplica, read-only)
                                              ▲
                                    em desastre: "promover" (excluir a replicação) e usar a réplica
```

```bash
aws efs create-replication-configuration --source-file-system-id fs-0123abcd \
  --destinations Region=us-east-1
# Cria o sistema de arquivos de destino automaticamente (somente leitura)

aws efs describe-replication-configurations --file-system-id fs-0123abcd
```

Pontos de atenção:

- A réplica é **somente leitura** até a replicação ser removida (failover).
- Para **failback** é preciso nova replicação na direção contrária.
- Há custo de armazenamento e transferência na região destino.
- Não substitui backup (corrupção/exclusão propaga para a réplica).

## RPO, RTO e escolha de estratégia

| Necessidade | Solução |
|---|---|
| Recuperar exclusão acidental de arquivos | **AWS Backup** (restauração parcial) |
| Sobreviver à perda de uma AZ | EFS **Regional** (nativo) |
| Sobreviver à perda de uma região | **Replicação** + runbook de failover |
| Reduzir custo de dados frios | **Lifecycle** (IA/Archive) |
| Proteger contra ransomware/exclusão maliciosa | Backup com **Vault Lock** e conta separada |

## Exemplo prático

Repositório de mídias de uma empresa (20 TB, 90% raramente acessado):

1. Criação **Regional**, throughput **Elastic**, criptografado.
2. Lifecycle: IA após 30 dias, Archive após 180, retorno a Standard no primeiro acesso.
3. Backup diário com retenção de 35 dias (AWS Backup) e cópia mensal para outra conta/região.
4. Replicação para outra região para DR do processo crítico, com runbook de failover testado trimestralmente.
5. Alarme de custo e acompanhamento de `StorageBytes` por classe.

## Erros comuns e armadilhas

- **Manter tudo em Standard** por não ter definido lifecycle.
- **Lifecycle sem retorno ao Standard** em dados que voltam a ser acessados: taxa de acesso IA repetida.
- **Esperar que arquivos pequenos (< 128 KiB) vão para IA.**
- **Tratar replicação como backup:** exclusões e corrupções também são replicadas.
- **Não testar a restauração** nem o failover da réplica.
- **Esquecer que a réplica é somente leitura.**
- **Archive para dados que ainda são acessados com frequência:** cobranças de acesso elevadas.
- **Desabilitar o backup automático** por engano e só perceber na hora do incidente.

## 🧩 Quiz de Fixação

1. O que faz a política de lifecycle do EFS e que dados ela não move?
2. Replicação do EFS substitui backup? Por quê?
3. Como reduzir custo de um EFS com muitos dados frios?

**Respostas:**
1) Move automaticamente arquivos não acessados por um período de Standard para IA e Archive (e pode retorná-los ao Standard no primeiro acesso). Arquivos menores que 128 KiB não são movidos para IA.
2) Não: a replicação é contínua, então exclusões acidentais e corrupções também são replicadas. O backup (AWS Backup) guarda pontos no tempo restauráveis.
3) Aplicando lifecycle para IA/Archive, escolhendo throughput Elastic/Bursting adequado, usando One Zone onde o risco for aceitável e removendo dados desnecessários.
