### O que é Amazon EFS — sistema de arquivos NFS elástico, mount targets, Regional vs One Zone e montagem em EC2, ECS e Lambda

> [!warning] Aviso
> Recursos, limites, preços e integrações do EFS mudam. Confirme na documentação. Os comandos **não foram executados**.

O **Amazon Elastic File System (EFS)** é um **sistema de arquivos de rede (NFS v4.0/4.1)** totalmente gerenciado, **elástico** (cresce e encolhe conforme você grava e apaga arquivos, sem provisionar capacidade) e **compartilhado**: milhares de clientes (EC2, contêineres, Lambda, servidores on-premises) podem montá-lo ao mesmo tempo. É voltado a **Linux** (não suporta Windows; para isso, veja o FSx for Windows File Server).

**Analogia:** se o EBS é um HD ligado a um computador, o EFS é a **pasta compartilhada do escritório**: todos acessam os mesmos arquivos ao mesmo tempo, e a "pasta" cresce sozinha conforme a equipe guarda coisas.

```
        VPC
  ┌─────────────────────────────────────────────────────────┐
  │ AZ-a: EC2 ─┐         AZ-b: EC2 ─┐        AZ-c: ECS ─┐   │
  │            ▼                    ▼                   ▼   │
  │      Mount target a       Mount target b      Mount target c   (ENIs com IP privado)
  │                \               |               /        │
  │                 └──────  EFS (Regional, multi-AZ)  ─────┘
  └─────────────────────────────────────────────────────────┘
```

## Características essenciais

| Característica | Detalhe |
|---|---|
| **Protocolo** | NFS 4.0 e 4.1; semântica POSIX (permissões, bloqueios de arquivo) |
| **Elasticidade** | Sem tamanho provisionado; você paga pelo que armazena |
| **Compartilhamento** | Vários clientes simultâneos, leitura e escrita |
| **Alta disponibilidade** | **Regional**: dados replicados em várias AZs; **One Zone**: uma AZ |
| **Durabilidade** | Muito alta (projeto de 11 noves no Regional; confirme) |
| **Integrações** | EC2, ECS, EKS (driver CSI), Fargate, Lambda, on-premises (VPN/Direct Connect) |
| **Sistema operacional** | Linux (amzn, Ubuntu, RHEL...) |
| **Escopo** | Regional, acessível dentro da VPC por **mount targets** |

---

## Regional × One Zone

| Critério | **Regional** (padrão recomendado) | **One Zone** |
|---|---|---|
| Disponibilidade | Multi-AZ, sobrevive à perda de uma AZ | Uma AZ; perda da AZ = indisponibilidade/risco de dados |
| Mount targets | Um por AZ | Um, na AZ escolhida |
| Custo | Maior | Cerca de **~47% menor** (ordem de grandeza; confirme) |
| Uso | Produção, dados importantes | Dev/test, dados recriáveis, cópias secundárias |

## Mount targets

Cada AZ onde você quer acessar o EFS precisa de um **mount target**: uma **ENI** com IP privado numa subnet, protegida por **Security Group** (liberando TCP 2049 de entrada). Clientes na mesma AZ usam o mount target local, evitando tráfego e custo entre AZs.

```
 Cliente ──TCP 2049──► Security Group do mount target ──► ENI (IP privado) ──► EFS
```

O nome DNS do sistema de arquivos (`fs-0123abcd.efs.sa-east-1.amazonaws.com`) resolve para o mount target **da AZ do cliente**.

## Montando o EFS

### Pelo utilitário `amazon-efs-utils` (recomendado)

```bash
# Em uma instância Amazon Linux (instalar o helper)
sudo yum install -y amazon-efs-utils

sudo mkdir -p /mnt/efs
# Montagem com TLS em trânsito (-o tls) usando o ID do sistema de arquivos
sudo mount -t efs -o tls fs-0123abcd:/ /mnt/efs

# Montagem persistente: /etc/fstab
echo 'fs-0123abcd:/ /mnt/efs efs _netdev,tls,noresvport 0 0' | sudo tee -a /etc/fstab
# _netdev: espera a rede; tls: criptografia em trânsito; noresvport: reconexão mais robusta
```

### Pelo cliente NFS padrão

```bash
sudo mount -t nfs4 -o nfsvers=4.1,rsize=1048576,wsize=1048576,hard,timeo=600,retrans=2,noresvport \
  fs-0123abcd.efs.sa-east-1.amazonaws.com:/ /mnt/efs
# Opções recomendadas pela AWS para throughput e resiliência; confira a documentação vigente
```

### Em contêineres e funções

| Plataforma | Como |
|---|---|
| **ECS (EC2 e Fargate)** | Volume do tipo EFS na task definition (`efsVolumeConfiguration`) |
| **EKS** | Driver **EFS CSI**, `PersistentVolume`/`StorageClass` |
| **Lambda** | Configuração de sistema de arquivos com **access point** (função na VPC) |
| **On-premises** | Montar via VPN/Direct Connect usando o IP do mount target |

```json
// Trecho da task definition do ECS (ilustrativo)
"volumes": [{
  "name": "dados-compartilhados",
  "efsVolumeConfiguration": {
    "fileSystemId": "fs-0123abcd",
    "transitEncryption": "ENABLED"
  }
}]
```

## Casos de uso

| Caso | Por quê EFS |
|---|---|
| **Conteúdo web compartilhado** (WordPress, uploads) entre várias instâncias | Mesmo diretório para todas |
| **Home directories** de usuários, ambientes de desenvolvimento | POSIX, permissões |
| **Contêineres com estado compartilhado** (ECS/EKS) | Volumes persistentes multi-AZ |
| **Machine learning / análises** com dataset compartilhado | Leitura concorrente |
| **Lambda com arquivos grandes/modelos** | Montagem do sistema de arquivos |
| **Migração de aplicações NFS** | Sem reescrever para S3 |

Quando não usar: banco de dados de alta performance (prefira EBS), objetos estáticos em larga escala sem semântica de arquivo (S3), Windows (FSx for Windows).

## Exemplo prático

```bash
# 1) Criar o sistema de arquivos Regional criptografado com throughput elástico
aws efs create-file-system \
  --creation-token app-compartilhada \
  --encrypted --performance-mode generalPurpose --throughput-mode elastic \
  --tags Key=Name,Value=app-compartilhada

# 2) Criar um mount target por AZ (subnet + Security Group que libera 2049)
aws efs create-mount-target --file-system-id fs-0123abcd \
  --subnet-id subnet-0aaa111 --security-groups sg-0efs123
aws efs create-mount-target --file-system-id fs-0123abcd \
  --subnet-id subnet-0bbb222 --security-groups sg-0efs123

# 3) Security Group do EFS: permitir TCP 2049 somente do SG das instâncias da aplicação
aws ec2 authorize-security-group-ingress --group-id sg-0efs123 \
  --protocol tcp --port 2049 --source-group sg-0app456

# 4) Verificar
aws efs describe-file-systems --file-system-id fs-0123abcd \
  --query 'FileSystems[0].{Estado:LifeCycleState,Tamanho:SizeInBytes.Value}'
aws efs describe-mount-targets --file-system-id fs-0123abcd
```

Explicação: duas instâncias em AZs diferentes montam o mesmo `fs-0123abcd` e enxergam os mesmos arquivos. Os mount targets precisam estar em estado `available` antes de montar.

## Escolhendo entre EFS, EBS, S3 e FSx

A dúvida mais comum não é "como montar o EFS", e sim "devo mesmo usar EFS aqui?". A tabela abaixo compara os quatro serviços de armazenamento que mais competem entre si.

| Critério | EFS | EBS | S3 | FSx (Windows/Lustre/ONTAP/OpenZFS) |
|---|---|---|---|---|
| Tipo | Arquivos (NFS) | Bloco | Objeto (HTTP) | Arquivos (SMB/NFS/Lustre) |
| Acesso simultâneo | Milhares de clientes, multi-AZ | 1 instância (Multi-Attach só io1/io2) | Ilimitado | Muitos clientes |
| Capacidade | Elástica, sem provisionar | Provisionada (GiB) | Ilimitada | Provisionada |
| Latência típica | Milissegundos baixos | Sub-milissegundo | Dezenas de ms | Sub-ms a ms |
| Sistema operacional | Linux (NFSv4.0/4.1) | Linux e Windows | Qualquer (via API) | Depende do tipo |
| Modelo de custo | Por GB-mês usado + throughput | Por GB provisionado + IOPS | Por GB usado + requisições | Por GB provisionado + throughput |

### Árvore de decisão

```
Preciso de armazenamento para minhas instâncias/containers?
│
├─ Só UMA instância usa os dados, precisa de baixa latência/IOPS?
│     └─ EBS
├─ Dados são objetos (imagens, logs, backups), acessados via API?
│     └─ S3
├─ Vários clientes Linux compartilham o MESMO diretório?
│     ├─ Crescimento imprevisível, sem administrar capacidade? ─► EFS
│     └─ Precisa de SMB/AD, ONTAP, ZFS ou Lustre? ──────────────► FSx
└─ Windows com SMB? ─► FSx for Windows File Server
```

## Topologia típica de um EFS Regional

```
                         VPC 10.0.0.0/16
 ┌───────────────────────────────────────────────────────────┐
 │  AZ-a                 AZ-b                 AZ-c           │
 │ ┌──────────┐        ┌──────────┐        ┌──────────┐      │
 │ │ EC2 / ECS│        │ EC2 / ECS│        │  Lambda  │      │
 │ └────┬─────┘        └────┬─────┘        └────┬─────┘      │
 │      │ NFS 2049          │ NFS 2049          │ NFS 2049   │
 │ ┌────▼─────┐        ┌────▼─────┐        ┌────▼─────┐      │
 │ │ Mount    │        │ Mount    │        │ Mount    │      │
 │ │ target   │        │ target   │        │ target   │      │
 │ │ (ENI+SG) │        │ (ENI+SG) │        │ (ENI+SG) │      │
 │ └────┬─────┘        └────┬─────┘        └────┬─────┘      │
 └──────┼───────────────────┼───────────────────┼────────────┘
        └───────────────────┼───────────────────┘
                  ┌─────────▼──────────┐
                  │  Sistema de        │
                  │  arquivos EFS      │
                  │  (dados replicados │
                  │   em ≥3 AZs)       │
                  └────────────────────┘
```

Repare que o dado existe **uma vez** (replicado pelo serviço), mas há **um ponto de entrada por AZ**. Isso explica por que um cliente na AZ-a deve usar o mount target da AZ-a: evita tráfego entre AZs e dependência de outra zona.

## Desempenho: modos e throughput

O EFS separa duas decisões independentes, definidas na criação (o modo de desempenho não pode ser alterado depois).

| Dimensão | Opções | Quando escolher |
|---|---|---|
| Performance mode | **General Purpose** (padrão) | Quase tudo: web, CMS, home dirs, CI |
| | **Max I/O** (legado, não recomendado para novos) | Paralelismo muito alto aceitando latência maior |
| Throughput mode | **Elastic** (recomendado) | Carga variável/imprevisível; paga pelo que transfere |
| | **Provisioned** | Carga previsível e constante com throughput alto vs. dados armazenados |
| | **Bursting** | Sistemas pequenos com picos ocasionais; throughput cresce com o tamanho |

> [!warning] Valores, limites e preços mudam; os exemplos deste material não foram executados. Confirme na documentação oficial e na calculadora de preços antes de decidir.

Regra prática: comece com **General Purpose + Elastic**. Só migre para Provisioned se o custo de Elastic ficar acima do de throughput provisionado numa carga estável, e meça antes com a métrica `PercentIOLimit` e `MeteredIOBytes` no CloudWatch.

## Troubleshooting de montagem

| Sintoma | Causa provável | Verificação / correção |
|---|---|---|
| `mount` trava e dá timeout | SG do mount target sem TCP 2049 de origem | Liberar 2049 a partir do SG do cliente; checar NACL |
| `Failed to resolve "fs-xxxx.efs..."` | DNS da VPC desativado ou AZ sem mount target | Habilitar `enableDnsSupport/Hostnames`; criar mount target na AZ |
| `access denied by server` | File system policy ou IAM negando | Revisar a policy; usar `-o iam` com role correta |
| Boot da instância demora | `fstab` sem `_netdev` | Adicionar `_netdev,nofail` |
| Lentidão em muitos arquivos pequenos | Latência por operação NFS | Usar cache local, agrupar I/O, avaliar EBS/FSx |
| Cliente Windows não monta | Windows não suporta NFS do EFS | Usar FSx for Windows File Server |

## Montagem com o helper oficial (CLI comentado)

```bash
# Instala o amazon-efs-utils (helper que habilita TLS e IAM)
sudo yum install -y amazon-efs-utils

# Cria o ponto de montagem local
sudo mkdir -p /mnt/efs

# Monta com TLS (criptografia em trânsito) usando o ID do sistema de arquivos
sudo mount -t efs -o tls fs-0123456789abcdef0:/ /mnt/efs

# Monta autenticando com a role IAM da instância
sudo mount -t efs -o tls,iam fs-0123456789abcdef0:/ /mnt/efs

# Entrada persistente no /etc/fstab (reboot-safe)
# fs-0123456789abcdef0:/ /mnt/efs efs _netdev,tls,nofail 0 0

# Confere o resultado e o tipo de montagem
df -hT /mnt/efs
mount | grep efs
```

## Estimando o custo

O custo do EFS tem três parcelas: **armazenamento** (GB-mês por classe), **throughput** (Elastic cobra por GB lido/escrito; Provisioned cobra o excedente do incluso) e **replicação/backup**, se ativados. Um erro frequente é comparar apenas o preço por GB do EFS Standard com o do EBS gp3 e concluir que o EFS é "muito caro": o EBS cobra pela capacidade **provisionada** (inclusive o espaço vazio), enquanto o EFS cobra só pelo **usado** e permite mover dados frios para IA/Archive via lifecycle.

Exemplo de raciocínio: 500 GB usados, dos quais 80% sem acesso há 30 dias. Com lifecycle para Infrequent Access, 400 GB passam a custar uma fração do Standard, e a conta cai de forma relevante sem tocar na aplicação.

## Erros comuns e armadilhas

- **Security Group sem TCP 2049:** `mount` trava por timeout.
- **Sem mount target na AZ do cliente:** tráfego entre AZs ou falha de resolução.
- **Esquecer `_netdev` no fstab:** instância demora/trava no boot esperando rede.
- **Usar EFS para banco de dados transacional:** latência maior que EBS.
- **Montar sem `tls`** quando a política exige criptografia em trânsito.
- **Espaço "ilimitado" sem controle:** custo cresce sem aviso; use lifecycle e monitore.
- **Acesso a partir de Windows:** não suportado.
- **Permissões POSIX/UID desencontradas** entre instâncias: arquivos inacessíveis (use Access Points).
- **One Zone em produção crítica:** perda da AZ afeta o serviço.

## 🧩 Quiz de Fixação

1. Qual a principal diferença entre EBS e EFS quanto a compartilhamento?
2. Para que servem os mount targets e que porta usam?
3. Quando escolher EFS One Zone?

**Respostas:**
1) O EBS é um volume de bloco normalmente anexado a uma instância (mesma AZ); o EFS é um sistema de arquivos NFS que milhares de clientes de várias AZs montam e usam ao mesmo tempo.
2) São as ENIs (uma por AZ) que expõem o EFS na VPC; protegidas por Security Group liberando **TCP 2049** (NFS).
3) Para dev/test, dados recriáveis ou cópias secundárias, onde o menor custo compensa o risco de perda ou indisponibilidade da única AZ.

**Questões complementares:**

4. Por que o cliente deve preferir o mount target da própria AZ?
5. Qual combinação de modos de desempenho/throughput é o ponto de partida recomendado e por quê?
6. Por que comparar o preço por GB do EFS com o do EBS pode enganar?

**Respostas das questões complementares:**
4) Evita tráfego entre AZs (latência e custo de transferência) e elimina a dependência de outra zona: se a AZ vizinha cair, o cliente continua acessando o EFS pelo seu próprio ponto de entrada.
5) **General Purpose + Elastic**: General Purpose atende quase todas as cargas com baixa latência, e Elastic ajusta o throughput automaticamente, cobrando só o que for transferido; só vale migrar para Provisioned se a carga for estável e o custo ficar menor.
6) Porque o EBS cobra a capacidade provisionada (inclusive espaço vazio) e vive em uma AZ, enquanto o EFS cobra apenas o usado, é multi-AZ, compartilhável e permite mover dados frios para classes mais baratas; a comparação justa considera uso real, compartilhamento e lifecycle.
