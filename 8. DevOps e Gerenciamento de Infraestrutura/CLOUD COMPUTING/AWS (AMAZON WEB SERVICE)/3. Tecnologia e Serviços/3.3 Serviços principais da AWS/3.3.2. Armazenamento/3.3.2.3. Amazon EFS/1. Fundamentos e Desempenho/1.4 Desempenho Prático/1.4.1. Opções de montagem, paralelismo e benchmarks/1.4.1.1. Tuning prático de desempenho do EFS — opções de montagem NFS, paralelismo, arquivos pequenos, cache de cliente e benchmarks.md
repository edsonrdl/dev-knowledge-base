### Tuning prático de desempenho do EFS — opções de montagem NFS, paralelismo, arquivos pequenos, cache de cliente e benchmarks

> [!warning] Aviso
> Limites de throughput e IOPS do EFS, recomendações de opções de montagem e comportamento de modos de throughput mudam. Os números são **ordens de grandeza**. **Teste com a sua carga real.** Os comandos **não foram executados**; benchmarks de escrita **consomem throughput e custam dinheiro** (modo Elastic cobra por GB transferido).

Na nota de desempenho vimos os *modos* (General Purpose/Max I/O e Elastic/Provisioned/Bursting). Aqui tratamos do **lado do cliente**: como **configurar a montagem**, como **gerar paralelismo suficiente**, por que **arquivos pequenos** doem, como funciona o **cache NFS**, como **medir** com `fio`/`rsync`/`dd` e como **diagnosticar** o gargalo. A maior parte da "lentidão do EFS" vem de **uso inadequado** (um thread, muitos arquivos minúsculos, cache desligado), não do serviço.

**Analogia:** o EFS é uma **rodovia de várias pistas, com pedágio a cada carro**. Se você manda **um carro por vez** (single thread), cada viagem espera o pedágio; se manda **muitos carros em paralelo**, a rodovia flui. E levar um piano em **mil viagens de caixinha** (arquivos pequenos) custa muito mais que em **uma viagem de caminhão**.

## Por que o EFS tem latência diferente do disco local

```
 Aplicação ─► kernel/NFS client ─► rede (TCP 2049, mesma AZ) ─► mount target ─► EFS (replicação síncrona em várias AZs)
   cada operação = ida e volta de rede + durabilidade multi-AZ  →  latência por operação em ~ms (leitura ~0,5-3 ms; escrita com fsync maior)
```

| Característica | Consequência |
|---|---|
| **Latência por operação** na ordem de milissegundos | Cargas sequenciais "um por vez" são lentas; **paralelismo** compensa |
| **Escrita durável multi-AZ** | `fsync` e escritas síncronas custam mais |
| **Metadados** (criar, abrir, `stat`, listar) | Cada um é uma operação de rede: milhões de arquivos pequenos = muitas operações |
| **Throughput agregado alto** | Escala com **número de clientes e threads** |
| **Cache NFS do cliente** | Reduz idas à rede para leituras repetidas (com semântica *close-to-open*) |

Resumo: o EFS é excelente em **vazão agregada paralela**; ruim para **cargas intensas de uma única thread com metadados** (ex.: `git clone`, `npm install`, builds com milhares de arquivos).

## Opções de montagem recomendadas

| Opção | Efeito | Observação |
|---|---|---|
| `nfsvers=4.1` | Protocolo moderno | Padrão recomendado |
| `rsize=1048576,wsize=1048576` | Blocos de 1 MiB | Maior throughput sequencial |
| `hard` | Retenta indefinidamente | Evita corrupção; evite `soft` |
| `timeo=600,retrans=2` | Tempo de espera/tentativas | Valores recomendados |
| `noresvport` | Nova porta de origem ao reconectar | Resiliência |
| `tls` (helper) | Criptografia em trânsito | Adiciona leve overhead de CPU (stunnel/proxy) |
| `noatime` | Não atualiza tempo de acesso | Menos operações de metadados |
| `lookupcache=positive` | Cache apenas de lookups positivos | Reduz consultas, com cuidado em cargas multi-cliente |
| `actimeo=N` | Tempo de cache de atributos | Maior = menos operações, menos coerência entre clientes |
| `nconnect=N` | Várias conexões TCP por montagem | Pode aumentar throughput em kernels recentes (validar) |

Nunca use `async` para ganhar velocidade em dados importantes sem entender o risco; o cache do cliente é seguro para leituras, mas escritas dependem de `close()`/`fsync()`.

## Paralelismo: como gerar vazão

| Técnica | Como |
|---|---|
| **Vários threads/processos** | Dividir o trabalho (arquivos, faixas de bytes) em N workers; cada um gera I/O concorrente |
| **I/O assíncrono / filas** | `libaio`, `io_uring`, `--iodepth` > 1 |
| **Vários clientes** | Mais instâncias/pods lendo/escrevendo em paralelo (EFS escala horizontalmente) |
| **Ferramentas paralelas** | `fpsync` (fpart+rsync), `parallel`, `s5cmd`-like, `xargs -P`, `cp` em lotes paralelos, `tar` paralelo |
| **Lotes grandes** | Operações com 1 MiB+ em vez de bytes/KB |
| **Evitar chamadas síncronas desnecessárias** | Reduzir `fsync` frequente |

```bash
# Copiar muitos arquivos em paralelo (16 processos) para o EFS
find /origem -type f -print0 | xargs -0 -n 200 -P 16 cp --parents -t /mnt/efs/destino/

# rsync paralelo por subdiretório
ls /origem | xargs -P 8 -I{} rsync -a /origem/{} /mnt/efs/destino/
```

## Arquivos pequenos e metadados

| Problema | Solução |
|---|---|
| **Milhões de arquivos minúsculos** (cache de gerenciador de pacotes, thumbnails) | Mantenha em **disco local/EBS** e use o EFS para dados compartilhados; **empacote** (tar/zip, squashfs, arquivos agregados) |
| **Diretórios gigantes** (milhões de entradas) | Hierarquia de subdiretórios (hash de nome) |
| **Listagens frequentes** (`ls -l`, `find`) | Evite em caminhos quentes; índice externo |
| **Builds/CI** | Cache de dependências local; EFS só para artefatos |
| **Git** | Repositórios em disco local |
| **Bancos de dados** | Não use EFS (prefira EBS/RDS) |
| **Aplicações PHP/WordPress** | Cache de opcode e de página (OPcache, CDN); código no disco local/imagem, **uploads** no EFS |

## Cache do cliente e coerência

- O cliente NFS armazena em cache **atributos** e **dados**. Coerência **close-to-open**: ao abrir um arquivo, o cliente verifica se mudou desde o último `close` de outro cliente.
- **Atributos** (`acregmin/acregmax`, `acdirmin/acdirmax`, `actimeo`): reduzem chamadas `GETATTR`; aumentam a janela em que um cliente vê dados "antigos" de outro.
- Para **múltiplos clientes escrevendo e lendo o mesmo arquivo**, use **bloqueios** (`flock`/`fcntl`) ou desenhe para evitar contenção; o NFS 4.1 suporta bloqueios.
- **Cache de aplicação** (OPcache, CDN, memória) reduz a dependência do EFS.

## Benchmarks (`fio`, `dd`, `rsync`)

Sempre meça com **paralelismo realista** e em **diretório de teste dedicado**.

```bash
# Throughput de escrita sequencial, 8 jobs, 1 MiB, 60 s (consome cota/custa no modo Elastic)
fio --name=escrita-seq --directory=/mnt/efs/benchmark --rw=write --bs=1M --size=2G --numjobs=8 \
    --iodepth=16 --ioengine=libaio --direct=1 --runtime=60 --time_based --group_reporting
# Leitura sequencial
fio --name=leitura-seq --directory=/mnt/efs/benchmark --rw=read --bs=1M --size=2G --numjobs=8 \
    --iodepth=16 --ioengine=libaio --direct=1 --runtime=60 --time_based --group_reporting
# IOPS aleatório 4k (pequenos I/Os)
fio --name=rand4k --directory=/mnt/efs/benchmark --rw=randrw --rwmixread=70 --bs=4k --size=1G --numjobs=16 \
    --iodepth=8 --ioengine=libaio --direct=1 --runtime=60 --time_based --group_reporting
# Latência de metadados: criar 10.000 arquivos pequenos
time bash -c 'for i in $(seq 1 10000); do : > /mnt/efs/benchmark/f$i; done'
```

Leitura dos resultados:

| Métrica | Interpretação |
|---|---|
| **BW (MiB/s)** | Compare com o limite do modo de throughput e da instância (rede) |
| **IOPS** | Para I/O pequeno; EFS depende do paralelismo |
| **clat p99** | Latência de cauda |
| **Tempo de criação de arquivos** | Indicador de metadados |

Cheque ainda a **banda de rede** da instância (a rede da instância limita) e `PercentIOLimit`/`PermittedThroughput`/`BurstCreditBalance` do EFS no CloudWatch durante o teste.

## Diagnóstico de lentidão

```
1. Qual operação é lenta? (leitura/escrita grande, metadados, listagem, abrir muitos arquivos)
2. Quantos threads/processos/clientes? (QD baixo = pouco throughput)
3. Opções de montagem corretas? (nfsvers=4.1, rsize/wsize 1 MiB, hard, noresvport)
4. Limites de rede da instância/Fargate? (bytes por segundo)
5. Modo de throughput: créditos de Bursting acabaram? Provisioned abaixo da necessidade? Elastic limitado?
6. Arquivos minúsculos? Diretórios enormes? Cache de atributos?
7. Mesma AZ do mount target? (tráfego entre AZs aumenta latência)
8. TLS (stunnel) saturando CPU em instâncias pequenas?
9. Mudança pequena → medir de novo
```

| Sintoma | Causa provável | Ação |
|---|---|---|
| Throughput baixo com um processo | Pouco paralelismo | Mais threads/processos; `fpsync` |
| Latência alta de `ls`/`find` | Diretório gigante/metadados | Hierarquia, índice externo, evitar |
| Lentidão após dias (Bursting) | Créditos acabaram | Mudar para Elastic/Provisioned |
| `PercentIOLimit` ≈ 100% | Limite de I/O do General Purpose | Reduzir pressão, paralelismo moderado, avaliar Max I/O (sem ganho garantido) |
| Cliente em outra AZ | Latência extra e custo | Montar via mount target da própria AZ |
| CPU alta no cliente com TLS | Overhead do stunnel | Instância maior ou reavaliar TLS (políticas) |
| Falhas/travamentos após queda de rede | `soft`, sem `noresvport` | `hard,noresvport` |
| Builds lentos | Muitos arquivos pequenos | Cache local; empacotar |

## Exemplo prático

Um pipeline de processamento de imagens grava 2 milhões de miniaturas (20 KB) e leva 9 horas:

1. **Diagnóstico:** processo único gravando um arquivo por vez; metadados dominam (`create`+`write`+`close` por arquivo); `PercentIOLimit` baixo — o gargalo é a **latência por operação**, não o throughput.
2. **Mudanças:**
   - Paralelismo: 64 workers (4 instâncias × 16 processos).
   - Diretórios sharded por hash (`/thumbs/ab/cd/arquivo.jpg`) para evitar diretórios gigantes.
   - Montagem com `noatime`, `rsize/wsize=1M`, `hard`, `noresvport`, mesma AZ do mount target.
   - Para o conjunto de miniaturas "frias", empacotar em arquivos agregados diários (`.tar`) e gravar no S3, deixando só as quentes no EFS.
3. **Resultado:** 9 h → 55 min; `PermittedThroughput` suficiente em Elastic; custo menor ao reduzir leituras repetidas.
4. **Medição contínua:** alarme em `PercentIOLimit` e em `ClientConnections`; `fio` trimestral como baseline.

## Erros comuns e armadilhas

- **Teste de desempenho com um único thread** e concluir que o EFS é lento.
- **Bancos de dados e repositórios Git no EFS.**
- **Arquivos minúsculos aos milhões** sem empacotamento nem sharding de diretórios.
- **`soft` mount** ou ausência de `noresvport`.
- **Ignorar a banda de rede** da instância/tarefa.
- **Esquecer que Bursting esgota créditos** com pouco armazenamento.
- **Benchmark em produção** sem medir impacto/custo.
- **Cache de atributos agressivo** (`actimeo` alto) em cargas multi-cliente que exigem coerência.
- **Cliente em AZ diferente do mount target.**
- **Comparar com EBS** sem considerar o modelo de rede e durabilidade multi-AZ.

## 🧩 Quiz de Fixação

1. Por que o EFS tem mais latência por operação que um disco local e como compensar?
2. Quais as opções de montagem recomendadas para NFS no EFS?
3. Por que milhões de arquivos pequenos prejudicam o desempenho e o que fazer?
4. Como identificar se o gargalo é o EFS, a rede ou a aplicação?

**Respostas:**
1) Porque cada operação atravessa a rede e a escrita é durável em várias AZs; compensa-se com paralelismo (threads, processos, clientes), blocos grandes e menos chamadas síncronas.
2) `nfsvers=4.1`, `rsize/wsize=1048576`, `hard`, `timeo=600`, `retrans=2` e `noresvport` (e `noatime`/TLS conforme o caso).
3) Cada arquivo implica várias operações de metadados em rede; mitiga-se empacotando arquivos, distribuindo em subdiretórios, usando cache/disco local para o que é pequeno e frequente e paralelizando.
4) Comparando o throughput obtido com o limite do EFS (`PermittedThroughput`, `PercentIOLimit`, créditos), com a banda da instância (rede) e com o paralelismo da aplicação; testando com `fio` multi-thread para ver o teto do serviço.
