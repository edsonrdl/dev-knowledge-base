### EFS com EC2, ECS, EKS, Lambda e on-premises — montagem, helper, driver CSI, Access Points, rede, DNS e migração de dados com DataSync

> [!warning] Aviso
> Versões de agentes (amazon-efs-utils, driver CSI), opções de montagem recomendadas, suporte de plataformas e limites mudam. Os exemplos são **ilustrativos e não foram executados**. **Confirme na documentação do EFS e do driver.**

O EFS só entrega valor quando é **montado de forma correta e resiliente** pelas plataformas de computação. Cada uma tem seu modo: **EC2** (helper `amazon-efs-utils` ou NFS padrão), **ECS** (volume EFS na task definition), **EKS** (driver **EFS CSI**, com PersistentVolumes e Access Points), **Lambda** (configuração de sistema de arquivos com Access Point) e **on-premises** (via VPN/Direct Connect). Esta nota apresenta cada cenário, as **opções de rede e DNS** (inclusive multi-VPC e multi-conta) e a **migração de dados** para o EFS com **AWS DataSync**.

**Analogia:** o EFS é uma **pasta compartilhada na nuvem**. Montá-lo é **mapear a unidade de rede** em cada computador: no escritório (EC2), em contêineres (ECS/EKS), em funções efêmeras (Lambda) e em filiais distantes (on-premises), cada um com seu "jeito de mapear".

## Pré-requisitos de rede (comuns a todas as plataformas)

| Item | Detalhe |
|---|---|
| **Mount target por AZ** | Uma ENI por AZ onde há clientes; o cliente usa o mount target da própria AZ |
| **Security Group do mount target** | Entrada TCP **2049** do SG dos clientes |
| **Security Group do cliente** | Saída 2049 para o mount target |
| **Subnets/Rotas** | Cliente na mesma VPC, ou via peering/Transit Gateway/VPN/Direct Connect |
| **DNS** | `fs-xxxx.efs.região.amazonaws.com` resolve para o mount target da **AZ do cliente** (requer DNS e hostnames habilitados na VPC) |
| **Nome por AZ** | `az.fs-xxxx.efs.região.amazonaws.com` fixa o mount target de uma AZ específica |
| **Entre VPCs/contas** | Peering/TGW + resolução do nome (Route 53 Resolver, hosts) ou uso do IP do mount target |

## EC2 (Linux)

### Helper `amazon-efs-utils` (recomendado)

```bash
sudo yum install -y amazon-efs-utils            # Amazon Linux/RHEL; Ubuntu: construir a partir do repositório
sudo mkdir -p /mnt/efs
sudo mount -t efs -o tls,iam fs-0123abcd:/ /mnt/efs                 # TLS e autorização IAM (opcional)
sudo mount -t efs -o tls,accesspoint=fsap-0abc123 fs-0123abcd:/ /mnt/app   # via Access Point
# fstab
echo 'fs-0123abcd:/ /mnt/efs efs _netdev,tls,noresvport 0 0' | sudo tee -a /etc/fstab
```

O helper: cria o **túnel TLS** (stunnel/proxy), resolve o nome de forma resiliente (monta por AZ), aplica opções recomendadas e permite **IAM + Access Points**. Verifique com `df -h`, `mount | grep efs`.

### Cliente NFS padrão (sem helper)

```bash
sudo mount -t nfs4 -o nfsvers=4.1,rsize=1048576,wsize=1048576,hard,timeo=600,retrans=2,noresvport \
  fs-0123abcd.efs.sa-east-1.amazonaws.com:/ /mnt/efs
```

| Opção | Por quê |
|---|---|
| `nfsvers=4.1` | Protocolo recomendado |
| `rsize/wsize=1048576` | Blocos de 1 MiB (maior throughput) |
| `hard` | O cliente retenta indefinidamente (evita corrupção por timeouts); aplicações bloqueiam durante falhas |
| `timeo=600,retrans=2` | Tempo de espera e tentativas |
| `noresvport` | Nova porta de origem ao reconectar (resiliência após falha) |
| `_netdev` (fstab) | Espera a rede |

### Boas práticas EC2

1. Montar no **boot** via `fstab` ou user data, com `_netdev` e `nofail` conforme necessidade.
2. Usar **IAM + TLS** em ambientes regulados.
3. **UID/GID consistentes** entre instâncias ou usar Access Points.
4. Não montar EFS em instâncias sem mount target na AZ.
5. Windows **não é suportado** (use FSx for Windows File Server).

## ECS (EC2 e Fargate)

```json
// Task definition (trecho): volume EFS com Access Point e IAM
"volumes": [{
  "name": "dados",
  "efsVolumeConfiguration": {
    "fileSystemId": "fs-0123abcd",
    "transitEncryption": "ENABLED",
    "authorizationConfig": { "accessPointId": "fsap-0abc123", "iam": "ENABLED" }
  }
}],
"containerDefinitions": [{ "name": "app", "image": "...", "mountPoints": [{ "sourceVolume": "dados", "containerPath": "/dados" }] }]
```

| Item | Detalhe |
|---|---|
| **Fargate** | Plataforma 1.4.0+ suporta EFS; sem acesso ao host; use Access Points para identidade POSIX |
| **EC2 launch type** | O agente ECS monta o volume; pode também montar no host |
| **Permissão** | A **task role** precisa de `elasticfilesystem:ClientMount/ClientWrite` quando `iam=ENABLED` |
| **Segurança de rede** | SG da task acessa 2049 do mount target |
| **Casos** | WordPress/CMS (uploads), compartilhamento entre tasks, caches de build, ML |

## EKS (driver EFS CSI)

O **Amazon EFS CSI Driver** permite que pods usem EFS como **PersistentVolume** (`ReadWriteMany`).

```yaml
# StorageClass com provisionamento dinâmico via Access Points
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata: { name: efs-sc }
provisioner: efs.csi.aws.com
parameters:
  provisioningMode: efs-ap
  fileSystemId: fs-0123abcd
  directoryPerms: "700"
  basePath: "/dinamico"
---
apiVersion: v1
kind: PersistentVolumeClaim
metadata: { name: compartilhado }
spec:
  accessModes: [ReadWriteMany]
  storageClassName: efs-sc
  resources: { requests: { storage: 5Gi } }      # valor simbólico: o EFS é elástico (sem limite real)
```

| Item | Detalhe |
|---|---|
| **Driver** | Add-on do EKS (`aws-efs-csi-driver`) com IRSA/Pod Identity (permissões `elasticfilesystem:*` necessárias para provisionamento dinâmico) |
| **Modos** | Estático (PV apontando para um Access Point/diretório) ou dinâmico (um Access Point por PVC) |
| **ReadWriteMany** | Principal vantagem sobre EBS (RWO) |
| **Limites** | Número de Access Points por sistema de arquivos (milhares, ajustável) |
| **Fargate no EKS** | Suporta EFS |
| **Boas práticas** | Um Access Point por aplicação; `uid/gid` fixos; observar desempenho de muitos arquivos pequenos |

## Lambda

| Requisito | Detalhe |
|---|---|
| **VPC** | A função precisa estar em subnets da VPC com mount target alcançável |
| **Access Point** | Obrigatório; define diretório e identidade POSIX |
| **Caminho local** | `/mnt/dados` (deve começar com `/mnt/`) |
| **IAM** | Role da função com `elasticfilesystem:ClientMount/ClientWrite` (se política exigir IAM) |
| **Casos** | Modelos de ML grandes, bibliotecas/dados que excedem o limite de pacote, processamento de arquivos compartilhados |
| **Atenção** | Latência de rede; cold start maior; throughput limitado por função; concorrência alta pode saturar o EFS |

```bash
aws lambda update-function-configuration --function-name processa-docs \
  --file-system-configs Arn=arn:aws:elasticfilesystem:sa-east-1:111122223333:access-point/fsap-0abc123,LocalMountPath=/mnt/dados
```

## On-premises e multi-VPC

| Cenário | Como |
|---|---|
| **Datacenter** | VPN ou Direct Connect para a VPC; montar por **IP do mount target** (ou DNS via **Route 53 Resolver inbound endpoint**); mesmas opções NFS; `amazon-efs-utils` também funciona on-premises |
| **Outra VPC (mesma conta)** | Peering ou Transit Gateway; resolver o nome (Resolver/hosts) ou IP; SG do mount target permite o CIDR/SG do cliente |
| **Outra conta** | Compartilhar rede (RAM/peering) + **política do sistema de arquivos** autorizando a conta/role; Access Points |
| **Outra região** | Preferir **replicação do EFS** para a região e montar localmente; montar através de regiões tem alta latência |
| **Desempenho** | A latência de rede afeta diretamente a experiência; evite para cargas sensíveis |

## Migração de dados para o EFS (AWS DataSync)

O **DataSync** copia dados de forma **rápida, incremental e verificada** de NFS/SMB/S3/HDFS/FSx para o EFS (e vice-versa), preservando metadados POSIX.

```
 Origem (NFS on-premises) ──[Agente DataSync]──► DataSync (gerenciado) ──► EFS (mount target na VPC)
```

| Etapa | Detalhe |
|---|---|
| **Agente** | VM/EC2 perto da origem (para on-premises) |
| **Locais** | `create-location-nfs` (origem), `create-location-efs` (destino) |
| **Tarefa** | Configurações: verificação, preservar `uid/gid`/permissões/timestamps, filtros, agendamento |
| **Incremental** | Copia só o que mudou (permite sincronizações repetidas até o corte) |
| **Desempenho** | Paralelismo, até 10 Gbps por agente (valores indicativos); limites de banda configuráveis |
| **Custo** | Por GB copiado |

```bash
aws datasync create-location-efs --efs-filesystem-arn arn:aws:elasticfilesystem:sa-east-1:111122223333:file-system/fs-0123abcd \
  --ec2-config SubnetArn=arn:aws:ec2:sa-east-1:111122223333:subnet/subnet-0aaa,SecurityGroupArns=arn:aws:ec2:sa-east-1:111122223333:security-group/sg-0efs
aws datasync create-task --source-location-arn $ORIGEM --destination-location-arn $DESTINO --name nas-para-efs \
  --options VerifyMode=ONLY_FILES_TRANSFERRED,PosixPermissions=PRESERVE,Uid=INT_VALUE,Gid=INT_VALUE
aws datasync start-task-execution --task-arn $TASK
```

Alternativas: `rsync` (pequenos volumes), **Storage Gateway**, **Transfer Family** (SFTP→EFS), Snow Family (grandes volumes offline), ou **AWS Backup/replicação** entre EFS.

Estratégia de corte: sincronização inicial → sincronizações incrementais → janela: parar escritas, última sincronização, validar, trocar o ponto de montagem das aplicações.

## Exemplo prático

Aplicação web em ECS Fargate + job de ML no EKS + backoffice on-premises compartilhando um mesmo EFS:

1. **EFS** Regional criptografado, throughput Elastic, mount targets nas 3 AZs; SG aceitando 2049 dos SGs de Fargate, EKS e do CIDR da VPN.
2. **Access Points**: `/web` (uid 1001), `/ml` (uid 2001), `/backoffice` (uid 3001); política do sistema de arquivos exigindo TLS e autorizando roles por Access Point.
3. **Fargate:** volume EFS na task definition com `accessPointId` do `/web` e IAM ativado.
4. **EKS:** add-on EFS CSI; StorageClass dinâmica por Access Point para jobs de ML (`ReadWriteMany`).
5. **On-premises:** servidores do backoffice montam com `amazon-efs-utils` pelo Direct Connect, usando o Access Point `/backoffice` e o DNS via Route 53 Resolver inbound.
6. **Migração:** DataSync do NAS legado (4 TB) para `/backoffice`, com sincronizações noturnas por 2 semanas e corte em fim de semana.
7. **Operação:** alarmes de `PercentIOLimit` e `BurstCreditBalance` (se aplicável), verificação de `df`, testes de failover de AZ.

## Erros comuns e armadilhas

- **Security Group sem 2049** (montagem trava).
- **DNS/hostnames desabilitados** na VPC: o nome do EFS não resolve.
- **Montar através de regiões** esperando baixa latência.
- **Sem `_netdev`** no `fstab` (boot trava).
- **Usar `soft`** em NFS: risco de corrupção por timeouts (prefira `hard`).
- **UIDs divergentes** sem Access Points.
- **Lambda sem Access Point** ou fora da VPC.
- **EKS com PV estático sem Access Point** e permissões POSIX erradas.
- **Workloads com milhões de arquivos pequenos** esperando latência de disco local.
- **Migração sem sincronização incremental** nem validação.
- **Montar EFS em Windows.**

## 🧩 Quiz de Fixação

1. Qual a diferença de usar `amazon-efs-utils` e o cliente NFS padrão?
2. O que é necessário para a Lambda usar EFS?
3. Qual a principal vantagem do EFS CSI sobre EBS no EKS?
4. Como migrar um NAS on-premises para o EFS com baixo downtime?

**Respostas:**
1) O helper simplifica TLS em trânsito, resolve o mount target por AZ, aplica opções recomendadas e suporta IAM e Access Points; o cliente NFS padrão exige configurar tudo manualmente (opções, sem TLS nativo).
2) A função deve estar na VPC com acesso ao mount target, usar um Access Point, ter o caminho de montagem em `/mnt/...` e uma role com as permissões do EFS quando a política exigir IAM.
3) O modo ReadWriteMany: vários pods em nós diferentes e AZs diferentes usam o mesmo volume ao mesmo tempo, o que o EBS (ReadWriteOnce) não permite.
4) Com o DataSync: sincronização inicial e incrementais até o corte, quando se param as escritas, faz-se a última sincronização, valida-se e troca-se o ponto de montagem para o EFS.
