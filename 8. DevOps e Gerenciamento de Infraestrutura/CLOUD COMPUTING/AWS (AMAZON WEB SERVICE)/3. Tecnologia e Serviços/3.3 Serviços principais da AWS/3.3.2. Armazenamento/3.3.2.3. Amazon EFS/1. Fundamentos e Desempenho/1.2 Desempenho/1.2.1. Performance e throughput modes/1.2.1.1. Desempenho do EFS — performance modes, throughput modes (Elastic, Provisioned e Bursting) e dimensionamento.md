### Desempenho do EFS — performance modes, throughput modes (Elastic, Provisioned e Bursting) e dimensionamento

> [!warning] Aviso
> Modos disponíveis, limites de IOPS/throughput, preços e recomendações mudam (a AWS vem simplificando as opções). Confirme na documentação. Os comandos **não foram executados**.

O desempenho do EFS tem duas dimensões configuráveis: o **performance mode** (perfil de latência × paralelismo) e o **throughput mode** (como a vazão é obtida e cobrada). Escolher bem evita pagar demais ou ter gargalos inesperados.

**Analogia:** o EFS é uma **rodovia compartilhada**. O *performance mode* define o tipo de pista (mais rápida para poucos carros ou larga para muitos). O *throughput mode* define como o **pedágio** é cobrado: pelo que você usa (Elastic), por uma faixa reservada (Provisioned) ou por créditos proporcionais ao patrimônio que você guarda (Bursting).

## Performance modes

| Modo | Característica | Quando |
|---|---|---|
| **General Purpose** (padrão e recomendado) | Menor latência por operação | Sites, CMS, home dirs, ambientes dev, a maioria dos casos |
| **Max I/O** | Maior paralelismo agregado (muitos clientes), porém **latência maior**; modo de geração anterior, com restrições com certos recursos | Workloads massivamente paralelos (milhares de clientes); avalie se é necessário, pois em muitos casos General Purpose + Elastic basta |

O performance mode é definido **na criação** e **não pode ser alterado** depois.

---

## Throughput modes

| Modo | Como funciona | Cobrança | Quando |
|---|---|---|---|
| **Elastic** (recomendado) | Escala sozinho para cima e para baixo conforme a demanda; sem planejamento | Por GB lido e gravado (pay per use) | Cargas **imprevisíveis ou espaçadas** (picos) |
| **Provisioned** | Você reserva um throughput fixo (MiB/s), independente do tamanho armazenado | Pelo throughput provisionado acima do que o armazenamento daria | Throughput previsível e alto com pouco dado armazenado |
| **Bursting** | Throughput **base proporcional ao tamanho armazenado**, com créditos para burst | Incluído no preço do armazenamento | Cargas com pico curto e média baixa; datasets grandes |

```
 Bursting:    base = f(tamanho armazenado)  + créditos de burst   → pouco dado = base baixa
 Provisioned: base = valor reservado        (independente do tamanho)
 Elastic:     sem base fixa; escala automaticamente até limites altos (e paga por uso)
```

Dica: **Elastic** é a escolha-padrão moderna. **Bursting** pode "secar" os créditos e derrubar o desempenho; **Provisioned** serve quando o uso é constante e alto.

## Fatores que afetam o desempenho

| Fator | Efeito |
|---|---|
| **Tamanho do I/O** | Operações maiores (≥ 1 MiB) aumentam o throughput; muitos arquivos pequenos aumentam a latência por operação (metadados) |
| **Paralelismo** | Mais threads/clientes → maior vazão agregada; o EFS escala horizontalmente |
| **Latência de rede** | Latência por operação de ~ms; cada leitura/escrita atravessa a rede |
| **Cache do cliente** | NFS faz cache de atributos e dados; ajustes de montagem alteram o comportamento |
| **Mesma AZ** | Montar pelo mount target da AZ local reduz latência e custo |
| **Instância/rede** | O limite de banda de rede da instância também limita a vazão |
| **Opções de montagem** | `rsize/wsize` de 1 MiB, `hard`, `noresvport` recomendados |

### Padrões de acesso

- **Muitos arquivos pequenos** (ex.: `node_modules`, builds): mais lento que em disco local; use cache local ou EBS/S3 quando o padrão for intensivo em metadados.
- **Leitura de grandes arquivos em paralelo**: ponto forte do EFS.
- **Operações `fsync` frequentes** adicionam latência (durabilidade síncrona entre AZs).

## Monitoramento

| Métrica (CloudWatch, `AWS/EFS`) | Uso |
|---|---|
| `PercentIOLimit` | Proximidade do limite de I/O (General Purpose); perto de 100% indica gargalo |
| `BurstCreditBalance` | Créditos restantes (Bursting); em queda contínua exige mudar de modo |
| `PermittedThroughput` | Throughput permitido atualmente |
| `MeteredIOBytes`, `DataReadIOBytes`, `DataWriteIOBytes` | Volume de I/O |
| `ClientConnections` | Clientes conectados |
| `TotalIOBytes` | Total de bytes de I/O |

Alarmes úteis: `BurstCreditBalance` baixo, `PercentIOLimit` > 80%.

## Mudando o modo de throughput

O throughput mode **pode ser alterado** (com limites de frequência), por exemplo de Bursting para Elastic quando o desempenho começa a sofrer; o performance mode, não.

```bash
# Migrar de Bursting para Elastic
aws efs update-file-system --file-system-id fs-0123abcd --throughput-mode elastic

# Provisionar 200 MiB/s fixos
aws efs update-file-system --file-system-id fs-0123abcd \
  --throughput-mode provisioned --provisioned-throughput-in-mibps 200

# Consultar a configuração e as métricas
aws efs describe-file-systems --file-system-id fs-0123abcd \
  --query 'FileSystems[0].{Perf:PerformanceMode,Thr:ThroughputMode,Prov:ProvisionedThroughputInMibps}'
aws cloudwatch get-metric-statistics --namespace AWS/EFS --metric-name BurstCreditBalance \
  --dimensions Name=FileSystemId,Value=fs-0123abcd \
  --start-time 2026-11-05T00:00:00Z --end-time 2026-11-06T00:00:00Z \
  --period 3600 --statistics Minimum
```

## Como escolher

```
Carga imprevisível ou espaçada, quer simplicidade?        ──► Elastic
Throughput alto e constante, pouco dado armazenado?        ──► Provisioned
Dataset grande, picos curtos, média baixa, custo mínimo?   ──► Bursting
Latência baixa na maioria dos casos?                       ──► General Purpose
Milhares de clientes em paralelo (avaliar necessidade)?    ──► Max I/O
```

## Exemplo prático

Um site WordPress com EFS para `wp-content` apresentou lentidão nos picos de campanha.

1. Métrica `BurstCreditBalance` chegou a quase zero: o modo Bursting esgotou créditos (o EFS tem poucos GB, base baixa).
2. Decisão: migrar para **Elastic** (picos pontuais, média baixa). Custo sob demanda por GB transferido.
3. Complemento: cache de página/objetos (CloudFront e cache do WordPress) reduz leituras no EFS.
4. Alarme em `PercentIOLimit` e `PermittedThroughput` para acompanhar.

## Dimensionando o EFS na prática

```
 Cliente (EC2/ECS/Lambda) ──NFS 4.1 (TCP 2049)──► Mount target (1 por AZ) ──► EFS (dados replicados em várias AZs)
 Throughput total = soma das conexões; muitos clientes em paralelo escalam melhor que um único cliente com uma thread.
```

| Padrão de carga | Throughput mode sugerido | Observação |
|---|---|---|
| Picos imprevisíveis, uso geral | **Elastic** | Escala sozinho; paga pelo que transfere |
| Throughput alto e constante | **Provisioned** ou Elastic | Compare o custo por MB/s |
| Carga pequena com picos curtos | **Bursting** | Créditos acumulados pelo tamanho armazenado |
| Latência mínima por operação | Performance mode **General Purpose** | É o padrão recomendado |

> [!warning] Modos disponíveis, limites de throughput e preços mudam; confirme na documentação atual.

## Regras práticas de desempenho

| Fator | Impacto | Ação |
|---|---|---|
| Número de threads/clientes | Throughput agregado sobe com paralelismo | Use `fpsync`, `parallel`, múltiplas conexões |
| Tamanho das operações | Arquivos pequenos são dominados por latência | Agrupe escritas, use buffers maiores |
| Metadados (listar, abrir muitos arquivos) | Limita operações por segundo | Evite diretórios com milhões de entradas |
| Montagem | Opções erradas reduzem desempenho | Use o `amazon-efs-utils` e `_netdev,tls` |
| Latência entre AZ | Cliente em AZ sem mount target local paga latência | Monte pelo mount target da própria AZ |

### Exemplo de CLI (comentado, não executado)

```bash
# Montar com o helper oficial (TLS em trânsito e IAM, se configurado)
sudo yum install -y amazon-efs-utils
sudo mount -t efs -o tls,iam fs-0123456789abcdef0:/ /mnt/efs
# Trocar para throughput Elastic
aws efs update-file-system --file-system-id fs-0123456789abcdef0 --throughput-mode elastic
# Observar consumo para decidir o modo
aws cloudwatch get-metric-statistics --namespace AWS/EFS --metric-name MeteredIOBytes \
  --dimensions Name=FileSystemId,Value=fs-0123456789abcdef0 --period 300 --statistics Sum \
  --start-time 2026-01-01T00:00:00Z --end-time 2026-01-02T00:00:00Z
```

## Diagnóstico de lentidão

| Sintoma | Causa provável | Ação |
|---|---|---|
| Queda abrupta de throughput | Créditos de burst esgotados (modo Bursting) | Migrar para Elastic ou Provisioned |
| `ls` demora minutos | Diretório gigante / metadados | Reestruturar diretórios |
| Aplicação single-thread lenta | Pouco paralelismo | Aumentar threads/processos |
| Picos de `PercentIOLimit` | Chegou ao teto do performance mode | Revisar o modo e distribuir carga |

## Custo

- Armazenamento por GB-mês conforme a classe (Standard, IA, Archive), mais acessos e, em Elastic/Provisioned, throughput.
- Lifecycle management move arquivos frios para IA/Archive e reduz o custo de armazenamento.
- Para dados raramente acessados, avalie S3 em vez de EFS.

---

## Erros comuns e armadilhas

- **Manter Bursting com pouco dado:** base baixa e créditos acabam; desempenho cai sem aviso.
- **Provisionar throughput acima da necessidade:** paga por capacidade ociosa.
- **Escolher Max I/O por reflexo:** latência maior e restrições sem ganho real.
- **Testar desempenho com arquivos pequenos e tirar conclusões** para cargas de arquivos grandes (e vice-versa).
- **Ignorar o limite de rede da instância.**
- **Esperar desempenho de disco local** em operações intensivas de metadados.
- **Mudar de modo repetidamente:** há janela mínima entre alterações.

## 🧩 Quiz de Fixação

1. Qual a diferença entre performance mode e throughput mode, e qual deles pode ser alterado depois?
2. Por que um EFS pequeno em modo Bursting pode ficar lento?
3. Quando usar Provisioned em vez de Elastic?

**Respostas:**
1) *Performance mode* (General Purpose ou Max I/O) define o perfil de latência/paralelismo e é fixo na criação. *Throughput mode* (Elastic, Provisioned, Bursting) define como a vazão é obtida/cobrada e pode ser alterado.
2) No Bursting o throughput base é proporcional ao tamanho armazenado; com pouco dado a base é baixa e, ao esgotar os créditos de burst, o desempenho cai.
3) Quando o throughput é previsível, alto e constante, e provisionar uma taxa fixa sai mais barato ou garante o mínimo necessário; para cargas variáveis, Elastic é mais simples.

### Questões de aprofundamento

4. O throughput do EFS em Bursting caiu de repente. Qual a causa mais provável?
5. Por que aumentar threads melhora o desempenho no EFS?
6. Como reduzir o custo de armazenamento sem apagar dados?

**Respostas:**
4) Esgotamento dos créditos de burst; migre para Elastic ou Provisioned.
5) Porque o EFS escala o throughput agregado com o paralelismo; uma única thread fica limitada pela latência por operação.
6) Habilitando o lifecycle management para mover arquivos frios para IA ou Archive.
