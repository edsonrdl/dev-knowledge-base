### AWS Backup por serviço — como EC2, EBS, RDS, Aurora, DynamoDB, S3, EFS, FSx e VMware são protegidos e restaurados, backup contínuo e particularidades

> [!warning] Aviso
> A matriz de recursos do AWS Backup por serviço (backup contínuo, cold storage, cópia entre contas e regiões, restauração parcial, camada de armazenamento) **muda com frequência** e há diferenças por região. **Consulte sempre a página "Feature availability by resource" na documentação.** Os comandos e JSONs **não foram executados**; restaurações **criam recursos novos e geram custo**.

O AWS Backup é um orquestrador: por baixo, ele usa os mecanismos **nativos de cada serviço** (snapshots do EBS, backups do RDS, backups do DynamoDB, versionamento do S3…), mas com **planos, cofres, retenção e auditoria unificados**. O que muda de serviço para serviço é **o que é capturado**, **como é restaurado**, **se há backup contínuo (PITR)**, **se aceita cold storage** e **quais armadilhas** existem. Esta nota é o mapa por serviço — um guia para planejar cada plano e cada teste de restauração.

**Analogia:** o AWS Backup é uma **central de seguros** que cobre casas, carros e joias. A apólice (plano) é uma só, mas cada bem tem sua própria perícia: o carro é fotografado por fora, a casa por dentro, a joia tem avaliação especial — e **a indenização (restauração) também depende do tipo de bem**.

## Visão geral por serviço

| Serviço | O que o backup captura | Contínuo (PITR) | Cold storage | Restauração cria... |
|---|---|---|---|---|
| **EC2** | **AMI** + snapshots dos volumes EBS + metadados da instância | Não | Camada Archive de snapshots (conforme suporte) | **Nova instância** (via AMI) ou só AMI/volumes |
| **EBS** | Snapshot do volume | Não | Archive (conforme suporte) | **Novo volume** |
| **RDS** | Snapshot do banco (ou backup automático gerenciado) | **Sim** (até 35 dias) | Não | **Nova instância** |
| **Aurora** | Snapshot do cluster | **Sim** | Não | **Novo cluster** |
| **DynamoDB** | Backup da tabela (com "advanced features": cópia entre regiões/contas, cold storage, tags) | **Sim** (PITR) | **Sim** (advanced) | **Nova tabela** |
| **S3** | Objetos e metadados (versionados) | **Sim** (contínuo) e periódico | Não | **Objetos em bucket** (existente ou novo) |
| **EFS** | Sistema de arquivos incremental | Não | **Sim** | **Novo sistema** ou **restauração parcial** |
| **FSx** (Windows, ONTAP, OpenZFS, Lustre persistent) | Backup do sistema de arquivos/volume | Não | Conforme sabor | **Novo sistema/volume** |
| **Storage Gateway (Volume)** | Snapshot do volume | Não | — | **Volume** |
| **DocumentDB / Neptune** | Snapshot do cluster | **Sim** | Não | **Novo cluster** |
| **Redshift / Serverless** | Snapshot do cluster / recovery points | Automático | Não | **Novo cluster/namespace** |
| **VMware (on-premises, via Backup gateway)** | VM inteira (disco + configuração) | Não | **Sim** | **VM** (no VMware ou como EC2/AMI) |
| **CloudFormation** | Pilha (stack) e recursos suportados | Não | — | **Nova stack** |
| **SAP HANA em EC2** | Backup do banco (Backint) | Log backups | — | Restauração no HANA |
| **Timestream, Aurora DSQL e outros** | Conforme suporte vigente | Varia | Varia | Varia |

(A tabela é um guia; confirme linha a linha na documentação.)

## Amazon EC2 e EBS

| Tema | Detalhe |
|---|---|
| **O que é protegido** | Todos os volumes anexados (raiz e dados), a configuração (tipo, SG, tags, perfil IAM, user data) e a AMI |
| **Consistência** | Por padrão, *crash-consistent*; para **consistência de aplicação** no Windows use o **agente/VSS** (opção "Windows VSS" na regra) |
| **Vários volumes** | Snapshots tirados juntos (grupo) para consistência entre discos |
| **Restauração** | `start-restore-job` com metadados: tipo de instância, VPC/subnet, SG, par de chaves, IAM; restauração de **volume único** também possível |
| **Cold storage** | Snapshots podem ir à camada Archive após N dias (retenção mínima de 90 dias) |
| **Cuidados** | A restauração **não é in-place**; recriação de IP elástico, ENIs e registros DNS é por sua conta; volumes criptografados exigem chave KMS acessível |

```bash
aws backup get-recovery-point-restore-metadata --backup-vault-name prod-vault --recovery-point-arn $RP_EC2
aws backup start-restore-job --recovery-point-arn $RP_EC2 --iam-role-arn $ROLE --resource-type EC2 --metadata '{
  "InstanceType":"m6i.large","SubnetId":"subnet-0aaa111","SecurityGroupIds":"[\"sg-0app123\"]","IamInstanceProfileName":"app-profile","DisableApiTermination":"true"}'
```

## Amazon RDS e Aurora

| Tema | Detalhe |
|---|---|
| **Snapshots** | Criados pelo plano (nomeados com prefixo `awsbackup:`); independentes dos backups automáticos do RDS |
| **Backup contínuo (PITR)** | No RDS/Aurora, habilite "continuous backup" na regra (retenção até 35 dias): restaura para **qualquer segundo** |
| **Backups automáticos do RDS** | Se já existem, o AWS Backup pode **gerenciar** os automáticos (verifique o modo) |
| **Cópia entre contas/regiões** | Suportada (snapshots compartilhados; chave KMS compartilhada) |
| **Restauração** | **Nova instância/cluster** com novo endpoint; reassociar parameter group, SG, subnet group, monitoramento |
| **Cuidados** | Parâmetros e opções não "voltam" sozinhos; recriar réplicas; atualizar a aplicação |

## Amazon DynamoDB

| Tema | Detalhe |
|---|---|
| **Backup básico** | On-demand via AWS Backup; **ativar "advanced DynamoDB backup features"** na conta/região para ganhar cópia entre regiões/contas, cold storage, tags e uso de regras de cofre |
| **PITR** | O AWS Backup oferece backup contínuo (PITR) por regra |
| **Restauração** | **Nova tabela**; índices opcionais; reconfigurar auto scaling, TTL, Streams, IAM, alarmes |
| **Sem impacto** | Não consome capacidade |
| **Cuidados** | Tabelas globais: backups por réplica; throughput de restauração |

## Amazon S3

O backup de S3 protege **objetos** com versionamento, em dois modos:

| Modo | Característica |
|---|---|
| **Contínuo** | PITR dos objetos (até 35 dias): restaura o bucket/prefixo para qualquer ponto do tempo |
| **Periódico** | Pontos de recuperação agendados |

| Tema | Detalhe |
|---|---|
| **Pré-requisito** | **Versionamento** habilitado no bucket e (para os modos) uma role com permissões; EventBridge habilitado nos modos contínuos (conforme documentação) |
| **Escopo** | Bucket inteiro ou filtrado por **prefixos** e/ou **tags de objeto** |
| **Criptografia** | SSE-S3 e SSE-KMS (chave acessível ao serviço) |
| **Restauração** | Para o **mesmo bucket** (opcionalmente com versões restauradas) ou **outro bucket**; restaura todos os objetos, um prefixo ou subconjunto |
| **Classes** | Objetos em Glacier precisam estar restauráveis; classes suportadas variam |
| **Cuidados** | Custo por objeto (milhões de objetos pequenos); a proteção cobre exclusão e sobrescrita acidental, não substitui **replicação** (CRR) nem **Object Lock** |
| **Bucket policy** | Não deve bloquear o serviço |

Compare com **versionamento + CRR + Object Lock** do S3 (veja a nota de segurança e proteção do S3): o AWS Backup acrescenta **plano central, retenção, auditoria e restauração em ponto no tempo**.

## Amazon EFS e FSx

| Serviço | Detalhe |
|---|---|
| **EFS** | Backups **incrementais**; **restauração completa** (novo sistema) ou **parcial** (arquivos/diretórios); suporta **cold storage**; backups automáticos podem ser gerenciados pelo AWS Backup; criptografia herdada |
| **FSx for Windows** | Backups do sistema de arquivos (inclui shadow copies? não: são separados); restauração para **novo** sistema; cópia entre regiões |
| **FSx for ONTAP** | Backups de **volume**; restauração para novo volume |
| **FSx for OpenZFS** | Backups de volume/sistema; restauração para novo |
| **FSx for Lustre** | **Somente Persistent** (Scratch não suporta); em HPC a fonte é o S3 |

## VMware e híbrido

O **AWS Backup gateway** (appliance virtual no vCenter) protege **VMs VMware** on-premises (e VMware Cloud on AWS) para a AWS:

```
 vCenter / ESXi ──[Backup gateway (VM)]──► AWS Backup (cofre) ──► restaurar como VM, ou como EC2 (AMI)
```

| Tema | Detalhe |
|---|---|
| **Instalação** | OVA do gateway; ativação; descoberta de VMs |
| **Backup** | Incremental (CBT), por VM ou etiquetas; suporte a cold storage |
| **Restauração** | Para o VMware (original/outro host) ou migração a EC2 |
| **Rede** | Conectividade para o endpoint do AWS Backup (HTTPS), Direct Connect/VPN |
| **Casos** | Backup híbrido, DR de VMs, aposentar infra de backup local |

## Restauração: boas práticas por serviço

1. Sempre use **`get-recovery-point-restore-metadata`** para ver os parâmetros que pode sobrescrever.
2. **Mantenha IaC** para recursos ao redor (SG, subnets, parameter groups, IAM, DNS): a restauração recria o dado, não a topologia.
3. **Teste por tipo de recurso** (um EC2, um RDS, uma tabela, um bucket, um EFS) com o **restore testing** do AWS Backup.
4. **Valide dados** (contagem, checksums, smoke tests da aplicação) antes de trocar o tráfego.
5. **Tempo de restauração** varia: EBS (minutos, lazy loading), RDS (dezenas de minutos a horas), DynamoDB (minutos a horas), S3 (proporcional ao número de objetos), EFS (proporcional ao tamanho); registre os valores reais.
6. **Chaves KMS** e **roles** devem existir/estar permitidas no destino.
7. **Custos**: restaurar cria recursos cobrados; apague os de teste.

```bash
aws backup list-recovery-points-by-backup-vault --backup-vault-name prod-vault --by-resource-type RDS \
  --query 'RecoveryPoints[].{Arn:RecoveryPointArn,Recurso:ResourceArn,Criado:CreationDate,Estado:Status}'
aws backup start-restore-job --recovery-point-arn $RP_S3 --iam-role-arn $ROLE --resource-type S3 --metadata '{
  "DestinationBucketName":"meu-bucket-restaurado","NewBucket":"false","Encrypted":"false","CreationToken":"rst-001"}'
aws backup describe-restore-job --restore-job-id $JOB
```

## Matriz de decisão: nativo × AWS Backup

| Necessidade | Use |
|---|---|
| Política central, auditoria, cópia entre contas/regiões, imutabilidade | **AWS Backup** |
| Recuperação rápida e granular dentro do serviço (shadow copies, snapshots ZFS/ONTAP, PITR do DynamoDB) | Recursos **nativos** (e AWS Backup para a camada de retenção) |
| Um único serviço e equipe pequena | Nativo pode bastar |
| Conformidade (WORM, Vault Lock, relatórios) | AWS Backup |
| Backup lógico / migração entre engines | Ferramentas do engine (dump, DMS) |

## Exemplo prático

Plano único para uma aplicação com EC2, RDS, DynamoDB, EFS e S3:

1. **Tags** `Backup=critico` em todos os recursos; seleção por tag no plano `app-critica`.
2. **Regras:** (a) contínua (RDS e S3, 35 dias) + (b) diária (EC2/EBS, EFS, DynamoDB, 35 dias, copiada para a conta bunker) + (c) mensal com cold storage (EFS/DynamoDB) por 7 anos.
3. **EC2:** Windows VSS ligado nos servidores de aplicação; AMI + volumes; restauração testada para a instância e para um volume.
4. **RDS:** PITR habilitado; teste de restauração ao minuto anterior a um erro simulado.
5. **S3:** versionamento + backup contínuo no bucket de documentos; teste de restaurar um prefixo para outro bucket.
6. **EFS:** restauração parcial de um diretório testada.
7. **Restore testing** semanal rotacionando um recurso por tipo; relatório no Audit Manager; tempos registrados no runbook.
8. **Resultado:** RTO real medido por tipo (EBS 12 min, RDS 48 min, DynamoDB 25 min, S3 prefixo 31 min, EFS diretório 9 min); lacunas encontradas (SG da instância restaurada, parameter group) corrigidas no IaC.

## Erros comuns e armadilhas

- **Assumir que todo serviço tem backup contínuo** ou cold storage.
- **S3 sem versionamento** ao configurar o backup.
- **Não ativar "advanced DynamoDB backup"** e perder cópia entre contas e cold storage.
- **EC2 sem consistência de aplicação** em bancos/Windows.
- **Restaurar e esquecer** a topologia (SG, DNS, IP elástico, parameter groups).
- **Chave KMS inacessível** no destino.
- **Não testar** cada tipo de recurso.
- **Selecionar recursos por ARN fixo** e deixar novos recursos sem proteção (prefira tags/políticas).
- **FSx for Lustre scratch** esperando backup.
- **Confiar em cold storage** sem considerar retenção mínima e tempo de restauração.
- **Duplicar mecanismos** (DLM + AWS Backup no mesmo recurso).

## 🧩 Quiz de Fixação

1. Que serviços do AWS Backup oferecem backup contínuo (PITR) e o que isso significa?
2. O que a restauração de um recurso cria e o que costuma ser esquecido?
3. Qual o pré-requisito para fazer backup de um bucket S3?
4. Como o AWS Backup protege VMs VMware on-premises?

**Respostas:**
1) RDS, Aurora, S3 e DynamoDB (e outros, conforme suporte): permite restaurar para qualquer segundo dentro da janela (até 35 dias), reduzindo o RPO a segundos.
2) Um recurso novo (instância, cluster, tabela, volume, sistema de arquivos ou objetos em bucket); costuma-se esquecer a topologia ao redor (SG, DNS, parameter groups, IAM, IP elástico, auto scaling, alarmes).
3) Versionamento habilitado no bucket (além de uma role com as permissões e a configuração do modo contínuo ou periódico).
4) Com o AWS Backup gateway, um appliance virtual no vCenter que faz backups incrementais das VMs para o cofre, com restauração no VMware ou como EC2.
