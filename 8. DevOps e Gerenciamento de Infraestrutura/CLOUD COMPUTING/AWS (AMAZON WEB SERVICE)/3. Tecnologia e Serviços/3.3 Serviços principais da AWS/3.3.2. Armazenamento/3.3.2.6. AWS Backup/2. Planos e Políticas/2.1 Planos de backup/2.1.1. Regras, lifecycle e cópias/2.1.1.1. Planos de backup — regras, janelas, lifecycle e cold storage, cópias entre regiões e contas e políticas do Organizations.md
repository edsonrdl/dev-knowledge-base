### Planos de backup — regras, janelas, lifecycle e cold storage, cópias entre regiões e contas e políticas do Organizations

> [!warning] Aviso
> Valores mínimos de retenção, regras de cold storage, suporte a backup contínuo por serviço e preços mudam. Confirme na documentação. Os JSONs e comandos **não foram executados**.

Um **plano de backup** é onde você transforma requisitos de negócio (**RPO**, retenção, conformidade) em configuração. Esta nota aprofunda as **regras**, **janelas**, **lifecycle**, **cold storage**, **cópias entre regiões e contas** e as **políticas de backup do AWS Organizations** para governar muitas contas.

**Analogia:** o plano é o **calendário de manutenção** do prédio: para cada sistema (regra), define o dia/hora, quanto tempo guardar o registro, quando mandar a papelada antiga para o arquivo morto e se uma cópia vai para outro prédio.

## Anatomia de uma regra

| Campo | Função | Dicas |
|---|---|---|
| **Schedule** | Cron/rate (ex.: `cron(0 3 * * ? *)` = 03:00 UTC diário) | Em UTC; escolha horário de baixa carga |
| **Start within** | Janela para o job *iniciar* | Padrão 1 h; aumente se há muitos recursos |
| **Complete within** | Janela para o job *concluir* | Padrão 7 dias; defina conforme o tamanho do recurso |
| **Backup vault** | Destino | Um por ambiente/sensibilidade |
| **Lifecycle** | Mover para cold storage após N dias; excluir após N dias | Cold exige retenção mínima (confirme) |
| **Continuous backup** | PITR (se suportado) | Retenção até 35 dias |
| **Copy actions** | Cópia para outro vault (região/conta) com lifecycle próprio | Base da estratégia de DR |
| **Tags nos recovery points** | Propagar tags do recurso | Custo/FinOps |
| **Windows VSS** | Snapshots consistentes para Windows (EC2) | Requer agente |

```
 Plano "critico"
   Regra A: contínuo (PITR 35 dias)              → vault "prod"
   Regra B: diária 03:00, retenção 35 dias        → vault "prod"
   Regra C: semanal dom 04:00, cold em 30 d, expira 7 anos → vault "prod" + cópia p/ conta "bunker"
```

Podem existir **várias regras no mesmo plano**, com RPO e retenção diferentes (padrão avô-pai-filho).

## Lifecycle e cold storage

| Estágio | Característica |
|---|---|
| **Warm** | Armazenamento padrão; restauração mais rápida e mais cara por GB |
| **Cold** | Armazenamento barato para retenção longa; só para serviços/tipos suportados (EFS, DynamoDB, VMware, SAP HANA, S3 etc., conforme lista vigente); exige período mínimo (por exemplo 90 dias) |
| **Expiração** | O recovery point é excluído automaticamente |

Regras práticas:

- Tempo em warm + cold respeita o mínimo exigido do cold (a regra "excluir após" ≥ "mover para cold" + mínimo).
- Nem todo recurso suporta cold; EBS, por exemplo, usa a camada Archive de snapshots em alguns casos.
- Aplicar lifecycle depois de criado afeta backups futuros e pode afetar os existentes conforme a configuração.

```bash
# Lifecycle de exemplo dentro de uma regra
"Lifecycle": { "MoveToColdStorageAfterDays": 30, "DeleteAfterDays": 2555 }
# 2555 dias ≈ 7 anos de retenção; cold após 30 dias (se o tipo de recurso suportar)
```

## Cópias entre regiões e contas

```
 Conta de produção (sa-east-1)           Conta "bunker" (us-east-1, outra conta)
   vault "prod"  ──copy action──────────►  vault "bunker"   (mesma organização)
   (recovery points)                         ↑ política do vault permite a conta de origem copiar
```

| Cenário | Requisitos |
|---|---|
| **Entre regiões (mesma conta)** | Vault de destino na outra região; chave KMS do destino |
| **Entre contas (mesma Organization)** | Habilitar *cross-account backup* na Organization; **política de acesso no vault de destino** permitindo a conta de origem; chave KMS compartilhada |
| **Isolamento forte** | Conta separada, com permissões mínimas, sem acesso administrativo de produção (proteção contra comprometimento) |

Boa prática 3-2-1 na AWS: **3** cópias (original + backup + cópia), **2** locais lógicos (região/conta), **1** isolada e imutável (vault lock/air-gapped).

## Políticas de backup do AWS Organizations

Permitem definir **um plano na conta de gerenciamento** (ou administrador delegado) e **aplicá-lo automaticamente** a OUs/contas.

```json
{
  "plans": {
    "padrao-org": {
      "regions": { "@@assign": ["sa-east-1"] },
      "rules": {
        "diaria": {
          "schedule_expression": { "@@assign": "cron(0 3 * * ? *)" },
          "target_backup_vault_name": { "@@assign": "org-vault" },
          "lifecycle": { "delete_after_days": { "@@assign": "35" } },
          "copy_actions": {
            "arn:aws:backup:us-east-1:{{account_id}}:backup-vault:org-dr": {
              "target_backup_vault_arn": { "@@assign": "arn:aws:backup:us-east-1:{{account_id}}:backup-vault:org-dr" },
              "lifecycle": { "delete_after_days": { "@@assign": "90" } }
            }
          }
        }
      },
      "selections": {
        "tags": {
          "por-tag": {
            "iam_role_arn": { "@@assign": "arn:aws:iam::$account:role/OrgBackupRole" },
            "tag_key": { "@@assign": "Backup" },
            "tag_value": { "@@assign": ["diario"] }
          }
        }
      }
    }
  }
}
```

Efeitos: contas-membro recebem o plano (somente leitura para elas), com vault e role que **precisam existir** em cada conta. Combine com SCPs que impeçam desabilitar o serviço. Veja a base em [[8. DevOps e Gerenciamento de Infraestrutura/CLOUD COMPUTING/AWS (AMAZON WEB SERVICE)/2. Segurança e Conformidade/2.3 Capacidades de gerenciamento de acesso da AWS/2.3.2. Serviços de segurança/2.3.2.7. AWS Key Management Service (KMS)|AWS KMS]] para chaves compartilhadas entre contas.

## Definindo RPO, RTO e retenção

| Requisito | Decisão de plano |
|---|---|
| **RPO de segundos/minutos** | Backup contínuo (PITR) onde suportado |
| **RPO de 24 h** | Regra diária |
| **Retenção legal de anos** | Regra mensal/anual + cold storage + Vault Lock |
| **DR regional** | Copy action para outra região |
| **Isolamento de ransomware** | Cópia para conta separada + vault imutável |
| **RTO curto** | Manter warm, testar restauração, pré-aquecer (ex.: EBS FSR) |

## Exemplo prático

Política corporativa em três camadas:

1. **Operacional (PITR + diário):** banco de produção com backup contínuo (35 dias) e diário (35 dias).
2. **Compliance:** mensal retido 7 anos (cold em 90 dias), cópia para conta `backup-archive`.
3. **DR:** semanal copiado para `us-east-1`.
4. Seleção por tag `Backup=critico|padrao|none`, com **tag policy** garantindo valores válidos (veja a nota de Organizations) e uma regra do AWS Config que sinaliza recursos suportados sem tag.

```bash
# Verificar quais recursos estão protegidos
aws backup list-protected-resources --query 'Results[].{Recurso:ResourceArn,Tipo:ResourceType,UltimoBackup:LastBackupTime}'

# Executar um backup sob demanda (antes de uma mudança de risco)
aws backup start-backup-job --backup-vault-name prod-vault \
  --resource-arn arn:aws:rds:sa-east-1:111122223333:db:meubanco \
  --iam-role-arn arn:aws:iam::111122223333:role/service-role/AWSBackupDefaultServiceRole \
  --lifecycle DeleteAfterDays=14
```

## Erros comuns e armadilhas

- **Janela de conclusão curta** para recursos grandes: o job falha por tempo.
- **Lifecycle inconsistente** (cold < mínimo): a API rejeita ou ignora.
- **Cópia entre contas sem política no vault de destino** ou sem chave KMS compartilhada: copy job falha.
- **Política da Organization sem vault/role na conta-membro:** nada é feito.
- **Usar cron em horário local** achando que é local: é UTC.
- **Misturar DLM e AWS Backup** no mesmo recurso.
- **Retenção "infinita" sem revisão:** custo cresce.
- **Esquecer de cobrir recursos novos** (sem tag).
- **Não monitorar jobs falhos.**

## 🧩 Quiz de Fixação

1. Que parâmetros definem quando um job pode começar e terminar?
2. O que é preciso para copiar backups para outra conta?
3. Para que servem as políticas de backup do Organizations?

**Respostas:**
1) *Start within* (janela para iniciar) e *Complete within* (janela para concluir), além do schedule em UTC.
2) Cross-account backup habilitado na Organization, um vault de destino com política de acesso permitindo a conta de origem e chaves KMS compartilhadas/compatíveis.
3) Definir um plano central que é aplicado automaticamente a OUs e contas, garantindo padronização e conformidade sem configurar conta por conta.
