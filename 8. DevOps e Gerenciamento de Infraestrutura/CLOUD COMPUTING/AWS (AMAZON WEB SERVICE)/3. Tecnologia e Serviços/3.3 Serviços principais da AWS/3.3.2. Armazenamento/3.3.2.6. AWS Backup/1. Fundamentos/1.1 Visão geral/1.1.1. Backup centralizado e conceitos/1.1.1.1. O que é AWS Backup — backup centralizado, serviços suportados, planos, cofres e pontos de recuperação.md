### O que é AWS Backup — backup centralizado, serviços suportados, planos, cofres e pontos de recuperação

> [!warning] Aviso
> A lista de serviços suportados, recursos (como cofres air-gapped, backup contínuo) e preços do AWS Backup muda com frequência. Confirme na documentação. Os comandos **não foram executados**.

O **AWS Backup** é um serviço **centralizado e gerenciado** para automatizar, agendar e governar backups de **vários serviços AWS** (e de workloads híbridos) a partir de um único lugar. Em vez de cada equipe configurar snapshots do EBS, backups do RDS, do DynamoDB, do EFS e do FSx de forma independente, você define **políticas** e a AWS as executa de modo consistente e auditável.

**Analogia:** é a **central de cópias de segurança da empresa**. Cada setor (bancos, discos, arquivos) continua com seus dados, mas uma única equipe define quando fazer cópia, por quanto tempo guardar, onde guardar uma segunda cópia e como provar que foi feito.

## Por que usar

| Benefício | Detalhe |
|---|---|
| **Centralização** | Um console/API/IaC para todos os serviços suportados |
| **Políticas por tag** | Novos recursos com a tag certa entram no plano automaticamente |
| **Retenção e lifecycle** | Regras de expiração e arquivamento (cold storage) por plano |
| **Cópias entre regiões e contas** | Resiliência a desastres e a comprometimento de conta |
| **Imutabilidade** | Vault Lock (WORM) e cofres logicamente isolados |
| **Conformidade e auditoria** | Backup Audit Manager, relatórios, CloudTrail |
| **Governança multi-conta** | Políticas de backup do AWS Organizations |
| **Restauração testável** | Restore testing automatizado |

## Conceitos-chave

| Conceito | O que é |
|---|---|
| **Backup plan** | Conjunto de **regras** de backup e a **seleção de recursos** que ele protege |
| **Backup rule** | Agenda (cron), janela de início/conclusão, cofre de destino, lifecycle (arquivar/expirar), cópias |
| **Resource assignment** | Quais recursos entram no plano (por ARN ou **tags**) e a role IAM usada |
| **Backup vault** | Contêiner lógico dos pontos de recuperação, com criptografia KMS e política de acesso |
| **Recovery point** | Um backup individual (snapshot) de um recurso |
| **Backup job / Restore job / Copy job** | Execuções de backup, restauração e cópia |
| **Lifecycle** | Transição para *cold storage* e exclusão após N dias |
| **Backup policy (Organizations)** | Plano definido no nível da organização e aplicado às contas |

```
  Backup plan "diario-prod"
   ├─ Rule: todo dia 03:00 UTC → Vault "prod" → mover p/ cold em 30d → expirar em 365d
   │         └─ cópia → Vault "dr" em outra região (retenção 90d)
   └─ Seleção: recursos com a tag Backup=diario  (role: AWSBackupDefaultServiceRole)

  EBS · RDS · DynamoDB · EFS · FSx · S3 · EC2 ... ──► recovery points no vault
```

## Backup contínuo e point-in-time recovery (PITR)

Para alguns serviços (S3, RDS, Aurora, DynamoDB, entre outros), o AWS Backup oferece **backup contínuo**: restauração para **qualquer segundo** dentro de uma janela (até 35 dias) além dos backups periódicos. Útil para reduzir o **RPO** a segundos ou minutos.

## Como se relaciona com recursos nativos

| Mecanismo nativo | Relação com AWS Backup |
|---|---|
| Snapshots EBS + DLM | O AWS Backup também cria snapshots do EBS; prefira um só orquestrador por recurso para evitar duplicidade |
| Backups automáticos do RDS | O AWS Backup pode gerenciá-los e adicionar cópias e lifecycle |
| Backups do EFS | Integração nativa; o EFS cria backups automáticos via AWS Backup |
| Versionamento/replicação do S3 | Complementar; o AWS Backup adiciona retenção, cópia entre contas e auditoria |
| Backups do DynamoDB | On-demand e PITR nativos; AWS Backup adiciona cópia entre regiões/contas e lifecycle |

## Exemplo prático

```bash
# Criar um cofre criptografado com a chave KMS gerenciada
aws backup create-backup-vault --backup-vault-name prod-vault \
  --encryption-key-arn arn:aws:kms:sa-east-1:111122223333:key/abcd-1234

# Plano diário com retenção de 35 dias e cópia para outra região
aws backup create-backup-plan --backup-plan '{
  "BackupPlanName": "diario-prod",
  "Rules": [{
    "RuleName": "diaria-03h",
    "TargetBackupVaultName": "prod-vault",
    "ScheduleExpression": "cron(0 3 * * ? *)",
    "StartWindowMinutes": 60,
    "CompletionWindowMinutes": 360,
    "Lifecycle": { "DeleteAfterDays": 35 },
    "CopyActions": [{
      "DestinationBackupVaultArn": "arn:aws:backup:us-east-1:111122223333:backup-vault:dr-vault",
      "Lifecycle": { "DeleteAfterDays": 90 }
    }]
  }]
}'

# Selecionar recursos por tag (Backup=diario)
aws backup create-backup-selection --backup-plan-id $PLAN_ID --backup-selection '{
  "SelectionName": "por-tag",
  "IamRoleArn": "arn:aws:iam::111122223333:role/service-role/AWSBackupDefaultServiceRole",
  "ListOfTags": [{ "ConditionType": "STRINGEQUALS", "ConditionKey": "Backup", "ConditionValue": "diario" }]
}'
```

Explicação: qualquer recurso suportado com a tag `Backup=diario` é protegido automaticamente. Detalhes de regras, lifecycle e cópias estão na próxima nota.

## Anatomia de um backup gerenciado

```
 Backup plan ──(regra: agenda, janela, lifecycle, cópia)──► Backup vault (KMS) ──► Recovery points
      ▲                                                          ▲
 Resource assignment (por tag ou ARN)                    Cópia cross-region/cross-account (opcional)
 IAM role de serviço (AWSBackupDefaultServiceRole) executa as operações
```

| Elemento | Função | Detalhe |
|---|---|---|
| **Backup plan** | Política de proteção | Uma ou mais regras |
| **Regra** | Agenda (cron), janela de início/conclusão, lifecycle | Retenção e transição para cold storage |
| **Vault** | Contêiner dos recovery points | Criptografado com KMS; política de acesso própria |
| **Recovery point** | Backup concreto | Restaurado como novo recurso |
| **Seleção de recursos** | Quais recursos entram | Tag (`backup=diario`), tipo, ARN |
| **Vault Lock** | WORM | Impede apagar/alterar retenção (modo governança ou compliance) |

> [!warning] Serviços suportados, tipos de cold storage e limites mudam; confirme na documentação atual.

## Estratégia 3-2-1 com AWS Backup

```
 Produção (região A) ──backup──► Vault A (mesma conta)
                      └─cópia──► Vault B (outra região)      ← proteção regional
                      └─cópia──► Vault C (conta de backup isolada) ← proteção contra comprometimento da conta
```

| Camada | Proteção |
|---|---|
| Mesma região/conta | Restauração rápida |
| Outra região | Desastre regional |
| Outra conta + Vault Lock | Ransomware e exclusão maliciosa |

## Troubleshooting

| Sintoma | Causa provável | Ação |
|---|---|---|
| Job falha com "Access denied" | Role sem permissão no recurso/KMS | Ajustar política da role e da chave |
| Recurso não entra no plano | Tag errada / sem opt-in do serviço | Conferir seleção e habilitar o tipo de recurso |
| Janela perdida | `StartWindow` curta | Aumentar a janela |
| Cold storage com retenção mínima | Transição antes de 90 dias | Respeitar o mínimo de retenção |

## Erros comuns e armadilhas

- **Achar que backup nativo e AWS Backup são a mesma coisa** e duplicar rotinas (custo e confusão).
- **Recursos sem a tag** do plano: ficam desprotegidos silenciosamente.
- **Role IAM sem permissões** no recurso ou na chave KMS: jobs falham.
- **Cofre sem política de acesso restritiva:** qualquer um com permissão pode apagar pontos de recuperação.
- **Não ter cópia em outra região/conta.**
- **Nunca testar a restauração.**
- **Esquecer que cada serviço restaura de forma diferente** (novo recurso, não sobrescreve).
- **Janelas de backup curtas demais:** jobs expiram.
- **Ignorar o custo** de armazenamento de recovery points antigos.

## 🧩 Quiz de Fixação

1. Qual a diferença entre backup plan, backup vault e recovery point?
2. Como garantir que novos recursos sejam protegidos automaticamente?
3. Por que manter uma cópia em outra região ou conta?

**Respostas:**
1) O *plan* define regras e a seleção de recursos; o *vault* é o contêiner (com KMS e política) onde os backups ficam; o *recovery point* é cada backup individual de um recurso.
2) Atribuir recursos ao plano por **tags** (ou por políticas de backup do Organizations): qualquer novo recurso com a tag entra no plano.
3) Para resiliência a falhas regionais e a comprometimento ou exclusão maliciosa na conta de origem; a cópia isolada permite recuperar mesmo nesses cenários.

### Questões de aprofundamento

4. Como proteger backups contra um atacante que comprometeu a conta de produção?
5. Por que uma regra com cold storage em 30 dias pode ser rejeitada ou custar mais?
6. Como incluir automaticamente novos recursos no plano?

**Respostas:**
4) Copiar para um vault em uma conta de backup separada e ativar Vault Lock (WORM), impedindo exclusão ou alteração de retenção.
5) Há retenção mínima em cold storage (por exemplo 90 dias); apagar antes gera cobrança proporcional.
6) Seleção por tag: qualquer recurso novo com a tag é incluído no plano.
