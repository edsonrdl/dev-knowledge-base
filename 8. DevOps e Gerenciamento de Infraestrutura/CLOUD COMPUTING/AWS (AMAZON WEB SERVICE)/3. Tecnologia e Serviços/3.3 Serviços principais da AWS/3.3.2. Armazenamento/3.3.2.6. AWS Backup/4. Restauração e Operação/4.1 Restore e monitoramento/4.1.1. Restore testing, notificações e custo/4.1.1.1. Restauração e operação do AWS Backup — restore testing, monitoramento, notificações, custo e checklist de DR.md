### Restauração e operação do AWS Backup — restore testing, monitoramento, notificações, custo e checklist de DR

> [!warning] Aviso

Um backup só tem valor se puder ser **restaurado dentro do tempo (RTO) e com a perda (RPO) aceitáveis**. Esta nota fecha o AWS Backup com **restauração**, **restore testing automatizado**, **monitoramento e alertas**, **custo** e um **checklist de DR**.

**Analogia:** é o **simulado de incêndio**. De nada adianta ter extintores (backups) se ninguém sabe usá-los ou se estão vazios: o simulado periódico descobre os problemas antes do incêndio real.

## Como funciona a restauração

Regra geral: a restauração **sempre cria um novo recurso** (volume, instância, banco, sistema de arquivos...), nunca sobrescreve o original. Depois você decide trocar o tráfego/apontamento.

| Recurso | O que a restauração cria | Pontos de atenção |
|---|---|---|
| **EBS** | Novo volume (ou snapshot) | Mesma AZ de destino que escolher; anexar à instância |
| **EC2** | Nova instância (AMI + volumes) | Escolher VPC/subnet/SG/IAM, tipo de instância |
| **RDS/Aurora** | Nova instância/cluster | Novo endpoint; ajustar a aplicação; PITR para um instante |
| **DynamoDB** | Nova tabela | Índices, auto scaling e TTL podem exigir reconfiguração |
| **EFS** | Novo sistema de arquivos (completo) ou **restauração parcial** de arquivos/diretórios | Parcial é útil para exclusões |
| **FSx** | Novo sistema de arquivos | Mesmo sabor e parâmetros |
| **S3** | Restaura objetos para um bucket (existente ou novo) | Pode restaurar para o mesmo bucket com prefixo |

```bash
# Listar recovery points de um recurso e restaurar um deles
aws backup list-recovery-points-by-resource --resource-arn $ARN_DO_RECURSO
aws backup get-recovery-point-restore-metadata --backup-vault-name prod-vault --recovery-point-arn $RP_ARN

# Restaurar (os metadados variam por tipo de recurso; veja o retorno acima)
aws backup start-restore-job --recovery-point-arn $RP_ARN \
  --iam-role-arn arn:aws:iam::111122223333:role/service-role/AWSBackupDefaultServiceRole \
  --metadata file://restore-metadata.json

# Acompanhar
aws backup describe-restore-job --restore-job-id $JOB_ID
```

Para **restauração entre contas/regiões**, restaure do cofre de destino (a cópia) — a chave KMS precisa estar disponível ali.

## Restore testing (testes de restauração automatizados)

O **Restore Testing** agenda restaurações de teste dos seus recovery points e valida o resultado, produzindo **evidência de conformidade** e o **tempo real de restauração**.

| Elemento | Função |
|---|---|
| **Restore testing plan** | Frequência, janela de início, seleção do recovery point (aleatório, mais recente) |
| **Seleção de recursos** | Por tipo/tag de recursos a testar |
| **Validação** | Janela de validação: você pode executar validações (script/Lambda) antes de o recurso de teste ser **excluído automaticamente** |
| **Resultado** | Tempo, sucesso/falha, relatório no Audit Manager/EventBridge |

```
 Plano semanal → restaura um recovery point de cada tipo → Lambda valida (ex.: SELECT no banco)
              → registra tempo/sucesso → exclui o recurso de teste (limpeza automática)
```

Benefícios: prova de que o backup funciona, medição de **RTO real**, detecção precoce de falhas de chave KMS, permissões e configuração.

## Monitoramento e alertas

| Fonte | Uso |
|---|---|
| **Console/Dashboard de jobs** | Visão de backup, copy e restore jobs, com status |
| **EventBridge** | Eventos de início/fim/falha de jobs, para acionar Lambda/SNS/Slack |
| **SNS (notificações do vault)** | `BACKUP_JOB_COMPLETED`, `COPY_JOB_FAILED`, `RESTORE_JOB_COMPLETED` etc. |
| **CloudWatch** | Métricas de jobs (`NumberOfBackupJobsFailed`, etc.) e alarmes |
| **CloudTrail** | Auditoria de API (`DeleteRecoveryPoint`, políticas de vault) |
| **Backup Audit Manager** | Conformidade e relatórios |
| **AWS Config** | Regras como `backup-plan-min-frequency-and-min-retention-check`, `backup-recovery-point-manual-deletion-disabled` |

```bash
# Notificações do vault via SNS
aws backup put-backup-vault-notifications --backup-vault-name prod-vault \
  --sns-topic-arn arn:aws:sns:sa-east-1:111122223333:alertas-backup \
  --backup-vault-events BACKUP_JOB_FAILED COPY_JOB_FAILED RESTORE_JOB_FAILED

# Listar jobs com falha nas últimas 24 h
aws backup list-backup-jobs --by-state FAILED \
  --by-created-after 2026-11-05T00:00:00Z \
  --query 'BackupJobs[].{Job:BackupJobId,Recurso:ResourceArn,Msg:StatusMessage}'
```

Alertas essenciais: **job com falha**, **recurso sem proteção**, **cópia não concluída**, **chamadas de exclusão/alteração de política**, **chave KMS desabilitada ou agendada para exclusão**.

## Custo

| Item | Observação |
|---|---|
| **Armazenamento dos recovery points** | Cobrado por GB-mês, com preços diferentes para warm e cold e por tipo de recurso |
| **Backups contínuos (PITR)** | Cobrança por armazenamento do log contínuo |
| **Cópias entre regiões** | Transferência entre regiões + armazenamento no destino |
| **Restauração** | Cobrança por GB restaurado em alguns serviços |
| **Restore testing e Audit Manager** | Cobranças próprias |
| **Cold storage** | Mais barato por GB, com permanência mínima e cobrança na restauração |
| **Cofre isolado** | Preço próprio |

Estratégias de redução:

1. Alinhar retenção ao requisito real (evitar "para sempre").
2. Usar **cold storage** quando suportado e a retenção é longa.
3. Evitar **duplicidade** (DLM + AWS Backup + snapshots manuais).
4. Excluir recovery points de recursos descontinuados (política de expiração).
5. Usar **tags de custo** nos backups.
6. Avaliar a frequência: horário vs diário conforme RPO.

## Checklist de DR e operação

- [ ] Todos os recursos críticos estão em um plano? (relatório de recursos protegidos)
- [ ] RPO/RTO definidos por sistema e coerentes com o plano?
- [ ] Cópia em **outra região** e **outra conta**? Vault lock/isolado nos dados críticos?
- [ ] Chaves KMS acessíveis no destino de DR e protegidas contra exclusão?
- [ ] Restore testing ativo e **RTO real medido**?
- [ ] Runbook de restauração documentado (quem, como, ordem, validações)?
- [ ] Alertas de falha de job e de ações sensíveis?
- [ ] SCPs impedindo exclusão e desativação?
- [ ] Revisão trimestral de retenção, custo e conformidade?
- [ ] Teste de DR completo (restaurar um ambiente em região/conta secundária) pelo menos anualmente?

## Exemplo prático

Simulado trimestral de DR de uma aplicação (EC2 + RDS + EFS):

1. Em uma **conta de recuperação**, usar o cofre isolado/cópia para restaurar o RDS (PITR para 10 min antes do incidente simulado), o EFS e a instância.
2. Registrar o tempo de cada etapa: RDS 38 min, EFS 22 min, EC2 15 min, validações 20 min → **RTO real ≈ 1h40**.
3. Descobrir problemas: a chave KMS da região de DR não estava compartilhada com a role de restauração; o SG padrão bloqueava o acesso ao EFS.
4. Corrigir, atualizar o runbook e repetir o teste.
5. Anexar o relatório do Restore Testing/Audit Manager como evidência.

## Erros comuns e armadilhas

- **Nunca restaurar para testar:** descobre-se o problema no desastre.
- **Esquecer que a restauração cria novo recurso** e não prever redirecionamento (DNS, strings de conexão).
- **Restaurar sem a chave KMS ou a role** no destino.
- **Ignorar o tempo de restauração** de grandes volumes/bancos ao estimar RTO.
- **Não validar o conteúdo** (restaurou, mas está corrompido/incompleto).
- **Alertas sem destinatário** ou sem plantão.
- **Deixar recursos de teste de restauração ligados** (custo).
- **Runbook desatualizado** após mudanças na arquitetura.
- **Confiar que "o status do job é Completed" = dados válidos.**

## 🧩 Quiz de Fixação

1. O que acontece com o recurso original quando você restaura um recovery point?
2. Qual o objetivo do Restore Testing?
3. Por que medir o RTO real em um simulado de DR?

**Respostas:**
1) Nada: a restauração cria um novo recurso (volume, instância, banco, sistema de arquivos...). O original não é sobrescrito, e é preciso redirecionar o tráfego ou a aplicação para o novo.
2) Agendar restaurações de teste automáticas e validar o resultado, gerando evidência de conformidade e o tempo real de restauração, e excluindo os recursos de teste ao fim.
3) Porque as estimativas teóricas ignoram dependências (chaves, permissões, rede, volume de dados); o tempo real mostra se o RTO prometido é atingível e quais ajustes são necessários.
