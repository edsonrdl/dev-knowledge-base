### Proteção e conformidade no AWS Backup — Vault Lock, cofres logicamente isolados, KMS e Backup Audit Manager

> [!warning] Aviso
> Modos do Vault Lock, cofres logicamente isolados (air-gapped), controles do Audit Manager e preços evoluem. **Vault Lock em modo compliance é irreversível após o período de carência.** Confirme na documentação. Os comandos **não foram executados**.

Ter backup não basta: é preciso **provar** que ele existe, **impedir que seja apagado** (por erro, ataque ou insider) e **controlar quem acessa**. O AWS Backup oferece **criptografia com KMS**, **políticas de acesso nos cofres**, **Vault Lock (WORM)**, **cofres logicamente isolados** e o **Backup Audit Manager**.

**Analogia:** os backups são **documentos num arquivo**. A política de acesso é a **lista de quem tem a chave da sala**; o Vault Lock é uma **tranca que nem o dono do prédio consegue abrir antes do prazo**; o cofre isolado é uma **sala-cofre em outro prédio com acesso separado**; o Audit Manager é o **auditor** que confere se as regras foram cumpridas.

## Ameaças que a proteção endereça

| Ameaça | Controle |
|---|---|
| Exclusão acidental de recovery points | Política do vault, IAM restritivo |
| **Ransomware / atacante com credenciais de admin** | **Vault Lock**, cofre logicamente isolado, conta separada |
| **Insider** malicioso | Separação de funções, Vault Lock compliance |
| Vazamento dos dados de backup | Criptografia KMS, política restritiva |
| Falta de evidência para auditoria | Backup Audit Manager, CloudTrail |
| Perda de acesso à chave | Gestão de KMS, políticas de chave, multi-região |

## Criptografia

- Todo vault tem uma **chave KMS** (a padrão `aws/backup` ou uma CMK sua).
- Muitos serviços criptografam o backup com a **mesma chave do recurso original**; para cópias entre contas/regiões, é preciso uma chave **compartilhada/compatível**.
- Use **CMK** quando precisar compartilhar com outra conta ou controlar a política de chave. Veja [[8. DevOps e Gerenciamento de Infraestrutura/CLOUD COMPUTING/AWS (AMAZON WEB SERVICE)/2. Segurança e Conformidade/2.3 Capacidades de gerenciamento de acesso da AWS/2.3.2. Serviços de segurança/2.3.2.7. AWS Key Management Service (KMS)|AWS KMS]].
- Deletar/desabilitar a chave torna os recovery points ilegíveis: **proteja a chave** (agendamento de exclusão com janela, políticas, alarmes).

## Política de acesso do vault

Uma **resource policy** no vault controla quem pode copiar, restaurar ou **apagar** pontos de recuperação.

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Sid": "NegarExclusaoDeRecoveryPoints",
    "Effect": "Deny",
    "Principal": "*",
    "Action": [
      "backup:DeleteRecoveryPoint",
      "backup:UpdateRecoveryPointLifecycle",
      "backup:PutBackupVaultAccessPolicy"
    ],
    "Resource": "*",
    "Condition": {
      "StringNotEquals": { "aws:PrincipalArn": "arn:aws:iam::111122223333:role/BackupAdminBreakGlass" }
    }
  }]
}
```

```bash
aws backup put-backup-vault-access-policy --backup-vault-name prod-vault --policy file://politica-vault.json
```

Princípios: apenas uma role de *break-glass* pode excluir; o resto do pessoal apenas lê/restaura. Combine com **SCP** negando `backup:DeleteBackupVault` e `backup:DeleteRecoveryPoint` fora da role autorizada.

## Vault Lock (WORM)

O **AWS Backup Vault Lock** aplica a regra **write-once-read-many**: ninguém (nem root) pode excluir recovery points antes do fim da retenção mínima, nem reduzir a retenção.

| Modo | Característica |
|---|---|
| **Governance** | Pode ser removido/alterado por usuários com permissão específica; bom para testar |
| **Compliance** | Após a **carência (cooling-off, mínimo de 3 dias)** a configuração torna-se **imutável**: nem a AWS nem o root conseguem remover o lock ou excluir antes do prazo |

Parâmetros:

| Parâmetro | Significado |
|---|---|
| `MinRetentionDays` | Retenção mínima obrigatória dos recovery points |
| `MaxRetentionDays` | Retenção máxima permitida |
| `ChangeableForDays` | Dias de carência; ao terminar, entra o modo compliance imutável |

```bash
# Modo compliance com carência de 7 dias (ATENÇÃO: após a carência é irreversível)
aws backup put-backup-vault-lock-configuration --backup-vault-name archive-vault \
  --min-retention-days 30 --max-retention-days 3650 --changeable-for-days 7
# Sem --changeable-for-days o lock é de governança (removível por quem tem permissão)
```

Atende requisitos como **SEC 17a-4**, **CFTC** e **FINRA** (verifique a documentação de conformidade). Teste sempre em governance antes de ir a compliance.

## Cofres logicamente isolados (logically air-gapped vaults)

Tipo de cofre com **isolamento lógico**: os recovery points ficam em **contas controladas pelo serviço**, com acesso **independente** da conta de produção, **imutáveis** por padrão e **compartilháveis** via AWS RAM com uma conta de recuperação.

```
 Conta de produção ──copy──► Cofre logicamente isolado (conta do serviço, imutável, KMS próprio)
                                     │ RAM
                                     ▼
                         Conta de recuperação (restaura mesmo se produção foi comprometida)
```

Quando usar: **recuperação após comprometimento de conta** (ransomware), onde nem as credenciais de admin da produção devem alcançar os backups. Complementa o Vault Lock.

## Backup Audit Manager

Audita a **conformidade** dos seus backups com **controles** e gera **relatórios**.

| Elemento | Descrição |
|---|---|
| **Framework** | Conjunto de controles (ex.: "recursos têm plano", "retenção mínima", "backup cross-region", "vault lock ativo", "backup criptografado") |
| **Controls** | Verificações individuais; algumas parametrizáveis |
| **Reports** | Relatórios de **jobs** (backup/restore/copy) e de **conformidade** em S3 (CSV/JSON), agendados |
| **Integração** | Relatório pode alimentar Athena/QuickSight; AWS Config usado nos bastidores |

```bash
# Relatório de jobs de backup gerado e entregue em S3 (resumo)
aws backup create-report-plan --report-plan-name jobs-diario \
  --report-delivery-channel S3BucketName=relatorios-backup,Formats=CSV \
  --report-setting ReportTemplate=BACKUP_JOB_REPORT
```

## Boas práticas (resumo)

1. Cofres separados por sensibilidade, com CMK própria e política restritiva.
2. **Vault Lock** (primeiro governance, depois compliance) para dados regulados.
3. Cópia para **conta separada** (e cofre isolado) para ransomware.
4. **SCPs** impedindo exclusão de vaults/recovery points e a desativação do AWS Backup.
5. **Audit Manager** + alarmes em jobs com falha.
6. **Teste de restauração** periódico (nota de restauração e operação).
7. Registro em CloudTrail e alerta em chamadas sensíveis (`DeleteRecoveryPoint`, `PutBackupVaultAccessPolicy`).

## Exemplo prático

Requisito: "dados financeiros devem ser retidos 7 anos, imutáveis, e recuperáveis mesmo se a conta de produção for invadida".

1. Cofre `fin-archive` na **conta bunker** com CMK própria; Vault Lock governance com `MinRetentionDays=2555` por 14 dias de testes.
2. Após validação, compliance com `ChangeableForDays=3` (carência mínima).
3. Plano mensal na produção com copy action para `fin-archive` e (opcional) cofre isolado.
4. SCP: negar `backup:DeleteBackupVault`, `backup:DeleteRecoveryPoint` e `kms:ScheduleKeyDeletion` nas contas de produção.
5. Backup Audit Manager com framework de retenção e relatório mensal enviado ao time de compliance.
6. Exercício semestral: restaurar a partir da conta bunker em uma conta limpa.

## Escolhendo o nível de proteção

| Modelo | Quem pode apagar | Protege contra | Quando usar |
|---|---|---|---|
| Vault comum + access policy | Admin com permissão | Erro operacional leve | Ambientes gerais |
| Vault Lock em modo **governance** | Quem tiver permissão específica de remover o lock | Exclusão acidental e descuido | Testes e adoção gradual |
| Vault Lock em modo **compliance** | Ninguém, após o período de carência | Ransomware, insider, conta comprometida | Regulatório (WORM) |
| Logically air-gapped vault | Só via compartilhamento controlado; conta separada | Comprometimento total da conta de origem | Recuperação cibernética |

> [!warning] Valores, limites e preços mudam; os exemplos deste material não foram executados. Valide carência mínima, serviços compatíveis e regiões na documentação antes de ativar compliance: o modo é irreversível.

### Camadas de defesa

```
 Conta de produção                    Conta de backup (isolada)
┌──────────────────────┐   cópia   ┌─────────────────────────────┐
│ Recursos + Plano de  │ ────────► │ Vault + Vault Lock          │
│ Backup (Organizations│           │  • retenção mín./máx.       │
│ backup policy)       │           │  • KMS própria              │
└──────────────────────┘           │  • sem delete antes do prazo│
        ▲                          └──────────────┬──────────────┘
        │ restore (via compartilhamento)          │
        └─────────────────────────────────────────┘
```

A ideia central: se o atacante assumir a conta de produção, ele não consegue destruir os recovery points da conta isolada, e o lock impede até o dono da conta de apagá-los antes do prazo.

## Roteiro seguro de adoção

1. Habilitar **governance** num vault de teste e validar retenções.
2. Definir retenção mínima e máxima coerentes com a política legal.
3. Testar restauração a partir do vault travado.
4. Só então ativar **compliance** com a carência (cooling-off) cobrindo o tempo de revisão.
5. Registrar a decisão: uma retenção errada fica fixa e custa armazenamento por anos.

## CLI comentado

```bash
# Ativa Vault Lock (sem ChangeableForDays = governance; com ele = compliance após a carência)
aws backup put-backup-vault-lock-configuration \
  --backup-vault-name cofre-critico \
  --min-retention-days 30 --max-retention-days 365 \
  --changeable-for-days 3        # carência de 3 dias antes de virar imutável

# Confere o estado do lock
aws backup describe-backup-vault --backup-vault-name cofre-critico \
  --query '{Locked:Locked,Min:MinRetentionDays,Max:MaxRetentionDays,LockDate:LockDate}'

# Gera um relatório de auditoria (Backup Audit Manager)
aws backup create-report-plan --report-plan-name conformidade-diaria \
  --report-delivery-channel S3BucketName=meu-bucket-relatorios \
  --report-setting ReportTemplate=BACKUP_JOB_REPORT
```

## Troubleshooting

| Sintoma | Causa provável | Ação |
|---|---|---|
| Plano falha ao salvar no vault | Retenção do plano fora do min/max do lock | Ajustar a retenção do plano |
| Não consigo excluir recovery point | Lock ativo (comportamento esperado) | Aguardar a expiração; não há atalho em compliance |
| Cópia para o vault isolado falha | Chave KMS ou compartilhamento mal configurado | Revisar key policy e RAM sharing |
| Relatório vazio | Report plan sem escopo/frameworks | Definir escopo e templates |

## Custo

O lock em si não tem custo adicional relevante, mas **retenção longa e obrigatória significa armazenamento por todo o período**, sem opção de apagar para economizar. Vaults logicamente isolados exigem uma segunda cópia e uma conta adicional. Calcule o custo de retenção × volume × anos antes de ativar compliance.

## Erros comuns e armadilhas

- **Ativar compliance sem testar:** configuração errada fica irreversível (e custosa).
- **Chave KMS apagada ou sem acesso:** backups inúteis.
- **Mesma conta e mesmas credenciais para produção e backups:** um comprometimento apaga tudo.
- **Política de vault permissiva demais.**
- **Achar que criptografar é o mesmo que imutabilidade.**
- **Não monitorar eventos de exclusão/alteração de política.**
- **Retenção mínima do Vault Lock maior que o necessário:** não dá para excluir antes; custos fixos.
- **Audit Manager ligado sem acompanhar os relatórios.**
- **Não restringir quem pode desabilitar o AWS Backup** (SCP).

## 🧩 Quiz de Fixação

1. Qual a diferença entre Vault Lock governance e compliance?
2. Por que um cofre logicamente isolado ajuda contra ransomware?
3. O que o Backup Audit Manager entrega?

**Respostas:**
1) Governance pode ser removido ou alterado por usuários autorizados; compliance, depois do período de carência, torna-se imutável: nem root nem a AWS conseguem removê-lo ou excluir recovery points antes do prazo.
2) Os backups ficam em um ambiente controlado pelo serviço, com acesso independente da conta de produção e imutáveis, permitindo recuperar mesmo que as credenciais de produção sejam comprometidas.
3) Frameworks de controles de conformidade e relatórios (de jobs e de conformidade) em S3, mostrando se os recursos estão protegidos conforme as políticas.

**Questões complementares:**

4. Qual a diferença prática entre os modos governance e compliance do Vault Lock?
5. Por que a conta de backup deve ser separada da conta de produção?
6. Qual o principal risco financeiro de ativar compliance sem planejamento?

**Respostas das questões complementares:**
4) Em governance, usuários com permissão específica ainda podem remover o lock; em compliance, após a carência, nem o administrador consegue alterá-lo ou apagar backups antes do prazo.
5) Para que o comprometimento da conta de produção (ransomware, credencial vazada, insider) não alcance os recovery points, que ficam sob outro controle de acesso, chave KMS e lock.
6) A retenção errada fica fixa e irreversível, gerando custo de armazenamento durante todo o período sem possibilidade de exclusão.
