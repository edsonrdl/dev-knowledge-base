### AWS Backup em organizações multi-conta — administrador delegado, políticas de backup, cópia entre contas, conta de cofre isolada e arquitetura de recuperação

> [!warning] Aviso
> Recursos de gestão multi-conta do AWS Backup (backup policies, administrador delegado, cofres logicamente isolados, aprovação de múltiplas partes, compartilhamento via RAM) **evoluem rapidamente** e há diferenças de regiões e exigências. Os JSONs e comandos são **ilustrativos e não foram executados**. **Confirme na documentação antes de aplicar.** Políticas organizacionais **afetam muitas contas de uma vez**: teste em uma OU piloto.

Em organizações reais, os dados vivem em **dezenas ou centenas de contas** (por aplicação, ambiente, unidade de negócio). Proteger tudo com planos configurados conta a conta é inviável e inseguro. O AWS Backup, integrado ao **AWS Organizations**, permite **definir uma política central**, **aplicá-la automaticamente a OUs e contas**, **delegar a administração**, **copiar backups para uma conta de cofre isolada** e **desenhar a recuperação** mesmo se uma conta de produção for comprometida. Esta nota apresenta os componentes e a arquitetura recomendada.

**Analogia:** é a diferença entre cada loja de uma rede guardar o próprio cofre (e perder tudo num assalto) e a matriz ter **um cofre-forte corporativo em outro endereço**, com regras iguais para todas as lojas, onde só poucas pessoas têm a chave.

## Peças da governança multi-conta

| Peça | Função |
|---|---|
| **AWS Organizations** | Estrutura (conta de gerenciamento, OUs, contas-membro) e base para políticas |
| **Integração do AWS Backup com Organizations** | Habilita políticas de backup, cópia entre contas e visibilidade centralizada |
| **Backup policies** | Política **JSON** na organização (aplicada a raiz/OUs/contas) que cria planos automaticamente nas contas-alvo |
| **Administrador delegado** | Conta de segurança/backup que administra políticas e monitora, sem usar a conta de gerenciamento |
| **Cross-account backup** | Cópia de recovery points para cofres em **outra conta** da mesma organização |
| **Cofre de destino (conta bunker/vault)** | Conta dedicada, com **resource policy** que aceita cópias da organização |
| **Logically air-gapped vault** | Cofre isolado, imutável por padrão, **compartilhável** via **AWS RAM** com uma conta de recuperação |
| **Multi-party approval** | Restauração a partir de cofres isolados exige aprovação de um **time de aprovação** (recurso de proteção contra comprometimento) |
| **Backup Audit Manager multi-conta** | Relatórios e frameworks agregados na organização |
| **SCPs** | Impedem desativar o backup, excluir cofres e alterar chaves |
| **KMS multi-região / compartilhado** | Chaves acessíveis entre contas/regiões |

```
 ORG
  ├─ Conta de gerenciamento   (habilita integrações; sem workloads)
  ├─ OU Segurança
  │    ├─ Conta "backup-admin" (administrador delegado: políticas, relatórios)
  │    └─ Conta "backup-vault" (cofres centrais; air-gapped; acesso mínimo)
  ├─ OU Produção     ← backup policy "prod-padrao" aplicada
  │    └─ contas de aplicação (cofre local + cópia para backup-vault)
  ├─ OU Não-produção ← backup policy "dev-reduzida"
  └─ OU Recuperação
       └─ Conta "restore" (limpa: usada só para restaurar em desastre/teste)
```

## Habilitar e delegar

Passos (resumo):

1. Na **conta de gerenciamento**: habilitar o *trusted access* do AWS Backup no Organizations e a **proteção entre contas** (*cross-account management*).
2. **Registrar a conta `backup-admin`** como administrador delegado do AWS Backup.
3. Habilitar os tipos de política **BACKUP_POLICY** e (se for usar) política de tags.
4. Criar **IAM roles** padronizadas nas contas-membro (ex.: `OrgBackupRole`) via **StackSets** — a política referencia a role por nome.
5. Criar os **cofres de destino** (e chaves KMS) nas contas membro e na conta `backup-vault`.
6. Aplicar as políticas às OUs.

```bash
# Na conta de gerenciamento
aws organizations enable-aws-service-access --service-principal backup.amazonaws.com
aws organizations register-delegated-administrator --service-principal backup.amazonaws.com --account-id 111111111111
aws organizations enable-policy-type --root-id r-abcd --policy-type BACKUP_POLICY
aws backup update-global-settings --global-settings isCrossAccountBackupEnabled=true   # (execução na conta de gerenciamento)
```

## Política de backup da organização

A política define **planos** (regras, seleção de recursos por tag, cofres, cópias) usando *operators* de herança (`@@assign`, `@@append`, `@@remove`) e variáveis (`$account`, `{{account_id}}`).

```json
{
  "plans": {
    "prod-padrao": {
      "regions": { "@@assign": ["sa-east-1", "us-east-1"] },
      "rules": {
        "diaria": {
          "schedule_expression": { "@@assign": "cron(0 3 * * ? *)" },
          "start_backup_window_minutes": { "@@assign": "60" },
          "complete_backup_window_minutes": { "@@assign": "360" },
          "target_backup_vault_name": { "@@assign": "cofre-local" },
          "lifecycle": { "delete_after_days": { "@@assign": "35" } },
          "copy_actions": {
            "arn:aws:backup:sa-east-1:222222222222:backup-vault:cofre-central": {
              "target_backup_vault_arn": { "@@assign": "arn:aws:backup:sa-east-1:222222222222:backup-vault:cofre-central" },
              "lifecycle": { "delete_after_days": { "@@assign": "90" } }
            }
          }
        }
      },
      "selections": {
        "tags": {
          "por-tag": {
            "iam_role_arn": { "@@assign": "arn:aws:iam::$account:role/OrgBackupRole" },
            "tag_key": { "@@assign": "Backup" },
            "tag_value": { "@@assign": ["critico", "padrao"] }
          }
        }
      }
    }
  }
}
```

| Aspecto | Detalhe |
|---|---|
| **Herança** | Políticas são mescladas da raiz → OU → conta; contas-filhas podem receber *append* de regras, mas não remover as obrigatórias (conforme operadores) |
| **Cofres** | Precisam **existir** nas contas-alvo com o nome indicado |
| **Role** | A role referenciada deve existir nas contas (StackSets) com permissões do `AWSBackupServiceRolePolicyForBackup` |
| **Recursos** | Selecionados por tag (padrão recomendado) ou por tipo de recurso |
| **Efeito** | A política cria o plano **nas contas-membro**; as contas veem o plano como gerenciado pela organização (não editável) |
| **Conformidade** | Combine com **tag policies** (valores válidos de `Backup`) e **AWS Config** (recursos sem tag) |

## Cópia entre contas e a conta de cofre

### Por que copiar para outra conta

| Ameaça | Como a conta separada ajuda |
|---|---|
| **Comprometimento da conta de produção** (credenciais roubadas, ransomware) | Quem entra na produção não tem acesso ao cofre central |
| **Exclusão acidental ou maliciosa** | Cofre central com Vault Lock/air-gap |
| **Erro de configuração** | Isolamento de blast radius |
| **Conformidade** | Evidência de segregação de funções |

### Requisitos de uma cópia entre contas

1. **Cross-account backup habilitado** na organização.
2. **Resource policy do cofre de destino** permitindo a organização (ou contas específicas) copiar:

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Sid": "PermitirCopiaDaOrganizacao",
    "Effect": "Allow",
    "Principal": "*",
    "Action": "backup:CopyIntoBackupVault",
    "Resource": "*",
    "Condition": { "StringEquals": { "aws:PrincipalOrgID": "o-abc123def4" } }
  }]
}
```

3. **Chave KMS** do cofre de destino que permita o uso pela organização (ou o recovery point é recriptografado com a chave de destino).
4. Role do serviço na origem com `backup:StartCopyJob` e acesso à chave.
5. Opcional: **cofre air-gapped** como destino da cópia.

### Cofre logicamente isolado (air-gapped) e RAM

- Recovery points copiados ficam em **cofre isolado** (acesso apenas por APIs próprias).
- **Compartilhe o cofre via AWS RAM** com uma **conta de recuperação** (`restore`), que poderá **restaurar** sem depender da conta de produção.
- **Aprovação de múltiplas partes** (quando habilitada): para acessar/restaurar de um cofre, um time de aprovação (membros do IAM Identity Center) precisa aprovar — mitigando insider e credenciais comprometidas.

```
 Conta prod (cofre local) ──copy──► Conta backup-vault (cofre air-gapped, imutável)
                                              │ AWS RAM (compartilhado)
                                              ▼
                              Conta restore (limpa) ── restaura recursos após aprovação (multi-party)
```

## Arquitetura de recuperação (cenário de comprometimento)

| Fase | Ação |
|---|---|
| **Detecção** | GuardDuty, CloudTrail, alarmes de exclusão/alteração de políticas |
| **Contenção** | Isolar a conta de produção (SCP "deny all", revogar credenciais) |
| **Decisão** | Declarar incidente; escolher o ponto de recuperação (antes do comprometimento) |
| **Aprovação** | Multi-party approval para liberar o cofre isolado |
| **Restauração** | Na **conta limpa** (`restore`), com IaC recriando a infraestrutura e `start-restore-job` do cofre compartilhado |
| **Validação** | Verificações de integridade, varredura de malware nos dados restaurados |
| **Retorno** | Redirecionar tráfego/DNS para o ambiente restaurado; investigação forense da conta antiga |

**Pré-requisitos para funcionar:** IaC para recriar contas/ambientes, imagens/AMIs limpas, chaves KMS acessíveis, DNS gerenciável, runbook **ensaiado** (ao menos anual), permissões mínimas preestabelecidas na conta de recuperação, e comunicação fora de banda.

## Governança contínua

| Controle | Como |
|---|---|
| **Descoberta de recursos sem proteção** | AWS Config (`backup-plan-min-frequency-and-min-retention-check`), consultas no Resource Explorer, Backup Audit Manager (`BACKUP_RESOURCES_PROTECTED_BY_BACKUP_PLAN`) |
| **Relatórios organizacionais** | Frameworks e relatórios multi-conta enviados a S3 centralizado |
| **SCPs** | Negar `backup:DeleteBackupVault`, `DeleteRecoveryPoint`, `StopBackupJob` e alterações de política fora de roles autorizadas |
| **Alarmes** | EventBridge central para falhas de job, cópias não concluídas, exclusões |
| **Custos** | Tags `centro-de-custo`; Budgets por OU; revisão de retenção |
| **Revisão de acessos** | Quem administra a conta `backup-vault` e o time de aprovação (poucas pessoas, MFA, revisão trimestral) |
| **Testes** | Restore testing contínuo e exercício de DR anual na conta `restore` |
| **Ciclo de vida de contas** | Novas contas herdam a política; contas encerradas: reter backups conforme política |

## Exemplo prático

Organização com 80 contas (produção, homologação, desenvolvimento) e requisito regulatório de 7 anos para dados financeiros:

1. **Estrutura:** OUs `Producao`, `Homolog`, `Dev`, `Seguranca`, `Recuperacao`; contas `backup-admin` (delegada), `backup-vault` e `restore`.
2. **Políticas:** `prod-padrao` (diária 35 dias + semanal 90 dias + mensal 7 anos com cold storage, cópia para `backup-vault`), `dev-reduzida` (diária 7 dias, sem cópia); seleção por tag `Backup` e **tag policy** com valores permitidos.
3. **Cofres:** cofre local em cada conta (KMS próprio), cofre central air-gapped na `backup-vault` (CMK multi-região), compartilhado via RAM com `restore`; **Vault Lock** em compliance para o cofre dos dados financeiros após 14 dias de testes.
4. **SCPs:** negam exclusão de cofres/recovery points, mudança de política de backup e desativação do serviço, exceto pela role *break-glass* da conta `backup-admin`.
5. **Governança:** Config e Audit Manager organizacionais com relatório mensal ao comitê de risco; alertas centralizados no EventBridge.
6. **Recuperação:** runbook de comprometimento — isolamento por SCP, aprovação multi-party (3 de 5 membros), restauração de um sistema crítico na conta `restore` por IaC + `start-restore-job`; **exercício anual** com RTO medido (4 h para o sistema tier 1).
7. **Resultado:** cobertura de 98% dos recursos críticos (medida), cópias fora da conta de produção e prova documentada de recuperação independente da conta comprometida.

## Erros comuns e armadilhas

- **Política organizacional sem os cofres e roles** nas contas-alvo (nada é executado).
- **Aplicar à raiz sem piloto** e gerar custo/falhas em massa.
- **Cross-account sem resource policy ou sem chave KMS compartilhada** (copy jobs falham).
- **Conta de cofre com administradores demais** ou acessível pelas mesmas credenciais da produção.
- **Usar a conta de gerenciamento** para operar backups em vez de um administrador delegado.
- **Não ter SCP** impedindo exclusão de cofres/desativação.
- **Recuperação dependente da conta comprometida** (sem conta limpa e sem IaC).
- **Nunca ensaiar** o DR e a aprovação multi-party.
- **Recursos sem tag** fora da proteção (sem controle de conformidade).
- **Ignorar custos** de cópias multi-região e retenção longa sem cold storage.
- **Chaves KMS em uma só região** (impossibilita restauração em DR).

## 🧩 Quiz de Fixação

1. Para que servem as backup policies do Organizations?
2. Por que ter uma conta de cofre separada da produção?
3. O que é necessário para uma cópia entre contas funcionar?
4. Como uma conta de recuperação limpa participa do DR?

**Respostas:**
1) Para definir centralmente planos de backup em JSON e aplicá-los automaticamente a OUs e contas-membro, padronizando regras, retenção, cópias e seleção por tag, sem configurar conta a conta.
2) Para que o comprometimento ou o erro na conta de produção não alcance os backups: o cofre central, isolado e imutável, tem acesso e administradores diferentes, reduzindo o raio de impacto de ransomware, insiders e exclusões.
3) Cross-account backup habilitado, resource policy no cofre de destino permitindo `backup:CopyIntoBackupVault` (por exemplo pela organização), chave KMS acessível e uma role de serviço com permissões na origem.
4) O cofre isolado é compartilhado com a conta `restore` via RAM; em um incidente, após aprovação (multi-party), os recursos são restaurados nessa conta limpa com IaC, sem depender da conta de produção comprometida.
