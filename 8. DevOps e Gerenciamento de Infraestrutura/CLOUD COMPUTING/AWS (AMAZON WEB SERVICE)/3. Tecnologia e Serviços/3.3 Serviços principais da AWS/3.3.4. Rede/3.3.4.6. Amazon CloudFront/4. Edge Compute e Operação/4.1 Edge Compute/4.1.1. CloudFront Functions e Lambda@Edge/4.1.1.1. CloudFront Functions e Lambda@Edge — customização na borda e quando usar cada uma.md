### CloudFront Functions e Lambda@Edge — customização na borda e quando usar cada uma

> [!warning] Aviso
> Limites (tempo de execução, memória, tamanho de código e de resposta), runtimes suportados, regiões e preços das duas opções mudam. Confirme na documentação. Os códigos abaixo são ilustrativos e **não foram executados**.

Às vezes cache e roteamento não bastam: é preciso **reescrever uma URL**, **redirecionar**, **validar um token**, **adicionar headers de segurança**, fazer **teste A/B** ou **gerar uma resposta** sem chegar à origem. O CloudFront permite executar código **na própria borda**, em duas modalidades com perfis bem distintos: **CloudFront Functions** e **Lambda@Edge**.

**Analogia:** CloudFront Functions é o **atendente do balcão** que faz tarefas rapidíssimas (carimbar, direcionar para outra fila), sem sair do lugar. Lambda@Edge é o **especialista da sala ao lado**: pode fazer coisas mais elaboradas (consultar sistemas externos, processar imagens), mas leva mais tempo e custa mais.

## Os quatro pontos de gatilho (eventos)

O código pode ser anexado a um **cache behavior** em até quatro momentos do fluxo:

```
 Viewer ──► [1 VIEWER REQUEST] ──► cache? ──hit──► [4 VIEWER RESPONSE] ──► Viewer
                                     │ miss
                                     ▼
                         [2 ORIGIN REQUEST] ──► ORIGEM
                                                  │
                         [3 ORIGIN RESPONSE] ◄────┘
                                     │ (guarda no cache)
                                     ▼
                         [4 VIEWER RESPONSE] ──► Viewer
```

| Evento | Quando roda | Roda a cada requisição? |
|---|---|---|
| **Viewer request** | Logo que a requisição chega, **antes** do cache | **Sim** (hit ou miss) |
| **Origin request** | Só em **cache miss**, antes de ir à origem | Não (apenas miss) |
| **Origin response** | Ao receber a resposta da origem, **antes de gravar no cache** | Não (apenas miss) |
| **Viewer response** | Antes de devolver ao viewer (hit ou miss) | **Sim** |

Dica: lógica **cara** deve ficar em *origin request/response*, pois o resultado fica em cache e roda poucas vezes. Lógica **barata e que precisa valer sempre** fica em *viewer request/response*.

## CloudFront Functions

Funções leves em **JavaScript** (runtime próprio, restrito) executadas **em todas as edge locations**, com latência de submilissegundo e capacidade de milhões de requisições por segundo.

| Característica | CloudFront Functions |
|---|---|
| Eventos | **Somente viewer request e viewer response** |
| Linguagem | JavaScript (subconjunto ECMAScript; runtime enxuto) |
| Duração | Submilissegundos (limite muito baixo) |
| Acesso a rede, disco, SDK | **Não** |
| Acesso ao corpo da requisição | **Não** (só headers, URL, cookies, query string) |
| Onde roda | Em **todas** as edges |
| Preço | Muito mais barato que Lambda@Edge |
| Armazenamento | Opcional: **KeyValueStore** (pares chave-valor de leitura rápida) |

Casos de uso: redirecionamentos e reescritas de URL, normalização da cache key (ordenar query strings, minúsculas), adicionar headers de segurança (HSTS, CSP), validar JWT simples (sem chamada externa), roteamento por header `CloudFront-Viewer-Country`, autenticação básica, teste A/B por cookie.

Exemplo (viewer request): redireciona `www` para o domínio raiz e acrescenta `index.html` em URLs terminadas em `/`:

```javascript
// CloudFront Function (runtime cloudfront-js-2.0) — evento: viewer request
function handler(event) {
  var request = event.request;
  var host = request.headers.host.value;

  // 1) Redirecionar www.exemplo.com.br → exemplo.com.br com 301
  if (host === 'www.exemplo.com.br') {
    return {
      statusCode: 301,
      statusDescription: 'Moved Permanently',
      headers: { location: { value: 'https://exemplo.com.br' + request.uri } }
    };
  }

  // 2) SPA/site estático: /docs/ → /docs/index.html
  if (request.uri.endsWith('/')) {
    request.uri += 'index.html';
  }

  return request; // continua o fluxo normal (cache/origem)
}
```

Exemplo (viewer response): adiciona headers de segurança:

```javascript
// Evento: viewer response
function handler(event) {
  var response = event.response;
  response.headers['strict-transport-security'] =
    { value: 'max-age=63072000; includeSubDomains; preload' };
  response.headers['x-content-type-options'] = { value: 'nosniff' };
  return response;
}
```

> Para headers estáticos de segurança, uma **response headers policy** (nota de cache) resolve sem escrever código. Use função só quando houver lógica.

```bash
# Fluxo de publicação (resumo; confira os parâmetros na documentação)
aws cloudfront create-function --name redireciona-www \
  --function-config Comment="redirect",Runtime=cloudfront-js-2.0 \
  --function-code fileb://funcao.js
aws cloudfront test-function --name redireciona-www --if-match <ETag> \
  --event-object fileb://evento-teste.json      # testa na própria AWS com um evento simulado
aws cloudfront publish-function --name redireciona-www --if-match <ETag>
# Depois associe à "viewer request" do behavior (FunctionAssociations)
```

## Lambda@Edge

Funções **AWS Lambda** replicadas para as **regiões** e executadas em **Regional Edge Caches** (mais perto do usuário que a região original, mas não em todas as edges). Criadas em **us-east-1** e replicadas pelo CloudFront.

| Característica | Lambda@Edge |
|---|---|
| Eventos | **Viewer request, origin request, origin response, viewer response** |
| Linguagens | Node.js e Python (confirmar runtimes vigentes) |
| Duração | Segundos (limite maior, depende do evento) |
| Acesso a rede/SDK AWS | **Sim** (chamadas HTTP, DynamoDB, etc.) |
| Acesso ao corpo da requisição | **Sim** (em eventos de request, com opção de incluir o corpo) |
| Onde roda | Regional Edge Caches |
| Preço | Por requisição + duração (mais caro) |
| Criação | Região **us-east-1**; versão numerada (não aceita `$LATEST`) |

Casos de uso: autenticação com chamada a serviço externo (validar token em IdP), geração de resposta dinâmica, **reescrita de origem** com base em lógica (escolher origem por país/dispositivo), redimensionar imagens sob demanda, **SEO/pré-renderização**, acesso a DynamoDB para roteamento, manipulação do corpo de POST.

Exemplo (origin request): escolhe origem S3 diferente conforme o país do viewer (mantém resultado em cache):

```javascript
// Lambda@Edge (Node.js) — evento: origin request
// O header CloudFront-Viewer-Country precisa estar na origin request policy
exports.handler = async (event) => {
  const request = event.Records[0].cf.request;
  const pais = request.headers['cloudfront-viewer-country']
    ? request.headers['cloudfront-viewer-country'][0].value : 'US';

  if (pais === 'BR') {
    request.origin = {
      s3: {
        domainName: 'conteudo-br.s3.sa-east-1.amazonaws.com',
        region: 'sa-east-1',
        authMethod: 'origin-access-identity', // ajuste conforme OAC/OAI configurado
        path: '', customHeaders: {}
      }
    };
    request.headers['host'] = [{ key: 'host', value: 'conteudo-br.s3.sa-east-1.amazonaws.com' }];
  }
  return request;
};
```

Observações:

- Roles precisam permitir que `lambda.amazonaws.com` **e** `edgelambda.amazonaws.com` assumam a role.
- Logs vão para o CloudWatch Logs **na região onde a função executou** (muitas regiões), o que dificulta depuração.
- Remover uma função associada é lento: é preciso desassociar e aguardar a remoção das réplicas.

## Comparação e escolha

| Critério | **CloudFront Functions** | **Lambda@Edge** |
|---|---|---|
| Latência/overhead | Submilissegundo | Dezenas a centenas de ms |
| Eventos | Viewer request/response | Viewer e **origin** request/response |
| Escala | Milhões de req/s | Alta, porém menor |
| Rede/SDK/FS | Não | Sim |
| Corpo da requisição | Não | Sim |
| Linguagens | JavaScript restrito | Node.js, Python |
| Preço | Baixo | Mais alto |
| Tamanho de código | Pequeno (KB) | Maior (MB) |
| Depuração | Logs centralizados e `test-function` | Logs distribuídos por região |

Árvore de decisão:

```
Precisa de rede, SDK, corpo da requisição ou evento de ORIGEM?
        ├── Sim → Lambda@Edge
        └── Não → Tarefa simples e rápida (redirect, rewrite, header, JWT local)?
                    ├── Sim → CloudFront Functions
                    └── Não → Mova a lógica para a origem (ALB/Lambda regional)
```

Outras alternativas: **response headers policy** (headers estáticos, sem código), **WAF** (regras de bloqueio), **origem Lambda function URL** (lógica pesada sem estar na borda).

## Exemplo prático

Site SPA em S3 + CloudFront que precisa de: (1) redirecionar `www` para raiz, (2) reescrever rotas `/app/*` para `/index.html`, (3) validar um JWT de uma API protegida consultando o JWKS do IdP.

- Itens 1 e 2: **CloudFront Function** em *viewer request* (lógica simples, roda sempre, custo baixíssimo). Para o item 2 alternativa mais simples: *custom error response* mapeando 403/404 para `/index.html` com status 200.
- Item 3: se a validação for só da assinatura com chave pública embutida, ainda cabe numa **Function**. Se precisar **buscar o JWKS** na rede a cada rotação, use **Lambda@Edge** em *viewer request* (com cache em memória da função) ou valide o token na própria API.

## Casos de uso mapeados para a ferramenta certa

| Caso | CloudFront Functions | Lambda@Edge |
|---|---|---|
| Redirect/reescrita de URL | Ideal | Excesso |
| Normalizar cabeçalhos/cache key | Ideal | Excesso |
| Validar JWT simples (sem chamada externa) | Possível | Ideal para validações complexas |
| Autenticação com chamada a API externa | Não (sem rede) | Sim |
| Gerar resposta dinâmica/HTML | Limitado | Sim |
| A/B test por cookie | Ideal | Possível |
| Manipular corpo da requisição | Não | Sim |

> [!warning] Valores, limites e preços mudam; os exemplos deste material não foram executados. Limites de tempo, memória, tamanho e eventos suportados diferem entre as duas e mudam; confirme na documentação.

```
 Viewer ─► [viewer request] ─► cache? ─miss─► [origin request] ─► Origem
 Viewer ◄─ [viewer response] ◄──────────────── [origin response] ◄─ Origem
   CloudFront Functions: só viewer request/response (PoP, sub-ms)
   Lambda@Edge: os quatro eventos (Regional Edge Cache, mais recursos)
```

### Árvore de decisão

```
A lógica é curta, sem rede e só mexe em request/response de viewer?
├─ Sim ─► CloudFront Functions (mais barata e rápida)
└─ Não
    ├─ Precisa de rede, SDK AWS, corpo da requisição ou execução mais longa? ─► Lambda@Edge
    └─ Precisa só de lógica na origem (não na borda)? ─► Lambda normal / API Gateway
```

## Cuidados de operação

1. **Teste** a função no console (aba Test) antes de associar.
2. Lambda@Edge é criada em **us-east-1** e replicada; logs aparecem na região do PoP que executou.
3. Erros em funções de viewer afetam **todas** as requisições do behavior: faça deploy gradual (behavior específico primeiro).
4. Versione e mantenha rollback pronto (associação à versão anterior).

## Troubleshooting

| Sintoma | Causa provável | Ação |
|---|---|---|
| 5xx em todo o behavior | Erro na função de viewer | Reverter associação |
| Função Lambda@Edge não cria | Região incorreta/role sem trust | Criar em us-east-1 com role para edgelambda |
| Cache hit caiu | Função altera a chave de cache | Revisar manipulação de cabeçalhos |
| Logs não aparecem | Procurando na região errada | Consultar o log group da região do PoP |

## Custo

CloudFront Functions cobram por invocação (bem mais barato); Lambda@Edge cobra por requisição e duração. Em alto volume, mover lógica simples de Lambda@Edge para Functions reduz a conta de forma relevante.

## Erros comuns e armadilhas

- **Usar Lambda@Edge para tarefas triviais:** mais caro e lento que uma Function.
- **Esperar rede/SDK em CloudFront Functions:** não existe; a função falha na publicação ou em tempo de execução.
- **Criar Lambda@Edge fora de us-east-1** ou usar `$LATEST`: não pode ser associado.
- **Lógica pesada em viewer request:** roda em toda requisição e eleva custo e latência; mova para origin request quando o resultado é cacheável.
- **Esquecer headers necessários na origin request policy** (ex.: `CloudFront-Viewer-Country`): a função não os vê.
- **Falta de testes:** use `test-function` e eventos de teste; Lambda@Edge é difícil de depurar em produção.
- **Esquecer permissões de role** (`edgelambda.amazonaws.com`).
- **Alterar demais a cache key** dentro da função: derruba o hit ratio.
- **Tentar deletar rapidamente uma Lambda@Edge:** réplicas persistem por um tempo após a desassociação.

## 🧩 Quiz de Fixação

1. Que eventos cada tecnologia suporta?
2. Você precisa redirecionar `www` para o domínio raiz e normalizar a caixa da URL. Qual escolher e por quê?
3. Uma regra exige consultar o DynamoDB para decidir a origem. Qual tecnologia e em qual evento?

**Respostas:**
1) **CloudFront Functions:** somente *viewer request* e *viewer response*. **Lambda@Edge:** os quatro (*viewer request/response* e *origin request/response*).
2) **CloudFront Functions** em *viewer request*: lógica simples, sem rede, roda em todas as edges com latência mínima e custo baixo.
3) **Lambda@Edge** em *origin request*: precisa de acesso a serviço AWS (rede/SDK), que Functions não permite; em origin request roda apenas em cache miss e o resultado pode ser reaproveitado do cache.

**Questões complementares:**

4. Por que um erro em função de viewer é crítico?
5. Em qual região se cria uma função Lambda@Edge?
6. Qual função usar para autenticação que chama uma API externa?

**Respostas das questões complementares:**
4) Porque executa em todas as requisições do behavior associado, então uma falha gera 5xx em escala; teste e reverta rápido.
5) Em us-east-1, de onde é replicada para as localizações de borda.
6) Lambda@Edge, pois CloudFront Functions não tem acesso à rede.
