### Cache policies, TTL, cache keys e invalidação — como aumentar o cache hit ratio

> [!warning] Aviso
> Valores de TTL padrão, políticas gerenciadas, limites de invalidação, preços de invalidação e nomes de recursos mudam. Confirme na documentação do CloudFront. Os comandos e JSONs abaixo **não foram executados**.

O desempenho de uma distribuição do CloudFront se resume a uma pergunta: **quantas requisições são respondidas pela borda sem ir à origem?** Essa proporção é o **cache hit ratio**. Três ideias controlam o resultado: a **cache key** (o que torna dois objetos "diferentes"), o **TTL** (por quanto tempo uma cópia é válida) e a **invalidação/versionamento** (como trocar uma cópia antes do TTL acabar). **Analogia:** a edge é um **armário de arquivos**. A *cache key* é a **etiqueta da pasta**: se a etiqueta incluir detalhes demais (hora da consulta, nome do usuário), cada pedido vira uma pasta nova e o armário nunca é reaproveitado. O *TTL* é a **data de validade** escrita na pasta. A *invalidação* é pedir ao arquivista para **jogar fora** pastas antes da validade.

## A cache key

Quando uma requisição chega, o CloudFront calcula a **cache key** e procura o objeto. Por padrão a chave é formada por **domínio da distribuição + caminho da URL**. Você pode acrescentar:

| Componente | Entra na chave quando... | Risco |
|---|---|---|
| **Query strings** | A origem devolve conteúdo diferente por parâmetro (`?lang=pt`) | Parâmetros de rastreio (`utm_*`) multiplicam objetos idênticos |
| **Headers** | Variação por `Accept-Language`, `CloudFront-Viewer-Country`, etc. | Incluir `User-Agent` ou `Host` cru gera milhares de variantes |
| **Cookies** | Conteúdo depende de sessão ou preferência | Cookie de sessão na chave = cache quase inútil |
| **Encoding** | Gzip/Brotli (via `EnableAcceptEncodingGzip/Brotli`) | Necessário para servir versões comprimidas corretas |

```
Pedido A: /produto/42?utm_source=email      ┐
Pedido B: /produto/42?utm_source=instagram  ├─ chave INCLUINDO utm_*  → 3 objetos (3 misses)
Pedido C: /produto/42                       ┘
                                              chave SEM query strings → 1 objeto (2 hits)
```

> **Regra de ouro:** coloque na cache key **somente** o que realmente muda a resposta. O resto vai (se necessário) para a origem por outro caminho, a *origin request policy*.

## Cache policy × Origin request policy × Response headers policy

São três políticas **reutilizáveis** que você anexa a um cache behavior:

| Política | Pergunta que responde | Afeta a cache key? |
|---|---|---|
| **Cache policy** | Quais valores (headers, cookies, query strings) formam a chave? Quais TTLs mínimo/padrão/máximo? Compressão? | **Sim** |
| **Origin request policy** | O que mais devo **enviar à origem** em um miss (além do que está na chave)? | **Não** |
| **Response headers policy** | Que headers de **resposta** adicionar (CORS, HSTS, CSP, `X-Frame-Options`)? | Não |

```
        Viewer request
             │
   ┌─────────▼─────────┐
   │   CACHE POLICY    │  → monta a CACHE KEY e decide TTL
   └─────────┬─────────┘
        miss │
   ┌─────────▼─────────┐
   │ ORIGIN REQUEST    │  → acrescenta headers/cookies/query strings
   │     POLICY        │    para a ORIGEM (sem entrar na chave)
   └─────────┬─────────┘
             ▼
          Origem
```

Exemplo de uso: a origem precisa do header `Authorization` para autenticar, mas a resposta é igual para todos os usuários autorizados. Coloque `Authorization` na **origin request policy** (a origem recebe), não na cache policy (não fragmenta o cache).

### Políticas gerenciadas pela AWS (as mais usadas)

| Nome | Uso típico |
|---|---|
| **CachingOptimized** | Conteúdo estático (S3): chave mínima, compressão, TTL longo |
| **CachingDisabled** | APIs e conteúdo dinâmico: **sem cache** |
| **Managed-CachingOptimizedForUncompressedObjects** | Objetos já comprimidos (vídeo, zip) |
| **AllViewer** (origin request) | Repassa tudo do viewer à origem |
| **CORS-S3Origin** (origin request) | Repassa headers CORS para S3 |

Os nomes e IDs exatos ficam na documentação; confira antes de referenciá-los em IaC.

## TTL — por quanto tempo uma cópia vale

O CloudFront combina **o que a origem diz** (`Cache-Control`, `Expires`) com **os limites da cache policy**:

| TTL na cache policy | Significado |
|---|---|
| **MinTTL** | Tempo mínimo que o objeto fica em cache, mesmo que a origem diga menos |
| **DefaultTTL** | Usado quando a origem **não** envia `Cache-Control`/`Expires` |
| **MaxTTL** | Teto: mesmo que a origem diga 1 ano, o CloudFront limita a este valor |

```
Origem envia Cache-Control: max-age=600 ; Policy: Min=0, Default=86400, Max=3600
→ TTL efetivo = 600 s   (dentro do intervalo Min..Max)

Origem envia max-age=999999 ; Policy Max=3600
→ TTL efetivo = 3600 s  (limitado pelo Max)

Origem NÃO envia nada ; Policy Default=86400
→ TTL efetivo = 86400 s
```

Observações:

- `Cache-Control: no-store`, `no-cache` ou `private` na resposta: com `MinTTL = 0`, o CloudFront **respeita** e não guarda; se `MinTTL > 0`, ele guarda mesmo assim. Cuidado com isso em conteúdo personalizado.
- Com a origem enviando `s-maxage`, ele tem precedência para caches compartilhados (CDN).
- Quando a cópia expira, o CloudFront **revalida** com a origem usando `If-None-Match`/`If-Modified-Since`; se a origem responde `304 Not Modified`, a cópia é renovada sem retransferir o corpo (`RefreshHit from cloudfront`).
- Erros (4xx/5xx) têm **TTL de cache de erro** separado (*error caching minimum TTL*, por padrão curto), configurável em *custom error responses*.

### Estratégia por tipo de conteúdo

| Conteúdo | Estratégia |
|---|---|
| Assets versionados (`app.3fa9c1.js`) | `Cache-Control: public, max-age=31536000, immutable` — nome muda a cada build |
| HTML de SPA (`index.html`) | TTL curto (segundos/minutos) ou `no-cache` para sempre revalidar |
| Imagens de produto | Dias/semanas; invalide ou versione quando trocar |
| API pública, GET idempotente | TTL curto (5–60 s) já derruba a carga da origem em picos |
| API autenticada/personalizada | `CachingDisabled` (ou chave com identidade, com muito cuidado) |

## Invalidação × versionamento

Para trocar um objeto antes do TTL há duas abordagens:

| Critério | **Invalidação** | **Versionamento de nome** |
|---|---|---|
| Como | `create-invalidation` com caminhos | Novo nome/query (`app.v2.js`, `?v=2`) |
| Velocidade | Em geral segundos a minutos para propagar | Imediata (é outro objeto) |
| Custo | Primeiros caminhos por mês gratuitos; depois cobrança por caminho (confirmar valores) | Nenhum |
| Escopo | Pode usar curinga `/imagens/*` (conta como 1 caminho) | Exige que o HTML/refência aponte para o novo nome |
| Quando usar | Corrigir conteúdo publicado, `index.html`, emergência | Padrão para assets de build |

```bash
# Invalidar caminhos específicos e um prefixo inteiro
aws cloudfront create-invalidation \
  --distribution-id E123ABCDEF \
  --paths "/index.html" "/imagens/*"
# /imagens/* conta como UM caminho; útil para lotes
# A invalidação remove da cache das edges; a próxima requisição vai à origem

# Acompanhar o status (InProgress → Completed)
aws cloudfront list-invalidations --distribution-id E123ABCDEF
```

> Invalidar é uma **rede de segurança**, não o fluxo normal. O fluxo saudável de front-end é: *build com hash no nome → TTL de 1 ano → só o `index.html` com TTL curto*.

## Como aumentar o cache hit ratio (checklist)

1. **Reduza a cache key:** remova cookies, headers e query strings desnecessários; ignore parâmetros de rastreio.
2. **Normalize as variações:** ordene query strings, padronize caixa de letras de URLs (a chave é sensível a maiúsculas/minúsculas) — pode ser feito numa CloudFront Function.
3. **Aumente os TTLs** de conteúdo estático e adote nomes com hash.
4. **Use compressão** (gzip/Brotli) por meio da cache policy, em vez de variar por `Accept-Encoding` manualmente.
5. **Habilite o Origin Shield** quando houver muitas edges disputando a mesma origem (veja a nota de custo e operação).
6. **Separe behaviors:** estático com cache longo, dinâmico sem cache; não misture tudo no padrão `*`.
7. **Não repasse `Host`/`User-Agent`/`Referer` para a chave** sem necessidade.
8. **Meça:** a aba *Cache statistics* do console e as métricas de `CacheHitRate` (métricas adicionais) mostram a taxa por distribuição.

## Exemplo prático

Cache policy personalizada para um catálogo de produtos: varia por `lang` e ignora o resto.

```json
{
  "Name": "catalogo-por-idioma",
  "Comment": "Chave = caminho + query string lang; compressao ligada",
  "MinTTL": 0,
  "DefaultTTL": 3600,
  "MaxTTL": 86400,
  "ParametersInCacheKeyAndForwardedToOrigin": {
    "EnableAcceptEncodingGzip": true,
    "EnableAcceptEncodingBrotli": true,
    "HeadersConfig": { "HeaderBehavior": "none" },
    "CookiesConfig": { "CookieBehavior": "none" },
    "QueryStringsConfig": {
      "QueryStringBehavior": "whitelist",
      "QueryStrings": { "Quantity": 1, "Items": ["lang"] }
    }
  }
}
```

```bash
# Criar a política a partir do arquivo acima
aws cloudfront create-cache-policy --cache-policy-config file://catalogo.json
# O retorno traz o Id; use-o em CachePolicyId do behavior desejado

# Verificar o efeito: 2ª chamada deve ser Hit; outra ?utm_source não cria novo objeto
curl -sI "https://www.exemplo.com.br/catalogo?lang=pt&utm_source=a" | grep -i x-cache
curl -sI "https://www.exemplo.com.br/catalogo?lang=pt&utm_source=b" | grep -i x-cache
# Esperado: Miss na primeira, Hit na segunda (utm_source fora da chave)
```

Explicação: apenas `lang` entra na chave; `utm_source` é descartado. As duas URLs resolvem para o mesmo objeto, então a segunda é um *hit*. Nota: `QueryStringBehavior: whitelist` descarta (não repassa à origem) os parâmetros fora da lista; se a origem precisa deles, use uma *origin request policy*.

## Erros comuns e armadilhas

- **Cookie de sessão na cache key:** cada usuário gera um objeto próprio; hit ratio próximo de zero.
- **Encaminhar "todas as query strings"** sem necessidade: `utm_*`, `fbclid` e timestamps fragmentam o cache.
- **Cache de conteúdo personalizado sem identificar o usuário:** um usuário vê a página de outro. Em dúvida, `CachingDisabled`.
- **`MinTTL > 0` com respostas `private`/`no-store`:** o CloudFront passa a guardar o que a origem pediu para não guardar.
- **Invalidar sempre em vez de versionar:** custo e fricção; e o navegador do usuário ainda pode ter cópia local (TTL do browser).
- **Esquecer o cache do navegador:** invalidar o CloudFront não limpa o cache local; use `Cache-Control` adequado.
- **URLs com maiúsculas diferentes:** `/Logo.png` e `/logo.png` são objetos distintos.
- **Confundir cache policy com origin request policy:** colocar `Authorization` na primeira fragmenta o cache; na segunda apenas repassa.

## 🧩 Quiz de Fixação

1. Qual a diferença entre cache policy e origin request policy, e quando usar cada uma?
2. A origem envia `Cache-Control: max-age=7200`, e a cache policy tem Min=0, Default=3600, Max=3600. Qual o TTL efetivo? E se a origem não enviasse o header?
3. Um site tem `app.js` trocado a cada deploy e sofre com usuários vendo versões antigas. Qual estratégia é melhor: invalidar ou versionar? Por quê?

**Respostas:**
1) A **cache policy** define o que compõe a **cache key** e os TTLs; tudo que entra nela diferencia objetos. A **origin request policy** define o que mais é **enviado à origem** em um miss, sem alterar a chave. Use a primeira para variações que realmente mudam a resposta (ex.: `lang`) e a segunda para informações que a origem precisa mas não alteram o conteúdo (ex.: `Authorization` em conteúdo igual para todos).
2) O TTL efetivo é **3600 s**: a origem pede 7200, mas o `MaxTTL` limita. Sem o header, vale o `DefaultTTL`, também 3600 s.
3) **Versionar** (nome com hash por build, TTL longo). É imediato, gratuito e funciona também para o cache do navegador. A invalidação é uma exceção para correções urgentes e para o `index.html`, que referencia o novo nome.
