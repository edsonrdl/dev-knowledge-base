### Acesso privado à origem e ao conteúdo — OAC, signed URLs, signed cookies e HTTPS

> [!warning] Aviso
> Recursos de segurança do CloudFront (OAC, VPC origins, key groups, políticas TLS) evoluem e algumas opções antigas (como OAI) estão em desuso. Confirme na documentação. Os JSONs e comandos **não foram executados**.

Segurança no CloudFront tem **duas perguntas diferentes**, que costumam ser confundidas:

1. **Quem pode acessar a origem?** Só o CloudFront, ou qualquer um que descubra o endereço? (*acesso privado à origem*: OAC, prefix list, VPC origin, header secreto.)
2. **Quem pode acessar o conteúdo pelo CloudFront?** Qualquer visitante, ou só quem tem permissão? (*acesso restrito ao conteúdo*: signed URLs, signed cookies.)

E uma terceira camada transversal: **HTTPS** nos dois trechos (viewer → CloudFront e CloudFront → origem).

**Analogia:** o CloudFront é uma **portaria de prédio**. Proteger a origem é **trancar a porta dos fundos** para que ninguém entre sem passar pela portaria. Restringir o conteúdo é **exigir um crachá** (URL assinada) na portaria. HTTPS é o **corredor blindado** por onde as pessoas e os pacotes passam.

```
          Viewer ──(HTTPS)──► CLOUDFRONT ──(HTTPS)──► ORIGEM
             │                    │                      ▲
   signed URL / cookie            │               OAC (S3) / VPC origin /
   (quem pode ver?)               │               prefix list (quem pode chamar?)
                                  ▼
                               WAF / Shield (próxima nota)
```

## Parte 1 — Proteger a origem

### S3: Origin Access Control (OAC)

O **OAC** permite que o CloudFront acesse um bucket S3 **privado** (com o *Block Public Access* ligado), assinando as requisições com **SigV4**. É o substituto recomendado do antigo **OAI** (Origin Access Identity), que não suporta SSE-KMS nem todas as regiões/métodos.

Fluxo:

```
 Viewer ──► CloudFront ──(requisição assinada SigV4, principal cloudfront.amazonaws.com)──► S3 (privado)
                                                      │
                          bucket policy: permite s3:GetObject somente se
                          AWS:SourceArn == ARN da DISTRIBUIÇÃO
```

Bucket policy típica:

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Sid": "PermitirSomenteCloudFrontViaOAC",
    "Effect": "Allow",
    "Principal": { "Service": "cloudfront.amazonaws.com" },
    "Action": "s3:GetObject",
    "Resource": "arn:aws:s3:::meu-site-exemplo/*",
    "Condition": {
      "StringEquals": {
        "AWS:SourceArn": "arn:aws:cloudfront::111122223333:distribution/E123ABCDEF"
      }
    }
  }]
}
```

Pontos de atenção:

- Use o **endpoint REST** do bucket. O *website endpoint* não suporta OAC.
- Com **SSE-KMS**, a chave KMS também precisa autorizar o principal `cloudfront.amazonaws.com` (condição `AWS:SourceArn`). Veja [[8. DevOps e Gerenciamento de Infraestrutura/CLOUD COMPUTING/AWS (AMAZON WEB SERVICE)/2. Segurança e Conformidade/2.3 Capacidades de gerenciamento de acesso da AWS/2.3.2. Serviços de segurança/2.3.2.3. AWS WAF|AWS WAF]] para a camada de filtragem, e [[8. DevOps e Gerenciamento de Infraestrutura/CLOUD COMPUTING/AWS (AMAZON WEB SERVICE)/2. Segurança e Conformidade/2.3 Capacidades de gerenciamento de acesso da AWS/2.3.2. Serviços de segurança/2.3.2.7. AWS Key Management Service (KMS)|AWS KMS]] para a política de chave.
- Sem o objeto, o S3 devolve **403** (não 404) quando o principal não tem `s3:ListBucket`; conceda `ListBucket` se quiser que ausências retornem 404 corretamente.
- Para o OAC também existem suportes para **Lambda function URLs** e MediaStore/MediaPackage (verifique a documentação).

### Origens não S3 (ALB, EC2, API)

Quando a origem é uma aplicação (ALB, EC2, API Gateway), não há OAC. Opções, da mais forte para a mais fraca:

| Opção | Como funciona | Força |
|---|---|---|
| **VPC origin** | O CloudFront acessa um ALB/NLB/EC2 em **subnet privada** via ENI gerenciada; a origem não tem IP público | **Alta** (a origem sai da internet) |
| **Managed prefix list** | Security Group da origem só aceita a lista `com.amazonaws.global.cloudfront.origin-facing` | Média-alta (qualquer distribuição CloudFront de qualquer conta ainda passa) |
| **Header secreto** (custom header) | CloudFront injeta `X-Origin-Verify: <segredo>`; ALB/WAF rejeita requisições sem ele | Média (segredo precisa ser rotacionado) |
| **Mutual TLS / SG + header** | Combinação das anteriores | Defesa em profundidade |

Recomendação prática: **VPC origin** quando disponível para o seu caso; senão **prefix list + header secreto** em conjunto, já que a prefix list sozinha também admite distribuições de terceiros.

## Parte 2 — Restringir quem vê o conteúdo

Por padrão qualquer pessoa com a URL pública da distribuição acessa o conteúdo. Para restringir:

### Signed URLs e Signed Cookies

| Critério | **Signed URL** | **Signed Cookie** |
|---|---|---|
| Escopo | **Um** objeto (uma URL) | **Vários** objetos (ex.: `/premium/*`) |
| Como é entregue | Na própria URL (`?Expires=...&Signature=...&Key-Pair-Id=...`) | Cookies `CloudFront-Policy/Signature/Key-Pair-Id` |
| Caso típico | Link de download único, arquivo avulso | Área de assinantes, vídeo HLS com muitos segmentos |
| Mudar URLs? | Sim | **Não** (URLs ficam iguais) |
| Compatibilidade | Clientes que não suportam cookies | Navegadores/apps que mantêm cookies |

Como funciona: sua aplicação (que conhece o usuário) **assina** uma política com uma **chave privada**; o CloudFront valida a assinatura com a **chave pública** cadastrada num **trusted key group** do behavior.

```
 1. Usuário autentica no SEU app  ─►  app decide que ele pode ver /premium/video.mp4
 2. App assina (RSA) {recurso, expiração, IP opcional} com a CHAVE PRIVADA
 3. App devolve  https://dxxxx.cloudfront.net/premium/video.mp4?Expires=...&Signature=...&Key-Pair-Id=K...
 4. CloudFront valida a assinatura com a CHAVE PÚBLICA (key group) e a expiração  → entrega ou 403
```

Em **canned policy** você define só URL e expiração; em **custom policy** pode adicionar janela de início, faixa de **IP** do cliente e curingas no recurso.

```bash
# Gerar o par de chaves RSA (a pública será cadastrada no CloudFront)
openssl genrsa -out private_key.pem 2048
openssl rsa -pubout -in private_key.pem -out public_key.pem

# Cadastrar a chave pública e criar o key group (resumo; confira os parâmetros na documentação)
aws cloudfront create-public-key --public-key-config \
  "CallerReference=chave-2025,Name=chave-app,EncodedKey=$(cat public_key.pem)"
aws cloudfront create-key-group --key-group-config \
  "Name=app-grupo,Items=ID_DA_CHAVE_PUBLICA"
# Depois associe o key group ao behavior (TrustedKeyGroups) e exija "Restrict viewer access"

# Gerar uma URL assinada (CLI): válida até a data indicada
aws cloudfront sign \
  --url "https://dxxxx.cloudfront.net/premium/video.mp4" \
  --key-pair-id K2JCJMDEHXQW5F \
  --private-key file://private_key.pem \
  --date-less-than 2026-12-31T23:59:59Z
# A URL assinada pode ser distribuída ao usuário; a chave privada nunca sai do seu backend
```

Observações:

- Use **trusted key groups** (não o antigo "trusted signer" com key pairs da conta-raiz).
- Guarde a **chave privada** em um cofre (Secrets Manager); nunca no front-end.
- Prazo curto de expiração reduz o risco de compartilhamento do link. Para limitar a um usuário, use custom policy com IP (com a ressalva de IPs móveis).
- **S3 pre-signed URLs** (gerados pelo S3) são outra coisa: servem acesso direto ao S3, sem passar pelo CloudFront.

### Alternativas para controle de acesso

| Necessidade | Opção |
|---|---|
| Autenticação por JWT/token em cada request | CloudFront Function ou Lambda@Edge validando o token |
| Bloquear países | Geo restriction (próxima nota) |
| Bloquear por IP/bot/regra | AWS WAF |
| Restringir por referer | Header `Referer` via WAF (fraco, facilmente forjado) |

## Parte 3 — HTTPS nos dois trechos

### Viewer → CloudFront

- **Viewer protocol policy** do behavior: `allow-all`, `redirect-to-https` (comum) ou `https-only`.
- **Certificado:** o padrão `*.cloudfront.net` ou um certificado do **ACM em us-east-1** para o seu domínio.
- **Security policy** (versão mínima de TLS e cifras): escolha uma política atual, como TLSv1.2 ou superior; evite TLS 1.0/1.1.
- **HSTS:** adicione `Strict-Transport-Security` por meio de uma *response headers policy*.

### CloudFront → Origem

- **Origin protocol policy:** `https-only` para origens custom (ou `match-viewer`).
- O certificado da origem precisa ser **válido e coincidir com o nome** usado (não aceita autoassinado). Sem isso o CloudFront devolve **502**.
- Para S3 REST via OAC, o tráfego já é HTTPS.

```
  Navegador ──TLS 1.2/1.3──► Edge ──TLS (https-only)──► ALB (certificado ACM do domínio da origem)
```

Dica: nomeie a origem com um **domínio seu** (ex.: `origem.exemplo.com.br`) com certificado ACM no ALB, em vez de usar o DNS padrão do ALB, que não combina com um certificado seu.

## Exemplo prático

Cenário: site de cursos. Vídeos ficam em S3 privado e só alunos matriculados podem ver. O site usa Route 53 → CloudFront → S3.

1. Bucket `cursos-videos` com *Block Public Access* ligado e **bucket policy do OAC** (acima).
2. Behavior `/videos/*` com **Restrict viewer access = Yes**, apontando para o key group `app-grupo`.
3. Backend (Lambda/ECS) verifica a matrícula e gera um **signed cookie** (`CloudFront-*`) com política `https://cursos.exemplo.com.br/videos/*` e expiração em 4 h.
4. O player HLS carrega manifesto e segmentos com os cookies automaticamente. Sem cookie válido → **403**.
5. Resultado: ninguém acessa o bucket diretamente, e os links não funcionam fora da sessão do aluno.

## Erros comuns e armadilhas

- **Bucket público "porque dá certo":** perde o controle; use OAC com *Block Public Access*.
- **Usar o website endpoint do S3 esperando OAC:** não funciona.
- **Esquecer a chave KMS** (SSE-KMS): o CloudFront recebe `403`/`AccessDenied`.
- **Confundir OAI com OAC:** OAI é legado; novos projetos usam OAC.
- **Assinar no front-end:** a chave privada fica exposta.
- **Expiração longa demais** em signed URLs: o link vaza e continua válido.
- **Confiar só na prefix list do CloudFront:** qualquer distribuição pode alcançar a origem; combine com header secreto ou use VPC origin.
- **Certificado da origem inválido/autoassinado:** erro 502.
- **Permitir HTTP no viewer** sem redirecionar: cookies e links assinados trafegam em claro.
- **Esquecer a política de cache dos conteúdos assinados:** a assinatura é validada pelo CloudFront antes do cache, mas verifique que a cache key não inclua os parâmetros de assinatura de forma que gere um objeto por usuário.

## 🧩 Quiz de Fixação

1. Qual a diferença entre proteger a origem e restringir o conteúdo? Dê um mecanismo para cada.
2. Quando usar signed cookies em vez de signed URLs?
3. Um ALB público é origem do CloudFront. Como impedir acesso direto, e por que a managed prefix list sozinha não basta?

**Respostas:**
1) *Proteger a origem* impede que alguém acesse o servidor sem passar pelo CloudFront (ex.: **OAC** para S3, **VPC origin** para ALB). *Restringir o conteúdo* controla quem consegue obter objetos pelo CloudFront (ex.: **signed URLs/cookies**). Um não substitui o outro.
2) Quando é preciso dar acesso a **vários arquivos** sem alterar as URLs (área de assinantes, vídeo HLS com milhares de segmentos) ou quando não se quer expor assinaturas na URL. Signed URL serve melhor para um único objeto/link de download.
3) Usar **VPC origin** (ALB em subnet privada) ou combinar **Security Group com a prefix list do CloudFront** e um **header secreto** validado no ALB/WAF. A prefix list sozinha libera os IPs do CloudFront para **todas as distribuições de todas as contas**, então um terceiro poderia criar uma distribuição apontando para o seu ALB.
