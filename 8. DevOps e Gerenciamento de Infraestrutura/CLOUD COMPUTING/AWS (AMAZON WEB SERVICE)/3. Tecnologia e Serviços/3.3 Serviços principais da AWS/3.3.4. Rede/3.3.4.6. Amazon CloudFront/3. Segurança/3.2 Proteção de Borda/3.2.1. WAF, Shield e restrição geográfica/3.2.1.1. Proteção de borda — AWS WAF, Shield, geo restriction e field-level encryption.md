### Proteção de borda — AWS WAF, Shield, geo restriction e field-level encryption

> [!warning] Aviso
> Regras gerenciadas, preços de WAF/Shield Advanced, limites de Web ACLs e opções do CloudFront mudam com frequência. Confirme na documentação. Os exemplos **não foram executados**.

Um dos grandes ganhos de colocar o CloudFront na frente da aplicação é **bloquear o tráfego ruim na borda**, longe da sua origem: ataques DDoS, injeções, bots, países indesejados e até dados sensíveis expostos em trânsito. Quatro mecanismos, cada um com um papel:

| Mecanismo | Pergunta que responde | Camada |
|---|---|---|
| **AWS Shield** | Esse tráfego é um ataque volumétrico (DDoS)? | 3 e 4 (e 7 com Advanced + WAF) |
| **AWS WAF** | Essa requisição HTTP é maliciosa ou indesejada? | 7 |
| **Geo restriction** | De que país vem a requisição? | Geografia |
| **Field-level encryption** | Esse campo de formulário precisa ser lido só por quem tem a chave? | Dados |

**Analogia:** a borda é a **portaria de um condomínio**. O Shield é a **barreira anti-multidão** (impede que mil pessoas bloqueiem a entrada). O WAF é o **porteiro que confere a mala** de cada visitante (SQL injection, XSS, bots). A geo restriction é a **lista de bairros permitidos**. A field-level encryption é o **envelope lacrado** que só o cofre do prédio consegue abrir.

```
 Internet ─► [Shield: DDoS L3/L4] ─► [Geo restriction] ─► [WAF: regras L7] ─► Cache/Origem
                                                                     └─ Field-level encryption (campos POST)
```

## AWS Shield no CloudFront

Notas gerais: [[8. DevOps e Gerenciamento de Infraestrutura/CLOUD COMPUTING/AWS (AMAZON WEB SERVICE)/2. Segurança e Conformidade/2.3 Capacidades de gerenciamento de acesso da AWS/2.3.2. Serviços de segurança/2.3.2.2. AWS Shield (Standard e Advanced)|AWS Shield (Standard e Advanced)]].

| Aspecto | **Shield Standard** | **Shield Advanced** |
|---|---|---|
| Custo | Incluído, sem custo extra | Assinatura mensal + uso (confirmar valores) |
| Cobertura | Ataques comuns de camada 3 e 4 | Ataques maiores/sofisticados, inclusive L7 com WAF |
| Resposta | Automática | Visibilidade detalhada, equipe de resposta (SRT), proteção de custo contra picos causados por DDoS |
| Recursos | CloudFront, Route 53, Global Accelerator... | Também ALB, NLB, EIP, etc. |

Em resumo: **toda** distribuição CloudFront já tem Shield Standard. Quem tem exigência de disponibilidade crítica avalia o Advanced, mas esta decisão é de negócio/custo, não de configuração do CloudFront.

> Usar CloudFront (e Route 53) como porta de entrada já **absorve** grande parte de ataques volumétricos, pois a capacidade da borda é muito maior que a de uma única origem.

## AWS WAF no CloudFront

O **WAF** inspeciona requisições HTTP/S na edge e as **permite, bloqueia, conta ou desafia (CAPTCHA/Challenge)** segundo regras agrupadas em uma **Web ACL**. Notas gerais: [[8. DevOps e Gerenciamento de Infraestrutura/CLOUD COMPUTING/AWS (AMAZON WEB SERVICE)/2. Segurança e Conformidade/2.3 Capacidades de gerenciamento de acesso da AWS/2.3.2. Serviços de segurança/2.3.2.3. AWS WAF|AWS WAF]].

Ponto específico do CloudFront: uma Web ACL associada a uma distribuição precisa ser criada com **escopo CLOUDFRONT**, que é **global** e **só pode ser gerenciada na região us-east-1**.

### Tipos de regras úteis

| Regra | Protege contra |
|---|---|
| **Managed rule groups da AWS** (Core rule set, Known bad inputs, SQL database, Linux/PHP/WordPress, Admin protection) | OWASP Top 10: SQLi, XSS, LFI, entradas conhecidamente maliciosas |
| **Amazon IP reputation list** / **Anonymous IP list** | Origens com má reputação, proxies/VPNs anônimos |
| **Rate-based rule** | Excesso de requisições por IP (força bruta, scraping, DDoS L7) |
| **Bot Control / ATP / ACFP** (grupos pagos) | Bots, takeover de contas, fraude em cadastro |
| **Regras próprias** | Bloquear caminho, header, tamanho de corpo, IP específico, regex |
| **Geo match** | Bloqueio/permissão por país dentro do WAF |

### Ordem de decisão

Regras são avaliadas por **prioridade** (número menor primeiro). A **ação** pode ser `Allow`, `Block`, `Count` (apenas registra), `CAPTCHA` ou `Challenge`. Sempre comece novas regras em **Count** para observar falsos positivos antes de bloquear.

```
Requisição → Regra 1 (IP deny list)      → Block?
           → Regra 2 (rate-based 2000/5min) → Block?
           → Regra 3 (managed Core set)  → Block?
           → ... → ação padrão da Web ACL (Allow ou Block)
```

### Exemplo — associando uma Web ACL a uma distribuição

```bash
# Web ACL com escopo CLOUDFRONT deve ser criada na região us-east-1
aws wafv2 create-web-acl \
  --name protecao-site \
  --scope CLOUDFRONT \
  --region us-east-1 \
  --default-action Allow={} \
  --visibility-config SampledRequestsEnabled=true,CloudWatchMetricsEnabled=true,MetricName=protecao-site \
  --rules file://regras.json
# regras.json: lista de regras (ex.: AWSManagedRulesCommonRuleSet + rate-based)

# A associação com o CloudFront é feita no campo WebACLId da distribuição
# (console: aba Security → Web Application Firewall; IaC: web_acl_id na distribuição)
```

Trecho ilustrativo de uma regra rate-based em `regras.json`:

```json
{
  "Name": "limite-por-ip",
  "Priority": 1,
  "Statement": {
    "RateBasedStatement": { "Limit": 1000, "AggregateKeyType": "IP" }
  },
  "Action": { "Block": {} },
  "VisibilityConfig": {
    "SampledRequestsEnabled": true,
    "CloudWatchMetricsEnabled": true,
    "MetricName": "limite-por-ip"
  }
}
```

Explicação: bloqueia IPs que ultrapassem o limite de requisições na janela do WAF (o limite mínimo e a janela são definidos pelo serviço; confirme na documentação). O CloudFront também pode ser configurado para ter a Web ACL ativada pelo console com "pacotes de proteção" simplificados, mas o recurso por baixo é o mesmo.

### WAF no CloudFront × WAF no ALB

| Critério | Web ACL no **CloudFront** | Web ACL no **ALB** |
|---|---|---|
| Onde bloqueia | **Na borda**, antes da origem | Dentro da região, depois da internet |
| Efeito no custo | Tráfego malicioso não chega à origem nem custa transferência | A requisição já chegou na região |
| Região de gestão | us-east-1 (escopo global) | A mesma região do ALB |
| Quando usar | Sites e APIs públicas atrás do CloudFront | Aplicações sem CloudFront ou com tráfego interno |

Na dúvida: filtre na **borda** e feche a origem para que ela só aceite o CloudFront.

## Geo restriction (restrição geográfica)

Recurso nativo e **gratuito** do CloudFront que bloqueia ou permite acesso **por país**, usando um banco de geolocalização de IPs.

| Modo | Efeito |
|---|---|
| **Allow list** | Somente os países listados acessam; os demais recebem **403** |
| **Block list** | Os países listados são bloqueados; os demais acessam |

```bash
# Trecho da DistributionConfig (ilustrativo)
"Restrictions": {
  "GeoRestriction": {
    "RestrictionType": "whitelist",
    "Quantity": 2,
    "Items": ["BR", "PT"]
  }
}
# RestrictionType: whitelist (allow) | blacklist (block) | none
# Códigos ISO 3166-1 alfa-2
```

Limitações importantes:

- A geolocalização por IP **não é perfeita**; VPN e proxies burlam.
- Bloqueia a **distribuição inteira** (não por behavior). Para controle mais fino use **WAF geo match** (permite combinar país com outras condições) ou o header `CloudFront-Viewer-Country` numa função.
- Para devolver uma página personalizada em vez do 403 padrão, use *custom error responses*.
- Existe ainda a geo restriction de **provedor de terceiro** (geolocalização de terceiros), mas ela é recurso separado e pago.

## Field-level encryption (criptografia no nível de campo)

Criptografa **campos específicos** de um formulário **POST** na borda usando uma **chave pública RSA** que você cadastra. Só o serviço que possui a **chave privada** consegue descriptografar.

```
 Navegador: POST /pagamento  cartao=4111...&nome=Ana
                    │
         Edge CloudFront  ──► criptografa cartao com a CHAVE PÚBLICA
                    │
         Servidores intermediários (ALB, app web) veem:  cartao=AYA...cifrado...  nome=Ana
                    │
         Serviço de pagamento (tem a CHAVE PRIVADA) ──► decifra cartao
```

Quando usar: dados muito sensíveis (cartão, documentos) que **não devem ser legíveis** pelos componentes intermediários, nem em logs. Requisitos e limites:

- Aplica-se a requisições **HTTPS POST** com `Content-Type` de formulário (`application/x-www-form-urlencoded`) e até certo número de campos; consulte os limites.
- Configura-se com *public key*, *field-level encryption profile* e *configuration*, vinculada ao behavior.
- Não substitui TLS (o tráfego continua em HTTPS); soma uma camada extra *além* do TLS.

## Resumo de decisão

| Quero... | Use |
|---|---|
| Absorver DDoS volumétrico | CloudFront + **Shield** (Standard já incluído) |
| Bloquear SQLi, XSS, bots, abuso por IP | **WAF** (managed rules + rate-based) |
| Bloquear/permitir países de forma simples | **Geo restriction** do CloudFront |
| Regras por país combinadas com outras condições | **WAF geo match** |
| Ocultar campo de formulário de componentes intermediários | **Field-level encryption** |
| Exigir autorização por usuário | Signed URLs/cookies ou autenticação na função de borda |

## Exemplo prático

Loja virtual com CloudFront + ALB. Estratégia de camadas:

1. **Origem fechada** ao CloudFront (prefix list + header secreto, ou VPC origin).
2. **Web ACL (escopo CLOUDFRONT, us-east-1)** com: IP reputation list (Count → Block), Core rule set (Count → Block), rate-based de 1000 requisições por IP, e regra de rate mais rígida para `/login`.
3. **Geo restriction**: allow list `BR`, já que a loja só entrega no Brasil (aceitando o risco de falso bloqueio de turistas brasileiros viajando).
4. **Field-level encryption** no `POST /checkout` para o campo `cartao`; apenas o microserviço de pagamento tem a chave privada.
5. **Logs do WAF** enviados a CloudWatch Logs/S3/Firehose para análise de falsos positivos.

Resultado esperado: ataques volumétricos absorvidos pela borda, abusos por IP cortados pelo rate limit, exploração web barrada pelas managed rules e o cartão ilegível no caminho.

## Erros comuns e armadilhas

- **Criar a Web ACL na região errada:** escopo CLOUDFRONT exige us-east-1.
- **Ativar regras em Block sem fase de Count:** falsos positivos derrubam usuários legítimos.
- **Esquecer que a origem continua pública:** um atacante que conhece o ALB contorna o WAF; feche a origem.
- **Contar com geo restriction como segurança forte:** VPN burla; é controle de conformidade/licenciamento, não de segurança.
- **Geo restriction em tudo para bloquear só uma rota:** ela vale para a distribuição inteira.
- **Rate-based muito baixo:** NAT corporativo (muitos usuários, um IP) acaba bloqueado.
- **Custos do WAF subestimados:** cobra-se por Web ACL, regra e milhões de requisições inspecionadas; grupos como Bot Control têm preço próprio.
- **Field-level encryption sem plano de rotação de chaves** e sem testar a descriptografia no serviço de destino.
- **Supor que Shield Standard resolve ataques de aplicação (L7):** isso é função de WAF (e Shield Advanced).

## 🧩 Quiz de Fixação

1. Em qual região se cria uma Web ACL do WAF para uma distribuição CloudFront, e por quê?
2. Qual a diferença entre geo restriction do CloudFront e geo match do WAF?
3. Para que serve a field-level encryption e como ela difere do HTTPS?

**Respostas:**
1) Em **us-east-1**, com escopo **CLOUDFRONT**, pois o CloudFront é um serviço global e suas Web ACLs são gerenciadas nessa região.
2) A **geo restriction** é nativa, gratuita, e se aplica à **distribuição inteira** com allow/block list de países (resposta 403). O **geo match** do WAF é uma condição dentro de regras, combinável com outras condições (IP, caminho, header) e com ações como Count ou CAPTCHA, mas tem o custo do WAF.
3) Ela criptografa **campos específicos** de formulários POST na borda com chave pública, de modo que só quem possui a chave privada (ex.: o serviço de pagamento) os decifra; componentes intermediários e logs só veem texto cifrado. O **HTTPS** protege o canal ponto a ponto entre dois nós, mas cada nó que termina o TLS (edge, ALB, aplicação) vê os dados em claro.
