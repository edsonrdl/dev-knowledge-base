## Streaming de vídeo

### Vídeo sob demanda (VOD)

```
 Vídeo fonte (S3) ──MediaConvert──► HLS/DASH (manifesto .m3u8/.mpd + segmentos .ts/.m4s) em S3 ──► CloudFront ──► players
```

| Componente | Função |
|---|---|
| **MediaConvert** | Transcodifica para múltiplas resoluções/bitrates (ABR) e empacota (HLS, DASH, CMAF) |
| **S3 (origem)** | Armazena manifestos e segmentos; acesso privado via **OAC** |
| **CloudFront** | Entrega com cache; **segmentos** com TTL longo; **manifestos** de VOD também podem ter TTL longo |
| **Segurança** | Signed URLs/cookies (cookies preferíveis em HLS com muitos segmentos), DRM no player, geo restriction |
| **Player** | HLS.js, Video.js, Shaka, players nativos; ABR automático |

### Ao vivo (live)

```
 Encoder (OBS, hardware) ─RTMP/SRT/RTP─► MediaLive ─► MediaPackage (HLS/DASH, DVR, DRM) ─► CloudFront ─► players
```

| Elemento | Detalhe |
|---|---|
| **MediaLive** | Codificação ao vivo, múltiplos bitrates, redundância (pipelines A/B) |
| **MediaPackage** | Empacotamento just-in-time, janela DVR (time-shift), DRM, endpoints HLS/DASH/CMAF |
| **CloudFront** | Distribui o endpoint do MediaPackage como origem (com cabeçalho secreto/CDN authorization) |
| **Manifestos ao vivo** | **TTL muito curto** (1-2 s) pois mudam a cada segmento |
| **Segmentos** | TTL maior (dezenas de segundos a minutos) |
| **Latência baixa** | CMAF/LL-HLS, segmentos curtos (1-2 s), partial segments; reduzir buffers do player |
| **Origin Shield** | Reduz requisições à origem em eventos com milhões de espectadores |

### Cache policy para streaming

| Tipo de objeto | TTL sugerido | Observações |
|---|---|---|
| **Segmentos VOD** (`.ts`, `.m4s`, `.mp4`) | Dias/semanas (imutáveis) | `Cache-Control: max-age=31536000, immutable` |
| **Manifesto VOD** | Horas/dias | Troca raramente |
| **Manifesto live** | 1-2 s | Segue a taxa de segmentos |
| **Segmentos live** | 10-60 s (ou conforme a janela DVR) | — |
| **Chave de cache** | Mínima (caminho; só query strings/cookies de autorização se necessários) | Evita fragmentação |
| **Range requests** | Permitidas (players pedem faixas) | CloudFront suporta cache de ranges |

### Boas práticas

1. **ABR com várias resoluções** e playlist mestre.
2. **Cookies assinados** para HLS (as URLs de segmentos não precisam ser reassinadas).
3. **Origin Shield** em eventos grandes.
4. **Compressão desligada** para vídeo (já comprimido).
5. **Monitorar** `BytesDownloaded`, taxa de erro, `OriginLatency`, rebuffering no player (métricas de QoE).
6. **Price class** conforme a audiência.

## Páginas de erro personalizadas (custom error responses)

O CloudFront pode **substituir** respostas de erro da origem por uma página sua e **alterar o código HTTP**.

| Configuração | Função |
|---|---|
| **HTTP error code** | 400, 403, 404, 405, 414, 416, 500, 501, 502, 503, 504 |
| **Response page path** | Caminho (em uma origem; pode ser outra behavior, ex.: `/erros/404.html`) |
| **HTTP response code** | Código devolvido ao cliente (ex.: 200, 404, 503) |
| **Error caching minimum TTL (ECMTTL)** | Quanto tempo o CloudFront **guarda o erro** (padrão 10 s) para não martelar a origem |

### Padrões comuns

| Caso | Configuração |
|---|---|
| **SPA (React/Angular/Vue) em S3** | Mapear **403 e 404** → `/index.html` com **200** (rotas do lado do cliente) |
| **Página de manutenção** | 503/502/504 → `/manutencao.html` com 503 e TTL curto |
| **Marca nos 404** | 404 → `/404.html` mantendo 404 |
| **Origin failover** | Complementa: erros 5xx acionam o grupo de origens antes da página de erro |

```json
"CustomErrorResponses": { "Quantity": 2, "Items": [
  { "ErrorCode": 403, "ResponsePagePath": "/index.html", "ResponseCode": "200", "ErrorCachingMinTTL": 10 },
  { "ErrorCode": 404, "ResponsePagePath": "/index.html", "ResponseCode": "200", "ErrorCachingMinTTL": 10 } ] }
```

Cuidados: mapear 404 para 200 em **APIs** esconde erros reais (aplique só no behavior estático); SEO e monitoramento (ficam "200"); o caminho da página de erro precisa existir e **não pode exigir** autenticação; defina o ECMTTL curto para recuperar rápido.

## Continuous deployment (staging de distribuições)

Permite **testar mudanças de configuração** (behaviors, políticas, funções) com uma **fração do tráfego real** antes de promover para produção.

```
 Distribuição PRIMÁRIA (produção) ──política de tráfego──► 5% (ou requisições com cabeçalho especial) ► Distribuição STAGING (nova config)
                                         └─ 95% segue na primária
 Validar métricas/erros ─► PROMOVER (copia a config do staging para a primária) ou descartar
```

| Elemento | Detalhe |
|---|---|
| **Distribuição de staging** | Cópia da primária onde se aplica a mudança |
| **Política de tráfego contínuo** | **Baseada em peso** (ex.: 5%) ou **baseada em cabeçalho** (`aws-cf-cd-staging: true`) |
| **Afinidade de sessão** | Mantém o mesmo visitante na mesma distribuição (opcional) |
| **Promoção** | `update-distribution-with-staging-config` copia a configuração do staging para a primária (sem downtime) |
| **Casos** | Mudar cache policy, adicionar CloudFront Function, trocar origem, ajustar TLS/HTTP versions, atualizar WAF |
| **Limitações** | Nem toda alteração é suportada no staging (consulte a lista); o domínio de staging só recebe tráfego pela política |
| **Rollback** | Descartar o staging ou reverter a configuração |

```bash
aws cloudfront copy-distribution --primary-distribution-id E123PROD --staging --caller-reference rel-2026-11
aws cloudfront create-continuous-deployment-policy --continuous-deployment-policy-config '{
  "StagingDistributionDnsNames":{"Quantity":1,"Items":["d9stg.cloudfront.net"]},"Enabled":true,
  "TrafficConfig":{"Type":"SingleWeight","SingleWeightConfig":{"Weight":0.05,"SessionStickinessConfig":{"IdleTTL":300,"MaximumTTL":600}}}}'
# Depois de validar métricas: promover
aws cloudfront update-distribution-with-staging-config --id E123PROD --staging-distribution-id E456STG --if-match <ETag>
```

Boas práticas: comece com 1-5% ou com cabeçalho para equipes internas, compare hit ratio, 4xx/5xx e latência entre as distribuições, e promova só com métricas estáveis.

## Logs: padrão e em tempo real

| Tipo | Entrega | Latência | Custo | Uso |
|---|---|---|---|---|
| **Logs padrão (access logs)** | S3 (ou CloudWatch Logs/Firehose na versão mais nova) | Minutos | Sem custo do recurso (paga S3) | Auditoria, Athena, análise de países/URLs |
| **Logs em tempo real** | **Kinesis Data Streams** (depois Firehose/Lambda) | Segundos | Por linha entregue + Kinesis | Alarmes, segurança, análise ao vivo, dashboards |
| **Logs do WAF / Functions** | CloudWatch Logs/S3 | — | — | Regras e funções |

### Logs em tempo real

| Parâmetro | Detalhe |
|---|---|
| **Taxa de amostragem** | 1-100% das requisições (use amostragem em tráfego alto) |
| **Campos** | Escolha os campos (`timestamp`, `c-ip`, `cs-uri-stem`, `sc-status`, `x-edge-result-type`, `time-taken`, `cs-user-agent`, `x-edge-location`, `cs-bytes`, `sc-bytes`, `x-edge-detailed-result-type`, etc.) |
| **Associação** | Por **behavior** (pode ligar só em `/api/*`) |
| **Destino** | Kinesis → Firehose (S3/OpenSearch) ou Lambda |
| **Uso típico** | Detectar picos de 5xx em segundos, bots/abuso, dashboards em OpenSearch/Grafana |

### Consultas do Athena em logs padrão

```sql
-- Razão de acerto de cache por URL
SELECT uri, count(*) req, sum(case when result_type in ('Hit','RefreshHit') then 1 else 0 end)*100.0/count(*) pct_hit
FROM cloudfront_logs WHERE date >= date_add('day',-1,current_date) GROUP BY uri ORDER BY req DESC LIMIT 20;
-- Erros por tipo detalhado
SELECT x_edge_detailed_result_type, sc_status, count(*) FROM cloudfront_logs WHERE sc_status >= 400 GROUP BY 1,2 ORDER BY 3 DESC;
```

## Compressão, protocolos e cabeçalhos

| Tema | Detalhe |
|---|---|
| **Compressão automática** | gzip e **Brotli**; objetos de 1.000 bytes a ~10 MB e tipos de conteúdo compressíveis; exige `Accept-Encoding` e a **cache policy** com `EnableAcceptEncodingGzip/Brotli` (variação na chave) |
| **Já comprimido** | Não comprimir vídeo/imagens/zip; se a origem comprime, ela deve enviar `Content-Encoding` coerente |
| **HTTP/2 e HTTP/3** | Ativos ao cliente (HTTP/3 configurável); mantém conexões eficientes |
| **WebSocket** | Suportado (behavior com métodos adequados; `Upgrade` encaminhado); timeouts de conexão |
| **gRPC** | Suportado em behaviors configurados para HTTP/2 end-to-end (confirme requisitos) |
| **Response headers policy** | CORS, HSTS, `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`, CSP, `Server-Timing`, cabeçalhos customizados — sem código |
| **Viewer request/response functions** | Lógica mais complexa de cabeçalhos |
| **IPv6** | Habilitar para alcançar clientes IPv6 |
| **Versões TLS** | Política de segurança mínima (TLS 1.2+) |
| **Proteção de origem** | Cabeçalhos secretos, VPC origins, prefix list |

## Troubleshooting

### Erros mais comuns

| Código | Causas comuns | O que verificar |
|---|---|---|
| **403** | OAC/bucket policy; **WAF bloqueou**; geo restriction; signed URL/cookie inválido/expirado; método não permitido; origem retorna 403; SSE-KMS sem permissão | `x-cache: Error from cloudfront`, logs do WAF, bucket policy e KMS, expiração da assinatura, `allowed methods` |
| **404** | Objeto inexistente; **origin path** errado; chave S3 diferente (maiúsculas, `/`); regra de behavior errada | Chave exata no S3, `OriginPath`, path pattern |
| **400** | Requisição malformada; cabeçalho `Host` inválido; **alternate domain (CNAME) não configurado** | CNAMEs e certificado |
| **502** Bad Gateway | **TLS com a origem falhou** (certificado inválido/expirado/nome não confere/SNI), origem fechou a conexão, resposta inválida, função (Lambda@Edge) com erro | Certificado da origem e SNI, protocolo `https-only`, logs da função, `x-edge-detailed-result-type` |
| **503** Service Unavailable | Capacidade/limite da origem ou do CloudFront; origem indisponível; `Function` throttled | Saúde da origem, quotas |
| **504** Gateway Timeout | Origem **não respondeu** no *response timeout* (padrão 30 s); SG/rede bloqueando; origem lenta | Timeout da origem, SG do ALB (prefix list do CloudFront), desempenho |
| **Conteúdo desatualizado** | TTL longo, sem invalidação; `Vary` ou cache key; cache do navegador | Invalidação/versionamento; cabeçalhos `Cache-Control`; `Age` |
| **Muitos misses** | Cache key fragmentada (query strings, cookies, cabeçalhos), TTL curto, `Cache-Control: no-store` da origem | Cache policy, métricas `CacheHitRate` |
| **CORS falha** | Cabeçalhos CORS não encaminhados/ausentes na resposta | Response headers policy, origin request policy com `Origin` |
| **Redirecionamento infinito** | HTTP→HTTPS entre CloudFront e origem; política de protocolo `match-viewer`/origem redirecionando | Origin protocol policy, regras do ALB |
| **Certificado/CNAME** | Certificado fora de us-east-1 ou sem o domínio | ACM, aliases |

### Ferramentas

```bash
curl -sI https://www.exemplo.com.br/img/logo.png | grep -iE "x-cache|via|x-amz-cf-pop|x-amz-cf-id|age|cache-control|content-encoding"
# Testar a origem diretamente (sem o CloudFront)
curl -sI https://origem.exemplo.com.br/img/logo.png
# Forçar um PoP/ignorar cache para teste
curl -sI -H "Cache-Control: no-cache" https://www.exemplo.com.br/img/logo.png
# Resolver o domínio a um IP específico de edge (diagnóstico)
curl -sI --resolve www.exemplo.com.br:443:<ip-da-edge> https://www.exemplo.com.br/
```

| Cabeçalho | Significado |
|---|---|
| `X-Cache: Hit/Miss/RefreshHit/Error from cloudfront` | Resultado do cache |
| `X-Amz-Cf-Pop` | Edge que atendeu |
| `X-Amz-Cf-Id` | ID da requisição (para suporte e correlação com logs) |
| `Age` | Segundos desde o cache |
| `Via` | Passagem pelo CloudFront |

Métricas: `Requests`, `BytesDownloaded`, `4xxErrorRate`, `5xxErrorRate`, `TotalErrorRate`, métricas adicionais (`CacheHitRate`, `OriginLatency`, taxas por código 401/403/404/502/503/504); logs com `x-edge-detailed-result-type` (por exemplo `OriginConnectError`, `OriginDnsError`, `ClientCommError`, `InvalidRequest`, `AbortedOrigin`).

## Exemplo prático

Portal de vídeo educacional (VOD + aulas ao vivo) com SPA em S3 e API em ALB sob a mesma distribuição:

1. **VOD:** MediaConvert gera HLS em 4 qualidades; S3 privado com OAC; behavior `/video/*` com **cookies assinados**, cache de segmentos por 1 ano (`immutable`), compressão desligada, **Origin Shield** em `sa-east-1`.
2. **Ao vivo:** MediaLive + MediaPackage; behavior `/live/*` com cache de manifesto de 2 s e segmentos de 30 s; origem protegida por cabeçalho secreto.
3. **SPA:** behavior padrão em S3; **custom error responses** 403/404 → `/index.html` (200) *apenas* na distribuição do front; o behavior `/api/*` (ALB) não tem mapeamento de erros.
4. **Página de manutenção:** 502/503/504 → `/manutencao.html` com 503 e ECMTTL de 30 s.
5. **Deploy seguro:** nova CloudFront Function de reescrita testada via **continuous deployment** com 5% do tráfego e cabeçalho para QA; após 24 h estáveis, promove.
6. **Logs:** padrão no S3 + Athena para análise diária; **logs em tempo real** só para `/api/*` e `/live/*` (amostragem 25%) → Kinesis → Firehose → OpenSearch com alarmes de 5xx.
7. **Troubleshooting registrado:** um pico de 502 em `/api/*` foi causado por certificado expirado no ALB (`OriginConnectError` nos logs); alarme de expiração de certificado adicionado.

## Erros comuns e armadilhas

- **Manifesto live com TTL longo** (o player recebe lista antiga).
- **Comprimir vídeo** ou variar a cache key por cabeçalhos desnecessários.
- **Mapear 404/403 para 200 em APIs** (esconde erros reais).
- **Página de erro hospedada na mesma origem que está falhando.**
- **ECMTTL longo** (o erro fica "preso" depois que a origem se recupera).
- **Continuous deployment sem métricas de comparação** ou promovendo cedo demais.
- **Logs em tempo real em 100% do tráfego** sem necessidade (custo de Kinesis).
- **Ignorar `x-edge-detailed-result-type`** no diagnóstico.
- **Origem com TLS inválido** (502) ou timeout curto para respostas lentas (504).
- **Esquecer CNAME/certificado** (400/erro de certificado).
- **Não proteger a origem** e perder cache/WAF.

## 🧩 Quiz de Fixação

1. Qual a diferença de TTL entre manifestos e segmentos em streaming ao vivo?
2. Como configurar uma SPA no S3 para rotas do lado do cliente?
3. Como o continuous deployment reduz o risco de uma mudança?
4. Quais as causas mais comuns de 502 e de 504 no CloudFront?

**Respostas:**
1) O manifesto ao vivo muda a cada segmento e deve ter TTL muito curto (1-2 s), enquanto os segmentos são imutáveis e podem ter TTL maior (dezenas de segundos ou mais), reduzindo o tráfego à origem.
2) Criar custom error responses que mapeiam 403 e 404 para `/index.html` com código 200 (aplicado apenas ao behavior estático), para que o roteador do cliente trate a rota.
3) Permite aplicar a mudança em uma distribuição de staging que recebe uma fração do tráfego real (por peso ou cabeçalho), comparar métricas e só então promover a configuração para a primária, com rollback simples.
4) 502: falha de TLS com a origem (certificado inválido/expirado, nome ou SNI), origem fechando a conexão ou erro de função; 504: a origem não respondeu dentro do timeout (lenta ou bloqueada por SG/rede).
