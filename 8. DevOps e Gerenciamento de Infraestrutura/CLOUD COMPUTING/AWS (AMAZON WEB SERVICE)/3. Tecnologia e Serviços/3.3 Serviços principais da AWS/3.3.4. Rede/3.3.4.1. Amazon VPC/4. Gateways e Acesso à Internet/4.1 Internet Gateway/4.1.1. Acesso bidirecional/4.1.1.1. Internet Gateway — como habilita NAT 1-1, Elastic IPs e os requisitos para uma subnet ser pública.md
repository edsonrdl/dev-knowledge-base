### Internet Gateway — NAT 1-1, Elastic IPs e os requisitos para uma subnet ser pública

> [!warning] Aviso
> Preços, limites, regiões e comportamentos de APIs da AWS mudam com frequência. Confira a documentação oficial (Amazon VPC User Guide) e a calculadora de preços antes de decidir. Os comandos de CLI abaixo são ilustrativos e **não foram executados** durante a escrita desta nota.

O Internet Gateway (IGW) é o componente que conecta uma VPC à internet pública, de forma **bidirecional**: recursos da VPC podem iniciar conexões para a internet, e a internet pode iniciar conexões para recursos da VPC que tenham IP público. Ele é simples (sem configuração além de criar e anexar), mas quase todo problema de "minha instância não acessa a internet" passa por ele. Esta nota explica o que o IGW realmente faz, como ele trata endereços e quais são as quatro condições para um recurso ser alcançável de fora.

## O que é o Internet Gateway

O IGW é um recurso **regional, horizontalmente escalável, redundante e altamente disponível**, gerenciado pela AWS. Você não escolhe tamanho, não paga por hora de existência e não gerencia failover: ele não é um "servidor" que pode cair em uma AZ. Ele é anexado a **uma única VPC por vez**, e cada VPC pode ter **no máximo um IGW** anexado.

Ele executa duas funções:

1. **Alvo de rota:** é o destino que você coloca na route table para tráfego destinado à internet (`0.0.0.0/0 → igw-xxxx`, ou `::/0` para IPv6).
2. **Tradução de endereço NAT 1-1:** para instâncias que têm IPv4 público, o IGW traduz entre o IP privado (dentro da VPC) e o IP público (fora).

**Analogia:** o IGW é a **porta da frente de um condomínio**. O porteiro (IGW) conhece o apartamento (IP privado) de cada morador e o número de rua (IP público) que ele usa para receber visitas. Quem mora num apartamento sem número de rua (sem IP público) não recebe visitas de fora, mesmo que a porta da frente exista. A porta só é útil se também houver um corredor (route table) levando até ela.

```
                      INTERNET
                          │
                  ┌───────┴───────┐
                  │ Internet      │  ← 1 por VPC, regional, sem custo por hora
                  │ Gateway       │
                  │ igw-0abc123   │
                  └───────┬───────┘
                          │  rota 0.0.0.0/0 → igw-0abc123
        ┌─────────────────┴───────────────────┐
        │ VPC 10.0.0.0/16                     │
        │  ┌───────────────────────────────┐  │
        │  │ Subnet pública 10.0.1.0/24    │  │
        │  │  EC2: 10.0.1.25 ↔ 54.10.20.30 │  │
        │  │       (privado)   (público)   │  │
        │  └───────────────────────────────┘  │
        └─────────────────────────────────────┘
```

## NAT 1-1: como o IGW trata endereços

Dentro da VPC, a instância **só conhece o IP privado**. A interface de rede (ENI) da instância nunca "vê" o IP público: ele não aparece em `ip addr`. Quem faz a tradução é o IGW, em ambos os sentidos:

```
SAÍDA (instância inicia):
  EC2 envia:   src=10.0.1.25   dst=93.184.216.34
  IGW traduz:  src=54.10.20.30 dst=93.184.216.34     (privado → público)

ENTRADA (internet inicia ou responde):
  Cliente envia: src=200.1.2.3  dst=54.10.20.30
  IGW traduz:    src=200.1.2.3  dst=10.0.1.25         (público → privado)
```

É uma tradução **1 para 1**: cada IP privado mapeia para exatamente um IP público. Isso difere do NAT Gateway, que faz N para 1 (vários IPs privados compartilhando um IP público via portas, o PAT).

| Característica | Internet Gateway | NAT Gateway |
|---|---|---|
| Tipo de tradução | NAT 1-1 (estático por ENI) | PAT (N:1, por porta) |
| Direção permitida | Bidirecional | Somente saída iniciada pela VPC |
| Exige IP público no recurso | Sim (IPv4) | Não (o NAT tem o IP) |
| Custo | Sem custo por hora ou por GB processado (a transferência de dados de saída é cobrada à parte) | Por hora + por GB processado |
| Fica em | Anexado à VPC | Dentro de uma subnet pública |
| Alta disponibilidade | Gerenciada pela AWS | Você cria 1 por AZ |

IPv6 é diferente: endereços IPv6 da AWS são **globalmente únicos e roteáveis**, então o IGW **não faz NAT** para IPv6; ele apenas encaminha. Para permitir só saída em IPv6, usa-se o **Egress-Only Internet Gateway** (veja a nota de IPv6 da VPC).

## IPs públicos: três formas de obter

Para o IGW traduzir, a ENI precisa ter um IPv4 público associado. Há três formas:

| Forma | Comportamento | Persistência | Custo |
|---|---|---|---|
| **IP público automático** (auto-assign na subnet ou na instância) | Atribuído do pool da AWS ao lançar a instância | Perdido ao **parar** a instância (muda em start/stop; mantém em reboot) | Cobrado por hora (todo IPv4 público é cobrado desde 2024, conferir valores atuais) |
| **Elastic IP (EIP)** | IP estático da sua conta, associado a uma ENI ou NAT Gateway | Permanece até você liberar | Cobrado por hora, estando em uso ou não |
| **BYOIP** (Bring Your Own IP) | Seu próprio bloco de IPs anunciado pela AWS | Controlado por você | Conforme documentação |

Pontos de atenção:

- **Mudança de cobrança de IPv4:** desde fevereiro de 2024 a AWS passou a cobrar por **todos** os endereços IPv4 públicos, em uso ou não (com Free Tier limitado para EC2). Isso muda a conta de arquiteturas com muitas instâncias públicas; confirme os valores atuais na página de preços de VPC.
- Um **Elastic IP não associado** gera custo sem fazer nada: libere o que não usar.
- Em subnets, a opção `MapPublicIpOnLaunch` define se novas instâncias recebem IP público por padrão; ela pode ser sobrescrita no lançamento da instância.

## As quatro condições para um recurso ser alcançável da internet

Ter um IGW **não basta**. Para uma instância receber conexão iniciada pela internet, as quatro condições abaixo devem ser verdadeiras ao mesmo tempo:

```
 1. IGW anexado à VPC
        │
        ▼
 2. Route table da subnet tem rota 0.0.0.0/0 → igw-xxxx
        │
        ▼
 3. ENI tem IP público (auto-assign ou Elastic IP)
        │
        ▼
 4. Security Group E Network ACL permitem o tráfego
        │
        ▼
   Recurso alcançável ✔
```

| # | Condição | Sintoma se faltar |
|---|---|---|
| 1 | IGW criado **e anexado** (estado `attached`) | Rota para o IGW aparece como `blackhole` ou nem pode ser criada |
| 2 | Rota `0.0.0.0/0 → igw` na route table **associada à subnet** | Sem rota para a internet: timeout (a subnet não é "pública") |
| 3 | IP público ou Elastic IP na ENI | Instância sai para a internet? Não: sem IP público, o IGW não traduz |
| 4 | SG com regra de entrada + NACL permitindo entrada **e** saída (ephemeral ports) | Timeout na porta específica, enquanto ping/outras portas podem funcionar |

Essa lista é o roteiro de diagnóstico: percorra na ordem. Ela também explica por que o conceito de "subnet pública" é, tecnicamente, **uma subnet cuja route table aponta para um IGW**, e não uma propriedade do nome.

## Exemplo prático: criar uma subnet pública

```bash
# 1) Criar o IGW (ainda não está ligado a nenhuma VPC)
IGW_ID=$(aws ec2 create-internet-gateway \
  --tag-specifications 'ResourceType=internet-gateway,Tags=[{Key=Name,Value=igw-producao}]' \
  --query 'InternetGateway.InternetGatewayId' --output text)
# Saída: id do IGW, guardado na variável IGW_ID

# 2) Anexar à VPC (condição 1). Uma VPC aceita só 1 IGW.
aws ec2 attach-internet-gateway \
  --internet-gateway-id $IGW_ID \
  --vpc-id vpc-0abc123

# 3) Criar route table dedicada às subnets públicas
RTB_ID=$(aws ec2 create-route-table \
  --vpc-id vpc-0abc123 \
  --query 'RouteTable.RouteTableId' --output text)

# 4) Rota padrão para a internet (condição 2)
aws ec2 create-route \
  --route-table-id $RTB_ID \
  --destination-cidr-block 0.0.0.0/0 \
  --gateway-id $IGW_ID
# Para IPv6 seria: --destination-ipv6-cidr-block ::/0

# 5) Associar a route table à subnet que será "pública"
aws ec2 associate-route-table \
  --route-table-id $RTB_ID \
  --subnet-id subnet-0pub1

# 6) Permitir IP público automático nas novas instâncias (condição 3)
aws ec2 modify-subnet-attribute \
  --subnet-id subnet-0pub1 \
  --map-public-ip-on-launch
```

Explicação linha a linha:

- `create-internet-gateway`: cria o recurso; sozinho ele não faz nada, pois ainda está `detached`.
- `attach-internet-gateway`: liga o IGW à VPC; é o que torna a rota válida.
- `create-route-table` + `create-route`: a rota `0.0.0.0/0 → IGW` é o que transforma a subnet em pública. Usar uma route table própria evita tornar públicas subnets que usam a **main route table**.
- `associate-route-table`: sem a associação explícita, a subnet usa a main route table (que normalmente não tem rota para o IGW).
- `modify-subnet-attribute --map-public-ip-on-launch`: instâncias novas recebem IPv4 público.

Para o equivalente em CloudFormation, o conjunto é `AWS::EC2::InternetGateway`, `AWS::EC2::VPCGatewayAttachment`, `AWS::EC2::RouteTable`, `AWS::EC2::Route` (com `GatewayId`) e `AWS::EC2::SubnetRouteTableAssociation`. (Não executado; valide em um ambiente de teste.)

## Erros comuns e armadilhas

- **Rota para o IGW na main route table por engano:** todas as subnets sem associação explícita ficam públicas, incluindo as de banco de dados. Mantenha a main route table sem rota para a internet e use route tables explícitas.
- **Esquecer o IP público:** a rota e o IGW existem, mas a instância não tem IPv4 público nem EIP. Resultado: ela não acessa a internet nem é acessível. (Para só saída, a solução correta é um NAT Gateway, não expor a instância.)
- **Achar que o IGW protege:** ele não filtra nada. A proteção vem de Security Groups e NACLs; veja [[8. DevOps e Gerenciamento de Infraestrutura/CLOUD COMPUTING/AWS (AMAZON WEB SERVICE)/3. Tecnologia e Serviços/3.3 Serviços principais da AWS/3.3.4. Rede/3.3.4.1. Amazon VPC/5. Segurança de Rede/5.2 Network ACLs/5.2.1. Firewall stateless por subnet/5.2.1.2. Security Groups vs NACLs — sobreposição de camadas, compliance e padrões de uso combinado|Security Groups vs NACLs]].
- **Esquecer as portas efêmeras na NACL:** NACL é stateless; a resposta usa portas altas (1024-65535) que precisam estar liberadas.
- **Tentar anexar um segundo IGW à mesma VPC:** a API recusa; é 1 por VPC.
- **Elastic IPs esquecidos:** custam por hora mesmo sem uso; revise periodicamente.
- **Tráfego de saída:** o IGW não tem custo próprio, mas a **transferência de dados para a internet** é cobrada conforme a tabela de data transfer (veja os conteúdos de Preços no Domínio 4 do guia AWS core).

## Quando usar e alternativas

| Necessidade | Solução |
|---|---|
| Servidor web público (ALB, bastion, instância pública) | Subnet pública + IGW + IP público/EIP |
| Instância privada que só precisa baixar atualizações | NAT Gateway em subnet pública |
| Só saída em IPv6 | Egress-Only Internet Gateway |
| Acessar S3/DynamoDB sem internet | Gateway VPC Endpoint |
| Acessar serviços AWS sem internet | Interface Endpoint (PrivateLink) |
| Acesso administrativo sem IP público | SSM Session Manager |

## 🧩 Quiz de Fixação

1. Quantos Internet Gateways podem ser anexados a uma VPC e o IGW tem custo por hora?
2. Uma instância em uma subnet com rota `0.0.0.0/0 → igw-xxxx`, com Security Group liberando a porta 443, não é alcançável pela internet. Cite a causa mais provável e como verificar.
3. Qual a diferença entre a tradução feita pelo IGW e a feita pelo NAT Gateway, e por que o IGW não faz NAT em IPv6?

**Respostas:**
1) **Um** IGW por VPC (e um IGW só pode estar anexado a uma VPC por vez). O IGW **não tem custo por hora** nem por GB processado; o que se paga é a transferência de dados para fora e os endereços IPv4 públicos usados.
2) A causa mais provável é a **ausência de IPv4 público (ou Elastic IP) na ENI**: sem ele o IGW não tem como traduzir. Verifique no console/CLI o campo de IP público da instância (`aws ec2 describe-instances`) e, em seguida, a NACL da subnet (entrada em 443 e saída em portas efêmeras). A rota e o SG, sozinhos, não bastam.
3) O IGW faz **NAT 1-1** (cada IP privado ↔ um IP público dedicado), bidirecional; o NAT Gateway faz **PAT N:1**, compartilhando um IP público entre muitas instâncias e permitindo apenas conexões iniciadas de dentro. Em IPv6 os endereços já são globalmente únicos e roteáveis, então não há o que traduzir: o IGW só encaminha, e o controle de entrada se faz por SG/NACL ou pelo Egress-Only IGW.
