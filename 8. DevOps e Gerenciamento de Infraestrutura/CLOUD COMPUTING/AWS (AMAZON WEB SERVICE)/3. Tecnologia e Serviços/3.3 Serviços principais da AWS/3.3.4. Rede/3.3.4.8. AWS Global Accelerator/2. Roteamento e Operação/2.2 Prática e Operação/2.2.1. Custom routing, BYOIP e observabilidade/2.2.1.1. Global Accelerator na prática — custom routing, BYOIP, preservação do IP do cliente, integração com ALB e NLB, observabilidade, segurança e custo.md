### Global Accelerator na prática — custom routing, BYOIP, preservação do IP do cliente, integração com ALB e NLB, observabilidade, segurança e custo

> [!warning] Aviso
> Tipos de endpoint suportados, regras de preservação de IP, limites (aceleradores, listeners, endpoints), regiões e preços do AWS Global Accelerator mudam. Os números são **ordens de grandeza**. **Confirme na documentação e na calculadora de preços.** Os comandos **não foram executados**; a API do serviço fica na região `us-west-2`.

As duas notas anteriores explicaram o *que é* o Global Accelerator (IPs anycast, listeners, endpoint groups, traffic dials) e quando escolhê-lo frente ao CloudFront e ao Route 53. Aqui vamos à **prática de produção**: **custom routing** para jogos e sessões determinísticas, **BYOIP** (trazer seus próprios IPs), **preservação do IP do cliente** (e o que ela exige), **integração com ALB e NLB**, **observabilidade** (métricas e flow logs), **segurança** (Shield, Security Groups) e **custo**.

**Analogia:** o Global Accelerator é um **serviço de transporte expresso com endereço fixo**. O *standard* leva o passageiro ao ponto mais próximo e saudável da sua rede de filiais. O *custom routing* é um **motorista que leva cada passageiro a uma sala específica** (um servidor de jogo determinado) a partir de um mapa de portas. O BYOIP é **usar o seu próprio número de telefone** na central.

## Standard × Custom routing

| Critério | **Standard accelerator** | **Custom routing accelerator** |
|---|---|---|
| Decisão de destino | O Global Accelerator escolhe o melhor endpoint saudável (proximidade, saúde, dials/pesos) | **Você** (sua aplicação) escolhe o destino exato; o acelerador mapeia **IP:porta → instância:porta** |
| Endpoints | ALB, NLB, EC2, Elastic IP | **Subnets de VPC** (todas as instâncias privadas da subnet ficam "alcançáveis" por mapeamento) |
| Health checks | Sim | Não por instância |
| Uso típico | Aplicações web/TCP/UDP, failover multi-região | **Jogos multiplayer, salas de VoIP/vídeo, sessões fixas** em servidores específicos |
| Protocolos | TCP e UDP | TCP e UDP |
| Mapeamento | Portas do listener → endpoint | Listener com faixa grande de portas mapeadas deterministicamente |

### Como o custom routing funciona

```
 1. Seu serviço de matchmaking escolhe o servidor de jogo i-0abc na subnet S (porta 7777)
 2. Consulta o mapeamento:  list-custom-routing-port-mappings-by-destination  → (IP do acelerador, porta 30041)
 3. Entrega ao jogador:  75.2.x.x:30041
 4. O jogador conecta; o acelerador encaminha (backbone AWS) ao i-0abc:7777 (IP privado)
```

| Elemento | Detalhe |
|---|---|
| **Listener** | Faixa de portas (ex.: 10.000-60.000) usada para o mapeamento |
| **Endpoint group por região** | Contém **subnets** da VPC (cada subnet cobre suas instâncias e portas) |
| **Destination port range** | Portas de destino permitidas (ex.: 7000-7999) |
| **Controle de acesso** | `allow-custom-routing-traffic` / `deny-custom-routing-traffic` por destino (padrão: nenhum permitido até liberar) |
| **Mapeamento** | Determinístico e consultável via API (`ListCustomRoutingPortMappings`) |
| **Escala** | Milhares de servidores sem IP público por servidor |
| **Segurança** | Instâncias permanecem **privadas**; Security Groups controlam |

```bash
aws globalaccelerator create-custom-routing-accelerator --name jogos --ip-address-type IPV4 --enabled --region us-west-2
aws globalaccelerator create-custom-routing-listener --accelerator-arn $ACC --port-ranges FromPort=10000,ToPort=60000 --region us-west-2
aws globalaccelerator create-custom-routing-endpoint-group --listener-arn $LST --endpoint-group-region sa-east-1 \
  --destination-configurations FromPort=7000,ToPort=7999,Protocols=UDP \
  --endpoint-configurations EndpointId=subnet-0jogos111 --region us-west-2
aws globalaccelerator allow-custom-routing-traffic --endpoint-group-arn $EG --endpoint-id subnet-0jogos111 \
  --destination-addresses 10.0.1.25 --destination-ports 7777 --region us-west-2
aws globalaccelerator list-custom-routing-port-mappings-by-destination --endpoint-id subnet-0jogos111 --destination-address 10.0.1.25 --region us-west-2
```

## BYOIP (Bring Your Own IP)

Você pode **trazer um bloco de IPs públicos que você possui** (por exemplo `/24` IPv4) e usá-lo no acelerador, **mantendo o endereço mesmo ao migrar** e evitando que parceiros mudem listas de liberação.

| Etapa | Detalhe |
|---|---|
| **Pré-requisitos** | Bloco registrado em um RIR (LACNIC/ARIN/…) com **ROA** (Route Origin Authorization) autorizando o ASN da AWS; tamanho mínimo (ex.: /24); prova de propriedade |
| **Provisionar** | `provision-byoip-cidr` com a assinatura de autorização |
| **Anunciar** | `advertise-byoip-cidr`; você pode **retirar** o anúncio para migrar |
| **Criar o acelerador** | Escolha os IPs do seu bloco (`--ip-addresses`) |
| **Benefícios** | IPs estáveis e conhecidos, migração sem alterar listas de parceiros, reputação de IP própria |
| **Limites** | Bloco mínimo, número de blocos por conta, tempo de propagação |

Boas práticas: planeje a janela de anúncio, mantenha o ROA válido, documente o proprietário do bloco e use dois IPs do bloco (o acelerador exige dois).

## Preservação do IP do cliente

Por padrão, o Global Accelerator **termina a conexão** na borda e abre outra ao endpoint, de modo que o alvo veria o IP do acelerador. Com a **preservação do IP do cliente**, o alvo enxerga o **IP original**.

| Endpoint | Preservação |
|---|---|
| **ALB** (internet-facing e, em versões recentes, internal) | Suportada e habilitada por padrão (o IP original vem em `X-Forwarded-For`, e o SG do ALB vê o IP do cliente via ENI do acelerador) |
| **NLB** | Suportada para alvos de instância/IP; o NLB precisa de configuração compatível |
| **EC2** | Suportada (o IP origem do pacote é do cliente) |
| **Elastic IP** | **Não** suportada (o tráfego chega com IPs do acelerador) |

Requisitos e implicações:

1. O Global Accelerator cria **ENIs gerenciadas** na sua VPC e um **Security Group gerenciado** (`GlobalAccelerator`); regras de SG devem **permitir** o tráfego do SG do acelerador ou dos IPs de clientes conforme a necessidade.
2. Em endpoints com preservação, os **Security Groups do ALB/instância** enxergam o **IP real do cliente**: abrir `0.0.0.0/0` ou restringir por CIDR de clientes.
3. As **respostas** retornam ao acelerador pela rota da VPC: tabelas de rotas e NACLs devem permitir.
4. Para logs e WAF, o IP real aparece em `X-Forwarded-For` (ALB) ou na conexão (EC2/NLB).

```bash
aws globalaccelerator add-endpoints --endpoint-group-arn $EG --region us-west-2 \
  --endpoint-configurations EndpointId=$ALB_ARN,Weight=128,ClientIPPreservationEnabled=true
```

## Integração com ALB e NLB

### ALB atrás do Global Accelerator

```
 Usuário ─► Global Accelerator (anycast, TCP/TLS na borda → backbone) ─► ALB (regional) ─► ECS/EKS/EC2
```

| Aspecto | Detalhe |
|---|---|
| **Listeners** | TCP 80/443; o **TLS termina no ALB** (o acelerador é L4) |
| **Health** | Usa a saúde dos alvos do ALB para decidir o failover entre regiões |
| **Segurança** | O ALB pode ser **somente alcançável** pelo acelerador (SG com o SG gerenciado) |
| **WAF** | Associado ao ALB (regional) |
| **Casos** | Aplicações multi-região ativo-ativo, failover rápido, IP estático para clientes corporativos |

### NLB atrás do Global Accelerator

| Aspecto | Detalhe |
|---|---|
| **Protocolos** | TCP, UDP e TLS (passagem) |
| **Casos** | Jogos, VoIP, MQTT/IoT, serviços proprietários |
| **Health** | Health checks do NLB (alvos) |
| **IP do cliente** | Preservado conforme tipo de alvo |

### Padrões multi-região

| Padrão | Configuração |
|---|---|
| **Ativo-ativo por proximidade** | Endpoint groups em 2+ regiões, dial 100% em ambas; usuários vão ao mais próximo saudável |
| **Ativo-passivo (DR)** | Região secundária com dial 0%; sobe para 100% em desastre (ou automático se a primária ficar não saudável) |
| **Blue/green entre regiões** | Ajuste de dials 90/10 → 50/50 → 0/100 |
| **Manutenção** | Dial 0% na região em manutenção para drenar |
| **Peso entre endpoints** | `Weight` 0-255 dentro do grupo |

## Observabilidade

### Métricas CloudWatch (`AWS/GlobalAccelerator`, região us-west-2)

| Métrica | Uso |
|---|---|
| `NewFlowCount` | Novos fluxos TCP/UDP (por listener/endpoint group) |
| `ProcessedBytesIn` / `ProcessedBytesOut` | Volume (base do custo DT-Premium) |
| `HealthyEndpointCount` / `UnhealthyEndpointCount` | Saúde por endpoint group |
| `TCP_Client_Reset_Count`, `TCP_AGA_Reset_Count`, `TCP_Endpoint_Reset_Count` | Quem encerrou conexões com RST (cliente, acelerador, endpoint) |
| `ActiveFlowCount` (conforme versão) | Fluxos ativos |

Alarmes: `UnhealthyEndpointCount` > 0 em um grupo; queda de `ProcessedBytes` (falha de rota); picos de `TCP_Endpoint_Reset_Count` (alvo recusando conexões).

### Flow logs

- Podem ser enviados ao **S3** (por acelerador) com campos: IPs de origem/destino, portas, bytes, região do endpoint, **IP do endpoint**, `action` (aceito/rejeitado).
- Úteis para **auditoria**, análise de tráfego por região, detecção de abuso e dimensionamento de custo.
- Consultas com **Athena**.

```bash
aws globalaccelerator update-accelerator-attributes --accelerator-arn $ACC --region us-west-2 \
  --flow-logs-enabled --flow-logs-s3-bucket logs-ga --flow-logs-s3-prefix ga/
```

### Diagnóstico

| Sintoma | Verificações |
|---|---|
| **Sem conectividade** | Listener (portas/protocolo), endpoint group da região, endpoint saudável, SG/NACL/rotas, endpoint em subnet pública com rota |
| **Endpoint "unhealthy"** | Health check (porta/caminho) alcançável a partir dos IPs de health check do GA; SG do alvo permite |
| **IP do cliente aparece como do acelerador** | Preservação desligada ou EIP como endpoint |
| **Latência alta** | O fluxo pode estar indo a uma região distante (dials, pesos, saúde); medir por região |
| **UDP não funciona** | Listener UDP e SG com UDP; MTU; aplicação |
| **Conexões longas caindo** | Idle timeout TCP (cerca de 340 s) / UDP (30 s): use keepalive |
| **Custo alto** | `ProcessedBytes` por direção/região; DT-Premium |

## Segurança

| Camada | Prática |
|---|---|
| **DDoS** | **Shield Standard** incluído (camadas 3/4); **Shield Advanced** pode proteger o acelerador (detecção, resposta, proteção de custo) |
| **Rede** | Mantenha os alvos privados quando possível (ALB/NLB internos aceitos como endpoints em versões recentes; confirme); SG do alvo restrito ao SG do acelerador |
| **TLS** | O acelerador é L4: use TLS fim a fim (ALB/NLB/aplicação) |
| **IAM** | Controle de administração (`globalaccelerator:*`), SCP; separação de quem altera dials/pesos |
| **WAF** | No ALB (não há WAF no GA) |
| **Acesso por IP** | Clientes liberam os 2 IPs estáticos (ou o bloco BYOIP) em firewalls |
| **Auditoria** | CloudTrail, flow logs, alarmes de mudanças de configuração |
| **Anti-spoofing** | Valide `X-Forwarded-For` somente de origens confiáveis |

## Custo

| Componente | Detalhe |
|---|---|
| **Taxa fixa por acelerador-hora** | Cobrada enquanto o acelerador existir (inclusive sem tráfego); *standard* e *custom routing* |
| **Transferência premium (DT-Premium)** | Por GB, na **direção dominante** (do destino para a origem), variando por **par de regiões** (origem do cliente, região do endpoint) |
| **IPs BYOIP** | Cobrança de uso do bloco (conforme política vigente) |
| **Flow logs, CloudWatch** | S3, Athena |
| **Dados do ALB/NLB** | LCU/NLCU do balanceador, normalmente além do custo do GA |

Comparação rápida com alternativas:

| Necessidade | Opção mais econômica/adequada |
|---|---|
| Conteúdo HTTP cacheável global | **CloudFront** (menor custo por GB, cache) |
| Aplicação HTTP dinâmica multi-região sem requisito de IP fixo | Route 53 (latência/failover) + ALBs |
| TCP/UDP global, IP fixo, failover rápido | **Global Accelerator** |
| Servidores de jogo com roteamento por sessão | **Custom routing** |
| Acelerar upload ao S3 | S3 Transfer Acceleration |

Estratégias: **consolidar** aplicações em um acelerador com vários listeners (cada acelerador tem custo fixo), **desligar** aceleradores ociosos, **medir** `ProcessedBytes` por região antes de adotar, usar **CloudFront na frente** para tráfego cacheável e **evitar GA para tráfego puramente regional** (sem benefício).

## Exemplo prático

Plataforma de jogos online (UDP) com servidores em `sa-east-1` e `us-east-1`, matchmaking centralizado e parceiros que precisam de IP fixo:

1. **Custom routing accelerator** `jogos` com listener de portas 10000-60000; endpoint groups nas duas regiões apontando para as subnets dos servidores (privados, sem IP público).
2. O **matchmaker** escolhe o servidor de cada partida, consulta `list-custom-routing-port-mappings-by-destination` e devolve `IP:porta` do acelerador ao jogador; `allow-custom-routing-traffic` só para os servidores em produção.
3. **API de login e lobby (TCP/443):** *standard accelerator* separado, com ALBs em ambas as regiões (ativo-ativo, dial 100/100), `ClientIPPreservationEnabled=true`, WAF no ALB.
4. **BYOIP:** o bloco /24 da empresa (ROA validada) usado no acelerador de login, mantendo o IP conhecido pelos parceiros durante a migração do datacenter.
5. **Observabilidade:** flow logs no S3 + Athena para análise por região; alarmes em `UnhealthyEndpointCount` e `TCP_Endpoint_Reset_Count`.
6. **Segurança:** Shield Advanced no acelerador de login; SG dos ALBs só aceita o SG gerenciado do GA; servidores de jogo privados.
7. **Custo:** `ProcessedBytesOut` monitorado por região; revisão trimestral (consolidar o login e o lobby no mesmo acelerador; desativar aceleradores de teste).

## Erros comuns e armadilhas

- **Esquecer que a API é us-west-2** e configurar na região errada.
- **Usar Elastic IP como endpoint e esperar preservação do IP do cliente.**
- **SG/NACL sem permitir o acelerador** (health checks e tráfego).
- **Confundir standard com custom routing** (e esperar health checks por instância no custom).
- **Esquecer `allow-custom-routing-traffic`** (nada é alcançado por padrão).
- **BYOIP sem ROA/validação** ou anúncio mal planejado.
- **Acelerador para tráfego cacheável HTTP** (CloudFront é mais barato).
- **TLS esperado no GA** (ele é L4).
- **Aceleradores esquecidos** pagando taxa fixa.
- **Ignorar o idle timeout** de conexões longas.
- **Não monitorar `ProcessedBytes`** (DT-Premium surpreende).

## 🧩 Quiz de Fixação

1. Qual a diferença entre o standard e o custom routing accelerator e quando usar cada um?
2. O que é BYOIP e que pré-requisito é indispensável?
3. Quando a preservação do IP do cliente não funciona?
4. Como o Global Accelerator é cobrado?

**Respostas:**
1) O standard escolhe o melhor endpoint saudável (ALB, NLB, EC2, EIP) com dials e pesos, ideal para aplicações e failover; o custom routing mapeia IP:porta do acelerador a instâncias e portas específicas em subnets, ideal para jogos e sessões determinísticas, sem health checks por instância.
2) É trazer seu próprio bloco de IPs públicos para usar no acelerador; é indispensável ter o bloco registrado em um RIR com ROA autorizando o ASN da AWS e provar a propriedade.
3) Quando o endpoint é um Elastic IP (e em configurações não suportadas): o tráfego chega com IPs do acelerador; para ALB, NLB e EC2 ela é suportada, com SG/ENIs gerenciados.
4) Pela taxa fixa por acelerador-hora (existindo ou não tráfego) mais a transferência premium (DT-Premium) por GB, que varia com o par de regiões, além de custos de balanceadores, logs e BYOIP.
