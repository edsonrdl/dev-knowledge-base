### O que é AWS Global Accelerator — IPs anycast, rede global da AWS, aceleradores, listeners e endpoints

> [!warning] Aviso
> Tipos de acelerador, endpoints suportados, preços e regiões do Global Accelerator mudam. Confirme na documentação. Os comandos **não foram executados**.

O **AWS Global Accelerator** dá à sua aplicação **dois endereços IP estáticos anycast** e leva o tráfego do usuário até o endpoint mais próximo e saudável **pela rede de backbone da AWS**, em vez de atravessar a internet pública por todo o caminho. Funciona para **TCP e UDP**, sem cache, e é ideal para aplicações não HTTP, jogos, IoT, VoIP e para quem precisa de **IPs fixos globais** com failover rápido entre regiões.

**Analogia:** a internet pública é uma **estrada com pedágios, buracos e desvios**. O Global Accelerator é uma **rampa de entrada para uma via expressa privada**: o motorista (pacote) entra na via expressa no ponto mais próximo e só sai perto do destino.

```
 SEM Global Accelerator:   Usuário ───── muitos saltos pela internet pública ─────► Região (sa-east-1)

 COM Global Accelerator:   Usuário ──► Edge mais próxima (IP anycast) ═══ backbone AWS ═══► Região
                                         (poucos saltos públicos)       (rede privada, estável)
```

---

## Conceitos

| Componente | O que é |
|---|---|
| **Accelerator** | O recurso principal; recebe **2 IPs anycast estáticos** (IPv4; dual-stack opcional) e um nome DNS |
| **Listener** | Define **portas e protocolo** (TCP/UDP) aceitos e a **afinidade de cliente** (nenhuma ou por IP de origem) |
| **Endpoint group** | Um grupo **por região**, com *traffic dial* e configuração de health check |
| **Endpoint** | Destino dentro do grupo: **ALB, NLB, instância EC2 ou Elastic IP** |
| **Standard accelerator** | Roteia ao melhor endpoint saudável (usa proximidade e saúde) |
| **Custom routing accelerator** | Mapeia usuários a **instâncias/portas específicas** (jogos multiplayer, sessões fixas) |

```
 Accelerator (IPs 75.2.x.x e 99.83.x.x)
   └─ Listener TCP 443
        ├─ Endpoint group us-east-1 (dial 100%) ─► ALB-us
        └─ Endpoint group sa-east-1 (dial 100%) ─► ALB-br
```

---

## O que é anycast

Os mesmos dois IPs são **anunciados simultaneamente por várias edge locations** no mundo. A internet encaminha cada usuário para a edge **topologicamente mais próxima**. A partir daí o tráfego segue pelo backbone da AWS até a região.

Consequências:

- **IPs não mudam**, mesmo que você troque/ adicione regiões ou endpoints atrás do acelerador. Ótimo para clientes que precisam **liberar IPs em firewall** ou não aceitam DNS (dispositivos embarcados).
- **Failover rápido**: o acelerador deixa de enviar a uma região doente em segundos (guiado pelos health checks), sem esperar expiração de TTL de DNS.
- Os IPs podem ser da AWS ou **seus (BYOIP)**, quando suportado.

## Standard accelerator (o caso comum)

Fluxo de uma conexão:

```
 1. Cliente resolve  a1234.awsglobalaccelerator.com  (ou usa os IPs diretamente)
 2. Pacote chega à edge AWS mais próxima
 3. O acelerador escolhe o endpoint saudável MAIS PRÓXIMO (por região, respeitando traffic dials)
 4. Tráfego vai pelo backbone até o ALB/NLB/EC2/EIP
 5. Resposta volta pelo mesmo caminho
```

Preservação do IP do cliente:

| Endpoint | IP do cliente visível? |
|---|---|
| **ALB** | Sim, via `X-Forwarded-For` (opção de preservar habilitada) |
| **NLB** com EC2/IP | Sim, conforme configuração |
| **EC2** | Sim (com preservação habilitada) |
| **Elastic IP** | Não (o acelerador faz NAT; sem preservação) |

---

## Custom routing accelerator

Mapeia deterministamente **combinações de IP/porta do acelerador** para **instâncias e portas específicas** em subnets VPC. Use quando **seu app decide** para onde cada usuário vai (ex.: **servidor de jogo** específico para uma sala, VoIP). Só com endpoints de **subnets VPC**; sem health check dinâmico igual ao standard.

---

## Casos de uso

| Caso | Por quê |
|---|---|
| Aplicação TCP/UDP global (jogos, VoIP, IoT/MQTT) | Camada 4 e backbone da AWS |
| **IPs estáticos globais** para whitelisting de parceiros | Anycast fixo |
| **Failover multi-região rápido** | Health check + traffic dials, sem depender de TTL |
| Reduzir **jitter e perda de pacotes** entre continentes | Backbone privado |
| Blue-green entre regiões | Traffic dials controlam o percentual por região |

Para HTTP cacheável e conteúdo estático, o CloudFront é a ferramenta; veja a comparação na próxima nota.

## Exemplo prático

```bash
# O serviço Global Accelerator usa a região us-west-2 como endpoint de API
aws globalaccelerator create-accelerator \
  --name app-global --ip-address-type IPV4 --enabled \
  --region us-west-2
# O retorno traz os 2 IPs estáticos e o DnsName do acelerador

# Listener TCP 443 com afinidade por IP de origem (opcional)
aws globalaccelerator create-listener --region us-west-2 \
  --accelerator-arn $ACC_ARN \
  --protocol TCP --port-ranges FromPort=443,ToPort=443 \
  --client-affinity SOURCE_IP

# Endpoint group na região do Brasil apontando para um ALB
aws globalaccelerator create-endpoint-group --region us-west-2 \
  --listener-arn $LISTENER_ARN --endpoint-group-region sa-east-1 \
  --endpoint-configurations EndpointId=$ALB_BR_ARN,Weight=128,ClientIPPreservationEnabled=true \
  --traffic-dial-percentage 100 \
  --health-check-protocol HTTPS --health-check-path /saude
```

Explicação: crie um endpoint group por região. Em ALB com `ClientIPPreservationEnabled`, a aplicação enxerga o IP real do cliente. O ALB deve estar com Security Group que permita o tráfego do acelerador (consulte a documentação sobre o grupo gerenciado).

## Anatomia detalhada de um acelerador

```
 Accelerator  (2 IPs anycast estáticos + nome DNS)
   └─ Listener TCP 443          (protocolo + portas + afinidade de cliente)
        ├─ Endpoint group sa-east-1   (traffic dial 100%)   ── Endpoint: ALB-br   (peso 128)
        │                                                    └─ Endpoint: ALB-br2  (peso 128)
        └─ Endpoint group us-east-1   (traffic dial 50%)    ── Endpoint: NLB-us   (peso 255)
```

| Elemento | Parâmetros e limites típicos |
|---|---|
| **Accelerator** | Tipo (*standard* ou *custom routing*), IPv4 ou dual-stack, nome DNS próprio; os IPs ficam atrelados ao acelerador enquanto ele existir |
| **Listener** | Protocolo **TCP**, **UDP** ou ambos; intervalos de portas; **afinidade de cliente**: `NONE` ou `SOURCE_IP` |
| **Endpoint group** | Um por **região**; *traffic dial* (0-100%), porta e protocolo do health check, intervalo (10 ou 30 s), limiar |
| **Endpoint** | ALB, NLB, instância EC2 ou Elastic IP; **peso** (0-255); preservação do IP do cliente |
| **Health check** | TCP, HTTP ou HTTPS; para ALB/NLB considera a saúde dos alvos |
| **Failover** | Tipicamente em dezenas de segundos, sem depender de TTL de DNS |

> [!warning] Limites, intervalos e valores mudam; confirme na documentação atual.

## Como o tráfego entra e é roteado

1. O cliente resolve o nome do acelerador (ou usa os IPs diretamente) e envia o pacote a um dos **IPs anycast**.
2. A internet roteia o pacote à **edge AWS mais próxima**.
3. Na borda, o acelerador termina a conexão TCP (ou encaminha UDP) e a envia pelo **backbone da AWS**, evitando congestionamentos da internet pública.
4. Escolhe o **endpoint group** por proximidade, saúde e traffic dial, e o endpoint pelo **peso**.
5. A resposta volta pelo mesmo caminho.

| Decisão | Critério |
|---|---|
| Qual região? | A mais próxima do usuário **saudável**, ajustada pelo *traffic dial* (o excedente transborda para outras regiões) |
| Qual endpoint? | Distribuição por **peso** entre os saudáveis |
| Qual conexão? | Com `SOURCE_IP`, o mesmo cliente tende ao mesmo endpoint |
| Tudo não saudável? | O tráfego é enviado mesmo assim (*fail-open*) para evitar queda total por health check mal configurado |

---

## O que o Global Accelerator **não** faz

| Não faz | Alternativa |
|---|---|
| **Cache** de conteúdo | CloudFront |
| **Terminação TLS/HTTP** (é L4) | ALB, NLB com TLS, CloudFront |
| **Roteamento por URL/host** | ALB, CloudFront behaviors |
| **Regras de WAF** | WAF no ALB/CloudFront |
| **DNS** | Route 53 (alias para o acelerador) |
| **Proteção total contra L7** | Shield Advanced + WAF |

## Casos de uso e padrões

| Caso | Como o acelerador entra |
|---|---|
| **Aplicação web multi-região** | Dois ALBs (um por região) atrás de um acelerador; failover rápido e IPs fixos |
| **IP estático para listas de liberação** | Parceiros liberam os 2 IPs; a infraestrutura por trás pode mudar |
| **Jogos e VoIP (UDP)** | Listener UDP; menor jitter pelo backbone |
| **IoT/MQTT** | TCP/TLS passando pelo acelerador até NLBs |
| **Blue-green entre regiões** | Traffic dials (90/10 → 50/50 → 0/100) |
| **Manutenção** | Dial 0% na região a drenar |
| **DR ativo-passivo** | Região secundária com dial 0%; assume se a primária ficar não saudável |

## Sinais de que vale a pena (e de que não vale)

| Vale | Não vale |
|---|---|
| Usuários globais com latência/jitter sensíveis | Usuários e origem na mesma região |
| Necessidade de IP fixo | Conteúdo HTTP cacheável (CloudFront é mais barato) |
| Failover entre regiões em segundos | Aplicação de região única sem requisito de IP fixo |
| Tráfego TCP/UDP não HTTP | Tráfego interno entre serviços da AWS |

---

## Erros comuns e armadilhas

- **Esperar cache de conteúdo:** Global Accelerator não faz cache.
- **Usar a região errada na API:** a API do serviço fica em us-west-2.
- **Esquecer de liberar os dois IPs anycast** no firewall do parceiro (ambos).
- **Health check apontando para caminho/porta sem resposta:** a região é tirada de rotação.
- **Elastic IP como endpoint** e esperar ver o IP do cliente: não é preservado.
- **Misturar expectativas com DNS:** o acelerador não substitui o Route 53; ele pode ser alvo de um Alias.
- **Não monitorar custo:** cobrança por hora do acelerador mais transferência (DT-Premium).

## 🧩 Quiz de Fixação

1. O que significa o acelerador ter IPs anycast estáticos?
2. Quais tipos de endpoint o standard accelerator aceita?
3. Quando usar um custom routing accelerator?

**Respostas:**
1) Os mesmos dois IPs são anunciados por várias edge locations; cada usuário entra na edge mais próxima. Os IPs não mudam mesmo ao alterar regiões ou endpoints, ótimo para whitelisting.
2) ALB, NLB, instâncias EC2 e Elastic IPs.
3) Quando a aplicação precisa direcionar usuários a instâncias/portas específicas de forma determinística, como servidores de jogo ou salas de VoIP.

### Questões de aprofundamento

4. Qual a diferença entre *traffic dial* e *peso* e como cada um é usado em um blue-green entre regiões?
5. O que acontece se todos os endpoints de um endpoint group ficarem não saudáveis?
6. Por que o Global Accelerator não substitui o CloudFront em um site estático global?

**Respostas:**
4) O *traffic dial* (0-100%) controla quanto do tráfego destinado a uma **região** vai para ela (o excedente transborda para outras); o *peso* (0-255) divide o tráfego **entre endpoints** dentro do grupo. No blue-green ajustam-se os dials (90/10, 50/50, 0/100).
5) O acelerador entra em *fail-open*: envia o tráfego mesmo assim, evitando queda total causada por health checks mal configurados; por isso é essencial monitorar a contagem de endpoints não saudáveis.
6) Porque não faz cache nem terminação HTTP/TLS: cada requisição ainda vai à origem. Para conteúdo estático global o CloudFront é mais rápido e barato; o Global Accelerator serve a TCP/UDP, IPs fixos e failover rápido.
