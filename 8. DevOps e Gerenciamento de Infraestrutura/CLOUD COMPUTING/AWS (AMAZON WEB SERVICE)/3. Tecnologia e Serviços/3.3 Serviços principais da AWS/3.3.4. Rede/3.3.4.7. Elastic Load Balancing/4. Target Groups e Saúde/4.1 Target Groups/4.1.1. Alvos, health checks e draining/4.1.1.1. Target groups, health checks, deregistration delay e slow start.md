### Target groups, health checks, deregistration delay e slow start

> [!warning] Aviso
> Valores padrão, limites e atributos de target groups mudam. Confirme na documentação do ELB. Os comandos **não foram executados**.

O **target group** é o elo entre o load balancer e a aplicação: define **quem** são os alvos, **como** falar com eles (protocolo e porta) e **como saber se estão saudáveis**. Entender health checks e o "desligamento suave" (deregistration delay) evita a maior parte dos erros 502/503/504 em produção.

**Analogia:** o target group é a **escala de plantão** de um hospital. Lista os médicos (alvos), checa periodicamente se respondem (health check), tira da escala quem não atende e, antes de liberar alguém, deixa terminar os atendimentos em curso (deregistration delay).

```
 Listener/regra ──► TARGET GROUP ──► alvo 1 (healthy)    ◄── recebe tráfego
                       │ health check ► alvo 2 (healthy)   ◄── recebe tráfego
                       │              ► alvo 3 (unhealthy) ◄── fora da rotação
```

## Tipos de alvo

| Target type | O que registra | Uso |
|---|---|---|
| **instance** | ID de instância EC2 (usa a IP primária e a porta do TG) | Auto Scaling Groups, EC2 tradicional |
| **ip** | Endereços IP privados (VPC, peering, on-premises via VPN/Direct Connect) | ECS Fargate/awsvpc, EKS (pods), híbrido |
| **lambda** | Uma função Lambda | Serverless atrás de ALB |
| **alb** | Um ALB (alvo de um NLB) | IP estático na frente do ALB |

O tipo é definido **na criação** e não pode ser alterado. Cada alvo pode participar de vários target groups (e portas diferentes).

## Health checks

O load balancer envia verificações periódicas a cada alvo; só os **saudáveis** recebem tráfego.

| Parâmetro | Função | Exemplo |
|---|---|---|
| **Protocolo / porta / caminho** | O que testar (`HTTP :traffic-port /saude`) | `/saude` leve |
| **Interval** | Segundos entre verificações | 30 |
| **Timeout** | Tempo de espera da resposta | 5 |
| **Healthy threshold** | Sucessos consecutivos para ficar saudável | 3 |
| **Unhealthy threshold** | Falhas consecutivas para ficar não saudável | 2 |
| **Success codes** | Códigos aceitos (ALB: `200` ou `200-299`) | `200` |

Tempo para remover um alvo ruim ≈ `interval × unhealthy threshold`. Para recolocá-lo: `interval × healthy threshold`.

```
 t=0   check OK      healthy
 t=30  check FALHA   (1/2)
 t=60  check FALHA   (2/2) → UNHEALTHY → deixa de receber tráfego
 ... o alvo se recupera ...
 3 checks OK seguidos        → volta a HEALTHY
```

### Estados do alvo

`initial` (registrando) → `healthy` → `unhealthy` → `draining` (sendo removido) / `unused` (TG não ligado a listener) / `unavailable`.

### Boas práticas de endpoint de saúde

- Rota **leve** e dedicada (`/saude`), sem autenticação.
- Verificar o **mínimo necessário** para atender: dependências críticas (ex.: conexão com o banco) opcionalmente, com cuidado — se o banco cair e **todos** os alvos falharem, o ALB com todos unhealthy passa a enviar tráfego a todos (*fail-open*) e a aplicação continua degradada.
- Não confundir **liveness** (processo vivo) com **readiness** (pronto para tráfego).
- Em NLB com TCP, o health check apenas abre a conexão: prefira HTTP/HTTPS se a aplicação puder falhar sem fechar a porta.

### Quando todos os alvos estão unhealthy

O ALB/NLB envia a requisição a **todos os alvos** (modo fail-open) em vez de devolver erro, para evitar queda total por um health check mal feito. Ainda assim, monitore `UnHealthyHostCount`.

## Deregistration delay (connection draining)

Quando um alvo é removido (deploy, scale-in, manutenção), o ELB entra em **draining**: **para de enviar novas requisições**, mas **permite terminar as em andamento** por até o tempo configurado.

| Atributo | Padrão | Observação |
|---|---|---|
| `deregistration_delay.timeout_seconds` | 300 s | Reduza para APIs rápidas (ex.: 30 s) para acelerar deploys; aumente para conexões longas (uploads, WebSocket) |

```
 Remover alvo ──► DRAINING (sem novas conexões) ──► conexões em curso terminam
                       │                                    │
                       └── passou o delay? ──► conexões restantes são encerradas ──► alvo removido
```

Em Auto Scaling, o **lifecycle hook** e o delay trabalham juntos para evitar derrubar o usuário no meio de uma requisição.

## Slow start

Ao entrar na rotação, um alvo novo (ainda "frio": cache vazio, JIT não aquecido) pode ser sobrecarregado se receber a parcela cheia de tráfego. O **slow start** aumenta **gradualmente** a participação do alvo durante uma janela (30 a 900 s).

- Disponível com algoritmo **round robin** em ALB (não combina com *least outstanding requests* na configuração padrão).
- Útil para aplicações Java/JVM e com cache local.

---

## Algoritmos de roteamento (ALB)

| Algoritmo | Como decide |
|---|---|
| **Round robin** (padrão) | Distribui em sequência |
| **Least outstanding requests** | Envia ao alvo com menos requisições pendentes; melhor com tempos de resposta variáveis |
| **Weighted random** | Opção com detecção de anomalias (*automatic target weights*), reduz envio a alvos com muitos erros |

No NLB, o roteamento é por **hash de fluxo**.

## Exemplo prático

```bash
# Target group HTTP porta 8080 com health check /saude
aws elbv2 create-target-group \
  --name app-tg --protocol HTTP --port 8080 \
  --vpc-id vpc-0abc --target-type instance \
  --health-check-path /saude --health-check-interval-seconds 15 \
  --health-check-timeout-seconds 5 \
  --healthy-threshold-count 2 --unhealthy-threshold-count 2 \
  --matcher HttpCode=200

# Ajustar draining, slow start e algoritmo
aws elbv2 modify-target-group-attributes --target-group-arn $TG \
  --attributes Key=deregistration_delay.timeout_seconds,Value=30 \
               Key=slow_start.duration_seconds,Value=60 \
               Key=load_balancing.algorithm.type,Value=least_outstanding_requests
# Atenção: slow start e least_outstanding_requests não funcionam juntos; escolha um conforme a documentação vigente

# Registrar alvos e consultar a saúde
aws elbv2 register-targets --target-group-arn $TG --targets Id=i-0aaa111 Id=i-0bbb222
aws elbv2 describe-target-health --target-group-arn $TG \
  --query 'TargetHealthDescriptions[].{Alvo:Target.Id,Estado:TargetHealth.State,Motivo:TargetHealth.Reason}'
# Motivos comuns: Target.FailedHealthChecks, Target.Timeout, Target.NotRegistered
```

Explicação: com interval 15 e unhealthy threshold 2, um alvo quebrado sai da rotação em ~30 s. `describe-target-health` é o primeiro comando de diagnóstico quando surgem 502/503.

## Diagnóstico rápido de erros do ALB

| Erro | Causa provável |
|---|---|
| **502 Bad Gateway** | Alvo fechou a conexão, resposta malformada, TLS inválido ao alvo |
| **503 Service Unavailable** | Nenhum alvo registrado/saudável no target group |
| **504 Gateway Timeout** | Alvo não respondeu dentro do timeout de ociosidade; SG/NACL bloqueando |
| **Alvo unhealthy** | Caminho/porta errados, Security Group do alvo sem liberar o do ALB, aplicação lenta, código de sucesso diferente |

## Parametrizando por tipo de aplicação

| Aplicação | Interval | Timeout | Healthy/Unhealthy | Delay de deregistro | Slow start |
|---|---|---|---|---|---|
| API stateless rápida | 10 s | 5 s | 2 / 2 | 30 s | 0 |
| Web com JVM de warm-up lento | 15 s | 5 s | 3 / 2 | 60 s | 60-120 s |
| Upload/streaming longo | 30 s | 10 s | 3 / 3 | 300+ s | 0 |
| WebSocket | 30 s | 10 s | 2 / 3 | Conforme sessão | 0 |

> [!warning] Valores, limites e preços mudam; os exemplos deste material não foram executados. Faixas permitidas para intervalo, timeout e delay variam por tipo de balanceador.

```
 Tempo de detecção ≈ interval × unhealthy_threshold
 10 s × 2 = 20 s   |   30 s × 3 = 90 s

 Deploy rolling com draining:
 [alvo marcado draining] ──► sem novas conexões ──► requisições ativas terminam
                         └─ ≤ deregistration delay ─► remoção segura
```

## Árvore de decisão para diagnosticar alvo unhealthy

```
Alvo unhealthy?
├─ Código de saída do health check (consulte a Reason no console)
│    ├─ Request timed out ──► SG do alvo não aceita o LB / app lenta
│    ├─ Response code mismatch ─► path errado ou retorna 301/401
│    └─ Connection refused ──► app não escuta na porta
└─ Só no deploy? ──► slow start / startup mais lento que o threshold
```

## CLI comentado

```bash
# Ajusta health check do target group
aws elbv2 modify-target-group --target-group-arn <TG_ARN> \
  --health-check-path /healthz --health-check-interval-seconds 15 \
  --healthy-threshold-count 3 --unhealthy-threshold-count 2 \
  --matcher HttpCode=200-299

# Define deregistration delay e slow start
aws elbv2 modify-target-group-attributes --target-group-arn <TG_ARN> \
  --attributes Key=deregistration_delay.timeout_seconds,Value=60 \
               Key=slow_start.duration_seconds,Value=90

# Vê o estado e o motivo de cada alvo
aws elbv2 describe-target-health --target-group-arn <TG_ARN>
```

## Troubleshooting

| Sintoma | Causa provável | Ação |
|---|---|---|
| Erros 502 durante deploy | Delay de deregistro curto demais | Aumentar o delay |
| Alvos oscilando | Health check muito agressivo | Elevar thresholds/timeouts |
| Todos unhealthy, app OK | SG sem origem do LB, path 404 | Revisar SG e path |
| Alvo novo sobrecarregado | Sem slow start | Habilitar slow start |

## Custo

Target groups em si não cobram; o custo vem do balanceador (hora e LCU/NLCU). Health checks muito frequentes geram tráfego e carga na aplicação, e delays longos prolongam a vida de instâncias em deploys, aumentando custo de capacidade duplicada.

## Erros comuns e armadilhas

- **Security Group do alvo não permite o SG do load balancer** na porta de tráfego **e** na porta do health check.
- **Health check em rota que exige login** (retorna 302/401): alvo sempre unhealthy.
- **Matcher `200` com a aplicação devolvendo 204/302.**
- **Health check pesado** (consulta ao banco por requisição): sobrecarrega a aplicação e causa quedas em cascata.
- **Deregistration delay padrão (300 s) em deploys frequentes:** deploys lentos.
- **Delay curto demais com conexões longas:** requisições cortadas.
- **Keep-alive do alvo menor que o timeout do ALB:** o alvo fecha a conexão antes e gera 502; o keep-alive da aplicação deve ser **maior** que o idle timeout do load balancer.
- **Registrar alvos por IP de outro tipo sem rota** ou sem SG correto.
- **Ignorar métricas** `HealthyHostCount`, `UnHealthyHostCount`, `TargetResponseTime`, `HTTPCode_Target_5XX_Count`.

## 🧩 Quiz de Fixação

1. Com interval 30 s e unhealthy threshold 2, em quanto tempo aproximado um alvo quebrado sai da rotação?
2. O que o deregistration delay faz e quando alterá-lo?
3. O ALB devolve 502 intermitente. Que configuração de keep-alive costuma explicar isso?

**Respostas:**
1) Cerca de **60 s** (interval × unhealthy threshold = 30 × 2).
2) Ele coloca o alvo em *draining*: não recebe novas requisições, mas as em andamento podem terminar até o tempo configurado (padrão 300 s). Reduza para APIs rápidas e deploys frequentes; aumente para conexões longas como uploads ou WebSocket.
3) O keep-alive timeout da aplicação menor que o idle timeout do load balancer: o alvo fecha a conexão ociosa enquanto o ALB ainda a reutiliza, gerando 502. O keep-alive da aplicação deve ser maior.

**Questões complementares:**

4. Como estimar o tempo para detectar um alvo doente?
5. Qual sintoma indica deregistration delay curto demais?
6. Quando habilitar slow start?

**Respostas das questões complementares:**
4) Aproximadamente intervalo × unhealthy threshold (por exemplo, 10 s × 2 = 20 s).
5) Erros 502 ou conexões cortadas durante deploys, porque requisições ativas são interrompidas antes de terminar.
6) Quando alvos novos precisam de aquecimento (JVM, caches) e não devem receber a carga completa imediatamente.
