### Application Load Balancer — listeners, regras, ações e roteamento por caminho, host e header

> [!warning] Aviso
> Condições, ações, limites de regras e recursos (autenticação, mTLS, gRPC) do ALB mudam. Confirme na documentação. Os comandos e JSONs **não foram executados**.

O **Application Load Balancer (ALB)** opera na **camada 7**: entende HTTP/HTTPS/gRPC e decide o destino olhando **caminho, host, headers, query string, método e IP de origem**. É o tipo ideal para sites e microsserviços, pois um único ALB atende vários serviços por meio de regras.

**Analogia:** o ALB é a **recepção de um prédio comercial**. O visitante diz a empresa (host) e o andar (caminho); a recepcionista (regra) o encaminha ao elevador certo (target group) ou o redireciona a outro prédio.

```
 Cliente ─► ALB
            └─ Listener HTTPS:443
                 ├─ Regra 1: host = api.exemplo.com.br        ─► TG-api
                 ├─ Regra 2: path /admin/* + IP 203.0.113.0/24 ─► TG-admin
                 ├─ Regra 3: path /img/*                       ─► TG-imagens
                 ├─ Regra 4: header X-Mobile = true            ─► TG-mobile
                 └─ Default                                     ─► TG-web
 Listener HTTP:80 ─► Redirect 301 para HTTPS:443
```

## Listeners

Um **listener** escuta uma combinação **protocolo:porta** (HTTP:80, HTTPS:443) e contém uma **ação padrão** mais regras com prioridade. Um ALB aceita vários listeners.

| Protocolo | Observações |
|---|---|
| **HTTP** | Sem criptografia; normalmente só redireciona para HTTPS |
| **HTTPS** | Exige certificado (ACM ou importado) e política de segurança TLS |
| **HTTP/2, gRPC, WebSocket** | Suportados (gRPC exige HTTPS e target group com protocolo gRPC) |

---

## Regras: condições e ações

Cada regra tem uma **prioridade** (1 a 50000; número menor é avaliado primeiro), uma ou mais **condições** (todas precisam casar) e **ações**. A regra **Default** é a última e não tem condição.

### Condições

| Condição | Exemplo |
|---|---|
| **Host header** | `api.exemplo.com.br`, `*.exemplo.com.br` |
| **Path pattern** | `/api/*`, `/img/*` |
| **HTTP header** | `User-Agent`, header customizado |
| **Query string** | `?versao=2` |
| **HTTP request method** | `GET`, `POST` |
| **Source IP** | CIDR do cliente |

### Ações

| Ação | Efeito |
|---|---|
| **forward** | Encaminha a um ou mais target groups (com **pesos**, útil para canary/blue-green) |
| **redirect** | Responde 301/302 para outro protocolo/host/caminho (ex.: HTTP → HTTPS) |
| **fixed-response** | Devolve uma resposta fixa (ex.: 503 de manutenção, 403) |
| **authenticate-oidc / authenticate-cognito** | Exige login via IdP OIDC ou Cognito antes de encaminhar |

Encaminhamento ponderado para canary:

```
Regra: path /*  ─► forward
   TG-v1 peso 90
   TG-v2 peso 10      # 10% do tráfego testa a nova versão
```

Comparação com o roteamento ponderado do DNS: o peso no ALB é **por requisição e imediato**, sem esperar TTL; veja [[8. ## Comportamentos importantes do ALB

| Tema | Detalhe |
|---|---|
| **Headers adicionados** | `X-Forwarded-For` (IP do cliente), `X-Forwarded-Proto`, `X-Forwarded-Port`; a aplicação enxerga o IP do ALB, não o do cliente |
| **Terminação TLS** | O ALB descriptografa; o tráfego ao alvo pode ser HTTP ou HTTPS |
| **Timeout de ociosidade** | Padrão 60 s; ajuste para uploads/requisições lentas |
| **Tamanho** | Cresce sozinho; cobrado por LCU (capacidade consumida) |
| **Múltiplos TGs por regra** | Permitido (forward ponderado) |
| **Autenticação** | OIDC/Cognito evita implementar login na aplicação |
| **WAF** | Web ACL regional pode ser associada ao ALB |
| **mTLS** | Autenticação mútua opcional por certificado de cliente (confirme suporte atual) |
| **Alvos** | Instâncias EC2, IPs (inclusive on-premises via VPN/Direct Connect), Lambda |

> Por trás de CloudFront ou outro proxy, use `X-Forwarded-For` com cuidado: o primeiro IP da lista é o do cliente, os seguintes são proxies.

## Exemplo prático

Cenário: `www.exemplo.com.br` serve o site; `/api/*` vai para outro serviço; HTTP é redirecionado.

```bash
# 1) Listener HTTP:80 que redireciona tudo para HTTPS
aws elbv2 create-listener \
  --load-balancer-arn $ALB_ARN --protocol HTTP --port 80 \
  --default-actions 'Type=redirect,RedirectConfig={Protocol=HTTPS,Port=443,StatusCode=HTTP_301}'

# 2) Listener HTTPS:443 com certificado do ACM; padrão encaminha ao site
aws elbv2 create-listener \
  --load-balancer-arn $ALB_ARN --protocol HTTPS --port 443 \
  --certificates CertificateArn=$CERT_ARN \
  --ssl-policy ELBSecurityPolicy-TLS13-1-2-2021-06 \
  --default-actions Type=forward,TargetGroupArn=$TG_WEB
# --ssl-policy: política TLS; use uma recente e confirme o nome vigente na documentação

# 3) Regra: /api/* vai para o target group da API
aws elbv2 create-rule \
  --listener-arn $LISTENER_443 --priority 10 \
  --conditions Field=path-pattern,Values='/api/*' \
  --actions Type=forward,TargetGroupArn=$TG_API

# 4) Regra: página de manutenção para um caminho
aws elbv2 create-rule \
  --listener-arn $LISTENER_443 --priority 5 \
  --conditions Field=path-pattern,Values='/relatorios/*' \
  --actions 'Type=fixed-response,FixedResponseConfig={StatusCode=503,ContentType=text/plain,MessageBody=Em manutencao}'
```

Explicação: a prioridade 5 (manutenção) é avaliada antes da 10 (API) e do padrão. A aplicação lê o protocolo original em `X-Forwarded-Proto`.

## Avaliação de regras: prioridade e ordem

```
 Requisição ──► Listener :443
                 ├─ Regra prio 10: Host = api.exemplo.com.br  AND Path = /v2/*   → forward TG-api-v2
                 ├─ Regra prio 20: Host = api.exemplo.com.br                      → forward TG-api-v1
                 ├─ Regra prio 30: Header X-Mobile = true                         → forward TG-mobile
                 ├─ Regra prio 40: Path = /antigo/*                               → redirect 301 /novo/
                 └─ Default                                                       → fixed-response 404
 Avaliação: menor prioridade primeiro; a primeira regra que casar vence (todas as condições AND).
```

| Item | Regra |
|---|---|
| Condições na mesma regra | Combinam com **AND**; valores múltiplos da mesma condição combinam com **OR** |
| Curingas | `*` (vários caracteres) e `?` (um caractere) em path/host |
| Prioridade | 1 a 50.000; números menores são avaliados antes |
| Regra padrão | Sempre existe e é avaliada por último |
| Limite de regras | Por listener, com valor padrão limitado (peça aumento se necessário) |

> [!warning] Limites de regras, condições e valores por regra mudam; confirme na documentação atual.

## Padrões de roteamento

| Padrão | Condição | Ação |
|---|---|---|
| Microsserviços por path | `/pedidos/*`, `/clientes/*` | forward para um TG por serviço |
| Multi-tenant por host | `cliente-a.exemplo.com` | forward para o TG do tenant |
| Canary | Mesma regra com dois TGs e pesos 95/5 | forward ponderado |
| Redirecionar HTTP→HTTPS | Listener :80 | redirect 301 para `https://#{host}:443/#{path}?#{query}` |
| Manutenção | Regra de maior prioridade | fixed-response 503 com corpo HTML |
| Roteamento por método | `HTTP request method = POST` | forward para TG de escrita |
| Restrição por IP | `source-ip` | forward, ou fixed-response 403 para o resto |

### Exemplo de CLI (comentado, não executado)

```bash
# Regra: host + path -> target group
aws elbv2 create-rule --listener-arn <ARN-listener-443> --priority 10 \
  --conditions Field=host-header,Values=api.exemplo.com.br Field=path-pattern,Values='/v2/*' \
  --actions Type=forward,TargetGroupArn=<ARN-tg-v2>
# Redirect HTTP -> HTTPS no listener 80
aws elbv2 modify-listener --listener-arn <ARN-listener-80> \
  --default-actions 'Type=redirect,RedirectConfig={Protocol=HTTPS,Port=443,StatusCode=HTTP_301}'
```

## Troubleshooting de roteamento

| Sintoma | Causa provável | Verificação |
|---|---|---|
| Sempre cai na regra padrão | Prioridade/condição errada; host com porta | Revisar regras; o Host não inclui `:443` na condição |
| 503 "no targets" | Target group vazio ou todos unhealthy | Console de Target Groups, health checks |
| 404 gerado pelo ALB | Resposta fixa configurada na regra padrão | Ajustar regra/ação |
| Loop de redirect | HTTPS→HTTP→HTTPS entre CDN e ALB | Alinhar protocolos de origem do CloudFront |
| Path com barra final falha | Padrão `/api` não casa `/api/` | Usar `/api*` ou `/api/*` conforme o caso |

## Custo

Cobrança por hora do ALB e por **LCU** (novas conexões, conexões ativas, bytes processados e avaliações de regras, vale a maior dimensão). Muitas regras complexas e uso intenso de cabeçalhos aumentam as avaliações de regra.

---

## Erros comuns e armadilhas

- **Ordem/prioridade errada das regras:** uma regra ampla (`/*`) com prioridade menor engole as específicas.
- **Esquecer o redirecionamento HTTP → HTTPS.**
- **A aplicação confia no IP do ALB** como IP do cliente: leia `X-Forwarded-For`.
- **Timeout de ociosidade menor que a requisição mais longa:** erro 504.
- **Security Group do alvo sem permitir o SG do ALB.**
- **Usar fixed-response e esquecer o content-type** em páginas HTML.
- **Muitas regras com condições complexas** sem medir: a avaliação é sequencial por prioridade.
- **Habilitar autenticação OIDC sem tratar o cookie de sessão** e a expiração.

## 🧩 Quiz de Fixação

1. Como o ALB decide para qual target group enviar uma requisição?
2. Como redirecionar todo o HTTP para HTTPS?
3. Como fazer um canary de 10% para uma nova versão sem DNS?

**Respostas:**
1) Avalia as regras do listener em ordem de **prioridade**; a primeira cujas condições (host, caminho, header, query, método, IP) casam executa sua ação (forward, redirect, fixed-response, autenticação). Se nenhuma casar, aplica-se a regra padrão.
2) Crie um listener HTTP:80 com ação padrão **redirect** para HTTPS:443 com status 301.
3) Em uma regra com ação **forward**, associe dois target groups com **pesos** 90 e 10.

### Questões de aprofundamento

4. Uma regra tem `Host = api.exemplo.com` e `Path = /v2/*`. Uma requisição para `web.exemplo.com/v2/x` casa?
5. Como fazer um canary de 5% no ALB sem criar nova regra por host?
6. O que gera 503 sem que a aplicação seja chamada?

**Respostas:**
4) Não; as condições dentro de uma regra combinam com AND, então ambas precisam ser verdadeiras.
5) Na ação forward da regra, indicar dois target groups com pesos 95 e 5.
6) Target group sem alvos saudáveis (ou vazio) ou erro de capacidade do ALB; o ALB responde 503 sem chamar a aplicação.
