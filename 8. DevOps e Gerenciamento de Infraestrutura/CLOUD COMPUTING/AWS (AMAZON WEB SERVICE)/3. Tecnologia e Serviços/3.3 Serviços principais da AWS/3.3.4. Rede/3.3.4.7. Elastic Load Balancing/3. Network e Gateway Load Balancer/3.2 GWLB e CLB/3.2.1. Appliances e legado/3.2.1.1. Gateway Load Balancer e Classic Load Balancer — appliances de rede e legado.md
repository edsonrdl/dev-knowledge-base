### Gateway Load Balancer e Classic Load Balancer — appliances de rede e legado

> [!warning] Aviso
> Aposentadoria do Classic Load Balancer, integrações do GWLB e limites mudam. Confirme o status e o plano de migração na documentação da AWS. Os comandos **não foram executados**.

Esta nota cobre os dois tipos restantes do ELB: o **Gateway Load Balancer (GWLB)**, para inserir **appliances de rede** (firewalls, IDS/IPS, inspeção profunda) no caminho do tráfego, e o **Classic Load Balancer (CLB)**, tipo **legado** que você encontrará em contas antigas e deve planejar migrar.

---

## Gateway Load Balancer (GWLB)

**Problema:** você quer que **todo** o tráfego (entrada, saída ou entre VPCs) passe por um firewall ou sistema de inspeção de terceiros (Palo Alto, Fortinet, Check Point, etc.), com escala e alta disponibilidade, sem montar balanceamento e roteamento manuais.

**Solução:** o GWLB atua na **camada 3** como um "gateway transparente" e balanceador ao mesmo tempo. Ele encapsula os pacotes no protocolo **GENEVE** (porta UDP 6081) e os entrega a uma frota de appliances; os appliances inspecionam e devolvem os pacotes ao GWLB, que os repassa ao destino.

**Analogia:** o GWLB é o **posto de inspeção de uma alfândega** com vários fiscais. Todo veículo passa pelo posto, é direcionado a um fiscal livre, inspecionado e liberado; o motorista nem percebe que houve um desvio.

```
 VPC de aplicação                                 VPC de segurança (inspeção)
 ┌──────────────┐   rota → endpoint GWLBE   ┌──────────────────────────────────┐
 │  App (EC2)   │ ───────────────────────►  │  GWLB ──GENEVE──► Appliance 1     │
 │              │ ◄───────────────────────  │       ◄─────────  Appliance 2 ... │
 └──────────────┘    (tráfego de retorno)   └──────────────────────────────────┘
        │  VPC endpoint do tipo "Gateway Load Balancer Endpoint" (GWLBE) via PrivateLink
```

### Componentes

| Componente | Função |
|---|---|
| **Gateway Load Balancer** | Distribui o tráfego entre appliances; mantém o fluxo (*flow stickiness*) para que ida e volta passem pelo mesmo appliance |
| **Target group (IP/instance)** | Appliances virtuais, protocolo GENEVE |
| **GWLB Endpoint (GWLBE)** | Endpoint (PrivateLink) na VPC do consumidor; o **destino das rotas** que desviam o tráfego |
| **Route tables** | Rotas apontando para o GWLBE para forçar o tráfego pela inspeção |

### Quando usar

- Firewall de próxima geração, IPS/IDS e inspeção de pacotes centralizados.
- Arquitetura de **inspeção centralizada** com Transit Gateway (VPC de inspeção).
- Qualquer appliance de terceiros que precise ser inserido de forma **transparente e escalável**.
- Opção gerenciada alternativa da AWS: **AWS Network Firewall** (sem appliances de terceiros; veja a trilha de segurança).

### Exemplo prático

```bash
# GWLB na VPC de segurança
aws elbv2 create-load-balancer \
  --name inspecao-gwlb --type gateway \
  --subnets subnet-0sec111 subnet-0sec222

# Target group GENEVE (porta 6081) com os appliances
aws elbv2 create-target-group \
  --name appliances --protocol GENEVE --port 6081 \
  --vpc-id vpc-0seguranca --target-type instance \
  --health-check-protocol HTTP --health-check-port 80

# Listener do GWLB: encaminha todos os pacotes ao target group
aws elbv2 create-listener --load-balancer-arn $GWLB_ARN \
  --default-actions Type=forward,TargetGroupArn=$TG_APP

# Publicar como endpoint service e criar o endpoint (GWLBE) na VPC do consumidor
aws ec2 create-vpc-endpoint-service-configuration \
  --gateway-load-balancer-arns $GWLB_ARN --no-acceptance-required
aws ec2 create-vpc-endpoint --vpc-endpoint-type GatewayLoadBalancer \
  --vpc-id vpc-0aplicacao --service-name com.amazonaws.vpce.us-east-1.vpce-svc-0abc \
  --subnet-ids subnet-0app111
# Por fim, ajuste as route tables para enviar o tráfego ao vpce-xxxx (GWLBE)
```

Explicação: cada consumidor recebe um endpoint na sua VPC; as **tabelas de rota** é que decidem quais tráfegos são desviados à inspeção.

## Classic Load Balancer (CLB)

O **CLB** é a geração original do ELB (antes do ALB e do NLB). Opera nas camadas 4 e 7 de forma **limitada**: balanceia HTTP/HTTPS/TCP/SSL, mas **sem roteamento por caminho/host**, sem target groups, sem WebSocket/HTTP2 completos, sem integração moderna com contêineres.

| Característica | CLB | Substituto recomendado |
|---|---|---|
| Roteamento por URL/host | Não | **ALB** |
| IP estático / TCP de alta performance | Não | **NLB** |
| Target groups / ECS dinâmico | Não | ALB/NLB |
| Registro | Instâncias diretamente | Target groups |
| API CLI | `aws elb` (antiga) | `aws elbv2` |

### Como identificar e migrar

1. Liste os CLBs da conta (`aws elb describe-load-balancers`).
2. Classifique o tráfego: HTTP/HTTPS → **ALB**; TCP/UDP/IP fixo → **NLB**.
3. Use as ferramentas de migração oferecidas no console (assistente de migração do CLB) ou recrie o balanceador com IaC.
4. Teste em paralelo e troque o DNS (Alias no Route 53) com **peso gradual**.
5. Desative o CLB depois de confirmar o tráfego.

```bash
# Inventário de Classic Load Balancers
aws elb describe-load-balancers \
  --query 'LoadBalancerDescriptions[].{Nome:LoadBalancerName,DNS:DNSName,Instancias:Instances[].InstanceId}'
```

### Diferenças de comportamento a lembrar na migração

- **Health check:** CLB usa configuração no próprio balanceador; ALB/NLB usam o target group.
- **Sticky sessions:** CLB tem cookie próprio; ALB tem cookie de duração/aplicação por target group.
- **Certificados e SNI:** o CLB tem suporte limitado a múltiplos certificados; o ALB suporta SNI com vários certificados por listener.
- **Registro de instâncias:** no ALB/NLB, via target group (e Auto Scaling associado ao TG).

## Tabela final dos quatro tipos

| Se você precisa de... | Use |
|---|---|
| Roteamento HTTP/HTTPS inteligente, WAF, autenticação | ALB |
| TCP/UDP, IP fixo, PrivateLink, performance extrema | NLB |
| Inserir firewall/IDS de terceiros de forma transparente | GWLB |
| Nada (legado a migrar) | CLB |

## Arquitetura de inspeção centralizada com GWLB

```
 Spoke VPC (apps) ──► Gateway Load Balancer Endpoint (GWLBe) ──PrivateLink──► GWLB (VPC de segurança)
                              ▲                                                     │ GENEVE (porta 6081)
                              └───────── tráfego devolvido (permitido) ◄────── Appliances (firewall/IPS)
 Tabelas de rota do spoke apontam 0.0.0.0/0 (ou o prefixo) ao GWLBe; o fluxo é simétrico e sticky.
```

| Característica | Detalhe |
|---|---|
| Camada | 3 (transparente, IP) |
| Encapsulamento | **GENEVE** na porta 6081, preservando o pacote original |
| Distribuição | Hash de 5-tupla; fluxos simétricos ficam no mesmo appliance |
| Escala | Appliances registrados em um target group, com health checks |
| Entrega | Via **GWLB Endpoint** (PrivateLink) dentro de cada VPC consumidora |
| Cross-zone | Opcional (desligado por padrão) |

## Classic Load Balancer: por que migrar

| Aspecto | CLB | Substituto |
|---|---|---|
| HTTP/HTTPS L7 | Limitado (sem regras por path/host) | **ALB** |
| TCP/UDP de alta performance | Limitado | **NLB** |
| WebSocket/HTTP2/gRPC | Não nativo | ALB |
| Sticky e health checks | Básico | ALB/NLB com TG |
| Suporte futuro | Legado (EC2-Classic encerrado) | ALB/NLB |

### Plano de migração do CLB

1. Inventariar listeners, health checks, stickiness e certificados.
2. Criar ALB (HTTP) ou NLB (TCP) equivalente com target groups.
3. Validar com tráfego de teste e Route 53 ponderado (por exemplo 5%).
4. Subir o peso gradualmente e desativar o CLB.
5. Para apps TCP puros, prefira NLB; use o assistente de migração do console quando disponível.

## Quando escolher cada um

| Necessidade | Escolha |
|---|---|
| Inserir firewall, IPS, DPI em linha | **GWLB** |
| Aplicação web com regras L7 | **ALB** |
| TCP/UDP, IP fixo, milhões de conexões | **NLB** |
| Sistema legado já estável | CLB (planejar migração) |

## Troubleshooting do GWLB

| Sintoma | Causa provável | Ação |
|---|---|---|
| Tráfego não chega ao appliance | Rotas do spoke não apontam ao GWLBe | Conferir tabelas de rota e subnets do endpoint |
| Fluxos assimétricos | Retorno por caminho diferente | Rota de retorno pelo mesmo GWLBe; appliance stateful |
| Appliances "unhealthy" | Health check em porta errada ou SG | Liberar porta de health check |
| MTU/fragmentação | Overhead GENEVE | Ajustar MTU (jumbo frames) e MSS |

## Custo

Cobrança por hora do GWLB e **GLCU**, mais por hora do endpoint (GWLBe) e por GB processado; a inspeção centralizada troca custo de appliances por VPC por custo de tráfego.

### Exemplo de CLI (comentado, não executado)

```bash
aws elbv2 create-load-balancer --name gwlb-seg --type gateway --subnets subnet-aaa subnet-bbb
aws elbv2 create-target-group --name tg-fw --protocol GENEVE --port 6081 --vpc-id vpc-seg

aws ec2 create-vpc-endpoint-service-configuration --gateway-load-balancer-arns <ARN-gwlb> --no-acceptance-required
aws ec2 create-vpc-endpoint --vpc-endpoint-type GatewayLoadBalancer --service-name <service> --vpc-id vpc-spoke --subnet-ids subnet-x
```

## Erros comuns e armadilhas

- **GWLB sem rotas apontando para o endpoint:** o tráfego nunca é desviado.
- **Appliances sem o suporte a GENEVE** ou sem health check configurado: ficam fora de rotação.
- **Ausência de simetria de fluxo** (ida e volta por appliances diferentes): quebra inspeção stateful; o GWLB mantém o fluxo, mas rotas manuais podem quebrar isso.
- **Esquecer o custo** do GWLB (por hora e por GB) além do licenciamento dos appliances.
- **Iniciar projeto novo em CLB.**
- **Migrar CLB para ALB sem rever health checks, timeouts e regras de sessão.**
- **Cutover de DNS brusco** na migração, sem peso gradual e sem rollback.

## 🧩 Quiz de Fixação

1. Para que serve o Gateway Load Balancer e qual protocolo ele usa para entregar tráfego aos appliances?
2. O que é o GWLB Endpoint e qual o papel das route tables?
3. Por que migrar de CLB e para qual tipo, conforme o caso?

**Respostas:**
1) Serve para inserir appliances de rede (firewall, IDS/IPS, inspeção) de forma transparente, escalável e altamente disponível. Ele encapsula os pacotes em **GENEVE** (UDP 6081) e os entrega aos appliances.
2) O **GWLBE** é um VPC endpoint (PrivateLink) na VPC do consumidor que dá acesso ao GWLB. As **route tables** apontam para ele como destino, desviando o tráfego que deve ser inspecionado.
3) O CLB é legado, limitado (sem roteamento L7, sem target groups, recursos modernos ausentes). Tráfego HTTP/HTTPS migra para **ALB**; TCP/UDP, IP estático ou alta performance migram para **NLB**.

### Questões de aprofundamento

4. Por que o GWLB usa GENEVE?
5. Como o tráfego de uma VPC aplicativa chega ao appliance?
6. Quando migrar de CLB para NLB em vez de ALB?

**Respostas:**
4) Para encapsular o pacote original sem alterá-lo, mantendo a transparência para firewalls e IPS.
5) As tabelas de rota apontam para um GWLB Endpoint, que entrega via PrivateLink ao GWLB; este distribui aos appliances e devolve o tráfego aprovado.
6) Quando o legado é TCP/UDP puro sem regras L7, ou exige IP fixo e desempenho elevado.
