### Network Load Balancer — camada 4, IP estático, preservação de IP e PrivateLink

> [!warning] Aviso
> Suporte a Security Groups no NLB, limites de listeners, recursos de TLS e quotas mudam. Confirme na documentação. Os comandos **não foram executados**.

O **Network Load Balancer (NLB)** opera na **camada 4** (TCP, UDP, TLS). Não olha o conteúdo HTTP: decide pelo **fluxo** (IP/porta de origem e destino). Em troca, oferece **latência muito baixa**, capacidade para **milhões de requisições por segundo**, **IP estático por AZ** e integração com **PrivateLink**.

**Analogia:** se o ALB é a recepcionista que lê o crachá e o destino do visitante, o NLB é a **cancela de estacionamento**: abre rápido para o carro seguinte sem perguntar nada, e cada carro (conexão) fica ligado à mesma vaga enquanto estiver dentro.

```
 Cliente ──TCP/UDP/TLS──► NLB (IP fixo por AZ) ──► Target group ──► Instância / IP / ALB
                              │ flow hash (IP, porta, protocolo)
                              └─ a conexão permanece no mesmo alvo
```

## Principais características

| Característica | Detalhe |
|---|---|
| **Protocolos** | TCP, UDP, TCP_UDP, **TLS** (terminação TLS no NLB) |
| **Desempenho** | Latência baixíssima, escala quase instantânea para picos |
| **IP estático** | Um IP por subnet/AZ; **Elastic IP** opcional (internet-facing) ou IP privado escolhido (internal) |
| **Preservação do IP do cliente** | Para alvos do tipo *instance*, o IP de origem é preservado; para alvos *IP*, depende da configuração (use **Proxy Protocol v2** para repassar o IP) |
| **Roteamento** | Sem regras L7: um listener encaminha a um target group (com opções de múltiplos TGs conforme versão) |
| **Alvos** | Instâncias, IPs (inclusive on-premises), outro **ALB** |
| **Security Groups** | Suportados em NLBs criados com SG (recurso mais recente; confirme); antes, o controle ficava nos SGs dos alvos |
| **Health check** | TCP, HTTP ou HTTPS |
| **Sticky** | Por fluxo (a conexão fica no mesmo alvo); *source IP affinity* opcional |
| **Cross-zone** | **Desabilitado por padrão** (pode ser habilitado, com custo de transferência entre AZs) |

## Casos de uso

| Caso | Por quê NLB |
|---|---|
| Aplicações com **IP fixo** que parceiros liberam em firewall | IP estático/Elastic IP |
| **TCP/UDP não HTTP** (jogos, IoT/MQTT, DNS, VoIP, bancos, SMTP) | Camada 4 |
| **Volume extremo** e latência mínima | Arquitetura de alto desempenho |
| **PrivateLink** (expor serviço a outras VPCs/contas) | Endpoint service exige NLB (ou GWLB) |
| Colocar **IP estático na frente de um ALB** | NLB com alvo ALB |
| Passar o **TLS direto** à aplicação (TCP puro) | Listener TCP sem terminar TLS |

### NLB na frente de um ALB

Quando é preciso **IP fixo + roteamento L7 + WAF**:

```
 Cliente ─► NLB (EIP fixos) ─► ALB (regras L7, WAF) ─► Alvos
```

Alternativa moderna: AWS Global Accelerator, que também fornece IPs estáticos anycast para ALB/NLB (nota própria desta trilha).

---

## PrivateLink com NLB

Um provedor publica um serviço atrás de um NLB como **endpoint service**; consumidores criam um **VPC endpoint (interface)** e acessam sem peering, sem internet e sem sobrepor CIDRs.

```
 VPC consumidora                                   VPC provedora
 [App] ──► VPC Endpoint (ENI privada) ═ PrivateLink ═► NLB ──► Serviço
```

Útil para SaaS, serviços compartilhados entre contas e para evitar peering/Transit Gateway quando se quer expor **apenas um serviço**.

## Exemplo prático

```bash
# NLB internet-facing com Elastic IPs fixos, uma subnet por AZ
aws elbv2 create-load-balancer \
  --name api-nlb --type network --scheme internet-facing \
  --subnet-mappings SubnetId=subnet-0aaa111,AllocationId=eipalloc-0111 \
                    SubnetId=subnet-0bbb222,AllocationId=eipalloc-0222
# AllocationId: Elastic IP reservado antes; garante IP fixo para parceiros

# Target group TCP porta 5000 com alvos do tipo instance
aws elbv2 create-target-group \
  --name api-tcp --protocol TCP --port 5000 \
  --vpc-id vpc-0abc --target-type instance
# Habilitar Proxy Protocol v2 (se a aplicação o entender)
aws elbv2 modify-target-group-attributes --target-group-arn $TG \
  --attributes Key=proxy_protocol_v2.enabled,Value=true

# Listener TLS:443 terminando TLS no NLB e enviando TCP ao alvo
aws elbv2 create-listener --load-balancer-arn $NLB_ARN \
  --protocol TLS --port 443 --certificates CertificateArn=$CERT_ARN \
  --ssl-policy ELBSecurityPolicy-TLS13-1-2-2021-06 \
  --default-actions Type=forward,TargetGroupArn=$TG
```

Explicação: os dois Elastic IPs ficam permanentes, mesmo se o NLB for recriado com os mesmos EIPs. A aplicação que precisa do IP do cliente em alvos por IP deve ler o cabeçalho do Proxy Protocol v2.

## ALB × NLB (resumo)

| Critério | ALB | NLB |
|---|---|---|
| Camada | 7 | 4 |
| Roteamento por URL/host/header | **Sim** | Não |
| IP estático/Elastic IP | Não | **Sim** |
| UDP / TCP puro | Não | **Sim** |
| WAF | **Sim** | Não |
| Autenticação OIDC/Cognito | Sim | Não |
| PrivateLink | Via NLB | **Sim** |
| Latência | Boa | **Menor** |

## Como o NLB funciona por dentro

```
 Cliente ──TCP/UDP/TLS──► [ENI do NLB em AZ-a: IP fixo/EIP]──┐
                          [ENI do NLB em AZ-b: IP fixo/EIP]──┼──► Target group (instância | IP | ALB)
                          [ENI do NLB em AZ-c: IP fixo/EIP]──┘
 Decisão por fluxo: hash de 5-tupla (protocolo, IP/porta origem, IP/porta destino, seq TCP)
 → todos os pacotes de um fluxo vão ao mesmo alvo enquanto o fluxo existe
```

| Característica | Detalhe |
|---|---|
| Camada | 4 (TCP, UDP, TCP_UDP, TLS) |
| IP por AZ | Um IP estático por subnet/AZ; pode usar **Elastic IP** ou IP privado escolhido |
| Latência | Muito baixa; escala para milhões de requisições por segundo |
| Preservação do IP do cliente | Padrão para alvos por instância; para alvos por IP use *proxy protocol v2* quando precisar |
| Security Groups | Suportados no NLB (opcional, ao criar); sem SG, o controle fica nos alvos |
| TLS | Terminação com certificado ACM e política de segurança escolhida |
| Cross-zone | **Desligado por padrão** (cobrança de dados entre AZs quando ligado) |

> [!warning] Limites, cobrança (NLCU) e recursos como Security Groups no NLB evoluem; confirme na documentação atual.

## Escolha entre os tipos de alvo

| Tipo de alvo | Quando usar | Observação |
|---|---|---|
| **Instância** | EC2 na VPC | Preserva o IP de origem do cliente |
| **IP** | Containers (ECS awsvpc), on-premises via VPN/DX, outras VPCs | O IP de origem visto é o do NLB, salvo proxy protocol |
| **ALB** | Combinar IP fixo do NLB com recursos L7 do ALB | Padrão "NLB na frente do ALB" |

## Health checks e failover

| Item | Valor/regra |
|---|---|
| Protocolos | TCP, HTTP, HTTPS |
| Limiar | Número de sucessos/falhas consecutivos configurável |
| Alvo não saudável | Removido do roteamento de novos fluxos |
| Todos não saudáveis em uma AZ | Com cross-zone desligado, a AZ fica sem alvos; com ligado, tráfego vai a outras AZs |
| Fail-open | Se todos os alvos estão não saudáveis, o NLB roteia para todos |

## Troubleshooting

| Sintoma | Causas prováveis | Ação |
|---|---|---|
| Timeout intermitente | Hairpin: cliente e alvo na mesma instância com IP preservado | Use alvos por IP ou separe cliente e servidor |
| Alvos "unhealthy" | SG do alvo bloqueia a porta de health check / origem do NLB | Liberar a porta e a faixa da VPC do NLB |
| IP de origem errado | Alvo por IP sem proxy protocol | Habilitar proxy protocol v2 e tratar no app |
| Uma AZ recebe pouco tráfego | Cross-zone desligado e poucos alvos | Equilibrar alvos por AZ ou ligar cross-zone |
| Conexões longas caem | Idle timeout do NLB (TCP ~350 s) | Keepalive no cliente/servidor |

## Custo

- Cobrança por hora do NLB e por **NLCU** (conexões novas, conexões ativas e bytes processados, vale o maior).
- Cross-zone ligado gera transferência entre AZs.
- Para IP fixo + L7, o par NLB+ALB soma os dois custos: avalie o Global Accelerator como alternativa.

---

## Erros comuns e armadilhas

- **Esperar roteamento por caminho no NLB:** não existe; use ALB.
- **Cross-zone desabilitado** com poucos alvos desbalanceados entre AZs: carga desigual.
- **Security Group do alvo** não liberando o IP do cliente (instâncias com IP preservado) ou o CIDR do NLB (alvos IP): conexões falham.
- **Hairpin/loopback:** com IP do cliente preservado, um alvo que chama o NLB e cai nele mesmo pode falhar (conexão do próprio alvo). Evite ou use alvos IP.
- **Esquecer o Proxy Protocol v2** quando precisa do IP real em alvos por IP.
- **Health check TCP considera saudável** um serviço que aceita conexão mas responde erro: prefira HTTP/HTTPS quando possível.
- **Desligar a terminação TLS e esquecer de renovar certificado na aplicação.**
- **Subestimar o custo** do tráfego cross-zone e de NLCU.

## 🧩 Quiz de Fixação

1. Quando escolher NLB em vez de ALB?
2. Como obter IP fixo para parceiros liberarem em firewall e ainda ter roteamento por URL?
3. Qual a relação entre NLB e PrivateLink?

**Respostas:**
1) Para tráfego TCP/UDP/TLS não HTTP, latência mínima, volumes extremos, IP estático/Elastic IP ou PrivateLink. O ALB é a escolha quando há roteamento L7, WAF ou autenticação.
2) Coloque um **NLB** com Elastic IPs na frente do **ALB** (alvo do tipo ALB), ou use o AWS Global Accelerator para IPs anycast estáticos.
3) O provedor publica o serviço como **endpoint service** atrás de um NLB (ou GWLB); consumidores criam um VPC endpoint de interface, acessando o serviço de forma privada sem peering nem internet.

### Questões de aprofundamento

4. Um parceiro só libera IPs fixos no firewall. Como expor um ALB com isso?
5. Por que alvos por IP não enxergam o IP real do cliente e como contornar?
6. Quando manter cross-zone desligado no NLB?

**Respostas:**
4) Colocar um NLB com Elastic IPs na frente do ALB (alvo do tipo ALB), ou usar o Global Accelerator com IPs anycast fixos.
5) Porque a conexão chega ao alvo vinda do NLB; habilite o *proxy protocol v2* no target group e faça a aplicação ler o cabeçalho.
6) Quando há alvos equilibrados por AZ e se quer evitar a cobrança de transferência entre AZs; aceita-se a distribuição por AZ proporcional.
