### O que é Elastic Load Balancing — tipos de load balancer, componentes e como escolher

> [!warning] Aviso
> Recursos, limites, preços e comportamentos de cada tipo de load balancer evoluem (inclusive o Classic, em desuso). Confirme na documentação do ELB. Os comandos **não foram executados**.

O **Elastic Load Balancing (ELB)** distribui o tráfego de entrada entre **vários alvos** (instâncias EC2, contêineres, IPs, funções Lambda) em uma ou mais **Availability Zones**, verifica a saúde deles e envia tráfego só para os saudáveis. Ele é gerenciado, escala sozinho e é a peça que transforma "um servidor" em "um serviço altamente disponível".

**Analogia:** o load balancer é o **maître de um restaurante**. Recebe os clientes na porta (listener), decide a mesa (alvo) com base em regras, para de encaminhar gente a uma mesa quebrada (health check) e chama mais garçons quando enche (escala do próprio ELB).

```
                          ┌──────────────────────── VPC ───────────────────────┐
  Usuários ──► DNS ──►    │   LOAD BALANCER (nós em várias AZs)                │
  (Route 53 Alias)        │     Listener :443 ── regras ──► Target Group A     │
                          │                          └───► Target Group B      │
                          │   AZ-a: [EC2] [EC2]   AZ-b: [EC2] [Contêiner]     │
                          └────────────────────────────────────────────────────┘
```

## Os quatro tipos

| Tipo | Camada OSI | Protocolos | Quando é a escolha |
|---|---|---|---|
| **Application Load Balancer (ALB)** | 7 | HTTP, HTTPS, gRPC, WebSocket | Aplicações web/microsserviços, roteamento por caminho/host/header |
| **Network Load Balancer (NLB)** | 4 | TCP, UDP, TLS | Latência muito baixa, milhões de req/s, IP estático, TCP/UDP genérico, PrivateLink |
| **Gateway Load Balancer (GWLB)** | 3 | IP (túnel GENEVE) | Inserir firewalls, IDS/IPS, inspeção de pacotes de terceiros |
| **Classic Load Balancer (CLB)** | 4 e 7 | HTTP/HTTPS/TCP | **Legado**; AWS recomenda migrar |

> [!info] Atenção
> No exame e na vida real: **ALB para HTTP**, **NLB para TCP/UDP e performance extrema/IP fixo**, **GWLB para appliances**, **CLB só em legado**.

## Componentes comuns

| Componente | O que é |
|---|---|
| **Load balancer** | O recurso em si, com um nome DNS (`meu-alb-123.sa-east-1.elb.amazonaws.com`) |
| **Nós do load balancer** | Instâncias gerenciadas, uma por AZ habilitada; recebem o tráfego |
| **Listener** | Processo que escuta uma porta/protocolo (ex.: HTTPS:443) e aplica regras |
| **Regra (rule)** | Condições (caminho, host, header...) → ação (encaminhar, redirecionar, responder fixo) — ALB |
| **Target group** | Conjunto de alvos + protocolo/porta + health check |
| **Target** | Instância, IP, função Lambda ou ALB (em NLB) |
| **Health check** | Verificação periódica que decide se o alvo recebe tráfego |

Detalhes de target groups e saúde: nota de **Target groups, health checks...** deste guia (4.1.1.1).

## Esquema (internet-facing vs internal)

| Esquema | Endereço | Uso |
|---|---|---|
| **Internet-facing** | IPs públicos; resolvido na internet; vive em **subnets públicas** (com rota para o Internet Gateway) | Entrada pública de aplicações |
| **Internal** | IPs privados; vive em subnets privadas | Comunicação entre camadas/microsserviços, apps internas |

O load balancer precisa de **uma subnet por AZ** habilitada (idealmente 2 ou mais AZs). Para internet-facing, as subnets precisam ser públicas. Veja a base de rede em [[8. DevOps e Gerenciamento de Infraestrutura/CLOUD COMPUTING/AWS (AMAZON WEB SERVICE)/3. Tecnologia e Serviços/3.3 Serviços principais da AWS/3.3.4. Rede/3.3.4.1. Amazon VPC/0 Amazon VPC (Tópicos )|Amazon VPC]].

Topologia clássica de três camadas:

```
 Internet ──► ALB (público, subnets públicas) ──► EC2/ECS (subnets privadas) ──► RDS (subnets privadas)
                    SG-alb: 443 de 0.0.0.0/0          SG-app: 8080 só do SG-alb      SG-db: 5432 só do SG-app
```

## Como o tráfego chega: DNS e IPs

- O nome DNS do load balancer resolve para os **IPs dos nós** (um por AZ). Os IPs de ALB **mudam** com o tempo; nunca fixe IPs, use o nome DNS (ou **Alias** no Route 53). Veja [[8. DevOps e Gerenciamento de Infraestrutura/CLOUD COMPUTING/AWS (AMAZON WEB SERVICE)/3. Tecnologia e Serviços/3.3 Serviços principais da AWS/3.3.4. Rede/3.3.4.5. Amazon Route 53/0 Amazon Route 53 (Tópicos )|Amazon Route 53]].
- O **NLB** oferece **um IP estático por AZ** (ou Elastic IP, se internet-facing), útil quando o cliente precisa liberar IPs em firewall.
- O ELB escala **automaticamente** conforme o tráfego; picos muito súbitos e enormes podem exigir aquecimento (*pre-warming*) pelo suporte AWS no ALB.

## Segurança e integrações

| Item | ALB | NLB | GWLB |
|---|---|---|---|
| **Security Groups** | Sim | Sim (suporte mais recente; confirme) | Não |
| **Terminação TLS** | Sim | Sim (listener TLS) | Não |
| **AWS WAF** | **Sim** | Não | Não |
| **Autenticação (OIDC/Cognito)** | Sim | Não | Não |
| **IP estático / Elastic IP** | Não | **Sim** | Não |
| **PrivateLink (endpoint service)** | Não (via NLB) | **Sim** | Sim (endpoint de GWLB) |
| **Integração com Auto Scaling** | Sim | Sim | Sim |
| **Alvo Lambda** | Sim | Não | Não |

Integrações importantes: **Auto Scaling Group** (registra e remove instâncias), **ECS/EKS** (registro de tarefas/pods), **CloudFront** (ALB como origem), **Global Accelerator** (ALB/NLB como endpoint), **ACM** (certificados), **CloudWatch** (métricas e logs de acesso).

## Como escolher (árvore de decisão)

```
Precisa inspecionar pacotes com firewall/IPS de terceiros?  ──► GWLB
          │ não
Protocolo é HTTP/HTTPS/gRPC e quer rotear por URL/host/header? ──► ALB
          │ não
TCP/UDP/TLS, IP fixo, latência ultrabaixa, milhões de conexões? ──► NLB
          │ 
Já existe CLB? ──► planeje migração para ALB ou NLB
```

## Exemplo prático

```bash
# Criar um ALB internet-facing em duas subnets públicas, com um Security Group
aws elbv2 create-load-balancer \
  --name loja-alb \
  --type application \
  --scheme internet-facing \
  --subnets subnet-0aaa111 subnet-0bbb222 \
  --security-groups sg-0alb123
# --type: application | network | gateway
# O retorno traz o DNSName e o LoadBalancerArn; aponte um Alias do Route 53 para o DNSName

# Listar load balancers e ver estado (provisioning → active)
aws elbv2 describe-load-balancers \
  --query 'LoadBalancers[].{Nome:LoadBalancerName,Tipo:Type,Esquema:Scheme,Estado:State.Code,DNS:DNSName}'
```

Explicação: `elbv2` cobre ALB, NLB e GWLB (a CLI `elb` antiga é do Classic). O load balancer só funciona de verdade depois de ter **listener** e **target group** (próximas notas).

## Comparação detalhada dos tipos

| Critério | **ALB** | **NLB** | **GWLB** | **CLB** |
|---|---|---|---|---|
| Camada OSI | 7 | 4 | 3 | 4 e 7 (limitado) |
| Protocolos | HTTP, HTTPS, gRPC, WebSocket | TCP, UDP, TLS | IP (GENEVE) | TCP, SSL, HTTP |
| Roteamento | Path, host, header, query, método, IP | Porta/protocolo | Transparente | Básico |
| IP estático/EIP | Não (use NLB ou Global Accelerator na frente) | **Sim** | Não aplicável | Não |
| Preserva IP do cliente | `X-Forwarded-For` | Sim (alvos por instância) | Sim | `X-Forwarded-For` |
| Alvos | Instância, IP, Lambda | Instância, IP, ALB | Appliances | Instâncias |
| Integrações | WAF, Cognito/OIDC | PrivateLink | Firewalls de terceiros | Legado |
| Latência | Milissegundos | Muito baixa | Baixa | Média |
| Status | Atual | Atual | Atual | Legado |

> [!warning] Recursos, limites e preços mudam; confirme na documentação atual.

## Ciclo de vida de uma requisição no ALB

```
 Cliente ─► DNS (alb-xxx.sa-east-1.elb.amazonaws.com → IPs por AZ) ─► nó do ALB (AZ-a)
   └─ TLS termina no listener ─► avalia regras ─► escolhe target (algoritmo round robin / least outstanding requests)
        └─ health check ok? ─► encaminha ─► resposta volta ao cliente (X-Forwarded-For/Proto/Port adicionados)
```

## Escala e capacidade

| Tema | Detalhe |
|---|---|
| Autoescala | ELB escala sozinho; picos súbitos muito grandes podem exigir **pre-warming** via suporte |
| IPs | Mudam com a escala: sempre use o nome DNS (CNAME/alias) |
| Subnets | Mínimo de IPs livres (ex.: /27) por subnet para o crescimento |
| Multi-AZ | Habilite ao menos duas AZs com alvos em cada uma |

## Exemplo de CLI (comentado, não executado)

```bash
aws elbv2 create-load-balancer --name alb-web --type application --scheme internet-facing \
  --subnets subnet-aaa subnet-bbb --security-groups sg-123
aws elbv2 create-target-group --name tg-web --protocol HTTP --port 80 --vpc-id vpc-123 \
  --health-check-path /health --target-type instance
aws elbv2 create-listener --load-balancer-arn <ARN> --protocol HTTPS --port 443 \
  --certificates CertificateArn=<ARN-ACM> --default-actions Type=forward,TargetGroupArn=<ARN-TG>
```

## Quando combinar tipos

| Necessidade | Combinação |
|---|---|
| IP fixo + regras L7 | NLB → ALB |
| Cache e borda global | CloudFront → ALB |
| Inspeção de rede + web | GWLB (segurança) + ALB (aplicação) |
| Multi-região com failover | Route 53 ou Global Accelerator → ALBs |

## Custo

Cada load balancer cobra por hora e por capacidade consumida (LCU/NLCU/GLCU). Consolidar várias aplicações em um ALB (roteamento por host/path) reduz o custo fixo.

---

## Erros comuns e armadilhas

- **Fixar o IP de um ALB** em firewall ou DNS: os IPs mudam; use o nome DNS ou um NLB com IP estático.
- **Subnets privadas em ALB internet-facing:** sem rota ao Internet Gateway ele não é alcançado.
- **Habilitar uma só AZ:** perde a alta disponibilidade.
- **Security Group da aplicação aberto à internet:** deve aceitar apenas o SG do load balancer.
- **Usar ALB onde TCP puro/IP fixo é necessário** (ou NLB onde precisa de roteamento por URL).
- **Manter o CLB em projeto novo:** recursos limitados e legado.
- **Esquecer o custo:** há cobrança por hora e por unidade de capacidade (LCU/NLCU); load balancers ociosos custam.
- **Misturar `elb` e `elbv2` na CLI.**

## 🧩 Quiz de Fixação

1. Que tipo de load balancer usar para rotear `/api/*` e `/img/*` para serviços diferentes? E para ter IP estático e UDP?
2. Por que não se deve fixar o IP de um ALB?
3. O que é um target group e qual o papel do health check?

**Respostas:**
1) **ALB**, com regras por caminho para target groups distintos. Para IP estático e UDP, o **NLB**.
2) Porque o ALB tem nós gerenciados que escalam e são trocados; seus IPs mudam. Use o nome DNS (Alias no Route 53) ou, se precisar de IP fixo, um NLB.
3) Target group é o conjunto de alvos (instâncias, IPs, Lambda) com porta, protocolo e verificação de saúde. O health check testa periodicamente cada alvo; só os considerados saudáveis recebem tráfego.

### Questões de aprofundamento

4. Por que nunca se deve usar o IP de um load balancer em configurações?
5. Como reduzir o custo fixo de dez aplicações pequenas?
6. Como oferecer IP fixo para uma aplicação web com roteamento por path?

**Respostas:**
4) Os IPs mudam conforme o balanceador escala; use sempre o nome DNS.
5) Consolidar em um ALB com regras por host/path e target groups por aplicação.
6) NLB com Elastic IPs encaminhando ao ALB (alvo do tipo ALB), ou Global Accelerator com IPs fixos.
