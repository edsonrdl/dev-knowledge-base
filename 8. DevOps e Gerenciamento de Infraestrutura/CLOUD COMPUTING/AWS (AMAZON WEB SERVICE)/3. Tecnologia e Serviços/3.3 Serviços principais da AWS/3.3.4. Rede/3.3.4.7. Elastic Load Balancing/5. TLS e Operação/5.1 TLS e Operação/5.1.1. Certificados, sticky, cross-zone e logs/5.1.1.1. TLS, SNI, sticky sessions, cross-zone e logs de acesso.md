## TLS no load balancer

### Terminação, passagem e re-criptografia

| Modelo | Como | Quando |
|---|---|---|
| **Terminação TLS** (comum) | O LB descriptografa; tráfego ao alvo em HTTP | Simplicidade, permite regras L7, desonera a aplicação |
| **Re-criptografia** | LB descriptografa, aplica regras e **recriptografa** (HTTPS) até o alvo | Exigências de criptografia ponta a ponta |
| **Passagem (passthrough)** | NLB com listener TCP, sem terminar TLS | A aplicação precisa ver o TLS original (mTLS próprio) |

```
 Cliente ──TLS──► ALB (termina, WAF, regras) ──HTTP──► alvo          (terminação)
 Cliente ──TLS──► ALB (termina) ──TLS──► alvo (https)                (re-criptografia)
 Cliente ──TLS────────── NLB (TCP) ─────────────────► alvo (termina) (passthrough)
```

### Certificados e ACM

- Use **AWS Certificate Manager (ACM)**: emissão e **renovação automática** de certificados públicos, integrados ao ELB, sem chave privada exposta.
- O certificado precisa estar **na mesma região** do load balancer (diferente do CloudFront, que exige us-east-1).
- Também é possível **importar** certificados de terceiros (renovação manual).
- Para o listener HTTPS você escolhe uma **security policy** (versão mínima de TLS e cifras). Prefira políticas recentes (TLS 1.2 e 1.3); evite TLS 1.0/1.1.

### SNI — vários domínios, um listener

Com **SNI** (Server Name Indication), o cliente informa o hostname no handshake e o ALB escolhe o **certificado correto** entre os associados ao listener. Assim um único ALB atende `loja.com`, `blog.com` e `api.com` com certificados distintos.

```
 Listener HTTPS:443
   cert padrão:  *.exemplo.com.br
   certs extras: blog.outro.com, api.parceiro.com   (SNI escolhe pelo nome pedido)
```

```bash
# Adicionar um certificado extra (SNI) ao listener HTTPS
aws elbv2 add-listener-certificates \
  --listener-arn $LISTENER_443 \
  --certificates CertificateArn=arn:aws:acm:sa-east-1:111122223333:certificate/abc-123
```

### Mutual TLS (mTLS) e headers

Em ALB é possível exigir **certificado de cliente** (modo *verify* ou *passthrough*). O ALB repassa informações do cliente em headers próprios; consulte a documentação para o formato. Em todos os casos, a aplicação lê `X-Forwarded-Proto` para saber se o cliente usou HTTPS.

## Sticky sessions (afinidade de sessão)

Por padrão cada requisição pode ir a um alvo diferente. **Sticky sessions** fazem o mesmo cliente voltar ao mesmo alvo por um período.

| Tipo (ALB) | Como | Observação |
|---|---|---|
| **Duration-based cookie** (`AWSALB`) | Cookie gerado pelo ALB, duração configurável (1 s a 7 dias) | Simples |
| **Application-based cookie** | Cookie gerado pela aplicação, o ALB o usa como chave | Para quem já controla a sessão |

Pontos de atenção:

- Habilita-se **no target group**, não no listener.
- Desequilibra a carga e prejudica o escalonamento: alvos antigos retêm sessões; alvos novos recebem pouco tráfego.
- Se o alvo sai (unhealthy, scale-in), a sessão é perdida e o cliente é redirecionado a outro.
- **Melhor solução:** aplicação **stateless**, com sessão em **ElastiCache/DynamoDB**, e sticky desligado.
- No NLB, a afinidade é por fluxo (conexão) ou por **IP de origem** (opção), sem cookies.

## Cross-zone load balancing

Define se cada nó do load balancer distribui tráfego para **todos os alvos de todas as AZs** ou **apenas para os da própria AZ**.

```
 SEM cross-zone (2 AZs, cada nó recebe 50% do tráfego):
   AZ-a: 2 alvos  → cada um recebe 25%
   AZ-b: 8 alvos  → cada um recebe 6,25%   ← desbalanceado

 COM cross-zone:
   10 alvos no total → cada um recebe 10%
```

| Tipo | Padrão | Custo da transferência entre AZs |
|---|---|---|
| **ALB** | **Habilitado** (pode ser desabilitado por target group) | Sem cobrança adicional pela distribuição entre AZs |
| **NLB** | **Desabilitado** | Cobrança de transferência entre AZs quando habilitado |
| **GWLB** | Desabilitado | Idem |
| **CLB** | Habilitado ao criar pelo console; varia | Sem cobrança extra |

Regra prática: mantenha **alvos distribuídos igualmente** entre as AZs; com isso o cross-zone pouco importa. Em NLB com alvos desiguais, habilite e aceite o custo, ou balanceie a quantidade de alvos.

## Timeouts e outros atributos úteis

| Atributo | Padrão | Observação |
|---|---|---|
| `idle_timeout.timeout_seconds` (ALB) | 60 s | Aumente para requisições longas; mantenha keep-alive do alvo maior |
| `deletion_protection.enabled` | desligado | Ligue em produção |
| `routing.http.drop_invalid_header_fields.enabled` | desligado | Protege contra headers inválidos |
| `routing.http.desync_mitigation_mode` | defensivo | Mitigação de HTTP desync |
| `access_logs.s3.enabled` | desligado | Logs de acesso no S3 |
| NLB: timeout de ociosidade TCP | 350 s | Use keep-alive no cliente/alvo |

## Observabilidade

### Métricas (CloudWatch, namespace `AWS/ApplicationELB`, `AWS/NetworkELB`)

| Métrica | Uso |
|---|---|
| `RequestCount`, `ActiveConnectionCount` | Volume |
| `TargetResponseTime` | Latência da aplicação |
| `HTTPCode_ELB_5XX_Count` | Erros gerados pelo próprio ALB (502/503/504) |
| `HTTPCode_Target_5XX_Count` | Erros devolvidos pelos alvos |
| `HealthyHostCount` / `UnHealthyHostCount` | Saúde dos alvos |
| `RejectedConnectionCount`, `TargetConnectionErrorCount` | Limites e falhas de conexão |

Alarmes úteis: `UnHealthyHostCount > 0`, `HTTPCode_Target_5XX_Count` acima do normal, `TargetResponseTime` p95 alto.

### Logs de acesso (ALB)

Habilite e envie para um **bucket S3** (com política que permite a conta do ELB da região escrever). Cada linha traz tipo, horário, IP do cliente, alvo, tempos, código, bytes, URL, `user_agent`, certificado, etc. Analise com **Athena**.

```bash
# Habilitar logs de acesso em um bucket S3
aws elbv2 modify-load-balancer-attributes --load-balancer-arn $ALB_ARN \
  --attributes Key=access_logs.s3.enabled,Value=true \
               Key=access_logs.s3.bucket,Value=meus-logs-alb \
               Key=access_logs.s3.prefix,Value=prod
# O bucket precisa de bucket policy permitindo o ELB da região escrever; consulte a documentação

# Proteger contra exclusão acidental
aws elbv2 modify-load-balancer-attributes --load-balancer-arn $ALB_ARN \
  --attributes Key=deletion_protection.enabled,Value=true
```

Logs de **conexão** (TLS) e logs de requisições com AWS WAF complementam o diagnóstico. Para tráfego global, combine com os logs do CloudFront ([[8. ## Exemplo prático

Cenário: ALB com dois domínios, HTTPS moderno, sessão sem sticky e logs para auditoria.

1. Certificados do ACM (região do ALB) para `loja.exemplo.com.br` (padrão) e `blog.exemplo.com.br` (SNI).
2. Listener HTTP:80 → redirect 301 para HTTPS; listener HTTPS:443 com política TLS 1.2/1.3.
3. Sessões do usuário em **ElastiCache**; sticky desligado; ALB com `least_outstanding_requests`.
4. Cross-zone habilitado (padrão) e alvos distribuídos entre as AZs.
5. `access_logs` no S3 com ciclo de vida de 90 dias; alarmes em `UnHealthyHostCount` e `HTTPCode_ELB_5XX_Count`; `deletion_protection` ligado.

## Configuração recomendada por cenário

| Cenário | TLS | Sticky | Cross-zone | Observação |
|---|---|---|---|---|
| API stateless pública | TLS 1.2+ (política moderna), redirect 80→443 | Não | Ligado (ALB: sempre) | Usar WAF |
| App legada com sessão em memória | TLS | Sim (app cookie/duração) | Ligado | Migrar sessão para Redis/DynamoDB |
| TCP/gRPC de alta performance (NLB) | TLS listener opcional | Por IP de origem | Desligado por padrão | Ativar se alvos desiguais por AZ |
| Múltiplos domínios no mesmo LB | Certificados múltiplos + SNI | — | — | ACM por domínio |

> [!warning] Valores, limites e preços mudam; os exemplos deste material não foram executados. Políticas de segurança TLS e comportamentos padrão variam por tipo de balanceador.

```
 Cross-zone desligado (NLB)              Cross-zone ligado
 AZ-a: 2 alvos  AZ-b: 8 alvos            qualquer nó → todos os 10 alvos
 cada AZ recebe 50% do tráfego           cada alvo recebe ~10%
 → alvos da AZ-a: 25% cada (sobrecarga)  → distribuição uniforme
```

### Árvore de decisão

```
Sessão fica em memória do servidor?
├─ Sim ─► corrigir (sessão externa); enquanto isso, sticky
└─ Não ─► sem sticky (melhor balanceamento e deploys)

Desequilíbrio de alvos entre AZs?
├─ Sim ─► cross-zone ligado
└─ Não ─► pode desligar (NLB) para evitar tráfego entre AZs
```

## Logs de acesso: o que investigar

Campos chave: `elb_status_code` vs `target_status_code` (quem falhou, o LB ou o alvo), `request_processing_time`, `target_processing_time` (lentidão da app) e `ssl_protocol` (clientes legados). Entrega no S3, consultável com Athena.

## CLI comentado

```bash
# Habilita logs de acesso no S3
aws elbv2 modify-load-balancer-attributes --load-balancer-arn <LB_ARN> \
  --attributes Key=access_logs.s3.enabled,Value=true \
               Key=access_logs.s3.bucket,Value=meu-bucket-logs

# Liga stickiness no target group (cookie gerado pelo LB, 1 hora)
aws elbv2 modify-target-group-attributes --target-group-arn <TG_ARN> \
  --attributes Key=stickiness.enabled,Value=true \
               Key=stickiness.type,Value=lb_cookie \
               Key=stickiness.lb_cookie.duration_seconds,Value=3600

# Política TLS do listener
aws elbv2 modify-listener --listener-arn <LISTENER_ARN> \
  --ssl-policy ELBSecurityPolicy-TLS13-1-2-2021-06
```

## Troubleshooting

| Sintoma | Causa provável | Ação |
|---|---|---|
| Alerta de certificado | Domínio não coberto pelo certificado | Adicionar certificado/SNI |
| Alvos desiguais com sticky | Clientes grandes (NAT) fixados | Rever necessidade de sticky |
| 504 em requisições longas | Idle timeout curto | Aumentar timeout e ajustar app |
| Logs não aparecem | Bucket sem policy para o LB | Aplicar policy do bucket |

## Custo

Cross-zone em NLB gera cobrança de transferência entre AZs; no ALB não há cobrança adicional por esse tráfego. Logs de acesso custam armazenamento no S3 e consultas no Athena; use lifecycle para expirar logs antigos.

## Erros comuns e armadilhas

- **Certificado ACM em região diferente** do load balancer: não aparece para seleção.
- **Política TLS antiga** aceitando TLS 1.0/1.1.
- **Falta do redirect HTTP → HTTPS.**
- **Apoiar-se em sticky sessions** para guardar estado: sessões perdidas em deploys e scale-in.
- **Cross-zone desabilitado em NLB com alvos desbalanceados:** AZ sobrecarregada.
- **Não habilitar logs** antes do incidente: sem histórico.
- **Bucket de logs sem a policy correta:** o ALB não consegue gravar e falha silenciosamente.
- **Deletion protection desligada** em produção.
- **Idle timeout do ALB maior que o keep-alive do alvo:** 502 intermitente.
- **Esquecer de renovar certificados importados** (ACM só renova os emitidos por ele).

## 🧩 Quiz de Fixação

1. Como um único ALB atende vários domínios HTTPS com certificados diferentes?
2. Por que evitar sticky sessions e qual alternativa usar?
3. Qual a diferença de padrão do cross-zone entre ALB e NLB, e o efeito no custo?

**Respostas:**
1) Usando **SNI**: associam-se vários certificados ao listener HTTPS; o ALB escolhe o certificado conforme o hostname enviado no handshake TLS.
2) Porque desequilibra a carga, atrapalha o escalonamento e perde a sessão quando o alvo sai. Prefira aplicação **stateless** com sessão em ElastiCache ou DynamoDB.
3) No **ALB** o cross-zone vem **habilitado** e sem cobrança extra entre AZs; no **NLB** vem **desabilitado** e, se habilitado, há cobrança de transferência entre AZs.

**Questões complementares:**

4. Que problema o cross-zone resolve quando há quantidades diferentes de alvos por AZ?
5. Como distinguir erro do balanceador de erro do alvo nos logs?
6. Quando evitar sticky sessions?

**Respostas das questões complementares:**
4) Evita que alvos de uma AZ com poucos alvos recebam carga desproporcional, distribuindo uniformemente entre todos os alvos.
5) Comparando `elb_status_code` com `target_status_code`: se o alvo retornou o erro, o campo do alvo mostra; se o LB gerou, o do alvo fica vazio.
6) Quando a aplicação é stateless: sticky prejudica o balanceamento e dificulta deploys e escalabilidade.
