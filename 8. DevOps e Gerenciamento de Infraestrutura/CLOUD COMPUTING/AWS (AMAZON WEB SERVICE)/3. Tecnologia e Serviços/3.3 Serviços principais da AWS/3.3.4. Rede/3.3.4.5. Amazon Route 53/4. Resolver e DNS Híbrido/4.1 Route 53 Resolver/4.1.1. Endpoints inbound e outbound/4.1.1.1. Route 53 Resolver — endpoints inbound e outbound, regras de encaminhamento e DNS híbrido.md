### Route 53 Resolver — endpoints inbound e outbound, regras de encaminhamento e DNS híbrido

> [!warning] Aviso
> Preços (ENI por hora e consultas), limites por ENI e recursos como DNS Firewall e Route 53 Profiles mudam. Confira a documentação oficial do Route 53 Resolver. Os exemplos **não foram executados**.

Até aqui o Route 53 foi tratado como DNS **autoritativo** (quem guarda os registros). O **Route 53 Resolver** é o outro lado: o **resolvedor recursivo** que as instâncias dentro de uma VPC usam para resolver nomes. Em ambientes híbridos (VPC + data center), surge o problema: como o servidor on-premises resolve `db.interno.aws.exemplo` (zona privada) e como uma instância na VPC resolve `erp.corp.exemplo` (DNS do data center)? Os **Resolver Endpoints** e as **regras de encaminhamento** resolvem isso. Base: [[8. DevOps e Gerenciamento de Infraestrutura/CLOUD COMPUTING/AWS (AMAZON WEB SERVICE)/3. Tecnologia e Serviços/3.3 Serviços principais da AWS/3.3.4. Rede/3.3.4.5. Amazon Route 53/1. Fundamentos e Zonas DNS/1.2 Hosted Zones e Registros/1.2.1. Tipos de registro e Alias/1.2.1.1. Hosted Zones públicas e privadas — tipos de registro, delegação de NS e split-horizon DNS|Hosted Zones públicas e privadas]].

## O resolvedor padrão da VPC

Toda VPC já vem com um resolvedor DNS, sem custo adicional e sem configurar nada, acessível em:

- o endereço **base da VPC + 2** (ex.: `10.0.0.2` para a VPC `10.0.0.0/16`); e
- o endereço link-local **`169.254.169.253`**.

Ele resolve:

1. Nomes DNS internos de instâncias EC2 (`ip-10-0-1-25.ec2.internal`).
2. **Zonas privadas** do Route 53 associadas à VPC.
3. Endpoints de VPC (PrivateLink).
4. Nomes públicos da internet (consultando a hierarquia DNS pública).

Exige `enableDnsSupport = true` na VPC (e `enableDnsHostnames` para nomes de host). O resolvedor padrão **só é acessível de dentro da VPC**: o data center não consegue consultar `10.0.0.2` por VPN. Daí os endpoints.

## Resolver Endpoints

Um **Resolver Endpoint** é um conjunto de **ENIs** (interfaces de rede) que você cria na VPC, em **pelo menos 2 subnets de AZs diferentes** (alta disponibilidade), e que servem de ponte entre o DNS da VPC e o DNS externo. Existem dois tipos:

| Tipo | Direção | Quem consulta quem | Uso |
|---|---|---|---|
| **Inbound** | rede externa → VPC | O DNS on-premises encaminha consultas para IPs das ENIs do endpoint | On-premises resolve nomes de zonas privadas da AWS |
| **Outbound** | VPC → rede externa | O Resolver da VPC encaminha, via ENIs, consultas de certos domínios para o DNS externo | Instâncias na VPC resolvem nomes do data center |

```
   DATA CENTER (on-premises)                        VPC AWS
  ┌──────────────────────┐                  ┌─────────────────────────────┐
  │ DNS corporativo      │  inbound         │ Resolver Endpoint INBOUND   │
  │ (encaminha *.aws.ex  │ ───────────────► │ (ENIs 10.0.1.10 / 10.0.2.10)│
  │  para as ENIs)       │   VPN / DX       │          │                  │
  │                      │                  │          ▼                  │
  │                      │                  │ Resolver da VPC ► Zonas     │
  │                      │                  │          ▲         privadas │
  │                      │   outbound       │          │                  │
  │ erp.corp.exemplo     │ ◄─────────────── │ Resolver Endpoint OUTBOUND  │
  │ 192.168.10.53        │                  │ (regra: corp.exemplo →      │
  └──────────────────────┘                  │  192.168.10.53)             │
                                            └─────────────────────────────┘
```

Requisitos de rede:

- **Conectividade privada** entre a VPC e o data center (Site-to-Site VPN ou Direct Connect), pois as consultas usam IPs privados.
- **Security Groups** do endpoint liberando **porta 53 TCP e UDP**: no inbound, a origem é o CIDR do DNS on-premises; no outbound, o destino é o IP do DNS externo (e o retorno).
- Regras de firewall/rotas no lado on-premises para chegar nas ENIs (inbound) ou nos servidores DNS (outbound).
- Cada ENI tem IP próprio (automático ou escolhido); o DNS on-premises é configurado com **esses IPs**.

## Regras de encaminhamento (Resolver Rules)

No outbound, o que define **quais domínios** vão ao DNS externo são as **regras**:

| Tipo de regra | Comportamento |
|---|---|
| **Forward** | Encaminha consultas de um domínio (`corp.exemplo`) para IPs de DNS que você informa (via endpoint outbound) |
| **System** | Faz o Resolver resolver normalmente um subdomínio, mesmo que exista uma regra Forward mais abrangente (exceção) |
| **Recursive** | Regras automáticas padrão do Resolver (nomes públicos, zonas privadas, internos) |

A regra **mais específica** vence (como o longest prefix match em rotas): com `corp.exemplo → DNS on-premises` e `aws.corp.exemplo → System`, o subdomínio `aws.corp.exemplo` volta a ser resolvido na AWS.

As regras são **associadas a VPCs**. Em organizações com muitas contas, centraliza-se o endpoint e as regras em uma conta de rede e **compartilha-se as regras via AWS RAM (Resource Access Manager)**, para que todas as VPCs usem o mesmo caminho para o data center, sem criar endpoints em cada conta (o endpoint é cobrado por ENI/hora).

```
  Conta de rede (hub)                       Contas de workload (spokes)
  ┌───────────────────────┐   RAM share     ┌──────────────────────┐
  │ Outbound Endpoint     │ ──────────────► │ VPC A  (regra assoc.)│
  │ Regra: corp.exemplo   │                 │ VPC B  (regra assoc.)│
  │        → 192.168.10.53│                 └──────────────────────┘
  └───────────────────────┘
```

## Exemplo prático

```bash
# 1) Endpoint INBOUND (on-premises -> VPC), 2 ENIs em 2 AZs
aws route53resolver create-resolver-endpoint \
  --name "inbound-corp" \
  --creator-request-id "inb-2026-01" \
  --direction INBOUND \
  --security-group-ids sg-0dns123 \
  --ip-addresses SubnetId=subnet-0aaa,Ip=10.0.1.10 SubnetId=subnet-0bbb,Ip=10.0.2.10
# --direction INBOUND: recebe consultas de fora
# --ip-addresses: no mínimo 2 subnets (AZs distintas) para alta disponibilidade

# 2) Endpoint OUTBOUND (VPC -> on-premises)
aws route53resolver create-resolver-endpoint \
  --name "outbound-corp" --creator-request-id "out-2026-01" \
  --direction OUTBOUND --security-group-ids sg-0dns123 \
  --ip-addresses SubnetId=subnet-0aaa SubnetId=subnet-0bbb

# 3) Regra Forward: corp.exemplo vai para o DNS do data center
RULE=$(aws route53resolver create-resolver-rule \
  --creator-request-id "rule-2026-01" \
  --name "forward-corp" --rule-type FORWARD \
  --domain-name corp.exemplo \
  --resolver-endpoint-id rslvr-out-0abc \
  --target-ips Ip=192.168.10.53,Port=53 Ip=192.168.11.53,Port=53 \
  --query 'ResolverRule.Id' --output text)

# 4) Associar a regra a uma VPC
aws route53resolver associate-resolver-rule \
  --resolver-rule-id $RULE --vpc-id vpc-0abc123 --name "assoc-prod"
```

E, no DNS on-premises (exemplo conceitual com BIND), um encaminhamento condicional:

```
zone "interno.aws.exemplo" {
    type forward;
    forward only;
    forwarders { 10.0.1.10; 10.0.2.10; };   // IPs das ENIs do endpoint inbound
};
```

Explicação: o passo 3 diz "consultas de `corp.exemplo` saem pelo endpoint outbound para dois DNS on-premises (redundância)"; o passo 4 liga essa regra a uma VPC; no data center, o encaminhador condicional manda `interno.aws.exemplo` para as duas ENIs do inbound.

## Recursos relacionados

- **Resolver DNS Firewall:** filtra consultas DNS originadas na VPC por **listas de domínios** (inclusive listas gerenciadas da AWS com domínios maliciosos) com ações ALLOW, BLOCK ou ALERT. Ajuda contra exfiltração de dados via DNS e malware. Veja [[8. DevOps e Gerenciamento de Infraestrutura/CLOUD COMPUTING/AWS (AMAZON WEB SERVICE)/2. Segurança e Conformidade/2.3 Capacidades de gerenciamento de acesso da AWS/2.3.2. Serviços de segurança/2.3.2.4. Amazon GuardDuty|GuardDuty]] (que também analisa logs DNS).
- **Query logging:** registra as consultas DNS da VPC (nome, tipo, resposta, instância de origem) em CloudWatch Logs, S3 ou Kinesis Data Firehose. Fundamental para auditoria e investigação.
- **Route 53 Profiles:** agrupa configurações de DNS (zonas privadas, regras, firewall) e as aplica a muitas VPCs/contas, simplificando a gestão em escala (verifique disponibilidade na documentação).
- **Validação DNSSEC no Resolver:** é possível habilitar a validação para respostas recursivas na VPC.

## Custos e limites (visão geral)

- Cada **ENI** de um endpoint é cobrada **por hora**; um endpoint com 2 ENIs custa 2 vezes. Somam-se as **consultas processadas** pelos endpoints.
- Cada ENI tem limite de consultas por segundo (conferir quota atual). Em cargas DNS intensas, adicione ENIs/IPs.
- O resolvedor padrão da VPC tem limite de pacotes por segundo **por interface de rede**, fonte clássica de `SERVFAIL`/timeouts em clusters com muito tráfego DNS (por exemplo, Kubernetes sem cache local). Use cache (NodeLocal DNSCache em EKS) e reduza consultas desnecessárias.

## Padrões de arquitetura de DNS híbrido

```
 Hub-and-spoke centralizado (recomendado)

 on-premises DNS ──► [inbound endpoint]  ┐
                                          │  VPC de rede (hub)
 VPCs spoke ──(regras compartilhadas via RAM)──► [outbound endpoint] ──► DNS on-prem
                                          │  (corp.exemplo.com.)
                     Private Hosted Zones associadas aos spokes
```

| Necessidade | Componente | Direção |
|---|---|---|
| On-prem resolve nomes AWS (`app.internal.aws`) | Inbound endpoint | on-prem → AWS |
| AWS resolve nomes corporativos (`corp.local`) | Outbound endpoint + Rule FORWARD | AWS → on-prem |
| Compartilhar regras entre contas | AWS RAM | — |
| Filtrar domínios maliciosos | DNS Firewall | AWS (saída) |

> [!warning] Valores, limites e preços mudam; os exemplos deste material não foram executados. Limites de consultas por ENI e número de regras mudam; consulte a documentação.

### Árvore de decisão

```
Preciso resolver nomes entre AWS e on-premises?
├─ Só AWS → on-prem ─► outbound endpoint + regra FORWARD
├─ Só on-prem → AWS ─► inbound endpoint (IPs nas subnets)
├─ Ambos ─► os dois, em VPC central, regras compartilhadas via RAM
└─ Só nomes internos AWS entre VPCs ─► Private Hosted Zone associada, sem endpoints
```

```bash
# Cria endpoint de saída (IPs em ao menos 2 subnets/AZs)

aws route53resolver associate-resolver-rule --resolver-rule-id rslvr-rr-0123 --vpc-id vpc-0123
```

## Troubleshooting

| Sintoma | Causa provável | Ação |
|---|---|---|
| On-prem não resolve nomes AWS | Firewall bloqueia UDP/TCP 53 ao inbound | Liberar 53 nos SGs e na rede |
| Nome corporativo falha na VPC | Regra não associada à VPC | Associar a regra |
| Loop de resolução | Regras apontando uma para a outra | Revisar encaminhamentos |
| Lentidão | Endpoint com poucas ENIs/AZs | Adicionar IPs/AZs |

## Custo

Cobra-se por ENI de endpoint por hora (mínimo de 2 por endpoint) e por milhão de consultas que passam pelo endpoint. Centralizar endpoints num hub reduz o número de ENIs em relação a um par por VPC.

## Erros comuns e armadilhas

- **Endpoint com apenas 1 ENI:** sem alta disponibilidade (a API exige no mínimo 2).
- **Security Group sem UDP e TCP 53:** consultas grandes (TCP) falham de forma intermitente.
- **Esquecer de associar a regra à VPC:** a regra existe, mas nada é encaminhado.
- **Rotas/ACLs impedindo o caminho VPN/DX:** consulta sai, resposta não volta.
- **Loop de encaminhamento:** DNS on-premises encaminha `aws.exemplo` para a AWS e a AWS encaminha de volta o mesmo domínio ao on-premises; use regras System e domínios bem delimitados.
- **Um endpoint por conta sem necessidade:** multiplica o custo; compartilhe regras via RAM.
- **Esperar que o resolvedor da VPC seja acessível por VPN:** só via endpoint inbound.

## 🧩 Quiz de Fixação

1. Um servidor no data center precisa resolver um nome de uma zona privada do Route 53. Que componente você cria e onde o DNS on-premises é configurado?
2. Instâncias na VPC precisam resolver `erp.corp.exemplo`, gerenciado pelo DNS corporativo. Quais recursos são necessários?
3. Por que centralizar endpoints e compartilhar regras via RAM em uma organização multi-conta?

**Respostas:**
1) Um **Resolver Endpoint inbound** (com ENIs em ao menos duas AZs), e o DNS on-premises recebe um **encaminhador condicional** para o domínio da zona privada apontando para os IPs dessas ENIs, sobre VPN ou Direct Connect, com SG liberando 53 TCP/UDP.
2) Um **endpoint outbound**, uma **regra Forward** para `corp.exemplo` com os IPs do DNS corporativo como destino e a **associação** da regra às VPCs, além de conectividade privada (VPN/DX) e SG liberando 53.
3) Cada endpoint é cobrado por ENI/hora e exige operação; centralizando em uma conta de rede e compartilhando as regras via **AWS RAM**, todas as VPCs usam o mesmo caminho, com menos custo e configuração consistente.

**Questões complementares:**

4. Qual endpoint permite que servidores on-premises resolvam nomes de uma Private Hosted Zone?
5. Por que centralizar endpoints em uma VPC hub?
6. Que ação resolve "nome corporativo não resolve dentro da VPC" quando a regra existe?

**Respostas das questões complementares:**
4) O inbound endpoint, para o qual o DNS on-premises encaminha consultas.
5) Reduz o número de ENIs (custo) e simplifica a gestão; as regras são compartilhadas com os spokes via RAM.
6) Associar a Resolver Rule à VPC, pois a regra só vale nas VPCs associadas.
