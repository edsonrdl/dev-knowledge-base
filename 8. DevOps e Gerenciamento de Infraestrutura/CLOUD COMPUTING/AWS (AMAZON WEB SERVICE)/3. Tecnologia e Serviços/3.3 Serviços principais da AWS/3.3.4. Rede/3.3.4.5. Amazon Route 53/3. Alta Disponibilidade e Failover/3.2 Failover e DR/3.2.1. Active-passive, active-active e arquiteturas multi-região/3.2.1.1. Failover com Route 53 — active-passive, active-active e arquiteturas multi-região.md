### Failover com Route 53 — active-passive, active-active e arquiteturas multi-região

> [!warning] Aviso

## Failover routing policy (active-passive)

Você cria **dois registros** com o mesmo nome: um **PRIMARY** e um **SECONDARY**. O Route 53 responde com o primário enquanto ele estiver saudável; se o health check do primário falhar, passa a responder com o secundário. Quando o primário se recupera, o tráfego volta.

```
                      ┌──────────────────┐
  usuários ─► DNS ──► │ Route 53         │
                      │ app.exemplo.com  │
                      └───────┬──────────┘
         HC primário OK?      │
            sim ──────────────┼────────────► PRIMARY   (região A: ALB + app + BD)
            não ──────────────┴────────────► SECONDARY (região B: standby ou página estática)
```

Características:

- O primário **deve** ter health check (ou Alias com `EvaluateTargetHealth`). O secundário pode ter ou não; se tiver e também estiver doente, o Route 53 devolve ambos (sem outra opção).
- O secundário pode ser: outra região completa, uma versão reduzida da aplicação ("pilot light") ou apenas uma **página de manutenção estática** em S3 ("sorry page").
- Só há um destino ativo por vez: capacidade ociosa no secundário (custo menor, recuperação mais lenta).

### Exemplo

```json
{
  "Comment": "Failover primario/secundario",
  "Changes": [
    {
      "Action": "UPSERT",
      "ResourceRecordSet": {
        "Name": "app.exemplo.com.br",
        "Type": "A",
        "SetIdentifier": "primario-sp",
        "Failover": "PRIMARY",
        "HealthCheckId": "11111111-aaaa-bbbb-cccc-222222222222",
        "AliasTarget": {
          "HostedZoneId": "Z0SAOPAULOALB",
          "DNSName": "alb-sp-111.sa-east-1.elb.amazonaws.com",
          "EvaluateTargetHealth": true
        }
      }
    },
    {
      "Action": "UPSERT",
      "ResourceRecordSet": {
        "Name": "app.exemplo.com.br",
        "Type": "A",
        "SetIdentifier": "secundario-va",
        "Failover": "SECONDARY",
        "AliasTarget": {
          "HostedZoneId": "Z0VIRGINIAALB",
          "DNSName": "alb-va-222.us-east-1.elb.amazonaws.com",
          "EvaluateTargetHealth": true
        }
      }
    }
  ]
}
```

`Failover: PRIMARY/SECONDARY` ativa a política; `HealthCheckId` é o health check do primário; os `HostedZoneId` são marcadores (use o `CanonicalHostedZoneId` real de cada ALB).

## Active-active

Todos os ambientes recebem tráfego simultaneamente. Usa-se uma política de distribuição (**Latency**, **Weighted**, **Geolocation** ou **Geoproximity**) com **health checks** em todos os registros. Se um ambiente cai, o Route 53 simplesmente o retira da resposta e os outros absorvem o tráfego.

```
          ┌───────────────┐
          │   Route 53    │  Latency + health checks
          └──┬─────────┬──┘
   (saudável)│         │(saudável)
       ┌─────▼───┐ ┌───▼─────┐
       │ Região A│ │ Região B│   ambas servem usuários o tempo todo
       └─────────┘ └─────────┘   se A cair, B recebe 100%
```

Vantagens: sem ambiente ocioso, melhor desempenho, failover natural. Exigências: **dados replicados** nas duas regiões (Aurora Global Database, DynamoDB Global Tables, S3 CRR), capacidade de cada região para absorver 100% da carga e tratamento de conflitos de escrita.

## Quanto tempo leva o failover?

```
Tempo total ≈ detecção (intervalo × threshold) + propagação + TTL do DNS

Exemplo A (padrão):  30 s × 3 = 90 s   +  TTL 60 s  ≈ 150 s (≈ 2,5 min)
Exemplo B (agressivo): 10 s × 3 = 30 s +  TTL 30 s  ≈  60 s
Alias para ELB com EvaluateTargetHealth: detecção é mais rápida (a saúde
do ELB já está medida) e o TTL do Alias é o do alvo (curto).
```

- Clientes que **cacheiam DNS** além do TTL (JVM com cache infinito, aplicações antigas, conexões persistentes) demoram mais; configure o cache DNS da aplicação.
- DNS não encerra conexões existentes: sessões já abertas ao primário continuam falhando até caírem.
- Failover é "bom o suficiente" para RTOs de minutos. Para segundos, considere **Global Accelerator** (anycast, failover na camada de rede) ou balanceamento no cliente.

## Control plane vs data plane: o cuidado em um desastre

O **plano de dados** do Route 53 (responder consultas, health checks) é distribuído e altamente disponível. O **plano de controle** (criar/editar registros via API/console) fica centralizado e é menos resiliente. Em um evento regional grave na região do plano de controle, **editar registros pode falhar**.

Consequência de projeto: **não dependa de alterar registros durante o incidente**. Prefira failover **automático** por health checks (que usam apenas o plano de dados), ou use o **Route 53 Application Recovery Controller (ARC)** com *routing controls*, cujo mecanismo de troca foi desenhado para funcionar via clusters de alta disponibilidade independentes do plano de controle comum. (Verifique a documentação atual do ARC.)

## Arquiteturas multi-região e níveis de DR

Os modelos de recuperação de desastres variam em custo e RTO/RPO. O Route 53 é o "interruptor" de tráfego em todos eles.

| Modelo | Ambiente secundário | RTO típico | Custo | Papel do Route 53 |
|---|---|---|---|---|
| **Backup & restore** | Só backups | Horas | Mínimo | Troca manual do registro após restaurar |
| **Pilot light** | Núcleo mínimo (BD replicado), compute desligado | Dezenas de minutos | Baixo | Failover para o secundário após ligar a infraestrutura |
| **Warm standby** | Versão reduzida rodando | Minutos | Médio | Failover automático para o secundário, que escala depois |
| **Multi-site active-active** | Totalmente ativo | Segundos a minutos | Alto | Latency/Weighted + health checks |

### Padrão: Latency + Failover aninhados

```
app.exemplo.com.br
   ├─ Latency: sa-east-1 ──► registro Alias "app-sp.exemplo.com.br"
   │                              ├─ Failover PRIMARY   → ALB São Paulo
   │                              └─ Failover SECONDARY → ALB Virgínia
   └─ Latency: us-east-1 ──► registro Alias "app-va.exemplo.com.br"
                                  ├─ Failover PRIMARY   → ALB Virgínia
                                  └─ Failover SECONDARY → ALB São Paulo
```

Cada usuário vai à região mais rápida; se ela cair, cai para a outra. Isso exige Alias entre registros de políticas diferentes (ou o Traffic Flow para desenhar a árvore).

### Página de manutenção estática no S3 como secundário

Barato e eficaz: hospede uma página estática (S3 website ou CloudFront), aponte o registro SECONDARY para ela. Quando todo o backend falha, o usuário recebe uma mensagem amigável em vez de erro.

## Checklist de um bom failover

1. Health checks refletindo a saúde **real** do serviço (não só a porta).
2. TTLs curtos (30 a 60 s) nos registros envolvidos.
3. Dados replicados e RPO definido.
4. Capacidade suficiente no destino (ou Auto Scaling com tempo de aquecimento conhecido).
5. Teste regular (game days): desligue o primário e meça o tempo real.
6. Alarmes avisando que o failover ocorreu (o secundário em uso não deve passar despercebido).
7. Procedimento de **failback** (voltar ao primário) definido, inclusive resincronização de dados.

## Calculando RTO e dimensionando o failover

```
RTO DNS ≈ detecção + propagação
 detecção  = intervalo do health check × limiar de falhas
 propagação = TTL do registro (cache dos resolvers)

 Ex.: intervalo 10 s × 3 falhas = 30 s  +  TTL 60 s  ≈ 90 s no pior caso
```

| Parâmetro | Valor agressivo | Valor conservador | Trade-off |
|---|---|---|---|
| Intervalo do health check | 10 s | 30 s | Custo e falsos positivos |
| Limiar de falhas | 2 | 3-5 | Estabilidade × velocidade |
| TTL | 30-60 s | 300 s | Consultas × velocidade de troca |
| Verificadores | Várias regiões | Poucas | Precisão |

> [!warning] Valores, limites e preços mudam; os exemplos deste material não foram executados. Intervalos mínimos e tarifas de health checks variam; confirme na documentação.

## Tabela de decisão: padrão de DR × política

| Estratégia de DR | RTO/RPO | Route 53 | Custo |
|---|---|---|---|
| Backup e restore | Horas / horas | Troca manual | Baixo |
| Pilot light | Dezenas de min | Failover ou manual | Baixo-médio |
| Warm standby | Minutos | Failover automático | Médio |
| Active-active | Segundos-minutos | Latência/ponderado + health checks | Alto |

```
 Usuário ─► Route 53 ─┬─ primário (região A) ── health check ✔
                      └─ secundário (região B)  ◄── assume se A falhar
 Health check calculado: combina checks filhos (AND/OR) para evitar falso failover
```

## Boas práticas de produção

1. Health check deve testar **dependências reais** (endpoint `/health/deep`), não apenas a porta aberta.
2. Use **calculated health checks** para evitar failover por uma falha parcial.
3. Teste o failover periodicamente (game day), invertendo o status do health check.
4. Não dependa do console no desastre: o data plane do Route 53 é muito resiliente, o control plane não; deixe alterações pré-prontas.

## CLI comentado

```bash
# Cria health check HTTPS
aws route53 create-health-check --caller-reference hc-$(date +%s) \
  --health-check-config Type=HTTPS,FullyQualifiedDomainName=api.exemplo.com,ResourcePath=/health,Port=443,RequestInterval=10,FailureThreshold=3

# Consulta o estado atual
aws route53 get-health-check-status --health-check-id <ID>

# Inverte o health check para simular falha (teste de failover)
aws route53 update-health-check --health-check-id <ID> --inverted
```

## Troubleshooting

| Sintoma | Causa provável | Ação |
|---|---|---|
| Failover não acontece | Health check aponta para endpoint que segue "saudável" | Testar dependências reais |
| Failover indevido | Limiar baixo, firewall bloqueando checkers | Liberar IPs dos checkers, subir limiar |
| Troca lenta | TTL alto | Reduzir TTL antecipadamente |
| Secundário sem capacidade | Warm standby subdimensionado | Auto Scaling + testes de carga |

## Custo

Health checks cobram por check/mês (mais por recursos como HTTPS e intervalo rápido). Active-active e warm standby elevam o custo de infraestrutura na região secundária; escolha o nível de DR pelo custo da indisponibilidade, não pelo mais sofisticado.

## Erros comuns e armadilhas

- **Secundário nunca testado:** na hora H não sobe ou não suporta carga.
- **Primário sem health check:** o Failover não dispara.
- **TTL longo:** failover ineficaz por horas.
- **Dados não replicados:** o tráfego muda de região, mas os dados não estão lá.
- **Depender do plano de controle para editar registros em incidente.**
- **Falso positivo por health check frágil:** `/health` dependente de componente não crítico causa failover indevido (e pode derrubar o secundário também).
- **Failback automático ruidoso (flapping):** instabilidade do primário faz o tráfego oscilar; use thresholds adequados.

## 🧩 Quiz de Fixação

1. Descreva como montar um failover active-passive entre duas regiões com o Route 53 e quais elementos são obrigatórios.
2. Um RTO de 1 minuto é viável apenas com DNS? Quais fatores determinam o tempo real?
3. Por que um plano de DR não deve depender de editar registros DNS manualmente durante o incidente, e quais alternativas existem?

**Respostas:**
1) Dois registros com mesmo nome e tipo, um com `Failover=PRIMARY` (obrigatoriamente com health check ou Alias com `EvaluateTargetHealth`) e outro `Failover=SECONDARY`, cada um com `SetIdentifier`, apontando para o ambiente de cada região. TTL curto e health check do primário refletindo a saúde real.
2) Só com configurações agressivas (intervalo 10 s, threshold baixo, TTL ≤ 30 s) e clientes que respeitam o TTL; o tempo real é **detecção (intervalo × threshold) + TTL + cache dos clientes**. Conexões já abertas e caches que ignoram o TTL aumentam o tempo. Para RTO em segundos, considerar Global Accelerator ou lógica no cliente.
3) Porque, em eventos graves, o **plano de controle** pode ficar indisponível e a edição falhar. Alternativas: failover automático por health checks (plano de dados), Route 53 Application Recovery Controller com routing controls e arquiteturas active-active onde nenhuma mudança manual é necessária.

**Questões complementares:**

4. Como estimar o RTO de um failover via DNS?
5. Para que servem health checks calculados?
6. Por que testar o failover periodicamente?

**Respostas das questões complementares:**
4) Somando o tempo de detecção (intervalo × limiar de falhas) com o TTL do registro; por exemplo, 10 s × 3 + 60 s ≈ 90 s.
5) Para combinar vários checks (AND/OR) e evitar failover por falha parcial ou falso positivo.
6) Para validar que a configuração funciona de verdade, medir o RTO real e descobrir falhas (capacidade do secundário, TTL, permissões) antes do desastre.
