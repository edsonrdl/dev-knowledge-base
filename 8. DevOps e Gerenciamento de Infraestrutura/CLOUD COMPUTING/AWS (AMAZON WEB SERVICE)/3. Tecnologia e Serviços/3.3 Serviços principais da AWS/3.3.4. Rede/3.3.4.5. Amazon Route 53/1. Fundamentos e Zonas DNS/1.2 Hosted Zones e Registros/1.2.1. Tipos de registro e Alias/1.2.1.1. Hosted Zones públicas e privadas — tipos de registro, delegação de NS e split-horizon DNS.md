### Hosted Zones públicas e privadas — tipos de registro, delegação de NS e split-horizon DNS

> [!warning] Aviso
> Quotas, preços e comportamentos de APIs da AWS mudam. Confirme na documentação oficial do Route 53. Os comandos e JSON abaixo são ilustrativos e **não foram executados**.

Uma **hosted zone** é o contêiner onde ficam os registros DNS de um domínio (ou subdomínio) no Route 53. É a unidade básica de trabalho: toda configuração de DNS começa criando uma zona. Existem dois tipos, **pública** (responde à internet) e **privada** (responde só dentro de VPCs). Esta nota cobre os dois tipos, os registros mais usados, como a delegação por NS funciona e como usar zonas públicas e privadas juntas (split-horizon).

## Hosted zone pública vs privada

**Analogia:** a zona pública é o **catálogo telefônico impresso** distribuído a qualquer pessoa. A zona privada é o **ramal interno da empresa**: só funciona para quem está dentro do prédio (VPC).

| Aspecto | Zona pública | Zona privada |
|---|---|---|
| Quem consulta | Qualquer pessoa na internet | Somente recursos das VPCs associadas |
| Precisa de domínio registrado | Sim (NS delegados no registrador) | Não (pode usar `interno.exemplo`, `corp`, etc.) |
| Associação | Nenhuma | Uma ou mais VPCs (mesmo de outras regiões ou contas) |
| Uso típico | Sites, APIs públicas, e-mail | Nomes internos: `db.interno.exemplo.com`, microsserviços |
| Health checks | Sim | Sim, via alarmes CloudWatch (health checkers públicos não alcançam a VPC) |
| Requisitos da VPC | n/a | `enableDnsSupport` e `enableDnsHostnames` ativados |

```
          INTERNET                           VPC 10.0.0.0/16
              │                                     │
   consulta exemplo.com.br                 consulta db.exemplo.com.br
              │                                     │
              ▼                                     ▼
   ┌─────────────────────┐             ┌──────────────────────────┐
   │ Zona PÚBLICA        │             │ Zona PRIVADA (associada  │
   │ www → ALB público   │             │ à VPC)                   │
   │ api → CloudFront    │             │ db  → 10.0.20.15         │
   └─────────────────────┘             └──────────────────────────┘
```

### Criando e associando

```bash
# Zona privada: precisa informar a VPC já na criação
aws route53 create-hosted-zone \
  --name interno.exemplo.com.br \
  --caller-reference "priv-2026-01" \
  --vpc VPCRegion=us-east-1,VPCId=vpc-0abc123 \
  --hosted-zone-config Comment="Nomes internos",PrivateZone=true

# Associar mais uma VPC à mesma zona privada
aws route53 associate-vpc-with-hosted-zone \
  --hosted-zone-id Z0987654321XYZ \
  --vpc VPCRegion=sa-east-1,VPCId=vpc-0def456

# Associar VPC de OUTRA conta: a conta dona da zona autoriza primeiro
aws route53 create-vpc-association-authorization \
  --hosted-zone-id Z0987654321XYZ \
  --vpc VPCRegion=us-east-1,VPCId=vpc-0outra999
# Depois, na conta da VPC, roda-se associate-vpc-with-hosted-zone
```

O resolvedor da VPC (Route 53 Resolver, no endereço base da VPC +2, por exemplo `10.0.0.2`) é quem consulta as zonas privadas associadas. Se `enableDnsSupport` estiver desligado, a VPC não resolve nomes privados.

### Split-horizon DNS

É possível ter **a mesma zona (mesmo nome) em versão pública e privada**. Quem está dentro da VPC enxerga a versão privada; quem está fora, a pública. Isso permite que `app.exemplo.com.br` aponte para o IP **privado** do balanceador internamente e para o **público** externamente.

Atenção: dentro da VPC, quando existe zona privada para `exemplo.com.br`, ela tem **precedência total** sobre o nome. Se um registro existir só na zona pública (por exemplo `www`), ele **não será resolvido** dentro da VPC a menos que você o replique na zona privada. Esse é um dos erros mais comuns de split-horizon.

## Estrutura de um registro

Um registro (resource record set) tem:

| Campo | Descrição | Exemplo |
|---|---|---|
| **Name** | Nome completo | `www.exemplo.com.br` |
| **Type** | Tipo do registro | `A` |
| **TTL** | Tempo de cache em segundos | `300` |
| **Value(s)** | Um ou mais valores | `203.0.113.10` |
| **Routing policy** | Como escolher entre registros de mesmo nome/tipo | Simple, Weighted... (Domínio 2) |
| **Set identifier** | Rótulo que distingue registros com mesma política | `"web-us"` |

---

## Tipos de registro mais usados

| Tipo | Função | Exemplo de valor | Observação |
|---|---|---|---|
| **A** | Nome para IPv4 | `203.0.113.10` | Mais comum |
| **AAAA** | Nome para IPv6 | `2001:db8::1` | Dual-stack |
| **CNAME** | Nome para outro nome | `lb-123.us-east-1.elb.amazonaws.com` | **Não pode no apex**; não coexiste com outros tipos no mesmo nome |
| **MX** | Servidores de e-mail, com prioridade | `10 mail.exemplo.com.br` | Menor número, maior prioridade |
| **TXT** | Texto livre | `"v=spf1 include:... ~all"` | SPF, DKIM, verificação de domínio |
| **NS** | Name servers da zona/delegação | `ns-123.awsdns-45.com` | Criado automaticamente no apex |
| **SOA** | Metadados da zona | Serial, refresh, mínimo (cache negativo) | Criado automaticamente |
| **SRV** | Serviço e porta | `10 5 5060 sip.exemplo.com.br` | VoIP, XMPP |
| **CAA** | Quais autoridades podem emitir certificados | `0 issue "amazon.com"` | Complementa o ACM |
| **PTR** | IP para nome (DNS reverso) | `host.exemplo.com.br` | Zonas `in-addr.arpa` |
| **DS** | Delegação DNSSEC | Digest da chave | Veja DNSSEC no Domínio 4 |

Os registros **NS e SOA** do apex são criados com a zona. Altere-os com cuidado; apagar os NS do apex quebra a zona.

### CNAME: restrições que caem em prova

1. **Não é permitido no apex** (zone apex, ou "naked domain"): `exemplo.com.br` não pode ser CNAME, pois o apex já precisa conter SOA e NS, e CNAME não pode coexistir com outros tipos no mesmo nome. A solução é o **Alias** (próxima nota).
2. Um nome que tem CNAME não pode ter A, MX, TXT etc.
3. Consultas a CNAME são cobradas como consultas padrão (Alias para recurso AWS não é cobrado).

## Delegação de subdomínios e NS

Há dois níveis de delegação:

1. **Registrador para o Route 53:** os NS no registrador do domínio precisam ser os 4 NS da hosted zone.
2. **Zona-pai para zona-filha (subdomínio):** para delegar `dev.exemplo.com.br` a outra hosted zone (talvez em outra conta), crie na zona-pai um registro NS apontando para os 4 NS da zona-filha.

```
Registrador (.br)   exemplo.com.br  NS → ns-1, ns-2, ns-3, ns-4 (zona A)
Zona A (exemplo.com.br)   dev.exemplo.com.br  NS → ns-9, ns-10, ns-11, ns-12 (zona B)
Zona B (dev.exemplo.com.br)   api.dev.exemplo.com.br  A → 10.0.0.5
```

Isso permite que cada equipe ou conta administre seu próprio subdomínio (padrão comum em organizações multi-conta).

## Criando, alterando e removendo registros

Alterações em lote usam `change-resource-record-sets`, com ações `CREATE`, `DELETE` e `UPSERT` (cria ou atualiza). As mudanças de um mesmo lote são **atômicas**: tudo aplica ou nada.

```json
{
  "Comment": "Cria www e api",
  "Changes": [
    {
      "Action": "UPSERT",
      "ResourceRecordSet": {
        "Name": "www.exemplo.com.br",
        "Type": "A",
        "TTL": 300,
        "ResourceRecords": [{ "Value": "203.0.113.10" }]
      }
    },
    {
      "Action": "UPSERT",
      "ResourceRecordSet": {
        "Name": "exemplo.com.br",
        "Type": "MX",
        "TTL": 3600,
        "ResourceRecords": [
          { "Value": "10 mail1.exemplo.com.br" },
          { "Value": "20 mail2.exemplo.com.br" }
        ]
      }
    }
  ]
}
```

```bash
aws route53 change-resource-record-sets \
  --hosted-zone-id Z0123456789ABC \
  --change-batch file://mudancas.json
# Retorna um ChangeInfo com Status PENDING; acompanhe até INSYNC:
aws route53 get-change --id /change/C0123456789
```

- `UPSERT`: idempotente, ideal para automação.
- Cada mudança tem status `PENDING` até se propagar pelos servidores da AWS (normalmente em até cerca de um minuto), e então `INSYNC`.

Em IaC, o equivalente CloudFormation é `AWS::Route53::HostedZone` e `AWS::Route53::RecordSet` (ou `RecordSetGroup`). Também há suporte em Terraform. (Não executado.)

## Exemplo prático: zona pública + privada para um mesmo domínio

Cenário: `exemplo.com.br` tem site público e um banco interno.

1. Zona **pública** `exemplo.com.br`: `www` → Alias para ALB público; `@` (apex) → Alias para o mesmo ALB.
2. Zona **privada** `exemplo.com.br`, associada à VPC de produção: `db` → CNAME para o endpoint do RDS; `www` e `@` → mesmos alvos da pública (para a aplicação interna também resolvê-los).
3. Na aplicação interna: conectar em `db.exemplo.com.br` em vez de decorar o endpoint do RDS; se houver failover/rotação do banco, só o registro muda.

## Erros comuns e armadilhas

- **Zona privada sem `enableDnsHostnames`/`enableDnsSupport`:** nomes não resolvem na VPC.
- **Split-horizon incompleto:** registros existentes só na zona pública somem dentro da VPC.
- **CNAME no apex:** a API recusa. Use Alias.
- **Duas zonas públicas com o mesmo nome:** é possível criar, mas só uma recebe tráfego (aquela cujos NS estão no registrador); a outra é inútil e gera confusão e custo.
- **Zona privada e VPN/Direct Connect:** consultas de on-premises para a zona privada exigem Resolver Endpoints (Domínio 4).
- **Apagar a zona:** só é possível depois de remover todos os registros exceto NS e SOA do apex.
- **Quotas:** há limites por zona (número de registros) e por conta (número de zonas); consulte as quotas atuais antes de projetar muitas zonas.

## 🧩 Quiz de Fixação

1. Por que `exemplo.com.br` (apex) não pode ser um CNAME e o que usar no lugar?
2. A aplicação dentro da VPC não consegue resolver `www.exemplo.com.br`, que funciona normalmente na internet. Existe uma zona privada `exemplo.com.br` associada à VPC. Qual a causa provável?
3. Como delegar `dev.exemplo.com.br` a uma zona gerenciada por outra conta AWS?

**Respostas:**
1) Porque o apex já precisa conter registros SOA e NS e, pelo padrão DNS, um CNAME não pode coexistir com nenhum outro tipo no mesmo nome. Usa-se um registro **Alias** (extensão do Route 53), que se comporta como A/AAAA no apex e aponta para recursos AWS (ELB, CloudFront etc.).
2) A zona privada com o mesmo nome tem precedência dentro da VPC e provavelmente **não contém** o registro `www` (ele existe só na zona pública). Correção: criar `www` também na zona privada (split-horizon completo).
3) Criar a hosted zone `dev.exemplo.com.br` na outra conta, copiar seus 4 NS e criar na zona-pai (`exemplo.com.br`) um registro **NS** `dev.exemplo.com.br` com esses 4 valores.
