### Alias vs CNAME — zone apex, alvos AWS suportados, custo de consulta e Evaluate Target Health

> [!warning] Aviso
> A lista de alvos suportados por Alias, IDs de hosted zone e preços muda com o tempo. Confira a documentação oficial ("Choosing between alias and non-alias records"). Os exemplos **não foram executados**.

O registro **Alias** é uma extensão exclusiva do Route 53 que resolve dois problemas do DNS tradicional: apontar o **apex do domínio** (`exemplo.com.br`) para um recurso que só tem nome (como um ALB) e fazer isso **sem custo de consulta** e com atualização automática quando os IPs do alvo mudam. Entender Alias vs CNAME é uma das perguntas mais frequentes em certificações AWS e uma decisão do dia a dia.

## O problema que o Alias resolve

Recursos AWS como ALB, CloudFront e API Gateway são acessados por **nomes DNS**, não por IPs fixos (`meu-alb-123.us-east-1.elb.amazonaws.com`). Os IPs atrás desses nomes mudam o tempo todo. Duas dificuldades surgem:

1. Para `www.exemplo.com.br` um **CNAME** serve. Mas para `exemplo.com.br` (apex) o CNAME é proibido.
2. CNAME exige uma **segunda consulta** do resolvedor (resolver o alvo), e as consultas CNAME são cobradas.

**Analogia:** um CNAME é um **cartão "mudamos de endereço, procure em ..."**: o visitante precisa fazer outra pergunta. O Alias é a **recepcionista que já consultou o endereço novo** e o entrega na hora, como se fosse o endereço original.

---

## Como o Alias funciona

Quando o resolvedor pergunta por `exemplo.com.br` (tipo A), o Route 53 encontra o Alias, **resolve internamente** o alvo (por exemplo um ALB) e devolve diretamente os **IPs (registros A/AAAA)** atuais do alvo. Para o cliente, parece um registro A comum. Por isso o Alias pode existir no apex.

```
CNAME (www):
  Cliente ──► Route 53: "www?"      ◄── "CNAME → alb-123.elb.amazonaws.com"
  Cliente ──► Resolver:  "alb-123...?" ◄── "IPs"        (2 consultas, cobradas)

ALIAS (apex ou qualquer nome):
  Cliente ──► Route 53: "exemplo.com.br?" ◄── "IPs do ALB" (1 consulta, grátis p/ alvo AWS)
```

## Alvos suportados (principais)

| Alvo do Alias | Observação |
|---|---|
| **Elastic Load Balancer** (ALB, NLB, CLB) | Informar o nome DNS e o hosted zone ID **da região do balanceador** |
| **CloudFront distribution** | Hosted zone ID fixo e global do CloudFront (`Z2FDTNDATAQYW2`, conferir na documentação) |
| **API Gateway** (endpoint regional/edge/custom domain) | Via domain name do API Gateway |
| **S3 website endpoint** | O nome do bucket deve ser igual ao nome do registro; somente endpoint website (HTTP) |
| **Elastic Beanstalk** | Ambientes com nome de domínio do ambiente |
| **VPC Interface Endpoint** | Para nomes de PrivateLink |
| **AWS Global Accelerator** | Via DNS name do accelerator |
| **Outro registro da mesma hosted zone** | Útil para apontar `www` para o apex, por exemplo |

**Não suportados como alvo:** instâncias EC2 diretamente pelo seu nome público (use A com Elastic IP) e nomes DNS fora da AWS. Para alvos externos, use CNAME (exceto no apex, onde não há solução com CNAME).

## Alias vs CNAME

| Característica | Alias | CNAME |
|---|---|---|
| Pode ser usado no **apex** | **Sim** | **Não** |
| Custo das consultas | **Gratuitas** quando o alvo é recurso AWS suportado | Cobradas (consulta padrão) |
| Alvo | Recursos AWS (e registro da mesma zona) | Qualquer nome DNS |
| Tipo exposto ao cliente | A, AAAA (comporta-se como A/AAAA) | CNAME |
| TTL | **Herdado do alvo** (não se define) | Definido por você |
| Health check do alvo | **Evaluate Target Health** (opcional) | Via health check associado (políticas) |
| Padrão DNS | Extensão da AWS (só no Route 53) | Padrão (RFC 1034) |
| Resolver no cliente | Transparente (resposta de A) | Cliente/resolvedor segue a cadeia |

Regra prática: **dentro da AWS, prefira Alias**; use CNAME só quando o alvo for externo.

## Evaluate Target Health

No Alias há uma opção `EvaluateTargetHealth`. Se `true`, o Route 53 considera o registro "saudável" apenas se o recurso-alvo estiver saudável, usando a saúde nativa do recurso (por exemplo, targets de um ALB). Com políticas como Failover, Weighted ou Latency, isso permite remover automaticamente um alvo doente da resposta, **sem criar um health check separado**.

Pontos importantes:

- Para ELB: o Route 53 verifica se há pelo menos um target saudável no balanceador.
- Para S3 website, CloudFront e alguns outros, não há avaliação real de saúde (o valor `true` não traz proteção prática).
- Em Alias para outro registro da mesma zona, a saúde é herdada daquele registro.

## Exemplo prático: apex e www apontando para um ALB

```json
{
  "Comment": "Apex e www para o ALB de producao",
  "Changes": [
    {
      "Action": "UPSERT",
      "ResourceRecordSet": {
        "Name": "exemplo.com.br",
        "Type": "A",
        "AliasTarget": {
          "HostedZoneId": "Z35SXDOTRQ7X7K",
          "DNSName": "dualstack.alb-prod-123456.us-east-1.elb.amazonaws.com",
          "EvaluateTargetHealth": true
        }
      }
    },
    {
      "Action": "UPSERT",
      "ResourceRecordSet": {
        "Name": "exemplo.com.br",
        "Type": "AAAA",
        "AliasTarget": {
          "HostedZoneId": "Z35SXDOTRQ7X7K",
          "DNSName": "dualstack.alb-prod-123456.us-east-1.elb.amazonaws.com",
          "EvaluateTargetHealth": true
        }
      }
    },
    {
      "Action": "UPSERT",
      "ResourceRecordSet": {
        "Name": "www.exemplo.com.br",
        "Type": "A",
        "AliasTarget": {
          "HostedZoneId": "Z0123456789ABC",
          "DNSName": "exemplo.com.br",
          "EvaluateTargetHealth": false
        }
      }
    }
  ]
}
```

Linha a linha:

- **Sem `TTL` nem `ResourceRecords`:** Alias não usa; o TTL vem do alvo.
- **`HostedZoneId` dentro de `AliasTarget`:** é o ID da zona **do alvo**, não da sua zona. Para ALB, é o ID da hosted zone do balanceador naquela região (veja a tabela de endpoints do ELB; `Z35SXDOTRQ7X7K` é apenas um exemplo de us-east-1, confira o valor atual). Você obtém o valor com `aws elbv2 describe-load-balancers` (campo `CanonicalHostedZoneId`).
- **Dois registros (A e AAAA):** se o alvo é dual-stack, crie um de cada tipo.
- **Terceiro registro:** `www` como Alias para o próprio apex, na mesma zona (o `HostedZoneId` aqui é o da sua zona).

```bash
# Descobrir o hosted zone ID e DNS name do ALB
aws elbv2 describe-load-balancers --names alb-prod \
  --query 'LoadBalancers[0].[DNSName,CanonicalHostedZoneId]'

# Aplicar a mudança
aws route53 change-resource-record-sets \
  --hosted-zone-id Z0123456789ABC --change-batch file://alias.json
```

### Exemplo: site estático em S3 + CloudFront

- Para apex com CloudFront: Alias → distribuição CloudFront, `HostedZoneId` = `Z2FDTNDATAQYW2`, domínio alternativo (CNAME) configurado na distribuição e certificado ACM em us-east-1.
- Para S3 website direto: o bucket deve se chamar exatamente `www.exemplo.com.br`, e o Alias aponta ao endpoint `s3-website-<região>`.

## Erros comuns e armadilhas

- **Usar o HostedZoneId da sua zona no AliasTarget:** deve ser o da zona do **alvo** (exceto quando o alvo é outro registro da mesma zona).
- **Criar só o registro A e esquecer o AAAA** em balanceador dual-stack: clientes IPv6 ficam sem resolver.
- **Esperar que Alias aponte para EC2 ou domínio externo:** não suporta.
- **Confiar em Evaluate Target Health onde não há avaliação real:** o failover não acontece.
- **Tentar definir TTL em Alias:** não existe; o TTL é do alvo (dezenas de segundos para ELB).
- **Alias para ALB interno em zona pública:** o nome resolve para IPs privados, inúteis na internet. Use zona privada.
- **Apagar o recurso-alvo e deixar o Alias:** o registro fica "pendurado" e pode ser alvo de **subdomain takeover** (outro cliente reaproveita o nome). Limpe registros ao remover recursos.

## 🧩 Quiz de Fixação

1. Uma empresa quer que `exemplo.com.br` (sem www) aponte para um Application Load Balancer. Qual tipo de registro usar e por quê?
2. Quais as vantagens de custo e operação de um Alias frente a um CNAME para um recurso AWS?
3. Com um Alias para um ALB e política Failover, para que serve `EvaluateTargetHealth` e em que ele difere de criar um health check explícito?

**Respostas:**
1) Um registro **Alias (tipo A, e AAAA se dual-stack)** para o ALB, pois o apex não aceita CNAME. O Alias devolve os IPs atuais do balanceador sem que o cliente siga outra consulta.
2) Consultas a Alias que apontam para recursos AWS são **gratuitas**, não há segunda resolução (menor latência), os IPs do alvo se atualizam automaticamente e funciona no apex. O CNAME é cobrado, exige outra consulta e não funciona no apex.
3) `EvaluateTargetHealth=true` faz o Route 53 usar a **saúde nativa do alvo** (para ALB, a existência de targets saudáveis) para decidir se o registro entra na resposta, sem criar e pagar um health check dedicado. Um health check explícito monitora um endpoint externamente (HTTP/TCP, string matching) e pode capturar falhas que a saúde interna do ELB não vê (por exemplo, uma rota de aplicação específica).
