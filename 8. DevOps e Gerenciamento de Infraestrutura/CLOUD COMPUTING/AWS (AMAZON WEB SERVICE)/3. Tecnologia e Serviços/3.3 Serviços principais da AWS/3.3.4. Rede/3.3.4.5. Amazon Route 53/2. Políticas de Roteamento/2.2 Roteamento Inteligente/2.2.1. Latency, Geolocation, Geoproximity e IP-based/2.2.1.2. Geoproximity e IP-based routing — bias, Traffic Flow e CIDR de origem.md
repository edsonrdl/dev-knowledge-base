## Geoproximity routing

Roteia pela **distância geográfica** entre o usuário e o recurso, com a possibilidade de **ajustar o "tamanho" da área** de cada recurso por um valor chamado **bias**.

Os recursos podem ser:

- **Recursos AWS**, identificados pela região AWS;
- **Recursos fora da AWS** (on-premises, outro provedor), identificados por **latitude e longitude**.

### Bias

O **bias** (de -99 a +99) aumenta ou reduz a **área geográfica** atendida por cada recurso:

| Bias | Efeito |
|---|---|
| **0** | Sem ajuste: o recurso atende os usuários mais próximos dele |
| **Positivo (+1 a +99)** | **Expande** a área: atrai tráfego de usuários mais distantes |
| **Negativo (-1 a -99)** | **Encolhe** a área: o recurso recebe menos usuários |

**Analogia:** cada região é uma **loja de franquia** com uma área de entrega. Sem bias, cada loja atende o bairro mais perto. Um bias positivo "aumenta o raio de entrega" da loja, pegando clientes das vizinhas. Um bias negativo reduz o raio.

```
Sem bias (0 / 0):                    Bias +30 em us-east-1:

  us-west-2 │ us-east-1               us-west-2 │   us-east-1
   ┌────────┼────────┐                 ┌───────┼─────────┐
   │ oeste  │ leste  │                 │ oeste │  leste  │ (fronteira
   └────────┴────────┘                 └───────┴─────────┘  desloca p/ oeste)
```

### Quando usar

- **Balancear capacidade** entre regiões desiguais (uma região maior atende uma área maior).
- **Migração gradual:** aumentar o bias de uma região nova para absorver tráfego sem trocar tudo de uma vez.
- **Esvaziar uma região** para manutenção usando bias negativo (para esvaziar por completo, prefira health check/failover).
- **Misturar AWS e on-premises** por coordenadas geográficas.

### Como é criada

A política é configurada com bias por recurso. Historicamente isso se fazia pelo **Traffic Flow** (editor visual/JSON de políticas de tráfego, cobrado por política); a documentação atual também descreve registros de geoproximity diretamente na hosted zone. Verifique qual caminho está disponível em sua conta e região.

Registro de exemplo (campo `GeoProximityLocation`):

```json
{
  "Action": "UPSERT",
  "ResourceRecordSet": {
    "Name": "app.exemplo.com.br",
    "Type": "A",
    "SetIdentifier": "virginia",
    "GeoProximityLocation": { "AWSRegion": "us-east-1", "Bias": 30 },
    "AliasTarget": {
      "HostedZoneId": "Z0VIRGINIAALB",
      "DNSName": "alb-va-222.us-east-1.elb.amazonaws.com",
      "EvaluateTargetHealth": true
    }
  }
}
```

Para um recurso fora da AWS, troca-se `AWSRegion` por `Coordinates` (`Latitude` e `Longitude`). (Sintaxe conforme a documentação no momento da escrita; confira o formato atual da API.)

## IP-based routing

Roteia com base no **endereço IP do cliente** (a origem da consulta), usando **blocos CIDR que você define**. Você cria uma **CIDR collection** (coleção de blocos agrupados em "locations") e associa cada location a um registro.

```
CIDR collection "provedores":
   location "ISP-A"  → 198.51.100.0/24, 203.0.113.0/24
   location "ISP-B"  → 192.0.2.0/24

Registro (IP-based):   ISP-A → endpoint A      ISP-B → endpoint B
                       padrão (*) → endpoint genérico
```

### Usos

- **Otimizar custo ou desempenho de rede** quando você conhece a rede dos clientes (por exemplo, enviar usuários de um provedor para o endpoint com peering direto com ele).
- **Roteamento por empresa ou parceiro:** clientes corporativos com faixas de IP conhecidas vão para endpoints dedicados.
- **Isolar tráfego** de redes específicas.

### Observações

- Ao contrário de Geolocation, **você** define o mapeamento IP → destino; não há banco da AWS envolvido.
- Funciona sobre o IP que o Route 53 enxerga: o do resolvedor, ou o do cliente se o resolvedor usa EDNS0 client subnet. Clientes atrás de resolvedores públicos grandes podem ser mal classificados.
- Também é recomendável ter um registro **padrão** (`*`) para IPs fora de qualquer coleção.

```bash
# Criar uma coleção de CIDRs e preencher uma location
aws route53 create-cidr-collection --name provedores --caller-reference "cidr-2026-01"

aws route53 change-cidr-collection --id <COLLECTION_ID> \
  --changes 'Action=PUT,LocationName=ISP-A,CidrList=198.51.100.0/24,203.0.113.0/24'
# Depois, cria-se o registro com CidrRoutingConfig (CollectionId + LocationName)
```

## Comparativo das políticas "inteligentes"

| Política | Critério | Ajustável | Melhor para |
|---|---|---|---|
| **Latency** | Menor latência de rede medida | Não | Desempenho multi-região |
| **Geolocation** | País/continente/estado do usuário | Regras fixas | Idioma, licenciamento, compliance |
| **Geoproximity** | Distância geográfica + bias | **Bias** (-99 a +99) | Equilibrar capacidade, migração gradual, híbrido |
| **IP-based** | CIDR do cliente | **CIDRs que você define** | Rotas por provedor/parceiro, custo de rede |

Todas essas políticas têm preço de consulta superior ao Simple. Combine-as com health checks e `EvaluateTargetHealth`.

## Geoproximity em profundidade: o mapa mental

```
 Sem bias:                         Com bias +25 em us-east-1 (ou -25 em sa-east-1):
 ┌───────────────────────┐         ┌───────────────────────┐
 │  fronteira = ponto    │         │ fronteira desloca para │
 │  equidistante entre   │         │ dentro da área de sa,  │
 │  sa-east-1 e us-east-1│         │ us-east-1 "atrai" mais │
 └───────────────────────┘         │ usuários               │
                                   └───────────────────────┘
```

| Conceito | Detalhe |
|---|---|
| Base do cálculo | Distância geográfica do usuário (pela localização estimada do resolver/EDNS) até o recurso |
| Recursos | Região da AWS ou coordenadas (latitude/longitude) para recursos fora da AWS |
| Bias | Valor de **-99 a +99**: positivo expande a área do recurso, negativo a encolhe |
| Ferramenta | Traffic Flow (editor visual de políticas) |
| Diferença para Latency | Latency mede a latência **medida**; geoproximity usa distância **geográfica** com ajuste manual |

## IP-based routing em profundidade

```
 Coleção CIDR "isp-a"  = { 200.10.0.0/16, 200.11.0.0/16 }  ──► registro → Endpoint X
 Coleção CIDR "isp-b"  = { 201.20.0.0/16 }                  ──► registro → Endpoint Y
 Padrão (*) sem correspondência                              ──► registro default → Endpoint Z
```

| Aspecto | Observação |
|---|---|
| Entrada | CIDR do **resolver DNS** (ou do cliente, com EDNS Client Subnet) |
| Quando usar | Direcionar um ISP ou rede corporativa a um endpoint específico, reduzir custo de trânsito |
| Limites | Número de coleções, locations e CIDRs por coleção são limitados; confirme na documentação |
| Pegadinha | Clientes atrás de resolvers públicos (8.8.8.8) aparecem com o IP do resolver |

> [!warning] Limites e recursos de Traffic Flow e coleções CIDR mudam; confirme na documentação atual.

## Quando usar cada política "inteligente"

| Necessidade | Política |
|---|---|
| Menor latência medida entre regiões | **Latency** |
| Conteúdo/regras por país ou continente | **Geolocation** |
| Controlar a "área de influência" de cada região, com ajuste fino | **Geoproximity** (bias) |
| Rotear por rede/ISP de origem | **IP-based** |
| Failover | **Failover** (com health check) |
| Distribuição proporcional | **Weighted** |

### Exemplo de CLI (comentado, não executado)

```bash
# IP-based: criar uma coleção de CIDRs
aws route53 create-cidr-collection --name isp-parceiro --caller-reference $(date +%s)
aws route53 change-cidr-collection --id <id> --changes \
  'Action=PUT,LocationName=isp-a,CidrList=[200.10.0.0/16,200.11.0.0/16]'
# O registro usa CidrRoutingConfig com CollectionId e LocationName no change-resource-record-sets
```

## Boas práticas

1. Combine com health checks para que a política não encaminhe a um endpoint fora do ar.
2. Documente cada bias aplicado e o motivo (a mudança afeta milhões de resolvers de uma vez).
3. Teste com `dig +subnet=<cidr>` ou o console (Test record) antes da publicação.
4. Mantenha TTL baixo (30-60 s) durante a calibragem.

## Erros comuns e armadilhas

- **Usar bias sem medir:** mudar o bias desloca tráfego de forma não linear; faça pequenos passos e monitore.
- **Esperar que o bias substitua o failover:** ele redistribui por geografia, mas não retira uma região doente; use health checks.
- **IP-based sem registro padrão:** clientes fora das coleções ficam sem resposta.
- **Esquecer o efeito do resolvedor:** o "IP do cliente" é frequentemente o do resolvedor, o que embaralha a classificação para quem usa DNS público.
- **Custos de Traffic Flow:** cada política de tráfego tem cobrança mensal; para casos simples, registros com política direta bastam.

## 🧩 Quiz de Fixação

1. A região us-east-1 está sobrecarregada e us-west-2 tem folga. Como usar Route 53 para deslocar parte do tráfego sem retirar nenhuma região do ar?
2. Uma empresa quer que os clientes de um provedor específico, com faixas de IP conhecidas, usem um endpoint com peering direto. Qual política?
3. Diferencie bias positivo de negativo e diga por que o bias não substitui health checks.

**Respostas:**
1) **Geoproximity** com **bias negativo** em us-east-1 (ou positivo em us-west-2), reduzindo a área atendida pela primeira e aumentando a da segunda. A mudança é gradual e pode ser ajustada por passos.
2) **IP-based routing**, criando uma CIDR collection com as faixas do provedor e associando essa location ao registro do endpoint dedicado, com um registro padrão para os demais.
3) Bias **positivo** expande a área geográfica do recurso (atrai mais usuários); **negativo** encolhe (atrai menos). O bias só ajusta a geometria da distribuição; ele não verifica a saúde do recurso. Para tirar um endpoint doente da resposta é preciso health check ou `EvaluateTargetHealth`.

### Questões de aprofundamento

4. O que um bias de +30 faz em uma região no Geoproximity?
5. Por que o IP-based routing pode falhar para clientes que usam DNS público?
6. Como testar uma política antes de publicar?

**Respostas:**
4) Expande a área geográfica atendida por aquele recurso, atraindo mais usuários de regiões vizinhas.
5) Porque a decisão usa o IP do resolver (ou o EDNS Client Subnet); o resolver público não pertence ao CIDR do ISP esperado.
6) Usando o teste de registro no console, `dig +subnet` e TTL baixo durante a calibragem.
