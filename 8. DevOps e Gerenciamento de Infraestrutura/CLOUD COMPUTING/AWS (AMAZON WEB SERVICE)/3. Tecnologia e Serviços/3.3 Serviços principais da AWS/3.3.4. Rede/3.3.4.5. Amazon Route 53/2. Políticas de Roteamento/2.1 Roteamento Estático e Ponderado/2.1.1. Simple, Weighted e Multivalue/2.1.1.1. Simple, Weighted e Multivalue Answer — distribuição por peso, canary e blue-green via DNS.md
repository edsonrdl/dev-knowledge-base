### Simple, Weighted e Multivalue Answer — distribuição por peso, canary e blue-green via DNS

> [!warning] Aviso
> Limites (como número máximo de valores devolvidos), preços por tipo de consulta e comportamentos mudam. Confirme na documentação do Route 53 ("Choosing a routing policy"). Os exemplos **não foram executados**.

Uma **política de roteamento** define como o Route 53 responde quando há **mais de um registro** (ou mais de um valor) para o mesmo nome. Esta nota cobre as três políticas "básicas": **Simple** (sem lógica), **Weighted** (distribuição por peso) e **Multivalue Answer** (vários valores saudáveis). As políticas baseadas em localização e latência estão na nota seguinte, e failover no Domínio 3.

## Visão geral das políticas

```
              ┌──────────── Route 53 recebe consulta por api.exemplo.com.br ────────────┐
              │                                                                         │
  Simple      │  1 registro; vários valores possíveis; devolve TODOS (cliente escolhe)  │
  Weighted    │  N registros com pesos; devolve 1, sorteado proporcionalmente           │
  Multivalue  │  N registros, cada um com health check; devolve até 8 saudáveis         │
              └─────────────────────────────────────────────────────────────────────────┘
```

| Política | Quantos registros de mesmo nome | Health check | Resposta | Uso típico |
|---|---|---|---|---|
| **Simple** | 1 (pode ter vários valores) | Não associável | Todos os valores, ordem aleatória | Um recurso único, site simples |
| **Weighted** | Vários, cada um com peso | Sim | Um registro sorteado pelo peso | Canary, blue-green, migração, A/B |
| **Multivalue Answer** | Vários, um valor por registro | Sim (por registro) | Até 8 registros saudáveis, aleatórios | Distribuição simples com remoção de doentes |

**Analogia:** Simple é uma **lista telefônica com vários números e o cliente liga para o que quiser**. Weighted é um **sorteio com bolas de pesos diferentes** (90 bolas azuis, 10 vermelhas). Multivalue é a mesma lista, mas **só com números de quem está de plantão**.

## Simple routing

É o padrão quando não se escolhe política. Um único registro com um ou mais valores.

- Se houver **múltiplos valores**, o Route 53 devolve **todos**, em **ordem aleatória**; o cliente (ou o resolvedor) escolhe qual usar, geralmente o primeiro.
- **Não é possível associar health checks** a um registro Simple, então valores indisponíveis continuam sendo devolvidos.
- Não é possível ter dois registros Simple com o mesmo nome e tipo.

```json
{
  "Action": "UPSERT",
  "ResourceRecordSet": {
    "Name": "api.exemplo.com.br",
    "Type": "A",
    "TTL": 60,
    "ResourceRecords": [
      { "Value": "203.0.113.10" },
      { "Value": "203.0.113.11" }
    ]
  }
}
```

Uso: ambientes simples, um único recurso (por exemplo Alias para um ALB, que já distribui internamente). Para vários servidores independentes que precisam de verificação de saúde, prefira Multivalue ou um ELB.

## Weighted routing

Distribui tráfego entre vários recursos com base em **pesos** (0 a 255). A proporção de cada registro é:

```
fração = peso do registro / soma dos pesos dos registros com mesmo nome e tipo
```

Exemplo: pesos 90 e 10 → 90% e 10% das respostas. Pesos 1, 1, 1 → um terço cada. **Peso 0** significa "não enviar tráfego" (útil para pré-provisionar). Se **todos** os registros tiverem peso 0, o Route 53 passa a responder todos igualmente.

Cada registro precisa de:

- um **Set Identifier** único dentro do conjunto (rótulo livre);
- o **peso**;
- opcionalmente um **health check** (registros doentes saem do sorteio).

```
        usuários ──► Route 53 ──┬── 90% ──► api.exemplo.com.br → ALB versão estável
                                └── 10% ──► api.exemplo.com.br → ALB versão canary
```

### Exemplo: canary de 10%

```json
{
  "Comment": "Canary 10% para a nova versão",
  "Changes": [
    {
      "Action": "UPSERT",
      "ResourceRecordSet": {
        "Name": "api.exemplo.com.br",
        "Type": "A",
        "SetIdentifier": "estavel",
        "Weight": 90,
        "AliasTarget": {
          "HostedZoneId": "Z35SXDOTRQ7X7K",
          "DNSName": "alb-estavel-111.us-east-1.elb.amazonaws.com",
          "EvaluateTargetHealth": true
        }
      }
    },
    {
      "Action": "UPSERT",
      "ResourceRecordSet": {
        "Name": "api.exemplo.com.br",
        "Type": "A",
        "SetIdentifier": "canary",
        "Weight": 10,
        "AliasTarget": {
          "HostedZoneId": "Z35SXDOTRQ7X7K",
          "DNSName": "alb-canary-222.us-east-1.elb.amazonaws.com",
          "EvaluateTargetHealth": true
        }
      }
    }
  ]
}
```

Evolução do canary: 90/10 → 50/50 → 0/100. Para rollback, ponha o peso do canary em 0. Para blue-green, mantenha 100/0, suba o green a 0/100 quando validado e mantenha o blue em peso 0 durante o período de segurança.

### Limites práticos do Weighted

- **A distribuição é por resolução DNS, não por requisição.** Resolvedores guardam o resultado por TTL; milhares de usuários atrás do mesmo resolvedor (um provedor, uma empresa) vão ao **mesmo** destino durante o TTL. Em amostras pequenas o percentual real se afasta do configurado.
- **TTL baixo (30 a 60 s)** melhora a granularidade e o rollback, ao custo de mais consultas.
- Clientes que mantêm conexões persistentes ou fazem cache próprio (JVM, por exemplo, com cache DNS infinito em algumas configurações) não rebalanceiam.
- Para pesos precisos por requisição e rollback instantâneo, prefira **ALB com weighted target groups** (peso no balanceador). DNS ponderado é adequado para dividir entre **regiões ou balanceadores diferentes**.

## Multivalue Answer routing

Devolve **até 8** registros saudáveis, escolhidos aleatoriamente entre vários registros de mesmo nome. Cada registro tem **seu próprio health check**; registros com health check falho não entram na resposta.

- Funciona como "Simple com health check", em que cada valor é um registro separado com `SetIdentifier`.
- Não substitui um load balancer: o cliente escolhe o IP, não há balanceamento por conexão, sticky ou verificação de camada 7 sofisticada.
- Se houver mais de 8 saudáveis, devolve 8 aleatórios.

```bash
# Health check HTTP para um servidor
HC_ID=$(aws route53 create-health-check \
  --caller-reference "hc-web1-2026" \
  --health-check-config 'IPAddress=203.0.113.10,Port=80,Type=HTTP,ResourcePath=/health,RequestInterval=30,FailureThreshold=3' \
  --query 'HealthCheck.Id' --output text)
```

```json
{
  "Action": "UPSERT",
  "ResourceRecordSet": {
    "Name": "web.exemplo.com.br",
    "Type": "A",
    "SetIdentifier": "web-1",
    "MultiValueAnswer": true,
    "TTL": 30,
    "ResourceRecords": [{ "Value": "203.0.113.10" }],
    "HealthCheckId": "COLOQUE-O-HC_ID-AQUI"
  }
}
```

Explicação: `MultiValueAnswer: true` ativa a política; cada servidor tem seu registro, seu `SetIdentifier` e seu health check. O health check da CLI define tipo, porta, caminho, intervalo e limite de falhas (o detalhamento está no Domínio 3).

## Como escolher

| Necessidade | Política |
|---|---|
| Um único destino | Simple (com Alias) |
| Dividir tráfego em proporção (canary, blue-green, migração) | Weighted |
| Vários servidores simples com remoção automática de doentes | Multivalue (ou, melhor, um ELB) |
| Resposta mais próxima/rápida/regional | Latency/Geolocation (próxima nota) |
| Ativo/passivo | Failover (Domínio 3) |

Combinação: políticas podem ser aninhadas via **Alias para outro registro de política** (traffic flow ou registros em camadas), por exemplo Weighted entre regiões, e dentro de cada região Latency/Failover. O **Traffic Flow** (editor visual de políticas) facilita essas composições, com custo próprio por política.

## Erros comuns e armadilhas

- **Esquecer o `SetIdentifier`:** obrigatório em qualquer política que não seja Simple.
- **Pesos que parecem percentuais:** 90/10 funciona, mas 3/1 e 75/25 também; a soma não precisa ser 100.
- **Esperar divisão exata por requisição:** o cache do resolvedor concentra tráfego.
- **Health check ausente em Weighted/Multivalue:** o Route 53 continuará sorteando um alvo morto.
- **Confundir Multivalue com load balancer:** o cliente decide; não há reequilíbrio nem draining.
- **TTL longo em canary:** o rollback pode levar o mesmo tempo do TTL.
- **Misturar tipos de política com mesmo nome/tipo:** não é permitido combinar, por exemplo, Simple e Weighted para o mesmo nome e tipo.

## 🧩 Quiz de Fixação

1. Dois registros `api.exemplo.com.br` têm pesos 3 e 1. Qual a proporção esperada de respostas e o que acontece se o peso do segundo for 0?
2. Por que o Weighted do Route 53 pode não dividir exatamente 90/10 para um grupo pequeno de usuários, e como melhorar?
3. Qual a principal diferença entre Simple com vários valores e Multivalue Answer?

**Respostas:**
1) 75% e 25% (3/(3+1) e 1/(3+1)). Com peso 0 no segundo, ele deixa de receber tráfego e o primeiro recebe 100% (a menos que todos estejam em 0, quando o Route 53 responde igualmente).
2) A divisão é feita por **consulta DNS** e os resolvedores guardam o resultado pelo TTL; usuários atrás do mesmo resolvedor vão ao mesmo destino. Melhora-se com TTL baixo, amostras maiores e, para precisão por requisição, usando weighted target groups em um ALB.
3) Simple devolve **todos** os valores sem poder usar health checks; Multivalue devolve **até 8 registros saudáveis**, pois cada registro tem seu próprio health check e os doentes são removidos da resposta.
