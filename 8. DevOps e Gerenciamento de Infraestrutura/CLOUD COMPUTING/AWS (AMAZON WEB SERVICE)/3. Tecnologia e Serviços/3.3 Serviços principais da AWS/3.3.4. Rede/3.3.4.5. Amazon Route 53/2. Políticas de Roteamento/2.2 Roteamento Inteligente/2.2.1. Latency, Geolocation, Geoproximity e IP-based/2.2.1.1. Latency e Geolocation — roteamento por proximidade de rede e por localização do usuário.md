### Latency e Geolocation — roteamento por proximidade de rede e por localização do usuário

> [!warning] Aviso
> Preços por tipo de consulta, bancos de geolocalização e detalhes de APIs mudam. Confira a documentação do Route 53 ("Choosing a routing policy"). Os exemplos **não foram executados**.

Quando a aplicação roda em mais de uma região, surge a pergunta: **para qual região mandar cada usuário?** O Route 53 oferece duas respostas com critérios diferentes. **Latency** escolhe a região com **menor latência de rede** para o usuário (foco em desempenho). **Geolocation** escolhe pela **localização geográfica** do usuário (foco em regras: idioma, licenciamento, residência de dados). ## Latency-based routing

Você cria **um registro por região** onde a aplicação roda, cada um marcado com a **região AWS** correspondente. Ao receber a consulta, o Route 53 compara a latência medida entre o **local do usuário (a rede do resolvedor)** e cada região, e devolve o registro da região com **menor latência**.

```
 Usuário em São Paulo ─┐                    ┌─► sa-east-1   (latência ~15 ms)  ◄── escolhido
 Usuário em Lisboa    ─┼──► Route 53 ──────┼─► eu-west-1   (latência ~25 ms para Lisboa) 
 Usuário em Tóquio    ─┘   (tabela de       └─► ap-northeast-1
                            latências)
```

Pontos-chave:

- A decisão se baseia em **medições de latência da AWS entre redes de usuários e regiões**, e não em distância física. Uma região geograficamente mais longe pode ser a mais rápida.
- As medições mudam ao longo do tempo (por rotas de internet), então o mesmo usuário pode ser enviado a regiões diferentes em momentos distintos.
- É a política natural para **aplicações multi-região ativas** (active-active) quando o objetivo é desempenho.
- Combina bem com health checks: se a região mais próxima está doente, o Route 53 escolhe a próxima de menor latência.
- A latência é estimada pelo **resolvedor** que consulta (não pelo cliente final). Se o cliente usa um resolvedor distante (por exemplo, um DNS público em outro continente), a escolha pode ser subótima. O suporte a **EDNS0 client subnet** ajuda quando disponível.

### Exemplo

```json
{
  "Changes": [
    {
      "Action": "UPSERT",
      "ResourceRecordSet": {
        "Name": "app.exemplo.com.br",
        "Type": "A",
        "SetIdentifier": "sao-paulo",
        "Region": "sa-east-1",
        "AliasTarget": {
          "HostedZoneId": "Z0SAOPAULOALB",
          "DNSName": "alb-sp-111.sa-east-1.elb.amazonaws.com",
          "EvaluateTargetHealth": true
        }
      }
    },
    {
      "Action": "UPSERT",
      "ResourceRecordSet": {
        "Name": "app.exemplo.com.br",
        "Type": "A",
        "SetIdentifier": "virginia",
        "Region": "us-east-1",
        "AliasTarget": {
          "HostedZoneId": "Z0VIRGINIAALB",
          "DNSName": "alb-va-222.us-east-1.elb.amazonaws.com",
          "EvaluateTargetHealth": true
        }
      }
    }
  ]
}
```

Os `HostedZoneId` acima são marcadores; use o `CanonicalHostedZoneId` real de cada ALB. `Region` é o campo que ativa a política e informa a região do recurso; `EvaluateTargetHealth: true` tira da resposta uma região sem targets saudáveis.

## Geolocation routing

Roteia pela **localização do usuário**, determinada pelo IP do resolvedor (ou do cliente, com EDNS0) mapeado em um banco de geolocalização. Você define registros para **continente, país ou estado dos EUA**, e o Route 53 usa a regra **mais específica** que combine.

```
Usuário no Brasil  ──► regra "BR"            → ALB sa-east-1 (site em português)
Usuário em Portugal ─► regra "PT"            → ALB eu-west-1 (site PT-PT)
Usuário na Europa   ─► regra "EU" (continente)→ ALB eu-west-1
Qualquer outro      ─► regra "Default" (*)   → ALB us-east-1 (inglês)
```

Regras de precedência: estado dos EUA > país > continente > padrão (`*`). Sem registro que combine **e sem registro Default**, o Route 53 devolve resposta vazia (NODATA), e o usuário não resolve o nome. **Sempre crie um registro Default.**

### Usos típicos

- **Localização de conteúdo e idioma** por país.
- **Licenciamento e direitos de distribuição** (conteúdo só em certos países).
- **Residência de dados e compliance** (por exemplo, usuários da UE vão para a região da UE).
- **Balancear carga por região geográfica** com capacidade dimensionada por país.

### Exemplo

```json
{
  "Action": "UPSERT",
  "ResourceRecordSet": {
    "Name": "app.exemplo.com.br",
    "Type": "A",
    "SetIdentifier": "brasil",
    "GeoLocation": { "CountryCode": "BR" },
    "TTL": 60,
    "ResourceRecords": [{ "Value": "203.0.113.20" }]
  }
}
```

Para o padrão: `"GeoLocation": { "CountryCode": "*" }`. Para continente: `"ContinentCode": "EU"`. Para estado dos EUA: `"CountryCode": "US", "SubdivisionCode": "CA"`.

## Latency vs Geolocation

| Aspecto | Latency | Geolocation |
|---|---|---|
| Critério | Menor latência de rede medida | Localização geográfica do usuário |
| Objetivo | Desempenho | Regras de negócio, idioma, compliance |
| Previsível | Não (varia com a rede) | **Sim** (mesmo país, mesmo destino) |
| Garante a região "mais perto" | Mais rápida, nem sempre mais próxima | Não relaciona com desempenho |
| Necessário registro padrão | Não | **Sim**, para locais sem regra |
| Chave do registro | Região AWS | Continente, país ou estado dos EUA |
| Custo de consulta | Maior que Simple | Maior que Simple |

**Pergunta de prova clássica:** "usuários de cada país devem ver conteúdo específico" → Geolocation. "usuários devem ser atendidos pela região mais rápida" → Latency. "queremos dar mais ou menos tráfego a uma região, independentemente da localização" → Geoproximity com bias (próxima nota).

## Como o Route 53 decide: o caminho de uma consulta

```
 Usuário ─► resolver recursivo (ISP/8.8.8.8) ─► Route 53 (anycast, 4 name servers da hosted zone)
              └─ Latency:     escolhe a região com menor latência MEDIDA entre a rede do resolver e a região
              └─ Geolocation: escolhe pela LOCALIZAÇÃO do resolver/EDNS (país > continente > padrão)
 Resposta cacheada pelo resolver durante o TTL → novas consultas só após expirar
```

| Aspecto | Latency | Geolocation |
|---|---|---|
| Critério | Latência medida pela AWS | País/continente/estado (EUA) |
| Objetivo típico | Performance | Conformidade, idioma, licenciamento |
| Registro padrão | Não é obrigatório, mas recomendável | **Obrigatório** (`Default`) para quem não casa com nenhuma regra |
| Health check | Suportado (evita região doente) | Suportado |
| Precisão | Depende de medições; muda com o tempo | Depende do banco de geolocalização por IP |

> [!warning] Precisão da geolocalização, regiões elegíveis e preços mudam; confirme na documentação atual.

## Padrões combinados

| Padrão | Como montar |
|---|---|
| Multi-região com failover | Latency records por região, cada um com health check; região doente sai da resposta |
| Conteúdo regionalizado | Geolocation: `BR → site-br`, `Europa → site-eu`, `Default → site-global` |
| Bloqueio por país (conformidade) | Geolocation apontando o país para uma página de aviso ou registro sem alvo útil |
| Latency + Weighted | Árvore de registros: latency no topo e weighted dentro de cada região (Traffic Flow ou alias encadeado) |
| Teste A/B por região | Weighted dentro do ramo da região-alvo |

## Troubleshooting

| Sintoma | Causa provável | Ação |
|---|---|---|
| Usuário vai para região "errada" | Resolver público (8.8.8.8) está em outra região | Latency avalia o resolver; use EDNS Client Subnet quando suportado |
| País sem resposta (NXDOMAIN/vazio) | Sem registro `Default` na geolocation | Criar registro padrão |
| Mudança não aparece | TTL alto / cache | Reduzir TTL antes da mudança; aguardar expiração |
| Região fora do ar ainda recebe tráfego | Sem health check / `EvaluateTargetHealth` desligado | Associar health check ao registro |

## Custo

Cobrança por hosted zone, por consulta (políticas de latency e geolocation custam mais por milhão de consultas que o roteamento simples) e por health check. TTLs maiores reduzem o número de consultas.

## Erros comuns e armadilhas

- **Usar Geolocation para ganhar desempenho:** um usuário em país sem regra cai no Default, que pode estar do outro lado do mundo. Para desempenho, use Latency.
- **Esquecer o registro Default (`*`) em Geolocation:** usuários sem regra ficam sem resolução.
- **Achar que a geolocalização é exata:** bancos de IP têm erros (VPNs, CGNAT, resolvedores públicos). Não use como mecanismo único de **controle de acesso**; use WAF com geo-match ou regras da aplicação para bloqueio real.
- **Falta de health checks:** com Latency, o registro da região doente continua sendo devolvido.
- **Mistura de políticas no mesmo nome/tipo:** não é possível; use composição por aninhamento (Alias para outros conjuntos) ou Traffic Flow.
- **Não considerar o resolvedor:** DNS público em outro continente distorce Latency e Geolocation quando não há EDNS0.

## 🧩 Quiz de Fixação

1. Uma empresa tem o site em duas regiões e quer que cada usuário vá para a região que responde mais rápido. Qual política usar e o que cada registro precisa ter?
2. Uma plataforma de streaming só pode exibir um catálogo no Brasil e outro nos demais países. Como configurar?
3. Um usuário na Argentina não consegue resolver `app.exemplo.com.br` numa configuração Geolocation que só tem regras para BR e US. Qual a causa e a correção?

**Respostas:**
1) **Latency-based routing.** Cada registro precisa do campo **Region** (a região AWS do recurso) e de um **Set Identifier**, de preferência com Alias e `EvaluateTargetHealth` ou um health check para sair da resposta quando a região estiver doente.
2) **Geolocation:** um registro com `CountryCode: BR` apontando para o catálogo brasileiro e um registro **Default (`*`)** apontando para o catálogo internacional.
3) Não há regra para a Argentina nem registro **Default**, então o Route 53 não devolve resposta. A correção é criar o registro Default (`CountryCode: *`) ou uma regra para a Argentina/continente América do Sul.

### Questões de aprofundamento

4. Por que um usuário no Brasil pode ser atendido por us-east-1 em Latency routing?
5. O que acontece com usuários de um país sem regra em Geolocation e sem `Default`?
6. Como combinar proximidade e failover?

**Respostas:**
4) Porque a decisão usa a latência medida entre a rede do resolver e a região; um resolver público pode estar fora do Brasil, ou a rota medida pode ser melhor para os EUA.
5) Recebem resposta vazia (sem resolução); sempre crie o registro `Default`.
6) Registros de Latency por região com health check e `EvaluateTargetHealth`; a região doente deixa de ser candidata.
