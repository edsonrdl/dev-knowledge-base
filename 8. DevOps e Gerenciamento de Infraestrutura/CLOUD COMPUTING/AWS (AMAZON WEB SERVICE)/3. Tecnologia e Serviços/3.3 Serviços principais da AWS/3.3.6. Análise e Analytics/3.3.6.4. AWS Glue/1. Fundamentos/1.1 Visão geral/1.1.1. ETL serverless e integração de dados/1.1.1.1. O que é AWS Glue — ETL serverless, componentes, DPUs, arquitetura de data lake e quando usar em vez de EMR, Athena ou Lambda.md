### O que é AWS Glue — ETL serverless, componentes, DPUs, arquitetura de data lake e quando usar em vez de EMR, Athena ou Lambda

> [!warning] Aviso
> Versões do Glue, tipos de worker, preços por DPU-hora, limites e recursos (Data Quality, Ray, zero-ETL, streaming) mudam com frequência. Os números aqui são referências de estudo; confirme na documentação oficial. Os comandos e códigos são exemplos e **não foram executados**.

O **AWS Glue** é o serviço de **integração de dados serverless** da AWS. Ele **descobre**, **cataloga**, **transforma** e **move** dados entre fontes e destinos, **sem que você provisione ou administre servidores**. Em termos práticos, o Glue é a **cola** (daí o nome) que **liga os dados brutos espalhados** (bancos, arquivos, streams, SaaS) ao **data lake e aos serviços de análise** (Athena, Redshift, QuickSight, EMR).

Ele reúne **vários componentes** em um só serviço: um **catálogo de metadados** (Data Catalog), **descobridores automáticos** (crawlers), **jobs de ETL** em **Apache Spark**, **Python** e **Ray**, **orquestração** (triggers e workflows), **preparação visual de dados** (Glue Studio e DataBrew), **qualidade de dados** (Data Quality) e **registro de esquemas** (Schema Registry). Você **paga apenas pelo tempo de execução** (por **DPU-hora**), não por servidores ociosos.

**Analogia:** o Glue é a **equipe de logística e organização de uma grande biblioteca**. O **catálogo** é o **fichário** que diz onde está cada livro e como ele é organizado; os **crawlers** são os **bibliotecários que percorrem as estantes** e fazem as fichas sozinhos; os **jobs** são os **operários que reformatam, limpam e reorganizam** os livros (ETL); os **workflows** são o **cronograma** de quem faz o quê e quando; e a **qualidade de dados** é o **fiscal** que confere se os livros chegaram completos e corretos.

## ETL, ELT e integração de dados

| Termo | Significado |
|---|---|
| **ETL (Extract, Transform, Load)** | **Extrai** dados da origem, **transforma** (limpa, junta, enriquece) e **carrega** no destino |
| **ELT** | **Carrega primeiro** (no data lake/warehouse) e **transforma depois**, usando o poder do destino (SQL, Athena, Redshift) |
| **Integração de dados** | Termo mais amplo: **descobrir, preparar, combinar e mover** dados para análise, ML e aplicações |
| **Data lake** | Repositório (S3) de dados em **formato aberto**, com **catálogo** e **governança** |
| **Camadas (medallion)** | **Bronze** (bruto) → **Silver** (limpo) → **Gold** (agregado/negócio) |

```
 FONTES                     AWS GLUE                                  DESTINOS / CONSUMO
 ──────        ┌─────────────────────────────────────────┐        ──────────────────────
 RDS/Aurora ──►│ Crawlers  ─► DATA CATALOG (metadados)    │        Athena   (SQL no S3)
 S3 (CSV/JSON)─►│ Jobs ETL (Spark/Python/Ray) ─► transforma│─────►  Redshift (warehouse)
 DynamoDB ────►│ Workflows/Triggers (orquestração)        │        EMR      (Spark/Hive)
 Kinesis/MSK ─►│ Data Quality ─► valida                   │        QuickSight(BI)
 SaaS/JDBC ───►│ Schema Registry ─► versiona esquemas      │        SageMaker (ML)
               └─────────────────────────────────────────┘        S3 (data lake curado)
```

## Os componentes do Glue

| Componente | Função | Quando usar |
|---|---|---|
| **Glue Data Catalog** | **Catálogo central de metadados** (bancos, tabelas, partições, esquemas), compatível com **Hive Metastore** | Sempre que houver dados no S3 a consultar com Athena/Redshift Spectrum/EMR |
| **Crawlers** | **Varrem fontes** e **inferem esquemas**, criando/atualizando tabelas no catálogo | Descoberta automática de dados |
| **Classifiers** | Reconhecem **formatos** (CSV, JSON, Parquet, Avro, logs) ao rastrear | Formatos custom |
| **Connections** | **Configurações de conexão** (JDBC, MongoDB, Kafka, redes VPC) | Acesso a bancos e fontes privadas |
| **Jobs de ETL (Spark)** | **Processamento distribuído** em **PySpark/Scala** | Transformações de médio/grande volume |
| **Python shell jobs** | **Scripts Python** em uma máquina (pequenos) | Tarefas leves, chamadas de API |
| **Ray jobs** | Processamento distribuído **Python/Ray** | ML e Python em escala |
| **Streaming jobs** | **Spark Structured Streaming** lendo Kinesis/Kafka | ETL contínuo |
| **Glue Studio** | **Editor visual** de jobs (arrastar e soltar) + notebooks | Autoria visual e interativa |
| **Notebooks / Interactive Sessions** | Desenvolvimento interativo (Jupyter) | Prototipagem |
| **Triggers e Workflows** | **Orquestração** de crawlers e jobs (agendados, por evento, por dependência) | Pipelines simples no Glue |
| **Glue DataBrew** | **Preparação visual sem código** (250+ transformações) | Analistas de dados |
| **Glue Data Quality** | **Regras de qualidade** (DQDL) e pontuação | Confiabilidade de dados |
| **Sensitive Data Detection** | Detecta **PII** e age (mascarar, hash) | Privacidade/LGPD |
| **Schema Registry** | **Versiona e valida esquemas** (Avro, JSON, Protobuf) de streaming | Kafka/Kinesis com contratos |
| **Zero-ETL integrations** | **Replicação gerenciada** de fontes (Aurora, DynamoDB, SaaS) para o lake/warehouse | Menos pipelines para escrever |

## DPU: a unidade de capacidade e de custo

A **DPU (Data Processing Unit)** é a unidade de capacidade do Glue: **4 vCPUs e 16 GB** de memória (referência).

| Tipo de job | Capacidade mínima | Observações |
|---|---|---|
| **Spark (ETL)** | Mínimo de **2 DPUs** (varia por versão) | Workers G.1X (1 DPU), G.2X (2 DPUs), G.4X, G.8X, memória otimizada (R) |
| **Spark streaming** | A partir de **2 DPUs** | Execução contínua |
| **Python shell** | **0,0625 ou 1 DPU** | Muito barato para scripts leves |
| **Ray** | Workers específicos (Z.2X) | Python distribuído |
| **Crawlers** | Cobrança por **DPU-hora** (mínimos por execução) | Execuções curtas custam pouco |
| **Data Catalog** | **Gratuito até um milhão de objetos** e requisições (confirme) | Acima disso, por armazenamento e chamadas |
| **Interactive sessions** | Por DPU-hora durante a sessão | Encerrar ao terminar |

```
 custo do job ≈ DPUs × horas de execução × preço por DPU-hora   (faturamento por segundo, com mínimo)
```

| Opção de execução | Descrição |
|---|---|
| **Standard** | Capacidade disponível "agora" | 
| **Flex** | **Capacidade excedente** com **desconto**, para jobs **não urgentes** (pode atrasar o início) |
| **Auto Scaling** (Glue 3.0+) | Ajusta o **número de workers** durante a execução, até um máximo |
| **Versão do Glue** | 4.0/5.0 (Spark/Python/runtimes mais novos; melhor desempenho) |

> [!tip] Paga-se por tempo de execução, não por existência
> Um job que roda **10 minutos por noite** custa **10 minutos de DPUs**. Diferente de um cluster EMR sempre ligado, **não há custo de ociosidade**. Esse é o grande atrativo do modelo serverless para **pipelines em lote**.

## Glue vs EMR vs Athena vs Lambda vs Redshift

| Critério | **Glue** | **EMR** | **Athena** | **Lambda** | **Redshift** |
|---|---|---|---|---|---|
| **Modelo** | ETL **serverless** (Spark/Python) | **Clusters** gerenciados (Spark, Hive, Presto...) | **SQL** serverless sobre S3 | **Funções** por evento | **Data warehouse** |
| **Gestão** | **Nenhuma** de infraestrutura | Você dimensiona/gerencia clusters (ou EMR Serverless) | Nenhuma | Nenhuma | Média (ou Serverless) |
| **Melhor para** | **ETL/ELT em lote e streaming**, catálogo | Big data **customizado**, controle total, bibliotecas especiais | **Consultas ad hoc** e ELT em SQL | Transformações **leves** por evento (< 15 min) | **Análises SQL** intensas |
| **Linguagens** | **Python/Scala (Spark)**, SQL, visual | Qualquer ferramenta do ecossistema Hadoop | SQL | Várias | SQL |
| **Escala** | Dezenas a centenas de DPUs | **Muito alta**, customizável | Automática | Concorrência limitada | Nós/RPUs |
| **Custo** | **Por DPU-hora** (sem ociosidade) | Por instância/hora (ou por vCPU no Serverless) | Por TB escaneado | Por invocação | Por nó/RPU |
| **Controle** | Moderado | **Total** | Baixo | Moderado | Moderado |
| **Catálogo** | **Glue Data Catalog** | Pode usar o Glue Catalog | Usa o Glue Catalog | — | Spectrum usa o Catalog |

```
 Pipeline em lote ou streaming com Spark, sem gerenciar clusters?                ─► AWS Glue
 Precisa de controle fino do cluster, versões específicas, ferramentas Hadoop?    ─► Amazon EMR
 Consultas SQL ad hoc e ELT simples em SQL sobre o S3?                            ─► Amazon Athena (CTAS/INSERT)
 Transformação pequena disparada por evento (arquivo no S3)?                      ─► AWS Lambda
 Preparação visual sem código para analistas?                                     ─► Glue DataBrew
 Replicar dados de Aurora/DynamoDB sem escrever pipeline?                         ─► Zero-ETL (Glue/Redshift)
```

## Visão do fluxo típico

```
 1. CRAWLER descobre os arquivos brutos em s3://lake/bruto/  ─►  cria tabelas no DATA CATALOG
 2. JOB ETL (Spark) lê a tabela, limpa, junta, converte para PARQUET particionado
 3. DATA QUALITY valida regras (completude, unicidade, faixas)
 4. Grava em s3://lake/curado/  e atualiza o CATALOG (novas partições)
 5. ATHENA/REDSHIFT/QUICKSIGHT consultam a camada curada
 6. WORKFLOW/EventBridge/Step Functions orquestram e re-executam em caso de falha
```

## Primeiros comandos

```bash
# Bancos e tabelas do catálogo
aws glue get-databases --query 'DatabaseList[].Name'
aws glue get-tables --database-name lake --query 'TableList[].[Name,StorageDescriptor.Location]'

# Executa um crawler e um job
aws glue start-crawler --name crawler-bruto
aws glue start-job-run --job-name etl-pedidos --arguments '{"--dia":"2026-11-09"}'

# Acompanha a execução
aws glue get-job-run --job-name etl-pedidos --run-id jr_abc123 \
  --query 'JobRun.[JobRunState,ExecutionTime,DPUSeconds,ErrorMessage]'
```

```python
# Esqueleto de job Glue (PySpark)
import sys
from awsglue.transforms import *
from awsglue.utils import getResolvedOptions
from pyspark.context import SparkContext
from awsglue.context import GlueContext
from awsglue.job import Job

args = getResolvedOptions(sys.argv, ['JOB_NAME'])
sc = SparkContext()
glueContext = GlueContext(sc)
spark = glueContext.spark_session
job = Job(glueContext)
job.init(args['JOB_NAME'], args)

# Lê do catálogo, transforma e grava em Parquet particionado
dyf = glueContext.create_dynamic_frame.from_catalog(database="lake", table_name="bruto_pedidos")
df = dyf.toDF().filter("valor > 0").dropDuplicates(["pedido_id"])
df.write.mode("overwrite").partitionBy("ano", "mes").parquet("s3://meu-datalake/curado/pedidos/")

job.commit()
```

## Modelo de custo (referência)

| Item | Cobrança |
|---|---|
| **Jobs de ETL e streaming** | **DPU-hora** (por segundo, com mínimo) |
| **Python shell** | Fração de DPU-hora |
| **Crawlers** | DPU-hora (por execução, com mínimo) |
| **Interactive sessions e notebooks** | DPU-hora enquanto ativas |
| **Data Catalog** | Gratuito até uma franquia de objetos e requisições; depois, por armazenamento e chamadas |
| **Data Quality** | DPU-hora das avaliações |
| **DataBrew** | Por sessão/hora de interação e por jobs (nó-hora) |
| **Schema Registry** | Sem custo adicional (confirme) |
| **S3, KMS, CloudWatch, rede** | Pelos serviços usados |
| **Zero-ETL** | Conforme a integração |

> [!warning] Jobs esquecidos e sessões interativas ligadas custam
> **Sessões interativas** e notebooks **ligados** cobram **DPU-hora**; jobs com **timeout alto** e **loops** podem consumir DPUs por horas. Defina **timeouts**, **desligue sessões** e use **alarmes de custo**.

## Exemplo prático: de CSV bruto a Parquet no data lake

1. Os pedidos chegam em CSV ao bucket `s3://lake/bruto/pedidos/` todos os dias.
2. Um **crawler** noturno cataloga os dados em `bruto_pedidos` (detecta esquema e partições).
3. Um **job Spark** lê a tabela, remove duplicatas, converte tipos, calcula campos e grava **Parquet particionado** em `s3://lake/curado/pedidos/`.
4. O **Data Quality** valida: `pedido_id` único, `valor` > 0 e completude mínima de 99%.
5. Um **workflow** encadeia crawler → job → crawler da camada curada.
6. O **Athena** consulta a tabela curada; o **QuickSight** a usa em dashboards (SPICE).
7. Alarmes avisam de falhas; custos acompanham DPU-hora por job.

## Erros comuns e armadilhas

- **Usar Glue para tarefas muito pequenas** (Lambda ou Python shell bastariam).
- **Crawler em tudo, o tempo todo**, gerando custo e esquemas instáveis.
- **Deixar sessões interativas ligadas.**
- **Dimensionar DPUs "no chute"** sem medir (desperdício ou lentidão).
- **Gravar muitos arquivos pequenos** no S3.
- **Ignorar o catálogo** e referenciar caminhos S3 "na mão".
- **Sem versionamento de scripts** (jobs editados só no console).
- **Esperar que o Glue seja um orquestrador completo** (para fluxos complexos, use Step Functions/MWAA).

## 🧩 Quiz de Fixação

1. O que é o Glue Data Catalog?
2. Qual a unidade de capacidade e cobrança dos jobs do Glue?
3. Qual a função de um crawler?
4. Quando preferir EMR ao Glue?
5. O que são jobs Python shell?
6. Por que o modelo serverless do Glue é vantajoso para pipelines em lote?

**Respostas:**
1) Um catálogo central de metadados (bancos, tabelas, partições, esquemas), compatível com Hive Metastore, usado por Glue, Athena, EMR e Redshift Spectrum.
2) A DPU (Data Processing Unit), com cerca de 4 vCPUs e 16 GB; cobra-se por DPU-hora, por segundo.
3) Varrer fontes de dados, inferir esquemas e criar ou atualizar tabelas no Data Catalog automaticamente.
4) Quando é preciso controle fino do cluster, versões e ferramentas específicas do ecossistema Hadoop ou cargas muito customizadas.
5) Scripts Python executados em uma máquina com fração de DPU, para tarefas leves e baratas.
6) Porque se paga apenas pelo tempo de execução do job, sem custo de ociosidade de cluster nem administração de servidores.
