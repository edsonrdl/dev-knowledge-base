### Jobs de ETL no Glue — Spark, DynamicFrames, job bookmarks, Python shell, Ray, streaming, parâmetros, bibliotecas e padrões de transformação

> [!warning] Aviso
> Versões do Glue (e de Spark/Python), tipos de worker, parâmetros de job, APIs de transformação e conectores mudam. Os códigos e números aqui são referências de estudo; confirme na documentação. Os códigos e comandos **não foram executados**.

Os **jobs de ETL** são o **motor de transformação** do Glue: programas que **lêem dados de uma ou mais fontes**, **os transformam** (limpam, convertem, juntam, enriquecem, agregam) e **gravam o resultado** em um ou mais destinos. Eles rodam em **infraestrutura gerenciada e efêmera**: o Glue **provisiona workers**, **executa o job** e **libera os recursos** ao terminar. Esta folha cobre **os tipos de job** (Spark, Python shell, Ray, streaming), o **modelo de programação** (GlueContext, **DynamicFrame** e **DataFrame**), os **job bookmarks** (processamento incremental), os **parâmetros e bibliotecas**, os **padrões de transformação** e a **leitura e escrita eficientes** no S3.

**Analogia:** um job é uma **linha de montagem temporária**. Quando chega o pedido (execução), a fábrica **monta a linha com N operários (workers)**, processa o lote de matéria-prima, entrega o produto acabado e **desmonta tudo**. Você paga **só pelas horas de linha montada**. O **bookmark** é a **anotação "até aqui já processei"** para que, na próxima vez, a linha só cuide do material novo.

## Tipos de job

| Tipo | Motor | Quando usar | Capacidade |
|---|---|---|---|
| **Spark (ETL)** | Apache Spark (PySpark/Scala) | Transformações **distribuídas** de volume médio/grande | **Mínimo de 2 workers**; G.1X, G.2X, G.4X, G.8X, R (memória) |
| **Spark Streaming** | Spark Structured Streaming | ETL **contínuo** de Kinesis, Kafka/MSK | Execução permanente |
| **Python shell** | Python em **uma máquina** | Scripts **leves**, chamadas de API, orquestração simples | **0,0625 ou 1 DPU** |
| **Ray** | Ray (Python distribuído) | **ML** e Python em escala (pandas-like, bibliotecas de ciência de dados) | Workers Z.2X |
| **Visual (Glue Studio)** | Gera código Spark | Autoria **sem escrever código** | Como Spark |
| **Notebook / Interactive sessions** | Spark interativo | Desenvolvimento e depuração | DPU-hora enquanto ativo |

### Tipos de worker (referência)

| Worker | vCPU / Memória (aprox.) | Uso |
|---|---|---|
| **G.1X** | 4 vCPU / 16 GB (1 DPU) | **Padrão** para a maioria dos jobs |
| **G.2X** | 8 vCPU / 32 GB (2 DPUs) | Transformações mais pesadas, *shuffles* |
| **G.4X / G.8X** | 16 / 32 vCPU | Jobs muito pesados, junções grandes |
| **R.xX (memória otimizada)** | Mais memória por vCPU | Cargas com muito *shuffle*/cache |
| **Z.2X (Ray)** | Específico para Ray | Jobs Ray |

> [!tip] Comece pequeno e meça
> Rode com **G.1X** e **poucos workers**, observe **memória, CPU e tempo** no Spark UI/CloudWatch e só então **aumente**. Mais workers **não** ajudam se o gargalo é **uma partição gigante** ou **leitura do S3**.

## Modelo de programação do job Spark

```python
import sys
from awsglue.transforms import *
from awsglue.utils import getResolvedOptions
from pyspark.context import SparkContext
from awsglue.context import GlueContext
from awsglue.job import Job

args = getResolvedOptions(sys.argv, ['JOB_NAME', 'dia', 'destino'])
sc = SparkContext()
glueContext = GlueContext(sc)
spark = glueContext.spark_session
job = Job(glueContext)
job.init(args['JOB_NAME'], args)        # necessário para bookmarks

# 1) LEITURA (do catálogo, com push down de partição)
pedidos = glueContext.create_dynamic_frame.from_catalog(
    database="lake", table_name="bruto_pedidos",
    push_down_predicate=f"(dia == '{args['dia']}')",
    transformation_ctx="pedidos_src",          # identificador do bookmark
)

# 2) TRANSFORMAÇÃO
pedidos = ApplyMapping.apply(frame=pedidos, mappings=[
    ("pedido_id", "string", "pedido_id", "long"),
    ("valor", "string", "valor", "double"),
    ("criado_em", "string", "criado_em", "timestamp"),
], transformation_ctx="mapeamento")
df = pedidos.toDF().filter("valor > 0").dropDuplicates(["pedido_id"])

# 3) ESCRITA (Parquet particionado, no S3)
saida = DynamicFrame.fromDF(df, glueContext, "saida")
glueContext.write_dynamic_frame.from_options(
    frame=saida, connection_type="s3",
    connection_options={"path": args['destino'], "partitionKeys": ["dia"]},
    format="glueparquet", format_options={"compression": "snappy"},
    transformation_ctx="saida_sink",
)

job.commit()                               # grava o estado do bookmark
```

| Elemento | Função |
|---|---|
| **`GlueContext`** | Ponto de entrada do Glue (cria DynamicFrames, lê/escreve) |
| **`getResolvedOptions`** | Lê **parâmetros** do job (`--dia`, `--destino`) |
| **`Job.init` / `Job.commit`** | Inicia e **finaliza** o job; **commit** persiste o **bookmark** |
| **`transformation_ctx`** | Nome que **identifica a etapa** para **bookmarks e relatórios** |
| **`push_down_predicate`** | Filtro aplicado **na listagem de partições** (lê menos S3) |
| **Formato `glueparquet`** | Escritor Parquet **otimizado do Glue** (gravação em *streaming*, esquema dinâmico) |

## DynamicFrame vs DataFrame

O Glue acrescenta o **DynamicFrame**, uma abstração sobre o DataFrame do Spark pensada para **dados semiestruturados e esquemas variáveis**.

| Aspecto | **DynamicFrame** | **Spark DataFrame** |
|---|---|---|
| **Esquema** | **Auto-descritivo** por registro; tolera **tipos conflitantes** (`choice`) | Esquema **fixo** e conhecido |
| **Dados sujos** | **Resolve** com `ResolveChoice`, `Relationalize`, `DropNullFields` | Falha ou converte para `null` |
| **Transformações do Glue** | `ApplyMapping`, `Filter`, `Join`, `Map`, `SelectFields`, `Relationalize`, etc. | API Spark (SQL, funções) |
| **Desempenho** | Boa; para operações complexas, **converta para DataFrame** | **Otimizador Catalyst** completo |
| **Interoperabilidade** | `toDF()` / `DynamicFrame.fromDF()` | — |
| **Quando usar** | **Ingestão** de dados brutos/variáveis; funções específicas do Glue | **Transformações pesadas**, junções, SQL, UDFs |

```python
# Tipos conflitantes: coluna 'valor' ora número, ora texto  →  escolha como resolver
dyf = dyf.resolveChoice(specs=[("valor", "cast:double")])

# Achatar JSON aninhado em tabelas relacionais (tabelas filhas para arrays)
tabelas = Relationalize.apply(frame=dyf, staging_path="s3://meu-bucket/tmp/", name="pedido")

# Usar SQL do Spark depois de converter
df = dyf.toDF()
df.createOrReplaceTempView("pedidos")
resumo = spark.sql("SELECT dia, sum(valor) AS total FROM pedidos GROUP BY dia")
```

> [!tip] Padrão prático
> **Leia com DynamicFrame** (tolerância a esquema), **limpe com `ResolveChoice`/`ApplyMapping`**, **converta para DataFrame** para o trabalho pesado (joins, janelas, agregações) e **volte ao DynamicFrame** só se precisar de recursos do Glue na escrita.

## Job bookmarks: processamento incremental

Os **bookmarks** fazem o job **lembrar o que já processou**, de modo que cada execução leia **apenas dados novos** (sem reprocessar tudo).

| Aspecto | Detalhe |
|---|---|
| **Como funciona** | O Glue guarda **estado por `transformation_ctx`** (S3: arquivos/timestamps/ETags; JDBC: colunas-chave) |
| **Habilitar** | Parâmetro `--job-bookmark-option job-bookmark-enable` |
| **Opções** | `job-bookmark-enable` (usa), `job-bookmark-disable` (ignora), `job-bookmark-pause` (usa mas **não avança**) |
| **Fontes S3** | Considera **arquivos já processados** (por data de modificação) |
| **Fontes JDBC** | Requer **colunas ordenadas** (chave primária crescente, timestamp) |
| **Reset** | `aws glue reset-job-bookmark --job-name ...` para **reprocessar** |
| **Exigência** | `job.init()`/`job.commit()` e `transformation_ctx` **únicos e estáveis** |

```
 Execução 1: lê arquivos A, B, C  → bookmark salva estado (A,B,C processados)
 Execução 2: chegam D, E          → lê só D e E  → bookmark: A..E
 Execução 3 (falha antes do commit) → bookmark NÃO avança → reprocessa D, E (idempotência importa)
```

| Cuidado | Motivo |
|---|---|
| **Mudar `transformation_ctx`** | O Glue "esquece" o estado e **reprocessa tudo** |
| **Arquivos reescritos** (mesmo nome, nova data) | Podem ser relidos/duplicados |
| **Falhas parciais** | Bookmark só avança no **commit**: escrita deve ser **idempotente** |
| **Fontes sem ordem** (JDBC sem chave crescente) | Bookmark não funciona bem |
| **Sobrescrita total** | Combine com `mode("overwrite")` por partição ou Iceberg `MERGE` |

> [!warning] Bookmarks não garantem exatamente-uma-vez
> Se o job **falha depois de gravar** e **antes do commit**, a próxima execução **relê** os mesmos dados. Para evitar **duplicatas**, **grave de forma idempotente** (sobrescrever a partição, `MERGE`, chaves únicas).

## Padrões de transformação

| Padrão | Exemplo |
|---|---|
| **Limpeza** | `dropDuplicates`, `filter`, tratamento de nulos (`coalesce`, `fillna`) |
| **Conversão de tipos** | `ApplyMapping`, `cast` |
| **Achatamento de JSON** | `Relationalize`, `explode` |
| **Enriquecimento** | `join` com dimensões (broadcast para tabelas pequenas) |
| **Agregação** | `groupBy().agg()` para camada gold |
| **Deduplicação por chave e recência** | Janela `row_number()` ordenada por timestamp |
| **SCD / CDC** | `MERGE` em **Iceberg/Delta/Hudi**; aplicar eventos de mudança |
| **Mascaramento/PII** | `sha2`, `regexp_replace`, **Sensitive Data Detection** |
| **Particionamento de saída** | `partitionBy` por data |
| **Compactação** | `coalesce`/`repartition` para controlar nº de arquivos |

```python
from pyspark.sql import Window
from pyspark.sql.functions import row_number, col, broadcast

# Mantém o registro mais recente por pedido
w = Window.partitionBy("pedido_id").orderBy(col("atualizado_em").desc())
ultimos = df.withColumn("rn", row_number().over(w)).filter("rn = 1").drop("rn")

# Junção com dimensão pequena (broadcast evita shuffle caro)
enriq = ultimos.join(broadcast(dim_produto), "produto_id", "left")

# Controla o número de arquivos de saída (evita milhares de arquivos pequenos)
enriq.repartition(8).write.mode("overwrite").partitionBy("dia").parquet("s3://lake/curado/pedidos/")
```

## Leitura e escrita eficientes no S3

| Técnica | Efeito |
|---|---|
| **`push_down_predicate`** (partições) | Lê **só as partições necessárias** |
| **`groupFiles` / `groupSize`** | Agrupa **arquivos pequenos** em tarefas maiores |
| **Parquet/ORC (colunar) na entrada** | Menos bytes lidos |
| **Selecionar só as colunas** | Poda de colunas (*projection pushdown*) |
| **`optimizePerformance` do Glue Parquet** | Leitor vetorizado |
| **Evitar muitos arquivos pequenos de saída** | `repartition/coalesce` |
| **Tamanho ideal de arquivo** | ~128 MB a 1 GB |
| **Escrever com `glueparquet`** | Escrita otimizada com esquema dinâmico |
| **`enableUpdateCatalog`** | Atualiza o catálogo (novas partições) ao gravar |

```python
dyf = glueContext.create_dynamic_frame.from_options(
    connection_type="s3",
    connection_options={"paths": ["s3://lake/bruto/eventos/"], "recurse": True,
                        "groupFiles": "inPartition", "groupSize": "134217728"},   # 128 MB
    format="json", transformation_ctx="eventos",
)
```

## Streaming ETL

Jobs **Spark Structured Streaming** processam **fluxos contínuos** de **Kinesis Data Streams, Kafka e MSK**.

| Aspecto | Detalhe |
|---|---|
| **Fontes** | Kinesis, Kafka, MSK (inclusive MSK Serverless) |
| **Modelo** | **Micro-lotes** com `forEachBatch` e janela de processamento (ex.: 100 s) |
| **Esquema** | Do catálogo ou do **Schema Registry** (Avro/JSON) |
| **Checkpoint** | Em S3 (`checkpointLocation`) para retomar |
| **Destinos** | S3 (Parquet/Iceberg), Redshift, OpenSearch, JDBC, etc. |
| **Execução** | **Permanente** (sempre ligado) → custo contínuo de DPUs |
| **Comparação** | Para **carga simples** em S3, o **Firehose** é mais barato e simples |

```python
dados = glueContext.create_data_frame.from_catalog(
    database="lake", table_name="stream_pedidos",
    additional_options={"startingPosition": "TRIM_HORIZON", "inferSchema": "true"})

def processar_lote(df, batch_id):
    if df.count() > 0:
        dyf = DynamicFrame.fromDF(df, glueContext, "lote")
        glueContext.write_dynamic_frame.from_options(
            frame=dyf, connection_type="s3",
            connection_options={"path": "s3://lake/curado/pedidos_stream/", "partitionKeys": ["dia"]},
            format="glueparquet")

glueContext.forEachBatch(frame=dados, batch_function=processar_lote,
    options={"windowSize": "60 seconds", "checkpointLocation": "s3://meu-bucket/chk/pedidos/"})
```

> [!tip] Streaming no Glue vs Firehose vs Flink
> **Só carregar no S3?** **Firehose**. **Transformar com Spark e gravar em Iceberg/Hudi com lógica complexa?** **Glue Streaming**. **Janelas, estado e latência de ms?** **Flink**.

## Exemplo prático: pipeline diário idempotente

1. O job recebe `--dia=2026-11-09` e lê **só essa partição** do bruto (`push_down_predicate`).
2. Limpa e **deduplica** por `pedido_id` (mantém a versão mais recente).
3. Converte tipos e **valida** campos obrigatórios; registros inválidos vão a uma tabela de **quarentena**.
4. Grava em **Parquet particionado**, **sobrescrevendo apenas a partição do dia** (idempotente) com **~8 arquivos** por partição.
5. Atualiza o **catálogo** (`enableUpdateCatalog`) e emite métricas.
6. Em falha, o job pode ser **reexecutado** para o mesmo dia **sem duplicar** dados.
7. Um **backfill** de 30 dias roda o mesmo job com datas diferentes, em paralelo controlado.

## Troubleshooting

| Sintoma | Causa provável | Como resolver |
|---|---|---|
| **`OutOfMemoryError`** | Partições grandes, *shuffle* pesado, coleta no driver | Worker G.2X/R; mais partições; evitar `collect()`/`toPandas()` |
| **Job muito lento** | Muitos arquivos pequenos, skew, poucas partições | `groupFiles`; `repartition`; tratar *skew* |
| **Job reprocessa tudo** | Bookmark desabilitado ou `transformation_ctx` mudou | Habilitar; fixar contextos; não resetar sem querer |
| **Duplicatas na saída** | Falha após gravar, antes do commit | Escrita idempotente (overwrite/`MERGE`) |
| **`Access Denied` no S3/KMS** | Role do job | Ajustar permissões (inclusive KMS) |
| **Job em VPC não acessa S3/Glue** | Sem endpoint/NAT | Endpoints de S3 e Glue; rota |
| **Muitos arquivos pequenos na saída** | Muitas partições Spark × partições de dados | `repartition/coalesce` antes de gravar |
| **Erro de tipo/`choice`** | Dados sujos | `ResolveChoice`, `ApplyMapping`, validar |
| **Timeout** | Job longo ou travado | Ver Spark UI; otimizar; ajustar timeout |
| **Streaming sem processar** | Checkpoint/permissões/posição inicial | Verificar `startingPosition`, checkpoint, acesso ao stream |
| **Dependência Python não encontrada** | Módulo ausente | `--additional-python-modules`; wheel no S3 |
| **Custo alto** | Workers demais, jobs longos, sessões abertas | Medir; auto scaling; Flex; timeouts |

## Erros comuns e armadilhas

- **Mudar o `transformation_ctx`** e reprocessar tudo sem perceber.
- **Confiar em bookmarks** como garantia de exatamente-uma-vez.
- **`collect()`/`toPandas()` em dados grandes.**
- **Gravar milhares de arquivos pequenos** por falta de `repartition`.
- **Usar DynamicFrame para tudo** (e perder o otimizador do Spark).
- **Não definir timeouts** nem `max-retries`.
- **Jobs sem parâmetros** (datas fixas no código).
- **Usar Glue Streaming** onde o Firehose bastaria.

## 🧩 Quiz de Fixação

1. Qual a diferença entre DynamicFrame e DataFrame?
2. Para que servem os job bookmarks?
3. Qual a função do `transformation_ctx`?
4. Quando usar Python shell em vez de Spark?
5. Como evitar duplicatas quando um job falha depois de gravar?
6. O que faz o `push_down_predicate`?

**Respostas:**
1) O DynamicFrame tem esquema auto-descritivo e tolera tipos conflitantes (choice), útil para dados brutos; o DataFrame tem esquema fixo e o otimizador completo do Spark, melhor para transformações pesadas.
2) Guardar o estado do que já foi processado para que cada execução leia apenas dados novos (processamento incremental).
3) Identificar cada etapa do job para bookmarks e relatórios; mudá-lo faz o Glue esquecer o estado.
4) Para tarefas leves e baratas, como chamar APIs ou executar scripts pequenos, que não precisam de processamento distribuído.
5) Gravando de forma idempotente: sobrescrevendo a partição, usando MERGE em formatos transacionais ou chaves únicas, pois o bookmark só avança no commit.
6) Filtra partições na listagem do catálogo, de modo que o job leia apenas as partições necessárias do S3.
