### Glue Data Catalog e crawlers — bancos, tabelas, partições, classifiers, evolução de esquema, connections, Schema Registry e estatísticas de colunas

> [!warning] Aviso
> Limites de objetos, comportamentos de crawlers, opções de política de esquema, formatos de tabela suportados e preços mudam. Os exemplos aqui são referências de estudo; confirme na documentação. Os comandos **não foram executados**.

O **Glue Data Catalog** é o **coração de metadados** do data lake na AWS: um **repositório central e persistente** que diz **quais dados existem, onde estão, em que formato e com quais colunas**. Quem consulta com **Athena**, **Redshift Spectrum**, **EMR**, **Glue ETL** ou **Lake Formation** usa **o mesmo catálogo**. Os **crawlers** são os **robôs que preenchem esse catálogo automaticamente**, descobrindo esquemas e partições. Esta folha cobre o **modelo do catálogo**, **como os crawlers funcionam e como configurá-los bem**, a **evolução de esquema**, as **conexões**, o **Schema Registry** e as **estatísticas de colunas**.

**Analogia:** o catálogo é o **fichário de uma biblioteca** (autor, título, estante, formato). Os **crawlers** são **bibliotecários que passam pelas prateleiras** e **atualizam as fichas** quando chegam livros novos. Se a ficha diz "romance, 300 páginas" mas o livro mudou para "ensaio", as **consultas quebram**: por isso a **política de evolução de esquema** importa.

## Modelo do catálogo

```
 Data Catalog (por conta e região)
 └── Database "lake"                          (agrupamento lógico, um "schema")
      ├── Table "curado_pedidos"              (definição sobre dados no S3 ou outra fonte)
      │    ├── colunas: pedido_id bigint, valor double, ...
      │    ├── partition keys: ano, mes, dia
      │    ├── storage descriptor: LOCATION s3://lake/curado/pedidos/ ; InputFormat/SerDe: Parquet
      │    └── partitions: ano=2026/mes=11/dia=09 ...   (cada uma com seu LOCATION)
      └── Table "bruto_clientes" ...
```

| Objeto | Descrição |
|---|---|
| **Database** | Contêiner lógico de tabelas (equivale a um *schema* do Hive) |
| **Table** | **Metadados**: colunas, tipos, formato (SerDe), local, **partition keys**, propriedades |
| **Partition** | Subconjunto da tabela mapeado a um **caminho do S3** (ex.: `ano=2026/mes=11/`) |
| **Connection** | Dados de acesso (JDBC, Kafka, MongoDB, rede VPC) |
| **Crawler** | Descobre dados e **cria/atualiza** tabelas e partições |
| **Classifier** | **Regras de reconhecimento de formato** usadas pelo crawler |
| **Schema (Registry)** | **Esquemas versionados** de streaming (Avro, JSON, Protobuf) |
| **Resource policy / Lake Formation** | Controle de acesso e compartilhamento do catálogo |

| Característica | Detalhe |
|---|---|
| **Compatível com Hive Metastore** | Ferramentas do ecossistema Hadoop/Spark usam o catálogo |
| **Região e conta** | Um catálogo **por conta e região**; compartilhável via **Lake Formation/RAM** |
| **Tipos de tabela** | **Hive externas**, **Iceberg**, **Hudi**, **Delta** (metadados), **views** do Athena/Glue |
| **Versões de tabela** | O catálogo guarda **versões** do esquema para consulta e auditoria |
| **Custo** | Gratuito até uma franquia de objetos/requisições (confirme); depois cobra |

> [!tip] O catálogo é infraestrutura compartilhada
> Uma alteração de esquema afeta **todos os consumidores** (Athena, Spark, Redshift, BI). Trate o catálogo como **contrato de dados**: **mudanças revisadas**, **versionadas** e **comunicadas**.

## Crawlers: como funcionam

```
 Crawler ──► conecta à fonte (S3, JDBC, DynamoDB, MongoDB...)
        ──► amostra os dados / lê metadados
        ──► aplica CLASSIFIERS (built-in e custom) para inferir formato e esquema
        ──► compara com o catálogo existente
        ──► cria/atualiza tabelas e partições (conforme a política de esquema)
        ──► agenda/registra métricas e logs
```

| Etapa | Detalhe |
|---|---|
| **Fonte (target)** | S3, **JDBC** (RDS, Redshift, outros), **DynamoDB**, **MongoDB/DocumentDB**, **Delta/Iceberg/Hudi**, Catalog tables |
| **Classificação** | **Classifiers built-in** (CSV, JSON, Parquet, ORC, Avro, XML, logs) e **customizados** (Grok, XML, JSON path, CSV com delimitador) |
| **Esquema** | Infere colunas e tipos; trata **partições** por estrutura de pastas (`chave=valor/`) |
| **Saída** | Tabelas no catálogo, em um **database** e com **prefixo** opcional |
| **Execução** | **Sob demanda**, **agendada** ou **por evento** (S3 event notifications) |
| **Custo** | **DPU-hora** (por execução, com mínimo) |

```bash
# Cria um crawler para o bucket bruto
aws glue create-crawler --name crawler-bruto \
  --role arn:aws:iam::123456789012:role/GlueCrawlerRole \
  --database-name lake --table-prefix bruto_ \
  --targets '{"S3Targets":[{"Path":"s3://meu-datalake/bruto/","Exclusions":["**/_temporary/**","**.tmp"]}]}' \
  --schedule "cron(0 3 * * ? *)" \
  --schema-change-policy '{"UpdateBehavior":"UPDATE_IN_DATABASE","DeleteBehavior":"LOG"}' \
  --recrawl-policy '{"RecrawlBehavior":"CRAWL_NEW_FOLDERS_ONLY"}'
```

### Configurações que mais importam

| Configuração | Opções | Recomendação |
|---|---|---|
| **Política de recrawl** | `CRAWL_EVERYTHING`, **`CRAWL_NEW_FOLDERS_ONLY`**, `CRAWL_EVENT_MODE` | **Só novas pastas** ou **por evento** em lakes grandes (mais barato e rápido) |
| **UpdateBehavior** | `UPDATE_IN_DATABASE` (atualiza), `LOG` (só registra) | `LOG` em produção estável; atualize de forma controlada |
| **DeleteBehavior** | `DEPRECATE_IN_DATABASE`, `DELETE_FROM_DATABASE`, `LOG` | **Evite excluir** automaticamente |
| **Tamanho da amostra** | Amostragem de arquivos por pasta | Aumentar se esquemas variam |
| **Exclusões** (`Exclusions`) | Padrões glob | Ignorar temporários, `_SUCCESS`, `_$folder$` |
| **Criar uma tabela por pasta?** | `TableGroupingPolicy: CombineCompatibleSchemas` | Evita explosão de tabelas |
| **Configuração de partição** | Detecta partições e **mesmo esquema** | Evita divergência |
| **Políticas de nomes** | Prefixo de tabela | Padronização |
| **Compatibilidade com Lake Formation** | Permissões da role do crawler | Conceder acesso no LF |

> [!warning] Crawlers podem "mudar o esquema" sem aviso
> Se um arquivo novo chega com **coluna extra** ou **tipo diferente**, um crawler com `UPDATE_IN_DATABASE` **altera a tabela**, e **consultas e jobs** podem **quebrar** ou **retornar nulos**. Em produção, prefira **esquemas definidos por DDL/IaC** e use o crawler com `LOG` para **detectar** mudanças e **alertar**.

### Quando usar (e quando não) crawlers

| Use crawler quando... | Evite crawler quando... |
|---|---|
| **Descoberta inicial** de dados desconhecidos | O esquema é **conhecido e estável** (use **DDL/IaC**) |
| Fontes com **esquema variável** e catalogação ocasional | Há **muitas partições** (use **partition projection** no Athena) |
| **Prototipagem** | Quer **controle fino** do esquema |
| Você precisa **acompanhar mudanças** (modo LOG) | O pipeline já **grava no catálogo** (jobs Spark atualizam partições) |

```
 Alternativas ao crawler para manter partições:
   • Job Spark grava com enableUpdateCatalog=true (atualiza partições ao gravar)
   • MSCK REPAIR TABLE / ALTER TABLE ADD PARTITION (Athena)
   • Partition projection (Athena) – sem registrar partições
   • Eventos S3 → Lambda → BatchCreatePartition
```

## Classifiers

Os **classifiers** dizem ao crawler **como ler** os arquivos:

| Tipo | Uso |
|---|---|
| **Built-in** | CSV, JSON, Parquet, ORC, Avro, XML, logs comuns, banco JDBC |
| **Grok** | Padrões de **logs de texto** (Apache, aplicações) |
| **XML** | Define a **tag de linha** (`RowTag`) |
| **JSON** | **JSON path** para o array/objeto de linhas |
| **CSV customizado** | Delimitador, cabeçalho, aspas, tipos |

```bash
aws glue create-classifier --csv-classifier '{
  "Name":"csv-ponto-virgula","Delimiter":";","QuoteSymbol":"\"","ContainsHeader":"PRESENT",
  "AllowSingleColumn":false}'
```

## Tipos de dados e evolução de esquema

| Tema | Comportamento |
|---|---|
| **Inferência de tipos** | Pode divergir entre arquivos (`int` vs `string`); o crawler escolhe um tipo "ampliado" ou cria `struct`/`choice` |
| **Colunas adicionadas** | Em Parquet/ORC/Avro/JSON, novas colunas aparecem; em CSV, **ordem importa** |
| **Colunas removidas ou renomeadas** | Em Hive/Parquet, renomear quebra leitura por posição/nome; Iceberg suporta evolução segura |
| **`choice` types (DynamicFrame)** | O Glue ETL representa tipos ambíguos como `choice` e resolve com `ResolveChoice` |
| **Arquivos com esquemas diferentes na mesma tabela** | Podem gerar erros de leitura ou nulos |
| **Formatos com evolução nativa** | **Iceberg** (add/drop/rename/reorder), Avro com Schema Registry |

| Estratégia | Detalhe |
|---|---|
| **Contratos de dados** | Esquemas **explícitos e versionados**; mudanças **aditivas e compatíveis** |
| **Schema-on-read com tolerância** | Aceitar colunas extras, tipos amplos (`string`) na camada bruta |
| **Camada curada estrita** | Esquemas fixos; falhar se fugir do contrato |
| **Versões de tabela** | Auditar mudanças (`GetTableVersions`) |
| **Alertas** | EventBridge para eventos de mudança no catálogo |

```bash
aws glue get-table-versions --database-name lake --table-name bruto_pedidos \
  --query 'TableVersions[].[VersionId,Table.UpdateTime,Table.StorageDescriptor.Columns[].Name]'
```

## Partições no catálogo

| Aspecto | Detalhe |
|---|---|
| **Papel** | Permite **poda de partições** (Athena, Spark) pela estrutura de pastas |
| **Registro** | Crawler, `MSCK REPAIR`, `BatchCreatePartition`, jobs com `enableUpdateCatalog` |
| **Escala** | Centenas de milhares de partições **degradam** o planejamento (use **partition indexes** ou **projection**) |
| **Partition indexes** | **Índices** do catálogo que aceleram `GetPartitions` com filtros |
| **Filtro no servidor** | `GetPartitions` com `Expression` evita trazer todas |

```bash
# Cria um índice de partição (acelera consultas com filtros por ano/mes)
aws glue create-partition-index --database-name lake --table-name curado_pedidos \
  --partition-index '{"Keys":["ano","mes"],"IndexName":"idx_ano_mes"}'

# Registra partições em lote
aws glue batch-create-partition --database-name lake --table-name curado_pedidos \
  --partition-input-list file://particoes.json
```

> [!tip] Menos partições, mais desempenho
> Particione por **data (dia ou mês)** e, no máximo, **mais uma coluna de baixa cardinalidade**. Partições com **poucos MB** geram **muitos arquivos pequenos** e sobrecarregam o catálogo.

## Connections

As **conexões** guardam **como acessar fontes externas**:

| Tipo | Uso |
|---|---|
| **JDBC** | Bancos relacionais (MySQL, PostgreSQL, Oracle, SQL Server, Redshift) |
| **Kafka / MSK** | Streaming |
| **MongoDB / DocumentDB** | NoSQL |
| **Network** | Apenas **configuração de rede** (VPC, subnet, security group) para jobs acessarem recursos privados |
| **Conectores do Marketplace / customizados** | Fontes especializadas |
| **SaaS (AppFlow-like)** | Salesforce, SAP, etc., via conectores gerenciados |

| Cuidado | Motivo |
|---|---|
| **Credenciais no Secrets Manager** | Sem senhas em texto |
| **VPC com acesso ao S3 (endpoint) e ao Glue** | Jobs em VPC precisam alcançar S3, catálogo e CloudWatch |
| **Security groups com regra de auto-referência** | Exigência para comunicação entre workers |
| **Conexão por AZ/subnet** | O job usa a AZ da conexão: planejar capacidade de IPs |
| **Testar a conexão** | Evita falhas em produção |

## Schema Registry

O **Glue Schema Registry** **gerencia e valida esquemas** de **dados em streaming** (Kinesis, MSK, Kafka), evitando que produtores publiquem dados **incompatíveis**.

| Elemento | Descrição |
|---|---|
| **Registry** | Agrupamento de schemas |
| **Schema** | Definição **versionada** (Avro, JSON Schema, Protobuf) |
| **Compatibilidade** | `BACKWARD`, `FORWARD`, `FULL`, `NONE` etc. (regras de evolução) |
| **SerDes** | Bibliotecas que **serializam/desserializam** com o ID do schema embutido |
| **Integrações** | KPL/KCL, Kafka clients, Flink, Glue Streaming, Lambda |

```
 Produtor ──(serializa com schema v3, ID no cabeçalho)──► Stream ──► Consumidor (busca o schema pelo ID e desserializa)
                 │
                 └─ Registry valida: v3 é BACKWARD compatível com v2? (se não, rejeita)
```

| Vantagem | Efeito |
|---|---|
| **Contratos entre equipes** | Menos quebras por mudanças inesperadas |
| **Evolução controlada** | Campos opcionais e valores padrão |
| **Menor payload** | Esquema não trafega em cada mensagem |
| **Governança** | Histórico de versões |

## Estatísticas de colunas e otimizações do catálogo

| Recurso | Função |
|---|---|
| **Column statistics** | Calcula **estatísticas** (valores distintos, nulos, min/max, tamanho médio) por tabela |
| **Uso** | **Athena/Redshift Spectrum** usam para **melhores planos de junção** |
| **Compactação automática** (tabelas Iceberg) | O catálogo **compacta arquivos pequenos** automaticamente |
| **Remoção de snapshots órfãos** | Limpeza de dados antigos em Iceberg |
| **Otimizadores de tabela** | Compaction, retention e orphan file deletion gerenciados |

```bash
aws glue start-column-statistics-task-run --database-name lake --table-name curado_pedidos \
  --role arn:aws:iam::123456789012:role/GlueStatsRole --sample-size 100
```

## Segurança e compartilhamento do catálogo

| Mecanismo | Uso |
|---|---|
| **IAM** | Acesso às APIs do Glue (`glue:GetTable` etc.) |
| **Lake Formation** | Permissões por **banco, tabela, coluna, linha** e **LF-Tags** |
| **Resource policies** | Compartilhamento do catálogo entre contas |
| **Criptografia do catálogo** | **KMS** para metadados e senhas de conexões |
| **Resource links** | Referências a bancos/tabelas **de outra conta** |
| **Auditoria** | CloudTrail e logs do Lake Formation |

> [!tip] Compartilhe com Lake Formation, não copiando
> Em organizações multi-conta, **uma conta produtora** mantém o catálogo e **compartilha** bancos/tabelas via **Lake Formation** com contas consumidoras, que criam **resource links**. Evita **duplicar** metadados e divergência.

## Exemplo prático: catálogo organizado de um data lake

1. Camadas em bancos separados: **`bruto`**, **`curado`**, **`analitico`**.
2. **Bruto**: crawler com `CRAWL_NEW_FOLDERS_ONLY` e política `LOG` para esquemas; tudo como `string`/tipos amplos.
3. **Curado**: tabelas **criadas por DDL/IaC** (Parquet particionado por dia), com esquemas estritos; jobs gravam com `enableUpdateCatalog`.
4. **Partition indexes** nas tabelas grandes; **column statistics** semanais.
5. **Schema Registry** para os eventos de streaming; compatibilidade **BACKWARD**.
6. **Lake Formation** concede acesso por **LF-Tags** (domínio, sensibilidade); contas consumidoras usam **resource links**.
7. **EventBridge** alerta para mudanças de esquema inesperadas no bruto; um painel mostra tabelas sem donos.

## Troubleshooting

| Sintoma | Causa provável | Como resolver |
|---|---|---|
| **Crawler cria tabelas demais** | Cada pasta com esquema ligeiramente diferente | `CombineCompatibleSchemas`; ajustar caminho/exclusões |
| **Crawler muda o esquema** e quebra consultas | `UPDATE_IN_DATABASE` em produção | Usar `LOG`; DDL/IaC; revisar mudanças |
| **Crawler lento/caro** | `CRAWL_EVERYTHING` em lake enorme | `CRAWL_NEW_FOLDERS_ONLY` ou por evento |
| **Tipos "inconsistentes"/`choice`** | Arquivos com tipos diferentes | Padronizar produtores; `ResolveChoice` no ETL |
| **Tabela sem partições** | Estrutura de pastas fora do padrão `chave=valor/` | Ajustar estrutura/registrar partições manualmente |
| **Athena retorna zero linhas** | Partições não registradas | `MSCK REPAIR`, crawler, projection |
| **`AccessDenied` no crawler** | Role sem acesso ao S3/KMS/Lake Formation | Ajustar permissões |
| **Conexão JDBC falha** | VPC, security group, credenciais | Testar conexão; liberar portas; Secrets Manager |
| **Job em VPC "preso"** | Falta endpoint S3 ou rota para Glue | Criar endpoints/NAT |
| **`GetPartitions` lento** | Muitas partições | Partition indexes; projection; menos partições |
| **Schema Registry rejeita mensagem** | Esquema incompatível | Corrigir produtor; revisar compatibilidade |
| **Catálogo "poluído"** | Tabelas órfãs/duplicadas | Governança: donos, limpeza, nomes |

## Erros comuns e armadilhas

- **Depender de crawlers em produção** sem controle de mudanças de esquema.
- **Não excluir arquivos temporários** do alcance do crawler.
- **Particionar demais** e sobrecarregar o catálogo.
- **Esquemas diferentes na mesma tabela** sem estratégia.
- **Credenciais de bancos em texto** em connections.
- **Catálogos duplicados por conta** em vez de compartilhar.
- **Esquecer partition indexes/projection** em tabelas gigantes.
- **Sem donos e sem documentação** das tabelas do catálogo.

## 🧩 Quiz de Fixação

1. O que armazena o Glue Data Catalog?
2. Qual a diferença entre `CRAWL_EVERYTHING` e `CRAWL_NEW_FOLDERS_ONLY`?
3. Por que cuidado com `UPDATE_IN_DATABASE` em produção?
4. Para que serve o Schema Registry?
5. O que são partition indexes?
6. Como compartilhar o catálogo entre contas?

**Respostas:**
1) Metadados: bancos, tabelas, partições, esquemas e propriedades dos dados, sem armazenar os dados em si.
2) O primeiro rastreia tudo a cada execução; o segundo só pastas novas, sendo mais rápido e barato em data lakes grandes.
3) Porque o crawler pode alterar o esquema automaticamente ao encontrar arquivos diferentes, quebrando consultas e jobs; em produção prefere-se DDL/IaC e o modo LOG para alertar.
4) Gerenciar e validar esquemas versionados de dados em streaming, impondo regras de compatibilidade entre produtores e consumidores.
5) Índices do catálogo que aceleram a busca de partições com filtros, melhorando o planejamento em tabelas com muitas partições.
6) Com Lake Formation (e políticas de recurso/RAM), compartilhando bancos e tabelas da conta produtora e usando resource links nas contas consumidoras.
