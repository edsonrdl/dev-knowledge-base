### Orquestração e qualidade no Glue — triggers, workflows, Step Functions, Glue Studio, DataBrew, Data Quality com DQDL e detecção de dados sensíveis

> [!warning] Aviso
> Recursos de orquestração, sintaxe do DQDL, tipos de regra, limites de workflows e preços mudam. Os exemplos aqui são referências de estudo; confirme na documentação. Os comandos e regras **não foram executados**.

Um job isolado raramente é um pipeline. Pipelines reais **encadeiam etapas** (descobrir, transformar, validar, publicar), **reagem a eventos** (chegou arquivo, terminou outro job), **tratam falhas** e **garantem que dados ruins não cheguem ao consumidor**. O Glue oferece **ferramentas próprias** para isso: **triggers e workflows** (orquestração simples), integração com **Step Functions, EventBridge e MWAA** (orquestração avançada), **Glue Studio** (autoria visual), **DataBrew** (preparação sem código), **Data Quality** (regras de qualidade em **DQDL**) e **Sensitive Data Detection** (privacidade). Esta folha cobre **quando usar cada uma** e como **construir pipelines confiáveis**.

**Analogia:** uma **linha de produção de alimentos**. O **cronograma** (triggers e workflows) define a **ordem das estações**; o **inspetor de qualidade** (Data Quality) **rejeita lotes fora do padrão** antes da embalagem; o **departamento de privacidade** (Sensitive Data Detection) **remove ingredientes controlados**; e a **estação de preparo sem fogão** (DataBrew) deixa **quem não programa** limpar e padronizar ingredientes visualmente.

## Triggers

Um **trigger** **inicia** jobs e crawlers.

| Tipo | Como dispara | Uso |
|---|---|---|
| **Agendado (SCHEDULED)** | **Cron/rate** | Rotinas noturnas |
| **Sob demanda (ON_DEMAND)** | **Manual** ou por API | Testes, backfills, orquestração externa |
| **Condicional (CONDITIONAL)** | Quando **jobs/crawlers anteriores** terminam com certo **estado** (SUCCEEDED, FAILED) | Dependências simples |
| **Por evento (EVENT)** | Evento do **EventBridge** (chegada de objeto S3, etc.) em workflows | Pipelines orientados a dados |

```bash
aws glue create-trigger --name apos-crawler --type CONDITIONAL \
  --predicate '{"Logical":"AND","Conditions":[{"LogicalOperator":"EQUALS","CrawlerName":"crawler-bruto","CrawlState":"SUCCEEDED"}]}' \
  --actions '[{"JobName":"etl-pedidos"}]' --start-on-creation
```

| Cuidado | Motivo |
|---|---|
| **Condição `SUCCEEDED` vs `FAILED`** | Defina tratamento de falha, não só do caminho feliz |
| **Dependências longas** | Triggers condicionais crescem em complexidade; prefira **workflows** |
| **Agendamentos sobrepostos** | Duas execuções do mesmo job; use **concorrência máxima** (`MaxConcurrentRuns`) |
| **Fuso horário** | Cron do Glue usa **UTC** |

## Workflows

Um **workflow** do Glue é um **grafo (DAG)** de **triggers, crawlers e jobs**, executado como **uma unidade**, com **propriedades compartilhadas** e **visão gráfica** do progresso.

```
 [Trigger agendado 02:00]
        │
        ▼
 [Crawler bruto] ──SUCCEEDED──► [Job ETL pedidos] ──SUCCEEDED──► [Job ETL clientes] ──┐
                                      │FAILED                                          ▼
                                      └─────────► [Job de notificação de falha]   [Crawler curado]
```

| Recurso | Descrição |
|---|---|
| **Run properties** | Pares chave/valor **compartilhados** entre os nós (ex.: `dia`) |
| **Visão do grafo** | Estado de cada nó, tempos, erros |
| **Reexecução (resume)** | Retomar a partir do **nó com falha** |
| **Máx. de execuções simultâneas** | Evita sobreposição |
| **Blueprints** | **Modelos parametrizados** que geram workflows (ex.: ingestão de JDBC → S3, *compactação*) |
| **Gatilho por evento** | Workflow iniciado por **EventBridge** (arquivo novo) |

```bash
aws glue create-workflow --name pipeline-pedidos --max-concurrent-runs 1
aws glue start-workflow-run --name pipeline-pedidos \
  --run-properties '{"dia":"2026-11-09"}'
aws glue get-workflow-run --name pipeline-pedidos --run-id wr_abc --include-graph
```

### Workflows do Glue vs Step Functions vs MWAA vs EventBridge

| Critério | **Glue Workflows** | **Step Functions** | **MWAA (Airflow)** | **EventBridge** |
|---|---|---|---|---|
| **Escopo** | **Apenas recursos do Glue** (jobs, crawlers) | **Qualquer serviço AWS** (Lambda, Glue, Athena, EMR, SageMaker, SNS…) | Qualquer coisa (operadores) | **Roteamento de eventos** |
| **Lógica** | Condicional simples | **Estados** (Choice, Map, Parallel, Retry/Catch) | **DAGs em Python**, enorme ecossistema | Regras e destinos |
| **Tratamento de erros** | Limitado | **Retry/Catch** nativos | Retries por tarefa | — |
| **Complexidade** | **Baixa** | Média | Média/alta (operação do ambiente) | Baixa |
| **Custo** | Sem custo extra | Por transição | Ambiente gerenciado (por hora) | Por evento |
| **Melhor para** | Pipelines **só em Glue** | Pipelines **multi-serviço** e com lógica | Equipes com **Airflow**, muitos pipelines | Disparo por evento |

```
 Pipeline simples só com Glue (crawler → job → crawler)?          ─► Glue Workflow
 Mistura de Glue + Athena + Lambda + notificações, com retries?    ─► Step Functions
 Equipe já usa Airflow, centenas de DAGs, dependências de dados?   ─► MWAA
 "Quando chegar arquivo no S3, comece o pipeline"?                 ─► EventBridge → Workflow/Step Functions
```

```json
{
  "StartAt": "ETLPedidos",
  "States": {
    "ETLPedidos": {
      "Type": "Task",
      "Resource": "arn:aws:states:::glue:startJobRun.sync",
      "Parameters": {"JobName": "etl-pedidos", "Arguments": {"--dia.$": "$.dia"}},
      "Retry": [{"ErrorEquals": ["States.TaskFailed"], "MaxAttempts": 2, "IntervalSeconds": 60, "BackoffRate": 2}],
      "Catch": [{"ErrorEquals": ["States.ALL"], "Next": "NotificaFalha"}],
      "Next": "ValidaQualidade"
    },
    "ValidaQualidade": {"Type": "Task", "Resource": "arn:aws:states:::glue:startJobRun.sync",
      "Parameters": {"JobName": "dq-pedidos"}, "Next": "Sucesso"},
    "NotificaFalha": {"Type": "Task", "Resource": "arn:aws:states:::sns:publish",
      "Parameters": {"TopicArn": "arn:aws:sns:us-east-1:123456789012:dados-falhas", "Message": "ETL falhou"}, "End": true},
    "Sucesso": {"Type": "Succeed"}
  }
}
```

> [!tip] A regra de bolso da orquestração
> **Glue Workflows** servem para **pipelines simples dentro do Glue**. Assim que surgirem **retries elaborados, ramificações, outros serviços ou aprovações**, **mude para Step Functions** (ou MWAA, se já houver Airflow).

## Glue Studio (autoria visual)

O **Glue Studio** oferece um **editor visual** (grafo de nós) que **gera o código PySpark** e permite **editar o script**.

| Elemento | Detalhe |
|---|---|
| **Nós de origem** | S3, Catalog, JDBC, Kinesis, Kafka, Redshift, DynamoDB, conectores |
| **Nós de transformação** | ApplyMapping, Filter, Join, Aggregate, SQL, Drop Duplicates, Detect PII, Custom code, Fill Missing, Flatten, Change Schema |
| **Nós de destino** | S3, Catalog, JDBC, Redshift, Iceberg/Hudi/Delta |
| **Editor de script** | Alternar para o código gerado e personalizar |
| **Notebooks** | **Interactive sessions** (Jupyter) para desenvolvimento |
| **Visualização de dados** | Pré-visualização dos dados em cada nó |
| **Métricas e execução** | Monitoramento de execuções e DPUs |

| Use o editor visual quando... | Use código quando... |
|---|---|
| ETL **padrão** (mapear, filtrar, juntar, gravar) | Lógica **complexa**, UDFs, algoritmos específicos |
| **Equipes menos técnicas** | Necessidade de **testes automatizados** e revisão por PR |
| **Prototipagem rápida** | **Reuso** e bibliotecas internas |

> [!warning] Código gerado precisa de versionamento
> O **grafo visual** não substitui **controle de versão**. Exporte/guarde o **script** (e a definição do job) em **Git/IaC** (CloudFormation/Terraform), com **CI/CD** para publicar.

## Glue DataBrew (preparação sem código)

O **DataBrew** é uma ferramenta **visual** para **analistas e cientistas de dados** **explorarem, limparem e padronizarem** dados **sem programar**.

| Recurso | Descrição |
|---|---|
| **Projetos** | Interface tipo planilha com **amostra** dos dados |
| **Receitas (recipes)** | **Sequência de passos** de transformação (versionável e reutilizável) |
| **250+ transformações** | Limpar, formatar datas, tratar nulos, dividir/mesclar colunas, normalizar, one-hot, agregar |
| **Perfis de dados (data profiling)** | **Estatísticas** automáticas: nulos, distinções, distribuição, correlação, **qualidade** |
| **Regras de qualidade** | Verificações (completude, unicidade, faixas) |
| **Jobs** | Aplicam a receita **em escala** (e agendam) sobre S3/Catalog/JDBC |
| **Linhagem** | Visualização de origem e destino |
| **Mascaramento de PII** | Transformações de **mascarar, hash e substituir** |

```
 Dados brutos (S3) ──► DataBrew (projeto + receita) ──► Job de receita ──► Dados preparados (S3, Parquet)
                          └─ perfil de dados e regras de qualidade
```

| DataBrew | Glue ETL (Spark) |
|---|---|
| **Sem código**, visual | **Código** (PySpark) ou visual (Studio) |
| Ótimo para **analistas** | Ótimo para **engenheiros de dados** |
| Volumes **moderados/grandes** (jobs gerenciados) | **Qualquer escala**, lógica complexa |
| Transformações **prontas** | **Total flexibilidade** |
| Menos controle fino | **Controle fino** de desempenho |

## Glue Data Quality

O **Glue Data Quality** **mede e monitora a qualidade** dos dados com **regras declarativas** escritas em **DQDL** (*Data Quality Definition Language*).

### Tipos de regras (DQDL)

```
Rules = [
    IsComplete "pedido_id",                          # sem nulos
    IsUnique "pedido_id",                            # sem duplicatas
    ColumnValues "valor" > 0,                        # faixa válida
    ColumnValues "status" in ["PAGO","PENDENTE","CANCELADO"],   # valores permitidos
    Completeness "email" > 0.95,                     # ao menos 95% preenchidos
    ColumnLength "uf" = 2,
    ColumnValues "criado_em" <= now(),               # sem datas no futuro
    RowCount > 1000,                                 # volume mínimo
    RowCount between 0.8 * avg(last(7)) and 1.2 * avg(last(7)),   # volume ±20% da média recente
    Mean "valor" between 10 and 5000,
    ReferentialIntegrity "cliente_id" "lake.dim_cliente.cliente_id" = 1.0,   # chave estrangeira
    DataFreshness "criado_em" <= 24 hours,           # dados atualizados
    CustomSql "SELECT count(*) FROM primary WHERE valor < 0" = 0
]
```

| Família de regras | Exemplos |
|---|---|
| **Completude e unicidade** | `IsComplete`, `Completeness`, `IsUnique`, `Uniqueness` |
| **Valores e domínios** | `ColumnValues`, `ColumnLength`, `ColumnDataType` |
| **Estatísticas** | `Mean`, `StandardDeviation`, `Sum`, `Entropy`, `DistinctValuesCount` |
| **Volume** | `RowCount` (absoluto e relativo a histórico) |
| **Integridade referencial** | `ReferentialIntegrity` |
| **Atualidade** | `DataFreshness` |
| **Customizadas** | `CustomSql` |
| **Correlação** | `ColumnCorrelation` |
| **Detecção de anomalias** | Regras **adaptativas** que aprendem o padrão |

### Como executar

| Modo | Descrição |
|---|---|
| **Em tabelas do catálogo** | **Ruleset** associado à tabela; execuções **agendadas ou sob demanda** |
| **Dentro de um job ETL** | Nó **Evaluate Data Quality** (no Studio) ou API; **decide** o que fazer com **linhas aprovadas/reprovadas** |
| **Recomendação de regras** | O Glue **sugere regras** analisando os dados |
| **Resultados** | **Pontuação de qualidade**, regras que falharam, **linhas problemáticas** (opcional) |
| **Integração** | **EventBridge** (resultados), **CloudWatch**, **SNS**, **Lake Formation/DataZone** |

```python
# Dentro de um job: valida e separa linhas boas e ruins
from awsgluedq.transforms import EvaluateDataQuality

regras = """Rules = [ IsComplete "pedido_id", IsUnique "pedido_id", ColumnValues "valor" > 0 ]"""
resultado = EvaluateDataQuality.apply(
    frame=pedidos, ruleset=regras,
    publishing_options={"dataQualityEvaluationContext": "dq_pedidos",
                        "enableDataQualityCloudWatchMetrics": True,
                        "enableDataQualityResultsPublishing": True},
    additional_options={"performanceTuning.caching": "CACHE_NOTHING"},
)
# resultado traz as linhas e o relatório; use "rowLevelOutcomes" para separar aprovadas/reprovadas
```

### O que fazer com a falha

| Ação | Quando |
|---|---|
| **Falhar o job** (parar o pipeline) | Dados **críticos** (financeiro, regulatório) |
| **Enviar linhas ruins à quarentena** (S3/tabela) e **seguir** com as boas | Qualidade parcial aceitável |
| **Alertar** (SNS/Slack) sem bloquear | Monitoramento |
| **Registrar métricas** (tendência da qualidade) | Governança |
| **Abrir ticket** com o dono dos dados | Resolução na origem |

> [!tip] "Contrato de dados" na prática
> Regras DQDL versionadas em Git funcionam como **contrato** entre produtores e consumidores: **mudanças** em dados que **violam o contrato** são detectadas **antes** de chegar a dashboards e modelos.

## Detecção de dados sensíveis

O **Sensitive Data Detection** do Glue **identifica PII** (CPF, e-mail, telefone, cartão, endereço, passaporte, etc.) em dados e **permite agir**.

| Ação | Descrição |
|---|---|
| **Detectar** | Por **padrões e ML** em colunas/linhas |
| **Classificar** | Marca colunas com tipo de entidade |
| **Mascarar / substituir** | Troca por `*****` ou valor fixo |
| **Hash (SHA-256)** | Pseudonimiza preservando junções |
| **Criptografar** | Com KMS |
| **Remover** | Descarta colunas/linhas |
| **Padrões customizados** | Regex para dados da empresa (matrícula, contrato) |
| **Usos** | **LGPD/GDPR**, compartilhamento de dados, ambientes de teste |

```
 Dados com PII (bruto) ──► Glue (Detect PII + Hash/Mask) ──► Dados curados sem PII exposta
                                   └─► relatório de colunas sensíveis (catálogo/Lake Formation tags)
```

| Boa prática | Motivo |
|---|---|
| **Detectar já na ingestão** | Impede PII em camadas amplamente acessíveis |
| **Combinar com Lake Formation** | Acesso por colunas/tags |
| **Pseudonimizar para análises** | Preserva utilidade |
| **Registrar decisões** | Auditoria |
| **Revisar falsos positivos/negativos** | Detecção não é perfeita |

> [!warning] Detecção automática não é garantia de conformidade
> Ferramentas de PII **reduzem risco**, mas **não substituem** a **governança** (mapeamento de dados, base legal, retenção, direitos dos titulares). Combine com **processos e revisão humana**.

## Padrões de pipeline confiável

```
 Fonte ──► INGESTÃO (bruto, imutável)
              │
              ▼
          Crawler/Catálogo (LOG de mudanças de esquema)
              │
              ▼
          ETL Spark (idempotente, bookmarks, parâmetros)
              │
              ▼
          DATA QUALITY (DQDL)  ──falha──► quarentena + alerta + (opcional) para o pipeline
              │ aprovado
              ▼
          PII (mask/hash) ──► CURADO (Parquet/Iceberg, catálogo atualizado)
              │
              ▼
          Consumo (Athena/Redshift/QuickSight) + monitoramento (CloudWatch/EventBridge)
```

| Princípio | Aplicação |
|---|---|
| **Idempotência** | Reexecutar não duplica |
| **Quarentena** | Dados ruins separados, não perdidos |
| **Observabilidade** | Métricas, logs, alarmes por etapa |
| **Contratos** | Esquemas e regras de qualidade versionados |
| **Backfill** | Parâmetros de data permitem reprocessar |
| **Ambientes** | Dev/homologação/produção com IaC |
| **Linhagem e donos** | Quem produz e quem consome |

## Exemplo prático: pipeline de pedidos com qualidade e privacidade

1. **EventBridge** detecta o arquivo do dia no S3 e inicia um **workflow** (ou Step Functions) com `dia`.
2. O **job ETL** lê só o dia (`push_down_predicate`), limpa e deduplica.
3. O nó **Evaluate Data Quality** aplica DQDL: `pedido_id` único, `valor` > 0, `RowCount` ±20% da média recente, integridade com `dim_cliente`.
4. Linhas reprovadas vão para `s3://lake/quarentena/pedidos/dia=.../`; se a **pontuação < 95%**, o job **falha** e **SNS** notifica o dono.
5. **Detect PII** aplica **hash** a CPF e e-mail antes de gravar na camada curada.
6. Grava **Parquet particionado** (idempotente por partição) e atualiza o catálogo.
7. Um **dashboard de qualidade** (QuickSight) acompanha a pontuação diária e as regras que mais falham.

## Troubleshooting

| Sintoma | Causa provável | Como resolver |
|---|---|---|
| **Trigger condicional não dispara** | Condição não satisfeita (job falhou/estado diferente) | Verificar estado e predicado; tratar `FAILED` |
| **Execuções sobrepostas** | Sem limite de concorrência | `MaxConcurrentRuns`; agendamento adequado |
| **Workflow "preso"** | Nó em falha sem tratamento | Ver o grafo; retomar (*resume*); adicionar caminho de falha |
| **Regras DQDL com erro de sintaxe** | Nome de coluna/estrutura incorreta | Validar DQDL; usar recomendação de regras |
| **Data Quality lento/caro** | Muitas regras estatísticas em tabelas enormes | Amostrar; priorizar regras; agendar fora do pico |
| **Falsos alertas de volume** | Sazonalidade (fins de semana) | Regras relativas por dia da semana; adaptativas |
| **PII não detectada** | Formato fora do padrão | Padrões customizados; revisão humana |
| **DataBrew job falha** | Permissões, formato, receita incompatível com esquema | Ver logs; ajustar a receita |
| **Studio gera código inesperado** | Nós mal configurados | Revisar o script; testar |
| **Step Functions falha em `startJobRun.sync`** | Permissões ou nome do job | Revisar IAM e parâmetros |
| **Pipeline não reage ao evento** | Regra do EventBridge/notificações S3 | Verificar padrões, região e permissões |

## Erros comuns e armadilhas

- **Orquestrar tudo só com triggers**, sem tratamento de falhas.
- **Não limitar execuções simultâneas** do mesmo job.
- **Qualidade como etapa "opcional"** que ninguém lê.
- **Regras de qualidade só no happy path**, sem quarentena.
- **PII exposta** na camada bruta amplamente compartilhada.
- **Autoria visual sem versionamento.**
- **Usar Glue Workflows** para lógica complexa multi-serviço.
- **Não monitorar a tendência** da pontuação de qualidade.

## 🧩 Quiz de Fixação

1. Quando usar Step Functions em vez de Glue Workflows?
2. O que é DQDL?
3. Para que serve a quarentena em um pipeline de qualidade?
4. Qual a diferença entre DataBrew e Glue ETL?
5. Como evitar execuções sobrepostas de um job?
6. Por que detectar PII já na ingestão?

**Respostas:**
1) Quando o pipeline envolve outros serviços, retries elaborados, ramificações ou aprovações; os Glue Workflows só orquestram recursos do Glue de forma simples.
2) A Data Quality Definition Language, usada para escrever regras declarativas de qualidade de dados no Glue Data Quality.
3) Separar e preservar linhas reprovadas para análise e correção, sem perdê-las e sem contaminar a camada curada.
4) O DataBrew é visual e sem código, voltado a analistas, com transformações prontas; o Glue ETL é programável (Spark), com controle fino e qualquer escala.
5) Definindo o máximo de execuções simultâneas (MaxConcurrentRuns) e agendamentos coerentes.
6) Para impedir que dados pessoais cheguem a camadas amplamente acessíveis, aplicando mascaramento ou hash antes da publicação.
