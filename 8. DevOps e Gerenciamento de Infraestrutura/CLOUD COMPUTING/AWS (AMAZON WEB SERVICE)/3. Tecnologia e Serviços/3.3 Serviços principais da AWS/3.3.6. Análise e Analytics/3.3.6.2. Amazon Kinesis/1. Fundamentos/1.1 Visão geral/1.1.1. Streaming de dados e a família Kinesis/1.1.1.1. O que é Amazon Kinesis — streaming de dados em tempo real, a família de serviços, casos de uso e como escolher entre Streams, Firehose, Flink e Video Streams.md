### O que é Amazon Kinesis — streaming de dados em tempo real, a família de serviços, casos de uso e como escolher entre Streams, Firehose, Flink e Video Streams

> [!warning] Aviso
> Nomes de produtos (a AWS renomeou serviços da família), limites de throughput, preços, modos de capacidade e funcionalidades mudam com frequência. Os números aqui são referências de estudo; confirme na documentação oficial. Os comandos e códigos são exemplos e **não foram executados**.

**Streaming de dados** é o processamento de dados **assim que eles são gerados**, de forma **contínua**, em vez de acumulá-los para processar em lote horas depois. Cliques em um site, leituras de sensores, transações financeiras, logs de aplicação, telemetria de jogos: todos são **fluxos de eventos** que chegam sem parar, e o valor deles costuma **decair com o tempo** (detectar uma fraude **agora** vale muito mais do que detectá-la amanhã).

O **Amazon Kinesis** é a **família de serviços da AWS para streaming de dados**: **coletar**, **armazenar temporariamente**, **processar** e **entregar** fluxos de dados **em escala**, de forma **gerenciada**, sem operar clusters de Kafka ou de processamento por conta própria.

**Analogia:** pense em um **rio**. Os dados são a água que corre sem parar. O **Kinesis Data Streams** é o **canal com comportas** que conduz a água (e a mantém por um tempo, para que vários usuários a coletem). O **Firehose** é a **tubulação automática** que leva a água até o reservatório (S3, Redshift, OpenSearch) sem que você precise cuidar de nada. O **Managed Service for Apache Flink** é a **estação de tratamento em tempo real**, que filtra, agrega e enriquece a água enquanto ela passa. O **Video Streams** é um canal **especializado em vídeo**.

## Lote vs streaming

| Característica | **Lote (batch)** | **Streaming** |
|---|---|---|
| Quando processa | Em intervalos (hora, dia) | **Continuamente**, evento a evento ou em micro-janelas |
| Latência do resultado | Minutos a horas | **Milissegundos a segundos** |
| Dados | Conjuntos delimitados | Fluxo **ilimitado** |
| Exemplo | Relatório de vendas noturno | Detecção de fraude no momento da compra |
| Ferramentas | Athena, Glue, EMR, Redshift | **Kinesis**, MSK, Flink, Lambda |
| Complexidade | Menor | Maior (ordem, duplicidade, estado, janelas) |

> [!tip] Streaming não substitui o lote
> A maioria das arquiteturas combina os dois: o **streaming** entrega **resultados imediatos** (alertas, dashboards ao vivo) e **grava tudo no data lake**, onde o **lote** faz análises profundas. É a base de arquiteturas **Lambda/Kappa**.

## A família Kinesis

```
 FONTES                      INGESTÃO / ARMAZENAMENTO       PROCESSAMENTO              DESTINOS
 apps, IoT, logs,    ──►   ┌──────────────────────┐   ──► Flink / Lambda / KCL  ──► S3, Redshift, OpenSearch,
 cliques, transações       │ Kinesis Data Streams │        (tempo real)                DynamoDB, APIs, dashboards
                           └──────────┬───────────┘
                                      │
 ──────────────────────────────►  ┌───▼──────────────┐
                                  │ Amazon Data      │ ───► S3 / Redshift / OpenSearch / Splunk / HTTP
                                  │ Firehose         │      (entrega gerenciada, sem código)
                                  └──────────────────┘

 Câmeras / vídeo ─► Kinesis Video Streams ─► reprodução, ML (Rekognition), análise
```

| Serviço | O que é | Quando usar |
|---|---|---|
| **Kinesis Data Streams (KDS)** | **Fluxo de dados** durável e ordenado por partição; **você** escreve produtores e consumidores | Processamento **customizado**, baixa latência, **múltiplos consumidores**, reprocessamento |
| **Amazon Data Firehose** (antes *Kinesis Data Firehose*) | **Entrega gerenciada** de streams para **destinos** (S3, Redshift, OpenSearch, Splunk, HTTP); transforma e converte formatos | **Carregar dados** em data lake/warehouse **sem escrever consumidores** |
| **Managed Service for Apache Flink** (antes *Kinesis Data Analytics*) | **Processamento de streams** com **Apache Flink** (SQL, Java, Python): janelas, agregações, junções, CEP | **Análise em tempo real** com estado e janelas |
| **Kinesis Video Streams** | Ingestão, armazenamento e processamento de **vídeo e áudio** | Câmeras, vídeo de dispositivos, ML sobre vídeo |

> [!warning] Nomes mudaram
> **Kinesis Data Firehose** passou a **Amazon Data Firehose** e **Kinesis Data Analytics** a **Managed Service for Apache Flink**. Em provas, materiais antigos e códigos legados você verá os **nomes antigos**; saiba os dois.

## Conceitos fundamentais de streaming

| Conceito | Definição |
|---|---|
| **Evento / registro (record)** | Uma unidade de dados (JSON, bytes) no fluxo |
| **Produtor** | Quem **escreve** no stream (aplicação, dispositivo, agente) |
| **Consumidor** | Quem **lê** e processa os registros |
| **Stream** | O **fluxo** nomeado e durável de registros |
| **Partição (shard)** | Subdivisão do stream que **paraleliza** e **ordena** dados |
| **Chave de partição** | Valor que define **em qual shard** o registro cai |
| **Retenção** | Tempo que o stream **guarda** os registros (permite reler) |
| **Janela (window)** | Agrupamento temporal para agregar (por minuto, por sessão) |
| **Ordem** | Garantida **dentro** de uma partição, **não** entre partições |
| **Semântica de entrega** | At-least-once (padrão), at-most-once, exactly-once (com cuidados) |
| **Backpressure** | Consumidor mais lento que o produtor |

### Janelas de tempo

| Tipo | Descrição | Exemplo |
|---|---|---|
| **Tumbling** | Janelas **fixas e sem sobreposição** | Total por minuto |
| **Sliding / Hopping** | Janelas **que deslizam** com sobreposição | Média dos últimos 5 min, a cada 1 min |
| **Session** | Janelas por **atividade** (fecham após inatividade) | Sessão de navegação |

### Tempo de evento vs tempo de processamento

| Tempo | Significado | Cuidado |
|---|---|---|
| **Tempo de evento** | Quando o evento **aconteceu** (carimbo do dado) | Eventos chegam **atrasados e fora de ordem** |
| **Tempo de processamento** | Quando o sistema **processou** o evento | Mais simples, menos preciso |
| **Watermark** | Marca de "já vimos tudo até este tempo" | Define quando fechar janelas |

## Casos de uso

| Caso | Como o Kinesis entra |
|---|---|
| **Análise de logs e métricas em tempo real** | Agentes enviam logs ao KDS/Firehose; Flink/Lambda detectam anomalias |
| **Clickstream de sites e apps** | Eventos de navegação → KDS → painéis ao vivo e data lake |
| **IoT e telemetria** | Sensores → KDS → alarmes e armazenamento |
| **Detecção de fraude** | Transações → KDS → Flink calcula padrões em janelas |
| **Pipelines de dados (ingestão)** | Firehose carrega S3/Redshift/OpenSearch automaticamente |
| **Replicação/CDC** | Mudanças de bancos (DMS/DynamoDB Streams) → KDS |
| **Gaming** | Telemetria e rankings ao vivo |
| **Vídeo** | Câmeras → Video Streams → Rekognition/ML |
| **Integração entre microsserviços** | KDS como **barramento de eventos** durável |

## Kinesis vs outras opções de mensageria e streaming

| Critério | **Kinesis Data Streams** | **Amazon MSK (Kafka)** | **SQS** | **SNS** | **EventBridge** |
|---|---|---|---|---|---|
| Modelo | **Stream** ordenado e retido | Stream (Kafka) | **Fila** (consumo e remoção) | Pub/sub (fan-out) | Barramento de eventos com regras |
| Retenção/reprocessamento | **Sim** (até 365 dias) | Sim (configurável) | Não (mensagem some após consumo) | Não | Arquivo/replay limitado |
| Ordem | **Por partição** | Por partição | FIFO opcional | FIFO opcional | Sem garantia forte |
| Múltiplos consumidores independentes | **Sim** | Sim | Um consumidor por mensagem (grupo) | Sim (assinaturas) | Sim (alvos) |
| Operação | **Gerenciado** | Gerenciado, mais complexidade | **Mínima** | Mínima | Mínima |
| Ecossistema | AWS nativo | **Kafka aberto** | AWS | AWS | AWS/SaaS |
| Throughput | Alto (por shard) | Muito alto | Alto | Alto | Moderado |
| Ideal para | **Streaming de eventos em escala na AWS** | Migração de Kafka, ecossistema Kafka | **Desacoplamento de tarefas** | Notificações e fan-out | **Integração baseada em regras** |

```
 Preciso de um fluxo ordenado, retido, com vários consumidores e reprocessamento? ─► Kinesis Data Streams
 Já uso Kafka (ecossistema, conectores, portabilidade)?                              ─► Amazon MSK
 Só quero desacoplar produtor e consumidor de tarefas (fila simples)?                ─► SQS
 Preciso avisar muitos assinantes de um evento?                                      ─► SNS (ou EventBridge)
 Só quero carregar dados no S3/Redshift sem código?                                  ─► Firehose
```

## Visão geral dos serviços em detalhe

### Kinesis Data Streams

| Aspecto | Resumo |
|---|---|
| **Unidade de capacidade** | **Shard** (partição) ou **modo sob demanda** |
| **Retenção** | 24 horas por padrão; até **365 dias** |
| **Consumo** | Vários consumidores independentes; **enhanced fan-out** (EFO) |
| **Ordenação** | Por **chave de partição** (dentro do shard) |
| **Integrações** | Lambda, Flink, Firehose, KCL, DynamoDB Streams, DMS, IoT |
| **Detalhes** | Veja as próximas folhas |

### Amazon Data Firehose

| Aspecto | Resumo |
|---|---|
| **Sem gerenciar shards** | Escala automaticamente |
| **Destinos** | S3, Redshift, OpenSearch, Splunk, HTTP endpoints, Iceberg, Snowflake e parceiros |
| **Transformação** | Lambda e **conversão para Parquet/ORC** |
| **Latência** | **Quase em tempo real** (segundos a minutos de buffer), não milissegundos |
| **Quando usar** | **Carga** gerenciada, sem consumidores customizados |

### Managed Service for Apache Flink

| Aspecto | Resumo |
|---|---|
| **Processamento com estado** | Agregações, janelas, junções, detecção de padrões |
| **Linguagens** | SQL, Java, Scala, Python |
| **Fontes e destinos** | KDS, MSK, S3, Firehose, OpenSearch, etc. |
| **Escala e tolerância a falhas** | Gerenciadas, com *checkpoints* e *snapshots* |

### Kinesis Video Streams

| Aspecto | Resumo |
|---|---|
| **Ingestão** | Vídeo, áudio, imagens térmicas, radar |
| **Armazenamento** | Durável e indexado por tempo |
| **Uso** | Reprodução (HLS/DASH), WebRTC, ML (Rekognition) |

## Modelo de custo (visão geral)

| Serviço | Cobrança (referência) |
|---|---|
| **Data Streams (provisionado)** | Por **shard-hora** + **PUT payload units** |
| **Data Streams (sob demanda)** | Por **GB ingeridos** e **GB lidos** + por stream-hora |
| **Retenção estendida / EFO** | Cobrança adicional por **shard-hora/GB** |
| **Firehose** | Por **GB ingerido** (e conversões/dinâmica) |
| **Flink** | Por **KPU-hora** (unidade de processamento) |
| **Video Streams** | Por GB ingerido e armazenado |

> [!tip] Comece pelo Firehose se só precisa carregar dados
> Muitas equipes montam um Data Streams, um consumidor e um job só para **gravar no S3**. Se o objetivo é **entregar**, o **Firehose resolve com menos esforço e custo operacional**.

## Exemplo prático: pipeline de clickstream

1. O site envia eventos de clique ao **Kinesis Data Streams** (chave de partição = `sessao_id`).
2. O **Managed Service for Apache Flink** calcula **usuários ativos por minuto** (janela tumbling) e grava em **DynamoDB** para o painel ao vivo.
3. Uma **Lambda** consome o mesmo stream e dispara **alertas** quando há picos de erro.
4. O **Firehose** lê o stream e grava **Parquet particionado** no **S3**.
5. O **Athena** consulta o S3 para análises históricas.
6. Todos os consumidores leem **o mesmo stream** de forma independente (com **EFO** onde necessário).

## Erros comuns e armadilhas

- **Usar streaming onde o lote bastaria**, ganhando complexidade sem benefício.
- **Escolher Data Streams para "só gravar no S3"** (Firehose é mais simples).
- **Ignorar a ordem por partição** e esperar ordem global.
- **Chave de partição ruim** (muito concentrada), criando "shard quente".
- **Não tratar duplicatas** (a entrega é *at-least-once*).
- **Confundir Kinesis com fila**: o stream **retém** e permite releitura; não "consome e apaga".
- **Esquecer os nomes novos** (Data Firehose, Managed Service for Apache Flink).
- **Dimensionar sem medir** o volume de entrada.

## 🧩 Quiz de Fixação

1. O que diferencia streaming de processamento em lote?
2. Qual serviço Kinesis entrega dados ao S3 sem código?
3. Onde a ordem dos registros é garantida no Kinesis Data Streams?
4. Qual a diferença essencial entre Kinesis Data Streams e SQS?
5. Para que serve o Managed Service for Apache Flink?
6. Como as janelas tumbling e sliding diferem?

**Respostas:**
1) O streaming processa dados continuamente, assim que gerados, com baixa latência; o lote os acumula e processa em intervalos.
2) O Amazon Data Firehose (antes Kinesis Data Firehose).
3) Dentro de uma partição (shard), definida pela chave de partição; não há ordem global entre shards.
4) O stream retém os registros por um período e permite múltiplos consumidores e releitura; a fila entrega e remove a mensagem após o consumo.
5) Processar streams com estado (agregações, janelas, junções, detecção de padrões) em tempo real usando Apache Flink.
6) Tumbling são janelas fixas e sem sobreposição; sliding deslizam e se sobrepõem (por exemplo, média dos últimos 5 minutos a cada 1 minuto).
