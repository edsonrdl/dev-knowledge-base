### Amazon Data Firehose — destinos, buffering, transformação com Lambda, conversão para Parquet, particionamento dinâmico, falhas e comparação com Data Streams

> [!warning] Aviso
> Destinos suportados, limites de buffer, preços por GB, recursos (particionamento dinâmico, Iceberg, Snowflake) e nomes mudam. Os números aqui são referências de estudo; confirme na documentação. Os comandos e configurações **não foram executados**.

O **Amazon Data Firehose** (antes chamado **Kinesis Data Firehose**) é o serviço **totalmente gerenciado de entrega de streaming**: ele **recebe dados continuamente**, **os acumula em um buffer**, opcionalmente **transforma, converte formato e particiona**, e **os entrega automaticamente** a **destinos** como **Amazon S3, Redshift, OpenSearch, Splunk, endpoints HTTP, Apache Iceberg e parceiros** (Datadog, Snowflake, New Relic etc.). **Não há shards, consumidores nem código de entrega para escrever ou operar**: ele **escala sozinho** e **só cobra pelo volume ingerido**.

**Analogia:** se o Kinesis Data Streams é uma **rodovia onde você dirige seus próprios caminhões**, o Firehose é uma **empresa de logística contratada**: você **deposita a carga na doca**, ela **embala em lotes** (buffer), **etiqueta e organiza** (transformação e particionamento) e **entrega no endereço certo** (S3, Redshift...). Você **não gerencia caminhões nem rotas**, mas **também não escolhe o horário exato de cada entrega**.

---

## Como o Firehose funciona

```
 Fontes                         DELIVERY STREAM                              Destinos
 ──────                  ┌──────────────────────────────┐                   ─────────
 Aplicações (SDK)  ─┐    │  Buffer (tamanho OU tempo)   │                 ┌─► Amazon S3
 Kinesis Data Streams ─┼─►│  ▸ transformação (Lambda)    │ ─────────────►  ├─► Amazon Redshift (via S3 + COPY)
 CloudWatch Logs   ─┤    │  ▸ conversão (Parquet/ORC)   │                 ├─► Amazon OpenSearch
 IoT / WAF / MSK   ─┘    │  ▸ particionamento dinâmico  │                 ├─► Splunk / HTTP / Datadog / ...
                         │  ▸ compressão / criptografia │                 └─► Apache Iceberg tables
                         └──────────────┬───────────────┘
                                        │ falhas e originais (opcional)
                                        ▼
                               S3 de erros / backup
```

| Componente | Descrição |
|---|---|
| **Delivery stream** | O fluxo de entrega configurado (origem, processamento, destino) |
| **Fontes** | **Direct PUT** (SDK/agente), **Kinesis Data Streams**, **MSK**, CloudWatch Logs/Events, IoT, WAF, etc. |
| **Buffer** | Acumula por **tamanho** (MB) **ou** **tempo** (segundos); entrega quando **o primeiro** limite é atingido |
| **Transformação** | **Lambda** para modificar, filtrar ou enriquecer registros |
| **Conversão de formato** | JSON → **Parquet/ORC** (precisa de esquema no Glue) |
| **Particionamento dinâmico** | Organiza o S3 por **campos do registro** (cliente, data) |
| **Compressão** | GZIP, Snappy, ZIP, Hadoop-Snappy |
| **Backup/erros** | Registros que **falham** (e opcionalmente os originais) vão a um bucket S3 |

## Fontes de dados

| Fonte | Como funciona |
|---|---|
| **Direct PUT** | Aplicações chamam `PutRecord`/`PutRecordBatch` (ou **Kinesis Agent**, **Fluent Bit**) |
| **Kinesis Data Streams** | O Firehose **lê o stream** como consumidor (sem escrever código) |
| **Amazon MSK** | Lê tópicos Kafka |
| **CloudWatch Logs / Events** | Assinaturas de logs entregues ao Firehose |
| **AWS IoT / WAF / Network Firewall / SES / outros** | Integração nativa |
| **Lambda** | Produtor serverless |

> [!tip] Padrão "Streams + Firehose"
> É comum **ingerir em Data Streams** (vários consumidores em tempo real) e **adicionar o Firehose como mais um consumidor** para **carregar no S3**, sem impactar os demais.

## Destinos

| Destino | Observações |
|---|---|
| **Amazon S3** | O mais comum; **prefixos por data**, particionamento dinâmico, compressão, Parquet/ORC |
| **Amazon Redshift** | Entrega **primeiro ao S3** e executa **`COPY`** no cluster/serverless |
| **Amazon OpenSearch (Service/Serverless)** | Indexação em tempo quase real; rotação de índices; backup de falhas no S3 |
| **Splunk** | Via HEC (HTTP Event Collector) |

| Característica por destino | S3 | Redshift | OpenSearch | HTTP/Splunk |
|---|---|---|---|---|

| Formato | JSON, Parquet, ORC, texto | CSV/JSON → COPY | JSON | JSON |
| Falhas | Backup no S3 | Retentativas + S3 | Retentativas + S3 | Retentativas + S3 |

## Buffering: o preço da simplicidade

O Firehose **não entrega registro a registro**: ele **acumula** e entrega por **lotes**.

| Parâmetro | Faixa de referência | Efeito |
|---|---|---|
| **`BufferingHints.SizeInMBs`** | 1 a 128 MB (S3) | Entrega ao atingir o volume |
| **`BufferingHints.IntervalInSeconds`** | 0 a 900 s (S3) | Entrega ao atingir o tempo |
| **Gatilho** | **O que ocorrer primeiro** | — |

| Escolha | Resultado |
|---|---|
| **Buffer pequeno/curto** | **Menor latência**, **mais arquivos pequenos** no S3 (ruim para Athena) |
| **Buffer grande/longo** | **Arquivos maiores** (bons para análise), **maior latência** |

> [!warning] Firehose é "quase em tempo real", não tempo real
> A latência de entrega é de **segundos a minutos** (dependendo do buffer), **não milissegundos**. Para **reagir em tempo real**, use **Data Streams + Lambda/Flink**. O Firehose é para **carga e arquivamento**.

> [!tip] Equilíbrio para data lakes
> Para dados que serão consultados no Athena, prefira **buffers de 64–128 MB** e **300 s**, gerando **arquivos grandes**. Se tiver **muitos arquivos pequenos**, **compacte** depois (CTAS/Glue).

## Transformação com Lambda

Uma **Lambda de transformação** pode **modificar, enriquecer, filtrar ou descartar** registros antes da entrega.

```python
import base64, json

def lambda_handler(event, context):
    saida = []
    for rec in event["records"]:
        dado = json.loads(base64.b64decode(rec["data"]))
        if dado.get("tipo") == "heartbeat":
            saida.append({"recordId": rec["recordId"], "result": "Dropped", "data": rec["data"]})
            continue
        dado["valor_centavos"] = int(dado["valor"] * 100)       # enriquece
        novo = (json.dumps(dado) + "\n").encode()                # JSON Lines
        saida.append({
            "recordId": rec["recordId"],
            "result": "Ok",                                      # Ok | Dropped | ProcessingFailed
            "data": base64.b64encode(novo).decode(),
        })
    return {"records": saida}
```

| Resultado por registro | Significado |
|---|---|
| **`Ok`** | Entregar o registro transformado |
| **`Dropped`** | Descartar (não entrega nem vai ao bucket de erros) |
| **`ProcessingFailed`** | Falha; vai ao **bucket de erros** |

| Cuidado | Motivo |
|---|---|
| **Devolver todos os `recordId`** recebidos | Senão o Firehose considera falha |
| **Tempo limite** da Lambda (até ~5 min) e **tamanho do lote** (buffer da Lambda) | Evita falhas |
| **Terminar linhas com `\n`** | Para arquivos legíveis (JSON Lines) |
| **Idempotência** | Reentregas podem acontecer |
| **Custo da Lambda** | Soma-se ao do Firehose |

## Conversão de formato (Parquet e ORC)

O Firehose converte **JSON** em **Parquet ou ORC** (formatos colunares) **antes de gravar no S3**, usando um **esquema do Glue Data Catalog**.

| Requisito | Detalhe |
|---|---|
| **Entrada** | JSON (um objeto por registro) |
| **Esquema** | Tabela no **Glue Data Catalog** (nome, tipos) |
| **Saída** | **Parquet** (padrão recomendado) ou **ORC**, com compressão (Snappy etc.) |
| **Benefício** | **Redução de custo e melhoria de desempenho** no Athena/Redshift Spectrum/EMR |
| **Registros inválidos** | Que não casam com o esquema vão ao **bucket de erros** |

> [!tip] A rota mais curta para um data lake analítico
> **JSON → Firehose (Parquet + particionamento por data) → S3 → Glue Catalog → Athena**. Com isso, os dados **já chegam prontos para consulta**, sem job de ETL adicional.

## Particionamento dinâmico

O **particionamento dinâmico** grava os dados em **prefixos S3 derivados de campos do registro**, em vez de apenas por **data de chegada**.

```
 Sem particionamento dinâmico:  s3://lake/eventos/2026/11/09/14/arquivo.gz            (por hora de chegada)
 Com particionamento dinâmico:  s3://lake/eventos/cliente_id=123/dia=2026-11-09/arquivo.parquet
```

| Elemento | Função |
|---|---|
| **Chaves de partição** | Extraídas do JSON (via **JQ**) ou de uma **Lambda** |
| **Prefixo** | `eventos/cliente=!{partitionKeyFromQuery:cliente}/dia=!{partitionKeyFromQuery:dia}/` |
| **Benefício** | Dados **já particionados** para Athena/Spark (poda eficiente) |
| **Limites** | Número de **partições ativas** simultâneas por stream (ajustável); partições novas abertas continuamente |
| **Custo** | Cobrança adicional por GB (e por objetos entregues) |

```json
"DynamicPartitioningConfiguration": {"Enabled": true, "RetryOptions": {"DurationInSeconds": 300}},
"ProcessingConfiguration": {
  "Enabled": true,
  "Processors": [{
    "Type": "MetadataExtraction",
    "Parameters": [
      {"ParameterName": "MetadataExtractionQuery", "ParameterValue": "{cliente: .cliente_id, dia: (.ts | .[0:10])}"},
      {"ParameterName": "JsonParsingEngine", "ParameterValue": "JQ-1.6"}
    ]
  }]
}
```

> [!warning] Particionar demais gera o problema de arquivos pequenos
> Particionar por **chave de alta cardinalidade** (por exemplo, `usuario_id`) cria **milhões de pastas minúsculas**. Escolha chaves **de baixa/média cardinalidade** (data, tenant, tipo de evento).

## Falhas, retentativas e backup

| Situação | Comportamento |
|---|---|
| **Destino indisponível** | O Firehose **retenta** por um período configurável (ex.: 24 h para S3; menos para outros); depois envia ao **bucket de erros** |
| **Falha de transformação** | Registro vai ao bucket de erros com o motivo |
| **Registros que não casam com o esquema** | Bucket de erros |
| **Backup dos dados originais** | Opção de gravar **todos os registros originais** em S3 (mesmo em destinos HTTP/OpenSearch) |
| **Redshift `COPY` falha** | Retentativas; manifestos de falha no S3 |

| Boa prática | Motivo |
|---|---|
| **Sempre configurar o bucket de erros** | Não perder dados problemáticos |
| **Alarmes de falha de entrega** | Detecção rápida |
| **Reprocessar os erros** (Lambda/Glue) | Recuperar dados |
| **Prefixo separado para erros** (`erros/!{firehose:error-output-type}/`) | Diagnóstico organizado |

## Firehose vs Kinesis Data Streams

| Critério | **Amazon Data Firehose** | **Kinesis Data Streams** |
|---|---|---|
| **Propósito** | **Entregar** dados a destinos | **Transportar e reter** dados para processamento customizado |
| **Gerência** | **Nenhuma** (escala automática) | Shards ou sob demanda |
| **Latência** | Segundos a minutos (buffer) | **Milissegundos** a poucos ms (EFO ~70 ms) |
| **Retenção/releitura** | **Não** (sem replay) | **Sim** (até 365 dias) |
| **Consumidores** | Os **destinos** integrados | **Vários** consumidores customizados |
| **Processamento** | Transformação (Lambda), conversão | Qualquer lógica (Lambda, Flink, KCL) |
| **Código** | **Quase nenhum** | Produtores e consumidores |
| **Cobrança** | Por **GB ingerido** | Por shard-hora/GB |
| **Ideal para** | **Carga em S3/Redshift/OpenSearch/Splunk** | **Tempo real**, reprocessamento, múltiplos consumidores |

```
 Só quero levar os dados para o S3/Redshift/OpenSearch com o mínimo de esforço? ─► Firehose
 Preciso reagir em milissegundos, reprocessar ou ter vários consumidores?       ─► Data Streams
 Preciso dos dois (tempo real + arquivo)?                                       ─► Data Streams com Firehose como consumidor
```

## Monitoramento

| Métrica (CloudWatch) | Indica |
|---|---|
| **`IncomingBytes`, `IncomingRecords`** | Volume ingerido (custo) |
| **`DeliveryToS3.Success` / `.DataFreshness`** | Sucesso e **idade do dado mais antigo** ainda não entregue |
| **`DeliveryToS3.Bytes`** | Volume entregue |
| **`ThrottledRecords` / `ThrottledGetRecords`** | Limites atingidos |
| **`ExecuteProcessing.Success` / `.Duration`** | Saúde da Lambda de transformação |
| **`DataReadFromKinesisStream.Bytes`** | Leitura do stream de origem |
| **`BackupToS3.*`** | Backup/erros |

> [!tip] Alarme de `DataFreshness`
> **`DeliveryToS3.DataFreshness`** mede há quanto tempo o dado mais antigo espera. Se **passa do esperado** (ex.: > 15 minutos), a entrega está **atrasada ou falhando**.

## Modelo de custo (referência)

| Item | Cobrança |
|---|---|
| **Ingestão** | Por **GB** ingerido (arredondado por registro, mínimo de 5 KB por registro em alguns modelos; confirme) |
| **Conversão de formato** | Por GB adicional |
| **Particionamento dinâmico** | Por GB e por objetos entregues |
| **Entrega a VPC** | Por hora e por GB |
| **Lambda de transformação** | Custo da Lambda |
| **S3** | Armazenamento e requisições |
| **Entrega a Iceberg** | Por GB |

> [!warning] Registros pequenos custam proporcionalmente mais
> A cobrança arredonda o **tamanho de cada registro** para um mínimo (em alguns modelos, **5 KB**). Milhões de eventos de **200 bytes** custam como se fossem de 5 KB. **Agrupe eventos** em registros maiores antes de enviar.

## Exemplo prático: logs de aplicação para o data lake

1. Os containers enviam logs JSON via **Fluent Bit** ao **Firehose** (Direct PUT).
2. A **Lambda de transformação** remove logs de *health check* (`Dropped`) e adiciona o campo `ambiente`.
3. O Firehose converte para **Parquet (Snappy)** usando o esquema `logs_app` do Glue.
4. O **particionamento dinâmico** grava em `s3://lake/logs/servico=checkout/dia=2026-11-09/`.
5. O buffer é de **128 MB ou 300 s**, gerando arquivos grandes.
6. Registros inválidos vão para `s3://lake/erros/`; um alarme monitora **`DataFreshness`** e falhas.
7. O **Athena** consulta as tabelas particionadas, com custo mínimo.

## Troubleshooting

| Sintoma | Causa provável | Como resolver |
|---|---|---|
| Muitos arquivos pequenos no S3 | Buffer pequeno/curto, particionamento excessivo | Aumentar buffer; menos chaves de partição; compactar |
| Dados atrasados | Buffer longo, falha de entrega, destino lento | Ver `DataFreshness`; reduzir o buffer; corrigir o destino |
| Registros no bucket de erros | Falha de transformação, esquema não bate | Ver o motivo (`errorMessage`); ajustar Lambda/esquema |
| `AccessDenied` na entrega | Role sem permissão no S3/KMS/Glue | Ajustar a role |
| Lambda de transformação falha | Timeout, formato de retorno incorreto | Devolver todos os `recordId`; aumentar timeout |
| Conversão para Parquet falha | JSON malformado ou esquema divergente | Validar JSON; atualizar a tabela do Glue |
| `ThrottledRecords` | Excedeu limites de ingestão | Aumentar quotas; usar Streams como fonte |
| Redshift não recebe | `COPY` falhando (permissões, esquema) | Ver erros de `COPY`; ajustar role/esquema |
| Custo alto | Registros muito pequenos ou conversões desnecessárias | Agrupar registros; revisar recursos habilitados |
| Duplicatas no destino | Retentativas (at-least-once) | Deduplicar no destino (chaves únicas, MERGE) |

## Erros comuns e armadilhas

- **Esperar latência de milissegundos** do Firehose.
- **Buffer mínimo "para ser rápido"**, criando milhões de arquivos pequenos.
- **Não configurar bucket de erros** e perder dados.
- **Lambda de transformação que não devolve todos os `recordId`.**
- **Particionar por chave de alta cardinalidade.**
- **Usar Data Streams + consumidor próprio só para gravar no S3.**
- **Enviar milhões de registros minúsculos** pagando o mínimo por registro.
- **Esquecer de deduplicar** no destino (entrega at-least-once).

## 🧩 Quiz de Fixação

1. Quando o Firehose entrega um lote ao destino?
2. Qual o requisito para converter JSON em Parquet?
3. Para que serve o particionamento dinâmico?
4. Qual a principal diferença entre Firehose e Data Streams?
5. O que acontece com registros que falham na transformação?
6. Qual métrica indica atraso na entrega ao S3?

**Respostas:**
1) Quando o primeiro dos limites de buffer é atingido: tamanho (MB) ou intervalo de tempo (segundos).
2) Um esquema (tabela) no Glue Data Catalog que descreva os campos e tipos dos registros JSON.
3) Gravar os dados no S3 em prefixos derivados de campos do registro (cliente, data), já organizados para consulta eficiente.
4) O Firehose entrega dados a destinos de forma gerenciada, com latência de segundos a minutos e sem retenção; o Data Streams transporta e retém dados para processamento customizado em baixa latência, com múltiplos consumidores e releitura.
5) Vão para o bucket de erros configurado, com o motivo da falha, em vez de serem entregues ao destino.
6) `DeliveryToS3.DataFreshness`.
