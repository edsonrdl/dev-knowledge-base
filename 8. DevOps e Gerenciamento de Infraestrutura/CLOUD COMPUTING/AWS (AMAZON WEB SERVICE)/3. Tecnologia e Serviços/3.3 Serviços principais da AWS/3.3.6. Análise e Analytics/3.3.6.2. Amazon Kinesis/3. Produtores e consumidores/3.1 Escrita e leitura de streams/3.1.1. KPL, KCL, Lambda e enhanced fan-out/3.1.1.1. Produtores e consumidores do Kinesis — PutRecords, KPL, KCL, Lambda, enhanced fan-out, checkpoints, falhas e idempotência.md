### Produtores e consumidores do Kinesis — PutRecords, KPL, KCL, Lambda, enhanced fan-out, checkpoints, falhas e idempotência

> [!warning] Aviso
> Versões de KPL/KCL, limites de API, parâmetros de Lambda (batch, janelas, paralelismo) e custos de EFO mudam. Os códigos e números aqui são referências de estudo; confirme na documentação. Os comandos e códigos **não foram executados**.

Um stream só tem valor se **alguém escreve nele** (produtores) e **alguém processa o que chega** (consumidores). É nessas pontas que aparecem os **problemas reais**: **falhas parciais na escrita**, **throttling**, **duplicatas**, **consumidores lentos que acumulam atraso**, **checkpoints que se perdem** e **reprocessamentos que corrompem resultados**. Esta folha cobre **como escrever** (SDK, `PutRecords`, **KPL**, agentes), **como ler** (**KCL**, **Lambda**, **enhanced fan-out**, Flink, Firehose) e **como tornar o pipeline confiável** (retries, checkpoints, idempotência, tratamento de erros).

**Analogia:** o stream é uma **esteira de fábrica**. Os **produtores** colocam caixas na esteira; se a esteira está cheia, precisam **tentar de novo com paciência** (backoff). Os **consumidores** pegam caixas conforme passam e **anotam num caderno até onde já processaram** (checkpoint). Se o operador faltar e outro assumir, ele **continua do ponto anotado**. Se uma caixa for processada duas vezes, o processo precisa ser **seguro para repetição** (idempotência).

## Produtores

### Opções de escrita

| Opção | Descrição | Quando usar |
|---|---|---|
| **AWS SDK** (`PutRecord`, `PutRecords`) | Chamadas diretas de API | Aplicações simples, baixo volume |
| **Kinesis Producer Library (KPL)** | Biblioteca com **agregação**, **batching**, **retries** e métricas | **Alto volume**, muitos registros pequenos |
| **Kinesis Agent** | Agente que **monitora arquivos de log** e envia ao stream | Logs de servidores |
| **Amazon Data Firehose / IoT Core / DMS / DynamoDB Streams / CloudWatch Logs** | Serviços que **publicam** em Kinesis | Integrações nativas |
| **Fluent Bit / Fluentd / Logstash** | Coletores de logs com *plugin* Kinesis | Containers e logs |
| **AWS SDK em Lambda/containers** | Produtores serverless | Microsserviços |

### `PutRecord` vs `PutRecords`

| API | Característica |
|---|---|
| **`PutRecord`** | **Um** registro por chamada; mais simples; mais chamadas |
| **`PutRecords`** | Até **500 registros** (e até ~5 MB) por chamada; **melhor eficiência**; **pode falhar parcialmente** |

```python
import boto3, json, time, random

kinesis = boto3.client("kinesis")

def enviar(registros, stream="pedidos"):
    entradas = [{"Data": json.dumps(r).encode(), "PartitionKey": str(r["cliente_id"])}
                for r in registros]
    tentativa = 0
    while entradas and tentativa < 5:
        resp = kinesis.put_records(StreamName=stream, Records=entradas)
        if resp["FailedRecordCount"] == 0:
            return
        # PutRecords pode falhar PARCIALMENTE: reenviar só os que falharam
        entradas = [e for e, r in zip(entradas, resp["Records"]) if "ErrorCode" in r]
        tentativa += 1
        time.sleep(min(2 ** tentativa * 0.1, 3) + random.random() * 0.1)   # backoff + jitter
    if entradas:
        raise RuntimeError(f"{len(entradas)} registros não enviados")
```

> [!warning] `PutRecords` retorna sucesso (HTTP 200) mesmo com falhas parciais
> Sempre verifique **`FailedRecordCount`** e reenvie **apenas** os registros com `ErrorCode` (`ProvisionedThroughputExceededException`, `InternalFailure`). Ignorar isso **perde dados silenciosamente**.

### Kinesis Producer Library (KPL)

| Recurso | Benefício |
|---|---|
| **Agregação** | Combina **vários registros do usuário em um registro Kinesis**, aproveitando o limite de 1 MB/s e de 1.000 registros/s por shard |
| **Collection (batching)** | Agrupa vários registros por chamada `PutRecords` |
| **Retries automáticos** | Com backoff |
| **`RecordMaxBufferedTime`** | Espera para formar lotes (latência vs eficiência) |
| **Métricas no CloudWatch** | Visibilidade do produtor |
| **Processo filho nativo (C++)** | Alto desempenho (bibliotecas em Java; wrappers para outras linguagens) |

> [!tip] Agregação exige desagregação no consumidor
> Registros agregados pela KPL precisam ser **desagregados** pelo consumidor (a **KCL** faz isso automaticamente; em Lambda/outros, use a **KPL deaggregation library**). Se o consumidor **não desagrega**, verá blobs estranhos.

### Boas práticas do produtor

| Prática | Motivo |
|---|---|
| **Chave de partição** de alta cardinalidade e com semântica de ordem | Distribuição e ordenação |
| **Agregar e agrupar** registros pequenos | Menos custo e throttling |
| **Backoff exponencial com jitter** | Evita sobrecarga em cascata |
| **Reenvio apenas dos falhos** | Eficiência |
| **Incluir `evento_id` e carimbo de tempo** no payload | Idempotência e tempo de evento |
| **Compactar payloads grandes** | Reduz volume (mas considere CPU) |
| **Esquemas versionados** (Glue Schema Registry, Avro/Protobuf) | Evolução sem quebra |
| **Métricas e alarmes** (`WriteProvisionedThroughputExceeded`) | Detecção rápida |

## Consumidores

### Opções de leitura

| Opção | Descrição | Quando usar |
|---|---|---|
| **AWS Lambda** (event source mapping) | Lê lotes do stream e invoca a função | **Simplicidade**, serverless, lógica por lote |
| **Kinesis Client Library (KCL)** | Biblioteca que **coordena workers**, **leases** e **checkpoints** | **Controle fino**, aplicações de longa duração |
| **Managed Service for Apache Flink** | Processamento com estado, janelas | **Análise em tempo real** |
| **Amazon Data Firehose** | Entrega gerenciada | **Carga** em S3/Redshift/OpenSearch |
| **Aplicações próprias (SDK)** | `GetRecords`/`SubscribeToShard` | Casos especiais (pouco recomendado) |
| **Glue Streaming / EMR Spark Streaming** | ETL em streaming | Pipelines Spark |

### Consumidor padrão (shared throughput) vs enhanced fan-out

| Característica | **Padrão (`GetRecords`)** | **Enhanced fan-out (EFO)** |
|---|---|---|
| **Modelo** | *Pull* (polling) | **Push** via HTTP/2 (`SubscribeToShard`) |
| **Throughput de leitura** | **2 MB/s por shard compartilhado** entre todos os consumidores | **2 MB/s por shard por consumidor registrado** |
| **Latência** | ~200 ms a 1 s (depende do polling) | **~70 ms** |
| **Nº de consumidores** | Poucos (até ~5 sem disputa séria) | Até **20** consumidores EFO por stream (por padrão) |
| **Custo** | Incluído | **Adicional** (por GB e por shard-hora de consumidor) |
| **Quando usar** | 1–2 consumidores, baixa pressão | **Vários consumidores independentes**, baixa latência |

```
 Padrão:   [Shard 2 MB/s] ──compartilhado──► Consumidor A, B, C (cada um recebe ~0,67 MB/s)
 EFO:      [Shard]       ──2 MB/s dedicado─► Consumidor A
                         ──2 MB/s dedicado─► Consumidor B
                         ──2 MB/s dedicado─► Consumidor C
```

```bash
# Registra um consumidor EFO
aws kinesis register-stream-consumer \
  --stream-arn arn:aws:kinesis:us-east-1:123456789012:stream/pedidos \
  --consumer-name analytics-flink
```

## Lambda como consumidor

A Lambda **faz polling** do stream (ou usa EFO) e **invoca a função com um lote** de registros.

```python
import base64, json

def handler(event, context):
    falhas = []
    for rec in event["Records"]:
        try:
            payload = json.loads(base64.b64decode(rec["kinesis"]["data"]))
            processar(payload)                       # lógica idempotente
        except Exception:
            # Falha parcial: reporta o número de sequência do primeiro que falhou
            falhas.append({"itemIdentifier": rec["kinesis"]["sequenceNumber"]})
    return {"batchItemFailures": falhas}
```

| Parâmetro do event source mapping | Função |
|---|---|
| **`BatchSize`** | Máx. de registros por invocação (até 10.000) |
| **`MaximumBatchingWindowInSeconds`** | Espera para formar lote (0 a 300 s) |
| **`ParallelizationFactor`** | **Invocações simultâneas por shard** (1 a 10), mantendo ordem **por chave de partição** |
| **`StartingPosition`** | `TRIM_HORIZON`, `LATEST`, `AT_TIMESTAMP` |
| **`BisectBatchOnFunctionError`** | Divide o lote ao falhar para isolar o registro "venenoso" |
| **`MaximumRetryAttempts`** | Tentativas antes de descartar (ou enviar ao destino de falha) |
| **`MaximumRecordAgeInSeconds`** | Descarta registros mais antigos que o limite |
| **`OnFailure` destination** | **SQS/SNS/S3** para registros que falharam |
| **`FunctionResponseTypes: ReportBatchItemFailures`** | Habilita **falha parcial** (reprocessa só a partir do falho) |
| **`TumblingWindowInSeconds`** | Agregações por janela entre invocações |
| **EFO (consumer ARN)** | Leitura dedicada de baixa latência |

> [!warning] O registro "venenoso" bloqueia o shard
> Com Lambda, se um registro **sempre falha**, o Kinesis **repete o lote** até **expirar a retenção** ou atingir limites de retry. **Todo o shard fica travado atrás dele**. Configure **`BisectBatchOnFunctionError`**, **`MaximumRetryAttempts`**, **`MaximumRecordAgeInSeconds`** e um **destino `OnFailure`** para isolar e desviar o problema.

| Cuidado com Lambda | Explicação |
|---|---|
| **Concorrência = nº de shards × ParallelizationFactor** | Cada shard tem **uma ou mais invocações simultâneas** |
| **Ordem** | Garantida **por shard/chave** |
| **Timeouts** | Lote longo demais estoura a função |
| **Idempotência** | Retries e falhas parciais geram **reentregas** |
| **Cold starts** | Impacto em latência de fluxos esparsos |

## Kinesis Client Library (KCL)

A **KCL** simplifica consumidores de longa duração, resolvendo **o trabalho difícil** da leitura distribuída.

| Responsabilidade da KCL | Detalhe |
|---|---|
| **Coordenação de workers** | Vários *workers* (instâncias) dividem os shards |
| **Leases** | Cada shard tem um **lease** (propriedade) guardado em uma tabela **DynamoDB** |
| **Checkpoint** | Salva o **último número de sequência processado** na tabela DynamoDB |
| **Rebalanceamento** | Redistribui shards quando workers entram/saem ou após resharding |
| **Resharding** | Lê **pais antes de filhos**, preservando ordem |
| **Desagregação** | Desagrega registros KPL |
| **EFO** | Suporta enhanced fan-out |
| **Métricas** | Publica no CloudWatch (`MillisBehindLatest`, etc.) |

```
 Aplicação KCL (N workers)                Tabela DynamoDB "minha-app"
   worker-1 ──lease shard-1,2 ───────────► [shard-1: worker-1, checkpoint=seq 123]
   worker-2 ──lease shard-3   ───────────► [shard-3: worker-2, checkpoint=seq 456]
   (worker-3 entra → rebalanceia)
```

```java
public class ProcessadorPedidos implements ShardRecordProcessor {
    public void processRecords(ProcessRecordsInput input) {
        for (KinesisClientRecord r : input.records()) {
            processar(r);                         // idempotente
        }
        input.checkpointer().checkpoint();       // grava progresso após processar com sucesso
    }
    // initialize, leaseLost, shardEnded, shutdownRequested...
}
```

| Prática com KCL | Motivo |
|---|---|
| **Checkpoint após processar** (não antes) | Evita perder dados em falha |
| **Checkpoint com frequência equilibrada** | Muitos checkpoints sobrecarregam o DynamoDB; poucos geram mais reprocessamento |
| **Mais workers que shards não ajuda** | Um shard é lido por **um** worker por vez |
| **Capacidade do DynamoDB** adequada | Tabela de leases com throughput suficiente |
| **Monitorar `MillisBehindLatest`** | Atraso do consumidor |

## Checkpoints e reprocessamento

| Conceito | Descrição |
|---|---|
| **Checkpoint** | Marca "já processei até aqui"; se o consumidor cai, retoma dali |
| **At-least-once** | Entre o processamento e o checkpoint, uma falha **reprocessa** registros |
| **Reprocessamento deliberado** | Recomeçar de `TRIM_HORIZON`/`AT_TIMESTAMP` para corrigir bugs (dentro da retenção) |
| **Poison pill** | Registro que sempre falha: isolar/descartar |
| **Dead-letter** | Enviar registros problemáticos a **SQS/S3** para análise |

```
 Fluxo seguro de um consumidor:
   1. lê lote
   2. processa de forma IDEMPOTENTE
   3. grava o resultado
   4. só então faz o CHECKPOINT
   (falha entre 3 e 4 ⇒ reprocesso; sem prejuízo se for idempotente)
```

## Idempotência e deduplicação

Como a entrega é **at-least-once**, o **efeito** do processamento deve ser o **mesmo** se um registro for processado várias vezes.

| Técnica | Como |
|---|---|
| **ID único do evento** | O produtor gera `evento_id` (UUID/ULID); o consumidor o usa como **chave** |
| **Gravação idempotente** | `PutItem` condicional, `INSERT ... ON CONFLICT DO NOTHING`, `MERGE` |
| **Tabela de deduplicação** | DynamoDB com TTL guardando IDs já processados |
| **Operações naturalmente idempotentes** | "Definir saldo = X" em vez de "somar 10" |
| **Janelas e *watermarks* no Flink** | Resultados corretos com eventos atrasados |
| **Exactly-once no Flink** | Com *checkpoints* e *sinks* transacionais/idempotentes |

```python
# Exemplo: gravação idempotente no DynamoDB por evento_id
tabela.put_item(
    Item={"evento_id": e["evento_id"], "valor": e["valor"]},
    ConditionExpression="attribute_not_exists(evento_id)",
)
```

## Tratamento de falhas e atrasos

| Problema | Sinal | Resposta |
|---|---|---|
| **Consumidor atrasado** | `GetRecords.IteratorAgeMilliseconds` crescendo | Escalar workers/paralelismo; otimizar processamento; EFO |
| **Registro venenoso** | Lote reentregue repetidamente | Bisect; descartar; destino de falha |
| **Throttling na leitura** | `ReadProvisionedThroughputExceeded` | EFO; menos consumidores; mais shards |
| **Perda por retenção** | Atraso > retenção | Aumentar retenção; corrigir o consumidor |
| **Backlog após incidente** | Iterator age alto | Processar em paralelo (`ParallelizationFactor`), temporariamente mais shards |
| **Dependências lentas** (banco, API) | Latência de processamento | Lotes, *bulk writes*, filas intermediárias, circuit breaker |

> [!tip] A métrica-chave do consumidor: iterator age
> **`GetRecords.IteratorAgeMilliseconds`** (e `MillisBehindLatest` na KCL) mede **quão atrás do presente** o consumidor está. Crie **alarmes** (por exemplo, > 1 minuto): é o **melhor sinal de saúde** de um pipeline de streaming.

## Escolhendo o consumidor

```
 Lógica simples por lote, serverless, sem estado?       ─► Lambda
 Agregações em janelas, junções, estado, CEP?           ─► Managed Service for Apache Flink
 Controle total, aplicação de longa duração, Java/Python?─► KCL
 Só carregar em S3/Redshift/OpenSearch?                 ─► Firehose
 ETL Spark em streaming?                                ─► Glue Streaming / EMR
 Vários consumidores com baixa latência?                ─► EFO em qualquer um acima
```

## Exemplo prático: pipeline confiável de pedidos

1. O produtor usa **KPL** com agregação e chave `cliente_id`; cada evento leva `evento_id` e `ts_evento`.
2. O stream (**provisionado**, 8 shards, retenção 7 dias) tem **três consumidores**:
   - **Lambda** (EFO) valida e grava em **DynamoDB** de forma **idempotente** (`attribute_not_exists`), com `BisectBatchOnFunctionError` e **destino de falha** SQS.
   - **Flink** (EFO) calcula **faturamento por minuto** (janela tumbling) e grava no painel.
   - **Firehose** entrega **Parquet particionado** ao **S3**.
3. Alarmes: **iterator age > 60 s**, falhas da Lambda e `WriteProvisionedThroughputExceeded`.
4. Após um bug, a equipe **reprocessa** a Lambda a partir de `AT_TIMESTAMP`, sem duplicar efeitos graças à idempotência.

## Troubleshooting

| Sintoma | Causa provável | Como resolver |
|---|---|---|
| Perda silenciosa de registros na escrita | Ignorou `FailedRecordCount` | Reenviar os registros com erro |
| `ProvisionedThroughputExceeded` na escrita | Shard acima do limite | Mais shards/sob demanda; chave melhor; backoff |
| Lambda repete o mesmo lote sem parar | Registro venenoso | `BisectBatchOnFunctionError`, retries limitados, `OnFailure` |
| Iterator age crescente | Consumidor lento | Escalar; `ParallelizationFactor`; otimizar; EFO |
| Duplicatas nos resultados | Sem idempotência | `evento_id` + gravação condicional |
| Registros "ilegíveis" (blobs) | Agregação KPL sem desagregar | Usar KCL/biblioteca de desagregação |
| Consumidores brigando por leitura | Throughput compartilhado | EFO |
| Worker KCL não assume shards | Lease/DynamoDB sem capacidade | Ajustar tabela e permissões |
| `ExpiredIteratorException` | Iterador expirou | Novo iterador; ler mais rápido |
| Ordem inesperada | Chaves diferentes para eventos relacionados | Mesma chave de partição |

## Erros comuns e armadilhas

- **Ignorar falhas parciais** de `PutRecords`.
- **Fazer checkpoint antes de processar**, perdendo dados em falha.
- **Processamento não idempotente** num mundo at-least-once.
- **Registro venenoso** travando o shard por falta de política de erro.
- **Vários consumidores no modo padrão** disputando 2 MB/s.
- **Não monitorar o iterator age.**
- **Usar KPL e esquecer a desagregação** no consumidor.
- **Ter mais workers KCL que shards** esperando mais paralelismo.

## 🧩 Quiz de Fixação

1. O que significa `FailedRecordCount` em `PutRecords`?
2. Qual a vantagem do enhanced fan-out?
3. Para que serve `BisectBatchOnFunctionError` na Lambda?
4. Onde a KCL guarda leases e checkpoints?
5. Por que o consumidor deve ser idempotente?
6. Qual a métrica que melhor indica atraso de um consumidor?

**Respostas:**
1) Quantos registros do lote falharam; a chamada pode retornar HTTP 200 e ainda assim ter falhas parciais, que devem ser reenviadas.
2) Dá a cada consumidor registrado 2 MB/s dedicados por shard, com entrega push de baixa latência, sem disputar a largura de banda de leitura.
3) Dividir o lote ao falhar para isolar o registro problemático, evitando que um registro venenoso trave o shard.
4) Em uma tabela do DynamoDB.
5) Porque a entrega é at-least-once: retries e reprocessamentos podem repetir registros, e o efeito deve ser o mesmo.
6) `GetRecords.IteratorAgeMilliseconds` (ou `MillisBehindLatest` na KCL).
