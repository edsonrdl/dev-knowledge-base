### Desempenho e custo no Athena — dados escaneados, formatos colunares, arquivos, bucketing, boas práticas de SQL, reuso de resultados e capacidade provisionada

> [!warning] Aviso
> Preços por TB, comportamento do otimizador, limites de consulta, capacidade provisionada e recursos de reuso de resultados mudam. Os números aqui são referências de estudo; confirme na documentação. As consultas **não foram executadas**.

No Athena, **desempenho e custo são quase a mesma coisa**: como a cobrança é **por dado escaneado**, **tudo que reduz o volume lido** também **acelera a consulta** e **diminui a fatura**. Por isso, otimizar o Athena é, na essência, **ler menos bytes**: escolher **formatos colunares**, **comprimir**, **particionar**, **dimensionar arquivos**, **selecionar só as colunas necessárias** e **escrever SQL que o otimizador consiga aproveitar**. Esta folha traz o **método**, as **alavancas** e os **controles de custo** (workgroups, limites, reuso de resultados e capacidade provisionada).

**Analogia:** pense em **pagar por página lida**. Se o livro é um **arquivo único sem índice**, você paga o livro inteiro para achar um dado. Se tem **capítulos separados por data (partições)**, **índice por coluna (formato colunar)** e **está resumido (compressão)**, você lê **só o capítulo e as páginas certas**. A mesma pergunta custa **centavos** em vez de **dezenas de dólares**.

---

## O raciocínio central: bytes escaneados

```
 Custo e tempo  ∝  bytes escaneados

 Para reduzir os bytes:
   1. Ler menos LINHAS      → partições, filtros, bucketing
   2. Ler menos COLUNAS     → formato colunar + SELECT só do necessário
   3. Ler menos BYTES/coluna→ compressão
   4. Evitar reler          → reuso de resultados, tabelas agregadas
```

| Alavanca | Efeito típico |
|---|---|
| **CSV → Parquet** | Redução de **60% a 95%** nos bytes lidos (depende das colunas) |
| **Compressão (Snappy/Zstd)** | Menos bytes e menos I/O |
| **Partições** | Poda linhas por data/região |
| **Selecionar colunas** | Lê só as colunas pedidas (em Parquet/ORC) |
| **Arquivos de tamanho adequado** | Menos overhead e melhor paralelismo |
| **Pré-agregação** | Consultas diárias leem uma tabela pequena |

> [!tip] O número que importa
> Depois de cada consulta, olhe **`DataScannedInBytes`** (console: "Dados verificados"). Se uma consulta que devolve 10 linhas escaneou 500 GB, **há um problema de modelagem**, não de SQL.

## Formato colunar: por que Parquet e ORC vencem

| Característica | CSV/JSON (linha) | Parquet/ORC (coluna) |
|---|---|---|
| Layout | Cada linha contém todas as colunas | Cada **coluna** é armazenada em bloco próprio |
| `SELECT a, b` em tabela de 100 colunas | Lê **todas** as 100 | Lê **só a e b** |
| Compressão | Pouca | **Alta** (valores homogêneos) |
| **Estatísticas por bloco** (min/max) | Não | **Sim**: permite **pular blocos** (*predicate pushdown*) |
| Tipos | Textuais | Tipados |
| Esquema | Frágil | Embutido |

```
 Tabela com 3 colunas: id, nome, valor
 CSV:      [1,Ana,10] [2,Bia,20] [3,Cris,30]   → SELECT valor lê tudo
 Parquet:  [1,2,3] [Ana,Bia,Cris] [10,20,30]   → SELECT valor lê só o bloco 3
```

| Dica de Parquet | Motivo |
|---|---|
| **Row groups de 128 MB a 1 GB** (por arquivo) | Bom equilíbrio de leitura |
| **Compressão Snappy ou Zstd** | Velocidade e taxa |
| **Ordenar por colunas filtradas** (ex.: data) ao escrever | Melhora *min/max pruning* |
| **Evitar colunas `string` gigantes** quando possível | Reduz custo de leitura |

## Tamanho e quantidade de arquivos

O Athena **processa arquivos em paralelo**; cada arquivo tem **custo fixo de abertura**.

| Problema | Sintoma | Solução |
|---|---|---|
| **Arquivos muito pequenos** (KBs) | Milhares de leituras S3 (`GET`), planejamento lento | **Compactar** em arquivos de **128 MB a 1 GB** |
| **Arquivos gigantes não divisíveis** (`.gz` de texto) | Um arquivo = uma tarefa; sem paralelismo | Dividir; migrar para Parquet |
| **Pouquíssimos arquivos grandes** | Baixo paralelismo | Reparticionar em mais arquivos |

```sql
-- Compactação por CTAS: reescreve em arquivos maiores
CREATE TABLE lake.eventos_compactado
WITH (format='PARQUET', external_location='s3://meu-datalake/compactado/eventos/',
      partitioned_by=ARRAY['dia'], bucketed_by=ARRAY['usuario_id'], bucket_count=8)
AS SELECT * FROM lake.eventos_pequenos;
```

> [!warning] Ingestão em streaming gera arquivos pequenos
> Kinesis Firehose e outras fontes costumam gravar **um arquivo a cada poucos minutos**. Configure **buffer maior** (tamanho/intervalo) e **compacte** periodicamente (job diário de CTAS ou Iceberg `OPTIMIZE`).

## Partições e bucketing

| Técnica | Quando | Cuidado |
|---|---|---|
| **Partição por data** | Quase sempre | Não gerar partições minúsculas |
| **Partição por região/tenant** | Se **todas** as consultas filtram por ele | Cardinalidade moderada |
| **Bucketing** (`bucketed_by`) | **Junções** e filtros frequentes por **chave de alta cardinalidade** (id do usuário) | Número de *buckets* adequado; mesmo `bucket_count` entre tabelas a juntar |
| **Partition projection** | Muitas partições previsíveis | Padrão de pasta rígido |
| **Ordenação** dentro de arquivos | Filtros por faixa | Escrever dados ordenados |

```
 Particionar:  poucas gavetas grandes, escolhidas por filtros QUE TODOS USAM
 Bucketizar:   dividir cada gaveta em N caixinhas por hash do id, para localizar/juntar rápido
```

## Boas práticas de SQL

| Prática | Exemplo |
|---|---|
| **Liste só as colunas necessárias** | `SELECT usuario_id, valor` em vez de `SELECT *` |
| **Filtre cedo e pela partição** | `WHERE ano='2026' AND mes='11'` |
| **`LIMIT` não reduz o escaneamento** em consultas com `ORDER BY`/agregação | Use filtros, não só `LIMIT` |
| **Tabela maior à esquerda do `JOIN`** | O Athena distribui a **tabela da direita**: coloque a **menor à direita** |
| **Evite `ORDER BY` em grandes volumes** | Exige agregação em um único nó; use `LIMIT`/`TopN` |
| **`approx_distinct()`** em vez de `COUNT(DISTINCT)` | Muito mais rápido, erro pequeno (~2%) |
| **Use `UNION ALL`** em vez de `UNION` se não precisa de deduplicação | Evita ordenação |
| **Filtros com `LIKE` no início** (`'abc%'`) | Mais eficientes que `'%abc%'` |
| **Evite funções na coluna de partição** | `WHERE date(ano||mes)` impede a poda |
| **Use `WITH` (CTE) com critério** | CTEs podem ser reavaliadas |
| **Regex com moderação** | Custo de CPU alto em muitos dados |
| **Tipos corretos** | Comparar `timestamp` com `timestamp`, não com `string` |

```sql
-- Menos eficiente
SELECT * FROM lake.eventos e
JOIN lake.usuarios u ON e.usuario_id = u.usuario_id   -- eventos (grande) à esquerda: ok
WHERE e.criado_em BETWEEN timestamp '2026-11-01' AND timestamp '2026-11-09';  -- sem partição!

-- Melhor
SELECT e.usuario_id, u.pais, sum(e.valor) AS total
FROM lake.eventos e
JOIN lake.usuarios u ON e.usuario_id = u.usuario_id
WHERE e.ano = '2026' AND e.mes = '11' AND e.dia BETWEEN '01' AND '09'
GROUP BY e.usuario_id, u.pais;
```

### Entendendo o plano

```sql
EXPLAIN SELECT ... ;            -- plano lógico/distribuído
EXPLAIN ANALYZE SELECT ... ;    -- plano com estatísticas de execução reais
```

Use `EXPLAIN` para verificar se há **poda de partições** e a **ordem das junções**.

### Estatísticas de tabela

O Athena (via **Glue**) pode usar **estatísticas de coluna** (contagem de linhas, valores distintos, min/max) para **melhorar o plano de junções**. Gere as estatísticas das tabelas grandes (**`ANALYZE`**/Glue column statistics) quando as consultas envolvem muitas junções.

## Reuso de resultados de consulta

O **query result reuse** permite que uma consulta **idêntica** reaproveite o **resultado de uma execução recente**, **sem reescanear** os dados.

| Característica | Detalhe |
|---|---|
| **Como habilitar** | Por consulta (`ResultReuseConfiguration`) com **idade máxima** (minutos) |
| **Quando ajuda** | **Dashboards** que repetem a mesma consulta, BI com muitos usuários |
| **Custo** | Resultado reaproveitado **não escaneia dados** (sem cobrança de bytes) |
| **Cuidado** | Dados **desatualizados** dentro da janela escolhida |

```bash
aws athena start-query-execution \
  --query-string "SELECT status, count(*) FROM vendas.pedidos_curado GROUP BY status" \
  --work-group bi \
  --result-reuse-configuration 'ResultReuseByAgeConfiguration={Enabled=true,MaxAgeInMinutes=60}'
```

## Workgroups: controle e governança de custo

Os **workgroups** separam **times, cargas e orçamentos**.

| Controle | Função |
|---|---|
| **Limite de dados por consulta** | **Cancela** consultas que escaneiam acima do limite (ex.: 100 GB) |
| **Limite de dados por workgroup** (diário/mensal) | **Alarme** (via CloudWatch/SNS) ao ultrapassar |
| **Local e criptografia dos resultados** | Imposição centralizada |
| **Versão do motor** | Fixar/atualizar de forma controlada |
| **Métricas no CloudWatch** | Bytes escaneados, tempos, consultas por workgroup |
| **Tags de custo** | Rateio por time/projeto |
| **Imposição de configurações** (*enforce workgroup settings*) | Usuários não sobrescrevem local de saída/criptografia |

```bash
aws athena create-work-group --name analistas \
  --configuration '{
    "ResultConfiguration": {"OutputLocation": "s3://meu-bucket-resultados/analistas/",
                            "EncryptionConfiguration": {"EncryptionOption": "SSE_KMS", "KmsKey": "arn:aws:kms:us-east-1:123456789012:key/abc"}},
    "EnforceWorkGroupConfiguration": true,
    "PublishCloudWatchMetricsEnabled": true,
    "BytesScannedCutoffPerQuery": 107374182400
  }'
```

> [!tip] Um workgroup por perfil de uso
> **`analistas`** (limite por consulta baixo), **`bi`** (reuso de resultados, capacidade reservada), **`etl`** (limite maior, janelas noturnas), **`auditoria`** (acesso restrito). Cada um com **tags** e **alarmes**.

## Capacidade provisionada

Por padrão, o Athena usa **capacidade compartilhada sob demanda**, cobrada por TB escaneado. A **capacidade provisionada** reserva **DPUs dedicadas** por **tempo** (cobrança por DPU-hora), útil quando:

| Situação | Benefício |
|---|---|
| **Cargas previsíveis e contínuas** (BI intenso) | Custo **previsível** em vez de por TB |
| **Necessidade de latência estável** | Sem competição com outras cargas |
| **Consultas de grande escaneamento recorrentes** | Pode sair mais barato que por TB |
| **Isolamento entre cargas** | Reserva por workgroup |

| Modelo | Quando escolher |
|---|---|
| **Sob demanda (por TB)** | Cargas esporádicas, exploratórias, volumes moderados |
| **Capacidade provisionada** | Alta utilização contínua e necessidade de previsibilidade |

> [!warning] Capacidade provisionada não elimina a má modelagem
> Mesmo com DPUs reservadas, **ler 50 TB desnecessários** continua lento e desperdiça a reserva. Otimize **formatos, partições e arquivos** primeiro.

## Estratégia: camadas e agregações

```
 BRUTO (CSV/JSON)  ──CTAS/ETL──►  CURADO (Parquet particionado)  ──agregações──►  ANALÍTICO (tabelas pequenas)
   (arquivo, auditoria)            (consultas gerais)                              (dashboards e relatórios)
```

| Camada | Uso | Custo por consulta |
|---|---|---|
| **Bruta** | Preservação e reprocessamento | Alto (evitar consultar) |
| **Curada** | Análises gerais | Médio |
| **Analítica/agregada** | Dashboards e relatórios | **Muito baixo** |

Consultas de dashboard devem ler **tabelas agregadas** (por dia/dimensão), **não os eventos brutos**.

## Exemplo prático: reduzindo 50 vezes o custo de um relatório

1. Situação: relatório diário de pedidos consulta **2 TB** de CSV, escaneando **tudo** a cada execução.
2. Converte os dados para **Parquet + Snappy**, particionados por `ano/mes/dia`: o volume cai para **~300 GB** totais.
3. O relatório passa a filtrar pela partição e selecionar **5 colunas**: escaneia **~2 GB**.
4. Uma **tabela agregada por dia** reduz o dashboard a **dezenas de MB**.
5. O workgroup `bi` habilita **reuso de resultados por 30 minutos**.
6. Um **limite de 50 GB por consulta** protege contra consultas acidentais.
7. Resultado: custo mensal cai de dezenas de dólares por consulta para **centavos**, e o tempo de segundos a minutos para segundos.

## Troubleshooting

| Sintoma | Causa provável | Como resolver |
|---|---|---|
| Consulta cara com poucos resultados | Sem poda de partições ou `SELECT *` | Filtrar pela partição; selecionar colunas; Parquet |
| Consulta lenta com poucos GB | Muitos arquivos pequenos | Compactar |
| `EXCEEDED_TIME_LIMIT` | Consulta muito pesada | Otimizar; dividir; capacidade provisionada |
| `Query exhausted resources` / `EXCEEDED_MEMORY_LIMIT` | `JOIN`/`ORDER BY`/`DISTINCT` grandes | Reescrever; tabela menor à direita; `approx_distinct`; filtrar |
| `TOO_MANY_REQUESTS` / limite de consultas | Concorrência acima da quota | Reduzir paralelismo; aumentar quota; capacidade provisionada |
| Custo alto de S3 `GET` | Muitos arquivos/leituras | Compactar; reduzir partições pequenas |
| Resultado desatualizado | Reuso de resultados | Ajustar `MaxAgeInMinutes` |
| Junção lenta | Ordem das tabelas/ausência de estatísticas | Menor à direita; gerar estatísticas; bucketing |
| Dashboard caro | Consulta repetida sobre dados brutos | Tabelas agregadas + reuso de resultados |

## Erros comuns e armadilhas

- **Otimizar o SQL antes de otimizar a modelagem** (formato, partição, arquivos).
- **Confiar em `LIMIT`** para reduzir custo.
- **`SELECT *`** em tabelas largas.
- **Função aplicada à coluna de partição**, matando a poda.
- **Sem workgroups nem limites**, sem controle de gasto.
- **Dashboards consultando dados brutos** repetidamente.
- **Particionar por colunas de alta cardinalidade** (ex.: `usuario_id`).
- **Comprar capacidade provisionada** sem antes corrigir a modelagem.

## 🧩 Quiz de Fixação

1. Por que reduzir bytes escaneados melhora custo e desempenho?
2. Por que o formato colunar é mais eficiente?
3. Qual o tamanho ideal aproximado de arquivos Parquet?
4. O que o reuso de resultados evita?
5. Para que serve o limite de dados por consulta em um workgroup?
6. Quando considerar capacidade provisionada?

**Respostas:**
1) Porque a cobrança é por dado escaneado e o tempo de execução depende do volume lido; ler menos bytes reduz as duas coisas.
2) Lê apenas as colunas necessárias, comprime melhor e usa estatísticas por bloco para pular dados irrelevantes.
3) Em torno de 128 MB a 1 GB por arquivo.
4) Reescanear os dados em consultas idênticas repetidas dentro da janela de idade configurada, sem custo de bytes escaneados.
5) Cancelar consultas que escaneiam acima do limite, protegendo contra custos acidentais.
6) Quando há cargas contínuas e previsíveis, necessidade de latência estável e isolamento, e a modelagem já está otimizada.
