### Consultas avançadas no Athena — logs da AWS, funções SQL, views, federated queries, UDFs, prepared statements e Apache Spark

> [!warning] Aviso
> Esquemas de logs, funções suportadas, conectores de federação, versões do motor e recursos do Spark mudam. Os exemplos aqui são referências de estudo; confirme na documentação. As consultas **não foram executadas**.

Dominar o básico (criar tabela e consultar) é só o começo. O poder do Athena aparece quando você **analisa os logs da própria AWS**, usa as **funções avançadas do SQL** (JSON, arrays, janelas, datas), cria **views reutilizáveis**, **consulta fontes externas** (RDS, DynamoDB, Redshift, APIs) com **federated queries**, estende o SQL com **funções definidas pelo usuário (UDFs)**, parametriza consultas com **prepared statements** e, quando o SQL não basta, recorre ao **Apache Spark** em notebooks. Esta folha reúne esses recursos com **exemplos práticos**.

**Analogia:** o Athena básico é uma **calculadora científica**. Esta folha é a **bancada de laboratório completa**: instrumentos prontos para amostras comuns (logs AWS), ferramentas de precisão (funções), **atalhos reutilizáveis** (views), **extensões para equipamentos de outros laboratórios** (federação) e uma **sala de computação pesada** (Spark) para o que a calculadora não resolve.

## Analisando logs da AWS

Muitos serviços entregam logs no S3 em **formatos conhecidos**, e o Athena os consulta com tabelas prontas.

| Fonte de log | Pergunta típica |
|---|---|
| **CloudTrail** | Quem chamou qual API, de onde? |
| **ALB / NLB / CLB** | Erros 5xx por URL, latência, clientes |
| **VPC Flow Logs** | Quem se conectou a quê; tráfego rejeitado |
| **CloudFront** | Acessos por país, URLs mais pedidas, erros |
| **S3 server access logs** | Quem acessou/baixou objetos |
| **Route 53 Resolver, WAF, Network Firewall** | Consultas DNS e requisições bloqueadas |
| **Cost and Usage Report (CUR)** | Custos por serviço, tag e conta |
| **GuardDuty / Security Hub (Security Lake)** | Achados de segurança |

### Exemplos

```sql
-- CloudTrail: tentativas negadas por identidade (últimas 24 h)
SELECT useridentity.arn, eventname, count(*) AS negadas
FROM cloudtrail_logs
WHERE year='2026' AND month='11' AND day='09'
  AND errorcode IN ('AccessDenied','UnauthorizedOperation')
GROUP BY useridentity.arn, eventname
ORDER BY negadas DESC LIMIT 20;

-- VPC Flow Logs: top destinos rejeitados
SELECT dstaddr, dstport, sum(packets) AS pacotes
FROM vpc_flow_logs
WHERE action = 'REJECT' AND day = '2026/11/09'
GROUP BY dstaddr, dstport
ORDER BY pacotes DESC LIMIT 20;

-- ALB: p99 de latência por URL
SELECT request_url, approx_percentile(target_processing_time, 0.99) AS p99,
       count(*) AS requisicoes
FROM alb_logs
WHERE day = '2026/11/09' AND target_processing_time >= 0
GROUP BY request_url
HAVING count(*) > 100
ORDER BY p99 DESC LIMIT 20;

-- CUR: custo por serviço no mês
SELECT line_item_product_code AS servico,
       round(sum(line_item_unblended_cost), 2) AS custo
FROM cur_tabela
WHERE year='2026' AND month='11'
GROUP BY line_item_product_code
ORDER BY custo DESC LIMIT 15;
```

> [!tip] Use os modelos da AWS
> A documentação e os consoles dos serviços fornecem o **DDL pronto** para as tabelas de logs (com **partition projection**). Reaproveite e adapte; evite escrever o esquema do zero.

## Funções SQL que valem conhecer

| Categoria | Funções úteis | Exemplo |
|---|---|---|
| **Datas e tempo** | `date_trunc`, `date_add`, `date_diff`, `from_iso8601_timestamp`, `at_timezone` | `date_trunc('hour', criado_em)` |
| **JSON** | `json_extract`, `json_extract_scalar`, `json_parse`, `json_format` | `json_extract_scalar(payload, '$.cliente.id')` |
| **Arrays e maps** | `cardinality`, `element_at`, `transform`, `filter`, `array_agg`, `UNNEST` | `CROSS JOIN UNNEST(itens) AS t(item)` |
| **Janela** | `row_number()`, `rank()`, `lag()`, `lead()`, `sum() OVER (...)` | Top N por grupo |
| **Strings** | `regexp_extract`, `regexp_like`, `split`, `substr`, `lower`, `concat` | Extrair campos de logs |
| **Agregação aproximada** | `approx_distinct`, `approx_percentile`, `approx_most_frequent` | Cardinalidade rápida |
| **Condicionais** | `CASE`, `COALESCE`, `NULLIF`, `TRY` | `TRY(cast(x as int))` |
| **Geoespaciais** | `ST_Point`, `ST_Distance`, `ST_Contains` | Análises de localização |

```sql
-- Top 3 pedidos por cliente (função de janela)
SELECT * FROM (
  SELECT cliente_id, pedido_id, valor,
         row_number() OVER (PARTITION BY cliente_id ORDER BY valor DESC) AS posicao
  FROM lake.pedidos WHERE ano='2026' AND mes='11'
) WHERE posicao <= 3;

-- Expandir um array de itens do pedido
SELECT p.pedido_id, item.sku, item.quantidade
FROM lake.pedidos_json p
CROSS JOIN UNNEST(p.itens) AS t(item)
WHERE p.dia = '2026-11-09';

-- Evitar falha por dado sujo
SELECT TRY(cast(valor_texto AS double)) AS valor FROM lake.bruto_pedidos;
```

> [!tip] `TRY()` salva consultas de dados imperfeitos
> Em data lakes, valores inválidos são comuns. `TRY(expressao)` devolve `NULL` em vez de abortar a consulta inteira.

## Views e consultas nomeadas

| Recurso | Uso |
|---|---|
| **View** | Consulta salva e **reutilizável** (armazenada no catálogo); encapsula **filtros, junções e regras** |
| **Named queries** | Consultas salvas no console, compartilháveis por workgroup |
| **Prepared statements** | Consultas **parametrizadas**, evitando concatenação de strings |
| **Views com colunas protegidas** | Expõem apenas colunas permitidas aos analistas |

```sql
CREATE OR REPLACE VIEW lake.vw_vendas_mes_atual AS
SELECT pedido_id, cliente_id, valor, status, criado_em
FROM lake.pedidos
WHERE ano = date_format(current_date, '%Y')
  AND mes = date_format(current_date, '%m');

SELECT status, sum(valor) FROM lake.vw_vendas_mes_atual GROUP BY status;
```

| Cuidado com views | Detalhe |
|---|---|
| **A view não armazena dados** | Cada consulta reexecuta a definição |
| **Poda de partição** | Depende de a view expor/filtrar a coluna de partição |
| **Permissões** | Quem consulta a view precisa de acesso às tabelas base (a menos que use Lake Formation) |
| **Views dependentes** | Alterar a base pode quebrar as views |

### Prepared statements

```sql
PREPARE consulta_status FROM
  SELECT count(*) FROM lake.pedidos WHERE status = ? AND ano = ? AND mes = ?;

EXECUTE consulta_status USING 'PAGO', '2026', '11';
```

Evitam **injeção de SQL** quando o SQL é montado por aplicações e facilitam reuso.

## Federated queries

As **consultas federadas** permitem consultar **fontes fora do S3** com SQL do Athena, **sem mover os dados**, usando **conectores** (funções **Lambda**) fornecidos pela AWS ou criados por você.

```
 Athena ──SQL──► Conector (Lambda) ──► RDS / Aurora / DynamoDB / Redshift / DocumentDB /
                                       OpenSearch / CloudWatch Logs / Redis / HBase / ...
                         │
                         └─ spill de dados grandes em S3 (bucket de "spill")
```

| Conector (exemplos) | Fonte |
|---|---|
| **JDBC** (MySQL, PostgreSQL, SQL Server, Oracle) | Bancos relacionais, RDS e on-premises |
| **DynamoDB** | Tabelas NoSQL |
| **Redshift** | Warehouse |
| **DocumentDB / MongoDB** | Documentos |
| **OpenSearch / Elasticsearch** | Índices de busca |
| **CloudWatch Logs / Metrics** | Logs e métricas operacionais |
| **Redis / Memcached, HBase, Cloudera, Neptune** | Outros |
| **Conectores customizados** | Via **Athena Query Federation SDK** |

```sql
-- Junta dados do S3 (data lake) com uma tabela do RDS (MySQL) em uma só consulta
SELECT l.cliente_id, c.nome, sum(l.valor) AS total
FROM lake.pedidos l
JOIN "lambda:conector_mysql".crm.clientes c ON l.cliente_id = c.id
WHERE l.ano = '2026' AND l.mes = '11'
GROUP BY l.cliente_id, c.nome;
```

| Boa prática | Motivo |
|---|---|
| **Replicas de leitura** para bancos transacionais | Não impactar produção |
| **Filtros e *predicate pushdown*** | O conector envia filtros à fonte, lendo menos |
| **Evitar `SELECT *`** de fontes grandes | Transferência e custo |
| **Bucket de spill com ciclo de vida** | Limpa dados temporários |
| **VPC e segurança** | Conector na mesma VPC do banco, com security groups restritos |
| **Credenciais no Secrets Manager** | Sem senhas em texto |
| **Limites de concorrência da Lambda** | Evita esgotar conexões do banco |

> [!warning] Federação não é para grandes volumes recorrentes
> Consultar **milhões de linhas** de um RDS por federação toda hora **sobrecarrega o banco** e é **lento**. Para cargas pesadas, **replique** os dados para o S3 (Parquet) com **DMS/Glue** e consulte lá; use federação para **consultas pontuais** e **enriquecimento**.

## UDFs (funções definidas pelo usuário)

Quando as funções nativas não bastam, o Athena aceita **UDFs** implementadas em **Lambda** (por exemplo, em Java ou Python).

| Característica | Detalhe |
|---|---|
| **Declaração** | `USING EXTERNAL FUNCTION nome(...) RETURNS tipo LAMBDA 'arn:aws:lambda:...'` |
| **Casos de uso** | Criptografia/descriptografia, tokenização, regras de negócio, validações especiais |
| **Desempenho** | Chamada por lote de linhas; custo de Lambda |
| **Governança** | A função fica sob IAM da conta |

```sql
USING EXTERNAL FUNCTION mascara_cpf(cpf VARCHAR) RETURNS VARCHAR
  LAMBDA 'arn:aws:lambda:us-east-1:123456789012:function:mascara-cpf'
SELECT cliente_id, mascara_cpf(cpf) AS cpf_mascarado FROM lake.clientes;
```

Use UDFs com **moderação**: cada chamada tem **latência e custo**, e a lógica fora do SQL é **mais difícil de manter**.

## Apache Spark no Athena

Além do SQL, o Athena oferece **sessões Apache Spark** em **notebooks interativos**, para análises que exigem **código** (Python/PySpark), **bibliotecas** ou **processamento complexo**, tudo **serverless**.

| Aspecto | SQL (Trino) | Spark (notebooks) |
|---|---|---|
| **Uso** | Consultas ad hoc | Análises programáticas, ML leve, transformações complexas |
| **Linguagem** | SQL | **PySpark/Python**, Spark SQL |
| **Início** | Imediato | Segundos (sessão com DPUs reservadas) |
| **Cobrança** | Por TB escaneado | Por **DPU-hora** da sessão |
| **Bibliotecas** | Funções do motor | pandas, matplotlib, etc. |
| **Quando preferir** | Exploração e relatórios | Visualização, preparação de dados, funções customizadas |

```python
# Notebook Spark no Athena
df = spark.sql("SELECT status, count(*) AS total FROM lake.pedidos WHERE ano='2026' GROUP BY status")
pdf = df.toPandas()
pdf.plot(kind='bar', x='status', y='total')
```

> [!tip] Comparação com Glue e EMR
> Para **pipelines agendados** e **ETL em produção**, **AWS Glue** (Spark gerenciado) ou **EMR** são mais adequados. O Spark do Athena brilha na **exploração interativa** e na **análise de dados** sem montar infraestrutura.

## Exemplo prático: investigação de segurança com SQL

1. Um alerta aponta atividade suspeita de uma role em horário incomum.
2. No **CloudTrail** (tabela Athena), a equipe lista todos os eventos da role nas últimas 48 h.
3. Cruza com **VPC Flow Logs** para ver os IPs de destino das conexões.
4. Faz **junção federada** com a tabela de ativos (RDS) para identificar o dono do recurso.
5. Usa `approx_distinct` e janelas para detectar **picos de `GetObject`** por identidade.
6. Salva as consultas como **named queries** e cria uma **view** `vw_atividade_suspeita` para uso recorrente.

## Troubleshooting

| Sintoma | Causa provável | Como resolver |
|---|---|---|
| Consulta federada falha | Conector sem acesso à rede/credencial | Verificar VPC, security group e Secrets Manager |
| Federação lenta | Sem filtros empurrados à fonte | Filtrar na consulta; usar réplica; replicar para S3 |
| Erro de função JSON | Campo ausente ou tipo inesperado | `json_extract_scalar` + `TRY`/`COALESCE` |
| UDF com timeout | Lambda lenta ou sem concorrência | Otimizar; aumentar timeout/concorrência |
| View lenta/cara | Sem filtro de partição | Expor e filtrar a coluna de partição |
| `Prepared statement not found` | Sessão/workgroup diferente | Preparar e executar no mesmo workgroup |
| Spark sem recursos | Limites de DPU/sessões | Ajustar sessões; reduzir paralelismo |
| `AccessDenied` na federação | Permissões do conector/IAM | Revisar roles da Lambda e do usuário |
| Dados de log "vazios" | Partição/projeção incorretas | Revisar `LOCATION` e projeção |

## Erros comuns e armadilhas

- **Federar milhões de linhas** de um banco de produção de forma recorrente.
- **UDFs para tudo**, aumentando custo e fragilidade.
- **Views sem filtros de partição**, escaneando o histórico completo.
- **Montar SQL por concatenação** em aplicações (risco de injeção).
- **Esquecer `TRY()`** em dados sujos.
- **Conectores sem controle de rede e credenciais.**
- **Usar Spark do Athena para ETL de produção** em vez de Glue/EMR.
- **Escrever esquemas de logs à mão** em vez de usar modelos prontos com projeção.

## 🧩 Quiz de Fixação

1. Como o Athena consulta fontes como RDS e DynamoDB?
2. Para que serve a função `TRY()`?
3. Qual a vantagem de views para analistas?
4. Quando usar o Spark do Athena em vez de SQL?
5. Qual o risco de federar grandes volumes de um banco de produção?
6. Para que servem os prepared statements?

**Respostas:**
1) Por federated queries: conectores (funções Lambda) acessam a fonte, e o Athena junta os dados com o S3 em uma só consulta.
2) Retornar NULL em vez de falhar a consulta inteira quando uma expressão tem dados inválidos.
3) Encapsulam filtros, junções e regras em uma consulta reutilizável, dando consistência e uma interface estável.
4) Quando a análise exige código (PySpark), bibliotecas, visualização ou transformações complexas em modo interativo.
5) Sobrecarregar o banco e obter consultas lentas; para cargas recorrentes é melhor replicar os dados para o S3.
6) Parametrizar consultas, evitando concatenação de strings (injeção de SQL) e facilitando reuso.
