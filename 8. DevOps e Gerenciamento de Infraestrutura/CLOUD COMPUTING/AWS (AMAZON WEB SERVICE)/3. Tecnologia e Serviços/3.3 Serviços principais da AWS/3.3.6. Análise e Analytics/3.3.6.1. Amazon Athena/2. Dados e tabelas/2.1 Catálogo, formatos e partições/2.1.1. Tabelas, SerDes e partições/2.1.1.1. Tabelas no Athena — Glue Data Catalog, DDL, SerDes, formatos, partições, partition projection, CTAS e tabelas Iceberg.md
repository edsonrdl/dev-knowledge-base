### Tabelas no Athena — Glue Data Catalog, DDL, SerDes, formatos, partições, partition projection, CTAS e tabelas Iceberg

> [!warning] Aviso
> Sintaxe de DDL, propriedades de tabela, suporte a formatos (Iceberg, Hudi, Delta), limites de partições e recursos do catálogo mudam. Os exemplos aqui são referências de estudo; confirme na documentação. As consultas **não foram executadas**.

No Athena, **tudo gira em torno das tabelas**: sem uma tabela bem definida, os arquivos do S3 são **apenas bytes**. A tabela diz **onde estão os dados**, **em que formato**, **com que colunas** e **como estão organizados em pastas (partições)**. Acertar esse desenho é o que decide **custo, desempenho e confiabilidade** das consultas. Esta folha cobre o **Glue Data Catalog**, o **DDL**, os **formatos e SerDes**, as **partições** (inclusive **partition projection**), o **CTAS** para converter dados e as **tabelas Iceberg** para atualizações e transações.

**Analogia:** o S3 é um **armário com milhares de pastas soltas**. A **tabela** é o **índice da biblioteca**: diz que as pastas "2026/11/09" guardam vendas, com colunas "valor" e "cliente", em tal formato. As **partições** são **gavetas rotuladas por data**: para saber das vendas de ontem, você abre **só a gaveta de ontem**, e não o armário inteiro.

## Glue Data Catalog

O Athena usa o **AWS Glue Data Catalog** como repositório de metadados.

| Elemento | Descrição |
|---|---|
| **Database (banco)** | Agrupamento lógico de tabelas (um *schema*) |
| **Table (tabela)** | Definição: colunas, tipos, formato, localização, partições |
| **Partition** | Subconjunto da tabela mapeado a um caminho do S3 |
| **Crawler (Glue)** | Varre o S3 e **descobre** esquemas e partições automaticamente |
| **Compartilhamento** | O mesmo catálogo serve Athena, Glue, EMR, Redshift Spectrum e Lake Formation |

| Forma de criar tabelas | Quando usar |
|---|---|
| **DDL manual** (`CREATE EXTERNAL TABLE`) | Controle total e reprodutibilidade (em IaC) |
| **Glue Crawler** | Descoberta inicial de dados desconhecidos |
| **CTAS** (`CREATE TABLE AS SELECT`) | Criar tabela a partir de uma consulta, já convertendo formato |
| **Console (wizard)** | Aprendizado e protótipos |
| **CloudFormation/Terraform** | Produção, com versionamento |

> [!tip] Catálogo é infraestrutura compartilhada
> Alterar uma tabela no Glue Data Catalog afeta **todos os serviços** que a usam. Trate esquemas como **contratos**: mudanças devem ser **revisadas e versionadas**.

## DDL essencial

```sql
-- Banco
CREATE DATABASE IF NOT EXISTS lake;

-- Tabela externa em Parquet, particionada por ano/mês/dia
CREATE EXTERNAL TABLE lake.eventos (
  evento_id   string,
  usuario_id  bigint,
  tipo        string,
  valor       double,
  criado_em   timestamp
)
PARTITIONED BY (ano string, mes string, dia string)
STORED AS PARQUET
LOCATION 's3://meu-datalake/curado/eventos/'
TBLPROPERTIES ('parquet.compression'='SNAPPY');

-- Descobrir partições existentes no S3 (padrão Hive: ano=2026/mes=11/dia=09/)
MSCK REPAIR TABLE lake.eventos;

-- Adicionar uma partição manualmente
ALTER TABLE lake.eventos ADD IF NOT EXISTS
  PARTITION (ano='2026', mes='11', dia='09')
  LOCATION 's3://meu-datalake/curado/eventos/ano=2026/mes=11/dia=09/';

-- Inspecionar
SHOW TABLES IN lake;
SHOW PARTITIONS lake.eventos;
DESCRIBE lake.eventos;
SHOW CREATE TABLE lake.eventos;
```

| Comando | Função |
|---|---|
| `CREATE EXTERNAL TABLE` | Define uma tabela sobre dados do S3 |
| `MSCK REPAIR TABLE` | Registra partições no padrão `chave=valor/` |
| `ALTER TABLE ... ADD PARTITION` | Registra uma partição específica |
| `ALTER TABLE ... SET TBLPROPERTIES` | Altera propriedades |
| `DROP TABLE` | Remove a definição (não os dados, em tabelas externas) |
| `SHOW CREATE TABLE` | Exibe o DDL (útil para versionar) |

## Formatos, SerDes e compressão

O **SerDe** (*serializer/deserializer*) **interpreta os bytes** do arquivo como linhas e colunas.

| Formato | SerDe / declaração | Observações |
|---|---|---|
| **CSV** | `OpenCSVSerDe` ou `LazySimpleSerDe` (`ROW FORMAT DELIMITED`) | Cabeçalho: `skip.header.line.count`; cuidado com aspas e vírgulas internas |
| **JSON** | `org.openx.data.jsonserde.JsonSerDe` ou `Hive JsonSerDe` | Um objeto JSON por linha (JSON Lines) |
| **Parquet** | `STORED AS PARQUET` | Colunar; **recomendado** |
| **ORC** | `STORED AS ORC` | Colunar |
| **Avro** | `STORED AS AVRO` | Com esquema embutido |
| **Logs com regex** | `RegexSerDe` | Logs de texto (ALB, Apache) |
| **Ion, CloudTrail, Grok** | SerDes específicos | Formatos especiais |

| Compressão | Observação |
|---|---|
| **Snappy** | Padrão em Parquet; rápida e boa |
| **Gzip** | Boa taxa, mas **não divisível** em texto (um arquivo = uma tarefa) |
| **Zstd** | Boa taxa e velocidade |
| **Bzip2** | Divisível; mais lenta |

> [!warning] CSV/JSON com GZIP: arquivos grandes não paralelizam
> Um arquivo `.gz` de texto **não pode ser dividido** entre trabalhadores: um único arquivo de 5 GB vira **uma única tarefa**. Prefira **vários arquivos médios** ou, melhor, **Parquet**.

## Partições: a maior alavanca de custo

**Particionar** é organizar os dados em **pastas por valor de coluna**, de modo que a consulta **leia só as pastas necessárias**.

```
 s3://meu-datalake/curado/eventos/
   ano=2026/mes=10/dia=31/arquivo-001.parquet
   ano=2026/mes=11/dia=01/arquivo-001.parquet
   ano=2026/mes=11/dia=02/arquivo-001.parquet   ← uma consulta com WHERE dia='02' lê SÓ esta
```

| Regra | Efeito |
|---|---|
| **Filtrar pela coluna de partição** no `WHERE` | O Athena **poda** (*partition pruning*) e ignora o resto |
| **Escolher colunas de partição de baixa/média cardinalidade** | Data, região, tipo de evento |
| **Evitar particionar demais** | Milhões de partições pequenas **prejudicam** o planejamento e o catálogo |
| **Tamanho ideal por partição** | Idealmente **centenas de MB a alguns GB** por partição |
| **Ordem das colunas** | Da mais usada em filtros (data) para a menos |

```sql
-- Bom: usa a partição
SELECT count(*) FROM lake.eventos WHERE ano='2026' AND mes='11' AND dia='09';

-- Ruim: filtra por coluna que não é partição; lê tudo
SELECT count(*) FROM lake.eventos WHERE date(criado_em) = date '2026-11-09';
```

> [!tip] Sempre filtre pela coluna de partição
> Mesmo que exista uma coluna de data nos dados, **a poda só acontece na coluna de partição**. Adicione sempre o filtro `ano/mes/dia` à consulta (ou use *views* que o façam).

### Partition projection

Em tabelas com **muitas partições** (por exemplo, uma por dia por anos), **registrar partições no catálogo** (via `MSCK` ou `ADD PARTITION`) é **lento e trabalhoso**. A **partition projection** faz o Athena **calcular as partições em memória** a partir de regras nas propriedades da tabela, **sem consultar o catálogo**.

```sql
CREATE EXTERNAL TABLE lake.alb_logs (
  tipo string, hora string, elb string, cliente string, status int, url string
)
PARTITIONED BY (dia string)
STORED AS PARQUET
LOCATION 's3://meu-datalake/logs/alb/'
TBLPROPERTIES (
  'projection.enabled'='true',
  'projection.dia.type'='date',
  'projection.dia.format'='yyyy/MM/dd',
  'projection.dia.range'='2025/01/01,NOW',
  'projection.dia.interval'='1',
  'projection.dia.interval.unit'='DAYS',
  'storage.location.template'='s3://meu-datalake/logs/alb/${dia}/'
);
```

| Vantagem | Observação |
|---|---|
| **Sem `MSCK REPAIR`** nem jobs de registro | Novas partições "existem" automaticamente |
| **Planejamento mais rápido** | Sem listar milhares de partições no catálogo |
| **Ideal para logs** | Datas, IDs previsíveis |
| **Limitação** | Padrão de pastas precisa ser **previsível**; o Athena **não valida** se a pasta existe |

## CTAS: converter e reorganizar dados

O **CTAS** cria uma **nova tabela a partir de uma consulta**, gravando os resultados no S3 no **formato, compressão e partições** escolhidos. É a **ferramenta de ETL em SQL** do Athena.

```sql
CREATE TABLE lake.eventos_curado
WITH (
  format            = 'PARQUET',
  parquet_compression = 'SNAPPY',
  external_location = 's3://meu-datalake/curado/eventos_curado/',
  partitioned_by    = ARRAY['ano','mes','dia']
) AS
SELECT evento_id, usuario_id, tipo, valor, criado_em,
       date_format(criado_em, '%Y') AS ano,
       date_format(criado_em, '%m') AS mes,
       date_format(criado_em, '%d') AS dia
FROM lake.eventos_bruto
WHERE criado_em >= timestamp '2026-01-01 00:00:00';
```

| Opção do CTAS | Função |
|---|---|
| `format` | `PARQUET`, `ORC`, `AVRO`, `JSON`, `TEXTFILE` |
| `partitioned_by` | Colunas de partição (**no fim** da lista do `SELECT`) |
| `bucketed_by` e `bucket_count` | **Bucketing** (distribuição por hash para junções) |
| `write_compression` | Compressão |
| `bucket_count` / tamanho de arquivo | Controla o número de arquivos de saída |

| Limite do CTAS | Observação |
|---|---|
| **Máximo de partições por consulta** | Limitado (por volta de 100 por consulta de escrita; use lotes) |
| **Local de saída** | Deve estar vazio |
| **Falhas parciais** | Limpe o destino antes de repetir |

```sql
-- Carga incremental em lotes (INSERT INTO)
INSERT INTO lake.eventos_curado
SELECT ... FROM lake.eventos_bruto WHERE criado_em >= timestamp '2026-11-09 00:00:00';
```

> [!warning] Cuidado com a explosão de arquivos pequenos
> Muitas partições com pouco dado cada geram **muitos arquivos minúsculos**. Combine **partições razoáveis** com **compactação periódica** (CTAS/INSERT reescrevendo, ou Iceberg `OPTIMIZE`).

## Tabelas Iceberg

O **Apache Iceberg** é um **formato de tabela aberto** que adiciona **transações, evolução de esquema e viagem no tempo** ao data lake. O Athena suporta Iceberg **nativamente**.

| Recurso | Vantagem |
|---|---|
| **`INSERT`, `UPDATE`, `DELETE`, `MERGE`** | Alterações a nível de linha (ACID) em dados no S3 |
| **Evolução de esquema** | Adicionar, renomear e remover colunas sem reescrever dados |
| **Partition evolution** | Mudar a estratégia de partição sem recriar a tabela |
| **Time travel** | Consultar versões anteriores (`FOR TIMESTAMP AS OF`) |
| **Compactação** | `OPTIMIZE ... REWRITE DATA USING BIN_PACK` |
| **Limpeza** | `VACUUM` remove snapshots e arquivos antigos |
| **Partição oculta** | Particiona por transformação (`day(criado_em)`), sem coluna extra |

```sql
CREATE TABLE lake.pedidos_iceberg (
  pedido_id bigint, cliente_id bigint, valor double, status string, atualizado_em timestamp
)
PARTITIONED BY (day(atualizado_em))
LOCATION 's3://meu-datalake/iceberg/pedidos/'
TBLPROPERTIES ('table_type'='ICEBERG', 'format'='parquet');

-- Atualização linha a linha
MERGE INTO lake.pedidos_iceberg t
USING lake.pedidos_novos s ON t.pedido_id = s.pedido_id
WHEN MATCHED THEN UPDATE SET status = s.status, atualizado_em = s.atualizado_em
WHEN NOT MATCHED THEN INSERT VALUES (s.pedido_id, s.cliente_id, s.valor, s.status, s.atualizado_em);

-- Viagem no tempo
SELECT * FROM lake.pedidos_iceberg FOR TIMESTAMP AS OF (current_timestamp - interval '1' day);

-- Manutenção
OPTIMIZE lake.pedidos_iceberg REWRITE DATA USING BIN_PACK;
VACUUM lake.pedidos_iceberg;
```

| Tabela Hive (padrão) | Tabela Iceberg |
|---|---|
| Somente anexa (`INSERT`) e reescreve por partição | **ACID**, `UPDATE`/`DELETE`/`MERGE` |
| Esquema rígido | Evolução de esquema fácil |
| Partições por pastas | Metadados do Iceberg; partição oculta |
| Sem histórico | **Time travel** |
| Simples, universal | Exige **manutenção** (compactar e limpar) |

> [!tip] Quando usar Iceberg
> Quando há **atualizações ou deleções** (CDC, LGPD "direito ao esquecimento"), **esquemas que evoluem** ou necessidade de **consistência transacional**. Para **logs append-only**, Parquet particionado simples continua sendo mais simples e barato.

## Boas práticas de modelagem

| Prática | Motivo |
|---|---|
| **Separar camadas** (bruto → curado → analítico) | Governança e reprocessamento |
| **Parquet + Snappy/Zstd** na camada curada | Custo e desempenho |
| **Particionar por data** (e no máximo mais uma coluna de baixa cardinalidade) | Poda eficiente |
| **Arquivos de 128 MB a 1 GB** | Equilíbrio entre paralelismo e overhead |
| **Esquemas versionados** (DDL em Git/IaC) | Reprodutibilidade |
| **Views** para encapsular filtros e regras | Consistência para analistas |
| **Convenções de nomes** (`bruto_`, `curado_`) | Clareza |
| **Tipos corretos** (`timestamp`, `decimal`) | Menos erros e conversões |

## Exemplo prático: do CSV bruto ao Parquet particionado

1. Os pedidos chegam diariamente em **CSV** no bucket `bruto/pedidos/`.
2. Cria-se a tabela `bruto_pedidos` (CSV) para exploração inicial.
3. Um job diário executa `CTAS/INSERT INTO` para a tabela `curado_pedidos` em **Parquet**, particionada por `ano/mes/dia`.
4. A tabela curada usa **partition projection**, dispensando `MSCK REPAIR`.
5. As consultas dos analistas passam a escanear **uma fração** do volume original, com filtros por dia.
6. Uma *view* `vw_pedidos_mes_atual` encapsula o filtro de data para o BI.

## Troubleshooting

| Sintoma | Causa provável | Como resolver |
|---|---|---|
| Consulta retorna **0 linhas** | Partições não registradas | `MSCK REPAIR TABLE` ou partition projection |
| `HIVE_BAD_DATA` / erro de tipo | Dados não batem com o esquema | Ajustar tipos; tratar dados sujos; usar `string` e converter |
| `HIVE_PARTITION_SCHEMA_MISMATCH` | Esquema da partição diferente do da tabela | Recriar partições ou alinhar esquemas |
| CSV com colunas deslocadas | Vírgulas dentro de campos | Usar `OpenCSVSerDe` com aspas |
| Muitas linhas com cabeçalho | Faltou `skip.header.line.count` | Adicionar a propriedade |
| Consulta lenta com poucos GB | Milhares de arquivos pequenos | Compactar (CTAS/OPTIMIZE) |
| `TOO_MANY_OPEN_PARTITIONS` | CTAS escrevendo > limite de partições | Escrever em lotes |
| Erro ao ler arquivos recém-gravados | Consistência/arquivos em escrita | Reexecutar; evitar ler durante gravação |
| `AccessDenied` no S3 | Permissões do bucket/KMS | Ajustar IAM/política do bucket e da chave |
| Projection retorna partições vazias | Padrão de pastas não coincide | Revisar `storage.location.template` |

## Erros comuns e armadilhas

- **Não particionar** (ou **particionar demais**).
- **Filtrar por coluna que não é partição** esperando poda.
- **Dados em CSV/JSON** na camada de consumo.
- **Arquivos pequenos em excesso** e sem compactação.
- **`SELECT *`** em tabelas largas.
- **Alterar esquemas** no catálogo sem avisar consumidores.
- **Usar Iceberg sem manutenção** (`OPTIMIZE` e `VACUUM`).
- **Esquecer de limpar** o destino antes de repetir um CTAS.

## 🧩 Quiz de Fixação

1. O que a tabela externa guarda no Athena?
2. Por que o filtro deve usar a coluna de partição?
3. Para que serve a partition projection?
4. O que faz um CTAS?
5. Qual a vantagem do Iceberg sobre uma tabela Parquet simples?
6. Por que arquivos pequenos em excesso são um problema?

**Respostas:**
1) Apenas os metadados (local, formato, colunas, partições); os dados permanecem como arquivos no S3.
2) Porque a poda de partições só ocorre na coluna de partição; filtrar por outra coluna faz o Athena ler todos os dados.
3) Calcular as partições em memória a partir de regras, sem registrá-las no catálogo, simplificando tabelas com muitas partições previsíveis.
4) Cria uma nova tabela a partir de uma consulta, gravando os resultados no S3 no formato, compressão e partições escolhidos (ETL em SQL).
5) Transações ACID (UPDATE, DELETE, MERGE), evolução de esquema e de partição, e time travel.
6) Cada arquivo gera overhead de abertura e planejamento, degradando desempenho e aumentando o tempo e o custo das consultas.
