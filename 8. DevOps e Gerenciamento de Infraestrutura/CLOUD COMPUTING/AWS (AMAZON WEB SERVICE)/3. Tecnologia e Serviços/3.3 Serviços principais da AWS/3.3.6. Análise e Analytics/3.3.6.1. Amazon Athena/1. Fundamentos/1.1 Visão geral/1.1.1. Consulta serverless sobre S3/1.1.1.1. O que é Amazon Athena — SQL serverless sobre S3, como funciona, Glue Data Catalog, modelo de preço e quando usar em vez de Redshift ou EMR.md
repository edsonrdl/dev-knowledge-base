### O que é Amazon Athena — SQL serverless sobre S3, como funciona, Glue Data Catalog, modelo de preço e quando usar em vez de Redshift ou EMR

> [!warning] Aviso
> Versões do motor, preços por TB escaneado, limites de consulta, quotas e recursos (Spark, capacidade provisionada, Iceberg) mudam. Os números aqui são referências de estudo; confirme na documentação oficial. Os comandos e consultas são exemplos e **não foram executados**.

O **Amazon Athena** é um serviço de **consulta interativa e serverless** que permite **analisar dados diretamente no Amazon S3 usando SQL padrão**, **sem provisionar servidores, clusters nem carregar os dados** em um banco. Você **aponta para os arquivos** (CSV, JSON, Parquet, ORC, logs), **define uma tabela** (esquema) e **consulta**. Paga-se, em geral, **apenas pelo volume de dados escaneado** em cada consulta.

Isso muda a lógica clássica de análise: em vez de **mover os dados para o banco** (ETL pesado), **leva-se a consulta até os dados**, que permanecem no **S3** (o *data lake*).

**Analogia:** o S3 é um **grande depósito de arquivos** e o Athena é um **bibliotecário-relâmpago**: você faz a pergunta em SQL e ele **vasculha as estantes certas**, devolve a resposta e vai embora. Você **não aluga o bibliotecário** (sem servidor), **não reorganiza o depósito para ele** (sem carga) e **paga por quantas páginas ele leu** (dados escaneados). Quanto melhor **organizados** estiverem os livros (partições, formato colunar), **menos páginas ele precisa ler** e **mais barato** fica.

## Como o Athena funciona

```
 Você (console / CLI / JDBC / BI)
        │  SQL
        ▼
 ┌─────────────────────────────────────────────────┐
 │                 AMAZON ATHENA                   │
 │   Motor de consulta distribuído (Trino/Presto)  │
 │   Capacidade gerenciada pela AWS (serverless)   │
 └───────┬─────────────────────────────┬───────────┘
         │ metadados (esquema, partições)│ lê dados
         ▼                              ▼
 AWS Glue Data Catalog             Amazon S3 (data lake)
 (bancos, tabelas, colunas,        (arquivos: Parquet, ORC, CSV, JSON...)
  partições)
         │
         ▼
   Resultados ──► bucket S3 de resultados (CSV) ──► console, BI, aplicações
```

| Componente | Função |
|---|---|
| **Motor de consulta** | Executa SQL em paralelo (baseado em **Trino/Presto**) |
| **Glue Data Catalog** | **Catálogo de metadados**: bancos de dados, tabelas, colunas, partições |
| **S3 (dados)** | Armazena os arquivos consultados; **o dado fica lá** |
| **S3 (resultados)** | Local onde o Athena grava o **resultado** de cada consulta |
| **Workgroup** | Agrupa consultas com **configurações, limites e custos** próprios |
| **Tabela externa** | Definição que **aponta** para um caminho do S3 (não copia dados) |

> [!tip] O Athena não guarda os seus dados
> Apagar uma **tabela** no Athena apaga **apenas a definição** (metadados), **não os arquivos** do S3 (em tabelas externas). Já **dropar** uma tabela **Iceberg** gerenciada pode remover dados. Saiba qual tipo de tabela você está usando.

## Modelo de preço (referência)

| Item | Como é cobrado |
|---|---|
| **Consultas SQL (padrão)** | **Por TB de dados escaneados** (com um mínimo por consulta) |
| **Consultas com falha** | Não cobradas |
| **Comandos DDL** (`CREATE TABLE`, `DROP`) | Sem custo |
| **Capacidade provisionada** | Por **DPU-hora** (reserva de capacidade dedicada) |
| **Consultas federadas** | Funções Lambda (conectores) cobradas à parte |
| **Apache Spark (notebooks)** | Por **DPU-hora** de uso |
| **S3 e Glue** | Armazenamento dos dados, solicitações e catálogo (Glue Data Catalog tem camada gratuita) |

```
 custo da consulta ≈ (bytes escaneados ÷ 1 TB) × preço por TB
```

| Exemplo (valores ilustrativos) | Resultado |
|---|---|
| 1 TB em **CSV** consultado por completo | 1 TB escaneado |
| Os mesmos dados em **Parquet** + **partições**, lendo só 3 colunas e 1 mês | Pode escanear **menos de 1% do volume** |
| 100 consultas por dia no mesmo dataset mal organizado | Custo multiplicado por 100 |

> [!warning] "Serverless" não significa "grátis"
> Uma consulta `SELECT *` sobre um data lake de dezenas de TB em CSV **custa caro e é lenta**. O **segredo do Athena** está em **reduzir o volume lido**: **formato colunar**, **compressão**, **partições** e **seleção de colunas**.

## Formatos de dados suportados

| Formato | Tipo | Quando usar |
|---|---|---|
| **CSV / TSV** | Linha, texto | Dados brutos de origem; evitar para consultas frequentes |
| **JSON** | Linha, texto (semi-estruturado) | Logs de aplicação, eventos |
| **Parquet** | **Colunar**, binário | **Padrão recomendado** para análise |
| **ORC** | **Colunar**, binário | Ecossistema Hive/EMR; bom desempenho |
| **Avro** | Linha, binário, com esquema | Streaming e evolução de esquema |
| **Logs (Apache, ALB, CloudTrail, VPC Flow)** | Texto/JSON com formatos conhecidos | Análise operacional e de segurança |
| **Iceberg / Hudi / Delta** | **Formatos de tabela** com transações | Atualizações, deleções e *time travel* (Iceberg é suportado nativamente) |

## Primeira consulta, de ponta a ponta

```sql
-- 1. Cria um banco de dados lógico
CREATE DATABASE vendas;

-- 2. Cria uma tabela externa apontando para arquivos CSV no S3
CREATE EXTERNAL TABLE vendas.pedidos_csv (
  pedido_id   bigint,
  cliente_id  bigint,
  valor       double,
  data_pedido string,
  status      string
)
ROW FORMAT DELIMITED FIELDS TERMINATED BY ','
STORED AS TEXTFILE
LOCATION 's3://meu-datalake/bruto/pedidos/'
TBLPROPERTIES ('skip.header.line.count'='1');

-- 3. Consulta
SELECT status, count(*) AS total, sum(valor) AS faturamento
FROM vendas.pedidos_csv
WHERE data_pedido >= '2026-10-01'
GROUP BY status
ORDER BY faturamento DESC;
```

```bash
# Pela CLI
aws athena start-query-execution \
  --query-string "SELECT status, count(*) FROM vendas.pedidos_csv GROUP BY status" \
  --work-group primary \
  --result-configuration OutputLocation=s3://meu-bucket-resultados/athena/

aws athena get-query-execution --query-execution-id <id> \
  --query 'QueryExecution.[Status.State,Statistics.DataScannedInBytes]'
aws athena get-query-results --query-execution-id <id>
```

| Estado da consulta | Significado |
|---|---|
| **QUEUED** | Aguardando recursos |
| **RUNNING** | Em execução |
| **SUCCEEDED** | Concluída; resultado no S3 |
| **FAILED** | Erro (ver `StateChangeReason`) |
| **CANCELLED** | Cancelada |

O campo **`DataScannedInBytes`** é o indicador de **custo** de cada consulta: aprenda a olhá-lo.

## Athena vs outras opções de análise

| Critério | **Athena** | **Redshift** | **EMR (Spark/Presto)** | **RDS/Aurora** |
|---|---|---|---|---|
| Modelo | Serverless, SQL sobre S3 | **Data warehouse** (cluster ou serverless) | Cluster gerenciado de big data | Banco relacional transacional |
| Onde estão os dados | **S3** (sem carga) | Armazenamento próprio (ou Spectrum no S3) | HDFS/S3 | Armazenamento do banco |
| Carga de trabalho | Consultas **ad hoc** e exploratórias | **BI intenso**, alta concorrência, dashboards | ETL complexo, ML, processamento customizado | **OLTP** |
| Latência | Segundos a minutos | **Sub-segundo a segundos** (otimizado) | Variável | Milissegundos |
| Esforço de operação | **Mínimo** | Médio (ou baixo no serverless) | Alto | Médio |
| Custo | Por TB escaneado | Por nó/RPU | Por instância/hora | Por instância |
| Ideal para | Logs, data lake, análises esporádicas | Relatórios recorrentes em larga escala | Pipelines de transformação pesados | Aplicações |

```
 Tenho dados no S3 e quero explorá-los com SQL agora, sem montar infraestrutura?  ─► Athena
 Tenho dashboards de BI com muitos usuários simultâneos e SLAs apertados?         ─► Redshift
 Preciso de transformação pesada, Spark customizado, ML em larga escala?          ─► EMR / Glue (Spark)
 Preciso de transações e baixa latência por registro?                              ─► RDS / Aurora / DynamoDB
```

> [!tip] Athena e Redshift não são rivais, são complementares
> Um padrão comum: **dados brutos e históricos no S3 consultados pelo Athena**, e **dados quentes e agregados no Redshift** para BI intenso. O **Redshift Spectrum** também consulta o S3.

## Limitações e quando não usar

| Limitação | Implicação |
|---|---|
| **Não é banco transacional** | Sem `UPDATE` linha a linha eficiente (exceto tabelas Iceberg) |
| **Latência de segundos a minutos** | Não serve para aplicações que exigem milissegundos |
| **Concorrência e quotas** | Há limites de consultas simultâneas por conta/região |
| **Custo por escaneamento** | Datasets mal organizados ficam caros |
| **Arquivos pequenos em excesso** | Degradam muito o desempenho |
| **Dependência do esquema** | O esquema é aplicado na leitura (*schema on read*); dados "sujos" geram erros |
| **Tempo limite de consulta** | Consultas muito longas atingem limites (ajustáveis) |

## Exemplo prático: análise de logs do ALB

1. Os logs do **Application Load Balancer** são gravados em um bucket S3 (um arquivo por poucos minutos).
2. Cria-se uma **tabela particionada por data** (com *partition projection*) apontando para o bucket.
3. A equipe consulta **erros 5xx por URL e por hora** e o tempo médio de resposta.
4. Uma consulta mostra que um único endpoint concentra 80% dos erros.
5. Os logs são convertidos para **Parquet** com `CTAS`, reduzindo o custo das consultas seguintes em mais de 90%.
6. Um **workgroup** com limite de dados por consulta evita sustos de custo.

```sql
SELECT date_trunc('hour', from_iso8601_timestamp(time)) AS hora,
       request_url, count(*) AS erros
FROM alb_logs
WHERE day = '2026/11/09'
  AND elb_status_code >= 500
GROUP BY 1, 2
ORDER BY erros DESC
LIMIT 20;
```

## Erros comuns e armadilhas

- **Usar `SELECT *`** em tabelas largas e grandes.
- **Consultar CSV/JSON bruto** de forma recorrente em vez de converter para Parquet.
- **Esquecer partições** e escanear o histórico inteiro.
- **Milhares de arquivos minúsculos** no S3 (problema de *small files*).
- **Não definir workgroup nem limites**, ficando sem controle de custo.
- **Achar que `DROP TABLE` apaga os arquivos** (em tabelas externas, não apaga).
- **Esperar desempenho de banco transacional.**
- **Não proteger o bucket de resultados** (contém dados das consultas).

## 🧩 Quiz de Fixação

1. O que significa o Athena ser serverless?
2. Como o Athena cobra pelas consultas SQL?
3. Qual o papel do Glue Data Catalog?
4. Por que Parquet reduz o custo em relação ao CSV?
5. Quando preferir Redshift ao Athena?
6. O que acontece com os arquivos ao dropar uma tabela externa?

**Respostas:**
1) Não há servidores nem clusters para provisionar ou gerenciar: a AWS cuida da capacidade, e você consulta os dados diretamente no S3.
2) Pelo volume de dados escaneado por consulta (por TB), além de opções como capacidade provisionada; consultas com falha e DDL não são cobradas.
3) Guarda os metadados (bancos, tabelas, colunas, partições) usados pelo Athena para interpretar os arquivos no S3.
4) Por ser colunar e comprimido: lê só as colunas necessárias e menos bytes, reduzindo o dado escaneado.
5) Para BI intenso com muitos usuários simultâneos, baixa latência e dashboards recorrentes em larga escala.
6) Nada: apenas a definição da tabela (metadados) é removida; os arquivos continuam no S3.
