### 1.1.1.1. O que é AWS Lake Formation — data lake governado sobre S3 e Glue Data Catalog, permissões centralizadas, credential vending, serviços integrados e quando usar em vez de IAM e políticas de bucket

> [!warning] Aviso
> Modos de acesso, nomes de recursos, serviços integrados, recursos descontinuados (como tabelas “governed” e certas APIs) e limites abaixo são **de memória e mudam com frequência**. **Confirme na documentação do AWS Lake Formation.** Comandos e JSONs são ilustrativos e **não foram executados**. Nomes de bancos, buckets, contas e usuários são fictícios. Políticas de acesso a dados devem ser **testadas com usuários reais de cada perfil** antes de produção.

## 1. O problema que o Lake Formation resolve

Um **data lake** (dados brutos e tratados no **Amazon S3**, com catálogo no **Glue Data Catalog**) é ótimo para **centralizar dados**, mas traz um problema sério: **quem pode ver o quê?**

| Dor | Sem Lake Formation |
|---|---|
| **Permissões em camadas** | **IAM + políticas de bucket + ACLs + KMS** por serviço (Athena, Glue, EMR, Redshift Spectrum) — **espalhadas e inconsistentes** |
| **Granularidade** | O S3 controla **buckets/prefixos/objetos**, **não colunas nem linhas** — impossível dizer “o analista vê tudo **menos o CPF**” só com S3 |
| **Manutenção** | Cada novo dataset/usuário → **editar muitas políticas** (limites de tamanho de policy, erros) |
| **Multi-conta** | Compartilhar dados entre contas exige **bucket policies + roles + catálogo** manuais |
| **Auditoria** | Difícil responder “**quem acessou quais colunas**” |
| **Governança** | Sem **tags de classificação**, sem política **por atributo** |
| **Conformidade (LGPD/GDPR/HIPAA)** | Exige **mascarar/limitar** dados pessoais por perfil |

O **AWS Lake Formation** é o serviço que **constrói, protege e gerencia data lakes**: oferece **uma camada central de permissões** (estilo “banco de dados”: **GRANT/REVOKE** em **bancos, tabelas, colunas, linhas**) sobre o **Glue Data Catalog** e o **S3**, **aplicada de forma consistente** pelos serviços de análise integrados (**Athena, EMR, Redshift Spectrum, Glue, QuickSight**…).

> [!info] Em uma frase
> **Lake Formation = “permissões de banco de dados (tabela/coluna/linha) sobre dados no S3”, com catálogo, tags, compartilhamento multi-conta e auditoria centralizados.**

## 2. Visão geral da arquitetura

```
 Fontes (RDS, logs, streams, S3 bruto)        Armazenamento                   Catálogo                 Consumo
   │ ingestão (Glue/blueprints/DMS/Firehose)     ┌─────────────┐          ┌────────────────────┐    ┌─────────────────────┐
   └──────────────────────────────────────────▶ │  Amazon S3  │ ◀──────▶ │ Glue Data Catalog  │ ◀─▶│ Athena • EMR • Glue │
                                                │ (locais     │          │ (bancos/tabelas)   │    │ Redshift Spectrum   │
                                                │ registrados)│          └─────────┬──────────┘    │ QuickSight • etc.   │
                                                └──────┬──────┘                    │               └──────────┬──────────┘
                                                       │      ┌────────────────────▼───────────────────────┐ │
                                                       └─────▶│        AWS LAKE FORMATION                  │◀┘
                                                              │  permissões (GRANT/REVOKE), LF-Tags,       │
                                                              │  filtros de linha/coluna/célula,           │
                                                              │  credential vending (credenciais temporárias)│
                                                              └────────────────────────────────────────────┘
```

Fluxo de uma consulta (Athena, por exemplo):

1. O usuário consulta `SELECT * FROM vendas.clientes`.
2. O **Athena** consulta o **Lake Formation**: “**este principal** pode ver **quais colunas/linhas**?”.
3. O **Lake Formation** responde com **credenciais temporárias restritas** (**credential vending**) para **ler os objetos S3 permitidos**, e o **plano de acesso** (colunas/linhas/células).
4. O Athena **lê apenas** os dados autorizados; o usuário **recebe** o resultado filtrado.

## 3. Conceitos fundamentais

| Termo | Significado |
|---|---|
| **Data lake** | Repositório centralizado de dados (normalmente no **S3**) |
| **Glue Data Catalog** | **Catálogo de metadados** (bancos, tabelas, partições, esquemas) — base do Lake Formation |
| **Registro de local (data location)** | Registrar um **caminho S3** no Lake Formation para que ele **gerencie o acesso** àqueles dados |
| **Credential vending** | O Lake Formation **emite credenciais temporárias** de acesso ao S3 para os serviços integrados, **restritas** ao que o principal pode ver |
| **Grant/Revoke** | Concessão/revogação de **permissões** (SELECT, INSERT, DESCRIBE, ALTER, DROP, DELETE, CREATE_TABLE…) |
| **Data lake administrator** | Principal com **poder administrativo** sobre as permissões do Lake Formation |
| **Database creator** | Principal autorizado a **criar bancos** |
| **Data filter** | **Filtro** que define **colunas e linhas** visíveis (segurança por **coluna/linha/célula**) |
| **LF-Tag** | **Rótulo** (chave/valor) aplicado a recursos e **usado em políticas** (**TBAC**) |
| **LF-TBAC** | **Tag-based access control**: conceder permissões por **tags** em vez de por recurso nomeado |
| **Named resource method (NRAC)** | Conceder por **nome** de banco/tabela/coluna |
| **Hybrid access mode** | Permite **coexistência** de **IAM/políticas de bucket** e **Lake Formation** para o mesmo recurso (migração gradual) |
| **Cross-account sharing** | Compartilhar dados **entre contas** com Lake Formation (**RAM** / LF-Tags) |
| **Resource link** | **Ponteiro** (link) na conta consumidora para um banco/tabela **compartilhado** |
| **Blueprint** | **Modelo de fluxo de ingestão** (workflow Glue) para fontes comuns |
| **Service-linked role** | Role que o Lake Formation usa para **acessar o S3 registrado** |

## 4. Modelo de permissões: Lake Formation vs IAM

O acesso a dados no lake é decidido por **duas camadas**:

```
Requisição de dados ──▶ [IAM do principal permite a ação no serviço (athena:*, glue:GetTable…)?]
                    ──▶ [LAKE FORMATION permite SELECT neste banco/tabela/coluna/linha?]
                    ──▶ credenciais temporárias do LF para o S3 (sem precisar de s3:GetObject do usuário)
```

| Aspecto | **Somente IAM** (modelo tradicional) | **Lake Formation** |
|---|---|---|
| **Onde residem as regras** | **Policies IAM + bucket policies** | **Catálogo central** (GRANT/REVOKE) |
| **Granularidade** | **Bucket/prefixo/objeto** | **Banco/tabela/coluna/linha/célula** |
| **Acesso ao S3 do usuário** | **Direto** (o usuário precisa de `s3:GetObject`) | **Mediado** (credenciais temporárias do LF; o usuário **não** precisa de acesso direto ao S3) |
| **Tags/ABAC** | `aws:PrincipalTag/ResourceTag` | **LF-Tags** (TBAC) |
| **Multi-conta** | Bucket policies + roles (complexo) | **Grants cross-account + RAM** |
| **Auditoria** | CloudTrail do S3 (sem coluna/linha) | CloudTrail com **eventos do LF** (quem pediu acesso a qual tabela/coluna) |
| **Escalabilidade** | **Limites de tamanho de policy** | **Permissões ilimitadas** (modelo de banco) |
| **Quando** | Datasets **simples**, poucos usuários | **Governança fina**, muitos datasets/usuários, dados sensíveis |

> [!warning] Armadilha clássica: “o usuário ainda acessa o S3 direto”
> Se o usuário tem **acesso direto ao bucket** (IAM/bucket policy), ele **contorna** o Lake Formation. Para aplicar a governança, **remova** o acesso direto ao S3 dos usuários finais e deixe **apenas o Lake Formation** (via serviços) conceder acesso. (O **hybrid access mode** ajuda a **migrar** sem quebrar tudo.)

## 6. Capacidades principais

| Capacidade | Descrição |
|---|---|
| **Controle de acesso centralizado** | **GRANT/REVOKE** em **bancos, tabelas, colunas** |

| **Credenciais temporárias** | **Sem** conceder `s3:*` aos usuários |

## 7. Casos de uso típicos

1. **Data lake corporativo** com **dados sensíveis**: analistas veem **colunas não sensíveis**; times de **compliance** veem tudo.
2. **Multi-tenancy**: cada **filial/cliente** vê **só suas linhas** (row filters).
3. **Compartilhamento entre contas/BUs** (**data mesh**): domínios publicam **produtos de dados**.
4. **Conformidade LGPD/GDPR/HIPAA**: **mascaramento por exclusão de colunas** e **auditoria**.
5. **Self-service analytics** com **tags** (novas tabelas **herdam** acesso por **tag**).
6. **Migração de dados on-premises** para o lake com **governança desde o início**.
7. **Governança unificada** para **Athena/EMR/Redshift/Glue**.

## 8. Quando usar Lake Formation (e quando não)

| Cenário | Lake Formation? |
|---|---|
| **Permissões por coluna/linha** no S3 | **Sim** |
| **Muitos datasets/usuários**, governança central | **Sim** (LF-Tags) |
| **Compartilhar dados entre contas sem copiar** | **Sim** |
| **Dataset simples** (1 bucket, poucos usuários) | **Talvez não** (IAM/bucket policy bastam) |
| **Acesso a arquivos/objetos** por aplicações (não analíticas) | **Não** (S3/IAM) |
| **Controle em Redshift (data warehouse)** | **Redshift** tem **seu próprio controle** (RLS/CLS/dynamic data masking); LF para **Spectrum/data sharing** (confirmar) |
| **Mascaramento dinâmico de valores** (ex.: mostrar `***-**-1234`) | LF faz **filtro de colunas/linhas**; **mascarar valores** exige **outras técnicas** (views, Redshift DDM, Glue/EMR) |
| **Catálogo e governança de negócio** (glossário, aprovação de acesso) | **Amazon DataZone/SageMaker Catalog** complementam |
| **Detecção de PII** | **Macie** (complementar) |

### 8.1 Lake Formation vs Glue Data Catalog vs IAM vs Macie

| Serviço | Papel |
|---|---|
| **Glue Data Catalog** | **Armazena metadados** (bancos/tabelas) |
| **Lake Formation** | **Governa o acesso** aos dados catalogados e aos arquivos no S3 |
| **IAM/bucket policies** | **Acesso tradicional** (granularidade bucket/objeto) |
| **Macie** | **Descobre dados sensíveis** no S3 (sinaliza onde aplicar controles) |
| **Athena/EMR/Redshift** | **Consomem** os dados (aplicam as permissões) |

## 9. Primeiros passos (visão geral, ilustrativo)

```bash
# 1) Definir administradores do data lake (ilustrativo)
aws lakeformation put-data-lake-settings --data-lake-settings '{
  "DataLakeAdmins":[{"DataLakePrincipalIdentifier":"arn:aws:iam::123456789012:role/LakeAdmin"}],
  "CreateDatabaseDefaultPermissions":[], "CreateTableDefaultPermissions":[] }'

# 2) Registrar um local do S3
aws lakeformation register-resource --resource-arn arn:aws:s3:::datalake-123456789012/curated --use-service-linked-role

# 3) Conceder SELECT em colunas específicas
aws lakeformation grant-permissions --principal DataLakePrincipalIdentifier=arn:aws:iam::123456789012:role/AnalistaVendas \
  --resource '{"TableWithColumns":{"DatabaseName":"vendas","Name":"clientes","ColumnNames":["id","nome","cidade","segmento"]}}' \
  --permissions SELECT

# 4) Listar permissões
aws lakeformation list-permissions --resource '{"Table":{"DatabaseName":"vendas","Name":"clientes"}}'
```

## 10. Erros comuns

- **Deixar acesso direto ao S3** (IAM/bucket policy) e achar que o LF protege.
- **Esquecer de registrar** o local S3 (o LF não gerencia o acesso).
- **Não definir administradores** e usar o root/qualquer role.
- **Ignorar as permissões padrão** (“Use only IAM access control”) que **delegam tudo ao IAM**.
- **Conceder por nome** (NRAC) em escala (milhares de grants) em vez de **LF-Tags**.
- **Achar que filtros de coluna mascaram valores** (eles **removem** colunas).
- **Esquecer** que o **IAM também precisa permitir** as ações dos serviços (athena/glue).
- **Não testar** com usuários reais.
- **Misturar modelos** sem planejar o **hybrid mode**.

## 11. Troubleshooting inicial

| Sintoma | Causas prováveis | Ações |
|---|---|---|
| `Insufficient Lake Formation permission(s)` | Sem grant no LF; só IAM | Conceder SELECT/DESCRIBE; verificar o modo |
| `Access denied` no S3 mesmo com grant | Local não registrado; role de acesso | Registrar o local; role do LF |
| Usuário vê dados que não deveria | Acesso direto ao S3; permissões padrão IAM | Remover acesso direto; revisar defaults |
| Tabela não aparece no Athena | Sem DESCRIBE; catálogo diferente; região | Grant DESCRIBE; verificar o catálogo/região |
| Filtro de linha não aplica | Serviço/versão sem suporte; tabela sem integração | Usar serviço suportado; revisar configuração |
| Erros de KMS | Chave sem permissão para a role do LF | Ajustar a key policy |

## 12. Resumo rápido

- **Lake Formation** = **camada central de governança** (GRANT/REVOKE em **banco/tabela/coluna/linha/célula**) sobre **S3 + Glue Data Catalog**, com **credential vending**, **LF-Tags (TBAC)**, **compartilhamento multi-conta** e **auditoria**.
- **Registrar locais S3**, definir **administradores**, conceder permissões; **serviços integrados**: **Athena, EMR, Glue, Redshift Spectrum, QuickSight, SageMaker**.
- **LF vs IAM**: LF dá **granularidade fina e escala**; **IAM também precisa permitir** os serviços; **remova o acesso direto ao S3** para evitar bypass.
- **Hybrid access mode** para **migração gradual**.
- **Quando usar**: dados sensíveis, muitos datasets/usuários, multi-conta; **não** para acesso simples a arquivos.
- **Não mascara valores** (remove colunas/linhas); complementos: **Macie, DataZone, Redshift DDM**.

## 🧩 Quiz de Fixação

1. Que limitação do S3/IAM o Lake Formation supera?
2. O que é credential vending?
3. Por que o acesso direto ao S3 é um risco para a governança do LF?
4. O que são LF-Tags e qual a vantagem sobre grants por nome?
5. Para que serve registrar um local do S3?
6. Cite três serviços integrados ao Lake Formation.
7. O que o hybrid access mode facilita?

**Respostas:**

1. A granularidade: S3/IAM controlam bucket/prefixo/objeto, enquanto o LF controla banco, tabela, coluna, linha e célula, de forma central.
2. O Lake Formation emite credenciais temporárias restritas aos dados que o principal pode ver, usadas pelos serviços integrados para ler o S3, sem o usuário precisar de acesso direto.
3. Porque o usuário com acesso direto ao bucket contorna o LF; a governança só vale se o acesso passar pelo LF.
4. São rótulos (chave/valor) usados para conceder permissões por atributo (TBAC); escalam melhor porque novos recursos com a tag herdam o acesso, sem milhares de grants nomeados.
5. Para que o Lake Formation passe a gerenciar o acesso aos dados naquele caminho, usando a service-linked role e o credential vending.
6. Athena, EMR, Glue, Redshift Spectrum, QuickSight e SageMaker (quaisquer três).
7. A migração gradual, permitindo que IAM/políticas de bucket e Lake Formation coexistam para o mesmo recurso.
