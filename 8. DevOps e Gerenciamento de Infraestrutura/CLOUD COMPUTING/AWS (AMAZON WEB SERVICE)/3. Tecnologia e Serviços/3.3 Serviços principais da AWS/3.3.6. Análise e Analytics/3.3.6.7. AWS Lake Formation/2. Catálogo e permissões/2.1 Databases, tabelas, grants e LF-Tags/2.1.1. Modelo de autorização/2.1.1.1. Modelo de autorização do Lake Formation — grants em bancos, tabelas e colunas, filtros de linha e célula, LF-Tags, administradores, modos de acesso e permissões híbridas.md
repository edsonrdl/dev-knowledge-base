### 2.1.1.1. Modelo de autorização do Lake Formation — grants em bancos, tabelas e colunas, filtros de linha e célula, LF-Tags, administradores, modos de acesso e permissões híbridas

> [!warning] Aviso
> Nomes de permissões, configurações padrão (“IAMAllowedPrincipals”), modos de acesso (híbrido), limites de LF-Tags e filtros, e suporte por serviço abaixo são **de memória e mudam**. **Confirme na documentação do AWS Lake Formation.** Comandos e JSONs são ilustrativos e **não foram executados**. Erros de configuração de permissões podem **expor dados sensíveis** ou **bloquear** pipelines: teste com perfis reais.

## 1. A lógica de permissões do Lake Formation

O Lake Formation implementa um **modelo estilo banco de dados**: **principais** recebem **permissões** sobre **recursos do catálogo** (bancos, tabelas, colunas), com **GRANT** e **REVOKE**.

```
PRINCIPAL (role/usuário/grupo/conta)  ──[PERMISSÃO]──▶  RECURSO do catálogo (database / table / columns / rows)
                                         SELECT, DESCRIBE, ALTER, INSERT, DELETE, DROP, CREATE_TABLE, DATA_LOCATION_ACCESS…
```

Duas perguntas definem o desenho:

1. **Quem** administra e concede? (administradores, donos, delegação)
2. **Como** concedo em escala? (**por nome** vs **por tags**)

## 2. Administradores e papéis

### 2.1 Quem pode fazer o quê

| Papel | Poder |
|---|---|
| **Data lake administrator** | **Concede/revoga** permissões a qualquer recurso; **registra locais**; cria **LF-Tags**; **todos os poderes** de gestão |
| **Read-only administrator** | **Visualiza** permissões (auditoria), sem alterar |
| **Database creator** | Pode **criar bancos** (ganha **dono** do banco) |
| **Table creator** (implícito) | Quem cria a tabela é **dono** (grantable) |
| **Principais com “grantable”** | Podem **repassar** permissões (**WITH GRANT OPTION**) |
| **Usuários/roles de consumo** | Recebem **SELECT/DESCRIBE** em colunas/tabelas |

```bash
aws lakeformation put-data-lake-settings --data-lake-settings '{
  "DataLakeAdmins": [{"DataLakePrincipalIdentifier":"arn:aws:iam::123456789012:role/LakeAdminRole"}],
  "ReadOnlyAdmins": [{"DataLakePrincipalIdentifier":"arn:aws:iam::123456789012:role/AuditorLakeRole"}],
  "CreateDatabaseDefaultPermissions": [], "CreateTableDefaultPermissions": [] }'
```

### 2.2 Boas práticas

1. **Poucos administradores**, via **roles** (não usuários), com **MFA/SSO** e **sessões curtas**.
2. **Separar** administradores de **plataforma** (infra) de **donos de dados** (domínio).
3. **Database creators** restritos a **donos de domínio**.
4. **Remover as permissões padrão amplas** (ver seção 7).
5. Registrar **quem é dono** de cada banco/tabela (tags/documentação).

## 3. Tipos de permissão

| Permissão | Efeito |
|---|---|
| **DESCRIBE** | **Ver** o banco/tabela/esquema (sem ler dados) |
| **SELECT** | **Ler dados** (colunas/linhas permitidas) |
| **INSERT / DELETE** | **Escrever/remover** dados (para tabelas gerenciadas pelo LF) |
| **ALTER** | Alterar **metadados** da tabela/banco |
| **DROP** | **Excluir** tabela/banco |
| **CREATE_TABLE / CREATE_DATABASE** | Criar objetos |
| **DATA_LOCATION_ACCESS** | Criar **bancos/tabelas** que apontam para um **local S3** registrado |
| **ASSOCIATE** (LF-Tags) | Permitir **associar tags** a recursos |
| **SUPER** | **Todas** as permissões (cuidado) |
| **Grant options** | Permitir que o principal **repasse** a permissão |

Princípio: **DESCRIBE** para “enxergar”, **SELECT** para “ler”; conceder **o mínimo**.

## 4. Controle por nome (Named Resource method)

Conceder permissões **recurso a recurso**, explicitamente.

```bash
# Tabela inteira
aws lakeformation grant-permissions --principal DataLakePrincipalIdentifier=arn:aws:iam::123456789012:role/AnalistaVendas \
  --resource '{"Table":{"DatabaseName":"vendas","Name":"pedidos"}}' --permissions SELECT DESCRIBE

# Colunas específicas (segurança por coluna)
aws lakeformation grant-permissions --principal DataLakePrincipalIdentifier=arn:aws:iam::123456789012:role/AnalistaMarketing \
  --resource '{"TableWithColumns":{"DatabaseName":"vendas","Name":"clientes","ColumnNames":["id","cidade","segmento","data_cadastro"]}}' \
  --permissions SELECT

# Todas as colunas EXCETO algumas
aws lakeformation grant-permissions --principal DataLakePrincipalIdentifier=arn:aws:iam::123456789012:role/AnalistaGeral \
  --resource '{"TableWithColumns":{"DatabaseName":"vendas","Name":"clientes","ColumnWildcard":{"ExcludedColumnNames":["cpf","email","telefone"]}}}' \
  --permissions SELECT
```

| Vantagem | Desvantagem |
|---|---|
| **Simples** e **explícito** | **Não escala**: N usuários × M tabelas × K colunas = **milhares** de grants |
| Bom para **poucos** casos/exceções | **Manutenção** difícil; **novas tabelas** exigem novos grants |

## 5. Controle por tags (LF-TBAC)

### 5.1 O modelo

Em vez de conceder por recurso, você:

1. **Define LF-Tags** (ex.: `sensibilidade = {publico, interno, confidencial, pii}`; `dominio = {vendas, rh, financeiro}`).
2. **Associa tags** a **bancos, tabelas e colunas**.
3. **Concede permissões** a principais por **expressão de tags** (ex.: “**SELECT** em tudo com `dominio=vendas` **E** `sensibilidade IN (publico, interno)`”).

```
LF-Tag:  sensibilidade = pii            ─▶ colunas: clientes.cpf, clientes.email, rh.salario
LF-Tag:  dominio = vendas               ─▶ banco: vendas
Grant:   AnalistaVendas  SELECT em  (dominio=vendas AND sensibilidade IN (publico, interno))
Resultado: vê colunas de vendas NÃO-PII; novas tabelas/colunas com essas tags herdam o acesso automaticamente
```

### 5.2 Comandos

```bash
# Criar a tag e valores
aws lakeformation create-lf-tag --tag-key sensibilidade --tag-values publico interno confidencial pii
aws lakeformation create-lf-tag --tag-key dominio --tag-values vendas rh financeiro

# Associar tags a recursos (banco, tabela, coluna)
aws lakeformation add-lf-tags-to-resource --resource '{"Database":{"Name":"vendas"}}' --lf-tags TagKey=dominio,TagValues=vendas
aws lakeformation add-lf-tags-to-resource \
  --resource '{"TableWithColumns":{"DatabaseName":"vendas","Name":"clientes","ColumnNames":["cpf","email"]}}' \
  --lf-tags TagKey=sensibilidade,TagValues=pii

# Conceder por expressão de tags
aws lakeformation grant-permissions --principal DataLakePrincipalIdentifier=arn:aws:iam::123456789012:role/AnalistaVendas \
  --resource '{"LFTagPolicy":{"ResourceType":"TABLE","Expression":[
       {"TagKey":"dominio","TagValues":["vendas"]},
       {"TagKey":"sensibilidade","TagValues":["publico","interno"]}]}}' \
  --permissions SELECT DESCRIBE
```

### 5.3 Herança de tags

| Nível | Comportamento (de memória — confirmar) |
|---|---|
| **Banco → tabelas → colunas** | Tags **herdam** do banco para as tabelas e destas para as colunas, **a menos que sobrescritas** |
| **Sobrescrita** | Coluna `cpf` com `sensibilidade=pii` **substitui** a tag herdada `interno` |
| **Semântica da expressão** | **AND entre chaves distintas**; **OR entre valores** da mesma chave |

### 5.4 TBAC vs NRAC

| Critério | **Nomeado (NRAC)** | **Tags (TBAC)** |
|---|---|---|
| **Escala** | Baixa | **Alta** (poucas tags, muitos recursos) |
| **Manutenção** | Alta (por recurso) | **Baixa** (classificar o recurso = conceder acesso) |
| **Novos recursos** | Precisam de grants | **Herdam** o acesso pelas tags |
| **Auditoria** | Lista de grants | **Políticas legíveis** (“quem vê PII?”) |
| **Curva de aprendizado** | Menor | Maior (desenho de taxonomia) |
| **Recomendação** | Exceções/casos pontuais | **Padrão para ambientes grandes** |

> [!tip] Desenho de taxonomia de tags
> Comece com **2–3 chaves** de alto valor: **domínio** (quem é dono), **sensibilidade** (o que é) e, se útil, **ambiente**/**finalidade**. Evite **dezenas de tags** (vira caos). **Automatize a classificação** (Macie/Glue classifiers → tags) e **governe** quem pode **associar** tags (permissão `ASSOCIATE`).

## 6. Segurança por linha e célula (data filters)

### 6.1 O que são

**Data filters** definem **quais colunas e linhas** um principal vê de uma tabela:

| Tipo | Efeito |
|---|---|
| **Column-level** | Lista de colunas **incluídas** (ou **excluídas**) |
| **Row-level** | **Expressão de filtro** (`regiao = 'sudeste'`) |
| **Cell-level** | Combinação **colunas + linhas** (cada principal vê **células** específicas) |

```bash
aws lakeformation create-data-cells-filter --table-data '{
  "TableCatalogId":"123456789012","DatabaseName":"vendas","TableName":"pedidos","Name":"filtro-sudeste",
  "RowFilter":{"FilterExpression":"regiao = '\''sudeste'\''"},
  "ColumnWildcard":{"ExcludedColumnNames":["cpf_cliente"]} }'

aws lakeformation grant-permissions --principal DataLakePrincipalIdentifier=arn:aws:iam::123456789012:role/GerenteSudeste \
  --resource '{"DataCellsFilter":{"TableCatalogId":"123456789012","DatabaseName":"vendas","TableName":"pedidos","Name":"filtro-sudeste"}}' \
  --permissions SELECT
```

### 6.2 Casos de uso

| Caso | Filtro |
|---|---|
| **Multi-região/filial** | Gerente vê **só a sua região** (linha) |
| **Multi-tenant** | Cliente vê **só seu `tenant_id`** |
| **PII** | Analista sem acesso a **colunas de identificação** |
| **Período** | Auditor vê **apenas o último ano** |
| **Mascaramento por omissão** | Excluir colunas sensíveis (não **mascara**, **remove**) |

### 6.3 Cuidados

- **Expressões de linha** têm **sintaxe e limites** (de memória: compatíveis com **PartiQL/SQL-like**; confirmar).
- **Desempenho**: filtros **complexos** podem **reduzir particionamento**/pruning; alinhar com **partições**.
- **Serviços suportados**: **Athena, EMR, Redshift Spectrum, Glue**… (verificar **versão/configuração**).
- **Não substitui** **mascaramento** de valores: a coluna **some**, não aparece **mascarada**.
- **Teste** com **usuários reais** (muitos erros vêm de **IAM** ou **modo de acesso**).

## 7. Modos de acesso e permissões padrão (ponto crítico)

### 7.1 “IAMAllowedPrincipals” (herança do modelo antigo)

Por **compatibilidade**, bancos/tabelas **podem** conceder **todas as permissões** ao grupo especial **`IAMAllowedPrincipals`**, o que significa: **“quem o IAM permitir, o Lake Formation permite”** — ou seja, o LF **não restringe** nada (**comportamento IAM-only**).

| Situação | Efeito |
|---|---|
| **`IAMAllowedPrincipals` com permissões** em um banco/tabela | **IAM** decide (**LF não filtra**); **LF-Tags/filtros** **não valem** para esses recursos |
| **Remover `IAMAllowedPrincipals`** | O **LF passa a decidir** (precisa de grants) |
| **Configurações padrão de novos bancos/tabelas** (“Use only IAM access control for new databases/tables”) | Se **marcado**, **novos recursos** nascem com `IAMAllowedPrincipals` → **sem governança do LF** |

> [!warning] Primeira coisa a verificar
> Em contas novas ou antigas, verifique **Data Catalog settings**: **desmarque** “**Use only IAM access control**” para **novos** bancos/tabelas e **revise** `IAMAllowedPrincipals` nos **existentes** — senão o LF **parece** configurado, mas **não protege nada**.

### 7.2 Hybrid access mode

| Aspecto | Detalhe (de memória — confirmar) |
|---|---|
| **O que é** | Modo que permite **opt-in por principal e por recurso** ao **Lake Formation**, mantendo **IAM/bucket policies** para os demais |
| **Para quê** | **Migração gradual** de **IAM-only** para **LF** sem **quebrar** pipelines existentes |
| **Como** | Habilitar o modo **híbrido** em bancos/tabelas; **optar** por **principais** que usam LF; os demais continuam com IAM |
| **Fim do caminho** | Migrar todos os consumidores, **remover IAM direto** e **desativar o híbrido** |

### 7.3 Caminho de migração (IAM → LF)

1. **Inventariar** quem acessa o quê (CloudTrail/S3/Athena logs).
2. **Registrar** os locais S3 no LF.
3. **Habilitar o híbrido** nos recursos-alvo.
4. **Criar grants/tags** equivalentes e **validar** com **principais piloto** (opt-in).
5. **Migrar** principais em ondas (analistas → pipelines → serviços).
6. **Remover** acesso direto ao S3 (IAM/bucket policy) dos usuários.
7. **Desativar `IAMAllowedPrincipals`/híbrido**; consolidar em **LF-Tags**.
8. **Auditar** e documentar.

## 8. Interação com IAM

| Camada | O que controla |
|---|---|
| **IAM (principal)** | **Ações dos serviços** (`athena:StartQueryExecution`, `glue:GetTable`, `lakeformation:GetDataAccess`, `s3:…` no **bucket de resultados do Athena**) |
| **Lake Formation** | **Quais dados** (tabelas/colunas/linhas) e **credenciais para o S3 do lake** |
| **S3 bucket policy** | Deve **permitir** a **role do Lake Formation** (service-linked) e **não** liberar **acesso direto** aos usuários |
| **KMS** | **Key policy** deve permitir **a role de acesso do LF** (e serviços) para **descriptografar** |

Exemplo (IAM do analista; **sem** `s3:GetObject` no lake):

```json
{
  "Version": "2012-10-17",
  "Statement": [
    { "Sid": "Athena", "Effect": "Allow",
      "Action": ["athena:StartQueryExecution","athena:GetQueryExecution","athena:GetQueryResults","athena:GetWorkGroup"], "Resource": "*" },
    { "Sid": "Catalogo", "Effect": "Allow", "Action": ["glue:GetDatabase","glue:GetDatabases","glue:GetTable","glue:GetTables","glue:GetPartitions"], "Resource": "*" },
    { "Sid": "LakeFormation", "Effect": "Allow", "Action": ["lakeformation:GetDataAccess"], "Resource": "*" },
    { "Sid": "ResultadosAthena", "Effect": "Allow", "Action": ["s3:GetObject","s3:PutObject","s3:ListBucket","s3:GetBucketLocation"],
      "Resource": ["arn:aws:s3:::athena-resultados-123456789012","arn:aws:s3:::athena-resultados-123456789012/*"] }
  ]
}
```

## 9. Exemplos de desenho de permissões

### 9.1 Perfis típicos

| Perfil | Acesso |
|---|---|
| **Engenharia de dados** | `CREATE_TABLE`/`ALTER`/`INSERT` nas camadas **bruta/curada**; `DATA_LOCATION_ACCESS` |
| **Analistas** | `SELECT` em **camada curada**, **colunas não-PII** (por **tags**) |
| **Cientistas de dados** | `SELECT` em **curada/enriquecida**; **PII** só com **justificativa** |
| **Compliance/Auditoria** | `SELECT`/`DESCRIBE` amplo (**leitura**), **auditoria** |
| **Aplicações/serviços** | Roles **por pipeline** com **escopo mínimo** |
| **Parceiros/outras contas** | **Cross-account** por **tags/filtros** (ver a folha de compartilhamento) |

### 9.2 Camadas (medalhão) e governança

| Camada | Acesso típico |
|---|---|
| **Bronze (bruta)** | **Somente engenharia** (pode conter PII) |
| **Silver (curada)** | Engenharia + analistas **por tags** |
| **Gold (negócio)** | **Amplo** (consumo), **sem PII** |

## 10. Erros comuns

- **`IAMAllowedPrincipals` mantido** e achar que o LF protege.
- **Defaults “IAM only”** para novos recursos.
- **Grants por nome em escala** (milhares) em vez de **tags**.
- **Tags demais**/sem governança de quem **associa**.
- **Esquecer `DESCRIBE`** (usuário não enxerga a tabela).
- **Usar `SUPER`** onde bastaria `SELECT`.
- **Filtros de linha** sem alinhar com **partições** (desempenho).
- **Confundir filtro de coluna com mascaramento**.
- **Não revisar** `DATA_LOCATION_ACCESS`.
- **Migrar de IAM para LF “de uma vez”** sem **híbrido/piloto**.
- **Esquecer** a **bucket policy/KMS** da role do LF.

## 11. Troubleshooting

| Sintoma | Causa provável | Ação |
|---|---|---|
| Usuário não vê a tabela | Sem `DESCRIBE`; IAM `glue:Get*` | Conceder `DESCRIBE` e permissões Glue |
| `Insufficient Lake Formation permission(s) on table` | Sem `SELECT` | Conceder `SELECT` (colunas) ou usar tags |
| LF-Tag não surte efeito | Recurso com `IAMAllowedPrincipals`; tag não associada; expressão errada | Remover `IAMAllowedPrincipals`; conferir associação/expressão |
| Todos veem todas as colunas | Defaults IAM-only | Revisar settings; remover permissões amplas |
| Filtro de linha ignorado | Serviço/versão sem suporte; consulta por outro caminho | Verificar suporte; bloquear acesso direto |
| Não consigo associar tags | Falta `ASSOCIATE`/administração | Conceder permissão de associação |
| Falha na criação de tabela | Falta `DATA_LOCATION_ACCESS`/`CREATE_TABLE` | Conceder |
| Pipeline quebrou após migração | Permissões LF ausentes | Híbrido; conceder as permissões do pipeline |

## 12. Resumo rápido

- **Modelo**: principal + permissão (**DESCRIBE, SELECT, INSERT, DELETE, ALTER, DROP, CREATE_TABLE, DATA_LOCATION_ACCESS, ASSOCIATE, SUPER**) + recurso (**banco/tabela/colunas/linhas**).
- **Administradores** (poucos, via roles), **database creators**, **grant option**.
- **NRAC** (por nome; simples, não escala) vs **LF-TBAC** (por **tags**; escala, **herança** banco→tabela→coluna; **AND entre chaves, OR entre valores**) — **recomendado em ambientes grandes**.
- **Data filters**: **colunas, linhas e células** (multi-tenant, regiões); **removem**, **não mascaram**.
- **Cuidado**: **`IAMAllowedPrincipals`** e **defaults “IAM only”** anulam o LF; **remova acesso direto ao S3**.
- **Hybrid access mode** para **migração gradual**; **IAM** continua exigindo **ações dos serviços** (`lakeformation:GetDataAccess`, `glue:Get*`, `athena:*`).

## 🧩 Quiz de Fixação

1. Qual a diferença entre DESCRIBE e SELECT?
2. Por que LF-Tags escalam melhor que grants por nome?
3. O que é `IAMAllowedPrincipals` e por que é uma armadilha?
4. O que é segurança em nível de célula?
5. Por que filtros de coluna não substituem mascaramento?
6. Quais ações de IAM o analista ainda precisa, mesmo com o LF?
7. Como migrar gradualmente de IAM para Lake Formation?

**Respostas:**

1. DESCRIBE permite ver o banco/tabela/esquema; SELECT permite ler os dados.
2. Porque classificar o recurso com a tag concede o acesso por herança, sem criar milhares de grants nomeados; novos recursos com a tag herdam as permissões.
3. É o grupo que delega a decisão ao IAM (modelo antigo); se tiver permissões no recurso, o LF não restringe, e tags/filtros não valem.
4. A combinação de filtros de colunas e de linhas, definindo exatamente quais células cada principal vê.
5. Porque removem colunas ou linhas, mas não alteram valores (por exemplo, mostrando um CPF parcialmente oculto); mascaramento exige outras técnicas.
6. Ações dos serviços, como athena:StartQueryExecution/GetQueryResults, glue:GetTable/GetDatabase/GetPartitions e lakeformation:GetDataAccess, além de acesso ao bucket de resultados do Athena.
7. Registrando locais, habilitando o hybrid access mode, criando grants/tags, validando com principais piloto, migrando em ondas, removendo o acesso direto ao S3 e desativando IAMAllowedPrincipals/híbrido.
