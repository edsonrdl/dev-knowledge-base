### 4.1.1.1. Compartilhamento multi-conta no Lake Formation — grants cross-account, RAM, LF-Tags, resource links, Organizations e data mesh

> [!warning] Aviso
> Versões do modelo de compartilhamento cross-account (v1–v4), comportamento de convites do RAM, requisitos de resource links, limites e recursos de data mesh abaixo são **de memória e mudam**. **Confirme na documentação do AWS Lake Formation (“Cross-account data sharing”) e do RAM.** Comandos e JSONs são ilustrativos e **não foram executados**. IDs de contas (`111111111111` produtora, `222222222222` consumidora) são fictícios. Compartilhar dados é **conceder acesso**: toda configuração deve ser **revisada pela governança de dados**.

## 1. O problema do multi-conta em dados

Em organizações grandes, os dados vivem em **muitas contas**: cada **unidade de negócio/domínio** (vendas, RH, financeiro, marketing) tem sua **conta**, seu **lake** e seu **time**. Surgem demandas como:

| Necessidade | Dificuldade sem Lake Formation |
|---|---|
| **Analistas de marketing** (conta B) precisam de dados de **vendas** (conta A) | **Copiar dados** (custo, divergência, LGPD) ou montar **bucket policies + roles cross-account + catálogo** manualmente |
| **Compartilhar só colunas/linhas** | S3 não filtra colunas/linhas |
| **Governança por tags** em várias contas | Políticas duplicadas |
| **Auditar** quem acessa dados de outra conta | Logs em contas diferentes |
| **Escalar** o compartilhamento a **dezenas de contas** | Operação manual |

O **Lake Formation** permite **compartilhar bancos/tabelas/colunas/linhas** **entre contas** (e **entre organizações**) **sem copiar os dados**: a conta **produtora** concede **permissões** à conta **consumidora**; o consumidor **consulta** com seus serviços (Athena/EMR/Redshift) **no mesmo S3** da produtora.

> [!info] Em uma frase
> **“Os dados ficam na conta dona; o Lake Formation concede acesso (colunas/linhas) a outras contas, que consultam sem copiar.”**

## 2. Como funciona o compartilhamento

```
CONTA PRODUTORA (111111111111)                              CONTA CONSUMIDORA (222222222222)
 S3 lake (registrado) + Glue Catalog                          Athena/EMR/Redshift
   banco "vendas" / tabela "pedidos"                           ┌─────────────────────────────┐
        │  LF: GRANT SELECT (colunas/filtro/TAGS)              │ Resource link "vendas_link"  │ ◀─ aponta ao banco/tabela remoto
        │  para a conta consumidora (ou OU/Org)                │ (no catálogo da consumidora) │
        └──────── via AWS RAM (convite/automático) ───────────▶│ Admin da consumidora delega  │
                                                               │ permissões a usuários locais │
                                                               └─────────────────────────────┘
 Consulta: consumidor ─▶ LF (da produtora) valida ─▶ credenciais temporárias ─▶ lê o S3 da PRODUTORA
```

### 2.1 Os dois lados

| Lado | Responsabilidades |
|---|---|
| **Produtor (dono dos dados)** | Mantém **S3**, **catálogo**, **qualidade**; **concede** acesso (por nome/tags/filtros); define **colunas/linhas** compartilhadas |
| **Consumidor** | **Aceita** o compartilhamento (via RAM, se aplicável); **cria resource links** para os recursos compartilhados; **delega** permissões a **seus usuários/roles** (o **admin do LF da consumidora** controla quem **internamente** pode usar) |

### 2.2 Dois modelos de compartilhamento

| Modelo | Descrição | Quando |
|---|---|---|
| **Named resource method** | Conceder **por nome** de banco/tabela/coluna a **conta/OU/org** | **Poucos** recursos/exceções |
| **LF-Tag based (TBAC)** | Conceder por **expressão de LF-Tags** a **conta/OU/org** | **Escala**; **novos recursos** com a tag **herdam** o acesso |

### 2.3 Papel do AWS RAM

| Aspecto | Detalhe (de memória — confirmar a versão do modelo) |
|---|---|
| **Uso** | O LF usa o **RAM** para **compartilhar recursos do catálogo** (bancos/tabelas) com **outras contas** |
| **Dentro da organização** | Com **sharing habilitado** (Organizations): **sem convite**, **automático** |
| **Fora da organização** | **Convite RAM** a ser **aceito** pela consumidora |
| **Versões do modelo** | Versões mais **recentes** (v3/v4) **simplificam**: menos **convites** e **permissões** (**LF-Tags** e **grants** cross-account **sem exigir** compartilhamento explícito de recursos via RAM para cada tabela; confirmar a versão configurada em **Data Catalog settings → Cross-account version**) |
| **Configuração** | **Cross-account version** nas configurações do catálogo (**atualize** para a **versão recente** se possível) |

## 3. Passo a passo (modelo por nome)

### 3.1 Na conta produtora

```bash
# Conceder SELECT em colunas específicas à conta consumidora (com possibilidade de repassar)
aws lakeformation grant-permissions --principal DataLakePrincipalIdentifier=222222222222 \
  --resource '{"TableWithColumns":{"DatabaseName":"vendas","Name":"pedidos","ColumnNames":["id","data","valor","regiao"]}}' \
  --permissions SELECT --permissions-with-grant-option SELECT

# Também DESCRIBE no banco
aws lakeformation grant-permissions --principal DataLakePrincipalIdentifier=222222222222 \
  --resource '{"Database":{"Name":"vendas"}}' --permissions DESCRIBE
```

### 3.2 Na conta consumidora

1. **Aceitar** o convite do **RAM** (se **fora** da organização/versão antiga).
2. O **admin do LF** da consumidora **cria um resource link** para o banco/tabela compartilhado:

```bash
aws glue create-database --database-input '{"Name":"vendas_link","TargetDatabase":{"CatalogId":"111111111111","DatabaseName":"vendas"}}'
# ou link para tabela
aws glue create-table --database-name analytics --table-input '{"Name":"pedidos_link","TargetTable":{"CatalogId":"111111111111","DatabaseName":"vendas","Name":"pedidos"}}'
```

3. O admin **concede** permissões aos **usuários/roles locais** sobre o **resource link** **e** sobre o **recurso alvo** (**DESCRIBE** no link; **SELECT** no alvo, via o **grant option** recebido):

```bash
aws lakeformation grant-permissions --principal DataLakePrincipalIdentifier=arn:aws:iam::222222222222:role/AnalistaMarketing \
  --resource '{"Table":{"CatalogId":"111111111111","DatabaseName":"vendas","Name":"pedidos"}}' --permissions SELECT
aws lakeformation grant-permissions --principal DataLakePrincipalIdentifier=arn:aws:iam::222222222222:role/AnalistaMarketing \
  --resource '{"Table":{"DatabaseName":"vendas_link","Name":"pedidos"}}' --permissions DESCRIBE
```

4. O analista **consulta** pelo **link** (`SELECT * FROM vendas_link.pedidos`) no **Athena** da consumidora.

### 3.3 Resource links

| Aspecto | Detalhe |
|---|---|
| **O que são** | **Objetos do Glue Catalog** que **apontam** para bancos/tabelas **de outra conta/região** |
| **Para quê** | Permitir **consulta/ETL** na consumidora **sem copiar** metadados e **resolver nomes** locais |
| **Permissões** | **DESCRIBE** no link; **SELECT** etc. no **recurso alvo** |
| **Segurança** | O link **não** dá acesso; **concessões** no alvo é que valem |
| **Cuidado** | **Links quebrados** se o alvo mudar/sumir |

## 4. Compartilhamento por LF-Tags (escala)

```bash
# Produtora: conceder a uma conta (ou OU) o acesso por expressão de tags
aws lakeformation grant-permissions --principal DataLakePrincipalIdentifier=222222222222 \
  --resource '{"LFTagPolicy":{"CatalogId":"111111111111","ResourceType":"TABLE","Expression":[
      {"TagKey":"dominio","TagValues":["vendas"]},
      {"TagKey":"sensibilidade","TagValues":["publico","interno"]}]}}' \
  --permissions SELECT DESCRIBE --permissions-with-grant-option SELECT DESCRIBE
```

| Vantagem | Detalhe |
|---|---|
| **Automático** | **Novas tabelas** com as tags **ficam disponíveis** à consumidora |
| **Menos RAM manual** | Menos convites/links por recurso (conforme a versão) |
| **Governança** | A **produtora** controla **tudo por tags** (inclusive **retirar o acesso** ao mudar a tag) |
| **Sensibilidade** | `sensibilidade=pii` **fica fora** do que foi concedido (**coluna** não é compartilhada) |

**Consumidora**: precisa **ter as LF-Tags** (ou **ver** as da produtora) e **delegar** a seus principais **via tags** ou **nomes**; **cria resource links** conforme necessário.

## 5. Compartilhamento com OU/Organização

| Opção | Efeito |
|---|---|
| **Conta específica** | Controle **máximo** |
| **OU** | **Todas as contas da OU** (atuais e futuras) |
| **Organização inteira** | **Qualquer conta** da org (**cuidado**) |
| **Fora da organização** | **Convite RAM**; **parceiros/clientes** (com **contratos e DPA**) |

> [!warning] Compartilhar com a organização inteira
> É **fácil** e **perigoso**. Prefira **OUs** específicas e **filtros/tags** (sem PII). Para **dados pessoais**, exija **base legal**, **finalidade** e **registro**.

## 6. Data mesh e arquitetura federada

### 6.1 Conceito

O **data mesh** trata dados como **produtos** de **domínios**: cada domínio **possui** e **publica** seus dados; um **plano de governança** garante **padrões** e **descoberta**.

```
DOMÍNIOS (produtores)                       GOVERNANÇA CENTRAL                     CONSUMIDORES
 Vendas (conta A): dados + LF  ──┐        ┌─ Catálogo central/portal (DataZone)    ┌─ Marketing (conta D)
 RH     (conta B): dados + LF  ──┼───────▶│  Políticas/tags padrão (LF-Tags)       ├─ Finanças  (conta E)
 Logística (conta C): dados + LF─┘        └─ Auditoria/qualidade/linhagem          └─ Ciência de Dados (conta F)
          compartilhamento cross-account (LF + RAM) por tags/filtros, sem copiar dados
```

| Elemento | Prática |
|---|---|
| **Domínio produtor** | **Dono** de **qualidade, esquema, SLAs** e **concessão de acesso** |
| **Governança central** | **Taxonomia de tags** (sensibilidade, domínio, finalidade), **políticas globais**, **auditoria** |
| **Plataforma de dados** | Templates (IaC), **pipelines**, **catálogo**, **observabilidade** |
| **Consumidores** | **Descobrem** no **catálogo** e **solicitam** acesso (fluxo de aprovação) |
| **Ferramentas AWS** | **Lake Formation**, **Glue Data Catalog**, **RAM**, **DataZone/SageMaker Catalog** (portal e assinatura), **Athena/EMR/Redshift**, **IAM Identity Center** |

### 6.2 Padrões de arquitetura

| Padrão | Descrição | Quando |
|---|---|---|
| **Lake centralizado** | **Uma conta** com todos os dados; consumidores acessam **cross-account** | Organizações **menores/centralizadas** |
| **Data mesh (federado)** | **Várias contas** produtoras; **governança central** | **Grandes empresas** com domínios autônomos |
| **Hub-and-spoke** | **Hub** de dados compartilhados (conformados) + **spokes** de domínio | Dados **mestres/compartilhados** |
| **Catálogo central + dados distribuídos** | **Catálogo** em uma conta; **dados** nas de domínio | **Descoberta** unificada |

## 7. Segurança e governança do compartilhamento

| Controle | Detalhe |
|---|---|
| **Menor privilégio** | **Colunas/linhas** mínimas; **tags** claras; **sem PII** por padrão |
| **Grant option controlado** | Conceder `GRANT OPTION` **só a admins** das consumidoras (evita **re-compartilhamento** descontrolado) |
| **Quem pode compartilhar** | **Donos de domínio**/admins do LF (IAM + **SCP** limitando **cross-account** a **contas aprovadas**) |
| **Compartilhamento externo** | **Bloquear** por **SCP/RAM** (`allowExternalPrincipals=false`) salvo **exceção** |
| **KMS** | **Key policy** da produtora deve permitir **decrypt** pela **role do LF**/consumidor (conforme o modelo) |
| **Auditoria** | **CloudTrail** nas **duas contas**; **agregar** em **log archive**; alarmes de **novos compartilhamentos** |
| **Revogação** | **Revogar** na produtora **corta** o acesso; **remover tags** muda o escopo |
| **Catálogo/linhagem** | **Documentar** produtos de dados, donos, SLAs |
| **Contratos e privacidade** | **DPA/Finalidade/Base legal** para dados pessoais (LGPD) |
| **Separação prod/dev** | **Não** compartilhar **dados de produção** com **ambientes de dev** sem **mascaramento** |

## 8. Custos e responsabilidades

| Item | Quem paga |
|---|---|
| **Armazenamento S3** | **Produtora** |
| **Consultas (Athena/EMR/Redshift)** | **Consumidora** (computação) |
| **Transferência cross-region** | Conforme regras (evitar cross-region) |
| **Glue Data Catalog** | Cada conta pelos **seus** objetos (links) |
| **Lake Formation** | **Sem custo** direto (paga os serviços subjacentes) |
| **KMS** | Requisições de **decrypt** (**cobrança** na conta da **chave**) |
| **Governança/portal** | DataZone etc. conforme uso |

Práticas: **tags de alocação**, **workgroups do Athena** por equipe/conta, **showback** de consultas.

## 9. Cross-region

| Aspecto | Detalhe (de memória — confirmar) |
|---|---|
| **Resource links cross-region** | É possível **apontar** para recursos **em outra região** (limitações; **latência/custos** de transferência) |
| **Replicação** | **S3 CRR** + catálogo replicado (**DR**) |
| **Boa prática** | **Consumir na mesma região** dos dados quando possível |

## 10. Erros comuns

- **Compartilhar com a organização inteira** sem filtros/tags.
- **Conceder `GRANT OPTION` amplo** (re-compartilhamento).
- **Esquecer de criar resource links** (consumidora não “vê” os dados).
- **Esquecer DESCRIBE no link** e **SELECT no alvo**.
- **KMS sem permissão** para o consumidor/role do LF.
- **Compartilhar PII** sem controle (colunas não filtradas).
- **Modelo antigo** (convites RAM em massa) em vez de **versão recente + LF-Tags**.
- **Sem auditoria** cross-account.
- **Compartilhar prod com dev** sem mascaramento.
- **Links quebrados** após renomear bancos/tabelas.
- **Não alinhar** taxonomia de tags **entre contas**.

## 11. Troubleshooting

| Sintoma | Causa provável | Ação |
|---|---|---|
| Consumidora não vê o banco | Sem resource link; convite RAM não aceito; versão cross-account | Criar o link; aceitar o convite; revisar a versão |
| `Insufficient Lake Formation permission(s)` cross-account | Falta SELECT no **alvo** ou DESCRIBE no **link** | Conceder em ambos |
| `Access denied` ao ler S3/KMS | KMS/bucket policy; role do LF | Ajustar as políticas na **produtora** |
| Nova tabela não aparece (TBAC) | Tags não aplicadas; consumidora sem as tags | Associar tags; alinhar taxonomia |
| Consumidora não consegue repassar acesso | Sem `GRANT OPTION` | Conceder grant option ao admin |
| Link quebrado | Alvo renomeado/removido | Recriar o link; versionar |
| Acesso persiste após revogar | Cache/propagação; outro caminho de acesso | Aguardar; verificar o acesso direto ao S3 |
| Consultas cross-region lentas/caras | Dados em outra região | Replicar/consumir na mesma região |

## 12. Resumo rápido

- **Compartilhar sem copiar**: **produtora** concede **permissões (colunas/linhas/tags)** à **conta/OU/org**; **consumidora** cria **resource links** e delega aos usuários; **dados permanecem no S3 da produtora**.
- **Dois métodos**: **por nome** (poucos recursos) e **por LF-Tags (TBAC)** (escala; novos recursos herdam).
- **RAM**: usado para compartilhar recursos do catálogo (convites **fora** da org; **automático** dentro com sharing habilitado); **versões recentes** do modelo cross-account **simplificam**.
- **Resource links**: **DESCRIBE no link** + **SELECT no alvo**.
- **Data mesh**: **domínios** produzem **produtos de dados**; **governança central** (tags, políticas, auditoria); ferramentas: **LF, Glue, RAM, DataZone**.
- **Segurança**: **menor privilégio**, **`GRANT OPTION` controlado**, **sem PII por padrão**, **KMS**, **CloudTrail**, **bloqueio de externos**, **separação prod/dev**.

## 🧩 Quiz de Fixação

1. O que a conta produtora e a consumidora fazem em um compartilhamento?
2. O que é um resource link e por que é necessário?
3. Por que preferir LF-Tags para compartilhar em escala?
4. Que permissões o analista da consumidora precisa?
5. Quais riscos há ao compartilhar com a organização inteira?
6. O que é data mesh e qual o papel da governança central?
7. Por que o KMS é um ponto de atenção?

**Respostas:**

1. A produtora mantém os dados e concede permissões (por nome ou tags) à conta consumidora; a consumidora cria resource links e delega permissões a seus usuários, consultando sem copiar os dados.
2. Um objeto do Glue Catalog na consumidora que aponta para um banco/tabela da produtora, permitindo consultas com nomes locais; o acesso real vem das permissões no recurso alvo.
3. Porque novas tabelas com as tags herdam o acesso automaticamente, evitando grants e links por recurso e permitindo políticas legíveis.
4. DESCRIBE no resource link e SELECT (nas colunas/linhas permitidas) no recurso alvo, delegados pelo admin do LF da consumidora.
5. Dá acesso a qualquer conta da organização, inclusive sandbox, ampliando exposição e riscos de privacidade; prefira OUs específicas e filtros/tags.
6. Data mesh trata dados como produtos de domínios autônomos; a governança central define taxonomia de tags, políticas globais, auditoria e descoberta.
7. Porque a key policy da produtora precisa permitir o decrypt pela role do LF/consumidor; sem isso, consultas falham, e permissões amplas demais expõem dados.
