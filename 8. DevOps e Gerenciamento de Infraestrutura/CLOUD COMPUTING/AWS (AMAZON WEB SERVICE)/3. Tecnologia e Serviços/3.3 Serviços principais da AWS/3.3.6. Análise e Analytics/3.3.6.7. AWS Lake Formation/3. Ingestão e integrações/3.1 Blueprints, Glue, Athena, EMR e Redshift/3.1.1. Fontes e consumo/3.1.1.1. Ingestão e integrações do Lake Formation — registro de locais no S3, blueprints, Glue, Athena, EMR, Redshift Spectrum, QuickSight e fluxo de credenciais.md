### 3.1.1.1. Ingestão e integrações do Lake Formation — registro de locais no S3, blueprints, Glue, Athena, EMR, Redshift Spectrum, QuickSight e fluxo de credenciais

> [!warning] Aviso
> Requisitos de versão/configuração por serviço, nomes de blueprints, comportamento de credential vending e recursos de cada integração abaixo são **de memória e mudam**. **Confirme na documentação do AWS Lake Formation e de cada serviço integrado.** Comandos, JSONs e fluxos são ilustrativos e **não foram executados**. Nomes de buckets/roles são fictícios.

## 1. Do dado bruto ao consumo governado

Um data lake governado tem **três momentos**:

```
[1] INGESTÃO ───────▶ [2] CATALOGAÇÃO E GOVERNANÇA ───────▶ [3] CONSUMO
 (Glue, DMS, Firehose,   (S3 registrado + Glue Data Catalog      (Athena, EMR, Redshift Spectrum,
  blueprints, Kinesis)     + permissões/tags do Lake Formation)    Glue, QuickSight, SageMaker)
```

Esta folha detalha **como os dados entram**, **como o S3 é registrado** e **como cada serviço de consumo se integra** (inclusive o **fluxo de credenciais**).

## 2. Registrando locais do Amazon S3

### 2.1 O que significa “registrar”

**Registrar um local** (um bucket ou prefixo, ex.: `s3://datalake-123456789012/curated/`) diz ao Lake Formation: “**gerencie o acesso** aos dados neste caminho”. A partir daí, o LF passa a **mediar** o acesso (via **credential vending**) para os serviços integrados.

| Aspecto | Detalhe |
|---|---|
| **Role de acesso** | **Service-linked role** do LF (`AWSServiceRoleForLakeFormationDataAccess`) **ou** uma **role customizada** (para casos específicos: KMS, cross-account, regras de bucket) |
| **Escopo** | **Bucket ou prefixo** (preferir **prefixos** por camada/domínio) |
| **Hierarquia** | **Locais aninhados**: não registre **pai e filho** com **roles diferentes** sem planejar |
| **Região** | Locais pertencem à **região**; **buckets** na **mesma região** do catálogo (preferível) |
| **Permissão de leitura/escrita** | O LF precisa de **acesso ao S3** (via a role) para **vender credenciais** |
| **Bucket policy/KMS** | Devem **permitir a role** do LF; **KMS** exige permissão de `kms:Decrypt/GenerateDataKey` |

```bash
aws lakeformation register-resource --resource-arn arn:aws:s3:::datalake-123456789012/curated --use-service-linked-role
aws lakeformation register-resource --resource-arn arn:aws:s3:::datalake-123456789012/raw \
  --role-arn arn:aws:iam::123456789012:role/LakeFormationDataAccessRaw
aws lakeformation list-resources
```

### 2.2 `DATA_LOCATION_ACCESS`

Quem **cria bancos/tabelas** que **apontam** para um local registrado precisa da permissão **`DATA_LOCATION_ACCESS`** naquele local — impede que usuários **criem tabelas** em **qualquer** caminho do S3.

```bash
aws lakeformation grant-permissions --principal DataLakePrincipalIdentifier=arn:aws:iam::123456789012:role/EngenhariaDados \
  --resource '{"DataLocation":{"ResourceArn":"arn:aws:s3:::datalake-123456789012/curated"}}' --permissions DATA_LOCATION_ACCESS
```

### 2.3 Boas práticas de organização do S3

| Prática | Detalhe |
|---|---|
| **Camadas** | `raw/` (bruto), `curated/` (limpo), `analytics/` (negócio) — **locais separados** com **permissões diferentes** |
| **Domínios** | `…/vendas/`, `…/rh/` (**donos distintos**) |
| **Partições** | `ano=/mes=/dia=` ou outras (aderência às consultas) |
| **Formato** | **Parquet/ORC/Iceberg** (colunar) |
| **Um bucket por domínio/ambiente** | Quando exigir **KMS/políticas** distintas |
| **Bloquear acesso direto** | **Bucket policy** negando usuários finais; **permitir** a role do LF e pipelines |
| **Versionamento/Lifecycle** | Conforme retenção |
| **Nomenclatura** | Padronizada (facilita **tags/automação**) |

## 3. Ingestão de dados

### 3.1 Opções

| Opção | Descrição | Uso |
|---|---|---|
| **Blueprints do Lake Formation** | **Modelos de workflow Glue** (assistente) para fontes comuns | Ingestão **rápida** sem escrever ETL |
| **AWS Glue (jobs/crawlers/workflows)** | ETL Spark/Python, **crawlers** para descobrir esquema | **Padrão** flexível |
| **AWS DMS** | Replicação de bancos (**full load + CDC**) para o S3 | Bancos relacionais |
| **Kinesis Data Firehose/Streams** | Streaming para o S3 (Parquet com conversão) | Eventos/logs |
| **AWS DataSync/Transfer Family/Snow** | Transferência de arquivos/volumes | Migração |
| **AppFlow** | SaaS (Salesforce, SAP, etc.) → S3 | Aplicações SaaS |
| **MSK/Kafka Connect** | Streams Kafka → S3 | Mensageria |
| **Zero-ETL** (RDS/Aurora/DynamoDB → Redshift/Lakehouse; confirmar) | Replicação **sem ETL** | Analytics quase em tempo real |
| **Glue Data Catalog federation** (confirmar) | Catálogos externos | Integração |

### 3.2 Blueprints

| Aspecto | Detalhe (de memória — confirmar) |
|---|---|
| **O que são** | **Workflows pré-definidos** (usando **Glue**: jobs, triggers, crawlers) criados por um **assistente** |
| **Tipos** | **Database snapshot** (carga completa de **JDBC** → S3), **Incremental database** (carga **incremental** por **bookmark/colunas**), **Log file** (**CloudTrail, ELB, ALB…** → S3 em **Parquet**) |
| **Resultado** | **Tabelas no catálogo**, dados em **Parquet** no S3 (local registrado), **permissões** configuradas conforme **você** |
| **Vantagens** | **Rapidez**, **boas práticas** (formato colunar, partições) |
| **Limitações** | Menos flexível que ETL **customizado**; para **transformações complexas**, use **Glue jobs** |
| **Governança** | Os dados **nascem** dentro de **locais registrados** com **permissões** |

### 3.3 Fluxo típico de ingestão (database → lake)

```
RDS (PostgreSQL) ──JDBC──▶ Blueprint (Database snapshot/Incremental) ──▶ S3 raw (Parquet, registrado)
         │                                    │
         └─ Glue Connection + Secrets Manager └─▶ Glue Crawler/Catálogo ──▶ tabelas em "raw"
Em seguida: Glue ETL (raw → curated: limpeza, tipagem, deduplicação, PII → tags) ──▶ S3 curated ──▶ consumo governado
```

### 3.4 Boas práticas de ingestão

1. **Formato colunar** (Parquet/ORC) e **partições** já na entrada (ou na camada curada).
2. **Esquema explícito** (evitar `crawler` “mágico” em dados instáveis; usar **schema registry**/definição de tabelas).
3. **Idempotência** (reexecuções não duplicam: `MERGE`/Iceberg, overwrite dinâmico).
4. **Classificação cedo**: aplicar **LF-Tags** por **sensibilidade** ao **criar** tabelas (automatizar com **Macie/Glue** → tags).
5. **Dados sensíveis**: **tokenizar/anonimizar** na ingestão quando possível.
6. **Qualidade**: **Glue Data Quality**/**Deequ**.
7. **Observabilidade**: métricas de jobs, **alarmes de falha**, **lineage** (DataZone/Glue).
8. **Credenciais de fontes**: **Secrets Manager**; **sem segredos** em código.
9. **Segregar** pipelines por **role** de **menor privilégio** (grants `INSERT`/`CREATE_TABLE` só na camada certa).

## 4. Credential vending: o fluxo de acesso aos dados

### 4.1 Como funciona

```
Usuário ─▶ Athena/EMR/Redshift Spectrum/Glue
              │ 1) valida IAM do principal (ação do serviço)
              │ 2) chama Lake Formation: GetDataAccess / (para EMR: integração)
              ▼
        LAKE FORMATION  verifica as permissões do principal (tabela/colunas/linhas, tags, filtros)
              │ 3) devolve CREDENCIAIS TEMPORÁRIAS restritas aos objetos S3 permitidos + plano de acesso
              ▼
        Serviço lê o S3 com essas credenciais e aplica filtros de colunas/linhas ─▶ resultado ao usuário
```

| Ponto | Detalhe |
|---|---|
| **Quem chama o LF** | O **serviço analítico** (em nome do principal) |
| **Permissão IAM necessária** | `lakeformation:GetDataAccess` (para o principal/role do serviço) |
| **Credenciais** | **Curta duração**, **escopo mínimo** (prefixos/objetos autorizados) |
| **Sem `s3:GetObject` para usuários** | O usuário **não** precisa de acesso direto ao S3 do lake |
| **Auditoria** | Eventos de acesso no **CloudTrail** (ex.: `GetDataAccess`) |
| **Bypass** | Se o usuário tem **S3 direto**, ele **ignora** (por isso **remover**) |

### 4.2 Papéis de execução

| Contexto | Quem é o principal |
|---|---|
| **Athena** | O **usuário/role** que executa a consulta (ou **workgroup** com role/**IAM Identity Center** em recursos de identidade confiável; confirmar) |
| **Glue ETL** | A **role do job** (precisa de grants no LF) |
| **EMR** | **Runtime role** do step/job (**recomendado**) ou instance profile (**menos granular**) |
| **Redshift Spectrum** | A **role do cluster/usuário** conforme a configuração |
| **QuickSight** | A **role do QuickSight** ou a identidade do usuário (**Enterprise**; configuração específica) |

## 5. Integração por serviço

### 5.1 Amazon Athena

| Aspecto | Detalhe |
|---|---|
| **Funcionamento** | Consulta o **catálogo** e **obtém credenciais** do LF; aplica **colunas/linhas/células** |
| **Requisitos** | **Athena engine v2/v3** (versões atuais), **workgroup**, **bucket de resultados** |
| **Recursos** | **LF-Tags**, **data filters**, **cross-account** (resource links) |
| **Dicas** | Resultados do Athena **são dados**: **proteger o bucket de resultados** (podem conter **PII** de consultas) |
| **Erros** | `Insufficient Lake Formation permission(s)` (grants); `HIVE_ACCESS_DENIED` (S3/KMS/role) |

### 5.2 AWS Glue

| Aspecto | Detalhe |
|---|---|
| **ETL jobs** | Ler/escrever tabelas **governadas**: a **role do job** precisa de **grants** (SELECT/INSERT/ALTER/`DATA_LOCATION_ACCESS`) |
| **Crawlers** | A **role do crawler** precisa de permissões para **criar/alterar tabelas** e `DATA_LOCATION_ACCESS` |
| **Data Catalog** | Metastore compartilhado com **Athena/EMR/Redshift** |
| **Glue Data Quality** | Regras e métricas |
| **Notebooks/Interactive Sessions** | Respeitam permissões da **role** |
| **Observação** | **Filtros de linha/célula** em Glue ETL exigem **versões/configurações** compatíveis (confirmar) |

### 5.3 Amazon EMR

| Aspecto | Detalhe (de memória — confirmar) |
|---|---|
| **Controle fino** | **Spark/Hive/Trino** no EMR com **colunas/linhas** do LF (**EMR on EC2 com runtime roles**, **EMR on EKS**, **EMR Serverless**) |
| **Requisitos** | **Release** do EMR compatível, **security configuration**, **role de sistema/usuário**, **modo de isolamento** de queries |
| **Alternativa antiga** | **Instance profile** (acesso amplo ao S3 — **perde** granularidade) |
| **Recomendação** | **Runtime roles** + **Lake Formation** para **multi-tenancy** |
| **Cuidado** | Ambientes **multiusuário** com instance profile único **violam** o modelo de menor privilégio |

### 5.4 Amazon Redshift (Spectrum e data sharing)

| Aspecto | Detalhe |
|---|---|
| **Spectrum** | Tabelas **externas** (S3/Glue Catalog) com **permissões do LF** (via **role do cluster/IAM**) |
| **Redshift data sharing com LF** | **Governança centralizada** de **data shares** (confirmar disponibilidade) |
| **Controle interno do Redshift** | **GRANT/RLS/CLS/DDM** do **próprio warehouse** (separado do LF) |
| **Cuidado** | Entender **onde** a política vale (**dados externos** vs **internos**) |

### 5.5 Amazon QuickSight

| Aspecto | Detalhe |
|---|---|
| **Fonte** | **Athena** (dataset) respeitando **LF** conforme **identidade** usada |
| **Edição** | Recursos de segurança por usuário/identidade são da **Enterprise** |
| **Boas práticas** | Evitar **dataset compartilhado** com **role ampla**; usar **RLS do QuickSight** **e/ou** identidade do usuário/LF conforme o modelo |
| **Cuidado** | Uma **role única** do QuickSight com acesso total **expõe** tudo aos usuários do dashboard |

### 5.6 Outros

| Serviço | Uso |
|---|---|
| **Amazon SageMaker** | Notebooks/treinos com **roles** e **LF** (confirmar) |
| **Amazon Athena for Apache Spark/EMR Studio** | Notebooks governados |
| **AWS Glue DataBrew** | Preparação visual (permissões na **role**) |
| **Amazon Macie** | **Descoberta de PII** → **alimenta tags** |
| **AWS DataZone/SageMaker Catalog** | **Portal de dados** e **fluxo de assinatura** com **Lake Formation** por baixo (confirmar) |
| **Apache Iceberg/Hudi/Delta** | Formatos de tabela transacionais (suporte conforme serviço/versão) |

## 6. Cenário completo (exemplo)

```
Fonte: RDS PostgreSQL (clientes, pedidos) ──DMS (full+CDC)──▶ S3 raw/ (registrado; acesso só engenharia)
Glue ETL (role EngDados): limpa, tipifica, pseudonimiza CPF ──▶ S3 curated/ (Parquet particionado; registrado)
Catálogo: bancos "raw" e "curated"; LF-Tags: dominio=vendas; sensibilidade=pii nas colunas cpf/email
Grants (TBAC): AnalistaVendas → SELECT em dominio=vendas AND sensibilidade IN (publico, interno)
               Compliance      → SELECT em dominio=vendas (inclui pii) + auditoria
               Gerente Sudeste → data filter regiao='sudeste'
Consumo: Athena (workgroup por equipe), QuickSight (dashboards), EMR (Spark com runtime roles)
Auditoria: CloudTrail → S3/Athena; alarmes para acessos a colunas pii
```

## 7. Erros comuns

- **Esquecer de registrar** o local (o LF “parece” configurado, mas **não media**).
- **Roles de job sem grants** no LF (jobs falham com `Insufficient Lake Formation permission(s)`).
- **Esquecer `DATA_LOCATION_ACCESS`** (não consegue criar tabela).
- **Acesso direto ao S3** por usuários finais.
- **Role única de QuickSight/EMR (instance profile)** com acesso total.
- **KMS/bucket policy** sem permitir a role do LF.
- **Crawlers sem controle** (alteram esquemas inadvertidamente).
- **Dados brutos com PII acessíveis** a analistas (raw sem restrição).
- **Bucket de resultados do Athena** sem proteção.
- **Misturar formatos/partições** sem padrão (desempenho ruim).
- **Ingestão sem classificação/tagging** (dados sensíveis “sem rótulo”).

## 8. Troubleshooting

| Sintoma | Causa provável | Ação |
|---|---|---|
| Athena: `Insufficient Lake Formation permission(s)` | Sem grant no LF; `GetDataAccess` | Conceder `SELECT`/`DESCRIBE`; IAM `lakeformation:GetDataAccess` |
| `HIVE_ACCESS_DENIED` / `AccessDenied` S3 | Local não registrado; role/KMS/bucket policy | Registrar; ajustar a role/KMS |
| Job Glue falha ao gravar | Sem `INSERT`/`DATA_LOCATION_ACCESS` | Conceder; verificar o local |
| Crawler não cria tabela | Sem `CREATE_TABLE`/`DATA_LOCATION_ACCESS` | Conceder à role do crawler |
| EMR ignora filtros do LF | Instance profile/modo; versão | Usar runtime roles/configuração suportada |
| QuickSight mostra dados demais | Role ampla/dataset compartilhado | Restringir a role; usar identidades/RLS |
| Tabela criada mas sem acesso | Sem grants/tags | Conceder/associar tags |
| Resultado do Athena exposto | Bucket sem proteção | Políticas e KMS; limpeza |

## 9. Resumo rápido

- **Registrar locais S3** (service-linked role ou role customizada) → o LF **media o acesso**; `DATA_LOCATION_ACCESS` controla **onde criar tabelas**; **organize camadas** (`raw/curated/analytics`) e **domínios**.
- **Ingestão**: **blueprints** (database snapshot/incremental/log), **Glue ETL**, **DMS**, **Firehose/Kinesis**, **DataSync/AppFlow**; **Parquet/Iceberg**, **partições**, **idempotência**, **classificação (LF-Tags)** e **qualidade**.
- **Credential vending**: serviço pede ao LF → **credenciais temporárias restritas** → lê S3; usuário **sem S3 direto**; IAM precisa de **`lakeformation:GetDataAccess`**.
- **Integrações**: **Athena, Glue, EMR (runtime roles), Redshift Spectrum, QuickSight (Enterprise), SageMaker**; cuidado com **roles amplas** e **instance profiles**.
- **Proteja** bucket de **resultados do Athena**, **KMS** e **acessos diretos**.

## 🧩 Quiz de Fixação

1. O que significa registrar um local no Lake Formation?
2. Para que serve `DATA_LOCATION_ACCESS`?
3. Quais são os tipos de blueprint do Lake Formation?
4. Descreva o fluxo de credential vending em uma consulta Athena.
5. Por que roles de jobs Glue precisam de grants no LF?
6. Que cuidado há com EMR e instance profile?
7. Por que proteger o bucket de resultados do Athena?

**Respostas:**

1. Informar ao LF que ele deve gerenciar o acesso àquele caminho do S3 (via role de acesso), passando a mediar leituras por credenciais temporárias.
2. Controlar quem pode criar bancos/tabelas que apontam para um local registrado, evitando tabelas em qualquer caminho do S3.
3. Database snapshot (carga completa JDBC), incremental database e log file (CloudTrail, ELB/ALB etc.).
4. O Athena valida o IAM, chama o Lake Formation (GetDataAccess), que verifica permissões e devolve credenciais temporárias restritas e o plano de acesso; o Athena lê só o permitido e aplica filtros.
5. Porque, em tabelas governadas, o LF decide o acesso do principal do job; sem SELECT/INSERT/ALTER/DATA_LOCATION_ACCESS o job falha.
6. Um instance profile único dá a todos os jobs o mesmo acesso amplo ao S3, perdendo a granularidade e a multi-tenancy; prefira runtime roles com LF.
7. Porque resultados de consultas são dados e podem conter PII ou informação sensível, funcionando como cópia fora da governança do lake.
