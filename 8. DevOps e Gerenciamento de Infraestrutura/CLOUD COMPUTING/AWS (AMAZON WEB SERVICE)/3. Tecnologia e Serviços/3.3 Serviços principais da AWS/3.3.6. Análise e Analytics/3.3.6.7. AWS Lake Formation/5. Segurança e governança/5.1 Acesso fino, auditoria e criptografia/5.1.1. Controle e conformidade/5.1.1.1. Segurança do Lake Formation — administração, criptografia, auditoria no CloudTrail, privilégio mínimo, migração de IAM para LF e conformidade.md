### 5.1.1.1. Segurança do Lake Formation — administração, criptografia, auditoria no CloudTrail, privilégio mínimo, migração de IAM para LF e conformidade

> [!warning] Aviso
> Nomes de ações IAM/LF, eventos do CloudTrail, comportamento de KMS com credential vending, configurações padrão e modos híbridos abaixo são **de memória e mudam**. **Confirme na documentação do AWS Lake Formation, do IAM, do KMS e do CloudTrail.** Políticas, comandos e consultas são ilustrativos e **não foram executados**. Um data lake concentra **dados sensíveis em escala**: erros de segurança aqui têm **impacto alto**.

## 1. Por que o data lake é um alvo

O data lake **concentra** dados de toda a empresa — frequentemente **dados pessoais, financeiros e de saúde**. Riscos típicos:

| Risco | Exemplo |
|---|---|
| **Acesso direto ao S3** | Usuários com `s3:GetObject` no bucket contornam o Lake Formation |
| **Permissões amplas** | `IAMAllowedPrincipals`, `SUPER`, grants a `*` |
| **Administração excessiva** | Muitos **data lake admins** ou roles compartilhadas |
| **Dados sensíveis sem classificação** | PII em tabelas “sem tag” acessíveis a muitos |
| **Chaves KMS expostas** | Políticas de chave amplas (decrypt para todos) |
| **Resultados de consultas** | Buckets de **resultados do Athena/exports** com cópias de dados sensíveis |
| **Compartilhamento externo** | Dados enviados a contas/organizações não aprovadas |
| **Falta de auditoria** | Sem trilha de **quem acessou quais dados** |
| **Pipelines com privilégios excessivos** | Roles de ETL com acesso a tudo |
| **Exfiltração** | Cópias para buckets externos, `CTAS` para bucket aberto |

Defesa em camadas: **identidade e administração** → **autorização fina** → **criptografia** → **rede** → **auditoria e detecção** → **governança e conformidade**.

## 2. Administração segura

### 2.1 Quem administra

| Papel | Prática |
|---|---|
| **Data lake administrators** | **Poucos** (2–4), via **roles** federadas (SSO + MFA), **sessões curtas**; **break-glass** com alerta |
| **Read-only administrators** | Auditoria/segurança |
| **Database creators** | **Donos de domínio** apenas |
| **Donos de dados** | **Grant option** limitado ao seu domínio |
| **Pipelines** | **Roles por pipeline**, com **grants mínimos** (INSERT/CREATE_TABLE na camada certa) |
| **Consumidores** | **SELECT/DESCRIBE** conforme tags/filtros |

### 2.2 IAM para administração do LF

| Ação (exemplos de memória) | Perfil |
|---|---|
| `lakeformation:GrantPermissions`, `RevokePermissions`, `BatchGrantPermissions` | **Admins/donos** |
| `lakeformation:PutDataLakeSettings` | **Somente administradores de plataforma** |
| `lakeformation:RegisterResource`, `DeregisterResource` | **Plataforma** |
| `lakeformation:CreateLFTag`, `AddLFTagsToResource` | **Governança de dados** (**taxonomia**) |
| `lakeformation:GetDataAccess` | **Principais consumidores/serviços** |
| `lakeformation:List*`, `Describe*`, `GetEffectivePermissions*` | **Auditoria** |

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Sid": "ProtegerAdministracaoLF",
    "Effect": "Deny",
    "Action": ["lakeformation:PutDataLakeSettings", "lakeformation:RegisterResource", "lakeformation:DeregisterResource",
               "lakeformation:CreateLFTag", "lakeformation:DeleteLFTag", "lakeformation:UpdateLFTag"],
    "Resource": "*",
    "Condition": { "ArnNotLike": { "aws:PrincipalArn": ["arn:aws:iam::*:role/LakePlataformaAdmin", "arn:aws:iam::*:role/GovernancaDados"] } }
  }]
}
```

(SCP ilustrativa.)

### 2.3 Configurações padrão (“Data Catalog settings”)

| Configuração | Recomendação |
|---|---|
| **“Use only IAM access control for new databases/tables”** | **Desmarcar** (senão novos recursos nascem **sem governança do LF**) |
| **Permissões padrão de criação** (`CreateDatabaseDefaultPermissions` / `CreateTableDefaultPermissions`) | **Vazias** (**sem** `IAMAllowedPrincipals`) |
| **Administradores** | Lista **mínima** |
| **Cross-account version** | **Versão recente** |
| **Hybrid access mode** | Somente **temporariamente** (migração) |

## 3. Privilégio mínimo na prática

### 3.1 Estratégia de grants

| Princípio | Aplicação |
|---|---|
| **Negar por padrão** | Sem `IAMAllowedPrincipals`; **tudo** via grants/tags |
| **DESCRIBE vs SELECT** | Conceder **só o necessário** |
| **Colunas** | **Excluir** PII por padrão (`sensibilidade=pii` fora) |
| **Linhas** | **Filtros** para **multi-tenant/regionais** |
| **Tags** | **Taxonomia** simples; **associação restrita** (`ASSOCIATE`) |
| **Camadas** | **Bruta** (restrita), **curada** (analistas por tags), **negócio** (ampla, sem PII) |
| **Grant option** | **Só para donos/admins** |
| **Revisão** | **Trimestral** de grants e roles |
| **Expiração** | Acessos **temporários** (projetos) com **prazo** e **revogação automática** |

### 3.2 Remover o acesso direto ao S3

| Ação | Detalhe |
|---|---|
| **IAM dos usuários** | **Sem** `s3:*` nos buckets do lake |
| **Bucket policy** | **Negar** acesso a **todos** exceto: **role do LF**, **roles de pipelines** e **admins**; usar `aws:PrincipalArn`/`aws:PrincipalOrgID` conforme o caso |
| **Block Public Access** | **Sempre** ligado |
| **ACLs** | **Desabilitadas** (BucketOwnerEnforced) |
| **VPC endpoints + policies** | Restringir caminhos de acesso |
| **Access Points** | Segmentação adicional (opcional) |

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Sid": "NegarAcessoDiretoAoLake",
    "Effect": "Deny",
    "Principal": "*",
    "Action": "s3:*",
    "Resource": ["arn:aws:s3:::datalake-123456789012", "arn:aws:s3:::datalake-123456789012/*"],
    "Condition": { "ArnNotLike": { "aws:PrincipalArn": [
        "arn:aws:iam::123456789012:role/aws-service-role/lakeformation.amazonaws.com/AWSServiceRoleForLakeFormationDataAccess",
        "arn:aws:iam::123456789012:role/PipelinesDados*", "arn:aws:iam::123456789012:role/LakePlataformaAdmin" ] } }
  }]
}
```

(Esboço: valide com a documentação e teste exaustivamente para não bloquear o próprio LF/serviços.)

## 4. Criptografia

### 4.1 Em repouso

| Camada | Prática |
|---|---|
| **S3** | **SSE-KMS (CMK)** por camada/domínio; **bucket default encryption**; **bucket keys** (reduz custo) |
| **Glue Data Catalog** | **Criptografia do catálogo** (metadados e senhas de conexão) com KMS |
| **Resultados do Athena** | **SSE-KMS** no workgroup/bucket de resultados |
| **Logs** (CloudTrail/Athena/Glue) | **KMS** |
| **EMR/Redshift/EBS** | Criptografia habilitada |

### 4.2 KMS com Lake Formation

| Ponto | Detalhe |
|---|---|
| **Credential vending e KMS** | A **role de acesso do LF** (service-linked ou customizada) precisa de **`kms:Decrypt`/`GenerateDataKey`** na **CMK** do bucket |
| **Key policy** | Permitir **role do LF**, **roles de pipelines**; **negar** o resto |
| **Cross-account** | A **key policy da produtora** deve permitir o **uso** pelas **roles** envolvidas (conforme o modelo de acesso) |
| **Separação de chaves** | **CMKs distintas** por **sensibilidade/domínio** |
| **Alarmes** | `DisableKey`/`ScheduleKeyDeletion` |
| **Rotação** | **Habilitada** |

### 4.3 Em trânsito

- **TLS** em todos os acessos (S3, Athena, JDBC/ODBC); **bucket policy** exigindo `aws:SecureTransport`.
- **VPC endpoints** (S3, Glue, Athena, KMS, STS) para **tráfego privado**.

## 5. Rede

| Controle | Detalhe |
|---|---|
| **VPC endpoints** | **S3 (gateway)**, **Glue**, **Athena**, **Lake Formation**, **KMS**, **STS**, **CloudWatch Logs** |
| **Endpoint policies** | Restringir **buckets/ações** acessíveis (ex.: só buckets do lake/organização) |
| **Sem internet** | Pipelines/EMR em **subnets privadas** |
| **Acesso de usuários** | **Athena console/JDBC** via **SSO** e rede corporativa/VPN; **bloqueio** de downloads massivos quando aplicável |
| **Egress** | **Network Firewall/proxy** para evitar **exfiltração** a destinos externos |

## 6. Dados sensíveis: classificação e proteção

| Prática | Detalhe |
|---|---|
| **Descoberta** | **Macie** (S3) e **Glue classifiers/Sensitive Data Detection** identificam **PII** |
| **Classificação automática** | Resultados → **LF-Tags** (`sensibilidade=pii/...`) via **automação** |
| **Minimização** | **Não ingerir** o que não é necessário; **tokenizar/pseudonimizar** na **ingestão** |
| **Mascaramento** | LF **remove** colunas/linhas; para **mascarar valores**, usar **views**, **Glue/EMR**, **Redshift DDM** |
| **Segregação** | **Camadas** e **domínios**; **PII** em **tabelas separadas** (junção sob justificativa) |
| **Direitos dos titulares (LGPD/GDPR)** | **Localizar** e **apagar/anonimizar** dados de um titular (**Iceberg/Hudi `DELETE`**, reprocessamento); manter **mapa de dados** |
| **Retenção** | **Lifecycle do S3** e **expurgo** por política |
| **Finalidade e base legal** | Documentar por **produto de dados** |
| **Resultados de consultas** | **Bucket protegido**, **retenção curta**, **KMS** |

## 7. Auditoria e detecção

### 7.1 Fontes

| Fonte | O que mostra |
|---|---|
| **CloudTrail (LF)** | **Concessões/revogações** (`GrantPermissions`, `RevokePermissions`), **configurações** (`PutDataLakeSettings`), **tags**, **registros** de recursos, e **`GetDataAccess`** (**quem pediu acesso a qual tabela/coluna**) |
| **CloudTrail (Glue/Athena)** | `StartQueryExecution` (texto da consulta), mudanças no catálogo |
| **CloudTrail data events (S3)** | **Acessos a objetos** (volume alto: habilitar **seletivamente**) |
| **Athena query history/logs** | Consultas executadas, **bytes escaneados** |
| **S3 server access logs** | Acessos ao bucket (incl. **acesso direto** indevido) |
| **KMS (CloudTrail)** | Uso de chaves (**Decrypt**) |
| **Macie/GuardDuty (S3 protection)** | **Dados sensíveis**, **anomalias** de acesso |
| **IAM Access Analyzer** | **Acesso externo** (buckets/KMS) |
| **Config/Security Hub** | **Conformidade** (buckets, criptografia, BPA) |

### 7.2 Consulta de auditoria (Athena sobre CloudTrail; ilustrativa)

```sql
-- Quem acessou dados via Lake Formation (GetDataAccess) nos últimos 7 dias
SELECT eventtime, useridentity.arn AS principal, requestparameters
FROM cloudtrail_logs
WHERE eventsource = 'lakeformation.amazonaws.com' AND eventname = 'GetDataAccess'
  AND eventtime > date_format(date_add('day', -7, current_timestamp), '%Y-%m-%dT%H:%i:%sZ')
ORDER BY eventtime DESC LIMIT 200;
```

### 7.3 Alarmes recomendados

| Alarme | Condição |
|---|---|
| **Alteração de configurações do LF** | `PutDataLakeSettings`, `Register/DeregisterResource` fora do pipeline |
| **Concessões amplas** | `GrantPermissions` com `SUPER`/`ALL`, a `IAMAllowedPrincipals`, **cross-account** novos |
| **Associação de tags sensíveis** | Remoção/alteração de `sensibilidade=pii` |
| **Acesso a dados PII** | `GetDataAccess` em recursos com tag PII por principais incomuns |
| **Acesso direto ao S3** | Acessos ao bucket **fora** da role do LF/pipelines |
| **Volume anômalo** | **Grande quantidade de dados** lidos/escaneados por um principal |
| **Compartilhamentos externos** | Novos grants/shares fora da organização |
| **Mudanças de KMS** | `DisableKey`, mudanças de key policy |
| **Falhas de autorização** | Picos de `AccessDenied` (varredura de permissões) |

## 8. Migração de IAM para Lake Formation (segurança)

| Passo | Cuidado |
|---|---|
| **Inventário de acessos** | CloudTrail/S3 logs/Athena history para **mapear consumidores** |
| **Hybrid mode** | Evita **quebrar** pipelines; **piloto** por principais |
| **Grants equivalentes** | Reproduzir acessos **legítimos**; **negar** o excesso |
| **Remover `IAMAllowedPrincipals`** | **Por banco/tabela**, após validar |
| **Remover S3 direto** | **Último passo** (após validar o LF) |
| **Testes** | Com **usuários reais** de cada perfil; **cenários negativos** (deve **negar**) |
| **Rollback** | Plano (reativar híbrido; reconceder temporariamente) |
| **Comunicação** | Donos e consumidores informados |

## 9. Governança e conformidade

| Tema | Prática |
|---|---|
| **Responsabilidades** | **Plataforma** (infra LF/S3/KMS), **Governança de dados** (taxonomia/políticas), **Donos de domínio** (grants), **Segurança** (auditoria), **Privacidade/DPO** (base legal) |
| **Catálogo de produtos de dados** | Dono, finalidade, sensibilidade, SLAs, **consumidores aprovados** |
| **Fluxo de acesso** | **Solicitação → aprovação (dono) → concessão (IaC/tags) → revisão periódica** |
| **IaC** | **Grants/tags/locais** como código (**Terraform/CloudFormation**), PR/aprovação |
| **Revisões de acesso** | **Trimestrais**; **recertificação** pelos donos |
| **Conformidade** | **LGPD/GDPR/HIPAA/PCI**: **minimização**, **controle de acesso**, **auditoria**, **retenção**, **direitos dos titulares** |
| **Evidências** | Relatórios de **permissões efetivas** (`list-permissions`/`GetEffectivePermissionsForPath`), **CloudTrail**, revisões |
| **Gestão de incidentes** | **Playbook**: exposição de dados → **revogar**, **investigar CloudTrail**, **notificar** (DPO/autoridades conforme a lei) |
| **Treinamento** | Donos e analistas entendem **LF-Tags**, **PII** e **riscos** |

## 10. Checklist de endurecimento

- [ ] **Poucos admins**, via roles com **SSO/MFA**; **SCP** protegendo configurações do LF
- [ ] **Data Catalog settings**: **sem** “IAM only” padrão, **sem** `IAMAllowedPrincipals` em recursos governados
- [ ] **Acesso direto ao S3 removido** para usuários; **bucket policy** restritiva; **Block Public Access**; ACLs desativadas
- [ ] **LF-Tags (TBAC)** com **taxonomia** simples e **associação restrita**; **PII fora** por padrão
- [ ] **Data filters** para linhas/colunas conforme necessidade; **grant option** controlado
- [ ] **KMS CMKs** por sensibilidade, **key policies mínimas**, **alarmes**; catálogo e resultados do Athena **criptografados**
- [ ] **VPC endpoints** + **endpoint policies**; **egress** controlado
- [ ] **Macie/classificação** → **tags** automáticas; **minimização/pseudonimização**
- [ ] **CloudTrail (LF/Glue/Athena/S3/KMS)** centralizado, **alarmes** e **consultas de auditoria**
- [ ] **IaC** para grants/tags/locais; **revisões trimestrais**
- [ ] **Processo** de acesso e **resposta a incidentes** documentados

## 11. Erros comuns

- **Acesso direto ao S3** mantido.
- **`IAMAllowedPrincipals`** e **defaults IAM-only**.
- **Admins demais** / roles compartilhadas.
- **PII sem tags** (acessível a muitos).
- **KMS** permissivo.
- **Bucket de resultados do Athena** exposto.
- **Compartilhamento externo** sem aprovação.
- **Sem auditoria** do `GetDataAccess`.
- **Migrar “de uma vez”** e quebrar pipelines (ou **deixar híbrido para sempre**).
- **Achar que filtros mascaram valores**.
- **Não revisar** acessos periodicamente.
- **Pipelines com `SUPER`**.

## 12. Troubleshooting

| Sintoma | Causa provável | Ação |
|---|---|---|
| Usuário acessa dados sem grant | Acesso direto ao S3/`IAMAllowedPrincipals`/híbrido | Remover S3 direto; revisar defaults e híbrido |
| `AccessDenied` KMS | Key policy sem a role do LF | Ajustar a key policy |
| LF-Tag não restringe | Recurso com `IAMAllowedPrincipals` | Remover; verificar associações |
| Pipeline quebrou após endurecer | Faltam grants/roles na bucket policy | Conceder/ajustar |
| Auditoria incompleta | Data events desabilitados; trail sem cobertura | Habilitar trails/data events seletivos |
| Muitos `AccessDenied` | Varredura ou má configuração | Investigar origem; corrigir permissões |
| Compartilhamento externo detectado | Grant/RAM indevido | Revogar; SCP; investigar |
| Dados sensíveis em tabela sem tag | Falta classificação | Macie/classificadores; taguear |

## 13. Resumo rápido

- **Alvo de alto valor**: proteger **administração, autorização, dados, chaves, rede e auditoria**.
- **Administração**: **poucos admins** (roles+SSO+MFA), **SCP** protegendo configurações, **defaults sem `IAMAllowedPrincipals`**.
- **Privilégio mínimo**: **TBAC**, **filtros**, **PII fora** por padrão, **grant option** restrito, **remover S3 direto** (bucket policy), **camadas**.
- **Criptografia**: **KMS CMKs** (role do LF com decrypt), **catálogo e resultados do Athena** criptografados, **TLS**, **VPC endpoints**.
- **Dados sensíveis**: **Macie → tags**, **minimização**, **pseudonimização**, **direitos dos titulares** (Iceberg/Hudi delete), **retenção**.
- **Auditoria**: **CloudTrail** (`GetDataAccess`, grants, settings), **S3/KMS logs**, **Access Analyzer**, **alarmes**.
- **Migração IAM→LF**: **híbrido + piloto**, **grants equivalentes**, **testes negativos**, **S3 direto removido por último**.
- **Governança**: **RACI**, **IaC**, **revisões trimestrais**, **incidentes**.

## 🧩 Quiz de Fixação

1. Por que o acesso direto ao S3 compromete o Lake Formation?
2. Quais configurações padrão do catálogo devem ser revisadas?
3. Como o KMS interage com o credential vending?
4. Como auditar quem acessou quais dados?
5. Que cuidado há ao migrar de IAM para LF?
6. Como lidar com direitos dos titulares (LGPD) em um lake?
7. Por que proteger o bucket de resultados do Athena?

**Respostas:**

1. Porque o usuário com acesso direto ao bucket contorna as permissões de tabela/coluna/linha do LF; a governança só vale se o acesso passar pelo LF.
2. “Use only IAM access control” para novos bancos/tabelas e as permissões padrão de criação (IAMAllowedPrincipals), além da lista de administradores, versão cross-account e uso temporário do hybrid mode.
3. A role de acesso do LF precisa de kms:Decrypt/GenerateDataKey na CMK do bucket; a key policy deve permitir essa role e as roles de pipelines, e negar o resto.
4. Pelo CloudTrail (eventos GetDataAccess, concessões e configurações do LF, consultas do Athena), complementado por logs do S3 e do KMS, consultados via Athena e com alarmes.
5. Usar hybrid mode e principais piloto, reproduzir acessos legítimos, testar cenários negativos, remover IAMAllowedPrincipals por recurso e retirar o acesso direto ao S3 por último, com plano de rollback.
6. Mapeando onde estão os dados do titular, usando formatos transacionais (Iceberg/Hudi) com DELETE ou reprocessamento, minimizando/pseudonimizando e definindo retenção.
7. Porque resultados de consultas contêm dados (possivelmente PII) e criam cópias fora da governança do lake.
