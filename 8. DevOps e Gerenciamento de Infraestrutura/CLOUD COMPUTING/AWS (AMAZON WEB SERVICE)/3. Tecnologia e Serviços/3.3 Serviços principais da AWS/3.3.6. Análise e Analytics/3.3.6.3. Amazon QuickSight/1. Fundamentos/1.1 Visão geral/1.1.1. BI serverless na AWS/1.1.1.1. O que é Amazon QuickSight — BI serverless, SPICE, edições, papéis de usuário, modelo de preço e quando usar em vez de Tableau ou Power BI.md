### O que é Amazon QuickSight — BI serverless, SPICE, edições, papéis de usuário, modelo de preço e quando usar em vez de Tableau ou Power BI

> [!warning] Aviso
> A AWS vem evoluindo e **reorganizando** a marca e os recursos do QuickSight (incluindo a integração com assistentes de IA generativa na linha **Amazon Quick Suite**). Edições, papéis, preços, limites e nomes de recursos mudam com frequência. Os números aqui são referências de estudo; confirme na documentação oficial. Os comandos são exemplos e **não foram executados**.

O **Amazon QuickSight** é o serviço de **Business Intelligence (BI)** da AWS: uma plataforma **totalmente gerenciada e serverless** para **conectar dados**, **criar visualizações e dashboards interativos**, **compartilhá-los com milhares de usuários** e **embuti-los em aplicações**, **sem instalar nem administrar servidores de BI**. Ele **escala automaticamente** conforme o número de usuários e se conecta às fontes de dados da AWS (Athena, Redshift, RDS, S3, OpenSearch) e a fontes externas (Snowflake, bancos on-premises, SaaS).

Dois ingredientes definem o serviço: o **SPICE** (um motor em memória que acelera consultas) e o **modelo de cobrança por usuário/sessão**, pensado para **espalhar BI por toda a organização** sem licenças caras por assento.

**Analogia:** os dados no data lake ou no warehouse são **ingredientes em um grande depósito**. O QuickSight é **o restaurante com salão e cozinha**: o **autor** (chef) prepara os pratos (análises e dashboards), o **leitor** (cliente) consome pelo cardápio (dashboard) e pode **explorar** (filtrar, detalhar), e o **SPICE** é a **bancada refrigerada** onde os ingredientes mais usados ficam **prontos e à mão**, para servir em segundos sem ir ao depósito toda vez.

## Onde o QuickSight se encaixa na arquitetura de dados

```
 FONTES                      PREPARAÇÃO / ARMAZENAMENTO              CONSUMO (BI)
 ──────                      ───────────────────────────             ────────────
 Aplicações, bancos ──► Glue / DMS / Firehose ──► S3 (data lake) ─┐
 SaaS, logs, IoT                                   Redshift        ├─► Athena / Redshift / RDS
                                                                    │          │
                                                                    └──────────▼───────────
                                                                         AMAZON QUICKSIGHT
                                                                      (datasets + SPICE + dashboards)
                                                                               │
                                          ┌────────────────────────────────────┼─────────────────────┐
                                          ▼                                    ▼                     ▼
                                   Dashboards (web/mobile)            Relatórios e alertas      Embutido em apps
```

| Camada | Função |
|---|---|
| **Fontes** | Onde nascem os dados |
| **Data lake / warehouse** | Armazenamento e modelagem (S3 + Athena, Redshift) |
| **QuickSight** | **Camada semântica e de visualização**: datasets, campos calculados, dashboards |
| **Consumo** | Usuários de negócio, aplicações embutidas, e-mails, alertas |

> [!tip] O QuickSight não é o seu data warehouse
> Ele **consome** dados já preparados. A **qualidade do BI depende da modelagem a montante** (tabelas curadas, particionadas, com nomes claros). Dashboards sobre dados brutos e desorganizados ficam **lentos, caros e confusos**.

## Conceitos centrais

| Conceito | O que é |
|---|---|
| **Data source (fonte de dados)** | **Conexão** com um sistema (Athena, Redshift, RDS, S3, Snowflake, arquivo) |
| **Dataset** | **Conjunto de dados preparado** para análise: tabelas, junções, campos calculados, filtros, tipos |
| **SPICE** | **Motor em memória** (Super-fast, Parallel, In-memory Calculation Engine) que **armazena uma cópia otimizada** do dataset |
| **Direct Query** | O dashboard **consulta a fonte diretamente** a cada interação (sem cópia no SPICE) |
| **Analysis (análise)** | Espaço de **criação** do autor: visuais, filtros, parâmetros, controles |
| **Visual (gráfico)** | Um elemento: barras, linhas, tabela, mapa, KPI, etc. |
| **Dashboard** | **Versão publicada e somente leitura** de uma análise, compartilhada com leitores |
| **Story / Pixel-perfect report** | Narrativa guiada / relatório de **layout fixo** para impressão/e-mail |
| **Topic (Q)** | Conjunto de dados preparado para **perguntas em linguagem natural** |
| **Namespace / Group** | Isolamento multi-inquilino / agrupamento de usuários para permissões |
| **Folder** | Organização de ativos (análises, dashboards, datasets) com permissões |
| **Theme** | Aparência (cores, fontes) reutilizável |

### O fluxo de trabalho típico

```
 1. Conectar uma FONTE  ──►  2. Criar um DATASET (junções, campos, SPICE ou Direct Query)
        │                              │
        ▼                              ▼
 3. Construir uma ANÁLISE (visuais, filtros, parâmetros)  ──►  4. Publicar um DASHBOARD
                                                                        │
                                       5. Compartilhar com usuários/grupos, alertas, e-mail, embedding
```

## SPICE vs Direct Query

| Critério | **SPICE** | **Direct Query** |
|---|---|---|
| **Onde estão os dados** | **Cópia** otimizada no SPICE | Na **fonte** (consultados em tempo real) |
| **Desempenho** | **Muito rápido**, independe da fonte | Depende do desempenho e carga da fonte |
| **Atualização** | **Agendada** (até 100 por dia em Enterprise) ou por API | **Tempo real** (sempre atual) |
| **Carga na fonte** | **Baixa** (só no refresh) | **Alta** (cada interação consulta) |
| **Custo** | **GB de SPICE** por mês | Custo de consulta da fonte (Athena por TB, Redshift) |
| **Limites** | Capacidade e tamanho do dataset | Tempo limite de consulta |
| **Concorrência** | Escala para muitos leitores | Pode **sobrecarregar** a fonte |
| **Quando usar** | **Maioria dos dashboards** | Dados que **precisam ser em tempo real** ou muito grandes para SPICE |

```
 Dados atualizados algumas vezes por dia basta?            ─► SPICE
 Muitos leitores, picos de acesso, quer baixa carga na fonte? ─► SPICE
 Precisa de dado do último segundo ou volume imenso?          ─► Direct Query (com fonte performática)
```

> [!warning] Direct Query em Athena pode ficar caro
> Cada filtro ou clique em um dashboard sobre **Athena** gera **uma consulta paga por TB escaneado**. Com muitos leitores, a fatura cresce. **SPICE** (ou **tabelas agregadas** no Athena) costuma ser a melhor escolha para dashboards populares.

## Edições e papéis de usuário

> [!info] Modelos de licença mudam
> Os nomes e preços de **edições e papéis** evoluem (Standard foi descontinuada para novos clientes em favor da **Enterprise**). Confirme o modelo vigente antes de decidir.

| Papel | O que faz | Cobrança (referência) |
|---|---|---|
| **Reader (leitor)** | **Consome** dashboards, filtra, explora | Barata, por usuário/mês **ou por sessão** (*pay-per-session*, com teto mensal) |
| **Reader Pro** | Leitor + **perguntas em linguagem natural (Q/IA)** e narrativas | Mais cara que Reader |
| **Author (autor)** | **Cria** análises, datasets e dashboards | Por usuário/mês |
| **Author Pro** | Autor + recursos de **IA generativa** (criar visuais por linguagem natural, construir narrativas) | Por usuário/mês |
| **Admin** | Gerencia usuários, permissões, capacidade e configurações da conta | Conforme o papel de autor |
| **Capacity pricing** (leitores por capacidade) | Contrata **sessões de leitor por mês** em pacote para **grandes populações** | Preço fixo por capacidade |

| Tipo de edição (Enterprise) | Recursos relevantes |
|---|---|
| **Enterprise** | **RLS e CLS**, **VPC connections**, **Active Directory / IAM Identity Center**, **embedding**, **criptografia em repouso (KMS)**, **ML Insights**, **relatórios agendados**, **alertas**, **API completa**, **auditoria** |
| **Enterprise + Q** | Adiciona **Topics** e **geração de insights por linguagem natural** |

> [!tip] Reader por sessão é o segredo da escalabilidade de custo
> O modelo de **leitores pay-per-session** permite dar acesso a **milhares de pessoas** que usam o dashboard **ocasionalmente**: paga-se **por sessão**, com **teto mensal por leitor**, em vez de uma licença fixa por assento (como em muitas ferramentas concorrentes).

## QuickSight vs outras ferramentas de BI

| Critério | **QuickSight** | **Tableau** | **Power BI** | **Looker / Metabase / Superset** |
|---|---|---|---|---|
| **Modelo** | **Serverless**, SaaS na AWS | Servidor/Cloud (Salesforce) | SaaS (Microsoft) + Desktop | SaaS ou autohospedado |
| **Licenciamento** | **Por usuário/sessão**, leitor barato | Por usuário (mais caro) | Por usuário (Pro/Premium) | Variado |
| **Integração com AWS** | **Nativa** (IAM, VPC, KMS, Athena, Redshift) | Conectores | Conectores | Conectores |
| **Escala de leitores** | **Muito boa** (sem servidores) | Exige dimensionamento | Capacidades Premium | Depende |
| **Profundidade de visuais** | Boa, em evolução | **Muito alta** | **Muito alta** | Variável |
| **Embedding** | **Forte** (SDK, anônimo por sessão) | Bom | Bom | Bom |
| **IA generativa** | Q / Quick Suite | Tableau Pulse/Einstein | Copilot | Variável |
| **Ideal para** | Quem **está na AWS** e quer BI barato e escalável | Análises visuais sofisticadas | Ecossistema Microsoft | Camada semântica e código |

```
 Dados já na AWS, muitos leitores, quer BI sem servidores e com embedding?  ─► QuickSight
 Precisa de visuais muito sofisticados e comunidade/ecossistema Tableau?    ─► Tableau
 Empresa centrada em Microsoft 365/Azure?                                    ─► Power BI
 Quer camada semântica como código e versionamento forte?                    ─► Looker / dbt + BI
```

## Limitações e cuidados

| Limitação | Implicação |
|---|---|
| **Menos flexível que Tableau/Power BI** em visuais muito customizados | Verifique se os visuais necessários existem |
| **Dependência de modelagem** | Dados ruins geram dashboards ruins |
| **SPICE tem capacidade e limites** | Datasets muito grandes exigem agregação ou Direct Query |
| **Refresh com limite diário** | Planejar a frequência |
| **Governança exige esforço** | Datasets duplicados e "dashboards órfãos" proliferam |
| **Custos de Direct Query** | Pode superar o do SPICE |
| **Região** | Dados e SPICE ficam em uma região |
| **Evolução de marca e recursos** | Documentação e nomes mudam |

## Primeiros passos (visão geral)

1. **Assinar o QuickSight** na região desejada (conta da AWS, edição Enterprise, método de autenticação: IAM Identity Center, IAM ou Active Directory).
2. **Conceder acesso** do QuickSight às fontes (S3, Athena, Redshift) via **permissões do serviço** (e VPC connections para privados).
3. **Criar a fonte e o dataset** (SPICE ou Direct Query).
4. **Construir uma análise** com visuais e filtros.
5. **Publicar o dashboard** e **compartilhar** com grupos.
6. **Agendar refresh** do SPICE e **alertas/relatórios**.

```bash
# Cria uma fonte do Athena (exemplo)
aws quicksight create-data-source --aws-account-id 123456789012 \
  --data-source-id athena-lake --name "Athena Lake" --type ATHENA \
  --data-source-parameters 'AthenaParameters={WorkGroup=bi}' \
  --permissions 'Principal=arn:aws:quicksight:us-east-1:123456789012:group/default/Analistas,Actions=quicksight:DescribeDataSource,quicksight:PassDataSource'
```

## Exemplo prático: dashboard de vendas

1. Os pedidos chegam ao **S3** (via Firehose, em Parquet particionado) e são catalogados no **Glue**.
2. Uma **tabela agregada diária** no **Athena** (CTAS agendado) reduz o volume para o BI.
3. No QuickSight, cria-se um **dataset sobre a tabela agregada** em **SPICE**, com **refresh a cada hora**.
4. A equipe de dados monta uma **análise**: KPIs de faturamento e ticket médio, linha do tempo, mapa por região, filtros por canal.
5. Publica o **dashboard** e compartilha com o **grupo Comercial** (leitores).
6. Configura **alerta** quando o faturamento diário cai mais de 20% e **relatório PDF** semanal para a diretoria.
7. A equipe de FinOps acompanha o custo do SPICE e das consultas.

## Erros comuns e armadilhas

- **Conectar dashboards a dados brutos** em Direct Query sobre Athena sem agregação.
- **Um dataset por analista**, criando duplicatas e números divergentes ("verdades múltiplas").
- **Não definir quem é Author e quem é Reader**, pagando licenças de autor para quem só consome.
- **Ignorar a capacidade do SPICE** e estourar o limite.
- **Refresh frequente demais** sem necessidade.
- **Dashboards sem donos nem documentação**, que viram lixo.
- **Esquecer RLS/CLS** em dados sensíveis.
- **Achar que o BI substitui a modelagem de dados.**

## 🧩 Quiz de Fixação

1. O que é o SPICE?
2. Qual a diferença entre uma análise e um dashboard?
3. Quando preferir Direct Query a SPICE?
4. Por que o modelo de leitor por sessão ajuda no custo?
5. O que é um dataset no QuickSight?
6. Por que modelar bem os dados antes do BI?

**Respostas:**
1) Motor em memória do QuickSight que armazena uma cópia otimizada dos dados para consultas rápidas e escaláveis.
2) A análise é o espaço de criação do autor; o dashboard é a versão publicada e somente leitura compartilhada com os leitores.
3) Quando os dados precisam estar em tempo real ou o volume é grande demais para o SPICE, e a fonte aguenta a carga de consultas.
4) Porque se paga por sessão (com teto mensal), permitindo dar acesso a muitos usuários ocasionais sem licença fixa por assento.
5) Um conjunto de dados preparado para análise: tabelas, junções, campos calculados, filtros e tipos, em SPICE ou Direct Query.
6) Porque dashboards sobre dados brutos e desorganizados ficam lentos, caros e confusos; a qualidade do BI depende da modelagem a montante.
