### Dados no QuickSight — data sources, datasets, junções, campos calculados, SPICE, refresh incremental, permissões de acesso e boas práticas de modelagem

> [!warning] Aviso
> Limites de SPICE, número de refreshes, tamanho de dataset, funções de cálculo e opções de conexão mudam. Os números aqui são referências de estudo; confirme na documentação. Os comandos e expressões **não foram executados**.

No QuickSight, **os dados vêm antes dos gráficos**. A experiência de quem usa o dashboard (velocidade, números corretos, filtros que fazem sentido) é decidida **na camada de dados**: **como as fontes são conectadas**, **como o dataset é modelado** (junções, campos calculados, tipos, hierarquias), **se ele roda em SPICE ou em Direct Query** e **como é atualizado**. Esta folha cobre esse alicerce: **data sources**, **datasets**, **junções e campos calculados**, **SPICE e refresh (incluindo incremental)**, **permissões** e **boas práticas de modelagem** para evitar os "números divergentes" que minam a confiança em BI.

**Analogia:** é a **cozinha do restaurante**. A **fonte de dados** é o fornecedor; o **dataset** é a **mise en place**: ingredientes **lavados, cortados e combinados** (junções, colunas calculadas) para que o chef (autor) monte pratos rápido; o **SPICE** é a **câmara refrigerada** com a mise en place pronta; o **refresh** é a **reposição programada**. Se a mise en place está errada, **todos os pratos saem errados**.

## Data sources (fontes de dados)

Uma **data source** guarda a **conexão** (host, banco, credenciais ou workgroup) com um sistema. A partir dela, criam-se **datasets**.

| Tipo de fonte | Como conecta | Observações |
|---|---|---|
| **Athena** | Workgroup + banco/tabela do Glue | Usa as permissões do QuickSight sobre S3/Glue/KMS |
| **Redshift** | Cluster ou Serverless (endpoint, banco, usuário) | Conexão pública ou via **VPC connection** |
| **RDS / Aurora** | Endpoint do banco | Normalmente **via VPC** (banco privado) |
| **S3** | **Arquivo manifesto** (JSON) listando os arquivos e o formato | CSV, TSV, JSON, XLSX |
| **Snowflake, Teradata, Databricks, etc.** | Parâmetros de conexão | Credenciais guardadas pelo QuickSight |
| **SaaS** (Salesforce, ServiceNow…) | OAuth/credenciais | Atualização por SPICE |
| **Upload de arquivo** | CSV/XLSX local | Para protótipos |
| **OpenSearch, Timestream, IoT** | Conectores | Séries temporais e logs |

```json
{
  "fileLocations": [
    {"URIPrefixes": ["s3://meu-datalake/relatorios/vendas/"]}
  ],
  "globalUploadSettings": {"format": "CSV", "delimiter": ",", "containsHeader": "true"}
}
```

### Acesso do QuickSight às fontes

| Cenário | O que configurar |
|---|---|
| **Athena + S3** | Em *Manage QuickSight → Security & permissions*: permitir **Athena**, os **buckets S3** de dados e de resultados e (se houver) a **chave KMS** |
| **Fonte em VPC privada** | **VPC connection** (ENIs do QuickSight em subnets e security groups seus) |
| **On-premises** | VPC connection + VPN/Direct Connect |
| **Lake Formation** | Permissões da **role do QuickSight** no Lake Formation (ou por usuário, conforme o modo) |
| **Credenciais** | Armazenadas pelo QuickSight (criptografadas); preferir usuários **somente leitura** |

> [!warning] "Erro ao acessar S3/Athena" é o problema nº 1 de quem começa
> Quase sempre é **permissão do QuickSight** não concedida ao bucket/chave KMS/Glue/Lake Formation. A origem é a **role de serviço do QuickSight** (`aws-quicksight-service-role-v0`): ajuste lá, não no usuário final.

## Datasets

O **dataset** é o **objeto central**: define **de onde vêm os dados** e **como se apresentam** ao autor.

| Elemento | Função |
|---|---|
| **Tabelas de origem** | Uma ou mais tabelas/consultas SQL |
| **Consulta SQL customizada** | Escrever SQL na fonte (Athena/Redshift/RDS) para pré-processar |
| **Junções (joins)** | Combinar tabelas (inner, left, right, full) no editor visual |
| **Campos calculados** | Colunas derivadas por **expressões** |
| **Tipos de dados** | Texto, inteiro, decimal, data, geográficos |
| **Hierarquias** | Níveis (país → estado → cidade) para *drill-down* |
| **Filtros do dataset** | Reduzem os dados **antes** de entrarem no SPICE |
| **Colunas renomeadas/ocultas** | Interface limpa para o autor |
| **Descrições e formatos** | Contexto para usuários |
| **RLS / CLS** | Segurança por linha/coluna (veja a folha de segurança) |
| **Modo de armazenamento** | **SPICE** ou **Direct Query** |

```
 Dataset "vendas"
   ├─ tabela vendas_dia (fato)                ── join (inner) ──► dim_produto
   │                                          ── join (left)  ──► dim_cliente
   ├─ campos calculados: margem = receita - custo ; margem_pct = margem / receita
   ├─ filtro: data >= '2024-01-01'
   ├─ hierarquia geográfica: pais > estado > cidade
   └─ armazenamento: SPICE (refresh a cada hora)
```

### Tipos de junção e cuidados

| Junção | Resultado | Risco |
|---|---|---|
| **Inner** | Só linhas com correspondência | Perde linhas sem par |
| **Left** | Todas da esquerda + correspondências | Nulos nas colunas da direita |
| **Right / Full** | Todas da direita / de ambos os lados | Nulos e volume |
| **Junção "muitos para muitos"** | Multiplica linhas | **Duplica valores** (soma inflada) |

> [!warning] A causa clássica de números errados: *fan-out* em junções
> Ao juntar uma **tabela de fatos** a outra tabela em **nível de detalhe diferente** (por exemplo, pedidos × itens), os valores do pedido **se repetem por item** e as somas ficam **infladas**. Corrija modelando **no nível de granularidade correto**, pré-agregando, ou usando **funções LAC-A/LAC-W** (agregação em nível de detalhe) nos cálculos.

### Camada semântica no dataset

| Boa prática | Motivo |
|---|---|
| **Um dataset "certificado"** por domínio (vendas, clientes) | Uma única fonte de verdade |
| **Nomes de negócio** (não `col_vlr_01`) | Legibilidade |
| **Campos calculados reutilizáveis** no dataset (não em cada análise) | Consistência |
| **Descrições** nos campos | Autoatendimento |
| **Ocultar campos técnicos** | Menos ruído |
| **Evitar `SELECT *` e colunas inúteis** | Menos SPICE e custo |
| **Prefira pré-agregar no data lake** | Dataset menor e rápido |

## Campos calculados

Os **campos calculados** criam colunas a partir de **expressões**, no **dataset** (valem para todas as análises) ou na **análise** (só para ela).

```text
# Texto e condicional
categoria_cliente = ifelse({total_compras} >= 10000, 'Premium',
                           {total_compras} >= 1000,  'Regular', 'Novo')

# Datas
mes_pedido        = truncDate('MM', {data_pedido})
dias_para_entrega = dateDiff({data_pedido}, {data_entrega}, 'DD')

# Métricas
margem_pct        = sum({receita} - {custo}) / sum({receita})

# Texto
nome_completo     = concat({nome}, ' ', {sobrenome})

# Janela por nível de detalhe (LAC-W): receita total por região, em cada linha
receita_regiao    = sumOver({receita}, [{regiao}], PRE_AGG)

# Participação no total
participacao      = {receita} / sumOver({receita}, [], POST_AGG_FILTER)
```

| Família de funções | Exemplos |
|---|---|
| **Agregação** | `sum`, `avg`, `count`, `distinct_count`, `min`, `max`, `median`, `percentile` |
| **Condicionais** | `ifelse`, `coalesce`, `isNull`, `in`, `nullIf` |
| **Datas** | `truncDate`, `dateDiff`, `addDateTime`, `extract`, `now`, `formatDate` |
| **Texto** | `concat`, `substring`, `toUpper`, `parseJson`, `split`, `replace` |
| **Numéricas** | `round`, `ceil`, `floor`, `log`, `abs` |
| **Cálculos de tabela** | `runningSum`, `rank`, `percentDifference`, `periodOverPeriod*`, `movingAverage`, `lag`, `lead` |
| **LAC-A / LAC-W** | `sumOver`, `avgOver`, `countOver`, `maxOver`... controlam o **nível de detalhe** |
| **Funções de período** | `periodToDateSum`, `periodOverPeriodDifference`, `parentGroupSum` |

> [!tip] Campos calculados no dataset vs na análise
> Coloque no **dataset** o que **todo mundo deve ver igual** (margem, categoria, KPI oficial). Deixe na **análise** o que é **exploratório**. Assim, a definição de "margem" é **única**.

### Cálculos na fonte vs no QuickSight

| Onde calcular | Vantagem | Desvantagem |
|---|---|---|
| **Na fonte (SQL/Athena/Glue)** | Reutilizável por outras ferramentas, mais rápido | Exige acesso à camada de dados |
| **No dataset (SPICE)** | Rápido para o autor, calculado no refresh (campos "materializados" em SPICE) | Fica "preso" ao QuickSight |
| **Na análise** | Flexível | Não reutilizável; calculado em tempo de consulta |

## SPICE

O **SPICE** é a **memória do QuickSight**: um **armazenamento colunar em memória** que **comprime** e **indexa** os dados do dataset.

| Aspecto | Detalhe |
|---|---|
| **Capacidade** | Cota de **GB por conta/região** (Enterprise: inclusão por autor + compra de GB adicionais) |
| **Limites por dataset** | Em torno de **centenas de milhões de linhas / centenas de GB** (varia; confirme) |
| **Criptografia** | Em repouso (inclusive **KMS com chave do cliente**) |
| **Desempenho** | Consultas em **segundos**, independente da fonte |
| **Compartilhamento** | Um dataset SPICE serve **muitas análises** e dashboards |
| **Custo** | Por **GB-mês** de SPICE utilizado |

### Estimando o SPICE

```
 GB de SPICE ≈ linhas × colunas × tamanho médio por valor ÷ razão de compressão
 Dica: filtre linhas e remova colunas ANTES de importar; agregue quando possível.
```

| Prática para economizar SPICE | Efeito |
|---|---|
| **Filtrar o período** (ex.: últimos 24 meses) | Menos linhas |
| **Excluir colunas não usadas** | Menos bytes |
| **Pré-agregar** (diário em vez de por evento) | Reduz drasticamente |
| **Evitar duplicar datasets** | Um dataset compartilhado |
| **Excluir datasets obsoletos** | Libera capacidade |

## Refresh de datasets SPICE

| Tipo de refresh | Descrição |
|---|---|
| **Completo (full refresh)** | Recarrega **todo** o dataset |
| **Incremental** | Carrega **só dados novos** dentro de uma **janela de tempo** (ex.: últimas 24 h) por coluna de data/hora |
| **Agendado** | Por hora, dia, semana, mês (até **100 por dia por dataset** em Enterprise; confirme) |
| **Sob demanda** | Pelo console ou **API** (`CreateIngestion`) |
| **Por evento** | Disparado por pipeline (EventBridge → Lambda → API) |

```bash
# Dispara um refresh (ingestão) por API
aws quicksight create-ingestion --aws-account-id 123456789012 \
  --data-set-id vendas-dataset --ingestion-id refresh-$(date +%s)

aws quicksight describe-ingestion --aws-account-id 123456789012 \
  --data-set-id vendas-dataset --ingestion-id refresh-xxxx \
  --query 'Ingestion.[IngestionStatus,RowInfo]'
```

| Estado da ingestão | Significado |
|---|---|
| **INITIALIZED / QUEUED / RUNNING** | Em andamento |
| **COMPLETED** | Sucesso |
| **FAILED** | Falha (ver `ErrorInfo`: permissão, fonte, limite) |
| **CANCELLED** | Cancelada |

> [!tip] Refresh orientado a eventos
> Em vez de "a cada hora às cegas", **dispare o refresh quando o pipeline terminar** (EventBridge/Step Functions chamam `CreateIngestion`). Os dashboards ficam atualizados **assim que há dado novo**, sem refreshes desnecessários.

### Refresh incremental

| Requisito | Detalhe |
|---|---|
| **Coluna de data/hora** | Usada para delimitar a janela |
| **Janela** | Ex.: últimas 2 horas, 7 dias |
| **Comportamento** | Linhas dentro da janela são **substituídas**; o restante permanece |
| **Vantagem** | **Menor tempo** e **menos carga** na fonte |
| **Cuidado** | Dados antigos **alterados fora da janela** não são atualizados; faça **refresh completo** periódico |

## Direct Query

| Aspecto | Detalhe |
|---|---|
| **Quando** | Dados em **tempo real** ou volume muito grande |
| **Mecanismo** | Cada visual dispara uma **consulta SQL** à fonte |
| **Cache** | O QuickSight pode **reaproveitar resultados** por curto período |
| **Limites** | Tempo de consulta (cerca de **2 minutos** por visual, aproximadamente) |
| **Custos** | Da fonte (Athena por TB, Redshift) |
| **Melhores práticas** | **Tabelas agregadas**, **materialized views**, **particionamento** e filtros obrigatórios |

```
 Direct Query em Athena: cada filtro do usuário = 1 consulta (cobrada por TB)
 → use tabelas curadas em Parquet particionado, com agregações, e limite os campos expostos
```

## Permissões do dataset e compartilhamento

| Conceito | Descrição |
|---|---|
| **Proprietário (owner)** | Pode editar, compartilhar e excluir |
| **Visualizador (viewer)** | Usa o dataset em análises, sem editá-lo |
| **Compartilhamento com grupos** | Preferível a compartilhar por usuário |
| **Folders** | Organização e herança de permissões para vários ativos |
| **Dashboards e datasets** | Quem vê o dashboard **não precisa** de acesso ao dataset (o dashboard usa as permissões do **dataset** publicado) |
| **Datasets entre contas** | Compartilhamento por **assets bundle** (exportar/importar) ou APIs |

> [!warning] Compartilhar o dataset ≠ compartilhar o dashboard
> Conceder a alguém acesso ao **dataset** permite que **crie análises próprias** com **todos os dados** (se não houver RLS/CLS). Para consumo, compartilhe o **dashboard**; reserve o dataset aos **autores**.

## Boas práticas de modelagem

| Prática | Motivo |
|---|---|
| **Modelo estrela** (fato + dimensões) no data lake/warehouse | Simplicidade e desempenho |
| **Granularidade clara** (uma linha = um pedido, um item, um dia) | Evita fan-out |
| **Tabelas agregadas** para dashboards populares | Rapidez e custo menor |
| **Chaves e tipos consistentes** | Junções corretas |
| **Datas em coluna própria e tipada** | Filtros, hierarquias, comparações de período |
| **Datasets por domínio e certificados** | Fonte única de verdade |
| **Nomenclatura e descrições de negócio** | Autoatendimento seguro |
| **Segurança no dataset** (RLS/CLS) | Aplicada a todos os dashboards |
| **Versionar via API/CloudFormation (asset bundles)** | Promoção entre ambientes |
| **Testar números** contra a fonte | Confiança |
| **Documentar definições** (o que é "receita líquida") | Alinhamento com o negócio |

## Exemplo prático: dataset de vendas bem modelado

1. No data lake, a equipe cria `vendas_dia` (granularidade: **loja × produto × dia**), em Parquet particionado, com **margem pré-calculada**.
2. O dataset do QuickSight usa **inner join** com `dim_produto` (descrições) e **left join** com `dim_loja`, **sem fan-out** (mesma granularidade das chaves).
3. Campos calculados no dataset: `margem_pct`, `categoria_preco`, `mes`.
4. **Filtro do dataset**: últimos 36 meses; colunas técnicas **ocultas**; descrições nos campos.
5. Armazenamento em **SPICE** com **refresh incremental** das últimas 48 h, disparado por **EventBridge** ao final do ETL, e **refresh completo** semanal.
6. **RLS** por região; o dataset é compartilhado **só com autores**; os leitores acessam o **dashboard**.
7. O dataset é **exportado como asset bundle** e promovido a produção por pipeline.

## Troubleshooting

| Sintoma | Causa provável | Como resolver |
|---|---|---|
| **Erro ao criar fonte Athena/S3** | QuickSight sem permissão no bucket/Glue/KMS | Ajustar *Security & permissions* e a role de serviço |
| **Refresh falha** (`FAILED`) | Permissão, fonte indisponível, limite de SPICE, erro de tipo | Ver `ErrorInfo`; corrigir; aumentar SPICE |
| **"SPICE capacity exceeded"** | Limite de SPICE atingido | Reduzir dados; excluir datasets; comprar capacidade |
| **Números inflados/duplicados** | *Fan-out* em junções | Rever granularidade; pré-agregar; LAC-A/LAC-W |
| **Dashboard lento em Direct Query** | Consultas pesadas, tabela sem agregação | Migrar para SPICE; tabelas agregadas; particionar |
| **Dados desatualizados** | Refresh atrasado ou falho | Verificar agendamento e status; refresh por evento |
| **Erro de conexão em RDS/Redshift privado** | Sem VPC connection ou SG bloqueando | Criar VPC connection; liberar portas |
| **Join retorna menos linhas** | Inner join sem correspondência / tipos diferentes | Ajustar tipo/chave; usar left join |
| **Campo calculado com erro** | Sintaxe, tipos ou agregações misturadas | Revisar expressão; separar agregado/não agregado |
| **Fuso horário/data incorretos** | Conversão de timestamp | Ajustar tipo e fuso no dataset/fonte |
| **Quotas de refresh** | Mais de N refreshes por dia | Consolidar; usar incremental |
| **Dados sensíveis expostos** | Dataset compartilhado sem RLS/CLS | Aplicar RLS/CLS; restringir acesso |

## Erros comuns e armadilhas

- **Modelar mal as junções** e produzir números divergentes.
- **Conectar Direct Query ao Athena** com milhares de leitores.
- **Campos calculados duplicados** em cada análise, com definições diferentes.
- **Importar tudo para o SPICE** sem filtrar nem agregar.
- **Compartilhar datasets** com leitores em vez de dashboards.
- **Refresh por relógio** em vez de por evento.
- **Sem refresh completo periódico** em refresh incremental.
- **Ignorar documentação e certificação** de datasets.

## 🧩 Quiz de Fixação

1. O que é um dataset no QuickSight e o que ele contém?
2. Qual a diferença entre refresh completo e incremental?
3. O que é fan-out em junções e como evitá-lo?
4. Por que definir campos calculados no dataset?
5. Como o QuickSight acessa o S3 e o Athena?
6. Por que compartilhar o dashboard em vez do dataset com leitores?

**Respostas:**
1) Um conjunto de dados preparado para análise, com tabelas, junções, campos calculados, filtros, tipos, hierarquias e o modo de armazenamento (SPICE ou Direct Query).
2) O completo recarrega todos os dados; o incremental carrega só os dados novos de uma janela de tempo, sendo mais rápido e leve.
3) Quando a junção entre tabelas de granularidades diferentes repete valores e infla somas; evita-se com granularidade correta, pré-agregação ou funções LAC-A/LAC-W.
4) Para que todas as análises usem a mesma definição (fonte única de verdade) e o cálculo seja reutilizado.
5) Pela role de serviço do QuickSight, com permissões concedidas em Security & permissions aos buckets, Athena, Glue, KMS e Lake Formation.
6) Porque o acesso ao dataset permite criar análises próprias com todos os dados; o dashboard limita o consumo ao que foi publicado.
