### Segurança e embedding no QuickSight — identidade, grupos, namespaces, RLS e CLS, VPC, criptografia, auditoria e incorporação de dashboards em aplicações

> [!warning] Aviso
> Métodos de autenticação, nomes de papéis, opções de embedding, limites de namespaces e preços mudam. Os exemplos aqui são referências de estudo; confirme na documentação. As políticas e comandos **não foram executados**.

Em BI, **segurança é decidir quem vê o quê**: o diretor vê a empresa toda, o gerente regional vê **só a sua região**, o analista de RH **não vê salários**, o cliente de um SaaS vê **apenas os seus dados**. O QuickSight oferece **camadas de segurança** que se combinam: **identidade e autenticação** (quem é você), **papéis e permissões** (o que você pode fazer), **segurança de dados** (**RLS** por linha, **CLS** por coluna), **isolamento multi-inquilino** (**namespaces**), **rede privada** (VPC), **criptografia**, **auditoria** e **embedding** (levar dashboards a aplicações e clientes externos). Esta folha cobre cada camada e como **combiná-las**.

**Analogia:** o QuickSight é **um edifício de escritórios**. A **portaria** valida quem entra (autenticação); o **crachá** define os andares acessíveis (papéis e permissões); dentro de cada sala, **cofres trancados** guardam documentos sensíveis (RLS/CLS); alguns **inquilinos têm andares isolados** (namespaces); o prédio tem **entrada privada por túnel** (VPC); e **câmeras** registram tudo (auditoria). O **embedding** é uma **janela** que mostra parte de uma sala a quem está do lado de fora, com **autorização temporária**.

## Identidade e autenticação

| Método | Descrição | Quando usar |
|---|---|---|
| **IAM Identity Center** | Login único corporativo; grupos sincronizados do IdP (Okta, Entra ID) via SCIM | **Padrão recomendado** em organizações |
| **Federação SAML (IdP externo) com IAM** | Usuários assumem **roles IAM** mapeadas ao QuickSight | Quando já há federação SAML |
| **Active Directory (AWS Managed Microsoft AD / AD Connector)** | Usuários e grupos do AD | Ambientes Microsoft |
| **Usuários IAM** | Usuários da conta AWS | Pequenas contas; evitar em escala |
| **Usuários do QuickSight (e-mail e senha)** | Gerenciados pelo próprio serviço | Convidados e cenários simples |
| **Embedding** | Acesso por **URL assinada** gerada pelo seu backend | Aplicações e portais |

> [!tip] Prefira IAM Identity Center ou federação
> Com **SSO corporativo**, o ciclo de vida do acesso (entrada, mudança de área, saída) acompanha o **diretório da empresa**, com **MFA** aplicado no IdP. Evite contas locais com senha.

### Papéis dentro do QuickSight

| Papel | Pode |
|---|---|
| **Admin** | Gerenciar usuários, grupos, permissões, capacidade, integrações; criar conteúdo |
| **Author** | Criar fontes, datasets, análises, dashboards |

| **Admin Pro** | Admin com recursos Pro |

## Grupos, compartilhamento e organização

| Elemento | Função |
|---|---|
| **Grupos** | Conjuntos de usuários; **compartilhe com grupos**, não com pessoas |
| **Folders** | Pastas (compartilhadas ou pessoais) para dashboards, análises e datasets, com **permissões herdadas** |
| **Permissões em ativos** | **Owner/Co-owner**, **Viewer** (e variantes por tipo: Contributor, Reader) |
| **Namespaces** | **Isolamento total** entre conjuntos de usuários na **mesma conta** (multi-inquilino) |
| **Custom permissions** | Restringem funcionalidades por grupo |
| **Ambientes** | Contas AWS separadas para dev/homologação/produção |

```
 Boa prática de acesso:
   IdP (grupos: "BI-Comercial-Leitores", "BI-Comercial-Autores")
        └─► IAM Identity Center ──► QuickSight (grupos sincronizados)
                                         ├─ Folder "Comercial" (grupo Autores = contribuidores; Leitores = visualizadores)
                                         └─ Dashboards/datasets herdam as permissões da pasta
```

## Segurança em nível de linha (RLS)

O **RLS (Row-Level Security)** **filtra linhas** do dataset **conforme o usuário ou grupo**, de modo que **cada pessoa vê apenas as linhas autorizadas**.

### RLS por regras de dataset (tabela de permissões)

Cria-se um **dataset de regras** (CSV, tabela) com **uma coluna de usuário/grupo** e **colunas de filtro**:

| UserName / GroupName | regiao | pais |
|---|---|---|
| `ana@empresa.com` | Sul | Brasil |
| `bruno@empresa.com` | Norte | Brasil |
| `grupo:Diretoria` | *(vazio = todas)* | *(vazio)* |

```
 Dataset "vendas" + Regras RLS  ─►  Ana vê só linhas com regiao='Sul' e pais='Brasil'
                                    Diretoria vê tudo (valores vazios/coringa)
```

| Regra | Efeito |
|---|---|
| **Colunas de filtro coincidentes** | O QuickSight **junta** o dataset às regras por essas colunas |
| **Vários valores** | Separados por vírgula ou várias linhas |
| **Valor vazio/coringa** | Acesso a **todos** os valores daquela coluna |
| **Usuário sem regra** | **Não vê nenhum dado** (comportamento "negar por padrão", configurável) |
| **Regras em SPICE** | O dataset de regras pode ser SPICE; atualize-o quando a organização mudar |

### RLS com tags (embedding)

Em **embedding**, as **tags** de sessão (**RLS com tags**) passam o **contexto do usuário** na URL: `regiao=Sul`, `cliente_id=123`. O dataset define **qual coluna** recebe qual tag, sem manter tabelas de usuários.

```json
{
  "SessionTags": [{"Key": "cliente_id", "Value": "123"}],
  "...": "o dataset tem regra: coluna cliente_id = tag cliente_id"
}
```

### Segurança em nível de coluna (CLS)

O **CLS (Column-Level Security)** **oculta colunas sensíveis** (salário, CPF) para certos usuários/grupos.

| Aspecto | Detalhe |
|---|---|
| **Configuração** | No dataset: **Column-level security** → colunas e **usuários/grupos permitidos** |
| **Efeito** | Quem não tem permissão **não vê** nem **consegue usar** a coluna (visuais com ela **dão erro**) |
| **Combinação** | RLS + CLS para **proteção completa** |

| Controle | Protege | Granularidade |
|---|---|---|
| **RLS** | **Quais linhas** o usuário vê | Por usuário/grupo/tags |
| **CLS** | **Quais colunas** o usuário vê | Por usuário/grupo |
| **Permissões de dashboard/dataset** | **Se** o usuário acessa o ativo | Por usuário/grupo |
| **Lake Formation (Athena)** | Linhas/colunas **na fonte** | Por principal |

> [!warning] RLS é aplicada no dataset, não no dashboard
> Qualquer **visual criado sobre o dataset** herda o RLS. Mas se o **mesmo dado** for exposto por **outro dataset sem RLS**, a proteção **não vale**. Padronize **datasets certificados com RLS** como a **única** porta de acesso a dados sensíveis.

## Rede privada e VPC

| Cenário | Solução |
|---|---|
| **Fonte privada (RDS, Redshift, on-premises)** | **VPC connection**: o QuickSight cria **ENIs** nas suas subnets, com **security groups** controlados por você |
| **Acesso privado ao próprio QuickSight** | **VPC endpoints (PrivateLink)** para a API/UI do QuickSight |
| **Restrição por IP** | **Lista de IPs permitidos** (*IP restrictions*) para console e embedding |
| **Domínios permitidos para embedding** | **Allowed domains** (CORS/iframe) |
| **Fontes via Direct Connect/VPN** | Combinar VPC connection com a conectividade híbrida |

```
 QuickSight ──(ENI na sua VPC, security group)──► RDS / Redshift privados / on-premises (via VPN/DX)
```

> [!tip] Menor privilégio de rede
> O **security group** da VPC connection deve **permitir saída somente** para as portas e destinos necessários (por exemplo, 5439 para Redshift). O banco, por sua vez, só deve aceitar **conexões desse security group**.

## Criptografia e proteção de dados

| Camada | Proteção |
|---|---|
| **Em trânsito** | **TLS** entre usuários, QuickSight e fontes |
| **SPICE em repouso** | Criptografado; **chave gerenciada pela AWS** ou **KMS com chave do cliente** (Enterprise) |
| **Credenciais de fontes** | Armazenadas criptografadas |
| **Exportações e e-mails** | Controle por **papéis restritos** (impedir download/e-mail de dados) |
| **Retenção** | Dados em SPICE são **excluídos** ao apagar o dataset |
| **Residência de dados** | SPICE fica na **região** escolhida |
| **Fontes com KMS** | A role do QuickSight precisa de permissões na chave (Athena/S3) |

```bash
# Impõe restrições de funcionalidades por grupo (custom permissions): exemplo conceitual
aws quicksight create-role-custom-permission --aws-account-id 123456789012 \
  --namespace default --role READER --custom-permissions-name sem-download
```

## Auditoria e monitoramento

| Fonte | O que registra |
|---|---|
| **CloudTrail** | Chamadas de **API** (criar/compartilhar dashboards, mudanças de permissões, ingestões) |
| **Logs de acesso a dashboards** (`GetDashboardEmbedUrl`, eventos de visualização via CloudTrail e APIs de *usage*) | Quem visualizou |
| **CloudWatch Metrics** (`AWS/QuickSight`) | Ingestões (sucesso/falha), tempo, linhas, **sessões** |
| **Lake Formation / Athena logs** | Acessos na fonte |
| **EventBridge** | Eventos de ingestão e mudanças para automação/alertas |
| **Relatórios de uso** | Admin console: usuários ativos, dashboards mais vistos, **SPICE** |

```json
{
  "source": ["aws.quicksight"],
  "detail-type": ["AWS API Call via CloudTrail"],
  "detail": {"eventName": ["UpdateDashboardPermissions","UpdateDataSetPermissions","DeleteUser","RegisterUser"]}
}
```

> [!tip] Alarme em mudanças de permissão
> Alerte para **alterações de permissões** de dashboards e datasets sensíveis e **criação de novos admins**. São os eventos de maior risco para vazamento de dados.

## Embedding: levando o BI para dentro de aplicações

O **embedding** permite **incorporar dashboards, análises, o console de autoria e o Q** em **aplicações, portais e produtos SaaS**, com a **identidade e as permissões do seu sistema**.

| Tipo | Quem acessa | Cobrança | Uso |
|---|---|---|---|
| **Embedding para usuários registrados** | **Usuários do QuickSight** (ou federados com Identity Center/IAM) | Por **usuário/papel** | Equipes internas, parceiros cadastrados |
| **Embedding para usuários anônimos (não registrados)** | **Qualquer pessoa** autenticada **no seu app** (sem conta QuickSight) | **Por sessão** (capacidade de sessões) | **Clientes finais de SaaS**, sites públicos |
| **Console embedding** | Autores | Por usuário | Autoatendimento de BI dentro do produto |
| **Embedding do Q / de visuais únicos** | Conforme tipo | Conforme tipo | Perguntas e visuais isolados |

```
 Navegador do usuário ──► Seu APLICATIVO (autentica o usuário)
                               │ backend chama a API do QuickSight
                               ▼
              GenerateEmbedUrlForAnonymousUser / GenerateEmbedUrlForRegisteredUser
                               │ (devolve URL assinada e temporária)
                               ▼
        <iframe> / SDK JavaScript embute o dashboard na página
```

```bash
# URL de embedding para usuário anônimo (sessão), com RLS por tag
aws quicksight generate-embed-url-for-anonymous-user \
  --aws-account-id 123456789012 --namespace default \
  --authorized-resource-arns arn:aws:quicksight:us-east-1:123456789012:dashboard/vendas \
  --experience-configuration 'Dashboard={InitialDashboardId=vendas}' \
  --session-tags Key=cliente_id,Value=123 \
  --session-lifetime-in-minutes 60 \
  --allowed-domains https://app.empresa.com
```

```javascript
// SDK JavaScript do QuickSight (esqueleto)
import { createEmbeddingContext } from 'amazon-quicksight-embedding-sdk';
const ctx = await createEmbeddingContext();
const frame = await ctx.embedDashboard({
  url: embedUrl, container: '#dash', height: '700px', width: '100%',
  parameters: [{ Name: 'p_regiao', Values: ['Sul'] }],
});
```

| Boa prática de embedding | Motivo |
|---|---|
| **Gerar a URL no backend**, após autenticar o usuário | Nunca expor credenciais no navegador |
| **Sessões curtas** (ex.: 15–60 min) | Menos risco se a URL vazar |
| **Domínios permitidos** (*allowed domains*) | Impede uso em sites não autorizados |
| **RLS por tags de sessão** | **Isolamento de clientes** sem criar usuários |
| **Role IAM mínima** para a geração de URLs | Só os dashboards necessários (`quicksight:GenerateEmbedUrl*` em ARNs específicos) |
| **Customizar interface** (ocultar menus, tema) | Experiência nativa |
| **Controlar parâmetros** pelo SDK | Navegação contextual |
| **Capacidade de sessões** dimensionada | Evita bloqueio por limite |
| **Testes de isolamento** | Garantir que um cliente não vê dados de outro |

> [!warning] Embedding sem RLS expõe todos os clientes a todos
> Em SaaS multi-cliente, **sem RLS por tag** (ou namespaces), **todos veem tudo** o que o dataset contém. Teste **explicitamente** o isolamento: autentique como cliente A e verifique que dados do cliente B **não aparecem**.

### Multi-inquilino: RLS por tag vs namespaces

| Critério | **RLS com tags (anônimo)** | **Namespaces** |
|---|---|---|
| **Isolamento** | **Dados** (linhas) por tag | **Usuários, ativos e permissões** isolados |
| **Escala de clientes** | **Milhares/milhões** (sem usuários) | Dezenas/centenas (limite de namespaces) |
| **Autoria por cliente** | Não | Sim (cada inquilino cria seu conteúdo) |
| **Custo** | Por sessão | Por usuário |
| **Ideal para** | **Dashboards padronizados** para muitos clientes | Clientes que precisam de **autoria própria** |

## Exemplo prático: SaaS com dashboards para clientes

1. Uma plataforma de logística quer oferecer **painéis de entregas** aos seus **500 clientes**.
2. Cria **um dataset único** `entregas` (SPICE) com coluna `cliente_id` e **RLS com tags**: `cliente_id` = tag de sessão `cliente_id`.
3. O backend, após autenticar o cliente, chama **`GenerateEmbedUrlForAnonymousUser`** com a tag, **sessão de 60 min** e **domínio permitido**.
4. O dashboard é **incorporado no portal** com **tema** da marca e **parâmetros** pré-selecionados.
5. A role de geração de URL tem **acesso apenas** àquele dashboard.
6. **Testes de isolamento** automatizados verificam que um cliente não acessa dados de outro.
7. O custo é por **sessão** (com capacidade contratada); **alarmes** de CloudTrail avisam sobre mudanças de permissão.

## Troubleshooting

| Sintoma | Causa provável | Como resolver |
|---|---|---|
| Usuário **não vê dados** | RLS sem regra para ele | Adicionar regras; revisar "negar por padrão" |
| Usuário vê **dados demais** | Sem RLS ou regra com coringa | Rever o dataset de regras |
| Visual dá **erro de coluna** | CLS bloqueando a coluna | Ajustar CLS ou remover a coluna do visual |
| **Login SSO falha** | Mapeamento de grupos/roles, metadados SAML | Revisar IAM Identity Center/federação |
| Usuário sem papel adequado | Papel Reader sem permissão no ativo | Compartilhar o dashboard/pasta |
| **Embedding retorna 401/403** | URL expirada, domínio não permitido, role sem permissão | Gerar nova URL; configurar `allowed domains` e IAM |
| Dashboard embutido **não carrega** | Bloqueio de iframe/CSP, cookies de terceiros | Ajustar CSP e domínios; usar SDK |
| **VPC connection falha** | Subnets/SG/rotas | Verificar conectividade e portas |
| Cliente A vê dados de B | RLS por tag ausente/errada | Corrigir regra de RLS; testar isolamento |
| **Limite de namespaces/sessões** | Quotas atingidas | Pedir aumento; rever o modelo |
| SPICE sem acesso a KMS | Política da chave | Permitir a role do QuickSight |
| Mudança de permissão não detectada | Sem alarme | EventBridge/CloudTrail para eventos críticos |

## Erros comuns e armadilhas

- **Compartilhar com usuários individuais** em vez de grupos.
- **RLS sem testes**, deixando regras incorretas.
- **Datasets sensíveis sem RLS/CLS** compartilhados com autores.
- **Autenticar por senha local** em vez de SSO/MFA.
- **Gerar URLs de embedding no navegador** ou com sessões longas.
- **Embedding multi-cliente sem teste de isolamento.**
- **Sem alarmes** sobre mudanças de permissão e admins.
- **Esquecer a revisão periódica de acessos.**

## 🧩 Quiz de Fixação

1. Qual a diferença entre RLS e CLS?
2. Para que servem os namespaces?
3. Qual o método de autenticação recomendado para organizações?
4. Como funciona o embedding para usuários anônimos?
5. Por que gerar a URL de embedding no backend?
6. Quando preferir RLS com tags a namespaces?

**Respostas:**
1) RLS filtra linhas que o usuário pode ver; CLS oculta colunas sensíveis para certos usuários ou grupos.
2) Isolar completamente conjuntos de usuários, ativos e permissões na mesma conta (multi-inquilino).
3) IAM Identity Center ou federação SAML com o IdP corporativo, com MFA no IdP.
4) O backend autentica o usuário no próprio aplicativo e gera uma URL assinada e temporária por sessão (sem conta QuickSight), com RLS por tags; cobra-se por sessão.
5) Para não expor credenciais, autenticar o usuário antes e limitar o escopo e a duração da URL.
6) Quando há muitos clientes consumindo dashboards padronizados e não precisam de autoria própria, pois a escala é maior e o custo é por sessão.
