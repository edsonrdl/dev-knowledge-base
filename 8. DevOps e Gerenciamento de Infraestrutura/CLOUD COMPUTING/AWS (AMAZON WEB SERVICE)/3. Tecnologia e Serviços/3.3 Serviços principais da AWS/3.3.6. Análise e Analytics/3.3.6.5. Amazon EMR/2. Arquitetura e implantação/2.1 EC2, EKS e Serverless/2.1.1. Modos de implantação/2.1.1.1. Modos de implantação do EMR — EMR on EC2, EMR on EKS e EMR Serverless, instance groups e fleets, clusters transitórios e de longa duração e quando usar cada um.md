### 2.1.1.1. Modos de implantação do EMR — EMR on EC2, EMR on EKS e EMR Serverless, instance groups e fleets, clusters transitórios e de longa duração e quando usar cada um

> [!warning] Aviso
> Recursos de cada modo (HA de primary, capacidade pré-inicializada, limites de workers, suporte a frameworks em Serverless e EKS) e preços abaixo são **de memória e mudam**. **Confirme na documentação do Amazon EMR.** Comandos e JSONs são ilustrativos e **não foram executados**. IDs, ARNs e nomes são fictícios.

## 1. Por que existem três modos

O EMR nasceu como **clusters de EC2**. Com a evolução da nuvem, equipes pediram **menos administração** (serverless) e **integração com Kubernetes** (frota única de containers). Hoje há **três modos**, com **trade-offs** entre **controle**, **simplicidade** e **custo**:

```
Controle total   ◀─────────────────────────────────────────────▶   Menos administração
EMR on EC2                  EMR on EKS                         EMR Serverless
(clusters que você           (jobs em pods Spark no seu           (sem clusters: submeter job,
 configura)                   cluster Kubernetes)                  a AWS provisiona)
```

## 2. EMR on EC2

### 2.1 Como funciona

Você cria um **cluster** de instâncias EC2 com **release label**, **aplicações**, **tipos de instância**, **rede** e **segurança**. O EMR **instala** e **configura** os frameworks e mantém o cluster.

| Aspecto | Detalhe |
|---|---|
| **Controle** | **Máximo**: tipo/família de instância, discos, AMI customizada, bootstrap, configurações de cada framework |
| **Frameworks** | **Todos** (Spark, Hive, Presto/Trino, HBase, Flink, Hue…) |
| **Cluster** | **Transitório** (por job) ou **persistente** (compartilhado) |
| **Rede** | Em **sua VPC/subnet** (security groups) |
| **Escala** | **Managed scaling** / auto scaling / manual |
| **Custo** | **EC2 + sobretaxa EMR por instância-segundo**; Spot e Graviton reduzem |
| **Administração** | Média: escolher instâncias, scaling, patches de AMI (custom), troubleshooting |

### 2.2 Instance groups vs instance fleets

| | **Instance groups** | **Instance fleets** |
|---|---|---|
| **Estrutura** | Cada grupo (primary/core/task) usa **um tipo de instância** e **um modelo de compra** | Cada **fleet** pode ter **até ~5 tipos** de instância e **mistura On-Demand/Spot** |
| **AZ** | **Uma subnet/AZ** | **Várias subnets/AZs** (diversificação) |
| **Spot** | Menos resiliente (um tipo/pool) | **Mais resiliente** (vários pools; “allocation strategy” como `capacity-optimized`) |
| **Dimensionamento** | Em **instâncias** | Em **unidades de capacidade alvo** (vCPU/memória ponderados) |
| **Managed scaling** | Suportado | Suportado |
| **Complexidade** | **Simples** | Mais flexível |
| **Quando** | Cargas previsíveis/simples | **Spot em escala**, capacidade variável |

```bash
# Instance fleet com Spot e vários tipos (ilustrativo)
aws emr create-cluster --name "etl-fleet" --release-label emr-7.2.0 \
  --applications Name=Spark --use-default-roles \
  --instance-fleets \
   'InstanceFleetType=MASTER,TargetOnDemandCapacity=1,InstanceTypeConfigs=[{InstanceType=m6g.xlarge}]' \
   'InstanceFleetType=CORE,TargetOnDemandCapacity=2,InstanceTypeConfigs=[{InstanceType=r6g.2xlarge}]' \
   'InstanceFleetType=TASK,TargetSpotCapacity=20,InstanceTypeConfigs=[{InstanceType=r6g.2xlarge,WeightedCapacity=1},{InstanceType=r6gd.2xlarge,WeightedCapacity=1},{InstanceType=r5.2xlarge,WeightedCapacity=1}],LaunchSpecifications={SpotSpecification={TimeoutDurationMinutes=10,TimeoutAction=SWITCH_TO_ON_DEMAND,AllocationStrategy=capacity-optimized}}' \
  --log-uri s3://logs-emr-123456789012/
```

### 2.3 Cluster transitório vs persistente

| | **Transitório (job-scoped)** | **Persistente (long-running)** |
|---|---|---|
| **Ciclo** | Cria → executa steps → **termina** | **Fica ligado**; recebe jobs ao longo do tempo |
| **Custo** | **Paga só o uso** | Paga 24×7 (mitigar com **scaling** e **auto-terminação por ociosidade**) |
| **Isolamento** | **Alto** (um cluster por job: configs sob medida) | Compartilhado (disputa de recursos) |
| **Dados** | No **S3** | No **S3** (HDFS só temporário) |
| **Melhor para** | **ETL agendado**, jobs previsíveis | **Análise interativa** (notebooks, Trino, Hive), muitos usuários |
| **Armadilha** | Tempo de **startup** (minutos) | **Ociosidade** e deriva de configuração |

> [!tip] Padrão moderno
> **Cluster transitório por pipeline** (orquestrado por **Step Functions/Airflow (MWAA)/Glue workflows**) + **dados no S3** + **catálogo no Glue Data Catalog**. Para interativo, um cluster **persistente com managed scaling** e **auto-terminação por ociosidade**.

### 2.4 Alta disponibilidade do primary

- Em EC2 é possível **três nós primary** para HA (alguns frameworks: YARN, HDFS NameNode, Hive Metastore; confirmar por release); sem HA, o primary é **ponto único de falha**.
- **Cluster com um primary**: se cair, o cluster é perdido; os **dados no S3** estão seguros, mas o trabalho em andamento se perde — **steps devem ser idempotentes**.

### 2.5 Steps, bootstrap e configuração

| Mecanismo | Uso |
|---|---|
| **Steps** | Submeter jobs (`spark-submit`, scripts, `hive`); definir `ActionOnFailure` (`CONTINUE`, `CANCEL_AND_WAIT`, `TERMINATE_CLUSTER`) |
| **Bootstrap actions** | Instalar libs, configurar SO **antes** das aplicações iniciarem |
| **Configurations (JSON)** | Ajustar `spark-defaults`, `yarn-site`, `hive-site`, `core-site`… |
| **Custom AMI** | Imagem com libs/hardening pré-instalados (reduz startup) |
| **Tags** | Alocação de custo e governança |

```json
[
  { "Classification": "spark-defaults",
    "Properties": { "spark.sql.adaptive.enabled": "true", "spark.dynamicAllocation.enabled": "true" } },
  { "Classification": "spark-hive-site",
    "Properties": { "hive.metastore.client.factory.class": "com.amazonaws.glue.catalog.metastore.AWSGlueDataCatalogHiveClientFactory" } }
]
```

## 3. EMR on EKS

### 3.1 Como funciona

Em vez de criar clusters EMR, você **registra um namespace de um cluster EKS** como **“virtual cluster”** do EMR e **submete job runs** (Spark). O EMR **cria pods** Spark (driver e executors) no seu cluster Kubernetes.

```
EKS (já existente, com outras cargas)
  └── namespace "spark-jobs"  ◀── Virtual cluster do EMR
         └── Job run → pods: driver + executors (imagens EMR runtime)
                           └── dados no S3 / Glue Catalog / Lake Formation
```

| Aspecto | Detalhe (de memória — confirmar) |
|---|---|
| **Frameworks** | **Spark** (principal); suporte a **outros** é limitado |
| **Infra** | **Reaproveita** o EKS (EC2/Fargate) — **frota única** para apps e analytics |
| **Isolamento** | **Namespaces**, RBAC, **IRSA** (roles por job) |
| **Imagens** | **EMR runtime** (otimizado) ou **customizadas** (ECR) |
| **Pod templates** | Customizar driver/executor (node selectors, tolerations, volumes) |
| **Escala** | **Cluster Autoscaler/Karpenter** do EKS |
| **Custo** | **Compute do EKS** + **sobretaxa EMR** por vCPU/GB (confirmar) |
| **Logs/Monitoração** | **CloudWatch/S3**, **Spark History Server** gerenciado |
| **Quando** | Empresa **já padronizada em Kubernetes**; **multi-tenancy**; consolidar clusters |

### 3.2 Quando não usar

- Time **sem experiência** em Kubernetes (curva de aprendizado).
- Precisa de **Hive/HBase/Trino/Flink completos** (melhor em EC2).
- Preferência por **zero administração** → **Serverless**.

### 3.3 Exemplo (ilustrativo)

```bash
aws emr-containers create-virtual-cluster --name vc-spark \
  --container-provider '{"id":"eks-analytics","type":"EKS","info":{"eksInfo":{"namespace":"spark-jobs"}}}'

aws emr-containers start-job-run --virtual-cluster-id vc123 --name etl-pods \
  --execution-role-arn arn:aws:iam::123456789012:role/EmrEksJobRole --release-label emr-7.2.0-latest \
  --job-driver '{"sparkSubmitJobDriver":{"entryPoint":"s3://codigo/etl.py","sparkSubmitParameters":"--conf spark.executor.instances=10 --conf spark.executor.memory=8G"}}'
```

## 4. EMR Serverless

### 4.1 Como funciona

Você cria uma **application** (Spark ou Hive) e **submete job runs**. A AWS **provisiona e escala automaticamente os workers**, **sem** clusters, instâncias ou Kubernetes para gerenciar.

| Aspecto | Detalhe (de memória — confirmar) |
|---|---|
| **Frameworks** | **Apache Spark** e **Apache Hive** |
| **Modelo** | **Application** (runtime/versão) + **job runs** (execuções) |
| **Capacidade** | **Workers** (driver/executors) alocados **sob demanda** conforme o job; limites de **máximo** por application |
| **Pre-initialized capacity** | **Workers pré-aquecidos** para **latência baixa** de início (paga enquanto mantidos) |
| **Escala** | **Automática** durante o job (alocação dinâmica) |
| **Rede** | **VPC opcional** (para acessar recursos privados) |
| **Custo** | **vCPU-hora + GB-hora + storage** apenas **durante** o job (e capacidade pré-inicializada) |
| **Administração** | **Mínima**: sem escolher instâncias nem dimensionar cluster |
| **Segurança** | **Execution role** por job, **Lake Formation**, criptografia |
| **Quando** | **ETL/batch** com carga **variável/esporádica**, times sem apetite para administrar |

### 4.2 Pre-initialized capacity

```
Sem pré-inicialização:  submit ─▶ [provisiona workers ~segundos-minutos] ─▶ roda ─▶ libera
Com pré-inicialização:  workers já prontos ─▶ submit ─▶ roda quase imediato (paga o pool ocioso)
```

Use para **jobs frequentes e sensíveis à latência**; evite deixar capacidade ociosa **sem necessidade**.

### 4.3 Exemplo (ilustrativo)

```bash
aws emr-serverless create-application --name app-spark --type SPARK --release-label emr-7.2.0 \
  --maximum-capacity '{"cpu":"400 vCPU","memory":"3000 GB","disk":"20000 GB"}' \
  --auto-stop-configuration '{"enabled":true,"idleTimeoutMinutes":15}'

aws emr-serverless start-job-run --application-id 00abc --name etl-serverless \
  --execution-role-arn arn:aws:iam::123456789012:role/EmrServerlessJobRole \
  --job-driver '{"sparkSubmit":{"entryPoint":"s3://codigo/etl.py","sparkSubmitParameters":"--conf spark.executor.cores=4 --conf spark.executor.memory=16g --conf spark.executor.instances=10"}}'
```

### 4.4 Limitações

- **Menos controle** (sem acesso SSH, sem AMI customizada, sem HDFS persistente).
- **Frameworks limitados** (Spark/Hive).
- **Imagens customizadas** possíveis (confirmar), mas **sem bootstrap actions** como no EC2.
- **Jobs muito longos e estáveis** podem ficar **mais baratos** em EC2 com Spot/Reserved/Savings Plans.

## 5. Comparação dos três modos

| Critério | **EMR on EC2** | **EMR on EKS** | **EMR Serverless** |
|---|---|---|---|
| **Gerenciar infra** | Instâncias/clusters | **Cluster Kubernetes (EKS)** | **Nada** |
| **Frameworks** | **Todos** | Spark (principal) | Spark, Hive |
| **Controle** | **Máximo** | Alto (pods/imagens) | Baixo |
| **Startup** | Minutos | Segundos–minutos (depende do EKS) | Segundos (pre-init: quase imediato) |
| **Escala** | Managed scaling/Spot | Karpenter/Cluster Autoscaler | **Automática** |
| **Custo** | EC2 + sobretaxa; **Spot/RI/SP** | EKS compute + sobretaxa | vCPU-h/GB-h **só enquanto roda** |
| **Multi-tenancy** | Por cluster | **Namespaces** | Por application |
| **Interatividade** | Notebooks/Hue/Trino persistente | Via EMR Studio/EKS | EMR Studio |
| **Melhor para** | **Cargas pesadas/customizadas**, Hive/HBase/Trino/Flink, custo otimizado em escala | **Plataformas Kubernetes**, consolidação | **ETL variável, simplicidade** |

### 5.1 Árvore de decisão

```
Precisa de Hive/HBase/Trino/Flink completos, SSH, AMI custom, controle fino?  ── sim ─▶ EMR on EC2
 └ não
Empresa padronizada em Kubernetes, quer consolidar frota e multi-tenancy?     ── sim ─▶ EMR on EKS
 └ não
Quer zero administração, jobs Spark/Hive com demanda variável?                ── sim ─▶ EMR Serverless
 └ Jobs gigantes e constantes 24×7 com Spot/RI?                               ──────▶ EMR on EC2 (custo)
```

## 6. Orquestração de pipelines

| Ferramenta | Papel |
|---|---|
| **AWS Step Functions** | Integração nativa para **criar cluster, adicionar steps, terminar** (`.sync`) |
| **Amazon MWAA (Airflow)** | Operadores EMR (EC2/EKS/Serverless) |
| **AWS Glue Workflows** | Mais simples, integrado ao Glue |
| **EventBridge Scheduler** | Disparar execuções por agenda |
| **CI/CD** | Versionar **código dos jobs** e **configurações** |

Padrão: **evento/agenda → Step Functions → cria cluster transitório (ou submete job Serverless) → steps → valida → termina → notifica**.

## 7. Erros comuns

- **Cluster persistente** para **ETL diário** (pagando ociosidade).
- **Instance groups com Spot de um só tipo** (interrupções frequentes) em vez de **fleets diversificadas**.
- **Escolher EKS** sem a equipe de Kubernetes.
- **Serverless para jobs 24×7 enormes** (pode sair mais caro).
- **Pre-initialized capacity** ligada sem uso.
- **Primary único** em cluster persistente crítico (sem HA).
- **Steps não idempotentes**: reexecuções duplicam dados.
- **Esquecer auto-terminação** (cluster esquecido ligado).
- **Misturar** ambientes dev/prod no mesmo cluster.
- **Sem versionar** as configurações (drift).

## 8. Troubleshooting

| Sintoma | Causa provável | Ação |
|---|---|---|
| Cluster `TERMINATED_WITH_ERRORS` na criação | Roles, subnet, capacidade, bootstrap | Ver `StateChangeReason`, logs de bootstrap |
| Spot interrompido, jobs falham | Task em um único pool | Instance fleet diversificada; `capacity-optimized`; core On-Demand |
| Job Serverless fica `PENDING` | Limite máximo de capacidade; sem workers | Ajustar `maximumCapacity`; pre-init |
| Pods Spark `Pending` no EKS | Sem nós; limites; taints | Escalar o EKS; ajustar pod templates |
| Custo Serverless alto | Jobs ineficientes; muitos executors | Otimizar o job; limitar capacidade |
| Cluster esquecido ligado | Sem auto-terminate/idle timeout | Configurar `AutoTerminationPolicy` |
| Notebook sem acesso | Rede/segurança do EMR Studio | Ver VPC/SG/roles |

## 9. Resumo rápido

- **EMR on EC2**: **máximo controle** e **todos os frameworks**; **instance groups** (simples) vs **fleets** (multi-tipo/multi-AZ, **Spot** robusto); **transitório** (por job) vs **persistente**.
- **EMR on EKS**: Spark em **pods** do seu **Kubernetes**; **virtual cluster** por namespace; reaproveita a frota; **IRSA/pod templates**.
- **EMR Serverless**: **applications + job runs**, **sem clusters**; **pre-initialized capacity**; paga **vCPU/GB-hora** durante o job.
- Escolha: **customização/Hive/HBase/Trino** → EC2; **padrão Kubernetes** → EKS; **simplicidade/carga variável** → Serverless.
- Orquestre com **Step Functions/MWAA**; **dados no S3**; **steps idempotentes**; **auto-terminação**.

## 🧩 Quiz de Fixação

1. Qual a vantagem das instance fleets sobre instance groups?
2. Quando preferir cluster transitório em vez de persistente?
3. O que é um virtual cluster no EMR on EKS?
4. Para que serve a pre-initialized capacity no EMR Serverless?
5. Quais frameworks o EMR Serverless suporta?
6. Em que cenário o EMR on EC2 pode ser mais barato que Serverless?
7. Que ferramenta nativa orquestra clusters EMR transitórios?

**Respostas:**

1. Permitem vários tipos de instância e AZs, misturando On-Demand e Spot com estratégias de alocação, o que aumenta a resiliência e reduz interrupções.
2. Para ETL agendado e previsível, pagando só durante o job, com isolamento e configurações sob medida.
3. O registro de um namespace do cluster EKS no EMR, onde os job runs criam pods Spark.
4. Manter workers pré-aquecidos para reduzir a latência de início dos jobs, ao custo de pagar o pool ocioso.
5. Apache Spark e Apache Hive.
6. Em jobs muito grandes e constantes, aproveitando Spot, Reserved Instances ou Savings Plans.
7. AWS Step Functions (com integração `.sync`), além do MWAA/Airflow como alternativa.
