### 1.1.1.1. O que é Amazon EMR — big data gerenciado com Hadoop e Spark, clusters, nós primary, core e task, frameworks suportados e quando usar EMR em vez de Glue, Athena e Redshift

> [!warning] Aviso
> Versões de frameworks, rótulos de release, limites, preços e a lista de aplicações suportadas abaixo são **de memória e mudam a cada release do EMR**. **Confirme na documentação do Amazon EMR (Release Guide) e na página de preços.** Comandos e JSONs são ilustrativos e **não foram executados**. Nomes de buckets, clusters e contas são fictícios.

## 1. O problema que o EMR resolve

Análise de **grandes volumes de dados** (terabytes a petabytes) costuma exigir **processamento distribuído**: dividir o trabalho entre dezenas ou centenas de máquinas. O ecossistema **Hadoop/Spark** nasceu para isso, mas **operar** esses clusters é trabalhoso:

| Dor | Detalhe |
|---|---|
| **Instalação e configuração** | Hadoop, YARN, Spark, Hive, Zookeeper… versões compatíveis entre si |
| **Provisionar e dimensionar hardware** | Comprar/alugar servidores para picos que acontecem duas vezes por mês |
| **Atualizações e patches** | Segurança do SO e dos frameworks |
| **Falhas de nós** | Substituir máquinas, rebalancear dados |
| **Custo ocioso** | Cluster ligado 24×7 para jobs de poucas horas |
| **Integração** | Conectar ao data lake, catálogo, segurança, monitoramento |

O **Amazon EMR (Elastic MapReduce)** é a plataforma **gerenciada** da AWS para **executar frameworks de big data** (Apache **Spark**, **Hadoop**, **Hive**, **Presto/Trino**, **HBase**, **Flink**, **Hudi**, **Iceberg**, entre outros) **na nuvem**: a AWS **provisiona e configura** clusters em minutos, integra com **S3**, **Glue Data Catalog**, **IAM** e **Lake Formation**, e você **paga pelo que usa**.

> [!info] Em uma frase
> **EMR = “clusters (ou serviço serverless) de Spark/Hadoop prontos em minutos, com dados no S3 e pagamento por uso”.**

## 2. Conceitos fundamentais

| Termo | Significado |
|---|---|
| **Cluster** | Conjunto de instâncias EC2 que executa os frameworks (EMR on EC2) |
| **Nó primary (master)** | Coordena o cluster: roda o **ResourceManager (YARN)**, **NameNode (HDFS)**, expõe UIs e distribui tarefas |
| **Nós core** | Executam tarefas **e armazenam dados no HDFS** |
| **Nós task** | Executam **apenas** tarefas (**sem HDFS**); ideais para **Spot** e escala elástica |
| **HDFS** | Sistema de arquivos distribuído **efêmero** do cluster (some quando o cluster termina) |
| **EMRFS** | Camada que permite ao Hadoop/Spark ler e escrever **diretamente no S3** (`s3://`) |
| **YARN** | Gerenciador de recursos do Hadoop (aloca CPU/memória para aplicações) |
| **Step** | Unidade de trabalho submetida ao cluster (job Spark, script Hive…) |
| **Bootstrap action** | Script executado **na inicialização** de cada nó (instalar libs/configurar) |
| **Release label** | Versão do EMR (`emr-7.x.x`) que define as **versões dos frameworks** incluídos |
| **Application** | Framework/ferramenta instalada (Spark, Hive, Hue, Livy, JupyterHub…) |
| **EMR Studio** | IDE web com notebooks para desenvolver/executar jobs |
| **Instance group / fleet** | Formas de definir os tipos e a compra (On-Demand/Spot) das instâncias |
| **Cluster transitório vs persistente** | Termina após os steps vs permanece ligado |

### 2.1 Arquitetura de um cluster EMR on EC2

```
                    ┌───────────────── VPC / subnet(s) ──────────────────┐
  Usuário/Step ───▶ │  NÓ PRIMARY  (YARN RM, NameNode, UIs, Livy)         │
                    │        │  distribui trabalho                        │
                    │   ┌────┴─────────────┬──────────────────┐          │
                    │   ▼                  ▼                  ▼          │
                    │ NÓS CORE (HDFS+tasks)  NÓS TASK (só tasks, Spot)    │
                    └───────────┬────────────────────────────────────────┘
                                ▼
                 Amazon S3 (dados de entrada/saída — EMRFS)   Glue Data Catalog (metastore)
```

### 2.2 Papéis dos nós

| Nó | Função | Falha |
|---|---|---|
| **Primary** | Coordenação; **ponto único de falha** em cluster simples | Perda = cluster perdido (use **3 primaries** para HA em alguns cenários; confirmar) |
| **Core** | Computação + **dados HDFS** | Perda de core pode **perder blocos** (replicação do HDFS mitiga) |
| **Task** | Computação **pura** | Perda **não** afeta dados; tarefas são reexecutadas |

> [!tip] Regra de ouro de custo
> **Dados duráveis no S3**, **HDFS só para temporários**, **core mínimo On-Demand** e **task em Spot** para absorver o grosso da computação.

## 4. Três formas de usar o EMR (visão geral)

| Modo | Descrição |
|---|---|
| **EMR on EC2** | **Clusters** em instâncias EC2 que **você escolhe** (mais controle) |
| **EMR on EKS** | Executa jobs **Spark em clusters Kubernetes (EKS)** já existentes |
| **EMR Serverless** | **Sem clusters para gerenciar**: você submete jobs e a AWS provisiona a capacidade |

A folha seguinte aprofunda os três.

## 5. Quando usar EMR (e quando usar outro serviço)

| Cenário | Melhor escolha |
|---|---|
| ETL em **Spark** que exige **controle fino**, bibliotecas customizadas, versões específicas | **EMR** |
| Migrar **cargas Hadoop/Spark/Hive on-premises** com mínima reescrita | **EMR** |
| ETL **serverless** gerenciado, catálogo e crawlers, pouca administração | **AWS Glue** |
| **SQL ad hoc** sobre dados no S3, sem infraestrutura | **Amazon Athena** |
| **Data warehouse** com SQL, BI e alta concorrência | **Amazon Redshift** |
| **Streaming** com baixa latência e SQL | **Kinesis/Flink (Managed Service for Apache Flink)** ou EMR com Flink |
| **ML em escala** com Spark | EMR (ou SageMaker) |
| Jobs **batch simples** sem Hadoop | **AWS Batch** |
| Pesquisa/log analytics com **busca** | **OpenSearch Service** |
| **Hudi/Iceberg** com muito controle de compactação | EMR (ou Glue) |

### 5.1 EMR vs Glue vs Athena vs Redshift

| Critério | **EMR** | **Glue (ETL)** | **Athena** | **Redshift** |
|---|---|---|---|---|
| Modelo | Clusters/serverless de Spark/Hadoop | ETL Spark **serverless** | SQL **serverless** (Trino) | **Data warehouse** colunar |
| Controle | **Máximo** (tipo de instância, configs, versão) | Médio (workers DPU) | Baixo | Médio |
| Frameworks | **Muitos** (Spark, Hive, Trino, Flink, HBase) | Spark/Python/Ray | SQL | SQL |
| Operação | **Maior** (EC2/EKS) ou baixa (Serverless) | **Baixa** | **Mínima** | Média |
| Custo | Instância + sobretaxa EMR (EC2) / vCPU-h (Serverless) | Por **DPU-hora** | **Por TB varrido** | Por nó/RPU |
| Melhor para | **Big data customizado**, migração Hadoop, jobs longos/pesados | ETL padrão sem gerir infra | Consultas exploratórias | BI/relatórios de alto desempenho |

Regra prática (prova SAA): **“Hadoop/Spark gerenciado”** → **EMR**; **“ETL serverless + catálogo”** → **Glue**; **“SQL direto no S3”** → **Athena**; **“DW colunar”** → **Redshift**.

## 6. Casos de uso típicos

1. **ETL em larga escala**: limpar, transformar e agregar dados brutos do S3 em Parquet particionado.
2. **Análise de logs** e dados de clickstream (Spark/Hive).
3. **Machine learning** distribuído (MLlib, feature engineering).
4. **Data lake** com Iceberg/Hudi/Delta (upserts, time travel).
5. **Genômica/pesquisa científica** com pipelines em Spark.
6. **Financeiro**: análise de risco, simulações Monte Carlo em escala.
7. **Migração Hadoop** on-premises → EMR + S3 (desacoplar compute e storage).
8. **Streaming** (Spark Streaming/Flink) em pipelines próprios.
9. **Consultas interativas** com Trino em grandes volumes.

## 7. Desacoplar compute e storage (princípio central)

```
Hadoop clássico (on-prem)          EMR moderno
┌──────────────────────┐          ┌──────────────┐       ┌──────────────┐
│ Compute + HDFS junto  │   ───▶  │ Compute (EMR) │ ◀───▶ │ Storage (S3)  │
│ escala os dois juntos │          │ efêmero/elástico│     │ durável, barato│
└──────────────────────┘          └──────────────┘       └──────────────┘
```

| Benefício | Detalhe |
|---|---|
| **Dados duráveis** | O S3 mantém os dados mesmo que o cluster seja encerrado |
| **Clusters descartáveis** | Subir só para o job e terminar (paga só o uso) |
| **Múltiplos clusters** | Vários clusters/serviços leem os **mesmos dados** |
| **Escala independente** | Aumentar compute sem pagar por disco extra |
| **Custo** | Storage no S3 é mais barato que discos de instâncias |

## 8. Primeiros passos (ilustrativo)

```bash
# Criar um cluster Spark transitório que executa um step e termina (ilustrativo)
aws emr create-cluster --name "etl-diario" --release-label emr-7.2.0 \
  --applications Name=Spark Name=Hive \
  --instance-groups \
    InstanceGroupType=MASTER,InstanceCount=1,InstanceType=m6g.xlarge \
    InstanceGroupType=CORE,InstanceCount=2,InstanceType=m6g.2xlarge \
  --use-default-roles --log-uri s3://logs-emr-123456789012/etl-diario/ \
  --steps Type=Spark,Name=job1,ActionOnFailure=TERMINATE_CLUSTER,\
Args=[--deploy-mode,cluster,s3://codigo-123456789012/jobs/etl.py,s3://dados/entrada/,s3://dados/saida/] \
  --auto-terminate

aws emr list-clusters --active
aws emr describe-cluster --cluster-id j-ABC123456789
aws emr list-steps --cluster-id j-ABC123456789
```

## 9. Erros comuns

- **Usar HDFS como armazenamento permanente**: ao terminar o cluster, os dados somem.
- **Cluster ligado 24×7** sem necessidade (custo).
- **Tudo On-Demand**: perder a oportunidade de **Spot em task nodes**.
- **Sem logs no S3** (`--log-uri`): sem diagnóstico após o término.
- **Escolher EMR quando Athena/Glue bastam** (complexidade desnecessária).
- **Misturar versões** de bibliotecas com o release do EMR (conflitos).
- **Dimensionar executors sem entender** YARN (memória/overhead).
- **Muitos arquivos pequenos** no S3 (desempenho ruim).
- **Sem particionamento/formatos colunares** (leituras caras).
- **Subnets públicas e security groups abertos** (risco).

## 10. Troubleshooting inicial

| Sintoma | Causas prováveis | Ações |
|---|---|---|
| Cluster fica em `STARTING` e falha | Capacidade da instância, subnet, role, bootstrap com erro | Ver o motivo (`StateChangeReason`); logs de bootstrap |
| Step falha | Código/dados/permissões S3 | Logs do step (stderr, controller) no S3 |
| `Container killed by YARN` | Memória insuficiente | Ajustar executors/memória/overhead |
| Cluster termina inesperadamente | Auto-terminate, falha de step com `TERMINATE_CLUSTER`, proteção desligada | Revisar as configurações |
| Lentidão | Skew de dados, arquivos pequenos, poucos executors | Particionar, compactar, ajustar paralelismo |
| `AccessDenied` no S3 | Role da instância sem permissão | Ajustar a EMR_EC2_DefaultRole/permissões |

## 11. Resumo rápido

- **EMR** = plataforma **gerenciada** de **Spark/Hadoop/Hive/Trino/Flink/HBase** etc., com **dados no S3** e clusters **elásticos e descartáveis**.
- **Cluster**: **primary** (coordena), **core** (tarefas + **HDFS**), **task** (só tarefas, bom para **Spot**).
- **HDFS efêmero**; **S3 (EMRFS)** é o armazenamento durável; **Glue Data Catalog** como metastore.
- **Três modos**: **EMR on EC2**, **EMR on EKS**, **EMR Serverless**.
- **Quando usar**: Hadoop/Spark **customizado** ou migração; **Glue** para ETL serverless; **Athena** para SQL ad hoc; **Redshift** para DW.
- Princípio: **desacoplar compute e storage**; clusters **transitórios**; **Spot** nos task nodes.

## 🧩 Quiz de Fixação

1. Qual a diferença entre nós core e task?
2. Por que não usar o HDFS como armazenamento permanente?
3. Que serviço escolher para ETL Spark serverless com catálogo e crawlers?
4. O que é EMRFS?
5. Quais são os três modos de uso do EMR?
6. Por que task nodes são bons candidatos a Spot?
7. Qual princípio de arquitetura o EMR moderno adota em relação ao Hadoop clássico?

**Respostas:**

1. Core executam tarefas e armazenam dados no HDFS; task executam apenas tarefas, sem dados HDFS.
2. Porque o HDFS é efêmero do cluster: quando o cluster termina, os dados são perdidos; o armazenamento durável deve ser o S3.
3. AWS Glue.
4. A camada que permite ao Hadoop/Spark ler e escrever diretamente no Amazon S3.
5. EMR on EC2, EMR on EKS e EMR Serverless.
6. Porque não guardam dados; se uma instância Spot for retomada, as tarefas são reexecutadas sem perda de dados.
7. Desacoplar compute e storage: dados no S3 e computação efêmera e elástica no EMR.
