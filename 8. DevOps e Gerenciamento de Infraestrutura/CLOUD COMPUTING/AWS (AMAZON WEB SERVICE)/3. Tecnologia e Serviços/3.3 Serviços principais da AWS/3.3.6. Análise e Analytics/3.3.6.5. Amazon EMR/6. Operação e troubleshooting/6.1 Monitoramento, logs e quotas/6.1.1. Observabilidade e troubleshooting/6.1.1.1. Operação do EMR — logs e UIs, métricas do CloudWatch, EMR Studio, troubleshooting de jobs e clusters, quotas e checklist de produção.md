### 6.1.1.1. Operação do EMR — logs e UIs, métricas do CloudWatch, EMR Studio, troubleshooting de jobs e clusters, quotas e checklist de produção

> [!warning] Aviso
> Nomes de métricas, caminhos de logs, estados de cluster/step, quotas e funcionalidades de UI (Spark History Server persistente, EMR Studio) abaixo são **de memória e mudam**. **Confirme na documentação do EMR e do Service Quotas.** Comandos e consultas são ilustrativos e **não foram executados**. Em incidente de pipeline, **priorize restaurar a entrega dos dados** (reexecução idempotente) antes de investigar a fundo.

## 1. O que significa operar o EMR

Operar EMR é garantir que **pipelines de dados rodem no prazo, com custo previsível e com dados corretos**. As perguntas do dia a dia:

1. **Os jobs terminaram e com sucesso?** (SLA, atrasos, falhas)
2. **Por que falhou/ficou lento?** (logs, UIs, métricas)
3. **O cluster está saudável e dimensionado?** (YARN, HDFS, scaling, Spot)
4. **Estamos dentro das quotas** e dos orçamentos?
5. **Os dados estão corretos e atualizados?** (qualidade, idempotência)
6. **Os clusters ociosos/esquecidos foram eliminados?**

```
Orquestração (Step Functions/MWAA) ─▶ Cluster/Job ─▶ Logs + Métricas + UIs ─▶ Alarmes ─▶ Runbooks ─▶ Custos/quotas ─▶ Melhoria
```

## 2. Logs

### 2.1 Onde ficam

| Log | Local | Conteúdo |
|---|---|---|
| **Logs do cluster (arquivados)** | **S3** em `--log-uri` (`s3://bucket/prefixo/<cluster-id>/`) a cada ~5 minutos | `steps/<step-id>/` (**stdout, stderr, controller, syslog**), `node/<instance-id>/` (daemons, bootstrap), `containers/<application-id>/<container-id>/` (logs do YARN/Spark) |
| **Logs no primary (local)** | `/mnt/var/log/` (ex.: `hadoop-yarn`, `spark`, `hive`) | Disponíveis enquanto o cluster existe |
| **CloudWatch Logs** | Via agente/configuração | Logs de aplicações e do sistema (consulta e alarmes) |
| **EMR Serverless** | **S3** e/ou **CloudWatch Logs** (configurável por job) | driver/executor logs |
| **EMR on EKS** | **S3** e/ou **CloudWatch Logs** | Logs de pods |

> [!warning] Sem `--log-uri`, sem diagnóstico
> Em **clusters transitórios**, ao terminar, **os logs locais somem**. **Sempre** configure `--log-uri` (e/ou CloudWatch) **antes** de rodar jobs.

### 2.2 Anatomia dos logs de um step

| Arquivo | Para quê |
|---|---|
| **`controller`** | O que o EMR fez ao executar o step (comando, erro de lançamento) |
| **`stderr`** | **Erros** do job (stack traces) — **começar por aqui** |
| **`stdout`** | Saída padrão |
| **`syslog`** | Mensagens Hadoop/YARN |
| **Logs de container (YARN)** | **Spark driver/executors**: `containers/application_.../container_.../stderr` — onde ficam os **erros reais** em modo `cluster` |

### 2.3 Boas práticas de logs

1. **Log URI** em **bucket dedicado** (SSE-KMS, retenção/lifecycle de **30–90 dias**).
2. **Logs estruturados** (JSON) nas aplicações, com **ID de execução** (data/partição).
3. **Correlacionar** com **orquestrador** (execução do Step Functions/DAG).
4. **CloudWatch Logs** para **alarmes** em padrões (`ERROR`, `OutOfMemory`).
5. **Evitar dados sensíveis** nos logs.

## 3. UIs e ferramentas de diagnóstico

| Ferramenta | Uso |
|---|---|
| **YARN ResourceManager UI** | Aplicações, filas, recursos, containers |
| **Spark History Server / Persistent App UI** | **Stages, tasks, skew, shuffle, memória** de jobs **concluídos** (UI **persistente** mesmo após o término do cluster, via EMR) |
| **Spark UI (job em execução)** | Diagnóstico ao vivo |
| **Tez UI / Hive** | Consultas Hive |
| **Ganglia/CloudWatch** | Métricas de cluster (Ganglia em releases antigos; CloudWatch é o caminho principal) |
| **Hue/Zeppelin/Jupyter** | Exploração interativa |
| **EMR Studio** | **IDE** de notebooks, **depuração** (links para UIs persistentes, logs) |
| **Console EMR** | Estados, steps, configuração, **application user interfaces** |

Acesso seguro: **EMR Studio/Console** (UI persistente), **Session Manager + port forwarding**; **não abra portas** à internet (ver segurança).

### 3.1 Como ler a Spark UI (diagnóstico rápido)

| Aba | O que procurar |
|---|---|
| **Jobs/Stages** | **Stage mais longa**; **tasks desbalanceadas** (min/mediana/max) → **skew** |
| **Tasks** | **GC time alto**, **spill (memória/disco)**, **shuffle read/write** gigante |
| **Storage** | Cache e uso de memória |
| **Executors** | **Executors mortos**, memória, tarefas falhas |
| **SQL** | Plano físico (broadcast? sort-merge? skew?) |
| **Environment** | Configurações efetivas |

## 4. Métricas do CloudWatch

### 4.1 Métricas do EMR (namespace `AWS/ElasticMapReduce`; nomes de memória — confirmar)

| Métrica | Interpretação |
|---|---|
| **`IsIdle`** | **1** quando o cluster está ocioso (sem steps/aplicações) — **base para auto-terminação/alarme** |
| **`AppsRunning` / `AppsPending`** | Aplicações YARN em execução/pendentes (**pendentes persistentes** = falta de recursos) |
| **`ContainerPending` / `ContainerAllocated`** | Pressão de containers |
| **`YARNMemoryAvailablePercentage`** | **Memória livre** no YARN (baixa → **escala**) |
| **`MemoryAvailableMB` / `MemoryAllocatedMB`** | Memória total/ocupada |
| **`CoreNodesRunning` / `TaskNodesRunning`** | Nós ativos |
| **`HDFSUtilization`** | **% do HDFS usado** (>80–90% → risco) |
| **`HDFSBytesRead/Written`**, **`S3BytesRead/Written`** | Throughput de I/O |
| **`MRUnhealthyNodes`, `MRLostNodes`** | Nós **não saudáveis/perdidos** (Spot, falha) |
| **`LiveDataNodes`, `MissingBlocks`, `CorruptBlocks`, `UnderReplicatedBlocks`** | Saúde do **HDFS** |
| **`ClusterStatus`/`StepsRunning`/`StepsFailed`** (por cluster/step) | Estado do trabalho |
| **`CapacityRemainingGB`** | Espaço livre no HDFS |
| **Métricas de Managed Scaling** | Capacidade solicitada vs provisionada |

### 4.2 Alarmes recomendados

| Alarme | Condição | Ação |
|---|---|---|
| **Step/Job falhou** | Evento (**EventBridge**: *EMR Step Status Change* `FAILED`) | Notificar/retry |
| **Cluster terminado com erro** | *EMR Cluster State Change* `TERMINATED_WITH_ERRORS` | Pager |
| **Cluster ocioso** | `IsIdle=1` por > N minutos (em clusters que deveriam terminar) | Terminar/alertar |
| **HDFS cheio** | `HDFSUtilization` > 85% | Limpar/escalar core |
| **Blocos perdidos/corrompidos** | `MissingBlocks`/`CorruptBlocks` > 0 | Investigar (Spot/core) |
| **Memória YARN baixa** | `YARNMemoryAvailablePercentage` < 15% por 10 min | Verificar scaling/job |
| **Aplicações pendentes** | `AppsPending` > 0 por 15 min | Falta de capacidade/quota |
| **Nós perdidos** | `MRLostNodes` > 0 | Spot/falha de nó |
| **Job passou do SLA** | Duração do step > limite | Investigar lentidão |
| **Custo** | Budgets > 80% | Revisar |

### 4.3 EventBridge: eventos do EMR

```json
{
  "source": ["aws.emr"],
  "detail-type": ["EMR Step Status Change"],
  "detail": { "state": ["FAILED", "CANCELLED"] }
}
```

Outros: **EMR Cluster State Change**, **EMR Instance Group/Fleet State Change**, **EMR Auto Scaling Policy State Change**, e eventos do **EMR Serverless** (job run state change). Use para **notificações, retry automático, tickets**.

## 5. Quotas e limites (ordem de grandeza — confirmar no Service Quotas)

| Item | Característica (de memória) |
|---|---|
| **Instâncias EC2 por família/região** | **Limite de vCPU** por tipo (On-Demand e Spot) — causa clássica de **cluster que não inicia/escala** |
| **Clusters ativos por região** | Limite (centenas) |
| **Steps por cluster** | Limite alto (milhares ao longo da vida); **steps simultâneos** limitados |
| **Instance groups/fleets** | Limites por cluster (ex.: até 48 task groups; 5 tipos por fleet) |
| **Taxa de API** (`DescribeCluster`, `ListSteps`…) | **Throttling** em automações agressivas |
| **EMR Serverless** | **Max capacity por application** (vCPU/memória/disco), **workers por job**, **applications por conta** |
| **EMR on EKS** | **Virtual clusters**, **job runs concorrentes**, limites do EKS |
| **S3** | **Requisições por prefixo** (3.500 PUT / 5.500 GET por segundo por prefixo) — **Slow Down** |
| **Glue Data Catalog** | Limites de partições/tabelas por banco; **throttling** em consultas |
| **IP disponíveis na subnet** | Cada nó consome 1 IP (cluster grande + subnet pequena = falha) |

Efeitos práticos:

- **Pré-validar** vCPU/quotas antes de grandes execuções (fim de mês).
- **Subnets com IPs suficientes** (/20 ou maiores para clusters grandes).
- **Backoff e paginação** nas automações.
- **Distribuir prefixos S3**; reduzir paralelismo por prefixo.

## 6. Troubleshooting operacional

### 6.1 Árvore: “o cluster não inicia / falha ao criar”

```
Cluster TERMINATED_WITH_ERRORS na criação?
├─ StateChangeReason: "VALIDATION_ERROR"/roles?           ─▶ Roles/PassRole/SG/subnet inválidos
├─ "INTERNAL_ERROR"/capacidade (InsufficientInstanceCapacity)? ─▶ Mais tipos/AZs (fleets); fallback On-Demand
├─ Limite de vCPU/instâncias?                              ─▶ Service Quotas
├─ Sem IPs na subnet?                                      ─▶ Subnet maior/outras subnets
├─ Bootstrap action falhou (exit code ≠ 0)?                ─▶ Logs de bootstrap em node/<id>/bootstrap-actions
├─ Sem rota/endpoints (subnet privada)?                    ─▶ NAT/VPC endpoints/Service Access SG
└─ Incompatibilidade release/aplicações/configurações JSON?─▶ Validar configurações
```

### 6.2 Árvore: “o step/job falhou”

```
Step FAILED?
├─ controller log: falha ao lançar (jar/script não encontrado, permissão S3)?   ─▶ Corrigir caminho/permissão
├─ stderr/container logs:
│    ├─ OutOfMemoryError / "Container killed by YARN for exceeding memory"?     ─▶ Memória/overhead/partições/skew
│    ├─ FileNotFound / AccessDenied (S3/KMS)?                                    ─▶ Roles/key policy/caminho
│    ├─ SchemaMismatch / AnalysisException?                                      ─▶ Schema/dados/catálogo
│    ├─ "ExecutorLostFailure"/nós perdidos?                                      ─▶ Spot/shuffle/HDFS; core On-Demand
│    └─ Timeout/Slow Down (S3)?                                                  ─▶ Paralelismo/retries/prefixos
└─ Dados corrompidos/vazios de origem?                                           ─▶ Qualidade; reprocessar upstream
```

### 6.3 Árvore: “o job está lento”

```
Job lento?
├─ Spark UI: poucos tasks gigantes (skew)?               ─▶ AQE skew, salting, repartition
├─ Muitos arquivos pequenos / listagem longa?            ─▶ Compactar; particionar; catálogo
├─ Shuffle/spill grande?                                 ─▶ Memória, NVMe, partições, broadcast
├─ CPU baixa e executors ociosos?                        ─▶ Mais partições; dynamic allocation
├─ Aguardando recursos (AppsPending, ContainerPending)?  ─▶ Escala/quotas/capacidade
├─ Spot interrompido / reexecuções?                      ─▶ Fleet diversificada; core On-Demand
└─ Leitura de dados em formato ineficiente (CSV/JSON)?   ─▶ Parquet/ORC; pushdown
```

### 6.4 Tabela de sintomas

| Sintoma | Causa provável | Ação |
|---|---|---|
| `Container killed by YARN for exceeding memory limits` | Overhead baixo; executors grandes; PySpark | Aumentar `memoryOverhead`; reduzir cores/executor |
| `java.lang.OutOfMemoryError: GC overhead` | Memória insuficiente; skew | Ajustar memória; mais partições |
| Job “travado” em 99% | **Skew** (um task gigante) | AQE/salting |
| `ExecutorLostFailure` frequente | Spot/OOM/nó perdido | Estratégia de Spot; memória |
| `S3 Slow Down (503)` | Excesso de requisições por prefixo | Reduzir paralelismo; distribuir prefixos |
| `NoSuchKey`/inconsistência de leitura | Dados removidos concorrentemente; commit não atômico | Committers/Iceberg; coordenação de jobs |
| `HDFS full` | Dados temporários/shuffle excessivos | Core maior/NVMe; limpar; mover para S3 |
| Cluster ocioso ligado | Sem auto-terminação | `IdleTimeout`/término após steps |
| Notebook não conecta | Rede/Livy/roles | Ver SG/Studio/roles |
| Saída duplicada | Reexecução não idempotente | Overwrite dinâmico/MERGE |

### 6.5 Runbook: pipeline atrasado ou falho

1. **Confirmar** o impacto (qual SLA/consumidores; dados do dia faltantes).
2. **Localizar** a falha: orquestrador (execução) → step → logs (`controller`/`stderr`/container).
3. **Classificar**: infra (capacidade/quota/Spot), código (bug/memória/skew), dados (schema/qualidade), permissão (IAM/KMS/Lake Formation), rede.
4. **Mitigar** com o **menor risco**: **reexecutar** (se idempotente), **aumentar recursos** temporariamente, **escalar** o cluster, **usar On-Demand** no lugar de Spot, **reprocessar partição específica**.
5. **Validar** os dados (contagens, checagens de qualidade) antes de liberar consumidores.
6. **Comunicar** (stakeholders) e **registrar** o incidente.
7. **Corrigir a causa-raiz** (código/dimensionamento/alarmes) e **adicionar teste/alarme** para evitar recorrência.

### 6.6 Idempotência e reprocessamento seguro

| Prática | Detalhe |
|---|---|
| **Particionar por data de execução** | Reprocessar só a partição afetada |
| **Overwrite dinâmico por partição** | Evita duplicar ao reexecutar |
| **MERGE** (Iceberg/Hudi/Delta) | Upserts determinísticos |
| **Marcadores de conclusão** | `_SUCCESS`/tabela de controle |
| **Escrita em staging + promoção** | Evita dados parciais visíveis |
| **Testes de qualidade** | Contagens, nulos, duplicatas antes de publicar |

## 9. Checklist de produção

- [ ] **`--log-uri`** (S3, KMS, lifecycle) e/ou CloudWatch em **todos** os clusters/jobs
- [ ] **EventBridge** para falhas de step/cluster/job → notificações e retry
- [ ] **Alarmes**: HDFS, YARN, nós perdidos, ociosidade, SLA, custo
- [ ] **Spark History persistente/EMR Studio** acessível aos engenheiros
- [ ] **Orquestração** com **retry**, **idempotência** e **marcadores de conclusão**
- [ ] **Quotas e IPs de subnet** verificados; **fleets/Spot** diversificados
- [ ] **Auto-terminação** e **tags** obrigatórias
- [ ] **Qualidade de dados** (checagens) antes de publicar
- [ ] **Runbooks** (cluster não inicia, job falha, job lento, pipeline atrasado) publicados
- [ ] **Versão do EMR** e **AMIs** atualizadas conforme política
- [ ] **Revisões periódicas** de custos, acessos e quotas

## 10. Erros comuns

- **Sem log URI** (impossível diagnosticar clusters transitórios).
- **Alarmes só de falha**, sem **SLA/atraso** nem **ociosidade**.
- **Reexecutar sem idempotência** (duplicação).
- **Ignorar quotas de vCPU** até o dia do pico.
- **Subnet pequena** para cluster grande.
- **Diagnóstico só pelo console do YARN** (que some com o cluster) em vez da **UI persistente/logs no S3**.
- **Notebook manual como produção**.
- **Clusters persistentes sem owner**.
- **Sem testes de qualidade** (dados errados publicados “com sucesso”).
- **Deixar a versão do EMR envelhecer** (segurança/desempenho).

## 11. Resumo rápido

- Operar = **entregar dados no prazo, com custo controlado e qualidade**.
- **Logs**: **`--log-uri` no S3** (steps: `controller`, `stderr`, `stdout`; containers YARN para erros do Spark), **CloudWatch**; **Spark History persistente/EMR Studio** para diagnóstico.
- **Métricas**: `IsIdle`, `AppsPending`, `YARNMemoryAvailablePercentage`, `HDFSUtilization`, `MRLostNodes`, `MissingBlocks`; **EventBridge** para falhas de step/cluster.
- **Quotas**: **vCPU por família**, clusters/steps, **IPs de subnet**, **prefixos S3**, **Glue Catalog**, limites de **Serverless/EKS**.
- **Árvores**: cluster não inicia (roles/capacidade/quotas/IPs/bootstrap), step falhou (controller → stderr → container), job lento (skew/arquivos pequenos/shuffle/recursos/Spot).
- **Reprocessamento seguro**: partições, overwrite dinâmico, **MERGE**, marcadores, staging, testes de qualidade.
- **Rotinas** diárias a semestrais; **runbooks** e **automação de alarmes**.

## 🧩 Quiz de Fixação

1. Por que configurar `--log-uri` é essencial em clusters transitórios?
2. Que arquivos do step ajudam a diagnosticar e por onde começar?
3. Que métrica indica cluster ocioso e como usá-la?
4. Que sinais na Spark UI indicam data skew?
5. Quais quotas costumam impedir um cluster de iniciar ou escalar?
6. Como reprocessar com segurança uma partição falha?
7. Por que notebooks manuais não devem ser a forma de rodar produção?

**Respostas:**

1. Porque ao terminar o cluster, os logs locais desaparecem; o S3 mantém stderr, controller e logs de containers para diagnóstico posterior.
2. `controller`, `stderr`, `stdout` e `syslog`; começar pelo `stderr` (e pelos logs de containers do YARN em modo cluster).
3. `IsIdle`; usa-se para alarmes e auto-terminação de clusters que deveriam ter terminado.
4. Poucos tasks muito mais longos que a mediana (diferença entre min, mediana e max), com stages que ficam presas em 99%.
5. Limites de vCPU por família de instância (On-Demand/Spot), número de clusters ativos e IPs disponíveis na subnet.
6. Com jobs idempotentes: particionamento por data, overwrite dinâmico ou MERGE, staging com promoção, marcadores de conclusão e checagens de qualidade antes de publicar.
7. Porque não são versionados, testados nem repetíveis; produção deve rodar código em repositório/CI/CD por steps ou job runs orquestrados.
