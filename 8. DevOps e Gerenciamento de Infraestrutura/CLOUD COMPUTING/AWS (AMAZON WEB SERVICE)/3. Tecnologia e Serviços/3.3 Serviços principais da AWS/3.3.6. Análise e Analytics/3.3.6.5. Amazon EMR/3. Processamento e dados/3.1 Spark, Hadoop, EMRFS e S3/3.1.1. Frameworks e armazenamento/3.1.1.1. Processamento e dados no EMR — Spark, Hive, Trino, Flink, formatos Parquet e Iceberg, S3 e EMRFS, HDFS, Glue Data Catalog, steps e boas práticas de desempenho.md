### 3.1.1.1. Processamento e dados no EMR — Spark, Hive, Trino, Flink, formatos Parquet e Iceberg, S3 e EMRFS, HDFS, Glue Data Catalog, steps e boas práticas de desempenho

> [!warning] Aviso
> Versões, nomes de configurações, comportamento do EMRFS/S3, otimizações do EMR Runtime e recomendações de desempenho abaixo são **de memória e mudam**. **Confirme na documentação do EMR, do Spark e dos formatos de tabela.** Código e comandos são ilustrativos e **não foram executados**. Ajustes de desempenho dependem de **medição** no seu workload.

## 1. A pilha de dados no EMR

```
Aplicação (Spark / Hive / Trino / Flink)
          │  lê/escreve tabelas e arquivos
          ▼
 Catálogo de metadados  ── Glue Data Catalog (ou Hive Metastore)
          │
          ▼
 Armazenamento:  S3 (via EMRFS/S3A)  ◀── durável, barato, compartilhado
                 HDFS (disco do cluster) ◀── efêmero, rápido, para temporários/shuffle
```

Compreender **onde os dados vivem** e **como são lidos** é a chave para desempenho e custo.

## 2. Armazenamento: S3 vs HDFS

### 2.1 Comparação

| Critério | **S3 (EMRFS)** | **HDFS** |
|---|---|---|
| **Durabilidade** | **Altíssima** (11 noves), independente do cluster | **Termina com o cluster**; replicação entre nós |
| **Custo** | **Baixo** por GB | Disco das instâncias (mais caro) |
| **Compartilhamento** | **Vários clusters/serviços** acessam | Só o cluster |
| **Latência/Throughput** | Maior latência por operação; **alto throughput agregado** | **Baixa latência**, I/O local |
| **Operações de rename** | **Não atômicas** (copy+delete) — impacto em commits | Rápidas |
| **Consistência** | **Forte** (read-after-write, listagem) desde 2020 | Forte |
| **Uso** | **Fonte da verdade**: dados de entrada e saída | **Temporários**, shuffle, checkpoints, cache |

> [!info] Consistência do S3
> Antes de dez/2020 o S3 tinha consistência eventual em listagens e o EMR oferecia o “**EMRFS consistent view**” para mitigar. Com **consistência forte** do S3, isso ficou **desnecessário** (recurso obsoleto; confirmar o estado atual).

### 2.2 EMRFS e S3A

- **EMRFS** (`s3://`): implementação do EMR (otimizada), com suporte a **SSE-S3/SSE-KMS/CSE-KMS**, **S3 Select pushdown** (quando aplicável) e **commit otimizado**.
- **S3A** (`s3a://`): conector open source Hadoop; o EMR recomenda **`s3://`** (EMRFS) no cluster.
- **Committers otimizados** (**EMRFS S3-optimized committer**, **magic committer** do Spark): **evitam o rename** lento no S3 ao finalizar jobs — **crítico** para desempenho de escrita e **atomicidade**.

### 2.3 Quando usar HDFS

- **Shuffle** e dados **intermediários** (Spark usa discos locais).
- **Cache** de dados quentes para jobs iterativos.
- **Checkpoints** de streaming (também há opção no S3).
- Cargas de **I/O intenso e baixa latência** (HBase em HDFS).

Nunca como **armazenamento permanente**: ao terminar, **perde-se tudo**.

## 3. Formatos de arquivo e tabelas

### 3.1 Formatos

| Formato | Tipo | Vantagens | Observações |
|---|---|---|---|
| **CSV/JSON** | Texto, por linha | Simples, legível | **Ineficiente** (sem schema/compressão/colunas); evite como formato analítico |
| **Parquet** | **Colunar** | **Compressão**, **leitura de colunas**, **predicate pushdown**, schema embutido | **Padrão recomendado** para análise |
| **ORC** | Colunar | Muito eficiente no ecossistema Hive | Similar ao Parquet |
| **Avro** | Por linha, com schema | Bom para **streaming/ingestão** e evolução de schema | Não é colunar |

Regras de ouro:

1. **Converter CSV/JSON → Parquet/ORC** na primeira camada de processamento.
2. **Compressão** (Snappy/ZSTD) **balanceando** CPU e armazenamento.
3. **Tamanho de arquivo** alvo de **128 MB–1 GB** (evite **milhões de arquivos pequenos**).
4. **Particionar** por colunas de filtro frequente (`data`, `região`) — mas **sem excesso** (cardinalidade alta = partições minúsculas).

### 3.2 Formatos de tabela abertos (lakehouse)

Parquet puro não oferece **transações**. **Iceberg**, **Hudi** e **Delta Lake** adicionam:

| Recurso | Descrição |
|---|---|
| **ACID** | Escritas atômicas, isolamento de leitores |
| **Upserts/Deletes (MERGE)** | Atualizar linhas sem reescrever tudo |
| **Time travel** | Consultar **versões anteriores** |
| **Evolução de schema/partição** | Adicionar colunas, mudar particionamento sem reescrever |
| **Compactação** | Consolidar arquivos pequenos |
| **Snapshots** | Rollback, auditoria |
| **Integração** | Glue Data Catalog, Athena, Redshift Spectrum, EMR, Glue |

Escolha (resumo): **Iceberg** (neutralidade e adoção ampla), **Hudi** (upserts/CDC e streaming incremental), **Delta** (ecossistema Databricks/Spark). Verifique **suporte por release** no EMR.

```python
# Exemplo (ilustrativo): escrever uma tabela Iceberg com Spark no EMR
spark.sql("""
  CREATE TABLE glue_catalog.analytics.vendas (
     id bigint, data date, valor decimal(12,2), regiao string)
  USING iceberg PARTITIONED BY (days(data))
  LOCATION 's3://datalake-123456789012/analytics/vendas/'
""")
spark.sql("MERGE INTO glue_catalog.analytics.vendas t USING novas n ON t.id = n.id "
          "WHEN MATCHED THEN UPDATE SET * WHEN NOT MATCHED THEN INSERT *")
```

## 4. Catálogo de metadados

| Opção | Descrição |
|---|---|
| **AWS Glue Data Catalog** | **Padrão recomendado**: metastore **compartilhado** com **Athena, Glue, Redshift Spectrum, Lake Formation** |
| **Hive Metastore local** (no primary) | **Efêmero** (some com o cluster) |
| **Hive Metastore externo** (RDS/Aurora) | Persistente, compartilhado entre clusters (mais administração) |

Configuração (Spark/Hive) para usar o **Glue Catalog** — marcar **“Use for Hive table metadata/Spark table metadata”** ao criar o cluster (ou classificações `hive-site`/`spark-hive-site`).

Benefícios: **tabelas persistem** após o término do cluster; **múltiplos serviços** consultam as mesmas tabelas; **Lake Formation** aplica **permissões**.

## 5. Frameworks em detalhe

### 5.1 Apache Spark

| Aspecto | Detalhe |
|---|---|
| **Modelo** | Processamento **em memória**, **DAG**, **RDD/DataFrame/Spark SQL** |
| **Componentes** | **Driver** (coordena), **executors** (executam tasks), **YARN** (gestão) |
| **Modos de deploy** | `--deploy-mode cluster` (driver no cluster — **recomendado em steps**) vs `client` |
| **Casos** | ETL, ML (MLlib), streaming estruturado, SQL |
| **EMR Runtime for Spark** | Otimizações da AWS (de memória: **mais rápido** que Spark open source em benchmarks; confirmar) |

```bash
spark-submit --deploy-mode cluster --master yarn \
  --conf spark.sql.adaptive.enabled=true \
  --conf spark.dynamicAllocation.enabled=true \
  --conf spark.executor.memory=16g --conf spark.executor.cores=4 \
  s3://codigo/etl.py s3://dados/entrada/ s3://dados/saida/
```

### 5.2 Apache Hive

- **SQL sobre dados** no HDFS/S3 (**HiveQL**), engine **Tez** (ou MapReduce).
- Usado em **migrações** de data warehouses Hadoop e **ETL SQL**.
- **Metastore** é a base do catálogo (Glue Catalog).

### 5.3 Trino/Presto

- **Consultas SQL interativas** (federadas) com baixa latência; lê S3, Hive/Iceberg, RDS, etc.
- Útil para **analistas** em cluster **persistente** (diferente de Athena, que é serverless gerenciado — Athena é Trino serverless).

### 5.4 Apache Flink

- **Streaming** com estado e processamento **evento a evento** de baixa latência.
- Alternativa gerenciada: **Amazon Managed Service for Apache Flink**.

### 5.5 HBase

- **NoSQL colunar** (leituras/escritas de baixa latência), pode armazenar no **S3** (modo S3 com cache) — persistente exige cuidado.

## 6. Steps e execução de jobs

### 6.1 Tipos de step

| Tipo | Exemplo |
|---|---|
| **Spark application** | `Type=Spark` (usa `spark-submit`) |
| **Custom JAR / Command Runner** | `command-runner.jar` + `spark-submit`/`hive`/`s3-dist-cp` |
| **Hive script** | `Type=Hive` |
| **Streaming (Hadoop)** | Mapper/reducer scripts |
| **s3-dist-cp** | Copiar grandes volumes entre S3 e HDFS |

### 6.2 `ActionOnFailure`

| Valor | Efeito |
|---|---|
| `CONTINUE` | Segue para o próximo step |
| `CANCEL_AND_WAIT` | Cancela os pendentes e **espera** (para depuração) |
| `TERMINATE_CLUSTER` | Termina o cluster (cluster transitório) |

### 6.3 Concorrência de steps

Clusters podem executar **steps em paralelo** (concorrência configurável; confirmar o limite); cuidado com **disputa de recursos** no YARN.

### 6.4 Idempotência e atomicidade

- Escreva **saída em diretório temporário** e **promova** (ou use **committers** apropriados/formatos transacionais).
- Reexecuções **não podem duplicar** dados: **overwrite por partição** (`spark.sql.sources.partitionOverwriteMode=dynamic`) ou **MERGE** em Iceberg/Hudi.

## 7. Boas práticas de desempenho

### 7.1 Dados

1. **Parquet/ORC** + **compressão**.
2. **Particionamento** adequado e **bucketing** quando útil.
3. **Compactação** de arquivos pequenos (jobs de **compaction** ou recursos do Iceberg/Hudi).
4. **Predicate/Projection pushdown**: filtrar cedo, selecionar só colunas necessárias.
5. **Evitar SELECT *** e **full scans**.
6. **Estatísticas** atualizadas (ANALYZE) quando relevante.

### 7.2 Spark

| Técnica | Detalhe |
|---|---|
| **Adaptive Query Execution (AQE)** | `spark.sql.adaptive.enabled=true` ajusta shuffle partitions e **skew joins** em runtime |
| **Dynamic allocation** | Executors escalam com a carga |
| **Dimensionar executors** | **Core por executor 4–5**, memória compatível (+ **overhead**); evitar executors minúsculos/gigantes |
| **Shuffle partitions** | Ajustar `spark.sql.shuffle.partitions` (padrão 200 pode ser pouco/muito) |
| **Broadcast join** | Para tabelas pequenas |
| **Skew** | **Salting**/AQE/repartition |
| **Cache** | Só quando reutilizado; `persist(MEMORY_AND_DISK)` |
| **Serialização** | **Kryo** em vez de Java |
| **Evitar UDFs Python** lentas** | Preferir funções nativas |
| **Coalesce/repartition** | Controlar o número de arquivos de saída |

### 7.3 Cluster

- **Instâncias** adequadas ao perfil: **memória (r)** para joins/caches, **computação (c)** para CPU-bound, **uso geral (m)**; **Graviton** (`g`) para custo/desempenho.
- **Discos locais** (NVMe/instance store ou EBS **gp3**) para **shuffle** pesado.
- **Rede**: **placement** e instâncias com **rede melhorada**.
- **Managed scaling** (ver a folha de escala).

### 7.4 S3

- **Prefixos distribuídos** (S3 escala por prefixo; padrões como `s3://bucket/ano=/mes=/dia=` ajudam).
- **Throttling** (503 Slow Down): reduzir **paralelismo** por prefixo; **retry** com backoff; **EMRFS** tem retries.
- **Evitar listar** milhões de objetos (usar **catálogo/partições**).
- **Mesma região** do cluster (latência e custo de transferência).

## 8. Exemplo de pipeline

```
S3 (raw: JSON/CSV) ──▶ Spark (limpeza, validação, schema) ──▶ S3 (curated: Parquet/Iceberg particionado)
                                   │                                  │
                                   └──── Glue Data Catalog ◀──────────┘ ──▶ Athena / Redshift Spectrum / QuickSight
```

Camadas típicas (**medalhão**): **bronze** (bruto), **silver** (limpo/conformado), **gold** (agregados de negócio).

## 9. Erros comuns

- **CSV/JSON** como formato analítico.
- **Milhões de arquivos pequenos** (listagem e abertura caras).
- **Particionar em excesso** (alta cardinalidade).
- **Escrever no S3 sem committer otimizado** (renames lentos, risco de inconsistência).
- **HDFS como fonte da verdade**.
- **Metastore local** (tabelas perdidas ao terminar o cluster).
- **Executors mal dimensionados** (OOM, subutilização).
- **Não habilitar AQE/dynamic allocation**.
- **Skew ignorado** (poucos tasks gigantes).
- **Steps não idempotentes** com `append` repetido.
- **Cache de tudo** (consome memória sem ganho).

## 10. Troubleshooting

| Sintoma | Causa provável | Ação |
|---|---|---|
| `OutOfMemoryError`/container killed | Memória/overhead; skew; partições grandes | Aumentar memória/overhead; mais partições; tratar skew |
| Job lento com pouca CPU usada | Poucos executors/partições; I/O de arquivos pequenos | Dynamic allocation; compactar; repartition |
| Última etapa muito lenta (escrita) | Rename no S3 sem committer | Habilitar o committer otimizado |
| `Slow Down` (503) do S3 | Muitas requisições por prefixo | Reduzir o paralelismo; distribuir prefixos |
| Tabela some após o cluster terminar | Metastore local | Usar o Glue Data Catalog |
| Dados duplicados após retry | Step não idempotente | Overwrite dinâmico/MERGE |
| Um task demora muito mais | Data skew | AQE skew join; salting |
| Consulta Hive/Trino lenta | Sem partição/formato colunar | Reorganizar dados |

## 11. Resumo rápido

- **Dados no S3 (EMRFS)** como fonte da verdade; **HDFS** só para **shuffle/temporários/cache**; S3 tem **consistência forte**.
- **Parquet/ORC** + compressão + **arquivos de 128 MB–1 GB** + **particionamento moderado**; **Iceberg/Hudi/Delta** para ACID, upserts e time travel.
- **Glue Data Catalog** como metastore persistente e compartilhado.
- **Spark** (ETL/ML/streaming), **Hive** (SQL/migração), **Trino** (interativo), **Flink** (streaming), **HBase** (NoSQL).
- **Steps** (`ActionOnFailure`), **idempotência**, **committers otimizados** no S3.
- **Desempenho**: **AQE**, **dynamic allocation**, executors bem dimensionados, **broadcast join**, tratar **skew**, instâncias adequadas e **mesma região** do S3.

## 🧩 Quiz de Fixação

1. Por que o S3 deve ser a fonte da verdade e o HDFS apenas temporário?
2. Que vantagens o Parquet traz sobre CSV?
3. Para que servem Iceberg, Hudi e Delta Lake?
4. Por que usar o Glue Data Catalog como metastore?
5. Qual o problema dos arquivos pequenos e como mitigar?
6. O que o AQE faz no Spark?
7. Por que o committer otimizado importa ao escrever no S3?

**Respostas:**

1. Porque o S3 é durável e independente do cluster, enquanto o HDFS desaparece quando o cluster termina.
2. Formato colunar com compressão, leitura apenas das colunas necessárias, predicate pushdown e schema embutido, reduzindo I/O e custo.
3. Adicionam transações ACID, upserts/deletes, time travel, evolução de schema e compactação sobre arquivos em data lakes.
4. Porque persiste os metadados além do cluster e é compartilhado com Athena, Glue, Redshift Spectrum e Lake Formation.
5. Sobrecarregam listagem e abertura de arquivos, prejudicando desempenho; mitiga-se com compactação e controle do número de arquivos de saída (coalesce/repartition), mirando 128 MB–1 GB.
6. Ajusta o plano em tempo de execução (número de partições de shuffle, joins com skew), melhorando o desempenho.
7. Evita renames lentos e não atômicos (copy+delete) no S3 ao finalizar o job, melhorando desempenho e consistência da escrita.
