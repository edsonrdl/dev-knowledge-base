### 5.1.1.1. Segurança do EMR — roles de serviço e de instância, security configurations, criptografia, Kerberos, Lake Formation, runtime roles, rede e Block Public Access

> [!warning] Aviso
> Nomes de roles padrão, opções de security configuration, suporte a Lake Formation/runtime roles por modo e release, e recursos de Block Public Access abaixo são **de memória e mudam**. **Confirme na documentação do EMR, do IAM e do Lake Formation.** Políticas e comandos são ilustrativos e **não foram executados**. Dados sensíveis e acessos a clusters devem seguir a política da sua organização; trate estes exemplos como ponto de partida.

## 1. Por que a segurança do EMR merece atenção especial

Um cluster EMR é, na prática, **um conjunto de servidores com acesso a grandes volumes de dados**, frequentemente **dados sensíveis** (clientes, financeiros, saúde), executando **código arbitrário** (jobs Spark, notebooks) escrito por muita gente. Riscos típicos:

| Risco | Exemplo |
|---|---|
| **Acesso excessivo aos dados** | Role da instância com `s3:*` em todos os buckets → qualquer job lê tudo |
| **Cluster exposto** | Primary com UIs (YARN, Spark, Hue, Jupyter) abertas à internet |
| **Credenciais vazadas** | Notebooks com chaves; metadata service acessível a código do usuário |
| **Dados em claro** | Sem criptografia em repouso/trânsito |
| **Movimento lateral** | Instância comprometida acessando outros recursos pela role |
| **Mudança não rastreada** | Configurações/segurança alteradas sem auditoria |
| **Multi-tenancy fraco** | Usuários de times distintos compartilhando o mesmo cluster com as mesmas permissões |
| **Supply chain** | Bootstrap/libs de origens não confiáveis |

Camadas de defesa: **identidade (IAM/Kerberos/LDAP)** → **autorização de dados (Lake Formation/Ranger/runtime roles)** → **criptografia** → **rede** → **auditoria**.

## 2. Roles do IAM

### 2.1 As três roles clássicas (EMR on EC2)

| Role | Quem assume | Para quê |
|---|---|---|
| **EMR service role** (`EMR_DefaultRole`) | O **serviço EMR** | **Provisionar** e gerenciar o cluster (EC2, rede, tags) |
| **EC2 instance profile** (`EMR_EC2_DefaultRole`) | As **instâncias** do cluster | **Acesso aos dados** (S3, Glue, DynamoDB…) pelos jobs |
| **Auto Scaling role** (`EMR_AutoScaling_DefaultRole`) | O serviço de auto scaling | Escalar instance groups (legado/managed) |

> [!warning] As roles padrão são amplas
> As roles **default** criadas por `--use-default-roles` são **permissivas** (ex.: S3 amplo). Em **produção**, crie **roles customizadas com menor privilégio** e **por carga de trabalho**.

### 2.2 Problema do instance profile único

Se **todos os jobs** compartilham a **role da instância**, **todo job** tem as **mesmas permissões** — uma vulnerabilidade de **multi-tenancy** e de **privilégio mínimo**. Soluções:

| Solução | Descrição |
|---|---|
| **Clusters por equipe/carga** | Cada cluster com sua instance profile mínima |
| **Runtime roles (job-scoped)** | **Role por step/job** (EMR on EC2 com **runtime roles**, EMR on EKS com **IRSA**, EMR Serverless com **execution role**) |
| **Lake Formation** | Autorização **por tabela/coluna** independente da role do S3 |
| **Apache Ranger** | Políticas centrais em clusters EC2 (integração gerenciada ou própria) |

### 2.3 Runtime roles

| Aspecto | Detalhe (de memória — confirmar) |
|---|---|
| **Ideia** | Cada **step/job** assume uma **role IAM específica** (não a instance profile) |
| **Benefício** | **Privilégio mínimo por job**; **auditoria** por identidade; multi-tenancy |
| **Como** | Submeter o step informando `ExecutionRoleArn`; a role precisa de **trust** para o EMR |
| **Requisitos** | Security configuration habilitando **runtime roles**; clusters com **release suportado** |
| **Integração** | Com **Lake Formation** (credenciais restritas) e **CloudTrail** (identidade do job) |

```bash
aws emr add-steps --cluster-id j-ABC123456789 \
  --execution-role-arn arn:aws:iam::123456789012:role/JobVendasRole \
  --steps Type=Spark,Name=vendas,ActionOnFailure=CONTINUE,Args=[--deploy-mode,cluster,s3://codigo/vendas.py]
```

### 2.4 Política de menor privilégio (exemplo da role de dados)

```json
{
  "Version": "2012-10-17",
  "Statement": [
    { "Sid": "LerEntrada", "Effect": "Allow", "Action": ["s3:GetObject", "s3:ListBucket"],
      "Resource": ["arn:aws:s3:::datalake-123456789012", "arn:aws:s3:::datalake-123456789012/raw/vendas/*"] },
    { "Sid": "EscreverSaida", "Effect": "Allow", "Action": ["s3:PutObject", "s3:DeleteObject"],
      "Resource": "arn:aws:s3:::datalake-123456789012/curated/vendas/*" },
    { "Sid": "Catalogo", "Effect": "Allow", "Action": ["glue:GetTable", "glue:GetTables", "glue:GetDatabase", "glue:GetPartitions", "glue:BatchCreatePartition"],
      "Resource": "*" },
    { "Sid": "KMS", "Effect": "Allow", "Action": ["kms:Decrypt", "kms:GenerateDataKey"],
      "Resource": "arn:aws:kms:us-east-1:123456789012:key/<id>" }
  ]
}
```

### 2.5 Permissões de **quem cria/gerencia** clusters

| Papel | Pode | Não deve |
|---|---|---|
| **Plataforma/Dados (engenharia)** | `elasticmapreduce:RunJobFlow`, `AddJobFlowSteps` **com roles permitidas** (`iam:PassRole` restrito) | `iam:PassRole` para **qualquer** role |
| **Analistas** | Notebooks/EMR Studio com **workspace** limitado | Criar clusters livres |
| **Auditoria** | `Describe*`, `List*` | Alterar |

**`iam:PassRole`** é o ponto crítico: quem pode criar cluster pode **passar roles poderosas**. Restrinja por **ARN de role** e **condições** (`iam:PassedToService`).

## 3. Security configurations

Uma **security configuration** é um **objeto reutilizável** que define **criptografia, autenticação e autorização** e é **aplicado na criação do cluster**.

```json
{
  "EncryptionConfiguration": {
    "EnableInTransitEncryption": true,
    "EnableAtRestEncryption": true,
    "InTransitEncryptionConfiguration": {
      "TLSCertificateConfiguration": { "CertificateProviderType": "PEM", "S3Object": "s3://seg-123456789012/certs/emr-certs.zip" }
    },
    "AtRestEncryptionConfiguration": {
      "S3EncryptionConfiguration": { "EncryptionMode": "SSE-KMS", "AwsKmsKey": "arn:aws:kms:us-east-1:123456789012:key/<id>" },
      "LocalDiskEncryptionConfiguration": { "EncryptionKeyProviderType": "AwsKms", "AwsKmsKey": "arn:aws:kms:us-east-1:123456789012:key/<id>", "EnableEbsEncryption": true }
    }
  },
  "AuthenticationConfiguration": { "KerberosConfiguration": { "Provider": "ClusterDedicatedKdc",
      "ClusterDedicatedKdcConfiguration": { "TicketLifetimeInHours": 24 } } }
}
```

```bash
aws emr create-security-configuration --name sec-prod --security-configuration file://sec-config.json
aws emr create-cluster ... --security-configuration sec-prod
```

> Security configurations são **imutáveis após o cluster iniciar**: planeje.

## 4. Criptografia

### 4.1 Em repouso

| Camada | Opções |
|---|---|
| **Dados no S3 (EMRFS)** | **SSE-S3**, **SSE-KMS**, **CSE-KMS** (cliente), **CSE-Custom** |
| **Discos locais (EBS/instance store)** | **EBS encryption** + **LUKS** (instance store) via **KMS** |
| **HDFS** | **Transparent encryption** (HDFS Encryption Zones) com KMS Hadoop/Ranger KMS |
| **Metastore (Glue Catalog)** | Criptografia do catálogo com KMS |
| **Logs no S3** | SSE-KMS no bucket de logs |

### 4.2 Em trânsito

| Canal | Mecanismo |
|---|---|
| **Entre nós** (Spark RPC, shuffle, HDFS, YARN) | **TLS** (certificados PEM/Custom) e criptografia de **Spark/Tez/Hadoop** habilitada pela configuration |
| **Cliente ↔ UIs/serviços** | **TLS/HTTPS** (Livy, Hue, Jupyter, UIs) |
| **Para o S3** | **HTTPS** (EMRFS) |
| **Para Kerberos/LDAP** | **LDAPS** |

### 4.3 Gestão de chaves

- **CMKs separadas** por ambiente/domínio de dados; **key policy** mínima.
- **Rotação** habilitada; **alarmes** para `DisableKey`/`ScheduleKeyDeletion`.
- **Cross-account**: permissões de chave quando o cluster está em outra conta que o bucket.

## 5. Autenticação: Kerberos e LDAP

| Opção | Detalhe (de memória — confirmar) |
|---|---|
| **Kerberos (KDC dedicado)** | O primary roda um **KDC**; usuários/serviços autenticam por **tickets**; bom para **isolamento de usuários** em clusters multi-usuário |
| **Kerberos com KDC externo** | Integra a um **AD** (Directory Service/Active Directory on-prem) via **trust** |
| **LDAP/AD** | Autenticação de usuários em **Hue, Presto/Trino, Zeppelin, JupyterHub** |
| **Identity Center/EMR Studio** | **Single sign-on** para o **EMR Studio** com **IAM Identity Center** |
| **Impersonation** | Livy/Hive impersonam o usuário final |

Quando usar: **clusters persistentes e multiusuário** com dados sensíveis. Para **clusters transitórios por pipeline**, **IAM + runtime roles** costumam bastar.

## 6. Autorização de dados: Lake Formation, Ranger e runtime roles

### 6.1 AWS Lake Formation com EMR

| Aspecto | Detalhe |
|---|---|
| **Ideia** | **Permissões por banco/tabela/coluna/linha** (no Glue Data Catalog) — o job **vê só** o que o **principal** pode |
| **Como** | O EMR **obtém credenciais temporárias restritas** do Lake Formation em nome do principal (modo de **fine-grained access control**) |
| **Suporte** | **EMR on EC2** (com runtime roles), **EMR on EKS**, **EMR Serverless** (com requisitos de release/versão; confirmar) |
| **Vantagem** | **Governança central**: as **mesmas permissões** valem para **Athena, Redshift Spectrum, EMR, Glue** |
| **Cuidado** | Requer **configuração específica** (roles de sistema, user mapping, ausência de acesso direto ao S3 pelos usuários) |

### 6.2 Apache Ranger

| Aspecto | Detalhe |
|---|---|
| **Papel** | Políticas **centralizadas** de acesso a Hive, HDFS, S3, Spark, Kafka, etc. |
| **EMR** | **Integração gerenciada** (plugins) com Ranger **no seu servidor** (confirmar suporte atual) |
| **Quando** | Ambientes **já padronizados em Ranger** (on-prem → nuvem) |

### 6.3 Escolha

| Cenário | Preferência |
|---|---|
| **Data lake AWS-nativo** multi-serviço | **Lake Formation** |
| **Migração com Ranger existente** | Ranger |
| **Isolamento por job sem governança de coluna** | **Runtime roles** + bucket/prefix policies |
| **Multi-tenancy forte** | **Clusters separados** + Lake Formation |

## 7. Rede

### 7.1 Princípios

| Controle | Prática |
|---|---|
| **Subnets privadas** | Clusters **sem IP público**; saída por **NAT** ou **VPC endpoints** |
| **VPC endpoints** | **S3 (gateway)**, **Glue**, **STS**, **KMS**, **CloudWatch Logs**, **EMR** (para chamar APIs sem internet) |
| **Security groups** | O EMR cria SGs gerenciados (`ElasticMapReduce-master/slave/ServiceAccess`); **restrinja** as origens de **SSH/UIs** |
| **Acesso às UIs** | **EMR Studio**, **Session Manager/SSM**, **port forwarding** ou **proxy** autenticado — **nunca** abrir portas à internet |
| **Metadata service** | **IMDSv2 obrigatório** (reduz roubo de credenciais) |
| **Egress** | Controlar com **Network Firewall/proxy** e **VPC endpoints** (evitar exfiltração) |
| **Segmentação** | **Subnets/SGs** por ambiente; **sem acesso** de dev a dados de prod |
| **Service Access SG** | Para clusters em **subnets privadas** (comunicação com o serviço EMR) |

### 7.2 EMR Block Public Access

Recurso **por região/conta** que **impede a criação de clusters** cujos **security groups permitam acesso de entrada público (0.0.0.0/0)** em portas, exceto **exceções permitidas** (ex.: porta 22 se necessário).

```bash
aws emr put-block-public-access-configuration --block-public-access-configuration \
  'BlockPublicSecurityGroupRules=true,PermittedPublicSecurityGroupRuleRanges=[{MinRange=22,MaxRange=22}]'
aws emr get-block-public-access-configuration
```

> **Boa prática:** habilitar **em todas as regiões** e **permitir exceções mínimas** (ou nenhuma). Use **SCP** para impedir sua desativação.

### 7.3 Acesso a notebooks e UIs

| Opção | Segurança |
|---|---|
| **EMR Studio** | Autenticação **IAM/Identity Center**, **Workspaces** isolados, **roles de serviço** e de usuário; **VPC e subnets** definidas |
| **JupyterHub no primary** | Autenticação **LDAP/PAM**, **TLS**; acesso por SSM/proxy |
| **Livy** | Ponto de integração; proteger com **Kerberos/TLS** |
| **Spark History/Persistent UI** | Acesso por **console/SSM** com IAM |

## 8. Auditoria e logs

| O que | Fonte |
|---|---|
| **Quem criou/alterou clusters e steps** | **CloudTrail** (`RunJobFlow`, `AddJobFlowSteps`, `TerminateJobFlows`, `PutBlockPublicAccessConfiguration`) |
| **Acesso a dados (S3)** | **CloudTrail data events** para buckets sensíveis; **S3 server access logs** |
| **Acesso por coluna/tabela** | **Lake Formation** (auditoria no CloudTrail) |
| **Logs de aplicação/cluster** | **S3** (`--log-uri`) e **CloudWatch Logs** (agente) |
| **Operações Kerberos/LDAP** | Logs do KDC/diretório (CloudWatch/SIEM) |
| **Mudanças de segurança** | **AWS Config** (regras para EMR: SG públicos, criptografia, logging; confirmar regras disponíveis) |
| **Atividade suspeita** | **GuardDuty** (CloudTrail/VPC DNS), **Macie** (dados sensíveis no S3) |

## 9. Governança e conformidade

| Tema | Prática |
|---|---|
| **Templates aprovados** | **Service Catalog/IaC** com security configuration, tags, auto-terminação e roles corretas |
| **Imagens/AMIs** | AMIs **endurecidas** e **atualizadas**; **imagens de contêiner** de repositório confiável (ECR) |
| **Bootstrap/libs** | **Repositório interno** (CodeArtifact/S3 versionado); sem `curl | bash` de origens externas |
| **Dados sensíveis** | **Classificação (Macie)**, **tokenização/mascaramento**, **Lake Formation** por coluna |
| **Retenção e residência** | Dados e logs **na região** exigida; **retenção** definida |
| **Segredos** | **Secrets Manager** (nunca em steps/notebooks); **IAM roles** para acesso |
| **Segregação** | Contas/ambientes separados (dev/hml/prod) |
| **Revisões** | Acessos, roles, clusters ativos, chaves, exceções (trimestral) |
| **LGPD/GDPR** | Mapear dados pessoais em jobs; **direito ao esquecimento** (Iceberg/Hudi **delete**); minimização |

## 10. Checklist de endurecimento

- [ ] **Roles customizadas** (service, instance profile, runtime/execution roles) com **menor privilégio**
- [ ] **`iam:PassRole`** restrito; permissão de criar clusters **limitada**
- [ ] **Security configuration** com **criptografia em repouso e em trânsito** e **KMS** (CMK)
- [ ] **Subnets privadas**, **VPC endpoints**, **IMDSv2**, SGs restritivos
- [ ] **EMR Block Public Access** habilitado em todas as regiões
- [ ] **Lake Formation** (ou Ranger/runtime roles) para autorização fina; **sem** acesso direto ao S3 contornando
- [ ] **Kerberos/LDAP** em clusters multiusuário; **EMR Studio + Identity Center**
- [ ] **Logs** no S3/CloudWatch + **CloudTrail** (incl. data events sensíveis) + **Config/GuardDuty/Macie**
- [ ] **Templates/IaC** com tags, auto-terminação e proteção
- [ ] **Sem segredos** em código; **Secrets Manager**
- [ ] **Imagens/AMIs** endurecidas e **bootstrap** de origem confiável
- [ ] **Revisão periódica** de acessos e exceções

## 11. Erros comuns

- **Roles default** em produção.
- **Instance profile único** com acesso a todos os dados.
- **`iam:PassRole` para `*`**.
- **UIs abertas** à internet (YARN/Hue/Jupyter).
- **Sem criptografia** em trânsito/repouso.
- **IMDSv1** habilitado.
- **Lake Formation configurado, mas usuários com acesso direto ao S3** (contorna).
- **Credenciais em notebooks** (chaves de acesso).
- **Bootstrap baixando scripts da internet** sem verificação.
- **Cluster compartilhado entre ambientes**.
- **Sem Block Public Access**.
- **Logs sensíveis** com dados pessoais sem proteção.

## 12. Troubleshooting

| Sintoma | Causa provável | Ação |
|---|---|---|
| `AccessDenied` no S3 | Role da instância/runtime sem permissão; política de bucket; KMS | Ajustar a role, a bucket policy e a key policy |
| Falha ao criar cluster por `iam:PassRole` | Permissão ausente ou ARN diferente | Conceder `PassRole` para as roles corretas |
| Lake Formation nega acesso esperado | Permissões do LF; user mapping; modo híbrido | Revisar grants e a configuração de integração |
| TLS entre nós falha | Certificados PEM inválidos/SAN incorretos | Regerar/validar os certificados |
| Kerberos: tickets expiram/falha de login | Relógio, KDC, realm, trust | Verificar NTP, KDC e configuração |
| Criação bloqueada por Block Public Access | SG com 0.0.0.0/0 | Restringir o SG ou ajustar a exceção |
| Notebook sem acesso a dados | Role do Studio/Workspace | Ajustar as permissões do Studio |
| Cluster em subnet privada sem comunicação | Falta de **Service Access SG**/endpoints/NAT | Configurar |

## 13. Resumo rápido

- **Roles**: **service role**, **EC2 instance profile**, **auto scaling role** — as **default são amplas**; use **roles customizadas**, **runtime roles (job-scoped)**, **IRSA/execution roles**.
- **`iam:PassRole`** restrito; **multi-tenancy** exige **isolamento** (clusters/Lake Formation/Ranger).
- **Security configuration**: **criptografia em repouso** (S3 SSE-KMS/CSE, EBS/LUKS, HDFS) e **em trânsito** (TLS) + **Kerberos**.
- **Autorização de dados**: **Lake Formation** (tabela/coluna/linha), **Ranger**, **runtime roles**.
- **Rede**: **subnets privadas**, **VPC endpoints**, **IMDSv2**, SGs restritos, **EMR Block Public Access**, acesso às UIs por **Studio/SSM**.
- **Auditoria**: **CloudTrail**, logs no S3/CloudWatch, **Config/GuardDuty/Macie**.
- **Governança**: **templates/IaC**, AMIs endurecidas, bootstrap confiável, segredos no **Secrets Manager**, revisões periódicas.

## 🧩 Quiz de Fixação

1. Quais são as três roles principais do EMR on EC2 e para que servem?
2. Por que as roles padrão não são adequadas para produção?
3. O que são runtime roles e que problema resolvem?
4. O que uma security configuration define?
5. Como o Lake Formation complementa o IAM no EMR?
6. Para que serve o EMR Block Public Access?
7. Por que exigir IMDSv2?

**Respostas:**

1. Service role (o EMR provisiona e gerencia o cluster), EC2 instance profile (as instâncias acessam dados e serviços) e Auto Scaling role (escala os instance groups).
2. Porque são amplas (por exemplo, acesso a S3 em geral), violando o menor privilégio e permitindo que qualquer job acesse dados demais.
3. São roles IAM por step/job (em vez da instance profile compartilhada), permitindo privilégio mínimo por carga, auditoria por identidade e multi-tenancy.
4. Criptografia em repouso e em trânsito e autenticação (como Kerberos), aplicadas na criação do cluster e reutilizáveis.
5. Dá permissões por banco, tabela, coluna e linha no Glue Data Catalog, valendo para vários serviços, com credenciais restritas ao que o principal pode ver.
6. Impedir a criação de clusters com security groups que permitam acesso público de entrada, exceto exceções explicitamente permitidas.
7. Porque reduz o risco de roubo de credenciais da role da instância por requisições (SSRF) ao serviço de metadados.
