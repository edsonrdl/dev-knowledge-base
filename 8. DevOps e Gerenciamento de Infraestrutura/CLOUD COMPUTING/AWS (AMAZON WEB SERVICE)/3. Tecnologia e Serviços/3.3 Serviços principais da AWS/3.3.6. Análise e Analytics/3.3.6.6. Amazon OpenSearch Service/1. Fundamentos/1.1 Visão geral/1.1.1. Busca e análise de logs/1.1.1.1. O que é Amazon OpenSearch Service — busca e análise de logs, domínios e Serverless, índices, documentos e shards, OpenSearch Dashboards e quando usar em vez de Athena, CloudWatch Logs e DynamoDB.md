### 1.1.1.1. O que é Amazon OpenSearch Service — busca e análise de logs, domínios e Serverless, índices, documentos e shards, OpenSearch Dashboards e quando usar em vez de Athena, CloudWatch Logs e DynamoDB

> [!warning] Aviso
> Versões, tipos de instância, limites, recursos (Serverless, vetores, zero-ETL) e preços abaixo são **de memória e mudam com frequência**. **Confirme na documentação do Amazon OpenSearch Service e na página de preços.** Comandos, consultas e JSONs são ilustrativos e **não foram executados**. Nomes de domínios, índices e contas são fictícios.

## 1. O problema que o OpenSearch resolve

Bancos relacionais e NoSQL são ótimos para **buscar por chave** ou por campos indexados, mas sofrem com perguntas como:

| Necessidade | Por que é difícil em um banco comum |
|---|---|
| **Busca de texto livre** (“notebook gamer barato”) | `LIKE '%termo%'` faz **varredura completa**; sem relevância, sem tolerância a erros de digitação |
| **Relevância e ranking** | Ordenar por **quão bem** o documento responde à busca |
| **Sugestões e autocompletar** | Exige estruturas especializadas (n-grams, prefixos) |
| **Análise de logs** em volume (milhões de eventos/min) | Buscar “erros 5xx do serviço X na última hora” com **filtros e agregações** rápidas |
| **Agregações em tempo quase real** | Contagens, histogramas, percentis sobre grandes volumes |
| **Busca semântica/vetorial** | Encontrar itens **parecidos** (embeddings) |
| **Observabilidade e segurança (SIEM)** | Correlacionar logs, métricas e traces |

O **Amazon OpenSearch Service** é o serviço **gerenciado** da AWS para **OpenSearch** (motor **de busca e análise distribuído**, derivado do Elasticsearch 7.10) e **OpenSearch Dashboards** (visualização, sucessor do Kibana). A AWS cuida de **provisionar, atualizar, escalar, fazer backup e monitorar** os clusters.

> [!info] Em uma frase
> **OpenSearch = “motor de busca e analytics sobre documentos JSON, para pesquisa de texto, logs, observabilidade e busca vetorial, gerenciado pela AWS”.**

## 2. Conceitos fundamentais

| Termo | Significado |
|---|---|
| **Documento** | Unidade de dados em **JSON** (um log, um produto, um pedido) |
| **Índice (index)** | Coleção de documentos com **mapeamento** (esquema) comum — análogo a uma “tabela” |
| **Mapeamento (mapping)** | Define **tipos dos campos** (text, keyword, date, long, geo_point, knn_vector…) e como são **indexados** |
| **Shard** | **Fatia** de um índice; cada shard é um **índice Lucene** completo; permite **paralelismo** |
| **Primary shard / replica** | Shard **primário** (grava) e **réplica** (cópia: **resiliência** e **leitura**) |
| **Nó (node)** | Instância do cluster; tipos: **dados**, **cluster manager (master)**, **ingestão**, **coordenação**, **warm/cold** |
| **Cluster / Domínio** | Conjunto de nós (no serviço, chamado **domínio**) |
| **Índice invertido** | Estrutura que mapeia **termo → documentos** (base da busca rápida) |
| **Analisador (analyzer)** | Quebra o texto em **tokens** (minúsculas, remoção de acentos, stemming) |
| **Query DSL** | Linguagem **JSON** de consulta |
| **Agregação** | Cálculos (contagem, soma, histograma, percentis) sobre resultados |
| **OpenSearch Dashboards** | Interface web: **Discover**, **Visualize**, **Dashboards**, **Dev Tools** |
| **Domain** (serviço) | A unidade gerenciada: cluster + configuração + endpoint |
| **Collection** (Serverless) | Agrupamento lógico de índices no **OpenSearch Serverless** |

### 2.1 Como a busca funciona (visão simplificada)

```
Documento JSON ──▶ Analisador (tokens) ──▶ ÍNDICE INVERTIDO
  "Notebook gamer rápido"      notebook → [doc1, doc7]
                               gamer    → [doc1, doc3]
                               rápido   → [doc1]
Consulta "notebook gamer" ──▶ interseção + pontuação de relevância (BM25) ──▶ resultados ordenados
```

### 2.2 Arquitetura distribuída

```
Índice "logs-2026.11.10"  (3 primary shards, 1 réplica cada)
   ┌─ Nó A: P0, R1 ─┐
   ├─ Nó B: P1, R2 ─┤   Escrita: vai ao primário do shard e replica
   └─ Nó C: P2, R0 ─┘   Leitura: qualquer cópia; coordenador agrega os resultados
Cluster manager (3 nós dedicados): estado do cluster, alocação de shards
```

## 3. Dois modelos do serviço

| | **OpenSearch Service (domínios)** | **OpenSearch Serverless** |
|---|---|---|
| **Gerenciamento** | **Você escolhe** tipos/quantidade de nós, EBS, AZs | **Sem clusters**: coleções com capacidade automática |
| **Controle** | **Alto** (shards, configurações, plugins permitidos) | Menor |
| **Unidade de cobrança** | **Instâncias/hora + armazenamento** | **OCUs** (OpenSearch Compute Units) **indexação/busca** + armazenamento |
| **Tipos de coleção** | n/a | **Search**, **Time series**, **Vector search** |
| **Escala** | Manual/planejada (e **Auto-Tune**) | **Automática** |
| **Quando** | Carga **previsível** e grande; **otimização de custo fina** | Carga **variável**; **simplicidade**; **sem administrar** |
| **Custo mínimo** | Depende do cluster | Há **mínimo de OCUs** (mesmo ocioso; confirmar) |

## 5. Quando usar (e quando não)

| Necessidade | Melhor escolha |
|---|---|
| **Busca full-text com relevância**, sugestões, facets | **OpenSearch** |
| **Logs com busca e dashboards interativos** | **OpenSearch** (ou CloudWatch Logs Insights para uso ocasional) |
| **SQL ad hoc sobre grandes volumes no S3, custo por consulta** | **Athena** |
| **Chave-valor/documento com latência previsível em escala** | **DynamoDB** |
| **Transações relacionais** | **RDS/Aurora** |
| **DW com BI de alta concorrência** | **Redshift** |
| **Logs de poucos serviços, consultas esporádicas** | **CloudWatch Logs Insights** |
| **Busca vetorial integrada a RAG** | **OpenSearch** (vector engine) ou **Aurora pgvector**/**Bedrock Knowledge Bases** |
| **Streaming + SQL contínuo** | **Kinesis/Flink** |
| **Banco principal de registro (source of truth)** | **Não use OpenSearch** (use RDS/DynamoDB; OpenSearch é um **índice derivado**) |

> [!warning] OpenSearch não é banco de registro
> Trate o OpenSearch como **índice secundário** de dados que **vivem em outro lugar** (S3, DynamoDB, RDS). Há **replicação eventual**, **sem transações multi-documento** e riscos operacionais (shards, memória) — **sempre** mantenha a **fonte da verdade** fora dele e saiba **reindexar**.

### 5.1 OpenSearch vs outros (comparação rápida)

| Critério | **OpenSearch** | **Athena** | **CloudWatch Logs Insights** | **DynamoDB** | **Redshift** |
|---|---|---|---|---|---|
| **Busca de texto/relevância** | **Excelente** | Fraca (LIKE/regex) | Básica | Não | Fraca |
| **Latência** | **Milissegundos–segundos** | Segundos–minutos | Segundos | **Milissegundos (chave)** | Segundos |
| **Dados** | Índices (cópia dos dados) | **No S3** (sem cópia) | Em CW Logs | Tabelas | Tabelas |
| **Modelo de custo** | **Cluster/OCU** | Por TB varrido | Por GB escaneado | Por requisição/capacidade | Por nó/RPU |
| **Melhor para** | Busca e logs interativos | SQL ocasional/lake | Diagnóstico pontual | Key-value/aplicações | DW/BI |

## 7. Visão geral do ciclo de uso

```
[1] Criar o domínio (ou coleção Serverless)  ─▶ [2] Definir índices/mapeamentos (ou templates)
[3] Ingerir dados (Firehose/Ingestion/agentes) ─▶ [4] Consultar (Query DSL/Dashboards)

```

## 9. Erros comuns

- **Usar OpenSearch como banco de registro** (sem fonte da verdade).
- **Shards demais ou de menos** (overhead ou gargalos) — ver folha de arquitetura.
- **Sem nós cluster manager dedicados** em produção.
- **Domínio de uma só AZ** para dados críticos.
- **Mapeamento dinâmico sem controle** (explosão de campos/“mapping explosion”).
- **Expor o domínio publicamente** com política aberta.
- **Reter logs indefinidamente em hot** (custo).
- **Sem snapshots** conhecidos/testados.
- **Escolher OpenSearch para consultas raras** que Athena/CloudWatch resolveriam por menos.
- **Ignorar a pressão de memória (JVM)**.

## 10. Troubleshooting inicial

| Sintoma | Causas prováveis | Ações |
|---|---|---|
| Cluster **amarelo/vermelho** | Réplicas/primários não alocados; disco cheio; nó perdido | Ver `_cluster/allocation/explain`; espaço; nós |
| Escrita rejeitada (`429`/`ThreadpoolWriteRejected`) | Sobrecarga de indexação | Reduzir taxa; aumentar nós; bulk adequado |
| Busca lenta | Muitos shards pequenos; consultas pesadas; pouca memória | Ajustar shards/queries; escalar |
| `ClusterBlockException` (somente leitura) | **Disco abaixo do watermark** | Liberar espaço/aumentar EBS; remover o bloqueio |
| `AccessDenied` / 403 | Política de acesso/FGAC/SigV4 | Revisar IAM, política do domínio e mapeamento de roles |
| Domínio inacessível | VPC/SG/endpoint | Ver rede e DNS |

## 11. Resumo rápido

- **OpenSearch Service** = **busca e análise** gerenciadas (OpenSearch + Dashboards): **full-text**, **logs/observabilidade**, **SIEM**, **geo**, **vetores/RAG**.
- **Conceitos**: documento JSON, **índice**, **mapeamento**, **shard primário/réplica**, **nós** (dados, cluster manager, warm/cold), **Query DSL**, **agregações**.
- **Dois modelos**: **domínios** (controle, instâncias) e **Serverless** (coleções, OCUs, automático).
- **Não é banco de registro**: índice derivado; **mantenha a fonte da verdade** e saiba **reindexar**.
- **Alternativas**: **Athena** (SQL no S3), **CloudWatch Logs Insights** (consultas pontuais), **DynamoDB** (chave-valor), **Redshift** (DW).
- **Ingestão**: **Firehose**, **OpenSearch Ingestion**, **CloudWatch Logs**, agentes.

## 🧩 Quiz de Fixação

1. Que tipo de necessidade o OpenSearch atende melhor que um banco relacional?
2. O que são shards primários e réplicas?
3. Qual a diferença entre domínios e OpenSearch Serverless?
4. Por que o OpenSearch não deve ser a fonte da verdade?
5. Quando preferir Athena a OpenSearch?
6. Cite duas formas de ingestão de logs no OpenSearch.
7. Para que serve o vector engine?

**Respostas:**

1. Busca de texto livre com relevância, sugestões, análise de logs com filtros e agregações rápidas e busca vetorial.
2. O primário recebe as escritas e a réplica é cópia para resiliência e leituras; cada shard é uma fatia do índice.
3. Em domínios você escolhe e gerencia nós, EBS e AZs; no Serverless a capacidade é automática em coleções cobradas por OCUs.
4. Porque é um índice derivado, com replicação eventual e sem transações multi-documento; a fonte da verdade deve estar em S3, DynamoDB ou RDS, com capacidade de reindexar.
5. Para consultas SQL ocasionais sobre dados no S3, pagando por TB varrido, sem manter cluster.
6. Kinesis Data Firehose, OpenSearch Ingestion, subscription do CloudWatch Logs ou agentes como Fluent Bit/Logstash (quaisquer duas).
7. Armazenar embeddings e executar busca por similaridade (k-NN) para busca semântica e RAG.
