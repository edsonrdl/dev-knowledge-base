### 4.1.1.1. Camadas de armazenamento e custos no OpenSearch — hot, UltraWarm e cold, Index State Management, snapshots, OpenSearch Serverless, instâncias reservadas e otimização

> [!warning] Aviso
> Preços, tipos de instância UltraWarm/cold, limites de tamanho, políticas ISM, retenção de snapshots automáticos e modelo de cobrança do Serverless (OCUs) abaixo são **de memória e mudam**. **Confirme na página de preços do OpenSearch Service e na documentação.** Valores monetários são **ordens de grandeza para raciocínio**, não cotação. Comandos e políticas são ilustrativos e **não foram executados**. Políticas ISM **excluem dados**: teste em índices de homologação.

## 1. Onde o dinheiro vai

Em clusters de logs e observabilidade, **80–90% do custo** costuma ser **armazenamento de dados antigos em nós hot** (instâncias caras com disco rápido), sendo que **a maioria das consultas olha só as últimas horas/dias**. A estratégia é **mover dados por camadas** e **expirar o que não é mais necessário**.

```
Idade do dado:    0 ─ 7 dias ───────▶ 7 ─ 90 dias ───────▶ 90 dias ─ 1 ano ──────▶ > 1 ano
Camada:           HOT                 WARM (UltraWarm)       COLD                   Snapshot (S3) / delete
Acesso:           frequente           ocasional              raro (anexar para consultar)   restaurar se preciso
Custo relativo:   $$$$$               $$                     $                      ¢
```

## 2. As camadas de armazenamento

### 2.1 Hot (nós de dados)

| Aspecto | Detalhe |
|---|---|
| **Onde** | **Nós de dados** (EBS gp3 ou NVMe local) |
| **Uso** | **Indexação ativa** e **consultas frequentes**/de baixa latência |
| **Custo** | **Mais alto** (instância + disco) |
| **Boas práticas** | Manter **só o necessário** (dias recentes); **rollover** de índices |

### 2.2 UltraWarm (warm)

| Aspecto | Detalhe (de memória — confirmar) |
|---|---|
| **O que é** | Camada de **nós warm** que armazena dados em **Amazon S3** com **cache local** |
| **Característica** | Índices em **somente leitura** (não indexa novos documentos) |
| **Custo** | **~até 90% menor** por GB que hot (S3 + nós warm de cache) |
| **Latência** | **Maior** que hot (primeira consulta puxa do S3), **aceitável** para análise histórica |
| **Requisitos** | **Cluster manager dedicado**; **versões/domínios compatíveis**; instâncias `ultrawarm1.*` |
| **Replicação** | Dados duráveis no S3 (réplicas locais não são necessárias para durabilidade) |
| **Uso** | **Logs históricos** de 7–90+ dias consultados ocasionalmente |
| **Opção Optimized (OR1/OM2)** | Famílias que usam **S3 como armazenamento primário** com **cache** (de memória); reduzem custo em **hot** de alto volume |

### 2.3 Cold storage

| Aspecto | Detalhe |
|---|---|
| **O que é** | Armazenamento **muito barato** em S3 **sem nós** associados |
| **Acesso** | **Não consultável** até **anexar** (attach) o índice a UltraWarm (leva minutos) |
| **Custo** | **Só armazenamento** (≈ preço de S3) |
| **Uso** | **Retenção longa** por **conformidade** com acesso **raro** |
| **Operação** | Mover de warm → cold via **ISM** ou API |

### 2.4 Comparação

| | **Hot** | **UltraWarm** | **Cold** | **Snapshot S3** |
|---|---|---|---|---|
| **Consulta** | Sim (rápida) | Sim (mais lenta) | **Não** (anexar antes) | **Não** (restaurar) |
| **Escrita** | Sim | **Não** | Não | — |
| **Custo** | $$$$ | $$ | $ | ¢ |
| **Disponibilidade de dados** | Imediata | Imediata (com cache frio) | Minutos para anexar | Restaurar = horas |
| **Uso** | Recente | Histórico recente | Compliance | Backup/DR/arquivo |

## 3. Index State Management (ISM)

O **ISM** automatiza o **ciclo de vida de índices** por **políticas de estados e transições**.

### 3.1 Conceitos

| Elemento | Função |
|---|---|
| **Policy** | Define **estados** (hot, warm, cold, delete), **ações** e **transições** |
| **Estado** | Fase do índice com **ações** (rollover, force_merge, replica_count, read_only, warm_migration, snapshot, delete) |
| **Transição** | Condição para passar ao próximo estado (**min_index_age**, **min_size**, **min_doc_count**) |
| **ISM template** | Associa **automaticamente** a política a **novos índices** por padrão de nome |
| **Rollover** | Cria **novo índice** quando atinge tamanho/idade (via alias/data stream) |

### 3.2 Exemplo de política (ilustrativo)

```json
PUT _plugins/_ism/policies/logs-ciclo-de-vida
{
  "policy": {
    "description": "hot 7d -> warm 30d -> cold 90d -> delete 365d",
    "default_state": "hot",
    "states": [
      { "name": "hot",
        "actions": [ { "rollover": { "min_size": "40gb", "min_index_age": "1d" } } ],
        "transitions": [ { "state_name": "warm", "conditions": { "min_index_age": "7d" } } ] },
      { "name": "warm",
        "actions": [ { "replica_count": { "number_of_replicas": 1 } }, { "force_merge": { "max_num_segments": 1 } }, { "warm_migration": {} } ],
        "transitions": [ { "state_name": "cold", "conditions": { "min_index_age": "30d" } } ] },
      { "name": "cold",
        "actions": [ { "cold_migration": { "timestamp_field": "@timestamp" } } ],
        "transitions": [ { "state_name": "delete", "conditions": { "min_index_age": "365d" } } ] },
      { "name": "delete", "actions": [ { "cold_delete": {} } ], "transitions": [] }
    ],
    "ism_template": [ { "index_patterns": ["logs-app-*"], "priority": 100 } ]
  }
}
```

(As ações exatas — `warm_migration`, `cold_migration`, `cold_delete` — dependem da versão; confirme os nomes na documentação.)

### 3.3 Boas práticas de ISM

1. **Rollover** por **tamanho** (≈ 30–50 GB por shard) **e** idade.
2. **Force merge** antes de mover para warm (reduz segmentos/armazenamento).
3. **Reduzir réplicas** em warm/cold conforme durabilidade no S3.
4. **Snapshot antes de delete** quando houver requisito de retenção legal.
5. **Testar** a política em um índice de homologação e **monitorar** o status (`_plugins/_ism/explain`).
6. **Alarmes** para índices com política **falhando** (`failed`).
7. Documentar **retenção por tipo de dado** (aprovada por jurídico/compliance).

## 4. Snapshots e backup

### 4.1 Automáticos e manuais

| Tipo | Detalhe (de memória — confirmar) |
|---|---|
| **Automatizados** | O serviço faz **snapshots horários** (retenção ~**14 dias**) **sem custo** adicional; úteis para **recuperação do domínio**; **não** acessíveis diretamente por você em alguns cenários (restaurar via API do serviço) |
| **Manuais** | Para **seu bucket S3** (repositório registrado com **role IAM**); **você controla** a frequência e a retenção |
| **Conteúdo** | Índices (e opcionalmente o **cluster state**) |
| **Incremental** | Snapshots posteriores só guardam **segmentos novos** |

### 4.2 Estratégia

| Cenário | Prática |
|---|---|
| **Disaster recovery** | Snapshots **manuais** em S3 com **replicação cross-region** do bucket |
| **Arquivar índices antigos** | Snapshot → **delete** do índice (restaurar quando necessário) |
| **Migração entre domínios/regiões** | Snapshot e **restore** no destino |
| **Compliance** | **Retenção** e **Object Lock** no bucket |
| **Teste** | **Restaurar periodicamente** em ambiente de teste (backup não testado não é backup) |

```json
PUT _snapshot/repo-s3
{ "type": "s3", "settings": { "bucket": "backups-opensearch-123456789012", "region": "us-east-1", "role_arn": "arn:aws:iam::123456789012:role/OpenSearchSnapshotRole" } }

PUT _snapshot/repo-s3/snap-2026-11-10
{ "indices": "logs-app-2026.10.*", "include_global_state": false }

POST _snapshot/repo-s3/snap-2026-11-10/_restore
{ "indices": "logs-app-2026.10.05", "rename_pattern": "(.+)", "rename_replacement": "restaurado-$1" }
```

## 5. OpenSearch Serverless: custos

### 5.1 Modelo de cobrança (de memória — confirmar)

| Componente | Cobrança |
|---|---|
| **OCUs de indexação** | **OCU-hora** de **indexação** (mínimos ao criar coleções; compartilháveis entre coleções) |
| **OCUs de busca** | **OCU-hora** de **busca** |
| **Armazenamento** | **GB-mês** (S3) |
| **Mínimo** | Há um **piso** de OCUs (ex.: **2 OCUs** indexação + **2 OCUs** busca, com opção **redundância desligada** em dev para reduzir; confirmar) → **custo fixo** mesmo ocioso |
| **Transferência** | Padrão AWS |

### 5.2 Serverless vs domínio (custo)

| Cenário | Mais barato tende a ser |
|---|---|
| **Carga pequena/variável/intermitente** | **Serverless** (sem pagar cluster ocioso), **se** o piso de OCUs for aceitável |
| **Carga constante e alta** | **Domínio** com instâncias **reservadas** e **UltraWarm** |
| **Muitos dados históricos** | **Domínio** com camadas (warm/cold) |
| **Dev/teste** | Domínio pequeno ou Serverless sem redundância |
| **Vetores** | Comparar memória: Serverless escala; domínio permite **quantização** e controle |

## 6. Instâncias reservadas e otimização de custos

### 6.1 Compra

| Opção | Detalhe |
|---|---|
| **On-Demand** | Flexível, mais caro |
| **Reserved Instances (1 ou 3 anos)** | **Desconto** significativo para **baseline estável** (hot + cluster managers + warm); **sem** conversível em alguns casos (confirmar) |
| **Savings Plans** | **Não** se aplicam diretamente ao OpenSearch (confirmar) |
| **Graviton** | **Melhor preço/desempenho** (frequentemente 10–30%) |
| **Rightsizing** | Revisar CPU/memória/disco; reduzir nós ociosos |

### 6.2 Checklist de economia

| Alavanca | Efeito |
|---|---|
| **UltraWarm/cold + ISM** | **Maior** redução de custo de armazenamento |
| **Retenção** definida | Apagar o que não tem valor |
| **Menos réplicas em dados frios** | Menos armazenamento |
| **Reduzir campos indexados** | Menos CPU/disco (`index: false` em campos só para exibição; `_source` filtrado) |
| **Desabilitar `_all`/campos inúteis**; `doc_values` só se necessário | Menos disco |
| **Compressão** (`best_compression` no codec) | Menos disco (mais CPU) |
| **Tamanho de shards** correto | Menos overhead |
| **Amostragem/filtragem** de logs na origem | Menos volume |
| **Escolha de instâncias** (r vs m; Graviton; OR1) | Melhor $/GB |
| **RIs** para baseline | −30–50% (ordem de grandeza) |
| **Tags e Budgets** | Visibilidade por equipe/ambiente |
| **Evitar over-provisioning** | Auto-Tune e métricas |
| **Consultas eficientes** | Menos CPU/nós |

### 6.3 Estimativa (raciocínio, **não cotação**)

```
Logs: 300 GB/dia, retenção total 180 dias, 1 réplica
Tudo em hot (dados + réplica): 300 × 2 × 180 = 108 TB  → dezenas de nós grandes → ordem de US$ 60–100 mil/mês (ilustrativo)

Com camadas:
  Hot 7 dias:      300 × 2 × 7  = 4,2 TB   (≈ 6–8 nós r6g)               ≈ US$ 8 mil
  UltraWarm 53 d:  300 × 53    = 15,9 TB  (S3 + nós warm ~ 3–4)          ≈ US$ 3–4 mil
  Cold 120 d:      300 × 120   = 36 TB    (S3 apenas)                    ≈ US$ 0,8–1 mil
  Total ilustrativo                                                       ≈ US$ 12–14 mil/mês   (~80% de economia)
```

## 7. Monitorar custos

- **Cost Explorer** por tag/serviço (instâncias, EBS, UltraWarm, transferência, Serverless OCUs).
- **Métricas**: `FreeStorageSpace`, `WarmStorageSpaceUtilization`, `ColdStorageSpaceUtilization`, uso de OCUs (Serverless).
- **Alarmes** de **crescimento de índices** inesperado (log verboso, loop).
- **Revisão mensal**: dados por camada, índices maiores, políticas ISM, campos caros.

## 8. Erros comuns

- **Tudo em hot** por meses.
- **Sem ISM** (retenção manual/esquecida).
- **Policy de delete sem snapshot** quando há requisito de retenção.
- **Cold sem processo de attach** documentado.
- **Réplicas excessivas** em dados antigos.
- **Serverless para carga constante gigante** sem comparar o custo.
- **Esquecer o piso de OCUs** do Serverless.
- **Snapshots nunca testados**.
- **Indexar todos os campos** (inclusive os que nunca são pesquisados).
- **Sem RIs** em baseline estável.
- **Warm sem cluster manager dedicado** (requisito).

## 9. Troubleshooting

| Sintoma | Causa provável | Ação |
|---|---|---|
| Índice não migra para warm | Política ISM falhou; requisitos (cluster manager dedicado/versão); índice com réplicas/estado | `_plugins/_ism/explain`; corrigir |
| ISM “travado” em `failed` | Ação inválida/permissão/estado do índice | Ver a mensagem; `retry` |
| Consulta em warm lenta | Cache frio; consulta pesada | Esperar o cache; reduzir o escopo; usar hot para o recente |
| Índice cold não consulta | Não anexado | Anexar a UltraWarm |
| Disco hot enchendo | Rollover/transição falhando | Corrigir ISM; escalar temporariamente |
| Restore de snapshot falha | Repositório/role/versão incompatível | Ver o repositório e a compatibilidade de versões |
| Custo Serverless alto | OCUs altos por picos/consultas | Limitar capacidade; otimizar consultas/ingestão |
| Fatura sobe sem crescimento aparente | Réplicas, logs verbosos, índices órfãos | Auditar índices e retenção |

## 10. Resumo rápido

- **Camadas**: **Hot** (nós de dados, rápido, caro) → **UltraWarm** (S3 + cache, somente leitura, ~90% mais barato) → **Cold** (só S3; anexar para consultar) → **Snapshot/delete**.
- **ISM**: políticas de **estados e transições** (rollover, force merge, réplicas, warm/cold migration, delete) com **ISM templates**; monitore com `explain`.
- **Snapshots**: **automáticos** (horários, ~14 dias) e **manuais em S3** (retenção/DR/migração); **teste a restauração**.
- **Serverless**: cobra **OCUs (indexação/busca)** + armazenamento, com **piso**; bom para carga **variável**.
- **Economia**: **camadas + retenção**, **menos réplicas em dados frios**, **campos indexados mínimos**, **Graviton**, **RIs** para baseline, **shards certos**.
- **Maior alavanca**: **não manter tudo em hot**.

## 🧩 Quiz de Fixação

1. Qual a principal diferença entre UltraWarm e cold?
2. Para que serve o ISM?
3. Por que fazer force merge antes de mover para warm?
4. Qual a diferença entre snapshots automáticos e manuais?
5. Quando o OpenSearch Serverless pode sair mais caro que um domínio?
6. Cite três alavancas de redução de custo além das camadas.
7. Por que testar a restauração de snapshots?

**Respostas:**

1. UltraWarm é consultável diretamente (somente leitura, S3 com cache); cold só tem armazenamento em S3 e precisa ser anexado para consultar.
2. Automatizar o ciclo de vida dos índices por estados e transições (rollover, warm, cold, delete), com políticas aplicadas por templates.
3. Reduz o número de segmentos, diminuindo armazenamento e melhorando a eficiência das consultas.
4. Automáticos são feitos pelo serviço (horários, retenção curta, sem custo) para recuperação; manuais vão para o seu bucket S3, com controle de frequência e retenção.
5. Em cargas constantes e grandes (ou com muitos dados históricos), onde instâncias reservadas e UltraWarm/cold são mais baratas, além do piso de OCUs.
6. Reduzir réplicas em dados frios, indexar menos campos, usar Graviton, Reserved Instances, compressão, shards corretos ou filtrar logs na origem (quaisquer três).
7. Porque um backup não testado pode falhar na hora de recuperar (repositório, permissões, versões); o teste valida o RTO e o processo.
