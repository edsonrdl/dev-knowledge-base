### 3.1.1.1. Ingestão e consultas no OpenSearch — mapeamentos, Query DSL, busca full-text, agregações, OpenSearch Ingestion, Firehose, CloudWatch Logs, vetores e k-NN

> [!warning] Aviso
> Sintaxe de Query DSL, tipos de campo, parâmetros de k-NN, recursos do OpenSearch Ingestion e conectores abaixo são **de memória e mudam entre versões**. **Confirme na documentação do OpenSearch e do OpenSearch Service para a versão do seu domínio.** Consultas, mapeamentos e comandos são ilustrativos e **não foram executados**. Use dados de teste; nunca indexe dados pessoais reais sem base legal e controles.

## 1. O caminho do dado: da origem à resposta

```
Fontes (apps, logs, S3, DynamoDB, Kafka)
      │ ingestão
      ▼
Pipeline (Firehose / OpenSearch Ingestion / agentes) ──▶ Índice (mapeamento + analisadores)
                                                           │ busca/agregação
                                                           ▼
                                           Aplicação (API) / Dashboards / Alertas
```

Duas decisões estruturam tudo: **como modelar o índice** (mapeamento) e **como ingerir** (volume, latência, transformação).

## 2. Mapeamentos e tipos de campo

### 2.1 Por que mapear explicitamente

O OpenSearch pode **inferir tipos automaticamente** (**dynamic mapping**), mas isso gera **surpresas**: um campo numérico vira `text`, um objeto com chaves variáveis cria **milhares de campos** (“**mapping explosion**”), e a **busca** perde precisão. **Defina mapeamentos explícitos** (via **index templates**).

### 2.2 Tipos principais

| Tipo | Uso | Observação |
|---|---|---|
| **`text`** | **Busca full-text** (analisado em tokens) | Não serve para agregações/ordenação (use `keyword`/multi-field) |
| **`keyword`** | **Valores exatos** (IDs, status, tags), **filtros, agregações, ordenação** | Não analisado |
| **`date`** | Datas/timestamps | Formato definido |
| **`long/integer/double/float`** | Números | Escolher o menor tipo suficiente |
| **`boolean`** | Booleanos | — |
| **`ip`** | Endereços IP | Consulta por CIDR |
| **`geo_point/geo_shape`** | Geoespacial | Buscas por distância/polígono |
| **`object` / `nested`** | JSON aninhado | `nested` preserva a relação entre campos de itens de lista (custo maior) |
| **`knn_vector`** | **Vetores** (embeddings) | Para busca por similaridade |
| **`flat_object`** | Objetos com chaves variáveis | Evita explosão de campos |

### 2.3 Multi-fields (texto + keyword)

```json
PUT _index_template/produtos-tpl
{
  "index_patterns": ["produtos-*"],
  "template": {
    "settings": { "number_of_shards": 3, "number_of_replicas": 1 },
    "mappings": {
      "dynamic": "strict",
      "properties": {
        "nome":      { "type": "text", "analyzer": "portuguese",
                       "fields": { "raw": { "type": "keyword", "ignore_above": 256 } } },
        "categoria": { "type": "keyword" },
        "preco":     { "type": "scaled_float", "scaling_factor": 100 },
        "criado_em": { "type": "date" },
        "tags":      { "type": "keyword" }
      }
    }
  }
}
```

`"dynamic": "strict"` **rejeita** campos não declarados (evita explosão); use `"false"` para **ignorar** campos extras sem indexá-los.

### 2.4 Analisadores

| Componente | Função |
|---|---|
| **Character filters** | Pré-processam o texto (remover HTML) |
| **Tokenizer** | Quebra em tokens (`standard`, `whitespace`, `ngram`) |
| **Token filters** | **Lowercase**, remoção de **stopwords**, **stemming**, **asciifolding** (acentos), **sinônimos** |
| **Analisadores prontos** | `standard`, `portuguese`, `english`… |
| **Autocomplete** | `edge_ngram` ou `completion suggester` |

Usar o **mesmo analisador** (ou compatível) na **indexação e na busca**, salvo casos específicos.

## 3. Query DSL: consultas

### 3.1 Estrutura de uma busca

```json
GET /produtos/_search
{
  "query": {
    "bool": {
      "must":     [ { "match": { "nome": "notebook gamer" } } ],            // afeta a relevância (score)
      "filter":   [ { "term": { "categoria": "informatica" } },
                    { "range": { "preco": { "gte": 3000, "lte": 7000 } } } ], // sem score, cacheável
      "should":   [ { "match": { "nome": { "query": "rtx", "boost": 2 } } } ],
      "must_not": [ { "term": { "tags": "descontinuado" } } ]
    }
  },
  "sort": [ "_score", { "preco": "asc" } ],
  "from": 0, "size": 20,
  "_source": ["nome", "preco"]
}
```

| Cláusula | Significado |
|---|---|
| **`must`** | Deve casar; **contribui ao score** |
| **`filter`** | Deve casar; **sem score**; **mais rápido** e cacheável — **preferir para filtros exatos** |
| **`should`** | Opcional; **aumenta** o score (ou obrigatório conforme `minimum_should_match`) |
| **`must_not`** | Exclui |

### 3.2 Tipos de consulta comuns

| Consulta | Uso |
|---|---|
| **`match`** | Full-text em um campo `text` |
| **`multi_match`** | Full-text em vários campos (com pesos) |
| **`match_phrase`** | Frase exata em ordem |
| **`term` / `terms`** | Valor **exato** em `keyword`/número |
| **`range`** | Intervalos (datas, números) |
| **`prefix`/`wildcard`/`regexp`** | Padrões (**custo alto**; evitar em campos grandes) |
| **`fuzzy`** | Tolerância a erros de digitação |
| **`exists`** | Campo presente |
| **`query_string`/`simple_query_string`** | Sintaxe de consulta para usuários avançados |
| **`function_score`** | Ajustar relevância (popularidade, recência) |
| **`geo_distance`** | Proximidade geográfica |
| **`knn`** | **Similaridade vetorial** |

### 3.3 Relevância (BM25)

O score combina **frequência do termo no documento** (TF), **raridade do termo** no índice (IDF) e **tamanho do campo**. Ajuste com **boosts**, **multi_match** com pesos, **function_score** e **sinônimos**. Teste com **conjunto de consultas reais** e métricas (precisão@k, nDCG).

### 3.4 Paginação

| Técnica | Uso | Limite |
|---|---|---|
| **`from` + `size`** | Páginas rasas | Limitado (`index.max_result_window`, 10.000); caro em páginas fundas |
| **`search_after`** | **Paginação profunda** eficiente (com ordenação estável) | Recomendado |
| **Scroll** | Exportação em lote (legado) | Use **PIT + search_after** |
| **Point in Time (PIT)** | Visão consistente durante a paginação | Prefira a scroll |

## 4. Agregações (analytics)

```json
GET /logs-aplicacao-*/_search
{
  "size": 0,
  "query": { "range": { "@timestamp": { "gte": "now-1h" } } },
  "aggs": {
    "por_status": { "terms": { "field": "http.status" } },
    "p95_latencia": { "percentiles": { "field": "latencia_ms", "percents": [50, 95, 99] } },
    "por_minuto": { "date_histogram": { "field": "@timestamp", "fixed_interval": "1m" },
        "aggs": { "erros": { "filter": { "range": { "http.status": { "gte": 500 } } } } } }
  }
}
```

| Tipo | Exemplos |
|---|---|
| **Bucket** | `terms`, `date_histogram`, `range`, `histogram`, `filters`, `geohash_grid` |
| **Metric** | `sum`, `avg`, `min`, `max`, `cardinality` (aprox.), `percentiles`, `stats` |
| **Pipeline** | `derivative`, `moving_avg`, `bucket_script` |

Dicas: agregar em campos **`keyword`/numéricos** (doc values), **evitar cardinalidades gigantes** (`terms` em campo de alta cardinalidade), usar `size: 0` quando só quer agregações, **filtrar antes** de agregar.

### 4.1 SQL e PPL

O OpenSearch oferece **SQL** e **PPL (Piped Processing Language)** para quem prefere esses estilos (plugins); úteis em **Dashboards/Query Workbench** e investigações.

```sql
SELECT http.status, COUNT(*) AS total FROM logs-aplicacao-* WHERE "@timestamp" > NOW() - INTERVAL 1 HOUR GROUP BY http.status
```

## 5. Ingestão de dados

### 5.1 Opções

| Opção | Descrição | Quando |
|---|---|---|
| **Bulk API** | Enviar **muitos documentos** por requisição (`_bulk`) | Cargas e integrações próprias; **lotes de 5–15 MB** |
| **Amazon Kinesis Data Firehose** | **Entrega gerenciada** com buffer, **transformação Lambda**, **backup S3** de falhas | **Logs/streams** sem servidor próprio |
| **OpenSearch Ingestion (OSI)** | **Data Prepper gerenciado**: pipelines com **fontes** (S3, Kafka/MSK, OTel, HTTP, DynamoDB), **processadores** (grok, rename, drop), **sinks** | **Pipelines ricos**, trace analytics, S3→OpenSearch |
| **CloudWatch Logs subscription** | Encaminha log groups ao OpenSearch (via Lambda gerenciada/Firehose) | Logs AWS |
| **Fluent Bit / Fluentd / Logstash / Beats** | Agentes em hosts/containers | Ambientes com agentes |
| **OpenTelemetry Collector** | Traces/metrics/logs → OSI/OpenSearch | Observabilidade |
| **DynamoDB zero-ETL** | Indexa tabelas DynamoDB automaticamente (confirmar disponibilidade) | Busca sobre dados do DynamoDB |
| **S3 (ingestão/Direct Query)** | Carregar objetos do S3 por OSI/Lambda; **consultas diretas** sobre S3 (confirmar) | Data lake + busca |
| **AWS Lambda/DMS/Glue** | Transformações e cargas customizadas | Integrações específicas |

### 5.2 Bulk API (boas práticas)

```json
POST _bulk
{ "index": { "_index": "logs-aplicacao-2026.11.10", "_id": "evt-1001" } }
{ "@timestamp": "2026-11-10T10:00:01Z", "servico": "pedidos", "nivel": "ERROR", "mensagem": "timeout no pagamento", "latencia_ms": 5200 }
{ "index": { "_index": "logs-aplicacao-2026.11.10" } }
{ "@timestamp": "2026-11-10T10:00:02Z", "servico": "pedidos", "nivel": "INFO", "mensagem": "pedido criado", "latencia_ms": 85 }
```

| Prática | Detalhe |
|---|---|
| **Tamanho do lote** | **5–15 MB** ou milhares de documentos; testar |
| **Concorrência** | Vários workers, com **backoff** em `429` |
| **IDs** | `_id` determinístico para **idempotência**; IDs automáticos para logs |
| **Refresh interval** | Aumentar (`30s`) ou desligar em **cargas em massa** (`-1`), restaurar depois |
| **Réplicas durante a carga** | Zerar na carga inicial e **restaurar** depois (se aceitável) |
| **Tratamento de erros** | Inspecionar `errors`/`items` da resposta bulk |
| **Compressão** | Gzip nas requisições |

### 5.3 Fluxo típico para logs

```
Aplicação ─▶ Fluent Bit/CloudWatch Agent ─▶ Kinesis Data Firehose ─▶ OpenSearch  (falhas ─▶ S3)
                                         └─▶ (alternativa) OpenSearch Ingestion com processadores e roteamento
Índices: logs-<serviço>-YYYY.MM.dd  (ou data streams)  + templates + ISM (rollover/retenção)
```

### 5.4 Data streams e rollover

**Data streams** gerenciam **séries temporais append-only** com **índices de apoio** (backing indices) e **rollover** automático:

```json
PUT _index_template/logs-tpl
{ "index_patterns": ["logs-app*"], "data_stream": {},
  "template": { "settings": { "number_of_shards": 3, "number_of_replicas": 1 } } }
PUT _data_stream/logs-app
```

Combina com **ISM** (próxima folha) para **rollover por tamanho/idade** e **retenção**.

## 6. Busca vetorial e k-NN

### 6.1 O que é

**Embeddings** (vetores numéricos que representam significado de textos/imagens) permitem **busca semântica**: encontrar itens **semelhantes** mesmo sem palavras em comum.

```
Texto ──▶ Modelo de embeddings (Bedrock/SageMaker) ──▶ vetor [0.12, −0.5, …] (ex.: 1024 dimensões)
Consulta ──▶ mesmo modelo ──▶ vetor ──▶ k vizinhos mais próximos no índice (k-NN)
```

### 6.2 Mapeamento e consulta

```json
PUT /base-conhecimento
{
  "settings": { "index": { "knn": true } },
  "mappings": { "properties": {
     "texto":   { "type": "text" },
     "vetor":   { "type": "knn_vector", "dimension": 1024,
                  "method": { "name": "hnsw", "space_type": "cosinesimil", "engine": "faiss",
                              "parameters": { "m": 16, "ef_construction": 128 } } },
     "fonte":   { "type": "keyword" } } }
}

GET /base-conhecimento/_search
{ "size": 5, "query": { "knn": { "vetor": { "vector": [0.12, -0.5, ...], "k": 5 } } } }
```

| Elemento | Detalhe (de memória — confirmar) |
|---|---|
| **Algoritmos** | **HNSW** (grafo; rápido, mais memória), **IVF** (clusters; menos memória); **motores** `faiss`, `nmslib`, `lucene` |
| **Métrica** | `cosinesimil`, `l2`, `innerproduct` |
| **Memória** | Grafos HNSW **residem em RAM**: dimensionar **instâncias** pela quantidade de vetores × dimensão; **quantização** (FP16/byte/binária) reduz memória |
| **Filtros** | **Pré/pós-filtro** com `knn` + filtros (eficiente em certos motores) |
| **Busca híbrida** | **Lexical (BM25) + vetorial** com combinação de scores (**hybrid query**/**search pipeline**) — frequentemente **melhor** que só vetor |
| **RAG** | Recuperar trechos → fornecer a um **LLM** (Bedrock) como contexto |
| **Serverless vector collection** | Coleções **Vector search** sem gerenciar nós |

### 6.3 Pipeline de RAG com OpenSearch

```
Documentos ──▶ Chunking ──▶ Embeddings (Bedrock Titan/Cohere) ──▶ Índice knn_vector (OpenSearch)
Pergunta ──▶ Embedding ──▶ k-NN (+ filtros/híbrida) ──▶ Trechos ──▶ Prompt ao LLM ──▶ Resposta com fontes
```

Alternativa gerenciada: **Amazon Bedrock Knowledge Bases** usando OpenSearch (Serverless/domínios) como **vector store**.

## 7. Boas práticas de modelagem e consulta

1. **Mapeamentos explícitos** e `dynamic: strict`.
2. **`keyword` para filtros/agregações**, `text` para busca; **multi-fields** quando precisar de ambos.
3. **Filtrar com `filter`** (sem score, cacheável).
4. **Evitar wildcards** com prefixo curinga e `regexp` pesados.
5. **Evitar `nested`** quando possível (custo); desnormalizar.
6. **Limitar o `size`** e usar **`search_after`** para paginar fundo.
7. **Agregações** só em campos com **doc values**; cuidado com **alta cardinalidade**.
8. **Índices por tempo** (data streams) + **ISM**.
9. **Reindexar** quando mudar mapeamentos (use **aliases** para troca sem downtime).
10. **Testar relevância** com consultas reais.

### 7.1 Aliases e reindexação sem downtime

```json
POST _aliases { "actions": [ { "add": { "index": "produtos-v2", "alias": "produtos" } }, { "remove": { "index": "produtos-v1", "alias": "produtos" } } ] }
POST _reindex { "source": { "index": "produtos-v1" }, "dest": { "index": "produtos-v2" } }
```

A aplicação consulta o **alias** `produtos`; trocar o alias muda o índice **sem alterar o código**.

## 8. Erros comuns

- **Dynamic mapping** em dados de origem variável (explosão de campos).
- **`text` para filtros exatos** (retorna resultados inesperados).
- **Deep pagination com `from`** (lento/limitado).
- **Bulk com lotes minúsculos** (overhead) ou gigantes (timeouts).
- **Refresh interval padrão em carga massiva** (lento).
- **Sem tratar `429`** (perda de dados).
- **Wildcard `*termo*`** em campos grandes.
- **Ignorar a memória de k-NN**.
- **Ingerir dados sensíveis sem mascarar**.
- **Trocar mapeamento sem reindexar** (não é possível alterar o tipo de um campo existente).

## 9. Troubleshooting

| Sintoma | Causa provável | Ação |
|---|---|---|
| Busca não acha termo existente | Analisador/`text` vs `keyword`; acentos | Verificar o analisador e o campo; `_analyze` |
| Erro de mapeamento ao indexar | Tipo conflitante; `strict` | Corrigir o payload/mapeamento; reindex |
| `429 Too Many Requests` | Sobrecarga de indexação | Backoff; reduzir a concorrência; escalar |
| Agregação lenta/erro de memória | Alta cardinalidade; fielddata em `text` | Usar `keyword`; reduzir cardinalidade |
| Resultados fora de ordem | Score vs sort; tipo do campo | Definir `sort`; checar o tipo |
| k-NN retorna pouco/impreciso | `k`/`ef_search` baixos; dimensão errada | Ajustar parâmetros; validar embeddings |
| Dados não aparecem | `refresh_interval`; falha de ingestão | Aguardar/forçar refresh; ver logs do pipeline/DLQ |
| Pipeline do OSI falhando | Permissões/formato/destino | Ver métricas e logs do pipeline |

## 10. Resumo rápido

- **Mapeamento explícito** (`dynamic: strict`), **`text` vs `keyword`**, **multi-fields**, **analisadores** (ex.: `portuguese`), **`knn_vector`** para embeddings.
- **Query DSL**: `bool` (`must`/`filter`/`should`/`must_not`); **`filter`** = sem score e cacheável; **BM25**; **`search_after`/PIT** para paginação funda.
- **Agregações**: bucket, metric, pipeline; cuidado com **alta cardinalidade**; **SQL/PPL** disponíveis.
- **Ingestão**: **Bulk**, **Firehose**, **OpenSearch Ingestion**, **CloudWatch Logs**, agentes, **DynamoDB zero-ETL**, S3; **data streams + rollover**.
- **Vetores/RAG**: **HNSW/IVF**, métricas, **memória em RAM**, **busca híbrida**; **Bedrock Knowledge Bases**.
- **Aliases + reindex** para evoluir esquemas sem downtime.

## 🧩 Quiz de Fixação

1. Qual a diferença entre `text` e `keyword`?
2. Por que preferir `filter` a `must` para critérios exatos?
3. Que problema o `dynamic: strict` evita?
4. Quando usar `search_after` em vez de `from/size`?
5. Cite três formas de ingerir logs no OpenSearch.
6. Por que a busca híbrida costuma superar só vetores?
7. Como alterar o mapeamento de um campo existente sem downtime?

**Respostas:**

1. `text` é analisado em tokens para busca full-text; `keyword` guarda o valor exato para filtros, agregações e ordenação.
2. Porque `filter` não calcula score, é mais rápido e pode ser cacheado.
3. A explosão de mapeamento e tipos inferidos incorretamente, rejeitando campos não declarados.
4. Para paginação profunda, pois `from/size` é caro e limitado (max_result_window).
5. Kinesis Data Firehose, OpenSearch Ingestion, CloudWatch Logs subscription, Fluent Bit/Logstash ou Bulk API (quaisquer três).
6. Combina correspondência lexical (termos exatos, siglas, nomes) com semelhança semântica, cobrindo casos que cada abordagem isolada perde.
7. Criar um novo índice com o mapeamento correto, reindexar e trocar o alias que a aplicação usa.
