### 1.1.1.1. O que é Amazon Cognito — user pools, identity pools, tokens JWT, autenticação vs autorização e quando usar em vez de IAM, Identity Center ou IdP próprio

> [!warning] Aviso
> Os comandos de CLI, JSONs, limites, planos e preços deste material são **ilustrativos, de memória e não foram executados**. O Cognito mudou bastante recentemente (novos **planos de recursos** Lite/Essentials/Plus, **Managed Login**, **passkeys**, cobrança de M2M). **Confirme limites, quotas e preços na documentação oficial e na página de preços** antes de projetar ou orçar. Valores em dólar são ordens de grandeza.

## 1. O problema que o Cognito resolve

Toda aplicação com usuários precisa de uma camada de identidade: **cadastro, login, recuperação de senha, verificação de e-mail/telefone, MFA, login social (Google, Apple, Facebook), federação com o IdP da empresa (SAML/OIDC), bloqueio de contas suspeitas e emissão de tokens**. Construir isso do zero é caro e perigoso: armazenar senhas com hash correto, tratar força bruta, expirar sessões, rotacionar chaves de assinatura, cumprir LGPD/GDPR. Erros nessa camada viram **vazamentos de dados**.

O **Amazon Cognito** é o serviço gerenciado de **identidade de clientes (CIAM — Customer Identity and Access Management)** da AWS. Ele oferece:

1. Um **diretório de usuários** escalável (milhões de usuários), com **sign-up/sign-in** prontos.
2. **Federação** com provedores externos (social, SAML, OIDC).
3. **Tokens padrão** (JWT, OAuth 2.0/OIDC) que o seu backend e o API Gateway sabem validar.
4. **Credenciais temporárias da AWS** para que usuários finais acessem **diretamente** serviços AWS (S3, DynamoDB, IoT...) com permissões mínimas.

```
 Usuário final (web, mobile)
        │ login / cadastro / social / SAML
        ▼
  ┌──────────────────────┐   JWT (ID/Access/Refresh)   ┌──────────────────┐
  │  COGNITO USER POOL   │ ───────────────────────────▶│  Seu backend /   │
  │  (quem é o usuário?) │                             │  API Gateway     │
  └──────────┬───────────┘                             └──────────────────┘
             │ token
             ▼
  ┌──────────────────────┐   credenciais temporárias   ┌──────────────────┐
  │ COGNITO IDENTITY POOL│ ───────────────────────────▶│ S3, DynamoDB,    │
  │ (o que pode acessar?)│    (STS, role IAM)          │ IoT, AppSync...  │
  └──────────────────────┘                             └──────────────────┘
```

## 2. Os dois componentes (a confusão mais comum)

O Cognito tem **duas peças independentes**, frequentemente combinadas. Confundi-las é o erro número um em provas e em projetos.

| Característica | **User Pool** | **Identity Pool** (Federated Identities) |
|---|---|---|
| **Pergunta que responde** | **Quem é você?** (autenticação) | **O que você pode fazer na AWS?** (autorização AWS) |
| **O que é** | **Diretório** de usuários e **provedor de identidade (IdP/OIDC)** | **Trocador** de tokens por **credenciais AWS temporárias** |
| **Entrega** | **Tokens JWT** (ID, access, refresh) | **Access key/secret/session token** (via STS) |
| **Guarda usuários?** | **Sim** (com atributos, grupos, MFA) | **Não** (só mapeia identidades para roles) |
| **Aceita** | Senha, social, SAML, OIDC | Tokens de user pool, social, SAML, OIDC, **desenvolvedor autenticado**, **convidados (guest)** |
| **Uso típico** | Login de app; **API Gateway** e **ALB** validam o token | App mobile que sobe **fotos direto no S3**; leitura de DynamoDB por usuário |
| **Integra com** | API Gateway, ALB, AppSync, Amplify | IAM (roles), STS |

Regra de memória: **User pool = login (JWT)**. **Identity pool = acesso a recursos AWS (credenciais)**. Muitas aplicações usam **só o user pool** (API protegida por JWT). Use o **identity pool** apenas quando o **cliente precisa chamar serviços AWS diretamente**.

## 3. Autenticação vs autorização no ecossistema AWS

| Conceito | Quem resolve no Cognito | Exemplos |
|---|---|---|
| **Autenticação** (provar quem é) | **User pool** | Senha, MFA, login social, SAML |
| **Autorização na sua API** (o que pode na aplicação) | **Claims/grupos/escopos do JWT** + sua lógica | `cognito:groups = ["admin"]`, escopo `pedidos:read` |
| **Autorização na AWS** (o que pode nos serviços AWS) | **Identity pool + roles IAM** | Role que permite `s3:PutObject` só no prefixo do usuário |

## 4. Tokens (visão inicial)

O user pool emite **três tokens JWT** após o login:

| Token | Conteúdo | Para que usar |
|---|---|---|
| **ID token** | **Identidade** do usuário (claims: `sub`, `email`, `cognito:username`, grupos, atributos) | Mostrar dados do usuário no app; autenticar no Cognito authorizer |
| **Access token** | **Autorização** (escopos, grupos, `client_id`) | **Chamar APIs** (Bearer); autorizar no API Gateway/JWT authorizer |
| **Refresh token** | Credencial de **longa duração** (opaca) | **Obter novos** ID/access sem novo login |

Detalhes (validade, assinatura, claims, revogação) estão na folha de tokens e OAuth.

## 5. Planos de recursos (feature plans) e custo (visão geral)

O Cognito passou a oferecer **planos de recursos** por user pool (confirme os nomes e o que cada um inclui):

| Plano | Para quem | Ideia |
|---|---|---|
| **Lite** | Necessidades básicas, baixo custo | Login simples, recursos essenciais |
| **Essentials** | Maioria dos apps | Managed Login, MFA, passkeys, access token customization etc. |
| **Plus** | Alta segurança | **Threat protection** (adaptive auth, credenciais comprometidas), logs avançados |

A cobrança é principalmente por **MAU (Monthly Active Users)** — usuários que fizeram login/ativos no mês — com **faixas decrescentes**, e há **cobrança à parte** para **M2M** (clientes de máquina com `client_credentials`), **SMS/e-mail** (SNS/SES), **identity pool** (sem custo por si, mas credenciais STS) e **recursos de segurança avançados**. Há um **nível gratuito de MAUs** (ordem de dezenas de milhares no plano Essentials/Lite, conforme as regras vigentes).

Exemplo de ordem de grandeza: 100.000 MAUs → custo mensal na faixa de centenas de dólares no plano Essentials; muito inferior ao de **construir e operar** um IdP próprio com segurança equivalente.

## 6. Quando usar Cognito vs alternativas

| Necessidade | Opção | Observação |
|---|---|---|
| Login de **clientes finais** de app web/mobile, escalável e barato | **Cognito user pool** | Foco em CIAM |
| **Força de trabalho** acessando contas AWS e apps corporativos (SSO) | **IAM Identity Center** | Funcionários, não clientes |
| Acesso de **máquinas/serviços AWS** entre si | **IAM roles/STS** | Sem usuários finais |
| Já existe IdP (Okta, Entra ID, Auth0) e a aplicação só valida tokens | **JWT authorizer + IdP** (Cognito opcional via federação) | Evita duplicar usuários |
| Necessidade avançada de **personalização total de UI/fluxos**, extensibilidade de CIAM enterprise | **Auth0/Okta CIC/Keycloak** | Cognito tem personalização limitada |
| Usuários finais precisam ler/gravar **direto** no S3/DynamoDB | **Cognito Identity Pool** (+ user pool) | Credenciais temporárias de menor privilégio |
| Backend próprio com API Gateway | **Cognito user pool + Cognito/JWT authorizer** | Padrão serverless |
| Sistema legado com diretório AD | **Directory Service / Identity Center / federação SAML** | Cognito pode federar via SAML |

Heurística: **Cognito para clientes (B2C/B2B2C)**; **Identity Center para funcionários**; **IAM para workloads**.

## 7. Casos de uso típicos

| Caso | Arquitetura |
|---|---|
| **App SaaS com login e MFA** | User pool + Managed Login + Cognito authorizer no API Gateway |
| **App mobile com upload de fotos** | User pool + Identity pool → role com `s3:PutObject` no prefixo `${cognito-identity.amazonaws.com:sub}` |
| **Login com Google/Apple/Facebook** | User pool federado com IdPs sociais |
| **Clientes corporativos com SSO (SAML)** | User pool com IdP SAML por cliente (multi-tenant) |
| **API M2M** | App client com `client_credentials` e escopos de um *resource server* |
| **Site com ALB** | ALB `authenticate-cognito` protege rotas sem código na aplicação |
| **Portal interno** | Cognito + grupos para papéis (admin, usuário) |
| **IoT** | Identity pool concede credenciais para publicar em tópicos IoT |

## 8. Conceitos centrais (vocabulário rápido)

| Termo | Significado |
|---|---|
| **User pool** | Diretório e IdP de usuários |
| **App client** | Aplicação registrada no user pool (com ou sem *client secret*) e suas configurações OAuth |
| **Hosted UI / Managed Login** | Telas de login/cadastro prontas, hospedadas pelo Cognito |
| **Domain** | Domínio do Cognito (ou custom) que serve o Managed Login e endpoints OAuth |
| **Group** | Agrupamento de usuários (papéis); aparece em `cognito:groups` |
| **Attribute** | Dados do usuário (padrão e `custom:`) |
| **Lambda trigger** | Função chamada em eventos (pré-cadastro, pré-token...) |
| **Federation** | Login via IdP externo (social, SAML, OIDC) |
| **Identity pool** | Troca tokens por credenciais AWS |
| **Resource server / scope** | Definem escopos OAuth customizados para APIs |
| **Adaptive authentication / threat protection** | Detecção de risco no login (plano Plus) |

## 9. Primeiro exemplo (ilustrativo)

```bash
# 1) Cria um user pool (e-mail como login, MFA opcional)
aws cognito-idp create-user-pool \
  --pool-name usuarios-app \
  --username-attributes email \
  --auto-verified-attributes email \
  --mfa-configuration OPTIONAL \
  --policies 'PasswordPolicy={MinimumLength=12,RequireUppercase=true,RequireLowercase=true,RequireNumbers=true,RequireSymbols=true}'

# 2) Cria um app client público (sem secret) para SPA/mobile
aws cognito-idp create-user-pool-client \
  --user-pool-id us-east-1_EXAMPLE \
  --client-name app-web \
  --no-generate-secret \
  --explicit-auth-flows ALLOW_USER_SRP_AUTH ALLOW_REFRESH_TOKEN_AUTH \
  --supported-identity-providers COGNITO \
  --allowed-o-auth-flows code --allowed-o-auth-scopes openid email profile \
  --allowed-o-auth-flows-user-pool-client \
  --callback-urls https://app.exemplo.com/callback

# 3) Cria um usuário de teste
aws cognito-idp admin-create-user --user-pool-id us-east-1_EXAMPLE --username teste@exemplo.com
```

Os endpoints OIDC públicos (`.well-known/openid-configuration` e **JWKS**) permitem que qualquer backend **valide a assinatura** dos tokens sem chamar o Cognito a cada requisição.

## 10. Erros comuns

> [!bug] Erros comuns
> 1. **Confundir user pool e identity pool** (o primeiro autentica; o segundo emite credenciais AWS).
> 2. **Usar identity pool quando só precisava de JWT** para o backend.
> 3. **Tratar o ID token como access token** em APIs (usar o token errado).
> 4. **Colocar client secret em app público** (SPA/mobile não guardam segredos).
> 5. **Esperar customizar totalmente a UI** do Managed Login e do fluxo.
> 6. **Atributos customizados imutáveis ou mal planejados** (alguns não podem ser removidos/alterados).
> 7. **Esquecer a validação do token** no backend (assinatura, `iss`, `aud/client_id`, `exp`, `token_use`).
> 8. **Role de identity pool ampla demais** (credenciais com `*`).
> 9. **Não planejar limites e custos** de MAU, SMS e M2M.
> 10. **Usar Cognito para funcionários/SSO** onde o IAM Identity Center seria o correto.

## 11. Troubleshooting inicial

| Sintoma | Causa provável | Ação |
|---|---|---|
| `NotAuthorizedException` no login | Senha incorreta, usuário desabilitado, fluxo não permitido no app client | Conferir usuário, status e `ExplicitAuthFlows` |
| `UserNotConfirmedException` | Cadastro não confirmado | Confirmar e-mail/telefone ou confirmar via admin |
| 401 no API Gateway com o token | Token errado (ID vs access), expirado ou issuer incorreto | Validar `token_use`, `exp`, `iss` e o authorizer |
| Credenciais AWS negadas | Role do identity pool sem a permissão | Ajustar a role (authenticated/unauthenticated) |
| Redirecionamento falha (`redirect_mismatch`) | Callback URL não registrada | Cadastrar a URL exata no app client |
| E-mail/SMS não chega | Limites do SES/SNS (sandbox) | Configurar SES/SNS para produção |

## 12. Resumo rápido

- **Cognito** = serviço gerenciado de **identidade de clientes (CIAM)**.
- **User pool** = diretório + IdP (**JWT**); **identity pool** = **credenciais AWS temporárias** (STS) para usuários finais.
- Tokens: **ID** (identidade), **access** (autorização de API), **refresh** (renovação).
- **Federação**: social, SAML e OIDC; **API Gateway/ALB/AppSync** integram nativamente.
- **Cognito para clientes**, **Identity Center para funcionários**, **IAM para workloads**; cobrança principalmente por **MAU**.

2. Quais os três tokens emitidos pelo user pool e para que serve cada um?
3. Quando usar um identity pool?
4. O que significa MAU na cobrança?
5. Cognito ou IAM Identity Center para funcionários acessando contas AWS?

**Respostas:**

1. User pool autentica e emite JWT; identity pool troca tokens por credenciais AWS temporárias e não guarda usuários.
2. ID token (identidade), access token (autorização de APIs/escopos) e refresh token (renovar sem novo login).
3. Quando o cliente (web/mobile) precisa acessar serviços AWS diretamente, como S3 ou DynamoDB, com permissões mínimas.
4. Monthly Active Users: usuários ativos no mês, base principal da cobrança.
5. IAM Identity Center; o Cognito é para clientes finais.
6. Porque SPAs e apps mobile não conseguem guardar segredos com segurança.
7. Assinatura (JWKS), issuer, audience/client_id, expiração e token_use (id ou access).
