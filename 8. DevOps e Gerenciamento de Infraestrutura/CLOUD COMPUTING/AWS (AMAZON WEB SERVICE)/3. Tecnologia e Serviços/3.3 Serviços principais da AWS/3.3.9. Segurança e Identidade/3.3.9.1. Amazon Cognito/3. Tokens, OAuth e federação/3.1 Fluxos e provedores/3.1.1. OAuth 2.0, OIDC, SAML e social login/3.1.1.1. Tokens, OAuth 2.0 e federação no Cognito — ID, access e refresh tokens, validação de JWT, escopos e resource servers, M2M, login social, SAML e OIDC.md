### 3.1.1.1. Tokens, OAuth 2.0 e federação no Cognito — ID, access e refresh tokens, validação de JWT, escopos e resource servers, M2M, login social, SAML e OIDC

> [!warning] Aviso
> Validades, claims, endpoints e comportamentos de revogação abaixo são **de memória e podem mudar**; o Cognito adicionou **customização de access token (V2/V3 triggers)** e novos planos recentemente. **Confirme na documentação oficial** (claims, limites de escopos, tempos de validade). Trechos de código e comandos são ilustrativos e não foram executados. **Nunca** confie em um JWT sem validá-lo.

## 1. Por que tokens

Depois que o usuário se autentica, a aplicação precisa **provar quem ele é** a cada chamada sem repetir senha. Isso é feito com **tokens**: pequenas credenciais **assinadas** que o backend valida localmente. O Cognito segue **OAuth 2.0** (delegação de autorização) e **OpenID Connect — OIDC** (camada de identidade sobre OAuth), emitindo **JWT (JSON Web Tokens)**.

```
JWT = header . payload . assinatura        (cada parte em Base64URL)
 header  : {"alg":"RS256","kid":"abc123"}               ← algoritmo e chave de assinatura
 payload : {"sub":"...","iss":"...","exp":...,"scope":..}← claims
 assinatura: RSA-SHA256(header.payload, chave privada do Cognito)
```

O backend busca as **chaves públicas (JWKS)** do pool e **verifica a assinatura**: não precisa consultar o Cognito a cada requisição.

## 2. Os tokens do user pool

| Token | `token_use` | Conteúdo típico | Uso |
|---|---|---|---|
| **ID token** | `id` | `sub`, `email`, `cognito:username`, `cognito:groups`, `custom:*`, `aud` (client ID) | **Identidade** do usuário para o **cliente**; Cognito authorizer do API Gateway (REST) |
| **Access token** | `access` | `sub`, `scope`, `cognito:groups`, `client_id`, `username` | **Autorizar chamadas de API** (Bearer); JWT authorizer (HTTP API); `userInfo` |
| **Refresh token** | (opaco) | Não é JWT legível | Obter novos ID/access **sem novo login** |

Claims essenciais a validar:

| Claim | Verificação |
|---|---|
| **`iss`** | Igual a `https://cognito-idp.<região>.amazonaws.com/<userPoolId>` |
| **`exp`** | Ainda não expirou |
| **`token_use`** | `access` (para APIs) ou `id` (conforme o caso) |
| **`aud`** (ID token) / **`client_id`** (access token) | É um client ID esperado |
| **`kid` + assinatura** | Assinatura válida com a chave do JWKS |
| **`scope`/`cognito:groups`** | Autorização granular |

> [!warning] ID token vs access token
> Usar o **ID token** para autorizar APIs (ou o **access token** onde o ID é exigido) é erro comum. Para **APIs**, use o **access token** (e valide `client_id`). O **Cognito authorizer** do REST API aceita ID token (ou access token com escopos); o **JWT authorizer** do HTTP API exige **audience/client_id** conforme o tipo — verifique o que o seu authorizer espera.

## 3. Validade e renovação

| Token | Validade (faixa/padrão, confirmar) |
|---|---|
| **ID / Access** | 5 min a 1 dia; **padrão 1 hora** |
| **Refresh** | 60 min a 10 anos; **padrão 30 dias** |

Estratégias:

- **Access curto** (5–15 min) para **limitar o dano** de um vazamento; renove com o refresh token.
- **Refresh rotation** (disponível conforme versão) para reduzir risco de roubo do refresh.
- Em SPAs, **armazene tokens com cuidado** (memória/BFF com cookies **HttpOnly**) — `localStorage` é vulnerável a **XSS**.
- Ao **sair**, chame **GlobalSignOut** ou **revoke** e limpe o armazenamento local.

### 3.1 Revogação e limites do JWT

O JWT é **autocontido**: mesmo após **desativar o usuário** ou **remover de um grupo**, **tokens já emitidos continuam válidos até expirar** (a menos que o backend consulte o Cognito). Mitigações:

| Técnica | Efeito |
|---|---|
| **Validade curta do access token** | Janela de risco pequena |
| **Token revocation** (`RevokeToken`, `EnableTokenRevocation`) | Revoga o **refresh token** (e os access tokens derivados, conforme versão) |
| **`GlobalSignOut` / `AdminUserGlobalSignOut`** | Invalida refresh tokens do usuário |
| **Lista de negação no backend** | Para casos críticos |
| **Checagem online** (`userInfo`/`AdminGetUser`) | Consulta ao Cognito em operações sensíveis |

## 4. OAuth 2.0 e OIDC no Cognito

### 4.1 Endpoints (domínio do user pool)

| Endpoint | Função |
|---|---|
| `GET /oauth2/authorize` | Inicia o login (authorization code) |
| `POST /oauth2/token` | Troca **code → tokens**, **refresh → tokens**, **client_credentials → access token** |
| `GET /oauth2/userInfo` | Dados do usuário (com access token) |
| `GET /logout` | Encerra a sessão do Managed Login |
| `POST /oauth2/revoke` | Revoga refresh token |
| `/.well-known/openid-configuration` | Metadados OIDC |
| `/.well-known/jwks.json` | **Chaves públicas** para validar JWT |

### 4.2 Fluxos OAuth

| Fluxo | Quando usar | Observações |
|---|---|---|
| **Authorization Code + PKCE** | **Padrão** para web (SPA), mobile e backends | Mais seguro; PKCE protege apps públicos |
| **Authorization Code (com secret)** | Aplicações servidor (confidencial) | Secret guardado no backend |
| **Implicit** | **Legado, não recomendado** | Tokens na URL; evitar |
| **Client Credentials** | **M2M** (serviço→serviço) | Sem usuário; app client com secret |

Fluxo Authorization Code + PKCE (resumo):

```
1) App gera code_verifier (aleatório) e code_challenge = SHA256(code_verifier)
2) Redireciona: /oauth2/authorize?response_type=code&client_id=...&redirect_uri=...&scope=openid email&code_challenge=...
3) Usuário faz login no Managed Login (e MFA)
4) Cognito redireciona para redirect_uri?code=XYZ
5) App chama POST /oauth2/token (code + code_verifier) ──▶ ID, access, refresh tokens
```

### 4.3 Escopos

- **Escopos padrão OIDC**: `openid` (obrigatório para OIDC), `email`, `profile`, `phone`, `aws.cognito.signin.user.admin` (chamadas à API do Cognito em nome do usuário).
- **Escopos customizados**: definidos em um **resource server** (`pedidos/read`, `pedidos/write`) e concedidos ao app client.

```bash
# Cria um resource server com escopos
aws cognito-idp create-resource-server --user-pool-id us-east-1_EXAMPLE \
  --identifier https://api.exemplo.com --name api-pedidos \
  --scopes ScopeName=read,ScopeDescription="Ler pedidos" ScopeName=write,ScopeDescription="Gravar pedidos"
# O escopo completo no token: https://api.exemplo.com/read
```

Use **escopos** para **autorização de API** (`scope` no access token) e **grupos** para **papéis do usuário**.

## 5. M2M (machine-to-machine) com client credentials

Para **serviços sem usuário**:

```bash
curl -s -u "$CLIENT_ID:$CLIENT_SECRET" \
  -d "grant_type=client_credentials&scope=https://api.exemplo.com/read" \
  https://login.exemplo.com/oauth2/token
```

O app client M2M precisa de **client secret**, **escopos do resource server** e **client_credentials** habilitado. O **access token** resultante tem `scope` e `client_id`, sem `sub` de usuário. **Cobrança à parte** (por cliente e por token). Cuide do **armazenamento do secret** (Secrets Manager) e de **rotação**.

## 6. Federação (login com outros provedores)

O user pool pode **delegar a autenticação** a um IdP externo; o usuário federado ganha um **perfil no pool** (`EXTERNAL_PROVIDER`) e o seu backend continua recebendo **tokens do Cognito** — um **ponto único** de integração.

| Tipo | Exemplos | Observações |
|---|---|---|
| **Social** | Google, Facebook, Apple, Amazon | Configurar *client ID/secret* de cada provedor; **mapear atributos** |
| **OIDC** | Auth0, Okta, Entra ID, Keycloak | Informar issuer, client, escopos; mapear claims |
| **SAML 2.0** | AD FS, Okta, Entra ID, PingFederate | Metadados XML/URL; **por cliente corporativo** (B2B) |
| **Identity pool** | Social/SAML/OIDC **direto** no identity pool | Sem passar pelo user pool (credenciais AWS) |

### 6.1 Mapeamento de atributos

Associe claims do IdP a atributos do pool (`email` → `email`, `custom:department` → `department`). **Atenção:** atributos vindos do IdP podem ser **sobrescritos a cada login** (configurável).

### 6.2 Vinculação de contas (account linking)

O mesmo e-mail pode existir como usuário local **e** federado (Google), gerando **duplicatas**. Soluções: **Pre sign-up Lambda** com `AdminLinkProviderForUser` para **vincular** identidades ao mesmo usuário (cuidado com **account takeover** se o IdP não verifica o e-mail).

### 6.3 SAML multi-tenant (B2B)

Padrão: **um IdP SAML por cliente** no mesmo pool, selecionado por **identifier** (domínio de e-mail → IdP), com **grupos/atributo de tenant** mapeados. Alternativa: **um pool por tenant** (isolamento total, mais gestão). Considere **limites de IdPs por pool**.

## 7. Customização de tokens (Pre token generation)

O **Pre token generation trigger** permite **adicionar, substituir ou suprimir claims** (ID e, em versões novas, **access token**): por exemplo, injetar `tenantId`, `plano`, papéis vindos de um banco, ou **remover** claims sensíveis. É também a forma de **adicionar escopos** dinâmicos ao access token (V2/V3, conforme plano).

```python
def handler(event, context):
    event["response"]["claimsAndScopeOverrideDetails"] = {
        "idTokenGeneration": {"claimsToAddOrOverride": {"tenantId": "acme"}},
        "accessTokenGeneration": {"claimsToAddOrOverride": {"plano": "gold"},
                                  "scopesToAdd": ["https://api.exemplo.com/read"]}
    }
    return event
```

## 8. Validando JWT no backend (exemplo)

```python
import jwt, requests   # PyJWT
JWKS = requests.get("https://cognito-idp.us-east-1.amazonaws.com/us-east-1_EXAMPLE/.well-known/jwks.json").json()

def validar(token: str):
    cab = jwt.get_unverified_header(token)
    chave = next(k for k in JWKS["keys"] if k["kid"] == cab["kid"])
    pub = jwt.algorithms.RSAAlgorithm.from_jwk(chave)
    claims = jwt.decode(token, pub, algorithms=["RS256"],
                        issuer="https://cognito-idp.us-east-1.amazonaws.com/us-east-1_EXAMPLE",
                        options={"verify_aud": False})        # access token não tem 'aud'
    assert claims["token_use"] == "access"
    assert claims["client_id"] in {"1h57kf5cpq17m0eml12EXAMPLE"}
    return claims
```

Boas práticas: **cache do JWKS** (as chaves rotacionam raramente), validação de `iss`, `exp`, `token_use`, `client_id`/`aud` e **escopos exigidos** pela rota.

## 9. Segurança de tokens e fluxos

| Prática | Motivo |
|---|---|
| **Authorization Code + PKCE**; evitar implicit | Evita tokens na URL |
| **Redirect URIs exatas** | Evita open redirect e roubo de code |
| **State/nonce** | Proteção contra CSRF e replay |
| **Access token curto; refresh protegido** | Reduz janela de ataque |
| **HTTPS sempre**; cookies **HttpOnly/Secure/SameSite** em BFF | Proteção contra XSS/CSRF |
| **Não logar tokens** | Evita vazamento em logs |
| **Escopos mínimos** | Menor privilégio |
| **Rotacionar secrets** de app clients e IdPs | Higiene |

## 10. Erros comuns

> [!bug] Erros comuns
> 1. **Autorizar API com o ID token** (ou confundir `aud` e `client_id`).
> 2. **Não validar `iss`/`token_use`/assinatura** (aceitar tokens de outro pool ou forjados).
> 3. **Usar o fluxo implicit** em apps novos.
> 4. **Guardar tokens em `localStorage`** em SPA sem proteção contra XSS.
> 5. **Achar que desativar o usuário invalida tokens já emitidos.**
> 6. **Redirect URI com curinga/não exata.**
> 7. **Vincular contas federadas por e-mail sem verificação** (takeover).
> 8. **Refresh token de 10 anos** em apps de alto risco.
> 9. **Client secret de M2M em código-fonte.**
> 10. **Confiar em claims de atributos editáveis pelo usuário.**

## 11. Troubleshooting

| Sintoma | Causa provável | Ação |
|---|---|---|
| `invalid_grant` no `/token` | Code expirado/usado ou PKCE incorreto | Refazer o fluxo; conferir `code_verifier` |
| `redirect_mismatch` | Callback URL diferente da registrada | Registrar a URL exata no app client |
| `invalid_scope` | Escopo não permitido ao app client | Habilitar o escopo/resource server no client |
| 401 no backend com token válido | `token_use`/`aud`/`client_id` errados | Ajustar a validação ao tipo de token |
| Token aceito de outro pool | `iss` não validado | Validar issuer exato |
| Claim novo não aparece | Pre token trigger/versão/plano | Conferir versão do trigger e o plano do pool |
| Login federado sem e-mail | Mapeamento de atributos ausente | Mapear `email` e escopos no IdP |

## 12. Resumo rápido

- **ID token** = identidade; **access token** = autorização de API (escopos, `client_id`); **refresh token** = renovação (opaco).
- Valide **assinatura (JWKS), `iss`, `exp`, `token_use`, `client_id/aud` e escopos**; JWT é **válido até expirar** — use **validade curta** e **revogação**.
- OAuth: **Authorization Code + PKCE** é o padrão; **client_credentials** para **M2M**; evite **implicit**.
- **Federação** (social, OIDC, SAML) centraliza tudo em tokens do Cognito; cuide de **vinculação de contas** e **mapeamento de atributos**.
- **Pre token generation** customiza claims/escopos; **resource servers** definem escopos de API.
