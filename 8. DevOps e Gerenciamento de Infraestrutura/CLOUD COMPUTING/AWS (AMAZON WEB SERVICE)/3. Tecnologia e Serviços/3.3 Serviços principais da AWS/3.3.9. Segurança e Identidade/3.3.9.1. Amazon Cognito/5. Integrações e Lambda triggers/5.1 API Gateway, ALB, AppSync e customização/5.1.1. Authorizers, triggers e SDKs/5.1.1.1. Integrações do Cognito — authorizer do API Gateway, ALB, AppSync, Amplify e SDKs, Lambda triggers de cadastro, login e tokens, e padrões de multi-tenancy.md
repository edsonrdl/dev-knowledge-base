### 5.1.1.1. Integrações do Cognito — authorizer do API Gateway, ALB, AppSync, Amplify e SDKs, Lambda triggers de cadastro, login e tokens, e padrões de multi-tenancy

> [!warning] Aviso
> Nomes de triggers, versões de eventos (V1/V2/V3), formatos de payload e limites abaixo são **de memória e mudam**; **confirme na documentação oficial** (especialmente Pre token generation e Custom sender). Código e comandos são ilustrativos e não foram executados. **Triggers rodam no caminho crítico do login**: uma Lambda lenta ou com erro **quebra o login de todos**.

## 1. Cognito como "peça central" de identidade

O Cognito raramente trabalha sozinho: ele **emite identidades** que outros serviços **consomem**. Os principais pontos de integração:

```
                           ┌────────────── API Gateway (Cognito/JWT authorizer)
 Usuário ──▶ COGNITO ──JWT─┼────────────── ALB (authenticate-cognito)
 (user pool)               ├────────────── AppSync (GraphQL)
                           ├────────────── Seu backend (validação de JWT)
                           └──▶ Identity pool ──▶ credenciais AWS (S3, DynamoDB, IoT)
        ▲
        └── Lambda triggers (cadastro, login, tokens, mensagens) ──▶ DynamoDB, SES, APIs, regras de negócio
```

## 2. API Gateway

### 2.1 REST API: Cognito user pool authorizer

Mecanismo **nativo**, sem Lambda: o Gateway valida o token do user pool. Dois modos:

| Modo | Token enviado | Autorização |
|---|---|---|
| **Sem escopos** | **ID token** (ou access token) | Basta ser válido |
| **Com escopos** | **Access token** | O método exige escopos (`https://api.exemplo.com/read`) |

```yaml
# SAM (REST) — Cognito authorizer
Auth:
  DefaultAuthorizer: CognitoAuth
  Authorizers:
    CognitoAuth:
      UserPoolArn: arn:aws:cognito-idp:us-east-1:123456789012:userpool/us-east-1_EXAMPLE
      Identity: { Header: Authorization }
```

O backend recebe as **claims** em `requestContext.authorizer.claims`.

### 2.2 HTTP API: JWT authorizer

Valida JWT de **qualquer OIDC** (inclusive Cognito) com **issuer** e **audience**; escopos por rota. Nativo e mais barato. Claims em `requestContext.authorizer.jwt.claims`.

### 2.3 Boas práticas

- **Access token + escopos** para APIs; **grupos** para papéis.
- **Autorização por recurso no backend** (o usuário é dono do pedido?).
- **CORS** configurado para o `Authorization` header.
- Se a API precisa de **regras dinâmicas**, use **Lambda authorizer** consultando o Cognito/banco.

## 3. Application Load Balancer (ALB)

O ALB pode **autenticar usuários antes de encaminhar** ao alvo, com a ação **`authenticate-cognito`** (ou `authenticate-oidc`):

```
Usuário ──▶ ALB (listener HTTPS) ──[sem sessão?]──▶ redireciona ao Managed Login do Cognito
                                  ◀── retorno com code ── ALB troca por tokens, cria cookie de sessão
Usuário (autenticado) ──▶ ALB ──▶ Alvo (EC2/ECS/Lambda) com cabeçalhos:
       x-amzn-oidc-data (JWT do ALB), x-amzn-oidc-accesstoken, x-amzn-oidc-identity
```

Vantagens: **zero código de login** na aplicação, ideal para **aplicações legadas** e portais internos. Cuidados:

- O ALB exige **HTTPS** e acesso do **ALB à internet** (ou **NAT/VPC endpoints**) para chegar ao endpoint do Cognito.
- A aplicação **deve validar** o cabeçalho `x-amzn-oidc-data` (JWT assinado pelo ALB, com chave pública regional) — **não confie** em cabeçalhos sem validar e **restrinja o acesso direto** ao alvo (Security Group só do ALB).
- Configure **timeout da sessão**, **escopos** e a ação em caso de falha (`authenticate`, `deny`, `allow`).

## 4. AWS AppSync (GraphQL)

O AppSync aceita **Cognito user pools** como modo de autorização: os resolvers recebem `$ctx.identity` (com `sub`, `groups`, `claims`), e diretivas (`@aws_auth(cognito_groups: ["admin"])`) controlam acesso por **grupo**. Alternativas: **OIDC**, **IAM** (com identity pool) e **Lambda**. Assinaturas em tempo real respeitam a mesma autorização.

## 5. Amplify, SDKs e bibliotecas

| Ferramenta | Uso |
|---|---|
| **AWS Amplify (Auth)** | Biblioteca de alto nível para **login, cadastro, MFA, federação** em web/mobile (React, Vue, Swift, Kotlin, Flutter); componentes de UI |
| **Amplify UI Authenticator** | Componente pronto de autenticação |
| **AWS SDKs (cognito-idp)** | Chamadas de baixo nível: `SignUp`, `InitiateAuth`, `RespondToAuthChallenge`, `AdminCreateUser`... |
| **Bibliotecas OIDC genéricas** | `oidc-client-ts`, `authlib`, `passport` apontando para o **issuer** do pool |
| **Frameworks backend** | Spring Security, ASP.NET, FastAPI com validação de JWT |
| **AWS CLI** | `aws cognito-idp ...` (administração) |

Recomendação de segurança: **Authorization Code + PKCE** via Managed Login/OIDC em SPAs e mobile (em vez de coletar senha na UI própria), e **backend-for-frontend** para guardar tokens em cookies **HttpOnly**.

## 6. Lambda triggers do user pool

Os **triggers** permitem **estender o comportamento** do pool em pontos-chave do ciclo de vida:

| Trigger | Quando dispara | Usos típicos |
|---|---|---|
| **Pre sign-up** | Antes de criar o usuário | Validar domínio de e-mail, **auto-confirmar**, **vincular contas federadas**, bloquear |
| **Post confirmation** | Depois da confirmação | Criar perfil no DynamoDB, enviar boas-vindas, adicionar a grupo |
| **Pre authentication** | Antes do login | Bloquear por regra (horário, IP, lista), checar status no banco |
| **Post authentication** | Depois de login bem-sucedido | Auditoria, métricas, atualizar último acesso |
| **Pre token generation** | Antes de emitir os tokens | **Adicionar/remover claims e escopos**, papéis do banco, tenant |
| **Custom message** | Ao enviar e-mail/SMS | Personalizar texto/idioma dos códigos e convites |
| **User migration** | Login de usuário inexistente | **Migrar do sistema legado** no primeiro login |
| **Define/Create/Verify auth challenge** | Fluxo `CUSTOM_AUTH` | **Passwordless**, OTP próprio, CAPTCHA, desafios customizados |
| **Custom email/SMS sender** | Envio de mensagens | Enviar via **provedor próprio** (código **criptografado com KMS**) |
| **Pre/Post token (V2/V3)** | Customização avançada | Access token com claims/escopos customizados (conforme plano) |

### 6.1 Exemplo: Pre sign-up (restringir domínio e auto-confirmar)

```python
def handler(event, context):
    email = event["request"]["userAttributes"].get("email", "")
    if not email.endswith("@empresa.com"):
        raise Exception("Cadastro permitido apenas para e-mails corporativos")
    event["response"]["autoConfirmUser"] = True
    event["response"]["autoVerifyEmail"] = True
    return event
```

### 6.2 Exemplo: Post confirmation (criar perfil)

```python
import boto3, time
tabela = boto3.resource("dynamodb").Table("Perfis")
def handler(event, context):
    a = event["request"]["userAttributes"]
    tabela.put_item(Item={"userId": a["sub"], "email": a["email"], "criadoEm": int(time.time())},
                    ConditionExpression="attribute_not_exists(userId)")
    return event
```

### 6.3 Regras para triggers

| Regra | Motivo |
|---|---|
| **Timeout curto** (≤ 5 s; o Cognito espera ~5 s) | Evita falha de login |
| **Idempotência** | O Cognito pode **repetir** a chamada |
| **Sempre devolver o `event`** (modificado) | Contrato do trigger |
| **Tratar erros** com mensagens claras (erro bloqueia a operação) | Evita travar usuários |
| **Permissões**: Lambda com a **resource policy** que permite `cognito-idp.amazonaws.com` invocá-la | Sem isso, o trigger falha |
| **Evitar dependências externas lentas** | Latência de login |
| **Logs** (sem dados sensíveis) e **alarmes** | Observabilidade |
| **Cold start**: provisioned concurrency em logins críticos | Latência |

```bash
aws lambda add-permission --function-name pre-signup \
  --statement-id cognito-invoke --action lambda:InvokeFunction \
  --principal cognito-idp.amazonaws.com \
  --source-arn arn:aws:cognito-idp:us-east-1:123456789012:userpool/us-east-1_EXAMPLE
```

## 7. Padrões de multi-tenancy

| Padrão | Como | Prós | Contras |
|---|---|---|---|
| **Um pool, tenant no usuário** | `custom:tenantId` (imutável) e/ou **grupos por tenant**; claim injetada no token (Pre token generation) | Simples, barato, escala | Isolamento **lógico**; limites compartilhados; cuidado com vazamento entre tenants |
| **Um pool por tenant** | Cada cliente tem seu pool (e IdPs) | **Isolamento forte**, configuração por tenant (MFA, SAML) | Gestão em escala, limites de pools, mais custo |
| **Um pool + um app client por tenant** | Clients separados com IdPs/escopos próprios | Meio-termo | Limites de clients |
| **Pool por camada (por tipo de tenant)** | Pools "standard" e "enterprise" | Equilíbrio | Complexidade |

Regras de ouro:

1. **Nunca** confie no tenant enviado pelo cliente: **derive do token** (claim assinada).
2. Atributo de tenant **imutável** e **não editável** pelo usuário.
3. **Toda consulta** ao banco inclui o tenant (chave de partição/filtro) — idealmente aplicado por **camada de dados** compartilhada.
4. Para B2B com **SAML**, mapeie **domínio → IdP → tenant** e valide a **claim** de tenant no backend.
5. Considere **ABAC** com tags de sessão (identity pool) para acesso direto a recursos.

## 8. Casos práticos integrados

### 8.1 SaaS com API serverless

```
SPA/Mobile ──(Managed Login + PKCE)──▶ Cognito ──JWT──▶ API Gateway (JWT authorizer) ──▶ Lambda ──▶ DynamoDB
                                                      claims: sub, scope, custom:tenantId
Pre token generation: injeta tenantId e papéis do DynamoDB
Post confirmation: cria perfil
```

### 8.2 Portal legado atrás do ALB

```
Usuário ──▶ ALB (authenticate-cognito) ──▶ Aplicação legada (lê x-amzn-oidc-data) — sem tela de login própria
```

### 8.3 App de GraphQL

```
App ──▶ AppSync (Cognito user pool) — @aws_auth por grupo, resolvers com $ctx.identity.sub
```

## 9. Erros comuns

> [!bug] Erros comuns
> 1. **Trigger lento ou com exceção**, bloqueando logins.
> 2. **Esquecer a permissão** para o Cognito invocar a Lambda (`cognito-idp.amazonaws.com`).
> 3. **Não devolver o `event`** ou devolver estrutura incorreta.
> 4. **Trigger não idempotente** (duplica perfis/e-mails).
> 5. **Confiar em cabeçalhos do ALB sem validar** o JWT e sem restringir o acesso ao alvo.
> 6. **Usar ID token para autorizar APIs** com escopos.
> 7. **Tenant vindo do cliente**, não do token.
> 8. **Claim de tenant editável** pelo usuário.
> 9. **Lógica de negócio pesada em Pre token generation**, aumentando a latência do login.
> 10. **UI própria coletando senha** sem necessidade, em vez de Managed Login + PKCE.

## 10. Troubleshooting

| Sintoma | Causa provável | Ação |
|---|---|---|
| `PreSignUp invocation failed` / login falha | Erro/timeout da Lambda ou sem permissão | Ver logs da função e a resource policy |
| 401 no API Gateway | Tipo de token/escopo/issuer incorreto | Alinhar token e authorizer |
| ALB entra em loop de redirecionamento | Callback URL ou cookies/SG/rotas | Registrar `https://<dns>/oauth2/idpresponse` no app client; conferir saída do ALB ao Cognito |
| Claims customizadas ausentes | Versão do trigger/plano | Conferir V1/V2/V3 e o formato de resposta |
| Mensagem de e-mail sem personalização | Custom message trigger ausente/erro | Verificar trigger e idioma |
| Usuário migrado com senha errada | Migração falha ao validar legado | Revisar a lógica da user migration |
| Tenant errado em tokens | Atributo mutável/derivado do cliente | Tornar imutável; derivar no Pre token generation |

## 11. Resumo rápido

- **Integrações**: **API Gateway** (Cognito/JWT authorizer), **ALB** (`authenticate-cognito`), **AppSync**, **Amplify/SDKs**, backends com validação de JWT.
- **Lambda triggers** estendem cadastro, login, tokens, mensagens e migração; devem ser **rápidos, idempotentes e com permissão correta**.
- **Pre token generation** injeta claims/escopos (papéis, tenant).
- **Multi-tenant**: pool único com tenant no token (simples) ou pool por tenant (isolamento forte); **nunca confie no tenant do cliente**.
- **Managed Login + PKCE** reduz risco; valide **cabeçalhos do ALB** e **tokens** no backend.

### 🧩 Quiz de Fixação

1. Qual mecanismo do ALB autentica com Cognito?
2. Qual a diferença entre o Cognito authorizer (REST) e o JWT authorizer (HTTP)?
3. Para que serve o Pre token generation?
4. Que permissão a Lambda precisa para ser usada como trigger?
5. Por que triggers devem ser rápidos e idempotentes?
6. Cite dois padrões de multi-tenancy.
7. De onde deve vir a informação de tenant?

**Respostas:**

1. A ação `authenticate-cognito` no listener do ALB.
2. O Cognito authorizer valida tokens de um user pool nativamente em REST; o JWT authorizer valida JWT de qualquer provedor OIDC no HTTP API.
3. Adicionar, alterar ou suprimir claims e escopos nos tokens (papéis, tenant, planos).
4. Uma resource policy permitindo `cognito-idp.amazonaws.com` invocar a função.
5. Porque rodam no caminho crítico do login (timeout curto) e podem ser repetidos pelo Cognito.
6. Um pool com tenant no usuário/token e um pool por tenant (também um app client por tenant).
7. Da claim assinada no token (derivada no servidor), nunca de um valor enviado pelo cliente.
