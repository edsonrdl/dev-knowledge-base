### 4.1.1.1. Identity pools do Cognito — credenciais temporárias via STS, roles autenticada e não autenticada, mapeamento de papéis, políticas por usuário e acesso direto a S3 e DynamoDB

> [!warning] Aviso
> Políticas IAM, JSONs, comandos e nomes de variáveis de política abaixo são **ilustrativos, de memória e não foram executados**. Credenciais AWS concedidas a clientes (web/mobile) são **sensíveis**: erros de política resultam em **acesso indevido a dados de outros usuários**. **Teste com o IAM Policy Simulator**, revise com segurança e **confirme na documentação oficial** o fluxo atual (enhanced vs basic).

## 1. O que é um identity pool e quando precisa dele

Um **identity pool** (antigo "Federated Identities") **não autentica ninguém**: ele **recebe a prova de identidade** (um token de um user pool, Google, Apple, SAML, OIDC, ou até um token que seu backend emite) e **devolve credenciais temporárias da AWS** — **access key, secret key e session token** — associadas a uma **role IAM**. Com elas, o aplicativo (web/mobile) chama **serviços AWS diretamente**, com as permissões da role.

Pergunta-guia: **o cliente precisa falar direto com um serviço AWS?**

| Cenário | Precisa de identity pool? |
|---|---|
| API própria protegida por JWT (API Gateway/ALB) | **Não** — user pool + JWT bastam |
| App mobile envia fotos **direto ao S3** | **Sim** |
| App lê/escreve em **DynamoDB** com permissões por usuário | **Sim** (ou via API) |
| App publica em **IoT Core**, usa **Rekognition/Polly/Transcribe** no cliente | **Sim** |
| Chamar **AppSync** com IAM | **Sim** (ou use user pool direto no AppSync) |
| Visitantes (não logados) leem um bucket público de forma controlada | **Sim** (identidades não autenticadas) |

> [!tip] Menos é mais
> Dar credenciais AWS ao cliente aumenta a **superfície de ataque**. Se um **backend** pode intermediar (e validar regras de negócio), **prefira API + JWT**. Use o identity pool quando o **acesso direto** (upload grande, streaming, IoT) traz ganho real.

## 2. Arquitetura e fluxo

```
 App ──(1) login ──▶ User Pool ──(2) ID token ──▶ App
 App ──(3) GetId / GetCredentialsForIdentity (com o token) ──▶ Identity Pool
                       │ valida o token com o provedor
                       │ escolhe a role (authenticated / unauthenticated / mapeada)
                       └─(4) STS AssumeRoleWithWebIdentity ──▶ credenciais temporárias
 App ──(5) usa as credenciais (SigV4) ──▶ S3 / DynamoDB / IoT / ...
```

Conceitos:

| Termo | Significado |
|---|---|
| **Identity ID** | Identificador único do usuário no pool (`us-east-1:uuid`) |
| **Provedor de identidade** | User pool, Google, Facebook, Apple, Amazon, SAML, OIDC, **developer authenticated** |
| **Role autenticada** | Role assumida por usuários logados |
| **Role não autenticada (guest)** | Role assumida por **visitantes** (opcional; **desabilitada por padrão**) |
| **Credenciais temporárias** | Validade tipicamente **1 hora** (renovadas pelo SDK) |
| **Basic vs Enhanced flow** | Enhanced (padrão atual): o Cognito faz a troca no STS por você, com **escopo reduzido e políticas de sessão**; basic expõe `AssumeRoleWithWebIdentity` ao cliente |

## 3. Roles e políticas

Cada identity pool tem **pelo menos** duas roles-padrão (authenticated e, se habilitada, unauthenticated). A **trust policy** da role precisa confiar no **`cognito-identity.amazonaws.com`** com condições:

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": { "Federated": "cognito-identity.amazonaws.com" },
    "Action": "sts:AssumeRoleWithWebIdentity",
    "Condition": {
      "StringEquals": { "cognito-identity.amazonaws.com:aud": "us-east-1:11111111-2222-3333-4444-555555555555" },
      "ForAnyValue:StringLike": { "cognito-identity.amazonaws.com:amr": "authenticated" }
    }
  }]
}
```

`aud` = **ID do identity pool** (impede que outro pool use a role); `amr` = `authenticated` ou `unauthenticated`.

### 3.1 Permissões por usuário (variáveis de política)

A grande vantagem: **uma única role** que dá a **cada usuário acesso só aos próprios dados**, usando a variável **`${cognito-identity.amazonaws.com:sub}`** (o Identity ID):

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ArquivosDoUsuarioNoS3",
      "Effect": "Allow",
      "Action": ["s3:GetObject", "s3:PutObject", "s3:DeleteObject"],
      "Resource": "arn:aws:s3:::meu-bucket-app/usuarios/${cognito-identity.amazonaws.com:sub}/*"
    },
    {
      "Sid": "ListarSomentePropriaPasta",
      "Effect": "Allow",
      "Action": "s3:ListBucket",
      "Resource": "arn:aws:s3:::meu-bucket-app",
      "Condition": { "StringLike": { "s3:prefix": ["usuarios/${cognito-identity.amazonaws.com:sub}/*"] } }
    },
    {
      "Sid": "DynamoSoLinhasDoUsuario",
      "Effect": "Allow",
      "Action": ["dynamodb:GetItem", "dynamodb:PutItem", "dynamodb:UpdateItem", "dynamodb:DeleteItem", "dynamodb:Query"],
      "Resource": "arn:aws:dynamodb:us-east-1:123456789012:table/Notas",
      "Condition": { "ForAllValues:StringEquals": { "dynamodb:LeadingKeys": ["${cognito-identity.amazonaws.com:sub}"] } }
    }
  ]
}
```

Isso implementa **isolamento multi-usuário** sem backend: cada identidade só alcança o **prefixo S3** e as **linhas do DynamoDB** (partition key = Identity ID) dela. **Atenção:** o `sub` aqui é o **Identity ID do identity pool**, **não** o `sub` do user pool — decida qual identificador usar como chave e mantenha consistência (ou grave o mapeamento).

## 4. Mapeamento de papéis (role mapping)

Além das roles-padrão, o identity pool pode **escolher a role por usuário**:

| Estratégia | Como funciona |
|---|---|
| **Padrão** | authenticated vs unauthenticated |
| **Escolher role de `cognito:preferred_role`** | Usa a role do **grupo** do user pool (com **precedência**) |
| **Regras (rules)** | Condições sobre **claims do token** (`custom:plano == gold` → role Gold) |
| **Token (token-based)** | Usa `cognito:roles` / `cognito:preferred_role` do ID token |
| **Fallback** | `ResolveBySuperset` ou **negar** se nenhuma regra casar (`Deny` recomendado) |

Exemplo: grupo `admin` → role com permissões de gestão; grupo `cliente` → role restrita. **Cuidado:** a role vem do **token**; garanta que **claims de papel não possam ser forjados** pelo usuário (atributos protegidos no user pool).

## 5. Identidades não autenticadas (guest)

Habilitar acesso de **visitantes** gera credenciais **sem login**. Use com **muita cautela**:

- Permissões **mínimas** (somente leitura de conteúdo público específico).
- Proteja contra **abuso e custos** (throttling, WAF/CloudFront, quotas).
- Em geral, prefira **CloudFront + S3** público controlado ou **API pública** a conceder credenciais AWS a anônimos.

## 6. Developer authenticated identities

O **seu backend** (que já autentica usuários) chama `GetOpenIdTokenForDeveloperIdentity` e entrega um **token** ao app, que o troca por credenciais. Útil quando o login **não** é via IdP suportado (sistema legado). Exige credenciais do backend com permissão `cognito-identity:GetOpenIdTokenForDeveloperIdentity`.

## 7. Uso nos SDKs

```javascript
// JavaScript (AWS SDK v3) — credenciais via identity pool + ID token do user pool
import { fromCognitoIdentityPool } from "@aws-sdk/credential-providers";
import { S3Client, PutObjectCommand } from "@aws-sdk/client-s3";

const s3 = new S3Client({
  region: "us-east-1",
  credentials: fromCognitoIdentityPool({
    identityPoolId: "us-east-1:11111111-2222-3333-4444-555555555555",
    clientConfig: { region: "us-east-1" },
    logins: { "cognito-idp.us-east-1.amazonaws.com/us-east-1_EXAMPLE": idToken }
  })
});
await s3.send(new PutObjectCommand({ Bucket: "meu-bucket-app", Key: `usuarios/${identityId}/foto.jpg`, Body: arquivo }));
```

O mapa **`logins`** associa o **provedor** ao **token**; o SDK **renova** credenciais automaticamente antes de expirar.

## 8. Alternativas ao acesso direto (para muitos casos, melhores)

| Necessidade | Alternativa |
|---|---|
| **Upload/download de arquivos** | **Presigned URLs do S3** geradas por um backend (Lambda) após autorizar o usuário; o cliente **não** recebe credenciais AWS |
| **Operações em banco** | **API (API Gateway + Lambda)** com JWT e regras de negócio |
| **Acesso a vários serviços** | **BFF** (backend for frontend) |
| **IoT** | Identity pool + política IoT **ou** certificados X.509 |
| **GraphQL** | **AppSync** com user pool/OIDC (sem credenciais AWS no cliente) |

Presigned URLs são comumente preferíveis: **validade curta**, **escopo por objeto**, **sem políticas amplas** no cliente.

## 9. Segurança: princípios

1. **Menor privilégio**: a role do identity pool deve permitir **somente** o que o app precisa, **escopada por usuário** (`${cognito-identity.amazonaws.com:sub}`).
2. **Nada de `*`** em ações/recursos.
3. **Validar a trust policy** (`aud` = ID do pool; `amr`).
4. **Role não autenticada desabilitada** salvo necessidade.
5. **Políticas de sessão** (enhanced flow) reduzem ainda mais o escopo.
6. **Monitorar** com **CloudTrail** (ações das roles) e **IAM Access Analyzer**.
7. **Limitar o acesso** por condições (`aws:SourceIp`, `aws:PrincipalTag`, `aws:RequestedRegion`).
8. **Tags de principal**: o Cognito pode mapear **atributos do usuário** para **tags de sessão** (**ABAC**), permitindo políticas como "acesso a recursos com a tag `tenant` igual à do usuário".

```json
{ "Effect": "Allow", "Action": "s3:*",
  "Resource": "arn:aws:s3:::dados-tenant/*",
  "Condition": { "StringEquals": { "s3:ExistingObjectTag/tenant": "${aws:PrincipalTag/tenant}" } } }
```

## 10. Exemplo ponta a ponta (app de fotos)

```
1) Usuário entra no app (user pool) → ID token.
2) App obtém credenciais do identity pool (logins = {user pool: ID token}).
3) Role autenticada permite s3:PutObject somente em usuarios/${identityId}/*.
4) App sobe a foto direto ao S3 (multipart), sem passar por servidor.
5) Evento S3 → Lambda gera miniaturas → DynamoDB (metadados por identityId).
6) App lista fotos consultando DynamoDB (LeadingKeys = identityId) ou via API.
```

Benefícios: **escala** (sem gargalo de servidor), **custo menor**, **latência baixa**. Riscos: política mal escrita, validação de conteúdo **só pós-upload** (use Lambda/Macie/antivírus), cotas e abuso.

## 11. Erros comuns

> [!bug] Erros comuns
> 1. **Dar credenciais ao cliente quando uma API/presigned URL bastava.**
> 2. **Role authenticated com `s3:*`/`dynamodb:*` em `*`** (todos veem tudo).
> 3. **Não usar `${cognito-identity.amazonaws.com:sub}`** para isolar usuários.
> 4. **Confundir o `sub` do user pool com o Identity ID** do identity pool.
> 5. **Habilitar identidades não autenticadas sem necessidade.**
> 6. **Trust policy sem `aud`/`amr`** (outras identidades assumem a role).
> 7. **Confiar em claims de papel editáveis** para mapear roles.
> 8. **Não limitar tamanho/tipo de upload** (custos e conteúdo malicioso).
> 9. **Role mapping sem `Deny` no fallback.**
> 10. **Não monitorar** o uso das credenciais (CloudTrail).

## 12. Troubleshooting

| Sintoma | Causa provável | Ação |
|---|---|---|
| `NotAuthorizedException` em `GetId` | Token inválido/expirado ou provedor não cadastrado | Verificar o `logins` e o provedor autorizado no identity pool |
| `AccessDenied` ao usar o S3/DynamoDB | Política da role não cobre o recurso/prefixo | Ajustar a política e testar no Policy Simulator |
| `InvalidIdentityPoolConfiguration` | Roles sem trust policy correta | Revisar a trust policy (`aud`, `amr`) |
| Usuário vê dados de outros | Política sem variável por usuário | Escopar por Identity ID |
| Credenciais expiram | Sem renovação | Usar o provider do SDK, que renova automaticamente |
| Role errada aplicada | Regras/precedência de grupos | Revisar role mapping e `cognito:preferred_role` |
| Guest acessa o que não deveria | Role unauthenticated ampla | Reduzir permissões ou desabilitar guest |

## 13. Resumo rápido

- **Identity pool** troca tokens (user pool, social, SAML, OIDC, developer) por **credenciais AWS temporárias** via **STS**, associadas a **roles IAM**.
- Use quando o **cliente precisa acessar serviços AWS diretamente**; senão, **API + JWT** ou **presigned URLs**.
- **Menor privilégio por usuário**: `${cognito-identity.amazonaws.com:sub}`; trust policy com **`aud` e `amr`**.
- **Role mapping** por grupo/claims; **guest** desabilitado por padrão; **ABAC** com tags de sessão.
- Monitore (CloudTrail) e valide políticas (Policy Simulator/Access Analyzer).

2. Quando preferir presigned URLs a identity pool?
3. Que variável de política isola dados por usuário no S3/DynamoDB?
4. Para que servem as condições `aud` e `amr` na trust policy?
5. O que é role mapping?
6. Quais riscos das identidades não autenticadas?

**Respostas:**

1. Credenciais AWS temporárias (access key, secret e session token) obtidas via STS para uma role IAM.
2. Quando um backend pode autorizar e gerar URLs de curta duração, evitando dar credenciais AWS ao cliente.
3. `${cognito-identity.amazonaws.com:sub}` (Identity ID).
4. `aud` restringe ao ID do identity pool; `amr` distingue authenticated de unauthenticated.
5. Escolher a role por usuário com base em grupos, claims ou regras, além das roles padrão.
6. Acesso anônimo a credenciais, abuso, custos e exposição de dados; deve ter permissões mínimas ou ficar desabilitado.
7. Mapear atributos do usuário para tags de sessão e escrever políticas por tags (PrincipalTag).
