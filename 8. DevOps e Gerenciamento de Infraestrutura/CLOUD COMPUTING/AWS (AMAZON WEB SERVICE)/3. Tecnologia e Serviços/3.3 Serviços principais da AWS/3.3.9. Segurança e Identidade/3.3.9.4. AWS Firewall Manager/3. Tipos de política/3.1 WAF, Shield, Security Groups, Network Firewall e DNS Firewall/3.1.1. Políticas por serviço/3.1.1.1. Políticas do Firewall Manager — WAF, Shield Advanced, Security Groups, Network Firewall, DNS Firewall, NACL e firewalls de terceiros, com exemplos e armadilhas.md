### 3.1.1.1. Políticas do Firewall Manager — WAF, Shield Advanced, Security Groups, Network Firewall, DNS Firewall, NACL e firewalls de terceiros, com exemplos e armadilhas

> [!warning] Aviso
> O catálogo de tipos de política, os campos de `ManagedServiceData`, limites e comportamentos de cada tipo abaixo são **de memória e mudam** (o serviço evolui rápido). **Confirme na documentação do Firewall Manager de cada tipo de política.** JSONs e comandos são ilustrativos e **não foram executados**. Políticas com remediação **alteram recursos de produção**: use OU piloto e modo de detecção primeiro.

## 1. Visão geral dos tipos de política

Cada **tipo de política** corresponde a **um serviço de segurança** que o FMS **implanta e mantém** no escopo:

| Tipo | Serviço gerenciado | Recursos-alvo | Objetivo principal |
|---|---|---|---|
| **WAFV2** (e WAF Classic legado) | AWS WAF | ALB, API Gateway (stage REST), CloudFront, AppSync, Cognito user pool, App Runner… | **Web ACL** corporativa em todos os endpoints web |
| **SHIELD_ADVANCED** | AWS Shield Advanced | ALB/CLB, EIP, CloudFront, Route 53 hosted zones, Global Accelerator | Proteção DDoS avançada **inscrita** em escala |
| **SECURITY_GROUPS_COMMON** | VPC Security Groups | Instâncias/ENIs | **SG padrão** aplicado a recursos |
| **SECURITY_GROUPS_CONTENT_AUDIT** | VPC Security Groups | SGs existentes | **Auditar o conteúdo** das regras (proibidas/permitidas) |
| **SECURITY_GROUPS_USAGE_AUDIT** | VPC Security Groups | SGs existentes | **Limpar SGs não usados/redundantes** |
| **NETWORK_FIREWALL** | AWS Network Firewall | VPCs | **Firewall + policy** em VPCs |
| **DNS_FIREWALL** | Route 53 Resolver DNS Firewall | VPCs | **Rule groups de DNS** nas VPCs |
| **NETWORK_ACL_COMMON** (de memória) | Network ACLs | Subnets | Regras de NACL padrão/auditoria |
| **THIRD_PARTY_FIREWALL** | Palo Alto Cloud NGFW, Fortinet… | VPCs | Firewalls de terceiros gerenciados centralmente |

> Esta folha detalha cada tipo: **o que a política faz, como configurar e as armadilhas**.

## 2. Política de AWS WAF (WAFv2)

### 2.1 O que faz

Cria e mantém uma **web ACL** com **rule groups** definidos pela segurança central e a **associa automaticamente** aos recursos do escopo; opcionalmente **centraliza os logs**.

### 2.2 Estrutura da web ACL gerenciada pelo FMS

```
Web ACL criada pelo FMS (por conta/região):
  ┌ 1. PRE-PROCESS rule groups (first)   ← definidos pela segurança central (sempre avaliados primeiro)
  ├ 2. Regras/rule groups da CONTA-MEMBRO ← os times de aplicação podem adicionar
  └ 3. POST-PROCESS rule groups (last)   ← definidos pela segurança central (avaliados por último)
  Ação padrão: ALLOW (ou BLOCK)
```

| Elemento | Detalhe |
|---|---|
| **First rule groups** | Baseline obrigatório (ex.: **AWS Managed Rules – Core**, **Known bad inputs**, **IP reputation**) |
| **Last rule groups** | Fechamento (ex.: bloqueio geográfico, lista de IPs proibidos) |
| **Regras da conta** | Permitem **customização local** sem perder o baseline (depende da opção **`overrideCustomerWebACLAssociation`**) |
| **Ação padrão** | `ALLOW` ou `BLOCK` (cuidado com `BLOCK` por padrão) |
| **Logging** | **Kinesis Data Firehose** (destino com prefixo `aws-waf-logs-`) com **campos redigidos** (cabeçalhos sensíveis) |
| **Associação a recursos existentes** | Opção de **associar a recursos que já têm web ACL** (`overrideCustomerWebACLAssociation`) — **substitui** a ACL local (cuidado) |

### 2.3 Escopo e tipos de recurso

- **Regional**: ALB, API Gateway (REST stage), AppSync, Cognito user pool, App Runner — política **por região**.
- **CloudFront**: política **global** (`us-east-1`), com escopo `CLOUDFRONT`.

### 2.4 Exemplo (`ManagedServiceData` legível)

```json
{
  "type": "WAFV2",
  "preProcessRuleGroups": [
    { "managedRuleGroupIdentifier": { "vendorName": "AWS", "managedRuleGroupName": "AWSManagedRulesCommonRuleSet" },
      "overrideAction": { "type": "NONE" }, "ruleGroupType": "ManagedRuleGroup",
      "sampledRequestsEnabled": true, "cloudWatchMetricsEnabled": true },
    { "managedRuleGroupIdentifier": { "vendorName": "AWS", "managedRuleGroupName": "AWSManagedRulesKnownBadInputsRuleSet" },
      "overrideAction": { "type": "NONE" }, "ruleGroupType": "ManagedRuleGroup",
      "sampledRequestsEnabled": true, "cloudWatchMetricsEnabled": true }
  ],
  "postProcessRuleGroups": [],
  "defaultAction": { "type": "ALLOW" },
  "overrideCustomerWebACLAssociation": false,
  "loggingConfiguration": { "logDestinationConfigs": ["arn:aws:firehose:us-east-1:222222222222:deliverystream/aws-waf-logs-central"] }
}
```

### 2.5 Armadilhas do WAF no FMS

- **`overrideAction: COUNT`** nas primeiras semanas: modo de observação (`COUNT`) antes de **bloquear**; senão há **falsos positivos** em produção.
- **Capacidade (WCU)** da web ACL é **limitada**: muitos rule groups gerenciados podem **estourar**.
- **Sobrescrever a web ACL local** (`overrideCustomerWebACLAssociation=true`) **remove** as regras específicas que os times criaram.
- **Logs com dados sensíveis** (cabeçalhos, cookies): configure **redaction**.
- **Custo**: WAF cobra por **web ACL, regras e requisições**; multiplicado pelo número de contas.

## 3. Política de Shield Advanced

### 3.1 O que faz

**Inscreve** recursos em **Shield Advanced** (ALB, CLB, EIP, CloudFront, Route 53, Global Accelerator) e, se configurado, **habilita resposta automática de camada de aplicação** (ajuste de regras no WAF durante ataques).

| Elemento | Detalhe (de memória — confirmar) |
|---|---|
| **Pré-requisito** | **Assinatura do Shield Advanced** (taxa mensal por **organização** com compromisso de 12 meses, mais uso de dados) |
| **Escopo** | Contas e tipos de recurso; opcionalmente por **tags** |
| **Resposta automática de camada de aplicação** | Requer **web ACL** associada ao recurso; o Shield pode **adicionar regras** de bloqueio/contagem durante ataques |
| **Proteção de limite de uso (cost protection)** | Créditos por picos causados por DDoS (condições do serviço) |
| **Health-based detection** | Associação a **Route 53 health checks** para melhor detecção |

### 3.2 Armadilhas

- **Custo**: a assinatura tem **compromisso**; avalie o número de contas (taxa por organização) e quais recursos realmente precisam.
- **Inscrição massiva** de recursos sem relevância → custos de transferência/uso.
- **Falta de WAF**: a resposta de aplicação exige **web ACL** (combinar com política WAF).

## 4. Políticas de Security Groups

São **três subtipos** com objetivos diferentes — muito cobradas em provas.

### 4.1 Common security group policy (SG comum)

| Característica | Detalhe |
|---|---|
| **O que faz** | **Cria e associa um SG “padrão”** (definido por você) a **ENIs/instâncias/…** no escopo |
| **SG primário** | O **SG modelo** é criado na conta administradora; o FMS **replica** em cada VPC das contas-membro |
| **Remediação** | **Associa** o SG replicado aos recursos; **mantém** as regras sincronizadas com o modelo |
| **Uso** | Baseline de acesso: ex.: liberar **SSH apenas do bastion corporativo**, **monitoramento**, **antivírus**/agentes |
| **Cuidado** | Recursos novos recebem o SG automaticamente; **remover** o SG manualmente é corrigido pelo FMS |

### 4.2 Content audit security group policy (auditoria de conteúdo)

| Característica | Detalhe |
|---|---|
| **O que faz** | **Audita as regras** dos SGs existentes contra **regras permitidas ou proibidas** |
| **Modos** | **Allow list**: só regras compatíveis com o SG de referência são aceitáveis. **Deny list**: regras **proibidas** (ex.: `0.0.0.0/0` em 22/3389) |
| **Remediação** | Opcional: **remover** regras não conformes (auditoria + correção) |
| **Uso típico** | “**Nenhum SG pode abrir RDP/SSH para o mundo**”, “**nenhum SG com `All traffic`**” |
| **Cuidado** | Corrigir em produção pode **cortar acessos legítimos**: **detecção primeiro**, comunicar, janelas |

Exemplo (conceitual) — **deny list**:

```json
{
  "type": "SECURITY_GROUPS_CONTENT_AUDIT",
  "securityGroupAction": { "type": "DENY" },
  "securityGroups": [ { "id": "sg-0modeloProibido" } ]
}
```

(o SG referência contém as **regras proibidas**; SGs com regras equivalentes ficam **não conformes**.)

### 4.3 Usage audit security group policy (auditoria de uso)

| Característica | Detalhe |
|---|---|
| **O que faz** | Identifica **SGs não usados** (sem ENIs associadas) e **redundantes** (regras idênticas) |
| **Remediação** | Opcional: **excluir** SGs não usados/redundantes após **período de graça** (minutos configuráveis) |
| **Uso** | **Higiene**: reduzir superfície e o limite de SGs por VPC |
| **Cuidado** | **SG “não usado” hoje** pode ser **referenciado por regras** de outros SGs/IaC que vão associá-lo depois: confirme referências, **tags de preservação** e período de graça |

### 4.4 Tabela comparativa de SG

| Subtipo | Pergunta que responde | Ação do FMS |
|---|---|---|
| **Common** | “Todos os recursos têm o SG baseline?” | Replica e **associa** |
| **Content audit** | “Alguma regra proibida/fora do padrão?” | Detecta/**remove** regras |
| **Usage audit** | “Há SGs sobrando?” | Detecta/**exclui** SGs |

## 5. Política de Network Firewall

| Elemento | Detalhe |
|---|---|
| **O que faz** | Implanta **Network Firewall + firewall policy + endpoints** nas **VPCs** do escopo |
| **Modelos** | **Distribuído** (um firewall por VPC; o FMS cria/gerencia subnets e endpoints) e **centralizado** (uma **VPC de inspeção** e **roteamento** pelo Transit Gateway/outros; o FMS monitora a configuração) |
| **Rule groups** | **Stateless e stateful** definidos na política (referências a rule groups existentes ou geridos) + opção de **a conta-membro adicionar** rule groups próprios |
| **Subnets de firewall** | O FMS **cria subnets de firewall** por AZ (distribuído) ou exige as da VPC de inspeção (centralizado) |
| **Roteamento** | **Rotas** podem ser **monitoradas/alertadas** (o FMS verifica se o tráfego é desviado ao endpoint) — **auto-remediação de rotas** é limitada (de memória; confirmar); planeje a parte de **route tables** com IaC |
| **Logging** | Configuração de logs (alert/flow) para S3/CloudWatch/Firehose |
| **Escopo** | VPCs por conta/OU/tags |

Armadilhas:

- **CIDRs de subnet de firewall**: o FMS precisa de **espaço de endereços** livre nas VPCs.
- **Roteamento assimétrico** em topologias complexas.
- **Custo** multiplicado: **endpoint por AZ por VPC** (ver a folha de custos do Network Firewall).
- **Conflito** com firewalls já implantados manualmente.

(Veja o serviço completo em [[0 AWS Network Firewall (Tópicos )|AWS Network Firewall]].)

## 6. Política de DNS Firewall

| Elemento | Detalhe |
|---|---|
| **O que faz** | **Associa rule groups de Route 53 Resolver DNS Firewall** a todas as VPCs do escopo |
| **Rule groups** | Contêm **listas de domínios** e **ações** (`ALLOW`, `BLOCK`, `ALERT`) — podem incluir **listas gerenciadas pela AWS** (domínios maliciosos, botnets) |
| **Compartilhamento** | Rule groups são **compartilhados** com as contas via **AWS RAM** |
| **Ordem** | **Prioridade** de rule groups por VPC; a política define **dois blocos** (primeiros e últimos), de forma análoga ao WAF |
| **Falha aberta/fechada** | Configuração de **fail-open** do DNS Firewall (comportamento quando o firewall não responde) |
| **Uso** | Bloquear **consultas a domínios maliciosos** (C2, exfiltração por DNS) em **todas as VPCs** |

Combina com o Network Firewall: DNS Firewall protege a **resolução de nomes**; o Network Firewall protege **HTTP/TLS** e demais protocolos.

## 7. Política de Network ACL (de memória — confirmar)

Permite **definir regras padrão de NACL** e **auditar** NACLs nas subnets do escopo (por exemplo, **negar tráfego de entrada** de intervalos conhecidos como maliciosos ou **exigir** certas regras). Suporta modo de **auditoria** e remediação. Cuidado: NACLs são **stateless** e **numeradas**: a política precisa **coexistir** com regras locais (ordem/numeração).

## 8. Política de firewalls de terceiros

| Elemento | Detalhe |
|---|---|
| **Produtos** | **Palo Alto Networks Cloud NGFW**, **Fortinet** (de memória) e outros parceiros |
| **O que faz** | Implanta e gerencia **endpoints do firewall do fornecedor** nas VPCs (usando **Gateway Load Balancer**) e **associa a política do fornecedor** |
| **Pré-requisito** | **Assinatura no Marketplace** e integração do console do fornecedor com o FMS |
| **Quando** | Padronização multicloud, recursos específicos de fornecedor, requisitos de compliance |
| **Cuidado** | **Custo de licença** e **dependência** do fornecedor |

## 9. Comparação resumida

| Política | Previne/detecta | Corrige automaticamente? | Principal risco |
|---|---|---|---|
| **WAF** | Detecta ALBs/stages sem web ACL | **Sim** (associa/cria ACL) | Bloqueio indevido; WCU; sobrescrever ACL local |
| **Shield Advanced** | Detecta recursos sem inscrição | **Sim** (inscreve) | Custo da assinatura |
| **SG common** | Detecta recursos sem o SG padrão | **Sim** (associa) | SG padrão amplo demais |
| **SG content audit** | Detecta regras proibidas | **Sim** (remove regras) | Cortar acesso legítimo |
| **SG usage audit** | Detecta SGs não usados | **Sim** (exclui) | Excluir SG que seria usado/referenciado |
| **Network Firewall** | Detecta VPCs sem firewall/rotas | Parcialmente (cria firewall; rotas limitadas) | Custo, roteamento, CIDR |
| **DNS Firewall** | Detecta VPCs sem associação | **Sim** (associa) | Bloqueio indevido de domínios |

## 10. Exemplos de cenários

### 10.1 “Nenhum SG pode abrir SSH/RDP para o mundo”

- Política **content audit (deny)**, escopo **organização inteira**, **detecção** primeiro; depois **remediação** (remover as regras) com aviso e exceção por **tag** governada.

### 10.2 “Todo ALB público precisa de WAF com o baseline”

- Política **WAFV2** (regional), escopo **OU Producao**, tipo **ALB**, first rule groups AWS managed; `COUNT` por 2 semanas, depois `NONE`/bloqueio; logs para Firehose central.

### 10.3 “Toda VPC de produção com DNS Firewall”

- Política **DNS Firewall**, escopo **OU Producao**, rule groups compartilhados via RAM, listas gerenciadas AWS + lista própria.

### 10.4 “Toda VPC com Network Firewall (modelo distribuído)”

- Política **NETWORK_FIREWALL**, escopo **tag `inspecao=true`**, subnets criadas pelo FMS, rule groups centrais, logs em S3.

## 11. Erros comuns

- **Ligar remediação** de SG content audit em produção sem comunicar → incidentes de acesso.
- **WAF sem fase `COUNT`**.
- **Sobrescrever web ACL local** sem avisar os times.
- **Estouro de WCU**.
- **Shield Advanced em tudo** sem análise de custo.
- **Usage audit excluindo SGs** referenciados por IaC futura.
- **SG common muito permissivo** (vira porta aberta replicada em toda a organização).
- **DNS Firewall sem exceção** para domínios legítimos internos → quebra de resolução.
- **Network Firewall via FMS sem planejar CIDR/rotas**.
- **Acumular políticas sobrepostas** para o mesmo recurso.

## 12. Troubleshooting

| Sintoma | Causa provável | Ação |
|---|---|---|
| ALB sem web ACL apesar da política | Tipo de recurso/escopo/região; Config; interno vs público | Revisar o escopo e `ResourceType`; checar o status de conformidade |
| Web ACL criada, mas regras locais sumiram | `overrideCustomerWebACLAssociation=true` | Ajustar a política e restaurar a ACL local via IaC |
| Falsos positivos no WAF | Regras gerenciadas em `NONE` | `COUNT` + exclusões de regras; ajustar |
| SG “não conforme” persistente | Regra em uso por aplicação; correção desligada | Tratar a regra; excluir via exceção |
| Política de Network Firewall falha | Sem CIDR livre; limites de subnets/AZs | Liberar CIDR; revisar |
| DNS Firewall bloqueando domínio legítimo | Lista gerenciada ampla | Exceção `ALLOW` com prioridade menor |
| Shield: recurso não inscrito | Sem assinatura/tipo não suportado | Verificar a assinatura e os tipos |

## 13. Resumo rápido

- **WAFV2**: **web ACL** com **first/last rule groups** + regras locais; `COUNT` antes de bloquear; cuidado com **WCU** e **sobrescrita**.
- **Shield Advanced**: **inscreve** recursos; resposta de aplicação exige **WAF**; custo com **compromisso**.
- **SG**: **common** (replica e associa SG baseline), **content audit** (allow/deny de regras), **usage audit** (SGs não usados/redundantes).
- **Network Firewall**: **distribuído** ou **centralizado**; atenção a **CIDR, rotas e custo**.
- **DNS Firewall**: **rule groups** compartilhados via **RAM**, listas gerenciadas AWS.
- **NACL** e **terceiros** (Palo Alto/Fortinet via GWLB) completam o catálogo.
- Em todos: **detecção → remediação**, escopo por **OU**, exceções governadas.

## 🧩 Quiz de Fixação

1. O que são first e last rule groups em uma política de WAF?
2. Qual a diferença entre SG common, content audit e usage audit?
3. Por que a política de Shield Advanced pode precisar de uma política de WAF?
4. Qual risco ao ligar a remediação de content audit em produção?
5. Para que serve o `COUNT` ao introduzir regras gerenciadas de WAF?
6. Como os rule groups de DNS Firewall chegam às contas-membro?
7. Qual o risco da opção `overrideCustomerWebACLAssociation`?

**Respostas:**

1. Rule groups definidos pela segurança central avaliados antes (first) e depois (last) das regras locais da conta-membro na mesma web ACL.
2. Common replica e associa um SG padrão aos recursos; content audit verifica e pode remover regras proibidas ou fora do padrão; usage audit identifica e pode excluir SGs não usados ou redundantes.
3. Porque a resposta automática de camada de aplicação do Shield Advanced atua adicionando regras a uma web ACL associada ao recurso.
4. Remover regras que sustentam acessos legítimos, causando indisponibilidade ou perda de acesso administrativo.
5. Observar quais requisições seriam bloqueadas, sem bloquear, para ajustar falsos positivos antes de ativar o bloqueio.
6. São compartilhados por AWS RAM e associados às VPCs pela política do FMS.
7. Substituir a web ACL local do recurso pela ACL do FMS, perdendo as regras específicas criadas pelos times.
