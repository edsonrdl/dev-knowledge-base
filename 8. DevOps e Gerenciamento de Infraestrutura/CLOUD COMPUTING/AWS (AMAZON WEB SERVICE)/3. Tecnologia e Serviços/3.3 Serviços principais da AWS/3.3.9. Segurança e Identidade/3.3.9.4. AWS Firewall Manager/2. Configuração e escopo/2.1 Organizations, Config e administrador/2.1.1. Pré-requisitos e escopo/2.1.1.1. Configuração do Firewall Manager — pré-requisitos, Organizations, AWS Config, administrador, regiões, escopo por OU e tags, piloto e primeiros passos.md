### 2.1.1.1. Configuração do Firewall Manager — pré-requisitos, Organizations, AWS Config, administrador, regiões, escopo por OU e tags, piloto e primeiros passos

> [!warning] Aviso
> Requisitos, nomes de ações de API, limites de administradores, comportamento de escopo e opções de remoção de política abaixo são **de memória e mudam**. **Confirme na documentação do Firewall Manager e do AWS Config.** Comandos, JSONs e IDs são ilustrativos/fictícios e **não foram executados**. Habilitar o AWS Config em todas as contas e regiões e criar políticas com auto-remediação **gera custo e altera recursos**: comece por uma OU piloto.

## 1. Visão geral da configuração

Configurar o Firewall Manager é uma **sequência de pré-requisitos** seguida de **políticas bem delimitadas**. Pular um pré-requisito é a causa número um de “a política não faz nada”.

```
[1] Organizations (all features)
        ▼
[2] Acesso confiável / serviços integrados habilitados
        ▼
[3] Conta administradora do FMS (Segurança) designada
        ▼
[4] AWS Config habilitado nas contas-membro e nas regiões-alvo
        ▼
[5] (conforme o tipo) Pré-requisitos do serviço: Shield Advanced, WAF logging, Network Firewall, etc.
        ▼
[6] Política em modo DETECÇÃO → piloto → auto-remediação → expansão
```

## 2. Pré-requisitos em detalhe

### 2.1 AWS Organizations com “all features”

| Requisito | Detalhe |
|---|---|
| **Organização existente** | O FMS depende da **estrutura de contas/OUs** |
| **All features habilitado** | Organizações apenas com **consolidated billing** **não** servem; é preciso habilitar **todos os recursos** |
| **Conta de gestão** | Fará a **designação do administrador** (uma vez) |
| **Estrutura de OUs** | Planeje OUs por **ambiente/criticidade** (Prod, Homolog, Dev, Sandbox) para **escopar** políticas com precisão |
| **Contas suspensas** | Não participam |

### 2.2 Conta administradora do Firewall Manager

- Pode ser a **conta de gestão** (padrão) ou, **recomendado**, uma **conta de Segurança dedicada** (administradora delegada).
- Há um conceito de **administrador padrão** e a possibilidade de **administradores adicionais com escopo restrito** (ex.: o time de rede administra apenas políticas de Network Firewall nas OUs de rede) — de memória; confirme limites e disponibilidade.
- **A designação** é feita pela **conta de gestão**:

```bash
# Na conta de GESTÃO (ilustrativo)
aws fms associate-admin-account --admin-account 222222222222
aws fms get-admin-account
```

> [!tip] Boa prática
> **Não** use a conta de gestão para operar políticas. Mantenha-a mínima e delegue a uma **conta de Segurança** com acesso via **SSO**, MFA e permissões enxutas.

### 2.3 AWS Config

| Requisito | Detalhe |
|---|---|
| **Habilitar** | Em **cada conta-membro** e **cada região** onde haverá política |
| **Gravador (recorder)** | Registrando **os tipos de recurso relevantes** (ex.: `AWS::EC2::SecurityGroup`, `AWS::ElasticLoadBalancingV2::LoadBalancer`, `AWS::EC2::VPC`, `AWS::ApiGateway::Stage`, `AWS::CloudFront::Distribution`) |
| **Como habilitar em escala** | **CloudFormation StackSets**, **Control Tower** ou **Config conformance packs/organization** (aggregator); automatize para contas novas |
| **Custo** | Cobrança por **item de configuração registrado** (ver folha de custos) |
| **Por quê** | O FMS **descobre recursos e avalia conformidade** com base no Config |

> [!warning] Sem Config, sem política
> Se o Config não estiver gravando os recursos do escopo, o FMS **não os enxerga**. O sintoma é uma política “válida” que **não aplica nada**.

### 2.4 Pré-requisitos por tipo de política

| Tipo | Pré-requisito adicional (de memória — confirmar) |
|---|---|
| **WAF/WAFv2** | Nenhum extra obrigatório; para **logs centralizados**, um **Kinesis Data Firehose** (nome prefixado `aws-waf-logs-`) |
| **Shield Advanced** | **Assinatura do Shield Advanced** na conta administradora (e nas membros conforme o modelo); para respostas automáticas, **web ACL** associada; **SRT** access opcional |
| **Security Groups** | SG **primário** (modelo) na conta administradora, ou regras de auditoria definidas |
| **Network Firewall** | **Rule groups** existentes (ou criados pela política); **subnets de firewall** (a política pode criar/exigir) e **estratégia de roteamento** (distribuída ou centralizada) |
| **DNS Firewall** | **Rule groups de DNS Firewall** criados/compartilhados (RAM) |
| **Firewalls de terceiros** | Assinatura do produto no **Marketplace** e integração do fornecedor |

## 3. Regiões e escopo global

- Políticas são **regionais**: criar uma política em `us-east-1` **não** protege `sa-east-1`. Para cada região usada, **uma política** (ou uma política **multi-região** quando suportada — confirme).
- **Recursos globais** (**CloudFront**, WAF **global/Classic** para CloudFront, Route 53) exigem política **global**, criada na região **`us-east-1`** (de memória).
- Habilite o FMS/Config **em todas as regiões** onde há workloads; use **SCP de regiões** para impedir uso de regiões sem proteção.

```
Política regional (us-east-1)   ─▶ ALB, API GW, VPCs, SGs de us-east-1
Política regional (sa-east-1)   ─▶ ALB, API GW, VPCs, SGs de sa-east-1
Política global   (us-east-1)   ─▶ CloudFront
```

## 4. Escopo da política

O **escopo** define **onde** a política se aplica. Quatro dimensões:

| Dimensão | Opções |
|---|---|
| **Contas** | **Toda a organização**, **OUs específicas** (incluindo filhas), **contas específicas**; **inclusão** ou **exclusão** |
| **Tipo de recurso** | ALB, CLB, API Gateway stage, CloudFront, EIP, ENI, VPC, etc., conforme o tipo de política |
| **Tags de recurso** | **Incluir** apenas recursos com certas tags (ex.: `ambiente=prod`) **ou excluir** por tags (`fms-exempt=true`) |
| **Região** | A região em que a política é criada |

### 4.1 Estratégia de escopo recomendada

| Fase | Escopo |
|---|---|
| **Piloto** | **Uma OU de teste** (ou 1–2 contas), **detecção apenas** |
| **Expansão 1** | OU **Dev/Homolog**, auto-remediação ligada |
| **Expansão 2** | OU **Prod** (ou conforme criticidade), com **janela** e comunicação |
| **Organização inteira** | Para baselines universais (ex.: SG sem 0.0.0.0/0 para portas de administração) |
| **Exceções** | **Tags de isenção** com governança (quem pode colocar a tag, validade) |

### 4.2 Escopo por OU vs por lista de contas

- **OU**: contas novas na OU **herdam** a política automaticamente — **recomendado**.
- **Lista de contas**: contas novas **ficam fora** — risco de lacunas.

### 4.3 Exclusões e exceções

- **Excluir contas** de sandbox/pesquisa só com **registro de aprovação**.
- **Tag de isenção** em recursos: controle quem pode **aplicá-la** (SCP/IAM condicionando `TagResource` na chave de isenção ao time de segurança), senão vira um atalho para fugir da política.

## 5. Ações de remediação

| Modo | Comportamento | Uso |
|---|---|---|
| **Somente detecção** (auto-remediação **desligada**) | Reporta **recursos não conformes**; **não altera nada** | **Piloto**, descoberta, fases iniciais |
| **Auto-remediação** (**ligada**) | **Corrige** (cria/associa proteções, adiciona SGs, etc.) | Após validação |
| **Remediação de recursos já existentes** | Algumas políticas permitem aplicar a **recursos existentes**, não só novos (confirmar a opção por tipo) | Cobertura total |
| **Remoção de recursos da política** | Ao **excluir** a política, é possível **remover os recursos criados** (opção `DeleteAllPolicyResources`) | Cuidado: pode **retirar proteções** |

> [!warning] Cuidado ao excluir políticas
> A opção de **apagar todos os recursos** criados pela política **remove web ACLs associações, firewalls, SGs de política** etc. Em produção, exclua políticas **com plano** e, se quiser parar de gerenciar sem remover, **desative a remediação** em vez de apagar (confirme a opção exata na documentação).

## 6. Primeiros passos (passo a passo ilustrativo)

### 6.1 Habilitar tudo na conta de gestão

```bash
# Organizations já com all features. Designar o administrador do FMS:
aws fms associate-admin-account --admin-account 222222222222   # na conta de gestão
```

### 6.2 Config em escala (exemplo conceitual)

```
StackSet "habilitar-config" → OU Producao + OU Homolog + OU Dev
   (gravador de configuração + canal de entrega + regras mínimas) em us-east-1, sa-east-1
Control Tower: habilitar Config automaticamente em contas novas (landing zone)
```

### 6.3 Política de teste — detecção, OU piloto

```json
{
  "PolicyName": "waf-baseline-alb-piloto",
  "SecurityServicePolicyData": {
    "Type": "WAFV2",
    "ManagedServiceData": "{\"type\":\"WAFV2\",\"preProcessRuleGroups\":[{\"managedRuleGroupIdentifier\":{\"vendorName\":\"AWS\",\"managedRuleGroupName\":\"AWSManagedRulesCommonRuleSet\"},\"ruleGroupArn\":null,\"overrideAction\":{\"type\":\"NONE\"},\"excludeRules\":[],\"sampledRequestsEnabled\":true,\"cloudWatchMetricsEnabled\":true,\"ruleGroupType\":\"ManagedRuleGroup\"}],\"postProcessRuleGroups\":[],\"defaultAction\":{\"type\":\"ALLOW\"},\"overrideCustomerWebACLAssociation\":false,\"loggingConfiguration\":null}"
  },
  "ResourceType": "AWS::ElasticLoadBalancingV2::LoadBalancer",
  "ResourceTypeList": ["AWS::ElasticLoadBalancingV2::LoadBalancer"],
  "ExcludeResourceTags": false,
  "RemediationEnabled": false,
  "IncludeMap": { "ORGUNIT": ["ou-abcd-11111111"] }
}
```

```bash
aws fms put-policy --policy file://waf-baseline-alb-piloto.json --region us-east-1
aws fms list-compliance-status --policy-id <id> --region us-east-1
```

(`RemediationEnabled: false` → **só detecção**. Depois de validar, alterar para `true` e **expandir o escopo**.)

### 6.4 Revisar conformidade e evoluir

1. Examine **recursos não conformes** (esperado: ALBs sem web ACL).
2. Verifique **falsos positivos**/exceções (ALBs internos que **não** devem ter WAF).
3. Ajuste **tipos de recurso/tags/exclusões**.
4. Ative **remediação** na OU piloto; valide **impacto** (latência, bloqueios).
5. **Expanda** em ondas, comunicando os times.

## 7. Organização das políticas (governança)

| Prática | Detalhe |
|---|---|
| **Convenção de nomes** | `<tipo>-<escopo>-<ambiente>` (ex.: `sg-audit-org-prod`) |
| **Uma política por finalidade** | Evitar políticas “faz-tudo” |
| **Documentação** | Dono, justificativa, escopo, exceções, data de revisão |
| **IaC** | Políticas via **CloudFormation (`AWS::FMS::Policy`)**/Terraform, em Git, com revisão e pipeline |
| **Versionamento e mudança** | PR + aprovação; **change windows** para políticas de impacto |
| **Revisão periódica** | Trimestral: escopo, exceções, regras, custos |
| **Inventário de exceções** | Dono, motivo, validade |

```yaml
# CloudFormation (ilustrativo e resumido) — política de auditoria de Security Groups
Resources:
  SgAuditoriaAdmin:
    Type: AWS::FMS::Policy
    Properties:
      PolicyName: sg-audit-portas-admin-org
      ExcludeResourceTags: false
      RemediationEnabled: false
      ResourceType: AWS::EC2::SecurityGroup
      SecurityServicePolicyData:
        Type: SECURITY_GROUPS_CONTENT_AUDIT
        ManagedServiceData: '{"type":"SECURITY_GROUPS_CONTENT_AUDIT","securityGroupAction":{"type":"DENY"},"securityGroups":[{"id":"sg-0abc123"}]}'
      IncludeMap: { ORGUNIT: [ou-abcd-11111111] }
```

## 8. Checklist de configuração

- [ ] Organizations com **all features**; OUs desenhadas por ambiente/criticidade
- [ ] **Conta de Segurança** designada como administradora do FMS (e administradores com escopo, se aplicável)
- [ ] **AWS Config** habilitado e gravando os tipos de recurso necessários em **todas** as contas/regiões-alvo (e em contas novas)
- [ ] **Pré-requisitos por tipo** atendidos (Shield, Firehose, rule groups, subnets)
- [ ] **Políticas por região** (e global para CloudFront, em `us-east-1`)
- [ ] **Escopo por OU**; tags de isenção **governadas**
- [ ] **Piloto**: detecção → remediação → expansão
- [ ] **Políticas como código**; revisão e aprovação
- [ ] **SCP** protegendo contra desabilitar Config/FMS (ver folha de segurança)
- [ ] **Notificações** (SNS) e painel de conformidade configurados

## 9. Erros comuns

- **Organizations sem all features** → o FMS não pode ser habilitado.
- **Config não habilitado** em regiões/contas → política sem efeito.
- **Política criada só em uma região**.
- **CloudFront sem política global** em `us-east-1`.
- **Escopo por lista fixa de contas** → contas novas desprotegidas.
- **Auto-remediação direta em prod** sem piloto.
- **Tag de isenção sem governança**: qualquer um se isenta.
- **Remover a política com opção destrutiva** sem plano.
- **Administrar na conta de gestão**.
- **Políticas sobrepostas** gerando recursos duplicados ou conflitos.

## 10. Troubleshooting

| Sintoma | Causa provável | Ação |
|---|---|---|
| `associate-admin-account` falha | Organizations sem all features; não é a conta de gestão; permissões | Verificar a organização e executar na conta de gestão |
| Política sem recursos avaliados | Config não grava; escopo incorreto; região | Habilitar Config; revisar o escopo e a região |
| Política em estado de erro | Pré-requisito ausente (Firehose, Shield, rule group) | Ver a mensagem de erro e atender ao requisito |
| Conta nova ficou de fora | Escopo por lista | Migrar para escopo por OU |
| Recursos não corrigidos com remediação ligada | Falta de permissão/role; tipo de recurso não suportado; limite de recursos | Ver `get-compliance-detail` e os motivos |
| Conflito com regras locais (WAF) | Ordem first/last, override | Revisar a configuração de rule groups e de associação |
| Excesso de custos após ligar | Config em tudo, muitas políticas × regiões | Revisar o escopo (folha de custos) |

## 11. Resumo rápido

- Ordem: **Organizations (all features)** → **administrador (conta de Segurança)** → **AWS Config em contas/regiões** → **pré-requisitos do tipo** → **política**.
- **Regional**: política por região; **global** (CloudFront) em **`us-east-1`**.
- **Escopo**: contas/OUs (preferir **OU**), tipos de recurso, **tags** (inclusão/exclusão), com **isenções governadas**.
- **Remediação**: **detecção** (piloto) → **auto-remediação** → expansão; cuidado com a **exclusão de política** (pode apagar recursos criados).
- **IaC** (`AWS::FMS::Policy`), convenção de nomes, documentação e revisão periódica.
- **Sem Config, sem política.**

## 🧩 Quiz de Fixação

1. Por que Organizations precisa estar com “all features”?
2. Quem designa o administrador do Firewall Manager e qual conta é recomendada?
3. Qual o papel do AWS Config na configuração?
4. Em qual região se cria a política global do CloudFront?
5. Por que preferir escopo por OU em vez de lista de contas?
6. Qual a estratégia segura de adoção de uma política nova?
7. Qual o risco de excluir uma política com a opção de apagar os recursos?

**Respostas:**

1. Porque o FMS depende dos recursos integrados de Organizations; com apenas consolidated billing não é possível habilitá-lo.
2. A conta de gestão da organização designa; recomenda-se uma conta de Segurança dedicada como administradora delegada.
3. Fornece o registro e a descoberta dos recursos que o FMS avalia; sem o Config gravando, a política não enxerga nem aplica nada.
4. Em us-east-1.
5. Porque contas novas na OU herdam a política automaticamente; com lista fixa elas ficam desprotegidas.
6. Começar em uma OU piloto com detecção, revisar conformidade e exceções, ligar auto-remediação no piloto e expandir em ondas.
7. Remover as proteções criadas pela política (web ACLs, firewalls, SGs), deixando recursos sem proteção.
