### 4.1.1.1. Implantação do Directory Service — VPC, subnets e AZs, DNS e DHCP options, security groups e portas, multi-região, compartilhamento, backup e recuperação

> [!warning] Aviso
> Portas, comportamento do security group gerado, limites de snapshots, tempo de provisionamento, recursos de multi-região e regras de DNS abaixo são **de memória e mudam**. **Confirme na documentação do Directory Service e da VPC.** CIDRs, IDs e comandos são fictícios/ilustrativos e **não foram executados**. Errar DNS ou rotas em um diretório em produção **quebra a autenticação** de todas as máquinas: planeje, teste e tenha rollback.

## 1. Por que a implantação é a parte difícil

Criar um diretório é um comando; **fazê-lo funcionar bem** depende de **rede e DNS**. A maior parte dos incidentes com Directory Service vem de **DNS, rotas, portas e AZs**, não do serviço em si. Esta folha cobre as decisões de arquitetura que evitam esses incidentes.

```
Decisões de implantação
  1. Onde (conta, região, VPC)?                2. Quais subnets/AZs?
  3. Como as máquinas resolvem o domínio?      4. Quais portas/security groups?
  5. Como conectar on-prem e outras VPCs?      6. Como proteger (backup/DR/multi-região)?
```

## 2. VPC, subnets e zonas de disponibilidade

### 2.1 Requisitos

| Item | Detalhe |
|---|---|
| **Duas subnets** | Em **AZs diferentes** (obrigatório); o diretório coloca **um DC em cada** |
| **Subnets privadas** | Recomendado (DCs não devem ter IP público) |
| **Espaço de IPs** | Cada DC consome IPs; reserve **faixa folgada** (inclusive para **DCs adicionais**) |
| **DNS na VPC** | **DNS resolution** e **DNS hostnames** habilitados |
| **Região** | O diretório vive **numa região**; workloads de outras regiões precisam de rota ou de **réplica** (multi-região) |
| **VPC dedicada** | Em ambientes grandes, uma **VPC de identidade** (conta de identidade) com conectividade por **Transit Gateway** |

### 2.2 Escolha de conta e VPC

| Modelo | Quando |
|---|---|
| **Diretório por conta/VPC** | Poucas contas; isolamento total; mais custo e administração |
| **Diretório centralizado (conta de Identidade) + compartilhamento** | **Padrão corporativo**: um diretório, várias contas |
| **Diretório em VPC de rede/compartilhada** | Conectividade simples a todas as cargas, com **governança** clara |

## 3. DNS e DHCP options (o ponto mais crítico)

### 3.1 O AD depende de DNS

O AD localiza DCs por **registros SRV** no DNS. Se a máquina **não resolve** `corp.example.com` para os **DCs**, o **domain join** e o **login** falham.

### 3.2 Como as instâncias resolvem o domínio

| Estratégia | Descrição | Quando |
|---|---|---|
| **DHCP option set da VPC** | Define **servidores DNS = IPs dos DCs** e o **domain name** | VPC **dedicada a cargas do domínio** (simples) |
| **Route 53 Resolver rules (forwarding)** | **Regra de encaminhamento**: consultas ao domínio (`corp.example.com`) → IPs dos DCs; o restante segue o resolver padrão | **Recomendado** em VPCs **mistas** e multi-conta (compartilhar regras via **RAM**) |
| **DNS conditional forwarders** | Encaminhamento **entre servidores DNS** (AD ↔ on-prem) | Integração com on-premises |
| **Hosts file/cliente** | Configuração local | Exceção; **evite** |

```bash
# DHCP option set apontando para os DCs do diretório (ilustrativo)
aws ec2 create-dhcp-options --dhcp-configurations \
  "Key=domain-name,Values=corp.example.com" \
  "Key=domain-name-servers,Values=10.0.1.10,10.0.2.10"
aws ec2 associate-dhcp-options --dhcp-options-id dopt-0abc --vpc-id vpc-0abc

# Regra de encaminhamento do Route 53 Resolver (ilustrativo)
aws route53resolver create-resolver-rule --creator-request-id r1 --name ad-corp \
  --rule-type FORWARD --domain-name corp.example.com \
  --target-ips Ip=10.0.1.10,Port=53 Ip=10.0.2.10,Port=53 --resolver-endpoint-id rslvr-out-0abc
```

> [!tip] Prefira regras de encaminhamento em ambientes multi-VPC
> **DHCP options** afetam **toda a VPC** (inclusive instâncias sem relação com o AD). Com **regras do Route 53 Resolver**, só o **domínio do AD** vai aos DCs; o resto continua pelo **resolver padrão**. Compartilhe as regras com **AWS RAM** e **associe** às VPCs.

### 3.3 DNS híbrido

```
Máquina AWS ──▶ Route 53 Resolver ──(regra: corp.local)──▶ outbound endpoint ──VPN/DX──▶ DNS on-prem
Máquina on-prem ──(forwarder: aws.corp.example.com)──▶ inbound endpoint / IPs dos DCs gerenciados
```

- Domínios **distintos** em cada lado (não use o mesmo nome em duas florestas).
- **Resolver endpoints** (inbound/outbound) para o DNS híbrido de outros usos; os DCs gerenciados também podem ser **alvos diretos**.

### 3.4 Armadilhas de DNS

- **AmazonProvidedDNS** como único DNS: **não resolve** o domínio do AD.
- **Nomes iguais** (`corp.local`) em on-prem e AWS → **ambiguidade**.
- **Sufixo DNS** incorreto no cliente.
- **Latência**: DCs em outra região/VPC distante → login lento.
- **Falta de DNS reverso** (alguns serviços exigem).

## 4. Security groups e portas

### 4.1 O SG gerado pelo diretório

O serviço cria um **security group** para os DCs. As **instâncias clientes** precisam alcançar os DCs nas portas AD:

| Porta | Protocolo | Uso |
|---|---|---|
| **53** | TCP/UDP | DNS |
| **88** | TCP/UDP | Kerberos |
| **123** | UDP | NTP/tempo |
| **135** | TCP | RPC endpoint mapper |
| **389** | TCP/UDP | LDAP |
| **445** | TCP/UDP | SMB (SYSVOL, GPO) |
| **464** | TCP/UDP | Kerberos alterar senha |
| **636** | TCP | **LDAPS** |
| **3268/3269** | TCP | **Global Catalog** (LDAP/LDAPS) |
| **49152–65535** | TCP | **RPC dinâmicas** (replicação, domain join, GPO) |
| **ICMP** | — | Diagnóstico (recomendado) |

### 4.2 Boas práticas

1. **Origem restrita**: permitir essas portas apenas dos **CIDRs/SGs** das cargas e da rede **on-prem** necessária (não `0.0.0.0/0`).
2. **SGs de cargas** (ex.: **SG-App**) como **origem** nas regras de entrada do SG do diretório (referência por SG).
3. **NACLs** simétricas (portas efêmeras).
4. **Egress** do diretório: permitir **o necessário** (DCs ↔ on-prem para trust, DNS).
5. **Sem exposição pública** (nenhum IP público nos DCs).
6. Documentar a **matriz de portas** por fluxo (cliente→DC, DC→DC, DC→on-prem).

## 5. Conectividade com on-premises e outras redes

| Cenário | Solução |
|---|---|
| **VPC ↔ on-premises** | **VPN site-to-site** (redundante) ou **Direct Connect** (preferido para produção) |
| **Várias VPCs** | **Transit Gateway** (hub) ou **VPC peering** (poucas) |
| **Várias contas** | Diretório **compartilhado** + conectividade de rede entre as VPCs |
| **Regiões** | **Multi-região** replicando o diretório, ou **TGW inter-região** |
| **Latência** | DCs **perto** das cargas; **replicação multi-região** para regiões remotas |

> [!warning] Disponibilidade da conectividade = disponibilidade da autenticação
> Para **AD Connector** (proxy) e para **trusts**, **queda do link** significa **queda de login**. Use **links redundantes** (dois túneis VPN/duas conexões DX), **monitoramento** e **rotas de contingência**.

## 6. Alta disponibilidade

### 6.1 Dentro da região

| Elemento | Detalhe |
|---|---|
| **2 DCs em 2 AZs** | Padrão; **replicação multi-master** entre DCs |
| **Substituição automática** | A AWS **substitui DCs com falha** automaticamente |
| **DCs adicionais** | Para **escala** e **mais resiliência** (inclusive em AZs adicionais) |
| **Clientes** | Devem usar **ambos** os DNS/DCs; **sites AD** nas AZs/VPCs (a AWS configura **sites**; confirmar o nível de controle) |

### 6.2 Multi-região (Managed AD Enterprise)

```
Região primária (us-east-1)  ── replicação automática ──▶  Região secundária (sa-east-1)
   DCs gerenciados                                          DCs gerenciados (réplica)
   Workloads locais                                         Workloads locais usam DCs locais
```

| Aspecto | Detalhe (de memória — confirmar) |
|---|---|
| **Edição** | **Enterprise** |
| **Modelo** | **Mesmo domínio** em várias regiões; **réplicas** com **replicação automática** |
| **Benefícios** | **Latência baixa** (login local), **DR**, aplicações **multi-região** |
| **Requisitos** | **VPC por região** com conectividade (TGW inter-região/peering) e **DNS**; **número mínimo de DCs** por região |
| **Escrita** | Multi-master (AD); alterações **replicam** |
| **Custo** | **DCs por região** |
| **Cuidados** | **Replicação** depende de **rede**; **DNS** e **sites** coerentes; teste de **failover** das aplicações |

### 6.3 DR sem multi-região

- **Snapshots** em outra região **não** são um recurso nativo simples; para DR de diretório, a rota principal é **multi-região** (Enterprise) ou **recriar** + **restaurar** a partir de **backups** (processo lento).
- Considere RTO/RPO: **multi-região** dá RTO baixo; **recriação** dá RTO alto.

## 7. Backup e recuperação

| Mecanismo | Detalhe (de memória — confirmar) |
|---|---|
| **Snapshots automáticos** | **Diários**, retidos por um período (ex.: 5 dias — confirmar) |
| **Snapshots manuais** | Até um **limite** (ex.: 5); **você** cria antes de **mudanças arriscadas** (esquema, migração) |
| **Restauração** | **Restaurar** o diretório a partir de um snapshot (**substitui** o estado atual; **downtime** e **perda** das mudanças posteriores); **só no mesmo diretório** (não cria cópia paralela) |
| **Escopo** | O **diretório** (objetos, GPO, DNS integrado); **não** inclui os **objetos de computador** fora do estado… (os computadores no AD fazem parte; máquinas devem **reconciliar** a senha da conta de máquina) |
| **Replicação multi-DC** | Protege contra falha de DC, **não** contra **exclusão/alteração lógica** (que replica) |
| **Lixeira do AD (Recycle Bin)** | Habilite para **restaurar objetos excluídos** (de memória, suportado; confirmar) |

```bash
aws ds create-snapshot --directory-id d-1234567890 --name pre-extensao-esquema
aws ds describe-snapshots --directory-id d-1234567890
aws ds restore-from-snapshot --snapshot-id s-abcdef1234     # ATENÇÃO: substitui o estado atual
```

Boas práticas:

1. **Snapshot manual antes** de **extensões de esquema**, **grandes mudanças de GPO** e **migrações**.
2. **Testar a restauração** em **ambiente de teste** (criar diretório de teste e restaurar? — em geral, validar o **processo** e o **tempo**).
3. **Habilitar o Recycle Bin** do AD para **exclusões acidentais**.
4. **Backups de GPO** (exportar via PowerShell) e **IaC** para a **estrutura de OUs/grupos**.
5. Documentar **procedimento de DR** com **RTO/RPO** e **responsáveis**.

## 8. Compartilhamento e multi-conta (arquitetura)

```
Conta Identidade (VPC-ID 10.10.0.0/16)  ── Managed AD (Enterprise) ──▶ réplica em sa-east-1
        │ compartilhado via Organizations
        ▼
Contas de Workloads (VPC 10.20.x/10.30.x) ──TGW──▶ DNS via Route 53 Resolver rules (RAM)
        ├─ EC2 (seamless join)  ├─ RDS SQL Server  ├─ FSx for Windows  └─ WorkSpaces
Conectividade on-prem: Direct Connect → TGW → VPC Identidade (trust com o AD corporativo)
```

Checklist de multi-conta:

- **Rotas** do TGW entre a VPC de identidade e as demais;
- **Regras de DNS** compartilhadas e **associadas**;
- **SGs** do diretório permitindo CIDRs/SGs das contas consumidoras (referência entre contas por CIDR);
- **Permissões** de compartilhamento (Organizations);
- **Governança**: quem cria computadores/OUs em nome de quais contas (**OUs por conta/equipe** com delegação).

## 9. Performance e capacidade

| Aspecto | Orientação |
|---|---|
| **Carga de autenticação** | Muitos logins simultâneos (horário de entrada) → **mais DCs** |
| **Latência** | DCs na **mesma região/VPC** das cargas; **multi-região** para regiões distantes |
| **Tamanho do diretório** | Edição adequada; **limpeza** de objetos obsoletos |
| **GPO** | Evitar GPOs excessivamente complexas (lentidão de logon) |
| **Replicação** | Acompanhar **atrasos** (métricas/logs) |
| **Consultas LDAP pesadas** | Aplicações mal escritas sobrecarregam; **filtros** e **paginação** |
| **Monitoramento** | Métricas do diretório no CloudWatch (de memória: conjunto limitado) e **logs de segurança** |

## 10. Erros comuns

- **DNS não configurado** (AmazonProvidedDNS apenas).
- **DHCP option set em VPC mista**: instâncias sem relação com o AD passam a usar DNS dos DCs.
- **Portas RPC dinâmicas bloqueadas**.
- **Subnets em uma só AZ** (inválido) ou **sem IPs livres**.
- **Link único** com on-prem (AD Connector/trust).
- **Sem snapshot manual antes de mudança de esquema**.
- **Restaurar snapshot** sem avaliar a **perda de dados** e o **impacto**.
- **Assumir que replicação = backup** (exclusões replicam).
- **Multi-região sem planejar DNS/rede**.
- **Sem Recycle Bin** do AD.
- **Nomes de domínio iguais** on-prem e AWS.

## 11. Troubleshooting

| Sintoma | Causa provável | Ação |
|---|---|---|
| Instância não resolve o domínio | DNS/DHCP incorreto; regra do Resolver não associada | Ajustar o DNS; associar a regra à VPC |
| Domain join expira (timeout) | Portas bloqueadas; rota ausente | Revisar SG/NACL/rotas |
| Login lento | DCs distantes; DNS dos DCs errados; GPO pesada | Aproximar DCs; revisar DNS e GPO |
| Falha após queda de link | AD Connector/trust sem redundância | Redundância de link; contingência |
| Réplica multi-região atrasada | Rede inter-região; carga de mudanças | Verificar conectividade/latência |
| Restauração não resolve exclusão acidental | Snapshot mais antigo; replicação já espalhou | Usar o **Recycle Bin**; reavaliar a estratégia |
| Diretório “Inoperable” | DCs/rede/SG | Ver o status dos DCs; chamado à AWS |
| SG do diretório bloqueando clientes | Regras sem os CIDRs/SGs das cargas | Adicionar as origens corretas |

## 12. Resumo rápido

- Implantação = **VPC/subnets em 2 AZs**, **DNS correto**, **portas/SGs**, **conectividade redundante**, **HA/DR** e **backup**.
- **DNS** é o ponto crítico: prefira **regras de encaminhamento do Route 53 Resolver** (compartilhadas via RAM) a DHCP options em VPCs mistas; **conditional forwarders** com o on-prem.
- **Portas AD**: **53, 88, 123, 135, 389, 445, 464, 636, 3268/3269 e RPC dinâmicas (49152–65535)**.
- **HA**: **2 DCs em 2 AZs**, **substituição automática**, **DCs adicionais**; **multi-região** (Enterprise) para latência e DR.
- **Backup**: **snapshots automáticos e manuais**; **restaurar substitui o estado atual**; **Recycle Bin** para exclusões; **replicação ≠ backup**.
- **Multi-conta**: diretório **compartilhado**, TGW, DNS por **Resolver rules**, OUs delegadas.

## 🧩 Quiz de Fixação

1. Por que o DNS é o ponto mais crítico da implantação?
2. Qual a vantagem das regras de encaminhamento do Resolver sobre DHCP options?
3. Quais portas as instâncias precisam alcançar nos DCs?
4. Por que a replicação entre DCs não substitui o backup?
5. O que acontece ao restaurar um snapshot?
6. Qual edição permite replicação multi-região?
7. Por que o link com on-premises precisa ser redundante em AD Connector e trusts?

**Respostas:**

1. Porque o AD localiza DCs por registros DNS (SRV); sem resolução correta do domínio, domain join e login falham.
2. Só o domínio do AD é encaminhado aos DCs, sem afetar a resolução de toda a VPC, e as regras podem ser compartilhadas por RAM entre contas/VPCs.
3. DNS (53), Kerberos (88/464), NTP (123), RPC (135 e dinâmicas 49152–65535), LDAP/LDAPS (389/636), SMB (445) e Global Catalog (3268/3269).
4. Porque alterações e exclusões lógicas também são replicadas; só snapshots/Recycle Bin recuperam estados anteriores.
5. O estado do diretório é substituído pelo do snapshot, com downtime e perda das mudanças posteriores.
6. Managed Microsoft AD Enterprise.
7. Porque a disponibilidade da autenticação depende do link; sem redundância, uma queda interrompe os logins.
