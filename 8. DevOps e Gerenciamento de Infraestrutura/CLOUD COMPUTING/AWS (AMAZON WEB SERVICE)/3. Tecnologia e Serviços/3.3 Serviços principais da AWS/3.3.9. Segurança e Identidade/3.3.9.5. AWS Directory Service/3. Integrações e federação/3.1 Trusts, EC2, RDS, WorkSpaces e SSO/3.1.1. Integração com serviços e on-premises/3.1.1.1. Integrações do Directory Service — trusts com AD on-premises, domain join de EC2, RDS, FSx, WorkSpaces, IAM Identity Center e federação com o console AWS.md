### 3.1.1.1. Integrações do Directory Service — trusts com AD on-premises, domain join de EC2, RDS, FSx, WorkSpaces, IAM Identity Center e federação com o console AWS

> [!warning] Aviso
> Direções de trust, portas, requisitos de DNS, nomes de documentos do SSM, serviços compatíveis e recursos de cada integração abaixo são **de memória e mudam**. **Confirme na documentação do Directory Service e de cada serviço integrado.** Comandos, scripts e JSONs são ilustrativos e **não foram executados**. Nomes e IPs são fictícios (`corp.example.com`, `10.50.0.0/16`). Alterar DNS e trusts pode **interromper autenticação** em produção: teste em ambiente isolado.

## 1. Integrações: por que importam

O diretório só tem valor se **serviços e pessoas** o **usam**. As integrações se dividem em quatro grupos:

```
                         ┌────────── Managed AD / AD Connector ──────────┐
 [1] ON-PREMISES         │                                                │
     trust / proxy  ─────┤  [2] COMPUTE & BANCOS: EC2, RDS, FSx           │
                         │  [3] APLICAÇÕES AWS: WorkSpaces, QuickSight... │
                         │  [4] ACESSO À AWS: IAM Identity Center / SAML  │
                         └────────────────────────────────────────────────┘
```

## 2. Integração com o AD on-premises: trusts

### 2.1 O que é um trust

Um **trust** é uma **relação de confiança** entre dois domínios/florestas: usuários de um lado podem **acessar recursos** do outro sem duplicar contas.

| Conceito | Significado |
|---|---|
| **Trusting domain** | O domínio que **confia** (onde estão os **recursos**) |
| **Trusted domain** | O domínio **confiável** (onde estão os **usuários**) |
| **Direção** | **One-way** (um lado confia no outro) ou **two-way** |
| **Tipo** | **Forest trust** (entre florestas inteiras) ou **External trust** (entre domínios específicos) |
| **Transitividade** | Forest trusts são transitivos; external trusts não |

### 2.2 Cenário típico

```
 AD on-premises (corp.local)   ── trust (forest, two-way ou one-way) ──   AWS Managed AD (aws.corp.example.com)
   usuários corporativos                                                  EC2/RDS/FSx/WorkSpaces (recursos)
```

- **Padrão recomendado**: o **AWS Managed AD** **confia** no AD on-premises (**one-way: AWS confia no on-prem**), de modo que **usuários on-prem** acessem **recursos na AWS**; as **contas permanecem on-premises**.
- Use **two-way** se **recursos on-prem** também precisarem aceitar **usuários do domínio AWS**.
- Na **documentação**, cuidado com a **nomenclatura**: “**incoming** vs **outgoing**” **depende de quem você está olhando** — valide a direção em ambos os lados.

### 2.3 Pré-requisitos de rede e DNS

| Item | Detalhe |
|---|---|
| **Conectividade** | VPN/Direct Connect entre a VPC e a rede on-premises |
| **Portas (entre DCs)** | **53** (DNS), **88** (Kerberos), **135** (RPC), **389/636** (LDAP/LDAPS), **445** (SMB), **464** (Kerberos password), **3268/3269** (GC), **49152–65535** (RPC dinâmicas) |
| **DNS** | Cada lado resolve o outro: **conditional forwarders** (no AD on-prem para o domínio AWS; no Managed AD para o domínio on-prem) |
| **Tempo** | **NTP** sincronizado (Kerberos) |
| **Nomes** | Domínios **únicos** e **NetBIOS** diferentes; evitar nomes que colidam |
| **Security groups/firewalls** | Permitir o tráfego nos dois sentidos |
| **Funcionalidade do domínio** | Níveis funcionais compatíveis |

### 2.4 Passos (visão geral)

1. **Rede**: VPN/DX operacional.
2. **DNS**: criar **conditional forwarder** no AD on-premises para `aws.corp.example.com` (IPs dos DCs gerenciados) e, no Managed AD, **conditional forwarder** para `corp.local` (IPs dos DNS on-prem).
3. **No AD on-prem**: criar o trust (Active Directory Domains and Trusts) com a **senha de trust**.
4. **Na AWS**: criar o trust no Directory Service com a **mesma senha**, direção e tipo.
5. **Verificar**: botão “Verify” do trust no console; **teste de login** de usuário on-prem em recurso na AWS.
6. **Autorizações**: conceder **grupos on-premises** em **ACLs** na AWS (grupos **universais/globais** do domínio confiável).

```bash
# Criar o trust no lado AWS (ilustrativo; a senha vem de um cofre)
aws ds create-trust --directory-id d-1234567890 \
  --remote-domain-name corp.local \
  --trust-password "$(aws secretsmanager get-secret-value --secret-id trust-pw --query SecretString --output text)" \
  --trust-direction One-Way:Outgoing --trust-type Forest \
  --conditional-forwarder-ip-addrs 10.50.0.10 10.50.0.11 \
  --selective-auth Disabled

aws ds describe-trusts --directory-id d-1234567890
aws ds verify-trust --trust-id t-abcdef1234
```

### 2.5 Autenticação seletiva (selective authentication)

- **Desabilitada**: todos os usuários do domínio confiável podem **autenticar** em **qualquer** recurso do domínio confiante (sujeito a ACLs).
- **Habilitada**: só usuários/grupos **explicitamente autorizados** em **cada servidor** (permissão **“Allowed to authenticate”**) — **mais seguro**, mais **trabalhoso**.

### 2.6 Alternativa: AD Connector + AD on-premises

Quando **não** se quer um diretório na AWS: **AD Connector** (proxy). Aqui **não há trust**; os serviços AWS **autenticam diretamente no AD on-premises**. **Trade-off**: simplicidade e fonte única versus **dependência total do link**.

## 3. Domain join de instâncias EC2

### 3.1 Formas de ingressar

| Método | Descrição |
|---|---|
| **Seamless domain join (SSM)** | O **Systems Manager** ingressa a instância **automaticamente** na inicialização (Windows e Linux) usando **documento SSM** `AWS-JoinDirectoryServiceDomain`, **IAM instance profile** e a **associação** com o diretório |
| **Console/CLI/CloudFormation** | Associar o diretório ao **launch** da instância (via **State Manager association**) |
| **Manual** | Ingressar com **credenciais** de conta com permissão (PowerShell `Add-Computer`; Linux `realmd/adcli/sssd`) |
| **Scripts em user data** | Para AMIs customizadas |

```json
{
  "schemaVersion": "1.0",
  "description": "Ingressar no domínio gerenciado",
  "runtimeConfig": { "aws:domainJoin": { "properties": {
      "directoryId": "d-1234567890",
      "directoryName": "aws.corp.example.com",
      "dnsIpAddresses": ["10.0.1.10", "10.0.2.10"] } } }
}
```

### 3.2 Requisitos

| Item | Detalhe |
|---|---|
| **DNS da instância** | Deve usar os **DNS do diretório** (via **DHCP option set** da VPC ou regras do **Route 53 Resolver**) |
| **IAM** | **Instance profile** com `AmazonSSMManagedInstanceCore` e `AmazonSSMDirectoryServiceAccess` |
| **Security groups** | Instância ↔ diretório nas **portas AD** |
| **SSM Agent** | Instalado e online |
| **OU de destino** | Computadores entram na **OU delegada** (ex.: `OU=Computers,OU=CORP,DC=aws,...`) |
| **Nome do computador** | Único; **limite de 15 caracteres** (NetBIOS) |

### 3.3 Boas práticas

- **Seamless join** em **Auto Scaling/launch templates** (instâncias entram sozinhas).
- **Remoção de objetos de computador** órfãos (scripts/lifecycle hooks) para evitar lixo no diretório.
- **GPO** para endurecimento (**CIS**), **RDP por grupo**, **política de senha**.
- **Acesso administrativo**: grupo **AD** com permissão **RDP/sudo**, e **Session Manager** como alternativa.
- **Linux**: **SSSD + Kerberos**, **sudoers por grupo AD**, **autenticação por chave** (opcional) combinada.

## 4. Amazon RDS

### 4.1 Autenticação Kerberos/Windows

| Engine | Suporte com Managed AD (de memória — confirmar versões e engines) |
|---|---|
| **RDS for SQL Server** | **Windows Authentication** (usuários e grupos do AD) |
| **RDS for Oracle** | **Kerberos** |
| **RDS for MySQL** | **Kerberos/Windows Authentication** (autenticação **via plugin**; confirmar) |
| **RDS for PostgreSQL** | **Kerberos** |
| **Aurora (MySQL/PostgreSQL)** | **Kerberos** (confirmar) |

Requisitos:

- Instância no **mesmo VPC/rede** com acesso ao diretório (ou **diretório compartilhado**);
- **Role do IAM** (`rds-directoryservice-access-role`) para o RDS **ingressar** no domínio;
- **AWS Managed Microsoft AD** (SQL Server também pode usar **AD on-prem via trust** — confirmar); **AD Connector/Simple AD não servem** para SQL Server Windows auth.

```bash
aws rds modify-db-instance --db-instance-identifier sqlserver-prod \
  --domain d-1234567890 --domain-iam-role-name rds-directoryservice-access-role --apply-immediately
```

### 4.2 Pontos de atenção

- **Logins do SQL Server** mapeados a **grupos do AD** (`CREATE LOGIN [CORP\DBAdmins] FROM WINDOWS`).
- **Multi-AZ**: o RDS gerencia o domínio nas duas instâncias.
- **Trust**: usuários do AD **on-premises** autenticam via trust (**one-way** AWS→on-prem).

## 5. Amazon FSx for Windows File Server

- **Exige AD** (**Managed AD** ou **AD self-managed**) para **autenticação e permissões NTFS/SMB**.
- Opções: **AWS Managed Microsoft AD** (padrão) ou **AD autogerenciado** (on-prem/EC2; inclusive via **AD Connector**? — o FSx usa conta de serviço no AD; confirmar suporte por tipo).
- **Cotas/ACLs** por usuários/grupos do domínio; **Shadow copies**, **DFS**.
- Considere **diretório compartilhado** para FSx em contas diferentes.

## 7. IAM Identity Center (SSO) e acesso ao console AWS

### 7.1 IAM Identity Center com AD

O **IAM Identity Center** pode usar o **diretório** como **fonte de identidade**:

| Opção | Detalhe (de memória — confirmar) |
|---|---|
| **AWS Managed Microsoft AD** | Conecta o Identity Center ao diretório; **usuários e grupos** do AD são **atribuídos** a **permission sets** em **contas AWS** |
| **AD Connector** | Mesmo conceito, com AD on-premises como fonte |
| **Sincronização** | Identity Center **sincroniza** (somente leitura) usuários/grupos selecionados; **atribuições** por **grupo** |
| **Provedor externo (SAML/SCIM)** | Alternativa **sem** diretório AWS (Okta, Entra ID) |
| **MFA** | **MFA do Identity Center** e/ou do provedor |

```
Usuário AD ──▶ Portal de acesso (Identity Center) ──▶ Conta AWS (Permission Set → role temporária) ──▶ Console/CLI
```

### 7.2 Federação SAML direta (sem Identity Center)

Para o **console** com **AD FS** (on-prem), **IAM Identity Provider (SAML)** e **IAM roles** — padrão **legado**; em geral, prefira **Identity Center**.

### 7.3 Boas práticas

- **Atribua por grupo** (não por usuário) → permissões **consistentes** e auditáveis.
- **Separe grupos por função e conta** (`AWS-Prod-ReadOnly`, `AWS-Dev-Admin`).
- **Sessões curtas** + **MFA**.
- **Desprovisionamento**: ao desativar o usuário no AD, o acesso AWS **cai** (sincronização/desativação).

## 9. Diretório compartilhado (directory sharing)

Em organizações com **muitas contas**, em vez de criar **um diretório por conta**:

```
Conta "Identidade" (dona do Managed AD)
   └─ compartilha o diretório ──▶ Contas A, B, C (via Organizations ou handshake)
        cada conta, em sua VPC, vê o diretório e faz domain join/usa RDS/FSx/WorkSpaces
```

| Característica | Detalhe |
|---|---|
| **Conectividade** | VPC das contas-consumidoras precisa **alcançar** o diretório (Transit Gateway/peering) para **DNS e portas AD** |
| **Controle** | A conta dona **administra** o diretório; consumidoras usam |
| **Custo** | Evita múltiplos diretórios; há cobrança de **compartilhamento** (confirmar) |
| **Uso** | **EC2 domain join**, **RDS**, **FSx**, **WorkSpaces** em outras contas |

```bash
aws ds share-directory --directory-id d-1234567890 \
  --share-target Id=111122223333,Type=ACCOUNT --share-method ORGANIZATIONS
```

## 10. Padrões de arquitetura

### 10.1 Híbrido com trust (recomendado para migração gradual)

```
On-prem AD (fonte das contas) ──trust──▶ Managed AD (recursos AWS: EC2, RDS, FSx) ──▶ Identity Center
```

### 10.2 AD Connector (identidade 100% on-prem)

```
Serviços AWS ──▶ AD Connector ──VPN/DX──▶ AD on-prem   (nada armazenado na AWS)
```

### 10.3 Nuvem primeiro

```
Managed AD como fonte principal (sem trust) ──▶ EC2/RDS/FSx/WorkSpaces; sincronização opcional para IdP externo
```

### 10.4 Multi-conta

```
Conta de Identidade (Managed AD + trust ao on-prem) ──compartilha──▶ contas de workloads
```

## 11. Erros comuns

- **Direção de trust invertida** (confundir incoming/outgoing).
- **DNS sem conditional forwarders** → trust “verifica” mas o login falha.
- **Portas RPC dinâmicas bloqueadas** no firewall.
- **Instâncias usando DNS da VPC (AmazonProvidedDNS)** em vez do diretório → domain join falha.
- **Instance profile sem `AmazonSSMDirectoryServiceAccess`**.
- **Tentar SQL Server Windows auth com AD Connector**.
- **Atribuir permissões AWS a usuários**, não a **grupos**.
- **Objetos de computador órfãos** acumulando.
- **Diretório compartilhado sem rota/DNS** nas outras VPCs.
- **Selective authentication** habilitada sem conceder “Allowed to authenticate”.

## 12. Troubleshooting

| Sintoma | Causa provável | Ação |
|---|---|---|
| Trust “verified”, mas login on-prem falha | DNS condicional, portas, SIDs/ACLs, horário | Testar resolução e Kerberos; revisar firewall e ACLs |
| Domain join falha | DNS aponta para o resolver errado; SG; credenciais; nome duplicado | Ajustar o DHCP/DNS; abrir portas; limpar objeto duplicado |
| SSM join não ocorre | Agente offline; profile sem permissão; associação ausente | Verificar SSM e IAM; reaplicar a associação |
| RDS não ingressa no domínio | Role do RDS ausente; subnets sem acesso ao diretório | Criar a role e revisar a rede |
| Identity Center não vê grupos do AD | Fonte de identidade/sincronização; escopo | Reconfigurar a sincronização e o escopo |
| Usuário desativado ainda acessa AWS | Sessão ativa; propagação | Revogar sessões; reduzir a duração |
| Diretório compartilhado inacessível | Rota/DNS/SG | Corrigir a conectividade entre VPCs |
| Kerberos “clock skew” | Horário dessincronizado | NTP em todos os lados |

## 13. Resumo rápido

- **Trust** (Managed AD ↔ AD on-prem): **forest/external**, **one-way/two-way**, exige **VPN/DX, DNS (conditional forwarders), portas AD e NTP**; padrão: **AWS confia no on-prem**.
- **Domain join EC2**: **seamless join via SSM** (`AmazonSSMDirectoryServiceAccess`), **DNS do diretório**, **OU delegada**.
- **RDS**: Kerberos/Windows Auth com **Managed AD** (SQL Server **não** com AD Connector/Simple AD); **role** `rds-directoryservice-access-role`.
- **FSx for Windows** exige AD; **WorkSpaces/AppStream/QuickSight** usam o diretório.
- **IAM Identity Center** com **Managed AD/AD Connector** como fonte; **atribuir por grupo**.
- **Directory sharing** para multi-conta; **gMSA**, **Transfer Family** e outros completam.

## 🧩 Quiz de Fixação

1. Qual o padrão recomendado de direção de trust entre Managed AD e AD on-premises e por quê?
2. Que pré-requisitos de DNS um trust exige?
3. Como funciona o seamless domain join via SSM?
4. Por que o AD Connector não serve para RDS SQL Server com Windows Authentication?
5. Que papel o IAM Identity Center tem com o diretório?
6. Para que serve o directory sharing?
7. O que a autenticação seletiva muda em um trust?

**Respostas:**

1. O AWS Managed AD confia no AD on-premises (one-way), para que usuários on-premises acessem recursos na AWS sem duplicar contas; two-way só se recursos on-premises precisarem aceitar usuários da AWS.
2. Cada lado deve resolver o domínio do outro, normalmente com conditional forwarders no AD on-premises e no Managed AD, além de portas e NTP corretos.
3. O Systems Manager ingressa a instância automaticamente no domínio na inicialização usando um documento/associação SSM, um instance profile com a permissão de diretório e os DNS do diretório.
4. Porque o AD Connector não armazena um diretório gerenciado na AWS; o RDS SQL Server precisa de um diretório integrado, como o Managed AD.
5. Usa o diretório como fonte de identidade, atribuindo grupos do AD a permission sets em contas AWS, com acesso temporário via roles.
6. Compartilhar um diretório entre várias contas, evitando criar um diretório por conta, mantendo o domain join, RDS, FSx e WorkSpaces nas contas consumidoras.
7. Restringe a autenticação a usuários/grupos explicitamente autorizados em cada servidor (permissão “Allowed to authenticate”), em vez de permitir todos do domínio confiável.
