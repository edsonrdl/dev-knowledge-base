### 1.1.1.1. O que é AWS Resource Access Manager — compartilhamento de recursos entre contas sem duplicação, resource shares, dono e consumidor, Organizations e quando usar RAM em vez de peering ou cópia

> [!warning] Aviso
> A lista de tipos de recurso compartilháveis, as permissões gerenciadas, limites e comportamentos por recurso abaixo são **de memória e mudam com frequência** (o RAM ganha tipos novos). **Confirme na documentação do AWS Resource Access Manager (lista “Shareable AWS resources”).** Comandos e JSONs são ilustrativos e **não foram executados**. IDs de contas (`111111111111` dona, `222222222222` consumidora) e ARNs são fictícios.

## 1. O problema que o RAM resolve

Organizações maduras usam **muitas contas AWS** (produção, homologação, dados, segurança, rede, uma por equipe/produto). Isso traz isolamento e governança, mas cria um problema: **muitos recursos são caros ou complexos de duplicar** em cada conta.

| Recurso | Por que duplicar é ruim |
|---|---|
| **Transit Gateway** | Um hub de rede por conta anularia o propósito de **centralizar** a conectividade |
| **Subnets de VPC** | Uma VPC por conta → **centenas de VPCs**, NATs, endpoints, **CIDRs** a coordenar |
| **Regras do Route 53 Resolver** (DNS híbrido) | Replicar regras e endpoints em todas as contas |
| **Network Firewall policies/rule groups** | Políticas divergentes e **trabalho repetido** |
| **Licenças (License Manager)** | Compartilhar **pools de licenças** entre contas |
| **Capacity Reservations** | Reservas de capacidade **ociosas** em uma conta que outra precisa |
| **Catálogo Glue/bancos Aurora** | Acesso a dados **sem copiá-los** |
| **Prefix lists, CA privada, AMIs/componentes do Image Builder** | Padronização central |

Alternativas antigas: **VPC peering** (N² conexões, sem compartilhar a infraestrutura), **cópia de recursos** (divergência), **políticas de recurso específicas** (nem todo recurso as suporta).

O **AWS Resource Access Manager (RAM)** permite **compartilhar recursos AWS de forma segura entre contas** (e entre **OUs** e **toda a organização**) **sem duplicá-los**: o **dono** mantém o recurso; os **consumidores** o usam como se fosse deles, dentro das **permissões** concedidas.

> [!info] Em uma frase
> **RAM = “crie uma vez, compartilhe com quem precisa”: recursos de uma conta passam a ser usados por outras contas, sem cópia e sem peering, com permissões controladas.**

## 2. Conceitos fundamentais

| Termo | Significado |
|---|---|
| **Resource share** | O **objeto do RAM** que liga **recursos** a **principais** com **permissões** |
| **Dono do recurso (owner)** | Conta que **criou** o recurso e o **compartilha**; responsável por **administrá-lo** |
| **Consumidor (principal)** | Conta, **OU**, **organização** (ou, em alguns casos, **role/usuário IAM**) que **recebe acesso** |
| **Recurso compartilhado** | O recurso em si (subnet, TGW, regra de DNS…) |
| **Permissão gerenciada (managed permission)** | **Conjunto de ações** permitidas ao consumidor sobre o recurso (AWS-managed ou **customer-managed**) |
| **Convite (invitation)** | Para principais **fora da organização**, o RAM envia um convite que deve ser **aceito** |
| **Compartilhamento com AWS Organizations** | Recurso habilitado que permite compartilhar com **OU/organização** **sem convite** |
| **Região** | Resource shares são **regionais** (para recursos regionais) |
| **Service-linked role** | `AWSServiceRoleForResourceAccessManager` (gerenciada pela AWS) |

### 2.1 Visão geral

```
CONTA DONA (111111111111)                                CONTAS CONSUMIDORAS
┌───────────────────────────────┐                      ┌────────────────────────────┐
│ Recurso (subnet, TGW, regra…) │                      │ Conta A (222222222222)      │
│        │                      │   RESOURCE SHARE      │   usa o recurso como seu    │
│        ▼                      │  (recursos + principais │                            │
│ [Resource Share] ─────────────┼──+ permissões)────────▶ │ Conta B / OU Produção / Org │
└───────────────────────────────┘                      └────────────────────────────┘
        (o recurso continua na conta dona; consumidores têm acesso conforme as permissões)
```

## 3. Como o compartilhamento funciona

### 3.1 Passos

1. **Dono** cria um **resource share**.
2. **Associa recursos** (por ARN) ao share.
3. **Associa principais** (contas/OUs/organização).
4. Define a **permissão gerenciada** para cada tipo de recurso.
5. O RAM **concede** o acesso:
   - **Dentro da organização** com **sharing habilitado**: **automático** (sem convite).
   - **Fora da organização**: **convite** (o consumidor **aceita**).
6. Consumidores **enxergam** e **usam** o recurso (console/API/CLI) em suas contas.

```bash
# Habilitar o compartilhamento com Organizations (uma vez, na conta de gestão; ilustrativo)
aws ram enable-sharing-with-aws-organization

# Criar um share, associando recursos e principais (ilustrativo)
aws ram create-resource-share --name rede-compartilhada \
  --resource-arns arn:aws:ec2:us-east-1:111111111111:subnet/subnet-0abc123 \
  --principals arn:aws:organizations::999999999999:ou/o-exemplo12345/ou-abcd-11111111 \
  --no-allow-external-principals

aws ram get-resource-shares --resource-owner SELF
aws ram list-resources --resource-owner SELF
aws ram list-principals --resource-owner SELF
```

### 3.2 Quem pode ser principal

| Principal | Suporte |
|---|---|
| **Conta AWS** (ID) | Sim |
| **OU** (ARN) | Sim (requer **Organizations** e **sharing habilitado**) |
| **Organização inteira** (ARN) | Sim |
| **IAM role / IAM user** | **Alguns tipos** de recurso permitem (confirmar por tipo) |
| **Serviço (service principal)** | Em casos específicos (por exemplo, **compartilhamento de recursos para serviços AWS**) |

### 3.3 O que o consumidor recebe

| Aspecto | Detalhe |
|---|---|
| **Acesso** | Conforme a **permissão gerenciada** (ex.: criar recursos **dentro** de uma subnet compartilhada, **associar** regras do Resolver às suas VPCs, **anexar** VPCs ao TGW) |
| **Propriedade** | Continua do **dono**: o consumidor **não** pode **excluir/alterar** o recurso (a menos que a permissão permita) |
| **Visibilidade** | Vê o recurso **em suas APIs** (ex.: `describe-subnets` mostra a subnet compartilhada com `OwnerId` do dono) |
| **Custos** | Depende do recurso: o **dono** paga o recurso; o **consumidor** paga o que **ele** cria usando o recurso (ver cada caso) |
| **Cotas** | Cotas do **consumidor** aplicam-se aos **seus** recursos criados |

## 4. Benefícios

| Benefício | Detalhe |
|---|---|
| **Reduz duplicação e custo** | Um **TGW**, um conjunto de **NATs/endpoints**, **uma** política de firewall — para muitas contas |
| **Governança central** | **Rede/segurança** centralizadas e consistentes |
| **Isolamento mantido** | Contas separadas (billing, IAM, limites) **sem** fundir ambientes |
| **Simplicidade de rede** | **VPC sharing**: menos VPCs, **sem peering** malha |
| **Aproveitamento de capacidade/licenças** | Pools **compartilhados** |
| **Sem custo do RAM** | **O serviço é gratuito** (paga-se os recursos subjacentes) |
| **Auditoria** | **CloudTrail** registra ações do RAM |
| **Automação** | **IaC** (CloudFormation `AWS::RAM::ResourceShare`) |

## 5. Quando usar RAM (e alternativas)

| Necessidade | Solução |
|---|---|
| **Compartilhar subnets** (VPC sharing) com várias contas | **RAM** |
| **Compartilhar Transit Gateway** para conectar VPCs de várias contas | **RAM** |
| **Compartilhar regras de DNS híbrido** (Resolver) | **RAM** |
| **Compartilhar políticas/rule groups de firewall** (Network Firewall, DNS Firewall) | **RAM** (com **Firewall Manager** para gestão em escala) |
| **Compartilhar pools de licenças** | **RAM + License Manager** |
| **Acesso a um bucket S3 de outra conta** | **Bucket policy/Access Points** (S3 **não** usa RAM) |
| **Acesso a uma role/serviço** | **IAM roles cross-account (STS AssumeRole)** |
| **Conectar redes de contas sem compartilhar infra** | **VPC Peering/PrivateLink/TGW** |
| **Compartilhar imagem (AMI)** | **Compartilhamento de AMI** (launch permissions) ou **EC2 Image Builder + RAM** |
| **Compartilhar secrets/chaves KMS** | **Resource policies** do serviço (não é RAM) |
| **Visão centralizada/gestão de políticas de segurança** | **Firewall Manager** (usa RAM por baixo para alguns recursos) |
| **Delegar administração de serviços** | **Administrador delegado** do serviço (Organizations) |

### 5.1 RAM vs políticas baseadas em recurso vs IAM cross-account

| Critério | **RAM** | **Resource-based policy** (S3, SQS, KMS…) | **IAM role cross-account** |
|---|---|---|---|
| **Modelo** | Compartilha **o recurso como se fosse do consumidor** | Concede acesso **a principais externos** no próprio recurso | Consumidor **assume** uma role na conta do dono |
| **Visibilidade** | Recurso **aparece** na conta consumidora | O recurso **não** “aparece” (acesso por ARN) | Atuação **dentro** da conta do dono |
| **Granularidade** | **Permissão gerenciada** por tipo | **Política** por recurso | **Política** da role |
| **Escala** | **OU/Organização** fácil | Lista de principais/condições (`aws:PrincipalOrgID`) | Uma role por relação |
| **Quando usar** | **Infra de rede/capacidade/licenças** | **Dados/mensageria/chaves** | **Operar** na conta do dono |

## 6. Casos de uso típicos

1. **Conta de rede compartilhada** (VPC sharing): equipes criam **EC2/RDS/EKS** em subnets **da conta de rede**, sem gerir VPC.
2. **Transit Gateway central**: **hub** compartilhado; contas anexam VPCs.
3. **DNS híbrido**: **regras do Resolver** na conta de rede compartilhadas com todas as contas.
4. **Inspeção central**: **Network Firewall** e **regras do DNS Firewall** compartilhadas.
5. **Licenciamento**: **pools** de licenças (Windows/SQL/Oracle) compartilhados.
6. **Data lake**: **catálogo Glue** compartilhado (via RAM/Lake Formation) para analistas em outras contas.
7. **Capacidade**: **Capacity Reservations** (ODCR) compartilhadas.
8. **CA privada (Private CA)**: emitir certificados em outras contas.
9. **Observabilidade/operações**: **Incident Manager** (contatos/planos) e outros recursos de operações.
10. **Padronização de imagens/builds**: **Image Builder** (componentes/imagens/receitas).

## 7. Limitações e cuidados (visão geral)

| Limitação | Detalhe |
|---|---|
| **Nem todo recurso é compartilhável** | Ex.: **Security Groups** (não compartilháveis; use **referência de SG** quando possível), **S3 buckets**, **IAM roles** |
| **Regional** | Shares regionais; **recursos globais** têm tratamento específico |
| **Zonas de disponibilidade** | **Nomes de AZ** (`us-east-1a`) **diferem entre contas**; use **AZ IDs** (`use1-az1`) ao compartilhar subnets |
| **Limites e cotas** | Por **share**, **recursos por share**, **principais por share** |
| **Custos e responsabilidade** | **Dono** responde pelo recurso; **consumidor** pelo que cria |
| **Dependências** | Excluir o recurso ou o share **afeta** consumidores |
| **Convites** | Fora da organização, **expiram** (de memória: ~7 dias) |
| **Segurança** | **Compartilhamento externo** pode **vazar** recursos; controlar |

## 8. Erros comuns

- **Usar RAM para S3/IAM/KMS** (não é o mecanismo).
- **Achar que o consumidor “possui” o recurso** e pode alterá-lo.
- **Compartilhar sem habilitar** o sharing com Organizations → convites manuais indesejados.
- **Ignorar AZ IDs** ao compartilhar subnets.
- **Compartilhar com a organização inteira** sem necessidade (exposição ampla).
- **Permitir principais externos** (`allow-external-principals`) por padrão.
- **Excluir o share/recurso** sem avisar os consumidores.
- **Não documentar** donos e consumidores.
- **Esquecer limites de cotas**.

## 9. Troubleshooting inicial

| Sintoma | Causas prováveis | Ações |
|---|---|---|
| Recurso não aparece na conta consumidora | Sharing com Organizations desabilitado; convite não aceito; região errada | Habilitar o sharing/aceitar o convite; conferir a região |
| `Resource share ... not found` | Share em outra região | Verificar a região |
| Subnet compartilhada sem EC2 criável | Permissão/AZ/ENI; limites | Ver permissão gerenciada e AZ IDs |
| Não consigo excluir o recurso | Share ativo; recursos dependentes | Dissociar/remover o share; limpar dependências |
| Convite expirou | Passaram ~7 dias | Reenviar o share |
| Erro ao compartilhar SG | Não suportado | Usar referências de SG/outra abordagem |

## 10. Resumo rápido

- **RAM** compartilha **recursos AWS entre contas/OUs/organização** **sem duplicar** nem usar peering; é **gratuito**.
- **Resource share** = **recursos + principais + permissões gerenciadas**; **dono** administra; **consumidor** usa conforme as permissões.
- **Organizations**: habilitar o **sharing** → compartilhamento por **OU/organização** **sem convites**; fora da organização → **convites**.
- **Compartilháveis** (exemplos): **subnets (VPC sharing)**, **Transit Gateway**, **regras do Resolver**, **Network Firewall/DNS Firewall**, **License Manager**, **Glue**, **Aurora**, **Capacity Reservations**, **Private CA**, **prefix lists**, **Image Builder**.
- **Não via RAM**: **S3**, **IAM roles**, **KMS**, **Security Groups** (outros mecanismos).
- Cuidado com **AZ IDs**, **externos**, **responsabilidades e custos** e **dependências**.

## 🧩 Quiz de Fixação

1. O que é um resource share e quais seus componentes?
2. Qual a diferença entre dono e consumidor?
3. Como o compartilhamento dentro da organização difere do externo?
4. Cite três recursos que podem ser compartilhados com RAM.
5. Por que usar AZ IDs ao compartilhar subnets?
6. Quando usar bucket policy ou role cross-account em vez de RAM?
7. O RAM tem custo?

**Respostas:**

1. É o objeto do RAM que associa recursos a principais com permissões gerenciadas (recursos + principais + permissões).
2. O dono cria e administra o recurso e paga por ele; o consumidor usa o recurso conforme as permissões, sem possuí-lo, e paga apenas pelo que criar com ele.
3. Dentro da organização, com o compartilhamento habilitado, o acesso é automático (por conta, OU ou organização); fora dela, é necessário um convite aceito pelo consumidor.
4. Subnets de VPC, Transit Gateway, regras do Route 53 Resolver, políticas/rule groups do Network Firewall, pools do License Manager, catálogo Glue, Capacity Reservations (quaisquer três).
5. Porque os nomes de AZ (us-east-1a) são mapeados de forma diferente entre contas, enquanto os AZ IDs identificam a mesma zona física.
6. Para dados, mensageria e chaves (S3, SQS, KMS), use resource policies; para operar na conta do dono, use IAM role cross-account com STS.
7. Não; o serviço é gratuito, pagando-se apenas pelos recursos compartilhados e pelo que os consumidores criarem.
