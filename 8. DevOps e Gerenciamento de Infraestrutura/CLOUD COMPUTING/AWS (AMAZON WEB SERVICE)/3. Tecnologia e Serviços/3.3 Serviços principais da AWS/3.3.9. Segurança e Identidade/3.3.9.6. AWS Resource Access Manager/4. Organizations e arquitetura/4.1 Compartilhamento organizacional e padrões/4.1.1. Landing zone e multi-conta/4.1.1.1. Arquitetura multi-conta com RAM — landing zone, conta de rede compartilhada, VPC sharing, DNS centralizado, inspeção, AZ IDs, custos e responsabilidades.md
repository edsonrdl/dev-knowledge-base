### 4.1.1.1. Arquitetura multi-conta com RAM — landing zone, conta de rede compartilhada, VPC sharing, DNS centralizado, inspeção, AZ IDs, custos e responsabilidades

> [!warning] Aviso
> Padrões de landing zone, nomes de contas/OUs, custos e regras de cobrança por recurso compartilhado abaixo são **de memória e mudam**. **Confirme na documentação do AWS Control Tower, do Organizations, do VPC sharing e de cada serviço.** Diagramas, CIDRs e comandos são ilustrativos/fictícios e **não foram executados**. Arquiteturas de rede multi-conta devem ser **validadas em homologação** antes de produção.

## 1. O RAM dentro de uma estratégia multi-conta

O RAM raramente é usado isoladamente: ele é **uma peça** de uma **landing zone** (ambiente multi-conta bem estruturado) com **Organizations**, **Control Tower**, **SCPs**, **IAM Identity Center** e contas **funcionais** (rede, segurança, logs, serviços compartilhados).

```
AWS Organizations (conta de GESTÃO — mínima)
 ├─ OU Segurança:      conta Log Archive • conta Audit/Segurança
 ├─ OU Infraestrutura: conta REDE (VPC/TGW/DNS/Firewall) • conta Serviços Compartilhados (AD, CA, Image Builder)
 ├─ OU Workloads-Prod: contas de aplicação (pedidos, pagamentos, dados…)
 ├─ OU Workloads-NonProd: contas de homologação/desenvolvimento
 └─ OU Sandbox / Suspensas
          ▲  RAM: a conta REDE e a de SERVIÇOS COMPARTILHADOS compartilham recursos com as OUs de Workloads
```

Papel do RAM: **conectar** contas **funcionais** (que **possuem** infraestrutura comum) às contas de **workload** (que **consomem**), **por OU**.

## 2. Contas funcionais típicas e o que compartilham

| Conta | Função | Compartilha (via RAM) |
|---|---|---|
| **Rede (Network)** | VPCs, **TGW**, Direct Connect/VPN, **Resolver**, inspeção | **Subnets**, **TGW**, **Resolver rules**, **Network Firewall/DNS Firewall**, prefix lists |
| **Serviços compartilhados (Shared Services)** | **AD/Directory Service**, **Private CA**, **Image Builder**, ferramentas | **Private CA**, componentes/imagens, **diretório** (Directory sharing — mecanismo próprio) |
| **Dados (Data Lake/Analytics)** | Catálogo, S3 do lake, Lake Formation | **Glue/Lake Formation** (via RAM) |
| **Licenciamento/Capacidade** | License Manager central, reservas | **License configurations**, **Capacity Reservations/Dedicated Hosts** |
| **Segurança** | GuardDuty/Security Hub/Firewall Manager (admins delegados) | Rule groups/policies de segurança |
| **Operações** | Incident Manager, observabilidade central | **Contatos/planos**, grupos de recursos |

## 3. Padrão 1: Conta de rede com VPC sharing

### 3.1 Desenho

```
Conta REDE (VPC-Prod 10.0.0.0/16)
  ├─ subnets de aplicação por equipe/AZ (compartilhadas por OU "Workloads-Prod")
  ├─ subnets de dados (compartilhadas com contas de dados)
  ├─ subnets de inspeção/egress (NAT, Network Firewall) — NÃO compartilhadas (uso exclusivo da rede)
  └─ endpoints (S3/DynamoDB/SSM/ECR…) compartilhados indiretamente pelos participantes (DNS privado)
Contas de Workload: criam EC2/RDS/EKS/Lambda nas subnets recebidas
```

### 3.2 Decisões

| Decisão | Recomendação |
|---|---|
| **Granularidade de subnets** | **Por equipe/ambiente/camada** (app, dados) e **por AZ** (3 AZs) — facilita **SGs/NACLs** e **custos** |
| **Compartilhar por OU** | **Sim** (herança); **separar prod/não-prod** em **VPCs e OUs** distintas |
| **CIDRs** | Planejar **blocos grandes** (ex.: `/16` por VPC), **`/20`–`/22`** por equipe; reserva para crescimento |
| **Egress/ingresso** | **NAT/IGW/ALB** centrais ou por equipe (custos e blast radius) |
| **Endpoints VPC** | **Centralizar** (S3/ECR/SSM/Logs) para **reduzir custos** |
| **SGs** | **Padrões** de nomenclatura; **referência entre SGs**; **Firewall Manager** para baseline |
| **Flow Logs** | **VPC Flow Logs** na conta de rede → **log archive** |
| **DNS** | **Zonas privadas** compartilhadas + **Resolver rules** (ver seção 5) |
| **Mudanças** | **IaC + PR + janelas**; owners claros |

### 3.3 Modelo de responsabilidade (RACI resumido)

| Atividade | Rede (dono) | Equipe (participante) | Segurança | FinOps |
|---|---|---|---|---|
| **Criar VPC/subnets/rotas/NACLs** | **R/A** | C | C | I |
| **Compartilhar subnets** | **R/A** | I | C | I |
| **Criar EC2/RDS/EKS nas subnets** | I | **R/A** | C | I |
| **Security Groups das cargas** | C | **R/A** | C | I |
| **Baseline de SG/WAF/firewall** | C | I | **R/A** | I |
| **Alocação de custos** | C | C | I | **R/A** |
| **Resposta a incidentes de rede** | **R** | C | **A** | I |

## 4. Padrão 2: Hub-and-spoke com TGW (VPCs por conta)

```
Contas de workload (VPC própria)  ──attachment──▶  TGW (conta Rede, compartilhado via RAM por OU)
                                                   ├─ RT Prod  ├─ RT NonProd  ├─ RT Compartilhado  ├─ RT Inspeção
                                                   └─ Direct Connect/VPN, VPC de inspeção (Network Firewall), egress central
```

| Aspecto | Detalhe |
|---|---|
| **RAM** | **Compartilha o TGW** com a OU; as contas **criam attachments** |
| **Aceitação** | **Manual** (controle) ou **auto-accept** + **guardrails** (IaC/Config) |
| **Segmentação** | **Route tables** por ambiente; **associações/propagações** controladas pela rede |
| **Inspeção** | Tráfego **leste-oeste/egress** passa pela **VPC de inspeção** |
| **CIDRs** | **Sem sobreposição** entre VPCs |
| **Custos** | **Por attachment/hora + por GB**; **alocar** às contas |
| **Quando** | **Isolamento** e **autonomia** são prioridade; **muitas** equipes com redes próprias |

### 4.1 Híbrido: VPC sharing + TGW

Muitas empresas usam **VPCs compartilhadas por ambiente/domínio** (reduz a quantidade) **e** **TGW** para **interligar** VPCs, on-premises e **inspeção**.

## 5. DNS centralizado (Resolver rules)

```
Conta REDE: Resolver endpoints (inbound/outbound) + regras (corp.local → DNS on-prem; aws.internal → privado)
        └─ RAM compartilha as regras com a OU de workloads
Contas de workload: associam as regras às suas VPCs (ou à VPC compartilhada)
On-prem → AWS: inbound endpoint resolve zonas privadas (hosted zones associadas)
```

| Boa prática | Detalhe |
|---|---|
| **Um conjunto** de endpoints/regras | Evita duplicar endpoints (custo por ENI/hora) |
| **Zonas privadas** compartilhadas | **Associação cross-account** de hosted zones privadas às VPCs (autorizada pelo dono) |
| **Automação de associação** | **Firewall Manager (DNS Firewall)** e **IaC**/**Control Tower customizations** associam regras a **novas VPCs** |
| **Query logging** | Centralizado na conta de **log archive** |
| **Resiliência** | **Endpoints em ≥ 2 AZs**; regras com **DNS on-prem redundantes** |

## 6. Inspeção e segurança de rede centralizadas

| Componente | Padrão |
|---|---|
| **Network Firewall** | Na **VPC de inspeção** (conta de rede); **policies/rule groups** compartilhados com outras contas para **firewalls locais** |
| **DNS Firewall** | Rule groups **compartilhados**; associados por **Firewall Manager** |
| **WAF/Shield** | **Firewall Manager** (políticas por OU) |
| **Security Groups** | **Baseline** via **Firewall Manager**; **referências** controladas |
| **Flow Logs/Traffic Mirroring** | Centralizados; **targets** compartilhados |
| **Detecção** | GuardDuty/Security Hub com **administradores delegados** |

## 7. Landing zone e automação com o RAM

### 7.1 Control Tower e Account Factory

- O **Account Factory** (ou **Account Factory for Terraform**) cria **contas novas** em **OUs**; com **shares por OU**, as contas **herdam** o acesso a **subnets/TGW/regras de DNS** **automaticamente**.
- **Customizations** (**CfCT**/**AFT**) executam **IaC pós-criação**: aceitar attachments, associar regras do Resolver, criar roles, **tags**, **budgets**.

### 7.2 Provisionamento por IaC

```yaml
# Conta Rede — shares por OU (ilustrativo, CloudFormation)
Resources:
  ShareSubnetsProd:
    Type: AWS::RAM::ResourceShare
    Properties:
      Name: subnets-workloads-prod
      AllowExternalPrincipals: false
      ResourceArns: [ !Sub "arn:aws:ec2:${AWS::Region}:${AWS::AccountId}:subnet/${SubnetAppA}", !Sub "arn:aws:ec2:${AWS::Region}:${AWS::AccountId}:subnet/${SubnetAppB}" ]
      Principals: [ "arn:aws:organizations::999999999999:ou/o-exemplo12345/ou-abcd-prod0001" ]
  ShareTgw:
    Type: AWS::RAM::ResourceShare
    Properties:
      Name: tgw-organizacao
      AllowExternalPrincipals: false
      ResourceArns: [ !Sub "arn:aws:ec2:${AWS::Region}:${AWS::AccountId}:transit-gateway/${Tgw}" ]
      Principals: [ "arn:aws:organizations::999999999999:ou/o-exemplo12345/ou-abcd-work0001" ]
```

### 7.3 Onboarding de uma conta (fluxo)

```
1) Conta criada na OU correta (Account Factory)  →  recebe automaticamente shares da OU (subnets/TGW/regras)
2) Pipeline pós-criação: tags, budgets, roles, baseline de segurança, associação de regras de DNS
3) Equipe cria workloads nas subnets/VPC (ou VPC própria + attachment ao TGW)
4) Observabilidade/logs ligados à conta de logs; custos alocados por tag
```

## 8. Custos e alocação

| Item | Quem paga (de memória — confirmar por recurso) | Alocação |
|---|---|---|
| **VPC, NAT Gateways, endpoints, IGW, Network Firewall** | **Dono (rede)** | **Showback/chargeback** aos participantes (por **uso**: GB/NAT, ENIs, tags) |
| **TGW (attachments/dados)** | Por **attachment/dados** — verificar quem é cobrado por **anexo** | Distribuir por **conta/anexo** |
| **Recursos nas subnets (EC2/RDS/EKS)** | **Participante** | Tags |
| **Transferência de dados inter-AZ/Internet** | **Quem origina** (regras específicas por recurso) | Monitorar por **AZ ID** |
| **License Manager** | **Dono** do contrato/licenças | Relatórios de uso por conta |
| **Capacity Reservations** | **Dono** | Alocar por **uso** |
| **Resolver endpoints** | **Dono (rede)** | Rateio |

Práticas: **tags obrigatórias**, **CUR + Athena** para ratear, **FinOps** com **owners** definidos, **alertas** (Budgets) por conta, **relatórios** de **uso de NAT/TGW por conta**.

## 9. Resiliência e blast radius

| Risco | Mitigação |
|---|---|
| **Erro de rota/NACL na conta de rede** afeta **muitas** contas | **IaC + PR + testes**, **janelas**, **canary** por ambiente, **VPCs/OUs separadas** (prod vs não-prod) |
| **Exclusão de share/recurso** | **SCPs** protegendo, **alarmes** de CloudTrail, **terminação protegida** |
| **Falha de AZ** | Subnets **em 3 AZs** (AZ IDs), **réplicas** e **Multi-AZ** |
| **Dependência de uma região** | **Multi-região** (VPCs/TGW peering entre regiões; RAM é **regional**) |
| **Cotas da VPC compartilhada** | **Múltiplas VPCs** por domínio; monitoramento de **IPs/SGs/ENIs** |
| **Conta de rede comprometida** | **Acesso mínimo**, MFA, SCPs, **break-glass**, monitoramento |
| **Acoplamento** | **Limites claros**; evitar **tudo** em **uma única VPC** |

## 10. Checklist de arquitetura multi-conta com RAM

- [ ] **Organizations + OUs** por função/ambiente; **sharing com Organizations habilitado**
- [ ] **Conta de rede** dedicada (e de serviços compartilhados) com **acesso mínimo**
- [ ] **Shares por OU** (herança), **`allowExternalPrincipals=false`**, **permissões mínimas**
- [ ] **CIDRs planejados**; **3 AZs** com **AZ IDs** documentados
- [ ] **Separação prod/não-prod** (VPCs/OUs/shares distintos)
- [ ] **DNS central** (Resolver rules) e **zonas privadas** associadas
- [ ] **Inspeção central** (Network Firewall/DNS Firewall) e **baseline** via **Firewall Manager**
- [ ] **IaC** (RAM, VPC, TGW, DNS) com **PR/aprovação**; **CfCT/AFT** para onboarding
- [ ] **Tags e alocação de custos** (CUR/Athena); **showback**
- [ ] **SCPs** e **alarmes** de CloudTrail (shares, TGW, rotas)
- [ ] **RACI** documentado (rede × equipes × segurança × FinOps)
- [ ] **DR/multi-região** considerados (RAM é regional)

## 11. Erros comuns

- **Compartilhar subnets de prod e dev** na mesma VPC.
- **Uma VPC gigante para a empresa toda** (blast radius/cotas).
- **Shares por conta individual** em vez de **OU**.
- **Conta de rede com acesso amplo** a muitos humanos.
- **Sem planejamento de CIDR** → IPs esgotados/sobreposição.
- **Ignorar AZ IDs** → HA/custos inconsistentes.
- **Custos de NAT/TGW “invisíveis”** para as equipes.
- **Mudanças de rede ad hoc** (sem IaC/revisão).
- **Auto-accept do TGW** sem guardrails.
- **Não prever multi-região** (shares são regionais).
- **Responsabilidades difusas** (quem corrige um problema de rota?).

## 12. Troubleshooting

| Sintoma | Causa provável | Ação |
|---|---|---|
| Nova conta não recebe subnets | Conta fora da OU; share não por OU; sharing org desabilitado | Mover para a OU; revisar o share |
| Conta sem acesso ao DNS corporativo | Regra do Resolver não associada à VPC | Associar (IaC/automação) |
| Latência/custo inter-AZ | AZ names divergentes | Usar AZ IDs |
| Attachment do TGW “pending acceptance” | Aceitação manual | Aceitar/automatizar |
| Conflito de CIDR | Planejamento ausente | Re-IP/NAT/segmentação |
| Limite de SGs na VPC | Muitos participantes | Cotas/VPCs adicionais |
| Mudança de rota derrubou várias contas | Blast radius | Rollback via IaC; reforçar processo |
| Custos NAT altos de uma equipe | Tráfego de egress | Endpoints VPC; otimizar; showback |

## 13. Resumo rápido

- **RAM + landing zone**: **contas funcionais** (rede, serviços compartilhados, dados, segurança) **compartilham por OU** com as contas de **workload**.
- **Padrões**: **VPC sharing** (poucas VPCs, gestão central), **hub-and-spoke com TGW** (VPCs por conta), **híbrido**; **DNS central** (Resolver rules), **inspeção central** (Network Firewall/DNS Firewall/FMS).
- **Automação**: **Control Tower/Account Factory + CfCT/AFT + IaC**; **shares por OU** herdam acesso; **tags** e **budgets** no onboarding.
- **Custos**: **dono paga infraestrutura** (NAT/TGW/endpoints) → **showback/chargeback** por tags/CUR; **participantes pagam seus recursos**.
- **Riscos**: **blast radius**, **cotas**, **CIDR**, **AZ IDs**, **regionalidade** → **IaC, SCPs, separação prod/não-prod, monitoramento**.
- **Governança**: **RACI**, **permissões mínimas**, **`allowExternalPrincipals=false`**, revisões periódicas.

## 🧩 Quiz de Fixação

1. Que contas funcionais costumam compartilhar recursos via RAM?
2. Por que compartilhar por OU ajuda no onboarding de contas?
3. Quais as diferenças entre VPC sharing e hub-and-spoke com TGW?
4. Como centralizar o DNS híbrido com RAM?
5. Quem paga NAT e TGW em uma rede compartilhada e como ratear?
6. Que riscos de blast radius existem e como mitigá-los?
7. Por que o RAM exige planejamento multi-região?

**Respostas:**

1. Conta de rede (subnets, TGW, Resolver, firewalls), de serviços compartilhados (Private CA, Image Builder), de dados (Glue/Lake Formation) e de licenciamento/capacidade.
2. Porque contas novas na OU herdam os shares automaticamente, sem trabalho manual, e as removidas perdem o acesso.
3. VPC sharing usa poucas VPCs com subnets compartilhadas (menor custo, gestão central, menos isolamento); hub-and-spoke usa uma VPC por conta conectada por TGW (mais isolamento e autonomia, mais custo e complexidade de CIDRs).
4. A conta de rede cria endpoints e regras de encaminhamento do Resolver e as compartilha por RAM; as contas associam as regras às suas VPCs, ou o Firewall Manager/IaC faz isso automaticamente.
5. Em geral o dono (rede) paga a infraestrutura compartilhada; rateia-se com showback/chargeback por tags, CUR/Athena e uso por conta/anexo.
6. Erros de rota/NACL ou exclusão de shares afetam muitas contas; mitigam-se com IaC e revisão, janelas, separação de prod/não-prod, SCPs, alarmes e VPCs separadas.
7. Porque shares são regionais; recursos e associações precisam existir e ser replicados em cada região usada, inclusive para DR.
