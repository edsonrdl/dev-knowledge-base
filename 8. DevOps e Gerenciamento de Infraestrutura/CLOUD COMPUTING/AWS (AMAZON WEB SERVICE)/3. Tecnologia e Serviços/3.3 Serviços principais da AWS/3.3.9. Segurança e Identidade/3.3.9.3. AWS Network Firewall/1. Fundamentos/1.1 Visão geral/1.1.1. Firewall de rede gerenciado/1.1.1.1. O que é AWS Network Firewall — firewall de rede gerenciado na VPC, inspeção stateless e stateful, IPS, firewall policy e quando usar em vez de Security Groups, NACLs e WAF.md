### 1.1.1.1. O que é AWS Network Firewall — firewall de rede gerenciado na VPC, inspeção stateless e stateful, IPS, firewall policy e quando usar em vez de Security Groups, NACLs e WAF

> [!warning] Aviso
> Nomes de recursos, limites, preços, recursos de TLS inspection, regras gerenciadas e modos de integração (por exemplo, anexo nativo ao Transit Gateway) abaixo são **de memória e mudam**. **Confirme na documentação do AWS Network Firewall e na página de preços.** Comandos e JSONs são ilustrativos e **não foram executados**. Mudanças de roteamento e regras de firewall podem **derrubar tráfego**: teste em ambiente isolado.

## 1. O problema que o Network Firewall resolve

Uma VPC já tem dois controles de rede nativos:

- **Security Groups**: firewall **stateful por ENI** (instância/Lambda/endpoint), só **permite** (allow) por protocolo/porta/origem;
- **Network ACLs**: firewall **stateless por subnet**, com allow e deny, regras numeradas.

Eles resolvem muito, mas **não** respondem a necessidades comuns de segurança corporativa:

| Necessidade | SG / NACL |
|---|---|
| **Filtrar saída por nome de domínio** (“só pode falar com `api.parceiro.com`”) | **Não** (só IPs, que mudam) |
| **Inspecionar o conteúdo** do tráfego (detectar exploits, C2, malware conhecido) | **Não** |
| **Regras com assinaturas** estilo IPS (Suricata/Snort) | **Não** |
| **Bloquear protocolos** fora da porta esperada (SSH na porta 443) | **Não** (só olham porta) |
| **Controle central** de tráfego entre VPCs e para a internet | Parcial e trabalhoso |
| **Logs de alerta e de fluxo** de inspeção profunda | **Não** |
| **Conformidade** exigindo “firewall de próxima geração/IPS” na borda | **Não** |

O **AWS Network Firewall** é um **firewall de rede gerenciado** e **serviço de detecção/prevenção de intrusão (IDS/IPS)** para VPCs: você define regras e a AWS cuida de **provisionar, escalar e manter** a infraestrutura de inspeção (sem instâncias de firewall de terceiros para operar).

> [!info] Em uma frase
> **Network Firewall = firewall de rede (L3–L7) gerenciado, com filtragem por domínio e regras Suricata/IPS, colocado no caminho do tráfego da sua VPC.**

## 2. Onde ele atua no modelo de camadas

```
Internet ── IGW ──▶ [ NETWORK FIREWALL ] ──▶ Subnets de aplicação ──▶ [ Security Group ] ──▶ Instância
                      inspeção de TODO o      [ NACL (subnet) ]        (por ENI)
                      tráfego roteado
                      por ele (ingress/egress/east-west)
```

| Camada | Controle | Escopo | Estado | Foco |
|---|---|---|---|---|
| **Instância/ENI** | Security Group | Recurso | Stateful | Quem pode falar com este recurso |
| **Subnet** | NACL | Subnet | Stateless | Bloqueio grosso por faixa de IP/porta |
| **VPC (caminho de rede)** | **Network Firewall** | Tráfego **roteado** pelo firewall | **Stateless + Stateful** | **Política de rede corporativa**, domínios, IPS |
| **Aplicação web** | **AWS WAF** | Requisições HTTP(S) (ALB, API Gateway, CloudFront) | — | SQL injection, XSS, bots (L7 HTTP) |
| **DDoS** | **Shield** | Borda | — | Volumétrico/protocolo |

Regra de ouro: **são camadas complementares** (defesa em profundidade), não substitutas.

## 3. Conceitos fundamentais

| Termo | Significado |
|---|---|
| **Firewall** | O recurso implantado **em uma VPC**, com **endpoints** em subnets dedicadas por AZ |
| **Firewall policy** | A **política** reutilizável: define **quais rule groups** aplicar e as **ações padrão**; um firewall tem **uma** policy |
| **Rule group** | Conjunto de regras: **stateless** ou **stateful**; tem **capacidade** (imutável) e pode ser **compartilhado** |
| **Firewall endpoint** | Ponto de entrada de tráfego em cada AZ (baseado em **Gateway Load Balancer**, de memória); a **route table** envia o tráfego para ele |
| **Firewall subnet** | Subnet **dedicada** (pequena, ex.: /28) que hospeda o endpoint |
| **Stateless engine** | Avalia **cada pacote isoladamente** (5-tupla), rápido, ações `pass`/`drop`/`forward` |
| **Stateful engine** | Avalia **fluxos/conexões** (estado), domínios, assinaturas Suricata, ações `pass`/`drop`/`alert`/`reject` |
| **Managed rule groups** | Rule groups **mantidos pela AWS** (listas de ameaças, domínios maliciosos, assinaturas) |
| **Logging** | Logs **de alerta** (regras acionadas) e **de fluxo** (conexões) para S3, CloudWatch Logs ou Firehose |

## 4. Como o tráfego é inspecionado

```
Pacote chega ao endpoint do firewall
        │
        ▼
 ┌─────────────────────────┐   ação "forward"   ┌──────────────────────────┐
 │ Motor STATELESS          │ ─────────────────▶ │ Motor STATEFUL           │
 │ (regras por prioridade;  │                    │ (fluxo, domínio, Suricata)│
 │  5-tupla)                │                    └───────────┬──────────────┘
 └──────────┬──────────────┘                                │
   pass / drop                                      pass / drop / alert / reject
        │                                                   │
        ▼                                                   ▼
   Segue ou é descartado                         Segue, é descartado ou gera alerta
```

1. **Stateless primeiro**: regras avaliadas **por prioridade**; ação `pass` (libera), `drop` (descarta) ou **`forward` ao stateful** (`aws:forward_to_sfe`). Há **ação padrão** (default action) para pacotes sem regra.
2. **Stateful** inspeciona o **fluxo completo**: aplica regras 5-tupla, listas de domínios (HTTP Host / TLS SNI) e **assinaturas Suricata**.
3. O resultado é **permitir, descartar, alertar** (e **registrar**) conforme a policy.

> [!tip] Dica de projeto
> Use o **stateless** só para **bloqueios/permissões grosseiras e rápidas** (ex.: descartar protocolos inúteis) e **encaminhe o resto ao stateful**, onde está o poder de inspeção.

## 5. Capacidades principais

| Capacidade | Descrição |
|---|---|
| **Filtragem por domínio** | Permitir/negar tráfego **HTTP/HTTPS** por **nome** (Host/SNI), com wildcards; essencial para **egress controlado** |
| **Regras 5-tupla** | Origem/destino IP e porta, protocolo; stateless e stateful |
| **Regras compatíveis com Suricata (IPS)** | Assinaturas e lógica avançada (`content`, `pcre`, `flow`, `threshold`); importar conjuntos de terceiros |
| **Inspeção TLS** (de memória) | Descriptografar/inspecionar tráfego TLS de saída/entrada com certificados no **ACM** (ver folha de segurança) |
| **Regras gerenciadas pela AWS** | Listas de ameaças (domínios maliciosos, botnets, malware) mantidas pela AWS |
| **Logs** | Alertas e fluxo para S3, CloudWatch Logs e Kinesis Data Firehose |
| **Escala automática** | Capacidade gerenciada (de memória: até dezenas de Gbps por endpoint, com autoscaling) |
| **Integração** | **Firewall Manager** (política central multi-conta), **Transit Gateway**, **Gateway Load Balancer**, **CloudFormation/CDK** |
| **Alta disponibilidade** | **Um endpoint por AZ**; sem ponto único de falha quando implantado em múltiplas AZs |

## 6. Casos de uso típicos

1. **Egress filtering**: workloads em subnets privadas só acessam **domínios autorizados** (atualizações, APIs de parceiros).
2. **Inspeção de entrada** (ingress): tráfego da internet para a VPC passa por regras e IPS antes de chegar às aplicações.
3. **Inspeção leste-oeste**: tráfego **entre VPCs/subnets** (via Transit Gateway) é inspecionado — segmentação e detecção de movimento lateral.
4. **Hub de inspeção centralizado**: uma **VPC de inspeção** atende a toda a organização.
5. **Conformidade**: PCI-DSS, políticas internas exigindo **IPS/IDS** e **logs de inspeção**.
6. **Proteção de VPN/Direct Connect**: inspecionar tráfego que chega do on-premises.
7. **Detecção e resposta**: alertas para SIEM; bloqueio de **C2/exfiltração** por domínio/assinatura.

## 7. Network Firewall vs alternativas

| Critério | **Network Firewall** | **Security Group** | **NACL** | **AWS WAF** | **Firewall de terceiros (EC2/GWLB)** |
|---|---|---|---|---|---|
| Camada | L3–L7 (rede, domínio, assinaturas) | L3/L4 | L3/L4 | **L7 HTTP** | L3–L7 (recursos próprios) |
| Estado | Stateless + **stateful** | Stateful | Stateless | — | Depende |
| Filtra por **domínio** | **Sim** | Não | Não | Por host/URI nas requisições HTTP | Sim |
| **IPS/assinaturas** | **Sim (Suricata)** | Não | Não | Regras gerenciadas p/ web | Sim (comercial) |
| Operação | **Gerenciada** (sem servidores) | Gerenciada | Gerenciada | Gerenciada | **Você opera** (patches, HA, escala) |
| Onde se aplica | Caminho roteado da VPC | ENI | Subnet | ALB/API GW/CloudFront | Caminho roteado |
| Custo | Por **endpoint/hora + GB** | Gratuito | Gratuito | Por ACL/regra/requisição | Licença + instâncias |
| Quando escolher | **Egress por domínio, IPS, inspeção central** | Controle básico por recurso | Bloqueio por faixa | **Ataques web** (SQLi, XSS, bots) | Recursos específicos do fornecedor, padronização multicloud |

### 7.1 Regras de decisão

- “**Restringir saída a domínios específicos**” → **Network Firewall** (ou **proxy**/DNS Firewall em casos específicos).
- “**Bloquear SQL injection**” → **WAF**, não Network Firewall.
- “**Inspecionar tráfego entre VPCs**” → Network Firewall + **Transit Gateway**.
- “**Permitir só a porta 443 de uma instância**” → **Security Group** (simples e barato).
- “**Bloquear um IP malicioso** em toda a subnet rapidamente” → **NACL** (ou regra stateless).
- “**IDS/IPS gerenciado** na VPC” → **Network Firewall**.
- “**Filtrar consultas DNS** por domínio” → **Route 53 Resolver DNS Firewall** (complementar; atua em DNS).

## 8. Exemplo guiado: egress controlado

Cenário: aplicações em subnets privadas devem acessar **somente** `*.amazonaws.com`, `repo.pacotes.example.com` e `api.parceiro.example.com`; todo o resto deve ser **bloqueado e logado**.

```
App (subnet privada) ──▶ Route table → endpoint do Network Firewall (AZ-a)
                                  │   stateless: forward tudo ao stateful
                                  │   stateful: domain list ALLOWLIST (HTTP_HOST + TLS_SNI)
                                  │             ação padrão: DROP + alert
                                  ▼
                           NAT Gateway ──▶ Internet Gateway ──▶ Destino permitido
```

Resultados: tentativas de comunicação com domínios não listados (por exemplo, um malware chamando um servidor de comando e controle) são **descartadas e geram alerta**, algo que **Security Groups e NACLs não conseguem** expressar por domínio.

## 9. Comandos básicos (ilustrativos, não executados)

```bash
# Criar um rule group stateful de lista de domínios (allow)
aws network-firewall create-rule-group --rule-group-name egress-permitidos \
  --type STATEFUL --capacity 100 \
  --rule-group '{"RulesSource":{"RulesSourceList":{
      "Targets":[".amazonaws.com","repo.pacotes.example.com","api.parceiro.example.com"],
      "TargetTypes":["HTTP_HOST","TLS_SNI"],"GeneratedRulesType":"ALLOWLIST"}}}'

# Criar a firewall policy e o firewall
aws network-firewall create-firewall-policy --firewall-policy-name politica-egress \
  --firewall-policy '{"StatelessDefaultActions":["aws:forward_to_sfe"],
      "StatelessFragmentDefaultActions":["aws:forward_to_sfe"],
      "StatefulRuleGroupReferences":[{"ResourceArn":"arn:aws:network-firewall:us-east-1:123456789012:stateful-rulegroup/egress-permitidos"}]}'

aws network-firewall create-firewall --firewall-name fw-inspecao \
  --firewall-policy-arn arn:aws:network-firewall:us-east-1:123456789012:firewall-policy/politica-egress \
  --vpc-id vpc-0abc --subnet-mappings SubnetId=subnet-0fw1 SubnetId=subnet-0fw2

aws network-firewall describe-firewall --firewall-name fw-inspecao
```

## 10. Erros comuns

- **Achar que “criar o firewall” já inspeciona**: sem **ajustar as route tables** para enviar o tráfego ao endpoint, **nada passa por ele**.
- **Esquecer o roteamento de retorno** (assimetria): o tráfego de ida passa pelo firewall e o de volta não → conexões quebram no stateful.
- **Usar o Network Firewall para ataques web** (SQLi/XSS): o lugar certo é o **WAF**.
- **Subnet de firewall compartilhada** com workloads (deve ser **dedicada**).
- **Um só endpoint/AZ** em ambiente multi-AZ → falha de AZ derruba o caminho.
- **Capacidade do rule group subdimensionada** (é **imutável**; precisa recriar).
- **Sem logs**: não há como saber o que foi bloqueado ou por quê.
- **Regra de domínio sem cobrir SNI e Host**: tráfego TLS passa despercebido.
- **Ação padrão “pass” em tudo** achando que está protegido.
- **Substituir SG/NACL pelo firewall**: perde defesa em profundidade.

## 11. Troubleshooting inicial

| Sintoma | Causas prováveis | Ações |
|---|---|---|
| Tráfego não é inspecionado | Route tables sem rota para o endpoint | Revisar as rotas (ingress, subnets de workload, firewall subnet) |
| Conexões caem/intermitentes | **Roteamento assimétrico** | Garantir que ida e volta usem o **mesmo endpoint/AZ** |
| Tráfego legítimo bloqueado | Ação padrão `drop`, domínio ausente, ordem de regras | Ver **logs de alerta/fluxo**; ajustar a regra/ordem |
| HTTPS para domínio permitido falha | Regra só por HTTP_HOST (sem TLS_SNI) ou TLS 1.3/ECH | Incluir `TLS_SNI`; avaliar inspeção TLS |
| Firewall “Provisioning” demorado | Criação de endpoints em subnets | Aguardar; verificar o status e as subnets |
| Capacidade excedida | Rule group sem capacidade | Recriar com capacidade maior (imutável) |
| Sem logs | Logging não configurado ou permissões do destino | Configurar S3/CloudWatch/Firehose e as permissões |

## 12. Resumo rápido

- **Network Firewall** = firewall de rede **gerenciado** e **IDS/IPS** para VPC: **stateless + stateful**, **filtro por domínio**, **regras Suricata**, **TLS inspection**, **managed rule groups** e **logs**.
- Recursos: **firewall** (endpoints em **subnets dedicadas por AZ**), **firewall policy** (reutilizável), **rule groups** (capacidade **imutável**).
- **Só inspeciona o que é roteado a ele**: o roteamento (route tables) é metade do trabalho; cuide da **simetria** do tráfego.
- Complementa (não substitui) **SG, NACL, WAF, Shield** e **DNS Firewall**.
- Casos: **egress por domínio**, inspeção de **ingress**, **leste-oeste** (com Transit Gateway), **conformidade**.
- Pergunta de prova: “**filtrar por domínio / IPS gerenciado na VPC**” → **Network Firewall**; “**SQL injection**” → **WAF**.

## 🧩 Quiz de Fixação

1. Quais limitações de Security Groups e NACLs o Network Firewall resolve?
2. Qual a diferença entre o motor stateless e o stateful?
3. O que é uma firewall policy e um rule group?
4. Por que criar o firewall não basta para inspecionar o tráfego?
5. Quando usar WAF em vez de Network Firewall?
6. Por que o roteamento assimétrico é um problema?
7. Para que servem as subnets de firewall?

**Respostas:**

1. Filtragem por nome de domínio, inspeção de conteúdo e assinaturas IPS (Suricata), controle central de caminho de rede e logs de inspeção profunda.
2. O stateless avalia cada pacote isoladamente por 5-tupla e prioridade (pass/drop/forward); o stateful avalia fluxos, domínios e assinaturas Suricata (pass/drop/alert/reject).
3. A firewall policy define quais rule groups e ações padrão o firewall aplica; um rule group é um conjunto reutilizável de regras (stateless ou stateful) com capacidade fixa.
4. Porque só o tráfego roteado para o endpoint do firewall é inspecionado; é preciso configurar as route tables.
5. Para ataques a aplicações web HTTP(S), como SQL injection, XSS e bots, em ALB, API Gateway ou CloudFront.
6. Porque o firewall stateful precisa ver os dois sentidos do fluxo; se a volta usar outro caminho, a conexão é quebrada.
7. Hospedam os endpoints do firewall por AZ; devem ser dedicadas (pequenas), separadas das subnets de workload.
