### 3.1.1.1. Regras do Network Firewall — rule groups stateless e stateful, ações, listas de domínios, Suricata, ordem de avaliação, regras gerenciadas e exemplos

> [!warning] Aviso
> Sintaxe de regras Suricata suportada, ações, variáveis, opções de ordem de avaliação, nomes de regras gerenciadas e limites de capacidade abaixo são **de memória e mudam**. **Confirme na documentação do Network Firewall e na do Suricata.** Regras e JSONs são ilustrativos e **não foram executados**. **Nunca ative `drop` direto em produção**: valide primeiro com `alert` e análise de logs. IPs/domínios são fictícios (faixas reservadas para documentação).

## 1. O modelo de regras em uma imagem

```
                    Firewall policy
         ┌────────────────┴─────────────────┐
         ▼                                  ▼
 STATELESS rule groups              STATEFUL rule groups
 (por pacote, 5-tupla,              (por fluxo: 5-tupla, domínio, Suricata)
  prioridade; pass/drop/forward)     (pass/drop/alert/reject)
         │ forward                          ▲
         └──────────────────────────────────┘
```

| | **Stateless** | **Stateful** |
|---|---|---|
| Unidade de análise | **Pacote** isolado | **Fluxo/conexão** (estado) |
| Critérios | 5-tupla + flags TCP | 5-tupla, **domínio**, **Suricata**, protocolo L7 |
| Ações | `pass`, `drop`, `forward (to stateful)`, `custom` (ex.: métricas) | `pass`, `drop`, `alert`, `reject` (e `drop`+`alert`) |
| Ordem | **Prioridade numérica** (menor primeiro) | **Default action order** ou **strict order** (ver seção 4) |
| Desempenho | Muito rápido | Mais pesado, mais poderoso |
| Uso típico | Bloqueios/permissões grosseiros, antecipar descartes | Egress por domínio, IPS, conteúdo, aplicações |

## 2. Rule groups stateless

### 2.1 Estrutura

Cada regra tem **prioridade** e uma **correspondência**:

| Campo | Exemplo |
|---|---|
| **Sources / Destinations** | `10.0.0.0/16`, `0.0.0.0/0` |
| **SourcePorts / DestinationPorts** | `443`, `1024–65535` |
| **Protocols** | `6` (TCP), `17` (UDP), `1` (ICMP) |
| **TCPFlags** | `Flags: [SYN]`, `Masks: [SYN, ACK]` |
| **Ação** | `aws:pass`, `aws:drop`, `aws:forward_to_sfe` |

```json
{
  "RulesSource": { "StatelessRulesAndCustomActions": { "StatelessRules": [
    { "Priority": 10, "RuleDefinition": {
        "MatchAttributes": { "Protocols": [1], "Sources": [{"AddressDefinition":"0.0.0.0/0"}],
                             "Destinations": [{"AddressDefinition":"10.0.0.0/16"}] },
        "Actions": ["aws:drop"] } },
    { "Priority": 100, "RuleDefinition": {
        "MatchAttributes": { "Sources": [{"AddressDefinition":"0.0.0.0/0"}],
                             "Destinations": [{"AddressDefinition":"0.0.0.0/0"}] },
        "Actions": ["aws:forward_to_sfe"] } }
  ] } }
}
```

(Regra 10: descartar ICMP vindo da internet; regra 100: encaminhar o restante ao stateful.)

### 2.2 Ação padrão (default action)

Pacotes que **não casam** com nenhuma regra stateless recebem a **ação padrão da policy**:

| Padrão | Efeito |
|---|---|
| `aws:forward_to_sfe` | **Encaminha ao stateful** (recomendado como padrão) |
| `aws:pass` | Libera (cuidado) |
| `aws:drop` | Descarta tudo que não foi liberado explicitamente |

Também há **fragment default actions** (para pacotes fragmentados).

> [!warning] Armadilha clássica
> Com `StatelessDefaultActions = aws:drop` e **sem** regra de `forward`, **nenhum tráfego chega ao stateful** — todo o poder de inspeção fica inútil e o tráfego é derrubado. O padrão seguro é **`aws:forward_to_sfe`**.

### 2.3 Custom actions (métricas)

Uma **ação customizada** publica **métricas no CloudWatch** (contagem de pacotes que casaram) — útil para medir tráfego sem bloquear (observabilidade stateless).

## 3. Rule groups stateful

Há **três formas** de definir regras stateful:

### 3.1 Standard stateful rules (5-tupla)

```json
{
  "RulesSource": { "StatefulRules": [
    { "Action": "PASS", "Header": {
        "Protocol": "TCP", "Source": "10.0.0.0/16", "SourcePort": "ANY",
        "Direction": "FORWARD", "Destination": "ANY", "DestinationPort": "443" },
      "RuleOptions": [ { "Keyword": "sid:1000001" } ] },
    { "Action": "DROP", "Header": {
        "Protocol": "TCP", "Source": "ANY", "SourcePort": "ANY",
        "Direction": "ANY", "Destination": "10.0.0.0/16", "DestinationPort": "22" },
      "RuleOptions": [ { "Keyword": "sid:1000002" } ] }
  ] }
}
```

Ações: `PASS`, `DROP`, `ALERT`, `REJECT` (envia RST/ICMP). **Direction**: `FORWARD` (origem→destino) ou `ANY` (bidirecional).

### 3.2 Listas de domínios (domain list)

A forma **mais usada** para **egress por nome**:

```json
{
  "RulesSource": { "RulesSourceList": {
    "Targets": [".amazonaws.com", "repo.pacotes.example.com", "api.parceiro.example.com"],
    "TargetTypes": ["HTTP_HOST", "TLS_SNI"],
    "GeneratedRulesType": "ALLOWLIST"
  } }
}
```

| Elemento | Detalhe |
|---|---|
| **TargetTypes** | `HTTP_HOST` (cabeçalho Host em HTTP) e/ou `TLS_SNI` (Server Name Indication no handshake TLS) — **inclua ambos** para cobrir HTTP e HTTPS |
| **Wildcard** | Prefixo com ponto (`.example.com`) cobre **o domínio e subdomínios** |
| **ALLOWLIST** | **Só** esses domínios passam; o restante HTTP/TLS é **descartado** |
| **DENYLIST** | Esses domínios são **bloqueados**; o resto segue |
| **Limitação** | Só enxerga **HTTP/HTTPS** (Host/SNI); **TLS 1.3 com ECH** (Encrypted Client Hello) pode esconder o SNI — avaliar inspeção TLS ou outros controles; outros protocolos não são filtrados por nome |

> [!info] Allowlist exige cuidado
> Uma **allowlist de domínios** descarta **HTTP/TLS** não listado, mas **não** afeta outros protocolos (por exemplo, DNS, SSH, TCP puro). Combine com **regras 5-tupla** (e DNS Firewall) para fechar a saída por completo.

### 3.3 Regras compatíveis com Suricata

Texto com **regras Suricata** (um conjunto por linha), para **IPS/assinaturas**:

```
# Alertar tentativa de download de executável Windows via HTTP
alert http $HOME_NET any -> $EXTERNAL_NET any (msg:"Download de EXE suspeito"; \
   flow:established,to_server; http.uri; content:".exe"; endswith; \
   sid:2000001; rev:1;)

# Bloquear tráfego a um servidor de comando e controle conhecido (IP documental)
drop tcp $HOME_NET any -> 203.0.113.50 any (msg:"C2 conhecido"; flow:to_server; sid:2000002; rev:1;)

# Bloquear SSH em porta não padrão (protocolo reconhecido pelo motor, não pela porta)
drop ssh $HOME_NET any -> $EXTERNAL_NET !22 (msg:"SSH em porta incomum"; flow:to_server; sid:2000003; rev:1;)

# Alertar TLS para um domínio específico (SNI)
alert tls $HOME_NET any -> $EXTERNAL_NET any (msg:"TLS para dominio vigiado"; \
   tls.sni; content:"servidor-vigiado.example.net"; nocase; endswith; sid:2000004; rev:1;)
```

| Elemento | Significado |
|---|---|
| **Ação** | `alert`, `drop`, `pass`, `reject` |
| **Protocolo L7** | `http`, `tls`, `dns`, `ssh`, `smb`, `ftp`... (o motor **identifica o protocolo pelo conteúdo**, não só pela porta) |
| **Variáveis** | `$HOME_NET` (sua VPC/CIDRs — **defina** em *rule variables*), `$EXTERNAL_NET` |
| **Opções** | `msg`, `flow`, `content`, `pcre`, `http.uri`, `tls.sni`, `threshold`, `sid` (único!), `rev` |
| **`sid`** | **Identificador único** obrigatório por regra |

**Variáveis de regra**: configure `HOME_NET` com os CIDRs da VPC (e do on-premises, se relevante) e **grupos de IPs/portas** (`IPSets`, `PortSets`) para reaproveitar.

Boas práticas:

1. **Teste a regra** com `alert` antes de `drop`.
2. **Use `flow:`** (`established,to_server`) para reduzir falsos positivos e custo.
3. **Evite `pcre` pesado** (consome capacidade e latência).
4. **`sid` únicos** (faixa reservada para regras próprias, ex.: ≥ 1.000.000).
5. **Versione** as regras no Git e implante via IaC.
6. **Regras de terceiros** (Emerging Threats etc.): confirme **licença/termos** e compatibilidade com o subconjunto do Suricata suportado.

## 4. Ordem de avaliação das regras stateful

Duas modalidades, definidas **na firewall policy** (e escolhidas **na criação**; de memória, imutável depois):

### 4.1 Default action order (padrão)

Regras são agrupadas **por ação**, avaliadas na ordem:

```
1) PASS  →  2) DROP  →  3) ALERT   (a primeira ação que casar vale; "pass" ganha de "drop")
```

Não há “prioridade por regra” dentro do conjunto; o que importa é **o tipo de ação**. Simples, mas **menos previsível** em políticas complexas (por exemplo, uma regra `pass` ampla “anula” um `drop` específico).

### 4.2 Strict order

Regras avaliadas **na ordem** dos **rule groups (priority)** e das regras dentro deles — como uma ACL tradicional (**first match wins**). Mais previsível e **recomendado** para políticas elaboradas.

| Ponto | Detalhe |
|---|---|
| **Prioridade** | Cada rule group stateful na policy tem **número de prioridade**; menor primeiro |
| **Ação padrão stateful** | Em strict order há **default actions**: `drop all`, `drop established`, `alert all`, `alert established` — definem o que acontece com tráfego **sem regra casada** |
| **Padrão recomendado** | **Strict order + default action `drop established` (+ alert)** com **allowlists explícitas** antes |
| **Regras de domínio** | Em strict order, a **ação padrão `drop`** é o que “fecha” o que não está na allowlist |

### 4.3 Exemplo de policy com ordem estrita

```json
{
  "StatelessDefaultActions": ["aws:forward_to_sfe"],
  "StatelessFragmentDefaultActions": ["aws:forward_to_sfe"],
  "StatefulEngineOptions": { "RuleOrder": "STRICT_ORDER" },
  "StatefulDefaultActions": ["aws:drop_established", "aws:alert_established"],
  "StatefulRuleGroupReferences": [
    { "Priority": 10, "ResourceArn": ".../stateful-rulegroup/bloqueios-conhecidos" },
    { "Priority": 20, "ResourceArn": ".../stateful-rulegroup/egress-permitidos" },
    { "Priority": 30, "ResourceArn": ".../stateful-rulegroup/assinaturas-ips" }
  ]
}
```

Leitura: primeiro **bloquear o que sabemos ser ruim**, depois **permitir o que é legítimo**, depois **assinaturas**; o resto cai na **ação padrão** (descartar estabelecido e alertar).

## 5. Rule groups gerenciados pela AWS

Pacotes de regras **mantidos e atualizados pela AWS** (e, em alguns casos, por parceiros), que você **anexa** à policy (somente referência; **não** consomem sua capacidade, de memória — confirmar):

| Tipo (de memória) | Conteúdo |
|---|---|
| **Domain/IP reputation** | Listas de domínios e IPs maliciosos (botnets, malware, spam) |
| **Threat signatures** | Assinaturas por categoria (malware, exploits, DoS, web, protocolos) |
| **Active Threat Defense** (confirmar) | Inteligência de ameaças ativa da AWS (MadPot) |
| **Allow/Deny lists** de serviços | Por exemplo, domínios abusados |

Uso: **anexe como base** e ajuste com regras próprias; atente às **ações padrão** das regras gerenciadas (algumas apenas `alert`) e ao possível **impacto de falsos positivos**.

## 6. Capacidade (capacity) dos rule groups

| Aspecto | Detalhe |
|---|---|
| **Definição** | Número inteiro definido **na criação**; limita o tamanho do rule group |
| **Imutável** | Para aumentar, **crie outro rule group** e troque a referência na policy |
| **Consumo** | Depende do tipo e da complexidade das regras (domínios, 5-tupla, Suricata) |
| **Limites** | Há limite por rule group e **total por policy** (confirmar quotas) |
| **Boa prática** | **Folga** de 20–50% e **documentar** o consumo; dividir em **vários** rule groups por finalidade |

## 7. Padrões de políticas (receitas)

### 7.1 Egress allowlist (modelo mais seguro)

```
Stateless:  default = forward_to_sfe
Stateful (STRICT):
  p10  bloqueios-conhecidos (managed: domínios/IPs maliciosos) — DROP+ALERT
  p20  egress-permitidos (domain allowlist) — PASS
  p30  regras 5-tupla para serviços internos (DNS, NTP) — PASS
  default: drop_established + alert_established
```

### 7.2 Proteção de ingress (aplicações expostas)

```
Stateless: descartar ICMP e portas inesperadas da internet (opcional)
Stateful (STRICT):
  p10  regras de IPS (Suricata gerenciadas) — ALERT/DROP
  p20  portas permitidas (80/443) para os destinos esperados — PASS
  default: drop_established + alert_established
```

### 7.3 Inspeção leste-oeste (segmentação)

```
Stateful (STRICT):
  p10  permitir pares de comunicação aprovados (VPC-A→VPC-B porta 5432) — PASS
  p20  alertar movimentos incomuns (SMB/RDP entre VPCs) — ALERT/DROP
  default: drop_established + alert
```

### 7.4 Modo de observação (rollout seguro)

1. Fase **alert-only** (todas as regras novas como `alert`) por 1–2 semanas.
2. Analisar **logs** (falsos positivos, tráfego legítimo bloqueável).
3. Promover para **`drop`** por etapas (por rule group/ambiente).
4. **Reavaliar** periodicamente (domínios novos, mudanças de aplicações).

## 8. Inspeção TLS (visão geral)

Sem inspeção TLS, o firewall vê **apenas o SNI** do tráfego criptografado (e metadados do handshake). Com **TLS inspection** (de memória — confirmar a disponibilidade e a configuração atuais):

- O firewall **descriptografa** (ação de *man-in-the-middle* autorizada), aplica regras L7/Suricata no **conteúdo** e **recriptografa**;
- Exige **certificado de CA** (importado/gerenciado no **ACM**) **confiável nos clientes** e **escopo** definido (quais fluxos);
- Há **custo de desempenho** e **riscos de privacidade/conformidade**: exclua tráfego sensível (bancos, saúde) e documente a base legal.
- **Certificate pinning** e algumas aplicações **quebram** com inspeção TLS.

Detalhes de segurança na folha de **Segurança e governança**.

## 9. Exemplos de comandos

```bash
# Criar um rule group Suricata (ilustrativo)
aws network-firewall create-rule-group --rule-group-name ips-basico --type STATEFUL --capacity 200 \
  --rule-group '{"RulesSource":{"RulesString":"drop tcp $HOME_NET any -> 203.0.113.50 any (msg:\"C2\"; flow:to_server; sid:2000002; rev:1;)"},
                 "RuleVariables":{"IPSets":{"HOME_NET":{"Definition":["10.0.0.0/16"]}}},
                 "StatefulRuleOptions":{"RuleOrder":"STRICT_ORDER"}}'

# Atualizar a policy (requer o token de atualização)
aws network-firewall describe-firewall-policy --firewall-policy-name politica-egress
aws network-firewall update-firewall-policy --firewall-policy-name politica-egress \
  --update-token <token> --firewall-policy file://politica.json
```

## 10. Erros comuns

- **Default stateless `drop`** sem forward → inspeção stateful nunca roda.
- **Allowlist de domínios** só com `HTTP_HOST` (sem `TLS_SNI`) → HTTPS bloqueado/ignorado.
- **Achar que a allowlist de domínios fecha toda a saída** (outros protocolos passam).
- **Ordem padrão com `pass` amplo** anulando `drop` específico.
- **Esquecer `HOME_NET`** → regras Suricata com direção errada ou que nunca casam.
- **`sid` duplicado** → regras ignoradas/erro.
- **Ativar `drop` sem fase de `alert`** → derrubar tráfego legítimo.
- **Capacidade subdimensionada** (imutável).
- **Regras Suricata não suportadas** (alguns recursos/keywords) → falha na criação.
- **TLS inspection sem escopo/CA** nos clientes → falhas de conexão.
- **Sem versionamento** das regras: mudanças manuais sem rastro.

## 11. Troubleshooting

| Sintoma | Causa provável | Ação |
|---|---|---|
| Nada é bloqueado | Tráfego não roteado ao firewall; default stateless `pass`; ordem padrão com `pass` | Verificar rotas e a ordem; usar strict order |
| Tudo bloqueado | Default `drop` sem allow; stateless drop | Revisar defaults e adicionar allow/forward |
| HTTPS permitido por domínio falha | Falta `TLS_SNI`; ECH; CDN com SNI diferente | Incluir SNI; revisar domínios (CDNs usam vários nomes) |
| Regra Suricata não cria | Sintaxe/keyword não suportada; `sid` repetido | Validar e corrigir; ver o erro da API |
| Alertas sem efeito de bloqueio | Ação `alert` em vez de `drop` | Ajustar a ação após validar |
| Muitos falsos positivos | Regras gerenciadas amplas | Ajustar/desativar assinaturas; `pass` de exceções específicas (strict order) |
| Capacidade excedida | Regras demais | Criar rule group maior e migrar |
| Alterações não surtem efeito | Policy não atualizada/propagação em andamento | Conferir o status e a **versão** da policy |

## 12. Resumo rápido

- **Stateless**: por pacote, **prioridade**, ações `pass/drop/forward`; default **`forward_to_sfe`**.
- **Stateful**: 5-tupla, **listas de domínios** (`HTTP_HOST` + `TLS_SNI`; allow/deny), **Suricata** (`sid` único, `HOME_NET`).
- **Ordem stateful**: **default action order** (pass → drop → alert) vs **strict order** (por prioridade, first match) com **default actions** (`drop_established`, `alert_established`) — **recomendado: strict**.
- **Managed rule groups** da AWS para reputação e assinaturas; **capacidade imutável** (folga!).
- **Rollout seguro**: **alert → analisar → drop**; regras versionadas (IaC).
- **TLS inspection** amplia a visibilidade, mas exige CA, escopo e cuidados de privacidade.

## 🧩 Quiz de Fixação

1. Qual o padrão recomendado para a ação padrão stateless e por quê?
2. Por que incluir `HTTP_HOST` e `TLS_SNI` em listas de domínios?
3. Qual a diferença entre default action order e strict order?
4. Para que servem `HOME_NET` e `sid` em regras Suricata?
5. Como implantar regras novas com segurança?
6. O que acontece com a capacidade de um rule group depois de criado?
7. O que uma allowlist de domínios não cobre?

**Respostas:**

1. `aws:forward_to_sfe`, para encaminhar o tráfego ao motor stateful, onde ocorrem a inspeção de domínio e IPS; `drop` sem forward bloquearia tudo.
2. Para cobrir tanto HTTP (cabeçalho Host) quanto HTTPS (SNI do handshake TLS).
3. Na default action order, a avaliação segue o tipo de ação (pass, depois drop, depois alert); na strict order segue a prioridade dos rule groups e regras (first match), como uma ACL.
4. `HOME_NET` define os CIDRs internos usados nas regras; `sid` é o identificador único obrigatório de cada regra.
5. Iniciar em `alert`, analisar logs por um período, ajustar falsos positivos e só então promover para `drop`, por etapas e via IaC.
6. É imutável; para aumentar é preciso criar um novo rule group e trocar a referência na policy.
7. Outros protocolos além de HTTP/HTTPS por nome (por exemplo, DNS, SSH, TCP puro) e potencialmente TLS com SNI criptografado (ECH).
