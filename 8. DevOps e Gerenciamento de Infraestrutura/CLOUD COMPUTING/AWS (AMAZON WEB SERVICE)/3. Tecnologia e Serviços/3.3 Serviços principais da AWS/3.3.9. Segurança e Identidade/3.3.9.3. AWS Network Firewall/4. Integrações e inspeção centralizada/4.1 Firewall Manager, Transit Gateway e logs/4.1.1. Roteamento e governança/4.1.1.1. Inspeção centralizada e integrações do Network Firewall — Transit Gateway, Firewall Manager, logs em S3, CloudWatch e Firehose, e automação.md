### 4.1.1.1. Inspeção centralizada e integrações do Network Firewall — Transit Gateway, Firewall Manager, logs em S3, CloudWatch e Firehose, e automação

> [!warning] Aviso
> Modos de anexo ao Transit Gateway, recursos do Firewall Manager para Network Firewall, formatos e campos de log, limites e preços abaixo são **de memória e mudam**. **Confirme na documentação do Network Firewall, do Transit Gateway e do Firewall Manager.** JSONs, rotas e comandos são ilustrativos e **não foram executados**. IDs e CIDRs são fictícios. Alterar rotas do Transit Gateway pode **cortar a conectividade de toda a organização**: teste e planeje rollback.

## 1. Por que centralizar

Com dezenas de VPCs e contas, manter um firewall **por VPC** significa **muitos endpoints** (custo por hora), **muitas políticas** divergentes e **logs espalhados**. A inspeção **centralizada** concentra o caminho em um **hub**:

```
 VPC-App1 ─┐                                    ┌──▶ Internet (egress central via NAT)
 VPC-App2 ─┼──▶ AWS TRANSIT GATEWAY ──▶ [VPC DE INSPEÇÃO + NETWORK FIREWALL] ──┤
 VPC-Dados ┘        (hub de rotas)                                             └──▶ Tráfego leste-oeste (VPC ↔ VPC)
 On-premises (VPN/DX) ─┘
```

| Benefício | Detalhe |
|---|---|
| **Política única** | Mesmas regras para todas as VPCs conectadas |
| **Menos endpoints** | Menos custo por hora que firewalls em cada VPC |
| **Inspeção leste-oeste** | Tráfego **entre VPCs** e entre **on-premises e VPCs** passa pelo firewall |
| **Egress compartilhado** | Um único conjunto de NAT/IGW de saída (menos IPs públicos para allowlist de parceiros) |
| **Logs centralizados** | Um ponto de coleta para auditoria |
| **Separação de funções** | A equipe de segurança **opera o hub**; times de aplicação consomem |

Riscos e custos a ponderar: **ponto de concentração** (HA, capacidade), **custo de processamento do TGW por GB**, **complexidade de rotas** e **raio de impacto** de erros no hub.

## 2. Network Firewall + Transit Gateway

### 2.1 Modelo clássico: VPC de inspeção

1. **VPC de inspeção** com **subnets de firewall** (endpoints) e **subnets de TGW** (anexo).
2. **Anexo VPC** da VPC de inspeção ao TGW com **appliance mode habilitado** (garante **simetria** por AZ).
3. **Route tables do TGW**:
   - **RT de spokes** (associada aos anexos das VPCs de aplicação): `0.0.0.0/0 → anexo da VPC de inspeção`;
   - **RT de inspeção** (associada ao anexo da VPC de inspeção): rotas de **retorno** para cada VPC (`10.1.0.0/16 → anexo VPC1`, ...).
4. **Route tables da VPC de inspeção**:
   - **Subnets de TGW**: `0.0.0.0/0 → endpoint do firewall` (da mesma AZ);
   - **Subnets de firewall**: `10.0.0.0/8 → TGW` (retorno aos spokes) e `0.0.0.0/0 → NAT GW`/IGW (egress);
   - **Subnets públicas (NAT)**: `10.0.0.0/8 → endpoint do firewall` (retorno do tráfego de internet de volta).

```
Spoke VPC ─▶ TGW (RT spokes: 0.0.0.0/0 → inspeção)
          ─▶ Subnet TGW (inspeção AZ-a) ─▶ [endpoint fw AZ-a] ─▶ Subnet NAT ─▶ IGW ─▶ Internet
                                                  │
                                      leste-oeste: volta ao TGW ─▶ VPC destino
```

### 2.2 Anexo nativo do firewall ao TGW (de memória — confirmar)

O firewall pode ser **anexado diretamente** ao Transit Gateway (sem construir e manter a VPC de inspeção, as subnets de TGW e as rotas internas):

| Aspecto | Clássico | Anexo nativo |
|---|---|---|
| **VPC de inspeção** | Necessária (você gerencia) | **Não necessária** |
| **Roteamento interno** | Manual (subnets/RTs) | **Gerenciado pela AWS** |
| **Appliance mode** | Você habilita | Tratado pelo serviço |
| **Egress para internet** | Via NAT/IGW na VPC de inspeção | Requer arquitetura de saída separada (ex.: outra VPC de egress) |
| **Complexidade** | Maior | **Menor** |

Escolha o nativo para **simplicidade**; o clássico quando precisa de **controle total** (NAT, rotas customizadas, combinação com outros appliances).

### 2.3 Appliance mode (modo clássico)

Garante que o TGW envie **ida e volta** do fluxo ao **mesmo endpoint/AZ**:

```bash
aws ec2 modify-transit-gateway-vpc-attachment \
  --transit-gateway-attachment-id tgw-attach-0abc \
  --options ApplianceModeSupport=enable
```

Sem ele, os dois sentidos podem usar AZs diferentes → o stateful **vê só metade** da conexão → **RSTs e timeouts**.

### 2.4 Padrões de tráfego

| Fluxo | Passa pelo firewall? | Observação |
|---|---|---|
| **Spoke → Internet** | Sim | Egress central; allowlist de domínios |
| **Internet → Spoke** (ingress) | Depende | Pode usar **ALB nos spokes** (não passar pelo hub) ou ingress central |
| **Spoke A ↔ Spoke B** | Sim | Segmentação leste-oeste |
| **On-premises ↔ Spoke** | Sim | Anexo VPN/DX ao TGW + rotas |
| **Dentro da mesma VPC** | **Não** | Rota `local` não passa pelo TGW |

## 3. AWS Firewall Manager

O **Firewall Manager** gerencia **políticas de segurança de forma central** em **Organizations**. Para o Network Firewall:

| Recurso | Descrição (de memória — confirmar) |
|---|---|
| **Política de Network Firewall** | Implanta **firewalls e policies** em **todas as VPCs** (ou por tag/OU) automaticamente, com rule groups **centrais** |
| **Modelos de implantação** | **Distribuído** (um firewall por VPC) ou **centralizado** (firewall na VPC de inspeção, apoiado por TGW/roteamento) |
| **Auto-remediação** | Cria endpoints/recursos faltantes e corrige **desvios** |
| **Escopo** | Contas, OUs, **tags** de VPC, exclusões |
| **Rule groups** | **Stateless/stateful** definidos na política; **contas-membro podem adicionar** rule groups próprios (opcional) |
| **Conformidade** | Painel de **VPCs compatíveis/não compatíveis** e **findings** |
| **Requisitos** | **Organizations**, **AWS Config** habilitado, **administrador do Firewall Manager** designado |

```
Administrador FMS (conta de segurança) ──política──▶ Organizations (OU Produção)
        └▶ cria/atualiza automaticamente:  firewall + policy + endpoints em cada VPC elegível
        └▶ monitora conformidade e remedia
```

| Quando usar Firewall Manager | Quando não |
|---|---|
| Muitas contas/VPCs e necessidade de **baseline único** | Poucas VPCs e uma equipe só |
| Exigência de **governança** (auditoria de conformidade) | Cenários muito customizados por VPC |
| **Novas contas** devem nascer protegidas | — |

> [!info] FMS não é só Network Firewall
> O Firewall Manager também governa **WAF, Shield Advanced, Security Groups, Route 53 Resolver DNS Firewall** e outros. A visão completa fica na folha própria do Firewall Manager (quando estudada).

## 4. Logging e visibilidade

### 4.1 Tipos de log

| Log | Conteúdo | Quando é gerado |
|---|---|---|
| **Alert logs** | Eventos de regras com ação **alert** (ou drop com alerta): assinatura, ação, origem/destino, severidade | Ao disparar a regra |
| **Flow logs** | Registro de **fluxos** que passam pelo motor stateful (início/fim, bytes) | Por conexão |
| **TLS logs** (se TLS inspection) | Eventos relacionados à inspeção TLS (erros, cipher) | Conforme configuração |

### 4.2 Destinos

| Destino | Melhor para | Observação |
|---|---|---|
| **Amazon S3** | **Retenção longa, baixo custo, análise com Athena** | Prefixos por data; **KMS**; Object Lock para evidência |
| **CloudWatch Logs** | **Consulta rápida**, **metric filters**, **alarmes**, Logs Insights | Custo por ingestão/armazenamento maior |
| **Kinesis Data Firehose** | **Streaming** para **SIEM/Splunk/OpenSearch/S3** | Transformação e entrega gerenciada |

```bash
aws network-firewall update-logging-configuration --firewall-name fw-inspecao \
  --logging-configuration '{"LogDestinationConfigs":[
     {"LogType":"ALERT","LogDestinationType":"S3","LogDestination":{"bucketName":"nfw-logs-123456789012","prefix":"alert"}},
     {"LogType":"FLOW","LogDestinationType":"CloudWatchLogs","LogDestination":{"logGroup":"/nfw/flow"}}]}'
```

### 4.3 Exemplo de alerta (resumido, fictício)

```json
{
  "firewall_name": "fw-inspecao",
  "event": {
    "event_type": "alert",
    "src_ip": "10.1.2.34", "dest_ip": "203.0.113.50", "dest_port": 443, "proto": "TCP",
    "alert": { "action": "blocked", "signature_id": 2000002, "signature": "C2 conhecido", "severity": 1 },
    "tls": { "sni": "servidor-vigiado.example.net" }
  }
}
```

### 4.4 Análise com Athena (S3)

```sql
-- Top origens bloqueadas na última semana (ilustrativo)
SELECT event.src_ip, count(*) AS bloqueios
FROM nfw_alert_logs
WHERE event.alert.action = 'blocked' AND dt >= date_format(date_add('day', -7, current_date), '%Y/%m/%d')
GROUP BY event.src_ip ORDER BY bloqueios DESC LIMIT 20;
```

### 4.5 Alarmes úteis

| Alarme | Fonte | Ação |
|---|---|---|
| **Pico de bloqueios** de uma origem | Metric filter (CW Logs) | Investigar host comprometido |
| **Alertas de severidade 1** | Firehose → SIEM / metric filter | Resposta a incidente |
| **Domínios novos bloqueados** (egress) | Athena/Logs Insights | Revisar a allowlist ou detectar C2 |
| **Queda de tráfego** (zero fluxo) | Métricas do firewall | Verificar rotas/endpoints |

## 6. Automação

### 6.1 Atualização de allowlist por pipeline

```
Pull request (alteração em domínios permitidos)
   ▶ validação (lint de sintaxe, testes)  ▶ aprovação (segurança)
   ▶ pipeline cria nova versão do rule group (ou atualiza com token)
   ▶ implantação por etapas (homologação ▶ produção) com monitoramento de alertas
```

### 6.2 Resposta automática a alertas

```
Alerta de alta severidade (CloudWatch Logs/Firehose)
   ▶ Lambda/Step Functions
        ├─ identifica o host de origem (ENI/instância) e seu dono
        ├─ aplica isolamento (SG de quarentena / NACL)  [com aprovação em produção]
        ├─ cria ticket e notifica o SOC
        └─ opcional: adiciona IP/domínio a uma lista de bloqueio (rule group dinâmico)
```

Cuidados: **idempotência**, limites de taxa (não bloquear a empresa por um falso positivo), **aprovação humana** nos casos críticos, **auditoria** de cada ação.

### 6.3 Listas dinâmicas

Rule groups **atualizados por Lambda** com **inteligência de ameaças** (feeds de IPs/domínios): lembrar da **capacidade imutável** e do **token de atualização** (`update-rule-group` exige `UpdateToken` para evitar conflitos).

## 8. Checklist de inspeção centralizada

- [ ] **Modelo** (clássico vs anexo nativo) escolhido e documentado
- [ ] **Appliance mode** habilitado (clássico); **RTs do TGW** (spokes e inspeção) revisadas
- [ ] **Rotas de retorno** nas subnets de firewall/NAT corretas
- [ ] **Firewall Manager** (se multi-conta) com política por OU/tag
- [ ] **Logs** (alert + flow) para **S3/CloudWatch/Firehose**, criptografados
- [ ] **Alarmes** de severidade, picos e queda de tráfego
- [ ] **DNS Firewall** e **WAF** complementando
- [ ] **IaC** e **pipeline** de mudança de regras com aprovação
- [ ] **Contingência**: procedimento de bypass testado
- [ ] **Custos** monitorados (endpoints, GB do firewall, GB do TGW)

## 9. Erros comuns

- **Sem appliance mode** (clássico) → fluxos assimétricos.
- **Rotas de retorno ausentes** na VPC de inspeção → tráfego “sumindo”.
- **TGW com propagação padrão** enviando tráfego direto entre spokes (sem passar pelo firewall) por falta de **tabelas separadas**.
- **Assumir que tráfego intra-VPC passa pelo hub** (não passa).
- **Logs só no CloudWatch** em alto volume → custo alto; usar S3/Firehose para volume.
- **Logs sem retenção/KMS**.
- **Firewall Manager sem Config** habilitado (política não aplica).
- **Automação de bloqueio sem salvaguardas** (auto-bloqueio da própria infraestrutura).
- **Subestimar o custo do TGW** (GB processados) além do firewall.
- **Allowlist de domínios** sem coordenar com **DNS Firewall**.

## 10. Troubleshooting

| Sintoma | Causa provável | Ação |
|---|---|---|
| Spokes sem internet após o hub | RT do TGW/VPC de inspeção incompleta; sem retorno | Revisar as RTs e as rotas de retorno |
| Conexões entre VPCs resetando | Falta de appliance mode; assimetria | Habilitar appliance mode; checar rotas por AZ |
| Tráfego **não** passa pelo firewall | Propagação direta entre anexos; RT errada | Separar RTs (spokes vs inspeção); remover propagação direta |
| FMS não implanta | Config desabilitado, escopo, permissões | Habilitar Config e revisar a política |
| Sem logs no S3 | Permissões do bucket; destino incorreto | Corrigir a bucket policy e a configuração |
| Logs sem campos de TLS | Sem TLS inspection | Habilitar (se justificável) |
| Latência alta | TLS inspection/capacidade; caminho cross-AZ | Medir; ajustar escopo e rotas |
| Custo alto de TGW | Muito leste-oeste inspecionado | Ajustar escopo (nem todo tráfego precisa passar) |

## 11. Resumo rápido

- **Centralizar** = **TGW + VPC de inspeção** (clássico, com **appliance mode**) ou **anexo nativo** do firewall: política única, menos endpoints, inspeção **leste-oeste** e egress compartilhado.
- **TGW**: RT de **spokes** (`0.0.0.0/0 → inspeção`) e RT de **inspeção** (retorno); **intra-VPC** não passa.
- **Firewall Manager**: implanta e **mantém** firewalls/policies em **Organizations** (distribuído ou centralizado), com **conformidade** e **auto-remediação** (exige **Config**).
- **Logs**: **alert**, **flow** (e TLS) para **S3** (retenção), **CloudWatch** (consulta/alarmes) e **Firehose** (SIEM).
- **Automação**: pipeline de regras com aprovação; resposta a alertas com salvaguardas.
- Complementos: **DNS Firewall**, **WAF**, **GuardDuty**, **Security Hub**, **CloudTrail**, **Config**.

## 🧩 Quiz de Fixação

1. Para que serve o appliance mode no Transit Gateway?
2. Quais route tables do TGW são necessárias no modelo clássico?
3. O que o Firewall Manager faz pelo Network Firewall?
4. Qual a diferença entre alert logs e flow logs?
5. Qual destino de log é mais indicado para retenção longa e análise com Athena?
6. Por que tráfego dentro da mesma VPC não passa pelo firewall do hub?
7. Cite uma salvaguarda necessária em automação de bloqueio.

**Respostas:**

1. Garante simetria: ida e volta do fluxo usam o mesmo endpoint/AZ, evitando que o firewall stateful veja só metade da conexão.
2. Uma para os spokes (`0.0.0.0/0` para o anexo da VPC de inspeção) e uma para a inspeção, com rotas de retorno para cada VPC.
3. Implanta e mantém firewalls, policies e rule groups em todas as contas/VPCs da organização, com monitoramento de conformidade e auto-remediação.
4. Alert logs registram eventos de regras acionadas; flow logs registram os fluxos (conexões) processados pelo motor stateful.
5. Amazon S3, com prefixos por data, KMS e consultas pelo Athena.
6. Porque o tráfego local usa a rota `local` da VPC e não passa pelo Transit Gateway nem pela VPC de inspeção.
7. Aprovação humana em produção, limites de taxa, idempotência e auditoria das ações, evitando bloquear a própria infraestrutura por um falso positivo.
