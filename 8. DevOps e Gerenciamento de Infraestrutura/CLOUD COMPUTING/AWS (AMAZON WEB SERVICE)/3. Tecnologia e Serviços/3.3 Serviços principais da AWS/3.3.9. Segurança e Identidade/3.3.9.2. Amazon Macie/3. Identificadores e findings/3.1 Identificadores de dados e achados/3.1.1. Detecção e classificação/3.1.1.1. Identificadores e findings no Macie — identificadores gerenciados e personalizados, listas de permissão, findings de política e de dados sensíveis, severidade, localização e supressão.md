### 3.1.1.1. Identificadores e findings no Macie — identificadores gerenciados e personalizados, listas de permissão, findings de política e de dados sensíveis, severidade, localização e supressão

> [!warning] Aviso
> Nomes de identificadores, campos de finding, critérios de severidade e limites (tamanho de regex, quantidade de identificadores) abaixo são **de memória e mudam**. **Confirme na documentação do Macie.** Regex, comandos e JSONs são ilustrativos e **não foram executados**. Todos os dados de exemplo (CPFs, cartões, e-mails) são **fictícios**; valide qualquer regex com dados de teste, nunca com dados reais de clientes.

## 1. Como o Macie decide que algo é “sensível”

A descoberta depende de **detectores**, chamados **data identifiers**. Eles decidem o que é um CPF, um cartão ou uma chave AWS dentro de bilhões de caracteres. Há três peças:

```
 Texto extraído do objeto
          │
          ▼
 ┌─────────────────────────┐   ┌──────────────────────────┐
 │ Managed data identifiers │   │ Custom data identifiers  │   ← o que DETECTAR
 │ (prontos, da AWS)        │   │ (regex + keywords + ...) │
 └────────────┬─────────────┘   └────────────┬─────────────┘
              └──────────────┬───────────────┘
                             ▼
                    Allow lists (o que IGNORAR)
                             ▼
                          FINDING
```

| Peça | Papel |
|---|---|
| **Managed data identifiers** | Detectores **prontos**, mantidos e atualizados pela AWS |
| **Custom data identifiers** | Detectores **seus**, para formatos próprios do negócio |
| **Allow lists** | **Exceções**: textos/padrões que **não** devem gerar finding |

## 2. Managed data identifiers

### 2.1 O que são

Detectores que combinam **padrões**, **validações** (por exemplo, o **dígito verificador** de um cartão/documento), **palavras-chave de contexto** e **heurísticas** para reduzir falsos positivos. A AWS mantém a lista (de memória: **mais de uma centena** de tipos, com variações por **país**).

| Categoria | Tipos típicos (exemplos de memória — confirmar) |
|---|---|
| **Credenciais** | `AWS_CREDENTIALS` (access key + secret), `OPENSSH_PRIVATE_KEY`, `PGP_PRIVATE_KEY`, `HTTP_BASIC_AUTH_HEADER`, tokens de serviços comuns |
| **Financeiro** | `CREDIT_CARD_NUMBER`, `CREDIT_CARD_EXPIRATION`, `CREDIT_CARD_MAGNETIC_STRIPE`, `BANK_ACCOUNT_NUMBER` (por país) |
| **PII** | `NAME`, `ADDRESS`, `EMAIL_ADDRESS`, `PHONE_NUMBER`, `DATE_OF_BIRTH`, `PASSPORT_NUMBER`, `DRIVERS_LICENSE`, `NATIONAL_IDENTIFICATION_NUMBER` |
| **PHI** | `HEALTH_INSURANCE_CLAIM_NUMBER`, `MEDICAL_RECORD`/códigos de diagnóstico, identificadores de paciente |

### 2.2 Seleção de identificadores em jobs e na automática

| Modo | Efeito |
|---|---|
| **ALL** | Usa todos os managed identifiers (padrão em jobs) |
| **RECOMMENDED** | Conjunto recomendado pela AWS (padrão na automática) |
| **INCLUDE** | Só os listados |
| **EXCLUDE** | Todos **exceto** os listados |
| **NONE** | Nenhum (só custom identifiers) |

Estratégia: **EXCLUDE** tipos que geram ruído no seu contexto (por exemplo, `NAME` em bases de produtos com nomes comuns) e **INCLUDE** só o essencial em jobs de conformidade específicos (ex.: PCI → cartões).

### 2.3 Limites a conhecer

- A cobertura **varia por país e idioma**; documentos brasileiros podem ter **cobertura parcial** — confirme e complemente com **custom identifiers** (CPF, CNPJ, RG, CNH, PIS, título de eleitor).
- O Macie **detecta texto**; **imagens** e **PDFs escaneados** (sem camada de texto) **não** são lidos (sem OCR — confirmar).
- **Contexto importa**: um número de 16 dígitos aleatório que **passa no teste de Luhn** pode ser sinalizado como cartão (falso positivo); **palavras-chave próximas** (“cartão”, “card number”) aumentam a confiança.

## 3. Custom data identifiers

### 3.1 Anatomia

| Campo | Função | Exemplo |
|---|---|---|
| **`regex`** | Padrão a casar | `\b\d{3}\.\d{3}\.\d{3}-\d{2}\b` (formato de CPF) |
| **`keywords`** | Palavras que devem estar **perto** do match | `cpf`, `documento` |
| **`maximumMatchDistance`** | Distância máxima (em caracteres) entre keyword e match (padrão ~50; confirmar) | `30` |
| **`ignoreWords`** | Palavras que, se **dentro do match**, o invalidam | `000.000.000-00` |
| **`severityLevels`** | Faixas de contagem → severidade (Low/Medium/High) | ≥1 Low, ≥10 Medium, ≥100 High |

### 3.2 Exemplos (ilustrativos)

```bash
# CPF formatado, com palavra-chave por perto para reduzir falsos positivos
aws macie2 create-custom-data-identifier \
  --name cpf-formatado \
  --regex '\b[0-9]{3}\.[0-9]{3}\.[0-9]{3}-[0-9]{2}\b' \
  --keywords cpf documento "numero do cpf" \
  --maximum-match-distance 30 \
  --ignore-words "000.000.000-00" "111.111.111-11" \
  --severity-levels '[{"occurrencesThreshold":1,"severity":"LOW"},{"occurrencesThreshold":50,"severity":"MEDIUM"},{"occurrencesThreshold":500,"severity":"HIGH"}]'

# Matrícula interna (ex.: "MAT" + 7 dígitos)
aws macie2 create-custom-data-identifier \
  --name matricula-colaborador \
  --regex '\bMAT[0-9]{7}\b'

# Testar o identificador contra um texto de exemplo ANTES de usar em produção
aws macie2 test-custom-data-identifier \
  --regex '\b[0-9]{3}\.[0-9]{3}\.[0-9]{3}-[0-9]{2}\b' \
  --sample-text "O cpf do titular de teste e 123.456.789-09 conforme o documento."
```

### 3.3 Boas práticas de regex

1. **Âncoras de palavra** (`\b`) para não casar no meio de números maiores.
2. **Formatos reais** (com e sem pontuação, se ambos ocorrem) — ou dois identificadores.
3. **Keywords** reduzem falsos positivos de números “soltos”; **mas** podem causar falsos negativos se o documento não tiver contexto (ex.: coluna CSV sem cabeçalho). Equilibre.
4. **Evite regex ambíguas** (`\d{9}`): casam com tudo.
5. **Valide dígitos verificadores no pós-processamento** (o Macie não valida o dígito de CPF num custom identifier): use Lambda/Athena nos resultados para filtrar.
6. **Teste** com `test-custom-data-identifier` e com **amostras controladas**.
7. **Versione** os identificadores (nome com versão) e documente o **dono**.

### 3.4 Limites e custo

- Há **quotas** de quantidade de identificadores e de tamanho/complexidade da regex (de memória; confirmar).
- Custom identifiers **não** têm custo separado do GB inspecionado, mas **regex pesadas** podem alongar o processamento.
- **Mudanças** em um identificador **não reprocessam** automaticamente objetos já analisados: é preciso **novo job**.

## 4. Allow lists

### 4.1 O que são

Listas de **exceções** que o Macie **não** reporta, mesmo que casem com um identificador:

| Tipo | Como define | Exemplo |
|---|---|---|
| **Lista de texto** | Arquivo S3 com **um texto por linha** (correspondência exata, sem diferenciar maiúsculas) | `teste@empresa.com`, `4111111111111111` (cartão de teste) |
| **Regex** | Expressão **até um tamanho limitado** | `.*@teste\.empresa\.com` |

```bash
aws macie2 create-allow-list --name emails-de-teste \
  --criteria '{"s3WordsList":{"bucketName":"macie-config","objectKey":"allow/emails-teste.txt"}}'
aws macie2 create-allow-list --name dominio-sandbox \
  --criteria '{"regex":"[a-z0-9._-]+@sandbox\\.empresa\\.com"}'
```

### 4.2 Uso

- Associe allow lists a **jobs** e à **descoberta automatizada**.
- Ideal para **dados de teste, exemplos de documentação, números públicos conhecidos**.
- **Cuidado**: uma allow list ampla demais **esconde dados reais**. Revise periodicamente e limite a **casos específicos**.

## 5. Findings

### 5.1 Famílias

| Família | Origem | Pergunta |
|---|---|---|
| **Policy findings** | **Postura/configuração do bucket** (a partir de CloudTrail e S3) | “O bucket está **exposto ou sem proteção**?” |
| **Sensitive data findings** | **Conteúdo do objeto** | “Há **dado sensível** neste arquivo?” |

### 5.2 Policy findings (de memória — confirmar nomes)

| Tipo | Gatilho | Severidade típica |
|---|---|---|
| `Policy:IAMUser/S3BlockPublicAccessDisabled` | Block Public Access desativado | Alta/Média |
| `Policy:IAMUser/S3BucketPublic` | Bucket passou a ser **público** | Alta |
| `Policy:IAMUser/S3BucketEncryptionDisabled` | Criptografia padrão removida | Baixa/Média |
| `Policy:IAMUser/S3BucketReplicatedExternally` | Replicação para fora da **organização** | Alta |
| `Policy:IAMUser/S3BucketSharedExternally` | Compartilhamento com conta **externa** | Média/Alta |
| `Policy:IAMUser/S3BucketSharedWithCloudFront` | Acesso via **OAI/OAC** do CloudFront | Informativa/Baixa |

Dados do finding: **ator** (principal IAM, IP, user agent), **ação** (CloudTrail), **horário**, **bucket**, **configuração anterior/atual**. Servem para **investigar** (quem abriu o bucket?) e para **disparar remediação** (reaplicar Block Public Access).

### 5.3 Sensitive data findings (de memória — confirmar)

| Tipo | Significado |
|---|---|
| `SensitiveData:S3Object/Personal` | PII |
| `SensitiveData:S3Object/Financial` | Dados financeiros |
| `SensitiveData:S3Object/Credentials` | Credenciais/chaves |
| `SensitiveData:S3Object/CustomIdentifier` | Casou com custom identifier |
| `SensitiveData:S3Object/Multiple` | Mais de uma categoria |

### 5.4 Severidade dos findings de dados sensíveis

| Elemento | Efeito |
|---|---|
| **Tipo do dado** | Credenciais e financeiro tendem a severidade maior que PII leve |
| **Quantidade** de ocorrências | Mais ocorrências → severidade maior |
| **Diversidade** de tipos | `Multiple` pesa mais |
| **Custom identifier** | Severidade definida **por você** (`severityLevels`) |
| **Exposição do bucket** | O contexto (público, compartilhado) é mostrado no finding e ajuda a priorizar |

### 5.5 Localização do dado (occurrences)

Para cada detecção, o finding informa **onde**:

| Formato | Localização |
|---|---|
| **Texto/CSV/TSV** | **Linha** e **coluna** (CSV: nome da coluna/índice) |
| **JSON/JSONL** | **Caminho** do campo (`$.clientes[3].email`) |
| **Excel** | **Planilha, linha e coluna** |
| **PDF/Word** | **Página** e posição |
| **Parquet/Avro** | **Registro** e campo |
| **Arquivo compactado** | **Caminho dentro do arquivo** + localização no membro |

O Macie **não** exibe o dado por padrão: mostra **onde** e **quanto**. Para **ver amostras** (ex.: 10 ocorrências), é preciso habilitar o recurso de **revelar amostras** com **role e permissões dedicadas** (ver a folha de segurança) — decisão consciente de privacidade.

### 5.6 Ciclo de vida do finding

| Estado/ação | Descrição |
|---|---|
| **Novo/Ativo** | Recém-gerado |
| **Arquivado** | Você **arquivou** (revisou/aceitou) |
| **Suprimido** | Coberto por **regra de supressão**: não aparece (mas existe) |
| **Retenção** | Findings ficam no Macie por ~90 dias; para histórico, use o **repositório de resultados** e/ou **Security Hub** |

## 6. Regras de supressão (suppression rules)

Filtram **automaticamente** findings **esperados**:

```bash
aws macie2 create-findings-filter \
  --name suprimir-buckets-de-teste --action ARCHIVE \
  --finding-criteria '{"criterion":{"resourcesAffected.s3Bucket.name":{"eq":["dados-sinteticos-teste"]}}}'
```

| Uso | Exemplo |
|---|---|
| **Buckets sabidamente de teste** | Suprimir findings do bucket sintético |
| **Findings de severidade baixa** de tipo aceito | Ex.: e-mails corporativos em logs, aprovados pelo DPO |
| **Findings já tratados** | Evitar reabrir o mesmo achado |

Princípio: **suprimir é decisão de risco**: documente **quem aprovou**, **por quê** e **até quando**.

## 7. Boas práticas de qualidade de detecção

1. **Meça**: taxa de **falsos positivos** por identificador (amostre findings e verifique).
2. **Contextualize**: keywords e distância nos custom identifiers.
3. **Combine** com **allow lists** de dados de teste.
4. **Revise** managed identifiers com muito ruído (EXCLUDE) e **reforce** os essenciais (INCLUDE).
5. **Validação pós-detecção**: Lambda para checar dígito verificador (CPF/CNPJ) antes de abrir ticket.
6. **Reprocessamento planejado**: ao mudar identificadores, **novo job** nos buckets relevantes.
7. **Taxonomia interna**: mapear tipos de finding → **classificação da empresa** (Público, Interno, Confidencial, Restrito) e **dono** do dado.

## 8. Mapeando findings para ações

| Finding | Ação típica |
|---|---|
| `S3BucketPublic` + dado sensível | **Incidente**: reativar Block Public Access, revisar logs de acesso, avaliar notificação regulatória |
| `S3BucketSharedExternally` inesperado | Revisar a bucket policy/ACL, remover a conta externa |
| `S3BucketEncryptionDisabled` | Reaplicar criptografia padrão (SSE-KMS) |
| `Credentials` | **Rotacionar** a credencial imediatamente; remover o arquivo; investigar uso (CloudTrail) |
| `Financial` em bucket não autorizado | Mover para ambiente PCI, aplicar controles, avaliar retenção |
| `Personal` em bucket sem base legal | Anonimizar/remover; revisar o fluxo de dados (LGPD) |
| `CustomIdentifier` (matrícula, contrato) | Tratar conforme a classificação interna |

## 9. Erros comuns

- **Regex frouxa** (`\d{11}`) → milhares de falsos positivos.
- **Keywords obrigatórias demais** → falsos negativos (CSV sem cabeçalho).
- **Allow list ampla** que esconde dados reais.
- **Supressão sem governança**.
- **Alterar identificadores e esperar reclassificação automática** (é preciso **novo job**).
- **Assumir validação de dígito verificador** em custom identifiers.
- **Ignorar a localização** e abrir ticket genérico (“tem PII no bucket X”) sem apontar o arquivo/coluna.
- **Tratar `Credentials` como PII comum**: é **prioridade máxima** (rotação imediata).
- **Dados reais em testes de regex.**

## 10. Troubleshooting

| Sintoma | Causa provável | Ação |
|---|---|---|
| CPFs conhecidos não detectados | Sem managed identifier para o país/formato, regex incompatível, keyword ausente, sem pontuação | Custom identifier com variações; testar com `test-custom-data-identifier` |
| Falso positivo em massa | Regex ampla, números sintéticos | Keywords, ignore words, allow list, ajuste do identificador |
| Custom identifier “não faz efeito” | Job anterior à criação do identificador | Novo job incluindo o identificador |
| Finding sem localização útil | Formato complexo (arquivo compactado, binário) | Analisar o membro indicado; extrair/converter para depurar |
| Allow list ignorada | Não associada ao job/automática; formato de lista incorreto; maiúsculas/espaços | Associar; corrigir o arquivo (um texto por linha) |
| Policy finding sem “quem” | Evento fora da janela do CloudTrail/região | Conferir trilha e retenção |
| Findings duplicados | Jobs sobrepostos | Consolidar escopos; usar filtros |

## 11. Resumo rápido

- **Managed identifiers** (prontos, por categoria e país) + **custom identifiers** (regex, keywords, distância, ignore words, severidade) + **allow lists** (texto/regex para ignorar).
- Custom identifiers **não validam dígito verificador**; teste com `test-custom-data-identifier`; mudanças exigem **novo job**.
- **Findings**: **policy** (postura do bucket, com quem/quando via CloudTrail) e **sensitive data** (Personal, Financial, Credentials, CustomIdentifier, Multiple), com **severidade** por tipo/quantidade/diversidade e **localização** exata.
- **Supressão** e **arquivamento** reduzem ruído — mas exigem governança.
- **Credenciais** → rotação imediata; **bucket público + dado sensível** → incidente.
- Retenção de findings ~**90 dias**: use **repositório de resultados**/**Security Hub** para histórico.

## 🧩 Quiz de Fixação

1. Qual a diferença entre managed e custom data identifiers?
2. Para que servem `keywords` e `maximumMatchDistance` em um custom identifier?
3. O que uma allow list faz e qual o risco de usá-la mal?
4. Que informações a localização de um finding fornece?
5. O que fazer ao encontrar um finding do tipo Credentials?
6. Alterei um custom identifier. Os objetos já analisados serão reclassificados?

**Respostas:**

1. Managed são detectores prontos mantidos pela AWS; custom são detectores seus, definidos por regex, palavras-chave e proximidade, para formatos específicos do negócio.
2. Exigem que determinadas palavras apareçam perto do trecho que casa com a regex (até a distância máxima), reduzindo falsos positivos de números soltos.
3. Faz o Macie ignorar textos/padrões conhecidos (como dados de teste); se for ampla demais, esconde dados sensíveis reais.
4. Onde está o dado: linha/coluna, caminho JSON, planilha, página ou registro, além do caminho dentro de arquivos compactados.
5. Rotacionar a credencial imediatamente, remover o arquivo e investigar o uso pelo CloudTrail.
6. Não; é preciso criar um novo job para reprocessar os objetos com o identificador atualizado.
7. Porque suprimir é aceitar risco: sem registro de quem aprovou, por quê e até quando, achados reais podem ficar escondidos.
