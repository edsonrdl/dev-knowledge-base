### 1.1.1.1. O que é Amazon Macie — descoberta de dados sensíveis no S3, inventário de buckets, identificadores gerenciados e personalizados, findings e quando usar Macie

> [!warning] Aviso
> Quantidade de identificadores gerenciados, formatos suportados, preços, quotas e nomes de tipos de finding abaixo são **de memória e mudam**. **Confirme na documentação do Amazon Macie e na página de preços.** Comandos e JSONs são ilustrativos e **não foram executados**. Dados pessoais citados são **exemplos fictícios**; nunca use dados reais em testes de classificação sem autorização.

## 1. O problema que o Macie resolve

Empresas guardam **petabytes no S3**: backups, exportações de banco, logs, planilhas, PDFs de clientes, dumps de suporte. Com o tempo ninguém sabe **o que existe** em cada bucket. Perguntas incômodas surgem — normalmente tarde demais, durante uma auditoria ou um incidente:

- **Onde** estão os CPFs, cartões de crédito, e-mails e prontuários que a LGPD/GDPR/PCI-DSS/HIPAA nos obriga a proteger?
- Algum bucket com **dados sensíveis** está **público** ou **compartilhado com outra conta**?
- Alguém colocou **chaves de acesso ou senhas** num arquivo de configuração esquecido?
- Os buckets que **deveriam** estar criptografados e privados realmente estão?
- Como **provar** a um auditor que você sabe onde estão os dados pessoais?

Procurar isso manualmente (amostrar arquivos, escrever scripts de regex, abrir PDFs) **não escala**. O **Amazon Macie** é o serviço gerenciado de **segurança e privacidade de dados** que usa **aprendizado de máquina e correspondência de padrões** para **descobrir, classificar e proteger dados sensíveis no Amazon S3**.

> [!info] Em uma frase
> **Macie = “onde estão meus dados sensíveis no S3 e quão bem protegidos estão os buckets que os guardam?”**

## 2. As duas capacidades centrais

```
                         ┌───────────────────────────── Amazon Macie ─────────────────────────────┐
   Buckets S3  ─────────▶│ 1) INVENTÁRIO e POSTURA dos buckets  → policy findings                 │
 (da conta/organização)  │    (público? criptografado? compartilhado? replicado externamente?)    │
                         │ 2) DESCOBERTA de DADOS SENSÍVEIS nos objetos → sensitive data findings │
                         │    (PII, financeiro, credenciais, identificadores customizados)        │
                         └──────────────┬───────────────────────────────┬─────────────────────────┘
                                        ▼                               ▼
                               Console / API / Dashboards        EventBridge • Security Hub • S3 (resultados)
```

| Capacidade | O que faz | Resultado |
|---|---|---|
| **Inventário e avaliação de segurança de buckets** | Mantém um **inventário contínuo** dos buckets S3 e avalia **configurações** (acesso público, criptografia, compartilhamento, replicação) | **Policy findings** + estatísticas por bucket |
| **Descoberta de dados sensíveis** | **Inspeciona o conteúdo** dos objetos, detecta tipos de dados sensíveis | **Sensitive data findings** com **localização** do dado |

Ponto importante: o Macie **só trabalha com S3** (de memória, confirmar escopo atual). Dados sensíveis em RDS, DynamoDB, EBS ou discos de EC2 **não** são varridos por ele — para isso exporte para S3 ou use outras ferramentas.

## 3. Conceitos fundamentais

| Termo | Significado |
|---|---|
| **Managed data identifier** | Detector **pronto**, mantido pela AWS, para um tipo de dado sensível (número de cartão, CPF, passaporte, chave de acesso AWS, etc.) |
| **Custom data identifier** | Detector **seu**: **expressão regular** + palavras-chave + distância de proximidade, para dados específicos do negócio (código de cliente, matrícula) |
| **Allow list** | Lista de **textos ou regex a ignorar** (e-mails de teste, números de exemplo) para reduzir falsos positivos |
| **Discovery job** | Execução **configurada por você** (única ou periódica) para inspecionar **conjuntos específicos** de buckets/objetos |
| **Automated sensitive data discovery** | Descoberta **contínua e automática**, por **amostragem**, em toda a conta/organização, sem configurar jobs |
| **Finding** | Achado: **policy** (postura do bucket) ou **sensitive data** (dado sensível dentro do objeto) |
| **Sensitivity score** | Pontuação de sensibilidade por bucket (de memória; resume o risco com base nos dados detectados) |
| **Administrator account / member** | Modelo **multi-conta**: uma conta administradora gerencia o Macie das contas-membro (via Organizations) |
| **Classification results repository** | **Bucket S3 seu**, criptografado com **KMS**, onde são armazenados os **resultados detalhados** da descoberta |

### 3.1 Categorias de dados sensíveis (managed data identifiers)

| Categoria | Exemplos |
|---|---|
| **Credenciais** | Chaves de acesso AWS (ID + secret), chaves privadas (PEM/SSH), tokens e credenciais de serviços comuns |
| **Informações financeiras** | Números de **cartão de crédito**, dados de conta bancária, IBAN/SWIFT (de memória) |
| **Informações pessoais (PII)** | Nomes, endereços, e-mails, telefones, **datas de nascimento**, **números de documentos** (passaporte, CNH, documentos fiscais por país) |
| **Informações de saúde (PHI)** | Códigos de diagnóstico, números de seguro saúde, identificadores de pacientes (por país) |
| **Customizados** | O que **você** definir por regex |

A lista é **extensa e regionalizada** (há identificadores por país); confira se há detector para **documentos brasileiros** (CPF, CNPJ) — se não houver, crie um **custom data identifier**.

## 4. Como o Macie inspeciona

1. **Enumera** buckets e objetos (via inventário e APIs do S3; **não exige** que você copie dados).
2. **Lê** os objetos (com a **role vinculada ao serviço** do Macie) e **extrai texto** conforme o formato.
3. **Aplica** managed/custom data identifiers e allow lists.
4. **Registra** achados com **localização exata** (arquivo, linha, coluna, página, caminho JSON).
5. **Não guarda** os dados sensíveis encontrados; guarda **metadados e localização** (e, opcionalmente, **amostras redigidas** sob configuração explícita — ver folha de segurança).

### 4.1 Formatos suportados (de memória — confirmar)

| Tipo | Exemplos |
|---|---|
| **Texto/estruturado** | `.txt`, `.csv`, `.tsv`, `.json`, `.jsonl`, `.xml` |
| **Colunares/analíticos** | **Parquet**, **Avro**, ORC (confirmar) |
| **Documentos** | **PDF**, Word (`.docx`), Excel (`.xlsx`), PowerPoint |
| **Compactados** | `.zip`, `.gz`, `.tar` (descompacta e inspeciona o conteúdo) |
| **Não suportados** | Imagens/áudio/vídeo (sem OCR; confirmar), formatos binários proprietários, objetos **criptografados com SSE-C** ou chaves que o Macie não pode usar |

### 4.2 Criptografia do objeto e acesso do Macie

| Criptografia do objeto | O Macie consegue inspecionar? |
|---|---|
| **Sem criptografia / SSE-S3** | Sim |
| **SSE-KMS com chave gerenciada pela AWS (`aws/s3`)** | **Sim**, porque a role pode usar a chave (confirmar) |
| **SSE-KMS com CMK sua** | **Só** se a **key policy** permitir o uso pela role do Macie |
| **SSE-C (chave do cliente)** | **Não** (o Macie não possui a chave) |
| **Criptografia no cliente (client-side)** | **Não consegue** ler o conteúdo útil |

Consequência: um bucket “não inspecionável” aparece com status de **classificação não suportada/erro de permissão** — é um **ponto cego** que deve ser corrigido, não ignorado.

## 5. Policy findings: a postura dos buckets

O Macie monitora **mudanças e estado** de segurança dos buckets e gera **policy findings** (nomes de memória — confirmar):

| Tipo de finding | Significado |
|---|---|
| `Policy:IAMUser/S3BlockPublicAccessDisabled` | O **Block Public Access** foi desativado |
| `Policy:IAMUser/S3BucketPublic` | Bucket **público** por ACL/policy |
| `Policy:IAMUser/S3BucketEncryptionDisabled` | Criptografia padrão **desabilitada** |
| `Policy:IAMUser/S3BucketReplicatedExternally` | Replicação para conta **fora da organização** |
| `Policy:IAMUser/S3BucketSharedExternally` | Compartilhado com conta **externa** |
| `Policy:IAMUser/S3BucketSharedWithCloudFront` | Compartilhado com uma **OAI/OAC do CloudFront** |

Cada um tem **severidade** (geralmente Low/Medium/High) e inclui **quem** fez a mudança (principal), **quando** e **de onde** (baseado em **CloudTrail**). Isso transforma o Macie também em **detector de desvio de configuração** de buckets.

## 6. Sensitive data findings: o que há dentro dos objetos

Exemplos de tipos (de memória — confirmar):

| Tipo | Quando ocorre |
|---|---|
| `SensitiveData:S3Object/Personal` | PII encontrada |
| `SensitiveData:S3Object/Financial` | Dados financeiros |
| `SensitiveData:S3Object/Credentials` | Credenciais/chaves |
| `SensitiveData:S3Object/CustomIdentifier` | Casou com custom data identifier |
| `SensitiveData:S3Object/Multiple` | **Vários** tipos no mesmo objeto |

O finding traz: **bucket e chave do objeto**, **tipo(s) detectado(s)**, **contagem de ocorrências**, **severidade** (calculada a partir do tipo e da quantidade) e **localização** (linhas, colunas, células, páginas, registros). A severidade de dado sensível costuma subir com a **diversidade e a quantidade** de ocorrências.

### 6.1 Exemplo de finding (resumido, fictício)

```json
{
  "type": "SensitiveData:S3Object/Financial",
  "severity": { "description": "High", "score": 3 },
  "resourcesAffected": {
    "s3Bucket": { "name": "exportacoes-financeiro" },
    "s3Object": { "key": "2026/10/clientes.csv", "publicAccess": false }
  },
  "classificationDetails": {
    "result": {
      "sensitiveData": [
        { "category": "FINANCIAL_INFORMATION",
          "detections": [ { "type": "CREDIT_CARD_NUMBER", "count": 412 } ] }
      ],
      "status": { "code": "COMPLETE" }
    }
  }
}
```

## 7. Quando usar o Macie (e quando não)

| Cenário | Macie? |
|---|---|
| Descobrir **PII/PCI/credenciais em S3** em escala | **Sim** — caso de uso principal |
| Provar a auditores o **mapa de dados sensíveis** em S3 | **Sim** (relatórios, resultados, dashboards) |
| Monitorar **buckets públicos/compartilhados** | **Sim** (policy findings); complemente com **Block Public Access**, **Config**, **IAM Access Analyzer** |
| Proteger/anonimizar dados em **RDS/DynamoDB** | **Não** (exporte para S3 ou use ferramentas do banco) |
| Detectar **ameaças** (atividade maliciosa, credenciais comprometidas) | **GuardDuty** (não é o objetivo do Macie) |
| Achar **vulnerabilidades** em EC2/containers/Lambda | **Inspector** |
| **Bloquear** upload de dados sensíveis em tempo real | **Não** — o Macie **detecta depois**; para prevenção use controles de aplicação, S3 policies, DLP próprio |
| **Mascarar/tokenizar** dados | **Não** — só detecta; remediação é sua (Lambda, Glue DataBrew, etc.) |
| Classificar **imagens/áudio** | **Não** (sem OCR/ASR) |

### 7.1 Macie vs GuardDuty vs Inspector (confronto clássico)

| Serviço | Pergunta que responde | Alvo |
|---|---|---|
| **Macie** | “**Que dados sensíveis** tenho e **como estão protegidos**?” | Conteúdo e configuração de **S3** |
| **GuardDuty** | “Há **atividade suspeita** na minha conta?” | Logs (CloudTrail, VPC Flow, DNS), S3 data events, EKS, malware |
| **Inspector** | “Há **vulnerabilidades** nos meus workloads?” | EC2, ECR, Lambda |

Na prova SAA, “**PII em S3**” → **Macie**.

## 8. Primeiros passos (visão geral)

```bash
# Habilitar o Macie na região (ilustrativo)
aws macie2 enable-macie

# Estado atual e inventário de buckets
aws macie2 get-macie-session
aws macie2 describe-buckets --max-results 20

# Habilitar a descoberta automatizada (ilustrativo; confirmar parâmetros)
aws macie2 update-automated-discovery-configuration --status ENABLED

# Listar findings
aws macie2 list-findings --max-results 20
aws macie2 get-findings --finding-ids <id>
```

Fluxo recomendado:

1. **Habilitar** o Macie (e, se multi-conta, designar o **administrador delegado**).
2. Configurar o **repositório de resultados** (bucket S3 + KMS).
3. Ligar a **descoberta automatizada** para ter visibilidade ampla.
4. Criar **jobs** direcionados para buckets críticos/novos.
5. Criar **custom data identifiers** e **allow lists** para o contexto local.
6. Integrar a **EventBridge/Security Hub** e definir **respostas** (ticket, bloqueio de acesso, criptografia).

## 9. Erros comuns

- **Achar que o Macie protege ativamente**: ele **detecta e alerta**, não bloqueia nem remove dados.
- **Esquecer que é regional**: habilitar numa região **não** cobre as outras; habilite em **todas** onde há buckets.
- **Ignorar objetos que o Macie não consegue ler** (SSE-C, KMS sem permissão): viram **pontos cegos**.
- **Esperar cobertura de dados fora do S3**.
- **Não ajustar para o contexto local**: sem custom identifiers (CPF/CNPJ, matrícula) e **allow lists**, aparecem falsos negativos e falsos positivos.
- **Varrer tudo sempre**: custo alto sem necessidade (ver folha de custos).
- **Sem processo de resposta**: findings acumulam e ninguém age.
- **Guardar o repositório de resultados num bucket sem KMS** ou acessível demais — os resultados em si descrevem onde estão os dados sensíveis.

## 10. Troubleshooting inicial

| Sintoma | Causas prováveis | Ações |
|---|---|---|
| Bucket aparece como “não classificável” | SSE-C, KMS sem permissão, formato não suportado, bucket vazio/bloqueado por policy | Revisar a criptografia e a bucket/key policy; permitir a role do Macie |
| Nenhum finding apesar de dados sensíveis conhecidos | Identificador inexistente para o formato local; amostragem na descoberta automatizada; objeto fora do escopo do job | Criar **custom identifier**; rodar **job dedicado** sem amostragem total |
| Muitos falsos positivos | Dados de teste/exemplo, números aleatórios que casam com padrões | **Allow lists** e ajuste de **máxima distância/palavras-chave** |
| Policy finding inesperado | Alguém alterou o bucket | Usar o **CloudTrail** (principal e horário) e reverter |
| Macie “ligado” e sem resultados | Região errada, sem jobs e automação desabilitada | Habilitar descoberta automatizada ou criar jobs |
| Não vê os buckets de outras contas | Sem integração multi-conta | Configurar **Organizations/administrador delegado** |

## 11. Resumo rápido

- **Macie** descobre e classifica **dados sensíveis no S3** (PII, financeiro, credenciais, customizados) e avalia a **postura de segurança dos buckets**.
- **Dois tipos de finding**: **policy** (bucket público, sem criptografia, compartilhado/replicado externamente) e **sensitive data** (conteúdo do objeto, com localização).
- **Managed data identifiers** (prontos) + **custom data identifiers** (regex/keywords) + **allow lists** (ignorar).
- **Descoberta automatizada** (amostragem contínua) **e jobs** (escopo definido, única ou recorrente).
- **Só S3**; **regional**; detecta, **não bloqueia nem mascara**; objetos **SSE-C/client-side** não são lidos.
- Saídas: **console/API**, **EventBridge**, **Security Hub** e **resultados no S3 (KMS)**.
- Prova: “**PII em S3**” → **Macie**; ameaças → **GuardDuty**; vulnerabilidades → **Inspector**.

## 🧩 Quiz de Fixação

1. Quais as duas capacidades centrais do Macie?
2. Qual a diferença entre policy findings e sensitive data findings?
3. Para que servem custom data identifiers e allow lists?
4. Por que objetos com SSE-C são um ponto cego?
5. O Macie bloqueia o upload de dados sensíveis? Justifique.
6. Dados sensíveis em RDS podem ser varridos pelo Macie?
7. Como o Macie se diferencia de GuardDuty e Inspector?

**Respostas:**

1. Inventário e avaliação de segurança dos buckets S3 (policy findings) e descoberta de dados sensíveis nos objetos (sensitive data findings).
2. Policy findings tratam da configuração/postura do bucket (público, sem criptografia, compartilhado externamente); sensitive data findings indicam dados sensíveis encontrados dentro dos objetos, com localização.
3. Custom identifiers detectam dados específicos do negócio por regex, palavras-chave e proximidade; allow lists ignoram textos/padrões conhecidos para reduzir falsos positivos.
4. Porque o Macie não possui a chave fornecida pelo cliente e não consegue ler o conteúdo para classificá-lo.
5. Não; ele detecta e alerta depois do fato. Prevenção e remediação (bloqueio, mascaramento) dependem de outros controles e automações.
6. Não diretamente; o Macie atua apenas em S3, então seria preciso exportar os dados para S3 ou usar outras ferramentas.
7. Macie olha dados sensíveis e postura de buckets S3; GuardDuty detecta atividade/ameaças a partir de logs; Inspector encontra vulnerabilidades em EC2, ECR e Lambda.
