### 4.2.1.5. Tags para alocação de custos — tags definidas pelo usuário e geradas pela AWS, ativação, estratégia de tagging, tag policies e Cost Categories

> [!warning] Aviso
> Prazos de propagação, limites de tags por recurso e comportamento por serviço **variam**; os números abaixo são de memória e didáticos. **Confirme na documentação de tags de alocação de custo e na documentação de cada serviço.** Comandos e políticas são ilustrativos e não foram executados. Políticas que **bloqueiam** criação de recursos sem tag precisam ser testadas em ambiente seguro para não travar equipes.

## 1. Por que tags de custo

A fatura da AWS mostra **quanto** você gastou por serviço e conta, mas não **quem** (qual equipe, produto, cliente, ambiente) gerou o gasto. Sem essa resposta, ninguém é responsável pelo custo, e a otimização vira "briga de todos contra todos". As **tags** resolvem isso: são **rótulos chave-valor** anexados a recursos que depois **aparecem nos relatórios de custo**, permitindo **showback** (mostrar o custo a cada equipe) e **chargeback** (cobrar internamente).

```
Recurso EC2 ── tags: {projeto=checkout, ambiente=prod, dono=time-pagamentos, centro-custo=CC-1042}
        │
        ▼  (tags ATIVADAS para alocação de custos)
 Cost Explorer / Budgets / CUR  →  "Custo do projeto checkout em prod = US$ 12.480"
```

## 2. Dois tipos de tags de alocação

| Tipo | Quem cria | Prefixo | Exemplos |
|---|---|---|---|
| **User-defined tags** | Você (engenharia/FinOps) | Sem prefixo especial (aparece como `user:` nos relatórios) | `projeto`, `ambiente`, `dono`, `centro-custo`, `cliente` |
| **AWS-generated tags** | A AWS, automaticamente (a ativar) | `aws:` | `aws:createdBy` (quem criou o recurso, em alguns serviços), `aws:cloudformation:stack-name` (pilha que criou o recurso) |

As **AWS-generated** são úteis para rastrear a origem do recurso (por exemplo, a pilha do CloudFormation), mas **não substituem** uma boa estratégia de tags próprias. Tags com prefixo `aws:` **não podem ser criadas ou editadas por você** e **não contam** para o limite de tags do recurso.

## 3. Ativação: o passo que todos esquecem

Marcar um recurso com uma tag **não** faz a tag aparecer nos relatórios. É preciso **ativá-la** como **cost allocation tag** no console de Billing (na conta de gerenciamento, em Organizations).

```
1. Marca o recurso (tag projeto=checkout)
2. A chave 'projeto' aparece em Billing → Cost allocation tags (pode levar até ~24 h)
3. Você ATIVA a chave
4. A partir da ativação (até ~24 h para refletir), custos passam a ser agrupáveis por 'projeto'
```

Pontos cruciais:

- **Não é retroativo:** a tag só aparece nos dados de custo **a partir da ativação**. Custos anteriores **não** são re-etiquetados (embora a AWS tenha introduzido, em alguns cenários, **backfill de até 12 meses** para tags recém-ativadas — verifique a documentação vigente).
- A ativação é **por chave** (a chave `projeto`, com todos os valores).
- Apenas a **conta de gerenciamento** (ou conta isolada) ativa tags de alocação para toda a organização.
- Tags **distinguem maiúsculas de minúsculas**: `Projeto` e `projeto` são chaves diferentes (e geram duas colunas!).

```bash
# Ativa chaves de tags de alocação (ilustrativo; via API de Cost Explorer)
aws ce update-cost-allocation-tags-status --cost-allocation-tags-status \
  TagKey=projeto,Status=Active TagKey=ambiente,Status=Active TagKey=dono,Status=Active

# Lista as chaves e seu status
aws ce list-cost-allocation-tags --status Active
```

## 4. Como as tags aparecem na análise

| Ferramenta | Uso |
|---|---|
| **Cost Explorer** | **Group by → Tag** e **Filter → Tag**; relatórios salvos por tag |
| **Budgets** | Filtro por **TagKeyValue** (orçamento por projeto/equipe) |
| **CUR / Data Exports** | Colunas `resource_tags_user_<chave>` (uma coluna por chave ativa) |
| **Cost Anomaly Detection** | Monitores baseados em tags |
| **Cost Categories** | Regras que **agrupam** com base em tags |
| **QuickSight/Athena** | Dashboards de custo por equipe/produto |

Itens **sem tag** aparecem como **"No tag key"/vazios**: o tamanho desse grupo é o **indicador de maturidade** da sua governança de tags (meta: o mínimo possível).

## 5. Estratégia de tagging

Boas tags são **poucas, padronizadas e obrigatórias**. Esquema recomendado (adapte):

| Chave | Valores (exemplos) | Finalidade |
|---|---|---|
| **`projeto`** / **`produto`** | `checkout`, `catalogo` | Alocação por produto |
| **`ambiente`** | `prod`, `homolog`, `dev` | Separar custo de produção de não produção |
| **`dono`** / **`time`** | `time-pagamentos` | Responsabilização e contato |
| **`centro-custo`** | `CC-1042` | Integração com contabilidade |
| **`cliente`** (SaaS multi-tenant) | `acme` | Unit economics por cliente |
| **`confidencialidade`** / **`compliance`** | `pii`, `pci` | Governança e segurança |
| **`ciclo-vida`** / **`expira-em`** | `temporario`, `2026-12-31` | Limpeza automática de recursos de laboratório |
| **`gerenciado-por`** | `terraform`, `manual` | Detectar drift e recursos fora do IaC |

Princípios:

1. **Taxonomia única** e documentada (um dicionário de tags), com **nomes em minúsculas** e padrão de separador (hífen).
2. **Obrigatórias** (poucas) vs **opcionais**.
3. **Aplicar via IaC** (CloudFormation, Terraform, CDK): `default_tags` no provider do Terraform e `Tags` globais no CDK.
4. **Herança**: tags no nível da pilha propagam para os recursos suportados.
5. **Automação** para corrigir: Lambda/Config que etiqueta ou notifica recursos fora do padrão.
6. **Valores controlados** (lista de valores permitidos) para evitar `Checkout`, `checkout`, `check-out`.

Exemplo no Terraform (ilustrativo):

```hcl
provider "aws" {
  region = "us-east-1"
  default_tags {
    tags = {
      projeto      = "checkout"
      ambiente     = "prod"
      dono         = "time-pagamentos"
      "centro-custo" = "CC-1042"
      "gerenciado-por" = "terraform"
    }
  }
}
```

## 6. Aplicando e auditando tags

| Ferramenta | Função |
|---|---|
| **Tag Editor** (Resource Groups & Tag Editor) | Buscar recursos (por região e tipo) e **adicionar/editar tags em massa** |
| **Resource Groups** | Agrupar recursos por tags |
| **Resource Groups Tagging API** | API para ler/gravar tags entre serviços (`tag:GetResources`, `tag:TagResources`) |
| **AWS Config** | Regra **`required-tags`** para detectar recursos sem tags obrigatórias |
| **Tag Policies** (Organizations) | Padronizar **chaves e valores permitidos** e verificar conformidade |
| **SCP / IAM com `aws:RequestTag` / `aws:TagKeys`** | **Exigir** tags na criação (bloqueando quando ausentes) |
| **Cost Explorer** (itens sem tag) | Medir a lacuna |

```bash
# Etiqueta em massa vários recursos (ilustrativo)
aws resourcegroupstaggingapi tag-resources \
  --resource-arn-list arn:aws:ec2:us-east-1:123456789012:instance/i-0abc arn:aws:s3:::meu-bucket \
  --tags projeto=checkout,ambiente=prod

# Recursos sem a tag 'projeto' (ilustrativo)
aws resourcegroupstaggingapi get-resources --tag-filters Key=projeto --resources-per-page 100
```

### 6.1 Tag Policies (padronização)

```json
{
  "tags": {
    "ambiente": {
      "tag_key": { "@@assign": "ambiente" },
      "tag_value": { "@@assign": ["prod", "homolog", "dev"] },
      "enforced_for": { "@@assign": ["ec2:instance", "s3:bucket"] }
    }
  }
}
```

A **tag policy** define **chave com a grafia correta** e **valores permitidos**; com `enforced_for`, impede criar/atualizar recursos com valor inválido (para os tipos suportados).

### 6.2 Exigir tags na criação (SCP)

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Sid": "NegarEC2SemTagProjeto",
    "Effect": "Deny",
    "Action": ["ec2:RunInstances"],
    "Resource": "arn:aws:ec2:*:*:instance/*",
    "Condition": { "Null": { "aws:RequestTag/projeto": "true" } }
  }]
}
```

Isso força que **toda instância nova** tenha a tag `projeto`. **Teste antes**: alguns fluxos (Auto Scaling, EKS, serviços gerenciados) criam recursos de formas que exigem permissões e *launch templates* com tags.

## 7. Limitações e casos difíceis

| Limitação | Como lidar |
|---|---|
| **Nem todo recurso suporta tags**, e nem todo custo é "taggável" (ex.: certos tipos de transferência de dados, suporte, impostos, créditos) | Use **Cost Categories** e regras de rateio por conta |
| **Custos compartilhados** (rede, observabilidade, plataforma) | Defina **regras de rateio proporcional** (por uso, por receita) com Cost Categories/CUR |
| **Tags não retroativas** | Ative cedo; planeje o backfill/reprocessamento |
| **Limite de tags por recurso** (50 para a maioria, menos em alguns) | Escolha poucas tags essenciais |
| **Kubernetes (EKS/ECS)** | Use **split cost allocation data** e tags de pods/tarefas |
| **Recursos criados por serviços gerenciados** (ex.: ENIs de NAT, volumes do EKS) | Propague tags (`propagateTags`, *launch template tags*) |
| **Tags em dados sensíveis** | **Não** coloque PII/segredos em tags (são visíveis amplamente) |
| **Atraso de ativação** | Aguarde até 24 h |

## 8. Cost Categories (complemento poderoso)

As **Cost Categories** permitem **agrupar custos** em categorias de negócio **sem depender 100% de tags**, com **regras**:

| Regra baseada em | Exemplo |
|---|---|
| **Conta** | Contas `1111`, `2222` → "Produto A" |
| **Serviço** | `AWS Support`, `Marketplace` → "Custos compartilhados" |
| **Tag** | `projeto=checkout` → "Pagamentos" |
| **Outra categoria / Região / Tipo de cobrança** | Regras aninhadas |
| **Rateio (split charge rules)** | **Dividir** custos compartilhados proporcionalmente entre categorias (proporcional, fixo ou uniforme) |

Uma categoria vira uma **dimensão** em Cost Explorer, Budgets, CUR e Anomaly Detection, permitindo relatórios por **unidade de negócio** mesmo com tags imperfeitas.

## 9. Processo de implantação (roteiro)

1. **Definir o dicionário de tags** com FinOps, engenharia, segurança e finanças.
2. **Tag Policy** para padronizar chaves/valores.
3. **Ativar** as chaves em Cost allocation tags (cedo!).
4. **IaC com `default_tags`** e módulos que exigem tags.
5. **Config `required-tags`** + dashboard de conformidade.
6. **Remediar** o legado com **Tag Editor** e scripts.
7. **SCPs/IAM** que exigem tags em tipos críticos (depois de testar).
8. **Cost Categories** para custos compartilhados e rateio.
9. **Medir:** % de custo alocado (meta > 90–95%), publicar mensalmente.
10. **Cultura:** showback regular e donos de custo conhecidos.

## 10. Erros comuns

> [!bug] Erros comuns
> 1. **Marcar recursos e esquecer de ativar a tag** em Billing.
> 2. **Achar que a ativação é retroativa.**
> 3. **Chaves inconsistentes** (`Projeto`, `projeto`, `project`) multiplicando colunas e confundindo relatórios.
> 4. **Tags demais**, que ninguém preenche.
> 5. **Não aplicar tags via IaC**, dependendo de etiquetagem manual.
> 6. **Bloquear criação sem tag** sem testar e quebrar pipelines.
> 7. **Colocar dados sensíveis em tags.**
> 8. **Ignorar custos não taggáveis** e compartilhados.
> 9. **Não medir a cobertura** (% de custo sem tag).
> 10. **Não definir donos** para os recursos e para o custo.

## 11. Troubleshooting

| Sintoma | Causa provável | Ação |
|---|---|---|
| Tag não aparece em Cost allocation tags | Nenhum recurso com a tag ainda ou atraso | Verificar o recurso e aguardar até 24 h |
| Cost Explorer sem a tag | Não ativada ou sem dados depois da ativação | Ativar e aguardar; lembrar que não é retroativo |
| Muito custo "sem tag" | Recursos legados, custos não taggáveis | Remediar com Tag Editor; usar Cost Categories |
| Colunas duplicadas no CUR | Chaves com grafias diferentes | Padronizar chaves e remediar |
| Recurso criado sem tag apesar da política | Serviço/caminho não coberto | Rever SCP/Config; propagar tags de launch templates |
| Pilha do CloudFormation sem propagar tags | Tags não definidas na pilha | Definir tags no nível da pilha |

## 12. Resumo rápido

- **Tags de alocação de custos** ligam gasto a **projeto, equipe, ambiente e cliente**; podem ser **definidas pelo usuário** ou **geradas pela AWS (`aws:`)**.
- É preciso **ativar** a chave em **Billing → Cost allocation tags**; **não é retroativo**; **maiúsculas importam**.
- Estratégia: **poucas tags padronizadas e obrigatórias**, aplicadas por **IaC** (`default_tags`).
- Governança: **Tag Policies**, **Config `required-tags`**, **SCP/IAM** (`aws:RequestTag`), **Tag Editor**.
- **Cost Categories** agrupam e **ratearam** custos compartilhados e não taggáveis; meça a **cobertura**.

**Respostas:**

1. As definidas pelo usuário são criadas por você; as geradas pela AWS têm prefixo `aws:` (como `aws:createdBy`) e não podem ser editadas por você.
2. Porque a chave não foi ativada como cost allocation tag em Billing (e leva até ~24 h para refletir).
3. Em geral não; passa a valer após a ativação (com possível backfill limitado, conforme a documentação vigente).
4. Tag Policies, AWS Config `required-tags`, SCP/IAM com `aws:RequestTag`, Tag Editor.
5. Agrupar custos em categorias de negócio e ratear custos compartilhados, mesmo com tags imperfeitas.
6. Porque chaves diferentes (Projeto, projeto) viram colunas e agrupamentos distintos, quebrando relatórios.
7. Porque as tags são amplamente visíveis em relatórios e consoles e não são um local seguro para segredos ou PII.
